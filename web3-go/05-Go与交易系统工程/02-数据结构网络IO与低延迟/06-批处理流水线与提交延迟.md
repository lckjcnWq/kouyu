# 大问题 6：怎样用有界批处理流水线提高吞吐，又不破坏命令顺序与提交承诺？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 批量传输 / 批量持久化 | 多项共用搬运或存储开销，并非把订单变成同一个业务身份。 | B1 仍有自己的请求、intent、结果身份和完整成交明细。 |
| 流水线 | 不同阶段可以同时处理各自手中的工作。 | 解析、提交和投影可重叠，同一本簿的状态裁决仍由有效单写者按序完成。 |
| intent / 载荷摘要 | 绑定订单参数的意图，以及核对原参数是否一致的标记。 | 同身份重试恢复原订单，不同参数要冲突拒绝，不能重复占资。 |
| commandSeq / 受理 ACK | 命令的权威位置，以及命令可恢复的确认。 | 只有耐久日志提交后才可靠受理，不说明已经获得 0.25 BTC。 |
| inflight / 在途窗口 | 已取出但尚未完成交付或确认的工作范围。 | 编码中、提交中、等待响应的对象都计预算，不只算 channel 内元素。 |
| N / B / W | 最大条数、目标最大字节和最长凑批等待。 | 任一先到就触发，第一项入空批启动计时，后来到达不能重置最老等待。 |
| 单项预算 / 字节触发线 | 一份完整结果可用的资源上限，以及普通批次何时停止追加的阈值。 | 超普通 B 的完整结果可走受控单项路径，不能截成两个独立确认的半结果。 |
| 私有工作状态 / 权威状态 | 前者供内部连续试算，后者已有可靠提交依据可对外承诺。 | 后条可依赖前条试算来规划，查询、行情与账务不能偷读未提交工作区。 |
| ResultBatch / AppliedSeq | 每条命令完整结果，以及共同提交的执行进度。 | 从 k+1 到 k+r 的连续结果必须各自完整，提交后才推进可发布水位。 |
| group commit / 原子边界 | 多个结果共用一次有效提交，以及全有或全无的真实存储范围。 | 底层只支持逐条原子，就逐条确认，不能把多次写入口头称为整组原子。 |
| 提交未知 / 内容摘要 | 可能已写入但没拿到响应，以及识别待核实原批次的内容标记。 | 停止依赖结果发布和继续提交，核实原身份与水位，不换批次制造新成交。 |
| AbortIntent / Cancel | 同序关闭意图或撤销已受理订单实际剩余量的命令。 | 超时不能退款，关闭必须挡住迟到原命令，已有成交不能被撤销。 |
| 账务完整批次 / 去重进度 | 共同处理成交与预留处置，并将处理身份、游标和资产一起提交。 | 不能先返还 10 却漏扣 15015，也不能先推进游标再等余额落库。 |
| 吞吐 / 尾延迟 / 恢复预算 | 单位时间完成量、慢请求耗时，以及不确定后可承担的恢复工作。 | 大批次可能省提交次数，却增加等待、内存和一次故障涉及的命令量。 |
| bounded timer / 硬实时 | 有主动等待上限的计时规则，与保证某时刻前必完成的承诺。 | W 只限制凑批，调度和存储仍会拖慢，定时器不提供端到端硬上限。 |

## 把整篇文章压缩成一个故事

甲的 B1 要买 0.25 BTC，账户先预留 15025 USDT，命令日志提交后只回复可靠受理。工程师小周发现每次持久化都有固定成本，于是把连续命令的提交聚合起来，同时让接入、撮合规划和已提交结果的后续处理形成流水线。B1 的身份、意图和参数不变，同一本簿仍由一个有效写者按 commandSeq 裁决，不能因为别人先凑满一批就插队成交。

小周为批次设 N、B、W 三个触发条件，任一先到就提交；低流量也不能永远等满批。写者可在私有区从 k+1 顺序规划到 k+r，但各条完整结果与对应 AppliedSeq 只有在存储真实支持的原子边界提交后，才能依序对外发布。若整组写入响应丢失，即使后面又规划了两条，也必须停住核实，不能先报它们成功；完整单项超普通字节目标时也不能截掉半份成交。

B1 的账户结果最终要一起表达 0.10 BTC 花 6000、0.15 BTC 花 9015，合计支出 15015、得到 0.25 BTC、退回 10，S2 余 0.05。账务事务连同去重和游标共同提交，不能提前把试算币变成可用资产。客户端超时仍查原身份，想终止则走同序关闭或撤单。判断批处理值不值得，要同时看等待、在途字节和恢复量；少几次提交不是已证实的端到端收益，更不能靠提前 ACK 换漂亮数字。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题沿“接入与预留→命令受理→顺序规划→结果提交→账务结转”讨论跨阶段流水线。重点是有界在途量、条数／字节／等待时间三阈值、连续结果的 group commit，以及不同确认边界对应的错误窗口；不展开可靠消息库选型，也不以增加同一交易对写者的方式提高吞吐。

**必要前提：** 沿用 [README 统一基线](README.md)，以下仅列本题新增前提。

- 批次仅聚合传输或持久化工作，不改变命令顺序、幂等身份或完整结果边界；未提交的工作状态与已提交权威状态必须隔离。
- 各阶段分别约束条数、字节和等待时间，在途对象也纳入预算。批量提交只能使用既有存储契约确实支持的原子边界，不能用多次独立写入冒充原子提交，也不在本题重新选型。

```text
接入鉴权与参数检查
    → 账户事务预留并绑定 intent
    → 耐久命令日志提交 commandSeq〔仅受理〕
    → 单写者依提交序号规划连续命令〔未提交工作状态不外露〕
    → 原子提交连续完整 ResultBatch 与对应 AppliedSeq
    → 发布已提交的权威状态、成交及订单结果
    → 账务按完整结果有序幂等结转〔随后确认资金完成〕
```

## 第 1 层：批处理能合并什么，不能合并什么

**面试官：** 这条交易链路里，怎样通过批处理提高吞吐，同时避免把“收到一批订单”误说成“这一批已经成交”？

**面试者：** 我会先分清批量传输、批量持久化和业务裁决。接入可以聚合请求，命令日志可以集中提交，但每笔订单仍保留原来的请求身份、intent 和载荷摘要，只有日志提交后才返回可靠受理。撮合写者按已提交的 commandSeq 逐条规划，不能为了凑批把后来的订单提前，也不能并行修改同一订单簿。连续规划出的完整结果可以一起提交，但必须同时提交对应的 AppliedSeq，再发布权威状态和结果。这样流水线重叠的是不同阶段的工作，不是改变同一交易对的裁决顺序。B1 的受理确认只说明命令可恢复，不能据此宣称已经买到 0.25 BTC，更不能直接把预留的 15025 USDT 变成成交支出。

## 第 2 层：流水线重叠之后，怎样限制在途状态

**面试官：** 你说不同阶段可以重叠。如果结果提交比命令受理慢，前面的阶段会不断领先；用几个带缓冲的 channel 就算有界了吗？

**面试者：** 不算。channel 容量只限制元素数量，同样一百个结果的字节数和成交条目数可能差很多。我会为每个阶段限制条数、累计字节和最老项年龄，并把当前正在编码、提交和等待确认的对象计入在途预算。记录至少带 commandSeq、intent、估算或实际字节数、入队时间和阶段状态；跨阶段交付的是不可变记录，缓冲区在接收方完成前不能复用。结果提交积压时，写者停止扩大未提交工作区，命令读取停止前推，准入再按容量收紧。已经受理的命令留在耐久日志等待，不能丢掉来伪造低延迟；已经预留却尚未明确受理的 intent 进入恢复流程，也不能因为 channel 满了就私自释放资金。

## 第 3 层：条数、字节与等待时间怎样共同触发提交

**面试官：** 上一答限制了队列大小，却没解决低流量时一直凑不满批次的问题。三个阈值具体怎样设置，超大结果又怎么办？

**面试者：** 我会设置最大条数 N、目标最大字节 B、最长凑批等待 W，任一条件先到就提交；第一项进入空批次时启动计时，后来不断来新项不能重置最老项的等待时间。追加下一项会超过 B 时先提交当前批，不能先超量积压再检查。这里的字节触发线与进程硬内存上限不是同一回事：一个完整 ResultBatch 不能为了塞进批次被拆成两个可独立确认的业务结果。单项结果必须有可证明的资源预算；超过普通批次目标但仍在单项预算内的，走有界单项提交并暂停扩张，不能截断成交。无法维持预算时要停止接纳或推进，保留已受理义务。W 只限制主动凑批等待，Go 调度、排队和持久化仍可能更慢，所以 bounded timer 不等于硬实时承诺。

## 第 4 层：连续结果怎样 group commit 而不提前外露

**面试官：** 你允许多个完整 ResultBatch 一起提交。但后一条命令依赖前一条的订单簿变化，前一条还没提交时，后一条到底依据什么规划？

**面试者：** 写者可以维护不对外可见的工作状态。假设权威 AppliedSeq 是 k，就在有界工作区依次规划 k+1 到 k+r；后一条看到前面命令的规划结果，但查询、行情和账务都不能读这份工作状态。每条命令形成独立、不可变的 ResultBatch，保留原 commandSeq、成交身份和订单版本。提交时把这些连续完整结果与 AppliedSeq=k+r 放在同一个原子边界内，成功后才依序发布新的权威状态与结果。若底层只支持逐条原子提交，就逐条推进，不能口头宣称整组原子。批次只是摊薄提交开销，不改变命令身份、时间优先依据或完整结果边界，也不能在提交开始时就发出“成交已确定”的 ACK。

## 第 5 层：提交超时后，为什么不能继续放行后续结果

**面试官：** 上一答在提交成功后才发布。现在 k+1 到 k+r 的提交调用超时了，而工作区已经规划到 k+r+2，能先发后面两条的结果吗？

**面试者：** 不能。超时只说明调用者没有拿到明确结果，不代表整组失败；后两条又依赖这组状态，外露它们会把不确定性变成已经承诺的事实。我会暂停该写者的后续依赖结果发布和继续提交，保留待核实的序号范围、批次身份与内容摘要，再通过既有耐久边界确认结果和 AppliedSeq。若确认整组已提交，就恢复权威状态并补发；确认未提交，才从最后已提交位置重新规划或重试原批次，身份不能改变；仍不能确认就保持停顿。若发现结果与水位不一致，应按存储契约被破坏处理，不能猜一个位置继续跑。接管还必须隔离旧写者，避免旧提交迟到。工作区可以领先权威状态，但绝不能领先对外承诺。

## 第 6 层：凑批与提交期间超时，怎样保留原请求身份

**面试官：** 你让不确定时暂停，客户端可能等不及而重试，账户里也还预留着钱。怎样既避免重复入队，又不把预留永远卡住？

**面试者：** 客户端用原请求标识和 intent 查询、重试，服务端核对载荷摘要，相同身份相同载荷返回原受理位置或处理状态，不再形成第二笔有效订单；相同身份不同载荷则拒绝。请求等待超时、连接断开和批次等待结束，都不是释放资金的依据。对于预留后尚未明确受理的意图，恢复者继续核实；若需要终止，提交关联原 intent 的 AbortIntent，让它与可能迟到的原命令在同一日志中裁决。已经受理或部分成交的订单则用 Cancel 裁决实际剩余量。只有耐久结果明确了不再承担的义务，账务才能幂等释放对应预留。不能把“当前查询没找到”当成终止，因为原命令仍可能在途；批处理也不能给重试换一个排序身份。

## 第 7 层：账务批量结转为何不能消费规划结果

**面试官：** 上一答要等裁决结果才释放预留。如果账务为了赶上流水线，提前消费 B1 的规划结果，只把真正记账延迟到批次末尾，是否可行？

**面试者：** 可以预取不影响业务的元数据，但不能用未提交规划结果授予可用资产、放行新交易或形成可见资金结论。B1 的完整耐久结果应同时表达两笔成交：0.10 BTC 按 60000 成交为 6000 USDT，0.15 BTC 按 60100 成交为 9015 USDT，以及订单与预留义务的变化。账务校验完整性后，在约定顺序内以稳定结果身份去重，将分录、余额变化和消费进度放进同一事务：买方增加 0.25 BTC，支出 15015 USDT，原预留中的 10 USDT 返还，卖方按成交结转；S2 余量为 0.05 BTC。事务失败就重试原结果，不能只释放 10 却漏掉支出，或因收到半个结果就先记第一笔；消费进度也不能在余额事务之外提前推进，否则崩溃恢复会永久跳过尚未入账的结果。批量结转不缩小任何一笔结果的完整性要求。

## 第 8 层：怎样判断吞吐收益是否值得新增等待与错误窗口

**面试官：** 你禁止账务提前放行，因此流水线可能仍有积压。怎样判断增大批次是在提高效率，而不是把提交延迟和恢复风险藏起来？

**面试者：** 我会按同一请求身份记录接入、预留、日志提交、开始规划、结果提交、发布和账务完成时刻，分别看阶段排队、凑批、执行与提交耗时，再看端到端尾延迟。低流量通常由 W 触发，高流量可能由 N 或 B 触发；增大阈值可能提高单位提交吞吐，也会增加等待、在途内存和一次不确定提交涉及的命令数。要同时观察最老未处理命令年龄、未提交工作区大小、已受理但未裁决数量，以及账务落后量，不能只看每秒提交次数。验证时固定相同交易与耐久承诺，分别推演低流量、突发和提交超时：若吞吐数字变好只是因为更早 ACK、漏算等待或延后资金义务，就不是可比较的优化。阈值要服从延迟和恢复预算，而不是追求最大批次。

## 本题收束

- **机制：** 流水线允许不同阶段重叠，但每交易对仍按已提交命令序号裁决；各阶段以条数、字节和最老等待约束在途工作，连续规划结果只能在有效原子边界内连同 AppliedSeq 提交，随后才发布。
- **易错边界：** 受理不等于成交，规划不等于提交，结果提交不等于账务完成；定时器不是硬实时保证，channel 的元素上限不是字节上限，批量提交更不能变成提前释放资金的理由。
- **反例验证：** 在 B1 的结果组“已经持久化、但提交响应丢失”处停住，再让依赖 B1 的下一条命令到达。正确方案必须暂停依赖结果外露，核实原批次后以原身份继续；重试 B1 不应重复买入，最终仍为成交 15015 USDT、返还 10 USDT、S2 剩余 0.05 BTC。若超时后直接重建新订单或先放行预留，这条链就没有闭合。
