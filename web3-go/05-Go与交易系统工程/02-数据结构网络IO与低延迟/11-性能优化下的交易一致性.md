# 大问题 11：怎样在降低延迟的同时，保证订单、成交、预留和账务始终对得上？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 订单数量不变量 | 每张订单的原始量都要能分到成交、撤销和剩余三处。 | 各项非负，不能一边把量成交，一边又把同一部分当作撤销。 |
| 资产覆盖 / 预留 | 订单资格与已成交义务背后必须有对应资产占用。 | B1 的 15025 USDT 不能因超时先退掉，让迟到订单无资产成交。 |
| intentID / reservationID | 固定业务意图及其资产预留的服务端身份。 | 绑定账户、市场、方向、价格数量和规则版本，不能任意换参数复用。 |
| payloadHash / 幂等身份 | 核对规范化载荷的标记，以及识别同一次逻辑操作的身份。 | 同身份相同参数恢复原结果，不同参数冲突；客户端传个预留字符串不构成资格。 |
| commandSeq / 权威顺序 | 本交易对裁决命令的确定位置。 | 成交、关闭、撤单在同一顺序竞争，不按回报或 goroutine 完成先后改历史。 |
| AbortIntent / 资格关闭 | 与原意图关联的关闭命令，以及不再接受它产生新义务的终态。 | 关闭先执行，迟到 Place 必须拒绝；Place 先赢，则保留成交、只处置余量。 |
| Cancel / B2 变体 | 撤实际剩余量的命令，以及独立于主例的部分成交买单。 | B2 买 0.25、限 60000，先成 0.10；若又成 0.05，后撤单只撤 0.10。 |
| 工作簿 / 已提交发布版本 | 内部可试算的状态，与已有耐久依据的权威视图。 | 查询、行情和账户不能抢先把 B1 的试算当事实。 |
| ResultBatch / AppliedSeq | 一条命令的完整裁决及其共同提交的执行进度。 | 两笔成交、订单变化、预留处置一起确定，提交未知就停住依赖状态发布。 |
| resultID / 成交身份 | 每份结果和每笔成交的稳定标识。 | 恢复与重试复用原事实，不因批量、重发或重算制造第二次成交。 |
| group commit / 连续耐久前缀 | 摊薄多个结果提交成本，以及已确认连续到哪里。 | 不合并订单身份、不提前 ACK；存储不支持整组原子就明确逐段确认范围。 |
| 本地账务事务 / PENDING | 单一教学账户域的共同提交边界，以及暂未结转状态。 | 两笔成交、双边资产、价差、去重和进度一起提交；不宣称覆盖独立分库。 |
| 去重 / 有序消费 | 防同一事实重做，与保证不同事实先后关系。 | 两者都要；不同事件各执行一次仍可能先释放后扣款而出错。 |
| 预期消费位置 | 账户事务要求接下来正好处理的位置。 | 不能跳过前序成交先释放余量；跨交易对共享余额还要受账户约束。 |
| 不可变结果 / 最后读者 | 已交付内容不再改变，复用晚于最后一次读取。 | channel 收到切片不说明账户已读完，提前回池会污染回报甚至资产。 |
| 私有回报 / 公共盘口 / 对账 | 不同读模型与核对事实的机制。 | 断线恢复不撤成交，盘口缺口要修复；对账不替代事前资格和提交约束。 |

## 把整篇文章压缩成一个故事

甲用 20000 USDT 中的 15025 预留提交 B1，买 0.25 BTC、限价 60100。请求超时、查询暂时没找到，小周却不能先退钱：Place 可能还在途中，也可能已受理但投影落后。系统保留绑定账户与原参数的 intent，沿原身份查询；若要放弃，就提交关联它的 AbortIntent。关闭先裁决，迟到 Place 失去资格；下单先裁决，则已经成交的部分不能被退款抹掉。

正常路径里，B1 先买 S1 的 0.10、花 6000，再买 S2 的 0.15、花 9015，S2 剩 0.05。单写者试算并不等于事实，完整 ResultBatch 与 AppliedSeq 共同提交后才可发布全成，账务暂时 PENDING。账户域再用一个本地事务处理两笔成交、双方资产、去重和进度，甲得到 0.25 BTC、支出 15015、返还 10。后序 C1 只能撤 S2 余量，不能靠保护撤单的名义跳过 B1。

工程师想批量落盘、并行消费、复用切片，都要回到这些边界。group commit 只省物理提交成本，不能提前确认；每事件只做一次也不够，先释放后扣成交仍会错。账户不能读半份结果，异步读者未退出的对象不能回池，网络断线也不改变经济事实。优化前后要按相同序列和规则核对身份、量、预留与完成水位；文中是在列验证方法，不用漂亮 p99 或事后对账替这些机制背书。

[返回专题总览](README.md)

**流程位置与核心机制：** 独立串联整个交易闭环的一致性母题。其他题分别优化结构、队列、网络和 Runtime；本题证明这些优化没有跨越提交、顺序、身份和资产边界。

**必要前提：** 托管现货限价 GTC、零手续费、按交易对单写者；账户域是统一教学账务域，能在一个本地事务内处理本批次涉及账户，不默认跨独立分库事务已经解决。

## 第 1 层：先定义不能被性能目标牺牲的不变量

**面试官：** 你做了单写者、对象复用和批量落盘，怎样保证订单、成交和买卖双方资产仍然一致？

**面试者：** 我会从不变量和共同提交边界回答。订单原始量等于累计成交、撤销量和当前剩余量之和；每笔成交只有一个稳定身份，买卖双方数量与成交额相等；已确定成交和仍有效挂单必须有必要预留覆盖，同一成交不能重复入账。网络超时和队列状态都无权改变这些业务事实。

账户预留与意图绑定在账户本地事务提交；命令耐久提交决定可恢复的处理位置；撮合把完整 ResultBatch 与 AppliedSeq 一起提交，再发布订单和成交事实；账户按完整批次有序处理，将资产变化、去重和消费进度一起提交。这不是一个跨系统大事务，而是具有明确暂态的分阶段协议。允许订单全成但账务 PENDING，禁止成交义务消失、重复扣账或尚未关闭的订单失去资产覆盖。

## 第 2 层：预留身份必须真的约束执行资格

**面试官：** 你说先预留再撮合，怎么防止一个预留 ID 被换价格、换数量，或者被用于两笔订单？

**面试者：** 预留不是客户端传一个字符串就生效。账户域在事务中保存 intentID、accountID、symbol、方向、价格数量、预留币种与金额、规则版本和规范化载荷摘要，并保证同一业务请求身份不能绑定冲突载荷。提交器只传递服务端可验证的不可变预留凭据，撮合校验其来源及与命令字段的绑定，不接受任意客户端 reservationID。

撮合域还要将 intentID 的接纳/关闭状态纳入可恢复裁决，防止重复命令创建第二笔订单。最重要的协议前提是：账户不能在撮合仍可能接纳该意图时自行释放预留。只有来自同一权威顺序的关闭或剩余量处置结果才授予释放权。凭据证明曾有预留，关闭协议保证资格未被偷偷撤回，两者缺一不可；只做一次远程“余额够不够”查询解决不了后续竞争。

## 第 3 层：提交超时不能成为释放依据

**面试官：** 预留成功后 Place 调用超时，查订单又查不到，为了让用户资金快点可用，能先释放吗？

**面试者：** 不能。查询可能读到落后投影，Place 也可能仍在传输或已经耐久提交但未执行。“暂未查到”不证明命令永远不会到达。此时保留原意图和 15025 预留，以同一请求身份查询或重试，不能创建新身份再占一笔资产，也不能把一个超时解释成确定拒绝。

如果确实要关闭意图，就向同一交易对命令顺序提交 AbortIntent。它先被执行时，撮合持久记录该意图已经关闭，迟到 Place 必须被拒绝；若 Place 已经执行，则关闭只处理其实际剩余量，已成交部分保留。账户收到已提交的关闭结果，并按该交易对前序结果顺序应用后，才释放不再承担义务的预留。这样关闭和接纳竞争有唯一裁决点，而不是让账户和撮合各自按超时猜结论。

## 第 4 层：撤单保护也不能越过已确定顺序

**面试官：** 你要低延迟保护撤单，那把 AbortIntent 或 Cancel 直接送到单写者前面，不就能更快释放吗？

**面试者：** 已经确定的权威命令顺序不能被绕过。可以在排序之前为撤单预留鉴权、接入队列和提交带宽，也可以定义公开的公平调度规则，但一个已提交的后序撤单不能越过先序成交去改写历史。否则不同副本或回放会对“先成交还是先撤”产生不同答案。

用总览的独立部分成交变体说明：B2 买 0.25、限价 60000，先成交 0.10，余 0.15。后来的撤单只能按执行时实际剩余量裁决；若在它之前又成交 0.05，就只撤 0.10。撤单调用成功、进入优先队列、甚至命令可靠受理，都不是释放原始 0.25 对应资产的理由。低延迟应减少排队和资源争抢，不是把业务因果顺序改成“谁更着急谁赢”。

## 第 5 层：试算结果为什么不能提前对外使用

**面试官：** 单写者已经把 B1 算完了，结果落盘还在等，能先把簿更新发布出去，把那次存储等待藏起来吗？

**面试者：** 可以在执行者独占的私有工作状态中试算，但不能把未提交变化当权威状态发布。ResultBatch 里同时包含两笔成交、S1 清空、S2 剩余、B1 全成和预留处置依据，它们与 AppliedSeq 必须同一提交。提交前的查询和行情应停留在上一个已提交版本，而不是读到试算簿。

若提交明确失败，可以按存储协议撤销试算或从已提交状态重建；若结果不确定，必须停止发布后续依赖结果并查明耐久边界。不能一边向客户端宣称 B1 成交，一边在恢复后重算出另一个事件身份。工作簿、已提交发布版本和恢复位置三者要明确区分。少一次等待带来的表面收益，不能抵消“用户得到一个系统自己无法证明存在的成交”这一错误。

## 第 6 层：批量提交如何保住每条命令的身份

**面试官：** 那你把几十个命令一起 group commit，是否必须把它们合并成一笔业务事务才能保证一致？

**面试者：** 不需要把业务身份合成一个订单。批量提交可以按连续 commandSeq 顺序计划多个命令，各自保留稳定 resultID、成交身份与完整 ResultBatch，在一个存储提交边界写入这些批次及最终 AppliedSeq。只有提交确认后才按原顺序发布，不能为了减少消息条数把 B1 的成交和 C1 的撤单混成没有因果关系的一包。

如果所用存储不支持整组原子提交，就必须明确它确认的是哪个连续耐久前缀，并逐个保证结果与进度一致，不能假装拥有整组全有或全无。批次越大，等待和失败恢复工作也可能越多，因此要有条数、字节、时间与在途窗口上限。group commit 改的是物理提交摊销，不是成交规则、幂等键和账户消费的完整性契约。

## 第 7 层：异步账务怎样避免只处理一半成交

**面试官：** B1 两笔成交到了账户域，先给 S1 入账成功，处理 S2 时失败，会不会导致资产只对上一半？

**面试者：** 在本教学基线里，账户消费者拿到的是完整 B1 结果批次，在一个本地事务里处理两笔成交与最终预留处置，并提交去重记录和消费进度。因此不能只把“给 S1 入账”单独提交后，再把同一批次其余部分交给运气。若事务失败，全部回滚；若提交响应丢失，重新读取或用同一批次重试，由事务内去重决定是否已经应用。

成功时甲的 15025 预留归零，0.25 BTC 入可用，10 USDT 退回可用；乙、丙分别得到 6000、9015，S2 仍保留 0.05 BTC 的卖出预留。若未来账户被拆到不能本地原子处理的独立存储，就必须另设计跨域义务、幂等分步状态和对账恢复，不能继续声称这一个本地事务覆盖所有账户。减少事务规模不能悄悄删除原有资产保证。

## 第 8 层：并行消费为什么不能先释放后扣成交

**面试官：** 为了加快账务，你把 B1 成交和后续撤单并行消费，按事件 ID 去重不就够了吗？

**面试者：** 事件去重只能防止同一事件重复应用，不能证明不同事件的先后关系。比如先有成交、后有撤销余量，若撤单消费者按原始预留或落后剩余量先释放，再处理成交，就可能让用户花掉原本承担成交义务的资金。即使每个事件都只执行一次，资产仍然会错。

本基线按交易对结果顺序处理完整批次，在同一事务内校验预期消费位置并更新资产；跨交易对的同一账户仍由账户域事务或版本约束串行化余额竞争。真正要并行，需证明命令的账户/预留依赖不相交，或者建立显式依赖调度，并保证单个预留的消费和关闭不乱序。不能简单按成交 ID 哈希分 worker 后，就认为多条跨事件约束自然成立。顺序与幂等解决的是两种不同问题。

## 第 9 层：网络和对象池不会改变资金承诺

**面试官：** 账务保证了，但回报因为慢客户端被丢掉，或者池化对象提前复用，对一致性还有什么影响？

**面试者：** 回报丢失不应改变已经提交的成交，客户端可以按耐久回报游标或权威查询恢复；连接队列可有界并断开慢连接，但不能把唯一一份成交事实只放在这个易失队列里。公共盘口帧也不能任意丢中间删除；需要连续补齐、正确合并或显式快照重建。网络交付的失败是读模型落后，不是回滚成交的授权。

对象池则可能更危险：如果 ResultBatch 引用了即将复用的成交切片，发送出去的价格数量可能已变成另一条命令的数据。即便耐久数据正确，错误回报也会驱动错误客户端决策；若账户消费也读同一片内存，更会污染资产。因此结果提交及发布对象必须保持不可变，直到最后一个读者结束才能回收，或者在边界复制。同步 channel 发送只证明接收发生，不证明异步消费已经完成。

## 第 10 层：怎样联合验证性能与一致性

**面试官：** 你讲了很多边界，最后用什么反例证明它们真的闭合，而不是只靠对账兜底？

**面试者：** 我会围绕每个提交边界设计可恢复性检查：预留后 Place 超时并迟到，先关闭后迟到 Place 必须无资格；结果已提交但响应丢失，恢复必须得到同一结果而非再成交；账务提交后确认丢失，重试不能再次入账；成交后撤单乱序投递，消费不能先释放承担义务的预留；回报对象复用不能改变已发布内容。

这些检查还要在性能优化开关前后使用相同序列与规则版本，比较订单量、成交量、预留和资产总量，以及承诺已经完成的水位。B1 始终是 15015 支出、10 返还、0.25 BTC 入账，不能因大批量或过载产生不同答案。对账负责发现和收敛残留故障，不代替事前资格约束、结果共同提交与事务内去重。本稿提供验证方法和手工案例，没有宣称执行过故障注入或工程测试。

## 本题收束

- **讲透的机制：** 以稳定意图身份、同一权威顺序、完整结果共同提交和账户事务闭合订单—成交—预留—账务链路。
- **易错边界：** 超时不等于拒绝，去重不等于有序，单写者不等于耐久，group commit 不等于可以提前确认，断线不等于撤单。
- **反例与验证：** 预留成功后提交超时，账户立即退款，迟到 Place 又被接纳。只要这个时序能发生，就算 p99 再低，也没有防住无资产覆盖的成交。
