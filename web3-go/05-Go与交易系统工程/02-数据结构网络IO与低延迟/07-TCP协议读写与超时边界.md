## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| TCP 字节流 / frame | 前者只保证有序字节，后者是应用协议自己划出的完整消息。 | 一次 Write 不对应一次 Read，半条请求不能送去预留或下单。 |
| length prefix / 端序 | 消息前固定宽度的长度字段，以及多字节数字的排列规则。 | 长度表示后续消息体字节数，头部收齐后按协议规定解析。 |
| 长度上限 / 溢出 | 允许接收的最大消息，以及长度运算超出数值范围的风险。 | 分配消息体之前先查下限、上限和加法，再纳入连接与全局预算。 |
| 分帧状态 / 截断 | 保存头体读到哪里；连接结束时仍缺字节的消息叫截断。 | 一批输入可含多条完整 frame 加半条尾巴，尾巴不能补零当订单。 |
| n / err / EOF | 本次有效字节数、错误，以及读取结束信号。 | Read 可同时返回 n>0 与错误，先处理字节再处理错误；n=0 且无错不能忙循环。 |
| io.Writer / 短写 | 写接口契约，以及本次写出的字节少于传入字节。 | 正常契约要求短写带错误，不能把短写无错当 net.Conn 常规路径。 |
| 单消息写者 / 偏移 | 同连接串行写消息的负责者，以及已写到的位置。 | 头、体、心跳不能被多个 goroutine 交叉拼接；带错短写后隔离连接。 |
| net.Conn 并发调用 | Go 允许多个协程调用连接方法。 | 只保证接口可并发使用，不替应用多段 frame 保证不交错。 |
| deadline / 零值 | 绝对截止时刻；零值表示清除相应期限。 | 分别管理读写方向，frame 组装预算不因每到几个字节而无限续期。 |
| context / GTC 生命周期 | 前者控制等待与任务，后者让订单在正式终态前继续有效。 | context 取消不自动设置连接 deadline，关闭连接也不自动撤 GTC。 |
| bufio / Flush | 用户态缓冲及把缓冲交给下层 writer 的操作。 | Write 进缓冲、Flush 成功、TCP 写成功都不证明客户端已应用。 |
| TLS | 正确认证配置下保护传输机密性、完整性与对端身份的协议。 | 它不保证订单只执行一次，也不能消除已提交但响应丢失。 |
| requestID / intent / 载荷 | 原请求身份、绑定意图，以及原订单参数。 | 重连查原身份并核对载荷，不把半帧续到新连接，也不换身份盲重下。 |
| commandSeq / 结果提交 / 账务完成 | 命令耐久位置、裁决已确定、资产已结转三个不同终点。 | 响应需说明阶段，网络传输成功不能替任何业务提交背书。 |
| AbortIntent / Cancel | 同序关闭原意图，或撤销已受理订单的实际剩余量。 | 暂未查到订单不等于能退款，迟到 Place 必须受关闭裁决约束。 |
| 提交未知 / 恢复 | 未获明确响应但业务可能已提交，须查询耐久事实。 | B1 若已成交，断网仍保留原两笔成交，支出 15015、仅返还价差 10。 |

## 把整篇文章压缩成一个故事

甲通过 TCP/TLS 发送 B1，买 0.25 BTC、限价 60100。服务端第一次只读到长度头的一部分，第二次才补齐头和部分消息体，这不是订单损坏，而是 TCP 本来就不保留消息边界。reader 先校验长度、预算和溢出，再收齐完整 frame、鉴权并进入业务；若最后一次读取同时带字节和 EOF，先处理有效字节，剩下截断的半条绝不补齐成订单。

B1 随后预留 15025 USDT、命令耐久受理，按 Maker 价完成两笔成交，结果提交后准备回报。writer 串行写 frame，不能让心跳插进头体中间；回报写出一半却报错时，记录已写字节并隔离连接，不把余下半帧续到新连接。即便 Flush 或全长 Write 成功，也只推进本地发送路径，不能证明客户端已应用，更不能由 TLS 推出账务已结转或业务只执行一次。

甲超时重连后想再买一次，工程师让他用原 requestID、intent 和载荷查原结果，而不是生成新订单。B1 若已全成，就恢复原来的 15015 USDT 支出、0.25 BTC 入账和 10 USDT 返还；断线没有撤销成交的权力。未确定意图要终止，仍走同序 AbortIntent，已受理单走 Cancel。读写各管绝对 deadline，部分字节不能无限续期；这些是协议与业务边界推演，不是网络实测结论。

**必要前提：** 沿用 [README 统一基线](README.md)，以下仅列本题新增前提。

- 示例采用固定宽度 length prefix，长度表示后续消息体的字节数，端序与最大值由协议固定；体内携带协议版本、消息类型和请求身份。
- 连接采用单读取者、单消息写入者，分别管理读写 deadline；连接关闭不撤 GTC 订单，网络完成也不替代业务提交。本题不指定新的日志或结果存储。

```text
TCP／TLS 字节到达
    → 检查长度前缀并组装完整 frame
    → 解码、鉴权、校验请求身份和参数
    → 预留绑定 intent → 命令日志提交〔受理〕
    → 撮合结果原子提交〔执行结果确定〕
    → 账务事务结转〔资金处理完成〕

各阶段响应 → 有界发送队列 → 单写者编码完整 frame → TCP／TLS

```

## 第 1 层：为什么一次 Write 不是一条完整交易消息

**面试官：** 客户端一次 Write 发出 B1，服务端一次 Read 没读全，是否说明请求损坏？交易协议应该怎样建立消息边界？

**面试者：** 不是。TCP 提供有序字节流，不保存应用层消息边界；一次 Write 可能被多次 Read 才读完，多次 Write 也可能在一次 Read 中返回。我会给每条消息增加固定宽度长度前缀，先确定消息体长度，再收齐对应字节，解码成完整请求后才进入业务链路。消息体包含版本、类型、requestID、交易参数等，分帧成功不代表鉴权或业务校验成功。B1 被解码后还要预留、提交命令并等待对应阶段结果，响应必须明确是受理、执行确定还是资金完成，不能只有模糊的成功字段。连接关闭最多说明这条通信通道结束，不能推出 B1 没受理，也不能撤销已经在簿上的 GTC 订单。

## 第 2 层：长度前缀怎样避免内存攻击与粘包误判

**面试官：** 你准备按前缀长度收齐消息体。如果前缀声明一个巨大长度，或者一批字节里同时有半条和几条完整消息，解析器具体怎样处理？

**面试者：** 先在固定大小的头部缓冲区收齐长度字段，以足够宽的无符号类型解析，校验合法下限、协议上限和加法溢出，再转换为分配所需类型；不能先按对端长度分配内存再检查。合法消息体也要纳入连接和全局缓冲预算。解析器保留当前状态与已收字节：头部不足就等待头部，体不足就保存进度，完整后交付一条，再继续消费剩余字节，所以一次输入可以产出多条 frame，也可以留下下一条的半个头。零长度是否合法必须由协议明确，不能当作自动心跳。接收不全时不把半条订单送入预留流程；长度违规通常关闭连接，不能随意扫描后续字节猜新的消息起点，否则攻击者能制造边界歧义。

## 第 3 层：Read 同时返回字节和错误时先处理什么

**面试官：** 上一答需要保存解析进度。现在 Read 返回 n 大于零，同时 err 是 EOF 或其他错误；如果直接按错误关闭，会不会丢掉最后一条完整请求？

**面试者：** 会，所以我先把本次 n 个有效字节交给分帧器，再处理 err，不能让错误分支跳过已经返回的数据。若这些字节补齐了若干完整 frame，就按既定解码与业务准入规则处理它们；末尾仍不完整的 frame 记录为截断，绝不补零或当成有效订单。随后终止这个读取会话，区分正常 EOF、超时和协议错误，恢复分支分别处理，但都不否定此前已经受理的命令。使用读取完整长度的辅助函数，也要检查已读数量和 EOF／UnexpectedEOF，不能只比较错误类型。n 为零而 err 也为空时不能忙循环。关键是“先处置字节”只保护完整消息不丢失，不意味着把缺少尾部的请求也提交；完整请求进入业务后是否受理，仍由耐久命令日志决定。

## 第 4 层：部分写入时怎样保护 frame 不交错

**面试官：** 你处理了最后一段读数据。如果服务端回报只写出半个 frame 就失败，而另一个 goroutine 正准备写心跳，该怎样处理剩余字节和整条消息的状态？

**面试者：** 每条连接由一个发送者串行写完整 frame，心跳也走同一序列，不能让多个 goroutine 分别写头和体。io.Writer 标准契约要求 n<len(p) 必须返回非 nil 的 err，所以“短写且无错”不是 net.Conn 的正常返回。若防御异常或自定义实现遇到这种违约返回，可按 n 推进偏移后只处理剩余部分，或直接报 io.ErrShortWrite；n=0 且 err=nil 必须终止，不能忙循环。正常短写带错误时，先记录本次 n，再停止发送并关闭或隔离连接，不把剩余半帧续到新连接。已写前缀不证明远端是否收到完整消息，全长写成功也不等于业务提交。重连后沿用原业务身份查询或重试完整消息，由服务端去重。net.Conn 允许并发方法调用，也不保证应用多段消息不会交错。

## 第 5 层：deadline 为什么不是每次操作的相对超时

**面试官：** 你让故障发送及时退出。如果每读到一点数据就把超时重设为“从现在起一段时间”，慢连接能否永远占住连接？读写又能否共用一个 deadline？

**面试者：** 能永远拖住，所以 deadline 要按阶段预算设计，而不是无限续期。Go 的 SetReadDeadline、SetWriteDeadline 设置的是绝对时刻，会影响相应方向当前阻塞和后续 I/O，直到修改；零值才是清除。读取者可区分空闲等待与已开始 frame 的组装预算，拿到头部后为该消息固定截止时刻，部分字节到达不应无限延后它。发送者单独维护写截止时刻，并把排队等待与 socket 写等待分别计入业务预算。读写可以并发，但各自拥有设置该方向 deadline 的职责，避免随手 SetDeadline 连另一方向一起打断；清理阶段也要防止旧任务清掉新操作的期限。context 取消不会自动替 net.Conn 设置 deadline，握手、空闲与消息超时也不能混为一个可无限刷新的计时器。

## 第 6 层：Flush 与 TLS 各自保证到哪一层

**面试官：** 上一答给写入加了 deadline。现在 bufio.Writer.Flush 成功，连接也启用了 TLS，是不是可以认为对端已经安全收到并只执行一次？

**面试者：** 都不能。bufio.Write 成功可能只是进入本地用户态缓冲；Flush 成功说明缓冲数据交给下层 writer，TCP 写成功也不证明远端应用已经读取，更不证明命令或结果已经耐久提交。TLS 在正确认证与配置前提下保护传输机密性、完整性及对端身份，不提供交易业务的恰好一次；断线后重发仍可能遇到“第一次已提交、响应没收到”。所以响应应带原请求身份、阶段和必要序号：受理指向 commandSeq，执行结果指向已提交结果及订单版本，资金完成另有账务事实。读到响应也必须按完整 frame 校验与关联，不能靠字节数猜阶段。Flush 失败后不盲目复用原缓冲区重发到新连接，恢复的是完整协议消息及业务身份，而不是一段未知偏移的字节。

## 第 7 层：超时、断线与撤单怎样分开裁决

**面试官：** 你说 TLS 也避免不了“已提交但响应丢失”。B1 客户端超时后想重新下单，或干脆断开连接要求退回 15025 USDT，服务端怎样回答？

**面试者：** 我会让客户端携带原 requestID 和 intent 查询或重试，服务端校验载荷一致性，再返回原 commandSeq 与处理状态；换新身份下单可能真的买两次。即使暂时查不到受理记录，也不能直接退回预留，因为原请求可能还在网络或恢复队列中。需要放弃意图时，将关联原 intent 的 AbortIntent 放入同一命令日志，与迟到的原命令裁决；已经受理的订单则提交 Cancel，由写者按日志顺序决定剩余可撤量。只有耐久结果明确释放范围，账务才事务处理。B1 若已完整成交，断线或撤单都不能撤销两笔成交，仍应支出 15015 USDT、返还 10 USDT。GTC 订单的生命周期独立于连接，网络超时不是业务失败证明，更不是释放资金的授权。

## 第 8 层：用哪些故障窗口验证整个边界

**面试官：** 上一答把恢复交给原身份和有序裁决。怎样验证它确实覆盖了半包、部分写入和提交不确定，而不是只验证正常收发？

**面试者：** 我会按消息边界和业务边界交叉推演：头部按字节拆开、体在任意位置截断、多个 frame 一起到达、最后一次读取同时带数据与 EOF；完整 frame 的输出序列必须不变，截断消息不得进入预留。发送侧让头、体或最后一个字节之后报错，检查只有单发送者推进偏移、无交错与忙循环，重连不续接半帧。业务侧分别在预留后、日志提交后、结果提交后丢响应，要求原身份重试只关联原订单。若撮合提交结果无法核实，写者停止外露后续依赖结果，不能因为 TCP 超时就继续承诺。最后检查 B1 仅有两笔预期成交，资产结转一次、返还 10 USDT，连接关闭不触发隐式撤单。这是协议和状态边界的验证条件，不是网络性能实测结论。

## 官方参考

- [Go 官方 io.Reader／io.Writer 契约](https://pkg.go.dev/io)：Reader 可能同时返回数据与错误；Writer 在 `n < len(p)` 时必须返回非 nil 错误，不能把短写无错当作正常路径。
- [Go 官方 net.Conn](https://pkg.go.dev/net#Conn)：核对并发调用、读写 deadline 的绝对时刻语义，以及写超时仍可能返回 `n > 0` 的边界。
- [Go 官方 bufio.Writer.Flush](https://pkg.go.dev/bufio#Writer.Flush)：Flush 将缓冲数据写入底层 io.Writer，不提供远端应用已读取或业务已提交的确认。
- [Go 官方 crypto/tls](https://pkg.go.dev/crypto/tls)：核对 TLS 的传输安全能力；不能从这些能力推导出交易业务恰好一次。

## 本题收束

- **机制：** length prefix 必须在分配前限制长度；分帧器保存头体进度并支持一次输入多个 frame；Read 先处理 n 字节再处理 err；发送方串行推进剩余字节，并以完整业务身份处理断线后的不确定性。
- **易错边界：** net.Conn 可并发调用不等于应用消息可并发拼写；deadline 是绝对时刻，不是自动续期的相对时长；本地缓冲成功、Flush、TCP、TLS 都不能替代可靠受理或业务提交，连接关闭也不撤 GTC 订单。
- **反例验证：** 服务端已经提交 B1 的 ResultBatch，但回报在写到一半时超时。若客户端换新身份重下、服务端因断线退回全部预留，方案即失败。正确结果是用原身份恢复查询，保留两笔成交与原订单结果，最终支出 15015 USDT、返还 10 USDT，而不是重新撮合或按超时回滚。
