# 大问题 13：怎样设计不隐藏排队的负载模型，并验收尾延迟与正确容量？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 容量 / 同等业务承诺 | 在给定资源和负载下可持续守住的完成能力，以及固定的可靠语义。 | 不只是成功 p99，要同时满足完成率、尾延迟、可恢复积压与正确性。 |
| commandSeq / 可靠受理 | 命令已耐久提交的权威位置。 | 不是进 channel；受理快不能冒充结果提交、账务或客户端完成快。 |
| ResultBatch + AppliedSeq | 一条命令的完整裁决与共同提交进度。 | 合法挂盘、撤单也有执行结果，不是每条 GTC 都必须成交。 |
| 账务终点 / 客户端终点 | 资产、去重、进度已提交，与客户端已应用对应版本。 | B1 全成回报不表示 0.25 BTC 已可花费，socket 收到也不等于页面应用。 |
| 闭环负载 / 协调遗漏 | 等上一笔完成再发下一笔，导致拥塞时本应到达的请求没有产生。 | 适合某些用户模型，却可能服务越慢发送越少，掩盖排队。 |
| 开环负载 / t_schedule | 按预定到达计划发送，与每笔原定应开始的时刻。 | 从计划时刻计时，不等发送线程终于运行才起表；执行端仍要有界。 |
| 实发 / 调度迟到 / 负载端遗漏 | 真正发出的请求、晚于计划的延迟、计划却未发出的项。 | 不能删掉未发项，也不能无限补发变成另一种突发后仍声称负载没变。 |
| 计划请求群体 / 分母 | 预先约定纳入观察的全部逻辑请求。 | 拒绝、失败、超时要计入相应完成率，重试不能变成多笔完成样本。 |
| 超时 / 晚完成 / 排空期限 | 没按时观察到终点、后来确认的完成，以及窗口后继续核对的时间边界。 | 超时不自动撤单；未完成单列，原身份追踪最终状态，不能填零延迟。 |
| 负载分布 / 热点 / 账户集中度 | 不同订单工作量、热门市场和资金竞争的构成。 | 冷门小单总量不能代表热门簿，两个市场共享账户也会竞争预留。 |
| fanout / slow client | 大单产生的成交扇出，以及应用回报慢的客户端。 | 一条命令可能扩大账务和发送字节，慢客户端要标明是场景还是负载端失能。 |
| 直方图 / 桶边界 | 把耗时落入相同区间计数的统计表示。 | 单位、边界、精度相同才能合并计数，再计算总体分位数。 |
| p99 / p999 / 加权均值 | 第 99、99.9 百分位与按样本数加权的平均值。 | 均值可按条件加权，分位数不能平均各端结果得到总体值。 |
| 样本量 / 长短窗口 | 观察数量，以及长期整体和短时片段。 | 1000 样本的最上方 0.1% 约一条，不能把 p999 说成稳定保证。 |
| 预热 / 故障区间 / 恢复预算 | 预先定义的准备阶段、异常阶段，以及允许清退积压的范围。 | 不能事后删最差窗口达标，持续积压不发散、突发后可清退才谈容量。 |
| 同序撤单 / 资产守恒 | 撤单服从权威顺序，成交与预留去向必须对应。 | B1 支出 15015、返还 10；后序 C1 只撤 S2 剩余 0.05，漂亮分位数不抵消错误。 |

## 把整篇文章压缩成一个故事

工程师小周要判断 BTC/USDT 能承受多少订单，先用 B1 把终点讲清：预留 15025 USDT 后，命令耐久提交只算受理，完整结果提交才算裁决确定，账务结转与客户端应用又是后两步。GTC 合法挂盘也是结果，不能要求每单都有成交。若另一个版本把 ACK 提前到内存入队，它测得再快，也不是同一可靠承诺下的容量提升。

小周发现等上一笔返回才发下一笔，会在系统变慢时自动降速，于是给每笔安排 t_schedule，从计划时刻开始计时，另记实发和迟到。发送器也不能无限开线程；未发出的计划项、拒绝、超时与截止时在途都要单列，不能只留快速成功样本。负载还要说明热点、账户集中、大单扇出、撤单和慢客户端，并补足后续流动性，不能反复吃同一份 S1、S2 还说簿规模没变。

汇总时，小周合并同桶直方图计数，不平均各端 p99；p999 也要附样本与窗口，不能靠少量尾部样本宣称稳定能力。再排除负载端 CPU、网络和回报读取瓶颈，检查长时积压与突发清退。正确性用 B1 核对支出 15015、返还 10、得到 0.25 BTC，后序 C1 只撤 S2 的 0.05；超时仍查原身份。只有同承诺的完成率、尾部、恢复和资产都满足预设条件才算通过，本稿并未执行压测或给出实测容量。

## 流程位置与核心机制

本题沿整条业务链定义观测终点，再检查负载是否真实到达、统计是否遗漏失败，最后讨论容量边界。**容量不是某个成功请求分位数，而是在明确业务承诺下，同时满足完成率、尾延迟、积压可恢复性与正确性的负载范围。**

## 必要前提

- Go 1.21+、业务规则、整数精度、S1/S2/B1 贯穿案例与共同提交边界，统一引用 [README 共同基线](README.md)；C1 沿用 B1 之后仅撤 S2 实际剩余量的约束。
- 下文的负载、计时与验收均是方法和手工推演，不创建可运行工程、不提供运行命令，不声称已经执行压测或达到任何性能指标。
- “下单成功”不能混指可靠受理、撮合结果提交、账务完成或客户端应用。GTC 订单合法挂盘也是执行结果，并非每条命令都应产生一笔成交。

## 第 1 层：谈延迟以前，怎样定义可靠受理、成交、账务与客户端终点？

**面试官：** 如果有人说下单 p99 很低，你会先追问什么？

**面试者：** 我会先问“从哪里开始，到哪个事实结束”。可靠受理终点是命令已耐久提交取得 `commandSeq`，不是进入 channel；成交结果终点是对应 `ResultBatch + AppliedSeq` 已原子提交，合法挂盘或撤单结果也属于执行结果；账务终点是资产、去重和消费进度已在本地事务共同提交；客户端终点则是应用了对应订单或账户版本，而不只是 socket 收到字节。客户端可以分别测到相应阶段确认的时长，但必须标明确认包含的传输成本，不能把服务端内部提交时刻与客户端观察时刻混用。B1 的成交回报可以早于账务完成，这不表示 0.25 BTC 已可花费。因此，比较前先固定承诺与终点，并为同一请求保留阶段关联，不能拿更早的 ACK 冒充整条链路完成。

## 第 2 层：为什么闭环发送会隐藏排队，开环又该从何时计时？

**面试官：** 终点已经明确。让每个连接收到结果后再发下一笔，测出的延迟是否可信？

**面试者：** 这种闭环负载适合描述特定并发用户，但服务越慢，发送方等得越久，实际到达率就越低，原本会在拥塞期间到达的请求根本没被生成，容易形成协调遗漏。要考察既定到达流，应预先按负载模型安排每笔请求的计划时刻 `t_schedule`，与上笔完成解耦，并从计划时刻计算端到端耗时，而不是等发送线程终于运行时才开始计时。同时记录实际发送时刻，把调度迟到暴露出来；单进程时长用单调时钟，跨机器阶段时间须另说明校时误差。若发送端没能按计划发出，不能悄悄从样本里删掉，也不能无限补发形成另一种突发。开环不是线程无限增长，而是有界执行、可核对的计划、实发与遗漏统计。

## 第 3 层：拒绝、超时和测试结束时未完成的请求怎样计入结果？

**面试官：** 计划到达已经保留了。若只对最终成功请求计算分位数，为什么仍会把过载看成性能改善？

**面试者：** 因为最慢的请求可能全部被拒绝或超时，剩下的成功子集反而很快。应按预先定义的计划请求群体记录总数，再分别统计实发、可靠受理、各阶段完成、拒绝、失败、超时与截止时仍在途；拒绝和超时必须进入对应完成率或达标率的分母，不能静默消失。成功延迟分布可以单独展示，但必须明确条件，不能拿快速拒绝当作快速成交，也不能给超时随意填一个小延迟。超时表示没有在期限内观察到终点，不代表订单自动取消；按原身份查询后发现的晚完成，应关联回原请求。观察窗口结束后还要有明确的排空期限和最终状态核对，未发出的计划请求标成负载端遗漏，不能当作服务端已成功承载。

## 第 4 层：统计不漏失败之后，为什么还不能只发最便宜的一种订单？

**面试官：** 失败和在途都计入了。如果反复发送同样大小、立即挂盘的 GTC 新单，能否代表交易容量？

**面试者：** 不能，命令条数相同不等于工作量相同。即使范围只含限价 GTC，也要区分不成交挂盘、部分成交和完全成交，描述价格档位深度、同价订单数、撤单比例以及撤单到达时目标是否仍活跃。还要声明交易对热门分布与账户集中度：跨很多冷门对的总量不能替代一本热门簿的压力，共享账户也会引入预留竞争。大单跨档触及很多订单，结果 fanout、账务条目和私有回报字节都会扩大；slow client 则暴露推送缓冲与恢复压力。初始簿和后续补单必须可解释，不能重复消费同一份 S1、S2 后仍声称负载未变。每种模型都保持相同的命令耐久受理、结果提交和账务承诺，不能用省略持久化来降低某类请求的成本。

## 第 5 层：多种请求、多个发送端的分位数怎样汇总才不失真？

**面试官：** 负载已经包含热点、大单和撤单。每个发送端各报均值和 p99，再把它们平均，可以得到总体结果吗？

**面试者：** 总体均值可以在终点和样本范围一致时按样本数加权，但总体 p99 不能平均各端 p99，因为分位数不是可线性相加的统计量。应合并原始时长样本，或合并单位、桶边界与精度一致的直方图计数，再从累计计数计算总体分位数；桶宽带来的误差也要说明。合并的是样本权重，不是每台发送端一票，同时防止重试把同一逻辑请求重复记成多个完成。总体之外仍须按交易对、命令类型、fanout 和完成阶段分桶观察，否则大量冷门小单会掩盖热门簿的大单尾部。均值有助于理解总耗时，却不能替代尾部分布；拒绝率与超时率应并列展示，不能通过只合并成功直方图把失败从结论中洗掉。

## 第 6 层：有了直方图，为什么 p999 仍需要样本量和长窗口说明？

**面试官：** 不再平均 p99 了。那么把总体 p999 放进验收条件，是否就足够严格？

**面试者：** p999 通常指第 99.9 百分位，但位数更多不代表证据更强。只有 1000 个样本时，最上方 0.1% 约对应一个样本，个别停顿就会改变估计，不能把这个数说成稳定能力；应同时报告样本量、观察时长、尾部样本数和估计不确定性，不能用某个固定样本数保证可信。较长窗口才有机会暴露周期性提交抖动、调度与 GC、连接重建以及持续积压，但长窗口也会把短时故障稀释。因此既看长窗口合并分布，也看短时间切片、最老积压与超时趋势；非稳态窗口不能混成一个“稳定 p999”。预热和稳态区间要事先定义，故障与恢复区间单独保留，不能事后删除最差片段来满足目标。

## 第 7 层：尾延迟恶化时，怎样排除负载端瓶颈并做同承诺对照？

**面试官：** 长短窗口都显示 p999 上升，能否据此断言撮合单写者达到容量上限？

**面试者：** 还不能。负载端自己的 CPU、编码、签名、连接和网卡也可能饱和，导致计划时刻到实际发送之间排队；网络拥塞或负载端读回报慢，同样能抬高端到端延迟。应并列核对计划与实发速率、调度迟到、连接写入等待及两端资源占用，再看服务端各阶段排队，避免把发送端瓶颈归因给撮合。对照还要固定初始簿、负载分布、资源与 Go 版本、完成终点、重试策略和持久化承诺。去掉日志提交或提前回 ACK 的版本只能说明另一种更弱承诺，不能作为同等优化。慢客户端既可能是刻意的业务场景，也可能是负载端失能，需标明角色；若负载计划无法交付，本轮只能说明证据不足，不能判定服务端已经通过容量验收。

## 第 8 层：怎样把延迟、积压、恢复与资产守恒合成容量验收？

**面试官：** 已排除发送端混淆，并固定同样的耐久承诺，最终应以什么条件判断容量可接受？

**面试者：** 我会把容量写成带前提的负载范围：指定模型、资源和观察窗口内，各终点的完成率与尾延迟满足预设目标，拒绝和超时不越界，持续段积压不发散，突发后能在约定期限清退。还要审查结果提交未知时确实停住、恢复后不跳命令不重复成交，账务重放把去重、消费进度与资产共同提交。手工核对 B1：预留 15025，成交 15015，只返还 10；S2 余 0.05，后续 C1 只撤这部分，买卖数量、资产与预留对应守恒。客户端超时仍按原身份核实，不能自动退款；慢客户端恢复不能丢私有事实。任一正确性不变量失败，即使成功 p99 很好也不算通过。本题仅列验收方法与预期，不把尚未执行的测量或恢复检查描述成已经通过。

## 本题收束

- **机制：** 先固定四类终点和持久化承诺，再按计划到达时刻进行开环计时；用计划、实发、受理、各阶段完成与失败状态闭合请求群体。分层展示分布，合并同口径直方图计数而非平均分位数，结合长短窗口与积压趋势审查容量。
- **易错边界：** 闭环可能因自动降速隐藏积压；开环若只从实际发送开始计时也会遗漏负载端排队。拒绝、失败与超时不得退出分母；超时不是自动取消。成功条件分布不是全量达标率，少量样本的 p999 不是稳定保证，平均 p99 更不是总体 p99。
- **验证反例：** 检查服务变慢但发送率同步下降、最慢请求全被超时剔除、冷门订单掩盖热门大单、负载端 CPU 或网络饱和、关闭持久化后宣称优化，以及恢复后重复成交或重复返还。只有相同承诺、真实交付的负载、可恢复积压与正确性守恒同时满足预先条件，才有资格讨论容量验收；这里不宣称任何实际压测已通过。
