# 大问题 2：订单簿怎样同时支持最优价撮合、同价时间优先和快速撤单？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| GTC / Maker 价 | 未成交限价单可继续挂着；成交采用原挂单的价格。 | B1 限价 60100，先吃 60000 的 S1，而非全部按自己的限价买入。 |
| 平衡价格树 / 有序 map | 按价格有序组织档位、避免树严重偏斜的索引。 | 买单找最低卖价，卖单找最高买价；Go 普通 map 不保证顺序。 |
| FIFO / 双向链表 | 先来的先服务，节点同时记住前后邻居。 | 同价新单放队尾；有节点位置后可直接摘除，不移动整档订单。 |
| byOrderID / 哈希定位 | 从订单身份直接找到节点的索引。 | 查找通常期望 O(1)，但仍要校验账户权限和当前状态。 |
| commandSeq / 接纳顺序 | 本交易对认可的命令位置与订单接受次序。 | 同价优先级不看客户端时间或 goroutine 抢锁先后。 |
| P / N / K / D | 分别是价位数、活跃订单数、触及的 Maker 数和删除的价位数。 | 撮合要访问 K 个订单，删除 D 档另计树维护，不用一个 n 包办成本。 |
| O(1) / O(log P) | 前者不随规模增长同阶增加，后者随价位规模缓慢增长。 | 已定位节点摘除可为 O(1)，清空最后一单后删除价位仍常需 O(log P)。 |
| 最优价缓存 | 把当前最好的价位记住，减少重复搜索。 | 最优档被清空必须更新缓存，后续维护并不免费。 |
| tick / lot | 价格与数量各自的整数格子。 | 0.01 USDT/BTC 一 tick，0.0001 BTC 一 lot；60100 是 6010000 tick。 |
| 乘积单位 / 溢出 / 舍入 | 整数相乘的金额单位、超过类型范围，以及转换精度的规则。 | tick×lot 得到 0.000001 USDT 单位；先查溢出，再按版本化规则入账。 |
| 跨结构不变量 | 树、队列、ID 索引与总量必须对同一状态说同一件事。 | 活跃单恰在一个队列，档位总量等于剩余量之和，空档不得残留。 |
| heapIndex / 惰性删除 | 堆内节点位置，以及先标废、等以后再清理的删除方式。 | 堆也能选用，但任意撤单和过期节点清理需要额外成本。 |
| 位图 / 价格空洞 | 用位表示档位是否有单；空洞是很多价格格子没有单。 | 稠密数组可能省指针访问，跨空洞找非空档却不能一概称 O(1)。 |
| 槽位 / generation | 可复用存储位置，以及区分该位置新旧身份的代次。 | 旧撤单不能误删复用槽位的新订单，新单也不能继承旧优先级。 |
| Big-O / p99 | 一个说成本如何随规模增长，一个说实际样本尾部耗时。 | 复杂度相近仍可能有缓存、分配、GC 和扇出差异，更不代表端到端延迟。 |
| ResultBatch / AppliedSeq / 参考模型 | 完整结果、共同提交进度，以及便于核对的简单实现。 | 内存索引更新不等于耐久提交；逐步比较顺序、身份和余簿，不只比总量。 |

## 把整篇文章压缩成一个故事

甲提交 B1，买 0.25 BTC、限价 60100。订单簿先用价格树找到 60000 档的 S1，成交 0.10，再到 60100 档的 S2，成交 0.15。S1 清空，要从队列、ID 索引和价格树共同移除；S2 原来 0.20，如今剩 0.05，仍留在原档。若同价还有先接纳的卖单，新来的单不能凭客户端时间更早就插到前面。

丙随后撤 S2，系统按订单 ID 找到节点、检查权限，再用前后链接摘掉，不必扫描整档。不过摘链只是 O(1) 那一段：若这是该价位最后一单，还要删除价格树节点、修正最优价缓存，通常付 O(log P)。同样，一笔大单触及很多碎单，就必须逐个生成成交，不能只因查树是对数级，就声称整次撮合成本固定，更不能把这个复杂度当成用户端耗时。

工程师把节点改紧凑后，还得防槽位复用让旧撤单误删新单，防缓存留着已空价位，并用整数 tick、lot 核对价格金额。B1 的两笔乘积合计应为 15015 USDT，不是预留的 15025。优化模型要与简单模型按同一命令序列逐步比较身份、顺序和余量，完整结果仍须与 AppliedSeq 共同提交；数据结构只负责内存访问，不替账户退款，也不证明已经做过性能或故障测试。

**流程位置与核心机制：** 单写者执行已提交命令时的内存结构与算法。重点是访问模式、索引组合、精度、复杂度和确定性；跨域成交与资金提交见第 11 题。

**必要前提：** 沿用总览限价 GTC、Maker 价成交与单交易对单写者。P 表示当前价格档数量，N 表示活跃订单数量，不能用一个 n 混淆二者。

## 第 1 层：先从三种访问模式选结构

**面试官：** 用 Go 实现现货订单簿，你会选什么数据结构，怎样保证价格时间优先和撤单效率？

**面试者：** 我会按访问模式组合结构，而不是找一种容器包办全部操作：买卖两侧分别用平衡价格树索引价位，每个价位内部放订单双向 FIFO，再用订单 ID 哈希表定位订单节点。买单找最小卖价，卖单找最大买价；同价只从队首成交，新挂单追加队尾；撤单先按 ID 找节点，再从对应队列摘除。

这样，已有价位追加和已定位订单摘除为 O(1)，新建或删除价位为 O(log P)，哈希定位通常期望 O(1)。最优价可缓存，缓存失效时维护树的极值位置；不能把所有后续维护都声称成 O(1)。Go 的普通 map 没有价格顺序，标准库也没有直接提供这种有序 map，需要选择并验证具体树实现。整个树、队列和 ID 索引由同一个执行者修改。

## 第 2 层：同价时间到底以哪个时间为准

**面试官：** 你说新订单追加队尾，但两个连接的时间戳相同，或者一个较早发送的订单晚到，FIFO 怎么决定？

**面试者：** 我不会用客户端时间戳决定同价先后，它可被伪造，也无法跨连接证明谁先到。本模型以交易对命令的权威排序及接纳顺序为准。已提交命令按 commandSeq 执行，订单被接纳并需要挂盘时进入对应价位队尾；其队列相对顺序由此确定，网络包到达某个 reader 的局部顺序不能替代这一规则。

例如 S1a、S1b 都卖 60000，S1a 先被接纳，后来的买单必须先消耗 S1a，哪怕 S1b 的客户端时间更早。新订单穿过多个价位后尚有剩余，剩余部分按它自己的接纳规则挂到买侧队尾。若增加改价改量能力，需另行定义是否保留优先级，不能原地修改价格后仍占旧队首。本基线不宣称已经支持改单。

## 第 3 层：撤单怎样避免扫描整档订单

**面试官：** 那同一价格有十万笔挂单，撤销中间一笔为什么不需要扫描十万笔？

**面试者：** `byOrderID` 保存能直接定位的节点，节点包含订单身份、账户、价位或价格、剩余量及前后链接。撤单先校验账户权限和当前状态，再通过前后链接摘除节点，更新价位总量并删除 ID 索引；若价位清空，还要从价格树删除它并维护最优价。因此“撤单 O(1)”只适用于哈希定位与非空价位内摘除，最后一单清空价位通常还需要 O(log P)。

如果用 slice 存档内订单，按 ID 找到下标以后删除仍可能移动大量元素；交换尾部元素又会破坏 FIFO。也可以用索引化链表而不是指针链表，但必须维护有效槽位与版本，不能把已复用槽位误认为原订单。撤单结果只是裁决实际剩余量，资金是否返还仍由已提交结果和账户事务决定。

## 第 4 层：一次扫多档的成本不能只写 log n

**面试官：** 你把单次插入和删除讲清了，那 B1 一次吃掉很多档位，撮合还是 O(log P) 吗？

**面试者：** 不是。成交必须访问实际被触及的订单并产生结果，输出本身就有成本。设触及 K 个 Maker 订单、删除 D 个价格档，在能够低成本推进当前最优档的实现中，可以把核心遍历理解为 O(K)，树删除另付 O(D log P)，最初定位和新余量挂盘还可能有 O(log P)。具体树若每次重新查最小值，也要把那部分查找成本计入，不能忽略实现差异。

本例 B1 触及 S1、S2 两单，S1 清空使 60000 档删除，S2 尚余 0.05，因此不删 60100 档。K 和 D 都小；但一笔扫十万个碎单的大单，会产生大量成交对象、序列化和账务工作，不能凭输入命令只有一个就当作恒定成本。执行预算和背压应考虑这种扇出，同时保持整条订单的既定规则。

## 第 5 层：价格索引怎样避免浮点相等陷阱

**面试官：** 你按价格找档，浮点的 60100 和计算得到的同一个价格可能不完全相等，你怎么处理？

**面试者：** 我会在接入层按明确精度把十进制输入转换成整数 tick 和 lot，拒绝超过允许精度的输入，不先转成 float64 再补救。总览约定价格 tick 为 0.01 USDT/BTC，数量 lot 为 0.0001 BTC，所以 60100 对应 6010000 tick，0.25 对应 2500 lot；同一整数价格只属于同一档。

成交额乘积单位是 0.000001 USDT。B1 两笔成交乘积之和是 15015000000 个该单位，等于 15015 USDT；预留则是 15025000000。乘法前检查数值上界与溢出，换到账务精度时定义舍入方向、余数归属和规则版本。本例能整除不代表所有精度组合都能整除。这样比较、累计、回放及对账都用同一套确定规则，不依赖机器浮点误差。

## 第 6 层：多个索引怎样保持同一份状态

**面试官：** 你同时维护树、FIFO、哈希表和价位总量，如果更新到一半出错，会不会出现幽灵订单？

**面试者：** 会，所以我会把跨结构不变量放到执行步骤中：每个活跃挂单在唯一一侧唯一价位中恰好出现一次，ID 索引指向同一个节点，价位总量等于队列剩余量之和，空价位不得留在价格树中。单写者避免其他线程看到中间更新，但它并不能自动修复错误代码或进程崩溃。

对一个命令，先完成参数、权限和业务资格检查，再在私有工作状态中执行一致的摘除/插入步骤，生成完整结果。对外发布以结果提交为界；中途发生不可恢复的结构错误时，应停住分片并从耐久状态重建，不能吞掉错误继续运行。内存操作成功也不能替代 ResultBatch 与 AppliedSeq 的共同提交；这里的多个索引属于同一撮合状态的不同访问路径，不是各自独立的事实源。

## 第 7 层：为什么不直接用两个堆

**面试官：** 平衡树维护很复杂，既然总是取最优价，换成买卖两个堆不是更简单吗？

**面试者：** 堆适合拿极值，但本需求还有按 ID 撤单、同价队列和有序深度遍历。可以用“价位堆＋价位 map＋FIFO”，但删除任意空价位时需要维护 heapIndex，或者使用惰性删除并处理过期节点。惰性删除会把工作推迟到堆顶，造成内存和尾延迟不稳定；没有索引的任意删除则会退化为扫描。

因此堆不是不能用，而是它的完整方案也需要多个索引与一致维护。平衡树天然支持有序遍历和范围访问，比较适合本基线的价格档操作。选型时要比较下单、撤单、档位变更、Top-N 快照等真实比例，而不只比“取最小值”一个操作。若只需要极值、档位集合非常小或访问模式不同，堆可能有优势，但应把这些改变的条件说出来。

## 第 8 层：稠密价格能不能用数组代替树

**面试官：** 你说要看实际负载，如果价格只在一个很窄的区间跳动，数组是不是比树更合适？

**面试者：** 在价格 tick 范围固定、稠密且内存可控时，可以用价格映射的数组存档位，再用位图或分层位图找下一个非空价格。它减少指针跳转，可能有更好的局部性，但不能把“找下一非空档”永远当作 O(1)：朴素扫描在大片空洞上会变慢，需要说明位图层级与范围成本。

如果价格范围无界、波动后越出窗口，数组要扩容、重定位或采用分块映射；这会引入停顿和复杂边界。还要按真实 tick 数估算空间，不能把 USDT 数值区间误当作档位个数。本基线继续用树支持稀疏动态价格，数组作为明确改变价格分布假设后的候选，再通过同一撤单比例和极端空洞负载比较，不在追问时悄悄换架构。

## 第 9 层：理论复杂度相同，为什么尾延迟不同

**面试官：** 如果两个方案渐进复杂度接近，为什么某个 Go 实现的 p99 仍明显更差？

**面试者：** 渐进复杂度没有描述对象分配、缓存未命中、分支预测和结果扇出。每个订单、链表节点和树节点分别分配，可能增加指针追踪和 GC 扫描；索引化节点、紧凑字段和预分配能减少这些开销，但复用槽位必须有安全的生命周期。大 slice 也不一定更好，它可能保留巨型底层数组，扩容还会产生复制峰值。

我会先固定订单簿规模、价位分布与下单撤单组合，分开观察执行 CPU、分配率、存活堆和调度等待，再比较数据布局。对外异步结果不能引用马上要被覆写的工作节点；否则把对象池用得越激进，越容易产生错误成交回报。内存布局的详细机制在第 03 题展开，本题保留的判断是：Big-O 只给增长方向，不能代替实际常数、内存和输出成本。

## 第 10 层：优化后怎样证明公平性和确定性不变

**面试官：** 你用了紧凑节点和最优价缓存，怎样证明撤单复用没有破坏同价顺序，回放也还能一致？

**面试者：** 我会把相同命令序列交给一个容易读懂的参考模型与优化模型，逐步比较成交身份、顺序、价格、数量、剩余簿和终态，而不是只比较最终总量。同价情况下，先挂 S1a 再挂 S1b，撤中间订单后再插入新订单，新订单必须在仍存活的旧订单之后；槽位复用不能让新单继承旧单的优先级或 ID 索引。

同时覆盖最优档清空、跨多档部分成交、撤不存在订单、重复命令、数量溢出和价格空洞。回放要用固定规则版本和确定的排序，不依赖 Go map 遍历顺序、当前时间或随机数改变成交结果。参考模型比较和不变量检查是验证方法，本稿没有运行这些工程测试。用总览 B1 推演时，两模型都应先成交 S1，再成交 S2 的 0.15，最终只剩 S2 的 0.05。

## 本题收束

- **讲透的机制：** 三类访问模式决定价格树、FIFO 和订单索引的组合；成本按价位、订单及输出量分别计算。
- **易错边界：** map 不排序，堆不免费支持任意删除；按 ID 找到节点后 O(1) 摘除，不代表空价位删除也 O(1)；客户端时间不是权威优先级。
- **反例与验证：** 最优档被最后一笔撤单清空后，再下买单。若缓存仍指向旧价，或复用槽位使新单排在旧单前，即使吞吐提高也说明实现不成立。
