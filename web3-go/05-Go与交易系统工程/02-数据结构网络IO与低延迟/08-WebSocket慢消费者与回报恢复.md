## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 私有回报 / 耐久来源 | 授权给账户看的订单、成交、资金事实，以及可恢复的底层记录。 | 连接队列不是唯一事实源，断线不能删除 B1 成交或资金义务。 |
| 慢消费者 / 有界缓存 | 客户端应用速度跟不上；发送缓存必须有限。 | 超条数、字节或年龄预算就断开或要求恢复，不反向堵住撮合写者。 |
| streamID | 标识回报属于哪个账户和范围的流身份。 | 恢复按账户鉴权，不能把连接自己的发送计数当成账户进度。 |
| epoch | 标识服务端序列谱系的一代。 | 普通重连不换代，谱系重建无法续旧游标时才明确要求重建。 |
| reportSeq / commandSeq | 账户回报流位置与撮合命令位置，属于不同编号系统。 | 一条命令可生多条回报，不能跨流直接相减判断丢失。 |
| 应用级 ACK | 客户端声明已经连续应用到某个位置。 | 不是 socket 写成功或 frame 到达；不能跳过缺口，也不能替另一设备确认。 |
| 本地检查点 / 去重 | 同步保存业务视图与恢复位置，并识别重发的同一事实。 | ACK 丢失允许重放；不能耐久保存时只用真实可恢复的较早游标。 |
| 快照锚点 s | 一份一致投影视图已覆盖的账户流位置。 | 快照须标范围、订单与账务版本，再补 s 之后的回报，不能临时拼表贴当前号。 |
| 保留窗口 / resync | 可重放历史的有效范围，以及显式要求重新同步。 | 游标过旧或追赶超预算就重建，不能跳到最新号假装没有缺口。 |
| 单读取者 / 单写入者 / 心跳 | 分别管理连接输入、串行输出及活性检测。 | 具体并发例外按库版本核对；心跳正常不证明应用已追上。 |
| 全局预算 / 重连退避 | 全进程资源上限，以及重连前逐步放慢并错峰。 | 每连接有界乘上大量连接仍会失控，快照、重放与编码中数据也计费。 |
| 公共 L2 / 绝对数量 | 公开的价位剩余量，以及用新数量覆盖某一档。 | 只覆盖帧内列出的档位，不是替换全簿；qty=0 的删除不能漏。 |
| prevSeq / seq | 当前帧要求的前序位置，以及应用后的新位置。 | 谱系一致且 prevSeq 等于本地位置才接续，否则暂停有效盘口并补齐或重建。 |
| anchor / 合法区间合并 | 从客户端已知位置起，压缩完整连续区间的最终档位状态。 | 合并 21～22 时必须同时保留 60000 删除与 60100 余 0.05，不压缩成交明细。 |
| generation | 客户端每次连接或恢复会话的本地代次。 | 新恢复使旧回调失去写视图资格；它与服务端 epoch 不能互相替代。 |
| 完成阶段 / 原身份恢复 | 成交与资金处理分开标注；仍沿原订单查询。 | 没看见 B1 回报不表示没成交，不能换身份重下或退全部 15025 预留。 |

## 把整篇文章压缩成一个故事

甲的 B1 已按 Maker 价成交 0.25 BTC，私有回报尚在慢手机的队列里，账务回报还会稍后到来。工程师不能用丢旧保新把两笔成交抹掉，而要让连接只做有界交付缓存，底层账户流耐久保留 streamID、epoch、reportSeq。队列超预算就断开，甲从真正已应用的游标恢复；服务端 Write 成功或心跳正常都不能替手机确认已应用，ACK 丢了可以重放去重。

同一时刻，公共盘口在 seq=20 还有 60000 和 60100 两档；21 删除 60000，22 只把 60100 改为 0.05 BTC。若跳过 21，即使数量是绝对值，旧的 60000 也会残留。客户端必须按 prevSeq 衔接，缺口就补齐或重建。若要合并，须从已知 anchor=20 覆盖完整 21～22 区间，同时发送 60000 为零和 60100 为 0.05，不能只取最后一帧。

甲重连安装新快照后，旧连接的迟到回调还可能覆盖页面，因此本地 generation 也要在写视图前核对。游标过期时，用带版本和流锚点的一致快照再接增量；追不上则显式恢复，不无限扩缓存。全局还要限制同时重放和重连的资源。过期的是连接写视图资格，不是 B1 的事实：最终仍支出 15015 USDT、得到 0.25 BTC、返还 10，断线不能退款或重新撮合；本文没有宣称执行过恢复测试。

**流程位置与核心机制：** 本题从已提交撮合结果到私有订单／资金回报、公共 L2 推送及客户端恢复。重点是耐久事件与连接解耦、每账户恢复游标、应用级 ACK、带锚点的快照、有界队列和全局资源预算，以及公共绝对数量增量的连续性；不实现完整行情系统，也不泛讲可靠消息库。

**必要前提：** 沿用 [README 统一基线](README.md)，以下仅列本题新增前提。

- 私有回报源于耐久事件，账户流具有 `streamID / epoch / reportSeq`，不依赖连接存活。撮合事实与账务事实分别标注完成阶段；不通过推送系统重新决定成交、余额或资金释放。
- 公共 L2 限定为约定订阅范围内的价格档绝对数量更新：`qty=0` 表示删除该档。增量携带 `streamID / epoch / prevSeq / seq`，快照与增量必须在同一序列域中衔接。私有 reportSeq、公共盘口 seq 与撮合 commandSeq 不是同一个游标。
- 不重新选择命令日志、结果或事件的具体存储。WebSocket 并发契约须针对选用库及其版本核实，本文按应用层单读取者、单写入者组织连接。

```text
已提交 ResultBatch → 耐久订单／成交事实 → 每账户可恢复回报流
账务事务完成       → 耐久资金处理事实   → 同一账户流内明确阶段
                                           ↓
                              有界连接队列 → 客户端应用 → 应用级 ACK
                                           ↓ 慢消费或断线
                           原账户游标重放／带锚点快照后补增量

已提交订单簿变化 → 公共 L2 序列 → 连续增量／合法锚点合并
                                     ↓ 缺口或失去合并前提
                                  显式 resync／快照重建
```

## 第 1 层：为什么不能给所有 WebSocket 数据统一丢旧保新

**面试官：** 一个账户读回报很慢，服务端队列一直增长。能否统一丢掉旧消息、保留最新一条，避免影响撮合？

**面试者：** 不能把所有推送当成可覆盖状态。私有成交和资金结果承载业务事实，旧成交不会因为有了新回报就失效；连接队列只能是有限的交付缓存，不能成为唯一事实来源。我会让已提交结果驱动耐久账户回报流，连接按游标读取，超过条数、字节或等待预算就断开或明确要求恢复，不让慢连接反向阻塞撮合写者。公共行情也不能简单一概丢旧：整份快照可能替代旧快照，但普通盘口增量存在前后依赖。B1 的两笔成交、订单全成和账务完成可以在不同阶段可见，必须带清楚的阶段与身份。断开连接允许停止这次发送，却不允许删除底层成交义务或把客户端没看到当成业务没发生。

## 第 2 层：连接之外怎样定义可恢复的私有回报位置

**面试官：** 你让连接队列不做唯一来源。服务进程重启后，怎样找回同一账户的下一条回报，而不是从新连接的第一条重新编号？

**面试者：** 我会把恢复身份定义为账户流的 streamID、epoch 和单调 reportSeq。streamID 标识账户及流范围，epoch 标识序列谱系，普通重连不更换 epoch；只有明确重建且旧游标不能直接续接时才更换，并要求重建。每条回报还关联来源结果身份、订单版本或账务版本，序号和来源映射必须能耐久恢复，不能只存连接内计数。结果已经提交但回报尚未投影时，恢复者从耐久来源继续幂等生成同一事实，不能因进程退出永久漏报。客户端请求从已应用游标之后补发，服务端按账户鉴权读取，不能让某条连接的发送计数变成账户进度。该序列只规定本账户回报顺序，不意味着所有交易对共享一个写者，也不能把成交回报误标为资金已结转。

## 第 3 层：ACK 应确认收到还是确认已应用

**面试官：** 上一答让客户端提交已应用游标。如果服务端 Write 成功就推进 ACK，或者客户端收到 frame 便 ACK，但尚未更新本地订单，会有什么问题？

**面试者：** 服务端写成功只说明本地发送路径推进了，不知道客户端是否解码，更不知道是否应用。这里 ACK 明确定义为客户端已经按序应用到 reportSeq，而不是 TCP、WebSocket 或收包确认。客户端应把业务视图与恢复游标作为一致的本地检查点保存；如果不能耐久保存，重启后只能使用真正可恢复的较早游标，接受重复重放，不能声称更大的已应用位置。服务端只接受同一 streamID、epoch 下不越过交付范围的累计连续 ACK，发现缺口先补齐，不靠最大序号跳过去。ACK 丢失会导致重发，客户端按序号和稳定事件身份去重；服务端不能因 ACK 就删除权威成交或账务记录。其他设备也不能直接继承本设备 ACK，除非共享同一份已应用状态，否则它可能跳过自己从没处理的回报。

## 第 4 层：游标超过保留范围时快照怎样接上增量

**面试官：** 你允许用较早游标重放。如果客户端离线太久，那个位置已经超出回报保留范围，还能只回一个“当前余额和未完成订单”就继续发新消息吗？

**面试者：** 不够，必须明确返回需要重建，并提供带账户版本、订单版本及账户流锚点的快照。快照要说明覆盖范围和完成阶段：余额按账务版本，订单与成交处理按相应版本，不能把尚未结转的成交拼成“资金已完成”。它必须对应同一流谱系下截至 reportSeq=s 的一致投影切面，随后只补 s 之后的回报；可从按序应用耐久事件的投影视图取得，不能先随意查多个表，再贴一个当前序号。如果现有读取契约无法证明这一切面，就不能宣称可无缝恢复。快照期间保留或可重读 s 之后的增量，超过恢复预算就重新取锚点。快照用于恢复视图，不替代耐久成交与资金记录；需要历史明细时走授权历史查询，不能用“最新状态一样”掩盖事实缺失。

## 第 5 层：追赶与实时切换怎样避免再次产生缺口

**面试官：** 上一答从快照锚点 s 补增量。但快照传输期间新回报还在产生，补发又赶不上实时速度，怎样切换才不会漏一段或堆满内存？

**面试者：** 我不会先发快照、再随手订阅实时通道。恢复会话先确定锚点和可重读区间，客户端安装快照后，从 s+1 按同一账户序列追赶；追到已确定水位再衔接后续，重叠可去重，不能有缺口。连接队列按条数、字节、最老年龄限额，编码中和写入中的数据也算在预算内。若持续追不上，就显式 resync 或断开，保留耐久来源，不无限申请缓存。连接采用单读取者处理 ACK、控制帧与关闭，单写入者串行发数据，设置写截止时间；具体库的控制帧并发例外要按版本核实，不能跨库照搬。心跳只判断连接活性，不代表应用追赶成功。恢复期间超过事件保留窗口也必须重新建锚点，不能跳到最新位置伪装连续。

## 第 6 层：所有连接都在限额内，为何进程仍会失控

**面试官：** 你已经限制单连接缓存并设置断开。如果大量慢账户同时重连，每条连接都没超限，为什么服务端仍可能耗尽资源？

**面试者：** 单连接上限乘以连接数仍可能超过进程容量，重连还会增加鉴权、快照读取、历史重放和序列化开销。我会增加全局、租户或账户维度的连接数与在途字节预算，限制同时恢复的会话、快照大小和重放带宽，并让实时推送与恢复任务拥有明确配额。准入要在大额分配前完成，断开、超时和取消时归还预算，不能只限制已经排入发送 channel 的对象。客户端采用带抖动的退避，服务端实施重连限流并明确可重试条件，不能靠不停立即重连自愈。预算耗尽时拒绝或延后新恢复任务，必要时断开慢者；这影响可用性，不改变订单受理或成交事实。不能为了腾内存推进虚假 ACK，也不能把成交或资金回报的耐久来源裁掉。

## 第 7 层：公共绝对数量增量为何也不能任意跳帧

**面试官：** 上一答不允许牺牲私有回报。公共 L2 的每个变化都是绝对数量，是否可以在资源紧张时任意丢掉中间帧，只发最新帧？

**面试者：** 也不行，绝对数量只对该帧明确列出的价格档覆盖，不是整本盘口替换。假设客户端在 seq=20 时有 60000 和 60100 两档；seq=21 把 60000 的数量设为零，seq=22 只把 60100 改为 0.05。若跳过 21，直接应用 22，60000 这档会永远残留，即使 22 的数量是绝对值也救不了。因此每帧携带 streamID、epoch、prevSeq、seq，客户端仅在谱系一致且 prevSeq 等于本地已应用 seq 时接续；检测到缺口就暂停把盘口标为有效，补齐或重建。心跳与 WebSocket 连接仍正常也不证明序列连续。发现缺口后也不能先推进本地序号再异步补数据，否则之后的连续性检查会建立在错误盘口上。公共行情可以采用合法合并或快照替换降低发送量，但不能把“公共”当成允许静默漏删除的理由。

## 第 8 层：什么样的合并才真的保留盘口状态

**面试官：** 你说可以合法合并。沿用 seq=20 的例子，怎样合并 21 和 22，才能既降低发送量，又让客户端知道没有漏掉删除？

**面试者：** 合并必须以客户端已知且可验证的 anchor=20 为起点，覆盖同一 streamID、epoch 和订阅范围内的完整连续区间 21 到 22，逐档保留该区间最后一次绝对数量，删除也保留为零。合并帧标 prevSeq=20、seq=22，包含 60000 为零和 60100 为 0.05，客户端只有本地序号正好为 20 才能应用；该帧明确表达区间压缩，不能靠普通逐帧格式暗中跳号。如果连接已有发送中的帧，要跟踪其边界或依据客户端已应用确认选择锚点，不能把“入队”当成“已应用”。只掌握最新帧、缺少区间中的删除，或锚点已无法追溯时，必须重建快照。合并只保留这个范围的最终盘口状态，不保留逐笔轨迹，因此绝不能拿它压缩掉成交明细或资金结果。

## 第 9 层：重连后怎样隔离旧连接与新快照

**面试官：** 上一答要求客户端恰好位于合并锚点。如果重连已安装新快照，旧连接才迟到一帧，甚至旧恢复请求才返回，怎样避免把新盘口或私有订单状态覆盖回去？

**面试者：** 客户端为每次连接及恢复会话增加本地 generation，所有异步回调、快照响应、增量和 ACK 都带着发起时的 generation，进入状态修改前再次校验。启动新恢复时使旧 generation 失效、取消旧任务，但不能只依赖取消成功；旧任务迟到也必须被拒绝。新快照在校验 streamID、epoch、范围和锚点后原子安装，再从锚点接增量，不能让旧队列与新队列同时写同一视图。generation 隔离本地会话，epoch 隔离服务端序列谱系，两者不能互相替代。私有与公共流分别保存游标，ACK 也不能串流或让旧连接代新连接推进。完成连续性校验之前页面应显示恢复中，不因为 WebSocket 重新连上就立刻宣称订单、余额和盘口都已实时。

## 第 10 层：恢复期间超时能否补偿撤销交易

**面试官：** 你会丢弃旧 generation 的迟到消息并显示恢复中。如果 B1 正好在重连前提交，用户始终没看到成交回报，能否把它当失败重新下单，或者退还全部预留？

**面试者：** 不能，丢弃的是过期连接对本地视图的写入资格，不是它承载过的业务事实。用户应以原 requestID 和 intent 查询、重试，鉴权后沿原订单与耐久回报恢复，不能换身份制造第二笔买单。需要放弃尚未确定的意图，用关联原 intent 的 AbortIntent 进入同一日志，与迟到原命令裁决；已受理订单则提交 Cancel，按顺序决定实际剩余量，账务依据完整结果释放。如果 B1 已成交，就必须恢复两笔成交及之后的账务事实：共支出 15015 USDT、获得 0.25 BTC、返还 10 USDT，S2 余 0.05 BTC。验证时可同时丢 ACK、拖慢连接、切换 generation 并制造 L2 删除缺口，正确结果应是回报可重放去重、盘口缺口显式重建，而不是靠删事实或超时退钱让页面暂时一致。

## 本题收束

- **机制：** 私有回报来自耐久事件，以每账户 streamID／epoch／reportSeq 恢复，ACK 表示客户端按序应用；超保留范围用账户与订单版本快照加锚点补增量。慢者通过有界队列、断开或显式 resync 隔离，并受全局预算与重连限流约束。
- **易错边界：** 单连接有界不等于全局有界；心跳正常不等于应用无积压；连接写成功不等于客户端已应用；公共 L2 的绝对数量不是全量快照，任意跳帧仍会漏删除。合法合并必须覆盖客户端已知锚点之后的完整区间，做不到就重建；成交与资金事实不能被丢弃或按盘口方式合并。
- **反例验证：** 客户端在旧连接等待 B1 回报时重连，公共流恰好漏掉删除 60000 档的帧，新快照安装后旧连接又迟到。正确方案应隔离旧 generation、按私有原游标恢复或快照续接、对公共缺口重建；最终只保留 B1 的原始两笔成交和一次资金结转，不保留已删除盘口档位，也不因网络超时释放全部预留。
