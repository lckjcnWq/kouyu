# 大问题 5：怎样用有界队列与背压保护撤单，而不丢掉已受理订单？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 有界队列 / 背压 | 缓存只装有限工作，下游慢就让上游减少继续接收。 | 满 channel 只说明本地容不下，不说明订单未提交，更不授权退款。 |
| 准入 / 容量许可 | 在制造业务义务前检查并取得后续所需资源。 | 尽量在预留前做，不能先无限冻结资产，再靠一个小 channel 兜底。 |
| 可靠受理 / 耐久积压 | 命令已可恢复，以及尚未执行的持久命令。 | 已受理不能丢；日志磁盘与保留期限也要有预算，不是无限队列。 |
| intent / clientOrderId | 绑定原参数的下单意图，以及同一逻辑订单的请求身份。 | B1 重试沿用原身份、原载荷，不换身份重复预留 15025 USDT。 |
| 条数 / 字节 / fanout | 工作项数量、保留数据大小，以及一条命令生成多少成交结果。 | 一条扫多档大单不等于一条普通挂单，条数上限不等于资源上限。 |
| 最老年龄 | 当前最早尚未完成工作已经等了多久。 | 超龄用于报警与收紧准入，不能据此删除旧命令或释放资金。 |
| inflight | 已出队但还在执行、编码或等提交的工作。 | 出队不等于义务完成，不能立刻归还全部容量。 |
| λ / μ | 同口径的到达率与处理率。 | offered 是尝试到达，admitted 是实际准入，有拒绝时两者不同。 |
| L=λW / Little 定律 | 稳态下平均在系统数量等于有效平均速率乘平均停留时间。 | W 是均值不是 p99，命令数也不能和成交笔数混算。 |
| 流体近似 / 净清退能力 | 把离散请求近似成连续流量，以及处理率减后续到达率。 | 2000 对 1000 条/秒持续 0.1 秒积压约 100；随后到达 500，约 0.2 秒清退。 |
| ResultBatch + AppliedSeq | 一条命令的完整结果与共同提交的执行进度。 | 提交未知先停住核实；撮合 CPU 空闲也不能无限积累未提交结果。 |
| 撤单保留容量 | 专门留给风险退出请求的接入与处理资源。 | 要覆盖连接、鉴权、字节、日志追加等环节，但不保证存储失效时仍立刻成功。 |
| 权威排序 / C1 | 日志确定的命令次序，以及 S2 所属账户的后序撤单。 | B1 在前，C1 就只能撤成交后剩下的 0.05 BTC，不能越序撤原 0.20。 |
| 公平规则 / 账户配额 | 排序前分配服务机会的办法，以及每账户可占用的上限。 | 保护撤单也不能让普通单永远饥饿，或被一个账户的重试独占。 |
| 退避 / jitter | 失败后逐步放慢重试，并随机错开时间。 | 防止重连和撤单风暴，仍优先查原状态，不能靠换身份重试。 |
| AbortIntent / Cancel | 前者关闭关联意图，后者裁决已受理订单实际剩余量。 | 都要进入同一权威顺序，挡住迟到 Place，资金只按已提交依据释放。 |

## 把整篇文章压缩成一个故事

甲提交 B1，买 0.25 BTC、限价 60100，系统已预留 15025 USDT，内部队列却满了。值班工程师不能回一句繁忙就删掉意图、退回资金，因为原命令可能已经提交或仍会迟到。无副作用的新请求可以在准入前明确拒绝；B1 则必须按原身份查询和恢复，已耐久受理的命令留在日志中按序完成。容量应尽量在预留前取得，不能把有界内存换成无限预留和磁盘积压。

小周把条数、字节、最老年龄、inflight 和账务落后一起纳入反馈。教学中假设突发每秒到达 2000 条、处理 1000 条，持续 0.1 秒便新增约 100 条积压；之后到达降为 500，净清退每秒只有 500，约需 0.2 秒。这不是实测 p99，也不是靠扩大 channel 就提高了处理率。下游提交变慢时仍要收紧入口，出队等待提交的对象不能提前从预算里消失。

丙要用 C1 撤 S2，小周为撤单留出鉴权、连接、字节和日志提交份额，并限制单账户风暴；但 B1 已排序在前，C1 绝不能插队。先成交 S1 的 0.10、S2 的 0.15，再撤 S2 余下 0.05。若提交未知就停住核实，若账务落后就保留义务，最终 B1 支出 15015、只返还价差 10。超龄、断线和 context 取消都不是退款依据，保护的是退出机会，不是改写成交历史。

## 流程位置与核心机制

本题贯穿“连接接入 → 账户预留 → 命令耐久受理 → 单写执行 → 结果提交 → 账务与回报”。有界队列限制内存占用，背压让下游能力不足反馈到上游准入；二者都不能把已经形成的业务义务变成可随意丢弃的数据。

## 必要前提

- Go 1.21+、业务规则、整数精度、S1/S2/B1 贯穿案例与共同提交边界，统一引用 [README 共同基线](README.md)。
- C1 是 B1 之后由 S2 所属账户提交的撤单，只撤实际剩余量。撤单请求也要鉴权、排序和耐久裁决，不能直接从连接侧修改簿或释放预留。
- 可靠受理指命令已经耐久提交，不是进入 channel。内存预取有界，剩余已受理积压由耐久日志承载；日志磁盘与保留期限也不是无限的。
- 速率与积压计算仅作给定假设下的流体近似，不代表实际负载、性能或容量结论。

## 第 1 层：队列满时，拒绝请求和丢弃订单有什么区别？

**面试官：** 把 Go channel 设成有界，满了就返回繁忙并丢掉当前请求，是否就完成过载保护了？

**面试者：** 要先问队列位于哪个业务边界。若请求尚未预留、尚无业务副作用，可以在准入处明确拒绝，告知没有受理；但 B1 已经冻结 15025 USDT 后，内部 channel 满只是传输失败，不能把意图连同资金责任一起丢掉。意图必须能按原身份查询和重试，资金仍保持受约束状态。若命令已经耐久受理，即使内存队列满或客户端离线，也要由日志保留并最终按序裁决。Go 的非阻塞发送只能表达当前缓冲是否容得下，不能证明订单没有提交，更不能授权退款。因此，容量许可尽量在预留前取得，并覆盖后续待提交义务；不能先制造无限预留，再指望一个有界 channel 兜底。

## 第 2 层：只限制条数，为什么仍可能耗尽内存并拖长等待？

**面试官：** 已经区分拒绝边界，并把入口限制为固定条数。这样能否给出可靠的资源上限？

**面试者：** 固定条数只是一个维度。相同条数的命令可能有不同载荷字节数，一条大单还可能生成很多成交和订单变化，因此要同时限制队列条数、载荷与保留对象字节数、最老请求年龄、正在执行或等待提交的 inflight，以及结果和账务的落后量。最老年龄用于暴露等待失控，超过阈值应收紧新准入，而不是删除已经受理的命令；inflight 要覆盖已经出队却尚未完成提交的工作，不能出队就归还全部容量。结果落后应按一致的流定义待处理条数、字节和年龄，不能把账户回报序号减去撮合序号。大单扇出预算也要纳入，内存有界之外还须限制耐久日志积压，避免把内存风险转成磁盘耗尽。

## 第 3 层：Little 定律能够直接算出 p99 所需的队列容量吗？

**面试官：** 指标有了，能否用每秒请求数乘以 p99，直接确定队列长度？

**面试者：** 不能。Little 定律 `L=λW` 描述稳定或足够接近稳态、口径一致时的长期平均量：L 是该边界内平均在系统数量，λ 是进入并经过这个系统的有效平均速率，W 是平均逗留时间，不是 p99。若只算等待区，就应使用平均排队时间；若计入执行和提交中的 inflight，就应使用相应完整停留时间。入口 offered 速率也不能在存在拒绝时冒充 admitted 速率，更不能把命令条数与成交笔数混用。持续到达率高于处理能力时积压发散，不存在可据此推导的稳定平均容量。它适合核对平均量是否自洽，但尾部、突发和大单服务成本分布仍要单独建模，不能靠换成 p99 就得到尾延迟保障。

## 第 4 层：非稳态突发怎样估算新增积压与清退时间？

**面试官：** 既然稳态均值不能描述突发，那到达短时超过服务能力时，你怎样推演？

**面试者：** 假定初始无积压、处理能力近似恒定，按命令条数作流体近似：突发到达率 λ 为每秒 2000 条，处理率 μ 为每秒 1000 条，持续 0.1 秒，则约到达 200 条、处理 100 条，新增积压为 `(2000-1000)×0.1=100` 条。随后 λ 降为每秒 500 条，服务仍为每秒 1000 条，净清退能力是每秒 500 条，清退这 100 条约需 `100/(1000-500)=0.2` 秒，而不是简单除以 μ 得到 0.1 秒。这个计算忽略离散到达、服务时间波动和提交停顿，不是 p99 预测。假如后续到达率并未降到服务率以下，积压就无法按上述时间清退；队列只能暂存，不能创造处理能力。若实际有大单扇出或下游减速，μ 也会变化；因此它只能说明缓冲和拒绝策略需要覆盖怎样的突发假设，不能当作已经测得的容量。

## 第 5 层：撮合还能计算，下游变慢时为什么也要停止放量？

**面试官：** 突发可以缓冲，但现在撮合 CPU 还很空，只是结果提交或账务变慢，为什么要限制入口？

**面试者：** 因为完整业务的处理能力不是撮合循环单独决定的。结果存储变慢，会使待提交批次和 inflight 增加；一旦某次 `ResultBatch + AppliedSeq` 提交结果不确定，执行者必须停止推进依赖该状态的后续计划，核实后再继续，不能先把试算当成交。若结果已提交而账务落后，成交义务已经存在，相关预留仍不能按连接超时释放，此时继续受理只会扩大未结算敞口与恢复工作量。我会把结果提交等待、待发布结果、账户待消费批次的数量、字节和最老年龄纳入准入反馈，并按明确预算逐级收紧。暂停新受理不等于丢弃旧积压，旧命令继续依靠耐久日志和幂等账务完成，系统不能用无限缓冲假装下游仍有能力。

## 第 6 层：给撤单留一个高优先级队列，为什么仍可能进不来？

**面试官：** 下游背压会挡住新请求，但撤单是风险退出通道。单独留一条撤单队列是否就够了？

**面试者：** 不够，撤单到达专用队列以前，可能已经被满连接数、读缓冲、解析鉴权或提交连接挡住；进入队列以后，也可能被新单耗尽日志追加与提交带宽。所以撤单保护需要端到端预留准入容量、字节预算、连接与处理名额，并为耐久命令提交留出预算，结果裁决链路也不能完全被新单挤占。若协议把撤单排在同一 TCP 流的大量新单字节之后，服务端优先级也无法越过未读字节，应在协议和连接策略中明确边界。保护通道仍须鉴权、限制帧长和每账户配额，不能成为无限旁路。预留资源只能提高撤单获得服务的机会，不承诺在存储完全不可用时仍能立即完成，更不允许绕开权威排序直接删单退款。

## 第 7 层：撤单优先从哪里开始生效，何时必须服从既定顺序？

**面试官：** 撤单现在有资源可进来了。为减少风险，能否让后来的 C1 越过已经排队的 B1？

**面试者：** 必须区分权威排序前后的队列。排序前可以按公开明确的公平规则选择下一条待提交请求，例如给撤单预留份额、按账户轮转，并用等待年龄防止普通请求长期饥饿；该规则属于接纳契约，不能事后随意改写。一旦 B1 已耐久提交在前，C1 已确定在后，即使两者还在执行者内存队列中，C1 也不能越过 B1。执行者必须先按 Maker 价完成 B1，使 S2 从 0.20 变成 0.05，再让 C1 撤剩余 0.05。客户端更早点击或本机更早收到都不是重排理由。所谓撤单优先应改善获得排序位置之前的服务机会，而不是推翻已经产生业务约束的日志全序；否则保护一个账户会变成破坏另一个账户的成交公平。

## 第 8 层：一个账户不停撤单和重试，怎样避免耗尽保护通道？

**面试官：** 优先级有边界了，但某账户用大量撤单与超时重试占满预留容量，如何控制？

**面试者：** 我会在全局和交易对预算之外增加每账户的速率、在途与字节配额，必要时约束连接和身份来源，避免单账户把保护通道变成独占通道。重试采用有上限的退避与 jitter，并优先查询原请求状态；同一个逻辑下单重试沿用原 `clientOrderId` 和绑定的 intent、不可变载荷，撤单也沿用自己的撤单请求身份，而不是把撤单伪装成原下单。相同身份但载荷不同应明确冲突，同身份并发尝试可以归并查询，但仍需限制它们消耗的网络和鉴权资源。超时不能自动生成新订单身份，也不能重复预留资金。公平规则还要限制撤单占比并保证普通请求最终获得机会，保护的是风险退出能力，不是允许某账户通过重试数量抢夺顺序。

## 第 9 层：已预留请求等太久，能否按最老年龄直接清理？

**面试官：** 配额挡住了重试风暴，但某个 B1 已预留且提交超时，年龄超过阈值。能否释放资金并删除它？

**面试者：** 不能，年龄阈值是控制准入和发现停滞的信号，不是资金释放凭证。首先按原身份核实命令是否已经提交；若结果未知，就保留预留与耐久意图，不再追加新身份请求。若业务要终止，在相同权威命令顺序中裁决 `AbortIntent` 或对已存在订单撤实际剩余量，并确保迟到的下单提交不能绕过这个终态。只有已提交结果给出预留处置依据，账户才能在本地事务中把去重、消费进度和资产变化一起提交。HTTP 超时、context 取消或连接断开都只表示调用方停止等待，不证明命令未受理，更不会让 GTC 自动过期。客户端生命周期与已受理业务生命周期必须分开，否则满队列与超时叠加时最容易造成已退款订单继续成交。

## 第 10 层：怎样联合检查突发、撤单和结果滞后，而不牺牲正确性？

**面试官：** 如果前述突发期间 B1 在 C1 前已受理，同时结果提交变慢、客户端断线，你怎样判断保护策略没有做错？

**面试者：** 我会按独立窗口手工核对。先确认准入前被拒绝的新请求没有预留；已预留的意图仍可按原身份恢复；已提交 B1 不因队列年龄或断线被丢弃。结果提交未知的窗口必须停住核实，不能放行资金；确认提交后，C1 才按既定顺序撤 S2 的 0.05 BTC。若账务暂时落后，保留结算义务并收紧新准入，恢复消费时 B1 只结转一次，成交额 15015 USDT，价差只返还 10 USDT。慢客户端不应阻塞结果生产，可按回报游标补齐，但不能把私有成交静默丢失。最后核对队列条数、字节、年龄、inflight 和各下游落后量都没有被某个隐藏缓冲绕过；这是一组机制验收条件，不是宣称执行过负载测试。

## 本题收束

- **机制：** 容量许可尽量前置到预留之前；条数、字节、最老年龄、inflight 与下游结果落后联合约束。下游变慢逐级反馈到入口，撤单预留接入与提交资源，并受明确公平规则和账户配额约束。
- **易错边界：** 满 channel 不是退款理由；出队不是业务完成；耐久日志不是无限缓冲。`L=λW` 只用于口径一致的稳态平均量；100 条突发积压和 0.2 秒清退来自给定流体假设，不是实测或尾分位数。撤单优先仅能在权威排序前影响接纳，不能让已排序的 C1 越过 B1。
- **验证反例：** 检查已预留后丢包、超时换身份、无限撤单优先、结果未知却继续计划、账务滞后却释放预留，以及慢客户端拖住执行者。无论拥塞发生在哪一段，最终订单与资产仍须守恒；超时不是自动取消，资金释放只接受已提交业务依据。
