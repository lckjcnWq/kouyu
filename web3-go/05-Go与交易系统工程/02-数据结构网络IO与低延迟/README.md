## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 托管现货 CLOB | 平台保管资产、把买卖限价单排成簿来撮合的市场。 | 买的是实际 BTC，不是永续仓位；这里不走链上结算。 |
| GTC / Maker 价 | 订单可持续挂着，直到成交或被正式撤销；成交按簿上原挂单价格。 | B1 限价 60100，吃 S1 时仍按 60000 成交。 |
| tick / lot | 价格与数量各自允许的最小整数格子。 | 价格一格为 0.01 USDT/BTC，数量一格为 0.0001 BTC，乘积单位为 0.000001 USDT。 |
| intent / reservation | 下单意图及为它占住的资产，必须绑定同一份订单参数。 | B1 先预留 15025 USDT；预留不等于已经花掉，也不等于命令已受理。 |
| commandSeq / 可靠受理 | 命令在本交易对耐久日志中的位置；可靠受理承诺命令可恢复。 | 进入 channel 不算；取得已提交位置也不说明撮合完成。 |
| 单写者 / 私有工作状态 | 一个有效执行者改这本簿；试算中的变化先藏在内部。 | B1 试算消耗 S1、S2 后，未提交的结果仍不能给查询或账户使用。 |
| ResultBatch / AppliedSeq | 一条命令的完整结果，以及与结果共同提交的执行进度。 | 两笔成交、订单变化和预留处置依据一起确定，不能只交半份结果。 |
| PENDING / 账务结转 | 前者表示资产处理尚未完成，后者才把成交义务记到账上。 | B1 可以先报全成；15015 支出、0.25 BTC 入账、10 USDT 返还仍须账户事务提交。 |
| 价格树 / FIFO / ID 索引 | 分别解决找最优价、同价排队、按订单身份定位。 | P 个价位、N 个订单、K 个触及订单分别计成本，Big-O 不等于端到端耗时。 |
| 有界预取 / inflight / 背压 | 只提前拿有限工作，出队但未完成的也算在途；下游慢就收紧入口。 | 条数之外还算字节、年龄、扇出和耐久积压，不能把无限排队搬到日志里。 |
| group commit / 三阈值 | 多份结果合用一次有效提交，以条数、字节或最长凑批等待触发。 | 摊薄固定成本，不改变顺序，也不允许提前确认成交。 |
| TCP / deadline | TCP 搬运有序字节，deadline 是相应读写方向的绝对截止时刻。 | 必须自行分帧、处理部分读写；写成功不证明对端应用或业务提交成功。 |
| streamID / epoch / seq | 标识是哪条流、哪一代序列，以及流内位置。 | 私有 reportSeq、公共盘口 seq、撮合 commandSeq 分开保存，不能互相减出缺口。 |
| 公共 L2 / 快照锚点 | L2 是各价位剩余量；锚点说明快照已覆盖到哪里。 | 绝对数量增量只覆盖列出的档位，零量删除不能被随意丢掉。 |
| sync.Pool / 最后读者 | 临时对象的复用缓存，以及最后一个仍会访问对象的人。 | 池可随时未命中，不管引用生命周期；异步结果被读完前不能归还。 |
| netpoll / runnable / GC | 分别是网络就绪机制、等 CPU 的可运行状态、垃圾回收。 | 网络等待、调度等待、分配与回收成本要分开定位，不能统称运行时慢。 |
| λ / μ / Little 定律 | 到达率、处理率，以及稳态平均数量与平均停留时间的关系。 | L=λW 不用 p99 代替平均 W；持续 λ≥μ 不能推出稳定容量。 |
| p99 / 开环 / 证据边界 | p99 是样本的第 99 百分位；开环按计划到达，不等上笔完成。 | 比较同一完成阶段，保留拒绝、超时和未完成项；文中无生产实测结论。 |

## 把整篇文章压缩成一个故事

甲有 20000 USDT，想在托管现货市场买 0.25 BTC，限价 60100。簿上 S1 卖 0.10 BTC、价格 60000，S2 卖 0.20 BTC、价格 60100，卖方资产都已预留。系统先为 B1 占住 15025 USDT，让甲可用降到 4975，再把绑定原参数的命令耐久提交。此时只能承诺可靠受理，不能因为网络收到了消息或 channel 发送成功就说已经买到币。

单写者按命令顺序，用价格树找档、FIFO 取单，先买 S1 的 0.10，再买 S2 的 0.15。两笔共花 15015，S2 还挂着 0.05。完整结果与 AppliedSeq 共同提交后，才可发布全成回报；账户仍可处于 PENDING。账户事务随后一起结转买卖双方、去重并推进消费进度，甲得到 0.25 BTC、退回价差 10，最终可用 4985 USDT。排在 B1 后的 C1 只能撤 S2 余下的 0.05。

若流量变大，工程师可以改善布局、批量提交、分片和网络交付，但不能让 C1 插队，不能提前报试算成交，也不能把仍有读者的切片还池。慢客户端由有界缓存和游标恢复隔离，公共盘口缺口则补齐或重建。最后要分清排队、netpoll、调度和 GC，按相同承诺检查尾延迟、失败与积压；文末的小模型只做内存手工演算，不实现这整套可靠链路，更不是已完成的压测。

## 第一部分：文字全流程

### 1.1 讨论基线与准备条件

采用与[撮合交易从 0 到 1](../../01-撮合交易与核心链路/01-撮合交易从0到1/README.md)一致的**托管现货 CLOB、链下撮合、链下账务结转**模型。只支持限价 GTC，价格优先、同价按权威接纳顺序优先，Maker 价成交；买卖账户不同，手续费为零。AMM、永续合约、链上结算属于改变前提后的比较，不混入本例。

Go 讨论以 **Go 1.21+** 为起点；调度器、GC 和网络轮询器的内部实现、工具选项及容器 CPU 默认行为随具体 Go 版本、操作系统而变，不把当前某一版本内部细节当语言契约。只需能手工维护队列、订单簿与资产表，不需要安装数据库、消息队列或压测工具。

### 1.2 贯穿案例

卖方资产已预留，卖盘有 S1：`0.10 BTC @ 60000 USDT/BTC`，S2：`0.20 BTC @ 60100 USDT/BTC`。甲有 20000 USDT 可用，提交 B1：`买入 0.25 BTC，限价 60100，clientOrderId=buy-001`。

```text
甲预留：0.25 × 60100 = 15025 USDT，可用降为 4975 USDT
B1 吃掉 S1：0.10 × 60000 = 6000 USDT
B1 再吃 S2：0.15 × 60100 = 9015 USDT
成交总量：0.25 BTC；成交总额：15015 USDT
账务结转后：甲 BTC 可用增加 0.25，USDT 可用为 4985，预留为 0
价差返还：10 USDT；S2 剩余 0.05 BTC，仍预留这部分 BTC
```

引入 C1：撤销 S2 剩余量，仅在讨论 B1 **之后**的顺序时使用。其他异常题是独立变体，不能让同一 S2 在不同失败假设中被重复消耗。

### 1.3 主链路：低延迟必须服务于完整业务

```text
甲经 TCP/TLS 连接提交 B1
    ↓
接入层分帧、鉴权、整数精度检查、请求身份与载荷核对
    检查入口容量；未进入业务的请求可明确拒绝
    ↓
账户域本地事务：创建下单意图、预留 15025、绑定不可变订单参数
    ↓
提交器向 BTC/USDT 耐久命令日志提交 Place(B1, reservationId)
    返回 commandSeq：可靠受理，尚不代表成交
    ↓
交易对单写者按已提交 commandSeq 取命令
    有界预取；不可因为撤单优先级或并行 worker 改写已确定顺序
    ↓
在私有工作状态上计划撮合
    价格索引找到 60000 → FIFO 取 S1 → 再到 60100 的 S2
    生成两笔成交、订单变化、预留处置依据
    ↓
原子提交不可变 ResultBatch + AppliedSeq
    提交确认前不向外暴露试算结果；不确定时停住并核实
    ↓
发布已提交状态与结果
    ├─ 私有回报：B1 全成，账务状态 PENDING；可按回报游标补发
    ├─ 公共行情：两笔成交与价位绝对数量变化；缺口时补齐或重建
    └─ 账户域：按交易对结果顺序消费完整批次
                     ↓
               本地账务事务：去重、扣预留、双边入账、退 10、提交进度
                     ↓
               账务完成；查询投影追上对应版本
                     ↓
客户端应用对应订单/账户版本，更新页面或恢复查询
```

网络读成功、进入 channel、命令耐久受理、撮合结果提交、账务完成、页面可见是不同终点。可以先发已提交成交回报再做账务，但回报必须说明完成阶段，不能把全成解释为账户已经可花费。

### 1.4 主要分支与状态归属

```text
帧过大 / 鉴权失败 / 入口容量不足且尚无业务副作用
    → 明确拒绝，不预留、不成交

预留成功，提交超时或内部队列满
    → 保留原 intentId 与预留，查询/重试原意图
    → 要关闭时，在同一命令顺序裁决 AbortIntent / 撤实际剩余量
    → 账户依据已提交结果释放；不能把本地满队列当成可直接退款依据

命令已受理，撮合/结果存储暂慢
    → 限制预取与新受理，保留可恢复积压，不丢已受理命令

结果提交结果不确定
    → 停止发布试算与后续依赖状态 → 依据耐久边界恢复核实

成交已确定，账务事务失败
    → 成交义务保留，必要预留不释放 → 幂等重试完整结果批次

客户端慢 / 写超时 / 断线
    → 有界缓冲、断开或显式失效；从耐久回报补发/按锚点重建
    → 不撤销已经提交的订单与成交
```

| 阶段 | 权威状态的拥有者 | 本例变化与完成含义 |
|---|---|---|
| 预留提交 | 账户域 | 可用 4975、预留 15025；不是撮合受理 |
| 命令提交 | 命令日志的排序与提交机制 | Place 有可恢复位置；不是成交完成 |
| 结果提交 | 撮合域 | B1 全成、S1 清空、S2 余 0.05；禁止再随意撤销成交 |
| 账务提交 | 账户域 | 甲 4985 USDT、0.25 BTC 可用，预留归零 |
| 回报应用 | 客户端/查询投影 | 表示读模型追到某版本，不创造新的成交事实 |

## 第二部分：核心板块

1. **订单簿及状态所有权。** 价格树、同价 FIFO 与订单定位索引共同决定公平性和撤单成本。单写者拥有可变簿；其他 goroutine 使用不可变结果或版本化投影，不能直接遍历正在变动的 map/list。
2. **排序、容量与提交流水线。** 按交易对有界预取，顺序裁决，结果提交后才发布。排队长度、最老年龄与下游积压决定是否继续接单，不能用无限 channel 隐藏容量不足。
3. **协议与推送。** 连接读写只搬运字节；接入负责完整命令解析，回报负责可恢复游标。公共状态可以按契约合并，私有事实不能静默丢失。
4. **Go Runtime 与内存。** 分配率、存活集、扫描、调度等待及 CPU 配额共同影响尾延迟；对象的实际最后读者决定回收时点，不能为了少一次分配造成串单或数据竞争。
5. **性能证据。** 用同一完成承诺、负载分布和错误统计比较优化；先分阶段定位，再用 profile、trace 和资源指标验证因果。

## 第四部分：设计与规则

### 4.1 业务不变量与精度

- 订单原始量 = 累计成交量 + 撤销量 + 当前剩余量，四者非负；B1 两笔成交合计 0.25 BTC，S2 剩余 0.05 BTC。
- 价格时间优先以权威命令处理与接纳顺序为准，不以客户端时间戳或哪个 goroutine 先拿到锁为准。
- 卖方剩余挂单必须有 BTC 预留；买方成交义务和剩余挂单必须有对应 USDT 预留。超时、入队或连接关闭都不授予释放权。
- 结果批次与 AppliedSeq 共同提交；账务变化、消费去重与进度在账户域本地事务共同提交。性能优化不得削弱这些边界。
- 使用定点整数：教学精度为价格 tick `0.01 USDT/BTC`、数量 lot `0.0001 BTC`，乘积单位为 `0.000001 USDT`。`priceTicks × quantityLots` 必须检查整数溢出，再按明确舍入规则转换到实际账务精度；本例恰能整除。不能用 float64 比较价位或累计资产。

### 4.2 架构、对象与顺序

```text
连接 reader → 有界解析/鉴权 → 账户预留/意图 → 命令提交器
                                                   ↓
                                            已提交命令日志
                                                   ↓ 按交易对有界预取
                                      单写者：工作簿 + 订单索引
                                                   ↓
                                    ResultBatch + AppliedSeq 原子提交
                                                   ↓
                     不可变结果 → 账户事务 / 私有回报日志 / 公共行情投影
                                                   ↓
                                   有界连接队列 → 连接 writer → 客户端
```

| 对象 | 必要字段与约束 |
|---|---|
| 命令 | `accountID, symbol, clientOrderID, intentID, reservationID, payloadHash, commandSeq`；幂等身份与完整载荷绑定 |
| 价位/订单 | 价格树节点、FIFO 首尾、订单 ID、剩余整数数量、前后链接；索引只由当前单写者更新 |
| 结果批次 | `symbol, commandSeq, resultID, trades[], orderChanges[], reservationActions[]`；发布后不可变，消费者拿不到半个批次 |
| 容量状态 | 当前条数、字节数、最老年龄、在途数、下游落后量；不能只看 channel 长度 |
| 私有回报 | 按账户定义 `streamID, epoch, reportSeq` 和应用确认；与撮合 commandSeq 分属不同命名空间 |
| 公共 L2 帧 | `streamID, epoch, prevSeq, seq` 与价位绝对剩余量，零量表示删除；只在规定连续关系成立时应用 |
| 测量上下文 | 请求身份、完成阶段、单机单调时长、队列与资源标签；跨机器时间需校时与误差说明 |

`commandSeq` 不必等于 `reportSeq` 或盘口 `seq`，一条命令可以产生两笔成交，多个源结果也可合成一个公共状态帧。不能跨流直接减游标计算丢包。

### 4.3 实现选择与容量口径

- 基线用**平衡价格树＋价位内双向 FIFO＋订单 ID 哈希索引**。P 为价位数、N 为活跃订单数，价位新增/删除为 O(log P)，同价追加与已定位节点摘除为 O(1)，哈希查找通常期望 O(1)；清空价位还要付索引维护成本。Go 标准库没有内建有序 map，具体平衡树实现需单独验证。
- 单写者可复用工作缓冲，但发给异步消费者的结果必须复制或明确移交所有权；不默认“放入 channel 后就能 Put 回 sync.Pool”。
- 按交易对分片，不能靠给同一本簿增加多个独立撮合 worker 来水平扩容。账户域仍须处理跨交易对共享余额竞争。
- 所有缓冲需考虑条数和字节预算，大单的成交扇出还需计执行成本。已受理命令的剩余积压由耐久日志承载，内存只预取有限窗口；日志保留与磁盘也必须有容量策略。
- 近似稳态中 `L=λW` 用于口径一致的平均量，不能直接用 p99 代替 W，也不能用 `λ≥μ` 的持续发散队列推导稳定容量。突发粗估 `新增积压≈(λ-μ)×持续时间`，清退时间还取决于后续到达量。
- 不预设生产 SLO 或宣称固定微秒级吞吐。可给阶段预算作为待验证目标，但必须随相同的耐久承诺、流量分布与错误率一起报告。

## 第七部分：工程实践——一个简洁 MVP

### 7.1 目标与范围

手工验证**有界入口、严格 FIFO 处理、最优卖价与同价顺序、按 ID 撤单和数量守恒**这一小闭环。只允许一个买入 B1 和撤销已存在卖单，初始卖单已按案例准备；不实现预留、持久化、网络、并发、真实树库或账务，因此输出只能叫“内存演算结果”，不能称生产系统已经可靠受理或结算。

### 7.2 核心伪代码

使用有序映射作为抽象数据结构，升序取最小卖价；每档是双向 FIFO，`byID` 直接定位节点。下述树查找、插删和链表摘除是明确的数据结构原语，不代替任何持久化或一致性能力。输入数量单位均为 `0.0001 BTC`，价格单位为 `0.01 USDT/BTC`。

```text
asks = 有序映射{6000000: FIFO[S1(1000)], 6010000: FIFO[S2(2000)]}
byID = {S1: 对应节点, S2: 对应节点}; queue = FIFO(); capacity = 2
seen = 空映射; input = 空映射; events = []

submit(cmd):
    key = (cmd.account, cmd.requestID)
    if key in input:
        if input[key] != cmd.payload: return PAYLOAD_CONFLICT
        return seen.get(key, QUEUED_IN_MEMORY)
    if queue.length == capacity: return REJECTED_BEFORE_ENQUEUE
    input[key] = cmd.payload
    queue.pushBack(cmd)
    return QUEUED_IN_MEMORY

drainOne():                              # 单一执行者，整条命令处理完才处理下一条
    cmd = queue.popFront(); key = (cmd.account, cmd.requestID)
    if cmd.type == CANCEL:
        node = byID.get(cmd.orderID)
        if node == nil: result = NOT_OPEN
        else if node.account != cmd.account: result = FORBIDDEN
        else:
            qty = node.remaining; level = asks[node.price]
            level.unlink(node); delete byID[node.id]
            if level.empty: delete asks[node.price]
            result = CANCELED(qty)        # 只有内存撤销量，不代表已退资金
    else:                                # 本 MVP 只接 B1 这种完全可成交的限价买
        remaining = cmd.qty; fills = []
        while remaining > 0 and asks.notEmpty:
            price = asks.minKey()
            if price > cmd.limit: break
            level = asks[price]; maker = level.front
            qty = min(remaining, maker.remaining)
            fills.append(maker.id, price, qty)
            remaining -= qty; maker.remaining -= qty
            if maker.remaining == 0:
                level.unlink(maker); delete byID[maker.id]
            if level.empty: delete asks[price]
        result = BUY_SIMULATED(fills, remaining) # 未成交余量不挂单；不是完整 GTC 实现
    seen[key] = result
    events.append(key, result)             # 仅内存记录，崩溃即丢
    return result
```

本 MVP 不覆盖买单余量挂盘，故只用完全可成交的 B1 验证买入；若输入其他买单，返回未成交余量而不宣称支持完整 GTC。它没有超时取消和重启幂等，不能拿这几十行代替前文生产契约。

### 7.3 输入与预期结果

以下是手工推演，非测试执行结果。账户甲对应 B1，账户丙拥有 S2。

| 输入序列或独立变体 | 预期结果 |
|---|---|
| 依次 submit B1、submit 丙的 C1；再 submit 另一个新请求，尚不 drain | 前两项仅返回内存排队；第三项明确拒绝，不留下 input 去重条目，更没有预留 |
| 接上行 drain B1 | 先成交 S1 的 1000，再成交 S2 的 1500；B1 余零、S2 余 500，即 0.05 BTC |
| 再 drain C1 | 只撤 S2 剩余 500；簿为空，不得撤掉原始 2000 或 B1 已成交部分 |
| 重新 submit 相同身份、相同载荷的 B1 | 返回原内存结果，不产生新成交；若进程重启，此保证不成立 |
| 相同身份把 B1 数量改为 3000 | 返回 PAYLOAD_CONFLICT，不再撮合 |
| 独立变体：甲尝试撤销丙的 S2 | 返回 FORBIDDEN，S2 不变；需要丙重新使用合法撤单身份 |

本例成交额整数为 `6000000×1000 + 6010000×1500 = 15015000000` 个 `0.000001 USDT`，即 15015 USDT。资产预留与返还沿用总览业务案例的数学结果，**不由本 MVP 伪代码实现**。
