# 大问题 1：一笔订单怎样走完低延迟交易链路，哪些边界不能为了快而省掉？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 托管现货 / GTC | 平台保管实际资产，未成交限价单可以继续挂着。 | 本例交易 BTC/USDT，不涉及杠杆或链上结算，断线不会自动撤单。 |
| B1 / S1 / S2 | 买单与两笔已有卖单的身份。 | B1 买 0.25 BTC、限价 60100；S1 卖 0.10、价 60000，S2 卖 0.20、价 60100。 |
| intent / 资产预留 | 固定下单参数的意图，以及先为它占住的资产。 | 从甲的 20000 中预留 15025 USDT，剩余可用 4975；尚不是撮合受理。 |
| commandSeq / 耐久命令日志 | 命令的权威位置，以及进程退出后仍可恢复的命令记录。 | 日志提交后才承诺可靠受理；内存入队或唤醒不能替代它。 |
| 单写者 / 工作簿 | 某交易对唯一有效修改者及其可变订单簿。 | 不让查询 goroutine 直接遍历正在变化的树、队列和索引。 |
| FIFO / 价格时间优先 | 先选最合适价格，同价按权威接纳顺序排队。 | 不以预处理 worker 完成顺序或客户端时间决定先成交谁。 |
| ResultBatch / AppliedSeq | 一条命令的完整裁决，以及共同提交的执行进度。 | B1 两笔成交、订单变化和预留处置依据不能只提交其中一部分。 |
| PENDING / settlementStatus | 资产处理尚未完成，以及说明资金完成阶段的字段。 | 已提交全成回报可以早于账务，但不能把 BTC 提前算为可花费资产。 |
| 账户事务 / 消费去重 | 将本批资产变化与处理身份、进度一起提交。 | 最终支出 15015、返还 10、得到 0.25 BTC；重试不能再次入账。 |
| 不可变快照 / 投影 | 固定版本的只读值，以及根据已提交事实整理出的查询视图。 | 内部切片也不能继续被写；读滞后须用版本解释。 |
| 查询屏障 | 让权威执行者在明确处理位置回答一次查询。 | 返回对应 AppliedSeq，不等于放开所有读者访问可变簿。 |
| 有界预取 / 背压 | 只取有限命令，下游慢时减少继续承诺的新工作。 | 同时控制条数、字节、年龄、在途结果与账务积压，不只扩大 channel。 |
| group commit | 多个连续完整结果共用存储实际支持的提交边界。 | 可以摊薄固定开销，提交成功后才依序发布；不能先报成交再落盘。 |
| 提交未知 | 调用没拿到确定结果，但持久写入可能已发生。 | 停住该市场依赖状态的推进与发布，核实耐久进度，不猜失败或退款。 |
| 单调时钟 / 跨机误差 | 前者用于本机经过时间，后者说明机器间时钟并非天然一致。 | 不把未校准的跨机时间相减后称为精确微秒延迟。 |
| p99 / 完成口径 | 一组样本的第 99 百分位，以及测量到哪一步算结束。 | 各阶段 p99 不能相加；固定资源、负载与耐久承诺后才比较端到端收益。 |

## 把整篇文章压缩成一个故事

甲有 20000 USDT，提交 B1，想按不高于 60100 的价格买 0.25 BTC。系统先检查完整消息、身份和精度，绑定下单意图并预留 15025，让可用降到 4975；再把命令提交到 BTC/USDT 耐久日志，才回复可靠受理。甲此刻只是知道请求不会因进程退出而凭空消失，还不能认为已经成交，更不能提前花掉预期得到的币。

单写者按日志顺序先买 S1 的 0.10 BTC、花 6000，再买 S2 的 0.15、花 9015，S2 留下 0.05。工作簿算完不算最终承诺，完整结果和 AppliedSeq 共同提交后才发布全成。若账户还在 PENDING，15025 预留继续覆盖义务；账户事务随后一次结转两笔成交、去重和进度，给甲 0.25 BTC、返还 10 USDT，可用最终为 4985。订单页面、资金页面和网络回报可以到达不同阶段，不能互相冒充。

甲嫌回报慢，工程师不能只把撮合函数改快或把 channel 开大。要沿同一请求找出等预留、等日志、等执行、等结果提交和等客户端应用各用了多久，再隔离慢消费者、限制积压、优化独立阶段。若结果提交超时，先停住核实，不能提前公布后续试算；撤单即使有预留容量，也不能改写既定顺序。文中数字只作教学推演，真正收益须在同负载、同承诺下连同失败率和积压验证。

**流程位置与核心机制：** 从连接入口到撮合、账务与客户端完成，建立后续结构、网络、Runtime 和性能测量共用的架构。本题讲清全貌与阶段责任；具体交易一致性证明见第 11 题。

**必要前提：** 沿用总览的托管现货 GTC、单交易对单写者、耐久命令与结果提交模型。所有数字是教学案例，不是生产性能。

## 第 1 层：先完整回答系统怎样工作

**面试官：** 让你用 Go 设计一条低延迟下单链路，从用户发起到业务完成，你会怎么设计？

**面试者：** 我会先把“快到哪一步”说清楚，再谈优化。连接接收完整请求，接入层鉴权、检查价格数量精度与请求身份；账户域在事务中预留资产并绑定订单意图；提交器把命令送入交易对的耐久日志，提交后才算可靠受理。交易对只有一个有效写者，按已提交序号撮合，原子提交结果批次与处理进度后，才发布成交和订单状态。

已提交结果分给账户消费者、私有回报和公共行情。账户事务按完整结果结转资产，同时保存消费去重与进度；查询和客户端再追上相应版本。这样受理、成交、账务完成和页面可见都有独立边界。实现上分别优化接入分帧、簿访问、排队、批量提交和回报，但不会为了减少一次等待，把内存入队伪装成可靠受理。

## 第 2 层：用同一笔订单落到具体状态

**面试官：** 你区分了成交和账务完成，那 B1 在两者之间到底是什么状态？

**面试者：** B1 是买入 0.25 BTC、限价 60100，先预留 15025 USDT，甲可用余额降到 4975。它与 S1 成交 0.10、与 S2 成交 0.15，总支出 15015；撮合结果批次提交以后，B1 的订单状态可以是全成，S2 只剩 0.05，但甲的账务结转还可能是 PENDING。

这段暂态允许存在，前提是 15025 的预留仍覆盖已确定的成交义务。账户事务提交时，扣成交额、给买方 0.25 BTC、给两个卖方入账、返还 10 USDT，甲最终可用 USDT 为 4985、预留为零。客户端看到全成不能据此绕开账户域直接增加可用资产。低延迟回报可以早于账务完成，但必须有明确的 settlementStatus 或等价阶段语义。

## 第 3 层：谁拥有权威簿，读请求从哪里来

**面试官：** 你说撮合只有一个写者，如果查询和行情也直接读这个订单簿，会不会更快？

**面试者：** 不能只比较少一次复制。单写者会连续修改价格树、FIFO 和订单索引，另一个 goroutine 同时遍历可能读到某个索引已删除、队列却未摘除的中间状态，也可能发生数据竞争。只给 map 加锁也不等于整个跨结构状态一致，还会把慢查询的等待带入撮合热路径。

在这个模型里，可变工作簿由撮合执行者独占；查询和行情读取已提交结果驱动的投影，或读取带版本的不可变快照。发布结果不能继续引用之后还会被修改的工作切片。代价是复制、投影计算和短暂读滞后，但它们可单独测量和限流。如果要求读取订单当前权威状态，可以向写者发查询屏障并返回明确 AppliedSeq，而不是无条件放开任意并发访问。

## 第 4 层：有了投影，怎样知道延迟花在哪里

**面试官：** 你把查询和推送异步化了，用户仍然说下单很慢，你怎样定位而不只看撮合函数耗时？

**面试者：** 我会用同一个请求身份记录阶段边界：接收完整帧、预留开始与提交、命令提交、执行开始、结果提交、账务提交、回报写出和客户端应用。单进程内用单调时钟测经过时间，把每段等待与服务时间分开；跨机器时间要说明校时误差，不能简单相减后声称得到精确微秒延迟。

例如执行只耗少量时间，但命令从受理到执行等了很久，问题首先是积压而非价格树算法；结果已经提交而客户端迟迟没应用，重点检查回报队列、网络和客户端处理。持久化等待、账户争用与调度等待也应独立观察。p99 是一组端到端样本的分位点，不能把各阶段的 p99 相加当作真实端到端 p99，因为各阶段最慢的未必是同一请求。

## 第 5 层：队列把慢隔开，也可能把慢藏起来

**面试官：** 如果受理到执行的等待过长，你把 channel 开大一点，让接入不阻塞，不就改善体验了吗？

**面试者：** 这只可能把阻塞从接入调用搬到队列里，未必减少用户等待。到达量持续超过处理能力时，扩大队列会增加内存、排队年龄和请求超时；受理回得快并不代表订单更快完成。还要计命令对象大小、大单成交扇出、在途结果，以及下游账务和回报的积压，不能只看一个 channel 的条数。

我会限定预取窗口，并在业务副作用之前按容量收紧准入；命令已可靠受理后，就不能因本地满队列把它丢掉，而应保留耐久积压并停止继续扩大承诺。对于已预留但提交结果不确定的请求，保留意图查询和恢复。撤单可以预留接入资源，但已确定的权威顺序不可被后来的撤单随意重排。排队治理见第 05 题。

## 第 6 层：异步优化不能跨过提交确认

**面试官：** 既然持久化也会排队，能否先用内存结果给用户报成交，后台慢慢落盘？

**面试者：** 在本模型的承诺下不能。结果批次是订单变化、成交身份和预留处置依据的共同事实；还没提交就报成交，进程崩溃后可能恢复不到这笔成交，但客户端和账户消费者已经认为它存在。只耐久记录输入也不自动证明输出唯一，还需要确定性规则、回放和事件身份等条件。

可以改进的是提交方式而不是偷换提交边界：连续命令按顺序试算，完整结果一起 group commit，提交成功后依序发布；批次需要条数、字节和最长等待上限。若提交返回不确定，不得继续基于可能未提交的状态对外发布下一笔结果，而要核实耐久进度后恢复。如果确实改成更弱的易失承诺，必须作为另一种产品协议公开讨论，不能和原方案用同一“成交延迟”数字比较。

## 第 7 层：哪些工作并行，哪些工作必须有序

**面试官：** 你不让提前报成交，又保留单写者，怎样继续提升吞吐？是不是只能换更快的机器？

**面试者：** 不是所有工作都必须串行。不同交易对可以分片并行，网络解析、鉴权、序列化、投影和只读计算也可与撮合流水执行，但进入某个订单簿后的裁决顺序必须唯一。并行预处理完成顺序不能偷偷变成同价时间优先的依据；提交器仍需定义排序与受理点。

单簿内部可以减少索引查找、分配和锁，控制批处理等待，使用局部性更好的数据布局。外部慢消费者应由不可变结果和有界队列隔离。若瓶颈是账户的共享余额争用或结果提交设备，增加撮合 worker 不解决问题，反而增加竞争。我的原则是先找限制阶段，再并行独立工作；需要修改单簿规则或拆市场时，明确这是业务及架构变化，不假装只是开了更多 goroutine。

## 第 8 层：怎样证明优化提升了真实业务

**面试官：** 假设改完以后撮合函数快了一倍，你怎样证明用户真的受益，而且正确性没退步？

**面试者：** 我会固定机器资源、Go 版本、订单簿规模、冷热交易对分布、下单撤单比例及同样的持久化承诺，对照端到端完成率与延迟，而不只测函数。持续到达与突发到达都要覆盖，统计拒绝、超时、积压年龄和恢复耗时；如果函数更快但结果提交队列更长，整体收益可能没有出现。

正确性方面检查同价顺序、订单数量守恒、成交总额、账户预留和结果重复处理。用本例应始终得到两笔成交、15015 支出和 10 返还；将进程崩溃、慢存储和断线作为验证场景时，不能出现“已报全成但恢复后没有成交”或超时直接退预留。这里只描述验证方法，不表示已经做过压测或故障注入。具体统计口径在第 13 题展开。

## 本题收束

- **讲透的机制：** 以请求身份串起网络、预留、命令、撮合结果、账务和客户端各阶段，先定义终点再优化。
- **易错边界：** channel 入队不是耐久受理，socket 写成功不是客户端应用，撮合全成不是账务完成，异步化不是允许提前确认。
- **反例与验证：** 在结果提交前崩溃，若客户端已收到确定成交而恢复后没有同一成交身份，说明所谓低延迟跨越了错误的确认边界。
