# 大问题 4：分片能否解决热门交易对瓶颈，迁移时怎样守住单写顺序？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 交易对分片 / 热点 | 把不同市场交给不同执行单元；热点是特别繁忙的那个市场。 | BTC/USDT 可与冷门对隔离，不意味着一本簿能随意拆给多个独立撮合者。 |
| 单写者 / worker | 前者是状态的唯一有效修改者，后者只是处理工作的执行单元。 | 多个 worker 从同一旧簿成交，可能重复消耗 S1，也可能破坏同价顺序。 |
| commandSeq | 本交易对已确定的权威命令位置。 | B1 在 C1 前，就先成交，再裁决 C1 能撤多少，不能靠抢锁改序。 |
| AppliedSeq | 与完整结果一起原子提交的执行进度。 | 日志受理到哪里，与结果确定到哪里是两个水位。 |
| 有界预取 / 在途结果 | 只提前读有限命令，并统计尚在处理或等待提交的结果。 | 热门对不能通过无限预取耗尽共享内存和提交能力。 |
| GOMAXPROCS / CPU 配额 | Go 并行执行能力设置，以及操作系统实际给的 CPU 时间额度。 | 每对一个 goroutine 不等于每对独占 CPU，隔离还要看共享资源预算。 |
| 共享账户域 / 本地事务 | 不同市场共同使用的资金权威，以及同一数据库内共同提交的边界。 | 甲只有 20000 USDT，两笔各要 15025 的订单不能都通过预留。 |
| intent / reservation | 绑定不可变参数的下单意图及其资产预留。 | 迁移不能另冻一次，提交未知时也不能丢意图或直接退款。 |
| 热路径 / 成交扇出 | 串行裁决的必要工作，以及一条命令产生多个结果。 | 跨多档大单比普通插单昂贵；把编码移出不等于允许多个写者改簿。 |
| handoff / H | 写权交接协议，以及封住旧接纳区间后的最后已提交业务序号。 | H 必须来自查清在途追加后的耐久前缀，不是复制内存那一刻随便记个数。 |
| 受控排空 | 停止扩大旧区间，把已确定区间内的工作完成并确认。 | 旧 writer 完成到 H，核实 ResultBatch 与 AppliedSeq=H 后再停。 |
| K / 恢复锚点 | 较早的可信快照位置，以及从哪里继续恢复的依据。 | 快照在 K，就用耐久材料恢复到 H，不能重复发布已存在的成交。 |
| epoch / fencing | 执行者代次，以及实际资源拒绝旧代次写入的机制。 | 命令追加端与结果存储都要限制旧写者，事务外看一次迁移标记不够。 |
| 预期 AppliedSeq | 写入时要求当前进度等于约定前序位置。 | 与代次一起原子校验，阻止旧写或跳步覆盖结果。 |
| 提交未知 / 在途收敛 | 写入可能已发生但响应不明；逐个确认旧请求最后的去向。 | 屏障外若仍有旧写或未知提交，不得宣布交接完成。 |
| 发布资格 / 账户消费进度 | 谁能发布已提交结果，以及账务已处理到的位置。 | 晚通知按稳定身份去重；账户落后不等于撮合没完成，迁移不能抹掉结算义务。 |

## 把整篇文章压缩成一个故事

BTC/USDT 太忙，工程师小周想把它从公共进程迁到独立资源组。B1 买 0.25 BTC，会先消耗 S1 的 0.10，再消耗 S2 的 0.15；若两个 worker 同时从旧簿出发，可能把同一流动性卖两遍。于是小周先按交易对保持唯一写者，限制热门对的预取、结果和共享提交资源，而不是把多开 goroutine 当作多出一颗 CPU。账户余额仍由账户域保护，搬簿不会搬走资金权威。

真正迁移时，小周先停新准入、收拢在途提交，按原身份查清超时追加，再封住旧接纳区间，耐久记下最后序号 H。旧写者把命令完成到 H，确认结果与 AppliedSeq=H 共同提交；若快照只到 K，就用耐久材料恢复到 H，不能把未提交试算当恢复事实。命令日志到 H 仅表示受理，结果到 H 才表示裁决确定，账务还可能落后，这三个位置不能混叫完成。

接着，命令追加端和结果存储必须真正拒绝旧代次，旧在途写入也须逐笔收敛，再次核实屏障与结果。仅切路由或看到旧进程停住不够，旧进程醒来仍可能写。新写者验证恢复状态后才从 H 后继续；B1 原有两笔成交不重做，账户最终只支出 15015、返还 10，后序 C1 只撤 S2 的 0.05 BTC。若仍有未知提交就继续停住，不能拿内存校验正确代替完整交接证明。

## 流程位置与核心机制

本题位于“账户预留与意图 → 耐久命令日志 → 交易对执行 → 结果提交”的交界处。交易对分片解决不同订单簿之间的隔离与调度，不能自然消除一本热门订单簿内部的串行依赖。迁移转移的是**某交易对从确定日志位置继续执行的写入权**，不是简单更换路由或复制内存。

## 必要前提

- Go 1.21+、业务规则、整数精度、S1/S2/B1 贯穿案例与共同提交边界，统一引用 [README 共同基线](README.md)。
- C1 仅指排在 B1 之后、由 S2 所属账户提交的撤单，只能撤实际剩余量。各故障推演互为独立变体，不在同一份订单上重复扣减。
- `commandSeq` 是本交易对的权威命令顺序；`AppliedSeq` 是已经与结果原子提交的执行进度。账户消费进度属于账户域，不等于撮合进度。
- 本题只讨论热点隔离与受控迁移，不展开完整高可用选举、跨地域复制或故障切换体系；以下均为机制推演，不是实测结论。

## 第 1 层：为什么以交易对分片，而不是给一本簿增加多个撮合 worker？

**面试官：** BTC/USDT 请求越来越多，把订单发给多个 worker 并行撮合，不就能扩容了吗？

**面试者：** 不能直接这样做。B1 会同时读取最优卖价、消耗 S1、部分消耗 S2，并修改订单索引；这些变化是一条命令的连续裁决。如果两个 worker 从相同旧状态各自成交，就可能重复消耗 S1；即使给节点加锁，谁先抢到锁也不等于权威命令顺序，同价 FIFO 仍可能被改写。因此，我按交易对确定可变订单簿的唯一写者，严格按已提交 `commandSeq` 计划和提交，读侧使用不可变结果或版本化投影。不同交易对可以并行，网络解析等前置工作也可以并行，但不能把一本簿的执行权任意摊给多个独立 worker。核心边界是状态所有权，不是 goroutine 数量。多线程解析得到的先后次序，也必须服从日志最终确定的接纳顺序。

## 第 2 层：交易对已经分开，为什么冷门对仍可能被热门对拖慢？

**面试官：** 既然不同交易对可以并行，我给每个交易对一个 goroutine，是否就完成隔离了？

**面试者：** 还没有。不同 goroutine 仍可能共享运行线程、CPU 配额、内存、日志提交连接和结果存储带宽；热门对如果无限预取命令或产生大量成交结果，仍会把公共资源吃满。我会给每对设置有界预取、在途结果和内存预算，让调度只在不同交易对之间公平分配执行机会，簿内顺序不变。必要时把热门对移到独立进程或独立资源组，并限制其对共享持久化资源的占用。在 Go 1.21+ 中，一个专属 goroutine 不等于一颗独占 CPU，`GOMAXPROCS` 也不是每交易对的 CPU 保障。隔离是否成立，要看共享资源上的排队与预算，而不能只看代码里是否分了 channel。尤其要防止共享提交连接被热门对长期占满，造成冷门对根本拿不到提交机会。

## 第 3 层：隔离以后热门单簿仍然 CPU 饱和，该优化什么？

**面试官：** 现在冷门对不受影响了，但 BTC/USDT 单写者已经占满可用 CPU，还能继续加 worker 吗？

**面试者：** 先区分真正的串行执行成本与被算进执行阶段的等待。若瓶颈确实是单簿计算，就减少每条命令的必要工作，例如改善价格索引、订单定位、内存局部性与分配，把可独立校验的内容放到排序前，把行情编码等工作移到结果提交后的异步投影；执行者仍按序做最终状态相关校验。还要按触及订单数评估大单成本，不能把一条跨很多档位的命令当成一条普通插单。按价格范围拆簿也不能随意做，因为 B1 本来就会跨价位消耗流动性，需要统一价格优先与命令原子边界。在这些约束下，硬件和热路径优化有上限，超出能力应收紧准入，而不是用乱序并行伪造吞吐。

## 第 4 层：订单簿隔离以后，跨交易对共享余额怎样避免超卖？

**面试官：** 单簿上限明确了。如果同一账户同时向两个交易对下单，两边各有单写者，资金是不是也被隔离了？

**面试者：** 没有，交易对分片不等于账户分片。独立变体中，甲只有 20000 USDT，却同时提交两笔各需预留 15025 USDT 的买单；两个撮合单写者即使各自正确，也不能允许两边都通过资金检查。账户域必须在自己的本地事务内，以条件更新或明确串行化方式完成余额检查、扣可用、增预留和创建绑定载荷的 `intent`，竞争者只能看到合法的剩余可用额。随后命令引用这份预留，不能重新解释成另一笔订单。结果消费同样要把去重、消费进度和资产变化一起提交，避免重放造成重复返还。通常不必让所有交易对共享一个撮合全序，但必须承认共享账户会形成独立竞争点，迁移订单簿也不会自动迁走这份资金权威。

## 第 5 层：要迁走热门对，怎样暂停入口并确定唯一交接屏障？

**面试官：** 共享账户仍由账户域处理。现在要把 BTC/USDT 移到另一执行者，能否先复制簿，再立即切路由？

**面试者：** 不能，复制期间旧写者可能继续处理，路由切换也挡不住在途提交。我会先关闭该交易对的新业务准入与旧提交通道：阻止产生新的预留意图，收拢已经开始的提交，按原身份核实所有提交超时；已有预留但尚未提交的意图保持耐久待处理，不能直接退款。接着由耐久日志的提交机制封住旧接纳区间，确定最后一个已提交业务序号 H，并耐久记录交易对、迁移代次和交接屏障，即 handoff 屏障。没有查清的不确定追加，不能绕过去宣布 H。旧执行者只允许完成到 H，新命令待交接完成后从 H 之后接纳。暂停入口只是准备动作，真正可恢复的边界必须是确定的耐久日志前缀。

## 第 6 层：有了日志屏障 H，为什么还必须核实结果提交位置？

**面试官：** 已经确定命令日志到 H，直接把旧写者的内存快照交给新写者，是否足够？

**面试者：** 不够。日志到 H 只说明命令已经受理，不说明结果已经提交；旧写者的内存还可能包含尚未提交的试算。我采用受控排空方案：旧写者逐条完成到 H，核实最后的 `ResultBatch + AppliedSeq=H` 已原子提交，然后停止推进。若提交超时，先查清耐久结果，不能用内存推断成功或失败。交接记录必须包含日志屏障 H、确认的结果提交位置以及可验证的状态恢复锚点。快照若位于较早的已提交位置 K，就依靠耐久快照和 K 之后的命令、结果恢复到 H；已有结果必须校验或复用，不能再发布一套新成交。账户消费者可以暂时落后，但那是保留中的结算义务，不能把它冒充为撮合尚未完成。

## 第 7 层：新写者接手前，怎样真正 fencing 住旧写者？

**面试官：** H 已经排空且快照可恢复。如果旧进程暂停后又醒来，只检查迁移标记够不够？

**面试者：** 不够，标记检查与实际写入之间存在竞态。必须在命令追加端和结果存储上 fence 旧代次；结果提交需原子校验代次与预期 `AppliedSeq`，并收敛所有旧代次在途写入，逐笔核实其提交或拒绝结果。此后再次读取耐久状态，确认最终日志屏障仍为 H，且结果与 `AppliedSeq=H` 一致。若发现屏障外新增的旧代次提交，或任一提交仍不确定，不得接管；先收敛恢复并重新确定交接边界。发布侧也不能只切路由，应校验发布资格，或仅由受控分发者读取耐久已提交结果，禁止旧写者发布试算；晚到的合法通知按稳定结果身份去重。只有这些条件与恢复状态都核实后，新代次才能从 H 后继续，这才是资源承认的单一写权。

## 第 8 层：怎样用反例判断迁移是否只搬了内存、没有闭合业务？

**面试官：** 顺序、结果位置和 fencing 都有了，你会用哪些反例审查这次迁移的正确性？

**面试者：** 我会分开推演三个窗口。第一，B1 已写入日志但结果未确定，此时必须核实并排空，不能从一张看似完整的内存簿直接接手。第二，B1 结果已提交但账务未完成，迁移后仍只能保留那两笔成交，账户按原结果重放，最终返还 10 USDT，不能再冻结一次或提前释放 15025。第三，旧写者在新代次生效后恢复写入，实际资源必须拒绝它推进结果。正常顺序下，B1 后的 C1 只能撤 S2 的 0.05 BTC，不能撤回已经成交的 0.15。审查还要核对已提交命令无缺口、结果无重复、订单优先顺序未改变，以及恢复材料能够重建 H；内存快照即使字节校验正确，也不能替代这些耐久闭包证据。

## 本题收束

- **机制：** 按交易对划分单写状态，以资源预算隔离热点；单簿内优化串行热路径，账户域独立守住共享余额。受控迁移依次建立入口暂停、耐久日志屏障 H、结果提交到 H、实际资源 fencing、状态恢复与新代次接手。
- **易错边界：** 专属 goroutine 不等于独占 CPU；多个 worker 或价格分区不会自动保持单簿价格时间优先；日志受理位置不是结果位置，结果位置也不是账务完成位置。未知提交不得越过，内存快照和路由切换均不是充分交接条件。
- **验证反例：** 分别检查在途追加未查清、结果提交超时、快照含未提交试算、旧写者复活、账户重复消费。手工业务预期仍为 B1 成交 0.25 BTC、成交额 15015 USDT、价差返还 10 USDT、S2 余 0.05 BTC；C1 仅撤剩余量。这里给出的是审查条件与推演结果，不声称发生过真实迁移或通过了性能验收。
