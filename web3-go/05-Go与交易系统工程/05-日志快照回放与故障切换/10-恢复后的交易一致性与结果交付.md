# 大问题 10：恢复后怎样保证订单、成交、预留与账务一致？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 交易一致性 / 全成 / 交收 | 订单、成交义务与钱的去向相互对得上，而不只是状态显示成功。 | 全成证明撮合裁决，真正到账要有账户消费与账本证据。 |
| 托管现货 / 同一事务域 | 平台内交换资产，且本例双方记账可在同一账户事务完成。 | 不假装拥有跨账户分片原子事务，也不引入链上结算。 |
| R-A / 预留 | 为 B1 稳定意图占住的 30,000 USDT 资格。 | 总额 50,000 中可用 20,000；已成交义务未交收前不能直接释放。 |
| command-only / 原子 apply | 已提交完整命令按确定规则生成所有结果并一次可见。 | 订单、成交、请求结果、outbox 和 appliedIndex 同步，不二次共识结果。 |
| eventID / 不可复用 shardID | 一笔经济效果的稳定编号，以及不能重用的来源空间。 | 原成交为 `btc-usdt-1/101/0`，重启和换主不重命名。 |
| outbox / 至少一次 | 保留待交付义务，允许网络导致重复发送。 | 成交不能和输出分家，确认丢失继续重送原事件。 |
| inbox / payloadHash / 唯一约束 | 账户的消费凭证、内容摘要，以及阻止重复身份写入的数据库规则。 | 同 ID 同载荷返回原结果，异载荷报警；inbox 不能早于资产变化单独提交。 |
| 复式分录 / 资产结转 | 每种币的来源去向平衡，且对应预留与余额同时变化。 | 全成时 A 得 1 BTC、B 得 30,000 USDT，由账户事务真正移动资产。 |
| sourceShard / token / 围栏行 | 来源、当前发送授权，以及与记账共锁的持久控制记录。 | 账户先验围栏再消费，token 不属于经济幂等键。 |
| 交付确认命令 | 把账户持久记账结果纳入撮合的可靠历史。 | 提交并 apply 后才逻辑清除义务，网络发送成功不够。 |
| logIndex / eventSeq | 所有日志条目的位置，以及仅实际交付批次的连续编号。 | 确认、空操作、去重重试可能无事件，不能要求每个日志位置都到达账户。 |
| q / q+1 / 连续游标 | 当前与下一交付批次，以及没有跳过缺口的消费范围。 | 缺成交 q 时不能先处理撤余量 q+1，更不能用最大序号推进。 |
| 有序终态 / 释放依赖 | 撮合明确裁决订单剩多少，以及先交收后释放的约束。 | 独立 0.4 BTC 变体成交需 12,000，撤 0.6 才释放 18,000 USDT。 |
| 资格撤销屏障 / 提交未知 | 有序禁止迟到接纳，以及原请求是否成功尚不确定。 | 查不到或 RPC 超时不能解冻；接纳在前就只能按实际余量撤。 |
| K→q / 同水位对账 | 撮合切点映射到它实际产出的交付前缀，再核对对应账户视图。 | 不拿两个“最新页面”比；要查事件、摘要、分录、资格占用与数量。 |
| PITR / 归档 / 受控补齐 | 账户回退、保留历史材料，以及隔离生产后补缺失事务。 | 已确认输出仍受回滚窗口约束，先围栏、补齐、同切点核对再接生产。 |

## 把整篇文章压缩成一个故事

本文把全成主例单独替换为部分成交：B 只为 S1 预留 0.4 BTC，A 的 B1 仍要买 1 BTC，预留 30,000 USDT。101 成交 0.4，随后有序撤掉剩余 0.6，交收要付 12,000，只能释放 18,000。工程师小孟恢复时若只看到订单终态就退回全部预留，会让已经成交的部分失去资金依据。撮合恢复必须同时找回订单数量、原请求结果和两项带依赖的交付义务。

假设成交批次是 q、撤余量批次是 q+1，后者先到也不能先释放。账户等待补齐缺口，在同一事务内核验当前围栏、唯一消费键与摘要，完成预留变化、资产结转、平衡分录和消费游标。成交已入账而回执丢了，就重送原事件取回原答案，不再付一次钱；撮合还要把确认可靠写回日志。最终 A 可用 38,000 USDT、预留为零、增加 0.4 BTC，B 收到 12,000 USDT；数量是 1=0.4+0.6+0。

小孟对账时对齐撮合切点及其实际交付前缀，不能把日志最大位置当账户进度。更难的是账户 PITR 回到入账前，撮合却已确认并清空在线 outbox：此时靠普通重试不够，要有保留归档或可重建历史。先隔离生产、装好当前围栏，再补预留等前置事实和原 ID 事件，同切点核对后才开放。回放恢复义务，账户事务兑现义务，两边不能各自扣一次，也不能用“outbox 空了”宣告业务闭环。

**流程位置与核心机制：** 本题从已提交命令的确定性执行，追到成交交收、余量释放和恢复验收，独立回答“交易一致性”，不只讨论消息是否送达。核心是订单、成交与交付义务同次 apply，账户消费与复式记账同事务，交付确认回写撮合日志，再以有依赖的交付顺序和同水位证据闭环。第 08 题解决提交前缀，第 09 题解决发送授权；本题不能用“Raft 已恢复”代替账务正确。

沿用总览：链下托管现货、三节点 Raft、BTC/USDT、无手续费，账户先建立独立预留资格，撮合不拥有余额。快照为 100；命令 101 是 A 的 B1 买入 1 BTC，限价 30,000 USDT，与已有 S1 成交。A 原有 50,000 USDT，其中 30,000 已预留；B 的 1 BTC 已预留。两人资产结转位于本模型账户服务的同一事务域，不暗加跨账户分片原子事务。

本专题采用 **command-only 确定性状态机方案**：命令提交后，apply 同时生成确定结果与逻辑 outbox；不把“先执行、另写结果日志并再次共识”混入本方案。稳定经济身份为 `不可复用 shardID/logIndex/批内序号`，本例为 `btc-usdt-1/101/0`。下文的 `eventSeq` 只用于实际交付批次的连续进度，不代替经济身份。

## 第 1 层：先定义交易一致性，不把全成当作到账

**面试官：** 撮合恢复后查到 B1 已全成，能否说明这笔交易已经一致地完成？

**面试者：** 不能，全成是撮合裁决，不等于账户已经交收。在这个模型中，账户先为 B1 预留 30,000 USDT、为 S1 预留 1 BTC；已提交的 101 执行后，两单全成，并形成双方资产结转的交付义务。账户可以暂时仍显示预留，但不能把这部分钱释放回可用。入账后 A 的 USDT 可用为 20,000、预留为零并增加 1 BTC，B 增加 30,000 USDT、BTC 预留归零。允许“成交已确定、交收处理中”的暂态，不允许成交消失、同一成交扣两次或欠款先解冻。数量守恒、逐币种资产守恒和每笔成交都有可追踪交收状态，才是本题的一致性目标。

## 第 2 层：成交与交付义务不能在崩溃时分家

**面试官：** 你要求每笔成交都有交收义务。如果 101 已修改订单簿，却在写待发送记录前崩溃，怎么补上？

**面试者：** 不能把这两个动作作为可分别对外可见的成功。本方案只 apply 已提交命令；单写者构造本条的订单变化、成交、请求键与摘要对应的原结果、完整逻辑 outbox，并与 appliedIndex 原子发布。构造失败就停止分片，不暴露半次执行。若只有快照 100，重启从可信已提交 101 重放，仍生成 `btc-usdt-1/101/0` 与相同载荷，不创建新成交。快照必须包含上述完整状态；确认前的义务不可因发送失败删除。这里不需要第二条结果日志再提交：结果的可靠性来自已提交命令、确定性执行及完整快照，而不是发送线程事后补一个普通文件。

## 第 3 层：至少一次交付怎样只产生一次账务效果

**面试官：** 既然回放会重建同一条 outbox，发送也会重试，账户怎样避免把 30,000 USDT 再扣一次？

**面试者：** 账户以 `sourceShard + eventID` 建唯一 inbox，并保存规范化经济载荷的 payloadHash 与原记账结果。处理时在同一个数据库事务内锁定该分片围栏行、核验当前 token、检查 inbox、核验双方预留，写入逐币种借贷平衡的复式分录、更新预留与余额，再保存消费结果。并发重复由唯一约束和事务锁协调，冲突方读取已提交结果；同 ID 同摘要返回原结果，同 ID 异摘要拒绝并报警。事务提交前失败则整体回滚，不能先单独提交 inbox，否则重试会误以为记过账。买卖双方结转在本例同一事务域完成；这是至少一次发送加本地幂等记账，不是消息队列保证的端到端 exactly-once。

## 第 4 层：确认丢失与确认回写之间怎样恢复

**面试官：** 账户事务已经提交，但确认包丢失；或者撮合收到了确认，尚未持久化就崩溃，这两个窗口分别怎么办？

**面试者：** 两个窗口都保留原交付义务并重发原事件。账户已提交时，inbox 返回原记账结果，不再变更资产；账户事务未提交时，重试才真正执行。撮合收到可信的持久记账确认后，提出交付确认命令写回同一 Raft 日志，等它提交并 apply 才把义务逻辑标记完成。只更新发送器内存不算确认，确认命令仅本地落盘也不算。若确认已经提交而节点尚未执行，恢复后按序重放即可；重复确认无副作用。恢复后换主重送时，可以更换已获准的围栏 token，但必须保留原 eventID、经济载荷和摘要，不能把接管任期变成新的扣款身份。

## 第 5 层：日志有间隔，不能据此判定漏事件

**面试官：** 你把确认也写回日志了。如果 101 有成交，102 是确认或去重重试，103 才有下一个交付事件，账户怎样判断是否漏了 102？

**面试者：** 不能把日志索引当连续交付序号，因为 no-op、确认和同键重试都可能不产出交付事件。我会由状态机仅为实际产出的账户交付批次分配连续 eventSeq，同次 apply 保存批次内容、序号和下一序号，快照也完整保存，回放确定性恢复。假设此前进度为 q−1，101 的成交批次为 q，103 的实际交付批次才是 q+1，不要求账户收到“102 事件”。每批内的经济 eventID 仍由日志索引与批内序号生成。这里的连续流覆盖该分片送给账户服务的全部批次，不是每个用户各自收到的子集；批次完整消费标记和连续游标与记账同事务，不能按见过的最大序号跳过缺口。

## 第 6 层：释放先到时怎样守住依赖与缺口

**面试官：** 按你的 eventSeq，若 q 是成交、q+1 是撤余量释放，但 q+1 先到，账户能先释放再等成交吗？

**面试者：** 不行。账户只能把已完整消费的连续前缀向前推进；收到 q+1 而缺 q 时，不执行释放、不推进游标，可有界持久暂存或拒绝并要求重送，同时保留预留。发送方保留 q 的义务与载荷，补齐后按序处理；如果缺口暂时无法解释，就停止该流相关释放并核对，不能用超时跳号。释放载荷还要关联订单、资格、确定撤销量及前置成交依赖，账户核验未结转与仍挂单部分，不能把任意终态消息解释成全额解冻。这个顺序不会给网络增加可靠性，只是把不可靠投递转成可检测的等待，避免用较晚结果覆盖尚未履行的较早义务。

## 第 7 层：部分成交 0.4 后，释放数额具体是多少

**面试官：** 你说只释放确定撤掉的余量。把案例单独改成 S1 只有 0.4 BTC，B1 成交 0.4 后撤单，具体哪些钱能动？

**面试者：** 这是替换原全成案例的独立变体，B 此时也只预留 0.4 BTC。101 使 B1 累计成交 0.4、剩余 0.6，成交交收需要 12,000 USDT；后续有序撤单只撤剩余 0.6，对应释放 18,000 USDT。成交消费先扣 A 预留 12,000、给 A 增加 0.4 BTC，并把 12,000 USDT 结转给 B；释放消费随后把剩余 18,000 从预留转回 A 可用。最终 A 的 USDT 为 38,000、预留为零。若成交尚未消费，这 12,000 仍是交收占用，不能因为订单已终态就释放整笔 30,000。金额和数量仍按整数最小单位计算，这些只是展示数值；重启后也不能读取当前余额重新推算撤单金额。撮合始终满足原始量 1＝成交 0.4＋已撤 0.6＋剩余 0。

## 第 8 层：没等到终态，不能拿 RPC 超时替代撤销

**面试官：** 你要求拿到有序撤单终态才释放。如果恢复期间只查到“暂未受理”，或下单 RPC 已超时，能否先把 R-A 撤销，免得一直占资？

**面试者：** 不能，暂未查到不是原命令永远不会到达的证明。R-A 是账户针对稳定下单意图建立的独立资格，不随 RPC 生命周期自动失效；请求不确定时保留预留，按原请求键查询或重试。要撤销，就让资格撤销屏障与接纳在撮合权威序列中裁决：尚未接纳时形成可恢复的撤销事实，之后拒绝携旧资格的迟到命令；已经接纳时转为有序撤单，只释放裁决出的余量。账户取得已提交且已执行的撤销或终态证据，并满足前置交收依赖后才解冻。若没有多数，屏障无法提交，就宁可继续占资，也不靠账户单方面超时释放来制造无担保成交。

## 第 9 层：恢复验收必须比较同一业务切点

**面试官：** 资格没有被超时释放，但系统恢复后订单全成、账户仍有预留。怎样区分正常交收滞后和真正的账务错误？

**面试者：** 要对齐水位，而不是直接比较两个系统的当前页面。选撮合已执行前缀 K，确定它实际产出的交付前缀 q，再取得账户恰好消费到 q 的一致视图，可暂停相关交付取切点或使用可信历史版本。逐事件核对 eventID、摘要、数量、inbox 与平衡分录，逐订单核对累计成交、已撤量、剩余量，逐资格核对已结转、已释放和仍应占用的资产。撮合 apply 到 K 不表示账户已到 q；账户已记账但撮合未确认，可查询原事件并补确认。若账户尚缺一批，保留义务继续交收；若同切点仍对不上，则隔离相关写入排查，不能用一笔无依据的余额调整把差异抹平。

## 第 10 层：已确认的事件遇到单边 PITR 仍要能找回来

**面试官：** 你按同水位核对时发现，账户单边 PITR 回到了入账前，但撮合早已确认并清除了待发送项。单靠重试还够吗？

**面试者：** 不够，确认后的逻辑 outbox 不能成为唯一恢复材料。保留策略须覆盖下游允许的回滚窗口：归档已确认事件完整载荷与序号，或保留可重建它们的完整历史及规则；确认不等于立即物理销毁。账户先停写，隔离旧发送者和生产入口，核实余额、账本、inbox、游标属于同一恢复点；经认证路径安装当前围栏，防止回退的 maxToken 放过旧包。随后仅开放受控修复通道，先恢复预留等前置历史，再按真实进度以原 ID、原摘要补齐事件，已有 inbox 自然去重；同切点核对通过后才分阶段接生产。若缺失材料则继续停写修复。反过来撮合单边倒退、账户保留成交时，应恢复原已提交历史，不能撤销既有成交或另造 ID。此类恢复依赖证据与保留范围，不承诺任意灾难下自动一致。

## 本题收束

- **讲透的机制：** 账户先预留独立资格；已提交 command 的一次确定性 apply 共同发布订单、成交、请求结果与逻辑 outbox；账户以 inbox、payloadHash、复式分录、预留及余额同事务消费；确认命令回写撮合日志。跨模块通过可恢复义务与有序重试收敛，不引入隐藏的分布式事务。
- **最容易答错的边界：** 全成不是到账，apply 水位不是账户水位，发送成功不是持久记账确认；`logIndex` 不是连续 `eventSeq`；围栏 token 不参与经济去重。部分成交撤单只释放余量，暂未受理和 RPC 超时都不足以撤销资格。逻辑确认完成也不免除下游回滚后的恢复责任，物理归档清理必须服从共同保留契约。
- **检验方案的反例：** 以 0.4 BTC 变体作组合推演，每一步完成恢复验收后才切入下一故障：先让释放早于成交到达；再模拟成交入账但确认丢失，补齐确认；最后把账户 PITR 到成交前。应先等缺口、只释放 18,000 USDT、重复交付不重复入账，并从保留历史按原 ID 恢复被回滚的账务；若最后只回答“outbox 已空，所以没事”，闭环就没有成立。

以上为教学方案与故障窗口推演，不代表个人生产经历、实测结果或已执行测试；本题不另建 MVP 或可运行工程。
