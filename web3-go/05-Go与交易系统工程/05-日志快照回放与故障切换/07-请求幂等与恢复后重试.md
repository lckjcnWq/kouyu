# 大问题 7：请求超时后，怎样在重启、切主和结果过期后仍不重复执行业务？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 请求幂等 / 账户消费幂等 | 阻止同一意图再撮合，以及阻止同一成交再入账的两道不同约束。 | 只防重复扣款，不能阻止换了请求身份后的第二笔真实买单。 |
| requestKey / 三元组 | 账户、操作、客户端请求号合成的稳定业务编号。 | B1 重试沿用 `A/place/r1`，不随连接、RPC、任期改变。 |
| payloadHash / 规范编码 | 将业务字段统一表示后计算内容指纹。 | 覆盖价格、数量、方向、订单与预留意图；不能直接 hash 无序 map。 |
| 同键同摘要 / 同键异摘要 | 编号和内容都相同就复用，编号相同内容不同就冲突。 | 后者不覆盖原结果，也不借旧身份提交新价格或数量。 |
| command-only / 确定性 apply | 已提交完整命令按固定规则执行，重建原结果。 | 不另提交 result；订单、去重、outbox 和 A 同一次原子发布。 |
| 快照 / 原结果 / outbox | 完整旧状态、首次裁决答案，以及未完成交付。 | 快照不能只存盘口；101 回放仍返回原成交 `btc-usdt-1/101/0`。 |
| 101 / 102 / A | 首次执行、重复命令的示例位置，以及已应用进度。 | 两条都可提交，但 102 只推进 A 并返回 101 原结果，不再成交。 |
| 提交未知 / 业务拒绝 | 暂时不知系统是否接下请求，以及已经裁决不能接纳。 | 网络超时是前者，不能写成确定失败或授权释放预留。 |
| 线性读屏障 / 未找到 | 在合法一致读取点查询，以及该时点尚无可见记录。 | 即使权威查询未找到，在途原提案仍可能后来提交，不能随意换号。 |
| R-A / 撤销屏障 | 稳定资金资格，以及在撮合顺序中关闭迟到接纳的事实。 | 30,000 USDT 不能因账户本地超时释放；已成交部分仍须交收。 |
| TTL / 结果保留期 | 完整答案保留多久，不等于多久以后允许重新执行业务。 | 七天结果到期后，第八天旧请求也不能重新变成首次请求。 |
| 墓碑 / 确定性清理 | 保留防重终态证据，以及有共同顺序的清理决定。 | 不按各副本本机时钟各自删；墓碑、撤销事实和进度都随快照恢复。 |
| 客户端槽位 / e / q | 认证客户端身份、会话世代和本会话请求序号。 | 编码进请求号，不能丢状态后悄悄从 1 重来。 |
| H / 连续前缀 | 客户端已确认都终态且无需再查询的一段完整范围。 | 不是见过的最大 q；缺口未闭合不能擅自跳过。 |
| 会话高水位 / 世代下界 | 拒绝旧序号与旧会话的持久屏障。 | 先共识提交并应用，再压缩旧记录；这些屏障本身不能随 TTL 清空。 |
| 分片身份 / 新会话新意图 | 成交的不可复用来源身份，以及换会话生成新键的业务含义。 | 切主不改原 eventID；新键重建旧经济操作不会自动被旧键幂等识别。 |

## 把整篇文章压缩成一个故事

A 为 B1 预留 30,000 USDT 买 1 BTC，下单超时后请求落到新主。工程师小郭要求继续用 `A/place/r1`，而不是换号再买。假设原请求和重试分别占了已提交位置 101、102：101 首次执行生成成交 `btc-usdt-1/101/0`，保存载荷摘要、原结果和交付义务；102 命中同键同摘要，只推进执行水位并取回原答案。若同一个键改成另一价格，必须冲突，不能覆盖原记录。

节点重启后，这份记录要么随快照恢复，要么由已提交命令确定性重建，不需要再做一次结果共识。查询暂时未找到也不授权换号或释放 R-A，连线性查询都只说明当时没有可见结果，旧提案仍可能迟到。A 若真想放弃，要把资格撤销排入撮合顺序；若接纳已经在前，就按实际成交和剩余量处理，不能把已欠交收的钱全退回去。

七天后，系统可以按契约缩减完整答案，却不能把防重证据也一删了之，让第八天的旧包再次成交。小郭保留墓碑，或与客户端约定会话世代、序号及连续高水位 H：先可靠推进拒绝旧请求的屏障，再删逐键记录。H 不是最大序号，会话轮换也不撤销旧订单。永久防重、永久保存原答案和账户不重复入账，是三项各有成本、不能相互冒充的承诺。

[返回专题总览](README.md)

**流程位置与核心机制：** 横跨入口重试、日志排序、确定性应用、快照恢复和结果保留。沿“稳定请求身份 → 原结果恢复 → 并发重试排序 → 查询的不确定性 → 预留撤销 → TTL 与会话屏障”追问。这里保证重复意图不再次撮合；账户消费幂等属于独立边界，不能代替请求去重。

**必要前提：** 沿用三节点 Raft 的已提交 command → 确定性 apply → 稳定结果与 outbox，不二次提交结果。案例请求键为 `A/place/r1`，B1 买 1 BTC、限价 30,000，资格 R-A；首次执行位置 101，成交 ID 为 `btc-usdt-1/101/0`。账户预留与余额属于独立账户服务。后文会话方案将会话信息编码进客户端请求号，不改变账户、操作、客户端请求号三元组的身份规则。以下是教学设计，不是生产经历或实测。

## 第 1 层：幂等究竟绑定请求键、载荷还是主节点？

**面试官：** B1 下单超时，客户端重试到新主。你怎样保证它仍是原来的意图，而不是再买一次？

**面试者：** 我会把账户、操作和客户端请求号作为稳定请求键，重试必须沿用 `A/place/r1`，不能按连接、任期或一次 RPC 生成新键。对价格、数量、方向、订单身份和预留意图等业务字段做规范编码并计算摘要，单位统一，不能直接 hash 随机顺序的 Go map 或原始 JSON。确定性 apply 首次接纳时保存键、摘要和原成功或业务拒绝结果；同键同摘要复用，同键异摘要返回冲突且不覆盖原记录。网络超时只是未知，不写成业务拒绝。可靠受理和执行完成也要区分，返回确定订单结果必须等该条实际应用。

## 第 2 层：原结果已经返回，重启后为什么仍能找到？

**面试官：** 你把原结果放在去重表，但 101 刚执行节点就崩溃，内存表丢了。新主怎样恢复，不另提交一次 result 日志吗？

**面试者：** 不需要另一次结果共识提交。101 的完整确定性命令已经提交，apply 把订单、稳定成交、请求摘要与原结果、outbox 和 A 一起原子发布。若快照仍是 S=100，就回放已提交 101 重建原记录；若快照已覆盖 101，原记录及未完成交付义务必须随同保存。不能只持久化盘口后宣称请求可恢复。恢复始终返回原成交 `btc-usdt-1/101/0`，不能因新任期而换 ID；业务拒绝也保留原原因。账户是否已入账另查原事件消费事实，撮合结果恢复不需要再次申请预留或重跑账户扣款。

## 第 3 层：未提交时的并发重试怎样只应用一次业务？

**面试官：** 恢复能重建已执行记录，但两次重试在记录出现前同时进入日志，占了 101 和 102，而且最后都提交了，怎么办？

**面试者：** 入口可以合并正在处理的同键请求来减压，但正确性必须落在单写者的已提交应用顺序上。假设 101 首先应用，它记录摘要、原结果并产生一次成交和 outbox；102 应用时命中同键同摘要，只复用 101 的结果并推进 A，不再次撮合，也不生成带 102 的新成交。若两次载荷不同，先按已提交顺序生效者绑定该键，后者冲突；在此之前都不能提前回确定成交。旧主未提交尾部最终是否保留由 Raft 决定。这里承诺业务效果一次，不承诺日志只出现一次，也不靠进程内锁跨重启提供保证。

## 第 4 层：查询未找到能否证明原请求不会再成功？

**面试官：** 那客户端先查询原键更省日志。如果新主返回“未找到”，客户端就换一个请求号重下，可以吗？

**面试者：** 不能直接换号。权威查询要由合法领导权取得线性读屏障，并等待 A 至少追到该屏障位置；落后副本只能返回带水位的非权威结果，不能用“未找到”作释放或重下依据。即使线性查询在某个时点确实没有结果，也只说明截至该时点没有可见原记录：先前在途提案仍可能随后提交。客户端应继续用原键查询或重试，必要时要求有序撤销。查询“未提交”“已提交未应用”“已执行”的可见证据也要区分，不能把入口缓存中没有任务解释成永远不会成交。

## 第 5 层：未知请求对应的预留何时才能释放？

**面试官：** 你让客户端保持原键，但 R-A 一直占着 30,000 USDT。账户服务能否设一个超时，先释放，再让迟到请求自行失败？

**面试者：** 不能仅凭本地超时释放，因为迟到命令可能携带仍被撮合认可的资格。账户预留要绑定稳定意图，重试复用 R-A；想放弃时，必须让资格撤销进入撮合的有序裁决，形成可恢复的撤销屏障，使之后到达的旧命令确定性拒绝。若接纳先于屏障，撤销要按订单当前终态或剩余量处理，已成交部分仍保留交收义务，不能把整笔预留释放。若屏障在前，撮合保存撤销事实并阻止迟到接纳，账户拿到对应持久证据后才释放未使用部分。仅查一次未找到、过期缓存或 RPC 超时都不是这种证据。

## 第 6 层：TTL 为什么不能直接删除去重与撤销记录？

**面试官：** 原结果和撤销屏障都要持久化，记录会越积越多。假设承诺结果保留七天，到期直接删除该键可以吗？

**面试者：** 直接删除会让第八天的旧请求重新变成首次请求。我会区分原结果的可查询保留期和禁止重新执行的期限：完整结果只有在契约允许、且不破坏未完成交付时才可缩减，之后仍保留键、摘要及终态墓碑，返回“结果已过保留期”，不能再次撮合。清理通过有序命令或已提交的确定性截止条件推进，不能各副本按本机当前时间独立删。墓碑、撤销屏障和清理进度都进入快照；outbox 是否可删由交付确认决定，不由请求 TTL 决定。若要求无限期返回原结果，就必须另付持久归档成本，不能声称有限存储免费做到。

## 第 7 层：怎样用客户端会话高水位压缩墓碑？

**面试官：** 你把完整记录变成墓碑，但墓碑仍无限增长。怎样删除旧墓碑，又不接受多年后才到达的旧请求？

**面试者：** 可以增加显式客户端协议：请求号编码稳定客户端槽位、会话世代 e 和单调序号 q；同一会话允许乱序到达，但不能用“见过的最大 q”跳过缺口。客户端确认一个连续前缀内的请求都已取得终态、无需再查原结果后，申请把高水位 H 推进到该前缀；推进命令先共识提交并应用，再删除 q≤H 的逐键记录。此后即使旧提案迟到或再次进入日志，也只能返回过期，不执行。H 与会话身份必须随快照恢复，H 以上记录照常保留。长期未确认的缺口会阻止压缩，这是协议代价，不能由服务端擅自跳过。

## 第 8 层：会话重启与旧资格怎样避免绕过高水位？

**面试官：** H 能拦住旧序号，但客户端丢失本地状态后从 1 重新编号，或换一个会话重发旧订单，怎么处理？

**面试者：** 不能悄悄重置序号。对同一认证客户端槽位，可限定一个活跃世代，由有序会话轮换命令持久推进可接受世代下界，拒绝旧世代；新世代才能从 1 开始，下界不能随 TTL 删除。轮换不会撤销旧订单，也不释放旧预留。恢复客户端必须先核对未完成意图；新会话新键是新意图，若随意重建旧经济操作，幂等层不能替它识别，资格也须防止跨意图复用。服务端快照同时保留世代下界、H、H 以上原结果及资格撤销事实。若不接受这些协议约束，就必须保留逐键防重证据，不能把有限 TTL 宣称为永久幂等。

## 本题收束

### 机制

- 请求键绑定业务意图，摘要检测载荷冲突；原结果与订单、稳定事件、outbox 在同一次确定性 apply 中产生，并能由快照或连续已提交日志恢复。
- 多条重复日志可以各自推进 A，但只有首次生效命令产生业务效果；后续同键返回原结果，不另生成成交身份。
- 有限结果保留依赖持久墓碑或显式会话高水位协议，删除逐键证据之前必须先持久化拒绝旧请求的屏障。

### 易错边界

- 线性读的“此刻未找到”不等于迟到请求已撤销；落后查询更不能授权重新下单或释放预留。
- 资格撤销须有序裁决，账户超时不能直接释放；已成交义务不因客户端换会话、撤销或结果 TTL 而消失。
- H 是客户端确认的连续前缀，不是最大序号；世代下界和 H 也不能过期清空。永久防重与永久返回原结果是不同承诺。
- `eventID` 使用不可复用的分片身份和首次生效位置；重启、切主、重试都不重置身份。账户消费幂等与撮合请求幂等不能互相替代。

### 反例检验

手工推演四个独立场景：同键同摘要在 101、102 都提交，只有 101 撮合；原键线性查询未找到后旧提案迟到，仍只能沿用原键或经过撤销屏障；完整结果过期后旧包到达，墓碑或 H 必须拒绝重执行；会话轮换后旧世代包到达，世代下界继续拒绝。任一场景导致第二笔成交或提前释放预留，方案即不成立。以上不是已执行的工程测试。
