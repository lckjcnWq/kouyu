## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 链下托管现货 / BTC/USDT | 平台保管资产，用 USDT 买卖真实 BTC 余额。 | B1 买 1 BTC，限价 30,000；不含杠杆、手续费或链上原子结算。 |
| 状态归属 | 每类事实由指定系统裁决，不能互相代写。 | 撮合管订单与成交，账户管可用、预留、交收及账本。 |
| R-A / 预留资格 | 为这笔意图占住资金并提供可核验的交易资格。 | A 的 50,000 USDT 中预留 30,000；RPC 超时不自动解冻。 |
| Raft / 持久多数 | 由协议协调顺序和选主，并把必要信息可靠保存在多数节点。 | 三个投票节点多数为两个；不是随便复制两个文件。 |
| command-only / 确定性状态机 | 提交完整命令后，用固定规则重建唯一结果。 | 本专题不再对成交结果做第二次共识；不能套用结果批次权威方案。 |
| 可靠受理 / 执行 / 账务完成 | 接下必须处理的命令、算出裁决、完成资产结转三个阶段。 | 提交命令不等于已经成交，订单全成不等于账户到账。 |
| S / A / C / D | 快照、已执行、已提交、本地持久日志各自走到的位置。 | 同节点同历史通常 S≤A≤C≤D；磁盘尾 D 不能冒充提交 C。 |
| requestKey / payloadHash | 业务意图的稳定编号与规范化内容指纹。 | 同键同内容复用原结果；同键异内容冲突，不能借重试再买一次。 |
| eventID / 批内序号 | 一笔经济效果始终不变的身份。 | 成交为 `btc-usdt-1/101/0`；切主换授权不换此 ID。 |
| outbox / 待交付义务 | 已裁决但还要确保交到账户的完整业务结果。 | 回放和快照都要找得回来，发送过不代表可以删除。 |
| inbox / 账户消费事务 | 收件凭证和真正记账一起提交，避免收据与钱分家。 | 去重、摘要、双方预留、资产结转和账本处在同一事务内。 |
| eventSeq / 连续前缀 | 给实际交付批次编号，并只承认没有缺口的完成范围。 | 确认和空操作未必产出事件，不能拿最大日志索引当账户进度。 |
| 一致快照 / manifest | 固定某一执行切点的完整镜像，以及列明文件与校验信息的清单。 | 订单、去重与未确认输出同属 S；数据持久后才发布引用。 |
| 安全截断 / 历史保留 | 有可信替代材料后才压缩恢复前缀。 | 不能连未交付结果、审计归档和账户回退所需历史一起盲删。 |
| 接管屏障 / token / 围栏 | 新主先提交接管凭据，再让真实写端拒绝旧授权。 | 账户安装 token 与记账锁同一围栏行；选主本身不能撤回旧网络包。 |
| PITR / 共同恢复清单 | 数据库恢复到过去事务切点，并靠跨系统清单说明还缺什么。 | LSN、撮合索引、链高度不能取最小值当全局进度。 |
| 链事件重扫 / 规范链 | 核对区块分支并重建相应链上事件投影。 | 找不回未上链的托管撮合成交，也不能撤回最终提现。 |
| RPO / RTO | 故障下允许丢多少已承诺事实，以及业务多久恢复。 | 零丢失受故障域限制；端口启动或选出主节点不是全链路恢复。 |

## 把整篇文章压缩成一个故事

A 有 50,000 USDT，为 B1 预留 30,000，想买下 B 已挂出的 1 BTC。撮合分片已有快照 100，主节点提出命令 101，还没把结果回给 A 就崩溃了。值班工程师小周先问“101 是否已提交”，而不是让 A 换号重下或把钱解冻：本地文件有记录不代表集群已经承诺，等待超时也不能证明请求失败。这个模型用三节点 Raft，在约定的单节点故障范围内保存已提交历史。

若协议确认 101 已提交，小周从可信快照连续回放，按原规则重建 B1、S1 全成、原成交 `btc-usdt-1/101/0` 与待交付义务。本专题靠完整命令确定结果，不另补一次结果共识。回放不直接扣钱；获准交付器重送原事件，账户把去重、预留结转、余额与账本放进同一事务。即使入账后回执丢了，重送也只取回原结果，A 最终可用 20,000 USDT、增加 1 BTC，B 收到 30,000 USDT。

小周还不能只凭订单全成宣布复业。他要验证快照清单和连续前缀，新主追到接管屏障，并让账户真实写端装好更高围栏，再分别开放查询、接单与交收。旧日志也不能随手删除：未确认交付和账户回退所需历史仍要留存。链重扫只管对应链事件投影，不能替代账务归档；多数永久丢盘等超出模型的灾难，也不能继续沿用“零丢失”的承诺。

## 一、文字全流程

### 1.1 讨论基线与故障模型

- **产品**：链下托管现货订单簿，BTC/USDT，限价持续有效订单，价格时间优先。此处不是 AMM，也不是链下成交、链上原子结算模型。
- **状态归属**：撮合分片拥有订单、成交裁决、请求去重和待交付结果；账户服务拥有可用、预留、交收及账本。撮合日志不等于账户账本。
- **复制**：一个交易对分片、三个投票节点，采用已有 Raft 实现；多数为两个。日志和投票等协议持久状态按实现契约持久化，不能用两个普通文件副本冒充共识。
- **执行**：只执行已提交命令，单写者按序修改内存状态。已提交输入包含决定结果的业务上下文，执行不读当前时间、当前 Redis 价格或随机数。
- **确认**：“可靠受理”表示命令进入不可任意撤销的已提交前缀；“执行完成”表示已按顺序产生确定结果；“账务完成”另看账户消费事务。返回确定订单结果至少要等本条执行完成。
- **承诺范围**：节点崩溃、重启、网络分区，以及单节点永久磁盘损失；不是拜占庭模型。两个以上持久副本同时永久丢失、存储虚报刷盘、全域灾难不在此承诺内。多数不可用时停止新提交，以可用性换安全性。
- **相邻边界**：账户预留资格在订单生命周期内有效；释放资格必须取得撮合有序终态或撤销屏障，不能由 RPC 超时触发。跨账户分片、跨撮合分片原子交易不在本模型内。

**与既有撮合专题的区别**：[既有崩溃恢复题](../../01-撮合交易与核心链路/01-撮合交易从0到1/09-撮合引擎崩溃恢复.md)采用命令提交与 `ResultBatch + AppliedSeq` 结果提交两个可靠边界，已有结果原样应用、确认无结果的尾部才重算。本文为深入共识状态机，明确改为“完整确定性命令已提交后，由各副本执行得到唯一结果”，不再要求第二次结果共识提交。收益是减少一层结果提交协议；代价是所有影响裁决的输入和历史规则必须完备、各副本执行必须一致。两种方案不能混称为同一套日志，也不能在回放中临时切换。经济规则仍保持托管现货，但以下使用独立数值案例。

### 1.2 一笔贯穿全文的业务

不计手续费、借贷与其他挂单，初始状态如下：

| 对象 | 初始状态 |
|---|---|
| A 的 USDT | 总额 50,000；已为买单 B1 预留 30,000；可用 20,000 |
| B 的 BTC | 总额 1 BTC；已为卖单 S1 预留 1 BTC；可用 0 |
| 已有卖单 S1 | 卖 1 BTC，价格 30,000 USDT/BTC，已在订单簿中 |
| 快照 | 分片 `btc-usdt-1`，已执行索引 S=100，包含 S1、去重表和未确认交付义务 |
| 新命令 | 索引 101：A 买 1 BTC，限价 30,000，请求键 `A/place/r1`，订单 B1，资格 R-A |
| 成交身份 | `btc-usdt-1/101/0`，0 为该命令内部确定的成交序号 |

金额使用整数最小单位：BTC 为 satoshi，USDT 本模型按 6 位小数；上表使用展示单位。价格网格为 1 USDT，数量网格为 0.001 BTC，示例均整除；乘法用足够宽的整数并检查溢出，不用浮点计算余额。

```text
A 发起 B1，携带请求键和订单条款
    ↓
账户服务以稳定意图建立 R-A，预留 30,000 USDT
    ↓
撮合入口校验身份、载荷、规则版本与预留资格
    ├─ 尚未受理 → 可以明确拒绝；释放须走资格撤销协议
    └─ 受理结果不明 → 保留预留，按原请求键查询或重试
    ↓
当前主节点提出命令 101，日志携带确定执行上下文
    ↓
共识协议形成持久多数并依法推进提交位置 C
    ↓ 此时才能承诺“可靠受理”，不能先回成功再补日志
单写者应用 101：B1 与 S1 各成交 1 BTC
    ├─ B1、S1 进入全成，产生稳定成交 ID
    ├─ 保存请求键、载荷摘要与结果
    └─ 产生不可因发送失败删除的结果交付义务
    ↓
结果交付器重复发送同一个成交批次
    ↓
账户事务：唯一消费键 + 校验预留 + 双方资产结转 + 账本
    ├─ 未提交或结果不明 → 重试同一事件，不生成新成交
    └─ 已提交 → 以相同结果确认
    ↓
交付确认以命令写回同一撮合日志，按序标记交付完成
    ↓
账户完成可查询；订单回报和行情按各自水位追上
```

交付确认命令占用后续日志索引，不假定它永远是 102。下文用 102 表示“另一条后续命令”时均单独说明条件。

### 1.3 在流程中发生崩溃

```text
101 未提交就崩溃
    → 不能当作成交；未提交尾部交给共识协议协调
    → 请求可能稍后提交，也可能被替换，超时方必须查询原键

101 已提交、尚未执行就崩溃
    → 从快照 100 读取已提交 101 → 执行并重建同一个成交

101 已执行、结果尚未送达就崩溃
    → 快照或回放重建待交付义务 → 发送原成交 ID

账户已入账、确认在网络中丢失
    → 撮合重发原事件 → 账户唯一消费键返回原结果，不再次入账

旧主失联、新主准备接管
    → 合法选举 + 确认提交屏障 + 应用追平
    → 接收端更新写权围栏 + 验证恢复状态 → 按能力分阶段开放
```

### 1.4 状态与完成条件

成交后，撮合中两单均全成，但账户可以暂时仍保留原预留；这代表**交收尚未完成**，不是可以把预留释放回可用。

账务事务完成后：A 的 USDT 可用 20,000、预留 0，BTC 增加 1；B 的 BTC 预留归零，USDT 增加 30,000。两人合计 USDT 仍为 50,000、BTC 仍为 1。实际资产在账户服务原子结转，不在回放线程里扣一次、消费线程里再扣一次。

拒绝、全成、撤余量都产生有序终态结果。部分成交变体另设为 S1 只有 0.4 BTC：成交 0.4 后 B1 剩余 0.6；撤单只释放剩余 18,000 USDT，已成交的 12,000 在交收结束前不得释放。不能把此变体与原始全成案例叠加。

## 二、核心板块

| 核心板块 | 决定什么、拥有何种状态 | 与上下游的契约 |
|---|---|---|
| 可靠受理与共识存储 | 命令能否进入可恢复前缀；任期、投票、日志、提交位置 | 入口不能把入队当提交；存储错误不得静默成功 |
| 确定性业务状态机 | 唯一订单状态、成交身份、去重结果、待交付义务 | 按已提交顺序执行；资金变化交给账户事务 |
| 快照与恢复器 | 某一执行位置的完整镜像及兼容元数据 | 快照与所需日志无缝衔接；损坏、缺口、版本不兼容则停机 |
| 复制与接管控制 | 合法新主、旧主失权、接管屏障 | 选举不等于应用追平；围栏须落到实际副作用接收端 |
| 结果交付与账户收敛 | 已裁决结果是否最终结转、是否重复入账 | 至少一次发送；账户消费键、记账和状态同事务 |
| 恢复验收与降级 | 哪类业务可安全恢复、剩余风险是什么 | 对照水位、数量、资产与交付证据，不能只看进程存活 |

## 三、核心 20%

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 确认与提交边界 | 提出到响应 | 定义已经承诺保留的事实 | 本地落盘成功被误称零丢失 | durable、commit、apply、账务水位 |
| 有序、完备的命令 | 提交到执行 | 同输入必须得到同结果 | 时间、随机、配置使回放改史 | 稳定身份、规则、批内顺序 |
| 切点一致的快照 | 执行到保存 | 镜像必须真属于一个位置 | 半新半旧镜像、漏去重或输出 | S/term、配置、发布、截断 |
| 已提交前缀恢复 | 重启到追平 | 不能漏执行，也不能执行孤儿尾部 | 假成交、静默跳过日志 | 连续性、校验、兼容、原子安装 |
| 唯一写权和围栏 | 失联到接管 | 检测超时不是旧主死亡证明 | 双主裁决、旧进程副作用 | 选举资格、屏障、接收端原子检查 |
| 交付义务与消费事务 | 成交到账本 | 复制撮合不自动复制账务 | 重复记账、丢交收、提前解冻 | outbox 重建、inbox、确认命令 |
| 可验证恢复门槛 | 追平到开放 | 恢复必须以业务证据收尾 | 技术健康但资金或状态错误 | 同水位核对、演练、容量与降级 |

这里的“20%”是正确性与取舍的集中点，不是限制题数。链扫描的规范链检查、数据库 PITR 等只讲本专题需要的恢复契约，不扩写为完整区块链索引或数据库教程。

## 四、设计与规则

### 4.1 水位、状态与不变量

对同一个节点、同一分片、同一条已验证历史：

- `S`：当前快照最后包含的已执行索引；`A`：业务状态机已执行索引；`C`：协议已知提交索引；`D`：本地已持久化的日志末位置。通常有 `S ≤ A ≤ C ≤ D`，安装快照后从 S 续接；D 大不代表分支正确或已提交。
- 重启时不能只从磁盘最后一条或从 `appliedIndex` 推断 C。由所选共识实现恢复协议状态、与集群协调并确认可用提交前缀；快照 S 只能来自已提交、已执行状态。
- 单条命令应用必须对观察者原子发布：订单、成交、请求结果、待交付义务与 A 共同前进。构造中失败不暴露半更新；致命错误停止分片并从可信基线重建。
- 订单数量满足 `原始量 = 累计成交量 + 已撤量 + 剩余量`；同一成交不能同时属于两个不同载荷。
- 请求身份为账户、操作、客户端请求号三元组；同键同摘要复用结果，同键异摘要拒绝。摘要按规范化业务载荷计算，覆盖方向、交易对、数量、价格和资格引用等；不把重试日志位置、网络封套或发送 token 加入业务摘要。重启、切主不生成新业务身份。
- 账户的交付进度独立于 A。`A=101` 不证明账户已记账；账户确认丢失也不证明未记账。按稳定事件键查询或重试。
- 已提交成交产生不可随意删除的交收义务。业务拒绝同样是可恢复结果；基础设施超时不是业务拒绝。
- 如用连续交付游标，则由状态机为实际产出的交付批次独立分配 `eventSeq`，连同下一序号进入快照；no-op、去重请求和确认命令可能没有交付事件，所以日志索引不等于连续事件序号。账户只推进已完整消费的连续前缀，不能用见过的最大值跳过缺口。
- 分片身份不可复用。灾难重建若可能重置日志索引，必须新建分片世代与下游映射，并通过受控迁移保留旧经济身份；不能沿用旧 `shardID` 使成交 ID 或围栏 token 倒退、碰撞。

### 4.2 架构与执行权

```text
入口／查询网关
    ↓ 提出命令、查询原请求
三节点共识组〔持久日志、任期／投票、集群配置〕
    ↓ 仅 committed entries
单写者业务状态机〔订单簿、去重结果、成交、待交付义务、A〕
    ├─ 一致镜像 S → 快照管理 → 恢复器
    └─ 当前获准的交付器 → 接收端围栏 + 账户消费事务
                                   ↓ 持久确认
                              提出交付确认命令
```

Raft 解决已提交历史与选主安全；应用层仍负责正确集成存储、确定性、快照内容和副作用。本文不自制一套 Raft，也不让 Redis 锁代替共识。

外部写入采用应用级围栏：新主提交一条接管屏障，其日志索引为递增 token；账户按预注册分片保存 `maxToken`，认证的接管控制路径安装 token。安装与每次写入都锁定同一围栏记录，在同一事务内校验 token、消费键和记账；新主等待安装确认才开放该外部写路径。token 不能只放在消息中而接收端不检查。

安装前可能到达的旧消息只允许引用真实已提交结果；安装后旧 token 拒绝，原合法事件由新主换用新 token、保留原事件 ID 重送。发送授权不能把未提交命令变成合法成交；任期/token 是执行授权，不是经济幂等键。外部系统不能支持围栏时，要另行设计可验证的幂等写网关或保守停写，不能宣称已隔离所有副作用。

### 4.3 必要数据

| 对象 | 必要字段与约束 |
|---|---|
| 命令日志 | `shardID, index, term, type, requestKey, payloadHash, payload, rulesVersion, schemaVersion`；存储层另有长度、校验和与记录边界 |
| 业务结果 | 原请求键、订单 ID、稳定成交 ID、确定条款、拒绝原因或成功结果；不绑定当前主节点地址 |
| 待交付义务 | 稳定 `eventID`、完整载荷与摘要、批内序号、依赖和逻辑确认状态；未确认内容须保留或可由受保留历史重建 |
| 账户消费 | `sourceShard,eventID,payloadHash,accountingResult`，唯一约束与资产变动同事务；同 ID 异摘要报警拒绝 |
| 快照清单 | `shardID,lastIncludedIndex,lastIncludedTerm`、生效配置、格式/规则版本、内容摘要、必要历史规则及文件清单 |
| 快照业务体 | 订单队列次序、索引重建材料、累计量、去重结果/过期屏障、成交与待交付义务、交付确认、A；不能只存盘口价格档 |

共识快照元数据由协议库维护或通过规定接口交接，不在业务代码中自行猜测成员配置。持久化顺序、消息发送与 `Ready/Advance` 等调用遵守选用实现的版本契约；“先广播再异步落盘总没问题”不是有效设计。

### 4.4 快照、截断与版本

快照在已应用切点 S 获取不可变镜像：短暂停写捕获或正确的 COW/MVCC，不把遍历 Go map 当原子快照。写临时文件、校验、同步数据、原子发布清单并按文件系统契约同步目录，再允许淘汰旧恢复材料。原子 rename 不自动等于掉电后持久。

只有新快照可信、必要协议元数据可恢复、未交付义务已包含或另有完整保留路径，才按保留策略压缩前缀。落后副本可通过 InstallSnapshot 追赶；灾备与审计保留不能因此一并删除。账户确认后可以从在线待交付集合逻辑移除，但若还承诺账户 PITR 或旧备份恢复，必须保留相应归档或共同检查点协议；账户回退会连同 inbox、余额和围栏记录一起回退，必须先隔离入口与旧发送者、恢复围栏并补齐缺失事实，不能直接接回生产。

旧规则执行器必须可获得；不兼容则停机。规则切换通过有序配置命令生效，并保证集群先具备执行能力。历史回放与修正业务是两件事，不能把新费率套到旧命令上“修复”。

## 七、工程实践——一个简洁 MVP

### 7.1 目标与范围

只手工验证“可信快照 100 + 给定已提交命令 101 → 重建稳定成交与待交付结果 → 重复投递不重复记账”。不实现文件 I/O、Raft、并发快照、选举、围栏、真实账户数据库或链扫描；`committed` 是题目提供的可信连续前缀，不由本伪代码推算。

### 7.2 核心伪代码

以下限定 S1 与 B1 各 1 BTC、价格相同、无手续费；内存集合用于表达语义，不宣称跨进程持久化。`atomic` 表示题目假设的账户事务，真实实现需要数据库事务与唯一约束。

```text
state = copy(verifiedSnapshot100)       // 含 S1、A=100、去重表、待交付集合
for cmd in committedAfter100:
    require cmd.index == state.A + 1
    require cmd.rulesVersion == supportedV1
    key = cmd.requestKey
    if key in state.requests:
        reply = state.requests[key].result if state.requests[key].hash == cmd.payloadHash
                else REQUEST_CONFLICT      // 不覆盖原请求结果，也不再次撮合
    else:
        require cmd is B1 and B1.qty == S1.remaining == 1 BTC
        require B1.price == S1.price == 30000 USDT/BTC
        require cmd.reservation == R_A and S1.reservation == R_B
        id = shardID + "/" + cmd.index + "/0"
        state.B1 = {status:FILLED, original:1, filled:1, cancelled:0, remaining:0}
        state.S1.status = FILLED; state.S1.filled = 1; state.S1.remaining = 0
        result = {id, buyer:A, seller:B, btc:1, usdt:30000,
                  buyReservation:R_A, sellReservation:R_B}
        state.pending[id] = result
        state.requests[key] = {hash:cmd.payloadHash, result:result}
        reply = result
    state.A = cmd.index               // 与本条全部状态在单写者内原子发布

for event in state.pending:           // 重发原事件，不能重造 id
    atomic accountTransaction:
        if event.id in inbox:
            require inbox[event.id].payload == event
            return inbox[event.id].result
        require reserved[A,R_A,USDT] == 30000
        require reserved[B,R_B,BTC] == 1
        reserved[A,R_A,USDT] -= 30000; available[B,USDT] += 30000
        reserved[B,R_B,BTC] -= 1; available[A,BTC] += 1
        ledger.append(event.id, USDT, A.reserved:-30000, B.available:+30000)
        ledger.append(event.id, BTC, B.reserved:-1, A.available:+1)
        inbox[event.id] = {payload:event, result:ACCOUNTED}
// 确认丢失时 pending 保留；生产方案将确认提交回撮合日志后才逻辑清除。
```

### 7.3 输入与预期结果

| 输入 | 手工预期 |
|---|---|
| 快照 100 + 已提交 101 | 恢复 A=101；两单全成；生成且仅生成原成交 `btc-usdt-1/101/0` |
| 从同一快照重新恢复 101 | 得到相同逻辑状态、结果 ID 和载荷；不是在已有 A=101 的状态上再次执行 101 |
| 同一结果投递两次，第一次入账后确认丢失 | inbox 命中，第二次不改变余额；USDT 合计 50,000、BTC 合计 1 |
| 执行后又提交同请求同摘要的重试命令 102 | 102 推进 A，但返回 101 原结果，不再撮合；不能以 102 生成新成交 |
| 缺少 101，直接读取 102；或规则版本不可用 | 停止恢复，不跳过、不采用当前规则替算 |
| 同一个 eventID 带不同载荷 | 拒绝并报警，不把“去重”理解成忽略载荷冲突 |

以上是预期推演，不是已执行的工程测试。MVP 不验证主备高可用，不能据此声称达到零数据丢失或某个恢复时长。
