# 大问题 12：怎样验证恢复的 RPO/RTO，并有依据地重新开放交易？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| RPO / 故障范围 | 已承诺数据允许损失多少，并说明承诺覆盖哪些失效。 | 本例保护模型内的持久提交前缀，不自动覆盖多数永久丢盘或账户任意回退。 |
| RTO / 分阶段开放 | 从约定业务能力受损起，直到该能力安全恢复的时间。 | 查询、撮合写入、交收、提现分别计时，选主或进程启动不是终点。 |
| 可靠受理 / apply / 交收 | 命令已提交、订单已执行，以及账户已完成资产结转。 | 101 成交 1 BTC 不代表 30,000 USDT 已结转，各阶段须有证据。 |
| 三节点多数 / 持久化失败 | 有效多数是两个，写盘失败节点不能冒充可靠参与者。 | 一个坏盘可由其余健康多数继续；两个无法持久写入就停新提交。 |
| S / D / A / 提交前缀 | 快照、本地持久尾部、已执行位置与协议确认历史。 | S=100、D=101 不足以执行 101，先由协议确认合法连续前缀。 |
| 接管屏障 / 围栏 | 新主提交并追到接管凭据，再让外部真实写端拒绝旧授权。 | 屏障索引不预设为 102，安装围栏本身也不直接授权恢复生产。 |
| Q / λ / μ | 待处理命令数、新增提交速率、恢复时持续处理速率。 | 必须在同一瓶颈按同单位估算；命令每秒不等于账户事件每秒。 |
| μ−λ / 净追赶速率 | 每秒消化积压而不是仅接住新流量的能力。 | 持续输入时 μ>λ 才能近似用 Q÷(μ−λ) 算收敛时间。 |
| 36,000 / 2,000 / 5,000 / 12 秒 | 本文用于解释追赶的假设数值。 | 36,000÷(5,000−2,000)=12 秒，不是实测能力或保证。 |
| 40 秒预算 / 关键路径 | 按串行阶段列出的恢复耗时设想。 | 5+3+8+12+2+6+4=40；PITR 补齐等额外工作不能藏起来。 |
| COW / 压缩 / GC | 写时复制、减小文件体积，以及 Go 回收不用对象的工作。 | 会占 CPU、内存和磁盘带宽，可能降低真实 μ，不是越多越快。 |
| 有界队列 / 背压 / goroutine 预算 | 限制等待与并发，把处理不过来的压力传回入口。 | 不能靠无限开协程追平，单分片 apply 仍按序。 |
| 可信快照 / 安全压缩 / 保留余量 | 新恢复材料经验证发布后，再按契约淘汰旧前缀。 | 空间要容纳临时文件、旧日志和归档，不能盘满就删唯一历史。 |
| PITR / 受控历史补齐 | 账户回退到旧事务切点后，按原身份补回缺失事实。 | 先隔离、围栏、补齐、同切点核对，再接生产，不能混同普通消费延迟。 |
| 能力门槛 / 撤单 / 提现 | 每种对外能力有自己的前置证据。 | 撤单仍须权威排序，提现还查账户与外部事实，“用户退出”不豁免安全边界。 |
| 演练预期 / 实测证据 | 先写清故障时应该怎样，再由真实运行记录验证。 | 本文只有设计、预算与推演，未执行不能说演练通过或报实测 RTO。 |

## 把整篇文章压缩成一个故事

B1 的命令 101 关系到 1 BTC 与 30,000 USDT，值班工程师小吴想承诺“故障后很快恢复”。他先写清三节点模型只保证约定单节点故障下的持久提交历史，账户恢复和外部提现另有证据。恢复也不是选出新主就结束：检测、选举、加载、追平、围栏、核对、开放按假设串行预算为 5、3、8、12、2、6、4 秒，合计 40 秒，只是计划值，不能包装成已达到的成绩。

其中 12 秒追赶预算还要算得通：假设积压 36,000 条，新增提交每秒 2,000，恢复处理每秒 5,000，净追赶每秒 3,000，才有约 12 秒。若压缩、COW 与 GC 抢资源，把持续处理能力压到不高于新增速率，等待不会让积压消失；小吴必须限流或停入口。账户消费另算，不拿命令吞吐充当交收吞吐，也不靠无限开 goroutine 或删除唯一恢复日志制造表面进展。

演练设计还要挑战禁止开放的分支：两个节点无法刷盘时，即使唯一健康节点能读到 101，也停止新提交；若账户 PITR，先隔离、围栏、受控补齐并同切点核对，再恢复生产。查询可标水位，撤单仍走合法顺序，已全成 B1 不能靠撤单退回成交款，提现更不能绕门槛。最后用提交位置、原事件 inbox、账本及各能力开放时间验收；没有真正执行演练，就只报告预期，不宣称零丢失实测或恢复时长达标。

**流程位置：**故障检测、接管、恢复、追平直到重新开放的验收闭环。本题承接前面的恢复机制，不再展开一套新架构，而是追问承诺适用于谁、容量是否足够、哪些证据允许哪类业务恢复。

**统一基线：**三节点 Raft，多数为两个；完整 command 经共识提交后，单写者唯一地确定性 apply。账户独立预留与记账。主例固定为快照 100、命令 101：B1 以预留的 30,000 USDT 买入 1 BTC，与 S1 全成；成交 ID 为 `btc-usdt-1/101/0`。账户消费键、预留结转、账本及余额变化同事务，监控和对账不替代事前原子性。

**核心机制：**按故障模型及确认语义定义 RPO，按业务开放阶段定义 RTO；用可信前缀、唯一写权、容量余量与交收证据逐项放行。本文所有时长和速率都是教学假设，不是生产经历、测量结果或已经执行的演练；不提供独立 MVP、可运行工程或测试结论。

## 第 1 层：先把 RPO 绑定到已承诺前缀和故障范围

**面试官：**你用了三节点 Raft，是不是可以直接承诺 RPO 为零，任何故障都不丢交易？

**面试者：**不能。只能在总览的崩溃、分区、单节点永久磁盘损失等承诺范围内，讨论已确认的持久提交前缀不丢失；两个以上持久副本同时永久损失、虚假刷盘及全域灾难不在这项保证里。多数不可用时停止新提交，不靠少数副本继续营业。

还要拆开确认语义：命令 101 已提交才可称可靠受理，确定订单结果要等 apply；账户是否已交收另看消费事务。超时请求可能后来提交，须按原请求键查询，不能算作明确拒绝。撮合前缀的 RPO 为零不自动覆盖账户 PITR、外部提现或归档丢失，更不意味着所有客户端都已收到响应。

## 第 2 层：RTO 计到业务开放，而不是进程启动

**面试官：**你已经缩小了零丢失的承诺，那恢复时间从哪里开始、到哪里结束？选出新主算不算恢复？

**面试者：**不算。以约定业务能力受损为起点，分别记录恢复查询、撮合写入、账户交收及提现的时刻；检测告警不能替代起点，否则漏掉检测耗时。关键路径至少包含检测、选举、加载恢复、应用追平、接收端围栏、业务核对及分阶段开放，选主只是其中一步。

例如假设这些阶段串行预算为 5、3、8、12、2、6、4 秒，合计 40 秒；这是分解预算，不是已达成 RTO。若账户回退恢复，还须在围栏安装后、核对前计入受控历史补齐耗时，不能直接沿用 40 秒；补齐及同切点核对前不开放生产写入。实际验收须记录阶段证据、停顿和失败分支，不能只报进程启动时间。

## 第 3 层：让可信前缀和接管屏障成为放行证据

**面试官：**预算说要“恢复、追平、核对”，具体要检查什么？假设新主本地已经有 101，为什么还不能开放？

**面试者：**因为本地末尾 D=101 不证明它已提交。先让 Raft 按协议确认合法前缀，验证快照 100 的分片、摘要、规则及配置，再连续应用已提交的 101，重建原成交、去重结果和交付义务；缺口或不兼容就停止。

接管屏障须提交并应用，索引不预设为 102。账户若回退恢复，顺序必须是隔离生产、原子安装当前围栏、仅受控修复通道按原 ID 补齐历史、同切点核对，再开放生产；围栏落地不等于放行。B1 全成只证明撮合完成，未交付时保留预留；只有原事件的持久消费结果才能证明交收，不能凭进程健康放行。

## 第 4 层：用净追赶速率证明积压能够收敛

**面试官：**固定屏障好验证，但健康节点可能仍在提交，或者还有存量交付。你凭什么给追平阶段分配 12 秒？

**面试者：**必须先定义同一瓶颈上的单位。令 Q 为待处理命令数，λ 为新增已提交命令速率，μ 为恢复时实际可持续处理速率；持续输入下须 μ 大于 λ，近似追赶时间才是 Q 除以 μ−λ。假设 Q=36,000、λ=2,000 条每秒、μ=5,000 条每秒，才得到 12 秒，且忽略波动和额外安装开销，不是实测承诺。

若已停提交，λ 为零；μ 不大于 λ 时则无法靠等待追上，应限流、暂停入口或扩大有效瓶颈能力。账户事件吞吐另算，不能把命令每秒直接当成交每秒。还要验证突发积压、磁盘和网络余量，使用有界队列、背压和有界 goroutine，不能无限并发把“追平”变成内存耗尽。

## 第 5 层：快照频率、压缩和 GC 要一起纳入容量

**面试官：**那多做快照，把 Q 压小，再多开 goroutine 解压回放，不就既快又省资源了吗？

**面试者：**不一定。快照更频繁会增加复制、序列化及刷盘负担；压缩节省传输和存储，却消耗 CPU，解压时仍要容纳状态及缓冲。COW 镜像与旧对象并存、海量临时分配又会扩大 Go 堆和 GC 压力，让刚才假设的 μ 下降。

容量应覆盖在线状态、快照制作或安装峰值、旧日志保留、归档积压和临时文件，采用有界工作池、缓冲与并发预算；单分片 apply 仍按序，不能靠并发改订单簿。只有新快照可信发布且未交付义务及灾备保留满足契约，才能压缩前缀。不能为解磁盘压力提前删唯一恢复材料；若没有资源余量，应降低入口负荷或保持停写。

## 第 6 层：磁盘满时分清单节点失效与多数不可用

**面试官：**保留快照和日志又使磁盘更紧。如果节点写满了，你会删旧日志保服务，还是让内存先接单？

**面试者：**都不能绕过持久化契约。单节点磁盘满或刷盘失败，应视为该节点不能可靠参与相应写入；若其余两个节点仍健康且可通信，可按 Raft 协议形成持久多数、必要时重新选主，不能把失败写盘伪装成确认。

若两个节点无法持久写入，多数能力已经丧失，即使剩余节点磁盘充足、内存也有 101，仍须停止新提交，不能临时降为一票或回成功后补盘。它至多提供带水位及陈旧性说明的可验证查询，不能无多数时承诺线性一致新读。清理只针对已安全淘汰的材料，恢复后仍须验证日志、追平与围栏；“磁盘空出来了”不是开放证据。

## 第 7 层：按能力降级，不能让撤单和提现绕过安全门槛

**面试官：**多数失效时只读尚可理解。如果多数恢复但账户还在追赶，至少放开撤单或提现，让用户先退出，是否更合理？

**面试者：**要逐项授权，不能把“退出”当成无副作用。撤单也是有序命令，须有合法多数、当前写权和已追平状态；资金释放还必须取得撮合终态或撤销屏障并经账户事务，RPC 超时不能释放 B1 的预留。

先区分普通消费延迟与账务回退恢复：后者必须隔离、围栏、受控补齐并同切点核对后才开放生产。仅对前者，可提供带水位查询，满足前提后接受撤单意图但不承诺立即解冻；预留有效、积压受控且契约齐全才考虑新单。B1 已全成就不能撤回已成交的 30,000 USDT。提现还须核实账户、授权及外部状态，退化不能突破原子性或最终性边界。

## 第 8 层：故障演练验证预期及停写路径，不包装成经历

**面试官：**这些门槛听上去都合理，怎样设计演练证明它们不是纸面规则？又如何避免只验证成功恢复？

**面试者：**先写故障窗口、预期不变量和禁止开放的条件，再设计注入：101 提交前主崩溃应按原键查明结果；提交未 apply 应从快照 100 重建同一成交；账户入账后丢确认应重送不重记；旧主迟到应被围栏拒绝。还要覆盖快照损坏、账户 PITR、磁盘满和多数丧失，后两者应包含停写预期。

预期证据包括提交及应用位置、快照摘要、围栏安装记录、inbox 与账本关联，以及各开放阶段时间。B1 最终仅结转 1 BTC 和 30,000 USDT，资产归属、预留及总量均正确；μ 不足时应限流而非无限等待。以上只是演练设计，未执行就不能宣称通过、报告实测 RTO，或把“没报警”当正确性证明。

## 本题收束

### 讲透的机制

- **RPO 是限定范围的承诺。**持久已提交前缀、客户端确认、账户交收和外部最终操作各有证据；不能用一个“零丢失”覆盖所有系统与所有灾难。
- **RTO 是分阶段业务恢复时间。**检测、选举、恢复、追平、围栏、核对与开放均有耗时和失败出口；应用未追平、围栏未落地时，新主身份不构成放行资格。
- **容量决定恢复是否收敛。**按同单位计算 Q、λ、μ，确认持续输入下 μ 大于 λ，并把快照、压缩、GC、磁盘、账户消费及保留成本计入有效能力。
- **降级是带前提的能力集合。**只读、撤单、新单、交收、提现分别有门槛；多数不可用必须停新提交，不能用“用户需要退出”授权少数派写入。

### 最容易答错的边界

- 假设预算、公式估算、演练预期和真实测量是四种不同证据；本题只提供前三者，没有声称已经运行演练。
- 快照和历史压缩必须服从可信发布、未交付义务及共同恢复窗口，不能把删恢复材料当作磁盘满时的通用自救。
- 监控负责发现异常，对账负责发现和定位差异；唯一消费键、资产结转、账本和余额的事前事务边界不能由它们补做。
- 同一已提交命令只按确定顺序 apply；回放重建交付义务，不在回放线程与账户消费线程各扣一遍钱。

### 一个反例

三节点中两个磁盘满，唯一健康节点加载快照 100，发现本地尾部有 101，便宣称“单机恢复 3 秒、RPO 为零”，直接放开 B1 新请求和提现。这个结论同时混淆本地持久与提交、进程启动与业务 RTO，也绕过多数写入及账户门槛。预期正确行为是停止新提交、标明可提供查询的水位，修复持久多数后验证可信前缀、接管围栏和账户事实，再逐阶段开放；不能靠事后监控把错误开放变成安全恢复。
