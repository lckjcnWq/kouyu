# 大问题 4：回放为什么会产生不同成交，怎样保证确定性？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 确定性状态转移 | 给定同一旧状态、输入顺序与规则，结果只能有一种。 | 不只盘口相同，订单、请求结果、成交身份和交付载荷都要相同。 |
| command-only / 结果批次权威 | 前者靠完整命令推导结果，后者以已提交结果作为恢复依据。 | 本专题选前者，不额外做结果共识；不能回放到一半换方案。 |
| 快照 100 / 命令 101 | S1 的可信起点，以及 B1 的已提交买入意图。 | S1 卖 1 BTC，B1 买 1 BTC、限价 30,000，原成交必须能重建。 |
| 完备输入 / 外部决定固化 | 把所有会影响裁决的条件纳入可恢复历史。 | 时间、风控、精度等不能在恢复时改查当前服务得到新答案。 |
| R-A / 预留资格 | 事先取得并持续有效的下单资格引用。 | apply 不重新查当前账户余额；否则结转后的余额会改变旧订单裁决。 |
| time.Now / 到期命令 | 本机当前时间，以及被排入业务顺序的到期事实。 | 回放不能用今天的墙钟判昨天订单过期，到期要有确定输入和规则。 |
| eventID / UUID / token | 经济身份、随机编号，以及发送授权。 | 成交用不可复用分片与首次执行索引、批内序号；不用随机数或新任期重命名。 |
| 单写者 / Go map | 独占可变状态的执行者，以及迭代顺序不固定的容器。 | 单 goroutine 不保证算法确定，不能让 map 遍历决定谁先成交。 |
| FIFO / 稳定全序 | 同价按先来先处理，并用明确字段决定所有先后。 | 保留原受理位置和队列次序，后台计算完成先后不能替代撮合顺序。 |
| satoshi / USDT 六位小数 | BTC 与 USDT 在本模型里的整数计量尺度。 | 展示的 1 BTC 与 30,000 USDT 要按固定单位转换，不用浮点算余额。 |
| 舍入 / 溢出 / 精度配置 | 除不尽怎么取整、数值超界怎么办，以及使用哪套尺度。 | 整数本身不包办正确性，乘除顺序与异常处理也须固定。 |
| rulesVersion / 历史执行器 | 标识业务规则版本，以及真正能执行它的旧实现。 | 存一个版本号不够，升级后仍要能重演历史规则。 |
| 有序配置命令 | 把新规则从哪里生效也纳入共同顺序。 | 集群先具备兼容能力，再切换；修 bug 不能偷偷改已确认历史。 |
| A / 整命令原子发布 | 已执行位置，以及一条命令的所有变化一起可见。 | 多笔成交、订单、去重、outbox 完整后再推进 A，不能边算边外发。 |
| outbox / 外部副作用 | 待交付的业务义务，以及账户扣款等真实外部效果。 | apply 只重建义务，不同步扣款；外发用原 ID 与账户事务去重。 |
| 同水位逻辑摘要 / 差分回放 | 在相同执行位置用规范化业务内容比较两个执行器。 | 排除内存地址和 map 顺序，但必须保留 FIFO 与原成交条款。 |

## 把整篇文章压缩成一个故事

A 的 B1 在命令 101 买到 S1 的 1 BTC，价格为 30,000 USDT，主节点随即崩溃。接班工程师小赵发现恢复程序想重新读取 Redis 价格、账户当前余额，再生成随机成交号。这样不是恢复，而是在另一个时间重新裁决：余额可能已结转、配置可能已升级，连同一笔成交的身份都变了。本专题不再提交第二份结果日志，因此必须让快照 100、完整命令和历史规则本身足以唯一推出原结果。

小赵让资格 R-A、规则版本、精度与所有影响裁决的条件都能从可靠历史取得。单写者按既定价位和 FIFO 执行，不让 Go map 顺序或后台任务完成速度挑选卖单；金额用固定整数尺度，同时规定乘除、舍入和溢出行为。订单、请求结果、稳定成交 `btc-usdt-1/101/0`、待交付义务与 A 一起发布。中途失败就丢弃不可信状态，从完整切点重建，不能把前半笔成果先发出去。

恢复线程只重建事实，不直接调用账户扣款；真正交付使用原事件身份，由账户事务避免重复经济效果。升级也先确保旧规则可执行，再通过有序命令切换，不能把修正历史藏在重启里。若快照已经覆盖 101，就从快照之后续接，不在全成订单上再撮合一次。是否确定要靠同水位逻辑状态和结果的比较验证，单 goroutine、版本号或整数类型本身都不是证明。

[返回专题总览](README.md)

**流程位置与核心机制：** 聚焦已提交命令如何唯一决定状态与结果。沿用总览单分片命令状态机；与已有撮合专题“先提交命令、再提交结果批次”的方案不同，本模型不依赖第二次结果共识提交，因此输入完备与历史规则可用是更强的前提。

## 第 1 层：确定性具体保证什么

**面试官：** 主节点处理 B1 后崩溃，新节点回放同一命令，怎样保证不会得到不同成交？

**面试者：** 我把业务执行定义成确定的状态转移：相同已验证初始状态、相同有序命令和相同规则版本，必须产生相同逻辑新状态与结果。快照 100 包含 S1 的 1 BTC 和队列位置，101 完整定义 B1，执行后都应产生两单全成及 `btc-usdt-1/101/0`。这里比较的不只是盘口总量，还包括请求结果、成交身份、数量、价格和待交付载荷。回放不是“再猜一次当时应该怎样成交”，而是重建当时唯一可导出的事实；做不到这一点，就不能选择这种纯命令状态机模型。

## 第 2 层：命令为什么不能只有订单参数

**面试官：** 你说输入必须完备，B1 的价格和数量已经在日志里，还缺什么？

**面试者：** 还要包含或引用可恢复状态中的全部决策条件：稳定请求身份、预留资格、规则和格式版本、精度配置，以及任何影响准入、排序和结果的业务时间或风险参数。若执行时访问当前账户可用余额，主节点在原时刻看到 30,000，回放节点看到结转后的余额，就可能拒绝原本合法的订单。基线通过事先建立且不会独立过期的 R-A 表达撮合资格，撮合不在 apply 中重新请求外部余额。外部校验若具有业务裁决含义，应将可验证决定转换为有序输入，而不是在每次回放时重新询问。

## 第 3 层：超时和随机身份如何处理

**面试官：** 如果执行到订单过期判断或生成成交 ID，能否直接调用 time.Now 和随机 UUID？

**面试者：** 不能让本地墙钟或随机值决定可恢复结果。同一命令在一分钟后回放，过期判断可能改变；随机 UUID 则让同一成交变成新的消费键。业务到期可以使用已记录的接入时间及规则，或由明确的到期命令在同一顺序中裁决；时间来源的可信性与准入规则另行定义，不能把当前时间当历史事实。订单身份随原意图稳定，成交身份由不可复用分片身份、首个执行命令索引及批内序号生成。选主的任期和发送围栏不参与经济身份，因此切主不会把旧成交重命名。

## 第 4 层：单写者为何仍可能不确定

**面试官：** 我已经只用一个 goroutine 撮合了，为什么同一输入还可能得到不同顺序？

**面试者：** 单写者解决并发修改，不自动解决遍历和算法的不确定性。Go map 迭代顺序不能决定同价订单优先级；要持久维护明确 FIFO 或用原受理位置及批内序号构成稳定全序。价格档必须按规定的最优价格访问，撤单索引只是定位工具，不能改变队列优先级。并发预处理可以做解码、摘要和非状态校验，但真正依赖状态的裁决及发布要回到同一顺序。不能按后台任务完成先后决定历史撮合顺序，否则相同日志在不同 CPU 调度下仍会产生不同结果。

## 第 5 层：整数金额是否就不会分叉

**面试官：** 遍历顺序固定了，再把金额都改成整数，是不是已经完全确定？

**面试者：** 整数避免浮点误差，但还要固定单位、乘除顺序、舍入方向和溢出行为。例如 BTC 数量用 satoshi、USDT 用六位小数，名义金额计算要有确定的尺度转换；不能某个版本先除后乘，另一个版本先乘后除。乘法必须使用足够宽的整数或显式溢出检查，不能依赖溢出后的偶然值。示例价格和数量网格保证整除，只能说明这笔例子简单，不证明其他输入正确。若后续增加手续费，就必须把费率和累计舍入规则纳入版本，不能在回放时临时读取最新费率。

## 第 6 层：升级后如何执行旧命令

**面试官：** 你已经固定算法和单位，但三个月后修了撮合代码，新程序回放旧日志怎么办？

**面试者：** 规则版本必须有明确执行入口和可获得的历史实现，不能只保存一个版本号却最终全部调用新函数。升级前先验证新节点能够解释当前快照与未压缩日志涉及的旧版本，再通过有序配置命令确定新规则从哪个位置开始生效。集群混合版本期间，任何可能参与应用的节点都必须具备执行能力；旧节点不兼容就不能让它继续承担该角色。修复代码若改变历史裁决，应该通过明确业务修订、迁移或新版本切点处理，不得让恢复过程静默把已经确认的历史改成“现在看来更正确”的结果。

## 第 7 层：已有结果是否需要重算验证

**面试官：** 如果快照已经存了 101 的成交结果，恢复时还要重新撮合 101 来检查吗？

**面试者：** 若快照 S 已经覆盖 101，恢复从 S 后继续，不能在该状态上重做 101。离线验证可以从更早可信快照和完整日志独立计算，再比较同一水位逻辑摘要，但不能把验证输出当第二份待入账成交。如果另一个架构以已提交结果批次为权威，应原样应用结果，只有确认无结果的命令尾部才按协议计算。本文选择的是完整命令决定结果的模型，两套恢复规则不能混用。历史校验负责发现差异，不能绕过原经济身份、账务去重或权威提交边界。

## 第 8 层：一条命令生成多笔成交时怎么办

**面试官：** B1 如果连续吃掉三个卖单，执行到第二笔时发生 panic，第三次启动会不会只补最后一笔？

**面试者：** 单条命令的全部状态与输出必须作为一个应用单位发布。可以先在私有变更集里计算订单变化、三笔稳定成交及请求结果，通过校验后在单写者边界共同发布，并推进 A；也可以在进程级故障后丢弃不可信内存，从已知完整切点整体重建。不能将 A 提前推进，也不能边算边对外发送前两笔，再从局部内存猜下一笔。若使用持久化业务状态，所有相关状态与 A 必须同事务或有等价恢复协议。批内成交序号按确定撮合顺序从零分配，不因中途失败而改号。

## 第 9 层：状态机里能否直接调用账户扣款

**面试官：** 既然要原子处理整条命令，我在 apply 末尾同步调用账户，成功后再推进 A，可以吗？

**面试者：** 这会把外部副作用和本地状态推进绑在一个没有共同事务的故障窗口里。账户已扣款而 apply 崩溃，恢复又会调用一次；网络不明还会阻塞整个状态机，副本回放更可能各自发请求。正确基线是 apply 只确定内部状态和待交付义务，外部交付独立执行，使用稳定事件 ID 和账户消费事务保证重发不重复入账。交付成功再以确认命令回写逻辑状态。即便接收端有幂等，也不能把任意外部 I/O 塞进确定性状态转移，让其成功与否反过来改变撮合历史。

## 第 10 层：怎样发现确定性被破坏

**面试官：** 你把所有约束都列了，怎样验证某次升级没有漏掉隐藏依赖？

**面试者：** 从相同快照、相同已提交前缀分别运行参考执行器和候选执行器，在相同 A 比较规范化逻辑状态及结果摘要。摘要按确定顺序编码订单、FIFO、累计量、请求结果和待交付义务，排除 map 顺序、内存地址、发送重试计数等非业务噪声。设计会暴露依赖的输入：同价多单、跨时间回放、不同随机种子、边界金额、规则切换和多成交中断。任何差异都先阻断升级或接管，定位规则与数据，不用多数结果投票掩盖业务 bug。本文提供验证方法与预期，不声称执行过跨版本回放测试。

## 本题收束

- **讲透的机制：** 输入完备、稳定全序、固定数值语义、历史规则和整命令应用，共同支撑提交命令决定唯一结果。
- **最易答错：** 以单 goroutine 代替确定性证明，以版本号代替历史实现，回放时重新访问当前外部状态或直接出账。
- **反例检验：** 对同一日志更换墙钟、map 构造次序和主节点任期；业务状态、原成交 ID 及载荷应不变，否则恢复前提不成立。
