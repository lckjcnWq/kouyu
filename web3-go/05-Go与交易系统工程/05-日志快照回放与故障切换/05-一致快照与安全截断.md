# 大问题 5：快照怎样保证属于同一时刻，并在崩溃后支持安全截断？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 快照 / S | 把某个完整执行位置的状态固定下来，S 是这个切点。 | 不只保存盘口，还要能继续裁决、识别重试并交付旧成交。 |
| A / C / lastIncludedTerm | 已执行、已提交位置，以及快照边界条目的任期。 | A=100、C=101 时只能捕获到 100，不能把未执行命令写进快照水位。 |
| 单写者应用边界 | 一条命令所有状态都完成之后的完整时刻。 | 在这里固定订单、请求结果、outbox 与 A，避免半条成交进入快照。 |
| 深拷贝 / 对象图 | 复制整个相互引用的可变数据，而不只是外层容器。 | map 中指针、slice 底层数组与嵌套集合都要固定在同一 S。 |
| COW / 版本根 | 写时复制，旧根保留旧对象，新写构造新路径。 | 共享可变子对象不能原地改；保存结束前也不能回收复用旧对象。 |
| FIFO / 派生索引 | 同价订单业务次序，以及便于查询的辅助结构。 | 索引可重建，原队列次序不能丢或重新排序。 |
| 去重结果 / 墓碑 / 会话屏障 | 记住原请求答案，以及清掉详细结果后仍阻止旧请求重做的证据。 | 这些同样进入快照，不能因为当前盘口不需要就省略。 |
| outbox / eventID / eventSeq | 未完成交付、经济身份，以及实际交付批次的连续编号。 | 保存完整载荷、确认状态与分配进度，日志压缩不能让旧义务消失。 |
| manifest / 文件闭包 | 清单及其必须引用的全部文件。 | 同代号、分片、S、版本、长度和摘要要匹配，缺一件就拒绝。 |
| 内容摘要 / 逻辑摘要 | 检查文件字节，以及按规范编码的业务内容。 | 摘要正确仍不能单独证明历史已提交，协议元数据也须核验。 |
| Sync / rename / 目录同步 | 数据持久化、名字原子切换，以及目录项持久化。 | rename 原子不等于掉电持久，必须数据先落稳、引用后发布。 |
| 原子发布 / 崩溃窗口 | 对外切换到完整新一代，以及中途可能掉电的间隙。 | 未完成发布前保留旧恢复材料，不能按文件名最大值盲选。 |
| InstallSnapshot / 原子安装 | 按协议把整份新状态和水位接管到本地。 | 先隔离校验，暂停应用与发布，再绑定协议元数据、业务根和 A。 |
| S+1 / 后缀衔接 | 快照之后第一条待续接的位置及合法历史。 | 后缀保留要看边界索引、任期和库规则，不能随便拼文件。 |
| 安全截断 / 归档保留 | 用可信快照替代部分本地恢复日志，不是删除所有旧事实。 | 落后副本仍要可追赶，审计、灾备与未完成输出另有保留契约。 |
| 交付确认 / PITR | 账户记账确认写回撮合，以及账户以后回退到过去切点的能力。 | 在线义务可逻辑清理，不代表恢复窗口内的事件材料可以物理销毁。 |

## 把整篇文章压缩成一个故事

B1 的命令 101 已经提交，但撮合内存还在 A=100，工程师小唐准备做快照，想直接给文件标上 C=101。这样重启就会以为成交已经包含在镜像里，跳过真正该买入 1 BTC 的命令。小唐必须在完整应用边界捕获 S，并让订单、去重、待交付结果与 A 同属这个位置。后台保存时，在线系统可以前进，但冻结镜像不能跟着改变；浅拷贝 map 或只锁一个集合都不够。

他可以暂停单写者深拷贝全部可变对象，也可以用正确 COW 保住旧版本，再把文件、长度、摘要和规则依赖绑定到同一清单。保存不能只做 rename：先同步数据及相关目录，再发布并持久化清单，且与共识库的快照元数据可恢复衔接。发布中掉电，旧材料必须仍在；重启只选能完整验证且能接上合法日志的一代，不看谁文件名最大。安装远端快照也不能把新盘口配上旧 A。

再设 101 已成交且账户已记账，但确认丢失，102 只是另一条已应用命令。即使新快照 S=102、旧日志已压缩，镜像仍须保存 `btc-usdt-1/101/0` 的完整未确认义务；重送由账户去重，不能再次结转。确认可靠写回后才能按策略清理在线项，账户 PITR 所需归档仍要保留。截断节省的是可被可信材料替代的恢复日志，不是把已经欠下的交收一笔勾销。

[返回专题总览](README.md)

**流程位置与核心机制：** 位于已提交命令的确定性应用之后、恢复与日志压缩之前。本题沿“选择应用切点 → 捕获不可变镜像 → 封装与持久发布 → 安装 → 淘汰旧材料”深入，重点证明镜像与恢复材料始终闭合，不展开完整选举或账户交收协议。

**必要前提：** 沿用总览的三节点 Raft、单写者状态机和 BTC/USDT 案例。快照初始切点 S=100；命令 101 让 B1 与 S1 各成交 1 BTC，稳定成交 ID 为 `btc-usdt-1/101/0`。命令提交后一次确定性 apply 同时生成订单结果、去重记录与 outbox，不另做一次结果共识提交。撮合仅持有预留资格引用，余额与账本属于账户服务。分片身份不可复用，不能重置索引后沿用旧身份生成碰撞的 eventID；若使用独立 eventSeq，其分配状态也属于快照。以下为教学设计与故障推演，不代表实测。

## 第 1 层：为什么快照切点必须是已应用位置 S？

**面试官：** 快照怎样保证属于同一时刻？既然 Raft 已经知道提交位置 C，直接把 C 写进快照清单可以吗？

**面试者：** 不可以，提交只证明命令不能任意撤销，不证明内存已经执行到那里。我会在单写者完成一条命令的全部状态更新后捕获镜像，把当时的已应用位置记为 S，同时取得该位置的任期及协议要求的元数据。例如 A=100、C=101 时，B1 尚未执行，镜像只能声明 S=100；写成 101 会让恢复跳过本应产生成交的命令。镜像中订单、请求结果、待交付义务和 A 必须属于同一切点。捕获后在线状态可以继续推进，但快照标签不能跟着当前 C 或 A 改写。

## 第 2 层：在切点处遍历 Go map 为什么仍不够？

**面试官：** 你已经选定 S=100，但后台编码时单写者继续执行 101。给保存订单的 Go map 加锁遍历，就能得到 100 的镜像吗？

**面试者：** 只保护一次 map 遍历不够：订单对象可能被指针引用，价位队列、去重表和 outbox 还可能分别更新，最终得到半新半旧的组合。一个直接方案是在应用边界暂停单写者，深拷贝整个可变对象图以及 A，再解除暂停，让后台只编码这份副本。拷贝必须覆盖 map 值指向的对象、slice 底层数组及嵌套集合，不能只是复制 map 头或结构体中的指针。所有修改路径都必须服从同一暂停协议。这样付出一次明确的停顿，换取镜像确实固定在 S；若停顿不可接受，才讨论更复杂的 COW。

## 第 3 层：COW 怎样避免共享指针把旧镜像污染？

**面试官：** 深拷贝停顿太长，你改成 COW。但 101 会改订单剩余量和多个队列，怎样保证保存线程仍然看到 100？

**面试者：** COW 的关键不是“复制一个根指针”，而是根以下被共享的可变对象都不能原地修改。我会在应用边界固定包含 A 的版本根；后续更新先复制受影响路径上的订单、队列节点、索引及去重和交付集合，再发布新根。旧根可达的 slice、指针对象和缓存也必须保持不可变，不能从旁路继续写。保存线程持有旧版本引用直到编码结束，期间不能回收或复用这些对象。版本积压要有内存预算，超限可暂停制快照或施加背压，不能偷偷退回共享写。无论选深拷贝还是 COW，成立条件都是整个状态图在 S 冻结。

## 第 4 层：冻结的对象图为什么不能只保留盘口？

**面试官：** 你保证了整个状态图不变。为了缩小快照，只编码价位和挂单数量，其余靠恢复时重新推导，可以吗？

**面试者：** 不行，盘口只是外观，不足以恢复未来裁决和已有承诺。快照要保留订单条款、同价队列次序、累计成交和撤单量，以及重建查询索引的材料；还要包含请求键、摘要与原结果、过期墓碑或会话屏障、稳定成交和未确认 outbox 的完整载荷、逻辑交付确认及 A。预留资格引用也要保留，但不能混入账户余额作为撮合权威。清单还须绑定分片、S、对应任期、生效配置、格式与规则版本，以及历史规则依赖。派生索引可以重建，前提是原材料足够且重建不会改变价格时间优先或遗失旧结果。

## 第 5 层：怎样证明这些内容确实属于同一份快照？

**面试官：** 你要保存这么多集合和文件，怎么发现少了一个 outbox 文件，或误把上一代去重表配进这一代？

**面试者：** 我会为快照分配不可复用的代号，让一份清单明确列出全部必需文件、长度和内容摘要，并将它们与同一分片、S、格式和规则版本绑定。编码只读取被冻结的版本根，不能编码到一半再读取在线集合。恢复必须检查清单的文件闭包，缺文件、长度不符、摘要错误或版本组合不兼容都拒绝。文件摘要检测字节损坏，逻辑摘要则按规范顺序编码字段；Go map 要排序，但同价队列必须保留业务顺序，不能排序掩盖差异。摘要一致也不证明历史合法，S、任期和成员配置仍须通过共识库的契约验证。

## 第 6 层：原子 rename 为什么不等于持久发布？

**面试官：** 清单和摘要都齐了。我把临时文件 rename 成正式快照，再删除旧日志，是否已经原子且持久？

**面试者：** rename 主要提供命名切换的原子性，不自动提供掉电持久性。我会先写完不可变数据文件，检查写入错误并逐个 Sync，再将临时名字改为正式代号，同步所在目录；新建目录时，其父目录项也要按文件系统契约持久化。随后写包含完整引用的临时清单，Sync 后原子替换当前清单，再同步该目录。只有全部成功且协议库接受这份持久快照，才把它作为截断依据。数据先持久、引用后发布，不能反过来。任何写入或同步错误都不授权压缩；旧快照和旧日志在此之前保持可恢复。

## 第 7 层：发布过程中崩溃，恢复该选择哪一代？

**面试官：** 你保留了旧材料。但如果清单 rename 已完成、目录同步尚未完成就掉电，重启时怎样判断能否使用新快照？

**面试者：** 这个窗口不能宣称发布已经持久，也不能启动旧材料清理。重启时可能看见旧清单，也可能看见新清单；恢复器应按发布协议检查候选清单、所有引用文件，以及它与共识快照元数据和保留日志的衔接，而不是挑文件名最大的版本。新清单完整且能按协议恢复才可使用；不完整则隔离，只有旧快照加连续所需日志仍齐全时才能回退。未被清单引用的临时文件不能自动当成有效快照。尤其不能业务体声明 S=100，协议元数据却声明已安装到 101；两者必须通过可崩溃恢复的交接协议绑定。

## 第 8 层：InstallSnapshot 怎样避免把新旧状态混在一起？

**面试官：** 本地发布可以交给恢复协议处理。落后副本正在应用日志时收到远端快照，又怎样把协议水位和业务状态一致地安装？

**面试者：** 收到文件不等于安装。我会先在隔离区校验来源分片、清单闭包、摘要、版本和规则支持，再让共识库判断快照是否可接受，拒绝过时或不合法的安装。切换时暂停应用与对外状态发布，按库规定持久化快照及协议状态，安装业务根并把 A 设为 S，然后从合法的 S+1 续接。日志后缀能否保留由边界索引、任期匹配及库的规则决定，不能无条件拼接。中途崩溃要能由持久标记重新完成同一安装，不能暴露半份新状态或把旧 A 配新订单簿。校验完成前也不启动交付器。

## 第 9 层：安装成功后，究竟能压缩哪些日志？

**面试官：** 新快照已可信发布并能安装。是不是可以立刻删除 S 以前的一切，而且必须等所有副本都有这份快照？

**面试者：** 可以进入压缩判断，但不是删除一切。先确认新快照及必要协议元数据持久可恢复，S 之后的日志能够连续续接，所有仍需履行的输出都有完整保留路径，再通过共识库接口压缩不再用于本地恢复的前缀。是否保留额外日志窗口取决于追赶成本；落后副本可按协议安装快照，不必把“所有副本确认”当成一律适用的压缩前提。但必须仍能向它提供可用快照和后缀。共识日志压缩不等于审计归档、灾备版本和结果保留都可删除。特别是输出来自索引小于 S 的命令，也可能仍未交付。

## 第 10 层：日志已压缩，早于 S 的交收义务怎样存活？

**面试官：** 你说早于 S 的输出还可能未完成。假设 101 已成交、账户已入账但确认丢失，之后制作 S=102 的快照并压缩日志，该留下什么？

**面试者：** 这里单独假定 102 是另一条已应用命令，不是交付确认。快照必须继续保存事件 `btc-usdt-1/101/0` 的完整载荷、摘要和未确认状态。恢复后重发同一事件，账户通过消费键与记账同事务返回原结果，不再结转资产。只有交付确认进入撮合日志、被应用，并被新的可信恢复材料覆盖，才可按策略清理该待交付项；网络发送成功或本地标记不够。请求结果、账户消费键保留各有独立契约；若承诺账户 PITR，还须保留归档或共同检查点，不能随在线清理一起删除。若快照只剩全成订单，101 日志又被删掉，这笔成交就失去了可靠交收来源。

## 本题收束

### 机制

- S 是一个已提交且已应用的业务切点，镜像中的订单、请求结果、outbox 与 A 同步冻结；用深拷贝或完整 COW 证明这一点。
- 快照清单封闭引用所有恢复内容；数据持久后发布引用，再与共识库完成可恢复交接，最后才允许压缩。
- 安装替换整份已验证状态，合法后缀从 S+1 续接；压缩只减少恢复所需日志，不撤销历史输出义务。

### 易错边界

- C 不能冒充 S；单独锁一个 Go map、浅拷贝指针或后台读取在线集合，都不构成一致镜像。
- rename 的原子可见性不能替代文件和目录持久化；摘要也不能替代共识历史与版本兼容校验。
- 撮合快照不是账户账本；未确认 outbox、请求去重屏障、审计与灾备材料不能跟着日志前缀一起盲删。

### 反例检验

手工推演“101 成交、账户入账、确认丢失 → 制作 S=102 快照 → 压缩到 102 → 节点重启”。应能重建原请求结果和原事件，重发不重复记账；若清单遗漏 outbox、混入其他切点数据，或发布未持久就清理旧材料，方案不成立。该推演不是已运行的工程测试。
