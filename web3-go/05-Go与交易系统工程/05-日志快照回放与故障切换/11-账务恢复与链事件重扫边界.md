# 大问题 11：账务恢复、链事件重扫与撮合回放能共用一个水位吗？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 权威域 / 因果映射 | 不同系统分别认定自己的事实，靠明确业务关系相连。 | 撮合成交、账户记账、链事件不能凭相同数字声称同一进度。 |
| S / A / C | 撮合快照、已执行、已提交位置。 | 只在同一分片同一合法历史内比较，101 apply 不证明账户已入账。 |
| LSN / WAL | 数据库日志位置，以及数据库用于恢复事务的预写日志。 | 不能和撮合索引、链高度取最小值当全局切点。 |
| PITR / 事务一致切点 | 把数据库恢复到过去位置，并确保相关表同属一个事务状态。 | inbox、预留、账本和余额必须一起恢复，仍可能回退已确认的交收。 |
| 共同恢复清单 / 检查点 | 双方约定可恢复范围及各份材料身份的持久说明。 | 关联撮合快照、账户备份、消费覆盖及最早切点，不只记几个裸数字。 |
| outbox / 归档 / 保留窗口 | 在线交付义务、完整历史备份，以及承诺能回退多远。 | 在线项已确认删除后，窗口内事件仍要能按原载荷重建。 |
| eventID / payloadHash / inbox | 经济事件身份、内容指纹和账户消费事实。 | 用 `btc-usdt-1/101/0` 补缺口，同 ID 同摘要不再入账，异摘要拒绝。 |
| 预留 / 补齐 / 空白投影 | 支付义务的占用、补缺失事务，以及从零重建的独立目标。 | 在已有余额上不能从创世累加全量旧账；预留被回退就先补合法依据。 |
| 恢复代际 / 当前围栏 | 区分本次修复阶段，并重建真实写端拒绝旧发送者的授权。 | PITR 可能连 maxToken 都回退，不能取旧备份最大值自行加一。 |
| 受控修复通道 | 隔离生产后只准授权历史补齐通过的入口。 | 围栏安装不是生产放行；顺序为隔离、围栏、补齐、核对、开放。 |
| 链上充值投影 / 托管成交 | 根据链事件建立的派生状态，以及链下撮合的经济事实。 | 本题额外加入前者作比较，B1 不因此变成 DEX 成交或天然可链上找回。 |
| chainID / blockHash / logIndex | 哪条链、哪个具体区块、区块中哪条事件。 | 配合交易身份定位事件，同高度不同哈希不是同一分支事实。 |
| 父块哈希 / 规范链 / 共同祖先 | 区块前后联系、当前认可分支，以及重组前后的最后共同块。 | 重扫先核验分支，不能只从最大高度向后接。 |
| reorg / 可逆投影 / 再应用 | 链分支变化、可撤销派生状态，以及旧块恢复规范时的合法处理。 | 旧分支逆依赖撤销，新分支顺序重扫；“见过”不等于永远不用再处理。 |
| 批次事务 / 游标 | 一批事件状态、投影变化和扫描进度共同提交。 | 崩溃后可重叠扫描，不把半恢复投影公布为已追平。 |
| 最终性策略 / 补偿分录 | 何时允许链事件变成可交易资产，以及突破假设后的风险处置。 | 深重组不能抹掉已提交成交或最终提现，只能按证据处理敞口和损失。 |

## 把整篇文章压缩成一个故事

B1 已用 30,000 USDT 买入 1 BTC，账户记账并确认后，撮合清理了在线待交付项。后来账户做时间点恢复，退回到预留已建立、成交尚未入账的位置。工程师小秦看到余额、预留、账本和 inbox 内部一致，却不能就接回生产：撮合仍认定两单全成，账户已丢失原消费事实，旧确认不能充当这次恢复的证据。撮合索引 101 和数据库 LSN 更不能拿数字大小直接对齐。

小秦要靠事前共同恢复清单定位备份与事件覆盖，并从保留归档取回原 `btc-usdt-1/101/0`。他先隔离生产和旧发送者，安装由合法接管历史证明的当前围栏，再通过修复通道按依赖补齐缺失事务。已有一致余额不从创世重加一遍，预留若也回退则先补合法来源。核对到目标后，A 可用 20,000 USDT、增加 1 BTC，B 收到 30,000 USDT，才能重新形成持久确认并分阶段开放。

有人提议扫描区块代替归档，小秦拒绝：这笔托管成交不必上链。另加的链上充值投影，要按链身份、块哈希与事件位置查规范分支，找到共同祖先后撤销可逆旧投影、重扫新分支。它不能撤销已提交 B1，也不能收回最终提现；突破确认策略的深重组要走有依据的风险和补偿流程。若成交归档确实没了，正确结论是材料缺失、继续停写，而不是造新 ID 或把原预留解冻掩盖差异。

[返回专题总览](README.md)

**流程位置：**撮合恢复已提交命令、重建交付义务之后，账户数据库恢复与外部事实重建之前。本题接续结果交付问题，重点不是正常运行时如何重试，而是某一权威系统退回历史状态后，其他系统凭什么补齐它。

**统一基线：**沿用总览的三节点 Raft、链下托管现货订单簿。完整 command 经共识提交后，单写者进行唯一的确定性 apply；不另设 command／ResultBatch 两道提交边界。账户独立拥有预留、余额和账本。主例始终是快照 100、命令 101：A 的 B1 用已预留的 30,000 USDT 买入 B 的 1 BTC，与 S1 全额成交，稳定成交 ID 为 `btc-usdt-1/101/0`。

**核心机制：**分清水位的权威域；用共同恢复清单与归档约束历史淘汰；按一致切点补齐缺失事务。第 5—7 层会明确增加“链上充值事件投影”这一比较条件，不把原托管案例替换成 DEX，也不假定撮合成交天然存在于链上。

## 第 1 层：先区分三个权威与各自水位

**面试官：**撮合有日志，账户有数据库，链上也有历史。故障后能不能让它们都退到 100，再统一重放 101？

**面试者：**不能，先问“100 属于哪条历史”。撮合的快照 S=100、已应用位置 A 和提交位置 C，只能在同一分片、同一已验证历史中比较。命令 101 提交后才能确定性 apply，重建 B1 与 S1 的成交及交付义务；它不直接修改账户余额。

账户数据库的 LSN 表示其自身恢复位置，inbox、预留、账本和余额才证明是否交收。即使撮合 A=101，账户仍可能没有入账。链上的高度、blockHash 与 logIndex 又属于另一套规范链坐标。三者不能数值取最小值；应以稳定事件 ID、载荷摘要和已持久确认的因果映射关联，不能制造一个伪全局水位。

## 第 2 层：PITR 的同一事务切点不等于已确认事实没有回退

**面试官：**你说账户要单独看。如果账户已经确认这笔成交，后来做数据库时间点恢复，inbox、账本和余额恢复到同一个切点，是否就安全了？

**面试者：**同切点是必要条件，不是充分条件。先隔离账户写入、交付和提现，再按数据库契约用一致备份及 WAL 恢复到事务一致的 LSN；inbox、预留、账本、余额不能各选一个“差不多”的备份，也不能保留新 inbox 却退回旧余额。

若切点在成交入账前、预留建立后，恢复后仍是 A 预留 30,000 USDT、B 预留 1 BTC，成交消费记录消失；撮合却可能早已全成并收到确认。这说明 PITR 会回退已经确认的账务，不能把预留当可释放余额。内部事务一致只排除了半笔账，尚未解释如何恢复对外承诺和切点之后的合法变动。

## 第 3 层：以共同检查点和归档协议约束 outbox 淘汰

**面试官：**既然确认也会被 PITR 回退，撮合已经按确认删掉 outbox，命令 101 又随快照压缩了，你拿什么补账？

**面试者：**必须事前有双方持久确认的共同恢复契约。清单关联撮合快照及已提交前缀、账户备份及 LSN、已消费事件集合或无缺口范围、允许的最早恢复切点；这些是带身份的因果映射，不是把 C、A 和 LSN 排成大小。

在约定恢复窗口内，101 即使已确认，完整事件及摘要、依赖、历史规则仍须有校验过的归档，或可由受保留的完整历史重建。快照里只有“已交付”标记不够。清理 outbox 和压缩日志都须受该协议约束，并覆盖预留、释放等相关来源。若既无归档又无共同可恢复基线，就停止恢复；不能假设共识会重新长出已淘汰的数据，窗口外恢复也须另行决策。

## 第 4 层：从一致余额补缺口，而不是叠加重放整部旧账

**面试官：**归档齐全后，是不是把所有旧事件重投一遍就行？已有余额怎么办，之前收到过的确认还算数吗？

**面试者：**先隔离生产写入并安装当前围栏，确定恢复代际和目标清单；随后只允许受控修复通道按原事件 ID 补齐，旧确认不能充当本次证据。保留切点内一致的余额与 inbox，按依赖恢复到目标的缺失事务；若预留也被回退，先恢复其合法依据。充值、提现、释放等来源同样要覆盖，完成同切点核对前不开放生产。

对 `btc-usdt-1/101/0`，账户在同一事务内检查唯一键及摘要、校验双方预留、结转 1 BTC 与 30,000 USDT 并写账本、inbox；重复投递返回原结果，异摘要拒绝。已有余额上从创世再累加全量旧账会重复计资；从零重建必须另建完整空白投影。不可逆外部操作只核实事实，不因数据库回退重新执行；补齐后再形成新的持久确认。

## 第 5 层：增加链上投影条件，仍不把托管成交变成链上成交

**面试官：**你强调外部事实不能重做，那直接扫描区块链找回缺失事件，能不能替代上述成交归档？

**面试者：**不能。基线里的 B1 是链下托管撮合，命令 101 和账户结转并不必然上链，扫描区块找不回撮合交付载荷。现在明确改变条件：另加一条支持事件日志的链上充值投影，仅比较它的恢复方法；原来的 BTC/USDT 撮合及预留关系不变，也不声称 BTC 原生交易会产生 EVM 日志。

新增投影按 chainID、blockHash、交易身份及 logIndex 标识事件，保存高度、父块哈希、过滤范围和规则版本。高度只方便定位，blockHash 才区分分支；logIndex 要和所属区块一起解释。这些坐标均不能与撮合 C/A 或数据库 LSN 数值比较，只能通过明确的充值业务身份关联。

## 第 6 层：链重扫要重建规范投影，而不只是去重插入日志

**面试官：**既然保存了 blockHash，重启后从最后高度继续扫描就够了吗？如果最后几块已经重组，旧充值还在投影里呢？

**面试者：**不够，要先验证保存的块哈希及父子关系是否仍属规范链，找到共同祖先。对祖先之后的孤块，按依赖逆序撤销可逆投影、标记旧分支事件，再按新规范分支顺序重扫；跨多个事务处理时暴露“恢复中”，不能提前公布追平。

每个处理批次都把事件状态、投影变化和游标放在同一数据库事务，崩溃后重叠扫描仍按原事件身份幂等。同高不同哈希不能覆盖成同一事件；曾撤销的块重新成为规范块时，要由投影状态机合法再应用，不能被简单的“已见过”跳过。这套恢复只证明链事件投影正确，尚不授权改变已经裁决的撮合或最终转账。

## 第 7 层：撤销充值投影不等于撤销撮合或最终提现

**面试官：**你说只能撤销可逆投影。如果充值已记成可用，用户又做成了 B1，甚至已经最终提现，重组后反向扣回来不就平了吗？

**面试者：**不能把余额减回去冒充撤销事实。链事件尚待确认时可撤销投影；若要转成可交易余额，必须先满足明确的链确认策略，并通过账户事务完成唯一消费、状态迁移和资产记账，事后对账不能替代这道原子边界。

若极端重组穿透该策略，命令 101 已提交的 B1 成交不会自动失效，已经最终执行的提现也不能靠本地回滚收回。应按风险规则限制新增支出、核实敞口，以有原因和审批依据的补偿分录或损失处理承接，不篡改旧成交。普通撤销与突破最终性假设的事故是两类流程；前者不能被宣传成后者的无损恢复方案。

## 第 8 层：用恢复代际、围栏与业务证据共同关闭恢复

**面试官：**PITR 连围栏 token 都可能回退，旧交付器也还活着。安装新围栏后能先接生产，再慢慢补账和核对链投影吗？

**面试者：**不能。严格顺序是隔离生产→安装围栏→受控补齐→同切点核对→开放生产。由存活 Raft 历史提交新接管屏障，通过认证路径安装到账户；围栏更新和消费锁定同一记录、事务校验 token，不能从旧备份最大值自行加一。安装后只准修复通道携当前 token、按原事件 ID 补齐，不等于生产获准写入。

按共同清单补齐后，在目标切点核对事件覆盖、预留、归属及外部事实。B1 仅消费一次：A 的 USDT 可用 20,000、预留 0、BTC 增加 1；B 的 BTC 预留归零、USDT 增加 30,000。链投影另核规范哈希；证据齐全才分阶段开放，缺口未解则停写。

## 本题收束

### 讲透的机制

- **权威域不同，坐标不可混算。**撮合 C/A 证明已提交、已执行到哪里；账户 LSN 证明数据库恢复位置；链坐标证明哪条分支上的哪个事件。跨域关联靠稳定业务身份、摘要及持久恢复清单。
- **PITR 与历史淘汰必须事前协商。**inbox、账本、余额和预留同切点恢复仍可能回退已确认事实。双方共同检查点、恢复窗口及完整归档，是允许清理历史的前提，而不是故障后的临时补丁。
- **补缺口与重建投影是两种动作。**已有余额只接续缺失事务；从零建投影必须使用空白目标和完整来源。链重组只撤销可逆投影，撮合裁决与最终提现另有不可逆边界。

### 最容易答错的边界

- 账户已确认不代表其任意 PITR 切点都保留该确认；撮合已删除 outbox 后，也不能只靠“会重试”恢复。
- 撮合回放按完整 command 的已提交顺序确定性 apply，不借恢复之名引入第二道结果提交，也不在 apply 中直接扣账户资金。
- 总资产守恒、监控和事后对账都不是充分证明；重复消费、预留释放、分录和余额变化必须先被事务及唯一约束限制。
- 跨账户分片、跨撮合分片原子恢复不在本题基线内；新增这些条件时，需要重新设计共同切点和协调协议。

### 一个反例

命令 101 已提交并完成账户记账，撮合随后删除交付载荷、压缩旧日志；账户再恢复到入账前的备份。此时两边各自都可能“恢复成功”，但成交已经全成、账务却缺失，且没有材料补齐。正确结论是恢复契约不完整，应保持停写并升级处置，而不是把原预留释放、重建一个新成交 ID，或在已有余额上从创世重放全部旧账。
