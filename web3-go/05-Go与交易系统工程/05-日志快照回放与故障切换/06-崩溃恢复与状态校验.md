# 大问题 6：从快照恢复到可服务，要经过哪些可信恢复与状态校验步骤？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 隔离启动 / 状态根 | 先关业务写入与交付，在私有完整状态里重建。 | 恢复到一半的订单、去重与 outbox 不能被外部读取或扣款。 |
| 可信快照 / S | 符合持久发布与协议契约、包含某个完整执行切点的镜像。 | 快照 100 包含 S1，不能随便加载临时目录或“最新文件”。 |
| manifest / schema / 规则执行器 | 文件清单、数据格式，以及可执行历史业务规则的实现。 | 分片、水位、任期、长度、摘要、版本都要匹配；不兼容就停。 |
| C / D / A | 协议提交、本地持久尾部、业务执行各自的位置。 | D=103 或保存的旧 A 不能单独证明恢复应执行到哪里。 |
| committed entries / Raft | 协议交付的已提交条目，以及负责确认合法历史的共识机制。 | 不把未知尾部升格为成交，多数不足时不能自行猜提交位置。 |
| T / 固定恢复目标 | 本轮检查决定追到的明确提交切点。 | 先证明 A 到达 T；之后的新提交另行追赶，不能拿移动目标冒充完成。 |
| A+1 / 连续前缀 | 下一步只能接着上一位置，不能跳过中间条目。 | 100 后缺 101 只有 102 时停止补齐，不用 103 填空。 |
| no-op / 配置项 | 不直接下单的协议空操作或成员控制条目。 | 按库契约处理相关位置，不能只筛买单却声称历史连续。 |
| 原子应用 / 原子发布 | 一条命令的全部变化构造完整后，一起对观察者可见。 | 订单、成交、原请求结果、outbox 与 A 不能各自先成功。 |
| 逻辑 hash / 文件 hash | 规范化业务内容的摘要，以及文件字节摘要。 | 同分片、同历史、同 T 才可比逻辑状态；字节正确不等于业务正确。 |
| FIFO / 数量不变量 | 同价订单先后，以及数量始终应满足的关系。 | 原始量等于已成交、已撤与剩余之和；摘要不能排序抹掉队列差异。 |
| eventID / eventSeq | 一笔成交的身份，以及账户交付批次的连续进度。 | 原成交为 `btc-usdt-1/101/0`，交付水位不能用最大日志索引代替。 |
| 账户消费事实 / 交付确认 | 账户原事务是否已记账，以及撮合可靠记录的确认。 | 两单全成而预留尚在可能只是落后；先查原事件，不能回滚成交。 |
| 线性读屏障 / 陈旧查询 | 读到合法进度的约束，以及只展示较旧水位的读法。 | 本地看似追平不等于可答“最新”，落后视图要明确非权威。 |
| 接管屏障 / 接收端围栏 | 新主的有序接管凭据，以及真实写端拒绝旧授权的约束。 | 应用追平与外部发送分别验收，围栏未确认不开放该交付路径。 |
| 分片世代 / 分阶段开放 | 不可复用的身份空间，以及按能力逐项放行。 | 灾难重建不能重置索引碰撞旧 ID；缺口、校验失败必须阻断。 |

## 把整篇文章压缩成一个故事

撮合节点崩溃后，工程师小许看到快照 100 和磁盘尾部 103，不能直接全部加载执行。他先关闭接单和结果交付，核验快照清单、分片、任期、摘要及历史规则，再由 Raft 确认可用提交前缀。若本轮目标定为已提交的 102，却发现本地缺少 101，就要补齐或安装可信快照；103 即使文件完整，也不能拿来顶缺口，更不能未经确认就执行。

补齐后，命令 101 从包含 S1 的旧状态重建 B1 买入 1 BTC、支付 30,000 USDT 的裁决。订单全成、原请求结果、成交 `btc-usdt-1/101/0`、待交付义务与 A 必须完整构造后共同可见。若只改完订单就出错，小许废弃不可信恢复状态，不能捕获错误后继续推进。到达目标还要比较同水位逻辑摘要、队列次序和数量关系，不能因为 A=102 或文件 hash 正确就放行。

账户若仍显示 30,000 USDT 预留，小许先按原事件查消费事实：没入账就重送，已入账而回执丢失就取回原结果，再补可靠确认，绝不在回放中再扣款或先解冻。完整状态核验通过后才发布；权威查询要有读屏障，新主接单要有合法接管凭据，外部交付要等接收端围栏。各能力各自过门槛，进程活着、内存追平和交易交收完成不是同一结论。

**流程位置与核心机制：** 位于进程重启、快照安装之后到重新开放服务之前。沿“隔离启动 → 验证恢复基线 → 共识确认提交前缀 → 连续回放 → 同水位校验 → 分能力开放”追问。本题使用上一题的快照发布契约，不另造选举算法，也不把撮合恢复当成账户数据库恢复。

**必要前提：** 沿用总览的三节点 Raft 与单写者状态机。快照 S=100 含卖单 S1；命令 101 是 A 的买单 B1，预留资格 R-A，执行后两单各成交 1 BTC，金额 30,000 USDT。已提交 command 经确定性 apply 生成稳定结果和 outbox，不二次提交结果。分片身份不可复用，重启与切主不能重置它或更换原成交 ID。以下只做教学推演，不声称运行过恢复演练。

## 第 1 层：恢复为什么不是加载快照再遍历磁盘日志？

**面试官：** 一个内存撮合节点崩溃后，你怎样从快照恢复到能服务？为什么不能加载快照，再把磁盘里的日志全部执行？

**面试者：** 我会先隔离启动，关闭业务写入和结果交付，避免恢复中的半成品成为权威状态。随后验证快照及版本，加载到隔离状态根；由 Raft 实现恢复协议状态，确认可用提交前缀，再从 S+1 连续应用到一个明确目标 T。磁盘尾部可能包含尚未提交、以后会被替换的命令，不能全执行。追平后还要校验水位、数量不变量、请求结果与交付义务，最后按查询、下单和外部交付各自门槛开放。恢复到 A=101 只说明撮合已执行，不说明账户已入账；快照是恢复基线，不是业务全链路完成证明。

## 第 2 层：什么样的快照才是可信基线？

**面试官：** 你先验证快照，但磁盘上可能同时有新清单、旧文件和残留临时目录。具体怎样判断哪份可以加载？

**面试者：** 我只接受符合发布协议的完整清单，逐项核对分片身份、S、对应任期、生效配置、文件长度和内容摘要，确认没有缺件或跨代拼接。再检查 schema、编码格式和历史规则执行器；规则不兼容就停止，不能用当前规则替算旧订单。文件 hash 只能发现字节不一致，不能证明来源历史已提交，所以快照元数据还要与共识库的恢复契约衔接。旧快照也不是天然可回退，必须仍有可验证、连续的后续日志。临时文件或“文件名最新”的目录都不能直接提升为可信状态，更不能加载失败就清空盘口继续服务。

## 第 3 层：提交位置 C 应该由谁恢复？

**面试官：** 快照验证通过，S=100，而磁盘日志写到了 D=103。怎样决定恢复到哪里，能否取磁盘末尾或保存的 appliedIndex 当 C？

**面试者：** 两者都不能单独证明 C。S=100 证明这份合法快照已包含提交且应用的前缀；后续哪些条目已提交，要由所选 Raft 实现按持久协议状态恢复，并在必要时与集群协调确认。库若持久化提交信息，也只能按其契约使用，不能由业务代码猜一个最大值。D=103 可能含未提交分支，保存的 A 也不能替代日志与共识元数据。恢复器只接收协议明确交付的 committed entries。若多数不可用且缺少必要确认，不能把未知尾部升格为成交；可做受限本地重建，但不因此开放新提交或承诺线性查询。

## 第 4 层：确认前缀后怎样处理缺口与未提交尾部？

**面试官：** 共识确认目标 T=102 已提交，但本地在 S=100 后只读到 102，没有 101；103 也在盘上，回放该怎么走？

**面试者：** 我要求每一步的索引严格等于当前 A+1，并检查记录边界、校验和及与协议历史的衔接。缺少 101 就停止本地恢复，按库协议向健康副本补齐或重新安装可信快照，不能跳到 102，更不能把 103 填进缺口。103 尚未被确认提交时不交给业务执行，保留还是覆盖由 Raft 决定。协议 no-op、成员配置项等也要按库契约处理并推进相应位置，不能只筛出下单日志却假称前缀连续。T 是本轮校验的固定目标，后续 C 继续增加可以另行追赶，不能把一个移动的最大值当作已经完成的证据。

## 第 5 层：回放中途失败怎样避免暴露半条成交？

**面试官：** 101 已补齐，但回放时刚把 B1 标成全成，尚未写去重表与 outbox 就发生错误。怎样防止恢复出半笔业务？

**面试者：** 我会在隔离状态中构造单条命令的完整变更，将订单、成交、请求摘要与原结果、outbox 和 A 作为同一可见边界发布。实现可以使用暂存变更或不可变状态根；不能先推进 A 再补其他对象。构造失败就丢弃本次变更，若原地状态已不可证明完整，则废弃整个恢复实例，从可信基线重新构建，而不是捕获异常后接着跑。回放只产生确定性状态，不直接扣账户余额或发送消息。若进程再次崩溃，仍从可信 S 和已提交日志重建同一成交 ID，不靠一次额外 result 提交弥补原子性。

## 第 6 层：追平后怎样发现“水位正确、内容错误”？

**面试官：** 现在隔离状态宣称 A=T=102，如何发现订单队列或 outbox 实际有错？只比较 A 或整个文件 hash 足够吗？

**面试者：** 不够。我会在同一分片、同一历史、同一目标 T 比较逻辑状态：按规范编码订单、保留同价队列次序、请求摘要与结果、交付义务和确认状态，再计算逻辑 hash；不同 T 的摘要不能直接比较。文件 hash 主要检验传输与存储，逻辑 hash 用来排除编码布局等非业务差异。还要检查原始量等于成交、已撤和剩余之和，成交双方一致，原结果能找到原事件，未确认输出没有缺载荷。交付水位若用 eventSeq，必须是连续前缀，不是最大日志索引。多个副本相同也可能共同有缺陷，所以业务不变量不能省。

## 第 7 层：撮合校验通过，为什么账户仍可能没有完成？

**面试官：** 你在 T 看见 B1、S1 全成和原 outbox，但账户显示 R-A 仍预留 30,000 USDT。这是恢复失败，要回滚成交吗？

**面试者：** 不能直接判错或回滚。撮合裁决与账户交收有不同完成边界；先按稳定事件 `btc-usdt-1/101/0` 查询账户消费事实。若尚未消费，由恢复后的获准交付器重发原载荷；若已入账但确认丢失，账户以消费键、载荷摘要和记账同事务返回原结果，再把交付确认写回撮合日志。不能因为账户暂时落后就撤销已提交成交，也不能提前释放预留。撮合只核对资格引用和交付证据，余额仍归账户服务。正常未完成义务可以继续收敛，但同事件异载荷、预留缺失等矛盾必须阻断相关交付并进入异常处置。

## 第 8 层：怎样把校验结论变成可执行的开放门槛？

**面试官：** 既然允许账户暂时落后，最后依据什么开放查询、下单和交付，避免“进程活着就算恢复成功”？

**面试者：** 我会分别设置门槛：快照可信、版本可执行、已提交前缀连续、A 到达本轮目标 T、同水位校验通过后，才发布完整状态根。线性查询还须取得合法读屏障并等 A 追到该位置；本地落后查询只能显式返回水位和非权威语义。新主接单还需有效领导权、提交接管屏障并应用追平；外部交付另等账户接收端围栏安装确认，保留旧事件身份重送。若追赶落后于新增流量，可限流或保持停写。缺日志、版本不兼容、逻辑校验失败不能降级为“带病成功”；账户积压则按风险和容量限制分阶段开放。

## 本题收束

### 机制

- 恢复从可信快照开始，由共识确定可用提交前缀，严格连续应用到固定目标 T，不从 D 或旧 A 猜 C。
- 在隔离状态中恢复，单条命令的订单、原结果、outbox 和 A 原子可见；校验通过后才发布完整状态。
- 同水位逻辑 hash 与业务不变量互补，服务开放还依赖读屏障、合法写权及接收端围栏。

### 易错边界

- hash 正确不等于历史已提交；A 达到目标不等于内容正确；撮合追平不等于账户完成。
- 正常待交收可按原事件继续履行，不能恢复时重新撮合、重扣余额或按超时释放预留。
- 分片身份不可复用，灾难重建若会重置索引，必须按总览采用新世代及受控映射，不能碰撞旧经济身份。

### 反例检验

手工给出可信 S=100、已提交 101、未提交尾部 102，并让账户在确认丢失前已消费 101。恢复应只重建同一个成交和待确认义务，不能执行未知提交状态的 102；重送 101 不重复记账。另将 101 删除或换成不支持的 schema，应停止而不是跳过。以上是预期检验，不是已运行的工程测试。
