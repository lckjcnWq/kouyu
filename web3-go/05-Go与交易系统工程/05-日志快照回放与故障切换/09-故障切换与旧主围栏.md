# 大问题 9：怎样切主并阻止旧主继续写？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 心跳超时 / 路由切换 | 怀疑节点失联，以及把新请求改送别处。 | 两者都不能证明旧进程已死，也不直接授予新主写权。 |
| 合法选举 / up-to-date | 按持久投票和日志新旧规则取得多数授权。 | 三节点多数为两个，先比末日志任期再比索引，不是谁响应快谁接管。 |
| 共识主权 / 外部发送授权 | 推动新命令提交的资格，以及让真实外部写端接受请求的资格。 | Raft 能限制新裁决，不能杀死旧进程或撤回旧网络包。 |
| 接管屏障 B=110 | 本变体中新主合法提交的本任期接管控制位置。 | B 是屏障，不是买单 B1；它确认此前历史，并提供应用追平目标。 |
| D / commitIndex / A | 本地持久尾部、协议提交位置和业务已执行位置。 | 盘上有 101 或旧内存水位都不是开放凭据，须恢复并追到屏障。 |
| token 90 / 110 | 旧、新发送者各自持有的授权编号。 | 来自各自已提交接管屏障索引，不是任期、墙钟或随手填的大数。 |
| sourceShard / maxToken | 外部接收端认定的来源分片，以及该分片当前持久授权。 | 分片须预注册且身份不可复用，数据包不能自行抬高 maxToken。 |
| 认证控制路径 / 幂等安装 | 经验证接管权的授权更新入口，以及同 token 可重复确认。 | 安装超时按原 token 查证或重装；发现更大值就停止本次接管。 |
| 围栏行 / 同事务行锁 | 安装授权与每次记账都锁同一记录直到事务结束。 | 不能先从缓存读 token，再另开事务写余额，防止旧写穿透。 |
| token == maxToken | 数据写入必须持有接收端当前授权。 | 安装 110 后 90 一律拒绝，即使该事件已在 inbox 中。 |
| 线性化边界 | 并发操作在同一约束下能明确排出先后。 | 旧合法事务先提交则属于安装前事实；安装先提交则旧事务必须拒绝。 |
| eventID / payloadHash / inbox | 经济身份、载荷指纹，以及账户已消费事实。 | token 不进入经济去重键；新主换授权仍重送 `btc-usdt-1/101/0`。 |
| outbox / 交付确认命令 | 尚欠交付的结果，以及把持久记账确认写回撮合的步骤。 | 发送失败不删除义务，确认须提交并应用后才逻辑完成。 |
| 多下游部分安装 / 按路径开放 | 有的接收端已更新、有的未更新时分别控制能力。 | 不回退已装围栏，某路径的全部必要下游确认后才开放该写路径。 |
| 最终副作用边界 / 写网关 | 真正落账或执行外部操作的位置，以及其前置代理。 | 网关只检查入口不够，还要挡住发往最终写端的旧在途请求。 |
| ReadIndex / 读屏障 / 水位 | 验证合法读取位置的机制，以及结果进度标签。 | 当选或追平一次不包办后续最新查询；失去主权就停止新提案与发送。 |

## 把整篇文章压缩成一个故事

命令 101 已让 B1 与 S1 成交 1 BTC，账户是否完成 30,000 USDT 交收还不明确，旧主 N1 却心跳超时。工程师小邓不能只切流量给 N2，因为 N1 可能只是暂停，手里仍有旧连接与迟到消息。N2 先合法当选，再提交本任期接管屏障；在本文变体中屏障 B=110，它按原历史恢复成交、去重与待交付结果，并应用追到 110，才完成撮合状态这一关。

外部写权还要另过一关：旧 token 是 90，新主通过认证控制路径把 110 安装到账户。安装和每笔记账都锁同一围栏行，在事务内校验当前 token，直到提交才放锁。若旧合法事务先持锁提交，它属于安装前的真实入账；若安装先完成，90 必须被拒绝，不能靠缓存检查漏过去。安装回包丢了就用 110 查证或幂等重装，不回退到 90，更不能随便造个 999 提权。

围栏切换只换发送资格，不换成交身份。N2 用 110 重送原 `btc-usdt-1/101/0` 与原载荷，账户再靠 inbox 和记账同事务避免第二次扣款；任何 token 都不能把未提交尾部变成合法成交。相关下游未全部确认的写路径继续停用，最终写端不支持围栏就保守停写。选主、状态追平与真实写端拒旧，三件事都成立，才能说这条业务路径安全接管，而不只是新主看起来在线。

[返回专题总览](README.md)

**流程位置与核心机制：** 位于“旧主失联 → 合法选举 → 提交接管屏障 → 恢复追平 → 下游围栏 → 分阶段开放”。本题重点是新主何时有资格服务、旧主的外部副作用怎样被拒绝；不把故障检测、共识主权和账户写入授权混为一件事。

**必要前提：**

- 沿用总览的链下托管现货 BTC/USDT、价格时间优先、三个投票节点和成熟 Raft 实现；多数为两个，非拜占庭模型，多数不可用时停止新提交。
- 快照 `S=100` 含卖单 S1：卖 1 BTC，价格 30,000；命令 101 是 A 的买单 B1。A 以独立资格 `R-A` 预留 30,000 USDT，卖方 B 已为 S1 预留 1 BTC。以下以 101 已提交、账户交收尚不明确时切主为主线。
- 本专题采用 command-only 确定性状态机：命令提交后，apply 将订单、成交、请求去重、逻辑 outbox 和执行水位同一原子发布；不是既有撮合专题的命令、结果双日志再次共识。撮合不拥有余额，资金变化由账户事务完成。

## 第 1 层：心跳超时只能触发怀疑，不能授予主权

**面试官：** 三节点中的旧主 N1 心跳超时，怎样切主并阻止它继续写？是不是把流量切到 N2 就行？

**面试者：** 不行。心跳超时只说明怀疑 N1，不证明它已死亡，也不直接授予 N2 写权。N2 必须依 Raft 的任期、每任期投票约束和日志 up-to-date 规则参加选举，取得合法多数授权；日志新旧比较最后日志任期，再比较索引，不是谁响应快谁当主。一旦新任期合法接管，N1 即使仍在运行，也不能继续合法提交新命令。我的接管顺序是合法当选、提交本任期接管屏障、应用追平并核验，再到外部写端安装围栏。Raft 主权和外部发送授权是两道门，路由切换或当选通知都不能直接开放业务写入。

## 第 2 层：用本任期屏障确认历史，再把应用追到屏障

**面试官：** 你说合法当选后还不能开放。如果 N2 磁盘日志已经超过 101，内存里也有 commitIndex，为什么还要接管屏障？

**面试者：** 磁盘末位置只证明本地有记录，重启前内存 commitIndex 也不能代替协议恢复。另设教学变体：101 后还有若干日志项，新主通过既有实现支持的接管控制命令提交本任期屏障 `B=110`，它不是客户端买单 B1。Raft 按本任期提交规则确认屏障及此前历史前缀已提交，再从可信快照 100 按序应用；101 重建原成交、去重结果和待交付事实，执行至少追到 110。还要核验订单数量、规则兼容和 outbox 完整性，缺口或错误就停。不能凭磁盘尾或一个本地变量开放，更不能把未提交尾部当作成交。

## 第 3 层：应用追平不等于外部旧写已被隔离

**面试官：** 你已经应用到屏障 110，也核验了状态。旧主又不能提交新命令，为什么还需要账户端围栏？

**面试者：** Raft 不会杀死旧进程，也不会撤回已经发出的网络包；旧主失权后，历史成交包仍可能到达账户。账户因此按预注册的 `sourceShard` 保存 `maxToken`，每次写入都核验授权。新 token 严格取已提交接管屏障的日志索引，本变体为 110；旧 token 假设来自此前已提交的屏障 90。它不是 term、随机数或墙钟。递增性限定在不可复用的分片身份内：灾备若重置日志索引，必须另建分片世代并受控迁移原交付义务，不能沿用旧 shardID。接收端持久围栏才约束迟到副作用，发送方自认退位不是隔离证明。

## 第 4 层：大 token 不是数据包自行提权的通行证

**面试官：** 你让账户保存 maxToken，那旧主或者错误客户端给成交包填一个 999，就能抬高围栏并抢回写权吗？

**面试者：** 不能。普通数据路径只比较 token，绝不能用包里的大数更新 maxToken。安装必须走认证的控制路径，核验预注册分片映射、申请者接管资格，以及可信共识接口确认的接管屏障已提交；节点自报任期、地址或本地有一条日志都不够。安装事务锁定该 sourceShard 的围栏行，只有验证通过的更大 token 才能推进持久值；同 token 可幂等确认，更小值不得覆盖。身份认证也不能替代接管权验证。但只给安装操作加锁仍不够，账户记账必须参与同一个串行化边界，否则旧请求仍可能越过围栏。

## 第 5 层：安装和记账必须锁同一行直到事务提交

**面试官：** 你说要共享串行化边界。如果旧事务先从缓存读到 90，随后安装事务提交 110，旧事务再异步更新余额，可以吗？

**面试者：** 不可以，缓存检查与实际写入之间存在穿透窗口。每笔记账事务先锁同一 sourceShard 围栏行，在事务内要求 `token == maxToken`，再做 inbox 去重；新事件还要校验预留、写复式账本、更新余额并持久保存 inbox，全部同事务提交，锁一直持有到结束。安装事务也锁这行。对于原已提交的合法事件，若旧事务先持锁并提交，它就在安装前完成，属于真实入账事实；若安装先提交，旧事务随后读到 110，携带 90 必须拒绝。这样两类事务才能串行线性化，不能先读围栏、释放锁，再到另一个事务记账。

## 第 6 层：安装响应丢失与部分成功不能靠猜测开放

**面试官：** 你把安装提交作为切换点。假如账户已经提交 110 但响应丢失，另一个必要下游还停在 90，新主该回滚围栏还是先开放？

**面试者：** 都不能。安装超时表示结果不明，新主通过认证控制路径用同 token 幂等重装，或查询持久值确认；等于 110 可以确认安装，遇到更大 token 说明已被后任取代，必须停止本次接管，不能再编一个更大数争抢。不同下游的安装不承诺原子完成，也不把已成功的围栏回退到 90。新主必须等某条写路径涉及的全部相关下游都确认安装，才能开放该路径；缺一个就保持相应能力停写。其他已满足独立依赖的能力可分阶段开放，但必须明确降级范围，不能用单个本地 ready 标志冒充全链路接管成功。

## 第 7 层：安装只切换发送授权，不改变成交事实

**面试官：** 你允许不同下游暂时处在不同围栏值。旧主拿 90 继续发包，安装前可以入账是否安全？安装后被拒的历史合法包又由谁补交？

**面试者：** 安装前旧包只能引用原已提交命令产生的真实结果；握有旧 token 也绝不允许发送未提交尾部的“预期成交”。符合这一条件的旧包在围栏仍为 90 时可能正常入账。安装 110 后，旧 token 即使携带合法历史事件也拒绝，不因 inbox 已存在就绕过围栏。交付义务由新主接续：从快照与已提交回放恢复 outbox，用新 token 110 重送原 `eventID=btc-usdt-1/101/0`、原 payload 和摘要。这个 ID 来自不可复用 shardID、日志索引、批内序号；切主只能换授权封套，不能重造经济身份或改写成交条款。

## 第 8 层：原事件重送靠经济幂等，不把追平当交收

**面试官：** 你说新主用原 ID 重送。如果账户早已入账，只是确认丢失，换成 token 110 会不会再扣一次？应用追到 110 能否直接回复交易全部完成？

**面试者：** 不能重复扣，也不能凭应用水位宣称交收完成。账户先在事务内通过 110 的围栏检查，再以 `(sourceShard,eventID)` 查 inbox；经济去重键不包含 token 或 term。同 ID 同摘要返回原记账结果，异摘要拒绝并报警。若尚未入账，才校验预留并原子完成资产结转、账本及 inbox。新主取得确认后，还须把确认命令提交回撮合日志并按序应用，才能逻辑清除交付义务；确认丢失就保留并重试。撮合已全成而账户尚保留预留是允许暂态，查询和回报要声明各自水位，不能因撮合追平就释放已成交资金。

## 第 9 层：最终写端不支持围栏，就不能宣称旧写已隔离

**面试官：** 你前面依赖账户事务检查围栏。如果某个必要下游只有普通 HTTP 写接口，不能事务核验 token，改用 Redis 锁、断旧主网络或者加一层网关够不够？

**面试者：** 这些动作不能直接等同绝对隔离。Redis 锁会过期，进程可能暂停后恢复，断网或 DNS 切换也不能撤回在途请求。可选替代是认证、持久化且幂等的写网关，但它必须把围栏落实到真正的副作用边界：不仅入口拒绝旧 token，网关到最终写端也必须有有效围栏，防止旧在途写稍后落地。只给网关入口加检查、后端仍无条件接受旧请求，并没有闭合保证。如果最终写端无法兑现这种约束，就保守暂停相关写能力或更换接口，明确不具备安全自动接管条件，不能拿探活、锁租期或路由变更充当证明。

## 第 10 层：开放资格要持续成立，查询也必须声明一致性

**面试官：** 你选择暂停没有最终围栏的路径。对于已经恢复的路径，如果接管者随后又失联，或者有人只要求“先恢复查询和回报”，开放门槛怎么持续执行？

**面试者：** 接管门槛不是一次启动检查。发现失去合法主权就停止新提案和发送；后任仍须提交自己的本任期屏障、应用追平、核验状态并完成相关下游安装，迟到旧包最终靠更高围栏拒绝，不能依赖退位通知。线性一致查询还要走实现支持的合法读屏障，例如 ReadIndex，并应用到对应水位，不是内存看似追平就能答最新。允许先开放的陈旧查询或回报必须标注分片、撮合执行水位及账户确认进度；账务未知就明确未知。只有协议主权、应用状态和该路径全部接收端授权均满足，才恢复相应写能力，多数不可用仍停止新提交。

## 本题收束

- **机制：** 故障检测只产生怀疑；合法选举给出共识主权，本任期已提交屏障确认历史前缀，应用追到屏障并核验恢复状态。以该屏障索引安装下游围栏，安装与每笔记账锁同一围栏行、同事务裁决；相关安装全部确认后，按能力开放。
- **易错边界：** 当选不等于可服务，磁盘末位置和内存 commitIndex 不等于接管凭据；Raft 失权不等于旧网络包消失。token 只能由验证接管权的控制路径安装，不能由数据包自行抬高；它也不是经济去重键。跨下游安装没有原子承诺，撮合执行水位不等于账户交收水位。
- **交付不变量：** 任何 token 都不能使未提交命令合法化。安装前可入账的旧消息只能是真实已提交事实；安装后旧 token 一律拒绝，合法欠交付结果由新主使用新 token、原 eventID 和原 payload 接续，不能因发送失败删除义务。
- **反例推演：** 让旧事务在事务外读到缓存 token 90 后暂停，接着完成 110 的安装并开放新主，再恢复旧事务写余额。如果旧写仍能提交，就证明检查与实际写入不在同一线性化边界。合格方案必须表现为：旧事务先持同一行锁提交，则安装随后发生；安装先提交，则旧事务拒绝。若换 token 顺便换 eventID，也已经破坏经济去重，即使某次恰好没重复扣款也不能算正确。

以上是教学模型和故障时序推演，不代表真实生产经历、实测切换时长或已验证的运行结果。
