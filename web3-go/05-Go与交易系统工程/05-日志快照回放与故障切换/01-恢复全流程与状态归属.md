# 大问题 1：一笔交易在撮合进程崩溃后怎样继续完成？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| BTC/USDT / 托管现货 | 平台账户之间交换 BTC 与 USDT，不是链上合约即时结算。 | B1 买 1 BTC，成交金额 30,000 USDT，资产由账户服务结转。 |
| B1 / S1 / R-A | 买单、已有卖单，以及买单使用的资金资格。 | 卖单来自快照 100，买方的 30,000 USDT 预留不会随调用超时消失。 |
| 状态归属 | 谁负责认定哪种事实、允许修改哪类数据。 | 撮合决定订单成交，账户决定余额与账本，页面只是展示进度。 |
| 已提交前缀 / committed command | 已经由协议确定、后续合法主必须继承的一段连续命令。 | 只有这段历史能进入撮合执行，不能把盘上所有尾记录都算进去。 |
| 快照 100 / 命令 101 | 可信的旧状态与之后需要继续处理的原输入。 | 恢复是接着履行原义务，不是补偿性地再下一张新买单。 |
| C / A | 协议确认提交到哪里，以及业务实际执行到哪里。 | C 包含 101 后，仍须等 A 覆盖它才有确定订单结果。 |
| 确定性回放 | 同样初始状态、顺序和规则必然重建同样结果。 | 原成交身份和载荷不因重启、切主改变。 |
| requestKey / payloadHash | 原意图编号和业务内容摘要。 | 用 `A/place/r1` 查证或重试，同键异内容不能冒用原结果。 |
| 撤销屏障 | 把不再允许旧资格接纳的决定排入权威顺序。 | 先挡住迟到命令，账户才有依据释放未使用预留；超时不具备此效果。 |
| eventID / 待交付义务 | 原成交的稳定身份，以及还欠账户的一项工作。 | `btc-usdt-1/101/0` 必须能从快照或回放找回，不随发送失败删除。 |
| 至少一次 / 唯一消费键 | 允许重复发送，但接收端识别同一经济事件。 | 来源分片与事件 ID 唯一，摘要、资产变化和消费结果同事务。 |
| 交付确认命令 | 把账户已持久记账的确认写回撮合的有序历史。 | “发送过”或内存里标完成不够，确认也要可恢复。 |
| 原子发布 / 不可变视图 | 完整状态一次对外可见，之后不被后台偷偷修改。 | 恢复半成品不能让查询、行情或账户消费者直接读取。 |
| 线性读屏障 / 水位 | 验证当前读权限与可读取位置的机制，以及数据进度标签。 | 落后副本查无订单不能证明不存在；撮合、行情、账务各有进度。 |
| 接管屏障 / 围栏 token | 新主的可验证接管位置，以及真实写端据此核验的授权。 | 安装新 token 后账户拒绝旧 token；发送授权不等于经济去重身份。 |
| 恢复验收 | 用订单、事件、账本及交付证据确认业务闭环。 | 进程监听端口不算完成；A 应可用 20,000 USDT 并增加 1 BTC。 |

## 把整篇文章压缩成一个故事

A 为买单 B1 预留了 30,000 USDT，打算买下 S1 的 1 BTC，撮合进程却在处理命令 101 时退出。工程师小林没有让客户重新下单，而是先隔离写入，从快照 100 恢复，再让共识协议确认哪些命令确已提交。若 101 只是磁盘上的未知尾部，就不能先造一笔成交；客户超时也不能据此释放 R-A，否则迟到命令可能拿已经挪作他用的钱成交。

当协议确认 101 属于提交前缀，小林按原顺序和规则重建两单全成、原请求结果与成交 `btc-usdt-1/101/0`。此时账户仍显示预留，可以是交收落后的暂态。交付器重送原事件，账户在同一事务里检查唯一消费键、核验预留、结转双方资产并写账本；若上次已入账只是回执丢了，就返回原结果，不再扣款。撮合还要把记账确认写回日志，而不是记住“我发过了”就删掉义务。

小林最后核对 A 可用 20,000 USDT、增加 1 BTC，B 收到 30,000 USDT，并检查原事件与确认都有证据。恢复状态先完整发布，查询明确水位；新主的外部交付还要等账户围栏安装，不能只靠路由切换宣布旧主失权。订单全成、账户到账和页面追平是三件事，每件事有责任人、有恢复依据，才算把故障后的交易接着做完。

**流程位置与核心机制：** 从可靠受理到资产结转建立全貌，解释恢复究竟恢复谁的状态。沿用总览的托管现货、快照 100、买单 B1 与命令 101；本题建立闭环，后续各题分别深挖存储、快照与切主协议。

## 第 1 层：不能只回答重启进程

**面试官：** A 买入 1 BTC，撮合处理期间进程崩溃。如果由你设计，怎样让这笔交易最终完成？

**面试者：** 我先确定命令越过了哪个可靠边界，而不是直接重新下单。账户已经为 B1 预留 30,000 USDT，撮合的可靠事实来自三节点共识组。恢复器加载已验证快照 100，由协议确认已提交前缀，再按顺序应用 101，重建 B1、S1 的全成状态、原成交身份和待交付结果。交付器把同一成交送到账户，账户在一个事务里去重并完成双方资产结转，之后撮合记录确认。订单执行完成、资金完成和页面可见分别给证据，不能把服务监听端口成功当作交易恢复完成。

## 第 2 层：日志有命令是否就等于有成交

**面试官：** 你说“确认已提交前缀”。如果磁盘上已经有 101，为什么不能直接执行？

**面试者：** 因为磁盘存在只能证明这个节点保存过一份条目，不能证明它属于集群最终选择的已提交历史。101 可能只是旧主在网络分区时写下的未提交尾部。基线只允许 committed command 进入业务状态机；先恢复共识状态、协调日志、确定 C，再执行 S 后到 C 的连续命令。若 101 已提交但未应用，它形成必须履行的业务处理义务；若尚未提交，它仍可能被后续提交或被合法新主替换，既不能先制造成交，也不能对客户断言“肯定没发生”。

## 第 3 层：客户超时与资金预留怎么办

**面试官：** 既然没法立刻知道 101 是否发生，A 超时后能否把 30,000 USDT 解冻，再重新下单？

**面试者：** 不能。超时只是调用方没有拿到结果，原命令可能已经提交，也可能正在延迟到达。A 应保留原请求键 `A/place/r1` 查询或重试，不能更换身份制造第二笔订单。账户保留 R-A 的交易资格，释放必须与撮合的有序拒绝、撤销或剩余量关闭达成契约。若需要取消尚未确定受理的意图，就先建立可恢复的撤销屏障，使迟到命令不能再凭已释放资格被接纳。否则先解冻后迟到成交，会把一份资金同时用在旧成交和新订单上。

## 第 4 层：已经全成但账户没变是否矛盾

**面试官：** 假设查明 101 已执行，两单都是全成，但账户仍显示原预留。系统是不是已经不一致？

**面试者：** 这是需要继续收敛的允许暂态，不是可以忽略的最终状态。撮合权威决定“已成交 1 BTC、应支付 30,000 USDT”，账户权威决定资产何时在账本中原子移动。撮合应用 101 时必须同时保存稳定成交、请求结果和待交付义务，因此即使发送前崩溃，恢复也能找回交收工作。原预留在账务结束前继续覆盖已确定义务，不因为订单全成就直接释放。对外可回答执行已完成、账务处理中；不能回答资金已到账，也不能回滚成交来掩盖账户服务暂时失败。

## 第 5 层：账务已成功但回执丢失

**面试官：** 你依靠重发收敛。账户其实已经完成结转，只是回执丢了，再发岂不是扣两次？

**面试者：** 发送保证采用至少一次，单笔业务效果由接收端事务保证。账户以来源分片和成交事件 ID 建唯一消费键，并将载荷摘要、余额变动、双方账本分录及消费结果放在同一事务里。第一次提交后回执丢失，第二次拿相同 ID 查询到已完成结果，不再移动资产；同 ID 不同载荷必须拒绝报警。撮合收到持久记账确认后，把交付确认作为命令写回日志，不能凭本机“发送过”删除义务。因此两个系统无需假装处在一个大事务内，也能明确解释每个失败窗口由谁继续。

## 第 6 层：恢复后的状态由谁对外发布

**面试官：** 内存状态已恢复，能否立即让查询、行情和账户消费者各自读取这个 map？

**面试者：** 不能把恢复过程中的半成品暴露出去。恢复器在隔离状态中完成快照加载、连续应用和不变量检查，形成带 A 的完整状态后，再通过单写者交接或不可变视图原子发布。查询要声明数据水位，强一致查询还要通过当前主的线性读屏障，不能从落后副本的“查无此单”推导订单不存在。行情使用自己的连续序号和缺口补齐，不把撮合日志索引直接当连续行情序号。账户只消费明确的完整业务结果，不扫描恢复中的临时结构做扣款。

## 第 7 层：新主接管还缺哪一步

**面试官：** 你已经恢复了状态。如果旧进程只是失联而没有死，新主发布结果时如何避免双写？

**面试者：** 共识先保证只有合法主能够推动新的已提交裁决，但旧进程还可能持有延迟 RPC 或外部连接。新主需要提交本任接管屏障，应用追平，再把该屏障索引作为更高围栏 token 安装到账户接收端。接收端在与记账相同的事务内检查 token，安装完成后拒绝旧 token；旧消息携带的合法已提交事件由新主保留原 ID 重送。token 用来限定发送授权，事件 ID 用来限定经济效果，两个身份不能合并。若外部接收端不支持这一约束，就不能宣称只靠选主隔离了全部副作用。

## 第 8 层：怎样证明交易真的恢复完成

**面试官：** 围栏也安装了，你会依据什么证据宣布 B1 已经恢复完成？

**面试者：** 我会按业务阶段验收：协议确认 101 在提交前缀内；撮合 A 已覆盖 101，B1 与 S1 各成交 1 BTC，成交 ID 和载荷与原结果一致；账户有对应消费事务及平衡分录，A 最终 20,000 USDT 和新增 1 BTC，B 收到 30,000 USDT；交付确认被撮合可靠记录。查询投影若落后则标注并补齐，不用投影替代账本证据。这里宣告的是这笔交易的恢复结果，整个分片重新开放还须检查连续水位、积压与写权。任何一个证据不明，都应报告具体阶段，而不是笼统说“恢复成功”。

## 本题收束

- **讲透的机制：** 恢复已提交事实、恢复业务状态、补交付、账户事务、取得唯一执行权和分阶段验收，是一条有责任人的闭环。
- **最易答错：** 把日志存在当提交，把超时当拒绝，把全成当已入账，把端口健康当业务可开放。
- **反例检验：** 在账户提交后、回执到达前崩溃，再从快照 100 恢复 101；应出现同一成交重发，但不能出现第二次扣款或提前解冻。
