# 大问题 3：日志怎样写才能检测损坏并正确恢复？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 结构化恢复日志 | 机器能严格识别边界并校验的记录，不是调试打印。 | 101 要有版本、长度、分片、索引、任期、完整载荷与摘要。 |
| 逻辑索引 / 文件偏移 | 命令排在历史中的位置，以及字节落在文件中的地址。 | 业务按索引有序推进，不能按物理偏移猜提交顺序。 |
| term / shardID | 条目所属任期和分片身份。 | 字节完整仍要验证历史衔接与归属，不能接入别的分片。 |
| 长度上限 / 记录边界 | 防止误读超大内容，并确认一条记录从哪里到哪里。 | 载荷只写一半时不能把后面的随机字节拼成新命令。 |
| 尾部撕裂 / 未完成追加 | 崩溃时最后一条可能只留下部分字节。 | 只有能证明未获持久承诺的未完成尾记录，才可按协议截去补齐。 |
| 中段损坏 | 不是正常追加残尾，而是已有历史内部出了问题。 | 101 校验失败、后面还有 102 时必须隔离修复，不能跳过或随意截断。 |
| CRC / 校验和 | 用于发现部分字节损坏的校验值。 | 校验通过不证明分支正确、已提交或能抵抗恶意篡改。 |
| write / 短写 / 页缓存 | 内核接受写入，但可能只接受一部分或暂存在内存。 | 需处理实际写入长度与错误，write 成功不等于掉电后还在。 |
| Flush / fsync / fdatasync | 清用户态缓冲，以及按平台契约要求持久化数据。 | Go writer 的 Flush 不是磁盘同步，进程退出实验也不等于断电验证。 |
| 追加所有者 / 有界等待队列 | 有人统一维护日志边界，并限制等待刷盘的请求数量。 | 多个 goroutine 不能各自抢文件游标，磁盘慢要反压入口。 |
| D / 批量同步水位 | 已经由真实同步覆盖的完整日志位置。 | 定时器触发不授权把新追加尾部也标成 durable。 |
| 分段清单 / 辅助索引 | 描述日志文件组织，以及帮助定位记录的可重建目录。 | 辅助索引不是第二权威，切段与清单也有持久化顺序。 |
| 冲突后缀覆盖 | 按共识证明替换不再属于当前历史的未提交尾部。 | 不能保留两条同索引让恢复器随选，也不能因请求超时主动删尾。 |
| committed entries | 共识协议明确允许业务执行的连续条目。 | 日志能解析、D 已前进，都不等于成交已经成立。 |
| 磁盘满 / 容量余量 | 新数据写不进去，以及为快照、切段、修复预留的空间。 | 停止虚假持久 ACK，不能为接新单删除唯一恢复材料。 |
| 可信修复 / 同水位逻辑摘要 | 从合法历史补齐后，在相同执行位置核对业务内容。 | 还要检查订单数量、去重和交付义务，CRC 全对不等于可立刻服务。 |

## 把整篇文章压缩成一个故事

B1 要用 30,000 USDT 买 1 BTC，命令 101 正在落盘时机器掉电。工程师小何重启后发现头部完整、载荷只剩一半。他不能看到“最后一条坏了”就直接删除，而要先查存储协议和提交证据：若能证明是未完成、未获持久承诺的追加，可截掉残尾并从健康副本补齐；若该位置本应已经可靠保存，就必须认定副本损坏，退出服务修复。

另一种情况更危险：101 长度完整却校验失败，后面 102 还完好。小何必须隔离这段历史，不能跳到 102，也不能把已承诺前缀剪掉。格式里的长度、校验和、索引和任期分别提供不同证据；write 返回、Go 缓冲 Flush、真正磁盘同步也不是同一层保证。批量同步只能把确实覆盖的完整记录计入持久水位，刚写进来的新尾部不能搭便车，最终是否提交仍交给 Raft 判定。

修复时，小何按合法快照与协议后缀补齐，再在同一提交切点检查订单数量、原请求结果和待交付义务。磁盘满则反压新请求，不能先删最老日志碰运气，因为它可能是找回成交的唯一材料。本篇给出的是应如何判断和验收，不是已经完成的掉电实验；“字节读得出来”只过了存储的一关，还没有替业务证明一笔成交。

**流程位置与核心机制：** 深入本地日志存储，不替代共识的提交判定。沿用总览三节点模型与命令 101，区分逻辑条目位置、物理字节偏移和持久化完成。

## 第 1 层：日志为什么不能只是打印一行

**面试官：** 如果由你为撮合命令设计日志，怎样让进程崩溃后还能正确读取？

**面试者：** 我会使用有明确记录边界的结构化日志，而不是把调试打印当恢复源。每条记录包含格式版本、长度、分片身份、索引、任期、命令类型、请求键、完整载荷与摘要，存储层为头部和内容设置合适的校验。启动时验证长度上限、记录完整性、连续性及分片归属，只有验证通过的记录才能交给协议恢复。业务日志顺序由逻辑索引定义，文件偏移只是定位字节。日志能读出来也不代表已提交，最后仍由共识协议提供 committed entries 给业务状态机。

## 第 2 层：追加到一半崩溃怎么办

**面试官：** 你依靠长度划分记录，假设 101 的头写完了、载荷只写一半就掉电，启动会怎样？

**面试者：** 解析器会发现声明长度超出实际有效尾部，不能把残片当作合法命令，也不能扫描后面的随机字节凑一条新记录。能证明是未完成追加、未获得持久化承诺的物理尾记录，可按存储协议截去并从健康副本补齐；不能只因它在文件末尾就推定可以丢。若持久状态或集群提交证据表明该位置必须存在完整条目，说明本副本违反了原可靠假设或已损坏，应退出服务并修复。尾部处置是证据驱动的恢复动作，不是“解析失败一律忽略”。

## 第 3 层：校验失败是否也能当残尾截断

**面试官：** 如果 101 长度完整，但校验和不对，后面还有 102，可否截去 101 及以后继续启动？

**面试者：** 不能把中段损坏伪装成正常掉电残尾。完整记录校验失败，特别是后面还有其他记录时，要认定本地副本不可信，停止提供该历史并从可信快照或其他副本修复。若损坏涉及已确认前缀，任意截断会丢失已经承诺的订单和成交；从 102 接着执行又会跳过状态依赖。校验和只能帮助发现部分随机损坏，不能证明记录属于当前规范日志，更不能抵御恶意篡改。正确的结构、索引任期一致性、协议状态与业务不变量都需要检查。

## 第 4 层：write 成功为何还不算落稳

**面试官：** 假设记录格式都正确，write 已返回成功，为什么复制 ACK 还要等同步？

**面试者：** write 通常只表示数据被内核接受，可能还在页缓存里；机器掉电时未必保留。存储层还要处理短写和写错误，再根据平台和协议契约完成 fsync、fdatasync 或等价持久化，成功后才能满足需要 durable 的响应条件。Go 的缓冲 writer 还多一层用户态缓冲，Flush 也不等于掉电持久。若底层设备谎报同步完成，软件层不能凭空补出可靠性，应把它列为存储假设和运维验证事项。不能以“平时 kill 进程都能读到”替代断电故障语义。

## 第 5 层：批量同步怎样与并发写配合

**面试官：** 我准备由多个 goroutine 同时追加，再定期 fsync 一次。怎样知道每条命令是否已经可靠？

**面试者：** 应有一个明确的日志追加所有者，或由经过验证的存储引擎序列化写入与覆盖。多业务 goroutine 提交请求，不直接竞争维护文件游标、记录边界和 durable 水位。批量同步成功后，只能提升到该次同步确实覆盖的完整条目位置，并唤醒对应等待者；期间追加的新尾部不能顺带被标成已持久。等待队列要有界，错误应传播到所有受影响的提议和协议处理。持久化位置 D 的推进必须与实际 I/O 完成关联，而不是由定时器触发后盲目赋值为最新索引。

## 第 6 层：日志分段和覆盖怎么处理

**面试官：** 单文件太大要分段，而且切主可能覆盖未提交尾部，你的索引还能用吗？

**面试者：** 我会区分分段清单、逻辑索引和物理位置。分段记录起始位置、格式与校验元数据，辅助索引可以由有效记录重建，不把索引文件单独当权威。协议要求从某个位置替换冲突尾部时，存储必须删除或使旧后缀不可见，再原子地暴露正确的新后缀，不能保留两条相同索引的记录让恢复器随便选。切段、新建文件、清单更新需要满足文件与目录持久化契约。只有协议证明可替换的未提交部分才能按该路径覆盖，业务代码不能因请求超时主动截断日志。

## 第 7 层：磁盘满时怎么保护已确认历史

**面试官：** 如果追加 102 时磁盘满，但 101 已经确认成功，是不是删掉最老日志就能继续？

**面试者：** 不能。最老日志可能仍是唯一可用快照之后的必要恢复前缀，也可能承载尚未归档的结果重建材料。先拒绝或背压新提议，保留已经承诺的数据；故障节点不能继续发持久成功 ACK。若其他两个节点仍健康，协议可在安全条件下继续；失去多数则停写。清理只能遵循已验证快照、下游恢复和备份保留规则，不能临时绕过。容量监控应在耗尽前留出日志切段、快照临时文件和恢复操作空间，避免“为了做快照先把剩余磁盘写满”的死循环。

## 第 8 层：修复后怎样判断副本可信

**面试官：** 你从其他节点补回了日志。只要 CRC 全对，就能让这个节点参与投票和服务吗？

**面试者：** 还要完成协议层与应用层校验。协议层确认分片和集群身份、快照锚点的索引任期、配置状态及后缀衔接，不能接入另一个分片或过期备份；持久状态按库要求恢复。业务层从可信切点回放到同一个已提交水位，核对订单数量、去重结果、成交摘要和待交付义务，比较逻辑状态摘要而非物理文件字节。再按协议和运维流程恢复其角色，不能边修复边提供强一致查询。本文给出的是修复验收条件，未执行损坏注入或磁盘实验，不声称已有测试证据。

## 本题收束

- **讲透的机制：** 结构化记录、完整性校验、真实持久化、正确覆盖和可信修复共同构成本地存储契约。
- **最易答错：** 把所有末尾错误都当可截断残片，把 Flush 当 fsync，把 CRC 正确当已提交或分支正确。
- **反例检验：** 修改已确认 101 中间的一个字节，再保留完整 102；启动必须隔离并修复，不能跳过 101、截断承诺或悄悄继续服务。
