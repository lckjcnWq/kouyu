# 大问题 8：主备复制怎样不丢已确认命令？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| N1 / N2 / N3 / 多数 | 三个投票节点，以及有效协议配置要求的多数票。 | 常态多数为两个，与买卖账户 A、B 区分；不是谁在线就重新数多数。 |
| 可靠受理 / 执行 / 账务完成 | 命令已承诺、订单已裁决、资产已结转三种证据。 | 101 提交才受理，返回成交还要等执行，复制撮合不等于复制账户。 |
| WAL / HardState / durable | 恢复日志、任期投票等协议状态，以及按契约真正保存完成。 | 内存收包不能算持久副本，写盘与响应顺序遵循所选库。 |
| term / commitIndex | 领导任期，以及协议已确认的连续提交位置。 | 旧条目有两份不等于可首次直接宣布提交，不能把最大磁盘位置当进度。 |
| 当前任期提交规则 / no-op | 按多数直接推进的位置须属于本任期，可用本任期空操作建立证明。 | 该位置合法提交后连带提交此前匹配前缀，不是另提交成交结果。 |
| lastLogTerm / lastLogIndex | 节点最后一条日志的任期和索引。 | 投票先比任期，再比索引，不能只选文件最长的节点。 |
| votedFor / 每任期一票 | 节点本任期已投给谁的持久记录。 | 重启不能忘票，这和日志新旧限制一起保护选举安全。 |
| Leader Completeness / 多数交集 | 后续合法主包含已提交历史的性质，以及多数集合相遇的条件。 | 多数交集不是全部证明，还依赖持久投票、日志匹配和选举限制。 |
| AppendEntries / prevLogIndex / prevLogTerm | 复制并检查前一位置与任期的协议机制。 | 冲突修复按协议替换后缀，普通心跳不等于无条件删本地尾部。 |
| 未提交尾部 / 本地水位落后 | 后缀尚无确定提交证据，或节点还没获知更高提交位置。 | 不能全执行，也不能按重启水位把可能已提交的 101 删掉。 |
| command-only / 原子 apply | 只共识提交完整命令，执行时完整发布业务状态。 | 订单、稳定成交、去重、outbox 和 A 一起前进，不另做结果共识。 |
| requestKey / eventID / outbox | 原请求身份、经济事件身份，以及未完成交付义务。 | 同键重试复用 `btc-usdt-1/101/0`；换主不能再造一笔成交。 |
| InstallSnapshot / 快照锚点 | 用完整快照追赶，并在边界索引、任期和配置处接上合法后缀。 | 不能只复制盘口，去重屏障和旧交付义务也要保留。 |
| learner / 晋升 | 先不投票地学习历史，追赶合格后再按协议获得投票资格。 | N4 刚启动不能立刻凑票替代丢盘的 N3。 |
| joint consensus / 联合配置 | 成员过渡期间同时受旧、新配置多数约束。 | 不能把两个配置节点混在一起简单算总数过半。 |
| 故障模型 / RPO / 可用性 | 哪些故障保住哪些事实，以及还能否继续提供业务。 | 单节点永久丢盘在基线内；失去多数停新提交，不承诺固定恢复时长。 |

## 把整篇文章压缩成一个故事

A 的 B1 要以 30,000 USDT 买下 S1 的 1 BTC。设命令 101 在当前任期依法提交，N1、N2 已按契约持久保存，N1 返回结果后连盘损失，N2 却还没收到最新提交水位，N3 只有快照 100。工程师小沈不能让 N2 按本地水位删掉 101，也不能挑响应最快的 N3 强行当主。真正要保住的是已承诺前缀，不是某台机器记忆里的最大数字。

合法选举先比较日志末任期、再比较索引，每任期投票也要持久。新主即使已经带着 101，仍可能暂时不知道提交水位；它通过本任期条目合法提交来确认此前匹配历史，而不是数两份旧任期记录就宣布成功。恢复只执行协议交付的连续前缀，未知尾部由协议协调。没有多数时停止新提交，客户继续沿原键查证，不能本地先成交或把 30,000 USDT 预留释放掉。

若落后节点需要的日志已压缩，小沈提供完整快照，让它恢复队列、去重、原成交身份与未完成交付，而不是只同步盘口。替换丢盘节点也先让新节点作为 learner 追赶，再按合法联合配置晋升。三节点模型保护的是约定单节点故障下的提交历史；多数持久副本永久丢失不能靠强选主补回来。即使命令保住了，账户交收和旧主外部写权仍要另行过门槛，复制安全不是全业务完成证明。

[返回专题总览](README.md)

**流程位置与核心机制：** 从主节点提出命令，追到持久多数、提交前缀、合法选举、日志修复与成员变更。本题回答“已承诺的历史凭什么保住”；接管后的外部写权围栏由下一题展开，不把选主直接等同于恢复全部业务。

必要前提：

- 沿用总览的三节点成熟 Raft，节点记为 N1、N2、N3，与交易账户 A、B 区分。存储如实履行持久化契约，讨论崩溃、重启、网络分区和单节点永久磁盘损失，不覆盖拜占庭故障或多数持久副本同时永久丢失。
- 快照已执行到 100，包含卖单 S1：卖 1 BTC，价格 30,000 USDT/BTC。命令 101 为 A 的买单 B1：买 1 BTC，限价 30,000，请求键为 `A/place/r1`。账户服务已为 A 预留 30,000 USDT、为 B 预留 1 BTC，撮合不得直接修改这些余额。
- 本专题采用 command-only 确定性状态机：命令携带完整业务上下文，提交后按序执行并生成结果，不另设结果日志做第二次共识。以下均为协议与业务的教学推演，不代表实测或个人生产经历。

## 第 1 层：先说清“已确认”承诺了什么

**面试官：** 对命令 101，主备复制怎样保证不丢已确认命令？你说的确认究竟发生在哪里？

**面试者：** 我先区分可靠受理、执行完成和账务完成。101 只有按照 Raft 提交规则进入持久多数支撑的已提交前缀，才能确认可靠受理；返回确定订单结果还要等状态机执行完成，账户是否入账则由账户事务决定。三节点的多数是两个，但不能把“两个节点见过数据”直接当作提交。承诺是不因模型内故障撤销这条已提交命令，新主仍能继续执行或恢复其结果，而不是请求永不超时。本地刷盘、进入发送队列、备机收到内存消息，都不足以越过确认边界；响应丢失也不意味着命令没被受理。

## 第 2 层：两个副本必须持久到什么程度

**面试官：** 你说两个节点见过数据还不够。假设 N1 已刷盘、N2 只收进内存，为什么不能先确认，重启时再补齐？

**面试者：** 因为 N1 磁盘永久损失、N2 随后重启，就可能把唯一持久内容一起丢掉。可用于本题承诺的多数必须满足所选实现的持久化契约：日志内容及索引、任期，连同协议要求的当前任期、投票等状态，必须按规定顺序保存；相关确认和投票响应不能越过其持久性要求。接入层也不能把普通网络收包当成 durable 确认。具体 WAL、快照、HardState 与消息发送顺序遵循库契约。普通同步双拷贝没有合法选举、投票限制和冲突修复规则，不能冒充共识；即使确有两份持久日志，是否可以推进提交还要检查任期。

## 第 3 层：旧任期条目为什么不能直接数副本

**面试官：** 你最后强调还要检查任期。那么新主发现旧任期的 101 此刻已在两个磁盘上，能否直接把 commitIndex 推到 101？

**面试者：** 不能仅凭此刻的副本数，把旧任期条目首次宣布为已提交。Raft 按复制数量直接推进 commitIndex 到 N，要求多数复制位置达到 N，且 N 对应条目属于当前任期；正常复制还须满足日志匹配和持久性契约。新主可追加本任期空操作或合法命令，等该条依法提交后，连带提交它之前的匹配历史前缀，包括旧任期的 101。这不是重写 101，也不是把成交结果再提交一次。历史上已依法提交的旧条目当然不会变回未提交；限制针对的是新主不能用一次“旧条目现有两份”的观察，替代协议规定的提交证明。

## 第 4 层：选举怎样保住新主尚不知道已提交的历史

**面试官：** 你说提交本任期条目能连带确定历史前缀。如果旧主提交 101 后就宕机，备机还不知道最新 commitIndex，新主凭什么一定带着 101？只选日志最长的节点吗？

**面试者：** 不是只看长度，也不要求候选人预先知道最新 commitIndex。投票者先比较候选人与自己的 lastLogTerm，任期相同才比较 lastLogIndex；日志更长但末条任期更旧，仍可能不够新。每任期至多投一票及相关任期、投票信息必须持久化，候选人须取得合法配置的多数票。多数交集只是证明的一部分，还要结合日志匹配和选举新旧限制，逐任期建立 Leader Completeness：后续合法主节点包含历史已提交前缀。因此，新主可能已有 101，却尚不知其提交水位；再提交本任期条目确认前缀，而不是凭本地水位决定历史是否存在。

## 第 5 层：重启后的孤儿尾部由谁裁决

**面试官：** 既然本地提交水位可能落后，旧主重启后只恢复出 commitIndex=100，但磁盘有 101、102、103，能否删掉 100 之后的日志，或者按磁盘末尾全执行？

**面试者：** 两种做法都不行。本地水位落后不证明后缀未提交，磁盘有条目也不证明它已提交。重启节点先恢复协议状态，加入当前合法主节点的协调；AppendEntries 用 prevLogIndex、prevLogTerm 检查匹配，再按协议定位冲突，替换冲突项及其后缀。不能把一条心跳理解为“无条件删掉主节点末尾之外全部内容”。已提交的 101 不得被合法历史覆盖；尚未确定的 102、103 可能后来提交，也可能被替换，业务线程不能自行裁决。状态机只执行库提供的已提交连续前缀；若发现与可信已提交历史冲突，应停机排查，而非当作普通尾部清理。

## 第 6 层：没有多数时宁可停在哪里

**面试官：** 你说尾部必须等待协议协调。但网络分区只剩一个节点可达，A 的 101 又超时了，能否先本地成交稍后补复制，或者直接释放预留？

**面试者：** 不能。单节点没有多数，不能新提交，也不能把本地推测的成交当成已确认结果。这里停止的是新提交，并非宣布所有历史命令不存在；101 可能此前已经提交，也可能仍是未提交尾部。RPC 超时只能报告结果不明，A 应沿原请求键查询或重试，孤立节点“查无记录”不足以证明未受理。30,000 USDT 预留必须保留，直到取得撮合有序终态或资格撤销屏障，不能靠超时解冻。多数恢复后再由协议确定前缀、顺序执行并答复。把可用性压力转成先成交或先解冻，会分别制造丢命令或无资金支持的迟到成交。

## 第 7 层：复制的不能只有盘口

**面试官：** 你要求 A 用原请求键重试。假设多数恢复并换主，新主只有复制来的盘口，却没有原请求结果和交付状态，还能实现这个承诺吗？

**面试者：** 不能，复制必须覆盖可恢复的请求结果和交付责任。各副本只 apply 已提交命令，将订单、成交、请求键与载荷摘要及原结果、逻辑 outbox、appliedIndex 在同一边界原子发布，不增加第二次结果共识。101 的成交 ID 为 `btc-usdt-1/101/0`，按 `shardID/logIndex/批内序号` 确定；shardID 全局唯一且不可复用，不能因灾备重用身份空间。同键同摘要重试返回 101 原结果，异摘要拒绝；重试即使另占日志位置，也不能重新撮合。账户确认必须作为命令提交同一日志，执行后才标记交付完成；发送成功不等于确认。余额始终只由账户事务修改。

## 第 8 层：日志截断后怎样补回完整状态

**面试官：** 你把去重和交付义务都纳入恢复了。如果 N3 长期落后，所需命令日志已被快照压缩，怎样追赶才不会漏掉这些义务？

**面试者：** 不能只复制当前盘口 map。主节点提供已提交、已执行切点 S 的完整快照，含 lastIncludedIndex、lastIncludedTerm、对应成员配置，以及订单队列次序、累计量、去重结果与过期屏障、成交、未确认 outbox、交付确认状态和执行水位；规则、格式版本与内容校验材料也须可验证。接收端依所选库的安装契约，协调业务镜像、协议元数据、持久化和安装确认，再按匹配关系处理后缀并从 S+1 续接已提交命令。不能自行猜配置或把覆盖 map 当原子安装。这样即使 101 已被压缩，其原结果和未完成交付仍然存在，不会因换节点变成重新成交或永久漏交收。

## 第 9 层：补好的节点何时才能算票

**面试官：** 你说快照带着成员配置安装。现在 N3 磁盘永久损失，想用 N4 替换它，能否先删掉 N3，再让刚启动的 N4 参加多数投票？

**面试者：** 不能自造先拆旧、后补新的协议。这里选用支持 learner 和 joint consensus 的成熟实现：通过其配置接口接纳 N4 为非投票 learner，完成快照及日志追赶，达到库规定的晋升条件后，再走受支持的配置过渡。旧配置为 N1、N2、N3，新配置为 N1、N2、N4；联合阶段的选举与提交须同时满足旧、新配置各自多数，不能只对节点总数取过半。最终配置的生效、退出联合阶段和移除旧成员，都遵循库的日志与生效契约。未追平的 N4 不能提前凑投票多数；如果原配置已无可用多数，也不能靠临时新增节点绕过这个限制。

## 第 10 层：安全承诺与可用性承诺分别到哪里

**面试官：** 连替换节点也不能绕过原配置多数。那么两个持久磁盘同时永久丢失时，强制剩余节点当主能否继续声称零丢失？最终保证是什么？

**面试者：** 不能，强制改配置不会凭空补回已承诺历史。安全承诺限于既定故障模型：依法提交的前缀不会被后续合法选举与复制覆盖；单节点永久损失后，剩余多数仍能保住它。失去多数则停止新提交，网络、磁盘与调度条件也使本题不能承诺固定恢复时长。两个以上持久副本永久丢失、存储虚报刷盘或全域灾难，要另走可信备份与审计的灾难恢复，不能沿用本题保证。即使合法选出新主，也须确认提交屏障、应用追平，外部写路径满足围栏后才开放。命令不丢不等于请求不超时，更不等于账户已经完成交收。

## 本题收束

- **机制：** 持久多数不是孤立的副本计数。它与当前任期提交规则、持久投票、日志新旧比较、日志匹配和合法成员过渡共同维持已提交前缀；完整快照承接压缩历史。状态机据此确定性重建订单、成交、去重与交付义务。
- **易错：** 不把普通双拷贝当共识，不直接数旧任期条目的副本宣布提交，不只按日志长度选主，也不要求候选人先掌握最新 commitIndex。不能按重启时本地水位删尾、按磁盘尾执行、因 RPC 超时释放预留，或把落后新节点提前算成投票多数。交付确认是同日志中的后续命令，不是第二份成交结果共识；日志索引也不是连续交付序号。
- **反例：** 假设 101 在所属当前任期依法提交，N1、N2 已持久化，N1 返回确定结果后磁盘永久损失，N2 尚未收到最新提交水位、N3 只有快照 100。若方案允许 N2 按本地水位删掉 101，或让缺少 101 的节点绕过投票新旧限制接管，就已经丢失已确认命令。正确路径必须保住 101，经合法选举和本任期提交屏障恢复原结果 `btc-usdt-1/101/0`；未确认交付仍须继续，同请求重试不得再生成一笔成交。
