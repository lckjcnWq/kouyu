# 大问题 2：怎样定义可靠受理与日志提交的持久化承诺？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 可靠受理 | 系统已承担后续必须按序处理这条命令的责任。 | 101 进入可恢复提交前缀才算数，不保证成交或到账。 |
| 执行完成 / 账务完成 | 订单裁决已确定，以及资产结转已提交。 | 返回具体订单结果要等执行；账户完成另看独立事务。 |
| channel / 提议路径 | 进程内传递工作，以及向共识组申请排入历史的路径。 | 入 channel 或提出命令都不等于已经可靠受理。 |
| write / fsync | 把数据交给内核，以及按存储契约要求同步到持久介质。 | 本机刷盘可支撑较窄故障承诺，不能独自扛本机永久丢盘。 |
| 故障模型 / 故障域 | 承诺覆盖哪类失效，以及哪些副本可能一起失效。 | 本例覆盖单节点永久磁盘损失，不自动覆盖整个机房永久丢盘。 |
| Raft / 持久多数 | 按共识规则协调命令，并可靠保存到多数节点。 | 三节点多数为两个，日志与必要协议状态都要按契约落稳。 |
| ACK / durable | 确认消息，以及真正满足持久化条件的状态。 | 普通收包或写失败不能算持久成功 ACK。 |
| C / committed entries | 协议判定的提交水位，以及获准应用的命令。 | 应用读取库提供的已提交条目，不自行数两个存储 ACK。 |
| term / 本任期提交规则 | 领导任期，以及直接按多数推进提交的限制。 | 不能仅凭旧任期条目有两份就首次宣布提交。 |
| no-op / 接管屏障 | 新主提交的不改业务空操作或接管控制命令。 | 本任条目依法提交后，可连带确认此前匹配前缀。 |
| currentTerm / votedFor | 节点当前任期和本任期已投给谁。 | 重启不能忘掉投票约束；只保存业务日志不足以维持协议安全。 |
| S / A | 快照包含到哪条，以及状态机已执行到哪条。 | 快照 100 加已提交 101 能恢复原结果，不能把未执行说成全成。 |
| requestKey / payloadHash | 稳定业务编号和规范化载荷摘要。 | 重试可另占日志位置，但同键同摘要只能复用原结果。 |
| group commit / p99 | 多条共享同步成本，以及最慢一端的延迟指标。 | 批处理不降低可靠门槛；批量与等待时间要有界。 |
| 提交未知 | 调用方暂时没有证据确认命令是否已提交。 | 超时后沿原键查询，不把网络失败写成业务拒绝。 |
| RPO / 验证证据 | 已承诺数据允许损失的范围，以及证明确认时序的材料。 | 零丢失要绑定故障域；故障窗口设计不是已经通过的实测。 |

## 把整篇文章压缩成一个故事

A 已为买 1 BTC 预留 30,000 USDT，接口想尽快回复 B1“已可靠受理”。工程师小陈发现旧实现只等命令进 channel 就回包：进程一退出，订单可能根本没留下。他把确认挪到共识提交之后，却仍要分清本机 fsync 和集群提交。前者只保护本机介质仍在的故障；本专题还承诺单节点连盘永久损失，所以三节点中的持久多数和合法提交规则都不能省。

命令 101 的日志与必要任期、投票状态按实现契约保存，协议确认提交后，接口才能承担处理义务；要返回“成交 1 BTC”，还得等状态机实际执行。新主若只看到旧任期条目有两份，不能自行数票宣告提交，而须遵守当前任期提交规则。若 101 提交后尚未执行就崩溃，从快照 100 继续应用即可得到原成交，不需要再下一个买单，也不另做一次结果共识。

A 若没收到回包，仍用原请求键查证：同键同摘要重试即使进入新日志，也只返回原结果。小陈可以批量刷盘分摊成本，但不能提前确认，也不能把同机房副本说成跨域容灾。验证时应分别挑战刷盘前、仅少数持久、提交后未响应等窗口；这些是要实施的检查，不是已经跑出的成绩。“可靠”最终指向明确承诺和证据，不是一个含混的 success。

**流程位置与核心机制：** 聚焦命令进入系统到可对外确认之间的可靠边界。沿用总览三节点 Raft、命令 101 和独立账户服务；本题定义承诺，复制题进一步推演选举与日志修复。

## 第 1 层：可靠受理承诺保留什么

**面试官：** 下单接口返回“可靠受理”，你究竟承诺了什么？

**面试者：** 在这个模型中，我承诺这条命令已经进入可恢复的已提交前缀，在约定的一节点故障范围内，后续合法主必须继承并按顺序处理它。它不保证成交，因为业务检查仍可能得出拒绝或未成交结果；也不保证账务已经结转。若接口返回具体成交或订单终态，还要等该命令被应用，取得确定结果。协议提交、业务执行、外部记账分别有自己的证据，接口应明确返回的是哪个阶段，不能用一个含混的 success 同时代表三者。

## 第 2 层：为什么进入 channel 不算可靠

**面试官：** 你说要等提交。入口已经成功把命令放入 Go channel，为什么不能先返回受理成功？

**面试者：** channel 只改变当前进程里的内存所有权，不提供崩溃后的保留承诺。发送返回可能仅说明接收方接到了对象，业务 goroutine 甚至还没开始写日志；进程或机器故障后，这条命令会消失。可以返回“已接收，结果待确认”，但不能让客户端把它当可靠受理，更不能据此释放重试责任。若要求可靠承诺，入口应把命令交给共识提议路径，等待对应请求映射到提交结果；在等待期间超时，返回不确定状态，后续按原请求键查证，而不是把超时解释成已经拒绝。

## 第 3 层：本机刷盘是否足够

**面试官：** 那我等本机 fsync 完成再返回，已经能扛进程崩溃，为什么还要多数复制？

**面试者：** 如果故障模型仅是进程退出而本机磁盘可靠保留，本机同步日志可以支撑较窄承诺。但总览允许一个节点连磁盘永久损失，仅本机保存会丢失已确认命令，因此基线要求共识协议形成持久多数并满足提交规则。三节点至少两个节点保存必要协议状态和日志，合法选举再保证提交历史被继承。复制不是免费的：跨节点网络与刷盘进入确认路径，延迟高于纯内存响应。可以改变故障承诺换取延迟，但必须在接口和恢复说明中直说，不能把异步备份包装成同等可靠性。

## 第 4 层：两份磁盘副本就一定已提交吗

**面试官：** 既然三节点中有两份持久副本，是不是数够两个 ACK 就可以推进 C？

**面试者：** 还必须满足协议规则。Raft 主节点不能仅凭某个旧任期条目已经复制到多数就直接把它判定为已提交；通过多数复制直接推进的位置 N 要满足该条目属于当前任期，再连带提交之前的前缀。旧任期尾部可能看起来有多个副本，却仍处于可能被合法新主覆盖的状态。应用层应使用协议库交付的 committed entries，而不是监听两个存储 ACK 后自行调用撮合。新主通常需要提交本任 no-op 或接管屏障以确认前缀，这也是“选举完成”与“可以服务”之间的重要区别。

## 第 5 层：收到 ACK 前必须持久化哪些内容

**面试官：** 你依赖协议库，那集成存储时只同步业务日志、不保存任期和投票，会有什么问题？

**面试者：** 重启后节点可能忘记已经投过票或见过的更高任期，从而破坏协议对选举安全的前提。必须按实现契约持久化日志和 `currentTerm/votedFor` 等硬状态，并在相关承诺或响应前完成要求的持久化。快照、日志覆盖及消息发送顺序也不能凭经验自由调整。有的实现允许特定流水线优化，但前提是满足它声明的依赖关系；不能推导成所有消息都可先发、数据都可稍后写。磁盘错误时必须向协议层报告并停用不可信节点，不能把写失败折叠成成功 ACK。

## 第 6 层：提交后还没执行就崩溃

**面试官：** 假设 101 确实已提交，但主节点还没执行就崩溃，客户拿到的受理承诺如何兑现？

**面试者：** 新节点从快照 100 恢复，再通过协议确认提交前缀包含 101，按相同规则执行它。因为命令携带完整业务输入，S1 的原状态来自快照，101 会生成相同订单结果和稳定成交 ID。这里不需要“补偿一条全新下单”，只需继续应用原命令。若执行发现不支持的历史规则或内部不变量破坏，要停止服务并修复执行能力，不能删除已提交命令绕过去。可靠受理保证的是必须完成这个有序处理义务，不保证软件永远没有 bug，更不允许失败后静默遗忘请求。

## 第 7 层：执行了却还没返回

**面试官：** 101 已执行产生全成结果，但回包丢了，客户端重试会不会又进入一条新日志？

**面试者：** 可以出现第二条承载同请求键的已提交命令，但只能有一次业务效果。状态机保存 `requestKey + payloadHash + 原结果`，第一条应用完成后，后续同键同摘要只复用结果并推进 A，不再撮合；同键异摘要返回冲突。这样入口缓存丢失、请求落到新主、并发重试都不会绕开去重。基线以首个实际执行的命令位置确定成交 ID，重试不能用新索引重新编号。请求表也必须进入快照，否则日志压缩后重试会失去识别原事实的能力。

## 第 8 层：持久化批处理能否降低延迟

**面试官：** 多数刷盘会拉高延迟，如果按一批命令一起同步，可靠语义是否会变？

**面试者：** 正确的 group commit 不改变语义，只共享同步成本。先把一批条目完整写入，完成要求的同步，再使这一批进入可计数的持久确认路径；每个请求仍等待协议提交和所需应用位置。要限制批次大小和最大等待时间，否则吞吐提高却拉长低负载延迟或 p99。队列必须有界，并在磁盘变慢时背压入口，不能为了避免超时提前发可靠 ACK。批内某条写入失败或记录不完整时，必须识别可靠边界，不能让整批靠一个内存标记假装都持久化了。

## 第 9 层：多数都在同一故障域怎么办

**面试官：** 两个持久 ACK 都来自同一个机房，机房断电并永久丢盘，所谓 RPO 为零还成立吗？

**面试者：** 不一定。零丢失只能针对明确故障范围与真正独立的持久副本。三节点同故障域部署可以应对单节点损失，但不自动应对整个机房永久丢失；云盘快照的异步时间差也不能变成同步多数。若业务要求跨域容灾，就要重新安排投票与存储故障域、确认路径和灾备恢复契约，接受跨域延迟及成本。超出承诺的多副本永久损失必须按灾难事件报告影响范围，从可信备份和外部证据恢复，不能强选一个落后副本后继续沿用“已确认数据绝不丢”的说法。

## 第 10 层：用什么证据检查确认实现

**面试官：** 我不想只听协议名。怎样检查接口确实没有提前确认？

**面试者：** 为请求关联提出位置、持久化完成、协议提交、业务应用和响应时间点，并用故障窗口挑战顺序。若在本机同步前、仅少数副本成功时切断主节点，不能观察到可靠受理成功；在提交后响应前崩溃，重试必须找到原处理义务；在执行后回包前崩溃，必须返回原结果。还要检查存储失败是否进入 ACK 统计、账户完成是否被误用作撮合提交证据。这些是应实施的验证设计，不是本文已经运行的测试。最终证据应证明承诺与故障模型匹配，而非只展示正常路径吞吐。

## 本题收束

- **讲透的机制：** 可靠受理是可继承的提交承诺；具体业务结果要等应用，账务完成另有事务边界。
- **最易答错：** 将 channel、write 返回、本机 fsync、任意两份旧任期副本分别当成同一提交条件。
- **反例检验：** 只有旧主本机保存 101 时强制更换节点；若客户端已收到可靠成功却无法恢复 101，承诺与实现不符。
