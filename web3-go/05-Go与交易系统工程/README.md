## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 交易系统工程 | 让下单、成交、资金处理在并发、重试和故障下仍有明确结果的一套技术方法。 | 不是只会写一个撮合函数，也不是堆中间件名字。 |
| 状态所有权 / owner | 规定某份业务数据最终由谁裁决、谁有权修改。 | 订单簿、账户、链上状态可能属于不同职责，不能谁方便谁改。 |
| 业务不变量 | 无论请求怎样交错，都不能被破坏的业务底线。 | 例如同一笔资金不能花两次、已成交数量不能又被当作未成交退款。 |
| goroutine / channel / mutex / atomic | Go 的并发任务、通信通道、互斥锁与原子操作。 | 管内存协作，不自动提供落盘、断电恢复或跨服务资金一致性。 |
| 数据结构 / 网络 IO | 前者决定怎样组织和查找数据，后者负责收发数据。 | 簿索引、撤单定位、协议读写都要放回完整交易链路分析。 |
| 背压 / 有界队列 | 下游跟不上时，限制继续接进来的工作，避免积压无限增长。 | 不能只是把 channel 堵住，再额外开无数 goroutine 等它。 |
| GC / 尾延迟 | Go 回收无用内存；尾延迟关注少数特别慢的请求。 | 平均耗时降低，不代表最慢的一批订单或撤单变快。 |
| 事务 / 唯一约束 / 索引 | 共同提交一组写入、防止重复业务身份、帮助定位数据的不同机制。 | 索引快不等于记账正确；事务也必须说明覆盖哪些事实。 |
| Redis / 缓存 | 保存便于快速读取或协调的数据副本与辅助状态。 | 本模块不默认它是资金真相源，缓存余额不能直接授予花费资格。 |
| 可靠事件 / 幂等 | 重要业务事实可继续交付；同一业务重试不会再次产生经济效果。 | 消息可能重复，仍要把稳定身份与实际业务写入绑定。 |
| Outbox / CDC | 前者把待交付事件与业务事实一起记下；后者从数据库变更中提取交付内容。 | 都要说明提交与交付的边界，不能把发出消息等同于下游已记账。 |
| 日志 / 快照 / 回放 | 留下处理依据、保存某个进度的状态、按依据重新恢复。 | 用来兑现已确认业务的恢复承诺，不是普通打印日志就够了。 |
| 水位 / 同水位对账 | 水位是“已经处理到哪里”；对账要比较同一段业务范围。 | 账务只到 100、成交已到 102，不能直接把两者的最新读数判成错账。 |
| 主备 / 围栏 | 备用实例接管工作；实际写入端拒绝已失权的旧实例。 | 宣布新主上线不等于旧主不能再写。 |
| 可观测性 / 故障复盘 | 看见业务进度与异常，再把故障原因转成可验证的防复发动作。 | 有日志不等于能定位，有复盘文字不等于回归验证完成。 |
| MVP / 教学推演 / 工程验证 | 最小示例、纸上走流程、真正运行实现取得证据，三者不同。 | 本模块不把伪代码、目录完整或预期数字当作实际测试结果。 |

## 把整篇文章压缩成一个故事

小林负责一个 Go 交易后端。用户先下买单，随后撤单，但页面一边显示“已撤”，另一边仍显示资金预留。小林不能直接把余额加回去：先要确认订单由谁裁决、成交与撤单谁先进入权威顺序，以及账务究竟处理到哪里。这是第一个专题要建立的状态所有权问题，不是一把锁就能包办。

查清原来是账务落后之后，小林继续沿链路排查：队列是否积压、网络是否卡住、对象分配是否拖长尾延迟，对应第二个专题；资金与去重是否共同提交、缓存是否返回旧值，对应第三个专题；成交通知能否补发、重复通知会不会再扣一次钱，对应第四个专题。优化必须让这些业务保证继续成立，不能为了快就提前承诺成交或丢掉撤单。

如果服务此时重启，第五个专题要求从可信日志和快照恢复，并在写入端挡住旧主；第六个专题则要求用不变量、进度、故障窗口和回归证据判断是否真的恢复。整份导航的读法就是：先说明哪种交易、要保护什么事实，再选工程工具，最后给出与承诺相匹配的验证；不要把“用了 Go、Redis 和消息队列”当作交易系统已经可靠。

## 二、使用方式

1. 从[交易业务全景](../00-交易业务全景/README.md)确定产品、成交机制、资产控制和结算方式。
2. 选择一个交易问题，先明确状态、不变量和故障承诺，再进入本模块选择工程实现。
3. 复用[旧版 Go 核心能力导航](../../深入/01-Go-P7核心能力/README.md)和[撮合交易从 0 到 1](../01-撮合交易与核心链路/01-撮合交易从0到1/README.md)，不重复维护整套基础材料。
4. 根据[P0 与 P1 补齐规划](../00-交易业务全景/01-P0与P1目录补齐规划.md)逐步补充问答，涉及资金、持仓和链上状态时引用对应业务专题。

## 三、共同边界

- Go 并发原语不能代替持久化与一致性协议；使用 channel 不等于请求已经可靠受理。
- 数据库、缓存和消息队列先说明用途与失效边界，不假设 Redis 是资金真相源或消息队列保证业务恰好一次。
- 日志回放、数据库恢复、链上事件重扫和业务对账是不同职责，需要衔接而不能相互替代。
- 性能分析同时给出正确性约束、负载和指标口径；教学伪代码、手工推演与实际测试结果分别标注。
