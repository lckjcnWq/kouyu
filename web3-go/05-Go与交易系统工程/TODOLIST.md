# Go 与交易系统工程：大白话导读任务清单

## 目标与范围

面向懂一些 Go 或后端开发、但尚不熟悉交易系统工程边界的读者，为本目录下全部 **86 个现有 Markdown 文件（79 篇正文 + 6 篇专题 README + 1 篇模块 README）** 添加前置导读。本文是执行清单，不属于待添加导读的业务文章。

每个文件在原有一级标题之后、原正文之前增加：

1. **先看懂：关键词大白话解释**：用表格解释本文的交易名词、Go 原语、英文缩写、公式符号及关键工程概念，说明在本文中的具体含义。
2. **把整篇文章压缩成一个故事**：沿一个具体人物或系统事件串起起因、处理过程、结果和不能理解错的边界。

## 编写与验收标准

- 保留原有标题、正文、链接、公式、问答和教学伪代码，不借导读改变原文规则。
- 各篇导读独立可读，不用“同上”代替解释；词表按本文内容选择，不机械复制通用名词。
- 先解释业务需要保护什么，再解释工程机制如何保护；每个类比都要说明适用范围。
- 区分可靠受理、撮合裁决、结果持久化、账务提交、查询投影与客户端收到回报，不能用“成功了”混称。
- 区分 Go 内存可见性、互斥、业务原子性、持久化和跨服务一致性；channel、mutex、atomic、单写者均不能跨层背书。
- channel 发送不等于深拷贝、消费完成或可靠受理；context 超时不等于撤单，取消信号不等于 goroutine 已退出。
- 成交与撤单沿同一权威顺序裁决；预留只按已经确定的实际义务消耗或释放，不能按请求超时或陈旧查询自行退款。
- 有界队列不能把无界积压转移到 goroutine、持久日志或慢消费者；撤单保留容量不等于允许撤单越序。
- 区分算法复杂度、吞吐与尾延迟；对象池、批处理、分片、GC 和网络优化必须保留原有正确性边界，不泛化示例指标为生产结论。
- 数据库语义按原文数据库与隔离级别说明；唯一约束、条件更新、事务、索引、Redis 缓存和分布式锁各自有明确保证范围。
- 区分提交未知与确定失败；幂等依赖稳定身份、相同载荷与效果提交边界，不把消息交付的“恰好一次”当作跨系统经济效果唯一。
- 区分 Outbox、CDC、消息确认与业务事务；重放、补偿、冲正不是同一种操作，跨分片与外部副作用不能伪装成单库事务。
- 区分快照水位、已提交日志前缀、回放规则版本、账务进度和链上最终性；同水位对账不能被“最新查询”代替。
- 围栏必须在实际写入边界拒绝旧执行者；租约过期、关闭 channel 或宣布切主不能单独证明旧主已失权。
- 保留各专题自己的产品、单位、规则和部署前提；不把现货、衍生品、链下撮合与链上结算案例混用。
- 用结构检查验证每个已完成文件均有且只有一套前置导读；与修改前工作区快照比较，确认原文逐字保留，未处理文件保持不变。
- 检查新增 Markdown 表格、相对链接和故事算式；完整记录本批范围、剩余任务及复利规则。
- 静态检查、手工推演和实际工程测试分开记录；不创建 Go 工程，不声称执行过 race、数据库故障注入、主备演练或性能测试。
