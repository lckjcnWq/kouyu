## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 现货 ETH/USDT / GTC | 用 USDT 买卖实际 ETH；GTC 限价单在成交、撤销等确定结果前可继续挂单。 | 本例无费用、杠杆或链上结算，不能套用永续仓位和强平规则。 |
| 手 / 价格单位 | 手是本例人为约定的数量单位，不是所有平台统一单位。 | 1 手 = 0.1 ETH；100 USDT/手 = 1000 USDT/ETH。 |
| owner / 单写者 | 某份可变状态只有一个受控修改入口。 | 每市场一个 goroutine 改簿；它没有随意修改账户余额的权限。 |
| 账户逻辑 owner | 全部账户写路径共同遵守的裁决与串行化契约。 | 多个实例靠同库事务、账户行锁和约束配合，不靠各自的本地锁。 |
| 可用 / 预留 / reservation | 可用是还能分配的资金；预留是已为订单占住的额度；reservation 记录归属与去向。 | 预留 1000 不是花掉 1000；之后分别支出 400、释放 600。 |
| T_admit / Accepted | 把身份、资金预留和有序命令一起提交的受理事务；Accepted 只承诺可靠接下。 | 不承诺已经成交、挂簿完成或账户结转完毕。 |
| cmdSeq / appliedSeq | 命令在本市场的权威位置，以及结果已经提交到的位置。 | 主例已有进度 100，接着处理 New101、Cancel102，不按通知先后跳步。 |
| T_result / OutcomeBatch | 提交某条命令完整裁决的事务，以及承载该裁决的结果批次。 | 成交、订单变化、释放义务、outbox 和执行进度一起确定。 |
| T_ledger / cursor | 将资产变化与去重一起记账的事务，以及账务已完成位置。 | 必须先记 101 的成交，再记 102 的撤单释放；可以暂时落后执行进度。 |
| Outbox / ExecutionReport | 待可靠交付的记录，以及面向用户的执行回报。 | 回报说撤了 6 手，不代表 600 USDT 已经可用。 |
| 不变量 / 线性化点 | 必须守住的业务等式，以及某项承诺可以视为正式生效的时刻。 | 数量须满足 10=4+6+0；受理生效与最终撤单生效不是同一承诺。 |
| happens-before / 可见性 | Go 同步规则保证写入在另一个读取前可见。 | 不替代复合业务原子性，也不保证进程退出后数据仍在。 |
| channel / 对象别名 | 通道传递值；不同引用可能仍指向同一份可变数据。 | 发送带 slice、map 或指针的结构体不等于深拷贝或持久受理。 |
| 不可变快照 / 投影 | 固定某个已提交进度的只读值，以及面向查询整理出的视图。 | 不能带着仍会被 owner 修改的订单指针冒充只读。 |
| context / Cancel | 前者控制等待和任务生命周期，后者是有业务顺序的撤单命令。 | 客户端超时不会把已经提交的订单自动撤掉。 |
| 背压 / 工作池 / 生命周期 | 限制新工作、约束并发任务，并明确任务何时退出及由谁接手。 | 既防无界积压，也不能把已受理责任随连接断开丢掉。 |
| epoch / baseVersion / 围栏 | 执行者任期、任务所依据的状态版本，以及实际写入端的失权拒绝。 | 挡住迟到任务和旧 owner；事务外查一次版本不够。 |
| race / 手工 MVP | 数据竞争检测，以及用极小状态演示规则的教学模型。 | 没有 race 不代表业务正确；文末内存推演不实现完整数据库与恢复保证。 |

## 把整篇文章压缩成一个故事

小林有 1500 USDT，想买 10 手 ETH，每手 0.1 ETH、价格 100 USDT。系统先在 T_admit 中共同写下请求身份、1000 USDT 预留和 New101，才回复 Accepted；小林此时可用 500，但还不能据此认为已经买到币。每个市场的 owner 按日志处理，在 101 中与卖方成交 4 手，再在 Cancel102 中撤掉剩余 6 手，各自完整裁决都必须先通过 T_result 提交。

页面可以先显示“成交 4 手、撤销 6 手”，账务却暂时没跟上。账户域先处理 101，支出预留里的 400 USDT，给小林记入 0.4 ETH，并给卖方记入 400 USDT；再处理 102，释放其余 600。最终小林可用 1100、预留 0，订单数量是 10=4+6+0。查询投影只是展示相应进度，不能一看到撤单就自行全额退款。

如果小林中途断网，只能恢复原请求的结果，真想撤单仍要提交 Cancel；如果通知丢了，owner 从日志补读；如果结果提交未知，该市场先停住推进与新状态发布，再查清持久事实。工作池不能越权改簿，旧 owner 不能绕过写入围栏，停机还要有人接住已受理责任。本文把这些边界逐题展开，最后只用内存 MVP 手工演示一小段规则，不宣称已实现或测试完整交易系统。

## 一、文字全流程

### 1.1 讨论基线：先确定谁有权修改什么

- **产品与交易机制：** 链下托管现货 ETH/USDT 订单簿，价格时间优先，只支持 GTC 限价单。无手续费，不讨论杠杆、持仓、AMM 或链上结算。
- **精度：** 案例以 1 手 = 0.1 ETH 计数量，以整数 USDT 计金额；100 USDT/手即 1000 USDT/ETH。生产系统应根据产品精度选择整数单位并检查乘法溢出，不能照搬案例精度。
- **执行所有权：** 一个服务进程内，每个市场一个 owner goroutine，独占该市场的订单簿、订单剩余量和撮合订单状态。其他 goroutine 只能提交命令、只读不可变快照，不能持有可写订单指针。
- **账户所有权：** 账务服务是账户状态的逻辑修改入口，以同一个 PostgreSQL 数据库的事务、行锁和约束保护所有实例；不是「每个实例各有一个 mutex」就足够。接入预留也是该账户域提供的事务能力，不允许接入层直接改缓存余额。
- **可靠边界：** 受理日志、资产预留、成交结果、账务各有明确的数据库提交点。channel 只作内存通知或受控队列；发送成功不代表可靠受理。
- **取消与超时：** context 控制等待和任务生命期；撤单是独立的业务命令。客户端停止等待不会自动撤销已经受理的订单。
- **讨论部署：** 基线仅一个活动市场 owner，后续通过明确增加第二个实例讨论围栏与交接。数据库提供所需事务语义；数据库灾难恢复承诺需另外配置复制与备份，不由 Go 原语提供。

### 1.2 一笔贯穿业务

A 初始有 1500 USDT 可用，0 ETH。B 的卖单 S1 已在 ETH/USDT 订单簿中：4 手，即 0.4 ETH，价格 100 USDT/手；对应卖资产已预留。主线开始时，S1 所在状态已有可信持久依据，市场 appliedSeq=100；下文从命令 101 继续处理。

A 发送买单 O1：限价 100 USDT/手，数量 10 手，即 1 ETH，需要预留 1000 USDT。该 New 命令获市场序号 101，成交 4 手、花费 400 USDT，余下 6 手挂单。随后 A 的 Cancel 命令获序号 102，撤销实际剩余的 6 手。

```text
A 提交 O1〔请求身份、账户、市场、买入、100 USDT/手、10 手〕
    ↓
接入 goroutine：鉴权、精度校验、有界准入、构造不可变请求
    ↓
账户域与排序入口执行 T_admit
    ├─ 检查请求身份与载荷，锁定市场控制行及账户行
    ├─ A 可用 1500 → 500 USDT，预留 0 → 1000 USDT
    └─ 同一事务写入预留身份和 New 命令 seq=101
    ↓ 事务提交后，才可返回 Accepted〔可靠受理，不是成交完成〕
唤醒市场 owner；通知丢失时，由日志扫描补读
    ↓
owner 按已提交市场序号取命令，独占修改订单簿
    ├─ O1 与 S1 成交 4 手，O1 剩余 6 手
    └─ 产生完整结果批次 OutcomeBatch(101)
    ↓
T_result：检查 epoch 与 expected appliedSeq
    └─ 同一事务提交结果批次、outbox 和 appliedSeq=101
    ↓
发布 ExecutionReport 与不可变查询快照〔携带市场序号〕
    ↓
账务消费者按市场连续批次执行 T_ledger(101)
    ├─ 消耗 A 的 400 USDT 预留，给 A 记入 0.4 ETH
    ├─ 消耗 B 的 0.4 ETH 预留，给 B 记入 400 USDT
    └─ 双边账、去重记录与账务游标共同提交
    ↓
A 提交 Cancel(O1) → 持久排序 seq=102 → owner 撤实际剩余 6 手
    ↓
T_result(102) 提交撤单结果与应释放的 600 USDT 预留
    ↓
T_ledger(102) 释放 600 USDT；发布明确的账务处理进度
    ↓
最终：O1 成交 4 手、撤销 6 手、剩余 0 手
      A 可用 1100 USDT、预留 0、ETH 0.4；B 收到 400 USDT
```

订单回报不必等账务完成才发布，但必须标明依据的是已提交的执行结果，而非「余额已经到账」。账户页只能根据账务提交后的投影显示资金，不能看到 Canceled 就自行增加可用余额。

### 1.3 独立异常分支

以下分别改变主案例的一个条件，不把它们连续叠加成另一笔交易。

```text
参数错误或资金不足
    → T_admit 不提交预留和 New 命令 → 返回明确拒绝

T_admit 调用超时，提交结果未知
    → 保留原 account + requestID 与载荷 → 查询该请求的持久受理结果
    → 不换新身份盲重试，不因客户端超时擅自释放

Accepted 已返回，但 channel 通知丢失
    → owner 根据 durable appliedSeq 继续扫描命令日志
    → 通知丢失不等于命令丢失

后续买单与 Cancel 竞争 S1 或 O1
    → 比较同市场权威命令顺序 → 各自在执行点读取实际剩余量
    → 不由 HTTP 到达时间、select 分支或回报先后裁决

T_result 失败或提交未知
    → 停止该市场继续推进和发布新状态 → 查询结果批次与 appliedSeq
    → 已提交则采用原结果；未提交则从可信前缀恢复再处理

撤单结果已提交，但 T_ledger 处理延迟
    → 允许订单已撤、资金仍预留的暂态
    → 重试连续账务批次；禁止跳过成交批次直接释放原始预留
```

### 1.4 状态与完成条件

| 阶段 | 订单与执行状态 | A 可用 USDT | A 预留 USDT | A 已记账 ETH | 阶段承诺 |
|---|---|---:|---:|---:|---|
| 初始 | O1 不存在 | 1500 | 0 | 0 | 尚未受理 |
| T_admit 提交 | O1 命令已可靠受理，未必执行 | 500 | 1000 | 0 | Accepted |
| T_result(101) 提交，账务未处理 | 执行事实为成交 4、剩余 6 | 500 | 1000 | 0 | 成交裁决确定，记账可能落后 |
| T_ledger(101) 提交 | 成交 4、剩余 6 | 500 | 600 | 0.4 | 本批成交记账完成 |
| T_result(102) 提交，释放未处理 | 成交 4、撤销 6、剩余 0 | 500 | 600 | 0.4 | 撤单裁决确定 |
| T_ledger(102) 提交 | 同上 | 1100 | 0 | 0.4 | 本案例资产处理完成 |

若两次执行结果均已提交而账务尚未消费 101，账户仍可能是 500 可用、1000 预留、0 ETH；消费者必须先处理 101 再处理 102。表格不承诺回报、投影和账务具有同一瞬间的全局快照。

## 二、核心板块

| 板块 | 为什么核心、拥有什么状态 | 与上下游的契约 |
|---|---|---|
| 可靠受理与账户预留 | 防止跨市场重复使用余额；拥有请求身份、预留与命令受理事实 | 原子提交预留与 New，成功才承诺 Accepted |
| 市场状态 owner | 决定成交与撤单的唯一裁决；拥有可变订单簿和订单状态 | 按已提交序号转换，不接受绕过 owner 的指针写入 |
| 同步与对象交接 | 决定初始化是否可见、内存对象是否被并发改写 | 明确 happens-before 与可变别名；不把发送当深拷贝 |
| 执行结果与账务交接 | 防止成交丢失、重复记账及过早释放 | 完整结果批次先提交，账务去重与资产变化共同提交 |
| 队列与任务生命周期 | 决定过载、超时和退出能否收敛 | 准入有界、已受理不丢、取消可退出、停机可恢复 |
| 所有权扩展与验证 | 防止分片、换主与优化破坏原保证 | 按不变量分片、写权围栏、竞争时序与历史验证 |

## 三、核心 20%

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 权威状态与单修改入口 | 全链路 | 先确定决策权再选择原语 | 每层都能改状态，锁再多也不一致 | owner、命令、投影、账户域 |
| 业务原子范围与线性化点 | 受理、执行、记账 | 定义哪个结果先发生及何时不可撤销 | race-free 仍超买、双重终态 | 检查和写入一起提交、命令序号 |
| happens-before 与别名治理 | goroutine 交接 | 发布可见性不等于后续互斥 | 半初始化读取、slice 与池对象被复用 | channel、锁、atomic、不可变快照 |
| 数量与资产不变量 | 成交、撤单、释放 | 将正确性变成可推演约束 | 负剩余、成交后全额退款 | 10=4+6+0、预留去向 |
| context 与业务命令分离 | 超时与停机 | 等待生命期不等于业务生命期 | 请求超时后释放但原单迟到执行 | 独立请求身份、服务托管任务 |
| 有界工作与背压 | 入队、异步处理 | 限制 goroutine、字节数及持久积压 | 无界排队拖垮所有市场 | 准入点、字节预算、公平性 |
| 版本检查与写权围栏 | 异步回写、owner 迁移 | 防旧任务或旧主修改新状态 | 迟到校验覆盖撤单、新旧双主 | epoch、baseVersion、appliedSeq |
| 恢复与验证边界 | 提交未知、崩溃、验收 | 内存同步不能穿越进程消失 | 已确认命令丢失或重复结算 | 持久前缀、去重、历史与故障窗口 |

不扩写订单簿算法、数据库索引调优、共识实现或链上 nonce 教程；但本专题依赖的账户事务、结果提交和旧 owner 隔离必须说明，不能用相邻专题名称代替机制。

## 四、设计与规则：全部问答的共同前提

### 4.1 业务规则与不变量

1. 对每个订单：`原始手数 = 累计成交手数 + 累计撤销手数 + 当前剩余手数`，各项非负。终态订单剩余为 0，不能重新挂回订单簿。
2. 同一市场命令按已提交 `cmdSeq` 连续处理；同价时间优先采用权威接纳顺序，不按 goroutine 调度顺序。
3. 每笔成交只有一个稳定身份，例如 `(market, cmdSeq, tradeIndex)`；重复交付不产生第二次经济效果。
4. 账户可用余额不得为负。买单预留被明确分为「仍冻结、成交支出、已释放」；案例 `1000 = 0 + 400 + 600 USDT`。买卖两侧转移分别守恒，不把 ETH 和 USDT 相加。
5. 账户记账只能消费完整、连续的市场结果批次；撤单释放仅依据裁决时的实际未成交量。价格改善等情形需额外计算价差释放，本案例成交价等于限价，不隐藏这项差异。
6. 任何对外承诺的已受理命令与已确定执行结果，必须有与承诺匹配的持久记录。锁、channel、atomic 和 goroutine 结束都不是持久记录。

### 4.2 架构与职责

```text
并行接入 goroutine
    │ 不可变输入；受控并发
    ▼
账户域 + 市场持久排序入口〔T_admit / Cancel 追加〕
    │ PostgreSQL：市场命令日志、预留、请求身份
    │ channel 只唤醒，日志才可恢复
    ▼
每市场一个 owner goroutine
    │ 唯一可变簿；连续 cmdSeq；校验异步返回的版本
    ▼
结果持久化〔T_result：batch + outbox + appliedSeq，校验 epoch〕
    ├─ 不可变快照 → 查询；ExecutionReport → 用户
    └─ 连续 OutcomeBatch → 账务服务〔T_ledger〕
                              │ 双边资产、预留、去重、cursor
                              ▼
                         账户查询与资金处理结果
```

接入与非权威预处理可并行；同市场改变订单簿的状态转换串行。各市场可并行，但涉及同账户的资产竞争必须进入同一账户事务约束。数据库 I/O、外部 RPC 与行情推送不得反过来取得订单指针直接写簿。

### 4.3 核心对象与字段

| 对象 | 必要字段与约束 |
|---|---|
| RequestRecord | account、requestID、规范化 payloadHash、处理身份与状态；同身份不同载荷拒绝 |
| Reservation | reservationID、account、orderID、asset、original、consumed、released、held；与受理原子绑定 |
| MarketControl | market、lastCommittedSeq、appliedSeq、ownerEpoch；每市场受理顺序与结果进度 |
| Command | market、cmdSeq、requestID、New/Cancel 等类型、orderID、reservationID、规则版本与规范化业务输入 |
| Order | orderID、account、side、limitPrice、originalLots、filledLots、canceledLots、remainingLots、version |
| OutcomeBatch | market、cmdSeq、epoch、规则版本、完整成交与订单变化、预留处理指令；即使无成交也有处理结果 |
| Trade | 稳定 tradeID、买卖 orderID、数量、价格；不可由交付重试生成新身份 |
| ReadSnapshot | market、appliedSeq、不可变的订单/盘口值；内部引用也不得继续被写 |
| AsyncResult | jobID、orderID、epoch、baseVersion、opSeq、值或错误；仅 owner 校验后决定采用 |

### 4.4 三个本地提交边界与锁序

- **T_admit：** 先锁市场控制行，再按账户稳定顺序锁相关账户行；检查幂等和资产，原子提交请求身份、资产预留、reservation 与带序号的 New。Cancel 也经过市场控制行排序，不重复预留。序号来自控制行事务递增而非直接用可能产生空洞的数据库 sequence；回滚不消耗该市场的已提交命令位置。它是教学可行方案，代价是每市场排序行的竞争。
- **T_result：** owner 按命令顺序计算批次，事务检查有效 `ownerEpoch`、`appliedSeq == cmdSeq-1`，共同写入完整批次、outbox 和新的 appliedSeq。同事务锁住/条件更新控制行，不能仅在事务外读一次 epoch。提交后才允许发布执行结果；已提交同序号批次必须返回原事实而非覆盖。
- **T_ledger：** 按市场账务游标先锁消费进度，再按账户稳定顺序锁买卖双方账户，原子提交双边记账、预留变化、批次去重与账务游标。它不在持有账户锁时回取 MarketControl。不同市场各有游标，同账户仍由数据库行锁约束。

同一次受理事务中的检查与写入不能拆成两个本地临界区。上述事务是一个数据库内的局部原子边界，不宣称受理、撮合、账务和回报是一笔全局事务。允许结果已确定而账务暂时落后，不允许账务凭猜测先释放。

容量约束与业务顺序分开：受理事务可共同检查持久积压配额；GTC 潜在/活跃挂单还需独立名额，不能在 New 命令处理完但订单仍挂簿时归还。New 与 Cancel 可预留不同准入容量，但进入日志后仍遵守相同 cmdSeq 顺序，详见母题 08。

### 4.5 内存交接、失败与恢复规则

- 命令交接采用值对象或明确转移访问权的协议；包含 slice、map、指针时，结构体按值复制并不是深拷贝。sender 在交接后停止修改，或复制所有仍会被修改的可达数据。
- 内存状态先计算、结果尚未提交时，不得发布为权威快照。结果提交失败或未知则冻结本市场推进与新状态发布，查询持久批次和 appliedSeq，从可信快照与日志恢复；不在不确定状态上继续接受下一次簿转换。
- 已受理任务由服务生命期托管；客户端断开只结束等待。业务撤单必须追加 Cancel，并与成交按同一顺序竞争。
- 换 owner 必须在持久写入边界校验 epoch；租约超时、停止续租、关闭本地 channel 均不能单独证明旧写入者已失去权限。

## 七、工程实践——一个简洁 MVP

### 7.1 目标与范围

只验证「同一 owner 串行处理两笔并发占资意图，以及成交后撤实际剩余量」的小闭环。**为手工推演，MVP 故意把单账户资金与单市场订单折叠到一个内存 owner**，不声称实现正文中分离的账户域、PostgreSQL 事务、可靠受理、结果交付、崩溃恢复或主备围栏。

输入顺序由教学命令序列明确给出，不把 channel 的竞争发送顺序当成业务优先级；金额使用整数，数量使用手。

### 7.2 一段核心伪代码

```text
状态：available=1500，held=0，spent=0，receivedETHLots=0
      orders={}，nextSeq=1
对明确有序的每个命令 c，由唯一 owner 执行：
    若 c.seq != nextSeq：停止，报告输入缺口
    若 c.kind == New：
        need = c.pricePerLot * c.lots     // 正整数；生产需检查溢出
        若 orders 已有 c.orderID：输出 Duplicate，不再次预留
        否则若 available < need：输出 Rejected，不修改余额
        否则：
            available -= need；held += need
            orders[c.orderID] = {original:c.lots, filled:0,
                                 canceled:0, remaining:c.lots, price:c.pricePerLot}
            输出 Accepted
    若 c.kind == Fill：
        o = orders[c.orderID]
        若 o 不存在 或 c.lots <= 0 或 c.lots > o.remaining：输出 Rejected
        否则：                         // MVP 成交价固定等于买单限价
            cost = c.lots * o.price
            o.filled += c.lots；o.remaining -= c.lots
            held -= cost；spent += cost；receivedETHLots += c.lots
            输出 Filled(c.lots, o.remaining)
    若 c.kind == Cancel：
        o = orders[c.orderID]
        若 o 不存在：输出 NotFound
        否则：
            n = o.remaining
            o.remaining=0；o.canceled += n
            held -= n * o.price；available += n * o.price
            输出 Canceled(n) 或 AlreadyTerminal〔n=0 时无新效果〕
    检查 available>=0，held>=0，available+held+spent==1500
    对每个 o 检查 o.original==o.filled+o.canceled+o.remaining
    nextSeq += 1
```

Fill 是教学输入，代表已经确定的匹配数量，不是向外开放「任意指定成交」的接口。这里省略卖方与双边记账，不能用 `receivedETHLots` 的局部变化证明双边资产守恒。Duplicate 也仅覆盖本次内存中的 orderID，不替代正文的请求身份与持久幂等。

### 7.3 输入与预期结果

每行是独立场景，除明确给出的命令序列外不继承其他场景状态。

| 场景 | 有序输入 | 手工推演的预期结果 |
|---|---|---|
| 主案例 | New(O1,10手,100) → Fill(O1,4手) → Cancel(O1) | 可用1100、held0、spent400、ETH记入4手；O1为成交4/撤6/剩0 |
| 两笔并发占资意图被排序 | New(O1,10手,100) → New(O2,10手,100) | O1占1000；O2见可用500而拒绝；可用500、held1000 |
| 撤单先于后续成交 | New(O1,10手,100) → Cancel(O1) → Fill(O1,4手) | 撤销10手并释放1000；后续Fill因remaining=0拒绝；可用1500 |
| 重复撤单 | New → Fill4 → Cancel → Cancel | 第二次撤单无新释放，仍可用1100，订单canceled仍为6 |
| 命令缺口 | New seq=1 → Cancel seq=3 | 在seq3处停止，不猜测缺失命令或继续执行 |

这些是伪代码的预期行为，不是已执行的测试结果。完整生产保证仍需验证数据库事务、未知提交恢复、双边记账和旧 owner 写入被拒绝等正文契约。
