# 大问题 13：race 检测通过为什么还不够，怎样验证交易并发正确性？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| data race / race detector | 缺少必要同步的冲突内存访问，以及查找实际执行中这类问题的工具。 | 本次没报错不覆盖所有未执行路径，更不认识交易业务规则。 |
| race-free / 业务原子性 | 没有数据竞争，与整次业务检查修改不可被拆散，是不同要求。 | 读取余额和扣款各自加锁，仍可能让两笔订单都基于旧余额获批。 |
| 临界区 / 条件更新 | 一起受保护的操作范围，以及条件满足才执行的原子写入。 | 正确边界须包含检查与预留，还须共同写入受理依据。 |
| 不变量 / original | 始终成立的业务约束，以及一笔订单或预留的原始总量。 | 订单 10=4+6+0；预留 1000=支出400+释放600+仍冻结0。 |
| tradeID / 双边经济效果 | 成交稳定身份，以及买卖双方对应的资产变化。 | 同一成交重投只能记一次，ETH 与 USDT 分别核对，不能跨单位相加。 |
| cursor / 阶段断言 | 已处理位置，以及根据当前阶段判断什么必须成立。 | 订单已撤而账务仍落后时，不错误要求余额已经到最终 1100。 |
| 并发历史 / 线性化 | 记录调用与响应、裁决和提交位置，检查能否对应合法的顺序操作。 | 最终余额碰巧对了，也可能曾经发出互相矛盾的成功承诺。 |
| Accepted / 最终结果 | 可靠接下意图的中间承诺，以及业务已确定的执行结果。 | 不能用 Accepted 当成最终撤单成功来裁定后续成交非法。 |
| 投影 / 水位 | 面向查询的视图与它已经追到哪里。 | 允许滞后的查询按真实进度验证，不强称所有读都实时线性一致。 |
| T_admit / T_result / T_ledger | 受理、执行结果与账务的三个本地事务边界。 | 每个边界分别检查提交前失败、提交后回包丢失和重复恢复。 |
| 提交未知 / 稳定身份 | 暂时不知道是否提交，以及重试不变的请求、命令、成交或批次身份。 | 查原事实再决定接续，不能换编号重做经济操作。 |
| 背压 / 资源进度 | 限制新责任，同时观察任务、队列和连接能否继续收敛。 | 不重复记账但无限积压 goroutine，也不算系统正确。 |
| cancel / join / 对象池 | 请求任务退出、确认实际退出，以及复用对象的机制。 | cancel 返回不等于任务结束，worker 仍用着对象就不能先放回池。 |
| 屏障 / 随机种子 | 显式控制阶段顺序的信号，以及复现随机输入的起点。 | 不靠 sleep 猜时序；辅助同步也不能意外把目标内存竞争同步掉。 |
| epoch / 参考状态机 | 执行者任期，以及用于比较结果和历史的独立规则模型。 | 可受控暂停旧 owner 后切任期，检查旧写被拒，而非只看进程名字。 |
| 静态检查 / 手工预期 / 工程测试 | 检查文档、按规则推演、真正运行实现取得证据。 | 本稿只提供前两类材料和验证设计，不存在可凭它批准上线的实现。 |

## 把整篇文章压缩成一个故事

小林看到 race detector 没报错，准备说交易并发已经正确。复核时却找到一个不需要 data race 的超买历史：账户有 1500，两个任务各自加锁读到 1500，再各自加锁申请扣 1000。每次访问都有同步，整次“检查并占资”却被拆开。验证要用屏障让两次读取都发生在扣款前，检查真正业务边界，而不是只等工具报警。

把占资边界补好之后，还要沿 New101 成交 4 手、Cancel102 撤 6 手检查数量、预留去向、稳定成交身份和连续进度。最终可用 1100 USDT、得到 0.4 ETH 只是部分答案：还得确认没有先说撤单完成再让同一剩余量成交，也没有因提交回包丢失而重复下单、重复扣款。中间账务尚未追上时资金仍预留可以合法，不能拿最终数字套每个瞬间。

最后还要检查慢消费者、饱和队列、等待者离开、停机和旧 owner 隔离，既守住安全，也能结束任务、恢复推进。小林能报告什么，取决于真正取得了哪些环境、负载与故障证据；只读完面试稿、检查 Markdown 或手工算对故事，不能写成工程测试已通过。整篇教的是分层建立证据，而不是给一个不存在的实现贴上“绝对正确”的结论。

**流程位置与核心机制：** 覆盖内存竞争、业务原子性、完成历史、持久化故障窗口和生命期进度的分层验证。不是完整测试平台教程；只定义每种证据能证明什么、不能证明什么。

**必要前提：** 沿用总览的 O1 案例与三个事务边界。本专题只交付面试稿和一个简洁伪代码 MVP，不创建可运行工程；下列均为验证设计或手工预期，不是已经执行的测试报告。

## 第 1 层：race-free 能不能等于并发正确？

**面试官：** 你的 Go 交易服务跑完 race detector 没报错，能不能说并发模型已经正确？

**面试者：** 不能。第一层是内存访问是否有必要的同步，第二层是多个读写组合是否形成合法的业务操作，第三层是进程故障后承诺是否仍能恢复。race detector 主要发现本次执行路径中的无必要同步的冲突内存访问，不知道「A 只能花 1500 USDT」或「撤单不能释放已成交部分」。

即使本次没有报告数据竞争，也不能证明未执行路径或未出现时序没有竞争。即使程序真的无数据竞争，Go 的顺序一致性交错保证也不等于业务操作自动原子化：两个分别加锁的余额读与扣减，可以组成不合法的检查更新流程。报告要写清负载、执行范围与结论级别，不能把工具沉默写成整个交易系统的证明。

## 第 2 层：没有 data race 的超买反例怎样构造？

**面试官：** 你说所有字段都加锁仍会超买，能给一个明确时序而不是概念解释吗？

**面试者：** 可以。Balance() 加锁返回 A=1500，Debit() 也加锁执行扣减；两个请求各要 1000。T1 调 Balance 返回 1500 后解锁，T2 调 Balance 也返回 1500 后解锁，两者都认为资金足够，再分别调用 Debit。每次访问都在同一把锁下，仍可能得到 -500 或在业务已经承诺后才发现第二笔不能扣。

验证这个问题，应受控把两次读取都安排在第一次扣款之前，检查被测接口能否把「校验并预留」作为一个操作完成。修复后要么同一个临界区包含检查与修改，要么数据库条件更新/行锁事务实现同样的原子范围；不能仅把更多字段改为 atomic。预期是两笔 1000 最多成功一笔，且受理命令与预留同步存在。

## 第 3 层：正确性断言具体写什么？

**面试官：** 你构造出了超买，那对主案例需要哪些断言，不能只检查最后 HTTP 都返回成功吧？

**面试者：** 至少分四类。订单检查 `original=filled+canceled+remaining`、数量非负、终态不重新入簿；预留检查 `original=consumed+released+held` 且可用非负；成交检查稳定 tradeID 只产生一次双边经济效果；进度检查命令、结果和账务游标各自连续，不把受理位置误当执行位置。

主案例的预期是 O1 的 `10=4+6+0`，A 的 `1000=400+600+0`，最终可用 1100、ETH 0.4，B 取得 400 USDT。中间时点要按阶段断言：T_result(102) 已提交但账务仍落后时，资金可以仍冻结，不能错误要求每个采样瞬间都已达到最终余额。跨币种分别守恒，不把 0.4 ETH 与 400 USDT直接相加。

## 第 4 层：最终数字正确，为什么仍可能是非法历史？

**面试官：** 假如最后数量和余额都对了，是不是就能确认成交与撤单顺序正确？

**面试者：** 仍不够，两个错误可能在最后抵消，或者最终状态正确但曾向用户承诺互相矛盾的结果。需要记录操作的调用开始、响应结束、requestID、cmdSeq、执行结果和提交位置，检查能否构造一个符合既定状态机、且尊重已完成操作实时先后的顺序历史。

本模型还要区分 Accepted 与最终结果：Accepted 只是受理，不能拿它当最终撤单完成来约束随后成交；T_result 提交后的明确撤单成功则不能被后续命令再次成交同一剩余量。投影读取若承诺的是带序号的最终一致视图，就按进度与不倒退验证，而不是强行当所有查询都线性一致。验证器必须使用接口真实承诺，否则既会误报，也会放过真实违约。

## 第 5 层：怎样覆盖提交未知而不是只测函数报错？

**面试官：** 顺序历史在正常运行能成立，但你怎么验证事务超时后不产生第二个订单或第二笔记账？

**面试者：** 失败点应贴着真实提交边界，而不是随便让一个函数返回 error。对 T_admit、T_result、T_ledger 分别考虑提交前失败、提交成功后响应丢失、重复恢复三种情形。调用方观察到的超时相同，但数据库里的事实不同，恢复应先查原身份再决定下一步。

T_admit 已提交时重试必须回到同一 orderID、reservationID 和 cmdSeq；T_result 已提交时重取原批次，不能改成交身份重算后覆盖；T_ledger 已提交时重复交付无新资产变化。若确认未提交，则从可信边界继续原操作。检查既包括最终不重复，也包括原请求最终能查询和继续处理，不能通过永久卡住一切来换取表面上的安全。

## 第 6 层：如何验证 goroutine 退出和背压？

**面试官：** 你重视安全，但服务没重复记账却越跑 goroutine 越多，验证方法怎么补上？

**面试者：** 需要独立验证进度与资源边界：队列按项数和字节数有限，工作池并发有限，客户端离开后回复发送不会永久阻塞 owner；每个阻塞点有相应停止条件，取消后还要确认任务真正退出，而不是只观察到 cancel() 返回。停机期间检查所有生产者停止后才关闭公共输入通道，未处理持久命令可恢复。

验证场景包括慢消费者、永不返回但受超时约束的外部调用、等待者提前退出、队列持续饱和和停机截止到达。观察 goroutine 堆栈、队列年龄、持久积压、连接和计时器回收，区分正常长期 worker 与悬挂任务。不能靠一次 goroutine 数量相同证明没有泄漏，也不能在 worker 仍持有对象时 Put 回池来让内存指标好看。

## 第 7 层：并发测试怎样可重复而不靠 sleep 碰运气？

**面试官：** 那些临界窗口很短，你是多 sleep 一会儿、循环跑几千次，还是有什么更可靠的安排？

**面试者：** 对已知窗口优先用屏障和显式阶段信号，让两个任务都完成指定步骤再放行；例如把两次 Balance 读取都挡在 Debit 前，或让旧 owner 通过事务外检查后暂停，再让新 epoch 生效。不要用「睡 10 毫秒，估计另一个 goroutine 已经到位」作为主要同步。随机调度和不同并发度用于补充发现未知窗口，并记录种子与输入便于复现。

测试辅助信号也会引入 happens-before，设计时不能意外把想暴露的内存竞争同步掉。业务层可以用参考状态机与生成的操作序列比较历史，故障层需要真实事务边界或行为等价的受控环境。Go 1.21+ 基线不默认依赖后续版本专有的测试 API；无论哪种工具，都要区分可复现场景覆盖和穷尽证明，不能把跑得多等同于已经穷尽所有时序。

## 第 8 层：最后怎样写一份不夸大的验收结论？

**面试官：** 现在你需要向评审说明「这个并发方案可以上线」，哪些证据缺一不可，又怎样避免写成空泛保证？

**面试者：** 我会给出分层证据：状态所有权和锁/事务边界审查；指定测试与负载下的 race 结果；关键不变量及竞争历史检查；受理、结果、账务的未知提交恢复；背压、停机和旧 owner 隔离场景。每项记录环境、输入、故障点、观察结果与未覆盖条件，并说明生产容量与数据库故障假设。文档静态检查只说明文件结构，不替代这些执行证据。

若当前只有本专题，应明确写「已完成教学设计和手工推演，尚未执行工程测试」，不能批准一个不存在的实现上线。实际有执行结果时，也只能在证据覆盖的负载与故障范围内下结论；指标、失败与跳过项应原样报告。能指出保证的边界，比把 race、事务和对账三个词并列成「绝对正确」更有工程说服力。

## 本题收束

- **讲透的机制：** 内存同步、业务不变量、顺序历史、故障恢复与资源进度分别验证，再按真实承诺合并证据。
- **最容易答错：** race 无报告等于安全；最终余额相等就代表历史合法；cancel 返回代表 worker 退出；文档校验通过代表工程测试通过。
- **检验反例：** 两个并发请求分别加锁读余额和扣款，race detector 可以无报告，仍可能超买。这一个时序就能否定「race-free 就等于业务正确」的结论。
