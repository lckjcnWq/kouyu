# 大问题 12：怎样优雅停机并回收 goroutine，又不丢掉已经受理的交易责任？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 优雅停机 / drain | 停止新增责任，让已有工作排空，或停在能可靠接续的位置。 | 不是进程退出就算完成；交易可以待恢复，但身份、持久依据和接手人不能丢。 |
| T_admit / Accepted | 可靠受理事务与已经可靠接下请求的确认。 | 事务把幂等身份、预留和命令一起提交；已 Accepted 的命令不能因为关机变成没下过单。 |
| request context / service lifecycle | 前者管一次请求的等待和准备，后者托管服务已经接下的工作。 | 客户端离开不删除交易责任；持久受理尝试仍需服务级登记、有限期限和恢复安排。 |
| account / requestID / payloadHash | 账户、请求标识和业务载荷核对依据，共同定位原请求。 | 提交未知时按原身份查询或幂等重试，不能新建一笔独立订单来代替。 |
| 受理门闩 / 在途登记 | 把“还许不许新增”和“已经接下哪些尝试”放进同一个协调边界。 | 先登记再派发，关门后不再新增；不能只数 HTTP 连接来判断数据库受理是否结束。 |
| 提交未知 | 事务超时或丢回执，无法据此断言已经提交还是确定没提交。 | 保留原身份和核对责任；一次查询未找到，不足以排除原事务稍后提交。 |
| quiesce | 让生产者停止创建新工作，并确认它们已经静止下来。 | 停生产不等于停消费，owner 和必要回写接收者此时还要继续工作。 |
| cutoff / market control | cutoff 是本轮处理的明确持久边界，market control 是协调市场准入和顺序的控制记录。 | 本机关接入、channel 为空都不能代表全市场停了；未知受理超出边界后仍须被恢复接管。 |
| cmdSeq / appliedSeq / checkpoint | 命令序号、已完整提交结果的连续前缀，以及可恢复检查点。 | 若只停在已提交的 101，就保留 102 待恢复；不能把试算状态或半个批次放进检查点。 |
| owner / IO worker / 回写路径 | owner 裁决和管理簿，worker 做授权 IO，回写路径把完成信息交回来。 | 等 worker 结束时必须保留接收者，不能让 worker 等发送、协调者又等 worker。 |
| OutcomeBatch / T_result / epoch | 完整裁决包、持久提交它的事务、执行者的所有权代际。 | 事务同时校验期望 appliedSeq 和有效 epoch，完整提交结果后才能发布新快照与回报。 |
| outbox / T_ledger / cursor | 分别是持久待交付事件、账务事务、账务消费进度。 | 市场结果确认与账户入账分别记录；退出不要求远端立即全部完成，但剩余义务要有持久依据。 |
| close / sender | close 关闭通道，sender 是可能向它发送的任务。 | 由掌握全部 sender 生命周期的协调者在确认不再发送后关闭；不证明消费、日志或账务已完成。 |
| WaitGroup / Add / Done / Wait / join | 登记任务、报告结束、等待登记任务结束的一套协作方法。 | Go 1.21 在启动前 Add、退出时 Done、停止新增后 Wait；等待结束也不自动证明交易责任完成。 |
| cancel / context.Done() / select | cancel 发取消信号，Done 让协作者观察，select 选择已就绪分支。 | 取消不会强杀 goroutine，同时就绪时也不保证取消优先，仍须实际完成确认与 join。 |
| shutdown context / deadline | 专门约束停机流程总等待时间的上下文与期限。 | 使用独立有限期限，不从已取消的运行上下文派生；超时要报告未完成范围，不能说任务已全结束。 |
| goroutine 泄漏 / 阻塞点 | 已失去管理却仍卡住或持有资源的执行任务；阻塞点是它在等的地方。 | 检查外部调用、锁、发送和重试的退出路径，另套 goroutine 超时返回不能解决底层卡住。 |
| sync.Pool / slice / GC / 引用 | Pool 复用对象，slice 可能共享数组，GC 只回收不可达内存。 | cancel、删除登记或发送返回都不能证明引用已释放；所有使用者结束前不能归池，GC 也不会替你停任务。 |

## 把整篇文章压缩成一个故事

沿用无手续费的 ETH/USDT 现货教学场景，1 手是 0.1 ETH：A 的 O1 买 10 手、预留 1000 USDT，New101 和 Cancel102 已经可靠受理，服务这时收到退出信号。协调者不能立刻 cancel 全部任务、close 所有通道，然后把预留退掉；它先关闭新增接入与任务登记，等已登记的受理尝试明确，辨不清的就按原账户、请求标识和载荷登记恢复责任。退出信号不是撤单，请求连接断开也不会抹掉已提交命令。

生产者确认不再创建新工作后，协调者在持久排序边界确定 cutoff；如果本轮覆盖到 102，owner 就从 appliedSeq100 连续确认 101 的成交 4 手，再确认 102 的撤销 6 手。排空期间 IO worker 和回写接收者仍需活着，先停 owner 再 Wait worker 可能让双方卡死。若 101 写库回执丢了，就冻结推进与新状态发布，核对完整持久批次；也可以只在已提交的 101 留检查点，把 102 明确交给恢复。账务最终按确定结果支出 400、释放 600 USDT，停在 101 时不能提前宣称已经撤单或释放剩余预留。

最后才按依赖确认任务结束、协调关闭通道并回收资源：cancel 只是请求退出，close 只是关闭发送路径，两者都不等于任务已结束；多个 sender 必须由知道它们都已结束的协调者统一处理。仍卡在外部调用或持有缓冲引用的 worker，不能靠删登记、归池或 GC 假装清理干净。独立停机期限到了，就如实记录最后确认的 seq、未知提交、待恢复日志及未退出任务；有持久依据并明确接手的待恢复责任，不应被含糊地当作任务丢失。这里给的是静态推演和检查条件，不是已经完成的停机演练或泄漏检测。

[返回专题总览](./README.md)

**流程位置：** 停止接入 → 辨明受理事务 → quiesce 生产者 → owner 排空或 cutoff → 结果确认 → join 与资源回收。
**独立边界：** 本题讲停机依赖、协作退出、channel 关闭和引用释放，不展开资金事务内部实现、日志格式或主备切换。

**必要前提：**

- 使用 Go 1.21+；链下托管 ETH/USDT 现货订单簿，GTC 限价、价格时间优先，无手续费、无链上环节。
- 1 手 = 0.1 ETH，100 USDT/手 = 1000 USDT/ETH。A 初始 1500 USDT，O1 买 10 手占 1000；B 已有卖 4 手的 S1，卖资产已预留，其订单状态已经提交，初始 appliedSeq=100。
- New101 成交 4 手花 400 USDT、余 6 手；Cancel102 撤 6 手。最终 A 可用 1100 USDT、冻结 0、ETH 0.4，B 得 400 USDT，10=成交4+撤6+剩0。
- 每市场单 owner goroutine 独占簿和订单状态；账户逻辑 owner 为账务服务，多个进程由同一个 PostgreSQL 库的事务与行锁约束。
- `T_admit` 原子提交 `(account,requestID,payloadHash)` 幂等、账户校验与预留、reservation 和连续市场 seq 的 New；Cancel 也走同市场持久排序器。
- market control 行分配无空洞的已提交 seq；同时涉及 market、account 的事务先锁 market，再按 account 稳定序锁，账务不反向取 market。
- Accepted 只承诺可靠受理。request context 只控制等待与准备，提交后由 service lifecycle 托管；channel 不负责持久排序，已受理命令不能因关机或队列满丢掉。

```text
关闭新增接入与任务登记入口
    ↓ 正在受理的事务明确，或未知尝试进入恢复责任
quiesce：生产者不再创建新工作，记录明确 cutoff
    ↓ owner 与结果接收者保持活跃，处理受理前缀
确认持久结果 / 保存可恢复 checkpoint / 保留后续日志
    ↓ join sender 与 worker，协调关闭必要通道，最后释放资源
```

## 第 1 层：优雅停机的业务完成条件是什么

**面试官：** 收到退出信号后，取消服务 context、关闭 channel，再等 goroutine 退出，这样算优雅停机吗？

**面试者：** 不一定，这三个动作可能恰好切断已经受理业务唯一的继续路径。
在这个模型中，优雅停机首先意味着不再创造无法接手的新责任，并把已经存在的责任推进到完成或可恢复边界。
我会分别记录接入是否关闭、受理事务是否明确、owner 停在什么 seq、结果是否持久，以及账务消费到了哪里。
进程退出并不要求所有远端账务立即完成，但要求未完成义务仍有完整持久依据和恢复负责人。

如果 New101 已经 Accepted，即使 owner 还没读到它，关机也不能把它作为未下单处理，更不能释放原预留。
如果 Cancel102 已受理，必须由 owner 按序处理，或者保留在日志里等重启继续；退出信号本身不是一条 Cancel。
单 owner 负责簿与订单状态，账务服务负责账户状态，停机协调者不能越过这两者直接改余额或删单。
channel 只是搬运与唤醒，关闭它不能证明日志已经排空，更不能证明账户已结转。

因此，我会先定义停机状态机：关接入、受理收敛、生产者 quiesce、受理前缀处理、结果确认、任务 join、资源回收。
每一步都有进入条件和超时后的遗留记录，而不是在 defer 中按书写顺序随手关闭所有东西。
最终可接受的是全部完成，或从明确持久位置继续；不可接受的是靠内存退出让已承诺业务消失。
所谓优雅，是有边界地交接责任，不是保证任何负载下都能瞬间干净退出。

## 第 2 层：怎样关住受理中的竞争窗口

**面试官：** 你第一步关接入，可一个 handler 已经进入 `T_admit`，另一个正准备交接任务，怎样确认没有漏掉它们？

**面试者：** 需要一个受监督的受理登记入口，把“允许新增任务”和“计入在途任务”放在同一个同步边界内。
handler 先尝试登记；登记成功才可以交给服务级受理任务，停机门闩关闭后新的登记必须失败。
协调者在同一边界内关闭新增登记，再等待所有已经登记的受理尝试，不靠 HTTP 连接数推测数据库工作是否结束。
这样“关门前通过、关门后才真正开始执行”的任务仍在已登记集合中，不会被漏掉。

请求 context 可以停止准备或取消这次响应等待，但持久受理尝试由 service lifecycle 托管，并有自己的有限操作期限。
正在提交的事务返回超时，应登记原 account、requestID、payloadHash、尝试状态和核对责任，而不是归类为未受理。
按权威库和同键幂等协议辨明提交结果；一次查询未找到，不能排除原事务尚在结束并最终提交。
只有原尝试明确未提交或受理结果已经确定，才能从“提交未知”这个状态中正常收敛。

本地准备令牌可以在实际操作结束且不再占用资源时归还，持久积压配额与 reservation 则必须按业务状态核对。
无法在停机期限内辨明的尝试，需要进入可恢复的未知清单，不能只留在即将消失的 goroutine 栈上。
原请求仍可使用相同身份查询或幂等重试，恢复过程不能重新创造一个独立 New 来替代原意图。
这一层先关住受理事实的边界，下一步才有资格讨论“究竟需要排空到哪里”。

## 第 3 层：有未知受理时怎样确定 cutoff

**面试官：** 你把未知受理登记好了，但不知道它最后会不会提交，怎么宣布某个市场 drain 到 seq102 就可以停止？

**面试者：** cutoff 必须是有明确语义的持久边界，不能把“当时 channel 为空”当成最后受理位置。
如果所有受理事务已经明确，并且没有其他受理生产者继续写该市场，可以在排序器边界确认最后已提交 seq。
如果仍有登记的未知尝试，cutoff 只能覆盖已经证明完整的已提交前缀，不能宣称它包含全部退出前业务。
未知尝试以后若提交到更高 seq，也必须留在日志与恢复责任中，不能因不在本次 drain 范围就删除。

多进程场景下，本进程关接入不等于其他接入进程也停止；需要由同一个持久排序器约束市场准入边界。
例如通过 market control 行记录受理门闩或本次 cutoff，使正在受理事务与边界记录按同一锁顺序协调。
在门闩之前已提交的命令纳入前缀，在门闩之后才取得资格的请求按策略拒绝或交给后续生命周期，不能隐式混在一起。
这里不展开所有权交接协议，只要求有明确持久边界，而不是靠一次读最大 seq 猜整个系统已经静止。

quiesce 的意思是通知生产者停止创建新工作，并等待确认；它不等于立刻杀掉所有消费者或关闭回写路径。
本例若已明确受理 New101、Cancel102，就可以把 102 作为 drain 目标；owner 从 appliedSeq100 连续处理到 102。
若选择只在结果已提交的 101 做 checkpoint，也必须保留 102，并明确剩余 6 手仍等待撤单执行。
未完成前缀不能伪装成已撤单，后续恢复才负责把这笔业务推进到预期终态。

## 第 4 层：owner 排空时为什么还需要保留 IO 和回写消费者

**面试官：** 你让 owner 继续 drain 到 cutoff，但服务正在关机，数据库 worker 和回写 channel 应该什么时候停？

**面试者：** 要按依赖从生产端向消费端收敛，而不是按组件名字统一 cancel。
owner 需要结果 IO，IO worker 又可能需要 owner 接收完成消息，所以 owner 不能先退出接收，再同步等待所有 worker。
协调者先停止新增派发，保留当前必要任务的 IO 与结果接收路径，让在途任务有机会完成或明确进入未知状态。
只有任务不再需要某条路径，才对那条路径执行关闭或资源释放。

每个命令的 OutcomeBatch 包含 tradeID、完整订单变化、release 剩余量、cmdSeq、epoch、ruleVersion。
`T_result` 以 expected appliedSeq 与有效 epoch 为条件，同事务提交完整 batch、outbox、appliedSeq，成功后才发布 seq 快照与 ExecutionReport。
如果 seq101 的结果 IO 超时，冻结该市场推进与新状态发布，查询原批次是否已经提交，不能按停机期限强行回滚。
查询仍可提供标明 appliedSeq 的最后已提交只读快照，但不能暴露试算中的候选状态。
只有确认结果或恢复到明确边界，才决定继续 102 或把它留在日志里。

账务按市场连续 batch，在 `T_ledger` 原子提交双边账、预留消耗或释放、幂等与 cursor。
订单撤销可以先于资金释放可见，但不能在退出时把尚未核对的 reservation 全额放回。
checkpoint 只代表已提交前缀，不能混入试算中的 101 或半个 batch；若其持久事实不明，就明确报告未知。
保留 IO 不是无限等待，而是在后面的总 shutdown 期限内优先完成最关键的责任交接。

## 第 5 层：多个 sender 时谁有权 close channel

**面试官：** 你保留完成路径直到任务结束，可多个 worker 都向同一回写 channel 发送，谁负责 close，怎样知道不会再有发送？

**面试者：** channel 的关闭责任属于知道全部 sender 生命周期的协调者，而不是任意一个 worker 或接收者。
每个 worker 只结束自己的发送行为并报告退出；协调者停止新增 sender，等待现有 sender 全部结束，再按协议 close。
关闭表示以后不再有发送，不表示队列里的内容已经被消费，更不表示持久日志和账务已经排空。
接收者若先 close，仍活跃的 sender 会 panic；每个 sender 都 defer close，则会发生重复关闭。

Go 1.21 用 `WaitGroup.Add/Done/Wait`：在启动任务前 Add，由任务 defer Done，在停止新增登记后 Wait。
不能在 Wait 已可能返回后又无序新增任务，也不能把 Add 放进 goroutine 内而让协调者先观察到零计数。
这里不使用 Go 1.25 的 `WG.Go`，也不把 WaitGroup 当成可自动传播取消和异常的任务系统。
需要多个阶段就建立独立的完成条件，让协调者明确知道当前等待的是生产者结束、worker 结束还是 owner 完成。

协调者等待 sender 时，接收者必须继续消费；否则有限回写 channel 填满，worker 等发送、协调者等 worker，会相互卡住。
通道不一定非关不可，若生命周期有独立 done 信号，也可以在 join 后释放整个私有结构。
关键是不用盲目 close 唤醒所有 goroutine，而是依据所有权和未来发送可能性决定。
发送关闭与消费完成是不同证据，任何一方都不能单独证明交易责任已经履行。

## 第 6 层：cancel 为什么不能保证 goroutine 很快退出

**面试官：** 你能 join 所有 sender，但它们循环里都监听 `ctx.Done()`，为什么还会泄漏或迟迟不结束？

**面试者：** 因为 context 是协作信号，不会抢占正在执行的普通函数，也不会自动解除所有类型的阻塞。
一个 goroutine 可能卡在不支持取消的外部调用、锁等待、没有接收者的发送，或者持有引用的无限重试里。
需要逐条检查阻塞点：网络调用有期限，连接和句柄可被拥有者关闭，重试有预算，等待有退出路径。
如果底层库不支持取消，只是外面套一层 goroutine 并超时返回，会把泄漏藏起来而不是解决它。

`select` 同时有数据和取消就绪时不保证取消优先，不能声称调用 cancel 后下一次迭代必定退出。
循环开头显式检查可以改善响应，但检查与后续发送、IO 仍不是原子动作，业务语义不能依赖这个竞争结果。
对于已受理任务，取消后仍可能需要完成登记和结果交接；对于未开始的辅助任务，可以停止派发并释放其独占资源。
必须按任务阶段决定如何收尾，不能把所有 goroutine 都写成见到 Done 立即扔下当前业务。

请求等待者离开也要覆盖：一次回复可以用容量为 1、唯一生产者最多发送一次的 channel，避免 owner 被退出的 handler 卡住。
非阻塞通知仅适合可由持久查询补回的提示；完整结果不能为了结束 goroutine 而 `default` 丢弃。
辅助 IO 回写携带 jobID、epoch、baseVersion、opSeq，由 owner 验收，worker 不能在退出前直接补改簿。
cancel 之后仍需实际完成确认与 join，才能从“要求退出”走到“已经不再访问资源”。

## 第 7 层：有界停机超时后怎样处理未退出任务和对象池

**面试官：** 你要求实际 join，可总 shutdown 期限已经到了，一个外部调用仍然没返回，这时还能承诺资源都已经安全回收吗？

**面试者：** 不能。我会用独立的有限 shutdown context 约束退出流程，而不是从已经取消的请求或运行 context 派生它。
期限到达后停止等待应有明确结果：哪些任务未结束、哪些提交未知、owner 最后确认哪个 seq、哪些日志需要恢复。
Go 没有安全强杀任意 goroutine 的通用机制，不能把超时返回写成“所有任务已终止”。
如必须由进程级退出结束残留执行，也要把它当作失败兜底，由持久恢复接手，而非正常 drain 成功。

池对象尤其不能提前回收：worker 仍持有输入 slice、编码器仍持有 batch、channel 仍引用结果时，都不能把底层缓冲放回 `sync.Pool`。
要在所有使用者完成并释放引用以后归还，必要时采用独占移交、深拷贝或明确引用计数。
GC 既不能终止活跃 goroutine，也不能回收仍可达的对象；把 map 项删掉不等于 worker 手里的别名已经消失。
无法确认引用释放时，宁可把它列为未回收资源，也不能让新任务复用这块仍会被旧任务读写的内存。

业务责任则保留命令日志、完整结果、outbox、消费 cursor 和原请求身份，不因为内存无法全部回收就清理持久事实。
如果停在已提交的 seq101，恢复后先确认该批次，再执行 Cancel102；不能重新生成一笔不同身份的成交。
A 的剩余预留仍按确定结果消耗或释放，不允许用“服务已关闭”绕过账务顺序。
有界退出限制本次进程的等待时间，恢复协议保证等待结束后责任仍然存在。

## 第 8 层：怎样证明停机没有遗漏责任或隐藏泄漏

**面试官：** 你承认有界退出可能留下未完成任务，怎样静态区分合理的待恢复工作与真正的 goroutine 泄漏？

**面试者：** 我会为每种 goroutine 写出创建者、上限、等待对象、退出条件、join 者，以及持有的引用和持久责任。
合理的后台任务必须有受控生命周期和负责人；请求已经结束、服务已停而仍无人管理地阻塞，才是典型泄漏风险。
仅看到 goroutine 数下降不够，任务可能退出了却把命令遗漏；数值不归零也不自动等于泄漏，因为运行时和常驻服务仍可能存在。
静态评审先找等待环、不可取消阻塞和未登记派发，再设计后续观测与验证，不假称已经得到运行证据。

对同一笔案例，分别推演受理提交回执丢失、New101 结果提交未知、Cancel102 已受理未执行、worker 回写时等待者离开。
每个窗口都要能指出下一任负责人、原始身份和恢复位置，且 channel 的关闭不早于其全部 sender 结束。
恢复后的顺序仍是从 appliedSeq100 确认 101，再处理 102；结果只能从持久提交边界发布。
最终账务应收敛到 A 可用 1100 USDT、冻结 0、ETH 0.4，B 得 400，订单数量 10=4+6+0。

后续可核查的证据包括停机阶段、受理未知清单、最后确认 seq、活跃任务登记、未完成 IO 和残留缓冲引用。
若 drain 超时，报告应写明已完成前缀与待恢复范围，不能笼统说“优雅停机成功，所有订单已完成”。
这些是可检验条件和静态反例，不是本次已经执行的测试或性能结果，也不附另一个小工程。
停机的闭环是每份责任都完成或被可靠接手，每个资源都释放或被诚实列为未释放。

## 收束：退出信号不是业务删除键

- **讲透的机制：** 关闭登记入口、受理收敛、生产者 quiesce、明确 cutoff、保留结果接收路径、sender 协调关闭、join 和引用生命周期。
- **易错边界：** cancel 不代替 join；close 不代表日志排空；`select` 不保证取消优先；WaitGroup 不负责业务完成；Pool 不能提前接收仍被引用的对象。
- **可检验反例：** 让 seq101 已写库但回执超时，同时让最后一个 worker 向满回写通道发送。若协调者先停 owner 再 Wait，或为退出而释放全部预留，就分别暴露等待环与业务责任丢失。
- **最终核对：** 停机可在明确前缀暂停，但日志与未知清单必须支持恢复到 101→102 和 10=4+6+0；不附额外 MVP，不声称工程验证通过。
