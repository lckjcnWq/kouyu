# 大问题 9：怎样并行执行慢任务，又保证异步回写不越过订单状态所有权？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 工作池 / worker | 用有限数量的工作任务处理可分离的计算或 IO。 | 可以并行解码、静态检查、纯计算和授权 IO，不能把同一订单簿的最终撮合拆给多个写者。 |
| owner / 状态所有权 | owner 是某份状态的唯一权威管理者，拥有最终修改和裁决权。 | worker 不持有可写订单引用，异步结果只能交回 owner 校验后决定是否采用。 |
| 不可变输入 / 非权威预处理 | 输入交出后不再变；预处理只提供辅助材料，不作最终业务裁决。 | 格式检查提前完成不等于可以提前撤单，依赖当前簿的校验仍在命令执行位置由 owner 完成。 |
| cmdSeq / appliedSeq | 前者是持久命令序号，后者是已完整提交结果的连续前缀。 | appliedSeq100 后先确认 New101，再处理 Cancel102；不能因为 102 的预处理先完成就先撤单。 |
| jobID | 区分一次具体任务尝试的身份。 | 重试换了尝试，旧 jobID 的结果就不能冒充当前任务，但原来的已受理命令仍然有效。 |
| epoch | 派发任务时的有效所有权代际。 | 拒绝旧代际回写，但同代际的旧任务还要靠其他字段识别，不能只查 epoch。 |
| baseVersion | 本次计算所依赖的状态版本。 | owner 核对依赖是否仍成立；只依赖不可变载荷的检查，不必假装依赖整本订单簿。 |
| opSeq | owner 为逻辑操作分配的递增序号，用来识别同代际里的先后尝试。 | 它防旧操作覆盖新登记，不等于 cmdSeq，不能拿它抹掉已经排序的交易义务。 |
| ABA / 稳定对象身份 | 旧对象消失后，新对象看起来又有同样地址或计数，导致误以为没有变化。 | 版本要结合稳定身份和单调变化，不能让复用地址的旧回写误中一份新状态。 |
| in-flight / 有界重排 | in-flight 是已派发未收敛的任务；重排是暂存先完成的辅助结果。 | 登记、等待集合、派发窗口和回写容量都要有上限，不能只限制入口 worker 数量。 |
| ruleVersion / 输入散列 | 标明所用规则和输入内容，帮助核对结果对应的计算条件。 | 来自已受理命令的任务要关联这些身份，不能只凭订单号就接受计算结果。 |
| OutcomeBatch | 一条命令的完整且封闭的裁决结果包。 | 包含成交身份、完整订单变化、剩余释放要求和版本信息，worker 不能临时改成另一种结果。 |
| T_result / expected appliedSeq | 结果事务与它要求的前一已提交位置。 | 同一事务校验有效 epoch 和期望前缀，提交 batch、outbox 并推进 appliedSeq，不能先查身份再另行写入。 |
| outbox / ExecutionReport | outbox 是持久待交付事件，ExecutionReport 是对外订单结果回报。 | worker 临时成功消息不能替代可靠事件；owner 验收并确认结果后才能发布新快照和回报。 |
| 提交未知 / 持久核对 | 超时没告诉你事务到底提交了没有，需要查原身份对应的持久事实。 | 冻结市场推进与新状态发布，核对完整 batch、outbox 和 appliedSeq，不能随意重算新 tradeID 或退款。 |
| T_ledger / reservation / cursor | 账务事务、业务预留和账务已消费位置。 | 按连续结果原子记双边账并消耗或释放预留；市场结果提交不等于账务已追到相同位置。 |
| channel / sync.Pool / 引用 | channel 传值或引用，Pool 复用临时对象；引用决定谁还在使用底层内存。 | 传 slice 不深拷贝数组，send 返回不证明使用结束；所有使用者完成前不能归池。 |
| cancel / join / WaitGroup | cancel 请求协作退出，join 等待实际结束；Go 1.21 可按协议用 Add、Done、Wait。 | 取消采用资格不证明 worker 已退出，回收前仍要确认；等待 worker 时不能先堵住唯一回写接收者。 |

## 把整篇文章压缩成一个故事

沿用无手续费的 ETH/USDT 现货例子，1 手是 0.1 ETH。A 的 O1 买 10 手、预留 1000 USDT，工作池同时准备 New101 和 Cancel102 的静态检查，撤单那份先返回。市场 owner 可以先收下这份辅助结果，却仍从 appliedSeq100 后先裁决 New101：成交 4 手、花 400 USDT、剩余 6 手；确认该结果后才在 102 撤掉剩余 6 手。工作池并行的是可分离工作，不是最终裁决权；先返回的任务不能抢先改订单簿。

owner 派发时登记 jobID、epoch、baseVersion 和 opSeq，回写时按实际依赖逐项校验，决定采用、丢弃还是重新计算。换了新尝试后，旧 worker 即使同代际、同订单号，也不能覆盖新登记；但丢弃旧辅助结果不代表取消原命令。owner 决定成交后，交给 IO worker 的是完整不可变 OutcomeBatch，写入边界还要由 T_result 在同一事务校验有效 epoch 和 expected appliedSeq。worker 不直接改簿或发布，owner 验收提交回执并确认持久结果后才推进；账务再按结果消耗 400、释放 600 USDT，不能按最初预留全退。

若写库后回执丢了，超时只是提交未知：冻结该市场推进与新状态发布，用原命令和批次身份查持久事实；即使旧回写不再有采用资格，已经提交的历史也不能假装不存在。查询可继续提供标明进度的最后已提交快照。退出时 owner 仍要接收必要回写，任务和等待集合保持有界；cancel 不等于 worker 已结束，channel 不深拷贝，send 返回也不等于结果对象已用完，最后使用者确认结束后才可归池。这里是异常窗口的静态推演，不声称加 worker 后实测更快或已通过并发测试。

[返回专题总览](./README.md)

**流程位置：** 非权威预处理 → 持久排序 → owner 决策 → 异步结果 IO → owner 验收与发布；重点是并行范围和回写资格。
**独立边界：** 本题讲工作池、任务身份、迟到结果和对象生命周期，不把单状态转换拆成并行撮合，也不展开资金事务或主备协议。

**必要前提：**

- 使用 Go 1.21+；链下托管 ETH/USDT 现货订单簿，GTC 限价、价格时间优先，无手续费、无链上环节。
- 1 手 = 0.1 ETH，100 USDT/手 = 1000 USDT/ETH。A 初始 1500 USDT，O1 买 10 手预留 1000；B 已有 S1 卖 4 手、卖资产已预留，其订单状态已经提交，初始 appliedSeq=100。
- New101 成交 4 手花 400 USDT、余 6 手；Cancel102 撤 6 手。最终 A 可用 1100 USDT、冻结 0、ETH 0.4，B 得 400 USDT，10=成交4+撤6+剩0。
- 每市场一个 owner goroutine 独占簿和订单状态；账户逻辑 owner 是账务服务，由同一个 PostgreSQL 库中的事务与行锁约束多个进程。
- `T_admit` 原子完成 `(account,requestID,payloadHash)` 幂等、账户校验与预留、reservation、带连续市场 seq 的 New；Cancel 也走同市场持久排序器。
- 排序器锁 market control 行分配无空洞的已提交 seq；同时涉及 market、account 的事务先锁 market，再按 account 稳定序锁，账务不反取 market。
- Accepted 只代表可靠受理。channel 是内存队列或唤醒，不决定持久顺序；容量必须在持久受理前约束，已受理业务不能因池满被丢弃。

```text
不可变输入 → 有界 worker：解码、静态检查、纯计算或受控 IO
                         ↓ 带身份与版本的完成消息
持久命令日志 → 市场 owner：验收结果、最终业务校验、顺序状态转换
                         ↓ 完整 OutcomeBatch 的持久 IO
                  确认 T_result → 发布带 seq 的结果
```

## 第 1 层：工作池应该并行什么，而不应该并行什么

**面试官：** 单个市场 owner 容易被慢任务拖住，能否把每个 New 和 Cancel 都丢进 worker 池，提高撮合并行度？

**面试者：** 不能把同一订单簿的权威状态转换交给多个 worker 并行执行，否则就改变了单 owner 模型。
我会先把工作拆成非权威预处理、owner 决策和结果持久 IO，而不是简单按接口名分配 goroutine。
解码、格式校验、基于不可变输入的纯计算可以并发；依赖当前簿、订单状态和先后关系的最终业务校验仍归 owner。
账户能否占资也不能由 worker 读取一份旧余额后决定，它仍属于受理事务和账户约束。

每个市场的 owner 按日志 seq 处理命令，New101 的执行结果会成为 Cancel102 的输入条件。
worker 可以提前准备两条命令的静态字段，却不能提前把 102 判断成“订单不存在”并结束它。
已经确定的成交、剩余数量和撤销数量只能由 owner 在对应命令位置裁决。
本例必须先确定成交 4 手、余 6 手，再撤 6 手，不能以“哪个 worker 先返回”作为业务顺序。

结果 IO 可以交给有限 worker 执行，以便 owner 管理循环继续接收控制和完成消息，但不因此允许同一市场无界推进。
在结果尚未确定前，owner 不能发布试算状态，也不能把后续命令建立在可能没提交的状态上。
工作池提高的是可安全分离的工作的并发度，不是凭空消除一条状态机的顺序依赖。
如果瓶颈恰好就在单簿的顺序转换，增加 worker 数量不能证明吞吐一定改善。

## 第 2 层：异步结果要携带哪些可验收的身份

**面试官：** 你让 worker 只做辅助工作，可它返回时 owner 的状态可能已变化，怎样判断结果还对应当初那次任务？

**面试者：** 我会给任务和回写都带上 `jobID、epoch、baseVersion、opSeq`，并关联 market、命令身份和预处理类型。
jobID 区分一次具体任务尝试，epoch 表示派发它的有效所有权代际，baseVersion 表示它依赖的状态版本。
opSeq 是 owner 为该逻辑操作分配的递增序号，避免同一个对象上的旧操作覆盖新操作；它不等于持久 cmdSeq。
如果任务源自已受理命令，还应明确关联 cmdSeq、输入散列和 ruleVersion，不能只拿一个订单号猜测上下文。

owner 维护有界的在途任务登记，派发前记录预期身份、依赖字段和允许的完成状态。
worker 只返回独立结果消息，不持有可修改的订单指针，也不能直接写 owner 的 map、队列或订单剩余量。
owner 收到结果后逐项核对登记、代际、操作序号、依赖版本和载荷身份，再决定采用、丢弃或重新计算。
即使静态预处理完全有效，最终业务校验也仍在 owner 执行到对应日志位置时完成。

这些字段不是一段“全都相等就万事大吉”的装饰，而是要与实际依赖一起定义。
例如纯格式检查只依赖不可变载荷及规则版本，不应假装依赖整本订单簿；基于盘口的计算则不能无视版本变化。
如果外部 IO 本身会产生持久副作用，仅在返回时拒绝旧结果还不够，持久写入也必须受身份、幂等与提交条件约束。
这里先明确回写资格，后面再把它落到完整结果批次的提交边界。

## 第 3 层：任务乱序完成怎样不变成业务乱序

**面试官：** 你有完整身份，但 seq102 的预处理先返回、seq101 一直很慢，能否先把 102 的结果交给 owner 执行？

**面试者：** 可以先接收它的完成消息，不能先执行它的业务状态转换。
owner 维护下一个可执行的持久位置，当前 appliedSeq=100，只能先裁决 seq101。
102 的预处理结果进入有界的等待集合，等 101 完成并提交结果后，再对 102 做最终业务校验。
预处理完成顺序与业务执行顺序是两件事，前者不得偷换成后者。

这个等待集合本身也必须有上限，派发窗口不能无限向后延伸，否则一个慢任务就能积累无限个已完成结果。
窗口满后停止派发更远任务，继续处理完成消息和控制事件；其余已受理命令保留在日志，不占无界内存。
如果 seq101 的预处理尝试失败，区分临时 IO 错误和可确定的输入问题，不把 worker 超时直接写成业务拒绝。
已受理命令必须在其 seq 位置形成确定结果，不能跳过这个位置让 appliedSeq 出现逻辑空洞。

对于只依赖输入的纯预处理，可以在有限重试预算内重做，并让旧尝试的结果失去采用资格。
如果两个 worker 都做基于旧簿的“完整撮合”，即使最终按 seq 交回，也不能把第二个结果直接套到已经变化的簿上。
本题不采用这种投机撮合，而是把最终裁决留给 owner，避免把错误包装成一个复杂重排缓冲区。
有限重排只整理辅助结果，不授予 worker 修改因果关系的权力。

## 第 4 层：同代际的迟到结果怎样防止覆盖新状态

**面试官：** 你会让旧尝试失效，但 epoch 没变、订单还是 O1，迟到回写怎么知道自己已经不是最新操作？

**面试者：** epoch 只隔离所有权代际，不能识别同代际里的重试、对象更新或操作替换。
我会由 owner 推进逻辑操作的 opSeq，并在登记中只保留当前可采用的 jobID 与依赖版本。
取消一次辅助任务的采用资格、派发替代任务时，都先更新登记，再允许新任务进入池。
旧结果即使先到或携带相同订单号，也会因为 jobID 或 opSeq 不匹配而被拒绝采用。

依赖版本要避免 ABA：订单对象被移除后，即使内存地址被复用，也不能重新从一个会碰巧相等的局部计数开始。
版本身份需要包含稳定对象身份和单调变化，市场生命周期变化则由 epoch 再加一层约束。
回写被拒绝时要释放它独占的缓冲和引用，但不能借清理动作修改新任务仍在使用的对象。
若当前任务依赖的状态已经变化，owner 决定重新计算或放弃这个辅助结果，而不是让 worker 自己修补簿。

已排序命令本身不能随辅助任务一起被放弃；失效的是某次计算结果，不是原命令的持久受理资格。
同样，Cancel102 的到来不能让 New101 的业务结果自动失效，因为它们本来就应按序共同成立。
采用哪个辅助结果可以由 opSeq 管，订单最终成交或撤单则仍由 cmdSeq 和当前状态管。
把这两个序号混成一个，会把“拒绝迟到计算”错误变成“删除先前交易义务”。

## 第 5 层：结果持久化 worker 怎样不越权发布

**面试官：** 你已经让 owner 独占决策，可结果持久化也在 worker 里；worker 写库成功后，能否顺手更新订单并发布回报？

**面试者：** worker 可以执行明确授权的持久 IO，但不能顺手修改 owner 的簿或把试算状态直接发布成权威状态。
owner 为当前命令构造不可变 OutcomeBatch，包含 tradeID、完整订单变化、release 剩余量、cmdSeq、epoch 和 ruleVersion。
派发记录还要带 expected appliedSeq、批次身份或散列，并保证同市场不存在未经控制的多个结果提交者。
worker 只按这份不可变批次执行 `T_result`，不能依据自己后来读到的状态重新创造另一种成交结果。

`T_result` 在同一事务中检查 expected appliedSeq 和有效 epoch，提交完整 batch、outbox 并推进 appliedSeq。
持久检查和写入不能拆成“先查当前身份，再另开事务写结果”，否则检查到实际写入之间仍可能失效。
worker 返回带原任务身份的提交回执，owner 验收后才把已提交状态向前推进，并发布带 seq 的快照与 ExecutionReport。
已提交 outbox 的可靠消费者可以独立交付持久事件，但 worker 的临时成功消息不能替代这个可靠出口。

本例 seq101 的 batch 要一起表达 A、B 两边订单变化及成交 4 手，不能先发布成交再补齐剩余量记录。
账务按市场连续 batch，在 `T_ledger` 原子完成双边账、预留消耗或释放、幂等与 cursor。
seq102 的撤销结果只能释放当时剩余 6 手对应的 600 USDT，不能取请求最初数量 10 手来回填。
工作池只执行被授权的 IO，业务状态、结果完整性和发布条件都没有因此转移给它。

## 第 6 层：持久化回执迟到或丢失怎样继续

**面试官：** 你等 worker 的提交回执再推进，但它返回超时，稍后又出现一个成功回执，这时应重试、回滚还是采用迟到结果？

**面试者：** 先把这次结果 IO 标记为未知，并冻结对应市场后续业务推进，不能直接按回滚处理。
worker 超时可能发生在数据库已提交、回执尚未返回之后，所以 owner 不应立即丢掉批次身份并重算新的 tradeID。
用原 cmdSeq、epoch、批次身份和 expected appliedSeq 查询持久结果，核对 batch、outbox 与 appliedSeq 的共同事实。
冻结包括当前市场推进与新状态发布，不停掉全部查询；仍可提供标明 appliedSeq 的最后已提交只读快照，不能暴露候选状态。

查到完整的同一批次已提交，就按持久事实接续；明确未提交时，才按原身份和有效提交条件重试。
若发现条件冲突、不同批次或代际已失效，停止盲重试并进入受控恢复，不能把 expected 值改大强行写过。
迟到回执只能作为核对线索，需确认它是否对应当前待确认任务，以及持久结果是否仍支持其结论。
即使当前 epoch 已变，旧 epoch 的已提交事实也不能被本地丢弃；“不采用旧回写”和“历史事务没发生”不是一回事。

对于没有副作用的预处理，超时后换 jobID 重做通常可控；对于可能已提交的结果 IO，重做必须遵守持久身份与提交约束。
业务预留不因等待超时而释放，配额也按持久状态核对，不能把 worker 槽位释放与业务资格归还混在一起。
这段未知窗口必须有可观测状态和明确恢复负责人，不能成为队列里永远不再调度的一条孤儿任务。
异步化减少了同步等待形式，却不会消除“提交是否发生”的根本不确定性。

## 第 7 层：回写通道与对象池怎样不制造阻塞和引用泄漏

**面试官：** 你保留了待确认任务，但等待者可能离开，任务结果也带大缓冲，怎样避免堵住 worker 或过早归还对象池？

**面试者：** 一次性响应可以使用容量为 1 的 channel，限制唯一生产者最多发送一次，让等待者离开后结果仍有容纳位置。
若使用非阻塞提示，必须存在持久查询或另一个明确托管者，不能把唯一完整结果用 `default` 丢掉。
owner 需要验收的关键完成消息必须有可达接收路径；在途数和回写容量一起设计，不能只给入口池设上限。
持久结果回执可以通过查询恢复，但这不意味着允许 worker 永久阻塞在没有接收者的发送上。

输入、输出和批次对象的所有权要明示：worker 只读独立输入，完成后转交结果，owner 处理后负责最终释放。
传一个 slice 只复制描述符，不复制底层数组；派发后继续改数组，或者一发送就把缓冲放回 `sync.Pool`，都会破坏这个契约。
可选择深拷贝，或使用严格的单次移交与有界引用计数，但归还前必须确认 worker、owner、编码器和发送路径都不再引用。
`sync.Pool` 不是生命周期管理器，GC 也不能解除仍被 goroutine、channel 或闭包持有的引用。

取消任务时只把采用资格失效，不等于 worker 已经退出或释放了指针；需要完成确认或 join 后再做最后回收。
对不可取消的外部调用，避免让它持有整本簿的快照或大共享缓冲，调用适配层也要限制并发和保留字节数。
清理队列与 in-flight map 时，应按真实完成状态删除引用，而不是为了让监控好看提前清空登记。
这样既不因慢接收者阻塞市场，也不以重用仍被引用的内存换取表面的低分配。

## 第 8 层：怎样关闭工作池而不破坏上述保证

**面试官：** 你要求引用释放和任务确认，停机时如果先 Wait worker、但 owner 已经不接回写了，怎样避免两边相互等待？

**面试者：** 我会把关闭顺序按依赖组织，而不是先统一 cancel 所有任务。
先停止新接入，辨明所有正在受理的事务或登记未知，再 quiesce 生产者，停止派发新的辅助任务。
owner 在需要的完成消息尚未回收前继续消费回写；允许 drain 已受理前缀，或在明确 cutoff 的可恢复边界停止。
等待 worker 结束的协调者不能同时堵住它们唯一的结果接收者，否则 join 本身就形成死锁。

Go 1.21 使用 `WaitGroup.Add/Done/Wait`：启动前 Add，任务退出时 Done，停止新增登记后再 Wait，不使用 `WG.Go`。
多个 sender 共用通道时，由协调者确认全部 sender 结束后决定 close；cancel 不代表已经满足 close 条件。
有界 shutdown 期限到达后，保留日志、待确认结果和恢复身份，不能删除它们或声称全部账务已经完成。
不得盲目归还仍被未退出任务引用的池对象；若资源不能确认释放，应明确保留与报告，而非伪装成正常回收。

静态推演可分别让 seq102 预处理先完成、旧 opSeq 结果迟到、seq101 写库回执丢失、等待者提前退出。
合格方案仍先确认 New101 的 4 手成交，再确认 Cancel102 的 6 手撤销，最后账务收敛到既定余额。
worker 不得直接改簿，旧结果不得覆盖新登记，任何回写等待都必须有接收者或可恢复出口。
这只是反例驱动的文稿推演，不表示已经执行并发测试，也不承诺增加 worker 后一定提高性能。

## 收束：并发的是辅助工作，不是状态裁决权

- **讲透的机制：** 非权威并行、带身份与版本的回写、有限重排、owner 最终校验、条件结果提交、未知 IO 冻结、引用释放与协作退出。
- **易错边界：** jobID 不代替 cmdSeq；epoch 不覆盖同代际旧操作；接收 channel 消息不转移全部别名；取消不证明 worker 已退出。
- **可检验反例：** 让 Cancel102 的预处理先返回，再让旧 jobID 携带 O1 的旧 baseVersion 回写。若 worker 能先撤单或把已经成交 4 手的状态覆盖掉，所有权约束就是空话。
- **最终核对：** 只采用合法回写并保持 101→102，得到 A 可用 1100 USDT、冻结 0、ETH 0.4，B 得 400，10=4+6+0；不附额外 MVP。
