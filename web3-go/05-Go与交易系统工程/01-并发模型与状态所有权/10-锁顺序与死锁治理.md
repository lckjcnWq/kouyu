# 大问题 10：多把锁和多个 owner 调用时，怎样避免死锁？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 死锁 / 等待图 | 各方互相等对方释放资源形成循环；等待图把这些关系画出来。 | 不只检查 Lock，还检查 channel、RPC、数据库连接及 owner 回调。 |
| owner / 单写者 | 一份可变状态的唯一受控修改者。 | 减少簿写锁竞争，不代表它不会阻塞在别的任务上。 |
| 稳定全序 / accountID | 与买卖角色无关的统一资源排序，例如规范化账户编号顺序。 | 不能一笔先买方再卖方，另一笔角色互换后就反向拿锁。 |
| assetID / 锁键去重 | 多资产行的稳定身份，以及同一资源只登记一次。 | 锁键可用账户与资产的组合，全部同类入口须遵守相同规则。 |
| MarketControl / T_admit | 市场控制记录，以及共同提交受理与预留的事务。 | 需要时先锁市场控制行，再按账户顺序拿行锁。 |
| T_ledger / 消费 cursor | 账务事务与账务已完成位置。 | 先锁自己的游标再锁账户，不拿账户锁反向取市场控制行。 |
| RPC / 连接池 | 远端调用，以及可借用连接的有限资源集合。 | owner 等 RPC、RPC 又等 owner，也能成环；占着连接等另一任务同样要检查。 |
| TryLock / 同步效果 | 尝试获取锁；成功同步才赋予相应受保护访问条件。 | 失败不是共享状态可以无锁读取的通行证。 |
| 超时 / 活锁 / 饥饿 | 放弃一次等待、反复退让仍没进度、某方长期得不到执行机会。 | 超时重试可能只改变卡住形式，不能替代无环设计。 |
| RWMutex / 锁升级 | 读写锁，以及持有读锁时想直接拿写锁。 | 不支持直接升级或降级，递归读锁也不能视为通用安全方案。 |
| 不可重入 / 不复制锁 | 同一执行路径不能再次取得自己未释放的锁；锁使用后不可复制。 | 内部持锁辅助函数与公开加锁方法要有明确契约。 |
| 不可变快照 / 版本回写 | 解锁后只交付不会被继续改的数据，并核验回写依据是否仍有效。 | Unlock 后把可写订单指针交给回调，会绕过原保护。 |
| 短临界区 / 业务原子性 | 缩短持锁时间，同时仍让相关检查与修改共同成立。 | 不能为了少等 I/O，把检查余额和实际占资拆成两个不相干动作。 |
| 堆栈 / 阻塞证据 / 局部死锁 | 观察任务停在哪里、谁等谁，以及只有部分任务永久互等的情况。 | 热点还有进度、慢 RPC 不一定成环；运行时没报全局死锁也不能排除局部死锁。 |

## 把整篇文章压缩成一个故事

两个账户 A、B 互相交易，第一笔事务先锁 A 等 B，第二笔先锁 B 等 A，谁都不肯先放手。小林把锁序改成统一账户编号顺序，而不是先买方后卖方；再检查市场控制行和账务游标的层级，禁止账务拿着账户锁回头等市场控制行。规则必须覆盖所有同类写入口，不能只修一条成交路径。

账户锁不再反向获取，市场 owner 却还是卡住：它同步等一个 RPC，RPC 为确认订单又同步问回这个 owner，owner 不回事件循环就无法应答。这个环连 mutex 都不需要。改造需要单向交付、无反向依赖的调用契约，以及有界资源，而不是再开几个轻量 goroutine 或给每一处等待加重试。

最后小林还要防止“修死锁”破坏业务：不能持读锁直接升级写锁，不能 TryLock 失败后读共享字段，也不能 Unlock 后把订单指针交给回调任意改。诊断时找出真实等待环，再验证操作能推进且数量、资金、重试身份仍正确；只有堆栈里出现 Lock 或一次超时，并不足以判定死锁，本文也没有声称已执行线上诊断实验。

**流程位置与核心机制：** 覆盖进程内锁、数据库行锁与 owner 间消息形成的等待关系。这里证明资源获取顺序和调用契约，不重复数据库索引与低延迟调优。

**必要前提：** 基线市场簿由单 owner 修改；账户事务会涉及多个账户行。T_admit 先取市场控制行，再取账户行；T_ledger 先取消费游标，再按账户稳定顺序取行锁，不在持有账户锁时反取市场控制行。

## 第 1 层：用了单写者还会不会死锁？

**面试官：** 你的订单簿已经是单 owner，是否就不再需要考虑死锁？

**面试者：** 只能说消除了多个线程为同一个簿互抢写锁的一类风险，不能说整个服务没有等待环。owner 可能阻塞在结果 channel、数据库连接或外部 RPC 上；如果它等待的另一任务又要调用 owner 才能完成，就形成消息层面的循环等待，完全不需要两个 mutex。

账户域仍可能同时锁买卖双方账户，不同市场也可能竞争同一账户。避免死锁要把「谁持有什么资源、下一步等待谁」连成等待图，而不是只搜索 Lock 函数。单 owner 是状态修改权约束，不是所有阻塞都自动安全的证明。

## 第 2 层：两个账户的锁怎样排序？

**面试官：** 那先看最典型的买卖双方账户，按买方再卖方加锁可以吗？

**面试者：** 不可以把业务角色当全局锁序，因为另一笔交易可能让两个账户交换角色。若 T1 先锁 A 再等 B，T2 先锁 B 再等 A，就构成环。应该采用稳定、与交易方向无关的顺序，例如按规范化 accountID 升序锁所有需要修改的账户，并对重复账户去重。

这个规则要适用于所有同类写入入口，不能成交结算按 ID 排序，而管理员调整或转账按来源、目标排序。若一次事务涉及多个资产行，锁键可定义为 `(accountID,assetID)` 的稳定全序；取哪些行、如何去重、在哪个范围持锁，都必须写进契约，不能说一句「注意顺序」就结束。

## 第 3 层：账户有序，市场控制行会不会形成新环？

**面试官：** 账户都按 ID 排好了，但受理事务还要拿 MarketControl，这不会和账务事务互相卡住吗？

**面试者：** 所以需要规定跨资源层级，而不仅是账户内部顺序。本模型 T_admit 先锁市场控制行，再按账户稳定序锁账户；T_result 只在事务内检查并更新相应市场控制与结果，不进入账户域；T_ledger 先锁自己的消费游标，再按账户稳定序锁账户，且绝不拿着账户行锁回取 MarketControl。

这样账务持有账户时，最多让受理等待，但不会再反向等待受理持有的市场行。若以后新增同时涉及多个市场的事务，就必须把市场之间的顺序也纳入全局规则，或拆成不形成环的协议，不能临时从任意市场开始锁。所有隐藏资源和新入口也要审查，显式锁序只能消除它覆盖的那一部分等待环。

## 第 4 层：代码都遵守锁序，为什么还会挂住？

**面试官：** 假设显式锁序没问题，但 owner 发出账务 RPC 后一直不返回，你会怀疑什么？

**面试者：** 我会检查调用是否跨越了同步依赖边界。例如 owner 等 RPC 完成，RPC 服务为了确认订单状态又同步查询这个 owner；owner 只有返回事件循环才会处理查询，于是形成 owner→RPC→owner 的环。数据库连接池也类似：任务拿着唯一连接等待另一任务，而后者必须先拿连接才能完成。

本模型不要求市场 owner 同步等待账务完成，结果批次提交后由独立消费者推进。必须等待的 I/O，要明确不会反向调用被阻塞的 owner，不持有业务锁等待不受控外部系统；涉及异步交接时，回写由 owner 校验版本采用。不能靠「goroutine 很轻」修复一个逻辑上永远不能解开的依赖环。

## 第 5 层：用超时或 TryLock 能不能代替锁序？

**面试官：** 给所有 Lock 加超时，拿不到就重试，是否就不必设计全局顺序？

**面试者：** 不行。标准 sync.Mutex 的 Lock 本身不接受 context；TryLock 失败也不提供同步效果，不能拿失败当读取共享状态的许可。即使自行做超时轮询，也可能把死锁变成活锁或长期饥饿：各方反复拿第一把锁、争第二把失败、一起退让又同时重试，业务没有进度。

数据库死锁检测和事务超时可以终止等待，但只能说明当前尝试被中止或需要确认结果；要整体回滚并按同一业务身份重试，不能拿着半套本地状态重试另一半。退避和有限重试是运行保护，稳定锁序、短事务和无环调用才是主要设计约束。若提交阶段超时仍要恢复原结果，不能一律当事务失败。

## 第 6 层：读锁为什么也可能造成自锁？

**面试官：** 你强调稳定顺序，那同一个对象先 RLock 读，再升级成 Lock 写，是不是天然有序？

**面试者：** RWMutex 不支持从读锁直接升级成写锁，也不支持写锁直接降级。持有 RLock 再调用 Lock，会让写锁等待自己释放读锁；递归 RLock 也不能作为通用方案，因为已有写者等待时，新读锁会被阻塞。Mutex 同样不是可重入锁，不能在持锁函数里随意调用另一个会锁同一对象的公开方法。

需要读后可能写时，可以释放读锁、获取写锁后重新校验版本和条件，承认两次之间状态可能变化；或者从一开始就使用写锁保护短小的检查更新。内部可区分清楚的「调用者已持锁」辅助函数，但必须让命名、可见性和审查规则明确，不能靠开发者记忆。锁首次使用后也不能复制，否则保护域本身就被误拆了。

## 第 7 层：所有锁都放开再调用外部函数够了吗？

**面试官：** 那我在调用回调之前都 Unlock，既缩短临界区又避免重入，是否就安全？

**面试者：** 只解决了部分等待风险，还要检查是否把可变引用泄漏出去。如果持锁取到 `*Order`，解锁后交给回调，回调仍可以越过保护域修改订单。安全做法是交付不可变值快照、明确复制可变的嵌套数据，或让回调只产生新的命令，再由 owner/写锁路径决定是否采用。

此外解锁后计算再回写要验证版本，否则会把旧状态计算结果覆盖到新状态。死锁治理不能以牺牲原子性为代价：不能为了不持锁做 I/O，把「检查余额」和「扣减预留」分成两个不相关动作。需要重新划分临界区、事务和消息协议，而不是机械地在每个慢调用前插一个 Unlock。

## 第 8 层：怎样区分死锁、热点等待和下游卡顿？

**面试官：** 线上请求都变慢了，你怎样确定是死锁而不是正常锁竞争，修复后又怎样验证？

**面试者：** 我会先看进度是否停止及等待关系是否成环：采集 goroutine 堆栈、阻塞与 mutex 相关证据、数据库等待者/持有者和事务时间，并把它们关联到 owner、市场、账户和请求。热点竞争通常还有工作持续完成；慢 RPC 会有外部等待但不一定有环；死锁需要定位具体循环，不能只凭一个堆栈里出现 Lock 就下结论。

验证时构造 A→B 与 B→A 的反向转账，以及 owner 等待会回调 owner 的依赖，受控让两侧都拿到第一份资源再继续。改为稳定顺序或单向消息协议后，检查操作能完成、不变量仍成立、超时和回滚不产生重复经济效果。Go 运行时的全局死锁提示只能捕捉特定整体停滞，不能覆盖有其他 goroutine 活着的局部死锁；本稿提出证据与场景，不虚构已运行的诊断结果。

## 本题收束

- **讲透的机制：** 资源稳定全序、跨资源层级、owner 调用的等待图，以及短临界区与状态原子性之间的正确边界。
- **最容易答错：** 按买卖角色锁账户；持读锁升级；认为 TryLock 失败后可以读；认为加超时就等于设计无死锁。
- **检验反例：** 没有任何 mutex 的两个 owner，若各自同步等待对方处理消息，也能永久互等。能画出这条等待环，才算真正理解死锁边界。
