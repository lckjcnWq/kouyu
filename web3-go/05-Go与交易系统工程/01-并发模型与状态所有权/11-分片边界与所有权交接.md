# 大问题 11：怎样分片和交接 owner，同时保持原来的业务不变量？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 分片 / 分片键 | 按某个业务归属把工作拆到不同执行范围。 | 先看哪些数据必须一起裁决，再选按市场、账户或其他身份拆分。 |
| 不变量 / 价格时间优先 | 始终不能破坏的约束，以及先比价格、同价再比权威先后的匹配规则。 | 不能把同一个簿随机分给多个独立 owner，再靠拼结果维持规则。 |
| 市场 owner / 热点 | 一个市场的唯一有效裁决者，以及流量集中到某个局部的情况。 | 多市场可并行，不表示单一热门市场能按 goroutine 数线性扩容。 |
| 共享账户 / 子账户 | 多市场共同使用的一份资产，与显式划拨后的不同资金范围。 | 各市场复制一份 1500 不是资金分片，会共同批准超过真实余额的占用。 |
| 买卖方向分片 | 买方和卖方分给不同执行者。 | 每次成交仍要协调双方价格、数量和优先级，依赖没有自动消失。 |
| 已受理位置 / appliedSeq | 命令已经接到哪里，与结果已经确定到哪里。 | 日志接到 m 不代表执行到 m，交接必须按可信执行前缀。 |
| cutoff k / 可信快照 | 固定的停止推进位置，以及准确对应完整已提交状态的快照。 | 旧 owner 停在 k，新 owner 恢复到 k，再从 k+1 接续。 |
| 确定性回放 / ruleVersion | 根据固定输入和原规则重建状态，以及原规则身份。 | 不能恢复时重新询问会变化的报价，生成另一份历史。 |
| epoch / e→e+1 | 控制有效写者任期的单调版本切换。 | 新 owner 获新任期，不代表可以重写已有同序号结果。 |
| 围栏 / T_result | 在结果提交事务内拒绝旧写者的机制与边界。 | 校验任期和 expected appliedSeq；事务外查一次随后无条件写不够。 |
| MarketControl / 条件写入 | 串行化权利切换与结果提交的权威控制记录。 | 旧结果先提交就接管更新前缀；切任期先提交就拒绝旧写。 |
| 提交未知 / 旧内存 | 不知道结果是否落库，以及旧 owner 算出的候选状态。 | 先查持久事实，既不盲信旧内存，也不因无回包就认定未提交。 |
| ExecutionReport / 投影水位 | 执行回报和查询视图的处理位置。 | 只能发布持久结果；旧通知迟到不能覆盖更高水位的新视图。 |
| 外部副作用 / 幂等身份 | 数据库以外的实际操作，以及其稳定业务编号。 | 数据库围栏不会自动约束外部服务，执行端仍需对应保护。 |
| 跨库账务 / 局部原子边界 | 双方数据分在不同库，以及原先只在一个库内共同提交的范围。 | 拆库后不能继续假设 T_ledger 能一笔提交双边账，须另行设计协议。 |
| 安全 / 可用性 | 不产生冲突权威历史，与故障时仍能提供多少服务的取舍。 | 无法证明写权或可靠提交时可停推进、提供标水位旧快照，不能两主各自成交。 |

## 把整篇文章压缩成一个故事

小林把 ETH/USDT 和 BTC/USDT 分给不同 owner，两个簿可以并行处理，但小林自己的 USDT 仍是同一份账户资金，不能在两个市场各复制 1500。若 ETH 市场特别热，也不能直接拆成买方 owner 和卖方 owner，因为一笔成交本来就要求双方共同裁决。能拆的是依赖边界，不是想用多少 CPU 就切多少份。

现在要把 ETH 市场从实例 X 迁到 Y。X 停在一个完整结果已提交的位置 k，Y 从可信快照与绑定规则恢复到 k，再从 k+1 接续。控制记录把任期 e 升为 e+1，每次 T_result 都在同一事务内检查任期和前一进度。若 X 暂停后又回来，旧任期写入必须被拒绝；若 X 的结果早已先提交，Y 就采用那段更新后的事实，而不是重复造一份成交。

迁移期间账务可以按自己的游标继续处理原结果，回报也只能来自已提交批次；旧内存算出的成交不能拿来向用户承诺。若进一步把双方账户拆到不同库，原先的单库原子记账前提已经改变，必须另论跨分片协议。整篇并不承诺切换永不停机，更不把心跳失联、拿到新任期或旧进程停止通知当作有效围栏的替代品；这些仍是教学推演，未执行双实例演练。

**流程位置与核心机制：** 从单市场单写者扩展到多市场并行、账户协调与 owner 迁移。重点是分片依据、可信交接位置与旧写者围栏；完整复制共识与灾备另见[日志快照回放专题](../05-日志快照回放与故障切换/README.md)。

**必要前提：** 基线每市场只有一个活动 owner，账户仍由共同 PostgreSQL 事务保护。只有本题明确增加第二个实例、迁移或拆库时，部署条件才发生变化；不会因为扩大规模自动获得分布式事务。

## 第 1 层：为什么不按 goroutine 数量直接扩容？

**面试官：** 一个 owner 吞吐不够，把同一市场的订单平均分给多个 goroutine，不就能并行了吗？

**面试者：** 不能先按计算量切，再想办法拼业务结果。分片边界首先取决于哪些状态必须共同裁决：一个价格时间优先订单簿里的买卖单会互相影响，随意分给多个独立写者会丢失同价优先和全市场最优价格的唯一裁决。多个 goroutine 同时写一个共享簿，也只是把单写者换成更复杂的协调方案，不自动获得更高的有效吞吐。

我会先按市场分片，因为不同市场的订单簿转换相对独立，每市场仍是一条权威命令序列。鉴权、解析、只读查询和不改变业务规则的预处理可以并行；同市场有序转换是否能进一步并行，必须另行证明依赖关系，不能用 CPU 核数代替业务证明。

## 第 2 层：市场独立，账户为什么不独立？

**面试官：** 既然按 ETH/USDT 和 BTC/USDT 分片，那每个 owner 各维护 A 的 USDT 余额，是否能完全去掉竞争？

**面试者：** 不能，因为 A 在两个市场花的是同一份 USDT。各市场复制一份 1500 的余额，会让它们同时批准 1000 的预留，总共占用 2000。订单簿的局部独立不等于账户资产也独立；不同对象的不变量会产生不同分片键。

本模型保留账户域的统一修改入口，跨市场预留最终落在同一账户行的事务约束上。市场分片获得的是撮合转换的并行，不承诺消除热门账户的资金竞争。如果要把资金预先划给各市场子账户，就必须显式改变资产模型，定义额度转移、回收和故障恢复，不能在缓存里多写几份余额就称为分片。

## 第 3 层：一个市场很热，按买卖方向拆行不行？

**面试官：** 如果只有 ETH/USDT 很热，按买方和卖方各设一个 owner，是否比按市场更均衡？

**面试者：** 买卖双方恰恰需要共同形成一次匹配，分开后每次成交都要协调两个 owner：同时确定价格、剩余量、优先级和成交身份。这个边界没有切断依赖，只是把原来的本地有序转换变成跨 owner 协议。撤单与成交竞争也不能让两侧各作决定。

可以并行构建行情投影、解析消息、处理不同市场，或在明确不变量后研究确定性并行执行，但当前基线不实现方向分片。对单一热点，应先测量单 owner 的实际瓶颈、减少无关工作和控制准入；不能承诺任意热点都能靠增加消费者线性扩容，更不能在积压时让撤单越过已经受理的前序命令。

## 第 4 层：迁移怎样找到准确的交接位置？

**面试官：** 那先保持每市场单写者，只把 ETH/USDT 从实例 X 迁到 Y，你打算怎样交接？

**面试者：** 计划迁移要区分命令受理位置和执行完成位置。先确定迁移期间接入策略，可以继续将命令写入持久日志并积压，但不能把每个新命令都要求旧 owner 执行完，否则始终找不到固定交接点。旧 owner 在某个已提交结果位置 k 停止推进，并报告带规则版本和校验信息的可信快照边界；快照中的状态必须对应完整的已提交结果前缀。

新 owner 恢复到同一个 appliedSeq=k，再从 k+1 连续取未处理命令。若快照较旧，可以从可信前缀确定性回放到 k；不能把「已受理到 m」当成「已经执行到 m」，也不能把旧 owner 内存里尚未提交的第 k+1 次变化当成接管依据。账务 cursor 可以落后于 k，它按自己的持久进度继续消费，不需要为迁移重复记账。

## 第 5 层：旧进程没有真的停掉怎么办？

**面试官：** X 说已经停了，但实际因为网络暂停过几秒又恢复，它继续提交结果怎么办？

**面试者：** 所以不能只相信停止通知或心跳。控制面在数据库中以受控事务将该市场 ownerEpoch 从 e 改为 e+1，Y 取得新 epoch；每次 T_result 都必须在同一提交事务中锁定或条件更新 MarketControl，检查自己的 epoch 仍有效以及 expected appliedSeq 正确。X 持旧 epoch 的后续写入必须在持久边界被拒绝。

epoch 切换和旧结果提交若竞争，需要在同一权威控制行上串行化：若旧事务先提交，新 owner 从更新后的前缀接管；若 epoch 切换先提交，旧事务就不能再提交。只在事务外读一次 epoch，随后无条件写结果，会留下检查与使用之间的缺口。围栏保护的是实际写入点，不是日志中打印了一句「我是主」。

## 第 6 层：拿到新 epoch 后能马上发用户回报吗？

**面试官：** 数据库拒绝旧写入就够了吧？即使 X 还在推送行情，也只是旧数据而已。

**面试者：** 要看推送的是什么。若 X 把未提交的内存成交当成新事实发布，用户可能收到数据库中不存在的成交，即使资金端拒绝记账，业务承诺也已经被破坏。本模型要求只有持久提交的 OutcomeBatch 才能生成权威执行回报；旧实例可以重投过去已提交结果，但不能发布自己的新推演。

回报和投影带上 market、cmdSeq 和必要的 epoch，消费者按已提交序号去重、识别缺口或较旧版本，不能用网络到达顺序覆盖新视图。epoch 也不是允许重写同 seq 结果的理由：同一个已提交命令位置只能对应原来的结果。若系统还有数据库之外的直接外部副作用，其执行端也要接受围栏或稳定幂等身份，不能假设数据库 epoch 自动约束外部服务。

## 第 7 层：旧 owner 已经改了内存但没提交怎么办？

**面试官：** X 在 epoch 切换前已经算出了 101 的成交，切换后提交被拒绝，Y 应该采用它的内存结果还是重新撮合？

**面试者：** 新 owner 只信可信的持久前缀。先查 101 的结果与 appliedSeq：若 T_result 已提交，就采用同一批次；若确认没有提交，则从 100 的可信状态按已提交命令 101 和绑定规则版本恢复处理。旧内存不能作为比数据库更高等级的事实，但也不能因为没收到提交响应就假设它肯定没提交。

恢复计算要有确定性依据，例如输入字段、规则版本和必要的外部决策结果已固化，不能重新调用一个随时间变化的外部报价再产生不同成交。本案例完全由订单簿和命令顺序决定。恢复期间不发布第 101 次暂态，也不继续在未知结果上算 102；围栏解决谁能写，确定性与持久结果解决写什么，这两层不能相互替代。

## 第 8 层：账户也拆库之后原方案还成立吗？

**面试官：** 市场迁移可以了，如果下一步把买卖双方账户放进不同数据库，还能沿用一笔 T_ledger 吗？

**面试者：** 不能，这是明确改变了共同事务条件。原来一笔 PostgreSQL 事务可同时提交双边账，现在两个库各自提交，可能出现一侧成功、一侧未知。进程内锁和统一 epoch 都不能把两个库恢复成一个原子提交域。需要重新选择协议，例如可用的分布式事务，或用可审计的持久成交义务、限制余额可用性和确定的跨分片结算状态机。

必须明确哪些资金在中间阶段不能使用、谁协调、重试身份是什么、怎样在部分提交和协调者重启后继续；不能用「一边失败就反向转账」掩盖已被花掉的资产。当前专题不声称实现拆库方案，继续保留同库账务基线。正确扩展的前提，是承认原局部原子边界已经消失，而不是把分片当作透明配置项。

## 第 9 层：围栏能够保证永远不停服务吗？

**面试官：** 你坚持每次写入校验 epoch，会不会在数据库或控制面暂时不可达时让系统停下来？能不能先在本地继续成交？

**面试者：** 会影响可用性，但不能在无法证明有效写权或无法持久提交结果时，仍对外承诺权威成交。本模型可以继续提供已提交的只读快照并标记进度，或按既定准入策略拒绝新工作；不能为了响应速度让新旧 owner 都各自确认成交，再指望恢复后合并两个不同的订单簿历史。

租约可以帮助发现失联、降低切换等待，副本复制可以提高持久化可用性，但安全承诺仍取决于具体提交条件和围栏的权威存储。要提高可用性，应设计并验证数据库/日志的复制、接管及故障假设，而不是把本地内存当临时真相源。单进程串行也无法跨越这个故障边界。

## 第 10 层：怎么验证交接没有双写或遗漏？

**面试官：** 怎样设计一组有说服力的交接场景，证明迁移后不是表面上只有一个主？

**面试者：** 我会让 X 在读到 epoch=e 后暂停，Y 将 epoch 提升并接管，然后恢复 X 的结果提交，预期旧写被拒绝。再反过来让旧结果先提交、随后切 epoch，要求 Y 必须看到更新后的前缀，不能重复产生第 101 批次。两种竞争都要检查 T_result 的实际条件写入，而不是只检查某个进程已停止心跳。

随后比较迁移前后连续的命令与结果序号、O1 的数量守恒、101/102 的稳定身份和账务最终余额；在快照落后、通知重复、旧投影迟到时也不能覆盖新结果。还要保留恢复进度与失败分支证据，证明旧主隔离和新主可推进分别成立。本稿提供静态推演方法，没有执行双实例迁移或故障注入，也不宣称已经验证高可用。

## 本题收束

- **讲透的机制：** 按不变量选分片键，按持久前缀交接状态，在真实写入边界校验 epoch，并保留确定性恢复与外部副作用约束。
- **最容易答错：** 每市场复制一份共享账户余额；按买卖方向拆簿；把租约到期当旧写者已停止；拆库后继续假设本地事务存在。
- **检验反例：** 旧 owner 已在事务外通过 epoch 检查，暂停后新 owner 接管，旧 owner 仍无条件写成功。只要这个时序成立，系统就没有完成有效围栏。
