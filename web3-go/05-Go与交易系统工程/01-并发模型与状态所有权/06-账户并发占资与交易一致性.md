# 大问题 6：怎样保证账户并发占资，以及订单、成交与资产的一致性？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 并发占资 / 超买 | 多个订单同时申请同一账户资金，以及申请总额超过真正可分配资金的错误。 | 初始 1500，两个市场各要 1000，不能两边都按旧读数批准。 |
| 可用 / 预留 / reservationID | 还能使用的金额、已为订单占住的金额、占用记录的稳定编号。 | 预留不是扣费；1000 最终分成支出 400、释放 600、仍冻结 0。 |
| 安全性 / 处理进度 | 必须始终守住底线，与已经完成到哪个阶段的区别。 | 不许重复花钱，但允许裁决已确定而账务暂时落后。 |
| 账户行锁 / 条件更新 | 在数据库共同记录上串行检查写入，或只在金额足够时原子扣减。 | 判断和预留不能分开；条件更新还须连同预留、受理事实共同提交。 |
| 本地 mutex / 缓存 | 只协调一个进程的锁，以及面向读取的副本。 | 都不能单独决定跨实例共享账户的花费资格。 |
| T_admit / 同库事务 | 将幂等身份、资金变化、预留和 New 命令一起提交。 | 当前条件是同一个 PostgreSQL 库，不宣称跨库也天然原子。 |
| account + requestID / 载荷 | 稳定业务请求身份及具体下单内容。 | 同身份同内容找回原命令；不能借重试把 10 手改成 20 手。 |
| 提交未知 / context | 不知道事务是否已成功，以及控制本地等待的上下文。 | 超时不是回滚证明；查询暂时没找到也不能直接退款。 |
| OutcomeBatch / tradeID | 一条命令的完整结果，以及一笔成交不随重发变化的身份。 | 扫多个卖单不能只交一半结果，重发不能另造第二笔成交。 |
| T_result / Outbox | 共同提交裁决、待交付记录和执行进度的结果事务。 | 消息可补发、可重复，但未提交的候选成交不能对外发布。 |
| epoch / appliedSeq | 有资格写结果的任期和结果已完成的位置。 | 结果写入事务检查有效写权与前一进度，不能只在事务外看一眼。 |
| T_ledger / 去重 | 资产变化、双边分录、消费身份和账务进度共同提交。 | 先记“已消费”再改余额会漏记；反过来分开提交会重记。 |
| cursor / 连续批次 | 账务已处理位置，以及不跳过中间义务的推进规则。 | 102 撤单先到也要补齐 101，不能先把原始预留全部退掉。 |
| 执行拒绝 / 释放义务 | 已受理命令的确定拒绝结果，以及它授权退还的剩余预留。 | 未知不等于拒绝；释放必须由完整确定结果产生，不能靠超时计时器。 |
| 对账 / 受控修复 | 找出身份、进度或分录差异，再沿正式规则补齐。 | 总额碰巧相等不证明每个用户正确，管理员也不能直接改余额凑平。 |

## 把整篇文章压缩成一个故事

小林账户有 1500 USDT，同时在两个市场各下一个要占 1000 的买单。两个请求都曾看到 1500 不重要，重要的是必须在共同数据库中把检查、扣可用、增加预留和受理命令放进同一事务。先成功的一笔留下 500，后一笔要按这个当前状态判断，不能拿缓存或本地锁给第二个实例再批 1000。

沿成功的 O1 继续，New101 成交 4 手、Cancel102 撤余下 6 手。市场先提交完整结果和 outbox，账务再把双边资产、预留变化、去重和 cursor 共同提交。即使 102 先送达，也要等到或补回 101，先支出 400 并给小林记入 0.4 ETH，再释放 600；最终可用 1100、预留 0，卖方收到 400 USDT。重复送同一批次不能重复产生经济效果。

如果受理响应丢失，小林按原请求身份查进度，而不是换编号再下；若受理后最终执行拒绝，也得由确定的拒绝批次产生释放义务。对账负责定位卡在哪个提交或交付窗口，修复仍沿原身份与正式账务规则，不靠“超时就退款”或管理员改数。整篇的一致性来自几个闭合的局部事务与交接协议，不是假装全链路没有暂态，也不是事后对账可以替事前约束兜底。

**流程位置与核心机制：** 串联受理预留、市场裁决、成交交付和账务结转，给出本专题独立的交易一致性回答。不同于[母题 05](05-成交撤单竞争与线性化.md)聚焦订单竞争，这里重点是跨模块原子边界与异常收敛，不完整扩写账本产品设计。

**必要前提：** 同一个 PostgreSQL 数据库保存受理、预留、执行结果与账务事实，但它们属于不同事务。A 初始 1500 USDT，O1 预留 1000；成交 400、撤单释放 600，最终可用 1100 USDT。市场 owner 只决定执行，不直接改账户余额。

## 第 1 层：怎样把交易一致性说成可验证的保证？

**面试官：** 你怎样保证并发下单、成交与撤单之后，订单、成交和买卖双方资产始终对得上？

**面试者：** 我会先分清必须始终成立的安全约束和允许落后的处理阶段。安全上，账户不能重复花同一笔可用资产，订单数量必须守恒，同一成交不能产生两次经济效果，撤单不能释放已成交的资产。进度上，允许执行结果已确定而账务尚未追上，但欠下的成交与释放义务必须是持久、可重试、能定位责任的事实。

本案例的订单约束是 `10=成交4+撤销6+剩余0`，买方预留去向是 `1000=支出400+释放600+仍冻结0`。保证来自三个局部原子边界：受理与预留共同提交，执行结果完整提交，账务资产变化与消费去重共同提交。Go 并发模型负责不绕过这些边界，不能用一个进程内 mutex 宣称整个链路已经是全局事务。

## 第 2 层：两笔订单都看到 1500 怎么办？

**面试官：** 你说不能重复花余额，如果 O1 和另一市场的 O2 同时各申请 1000 USDT，两个 goroutine 都读到 1500，具体如何阻止超买？

**面试者：** 不能把「读取余额判断足够」和「扣可用、增加预留」分开执行。本模型由账户域在数据库事务中锁定账户行，读取当前可用量后检查并更新，同时创建稳定 reservationID。第一笔把 1500 改成 500 后，第二笔必须基于锁定后看到的新状态判断，不得沿用事务外缓存的 1500。

可以用满足条件的原子更新结合受影响行数实现同类约束，但相关预留记录与命令受理仍要同事务。本模型不依赖某个实例的 account mutex，因为另一市场或另一个服务实例可以同时请求同账户。数据库事务保护的是共同的账户真相，缓存只做提示或查询投影，不能授予花费资格。

## 第 3 层：预留成功但没有写入市场命令怎么办？

**面试官：** 你把余额锁住了，但扣掉 1000 后进程崩溃、命令没发出去，不就一直冻结了吗？

**面试者：** 所以在当前同库基线下，T_admit 不是先扣款再调一次 RPC，而是同一个数据库事务提交四类关联事实：请求幂等身份、账户可用/预留变化、reservation、带市场 cmdSeq 的 New 命令。失败回滚时四者都不生效；提交成功后，即使内存通知没发出，owner 仍能扫描日志找到命令。

事务遵循先市场控制行、再账户行的锁序，不能拿着这些数据库锁等待外部系统。这个方案利用了同一数据库的条件，不能推广成跨数据库也天然原子。若未来拆库，就必须显式引入可靠预留意图与接纳/作废竞争协议；那是改变部署条件后的新设计，不能在本题中靠一句「最终一致」跳过中间窗口。

## 第 4 层：事务超时是否可以当成失败？

**面试官：** T_admit 变成一笔事务，但客户端超时没收到 Accepted，你能直接释放并建议重新下单吗？

**面试者：** 不能。调用超时只说明没有观察到确定响应，不证明事务没有提交。客户端或恢复任务应沿用原 `(account, requestID)` 和规范化载荷查询；已提交则返回同一个 orderID、reservationID 和 cmdSeq，未确定时明确标记结果未知，不换一个请求身份再次占资。

相同身份不同载荷必须拒绝，不能让原来 10 手的请求重试成 20 手。对于原请求与取消同时发生，要么恢复原受理结果后提交有序 Cancel，要么设计同一请求意图的持久终态，确保「确认未受理」与原命令迟到不会并存；不能做一次普通查询没查到就猜测释放。当前基线通过原身份恢复加市场 Cancel 闭合，不声称 context.Done 是数据库撤销证明。

## 第 5 层：单 owner 为什么不能直接发成交消息？

**面试官：** 好，订单已经可靠受理。owner 在内存撮合成功后直接发消息给账务，不就完成下一段了吗？

**面试者：** 如果先改内存再尽力发消息，进程在两者之间崩溃，可能有成交但账务永远不知道；先发消息后记录结果，又可能让账务消费到恢复后无法重现的成交。因此 owner 先生成完整 OutcomeBatch，在 T_result 内同时提交批次、outbox 和 appliedSeq，校验有效 epoch 及上一处理位置，成功后才发布执行回报和快照。

批次包括本命令所有成交、订单变化和预留处理指令，不能一笔扫多个卖单只提交一半成交。tradeID 固定为类似 `(market,cmdSeq,tradeIndex)` 的业务身份，重发不换 ID。outbox 负责提交后的补交付，重复允许发生；不承诺消息中间件替业务完成恰好一次记账。

## 第 6 层：消息重复时，只先写去重标记够不够？

**面试官：** 你允许重复交付，账务先写一个已消费标记，再异步改双方余额，能不能避免重复？

**面试者：** 不够。先提交去重再改余额，崩溃后会因为「已经处理」而漏记；先改余额后补标记，则会在重试时重复记账。本模型的 T_ledger 在同一事务内提交消费身份、双边分录、预留消耗与释放，以及该市场账务游标，只有全部提交才算消费完成。

主案例 101 消耗 A 的 400 USDT 预留并增加 A 的 0.4 ETH，同时消耗 B 的 0.4 ETH 预留并增加 B 的 400 USDT。买卖账户按稳定顺序锁定，避免不同方向交易反向拿锁。批次若已完整提交，重投返回已有事实而不再变化资产；事务回滚则可用同身份重试，不能让一侧提交、另一侧留给一次不可靠补偿调用。

## 第 7 层：撤单先到达账务，能不能先退款？

**面试官：** 如果 102 的撤单批次先到达，而 101 的成交批次延迟，你不能一直卡着用户退款吧？

**面试者：** 可以降低等待，但不能改变正确性条件。消费者以持久账务 cursor 要求本市场连续批次：若当前只处理到 100，却收到 102，就识别缺口并补拉或等待 101，不立即执行释放。先消费 101 后，O1 预留从 1000 降为 600，102 再精确释放 600。

不能把「总览里我知道成交了 400」当成消费者可跳步的证明，因为它还必须处理买卖双方和去重。可以另行设计带依赖与可交换操作的更细并行协议，但要证明释放不会超越待结算义务；当前基线选择连续批次以换取可证明性，并承认一个缺口会阻塞该市场的后续记账。

## 第 8 层：受理后最终被拒绝，预留由谁释放？

**面试官：** 你一直讨论合法成交，如果 New 可靠受理后，在执行时因业务条件被拒绝，1000 USDT 会不会一直占着？

**面试者：** Accepted 只说明进入处理序列，不保证订单一定被挂入簿。对于已受理但最终执行拒绝的命令，owner 也必须提交一个完整、可恢复的结果批次，明确拒绝原因与该 reservation 的释放义务；账务按同一连续消费规则执行，而不是接入层另外启动一个超时退款计时器。

释放数量应依据尚未消费的预留，且结果与身份都不能由重试重新生成。本案例若独立变体中 O1 完全未被接纳、未成交，合法拒绝才可释放原 1000；若已经有成交，释放必须以最终裁决后的剩余义务为依据。未知状态不是拒绝，系统不能为了让冻结数字消失，制造「已经能成交又已经退钱」的双重资格。

## 第 9 层：有了一致性协议，还需要对账做什么？

**面试官：** 这些事务和去重都做了，再加对账是不是就足以兜底所有问题？

**面试者：** 对账是发现缺口和启动受控修复，不是允许事前跳过原子边界。它可以比较命令受理与结果进度、结果批次与账务 cursor、每个 reservation 的去向，以及双边资产分录；发现「102 已提交但账务仍在 100」就查 101 的交付或消费错误，而不是直接把 1000 解冻。

修复仍要引用稳定的原始业务身份，通过同一账务写入规则和审计流程，不能管理员直接改余额让总数看起来相等。恢复也要区分数据库提交事实、内存视图和消息投递尝试；对账无法仅凭一个相等的总额证明每个用户都被正确记账，必须保留订单、成交、预留与账户的关联证据。

## 第 10 层：怎样验证这套保证的边界？

**面试官：** 你会选哪些最少的竞争与失败场景，检查这套一致性方案是否真的闭环？

**面试者：** 第一组是两个市场同时给 A 各预留 1000，检查最多只有一笔占资成功，可用不能为负。第二组是在 T_admit 提交成功但返回丢失后重试，要求原身份返回同一命令，不产生第二份预留。第三组在 T_result 提交前后分别中断通知，要求只有已提交结果能被发布或恢复，且成交身份不变。

第四组将 102 先交付、101 后交付，并重复投递两者，最终仍必须得到 A 可用 1100、预留 0、ETH 0.4，B 收到 400，且账务 cursor 连续。每组既检查安全性，也检查补拉或重试后能继续推进；没有实际执行与故障注入记录时，只能说这是验证计划和手工预期，不能声称事务或 race 工具已经证明了整个系统。

## 本题收束

- **讲透的机制：** 以账户不变量确定原子范围，以完整结果确定跨模块义务，以消费事务连接去重与资产变化。
- **最容易答错：** 用本地锁保护多实例余额；把超时当回滚；去重与记账分两次提交；跳过成交直接处理撤单释放。
- **检验反例：** 如果 102 先到就能把原始 1000 全部解冻，而 101 之后仍能结算 400，这套协议已经允许重复使用资产，无论是否发生 data race 都不合格。
