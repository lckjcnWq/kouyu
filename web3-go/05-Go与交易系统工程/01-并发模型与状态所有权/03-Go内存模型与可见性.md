# 大问题 3：Go 怎样保证撮合状态对其他 goroutine 可见，这与业务正确性有何区别？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| owner / goroutine | goroutine 是并发执行任务；owner 是被指定为某份状态唯一管理者的任务。 | 市场 owner 独占订单簿的修改权，但查询 goroutine 直接读可变簿仍可能与它冲突。 |
| Go 内存模型 / 可见性 | 规定并发任务之间，什么写入能通过同步被另一个任务可靠观察到。 | 解决进程内怎样交接数据，不证明数据库已持久化，更不替跨服务交易保证一致性。 |
| happens-before / synchronizes-before | 前者是由程序顺序和同步关系串出的先后链，后者是其中明确的同步连接。 | 要指出具体哪次解锁、发送或原子发布连接了读写；睡一会儿、日志时间更早都不算。 |
| 数据竞争 | 多个任务未正确同步地访问同一内存位置，且至少一个在写。 | 一个写者加多个读者仍可能有竞争；单写者并不自动保护所有查询。 |
| DRF-SC / 顺序一致性 | 无数据竞争的程序可以按遵守各任务内部顺序的交错执行来理解。 | 合法交错仍可能把不同版本字段拼在一起；它不等于多个字段组成一次业务事务。 |
| channel / send / receive | channel 交接值；一次发送与对应接收之间有规定的同步关系。 | 接收方能看到发送前的初始化，但 send 返回不证明接收后的业务处理已经结束。 |
| close / done / WaitGroup | close 关闭通道；专用 done 信号或 WaitGroup 可按协议通知并等待工作完成。 | 只有约定工作确实先完成，再发完成信号才有意义；关闭数据队列或取消信号不等于任务已结束。 |
| Mutex / RWMutex | 让遵守同一套锁规则的访问者协调读写范围。 | 锁要覆盖相关字段的共同读写；锁内取出指针、解锁后继续读可变内容仍不安全。 |
| sync.Once | 让同一项初始化按协议只执行一次，并把初始化结果同步给调用者。 | 适合初始化后只读的规则表，不负责后续热更新，初始化 panic 后也不会自动重试。 |
| atomic.Pointer / Store / Load | 用原子操作发布和获取一个对象指针。 | 先完整构造快照再 Store；Load 观察到该 Store 才建立相应发布关系，不会给对象内部自动加锁。 |
| 不可变快照 / 别名 | 快照是一份固定版本；别名是不同引用仍指向同一块数据。 | 发布后连可达的 slice、map 和订单对象都不能再改，也不能与可变簿共享会被改写的内容。 |
| cmdSeq / seq | 市场命令及其结果在权威历史里的顺序编号。 | seq101 先成交 4 手，seq102 再撤 6 手；worker 谁先完成不能改变这个顺序。 |
| appliedSeq | 已完整提交结果的连续命令前缀，表示处理确认到了哪里。 | 查询要标明快照对应的进度；读到一致版本不代表已经追到最新命令。 |
| epoch | 当前执行者的所有权代际，类似随所有权交接更新的任职编号。 | 结果事务必须校验有效代际，防止旧执行者继续承诺新结果，不能只在内存里检查。 |
| T_result | 把一次命令的完整裁决结果可靠提交到数据库的事务。 | 确认成功后才能发布新快照；提交失败或未知时，冻结推进并核对持久事实。 |
| OutcomeBatch / outbox | 前者是一条命令的完整结果包，后者是与结果一起持久保存的待交付事件。 | 它们与 appliedSeq 同事务提交；channel 通知和原子指针都不能替代这份持久依据。 |
| ExecutionReport | 对外报告订单裁决结果的回报。 | 只能在对应结果确认提交后发布；已经发布不保证网络按序送达，也不证明客户端已收到。 |
| 账务提交 / 账务进度 | 把成交支出、资产变化和预留消耗或释放真正记入账户。 | 市场快照已提交不等于账户已经记到同一 seq，资金结论仍要核对账务事务及进度。 |

## 把整篇文章压缩成一个故事

沿用无手续费的 ETH/USDT 现货教学例子，1 手是 0.1 ETH。A 的 O1 买 10 手，市场 owner 在 seq101 裁决成交 4 手、剩余 6 手，再在 seq102 撤掉这 6 手。查询 goroutine 想给 A 展示订单进度：如果直接盯着 owner 正在修改的订单，只有一个写者也可能发生数据竞争；即使各字段分别改成 atomic，也可能拼出“成交 4 手、剩余 10 手”这种从未成立的订单版本。

于是 owner 不再把可变簿交给查询，而是先构造与簿脱离的完整快照，在对应 T_result 确认成功后，用 channel、共同的锁或 atomic.Pointer 按明确协议发布。查询每次取定一个版本，只读这一版里的数量和 seq；快照里的数组、映射和指针所指内容也不能在发布后改写。channel 发送返回只说明本地交接到了规定位置，无缓冲发送也不证明接收方已处理完；若要等待工作结束，必须由真正完成工作的一方发完成信号，或按规则 Done 后由另一方 Wait。

最后还要防一件没有数据竞争也会发生的错事：两个 worker 先发布 seq102，再发布 seq101，A 就会看到订单从已撤退回活跃。因此由 owner 按连续提交结果唯一发布，数据库同时检查 appliedSeq 和有效 epoch；提交未知就停下推进与新状态发布，查完整持久结果，查询最多继续展示标明进度的最后已提交快照。内存可见性不等于持久化，完整快照也不等于账务已完成；本故事只是设计推演，不是 race 检测或运行测试结果。

**流程位置与核心机制：** 聚焦市场 owner 向查询与回报 goroutine 交付状态时的 happens-before、channel 同步、锁与原子发布。解释“内存可见、没有数据竞争、读到完整快照、结果已经持久提交”为什么不是同一件事；对象交接协议在下一母题细化。

**必要前提：** Go 1.21+；使用总览中的链下托管现货 GTC 限价订单簿。每市场一个 owner goroutine，独占订单簿与订单状态，查询只能读取带 seq 的不可变已提交快照，不读取可变簿。

- ETH/USDT，1 手 = 0.1 ETH，100 USDT/手。A 初始可用 1500 USDT，O1 买 10 手预留 1000 USDT；B 的 S1 有已预留的 4 手卖资产。
- seq101 前 S1 已是可信状态，appliedSeq = 100；seq101 成交 4 手，seq102 撤剩余 6 手。账务完成后 A 可用 1100 USDT、冻结 0、新增 0.4 ETH；B 收 400 USDT。
- T_result 使用共享市场 control 行锁、期望 appliedSeq 与有效 epoch，同事务提交完整 OutcomeBatch、outbox 和 appliedSeq；成功后才允许发布快照与 ExecutionReport。
- 内存模型约束同一进程内的执行，跨实例资产约束仍由 PostgreSQL 事务与账户行锁保证；每个异常变体独立讨论。

## 第 1 层：只有一个写者，为什么查询仍然可能发生数据竞争

**面试官：** 市场订单只有 owner 一个写者，查询 goroutine 从不修改订单。为什么不能让它们直接读订单对象？Go 内存模型到底要求补什么？

**面试者：** 一个写者加多个读者仍然可能并发访问同一内存位置；只要存在未正确同步的读写冲突，就可能构成数据竞争。
owner 唯一写入解决的是写权限归属，不会自动让其他 goroutine 的读取获得可见性保证，更不会让多个字段自然组成一致快照。

我会先找 happens-before 关系，而不是用“写得早、读得晚”解释。它由 goroutine 内的程序顺序与同步关系传递形成；墙上时间、打印日志顺序和短暂 sleep 都不是同步协议。
创建 goroutine 的 go 语句先于该 goroutine 开始执行，但 goroutine 后续对共享对象的修改，不会因此自动同步给所有其他读者。

如果采用 Mutex，写者解锁与后续按规则成功加锁的读者之间可以建立同步；如果采用 channel，也必须指出是哪次 send 与哪次 receive 建立关系。
如果是只初始化一次的共享规则表，也可以用同一个 sync.Once 的 Do：初始化函数完成同步先于相关 Do 返回，再由调用者只读。它不负责后续热更新；函数 panic 后普通 Once 仍视为已执行，不会自动重试。
没有这种依据，不能假设查询一定看到最新剩余量，更不能假设“已成交量”和“剩余量”来自同一个订单版本。

本模型因此不让查询直接观察可变订单对象。owner 先形成已提交版本的独立快照，再通过明确同步手段发布；读者拿到这个版本后只读。
后续讨论的关键是如何安全发布这个对象，而不是把“单写者”误当作语言自动提供的全体读者屏障。

## 第 2 层：channel 具体同步哪两步，不同步什么

**面试官：** 那就让 owner 把快照发到 channel。能不能准确说明，接收方为什么能看到快照字段，以及发送方返回后能不能认为接收方已经读完？

**面试者：** Go 的保证是：一次 channel send synchronizes-before 对应 receive 的完成。发送前已完成的快照初始化，经这个同步关系传递到接收方，接收完成后可以按协议读取。
因此需要说明是哪个值对应哪次接收，而不是泛泛说“经过 channel 的所有对象从此都线程安全”。

这个关系的方向首先是发送侧发布给接收侧。对于无缓冲 channel，还存在对应 receive synchronizes-before 那次 send 完成的反向关系。
但这也不表示接收方在 receive 返回后执行的业务逻辑都已经完成；读快照、写回报等动作发生在接收之后，发送方不能仅凭 send 返回就认为它们结束。

对有缓冲 channel，send 完成甚至可能发生在消费者开始接收之前，不能套用无缓冲 channel 的反向保证。
容量为 C 时，第 k 次 receive synchronizes-before 第 k+C 次 send 完成，是缓冲槽位复用的特定关系；它不是“当前这次 send 会等自己的消费者处理完”。

所以 channel 足以作为一次发布同步，但发送完成不是消费完成，更不是 T_result 已提交的证明。
若要知道消费者处理结束，必须另有明确完成信号；若要知道业务提交成功，则必须核对对应持久结果，不能把这两种确认混在一起。

## 第 3 层：close 和 goroutine 退出能不能充当处理完成通知

**面试官：** 你要求额外完成信号。消费者关闭 done channel，或者处理完直接退出 goroutine，不都能表示“已经结束”吗？缓冲 channel 被关闭又怎么解释？

**面试者：** 如果消费者先完成约定工作、再关闭专用 done channel，等待方因该关闭而返回零值的 receive，能够通过 close synchronizes-before 这次接收建立完成关系。
这里的前提是 close 被定义为那项工作的完成通知，而且前面的写入确实属于关闭前的执行顺序，不是另一个还在运行的 worker 的未同步写入。

关闭业务数据 channel 的语义不同：缓冲区里的旧值仍会先被接收，接收旧值有对应 send 的同步依据，不能把它一概解释为“已经因关闭收到零值”。
close 本身也不等待消费方把缓冲值处理完，更不等待它们的数据库事务完成；生产者关队列只表示不再发送，不代表整条链路已经清空。

goroutine 自行退出则没有自动同步给其他 goroutine 的保证。需要 WaitGroup、专用完成 channel 等同步方式，由等待方观察约定的结束点。
例如 WaitGroup 中与某次 Wait 解阻塞相对应的 Done 可以建立完成关系，但前提仍是工作确实在 Done 前完成，不能提前 Done 再继续异步写状态。

context.Done() 的关闭只表达取消通知，不自动表达任务已退出、结果已提交或剩余预留已释放。
所以完成协议要写明“谁在什么之后发信号，谁等待该信号”，不能用“channel 已关闭”四个字同时代替停止接收、处理完成和业务撤销。

## 第 4 层：改用 Mutex，就能读取完整订单状态吗

**面试官：** channel 的完成语义这么容易混淆，我把快照放进共享字段，用 Mutex 保护读写。这样是否既解决可见性，又解决完整状态？

**面试者：** 在全部访问者遵守同一把锁时，可以。对同一 Mutex，前一次 Unlock synchronizes-before 后续相应的 Lock 返回；写者在临界区完成的写入，能通过这个关系被后续持锁读者看到。
但要区分“可见”与“完整”：锁必须保护所需字段的共同读写范围，不能写者分别锁一次成交量、一次剩余量，读者再把两个不同版本拼成一个订单。

读者也不能在锁内拿到订单指针，解锁后继续读取仍会变化的内容。那样受保护的只是“取指针”动作，不是指针所指对象后续的访问。
如果要解锁后使用，应在锁内复制出独立不可变数据，或另有可证明的对象生命周期协议。RWMutex 的读锁同样不会让被引用对象自动冻结。

此外，锁住内存不意味着读到的是已持久提交状态。owner 可能已经更新内存、T_result 仍在等待，此时合法加锁的查询仍可能看到一个禁止对外承诺的候选版本。
本基线要求查询字段只指向提交成功后发布的快照；结果事务失败或未知时冻结推进与新状态发布，可提供标明 appliedSeq 的最后已提交只读快照，但不保证已追上最新，不能让 Mutex 给候选内存“背书”。

因此 Mutex 可以同时建立可见性并保护复合读取，但它的能力范围由临界区与发布协议决定。
它没有代替数据库事务，也没有代替按 cmdSeq 裁决；如果读路径希望避免每次加读锁，就需要另一种同样明确的不可变对象发布方式。

## 第 5 层：atomic.Pointer 发布快照，为什么不仅是原子读指针

**面试官：** 你说查询可以不加读锁。如果 owner 用 atomic.Pointer 发布快照，读者 Load 后直接访问整个对象，为什么对象字段也能正确可见？

**面试者：** 正确做法是先完整构造一个私有快照，在 T_result 确认成功后用 atomic.Pointer.Store 发布；查询只用对应的原子 Load 获取版本，再读取对象。
Go 的原子操作具有顺序一致语义；当原子 Load 观察到某次原子 Store 的效果时，那次 Store synchronizes-before 该 Load，发布前的初始化写入得以传递给读者。

但原子保护的是指针位置的访问与发布关系，不是对整个可达对象图持续加锁。发布之后继续改 snapshot.Orders、复用 slice 底层数组，或修改其中共享的订单指针，仍然可能与读者竞争。
所以快照不可变必须是深层可达数据的协议，不是把外层变量声明成 atomic.Pointer 就完成；构造时应切断与可变簿的别名。

读者每次请求只 Load 一次快照指针，再从同一个版本读取 seq、订单状态和数量，不能每读一个字段都重新 Load 并拼接不同版本。
这种做法保证读到一个完整已发布版本，不保证它是全世界最新时刻，也不保证账户账务已经追到同一 seq；版本和账务进度仍需分别说明。

所有对该发布位置的并发访问都要使用对应原子协议，不能某处原子 Load、另一处普通写；已经包含原子同步对象的结构也不能随意复制当成新的共享变量。
安全发布的收益来自“完整初始化 → 同步发布 → 发布后不变”，三步缺一不可，不是来自原子 API 的名称。

## 第 6 层：每个字段都用 atomic，为什么还可能得到不存在的订单版本

**面试官：** 深复制可能有成本。既然原子操作顺序一致，我把订单状态、已成交量和剩余量分别改成 atomic，是否就可以不做快照了？

**面试者：** 不能据此保证复合业务状态一致。假设某版本为已成交 0、剩余 10，另一版本为已成交 4、剩余 6，写者分两次原子 Store 更新。
读者的两次 Load 可能夹在这些 Store 之间，得到已成交 4、剩余 10，或者得到已成交 0、剩余 6；每次原子访问都合法，但拼出来的状态不满足订单数量守恒。

顺序一致意味着这些原子操作可以按一个符合各 goroutine 顺序的全局交错来理解，不意味着多个操作被合并成一次不可分割事务。
Go 的 DRF-SC 保证同样不能越界理解：无数据竞争的程序可以按顺序一致的交错执行解释，但交错仍有多个，业务不变量不会由语言替你补上。

对需要共同读取的订单版本，应使用一次发布的不可变快照，或把共同读写置于同一临界区。
若使用版本校验重试等替代设计，还必须证明在 Go 中全部相关内存访问本身合法，不能先无锁读写普通字段、最后发现版本变化就声称此前的数据竞争无效。

在本模型中，选择整体快照比把每个字段分别原子化更直接：查询读的是 owner 对某个已提交前缀的完整解释。
这也暴露下一层问题：即使每份快照内部一致，如果发布它们的 goroutine 乱序，最新指针仍可能倒退。

## 第 7 层：原子发布多个正确快照，为什么仍然可能版本倒退

**面试官：** 假设 seq101、seq102 的快照都正确且不可变。两个异步 worker 分别发布，seq102 先 Store，seq101 后 Store，这里有什么内存错误吗？

**面试者：** 它可以没有数据竞争，原子语义也完全成立，但业务观察退回了旧版本。原子 Store 的全局顺序只反映实际发布顺序，不知道 cmdSeq 应该递增。
因此“各个对象正确”和“发布历史正确”是两个条件；不能让异步任务完成时间决定市场结果先后。

本基线由 owner 作为唯一发布者，在确认对应 T_result 成功后按连续命令结果发布快照与 ExecutionReport；外部投影仍须按 seq 单调应用并处理缺口，唯一发布者不保证网络接收顺序不乱。
初始 appliedSeq 为 100，提交 seq101 时校验期望前缀，之后才能提交并发布 seq102；数据库还必须校验有效 epoch，阻止过期执行者承诺结果。

如果某次提交结果未知，owner 不能先发布更晚快照再回头猜测，而要冻结推进与新状态发布，读取 durable batch、appliedSeq 后恢复；可继续提供标明 appliedSeq 的最后已提交快照，但不得宣称已追上最新。
channel 通知、原子指针、内存锁都不能证明数据库事务是否提交；同样，一条已经受理的命令也不等于它一定成交，必须查看完整 OutcomeBatch。

需要并行构造快照时，可以把只读构造工作交出，但接受与发布回执仍要验证 cmdSeq、epoch 和当前期待版本，不能让 worker 各自 Store。
这里不展开异步回写方案；必须记住的边界是，语言同步保证数据交接，市场顺序与持久提交资格由业务协议保证。

## 第 8 层：怎样把内存模型回答变成可审查的证据

**面试官：** 你已经区分数据竞争和版本倒退。面试中如果只说“我们跑过 race”，是否足以证明上述快照发布和交易结果正确？你会怎样检查？

**面试者：** 不足以。race 检测针对实际覆盖到的执行路径发现未同步内存访问，没报错既不代表所有交错都被覆盖，也不证明没有死锁、版本倒退或资产错误。
本材料只是离线设计与手工推演，没有执行工程测试，更不能声称检测通过。即使未来检测无报错，也应限定它提供的是哪一类证据。

我会先画出一条发布链：owner 初始化快照字段 → 观察到 T_result 确认成功 → 同步发布指针或发送值 → 查询同步取得对象 → 只读同一不可变版本。
对每段跨 goroutine 的普通内存访问，指出具体的锁、对应 send/receive 或观察到的原子操作；找不到关系的地方不能用“应该已经执行完”代替证明。

再检查对象图和执行历史：快照是否共享可变 slice、map、指针；旧对象是否过早放回池；是否存在第二个发布者让 seq102 后又出现 seq101。
前一组是生命周期与内存安全问题，后一组即使 DRF-SC 成立仍可能失败。检查时必须保留它们的独立性，避免用一类工具结论覆盖另一类不变量。

最后回到主案例，观察 seq101 的完整版本是成交 4 手、剩余 6 手，seq102 的完整版本是成交 4 手、撤销 6 手、剩余 0。
任何查询都不能看到混合版本，也不能把候选结果当成已提交结果；A 最终 1100 USDT 可用等资金结论还要通过账务事务验证，不由内存发布推导。

## 收束：机制、易错边界与反例验证

### 讲透的机制

- happens-before 来自程序顺序和明确同步关系；实际先发生、sleep 和日志时间不是替代品。
- send 同步先于对应 receive 完成；无缓冲反向关系与有缓冲容量规则不能混用。
- close 只对因关闭返回零值的接收提供相应同步；goroutine 退出不自动提供完成通知。
- Mutex 能保护共同临界区；atomic.Pointer 可发布完整初始化且之后不变的快照，不能递归保护对象字段。

### 最容易答错的边界

- DRF-SC 不等于业务原子性或确定性；多个正确原子操作之间仍然能出现错误业务交错。
- 同步发布不等于可靠提交，完整快照不等于账户已记账，原子 Store 不等于版本单调。
- 接收到指针不代表发送方丧失语言层面的访问能力；必须另有不可变或排他交接协议。

### 反例验证

独立变体：先原子发布不可变 seq102 快照，再原子发布不可变 seq101 快照，读者全程只用原子 Load，所有字段都不再修改。
该历史可能完全没有数据竞争，却让客户看到订单从已撤退回活跃。若回答用“原子操作是顺序一致的”否认这个历史，就把内存顺序误当成了市场业务顺序。
