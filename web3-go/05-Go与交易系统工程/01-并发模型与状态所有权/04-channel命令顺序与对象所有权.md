# 大问题 4：channel 能保证哪些命令顺序，跨 goroutine 传对象时谁还能修改它？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| channel / FIFO | channel 是进程内交接值的通道；FIFO 表示局部通信按先进先出处理。 | 它不会替多个并发发送者按业务 seq 排序，也不保证多个消费者按接收顺序完成任务。 |
| 持久排序器 / cmdSeq | 排序器把命令和先后位置可靠记下，cmdSeq 是命令在市场历史里的编号。 | 先执行已提交的 seq101，再执行 seq102；通知到达顺序不能改写市场裁决顺序。 |
| owner | 某份状态的唯一权威管理者。 | 市场 owner 独占订单簿和订单状态的修改权，worker 拿到结果指针也不能接管簿。 |
| appliedSeq | 已完整提交结果的连续命令前缀。 | 当前为 100，收到 102 的通知也从 101 开始补读；重复或丢失唤醒不改变可靠日志。 |
| T_admit / Accepted | T_admit 是可靠受理事务；Accepted 表示这笔请求已被可靠接下。 | 幂等身份、预留和命令一起提交才可确认受理，send 成功不算，也不保证一定成交。 |
| requestID / canonical payload hash | requestID 标识请求；规范化载荷哈希帮助核对同一请求的业务内容。 | 用于校验、持久提交和实际执行的字段含义必须一致，不能算完哈希后又改共享载荷。 |
| 指针 / 别名 / 所有权 | 指针指向对象；不同引用指向同一对象就是别名；所有权规定谁能改和回收。 | 发送指针只复制地址，发送方原引用不会失效，必须另约定不变或排他交接。 |
| 结构体按值复制 | 复制外层结构体的字段值，而不是递归复制它引用的一切。 | 改成 chan Command 仍可能共享内部 slice、map 和指针，不能当成自动深拷贝。 |
| slice / []byte / 底层数组 | slice 是描述一段数组的头部，[]byte 也是 slice。 | 传过去两个描述符仍可能指向同一块字节，发送后改缓冲会污染接收方输入。 |
| map / 对象图 / 深拷贝 | map 是映射；对象图包含从它继续能访问到的嵌套数据；深拷贝要切断相关可变引用。 | 新建一张 map 还要检查元素里的指针和 slice；能证明始终不可变的数据才可安全共享。 |
| send / receive / 同步发布 | 发送与对应接收建立规定的同步关系，让接收方看到发送前的初始化。 | send 返回不证明消费结束，无缓冲交接也不证明接收后的业务处理已经完成。 |
| sync.Pool / Put / Get | 对象池用 Put 归还临时对象，用 Get 再借出；它不是任务完成管理器。 | 必须确认最后使用者结束后才能归还，不能 send 完就 Put，也不能靠池保存可靠业务状态。 |
| GC / 对象生命周期 | GC 回收不可达内存；对象生命周期还要看业务上谁仍在使用它。 | 发布新快照不说明旧读者已结束；仍被引用的旧快照不能主动清空并复用。 |
| OutcomeBatch / T_result | 前者是完整裁决结果包，后者是条件提交该结果的事务。 | worker 只按封闭的不可变批次做 IO；结果提交成功后，owner 才能发布新快照和回报。 |
| epoch / 预期版本 / ruleVersion | 分别标明所有权代际、任务依赖的状态版本和采用的规则版本。 | owner 验收回执要核对当前 cmdSeq、epoch 和预期版本，旧任务的成功不能冒充当前结果。 |
| context.Done() / select | Done 通知取消；select 从已就绪的分支中选择一个。 | 发送和取消同时就绪时不保证取消优先；必须按实际选中的分支判断临时对象是否已交接。 |
| close / sender 协调 | close 宣布通道关闭；关闭方必须知道所有发送者的生命周期。 | 仍可能发送时不能关；关了也不等于缓冲对象已用完、任务已结束或日志已处理完。 |
| reservation / T_ledger | reservation 是业务预留记录，T_ledger 把结果对应的资产变化及预留处理原子记账。 | 本地取消、通知未发出或关闭通道都不能直接释放预留；账务按连续持久结果推进。 |

## 把整篇文章压缩成一个故事

沿用无手续费的 ETH/USDT 现货例子，1 手是 0.1 ETH：A 的 O1 买 10 手，持久排序器已经记下 seq101 的下单和 seq102 的撤单。两个通知 goroutine 恰好把撤单提醒先送进 channel，市场 owner 也不能因此先撤单；它从 appliedSeq100 后补读可靠日志，仍先裁决成交 4 手，再撤剩余 6 手。channel 的 FIFO 管的是这条通道的通信，不是给市场重新排历史；通知丢了或重复了，也要靠日志补读继续。

加载器随后想省分配，把一个 *Command 发给 owner，send 返回就放回 sync.Pool，下次借到后改成另一条命令。这时 owner 可能还没取出指针，或正在读它，原来的 10 手就可能被共享对象的改写污染。改成按值发送也不能一劳永逸：结构体里的 slice、map、[]byte 仍可能共用底层数据。正确交接必须切断可变别名，或明确发送后谁独占、谁只读、谁是最后使用者；channel 不做深拷贝，send 也不证明消费结束，无缓冲通道同样不能作为立即归池的依据。

结果侧也一样：owner 封闭完整 OutcomeBatch，worker 只做授权 IO，不碰可变簿；回执回来后，owner 核对命令身份、epoch 和预期版本，确认 T_result 已提交，才发布结果。若提交未知，就冻结推进与新状态发布，核对持久批次，而不是因回执没到便重算或退款。取消请求只结束相应等待，不是撤单；close 只关交接路径，不证明任务、账务或缓冲对象的使用已经结束。故事要证明的是顺序、修改权和回收责任都闭合，不是声称做过对象池性能实测。

- seq101 前 S1 已是可信状态，appliedSeq = 100；seq101 成交 4 手，seq102 撤剩余 6 手。账务完成后 A 可用 1100 USDT、冻结 0、新增 0.4 ETH；B 收 400 USDT。
- 所有市场输入由持久排序器追加；channel 仅负责唤醒或内部排队。T_result 连续提交完整 OutcomeBatch、outbox 与 appliedSeq 后，才能发布不可变快照和 ExecutionReport。

## 第 1 层：一个 FIFO channel 为什么不能决定市场裁决顺序

**面试官：** 只有一个市场 owner 接收 channel，而 channel 是 FIFO。为什么你还说成交与撤单的顺序不能由 channel 决定？

**面试者：** FIFO 只能约束实际进入该 channel 的通信顺序，不会替多个并发生产者决定符合业务要求的先后。
如果 New 的通知由一个 goroutine 发送，Cancel 的通知由另一个发送，调度可能让后者先进入队列。channel 不会识别 cmdSeq 并替我排序，也不承诺生产者竞争公平性。

本模型中，seq101 的 New、seq102 的 Cancel 已经由持久排序器确定顺序，因此 owner 必须先处理 seq101，再处理 seq102。
主案例先成交 4 手、再撤 6 手。把先到 channel 的撤单当成先发生的业务，会把持久化历史改成另一个历史，即便内存访问完全没有竞争也不正确。

如果一个生产者顺序发送两个值、一个消费者顺序接收，可以依赖相应 FIFO，但这只是局部通信协议的性质。
它既不证明多个生产者的发送顺序符合已提交 seq，也不保证进程重启后队列仍在，更不保证并行消费者完成业务的先后与接收先后一致。

因此我会把 channel 定义成“提醒这个市场去检查已提交日志”的工具，而不是市场顺序的来源。
只有在明确改变基线、以另一套可靠协议建立顺序时，才可能让队列承担不同责任；不能因为接口看起来是 FIFO 就省掉现有持久排序器。

## 第 2 层：通知丢失、重复或乱序，owner 怎样仍按正确前缀推进

**面试官：** 你把 channel 降为唤醒，那 seq102 先通知、seq101 的通知丢了怎么办？如果消息里带着完整命令，owner 能直接执行它吗？

**面试者：** owner 当前已应用前缀是 100，收到“有新命令”的通知后，从数据库读取 101 开始的连续已提交命令。
即使通知只提到 102，也先检查并处理 101；重复通知只触发再次检查。通知彻底丢失时，由日志补读机制发现积压，而不是等待那个内存值永远回来。

New 的可信依据来自 T_admit：account + requestID 与规范化载荷哈希、扣可用增预留、reservation 和 New 命令在一个事务内提交。
事务通过市场 control 行生成无空洞提交 seq，先锁 control 再按账户稳定序加锁，不持这些锁做外部调用；T_result 也使用同一 control 行锁约束连续结果提交。

所以即使消息携带完整命令，它也只能是可靠命令的传输副本，必须与已提交身份和进度契约一致，不能把未提交请求直接送进裁决。
Accepted 来自 T_admit 成功，而不是 send 成功；数据库受理也只保证命令可追踪处理，并不保证它必然成交。显式 Reject 等结果同样不能悄悄跳过序号。

owner 每完成一条完整结果提交才推进已应用前缀，结果失败或未知就冻结推进与新状态发布，查 durable batch 与 appliedSeq 恢复；仍可提供标明 appliedSeq 的最后已提交只读快照，但不保证它已追上最新。
这样 channel 是否重复或丢失，不影响权威命令内容与结果顺序，也不能让查询暴露候选内存。不过本地交付副本仍可能因对象共享被篡改，这就是下一层需要解决的问题。

## 第 3 层：把指针发送给 owner，会自动转移修改权吗

**面试官：** 命令已经落库，加载器读出来一个 *Command 并发给 owner。发送完成后，加载器能否把这个对象改成下一条命令继续使用？

**面试者：** 不能。Go 的 channel 发送指针会复制指针值，不会像某些带所有权类型系统的语言那样，使发送方原引用失效。
owner 和加载器仍然可以指向同一个对象；如果加载器把 Quantity 从 10 改成 20，owner 可能裁决被改写的命令，而数据库里仍是 10 手。这既可能构成数据竞争，也会破坏命令身份与预留依据。

需要显式约定一种交接协议：发送前完成构造，发送成功后发送方不再修改，接收方按约定独占这个临时副本；或者把一个真正不可变副本交给接收方。
如果加载器还要重用自己的缓冲对象，就必须先复制出与它完全脱离的命令。Go 不会替我们检查这条规则，所有持有别名的模块都必须遵守。

send synchronizes-before 对应 receive 完成，能让接收方看到发送前的初始化，但不禁止发送方在发送后继续写。
即使用无缓冲 channel，send 返回也不代表接收方已完成处理；缓冲 channel 则可能在接收方尚未取值时就让 send 返回。同步发布与生命周期结束是两回事。

而且“独占临时命令副本”不等于可以改变已提交业务含义。owner 应把原始命令当作不变输入，另建私有工作状态与候选结果。
如果发现副本与持久内容不一致，应停止并核查，不能借着本地指针可写就把 10 手改成 20 手，或重新生成另一份请求载荷。

## 第 4 层：按值发送结构体，为什么还不等于彻底复制

**面试官：** 那我不发指针，改成 chan Command，发送结构体值。结构体里有 slice、map 和 []byte，这是否已经切断别名？

**面试者：** 没有。结构体按值复制只复制各字段的值；slice 字段复制的是描述底层数组的头部，map 字段仍引用同一张映射，指针字段仍指向原对象。
因此外层 Command 是两份，不代表它们可达的数据是两份。发送方修改原 []byte 的某个字节，或改 map 中的规则字段，接收方仍可能观察到变化。

切断别名需要沿实际可变对象图复制：为 slice 分配独立底层数组，复制需要保留的元素；为 map 建新映射；若元素中还有指针、嵌套 slice 或 map，继续按业务结构处理。
不能把复制一层 []OrderPointer 说成已经复制所有订单。反过来，如果某个被共享对象能保证终身不可变，就可以共享，但这个保证必须覆盖全部写入入口。

命令载荷尤其要稳定：用于 canonical payload hash 的字段，与持久提交和 owner 执行的规范化字段必须是一套含义。
不能一边计算哈希、一边让调用方继续改共享 map；也不能验证的是独立副本，实际提交的却还是原可变缓冲区。否则“同 ID 同载荷”的判断与真实执行输入可能脱节。

在本例中，市场、买方向、限价 100 USDT/手、数量 10 手等核心字段适合用明确值类型表达，减少任意 map 带来的边界。
扩展字段确实需要 slice 或 []byte 时，再针对它们定义复制或不变协议。关键不是追求任何对象都深复制，而是证明每一处共享可变性已经被消除或被同步管住。

## 第 5 层：工作 goroutine 能不能通过返回结果指针接管簿修改

**面试官：** 输入副本现在不变了。为了避免 owner 等数据库，我把 OutcomeBatch 指针发给 I/O worker，再把回执指针发回来。这个双向交接还需要什么？

**面试者：** 输入命令不变只是第一步，输出批次也必须在交给 worker 前封闭。OutcomeBatch 应完整包含唯一 trade ID、订单变化、剩余释放要求、cmdSeq、epoch 与规则版本。
worker 可以按约定持有不可变批次完成 I/O，但不能拿到可变订单簿引用并在等待期间“顺便更新”；状态修改权仍属于 owner，不能借返回一个指针变成多写者。

owner 交出批次后，不得让其他 goroutine 改簿，也不能在当前结果未确定时推进会改变该市场裁决基础的后续命令。
回执返回时必须核对它属于当前待提交的 cmdSeq、epoch 和预期版本，不能把某个旧任务的“成功”当成当前命令完成。即使交接内存安全，业务版本也必须再次验证。

worker 的 send 返回只证明本地发送完成，不证明 owner 已处理回执、发布快照或完成账务。owner 只有确认 T_result 成功后才能发布不可变快照和 ExecutionReport；外部投影仍按 seq 单调应用，不能假设收到回报的顺序不乱。
提交失败或未知时冻结推进与新状态发布，查 durable batch 和 appliedSeq，安全旧快照可带进度标识继续查询；不得因 worker 超时重算不同价格，也不能把“没有收到回执”当成“没有提交”。

完整的工作池与回写调度见[工作池与异步结果回写](09-工作池与异步结果回写.md)，本题只锁定交接契约。
尤其要写清结果对象由谁持有、谁有权修改、何时所有读者结束；否则即便两个方向都用了 channel，缓冲区和对象池复用仍会破坏它。

## 第 6 层：sync.Pool 为什么不能以 send 返回作为归还时机

**面试官：** 结果对象分配多，我想从 sync.Pool 取一个批次，send 给 owner 后立刻 Put 回去。既然 channel 已经同步过了，为什么不安全？

**面试者：** 因为 send 完成不是接收者使用完成。缓冲 channel 里可能还存着这个指针，另一个 goroutine 已从 Pool 取出同一对象并清空字段。
即便无缓冲 channel 已完成交接，接收方还可能正在读批次；发送方 Put 之后，自己和下一个借用者都不能继续假设旧内容仍有效。

sync.Pool 对同一个对象的 Put 和后来返回该对象的 Get 有相应同步保证，但这只协调归还后的下一次借用，不会等所有旧读者结束。
Pool 也不保证某个对象一定被保留或按固定顺序返回。因此它既不是所有权检查器，也不是任务完成确认器，更不能用作业务状态的可靠存储。

可行协议是把池对象的排他使用权明确交给接收方，由最后使用者在确认不再有引用后归还；或者发送前复制出独立结果，发送方只回收自己的原对象。
如果结果还会被序列化 worker、outbox 发布或查询快照引用，就必须把这些使用者纳入生命周期。不能仅因为 owner 已读过 cmdSeq 就提前回收整个对象图。

对外发布的快照尤其不能因发布了一个新版本，就立即把旧版本放回池。某个读者可能仍持有旧指针；Go 的垃圾回收不会阻止业务主动复用那个对象。
在无法简洁证明所有读者已经结束时，不池化这类快照通常更容易保证正确。本文不虚构对象池带来的收益，也不展开引用计数等替代机制。

## 第 7 层：取消发送和关闭队列，分别结束了什么责任

**面试官：** 对象交接还有失败路径。如果 select 在发送和 context.Done() 之间选择，或者停机时关闭了 channel，命令与对象的责任该怎么划分？

**面试者：** 先分清本地交接与业务受理。若 select 选择了取消分支，则这次发送没有发生，发送方仍负责其尚未交接的临时对象；若选择发送分支，就必须遵守发送成功后的不变或排他转移协议。
当发送和取消都已就绪时，select 不保证优先取消。不能把“context 已取消”当成“send 一定不会发生”，更不能由此推断已提交业务不存在。

T_admit 可能早已提交，这时即使本地通知未发送，原命令仍应从日志恢复并处理。请求取消只停止等待，业务撤单需要另一个有 seq 的 Cancel 命令。
受理提交与请求取消竞争时，结果可能未知，应按原 account + requestID 查询；不能把未交接通知对象的回收，与账户 reservation 的释放绑定。

关闭 channel 表示不再继续发送，不能让已在缓冲区的对象立即失效。close 不会等待消费方用完这些对象，也不会自动提交或撤销它们代表的业务。
应由明确协调发送者的关闭方执行关闭，避免发送与关闭竞争；业务停机必须处理已受理但尚未应用的日志位置，不能用一次 close 宣称全部业务完成。

取消和关闭的完整治理分别见[context取消与业务超时](07-context取消与业务超时.md)与[优雅停机与goroutine泄漏](12-优雅停机与goroutine泄漏.md)。
这里的判据仍然只有两个：本地对象是否已经交给别人，持久业务是否已经越过提交边界。它们可能发生在不同时间，不能共享一个含糊的“成功/失败”变量。

## 第 8 层：怎样审查一条 channel 的顺序与所有权契约

**面试官：** 一个系统里可能有很多 channel。你怎样快速判断某条 channel 的设计是否闭合，而不是把 send、receive 和 close 当成正确性的证明？

**面试者：** 我会先给这条 channel 写明角色：是唤醒、传命令副本、传不可变结果，还是传完成信号；再写明生产者数量、消费者数量和实际顺序来源。
同一市场本模型的顺序来自持久日志，不来自 select、发送竞争或 worker 完成顺序。即使通知先到 102，owner 仍要从已应用前缀 100 后处理 101。

第二步沿对象生命周期检查：值中是否有指针、slice、map、[]byte；发送前谁构造，成功发送后谁还能写，接收方何时用完，谁最终回收。
“结构体按值传递”和“单消费者”都不足以回答这些问题。若协议要求发送后不可变，就要连同发送方保留的所有别名一起禁止修改，而不是只禁止改一个变量名。

第三步检查承诺边界：send 成功不返回 Accepted，receive 成功不代表 T_result 成功，worker 回执已送达不代表快照已发布，close 不代表账务已完成。
T_result 必须连续提交完整结果，T_ledger 才能按市场连续批次，在账户稳定锁序下完成成交、预留处理、事件去重和账务游标。channel 不代替这些数据库约束。

最后用主案例推演：重复或乱序唤醒不能多成交，复用缓冲区不能把 10 手改成 20 手，旧回执不能覆盖新 seq，提前回收不能污染已发布快照。
预期仍是成交 4 手、撤销 6 手，账务完成后 A 可用 1100 USDT、冻结 0、新增 ETH 0.4。这个结论来自顺序与所有权协议共同成立，不是来自 FIFO 三个字。

## 收束：机制、易错边界与反例验证

### 讲透的机制

- channel 保证规定范围内的通信同步与顺序，不负责给并发生产者生成持久市场 seq。
- 发送指针不转移 Go 语言层面的所有权；必须约定发送后不变、排他交接，或复制独立对象。
- 结构体值复制不递归复制 slice、map、[]byte 及其内部指针；对象池回收要覆盖全部读者生命周期。
- 本地交接、可靠受理、结果提交和账务完成必须分别确认，不能用一个 send 或 close 合并表示。

### 最容易答错的边界

- send 返回不等于消费方处理完；无缓冲 channel 也不能据此把对象立即归池。
- select 不保证取消优先；发送未发生也不代表数据库受理未发生，更不能据此释放资产。
- 旧快照仍被读者引用时，发布新快照不赋予旧对象的复用权限；Pool 和 GC 都不会替业务阻止错误复用。

### 反例验证

独立变体：加载器从 Pool 取得 *Command，填入 seq101、数量 10，发入缓冲 channel，立即 Put；下一次 Get 将同一对象改为 seq102 的 Cancel。
owner 可能尚未接收就只看见被覆盖后的内容，导致 seq101 丢失或两次读到同一命令。正确方案必须切断别名或把回收权交给最后使用者，并继续以持久日志核对内容，不能只靠扩大 channel 容量补救。
