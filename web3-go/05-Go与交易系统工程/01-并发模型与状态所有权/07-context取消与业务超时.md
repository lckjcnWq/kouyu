# 大问题 7：请求超时后，怎样取消等待而不误撤已经受理的订单？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| request context / deadline | 这次请求的等待与准备范围，以及允许等待到的时间。 | HTTP 超时只结束本次交互，不证明交易已经回滚。 |
| ctx.Done / cancel | 协作取消的信号和发出信号的操作。 | 不强杀 goroutine，不自动发出有序业务撤单。 |
| service lifecycle / operation context | 服务接手后的任务生命周期，以及一次操作自己的有限期限。 | 已交接受理任务有登记、并发上限和负责人，不跟着 handler 消失。 |
| WithTimeout / WithoutCancel | 前者派生有限期限；后者在 Go 1.21 中解除父上下文取消等传播。 | WithoutCancel 本身不给期限、服务监督或业务可靠性，不能裸用后放任任务。 |
| T_admit / Accepted | 共同提交请求身份、预留与命令的事务，以及可靠受理的承诺。 | Accepted 不是成交完成，也不是账务完成。 |
| Commit 超时 / 提交未知 | 没能确定观察到事务的提交结果。 | 可能未提交，也可能提交成功但回执丢失，不能按错误文本直接退款。 |
| account + requestID / payloadHash | 原请求身份与内容摘要。 | 用原键在权威存储核对，同键不同内容拒绝，不换键再占一份钱。 |
| Cancel / cmdSeq | 业务撤单命令及其市场排序位置。 | Cancel102 不能越过 New101，只能撤实际剩余 6 手。 |
| T_result / appliedSeq / epoch | 提交完整执行结果、已提交进度与有权执行的任期。 | 101 的结果未知时不能先执行 102 或发布 101 的候选快照。 |
| T_ledger / reservation | 账户记账事务，以及被订单占用的资产记录。 | 账务按顺序支出 400、释放 600，不按客户端等待期限全退 1000。 |
| 一次性回复 channel | 给单个等待者的一次结果提示通道。 | 容量 1 且唯一生产者最多发送一次，等待者离开也不把 owner 卡住。 |
| select / 非阻塞通知 | 在就绪分支中选择，或无接收条件时不继续等待。 | 取消与回复都就绪时不保证取消优先；允许丢的是可补查提示，不是唯一业务事实。 |
| Outbox / 查询恢复 | 已提交的可靠交付依据，以及按身份重新查到结果。 | 客户端没收到即时提示，结果仍需可交付、可追踪。 |
| quiesce / drain / checkpoint | 停止产生新工作、处理已有工作、记下可恢复位置。 | 停机仍要留出受理核对与结果确认的生命期。 |
| WaitGroup / join / shutdown 期限 | 跟踪任务、确认实际结束，以及约束退出等待的时间。 | 启动前 Add，先关新增登记再 Wait；期限到了也不能删掉未完成日志。 |

## 把整篇文章压缩成一个故事

小林用 1500 USDT 中的 1000 下单买 10 手 ETH，页面却在受理回执到来前超时。handler 可以停止等待，服务却必须查清 T_admit 是否已提交：按原请求键发现 New101 已存在，就继续同一笔业务，不能另建订单或退回预留；暂时查不到，也不能排除原事务仍在结束。服务任务有自己的有限操作期限和监督责任，不是随手开个后台 goroutine 永久跑。

小林想取消购买，需要另交 Cancel102。owner 仍先处理 101 成交 4 手，再在 102 撤剩余 6 手；若 101 结果提交超时，市场先停在这个未知边界，核对完才继续。账务随后支出 400、释放 600，最终小林可用 1100、预留 0、得到 0.4 ETH。任何客户端 deadline 都不能把已经成交的 4 手抹掉。

等待者离开后，一次性回复不能阻塞 owner；可靠结果仍可从持久记录与 outbox 找回。服务停机也不能一开始就 cancel 全部核对任务，而要先停接入、辨明受理尝试，再排空或留下可恢复位置，最后等任务实际结束。整篇把“我不等了”“这次调用结束了”“业务撤销了”和“服务已收尾”拆开，避免一个取消信号越权改变交易事实。

[返回专题总览](./README.md)

**流程位置：** 接入准备与等待 → 持久受理 → owner 执行 → 结果提交 → 查询或独立撤单；重点区分各阶段的超时含义。
**独立边界：** 本题讲 context 的传播、提交未知、等待者离开与任务托管，不展开资金事务实现或主备切换协议。

**必要前提：**

- 使用 Go 1.21+；产品是链下托管的 ETH/USDT 现货订单簿，只支持 GTC 限价、价格时间优先，无手续费、无链上环节。
- 数量以手计，1 手 = 0.1 ETH；价格 100 USDT/手 = 1000 USDT/ETH。A 初始有 1500 USDT，O1 买 10 手预留 1000；B 已有卖 4 手的 S1，卖资产已经预留。
- New 的 cmdSeq=101，成交 4 手支出 400 USDT、剩 6 手；Cancel 的 cmdSeq=102 撤剩余 6 手。最终 A 可用 1100 USDT、冻结 0、ETH 0.4，B 得 400 USDT，数量满足 10=成交4+撤6+剩0。
- S1 的订单状态在主线开始前已持久提交，市场初始 appliedSeq=100。每市场一个 owner goroutine 独占订单簿和订单状态；账户逻辑 owner 是账务服务，跨进程约束由同一个 PostgreSQL 库中的事务与行锁完成。
- `T_admit` 原子完成 `(account,requestID,payloadHash)` 幂等、账户校验与预留、reservation 和带市场连续 seq 的 New 命令；Cancel 也经过同市场持久排序器。
- 排序器锁 market control 行分配无空洞的已提交 seq；同时涉及 market、account 的事务先锁 market，再按 account 稳定顺序锁账户，账务不反向获取 market 锁。
- `T_result` 以 expected appliedSeq 和有效 epoch 为条件，原子提交完整 OutcomeBatch、outbox、appliedSeq，随后才能发布带 seq 的快照和 ExecutionReport；账务按连续 batch 在 `T_ledger` 中推进。

```text
request context：约束接入准备、排队等待与本次响应等待
    ↓ 进入受监督的持久受理尝试
service lifecycle：辨明提交结果 → 按日志处理 → 持久结果 → 有序账务
    ↑ request context 结束不撤销这条链；撤单必须另交 Cancel
```

## 第 1 层：超时到底取消了什么

**面试官：** A 提交 O1 后 HTTP 请求超时，能否让 context 取消撮合，并把预留的 1000 USDT 释放？

**面试者：** 不能。request context 表示这次调用已经不值得继续等待，不表示账户或订单状态已经回滚。
我先区分未受理、受理结果未知、已经 Accepted、撮合结果已提交和账务已完成几个阶段。
只有确定没有形成持久受理事实，才可能按未受理收尾；已受理业务必须继续受服务生命周期管理。
Accepted 只承诺可靠受理，不承诺已经撮合，也不承诺账户已经结转。

在这个模型中，接入准备可以响应 `ctx.Done()` 停止解码、预检查或等待准入。
一旦持久受理成功，owner 从日志读取 seq101，不能因为原 HTTP handler 已退出就跳过它。
channel 只是通知或内存搬运，接收或未接收都不改变日志中的资格与顺序。
业务要撤销，只能提交独立的 Cancel，让它与成交在同一个市场顺序中裁决。

因此，seq101 仍然先成交 4 手、留下 6 手；seq102 才撤这 6 手，而不是把原订单全部抹掉。
账务依据确定结果消耗 400 USDT、释放 600 USDT，不依据超时直接释放 1000。
如果把取消等待当成撤单，原命令迟到执行时就可能使用已经被重新花掉的资金。
这不是 context 传播不够及时，而是把调用生命周期误当成了业务状态机。

## 第 2 层：怎样切断请求与持久任务的取消传播

**面试官：** 你说已受理任务归服务托管，但提交发生在 handler 中，父请求一取消，数据库调用也跟着结束，怎样划清边界？

**面试者：** 我会在发起持久受理尝试之前做明确交接，而不是事后临时启动一个无人管理的 goroutine。
接入先取得有界的准备资源，验证请求上下文仍允许继续，再将请求身份和不可变载荷交给受监督的受理任务。
受理任务有服务级登记、并发上限和自己的有限操作期限；handler 可以取消等待，但不能销毁任务身份。
在准备阶段检查过 context，不代表此后取消与数据库提交之间具有原子性。

准备步骤可以使用 `context.WithTimeout(requestCtx, prepareBudget)`，取得 cancel 后及时调用它。
持久受理尝试使用服务生命周期派生的有限 operation context，而不是请求 context 或没有期限的 `Background()`。
操作期限控制数据库资源占用，不能证明超时后事务一定没提交；这一点由后续核对处理。
如果使用 Go 1.21 的 `WithoutCancel`，也仍要补上服务托管、期限和退出责任，它本身不是可靠任务系统。

交接以后，handler 只等待提交回执、明确错误或自己的 deadline；服务任务负责把尝试推进到已知结果或登记未知。
即使请求在交接与数据库提交之间结束，也不能承诺“取消一定阻止受理”，只能告知可能仍在处理中。
服务停机时也必须等这些正在受理的事务明确，或把未知尝试纳入恢复责任。
这样取消传播边界由协议定义，而不是由某一次调度先执行哪行代码决定。

## 第 3 层：数据库超时为什么不能等价于未提交

**面试官：** 你给受理任务设置了独立期限，但 `Commit` 返回超时，既没拿到 Accepted，又不能一直占资源，接下来怎么处理？

**面试者：** 我把它标记为提交结果未知，而不是业务失败，也不生成一个新 requestID 再下一次单。
用原 `(account,requestID)` 和 payloadHash 查询权威 PostgreSQL 状态，检查是否已经存在一致的受理记录与命令位置。
若已提交，返回原命令身份；若相同请求身份对应不同散列，返回载荷冲突，不能悄悄替换原业务。
查询必须针对权威提交事实，不能用滞后的缓存“未查到”证明不存在。

暂时查不到也未必能判定未提交，因为原事务可能仍在结束过程中，查询可能早于它的最终提交。
我需要等待原尝试明确结束，或通过同一幂等键、唯一约束和受理协议协调重试，让并发尝试收敛到一个结果。
原事务明确未提交后，同键重试仍走完整校验；发现已经提交则复用，不重复预留、不生成第二个 New。
请求取消与 `Commit` 竞争的窗口因此变成一个可核对的状态，而不是凭错误类型猜测数据库状态。

资源也要分类释放：handler 栈、临时解码缓冲和已经停止使用的连接等待资格可以回收。
reservation、持久积压配额和业务执行资格则不能因为本次操作期限已过直接归还。
受监督的核对任务携带原请求身份继续工作；进程退出后仍应通过持久记录和原请求键收敛。
不能把“本地不再等待”包装成“全系统已经撤销这次业务”。

## 第 4 层：超时后的撤单怎样与原请求衔接

**面试官：** 你要求按原请求键核对，可 A 不想继续等，只想赶紧撤单；能否把超时信号直接转成一个高优先级取消事件？

**面试者：** 可以帮助用户发起独立撤单意图，但不能把 context 信号本身当成已经生效的撤单。
先辨明原受理身份，得到 O1 或能够稳定关联原请求的订单标识，再用独立 requestID 提交 Cancel。
Cancel 也要经过同一市场的持久排序器，收到 Accepted 只说明撤单命令被可靠接收。
若原 New 仍处于未知状态，就不能仅凭一次“订单不存在”查询宣告原意图永远不会出现。

本例明确的顺序是 New101、Cancel102；owner 必须先执行 101，依据当时的订单簿确定 4 手成交。
102 只能撤掉执行到它时的实际剩余 6 手，不能抢占 seq101，也不能追溯撤回已经确定的成交。
若另一个场景中订单到撤单时已全成，应形成相应撤单结果，而不是伪造成功撤掉原始数量。
支持引用原请求的撤单接口时，仍要定义关联与排序规则，不能靠“优先级 channel”掩盖 New 尚未确定的问题。

账务消费 seq101 的成交结果，再消费 seq102 的释放结果，允许订单已撤销而释放尚未到账的暂态。
界面应分别展示受理、撤单结果和资金结转阶段，不能把 HTTP 的 200 或超时当成最终账务状态。
用户主动放弃等待也不改变数量恒等式，任何通知丢失都不能使这 4 手成交消失。
因此，撤单是可查询的业务命令，取消等待只是这次交互的控制信号。

## 第 5 层：结果写入超时后为何必须暂停市场推进

**面试官：** 你说撤单只能按 seq 执行；若 owner 已算出 seq101 的成交，但写结果的 IO 超时，能否先处理 seq102，稍后补写 101？

**面试者：** 不能把未知结果当成失败后继续前进；我会冻结这个市场的后续状态推进，先确认 seq101 的持久事实。
owner 为每个命令形成 OutcomeBatch，包含 tradeID、完整订单变化、release 剩余量以及 cmdSeq、epoch、ruleVersion。
`T_result` 必须在同一事务中检查 expected appliedSeq 和有效 epoch，写完整 batch、outbox 并推进 appliedSeq。
只有确认这次提交成功，才能发布相应 seq 的快照和 ExecutionReport，再处理 seq102。

若 IO 超时，可能是事务没提交，也可能已经提交但回执丢失；试算出的内存状态不能先作为权威结果对外发布。
owner 保留待确认批次身份和受限的试算状态，暂停消费后续业务，查询已提交批次与 appliedSeq 是否一致。
查到同一批次就接续；明确未提交时才按原身份和条件重试；发现冲突则停止并恢复核对，不能盲改 expected 值覆盖。
这里仅使用 epoch 的有效性契约，不借机展开主备选举，但旧身份不能绕过结果提交检查。

账务只消费这个持久 outbox 中按市场连续的 batch，不接受 owner 的“可能已成交”临时通知。
`T_ledger` 原子完成双边账、预留消耗或释放、幂等记录与消费 cursor，不能把其中一部分提前做完。
冻结的是推进与新状态发布；查询仍可返回标明 appliedSeq 的最后已提交只读快照，不能暴露候选状态。
结果 IO 的超时限制一次尝试的等待时间，不授予重排或回滚业务的权力。

## 第 6 层：等待者走了怎样避免堵住 owner

**面试官：** 你要求确认结果后再发布，可请求早已超时退出，owner 往回复 channel 发送结果时会不会一直堵住？

**面试者：** 不应让权威状态机等待一个可能已经离开的 HTTP handler。
一次性回复可以使用容量为 1 的独立 channel，并约束只有一个生产者、最多发送一次，接收者不负责 close。
在这个约束下，等待者离开也仍有一个槽可接收通知，owner 无须等待对方重新上线。
若取消与回执同时就绪，Go 的 `select` 不保证取消优先，接口语义必须允许任一等待结果并提供后续查询。

也可以采用非阻塞的一次通知，但其内容只能是可以通过持久查询找回的提示，而不是唯一的完整业务结果。
例如提示某 requestID 的状态已更新；未收到提示的客户端仍查询原受理键与命令位置。
完整 OutcomeBatch 和 ExecutionReport 的可靠交付责任在持久结果与 outbox，不能用 `default` 丢弃来完成。
若一次回复设计出现第二次发送，应视为实现错误或重复通知处理问题，不能偷偷把 channel 改成无限缓冲。

等待者退出时释放自己的订阅登记与临时引用，但不能关闭仍有发送者的公共通道，也不能回收 owner 尚在使用的对象。
对连续订阅，慢客户端需要有限缓冲、断开与按 seq 补查协议，而不是让 owner 逐个同步写网络。
这些措施切断了“客户端不读 → owner 不推进 → 整个市场停住”的依赖链。
它们解决的是响应路径阻塞，不改变前面确定的结果持久化与业务取消语义。

## 第 7 层：服务停机时谁负责等待这些任务结束

**面试官：** 你切断了客户端与 owner 的阻塞依赖，但服务也有总 context；停机直接 cancel 它，不就能回收全部任务了吗？

**面试者：** cancel 是请求协作退出，不是 join，更不是把所有持久任务变成未受理。
停机先关闭新接入，等待正在受理的事务明确，或登记未知尝试，再 quiesce 通知生产者停止创建新任务。
随后 owner drain 已受理前缀，或在明确 cutoff 内形成可恢复 checkpoint；结果确认与必要回复消费仍需保持存活。
如果一开始就取消所有服务 IO，可能恰好把正在提交的结果推入未知窗口，却又关闭了核对者。

Go 1.21 的任务登记使用 `WaitGroup.Add/Done/Wait`，在启动 goroutine 前 Add，由实际任务 defer Done。
开始 Wait 前必须关闭新增登记的入口，避免计数归零以后又出现未被覆盖的新任务；这里不使用 Go 1.25 的 `WG.Go`。
多个 sender 共用 channel 时，协调者应先确认全部 sender 结束，再决定是否 close，不能让每个 worker 都 defer close。
owner 仍依赖 worker 回写时，应保持回写消费，不能先 Wait worker、后恢复收消息而构成等待环。

最后用独立的有界 shutdown 期限约束整个退出过程，期限到达不等于允许删除未处理日志。
未完成的受理命令、未知结果和未消费 outbox 留给恢复；业务资格与持久配额仍按权威状态核对。
无法及时停止的外部调用应被明确报告，不能声称 Go 能强杀任意 goroutine。
生命周期管理因此包含“停止创建、完成交接、确认退出”，而不只是树根调用一次 cancel。

## 第 8 层：怎样证明取消只影响等待而没有改变业务事实

**面试官：** 你保留日志并等待退出，怎样用同一笔业务的静态时序证明这些取消边界没有自相矛盾？

**面试者：** 我会把 request deadline、受理提交、结果提交和账务 cursor 分别画在时间线上，不用一个“成功”字段混在一起。
先推演 O1 的 `T_admit` 已提交、handler 同时超时的窗口：原键查询得到 New101，不能再预留一笔 1000。
然后让 seq101 的结果回执超时：市场停在待确认状态，seq102 即使已经受理也不能提前改变订单。
确认 seq101 的完整 batch 已持久后，才继续 102 并发布对应快照与回报。

再让客户端在 owner 回复之前退出：一次性通知不阻塞 owner，可靠结果仍从 outbox 交付或通过查询恢复。
账务按连续 batch 完成后，A 的 1500 USDT 中支出 400，剩下 1100 可用、冻结为 0，并获得 0.4 ETH。
B 获得 400 USDT；O1 的 10 手等于成交 4、撤销 6、剩余 0，不能因为任何 deadline 产生额外释放。
如果在任一窗口看到全额退款、重复 New 或 seq102 先执行，方案就没有守住前面承诺。

最后检查每项等待是否有负责人、期限和可查询身份，区分请求终止原因、任务结果与业务终态。
观察项应包括未知受理数、未知结果停滞位置、活跃等待者和停机未完成任务，而非只看 HTTP 超时率。
这些都是静态推演与后续验证口径，不代表已经运行工程测试，也不声称测得某个延迟或吞吐。
判断标准是取消前后的持久业务事实一致，以及所有遗留责任都有明确接手者。

## 收束：取消的权力止于哪里

- **讲透的机制：** request 与 service 生命周期分离；未知提交按原身份核对；结果提交前不发布；等待者与权威执行解耦；cancel 后仍需 join。
- **易错边界：** `ctx.Err()` 不证明数据库回滚；Accepted 不等于撮合或记账完成；取消等待不等于 Cancel；`select` 不保证取消优先。
- **可检验反例：** 在 `T_admit` 已提交而回执未到达时取消请求，再以原键查询并提交 Cancel102。若系统重新占资、提前释放 1000 或丢掉 New101，就推翻了实现。
- **最终核对：** A 可用 1100 USDT、冻结 0、ETH 0.4，B 得 400 USDT，10=4+6+0；只作静态预期，不附额外 MVP。
