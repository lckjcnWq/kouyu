# 大问题 5：成交与撤单竞争时，怎样产生唯一的订单结果？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 成交 / Cancel 撤单 | 一部分订单数量已买卖成功；撤单只让尚未成交部分退出撮合。 | 已成交 4 手不能因为状态变成 Canceled 就退回成“从未发生”。 |
| owner / 权威命令顺序 | 唯一裁决订单的执行者，以及所有相关输入共同遵守的先后。 | 后续成交来自另一个入场订单的匹配，不由回调线程直接扣量。 |
| cmdSeq / MarketControl | 持久命令位置与事务排序的市场控制记录。 | New101、Cancel102 按已提交顺序处理，不按 HTTP 或通知到达时间。 |
| channel / FIFO | 内存通道按相应发送关系传递元素的规则。 | 多生产者竞争不能提供稳定业务优先级，进程消失也不能靠它恢复。 |
| Accepted / T_admit | 可靠接下命令的中间承诺，以及它的事务提交边界。 | 撤单请求被接下，不等于已经确定撤销数量。 |
| 线性化点 / T_result | 对某个最终操作，可视为一次正式生效的时刻；本模型用结果提交承载最终裁决。 | 受理与最终撤单各有不同承诺，不能把中间响应当最终响应。 |
| original / filled / canceled / remaining | 原始、累计成交、累计撤销、当前剩余数量。 | 始终 original=filled+canceled+remaining；本例最终 10=4+6+0。 |
| status / 终态 | 对数量与生命周期的摘要，以及不能再参与撮合的结果状态。 | status=Canceled 仍需保留已有成交，不能单独乱写状态字段。 |
| 原子状态转换 / CAS | 完整处理相关读写的边界；CAS 是条件成立才替换一个值的原子操作。 | 只 CAS 状态字段，不自动维护数量、索引与成交记录的一致性。 |
| requestID / AlreadyTerminal | 稳定请求身份，以及订单已经没有可撤部分的响应。 | 同身份重试找回原结果；第二次撤单不能再次生成退款。 |
| 结果批次 / epoch / appliedSeq | 完整裁决、提交者任期和已提交进度。 | 结果事务共同检查资格与前缀，提交未知时不能自行挂回订单。 |
| 预留 / T_ledger | 为订单占住的资金，以及实际消耗、释放它的账务事务。 | 先处理成交支出 400，再释放剩余 600，不是按原始 1000 全退。 |
| 投影 / 读取水位 | 查询整理视图，以及它已经追到的位置。 | 想看到撤单后的状态可要求至少到 102；滞后投影不是实时线性一致读。 |
| 并发历史 / race | 请求、受理、裁决与响应的时序证据，以及内存竞争检查。 | 两个任务都没报错，不足以证明这段业务历史合法。 |

## 把整篇文章压缩成一个故事

小林挂了买 10 手 ETH 的订单，系统先在 New101 中成交 4 手，余下 6 手还在簿里。小林点撤单时，另一个可成交订单也可能进入市场。谁先到客户端、哪个 goroutine 先运行都不能裁决，必须看它们的持久命令顺序：若后续匹配先发生，撤单只撤更少的剩余；若撤单先确定，那些数量就不能再成交。

主案例 Cancel102 撤掉 6 手，数量从 10=4+0+6 变成 10=4+6+0。收到 Accepted 只说明撤单意图可靠进入序列；T_result 提交才确定最终撤销结果。小林再次发撤单，同身份应找回原结果，即使用不同身份重发，状态机看到剩余为 0 也不能生成第二笔释放。

如果内存删单后数据库响应超时，系统先冻结该市场推进与新状态发布，查清 102 是否已提交，而不是猜着挂回去或继续往前跑。即使执行上已撤，账务仍要先消费 101 支出 400，再消费 102 释放 600；小林最终可用 1100 USDT、得到 0.4 ETH。本文要守住的是唯一数量裁决及其资金依据，不是把“已受理”“已撤”“钱已可用”和“页面已刷新”混成一个瞬间。

[返回专题总览](README.md)

**流程位置与核心机制：** 从市场命令排序追到订单状态机、结果提交与资金释放。这里证明同一订单竞争操作怎样裁决；账户跨市场占资与完整交易一致性在[母题 06](06-账户并发占资与交易一致性.md)展开。

**必要前提：** 沿用总览的链下现货模型。O1 买入 10 手，每手 100 USDT；New 命令 101 成交 4 手、余 6 手，Cancel 命令 102 撤实际剩余量。市场 owner 独占可变订单簿，命令与执行结果分别有持久提交边界。

## 第 1 层：两个操作同时发生，谁说了算？

**面试官：** 订单部分成交后，撤单和后续成交同时发生，你怎样保证订单不会既全成又撤销？

**面试者：** 我不会让成交回调和撤单接口各自修改订单状态，而是把会影响同一订单的操作放进同一市场的权威命令顺序，由唯一 owner 执行状态转换。后续成交来自后续入场订单的匹配，不是另一个线程直接扣 O1 剩余量。撤单也不是接入层把状态改成 Canceled，而是一个有自己序号的 Cancel 命令。

在主案例中，101 已成交 4 手，102 执行时看到的剩余量是 6，所以只能撤 6。若独立变体中另一个可成交订单排在撤单前，就先按那次匹配减少剩余量，撤单再处理新的剩余量；若排在撤单后，就不能再匹配已经移出簿的 O1。两种结果都可以合法，不能同时对同一手数量宣称已成交和已撤销。

## 第 2 层：单个 channel 的先后能不能当裁决顺序？

**面试官：** 你说所有操作交给一个 owner，那把它们放进同一个 channel，不就自然有顺序了吗？

**面试者：** channel 可以串行交付实际进入它的元素，但多个生产者的竞争发送顺序不代表 HTTP 到达顺序，更不代表崩溃后能恢复的业务顺序。本模型的顺序来自数据库中已提交的 `cmdSeq`，channel 只是通知 owner 去取哪些工作。

市场排序入口锁定 MarketControl 行，事务内分配下一个序号并写入命令，提交后这个位置才有效。owner 从 durable appliedSeq 的下一项连续读，不能因为先收到 seq=103 的通知就越过 102。这样两个并发请求可以由持久排序器选择任意合法先后，但一旦返回相应承诺，之后查询、回放和重试就必须沿用这个顺序。

## 第 3 层：序号与线性化点是不是一回事？

**面试官：** 既然写入命令日志时就定了顺序，是不是 Accepted 返回时订单已经线性化成「已撤销」？

**面试者：** 不是，必须先说清正在讨论哪个操作的承诺。可靠受理接口的生效点是命令受理事务提交；它只承诺命令进入可恢复的处理序列。Cancel 的最终业务结果，要等 owner 在该序号读取权威订单状态，形成完整结果并提交 T_result，才能对外承诺「撤销了多少」或「已无可撤剩余」。

在这个顺序执行、顺序提交的模型中，可以把最终执行接口的生效点放在该命令 T_result 的提交处：它位于请求发起和最终成功响应之间，且不得违背已完成操作的实时先后。Accepted 是中间响应，不是最终撤单响应。投影查询若允许滞后，就只保证带序号的投影视图，不能借用执行接口的保证声称所有读取都线性一致。

## 第 4 层：状态机为什么不能只存一个 status？

**面试官：** 你说读取权威状态，直接判断 status 是不是 Filled，再把它改成 Canceled 不够吗？

**面试者：** 不够，因为 status 是数量事实的摘要，不能替代数量本身。我至少维护 originalLots、filledLots、canceledLots、remainingLots，并在每次转换后检查 `original = filled + canceled + remaining`，各项非负。状态只能由这些事实与生命周期规则推导或同时校验，不能独立乱写。

主案例先从 `10=0+0+10` 转成 `10=4+0+6`，撤单后是 `10=4+6+0`。这个终态可以叫「部分成交后已撤销」，但必须保留累计成交 4 手，不能因 status=Canceled 就理解为从未成交。若订单已经全成，则是 `10=10+0+0`，撤单返回不可再撤的结果，不产生新的撤销数量。

## 第 5 层：检查和扣量之间的缝隙怎么堵？

**面试官：** 如果两边都先检查 remaining=6，再分别成交 6 和撤销 6，你的数量公式还是会被破坏，具体怎么防？

**面试者：** 关键是让「读取剩余量、验证条件、修改数量、维护簿索引、生成结果」属于同一个有序状态转换。单 owner 方案在处理一条命令时，不让其他 goroutine 直接写同一个订单；即使因为 I/O 暂停，也不把下一条依赖该订单的转换插进来。如果改成共享内存加锁，检查和整套变化必须在同一保护域内，不能检查时锁一次、扣量时再锁一次。

不安全时序是 F 和 C 都读到 6，F 写 filled=10、remaining=0，C 又按旧值写 canceled=6、remaining=0，最终得到 `10 != 10+6+0`。单 owner 的合法历史只有 F→C 或 C→F，不允许两者都消费同一个旧版本。CAS 单个 status 也不能自动把簿索引、数量和成交记录变成一个原子转换。

## 第 6 层：两条撤单命令怎样避免重复释放？

**面试官：** 你堵住了成交与撤单，但客户端超时重发撤单，两个 Cancel 都进入日志怎么办？

**面试者：** 相同账户和 requestID 的重试应先命中持久请求记录，返回原命令身份；载荷不同则报身份冲突。即使客户端用两个不同请求身份提交两次撤单，状态机也必须安全：第一条只撤当时实际剩余量，第二条看到 remaining=0，只返回 AlreadyTerminal 一类无新经济效果的结果。

主案例第一条撤 6 手，对应释放义务 600 USDT；第二条不能再按 originalLots=10 生成释放，更不能重复生成新的 600。已提交批次有稳定身份，账务消费的去重记录与资金变化同事务提交。请求幂等、状态机终态和账务去重分别挡住不同入口，不能只靠 HTTP 层缓存一次响应。

## 第 7 层：内存已经撤了，提交失败怎么办？

**面试官：** owner 已经从内存簿删掉 O1，但写撤单结果到数据库超时了，还能继续接下一条命令吗？

**面试者：** 不能继续在不确定状态上推进或发布新快照。超时既可能是事务未提交，也可能是提交成功但响应丢失；如果直接把 O1 挂回去，可能让已经撤销的订单再次成交；如果直接宣布成功，又可能没有可恢复的撤单事实。

我会冻结该市场的推进和新状态发布，按 market、cmdSeq 查询完整结果批次与 appliedSeq。若 102 已提交，就采用原批次；若确认未提交，就丢弃不可信的暂态，从可信快照和已提交前缀恢复，再处理原命令。T_result 同时校验 epoch 和前一 appliedSeq，保证不能覆盖已有同序号结果。这个流程是进程内串行之外额外的持久化协议，不是 mutex 自动提供的回滚。

## 第 8 层：订单已撤为什么资金还冻结？

**面试官：** 你说 102 已提交才能宣布撤单，可用户看到订单已撤、余额仍冻结，是不是一致性已经坏了？

**面试者：** 在本模型中这是被定义并可恢复的暂态。102 提交确定的是订单退出簿和释放剩余预留的义务，不代表账务消费者已经完成所有前序批次。私有回报可以说明撤了 6 手，并携带执行序号；账户页面应依据账务进度显示预留，不得根据订单状态自行加余额。

账务必须先消费 101 的成交，消耗 400 USDT，再消费 102 释放 600。如果 102 先到达，就暂存或补拉缺口，不能先把原始 1000 全部退掉。允许「已撤但稍后到账」不等于允许无限搁置，需要积压、失败告警与恢复责任；禁止的结果是撤销后仍匹配、释放已成交资金或重复给可用余额加钱。

## 第 9 层：查询怎样避免看到半套结果？

**面试官：** 你允许回报和账务不同步，那一个查询会不会看到 canceledLots=6，但 O1 还在可撮合索引里？

**面试者：** owner 内部转换期间的中间结构不能被并发查询直接观察。对外查询读取 T_result 提交后发布的不可变快照，其中订单数量、状态和簿视图来自同一个 appliedSeq；如果各视图分别构建，也必须标出各自进度，不能拼装成伪装一致的同一快照。

如果调用者需要「至少看到我这次撤单之后的状态」，可以带上撤单结果中的市场序号 102，查询端等投影达到该序号或返回明确的尚未追上，而不是强称最终一致查询具有实时一致性。余额和订单仍是不同进度的领域事实，前端需要展示处理阶段，不能通过读取同一个缓存对象来假装完成跨域提交。

## 第 10 层：怎样验证你说的唯一裁决不是口号？

**面试官：** 那你怎样用一个具体反例检查实现，避免只是把「单写者、幂等、顺序」挂在嘴上？

**面试者：** 我会把撤单与另一笔可成交入场订单置于同一段并发历史中，明确记录请求开始、Accepted、cmdSeq、T_result 提交和最终响应。改变两个输入的持久排序，只允许得到两种对应的合法结果；每种结果都检查原始量守恒、终态不可再成交、释放金额只来自实际剩余。不能只看两个 goroutine 最后都返回 nil。

再把失败点放在「内存撤单后、T_result 提交响应前」，分别推演事务未提交和已提交但回包丢失。恢复必须沿同一已提交前缀，且同一 seq 不产生第二份不同结果。race 检测可补充发现逃逸指针的并发写，但无法替我证明日志顺序、终态和资金处理；本稿只给验证方法与预期，没有声称执行过这些检查实验。

## 本题收束

- **讲透的机制：** 权威命令顺序、完整状态转换、受理与最终结果的不同生效点，以及从撤单结果到预留释放的依赖。
- **最容易答错：** 把同 channel 当作持久顺序；把 Accepted 当撤单完成；把 Canceled 当从未成交；结果提交未知时继续推进。
- **检验反例：** 两个操作都基于 remaining=6，最终却各自消费 6；即使所有字段访问都分别加锁、没有 data race，这仍是非法业务历史。
