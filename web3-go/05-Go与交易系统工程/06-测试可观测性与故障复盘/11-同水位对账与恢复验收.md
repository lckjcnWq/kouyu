# 大问题 11：撮合、账务和查询进度不一致时，怎样在同一水位定位差异、修复错误，并证明系统可以恢复？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 同水位 / 业务切面 | 比较对应同一段完整业务的状态。 | 420 已成交、账户在 419 不能立刻定性错账或退款。 |
| 一致快照 / 历史视图 | 前者固定一次可达读状态，后者重建特定过去状态。 | 当前事务快照不能自动给出任意过去批次余额，必须绑定真实进度。 |
| 屏障 / 冻结窗口 | 让新增受限、处理排到明确位置后获取证据。 | 避免刚读完水位 419，余额却已经含 420，再拼成假状态。 |
| 版本向量 | 用多个独立进度坐标描述共同切面。 | 多市场共享账户变体不能只拿一个市场水位解释全部资金。 |
| 三方核对 | 将权威成交、账务凭证与账户状态相互对应。 | 总额平衡之外还检查收款人、订单和预留来源。 |
| 预留生命周期 | 资产何时占用、消耗、释放及仍为谁占用。 | 甲消耗 15,015、释放 10；丙剩余 5 lot 仍属于 S2。 |
| 缺失 / 重复 / 冲突 / 漂移 | 分别是待处理事实、重复到达、内容矛盾和物化状态偏离。 | 先分类再修复；重复投递被幂等吸收不等于重复扣款。 |
| 原身份补交 | 把未完成的原始结果按既有身份继续交付。 | 不造修复版 420、不换成交号，也不跨过前序缺口。 |
| 去重与连续水位 | 前者认出已做过，后者证明前面全做完。 | 迟到旧批次也要查摘要，不能仅凭序号较小吞掉冲突。 |
| 授权补正 / 冲正 | 用新的审计凭证表达对已错账的更正。 | 关联原账与修复案件并幂等执行，不删旧分录或直接改目标余额。 |
| 围栏 / RPO / RTO | 阻止旧写者、允许的数据损失界限和业务恢复时间目标。 | 备份能启动不证明满足承诺，恢复预算还包括回放与对账。 |
| EVM 重扫 / 补偿 | 重建规范链观察，并另行处理已入账信用影响。 | 重扫不会自动撤回链外转出，也不能抹去链下成交。 |
| 有界验收期间 | 固定事故起点和截止切面，让核对有终点。 | 范围外新义务另统计，不能无限追最新或借新业务掩盖旧差异。 |
| 分阶段签核 | 按责任域确认具体完成程度与遗留限制。 | 账务、投影、订单准入与提现扩展不能用一个恢复按钮包办。 |

## 把整篇文章压缩成一个故事

核对者看到撮合 420、账户 419、查询 418，没有马上给甲补钱。下一秒账户可能已经处理 420，如果拿刚读的 419 标签配上当前余额，会制造一份从未真实存在的状态。团队因此取得水位与余额绑定的一致快照，或在受限准入下排空到屏障，再把撮合历史重放到对应切面；多市场共享账户的扩展还需多个资金流坐标，不能强套一个序号。

在包含 420 的切面，逐笔核对两笔成交、分录归属和预留：甲花 15,015 USDT、释放 10、得到 25 lot，乙新增 6,000 USDT，丙新增 9,015且仍预留 5 lot。若只是未交付，就保留原身份补交；重复被去重吸收不算错账，同身份不同摘要要隔离。若已经把丙的钱记给别人，重放不会修好，必须授权冲正和补记，关联原凭证与稳定修复案件，不能关掉去重或直接涂改余额。

恢复验收固定截止范围，证明旧写者失权、连续进度无缺口、修复可审计、投影追平，再分步开放功能。灾备不能因备份只有 419 就丢掉已承诺的 420；另加 EVM 充值重组时，要区分重扫观察与已入账信用补偿，链外转出不会自动撤回。本文给出核对和签核方案，没有实际执行恢复、补账、数据库验证或链上演练。

[返回专题总览](README.md)

**流程位置：** 可靠受理 → 单市场撮合 → 成交结果可靠提交 → 账户域入账 → 异步查询；本题沿“辨别在途 → 固定核对切面 → 分类修复 → 重建证据 → 有界验收”连续追问。

**核心机制：** 先对齐同一业务切面，再核对成交、分录、余额与预留；恢复不是让数字暂时相等，而是解释每个差异，并保留不可篡改的修复因果。

**公共短前提：**

- Go 1.21+；BTC/USDT 托管现货，市场标识为 `BTC-USDT`；链下单市场单写者、价格时间优先、限价 GTC、零费、无杠杆。撮合拥有权威订单与成交，账户域拥有余额、预留和账本，异步查询投影不是真相。
- 价格步长为 1 USDT/BTC，数量 `1 lot = 0.01 BTC`，资金最小单位为 1 USDT；这是本例的整数教学网格，不代表生产精度，也不允许浮点计算或静默截断。
- 甲初始 20000 USDT，买单 B1 为 `0.25 BTC @ 60100`，预留 15025 USDT、可用 4975 USDT；乙 S1 为 `0.10 BTC @ 60000`，丙 S2 为 `0.20 BTC @ 60100`，两卖单 BTC 已预留。
- 成交 `T420-1 = 0.10 BTC / 6000 USDT`、`T420-2 = 0.15 BTC / 9015 USDT`；`ResultBatch(market=BTC-USDT, batch_seq=420, trades=[T420-1,T420-2], release=10 USDT)` 完整可靠提交后，再至少一次交付。
- 账户域在同一 PostgreSQL 事务内原子提交双边分录、余额与预留、稳定批次身份去重及 payload 摘要、每市场连续消费水位和通知意图；乱序不能跨缺口。可靠受理、成交提交、账务提交、查询可见是不同阶段；客户端超时不能认定失败或释放，既成成交不能靠改状态、改余额抹去。
- 本例完成入账后，甲为 4985 USDT + 0.25 BTC，预留为 0；乙收到 6000 USDT，预留 BTC 为 0；丙收到 9015 USDT，仍预留 0.05 BTC。链上重组、预言机、提现均不属于上述主线，涉及时另行显式改变前提。

> 以下是教学面试设计，不是用户项目经历；核对、恢复与签核均为设计方案，不包含实测成绩或已执行验证结论。

## 第 1 层：420 已成交提交、账务仍到 419，不一定是错账

**面试官：** 撮合里有 420 的两笔成交，账户域水位为 419，查询还显示甲预留 15025 USDT。你会立刻补账或退款吗？

**面试者：** 不会。这可能是合法在途，而不是已经证明的漏账。可靠受理说明请求进入承诺范围，成交提交说明撮合结果已经成为权威事实，账务提交说明账户事务落地，查询可见则还要等异步投影追上；这些阶段不能混成一个成功状态。撮合已到 420、账户域在 419 时，查询仍显示成交前预留，有一种合法解释就是 420 尚未入账。我先核验各水位的来源、采样时间、批次摘要和最老在途年龄，查清交付停在哪一段。此时不能拿撮合终态直接断言当前余额错误，更不能退款。只有把两边放到同一切面，才能判断是正常延迟、缺失处理还是账务事实冲突。

## 第 2 层：同一水位必须绑定一致快照，不能拿当前余额比过去

**面试官：** 那就统一比较 419。可是你读取余额时，账户域已经处理了 420；若以后还增加别的市场，共享 USDT 又该怎么对齐？

**面试者：** “都写 419”不等于取得了 419 的状态。暂停新增并排空到约定屏障后，可以在冻结窗口内获取撮合与账户的对应快照；在线核对则需要可重建的历史状态，或先取得绑定水位的数据库一致快照，再把撮合历史重放到同一切面。账户水位与余额必须在同一个 PostgreSQL 一致快照中读取，不能分别查询后拼接。数据库的一致快照也不能自动提供任意过去批次的余额。主线只有一个市场；若显式扩展成多市场，共享账户的余额包含各市场及其他资金流的影响，单个 419 不够，要用版本向量及相关资金流进度标识一个可达切面，或隔离账户与入账窗口。不同市场的序号相同没有全局先后含义。

## 第 3 层：核对成交、分录归属和账户状态，不只核对借贷平衡

**面试官：** 已经取得包含 420 的一致切面，而且每个币种借贷都平衡。能不能据此宣布账没问题？

**面试者：** 还不能，给错账户的分录也可能完全平衡。我做三方核对：撮合的权威成交明细和释放指令、账户域的分录凭证、由账本与预留记录支持的账户状态。逐笔检查 T420-1、T420-2 的买卖账户、资产、数量、金额、归属订单及批次摘要，再验证聚合。甲预留应减少 15025 USDT，其中 15015 支付给乙丙、10 回到可用，BTC 增加 25 lot；乙预留减少 10 lot、USDT 增加 6000；丙预留减少 15 lot、USDT 增加 9015，剩余 5 lot 继续归属 S2。还要对照订单剩余量与预留生命周期，证明没有提前释放或多扣。每币种平衡只是必要条件，身份、归属、完整性和余额聚合也必须成立。

## 第 4 层：先分类差异，避免所有异常都用重放处理

**面试官：** 三方核对发现，有的批次找不到分录，有的出现两次，有的同一批次内容不同，还有的分录正确但余额不对。你怎么安排修复？

**面试者：** 我先保留原始凭证并按类型处置。权威结果存在、账户事务不存在，且已经超过合法在途条件，是待补交或待重放的缺失；交付记录出现两次而账务只发生一次，是被幂等吸收的重复，不是重复扣款。若账本确实重复记账，则属于真实账务错误。相同批次身份出现不同摘要，是内容冲突，必须隔离并回查权威来源，不能选最新一份覆盖。分录与预留明细正确、同切面余额聚合错误，才是物化状态漂移；只有查询旧，则是投影落后。每类都要带上水位、快照身份和证据时间。若所谓差异是比较切面错误，先修核对口径，不能为了对齐报表制造一笔无依据的补账。

## 第 5 层：缺失批次按原身份补交，去重与入账必须同事务

**面试官：** 现在确认账户域停在 419，420 完整可靠提交但没有入账，421 反而先送到了。你怎样补交，而且避免再次超时后重复记账？

**面试者：** 我从撮合可靠记录取回原始 420，保留 `(market,batch_seq)`、成交身份和既有摘要口径，不生成一个“修复版 420”或换新批次号。账户事务先验证写入权限与任期围栏、锁定该市场进度，再查询原批次去重证据：已存在则核验摘要，相同就返回原结果，不同就隔离冲突；仅对尚未应用的新批次检查 `batch_seq == 当前连续水位 + 1`，本次为 420 紧接 419。然后按同一事务提交双边分录、余额和预留变化、去重记录、水位 420 以及通知意图，提交确认后才确认交付。421 可以暂存或延后重送，但不能跨过缺口。若提交回包丢失，按原身份重试：已提交且摘要相同就返回既有结果，摘要不同则阻断。即使当前水位已经更高，迟到重复也要查原批次证据，不能仅凭序号小就吞掉冲突。通知从持久意图继续发送，不能用通知重发触发再次入账。

## 第 6 层：真实错误用授权补正保留因果，不篡改旧账

**面试官：** 重放可以补缺失，但如果 420 已提交，账本却把丙的 9015 USDT 记给了其他账户，借贷仍然平衡呢？再重放一次能修好吗？

**面试者：** 不能，正常去重会阻止再次执行，关掉去重则会连正确的部分也再记一遍。这是已有凭证证明的真实错误，需要冻结受影响操作，核清错误分录、后续资金使用和正确归属，再走授权补正。补正以独立且稳定的修复案件身份入账，关联原批次、原分录、原因、审批人和核对切面，用冲正与正确补记表达净变化，同事务更新相应账户状态并留下审计证据，不能改旧分录或直接把余额改成目标数。若误收账户已用掉资金，还要显式处理冻结、追偿或损失，不能假装钱仍在。补正自身也须幂等，重复执行修复案件不能再补一次；后续重放原 420 仍只认原事务，不会重复应用补正。

## 第 7 层：灾备恢复先围栏旧主，再按承诺还原各阶段证据

**面试官：** 你刚做完补正，主库又发生故障。备份能启动，但只到 419，旧主可能还活着。怎样判断这算不算恢复成功，RPO、RTO 又怎么定？

**面试者：** 先在权威持久化写入点围栏旧主，保证新旧写者不能同时提交，再接入备份与可靠日志。要分别恢复可靠受理的请求身份和命令位置、撮合提交的结果及摘要、账户事务与补正凭证、连续水位和通知意图；查询投影可以从权威数据重建，但不能拿它反推账本。备份到 419 不代表允许丢掉已承诺的 420，也不能漏掉刚提交的补正。RPO 来自对外持久性承诺及故障域：若承诺覆盖该故障下的零已确认数据丢失，就必须有相应日志与副本证据；证据丢失应升级事故，不能宣称满足。RTO 则从业务允许中断时间倒推围栏、恢复、重放、对账和准入验收预算，不是数据库能连接或进程启动的时间。

## 第 8 层：显式扩展 EVM 充值后，重组不能照搬普通成交重放

**面试官：** 按这个证据链恢复时，如果额外发现同一事故窗口内一笔 EVM 充值来自已被替换的区块，能像补交 420 一样重新扫链就结束吗？

**面试者：** 这里显式扩展为带 EVM 托管充值和提现的场景，不改变前面现货成交的权威性。充值观测必须保留链标识、交易与日志定位、区块高度、block hash、父块关联及确认状态，不能只记高度。重组先按区块哈希找共同祖先，撤回孤块上的待确认投影，再按新规范链重扫；重新包含时也要根据来源凭证和状态迁移防止双记。若充值已经入账，就不能删旧分录或只回撤页面余额，要用关联原充值的幂等补偿流程及授权凭证处理。资金已被使用或提走时，还需冻结受影响资金操作并核查敞口，链外转出不会随重扫自动撤回。普通 420 是已经提交的链下成交义务，不能因充值重组被抹去，两类恢复的证据和风险边界不同。

## 第 9 层：划定有界验收期间，并证明观测仍然新鲜

**面试官：** 链下批次、补正和这个充值变体都能解释了，但新事件一直到来，对账总在追最新高度。怎样给恢复验收一个真正能结束的范围？

**面试者：** 我先固定事故影响起点和验收截止切面，为每市场列出连续水位、相关资金流进度、账户快照版本及补正版本；若包含充值变体，还要记录规范链截止区块哈希和确认口径。可以在受限准入下排空到屏障，也可以基于可重建历史选择一个已完成的可达切面，不能无限追逐最新头部。范围内每个缺失、冲突、漂移都要有分类、处理结果与复核证据，范围外的新义务另行统计，不能混入旧期间掩盖差异。随后核验监控采样时间、来源和实际水位，防止缓存或断采的“零积压”被当作恢复。追平速度、最老未完成义务年龄和风险功能限制也要可解释；有界结案不等于停止观察后续风险。

## 第 10 层：恢复签核要区分账务完成、查询追平和准入放开

**面试官：** 有界期间已经核完，观测也新鲜。是不是签一个“恢复成功”，就可以把订单、查询和扩展场景里的提现同时放开？

**面试者：** 应分阶段签核。先证明权威写者唯一、承诺数据可恢复、连续水位无缺口、批次摘要一致、真实错误已授权补正并复核，再声明账务恢复到指定切面；查询投影随后追平，并明确展示截至水位。对于本例无其他后续操作的 420 切面，应看到甲 4985 USDT 加 0.25 BTC、预留为零，乙收到 6000 USDT 且预留 BTC 为零，丙收到 9015 USDT 且仍预留 0.05 BTC。订单按小流量、观察窗口、逐步放量恢复，阈值恶化就暂停或退回；提现扩展另需资金可信与转出风险核验。账户、撮合、运维及风险责任人分别确认对应证据和遗留限制，签核记录具体切面与条件，不用一句“服务已启动”代替全部恢复结论。

---

**讲透的机制：** 同切面对齐 → 三方核对 → 差异分类 → 原身份补缺或授权补正 → 阶段证据恢复 → 有界验收与签核。

**最容易答错的边界：** 当前余额不能直接对比过去水位；借贷平衡不证明归属正确；幂等重放不能修复已经提交的错误账，更不能撤销链外提现。

**检验反例：** 撮合到 420、账户到 419、查询到 418，且下一秒账户已经到 421。如果方案直接拿当前余额对比 420 并自动补差，或只因借贷相等就通过验收，就没有真正建立同水位核对。
