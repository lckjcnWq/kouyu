# 大问题 4：怎样验证 Go 交易服务的并发历史与退出生命周期，而不把无数据竞争当成业务正确？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| goroutine / 单市场写者 | 前者是并发任务，后者独占某市场订单簿的裁决权。 | 撮合串行不等于入口占资、账户提交和查询都自动串行。 |
| 权威顺序 | 系统对业务已经承诺的处理先后。 | 不能靠 goroutine 启动时间、客户端点击时间或回包速度重排。 |
| 并发占资 | 多个请求争用同一份可用资产。 | 甲的 20,000 USDT 不能同时支持 15,025 与 10,000 的预留。 |
| 数据库约束 | 在真实存储处约束并发写入的机制。 | 行锁、条件更新等保护账户，进程无共享变量仍可能出现业务竞争。 |
| 成交撤单竞争 | 同一数量究竟先被成交还是先被撤销的裁决。 | B1 若先提交，后撤 S2 只能撤剩余 5 lot。 |
| 线性化 / 合法历史 | 将承诺原子生效的操作解释为满足约束的串行顺序。 | 只检查明确承诺的局部范围，不要求异步页面与撮合共享全局瞬间。 |
| 未决操作 | 已调用却没有明确终局回执的操作。 | 超时不能一律删除，要保留可能已经完成的分支或查权威结果。 |
| barrier / 语义屏障 | 明确知道任务到达某一步后再放行。 | 比 sleep 更能控制余额决策、提交后未响应等目标窗口。 |
| race detector | 检查实际执行里部分未同步内存访问的工具。 | 不能证明没有数据库透支、错误历史、死锁或任务泄漏。 |
| request context / 服务生命周期 | 前者管理一次等待，后者管理服务托管的工作。 | 客户端离开不取消已可靠受理的 B1，也不授权释放预留。 |
| close / 关闭所有者 | 结束通道发送的一种操作，以及负责协调它的一方。 | 多发送者要先确认都结束，消费者不能随手关闭仍有人写的队列。 |
| WaitGroup / join | 登记任务并等待它们真正退出。 | Go 1.21 先登记再启动；通道为空或已关闭都不能替代退出确认。 |
| select / 取消竞争 | 多个就绪动作之间的选择。 | 同时可发送又已取消时，不保证取消分支优先。 |
| 泄漏与恢复证据 | 分别证明资源有人管理、持久义务没有丢失。 | 栈、任务登记和重启后业务核对要一起看，不能只数 goroutine。 |

## 把整篇文章压缩成一个故事

测试者给甲设置 20,000 USDT，显式增加一个竞争变体：B1 要预留 15,025，B2 要预留 10,000，暂时冻结撮合与释放。用屏障让两次占资接近决策点，再检查真实数据库只能允许其中一个成功。即使每个请求使用独立 goroutine、race 检测没有内存冲突，两者都按旧余额成功仍然是透支；后面的单市场写者救不了前面的账户错误。

另一个独立变体让撤 S2 与 B1 竞争。若 B1 先提交完整 420，乙成交 10 lot、丙成交 15 lot，后来的撤单只能处理丙剩余 5 lot；若撤单先权威生效，B1 的未成交部分则按 GTC 留簿，不能仍套用基线终态。历史检查按各自承诺范围找合法顺序，不把异步页面强行纳入全局线性化，也不能把超时操作一概当作没发生。

最后在可靠受理后取消客户端等待，再安排服务停止。已接下的 B1 仍应能恢复；协调者停止新增、等发送者结束后按所有权关闭通道，等 worker 真正返回并 join，保留必要消费路径避免互等。退出验证还要查未登记重试任务、栈和持久进度：任务少了却丢成交，或账务正确却留下无人管理的阻塞，都不合格。这是并发与生命周期验证设计，未实际运行竞争检测、停机演练或数据库测试。

[专题总览](README.md)

- **流程位置：**并发入口占资与可靠受理之后，由单市场写者排列撮合命令，再经账务与异步 worker 完成交付和退出。
- **核心机制：**局部权威顺序、受控交错、限定承诺范围的历史检查，以及取消、关闭与 join 的所有权。
- **前提：**Go 1.21+；BTC/USDT 托管现货；链下单市场单写者订单簿；限价 GTC、价格时间优先、零费、无杠杆。以下均为教学验证方案，不表示实际执行过并发或竞争检测。

**共同教学基线。**甲初始 20000 USDT；乙 S1 卖 0.10 BTC@60000，丙 S2 卖 0.20 BTC@60100，卖单 BTC 已预留。甲 B1 买 0.25 BTC@60100，预留 15025 USDT，可用 4975 USDT。T420-1 按 S1 价格成交 0.10 BTC/6000 USDT；T420-2 按 S2 价格成交 0.15 BTC/9015 USDT。`ResultBatch(market=BTC-USDT,batch_seq=420,order=B1,trades=[T420-1,T420-2],release=10USDT)` 完整持久提交后交付，重试保持批次身份及载荷摘要。账户在一个 PostgreSQL 本地事务内提交双边分录、余额与预留、批次去重、该市场连续消费水位和通知意图；同载荷重复无新增业务影响，异载荷冲突隔离，乱序不越缺口。通知与查询投影异步，消息至少一次。最终甲 4985 USDT+0.25 BTC、预留 0；乙 6000 USDT、BTC 预留 0；丙 9015 USDT、0.05 BTC 仍预留。未给出的账户初始资产只断言增量。

价格单位为 1 USDT/BTC，数量为整数 lot、1 lot=0.01 BTC，资金为整数 USDT；`60000×10÷100=6000`、`60100×15÷100=9015`，金额必须整除，其他精度另作变体。撮合域权威订单与成交，账户域权威余额、预留与账本，查询投影非权威。可靠受理≠撮合提交≠账务提交≠投影可见；超时不能证明失败或触发释放预留。基线不涉及链上。下面为制造竞争而增加订单或撤单时，会显式称为变体，不将其结果混入基线终态。

## 第 1 层：请求同时到达，究竟是谁决定同市场的权威顺序？

**面试官：**Go 有多个入口 goroutine，B1 与撤单可能同时进入。单市场单写者到底能保证什么，又不能保证什么？

**面试者：**单写者保证该市场订单簿只有一个权威状态转换顺序，处理命令时按已承诺的序号推进，而不是让多个 goroutine 各改一部分盘口。价格时间优先中的“时间”应落实到同价订单的权威受理顺序，不能用 goroutine 启动先后或墙钟误差替代。命令尚未确定先后时，任一符合受理契约的顺序都可能合法；如果系统已向外承诺序号，恢复和排队就不能任意重排。这个保证不自动扩展成账户事务、消息投递和页面查询的全局顺序。验证要分别记录入口调用、命令身份、受理序号与撮合提交点，先明确系统究竟在哪个边界承诺排序，再判断交错是否违规。

## 第 2 层：市场只有一个写者，为什么入口占资仍可能竞争透支？

**面试官：**订单簿已经串行了，你还会怎样验证两个并发买单抢同一份 USDT 的问题？

**面试者：**占资属于账户域，不能指望后面的撮合串行弥补入口余额检查的竞态。我会显式增加竞争变体：甲仍有 20000 USDT，B1 要预留 15025，另一买单 B2 要预留 10000，先暂停后续撮合和释放，只检查两次占资。通过屏障让两个请求都进入余额决策附近，验证真实数据库中的行锁、条件更新或等价约束使它们按合法顺序生效；在这个冻结窗口内只能一张成功，另一张因不足被拒绝，不能都凭旧余额成功。预留记录还要绑定各自命令身份，重复请求不能再占一次。即使 Go 内存没有共享变量，数据库层的先查后改仍可能发生业务竞争，因此必须检查权威余额与预留，而不只看返回码。

## 第 3 层：占资安全以后，撤单与成交竞争的合法结果怎样界定？

**面试官：**再增加一个撤销 S2 的命令，与 B1 同时到达。测试应该固定期待撤单成功，还是固定期待 B1 吃掉 S2？

**面试者：**都不能无条件固定，我会按单写者确定的命令顺序给出合法结果集合。若 B1 先处理并完整提交 420，就先形成基线的两笔成交，随后撤 S2 只能取消剩余 5 lot，并通过后续持久结果驱动账户释放那部分 BTC；不能声称已成交的 15 lot 也撤回。若撤 S2 先提交，B1 后来只能先吃 S1，未成交部分按 GTC 留簿，这已是不同于基线的变体终态。验证禁止出现既报告 S2 全撤成功，又把其中同一数量交给 T420-2 的历史。账户按连续批次处理释放与成交，不能因撤单回包更快就越过 420，或由入口超时直接归还卖方预留。

## 第 4 层：有合法结果集合后，怎样做历史线性化检查才不过度承诺？

**面试官：**你会不会把占资、撤单、撮合和页面读取放在一起，要求它们都对应一个瞬时完成的串行历史？

**面试者：**不会，线性化检查只覆盖系统确实承诺原子生效的操作范围。我会为账户占资记录调用与返回，为单市场撮合记录对应的权威提交事件，再用各自顺序模型搜索是否存在满足非重叠操作先后约束的合法历史。重叠操作允许多个顺序，超时未决操作也不能被粗暴当作未发生，必须保留可能完成的分支或补充权威结果。可靠受理的返回只承诺命令可恢复，不能被解释为撮合已经完成。异步投影读不承诺线性一致，应按版本单调性和追平规则检查，而不是强行寻找一个全局线性化点。对完整链路，我检查因果关系与资金不变量，不伪造跨域原子事务。

## 第 5 层：历史检查需要精确交错，为什么不能靠 sleep 和 race detector？

**面试官：**我启动两个 goroutine，各 sleep 几毫秒，再跑竞争检测，没报警是否就证明这类历史安全？

**面试者：**不能。sleep 只能改变概率，不能证明第二个请求确实停在目标窗口。我会用测试专用 barrier 或可控端口，让任务报告“已到余额读取前”“已提交但响应未交付”等语义位置，测试端收到就绪后再放行下一动作；数据库竞争验证仍使用真实事务和独立连接，不把生产同步本身替换掉。race detector 只能发现本次执行中被触发的部分内存数据竞争，查不出加锁正确但账户归属错误、数据库丢更新、重复入账或 goroutine 泄漏。屏障也只覆盖选定交错，可能改变时序，因此需要多种受控历史与非受控调度探索互补。无报警最多是一项证据，不是对所有业务竞争和全部调度的证明。

## 第 6 层：请求 context 取消后，已可靠受理的下单意图能否一起取消？

**面试官：**你把请求 context 传进所有 worker，客户端断开就全部退出，这不是最干净的生命周期管理吗？

**面试者：**对尚未可靠受理的临时工作可以取消，但已持久受理的交易意图不能随客户端连接消失。请求 context 管理本次等待，不是撤单授权；受理成功但回包丢失时，服务必须能按命令身份恢复并查询，不能提前释放 B1 的 15025 USDT。持久意图由服务生命周期下的 worker 继续推进；若用户要撤单，必须提交独立、可恢复并进入市场顺序的撤单命令。验证可在受理提交后、撮合前取消请求，随后确认仍只有一个订单和一条可追踪结果。服务退出可以停止当前处理尝试，但必须留下可恢复进度，context 不能撤销已经提交的事务，也不能保证一个正在 select 的发送分支绝不会继续运行。

## 第 7 层：服务自身要退出时，怎样安排 worker join 和 channel 关闭？

**面试官：**请求取消不能丢持久意图，那进程停止时如何避免 worker 互等、向已关闭 channel 发送，或者无限等积压清空？

**面试者：**我会先停止新接收并等待入口发送者退出，再由明确的所有者关闭工作 channel，或统一用取消信号停任务，不能让消费者随手关生产者仍在写的通道。多生产者场景由协调者等所有发送者结束后关闭，接收方只负责读取结束信号。已受理的任务可以在期限内排空，超期则停在可恢复边界，不能把内存队列遗失当成业务已取消。每个 worker 都有 join 句柄或 WaitGroup，先登记再启动，避免计数为零时与 Wait 并发 Add。关闭缓冲 channel 也不代表任务已执行完，必须等待消费者真正返回。Go 1.21+ 的教学方案使用这些基础原语，不依赖更高版本才有的便捷启动接口。

## 第 8 层：join 返回还不够时，怎样收集无泄漏与可恢复的验收证据？

**面试官：**所有登记的 worker 都退出了，但还有未登记的 goroutine 或丢失通知，你会怎样设计最后一轮验证？

**面试者：**我会覆盖 worker 在收消息、发消息、等定时器、等数据库和等重试时的退出，再用屏障确保确实进入相应阻塞点后触发停止。验收同时看登记任务的 join 结果、活动任务计数、待提交事务状态和 goroutine 栈；总 goroutine 数只能作线索，要扣除已知运行时与数据库连接池后台任务，不能要求机械回到同一个整数。然后重启处理链，证明已受理命令、未确认的批次和已提交的通知意图能被恢复，重复交付不产生第二次业务影响。最终基线资金与预留必须正确，投影在限定条件下追平。退出得快却丢掉持久义务不是成功，账务正确但永远卡住的 worker 也不算生命周期合格。

## 讲透的机制

- **顺序有归属：**单市场写者管理订单簿顺序，账户事务管理占资与记账顺序，异步投影有独立进度；不能用其中一个替代全部。
- **历史检查有范围：**在承诺的原子操作范围内检查线性化，在跨域链路检查因果与连续水位，对投影检查版本与最终追平。
- **退出有责任链：**停止受理、结束发送者、按所有权关闭、让 worker 返回并 join、恢复未尽持久义务，缺一环都可能留下泄漏或丢任务。

## 最容易答错的边界

- 没有 Go 数据竞争，不代表数据库没有占资竞争，更不代表业务历史符合价格时间优先。
- 多个请求“同时开始”不等于它们在权威受理边界没有先后；已承诺的序号不能被 goroutine 调度推翻。
- context 取消、客户端超时和 channel 关闭都不是撤回已提交意图的业务命令。
- channel 被关闭、缓冲被读空与消费者完成业务是不同事件；需要 join 证明任务真正退出。
- Go 的 select 在多个分支同时就绪时不保证优先选择取消分支，不能仅靠 select 顺序断言取消后绝无副作用。

## 检验反例

1. **无内存竞争却透支：**两个请求分别从数据库读到 20000 USDT，再各自占资成功；race detector 可沉默，账户历史必须拒绝。
2. **撤成双赢：**S2 报告全量取消成功，T420-2 又消费同一 15 lot；必须不存在符合撮合顺序的合法历史。
3. **假撤单：**B1 已可靠受理后客户端取消 context，系统直接退回 15025 USDT，但撮合稍后完成；生命周期设计必须阻止这类释放。
4. **假退出：**接收方关闭 channel 后主函数返回，生产者尚未结束；即使一次没 panic，也没有证明关闭所有权正确。
5. **未登记泄漏：**worker 的 join 已完成，内部另起的重试 goroutine 仍等待永不触发的定时器；栈与任务归属证据应使验收失败。
