# 大问题 6：怎样证明交易系统的容量是可持续结算的容量，而不是 HTTP 成功率堆出来的数字？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 可持续结算容量 | 持续受压仍能完整履约、积压不失控的处理能力。 | HTTP 受理快只是入口能力，不能替账务提交速度背书。 |
| 去重吞吐 / 负载 mix | 前者不把重复当新业务，后者明确流量种类与比例。 | 420 重投不是新成交；只压不成交挂单也测不到真实入账能力。 |
| 独立资金夹具 | 为测试工作准备明确的账户与资产初态。 | 防止余额耗尽后全走快速拒绝，让吞吐虚高。 |
| 闭环 / 开环 | 闭环等响应再发送，开环按计划到达节奏发送。 | 两者模拟不同负载，开环不能让服务慢自动减少计划压力。 |
| 协调遗漏 | 服务变慢时，发生器跟着少发，漏掉本该到达的慢样本。 | 要同时报告计划量、实发量、发送迟滞和未发工作。 |
| t0 / t1 | 请求计划发送与真正发送的时间。 | 从 t0 计时包含发生器等待，从 t1 计时解释实际服务路径，两者都保留。 |
| tA / tM / tJ / tV | 受理、撮合提交、账务提交与投影可见的阶段时间。 | 未成交 GTC 不要求立即产生 tM；成交到账务从真实 tM 起算。 |
| P99 / 合并直方图 | P99 描述慢端分布，直方图用桶计数汇总样本。 | 先合并相同口径的桶，再估分位数，不能平均各实例 P99。 |
| pending / 超时样本 | 尚未完成和已到期仍未完成的对象。 | 不能只统计完成者，把最慢、卡死请求从报告里删除。 |
| 稳态 / 排空 | 前者持续运行不漂移，后者停止或减少新增后清完积压。 | 短时峰值不能代替稳定容量，恢复要看最老年龄下降。 |
| pprof / 单变量对照 | 前者提供开销与等待线索，后者验证某项改动的影响。 | CPU 热点不能直接证明数据库慢的根因，没有采样就不能编造发现。 |
| 撤单资源保护 | 在权威排序之前预留撤单接入能力。 | 不授予后来的撤单越过已排序成交命令的权力。 |
| 背压 / 持久义务 | 减少新增压力，同时保留已可靠接下的责任。 | 队列满不能丢已提交成交或提前确认交付。 |
| 正确性验收 | 压力与恢复下仍逐笔核对权威结果。 | 420 的两笔成交、10 USDT 释放和丙剩余 5 lot 要同时正确。 |

## 把整篇文章压缩成一个故事

容量评审看到下单 HTTP 成功率很好，却发现撮合不断提交结果、账户一直停在 419。团队于是重新定义测量：用独立资金夹具准备 B1 类成交、挂单、撤单和重试，不把重复投递算成新成交，也不让账户耗尽后全走快速拒绝。真正要看的，是完整批次持续入账、积压和最老年龄稳定，而不是入口把多少义务暂时塞进队列。

发生器同时安排闭环和开环场景，分别记录计划时间 t0、实发时间 t1、可靠受理、撮合提交、账务提交和投影可见。服务变慢时，计划却没发出的工作也要报告，不能把压力偷偷降掉。多个发生器先合并相同口径的直方图，不平均 P99；超时、pending 和热市场单列，不能让快速拒绝把慢结算稀释。资源与 pprof 只是定位线索，优化还需单变量对照和重新核账。

当数据库变慢，就限制新增、保留撤单接入资源，但不让后来的撤单越序，也不丢 420。恢复方案应证明最早缺口补齐、排空有余量，并核对两笔成交只让甲花 15,015 USDT、释放 10，最终可用 4,985且新增 0.25 BTC，丙仍预留 0.05 BTC。性能曲线变好而资金重复生效仍然失败。本文只给压测口径与手工推演，没有执行压测、采样或提供容量成绩。

**流程位置与核心机制：** 从压测流量进入、可靠受理、单写者撮合、成交批次可靠提交，走到账务事务提交和异步可见。容量必须同时满足进度稳定、尾延迟可控与业务不变量，不能只看入口响应。

**共同前提：** Go 1.21+；BTC/USDT 托管现货，链下单市场单写者、价格时间优先，只讨论限价 GTC、零手续费、无杠杆。甲初始 20000 USDT，买 B1：0.25 BTC@60100，预留 15025 USDT、可用 4975 USDT；乙卖 S1：0.10 BTC@60000，丙卖 S2：0.20 BTC@60100，卖单 BTC 均已预留。按既定顺序得到 T420-1＝0.10 BTC/6000 USDT、T420-2＝0.15 BTC/9015 USDT；完整 `ResultBatch(market=BTC-USDT,batch_seq=420,trades=[T420-1,T420-2],release=10USDT)` 可靠提交后至少一次交付。账务在同一个 PostgreSQL 事务中提交双边分录、余额/预留、稳定批次身份及载荷摘要、每市场连续消费水位和通知意图，不能跨缺口推进；投影异步。

最终甲为 4985 USDT＋0.25 BTC、预留为 0；乙为 6000 USDT、BTC 预留为 0；丙为 9015 USDT、0.05 BTC 仍预留。价格单位为 1 USDT/BTC，1 lot＝0.01 BTC，资金单位为 1 USDT：本例数量为 25、10、20 lots，成交为 10、15 lots，总成交额 15015 USDT，释放的 10 USDT 是价差退款，不是利润。撮合权威是订单和成交，账户权威是账本与资产，查询投影不是资金真相。可靠受理、成交提交、账务提交、可见性分别确认，客户端超时不能认定业务失败或触发释放。链上机制只作为明确声明的变体，不纳入本篇主线。

**证据范围：** 以下为教学压测方案、伪代码口径和手工推演，未执行真实测试，不提供性能成绩，也不声称个人生产经历。

## 第 1 层：为什么 HTTP 成功吞吐不能代表交易容量？

**面试官：** 如果下单接口的 HTTP 200 很多、延迟也很低，你会如何判断这台交易系统还能不能继续加流量？

**面试者：** 我不会把 HTTP 200 当作已结算。先按接口约定确认它是否只表示可靠受理，再分别统计成交批次可靠提交、账务提交及投影追上的速度。这里可结算吞吐的主指标是：观察窗口内，完整批次已在账务事务提交的去重成交笔数或成交量，不能把重投次数算成成交，也不能把没有成交的 GTC 挂单算成账务失败。B1 产生两笔成交，但只交付一个包含释放动作的 420 批次，不能只结算其中一笔便宣告完成。只有持续施压时入口、撮合、账务进度都稳定，积压和最老待处理年龄不持续上升，延迟与正确性也满足约定，才可讨论可持续容量；靠队列暂存出来的峰值只是缓冲能力。

## 第 2 层：怎样让负载 mix 不把撮合和幂等路径测空？

**面试官：** 你选了端到端可结算吞吐，但如果流量全是不成交的挂单，数字仍然很好看，怎样设计负载？

**面试者：** 我会把下单、可成交限价单、长驻挂单、撤单、重复撤单和重试组成明确的负载 mix，并分开记录各类结果；比例是待论证的教学参数，不冒称来自真实生产。主线反复使用独立资金夹具推演 B1、S1、S2，避免余额耗尽后所有请求都走快速拒绝路径。重复撤单沿用稳定业务意图，验证不会重复释放；撤单与成交竞争要服从单写者的权威排序。冷热 market 只在显式多市场容量变体中加入：每市场仍单写者、独立序列，热市场集中冲击，冷市场验证隔离，不能用冷市场平均值掩盖热市场。另行标注共享账户造成的账务锁竞争，不能把资金准备、市场扩展和撮合算法的成本混为一个数字。

## 第 3 层：为什么只用闭环压测会漏掉最难看的尾延迟？

**面试官：** 负载已有成交和撤单，但客户端收到响应后才发下一单；当服务变慢，这种闭环方式有什么盲区？

**面试者：** 闭环适合模拟有限并发用户，却会随响应变慢自动降速，减少本该在拥塞期到达的请求，这就是协调遗漏的重要来源。我会保留闭环场景，同时增加按预定到达时间发出的开环场景，让到达率不被服务完成速度悄悄拉低。发生调度落后时，记录计划量、实际发送量、发送迟滞和未发出的工作，不能只统计成功发出的样本。开环发送队列也必须有界，超出的计划请求作为明确的发生器欠载或丢弃报告，不能假装系统承受了计划流量。交易依赖仍需成立：用预先准备的独立账户和已知可撤订单构造工作，不能为了赶进度凭空撤未受理订单。最终同时报告目标到达率、实际到达率和完成率，先证明压力确实施加到了被测链路。

## 第 4 层：怎样定义计时起点，避免把发送排队和异步提交藏起来？

**面试官：** 既然要保留计划到达时间，假设某请求计划在 t0 发出、t1 才真正发送，HTTP 返回后账务仍在排队，你如何计时？

**面试者：** 我会定义 t0 为计划发送、t1 为实际发送、tA 为可靠受理、tM 为完整成交批次可靠提交、tJ 为账务事务提交、tV 为对应投影可见。客户端同时测从 t0、t1 到收到受理凭据及观察到账务已提交的耗时，前者包含发生器迟滞，后者解释服务路径，两者都保留。客户端观察确认会包含回传或轮询开销，不能冒充数据库内部提交耗时；服务端各阶段另用本进程单调时钟计持续时间。跨机器时间戳需要同步及误差说明，不能直接相减便声称微秒级精度。tA 到 tM 不保证限价单立即成交，账务延迟应从实际产生的 tM 起算；tJ 到 tV 单独记录，禁止用投影暂未可见推断资金未入账。

## 第 5 层：多个发生器和实例的 p99 应该怎样合并？

**面试官：** 你已经分开计时，但十个发生器各报一个 p99，负责人要求一个总 p99，能否直接取平均？

**面试者：** 不能。分位数不是可线性平均的统计量，低流量实例与高流量实例的 p99 平均也没有全局分位数意义。我会统一计量单位、阶段、窗口和桶边界，合并各发生器的桶计数与总样本数，再从合并后的直方图估计 p99；选用可合并草图时，也要声明算法、精度和兼容条件。全局结果之外保留热市场、成交链路和撤单路径的受控分组，不能让大量快速拒绝稀释少量慢结算。超时和未完成样本不是自动消失的尾部：已经到期的样本计入失败，仍 pending 的单列数量及年龄。桶宽决定估计精度，目标附近必须有足够分辨率；报告还应给出样本量和边界误差，不能把粗桶插值得到的小数当作精确观测。

## 第 6 层：稳态资源与 Go pprof 能证明根因吗？

**面试官：** 合并后的账务尾延迟在长时间运行后恶化，而短时峰值很好看，你怎样用资源数据和 pprof 排查？

**面试者：** 我会在相同负载 mix、资金准备和阶段定义下延长观察，区分预热、稳态与排空，检查吞吐、积压年龄、goroutine、堆存活量、分配速率、GC、CPU、数据库连接等待和锁等待是否共同漂移。Go 1.21+ 的 CPU、heap、allocs、goroutine、block、mutex profile 用于提出假设，按需开启有开销的采样，并限制采集接口权限。CPU 热点只说明采样期间在哪里消耗 CPU，不能直接解释数据库提交慢；堆大也不等于泄漏，要结合存活对象及持续增长。随后做单变量对照，例如只改变批次大小或连接池上限，重新核对阶段延迟、资源与正确性，排除同时改多项带来的伪归因。没有实际采样和对照证据时，只能说“拟检查这些机制”，不能编造发现了某个生产瓶颈。

## 第 7 层：过载时能否让撤单走优先队列插到前面？

**面试官：** 如果长时间压力证明入口超过可持续能力，你希望保住撤单体验；给撤单独立队列并提高优先级可以吗？

**面试者：** 可以隔离撤单入口的连接、校验、配额和排队资源，但边界必须在权威排序之前。所有已进入同一市场权威顺序的命令仍按该顺序执行，不能让后来的撤单越过已排序的成交相关命令，也不能因此改变价格时间优先。为撤单预留有界资源、为新增风险流量限流，只是在排序前提高被接纳的机会，不是承诺撤单必定成功。可靠受理后的命令不能因队列满就静默丢弃，受理前明确拒绝与受理后结果未知也必须区分。如果已经完成资金预留却尚未可靠受理，应通过有身份、可核对的补偿协议恢复，而不是超时即解冻。过载验证要观察拒绝、排队年龄和撤单结果，检查重复撤单没有重复退款，终态订单没有再次成交。

## 第 8 层：下游变慢后，怎样证明恢复排空没有牺牲资金正确性？

**面试官：** 你已经保护了排序与撤单资源，若 PostgreSQL 暂时变慢，撮合仍产生已提交批次，恢复后怎样验收？

**面试者：** 我会保留所有已可靠提交的成交批次，限制新增受理并对积压设容量边界，不能以提高曲线为由丢掉成交或只交付批次前半段。手工故障场景包括 420 重投、先看到 421 却缺 420，以及账务已提交但确认丢失；账务必须依稳定身份和摘要幂等处理，在同一事务提交资产、分录、去重、水位与通知意图，连续水位不能跳过缺口。恢复时同时观察新增速率与排空速率，证明最老年龄下降而不是仅处理新数据。最后核对 420 的两笔成交与 10 USDT 释放恰好一次生效，甲 4985 USDT＋0.25 BTC，乙 6000 USDT，丙 9015 USDT 且仍预留 0.05 BTC，并核对每币种分录平衡。只改善吞吐却重复入账、漏释放或跨缺口推进，容量验证就是失败。

## 收束：容量结论必须附带正确性与测量边界

- **机制：** 可持续容量是“实际负载进入→完整成交提交→账务连续提交→有界排空”的闭环，不是某一跳的峰值 QPS。
- **易错边界：** 受理不等于成交，成交不等于入账，投影不等于账本；不能平均 p99，也不能把超时样本、发生器迟滞和 pending 删掉。
- **验证反例：** 构造“HTTP 都成功但账务水位停在 419”“全局 p99 好看但热市场持续积压”“恢复后重复投递 420”。任一场景不能被识别并保住不变量，就不足以给容量背书。
- **整数边界：** 本例 `价格整数×lots÷100` 恰好得到整数 USDT；扩展价格数量组合必须校验结算粒度与乘法溢出，不能用浮点或无约定舍入换取性能。本篇未运行压测，以上均为待实施、待举证的教学方案。
