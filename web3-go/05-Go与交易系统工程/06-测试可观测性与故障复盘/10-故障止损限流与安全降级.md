# 大问题 10：账务积压时，怎样止损、保护安全撤单，并在不破坏已提交成交的前提下恢复交易？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 止损 / 准入屏障 | 限制继续增加风险，并明确限制从哪里生效。 | 关新增不删除此前可靠受理的命令，更不抹去已提交 420。 |
| 在途义务 / 失控积压 | 已承诺待完成的工作，以及超过可控预算的堆积。 | 短暂落后不必然错账，但最老年龄与待履行规模恶化应收紧准入。 |
| 仅撤单模式 | 不再接新风险订单，保留可安全进入的撤单能力。 | 原有 GTC 不自动消失，撤单仍由市场权威顺序裁决。 |
| 撤单配额 / 有界缓冲 | 在入口保护撤单所需的连接和队列资源。 | 资源优先不等于执行越序，也不保证订单仍有剩余量可撤。 |
| 权威释放依据 | 已确定的成交与剩余量产生的资金处理事实。 | B1 全成后只释放价差 10 USDT，不能退原始 15,025。 |
| 熔断 / context 超时 | 限制新调用或停止当前等待。 | 都不推翻 COMMIT，未知不能直接标成失败。 |
| 提交未知 / 稳定批次身份 | 不清楚终局时，靠原业务键核对与收敛。 | 同 420、同摘要返回既有结果，不能换号再扣款。 |
| 重试预算 / 退避抖动 | 限制某段尝试的次数、速率和拥挤程度。 | 耗尽预算转持久待处理或人工负责，不等于丢弃成交。 |
| 背压 / ACK | 背压减少继续施压，ACK 确认这一段交付。 | 不能提前确认或覆盖旧消息来制造低积压。 |
| 风险功能降级 | 按功能的真实风险决定哪些能力受限。 | 基线现货无杠杆、无预言机，不能机械套只减仓。 |
| 提现扩展前提 | 另加平台资金对外转出的能力。 | 新增该前提后，授权依权威资金与待履行义务，不看旧投影余额。 |
| control_version / epoch | 控制策略的版本与写入所有权代际。 | 准入限制和旧主围栏要在实际授权、持久提交处生效。 |
| 合法旧结果 / 过期新写入 | 已经承诺的旧批次与失权者想新提交的结果。 | 围栏旧写者不能变成拒收旧代次合法 420，导致漏账。 |
| 恢复滞回 / 分阶段放量 | 退出限制要求持续稳定，并逐级开放。 | 不随 CPU 一降就全开，交易与提现扩展各有独立门槛。 |

## 把整篇文章压缩成一个故事

BTC-USDT 已提交 420，账户只到 419，最老批次越来越老。值班人员先确认数据新鲜和影响范围，再在权威准入点限制新订单与新增预留，保留结果交付、账务处理和查询。仅撤单模式保护连接与有界资源，不让后来撤单插到已排好顺序的命令前；甲的 B1 已全成，撤单超时也不能退回原来的 15,025 USDT，批次只允许释放未花掉的 10。

数据库调用超时、熔断打开以后，420 可能已经提交。团队保留原批次与摘要，按权威去重和水位查证；未知不退款、不放行 421。重试有并发、速率与退避预算，耗尽就转持久待处理并明确负责人，不丢义务。降级配置带版本和生效屏障，旧主在实际写入事务受 epoch 约束；但旧代次合法提交的结果仍须补交，不能把防双写变成漏账。

恢复时核对甲可用 4,985 USDT、0.25 BTC与零预留，卖方收入及丙剩余 0.05 BTC，再确认缺口补齐、观测新鲜和排空有余量，逐步放量并保留退档条件。正文另加提现时，转出需要独立资金可信门槛；基线现货不能套用衍生品只减仓。本故事是授权处置的设计推演，没有执行限流、切主、资金修复或生产恢复验证。

[返回专题总览](README.md)

**流程位置：** 可靠受理 → 单市场撮合 → 成交结果可靠提交 → 账户域入账 → 异步查询；本题沿“账务落后 → 收紧准入 → 保留降险通道 → 排空义务 → 验证恢复”连续追问。

**核心机制：** 止损要切断新增风险，不是删除存量义务；优先级不能越过权威顺序，熔断不能撤销已经提交的事实。

**公共短前提：**

- Go 1.21+；BTC/USDT 托管现货，市场标识为 `BTC-USDT`；链下单市场单写者、价格时间优先、限价 GTC、零费、无杠杆。撮合拥有权威订单与成交，账户域拥有余额、预留和账本，异步查询投影不是真相。
- 价格步长为 1 USDT/BTC，数量 `1 lot = 0.01 BTC`，资金最小单位为 1 USDT；这是本例的整数教学网格，不代表生产精度，也不允许浮点计算或静默截断。
- 甲初始 20000 USDT，买单 B1 为 `0.25 BTC @ 60100`，预留 15025 USDT、可用 4975 USDT；乙 S1 为 `0.10 BTC @ 60000`，丙 S2 为 `0.20 BTC @ 60100`，两卖单 BTC 已预留。
- 成交 `T420-1 = 0.10 BTC / 6000 USDT`、`T420-2 = 0.15 BTC / 9015 USDT`；`ResultBatch(market=BTC-USDT, batch_seq=420, trades=[T420-1,T420-2], release=10 USDT)` 完整可靠提交后，再至少一次交付。
- 账户域在同一 PostgreSQL 事务内原子提交双边分录、余额与预留、稳定批次身份去重及 payload 摘要、每市场连续消费水位和通知意图；乱序不能跨缺口。可靠受理、成交提交、账务提交、查询可见是不同阶段；客户端超时不能认定失败或释放，既成成交不能靠改状态、改余额抹去。
- 本例完成入账后，甲为 4985 USDT + 0.25 BTC，预留为 0；乙收到 6000 USDT，预留 BTC 为 0；丙收到 9015 USDT，仍预留 0.05 BTC。链上重组、预言机、提现均不属于上述主线，涉及时另行显式改变前提。

> 以下是教学面试设计，不是用户项目经历；阈值和处置动作属于设计口径，不包含实测成绩或已执行验证结论。

## 第 1 层：先判断积压意味着什么，再关闭新增风险入口

**面试官：** 撮合已经提交 420，账户域只到 419，而且落后时间还在增加。你会先扩容，还是先停交易？

**面试者：** 我先把“允许的在途”与“失控的积压”分开。420 已成交提交、账户域尚未入账，本身不说明账错；但最老未入账批次年龄、连续水位差、待处理资金义务和追平速度持续恶化，就需要止损，不能等 CPU 打满。先确认观测时间与来源新鲜，再按预先约定的风险预算限制新订单和新增预留，必要时进入仅撤单模式。限制必须落到权威准入点，不能只在网关提示维护。与此同时保留结果交付、账务处理和状态查询，明确返回所处阶段。暂停生效前已经可靠受理的命令仍须按权威顺序产生处理结果，不能静默删除；420 更不能因为系统暂停就被当成没有发生。

## 第 2 层：仅撤单模式保护的是准入资源，不是越序执行权

**面试官：** 你已经暂停新订单，但大量客户端重试把撤单接口也打满了。怎样让用户撤单，又不让“撤单优先”破坏原来的顺序？

**面试者：** 我给撤单保留独立的准入配额、连接资源和有界缓冲，并按账户、订单身份合并重复请求，避免重试用户挤掉其他人的降险机会。但这种优先只作用于接入资源，不允许已排在后面的撤单越过同市场已经确定顺序的命令。最终撤单仍进入同一个权威序列，由单写者判断订单剩余量。仅撤单模式禁止新增风险命令在暂停屏障后进入执行，不代表既有 GTC 订单自动消失。撤单产生的预留释放也要作为权威结果进入账户域的有序处理链；账户域卡在 419 时，不能绕过 420 先退后续撤单的钱。接口可报告撤单已受理，但必须区分权威撤成与资金释放到账。

## 第 3 层：成交与撤单竞争，只能由权威序列决定

**面试官：** 那么 B1 的撤单请求超时了，用户说自己是在看到成交前点的撤单。你能为了止损先把 15025 USDT 还给他吗？

**面试者：** 不能。客户端点击时间和查询展示时间都不是竞争裁决点，必须查撤单命令相对成交的权威位置。在本例中，420 已完整提交，B1 已成交 0.25 BTC，后来的撤单只能得到已终结或剩余量为零的结果，绝不能再释放原始 15025 USDT；应释放的只是批次中明确的 10 USDT 差额。S2 若在后续权威位置撤成，只能撤剩余 0.05 BTC，其释放还要等待对应账务处理。假如撤单真的在成交前权威生效，成交结果就不应还是本题给定的两笔交易，那是另一条历史，不能两种结果都保留。超时期间返回处理中或结果未知，并用原请求身份查证，不能拿临时退款替代确定性裁决。

## 第 4 层：熔断限制后续调用，不能取消已提交事务

**面试官：** 你坚持不提前退款，但处理 420 的数据库调用也超时了，熔断器已经打开。能取消这个事务，再从 419 重做吗？

**面试者：** 先承认提交结果未知。Go 的 context 超时、连接断开或熔断打开，只说明当前调用不能继续等待，不证明 PostgreSQL 没有提交；发出取消请求也不保证抢在 COMMIT 之前生效。我用稳定身份 `(market,batch_seq)` 到权威数据库核对去重记录与 payload 摘要，并结合事务内水位查证。若 420 已提交，双边分录、余额、预留、水位及通知意图应一起存在，重交同一批次只返回既有结果；若确定未提交，才按原身份重试。查证前不释放预留，不让 421 越过缺口。熔断器可以阻止新尝试、降低并发，却不能逆转既成提交，更不能把未知结果直接标成业务失败。

## 第 5 层：有界重试和有界队列，不能变成丢失义务

**面试官：** 结果未知的调用越来越多，大家都重试；你又要求不丢 420。怎样既保护数据库，又不让队列无限增长？

**面试者：** 我把单次尝试预算与业务义务寿命分开：每次调用有超时，重试有总并发、速率和阶段性预算，采用有上限的指数退避与抖动，并优先恢复每市场最早的缺口。预算耗尽后进入持久化待处理或人工处置状态，不代表丢弃批次。Go 的有界 channel 只是内存工作集，完整结果仍由可靠日志或持久队列保存，只有账户事务确认提交后才能推进交付确认；崩溃后允许原批重送。队列满时暂停拉取、施加背压，存储接近安全边界时进一步关闭新增受理，不能用覆盖旧消息或提前 ACK 换低积压。摘要冲突等确定性错误要隔离告警，不能靠无限重试淹没数据库，也不能跳过它推进水位。

## 第 6 层：数据不可信时，要按风险功能降级而非套用只减仓

**面试官：** 持久化重试保住了义务，但查询余额可能旧，账务还在核查。若产品要求“至少让用户提走钱”，你如何决定？预言机异常时能否统一只减仓？

**面试者：** 这里先显式扩展前提：原题没有充提，现在增加托管充值提现功能。提现是资金离开平台的动作，不能拿异步余额投影作授权依据；账务缺口、预留归属或已提交义务尚不可信时，应限制受影响账户与资产的提现，影响范围无法可靠界定时扩大限制范围，同时继续核查和处理已提交义务。只有权威账本、预留与待履行扣款足以支持授权时，才谈恢复资金转出。原现货撮合不依赖预言机，也没有杠杆仓位，不能机械套用“只减仓”。若另行改为杠杆或衍生品场景，才需要定义可信价格边界、风险暴露和可证明的降险操作；不能在价格不可信时仅凭一个方向标签放行交易。

## 第 7 层：控制面有版本，旧主必须在持久化写入处被围栏

**面试官：** 你决定限制提现并维持仅撤单，可有些实例还拿着旧配置，切主后旧撮合进程也可能恢复。怎样保证这些限制真的生效？

**面试者：** 降级策略需要版本、作用域、生效屏障、操作人、原因和审批审计；提现扩展策略与现货准入策略分别管理。网关只负责尽早拒绝，撮合权威入口与账户授权处还要核验有效策略，配置不可确认时不自动放开高风险操作。切主不是简单换路由：撮合持久化命令与结果的提交点必须校验写入 epoch，账户写入也应在同一数据库事务中锁定并核验所属分区的持久化 epoch；提升新主与旧主写入由这些落点串行裁决，过期写者不能提交。不能只靠进程自查或租约心跳。不过围栏限制的是新的权威写入，不应拒绝旧代次已经合法提交的 420 补交，否则会把防双写变成漏账。

## 第 8 层：恢复要看业务追平与稳定窗口，不是 CPU 降下来了

**面试官：** 控制面和旧主围栏都落实了，CPU 已经恢复正常。现在能一键恢复全部订单与提现吗？

**面试者：** 不能。CPU 下降可能只是入口关闭了，并不证明义务处理正确。我先核验旧主已被围栏、权威数据可查、连续水位无缺口、摘要无冲突，并在同一水位核对成交、分录、余额和预留；本例 420 入账后应得到甲 4985 USDT 加 0.25 BTC、乙 6000 USDT、丙 9015 USDT 且仍预留 0.05 BTC。再检查最老积压年龄、撤单排队时间、通知意图积压和观测新鲜度，并证明处理速率有追平余量。恢复按核查、仅撤单、小额限速新增、逐步放量推进，进入限制与退出限制使用不同阈值并要求持续稳定，避免来回振荡。提现扩展另有账本可信与转出安全门槛，不随交易入口一起自动解封；任一阶段恶化就退回上一安全档并留存证据。

---

**讲透的机制：** 准入止损、权威顺序、持久化义务与分阶段恢复形成闭环；资源优先级不能替代业务裁决。

**最容易答错的边界：** 超时不等于失败，熔断不等于回滚；撤单优先不等于越序退款，旧主围栏也不等于丢弃旧主合法提交的结果。

**检验反例：** 420 已账务提交但回包丢失，客户端再撤 B1。如果方案会释放 15025 USDT、丢弃重送批次，或仅凭 CPU 回落解除全部限制，就没有守住资金边界。
