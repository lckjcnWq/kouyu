# 大问题 7：怎样用业务 SLO 与连续进度水位说明用户到底等在哪一步？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| SLI / SLO | SLI 定义怎么量，SLO 定义希望达到什么服务水平。 | 先定对象、起止点、分母和证据，不能只写一个成功率。 |
| 分阶段承诺 | 受理、成交、入账与可见性分别评价。 | GTC 尚未成交不算结算违约，页面旧也不等于账务未完成。 |
| 稳定意图 / 批次身份 | 跨重试识别同一对象的业务键。 | 420 重投十次仍是一个批次，重试不重置首次合格请求时间。 |
| cohort / 窗口截尾 | 按开始事件分组，处理跨统计窗口尚未完成的对象。 | 到期才定案；未到期单列，已超时后来完成也保留原违约。 |
| HM / HJ / HP | 同市场撮合、账务及适用投影的完整连续进度。 | HP 只有使用相同批次坐标才可直接对比，独立序列需映射。 |
| 连续前缀 / 最大已见 | 前者前面全齐，后者只说明见过某个较大编号。 | 缺 420 却见 422，HJ 仍为 419。 |
| 水位差 / 最老年龄 | 分别描述同序列域积压数量与最老义务等待时间。 | HM−HJ 不是成交笔数，更不能跨市场相减。 |
| 指标标签基数 | 某个标签可能产生多少不同监控序列。 | 订单、账户和批次号无界，放受控日志而不放指标标签。 |
| 直方图 / 阈值桶 | 按耗时区间计数，明确服务目标的分界。 | 先合桶再算分位数；已完成耗时还需联看 pending。 |
| 错误预算 | 对服务及时性或可用性允许的违约比例。 | 教学 99.9% 对应 0.1% 坏事件，不允许拿它豁免重复记账。 |
| 燃烧率 / 多窗口 | 消耗预算的速度，以及长短窗联合判断。 | 坏比例除以 0.1%；14.4 倍对应 1.44%，不是实测生产阈值。 |
| 采集新鲜度 / 未知 | 观测是否仍可信，以及缺证据时的状态。 | 指标断流不能填零，也不能拿旧水位宣布恢复。 |
| 独立核对 | 按权威身份与一致切面验证实际业务效果。 | 指标健康不证明归属正确，资金异常要独立升级。 |

## 把整篇文章压缩成一个故事

用户问“B1 成功了，钱怎么还不能用”，指标负责人先拆问题：受理是否可靠、420 是否成交提交、账户是否完成、页面是否追上。教学目标分别为受理 300 毫秒、成交到账务 2 秒、账务到可见 1 秒内达到 99.9%，不是已取得的成绩，也不能把三个百分比直接当成同一群体的端到端保证。合法 GTC 挂单尚未成交，不应混进结算超时分母。

同一 420 重投十次只算一个对象，重试不能刷新起点；到期仍未完成就是违约，后来补交也不抹掉它。负责人看到 422 已到而 420 缺失，仍把账户连续水位保留在 419，并追踪最老批次年龄。水位差只能在同市场同序列域解释，投影若另有序列就用映射。汇总耗时先合桶，不平均 P99；订单号留在受控诊断路径，不把监控标签撑成无界集合。

告警用长短窗燃烧率观察持续违约，还要照顾低流量单笔卡死；监控断采则显示未知，不是假装错误归零。最终用权威记录核对甲花 15,015 USDT、释放 10，得到 0.25 BTC并剩可用 4,985。即使整体服务比例仍达标，重复扣款也不能被预算接受。这里只规定度量与手工推演，没有真实采集、SLO 达标或生产阈值验证。

**流程位置与核心机制：** 把可靠受理、完整成交批次提交、账务提交与异步可见分别度量，用稳定业务身份确定分母，用每市场连续水位和最老未完成年龄解释积压，再用错误预算决定响应力度。资金正确性不接受可用性预算折扣。

**共同前提：** Go 1.21+；BTC/USDT 托管现货，链下单市场单写者、价格时间优先，限价 GTC、零手续费、无杠杆。甲初始 20000 USDT，买 B1：0.25 BTC@60100，预留 15025 USDT、可用 4975 USDT；乙卖 S1：0.10 BTC@60000，丙卖 S2：0.20 BTC@60100，卖单 BTC 已预留。成交 T420-1＝0.10 BTC/6000 USDT、T420-2＝0.15 BTC/9015 USDT，完整 `ResultBatch(market=BTC-USDT,batch_seq=420,trades=[T420-1,T420-2],release=10USDT)` 可靠提交后至少一次交付。

账务在同一个 PostgreSQL 事务提交双边分录、余额/预留、批次去重记录（稳定身份＋载荷摘要）、每市场连续消费水位与通知意图，不跨缺口推进；投影异步。最终甲 4985 USDT＋0.25 BTC、预留 0；乙 6000 USDT、BTC 预留 0；丙 9015 USDT、0.05 BTC 仍预留。价格单位 1 USDT/BTC，1 lot＝0.01 BTC，资金单位 1 USDT；总成交 15015 USDT，释放 10 USDT 是价差返还而非利润。撮合权威订单成交、账户权威账本资产，查询不是资金真相。客户端超时既不能认定失败，也不能据此释放资产。本篇不引入链上最终性；链上机制只能另作显式变体。

**证据范围：** 以下数字仅为教学目标，所有口径、查询与推演均是文档方案；没有真实运行、SLO 达标记录或生产性能成绩。

## 第 1 层：用户承诺应该按哪个完成阶段定义？

**面试官：** 用户说“下单成功但余额不对”，你怎样从这句话定义业务指标，而不是先堆 CPU 和接口成功率？

**面试者：** 我先拆开承诺：系统是否可靠受理了同一个下单意图，是否已经产生可靠提交的完整成交批次，成交是否已完成账务提交，以及余额页面是否追上对应资产版本。它们不是同一个“成功”。B1 被受理但尚未遇到卖单时，挂在订单簿是合法状态；420 已成交而账务尚未提交时，是结算 pending；账务已提交而页面仍旧，才是可见性延迟。因此每个 SLI 都要声明对象、起止事件、成功条件和证据来源，不能要求所有 GTC 都在固定时间成交。对资产是否真实变动，以账本为准；对用户看到什么，以投影版本为准。只有把抱怨定位到具体阶段，才知道该修账务链路还是查询链路，而不是把页面旧数据当成资金丢失。

## 第 2 层：受理、账务和可见性为什么必须是不同 SLO？

**面试官：** 既然你把用户等待拆成了阶段，能给出可计算的目标吗？约束是 HTTP 返回不能再代表账务完成。

**面试者：** 我会先给教学目标而非成绩：可靠受理在服务边界收到合格意图后 300 毫秒内完成，目标 99.9%；从完整成交批次可靠提交到整批账务提交不超过 2 秒，目标 99.9%；从账务提交到对应查询投影可见不超过 1 秒，目标 99.9%，分别按约定的 30 天窗口评估。受理以持久化凭据为证据，账务以同事务批次记录、水位和资产状态为证据，可见性要求投影至少覆盖目标批次或资产版本，不能只查页面是否返回 200。未成交的合法挂单不进入成交结算分母。三个阶段有不同起点和群体，不能把三个 99.9% 直接说成用户端到端 99.9%；需要端到端承诺时，另定义起止点及同一业务群体的统计口径。

## 第 3 层：重试与窗口截尾如何让 SLI 看起来虚假健康？

**面试官：** 你已有三个阶段目标，但同一订单重试十次，跨窗口时仍有一批未完成；分母和失败应怎么记？

**面试者：** 受理分母按调用方范围内的稳定意图 ID 去重，并校验载荷摘要；同 ID 换参数是冲突事件，不是新成功。同一意图的重试不能重置首次合格请求时间，HTTP 尝试指标另算。账务分母按稳定批次身份去重，420 重投十次仍是一个对象，不能按投递次数放大分母。为处理截尾，我按起始事件归属 cohort，并在截止时间到达后定案；尚未到期的对象标记未成熟，不能直接当好事件。到期未完成就计坏事件，即使稍后补交也保留这次违约，同时记录最终完成。窗口边缘因此需要回看期限并声明统计延迟；pending 数量、年龄与超时数持续展示，不能只看已经完成的快速样本。限流、权限错误和参数错误是否属于合格分母须事先约定，禁止故障时临时改口径排除坏事件。

## 第 4 层：为什么水位必须连续，且不能跨市场相减？

**面试官：** 按 cohort 已能判断违约，但还需要知道账务卡在哪里；消费者报告“最大已见序号 422”，可以说进度到 422 吗？

**面试者：** 不可以。我把同一市场完整批次可靠提交的连续前缀记作 HM，账务事务已提交的连续前缀记作 HJ；只有投影也按同一批次坐标维护连续前缀时，才记 HP。若 420 缺失而 421、422 已送达，HJ 仍为 419，最大已见值只能诊断乱序，不能表示已结算。`HM−HJ` 仅在相同 market、相同序列域下表示待账务批次数，批次大小不同，不能等同成交笔数或等待时长；市场 A 的 420 与市场 B 的 900 没有减法意义。年龄要追踪最老未结算批次的权威提交时间或可信等待时长，缺失数据时标明未知。若投影使用独立事件序列，就展示映射关系或版本向量，不能强行相减。无积压且采集新鲜时年龄可为零，空闲水位不动不等于停滞。

## 第 5 层：怎样准确聚合延迟，又不让标签拖垮监控？

**面试官：** 你现在有每市场水位和年龄，还要把多实例延迟汇总；如果给每个订单都打标签，定位会不会更方便？

**面试者：** 不会把订单 ID、账户 ID、trade ID 或 batch_seq 当指标标签，它们会制造无界时间序列，应保留在受控日志和按身份查询的诊断路径里。指标使用阶段、结果、服务、有限市场集合等受控维度；市场很多时，用预先声明的分组与重点市场看板，独立保留精确水位查询，不能任意截掉最差市场。延迟采用相同单位、窗口和桶边界的直方图，先合并桶计数再算分位数，不能平均各实例 p99。教学 SLO 的 300 毫秒、2 秒和 1 秒应有明确阈值桶，方便计算按时完成比例；p99 只是补充描述，不替代好事件计数。直方图通常只观察完成对象，因此必须联看到期坏事件和 pending 年龄，不能用“已完成样本都很快”掩盖卡死的请求。

## 第 6 层：怎样把错误预算转成可操作的多窗口燃烧率？

**面试官：** 阈值桶和坏事件已有了，但瞬时抖动不应每次叫醒人；你会怎样设置错误预算告警？

**面试者：** 仍以教学目标说明：99.9% 对应坏事件比例预算 0.1%，燃烧率＝窗口内坏事件比例÷0.1%，不是坏事件数量直接除以天数。可设计一组快速规则：1 小时与 5 分钟都超过 14.4 倍；另一组慢速规则：6 小时与 30 分钟都超过 6 倍，两组任一成立触发相应处置。对应坏比例分别为 1.44% 和 0.6%，它们不是声称已经验证合适的生产阈值。长窗确认持续预算消耗，短窗确认问题仍在，避免已经恢复后迟到叫人；不同阶段分别计算，不把受理与账务分母混合。低流量时比例不稳定，应联合事件数与具体业务影响，但不能用最小样本门槛把唯一一笔严重卡单屏蔽掉，连续水位停滞和超龄事件仍需要独立规则。

## 第 7 层：监控链路断了，为什么不能把缺失当作零？

**面试官：** 燃烧率突然降为零，但恰好账务服务的指标采集也中断了；怎样避免把观测失明当恢复？

**面试者：** 我会把观测状态区分为健康、违约和未知，分别暴露采集成功时间、目标存活、导出错误、时间偏差与评估器心跳。缺失序列不能自动填零，尤其不能把账务错误计数缺失解释成没有错误，也不能沿用很旧的 HJ 宣布进度正常。另用受权限控制的只读检查核对撮合提交记录、账务事务记录和通知意图，必要时使用隔离账户的受控探针，不能让探针污染真实用户指标。空闲市场要结合 HM 是否前进、是否存在未结算对象判断；没有新交易且水位不动可以健康，有新批次但采集断了则是未知。观察数据补齐后再重算受影响窗口，并保留这段观测缺口，不能把未知区间擦掉后宣称整个窗口达标。

## 第 8 层：99.9% 预算能否允许少量重复入账或资产不平？

**面试官：** 采集故障已经排除，但人工 reconciliation 发现 420 被重复计入，整体成功率仍高于 99.9%，可以用预算接受吗？

**面试者：** 不可以。延迟和可用性的错误预算不授权破坏资金不变量。人工 reconciliation 应按 market＋batch_seq 对齐完整成交批次、两笔 trade、释放动作、账务分录与账户资产，校验相同身份摘要一致、每币种分录平衡、连续水位没有跳缺口。420 只应让甲得到 0.25 BTC、USDT 最终为 4985 且预留清零；乙得到 6000 USDT、BTC 预留清零；丙得到 9015 USDT，剩余 0.05 BTC 保持预留。总成交 15015 与释放 10 必须能分别解释。若出现重复入账，应独立升级资金事件、限制受影响写入、保全证据，按授权更正流程处理，不能为了补齐 SLO 改账或抬水位。人工核对结果也是证据，需要注明查询范围、版本和时间，而不是一句“看起来对上了”。

## 收束：让指标证明承诺，而不是替承诺找借口

- **机制：** 分阶段、分对象、分序列域定义 SLI；按稳定身份去重，以连续前缀和超龄对象解释用户等待。
- **易错边界：** p99 不是 SLO 本身，最大已见不是连续水位，缺失不是零，恢复后完成也不能撤销已经发生的超时违约；资金不变量独立于 99.9% 预算。
- **验证反例：** 手工构造“420 缺失但看到 422”“420 重试十次”“月底仍 pending”“采集断开后错误变零”。口径必须分别暴露缺口、保持分母稳定、记住到期违约、报告未知。
- **数值边界：** 本例整数金额可精确结算；扩展输入仍要验证 lot 与资金单位兼容、整数乘法不溢出。所有目标、燃烧率阈值和观测方法均待实际验证，本篇没有达标结论。
