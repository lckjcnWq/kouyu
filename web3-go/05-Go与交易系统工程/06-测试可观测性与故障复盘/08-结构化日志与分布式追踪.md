# 大问题 8：异步成交和至少一次交付下，怎样用日志与追踪定位资金链路而不把它们当资金真相？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| request_id / intent_id | 前者认一次网络尝试，后者认同一个业务意图。 | 重试可换请求号，但不能把 B1 变成新的独立交易。 |
| order / trade / batch / journal | 分别是订单、成交、完整结果包和记账凭证。 | 一张 B1 产生两笔成交；420 与多条分录之间需保留明确映射。 |
| trace_id / span | trace 关联一次诊断链，span 描述其中某次执行。 | 每次消费尝试可有新 span，trace_id 不做幂等键或授权依据。 |
| trace context / span link | 可传播的诊断字段，以及跨异步执行的关联。 | 消息不保存 Go context 对象，长延迟或多来源可用 link 表达因果。 |
| 服务级有界 context | 由服务托管、有单次期限的执行上下文。 | HTTP 请求结束不终止已提交 420 的交付责任。 |
| outbox / 通知意图 | 与业务事实一起持久保存的发送责任。 | 诊断上下文缺失也必须继续结算，不能依赖 trace 才找得回业务。 |
| 规范载荷摘要 | 检查相同身份下业务内容是否一致的核对值。 | 同 420 不同内容需隔离，较新的 span 不能覆盖原载荷。 |
| slog / schema_version | 结构化日志接口与字段格式版本。 | Go 1.21 可用统一字段、类型和版本，而非自由拼接模糊文本。 |
| event_time / observed_time | 事件发生时间与被采集看到的时间。 | 收集延迟和时钟偏差要保留，数据库 created_at 也不冒充准确提交时刻。 |
| 因果顺序 / 单调持续时间 | 前者解释先后依赖，后者测本进程经过多久。 | 跨机墙钟倒序不改变成交先提交、账务后消费的业务关系。 |
| 采样 / 遥测丢弃 | 为控制诊断成本而只保留部分数据。 | 没有成功日志不证明没入账，普通诊断可以丢而账本不能丢。 |
| 字段白名单 / 脱敏 | 只记录允许字段，并限制身份细节暴露。 | 不记录 token、签名、私钥或完整凭据；替换 ID 仍可能可关联。 |
| 可靠审计 | 对敏感业务与管理动作承担留证责任的记录。 | 不等于 stdout；必要审计不可用时不能静默绕过限制。 |
| 权威身份查询 | 经授权按稳定业务键核查持久事实。 | 即使 trace 全缺，也应能从 B1 找到 420、去重、分录和投影版本。 |

## 把整篇文章压缩成一个故事

客服收到 B1 超时的投诉，只拿到一次 request_id。排查者先经授权映射到稳定 intent_id、订单 B1、批次 420、两笔成交及账务凭证，而不是把网络请求号当成业务身份。420 在异步投递中可能重试，每次用新 span 描述执行，但业务身份与摘要不变；原 HTTP context 已取消，也不删除服务托管的交付责任。

假设 trace 里没有成功提交记录，排查者不能立刻重做资金操作。先查权威库中 420 的去重、分录、余额、预留、水位和通知意图；可能数据库早已提交，只是进程还没写成功日志便退出。跨机日志时间相反时，用批次顺序与事务因果解释，不擅改时间伪造线索。若账户已完成，就应核对甲可用 4,985 USDT、新增 0.25 BTC、预留归零，以及乙丙的收入和丙剩余 0.05 BTC预留，再查页面版本。

故障时诊断队列还可能满，普通日志和追踪可以有界采样，但须暴露丢弃和失明；账本与必要审计不能混入可丢队列。敏感字段采用白名单与权限保护，不为排查方便复制鉴权签名或密钥。真正稳健的诊断路径在完全无 trace 时仍能核实资金，日志只帮定位。本篇字段和排查均为教学设计，没有真实观测样本或已经运行的故障验证。

**流程位置与核心机制：** 沿“请求尝试→业务意图→订单→成交→完整批次→账务分录→异步投影”串联身份；跨异步边界显式传播上下文，重试建立新 span，权威状态仍通过撮合提交记录和账务事务核实。诊断数据允许采样，资金事实不允许靠日志补猜。

**共同前提：** Go 1.21+；BTC/USDT 托管现货，链下单市场单写者、价格时间优先，限价 GTC、零手续费、无杠杆。甲初始 20000 USDT，买 B1：0.25 BTC@60100，预留 15025 USDT、可用 4975 USDT；乙卖 S1：0.10 BTC@60000，丙卖 S2：0.20 BTC@60100，卖单 BTC 已预留。成交为 T420-1＝0.10 BTC/6000 USDT、T420-2＝0.15 BTC/9015 USDT；完整 `ResultBatch(market=BTC-USDT,batch_seq=420,trades=[T420-1,T420-2],release=10USDT)` 可靠提交后至少一次交付。

账务在同一 PostgreSQL 事务共同提交双边分录、余额/预留、批次去重（稳定身份＋载荷摘要）、每市场连续消费水位与通知意图，不跨缺口推进；投影异步。最终甲 4985 USDT＋0.25 BTC、预留 0；乙 6000 USDT、BTC 预留 0；丙 9015 USDT、0.05 BTC 仍预留。价格单位为 1 USDT/BTC，1 lot＝0.01 BTC，资金单位为 1 USDT，总成交 15015 USDT，10 USDT 释放是价差返还而非利润。撮合权威订单成交，账户权威账本资产，查询投影不是资金真相。可靠受理、成交提交、账务提交、可见性分开，客户端超时不能证明失败或触发解冻。链上机制仅可另作显式变体，本篇只讲链下。

**证据范围：** 以下为教学字段设计与手工排查方案，不是实际日志样本、真实链路数据或已经验证的运行结果，不虚构生产经历。

## 第 1 层：为什么一个 request_id 不足以串起交易全程？

**面试官：** 用户重试下单后，客服拿到一个 request_id；你怎样保证查到的是同一笔业务，而不是某次网络尝试？

**面试者：** 我会区分请求尝试与业务身份：每次网络尝试有独立 request_id，同一个合格下单意图使用调用方范围内稳定的 intent_id，并用规范化载荷摘要识别同 ID 不同参数。意图映射到 B1 的 order_id，订单可对应多笔 trade_id；T420-1、T420-2 共同属于 market＋batch_seq＝BTC-USDT＋420，账务再映射到 journal_id 及多条分录。它们不是一对一，必须保留明确关联，不能拿一条 journal 日志代表整批完成。trace_id 只用于可观测性关联，既不做业务幂等键，也不替代授权。跨重试保持意图、订单、成交和批次身份稳定，变化的是请求尝试与执行 span；客服只掌握 request_id 时，应先经受权限控制的映射找到稳定意图，再沿权威身份核查。

## 第 2 层：outbox 异步投递后，trace 上下文应该怎样续接？

**面试官：** 你已区分稳定业务 ID 与请求尝试，但下单响应结束后，420 要经 outbox 和重试进入账务，原来的 context 已取消，怎么办？

**面试者：** 我不会把原请求的 Go context 对象或取消生命周期存进消息。应随可靠发布意图保存允许传播的 trace 上下文字段及稳定业务身份；撮合提交完整结果批次及可恢复发布意图后，投递器使用自身有界超时的 context 处理。上下文存在且可信时，消费 span 可以续接父上下文；长时间延后、多来源合批或跨重试场景可用 span link 表达关联，不必伪装成同步调用。每次投递与消费尝试建立新 span，稳定 batch 身份不变，retry attempt 只作诊断，不能参与业务去重键。HTTP 请求取消后，已可靠提交的批次仍须交付；异步 worker 的本次超时只结束执行尝试，不能让撮合撤销成交或账务释放预留。没有 trace 上下文也必须能够正常结算。

## 第 3 层：为什么不能看到 commit span 成功就认定账务成功？

**面试官：** 你选择每次重试一个新 span；如果某次账务 commit span 显示成功，另一次因采样没留下记录，可以据此决定是否重放吗？

**面试者：** 不能。trace 可能被采样、延迟、丢弃，数据库也可能已提交而进程在写成功 span 前崩溃，反过来“准备提交”的 span 也不证明事务提交。重放决策应查询稳定批次身份对应的账务去重记录和摘要，并核对同事务提交的分录、资产、水位与通知意图。相同身份相同摘要是幂等重投，摘要不同应停下并升级冲突，不能以较新的 trace 覆盖原载荷。两笔 trade 的 span 都存在也不能证明 10 USDT 释放已经执行，更不能把 trace 顺序当作资金顺序。trace 用来缩小耗时与失败窗口，是否已经生效只能由权威存储回答；即使整条 trace 缺失，至少一次交付和幂等协议仍必须保持正确。

## 第 4 层：结构化日志需要哪些时间、版本与水位字段？

**面试官：** 既然 trace 不能当提交证据，结构化日志应补哪些字段，才能让排查者分清事件发生、观察时间和业务进度？

**面试者：** 我会使用 Go 1.21+ 的 slog 等结构化接口，统一字段名与类型：schema_version、service、build_version、instance、event_name、event_time、observed_time，以及 market、batch_seq、intent_id、order_id、trade_id、journal_id、attempt 和可选 trace_id。批次事件带 payload_digest、处理结果及已核实的连续水位，资产投影事件带对应资产版本；字段按事件类型出现，不要求每条日志填满。持续时间用本进程单调时钟测量，跨进程时间戳注明 UTC、精度与时钟误差。大整数 ID 和金额采用无精度损失的约定编码，金额必须带币种和整数单位。数据库行的 created_at 可能早于事务提交，不能命名为准确 commit_time；提交前记录只能叫 commit_attempt，提交确认日志仍不替代数据库证据。

## 第 5 层：日志时间戳相反时，怎样恢复真实因果顺序？

**面试官：** 现在字段齐全，但账务机器的时间比撮合快两秒，收集器又乱序送达；按时间排序出现“先入账后成交”，怎么办？

**面试者：** 我会先保留时钟异常，不通过改时间戳伪造顺序，再用业务因果关系重建链路：单市场权威命令顺序决定订单行为，完整 ResultBatch 的提交先于其可靠交付，账务事务将分录与连续水位共同推进，通知意图随后驱动投影。不同重试 attempt、span parent/link 和载荷摘要可解释重复到达，日志 event_time 与 observed_time 只提供辅助时间范围。market 内的 batch_seq 可以比较批次顺序，却不是不同市场的全局时钟，也不能替代批次内的订单成交关系。如果观察到 421、422 而连续水位仍为 419，先定位缺失的 420，不能按“日志已出现 422”跳进度。跨服务持续时间缺乏可信时钟界限时，应报告区间或未知，而不是输出负延迟后将其截成零。

## 第 6 层：关联信息越充分，怎样防止日志成为资产泄露入口？

**面试官：** 你能靠身份和因果链定位问题了，但有人建议把请求头、完整报文和签名一起打进日志，以免下次缺证据，接受吗？

**面试者：** 不接受。采用字段白名单，禁止记录鉴权签名、token、cookie、密码、私钥、助记词及数据库凭据，也不把这些字段放进异常、trace baggage 或 URL。主线虽是链下托管，也不能假设没有密钥材料泄露风险。账户和用户关联使用受控内部标识，普通排查视图做脱敏，必要的订单与资产明细通过细粒度权限、短期授权和审计访问；脱敏 ID 仍可能可关联，不能宣传为完全匿名。日志传输与存储要加密，保留期限、导出权限和删除策略分级。业务载荷摘要用于规范化内容一致性校验，不是记录敏感凭证的借口，更不是对低熵秘密做简单哈希后就安全。排查证据应尽量在授权查询里取，而非永久复制完整用户数据。

## 第 7 层：诊断队列拥塞时，业务日志与审计记录可以同样丢弃吗？

**面试官：** 字段已脱敏，但故障时日志量暴涨，导出器堵塞；为了不拖垮交易链路，所有日志都改为有界队列、满了丢弃，可以吗？

**面试者：** 普通诊断日志和 trace 可使用隔离的有界队列、限流、采样及批量导出，避免远端日志平台把撮合单写者卡死，但必须统计丢弃量、队列年龄和导出失败，并保留紧凑的关键异常通道。资金账本、分录、批次去重、水位及通知意图不能塞进这种可丢队列，它们仍按 PostgreSQL 同事务规则提交；需要可靠业务审计事件时，通过对应事务内的持久意图与可恢复交付关联，而不是指望 stdout 永不丢。安全管理操作的审计还有独立授权与留存要求，必要审计不可用时按预定策略限制该操作，不能悄悄旁路。诊断降采样不应改变业务结果；可靠审计也不意味着无限缓冲，持久容量不足时要背压或止损，并明确拒绝与未知状态。

## 第 8 层：没有任何 trace 样本，还能怎样查清一次余额投诉？

**面试官：** 假设故障时 trace 已被采样，普通日志又被限流；用户说 B1 超时后余额不对，你还剩怎样的定位路径？

**面试者：** 我先在授权范围内用稳定意图查可靠受理记录及 B1，不能把客户端超时解释成失败。再从撮合权威记录确认 T420-1、T420-2 和完整 420 的摘要，查询账务批次去重、两边分录、预留变化、HJ 与通知意图；若 HJ 停在 419，就定位缺口而非手动抬水位。如果 420 已提交，核对甲 4985 USDT＋0.25 BTC、预留 0，乙 6000 USDT、BTC 预留 0，丙 9015 USDT、剩余 0.05 BTC 仍预留，再查投影消费的批次或资产版本。只在页面滞后时修复可见性链路，不能再次入账或凭页面释放预留。结论附权威身份、查询范围和证据版本；日志缺失单独记录为观测缺口，不编造时间线，也不拿“没有搜到”证明业务未发生。

## 收束：追踪提供线索，权威身份提供可核验事实

- **机制：** 请求 ID 定位尝试，稳定业务 ID 串联事实，span 描述执行；异步上下文显式传递，重试新建 span，幂等身份不随重试变化。
- **易错边界：** trace_id 不是幂等键，日志顺序不是因果顺序，成功日志不是事务证明，脱敏不等于匿名，普通可丢日志不是可靠审计。
- **验证反例：** 手工构造“账务已提交但没有成功日志”“跨机时间倒序”“420 重投产生新 span”“完全无 trace”。仍能依权威身份确认是否生效，才算诊断链路不绑死采样。
- **资金边界：** 15015 USDT 成交与 10 USDT 释放分别核对，金额保持整数并验证结算粒度与溢出，不能用浮点日志反推资产。本篇只给教学路径，没有执行真实观测或故障验证。
