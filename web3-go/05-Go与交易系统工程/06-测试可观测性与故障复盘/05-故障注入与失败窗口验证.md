# 大问题 5：怎样沿持久提交边界注入故障，验证交易恢复不会丢结果、重复记账或错误释放资金？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 故障注入 / 语义窗口 | 在明确业务位置制造受控失败。 | 分别切受理、撮合整批、账务和回执边界，不随机杀进程后猜结论。 |
| 可靠受理证据 | 重启后仍能认出同一订单意图的持久依据。 | 内存队列不算，预留与命令分开提交时还需关联恢复责任。 |
| 完整 ResultBatch | 一次撮合的全部权威结果。 | 420 的两笔成交和 10 USDT 释放依据不能拆成半批承诺。 |
| 未提交试算 | 只在内存算出、尚未成为持久事实的结果。 | 崩溃后从可信状态恢复，不能先把 T420-1 单独给账户生效。 |
| 事务原子性 | 相关变化对外一起存在或一起不存在。 | 分录、余额、预留、去重、水位与通知意图须共同提交。 |
| 提交未知 / COMMIT | COMMIT 发起提交；未知表示暂时不知终局。 | 没收到成功不证明回滚，一次查不到记录也不能排除稍后提交。 |
| 稳定身份 / 载荷摘要 | 分别识别同一业务并核对其内容。 | 原 420 重试不换号；同号改收款人要隔离，不能覆盖。 |
| ACK / 通知意图 | ACK 是交付确认，通知意图是账务同时保存的后续发送责任。 | 结果到账户、通知到投影是两条不同确认链，都可能重投。 |
| 缺口 / 连续水位 | 前序未齐的位置与完整完成的前缀。 | 账户在 419 时先见 421，不能跳过 420 产生资金效果。 |
| 冷启动 / 旧写者围栏 | 清空进程状态后恢复，并阻止旧实例继续承诺写入。 | 不能靠残留内存去重，启动健康也不证明已恢复履约。 |
| 安全与进展 | 前者不做错事，后者在条件具备后继续完成。 | 故障期间守住资金，解除故障并允许重试后才要求有界追平。 |
| EVM 日志观察身份 | 识别在哪条链、哪个具体区块里见到哪条日志。 | 链上变体要含 block hash、交易与日志定位，不能只用高度或裸交易 hash。 |
| 重组 / 最终性 | 规范链可能替换历史，最终性取决于明确的网络策略。 | 普通确认数不是绝对最终性，finalized 异常要隔离核查。 |
| 补偿分录 | 用新的、可审计业务动作处理既有信用影响。 | 充值重组不能删旧账，更不能撤销独立的链下 B1 成交。 |

## 把整篇文章压缩成一个故事

验证者为 BTC/USDT 的 B1 画出一排精确停点：受理提交前后、撮合计算到一半、完整 420 提交前后、账户提交前后、确认发送前后。甲原本预留 15,025 USDT，两笔成交共花 15,015、释放 10。若撮合只算出第一笔就崩溃，账户不该看到半个批次；若整批已提交才崩溃，就必须恢复原两笔成交、原身份和释放依据，不能重启后再造另一套交易。

账户收到 420 后，提交前失败应全部回滚；提交成功但响应被截断则是未知，按原身份核对或重试，不能退款或换号重做。还要分别切断到账户的 ACK 和到账务投影的通知确认，验证重复传输不增加资金效果。先见 421 时保留 420 缺口，摘要冲突隔离，清空进程内缓存重启后仍依持久证据恢复。最终有界核对甲 4,985 USDT、0.25 BTC与零预留，及卖方归属和剩余资产。

正文后段另开 EVM 充值索引变体：同高度区块可能被替换，必须按区块哈希、父链和日志身份重扫；已入账充值需要授权且幂等的补偿，钱已使用还要处理敞口，不能删账或撤销链下成交。所有注入都应先在获授权隔离范围规划并设置止损。这里没有实际执行故障实验，进程崩溃方案也不自动证明断电、磁盘损坏或跨机切换的持久性。

[专题总览](README.md)

- **流程位置：**沿可靠受理、撮合批次提交、账务提交、消息确认与投影追平逐段切断；最后两层显式切换到 EVM 充值索引变体。
- **核心机制：**语义故障屏障、稳定业务身份、未知结果收敛、重复乱序恢复，以及故障解除后的权威验收。
- **前提：**Go 1.21+；BTC/USDT 托管现货；链下单市场单写者订单簿；限价 GTC、价格时间优先、零费、无杠杆。以下为教学设计与验证方案，不是已执行的混沌实验或实测成绩。

**共同教学基线。**甲初始 20000 USDT；乙 S1 卖 0.10 BTC@60000，丙 S2 卖 0.20 BTC@60100，卖单 BTC 已预留。甲 B1 买 0.25 BTC@60100，预留 15025 USDT、初始可用 4975 USDT。T420-1 按 S1 价格成交 0.10 BTC/6000 USDT；T420-2 按 S2 价格成交 0.15 BTC/9015 USDT。整批为 `ResultBatch(market=BTC-USDT,batch_seq=420,order=B1,trades=[T420-1,T420-2],release=10USDT)`，完整持久提交后交付，重试使用同一批次身份与载荷摘要。账务在同一 PostgreSQL 本地事务内提交双边分录、余额与预留、批次去重、该市场连续消费水位和通知意图；同载荷重复不产生新业务影响，冲突隔离，乱序不越缺口。通知投影异步，消息至少一次。最终甲 4985 USDT+0.25 BTC、预留 0；乙 6000 USDT、BTC 预留 0；丙 9015 USDT、0.05 BTC 仍预留。未给出的初始账户资产按增量检查。

价格单位为 1 USDT/BTC，数量为整数 lot、1 lot=0.01 BTC，资金为整数 USDT；`60000×10÷100=6000`、`60100×15÷100=9015`。金额必须整除，其他精度必须声明为变体。撮合域权威订单与成交，账户域权威余额、预留与账本，查询投影非权威。可靠受理≠撮合提交≠账务提交≠投影可见；超时是结果未知，不能释放预留。第 1—8 层始终是链下现货，第 9—10 层才改变外部输入为 EVM 充值索引，绝不把基线成交改为链上结算。

## 第 1 层：为什么先切可靠受理边界，而不是随机杀一个进程？

**面试官：**要验证 B1 故障恢复，你先从哪里注入故障，怎样判断客户端没收到回包时订单究竟有没有丢？

**面试者：**我先定义稳定命令身份、预留关联和“可靠受理”的持久证据，再分别在受理提交前、提交后但回包前停机。前一种应没有已确认意图，若占资已单独提交，必须留下可对账的关联状态，不能凭超时猜测释放；后一种重启后必须找回同一命令，重试也不能形成第二张 B1。内存队列中有消息不算可靠受理。预留与意图若跨事务，就需要明确恢复责任，不能暗称它们天然原子。每次注入记录命令身份、语义位置和预期观察，先在隔离环境验证；生产注入需要授权、限定账户和范围、止损阈值与中止开关，不能把随机制造事故当作验证方法。

## 第 2 层：命令能恢复以后，怎样切撮合批次提交的前后窗口？

**面试官：**B1 已可靠受理，撮合器已经算出第一笔成交就崩溃。恢复时能不能先把 T420-1 交给账户，之后再补第二笔？

**面试者：**不能，交付单位是完整持久提交的 ResultBatch。我会在计算出部分结果、整批提交前、整批提交后但尚未发送三个位置分别停机。提交前崩溃必须丢弃未提交的内存改动，从最后持久状态和命令恢复；不能让账户看到半个 420。提交后崩溃则恢复原批次，保留两个成交、释放 10 USDT、批次号和载荷摘要，不因重启再生成不同成交身份。验证还要证明订单簿恢复状态与已提交批次一致，不是账务拿到两个成交而 S2 又恢复成完整 20 lot 可卖。命令回放必须维持权威顺序，持久日志与快照的切面要一致，单看消息是否最终发出远远不够。

## 第 3 层：批次完整了，账务事务内部失败应留下什么证据？

**面试官：**账户开始处理 420，已经写完 T420-1 的分录，再更新甲余额时失败。你怎样证明没有半批入账？

**面试者：**我会在真实 PostgreSQL 的事务内部设置失败点，例如写入部分分录后触发约束失败，或者在提交前终止连接。等事务确定回滚后，用独立连接读取，应仍是入账前的账户状态，不能留下半笔分录、扣减后的预留、去重标记、水位推进或通知意图。与之配对，在确定提交后停进程，应一次看见双边分录、余额与预留、批次去重、水位和通知意图全部成立。不能先在另一个事务写“已处理”，否则失败重试可能永远跳过实际记账。多个账户更新过程中的中间状态只在本事务内暂存，外部可见的提交切面必须原子；尚在执行的事务不能仅凭暂时没查到记录就判定已经回滚。

## 第 4 层：提交结果未知时，怎样证明重试不会把已成功变成双扣？

**面试官：**你能验证提交前后，但最难的是 COMMIT 已发出、数据库响应没有回来。此时怎么设计注入和恢复断言？

**面试者：**我会区分提交请求发出前断开、数据库已持久提交但成功响应被截断，以及暂时无法判断终局三种情况。仅在仓储接口返回一个人为错误，不足以验证驱动和数据库的未知提交语义；要控制真实连接或响应交付点，并用数据库权威证据判定。未知期间保留原批次身份和完整载荷摘要，不退款、不新建批次，通过查询和同身份重试收敛。如果原事务仍活着，重试需在锁与唯一约束下与它串行化；一次查不到去重行不能作为重做资金操作的许可。同摘要已处理返回原结果，异摘要隔离，最终只允许出现一次 15015 USDT 支出和一次 10 USDT 释放。

## 第 5 层：账务成功但 ACK 丢失，为什么还要分别验证两条消息链？

**面试官：**账户确认已提交，消息代理却没收到 ACK，于是又投递 420。通知发送成功却没记发送进度时，又会发生什么？

**面试者：**第一条是撮合结果到账户：只有账务事务提交后才能确认消息，ACK 丢失导致重复交付时，账户以批次身份和摘要去重，不能重复扣款或释放。第二条是账务通知意图到投影：通知意图已经与账务一起提交，发送后进度更新失败也会重发，投影必须按事件身份或业务版本幂等应用，不能把余额增量再加一遍。我会分别在两条链的“接收方已成功、发送方未确认”位置切断，验证业务影响一次而传输可多次。不能靠先确认消息来避免重复，那会制造提交前崩溃时的丢失窗口；也不能把代理确认、账务确认和投影可见混成同一个成功标志。

## 第 6 层：重复能承受以后，乱序、缺口和载荷冲突怎么验？

**面试官：**现在人为让 421 先到，再把 420 重复十次，最后混入一个同批次号却改了收款人的载荷，系统该怎么走？

**面试者：**我先把账户该市场连续水位固定在 419。421 可以进入缓冲或触发补扫，但不能先产生业务影响或把水位推进到 421；420 到达并完整提交后，才允许继续处理 421。这里 421 是显式扩展批次夹具，只核验其声明的增量，不能把它混入基线的最终余额。同摘要的 420 重复任意次，都不增加分录或改变余额；改收款人会改变规范摘要，应隔离并告警，不能覆盖已入账记录，也不能作为正常新批次绕过去重。再注入截断、缺必填字段和摘要不符的消息，要求拒绝或隔离，余额与水位均不推进。若冲突在缺口处，安全性优先于自动追平，必须保留证据等待处理。再检查缺口补齐后水位连续前进，而不是只看最终水位数值碰巧到达。

## 第 7 层：处理进程重启时，怎样避免内存状态让测试看起来恢复成功？

**面试官：**乱序测试通过了，但去重表、待补批次和重试任务可能还留在进程里。你怎样验证真正的冷启动恢复？

**面试者：**我会终止整个处理进程并清空进程内缓存，只允许从持久命令、撮合日志与快照、账户事务记录和通知意图恢复。重启后先取得单市场写者资格并排除旧写者继续提交，再从匹配的日志位置恢复订单簿，补送所有未确认批次。账户从已提交连续水位恢复，不能相信尚未提交的内存游标；通知发送者也从持久意图恢复，而不是重建一串无法对应的事件。测试应覆盖旧连接与未决事务被清理后的重投，并证明不能出现两个有效写者。重启完成不等于业务恢复完成，还要证明队列有进展、缺口能补齐、重复可收敛，不能只用健康检查返回成功作结论。

## 第 8 层：故障已经解除，最后怎样验收，而不是“服务起来了就算好”？

**面试官：**前面每个窗口都试过，依赖也恢复了，你会拿出什么最终证据？故障注入能不能证明所有时序安全？

**面试者：**我会停止故障、恢复依赖、保证重试有机会执行，并设置有界等待。用稳定身份串起 B1、420 和两个成交，核对权威订单簿、逐账户资金、每币种分录、预留归属、去重行、连续水位与通知意图；最终必须回到基线的甲 4985 USDT+0.25 BTC、乙 6000 USDT、丙 9015 USDT 且仍预留 0.05 BTC。再让投影追到相应版本，检查没有遗漏或重复增量，并观察恢复期间没有负余额、越缺口或冲突被覆盖。注入只证明被覆盖的窗口与交错，不穷尽所有时序，更不能用网络断开代替存储持久性验证。若超时未收敛，报告最后权威边界和阻塞原因，不通过放宽断言伪装成功。

## 第 9 层：显式切换到 EVM 充值索引，为什么只有区块高度和交易哈希还不够？

**面试官：**把外部输入改成 EVM ERC-20 充值日志，RPC 断连后补扫，又遇到同高度区块被替换，你会怎样扩展刚才的恢复验证？

**面试者：**这里已切换为独立的 EVM 充值索引变体，资产、链 ID、合约与原子单位另行声明，不使用 BTC 现货的 lot 精度，也不改变 420 的链下成交。我会保存高度与区块 hash、父 hash，用规范链锚点校验连续性，不能把相同高度当作同一区块。日志观察身份包含链、区块 hash、交易 hash 和日志序号，重复扫描幂等，同一交易被重新打包则按业务充值身份做关联，不能形成两份有效入账。注入断连、重叠补扫、同高度替换与父链不连贯，验证游标回退到共同祖先并重建受影响索引。仅有交易 hash 既不能区分一笔交易里的多条日志，也不能证明观察来自当前规范链。

## 第 10 层：重组穿过充值确认边界时，怎样验证最终性判断与下游补偿？

**面试官：**变体中某笔充值已经标为可入账，后来发现它所在区块变成孤块，甚至入账资金已被使用，你会怎样验收？

**面试者：**我会先声明该 EVM 网络的确认策略：若采用明确支持的 finalized 检查点，就验证它覆盖的规范祖先；若只取若干确认，则只能称风险阈值，不能冒称绝对最终性。测试分别制造阈值前重组与确认后异常：前者撤销待确认观察、不产生可用余额；后者停止新增信用、标记受影响充值，按账户规则追加可审计且幂等的补偿分录，并同步下游状态，不能删账掩盖历史。若资金已消费导致无法安全扣回，要进入受限与差额追偿流程，不能强行制造负可用。最终化块被替换应作为严重异常隔离核查。所有这些动作只修复充值及其下游影响，绝不能回滚 B1 的链下成交；生产演练仍须授权、隔离和明确止损。

## 讲透的机制

- **故障点按承诺定位：**受理提交前后、撮合整批提交前后、账务事务提交前后，以及各条消息链确认前后，预期状态各不相同。
- **恢复依赖稳定身份：**命令、批次、成交、通知各有可关联身份；同批次同载荷可重试，冲突不能悄悄覆盖，连续水位不能跨缺口。
- **验收兼顾安全与进展：**故障期间不发生非法资金变化，故障解除且具备恢复条件后才要求追平；可启动、可查询、可恢复完成是不同证据。
- **EVM 变体另设权威边界：**区块身份与规范链、确认或最终性策略、充值信用与补偿分别验证，不把链下订单簿改造成链上结算。

## 最容易答错的边界

- “提交前”指数据库尚未提交，不是应用还没收到成功；应用未收到响应时，数据库可能早已提交。
- 重试不是更换批次号重做业务；先写去重后单独记账、先 ACK 后提交都会制造丢账窗口。
- 全部消息到齐后最终余额正确，仍不能掩盖中途越缺口、重复扣款后再纠正等违反安全属性的行为。
- 进程崩溃实验只覆盖该进程窗口，不能自动证明主机断电、磁盘损坏或主备切换后的持久性承诺。
- EVM 日志重复身份与充值业务身份不能只用一个裸交易 hash 替代；交易重上链时须按已声明规则关联，避免双重信用。
- finalized 的含义取决于所接网络与数据源；普通确认数、某些二层网络状态与 L1 最终性不能混称同一个保证。
- 补偿是新的、可追踪且幂等的业务动作，不是删除历史，也不是撤销不相关的链下现货成交。

## 检验反例

1. **半批提前生效：**完整批次尚未持久提交，就把 T420-1 当作确定结果发布；或者账户收到半批便入账并推进水位。即使后来补齐，也已经违反提交和原子边界。若完整批次已提交，传输层仅分片送达、账户收齐并校验后才整批入账，则不属于此反例。
2. **未知结果误退款：**账户已提交但响应丢失，调用方把甲预留全部释放；重试后发生双重使用，验证必须拒绝。
3. **确认链混淆：**代理已 ACK，但账务未提交，进程随即崩溃；没有可恢复批次就会永久丢账，不能算至少一次交付成功。
4. **水位假进展：**421 先记账并推进水位，随后将 420 标记“旧消息”丢弃；健康指标可能正常，连续消费与逐批证据必须失败。
5. **假最终性：**充值只达到确认数就称不可重组，孤块出现后直接删除入账历史；这既没有验证最终性，也没有实现可审计补偿。
6. **错域回滚：**EVM 充值重组后撤销 T420-1、T420-2，属于混淆独立业务域；正确方案只能处理受影响充值信用及显式下游补偿，不篡改基线成交事实。
