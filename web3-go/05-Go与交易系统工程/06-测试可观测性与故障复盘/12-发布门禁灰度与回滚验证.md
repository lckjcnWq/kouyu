# 大问题 12：怎样发布交易系统新版本，在灰度、消费者升级和回滚中守住已提交成交与账务事实？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 发布门禁 | 没有满足必要条件就不允许推进上线。 | 检查权威写者、资金不变量和失败窗口，不能只看接口成功率。 |
| 构建摘要 / 规则版本 | 标识执行程序与所用业务规则。 | 回放比较必须固定产物、配置、工具链、事件和数据库格式。 |
| 确定性回放 | 相同初态、权威命令和规则产生可解释的相同业务结果。 | 纯性能改造不应改变 420 两笔成交和 10 USDT 释放。 |
| 生效屏障 | 新版本或新规则正式接手的确定位置。 | 历史批次仍按原语义解释，不能用新规则重算旧承诺。 |
| 权威灰度 / 市场所有权 | 让有限范围由新版本负责，但每份状态仍只有合法写者。 | 单市场不能按请求随机分给两套簿，本例需整体切换并限速观察。 |
| epoch / 持久化围栏 | 代际身份与实际写入处对失权者的拒绝。 | 换路由不够，旧主不能继续提交结果。 |
| 影子流量 | 复制真实输入到没有真实业务执行权的环境。 | 只写模拟状态，凭据与网络权限禁止真实记账和通知。 |
| schema / 语义兼容 | 数据结构版本，以及字段含义是否被正确理解。 | 能忽略新字段不代表理解新的资金处理规则。 |
| expand-contract | 先扩展兼容能力，待旧版退出和观察完成后再收缩。 | 先表结构与消费者、后生产新事件，不能当天删旧字段。 |
| 消费者交接 | 旧处理者停止新增并核清在途，新处理者接续原进度。 | 保留去重和摘要，不能重置水位或换身份躲开兼容问题。 |
| 程序回滚 / 业务历史 | 切回兼容执行程序，与已经生效的业务事实是两件事。 | 不能因新版故障把数据库从 420 恢复到 419。 |
| 前向修复 / 授权补正 | 修好兼容程序继续处理，或另记凭证修正真实错账。 | 旧版看不懂新数据时先安全暂停，不能强拉旧版覆盖事实。 |
| 灰度样本 / 对照口径 | 判断风险所需的有效业务覆盖和相同测量条件。 | 少量零错误、低负载快延迟不能证明可以全量。 |
| 有限自动化权限 | 事前授权自动暂停、限流或兼容回退的范围。 | 不包含删成交、清去重、退水位或改余额。 |

## 把整篇文章压缩成一个故事

团队准备给 BTC-USDT 换一个更快的撮合版本。先固定构建、规则、初始快照和权威输入，在隔离环境核对 B1 仍形成 6,000 与 9,015 USDT 两笔成交、释放 10 USDT。影子实例可以比较结果，却不能拥有真实记账或推送权限；加个影子日志标签不构成隔离。由于基线只有一个市场，不能把百分之一请求分给新簿、其余给旧簿同时裁决。

正式切换要有所有权屏障、连续历史和写端 epoch 围栏，限制新增观察。若事件增加字段，先扩展数据库、部署理解旧新语义的消费者，再允许生产新格式，保留旧字段直到回滚观察期结束。消费者交接仍沿原批次和去重进度，不能重置水位。灰度少量请求没有错误也不够，还需覆盖重复、撤单竞争和积压恢复，并按相同负载与窗口比较性能。

假设新版已经把 420 入账后报警，团队只能在旧版兼容现有数据时回退程序；不能恢复到 419 抹掉甲已花的 15,015 USDT和收到的 0.25 BTC。旧版不兼容则安全暂停并前向修复，真实错账另走授权补正。自动化可停止放量，却没有删账权限。本文是发布验证设计，没有执行灰度、影子运行或兼容回滚测试，也没有性能提升成绩。

[返回专题总览](README.md)

**流程位置：** 构建与规则固化 → 发布门禁 → 权威写者切换 → 隔离观察 → 消费者与数据兼容 → 继续放量或停止发布；本题围绕“同一笔 420 在跨版本发布中不能丢、不能重、不能改”连续追问。

**核心机制：** 发布切换的是执行版本，不是业务历史；灰度必须保持权威所有权，回滚必须满足新数据可读与语义兼容，自动处置不能删除已经提交的事实。

**公共短前提：**

- Go 1.21+；BTC/USDT 托管现货，市场标识为 `BTC-USDT`；链下单市场单写者、价格时间优先、限价 GTC、零费、无杠杆。撮合拥有权威订单与成交，账户域拥有余额、预留和账本，异步查询投影不是真相。
- 价格步长为 1 USDT/BTC，数量 `1 lot = 0.01 BTC`，资金最小单位为 1 USDT；这是本例的整数教学网格，不代表生产精度，也不允许浮点计算或静默截断。
- 甲初始 20000 USDT，买单 B1 为 `0.25 BTC @ 60100`，预留 15025 USDT、可用 4975 USDT；乙 S1 为 `0.10 BTC @ 60000`，丙 S2 为 `0.20 BTC @ 60100`，两卖单 BTC 已预留。
- 成交 `T420-1 = 0.10 BTC / 6000 USDT`、`T420-2 = 0.15 BTC / 9015 USDT`；`ResultBatch(market=BTC-USDT, batch_seq=420, trades=[T420-1,T420-2], release=10 USDT)` 完整可靠提交后，再至少一次交付。
- 账户域在同一 PostgreSQL 事务内原子提交双边分录、余额与预留、稳定批次身份去重及 payload 摘要、每市场连续消费水位和通知意图；乱序不能跨缺口。可靠受理、成交提交、账务提交、查询可见是不同阶段；客户端超时不能认定失败或释放，既成成交不能靠改状态、改余额抹去。
- 本例完成入账后，甲为 4985 USDT + 0.25 BTC，预留为 0；乙收到 6000 USDT，预留 BTC 为 0；丙收到 9015 USDT，仍预留 0.05 BTC。链上重组、预言机、提现均不属于上述主线，涉及时另行显式改变前提。

> 以下是教学面试设计，不是用户项目经历；发布门禁、故障验证与灰度指标属于设计要求，不包含实测成绩或已执行验证结论。

## 第 1 层：发布门禁先写不变量与故障窗口，而不是只看接口成功率

**面试官：** 团队要发布撮合与账务的新版本，正常下单接口都能返回成功。你还会给发布加什么门禁？

**面试者：** 我先把承诺写成可核验的不变量：单市场权威写者唯一、价格时间优先、数量和每币种资金守恒、预留不提前释放、稳定批次最多一次产生账务效果、连续水位不跨缺口。再列出会破坏承诺的故障窗口，例如结果提交前后崩溃、交付重复乱序、账户 COMMIT 回包丢失、通知尚未发送以及切主时旧实例复活。门禁要求这些窗口都有明确预期和核对证据，不能拿接口成功率代替。本例必须解释 420 如何可靠交付、甲的 10 USDT 如何仅释放一次，以及丙的 0.05 BTC 为何继续预留。这里提出的是发布前应执行的验证方案，不因写出了方案就宣称验证完成。

## 第 2 层：固化构建、规则和 schema，确定性回放才有可比基准

**面试官：** 不变量已经列清，但新旧版本回放同一组请求，偶尔产生不同结果。你怎样让这个门禁能够定位差异，而不是简单重跑到一致？

**面试者：** 我固定构建产物摘要、源码版本、Go 工具链与依赖、撮合规则版本、配置及事件和数据库 schema 版本，同时固定初始快照与权威命令序列。价格时间优先依赖权威序列，不依赖回放机器的墙钟时间或 goroutine 调度；整数网格与释放规则也必须一致。回放在隔离环境比较订单终态、成交身份与顺序、批次内容及账户预留变化，排除传输时间等非业务字段后按固定规则核对摘要。若本次只是性能改造，本例两笔成交和 10 USDT 释放就不应改变；若确实改变业务规则，要定义生效位置及历史规则保留，不能让旧批次被新规则重新解释。无法解释的非确定性差异应阻断发布，而不是挑一轮好结果。

## 第 3 层：灰度切换权威所有权，不按请求随机分流同一市场

**面试官：** 隔离回放已经能解释差异。线上先给新版本百分之一流量，旧版保留其余流量，这样能安全灰度撮合吗？

**面试者：** 对同一市场不能这么做，两套订单簿同时写会破坏价格时间优先和成交唯一性。撮合灰度按市场所有权切换：先固定切换屏障，保存可恢复状态并核清已提交结果，再在持久化提交点围栏旧 epoch，授权新版本接管同一连续历史。本题只有 BTC-USDT 一个市场，不能凭空声称已有独立市场可灰度；可以先做隔离演练，再以整个市场切换、限制新增速率和敞口观察。账户服务若按账户或分区灰度，也要保持确定路由和权威状态，不能把同一批次双边分录拆给不兼容版本各自提交；共享余额仍由数据库事务和锁保护。灰度比例不是打破单写者与账务原子边界的理由。

## 第 4 层：影子流量只能产生隔离结果，不能进入真实资金链路

**面试官：** 整个市场切换仍然担心风险。那在切换前，把真实命令复制给新版本，和旧版同时撮合，再对比成交，行不行？

**面试者：** 可以做影子比较，但新版本必须是没有真实执行权的隔离计算者。它使用相同起始快照和权威排序输入，只写模拟订单簿、模拟结果或独立的模拟账户环境，凭据与网络权限禁止它进入真实结果交付、账户记账和通知链路。不能只是加一个“影子”日志标签，却继续发布真实 ResultBatch；真实账户即使批次去重，也不该承担吸收影子错误的风险。比较时要对齐输入序列、水位和规则版本，核对成交归属、剩余量与释放金额，而不是比两边谁先输出。影子结果也不能在主链路故障时自动顶成权威历史；真正接管仍要经过所有权屏障、旧主围栏和状态恢复验证。

## 第 5 层：消费者升级要兼容事件语义，并采用 expand-contract 迁移

**面试官：** 影子环境里结果一致，准备切换了，但新撮合需要新增结果字段，旧账户消费者和旧数据库表还在运行。你按什么顺序升级？

**面试者：** 先明确新增字段是否只是可选信息，还是会改变资金处理语义；旧消费者能忽略未知字段，不代表它能安全处理新业务含义。我先扩展数据库 schema，使新旧程序都能读取和写入，再上线能读旧新事件的消费者，确认幂等身份、摘要规范和连续水位语义保持稳定，随后才允许生产新事件。消费者交接要停止旧所有者继续取新工作，核清在途事务并围栏，保留原进度与原批次去重证据。若迁移确需双写兼容字段，应在同一事务内一致完成，并核验回填范围。只有旧版本退出且回滚观察期结束后，才收缩字段或约束；不能发布当天就删旧列，也不能通过重置水位、换批次身份躲开兼容问题。

## 第 6 层：回滚程序不能回滚事实，旧版不兼容就暂停或前向修复

**面试官：** 新版已经提交并入账 420，随后发现故障。直接把程序镜像退回旧版，再把数据库恢复到 419，能不能最快止损？

**面试者：** 不能，那会抹去已经承诺的成交与资金变化。回滚前先限制新增风险，确认 420 到底停在成交提交、账户提交还是查询阶段，再核验旧版能否读取并正确解释新版 schema、事件、快照及规则版本。满足兼容条件时，只切换执行程序并保留现有账本、水位、去重记录和通知意图，原批重送仍只能得到既有结果，不能重新扣款。若旧版不理解新数据或状态，禁止强行回滚，应保持安全暂停，前向修复或使用经核验的兼容版本接管。已经真实入账的业务错误另走授权补正并关联原凭证，不靠恢复旧备份抹除；恢复旧备份即使页面看似回到正常，也不是安全的程序回滚。

## 第 7 层：灰度结论需要足够样本，以及相同负载和时间窗口

**面试官：** 你决定保留兼容回滚能力继续观察。灰度只来了少量请求，错误率为零，延迟看着也更低，能不能马上全量？

**面试者：** 不能把样本少当成风险低。先写清观察窗口、最低有效业务样本与场景覆盖，尤其要看到跨批次、重复交付、撤单竞争和积压追平等关键路径；样本不够就延长观察或维持受限流量，不能自动判绿。性能比较还要对齐到达率、订单簿深度、成交密度、账户热点、积压初值与资源条件，使用相同时间窗口和统计口径，避免拿低负载灰度对比高峰旧版。正确性指标如摘要冲突、重复入账、越水位和守恒差异要单独设阻断条件，不能用平均延迟改善抵消。CPU、错误率和分位延迟也都要带样本量与采样新鲜度；本题没有实测数据，因此只能提出门禁，不能给出提升成绩。

## 第 8 层：权限审批与自动暂停形成闭环，不能自动删数据

**面试官：** 门禁和观察口径都明确了，但凌晨灰度告警触发时负责人不在线。自动化能做什么，事后怎样避免下次发布再犯？

**面试者：** 事先授权的自动化可以停止继续放量、收紧新增准入、保留安全撤单，并在兼容条件已经验证时执行有限的程序回退；它没有删除成交、清空去重表、回退账务水位或改余额的权限。发布、数据库迁移、业务补正和紧急处置应分开授权，敏感动作按既定审批执行并记录操作者、产物、策略版本、生效屏障和证据。告警后先固定事故切面，辨别是权威错误还是投影延迟，再决定继续暂停或人工接管。复盘要把实际失败窗口变成可重复的发布回归场景，例如 420 提交回包丢失后跨版本重送仍只入账一次，并指定责任人、验收条件和再次放量的审批入口。回归项被记录不等于已经执行，更不能代替恢复证据。

---

**讲透的机制：** 不变量门禁 → 版本固化与确定性回放 → 权威灰度 → 影子隔离 → 兼容迁移 → 有条件回滚 → 有证据放量 → 故障回归。

**最容易答错的边界：** 请求百分比不能拆出同市场多个权威写者；能解析新字段不等于语义兼容；程序回滚不能撤销已提交成交与账务，自动暂停也不包含自动删账。

**检验反例：** 新版提交 420 并写入旧版无法解释的状态后告警。如果方案把旧版直接拉起、将数据库退回 419，或者让影子实例接管真实资金写入，就没有具备可用的回滚边界。
