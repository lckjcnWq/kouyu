## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 质量闭环 | 先定规则，再验证、发现、处理，最后防止同类问题重来。 | 本专题把测试、监控、止损、恢复和发布门禁串起来，而不只讨论接口测试。 |
| 权威状态 | 有资格决定业务事实的记录。 | 撮合决定成交，账户决定资金；页面和监控不能反向改账。 |
| 可靠受理 | 系统已经留下可恢复的订单意图与处理依据。 | 接下 B1 不等于已经成交，更不等于资产已经到账。 |
| lot / 教学网格 | 把数量和金额切成明确的整数单位。 | 1 lot 为 0.01 BTC，价格乘 lot 后除以 100；本例金额均整除。 |
| ResultBatch | 一次撮合产生的完整结果包。 | 420 包含两笔成交及释放依据，不能拿半包宣告完成。 |
| 本地事务 | 在同一数据库中把一组修改一起提交或一起撤销。 | 本例 PostgreSQL 共同提交分录、余额、预留、去重、水位和通知意图。 |
| 业务不变量 | 无论怎样重试或故障，都不能破坏的规则。 | 数量守恒、每币种平衡之外，还要核对收款人和预留归属。 |
| 独立判据 | 不直接照搬被测实现的验算依据。 | 用简单模型和人工可审计数字，避免实现和测试一起算错。 |
| 属性测试 / 反例 | 生成多种历史检查通用规则，并保存违反规则的具体过程。 | 不是随机下很多单不报错就算正确，还要能缩小并复现错误。 |
| 故障窗口 | 在业务承诺前后精确切断的位置。 | 提交前故障、提交后丢回执和提交未知需要不同断言。 |
| 连续水位 | 前面每一项都完整完成的位置。 | 看到 422 而缺 420，不能把账户进度从 419 抬到 422。 |
| SLI / SLO | 前者是承诺的度量方法，后者是事先约定的服务目标。 | 分别衡量受理、入账和可见性；资金错误不受可用性预算豁免。 |
| 可观测性 / 遥测 | 用指标、日志和追踪理解系统发生了什么。 | 诊断数据可延迟或采样，不代替持久交易事实。 |
| 同水位对账 | 在对应的完整截止点核对不同域的事实。 | 不能拿撮合 420 的结果直接比较尚停在 419 的账户当前值。 |
| 止损 / 恢复验收 | 先限制风险扩散，再用证据确认已有义务恢复。 | 不删除已成交结果、不凭超时释放资金，也不凭进程活着就放量。 |
| 发布门禁 / 复盘 | 前者限制不合格变更上线，后者把事故转成可验收改进。 | 故障反例应进入回归和门禁，而不是只留一份总结。 |

## 把整篇文章压缩成一个故事

甲带着 20,000 USDT 下单买 0.25 BTC，限价 60,100 USDT/BTC，先预留 15,025 USDT。撮合按价格时间优先吃掉乙的 0.10 BTC 和丙的 0.15 BTC，把两笔成交以及释放依据一起提交为批次 420。实际支出 15,015 USDT，剩余 10 是没花掉的预留，不是利润；丙未成交的 0.05 BTC 仍为卖单预留。质量负责人要证明的，是每个阶段都守住这些事实，而不是只证明下单接口返回成功。

假设撮合已经提交 420，账户水位却停在 419。团队先用分阶段指标和最老待入账年龄发现积压，再按订单、批次和分录身份查证：尚未入账就恢复整批处理，若已经入账但回执丢失，就用原身份重投并返回原结果。测试方案应分别覆盖纯规则、真实数据库事务、并发交错和这些失败窗口，不能用 mock 成功代替数据库证据。止损时可以限制新增风险，但不能删成交或把甲的预留全退掉。

恢复后，在一致截止点核对甲可用 4,985 USDT、新增 0.25 BTC、预留为零，乙新增 6,000 USDT，丙新增 9,015 USDT且仍预留 0.05 BTC，再检查投影追平。将这次窗口保存成最小回归案例、告警及发布门禁，才形成闭环。日志没有错误不代表资金正确，文档里的方案和手工推演也不代表已经运行测试；本专题没有压测成绩、故障演练结果或生产达标结论。

## 一、文字全流程：从一笔交易到故障闭环

### 1.1 讨论基线与贯穿案例

采用已有[撮合交易从 0 到 1](../../01-撮合交易与核心链路/01-撮合交易从0到1/README.md)的托管现货案例：

- **产品与执行**：BTC/USDT 现货，链下托管账户、单市场单写者订单簿、价格时间优先、限价 GTC，零手续费、无杠杆。
- **状态归属**：撮合域拥有订单、命令顺序和成交事实；账户域拥有可用余额、预留、分录和入账事实；查询与推送是派生投影。
- **可靠边界**：命令可靠受理、完整撮合结果提交、账户事务提交、投影可见分别确认。成交结果至少一次交付，不能拿 HTTP 成功或消息 ACK 代替账务完成。
- **账务实现前提**：本例涉及的账户在同一个 PostgreSQL 数据库；双边分录、余额与预留、批次去重、该市场连续消费水位和通知意图在同一本地事务中提交。不声称跨库全局事务已经解决。
- **技术前提**：Go 1.21+。只讨论验证接口与机制，不创建完整 Go 工程。

甲有 20,000 USDT。乙的卖单 S1 为 `0.10 BTC @ 60,000 USDT/BTC`，丙的卖单 S2 为 `0.20 BTC @ 60,100 USDT/BTC`，卖方 BTC 已按订单预留。甲提交 B1：`买入 0.25 BTC，限价 60,100 USDT/BTC`。

为避免本专题被精度问题分散，使用明确的教学网格：价格单位为 `1 USDT/BTC`，数量 `1 lot = 0.01 BTC`，资金单位为 `1 USDT`。数量存整数 lot，金额计算为 `价格整数 × lot / 100`，本例均整除；真实系统采用更细精度时必须重新定义换算、溢出检查和舍入规则，不能直接照搬这个网格。

| 环节 | 权威变化与案例数值 | 完成含义 |
|---|---|---|
| 资金预留 | 甲预留 `60,100 × 25 / 100 = 15,025 USDT`，可用变为 4,975 USDT | 取得明确订单意图对应的资产约束；不等于已成交 |
| 可靠受理 | 命令身份、载荷和可恢复位置确定 | 超时后可以查询、重试原意图；不承诺最终全成 |
| 撮合提交 | T420-1：10 lot、6,000 USDT；T420-2：15 lot、9,015 USDT；B1 全成，S1 全成，S2 剩余 5 lot | 完整 `ResultBatch(BTC-USDT, 420)` 成为不可随意删除的成交义务 |
| 账户提交 | 支付 15,015 USDT，释放价差预留 10 USDT；双边分录和去重等一起提交 | 甲可用 4,985 USDT、0.25 BTC、预留为零；乙可用 6,000 USDT；丙可用 9,015 USDT，仍预留 0.05 BTC |
| 投影交付 | 更新私有订单、成交及资产查询 | 页面展示跟上账户和成交事实，不反向裁决资金 |
| 恢复验收 | 核对对应市场水位、订单数量、分录归属、预留及投影进度 | 不只是服务进程存活或告警消失 |

价差释放的 10 USDT 是原预留中未花掉的资金，不是交易收益。本例不含充提和链上结算；链上充值重组、预言机失效等只在问答中作为**显式改变前提的分支**讨论。

### 1.2 一笔业务的完整主链路

```text
用户提交 B1〔请求身份、订单意图、价格、数量〕
    ↓
接入鉴权与参数检查
    ├─ 拒绝 → 明确原因；不产生交易资格，不新增预留
    ↓
账户域以订单意图预留 15,025 USDT
    ↓
命令可靠受理并进入该市场的权威顺序
    ↓
撮合域依次消耗 S1 的 10 lot、S2 的 15 lot
    ↓
完整 ResultBatch〔market=BTC-USDT，batch_seq=420〕提交
    ├─ 包含两笔成交、订单变化、10 USDT 价差释放依据
    └─ 未提交的计算结果不得被当作确定成交发布
    ↓
可靠交付〔可能重复、超时、ACK 丢失；按身份恢复〕
    ↓
账户域检查身份、载荷和连续水位
    ├─ 同身份同载荷 → 返回原结果，不重复改变资金
    ├─ 同身份异载荷 → 隔离冲突，不当普通重试
    └─ 前序批次缺失 → 保留缺口，不跳水位
    ↓
账户本地事务
    ├─ 双边分录、余额与预留共同变化
    ├─ 去重记录和连续消费水位共同变化
    └─ 通知意图共同提交
    ↓
查询与私有回报异步追平
    ↓
用户能够核对成交、可用资产与剩余预留
```

不要求等账务完成才对外展示“成交已确定”，但回报必须注明依据和阶段，不能把“已成交”包装成“资产已到账可提现”。B1 的账户完成状态也不意味着 S2 的剩余 0.05 BTC 应被释放。

### 1.3 正常链路旁的质量与运维闭环

```text
定义承诺、权威状态和业务不变量
    ↓
可测试设计〔隔离时钟、依赖与副作用；固定规则版本〕
    ↓
分层验证〔规则单测 → 属性/并发 → 存储契约 → 端到端〕
    ↓
故障窗口验证、容量与恢复验证
    ↓
发布门禁与受控灰度〔兼容性、权威写入范围、回退条件〕
    ↓
业务运行
    ├─ Metrics：结果、耗时、在途年龄、连续进度、数据新鲜度
    ├─ Logs / Traces：以业务身份定位证据和因果链
    └─ 独立核对：对齐截止点验证订单、成交、账务与预留
    ↓
业务症状或不变量异常触发告警
    ↓
值班人员确认影响 → 按权限限制新增风险并保留必要证据
    ↓
确定权威事实与故障窗口 → 修复并恢复原义务
    ↓
同水位对账、权限/围栏检查、分步放量、观察稳定性
    ↓
复盘形成回归案例、告警/预案修改和可验收行动项
    └─ 回到发布门禁，而不是只写一份事故总结
```

### 1.4 关键异常分支

```text
预留成功，受理调用超时
    → 状态未知，查询/恢复同一订单意图
    → 不能凭超时释放；需要确定交易资格已关闭且已有成交处理完毕

撮合批次 420 已提交，账户水位停在 419
    → 合法但必须受期限约束的在途义务
    → 限制继续堆积新增风险；恢复完整批次，不删除成交

账户事务已提交，ACK 丢失
    → 同批次重投，命中持久去重与原结果
    → 资金效果不再发生；ACK/日志次数不等于成交笔数

部分成交后撤单
    → 撤单与后续成交按同一权威顺序裁决
    → 只释放确定的未成交剩余量，不能按客户端看到的旧数量释放

账户已入账，投影仍旧
    → 可见性故障，不等于重新撮合或重新入账
    → 修复投影缺口；是否可以交易取决于权威数据是否可信

监控采集停止
    → 数据未知而非错误数为零
    → 检查采集新鲜度，用独立查询和核对证据确认业务状态
```

## 二、核心板块：分别决定什么

| 核心板块 | 为什么核心 | 拥有的状态或证据 | 上下游契约 |
|---|---|---|---|
| 可测试设计与测试判据 | 没有独立判据，测试可能稳定复现同一个错误 | 规则版本、输入序列、参考模型、预期不变量 | 以明确前提驱动业务接口，不让 mock 替代数据库保证 |
| 属性、并发与故障验证 | 最危险的问题通常藏在重试、交错和提交窗口 | 命令历史、种子、调度屏障、故障位置、恢复输出 | 区分合法在途和禁止状态，验证每次关键提交而非只看最终结果 |
| 容量与过载验证 | 交易吞吐必须以可完成义务为前提 | 负载定义、端到端耗时、队列、资源、恢复排空能力 | 不把入口受理量当成结算能力，不以丢成交换低延迟 |
| 业务可观测性 | 进程健康无法说明资金是否正确 | 分阶段 SLI、连续水位、在途年龄、日志和追踪关联 | 有界指标标签；可采样追踪不能替代持久业务记录 |
| 告警、止损与恢复 | 发现异常后必须限制影响且保留履约路径 | 告警上下文、控制版本、权威截止点、修复审计 | 撤单保护不改变成交顺序；恢复依赖同水位证据 |
| 发布与复盘闭环 | 防止修复本身引入新错，让经验真正变成能力 | 构建/规则版本、兼容矩阵、回归案例、行动项验收 | 回退程序不等于回退已确定业务，整改应进入门禁 |

## 三、核心 20%：优先掌握的机制

“20%”是重要性筛选，不是减少题目的配额。以下机制覆盖主要风险；不把 Kubernetes 部署、通用监控组件安装或完整交易引擎实现扩写成另一个专题。

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 明确完成阶段和独立测试判据 | 定义需求与验收 | 先回答测什么才有正确的测试 | HTTP 200、错误快照和 mock 成功被误认成交易成功 | 权威源、规则版本、模型与真实存储契约 |
| 数量、归属、余额与预留联合不变量 | 撮合与账户提交 | 总数平衡仍可能把钱给错人 | 丢成交、重复效果、错账户和错误释放 | 每订单守恒、每币种平衡、逐成交对应与局部原子性 |
| 可复现的历史与失败窗口 | 并发、交付、崩溃 | 单次顺利通过不能覆盖时序 | race-free 但业务错误，重启后才暴露缺失 | 调度屏障、操作历史、提交前后、ACK 丢失和结果未知 |
| 端到端容量与有界背压 | 压测、过载与恢复 | 受理产生未来义务 | 入口很快、账务无限落后 | 计划发送时间、分位数合并、热点、排空与正确性对照 |
| 分阶段 SLI 与连续水位 | 运行观测 | 直接反映用户承诺和缺口 | 最大序号上涨掩盖中间丢失 | 分母、窗口截尾、最老未完成项、监控新鲜度 |
| 业务身份贯穿而非指标高基数 | 日志、追踪与定位 | 将个案定位和总体趋势分工 | 无法追单或监控被标签打爆 | request / intent / order / trade / batch / journal 身份 |
| 告警到动作、止损到恢复的证据链 | 值班处置 | 告警只有可执行才有价值 | 反复重启、提前放量或错误释放资金 | 影响、权限、准入控制、围栏、同水位验收 |
| 回归与门禁化整改 | 发布与复盘 | 把一次事故转为可持续约束 | 总结完成但原故障仍能发布上线 | 最小反例、兼容发布、行动项责任与有效性复核 |

## 四、后续问答共用的设计与规则

### 4.1 业务不变量及允许的暂态

1. **订单数量守恒**：`原始量 = 累计成交量 + 累计撤销量 + 当前剩余量`，所有量非负；GTC 终态不能再次成交。B1：`25 = 25 + 0 + 0`；S2：`20 = 15 + 0 + 5`，单位均为 lot。
2. **分录平衡且归属正确**：每笔成交、每币种的资产增减分别合计为零，BTC 和 USDT 不能相加抵消。还要核对成交参与方、方向、金额、数量和预留来源；借贷平衡不证明转对账户。
3. **余额与预留闭合**：可用和预留不能为负，聚合余额与有效分录对得上，订单预留明细与聚合预留一致。释放必须有权威剩余量和执行资格依据。
4. **批次效果至多发生一次**：以 `(market, batch_seq)` 作为本例批次去重身份，规范化业务载荷摘要包含订单变化、成交身份与内容、释放依据和规则版本；投递次数、trace ID、重试时间不属于业务载荷。
5. **连续进度而非见过的最大值**：水位表示该市场截至该位置的完整结果全部处理完成；见到 422 不代表缺少的 421 已经完成。不同市场的序号不能直接比较或相减。
6. **权威事实不能由遥测修改**：日志、指标、追踪可以延迟、重复、采样或短时丢失，不拥有资金裁决权。强制审计记录属于业务提交/权限系统的可靠要求，不等于普通可丢诊断日志。
7. **安全约束不交给错误预算**：资金错误、未授权操作不能因为“还在 99.9% 以内”而被允许。SLO 衡量服务承诺，不为违反业务不变量授权。

撮合水位 420、账务水位 419、投影水位 418 可以是短暂合法状态，前提是义务有可靠依据、没有重复或错误释放，并能在定义的时限内收敛。账户事务内部不能对外暴露“买方已扣、卖方未加”的已提交状态。本专题将正常在途、期限违约和数据损坏分别判断。

### 4.2 架构与观测路径

```text
接入/预留 → 可靠命令位置 → 单市场撮合 → 已提交结果批次
                                                ↓
                                           可靠交付
                                                ↓
                     账户 PostgreSQL 本地事务〔分录/余额/预留/去重/水位/通知〕
                                                ↓
                                           查询与回报投影

各阶段 ──→ 有界指标、结构化日志、可采样追踪 ──→ 告警与排查
权威历史/一致快照 ──→ 独立核对 ──→ 修复依据与恢复验收

遥测与查询不反向决定成交、余额或释放资格
```

本例不增加全局追踪数据库来参与交易提交，也不要求请求在多个模块共用一条数据库事务。跨域正确性由可靠事实、稳定身份、交付与各自本地原子性共同约束；测试验证这些契约，而不是声称分布式系统不存在暂态。

### 4.3 核心对象、身份与确认边界

| 对象 | 最少需要的字段或语义 | 用于什么 |
|---|---|---|
| 业务请求 | request_id、稳定 intent_id、规范化载荷摘要 | 区分某次网络调用与同一个业务意图，发现同身份异载荷 |
| 订单/预留 | order_id、账户、市场、方向、原始/成交/撤销/剩余量、reservation_id、状态版本 | 建立数量和资产约束，验证迟到命令与释放竞争 |
| 撮合结果 | market、batch_seq、rule_version、完整成交集合、订单变化、释放依据、摘要 | 完整提交与恢复交付，不把两笔成交的任意一笔当整批完成 |
| 成交/分录 | trade_id、双方账户、整数价量、资产、journal_id、批次身份 | 核对业务归属与每币种金额，防止“平账但错账” |
| 进度 | 各市场已提交/已交付/已入账/已投影连续水位及最老待处理年龄 | 区分执行、账户和可见性瓶颈 |
| 诊断事件 | stage、outcome、业务身份、规则/构建版本、错误分类、事件时间和采集时间 | 日志/追踪定位；指标仅提取有界维度 |
| 修复与控制 | incident_id、scope、control_version、操作者、权限、依据水位和结果 | 审计止损、补正与恢复，防旧配置或旧主继续生效 |

### 4.4 实现与验证选择

- 纯规则与副作用端口分离；固定输入、时钟和随机种子，让失败可以缩小并重放。
- 单元测试验证规则，真实存储集成验证事务与约束，端到端验证跨域契约；mock 不证明 PostgreSQL 的提交原子性。
- 属性测试与独立简化模型覆盖状态空间；并发验证记录调用、返回、提交与权威顺序，只对承诺线性化的范围做线性化判断。
- 故障注入从有名称的提交窗口开始，验证提交前、提交后和提交结果未知，不拿网络超时等同于服务端失败。
- 观测按用户承诺拆分阶段；指标标签不用订单、账户、交易 hash。个案身份放在权限受控的日志、追踪及权威记录中。
- 恢复核对采用同一截止点的一致快照或可验证历史视图；持续有写入时不能直接比较不同时间的当前余额。多市场共享账户必须使用一致切面/版本向量或隔离核对窗口。
- Go race detector、pprof、SQL 执行分析、故障调度器都只是某类证据来源，不独立证明业务正确。本轮只编写方案，不运行这些工具。

## 七、工程实践：一个简洁 MVP

### 7.1 目标与范围

只手工验证“**完整结果批次入账 → 提交前故障/提交后回执丢失 → 原身份重试 → 资金、预留与水位核对**”这一个小闭环。

输入是已经由撮合提交的固定 B1 批次，初始账户状态是预留完成、账户水位 419。模型不重新实现撮合、真实数据库、持久化、主备、并发控制、通知意图与投影交付、遥测基础设施或链上重组。下面的单步状态替换只表达预期原子边界，不声称实现了断电持久性。

### 7.2 核心伪代码

`A/R` 表示可用/预留；BTC 用整数 lot，USDT 用整数元。`expectedDigest` 来自固定的完整已提交夹具，规范化摘要不包含本次故障参数或追踪身份。`delta` 的每行是“账户、资产、可用变化、预留变化”，不是省略的自动对账函数。

```text
S = {cursor:419, seen:{}, journals:[], balances:{
     甲:{USDT_A:4975, USDT_R:15025, BTC_A:0, BTC_R:0},
     乙:{USDT_A:0, USDT_R:0, BTC_A:0, BTC_R:10},
     丙:{USDT_A:0, USDT_R:0, BTC_A:0, BTC_R:20}}}

apply(batch, fault):
    key = (batch.market, batch.seq)
    digest = hash(canonical_business_payload(batch))
    if key in S.seen:
        if S.seen[key] != digest: return CONFLICT
        return ALREADY_APPLIED
    if batch.market != BTC-USDT: return OUT_OF_SCOPE
    if batch.seq != S.cursor + 1: return GAP
    if digest != expectedDigest: return INVALID_BATCH
    assert batch.trades == [(T420-1,甲,乙,60000,10),
                            (T420-2,甲,丙,60100,15)]
    paid = (60000*10 + 60100*15) / 100  // =15015，先确认均整除
    release = 15025 - paid             // =10
    delta = [(甲,USDT,+release,-15025), (甲,BTC,+25,0),
             (乙,USDT,+6000,0), (乙,BTC,0,-10),
             (丙,USDT,+9015,0), (丙,BTC,0,-15)]
    for asset in [BTC,USDT]: assert sum(dA+dR for delta of asset) == 0
    next = deep_copy(S)
    for (account,asset,dA,dR) in delta:
        next.balances[account][asset_A] += dA
        next.balances[account][asset_R] += dR
    assert every balance in next.balances >= 0
    assert next.balances[甲].USDT_R == 0 and next.balances[乙].BTC_R == 0
    assert next.balances[丙].BTC_R == 5
    next.journals.append(deep_copy({key,digest,trades:batch.trades,delta:delta}))
    next.seen[key] = digest
    next.cursor = 420
    if fault == BEFORE_COMMIT: return RETRYABLE  // S 原样保留
    S = next   // 教学模型唯一原子提交点；不是磁盘持久化实现
    if fault == AFTER_COMMIT_ACK_LOST: return UNKNOWN
    return APPLIED
```

生产实现应把状态替换落实为本例数据库事务，并实现真实提交结果未知后的查询/同身份重试；这个 MVP 不以一个抽象函数冒充跨域一致性。伪代码检查的参与方来自固定夹具，独立参考模型、通用金额校验和任意订单序列不在实现范围内。

### 7.3 输入与预期结果：仅手工推演

以下每行从初始 S 独立开始；同一行中的箭头表示连续操作，不把各行异常累积。

| 输入 | 预期返回 | 手工应核对的状态 |
|---|---|---|
| 正确批次 420，无故障 | APPLIED | 一条批次凭证、水位 420；甲 4,985 USDT / 25 lot，预留为零；乙 6,000 USDT；丙 9,015 USDT，预留 5 lot |
| 420 在提交前故障 → 同身份正常重试 | RETRYABLE → APPLIED | 故障后仍是水位 419、甲预留 15,025；重试后才发生一次资金效果 |
| 420 提交后回执丢失 → 同身份正常重试 | UNKNOWN → ALREADY_APPLIED | 第一次虽然返回未知，资金和水位已经变化；重试不新增凭证、不再扣款 |
| 正常提交 420 → 同 key 修改一笔金额 | APPLIED → CONFLICT | 原账不变，冲突不能当成已完成，也不能把新金额覆盖原凭证 |
| 未处理 420，先收到 421 | GAP | 水位仍 419，不出现“最大见过 421，所以处理完成”的误判 |
| key 为 420，但参与方或释放字段与固定完整载荷不符 | INVALID_BATCH | 不提交任何账户变化，不能只凭每币种总和为零放行 |

观测上分别记录“尝试次数、返回结果、最终已入账批次及最老待处理项”。其中尝试计数可以大于一，不能据此认定多成交；最终是否入账必须查 S 所代表的权威事实。以上为预期结果，**没有执行程序测试，也没有性能数据**。
