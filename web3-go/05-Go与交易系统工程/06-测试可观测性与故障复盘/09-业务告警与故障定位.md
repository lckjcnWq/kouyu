# 大问题 9：HTTP 仍然成功但资金链路已经积压，怎样让告警带着证据和动作找到真正故障？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |

| 业务症状 | 用户承诺没有按阶段兑现的现象。 | HTTP 正常但成交后资产迟迟未可用，需要查入账与可见性。 |
| HM / HJ | 同市场撮合和账务完整提交的连续前缀。 | HM=420、HJ=419 指向交付或入账待查，不自动等于丢钱。 |

| 严重度 / 资金不变量 | 按业务影响分级，以及不可破坏的资金规则。 | 重复入账要独立升级，不能被普通数据库故障告警合并抑制。 |
| 路由 / 有期限静默 | 将告警送到负责角色，或按授权暂时抑制通知。 | 静默要留原因、期限与审批，不能让问题永久失声。 |

| 观测新鲜度 / 未知 | 采集还是否有效，以及证据不足时的状态。 | 看板归零可能断采，不能自动当恢复。 |
| 资源线索 / 根因 | 资源数据提示候选解释，根因需要证据支持。 | 连接等待高也可能是慢事务占连接，不能盲目扩池。 |

## 把整篇文章压缩成一个故事

值班人员看到下单 HTTP 200 很正常，但用户说成交后钱不能用。告警不再只写“CPU 高”，而是指出 BTC-USDT 的完整批次 420 已提交、账户连续水位停在 419、最老义务超龄，并附证据入口。先确认是未入账还是已入账但页面旧，才能决定检查结果交付、消费者、数据库，还是查询投影；不能看到投诉就再结算一次。

整个市场都积压时，按责任域和处置动作聚合告警，保留代表性批次，不让每个订单反复叫人，也不压掉独立资金异常。连接等待、goroutine 增长只是候选原因，可能是慢事务占住连接，而非池太小。若看板突然全零，先查采集与通知心跳，再有限只读核验权威数据，证据不足就报未知。低流量一笔卡死另有超龄规则，不能等大样本比例触发。

预案允许授权限制新增风险、保护排序前撤单资源，并按原身份补交 420；不许手改水位或全退预留。恢复应核对甲可用 4,985 USDT、新增 0.25 BTC，乙丙分别新增 6,000、9,015 USDT且丙仍预留 0.05 BTC，再查投影与新鲜度。演练方案还要验证空闲不误报、失明不假绿和路由有效。本篇没有真正发出告警、执行演练或取得响应时间成绩。

**流程位置与核心机制：** 从用户承诺违约进入，沿可靠受理、成交批次、账务连续水位与投影版本缩小范围；按业务影响和处置动作聚合告警，结合错误预算与低流量停滞规则，再通过有权限边界的 runbook 和演练方案检验响应闭环。

**共同前提：** Go 1.21+；BTC/USDT 托管现货，链下单市场单写者、价格时间优先，限价 GTC、零手续费、无杠杆。甲初始 20000 USDT，买 B1：0.25 BTC@60100，预留 15025 USDT、可用 4975 USDT；乙卖 S1：0.10 BTC@60000，丙卖 S2：0.20 BTC@60100，卖单 BTC 已预留。成交 T420-1＝0.10 BTC/6000 USDT、T420-2＝0.15 BTC/9015 USDT；完整 `ResultBatch(market=BTC-USDT,batch_seq=420,trades=[T420-1,T420-2],release=10USDT)` 可靠提交后至少一次交付。

账务在同一个 PostgreSQL 事务中共同提交双边分录、余额/预留、批次去重（稳定身份＋载荷摘要）、每市场连续消费水位与通知意图，不跨缺口推进；投影异步。最终甲 4985 USDT＋0.25 BTC、预留 0；乙 6000 USDT、BTC 预留 0；丙 9015 USDT、0.05 BTC 仍预留。价格单位 1 USDT/BTC，1 lot＝0.01 BTC，资金单位 1 USDT；总成交 15015 USDT，释放 10 USDT 是价差返还而非利润。撮合权威订单成交，账户权威账本资产，查询投影不是资金真相。可靠受理、成交提交、账务提交、可见性必须分开，客户端超时不能认定失败或据此解冻。本篇只讲链下，链上机制仅作另行声明的变体。

**证据范围：** 以下是教学告警、处置和故障演练验收方案；数字不是已验证阈值，没有真实执行、告警到达记录、性能成绩或生产经历。

## 第 1 层：HTTP 200 正常，怎样确认账务慢已经影响用户？

**面试官：** 下单接口 200 比例正常，但用户说成交后资金迟迟不能使用，你会首先发什么告警？

**面试者：** 我首先看“完整成交批次已可靠提交，但未在约定时间完成账务”的业务症状，而不是等 HTTP 错误。告警应包含受影响 market、连续成交水位与账务水位、最老未结算年龄、超龄批次数、开始时间和证据链接。比如 420 已可靠提交而账务仍停在 419，能说明成交到结算的链路待查，却还不能证明重复入账或资产丢失。要先区分账务确实未提交，还是账务已提交但投影滞后；后者应发可见性告警，不能指挥再次结算。合法未成交的 GTC 挂单也不属于结算超时。告警描述必须说清“哪类用户承诺、哪段进度、需要什么动作”，HTTP 成功只能说明它所承诺的受理阶段，不足以替资金链路背书。

## 第 2 层：怎样沿水位和请求身份把症状定位到具体边界？

**面试官：** 你已经报出 BTC-USDT 的 420 超龄，但还不知道丢在交付、账务还是查询，接下来怎么缩小范围？

**面试者：** 我先用请求尝试找到稳定意图与 B1，再核对撮合权威中的完整 420、两笔 trade 和载荷摘要。设 HM 为撮合可靠提交的连续前缀、HJ 为账务事务提交的连续前缀；HM＝420、HJ＝419 时，继续核对发布意图、投递尝试、消费者和数据库事务，而不是直接怪查询。如果 HJ 已到 420，再查同事务通知意图及投影是否覆盖目标批次或资产版本。最大已见 422 不能取代连续水位 419，其他市场的序号也不能拿来相减。日志和 trace 提供线索，最终是否生效要查账务去重记录、分录和资产。只读查询应限定 market、身份和时间范围，避免全表扫描反过来加重故障；没有 trace 样本也不能中断这条权威身份路径。

## 第 3 层：怎样按业务严重程度和处置动作聚合，避免告警风暴？

**面试官：** 按这条路径你发现整个市场账务都在排队，每个订单、每个实例都发告警；怎样只叫醒真正需要的人？

**面试者：** 我按环境、责任域、受影响市场或依赖故障域和处置动作生成稳定告警指纹，不用 order_id、batch_seq 或 trace_id 当聚合键，否则每个新对象都会变成新事件。重复通知合并进同一事故，保留最早时间、影响范围、代表性批次与趋势。严重度由资产正确性、受影响范围、持续时间和可恢复性决定：重复入账或不平应立即升级资金事件，普通投影延迟不能与它同级。共享数据库故障可合并派生通知，但不得把独立的资金不变量告警一并抑制。告警路由要有当前值班人与升级超时，静默必须带原因、期限和审批记录。恢复通知也要绑定业务水位追上和超龄对象消失，不能仅因实例重启或 CPU 降下来就自动结案。

## 第 4 层：多窗口燃烧率为什么还抓不住低流量静默故障？

**面试官：** 聚合后噪声少了，但负责人只愿保留多窗口错误预算告警；冷市场一笔 420 卡死时，这样够吗？

**面试者：** 不够。教学目标若为账务 2 秒内完成 99.9%，预算坏比例是 0.1%，可用“1 小时与 5 分钟燃烧率都大于 14.4”或“6 小时与 30 分钟都大于 6”的双窗口组合观察持续违约；这些只是教学起点，不是现成生产配置。低流量会让比例极不稳定，缺失数据也可能让规则不触发，因此另设具体对象超龄与进度停滞规则：存在可靠提交且待结算的批次，最老年龄越过阈值，连续 HJ 在观测区间没有推进，就进入对应响应。无成交的空闲市场不应仅因水位不变报警；单笔严重卡单也不能被最小样本数屏蔽。完成直方图还要结合到期未完成对象，不能让彻底卡死的 420 因没有完成样本而消失。

## 第 5 层：基础设施指标怎样解释症状，而不是替代业务证据？

**面试官：** 420 的超龄规则触发，同时数据库连接等待、CPU 和 goroutine 都升高；能直接下结论是连接池太小吗？

**面试者：** 不能。这些指标用于给业务症状建立候选解释：账务可能在等连接，也可能因慢事务或锁持有太久使连接耗尽，盲目扩池反而放大数据库争用。先对齐故障区间内的提交速率、批次年龄、连接获取等待、事务耗时、锁等待与下游错误，区分入口突增和服务能力下降。Go 1.21+ 的 CPU、heap、goroutine、block、mutex profile 可进一步定位等待或开销，但采样热点不等于根因，还应限制诊断开销和访问权限。只改变一个受控变量观察因果，并保留回滚点，不能同时扩池、加 worker 和改批量后说已经证明原因。即使资源利用率回落，也要继续核对 HJ 是否连续前进、积压是否排空、同一批次是否只入账一次，基础设施恢复不等于业务恢复。

## 第 6 层：当监控本身失效，怎样交叉核验而不宣告假恢复？

**面试官：** 你准备比较资源和水位，突然看板全部归零，用户投诉仍在；怎样判断是恢复还是观测链路断了？

**面试者：** 我先检查采集时间、抓取成功率、目标存活、规则评估器和通知通道的独立心跳，缺失序列显示未知，绝不填零当健康。然后用独立、受权限控制的只读路径抽查撮合提交与账务批次记录，交叉确认 HJ、未结算对象及数据库自身的连接或事务状态；通知平台不可用还需要独立升级通道。可以在隔离账户上安排受控业务探针，但探针不能绕过风控、覆盖真实资产，也不能替代真实业务积压检查。若指标旧而权威记录显示 420 已提交，就记录“业务可能恢复、观测仍失明”，继续核对投影和影响范围；若无法取证，结论应是未知而非恢复。缺少错误日志同样不能证明没错，日志限流与丢弃计数要纳入这次故障证据。

## 第 7 层：runbook 应怎样约束权限、止损和恢复证据？

**面试官：** 交叉核验确认 PostgreSQL 曾变慢，420 等批次积压；值班人员能直接改水位、释放预留让用户先用钱吗？

**面试者：** 不能。runbook 先列只读证据：影响 market、首个缺口、批次摘要、事务记录、积压年龄和采集新鲜度，再列需授权的动作及回滚条件。可在排序前限制新增受理、保留有界撤单资源，但已进入权威顺序的命令不能被后来的撤单越过，已提交成交不能丢弃。对完整批次按稳定身份和摘要重放，由账务幂等协议处理重复，不手动跳水位、不凭客户端超时解冻。涉及资产更正、数据库高权限或切换写入的动作必须按角色审批与审计；本基线不擅自引入多写者。恢复证据包括 HJ 连续追上、最老积压清除、通知意图可继续交付，以及 420 的甲 4985 USDT＋0.25 BTC、乙 6000 USDT、丙 9015 USDT 且仍预留 0.05 BTC 全部核对成立，页面恢复只是其中一层。

## 第 8 层：故障演练怎样验收告警覆盖、误报和响应闭环？

**面试官：** runbook 已明确不能直接改账，你怎样设计演练验收，证明告警确实能把人带到正确动作，而不是只验证消息发出？

**面试者：** 我会在获授权的隔离环境规划“注入→预期症状→告警→确认→止损→恢复→核对”的演练矩阵：账务变慢且 HTTP 正常、420 缺口却先见 421、420 重复交付、投影独自滞后、监控断流、冷市场单笔卡死分别设预期。也加入无新成交的空闲市场与短时可恢复抖动作为误报对照。验收记录覆盖了什么、漏了什么、是否重复叫人、消息是否送达责任人、多久确认与执行动作，以及动作是否越权；时间目标是预先约定的教学目标，不编造实测响应。恢复必须验证连续水位、积压年龄、账务不变量与用户可见版本，而不是告警自动变绿。最后把缺失证据、无效动作和新增风险转成带责任人与复验条件的改进项，再安排复验；本轮只写方案，不实际注入故障。

## 收束：告警的终点不是变绿，而是影响被解释并正确恢复

- **机制：** 业务症状确定影响，连续水位确定边界，资源数据解释候选原因，授权 runbook 控制动作，恢复核对与复验关闭问题。
- **易错边界：** HTTP 200、CPU 回落、最大已见序号、告警消失都不是独立恢复证据；多窗口比例不能替代低流量超龄规则，缺失监控必须显式报告未知。
- **验证反例：** 手工推演“HTTP 200 但 HJ＝419”“监控断流后全部归零”“只修复投影却又重放入账”“为了降积压跳过 420”。方案必须分别报警、保留未知、阻止重复入账、拒绝跨缺口推进。
- **资金边界：** 15015 USDT 成交和 10 USDT 价差释放分开核对；整数精度、结算粒度、溢出与每币种守恒不能被恢复时效牺牲。本文仅为文档与教学方案，没有执行演练或给出真实成绩。
