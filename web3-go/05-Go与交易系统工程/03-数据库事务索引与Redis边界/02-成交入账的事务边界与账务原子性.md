# 大问题 2：怎样划定成交入账的事务边界，保证账务整体正确？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| T100 / 成交义务 | 已经确定、应按规则履行的一次资产交换。 | 买方 101 支付 3000 USDT，卖方 202 交付 0.1 BTC，不重新撮合。 |
| 单库事务 / 原子性 | 同一数据库内的一组修改一起提交或一起撤销。 | 不是先扣买方再给卖方另开事务；跨库后不能照搬这一保证。 |
| settlements / APPLIED | 成交身份及已完成结果的持久记录。 | 事务内可以先占 T100 身份，但必须补齐完整结果后才提交。 |
| ledger_entries / leg_no | 资产增减明细与一笔成交内的腿编号。 | 四腿各有唯一身份，便于追查和防止同一腿重复。 |
| delta / 逐币种守恒 | 每条分录的正负变化，各币种各自核对收支。 | USDT 为 −3000 与 +3000，BTC 为 −0.1 与 +0.1，不能跨币种混加。 |
| available / frozen | 可再次分配的余额与已经被占用的余额。 | 本次从 frozen 消费，不对 available 再扣一遍。 |
| hold.remaining / consumed | 预占还能消费多少，以及已被用完的状态。 | HB、HS 剩余归零；减少 remaining 不是额外扣一笔资产。 |
| CHECK / 外键 | 检查单行条件与引用关系的数据库约束。 | 非负和归属引用可下沉，但普通 CHECK 不负责跨表四腿守恒。 |
| 整型最小单位 / 溢出 | 用固定最小刻度存钱，同时防止整数超范围。 | BTC 按 1e8、USDT 按 1e6 缩放，不能依赖浮点补舍入。 |
| FOR UPDATE / 预建余额 | 锁住既有行后再判断，且所需余额行事先存在。 | 先锁齐四条余额，再锁 HB、HS；查无行不等于锁住未来插入。 |
| BeginTx / *sql.Tx | Go 中开启事务并绑定同一连接的对象。 | 本次全部读写走同一 tx，中途不能改用 db 在事务外更新。 |
| RowsAffected | 更新真正影响了几行。 | 条件更新零行即业务校验未通过，SQL 没报错也不能提交成功。 |
| outbox / event.version | 同事务通知记录及该成交事件的版本。 | T100:applied 的版本 1 不是四个余额共用版本或全局水位。 |
| Commit 未知 / defer Rollback | 提交结果不明与延迟资源清理。 | 清理调用不能证明远端撤销；仍须按原 T100 核验主库。 |
| WAL / fsync / 同步提交 | 数据库用于崩溃恢复的日志及刷盘配置。 | 本机提交耐久性不自动覆盖切换到落后异步副本的丢失风险。 |

## 把整篇文章压缩成一个故事

T100 要让小林拿出已冻结的 3000 USDT，换小周已冻结的 0.1 BTC。工程师阿宁没有把“给两个人改余额”拆成两次成功，而是先取得 T100 的唯一身份，再按账户币种顺序锁齐四条余额，随后锁 HB、HS。四行余额事先存在，锁内重新核对归属、币种、状态和剩余量，不拿刚才的普通查询结果当通行证。

阿宁在同一个 Go 事务里写四条分录、改四条余额、消费两份预占、填好 APPLIED 结果并留下 outbox。USDT 和 BTC 分别收支相抵，hold 只记录冻结资格被用完，不再多扣一遍。整体提交后，小林 USDT 为可用 7000、冻结 0，BTC 增加 0.1；小周 BTC 为可用 0.4、冻结 0，USDT 增加 3000。若第三步报错，不能留下前两步。

最难的事故不是中途报错，而是 COMMIT 发出后断网：它可能已经提交，defer Rollback 也无法证明撤销。恢复必须沿原 T100 查权威主库，通知则由 outbox 继续交付；Redis 旧读不改资产。即使收到成功，也只承诺既定刷盘和复制条件下的耐久性，不能顺势声称任意切主零丢失，更不能把单库原子性延伸成跨片原子性。

[返回专题总览](README.md)

**流程位置与核心机制：** 撮合已经确定成交之后，讨论余额、分录、预占和成交结果怎样在数据库中共同生效。重点是单库原子性、并发约束与恢复边界，不展开会计科目体系或消息队列架构。

**沿用总览基线：** 链下托管 BTC/USDT 现货，T100 已确定成交；PostgreSQL 16、Read Committed，Go 1.21+ `database/sql`。BTC 用 `1e8`、USDT 用 `1e6` 的整型最小单位存储，以下金额使用界面单位解释。四条余额行事先存在；Redis 7.x 可丢失，不拥有资产裁决权。

## 第 1 层：一笔成交究竟要在哪个边界内完成？

**面试官：** T100 是买方 101 向卖方 202 买入 0.1 BTC，成交价 30000 USDT/BTC。怎样保证不会只扣买方的钱，却没有给卖方入账？

**面试者：** 我会把这笔成交的全部账务放进同一个 PostgreSQL 事务：写入唯一的 `settlements(T100)`，写四条 `ledger_entries`，更新四条 `balances`，消费 HB、HS 两条 hold，再写一条 outbox，最后统一提交。T100 的 3000 USDT 来自买方 frozen，不再扣 available；0.1 BTC 同样来自卖方 frozen。任何一步失败都整体回滚，不能把两边分别提交后依赖补偿补齐。`settlements` 可以在事务内先占身份，但提交前必须填好 APPLIED 结果；只有整体提交后的记录才表示入账完成。

## 第 2 层：同事务只是形式，具体要守住哪些不变量？

**面试官：** 你把这些写入放到同一事务了，但如果代码把数量算错，事务仍然能提交。怎样定义“正确”？

**面试者：** 我会先列可核对的不变量。T100 的四条分录分别是买方 USDT frozen 减 3000、卖方 USDT available 加 3000、卖方 BTC frozen 减 0.1、买方 BTC available 加 0.1，逐币种 delta 和必须为零，不能把 BTC 与 USDT 混加。所有 available、frozen 和 hold.remaining 非负，余额快照变化必须与对应分录一致。提交后买方 USDT 为 available 7000、frozen 0，BTC available 0.1；卖方 BTC 为 available 0.4、frozen 0，USDT available 3000。全体账户仍合计 10000 USDT、0.5 BTC，不计费用。

## 第 3 层：为什么还要改 hold，余额和分录不够吗？

**面试官：** 你已经用分录解释了余额变化。为什么还要把 HB、HS 与它们共同提交，hold 会不会又算了一次资产？

**面试者：** hold 不是第五条资产分录，而是说明哪份冻结资金还可被哪项业务消费。这里 HB 原剩余 3000 USDT，HS 原剩余 0.1 BTC，恰好被 T100 全部消费；事务中它们都变为 remaining 0、status consumed，并递增 version。如果余额扣了而 hold 没改，后续释放程序可能再把这笔冻结资金转回 available；反过来只消耗 hold 不动余额，也会使两套状态失配。因此我会在锁内校验归属、币种、剩余量及允许状态，再同步更新。hold.remaining 减少是预占状态变化，不再额外产生同方向经济扣款。

## 第 4 层：这些规则哪些能直接交给数据库约束？

**面试官：** 既然规则明确，能不能全部写成约束，让业务代码只负责 INSERT？

**面试者：** 单行规则和唯一身份应尽量下沉：余额主键是 `(account_id, asset)`，分录唯一键是 `(trade_id, leg_no)`，成交 trade_id、hold.id、outbox.event_id 各自唯一；余额与 remaining 用整型并设非负 CHECK，分录 delta 则必须允许正负，必要的归属关系设外键。但 PostgreSQL 普通 CHECK 不能可靠表达跨行、跨表的“恰好四条分录、每币种和为零、余额变化等于分录、hold 消费量相等”。这些需要受控写入入口在同事务内核验，必要时使用正确设计的延迟约束触发器。外键也不会替我核对资产与金额。还要检查整型运算溢出，不能靠浮点再四舍五入补救。

## 第 5 层：RC 下如何防止两个事务同时消费同一份冻结？

**面试官：** 约束不覆盖全部跨表规则。RC 又允许并发，两个处理者同时读到 HB 还有 3000，怎样让它们不能各消费一次？

**面试者：** 我会先用 T100 的唯一身份挡住同成交重复，再用统一行锁协议协调所有资产写者。每个事务先按明确的 `(account_id, asset)` 升序逐条锁全部受影响 balance：本例是 101/BTC、101/USDT、202/BTC、202/USDT；全部拿到后，再按 hold_id 升序锁 HB、HS。锁内重验余额和 hold，更新时保留状态与非负条件并核对影响行数。四条余额预建，避免把“查询没返回行”误当成锁住了未来行。不能假定一个任意 `WHERE ... IN (...) FOR UPDATE` 自动按这个顺序加锁，更不能只锁 hold 就扣钱。

## 第 6 层：Go 实现怎样避免名义上同事务、实际漏出事务？

**面试官：** 锁顺序说清楚了。用 `database/sql` 实现时，哪些细节会让这个原子边界失效？

**面试者：** 我会用 `BeginTx` 明确请求 `sql.LevelReadCommitted`，随后所有锁定、查询和写入都通过同一个 `*sql.Tx`，不在中途调用 `db.ExecContext` 开另一条连接。事务建立后安排 `defer tx.Rollback()`，逐项处理查询、扫描、Exec、RowsAffected 和结果编码错误；任何不符合预期的行数都不提交。锁内生成四条确定的分录及更新后版本，写好 settlement.result 与 outbox，再检查 `Commit`。defer 是资源清理，不是“提交报错就一定撤销成功”的证明。事务内也不做耗时 HTTP 调用，避免持锁等待不可控的外部系统。

## 第 7 层：提交之后还要通知缓存，为什么不能直接先通知？

**面试官：** 你不在事务里调用外部系统，那 Redis 失效通知和用户结果交付怎么保证不漏？

**面试者：** 我会让 outbox 与账务同事务提交，而不是提交前删缓存或发送“已入账”通知。示例事件可以是 `event_id=T100:applied`、`aggregate_id=T100`、`version=1`，payload 包含四个 balance 键及各自更新后 version，delivery_state 表示交付进展。这样未提交就没有可交付事件，提交成功即留下可恢复的通知义务。这里 event.version 是 T100 结果版本，不是全站账户的统一进度。outbox 只负责可靠失效与结果交付，不参与金额计算，也不把 Redis 更新成功作为资产事务成功的条件。

## 第 8 层：不同崩溃位置会留下什么状态？

**面试官：** 有了 outbox，如果进程写完两条分录就崩溃，或者刚发出 COMMIT 就断网，分别怎样恢复？

**面试者：** 写到中途且事务没有提交，数据库恢复会把这次未提交修改作为未完成事务处理，不应留下半套余额或可见的完成标记；恢复者仍以 T100 重放完整入账。COMMIT 发出后连接断开则不同：服务端可能已经提交，只是应答没回来。我必须把结果记为未知，通过新连接查询权威主库的 T100，并以原 trade_id、原载荷恢复，不能换身份再扣一次。若权威成交 T100 对应的 hold 不一致，我会告警隔离、等待修复；不能撤销已确定成交，也不能把异常解释成允许释放冻结资产。

## 第 9 层：账务完整提交后，通知长期没送到会不会破坏正确性？

**面试官：** 假设查询主库确认 T100 已完成，但进程在更新 outbox.delivery_state 之前又崩溃，Redis 还是旧余额，怎么办？

**面试者：** 这时资产已经正确，未完成的是结果投递。交付者可以继续扫描待处理 outbox，允许重复失效通知或重复结果事件；接收方按事件身份去重，涉及账户版本时按每个 balance 的版本处理，不能用 T100 的事件版本 1 覆盖其他成交产生的新账户状态。Redis 旧值只能影响展示，下一次资金裁决仍回主库并执行锁内校验。即使缓存过期、丢失或者读副本滞后，都不允许重新计算并回写权威资产。交付状态更新与外部动作之间仍可能重复，因此这里没有宣称外部交付恰好一次。

## 第 10 层：事务提交的持久化承诺到哪里为止？

**面试官：** 你把主库提交作为完成点。如果数据库主机断电或主备切换，“已经提交就永不丢”这句话成立吗？

**面试者：** 要把故障范围说清楚。PostgreSQL 正常 WAL 持久化配置下，例如 fsync 开启、同步提交等待本机 WAL 刷盘，成功 COMMIT 承诺的是相应本机持久性，仍依赖存储正确履行刷盘语义。若改为异步提交，或者切换到未收到相应 WAL 的异步副本，故障时就可能丢失先前应答过的提交；本机 ACID 不自动承诺任意切主零丢失。更高承诺需要匹配复制确认与切换规则。若改成跨分片或外部支付，也已经改变单库基线，不能继续用“一个事务”概括全局原子性。

## 收束：机制、边界与反例

- **讲透的机制：** T100 的唯一结果、四条分录、四条余额、两条 hold 与 outbox 共同提交；数据库约束和统一锁内校验分工，不互相替代。
- **易错边界：** frozen 的成交消费不能再扣 available；hold 是预占归属而非额外资产；提交网络错误不等于回滚；单机持久性不等于异步切主零丢失。
- **反例检验：** 如果先单独提交 `settlements(T100)`，再写余额时崩溃，重投就可能被“已完成”挡住，永久漏账。正确方案中不存在可见的“去重成功、账务没做完”状态。

**核实资料：** [PostgreSQL 16 事务隔离](https://www.postgresql.org/docs/16/transaction-iso.html)、[PostgreSQL 16 显式锁](https://www.postgresql.org/docs/16/explicit-locking.html)。
