# 大问题 11：Redis 的原子计数、Lua 和事务能保证什么，限流为什么不能代替资金控制？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 请求预算 / 资金控制 | 限制让多少请求继续处理，与判断钱够不够不同。 | Redis 放行不代表鉴权、资产检查或可靠受理已经完成。 |
| 固定窗口 / 滑动窗口 / 令牌桶 | 按固定时间段、滚动时间段或补充令牌限制请求。 | 先定义业务口径；固定窗口边界前后仍可能出现短时突发。 |
| INCR / EXPIRE | 增加计数与设置键的到期时间。 | 拆开调用可能计数成功却没设 TTL，留下长期存在的计数键。 |
| TTL / 首次设期限 | 让窗口状态在约定时间结束，而不是每次访问都续命。 | 不小心反复延期，会把固定窗口改成另一种封禁语义。 |
| Lua 原子执行 | 脚本执行期间不被其他普通客户端命令穿插。 | 不等于报错回滚，也不承诺计数在故障切换后绝不丢。 |
| 运行时错误 / redis.pcall | 执行中出错与捕获该错误。 | 先 INCR 再报错，已完成的计数仍在；pcall 不会撤销它。 |
| MULTI / EXEC | 把命令排队后按 Redis 事务规则执行。 | 入队错误和执行错误不同，执行中一条失败不通用回滚其他成功命令。 |
| WATCH / 乐观并发 | 提交时检查监视键是否自读取后发生变化。 | 变化则中止并重读，须有限重试，监视与事务绑定同一连接。 |
| pipeline | 把多条命令一起发送以减少网络往返。 | 本身不保证整批隔离，也不是多维限流的全局事务。 |
| Cluster / hash slot / hash tag | Redis 集群把键分槽，标签可使相关键落到同槽。 | 单脚本多键须同槽；强行把全部用户和 IP 聚一起可能制造热点。 |
| 用户维度 / IP 维度 | 分别限制账户行为与来源流量的防护规则。 | 跨槽分步执行可接受额外配额消耗，但不能冒称全有或全无。 |
| NAT / 可信代理链 | 多人共用出口与用于确认来源的受控转发路径。 | 共享 IP 会误伤，客户端自己填的转发头不能直接信任。 |
| 保守误拒绝 | 多算一次配额而少放一个请求的可约定后果。 | 网络结果未知或跨维度后一步拒绝时可出现，不能类比为资产多扣可接受。 |
| fail open / fail closed | 防护不可用时有限放行，或拒绝进入。 | 按接口风险和降级预算选择，本地限额不等于多实例全局限额。 |
| 撤单独立预算 / 可靠结算通道 | 给退出请求和既定义务保留受控处理能力。 | 不保证立即撤成，不越过裁决；已确定 T100 不能因入口限流而被永久丢弃。 |

## 把整篇文章压缩成一个故事

小林不断发新单，阿宁用 Redis 给账户和可信来源 IP 设请求预算。放行只是允许继续鉴权、查资和受理，绝不是账户还有钱的证明。固定窗口里，她把计数与首次设置期限放进短 Lua，防止 INCR 成功后进程退出、EXPIRE 没执行而留下永久键；同时承认窗口边界附近会突发，不把它说成任意滑动区间的严格上限。

故障演练的纸面反例是脚本先计数，后因键类型错误报错。阿宁明确已有计数不会回滚，pcall 和 MULTI/EXEC 也不是数据库式撤销。WATCH 能在并发变化时拒绝提交，但需同连接重读重试；pipeline 只省往返。用户与 IP 键到了 Cluster 还可能跨槽，分步消费预算可约定保守误拒绝，不能拿两段执行冒充一次全局原子操作。

Redis 超时后，行情查询可以按本地预算有限放行，高风险接口则按合同拒绝或走专用通道，不能统一无限 fail open。撤单有独立但有界的资源，仍须权威裁决；已确定的 T100 是 0.1 BTC 换 3000 USDT，结算不能因新单窗口耗尽被丢弃。无论计数丢失、重复还是故障切换，资金仍由 PostgreSQL 同事务、唯一身份和预占条件保护，限流原子性不等于资产耐久性。

**流程位置与核心机制：** 本题讨论接入层请求预算，连续追到命令失败、多维限流、Cluster 和故障策略。基线是链下托管 BTC/USDT，撮合已确定 T100：0.1 BTC × 30000 = 3000 USDT，无手续费；PostgreSQL 16 RC 是账务权威，Go 1.21+ 使用 `database/sql`，Redis 7.x 仅承担可丢限流状态。BTC、USDT 分别用 1e8、1e6 最小整型单位存储，不以浮点数计资。

## 第 1 层：请求放行与交易成功有什么区别？

**面试官：** 你会怎样用 Redis 限制交易接口请求？能否让“限流成功”顺便代表账户可以成交？

**面试者：** 我会先定义限制的是账户的新单请求数、来源 IP 的尝试数，还是昂贵查询的资源预算，再选择固定窗口、滑动窗口或令牌桶。限流结果只代表这一层愿意继续处理请求，不代表鉴权通过、资产足够或订单已受理。T100 已经由撮合确定成交，后续结算重试也不能因为入口窗口耗尽就永久丢弃，而要进入独立受控的可靠处理通道。即使同一用户每秒只允许一个新单，他也可能在两个不同窗口提交竞争余额的请求；防超买仍依赖数据库事务与预留约束。Redis 的计数丢失可能改变滥用防护强度，但不能因此改变用户资产，更不能把计数器当作余额。

## 第 2 层：INCR 和 EXPIRE 为什么不能随手分开执行？

**面试官：** 既然只是入口预算，固定窗口用 INCR 计数，再 EXPIRE 设置过期时间，不就够了吗？

**面试者：** 如果两条命令分开执行，进程可能在 INCR 成功后、EXPIRE 前崩溃，计数键就没有 TTL；之后若只在计数为 1 时设置过期，它可能长期存在。每次访问都续期又会把固定窗口变成另一种滑动封禁语义。因此通常用短 Lua 把计数和首次设定期限放进一次不被其他客户端命令穿插的执行，窗口边界和请求时钟也必须先约定。固定窗口本身还允许边界前后短时突发，不能声称它提供任意滑动区间的严格上限。若使用时间桶键，也仍要处理无过期键造成的空间泄漏，而不是以“旧桶不再读取”为理由忽略故障。

## 第 3 层：Lua 原子执行是否等于数据库事务回滚？

**面试官：** 你说把计数与设 TTL 放进 Lua 就原子了。如果脚本先 INCR，后面的命令类型或参数错误，会撤销前面的计数吗？

**面试者：** 不会。Redis Lua 的原子性主要是不被其他普通命令交错观察执行过程，不是遇错回滚。先写成功再出现运行时错误，之前的写仍保留；`redis.pcall` 只是捕获错误，也不会撤销写入。设计时应在写之前验证参数、键类型和范围，缩短脚本，并明确失败后的修复或保守计数语义，不能把业务拒绝分支放在扣减后再靠报错恢复。MULTI/EXEC 同样没有通用回滚：入队阶段错误可能导致事务被拒绝执行，但 EXEC 期间某条命令的运行时错误不会撤销其他成功命令。检查返回结果必须逐项进行，不能只看 EXEC 有响应，就认定“计数与期限都成功”。

## 第 4 层：WATCH 与 pipeline 分别补上什么能力？

**面试官：** 如果我不想写脚本，能用 WATCH 加事务避免并发竞争吗？pipeline 能不能直接替代？

**面试者：** WATCH 可以做乐观并发控制：监视键、读取状态，计算新值，再 MULTI/EXEC；期间被监视键改变，EXEC 会中止，需要重新读取后有限重试。它不回滚运行时错误，网络超时还可能让执行结果未知，重复尝试可能多计一次，因此限流合同要允许这种保守误拒绝，或另设请求身份去重。WATCH 和事务必须固定在同一连接上，连接归还前清理状态，不能让连接池把监视与提交拆开。pipeline 主要节省往返，不保证整批命令隔离，其他客户端可能穿插执行。Lua、WATCH 事务和 pipeline 的目标不同；高竞争下 WATCH 的重试成本也可能使一个短脚本更适合，但这不是资金事务迁到 Redis 的理由。

## 第 5 层：Cluster 中一个脚本能否原子处理任意多个键？

**面试官：** 你倾向短脚本。假设脚本要同时看用户计数和 IP 计数，放到 Redis Cluster 后还保持原子吗？

**面试者：** 不能默认成立。Cluster 中脚本或事务涉及的多个键必须位于同一槽，并显式声明脚本所用的键；用户键和 IP 键天然不一定同槽。hash tag 可以强制同槽，但一个用户关联多个 IP、一个 IP 又关联多个用户，把所有相关键都放到统一标签容易形成热点，甚至让分片失去意义。若选择跨槽分别执行，就承认没有一次原子更新全部维度的保证，不能把两段 pipeline 包装成全局事务。可以接受先消费一个维度、后一个维度拒绝造成的额外配额消耗，因为损失的是请求预算而非资产；但必须把保守误拒绝、失败重试和容量集中这些代价写进限流策略。

## 第 6 层：用户与 IP 两个维度怎样组合才不误导业务？

**面试官：** 既然可以接受额外消耗，具体怎样组合用户与 IP 规则？共享出口和伪造 IP 会不会让规则失效？

**面试者：** 我会让用户预算和可信来源 IP 预算分别判断，任一超限就拒绝新单；明确统计尝试请求还是成功受理请求，避免执行顺序无意改变语义。用户维度限制单账户，IP 维度拦截批量探测与多账户滥用，但共享 NAT 可能误伤，代理和 IPv6 地址变化也可能绕过单 IP 规则。只能信任经受控代理链校验的来源信息，不能直接相信客户端传来的转发头。IP 常作为更宽的外层保护，账户与接口类别提供更细预算；匿名请求另外约束。跨维度不要求资产式的精确全有或全无，允许拒绝后不退配额，防止补偿被滥用。这样的防护模型不能复用于冻结金额，因为多扣一次资产和多占一次请求预算不是同一种后果。

## 第 7 层：Redis 故障时，到底应该放行还是拒绝？

**面试官：** 你允许请求预算保守消耗，那 Redis 超时或重启丢掉计数时，统一 fail open 是否就能保证可用性？

**面试者：** 不能统一选择，应该按安全合同决定。公共行情查询可以在进程内保底限额和有界并发下有限放行；高风险登录、提币验证等若依赖共享防滥用预算，就应拒绝或进入另外定义的安全通道。新单在无法满足约定防护时可以暂停接入，不能无限回源压垮主库。多实例的本地限额不等于全局限额，Redis 恢复后计数丢失也可能额外放量，因此不能承诺故障期间仍维持原来的精确跨实例窗口。对每类接口要说明故障检测、降级预算、持续时间与拒绝结果；并结合数据库余量收紧接入。这里降低的是入口可用性，绝不能通过跳过账户约束来“保交易成功”。

## 第 8 层：保护撤单后，账务正确性靠什么闭合？

**面试官：** 新单可以暂停，那撤单和已确定的 T100 结算怎样处理，才能既保护用户退出，又不让 Redis 降级变成资金漏洞？

**面试者：** 撤单使用独立预算、队列和鉴权通道，优先保护退出能力，但仍受有界资源与权威订单裁决约束；不能承诺任何故障下都立即撤成，更不能因 Redis 超时直接释放预留。T100 的结算则在单库事务内按 `(account_id, asset)` 升序锁完四条预建余额行，再按 hold_id 升序锁 HB/HS，直到事务结束释放。四分录分别扣买方 USDT frozen 3000、加卖方 USDT available 3000、扣卖方 BTC frozen 0.1、加买方 BTC available 0.1，各币种 delta 和为零，余额及 hold.remaining 非负。成交唯一身份、分录、余额、两 hold 与 outbox 一起提交；Commit 断网按原 trade_id 查主库或重入恢复。Redis 是否放行、是否丢计数都不能替代这些约束。

## 本题收束

- **讲透的机制：** 脚本提供单次执行不被交错的能力；WATCH 提供有条件的乐观提交；pipeline 主要减少网络往返；多键原子性还受 Cluster 槽位约束。
- **最容易答错的边界：** Lua 和 MULTI/EXEC 不是通用回滚事务；TTL 设置不能随意拆开；跨槽多维限流不能假装全局原子；fail open/closed 必须由接口安全合同决定。
- **检验反例：** 先让一个限流脚本成功 INCR，再让后续命令报运行时错误。正确回答应承认已有计数仍在，并说明修复与误拒绝语义；若把同样的“报错即撤销”假设用于资产扣减，方案就已经失效。
