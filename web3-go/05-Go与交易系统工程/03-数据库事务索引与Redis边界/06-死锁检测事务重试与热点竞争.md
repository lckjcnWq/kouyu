# 大问题 6：怎样处理死锁、事务重试与热点账户竞争？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| T100 / 原载荷 | 重试始终要兑现的同一份成交义务。 | 0.1 BTC 换 3000 USDT，不能因冲突换 trade_id 或改金额。 |
| 普通锁等待 | 我等你，但你还能继续完成并释放资源。 | 热点余额更新排队不一定存在死锁。 |
| 死锁 / 等待环 | 双方各拿一部分资源，又互等对方手里的资源。 | A 持 X 等 Y，B 持 Y 等 X，形成 A→B→A。 |
| 固定锁序 | 所有相关写者按同一资源顺序获取锁。 | 先升序逐条锁齐 balance，再升序锁 hold；任意 IN 列表不承诺此顺序。 |
| 40P01 / 牺牲事务 | PG 检测死锁后中止某次执行以打破环。 | 清理旧事务，再从身份竞争到提交完整重试，不只重发最后一句。 |
| 40001 / 序列化失败 | 较强隔离级别下拒绝不安全的并发执行。 | PG RR、Serializable 的独立对比也要求新事务重新读取判断。 |
| 55P03 / lock_timeout | 锁当前拿不到或等待超过设定时间。 | 不等于检测到死锁，更不是余额不足；回滚后再按策略处理。 |
| 57014 / query_canceled | 数据库语句因超时或取消被中止。 | 要结合执行阶段分类，不能把各种错误都当成同一种重试信号。 |
| MySQL 1213 / 1205 | InnoDB 死锁与锁等待超时的不同错误。 | 1213 通常撤销牺牲事务；默认 1205 通常只撤销超时语句。 |
| innodb_rollback_on_timeout | 控制 MySQL 锁超时回滚范围的配置。 | 默认 OFF；应用仍应显式回滚整笔业务，避免把前半笔提交。 |
| Commit 未知 | 通信失败导致不能确认是否已经提交。 | 不走明确回滚重试分支，要按原 T100 核验主库或幂等恢复。 |
| 指数退避 / jitter | 冲突后逐步延长等待，再加随机差异。 | 先释放事务和连接再等，有次数与总预算上限，不持锁睡眠。 |
| context / 持久恢复 | 在线请求等待结束与成交后续恢复的不同生命周期。 | 请求取消可以停止本次尝试，但不能丢掉既定 T100 或释放 HB/HS。 |
| 可重试闭包 / 外部副作用 | 会被重新执行的事务单元，与不能随回滚撤销的动作。 | 不在闭包里发成功通知或扣外部款，通知义务用同事务 outbox 保存。 |
| 热点串行化 / 有界并发 | 同一物理余额行只能互斥写，排队也须有上限。 | 增加 goroutine、连接或重试次数不能消除该瓶颈。 |

## 把整篇文章压缩成一个故事

工程师阿宁排查 T100 卡住，发现处理它的 A 先锁了 101/USDT，而另一笔成交的 B 先锁了 202/BTC。A 接着要 B 的行，B 又要 A 的行，于是谁也走不了。这是故意违反基线锁序的死锁反例，不是两个 T100 在等唯一键，也不是正常的单向排队。修复要覆盖所有资金写者：先按账户币种锁齐余额，再按 ID 锁预占。

PostgreSQL 返回 40P01 后，阿宁清理整个旧事务，以原 T100 和载荷重新争身份、读数据、校验并生成账务，不只补发最后一条 UPDATE。她先释放连接，再进行有上限的随机退避。若换成 MySQL，对 1205 更不能想当然：默认可能只撤掉超时语句，前面的修改还在，所以应用明确回滚整笔。COMMIT 断网则另走未知核验，不能当确定失败。

为防重试污染外部，成功通知改由同事务 outbox 留下，真正提交后再交付；在线预算耗尽，既定成交仍由持久恢复继续，HB/HS 不因超时释放。阿宁也不再用无限加连接治疗热点：同一余额行本就串行，应缩短事务、限流和有界排队。锁序消除一类等待环，重试恢复被拒绝的尝试，都不是凭空增加热点账户写容量的办法。

**流程位置与核心机制：** 从 T100 涉及的多余额锁推演死锁，随后区分数据库错误、整事务重试和不可盲重试的提交未知。最终解释热点单行的物理串行化，避免把“加重试”当吞吐方案。

**沿用总览基线：** 链下托管 BTC/USDT，T100 已确定成交 0.1 BTC、3000 USDT。PostgreSQL 16 RC，Go 1.21+ `database/sql`；BTC `1e8`、USDT `1e6` 整型最小单位。四条余额预建，余额、四条分录、HB/HS、唯一 settlement 与 outbox 整体提交。所有资金写者按 `(account_id, asset)` 升序逐条锁全部余额，再按 hold_id 升序锁 hold。Redis 7.x 不能代替数据库裁决；MySQL 只在明确标记的段落对比。

## 第 1 层：两个事务怎样形成真正的死锁？

**面试官：** T100 要改多条余额，另一个事务也改相同账户。怎样区分普通锁等待与死锁？

**面试者：** 我用一个故意违反基线锁序的反例说明，不把它当正确实现。事务 A 处理 T100，先锁 X=101/USDT；事务 B 是另一笔触及这些余额的账务事务，先锁 Y=202/BTC。随后 A 要 Y，被 B 阻塞；B 又要 X，被 A 阻塞，就形成等待环。只出现 A 等 B、B 能继续提交，是普通等待，不是死锁。这里 B 不是 T100 的重复处理者，避免把唯一身份上的等待和资产行锁竞争混为一谈。下面仅省略各事务其他余额行，不改变“一笔成交全部余额与 hold 同事务”的要求。

```text
A 持有 X，等待 Y 的持有者 B
B 持有 Y，等待 X 的持有者 A
等待关系：A → B → A
```

## 第 2 层：固定锁序怎样拆掉等待环？

**面试官：** 既然问题是互相等，把 T100 的两条锁交换顺序就够了吗？其他余额和 hold 怎么办？

**面试者：** 不能只修一个调用点，必须让结算、预占、释放、人工修复等所有资金写者服从同一协议。T100 先按 `(account_id, asset)` 升序逐条锁 101/BTC、101/USDT、202/BTC、202/USDT，再按 hold_id 升序锁 HB、HS；拿齐后才做相互依赖的校验和更新。这样针对这类资源的等待都朝同一个方向，不能形成反向环。不能假设任意 IN 查询自然按列表顺序加锁，也不能先拿 hold 再补锁 balance。唯一身份、外键和其他资源也可能参与死锁，因此应统一相关获取顺序，固定资产锁序能大幅消除该类环，但不承诺数据库里再无死锁。

## 第 3 层：PG 检测出死锁后，应该重试哪一段？

**面试官：** 你仍保留了死锁处理。PostgreSQL 返回 40P01 时，能不能只重发刚才失败的 UPDATE？

**面试者：** 不行，`40P01 deadlock_detected` 表示数据库选中一个牺牲事务以打破等待环，这次事务不能继续沿用。应用应清理旧 `*sql.Tx`，重新 BeginTx，并完整重做身份竞争、锁定、读取、业务判断、分录与结果生成，最后重新提交，而不是只重发最后一条 UPDATE。独立改用 PostgreSQL RR 或 Serializable 后遇到 `40001 serialization_failure`，也需要同样的整事务重试。重试保持 T100 和原 payload 不变，不能拿旧快照里的金额或旧 version 拼接新写入。若 hold 与确定成交不一致，那是需隔离修复的业务完整性问题，不是无限重试即可解决。

## 第 4 层：55P03、超时和提交断网都能按死锁处理吗？

**面试官：** 你按错误码重试事务。那锁拿不到、语句超时、context 取消和 Commit 断网，是不是也统一放进同一个重试分支？

**面试者：** 要分开。PostgreSQL `55P03 lock_not_available` 常见于 NOWAIT 或 lock_timeout，`57014 query_canceled` 可对应语句超时或取消，它们不证明有等待环，也不代表业务余额不足；在无 savepoint 的普通事务里要回滚并清理，再按策略决定是否重试。Go 还可能先得到 context 错误，需结合阶段判断。尤其 Commit 网络错误不能当作明确回滚后重试：结果可能已提交，必须新连接按同一 T100 查询权威主库并走幂等恢复，暂时未查到也不证明失败。不能把“可重试”简化成“所有 err 都重新扣一次”。

## 第 5 层：MySQL 1213 和 1205 的回滚范围一样吗？

**面试官：** 如果数据库换成 MySQL 8.0 InnoDB，同样把死锁和锁等待超时视为整个事务已撤销，是否正确？

**面试者：** 这是独立数据库对比，不能沿用 PostgreSQL 的失败事务语义。InnoDB 死锁错误 1213 通常会选择并回滚整个牺牲事务；锁等待超时 1205 在默认 `innodb_rollback_on_timeout=OFF` 下通常只回滚超时的那条语句，之前成功的修改及其锁仍可能留在事务中。若错误处理直接提交，就可能提交半笔业务。无论默认机制撤销多少，我的应用策略都是显式回滚本次业务事务，再按条件整事务重试；开启 rollback_on_timeout 会改变超时回滚范围，也应明确配置。不能因为 MySQL 常见 RR，就把 PG 的锁、错误码或快照行为混用过来。

## 第 6 层：Go 中怎样设计有界、可取消的重试？

**面试官：** 整事务重试的原则明确了。Go 服务怎样避免重试风暴，还能保证 T100 最终被恢复？

**面试者：** 我会把一次完整数据库事务作为尝试单元，错误分类后先回滚、释放连接，再做带随机抖动的指数退避，并设置最大次数、退避上限和总时间预算。每次尝试显式用 PostgreSQL RC，新建 Tx、沿用同一 trade_id 和 payload_hash，重新读取判断，不在持锁时睡眠。退避等待也监听 context，取消就结束当前请求，不在后台偷偷无限续跑。已确定成交不能因请求预算耗尽而丢掉：把状态保持为待恢复或未知，由有持久来源的恢复流程继续处理，不能释放 HB/HS。唯一冲突、参数冲突、业务不一致和提交未知各走自己的分支，不只看错误字符串重试。

## 第 7 层：重试函数里能不能顺便发通知或扣外部款？

**面试官：** 你会重新执行整个函数。如果第一次已发“入账成功”通知，事务随后死锁，重试不是又发一次吗？

**面试者：** 所以重试闭包内只能放可随事务回滚的数据库动作和无外部副作用的计算，不能夹带 HTTP 扣款、发邮件或直接发布成功通知。T100 的 outbox 与账务同提交，只有真正提交的尝试留下 `T100:applied` 交付义务；失败尝试连同其 outbox 回滚。交付者在事务外执行可靠失效和结果通知，允许重复并由事件身份处理，不能再用本地事务包住外部网络来宣称原子性。Redis 更新失败也不回滚已提交账务，缓存可丢；若新增外部支付，就已经改变这个单库模型，需要另定义外部幂等与恢复契约。

## 第 8 层：锁序正确且能重试，为什么热点仍然慢？

**面试官：** 如果已经没有明显死锁，但大家都在更新同一个大账户，继续增加 goroutine 和重试次数会提升吞吐吗？

**面试者：** 往往只会扩大排队和连接占用。对同一余额行的互斥写入存在物理串行化点，固定锁序解决等待环，不消除资源竞争；CAS 也仍要更新同一物理行。我会先缩短持锁事务、移出网络和重计算、检查索引与锁等待来源，再用有界并发、入库前排队和限流降低无效竞争。单账户队列能改善调度，但跨多个账户仍须遵守全体锁序和事务边界。把资产拆成多个额度桶属于独立规则改造，必须先解决额度分配与守恒，不能直接多写几行余额。Redis 协调只优化负载，最终资产约束仍在 PostgreSQL。

## 收束：机制、边界与反例

- **讲透的机制：** 等待图识别死锁，全写者固定资源顺序，PG 40P01/40001 整事务重试，错误分类和 bounded jitter 约束重试成本，热点通过调度与缩短临界区改善。
- **易错边界：** 55P03 不等于死锁，Commit 断网不等于回滚；MySQL 1205 默认只撤销当前语句；可取消的在线请求与必须继续恢复的已确定成交是两个生命周期。
- **反例检验：** 第一次尝试先发成功通知，随后被选为死锁牺牲者，第二次再发一次。即使数据库最终只有四条分录，外部观察仍已被错误污染，说明副作用越过了可重试边界。
