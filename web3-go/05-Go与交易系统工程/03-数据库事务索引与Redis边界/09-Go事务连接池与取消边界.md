# 大问题 9：Go 如何正确管理事务、连接池、取消与提交边界？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| database/sql | Go 标准库提供的数据库连接与事务管理接口。 | 本文讲生命周期，不提供可运行工程，具体错误还要由驱动识别。 |
| *sql.DB / 连接池 | 可供并发请求借用数据库连接的入口。 | 它不是专属连接，多次 db 调用不保证属于同一会话或事务。 |
| BeginTx / *sql.Tx | 开启事务并将操作绑定到一条事务连接。 | T100 的余额、分录、hold、结果和 outbox 全部通过同一 tx 操作。 |
| 事务执行器 / helper | 显式接收事务能力的下层辅助函数。 | helper 不能偷用全局 db，也不能擅自提交或重新开启本次业务事务。 |
| 事务逃逸 | 看似在事务里，某条 SQL 却跑到另一连接单独提交。 | 中途调用 db.ExecContext 可能使一部分账务无法随其余步骤回滚。 |
| RowsAffected | SQL 真正更新的行数。 | 条件不足时可能零行但无 SQL 错误，关键更新必须确认恰好一行。 |
| Scan / rows.Err / Close | 读取查询结果、检查遍历错误与释放结果资源。 | 不只检查 Query 返回值；下一语句前还需处理好未消费结果集。 |
| defer Rollback | 函数退出时尝试结束未完成事务的清理安排。 | 成功 Commit 后不会撤销账务，也不能证明提交网络错误已被回滚。 |
| 单连接 / goroutine 并发 | 多个 Go 执行流不等于多条事务 SQL 通道。 | 不靠四个 goroutine 共用 tx 提速，避免打乱显式锁序和错误归属。 |
| context / 事务生命周期 | 控制等待预算，并触发库与驱动的取消处理。 | BeginTx 的取消会安排回滚，但取消与提交竞争时仍须判断真实结果。 |
| Commit 错误 / UNKNOWN | 提交未确认，事务内结果不能当成功事实使用。 | 通信失败按原 T100 查主库；不返回尚未证实提交的余额。 |
| SQLSTATE / 整事务重试 | 用数据库错误分类决定是否重新开始完整尝试。 | 明确冲突结束旧事务后再重试，提交未知不能混进普通重试分支。 |
| 池上限一 / 资源循环等待 | 事务占唯一连接，却等 helper 再借第二条连接。 | helper 等连接，外层等 helper，数据库行锁图未必能看到这个环。 |
| db.Stats / WaitCount、WaitDuration | 连接池占用与等待情况的统计。 | 结合增量、追踪区分池前等待和库内阻塞，不只盯慢 SQL。 |
| SetMaxOpenConns / 关闭恢复 | 限制连接预算，并有序结束服务工作。 | 池不是越大越好；停接新任务后让当前尝试收敛，未知成交保留恢复途径。 |

## 把整篇文章压缩成一个故事

阿宁用 Go 实现 T100：小林以 3000 USDT 换小周 0.1 BTC。她已经 BeginTx，却发现一个写预占的 helper 仍调用全局 db。那条 SQL 可能在另一连接单独提交，破坏四腿账务、余额和 hold 的共同回滚；池上限设成一时更糟，helper 等第二条连接，外层等它返回，连数据库死锁图都看不到完整依赖。

她让相关函数显式接收同一个 tx，按顺序锁余额再锁预占，逐项检查 Scan、RowsAffected 和遍历错误，及时关闭结果集。SQL 返回 nil 不代表条件更新成功，零行必须停下。四个 goroutine 共享 tx 也不会变出四条独立 SQL 通道，反而让锁序和错误处理更难判断。只有所有检查通过并确认 Commit，才能把结果称为 APPLIED。

客户中途断线时，context 会触发取消与回滚安排，但若 COMMIT 已发出、应答丢了，不能据此宣布没入账。阿宁丢弃未确认的事务结果，按原 T100 用受管理的恢复流程查主库，不依赖 defer Rollback 证明远端撤销。明确可重试冲突先结束旧事务再退避；服务关闭则停接新任务、等待收敛并保留未知义务。资源能释放与钱只记一次，必须分别闭合。

**流程位置与核心机制：** 把同库原子入账落到 Go 的 `database/sql` 生命周期，说明连接归属、资源释放、错误分类和超时；幂等协议与死锁重试分别引用第 5、6 题。

**必要前提：** Go 1.21+、PostgreSQL 16、RC；通过实际驱动识别 SQLSTATE。这里只解释实现选择，不增加可运行项目或第二个 MVP。

## 第 1 层：事务属于一条连接，不属于任意 db 调用

**面试官：** 在 Go 里实现 T100 入账，你怎样确保四条余额、分录和预占都属于同一个事务？

**面试者：** 我用 `db.BeginTx(ctx, opts)` 取得 `*sql.Tx`，立即安排 `defer tx.Rollback()`；属于本次账务的所有读写都通过这个 tx 执行。任何语句失败都停止正常路径，只有所有检查通过才调用 Commit，并检查它的返回值。成功提交后的延迟 Rollback 不会撤销已提交结果。

`*sql.DB` 是并发安全的连接池抽象，不是一条专属连接；`*sql.Tx` 才把操作绑定在事务连接上。事务已开始后再调用 `db.ExecContext`，那条语句可能在另一条连接上、事务之外提交，破坏共同提交边界。手工向 db 发 BEGIN 再发若干 SQL 也不能依赖连接池恰好分配同一连接。

## 第 2 层：怎样避免 helper 悄悄逃出事务

**面试官：** 你的 repository 原来都接收 db，你说统一改用 tx，怎么防止底层某个 helper 仍旧直接查 db？

**面试者：** 我会让需要执行本次账务的函数显式接收事务执行器，只暴露所需的 QueryContext、QueryRowContext 和 ExecContext 等能力，或直接接收 `*sql.Tx`。不要让 helper 在内部读取全局 db 后自行开始或结束事务；谁创建事务，谁拥有提交与回滚决策。

同时明确接口语义：返回“执行成功”不是“事务已提交成功”，不能让中间层提前发布 APPLIED。审查时沿调用链检查余额、预占、分录和 outbox 是否都使用同一个执行器。抽象接口只是帮助表达约束，不会自动证明实现没有逃逸；针对事务外写入的故障窗口仍需静态审阅和后续受控验证。本专题只交付面试稿，不把这些验证说成已经完成。

## 第 3 层：SQL 没报错为什么仍可能失败

**面试官：** helper 都接收 tx 了，Exec 返回 nil 是不是就能继续提交？

**面试者：** 不够。条件更新 `WHERE available >= amount` 在条件不满足时通常不报 SQL 错误，而是影响零行；我要检查 `RowsAffected()` 本身的错误和实际行数是否等于一。预占状态转换、完整结果更新也都要检查行数，不能把“命令执行成功”当成“业务条件满足”。

查询也有资源与错误边界：QueryRow 的错误由 Scan 暴露；遍历 Rows 后要检查 `rows.Err()`，并及时关闭 Rows，不能只检查创建迭代器时的错误。在同一连接发下一条语句前，应结束未消费的结果集，具体驱动限制也要考虑。任一关键检查失败都回滚整笔，不能留下前两条余额变化再返回“后续重试”。

## 第 4 层：同一个事务并发跑四条 UPDATE 会更快吗

**面试官：** 四行更新互相独立，我能在四个 goroutine 里共用同一个 tx 来减少耗时吗？

**面试者：** 我不会用这种方式实现基线。事务使用同一数据库连接，不意味着能把它变成四条独立并行执行的 SQL 通道；驱动和协议还可能限制未消费结果时继续发命令。更重要的是并发发语句会破坏我们显式约定的锁顺序，使错误处理、取消与结果归属更难推理。

我按统一顺序取得全部必要余额锁，再取得预占锁，完成校验后顺序写入。需要减少往返时，可以讨论参数化批量语句或受控服务端逻辑，但必须证明锁序、逐行条件和原子边界没有改变。Go API 即使在某些使用上是并发安全，也不等于这种事务组织更快、更符合业务顺序。

## 第 5 层：请求取消不等于已经确认业务回滚

**面试官：** 如果客户端断开，context 被取消，Go 不就会自动回滚了吗？为什么还要讲未知提交？

**面试者：** BeginTx 的 context 用于事务生命周期，取消后 `database/sql` 会安排回滚，后续操作和 Commit 也可能报错；Context 方法还让驱动有机会取消当前操作。但我不会把所有阶段的 `context canceled` 或超时都映射成“数据库肯定没发生变化”。

在明确尚未进入提交、驱动已经完成回滚的场景，可以按确定失败处理。若 COMMIT 已发出而响应丢失，或者取消与提交发生竞争，调用方必须按提交协议判断，不能仅凭请求 ctx 状态否定已提交结果。对上游保留 T100 身份，让独立的恢复流程用有界生命周期查询主库事实；不是无限使用已取消 ctx，也不是随便启动脱离管理的后台 goroutine。

## 第 6 层：Commit 返回错误后为什么不能相信之前的结果

**面试官：** 既然 SQL 都返回了更新后的余额，Commit 失败时先把这些余额返回给用户，再异步核验行不行？

**面试者：** 不行。事务中读到的更新结果包含本事务尚未确认提交的修改；Go 官方要求 Commit 失败时丢弃事务查询和执行结果，不能把它们当成功事实返回。我要分类已知的事务拒绝与无法确认的通信失败：前者回滚并按规则重试，后者返回 UNKNOWN 并以原 trade_id 查询或重入。

恢复者查到已提交 APPLIED 后才能返回持久结果，不能把内存里那份 result 直接包装成成功。即使 defer Rollback 随后执行，也不能据此断言撤销了一个可能已经提交的事务。这里安全依赖数据库的唯一身份和完整原子结果，而不是依赖 Go 错误字符串猜测远端状态。

## 第 7 层：连接池耗尽怎样制造应用层死锁

**面试官：** 你已经避免数据库行锁死锁，为什么服务仍可能卡住，数据库里还看不到等待图？

**面试者：** 可能是应用拿着事务连接，又去调用需要另一条池连接的 db 方法。假设池上限为一，当前事务已占用唯一连接，helper 的 db.Query 会等待新连接；外层又等待 helper 才能提交释放旧连接，形成池资源层面的循环等待，数据库无法看到完整依赖。

我会看 `db.Stats()` 的 InUse、Idle、WaitCount 和 WaitDuration 及其增量，结合请求追踪确认是在池前等待还是库内等待。SetMaxOpenConns 是全服务实例共享数据库容量的预算，不是越大越好；还要设置合理的空闲与连接生命周期，防止连接泄漏和同步重连。加大池可能暂时隐藏错误调用链，但不修复事务逃逸或连接依赖。

## 第 8 层：怎样把重试、预算和退出收成闭环

**面试官：** 那最终你怎样组织事务重试与服务关闭，避免取消、连接池和重复入账互相放大？

**面试者：** 我让一次尝试拥有完整事务生命周期；明确的可重试冲突结束旧事务后，才按剩余请求预算、有界次数与随机退避开启新事务，始终使用原 trade_id。未知提交进入核验，不冒充普通失败重新生成业务身份；事务中不做不可回滚的外部副作用。

服务关闭先停止接收新的入账任务，再在受控截止时间内等待当前尝试收敛，对无法确认的 T100 保留上游重投与恢复途径，最后释放连接池资源。监控同时看池等待、长事务、冲突重试、未知结果数量与账务不变量，而不是只看 HTTP 成功率。手工反例是“池上限一加事务内误用 db”和“Commit 回包丢失后原身份重入”，两者能检验资源归属与业务幂等是否真的独立闭合。

## 本题收束

- **讲透的机制：** 同一 tx 绑定连接与提交边界，错误和影响行数都要检查，资源预算与恢复协议相互配合。
- **最容易答错的边界：** defer Rollback 不是提交成功后的撤销；请求取消不自动证明 COMMIT 没生效。
- **验证反例：** 把连接池限制为一，检查事务内 helper 是否仍调用 db；把 Commit 响应视为丢失，检查代码是否错误返回未确认余额。
