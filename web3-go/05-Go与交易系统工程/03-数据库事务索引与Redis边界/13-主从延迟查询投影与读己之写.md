# 大问题 13：主从延迟下怎样实现读己之写，并证明查询投影真的追到了同一个水位？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 读己之写 | 确认自己提交后，后续读取不再倒退到该写之前。 | 不等于永远返回 T100 那一刻的历史余额，后续合法交易也可能已生效。 |
| settlements/result / 当前余额 | 某笔成交的持久结果，与现在账户状态不同。 | 查 T100 原结果读 result；查现有可用余额要接受后续变化。 |
| 异步物理副本 / replay | 数据库复制日志后再重放成可查询状态。 | 收到或落盘 WAL 不等于已重放，旧冻结不证明主库结算失败。 |
| 主库 RC 新语句 | 到同一有效主时间线读取新的语句快照。 | 确认提交后绕过缓存读主，可避免本次提交前的状态；多语句仍非组合原子快照。 |
| WAL / LSN | 数据库恢复日志与其中的位置标记。 | 可用于同一有效复制历史里的因果等待，不是随意跨集群比较的数字。 |
| pg_current_wal_insert_lsn | 在主库采样当前 WAL 插入位置。 | 提交确认后采样可给出不早于本次提交的保守位置，不能用事务内旧采样冒充。 |
| pg_last_wal_replay_lsn | 物理副本已经重放到的位置。 | 达到因果 token 后再开启读取的新快照，不继续用追赶前旧视图。 |
| 因果 token / 时间线代际 | 让读者证明已包含某次写的凭据及其所属历史。 | 绑定集群和拓扑，切主后需验证历史关系，超预算就回主或明确不可读。 |
| 查询投影 / application cursor | 独立处理业务变更的视图及完整应用进度。 | 物理副本追上不代表外部投影追上，数据和游标须共同提交。 |
| 完整前缀 / MAX(id) | 此前每笔都已完整处理，与看过最大号不同。 | 101 先到不证明 100 已完成，多分区需各自前缀与屏障。 |
| 快照与增量配对 | 重建的初始视图和随后变更有无缝对应关系。 | 普通全表扫描再从最大 ID 消费，可能留下永久缺口。 |
| CDC / 完整事务批次 | 从数据库交付变更，并保持同事务的全部变化边界。 | T100 四腿不能只放买方就推进游标；只含缓存键的 outbox 也不是完整账务流。 |
| 投影代际 / keyset 游标 | 标识使用哪一代视图，以及按哪个稳定键继续翻页。 | 追到水位不冻结列表，完整导出还要固定集合或快照，旧游标不能静默跨代际。 |
| 新鲜度 / 原子裁决 | 读得新，与读后还能独占使用是不同能力。 | 资金准入仍在主库锁内或条件更新中决定，投影不能批准冻结。 |
| 当前授权 / 租户范围 | 现在是否能看，以及数据属于谁。 | 缓存键和游标要绑定访问范围，旧投影不能替代每次请求的当前授权。 |

## 把整篇文章压缩成一个故事

T100 已确认入账，小林马上刷新，却从副本看到 USDT 仍冻结 3000。客服阿宁不据此重扣或退款：主库已完成 0.1 BTC 与 3000 USDT 的交换，异步副本只是还没重放。她先展示 T100 的持久结果，把即时核验路由主库并绕过缓存；当前余额若已经包含后续合法交易，也不是违背读己之写，它本来就不同于成交时的历史截图。

为减轻主库读取，她在提交确认后从同一主节点取得保守 WAL 位置，绑定集群和时间线，让副本重放达到后再建立新查询快照。超预算就回主或明确暂不可读，不能只等固定几百毫秒碰运气。外部汇总投影还要证明自己的完整应用前缀：数据与游标一起提交，T100 四腿处理齐才推进，看到最大 ID 也不能推断较小编号没有晚提交。

投影损坏时，阿宁把一致快照与变更起点配对，按完整批次恢复后切新代际，不拿缓存失效事件假装完整 CDC。即使投影追上，实时翻页仍可能变化，完整导出需另固定集合；每次读取也仍做当前授权。更重要的是，读得再新也不等于锁住这笔钱，资金准入仍在主库事务里裁决。复制进度、投影进度、跨页快照与资产写权，不能合成一句“数据够新就安全”。

**流程位置与核心机制：** 本题讨论账务提交后的查询可见性，区分主库、副本、缓存与异步投影的保证。基线是链下托管 BTC/USDT、PostgreSQL 16 RC、Go 1.21+ `database/sql`；Redis 7.x 是可丢的弱一致缓存。T100 已确定成交 0.1 BTC × 30000 = 3000 USDT，无手续费；BTC、USDT 分别以 1e8、1e6 最小整型单位存储，四行余额预先存在。物理副本与额外查询投影是不同的可选读路径，不能混为同一组件。

## 第 1 层：提交成功，为什么紧接着查询却像没成交？

**面试官：** T100 结算返回成功，用户马上查余额，副本仍显示买方 frozen USDT 3000。是不是数据库事务没生效？

**面试者：** 不能只凭副本旧读作这个判断。结算成功表示主库同一事务已提交 settlements、四条分录、四行余额、HB/HS 消费以及 outbox，不表示异步副本、Redis 或查询投影已追上。成功后买方 USDT 是 available 7000、frozen 0，BTC 是 0.1；卖方 BTC 是 available 0.4、frozen 0，USDT 是 3000。副本尚未重放提交记录时，仍可能看到提交前的完整旧状态，而不是部分结算。需要即时确认时，可以先展示权威结算 result，并把相关查询路由主库。若 Commit 本身断网，情况则是 unknown，必须按原 trade_id 查主库或重入恢复，不能把副本暂时查无结果当成没有提交。

## 第 2 层：强制读主库究竟保证到哪一步？

**面试官：** 你说查询改读主库就能确认，那“读己之写”是不是意味着永远读到 T100 提交时那份余额？

**面试者：** 不是。确认 Commit 成功后，在同一有效主时间线的新语句中读主库，可以避免读到 T100 之前的状态，但并发的后续充值、交易或冻结也可能已经提交，所以结果不一定等于 T100 的历史余额截图。要查该成交结果应读 settlements/result，要查当前可用余额则接受后续合法变化。RC 的快照按语句取得，多条 SELECT 即使都读主库，也不自动构成同一时刻的组合快照；相关行可用一条查询读取，需要跨语句稳定视图时明确选择快照事务。Go 中要把查询送到主库连接池并绕过缓存，不能只给请求加一个标记、实际仍被路由副本。异步切主若丢失已确认写，原保证也不再成立，需由高可用的数据保留合同另行闭合。

## 第 3 层：如何让副本带着因果条件再接查询？

**面试官：** 主库读流量很大，能否给 T100 的响应带一个位置，让副本追到这里再回答，避免固定等待几百毫秒？

**面试者：** 对 PostgreSQL 物理副本，可以在确认提交之后，从同一主节点取得不早于本次提交记录的 WAL 位置，作为保守的因果 token；例如提交后再采样 `pg_current_wal_insert_lsn()`，它可能包含其他事务进度，但不会因此不安全；这里取插入位置作为保守上界，不把尚未推进的写盘或刷盘位置误当作本次提交的覆盖证明。不能把事务内提前采到的位置当成自己的提交位置。副本必须确认 `pg_last_wal_replay_lsn()` 已达到 token，再开启读取所用的新快照，不能只看接收或落盘位置，也不能复用追赶前的旧快照。token 还要绑定集群身份和主时间线／拓扑代际；同一主时间线上的位置才有这项比较意义。切主后需验证祖先关系与数据保留，或废弃 token、重新走权威确认，不能只比较 LSN 数值。等待超预算就回主库或明确暂不可读。

## 第 4 层：物理副本追上，为什么查询投影仍可能没追上？

**面试官：** WAL token 能确认副本已重放，那么外部订单列表或账户汇总投影，也能拿同一个 token 直接宣布已追上吗？

**面试者：** 不能，因为物理重放证明的是副本数据库状态，外部投影还有独立的接收、转换与应用过程。投影需要 application cursor，表示某个有序输入中一个完整前缀的事务已全部应用，而且投影数据与游标共同提交；仅收到事件、完成部分分区或记下见过的最大 ID 都不够。比如先分配到 100 的事务尚未提交，101 先提交并投影，`MAX(id)=101` 并不证明 100 已处理，序列空洞也可能来自回滚。多分区可以维护各分区完整前缀和屏障，不能伪造一个最大值代表全局完成。T100 内的四条账务变化必须作为完整事务批次处理，不能买方已更新就推进整个批次游标，让卖方还停在旧状态。

## 第 5 层：从快照重建投影，怎样不漏掉夹在中间的写？

**面试官：** 游标要求完整前缀，那投影损坏后先全表扫描、再从最大事件 ID 继续消费，能否恢复这个保证？

**面试者：** 不能，普通全表扫描与增量起点之间可能有缺口，也可能重复覆盖。需要把一致性快照与变更流起点按数据库支持的协议配对，例如建立逻辑复制一致点及对应快照，保留这之后的变更；先装载快照，再按事务边界应用后续完整增量，最后原子切换查询代际。重复批次按稳定身份去重，数据更新与游标推进共同提交。主基线的 `T100:applied` 只有四个缓存键和各自版本，事件 version=1 不是全局水位，也不是完整账务增量。拿它做按需回源可以收敛展示，但不能直接重建精确历史投影；若要求那种能力，就要显式增加完整 CDC 或可审计业务变更流，不能凭现有失效消息声称已经实现。

## 第 6 层：投影追到水位后，分页为什么还会重复或漏项？

**面试官：** 假设投影已经追到完整前缀，用户翻订单或流水列表，为什么仍可能出现上一页的记录再次出现在下一页？

**面试者：** 因为水位保证某些变化已经纳入，不保证翻页期间集合不再变化。offset 分页遇到新插入或状态更新会移动位置；改成按 `(created_at, stable_id)` 的 keyset 能减少位移，但若排序字段可变，或列表由持续变化的“当前状态”过滤，也不自动提供一致快照。要承诺完整且不重复的历史导出，可以固定截止业务集合和投影代际，在不可变排序键上分页，或者使用受控的一致性快照；游标中绑定这些条件和授权范围。长事务快照会增加资源与清理压力，不能无限保持。普通实时列表也可以选择较弱合同，明确刷新可能改变内容。不能一边允许快照变化，一边宣称单靠一个 last_id 就得到跨页全局一致结果。

## 第 7 层：既然能等到投影追上，资金准入能否改读投影？

**面试官：** 你已经能固定完整前缀和分页快照，为什么不直接从这个“足够新”的投影判断账户是否还能预占资金？

**面试者：** 因为新鲜读取仍不等于原子裁决。读完投影到执行冻结之间，其他请求可能已经消费余额；哪怕读取主库后无条件扣减，也同样有检查与使用的窗口。资金准入只能在主库事务里锁定或条件更新权威余额，并统一遵守先按 `(account_id, asset)` 升序锁全部余额、再按 hold_id 升序锁 hold 的顺序。比如原 available USDT 7000 上，R1 请求预占 7000、R2 请求预占 4000，不能因两者都读到 7000 就都成功；原 frozen 3000 属于 HB，也不能被新请求挪用。投影适合展示、检索与分析，因果 token 只改善读体验，不替代互斥、不变量和成交身份幂等。

## 第 8 层：投影恢复与权限变化，应该怎样一起处理？

**面试官：** 资金继续留在主库，那投影落后、重建甚至权限撤销时，查询系统还需要守住哪些边界？

**面试者：** 要把新鲜度与授权分开。查询应暴露受控的投影代际、水位或更新时间，落后时可降级到受限主库查询、返回暂不可用，不能无限回源挤占结算资源。重建采用旁路新代际，核验完整批次和截止集合后再切换，旧游标不能静默跨代际复用。投影和缓存键必须包含账户、租户及必要的访问范围；每次请求都做当前授权校验，不能把旧投影里的“曾经有权限”当成当前凭证。失效、撤权和数据清理也要覆盖重建副本与导出文件。即使投影已追上业务游标，授权服务不可用时也不能自动放宽敏感数据访问。这里保护的是查询正确性和隐私，不改变数据库里的资产归属。

## 本题收束

- **讲透的机制：** 主库读己之写、物理 WAL replay 条件、投影 application cursor 和跨页快照是不同层次；各自必须说明完成边界、代际与故障策略。
- **最容易答错的边界：** 提交成功不等于副本或缓存可见；接收 WAL 不等于重放；最大流水 ID 不等于完整提交前缀；水位够新也不能让投影承担资金准入。
- **检验反例：** 让小 ID 事务延迟提交，大 ID 事务先被投影，再把最大 ID 当恢复起点。若小 ID 此后被永久漏掉，就证明游标没有覆盖完整前缀；正确恢复应依靠配对快照与事务变更流，而不是补猜序列号。
