# 大问题 10：数据库提交成功后，怎样处理缓存失效失败、旧值回填与故障恢复？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| APPLIED / 展示滞后 | 账已经提交，与页面是否追上是两件事。 | T100 完成后缓存仍旧，不能据此重扣、取消成交或覆盖主库。 |
| cache-aside | 先查缓存，未命中再查数据库并尝试回填。 | 基线供普通余额展示使用，资金裁决仍回 PostgreSQL 主库。 |
| 提交后 DEL | 权威新值已经提交，再删除派生缓存。 | 减少先删后写的竞态，但不能消灭早先读到旧值的迟到回填。 |
| outbox / 失效义务 | 随账务共同保存的待交付任务。 | T100:applied 让进程崩溃后仍能找回四个余额键的删除工作。 |
| event.version / balance.version | 一笔成交事件的版本与各余额行自己的版本。 | 事件版本 1 不是四行余额的共同版本，更不是全局提交水位。 |
| delivery_state | 记录通知交付进行到了哪里。 | 四键集合全部处理成功后再确认，不能先标完成再去删除。 |
| 至少一次 / 重复 DEL | 未确认任务可再次交付，删除可重复执行。 | 部分成功或确认丢失就重删整个集合，不因此重复改资产。 |
| 旧值回填 / v、v+1 | 读者拿着旧版本暂停，稍后又塞回缓存。 | T100 提交 v+1 并删完后，读者仍可能把先前的 v 写回来。 |
| TTL / 随机 TTL | 缓存写入后的寿命与打散过期时点的策略。 | 普通相对 TTL 从 SET 起算，不无条件限定相对数据库提交的陈旧时长。 |
| 延迟双删 | 过一段经验时间再删除一次。 | 只能覆盖有限时间窗，不能保证暂停很久的读者已结束。 |
| deadline / 剩余寿命 | 将源读取时确定的绝对失效点带到缓存准入。 | 属于加强策略，过期不回填、不滑动续命，还依赖时钟与读源条件。 |
| watermark / 版本水印 | 拒绝比已知可信下限更旧的缓存版本。 | 需要失效与回填脚本共同执行规则，只有 version 字段加 DEL 不够。 |
| Redis Cluster 同槽 | 多键脚本原子操作所需的分区位置约束。 | 水印和值需同槽；四个余额键跨槽时不能假装一次多键 DEL 原子完成。 |
| 缓存代际 | 重建后给一批缓存及请求换一个有效世代。 | 水印丢失或旧快照恢复时，可拒绝旧代际迟到回填，不直接沿用旧保证。 |
| 回源预算 / 合并同键 | 控制查主库的并发、连接和队列，重复查询尽量合并。 | Redis 全挂不能把展示流量无限倒给主库、挤垮结算。 |
| 提交 UNKNOWN | 通信失败时暂不能确认入账结果。 | 按原 T100 查主库或重入，不以缓存、超时或删除结果推断是否提交。 |

## 把整篇文章压缩成一个故事

T100 已经把小林冻结的 3000 USDT 换成 0.1 BTC，小周收到 3000 USDT，四腿账务与 HB/HS 消费在主库一起提交。小林页面还显示旧冻结，失败的是展示追赶，不是成交本身。服务采用提交后删缓存，并把四键失效任务同事务写进 outbox；即使提交后进程立刻退出，恢复扫描器也能继续删除，不能把旧页面反写到账本。

但有个读者早已读到版本 v，然后暂停。T100 提交 v+1、DEL 成功、任务也确认后，它才醒来 SET v，于是旧值重新出现。再加一分钟 TTL 也不能保证“提交一分钟后绝不旧”，因为寿命从这次迟到 SET 才开始；随机 TTL 只打散过期，延迟双删也不是证明。事件带 v+1 只是信息，没有拒绝旧回填规则就挡不住它。

若业务要更强展示，需明确引入绝对截止或水印准入，并处理水印淘汰、故障回退及缓存代际；这些不是基线已有能力。基线仍允许弱一致，四键只删成两个就保留任务重试，跨槽不伪装原子删除。Redis 全挂时，展示回源必须有独立预算和有界排队，不能挤垮资金事务，更不能改读缓存批准扣款。正确性留在主库，展示降级也要受控。

**流程位置与核心机制：** 本题从 T100 已确定成交后的账务提交，追到展示缓存失效、重试、旧值回填和冷启动保护。沿用链下托管 BTC/USDT、PostgreSQL 16 Read Committed、Go 1.21+ `database/sql`、Redis 7.x；Redis 可丢，不是资产真相。金额分别以 BTC 的 1e8、USDT 的 1e6 最小单位整数存储，文中的 0.1 BTC、3000 USDT 是便于复述的展示单位。

## 第 1 层：提交与展示不一致，究竟算哪一部分失败？

**面试官：** T100 已在数据库结算成功，但 Redis 还显示旧余额。你怎样定义这个结果，第一步该做什么？

**面试者：** 我会把账务完成与展示更新分开。T100 是买方 101 用 3000 USDT 买入卖方 202 的 0.1 BTC，无手续费；数据库必须在同一事务提交成交身份、四条分录、四行余额、HB/HS 的恰好消费以及 outbox。提交后，买方 USDT 是 available 7000、frozen 0，BTC 是 0.1；卖方 BTC 是 available 0.4、frozen 0，USDT 是 3000。缓存仍旧只说明查询投影滞后，不能回滚成交或让缓存覆盖数据库。本基线采用 cache-aside：读缓存未命中才查库，写路径先提交数据库，再删除相关缓存。普通展示允许暂时旧，资金准入和冻结判断必须查主库并在事务中裁决。

## 第 2 层：提交后删除失败，谁负责把失效任务找回来？

**面试官：** 你说先提交再删除，如果进程恰好在这两个动作之间崩溃，单靠接口里的重试够吗？

**面试者：** 不够，因为接口重试也会随进程一起消失。结算事务要同时写入 `event_id=T100:applied`、`aggregate_id=T100`、`version=1` 的 outbox 事件，payload 列出四个 balance 键及各自更新后的余额版本。事件版本 1 只属于 T100 这个聚合，不是四行余额的版本，更不是全局提交进度。事务提交前填好 settlements 的 APPLIED 结果，不提前单独提交一个账务身份。提交后可以立即尝试 DEL，失败则由持久化扫描器继续投递；只有整个失效集合处理成功，才更新 delivery_state。这样即使接口不再被调用，数据库里仍然留有可恢复的失效义务，而不是依赖一条内存消息。

## 第 3 层：为什么删除顺序不能随便调整？

**面试官：** outbox 能补删，那为什么不先删缓存再更新数据库？先删不是也能让下一次查询回源吗？

**面试者：** 先删会暴露一个直接的旧值回填窗口：写者删掉缓存，读者未命中后读到尚未提交的旧余额并回填，随后写者提交，缓存却重新留下旧值。本基线选择提交后删除，是先让新权威事实可读，再触发回源。不过它仍不是严格一致性协议：读者可能在提交前已经拿到了旧值，只是很晚才写缓存，最终覆盖删除后的空键。因此，顺序选择只是减少一种竞态，不是证明其他竞态不存在。延时再删一次也只能覆盖某个经验时间窗，不能保证一个暂停很久的读者一定已经结束，更不能把这种经验延时当成资金正确性的依据。

## 第 4 层：删除成功后，旧值怎样重新出现？

**面试官：** 你说提交后 DEL 仍会旧值回填，请沿 T100 给出完整时序，并解释为什么事件带版本也没有自动解决它。

**面试者：** 设某余额提交前版本是 v，提交后是 v+1。读者 R 先缓存未命中，从主库读出 v，然后暂停；T100 提交 v+1，写者 DEL 成功，outbox 也确认失效完成；最后 R 恢复，把 v 写回 Redis。此时数据库正确，缓存却倒退了。若另一个读者已经回填 v+1，R 甚至可能直接覆盖它。事件 payload 携带 v+1，但消费者只执行 DEL，并没有建立拒绝 v 的规则，所以版本只是诊断信息。迟到的旧失效事件还可能删除较新的缓存，导致额外回源；它通常不伤账务，却说明缓存命中率和版本单调性都不是当前主基线的承诺。我们必须明确允许这个弱一致窗口。

```text
R：缓存未命中 → 主库读出旧版本 v → 暂停
W：T100 提交新版本 v+1 → DEL → outbox 确认
R：恢复 → SET 旧版本 v，并重新设置缓存 TTL
```

## 第 5 层：TTL 能否给出严格的陈旧时间上界？

**面试官：** 那给每个键设置一分钟 TTL，是否就能承诺提交一分钟后绝不会再看到旧值？随机 TTL 又解决什么？

**面试者：** 不能无条件这样承诺，因为 TTL 通常从 SET 时开始，而不是从源数据被读取或事务提交时开始。上面的慢读者若十分钟后才恢复，再 SET 一分钟 TTL，旧值就在提交很久后重新出现。随机 TTL 主要打散大量键同时到期，并不修复这个时序。更强的可选策略是记录源读取开始时刻，携带绝对失效 deadline，回填时只设置剩余寿命，过期直接拒绝；命中时也验证 deadline，且不滑动续命。它还依赖时钟误差、读源新鲜度和请求耗时约束，副本旧读尤其要另管。也可以拒绝低于可信源版本下限的数据，但这个下限必须另有可靠来源，不能拿同一个旧值自证新鲜。

## 第 6 层：版本水印能改善什么，又不能承诺什么？

**面试官：** 既然拒绝旧版本需要可靠下限，能否在 Redis 中增加版本水印，让 v 再也写不回来？

**面试者：** 可以作为显式加强变体，但不是本基线已具备的能力。对每个余额，把缓存值和 watermark 放在同一个 Cluster 槽；失效脚本原子推进水印到已知余额版本，并删除低版本缓存，回填脚本只接受不低于水印、也不低于现存缓存的源版本。这样能压住水印存续期间的旧回填和乱序覆盖，但水印的过期、淘汰、恢复和故障回退都必须设计。若缓存键还活着、慢请求还可能回来，水印却先丢了，保护就失效。恢复时可切换缓存代际、拒绝旧代际请求，并从主库重新建立下限；不能只给水印一个随意 TTL 就宣称闭合。它仍不保证提交到失效事件送达之间没有旧读，也不是 Redis 缓存线性一致，更不能用于资产裁决。

## 第 7 层：失效重试怎样做到可恢复，而不是越重试越乱？

**面试官：** 水印是可选的，回到只 DEL 的主基线。四个键只删成功两个，或者删完但确认响应丢了，扫描器怎么办？

**面试者：** 扫描器按至少一次处理，重新删除整个四键集合即可，DEL 对不存在的键也安全。Cluster 中四个键可能跨槽，不假装一次多键 DEL 原子完成，可以逐键或按槽执行，全部成功后再确认事件；部分成功就保留重试义务。删除成功但确认前崩溃，下一轮重复删除最多降低命中率，不会重复扣资产。任务领取、租约与 delivery_state 的更新要持久化，失败采用退避、抖动和可观测的告警，不能达到重试次数后静默丢弃。去重也不能先把事件永久标成已处理、再做 DEL，否则中间崩溃会漏删。记录事件年龄和重试原因，才能区分积压、Redis 不可用与单键异常。

## 第 8 层：Redis 整体故障恢复时，怎样避免数据库被压垮？

**面试官：** 失效任务可以一直重试，但 Redis 全挂后所有展示请求都回源，会不会把主库拖垮，反而影响真正的结算？

**面试者：** 会，所以“Redis 可丢”不等于“回源容量无限”。我会给展示回源独立并发预算、连接池额度和排队上限，进程内合并同键请求，允许展示明确标注的旧副本或返回暂不可用，不能把资金请求挤到无限队列里。Redis 恢复后优先消费失效积压并分批预热，必要时启用新缓存代际，防止恢复的旧快照与迟到回填重新污染热键；随机 TTL 只承担削峰。普通展示可以降级，资金裁决仍进入主库同一套事务，容量不足就明确拒绝新的业务受理，不能切到 Redis 放行。结算 Commit 断网仍是 unknown，要按原 trade_id 查主库或重入恢复，既不换身份重扣，也不按缓存或超时释放 HB/HS。

## 本题收束

- **讲透的机制：** 数据库提交先确定账务事实；同事务 outbox 保存失效义务；DEL 至少一次重试与有限 TTL 组合提供可恢复的弱一致展示。
- **最容易答错的边界：** `version + DEL` 不等于拒绝旧写；随机 TTL 不等于一致性；普通 SET 的相对 TTL 不给出相对数据库提交的无条件严格延迟界；水印丢失后不能继续沿用旧保证。
- **检验反例：** 让读者持有 v 暂停，完成 v+1 提交、DEL 和事件确认后再恢复读者。主基线允许缓存暂时出现 v，但主库资金操作必须仍按 v+1 裁决；若回答声称这个时序下缓存绝不倒退，就漏掉了旧回填窗口。
