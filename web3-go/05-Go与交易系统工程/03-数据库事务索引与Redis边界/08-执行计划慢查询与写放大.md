# 大问题 8：怎样从执行计划、锁等待与写放大定位交易数据库瓶颈？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 分层耗时 | 把一次接口等待拆开，确定到底卡在哪里。 | T100 可能等入口、连接、行锁或 WAL，不一定是 SQL 扫得慢。 |
| 连接池等待 / 行锁等待 | 等一条连接与拿到连接后等某行修改资格。 | 两者来源不同，扩池不必然解决，反而可能增加库内竞争。 |
| EXPLAIN | 展示数据库准备怎样执行语句的估计计划。 | 可先检查候选路径，但不证明实际性能，更不保证计划长期不变。 |
| EXPLAIN ANALYZE | 真正执行语句并收集运行情况。 | 不是只读标签，对资金 UPDATE 使用时会实际产生修改与负载。 |
| BUFFERS / shared hit、read | 计划里的缓冲区访问统计。 | shared read 可能来自操作系统缓存，不能直接等同物理磁盘读。 |
| rows / actual rows / loops | 估计行数、实际行数与节点执行次数。 | 多次执行节点的实际行数和时间通常按每次平均报告，要结合次数看工作量。 |
| 父子节点时间 | 计划节点之间的包含关系。 | 父节点一般包含子节点，逐项相加会把同一耗时重复计算。 |
| Seq Scan / Index Scan | 顺序读表与沿索引定位的访问方式。 | 小表或大范围读取走顺序扫描可能合理，不以必须走索引作为结论。 |
| 统计信息 / 数据倾斜 | 规划器对数据分布的估计与账户冷热差异。 | 普通账户的好计划不一定适合超大热点账户，需要代表性参数。 |
| pg_stat_activity / 阻塞链 | 数据库会话活动及谁在等谁的证据。 | 结合 pg_blocking_pids 找真正持锁者，而非只看最慢的等待语句。 |
| idle in transaction | 事务还开着，却暂时没有执行 SQL。 | 可能仍持锁并阻塞 T100，等待外部 RPC 也不是无害空闲。 |
| WAL / 写放大 | 一笔写入额外产生恢复日志和索引维护。 | 宽索引、页分裂等可延长持锁与提交耗时，读优化可能拖慢结算。 |
| HOT 更新 | PG 在满足条件时减少索引维护的一种更新路径。 | 受更新列、索引和页内空间影响，不是“非主键更新必然免费”。 |
| vacuum / 死元组 | PG 清理不再需要的旧行版本与待清理版本。 | 长快照可拖住清理，持续膨胀不能只靠再加索引解释。 |
| InnoDB undo / purge | MySQL 保存与回收旧版本的实现机制。 | 可对比长读视图的代价，但不是 PostgreSQL heap/vacuum 的同一实现。 |
| work_mem / 尾延迟 | 单类执行操作的内存预算与较慢请求的耗时。 | 并发会放大内存成本；验收要看尾部、锁等待和正确性，不只看平均值。 |

## 把整篇文章压缩成一个故事

T100 入账越来越慢，阿宁先没有给余额表加索引，而是把时间拆成排队、等连接、执行、等行锁和提交。她发现某条主键 UPDATE 计划很短，却被另一个持锁后等待外部 RPC 的事务堵住。此时增加连接只让更多请求挤进库里，新增索引也不能让两个人同时修改同一余额行，先缩短事务和控制并发才对症。

另一条流水查询才真正需要查访问路径。阿宁在受控环境用代表性参数取实际计划，对比估计与实际行数、loops、排序和缓冲区访问；她不把父子耗时重复相加，也不把 shared read 全算成磁盘 IO。生产资金语句先看估计计划和现有监控，因为 EXPLAIN ANALYZE 会真的执行，外面包回滚仍会拿锁、产生负载，不能当成无副作用沙箱。

查完读路径，她还检查索引维护、WAL 和长快照是否拖住版本清理。宽索引也许让列表快了，却拉长 T100 的持锁时间；长只读事务也可能让旧版本难清除。任何优化仍须保留四腿账务、余额、HB/HS 和结果共同提交，不能为漂亮吞吐改成两边分开记账。本篇给的是取证与验收方法，没有真实负载数据就不能宣称 p99 已改善。

[返回专题总览](README.md)

**流程位置与核心机制：** 回答 T100 入账或账务查询变慢时，怎样先分层取证再选择优化；上一题负责候选索引，下一题负责 Go 连接与事务生命周期。

**必要前提：** PostgreSQL 16 单库 RC、余额与预占同事务；MySQL 8.0 InnoDB 的版本清理仅作比较。以下是诊断方法与假设现象，不是已经执行的压测结论。

## 第 1 层：接口慢，不等于 SQL 扫描慢

**面试官：** T100 入账接口越来越慢，你会先加索引还是增加数据库连接数？

**面试者：** 我先把耗时拆成入口排队、连接池等待、执行语句、行锁等待和 Commit/WAL 等待，再看下游通知是否被错误放进事务。用户看到接口慢，可能是根本没拿到连接，也可能是精确主键更新在等热点账户锁，不能直接归因于扫描。

我会关联请求 ID、trade_id、事务耗时和数据库会话，检查活动会话、等待事件和阻塞关系；慢 SQL 日志只覆盖其中一部分。对账务列表，再看匹配行数、返回行数、排序和 IO。先确认慢在哪一层，才决定改查询、缩短事务、限制并发或改善持久化能力。扩池可能只把更多等待搬到数据库，索引也不会消除同一余额行必须串行修改的事实。

## 第 2 层：拿到 SQL 后，如何安全获取执行计划

**面试官：** 你已经定位到账务列表和余额更新，拿 EXPLAIN ANALYZE 看一下就够了吗？

**面试者：** 要先区分普通 EXPLAIN 与 EXPLAIN ANALYZE。前者展示估计计划，后者实际执行语句并收集运行信息。对 UPDATE、DELETE 或带副作用的函数直接在生产执行，可能真的改变资产，不能把它当只读诊断。

我优先在受控环境用代表性参数获取 `EXPLAIN (ANALYZE, BUFFERS)`；生产取证遵守权限、采样与超时边界。事务包住后回滚能撤销大部分事务内数据修改，却仍会拿锁、产生负载和 WAL，也不撤销序列推进或外部非事务副作用。高风险资金语句宁可先看估计计划和已有监控，不为了补一张计划破坏业务。MySQL 的分析命令支持范围也应按实际版本核实，不能机械照抄。

## 第 3 层：估计行数和实际行数怎样读

**面试官：** 在受控环境得到计划了，你具体看哪些信息，而不是看到 Seq Scan 就说错了？

**面试者：** 我沿关键节点对比估计 rows 与 actual rows，观察 loops、过滤掉的行、排序是否落盘以及缓冲区访问。估计严重偏离会影响连接顺序和访问路径，需要检查统计信息、数据倾斜、字段相关性与参数差异；不能把所有偏差都归因于索引不存在。

当 loops 大于一时，actual rows 和时间通常是每次执行的平均值，需要乘执行次数理解总工作量；父节点又包含子节点时间，不能逐节点相加冒充整条 SQL 耗时。小表或必须读取大部分行的查询走 Seq Scan 可以合理。我要证明的是为了返回几十条记录做了多少额外工作，以及哪些工作可避免，不是证明“计划里必须出现 Index Scan”。

## 第 4 层：读了很多块，是否一定是磁盘瓶颈

**面试官：** 计划里 shared read 很高，你是不是可以断定磁盘随机 IO 扛不住了？

**面试者：** 还不能。PostgreSQL 的 shared read 表示块被读入共享缓冲区，它可能命中操作系统缓存，不等于每次发生物理磁盘读。shared hit 则是在共享缓冲区命中。父节点的缓冲区数也包含子节点，不能把全树数值直接相加。

我会结合 IO timing、系统存储延迟、CPU、缓存容量、读写吞吐和查询并发，区分物理 IO、内存访问和计算成本。如果最近新增宽索引挤掉热数据，问题可能是工作集扩大；如果排序或哈希产生大量 temp 读写，还要看基数估计和内存配置。全局调大 work_mem 也有并发倍增成本，不能只凭单条查询的结果给所有连接增加巨大内存预算。

## 第 5 层：主键 UPDATE 也慢，怎样找阻塞源

**面试官：** 余额 UPDATE 明明只按主键改一行，计划很短，但仍然要等几秒，下一步怎么查？

**面试者：** 我先看会话等待事件和阻塞链，例如用 `pg_stat_activity` 关联 `pg_blocking_pids()`，再看持锁事务在做什么。阻塞者可能已经执行完 UPDATE，却在事务中等待外部 RPC，甚至处于 idle in transaction；不能因为它当前没跑 SQL 就当它无关。

处理上先止住新进入的过量并发，再按权限决定是否取消或终止异常会话，提前评估回滚与业务未知结果。长期方案是缩小事务、固定锁顺序、索引化精确定位，并避免事务持锁期间访问 Redis 或链上 RPC。如果所有请求都正常竞争同一账户，锁等待也可能是业务热点的真实串行成本，不存在一个“再加索引”就消灭竞争的方案。

## 第 6 层：索引多了为什么反而拖慢入账

**面试官：** 为了列表你已经加了覆盖索引，现在锁持有时间又增长了，索引和更新延迟有什么关系？

**面试者：** 每次余额或账务写入不只改一份逻辑记录，还可能维护多棵索引、产生 WAL、修改页并触发页分裂。索引越宽、越多，提交前做的工作越多，事务持锁时间也可能被拉长。热点余额的 version 每次变化，如果它也放在被维护的索引中，优化读的收益可能被写放大抵消。

PostgreSQL 的 HOT 更新在满足条件时能减少索引维护，但依赖更新列、索引类型和页内空间等条件，不能把“更新非主键”就等同于 HOT。账务追加写和余额原地逻辑更新的负载不同，应分开评估。我会比较查询收益与写入 WAL、索引体积、页利用和提交耗时，而不是把每个候选索引永久保留。

## 第 7 层：长事务怎样影响版本清理

**面试官：** 写放大控制了，表和索引仍持续膨胀，为什么你还会检查一个长时间只读的事务？

**面试者：** MVCC 让旧版本为某些活动快照保留可见性。PostgreSQL 中持有旧快照或相关清理边界的长事务可能阻碍 vacuum 清除旧元组，积累死元组、增加扫描和索引负担；不是“只读所以免费”。还应检查复制槽与备份等可能拖住资源回收的因素，区分表清理边界和 WAL 保留边界。

MySQL InnoDB 也需要关注长 Read View 对 undo purge 的影响，但它的 undo、purge 与 PostgreSQL heap/vacuum 不是同一套实现。我的措施是限制在线长事务，审计导出使用受控任务，观察清理是否追得上写入，并规划存储和维护窗口。直接重建大表或加机器只能缓解结果，不能代替消除持续持有旧版本的根因。

## 第 8 层：怎样证明优化没有牺牲正确性

**面试官：** 假设你缩短事务、删索引、做了批量入账，怎样判断真的更好了，而不是把资金安全换成吞吐？

**面试者：** 我先保持 T100 的共同提交边界和固定身份不变，再逐项比较同一负载下的吞吐、尾延迟、连接与锁等待、WAL、死元组和失败率。批量可以减少每笔的固定成本，但会延长锁持有、扩大回滚范围并改变公平性，所以需要批量上限，不是越大越好。

正确性仍检查每币种分录和为零、余额与预占非负、同一 trade_id 只产生一次四腿变化；对于故障恢复，确认已承诺的提交没有被放宽为未刷盘“成功”。任何用缓存余额替代主库校验、先提交一边再补另一边的提速，都已经改变业务合同，不能作为无损优化。没有测量数据时，只能给出验证方案，不能声称吞吐或 p99 已改善。

## 本题收束

- **讲透的机制：** 先拆等待，再看实际访问路径，最后同时评估索引收益、写放大和版本清理。
- **最容易答错的边界：** EXPLAIN ANALYZE 会执行；回滚不是无副作用沙箱；shared read 不直接等于物理磁盘读。
- **验证反例：** 让另一个事务锁住余额后等待外部调用，此时再建索引仍不能让同一余额行立即更新。
