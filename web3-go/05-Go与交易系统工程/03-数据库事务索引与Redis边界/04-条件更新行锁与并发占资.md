# 大问题 4：条件更新、行锁与版本号怎样防止并发占资？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 预占 / 成交消费 | 先把钱留给业务，与之后兑现已确定成交是两步。 | 新预占把 available 转 frozen；T100 只消费已有 HB、HS。 |
| R1 / R2 独立变体 | 用来演示抢同一余额的两次新请求。 | 各要 7000、4000 USDT，竞争原 available 7000，不占用属于 T100 的 frozen 3000。 |
| available / frozen | 可分配余额与已被业务占住的余额。 | R1 先成时为 0/10000；R2 先成时为 3000/7000，不能二者都获准。 |
| 丢失更新 | 用旧余额算出的常量覆盖别人刚完成的更新。 | 余额看似非负，也可能漏掉一次实际预占。 |
| 条件 UPDATE | 把足额检查和相对金额修改写在同一数据库操作里。 | PG RC 等待同一行更新后重验 available 条件，不足就不能占资。 |
| RowsAffected | 更新实际改到了多少行。 | 必须检查恰好一行；零行不能继续写“预占成功”。 |
| 金额参数 / 最小单位 | 正数金额以固定整数刻度传入。 | 7000 USDT 为 7000000000，先校验精度、正值和溢出。 |
| 新 hold / 请求身份 | 新预占的归属凭据和稳定业务编号。 | 与余额变化共同提交，不能复用 HB/HS 或重试时再造一次占用。 |
| SELECT FOR UPDATE | 先锁住目标行，再按锁内状态判断。 | 所有后续修改都在同一 tx 内；锁完提交再扣钱不受保护。 |
| version / CAS | 只有版本仍等于预期值才尝试修改。 | 版本和金额一起更新；PG CAS 仍取得行锁，不是数据库无锁算法。 |
| 共同额度行 / 跨行谓词 | 多行共用一个需要整体保护的条件。 | 两子账户各预占 4000，单行足额也可能突破组上限 6000。 |
| 固定锁序 | 所有资产写者按同一顺序取得完整资源集合。 | 先锁齐账户币种余额，再按 ID 锁 hold，不能边锁预占边补余额。 |
| consumed / remaining | 预占已经用掉，以及尚可消费的量。 | T100 全额消费后剩余零，迟到释放不能把钱退回可用。 |
| 释放资格 / 权威裁决 | 先确定哪些义务已关闭、哪些仍须兑现。 | 即使 hold 尚未 consumed，已确定成交也不能因超时被释放。 |
| Redis 租约 / context | 临时协调权限与调用等待预算。 | 都不能取代 PG 条件、唯一身份和状态校验，也不能证明提交未发生。 |

## 把整篇文章压缩成一个故事

先看独立预占场景：小林可用 7000 USDT，另有属于 T100 的冻结 3000。R1 想占 7000，R2 想占 4000，若都先普通查询再按旧值扣款，就可能超占或覆盖更新。服务把足额条件写进同一条 PostgreSQL UPDATE，竞争者等待后重验；无论谁先成功，另一个都不够。原有冻结不是公共备用金，不能拿来补差。

条件更新成功也不能就此提交：请求身份、新 hold 和必要流水必须一起落库，创建凭据失败要整笔回滚。若采用版本 CAS，版本也须共同更新，零行后重新读取判断；它仍会锁数据库行。扩展到多余额时先锁齐完整集合，多行共用额度还要锁共同保护对象。单行都非负，不代表组级限额一定没被突破。

然后撤去 R1/R2 变体，回到 T100：服务消费 HB 的 3000 USDT 和 HS 的 0.1 BTC，不再新冻一次，四条分录、余额、预占和结果一起提交。迟到释放者即使曾读到 ACTIVE，也要锁内重验，更要确认权威释放资格；成交已确定不能因五分钟超时退款。Redis 丢锁或客户端取消只影响协调与等待，不改义务，提交未知仍沿原 T100 查主库恢复。

**流程位置与核心机制：** 先用两次竞争预占解释单行原子判断，再回到 T100 的多余额、多 hold 消费与迟到释放。重点是数据库里的裁决条件，不把 Redis 锁当资产正确性的唯一来源。

**沿用总览基线：** 链下托管 BTC/USDT；PostgreSQL 16 RC，Go 1.21+ `database/sql`；BTC `1e8`、USDT `1e6` 整型最小单位，四条余额预建。T100 已确定成交 0.1 BTC、3000 USDT，必须同事务消费 HB/HS、更新四条余额、写四条分录、唯一 settlement 和 outbox。所有写者先按 `(account_id, asset)` 升序逐条锁全部受影响余额，再按 hold_id 升序锁 hold；Redis 7.x 只做可丢缓存、限流或协调。

**独立变体说明：** 第 1—7 层暂时讨论 T100 入账前的另两次预占请求：R1 要 7000 USDT，R2 要 4000 USDT，共同竞争买方原 available 7000。原 frozen 3000 及 HB 仍属于 T100，不能挪用；新预占使用自己的请求身份与 hold，不复用 HB/HS。第 8 层回到原始 T100，不把竞争预占的结果叠加进去。

## 第 1 层：先查余额再扣，为什么会超占？

**面试官：** 买方 available 是 7000，R1 要预占 7000，R2 要预占 4000。两次请求各自先查再更新，会发生什么？

**面试者：** 如果两次普通 SELECT 都读到 7000，然后在应用里判断足额，再不带条件地扣减，两者都可能获准。使用相对减法会把 available 扣成负数；使用旧值算好的常量回写还可能覆盖对方更新，看起来不负却漏记一次扣减。正确结果只能允许其中一个成功：R1 先成功则 available 0、frozen 10000；R2 先成功则 available 3000、frozen 7000，另一个都应拒绝。原 frozen 3000 是 HB 的钱，不能拿来补足另一个请求。这是两次独立预占的竞争，不是在重新冻结 T100 的成交金额。

## 第 2 层：条件 UPDATE 怎样把检查和占资合为一步？

**面试官：** 你说不能分开检查，怎样写一条 PostgreSQL RC 的更新，让等待后的余额也受到约束？

**面试者：** 我会执行 `UPDATE balances SET available=available-$1, frozen=frozen+$1, version=version+1 WHERE account_id=101 AND asset='USDT' AND available >= $1`，参数分别是 7000000000 或 4000000000，即 USDT 最小单位。先校验 amount 严格为正、精度合法并防止运算溢出，再检查 RowsAffected 必须为一。并发 UPDATE 会竞争同一行，等待者在对方提交后重验 WHERE，不足就影响零行。这条单余额更新本身获得该 balance 的行锁；之后才能处理 hold。零行不是成功，不能继续创建“已预占”的业务结果。

## 第 3 层：余额扣成功后，hold 创建失败怎么办？

**面试官：** 条件更新成功了，但创建新 hold 时进程崩溃，或者重复请求撞上 hold 唯一约束，会不会留下没有归属的冻结？

**面试者：** 所以条件 UPDATE 只是事务内部的一步，不能单独提交。预占余额变化、请求身份、对应的新 hold 及必要的预占流水必须整体提交，预占流水不混入 T100 的四条成交分录。新 hold.remaining 等于本次占用金额，并绑定对应账户、币种与业务意图；任何后续写入失败都回滚整个预占。R1 重试也必须沿用原身份并核对载荷，不能生成新 hold 后再占一次。PostgreSQL 若发生唯一冲突异常，事务已失败，不能 catch 后仍提交前面的余额更新，应回滚并进入既定的幂等查询或重试路径。

## 第 4 层：已经有条件 UPDATE，FOR UPDATE 还有什么用？

**面试官：** 一条条件更新能保护余额，那什么时候会选择先 SELECT FOR UPDATE，再判断是否预占？

**面试者：** 单行、单个足额条件用条件 UPDATE 最直接；如果需要检查多项状态、生成精确结果，或者同一事务随后还要联动多个对象，我会先锁余额再读取并判断。`FOR UPDATE` 让同一行的其他冲突写者等待，锁后读到的当前值才是本次裁决基础，不是先前普通查询的值。Go 要让锁定查询和所有更新都走同一个 `*sql.Tx`，并检查查无行、扫描错误及影响行数，不能锁完就提交，再到事务外扣钱。本例只有一条余额，随后创建新 hold；若扩展到多余额，必须先拿齐全部余额锁，不能边锁 hold 边继续找下一条余额。

## 第 5 层：version CAS 能否完全替代行锁？

**面试官：** 你提到先锁再判断。如果余额已经有 version，直接用 CAS 更新是否更简单，还需要什么条件？

**面试者：** 可以用 `WHERE version=$old AND available >= $amount`，成功时金额与 version 一起更新；所有写者都必须递增 version，影响零行就表示旧判断不能直接沿用，需要重新读取并区分版本冲突与余额不足。PostgreSQL 的 CAS UPDATE 仍会取得行锁，不是数据库里的无锁算法，也不能承诺永不等待。在这个单余额变体中，它仍须与请求身份、新 hold 同事务提交。若是多余额事务，不能分别 CAS 成功一条就提交一条；基线仍先按统一顺序锁齐全部余额、再锁 hold，version 可作为额外校验和缓存版本，不能成为绕过锁协议的理由。

## 第 6 层：每行都不为负，为什么跨行规则仍可能失败？

**面试官：** 你保留了多余额的整体事务。假如每一行都用条件更新或者 CAS，还有什么业务规则不是这些条件能保护的？

**面试者：** 跨行谓词不一定包含在单行条件中。举一个独立规则变体：某资金组有两个 USDT 子账户，各自余额充足，但全组新增预占上限 6000；两事务都看到本轮预占合计零，分别在不同子账户预占 4000。每行都足额、版本都匹配，合计却变成 8000。仅把各自更新包在事务里也不够。我会要求相关写者锁共同额度行，或在固定成员范围内锁全部相关余额并在锁后重算；范围可新增成员时还要保护成员变化，必要时用可串行化和完整事务重试。这条组级规则不叠加到原 T100。

## 第 7 层：锁更多行会不会把系统拖成串行？

**面试官：** 为了跨行规则扩大锁范围，遇到热点账户怎么办？能不能先扣一行，发现另一行不够再补偿？

**面试者：** 不能为了缩短等待拆开资产原子边界。每个事务先确定完整受影响集合，按明确的 `(account_id, asset)` 升序逐条拿齐余额锁，再按 hold_id 升序拿 hold，锁内只做必要校验与写入。任意 SQL IN 列表不等于承诺加锁顺序。热点单行写入本来就有物理串行化点；可缩短事务、减少无关索引写入、在事务外做参数计算，并用有界排队和限流降低冲突，但不能漏掉必须保护的行。若要拆成独立资金桶，需要先定义桶间额度分配与守恒，是改变业务分区规则，不是免费的性能优化。

## 第 8 层：回到 T100，成交消费和预占有什么不同？

**面试官：** 刚才一直在把 available 转为 frozen。回到原始 T100，是否也先判断 available 足够，再创建一次 hold？

**面试者：** 不会，这里撤去 R1/R2 变体，恢复原始余额。T100 已确定，HB 的 3000 USDT 与 HS 的 0.1 BTC 就是待消费的冻结资金，不能再次预占。我按协议锁齐四条余额，再锁 HB/HS，核对归属、币种、允许状态和 remaining，按四条成交分录改变对应 bucket，并把两 hold 置为 remaining 0、consumed。余额、分录、hold、settlement 和 outbox 整体提交，各币种 delta 和为零。成功后买方 USDT available 7000、frozen 0，BTC available 0.1；卖方 BTC available 0.4、frozen 0，USDT available 3000。

## 第 9 层：释放程序迟到，怎样避免把已成交资金退回？

**面试官：** 你说 hold 已 consumed。若一个超时释放程序早先查到 HB 仍有效，现在拿到锁了，能不能按旧判断释放？

**面试者：** 不能。释放者也必须先锁相关余额，再锁 hold，在锁内重验状态、剩余量和释放资格；看到 consumed 就不能把钱退回 available。更关键的是，尚未入账不等于尚未成交：T100 已经确定时，即使 HB 还没有 consumed，也不能因处理超时释放。一般未成交撤销必须先由权威状态机串行裁决执行资格，确认未来迟到命令不能再成交、既有成交义务已被保留，才可释放真正剩余量。时间戳或 hold 行锁本身不能完成跨阶段资格撤销。无法确认时保留冻结并恢复核对，不靠超时猜测；合法成交遇 hold 不一致则告警隔离。

## 第 10 层：Redis 锁与客户端超时能否改变这个裁决？

**面试官：** 如果释放和入账都持有同一把 Redis 锁，而且 Go 请求已经超时，是否就能安全释放并重做？

**面试者：** 不行。Redis 锁可能过期、丢失或在故障切换后失去互斥，旧持有者也可能暂停后恢复；它只能减少竞争，最终条件仍由 PostgreSQL 锁、状态和唯一身份裁决。Go 的 context 到期只说明调用预算用完，不证明事务未提交，更不撤销已确定成交。提交阶段断网要用同一 T100 查询权威主库并恢复，不能换 trade_id 或释放 HB/HS。对于明确未提交的失败，也要重开事务重新校验，不能复用旧余额。正确方案应在 Redis 完全不可用时仍不超占，只是限流、协调或展示能力可能降级。

## 收束：机制、边界与反例

- **讲透的机制：** 单行足额判断放入条件 UPDATE；请求身份、余额与 hold 同事务；多行条件增加共同保护对象；成交消费与释放在权威资格和锁内状态上裁决。
- **易错边界：** CAS 仍有数据库行锁；零影响行不是成功；先余额后 hold 的规则适用于所有写者；预占增加 frozen，成交消费 frozen，两者不能重复执行。
- **反例检验：** T100 已确定但尚未入账，释放任务因“超过五分钟”把 HB 退回，随后迟到的 T100 再来消费。即使每个 UPDATE 都带非负条件，也已经破坏成交义务，不能把后续扣款失败当作正确处理。
