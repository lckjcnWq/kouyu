# 大问题 3：读取 T100 的余额时，MVCC 与隔离级别究竟保证什么？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| MVCC | 为并发读取保留不同版本，让读者按规则看到合适的版本。 | 看到旧余额可能是正常快照，不代表 T100 只提交了半笔。 |
| 快照 / 可见性 | 一次读取认定哪些事务结果可以看见。 | 单条普通 SELECT 可在同一语句视图内读齐四条余额，也可见自身修改。 |
| PostgreSQL RC | 读已提交，每条普通查询重新取得语句快照。 | 一个事务先后读买卖方，可能跨过 T100 提交而拼出两个时点。 |
| 目标行条件重验 | 更新等到并发写者提交后，再检查这行是否符合 WHERE。 | PG RC 下 frozen 已变零，足额条件不满足就影响零行；不推广到所有复杂子查询。 |
| frozen >= 3000000000 | 冻结 USDT 至少够本次消费的最小单位条件。 | 3000 USDT 按 1e6 缩放；仍不能省略 T100 身份及全体锁协议。 |
| PostgreSQL RR | 在首次需要快照的数据语句处固定事务视图。 | 普通查询重复使用快照，不是 BEGIN 就必然建好，也不许覆盖后来的更新。 |
| 40001 / serialization_failure | 数据库拒绝了不能继续安全完成的并发执行。 | PG RR 更新快照后被改过的行可能失败，需要重试完整事务。 |
| 写偏差 / 跨行规则 | 各改不同的行都看似合法，合起来却违反共同约束。 | 两账户各 500、合计至少留 500，各扣 400 后只剩 200。 |
| Serializable / SSI | 让已提交事务可按某个串行顺序解释的隔离机制。 | PostgreSQL 通过依赖检测和中止执行防异常，不等于把所有查询变全表阻塞锁。 |
| 谓词读锁 | 为依赖检测记录读取范围的标记。 | SSI 会按一定粒度记录，不是任意业务状态机或外部效果保证。 |
| MySQL InnoDB 一致性读 | MySQL 普通 SELECT 使用的快照读取路径。 | RR 通常首次一致性读建快照；显式一致快照启动方式另有规则。 |
| 当前锁定读 | MySQL 中锁定或修改当前可处理记录的读取路径。 | FOR UPDATE、UPDATE、DELETE 不沿用普通一致性读的旧视图。 |
| record / gap / next-key lock | 锁索引记录、记录间空隙，或两者结合。 | InnoDB 范围保护依索引和操作而定，不能说所有 RR 查询都锁住未来插入。 |
| 幻读 / 可串行化异常 | 查询集合变化与无法按串行顺序解释的并发结果。 | 没有标准幻读也不代表没有写偏差，RR 不能直接叫 Serializable。 |
| 全体余额与 hold 锁协议 | 资金写者共同遵守的显式裁决顺序。 | T100 基线仍选 PG RC，先按账户币种锁余额，再按 ID 锁预占。 |

## 把整篇文章压缩成一个故事

客服阿宁核对 T100：小林用 3000 USDT 买到小周的 0.1 BTC。她在一个 PostgreSQL RC 事务中先查小林，看到冻结 3000；T100 随后整体提交，她再查小周，看到已收到 3000。把两次查询拼起来像钱多了一份，其实是语句快照跨了时点，并非半笔入账。用一条普通 SELECT 读四行，才属于同一个语句视图。

她改用 PostgreSQL RR 核对时，普通查询能维持固定视图，却不代表旧视图里的钱还能被扣。要更新快照建立后被别人改过的行，可能收到 40001，必须整笔重试。独立的组级反例更直接：两个各有 500 的账户要求合计保留 500，两事务各扣 400 都觉得足额，最后只剩 200。共同保护对象或正确使用 Serializable 才能守住这类规则。

同事提出“MySQL RR 的 FOR UPDATE 可以看新值”，阿宁指出那是 InnoDB 当前锁定读，不能套到 PostgreSQL RR；next-key 锁也有操作与索引范围条件。最后 T100 仍回到明确的 PG RC 基线，用唯一身份、余额及预占锁内校验和共同提交保护资金。隔离级别解释能看什么，业务协议决定能做什么，名字更强不等于所有义务自动闭合。

[返回专题总览](README.md)

**流程位置与核心机制：** 从 T100 提交前后的余额读取追到并发更新、快照隔离、SSI，再显式比较 MySQL。隔离级别是具体数据库的协议，不能只背“脏读、不可重复读、幻读”三个名词。

**沿用总览基线：** 链下托管 BTC/USDT，T100 已确定以 3000 USDT 买入 0.1 BTC。PostgreSQL 16 RC，Go 1.21+ `database/sql`；金额以 BTC `1e8`、USDT `1e6` 的整型最小单位保存。四条预建 balance、四条分录、HB/HS、唯一 settlement 与 outbox 同事务提交；资金写者先按 `(account_id, asset)` 升序逐条锁全部余额，再按 hold_id 升序锁 hold。Redis 7.x 不裁决资产。以下改变隔离级别或规则的段落都是独立对比，不叠加进基线。

## 第 1 层：RC 事务里的两次查询一定看到同一笔账吗？

**面试官：** T100 入账时，另一个 PostgreSQL RC 事务先后查询买方和卖方余额，会看到什么？

**面试者：** RC 的普通查询按每条语句开始时建立快照，不是 BEGIN 时把整个事务的视图固定住。如果第一条语句在 T100 提交前读买方 USDT，会看到 available 7000、frozen 3000；T100 随后整体提交，第二条语句再读卖方，就可能看到 USDT available 3000。把两次结果拼在一起会得到不属于任何一致时点的总额，但这不代表数据库只提交了半笔账。一条普通 SELECT 同时读取四条余额，则在该语句快照内看到提交前或提交后的整体状态，也能看到本事务自己的修改。

## 第 2 层：快照里有钱，更新时就一定扣得到吗？

**面试官：** 既然每条语句都有快照，假设 UPDATE 开始时看到了买方 frozen 3000，却等到 T100 提交才拿到行锁，它还会照旧扣款吗？

**面试者：** 对 PostgreSQL RC 的同一目标行，UPDATE 遇到并发更新会等待；对方提交后，会针对更新后的行版本重新检查自己的 WHERE。拿 `WHERE frozen >= 3000000000` 这段 USDT 最小单位条件分析：T100 已把 frozen 变为零，重验不满足，就不会再扣这行，影响行数为零；对方回滚则仍可能满足。这里是在分析单条 SQL 的执行语义，不是允许跳过 T100 唯一身份和全体余额锁。这个保证适合约束当前目标行，但不能据此声称复杂子查询或跨行规则都会在一个全新一致快照上整体重算。

## 第 3 层：换成 PostgreSQL RR，等待行为和读取有什么变化？

**面试官：** RC 会混合两个时点，那把余额查询改为 Repeatable Read，是不是连刚才的 UPDATE 问题也一并解决了？

**面试者：** 这是独立的隔离级别对比。PostgreSQL RR 在事务第一次需要快照的数据语句时确定事务快照，之后普通查询继续使用它，所以反复读四条余额不会因 T100 后来提交而换到新时点。但旧快照不代表可以覆盖新状态：如果 RR 事务要更新或锁定一行，而该行被快照建立后提交的事务改过，可能得到 `40001`，必须回滚并重试完整事务，不能按 RC 那样理解为等待后总能继续。RR 解决一致视图，不自动保证所有基于多行读取作出的业务判断都可串行化。

## 第 4 层：视图一致为什么还可能发生写偏差？

**面试官：** 你说 RR 仍可能违反多行规则，能沿着账户资金判断给一个具体反例吗？

**面试者：** 可以，但要明确这是新增规则的独立反例，不是 T100 的入账逻辑：假设一个资金组有两条 USDT 余额，各有 500，规则要求组内至少保留 500；两个 RR 事务都读取合计 1000，一个从甲账户扣 400，另一个从乙账户扣 400。若它们各自只锁并更新自己的行，都能判断“扣完还有 600”，最后却只剩 200。这是读到相同快照、写入不同行形成的写偏差。T100 仍按四条余额和两条 hold 的统一协议处理；新增组级规则必须锁住共同保护对象或全部相关行，不能只把隔离级别名字换成 RR。

## 第 5 层：Serializable 怎样阻止这个反例，是否等于全表加锁？

**面试官：** 如果组级规则不方便锁全体账户，PostgreSQL Serializable 能不能处理，代价在哪里？

**面试者：** 在这个独立反例中，若相关事务都正确采用 Serializable，PostgreSQL 的 SSI 会跟踪读写依赖，识别可能无法组成串行顺序的危险结构，并通过 `40001 serialization_failure` 中止某次执行。它不是把所有 SELECT 改成阻塞的全表锁；谓词读锁主要服务依赖检测，也可能按页或关系等粒度记录。应用必须重新开启事务、重新读取并判断，不能重发原来计算好的 UPDATE。SSI 保证已成功提交事务可串行化，但不是外部业务状态机，也不消除死锁；唯一身份、hold 资格和提交未知恢复依然需要独立机制。

## 第 6 层：MySQL RR 的普通读也完全一样吗？

**面试官：** 你刚说 RR 固定事务快照。如果换成 MySQL 8.0 InnoDB，读取 T100 余额时照搬这句话够不够？

**面试者：** 不够，必须标明数据库。这是把数据库换成 MySQL 8.0 InnoDB 的独立对比：RR 普通一致性读通常在事务内第一次一致性读时建立快照，不是普通 BEGIN 立刻建好；`START TRANSACTION WITH CONSISTENT SNAPSHOT` 是显式提前建立的一种方式。但 `SELECT ... FOR UPDATE`、UPDATE、DELETE 属于当前锁定读取路径，不沿用普通一致性读的旧快照，而是处理可锁定的当前记录。于是同一 RR 事务先普通 SELECT 看旧余额，再 FOR UPDATE 可能看到 T100 提交后的新余额。不能把这个行为套到 PostgreSQL RR，后者可能直接以 40001 拒绝相关锁定或更新。

## 第 7 层：next-key lock 能让 MySQL RR 没有所有幻读吗？

**面试官：** MySQL 当前读会看到新状态，那加上 next-key lock，能不能说 RR 就没有幻读，等同 Serializable？

**面试者：** 不能这样概括。InnoDB RR 对需要保护范围的锁定读或修改，通常结合记录锁与 gap lock 形成 next-key lock，阻止其他事务向受保护索引间隙插入；唯一索引精确命中既有记录等情况不一定需要间隙锁。普通一致性读不靠 next-key 锁稳定结果，而靠快照，两种路径不能混为一谈。换成 InnoDB RC 后，每次一致性读建立新快照，间隙锁通常减少，但外键检查、重复键检查等仍有例外。锁住哪些范围还受索引与执行方式影响，RR 既不等于所有查询都禁止新行，也不等于任意跨行业务判断可串行化。

## 第 8 层：回到 T100，为什么最终仍选 RC 加明确锁协议？

**面试官：** 各种 RR 的边界这么多，T100 到底怎样选隔离级别，才能既解释读取又保证入账？

**面试者：** 我会回到 PostgreSQL 16 RC 基线：查询展示可用单条 SELECT 获取一致时点的四条余额；需要跨语句固定视图的只读核对，可单独选择 RR。入账则用 T100 唯一身份和统一顺序的全部 balance、hold 行锁，在锁内校验并一次提交，成功后买方 USDT 7000/0、BTC available 0.1，卖方 BTC 0.4/0、USDT available 3000，两 hold consumed。提高隔离级别不能代替这些业务条件。Go 通过 BeginTx 显式指定所需级别并处理错误，不依赖连接默认值；缓存或副本读到旧余额也不得参与扣款裁决。

## 收束：机制、边界与反例

- **讲透的机制：** PostgreSQL RC 的语句快照与目标行条件重验，RR 的事务快照与写偏差，Serializable SSI 的失败重试；MySQL 普通一致读和当前锁定读的分离。
- **易错边界：** PostgreSQL RR 通常不出现标准意义的幻读，仍可能有序列化异常；MySQL RR 的范围锁也不使它等同 Serializable。BEGIN、首个快照和当前读不是一个概念。
- **反例检验：** “两条查询都在同一 RC 事务，所以能拼出同一时点资产总额”不成立；“两个 RR 事务都看到足额且各改不同行，所以组级限额安全”也不成立。

**核实资料：** [PostgreSQL 16 事务隔离](https://www.postgresql.org/docs/16/transaction-iso.html)、[PostgreSQL 16 显式锁](https://www.postgresql.org/docs/16/explicit-locking.html)、[MySQL 8.0 InnoDB 一致性非锁定读](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html)。
