# 大问题 1：一笔成交从入账到查询的完整流程与存储职责是什么？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| T100 / BTC/USDT 现货 | 用 USDT 交换真实 BTC 余额的一笔已确定成交。 | 买方 101 用 3000 USDT 向卖方 202 买入 0.1 BTC，无手续费。 |
| 最小单位整数 | 把小数换成固定刻度的整数再算账。 | BTC 按一亿分之一、USDT 按一百万分之一计量，不能把两种币直接相加。 |
| available / frozen | 尚可使用的钱与已经为业务占住的钱。 | 本次消费买方 frozen 3000 USDT，不再扣 available 7000。 |
| holds / HB、HS | 记录哪笔业务有权消费哪份冻结的凭据。 | HB 对应 3000 USDT，HS 对应 0.1 BTC；消费后剩余为零。 |
| settlements / trade_id | 持久保存成交身份及其完整入账结果。 | T100 的记录只有与全部账务共同提交后，才代表入账完成。 |
| payload_hash | 对规范化成交内容做出的核对摘要。 | 同为 T100 但金额或预占引用不同，不能当成普通重复请求。 |
| ledger_entries / 四腿分录 | 把一次交换拆成四条可追查的资产增减。 | 买方出 USDT、进 BTC，卖方出 BTC、进 USDT，每币种分别守恒。 |
| balances | 执行业务时使用的当前余额快照。 | 余额变化必须与分录和预占消费对应，不能任意互相覆盖。 |
| PostgreSQL RC | PostgreSQL 的读已提交隔离方式。 | 普通读按语句取得快照，资金写入还需要明确的事务和锁协议。 |
| 行锁 / 固定锁序 | 并发写者按同一顺序取得修改资格。 | 先按账户币种锁齐四条余额，再按 ID 锁 HB、HS，锁内重新校验。 |
| Commit / APPLIED | 整笔事务提交与已入账状态。 | 执行了一条 UPDATE 还不算完成；成功承诺也受持久化部署条件限制。 |
| outbox / T100:applied | 随账务一起保存的待通知清单。 | 进程提交后崩溃，恢复者仍能找到四个余额键的失效义务。 |
| cache-aside / DEL / TTL | 缓存未命中才查库，更新后删除，缓存有寿命。 | 只用于普通展示；删除与过期并不彻底阻止旧查询迟到回填。 |
| UNKNOWN / 原身份重入 | 暂时不知道是否提交，继续用原编号核验或恢复。 | COMMIT 回包丢失不能换 T100 的身份重扣，也不能直接释放冻结。 |
| 权威主库 / 派生视图 | 负责资金裁决的事实源与用于展示的副本。 | Redis、页面或读副本落后，不表示主库没有入账。 |

## 把整篇文章压缩成一个故事

买方小林的 3000 USDT 已由 HB 冻结，卖方小周的 0.1 BTC 已由 HS 冻结，撮合确定了成交 T100。账务服务收到它时，任务不是重新决定买卖，而是兑现这份义务。服务先核对来源、身份和整数金额，再进入 PostgreSQL 事务，按统一顺序锁余额和预占，避免其他写者同时动用同一份钱。

事务把 T100 身份、四条分录、四条余额、两份预占消费和 outbox 一起提交。之后小林 USDT 可用仍为 7000、冻结为零，新增 0.1 BTC；小周 BTC 可用仍为 0.4、冻结为零，收到 3000 USDT。四条分录逐币种一出一入。此时可以说“已入账”，即使通知还没送达、页面仍显示旧冻结，也不能重做这笔交换。

假如提交后服务崩溃，恢复者靠 outbox 继续删除缓存；旧查询随后回填旧余额，也只能造成展示滞后，不能批准花钱。若丢的是 COMMIT 应答，则结果是未知，要用原 T100 查主库或受唯一约束保护地重入。合法成交却发现预占不符时，应隔离核查而非擅自取消。整个故事要分清：成交义务、账务提交和页面可见是三个不同阶段。

**流程位置与核心机制：** 串起成交输入、账务原子提交、可靠失效和查询，负责说明各层拥有什么事实；事务实现、缓存竞态和分片协议分别在后续母题深入。

**必要前提：** 沿用总览的单库 PostgreSQL 16、RC、链下托管现货案例 T100：0.1 BTC 对 3,000 USDT，不计费用。它是教学模型，不是对目标公司实际架构的推断。

## 第 1 层：从收到成交到用户看到余额，完整流程是什么

**面试官：** 撮合已经确定 T100，你怎样把它入账并让用户查询到结果？数据库和 Redis 分别做什么？

**面试者：** 我先验证成交来源、稳定身份和整数金额，再用一个数据库事务完成身份去重、四条余额变化、两条预占消费、四条账务分录、完整结果与 outbox 写入。Commit 成功才称为入账完成，不能把执行了一条 UPDATE 当成完成。

事务之外，交付者根据 outbox 重试删除四个余额缓存键，普通查询未命中时从数据库重建缓存。Redis 用来加速展示和做限流，不批准扣款。用户立即核验刚完成的入账或系统决定能否继续花钱时，应访问权威主库，而不是等待缓存碰巧更新。这样即使 Redis 整体丢失，也只影响查询性能和展示新鲜度，不改变 T100 的经济结果。

## 第 2 层：为什么不能直接修改买卖双方余额

**面试官：** 你说需要这么多表。只在事务里把四个余额改完，不也能完成成交吗？

**面试者：** 四个余额只描述当前状态，无法独立证明“为什么变成这样、这笔成交有没有执行过、冻结依据是否已经消费”。T100 重投时，没有持久身份就可能重复转账；余额改完而 HB、HS 未消费，后续释放可能把已经花掉的冻结款重新释放。

因此 settlements 绑定一次业务身份与结果，holds 记录预占剩余与资格，ledger_entries 留下逐资产逐桶的变化事实，balances 提供执行时高效读取的余额快照。它们不是四份任意互相覆盖的真相，而是同一业务变化的不同约束视角，必须共同提交。outbox 则记录这次提交还需要通知哪些派生视图，避免进程在提交后崩溃就永久漏掉失效通知。

## 第 3 层：这些对象具体怎样共同变化

**面试官：** 你说它们是同一变化的不同视角，能用 T100 把提交前后讲具体吗？

**面试者：** 买方 USDT 冻结从 3,000 变成零，可用仍为 7,000；卖方 USDT 可用增加 3,000。卖方 BTC 冻结从 0.1 变为零，可用仍为 0.4；买方 BTC 可用增加 0.1。HB、HS 的剩余量归零并转为 CONSUMED。

同时写四条对应分录，每种币分别一出一入，USDT 的变化和为零，BTC 的变化和也为零。settlements 的 T100 保存规范载荷哈希和 APPLIED 结果，outbox 写 `T100:applied`，其载荷指明四个余额键及各自版本。所有余额与预占写者都遵守“先按账户币种排序锁余额，再按 ID 排序锁预占”的协议。只有整体提交以后，外部才有资格把这些值称为本次入账结果。

## 第 4 层：谁有权说一笔业务已经完成

**面试官：** 既然数据库已经整体提交，能不能给撮合、账务和页面都返回一个统一的“完成”？

**面试者：** 可以给调用方定义清晰状态，但不能抹掉阶段差异。撮合确定表示成交义务已成立；账务 APPLIED 表示本次账户结转已原子提交；通知交付表示下游已经按约定确认接收；页面显示新余额只表示某个展示视图已经追上。

在本模型中，我给入账接口返回 APPLIED，承诺的是数据库提交的结果，不承诺所有页面同一毫秒刷新。页面可带余额版本或入账查询入口来解释短暂滞后。反过来，页面已经收到一条 WebSocket 消息也不替代主库的入账事实。业务不变量要求“不重复、不透支、不丢既定义务”，而不是要求所有派生视图同步变化。

## 第 5 层：跨过提交边界后，缓存失败怎样处理

**面试官：** 那数据库提交成功以后，进程刚好在删除 Redis 前崩溃了。你刚说的展示最终追上靠什么？

**面试者：** 靠与账务同事务写入的 outbox，而不是靠那一次进程内调用一定成功。恢复后的交付者扫描未完成记录，发送四个键的失效操作；删到第三个失败时可以重试整个集合，因为删除本身可重复。只有获得约定交付确认才推进交付状态，发送成功后确认丢失允许再次发送。

有限 TTL 也能帮助缓存自我修复，但它不代替可靠失效记录，更不能声称解决所有旧值回填。旧查询可能在删除之后才把旧值重新塞进去。基线接受普通展示的弱一致窗口，资金执行始终重新检查主库。若需要更强新鲜度，要另加版本准入或主库读合同，不能把“最终一致”当作没有条件的保证。

## 第 6 层：提交回包丢失时，怎样保持原流程

**面试官：** 缓存失败你知道数据库成功了；如果 COMMIT 时连接断开，你根本不知道数据库是否成功，怎么办？

**面试者：** 我把它标成 UNKNOWN，不把网络错误直接映射为业务失败。恢复者按 T100 查询权威主库的完整 settlements 结果；查到相同载荷的 APPLIED 就返回原结果，不再改钱。若暂时查不到，也不能断言原事务已回滚，因为它可能仍在完成，或当前主库身份、连接状态尚待确认。

安全重入使用同一个 trade_id 和同一规范载荷，继续让数据库唯一约束裁决。原事务若提交，新事务只能读回旧结果；原事务若回滚，新事务才可能取得身份执行。这里的前提是已确认的数据库主控与持久化历史没有丢失。主从切换如果能丢已确认事务，业务幂等也可能随记录一起丢，必须另外限制接管承诺。

## 第 7 层：已确定成交却无法消费预占怎么办

**面试官：** 你强调同身份重入。但如果恢复后 T100 确实没入账，HB 却已经被另一条路径释放了，能直接取消 T100 吗？

**面试者：** 不能。T100 的成交义务已由撮合确定，账务服务没有权力仅凭缺少预占就把成交改为取消。这个状态说明跨模块资格协议或数据存在异常，我会回滚本次不完整入账、隔离该成交和相关资金操作，保留输入与已观察版本，查询预占创建、撤销及成交接受的权威顺序。

修复可能是重放缺失预占事件、纠正错误释放或走受审计的补记流程，取决于找到的持久证据；不能凭猜测制造余额。更关键的是事前规定：释放与消费必须串行裁决，迟到成交不能越过已撤销资格，撤销也不能释放已承诺给成交的部分。对账负责发现违反协议的事实，不负责把原本没有裁决规则的竞争变正确。

## 第 8 层：怎样证明架构没有把正确性寄托在缓存上

**面试官：** 你这套流程画起来都合理，给我一个能检验职责边界的反例，而不是再列组件。

**面试者：** 我会拿三个故障窗口做手工推演：第三条余额 UPDATE 后进程失败，应整笔回滚；Commit 实际成功但回包丢失，重入 T100 应返回原结果且分录仍只有四条；账务提交后清空 Redis，再把旧余额缓存回填，也不能让下一笔资产操作突破主库余额与预占条件。

检查的证据是同一 trade_id 的完整结果、四腿分录、两条预占和余额变化，不是“接口只调用了一次”。再检查数据库持久化与故障接管范围，确保不会把丢了幂等记录的新主当成完整历史。能在缓存重复、丢失、滞后时保持资金约束，才说明 Redis 是性能层；如果删除一个缓存键就允许再次记账，职责边界从根上就错了。

## 本题收束

- **讲透的机制：** 一次经济效果由同库提交确定，通知与展示异步追赶，稳定身份让未知结果可以恢复。
- **最容易答错的边界：** 把撮合确定、入账完成、消息到达、页面可见混成一个成功状态。
- **验证反例：** 让缓存显示旧冻结款，再尝试重复入账与释放；主库仍必须拒绝重复效果，不能让缓存参与资产裁决。
