## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| BTC/USDT 现货 / T100 | 用 USDT 交换 BTC 余额的已确定成交。 | 买方 101 以 30000 USDT/BTC 买卖方 202 的 0.1 BTC，共 3000 USDT，无费用。 |
| 最小单位整数 | 按固定刻度把小数金额化成整数存算。 | 0.1 BTC 为 10000000，3000 USDT 为 3000000000，币种不同不能直接混加。 |
| available / frozen | 还能用于新业务的钱与已经占给业务的钱。 | 买方入账前为 7000/3000 USDT，本次只消费 frozen，不重复扣 available。 |
| holds / HB、HS | 预占归属、资格和剩余量的持久凭据。 | 买方 HB 对应 3000 USDT，卖方 HS 对应 0.1 BTC，全额消费后归零。 |
| settlements / trade_id | 成交稳定身份与完整入账结果。 | T100 重投返回同一结果，不能先提交“已处理”再慢慢改资产。 |
| payload_hash | 核对固定身份是否仍对应相同业务内容的摘要。 | 同 T100 却改金额、账户或预占引用应冲突隔离，而不是冒用旧成功。 |
| ledger_entries / 四腿 / delta | 逐资产、逐桶记下四笔正负变化。 | 买卖双方各出一种币、入另一种币，每币种变化和为零。 |
| 单库事务 / APPLIED | 所有关联修改一起提交，随后才称已入账。 | 身份、分录、四余额、两预占与 outbox 不能拆开确认成功。 |
| PostgreSQL RC / MVCC | PG 按已提交版本提供语句视图的隔离机制。 | 读到余额不等于锁住资金，MySQL RR 的当前读规则也不能直接套来。 |
| 条件更新 / 行锁 / CAS | 在实际更新时检验金额、状态或版本。 | 先按账户币种锁齐余额，再按 ID 锁预占，关键更新检查影响行数。 |
| 死锁 / 整事务重试 | 资源形成等待环后，失败尝试从头重新校验。 | 沿原 T100 有界退避重试，不能只重发最后一句或夹带外部扣款。 |
| outbox / T100:applied | 随账务提交的通知与缓存失效义务。 | 事件版本 1 不代表全局进度；四个余额各有自己的版本。 |
| cache-aside / TTL / 旧回填 | 未命中才查库、缓存有限寿命，旧读者仍可能迟到写回。 | 基线是弱一致展示，提交后 DEL 加重试不等于缓存从此绝不旧。 |
| 索引 / EXPLAIN | 帮助定位数据的目录与分析访问路径的证据工具。 | 候选索引要衡量写成本，ANALYZE 会执行，单张计划不保证稳定性能。 |
| *sql.DB / *sql.Tx / context | Go 的连接池、事务连接与等待取消控制。 | 同一账务读写全走 tx；请求超时与 defer Rollback 都不能单独证明远端未提交。 |
| UNKNOWN / 原身份恢复 | COMMIT 应答不明时，沿原业务查证或安全重入。 | 权威主库暂时查不到也不等于回滚，不改号重扣、不擅自释放预占。 |
| Redis Lua / 租约 / fencing | 不交错执行、临时协调与资源端拒绝旧写的不同能力。 | Lua 不通用回滚、不自动耐久，租约失效也不会自动撤销数据库写权。 |
| 读己之写 / 同水位 / 跨片原子域 | 读取包含自己的提交、核对同一业务集合，以及共同提交的范围。 | 副本需因果进度，投影需完整前缀；拆库后本地锁和唯一键不能提供全局原子性。 |

## 把整篇文章压缩成一个故事

小林买小周 0.1 BTC，成交 T100 已确定，金额为 3000 USDT。双方相应资产已由 HB、HS 冻结，账务服务要兑现义务，而不是再决定能否成交。服务核对整数金额与载荷，争取 T100 唯一身份，按顺序锁齐四条余额再锁两份预占，在同一 PostgreSQL 事务里写四腿分录、消费预占、保存完整结果和 outbox，不能先写一个成功标记。

提交后小林 USDT 可用仍为 7000、冻结为零，BTC 增加 0.1；小周 BTC 可用仍为 0.4、冻结为零，USDT 增加 3000，每币种分别守恒。页面可能还旧，outbox 负责继续删除缓存，副本与投影按各自进度追赶；Redis 丢失也不能改变资产。若 COMMIT 回包丢失，服务报告未知，以原 T100 查主库或重入，不换号再扣，更不因超时把 HB、HS 退回。

流量增加后，阿宁先拆连接、锁、扫描和 WAL 等待，用计划评估索引与写放大，不靠扩池或 Redis 锁替代资金规则。Lua 的不交错不是故障耐久，租约也不是外部写权围栏。将来若拆账户分片，四腿的共同提交范围已经变化，必须另定义全局义务与可花门禁；迁移守住唯一资金主，对账比较同一完整业务集合。这里都是教学设计和手工推演，不是已经完成的工程实验。

## 一、文字全流程：一笔成交怎样只入账一次

### 1.1 锁定讨论基线

- **产品与执行：** 链下托管现货 BTC/USDT，撮合已经可靠确定成交。本文深入其账户结转，不重新设计撮合，不引入链上结算。它不是所有 DEX 的通用资产模型。
- **状态归属：** PostgreSQL 16 单库中的成交入账记录、账户余额、预占和账务分录是本模型的持久化权威；Redis 7.x 只是缓存、限流和减少重复工作的协调层。
- **默认事务：** PostgreSQL `READ COMMITTED`，显式事务、唯一约束、条件更新与统一行锁协议共同保证正确性。MySQL 8.0 InnoDB 仅作为标明前提的比较，不能照搬 PostgreSQL 的报错和快照规则。
- **实现：** Go 1.21+，用 `database/sql` 表达事务生命周期，不提供可运行工程。
- **精度：** BTC 用 `10^-8 BTC`，USDT 用 `10^-6 USDT` 为最小单位，数据库存整数；下表为了可读性显示十进制金额。不用浮点数参与资产裁决，生产需检查乘法中间值与字段范围。
- **预先条件：** 所需的四条余额行已存在；订单预占凭据 `HB`、`HS` 已建立，并且足额、未被撤销。基线无费用、无舍入尾差，不支持负余额或信用透支。

贯穿全文的是同一笔成交 `T100`：买方账户 `101` 买入 `0.1 BTC`，卖方账户 `202` 卖出 `0.1 BTC`，价格 `30,000 USDT/BTC`，成交金额 `3,000 USDT`。

| 对象 | 入账前 | 入账后 |
|---|---|---|
| 买方 USDT | 可用 7,000，冻结 3,000，总额 10,000 | 可用 7,000，冻结 0，总额 7,000 |
| 买方 BTC | 可用 0，冻结 0 | 可用 0.1，冻结 0 |
| 卖方 BTC | 可用 0.4，冻结 0.1，总额 0.5 | 可用 0.4，冻结 0，总额 0.4 |
| 卖方 USDT | 可用 0，冻结 0 | 可用 3,000，冻结 0 |
| 预占 HB | 买方 USDT 剩余 3,000，ACTIVE | 剩余 0，CONSUMED |
| 预占 HS | 卖方 BTC 剩余 0.1，ACTIVE | 剩余 0，CONSUMED |

内部整数：`0.1 BTC = 10,000,000`，`3,000 USDT = 3,000,000,000`。两种币不能直接相加验证守恒。

### 1.2 从输入一直讲到查询可见

```text
撮合结果交付者发送 T100〔双方、订单/预占、币种、数量、金额、规则版本〕
    ↓
Go 入账服务校验来源、格式、精度与业务载荷，计算规范化 payload_hash
    ↓
开启 PostgreSQL 事务，竞争 settlements.trade_id 唯一身份
    ├─ 已有相同载荷的完整结果 → 返回原结果，不再次改余额
    ├─ 同身份不同载荷 → 冲突隔离、报警，不把它当普通重复
    └─ 本事务取得身份 → 继续
                           ↓
按统一顺序锁定四条余额，再锁 HB、HS，核对预占和成交资格
                           ↓
消费两条预占，更新四条余额，写入四条逐资产分录
                           ↓
写 settlements 完整结果与 outbox 失效/结果通知记录
                           ↓
提交一个数据库事务
    ├─ 确定回滚 → 本次不产生账务效果，以同一身份按规则重试
    ├─ 提交结果不确定 → 查询/重入 T100，不另建身份、不擅自释放预占
    └─ 提交成功 → 账务完成，可返回 APPLIED
                           ↓
outbox 交付者重试发送余额失效通知，缓存删除可重复
                           ↓
普通查询走 cache-aside；资金裁决与未知结果核验走权威主库
                           ↓
页面最终追上入账结果；这一步不是账务原子提交的一部分
```

四条分录分别是买方 USDT 冻结 `-3,000`、卖方 USDT 可用 `+3,000`、卖方 BTC 冻结 `-0.1`、买方 BTC 可用 `+0.1`。它们、余额变化、预占消费、入账身份和 outbox 同时提交；不能先提交“已处理”再慢慢改钱。

### 1.3 主要异常分支

```text
无效格式/未授权输入 → 拒绝执行，不生成账务事实
同 trade_id、不同 payload_hash → 业务冲突，保留证据并隔离
死锁/可重试并发失败 → 整个事务回滚 → 有界退避后重试原 trade_id
四行余额更新到第三行失败 → 整体回滚，不能只保留前两行
合法成交却找不到足额有效预占 → 隔离待处理与报警，不撤销既定成交义务
COMMIT 回包丢失 → UNKNOWN → 以同一 trade_id 查主库/重入收敛
账务已提交、Redis 删除失败 → APPLIED 不回滚；outbox 重试与有限缓存寿命兜底
副本/页面暂未看到 T100 → 视图滞后，不据此再次入账或释放预占
```

**本专题没有给已确定成交增加“超时自动取消”规则。** 新占资、撤销与成交消费的竞争必须先确定谁拥有资格裁决权；本地 RPC 超时不是释放授权。

### 1.4 不同的“完成”

| 阶段 | 可以承诺什么 | 不能推导什么 |
|---|---|---|
| 成交已经确定 | 存在按约定规则履行的成交义务 | 尚不能说账户已结转 |
| 本事务执行到一半 | 当前事务拥有临时修改与锁 | 其他客户端不能把它当已入账 |
| Commit 返回成功 | 在既定数据库持久化部署承诺下，本次整体入账成功 | 不等于 Redis、副本、页面已更新，也不自动等于零 RPO 切主 |
| Commit 返回网络错误 | 调用方不能确认本次结果 | 不等于数据库必然回滚 |
| 缓存/查询投影追上 | 普通查询可展示新结果 | 展示不是资金真相的裁决者 |

## 二、核心板块：先确定谁能改钱

| 核心板块 | 决定什么、为什么核心 | 拥有的状态与上下游契约 |
|---|---|---|
| 入账身份与原子事务 | 同一成交是否只生效一次，多个资产是否共同变化 | 接收稳定 `trade_id` 与载荷；在同一事务内提交 settlements、账务、余额、预占和 outbox |
| 隔离、锁与并发裁决 | 并发占资、消费和释放能否破坏非负与守恒 | 所有写者遵守同一锁顺序和状态条件；不以旧快照查询替代执行时校验 |
| 索引与数据库资源 | 正确方案是否会被扫描、等待和连接耗尽拖垮 | 由查询形态设计索引；由执行计划、锁图、WAL/IO、池等待识别瓶颈 |
| Redis 与普通查询 | 允许多旧、失败时如何降级、怎样避免回填覆盖 | 余额展示可以滞后；缓存没有资格批准扣款，失效必须可重试 |
| 副本、分片与恢复 | 扩展后哪些原子性、因果和截止点已不再成立 | 单库事务不推广为跨库事务；对账比较同一业务集合与完成水位 |

## 三、核心 20%：只挑决定结果的机制深入

“20%”是重要性筛选，不是题数上限。以下机制必须闭合，B 树实现细枝末节、Redis 全命令表和完整消息平台不在本专题展开。

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 逐资产守恒与共同提交 | 四条分录到账务完成 | 定义正确结果与原子边界 | 一边扣款、一边未到账；标记成功但没记账 | 余额/分录/预占同提交，约束能表达的范围 |
| MVCC 与执行时校验 | 查询、占资、消费预占 | 读到不代表仍能使用 | 用 RC/RR 旧读批准超额占资 | PG/MySQL 快照差异、写偏差、锁定读 |
| 条件更新与固定锁序 | 多账户、多预占更新 | 决定唯一合法状态 | 负余额、丢失更新、死锁雪崩 | 影响行数、CAS、所有写者协议 |
| 唯一身份与未知提交收敛 | 重复交付、COMMIT 断网 | 持久化幂等比临时去重重要 | 重扣、重复记账、误释放 | 载荷冲突、冲突后读取、原身份重试 |
| 工作负载驱动索引 | 余额定位、账务/订单分页 | 缩小扫描与资源占用 | 索引越加越多，写入和维护恶化 | 联合索引、键集分页、覆盖与可见性 |
| 有证据的性能定位 | SQL、连接池、热点 | 慢不一定是缺索引 | 扩池加重雪崩，误操作生产数据 | EXPLAIN、锁等待、长事务、vacuum/undo |
| 缓存可丢与失效恢复 | DB 提交之后 | 避免双写真相 | Redis 故障变成资金错误 | outbox、旧回填、TTL 和版本边界 |
| 租约与持久化边界 | Redis Lua/锁/切换 | 原子执行不等于永久有效 | 误把脚本、锁、WAIT 当金融提交 | 不回滚、旧持有者、围栏与资源校验 |
| 因果读与同水位对账 | 副本、投影、跨片 | 区分正常滞后与真实丢失 | 假差异、重复补记、局部成功冒充全局 | 完整前缀、时间线、跨库协议 |

## 四、设计与规则：所有母题共用的前提

### 4.1 不变量与合法状态

1. 同一 `trade_id` 的规范化载荷只能对应一个确定结果；身份相同但载荷不同是冲突。
2. 每个币种分别满足 `Σ ledger_delta = 0`；余额变动与对应分录逐桶一致。
3. `available >= 0`、`frozen >= 0`、`hold.remaining >= 0`。冻结余额应与对应未消费预占按同一截止状态核对。
4. 本模型一笔成交要么四个资产桶全部结转，要么全部不结转；不能靠事后对账代替事前原子性。
5. `HB/HS: ACTIVE → CONSUMED`，对应剩余量降到零。本案例无部分消费；部分成交是明确改变数量条件后的变体。
6. `settlements` 只有整体提交后才代表 `APPLIED`。事务内可以先插入身份再补齐结果，但不得把未完成身份单独提交。
7. 缓存值、缓存锁、客户端超时和副本的“查无记录”都不能决定是否释放预占或再次记账。
8. 成交已确定但入账条件异常时保留义务并隔离修复；不能把技术失败偷换成成交取消。

### 4.2 架构与职责

```text
已确定成交的权威来源
    │ 稳定身份、规范化经济字段、可重复交付
    ▼
Go 入账服务
    │ 同一 *sql.Tx；固定锁序；所有失败检查
    ▼
PostgreSQL 主库
    ├─ settlements：业务身份与完整入账结果
    ├─ balances / holds：执行时可支配状态与预占
    ├─ ledger_entries：逐资产、逐桶不可随意改写的变动事实
    └─ outbox：同提交的待交付失效/结果通知
             │ 事务外重试、可能重复
             ▼
       缓存失效与查询投影
             ▼
       Redis / 可滞后读副本 / 页面

资金裁决与未知提交核验 ─────────→ 主库权威事实
```

服务可以合并部署，职责不能合并成“Redis 加锁之后就安全”。不在持有数据库事务锁时等待 Redis 或外部 RPC；出站副作用放在事务之后，并用稳定身份处理重复。

### 4.3 核心对象与锁协议

| 对象 | 必要字段与约束 | 本专题的保证 |
|---|---|---|
| settlements | `trade_id` 主键，`payload_hash`、`status`、`result` | 提交记录为 APPLIED 且结果完整；hash 包括双方、预占、币种、整数数量与规则版本，不包含重试时间 |
| balances | `(account_id, asset)` 主键，`available`、`frozen`、`version` | 非负检查；更新成功版本递增；四行预先创建 |
| holds | `id` 主键，`account_id`、`asset`、`remaining`、`status`、`version` | 归属与消费资格核验；余额更新与预占更新同事务 |
| ledger_entries | `(trade_id, leg_no)` 唯一，账户、币种、资产桶、整数 `delta` | 本案例固定四腿；唯一约束防同一腿重复，跨行守恒由封闭写入路径校验 |
| outbox | `event_id` 唯一，`aggregate_id`、`version`、`payload`、`delivery_state` | 示例 `T100:applied`；payload 含四个余额键及各自更新后版本，部分失效失败可重试整个集合 |

`outbox.version = 1` 表示成交结果事件版本，不是全局提交序号，也不是四个余额共用的版本。余额键各有独立 `version`。

**所有修改余额或预占的写者：** 先按明确的 `(account_id, asset)` 升序逐行锁定本次所需的全部余额，再按 `hold_id` 升序锁定全部预占；锁住后校验并修改。不能假定任意 `WHERE id IN (...)` 都按调用方列表顺序加锁。新预占、释放和成交消费都必须遵守，不能一条路径先拿 hold 锁，另一条路径先拿余额锁。

### 4.4 实现与失效边界

- RC 下唯一约束负责身份竞争；冲突不插入后，用下一条语句读取已提交结果，核验载荷。不能以应用层 `SELECT` 查重代替唯一约束。
- 条件更新必须检查影响行数；涉及多行和多项条件时，用统一锁协议缩小推理范围，不能认为“加了事务”就自动消灭业务竞争。
- 缓存采用 **cache-aside + DB 提交后删除 + 同事务 outbox 重试 + 有限 TTL**。这是普通展示的弱一致方案，允许旧值回填窗口，不宣称线性一致或严格固定最大陈旧时间。
- Redis 版本水印、因果位点和跨分片协议都是相应母题中明确改变前提后的加强方案，不当作基础方案已经具备的功能。
- 单库 Commit 成功的耐久性依赖 WAL 刷盘及复制/切换承诺；异步副本不能无条件接管并声称零数据损失。

## 七、工程实践：唯一简洁 MVP

### 7.1 目标与范围

手工验证一个闭环：`T100` 重复交付时，四条余额变化、两条预占消费、四条分录、一个完整入账结果和一个 outbox 记录只整体生效一次。

不实现缓存消费者、完整事件重放、数据库高可用、链上交互或跨分片事务；网络未知结果只明确返回与后续重入规则，不用虚构函数假装自动解决。下述为教学伪代码，所有 SQL/编码/错误分支都必须检查，不能直接当可运行 Go 复制。

### 7.2 核心伪代码

```text
Apply(T100, payload):
  校验来源与精度；h = 规范化载荷哈希；tx = BEGIN READ COMMITTED
  任意未处理错误均 ROLLBACK，不返回成功
  claimed = INSERT settlements(trade_id, payload_hash, status)
            VALUES(T100, h, 'BUILDING') ON CONFLICT DO NOTHING RETURNING trade_id
  if 未取得 claimed:
    old = 下一条 SELECT settlements WHERE trade_id=T100  // RC 新语句快照
    若无可核验完整结果：ROLLBACK；返回待核验，以原身份重入
    若 old.payload_hash != h：ROLLBACK；返回身份冲突
    ROLLBACK；返回 old.result
  按 (account_id, asset) 升序逐条 SELECT 四条 balances FOR UPDATE
  按 hold_id 升序逐条 SELECT HB、HS FOR UPDATE
  校验双方、币种、ACTIVE、剩余量、冻结余额和四行均存在
  若失败：ROLLBACK；返回隔离待修复，不取消既定成交
  changes = [(101,USDT,frozen,-3000000000), (202,USDT,available,+3000000000),
             (202,BTC,frozen,-10000000), (101,BTC,available,+10000000)]
  验证 changes 按币种求和均为 0
  对每项 change:
    UPDATE 对应余额桶 = 桶 + delta, version = version + 1
           WHERE 精确账户币种 AND 桶 + delta >= 0
    要求影响行数 = 1；否则 ROLLBACK 并隔离
    INSERT ledger_entries(T100, leg_no, account, asset, bucket, delta)
  对 HB、HS:
    UPDATE holds SET remaining=0,status='CONSUMED',version=version+1
           WHERE id=指定hold AND status='ACTIVE' AND remaining=约定消费量
    要求影响行数 = 1；否则 ROLLBACK 并隔离
  result = 四行更新后余额与各自版本
  UPDATE settlements SET status='APPLIED',result=result WHERE trade_id=T100
  要求影响行数 = 1
  INSERT outbox('T100:applied',T100,1,四个余额键及各自版本,'PENDING')
  err = COMMIT
  if err 是不能确认结果的通信错误：返回 UNKNOWN(T100)，后续只查/重入原身份
  if err 是明确事务失败：返回可分类错误，不返回 result
  return APPLIED(result)
```

`BUILDING` 只存在于尚未提交的事务中；只有补齐结果才允许提交。服务写入权限、写入路径和提交前校验必须封闭，不把一张允许任意写入的表误当成数据库自动保证完整四腿。正式结构可以进一步用受控存储过程/延迟约束触发器加强跨行检查，不能用普通 `CHECK` 声称已经检查其他表。

### 7.3 输入与预期结果

以下案例独立从指定状态开始，均为**手工预期，不是测试通过记录**。

| 输入或故障窗口 | 预期结果 |
|---|---|
| 初始状态第一次投递 T100 | 买方 USDT 7,000/0、BTC 0.1/0；卖方 BTC 0.4/0、USDT 3,000/0；两预占消费；四分录、一结果、一 outbox |
| 已成功后，同载荷再投递 T100 | 返回原结果；余额和预占不再次变化，不增加分录或 outbox |
| 已成功后，T100 数量改为 0.2 BTC | 身份与载荷冲突，不能当第二笔成交，也不覆盖原结果 |
| 第三条余额修改后插分录失败 | 所有本次变化回滚，HB/HS 保持原状态，不提交 BUILDING |
| 两个工作者同时投递同一 T100 | 唯一身份竞争使其收敛到同一结果；等待、死锁等技术错误依分类重试，不能两个都改钱 |
| COMMIT 发出后断网 | 调用方 UNKNOWN；若实际提交，原身份重入读原结果；若实际回滚，原身份可重新取得身份并执行；两者不能累计两次效果 |
| DB 已提交，Redis 完全不可用 | APPLIED 不撤销；outbox 保留交付义务；普通查询受限降级，资产操作仍按主库事实裁决 |
