# 大问题 5：唯一约束怎样实现成交幂等，提交结果未知时怎样恢复？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 幂等 / 稳定 trade_id | 同一业务反复送来，仍只产生一套已提交效果。 | T100 永远指向这笔 0.1 BTC 换 3000 USDT 的成交，不因重试换号。 |
| 先查再写竞态 | 两个处理者都查不到，于是都以为自己是第一次。 | 普通 SELECT 不能替代数据库唯一约束裁决身份。 |
| settlements / APPLIED | 持久成交身份、状态及完整入账结果。 | 与四腿账务、余额、hold 和 outbox 同提交，不能先单独标“已处理”。 |
| payload_hash / 规范化载荷 | 用固定编码核对同一身份对应的业务内容。 | 包含账户、币种、整数金额、预占和规则版本，不把重试时间混进去。 |
| 同身份异载荷 | 编号没变，经济事实却变了。 | T100 从 0.1 改成 0.2 BTC 要冲突告警，不能冒用旧成功。 |
| ON CONFLICT DO NOTHING | 遇到指定唯一竞争时不插入，走正常冲突分支。 | 避免把预期的成交重投变成 PostgreSQL 事务异常。 |
| RETURNING / 下一条 SELECT | 看本次是否取得身份，再用新语句读取赢家。 | PG RC 唯一检查可等待赢家，但同语句普通快照不一定看得到它。 |
| 23505 / savepoint | 唯一冲突错误与预先建立的事务保存点。 | PG 普通冲突后事务失败；仅在 Go catch 不能让它恢复可用。 |
| UNKNOWN / Commit 网络错误 | 调用方暂时不知道服务器是否完成提交。 | 不信原事务内存结果，改用新连接核验权威主库。 |
| 暂时查无记录 | 此次查询快照还没看到持久完成结果。 | 原事务仍可能稍后提交，空结果不是已经回滚的证明。 |
| 原身份重入 | 保持业务编号和载荷不变，重新走受约束的事务。 | 原事务提交就读回原结果，回滚才可能由恢复者取得身份。 |
| 归档 / 唯一登记屏障 | 旧结果可搬迁，但禁止旧业务再次进入的依据仍要有效。 | 不能像删缓存一样清掉 T100 后重新开放入账资格。 |
| 至少一次 / outbox | 允许重复交付，用持久记录确保交付可恢复。 | 账务提交后确认丢失可再投递；通知接收方仍需处理重复。 |
| event.version / balance.version | 成交事件版本与每条余额自身的版本。 | T100:applied 的版本 1 不等于四个账户余额的共同进度。 |
| fencing / epoch | 在实际写入端检验新旧执行资格的围栏代次。 | 租约本身不拦 PG 写入，围栏也不替代成交唯一身份与共同提交。 |

## 把整篇文章压缩成一个故事

T100 的交付应答丢了，两个工作者同时收到“小林用 3000 USDT 买小周 0.1 BTC”。它们先查都没找到，若只靠这次查询就改钱，会各做一遍。正确做法是竞争 PostgreSQL 的 T100 唯一身份：赢家把四腿账务、余额、HB/HS 消费、完整 APPLIED 结果和 outbox 一起提交；另一方核对载荷并返回同一份持久结果。

在 RC 下，ON CONFLICT 可能等到赢家提交，却因本语句起始快照较早而不能从普通查询分支读到它，所以未插入者用下一条 SELECT 读取。若第二次仍叫 T100 却改为 0.2 BTC，应冲突隔离，不是再造 T101。普通 INSERT 撞唯一键后，Go 即使捕获错误，PG 事务也已经失败，不能接着当正常事务使用。

更棘手的是赢家发出 COMMIT 后断网。它只能报告未知，用新连接按原 T100 查主库；暂时查不到也不能退款，因为原提交可能仍在完成。恢复者继续用同身份同载荷重入，让唯一约束收敛，而非换号重扣。多年后重放也需要这道持久身份屏障。这里保证的是同一权威单库内一套经济效果，不是消息、Redis 或外部系统都只物理执行一次。

**流程位置与核心机制：** 围绕 T100 的重复交付、唯一键竞争、事务完成标记与提交未知恢复。目标是在同一权威单库中让同一成交只产生一套已提交账务效果，不把它泛化为全链路 exactly once。

**沿用总览基线：** 链下托管 BTC/USDT；T100 已确定为 0.1 BTC × 30000 USDT/BTC = 3000 USDT，不计费。PostgreSQL 16 RC，Go 1.21+ `database/sql`，BTC `1e8`、USDT `1e6` 整型最小单位。唯一 settlement、四条分录、四条预建余额、HB/HS 与 outbox 同事务提交；资产锁先按 `(account_id, asset)` 升序逐条取齐 balance，再按 hold_id 升序取 hold。Redis 7.x 可丢失，缓存与副本滞后不得影响资产正确性。

## 第 1 层：为什么“先查有没有 T100”不构成幂等？

**面试官：** T100 被重复投递两次，两个处理者都先查 settlements，查不到才入账，这样安全吗？

**面试者：** 不安全，两个 RC 查询可能都在对方提交前看不到记录。T100 必须有来自成交事实的稳定 trade_id，由数据库唯一约束裁决谁能创建它，而不是靠先查或进程互斥。获得身份的事务才执行本次四条分录、余额及 hold 更新，并在同一事务里形成结果与 outbox；未获得身份的处理者核对并返回原结果。`(trade_id, leg_no)` 唯一约束是分录层防线，但不能代替完整成交事务。不能先单独提交“已处理 T100”，否则后面的账务失败会被这个标记永久挡住。

## 第 2 层：同一个 trade_id 却带着不同金额怎么办？

**面试官：** 你用 T100 做身份。如果第二次请求仍叫 T100，却把数量改成 0.2 BTC，直接返回成功会不会掩盖错误？

**面试者：** 所以身份之外还要保存并比较 payload_hash。同一 trade_id 应对应不可变的业务事实，规范化内容包括买卖账户、币种、数量、金额、价格及其精度、HB/HS 引用和必要的规则版本，金额用最小单位整数，不依赖浮点字符串格式。hash 的编码与版本也应固定，必要时保留原始规范化载荷供核对。查到同身份同载荷才返回原结果；身份相同而载荷不一致应明确报冲突、告警，不覆盖旧记录或偷偷生成 T101。对已确定成交，这意味着交付或数据完整性问题，不意味着可以自行撤销成交或释放 hold。

## 第 3 层：PostgreSQL RC 的 ON CONFLICT 应怎样读取赢家？

**面试官：** 载荷也固定了，两个事务仍可能同时 INSERT。怎样不靠异常处理抢到身份，并取到原结果？

**面试者：** 可以用 `INSERT INTO settlements (...) VALUES (...) ON CONFLICT (trade_id) DO NOTHING RETURNING trade_id`。返回一行表示本事务获得身份，随后完成账务并在提交前填好 APPLIED/result；草稿只存在于未提交事务，基线不单独持久化 PENDING。返回零行说明没有插入，唯一索引检查可能已等待另一个事务提交，而对方记录不一定在本条 INSERT 起始快照内可见。因此在 RC 下用下一条 SELECT 获取新语句快照，再读持久结果并比较 hash。不要强求同一条语句的普通查询分支一定能看到冲突赢家；对方若回滚，本次 INSERT 则可能继续成功。

## 第 4 层：为什么 catch 唯一冲突后不能直接继续查询？

**面试官：** 不用 ON CONFLICT，直接 INSERT，遇到唯一冲突后 catch 一下，再在当前事务里 SELECT，不也一样吗？

**面试者：** PostgreSQL 普通 INSERT 触发 `23505 unique_violation` 后，事务会进入失败状态；应用 catch 只是控制 Go 分支，没有修复数据库事务，继续 SELECT 通常得到事务已中止的错误。最简单的做法是回滚，再开启新事务或查询原结果；事先有正确的 savepoint 才能回滚到保存点继续，但没有必要为预期幂等冲突增加这套复杂性。ON CONFLICT 正是把预期的唯一竞争变为正常分支。其他唯一键冲突也不能一概当作 T100 重投成功，仍需识别冲突对象并核验持久事实。

## 第 5 层：Commit 返回网络错误，究竟算成功还是失败？

**面试官：** 获得身份的事务已经写好全部账务，但 `tx.Commit()` 返回连接错误。此时能不能回滚并告诉上游重做？

**面试者：** 不能武断判失败。COMMIT 可能已在服务器完成，只是成功应答丢失；也可能根本没完成。Go 这时已经不能依赖原 `*sql.Tx` 继续查询或重发 SQL，defer Rollback 也证明不了服务端已撤销。我会把结果标记为未知，用新的连接按原 T100 查询权威主库。若找到载荷一致的 APPLIED/result，就按已完成处理；因为 settlement 与四条分录、四条余额、HB/HS 和 outbox 同提交，这条持久结果具有完成含义。不能换 trade_id 再入账，不能把冻结资金先退回以“补偿网络错误”。

## 第 6 层：主库暂时查不到，为什么还不能认定失败？

**面试官：** 你用新连接查了权威主库，暂时没有 T100。不是已经证明刚才的事务没提交吗？

**面试者：** 只证明这次 SELECT 的快照没看到已提交 T100。原事务可能仍在执行、等待锁或完成提交，不能从一次空结果推导它未来不会提交；更不能拿副本或 Redis 的空结果作证明。恢复者应保持同一身份、同一载荷，重新执行受唯一约束保护的入账事务：原事务提交就进入冲突读取原结果，原事务回滚才可能由恢复者取得身份。若权威主库不可达或仍不能确定，就继续保持未知并排队恢复，不凭超时宣布失败或释放 HB/HS。客户端等待预算结束，不等于成交义务结束。

## 第 7 层：多个恢复者用同一个 key 重试，会不会再次重复？

**面试官：** 如果三个恢复者同时按 T100 重试，甚至上游也在重投，怎样避免它们相互覆盖结果或无限等待？

**面试者：** 它们仍竞争同一唯一键，数据库允许最多一套该身份的事务提交。每次尝试使用新事务，先完成身份竞争再拿资产锁，避免某些处理者先锁余额、另一些先等身份造成额外锁序倒置。未插入者用下一语句读结果、核对 hash，返回原 result，而不是重新计算一份“当前余额”冒充当时结果。应用可对同 key 合并等待，并用有界次数、抖动退避和 context 控制资源；超过预算返回处理中或未知，由持久恢复继续接管。重试次数变化不改变 trade_id、payload 或已经确定的成交事实。

## 第 8 层：去重记录能不能像缓存一样过期删除？

**面试官：** T100 已经处理很久了，能不能删掉 settlements 来节约空间，只保留最近一天去重？

**面试者：** 不能只按时间删除后重新放开身份。成交可能因历史回放、人工恢复或延迟消息多年后重现，Redis TTL 更不能定义财务幂等窗口。需要长期保存可校验的权威身份、载荷摘要与结果引用；归档时仍保留能够强制阻止再次创建 T100 的唯一登记，或者把权威查询和唯一性规则一起迁移到有明确切换协议的存储。只把旧行搬到另一个表、从活跃表删除，却不保留准入屏障，会让新 INSERT 重新成功。分录唯一键能额外挡错，但不能把预期幂等完全寄托在后续撞错回滚上。

## 第 9 层：至少一次消息与 outbox 到底承诺了什么？

**面试官：** 你持久保留身份。若消息至少一次投递，事务提交后进程没来得及确认，重复消息和重复通知怎样收敛？

**面试者：** 接收方只在账务提交可确认、或者恢复查询已确认原结果后，才报告处理完成；提交后确认前崩溃，消息会重来，再由 T100 唯一身份返回原结果。outbox 与账务共同提交，例如 `T100:applied`、aggregate_id T100、event.version 1，payload 带四个余额键及各自更新后 version，用于可靠失效或结果交付。外部动作与 delivery_state 更新之间仍有重复窗口，所以接收通知的一方也需幂等。这里实现的是同一数据库中同成交的一套已提交效果，不是网络、缓存或所有外部系统都物理执行一次。

## 第 10 层：fencing 能否把恢复升级为“全局恰好一次”？

**面试官：** 如果再给恢复任务加租约和 fencing token，是否就能彻底消除旧任务并发，宣称 exactly once？

**面试者：** 不能把范围说大。fencing 是独立的任务所有权增强变体：只有权威写入端持久保存并原子检查递增 epoch，才可以拒绝旧持有者；Redis 租约过期或新任务持有 token，本身不会阻止旧进程写 PostgreSQL。校验还必须与受保护写入同事务，所有写者都遵循它。基线已有的唯一身份、载荷核验与账务共同提交依然不能省，token 也不改变业务 trade_id。若旧任务提交结果未知，仍查询或恢复原 T100；如果切主可能丢失已确认提交，还要先定义持久性和切换契约，不能用 fencing 掩盖数据丢失。

## 收束：机制、边界与反例

- **讲透的机制：** 稳定身份加规范化载荷、数据库唯一竞争、RC 下一语句读结果、结果与账务共同提交、提交未知时按原身份恢复。
- **易错边界：** ON CONFLICT 的唯一性检查与普通语句快照不是同一可见性规则；PG 事务失败不能 catch 后照常使用；空查询、context 超时和 Commit 网络错误都不构成释放依据。
- **反例检验：** 原 T100 已提交但应答丢失，服务换成新身份再消费一次。即使每个身份都满足唯一约束，也没有业务幂等；正确恢复始终沿用 T100，最终仍只有四条分录、两 hold consumed 和一份 APPLIED 结果。

**核实资料：** [PostgreSQL 16 RC 与 ON CONFLICT 语义](https://www.postgresql.org/docs/16/transaction-iso.html)、[PostgreSQL 16 显式锁](https://www.postgresql.org/docs/16/explicit-locking.html)。
