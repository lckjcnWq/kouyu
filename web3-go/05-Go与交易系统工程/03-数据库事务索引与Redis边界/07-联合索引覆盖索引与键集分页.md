# 大问题 7：交易查询怎样设计联合索引、覆盖索引与键集分页？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 查询形态 | 查询按什么筛选、怎么排序、取多少条、返回哪些列。 | 先区分余额定位、T100 查重、账务列表和 outbox 扫描，再选择索引。 |
| 主键 / 唯一索引 | 快速定位记录，并强制身份不能重复。 | balances 的账户币种键、T100 的 trade_id 不只是性能工具，不能随意删掉。 |
| 联合 B 树索引 | 把多个字段按约定次序排进一套检索目录。 | 账户和币种等值定位后，再按时间和 ID 倒序取记录是候选路径。 |
| 左侧键 / 扫描区间 | 索引前面的字段影响从哪里开始、要走过多少记录。 | 缺少币种条件时，不能假定分币种排列天然提供账户全币种时间顺序。 |
| created_at / entry_id | 记录时间与不可变、非空的唯一分录编号。 | 时间相同时靠 entry_id 稳定排先后，二者都不是全局提交水位。 |
| 稳定排序 | 相同时间的记录也有明确的并列裁决规则。 | 查询与索引都按时间、ID 倒序，游标边界才可复现。 |
| OFFSET / LIMIT | 跳过前面若干条，再取限定条数。 | 深页通常仍需扫描并丢弃大量记录，不是直接跳到免费位置。 |
| keyset / 键集分页 | 记住上页最后的排序键，从它之后继续找。 | 用二元游标取更小的键；同为倒序且非空才可直接用本文元组比较。 |
| 游标绑定 | 翻页标记同时带上筛选范围与访问归属。 | 账户、币种、方向不能随意替换，游标也不应成为越权入口。 |
| MAX(entry_id) / 完整前缀 | 看见的最大编号，与之前每笔都已完整提交是两回事。 | 小 ID 可能晚提交，最大值不能证明没有遗漏。 |
| 一致性快照 / 审计导出 | 固定读取集合后再做完整核对。 | 普通在线列表可变化；完整导出需要受控快照或封闭业务水位。 |
| INCLUDE / index-only scan | 把返回列也存进索引，使查询可能主要从索引取数。 | PG 即使包含 delta、bucket，也不保证永远不用访问表。 |
| all-visible / Heap Fetches | 表页可见性标记与实际访问表页的次数。 | PG 还要判断 MVCC 可见性，写入频繁区域可能继续回表。 |
| InnoDB 聚簇主键 | MySQL 按主键组织数据，二级索引叶子还带主键。 | 它的覆盖路径不能用 PostgreSQL 可见性图的规则解释。 |
| 部分索引 / PENDING | 只给满足固定条件的记录建立索引。 | PG 可缩小待交付 outbox 扫描；查询须能证明满足谓词，MySQL 8.0 不直接等同支持。 |
| 写放大 / 候选索引验收 | 写一条业务记录还要维护更多索引与日志。 | 读得快不代表整体更好，必须结合负载、计划、尾延迟和写入成本评估。 |

## 把整篇文章压缩成一个故事

小林想看账户 101 的 USDT 流水，每页 50 条，还要能找到 T100 的记录。工程师阿宁先分开需求：按账户币种查余额、按 trade_id 找入账结果已有主键或唯一索引保护；流水列表则考虑账户、币种在前，时间和 entry_id 倒序在后的联合索引。时间相同用唯一 ID 决定次序，避免一页边界上的记录顺序飘动，但这还只是候选方案。

翻到很深时，阿宁不用 OFFSET 丢弃十万条，而把上页最后的时间和 ID 放进游标，继续找更小的键，同时绑定账户、币种和权限。小林浏览实时列表可以刷新看新记录；审计人员却不能因此认定导出完整：某笔提前分配小 ID 的事务可能在翻过该位置后才提交。稳定排序不等于完整提交前缀，审计需要另设受控快照或封闭水位。

阿宁再尝试把金额变化和资产桶放进 PG 索引，却仍检查 Heap Fetches，因为 MVCC 可见性可能要求回表。给 PENDING outbox 做部分索引也有维护成本，不能照搬到 MySQL。最终保留哪些索引，要用代表性数据比较扫描、排序、尾延迟和 WAL 成本；不能为提速删掉正确性唯一约束，也不能凭“用了覆盖索引”就宣称性能永远稳定。

**流程位置与核心机制：** 从 T100 的余额定位与账务列表出发，推导索引键顺序、排序和分页；下一题负责用实际计划诊断性能，不能把本题的候选索引当成已经测量有效。

**必要前提：** PostgreSQL 16 为基线，MySQL 8.0 InnoDB 只作显式比较。账务事实沿用总览；为查询说明补充 `created_at` 和唯一 `entry_id`，不把它们当全局提交水位。

## 第 1 层：不是每个过滤字段都该加索引

**面试官：** 余额和账务查询慢，你怎样决定加哪些索引，而不是所有 WHERE 字段各加一个？

**面试者：** 我先列主要查询形态：执行时按账户币种定位余额，按成交身份查入账结果，按账户、币种、时间列账务，按未交付状态扫描 outbox。前两类由主键或唯一索引直接承担；列表和后台扫描则需要匹配过滤、排序、LIMIT 的候选索引。

例如余额主键是 `(account_id, asset)`，T100 去重用 `trade_id` 唯一约束，不能为了性能去掉正确性约束。账务列表可考虑 `(account_id, asset, created_at DESC, entry_id DESC)`。我会同时估计行数分布、热点账户和写入成本，再用代表性计划验证。单列索引可能被组合，也可能需要大量排序；“字段出现就加索引”没有解释访问路径，更没有解释账务高写入下的代价。

## 第 2 层：联合索引的键顺序为什么这样放

**面试官：** 你提出账户、币种、时间和 ID 的联合索引。把时间放最前面不也能筛选最近记录吗？

**面试者：** 对“账户 101 的 USDT 账务，按时间倒序取前 50 条”，账户和币种是等值条件，先定位一个连续键区间，再按时间与 ID 顺序向后取少量记录，通常比扫描全平台最近记录再过滤账户更可控。

如果查询没有币种过滤，`(account_id, asset, created_at, entry_id)` 中不同币种分组，不能直接认为它已经提供账户全币种的统一时间顺序。可能另建 `(account_id, created_at DESC, entry_id DESC)`，也可能接受排序，要根据负载选择。联合 B 树的左侧条件通常最影响扫描区间；后续字段仍可能参与过滤，不能背成“遇到范围条件后所有字段永远无效”，也不能假定优化器在每个版本都自动替我补全理想路径。

## 第 3 层：稳定排序需要唯一的并列裁决键

**面试官：** 为什么还要 entry_id？只按 created_at 倒序不更简单吗？

**面试者：** 同一个时间戳可能写入多条账务，尤其批量处理 T100 四个分录时。只按 created_at 排序，相同时间内没有稳定次序，LIMIT 边界就可能重复或遗漏。因此我把不可变、非空的唯一 entry_id 作为最后一个裁决键，并让查询与索引使用同样的排序方向。

这里 ID 只承担唯一排序，不承担提交先后或业务因果：事务先拿到序列值，可能后提交。游标需要携带上页最后一条的 `(created_at, entry_id)`，账户和币种等筛选条件也必须与游标绑定。服务还要检查游标归属，不能让客户端换账户后复用旧游标越权读取其他人的账务。

## 第 4 层：深分页为什么用键集而不是 OFFSET

**面试官：** 有稳定排序以后，OFFSET 100000 LIMIT 50 不就可以翻到后面了吗？

**面试者：** OFFSET 通常仍要走过并丢弃前面的许多匹配行，页越深成本越大。键集分页用最后一个已见排序键继续扫描，候选查询为：

```sql
SELECT entry_id, created_at, delta, bucket
FROM ledger_entries
WHERE account_id = $1 AND asset = $2
  AND (created_at, entry_id) < ($3, $4)
ORDER BY created_at DESC, entry_id DESC
LIMIT 50;
```

这里两列非空、同为倒序，才可以直接用这个元组比较；混合升降序需要改写比较条件。第一页没有游标谓词。这个方案避免深 OFFSET，却不能免费支持“跳到第两万页”，也不能自动固定跨请求快照。它解决的是访问路径和稳定边界，不是所有列表语义。

## 第 5 层：键集分页为什么仍可能漏掉新提交的旧键

**面试官：** 你说不能固定快照。既然 entry_id 唯一、顺序稳定，为什么还会遗漏？

**面试者：** 假设事务 A 提前分配 ID 和 created_at 后未提交，用户第一页已经越过那个排序位置，A 才提交；下一页用“小于游标”继续走，A 新出现的记录如果落在已翻过区间，就不会出现在后续页。稳定键并不等于完整提交前缀，`MAX(entry_id)` 也不能证明较小 ID 都已提交。

普通用户列表可以接受“边翻边变化”，通过刷新首页发现新结果；审计导出则应采用同一数据库一致性快照、受控导出任务，或具有缺口检测的封闭业务水位。不能为所有用户长期持有 RR 事务来冻结无限列表，否则会拖累版本清理。需求从在线浏览变成审计完整导出时，必须明确改变合同与资源成本。

## 第 6 层：覆盖索引不等于永远不访问表

**面试官：** 列表只返回 delta 和 bucket，把它们也放索引里，是不是就完全不用读表了？

**面试者：** PostgreSQL 可以考虑 `INCLUDE (delta, bucket)`，但它只让索引存有所需列，index-only scan 仍受 MVCC 可见性影响。页没有相应 all-visible 标记时，需要访问 heap 判断可见性，写入频繁的账务末尾不一定能达到理想覆盖效果。还要检查实际计划里的 Heap Fetches，而不是看到 INCLUDE 就宣布零回表。

MySQL InnoDB 二级索引叶子带主键，覆盖查询和聚簇主键布局要按该引擎解释，不能套 PostgreSQL 的可见性图说法。无论哪种实现，索引变宽都会增加内存、存储和写入成本。金额、资产桶作为候选覆盖列可以讨论，但把整段 JSON 结果也塞进去，往往先把写放大和缓存效率变坏。

## 第 7 层：热点扫描与部分索引怎样控制成本

**面试官：** 账务是追加写还好，outbox 一直把 PENDING 改成已交付，你会怎么给后台扫描设计索引？

**面试者：** PostgreSQL 可以针对固定谓词考虑部分索引，例如只索引 `delivery_state='PENDING'` 的 `(created_at, event_id)`，让少量待处理记录的扫描避开大量历史完成记录。实际查询必须能让规划器证明满足谓词，参数化和通用计划不一定都能使用预期部分索引。

状态改变会把记录移出索引，仍有维护、WAL 与死元组成本；不能说部分索引免写放大。MySQL 8.0 不直接具备同样的任意谓词部分索引，可以比较普通状态联合索引或经明确设计的替代结构。账务分区也不是索引替身：按时间分区有利于裁剪和归档，但唯一约束范围、跨分区查 trade_id 和全局幂等仍需单独保证。

## 第 8 层：怎样验收一个索引是否值得留下

**面试官：** 你列了好几个候选索引，怎样决定最终保留哪个，不让索引越堆越多？

**面试者：** 我会固定代表性 SQL、账户规模分布、时间范围和返回列，比较计划中的扫描行数、排序、缓冲区访问、堆访问和延迟分布，再同时观察写入 WAL、索引大小、缓存命中与维护开销。小表顺序扫描或大范围查询走顺序扫描并不一定是退化，强制索引不能替代成本分析。

例如全平台离线统计不该为了命中账户列表索引而改成无数小查询；超大热点账户也不能只看普通账户的平均效果。删除索引前先区分正确性唯一约束和纯性能索引，确认依赖及完整观测周期，再规划回退。面试中我能说明候选路径与验证口径，但没有真实负载数据时不会编造“上线提速多少倍”。

## 本题收束

- **讲透的机制：** 查询形态决定联合键序，唯一排序支撑键集分页，覆盖能力要结合引擎可见性与写入成本。
- **最容易答错的边界：** 唯一递增 ID 不是完整提交水位；键集分页不是跨请求一致性快照。
- **验证反例：** 延迟提交一个较小排序键的事务，在第一页返回后提交它，检查列表与审计导出是否分别符合各自合同。
