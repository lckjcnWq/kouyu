# 大问题 12：Redis 分布式锁在暂停、过期与故障切换后还安全吗，资金正确性究竟靠什么？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 协调锁 / 资产约束 | 减少重复工作与强制不重复扣钱是两种职责。 | Redis 锁保护扫描、重建的效率，T100 资金仍由数据库唯一身份和事务保护。 |
| SET NX PX | 只在键不存在时占有，并同时设置租约期限。 | 不能先占有再单独补期限，每次获取使用新的随机 token。 |
| random_token | 标识某一次租约是谁拿到的随机值。 | 用来比较释放和续期资格，没有大小顺序，不是围栏代次或成交编号。 |
| 条件解锁 / 条件续期 | 只有锁键仍属于自己才删除或延长。 | 防止 A 过期后误删 B 的新锁，却不能阻止 A 继续做旧工作。 |
| lease / 租约过期 | 允许在约定时间后重新获得协调资格。 | Redis 允许 B 拿锁，不等于撤销 A 的 PG 连接或已发出的请求。 |
| 长暂停 / 网络分区 | 执行者暂时不运行，或只能访问一部分节点。 | A 可能超过租约后恢复，与 B 的任务发生重叠。 |
| watchdog | 周期续期的看护逻辑。 | 能降低正常过期概率，但可能一起暂停或丢请求，不能证明互斥。 |
| 检查与使用窗口 | 检查资格后到真正写入前，资格可能变化。 | 先查自己持锁再无条件写数据库，仍可能在中间过期。 |
| fencing / epoch | 受保护资源用代次拒绝旧执行者的写入。 | 必须在实际写入原子边界检验，不能只由客户端自报或自觉停止。 |
| 权威 fence 行 | 在可靠数据库里保存当前有效代次的协调对象。 | 授权切换与受保护写锁同一权威行校验，前提是持久历史不回退。 |
| Redis INCR 回退 | 计数器故障恢复后可能失去已应答过的增量。 | 看似递增的数字不能无条件作为数据库可靠单调授权。 |
| RDB / AOF | Redis 定时快照与追加命令日志的持久化方式。 | 数据保留窗口受快照、刷盘策略影响，持久化不自动解决角色切换隔离。 |
| WAIT / 复制确认 | 等一定数量副本确认到达某个复制偏移。 | 不等于所有候选已刷盘，也不把 Redis 变强一致；未满足不撤销原写。 |
| Redlock | 在多个独立 Redis 实例获取多数租约的方案。 | 仍依赖时间与故障假设，也不自动赋予外部数据库围栏能力。 |
| outbox / 重复 DEL | 持久通知任务与可重复执行的缓存删除。 | 两个工作者重叠删除 T100 四个余额键，不该改变任何资产。 |
| Commit UNKNOWN / 原身份恢复 | 提交应答不明时沿业务原编号核验。 | 用原 T100 查主库或重入，不因丢锁换号，也不按超时释放 HB/HS。 |

## 把整篇文章压缩成一个故事

阿宁让工作者 A 拿 Redis 租约扫描 T100:applied，任务只是删除四个余额缓存键，不是批准 T100 结算。A 突然长暂停，租约过期，B 拿到新锁继续扫描。A 恢复时，比较随机 token 的 Lua 可以阻止它误删 B 的锁，却不能收回 A 已持有的数据库连接或已经发出去的工作；两个执行者仍可能重叠，所以扫描和确认必须能承受重复。

同事建议加 watchdog、AOF 和 WAIT。阿宁逐一划边界：续期也会暂停，刷盘与复制确认也不自动阻止旧主继续活动；WAIT 没等够还不会回滚先前写入。Redlock 的多数租约同样不自动给外部资源装围栏。若真要拒绝旧执行者，得让实际资源持久保存授权代次，并在同一写入原子边界校验，新代次未在资源端激活前不能假装旧写已被封住。

回到资产，T100 是 0.1 BTC 换 3000 USDT，唯一身份、四腿分录、四条余额、HB/HS 和 outbox 在 PostgreSQL 一起提交。即使 A、B 都来结算，也只能收敛为同一载荷的一套效果；若 COMMIT 断网，按原 T100 查主库恢复，不换号、不超时退款。重复 DEL 最多影响命中率，若丢一次 Redis 锁就多扣钱，错的是资产写入边界，而不是锁时间不够长。

**流程位置与核心机制：** 本题把锁限定在 outbox 扫描、缓存重建等协调工作，追问租约、围栏与 Redis 持久化的边界，不实现锁框架。业务基线仍是链下托管现货 BTC/USDT、PostgreSQL 16 RC、Go 1.21+ `database/sql`、Redis 7.x；T100 已确定为 0.1 BTC 换 3000 USDT，无手续费。BTC、USDT 以 1e8、1e6 最小整型单位计量，Redis 不是资产真相。

## 第 1 层：先决定锁失败后能不能重复工作

**面试官：** 你准备用 Redis 锁保护什么？如果它偶尔出现两个持有者，T100 会不会被结算两次？

**面试者：** 我只让它减少 outbox 扫描、同键缓存重建等重复工作，不让它决定资产能否扣减。即使两个扫描器同时处理 `T100:applied`，重复 DEL 也应安全；即使两个重建者同时回源，数据库资金事实也不能变化。任务领取和确认仍由数据库里的可恢复状态约束，不能因为“拿过 Redis 锁”就永久跳过任务。T100 是否已经结算，靠 settlements 的 trade_id 唯一约束以及同一事务里的账务结果判断，而不是一个过期键。因此，我会先验证不拿锁时系统仍然正确，只是多做一些工作；如果重复执行会多扣钱，问题在受保护资源缺少持久约束，不能靠调长锁时间掩盖。

## 第 2 层：一把租约锁的最小协议是什么？

**面试官：** 既然只用于减少重复扫描，具体怎样加锁和解锁，为什么不能直接 DEL 锁键？

**面试者：** 可以用 `SET lock_key random_token NX PX lease_ms`，设置占有和期限必须是一个操作，每次获取使用新的不可猜随机 token。释放时执行短 Lua：只有当前值仍等于自己的 token 才 DEL。否则 A 的锁过期后 B 已拿到新锁，A 直接 DEL 就会误删 B。续期同样必须比较 token 后再延长，不能无条件 PEXPIRE。随机 token 表示本次租约身份，不是业务幂等键，也不是有大小关系的围栏序号。加锁调用超时意味着结果未知，不能按“没有收到失败”就开始工作；释放或续期无法确认时也应保守停止新工作。客户端的等待时限、租约剩余时间和业务超时分别定义，不能混成一个数字。

## 第 3 层：条件解锁为什么仍不能保证始终只有一个执行者？

**面试官：** 解锁已经校验 token 了，假设 A 执行到一半发生长时间暂停，租约过期后 B 拿锁，A 恢复时会发生什么？

**面试者：** A 不会误删 B 的锁，但它仍可能继续执行已经发出的工作，这与解锁正确是两个问题。进程暂停、网络分区或长尾调用都可能超过租约；Redis 过期只是允许新客户端获得租约，不会撤销 A 手里的数据库连接，也不会取消已到达下游的请求。A 恢复后即使先检查锁仍属于自己，也可能在检查之后、真正写资源之前再次过期，形成检查与使用之间的窗口。因此减少重复的扫描任务必须允许重叠，确认动作要有任务身份或领取代次保护；缓存重建要接受基线弱一致性，或者使用明确的版本防旧写方案。不能把“释放安全”直接提升成“业务执行永不重叠”。

## 第 4 层：watchdog 能否把过期问题变成可靠互斥？

**面试官：** 那启动 watchdog 定期续期，只要任务没完成就不让锁过期，是不是就补上了这个窗口？

**面试者：** watchdog 能减少正常长任务超时，但不能证明互斥。它与业务进程可能一起暂停，也可能只能访问 Redis、不能判断业务线程是否健康；续期请求还可能丢失或响应迟到。失去租约后停止新步骤、取消 context 是必要的自我约束，却不能阻止已经在网络中或下游执行中的写入。每次续期比较 token 可以防止给别人的锁续命，但仍没有赋予资源拒绝旧持有者的能力。真正需要这种拒绝能力时，要由资源端识别新旧授权，即 fencing，而不是无限延长 TTL。对于只做幂等 DEL 的扫描，通常没有必要为追求表面互斥增加复杂框架，持久任务状态与重复安全才是先决条件。

## 第 5 层：围栏序号必须在哪里生成、在哪里检查？

**面试官：** 你说资源要拒绝旧持有者，能不能在 Redis 每次拿锁后 INCR，带着更大的序号去写数据库？

**面试者：** 不能把可能故障回退的 Redis INCR 当成可靠单调授权。显式加强变体可以在权威数据库中维护协调资源的 fence 行，通过加锁更新计数并持久提交产生代次；受保护的数据库写必须在同一事务锁定该权威行，校验自己的代次仍等于当前授权，再执行写入。新代次激活也锁同一行，于是旧写要么先完成，要么在新代次生效后被拒绝，不能先查代次再无条件 UPDATE。若资源在外部，它必须原子保存最高已接受代次并拒绝旧请求，还要明确新代次何时在资源端激活；未激活前不能假装旧请求已经被挡住。这依赖数据库已确认提交不回退和明确的切主代际，不是数字看起来递增就足够。普通余额写本来由数据库事务保护，无须绕到 Redis 再造授权。

## 第 6 层：持久化与 WAIT 能不能让 Redis 租约成为强保证？

**面试官：** 既然问题在故障回退，给 Redis 配 AOF、RDB，再用 WAIT 等副本确认，是否就能让锁和 INCR 都足够可靠？

**面试者：** 这些措施改善数据保留概率，但不能直接推出线性一致的锁服务。RDB 可能丢失最近快照后的数据；AOF 的损失窗口取决于刷盘策略，即使更频繁落盘，也没有自动解决主从角色切换与旧主隔离。典型反例是 A 在旧主拿锁成功，锁还没复制到新主候选，旧主失联后 B 在新主又拿到同名锁。WAIT 等待指定数量副本确认复制偏移，能缩小某些丢失窗口，但不等于所有候选都持有数据，也不等于副本已按期望持久化，更不会把 Redis 变成强一致系统。即使等待条件未满足，前面的写也不会回滚。锁键、计数与水印均可能回退，故障恢复不能继续沿用未成立的单调性承诺。

## 第 7 层：Redlock 是否等于金融级互斥？

**面试官：** 单主切换有这些问题，那换成 Redlock 多节点多数派，是否就能把 T100 的正确性搬到分布式锁上？

**面试者：** 不能自动得出这个结论。Redlock 在多个独立 Redis 实例上获取多数租约，还需要计算获取耗时和有效期；它的适用性依赖时钟漂移、暂停和网络延迟等假设，并增加失败清理与运维成本。即使租约获取符合算法条件，也没有自动给外部数据库提供 fencing，更没有让买卖双方的分录、余额和 hold 原子提交。我们应先问在假设被突破时，旧持有者是否仍能写资源，以及重复工作是否有害，而不是把多数派当成金融正确性的标签。本基线不要求实现或引入 Redlock：用 Redis 协调可重复的扫描，用数据库约束资产。若业务真的需要强协调，应另选并证明授权与资源校验协议，而不是更换锁名称后沿用原结论。

## 第 8 层：丢锁、重复扫描与提交未知，怎样共同闭合？

**面试官：** 回到 T100：Redis 丢锁使两个工作者重叠，其中一个 Commit 又断网。最后怎样确认没有多扣、漏记或错误释放？

**面试者：** 结算者始终按 `(account_id, asset)` 升序锁全部四条预建余额行，再按 hold_id 升序锁 HB/HS，到事务结束才释放。四条分录是买方 USDT frozen −3000、卖方 USDT available +3000、卖方 BTC frozen −0.1、买方 BTC available +0.1，每币种 delta 和为零，余额与 hold.remaining 非负。settlements 的唯一身份和 payload_hash、APPLIED/result、唯一的四条分录、余额、两个 hold 和 `T100:applied` outbox 一起提交。重复请求校验同一 payload 后复用已提交结果；Commit 断网是 unknown，按原 trade_id 查主库或重入恢复，绝不换号重扣，也不按超时释放。两个失效工作者重复删四键无妨，部分成功继续重试；Redis 锁只影响工作量，不改变最终资产。

## 本题收束

- **讲透的机制：** token 条件释放防误删，租约不能终止旧执行者，watchdog 不能替代 fencing；fence 必须由可靠权威产生，并在受保护写入的原子边界内校验。
- **最容易答错的边界：** AOF、RDB、WAIT、Redlock 各自有条件和代价，不能组合成一句“锁绝不会丢”；Redis INCR 故障回退后也不具备数据库授权所需的单调性。
- **检验反例：** A 暂停至租约过期，B 获得新租约并激活新授权，然后 A 恢复。若旧 A 仍可无条件覆盖受保护状态，所谓围栏就没有落实；若只是重复 DEL，则应依靠幂等承受重叠，而不是声称重叠永不发生。
