# 大问题 14：账户分片后怎样定义跨片结算原子性，并在同一水位对账和恢复差异？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| account_id 分片 / 原子域 | 按账户分散存储，同时改变哪些写能一起提交。 | 把 101 放 A、202 放 B 后，T100 四腿不再天然属于一个 PG 事务。 |
| 单库基线 / 局部事务 | 同一库内整体提交的边界。 | 四余额、四分录、HB/HS、唯一结果与 outbox 同提交；两个局部事务不是全局事务。 |
| 局部唯一键 / 全局身份 | 单库禁止重复的规则，与跨片同一义务的识别。 | 两片都认 T100，也不能靠各自唯一键强迫另一片同时提交。 |
| 2PC / 协调器 | 先让参与者持久准备，再持久决定全局提交或中止。 | 不是给两边发一句 COMMIT，普通 Go Tx.Commit 也不自动提供它。 |
| PREPARED / GID | PostgreSQL 已准备事务与其唯一事务标识。 | 事务可脱离原连接仍继续持锁，需要可靠恢复管理，不能超时自行撤销。 |
| 持久 COMMIT 决议 | 跨片提交决定已经不可凭猜测反转。 | 后续恢复重发同一决议，不能因参与者一时失联改为退款。 |
| 全局完成门禁 | 所有相关读取和可花资产操作都检查共同完成条件。 | 2PC 决议一致不等于两库同瞬间可见，绕过门禁仍可能看到半边。 |
| Saga / 补偿 | 局部步骤先提交，再按业务规则收敛或做反向动作。 | 已转走的 BTC 未必可扣回，补偿不能直接证明与单库合同相同。 |
| SETTLING / pending / 在途 | 义务处理中、应收但不可花及差额的审计归属。 | 显式清算变体要增加状态和记录，不能假装仍只有原四腿即可。 |
| APPLY_DECIDED / receipt | 不可撤销的应用决议与各片持久完成凭据。 | 各片消费对应 hold、记录 pending 和凭据，响应未知时按原身份查。 |
| COMPLETE / 可花转换 | 全部参与确认后形成的全局完成状态。 | pending 转 available 必须确认持久 COMPLETE 并本片幂等执行，不能提前花用。 |
| inbox / outbox / 步骤身份 | 本地重复识别、待发送任务与稳定协议步骤编号。 | 与本地金额、载荷核验、receipt 同事务提交，不因重试生成新业务。 |
| ownership epoch / 写权围栏 | 标识账户现归谁写，并在资源端拒绝旧授权。 | 迁移先关闭旧主写权再启新主，路由更新或独立双写不能替代围栏。 |
| 同水位 / 截止业务集合 | 两边比较同一批应完成的业务事实。 | 需要封闭完整前缀或配对快照；相等 MAX ID 和各自最新余额都不够。 |
| 逐币种守恒 / 未决义务 | 各币种分别核对变化，并显式列出尚在途的成交。 | 不能把 BTC 和 USDT 混加，也不能只挑已完成交易掩盖卡住的 T100。 |
| 重放 / 更正 / 冲正 | 补齐派生处理与修复已记账错误的不同操作。 | 原义务按原决议恢复，真实账错留新审计分录，不直接覆盖历史余额。 |

## 把整篇文章压缩成一个故事

负责人想把买方 101 迁到 A 库、卖方 202 留在 B 库，以为 T100 仍只是各开一个事务。阿宁让 A 先扣冻结 3000 USDT、把 0.1 BTC 变可花，再暂停 B：小林已能转走 BTC，小周却没收到钱。两边各自有唯一键也救不了这个中间态；分片改变的是原子域，不只是查 account_id 的路由。单库瓶颈没证实前，不应先引入这份成本。

若采用 2PC，两边先持久准备，协调器再记录共同决议，恢复者继续完成；B 不能因等久了自行回滚，而且共同决议也不保证两个独立读瞬间同步。另一种显式变体把 T100 标成结算中，收款先记不可花 pending，所有参与凭据确认后才按 COMPLETE 幂等转可用。这改变了可见与可花合同，不是喊一句 Saga、以后补偿，就能兑现原单库承诺。

迁移还要让旧库真正失去写权，不能 A、C 都接新成交后再比余额。阿宁要求快照与增量配对、旧侧围栏拒绝过期 epoch，再切新主。对账比较同一封闭业务集合，逐笔核对四腿、hold 和参与凭据，卡住的 pending 也要列出，最大流水号相等不算证明。发现差异先分清滞后、未决和真账错，再按原决议恢复或新增审计更正，不能直接改余额抹平证据。

**流程位置与核心机制：** 本题先守住单库结算基线，再讨论分片何时必要，以及跨片协议改变了什么。主基线是链下托管现货 BTC/USDT、PostgreSQL 16 RC、Go 1.21+ `database/sql`、Redis 7.x 可丢缓存，未实现跨库结算。BTC、USDT 分别用 1e8、1e6 最小整型单位存储。T100 已确定成交 0.1 BTC × 30000 = 3000 USDT，无手续费；买方 101 初始 USDT available 7000、frozen 3000，BTC 0；卖方 202 初始 BTC available 0.4、frozen 0.1，USDT 0。HB/HS 被恰好消费，不因系统超时撤销已确定成交。

## 第 1 层：什么证据足以把单库问题升级成分片问题？

**面试官：** 交易账户越来越多，是否应该立刻按 account_id 分库？你怎样判断分片真的值得做？

**面试者：** 不应该只看账户总数。我会先判断压力在容量、IO、连接、查询索引，还是一个热点账户的余额行争用，再看限流、索引、归档、只读投影和垂直隔离能否解决。账户分片能够分散不同账户的负载，却不能消除同一个做市账户的串行资金竞争，反而会让买卖双方结算跨库。必须有明确容量或隔离需求，并愿意承担跨片协议、全局查询、迁移和恢复成本，才进入这一变体。本题的可执行基线仍是单库，不把“将来可以分片”说成已经具备的能力；也不编造一个吞吐阈值，假装超过该数就必须分库。架构变化首先改变的是原子边界，而不只是路由函数。

## 第 2 层：两个局部事务为什么不能拼成一笔原子结算？

**面试官：** 你说边界会改变。把 101 放在 A 库、202 放在 B 库，T100 在每边各开一个事务，具体哪里会出错？

**面试者：** 单库里，trade_id 唯一的 settlements 身份、四条 `(trade_id, leg_no)` 唯一分录、四行余额、两 hold 与 outbox 一起提交；四行余额事先建好，先按 `(account_id, asset)` 升序锁完，再按 hold_id 升序锁 hold。拆库后，A 只能原子扣买方 USDT frozen 3000、加买方 BTC available 0.1，B 只能原子扣卖方 BTC frozen 0.1、加卖方 USDT available 3000。A 提交后 B 宕机，就会出现买方已可用 BTC、卖方却未收 USDT 的部分结算。各库自己的唯一键只能防本库重复，不能让另一库一起提交；Redis 锁和消息重试也不能把两个本地提交点变成一个全局提交点。每币种 delta 和为零必须跨两边核验，不能只看各片内部事务都合法。

## 第 3 层：如果要求全局提交决议，2PC 到底做了什么？

**面试官：** 如果不能接受这个部分结算，采用 2PC 是怎样执行的？是不是协调器给两个库发一句 COMMIT 就行？

**面试者：** 不是。作为显式跨库变体，协调器先用稳定的 T100 和载荷摘要标识同一义务，各参与者完成本地校验与写入，再进入 PREPARE；只有确认所有参与者都已持久准备，协调器才能持久记录全局 COMMIT 决议，随后通知各方提交已准备事务。准备失败且尚无 COMMIT 决议，才能走全局 ABORT，重试时仍沿用 T100。PostgreSQL 的 prepared transaction 需要专门配置、唯一 GID 和恢复管理，不是 `database/sql` 的普通 `Tx.Commit()` 自动提供的跨库能力。业务的 APPLIED 结果要等所有参与者确认完成，不能把“协调器已决定提交”直接显示成双方余额均已更新。参与者准备时还要冻结规则和载荷，避免恢复过程拿新参数继续同一笔交易。

## 第 4 层：2PC 的阻塞与可见性成本如何落实？

**面试官：** 协调器记录 COMMIT 后崩溃，A 已提交、B 还停在 PREPARED，难道 2PC 就没有部分可见了吗？

**面试者：** 2PC 给出的是共同决议，不自动让两个数据库的独立读在同一瞬间看到新状态。A 先落地、B 后落地的区间仍然存在；若要求外部不见半边，就需要查询与可花资产访问共同遵守全局完成门禁，不能允许客户端绕过门禁直接读写局部结果。B 的 prepared transaction 必须保持资源并等待权威决议，不能超时自行回滚，因为 A 可能已依据 COMMIT 完成。恢复者根据持久协调日志重发决议，反复提交同一 GID，并核对本地完成凭据；若已提交后响应丢失，仅凭“找不到 prepared 事务”不能判断它回滚了。长时间准备会占用锁、预备事务槽位等资源并增加运维负担；PostgreSQL 的 PREPARE TRANSACTION 完成后事务已脱离原会话，不要求长期占住原连接。协调日志及参与库切主也必须保留这些事实。因此 2PC 的阻塞与恢复是真成本，不是一个透明开关。

## 第 5 层：Saga 为什么必须先改变“完成”的可见性合同？

**面试官：** 2PC 的成本很重，如果换成 Saga，允许先给一边入账、失败再补偿，能否仍承诺与单库完全相同？

**面试者：** 不能。Saga 允许局部步骤先提交，必须明确哪些中间结果可见、能否花用，以及补偿是否真的可逆。T100 已由撮合确定，买方若先拿到可花 BTC 并转走，随后简单扣回就可能失败；不能拿“后面会补偿”证明守恒。因此另一个显式变体是清算义务协议：创建持久义务 `T100=SETTLING`，两边先记录 PREPARED receipt 并固定原 HB/HS，把待收款记为不可花的 pending，而不是立刻加 available。参与者还要保留可审计的在途科目或义务记录，使差额有明确归属。此时前端显示的是成交已确定、结算处理中，不再承诺普通跨库读立即看到单库那种原子余额变化；这个合同改变必须先讲清。

## 第 6 层：pending 与锁资协议怎样走到双方可花？

**面试官：** 你引入了 PREPARED 和 pending，具体什么时候消费 hold、什么时候允许花用？一边失联又怎么办？

**面试者：** 可以规定：协调器收齐两边持久 PREPARED 后写入不可撤销的 APPLY_DECIDED；各片据此把本方原 frozen 转入结算在途、消费对应 hold，并把对方应收记为不可花 pending，在同一局部事务留下 APPLIED receipt。两边 receipt 都确认后，协调器才写全局 COMPLETE；任何 pending 转 available 或被计入可花额度，都必须确认这个持久 COMPLETE，并做本片幂等转换。未 COMPLETE 时，两边都不能提前花用，也不能按超时释放 HB/HS；失联方恢复后按原身份继续。跨片读取仍可能看见门禁转换的时间差，因此这是“禁止过早花用的最终结算协议”，不是恢复了单库同时可见。若要更强合同，仍需共同门禁参与全部访问。此变体新增在途科目、义务表和状态机，不能套用主基线四分录后声称无需额外设计。

## 第 7 层：消息重复、决议未知，怎样恢复同一笔义务？

**面试官：** 协调器和参与者都要发消息，如果 PREPARE、APPLY 或 COMPLETE 重复、乱序，甚至发送成功却没收到响应，会不会走错状态？

**面试者：** 每个步骤都要使用稳定的业务身份，例如 `(T100, protocol_version, participant, step)`，而不是每重试一次生成新 message_id 就当成新业务。参与者把 inbox 去重、payload_hash 校验、本地资金或 pending 变化、receipt 与 outbox 放在一个局部事务里；同身份异载荷必须拒绝并告警。状态只能按协议前进，缺少 PREPARED 的 APPLY 不得越过校验，重复 COMPLETE 也不能再加一次 available。响应未知时按原身份查权威步骤结果，协调器决议查询暂不可用就保持锁资和 pending。只有所有参与者确认尚未形成不可撤销决议，才能按协议结束一次失败尝试；已确定 T100 的清算义务仍然存在，不能把局部失败解释成撤销成交。消息只负责可靠传递，真正裁决来自持久状态和恢复规则。

## 第 8 层：迁移和双写为什么可能制造两个资金主？

**面试官：** 稳定身份能防重复，那账户从 A 迁到 C 时，先双写一段时间、验证一致后切流量，是否就安全了？

**面试者：** 不能让 A、C 同时接受独立资金写。即使二者都以 T100 去重，也会各自接受不同的新 trade_id，造成两个账本分叉。迁移需要账户所有权 epoch：先复制与一致快照配对的历史增量，再冻结或排空迁移账户的写，处理未完义务与 prepared 状态，关闭旧主写权限；确认旧侧已经被不可绕过的资源校验隔离，才发布新 epoch 并启用 C。路由缓存只帮助找到主，旧 A 也必须在写入路径拒绝过期 epoch，不能靠应用“自觉不再调用”。双写若存在，应由唯一权威主提交后向影子副本复制，影子不能接独立业务。增量追赶要覆盖完整前缀，不能以最大流水号相等为迁移完成依据；未完成跨片义务还要保留可恢复的参与者地址或稳定逻辑身份。

## 第 9 层：跨片对账怎样证明比较的是同一业务集合？

**面试官：** 迁移后还要对账。如果 A 的最大流水 ID 是 1000，C 也是 1000，就能判定追平吗？完整对账应该取什么水位？

**面试者：** 不能，序列分配不等于提交顺序，跨库序列也没有共同含义。对账必须先定义同一截止业务集合，例如权威成交流上一个已封闭的完整前缀，并取得每个参与片对该集合的完整处理证明；若采用快照，就需要协议支持的跨片一致快照或配对快照加增量重建，分别打开两个本地快照并不自动一致。比较累计余额还要从相同初始检查点回放该集合，不能把更晚成交已经混入的当前余额拿来比。对每个 trade_id 核验唯一载荷、四条业务腿、hold 消费和参与 receipt，pending 义务单独列出；聚合时同时看每币种 delta 和与逐账户重建值。集合只比较已完成项会掩盖卡住的成交，所以截止集合必须包含应完成却仍 pending 的义务，并显式报告其状态。

## 第 10 层：发现差异后，怎样修复而不抹掉证据？

**面试官：** 同水位发现 T100 一边缺腿，或者汇总余额差了 3000 USDT，你会直接把余额改成对的一边吗？最后采用哪套方案？

**面试者：** 不会直接改余额抹平。先区分观察水位错配、投影漏放、步骤未决、重复执行或真实账务错误；投影可从可信检查点按原身份重放，未决义务按原决议继续，已入账错误则通过带原因、关联原分录、审批和审计记录的新更正或冲正分录修复，不改写历史。必要时暂停受影响账户的新资金动作，保留对外沟通和恢复证据。对本题仍选择单库基线：成功后买方 USDT 7000+0、BTC 0.1，卖方 BTC 0.4+0、USDT 3000；每币种 delta 和为零，余额与 hold.remaining 非负。settlements 在同一事务提交前填 APPLIED/result，连同四分录、四余额、两 hold、`T100:applied` outbox 一起提交。Commit 断网按原 trade_id 查主库或重入恢复，不改号重扣、不按超时释放。跨片方案是条件变化后的分析，不声称已实现。

## 本题收束

- **讲透的机制：** 账户分片改变结算原子边界；2PC 要有持久决议、参与者恢复与阻塞处理；pending 义务协议只能在明确改变可见性和可花合同后成立；迁移必须保持单一资金主。
- **最容易答错的边界：** 两个本地事务不是全局事务；2PC 不是天然同时可见；Saga 补偿不是任意资金动作都可逆；相同最大流水 ID 不是完整水位；对账不能替代事前协议。
- **检验反例：** A 提交买方可花 BTC 后暂停 B，并让买方尝试转走 BTC。若系统放行，却只用“B 恢复后补偿”解释安全，就已经暴露了不成立的完成合同。再让小流水号事务晚提交，检查对账是否能识别它，而非被 MAX ID 跳过。

参考：[PostgreSQL 16 PREPARE TRANSACTION](https://www.postgresql.org/docs/16/sql-prepare-transaction.html)：预备事务脱离原会话，但继续持锁，必须由事务管理器可靠收尾。
