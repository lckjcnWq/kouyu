## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| BTC/USDT 现货 / GTC | 用 USDT 买实际 BTC；限价单在确定结束前可以继续挂着。 | 链下托管、maker 价、零手续费，不是合约仓位或链上兑换。 |
| maker 价 / 价差返还 | 按原挂单价格成交，少花的预留退回可用。 | 两笔实付 15,015 USDT，比预留少 10，返还不是新入金。 |
| clientOrderId / payloadHash | 用户给业务取的编号，以及固定格式参数的摘要。 | buy-001 绑定原价格数量；同键改参数必须冲突。 |
| intentId / reservationId | 一次业务意图的身份，以及专门给它占资的凭据。 | I1 绑定 R1 的 15,025 USDT，重试不能再占一份。 |
| CommandLog / commandSeq | 可恢复的命令记录，以及本市场的裁决位置。 | 101 已受理不表示已成交；重复意图也可能进入新位置。 |
| streamId / epoch | 持久业务流的名字，以及执行者的任期。 | BTCUSDT:v1 切主不改名；epoch 只管理写权。 |
| ResultBatch / AppliedSeq | 某条命令的完整裁决，以及结果已共同提交的前缀。 | 101 的成交、订单变化、预留处置与进度不能分开落地。 |
| batchId / tradeId / eventId | 分别定位整批、批内成交和具体业务事件。 | T0、T1 的身份跨重发不变，返价差不能伪造成第三笔成交。 |
| schemaVersion / ruleVersion | 数据怎样读，以及裁决按哪套业务规则解释。 | 恢复使用原版本，不按今天规则重算历史价格。 |
| contentHash / eventCount | 完整内容的摘要，以及协议定义的事件数量。 | 数量对了仍可能缺 T1；须核对清单、身份及整体摘要。 |
| Outbox / CDC | 同事务登记交付待办，以及读取已提交数据库变化的机制。 | 适用于数据库事实路径，不替代默认撮合结果日志。 |
| inbox / effectNamespace | 持久消费证据，以及“哪一种业务效果”的固定范围。 | 资金结转的命名空间不随消费组换名而变化。 |
| 分录腿 / 本地事务 | 每项资产桶变化，以及能共同提交或回滚的存储范围。 | 双方资产、预留、分录、去重与进度默认都在同库。 |
| lastSeq / offset / ACK | 业务已应用前缀、消息运输位置，以及接收方确认。 | 三者不同；默认账务提交后才确认，不能取最大位置跳缺口。 |
| AbortIntent / 关闭墓碑 | 有序关闭交易资格的命令，以及防止迟到请求复活的记录。 | 先履行既有成交，只释放确定可退余量，不按超时退款。 |
| 重放 / 冲正 | 重读原历史，以及有原引用的新纠错事实。 | 补交付不造新成交，冲正不删除旧分录。 |
| 水位向量 / 投影 | 各来源完整处理到哪里，以及由事实整理出的读视图。 | 对账绑定同一一致快照；页面不是资金裁决源。 |
| 链最终性 / 跨分片 | 链观察达到的稳定政策，以及越过单库事务的部署变化。 | 重组、外部支付另有协议，不能套用链下同库结转结论。 |

## 把整篇文章压缩成一个故事

甲拿着 20,000 USDT 买 0.25 BTC，限价 60,100。账户先为原请求建立 I1、R1，预留 15,025，剩余可用 4,975。命令排到 101，撮合按已有卖单价格产生两笔成交：向乙买 0.10 BTC 花 6,000，向丙买 0.15 BTC 花 9,015。只有完整裁决和执行进度共同提交，才能说成交已确定，不能凭内存试算或下单回包承诺到账。

分发器刚发送这批结果就失联，账户可能先看到后继 102。它不能先释放资金，要补齐完整 101，再用同库事务一起扣双方预留、记双方收入、返还 10 USDT，并保存分录、去重和进度。甲最终可用 4,985 USDT、拥有 0.25 BTC，丙仍预留 0.05 BTC。确认丢失再收原批次，只核验原内容返回原结果，不再改钱。

若甲在 Place 超时后想放弃，查询为空也不够，必须让关闭命令与迟到下单在同一顺序裁决；已经成交的部分继续履约。运维排查先对齐水位，缺交付补原事实，页面落后重建投影，真实错账另建审计更正，不能换消费组重记一遍。链重组与跨库支付另讲边界，文末小模型只是手工预期，并未实现或运行这些工程保证。

## 第一部分：文字全流程

### 1.1 讨论基线与准备条件

本专题复用[撮合交易从 0 到 1](../../01-撮合交易与核心链路/01-撮合交易从0到1/README.md)的业务规则：链下托管 BTC/USDT 现货订单簿、限价 GTC、价格时间优先、maker 价成交、零手续费。每市场一个有效写入者，账户域是余额与预留的权威源，撮合域是订单与成交的权威源。

本专题重点不是撮合算法，而是**权威事实的可靠产生、交付、唯一生效与核对**。默认所有参与账户、账务分录、消费去重与进度位于同一本地事务数据库；跨账务分片和外部支付仅作为明确改变前提的第 14 题。消息系统允许至少一次交付，不假设它能替数据库提交事务。

无需安装 Go、数据库或消息队列。阅读时可手工记录批次、进度、预留与分录；生产协议的论证不等于实现了这些基础设施。

### 1.2 唯一贯穿案例

订单簿已有 S1、S2，卖出资产已合法预留。乙、丙初始没有 USDT，除表中资产外不引入其他资金流。

| 对象 | 初始状态 |
|---|---|
| 甲 | 可用 20,000 USDT，0 BTC |
| S1／乙 | 卖出 0.10 BTC，限价 60,000 USDT/BTC，预留 0.10 BTC |
| S2／丙 | 卖出 0.20 BTC，限价 60,100 USDT/BTC，预留 0.20 BTC |
| B1／甲 | 买入 0.25 BTC，限价 60,100 USDT/BTC，clientOrderId=buy-001 |

B1 预留 `0.25 × 60,100 = 15,025 USDT`，形成 intentId=I1、reservationId=R1，甲可用变为 4,975 USDT。

为便于讨论交付，假设该市场账户消费者已经完整处理至序号 100；B1 对应的命令位于 101，且 100 以前所有预留和账务已经就绪。

```text
streamId = BTCUSDT:v1
commandSeq = 101
batchId = (BTCUSDT:v1, 101)

T0 = (BTCUSDT:v1, 101, 0)：0.10 BTC × 60,000 = 6,000 USDT
T1 = (BTCUSDT:v1, 101, 1)：0.15 BTC × 60,100 = 9,015 USDT

买方实际支出 = 15,015 USDT
价差返还     = 15,025 - 15,015 = 10 USDT
甲最终       = 可用 4,985 USDT、预留 0 USDT、可用 0.25 BTC
乙最终       = 可用 6,000 USDT、S1 预留 0 BTC
丙最终       = 可用 9,015 USDT、S2 仍预留 0.05 BTC
```

`v1` 是持久流命名空间，不是领导者任期；切主不改变它，也不从头生成相同序号的新事实。其他故障案例分别改变一个条件，不把正常案例、部分成交撤单与链重组叠成同一笔业务。

### 1.3 主链路：直到资金效果与查询进度有据可查

```text
甲提交 B1〔账户、clientOrderId、参数〕
    ↓
接入层：鉴权、精度、身份与规范化载荷校验
    ├─ 同键异载荷 → 冲突拒绝，不建立第二笔意图
    └─ 新请求或同载荷重试
         ↓
账户域本地事务
    创建／找回 I1、R1，将 15,025 USDT 从可用转为预留
    绑定订单身份、交易对、载荷与预留金额
         ↓
提交器使用原 I1 重试 Place
    ↓
CommandLog 提交：获得 commandSeq=101〔可靠受理点〕
    ↓
撮合域单写者按提交顺序裁决
    计算 T0、T1、订单变化和预留处置依据
    ↓
原子提交完整 ResultBatch(101) 与 AppliedSeq=101〔成交事实点〕
    ├─ 失败／结果未知 → 查原提交，不按内存结果发布新事实
    └─ 已提交 → 形成不可被下游超时抹去的两笔成交义务
         ↓
可恢复分发器读取已提交结果，发布稳定 batchId 与 contentHash
    发送超时／确认丢失 → 保留来源，重发同一身份
         ↓
账户消费者校验流、批次完整性、版本、哈希与连续序号
    ├─ 102 先到 → 持久暂存或要求重投，先补 101
    └─ 101 完整可处理
         ↓
同一本地数据库事务
    锁定流进度及账户／预留
    校验原业务效果身份和足额资产
    扣双方预留、给双方入账、返还 10 USDT
    写分录、去重记录、settlementStatus=APPLIED、lastSeq=101
         ↓
数据库事务提交〔资金效果点〕
    ↓
再 ACK／提交可安全越过的消息位置
    确认丢失 → 重投后核验原哈希与提交结果，不再次改余额
         ↓
私有查询／回报显示成交状态、结转状态与各自进度
    账户完成不代表所有查询副本已经同步；客户端可携带最低水位查询
```

分发器的发布确认只证明其配置承诺内的消息持久性，不证明账户数据库已结转。公共成交与私有成交回报可在 ResultBatch 提交后发布，但必须把“成交已确定”和“账户已结转”分开表达。

### 1.4 关键状态与完成含义

| 边界 | 权威状态与资产 | 可以承诺 | 不能承诺 |
|---|---|---|---|
| 账户预留提交 | 甲可用 4,975、预留 15,025 USDT | 原意图有有效交易资格 | Place 已可靠受理 |
| CommandLog 提交 | 命令 101 可恢复 | 命令会被按协议处理 | 一定接纳订单或成交 |
| ResultBatch 提交 | B1 全成；两笔成交义务成立，资产仍可尚未结转 | 原结果可以恢复、交付 | 消息和账务已经完成 |
| 账户事务提交 | 甲可用 4,985 USDT、0.25 BTC；lastSeq=101 | 资金效果、分录、去重与进度共同生效 | 页面和所有副本同时可见 |
| 查询投影追上 | 投影携带实际水位和版本 | 该投影覆盖所声明的前缀 | 它能代替权威状态裁决新交易 |

逐币种守恒：本例 USDT 合计始终 20,000，BTC 合计始终 0.30；BTC 不能与 USDT 相加。允许 B1 全成而结转 PENDING；禁止退掉成交所需预留后仍允许该成交扣款，或消费者只给买方入账就确认整批完成。

### 1.5 主要异常分支

```text
参数非法／余额不足
    → 明确拒绝，不形成可执行的新资格

预留完成，Place 调用超时
    → 复用 I1 查询和重试，不创建新预留
    → 要放弃时向同一命令流提交 AbortIntent(I1)
    → 撮合按序关闭资格／撤实际余量
    → 账户按先前成交及关闭结果顺序释放确定可退部分

ResultBatch 已提交，消息尚未发送
    → 从结果源补交付，原成交不删除、不重新撮合

账户事务提交，ACK 丢失
    → 重投同一 batchId，核对内容后返回原结果

101 无法解析或缺失，102 已到
    → 阻断受影响流的资金进度，保留预留、补齐或升级处理
    → 不能把“进入死信队列”当成允许越过 101 的业务证明
```

部分成交撤单另设独立变体：B2 限价改为 60,000，数量仍为 0.25 BTC，预留 15,000 USDT。先成交 0.10 BTC、支出 6,000，剩余预留 9,000；撤单与下一笔成交在同一命令顺序裁决，账户不得先处理释放再补前序成交。

链上重复／重组是另一种事实来源的变体：先区分观察与最终业务事实，再处理投影撤销和唯一入账，不把链下已确定成交说成可随意回滚的链观察。

## 第二部分：核心板块

| 板块 | 为什么核心／决定什么 | 拥有的状态 | 上下游契约 |
|---|---|---|---|
| 意图与资格管理 | 超时重试是否制造第二笔订单或第二份占资 | 请求键、载荷摘要、意图、预留 | 同键同载荷找原结果；关闭须阻止迟到执行 |
| 事实源与提交 | 失败后是否仍有完整业务义务可恢复 | 命令提交前缀、完整结果、AppliedSeq | 未提交不发布；已提交不因消息失败改事实 |
| 可靠交付 | 已确定事实能否在重启后继续送达 | 发布进度、租约、重试及来源保留 | 允许重发，不声称一次发送等于唯一效果 |
| 消费原子性与顺序 | 两边资产、去重与进度是否共同生效 | 余额、预留、分录、inbox、lastSeq | 完整批次、连续前缀、本地事务后确认 |
| 收敛与证据 | 历史是否可重放，差异能否解释与修复 | 归档、水位、阻断、修复任务与审计 | 补交付不造新事实，冲正不删历史 |
| 投影与异构边界 | 不同下游能承诺什么新鲜度与最终性 | 私有版本、公共序号、链观察修订 | 展示、账务、链规范性分别定义完成 |

## 第三部分：核心 20%

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 分层身份与载荷绑定 | 请求到分录 | 确定何为“同一件事” | 重试换身份、同键改金额、重放重复扣款 | 作用域、规范化、哈希、唯一约束 |
| 可靠事实先成立 | 裁决到分发 | 提供可恢复的交付来源 | 内存成功但成交永久丢失 | ResultBatch＋AppliedSeq、未知提交 |
| 事务与消息缺口 | 数据库事实源到 MQ | 两套系统不能靠调用顺序一起提交 | 成交未发或事务回滚却通知成功 | Outbox、CDC、日志方案适用条件 |
| 消费事务与效果唯一 | 接收到账务 | 重投必须不重复变资产 | 去重先写造成漏账，后写造成重账 | inbox、业务唯一键、余额与进度同提交 |
| 连续前缀与完整批次 | 乱序到账务 | 防止退资越过成交 | 半批结转、跳序释放 | 排序域、批次清单、缺口恢复 |
| 资格关闭协议 | 预留超时到撤销 | 防止“查询没有”之后迟到成交 | 钱已释放，命令仍可花掉 | AbortIntent、关闭墓碑、权威排序 |
| 重放、保留与恢复契约 | 历史到新实例 | 唯一效果不只持续几分钟 | 去重过期或旧备份恢复后再次入账 | 安全保留边界、检查点、effect namespace |
| 同水位核对与异构完成 | 多下游 | 解释暂态并定位真实差异 | 错把在途当错账或缓存当真相 | 向量水位、逐资产核对、最终性与修订 |

## 第四部分：设计与规则

### 4.1 权威架构与三种可靠来源

```text
账户数据库〔意图、预留、余额〕
    └─ 原意图提交器 → CommandLog〔命令可靠受理〕
                          ↓
                    撮合域有效单写者
                          ↓
              结果存储〔ResultBatch＋AppliedSeq 原子提交〕
                          ↓
                     可恢复分发器
                          ↓
                        消息系统
              ┌───────────┼───────────┐
              ↓           ↓           ↓
        账户消费事务   私有回报投影   公共行情投影
        资金权威源     派生状态       派生状态
```

本例选择可恢复结果日志作为撮合事实源，不把逐订单事务数据库撮合当作默认架构。ResultBatch 与 AppliedSeq 的共同提交是可靠存储必须提供的能力，不是两次独立写入；内存状态按已提交结果推进，崩溃后从一致检查点恢复并应用已提交结果，不以未提交内存状态为真相。

若事实本来由关系数据库事务产生，例如费用批次或提现申请，则可在**同一数据库事务**写业务变化与 Outbox，再由发布器或 CDC 交付。CDC 读取事务提交后的变化，不能替代未记录的业务语义，也不能凭普通表更新自动知道完整交易义务。三种路径按事实源选用，不叠组件来掩盖原子边界。

### 4.2 核心对象与稳定身份

| 对象 | 必要字段／约束 |
|---|---|
| 请求／意图 | `(accountId, operation, clientOrderId)` 唯一；intentId、payloadHash、schemaVersion、symbol、reservationId、状态 |
| 预留 | reservationId 唯一，绑定 intentId、账户、资产、金额与参数；同一预留不能供不同订单重复使用 |
| 命令 | streamId、commandSeq、intentId、commandType；传输重试可能进入新位置，但同一意图只能首次有效执行 |
| 结果批次 | batchId=`(streamId, commandSeq)`，schemaVersion、ruleVersion、contentHash、eventCount、完整事件及订单／预留处置结果；哈希绑定身份、解释版本和完整经济载荷，计算时排除 contentHash 自身及会随投递变化的 attemptId |
| 成交／事件 | tradeId=`(streamId, commandSeq, matchIndex)`；eventId 为稳定批次内身份，消息投递尝试 ID 不参与业务去重 |
| 账户分录 | effectNamespace、tradeId、legType、accountId、asset 唯一；保存原事实引用与资产桶变化 |
| 消费去重 | `(effectNamespace, streamId, seq)` 唯一，contentHash、schemaVersion、原处理结果；namespace 表示业务效果，不随进程重启或消费组换名改变 |
| 消费进度 | `(effectNamespace, streamId)` 的 lastSeq，与资产效果同事务提交；不是消息系统 offset 的别名 |
| 投影／链观察 | sourcePosition、projectionVersion；链证据另带 chainId、blockHash、txHash、logIndex、规范性与最终性依据 |

载荷采用固定版本的规范化编码：金额、数量先转最小单位整数，明确字段顺序、空值和枚举；摘要仅用于快速比较，授权与关键经济字段仍需校验。示例价格是 USDT/BTC，不用浮点乘法写资金。

完整批次有确定编码和完整性校验；若传输拆片，先持久组装并核对清单、数量与总哈希，再进入账户事务。eventCount 不能单独证明内容无缺无重。

### 4.3 必须成立的不变量

1. **意图唯一：** 同一请求作用域、同一载荷返回原意图；同键异载荷拒绝，不能靠延长锁 TTL 代替持久约束。
2. **事实不丢：** 对外承诺提交的命令与结果必须落入可恢复的持久化承诺；分发器只能发布已提交事实。
3. **资金效果至多一次：** 重发、消费组更名、进程重启和补交付不改变 tradeId、batchId 或 effectNamespace。
4. **完整且连续：** 基线中每个已处理命令位置都有结果批次，包括拒绝、关闭、无成交与重复意图的新命令位置；账户 lastSeq 只能从 s 推进到完整的 s+1。
5. **本地共同提交：** 双方资产、预留、平衡分录、去重与 lastSeq 一起提交；失败不能留下“去重成功但没记账”。
6. **资格与义务约束：** 成交需要足额合法预留；关闭与 Place 同域排序。释放只依据确定关闭／撤余量结果，并服从先前成交顺序。
7. **守恒与不可逆边界：** 每币种内部转移之和为零，余额桶非负；已确定成交不能因交付失败删除。纠错产生带原引用的新审计事实，不覆盖历史。
8. **收敛有条件：** 来源可恢复且保留充分、消费者最终可运行、毒消息能被解决、处理能力足够且确认协议正确时，才能承诺最终追上；不是无条件“最终一致”。

### 4.4 消费、并发与查询约定

- 同流资金应用串行化，可用数据库进度行锁及唯一约束共同防守；Go worker 的内存锁不能跨实例保护数据库。
- 不同市场可并行，但共享账户事务必须按固定账户／资产／预留顺序加锁，死锁可回滚重试；跨流经济依赖另建显式依赖，不能靠墙钟排序。
- ACK 在事务提交后。若 SDK 提前把接收落到持久 inbox，则必须明确 ACK 只代表已持久接收，后续业务应用有独立连续进度；仅放入内存不算完成。
- 消息 offset 是传输位置，commandSeq 是业务顺序；批量提交 offset 只能越过已持久接收或已应用的连续前缀，取决于声明的确认契约。
- 资金流遇到未知版本、载荷冲突、缺口或不变量失败需阻断受影响范围；可重建公共视图按协议快照重同步，不自动继承资金流处理规则。
- 多市场不存在天然全局序号；对账和一致性读取采用各流水位向量及数据库一致快照，不能把各流最大值拼成已覆盖前缀。稳定 streamId、业务效果命名空间与恢复水位属于持久协议；epoch、workerId、consumerGroup 只是执行和传输管理身份。
- 去重明细、账务效果证据、源日志和归档按同一恢复契约保留，不设独立的“七天后就当新事件”。旧数据库备份与较新的消息 offset 不可直接拼接恢复；必须从共同检查点重建余额、分录、去重和进度，无法证明时先阻断资金应用。

## 第七部分：工程实践——一个简洁 MVP

### 7.1 目标与范围

仅手工验证：**完整 101 批次在一个账户本地事务中结转；ACK 丢失重投不重账；102 先到不跨缺口释放。** 初始表采用 1.2 节预留已完成的状态，lastSeq=100。金额和数量用最小单位整数，批次视为可信已提交来源，仍校验内容与业务身份。

未覆盖真实持久化、撮合、Outbox、租约、消息 SDK、跨分片、链重组或故障注入。下面的“事务”明确要求真实实现时有共同提交能力，不能用普通内存 map 冒称跨崩溃原子性。伪代码中的 6,000 USDT、0.10 BTC 等为可读业务单位的记号，进入计算前须按固定精度转为整数，不表示使用浮点余额；检查乘法溢出并按资产分别核对。

### 7.2 一段核心伪代码

```text
Apply(batch):
    if batch.streamId != BTCUSDT:v1: 返回 OUT_OF_SCOPE
    校验受支持的schemaVersion、ruleVersion、固定编码、完整清单、总哈希与来源
    校验不通过则拒绝，缺内容返回 INCOMPLETE，未知版本返回 UNSUPPORTED_VERSION
    BEGIN 本地账户事务
    p = FOR UPDATE progress[资金结转, batch.streamId]
    if p 不存在: ROLLBACK; 返回 INVARIANT_BROKEN
    old = inbox[资金结转, batch.id]
    if old 存在:
        if old.contentHash != batch.contentHash: ROLLBACK; 返回 CONFLICT
        COMMIT; 返回 old.result
    if batch.seq <= p.lastSeq: ROLLBACK; 返回 HISTORY_REQUIRED
    if batch.seq != p.lastSeq + 1: ROLLBACK; 返回 GAP(p.lastSeq + 1)
    if batch.seq != 101: ROLLBACK; 返回 OUT_OF_SCOPE
    按固定账户／资产／预留顺序锁定本批相关行
    校验批次确为B1的T0/T1及全成处置，账户、资产、价格、数量、金额匹配1.2节
    校验全部 tradeId、方向、合法预留绑定与剩余金额；不符则回滚拒绝
    若任何已有成交效果与本批不一致: ROLLBACK; 返回 EFFECT_CONFLICT
    计算全部资产桶变化和分录；逐资产验证平衡与桶非负
    # 本例是全新101批次；异常“分录已存在而整批未提交”须阻断调查
    if 任一目标分录唯一键已存在: ROLLBACK; 返回 INVARIANT_BROKEN
    对 T0：甲预留USDT -= 6000；乙可用USDT += 6000
            乙预留BTC -= 0.10；甲可用BTC += 0.10
    对 T1：甲预留USDT -= 9015；丙可用USDT += 9015
            丙预留BTC -= 0.15；甲可用BTC += 0.15
    依据B1全成及处置结果：甲预留USDT -= 10；甲可用USDT += 10
    同步逐笔预留：R1.remaining=0 USDT；S1预留.remaining=0 BTC
                  S2预留.remaining=0.05 BTC；关闭已耗尽的R1与S1预留
    写上述变化的平衡分录〔原 tradeId／batchId 与稳定 legType〕
    写 inbox[资金结转, batch.id] = {contentHash, result: APPLIED}
    写 B1.settlementStatus = APPLIED；写 p.lastSeq = 101
    COMMIT
    返回 APPLIED

收到消息 → Apply
    APPLIED／已核验原结果 → 再 ACK
    GAP／INCOMPLETE → 补齐或重投，不确认成已应用
    CONFLICT／EFFECT_CONFLICT／INVARIANT_BROKEN／HISTORY_REQUIRED → 阻断核查，不自行退款
    OUT_OF_SCOPE／UNSUPPORTED_VERSION／其他校验拒绝 → 不应用、不ACK为已处理，报告路由或版本问题
    提交结果未知 → 用同一批次重试或查权威结果，不先 ACK
```

这是针对本例 101 的小闭环，不声称已经实现通用账务引擎；对 102 的真实处理仍需它自己的合法事件与处置依据。ACK 的简化采用“已应用后确认”，未使用提前持久 inbox 确认模式。

### 7.3 输入与预期结果

| 输入／故障点 | 手工预期 |
|---|---|
| 首次收到完整 101 | 甲 4,985 USDT、0.25 BTC；乙 6,000 USDT；丙 9,015 USDT 与 0.05 BTC 预留；逐笔 R1、S1 预留归零关闭，S2 预留剩余 0.05 BTC；lastSeq=101 |
| 101 提交后 ACK 丢失，再收同内容 101 | 返回原 APPLIED，余额、分录数量与 lastSeq 不再变化 |
| 同一 batchId，把 T1 金额改成 9,016 并重算传输校验 | 与原持久 contentHash 冲突，阻断；不能按“重试”接受改价 |
| 初始 lastSeq=100，先收到声称可释放余量的 102 | 返回 GAP(101)，不改资金，不把 102 的接收当成处理完成 |
| 101 只有 T0，缺 T1 | 完整性校验失败，不处理半批，lastSeq 仍为 100 |
| 账户事务任意写入后但提交前失败 | 共同回滚，余额、分录、inbox 与进度都不留半次效果 |
| 101 已提交，但 inbox 被错误单独删除 | seq 已覆盖而缺原记录，要求历史核验；不能仅凭旧 seq 静默接受改载荷 |
| 其他市场的合法批次，MVP 未初始化它的进度 | 读取进度前即 OUT_OF_SCOPE，不访问空进度、不发起无关补扫 |
| 101 完成后，继续收到合法 102 | 固定 MVP 返回 OUT_OF_SCOPE，不执行 101 的固定金额；真实后继消费者需按 102 自身内容实现 |

这些是设计预期与手工推演，不是已经执行的工程测试。
