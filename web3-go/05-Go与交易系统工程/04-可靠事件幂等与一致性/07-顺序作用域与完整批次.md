# 大问题 7：重复、乱序、缺口和拆片到达时，怎样只应用完整连续的业务批次？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 顺序作用域 / streamId | 哪些事实共享同一套先后位置。 | BTCUSDT:v1 内比较 101、102，不能与别的市场直接比大小。 |
| commandSeq / offset | 权威业务位置，以及消息分区中的运输位置。 | 重发和拆片会改变对应关系，资金进度不能照抄消息位置。 |
| lastSeq / 连续前缀 | 起点到某位置都已完整应用，而非见过的最大号。 | 初始为 100，先到 102 也不能跨过 101。 |
| effectNamespace / epoch | 固定业务效果范围，以及执行者任期。 | 任期、消费组变化不生成新资金效果或新业务流。 |
| 空／重复结果 | 没有新成交但仍有完整处理结论的批次。 | 挂单、拒绝、关闭也要有结果，不能让资金流凭空缺号。 |
| 过滤流 / 覆盖证明 | 只保留部分事件的订阅，以及被省略位置无遗漏的依据。 | 只发成交的过滤器不能直接承诺覆盖全部命令位置。 |
| tradeId / eventId | 批内成交和事件的稳定身份。 | 两份 T0 仍是重复，不能用来顶替缺失 T1。 |
| eventCount / 清单 | 事件数量与应出现的具体成员集合。 | 个数相同不代表成员正确，还要含订单和预留处置。 |
| schemaVersion / contentHash | 固定编码版本及绑定整批内容的摘要。 | 不混两个内容版本，金额、身份和完整经济载荷都受绑定。 |
| 分片索引 / end=true | 片段的位置编号，以及发送端声明的结束标记。 | 结束标记先到不证明其他片齐全。 |
| 持久组装 / READY | 可靠保存片段并核验，以及内容已经齐备的状态。 | READY 只准进入候选处理，仍不能越过前序资金批次。 |
| 进度行锁 / 原子应用 | 事务内重新检查顺序，并共同提交完整资金效果。 | 102 先拿锁但进度在 100，必须返回 GAP(101)。 |
| RECEIVED / APPLIED | 已可靠接收与已完成业务效果。 | 暂存 102 不代表 lastSeq 可以写成 102。 |
| ACK / 运输确认前缀 | 消息确认及可以安全累计越过的位置。 | 应用后确认与持久接收后确认是两份契约，不能混用。 |
| DLQ / HISTORY_REQUIRED | 隔离错误的死信队列，以及要求核对旧历史的状态。 | 都不授权跳过资金义务或把旧事件当新事件执行。 |
| 显式依赖 / 水位向量 | 记录跨流先决条件，以及各流分别完成到哪里。 | 共享账户仍受同库事务保护，不靠墙钟拼造全局顺序。 |

## 把整篇文章压缩成一个故事

账户资金进度还在 100，网络却先送来 102。处理器没有取最大号前进，因为 B1 在 101 的两笔成交还没结转，后继的任何释放都不能先把付款资格退掉。它把 102 按约定可靠暂存或要求重投，转向结果源补 101。其他市场有自己的位置，不能用它的更大序号证明 BTCUSDT 已经完整，也不能把过滤后没看到的命令随便判为空。

101 被拆成片段送来，接收器看见两份 T0 和一个结束标记，仍缺 T1。数量再像齐了也不能记账，要按固定版本的清单、事件身份、各片与整体摘要组装核验。完整后，事务再锁进度确认正是下一批，才共同完成 15,015 USDT 付款、0.25 BTC 转移和 10 USDT 返还，进度变为 101；随后才能处理 102 自己的合法内容。

若 101 解析不了，送进死信只能保存问题，不能替它生成空结果。若先持久接收就确认运输，后台仍要承担补片和应用责任，RECEIVED 不能冒充 APPLIED。其他独立市场可以继续，但谁也不能动用 B1 的 R1 预留；真正的跨流依赖必须写进协议。完整性证明这批没缺内容，连续性证明前面没缺义务，两者都成立才有资格产生资金效果。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题从消息到达进入账户事务之前展开，定义业务顺序作用域、完整批次证据、拆片组装与缺口恢复，并明确“阻断不确认”与“持久 inbox 接收后确认”的不同责任。第 6 题负责原子资金效果，本题负责确定什么内容已经完整、什么顺序才允许进入该事务。

**讨论前提：** 沿用 BTCUSDT:v1，账户应用进度 lastSeq=100，B1 位于 101。完整 101 含 T0、T1 及订单／预留处置结果，支出 15,015 USDT，返还 10 USDT；102 是同流后继命令自己的合法结果，不能虚构成再次释放 B1 的资格。本文不新增 MVP，总览的唯一 MVP 仅覆盖固定 101。

```text
运输记录到达 → 按稳定 streamId 与 batchId 分组
    → 拆片则持久组装 → 核验清单、各片、事件身份及整体哈希
    → 与该流 lastSeq 比较：重复核验／缺口等待／恰好下一批
    → 完整 101 进入账户事务共同提交 → lastSeq=101
    → 再按 102 自己的合法内容完整应用 → lastSeq=102
```

## 第 1 层：102 先到为什么不能先应用

**面试官：** 账户 lastSeq=100，102 先到，101 还没收到。102 看起来可以处理，先做它再回补 101，有什么问题？

**面试者：** 在本专题的资金流契约里不能先应用，因为 lastSeq 声明的是完整覆盖的业务前缀，不是看见过的最大序号。
101 对应 B1 的两笔成交和预留处置义务尚未结转，102 不能证明这些前序义务已经不存在；后继若涉及关闭或释放，越序可能先退掉成交所需资产。
因此 lastSeq=100 时只允许完整 101 进入下一次应用事务，102 应等待缺口补齐。

完整 101 同时扣甲预留 15,015 USDT、给乙 6,000 和丙 9,015 USDT，并将乙、丙预留中的 0.25 BTC 转给甲，再返还价差 10 USDT。
提交后甲可用为 4,985 USDT、0.25 BTC，丙仍预留 0.05 BTC，且 lastSeq=101；此时才轮到 102 自己的完整结果。
不能只收到 T0 就把进度写成 101，也不能把 B1 已全成后的 102 编造成再次释放 15,025 USDT。

先到的 102 可以按明确契约要求重投，也可以持久暂存，但这都只是运输或接收状态，不是资金已应用。
如果要改成允许某些事件交换顺序，必须证明相关资产、预留及效果没有依赖，并重新定义进度语义；本基线不采用这种隐含优化。
顺序约束先保证安全，最终能否追上则依赖 101 的来源仍可恢复以及缺口最终被解决。

## 第 2 层：明确业务序号的作用域

**面试官：** 你一直说前缀。消息队列也有 offset，直接把账户 lastSeq 写成最新消费 offset，或者把所有市场放进一个计数器不就行了？

**面试者：** offset 是运输系统某个分区里的记录位置，commandSeq 是权威命令流里的业务位置，两者不能互换。
一个业务批次可能拆成多条运输记录，同一批次重发又占据新 offset；多个市场也可能共用一个分区，所以两者既不是一一对应，也不一定同速增长。
账户 lastSeq 按 `(effectNamespace, streamId)` 保存，运输确认另按分区及其记录位置管理。

`BTCUSDT:v1` 是持久业务流命名空间，切主不能把它改名并从 1 重新生成相同经济事实。
领导者 epoch、worker 实例与 consumerGroup 是所有权或运输管理身份，不是业务效果命名空间，也不是新资金效果的授权。
不同市场各有连续序号，BTCUSDT 的 101 与另一个市场的 101 不代表同一事实，也没有天然先后关系。

同流只应用 lastSeq+1，指的是这个明确业务作用域内的完整结果位置。
运输 offset 可以服务重投和接收恢复，却不能证明这个位置之前的所有业务义务都已记账；反过来，一个已经应用的业务批次也可能在新 offset 再次出现。
既然进度按业务位置定义，下一步必须解释为何这个流的每个已处理位置都应该有结果。

## 第 3 层：没有成交的命令也必须有结果批次

**面试官：** 如果 101 之后的 102 是一笔没有成交的 GTC 挂单，消息里没有 trade，消费者一直等 102 会不会永远等不到？

**面试者：** 不会，因为本基线要求每个已处理命令位置都产生一个完整结果批次，而不是只有成交才发布。
102 即使没有 trade，也要有自己的 batchId、版本、事件清单和内容摘要，并明确命令结果、订单变化及预留处置依据。
拒绝、关闭、无成交和同一意图重试进入新命令位置后的无新增效果结果，都不能在连续流中悄悄消失。

“没有 trade”也不等于没有业务信息：新挂单可能仍占用原合法预留，拒绝或资格关闭可能带来确定的处置结果。
消费者按完整批次语义处理；如果它对本账户效果确实为空，仍要在事务中保存内容绑定与处理结果、推进 lastSeq，而不是靠超时猜测该位置可跳过。
该 102 是独立合法命令的结果，不修改 101 中 B1 已全成、价差已返还的事实。

因此，来源恢复查询应能回答“102 已提交但没有成交”“尚未处理到 102”以及“102 的完整结果缺失”，不能只返回一个空的成交列表。
如果来源明确已处理到 103，却无法提供 102，属于恢复或数据完整性问题，不能由消费者自行生成空批次填洞。
连续处理成立的基础是来源覆盖契约，不是所有业务系统的序号天然无间断。

## 第 4 层：多流与过滤不能制造假缺口

**面试官：** 每个业务位置都有批次，但一个分区混了多个市场，或者订阅只保留成交事件。看到数字跳号时，怎么区分真缺口和过滤导致的空洞？

**面试者：** 首先按正确作用域比较，不能用运输位置或其他市场的序号推断 BTCUSDT 缺了什么。
例如分区 offset=500 是 BTCUSDT 的 101，offset=501 是 ETHUSDT 的 77，offset=502 是 BTCUSDT 的 102；BTCUSDT 在业务上完全连续。
若中间记录被正常过滤，运输 offset 不连续也不能直接报业务缺口，运输确认必须依据客户端实际提供的分区位置契约。

其次，资金消费者不能从“只保留成交”的过滤流继承完整 commandSeq 前缀，因为无成交批次已经被上游藏掉。
基线应给它交付完整业务封套，包括没有资金变化的结果；若要建立过滤后的专用流，来源须定义新的连续序号及原位置映射，或提供可信的覆盖范围与无效果证明。
不能以“我只关心甲”为由丢掉 T1 后仍声称自己完整处理了涉及甲、乙、丙共同事务的 101。

只有来源契约要求该业务位置必须可见，且后继表明它尚未覆盖，消费者才能把它标记为真实待补位置。
普通过滤器不知道哪些缺席位置对资金无影响，所以既不能把所有跳号都报警，也不能把所有跳号都解释成过滤后正常。
明确订阅覆盖后，还需要证明“一个已经收到的批次”内部没有缺失，外部序号连续本身不够。

## 第 5 层：eventCount 正确为什么仍可能半批

**面试官：** 外部顺序已经清楚。101 声明 eventCount=2，我收到两条成交就算完整，为什么还需要清单和总哈希？

**面试者：** 数量相同不证明身份和内容完整，收到两份 T0 仍可能缺 T1。
而且 eventCount 的口径应覆盖协议定义的完整事件集合，不是任意设为“成交笔数”；101 还需要订单终态和 10 USDT 返还等处置依据。
本模型的 tradeId 为 `(BTCUSDT:v1, 101, matchIndex)`，重复投递不能占据另一个 matchIndex 的位置。

完整封套要有固定版本的规范化编码、稳定事件身份和可核验清单，并将全部经济内容、订单结果及预留处置绑定到整体 contentHash。
消费者核对预期事件集合与实际集合，拒绝重复占位、额外事件、身份错配和关键字段不一致；还要验证来源权限，而不是仅相信消息自己声明的摘要。
若整个批次作为一条不可分消息传输，也仍要检查结构与语义，不能把“消息体存在”直接等同于“业务义务完整”。

101 只有 T0、没有 T1，哪怕包装层声称接收成功，也不得给甲加 0.10 BTC 后把 lastSeq 推到 101。
逐资产平衡只能检查已收到内容是否自洽，不能证明没有漏掉一组本身平衡的转移，所以完整性与资金校验都必需。
当一条完整批次超出传输大小限制时，拆片必须保留这种整体绑定，而不能退回只数消息条数。

## 第 6 层：拆片的最终标记为什么不够

**面试官：** 那把 101 拆成几片，最后一片带 end=true，收到结束标记就开始结转，可以避免等 eventCount 吗？

**面试者：** 不能，结束标记先到不代表此前各片都到达，更不代表各片内容属于同一版本。
清单须绑定原 batchId、schemaVersion、整体 contentHash、预期分片集合与每片摘要，以及完整事件的数量和编码规则；每片带片号及对应内容身份。
组装键要能区分同批次的内容冲突，不能让两套不同摘要的片段覆盖彼此，再凑出一个看似完整的批次。

消费者持久保存片段和清单，逐片校验后核对预期片集合、事件去重及重建后的整体摘要，所有条件成立才标记 READY。
重复的同内容片段可以复用，缺片继续等待；同片号不同内容、清单冲突或未知编码版本必须阻断，不以“最后到达者覆盖”为恢复策略。
仅有分片数量也不够，因为重复片可能占满计数，整体哈希则要绑定经济字段而不是只绑定传输头。

最终标记最多证明发布者宣称封套已经封存，不能替代片段齐全及来源真实性的证明。
若来源跨事务准备分片，还必须保证封存所引用内容已经持久、不可变、可恢复，提交最终标记不能补回尚不存在的片段。
组装过程本身不改资金，READY 才有资格进入第 6 题的完整账户事务。

## 第 7 层：完整性、连续性与事务竞争共同闭合

**面试官：** 101 已经组装为 READY，102 也完整了，两个 worker 一起调应用。如何保证不是先检查到 101、最后却把 102 先提交？

**面试者：** READY 只证明内容齐全，不授予跳过前序的权利；应用事务仍先锁稳定业务命名空间下的流进度行。
在锁内重新读取 lastSeq，并核验原 inbox 和内容绑定，只有恰好等于 lastSeq+1 的新批次才能执行；锁外读到的进度不能作为最终依据。
组装完成的内容应不可变，事务使用的是经校验且绑定该摘要的完整载荷，不能校验后又被另一个 worker 改写。

如果 102 的事务先取得锁，此时仍看到 lastSeq=100，就返回 GAP(101)，不做资金变化；101 随后按完整内容提交 lastSeq=101。
102 重试取得锁后，才按它自己的合法结果应用并推进到 102；101 的重复回调则核验原记录返回原结果。
双方资产、预留、分录、APPLIED 证据与进度共同提交，不能让事务外的组装完成回调直接更新 lastSeq。

102 可以是无新增资产变化的结果，但也要记录原内容与处理结论，不能只做一次“最大值更新”。
若 101 全部提交后进程崩溃，恢复依靠原 inbox 和进度识别完整效果，而不是依靠某个 worker 记得自己处理过哪些片段。
到这里业务应用的安全条件已闭合，但还没说明暂存和 ACK 之间谁负责恢复待办。

## 第 8 层：阻断重投与持久接收是两种确认契约

**面试官：** 102 先到时不能应用，但一直不 ACK 可能阻塞同分区后面的 101。究竟是阻断不确认，还是先存 inbox 就确认？

**面试者：** 两种方式都可设计，但必须先声明 ACK 的含义，不能混用。
基线“已应用后确认”下，未应用的 102 不标记完成；传输可乱序时应结合有界暂存、暂停调度和按业务位置补拉 101，避免只能靠阻塞重投等待。
运输按分区累计提交位置时，不能越过尚未满足确认契约的前序记录，即使后面的某条已经应用。

另一种是持久接收后确认：先把片段或完整封套及其身份、摘要、组装状态写入可靠 inbox，提交后 ACK 只代表恢复责任已转给数据库。
此时可以在保留 102 待办的同时继续接收 101；后台应用器仍按完整 101→102 推进，RECEIVED 与 APPLIED 必须区分。
若按片 ACK，每个已确认片段和来源关联也必须持久可恢复，不能只存一条“见过最后片”的标记就丢弃其他内容。

提前确认要求持续扫描待办、缺片补取、容量上限、告警以及覆盖相应待办的备份恢复契约，不能落到内存队列后就 ACK。
运输提交位置只能越过已持久接收的运输前缀，应用 lastSeq 则只越过已完整结转的业务前缀；两者可能长期不同。
因此是否可以 ACK 不由“是否放入 inbox”几个字决定，而由写入是否持久、内容是否充分以及承诺的是接收还是应用决定。

## 第 9 层：补不到、解析不了与旧历史缺证据怎样处理

**面试官：** 已经接走恢复责任，但 101 缺片一直补不到，或者是未知版本。把它放进死信队列，再让 102 继续，能否保证系统最终一致？

**面试者：** 死信队列只改变存放位置，不提供跳过经济义务的业务证明，所以不能推进受影响流的资金应用进度。
我会记录缺失批次与分片、已见摘要、来源恢复位置和阻断原因，从可信结果源或归档按原身份补齐；未知版本需恢复对应解析能力或走审计批准的处理流程。
不允许自行生成空 101、降低完整性检查，或把 102 中的释放视为前序成交已经不存在。

去重明细、分录等效果证据、进度、待组装内容、可靠来源与归档要服从共同恢复保留契约。
若 lastSeq 已覆盖 101，却找不到原 inbox，不能仅按“这是旧序号”无条件 ACK，尤其不能放过同 ID 异内容；要恢复可信历史绑定并核验，缺证据则阻断核查。
旧备份恢复也需按一致检查点与保留历史重建，不能只恢复运输 offset 就假定资金和去重状态已经一致。

修复应补回原事实或产生有原引用的新纠正事实，不能改掉原 batchId 的经济内容；epoch 和 consumerGroup 更名都不创建新效果命名空间。
若来源与归档均已丢失，应明确报告无法自动恢复并升级，不宣称反复重试必然收敛。
阻断保护的是受影响依赖范围，接下来还需要说明怎样避免一个市场的缺口被误扩张为所有市场停摆。

## 第 10 层：多流并行与跨流依赖怎样界定阻断范围

**面试官：** BTCUSDT 因 101 阻断，ETHUSDT 是否也必须停？如果两边共享甲的账户，怎样既不全局停机，又不让其他流释放了 BTCUSDT 的预留？

**面试者：** 没有显式业务依赖的流可以各自推进完整前缀，不需要发明跨市场全局序号。
共享账户仍由同一本地事务数据库串行保护相关资产和预留，全部写路径按固定顺序加锁，并校验各自的合法资格；不能以市场可并行为由越权消费另一流的预留。
甲的 R1 仍绑定 I1／B1，BTCUSDT 的 101 尚未解决时，另一个流或超时任务不能把它当成无主余额释放。

若一个业务确实要求 ETHUSDT 等待 BTCUSDT 的某个事实，应在协议中保存显式依赖，例如目标流必须已应用至指定位置，并在应用时验证。
墙钟时间、两个流 seq 的大小、消费者收到消息的先后，都不是这份依赖已经满足的证明。
阻断按真实依赖传播；资金安全依靠合法预留和数据库原子性，不能靠“所有消息看起来有序”替代。

跨流查询和对账使用各流水位向量及一致数据库快照，例如分别声明 BTCUSDT 覆盖到 100、其他流覆盖到其已应用位置。
不能把各流见过的最大 seq 拼成完成水位，也不能把单流未解决的 101 隐藏在一个全局最大值里。
完整闭环是：流内完整连续、流间依赖显式、接收与应用分开、恢复证据充足；在这些条件成立且阻断最终解决时，系统才有依据追上来源。

## 本题收束

**讲透的机制：** 明确业务顺序作用域；每个已处理命令都有完整结果；过滤不得伪造缺口或前缀；清单、稳定身份和整体摘要证明完整性；拆片持久组装后进入同流账户事务；ACK 明确区分已应用与已持久接收。

**易错边界：**

- 运输 offset 不等于业务 seq，跨市场没有天然总序；无成交批次不能从资金订阅中无说明地消失。
- eventCount、重复片计数和最终标记都不能单独证明完整；半批资金平衡也不能证明没有漏掉另一组平衡转移。
- 死信不是跳序许可；已覆盖 seq 缺原 inbox 必须历史核验；提前 ACK 只转移恢复责任，不推进应用水位。

**反例：** lastSeq=100，先收到 102，再收到 101 的 T0 两次与最终标记，T1 始终缺失。若按最大 seq 推进、按两条成交认定 eventCount 满足，或按最终标记结转，就会把不完整义务当成完整前缀。正确结果是 lastSeq 保持 100，资金不变，持久保留已接收证据并补齐真实 101；完整 101 提交后才允许应用合法的 102。
