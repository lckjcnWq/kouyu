# 大问题 1：一条业务事件从订单请求到账务完成，完整流程与可靠边界是什么？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 现货 / 限价 GTC | 买卖真实币，按限价约束成交，未结束可以挂着。 | BTC/USDT 链下托管、零手续费，不涉及杠杆。 |
| 权威域 / 投影 | 有权裁决原状态的地方，以及面向查询的整理副本。 | 撮合定成交，账户定余额，页面不能代替两者。 |
| I1 / R1 | 原交易意图与绑定它的预留身份。 | 15,025 USDT 只为 B1 占一次，不能被另一单借用。 |
| clientOrderId | 客户端标记同一笔业务的编号。 | 超时继续查原 buy-001，不另建订单。 |
| CommandLog / commandSeq | 持久受理记录与本市场命令位置。 | 提交 101 证明命令可恢复，不证明一定接纳或成交。 |
| streamId | 业务顺序所属的持久命名空间。 | BTCUSDT:v1 的前后关系不由消息到达时间决定。 |
| ResultBatch / AppliedSeq | 完整业务裁决与结果已提交进度。 | 二者共同提交，才确立 T0、T1 的成交义务。 |
| batchId / tradeId | 整批结果与其中每笔成交的稳定身份。 | 补发 101 不换两笔成交的身份。 |
| schemaVersion / contentHash | 内容的解释格式版本与原内容摘要。 | 重投要核验原绑定，同身份改金额不是安全重复。 |
| settlementStatus | 这笔成交的资金结转到了哪一阶段。 | PENDING 可以与订单全成并存，APPLIED 要有账户提交证据。 |
| inbox / 去重 | 与资金效果一起保存的原批次处理证据。 | 不能先写“处理过”再另做记账，否则会漏账。 |
| lastSeq / 连续前缀 | 从起点到这里的结果都已完整应用。 | 从 100 只能先到 101，不能直接用 102 退款。 |
| ACK / 发布确认 | 消费者的确认与消息系统给发送方的确认。 | 发布确认不是账务完成；默认账户提交后再 ACK。 |
| AbortIntent / 关闭墓碑 | 关闭原意图的有序命令与防复活记录。 | 查询为空不能代替关闭，迟到 Place 必须被持久规则约束。 |
| 平衡分录 / 逐币种守恒 | 每项资金转移有对应记录，同币种内部总量不凭空变化。 | USDT 为 20,000，BTC 为 0.30，两种币不能相加。 |
| 同水位核验 / 最低水位读取 | 比较相同处理范围，或要求查询至少覆盖指定进度。 | 分清账未结转与页面未追上，不拿旧缓存证明资金丢失。 |

## 把整篇文章压缩成一个故事

甲提交 B1 买 0.25 BTC，账户先把 15,025 USDT 留给这笔订单，可用剩 4,975。客服这时只能说“资金已准备”，不能说“币已到账”。原意图 I1 排进命令日志 101 后，撮合按序产生 T0、T1，两笔合计 15,015 USDT；完整结果与执行进度共同提交，才正式形成甲收币、乙丙收款的义务，发不发出消息不改变它。

分发器在发送前崩溃，重启从结果源取回原批次。账户收到后检查版本、摘要和完整性，在一个事务里同时划转双方资产、返还 10 USDT，并保存分录、去重和连续进度。甲最终可用 4,985 USDT、得到 0.25 BTC；确认丢失再投递一次，只返回原结果。页面可能还没刷新，那是展示进度落后，不是允许再给甲补一份币。

另一次故障中，后继关闭结果 102 比成交 101 先到，账户仍要保留必要预留，补齐前序后再处理确定余量。下单超时查不到也不能先全退，要在原命令流关闭资格，阻止迟到下单继续执行。排障人员沿结果源、交付、账户和投影分别查水位，在同一切面逐币种核对；这样才知道该补消息、继续结转还是修页面，而不是把所有状态都叫“成功”。

[返回专题总览](README.md)

**流程位置与核心机制：** 串起请求、预留、命令受理、撮合事实、交付、账务和查询，回答每一段由谁负责、凭什么恢复、能承诺到哪里。本题建立端到端地图；身份设计、资格关闭和结果原子提交分别在第 2—4 题继续证明，不把消息发送成功当成业务结束。

沿用总览的链下托管现货、限价 GTC、零手续费和同库账务事务。正常案例始终是 `BTCUSDT:v1` 的 101 批次，T0 为 6,000 USDT，T1 为 9,015 USDT；异常分支单独改变条件。

## 第 1 层：从请求开始讲到一笔业务真正完成

**面试官：** 甲提交 B1 后，系统完整经过哪些步骤？请不要只介绍消息队列。

**面试者：** 我会从资金资格开始讲，而不是从生产消息开始讲。接入层校验身份、价格数量精度和请求载荷，账户域在本地事务中建立 I1、R1，把 15,025 USDT 从可用移入预留。甲可用变成 4,975 USDT，但这时只能说资金准备完成，不能说订单已经成交。

随后提交器携带原 I1 发送 Place，命令日志提交后确定位置 101。
撮合单写者按序处理，计算两笔成交和订单变化，将完整结果批次与 AppliedSeq 一起提交。
只有跨过这个边界，T0、T1 才成为必须履行的成交义务；内存中刚算出来还不算。

```text
请求 → 账户预留提交 → CommandLog 提交 101
     → 按序裁决 → ResultBatch(101) 与 AppliedSeq 共同提交
     → 可恢复分发 → 消费者校验完整批次及连续序号
     → 账户本地事务提交 → ACK → 查询投影追赶
```

消费者在同一账户数据库事务中完成双方资产变化、分录、去重和 lastSeq。
成功后甲得到 0.25 BTC，实际支出 15,015 USDT，返还价差 10 USDT，最终可用 4,985 USDT。
如果这一步失败，成交事实仍成立、预留仍保留，任务是继续结转，不是删除成交重新下单。

## 第 2 层：沿流程划分权威状态与决策权限

**面试官：** 你说失败后不能删成交，那订单、余额、消息和页面发生矛盾时，到底听谁的？

**面试者：** 要按状态所属领域找权威，不能选一个组件包办全部真相。账户数据库拥有余额和预留；撮合域已经提交的结果拥有订单裁决和成交事实；CommandLog 证明某条命令已可靠受理，而消息系统只承载这些事实的交付。页面和查询缓存都是投影，没有改写成交或释放预留的权限。

执行时，每个跨域请求携带原意图和稳定事实引用。
账户服务不因为“页面查不到订单”就释放 R1，而是追查撮合域的受理、裁决或关闭结果。
撮合域也不能因为账务暂时不可用就把已成交订单改回未成交。

两边可以出现可解释的暂态：B1 已全成，账户结转仍为 PENDING。
此时查询应展示成交进度和账务进度，而不是用一个含混的 SUCCESS 隐藏差异。
如果投影丢失，重建投影；如果资金桶与权威分录矛盾，阻断并核查账务，不能用缓存覆盖资金源。

这里的责任边界同时也是恢复边界：恢复资金看账户提交，恢复成交看结果提交。
消息里的一个状态字段只有带着这些来源和位置，才有可核验的含义。

## 第 3 层：区分受理、事实、资金与投影四种完成

**面试官：** 既然有多个权威域，接口应该在哪一步返回成功，才不会让用户把受理误认为到账？

**面试者：** 我会让接口明确返回完成阶段和可查询身份。预留提交只能承诺 R1 存在；CommandLog 提交可以承诺命令 101 可恢复地受理；ResultBatch 提交可以承诺 B1 的成交已经确定；只有账户事务提交后，才承诺这一批资金效果已经应用。同步接口可以等待更后阶段，但超时不能把已经跨过的提交点变回未发生。

以 101 为例，受理响应返回 I1、订单身份、streamId 和 commandSeq。
成交响应引用 batchId 及成交状态，账务查询再返回 settlementStatus 和账户消费水位。
公共成交回报可以在结果提交后发布，不必等所有查询副本追上，但不得写成“资金已到账”。

如果响应在网络中丢失，客户端用原 clientOrderId 查询和重试。
服务端应返回原意图及目前已知阶段，而不是为了让重试得到一个新成功响应再建立订单。
返回“处理中”不是失败回滚承诺；返回“已受理”也不是撮合一定接纳的承诺。

因此我会先定义每个状态对应的持久证据，再设计接口状态码。
只调整响应文案、不绑定证据，不能解决不同进程对“成功”的理解冲突。

## 第 4 层：解释成交事实与消息发布之间的故障窗口

**面试官：** 你要求凭 ResultBatch 承诺成交；如果结果提交后进程马上崩溃，消息一条都没发，成交怎样不丢？

**面试者：** 关键是可交付来源已经独立于发消息进程存在。撮合域提交完整 ResultBatch(101) 和 AppliedSeq=101，分发器只扫描这个已提交来源。进程在提交后、发布前崩溃，重启后仍能读取原批次，带原 batchId、tradeId 和 contentHash 补发；不能依赖内存 channel 保存唯一副本。

发布进度也不能凭“准备发送”就提前推进。
先读已提交结果，再发消息，收到配置契约内的发布确认后记录进度；确认丢失允许重发。
发布与进度记录之间仍有重复窗口，所以消费者必须支持重复，而不是假设生产端永远只发一次。

如果结果提交本身超时，则先查结果存储的权威提交状态。
查到已提交就交付原结果，确定未提交才能从已提交状态恢复裁决；结果未知时不能把内存 T0、T1 发出去。
否则可能出现消费者已经给钱、结果源却没有这笔义务，后续没有可信来源可以恢复和核对。

这不是给任意双写套上 Outbox 名字。
本基线选择结果日志；只有业务事实本来在数据库事务中产生时，才讨论业务变化与 Outbox 同事务的另一条路径。

## 第 5 层：把至少一次交付转成唯一资金效果

**面试官：** 你允许分发器重发；假设 101 的账已经记完，但 ACK 丢了，重投怎样不再扣一次？

**面试者：** 账户消费者必须把“已经处理”与资金效果放在同一本地事务里。它先校验批次来源、版本、哈希和完整性，再锁定资金结转命名空间下的流进度，检查是否已有同 batchId 的去重记录。有记录且内容相同就返回原 APPLIED；同身份内容不同则阻断，不能把冲突也当重复成功。

首次处理时要求 lastSeq=100，再按固定顺序锁账户、资产和预留。
一次事务完成 T0、T1 双方划转、价差返还、平衡分录、去重记录和 lastSeq=101。
事务提交后才 ACK；若提交前失败，所有写入共同回滚，不能留下半批入账。

本例甲预留减少 15,015 USDT 用于成交，再减少 10 USDT返还可用；甲 BTC 增加 0.25。
乙收到 6,000 USDT、预留 BTC 减少 0.10；丙收到 9,015 USDT、预留 BTC 减少 0.15。
如果 T1 的预留校验失败，T0 也不能先提交并宣布整批完成。

ACK 丢失后，重投读到的是资金和去重已经共同成立的事实。
先单独写去重会漏账，先单独扣款会重账；消息系统的去重配置不能补上这两个数据库故障窗口。

## 第 6 层：由连续进度约束释放与无成交结果

**面试官：** 你刚才要求 lastSeq 从 100 到 101；如果 102 先到，而且它说可以释放预留，为什么不能先处理？

**面试者：** 因为释放可能依赖 101 已经形成、尚未结转的成交义务。消费者只知道收到了 102，不等于已经覆盖了 101。它应持久暂存 102 或要求重投，补齐 101 后再推进；不能把消息到达顺序当成业务裁决顺序，更不能先退钱再指望后面扣得回来。

基线要求每个已处理命令位置都有完整结果批次。
即使新位置对应重复 Place、拒绝或无成交，也要保留该位置的裁决结果，资金消费者核验后可在事务中推进进度。
否则 lastSeq 停在 101 时，无法区分 102 是合法无资金变化，还是一笔丢失的成交。

“空结果”只是没有新增成交，不等于没有来源、意图、裁决或哈希。
重复 Place 的新位置必须引用原处理结论，不能把 T0、T1 换成新身份再发一遍。
对于完全相同的 101 消息重投，则仍是原批次，不创建新业务位置。

若 101 无法解析或完整性不成立，就阻断该资金流并保留预留。
死信保存了错误材料，但没有证明跨过缺口是安全的，所以不能自动把 lastSeq 改成 102。

## 第 7 层：从超时恢复追到交易资格关闭

**面试官：** 你说缺口时保留预留；那 Place 超时、查询又没有订单，是否也一直冻结，怎样安全退出？

**面试者：** 不能用超时或查询为空直接退出，因为原 Place 仍可能在网络中或已经可靠受理但尚未形成查询投影。系统先用 I1 继续查询和恢复；用户确定放弃时，向同一市场命令流提交 AbortIntent(I1)，让关闭资格和迟到 Place 在同一权威顺序中裁决，而不是让账户服务自行决定撮合已经不会执行。

如果 Place 先执行，关闭处理已成交义务和真实剩余量；已经成交的部分不能撤销。
如果 AbortIntent 先执行，撮合状态持久保留关闭墓碑，迟到 Place 只能得到拒绝结果。
关闭结果仍经 ResultBatch 交付，账户按连续顺序处理先前成交，再释放确定可退的余额。

在正常 B1 已全成的分支，T0、T1 必须照常结转，关闭不会退回 15,025 USDT。
在完全未接纳、关闭先发生的独立分支，证明未来不能接纳且此前没有义务后，才可能全额释放。
两个分支不能混成“超时先全退，后来有成交再补扣”。

如果关闭响应也丢了，重试的是同一个关闭意图，查询的是原关闭裁决。
为了提高可用性可以报警和催办，但没有关闭证据时，自动退款会把等待问题升级成资产损失。

## 第 8 层：用同水位证据判断能否真正收敛

**面试官：** 关闭和重试都有了；线上看到订单全成但余额没变，怎样判断是正常在途还是已经丢账？

**面试者：** 我会先对齐位置，不直接对比两个不同时间的页面。查 101 是否已提交完整结果，再查分发器交付记录、账户资金结转 lastSeq 和 101 的事务结果。如果结果源有 101、账户还在 100，这是可定位的待处理义务；如果账户声称已覆盖 101，却找不到匹配的分录和去重证据，就是本地原子性或历史保留契约异常，不能用“最终一致”解释。

核对资产时使用同一数据库一致快照，并按币种分别求和。
正常结转后的 USDT 合计仍是 20,000，BTC 合计仍是 0.30；丙的 0.05 BTC 还在 S2 预留中，不能漏算。
查询副本还未追上时，可携带最低水位请求权威读取或返回尚未满足，不把旧缓存当作资金丢失证据。

恢复动作从差异类型推出：未发送就补交付，未应用就重试原批次，投影落后就追赶。
若已确认历史事实错误，走带原引用的新纠正流程，不修改原 T0、T1 或重新生成 tradeId。
可靠来源、充分保留、消费者可恢复运行及阻断问题得到解决，才是最终追上的前提。

验证时可以在各提交点前后人为安排一次崩溃并手工推演恢复状态。
检查的不是“消息有没有出现过”，而是每个已提交义务是否有来源、每个资金效果是否唯一、每次释放是否有完整依据。

## 本题收束

**机制：** 账户预留、命令受理、结果事实、账务效果和查询可见分别有自己的完成证据。持久来源负责不丢事实，稳定身份和消费事务负责不重账，连续前缀与资格关闭负责不提前退资。

**易错边界：** 发布确认不等于账务提交；订单全成不等于账户已结转；查询为空不等于永不执行。ResultBatch 已提交后，交付故障只能改变履行进度，不能取消成交义务。

**反例验证：** 让 101 已提交但尚未交付，102 的关闭结果先到，再让 101 记账后 ACK 丢失。正确结果是先补齐 101、只结转一次、再依据关闭结果释放确定余量；若出现先全额退款或重投再次扣款，协议就没有闭环。
