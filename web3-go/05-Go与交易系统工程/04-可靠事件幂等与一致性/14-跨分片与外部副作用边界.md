# 大问题 14：跨账务分片与外部副作用还能原子消费吗？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 本地事务 / 跨账务分片 | 单库能共同提交的范围与账户分属不同库的变化。 | 每库各自成功不能证明整个 101 同时完成。 |
| batchId / tradeId / 完整义务清单 | 原批次、原成交及全部应履行效果。 | 拆库不改 B1、T0、T1 的价格数量，也不允许删已成义务。 |
| transferId | 一条跨库资产转移的稳定身份。 | 绑定 tradeId、asset、direction 与原账户金额，重试不换号。 |
| leg / 预留绑定 | 一条经济腿及它可以使用的原资金资格。 | T0 的 BTC 与 USDT 是不同义务，不能换币种凑总额。 |
| 清算在途科目 | 源端已经锁定用于跨库履约、暂不可花的资金位置。 | 不是扣余额后仅在协调器内存记一笔，也不因超时退给甲。 |
| 待收影子 / 控制科目 | 目的端未可用的接收状态与配对核对的清算记录。 | 不能和源端在途重复计成两份经济资产。 |
| 释放决定 / 全局完成水位 | 准许待收转可用的持久决定与整批完成前缀。 | 先收齐全部源腿依据和待收状态，局部 ACK 不是整批 APPLIED。 |
| 2PC / prepare | 两阶段提交及参与资源持久准备的能力。 | 有可靠协调日志和真实数据库支持才成立，不是多调几个接口。 |
| in-doubt / COMMIT 决定 | 参与者尚不知全局结论，以及已持久的共同提交决定。 | 等待超时不能自行回滚可能已全局提交的事务。 |
| 读屏障 / 协调围栏 | 限制半批可见，以及阻止旧协调器写冲突决定。 | 2PC 也不自动让任意跨库查询看到同一瞬间。 |
| Saga / 补偿 | 可恢复步骤工作流，以及业务允许的新反向动作。 | 不是失败就退款，更不能逆转已让对方使用的成交资产。 |
| P1 / payoutId | 独立法币提现的业务身份。 | 本例 100 USD、零手续费，不改变 BTC/USDT 成交产品。 |
| providerKey / providerPaymentId | 给支付商的固定业务键与支付商返回的支付身份。 | 原键绑定商户、收款人、币种、金额和业务版本，接管仍复用。 |
| PENDING / UNKNOWN / SUCCEEDED | 待处理、结果不明与有成功证据的状态。 | 超时保持 UNKNOWN，不能退预留再换键重付。 |
| NOT_FOUND / 终局失败 | 暂未查询到与能证明不会再执行的最终拒绝。 | 查询索引可能滞后，查空不自动授权退款。 |
| webhook / 事件去重 | 外部回调与对通知尝试的持久识别。 | 验签并核对商户载荷，通知防重不能代替 P1 唯一资金效果。 |
| 幂等保留窗口 | 支付商承诺原键持续防重的期限与作用域。 | 超出窗口仍未知就暂停自动重发，不默认旧请求不存在。 |
| Outbox / 外部副作用 | 本地交付待办与不受本地回滚控制的远端动作。 | 本地事务、消息 ACK 和长 HTTP 事务都不能回滚已执行支付。 |

## 把整篇文章压缩成一个故事

甲乙丙的账户拆到不同数据库后，B1 仍产生原来两笔成交，但已不能一次本地事务把全部资金一起结转。协调器给每条转移固定身份，源库把对应预留移到不可花的清算在途并留下可靠义务，目的库核验后建立待收。完整批次先收齐全部源腿资金依据和待收状态，再持久决定放行；逐库完成期间可以有阶段差异，不能把影子和在途重复算资产。

乙的入账确认丢失，协调器只能沿原转移身份查证和补交付，不能先退甲 6,000 USDT。要求更强共同提交可考虑真正支持准备状态与可靠全局决定的 2PC，但会付出阻塞和恢复代价，跨库读取还需约束。Saga 能组织续做，不意味着任何失败都能撤销成交；已成 T0、T1 的义务仍要履行，整批完成也不能拿某个分片的 ACK 代替。

另看独立提现 P1：本地先预留 100 USD 并登记固定支付键，再调用支付商。超时、查不到都可能是对方已执行但索引没更新，必须保留 UNKNOWN 和预留，核验迟到回调与权威查询，不能换键重付。只有证明不会再执行才可释放；若对方没有稳定键、查询能力或窗口已失效，就暂停自动尝试并人工核对。本地唯一再严，也无法保证一个不遵守身份契约的远端恰好支付一次。

[返回专题总览](README.md)

**流程位置与核心机制：** 讨论账户结转越过本地事务边界后，怎样保留资金约束、明确在途状态并履行已确定义务；再以独立外部支付变体讨论稳定请求身份、未知结果与能力上限。不扩写完整分布式事务或支付工程。

**明确改变前提：** 总览默认所有相关账户、分录、去重与进度在同一事务数据库。本题第 1—5 层改为甲、乙、丙分属不同账务数据库，不能再依赖一次本地事务完成整批结转；BTC/USDT、B1、T0、T1、零手续费等经济规则不变。

**独立支付变体：** 第 6 层另设已经批准的法币提现 P1，金额 100 USD、零手续费，通过外部支付商执行。它不是把 B1 的 BTC 交易改成法币结算，也不假设资金转到支付商后仍受本地数据库控制。

```text
完整成交批次 → 持久清算义务〔原 tradeId 与全部资产腿〕
    ↓
各分片本地事务：约束预留／记录转出在途、待收状态与可靠交付
    ↓
核验全部资金依据和义务状态 → 按协议释放可用性
    ↓
汇总完整批次状态，不能以某个分片的 ACK 代替整批完成

独立提现 P1 → 本地预留与支付任务共同提交
    ↓
同一 providerKey 调用支付商 → 成功／明确失败／结果未知
    ↓
查询、可信通知与对账 → 按原提现身份确认或继续挂起
```

## 第 1 层：拆库以后失去的原子性具体是什么

**面试官：** 总览把双方余额、去重和进度放在一个事务里。现在买卖双方分属不同数据库，仍然“每个消费者做事务再 ACK”，能保证整批结转吗？

**面试者：** 只能保证各自本地原子，不能保证整个 ResultBatch(101) 一起生效。
甲库先扣 USDT、乙库随后入 USDT，中间乙库失败，就会出现跨库暂态；反过来先给乙可花 USDT，再扣甲失败，就可能放出没有资金依据的资产。
每库都写 inbox 只说明每个局部效果不会重复，不能把几个本地提交自动拼成一个全局事务。

本例还包含甲获得 0.25 BTC、乙获得 6,000 USDT、丙获得 9,015 USDT，以及甲返还 10 USDT 和丙保留 0.05 BTC 预留。
不能只做完其中一条腿，就标记整批 APPLIED；成交事实已经可靠确定，也不能因为跨库难处理而退掉全部预留、宣布交易没发生。
此时必须选择分布式提交协议，或接受显式在途并定义可恢复的清算协议。

我会先保留原 tradeId、batchId 和完整义务清单，再确定每条资产腿由哪个分片处理、什么证据允许收款可用。
本题改变的是结转的原子范围，不是撮合价格、成交数量或成交的约束力。
如果业务不能接受跨库暂态，又不愿承担协调代价，就应重新评估分片方式，而不是拿“最终一致”代替设计。

## 第 2 层：在途资金与清算义务怎样保持可核对

**面试官：** 你选择显式在途。甲库已经扣了 6,000 USDT，乙库还没入账，这笔钱落在哪里，怎样证明既没丢也没凭空增加？

**面试者：** 我会为 T0 的这条转移建立稳定 `transferId=(tradeId, asset, direction)`，并绑定来源账户、目的账户、金额和完整载荷。
源分片在同一本地事务内把甲的对应预留转到不可花的清算在途科目，写平衡分录、唯一转出效果与可靠交付记录。
这不是把甲的余额字段减掉后只在协调器内存里记一句“稍后补给乙”，而是可恢复的资金位置和支付义务。

目的分片先核验稳定转移身份与可信资金依据，记录不可花的待收或影子状态；源端提交证据只能授权原来这一条腿，不能复用于另一个收款人。
完成入账时，目的库也要用平衡分录和唯一效果约束连接收款账户与清算控制科目；跨库控制科目按同一 transferId 配对核对。
待收影子不能与源端在途重复计作新增经济资产，更不能提前并入用户可用余额。

全局核对既检查各库分录平衡，也检查用户资产桶、唯一在途位置和跨库控制科目的对应关系。
T0 的 0.10 BTC 与 6,000 USDT 是不同币种的两条义务，T1 同理，不能把币种相加后用一个差额掩盖缺腿。
甲的 10 USDT 价差也必须依据完整成交处置结果返还，不能把尚未收到确认的本金误认成可释放余量。

## 第 3 层：超时不能释放已绑定义务的在途资金

**面试官：** 在途记录已经持久化，但乙库入账成功后的确认丢了。协调器超时，能否先把甲的 6,000 USDT 退回，再决定是否重试？

**面试者：** 不能。超时只代表协调器不知道目的效果，不代表乙没有收到，也不代表成交义务消失。
源端按同一 transferId 查询、补交付和核对，目的端通过唯一效果返回原结果；旧协调任务失去所有权后，还要防止它继续生成与新任务冲突的状态决定。
在结果未决时保留不可花在途或原有资金承诺，不能因一个计时器到期就把已绑定资金重新交给甲使用。

如果采用本题的显式在途方案，我会先为完整批次收齐全部源腿不可撤销的资金依据，并在各目的分片建立对应的待收状态，再持久化允许释放的决定。
之后各库按稳定释放身份把待收转为可用；目的入账证据用于核销源端在途和配平控制科目，不是再给甲退款的依据。
确认丢失时按同一 transferId 查证并核销，核对按转移状态配对，不能把源端未清在途与目的端已到账再加成两份资产。
部分库暂时未完成时，协调器继续履约，不能撤销已经开放的另一边；允许的是阶段差异，不是没有可靠资金义务的可花资产。

全部本地应用证据收齐后才将整批标记完成；各分片自己的已应用水位与全局完成水位必须区分，不能拿局部最大值冒充完整前缀。
若缺少永久可恢复的资金依据，或者业务要求所有账户同时可用，这个异步方案就不满足要求，需要更强协调。
不能靠隐藏 PENDING 字段，把没有实现的跨库原子性包装成已经保证。

## 第 4 层：2PC 提供什么，又为什么付出可用性代价

**面试官：** 如果业务不能接受你说的阶段差异，改用两阶段提交不就行了吗？为什么不一开始就选 2PC？

**面试者：** 如果参与数据库都支持持久 prepare，并且协调器有可靠的全局事务日志，2PC 可以让这些受控资源服从同一个提交或回滚决定。
参与者先校验并准备余额、预留、分录、唯一效果和局部进度；协调器收齐准备成功后持久记录 COMMIT，再推动各参与者完成。
未进入全局提交决定时可以回滚准备动作，但回滚的是本次结转尝试，不会抹去已经确定的成交义务，之后仍需恢复处理。

代价是准备状态可能长期占锁、占连接或限制后续资金操作，协调器故障和网络分区会使参与者处于 in-doubt。
参与者不能因为自己等待超时就随意回滚一个可能已经全局 COMMIT 的事务；恢复必须查询可靠决定，并防止旧协调器写入冲突决定。
分片数越多、热点账户越集中，事务寿命和故障影响范围越难控制，不能把协调器的一条数据库记录当成完整 2PC 实现。

2PC 的原子提交也不自动等于任意跨库读都能看到同一瞬间，各库提交可见时间和隔离级别仍需统一读取协议约束。
若要求对外不能观察到半批，需要通过全局完成标记、读屏障或相应隔离设计限制业务可见性。
它只覆盖真正参与协议的资源，不能顺手把不支持 prepare 的 HTTP 支付商也纳入同一个原子提交承诺。

## 第 5 层：Saga 是恢复工作流，不是随时逆转成交

**面试官：** 2PC 太重，那用 Saga 加补偿，让失败分片触发其他分片退款，是否就兼顾吞吐和正确性了？

**面试者：** Saga 可以组织可恢复的局部步骤，但补偿必须是业务允许的新动作，不是让过去的成交自动失效。
在 T0、T1 已确定的前提下，优先策略是保留原预留或在途资金，继续完成原清算义务；某一步失败就退款，可能导致对手方已经拿到资产，而系统失去付款依据。
因此我会持久记录步骤、载荷、原效果引用、重试结果和未完成义务，让任务重启后继续同一协议。

只有真正可撤销且尚未越过承诺边界的准备动作，才可以按规则解除；已经确定用于履约的资金不能因任务失败被当作普通临时锁释放。
如果确需纠错、冲正或追索，要产生带原引用的新审计事实，评估余额是否已转移，以及由谁承担不能追回的缺口。
协调器发出一个 `Compensate` 命令并不意味着外部或其他账户一定能够恢复原样，补偿自己也可能失败。

选择异步方案时，我会把最大在途量、最长未完成年龄、受影响资产范围与人工接管条件列为运行约束。
局部异常要阻断依赖它的后续完成承诺，而不是无限堆任务后声称一定会最终一致；要承诺收敛，来源、状态和处理能力都必须可恢复。
若这些约束无法满足，应该缩小跨分片事务范围或承担更强协调，而不是给 Saga 换个名字就当作已解决原子性。

## 第 6 层：外部支付必须绑定稳定 providerKey

**面试官：** 你说协调协议只覆盖受控资源。如果下一步是调用外部支付商，发出独立提现 P1 的 100 USD，怎样防止重试多打一次钱？

**面试者：** 这里切换到开头声明的独立法币提现变体，不改变 BTC 现货清算规则。
先在本地事务中把 100 USD 从可用转为提现预留，创建稳定 payoutId=P1、固定 providerKey 和可恢复支付任务，提交后才允许调用支付商。
providerKey 绑定商户作用域、币种、金额、收款人及业务版本；重启、超时、worker 接管都使用原键，不能每次尝试生成新键。

支付商需要明确承诺在相同商户和键下，同载荷返回原支付结果、异载荷冲突，并说明这个承诺的保留窗口。
发起任务前还要验证收款资料、授权和限额；幂等只限制重复效果，不替代这些业务检查。
本地协调器可用租约减少并发，但真正防止多个 worker 越过网络边界重复打款，依赖支付商承认同一稳定键的去重契约。

支付提交成功后才崩溃、本地尚未记状态，是正常必须覆盖的故障窗口。
本地数据库事务、Outbox 和消息 ACK 都不能回滚支付商已经完成的动作，不能把 HTTP 调用包在一个长事务里就宣称一起提交。
支付任务要保留 PENDING、UNKNOWN、SUCCEEDED、明确失败等状态，并把资金桶转换与本地状态在事务内绑定。

## 第 7 层：查询未知结果与处理迟到通知怎样衔接

**面试官：** P1 调用超时，查询暂时查不到，之后成功 webhook 又迟到了。此时能否换个 providerKey 重试，或者先退回提现预留？

**面试者：** 都不能。超时后先保持 UNKNOWN 和原预留，按原 providerKey 或原 providerPaymentId 查询权威结果。
查不到可能只是支付商查询索引尚未同步；除非契约明确证明原请求已终止且不可能迟到生效，否则 NOT_FOUND 不是安全退款依据。
允许重发时也只在原键有效去重窗口内重发相同载荷，不能把查询失败转换为一笔新支付。

webhook 要验证签名、商户归属、支付身份和载荷，并在本地以稳定事件身份去重；但通知事件去重不替代 P1 的唯一资金效果。
迟到的 PENDING 不能覆盖已确认成功，互相矛盾的终态应查询权威状态并阻断核查，不能按到达顺序最后写赢。
成功证据确定后，以 P1 为效果身份在本地事务中消费预留、写平衡分录、记录支付结果和通知来源，重复回调只返回原结果。

只有得到明确拒绝、已完成取消或其他足以保证原支付不会再执行的终局证据，才按策略释放预留。
支付商返回“已受理”也未必等于资金最终到达，应按其状态契约区分提交、清算和收款完成；可逆状态不能伪装成终态。
若确已支付却需撤回，退款是引用原支付的新业务义务，可能受余额、费用或对方配合限制，不能当作数据库回滚。

## 第 8 层：缺少外部幂等或查询能力时怎样诚实限定保证

**面试官：** 支付商不支持稳定键去重，也不能按业务身份查询；或者幂等窗口已经到期，P1 仍然未知。你的方案还能保证恰好一次吗？

**面试者：** 不能。在“请求可能已执行，但调用方无法确认”的窗口里，盲目重发可能重复支付，不重发可能永久漏付。
本地唯一键只能约束本地记录，不能阻止一个不理解 providerKey 的远端再次转账；没有可靠查询也就不能消除这个不确定性。
即使支持幂等，超过保留窗口仍未知时也不能默认旧请求不存在，更不能自动换键继续。

我会暂停自动重发并保留未知义务和资金约束，通过支付商流水、人工核验或更强渠道补足证据；若始终拿不到证据，就向业务明确无法自动收敛的风险。
产品只能在受控的“避免再次发送但可能漏付”与“持续重试但可能重复”之间作取舍，或更换具备所需契约的服务商，不能宣传外部效果恰好一次。
人工处理也要保留原 P1 和证据，不能删掉 UNKNOWN 再建新单，把同一个不确定支付伪装成全新业务。

检查时我会分别推演：源分片已扣但目的确认丢失、全局决定提交后协调器崩溃、外部支付成功但本地超时、NOT_FOUND 后成功回调，以及幂等窗口过期。
预期是恢复原义务、不先退款、不重放已可花资产，并在缺证据时停止自动放行；这是设计预期，不是已执行的工程实验。
系统的保证上限由最弱的跨边界契约决定，不能靠增加 worker、消息队列或补偿任务突破它。

## 本题收束

**讲透的机制：** 拆库必须重建原子边界；显式在途与持久义务约束资金可用性；2PC 需要真正的 prepare 和可靠决定；Saga 组织恢复而非逆转成交；外部支付依靠稳定 providerKey、查询与唯一业务效果闭环。

**易错边界：** 各库事务不等于跨库事务；在途与待收不能重复计作资产；局部 ACK 不等于整批完成；已给出可花资产后不能把失败当没发生；支付超时与 NOT_FOUND 都不自动授权退款或换键重发。

**检验反例：** 支付商已经执行 P1，但响应丢失，本地先退回 100 USD，再用新 providerKey 重试。用户既拿回可用余额，又可能收到两次外部支付；本地每条任务都“事务成功且唯一”也无济于事，错误发生在跨边界的未知结果与身份协议。
