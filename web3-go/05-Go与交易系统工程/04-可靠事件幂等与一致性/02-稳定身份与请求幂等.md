# 大问题 2：请求与业务身份怎样设计，才能在超时、重复和恢复后安全重试？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 幂等 / 稳定身份 | 同一业务重试仍找原结果，不再产生第二份效果。 | 不仅防重复下单，还要防重复撮合与重复入账。 |
| accountId / operation / clientOrderId | 谁发起、做什么、用户给它的业务编号。 | 三者共同组成请求作用域，甲的 buy-001 不是全局裸编号。 |
| traceId / attemptId | 一次调用链或一次网络尝试的排障编号。 | 每次可变，但不能据此新建订单或重记资金。 |
| intentId / reservationId | 原业务意图及其专用预留的身份。 | I1、R1 与请求映射和 15,025 USDT 预留共同提交。 |
| 唯一约束 / 先查再插 | 数据库裁定同键只能有一条，与存在竞争窗口的普通查找。 | 两实例都查空时仍只能建立一份有效资格。 |
| 同键异载荷 | 编号相同，经济参数却与原业务不同。 | buy-001 改为 0.30 BTC 是冲突，不是安全重试。 |
| 规范化 / 最小单位整数 | 先把相同经济值转成统一、精确的表示。 | 0.250 与 0.25 可相同，不能用浮点近似计算资金。 |
| schemaVersion / payloadHash | 原参数的编码规则版本及摘要。 | 查旧意图用原版本，摘要不替代授权和关键字段校验。 |
| COMMIT 未知 / 权威读取 | 提交回包丢失时，从负责该状态的存储查证。 | 副本暂时查不到不证明原预留失败，不能另发 buy-002。 |
| commandSeq / batchId | 命令顺序位置及该位置的结果身份。 | 同一 I1 可进入 101、102，但只首次执行。 |
| tradeId / matchIndex | 一笔成交的稳定身份及其在批次内的序号。 | T0、T1 由原流、101 和各自序号定位，不能重发换号。 |
| 空／重复结果 | 有处理结论但没有新成交的完整批次。 | 102 引用原裁决，仍填满进度，不能重新包装 T0、T1。 |
| effectNamespace / consumerGroup | 业务效果的固定范围，以及消息订阅的部署名字。 | 换消费组不代表可以再做一遍资金结转。 |
| legType / 分录唯一键 | 资产变化属于哪条经济腿。 | 买方支出、卖方收入分别定位；价差返还不虚构新成交。 |
| contentHash / HISTORY_REQUIRED | 原整批内容的绑定，以及缺历史证据时的核验要求。 | 已覆盖旧序号也不能吞掉异内容，缺原记录先查归档。 |
| TTL / 关闭墓碑 / epoch | 保留时间参数、防迟到复活记录与执行任期。 | 清理和切主不能抹掉意图裁决，epoch 不加入原成交身份。 |

## 把整篇文章压缩成一个故事

甲用 buy-001 下单买 0.25 BTC，限价 60,100，两个接入实例几乎同时收到。它们都可能先查不到记录，但数据库唯一约束与账户事务只允许一份 I1、R1 生效，预留 15,025 USDT。回包丢失后，甲仍带原键和原参数查询；若客户端把数量改成 0.30，就必须报冲突，不能借“重试”悄悄改掉已绑定的交易。

恢复扫描把原 Place 又送了一次，第一次排到 101，第二次排到 102。撮合认的是同一个意图：101 产生 T0、T1，102 记录重复结论和原结果引用，没有新成交，但也不能省掉结果造成缺口。两笔原成交实际花费 15,015 USDT；账务用固定效果身份结转并返还 10，甲最终可用 4,985 USDT、得到 0.25 BTC。

上线时运维换了消费组，旧 101 又从归档出现。新进程必须沿用资金结转命名空间，核验原内容返回原结果，不能因为组名新就再次入账。热去重过期也不是重新接纳的许可，缺证据要查历史；切主还要恢复意图裁决和关闭墓碑。请求、命令位置、成交、分录各有自己的身份，只有这条链不断，超时与恢复才不会把同一件事变成第二笔业务。

**流程位置与核心机制：** 从 clientOrderId 追到 intentId、reservationId、commandSeq、batchId、tradeId 和分录效果身份，证明同一业务不会因重试变成第二笔。本题重点是身份作用域、载荷绑定、持久唯一性和保留契约；不替代第 3 题的关闭协议与第 6 题的完整消费事务。

沿用总览的甲、B1、I1、R1 和 `BTCUSDT:v1`。101 批次产生 T0、T1，两笔实际支出合计 15,015 USDT，原预留 15,025 USDT；所有重试都必须指回这组事实。

## 第 1 层：区分一次请求、一个意图和一次投递

**面试官：** 客户端下单超时后重试，你会怎样设计身份，防止重复下单和重复占资？

**面试者：** 我会先区分用户业务意图和网络尝试。请求键采用 `(accountId, operation, clientOrderId)`，本例是甲的下单操作 buy-001；同键同载荷必须找到同一个 I1、订单身份和 R1。HTTP traceId、RPC attemptId 或消息投递 ID 每次都可以变化，但它们只能用于排障，不能决定是否再建立业务。

账户域在一个本地事务里建立请求映射、I1 和 R1，并把 15,025 USDT 从可用移到预留。
事务提交后才允许向撮合提交原 I1；重试先读映射，不再扣一次可用余额。
不能先返回一个订单号，随后异步建立预留，却声称同一请求已经有完整交易资格。

下游还有不同层次的身份：commandSeq 表示有序命令位置，batchId 表示该位置的结果，tradeId 表示批次里的某笔成交。
同一个意图的重复命令可能进入新位置，所以 commandSeq 不能代替请求去重键。
反过来，I1 也不能直接代替所有分录键，因为一个订单可能对应多笔成交和多条资产变化。

如果只用一个消息 ID 贯穿所有场景，重发换 ID 会重账，不换 ID 又可能混淆多笔合法成交。
身份必须回答“哪一种对象的同一个”，然后才谈如何去重。

## 第 2 层：让两个并发首次请求只占一份资金

**面试官：** 你说先读映射，但两个实例同时没读到 buy-001，会不会各建一个意图？

**面试者：** 会，所以“先查再插”本身不够。我会由数据库唯一约束裁决请求键，且请求映射、意图、预留和余额桶变化必须共同提交。可以先尝试插入唯一请求行，再锁账户资产行校验可用并预留；另一个事务在同一唯一键上等待或冲突，回滚自己的尝试后读取已提交的原结果，不能继续使用自己生成的第二个意图。

对于甲，本次合法提交只把可用 20,000 改为 4,975 USDT，并建立一份 15,025 USDT 的 R1。
败方即使提前生成过候选 ID，也不能让它离开事务成为有效资格。
如果持锁事务在提交前崩溃，其插入和扣款一起回滚；胜负必须看数据库提交，不看哪个实例先打印了日志。

余额不足与同键并发冲突也要区分。
如果已有 I1，重试返回 I1 的状态，不因为甲当前可用只剩 4,975 就把原成功请求改判成新下单余额不足。
若同键原事务最终没有提交，才重新走首次创建和余额校验。

Redis 锁可以减少竞争，但锁过期、实例暂停或故障切换后都不能替代唯一约束。
真正防止双占资的是同一个持久提交边界，而不是某段时间内“应该只有一个执行者”。

## 第 3 层：同一键携带不同经济参数怎么办

**面试官：** 并发请求最终找到了同一行；但第二个把数量改成 0.30 BTC，是否仍返回原成功？

**面试者：** 不能。幂等键绑定的是原业务载荷，不是允许随时改参数的订单别名。系统必须先比较规范化载荷；同键同载荷返回原意图，同键异载荷返回冲突，不新建 R1，也不把原订单悄悄改成 0.30 BTC。如果用户要改价改量，应按产品规则发起另一种明确操作，而不是复用下单键。

规范化时，先按交易对精度把价格、数量转成最小单位整数。
固定 schemaVersion、字段顺序、空值与枚举表示，把方向、交易对、限价、数量、订单类型等经济字段绑定到摘要。
`0.250` 与 `0.25` 可以表示同一数量，但不能因普通 JSON 字段顺序不同误判冲突，也不能把买卖方向漏出摘要。

保存 payloadHash 的同时，要保留足够的原始规范化参数及版本以便审计和冲突定位。
摘要用于快速比较，不是鉴权凭证；账户、授权范围和关键经济字段仍须验证。
升级编码不能把老意图按新规则重新解释，查老请求时应使用它原来的载荷版本。

本例 buy-001 绑定 0.25 BTC、60,100 USDT/BTC 和原市场。
改成 60,000 或换到另一个市场，都是同键异载荷，不能用“客户端重试”掩盖另一笔经济行为。

## 第 4 层：预留事务提交超时，不制造第二份意图

**面试官：** 载荷已经绑定；但创建 I1 的数据库 COMMIT 超时，服务端也不知道成没成功，还能怎样重试？

**面试者：** 我会把它当成提交结果未知，而不是事务肯定回滚。恢复时按原请求键查询权威数据库，找到记录后核对载荷，再返回同一个 I1、R1 和状态。如果读的是延迟副本而暂时没有记录，不能据此建立另一份资格，更不能先补回 15,025 USDT；需要权威读取或通过同键事务重试让数据库唯一约束完成裁决。

这时安全重试仍是原键、原载荷，不能为提高成功率生成 buy-002。
如果原事务已提交，新尝试命中唯一键；如果已确定回滚，新尝试才可能成为唯一首次提交。
若数据库暂时无法确认，就返回处理中并保留查询入口，不把不确定性伪装成明确失败。

预留提交后、Place 发出前崩溃，也要能继续推进。
账户数据库中的已提交待提交意图应可被恢复扫描，提交器找回 I1，使用同一绑定预留继续发送。
如果只有内存队列记录“待发 Place”，重启后就会永久占资而没有恢复任务。

恢复扫描可能与原提交器并发，因此下游也必须按 I1 去重。
账户侧的一次提交解决重复占资，但不会自动让跨进程发送只发生一次。

## 第 5 层：同一意图进入两个命令位置也只能执行一次

**面试官：** 你承认恢复扫描可能重发；原 Place 在 101，重发又进入 102，commandSeq 不同还能去重吗？

**面试者：** 能，但必须在撮合域持久维护意图裁决，而不能按 commandSeq 判断是否新订单。有效单写者按序处理 101 时，校验 I1 的载荷及 R1 资格，首次有效执行并产生 T0、T1；处理 102 时发现 I1 已有裁决，就引用原位置和结果，不再次入簿、撮合或消耗预留。意图裁决必须能从已提交结果或一致检查点恢复。

101 的身份是 `(BTCUSDT:v1, 101)`，两笔成交分别是 `(BTCUSDT:v1, 101, 0)` 和 `(BTCUSDT:v1, 101, 1)`。
102 仍然需要自己的结果批次，记录重复意图、原裁决引用和零新增成交。
“重复命令无资金变化”不能解释成没有 102，否则下游无法形成完整连续前缀。

102 可以携带供查询使用的原结果引用，但不能把 T0、T1 当作本位置新产生的交易事件重新装载。
在 ResultBatch 与 AppliedSeq 的共同提交中，首次意图裁决也必须具备可恢复证据。
如果崩溃后忘了 I1 已执行，稳定 batchId 本身也阻止不了它在新位置再成交一次。

Place 若曾被明确拒绝，也要返回已确定的原裁决，而不是等余额或盘口变化后自动变成成功。
想建立另一笔业务必须有新意图和新的合法资格，不能让重试具有条件性重新执行的含义。

## 第 6 层：把稳定身份继续约束到账务效果

**面试官：** 你保证撮合不重做了；同一个 101 交付两次，或者消费者换了消费组，账务身份该怎样设计？

**面试者：** 消费去重键应包含稳定业务效果命名空间和原批次身份，例如 `(资金结转, BTCUSDT:v1, 101)`，不包含消费组名、实例 ID 或发布尝试 ID。换消费组是部署行为，不是重新产生账务义务；命名空间若随部署变化，原成交就会被当成新业务再次入账。

去重记录保存 contentHash、版本和原处理结果，与资金、分录、lastSeq 一起提交。
相同 batchId、相同内容返回原结果；相同 batchId、不同内容阻断。
若 lastSeq 已覆盖 101 而原记录丢失，应查归档证据，不能仅凭“老序号”吞掉可能的内容冲突。

分录还需要更细的效果身份。
对成交资产腿，可用 `(effectNamespace, tradeId, legType, accountId, asset)` 唯一约束；价差返还则引用原 batchId、订单或预留和稳定处置类型，不能虚构第三笔 tradeId。
这样 T0 的买方支出、卖方收入和 BTC 转移各有确定位置，但同一腿不会因重放再出现一次。

批次唯一和分录唯一是两道防线，不是允许半批成功后逐条忽略冲突。
本基线若出现“原批次未提交但部分分录已存在”，应阻断调查共同事务为何被破坏，而不是继续拼出一个看似成功的结果。

## 第 7 层：去重记录过期后怎样面对历史重试

**面试官：** 你需要保存原身份和哈希；如果一天后清理去重记录，旧消息或旧客户端请求又来了怎么办？

**面试者：** 不能仅按缓存 TTL 宣布历史已经安全。请求键保留期、命令可重放范围、消息和归档保留期、备份恢复跨度以及客户端重试契约必须一起设计。只要旧事件还可能被合法重放，系统就要保留能证明原裁决和效果的持久证据，或明确拒绝超出安全窗口的重试，不能把“查不到”解释成新请求。

热表可以压缩，历史也可以归档，但必须保留身份不可复用的边界和核验路径。
遇到旧键时，查原意图及摘要，或者返回历史查询／超出重试窗口；不能删除唯一映射后重新预留。
对于已覆盖序号，消费者可从可信归档核对原内容，不得在去重表为空时重新应用。

如果必须允许用户重复使用业务编号，应显式引入有契约的代际作用域，并让旧请求带旧代际被拒绝。
不能用当前日期隐式换代，因为迟到请求可能在午夜后被当作新请求。
本专题不引入这种额外能力，buy-001 始终指向原 I1。

历史保留也覆盖关闭墓碑和已执行意图映射。
保留成交却删掉意图裁决，迟到 Place 仍可能在新位置执行；所以保留策略保护的是整条业务证据链，不只是消费者的一张去重表。

## 第 8 层：恢复与迟到请求不能复活原身份

**面试官：** 你把关闭墓碑也纳入保留了；若切主或恢复旧备份，旧 I1 会不会被重新接纳？

**面试者：** 恢复必须把订单、意图裁决、关闭墓碑和 AppliedSeq 放在同一个逻辑前缀上。先从一致检查点恢复，再应用之后已提交结果，把 I1 的首次执行或关闭状态补齐，最后才能接新命令。不能只恢复订单簿、忘记已处理意图，也不能直接从落后备份开放交易，否则迟到请求会被误当首次出现。

`BTCUSDT:v1` 是流命名空间，切主不改变它。
领导者任期和围栏凭证用于阻止旧主继续提交，但不能拼进 tradeId 把原事实变成新身份。
恢复和补交付仍使用原 batchId、tradeId 与资金结转命名空间；规则版本也沿用原裁决需要的版本。

若 I1 已关闭，迟到 Place 必须命中同域排序形成的关闭状态，输出拒绝或重复结果，不能因账户当前又有钱就重启资格。
若 B1 已成交，恢复只能继续履行 T0、T1，不能先退资再重撮合。
身份相同也不意味着请求天然有权限，重试仍要验证账户授权和原绑定参数，不能让持有某个 intentId 的调用方替别人操作。

最终验收要同时检查不重复创建、不重复执行和不重复应用。
只证明数据库有一条 buy-001，而撮合和账务仍能用新位置或新命名空间多执行一次，不能叫端到端幂等。

## 本题收束

**机制：** 请求键确定意图，意图绑定预留与规范化载荷，命令位置确定结果批次，批次内身份确定成交，业务效果命名空间确定分录与消费去重。每一层唯一约束保护的对象不同，不能用投递 ID 或内存锁互相替代。

**易错边界：** 同键异载荷是冲突，不是安全重试；新 commandSeq 不代表新意图；新消费组不代表新资金效果。空／重复结果也要占有它自己的已处理位置，不能重新包装原成交成为新事实。

**反例验证：** 两个实例同时提交 buy-001，预留提交响应丢失，Place 被恢复扫描再发到 102，最后换消费组重投 101。正确结果只有 I1、R1 一份，T0、T1 各一笔，甲最终可用 4,985 USDT、0.25 BTC；若任何一步因换身份多做一次，幂等链就断了。
