# 大问题 6：消息重复消费时，怎样只产生一次完整账务效果？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 完整 ResultBatch | 一条命令全部裁决的整体，而不是单条成交回调。 | 101 要覆盖 T0、T1 和价差处置，不许只给买方入账。 |
| effectNamespace | 标记同一种业务效果的固定范围。 | 资金结转不会因消费组、实例或部署版本改变而重新成立。 |
| streamId / seq / batchId | 原流、流内位置及整批身份。 | 消费身份指向 BTCUSDT:v1 的 101，不按投递次数判断新业务。 |
| inbox / RECEIVED / APPLIED | 持久接收与处理证据，以及接到、应用完两种状态。 | 记录存在不等于已经记账，提前接收仍有未完成责任。 |
| contentHash / schemaVersion | 原内容绑定及编码版本。 | 同叫 101 却改 9,015 为 9,016 必须冲突，不能静默去重。 |
| lastSeq / GAP | 已应用连续前缀，以及缺前序的结果。 | 新批次只能是下一位，不能把最大已见值写成完成进度。 |
| 进度行锁 / mutex | 数据库跨实例串行化，以及进程内互斥。 | 每实例的 Go 锁不能挡另一实例同时写资金。 |
| 共同提交 / 本地事务 | 一组写入要么全成立，要么全回滚。 | 双方资产、预留、分录、去重、结转状态和进度在同库完成。 |
| 预留绑定 / R1 | 这笔资金资格究竟属于哪个订单。 | 总预留足够不代表能扣另一单的钱，R1 必须对应甲的 I1、B1。 |
| tradeId / legType | 原成交与具体经济腿的稳定标记。 | 支出、收入、BTC 转移各有唯一效果，返 10 另引用原处置。 |
| 唯一约束 / ON CONFLICT | 数据库拒绝重复身份，以及可能吞掉插入冲突的语法。 | 不能忽略冲突后继续扣钱，须回滚或受控重读核验。 |
| 逐资产平衡 / 桶非负 | 各币种转移有对应去向，各资金桶不能透支。 | BTC 不与 USDT 相加，守恒也不能证明账户归属正确。 |
| COMMIT 未知 / HISTORY_REQUIRED | 提交成败待查，以及旧批次缺证据需历史核验。 | 不先退款、不换身份，已覆盖序号也不能无条件返回成功。 |
| ACK / offset | 消息确认与运输位置。 | 默认应用后确认；提前 ACK 必须先可靠持久接收完整内容。 |
| 锁序 / 死锁重试 | 各写路径统一取锁次序，以及整笔回滚后的重做。 | 多市场共享账户时仍锁当前资金行，失败重试原完整批次。 |
| 外部副作用 / 跨分片 | 不受同一本地事务控制的支付或其他数据库写入。 | 事务内调用 HTTP 也不能回滚远端，本题保证不包外部系统。 |

## 把整篇文章压缩成一个故事

账户消费者收到 B1 的完整 101，甲为它预留了 15,025 USDT。程序先锁该流进度，再锁甲乙丙的资产与预留，确认每笔义务属于正确订单。一次事务付乙 6,000、付丙 9,015 USDT，把卖方 0.25 BTC 转给甲，再把 10 USDT 返回甲可用；分录、原批次处理证据、结转状态与进度也同时提交，任何一腿失败整批回滚。

事务刚完成，消息确认丢了，另一实例又拿到 101。它等待同一数据库进度锁，读取原内容绑定，核验一致就返回原 APPLIED，不再次改钱。甲仍是可用 4,985 USDT、0.25 BTC；若重投把 T1 改成 9,016，即便自带新校验和，也必须报冲突。若进度已到 101 却没原记录，则先找历史证据，不能凭旧序号盲目宣告成功。

为了减轻消息阻塞，团队也可先持久接收再确认，但 RECEIVED 不能冒充 APPLIED，后台仍要完成原资金事务。换消费组也继续使用同一资金效果范围，不能新组重记一遍。把去重先写会漏账、把余额先写会重账，Go 锁和消息配置都补不上这道缺口；跨库或外部支付更不能顺便塞进本地事务，必须另定协调与未知结果处理协议。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题从完整 ResultBatch 到达账户消费者开始，追问双方资产、预留、分录、消费去重和 lastSeq 怎样共同提交。核心是数据库事务与持久唯一约束，不是靠一次网络投递或进程锁得到“恰好一次”；完整性和顺序来源由第 7 题继续展开。

**讨论前提：** 所有相关账户、预留、分录、inbox 与进度都在同一本地事务数据库。沿用 BTCUSDT:v1 的完整 101：甲的 B1／I1／R1 预留 15,025 USDT，T0 为 6,000 USDT、T1 为 9,015 USDT，价差返还 10 USDT；初始 lastSeq=100，零手续费。

```text
完整批次到达 → 校验来源、版本、规范化编码和完整性
    → 开始账户事务 → 锁流进度 → 核验原批次与连续序号
    → 锁双方账户及预留 → 校验全部义务 → 写资产、分录、inbox、lastSeq
    → 事务提交 → 再 ACK；提交未知则查原结果或重试原批次
```

## 第 1 层：重复可以发生，资金效果不能再次发生

**面试官：** 账户消费者结转 101 成功后，ACK 丢失，消息又来一次。怎样保证甲、乙、丙不会再次入账？

**面试者：** 我会让“101 已产生账务效果”的证据与全部账务变化处于同一个本地事务。
消费身份采用 `(effectNamespace, streamId, seq)`，其中批次是 `(BTCUSDT:v1, 101)`，业务命名空间表示资金结转。
首次提交同时改变双方资产和预留、写平衡分录、保存 inbox 的原内容摘要与处理结果，并把 lastSeq 从 100 推进到 101。

ACK 丢失后，重投仍携带原批次身份和内容；消费者查到已提交记录，核验内容相同后返回原 APPLIED，不再执行余额变化。
如果第一次在事务提交前失败，资产、分录、inbox 与进度共同回滚，重试可以完整执行，而不是接续一半的入账。
这里保证的是同一业务效果至多发生一次，并在可靠来源和持续重试等条件下完成，不是消息只能到达一次。

去重若先单独提交，进程可能在记账前退出，形成“已处理但没给钱”；若记账先提交、再补去重，窗口内重试可能重复入账。
因此 Redis 标记、内存集合或消息系统的已消费标记都不能替代这次数据库共同提交。
允许重复的消息尝试，不能变成重复的经济义务。

## 第 2 层：同一批次号并不证明内容相同

**面试官：** 你说查到已处理就返回 APPLIED。假如重投仍叫 101，却把 T1 从 9,015 改为 9,016 USDT，直接跳过也不会多扣钱，为什么不行？

**面试者：** 直接跳过虽然可能暂时没有多扣钱，却掩盖了权威事实冲突，不能声称幂等校验成功。
同一 batchId 必须绑定同一规范化内容和版本；原 inbox 保存 contentHash、schemaVersion 及可查询的处理证据，重投先核验这些绑定。
即使新消息自行重算了传输校验和，也不能改变数据库中原批次已经绑定的内容。

若摘要或版本绑定不同，我会返回冲突并阻断受影响流，保存两份证据供核查，不覆盖原记录、不按差额补扣，也不把它当正常重复 ACK。
摘要应基于固定编码，金额与数量转为最小单位整数，避免相同经济内容因浮点或字段编码差异被误判。
关键经济字段、授权与来源仍要校验，不能因为两个摘要相等就认为任意来源都有权产生资金效果。

lastSeq=101 也只说明该前缀曾被应用，不说明任何声称属于 101 的载荷都正确。
若原 inbox 因错误清理而不见，不能只按 `seq <= lastSeq` 静默成功；必须找回可信历史证明，否则转入 HISTORY_REQUIRED 并核查。
“原身份、原内容、原结果”一起成立，才是安全返回原结果的重复。

## 第 3 层：把去重、顺序与资产放进同一提交边界

**面试官：** 内容必须核验，那具体怎样安排事务步骤？进度、inbox 和余额分别何时读写，才能避免读完之后状态又被改掉？

**面试者：** 来源、固定版本编码和整批完整性可以先做无副作用校验，但涉及当前资金状态的判断必须在事务内完成。
开始事务后先锁 `(资金结转, BTCUSDT:v1)` 的进度行，再读取原 inbox；已存在时核验绑定并返回原结果，不存在时要求 seq 恰好等于 lastSeq+1。
进度行的初始化也须有唯一约束和受控起点，不能由任意消息自行宣布“此前都处理过”。

对于全新 101，按固定顺序锁定甲、乙、丙的账户／资产桶及相关预留，校验完整事件、订单绑定、预留余额和分录唯一键。
全部条件成立后，才写资金变化、平衡分录、inbox 的 APPLIED 结果、B1 的 settlementStatus=APPLIED，以及 lastSeq=101。
这些写入必须使用同一数据库事务，任何一步失败都回滚，不能由不同服务连接各自提交后声称逻辑上属于一批。

事务提交前不 ACK；提交成功后才能按照“已应用后确认”契约确认消息。
即使进程在写完第一条分录之后崩溃，数据库也只能恢复到整批未提交或整批已提交，而不是要求应用靠猜测补完半笔账。
因此本题的原子单位是完整结果批次的账户效果，不是一个成交腿或一条消息回调。

## 第 4 层：完整 101 究竟共同改变哪些资金

**面试官：** 你强调完整批次，能把 101 的双方资金和预留全部展开吗？如果只给买方入账，再异步通知卖方补账，有什么问题？

**面试者：** T0 将甲预留 USDT 减少 6,000，乙可用 USDT 增加 6,000；乙预留 BTC 减少 0.10，甲可用 BTC 增加 0.10。
T1 将甲预留 USDT 减少 9,015，丙可用 USDT 增加 9,015；丙预留 BTC 减少 0.15，甲可用 BTC 增加 0.15。
B1 全成且实际支出 15,015 USDT，剩余 10 USDT 根据批次中的处置依据从甲预留转回甲可用，不能当成一笔新入金。

因此甲从预留后的可用 4,975、预留 15,025 USDT，变为可用 4,985、预留 0 USDT，并拥有可用 0.25 BTC。
乙得到可用 6,000 USDT，S1 的 0.10 BTC 预留耗尽；丙得到可用 9,015 USDT，S2 仍保留 0.05 BTC 预留。
分录逐资产反映这些桶变化：USDT 总额仍为 20,000，BTC 总额仍为 0.30，不能把两种资产相加求“总额平衡”。

这些变化和进度在本地事务里一起提交，外部只会看到提交前或提交后的权威状态。
只给甲加 BTC 就确认完成，会把尚未扣除卖方预留的 BTC 同时算作两方资产，也无法解释 lastSeq=101 为何没有覆盖完整义务。
只做一侧然后靠后续消息补齐，已经改变了本题的共同事务前提，不能作为同一保证下的优化。

## 第 5 层：守恒之外还要证明预留确实属于这笔义务

**面试官：** 数量都平衡就够了吗？如果甲恰好还有另一笔 15,025 USDT 预留，消费者从那里扣，也能算出同样结果。

**面试者：** 守恒只是必要条件，不能证明授权和归属正确。
扣 R1 前必须确认它绑定甲、I1、B1、BTCUSDT、买入方向、USDT 及原始请求载荷，并检查当前剩余金额；卖方预留同样绑定 S1／乙和 S2／丙。
不能从“这个账户总预留足够”推导出可以随意消费任何订单的交易资格。

还要核验 T0、T1 的稳定 tradeId、数量、maker 价格、方向及批次中的订单和预留处置结果，确保金额计算一致、桶非负。
成交分录的唯一键沿用 `(effectNamespace, tradeId, legType, accountId, asset)`，legType 区分不同经济腿，而不是由重试次数生成。
10 USDT 返还绑定原批次的预留处置事件与稳定腿类型，不假造一笔新成交，也不能在每次回调时产生新的返还身份。

若预留不足、绑定错误或已有分录与整批状态不一致，应整体回滚并阻断核查，不能换另一份预留、临时放开负数或把批次标记完成。
本模型中全新 101 不应出现“部分分录已提交、整批 inbox 尚未提交”；出现意味着原子性或历史数据已经有问题。
分录唯一键用于拒绝重复和发现破坏，不是让消费者把冲突腿跳过后继续提交剩余部分的许可。

## 第 6 层：并发时唯一性靠谁最终裁决

**面试官：** 这些检查都通过了，但两个 Go 实例同时处理 101，各自都先查到 inbox 不存在。检查再插入还有竞争，怎样挡住？

**面试者：** 同流事务先锁同一个数据库进度行，使两个实例不能同时在 lastSeq=100 的基础上应用 101。
第一个事务提交后，第二个取得锁，再读原 inbox 和进度，核验相同内容后返回原结果；第一个回滚则第二个可以完整执行。
Go mutex 只能约束当前进程，消费组通常分配给一个实例也不是数据库层面的永久互斥证明。

数据库还必须有消费身份与分录身份的唯一约束作为最终防线，不能只依赖“业务代码先查过”。
inbox、分录和资产写入始终在同一事务内；若发生唯一冲突，按数据库语义回滚或回滚到受控保存点后重新核验，不能忽略错误继续提交资金。
尤其不能对 inbox 执行 `ON CONFLICT DO NOTHING` 后，不检查是否插入成功、也不比较原载荷，就继续或宣称成功。

若使用乐观进度更新，也必须将 `lastSeq=100` 的条件更新及受影响行数检查放在同一事务，失败则整批回滚重试。
不同隔离级别下要验证锁定读、唯一冲突和重试语义，不能从一次普通 SELECT 的结果推断未来不存在并发写入。
进度串行化提供正常执行路径，唯一约束封住重复身份；两者各自承担明确责任。

## 第 7 层：不同市场共享账户时仍在同一数据库争用

**面试官：** 同一流已经串行了，但两个市场都涉及甲，另一个事务先锁卖方再锁甲，会不会死锁？要不要把账户锁取消，换成异步合并？

**面试者：** 不同流没有全局总序，但共享资产仍由数据库事务共同保护，不能因为市场不同就忽略账户竞争。
我会约定全部相关写路径先锁各自必要的流进度，再按统一账户／资产／预留顺序锁定资金行；涉及多个流进度的操作也需明确统一顺序。
在获得全部必要锁之后才校验当前桶余额与预留状态，不能把锁外读到的余额当成最终可扣依据。

统一锁顺序可以降低死锁，但索引访问、其他事务路径等仍可能使数据库判定死锁，因此回滚并按原批次完整重试是正常恢复方式。
重试不能只补做“还没执行到的腿”，因为被选为死锁牺牲者的事务整体没有提交；也不能在重试时创建新 tradeId。
条件扣减、非负检查和唯一约束仍留在事务里，锁策略优化不能删掉经济不变量。

共享账户热点会带来等待，但异步合并余额会改变权威资金何时生效，不能继续承诺本题的共同事务语义。
这里允许不同市场分别推进自己的连续进度；若存在跨流经济依赖，需要显式依赖事实，而不是比较两个市场的 seq 大小。
锁和死锁重试解决本地竞争，下一步仍要面对事务提交请求本身的结果未知。

## 第 8 层：提交未知与提前 inbox ACK 怎样区分

**面试官：** 死锁通常能明确回滚，但 COMMIT 后连接断开可能不知道成败。此时怎么 ACK？如果先存 inbox 就 ACK，是否也满足你的保证？

**面试者：** 提交结果未知时不能认定失败，也不能先 ACK 为“已结转”。
我会在可确认权威状态的数据库连接上按原业务键查询，或重试原批次；原事务已提交就能核验 APPLIED，未提交则重新完整应用。
不能先退款、换批次号或只重做某个腿，因为原事务可能已经同时改变了所有资金和进度。

基线采用“应用事务提交后 ACK”。提前 ACK 是另一份契约：必须先将完整消息或可恢复组装依据存入持久 inbox，并把它标为 RECEIVED，而非 APPLIED。
后续应用仍需在一个事务内共同更新双方资产、预留、分录、inbox 的 APPLIED 状态和 lastSeq；仅存在一条接收记录不能触发“已处理”分支。
内存队列、异步但未落盘的写入，或与载荷不匹配的接收记录，都不足以接走消息系统的重投责任。

这时需要分别报告接收水位和应用水位，后台恢复器必须能重新扫描未应用记录；数据库保留、备份和灾难恢复也要覆盖已 ACK 的待办。
消息 offset 只能越过符合当前契约的连续运输前缀，不能因为较大 offset 已应用就跳过较小的未持久消息。
提前接收不放宽资金顺序，也不把 102 已持久接收解释成 lastSeq 已经可以变为 102。

## 第 9 层：消费组换名和历史重放不能重新定义效果

**面试官：** inbox 已经持久，应用也可恢复。升级时换一个 consumerGroup 从头读历史，是不是新组用新去重键，就能避免与老进程冲突？

**面试者：** 资金结转的 effectNamespace 不能随消费组、部署版本或进程名字变化。
consumerGroup 表示运输订阅和调度身份，epoch 表示所有权任期，effectNamespace 表示“这笔原事实产生的同一种业务效果”；换组或切主重放仍是相同资金结转。
若把消费组或任期当作效果命名空间，101 会被视为新效果，甲、乙、丙可能再次入账，持久 inbox 也就失去了跨运维动作的意义。

升级后应继续使用原 namespace 和稳定身份，核验原载荷并返回原结果；新的展示投影可以有自己的命名空间，但不得借此再次修改原权威资金。
真正需要纠正旧账时，应产生有原始引用、原因和审计身份的新纠正事实，而不是修改旧 101，或用“v2 消费组”重复结转。
去重明细、分录等效果证据、可靠来源与归档须遵守共同恢复保留契约，覆盖允许重投、补交付和重放的历史；旧备份中的余额、分录、inbox 与进度还必须来自同一一致检查点。

若已经覆盖的旧序号找不到原 inbox，需要恢复可信归档或等价证据后核验，不可以顺手把它当新批次执行。
仅恢复余额而没恢复去重，或只保留 lastSeq 却删除全部内容绑定，都会破坏本题的闭环。
持久唯一性不仅防住同时运行的两个实例，也必须跨重启、改名和恢复过程保持含义不变。

## 第 10 层：本地唯一效果不能顺便包住外部系统

**面试官：** 命名空间稳定后，我在同一个事务里调用外部支付或通知接口，再写 APPLIED，是否连外部副作用也能只发生一次？

**面试者：** 不能。本地数据库事务不控制外部接口的提交，外部成功后本地回滚，重试就可能再次支付；本地先提交，调用前崩溃又会漏调用。
把 HTTP 调用放在数据库事务中只会延长持锁，无法让远端跟着 ROLLBACK；连接超时也不能证明外部没有执行。
因此本题只承诺同一本地数据库内的资产、分录、inbox 与进度共同生效。

若确有外部交付需求，可以在本地事务共同登记稳定外部请求身份及待办，提交后交付，并使用对方承诺的幂等键、结果查询与核对协议。
对方不支持幂等或查询时，就必须承认未知执行结果的风险，设计隔离、人工确认等恢复边界，而不是把“不断重试”称为唯一支付。
跨账务分片同样改变共同事务前提，需要第 14 题的在途状态或协调协议，不能把两边各自成功拼成一个本地事务。

回到 B1，101 提交后甲可用 4,985 USDT、0.25 BTC，乙 6,000 USDT，丙 9,015 USDT 和 0.05 BTC 预留，这些是权威资金效果。
公共成交回报或私有查询可能尚未追上，它们有各自的交付与投影进度，不能反过来否认已经成立的资金提交。
完整回答应明确“哪些效果共同提交、哪些只是后续交付”，而不是用恰好一次的口号抹平系统边界。

## 本题收束

**讲透的机制：** 稳定效果身份与原内容绑定；同流数据库串行化及唯一约束；双方资产、合法预留、平衡分录、inbox、结转状态与 lastSeq 共同提交；提交未知查原结果；ACK 按已应用或已持久接收的明确契约执行。

**易错边界：**

- 同 batchId 不同载荷必须冲突，`seq <= lastSeq` 或唯一键已存在都不是无条件静默跳过的依据。
- inbox 的 RECEIVED 不等于 APPLIED；分录唯一冲突不能通过跳过部分腿来“完成”全新批次。
- effectNamespace 不随 consumerGroup 改名；本地事务不能覆盖外部支付、跨分片或所有查询副本。

**反例：** 两个实例同时读取到没有 101，先各自加余额，再各自写 Redis 去重；即使最后只有一个标记，资金也可能已增加两次。反过来，先提交去重再记账会在中间崩溃时永久漏账。只有把完整账务和持久处理证据放进同一个提交边界，重投才能核验原结果而不重做效果。
