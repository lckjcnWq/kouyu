# 大问题 3：没有全局事务，怎样保证预留、撮合、账务与资格关闭始终对得上？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 全局事务 / ACID | 跨步骤共同提交的能力，以及事务原子性、一致性、隔离性、持久性。 | 本文只有分域提交，不承诺预留、撮合和结转同时变化。 |
| 不变量 / 安全性 | 无论谁超时，都不能破坏的资金与资格规则。 | 允许成交已定账未结，禁止钱先退了原单还能花。 |
| I1 / R1 / 资格绑定 | 原意图、专用预留及它们与订单参数的关系。 | R1 只能支持绑定的账户、市场、方向和金额。 |
| Place / CommandLog | 下单命令与它进入的权威排序记录。 | 网络迟到的 Place 仍可能执行，查询空不是未来不会执行。 |
| CLOSE_REQUESTED | 账户已经提出关闭要求。 | 只是请求状态，不是撮合已经取消资格的证明。 |
| AbortIntent | 让撮合关闭原意图的有序业务命令。 | 与 Place 在同一市场顺序裁决，不由账户独立宣布关闭。 |
| 关闭墓碑 | 留下“这份资格不许再用”的持久记录。 | 即使下单从未到过，也能阻止关闭后的迟到首次执行。 |
| ResultBatch / AppliedSeq | 完整裁决及共同提交的执行进度。 | 关闭也要提交裁决，只有关闭命令已受理还不够。 |
| batchId / tradeId | 一批裁决与原成交的稳定身份。 | 重试、切主不能改号，已成 T0、T1 不因结转失败消失。 |
| contentHash / 原载荷 | 已绑定内容的摘要及完整经济参数。 | 提交未知查原结果，不能修改金额再称原批次重试。 |
| lastSeq / 连续结转 | 所有前序义务已完整应用的进度。 | 在 100 先收关闭 102，仍须补齐成交 101。 |
| 真实余量 / 价差返还 | 关闭时未成交部分，与原成交少花的额度。 | B1 全成只在 101 返 10，102 不能再退原预留。 |
| B2 独立变体 | 单独改变限价形成的部分成交案例。 | 预留 15,000、先花 6,000，关闭先赢才释放余下 9,000。 |
| APPLIED / ACK | 原账务效果已共同提交，以及消息确认。 | 提交未知不先确认；确认丢失重投不再改钱。 |
| 检查点 / 围栏 | 一致恢复起点，以及写入端拒绝旧执行者的机制。 | 恢复必须含意图和墓碑，不只恢复盘口；旧主不能另提相反裁决。 |
| 收敛 / 保留契约 | 未完成义务最终被推进，以及来源和效果证据保留的条件。 | 安全冻结不等于已经完成，仍要有可恢复来源和问题处理路径。 |

## 把整篇文章压缩成一个故事

甲的 15,025 USDT 已为 B1 预留，Place 却超时了。页面甚至权威查询此刻都没找到订单，客服想先退钱，工程师拦住：原命令可能还在路上，退完后迟到成交就会花掉已重新可用的资金。甲要放弃，应记录关闭请求，把 AbortIntent 送进同一市场命令流，而不是等一个本地计时器到点就解冻。

先看独立的关闭先赢分支：关闭占 101，持久墓碑挡住 102 的迟到 Place，没有前序义务后账户才可全退，后续重复请求不再退款。再回到正常分支：Place 在 101 已产生 T0、T1，合计付款 15,015，102 的关闭只能承认已经全成。账户必须先结转 101 并返还原价差 10，即便关闭回报先到，也不能先释放、更不能退回 15,025。

若要讨论部分成交，另用 B2：限价 60,000、预留 15,000，先成交 0.10 BTC 花 6,000；关闭排在后续成交之前，才释放剩余 9,000。切主或提交回包丢失时，都恢复原意图、墓碑、完整结果和连续账务证据，不能删成交重来。安全性守住的是任何排序都不双花；真正结束等待还需要来源保留、重试和阻断修复，不能用一句最终一致替代这些条件。

[返回专题总览](README.md)

**流程位置与核心机制：** 证明“预留 → Place → ResultBatch → 账务 → 关闭”的端到端安全性，重点追问超时、迟到命令、关闭竞争和释放依据。账户事务与撮合结果提交是不同原子边界，不能冒称跨域 ACID；闭环依赖不可复用的资格、同域裁决、不可抹去的义务和有序结转。

沿用总览的本地同库账务前提。正常案例是 `BTCUSDT:v1` 的 101 批次：B1 预留 15,025 USDT，T0 支出 6,000、T1 支出 9,015，价差返还 10。文中关闭先于 Place 和 B2 部分成交均是独立变体，不叠加到正常 B1。

## 第 1 层：没有全局事务时，一致性到底保证什么

**面试官：** 账户预留、撮合和账务分处不同提交边界，没有全局事务，你怎样保证交易一致性？

**面试者：** 我不会承诺所有模块在每个瞬间同时变更，而是定义不能被打破的不变量。每个可执行订单必须绑定足额合法预留；同一意图只能首次有效执行；已提交成交必须有完整可恢复结果；资金效果只能应用一次；释放不能越过先前成交或仍可执行的资格。允许成交已确定、账务暂未结转，禁止先退款后仍允许这笔成交花掉同一份钱。

执行链是账户先提交 I1、R1，再用原 I1 提交 Place。
撮合按命令流裁决，完整 ResultBatch 与 AppliedSeq 共同提交；之后消费者以完整连续批次驱动本地账户事务。
账务共同提交双方资产、预留、分录、去重与进度，关闭也必须提供同一裁决序列内的释放依据。

本例账户预留时甲可用 4,975 USDT，结果提交后形成 15,015 USDT 的付款义务。
账务完成后再得到甲可用 4,985 USDT、0.25 BTC；中间不能因为还没记账就说没有成交。
逐币种守恒和余额桶非负用于核验结果，但事后对账不能代替上述执行约束。

## 第 2 层：预留怎样成为不可被重复花费的资格

**面试官：** 你说每个可执行订单都绑定合法预留，撮合怎样知道 R1 不是过期的、假的，或被另一单用过的？

**面试者：** R1 必须来自账户权威域已经提交的资格记录，绑定 I1、订单身份、账户、市场、方向、资产、金额与载荷。可信提交路径传递可核验的原记录引用，撮合校验来源和绑定，不能相信客户端声称“我已冻结”。同一个 R1 只服务绑定的意图，重复 Place 命中原裁决，不能给另一订单重复提供购买力。

账户在事务中锁定甲的可用 USDT，检查并预留 15,025，再开放提交。
撮合仅在资格有效且业务条件通过时接纳 B1，卖单 S1、S2 也有已合法预留的 BTC。
执行价格不高于买限价，本例零手续费，因此这一预留足以覆盖两笔成交和后续确定返还。

资格一旦可能进入命令流，账户就不能按本地 TTL 自行取消。
远程查询一次 R1 有效、随后账户自行释放，仍然会留下查询与执行之间的竞争窗口。
本模型用关闭协议约束资格失效：账户可以记录关闭请求，但未取得撮合关闭证据前继续保留必要预留。

## 第 3 层：查询为空为什么不是释放证明

**面试官：** 那 R1 已提交，Place 超时，权威查询也暂时没找到 I1，为什么还不能直接退款？

**面试者：** 查询为空最多说明查询时刻没有可见的受理或裁决，不能证明原 Place 今后不会到达。命令可能仍在提交器、网络或日志提交过程中；即便此次查询线性一致，查询结束后迟到命令仍可能被接纳。直接释放会让甲重新花掉这 15,025 USDT，随后 B1 又成交，形成同一资产被承诺两次。

首先用原 I1 查受理和结果，必要时以相同载荷重试提交，不创建第二个预留。
如果用户要放弃，账户记录 CLOSE_REQUESTED 并发起 AbortIntent(I1)，但这个本地状态只表达请求，不表示资格已经关闭。
必须等撮合在同一排序域产生关闭裁决，才能证明迟到 Place 不会再取得执行资格。

若网络分区使关闭也无法确认，就保留预留、展示处理中并触发恢复任务。
这牺牲了该笔资金的暂时可用性，不是协议漏洞，而是没有关闭证据时必须选择的安全边界。
设定一个更长的超时或连续查询十次为空，都不能把“暂未看到”变成“未来不可能执行”。

## 第 4 层：让关闭和迟到 Place 竞争同一个裁决顺序

**面试官：** 你提出 AbortIntent，但它和迟到 Place 同时到达不同实例，谁来保证关闭真正赢或输？

**面试者：** 两者必须按同一市场 CommandLog 的已提交顺序，由有效单写者裁决；不能让账户服务与撮合服务分别决定。AbortIntent 带原 I1 和授权绑定，即使撮合还没见过 Place，也要能够为这个意图建立关闭墓碑。命令受理本身不是关闭完成，只有关闭裁决随结果批次提交后才是有效关闭证据。

如果 Place 排在前面，先接纳并处理它，再由 AbortIntent 撤销真实剩余量，保留已成义务。
如果 AbortIntent 排在前面，先提交 I1 的关闭墓碑，后来的 Place 校验意图状态时拒绝执行。
同一意图不允许通过换请求尝试、换网络连接或换提交实例绕过墓碑。

关闭结果要引用意图、预留、裁决位置、此前结果依赖和实际处置，账户校验后才使用。
关闭记录和意图状态必须能够从结果日志与一致检查点恢复；只在内存里标记关闭，重启就会复活迟到命令。
领导者切换还要有存储围栏，阻止旧写入者在新关闭之后提交另一套合法结果。

## 第 5 层：关闭先发生也必须填满每个命令位置

**面试官：** 你说关闭先发生就能挡住迟到 Place；若关闭在 101，Place 在 102，重复 Place 又在 103，下游要等哪些结果？

**面试者：** 这是与正常 B1 不同的独立时序：101 是关闭裁决，因此不产生正常案例的 T0、T1。101 的完整 ResultBatch 记录 I1 关闭、R1 的可退依据和墓碑；102 的迟到 Place 得到已关闭拒绝；103 的重复请求得到同一意图已关闭或重复裁决。每个位置都有自己的完整批次，即使新增成交数为零。

账户从 lastSeq=100 处理 101，核验关闭已禁止未来执行且没有前序成交义务，才能释放 R1 的 15,025 USDT。
再处理 102、103 时，只核验各自结果并推进进度，不再次释放。
关闭效果也有稳定身份和去重记录，不能因为同一请求又来一次就重复返资。

不能为了节省消息省掉无成交批次，也不能把 102 的拒绝当作还可以重做的临时状态。
空／重复结果仍包含原意图、裁决类型、原结果引用及完整性证据，说明位置确已处理。
这样后续位置才能证明连续，而不是靠“应该没有交易”跳过无法解释的缺口。

## 第 6 层：Place 先发生，关闭只能处理尚未形成的义务

**面试官：** 刚才是关闭先赢；回到正常案例，如果 Place 在 101 先成交，AbortIntent 在 102，还能退多少？

**面试者：** 正常 B1 在 101 已全成，两笔成交义务合计 15,015 USDT 不可撤销；101 的确定处置返还价差 10 USDT。102 看到的是已全成订单，没有可撤剩余量，不能再释放 15,025，也不能再次返还那 10。关闭的是未来执行资格，不是把已经提交的成交从历史抹掉。

账户必须先应用 101，扣付 T0、T1 并返还 10，再处理 102 的无新增退款结论。
即使撮合发出关闭回报时账务还在 100，也不能把账户表里仍显示的全部预留都当成可退。
这部分预留正承担着已经确定但尚未结转的付款义务。

部分成交使用总览的独立 B2 变体：限价 60,000、数量 0.25、预留 15,000 USDT。
先成交 0.10 BTC，支付 6,000，剩余预留 9,000；若关闭先于后续匹配，才撤余量并释放这 9,000。
若另一笔成交按序排在关闭之前，就先结转那笔成交，只释放关闭时实际剩余，不能按发出撤单请求时的旧余量退款。

## 第 7 层：关闭结果先到达，不代表可以先释放

**面试官：** 正常案例中 102 的关闭结果先送到，101 还卡在分发器；账户不是已经知道订单全成了吗，能先退 10 吗？

**面试者：** 基线采用完整批次、连续前缀的资金应用，不能拆出 10 单独越过 101。账户 lastSeq=100 时只能把 102 可靠暂存或要求重投，并补取 101。关闭回报告诉我们未来不再执行，但没有替代前序成交的完整内容、分录和资产校验；这里 10 的返还处置本来就属于 101，不能从 102 的描述重新制造一次退款。

```text
账户 lastSeq=100，先收到关闭批次 102
    → 保留 R1，不作资金应用，补齐 101
    → 同事务结转 T0、T1 与价差返还，lastSeq=101
    → 核验并应用 102 的关闭结论，lastSeq=102
```

处理 101 时一次事务扣双方预留、记双方收入、返价差、写平衡分录和去重进度。
任何一腿校验失败都回滚，不能先把买方 BTC 入账或先返价差，再把其余部分留给下一次。
如果 101 有毒或丢失，就阻断并恢复来源；进入死信只保留错误材料，不构成跳到 102 的资金证明。

## 第 8 层：账务提交未知时，已成义务仍然不能删除

**面试官：** 101 终于补到了，但账户提交超时，撮合和客户端都在催；能撤销成交后重来，让状态重新一致吗？

**面试者：** 不能。结果批次提交已经确定乙、丙应收到 USDT，甲应收到 BTC，账务超时只让履行状态未知。先按原 batchId 和资金效果命名空间查权威事务结果；若提交成功，返回原 APPLIED；若确定未提交，重试同一完整批次；若仍未知，继续核验，不先退款、ACK 或创建新 tradeId。

本地事务把资产、分录、去重与 lastSeq 一起提交。
因此正常恢复只会看到全部未应用，或者全部应用；读到单边分录却没有整批完成证据，是要阻断调查的异常，不是“补另一边就好”。
ACK 丢失则允许重投，原 contentHash 匹配后返回原结果，不再次改余额。

已经形成的义务不能因消费者故障删除、改价或重新撮合。
若业务事实确需纠正，必须另走授权、带原引用、可审计的新纠正事实，并验证相应资产条件。
“补偿”不是假定所有参与方都还没动过资金，更不是把数据库历史行删掉就当从未成交。

## 第 9 层：任一提交点崩溃，恢复仍必须保留资格与义务

**面试官：** 你依赖这些持久证据；如果恰好在关闭和结果提交之间切主，怎样保证旧 Place 不复活？

**面试者：** 接管者先恢复一致检查点，再应用已提交结果到同一 AppliedSeq，恢复订单、意图首次裁决、关闭墓碑和预留处置依据，确认旧写入者已被围栏后才能接管。不能只恢复盘口，不恢复关闭状态。流仍叫 BTCUSDT:v1，任期变化只用于写权限，不改变 batchId 或 tradeId。

预留提交后、命令提交前崩溃，由账户待处理意图恢复扫描继续提交或关闭。
命令已受理、结果未提交时，从已提交撮合状态处理原命令；结果已提交、响应丢失时，读取原结果，不重新执行。
关闭命令只有受理记录而没有裁决提交时，账户仍保留预留，接管者继续完成原关闭。

若关闭裁决已提交但账户未应用，补交付同一个关闭结果，并补齐它之前的全部资金依赖。
账户提交后崩溃则由去重与进度证明原释放已经完成，重投不再释放。
若存储暂时无法确认原写是否提交，就暂停相关流的推进，不能让新主用“没看见”制造另一个相反裁决。

## 第 10 层：给出安全性证明与收敛条件

**面试官：** 你列了恢复步骤；怎样证明不是遗漏某个时序后才出错，又怎样区分安全和一直冻结？

**面试者：** 我会沿提交前缀做归纳。初始时 R1 已合法预留且未被其他意图占用；每个命令位置只允许在“首次有效 Place”“关闭”“重复或拒绝”之间按当前持久状态裁决。Place 消耗的是已有资格，关闭禁止未来首次执行，重复不产生新成交。ResultBatch 与 AppliedSeq 共同提交，保证每次状态推进都有完整可恢复的义务或无新增义务证明。

再沿账户 lastSeq 归纳：从 100 开始，只应用完整的下一个批次。
每步共同提交平衡资产变化、预留处置、分录、去重和进度，所以重投不重账、释放不越过前序付款。
关闭先发生则未来无成交；Place 先发生则既有义务保留、只退实际余量，两种排序都不会释放仍可能被消费的资产。

这是安全性，不自动意味着有限时间内完成。
还需要命令和结果源可恢复且保留充分、有效写入者最终可用、分发与消费者持续重试、缺口和毒消息被解决。
运行上应按 I1、R1、裁决位置和账户水位追踪滞留，恢复原流程；没有证据时保持冻结并升级处理，不能用自动退款换取表面完成率。

## 本题收束

**机制：** 预留提供资金资格，Place 与 AbortIntent 同域排序，结果共同提交形成不可丢义务，账户按完整连续批次共同结转与释放。关闭只禁止未来执行或撤真实余量，不取消已成交易。

**易错边界：** 查询为空、超时、关闭命令受理、页面已撤单，都不单独构成退款依据。关闭墓碑必须可恢复；重复命令的新位置必须有空／重复结果；不能独立更新 AppliedSeq，也不能把已成义务删掉重来。

**反例验证：** 分别推演“关闭 101、迟到 Place 102”和“成交 101、关闭 102，但交付顺序相反”。前者允许在关闭应用后全退且拒绝迟到执行；后者必须先履行 15,015 USDT 与 0.25 BTC，再仅返原 10 USDT。两种分支都加一次提交响应丢失，身份、义务和最终资金效果应保持不变。
