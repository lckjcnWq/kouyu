# 大问题 4：怎样确保成交一旦确定，永远有完整、稳定且可恢复的结果可以交付？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| CommandLog / 可靠受理 | 留下可以恢复处理的原命令记录。 | 101 进日志不表示已经确定 T0、T1，更不表示到账。 |
| 候选结果 / 已提交事实 | 内存试算与已经越过可靠提交边界的业务义务。 | 候选可以丢弃恢复，已提交成交不能重撮合。 |
| ResultBatch | 某次裁决的完整业务封套。 | 不仅两笔成交，还含 B1、S1、S2 状态和预留处置。 |
| AppliedSeq / 期望前缀 | 已共同提交的结果进度，以及本次写入所要求的前驱。 | 从 100 原子推进到 101，不能单独先改进度。 |
| streamId / commandSeq / batchId | 持久流、流内命令位置及其组合身份。 | 原批次是 BTCUSDT:v1 的 101，切主重发不改号。 |
| tradeId / matchIndex | 原成交身份与批内成交序号。 | T0、T1 由 101 的 0、1 定位，价差返还不是第三笔成交。 |
| eventId / 完整清单 | 稳定事件身份，以及这批应有内容的集合。 | 两份 T0 不能冒充 T0 与 T1 齐全。 |
| eventCount / contentHash | 按协议统计的事件数，以及整体经济内容摘要。 | 只数数量不够，还要核对成员、内容与来源。 |
| schemaVersion / ruleVersion | 数据编码版本与原裁决规则版本。 | 历史沿用原解释，不按重发当天规则重新定价。 |
| 最小单位整数 | 把资金数量变成精确的整数单位。 | 可读的 6,000、9,015 USDT 入存储前按固定精度编码。 |
| 原子提交单元 / 提交标记 | 存储能整体确认的内容，以及区分已提交记录的依据。 | 普通文件两写、单次 append 或写到部分字节都不天然满足。 |
| 围栏 / 持久化承诺 | 写入端挡旧写者，以及哪些故障后仍保留事实的保证。 | 永久主机故障要相应副本能力，不靠函数名承诺永不丢。 |
| 提交未知 | 调用方不知道原操作是否已可靠成立。 | 先停推进查原批次，查空不证明在途原写不会再提交。 |
| 检查点 / 已提交前缀 | 某个一致恢复起点，以及后续可确认成立的连续结果。 | 恢复订单、意图与关闭记录，不以半安装内存继续撮合。 |
| 拆片 / 持久组装 | 大封套拆成运输片段，收齐后还原整批。 | 校验清单和总摘要后才可记账，不能先结 T0。 |
| 发布进度 / 来源保留 | 发送已走到哪里，以及原结果还能从哪里恢复。 | 发布确认不代表资金结转，不自动授权删掉最后来源。 |

## 把整篇文章压缩成一个故事

撮合进程为甲的 B1 算出两笔成交：0.10 BTC 花 6,000 USDT，0.15 BTC 花 9,015。它还知道甲全成、乙的 S1 用尽、丙的 S2 剩 0.05 BTC，以及甲有 10 USDT 价差可返。工程师没有立即发成交回报，因为这些仍是内存候选；必须把完整 101 与执行进度从 100 到 101 的变化共同提交，才能形成下游必须履行的义务。

存储刚提交，进程尚未安装新内存就崩溃。接管者从一致检查点恢复订单、意图裁决和关闭记录，再应用已提交的原 101，不按新盘口重撮合，也不重造 T0、T1。若原调用只是超时，就先查原身份与内容，暂停相关推进；既不能直接假定失败，也不能拿未决内存结果发给账户，否则持久事实与外部付款会分叉。

分发器只读取已提交来源，消息太大可以拆片，但账户要核对全部清单与摘要后才结转。两份 T0、一个结束标记都不能补上缺失 T1；重复意图排进 102 时也要有零新增成交的完整结果。发布确认丢了就重发原批次，归档仍保留原身份和版本；“可靠”是故障与保留契约内有恢复路径，不是宣称磁盘、消息和账户从此没有不同进度。

**流程位置与核心机制：** 从撮合裁决进入可靠事实源，追到结果完整性、ResultBatch 与 AppliedSeq 共同提交、未知提交、内存恢复及可恢复发布。本题只证明事实可靠成立与可交付，不把发布确认当作账户完成，也不另造总览之外的 MVP。

沿用可恢复结果日志作为撮合事实源，不改成逐订单关系库事务撮合。`BTCUSDT:v1` 的命令 101 产生 T0、T1，账户消费者初始 lastSeq=100；结果中的订单、成交和预留处置必须共同解释总览的 15,015 USDT 实际支出与 10 USDT 价差返还。

## 第 1 层：可靠受理为什么还不等于可靠成交

**面试官：** 命令已经写进日志了，为什么还需要一个可靠结果源？成交在内存里算完就发消息不行吗？

**面试者：** CommandLog 只能证明命令已受理，不能单独证明它产生了哪些成交和处置。Place 可能接纳、拒绝、无成交或形成多笔成交，结果依赖当时的订单簿状态与规则版本。内存计算后立即发消息，会在发布与持久化之间留下缺口：下游可能已经入账，而重启后找不到对应成交事实，或者还原出另一套结果。

本模型把内存裁决当作候选结果，可靠边界是完整 ResultBatch 与 AppliedSeq 共同提交。
对 101，提交内容明确包含 T0、T1、B1 全成、S1 全成、S2 剩余 0.05 BTC，以及价差返还依据。
提交前不对外发布成交成功，提交后无论消息是否发出，这两笔义务都已经成立。

可靠受理后的命令可以等待恢复处理，但已可靠成交的结果不能重新撮合。
消费者处理失败也不改变这个事实，只改变账务履行进度。
所以我会分别定义命令提交点、结果提交点和资金提交点，不用一个“写了日志”掩盖三种不同承诺。

如果选用其他模型，可以用确定性命令日志和完整规则状态重建结果，但必须证明相同保证。
这里既然选择持久结果日志，就不能在故障时悄悄退回只靠未提交内存和当前规则重新计算。

## 第 2 层：一个批次要包含哪些不可拆开的业务结果

**面试官：** 你要求完整 ResultBatch；假如只保存两个 tradeId 和成交数量，是否已经足以补消息？

**面试者：** 不足以。批次必须能解释这次裁决的全部业务变化，而不只是列两个标识。头部包含 streamId、commandSeq、schemaVersion、ruleVersion、contentHash 和完整性清单；业务内容包含意图及命令引用、成交价格数量、买卖双方订单和预留引用、订单变化以及资金处置依据。还要保存或可确定恢复意图首次裁决、关闭状态等撮合状态变化。

T0 的 tradeId 是 `(BTCUSDT:v1, 101, 0)`，金额 6,000 USDT、数量 0.10 BTC。
T1 是 `(BTCUSDT:v1, 101, 1)`，金额 9,015 USDT、数量 0.15 BTC。
两笔成交分别引用对应卖方预留，B1 的 10 USDT 返还引用原订单和 R1 的确定处置，不虚构第三笔成交。

完整清单要表达所有事件及稳定批次内 eventId，编码规则固定，哈希覆盖明确的完整业务载荷。
接收方校验清单成员、数量、唯一性和总哈希；只有 eventCount=2 不能识别“T0 发了两次、T1 漏了”。
资金金额按最小单位整数编码，不能回放时从浮点数重新推导一个近似金额。

规则版本用于解释和恢复，不能在重发时按新规则重算价格。
如果结果不足以恢复订单余量或解释释放依据，它就不够完整，哪怕已经能够拼出一条公共成交行情。

## 第 3 层：ResultBatch 与 AppliedSeq 怎样真正共同提交

**面试官：** 内容完整了，但我先写 ResultBatch，再把 AppliedSeq 改成 101；两次都成功不就可以了吗？

**面试者：** 不可以把正常路径两次成功当成原子性。若结果已写、进度未改就崩溃，恢复可能再次执行 101；若先改进度、结果没写完，恢复会跳过无法交付的成交。无论调换顺序还是加重试，都没有消除中间状态。本模型要求存储原生提供共同提交能力，对外只可见“仍在 100”或“完整 101 与新 AppliedSeq 一起成立”。

一种满足契约的结果日志设计，是在一个原子提交单元内记录期望前缀 100、完整批次和新前缀 101。
提交时同时校验有效写入者围栏、位置唯一性和前驱位置，只有存储确认整个单元可靠提交才暴露新前缀。
AppliedSeq 可以由已提交结果前缀推导或随单元共同记录，但不能另有一次独立写决定它的权威值。

磁盘上写入部分字节不等于提交，单条 append 调用返回也未必满足所承诺的持久性。
要由真实存储定义记录完整性、提交标记、持久化与复制确认边界，恢复只采纳已提交前缀。
如果需要在主机永久损坏后保住已确认事实，提交契约还必须包含相应故障模型下的副本持久性，不能只靠单机内存确认。

本题依赖这个存储能力，不声称普通文件两写或两个数据库操作已经实现它。
若现有组件无法给出共同提交，就应改变实现方案并重新证明边界，不能在描述中把缺失能力包装成一个函数名。

## 第 4 层：共同提交超时，不能凭感觉判定成功或失败

**面试官：** 你已经要求原子提交；但存储响应超时，撮合也不知道 101 成没成功，下一步怎么做？

**面试者：** 原子性只保证提交状态没有一半，不保证调用方一定收到结果。提交超时后暂停相关状态推进，按原 batchId 查询权威已提交前缀和内容。若完整 101 已提交且哈希匹配，就承认原结果并继续安装状态和交付；如果明确未提交且原尝试已经被裁定结束，才从已提交前缀恢复处理。不能因为一次读取没看到，就假定原写以后不可能提交。

结果未知时，重试也必须用原提交身份和期望前缀，由存储保证同位置不能提交两份不同结果。
若原写仍在执行，先等待其权威结论，或由存储的幂等提交和围栏协议消除并发歧义。
发现同一 batchId 对应不同 contentHash，必须阻断核查，不选择较新的覆盖较旧的。

最危险的错误是把内存 T0、T1 先发出去，同时把超时当失败重做 101。
另一个错误是超时后直接推进到 102，让未决的 101 状态成为后续撮合基础。
两个错误都会让外部义务和持久前缀分叉，后续去重不能弥补源头分歧。

因此超时不是回滚证明，也不是发布许可。
恢复过程中宁可停住该流等待可靠结论，也不能凭接口错误码发明第二套权威成交。

## 第 5 层：内存订单簿怎样跟随提交与恢复

**面试官：** 查明 101 已提交了，但进程恰好在更新内存前崩溃；恢复时会不会漏掉这两笔成交？

**面试者：** 内存不是独立真相源。恢复先找与某个已提交 AppliedSeq 一致的检查点，恢复盘口、订单、意图裁决与关闭墓碑，再按顺序应用检查点之后已经提交的 ResultBatch。101 已提交就应用原订单变化和原 T0、T1 引用，不重新撮合、不生成新 tradeId，然后才接着处理尚未出结果的命令。

运行中也应区分候选状态与已提交状态。
可以在私有工作副本上计算 101，提交成功后安装对应状态；或者在独占状态上试算，但失败时必须丢弃或可靠撤回，不能让未提交修改参与下一条命令。
对外读取、成交回报和分发只能引用已提交视图，不能读取试算中的盘口就宣布成交。

如果 101 未提交就崩溃，丢弃候选结果，从已提交状态处理原命令，使用原位置与规则版本确定身份。
如果 101 已提交而内存只安装一部分，直接重建到一致前缀，不把半安装内存当作新的起点。
快照不能标记 AppliedSeq=101 却仍保存 100 的订单和去重状态，否则恢复会永久漏掉或重复执行。

恢复后也不重新用随机数生成成交 ID。
历史结果用原 ID，未提交命令使用原 streamId、commandSeq 和确定 matchIndex；切主任期不能掺进身份制造“另一笔同样成交”。

## 第 6 层：重复、拒绝和无成交也必须有完整位置证明

**面试官：** 恢复状态时你还需要意图裁决；如果同一个 I1 又进入 102，但没有新成交，能不写结果吗？

**面试者：** 不能。CommandLog 的位置和业务意图不是一一对应，同一 I1 可以因传输重试进入 102。撮合查到 I1 已在 101 裁决，就不再次入簿或撮合，但仍提交 ResultBatch(102) 与 AppliedSeq=102，记录重复结论、原位置引用以及零新增成交。这个结果证明 102 已处理，不是 102 的成交消息丢了。

拒绝、关闭和正常无成交也遵守同一规则。
一个有效 GTC 订单没有立即成交，仍可能发生订单入簿和资格状态变化，所以“无成交”更不等于“没有结果”。
完整批次中可以没有成交事件，但必须有足以解释裁决和恢复状态的内容。

对于 102 的重复结果，可以提供查询原 101 的引用，不能把 T0、T1 当作 102 新成交再次对外发布。
同一 101 批次的网络重投，则保留原 batchId 与原内容；不能为了统一处理把每次投递都分配新 commandSeq。
重放更新的是派生状态或交付进度，不创造新的业务位置。

账户消费者因此可以从 101 连续走到 102，即使 102 的资金变化为零。
若省掉结果，后续 103 到达时只能看到一个无法证明安全的缺口，不能靠猜测推进资金进度。

## 第 7 层：分发器只能发布已提交事实与完整批次

**面试官：** 你把每个位置都保存了；分发器是否可以提前从撮合内存拿结果，等提交成功再补一个确认？

**面试者：** 不可以，因为消费者可能在补确认之前就产生不可忽略的资金或展示效果。分发器必须从受已提交前缀约束的结果源读取完整批次；如果为了低延迟使用通知，通知只能提醒“去读取这个已提交位置”，不能让未提交内存载荷成为事实。结果提交失败时，也不能指望一条撤回消息追回已经发生的外部效果。

发送时沿用固定 batchId、contentHash、schemaVersion 和原事件身份。
发送超时或发布确认丢失就重发原内容；只有收到符合消息存储承诺的确认后，才能推进相应发布进度。
进度落盘失败会造成重发，这是可接受的；提前推进导致永不补发则不可接受。

若批次太大必须拆片，拆片只是传输行为。
每片携带原批次、片序号和完整清单引用，接收方先持久组装并核对成员、总量与总哈希，再进入完整批次处理。
收到 T0 就先给甲记 0.10 BTC，等 T1 到了再说，不符合本地整批账务基线。

发布确认只证明消息系统在其契约内接管消息，不能据此删除账户尚可能需要的原结果。
私有回报可以声明“成交已确定”，但“账户已结转”必须另有账户事务的证据。

## 第 8 层：来源保留与核验怎样支持真正可恢复

**面试官：** 你不让发布确认决定删除；那结果保存到什么时候，怎样证明恢复不会读到被修改的历史？

**面试者：** 先明确故障和恢复承诺，而不是承诺物理意义上的永远不丢。只要已提交义务尚未履行，或仍在契约允许的补交付、重放、备份恢复窗口内，就必须有可访问的完整原结果。清理热日志前要结合各必要消费者的连续水位、归档验证、检查点和最大恢复跨度，确认移走的是已被可靠保留的事实，而不是最后一份来源。

归档仍保留原 batchId、tradeId、版本、规范化内容和校验信息，补交付不得重新分配身份。
源端把已提交结果视为不可变，读取时核验记录完整性及提交前缀；下游与其已保存的哈希比较，以发现同身份异内容。
哈希不是授权或最终真相，攻击者能重算哈希时仍要依赖可信来源、写权限和提交历史，不能只校验消息自带摘要。

若发现中间记录损坏或缺失，就停止推进受影响范围，向经过验证的副本或归档恢复原内容。
不能把 AppliedSeq 手工跳到下一条，也不能重新撮合补出“差不多”的成交。
恢复只认完整已提交前缀；截断可以针对未提交尾部，不能为启动成功截断已经对外确认的成交义务。

最后用提交点前后、内存安装前后和发布前后的故障窗口做手工推演。
每种窗口都应能回答原结果在哪里、状态恢复到哪、哪些消息允许重发，以及为什么 T0、T1 的身份与金额不会改变。

## 本题收束

**机制：** 结果批次是完整业务裁决，不只是成交列表；ResultBatch 与 AppliedSeq 必须在真实可靠存储中共同提交。内存状态、恢复与发布都跟随已提交前缀，历史交付始终沿用原身份和版本。

**易错边界：** 两次写入不等于共同提交；提交超时不等于未提交；无成交不等于无结果；任期变化不等于新业务命名空间。未提交内存不可外发，已提交义务不可因交付失败删除。

**反例验证：** 在 101 共同提交后、安装内存前崩溃，恢复原 T0、T1，再在发布成功但进度未落盘时崩溃。正确恢复只能重建原状态并重发同一批次；若 tradeId 变化、缺 T1、AppliedSeq 单独领先，或未提交候选结果已经被消费，就没有建立可靠事实源。
