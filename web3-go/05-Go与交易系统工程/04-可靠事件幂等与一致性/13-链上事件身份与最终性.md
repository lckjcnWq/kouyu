## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EVM / USDC 最小单位 | 以太坊虚拟机生态与该代币的整数计量单位。 | 本独立充值例精度为 6，10 USDC 是 10,000,000 个单位。 |
| 合约 C / Deposit | 已审核的充值协议及其充值事件。 | 只信允许的合约版本、资产和语义，不因事件同名就入账。 |
| beneficiary / token / amount | 受益人、代币与金额字段。 | 与原充值身份持久绑定，变受益人或金额必须冲突。 |
| OBSERVED / CANONICAL_PENDING / CREDITED | 见过证据、规范链待确认、业务已入账。 | 待确认能展示，不能先变成可下单或提现的余额。 |
| evidenceId | 定位某个具体区块里某条日志的完整证据键。 | 使用 chainId、blockHash、txHash、logIndex，重到核对原内容。 |
| blockHash / 高度 | 区块身份与区块所在层数。 | 同高度重组后可能换区块，不能只按高度去重。 |
| txHash / logIndex | 交易身份与区块内日志位置。 | 一笔交易可有多日志，重打包后日志位置也可能改变。 |
| depositId / logicalDepositId | 协议提供的充值编号及其经济身份。 | 经济键为 chainId、C、depositId，D1 换区块不产生第二次入账。 |
| topics / data / 执行结果 | 日志签名索引、事件数据与交易是否真正成功。 | 还须核验来源、合约和资产，消息摘要不能替代这些检查。 |
| reorg / canonical / removed | 链重组、当前规范链及节点报告的撤销标记。 | removed 只触发核验，不单独证明完整重组顺序。 |
| 链视图代次 / revisionSeq | 当前认可哪版规范链，以及规范性修订的连续位置。 | 先撤销后迟到观察不能复活旧证据，旧写者也须被限制。 |
| 修订身份 / 撤销墓碑 | 一次状态修订的身份与保留的失效依据。 | 同证据可有多次修订，不能把它们一律当重复丢掉。 |
| finalized / N 次确认 | 协议最终状态标记与按块数等待的风险政策。 | 依具体网络验证，确认数不是绝不重组的数学保证。 |
| 完整采集前缀 | 当前规范链从起点到此都已可靠扫描。 | 105 已见、103 未采完，不能因门槛到 110 就越过 102。 |
| CreditDecision / 政策版本 | 已提交的业务入账决定及其风险规则依据。 | 与重组修订在同一权威状态机裁决，绑定支持证据可靠交付。 |
| Outbox / 版本校验 | 同事务保存决定待办，并检查当前链代次未改变。 | 防检查后重组却仍按旧条件提交，未提交结论不能外发。 |
| 充值效果命名空间 / ACK | 固定经济去重范围与应用后的确认。 | 同一 D1 只提交一份余额、平衡分录、去重和进度。 |
| 深重组 / 最终性违约 | 超出已接受稳定政策的异常。 | 已花资产不能删账恢复，需冻结风险、核对缺口和授权处置。 |

## 把整篇文章压缩成一个故事

甲通过审核过的合约 C 充值 10 USDC，协议给这笔意图 D1，金额精确记为 10,000,000 个最小单位。索引器先保存区块 A 中的完整证据身份，页面显示待确认，不增加可花余额。随后重组，D1 在区块 B 重现，日志位置也变了：这是两份不同观察，但仍是一笔经济充值，不能因为证据键新了就再次放款。

索引器按规范链修订顺序撤销 A、验证 B，保留失效记录，防止迟到的旧观察复活。B 的稳定性重新计算；即便见到高度 105、门槛已到 110，只要 103 尚未完整采集，前缀仍止于 102。满足同一有效链上的稳定政策和完整采集后，再与重组裁决串行提交原 D1 的入账决定与交付来源，账户按经济身份共同记余额、分录、去重和进度，确认丢失也不再加钱。

这些保证依赖合约确实提供可验证的稳定 depositId，普通转账不能照抄；确认数也不能泛化成所有链的绝对最终性。若政策已经接受、甲也花了币，后来发生深重组，就进入事故冻结和资产负债核对，不能删原分录、随意扣成负数或撤销无辜对手方成交。待确认投影可修订与已承担资金义务是两条边界，也不能把链下 B1 说成普通重组可回滚的观察。

[返回专题总览](README.md)

**流程位置与核心机制：** 讨论链观察进入业务系统时的证据身份、经济身份、规范性修订、最终门槛与唯一入账。本题只定义链索引器交付给业务消费者的契约，不展开完整节点同步或链共识协议。

**独立变体：** 总览仍是链下托管 BTC/USDT 交易，不将 B1 的成交改成可以重组的事实。本题另设 EVM 充值场景：已审核的充值合约 C 发出 `Deposit(depositId, beneficiary, token, amount)`，甲充值 10 USDC；代币精度为 6，金额按 10,000,000 个最小单位核验。

**身份前提：** 合约协议提供可验证、与区块无关的 depositId，同一业务充值意图重复执行仍使用原 ID，并约束其唯一消费；系统绑定受益人、资产与金额。若实际接入的是不提供这种身份的普通转账，必须重新设计可验证的经济身份，不能直接套用本例的保证。

```text
链日志 → 验证来源与内容 → 记录具体区块中的观察证据
    ↓
规范性校验／重组修订 → 更新待确认投影，不增加可花余额
    ↓
有效最终门槛 ∩ 当前规范链的完整采集前缀
    ↓
提交稳定经济身份的入账决定 → 可靠交付
    ↓
账户事务：唯一效果、平衡分录、进度共同提交
    ↓
若已接受最终性之后仍发生深重组 → 冻结风险并进入事故处置
```

## 第 1 层：为什么链日志不能直接当成最终入账事实

**面试官：** 消费到一条充值日志，按日志 ID 去重后增加用户余额，不就已经解决重复充值了吗？

**面试者：** 只解决“同一观察重复到达”还不够，因为链上的观察可能暂时属于规范链，之后因重组离开规范链。
在这个独立充值模型中，索引器先记录证据，再维护当前规范性和最终性；业务层只对满足入账政策的充值形成可花资产。
订阅连接收到日志、RPC 返回成功和消息已持久化，都不代表这条充值已经满足资金入账条件。

我会把 `OBSERVED`、`CANONICAL_PENDING` 与业务 `CREDITED` 分开建模。
待确认页面可以展示甲充值 10 USDC，但不把它放进可用于下单或提现的余额；离开规范链时修订待确认状态，并保留旧观察供审计。
即使全部日志只交付一次，这个规范性问题也仍然存在，不能由消息系统的投递语义替代。

这与总览中已提交的链下成交不同：T0、T1 一旦可靠确定，就有不可因交付失败删除的清算义务。
不能因为本题支持撤销链观察，就把撮合结果也设计成消费者随意回滚的临时消息。
两种事实来源必须在进入业务时分别确定可靠边界。

## 第 2 层：具体区块里的日志怎样取得稳定证据身份

**面试官：** 既然先保存观察，同一交易被多个节点重复返回，或者重组后又进入另一个区块，你用什么键区分这些证据？

**面试者：** 我采用完整链证据身份 `evidenceId=(chainId, blockHash, txHash, logIndex)`。
它标识某条链上、某个具体区块中、某笔交易的具体日志；同一证据重复到达时，应核对规范化内容后复用原记录。
同键却出现不同合约地址、topics 或 data，属于来源冲突或解析错误，必须阻断核查，不能最后写入者覆盖。

高度不是区块身份，重组后同一高度可能对应不同哈希；`txHash` 也不能区分一笔交易发出的多条日志。
EVM 的 logIndex 通常是区块内日志位置，交易重新打包后它也可能改变，所以不能假设去掉 blockHash 后的组合就是稳定经济身份。
旧证据与新证据可以同时保留，分别标记它们所属于的规范链版本与当前状态。

证据还要核验 chainId、目标合约及其允许版本、事件签名、交易执行结果和支持资产，不是看到相同事件名就信任。
金额与受益人依据经审核的合约语义校验，不能允许任意合约发一条同名日志给用户造余额。
这里的唯一键证明“这条观察是否重复”，尚未证明“这个用户应该新增几次资产”。

## 第 3 层：区块身份变化不能制造第二次经济入账

**面试官：** 你保存了两个不同区块中的证据。如果它们都代表甲的同一次充值，消费者按 evidenceId 去重，不就仍然会入账两次吗？

**面试者：** 所以账户效果还需要独立的 `logicalDepositId=(chainId, C, depositId)`。
本例的 depositId 来自约定的充值业务协议，不由索引器按区块哈希重新生成；同一充值在新区块重现，只增加或替换它的支持证据。
账户去重绑定这个经济身份，而不是新区块的 evidenceId、消息尝试 ID 或索引器重启后的消费组名。

首次接受逻辑充值时，系统持久绑定受益人、资产、最小单位金额和协议版本，并记录当前支持证据。
新区块证据若仍是 D1、甲、10 USDC，就按原经济身份核验；若 D1 对应的受益人或金额改变，必须进入冲突处理，不能覆盖原绑定后再次入账。
不同合法 depositId 则可以是两笔真实充值，不能因为金额相同就错误合并。

这个保证依赖协议本身提供可核验的稳定身份，不能靠数据库事后猜测用户意图。
对于普通 ERC-20 Transfer 等没有本例 depositId 的来源，需要另定能区分多次合法转入、又能识别重现的业务规则和验证条件。
如果无法建立这种关系，就应明确能力边界，而不是宣称一个日志键已经实现经济上的恰好一次。

## 第 4 层：撤销、重现与迟到观察怎样按顺序修订

**面试官：** D1 已经绑定成功，但旧区块的撤销通知先到，旧观察后到，新区块的观察又夹在中间，怎样避免把失效证据重新激活？

**面试者：** 我不会按消息到达时间维护一个简单的“最后状态”。
索引器由受控的规范链状态机裁决，持久化当前链视图代次，并输出有连续 `revisionSeq` 的修订流；每条修订有稳定身份、证据引用和前置状态。
多实例切换也要限制旧写入者，不能让旧代次继续提交新的规范性结论。

发现重组时，先持久记录受影响旧证据的撤销，再记录新分支证据与验证结果，最后才推进新代次的完整覆盖前缀。
消费者按修订流连续应用，修订去重、投影变化和进度同事务提交；旧观察晚到时，依据当前代次和已存在的撤销记录核验，不能重新置为有效。
即使撤销先于观察明细到达，也要保留撤销墓碑或待补记录，而不是因“没查到这条日志”直接丢弃。

同一证据可能先被观察、再被撤销，也可能经权威重新验证后恢复，因而不能把所有修订都按 evidenceId 当成重复而忽略。
修订身份负责区分状态变化，证据身份负责定位观察，logicalDepositId 负责约束资金效果，三者作用不同。
节点的 removed 标记只能触发核验，不能独自充当完整重组顺序或最终性证明。

## 第 5 层：最终门槛与完整采集前缀必须同时满足

**面试官：** 修订已经有序了。D1 所在区块确认数达到阈值，就可以提交入账吗？如果中间有一段日志补扫还没完成呢？

**面试者：** 不能只看某个日志已经等了多少块，还必须证明它属于当前链视图，并被可靠采集覆盖。
最终门槛由具体网络与风险政策决定：如果采用协议提供的 finalized 标记，要核验其可信来源及祖先关系；如果采用 N 次确认，则明确这只是概率性风险政策，不是绝不重组的数学保证。
不能把一次普通最新高度读取称为已获得最终性。

另一个条件是目标扫描范围在当前规范链上的完整前缀，逐块记录哈希、父子衔接与完整采集结果，包含没有目标日志的空区块。
假设 D1 在高度 105，最终门槛已到 110，但 103 的采集未完成，则本模型的完整前缀仍止于 102，不能因为已经见到 105 就越过缺口。
RPC 成功返回也只是在约定可信数据源与完整查询条件下的采集证据，不能自动证明服务端没有漏报。

可入账边界应是已通过门槛、属于同一有效祖先链且完整采集的最大连续前缀。
不同链、不同过滤范围或旧链代次的最大高度不能直接取最小值后拼成这个证明；换链视图后，受影响区间必须重新验证。
最终性解决“是否足够稳定”，完整前缀解决“是否有缺口”，两者缺一不可。

## 第 6 层：入账决定不能与重组裁决并发穿透

**面试官：** 你检查时 D1 满足两个条件，但检查后、提交入账指令前发生重组，怎样避免用刚刚失效的检查结果放款？

**面试者：** 最终入账决定必须与规范性修订在同一权威状态机内串行裁决，而不是先读一个内存标志再异步发送资金消息。
提交时校验当前链代次、支持证据、最终门槛与覆盖前缀，原子记录 `CreditDecision(D1)` 和可恢复的交付来源。
若用数据库承载它们，可以同事务校验版本并写决定与 Outbox；并发版本改变则回滚、重新判断。

如果重组先被接受，旧证据就不能再通过正常最终化路径；如果入账决定先提交，它已经成为系统接受的经济决定，必须可恢复、可审计。
决定事件携带 logicalDepositId、载荷绑定、支持证据与政策版本，消费者不能自行换一个 blockHash 再制造新决定。
发布超时后恢复原决定，不重新选择身份，也不能把未提交的内存结论发出去。

这个边界还区分普通重组和已越过系统最终性政策的异常。
已接受的决定后来遭到深重组挑战时，应进入事故控制，必要时暂停在途决定的继续放款；但不能静默删除原决定，假装从未承担过义务。
索引器与账户不在一个事务里时，靠稳定决定与可靠交付衔接，不能虚构一次跨库原子读取把两个系统锁在同一时刻。

## 第 7 层：账户怎样把最终决定变成唯一资金效果

**面试官：** 最终决定已经可靠交付。如果账户事务提交后确认丢失，或者新区块的支持证据随后补到，怎样确保甲最终只增加 10 USDC？

**面试者：** 账户使用固定的充值效果命名空间和 logicalDepositId 建立持久唯一约束，并校验受益人、资产、金额等已绑定载荷。
同一本地事务内写充值分录、用户余额、效果去重、原决定引用与业务进度，提交后才确认已应用。
确认丢失时重投只返回原结果；同一经济身份即使由另一个 evidenceId 支持，也不再增加余额。

分录需要有明确的入金对手科目，并与经验证的外部资产流入核对，不能凭空只改用户余额。
USDC 金额统一使用最小单位整数；本例不假设任意代币的事件金额都等于实际收到金额，非标准代币必须另定可验证规则或拒绝接入。
最终决定流有自己的连续位置，账户不能把区块高度或 RPC 请求编号冒充已完成的消费前缀。

若发现同一 D1 载荷冲突、旧效果记录缺失，或账务恢复到不匹配的历史点，应阻断核查，不能简单换命名空间重新充值。
投影重建只重放充值状态，不重新执行资金入账；资金历史的保留期限必须覆盖允许的重放和恢复范围。
在来源最终可交付、消费者可恢复等条件下，重投与持久唯一效果才能共同实现一次业务入账，而非依靠单次消息投递。

## 第 8 层：门槛之前的重组怎样恢复待确认状态

**面试官：** 你要求资金只增加一次。如果 D1 尚未入账就被撤销，随后又在新区块出现，重启恢复时怎样不永久漏掉它，也不把旧确认数继承过去？

**面试者：** 重启从持久的规范链代次、修订进度和覆盖检查点恢复，而不是把历史见过的所有证据都标为有效。
旧证据失效后，D1 可以显示为待重新确认或已脱离规范链；新区块证据重新关联原 logicalDepositId，保留原载荷约束。
只要尚未形成资金效果，待确认展示可以修订，不需要对用户可用余额做“先加再减”。

新证据的稳定性依据它在当前链中的位置重新计算，不能沿用旧区块累计的确认数。
如果新区块尚未补扫完整、父链衔接不明或来源仍冲突，就保持待确认并补齐，不因旧证据曾接近门槛而提前入账。
修订流恢复也必须先补缺口；不能 ACK 后只记住最大修订序号，再指望启动时猜出漏掉的撤销。

若历史保留已不足以判断某个入账决定是否存在，需要从可信归档和账务原引用恢复证据链，而不是把未查到等同于从未入账。
在正常重组路径里，变化的是观察和等待条件，不是已经确定的账户历史。
这个限制让系统能解释“页面里的充值暂时消失”，同时保证资金不会因重建而重新生成。

## 第 9 层：已入账之后的深重组为什么是事故边界

**面试官：** 假设政策已经接受 D1，甲的 10 USDC 也用于后续交易了，随后深重组让充值消失。能不能发一条撤销消息把所有余额改回去？

**面试者：** 不能把这种情况按普通待确认投影回滚处理，因为用户资产可能已经转移给其他用户或被提现，系统已经形成后续经济义务。
我会触发最终性违约事故：暂停受影响来源的新入账，按风险范围限制提款或相关账户操作，并固定原决定、链证据、账务分录和受影响依赖。
冻结是阻止风险扩散，不代表可以把所有后续成交宣布无效。

处置时先确认当前规范链与真实托管资产，核对已形成的用户负债、在途出金和可能的资产缺口。
未放行的在途入账可以受控暂停，但原决定及处置状态必须保留；已经入账的历史不能被直接删除或覆盖。
需要追索、损失承担或账务调整时，依据明确业务与授权政策产生引用原记录的新分录，并承认可能存在无法自动追回的缺口。

如果余额已花掉，简单做负数扣回、让任意无辜对手方退钱或重新播放旧链都不能证明系统已经恢复偿付能力。
后续操作必须由事故流程与风控权限裁决，保留审批、影响范围及核对证据，再决定何时恢复业务。
因此“达到门槛后按业务最终处理”是一项风险承诺，不是声称底层链永远不再发生超预期变化。

## 第 10 层：怎样证明身份、修订与最终边界没有混淆

**面试官：** 这套方案既有三个身份，又有普通重组和事故边界。你会用什么具体反例检查它，而不是只验证正常充值一次？

**面试者：** 先让同一 evidenceId 重复十次，再让同一 D1 在另一个 blockHash、不同 logIndex 下重现。
预期是保存不同证据、维持一个经济身份；只有当前有效证据满足门槛和覆盖条件后，才产生一份有效入账义务并形成一笔资金效果。
再修改 D1 的金额或受益人，预期进入载荷冲突，不按新证据重新放款。

第二组让撤销先到、旧观察迟到、修订中间缺一条，并让 105 已观察而 103 采集不完整。
预期分别是保留撤销依据、旧证据不被迟到消息复活、连续修订阻断，以及最终化边界不越过 102。
在决定提交和账户提交后分别丢失确认，恢复后仍复用原决定和原资金效果，不重新生成充值 ID。

最后在资金已被后续使用后模拟最终性政策遭破坏，预期进入事故冻结与缺口核对，而不是删除历史分录。
这些是设计推演，不冒充已经执行的链故障实验；每个结论都要能追到可信来源假设、修订顺序、最终政策和账务提交证据。
如果无法证明来源完整性或经济身份稳定性，就明确缩小保证，而不是用“区块链不可篡改”遮蔽缺失条件。

## 本题收束

**讲透的机制：** 链证据身份定位一次具体观察，修订身份约束观察变化的顺序，逻辑充值身份约束唯一经济效果；最终门槛和完整规范链前缀共同决定是否可进入资金路径。

**易错边界：** 新 blockHash 不代表新充值；logIndex 不是跨重组稳定的经济 ID；撤销不能被迟到观察复活；确认数不能代替完整采集；最终性之后的深重组不能自动抹掉资金历史。

**检验反例：** D1 先在区块 A 出现，重组后同一充值在 B 重现，logIndex 也改变。若用新证据键再次给甲增加 10 USDC，说明把观察去重误当成经济幂等；若 A 已导致放款且后续已使用，又直接删掉原分录，则同时越过了事故处置边界。
