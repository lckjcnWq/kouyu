# 大问题 12：行情、私有回报与查询需要同样的一致性吗？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| ResultBatch / 成交事实 | 撮合已经共同提交的完整裁决。 | 101 可证明 B1 全成，不自动证明资金或页面都完成。 |
| orderStatus=FILLED | 订单数量已经全部成交。 | 不能翻译成甲现在已经可花 0.25 BTC。 |
| settlementStatus=PENDING/APPLIED | 账户结转待处理或已经提交。 | 以账户权威事实驱动，不由订单投影自行推断。 |
| 投影 / 权威源 | 由事实整理的读视图与拥有裁决权的来源。 | 页面可重建，但不获准修改成交、预留或余额。 |
| Outbox / 结转通知 | 与账户事务共同登记的可靠交付依据及通知。 | 资金完成通知有自己的来源身份，不能只凭订单全成编造。 |
| streamId / 来源位置 | 某一来源的顺序范围及其处理坐标。 | 撮合的 101 与账户通知的 101 不天然相同。 |
| projectionVersion / 构建代次 | 读模型采用哪套解释，以及哪一次隔离构建。 | 数据、去重与真实进度要绑定，不可旧内容贴新版本。 |
| 连续水位 / 水位向量 | 已完整覆盖的前缀，以及多来源的各自前缀。 | 不取最大号，联合视图还须包含结转所依赖的成交明细。 |
| 最低读取凭据 / 读屏障 | 要求本次结果至少包含某个已确认效果的约束。 | 受理回执不能冒充账务完成凭据，凭据也不替代下单资金校验。 |
| 实际读取端 / 一致快照 | 真正返回内容的副本，以及内容与水位的同一切面。 | 先查主库进度再读旧副本，不能声称满足最低水位。 |
| NOT_CAUGHT_UP | 明确说明这个读取路径尚未追上。 | 可以有界等待或换满足条件的路径，不能伪装成新鲜结果。 |
| WebSocket / 恢复游标 | 长连接推送与客户端真正应用到的位置。 | 最后收到不等于已应用，断线需要补缺或重新取快照。 |
| 私有订阅版本 / 过滤流 | 用户专属回报协议及其可见事件范围。 | 应提供自身连续位置，不能让客户端猜哪些市场号被过滤。 |
| 快照 S / live 高水位 H | 重建起始切点与追赶阶段的固定目标。 | 快照严格对应 S，持久补上后缀，覆盖 H 后才合流。 |
| 盘口增量 / 绝对值合并 | 对展示状态的变化量，以及协议允许的最新值替换。 | 可重同步不等于任意丢增量，更不等于删经济事实。 |
| 激活围栏 / 单调读取 | 防旧构建夺回服务入口，以及会话不读回更旧版本。 | 切换和回切都要满足实际水位，重建不重启资金结转。 |

## 把整篇文章压缩成一个故事

B1 的结果 101 已提交，行情和私有订单页很快显示甲买到 0.25 BTC，但账户仍在结转。产品把“全成”和“结转中”分开：前者由撮合证明，后者只能由账户事务或可靠完成通知证明。等账户实际付出 15,015 USDT、返还 10 后，甲才有可用 4,985 USDT、0.25 BTC；消息先到页面不代表余额已经可支配。

甲拿到账务完成回执立刻查余额，请求要求至少覆盖这次结转。读服务要在真正返回内容的副本上核验同快照水位；若副本还在 100，就等待、换路由或明确未追上，不能从主库借来 101 给旧余额贴标签。私有推送断线后也要按实际应用游标补缺，超过保留窗口取带切点快照，不能把下一条新回报当作补齐了中间全部历史。

升级投影时，团队隔离构建新代次，从严格对应 S 的快照接连续增量，并持久保留实时尾流，追到目标 H 再受控切换。读请求固定某一代次，旧任务不能夺回服务入口，回切也不能倒退已承诺水位。公共盘口可以按协议重同步，丢掉的是可重建展示中间态，不是 T0、T1 的资金义务；整个重建过程也绝不能再次调用真实结转或外部支付。

[返回专题总览](README.md)

**流程位置与核心机制：** 位于可靠结果交付之后，讨论不同下游的完成承诺、连续水位、私有读取屏障、断线补齐与投影重建。资金消费事务沿用总览，本题不让缓存或查询投影获得资金裁决权。

**共同前提：** 沿用链下托管 BTC/USDT、限价 GTC、maker 价、零手续费与 B1 案例。完整 ResultBatch(101) 包含 T0、T1；账户完成结转后，甲可用为 4,985 USDT、0.25 BTC，不能因为页面提前显示全成就提前使用这笔 BTC。

```text
已提交 ResultBatch(101)〔成交事实〕
    ├─ 公共行情投影 → 带序号的快照／增量 → 客户端可见
    ├─ 私有订单投影 → B1 全成、结转状态单独展示
    └─ 账户本地事务 → 余额、分录、去重、lastSeq=101
                          ↓
                     已提交结转通知
                          ↓
                 私有资产投影／查询副本
                          ↓
            核验实际读取水位 → 返回结果或明确尚未追上
```

三条分支可在不同时间到达；“客户端看到了成交”不能反向证明账户事务已经提交。

## 第 1 层：先区分成交完成、账务完成与显示完成

**面试官：** B1 已经全部成交，但用户的余额还没更新。行情、私有回报和查询必须一起等到账务完成再返回吗？

**面试者：** 不必一起等待，但每个接口必须说清自己证明了哪一阶段。
ResultBatch(101) 可靠提交后，撮合域可以证明 B1 全成、产生 T0 和 T1，并承担交付这两笔成交义务的责任。
此时私有成交回报和公共成交行情可以发布，账户结转仍可以是 PENDING，不能把订单全成直接翻译成“资产到账”。

账户域只有在余额、预留、分录、去重和进度共同提交后，才能证明账务完成。
本例中这意味着甲实际支出 15,015 USDT、返还价差 10 USDT，并得到 0.25 BTC；如果消费事务还未提交，甲的预留仍须覆盖成交义务。
查询副本或前端尚未同步不改变这个已提交事实，也不能触发退款或重新撮合。

显示完成则是某个具体投影或客户端已经应用了相应版本，不是全系统新增的经济终态。
我会把 `orderStatus=FILLED`、`settlementStatus=PENDING/APPLIED` 和响应覆盖的水位分开返回，并标明结转状态来自哪里。
这样既不用为了行情等待所有下游，也不会用“最终一致”掩盖用户当前能否支配资产。

## 第 2 层：多个事实源怎样合成一个不说谎的投影

**面试官：** 你把订单和结转状态分开了。如果订单投影先收到 101，而结转通知晚到，怎样避免它把“全成”合成为“已到账”？

**面试者：** 我会让两种状态分别由其权威事实驱动，而不是由投影自行推断。
订单状态依据撮合结果，结转状态依据账户已提交的结转通知或权威查询；通知需要可靠来源，例如账户事务内产生的 Outbox。
账户通知即使先到，也只记录明确的结转证据，不能据此编造尚未获取的成交明细。

投影行保存订单来源位置、账户来源位置和投影版本；消费去重与更新进度也要在投影自己的本地事务中共同提交。
对撮合流使用 `(streamId, commandSeq)`，对账户通知使用它自身稳定的事件身份与连续位置，不能因为两边都出现数字 101 就认为它们是同一条流。
重投相同身份但内容不同要报冲突，不能按最后到达时间覆盖。

投影的覆盖水位表示已完整应用的前缀，不是收到过的最大序号。
撮合流中的拒绝、无成交等位置也需要通过完整批次或经过验证的覆盖记录推进；过滤业务字段不能制造未知缺口。
如果账户通知依赖某个成交批次，联合视图还要保留这个依赖，缺明细时返回“详情同步中”，而不是拼成假完整结果。

## 第 3 层：最低读取水位必须在实际读取端兑现

**面试官：** 既然状态可以晚到，用户收到“账务已完成”后立刻查询却读到旧余额，怎样保证这次读取至少覆盖刚才的结果？

**面试者：** 完成回执可以携带服务端生成的最低读取凭据，标明账户、来源命名空间、最低结转版本及其业务含义。
请求可靠受理的回执只能提供受理位置，不能冒充账务完成凭据；撮合序号 101 也只有在对应账户结转已提交时，才能成为账务读取要求。
多个市场或来源需要水位向量，不能对互不相关的序号取一个最大值。

读服务必须在实际返回数据的副本上检查覆盖水位，并保证水位与余额来自同一个一致快照。
若使用异步数据库副本，就应在该副本、同一读取事务中获取投影内容和提交标记；先查主库进度再去任意副本读余额不成立。
若读取缓存，缓存包也必须同时包含内容及其真实版本，不能另从主库取新水位给旧内容贴标签。

未追上时，可以有界等待、路由到满足条件的权威读路径，或明确返回 `NOT_CAUGHT_UP` 和实际水位。
不能悄悄返回低于最低水位的旧余额，同时带上“已完成”字段；客户端选择接受旧数据，也必须是显式降级，不能伪称已满足原读取要求。
同一会话继续携带已见水位可避免跨副本倒退，但撮合准入仍须由账户权威源检查可用资产，而不是相信客户端凭据。

## 第 4 层：断线重连不能只靠下一条推送掩盖缺口

**面试官：** 最低水位能约束查询，但用户主要靠 WebSocket 看私有回报。收到完成回报后断线，重连又遇到重复和乱序怎么办？

**面试者：** 我会给私有订阅定义稳定的排序域、持久投递位置和恢复协议。
客户端保存最后真正应用到本地视图的位置，而不是最后收到的网络包编号；服务端重连后可以从该位置补发，重复回报按稳定身份和版本忽略。
如果服务端发送的是过滤后的账户流，应提供该账户流自己的连续位置，不能要求客户端猜测跳过的市场序号是否属于其他用户。

客户端发现预期 51 却收到 53 时，先标记视图不完整，缓冲在界限内的数据并请求补齐 52。
保留窗口内无法补齐时，改为获取带切点的私有快照，再接快照后的增量；不能把 53 当作覆盖整个历史，也不能用本机时间排序订单与结转。
客户端本地持久化若需要跨重启恢复，应用状态和恢复游标也要共同保存，或在不确定时放弃旧游标重新同步。

慢连接要用有界队列和背压处理，超过上限就通知重同步或断开，不能不断创建 Go goroutine 等待发送。
网络回报的“已送达”不等于客户端已应用，更不等于账户新产生一次效果；交易操作仍查权威状态。
恢复协议改变时还要携带订阅版本，不能把旧游标套到另一套投影语义上继续使用。

## 第 5 层：公共行情可以重建，但不能丢掉经济事实

**面试官：** 私有回报缺口要补。公共盘口更新很密集，能否直接丢掉积压消息，取一份最新盘口继续？

**面试者：** 对可重建的盘口投影可以这样设计，但必须有明确的快照加增量协议。
例如快照声明覆盖行情流到序号 S，客户端丢弃不晚于 S 的增量，再按连续区间应用 S 之后的变化；发现缺口就停止声称盘口新鲜并重新同步。
如果增量是价位数量变化，丢一条后直接应用后面的变化可能永远得到错误盘口，不能用“后面还有更新”作证明。

合并同一价位的最新绝对值，需要协议明确它可替代哪些区间及其版本；不同价位、成交明细和订单回报不能一概覆盖。
展示用的最近成交列表可以按产品约定只保留窗口，但完整成交与账务事实必须留在其可靠来源或归档中，供交付、核对与审计使用。
可丢的是能从事实源重建的展示中间态，不是 T0、T1 的经济义务，更不是账户尚未处理就删除的资金事件。

行情过期可以显示陈旧标记、暂停依赖新鲜行情的展示功能，或者重取快照，不能据此修改已确定成交价格。
下单时的价格约束、余额和预留仍由交易核心检查，公共盘口只是信息输入。
因此，公共行情与资金事件可以采用不同保留和背压策略，但两者之间必须保留可恢复、可核验的责任边界。

## 第 6 层：全量重建与 live 合流怎样选安全切点

**面试官：** 你依赖快照恢复。现在私有投影逻辑升级，要全量重建，同时新成交还在持续发生，怎样不漏掉快照与实时流之间的事件？

**面试者：** 我会先建立可恢复的增量接收位置或足够长的来源保留，再取得与来源水位 S 严格对应的一致快照。
快照要么来自声明了准确切点的权威快照，要么由完整历史回放到 S 生成，不能一边无锁扫描变化中的表一边标注“当前最大序号”。
构建期间把后续 live 数据持久暂存，或依靠已固定保留边界的日志补读，不能只放在进程内存中。

新投影在独立构建代次里装载快照，随后从 S 的下一位置开始连续回放，重叠部分按稳定身份去重。
对订单与账户联合视图，S 是各来源的水位向量，还要满足依赖闭合：已显示的结转不能缺少它所依赖的成交依据。
账户余额来自账户的一致快照和账户变更流，不能仅回放撮合结果就在读模型中重新创造资金余额；来源被截断时应重新取可用快照或恢复归档。

追赶中可以记录某个 live 高水位 H，证明新投影已完整覆盖到 H，再继续追随 H 之后的事件。
这不是取一次“最大值”就算完成：每条流都要无缺口，未知版本必须解决，暂存溢出或保留失效则应中止本轮构建。
只有快照切点、连续增量与来源保留形成闭环，才能保证全量重建不会在 live 合流处永久少一笔。

## 第 7 层：切换新投影不能让游标与内容分家

**面试官：** 新投影已经追到 H，但旧投影还在服务请求。切换瞬间有新回报到达，怎样避免旧内容配上新游标，或者把新投影的进度又切回去？

**面试者：** 我会把投影代次、模式版本、实际覆盖水位与可读数据绑定为一个可验证的发布单元。
新投影每次应用事件时，数据、去重和进度同事务提交；激活只切换到已通过检查的代次，不能先对外公布 H 再慢慢填数据。
各代次由受控的应用器推进，切换入口有版本比较或围栏，避免旧构建任务迟到后重新夺回服务指针。

切换前先让新代次接入可持续恢复的 live 尾流，证明它已覆盖旧服务承诺的切点；切换后读请求固定在某一代次完成。
若允许旧请求读完，就返回旧代次及其真实水位，仍须满足该请求的最低读取要求；不满足就等待或重路由，不能借新代次的进度包装旧数据。
推送游标同样带代次，无法跨代次翻译时要求客户端重新同步，而不是把相同数字当成相同内容。

构建进程在切换前崩溃，旧代次继续服务；切换后崩溃，则由新代次已提交的检查点恢复，不凭内存尾指针跳过事件。
旧代次先保留用于核对，但回切也要重新满足单调读取与水位条件，不能为了回滚程序而倒退业务可见性。
重建仅产生读侧数据，不重启资金结转、不更换资金效果命名空间，也不调用外部通知或支付副作用。

## 第 8 层：怎样检验新鲜度承诺与重建闭环

**面试官：** 你把水位、快照和切换都串起来了。假如上线后用户仍说“回报已完成，但查询不对”，你怎样判断是允许的延迟，还是协议真的失效？

**面试者：** 我先收集完成回执的阶段、最低读取凭据、查询实际代次与水位，并查相同来源位置上的权威结果。
若回执只是成交完成，而账户尚未结转，余额未更新属于明确允许的阶段差异；若账户已完成、查询未要求最低水位，也可以是被如实标注的旧读。
但请求明明要求账务版本至少为指定值，服务却返回更低版本并称已满足，或者水位达标而余额仍是旧值，就是读取协议错误。

我会手工推演或设计故障用例：账户提交后延迟副本复制、丢失一条私有增量、打乱重建尾流，并在发布指针切换前后中断进程。
预期分别是有界等待或明确未追上、缺口补齐或快照恢复、阻止不连续激活，以及从绑定的数据与检查点恢复。
对 T0、T1，还要在相同水位比较订单数量、结转状态和甲的 4,985 USDT、0.25 BTC，不能拿两个不同时刻的数值判定错账。

监控也围绕这些承诺设置：连续水位落后量、最老缺口年龄、最低水位读取失败、重建暂存量和切换代次，而不仅是消息消费速度。
如果来源永久缺失或消费能力不足，就撤回无条件追上的承诺并升级处理，不能把“最终一致”解释为无限期不修复。
这些是设计检查与预期，不是已执行的工程测试；真正的合格标准是每一次可见性承诺都能追到相应提交证据。

## 本题收束

**讲透的机制：** 成交、账务、显示分别定义完成；投影按来源维护连续水位；最低水位由实际读取路径兑现；快照、增量、构建代次和检查点共同保证重建合流。

**易错边界：** 看到 FILLED 不代表可花资产增加；主库水位不能证明副本内容新鲜；可重建行情允许重同步，不意味着可以丢掉未完成交付的经济事实；重建不是重新执行账务。

**检验反例：** 账户已结转 101，副本仍在 100。接口先从主库读到 101，再从副本读出甲 4,975 USDT、0 BTC，却返回“101 已完成且已满足最低水位”。即使副本稍后会追上，这次响应也已经违反协议，必须等待、改路由或明确未追上。
