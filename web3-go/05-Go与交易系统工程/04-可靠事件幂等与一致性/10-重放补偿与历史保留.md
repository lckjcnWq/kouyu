# 大问题 10：重放、补交付、补偿和历史保留，怎样既能恢复又不重复产生资金效果？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 补交付 | 把已经成立却未送到的原事实重新送达。 | 取回完整原 101，不重新下单或撮合 B1。 |
| 重放 / 未完成结转 | 按顺序重读历史，以及继续履行原义务。 | 今天处理旧成交也不成为今天的新成交。 |
| 投影重建 / projectionVersion | 在隔离读模型里重新整理历史及其构建版本。 | 可以新建查询代次，但不能由此再次修改真实资金。 |
| 补偿 / 冲正 | 有业务依据、引用原事实的新纠错动作。 | 不等于删除旧分录，也不是未知提交时先做反向效果。 |
| batchId / tradeId | 原结果和原成交的稳定身份。 | T0、T1 跨归档、补发、升级都不改号。 |
| schemaVersion / ruleVersion / contentHash | 原格式、原裁决规则及原内容摘要。 | 历史要可解释、完整可核验，不从当前盘口猜结果。 |
| effectNamespace / consumerGroup | 业务效果范围与运输订阅名字。 | 新组仍复用原资金命名空间，否则会绕过去重重复入账。 |
| TTL / 热去重 | 时间过期参数及在线存储的处理明细。 | 记录到期不表示旧资金效果失效，归档仍可能重投。 |
| lastSeq / 历史核验 | 已应用连续前缀与对旧身份原内容的查证。 | 已覆盖但缺去重行，不当新事件，也不无条件静默成功。 |
| 共同检查点 / 水位向量 | 内容与进度对应的一致恢复切面。 | 余额、预留、分录、去重和各流进度不能各取一份备份。 |
| 保留下界 / 可恢复后缀 | 最早仍需保留的位置与检查点后的完整历史。 | 由最老合法备份、补交付和重放路径共同决定。 |
| offset / 接收 inbox | 消息端运输位置与本地可靠接收的待办。 | 恢复旧库不能信当前高 offset，已确认待办也须共同恢复。 |
| 效果证据 / 证据修复 | 证明原资金实际提交的记录及其受控恢复。 | 当前余额相近不够，修证据不能顺便再改资金。 |
| correctionId | 新更正事实自己的稳定身份。 | 绑定原成交、原因、审批与金额，更正重试也只能生效一次。 |
| 逐资产平衡 / 风险处置 | 每币种去向可解释，以及缺口由谁授权承担。 | 资金已转走不能强写负可用来假装冲正完成。 |
| 外部效果 / 恢复隔离 | 不随本地备份回退的动作，以及恢复期间不开放真实资金的限制。 | 跨分片或支付另有协调，本地重放不回滚外部世界。 |

## 把整篇文章压缩成一个故事

账户丢了 101 的消息，修复人员从可信结果源或归档取回原完整批次，保留 T0、T1、金额、版本和摘要补交付。未结转就履行原义务，已结转就核验原结果。若只是订单页面有错，可以建新投影版本隔离重放，但绝不能让读模型重建顺手调用真实结转，再给甲增加 0.25 BTC；换消费组也不允许换资金效果身份。

后来数据库恢复到进度 100 的一致旧备份，消息组却已确认过 101。系统先保持恢复隔离，共同恢复余额、预留、分录、去重和进度，再补齐检查点后的全部相关账户事实，不能只补成交就开放余额。此时应用原 101 是恢复那套旧状态，不是增加第二份效果；高 offset 不能证明恢复后的库还持有原数据，热去重过期也不能让旧输入变新业务。

另一个独立事故里，调查确证历史记账错误，才建立带原引用和审批的 correctionId，通过新分录纠正，不覆盖 T0、T1。客户若已花掉资产，还要明确追偿或损失承担，不能强写负数抹平。保留计划必须同时覆盖原事实、效果证据、最老合法备份与完整后缀；没有这些材料，再可靠的“重放按钮”也不能证明恢复正确，更不能保证外部支付随本地备份退回。

**流程位置与核心机制：** 本题覆盖已提交事实的历史恢复、派生视图重建、旧备份接续与错误更正，重点是身份和保留边界。
沿用总览的本地账户事务、稳定 batchId／tradeId 与 effectNamespace；不把重放当作再次撮合，也不为补交付创造新成交。

## 第 1 层：四种恢复动作的业务含义有什么区别？

**面试官：** 出现历史缺口时，团队常说重放、补发或补偿。它们是不是把消息再处理一遍的不同叫法？

**面试者：** 不是，首先要说清是在补传事实、重建派生状态、继续未完成效果，还是产生新的纠错事实。
补交付是把已经提交的 ResultBatch 再送到缺少它的下游，原 batchId、tradeId、内容和版本不变。
重放是按原顺序重新读取历史，具体是否改变状态取决于目标：投影可以重建，资金消费者则必须复用原效果身份。
恢复未完成结转仍是在履行原义务，不能因为处理发生在今天，就当作今天新产生了一笔成交。

补偿或冲正则是在有明确业务依据时，产生带原事实引用的新审计事实，不是把旧消息换个 ID 再投一遍。
B1 已确定 T0、T1 后，消息丢失只需要补交付，不能删除成交重撮合，也不能先生成反向资金效果。
如果原账务确实错误，要说明原来错了什么、纠正多少、由谁授权，而不是使用“补偿”掩盖未知提交。
这几个动作虽然都可能读取历史，但它们的完成条件、权限和是否允许新业务效果完全不同。

## 第 2 层：补交付怎样证明送回的是原来的完整事实？

**面试官：** 你说消息丢失只补交付。现在 101 在消息系统里找不到了，从哪取，能不能重新执行 B1 来恢复结果？

**面试者：** 应从已提交的结果源或可验证归档取原 ResultBatch(101)，不能重新提交 B1 获取一份新结果。
重新撮合可能面对不同订单簿、规则或价格，即使最后数量相同，也不等于恢复了原 T0、T1。
需要核对 streamId、commandSeq、批次清单、原 contentHash、schemaVersion 和 ruleVersion，确认取得的是完整原事实。
若原传输拆片，先按清单重组并验证，不能只找到 T0 就宣布 101 已经补齐。

补交付可以增加新的投递尝试记录，但 T0=(BTCUSDT:v1,101,0)、T1=(BTCUSDT:v1,101,1) 仍然不变。
账户接到原 101 后，尚未应用就按原事务应用，已经应用就核验原结果，同身份不同内容则阻断。
原事实不可恢复时，必须承认出现证据缺失，不能根据当前余额和页面记录拼一份“应该差不多”的成交。
恢复能力来自事先保存的可信事实及其完整性承诺，不来自重放按钮本身。

## 第 3 层：为什么投影重建可以新建版本，资金重放却不能照做？

**面试官：** 原事实能取回了。如果要修复错误的订单查询视图，能否和账户一样把历史重新消费一遍？

**面试者：** 可以读取同一历史，但要把目标限定为隔离的派生投影，不能让重建路径同时产生资金写入。
例如新建一个 projectionVersion，在空的查询表或隔离存储中按原事实重建订单与成交展示，记录自己的连续水位。
规则、字段解释与快照版本要明确，重建期间旧视图继续服务，新视图追到约定水位并验证后再切换读取入口。
新建投影版本是重建派生状态的标识，不是新成交身份，也不是新的资金效果命名空间。

如果从快照加增量恢复，快照内容、各流水位和版本必须来自共同的一致切面，再接上各流之后的完整后缀。
不能先复制不断变化的查询表，随后拿另一次读取的最大序号当起点，否则快照与增量之间可能遗漏或重复。
重建程序应通过存储与权限隔离禁止写余额，避免一段“通用重放逻辑”顺手调用真实结转。
回放可以再次生成相同展示行，却不能因此把甲再增加 0.25 BTC；这是两个不同目标的核心边界。

## 第 4 层：更换 consumerGroup 为什么不能更换 effectNamespace？

**面试官：** 你要求隔离投影。若账户消费者升级后换了消费组，从头读取历史，换一个 effectNamespace 能避免旧去重记录干扰吗？

**面试者：** 对真实资金结转不能这样做，因为 consumerGroup 是运输与部署身份，effectNamespace 表示业务效果的语义范围。
同一成交向同一套真实账户结转，升级、换组、换主题或重启，都必须保持原 effectNamespace、tradeId 和分录身份。
把消费组名字拼到效果命名空间里，会使同一 T0 在新组里看起来“从未发生过”，从而绕过原去重与分录唯一约束。
正确做法是让新组读取已有账户进度与原效果记录，重投部分核验原结果，未完成后缀才继续应用。

空白沙箱或只读演算可以有隔离目标和版本，但它们不能直接连接真实余额表，演算结果也不能作为第二次结转上线。
若升级涉及新的合法业务效果，例如独立的费用更正，应定义新的权威事实和原事实引用，而不是把全部旧成交再入账。
对于已应用的原效果，新算法发现差异也不能悄悄覆盖其金额，应进入可审计的纠错流程。
命名空间是业务语义的一部分，不能作为绕过历史约束、让部署“顺利跑起来”的开关。

## 第 5 层：为什么给去重记录设一个 TTL 还不足以安全清理？

**面试官：** effectNamespace 保持不变，但去重记录越来越多。给每条记录设置 TTL，过期后让历史重试自然消失，可以吗？

**面试者：** 单独按时间过期不安全，因为消息可重投的范围与业务证据的保留范围可能远大于这个 TTL。
旧消息可能来自长时间积压、人工补交付、归档或旧备份恢复，不能只按通常的网络重试时间估算。
一旦原效果证明消失，而消费逻辑又把“去重行不存在”解释成新事件，就可能再次产生资金效果。
同一流的持久连续进度和分录唯一约束可以继续防重，但它们必须真实保留且被正确使用，不能被 TTL 一起清掉。

对于 seq 已被 lastSeq 覆盖、却缺少原去重行的输入，不能当作新批次应用，也不能不看内容就静默返回成功。
应按保留协议取归档核验原身份与内容，或者进入需要历史核验的阻断状态；持久进度不允许倒退来迁就旧消息。
仅有“这个序号以前处理过”还不足以证明现在收到的内容与原来一致，哈希或等价证据也要有去处。
TTL 最多是已证明安全后的存储管理参数，不是这个证明本身，更不是资金效果的有效期限。

## 第 6 层：源、归档、重投与旧备份怎样共同确定保留下界？

**面试官：** 那保留多久才安全？如果在线源已经删掉很早的批次，是不是就能同步删除相应去重和分录证据？

**面试者：** 不能只看在线源，因为归档、人工工具、接收 inbox 和仍允许恢复的旧备份都可能重新引入历史。
我会先列出所有合法恢复路径，确定最早可能重投的位置、最老可用备份的检查点，以及恢复到目标水位必需的全部后缀。
保留计划至少要覆盖这些路径中最远的历史范围，而不是对几个互不关联的 TTL 分别拍板。
如果归档允许任意历史补交付，就必须同时保留相应的效果判定证据，或者有可信检查点和旧输入拒绝协议。

在线热去重可以迁入不可变归档，但仍要能按身份核对原内容、效果与检查点，不能只留一个无法定位业务的总文件。
可信检查点须绑定账务快照、各流连续进度、版本与完整性依据；拒绝检查点之前输入时仍保留历史核验入口，不能当新事实接纳。
若选择彻底结束某段历史的可重放能力，必须同步禁用对应旧备份与补交付入口，并证明不存在依赖这段历史的待处理义务。
原始载荷仍可从任何合法入口进入时，单独删除唯一效果证据就打破了共同契约。

反方向也一样：保留完整去重记录，却删掉最老备份之后唯一的结果后缀，同样无法完成恢复。
未应用的 inbox 和未结清义务不能因日期老而清除，来源迁移要先验证归档完整可读，再改变在线保留边界。
因此下界应以各流位置和可恢复切面表达，时间只用于容量估计与留余量，不代替完整性判断。
最简单的基线是对应范围内同时保留事实与效果证据；压缩方案必须额外证明旧输入不会被当作新资金效果。

## 第 7 层：恢复旧数据库备份后，应该从哪个位置接续？

**面试官：** 保留契约已经列清。现在账户数据库恢复到 lastSeq=100 的旧备份，但消息组 offset 早已越过 101，该怎么恢复？

**面试者：** 应先把账户系统保持在恢复隔离状态，以备份自身的一致检查点为起点，而不是相信消息系统当前 offset。
基线要共同恢复余额、预留、分录、效果去重、业务进度，以及所采用接收模式中的 inbox，不能只恢复余额表。
然后从可信结果源或归档补取检查点之后的完整批次，包括本例 101，以原身份推进到确定的恢复目标水位。
消息组 offset 可以在验证后重设或改用补交付通道，但它不能证明恢复后的数据库仍拥有曾经确认的数据。

在整套一致备份回到 100 的基线下，101 的原资金效果也不在这套恢复状态里，重应用 101 是恢复原状态，不是合法增加第二份效果。
但必须恢复备份之后的全部相关账户事实，不能只补成交、遗漏后续预留或账户域命令，再把余额立即对外开放。
如果只恢复去重或只恢复进度，会使它们与已经存在的分录、余额不一致，这不是“正常重放”能掩盖的问题。
应使用共同快照及配套恢复日志恢复一致切面，缺失后缀就停止接管，不能拿当前余额猜出历史。

如果备份声称持久接收过 101，却没有尚未应用的 inbox，说明接收恢复承诺本身被破坏，也不能靠高 offset 跳过。
系统对外开放前，需要确认目标范围已追平、身份约束仍有效，并完成同水位对账。
涉及外部支付或跨账务分片时还存在不能随备份回滚的外部效果，那是改变基线后的额外协调问题。
本地数据库恢复能重建本地一致状态，不能被夸大为能够撤销任意外部世界的历史。

## 第 8 层：历史证据不完整时，能否靠当前余额推断已处理？

**面试官：** 恢复时发现 101 的热去重行缺失，但某些分录还在，或者归档也不完整。能否根据金额对得上就补一条 APPLIED？

**面试者：** 不能从一个当前余额或几条金额相近的分录推断整批 101 已经正确应用。
余额可能混入后续成交、预留、释放或人工更正，金额相等也不证明原 tradeId、账户、资产桶和批次完整性一致。
需要先依据原哈希、完整分录集合、共同进度与可信恢复记录，确定这是合法归档后的证据迁移，还是不应发生的部分损坏。
正常协议下资金、效果去重与进度共同提交，出现无法解释的半套证据应按不变量破坏阻断。

如果可信归档能够证明完整原结果及原处理结果，可以依受控恢复流程重建丢失的证据或恢复一致备份。
恢复证据本身要记录来源、范围和审计，不能借补记录之名把未知资金效果直接标为完成。
若查到原 101 已正确应用，只修复其证据与读取路径，不再修改余额；若恢复基点证明尚未应用，才执行原事务。
仍无法证明时就保留问题和受影响限制，不生成新的 batchId，也不将 lastSeq 人工拨过缺口。

## 第 9 层：确认原账务错误后，冲正为什么必须是新审计事实？

**面试官：** 你拒绝猜测。如果调查已经证明一笔历史记账错误，需要纠正，为什么不直接改原分录或删掉原成交后重放？

**面试者：** 因为原成交、原记账以及这次更正分别是需要解释的事实，覆盖或删除会让差异失去来源。
更正应由有权威资格的流程产生独立 correctionId，引用原 tradeId、batchId、分录和事故依据，明确更正原因、资产与金额。
更正也要有稳定的业务身份、审批记录和唯一效果约束，重复执行同一更正不能再产生一份反向资金效果。
原 T0、T1 的身份和内容仍然保存，不能把链下已确定成交当作消息故障导致的可删除临时记录。

例如只在独立故障变体中确认某个记账腿错误，应冲回错误效果并记录正确更正，而不是把正常案例的 15,015 改成另一个支出。
更正仍须逐资产平衡，并检查合法资金来源、预留和余额桶约束；客户资产已经转走时，不能为“账面归零”强行写负可用。
这类情况需要明确的追偿、垫付或风险处置授权及其独立记录，不能隐藏在普通重试函数里。
重建投影时展示原事实与更正关系，账户则应用各自唯一效果，最终能从历史解释当前状态。

## 第 10 层：如何证明保留与恢复契约真的闭合？

**面试官：** 原事实和更正都可追溯了。你会怎样验证去重清理、归档和旧备份恢复组合起来仍然安全？

**面试者：** 我会选取仍被允许恢复的最老备份，逐流核对其检查点到目标水位的来源后缀是否完整、可读取且版本可解释。
再核对这些历史可能经过的所有接收入口，确保同一资金效果始终使用原 effectNamespace，而不是靠新的消费组绕开历史。
归档不仅要有文件，还要验证身份索引、完整批次、原哈希与访问权限，恢复工具不能缺少它需要的规则版本。
如果任何必需后缀已被删除，就应明确宣布该备份不再具备完整恢复资格，而不是继续把它列为可用备份。

故障推演要覆盖热去重清理后的迟到重投、换组从头读取、只恢复旧接收数据，以及归档暂时不可用。
已应用历史应核验原效果或阻断历史核查，不能再改资金；未应用后缀应连续接续，不能跳过缺口。
同一 correctionId 重复出现也只能生效一次，并且原成交与更正历史始终可解释。
对本例恢复 101 后，甲仍只获得 0.25 BTC，支出 15,015 USDT 并返还 10 USDT，而不是把这些金额再加一遍。

容量优化最终要服从这个证明，而不是为了先清表再让业务补规则。
可以压缩、分层或迁移历史，但必须同步调整允许的重放、备份恢复和输入接纳边界，并保留审计可查性。
这些是应进行的恢复验证，不代表本文已经执行了备份演练或验证了某个归档系统。
能够指出哪些历史可恢复、哪些只能核验、哪些已被明确拒绝，才算把重放边界真正说清。

## 本题收束

**讲透的机制：** 补交付恢复原事实，投影重建隔离派生状态，资金重放保持原效果身份，冲正产生有原引用的新审计事实。
源、归档、去重证据、连续检查点与最老允许恢复备份，必须作为一份共同契约设计。

**最易答错的边界：** 换 consumerGroup 不换 effectNamespace，在线源已删除不代表归档不能重投，TTL 到期不代表资金效果到期。
恢复旧备份不能信当前高 offset，缺去重行不能当作新事件，纠错不能覆盖原成交和原分录历史。

**反例检验：** 去重证据已清理，新消费组改了资金 effectNamespace，再从长期归档重放 T0。
它会把同一成交认作新效果；即使归档完全可靠、每个事务都原子提交，也仍会重复记账，说明可靠保存事实不等于正确解释历史。
