# 大问题 5：数据库与消息双写之间的故障缺口怎样解决？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 双写缺口 | 两个系统分别提交，中间崩溃会留下只成功一边的窗口。 | 交换写库、发消息顺序都不能自动消除。 |
| 权威事实源 / 结果日志 | 能决定原义务的持久来源。 | 撮合默认由 ResultBatch 与 AppliedSeq 共同提交，不强塞独立 Outbox。 |
| Outbox | 在产生业务事实的同一事务里登记交付待办。 | 独立费用对比路径使用它，不向零手续费 B1 加费用。 |
| 不可变载荷 / factId | 不随后续表更新改变的原内容及原事实身份。 | 只留主键再查当前行，未必能还原当初的费用义务。 |
| schemaVersion / contentHash | 编码解释版本及规范化内容摘要。 | 同事实重发不改原金额和版本，摘要也不替代授权。 |
| 发布确认 / 至少一次 | 消息系统接管的确认，以及允许原消息重到的交付方式。 | 发送超时重发同一事实，不能标完成或换业务 ID。 |
| owner / leaseUntil / claimToken | 领取者、租约截止和本轮领取凭证。 | 短事务领取，网络发送放事务外，凭原 token 条件更新状态。 |
| 租约围栏边界 | 旧领取者失权后哪些动作能被实际拒绝。 | token 能挡旧实例改任务状态，不能撤回它已经在途的网络请求。 |
| streamId / seq / offset | 业务排序范围、流内位置与运输位置。 | 创建时间和领取先后都不能替代业务顺序。 |
| CDC | 变更数据捕获，沿数据库日志读取已提交变化。 | 可替代轮询交付，不凭空补足未记录的业务语义。 |
| LSN / 连接器位点 | 数据库日志位置及 CDC 已恢复到的来源坐标。 | 它们不天然是逐号连续的业务序号；先推进位点可能漏交付。 |
| 初始快照 / 增量切换 | 先读已有数据，再接后续提交变化。 | 切点要一致，重叠按原身份去重，不能漏掉切换期间提交。 |
| 业务封套 / 事务 begin/end | 完整业务结果与数据库事务起止信息。 | 一次事务结束不证明已涵盖被应用拆成多事务的整笔业务。 |
| 封存清单 / 分片摘要 | 声明批次最终内容及各片应有值的记录。 | 所引用片段先持久且不可变，收齐核验后才能应用。 |
| lastSeq / 连续前缀 | 已完整结转到哪里。 | 102 先到仍等待 101，发布侧有序化不替代消费侧检查。 |
| effectNamespace / 恢复保留 | 固定业务效果范围与来源、归档、去重的共同留存要求。 | 换消费组不造新效果，删 Outbox 不表示撤销原事实。 |

## 把整篇文章压缩成一个故事

团队要把已确定事实交给账户。工程师先分清两条路：B1 的 T0、T1 已在撮合结果日志共同提交，直接从该源恢复分发；另一份独立费用批次本来在关系库产生，就把业务变化和 Outbox 放同一事务。若费用提交后进程马上退出，持久待办仍在；若先发消息再提交业务，下游可能为后来回滚的事实入账，调换调用顺序救不了它。

发布器领取待办后发送，消息系统收到了，确认却丢失。租约到期，新发布器接手，旧实例随后也恢复，于是原事实可能到达多次。它们必须保留同一身份、内容与版本；领取凭证能阻止旧实例覆盖任务状态，却不能让在途请求消失。账户仍靠原业务身份和事务防重，收到后继 102 也不能越过缺失的 101。

换成 CDC 后，同样只能交付已提交变化，还要协调发送与来源位点的恢复。逐行更新和事务结束标记不等于完整业务封套；拆片必须按封存清单核验，不能把两个版本凑起来。最后能否清理，要看消息保留和归档是否真正接走恢复责任，不能机械等待所有消费者，也不能删掉最后来源。Outbox 和 CDC 保住的是可恢复交付，不是跨系统资金恰好一次。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题讨论“权威事实已产生，怎样可靠交付给下游”。重点是数据库事实与 Outbox 的共同提交、发布未知后的重试、租约竞争、CDC 的事务边界以及来源保留；不替代第 4 题的撮合结果提交协议，也不把消息送达当成第 6 题的账务完成。

**讨论前提：** 默认撮合事实源仍是可恢复结果日志，`ResultBatch + AppliedSeq` 原子提交；B1 仍为零手续费现货订单。下文的费用批次是“事实本来由关系数据库产生”的独立对比，不向 B1 添加费用，也不把 BTCUSDT 的 101 改造成费用批次。

```text
默认撮合路径：完整结果日志提交 → 可恢复分发器 → 消息系统
数据库事实路径：业务变化与 Outbox 同事务提交 → 发布器或 CDC → 消息系统
共同要求：只发布已提交的稳定事实；发送结果未知时能够重发原事实
共同边界：发布确认不代表账户结转；下游仍须完整校验、顺序处理和事务幂等
```

## 第 1 层：先确认双写发生在哪个事实源

**面试官：** 数据库已经写成功，消息发送失败，怎么避免事实永久丢失？是不是撮合链路也统一加一个 Outbox 就行？

**面试者：** 要先确定谁是权威事实源，再选择可靠交付方案。
本专题的撮合结果来自结果日志，101 中 T0、T1 及订单、预留处置结果已经共同提交，分发器从该来源恢复发送即可。
若再把一次独立数据库写入设为发布前提，就会引入“结果日志已提交、Outbox 尚未写入”的新缺口，并没有自然得到原子性。

如果讨论的是费用批次等数据库权威事实，我会让业务变化与交付记录进入同一个本地事务。
事务成功后，即使应用在调用消息系统之前崩溃，持久 Outbox 仍表明有一个待交付义务；事务失败则业务与该义务一起不存在。
这解决的是“事实已经成立，却没有可恢复的发送依据”，而不是让数据库和消息系统成为一个事务。

因此，两种路径的共同点是从已提交来源恢复，区别是原子边界所在的存储不同。
B1 仍按原日志产生 `(BTCUSDT:v1, 101)`，不能因为比较 Outbox 就重新撮合或为 T0、T1 生成新身份。
下游资金效果唯一和连续进度仍需另外保证，Outbox 不负责跨系统的一次性生效。

## 第 2 层：同事务具体保存什么才足够恢复

**面试官：** 你说业务与 Outbox 同事务。如果只存一个业务主键，发布时再查当前业务表，不也能恢复吗？

**面试者：** 只存主键未必能恢复原事实，因为业务表可能已经被后续事务更新。
例如费用批次从“已确定”进入“已结转”，发布器若读取当前状态临时拼消息，得到的可能不是那次提交对应的内容。
我会在原事务保存不可变事件载荷，或保存指向不可变版本的引用，不能把“能找到这行”误认为“能还原当时的义务”。

交付记录至少绑定稳定 factId、业务流与序号、schemaVersion、规范化 contentHash、完整载荷或不可变引用，以及待发送状态。
同一业务事实的交付身份要有数据库唯一约束；业务变化与该记录用同一连接、同一事务提交，不能在业务提交后才补写 Outbox。
如果事务提交结果未知，先按稳定业务键查权威提交结果，再恢复原事实，不能重建一笔新的费用义务。

载荷中的金额和数量使用最小单位整数，并固定编码版本、字段顺序、空值和枚举定义。
摘要便于识别同键异载荷，但接收方仍要核验来源、关键经济字段和授权范围；摘要不是业务正确性的替代品。
这些内容让发布器可以不依赖进程内存，也不依赖业务表后来的状态来重建消息。

## 第 3 层：交换两个调用的先后次序为何都不行

**面试官：** 既然载荷可以保存，为什么不先提交业务再直接发消息？或者反过来，先发成功再提交业务，省掉扫描 Outbox？

**面试者：** 先提交业务再发消息，存在业务已经提交、进程却在发送前退出的窗口。
如果交付义务只在内存里，重启后无法区分“无需发”和“本来应发但没发”；依赖调用日志也不能替代同事务的业务证据。
Outbox 把这个窗口变成可扫描的待办：业务成立时，发送依据必然已经持久存在。

先发消息再提交业务则是相反的问题：消息已对消费者可见，业务事务随后回滚，下游却可能已经据此入账。
即使把发送放进尚未提交的数据库事务内部，也没有让消息回滚，而且会在持锁期间等待外部系统。
消息发送成功之后、本地提交之前崩溃，仍可能产生“外部看见了不存在的数据库事实”。

正确顺序是先共同提交业务与 Outbox，再由独立交付过程读取已提交记录。
它允许“事实已成立、消息尚未送达”的暂态，但禁止发布未提交事实；这与默认日志路径只发布已提交 ResultBatch 是同一条约束。
接下来剩余的缺口不是有没有待办，而是消息系统已经接收时，发布器能不能准确知道结果。

## 第 4 层：发布结果未知时为什么必须允许重复

**面试官：** 消息系统已持久接收，但发布器没收到确认。Outbox 仍是待发送，这次重试会不会把同一费用或成交做两次？

**面试者：** 这个窗口不能靠猜测消除，我会保留待交付状态并重发同一事实。
确认丢失时，发送方无法仅凭超时判断消息没有进入系统；若直接标记完成，可能真漏发，若重试则可能重复。
选择至少一次交付，需要稳定 factId、原载荷和下游事务幂等共同承担重复，而不是每次发送生成新的业务 ID。

发布器只能在取得符合配置承诺的持久确认后更新发送状态，不能先标“已发送”再调用网络。
若收到确认后、更新 Outbox 前崩溃，恢复后仍可能重发；若更新发送状态的数据库提交结果未知，就查原记录或再次按原身份交付。
发送尝试 ID 可以不同，但原批次身份与 contentHash 不变，不能把一次重试伪装成新的费用事实。

发布确认也不是无限期保留证明，更不是账户结转证明，它只覆盖消息系统实际配置的持久性和保留范围。
默认撮合的 101 重投后，账户必须识别原批次，不能再次给甲增加 0.25 BTC，或再次给乙、丙增加 USDT。
这说明“可靠发送”和“唯一资金效果”必须在不同边界分别闭合。

## 第 5 层：多个发布器怎样领取而不靠长事务锁网络

**面试官：** 重试可以接受，但多个发布器同时扫描会重复发送很多次。你准备怎样领取任务，又怎样处理发布器领取后崩溃？

**面试者：** 我会用短数据库事务领取，把待交付记录更新为带 owner、leaseUntil、claimToken 的租约状态，提交后再进行网络发送。
领取可以用行锁或条件更新，时间判断以数据库约定为准；不能从“读取到了 pending”直接推导出自己独占任务。
网络请求不放在领取事务里，否则一个慢发送会长期占有数据库锁，影响业务写入与其他领取者。

发送得到持久确认后，发布器按原 owner 和 claimToken 条件更新完成状态，并检查实际受影响行数。
领取者崩溃后，租约到期允许新实例接管；续租也要带原 token，不能让失去所有权的实例延长别人的租约。
失败记录保留稳定内容与尝试信息，退避控制重试负载，不能通过改 factId 来绕过失败。

租约减少重复工作，但不证明外部发送只有一次，因为旧发布器可能暂停后恢复，网络请求也可能在租约过期后才完成。
claimToken 能阻止旧实例覆盖数据库中的新状态，却不能自动围栏消息系统里已经在途的请求。
所以这个机制首先保证任务可接管和状态不被旧实例篡改，资金正确性仍不能依赖它消灭所有重复。

## 第 6 层：租约不等于消息顺序证明

**面试官：** 旧实例过期后还可能发送，那么新实例已经交付后继批次时，旧批次才到达怎么办？按创建时间扫描能保证顺序吗？

**面试者：** 创建时间不是业务顺序，领取顺序也不等于网络完成顺序。
即使扫描时先取 101、再取 102，前者超时而后者成功，接收端仍可能先看见 102；旧实例恢复后还可能补来重复的 101。
需要在事实中保留明确 streamId 和业务 seq，不能把扫描顺序或租约 token 当成业务序号。

若发布端需要减少乱序，可按流串行推进发布位置，等待前序获得确认，再交付后继，并使用稳定的流路由键。
但超时的旧请求、主备接管及不同传输路径仍须纳入消息系统契约；数据库租约本身不提供外部发送顺序的充分证明。
数据库费用流也要定义自己的顺序域，不能借用 BTCUSDT 的 commandSeq 来假装与撮合共享一个总序。

账户正确性最终依赖接收侧只应用完整连续前缀：lastSeq 为 100 时，先到的 102 不得越过 101。
同身份同内容的迟到副本可以核验后返回原结果，同身份异内容则必须阻断；不能因为它来自旧租约就放松内容检查。
发布侧有序化用于减少等待和补齐成本，消费侧连续性约束才负责拒绝危险的越序资金效果。

## 第 7 层：改用 CDC 后哪些窗口消失，哪些仍在

**面试官：** 轮询还要维护租约与发送状态。换成 CDC 直接读数据库日志，是不是就能去掉重复和事务判断？

**面试者：** CDC 可以替代应用轮询交付，但不能替代业务与交付语义的同事务记录。
我会让 CDC 读取已提交 Outbox；数据库事务未提交时，连接器可以内部缓存或溢写大事务变化，但不得把它们当成已成立事实交给业务消费。
回滚事务不产生业务义务，事务提交后的变化才进入可交付集合。

连接器还要持久保存来源位点，并协调“消息已交付”与“位点已记录”的恢复窗口。
若先推进位点再安全交付，故障会漏消息；若先交付后推进位点，恢复可能重复，所以仍需稳定业务身份和下游去重。
数据库日志位置是恢复坐标，不会自动成为业务 seq，也不能代替原事实的载荷绑定。

初始快照与增量切换同样要有一致边界，允许重叠时依靠原身份去重，不能漏掉切换期间的提交。
日志被清理、复制槽失效或来源切换时，必须确认还能从保留位置连续恢复；不能随意从最新位点启动并宣称历史已经交付。
CDC 减少的是轮询与任务领取工作，不是跨系统原子提交的全部问题。

## 第 8 层：数据库事务提交不等于完整业务批次

**面试官：** 你要求 CDC 只看提交事务，但一笔业务更新了多张表，甚至分几次事务写入。收到事务提交标记就能拼出完整批次吗？

**面试者：** 不能。数据库事务边界说明这次数据库修改共同生效，不自动说明这些行就是下游需要的完整业务事件。
一笔转移可能同时修改账户、状态与审计表，逐行 CDC 会暴露存储细节；消费者既不知道哪些行属于同一业务，也不知道还应期待几行。
即使连接器提供 begin/end 元数据，它覆盖的也是来源事务，不是应用自行拆开的多个业务事务。

更稳妥的是在产生事实的事务里显式写出完整业务封套，或绑定不可变清单与完整内容。
若传输层把一个完整封套拆成多条记录，接收方按清单、分片索引、各片摘要及整体摘要组装，而不是看到第一条行事件就记账。
连接器按行分别交付，不能成为只处理 T0、遗漏 T1 却把 101 标记完成的理由。

如果应用本身跨多次事务生成一个大批次，则必须先明确此前写入只是准备状态，还是已经独立成立的业务事实。
前者需要最终原子封存完整清单，并保证所引用内容已持久、不可变且可恢复；后者不能靠事后补一个标记伪装成一次原子业务提交。
“最后一行已到”本身既不证明所有内容存在，也不证明各行属于同一内容版本。

## 第 9 层：跨事务行事件怎样证明完整且按业务顺序成立

**面试官：** 假设允许先分批准备、再封存清单。各片和清单由不同事务产生，CDC 到达也会交错，具体怎样避免误组装和误排序？

**面试者：** 封存记录必须绑定稳定批次身份、内容版本、预期分片集合及每片摘要、事件数量与整体 contentHash。
只有全部引用内容已经可靠提交且禁止被覆盖后，才提交具有明确业务含义的封存；CDC 先送到封存记录时，接收端也只能等待缺片。
它应按身份和版本持久组装，核对每个片号与摘要，重复片不能顶替缺失片，更不能把两个版本混成完整批次。

完整性成立后，还要单独检查业务顺序：来源必须定义序号何时分配、哪些已提交位置一定有封套，以及中间失败怎样暴露。
数据库自增号可能因回滚留下空洞，提交 LSN 则反映存储日志位置；都不能未经定义就宣称业务必须逐号连续。
若消费者只订阅某类行更新，还需专用连续流或可信的覆盖范围证明，不能把被过滤的其他事件误报成业务缺口。

默认撮合已明确每个处理过的命令位置都有完整 ResultBatch，包括无成交结果，账户按该流连续推进即可。
费用对比方案若要提供相同性质，必须自己建立完整的序号和封存契约，不能只靠 CDC 的“已提交”标签继承这些保证。
遇到缺片、同键异摘要或未知版本时保留证据并阻断应用，而不是为了继续前进而省略缺失经济义务。

## 第 10 层：何时可以清理 Outbox 与来源日志

**面试官：** 完整性和顺序都由协议补上了，Outbox 发布成功后马上删除，数据库日志也按固定天数清理，可以吗？

**面试者：** 清理依据应是恢复责任已经被可靠接走，而不是“调用曾经返回成功”。
如果消息系统的持久确认、保留范围与归档足以覆盖全部下游恢复要求，Outbox 可以在满足交接条件后删除，不必机械等待每个消费者都已经应用。
反过来，若它仍是唯一可补交付来源，或者下游可能离线超过消息保留期，就不能仅凭已发布状态删除。

CDC 位点、来源与归档、下游去重明细和效果证据、接收／应用水位要形成共同恢复保留契约。
慢消费者、长期阻断、旧备份恢复和规则升级重放都可能需要更早历史；必须能从一致检查点继续，并保留原身份及内容校验依据。
consumerGroup 或 epoch 变化不能改写 effectNamespace；无法覆盖的恢复窗口应明确限制或暂停清理，不能给历史换 ID 来“补消息”。

Outbox 清理产生的删除行事件只是交付元数据清理，不能被解释成撤销原费用或撤销已确定成交。
保留可靠来源提供的是最终可达的条件；若消费者永久停机、毒消息无人解决或处理能力长期不足，仍不能无条件承诺最终追上。
到这里闭合的是“业务提交后始终存在可恢复交付路径”，不是靠一张表获得跨系统恰好一次。

## 本题收束

**讲透的机制：** 数据库事实与 Outbox 共同提交；已提交来源驱动交付；未知发送按稳定身份重试；租约保护任务状态而非消灭外部重复；CDC 必须尊重事务提交、业务封套与恢复位点；清理不能切断最后一条恢复路径。

**易错边界：**

- Outbox 是数据库权威事实源的方案，不是替换默认撮合日志的理由；B1 仍零手续费，T0、T1 不因比较方案而改变。
- 发布成功、持久接收、完整批次成立与资金结转是不同承诺；租约、CDC 提交标记和最终分片标记均不能相互替代。
- 数据库日志顺序、业务序号和消息 offset 不同；过滤后的行事件不能天然继承连续业务流的含义。

**反例：** 旧发布器发送超时，租约过期后新发布器重发；消息成功后旧实例恢复再发一次。若更换业务 ID 或消费者只靠消费组去重，就可能重复记账；若将超时直接视为成功并清掉唯一来源，又可能永久漏发。正确结果是允许原事实重复到达，同时保有恢复证据并只产生一次业务效果。
