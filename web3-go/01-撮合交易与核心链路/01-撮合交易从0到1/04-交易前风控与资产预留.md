# 大问题 4：多交易对共享余额，怎样防止超买、超卖和重复占资？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> “查过余额够用”不等于“这笔钱已经归这张单占住”。本文讲零费链下现货的足额预留，不是合约保证金风控；多个市场用同一份余额时，必须由账户数据库统一裁决。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 可用 available / 预留 reserved | 可用能另花，预留已为某个意图占住但尚未付给卖方。 | 占 15,000 后就不能再拿这份钱支持另一市场的订单。 |
| 超买 / 超卖 | 承诺花掉的钱或卖出的币超过自己实际拥有的份额。 | 每个订单簿都串行，也挡不住两个市场各认领同一笔 USDT。 |
| 原子预留 / 条件更新 | 余额检查、扣可用和加预留作为一个不可分割动作。 | 只有当前可用足够才更新，不能先查一次、稍后再独立扣款。 |
| accountId + asset / 行锁 | 用账户和资产定位共同竞争的资金记录，并让数据库串行修改它。 | 两个服务实例也竞争同一行，不是各自加锁各自通过。 |
| 本地事务 / 回滚 | 余额、预留和意图要么一起保存，要么全不保存。 | 不能扣了可用却没有预留归属；死锁后整笔回滚再重试。 |
| Go mutex / actor | 前者是进程内互斥锁，后者是单负责人处理状态的模型。 | 本地锁不覆盖其他实例；市场 actor 也不统一保护跨市场余额。 |
| clientRequestId / 唯一约束 | 识别一次业务请求，并由数据库保证该请求只能创建一份记录。 | 结合账户、操作类型比较规范化内容，重试返回原预留。 |
| intentId / reservationId / payloadHash | 意图编号、预留编号和不可变请求内容的摘要。 | 一份预留只支持绑定的账户、市场、方向、数量与规则，不能换单复用。 |
| 预留凭据 / TTL | 凭据证明有已提交预留；TTL 是按时间到期的寿命。 | 本文凭据不因超时自行失效，签名正确也不能替代资金确已占住。 |
| 持久待提交状态 | 账户记录“这次意图还需继续投递”，重启后也能发现。 | 预留成功但 Place 提交响应丢失，恢复时用原编号继续。 |
| CommandLog / commandSeq | 可靠命令日志和市场内连续逻辑排号。 | 重投可占新位置，但必须识别为原业务，不能再占资或成交。 |
| AbortIntent / CLOSING | AbortIntent 请求关闭交易资格；CLOSING 只说明正在申请关闭。 | 真正生效要等市场有序提交关闭事实，不是账户先标记就能退款。 |
| Cancel / 关闭屏障 | Cancel 撤已有订单；关闭屏障还要禁止尚未接纳的迟到下单。 | 普通 Cancel 返回未找到，不证明未来 Place 不能执行。 |
| ResultBatch / AppliedSeq | 完整命令结果及已提交执行位置。 | 关闭事实和处置依据先可靠保存，账户才据此处理。 |
| 价差 / 取消退款 / 未结转义务 | 分别是少花的钱、不再交易的部分，以及已成交但尚未付款的部分。 | 三者不能混成“订单终态就全解冻”。 |
| tick / lot / int64 | 价格、数量的整数刻度及有限范围的整数类型。 | 金额、汇总与收款方余额加减都先查上限，不只检查买单本身。 |
| lastAppliedSeq / 去重事务 | 连续账务进度与防重复记录，和资产变化一起提交。 | 先记前序成交再释放余量；确认丢失不再退款一次。 |

## 把整篇文章压缩成一个故事

甲只有 20,000 USDT，却同时在两个市场各下一个要占 15,000 的买单。两个市场各自看余额都够，若只各自串行撮合，合起来就承诺花 30,000。正确做法是让两次预留竞争同一个账户资产记录：第一笔在数据库事务里把可用改为 5,000、预留加 15,000，并保存原请求和意图；第二笔再判断时就不够，必须拒绝。钱不是先付出去了，而是不再允许重复承诺。

为了看清后续金额，甲重置初始状态，单独提交 B1：买 0.25 BTC，限价 60,100，先占 15,025。事务把预留、意图和原请求绑在一起，重试只返回这份记录，不再占一次；若同一个编号把数量改了，就报冲突。提交给撮合的凭据也必须绑定这张单的完整内容，不能拿另一张小额预留来冒充足额资格。

假设 Place 的提交响应丢失。系统保留资金，用原身份查和重投，不因过了几秒就把钱退回去。甲想放弃时，提交 AbortIntent，让关闭和迟到 Place 在同一市场队列中竞争：关闭先到就持久禁止原单执行；Place 先到则保留已成交部分，只撤实际剩余。账户标记“关闭处理中”不是关闭完成，普通撤单未找到也不是退款证明。

若 B1 正常先与 0.10@60,000、再与 0.15@60,100 成交，实际支付 15,015，返还价差 10，甲最终为 4,985 USDT、0.25 BTC。若独立改成买价 60,000 的 B2，只成交 0.10，则剩余 0.15 仍占 9,000；无后续成交时撤掉余量，才退这 9,000，最终可用 14,000。账户必须先结转成交，再处理退款；关闭已退过之后，迟到 Place 被拒绝也不能再退一遍。安全闭环靠的是唯一资格、有序关闭和同事务记账，不是一个超时解冻开关。

**流程位置与核心机制：** 位于接入校验之后、Place 可靠受理之前，负责把“余额看起来够”变成不可被其他订单重复使用的交易资格。主线是共享余额的本地事务、请求身份、预留绑定，以及不确定受理下的有序关闭；撮合算法和完整恢复机制不在本题重复展开。

**必要前提：** 沿用总览的 BTC/USDT 链下托管现货 CLOB、限价 GTC、maker 成交价、零费、不同账户和单交易对单写者。账户资产位于同一事务数据库。提到其他市场仅为说明共享 USDT 的竞争，不改变 BTC/USDT 案例；预留成功、命令受理、撮合完成和账务完成是不同阶段。

## 第 1 层：为什么已经串行撮合，还必须提前预留资产

**面试官：** 每个交易对只有一个撮合写入者，为什么还要交易前风控与资产预留？直接检查余额再撮合不行吗？

**面试者：** 不行，市场串行只保证一个订单簿里的裁决顺序，不保证跨市场共享余额不被重复使用。甲只有 20,000 USDT，两个市场分别读到这笔余额，各接受一个占用 15,000 USDT 的买单，即使各自完全串行，合计也已经超买。卖单同理，必须防止同一份 BTC 被多个订单占用。

我会先检查账户权限、交易对、方向、正数价格和数量、精度以及业务上限，再让账户域原子地扣可用、加预留，并创建意图与预留记录。买单预留限价乘原始数量，卖单预留卖出 BTC 数量。这个零费现货模型不需要计算杠杆和强平风险，不能把永续合约的保证金规则混进来。

预留的含义不是资产已经付给对手方，而是这部分资产暂时不能支持其他交易。订单之后可能挂单、成交或被拒绝；在得到确定结果之前，账户必须保留它所覆盖的执行资格。

## 第 2 层：把余额检查和预留落在同一个数据库事务

**面试官：** 你说“原子预留”，如果两个市场从两个服务实例同时扣甲的 USDT，具体如何只有一笔成功？

**面试者：** 我会让它们竞争同一个 `accountId + asset` 余额行，而不是各自在 Go 进程里加 mutex。事务中的条件更新语义是：仅当 `available >= need`，且 `reserved + need` 不越过整数和业务上限时，执行 `available -= need、reserved += need`。受影响行数为一才表示拿到额度；另一事务等待后重新判断，只剩 5,000 USDT，就不能再占 15,000。

这个事务还必须插入 `intentId`、`reservationId`、请求身份和持久待提交状态。任何一步失败，前面的余额更新也回滚，不能留下“扣了可用却找不到预留”的孤儿记录。也可以先锁余额行再检查更新，但检查与写入不能分成两个独立事务。

涉及多资产或多账户时按固定的账户、资产顺序加锁，死锁则整笔回滚后重试。数据库覆盖跨实例竞争，单交易对 actor 只覆盖撮合状态，两者不能互相替代。预留时的余额检查只是第一道约束；以后给对手方入账、价差返还或释放预留，每次余额加减和批次聚合也要检查范围。不能假定买方金额合法，就自动证明卖方已有余额加上收入不会溢出。

## 第 3 层：事务能防并发超花，怎样再防重试重复占资

**面试官：** 数据库能防余额变负，但甲余额很充足时，同一个下单请求重试两次，可能两次预留都成功，怎么办？

**面试者：** 需要把业务身份和余额变化放进同一个事务。请求键明确为 `accountId + commandType + clientRequestId`，建立唯一约束；不能仅用客户端订单号或连接号猜是不是同一请求。先精确解析并规范化载荷，固化交易对、方向、价格、数量、订单类型、有效期规则及其版本，再保存规范载荷与哈希。

同键同载荷只能返回原意图、原预留和当前进度，不再扣一次钱。同键不同载荷返回冲突，不能把数量从 0.25 改为 0.20 后仍沿用旧预留。并发插入同一请求键时，由数据库唯一约束裁决；失败事务必须整体回滚，再读取胜出事务的记录比较载荷。

如果第一次明确余额不足，我会保留可解析请求的拒绝结果；客户端想重新发起业务要用新请求键，而不是让同一请求在不同时间悄悄变成另一种结果。原意图已经关闭也不重开，避免旧请求重新取得执行资格。REJECTED 是意图处理结果，不是已接纳的活跃订单：可记录 requestedQty，但不创建 originalQty 大于零、其余数量全零的守恒账本。

## 第 4 层：预留凭据必须证明什么，而不是只证明签名有效

**面试官：** 原意图只预留一次了。撮合怎样知道凭据不是拿另一笔小额预留来支持这笔大订单？

**面试者：** 凭据必须绑定 `intentId、reservationId、accountId、symbol、side、priceTicks、qtyLots、orderType、timeInForce、ruleVersion` 及不可变载荷摘要。买单还绑定预留 USDT 金额，卖单绑定 BTC 数量。只有余额、预留和意图事务提交后才能签发；签名或其他完整性证明只是防篡改，不能代替“确有已提交预留”这个前提。

撮合接入验证身份、载荷和金额相符，把验证依据固化进命令，再进入可靠 CommandLog。回放不能重新查询“账户现在还有多少钱”来改变历史裁决；新的余额可能已经包含后续业务。需要使用当时被接受、可恢复的验证依据。

本模型的凭据不因 TTL 自行失效。否则账户按时钟释放后，撮合仍可能按已提交 Place 成交。账户要撤销交易资格，必须走同序列关闭协议，而不能通过删预留记录或让签名过期绕过撮合。

## 第 5 层：预留成功后提交超时，为什么不能恢复可用余额

**面试官：** 既然凭据不会自己失效，Place 提交超时岂不是会一直占资？怎样既能恢复，又不重复撮合？

**面试者：** 超时只是没拿到响应，不能证明命令未提交。账户在预留事务里留下持久待提交状态，恢复提交器可以按原意图查询、重投；只有 CommandLog 已经多数派提交，才能承诺可靠受理。失去多数派时不能把内存排队当受理成功，更不能据此决定退款。

每个市场的 `commandSeq` 是连续逻辑命令位置，不是混合日志的物理 logIndex。重投可能获得新的 `commandSeq`。这不等于新业务：撮合在该位置按原请求键、载荷和意图做持久业务去重，返回原结果引用，并提交不含新增成交、占资或退款动作的空效果 ResultBatch，照样连续推进 `AppliedSeq`。不能因去重就跳过该位置，留下账户消费缺口。

需要结束占资时，恢复任务提交绑定原身份的 `AbortIntent`。它解决“未来是否还能执行”，而不是仅查询“现在看没看到”。超时可以触发关闭申请，但不能直接触发资金释放。

## 第 6 层：关闭与迟到下单怎样形成唯一裁决

**面试官：** 你把退款变成 AbortIntent，但它和迟到 Place 同时发生时，哪一个能决定预留还有效？

**面试者：** 由市场权威序列决定。Place、Cancel、AbortIntent 都进同一个 CommandLog，单写者只处理已提交输入。AbortIntent 先到且意图尚未接纳，就在该命令的完整结果里持久化关闭标记；迟到 Place 即使携带原来合法的凭据，也必须因意图已关闭而拒绝。

如果 Place 先到，它可能已经成交或挂单。后到 AbortIntent 只能撤销当时剩余量，保留已有成交义务；全成时可退剩余量为零。结果批次连同新 `AppliedSeq` 原子提交后才可发布，不能先让账户退款，再补写关闭事实。

账户本地的 `CLOSING` 只表示正在申请，不是资格已经失效。关闭标记必须进入恢复状态，不能按短 TTL 删除。普通 Cancel 查不到订单也不自动等于持久关闭意图；这里专门用 AbortIntent 封住尚未接纳的 Place，账户据其确定结果按序处理。

## 第 7 层：交易资格关闭后，为什么也不能直接清空预留

**面试官：** 已拿到确定结果，账户到底释放多少？用 B1 说明，再解释部分成交后撤单的区别。

**面试者：** 要区分已成交支出、成交价差和取消量，而不是看到终态就全部解冻。B1 买 0.25 BTC、限价 60,100，预留 15,025 USDT，甲可用先降到 4,975。与 S1 成交 0.10@60,000 支出 6,000，与 S2 成交 0.15@60,100 支出 9,015，共支出 15,015，返还价差 10；账务完成后甲有 4,985 USDT 和 0.25 BTC，S2 仍预留 0.05 BTC。

计算使用整数：价格 tick 为 0.01 USDT/BTC，数量 lot 为 0.0001 BTC，quote unit 为 0.000001 USDT，所以 `quoteUnits = priceTicks × qtyLots`。B1 是 `6,010,000 × 2,500`；相乘和累计金额之前都检查 int64 溢出，不能先溢出再比较。

独立变体 B2 只把买价改为 60,000，初始预留 15,000。成交 0.10 支出 6,000，剩余 0.15 仍占 9,000，可用为 5,000；在没有新成交的情况下撤掉余量，再释放 9,000，可用才是 14,000。不能沿用 B1 的 10 USDT 价差，也不能撤单时退回已支付的 6,000。

## 第 8 层：把确定结果变成资金变化时，怎样封住最后的失败窗口

**面试官：** B2 撤单结果先送达，前面的成交批次还没处理，账户如果按你算的余额退款，会不会仍然错？

**面试者：** 会，所以退款还受账户消费顺序约束。消费者先锁 `symbol` 的进度记录，只处理 `lastAppliedSeq + 1` 的完整批次；缺前序就补齐等待。先应用成交、再应用关闭，不拿撮合最新 `leavesQty` 直接覆盖旧账务位置的预留。撮合领先时，预留里还含未结转成交义务，不能只保留挂单金额。

完整批次的买卖双方资产、分录、预留处置、批次去重与消费进度在同一数据库事务中提交。中途失败全部回滚，原预留仍在；提交后确认丢失，重投只返回已处理结果。确定拒绝可生成释放动作，但只能释放该意图尚未消费、尚未释放的余额；关闭已退款后迟到 Place 的拒绝不能再退一次。

如果资金不足拒绝发生在预留事务之前，就根本没有预留可退。结果暂未查明则继续保留预留并恢复协议。这些路径分别回答“没有拿到资格”“拿到资格但未定”“资格确定关闭”，不能都用一个失败回调退款。

**本题收束**

- **讲透的机制：** 数据库事务保护共享余额，请求唯一身份防重复占资，预留绑定不可变意图，同序列关闭撤销未来执行资格，账户按完整结果顺序结转和退款。
- **易错边界：** 单市场串行不保护跨市场余额；超时、查询缺失、TTL 和订单终态都不是单独的解冻依据；账务落后时不能用最新剩余量覆盖预留。
- **反例验证：** 手工推演“预留完成→Place 超时→AbortIntent 先提交→账户退款→原 Place 迟到”。迟到 Place 必须被拒绝，且拒绝批次不能再次退款；若能成交或二次释放，说明资格或预留去重仍有漏洞。这里只做机制推演，不声称执行过故障测试。
