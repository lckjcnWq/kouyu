# 大问题 5：部分成交、撤单和新成交竞争时，怎样得到唯一订单终态？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 撤单不是“当这张单从没发生过”，而是停止轮到撤单时尚未成交的部分。本文采用零费链下现货、限价 GTC；状态名必须配合数量和已提交结果解释，不能只看页面上的“已撤”。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 生命周期 / 状态机 | 一张订单从接纳到结束允许经历哪些变化。 | 已结束不能重新挂回去，部分成交后取消仍保留原成交历史。 |
| originalQty / cumFilledQty | 已接纳订单最初总量，以及累计真正成交的量。 | B2 原始买 0.25，后来撤单也不能把已成交 0.10 清零。 |
| leavesQty / canceledQty | 仍可成交的量，以及已经取消、不再参与成交的量。 | 原始量等于已成交、剩余、取消三者之和，且每项非负。 |
| NEW / PARTIALLY_FILLED | 没成交但还有效，以及成交过一部分且还有剩余。 | B2 买到 0.10、还挂 0.15 时是部分成交。 |
| FILLED / CANCELED / 终态 | 全量已成交，或余量已取消；终态没有可继续成交量。 | CANCELED 不表示零成交，FILLED 也不表示账务已完成。 |
| REJECTED / requestedQty | 未合法接纳的拒绝结果及原请求想交易的量。 | 本文拒绝意图不进入活跃订单数量公式，不能伪造不守恒订单。 |
| Place / Cancel / AbortIntent | 下单、撤已有订单，以及关闭原下单意图。 | Cancel 未找到没有封住未来下单，AbortIntent 才能阻断迟到 Place。 |
| commandSeq / 单写者 | 市场里的逻辑排号和唯一有效执行者。 | 成交与撤单争同一份剩余量，按队列先后，不比较谁喊得更急。 |
| cancelRequestStatus / PENDING | 撤单请求自身的处理进度，PENDING 表示还在等裁决。 | 请求受理不直接把订单执行状态变成 CANCELED。 |
| canceledQtyDelta / orderVersion | 本次真正新增的取消量，以及订单状态版本。 | 新成交先到后，本次能撤的量会减少；旧回报不能覆盖新终态。 |
| prioritySeq / 幂等 | 首次合法接纳顺序，以及同次请求重复来不重复生效。 | 重试不能重新排队、再次取消同一数量或再次退款。 |
| ResultBatch / AppliedSeq | 整条命令的结果和已提交执行进度。 | 临时从链表摘掉节点不算已撤，完整结果提交才算数。 |
| intentId / reservationId / 关闭标记 | 交易意图、预留的身份，以及以后不可再接纳的事实。 | 标记要可持久恢复，不能重启或 TTL 清理后让原单复活。 |
| 预留 / 结转 / lastAppliedSeq | 占住资产、落实成交资金变化，以及账户连续处理到的位置。 | 撤单结果先送到，也要先补前序成交，不能因剩余为零就全退。 |
| tick / lot / quote unit | 精确表达单价、数量和 USDT 金额的整数单位。 | 退款取限价乘实际取消量，范围检查在运算前完成。 |
| 只读投影 / 快照重放 | 供展示的状态副本，以及从历史恢复权威状态的方法。 | 页面不能回写成交；恢复必须保留数量、终态、去重和关闭信息。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，提交 B2：限价 60,000 买 0.25 BTC，预留 15,000。卖盘里只有乙的 0.10@60,000 能匹配，另一档 60,100 太贵，不能买。先成交 0.10、花 6,000，剩余 0.15 继续挂着并占 9,000。甲现在发撤单，意思只是“不要再买剩下的”，不是把已经买到的 0.10 也倒回去。

此时另一账户又来卖 0.04 BTC，单价 60,000，资产已预留。假如这笔新卖单的命令先执行，甲累计买到 0.14，撤单只能取消 0.11；若撤单先执行，就取消全部余量 0.15，新卖单不能再碰它。两种结果都可能合法，但每一种都必须满足 `0.25 = 已成交 + 剩余 + 已取消`。新卖单先到的路径最终是 `0.25 = 0.14 + 0 + 0.11`，不是两边各自再用一次 0.15。

入口只能先告诉甲“撤单请求已受理”，等整包撤单结果提交后，才报告实际取消量和终态。在没有那笔新成交的路径中，账户先结转 6,000，再释放 9,000，甲最终有 14,000 USDT 和 0.10 BTC。即使页面已经显示 CANCELED，也不能把最初 15,000 全退；运输层先送来撤单结果时，要等前面的成交补齐。重复撤单或重复结果都不能产生第二次退款。

还有一个容易误解的场景：甲连订单都没查到就要求放弃。普通 Cancel 未找到，只说明那个位置上没有现存订单，迟到 Place 以后仍可能到。要真正结束原意图，必须用 AbortIntent 在同一队列里留下持久关闭标记：先关闭就拒绝迟到下单，先下单就只撤真实剩余。重启要恢复这个标记、原优先级和去重记录；迟到的旧回报只能被版本规则挡住，不能把终态重新变成活跃订单。

[返回专题总览](README.md)

**流程位置与核心机制：** 从订单合法接纳开始，追踪成交、撤单、意图关闭和终态回报，重点是数量守恒、同序列裁决、不可逆的终态以及与资金释放的边界。它不替代请求幂等或故障恢复专题，但必须说明这些机制如何保护生命周期。

**必要前提：** 沿用总览的 BTC/USDT 链下托管现货 CLOB、限价 GTC、maker 成交价、零费、不同账户和单交易对单写者。Place、Cancel、AbortIntent 共用权威命令序列。B2 是独立变体：只把 B1 买价改为 60,000，其余初始条件不变；后文的新对手单是该变体之后另行说明的竞争输入，不回写原案例。

## 第 1 层：先用数量定义状态，而不是只画状态箭头

**面试官：** 部分成交后撤单，该订单究竟算成交还是取消？怎样定义不会互相矛盾的生命周期？

**面试者：** 我会把执行状态和数量一起定义。合法接纳的订单满足 `originalQty = cumFilledQty + leavesQty + canceledQty`，右侧都非负。无成交且有剩余是 NEW；有成交且有剩余是 PARTIALLY_FILLED；全部原始量成交是 FILLED；剩余被取消后是 CANCELED，即使它之前已经部分成交，也必须保留累计成交量。

终态的关键是 `leavesQty = 0` 且不能重新入簿，不是把历史字段清零。订单执行状态和账务状态分开，FILLED 仍可能对应结转 PENDING，不能据此取消已经形成的支付义务。

这里约定 REJECTED 是未被合法接纳的意图处理结果，只记入请求或意图结果记录，不进入活跃订单数量账本。它可展示请求的数量，但应标明为 `requestedQty`，不拿它冒充参与上述公式的 `originalQty`。不能保存“原始量大于零、其他三项全零”再声称守恒。

## 第 2 层：把守恒公式落实到一次部分成交和撤单

**面试官：** 你要求保留历史数量，具体需要哪些字段？用 B2 说明每一步改什么，不能只报一个 CANCELED 标签。

**面试者：** 撮合权威订单至少有 `orderId、intentId、accountId、symbol、side、priceTicks、originalQty、cumFilledQty、leavesQty、canceledQty、prioritySeq、version`。账户预留身份绑定原意图，不能由撤单接口重新猜。每次确定变化增加版本，终态保留原数量和累计成交。

B2 买 0.25 BTC、限价 60,000，预留 15,000 USDT。与 S1 成交 0.10 后，累计成交 0.10、剩余 0.15、取消零；S2 的 60,100 超出买价，不能继续吃。撤单处理时读取当前剩余 0.15，把它加入取消量并把剩余置零，再从买侧队列与订单节点索引移除，状态为 CANCELED。

此时 `0.25 = 0.10 + 0 + 0.15`。订单历史表保留记录，不能因移除活跃节点就变成“查无此单”；否则后续重试无法分辨已撤、全成与从未存在。

## 第 3 层：成交与撤单都想消耗剩余量，谁先取得它

**面试官：** 你刚才取消了 0.15。假设此时又来一笔可成交卖单，撤单和成交是否可能各自用掉这 0.15？

**面试者：** 不允许两个线程各读一次剩余量再分别更新。新卖单的 Place 和 B2 的 Cancel 都进入同一个市场 CommandLog，先多数派提交，再由唯一有效写入者按连续 `commandSeq` 执行。Cancel 处理的是轮到它时的真实剩余，不是客户端提交撤单时看到的数量。

在 B2 已部分成交的状态下，另来一笔不同账户、BTC 已预留的卖单 0.04@60,000。若它的 Place 先执行，B2 累计成交变为 0.14、剩余 0.11，后续 Cancel 只取消 0.11。若 Cancel 先执行，就先取消全部余量 0.15，新卖单不能再成交 B2。

这是两个合法的先后结果，不存在一个脱离序列的“绝对同时”。网关接收时间、客户端时间和 goroutine 抢锁先后都不能取代已经约定的权威位置。

## 第 4 层：撤单请求已受理，为什么订单仍可能成交

**面试官：** 顺序能裁决竞争，但用户已经拿到撤单成功响应后又收到成交，会不会违反你的状态机？

**面试者：** 要先问响应承诺什么。Cancel 进入多数派已提交日志，只能响应“撤单请求可靠受理”，带请求身份和 `commandSeq`，不能提前承诺已取消。网关可以显示独立的 `cancelRequestStatus = PENDING`，但不能把权威执行状态直接改成 CANCELED，也不能冻结引擎中的剩余量。

等 Cancel 的完整结果提交，才返回 `canceledQtyDelta、cumFilledQty、leavesQty、orderVersion` 和实际终态。如果前序 Place 已让 B2 全成，Cancel 返回已全成、取消增量为零，绝不把 FILLED 改写成 CANCELED。部分成交后撤单则保留累计成交。

通知可能在网络中乱序，客户端要按订单版本应用更新，旧的 PARTIALLY_FILLED 不能覆盖新的终态。即使采用同步等待接口，等待超时也只是撤单结果未知，不能当作已经取消后立刻退款。

## 第 5 层：查不到订单的撤单，能否封住未来的下单

**面试官：** 用户还没查到订单就要撤，Cancel 先执行后返回不存在，迟到 Place 又把订单挂出来，怎么解释？

**面试者：** 这暴露了“撤已存在订单”和“关闭下单意图”的差别。本模型中，普通 Cancel 以账户、交易对和订单为目标，找不到订单就返回该命令位置上的明确未找到结果，不默认替尚未接纳的意图创建关闭标记。因此它不能单独证明未来 Place 永远不会到达。

如果账户已经完成预留，而 Place 受理不确定，需要提交 `AbortIntent`，绑定原 `intentId、reservationId、accountId、symbol`，由有权关闭该意图的流程发起。账户可标记关闭处理中，但不能因 Cancel 未找到或查询暂缺就释放预留。

普通 Cancel 的权限也要检查订单归属。请求键中的账户不是任意传入参数，而是鉴权主体；其他账户不能靠知道 orderId 撤单。不存在、越权和已终态的响应可以按产品规则处理披露，但都不能产生未经授权的状态变化。

## 第 6 层：关闭意图与迟到 Place 怎样只留下一个终局

**面试官：** 你增加了 AbortIntent，它和 Place 本身也竞争。谁来保证一边退款，另一边不会继续成交？

**面试者：** 两者仍由同一序列裁决，不在账户域另设一个能抢先退款的终态。AbortIntent 先执行且尚未接纳订单，就把意图关闭标记放入其完整 ResultBatch；结果提交后，迟到 Place 即使持有签名正确的原预留凭据，也必须拒绝。凭据本身不因 TTL 失效，真正阻断执行的是持久关闭事实。

如果 Place 先执行，AbortIntent 只能撤掉当时剩余量，不能删除先前成交；全成时只返回终态与已有义务。若 Place 已经得到确定拒绝，也保持原拒绝和关闭依据，不另造一张可成交订单。

关闭后的迟到 Place 拒绝仍应有结果位置，但不能再次产生退款动作。退款归属于预留的一次有效处置；已有关闭释放后，拒绝只是重申不能接纳。否则虽没有重复成交，仍可能重复增加可用余额。

## 第 7 层：命令重新投递，怎样不重复入簿或取消

**面试官：** 你依赖序列，但提交器超时重发同一个 Place 或 Cancel，又获得一个新 commandSeq，怎么不让终态变化第二次？

**面试者：** `commandSeq` 是每市场连续的逻辑命令处理位置，不是混合日志的物理 logIndex，也不是业务请求身份。请求键使用 `accountId + commandType + clientRequestId`，规范载荷包括目标身份和对应业务参数；同键同载荷返回原结果，同键不同载荷冲突。Place 的意图与预留绑定也必须唯一，不能换一个请求键就复用原预留再建订单。

如果重复投递拿到新序号，单写者在新位置做业务去重，生成无新增订单、成交、取消或退款动作的空效果批次，引用原裁决，仍推进 `AppliedSeq`。不能直接丢掉新位置让下游的连续消费永远等不到结果，也不能给原订单重新分配 `prioritySeq` 插回队尾。

Cancel 换新请求键属于新命令，但目标若已终态，取消增量仍为零，终态不变。业务去重保护同一次请求，终态和数量约束还要保护不同请求反复操作同一个订单，两者缺一不可。

## 第 8 层：取消节点后崩溃，终态到底是否已经成立

**面试官：** 去重规则完整了，但引擎已把 B2 从内存队列删掉，还没持久化撤单结果就崩溃，恢复后按什么算？

**面试者：** 按已提交结果算，不能以内存动作是否执行过为准。引擎从前序已提交状态形成临时变更集，把订单数量、节点移除、关闭标记、去重结果和预留处置依据组织为完整 ResultBatch，与新的 `AppliedSeq` 原子提交，且校验任期和预期前序位置，然后才安装状态并对外发布。

提交前崩溃，没有新的权威终态，恢复旧边界后重算该输入；提交后崩溃，恢复已提交结果，不再创造第二个取消。提交响应丢失时先按 `symbol + commandSeq` 查明是否提交，不能盲目进入下一命令。

同一 Place 触发多个成交时也一样，成交身份是 `symbol + commandSeq + matchIndex`，订单不能先持久化全成而成交只留下半份。发布路径只读已提交结果，避免用户看到恢复后不存在的撤单或成交。

## 第 9 层：订单终态已确定，怎样按序释放而不退掉成交款

**面试官：** 订单端可靠了。B2 已取消，但账户还没有结转它的前序成交，直接看到 leavesQty 为零就清空预留可以吗？

**面试者：** 不可以。初始 B2 占 15,000 USDT，在没有额外竞争成交的路径里，先结转 0.10 BTC 的 6,000 USDT 支出，保留余量对应的 9,000，再按 Cancel 释放这 9,000。甲可用先是 5,000，撤后为 14,000。若先前多成交了 0.04，则取消量仅 0.11，释放额应随确定数量变化，不能仍退 9,000。

消费者按市场 `lastAppliedSeq + 1` 取完整批次，缺前序就等待补齐；批次内双边资产、分录、去重和进度在同一数据库事务中提交。事务失败全部回滚，确认丢失重投不再记一次。即使运输先送来撤单，消费也不能越过成交义务。

单位固定为 price tick 0.01 USDT/BTC、qty lot 0.0001 BTC、quote unit 0.000001 USDT，退款等于限价 ticks 乘实际取消 lots。int64 乘法、累计金额以及各账户余额的加减都要先检查范围，不能先溢出再判断；小数展示或浮点计算不能决定取消数量与退款。

## 第 10 层：重启与旧回报为什么不能让终态复活

**面试官：** 你已经把终态和退款分开。重启、快照或迟到回报又到来时，怎样证明已经撤掉的数量不会再次进入订单簿？

**面试者：** 恢复状态必须包含订单数量和版本、原接纳优先序、请求去重、意图关闭标记、规则版本和结果位置，不只是活跃价位列表。先恢复快照，再应用后续已提交结果；只有已提交输入尚无结果的尾部才继续按序裁决。不能因订单不在活跃簿里，就清掉能识别终态和旧意图的持久信息。

终态不接受追加成交，关闭意图不接受新 Place，旧投影回报只能被版本规则忽略，不能回写撮合权威状态。关闭和去重记录也不能随意按 TTL 清理；若需要归档，必须另有持久机制保证旧请求永不重新取得资格。本题不假定这种清理机制已经存在。

手工核对时，不只看最终状态名，还要检查每一步数量非负、原始量守恒、终态不入簿、成交身份唯一，以及退款只对应实际取消和价差。安全结果可以暂时占资并等待恢复，但不能为了快速展示“已撤”而让同一数量既成交又退款。

**本题收束**

- **讲透的机制：** 用数量定义生命周期，以权威序列裁决竞争，完整结果提交确定终态，业务去重与持久关闭防止复活，账户按序把结果转为资金变化。
- **易错边界：** 撤单受理不等于撤成；普通 Cancel 未找到不等于关闭意图；部分成交后取消不抹除成交；未接纳的 REJECTED 不套用活跃订单数量公式。
- **反例验证：** 分别推演新卖单先于 Cancel、Cancel 先于新卖单、AbortIntent 先于迟到 Place，再把每条请求重投到新序号。允许不同的确定先后结果，但不允许重复成交、二次退款、数量账不平或终态复活。这里只给出手工验证条件，没有运行工程或测试。
