## 先看懂：关键词大白话解释

> 这篇不是只教“怎样把买单和卖单配上”，而是解释配上之后怎样不丢成交、不花两次钱、故障后仍认同一本账。基线是链下托管现货、限价 GTC、零手续费；下面的金额和规则仅用于本文教学模型。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| BTC / USDT / 交易对 | BTC 是买卖的资产；USDT 是报价和支付用的稳定币，不是无风险现金。 | BTC/USDT 的价格 60,100，表示每 1 BTC 要价 60,100 USDT。 |
| 现货 / 链下托管 | 现货是实际买卖资产；链下托管是在平台内部账户记录归属。 | 甲买入后内部账户增加 BTC，不表示每次成交都在链上转币。 |
| CLOB / 订单簿 | CLOB 是中央限价订单簿：把未成交买卖单按规则排起来等对手。 | 买方找最低卖价，卖方找最高买价，不是 AMM 资金池报价。 |
| 限价 / GTC | 限价划定能接受的单价；GTC 表示剩余订单继续有效，直到成交或取消。 | 买价 60,100 是最高可付单价，不是每笔必须支付的价格。 |
| maker / taker | maker 是原本挂在簿里的订单，taker 是新来与它成交的订单。 | 本文按 maker 的挂单价成交，B1 先按 60,000 买到 S1。 |
| 价格优先 / FIFO | 先选更划算的对手价，同价再按先入先出的队列选。 | 同价的“先”取首次合法接纳顺序，不比客户端时钟。 |
| 可用 / 预留 reservation | 可用是还能花的钱；预留是为某个交易意图占住、不能另花的钱。 | 买 B1 先占 15,025 USDT，钱还没交给卖方。 |
| intentId / reservationId | 分别是一次下单意图和它那份预留的编号。 | 预留绑定账户、交易对和不可变订单内容，不能挪给另一张单。 |
| clientRequestId / 幂等 | 请求编号用来辨认是不是同一次操作；幂等表示重复请求不重复生效。 | 同账户、同操作类型、同编号还要比较内容；改数量不是原请求重试。 |
| CommandLog / commandSeq | 前者是可靠保存的命令队列，后者是某交易对内的逻辑排号。 | Place 下单、Cancel 撤单、AbortIntent 关闭意图按同一顺序裁决。 |
| ACCEPTED / 可靠受理 | 命令已进入故障后能继续处理的范围。 | 不是“肯定成交”，甚至不保证一定合法挂上订单簿。 |
| 单写者 / actor / goroutine | 一个市场只有一个有效负责人改订单簿；goroutine 是 Go 的并发执行单元。 | 入口可以并发，订单簿不能由多个请求线程各改一份剩余量。 |
| ResultBatch / AppliedSeq | 一条命令产生的整包结果，以及撮合结果已提交到的位置。 | 两笔成交、订单变化和处理进度一起提交，不能只留下半次撮合。 |
| 原子提交 / 本地事务 | 一组变化要么一起成立，要么都不成立；本地事务只覆盖同一事务数据库。 | 撮合结果提交和账户结转是不同边界，不是全系统一次提交。 |
| originalQty / cumFilledQty / leavesQty / canceledQty | 分别是已接纳订单的原始量、累计成交量、仍可成交量和取消量。 | 原始量等于后三项之和；撤单不把已成交量清零。 |
| AbortIntent / 关闭屏障 | 把“这次下单以后也不能再执行”变成持久事实。 | 它先于 Place 执行就挡住迟到下单；普通撤单未找到没有这个保证。 |
| 结转 / PENDING / APPLIED | 结转是把已确定成交落实成正式资产变化；后两者表示待处理和已处理。 | 订单 FILLED 全成时，账务仍可以 PENDING，但成交款不能先退掉。 |
| 至少一次交付 / 去重 | 允许同一结果送到多次，由收方识别并只记一次账。 | 双边余额、分录、去重和消费进度同事务提交，不靠消息确认猜是否扣过款。 |
| lastAppliedSeq / 水位 | 表示账户已经连续处理到哪条市场结果。 | 后来的撤单退款不能越过尚未入账的前序成交。 |
| 投影 / 私有回报 / 公共行情 | 投影是从权威结果复制出的读视图；私有回报通知本人，行情展示市场。 | 页面旧了不等于成交没发生，查询缓存不能决定资金解冻。 |
| tick / lot / quote unit | 价格、数量和报价币金额各自的整数刻度。 | 本文依次为 0.01 USDT/BTC、0.0001 BTC、0.000001 USDT，整数相乘恰好换算。 |
| 快照 / 重放 / ruleVersion | 保存某个已提交位置的完整状态，再按历史结果恢复；规则版本固定当时算法。 | 不能用今天的新规则重新裁决昨天已经成立的成交。 |
| 多数派提交 / epoch / fencing | 多数派可靠确认；epoch 是负责人代次；fencing 是阻止旧负责人写入的围栏。 | 不是只改一个“我是主节点”变量，存储必须拒绝旧代次的新结果。 |
| 背压 / 尾延迟 | 忙不过来时限制入口；尾延迟看最慢那部分请求等了多久。 | 队列不能无限加大，撤单和账务积压都需要保护。 |
| MVP / 不变量 | MVP 是最小演示；不变量是无论正常还是故障都不能破坏的约束。 | 本文内存模型只供推演，不能证明生产主备、恢复和性能已经通过测试。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，想最多按每 BTC 60,100 USDT 买入 0.25 BTC。卖盘里，乙挂着 0.10 BTC，单价 60,000；丙挂着 0.20 BTC，单价 60,100，两人的卖出 BTC 都已预留。系统先检查甲的请求，把最多可能花的 `60,100 × 0.25 = 15,025 USDT` 从可用挪到预留，留下 4,975 可用。这是占住购买资格，不是甲已经付钱，更不是已经买到币。

下单命令可靠排入该市场的队列后，撮合负责人按顺序处理：先买乙的 0.10，花 6,000；再买丙的 0.15，花 9,015。甲全买到了，丙还剩 0.05 继续挂单。引擎必须先把两笔成交及相关订单变化作为完整批次提交，才能说这些成交成立，不能内存算出第一笔就宣布整单成功。

随后账户在同一个数据库事务中处理买卖双方资产，支付合计 15,015，返还多预留的 10。甲最终有 4,985 USDT 和 0.25 BTC；乙得到 6,000 USDT，丙得到 9,015 USDT，并继续预留未卖出的 0.05 BTC。10 是没花出去的限价差额，不是交易利润。成交已经成立但账户暂未处理时，可以告诉甲“已全成、待结转”，不能把 15,025 先全部恢复成可用。

如果中途响应丢失，甲用原请求编号查和重试，不新占一份钱。如果要放弃一笔结果未知的下单，就把关闭意图命令排进同一序列：它先到则封住迟到下单，下单先到则保留已有成交、只撤实际剩余。账户先结转成交，再退可退部分；重复送来的批次不再改一次钱。崩溃后也从已提交结果恢复，旧主不能再提交新事实，查询和行情只是跟随这些事实更新。

整篇后续问答分别检查这条链的薄弱点：怎样排队、怎样撤单、怎样重试、怎样补交结果、怎样重启和换主，以及太忙时怎样限流。最后的内存 MVP 只把业务数量和金额串起来，便于手算；它没有实现前面那些持久化与故障协议，不能把“故事算通了”当成“生产系统测过了”。

## 第一部分：文字全流程

### 1.1 先确定讨论基线

本篇讨论**链下托管账户、链下撮合、链下账务结转的现货中央限价订单簿**。

| 项目 | 本篇约定 |
|---|---|
| 产品 | BTC/USDT 现货，不加杠杆，不涉及持仓和强平 |
| 订单类型 | 仅限价 GTC：可成交部分立即成交，剩余量持续挂单，直到成交或撤单 |
| 撮合规则 | 价格优先，同价按撮合系统确定的接纳顺序优先；成交价取已有挂单的价格 |
| 状态分工 | 撮合域决定订单与成交；账户域决定可用、预留与账务分录 |
| 执行方式 | 每个交易对只有一个有效写入者，按已提交命令顺序裁决 |
| 资金要求 | 买单预留限价乘数量对应的 USDT；卖单预留卖出数量对应的 BTC |
| 费用 | 为突出核心机制，手续费设为零；有手续费时必须补充费用币种、费率版本和预留规则 |
| 链上范围 | 充值、提现、交易广播、确认和重组不在本篇范围内；不能把本篇“记账完成”解释为链上最终确认 |
| 本例账户 | 买卖双方是不同账户；不把尚未定义的自成交保护策略算作已支持能力 |

市价单、IOC、FOK、AMM、永续合约都是改变条件后的扩展，不能在回答中悄悄切换到这些模型。

**准备条件：** 只需能手工维护订单簿和资产表，不需要安装 Go、数据库或消息队列。生产架构用于解释职责和故障窗口，最后的 MVP 不实现这些基础设施。

### 1.2 一笔贯穿全文的订单

交易前，订单簿中已经有两笔合法挂单，其卖出资产已完成预留：

| 订单 | 账户 | 方向 | 限价 | 初始挂单量 | 已预留资产 |
|---|---|---|---:|---:|---:|
| S1 | 乙 | 卖 | 60,000 USDT/BTC | 0.10 BTC | 0.10 BTC |
| S2 | 丙 | 卖 | 60,100 USDT/BTC | 0.20 BTC | 0.20 BTC |

账户甲有 **20,000 USDT 可用余额、0 BTC**。现在提交：

```text
订单 B1
账户：甲
交易对：BTC/USDT
方向：买
限价：60,100 USDT/BTC
数量：0.25 BTC
clientOrderId：buy-001
```

预期成交：

```text
B1 与 S1 成交：0.10 BTC × 60,000 = 6,000 USDT
B1 与 S2 成交：0.15 BTC × 60,100 = 9,015 USDT

B1 累计成交：0.25 BTC
实际支出：15,015 USDT
初始预留：0.25 × 60,100 = 15,025 USDT
价差返还：15,025 - 15,015 = 10 USDT

最终订单簿：仅剩 S2，卖价 60,100，剩余 0.05 BTC
```

这里的 10 USDT 是限价预留与实际支出的差额，不是凭空产生的收益。

### 1.3 主链路：从点击下单到资金处理完成

```text
甲提交 B1〔账户、交易对、方向、限价、数量、clientOrderId〕
    ↓
接入层
    鉴权、参数校验、精度检查、请求身份与载荷检查
    ├─ 非法 → 返回拒绝，不预留、不撮合
    └─ 合法
         ↓
账户域：在一个本地事务中创建下单意图与预留
    甲 USDT：可用 20,000 → 4,975
             预留      0 → 15,025
    固化 reservationId 与订单载荷的绑定
         ↓
提交器：把 Place(B1, reservationId) 送入该交易对的可靠命令日志
    日志提交后获得 commandSeq
    “可靠受理”只表示命令已进入可恢复处理范围，不表示成交
         ↓
撮合域：按 commandSeq 处理已提交命令
    验证预留凭据、订单身份、是否被提前关闭
    按价格时间优先计算两笔成交与全部订单变化
         ↓
原子提交本命令的 ResultBatch 与新的 AppliedSeq
    包含：成交、订单变化、预留处置依据、事件身份
    只有提交成功，才把这次计算作为权威撮合结果
         ↓
已提交的结果向外分发
    ├─ 私有回报：甲看到 B1 已全成，settlementStatus = PENDING
    ├─ 公共行情：发布两笔成交与盘口变化
    └─ 账户消费者：按该交易对的结果顺序处理完整批次
                             ↓
                       一个本地账务事务
                       扣买方预留、给卖方入账
                       扣卖方预留、给买方入账
                       返还价差，处理确定可释放的预留
                       同时提交去重记录与消费进度
                             ↓
                       账务完成
                       B1 的结转状态为 APPLIED
                       查询投影最终追上相应版本
```

**主链路中有两个不同的提交边界：** 命令日志提交，保证已受理命令可恢复；结果批次提交，确立订单变化与成交事实。账户事务再把这些事实转成资产变化。三者不能合并成一句“下单成功”。

### 1.4 沿案例看清资产与订单变化

以下金额均为 USDT，BTC 另标单位；不计手续费。

| 时点 | 甲 USDT 可用 | 甲 USDT 预留 | 甲 BTC 可用 | 说明 |
|---|---:|---:|---:|---|
| 下单前 | 20,000 | 0 | 0 | 尚无 B1 预留 |
| 完成预留 | 4,975 | 15,025 | 0 | 有交易资格，不等于命令已受理 |
| 撮合结果已提交，账务尚未处理 | 4,975 | 15,025 | 0 | B1 已全成，但资产暂未结转；预留仍覆盖成交义务 |
| 完整批次账务事务提交 | 4,985 | 0 | 0.25 BTC | 支出 15,015，返还价差 10 |

账务完成后的其余状态：

- 乙收到 6,000 USDT；S1 累计成交 0.10 BTC，剩余量为零。
- 丙收到 9,015 USDT；S2 累计成交 0.15 BTC，仍预留 0.05 BTC，继续挂单。
- 本例账户集合的 USDT 总量仍为 20,000；BTC 总量仍为 0.30 BTC，包括丙剩余预留。
- B1「撮合全成」先于「账务完成」是允许的暂态；甲既能花掉成交所需预留，又能拿到买入 BTC，是禁止结果。

### 1.5 主要异常分支

#### 分支一：参数拒绝或余额不足

```text
精度、方向、数量等参数不合法
    → 接入拒绝 → 不进入预留与撮合

参数合法，但可用余额不足
    → 账户事务拒绝 → 不生成有效预留凭据 → 不提交有效 Place
```

#### 分支二：预留成功，但提交超时

```text
账户已预留 15,025 USDT
    ↓
Place 提交超时：不知道已提交、尚在传输，还是根本未提交
    ↓
按原 clientOrderId / intentId 查询与重试
    ├─ 查到权威结果 → 沿原意图继续，不重复预留
    └─ 用户要放弃，或系统需要关闭悬挂意图
         ↓
       向同一交易对日志提交 AbortIntent
         ↓
       撮合域按权威顺序关闭意图或撤掉实际剩余量
         ↓
       账户按已提交关闭结果及先前成交顺序处理，才释放可退部分
```

**不能因为一次查询“没有订单”，就按超时释放。** 原 Place 可能仍在路上。关闭必须让迟到 Place 失去执行资格，详见第 6 题。

#### 分支三：部分成交后撤单

这是一个独立变体：把 B1 的买入限价改为 **60,000**，其余初始状态不变。

```text
B2：买入 0.25 BTC，限价 60,000
    ↓
预留 15,000 USDT
    ↓
与 S1 成交 0.10 BTC，支出 6,000 USDT
    ↓
剩余 0.15 BTC 挂在买侧，仍需预留 9,000 USDT
    ↓
撤单命令与潜在的新成交进入同一条权威顺序
    ├─ 撤单先执行 → 撤掉 0.15 BTC → 释放 9,000 USDT
    └─ 新成交先执行 → 先扣除其成交量 → 只撤最终剩余量
```

这里不是“撤单接口调用成功就立刻退钱”，而是先知道到底撤掉多少。

#### 分支四：成交确定，账户结转失败

```text
ResultBatch 已提交，两笔成交成立
    ↓
账户事务执行失败或服务宕机
    ↓
整批事务回滚，原预留保留，消费进度不前移
    ↓
恢复后重试同一批次
    ├─ 尚未提交过 → 完整记账
    └─ 已提交但确认丢失 → 去重后返回原处理结果
```

不通过删除成交来修复记账失败，也不因为订单全成而先释放全部预留。

### 1.6 四种完成含义

| 阶段 | 可以承诺什么 | 不能承诺什么 |
|---|---|---|
| 预留成功 | 资产已经被原意图占用 | 命令一定进入撮合 |
| 可靠受理 | 命令已进入可恢复的权威处理范围 | 一定合法挂单、一定成交 |
| 撮合结果提交 | 成交与订单变化已确定，不能因下游失败随意撤销 | 账户和页面已经同步完成 |
| 账务事务提交 | 本批次资金变化及处理进度已原子生效 | 所有查询副本都已追上 |

## 第二部分：核心板块

不是每个服务都同样核心。先看谁决定成交，再看哪些环节使成交不会变成错账。

| 核心板块 | 决定什么 | 拥有的权威状态 | 上下游契约 |
|---|---|---|---|
| 下单意图与资产预留 | 这笔订单有没有足额、不可重复使用的交易资格 | 余额、预留、意图与载荷绑定 | 输出已持久化的预留凭据；不能凭超时自行撤销已可能执行的资格 |
| 命令接纳与排序 | 哪条命令先裁决，哪些请求算可靠受理 | 已提交命令、commandSeq、请求身份 | 只交给引擎已提交的命令；接纳与最终业务成功分开 |
| 撮合裁决与订单簿 | 与谁成交、成交多少、什么价格、剩余如何处理 | 订单执行状态、价位队列、关闭标记 | 单写者按序处理，原子提交完整结果；不直接随意修改账户余额 |
| 成交交付与账务结转 | 成交是否不丢不重地落实为资产变化 | 结果批次、账务分录、去重记录与消费进度 | 只消费已提交完整结果，按序在本地事务中结转 |
| 恢复与投影 | 崩溃后能否恢复同一事实，用户能否辨认数据新旧 | 日志位置、快照版本、查询投影进度 | 权威结果不能被缓存覆盖；投影落后必须可观察、可补齐 |

**最核心的局部算法是订单簿撮合；最核心的系统能力是让订单、成交、预留和账务共同闭环。** 只讲其中一侧，都不足以回答“撮合交易从 0 到 1”。

## 第四部分：设计与规则

这一部分只建立后续共同前提，详细论证留在连续问答中。

### 4.1 业务规则与不变量

#### 规则一：用整数表达价格、数量和资产

为了让本例所有乘法都精确：

- 价格单位：`0.01 USDT/BTC`，即 `priceTicks`。
- BTC 数量单位：`0.0001 BTC`，即 `qtyLots`。
- USDT 账务单位：`0.000001 USDT`，即 `quoteUnits`。
- 则 `quoteUnits = priceTicks × qtyLots`，没有隐含除法和舍入。

例如，60,100 USDT/BTC 对应 `6,010,000 ticks`，0.25 BTC 对应 `2,500 lots`，相乘得到 `15,025,000,000 quoteUnits`，即 15,025 USDT。

Go 实现可使用受业务上限约束的 `int64`；**先检查乘法溢出、价格和数量上限，以及余额加减与批次金额累计的范围，再预留**。API 十进制字符串直接按规则解析，不先转 `float64`。展示两位小数不代表账本只存两位。

#### 规则二：订单数量守恒

```text
originalQty = cumFilledQty + leavesQty + canceledQty

三个右侧分量均非负
撤单只增加 canceledQty，不回退 cumFilledQty
终态订单 leavesQty = 0，不能重新进入订单簿
```

已接纳订单的状态可以是 `NEW / PARTIALLY_FILLED / FILLED / CANCELED`，但标签不能代替数量字段。例如部分成交后撤单为 `CANCELED`，其累计成交仍保留。上面的数量公式作用于已接纳订单；准入失败的 `REJECTED` 是意图处理结果，不进入活跃订单数量账本。若产品要求为拒单也建完整数量记录，应另定义拒绝量并扩展公式，不能把原始量保留为正、其余分量全置零。

#### 规则三：每笔成交满足双边和资产约束

```text
买方成交 BTC 数量 = 卖方成交 BTC 数量 = tradeQty
买方支付 USDT = 卖方收到 USDT = tradePrice × tradeQty
每一资产的可用与预留余额均不得为负
在零手续费、无外部充提条件下，各资产总量不变
```

#### 规则四：预留不能早于交易资格关闭而释放

- Place 可能执行时，预留必须仍有效。
- 成交结果提交后，对应资金承担既成成交义务，不能按订单超时解冻。
- 终态只说明未来不再成交；已有成交仍要结转，不能拿“终态”跳过待处理结果。
- 已结转到相同结果位置时，活跃买单对应的剩余预留应为 `限价 × leavesQty`；卖单应为 `leavesQty`。
- 撮合领先于账务时，实际预留还包含未结转成交和待执行退款对应的部分，不能直接用最新 `leavesQty` 覆盖它。

#### 规则五：请求、订单、成交与账务有不同身份

```text
请求身份：accountId + commandType + clientRequestId
下单意图：intentId，绑定唯一 reservationId 与不可变订单载荷
订单身份：orderId
命令位置：symbol + commandSeq
结果批次：symbol + commandSeq
成交身份：symbol + commandSeq + matchIndex
```

同一请求身份、相同规范化载荷，返回原意图或原结果；同一身份、不同载荷，返回冲突。请求身份不是 TCP 连接号，成交身份也不是消费时重新生成的 UUID。

`commandSeq` 是每市场连续的逻辑命令序号，不是复制日志所有物理记录的 `logIndex`。结果记录不再占用一个命令序号。接入层可以提前返回缓存的持久结果；若重投仍进入日志并获得新命令位置，引擎按原请求/意图身份去重，为该新位置提交空效果结果和原结果引用，不再占资、撮合或生成另一组退款动作。后续消费者仍可连续推进。首次合法接纳的顺序才决定 FIFO，重试不能重新排队。

### 4.2 架构与职责

```text
客户端
    ↓
接入 / 订单接入服务
    ├─ 查询身份与载荷
    └─ 账户域〔共享资产数据库〕
           本地事务：余额 + 预留 + 下单意图
           持久化提交状态，由提交器重试投递
                     ↓
             每交易对复制日志服务
             已提交 CommandLog〔commandSeq〕
                     ↓
             每交易对撮合单写者〔epoch〕
             内存订单簿：已提交结果的执行状态副本
                     ↓
             复制日志中的 ResultBatch
             同一原子记录推进 AppliedSeq
                ├─ 按序投递 → 账户账务消费者
                │              本地事务：双边资产 + 分录 + 去重 + 进度
                ├─ 私有订单回报投影
                └─ 公共成交与盘口投影
```

本模型明确使用能提供**持久化多数派提交、顺序日志和任期隔离**的复制日志服务。日志服务拒绝旧 `epoch` 写入；对外确认可靠受理之前，命令必须已经提交。单机 `fsync` 只能覆盖相应单机故障假设，不能自动替代这里的主备保证。

`CommandLog` 与 `ResultBatch` 是两类记录，不假定它们在同一个事务里写完。引擎只处理已提交输入；一次结果追加必须校验当前 `epoch`、批次身份及预期的前序 `AppliedSeq`，并在一个原子记录中提交结果和新进度。前一次结果的提交状态没有查明前，不处理下一条命令。

计算结果可以先在临时变更集中形成，但不能把未提交的修改当作已生效结果对外发布。内存进程在中途崩溃，可以丢弃临时计算，从已提交边界恢复。

可靠命令日志固定的是已经受理的输入和顺序，不等于成交承诺；尚未提交的结果可能在恢复后按相同规则重算。结果一经提交，重投必须引用它。日志服务的任期隔离、条件追加和多数派提交是本模型显式依赖的能力，不把任意消息队列或一次磁盘写入假称为已经具备这些语义。

### 4.3 核心对象与交互

| 对象 | 必要字段 | 权威归属与用途 |
|---|---|---|
| 下单意图 | intentId、accountId、symbol、clientOrderId、payloadHash、reservationId、提交状态 | 账户域持久化，保证重试不重复占资；提交状态不是撮合终态 |
| 预留 | reservationId、intentId、asset、amount、不可变载荷绑定 | 账户域持有，凭据只在预留事务已提交后签发，不独立按 TTL 失效 |
| 命令 | commandSeq、commandType、intentId、orderId、载荷、预留凭据、ruleVersion | 撮合日志排序；Place、Cancel、AbortIntent 使用同一裁决序列 |
| 订单 | orderId、side、priceTicks、originalQty、cumFilledQty、leavesQty、canceledQty、prioritySeq、version | 撮合域决定执行状态，prioritySeq 来自首次合法接纳顺序 |
| 结果批次 | symbol、commandSeq、ruleVersion、trades、orderChanges、reservationActions、关闭与业务去重结果 | 撮合域原子提交；空成交批次也明确处理结果，便于连续推进 |
| 账务进度 | symbol、lastAppliedSeq、batchId、分录与处理结果 | 账户数据库中与资产变化同事务提交；不是单独依赖消息队列 offset |
| 投影 | orderVersion、lastAppliedSeq、settlementStatus | 查询与展示使用，不能反向裁决成交或解冻 |

预留凭据包含绑定字段与完整性证明，撮合接入验证后把验证依据随命令固化，回放不依赖“现在再查一次账户是否还有钱”。本模型不允许账户域在撮合未知的情况下先让凭据过期；需要关闭时使用有序的 `AbortIntent`。

`AbortIntent` 必须来自有权关闭该意图的内部流程，绑定原账户、交易对和预留身份。若意图尚未接纳，记录不可再接纳的关闭标记；若订单已经接纳，撤掉当时剩余量；若已全成，只返回终态和既有义务，不退已成交资金。

### 4.4 实现选择与边界

- **订单簿：** 买卖各一个有序价位索引，每个价位一个 FIFO 双向链表，再用 `orderId → 节点` 哈希索引定位撤单。价位索引操作约为 `O(log P)`，同价队首操作为 `O(1)`；撮合还与触及订单数有关，不能只说“整体 O(1)”。
- **Go 并发：** 每交易对 actor/goroutine 独占订单簿；入口与分发可并发，但不能用“所有请求都起 goroutine”替代裁决顺序。有界队列满时按约定拒绝或背压。
- **共享余额：** 账户域使用数据库条件更新或行锁；多条余额记录按固定顺序加锁，避免用进程内互斥锁覆盖跨实例、跨交易对竞争。
- **结果交付：** 从已提交结果日志按位置重投，允许至少一次交付；不要求引擎同时双写一个独立消息队列。若加消息中间件，它只是运输层，不成为第二个成交事实源。
- **账户结转：** 本教学模型把参与结转的账户放在同一事务数据库，完整命令批次在一个事务中处理。跨账务分片会改变原子边界，本专题不把它当成已经解决的能力。
- **查询与行情：** 都是结果的投影。回报可以先于记账，但必须表达所依据的阶段和版本；旧缓存不能作为资金释放依据。
- **恢复：** 快照包含订单簿、订单数量、去重与关闭标记、规则版本及结果位置。快照之后的已提交结果用于重建；对有已提交输入但没有已提交结果的尾部，才按固定规则继续执行。

## 第七部分：工程实践——一个简洁 MVP

### 7.1 目标与范围

用一个**串行、单进程、内存状态**的小模型验证：价格时间优先、限价预留、双边即时结转、价差退款、部分成交后撤单，以及相同请求重复提交不重复改变资产。

**不覆盖：** 持久化日志、异步结算、崩溃恢复、主备、跨进程并发和链上结算；因此不能用这个 MVP 证明前文生产可靠性协议已经实现。

MVP 把一次命令的状态变更放在临时副本中，成功后整体替换内存状态。它和前文生产方案共享业务规则，但有意把撮合与结转折叠为一步，便于看清最小闭环。

### 7.2 核心伪代码

下面全部使用第四部分的整数单位：价格为 ticks，BTC 为 lots，USDT 为 quoteUnits，`p × q` 直接得到 USDT 账务整数。`available` 与 `reserved` 都按账户、资产分别保存。

```text
处理(cmd):                                      // 仅由一个串行调用者执行
    key = (cmd.account, cmd.type, cmd.requestId)
    payload = 规范化载荷(cmd)                    // 十进制精确解析；拒绝非法精度
    若 key 已存在:
        若 已存载荷 != payload: 返回 请求身份冲突
        返回 已存结果                            // 不重复占资、成交或退款
    w = 复制全部内存状态()
    w.nextSeq += 1                              // 同时检查序号、余额与累计金额上限
    若 参数、数量或乘法上限检查失败:
        w.请求表[key] = (payload, 参数拒绝)
    否则若 cmd.type == PLACE:
        o = 新订单(id由key确定, cmd, priority=w.nextSeq, cum=0, leaves=cmd.qty, canceled=0)
        asset = 买单 ? USDT : BTC
        need = 买单 ? o.limit * o.leaves : o.leaves
        若 w.available[o.account, asset] < need:
            w.请求表[key] = (payload, 余额不足)
        否则:
            w.available[o.account, asset] -= need
            w.reserved[o.account, asset] += need
            当 o.leaves > 0 且存在与限价交叉的对手单:
                m = 最优对手价位的FIFO队首
                p = m.limit
                q = min(o.leaves, m.leaves)
                buy = o为买单 ? o : m
                sell = o为卖单 ? o : m
                w.reserved[buy.account, USDT] -= buy.limit * q
                w.available[buy.account, USDT] += (buy.limit - p) * q
                w.available[buy.account, BTC] += q
                w.reserved[sell.account, BTC] -= q
                w.available[sell.account, USDT] += p * q
                o.leaves -= q; o.cum += q
                m.leaves -= q; m.cum += q
                w.成交表追加(orderId双方, p, q, w.nextSeq, 匹配序号)
                若 m.leaves == 0: 从订单簿移除m，状态置为FILLED
                否则: m状态置为PARTIALLY_FILLED
            若 o.leaves > 0: 按价格及本地接纳序号入簿
            o状态 = leaves为0 ? FILLED : (cum大于0 ? PARTIALLY_FILLED : NEW)
            w.订单表[o.id] = o
            w.请求表[key] = (payload, 本次订单与成交结果)
    否则若 cmd.type == CANCEL:
        o = w.订单表[cmd.orderId]
        若 o不存在或不属于cmd.account:
            w.请求表[key] = (payload, 撤单拒绝)
        否则:
            q = o.leaves                         // 终态重复撤单时为0
            asset = o为买单 ? USDT : BTC
            refund = o为买单 ? o.limit * q : q
            w.reserved[o.account, asset] -= refund
            w.available[o.account, asset] += refund
            o.canceled += q; o.leaves = 0
            若 q > 0: 从订单簿移除o，状态置为CANCELED
            w.请求表[key] = (payload, 撤单结果及原终态)
    否则:
        w.请求表[key] = (payload, 不支持的命令)
    内存状态 = w                                // 本模型内整体生效，不是持久化提交
    返回 内存状态.请求表[key].结果
```

补充两条边界：非法载荷无法规范化时可直接拒绝且不改变业务状态；这里的重试只指进程存活期间，重启丢失内存请求表就不再具备持久幂等。订单节点与订单表在临时状态中引用同一订单对象，不能各存一份却只更新一份。

### 7.3 输入与预期结果

初始状态通过两笔合法卖单建立：乙有 0.10 BTC，提交 S1 后全部预留；丙有 0.20 BTC，提交 S2 后全部预留；甲仍有 20,000 USDT 可用。每个独立变体都从这个初始状态重新开始，只有明确说明的重复或撤单才接着前一步执行。

| 案例 | 输入 | 手工推演的预期结果 |
|---|---|---|
| A：正常全成 | 甲提交 B1：限价 60,100，买 0.25 BTC | 成交 0.10@60,000 与 0.15@60,100；甲 USDT 可用 4,985、预留 0，BTC 可用 0.25；S2 剩余 0.05 |
| B：相同请求重试 | 在 A 后，以相同 requestId、相同载荷重提 B1 | 返回 A 的原结果；不再占资，不再新增成交，资产不变 |
| C：请求身份冲突 | 在 A 后，复用 B1 的 requestId，但数量改为 0.20 BTC | 返回冲突，不把它当成新订单，资产和订单簿不变 |
| D：独立的部分成交变体 | 从初始状态提交 B2：限价 60,000，买 0.25 BTC | 只成交 S1 的 0.10；甲 USDT 可用 5,000、预留 9,000，BTC 可用 0.10；B2 剩余 0.15 |
| E：承接 D 撤单 | 用新的撤单 requestId 撤 B2，再重复相同撤单请求 | 首次释放 9,000；甲 USDT 可用 14,000、预留 0；B2 累计成交 0.10、取消 0.15；重复不再次退款 |
| F：独立的余额不足变体 | 初始条件仅改为甲可用 1,000 USDT，再提交 B1 | 预留失败，无成交，卖盘和全部资产不变 |
| G：独立的非法精度变体 | 从初始状态买 0.25005 BTC | 不符合 0.0001 BTC 数量单位，拒绝；不预留、不成交 |

**手工核对，不是测试报告：**

- A 中甲的 USDT：`20,000 - 6,000 - 9,015 = 4,985`。
- A 中全部 USDT：`4,985 + 6,000 + 9,015 = 20,000`。
- A 中全部 BTC：`甲 0.25 + 丙预留 0.05 = 0.30`。
- E 中 B2 数量：`原始 0.25 = 成交 0.10 + 取消 0.15 + 剩余 0`。
- B、C 和重复撤单不得新增资产变化；生产场景还需验证日志、重投与重启，不能从内存手算推导这些能力已通过测试。
