# 大问题 12：怎样提高吞吐、降低尾延迟，并在过载时保护撤单？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文讨论“整条交易流水线能长期稳定处理多少、挤爆时先保护什么”，不是给撮合函数跑一个好看的速度。案例仍是链下托管的 BTC/USDT 现货，限价 GTC、按先挂订单价格成交、零费用，市场单写，账户用同库双边事务结转。优化不能改变完整结果提交、权威命令顺序和先成交后退款这些边界。文中的容量、排队和优化判断都是设计方法；Go 讨论以 1.21+ 为前提，没有工程压测数据，也不把推演写成成绩。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 每市场单写者与 goroutine | 同一交易对由一个有效写入者裁决；goroutine 是 Go 的轻量并发执行单元。 | 一个 goroutine 独占可变订单簿；不同市场和独立阶段可并行，同一盘口不能简单多开几个写入者。 |
| 命令吞吐与成交吞吐 | 一秒接或处理多少条操作，与一秒产生多少笔成交，是两种工作量。 | 甲一条买单可产两笔成交，大扫单还会产更多结果和账务动作，比较性能须交代负载结构。 |
| 分位延迟与尾延迟 | 不只看平均耗时，还看慢到某个比例边界的请求。 | 如 p99 是第 99 百分位延迟，不是某个实测毫秒数；受理、撮合提交、结转和投影各段都要看等待与服务耗时。 |
| 单调时钟与关联追踪 | 单调时钟量本进程经过多久，追踪用业务身份把跨进程步骤串起来。 | 不能直接拿有偏差的机器墙钟相减；积压还看年龄和逻辑位置差，不只数队列里有几条。 |
| 到达模型与闭环施压 | 压测可以按设定速度送请求，也可以等上次完成再发。 | 只用后一种会在系统变慢时自动降低压力，容易遮住真实排队；还须固定成交率、撤单率、热点和对手单数。 |
| 有界 Go channel 与等待预算 | channel 是 Go 的传递队列，必须有容量和最长可接受等待约束。 | 扩容缓冲只能吸收短波动，不能让长期超出处理能力的流量消失，还会增加超时重试和占款。 |
| 背压与准入 | 下游来不及，就让上游少接新工作。 | 尽量在预留前拒绝过载新单；已预留、受理未知或已可靠受理的请求，要分别恢复、关闭或继续裁决，不能统一丢弃退款。 |
| `Place` / `Cancel` / `AbortIntent` | 新下单 / 撤已接纳订单 / 关闭原下单意图。 | 准入层为撤单和关闭留连接、队列与预算，对新单更早限流；保护通道仍要鉴权和限频。 |
| `commandSeq` 与 FIFO | 前者是权威命令逻辑号，FIFO 是 First In, First Out，即同价先来先成交。 | 撤单可在尚未分配权威位置前按公开策略调度，入日志后不得越过更早命令；逻辑号不是物理日志偏移。 |
| 热点迁移与 `epoch` 围栏 | 给热门市场换独占资源，并用新任期接替旧写入者。 | 要在已提交边界恢复，旧写权限由权威存储的任期校验挡住；不能两台同时做一会儿再合并盘口。 |
| 数据所有权与不可变副本 | 明确一个对象归谁改、何时能回收，交出去的结果不能再被改坏。 | 查询读独立投影；异步消费者仍引用的切片不能被下一次撮合复用，不能为省分配暴露半成品。 |
| `ResultBatch` 与提交未知 | 结果包包含一条命令的全部业务变化；回复超时不证明提交失败。 | 整包与撮合进度完整原子提交后才能发布；查不明前不推进下一命令，不能用低延迟掩盖缺失事实。 |
| CPU、GC 与性能剖析 | CPU 是处理器，GC 是 Garbage Collection，即垃圾回收；剖析找出时间和分配到底花在哪。 | 先查计算、分配和阻塞，再评估预分配、链表布局等优化，不凭感觉改数据结构。 |
| `sync.Pool` | Go 提供的临时对象复用池，不是可靠仓库。 | 池中对象可能被清掉，也不能在消费者仍使用时提前归还；对象生命周期优先于少分配一次。 |
| group commit | 多条记录共享一次持久化开销的组提交方式。 | 可研究传输或复制层合批，但每条命令的完整结果边界不变，真正提交后才确认，批大小和等待窗口都要有上限。 |
| 推测执行、CAS 与回滚 | 先在未提交状态上计算后续命令，就得额外处理整组进度竞争和失败恢复；CAS 是 Compare And Swap，即预期前值校验。 | 基线不跨越提交未知继续撮合；跨命令推测合批需要新增未提交状态层、批量校验和回滚协议，不是免费参数。 |
| GTC 与 FOK | GTC 是 Good Till Cancelled，即未成量持续挂单；FOK 是 Fill Or Kill，即立即全部成交，否则一笔不成。 | 本文基线是限价 GTC；FOK 仅作不可拆坏业务原子性的反例，不表示本基线已支持它。 |
| 账户进度与同库双边事务 | 账户按市场连续结果结转，整批买卖双方资产、分录、去重与进度同事务落地。 | 账务持续落后会积累预留和待结转义务；同库扩容有边界，不能靠拆成两边独立更新或先退钱来减压。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，下单买 0.25 BTC，限价 60,100，预留 15,025 USDT；成交会依次匹配 0.10 BTC、价格 60,000 和 0.15 BTC、价格 60,100。恰逢 BTC/USDT 流量突增，运维发现撮合函数看起来很快，用户却一直等。原因要沿整条链路查：从请求到可靠受理、从受理到完整结果提交、从结果到双边结转、从结果到页面可见，各段的排队与服务时间都不同。甲一条买单带来两笔成交，别人的大扫单可能带来很多笔，不能只拿“每秒订单数”评价容量。测量还要看尾延迟、积压年龄及位置差，压测不能因客户端等回复而自动降速，再把隐藏的排队当作不存在。

入口队列逐渐满了，盲目扩大 Go channel 只是把拒绝改成长时间等待，增加预留占款和超时重试。系统应限制队列与等待预算，尽量在预留前拒绝新的过载请求；甲若已预留但可靠受理状态未知，就沿原意图恢复或提交有序关闭，不能一见队列满便退款。已经可靠受理的命令也不能因等太久被扔掉。为了让用户还有退出风险的机会，准入层给撤单与关闭请求留独立预算、对新下单更早限流，但撤单一旦取得权威逻辑序号，就仍须排在所有前序命令之后执行，不能抢在已承诺更早的成交前面。

热点仍然很高，团队先给这个市场独占资源，把鉴权、其他市场和已提交结果的查询、行情处理等独立工作并行化，而不是按买卖方向或价格把同一订单簿随手拆给多个写入者。甲的一次撮合会跨两个价位，还与撤单竞争，拆分就需要重新设计跨片顺序与原子输出。真要迁移市场，先关闭旧写权限、在完整提交边界恢复，再让权威存储认可新任期，不能两台同时成交后再合并。Go 侧也由一个 goroutine 持有可变订单簿，交给异步分发的是不可变或独立所有权结果；先用处理器、分配与阻塞剖析找证据，再考虑预分配或对象池，不能复用仍被上一批消费者引用的切片。

日志成本高时，可以研究复制或传输层组提交，让多条记录摊薄持久化开销，但确认仍要等各记录真正提交，甲这条命令的两笔成交及相关变化仍是一个完整原子结果包。批量等待会增加低负载延迟，需要批大小和等待上限。前一结果提交超时未知时，基线仍停下查权威记录，不能为了凑批先撮合下一条；若另做跨命令推测执行，必须补上未提交状态、批量前序校验和回滚协议。面对大扫单，应在准入与版本化业务规则中规定可接纳资源边界，不能做到一半随意丢余量，更不能把需要全成或全撤的另一类订单拆成可见的部分成交。

最后瓶颈转移到账户数据库：撮合结果持续增长，账户连续进度越来越落后。系统必须按最老积压、未完成义务和预计恢复时间收紧新下单预算，保留结转、关闭与恢复资源；关闭退款仍不能越过旧成交，已经成立的成交也不能改成失败、丢结果或提前释放预留。甲的完整批次最终仍要在同库双边事务里只结转一次，支付 15,015 USDT、退回 10 USDT、得到 0.25 BTC，可用余额为 4,985 USDT。恢复能力必须高于受控新流量才追得上；若同库容量不足，要承认边界并另立跨片结算协议。只有相同负载下阶段延迟、积压与数量和资产守恒等一起核对，才能评价优化，而本文给的是测量及验收方法，没有任何已取得的吞吐或容量实测结论。

**流程位置与核心机制：** 本题覆盖整条交易链路的容量与运行约束。优化对象不是孤立的撮合循环，而是从预留、可靠受理、撮合结果提交到账务结转的可持续吞吐与延迟。

**必要前提：** 沿用限价 GTC、每交易对单写者、完整结果提交后发布的共同基线。以下均为设计方法，不提供虚构性能数字。Go 实现讨论以 Go 1.21+ 为前提，不生成可运行工程。

## 第 1 层：单写者的性能上限在哪里

**面试官：** 每交易对只有一个撮合写入者，吞吐会不会很差？你会怎样优化整个系统？

**面试者：** 单写者限制了一个市场的串行裁决能力，但也避免了订单簿多写者锁竞争，使价格时间优先和撤单顺序容易成立。我会先保留这个正确性边界，再把独立工作并行化：不同交易对独立执行，接入鉴权与格式校验并行，已提交结果的查询、行情投影和账户处理在各自边界运行。

真正的端到端吞吐由最慢的可持续阶段限制。撮合循环很快，但结果日志提交慢，或者账户结转积压，系统仍然无法持续接单。所以第一步不是宣称单线程能跑多少，而是测量每阶段服务时间、排队时间与积压变化。

还要区分命令吞吐和成交吞吐。一笔 B1 产生两笔成交，一笔扫过大量小挂单的命令会产生更大的结果和账务事务。只报每秒订单数，不说明负载结构，无法判断性能是否满足业务。

## 第 2 层：测量怎样不掩盖真实排队

**面试官：** 你说先测量。如果撮合函数平均只用很短时间，为什么用户仍然会遇到很高的延迟？应该看哪些指标？

**面试者：** 因为函数执行时间不包含入口队列、日志提交、结果提交和下游等待。端到端要分别观测请求到可靠受理、受理到结果提交、结果到结转，以及结果到投影可见；每段都看分位延迟与队列深度，不能只看平均值。

跨机器时间戳容易受时钟偏差影响，进程内阶段耗时用单调时钟测量，跨进程使用有关联身份的追踪和可校准的观测。积压还要看年龄和位置差，单纯队列长度不能反映一条超大命令卡住后面的情况。

如果设计压测，我会明确限价范围、成交比例、热点市场、撤单比例和对手单数量，并采用能够暴露排队的到达模型。只让一个客户端等前一条完成再发下一条，会自动降低施压，容易漏掉过载尾延迟。这里是测量方案，不表示本专题已经运行压测或得到任何指标。

## 第 3 层：发现积压后为什么不能只加缓冲

**面试官：** 假设监控确认入口积压了。Go channel 加大一点，先把请求都收下，不就能减少拒绝吗？

**面试者：** 只能暂时吸收波动，不能增加服务能力。长期到达速度超过处理速度，扩大队列只是把明确拒绝换成更长等待，还会增加内存、悬挂预留和超时重试。

所以队列应有容量和等待预算，并区分受理前与受理后。能在预留前拒绝的过载请求，尽量提前拒绝；已经预留但尚不确定是否受理的意图，不能队列满就直接退款，需要用原意图恢复或通过有序关闭协议结束。已经可靠受理的命令，不能因为它变老而丢弃，必须继续处理或产生确定的拒绝、关闭结果。

我还会根据账户结转积压向上游传递背压。撮合快于记账不是无限接单的理由。有限队列的价值是限制风险和等待，让系统仍能恢复，不是保证任何负载都不拒绝。

## 第 4 层：怎样保护撤单又不破坏顺序

**面试官：** 你准备拒绝新单保护系统。但新单把队列塞满时，撤单也进不去，用户风险还在增加。你会让撤单插队吗？

**面试者：** 要明确插队发生在哪个边界。命令已经进入权威日志后，就必须按 commandSeq 执行，不能把序号较大的撤单提到较小的新单前面，否则会改变已经承诺的裁决顺序。

可以在尚未分配权威位置的准入层为撤单和关闭请求预留队列、连接和处理预算，对新 Place 更早限流，采用有上限的类别调度。这个调度本来就是进入日志前的排序政策，必须公开其语义；同价 FIFO 仍以最终接纳顺序为准。撤单本身也要鉴权和限频，不能让无效撤单占满保护通道。

如果日志里已经积压大量已受理新单，预留通道不能瞬间消除这段等待，所以受理上限和积压年龄阈值必须提前生效。保护撤单意味着在不改写既定顺序的前提下保住关闭能力，而不是承诺撤单总能抢在已经在前面的成交之前。

## 第 5 层：单个热门市场为什么不能随意再切碎

**面试官：** 准入解决不了一个热门交易对持续超载。既然不同市场能分片，为什么不能把同一市场按价格或者买卖方向分给多个写入者？

**面试者：** 因为一次撮合可能跨多个价格档，还要同时更新双方数量并与撤单竞争。简单按买卖方向拆分，会让一次成交跨写入者；按价格拆分会让扫单和最优价选择跨分片。原来局部串行就能裁决的问题，变成需要协调的跨分片原子顺序。

我会先把热点市场独占执行资源，优化数据布局、减少无关工作，并检查瓶颈是否真的在撮合，而不是日志或账务。热点迁移也需要暂停旧写入权、在已提交边界恢复并启用新任期，不能两台同时处理一会儿再合并结果。

如果这些仍不满足业务需求，可以研究分布式订单簿或改变交易机制，但必须重做最优价格、FIFO、撤单和原子输出协议，不能继续沿用本专题已经证明的单写者结论。一个市场的串行热点是真实约束，不能用“增加 goroutine”掩盖。

## 第 6 层：Go 优化应该保留哪些并发边界

**面试官：** 那先优化单市场。你会具体怎样减少 Go 撮合循环的开销，又怎样避免优化引入数据竞争？

**面试者：** 我会让一个 goroutine 独占可变订单簿，命令进入后由它确定顺序。其他 goroutine 不拿到可变订单节点，查询读取独立投影。结果交给异步分发之前，要形成生命周期明确的不可变副本或拥有独立所有权的对象，不能下一次撮合复用切片后把上一批成交改掉。

具体优化先由 CPU、分配和阻塞分析定位：减少每次匹配的临时对象，预分配有业务上限的结果切片，评估订单链表指针追踪和 GC 成本；只有证据表明需要时，再考虑池化或更紧凑的布局。`sync.Pool` 不保证对象一直存在，也不能在消费者仍引用时提前归还。

不能为了少一次分配而把半成品 ResultBatch 暴露出去，也不能在日志写入不确定时继续修改订单簿处理后续命令。数据所有权和提交边界优先于微优化；错误的低延迟成交没有业务价值。

## 第 7 层：批处理和大订单怎样影响尾延迟

**面试官：** 你保留了结果提交边界，那每条命令都等日志，会不会很贵？批处理或把一个大订单拆成几段能不能改善？

**面试者：** 可以研究批量传输或复制层 group commit，让多个记录共用一次持久化成本，但确认必须仍在相应记录真正提交后，组内顺序和每命令 ResultBatch 的完整边界不变。批量等待窗口越大，吞吐可能提高，低负载延迟也可能变差，所以必须用受控批大小与等待上限衡量。

本基线中前一个结果提交不确定时，引擎不处理下一条命令。若要跨命令推测执行形成批量结果，就需要额外定义未提交状态层、批量 CAS 和回滚恢复协议，那是改变实现前提，不是免费加一个批量参数。

大扫单还会制造很大的结果和账户事务。可以预先限制订单数量、系统可接纳的流动性规模和单批可处理资源，或制定明确的新执行规则；不能运行到中途随意丢掉余量，也不能把一个本应原子的 FOK 拆成有外部可见部分成交的几段。任何截断或继续处理政策都必须进入版本化业务规则。

## 第 8 层：优化后如何确认没有把风险转给下游

**面试官：** 假设撮合优化后吞吐提升，但账户结转越来越慢。你怎样判断可以继续扩量，以及什么时候必须停止接新单？

**面试者：** 我看的是整条链路的稳定性。若结果持续增长而账户进度持续落后，预留和待结转义务会积累，即使撮合延迟漂亮，也不具备可持续容量。应按结转积压年龄、未完成义务规模和恢复预计时间设置准入预算，在到达风险阈值之前限制新 Place，并保留关闭与恢复所需资源。

已经提交的成交继续结转，不能通过丢结果、提前释放资金或改成失败订单来降低积压。恢复时处理能力必须高于受控的新流量，否则永远追不上；如果账务数据库已成为瓶颈，需明确承认同库双边事务的扩容边界，另立跨分片协议，而不是悄悄把两边拆成独立更新。

验证优化时，我会在相同负载定义下对比阶段延迟与积压，同时检查数量守恒、资产守恒、重复处理和恢复结果。性能改进只有在正确性不变量仍成立、过载能够有界退化、恢复能追平时才算成立。这里没有运行工程压测，不能把这些验收条件写成已取得的成绩。

**本题收束**

- **讲透的机制：** 保留市场裁决单写者，测量全链路瓶颈，用有界准入和下游背压约束风险，再做有证据的布局、并行和批处理优化。
- **最容易答错：** 无限加队列；让撤单越过已提交命令；把同市场拆分当作免费并行；只测撮合吞吐而忽略结转积压。
- **检验反例：** 把账户处理能力持续降到结果产生速度以下。若系统仍无限可靠受理、预留无限增长，却只展示撮合平均延迟，说明容量设计没有闭环。
