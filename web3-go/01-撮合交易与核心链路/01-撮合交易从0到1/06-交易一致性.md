# 大问题 6：怎样保证订单、成交、预留和买卖双方账务始终对得上？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 一致性不是“所有页面同一毫秒刷新”，而是即使暂时不同步，也不能让一份钱花两次、成交没钱付或一笔成交记两次。本文只在零费链下现货、双边账户同库的条件下给出闭环，不宣称已解决跨数据库或链上结算。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 不变量 / 数量与资产约束 | 正常或故障时都必须守住的底线。 | 已接纳订单数量对得上，买卖引用同笔成交，各资产不透支、不凭空增加。 |
| 预留 reservation / 执行资格 | 为订单占住所需资产，使它真成交时有钱或币履约。 | Place 还有可能执行，就不能单凭超时把预留恢复成可用。 |
| intentId / reservationId / 载荷 | 下单意图、所占资产的编号和固定请求内容。 | 相同意图重试继续原流程，不重新占钱或改成另一张单。 |
| 本地事务 / 三个可靠边界 | 一份存储内一起生效的一组动作，不是全系统只有一次提交。 | 先提交意图预留，再提交撮合完整结果，最后提交双边账务。 |
| Place / Cancel / AbortIntent | 下单、撤已有订单，以及关闭下单意图。 | Cancel 未找到不阻断迟到 Place；AbortIntent 的持久关闭才构成屏障。 |
| TTL / 超时未知 | TTL 是时间寿命；超时是未拿到响应，不是知道失败。 | 本文预留凭据不自行到期，超时只触发恢复或申请关闭。 |
| commandSeq / 权威顺序 | 同一市场每条逻辑命令的裁决位置。 | Place 与关闭谁先轮到，决定是零成交还是保留已成交部分。 |
| 关闭标记 / 唯一释放依据 | 持久记录不能再接纳该意图，以及哪次结果授权退款。 | 关闭已退过钱，迟到下单的拒绝不能又授权退一次。 |
| 未结转成交义务 / 价差 | 已成交但尚未落实的付款责任，以及少于限价而未花的钱。 | 最新剩余量为零，不表示原预留全部可以退。 |
| ResultBatch / AppliedSeq | 一条命令的完整结果和已提交执行进度。 | 多笔成交和订单变化共同提交，不能持久化全成却丢了第二笔成交。 |
| 空效果批次 / 业务身份 | 重投占了新处理位置，但没有新的交易效果；业务身份辨认原请求。 | 序号变了不代表新下单，仍推进进度但不重放成交或退款。 |
| lastAppliedSeq / 消费缺口 | 账户已连续处理的位置，以及前序结果尚未补齐的情况。 | 撤单退款不能越过缺失的成交批次。 |
| 去重 / 消费确认 | 去重记住业务已生效；确认只是告诉运输层已经收到了。 | 事务已提交、确认丢失，重投查到原记录就不再记账。 |
| 跨市场余额竞争 / 行锁 | 不同交易对争同一账户资产，交给数据库统一协调。 | 两笔各占 15,000、总钱仅 20,000 时不能都通过。 |
| epoch / 旧主围栏 | 负责人代次，以及在存储处拒绝过时负责人新增写入。 | 旧主补发已提交历史结果可以去重，不能提交新的冲突成交。 |
| 安全性 / 活性 / 对账 | 不做错事、恢复后最终走完流程，以及对历史事实进行核查。 | 允许暂时占资等待恢复；对账不能替代执行约束，也不能直接改余额抹平差异。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，下 B1：最高 60,100 买 0.25 BTC。账户已经预留 15,025，但提交 Place 时响应丢了，查询也暂时没有这张单。此时系统不知道原命令是没到、在路上，还是已处理但页面落后。立刻退款看似让用户安心，实际上可能让甲把同一份钱再花一次，而迟到订单仍能成交。

甲决定放弃，系统于是把 AbortIntent 也送到同一市场命令序列。如果关闭排在 100、Place 在 101，就先提交关闭标记和唯一释放依据，101 的原下单必须拒绝，且不再退第二次。若 Place 在 100、关闭在 101，则保留已经成立的成交，只撤当时剩余。账户本地说“正在关闭”，并没有资格跳过这个裁决先退款。

用一个独立变体算清第二条路径：初始卖盘只有 0.10@60,000，另一档尚未出现。B1 占 15,025 后先买 0.10，实际要付 6,000，该部分少花的价差为 10，余下 0.15 仍需 9,015。关闭后最终只能支付 6,000、合计返还 9,025，不能因剩余归零就返还全部 15,025。即使关闭消息先到，账户也必须先补齐成交、再处理关闭，保证付款义务始终有预留覆盖。

这条链上各方各守一个可靠边界：预留与意图一起保存，完整撮合结果与执行进度一起提交，双边资产与分录、去重、账务进度再在一个事务里生效。确认丢了查原批次，不能重记账；其他市场要占同一余额，也必须竞争账户记录，不能以“每个市场都单线程”为理由各自放行。换主时旧负责人被存储围栏挡住，已经提交的历史结果可以补发，未提交的新计算不能冒充成交。

最终检查的不是画面是否瞬时一致，而是每份钱有没有明确归属、每笔成交是否只生效一次、故障恢复后能否继续走完。若未来拆成买卖双方不同数据库，原本的本地事务就不再覆盖双方，需要另设计清算义务和恢复协议；不能继续沿用本篇的原子记账承诺。这些是设计与手工核对要求，不是已经运行过的故障实验。

**流程位置与核心机制：** 单独覆盖从预留到结转的端到端一致性。重点不是再次罗列模块，而是在超时、迟到、竞争和崩溃时说明谁有权决策、什么必须原子提交、哪些状态可以暂时不同步。

**必要前提：** 沿用总览的限价 GTC、零费现货和 B1 案例。预留凭据绑定不可变意图，不独立按 TTL 失效；双方账户在同一事务数据库。普通 Cancel 只撤现存订单，AbortIntent 才能为尚未接纳的意图建立关闭屏障。

## 第 1 层：先定义“一致”，再谈技术组合

**面试官：** 你怎样保证订单、成交和双方资产的一致性？不能只回答“事务、幂等、重试、对账”。

**面试者：** 我先把一致性定义成可检验约束，而不是要求所有页面同一毫秒显示相同状态。

第一，订单数量守恒：原始量等于累计成交、剩余量和取消量之和，每笔成交对买卖双方引用相同价格与数量。第二，资产不能透支，任何可能被撮合执行的订单都有对应预留。第三，成交一经提交，就必须有可恢复的资金义务；不能因为记账暂时失败就把预留释放。第四，同一成交只产生一次有效账务变化，完整批次内的双边变化共同提交。

落实到本模型，我用三个可靠边界：账户本地事务创建预留与意图；撮合日志原子提交完整结果与执行进度；账户本地事务提交双边结转、去重与消费进度。边界之间允许积压，用稳定身份和有序协议收敛。对账用于检查这些约束和发现故障，不代替前面的执行约束。

## 第 2 层：三个局部事务之间，怎样防止超时误释放

**面试官：** 你说账户先预留、撮合后接纳。预留成功后下单调用超时，账户能不能把 15,025 USDT 释放？

**面试者：** 不能。超时只说明调用方没拿到结果，不说明 Place 没被接纳或没成交。释放后如果原 Place 继续执行，甲就可能同时把这笔钱用于别的交易，成交却没有足额资产可扣。

我会在预留事务里同时持久化 `intentId`、请求身份、载荷哈希和 `reservationId`。提交器用原意图查询、重试，不另建预留；恢复程序也能发现尚未收敛的意图。如果要放弃，必须请求撮合域关闭原意图，取得已提交的关闭结果，再依照结果释放可以退的部分。

所以这里没有“超过三十秒就自动解冻”的孤立规则。可以有超时触发的关闭任务，但它触发的是协议动作，而不是直接更改资产。暂时占资是允许的故障暂态，无钱成交不是。

## 第 3 层：查不到订单，为什么仍然不能直接解冻

**面试官：** 那我先查。撮合告诉我暂时查不到 B1，为什么还不能释放？原 Place 如果晚一点才到呢？

**面试者：** “暂未查到”不是“未来不可能执行”的证明。尤其是查询投影落后或 Place 仍在网络中时，释放会留下迟到执行窗口。

本模型为这类情况定义 `AbortIntent`。它绑定原意图、账户、交易对和预留身份，进入与 Place 相同的权威命令日志。如果 AbortIntent 先被处理，撮合域持久化该意图已关闭的标记；以后相同意图的 Place 到达，必须拒绝，不能再凭原预留凭据进入订单簿。

如果 Place 先被处理，则 AbortIntent 针对现有订单取消当时剩余量，并返回已经成立的成交义务。账户只能使用这个关闭结果，而不是一次未查到的响应，决定是否退款。关闭标记要进入快照和恢复范围，不能重启就消失。

## 第 4 层：关闭与接纳同时发生，到底由谁裁决

**面试官：** 你加了 AbortIntent，但它和 Place 仍然可能同时到达。账户先标记关闭、撮合先执行 Place，会不会各说各的？

**面试者：** 账户可以记录“关闭处理中”，但不能把这个本地状态当作已经撤销撮合资格。真正决定该意图是否还能执行的是撮合域的有序裁决。Place 和 AbortIntent 只能按同一市场的 `commandSeq` 先后执行。

例如 AbortIntent 在 100，Place 在 101：100 的结果提交关闭标记及唯一释放依据，101 看到标记就拒绝，但不再生成第二次退款动作。反过来，Place 在 100，AbortIntent 在 101：100 可能已成交，101 只能撤剩余量。两种顺序的退款可能不同，但都合法且可恢复。

还有一个容易遗漏的窗口：关闭结果已经提交，而账户还没退款。这时只是多占了一会儿资金，后续继续结转即可；不能为了让两边“看起来同步”先退款再补关闭。关闭标记也不能按短 TTL 清除，除非存在持久化的拒绝旧意图机制，能证明过期请求永远不会再次执行。

## 第 5 层：已经部分成交，关闭时究竟释放多少

**面试官：** Place 先执行，B1 已经与 S1 成交 0.10 BTC，但账务还没处理。现在关单，账户看到终态后能不能只按 leavesQty 计算预留？

**面试者：** 不能直接拿最新撮合剩余量覆盖账户预留。必须分清未结转成交义务和可退部分。这里的场景是一个独立变体：假设下单时只有 S1 可成交，S2 尚未挂出，B1 成交 0.10 BTC 后还有 0.15 BTC。

B1 初始预留 15,025 USDT。先前成交需要实际支付 6,000，同时退还该成交部分的价差 10；剩余挂单需要 9,015。关单后，这 9,015 也可以退款。因此最终应支付 6,000、合计返还 9,025，而不是因为 `leavesQty = 0` 就返还全部 15,025。

本模型让账户严格按该交易对结果顺序处理：先应用成交批次，再应用关单批次。成交时扣除实际支付并退对应价差，关单时释放实际取消数量乘限价。若关单事件先到运输层，先补齐前序批次，不越过缺口执行。这样已有成交始终由预留覆盖。

## 第 6 层：撮合只提交了半个结果怎么办

**面试官：** 你依赖成交结果，但撮合执行两笔成交时，中间崩溃了：B1 减了量，第二笔成交还没写下来，怎么办？

**面试者：** 这说明需要区分临时计算和权威提交。两笔成交与相关订单变化必须作为同一个完整 ResultBatch 提交，并且与新的 `AppliedSeq` 共用原子记录。不能先持久化 B1 全成，再分别持久化两笔成交。

如果日志中没有已提交的结果，内存里算过多少都不算权威完成。恢复时从前一个已提交边界重建，按相同输入和规则重新计算。若结果已提交，只是进程没拿到提交响应，则先按批次身份查询，不能生成另一组结果覆盖它。

日志追加还校验当前任期和前序处理位置。重试同一结果追加时，相同 `symbol + commandSeq` 只能找到原批次，不能形成第二次有效提交。如果是同一业务请求重新进入命令日志而获得新序号，引擎在新位置提交空效果批次与原裁决引用，不重新撮合，也不重放原退款动作。这区分了命令位置和业务身份。对外回报也必须来自已提交结果，否则用户可能拿到一笔恢复后不存在的“成交”。

## 第 7 层：订单不超卖，为什么共享账户仍可能超买

**面试官：** 即使每个交易对都串行，甲同时在 BTC/USDT 和 ETH/USDT 各下一个占用 15,000 USDT 的单，账户只有 20,000，怎么办？

**面试者：** 每交易对串行只保护本订单簿，不保护跨交易对共享余额。这一层必须由账户域的原子预留解决。

例如两个请求都执行“读到余额 20,000，然后各自判断够用”，会同时通过。正确做法是在同一个账户资产行上使用条件更新，或加行锁后在本地事务里检查并更新。条件更新的语义是：仅当当前可用不少于 15,000 时，才扣可用、加预留，并创建唯一预留记录和意图；这些动作共同提交。

第一笔成功后可用只剩 5,000，另一笔就应失败。相同请求的重试还受唯一身份约束，只能找到原预留，不能再次扣款。跨服务实例不能靠各自的 Go mutex 解决；如果账户数据库再拆分，也要让同一账户同一资产的预留竞争落在明确的原子所有者上。

## 第 8 层：事务提交了，但消费确认丢失，如何不重复记账

**面试官：** 预留没问题了。账户完成 B1 两笔成交后宕机，没有发出消费确认。重投后怎样保证不是再扣一次 15,015 USDT？

**面试者：** 账户把批次处理记录、分录、双边余额变动和 `lastAppliedSeq` 放进同一个本地事务。如果事务确实提交了，即使确认丢失，恢复后仍能查到这个批次已经处理；如果没提交，就不应该留下半边资产变化或已前移的进度。

消费时先锁定该交易对的进度记录。批次位置已处理，校验身份后返回原结果；恰好是下一条，执行完整事务；出现缺口，暂停这个市场的后续应用并补齐前序。这里每个已处理命令都有结果批次，即使没有成交，也能连续推进。

多市场会并发触碰同一账户，所以还需要数据库余额锁或条件更新，并按固定顺序取得多账户、多资产锁，死锁时回滚重试。消息队列的“消费一次”不是账务保证；真正有效的是业务身份与资产变化共用事务边界。

## 第 9 层：旧主恢复后，为什么不能再次创造有效结果

**面试官：** 刚才都假设只有一个引擎。主节点失联后备节点接管，旧主又恢复，它继续撮合并发消息，会不会出现两份有效结果？

**面试者：** 仅靠一个本地 `isLeader` 标记不够。单写者必须由可靠存储边界强制执行。本模型的复制日志有单调递增的 `epoch`，命令和结果写入都受任期检查，旧主不能把新结果提交为权威事实。

备节点接管时先确认已提交的命令与结果位置，从有效快照和后续记录恢复；对命令已提交、结果未提交的尾部继续处理，对已提交结果不重新创造另一笔成交。如果失去多数派就不能继续承诺新的可靠受理，不能为了可用性在两个分区分别成交。

旧主可能仍发送先前已提交的结果，这只是重复交付，由稳定批次身份去重；旧主在失联期间算出的未提交结果，不能进入权威发布路径。分发必须读取已提交日志，而不是信任任意引擎进程的内存消息。任期隔离解决旧写入者问题，不能只靠下游去重掩盖两份互相冲突的新成交。

## 第 10 层：怎样证明方案闭环，又怎样承认能力边界

**面试官：** 到这里有预留、有序关闭、结果日志、事务和主备。你准备怎样验证它们不是各说各话？如果以后拆分账务数据库呢？

**面试者：** 我会围绕同一个意图列故障切点，而不是只测接口返回码：预留事务前后，Place 提交前后，AbortIntent 与 Place 的两种顺序，结果提交前后，以及账务提交成功但确认丢失。每个切点恢复后，检查订单数量、成交唯一性、各资产守恒和预留是否仍覆盖未履行义务。

还要专门验证迟到请求：先提交关闭结果并退款，再投递原 Place，必须被拒绝；验证重投完整成交批次后，余额和账务分录不得再次变化；验证先收到关单结果时，不能越过未处理成交释放资金；验证旧任期提交必须被存储层拒绝。这里说的是验证方案，不声称已经执行过这些实验。

如果以后买卖双方账务落到不同数据库，原来的双边本地事务就失效了。我需要另行定义持久清算义务、各分片的幂等扣划与入账、未结转期间的可用性限制及恢复协议；否则不能复用“双方原子记账”的承诺。本专题不展开这套替代架构，也不通过临时加一个组件假装已经解决。

最终我会给出两类验收：安全性要求是不超花、不重复成交、不重复记账、不错误解冻；活性要求是在存储与服务恢复、处理能力足够时，已受理意图最终成交、挂单或关闭，已提交成交最终完成结转。对账用于核查与定位，修复也应通过有审计依据的补记或纠正流程，不直接改库抹平差异。

**本题收束**

- **讲透的机制：** 以预留覆盖执行资格，用同一序列裁决接纳与关闭，以完整结果确立成交义务，再用本地账务事务实现唯一资产变化。
- **最容易答错：** 超时就退款；查不到就当作未受理；订单终态就清空预留；用消息去重代替结果原子性；用单交易对串行代替共享账户并发控制。
- **检验反例：** 甲预留后超时，系统先处理 AbortIntent、完成退款，原 Place 随后迟到。如果它仍能成交，说明交易资格没有真正关闭，前面所有“最终一致”表述都不成立。
