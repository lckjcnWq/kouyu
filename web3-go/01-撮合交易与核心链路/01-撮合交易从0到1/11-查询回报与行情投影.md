# 大问题 11：查询、订单回报与行情怎样跟上权威撮合结果？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文讲“已经发生的交易，怎样被页面正确看见”，不重新决定成交或退款。统一案例是链下托管的 BTC/USDT 限价现货，未成交量继续挂单，按先挂订单价格成交、零费用，账户在同一事务数据库里结转。订单查询、私有回报和公共行情都是读取已提交事实后做出的展示副本，可以先后更新，但必须说清自己看到哪个阶段、哪个位置；页面慢一点可以，拿旧画面重下单、改成交或放款不可以。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 查询投影 | 从权威结果整理出来、方便查询的展示副本。 | 订单表、余额读副本和客户端缓存都可能落后，不能反过来作为成交裁决或退款依据。 |
| `ResultBatch` | 一条市场命令的完整已提交结果包。 | 执行投影、私有订单回报和公共行情从它取事实；原包完整原子提交，页面消费不改变结果本身。 |
| `ACCEPTED` / `FILLED` | 命令已可靠受理 / 订单执行已全成。 | 受理时可能尚无裁决；全成时可能尚未到账，不能把两个状态压成含糊的“都成功了”。 |
| `PENDING` / `APPLIED` | 账务待结转 / 对应位置的账务已完成。 | 只有账户整批事务提交才算已结转；挂单未来还可继续成交，所以“已结转”必须带版本或批次范围。 |
| 执行版本与结转位置 | 一把尺量订单执行更新，另一把尺量账户处理进度。 | 两者分别单调推进，旧订单通知不能把已确认的结转进度改回待处理，也不能整行最后到达者覆盖。 |
| 结转通知：`symbol、batchId、lastAppliedSeq` | 分别指市场、结果包身份、账户连续结转到的位置。 | 待发通知与账户资产在同库事务中保存，失败可重送；不能把一次 WebSocket 调用当成可恢复交付。 |
| `commandSeq` | 交易对内权威命令的连续逻辑号。 | 不是数据库时间、网络到达次序或物理日志偏移；服务器消费完整市场结果可按它检测缺口。 |
| `streamSeq` 与过滤流 | `streamSeq` 是某条推送流自己的连续序号；过滤流只含某账户或某类变化。 | 只订阅甲的事件，本来就不会收到所有命令；需独立连续号或明确源结果覆盖区间，不能把所有跳号都当丢包。 |
| 流身份、市场与订阅范围 | 解释“这个序号属于哪一条流、哪类数据”的上下文。 | 不同市场、账户或订阅范围的序号不能随便互相比较或接续。 |
| 完整状态与增量 | 前者给某个范围的全貌，后者只说本次改了什么。 | 较新完整状态在覆盖范围明确时可替代旧状态；增量漏一条可能留下已不存在的挂单，不能仅保证版本变大。 |
| 快照水位 W | 快照确切反映到哪个结果位置的标记。 | 内容必须与 W 一致；先缓存增量、再装快照，丢掉 W 已覆盖部分后连续续接，不能拼跨时刻盘口。 |
| 水位映射与游标过期 | 映射连接源结果位置和推送流位置；过期表示所需历史已不在恢复范围。 | 独立流序号不能直接减命令序号；无法续接要明确重新同步，不能随机选个位置假装接上。 |
| 可恢复游标与事件去重 | 游标记住“我收到哪里”，事件身份识别“这条是否已处理”。 | 断线重连补发可能重叠，客户端也要去重；最新订单表不能替代用户需要的逐笔成交明细。 |
| 私有回报与公共行情 | 前者含某账户的订单和成交，后者面向所有人展示成交或盘口。 | 私有补发需账户授权，知道游标不等于有权读取；两类流的保留期与恢复内容可以不同。 |
| 读己之写 | 用户刚拿到的受理或结果凭据，不会被落后查询轻易否认。 | 带原意图与目标位置查询，未裁决就说待裁决，投影未追上就有限等待、换读取来源或明确同步中。 |
| 有界队列、背压与慢消费者 | 发送缓存有限，客户端太慢就让它重同步，而不是无限堆内存。 | 撮合提交不等某个客户端确认；限制连接数、等待数与补取范围，慢连接必要时断开恢复。 |
| 绝对数量合并与覆盖区间 | 公共盘口可把同价位多次变化压成一条较新的“现在总量”。 | 合并要声明覆盖范围；不能乱加增量还冒用原序号，也不能静默丢掉承诺逐条补发的成交或私有回报。 |
| 组合查询与多投影水位 | 把订单、账户、行情几幅不同进度的画面放到一起。 | 只有执行和账户都覆盖目标批次，且实际读取副本也够新，才能描述该批次已完成；没有全局协议就不保证跨域同一时刻可见。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，下单买 0.25 BTC，限价 60,100，先预留 15,025 USDT。手机拿到“已可靠受理”，立刻查询却没看到订单，原因可能只是撮合还没裁决，或订单查询副本尚未追上。正确界面应拿着原意图、订单身份和命令位置，显示已受理待裁决，或明确展示同步中；不能说“下单失败，换个请求号再买”。如果甲的请求本身超时，也继续沿原请求身份查，不把没看到答案当成确定失败。

市场已经依次成交 0.10 BTC、价格 60,000 和 0.15 BTC、价格 60,100，并原子提交完整结果包。分发器可以立即更新订单执行投影、给甲推送两笔成交及“已全成”，同时删减公共盘口，不必等账户和所有查询副本都刷新。但此刻账户可能仍待结转，甲不能因“已全成”就认定 BTC 已经可用。只有账户把整批双边资产在同库事务中提交，才有支付 15,015 USDT、返还 10 USDT、得到 0.25 BTC、可用 4,985 USDT 的到账事实；页面是否已经读到这份新余额，是另一个投影进度问题。

恰好账户的完成通知先到，订单较旧的待结转画面后到。页面分别记录执行版本与账户处理位置，先保存“账务已覆盖该批次”，再组合订单信息，不能让后到的旧通知把已结转改回待处理。账户的待发完成通知也应与账务事务一起持久保存，发送失败可以重送。甲的私有流只包含甲的事件，市场中其他人的命令没有推给甲，不能因此误报丢包；真正的缺口要依该订阅流的连续序号或声明的覆盖区间检测，而不是只看市场命令号有没有跳。

随后甲的网络断线，公共盘口少收到一条价位删除增量，私有成交回报也可能只看到第一笔。重连不能直接继续套用后续盘口变化，否则会留下不存在的卖单；客户端先建立能缓存增量的订阅，再装入带精确水位 W 的一致快照，丢弃已覆盖增量，从可映射的下一流位置连续续接。私有流则从已确认游标补发，并按事件身份去重；游标过期就重新查询当前订单和逐笔成交，再从服务端给出的恢复水位续订。不能从“全成 0.25 BTC”倒推出两次不同价格，私有历史补查还必须核验账户权限。

最后甲的手机持续变慢，发送队列满了，系统应通知重新同步或断开恢复，而不是让所有撮合都等甲确认。公共盘口若合并同价位的较新绝对数量，要说清覆盖区间；承诺逐条保留的成交和私有回报不能静默丢掉。组合页也要检查它实际读取的订单和账户副本水位，不能拿一条新结转通知配一份旧余额就显示“全部到账”。这套设计保证各投影版本不倒退、缺口有恢复路径、阶段不冒充，但不保证订单、余额与行情在同一物理瞬间原子可见，更不允许投影反过来裁定关闭资格或释放预留。以上是应手工构造的时序边界，不是已经执行的测试报告。

**流程位置与核心机制：** 本题覆盖撮合结果提交后的可见性：怎样构建订单查询、私有回报与公共行情，怎样处理缺口、重复、重连和慢消费者。成交是否成立由撮合结果决定；资产是否结转由账户事务决定，本题不重新定义它们的可靠边界。

**必要前提：** 沿用总览的链下现货基线。`commandSeq` 是交易对内逻辑命令位置，不是数据库时间或 WebSocket 消息到达时间。下文的客户端缓存都只是投影，不能作为退款依据。

## 第 1 层：订单全成与资产到账能否分开通知

**面试官：** 撮合产生结果之后，订单查询、用户回报和行情应该怎样更新？必须等账户结转完成再发布吗？

**面试者：** 不必全部等待，但必须明确每条通知表达什么事实。在这个模型中，分发器读取已提交的 ResultBatch，更新订单执行投影并生成私有订单回报，同时更新公共成交和盘口。它们可以在账户尚未结转时发布，因为这时成交已经成立。

以 B1 为例，可以先通知成交 0.10 BTC 和 0.15 BTC、订单执行状态为 FILLED，但结转状态仍为 PENDING。只有账户事务确实提交后，才能把对应批次的结转状态更新为 APPLIED，不能看到 FILLED 就推断买入 BTC 已经可用。公共盘口删除 S1、减少 S2，依据的是已提交撮合结果，不需要等所有查询副本刷新。

因此我会同时携带订单版本、来源结果位置和结转位置。这样“页面旧”“账务待处理”和“撮合没完成”能够被区分，而不是全部显示成一个含糊的成功状态。

## 第 2 层：两个来源的通知怎样不互相覆盖

**面试官：** 你把执行与结转分开了。如果账户完成通知先到，较旧的订单投影后到，会不会把 APPLIED 覆盖回 PENDING？

**面试者：** 会，所以不能用整行最后写入者获胜。订单投影和结转投影要分别拥有版本维度：执行字段按撮合的订单版本更新，结转字段按账户已处理的结果位置更新，旧版本只能被忽略，不能覆盖新版本。

账户事务提交时，可以在同一数据库事务里记录待发布的结转通知；通知携带 `symbol、batchId、lastAppliedSeq`。通知发送失败后由持久记录重发，也可以通过账户进度补查。不能只在事务提交后调用一次 WebSocket，然后把那次调用当作可恢复通知。

即使结转通知先到，我也可以先记录“账户已覆盖到该位置”，等订单投影到达后组合展示。对一个挂单多次成交的订单，APPLIED 表示已经结转到哪个版本或批次，不表示这个订单未来不再有成交。执行版本与账务位置各自单调推进，才不会因消息到达顺序而倒退。

## 第 3 层：版本单调为什么还不足以发现缺口

**面试官：** 你会忽略旧版本，那收到 103 后直接覆盖 101，不也算单调吗？漏掉 102 会有什么问题？

**面试者：** 对完整状态快照和增量消息，处理方式不同。若每条都是某订单的完整状态，而且有明确覆盖范围，较新快照可能覆盖旧状态；但盘口增量不能任意跳过。漏掉 102 的价位删除，再应用 103 的另一档增量，就会留下不存在的挂单。

因此每个增量流需要定义连续的 `streamSeq` 或明确的前后覆盖区间。重复位置可丢弃，下一位置才正常应用，发现缺口要暂停应用后续增量，补取缺失区间或重建。服务器端投影消费完整市场结果时，可以按连续 commandSeq 推进；客户端若只订阅某账户或只接收有盘口变化的结果，就不能要求每个 commandSeq 都出现。

过滤流应另外分配连续序号，或明确告知一条消息覆盖的源结果区间。否则把“别人的订单没有推给我”误判成丢包，或者真的丢了自己的事件却察觉不到。序号必须连同流身份、市场和订阅范围解释。

## 第 4 层：补快照时怎样不漏掉正在发生的变化

**面试官：** 出现缺口后你说重建。客户端一边拉快照、一边收增量，快照生成期间市场还在交易，怎样衔接？

**面试者：** 快照必须带一个精确水位 W，并且内容确实代表这个水位的盘口，不能边读边拼出跨多个时刻的混合视图。服务端可以从投影的一致视图生成它，发布后保留 W 之后的增量供衔接。

客户端先建立能够缓存增量的订阅，再获取带 W 的快照；装入快照后丢弃已经被 W 覆盖的增量，从 W 的下一位置连续应用。若流使用独立 streamSeq，服务端要提供 W 与该流位置的对应关系，不能把两套序号直接相减。

如果请求快照太慢，增量已经超出保留范围，就明确返回游标过期，重新获取可衔接快照，而不是假装从某个随机位置续上。缺口重建期间可以显示“同步中”，不能把未校验的本地盘口当作最新可交易事实。

## 第 5 层：重连后私有订单和公共盘口能否一样补

**面试官：** 快照能解决公共盘口。用户断线十分钟又回来，私有成交回报也直接覆盖成一张最新订单表就够了吗？

**面试者：** 不一定。最新状态能够回答订单现在怎样，但无法替代用户需要查看的逐笔成交和历史回报。私有流应携带可恢复游标，客户端重连后从最后确认位置补发；客户端也必须按事件身份去重，因为断线可能发生在消息已处理但游标未保存之后。

若游标过期，服务端应提供明确的恢复方式：查询订单当前状态及成交明细，在一个服务端给出的恢复水位后继续订阅。不能用最新订单状态反推出所有历史成交价格，因为同一订单可能在多个价格成交。

私有补发还必须绑定账户与授权，不能只知道某个游标就能读取其他账户的成交。公共流与私有流可以复用缺口检测方法，但保存周期、权限和恢复内容不同。通知是便利通道，可查询的权威历史与可说明的恢复边界才是重连后的依据。

## 第 6 层：查询落后时怎样实现读己之写

**面试官：** 你提供了查询，但用户刚拿到下单 ACCEPTED，立即查询却说没有订单。让用户不停刷新就算解决了吗？

**面试者：** 不算。ACCEPTED 只保证命令已经可靠受理，所以响应应带原意图、订单身份与命令位置。立即查询时，如果执行结果还没产生，应该返回“已受理、待裁决”，而不是把查询投影暂时没有记录解释为下单失败。

如果执行结果已经提交，客户端可以带目标结果位置请求查询。查询服务检查自身投影水位是否至少覆盖该位置：已覆盖就返回数据；未覆盖可以短暂等待、转到满足水位的读取来源，或明确返回同步中及当前水位。等待应有上限，不能让所有请求无限阻塞。

还要说明等待的是执行投影还是账户投影。看到订单 FILLED 不代表账户进度也已覆盖它。对于超时请求，仍通过原请求身份查询，不能指导客户端换一个 ID 重下。读己之写是一项按阶段定义的协议，不是简单把读取全部打到主库。

## 第 7 层：等待与补发会不会拖垮撮合

**面试官：** 查询可能等水位，WebSocket 还要缓存增量。如果很多用户网络很慢，你怎么避免这些等待反过来卡住撮合？

**面试者：** 撮合提交路径不等待某个客户端确认。已提交日志与投影服务之间保持可恢复消费，客户端连接则使用有界发送队列、超时和断线恢复。一个慢客户端的队列满了，就通知重新同步或断开连接，不能让它无限占用内存，也不能让它阻止结果提交。

公共盘口可按协议合并为同一价位的较新绝对数量，但合并后的消息必须声明覆盖区间，不能把任意增量相加后继续冒用原序号。逐笔成交和私有回报若承诺逐条补发，就不能为了减压静默丢弃；要转为从持久历史恢复。

服务端还应限制每账户连接数、并发水位等待数和历史补取范围，观察投影延迟及发送积压。这样慢消费者承担重新同步的成本，不会把市场裁决链路变成所有客户端网络速度的最小值。

## 第 8 层：多个投影怎样给出可信但不过度承诺的画面

**面试官：** 你隔离了慢消费者，但订单、余额、行情仍有不同水位。产品想让用户看到一个“完整实时状态”，你能承诺什么？

**面试者：** 我能承诺每个投影内部遵循自己的版本和恢复协议，并展示数据来自哪个阶段；不能在没有全局一致快照协议时，承诺跨市场、跨账户和行情在同一物理时刻原子可见。

对某一批次，可以把订单执行位置与账户处理位置关联：执行已覆盖而账户未覆盖，标记结转中；两者都覆盖，才把这批次描述为账务已完成。若组合查询还使用落后的账户读副本，也要检查该副本水位，不能只看账户通知就用旧余额拼出“已全部到账”的画面。

验证时，我会构造执行通知先到、结转通知先到、重复增量、断线缺口和快照切换等独立时序，检查是否出现版本倒退、盘口残影或错误完成承诺。这里给的是验证方法，不是已经执行的测试报告。最后需要守住的边界是：投影可以落后，但不能用落后的画面重新决定成交、关闭资格或释放资产。

**本题收束**

- **讲透的机制：** 执行与结转分版本，增量有连续性契约，快照带可衔接水位，断线和慢消费者有有界恢复路径。
- **最容易答错：** 用到达时间覆盖所有状态；把过滤流的 commandSeq 跳号直接当作丢包；把订单全成显示为资产已经可用。
- **检验反例：** 在订单投影落后时先收到结转通知，再重放旧订单通知。如果页面状态倒退，或直接用旧查询结果退款，说明投影与权威决策的边界已经失守。
