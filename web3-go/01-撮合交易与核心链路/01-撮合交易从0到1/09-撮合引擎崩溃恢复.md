# 大问题 9：内存撮合引擎崩溃后，怎样恢复原订单簿与处理结果？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文不是教“重启后把盘口总量补得差不多”，而是恢复每张订单的排队位置、数量、旧请求处理记忆和原成交身份。背景仍是链下托管的 BTC/USDT 限价现货，未成交部分继续挂着，按先挂订单价格成交、零费用；市场单写，账户共用事务数据库。恢复以已经持久提交的事实为准：已有结果只应用，不再撮合；只有确认尚无结果的已受理命令尾部才继续执行。这里描述恢复协议与验收设计，不代表已经做过故障实验。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 内存执行副本与权威事实 | 内存是工作台，已提交日志才是能据以恢复的正式底稿。 | 崩溃前没提交的减量、候选成交和发送缓冲可以丢弃，不能拿它们推翻持久结果。 |
| `CommandLog` / `ResultBatch` | 已受理命令日志 / 一条命令的完整结果包。 | 接到任务和完成裁决是两次提交；全部成交、状态变化及新撮合进度必须完整原子成立。 |
| `commandSeq` / `AppliedSeq` / `logIndex` | 命令逻辑序号 / 已完整裁决到的位置 / 底层复制日志记录位置。 | 命令和结果会穿插占用底层日志位置，不能把物理偏移或日志索引当逻辑命令号；已受理上界也不等于已裁决进度。 |
| 一致提交视图与超时未知 | 从权威日志确认同一时点哪些结果已成立，而不是随便查一个副本。 | 追加回复丢失后，落后副本“未找到”不能证明未提交；查不明就停在原边界。 |
| `epoch` 与 CAS | `epoch` 是主写任期；CAS 是 Compare And Swap，即前序仍等于预期才提交。 | 新结果必须通过权威日志的任期和前序进度校验；旧进程即使恢复正确，也无权继续新写。 |
| 快照与一致边界 K | 在完整结果 K 之后拍下的一份可恢复状态底片。 | 订单簿、幂等和关闭状态都必须来自 K，不能前半张是 K、后半张是 K+1。 |
| FIFO 与订单簿索引 | FIFO 是 First In, First Out，即同价先来先成交；索引用来快速找到订单。 | 索引可以重建，真实队列顺序不能猜；只存每档总量会丢掉下一笔该跟谁成交。 |
| `orderId`、预留引用与数量守恒 | 订单身份、关联哪笔占款，以及每份数量最后去了哪里。 | 已接纳订单满足原始量＝累计成交量＋剩余量＋取消量；账户、优先级和订单版本也要恢复。 |
| 幂等索引与关闭标记 | 记住旧请求已经怎样裁决，以及哪个下单意图已经被关闭。 | 不能因为订单已终态或离簿就丢掉，否则已经退款的迟到下单可能重新成交。 |
| 写时复制与原子发布清单 | 先固定一份不再变化的视图，写完整后才一次性公布“这张快照可用”。 | 半写文件不能参与恢复；hash 即内容校验摘要、格式和关联位置验证成功前，旧快照及所需日志要保留。 |
| `orderChanges` / `reservationActions` | 恢复订单变化的清单 / 预留资金处置依据。 | 已有结果按记录重建状态，不重新跑匹配；资金动作由账户按原批次去重结转，撮合恢复不直接改钱。 |
| `ResultBatchId` / `tradeId` / `matchIndex` | 结果包身份 / 成交身份 / 本命令内部的匹配序号。 | 前者用市场加命令序号，成交再加匹配序号；恢复沿用原值，不重新编号或刷新排队位置。 |
| 空成交与空效果批次 | 没有新成交的结果，不一定没有业务变化；旧业务重投则不应再有资产效果。 | 挂单、拒绝、撤单和关闭都要恢复；拒单不建活跃订单，重投批次只恢复原结果引用并推进位置。 |
| 连续结果前缀与无结果尾部 | 前面每条都有正式结果，后面命令已受理但确实还没结果。 | 只有确认的尾部可继续执行；若有 K+2 的结果却缺 K+1，必须停查，不能把中间缺口拿来重算。 |
| 预留凭据与 TTL | 凭据证明原请求已有预留；TTL 是 Time To Live，即自动过期时长。 | 恢复按原绑定和关闭裁决认执行资格，不看当前余额重新审核，也不按重启时钟擅自让凭据失效。 |
| tick / lot / quote unit | 最小价格刻度 / 最小数量单位 / 计价资产的最小记账单位。 | 本文分别为 0.01、0.0001、0.000001，整数价格乘整数数量得到 USDT 记账单位；仍要查溢出并沿用历史规则版本。 |
| 确定性重放与状态摘要 | 相同历史输入应得相同结果；摘要用于核对恢复状态。 | 不靠 Go map 的无序遍历决定匹配，也不能临时换当前时钟、随机数或单位规则；摘要序列化顺序也须固定。 |
| 账户 `lastAppliedSeq` 与历史保留 | 账户独立记着账结到哪条结果，可能比撮合恢复进度落后。 | 补发原结果由账户去重结转；最新撮合快照不能替代旧账务明细，历史归档必须可检索、可校验、可恢复。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，下单买 0.25 BTC，限价 60,100，账户已经预留 15,025 USDT。引擎有一份位于完整结果边界 K 的快照，之后甲的买单先匹配 0.10 BTC、价格 60,000，再匹配 0.15 BTC、价格 60,100。引擎提交包含两笔成交的完整结果包时回复丢了，紧接着进程崩溃。重启者不能把“没收到回复”当作失败，也不能把工作台上减到一半的订单数量当成事实；它先从日志服务取得一致提交视图，查明 K+1 的结果到底有没有正式成立。无法查明，就不能继续下一条。

恢复者先验证并加载 K 的完整快照。这张底片不只要有每档价格总量，还要保留每张订单、同价队列顺序、已成与剩余及取消数量、账户和预留引用、订单版本，以及旧请求幂等记录和意图关闭标记。若同价两卖单的先后被交换，下一笔买单就会成交给错的人；若一份已关闭且已退款的意图标记丢失，迟到下单就可能拿旧凭据重新买币。快照必须把这些内容一起固定在 K，写完整、校验通过并原子公布后才算有效，半张文件不能顶替上一张完整快照。

权威查询证明甲在 K+1 的完整结果已经提交，恢复者就按原 `orderChanges` 应用订单变化、恢复关闭与幂等结论，再推进内存撮合进度，不把甲的原买单重新放进匹配循环。原结果包身份和两笔成交身份一律保留。后面的挂单、拒绝、撤单、关闭及重复业务的空效果结果包也逐条恢复，不能只挑有成交的记录；拒单不能凭空建活跃订单，重投也不能把旧成交再应用一次。逻辑命令号决定这条恢复顺序，不能拿混有命令与结果的底层日志索引直接代替。

继续追到 R 后，只有日志服务确认后面的命令已经受理、却确实没有结果，当前有效写入者才从 R+1 开始继续确定性执行。每条新结果仍需通过权威存储的任期与前序进度校验并完整原子提交，再处理下一条；若发现 R+2 有结果而 R+1 没有，就停查，不能擅自补算。尾部命令使用原规范载荷、历史规则和整数单位，预留资格也按原凭据与已恢复的关闭标记判断，而不是看“现在账户余额够不够”。代码升级不应改变历史价格含义、同价顺序或成交身份，不支持历史版本就不能激活。

最后还要核对快照摘要、结果连续性、订单版本、数量守恒和队列索引。撮合恢复成功不代表甲的账也要重做：原完整结果可补发，账户用自己的连续进度与批次去重，在同库事务里完成全部双边结转；若此前已经结过账，补发仍只能留下支付 15,015 USDT、返还 10 USDT、得到 0.25 BTC，最终可用 4,985 USDT。账户尚未结转时不能为了“追平”直接退预留或改游标。最新快照也不能成为删尽旧结果的理由，因为落后账户和旧备份还需要历史；材料不足就停止相关业务，不能从当前盘口猜旧账。恢复期间日志有多数派可按约定继续受理排队，但执行未就绪就不能承诺已裁决，积压过大还要背压。

**流程位置与核心机制：** 从崩溃后的权威边界识别，追到快照、结果重放、无结果尾部执行和日志保留。目标不只是恢复看起来相同的盘口，还要恢复 FIFO、数量、业务幂等、关闭资格及原成交身份。

**必要前提：** 沿用链下托管 BTC/USDT 现货 CLOB、限价 GTC、maker 价、零费用、每市场单写者。CommandLog 与 ResultBatch 分别提交；日志服务提供持久化多数派提交、epoch 隔离及前序 AppliedSeq 的 CAS。账户位于共享事务数据库，恢复撮合不直接修改账户资产。以下是生产设计，不是已执行的故障实验。

## 第 1 层：恢复的是已提交状态，不是进程现场

**面试官：** 撮合引擎把订单簿放在内存，执行到一半进程崩溃了，重启后从哪里恢复？

**面试者：** 在这个模型中，内存只是已提交状态的执行副本，不是唯一事实源。重启先取得一致的已提交边界，从有效快照恢复，再按逻辑命令顺序应用快照之后的已提交 ResultBatch；最后只有已提交 CommandLog、没有已提交结果的尾部，才继续确定性执行。未提交的内存减量、撮合候选和发送缓冲都可以丢弃。

可靠受理只证明输入可恢复，不证明它已经裁决。每条命令的完整成交、orderChanges、reservationActions、关闭和幂等结果与 AppliedSeq 单个原子记录提交，因此不存在“权威结果只留下半笔成交”的合法状态。若日志实际出现不完整记录，应视为损坏或实现违约，不能自行补一个看起来合理的订单终态。

## 第 2 层：先查明最后一次结果是否提交

**面试官：** 你要区分有结果和无结果，但崩溃前最后一次追加超时了，重启看不到结果就能认定未提交吗？

**面试者：** 不能把一次查询未找到当成最终结论，尤其不能读落后副本来裁决。恢复者先在日志服务取得当前有效 epoch 下的一致提交视图，按 `symbol + commandSeq` 查明结果及 AppliedSeq；必要时等待服务完成提交状态判定。不能查明就停在旧边界，不处理下一条，也不发布猜测结果。

例如快照到 K，最后请求提交 K+1：若结果已提交，必须恢复原批次；若已确定没有提交，当前写入者才可以从 K 重算并追加，仍受 epoch 和前序 K 的 CAS 保护。CommandLog 和 ResultBatch 共用底层日志时，原始 logIndex 会穿插两类记录，不能直接当 commandSeq。逻辑序号由服务分配并按已提交命令连续检索，AppliedSeq 表示已产生完整结果的逻辑位置，不是“最后读到的日志行”。

## 第 3 层：快照必须保存恢复业务语义的状态

**面试官：** 查明边界后，如果快照只保存每个价格的总挂单量，能不能先恢复盘口，再慢慢补订单？

**面试者：** 不能用聚合深度替代执行快照。同价总量相同，不代表下一笔成交对象相同。快照要保存买卖价位、每个价位的订单 FIFO 顺序、orderId 和账户及预留引用、价格与原始量、累计成交量、剩余量、取消量、优先级和订单版本；定位索引可以重建，但队列业务顺序不能猜。

还必须包含持久业务请求绑定和原裁决引用、已关闭意图标记、规则与整数单位版本、已提交结果位置及 AppliedSeq、必要的内容 hash 和快照格式版本。终态订单可以按约定压缩保存，但不能丢掉阻止旧请求重执行的身份与数量依据。若 AbortIntent 先关闭后退款，快照漏了关闭标记，迟到 Place 就可能借原凭据重新入簿；这不是盘口误差，而是无钱成交风险。

## 第 4 层：快照必须对应一个完整提交位置

**面试官：** 保存这么多字段时，撮合还在运行，前半张快照在 K，后半张在 K+1，会不会拼出不存在的状态？

**面试者：** 所以快照要捕获完整结果边界上的一致状态。可以由单写者在已应用结果 K 后短暂停顿，形成不可变副本或受控的写时复制视图，再异步持久化；不能后台遍历仍在变化的订单节点，最后随手贴一个最新 AppliedSeq。副本里的订单簿、幂等和关闭标记必须都属于 K。

快照写完后校验内容 hash、格式、规则版本和关联结果位置，再原子发布清单，使其成为可发现的完整快照。写到一半宕机留下的临时文件不算有效版本，上一份完整快照与必要日志要继续保留。只有知道“快照文件持久化”和“指向该快照的元数据可恢复”都成立，才能把它计入恢复与清理依据；快照上传请求返回不确定时同样不能提前删除旧材料。

## 第 5 层：已有结果只应用，不重新撮合

**面试官：** 拿到 K 的一致快照后，K+1 的成交已经提交，恢复时为什么不能直接再跑一次 K+1 的 Place？

**面试者：** 因为已经有权威结果，应当应用那个结果，而不是再次作裁决。重放按连续 commandSeq 读取完整已提交批次，校验市场、版本、前序位置和内容完整性，依据 orderChanges 恢复订单数量、入簿或出簿与版本，再应用关闭和业务幂等状态，最后推进内存 AppliedSeq。结果必须携带足以恢复的状态变化，不能只存一条“执行成功”。

空成交批次也要重放：它可能包含拒绝、挂单、撤单或关闭。拒单只恢复请求裁决和必要处置，不把未经接纳的原始数量塞入活跃订单数量账本，也不创建 FIFO 节点；已接纳订单才按数量守恒重建。相同业务输入重投占了新序号时，其空效果批次只记录原结果引用并推进位置，不能把原成交再应用一遍。`ResultBatchId = symbol + commandSeq`，`tradeId = symbol + commandSeq + matchIndex` 都沿用原值；恢复不重新编号，也不因为重复下单刷新原 FIFO 位置。

## 第 6 层：仅对无结果尾部继续确定性执行

**面试官：** 你已经应用到 R，但后面还有已提交命令没有结果；怎样确定它们是可执行尾部，而不是结果读取漏了？

**面试者：** 先通过日志服务的一致检索确认 R 是连续已提交结果前缀，后面的已提交命令确实没有结果。若找到 R+2 的已提交结果却缺 R+1，就违反了连续 AppliedSeq 协议，应该停止并调查读取或存储问题，不能把中间缺口当成可重算尾部。随后在有效 epoch 下从 R+1 逐条执行，每条仍须完整原子提交后才前推。

执行使用日志中固定的规范命令、规则版本和预留验证依据。预留凭据只在账户预留事务提交后签发，绑定账户、市场、intent、reservation 与载荷；恢复不重新按“现在账户还有多少钱”判断原请求，否则账务已推进会改变历史资格。凭据不独立 TTL 过期；迟到资格是否关闭由先前恢复出的 AbortIntent 标记决定，不能按重启时的时钟猜测。

## 第 7 层：升级和整数规则也必须可重放

**面试官：** 你要求固定规则，但崩溃期间恰好升级了代码和价格单位，旧命令还能用新版执行吗？

**面试者：** 不能默默使用当前默认配置。命令、结果和快照都标明规则、单位与格式版本，恢复者必须能读取旧结果，并为无结果尾部选择对应的历史执行规则。不支持该版本就拒绝激活，或走事先设计的有序迁移边界，不能靠修改配置文件让历史价格重新解释。验证签名需要的密钥标识或已固化验证证明也要可追溯，不依赖一把已被替换的当前密钥。

这里价格 tick 为 0.01、数量 lot 为 0.0001、quote unit 为 0.000001，整数 `p × q` 直接得到 quoteUnits，无需舍入，但仍须检查乘法上限。撮合遍历明确使用价格和 FIFO，不能依赖 Go map 遍历顺序。影响裁决的时间、随机标识或规则变更必须在首次命令中固定或成为有序输入，不能在尾部重算时调用当前时钟和随机数来改变成交对象。

## 第 8 层：恢复校验不能反过来重做账务

**面试官：** 固定版本后怎样判断恢复没有出错？账户可能已结转了部分结果，你会不会重新扣一次钱？

**面试者：** 恢复首先校验快照 hash、结果连续性、订单版本和数量守恒、价位与 FIFO 索引一致性，再核对已知位置的状态摘要。摘要规则要固定序列化顺序，不能把无序 map 的输出当状态 hash；校验失败时停止接管，不擅自丢订单或修改结果使 hash 对上。

撮合恢复只重建执行状态，不直接重做账户资产。可从已提交日志补发结果，账户按自己的 batchId 去重和 lastAppliedSeq 继续结转。正常 B1 的两笔成交已记账时，即使整批再发，也应仍只有 15,015 USDT 支出、10 返还、0.25 BTC 入账。账户进度落后于恢复后的撮合位置是允许的暂态，必须继续保留预留；不能为“对齐进度”直接释放或把账户游标改到 R。

## 第 9 层：快照完成不代表历史结果可以全删

**面试官：** 你说还要补发结果，快照已经到 R，R 以前的日志到底什么时候能清理？

**面试者：** 不能只看最新撮合快照。恢复依赖有效快照及后续日志，账户依赖尚未应用的完整结果；消费者从旧备份恢复还可能需要更早位置。清理策略应明确快照覆盖范围、结果归档位置、检索方式、保留周期及消费者可恢复的最低位置，确保所需数据仍能取回，再释放在线存储。

业务幂等与关闭标记还有更长的重放约束，不能因原订单离簿就随日志消失；可以保留摘要和可查询的原结果归档，但不得重新接受同一旧请求。归档也要验证完整性与可读性，不能仅记录“已备份”。如果所需结果和备份都不存在，就应承认无法按原契约恢复并停止相关业务，不能从最新盘口猜出过去双边账务，或宣布跳过历史缺口已经完成恢复。

## 第 10 层：完成追赶后才恢复裁决与服务承诺

**面试官：** 历史都保留好了，重放追上了，什么时候能开放接单？怎样用反例检查接管边界？

**面试者：** 要分开可靠受理和执行激活。恢复期间日志服务若仍有多数派，可以按约定受理并排队，但不能声称内存已就绪或给出未提交执行结果。恢复者须具有有效 epoch，加载并验证快照，应用连续已提交结果，查明不确定追加，确认未结果命令尾部的处理起点，才能按权威顺序继续裁决；积压过大时应背压，不能跳到最新命令。

我会设置同价两卖单及一个先关闭的意图，在结果追加响应丢失后崩溃，再恢复：已提交结果必须原样应用，FIFO 不能调换，关闭标记不能丢；无结果尾部才允许重新执行。再重复发送原批次，账户不能二次变更。旧 epoch 的恢复进程即使重建完全正确，也无权提交新结果。这个推演检验的是“恢复到哪个事实、凭什么继续”，不是声称某次重启已经通过生产验收。

## 本题收束

- **讲透的机制：** 快照固定完整结果边界，先恢复状态再应用已有已提交结果，仅对确认无结果的已提交命令尾部确定性执行，逐条原子提交并前推。
- **易错边界：** 原始 logIndex 不等于逻辑 commandSeq；AppliedSeq 不等于已受理上界；盘口总量不等于可执行快照；历史结果不重新撮合；撮合恢复不直接重做账户账务。
- **反例验证：** AbortIntent 已关闭并退款，随后一次结果提交响应丢失且引擎崩溃。恢复后投递迟到 Place、重复业务命令及原结果批次，关闭标记必须仍生效、原成交身份保持、资产无第二次变化；删除任一必要标记就应能暴露协议漏洞。
