# 大问题 3：怎样用订单簿实现价格优先与同价时间优先？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 把订单簿想成“先按价格分柜，再在每个柜子里排队”：价格选柜子，接纳顺序选队首。本文是零费链下现货模型；数据结构快，不代表成交已经可靠保存，也不代表金额不会溢出。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| CLOB / 订单簿 | 中央限价订单簿，保存尚可成交的买卖订单。 | 买单找最低卖价，卖单找最高买价，不拿 Go map 的遍历顺序选价格。 |
| 价格时间优先 | 先选更好的对手价格，同价再选先被合法接纳的订单。 | 更早挂出的高价卖单，也不能越过更便宜的卖单。 |
| maker / taker / 交叉 | maker 是原挂单，taker 是新来吃单者；交叉表示双方价格允许成交。 | 本文取 maker 价，能继续成交时不能把 taker 剩余直接挂起来。 |
| PriceLevel / 有序价位索引 | 把同一价格的订单放在一个价位，用有序结构找最优价。 | 买侧取最大价格，卖侧取最小价格，空价位要删除。 |
| FIFO / 双向链表 / head / tail | 先入先出队列；前后都有连接，head 是队首，tail 是队尾。 | 同价队首先成交；部分成交的老订单留在原位置。 |
| orderId → 节点 / 哈希索引 | 按订单编号直接找到它在队列中的位置。 | 撤中间订单不用从队首挨个找，摘链后也要删活跃索引。 |
| totalLeavesLots | 一个价位上全部订单剩余量的合计整数值。 | 成交或撤单后汇总也要一起减，不能链表变了、盘口总量没变。 |
| originalQty / cumFilledQty / leavesQty / canceledQty | 原始、累计成交、剩余和取消数量。 | 已接纳订单原始量等于后三项之和，活跃节点移除不等于删除历史。 |
| prioritySeq / commandSeq | 首次合法接纳的排队号，以及市场每条逻辑命令的处理号。 | 重试可能有新命令位置，但不能重分优先号或重复入簿。 |
| writer goroutine / 所有权 | 一个 Go 执行单元独占该市场可变订单簿。 | 查询拿只读副本，不把链表节点指针交给 HTTP 线程随意改。 |
| tick / lot / quoteUnits | 价格、数量、报价资产金额的整数单位。 | 本文依次为 0.01 USDT/BTC、0.0001 BTC、0.000001 USDT。 |
| int64 / 溢出 / 业务上限 | 整数也有最大范围，单笔与累计值都不能超过。 | 先检查再乘、再加；每单合法不保证整个价位或批次合计合法。 |
| 临时变更集 / ResultBatch | 先私下算完整变化，再组成整条命令的结果包。 | 未提交不发布，也不让下一条命令看见尚未成立的成交。 |
| AppliedSeq / epoch | 已提交结果进度与有效负责人的代次。 | 存储同时检查当前代次和预期前序进度，防旧主或错误位置写入。 |
| AbortIntent / 关闭标记 | 持久记录一次下单意图以后不能再被接纳。 | 超时后关闭先执行，就能挡迟到 Place；标记也必须可恢复。 |
| 快照 / 重放 | 从某个已提交状态开始，按之后的历史结果恢复。 | 同价仍按原 prioritySeq 建队列，不能按 map 遍历或订单号排序。 |
| O(1) / O(log P) / M / L | 描述操作量随规模怎样增长；P 是价位数，M 是触及订单数，L 是删掉的价位数。 | 定位撤单平均 O(1)，删空价位仍需树操作；扫 M 单不可能整体常数成本。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，要按最高 60,100 买 0.25 BTC。卖侧有乙的 0.10@60,000 和丙的 0.20@60,100，卖出的币都已预留。系统为甲占 15,025 USDT，撮合先到最便宜的 60,000 柜子取队首乙，再到 60,100 取丙。乙全卖完，节点和空价位都移除；丙卖出 0.15，原节点留下 0.05，不重新排队。甲实际花 15,015，账务完成后返 10，最终为 4,985 USDT 和 0.25 BTC。

同一个负责人需要同时维护订单对象、队列连接、按编号找节点的索引，以及每档总剩余量。部分成交只改数量，不改原优先级；撤单排到自己时，按真实剩余摘掉节点并减汇总。比如从初始状态另试买价 60,000 的 B2，买到 0.10 后还剩 0.15，预留 9,000；没有后续成交时，撤掉这 0.15 才释放 9,000。不能拿客户端原先看见的数量直接退款。

这些链表动作先在临时变更集中算，价格、数量、价位总量和金额都先检查精度与上限。完整结果与执行进度提交成功，才安装到内存并发布；响应丢失先查是否已提交，不直接继续下一单。重试占了新的命令位置，也只记空效果结果并引用原裁决，不让老订单再次挂入队尾；超时需要放弃时，则用同序列的关闭标记封住迟到下单。

有一天引擎在结果已提交、内存尚未全部安装时崩溃。恢复者先读一致快照，再应用后续已提交结果，重建原价格分组和同价优先序。即使某张同价老单经历部分成交和重试，仍要排在后来的单前；已有成交不再撮合。索引、队列和汇总都核对一致后，才继续无结果的命令尾部。所谓高效，是每项操作的成本清楚，不是把扫单、持久化和恢复全部说成 O(1)。

**流程位置与核心机制：** 本题位于“命令可靠受理与排序 → 撮合裁决 → 完整结果提交”，重点是把价格时间规则落实为价位索引、FIFO 队列和撤单定位，并说明这些结构怎样跨越持久化与恢复边界；不另行展开账户系统或主备专题。

**必要前提：** 沿用总览的 BTC/USDT 链下托管现货 CLOB：仅限价 GTC、maker 价成交、零手续费、买卖双方不同账户，每交易对一个有效写入者。CommandLog 先多数派提交，引擎才按序执行；完整 ResultBatch 与 AppliedSeq 原子提交后才发布。账户位于同一事务数据库，按序消费完整批次，双边结转、去重和进度同事务提交。以下案例是教学推演，不是个人经历或实测结果。

## 第 1 层：先把价格时间规则变成唯一选择

**面试官：** 怎样用订单簿保证价格优先与同价时间优先？你先说明每次究竟选谁，而不是直接报数据结构名称。

**面试者：** 买单找最低卖价，只要卖价不高于买方限价就能成交；卖单找最高买价，只要买价不低于卖方限价就能成交。先选最优对手价位，再选该价位最早接纳、仍有剩余量的订单。成交量是双方剩余量的较小值，成交价取已在簿中的 maker 价格。

因此必须分开两种顺序：不同价位比较价格，同一价位比较权威接纳顺序。不能把全部订单只按到达时间排队，也不能按买卖双方报价的平均值成交。

实现上我会用买卖两套有序价位索引，每个价位保存 FIFO 双向链表，再加一个 `orderId → 节点` 哈希索引。GTC 的剩余量进入自己方向的队尾；只有不能继续交叉成交时才挂单，不能留下仍可成交的交叉盘口。

## 第 2 层：从两级顺序落到节点、字段和所有权

**面试官：** 你选择了“有序价位＋FIFO＋订单索引”。如果要支持中间节点删除和价位汇总，具体怎样组织，Go 中谁能改它？

**面试者：** 价位索引可以选平衡搜索树，以整数 `priceTicks` 为键：买侧取最大键，卖侧取最小键，缓存最优价位指针。Go 的普通 map 不提供有序遍历，不能拿遍历顺序充当价格顺序。

每个 `PriceLevel` 保存 `priceTicks、head、tail、totalLeavesLots`。每个订单节点保存 `prev、next、level`，并引用唯一订单对象；订单对象包含 `orderId、accountId、intentId、reservationId、side、priceTicks、originalQty、cumFilledQty、leavesQty、canceledQty、prioritySeq、version`，数量都用 lots。`orderId` 索引指向这个节点，不能再复制一份独立剩余量，否则撤单与撮合可能各改各的。

每交易对由一个 writer goroutine 独占这些可变对象。查询和行情获得只读值副本或不可变快照，不拿链表节点指针，更不能让 HTTP goroutine 直接摘节点。单写者消除了结构内部的并发写竞争，但还没有解决崩溃时哪些修改算数。

## 第 3 层：沿节点变化推演连续吃单与部分成交

**面试官：** 既然节点由单写者维护，一笔买单连续吃两个价位时，哪些字段、链表和索引要一起变？部分成交会不会重新排队？

**面试者：** 每轮读取最优卖价及其队首，判断是否交叉，再计算 `q = min(taker.leavesQty, maker.leavesQty)`。双方 `leavesQty` 减 q、`cumFilledQty` 加 q，相关订单版本递增，maker 价位的 `totalLeavesLots` 减 q，同时记录成交身份、价格与数量。

maker 仍有剩余量，就保持原节点位置与 `prioritySeq`；全部成交才摘链、删 `orderId` 活跃索引。价位变空还要删树节点并更新最优价位。终态订单仍可保存在生命周期状态表中，不能把“删活跃索引”理解成抹掉订单历史。taker 若有剩余，停止吃单后才按自身价格入簿。

贯穿案例中，乙的 S1 为 `0.10@60000`，丙的 S2 为 `0.20@60100`，卖出 BTC 均已预留。甲有 20000 USDT，B1 买 `0.25@60100`，预留 15025。先成交 S1 的 0.10，再成交 S2 的 0.15；S1 及 60000 空价位被移除，S2 原位剩余 0.05。B1 全成，不入买簿。

两笔支付分别为 6000、9015，合计 15015；完整批次结转后返还价差 10，甲最终为 4985 USDT、0.25 BTC。这里的字段变化先是临时计算，提交边界在后面继续说明。

## 第 4 层：把队首撮合推广到任意位置撤单

**面试官：** 你刚才只从队首摘全成订单。现在要撤同价队列中间的订单，而且它可能刚部分成交，怎样既不遍历队列，也不删错数量？

**面试者：** Cancel 进入与 Place 相同的命令序列，由 writer 执行。先验证账户归属，再用 `orderId` 找活跃节点，读取执行到此时的 `leavesQty = r`，修改前后邻居及 head、tail，价位总量减 r，删除活跃索引；订单 `canceledQty` 加 r、`leavesQty` 置零并更新版本。价位最后一个节点被删时，同样移除有序索引并刷新最优价位。

不存在或已终态时返回相应确定结果，不能从一个失效指针再摘一次，也不能回退累计成交。定位和摘链是哈希平均 O(1) 与链表 O(1)，但删除空价位仍有树操作成本。

B2 是从相同初始卖盘重新开始的独立变体，只把买价改成 60000：买 0.25，预留 15000；成交 S1 的 0.10，支付 6000，剩余 0.15 入买簿，继续预留 9000，可用为 5000。若无后续成交，撤单取消 0.15，账务按结果释放 9000，可用变为 14000。若新成交排在撤单前，先扣成交量，再撤真实剩余，不能照用户请求的原数量退款。

## 第 5 层：让权威排队顺序经得住重试和迟到

**面试官：** 你说撤单看序列中的实际剩余。那跨网关请求、部分成交后的重试，以及超时后迟到的 Place，怎样不插队、不重复挂单？

**面试者：** `prioritySeq` 取订单首次合法接纳时的命令位置，不取客户端时间或 goroutine 抢锁顺序。部分成交不改它，重试也不重新入队。本模型没有改单能力，不能悄悄让修改价格后的订单保留旧优先级。

Place、Cancel、AbortIntent 共用每交易对连续的逻辑 `commandSeq`；它不是混合日志的物理偏移。每个序号都有结果批次，无成交也推进。业务请求重投可以获得新 seq，但必须命中持久去重，提交空效果批次并关联原结果，不再次占资、撮合或入簿。

请求键为 `accountId + commandType + clientRequestId`；同键比较规范化载荷，相同返回原意图或结果，不同则冲突。Place 还须绑定 `intentId + reservationId + 不可变载荷`，同一意图不能换请求键就生成第二个订单。预留凭据来自已提交预留，验证依据固化，不能因墙上时钟 TTL 到期而失效。

超时要关闭时提交 AbortIntent：它先到就持久关闭意图，拒绝迟到 Place；Place 先到则只撤实际剩余，已成立成交仍保留。关闭标记和去重状态也必须持久化，不能重启后只恢复订单链表。至此保证的是一次合法接纳只产生一次有效变化，但数值本身还须能精确表达。

## 第 6 层：给一次合法变化加上精度与聚合上限

**面试官：** 即使只接纳一次，一笔单也可能扫很多订单。价格乘数量、价位总量和累计金额会不会溢出，能不能等计算后再检查？

**面试者：** 不能。价格 tick 为 `0.01 USDT/BTC`，数量 lot 为 `0.0001 BTC`，报价资产最小单位为 `0.000001 USDT`，所以 `quoteUnits = priceTicks × qtyLots`，不需要除法舍入。API 十进制字符串直接精确解析，拒绝不整 tick、lot 的输入，不先经过 float64。

例如 B1 为 `6010000 ticks × 2500 lots = 15025000000 quoteUnits`，即 15025 USDT。使用 int64 时，正数 p、q 相乘前检查 `p <= MaxInt64 / q`，还要满足固定业务上限；溢出后再判断负数已经太晚。

聚合也要先检查：非负 a 加 b 前判断 `a <= MaxInt64-b`，减量前确认足够。检查对象不仅是单笔成交额，还包括 `totalLeavesLots`、累计成交量、批次累计金额及其下游可表达范围；账户结转也须在每次余额加减前检查范围，不能只验证单笔订单。数量守恒式 `originalQty = cumFilledQty + leavesQty + canceledQty` 的核对也不能用可能溢出的裸加法。

预留前先做订单金额检查；入簿及撮合的所有聚合变化在临时变更集中检查，执行固定版本的容量规则。若剩余入簿会使价位聚合越界，整条命令形成确定拒绝，不能先提交几笔成交再临时宣布剩余部分失败。整数精度解决舍入问题，不自动解决容量问题。

此类拒绝结果必须同时持久关闭原意图，给账户提供按结果顺序释放原预留的依据，不能只返回错误而留下迟到 Place 的执行资格。未合法接纳的请求只记录 `requestedQty` 与拒绝原因，不创建活跃订单数量账本；不能记成 `originalQty > 0`，却让 `cumFilledQty、leavesQty、canceledQty` 三者全为零。

## 第 7 层：临时结构变化怎样跨过结果提交边界

**面试官：** 你已经在临时变更集中检查完数量和金额。如果链表先改了，ResultBatch 写失败，后面的订单会不会读到根本不存在的成交？

**面试者：** 因此不能先改权威内存再赌写入成功。writer 基于当前已提交状态，用字段副本与摘挂动作形成私有变更集；完整批次包含成交、全部订单变化、价位变化所需信息、预留处置依据、去重结果及意图关闭标记。成交 ID 固定为 `symbol + commandSeq + matchIndex`，不能重试时重新生成。

对序号 s，存储校验有效 epoch 和前序 `AppliedSeq = s-1`，再原子提交 ResultBatch 与 `AppliedSeq = s`；空效果批次也如此。提交前不发布成交、盘口或最终订单回报。提交失败且确定未生效，丢弃临时变更；提交响应丢失则先查询该批次，不能贸然重算覆盖，也不能继续执行 s+1。

提交成功后安装内存变更，再处理下一命令；若安装中途失败，停机重建，不能回滚已提交成交。发布端从已提交批次读取，内存和只读快照都不得泄漏未提交节点。

账户消费者只按序处理完整批次，在同一数据库事务内提交双边资产、分录、去重和进度。失败释放须依据已提交关闭或拒绝结果，且不能越过前序成交；迟到 Place 的拒绝也不能让已关闭预留再退一次。订单终态不等于既有成交义务消失。

## 第 8 层：恢复同一队列，再核算真实复杂度

**面试官：** 如果结果已经提交、内存链表还没装完就崩溃，怎样恢复原来的同价先后？加上这些恢复索引后，你还会说撮合整体 O(1) 吗？

**面试者：** 不会。先加载已提交结果位置 A 的一致快照，包含活跃订单及数量、`prioritySeq`、去重状态、关闭标记和规则版本。按价格分组，同价按原 `prioritySeq` 重建 FIFO，再重建节点索引和价位总量；不能按 map 遍历、客户端时间或 orderId 排序。

之后按序应用 A 后的已提交 ResultBatch，恢复到最后结果位置 R。已有结果的命令不再撮合；只有 R 后已提交 CommandLog、尚无结果的连续尾部，才按固定规则继续计算。恢复不能让已关闭意图复活，也不能把部分成交订单重新追加到同价队尾。检查每个活跃订单只有一个节点、队列优先序递增、价位汇总等于节点剩余量之和，且没有空价位。

设 P 为价位数：查找或新建价位 O(log P)，已定位价位追加与部分成交更新 O(1)；撤单哈希定位平均 O(1)，摘链 O(1)，空价位删除 O(log P)。缓存最优指针可 O(1) 读取，但移除最优价位仍要维护索引。一次吃 M 个订单、删 L 个价位，核心更新约为 O(M + L log P)，另加剩余入簿成本；完整结果构造、持久化和恢复也不是常数成本。

用一个独立反例检查公平性：同价卖单 A 先于 B，A 部分成交后重试并经历重启，下一笔买单仍应先吃 A 的剩余量；若吃了 B，说明重试或恢复改变了队列。如果树里已经没有某价位，最优指针却仍指向它，下一笔买单也可能读到幽灵订单，所以索引一致性和 FIFO 一样必须检查。

**本题收束**

- **机制：** 有序价位决定价格优先，同价 FIFO 与首次合法接纳的 prioritySeq 决定时间优先；订单节点索引支持撤单，完整结果边界让这些结构可恢复。
- **易错边界：** 部分成交不重排，重试不重复入簿，空价位要清理；单 writer 不等于持久原子性，整数不等于不会溢出，撤单定位 O(1) 不等于整次撮合 O(1)。
- **反例验证：** 手工核对 B1 的两笔 maker 价成交、10 USDT 返还与 S2 剩余 0.05；独立核对 B2 撤后可用 14000。再推演“同价 A 部分成交 → 重投 → 结果已提交但内存未装完即崩溃 → 恢复”，A 必须仍先于 B，既有成交不能再生成。这些是设计自查与预期，不表示运行过工程或测试。
