# 大问题 8：怎样避免成交丢失、重复记账和乱序释放资金？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文讲一笔买单已经撮合后，怎样把全部成交可靠送到账户，而且不重复扣钱、不只给一边入账、不抢先退款。基线是链下托管的 BTC/USDT 限价现货，未成交量继续挂单，按先挂订单的价格成交，费用为零；所有参与账户在同一个事务数据库里。重点是“完整事实先成立、运输允许重复、账务整批生效”，不假设消息队列能保证网络恰好只送一次，也不把跨账务分片结算当作已有能力。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| `CommandLog` 与可靠受理 | 市场按顺序保存已接下的命令。 | 命令达到持久化多数派提交才算可靠受理，但这还不是撮合结果提交，更不是资产到账。 |
| `ResultBatch` | 一条命令引起的完整业务结果包。 | 全部成交、订单变化、预留处置、关闭及幂等结论，与新撮合进度在单个原子记录里确立，不能先公布半批。 |
| `batchId = symbol + commandSeq` | 市场名加命令逻辑序号，构成结果包的固定身份。 | `symbol` 如 BTC/USDT；补发时沿用原身份和原内容，不另造一份“新成交”。 |
| `matchIndex` 与成交身份 | `matchIndex` 是一条命令内部第几次匹配。 | 成交用市场、命令序号、匹配序号唯一标识，不在发送时随机生成新的 UUID，即通用唯一标识符。 |
| `orderChanges` / `reservationActions` | 订单变化清单 / 预留资金处置清单。 | 接收方必须拿到这些完整依据，不能只凭一条成交消息猜该扣多少、退多少。 |
| `AppliedSeq` 与 `Raft logIndex` | 前者是完整撮合结果已提交到哪条逻辑命令，后者是底层复制日志位置。 | 日志混有命令与结果等记录，两者不能当作同一序号或物理偏移使用。 |
| `epoch` 与 CAS | `epoch` 是主写任期；CAS 是 Compare And Swap，即“前值仍符合预期才写”。 | 权威日志或存储同时检查当前任期和前序撮合进度，拒绝旧主新写或基于错误前序提交结果。 |
| 提交超时未知 | 没收到提交回复，不代表那次提交没成功。 | 按批次身份查权威已提交记录；存在就用原结果，无法查明则暂停该市场，不能猜着处理下一条。 |
| 至少一次交付 | 发送方会补发，所以同一结果可能抵达多次。 | 消息队列只是运输工具；可重投加接收方业务去重，才让资产有效变化一次。 |
| `PENDING` / `APPLIED` | 待结转 / 已完成账务结转。 | 执行已全成时账户仍可能是待结转；只有账户事务完成，才能说这批钱和币已到账。 |
| 分片暂存与完整性校验 | 大包先拆着传，收齐并核验后才交给记账。 | 分片号、总数、版本和整体 hash，即内容校验摘要，要相互吻合；缺片或同号异内容不能先入半笔账。 |
| 同库双边事务 | 买方、卖方及全部关联资产在同一个数据库事务里一起变更。 | 整条命令的全部成交、预留、分录、去重和进度共同成功或共同回滚，不是先买方后卖方。 |
| `lastAppliedSeq` | 账户已经完整结转到哪条市场命令。 | 它是账务进度，不是撮合进度；只接受下一连续批次，无成交和空效果批次也要推进。 |
| 空效果批次 | 新命令位置上对旧业务请求作出的“已处理”回执。 | 例如 103 引用 100 的原结果，账户只推进到 103，不再执行 100 的成交。 |
| 市场进度锁与余额行锁 | 前者防同市场乱序，后者防多个业务同时改同一笔钱。 | 多市场共享甲的 USDT 时仍需统一锁序；死锁等可重试冲突必须整批回滚，不能留半批效果。 |
| `Cancel` / `AbortIntent` | 撤单 / 关闭原下单意图。 | 只按裁决释放实际取消部分；关闭先送到也不能越过前面尚未结转的成交。 |
| 独立消费者进度 | 账户、私有回报、公共行情各记各的处理位置。 | 行情收到、发送器发过、账户暂存过，都不能证明双边账务已提交。 |
| 结果保留与消费者恢复契约 | 保存足够历史，让落后的消费者或旧备份能找回欠账。 | 引擎有最新快照不等于账户历史已结清；归档要能按逻辑位置取回完整结果，缺历史时不能跳进度退款。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，买入 0.25 BTC，限价 60,100，先预留 15,025 USDT。市场依次匹配到 0.10 BTC、价格 60,000 的卖单和 0.15 BTC、价格 60,100 的卖单，因此应支付 15,015 USDT、返还价差 10 USDT。引擎不能边算边把第一笔当作正式成交发出去，而要把两笔成交、所有相关订单变化、预留动作、业务去重结论及新的撮合进度装成一个完整结果包，原子提交。若提交回复丢了，市场暂停前推，先查同一批次是否已经成立；旧主的新写还必须被权威存储的任期检查挡住。

结果包确实已提交，发送器却只发出第一部分就崩溃。换一个发送器后，按市场和命令序号找回原包继续补发，成交内部序号也保持不变；不会再让甲撮合一遍。如果包太大必须拆片，账户先持久暂存，收齐后检查分片数、版本和整体内容摘要，期间没有任何资产效果。收到第一笔成交或“订单全成”回报，都不能推断其余明细齐了。同号出现不同内容，要阻断并查原日志，不能当成普通重复吞掉。

完整载荷终于到齐，账户先锁住本市场账务进度，再按统一顺序锁住整批涉及的账户资产和相关记录。一个本地事务同时处理两笔成交的买卖双方：从买方 USDT 预留转给卖方，从卖方 BTC 预留转给买方，退回价差，并保存分录、批次去重记录及连续账务进度。成功后甲才真正得到 0.25 BTC，可用 USDT 为 4,985。若事务中途失败，整批回滚；若事务成功但确认丢了，重送核验原批次后只返回原处理结果。市场内串行不能替代共享余额锁，因为甲的 USDT 还可能同时被其他市场使用。

这时运输又把一条撤单或关闭结果提前送到，但它前面缺一个结果包。即便后到的结果没有新成交，账户也不能跳过缺口，必须先补齐前序；同一业务重投占用的新命令位置，则有自己的空效果结果包，只推进进度，不重付原成交。若甲是在“仅有第一档卖盘”的另一种盘面中成交 0.10 BTC 后关闭余下 0.15 BTC，正确顺序就是先支付 6,000、退价差 10，再释放取消余量对应的 9,015 USDT，不能因订单已终态就退掉全部 15,025 USDT。关闭阻止未来执行，不取消已经成立的付款义务。

后来账户服务停机很久，甚至从旧备份恢复，而行情消费者早已追平。系统仍要按照账户自己的持久进度从日志或归档补齐完整结果，不能借行情进度或引擎最新快照宣称“账已结完”。若历史不足，就暂停该市场的账务应用和退款，进入备份、归档与核对恢复流程；积压过大还应限制新受理。可靠交付承诺的是事实不丢、能够去重和按序补齐，最终处理能力仍要靠容量设计与恢复契约保障，这些都是待验收的设计要求，不是已经通过的测试结果。

**流程位置与核心机制：** 覆盖撮合结果确立、完整批次交付和账户结转，重点是运输可以重复、资产作用不能重复，且退款不能越过旧成交。请求身份与主备选举不是本题主线，但相应约束不能省略。

**必要前提：** 沿用链下托管 BTC/USDT 现货 CLOB、限价 GTC、maker 价、零费用、每市场单写者。参与账户位于同一个事务数据库；复制日志提供持久化多数派提交、epoch 隔离和前序 AppliedSeq 的 CAS 校验。这里描述生产设计与预期行为，不声称已经实现或测试通过。

## 第 1 层：成交确定与消息发送分开

**面试官：** 撮合一次产生两笔成交，引擎发出第一笔后宕机，怎样保证第二笔不丢？

**面试者：** 我会先保证结果已经完整成立，再讨论消息有没有送到。引擎对一条已提交命令形成完整 ResultBatch，把全部成交、相关订单变化、预留处置依据、关闭和幂等结果，以及新的 AppliedSeq 放进单个原子记录提交。提交前仅是临时计算，不能发布为成交事实；提交后整批结果都能按位置找回。

发送器只读取已提交结果日志，记录发送进度并允许重投。它发出一部分就崩溃，恢复后重取整批即可，不要求撮合内存记住哪条消息发过。若引入消息队列，队列只是运输层，不让引擎同时双写日志和队列来制造新的原子性缺口。账户认完整批次，不凭第一笔成交或一条全成通知推断其他资金变化。

## 第 2 层：完整批次必须能被唯一识别

**面试官：** 你说重取整批，但发送器换实例后，怎样确定拿到的是原来的批次，而不是又生成了一组成交？

**面试者：** 批次身份固定为 `symbol + commandSeq`，成交身份固定为 `symbol + commandSeq + matchIndex`。matchIndex 按本次确定的匹配顺序编号，不在发送时生成 UUID。日志保存规则与单位版本、成交明细、完整 orderChanges、reservationActions、请求裁决及关闭标记，保证接收方能够验证完整性并关联原预留。

ResultBatch 的 AppliedSeq 是已经形成完整结果的逻辑命令位置，不是底层 Raft logIndex。日志里混有命令和结果记录，逻辑 commandSeq 由服务连续分配并可按位置检索。为发现损坏和内容冲突，可保存批次内容 hash、条数和版本。相同 batchId 对应不同内容必须阻断并告警，不能按“已经见过这个 ID”吞掉差异；身份稳定不代表内容天然可信。

## 第 3 层：提交超时不能直接重算下一条

**面试官：** 有稳定批次身份，但追加结果超时了，引擎不知道结果提交没有，能否先处理下一命令再回来补？

**面试者：** 不能。CommandLog 受理与 ResultBatch 裁决是两个提交边界。结果追加校验当前 epoch 和预期前序 AppliedSeq，把整批结果与新进度一起提交；追加响应丢失后，必须先按批次身份查询已提交状态。结果已存在就采用原内容，不再产生第二组；确认未提交且仍具有效写权限，才可在原前序状态上重试。

如果暂时无法查明，就暂停该市场前推。下一条的撮合依赖前一条究竟减掉了哪些数量，猜测成功或失败都会污染后续结果。内存可以保留候选变更，但没有提交证明就不能生效或发布。旧 epoch 的结果追加必须由日志或存储拒绝，不是等下游发现两份冲突成交后再补救。

## 第 4 层：结果成立后仍允许重复投递

**面试官：** 引擎暂停查明了提交状态，发送器也拿到原批次；账户写完后回执丢了，还要不要再发？

**面试者：** 要允许再发，因为发送方无法从超时区分“账户没收到”和“账户已提交但回执丢失”。发送成功回执最多帮助减少重复，并不定义资产是否已经变化。可靠边界是结果可找回、可重投，账户按持久业务身份判断是否已经应用。

不同消费者有独立进度。公共行情已经收到，不代表账户已结转；发送器记下已发送，也不能作为删除账户所需结果的依据。私有回报可以先报执行已全成，但结转状态仍为 PENDING，只有账户事务完成才能变为 APPLIED。旧进程重复发送先前已提交结果只是重复运输；它临时算出的内容即使字段齐全，也不得进入发布路径。

## 第 5 层：运输分片不等于账务分批

**面试官：** 你要求整批，但大订单有很多成交，网络上必须拆成多条消息，账户收到前半批能否先入账？

**面试者：** 不能把网络分片变成部分账务提交。可以先将分片放入不产生资产效果的持久暂存区，按 batchId、分片号、总数和整体 hash 组装；补齐后核对身份、版本、明细数量及完整载荷，才能交给账户事务。重复片校验一致后忽略，内容冲突或缺片则阻断该市场后续应用并补取原日志。

更直接的运输方式是消息只携带批次位置和完整性信息，由账户按位置拉取完整已提交记录。无论哪种方式，暂存成功不等于记账成功。还要在准入时约定单命令规模和存储可支持的最大批次，不能等结果已成立后因事务太大而任意拆成先买方后卖方。改变完整批次的原子边界，需要另行设计清算协议，不属于这套基线已经支持的能力。

## 第 6 层：将双边变化和去重共同提交

**面试官：** 完整载荷已经到齐，账户事务具体包含什么，怎样避免加完买方 BTC 后卖方入账失败？

**面试者：** 一个本地事务覆盖整条命令的全部双边余额变化、预留扣减与释放、账务分录、批次去重记录和市场 lastAppliedSeq。先验证原预留身份与结果动作的一致性，再按每笔成交扣买方 USDT 预留、增加卖方 USDT，扣卖方 BTC 预留、增加买方 BTC，并执行对应价差返还和确定退款。整个事务共同成功或共同回滚。

不能先提交“已消费”再改钱，也不能先提交资产再单独补去重。事务失败时进度不动、预留仍在；提交响应不确定时先查同库批次记录，不能盲目再扣。事务提交成功而消费确认丢失，重投命中原批次及内容核验后返回原处理结果，没有第二次资产变化。这才是有效一次的账务作用，不是对网络恰好投递一次的承诺。

## 第 7 层：连续进度覆盖无成交与重投命令

**面试官：** 你让去重和 lastAppliedSeq 一起提交，那某条命令没有成交，或者重复请求占了新序号，进度怎么走？

**面试者：** 每条逻辑命令都必须有结果批次，包括挂单、拒绝、撤单、关闭，以及同业务身份重投的空效果裁决。账户事务先锁市场进度行：序号是 lastAppliedSeq 加一，才应用当前批次；更大则有缺口，先补前序；已经处理的位置核对原批次身份和内容凭据后返回原结果。不能因“这一条没成交”就在结果流里省掉它。

例如原 Place 在 100 裁决，重投在 103；103 的 batchId 是市场加 103，但引用 100 的原业务结果且资产动作为空，账户只推进到 103，不能再执行 100 的成交。对历史批次的核验依赖持久处理记录或可验证归档，不能只看一个数字就接受任意旧内容。序号缺口也不按超时跳过，因为缺的可能正是后续退款必须先履行的成交义务。

## 第 8 层：市场进度锁解决不了共享账户竞争

**面试官：** 每个市场锁了自己的进度，两个市场却都在改甲的 USDT，是否仍会丢更新或死锁？

**面试者：** 会，所以市场串行和账户并发是两层约束。消费事务先取得本市场进度行锁，读取并验证序号，再收集整批涉及的余额行，以全局统一的账户、资产排序加锁；预留、分录等其他行也纳入统一锁定规范。跨市场事务不会因各自按买卖方向反向取余额锁而互相等待。

预留服务和结转服务也必须遵守兼容的锁顺序，不能一条路径先拿余额再等待进度，另一条反过来。需要的余额行可预先创建，或采用确定的创建规则，避免首次插入绕开锁顺序。数据库隔离和条件更新保证余额、预留不负；遇到死锁或可重试冲突，整批事务回滚后重试，不能带着部分结果推进进度。这里依赖共享事务数据库，不把跨账务分片的双边原子性当成现成能力。

## 第 9 层：退款必须排在既成成交之后

**面试官：** 锁顺序解决了并发，但关闭结果先送到，甲急着要退款，你能否先处理关闭再补缺失成交？

**面试者：** 不能。AbortIntent 或 Cancel 的结果只授权退实际取消部分，账户还必须先结转旧成交。运输先后不改变市场裁决先后，发现关闭批次前有缺口就补齐，不能把“订单已终态”翻译成“预留全部可退”。

以独立变体说明：只有 S1 可成交，B1 预留 15,025，成交 0.10@60,000 后关闭余量。前一成交批次应支付 6,000、退价差 10，关闭批次再退余量对应的 9,015。如果先按终态清空预留，就把那 6,000 的义务也退了出去。账户按连续位置处理使退款不会越过旧成交；即便关闭批次无新成交，也必须保留它自己的释放动作和处理身份，重投时不再退款。

## 第 10 层：补发依赖结果保留与消费者恢复契约

**面试官：** 你靠补齐缺口保护退款，但账户停机很久，日志已经清理了，拿什么补？

**面试者：** 结果保留必须覆盖消费者恢复，而不是只看引擎是否有最新快照。清理前要知道账户已持久应用到哪里、归档能否按市场逻辑位置取回完整结果、消费者备份恢复后会不会退回更早位置。账户不能直接把进度改到最新快照，因为撮合快照不包含它尚未履行的双边账务。

没有足够历史时应暂停应用和退款，按既定账务备份、结果归档及核对流程恢复，不能跳过缺口宣称追平。容量上监控结果积压、最老未结转位置与预留占用，必要时限制新受理；保存不丢事实和最终能够处理是不同承诺。手工反例可以设置为“仅收到半批、事务确认丢失、关闭先到、账户恢复到旧备份”：每种情况下，都应能找回原完整批次、按序结转且资产只变化一次。这是恢复契约的验收设计，不是测试报告。

## 本题收束

- **讲透的机制：** 完整 ResultBatch 与 AppliedSeq 原子确立事实，从已提交结果至少一次交付，账户将双边资产、分录、去重和连续进度放在同一本地事务中。
- **易错边界：** 发送成功不是记账成功；运输拆片不能拆散账务原子性；重复业务的新序号不是新成交；市场进度锁不能代替共享余额锁；引擎快照不能代替账户历史结转。
- **反例验证：** 让 B1 两笔成交只到达第一部分，再送来关闭批次，并在最终账户提交后丢弃确认。预期是缺片和缺口期间不退款，补齐后完整结转，重投不新增余额或分录；任何单边入账或第二次退款都违反设计。
