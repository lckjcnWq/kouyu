# 大问题 10：主备怎样复制与切换，怎样避免双主和丢失已确认数据？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文讲的是“换一个进程继续干活，怎样不丢已答应的事、不让两个人同时有效写入”，不是从零实现共识算法。案例仍为链下托管的 BTC/USDT 限价现货，未成交部分继续挂单，按先挂订单价格成交、费用为零；每市场单写，账户共用事务数据库。复制日志已经提供持久化多数派提交、任期隔离和前序进度校验，本文在这些前提上推演接管协议，不承诺网络分区时人人能成交，也不报告实测切换耗时。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 主节点 / 备节点 / 每市场单写者 | 主节点负责有效裁决，备节点保存或跟进可接管状态；同一市场只能有一个有效写入来源。 | 单写不能只靠进程自觉，最终必须由权威日志或存储拒绝不合资格的新写入。 |
| `CommandLog` 与可靠受理 | 把市场已接下的命令按权威顺序持久保存。 | 只有输入达到多数派持久提交，才能说可靠受理；没回复可能是未知，不等于没提交，更不等于没成交。 |
| `ResultBatch` 与裁决成立 | 一条命令的全部成交、订单与预留变化、关闭和去重结论构成一个完整结果包。 | 整批与新的撮合进度原子提交才算裁决成立；它和命令受理不是同一次事务。 |
| 持久化多数派 | 按共识规则，有足够副本真正持久保存并确认提交。 | 三副本取两份只是示例；某个备机内存收到或旧主仅写本地盘，都不等于满足基线承诺。 |
| 已提交输入前缀 / 结果前缀 | 前者是连续受理到哪里，后者是连续裁决到哪里。 | 接管必须继承两者；两者之间可有已接下、尚未形成结果的命令，不能混成同一进度。 |
| `epoch` | 单调递增的主写任期，相当于权威服务发的当班号。 | 拿到新任期不代表订单簿已恢复好；旧主复活后不能继续拿旧号提交新结果。 |
| fencing token 与权威围栏 | 用任期作为“存储真的会检查的写入凭证”。 | 新任期生效要在权威服务提交，并与命令、结果追加串行裁决；本地标志、Redis 锁或租约计时不能代替它。 |
| CAS 与前序 `AppliedSeq` | CAS 是 Compare And Swap，即“前序仍是我预期的位置才准写”。 | 任期检查管谁能写，CAS 管基于哪个状态写；同任期重复工作线程也不能覆盖已有结果。 |
| `batchId`、`tradeId` 与 `matchIndex` | 批次身份、成交身份，以及命令内部第几次匹配。 | 批次用市场加命令序号，成交再加匹配序号；同号不同内容必须阻断调查，不能最后写入覆盖前者。 |
| `commandSeq` / `Raft logIndex` | 市场业务命令的连续逻辑号 / 底层复制日志索引。 | 底层还穿插结果与控制记录，不能用日志索引或物理偏移加一直接算下一条待撮合命令。 |
| 一致快照与结果重放 | 先加载完整结果边界上的状态底片，再按原结果补齐后续变化。 | 已提交结果只应用、不重撮合；只有确认无结果的已提交命令尾部才继续执行。 |
| 热备、FIFO 与状态 hash | 热备平时跟进结果；FIFO 是同价先到先成交；hash 是核对状态的内容摘要。 | 热内存必须保留队列、数量、幂等和关闭标记等，并与权威结果边界核对，不能只数日志条目就升主。 |
| 领导权与执行激活 | 前者是获准当班，后者是状态追平、验证通过后能安全裁决。 | 恢复期间可按约定受理排队，但未恢复的内存订单簿不能开始执行。 |
| 历史补发与非法新写 | 重送已经成立的旧事实，与失权后创造新事实是两件事。 | 旧任期已提交结果仍可合法补发；围栏拒绝旧主新写，不能顺手把所有带旧任期的历史结果都作废。 |
| `lastAppliedSeq` 与同库双边事务 | 账户的连续结转进度，以及买卖双方全部资产一起提交的事务。 | 账务、分录、批次去重和该进度共同提交；补发可重复运输，资产只能有效变化一次。 |
| CLOB 与网络分区 | CLOB 是 Central Limit Order Book，即集中限价订单簿；网络分区是节点彼此失联。 | 不能让两个分区独立消耗同一卖单，再指望事后无损合并价格时间优先顺序；少数派不能承诺可靠受理或成交。 |
| `AbortIntent` 与 TTL | 前者是正式关闭下单意图的命令；TTL 是 Time To Live，即自动过期时长。 | 预留后提交未知，要按原身份查询或有序关闭；不能靠过期直接解冻，退款还须先履行前序成交。 |
| 结果归档与消费者恢复契约 | 保存下游尚需的完整结果，并约定旧备份能恢复到哪里、怎样补齐。 | 主备都追平不等于账户已结账；账户数据库自身也须有兼容的高可用和备份方案，不能仅复制订单簿就宣称资产可恢复。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，买入 0.25 BTC，限价 60,100，账户在同一数据库事务中预留了 15,025 USDT。命令先被复制日志的多数派持久提交，平台才答复可靠受理；主节点随后依次撮合 0.10 BTC、价格 60,000 和 0.15 BTC、价格 60,100，将全部成交及订单、预留、幂等变化与撮合进度装成结果 K+1 原子提交。偏偏结果提交回复丢失，旧主又与多数派断联。此时“订单已接住”和“结果是否已成立”必须分别查清，既不能把超时当确定失败重建订单，也不能凭旧主内存承诺成交到账。

多数派选出的接管者要先让新任期在权威日志或存储里正式生效；存储从此拒绝旧任期的新写入，而不是只给旧主发个退出通知。旧主即使暂停很久后复活、仍自称主，也不能绕过围栏。任期之外还要检查预期前序进度：即便是同任期的两个工作线程，也只有基于正确 K 的完整 K+1 结果能合法提交。在甲这次故障里，如果 K+1 已在新任期生效前提交，接管者必须继承原结果；若新任期先成立，旧主那次追加就必须被拒绝。两者先后由权威存储裁决，不能各留一份成交再靠下游去重“合并”。

新主接着加载一个有效快照，按连续逻辑命令序号应用后续已提交结果，恢复全部数量、同价先来先服务的队列、业务幂等及关闭记忆。已经存在的甲的结果只恢复、不重新撮合；查明确实没有结果的已受理尾部，才用固定规则继续裁决。底层日志还混有结果和控制记录，日志索引最新不代表业务状态已追平；热备即使平时在跟，也得核对状态摘要和一致提交边界。拿到任期与执行激活是两步，未就绪时可以受控排队，不能让半恢复的订单簿接着交易。

旧主恢复网络后，把断联前已经提交的甲的结果再发一次，新主的发送器也在补发。这是允许的历史重复运输，不能仅因结果来自旧任期就拒绝合法旧事实；但旧主失联期间的临时计算，即使字段齐全，也不能进入发布链路。账户用原批次身份核验并去重，在一个本地事务里结转整条命令的全部双边资产、分录与连续账务进度。因此甲最终只支付 15,015 USDT、返还 10 USDT、得到 0.25 BTC，可用 USDT 为 4,985，重复补发不会再扣一遍。若补发的是关闭退款，也仍须先补齐并结转此前成交，不能借切主跳过付款义务。

如果多数派暂时不存在，少数派最多提供注明旧版本的查询，或按产品约定收集尚未可靠受理的请求，不能继续承诺受理和成交。账户预留成功而下单状态未知时，钱可能暂时占着；甲真要放弃，就让关闭意图命令回到同一权威序列，先关闭挡迟到单、后关闭只撤剩余量，再按序结账退款，不能靠 TTL 到时解冻。恢复闭环还要求旧结果可从归档取回、历史版本可读、账户数据库及其备份能恢复。这里用暂停部分交易换取事实一致，复制数量、故障范围和追赶能力都是承诺条件，不是已测得的零丢失或秒级切换指标。

**流程位置与核心机制：** 从可靠受理承诺追到复制范围、任期隔离、结果提交竞争和接管位置，说明单写者如何由持久存储执行，而不是只靠一个主进程自觉遵守。

**必要前提：** 沿用链下托管 BTC/USDT 现货 CLOB、限价 GTC、maker 价、零费用和每市场单写者。共享账户仍在同一事务数据库。复制日志服务已经具备持久化多数派提交、单调 epoch 隔离及前序 AppliedSeq 的 CAS，不在本文假装从零实现共识算法。以下为生产设计，不是个人经历或实测可用性指标。

## 第 1 层：先定义切换时不能丢什么

**面试官：** 撮合主节点宕机，备节点怎样接管，才能既不丢订单又不产生两份成交？

**面试者：** 我会把“不能丢”限定到已承诺的事实。只有命令经过持久化多数派提交，才能向客户端承诺可靠受理；只有完整 ResultBatch 与 AppliedSeq 原子提交，才能承诺撮合裁决成立。备节点必须继承这两个已提交前缀，不能按旧主最后一次内存状态或网关响应缓存接管。

接管者先取得可被存储验证的新 epoch，恢复已提交结果对应的状态，再执行已受理但尚无结果的命令尾部。旧进程即使还活着，也不能再提交新结果。下游仍可能收到同一已提交结果的重复发送，因此账户还需批次去重和顺序事务；主备切换不能代替账务协议。这里追求故障假设内已确认事实不丢和唯一裁决，不是承诺网络分区时所有节点都可写。

## 第 2 层：同步复制必须覆盖输入和输出

**面试官：** 你提到两个前缀，那只同步复制下单命令，备机重跑撮合，不也能得到相同结果吗？

**面试者：** 仅复制输入不足以覆盖已经对外确认的结果边界。本模型复制已提交 CommandLog，也复制完整 ResultBatch、AppliedSeq、业务幂等和关闭状态的变化，以及恢复所需快照和版本资料。已有结果是权威事实，备机按结果重建，不重新撮合创造另一份裁决。只对已提交命令、无已提交结果的尾部执行固定规则。

CommandLog 与 ResultBatch 不是同一次事务：输入先提交，输出后提交。结果单个原子记录包括整批成交、orderChanges、reservationActions、关闭和幂等结论及进度。账务数据由共享账户数据库自身的事务与高可用方案保护，不是靠复制订单簿就获得同等保证。如果日志可靠而账户数据库永久丢失，仍不能宣称端到端资产恢复成立。

## 第 3 层：多数派提交不是任意副本收到了

**面试官：** 既然输入输出都复制，旧主写完本地磁盘、异步发给备机就先返回，能否降低延迟？

**面试者：** 可以降低等待，但那会改变已确认不丢的故障契约，不属于当前基线。比如三个副本以两个满足持久化条件的副本构成提交多数派，必须由共识服务确认提交后再返回；不是任意节点内存里收到了字节就算。新领导者的选举和日志继承规则必须保留已提交前缀，不能只凭磁盘最长或更新时间最新就任意升主。

客户端没拿到响应时状态可能不确定，不能推断命令未提交，应按原请求身份查询或重投。三个副本的例子只说明在约定的单副本故障等条件下保住提交数据，不承诺相关性磁盘损坏、全部副本丢失或运维误删仍零损失。主备复制的延迟成本与更强确认语义相绑定，不能同时许诺本地返回延迟和多数派故障保证。

## 第 4 层：网络分区时旧主必须失去写入资格

**面试官：** 旧主没宕机，只是和多数派断开，它认为自己还是主，新主已经接管，谁阻止双主？

**面试者：** epoch 必须成为日志服务或权威存储校验的 fencing token。新 epoch 的生效本身通过权威服务提交，并与后续命令和结果追加串行裁决；服务只接受当前授权任期，拒绝旧 token。旧主的本地 isLeader、租约计时或 Redis 锁都不能覆盖“暂停很久后又恢复”的进程，所以不能作为最终隔离边界。

旧主失去多数派后，不能继续承诺新的可靠受理或发布未提交撮合结果；可以明确返回不可用或待确认，并保留查询身份。即便它继续在内存里算，也不能把计算变成权威事实。隔离不是发一条通知要求旧主退出，而是它不配合也无法写入；若底层仍接受旧 epoch 的结果，那么“每市场单写者”只是约定，并没有被系统强制执行。

## 第 5 层：任期隔离还需要前序进度比较

**面试官：** 存储已经拒绝旧 epoch，为什么还要对前序 AppliedSeq 做 CAS？新主不是唯一写者了吗？

**面试者：** epoch 约束谁有权写，CAS 约束这次结果基于哪个已提交状态。即使同一任期，重复 worker、超时重试或编程错误也可能同时计算同一命令；追加必须核对预期前序 K、目标 K+1 和唯一 batchId，把完整批次与新 AppliedSeq 原子提交，不能只检查身份有效就覆盖现有结果。

如果旧主的 K+1 先于新 epoch 生效已经提交，新主必须继承它；若新 epoch 先生效，旧追加就被拒绝。这两种顺序都由权威日志确定。新主查询到 K+1 已有结果后应用原内容，不能继续用基于 K 另算的候选结果。发现同一 batchId 不同内容应停止并调查，不能用最后写入获胜来解决。epoch 与前序 CAS 分别封住旧写入者和错误状态基线的漏洞。

## 第 6 层：接管不能把底层日志位置当业务进度

**面试官：** 新主继承 K+1 后怎样知道下一条是什么？直接从底层 Raft logIndex 加一开始撮合可以吗？

**面试者：** 不可以。底层日志混合命令、结果及控制记录，原始 logIndex 不是逻辑 commandSeq。服务分配每市场连续逻辑命令位置并提供按位置检索；AppliedSeq 是已形成完整结果的命令前缀，另一个边界才是已提交输入上界。未提交候选不计入已可靠受理的逻辑前缀，不能留下业务缺号让消费者猜测。

新主取得一致提交视图，校验并加载某个 AppliedSeq 为 S 的快照，应用 S 之后所有连续已提交结果到 R，再处理 R 之后已提交且确认无结果的命令。前次结果提交仍不确定时先查明，不能先处理后续。日志领导权和撮合激活是不同阶段，拿到任期不代表内存状态已可裁决；可以受控排队，但不能让未恢复的订单簿接入执行路径。

## 第 7 层：热备也要验证业务状态而非只数条目

**面试官：** 冷恢复太慢，能让备机平时跟着重放，升主后直接使用热内存吗？

**面试者：** 可以，但热备是已提交结果的执行副本，不能与主并发产生有效裁决。它按完整 ResultBatch 连续应用，保留订单 FIFO、全部数量、业务幂等与关闭标记、规则及单位版本，并记录自己追到的 AppliedSeq 和状态 hash。缺口、hash 不符或不支持历史版本时就停止追赶，不能只因为读到最新 logIndex 就声称可立即接管。

升主仍要取得有效 epoch，并与一致提交边界核对。热内存确实对应 R，才从 R 后的无结果尾部继续；不确定就重新加载有效快照和结果。异步热备可以减少恢复耗时，但不能拿它尚未追上的内存覆盖已经多数派提交的事实。快照也必须在完整结果边界捕获，文件和清单持久发布后才算可恢复，不能复制一半就切换过去。

## 第 8 层：旧主恢复后仍可能发送历史结果

**面试官：** 旧主无法写了，却还持有待发消息，新主也在补发，两边同时发送会不会重复成交或扣钱？

**面试者：** 要区分历史事实重复发送和非法创造新事实。发送器只能从已提交结果日志读取内容；旧进程发送先前已提交批次是允许的重复运输，不能发送失联期间的临时计算。消息里的“我是主”不是提交证明，不能让任意内存对象直接进入权威发布链路。

账户以 `symbol + commandSeq` 识别批次，以 `symbol + commandSeq + matchIndex` 识别成交，完整双边余额、分录、去重和市场 lastAppliedSeq 同事务提交。重复批次核验后无第二次资产变化，新序号上的重复业务只应用空效果批次。旧进程重复发的退款也不得越过前序成交；跨市场还要使用进度锁和全局固定余额锁顺序。下游去重只处理同一事实的重发，不能替代 fencing 去解决两份相互冲突的新结果。

## 第 9 层：少数派不停服会改变安全承诺

**面试官：** 为了可用性，能否让少数派暂时接单成交，恢复网络后再和多数派合并？账户先预留是不是就安全了？

**面试者：** 不能在当前 CLOB 语义下这样做。预留只防账户超花，不保证同一挂单剩余量不会在两个分区分别成交，也不能给两个分区独立裁决的价格时间优先顺序事后无损合并。少数派最多提供标明旧版本的查询，或按明确产品约定收集尚未可靠受理的请求，但不能确认可靠受理和成交。

账户预留已成功而 Place 不确定时，保留原意图与待提交状态，恢复后使用原请求身份处理。需要放弃就让 AbortIntent 回到同一权威序列：先到关闭标记封禁迟到 Place，后到撤实际余量；账户先结转旧成交再退款。网络分区可能造成暂时占资和不可交易，这是本模型的可用性代价，不能用 TTL 解冻或 Redis 锁接管悄悄牺牲安全性。

## 第 10 层：完整高可用还依赖结果和消费者可恢复

**面试官：** 你接受分区时停写，新主也恢复好了，是不是就能宣布高可用闭环？

**面试者：** 还要确认恢复依赖和下游义务没有丢。结果不能因主备都追上就截断，账户可能落后，或将来从旧备份恢复。必须建立快照、完整结果归档和消费者恢复契约，保留可按逻辑位置补齐的历史；不支持历史版本、归档损坏或必要结果缺失时，就不能宣称可安全接管。账户自身的备份恢复也要与这套契约兼容。

我会围绕相同故障窗口手工推演：命令多数派提交后旧主失联，结果提交响应丢失时切换，旧主暂停后带旧 epoch 复活，以及新旧发送器重复补发。预期是已确认输入仍在，已提交结果原样保留，无结果尾部仅裁决一次，旧写入被存储拒绝，账户最终只变更一次。可用性恢复还依赖多数派和账户数据库恢复、处理能力足以追赶；这些是承诺条件，不能写成已测得的零丢失或切换耗时。

## 本题收束

- **讲透的机制：** 输入和输出分别持久化多数派提交，权威服务强制 epoch 隔离，前序 AppliedSeq 的 CAS 保证连续结果提交，接管先恢复结果再执行尾部。
- **易错边界：** 备机收到不等于提交；有任期不等于已恢复；原始 logIndex 不等于 commandSeq；旧主可以重发已提交事实但不能发布临时结果；少数派不能承诺可靠受理。
- **反例验证：** 在 K+1 结果提交响应丢失时切换任期，再恢复旧主，令它尝试写 K+1、K+2 并发送缓存。预期是旧写入全部被拒绝，已提交的 K+1 被继承而非重算，历史重发无二次记账，未提交缓存不能对外成为成交。
