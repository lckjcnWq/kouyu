# 大问题 7：重复下单、重复撤单和请求超时怎样处理？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文解决的是“同一件事反复送来，怎样只做一次”，不是让网络永不重复。背景是平台内部记账的 BTC/USDT 现货交易：用户买的是实际 BTC，不是合约；限价 GTC 订单未成交的部分会继续挂着，成交采用先挂在簿里的订单价格，费用按零计算。账户共用一个事务数据库，每个市场只有一个有效写入者。下文把请求身份、资金预留、撮合裁决和账务去重分开说明，方案属于设计推演，不代表已经实测。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 请求身份：`accountId + commandType + clientRequestId` | 账户、操作种类和客户端请求号合成的业务“收据号”。 | 同一次操作重试沿用它；真想再买一次才换新号，不能用连接或重试次数代替。 |
| 规范载荷 | 把价格、数量、方向和目标订单等按固定规则整理后的请求内容。 | `0.25` 与 `0.2500` 可以归一；同号改价格或数量要报冲突，不能悄悄覆盖，哈希也不能替代原内容。 |
| `intentId` | 平台为这次操作保存的意图编号。 | 请求还没裁决时也能用它继续查进度，不必重新建一份操作。 |
| `reservation` 与预留凭据 | 前者是“这笔钱已经占好”的持久记录，后者是证明该预留已成立的通行凭证。 | 预留、意图、请求绑定和待提交状态一起提交后才能发凭据；凭据绑定不可变请求，不能凭空再占一份钱。 |
| 唯一约束与条件更新 | 数据库分别检查“这个业务号只能有一份”和“余额确实还够扣”。 | 两个网关同时进来也只能建一份预留；不同请求争同一余额，还得靠条件更新或行锁保护。 |
| `Place` / `Cancel` | 下单命令 / 撤单命令。 | 重复下单不重新撮合；重复同一撤单返回原裁决，不按今天的订单状态重写昨天的答案。 |
| `AbortIntent` | 把一份未查清的下单意图按正式流程关掉。 | 与下单、撤单排在同一市场队列里；先关闭就挡住迟到下单，后关闭就只能撤实际剩余量。 |
| 确定拒绝与超时未知 | 前者是业务已经作出并保存否决，后者只是没拿到答案。 | 已提交的余额不足拒绝不会因后来充值自动变成功；数据库超时不能直接当成失败、重建或退款。 |
| 多数派提交与可靠受理 | 命令已经按约定被足够多的副本持久保存，平台才承诺接住它。 | 受理不等于成交，成交也不等于账户已经到账；“提交器发过了”更不算可靠受理。 |
| `commandSeq` | 命令在该市场权威队列里的逻辑序号，不是磁盘字节地址。 | 重投可以取得新序号，但仍按原业务身份去重，不能借新号再做一次买卖。 |
| `AppliedSeq` | 撮合已完整提交到哪个命令的进度牌。 | 必须与该命令的完整结果、幂等状态一起提交，不能先把进度写成“处理完”。 |
| `ResultBatch` | 一条命令产生的完整结果包，包括成交、订单变化及需要结算或释放的动作。 | 结果、去重状态和撮合进度要原子落定，不能只留下“做过”却丢掉成交，也不能留下半个结果包。 |
| 空效果结果批次 | “这次送来的是旧操作”的正式处理回执，没有新的业务改动。 | 仍保存原裁决引用并推进自己的命令序号，不增加成交、取消量或退款。 |
| FIFO | First In, First Out，即同价位先来先服务。 | 重试不是重新排队买一次，更不能借重投刷新原订单的时间优先级。 |
| `leavesQty` 与数量守恒 | `leavesQty` 是还挂着的数量；原始量必须等于累计成交、剩余量、取消量之和。 | 剩余量变零可能是成交也可能是撤销，不能据此断言原预留应全退。 |
| 连续结果位置与账务去重 | 账户按市场结果顺序办事，并记住哪个完整结果包已入账。 | 至少一次交付可以重送，但每批资产只变一次；后来的关闭退款不能越过先前成交缺口。 |
| TTL | Time To Live，即自动过期时长。 | 不能让预留凭据或去重身份静默过期后重新有效；超时应触发有序关闭协议，不是直接松开钱。 |
| Redis、持久幂等索引与关闭标记 | Redis 是快速缓存，后两者才是不能随重启遗忘的业务记忆。 | 缓存清空、查询落后或订单移出订单簿，都不能让旧请求重新执行；归档也必须保留身份占用和可追溯结果。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，点击买入 0.25 BTC，限价 60,100 USDT。为看清“先成交一部分、再关闭”的边界，这里采用原文的独立变体：卖盘暂时只有 0.10 BTC，价格为 60,000。甲的手机超时后连点重试，两个网关几乎同时收到同一个请求号。数据库不能靠“先查有没有”碰运气，而是在一个事务里用唯一约束认领请求身份、检查余额、预留 15,025 USDT，并保存意图和待提交状态。另一个网关只复用这份记录；同号若改成买 0.30 BTC，得到的是冲突，不是第二份订单。

账户事务已经提交，只是响应丢了，提交器必须先找回原意图，再用原凭据继续投递。命令被多数派持久提交，只说明市场可靠受理，还没承诺成交或到账。重投即使排到新的逻辑命令序号，撮合也要认出“还是甲那次操作”：首次有效下单才执行，后面的重复命令只提交引用原裁决的空效果结果包。每个结果包、业务去重记忆和撮合进度必须完整原子提交，原订单的同价位排队次序也不能被重试改变。

甲的订单先成交 0.10 BTC，随后甲不想再等剩下的 0.15 BTC。网关不能因为“原请求查不到”就直接退款，而要提交绑定原意图的关闭命令，让它与下单排在同一权威序列里。在这条故事线上，下单先执行，关闭只能取消剩余 0.15 BTC，不能抹掉已成交的 0.10 BTC；若顺序反过来、关闭先执行，持久关闭标记就必须挡住所有迟到下单。重复同一撤单或关闭请求仍返回原裁决，不能再加一次取消量。

偏偏关闭结果先送到账户，成交结果还在路上。账户必须等前面的完整成交批次补齐：先结转支付 6,000 USDT、得到 0.10 BTC，返还成交价差 10 USDT，留下 9,015 USDT 预留；再处理关闭批次，释放这 9,015 USDT。总退款是 9,025 USDT，而不是把最初 15,025 USDT 全退。相同批次后来再送一遍，账户凭业务去重记录跳过，不能再次付款或退款。这样才把“已成交”和“已到账”之间的缺口补上。

最后系统重启，Redis 也清空了，甲那份迟到的下单请求又出现。恢复后的持久请求绑定、幂等索引和关闭标记必须仍能证明它已处理、已关闭；落后的查询副本只能说待确认，不能说“没有这笔，重新买吧”。历史结果可以归档，但请求身份不能悄悄回收，关闭标记也不能仅因订单已不在簿里就删除。否则已经退回的钱会再次支撑一笔迟到成交，前面做对的所有重试处理都会失效。

[返回专题总览](README.md)

**流程位置与核心机制：** 从接入重试追到预留、命令裁决和结果保留。重点是让同一业务请求只有一份有效作用，而不是保证网络只投递一次；成交交付与恢复分别由第 8、9 题深入。

**必要前提：** 沿用总览的链下托管 BTC/USDT 现货 CLOB、限价 GTC、maker 价、零费用及每市场单写者。账户共享一个事务数据库；Place、Cancel、AbortIntent 使用同一市场权威命令序列。以下均为生产设计推演，不是个人项目经历或已通过的工程验证。

## 第 1 层：先定义同一次业务请求

**面试官：** 用户下单超时后又点了一次，怎样判断它是重试还是另一笔订单？

**面试者：** 在这个模型中，请求身份是 `accountId + commandType + clientRequestId`，客户端对同一次业务操作沿用原标识。相同身份、相同规范载荷，返回原意图或原结果；相同身份但载荷不同，返回冲突，不把后来的价格或数量覆盖进去。用户真正想再买一次，才生成新的请求身份。连接、网关实例和 HTTP 重试次数都不是业务身份。

原请求尚未裁决时，返回同一个 intentId 和待处理阶段，不伪造最终结果。原裁决已经形成，则返回固定裁决及其位置；订单后续被成交或撤销，可通过带版本的当前状态查询体现。这样重试既不会创造新操作，也不会被误解成订单状态永远冻结在首次响应。

规范载荷包含市场、方向、整数价格和数量、订单类型，以及相关目标身份。Place、Cancel 的字段不同，Cancel 要固定目标订单，不能只比较请求标识。十进制字符串按规定单位精确解析，`0.25` 与 `0.2500` 可归一为同一数量；非法精度直接拒绝，不经浮点近似。规则和单位版本随首次绑定固化。哈希用于索引和完整性核验，规范内容本身也应保留，不能只凭一个短哈希承担不可重复交易的判断。

## 第 2 层：两个网关同时首次收到相同请求

**面试官：** 你说先绑定请求身份，但两个网关同时查到“没有记录”，会不会分别预留一份钱？

**面试者：** 所以不能把“先查再建”当成互斥机制。账户数据库对请求身份建立唯一约束，首次创建在事务中取得该身份的归属，同时完成余额条件检查、可用转预留、reservation、intent、规范载荷绑定及待提交状态写入。竞争者遇到唯一约束后结束当前尝试，读取已提交记录；同载荷复用，异载荷冲突。失败事务里的余额更新必须一起回滚。

若已经绑定的合法请求因余额不足被业务拒绝，可持久提交该拒绝结论而不创建预留；之后同键重试仍返回原拒绝，不因充值到账而自动变成新订单。数据库暂时不可用或事务回滚则不同，不能声称已有确定业务拒绝，恢复后仍须先查是否存在已提交绑定，再决定继续。

余额检查还要使用条件更新或行锁，不能只依赖请求唯一键，因为不同请求也可能争用同一账户资产。以 B1 为例，最多形成一份 15,025 USDT 预留，不能因双入口占用两份。只有事务提交已确定后才能签发绑定账户、市场、intent、reservation 和不可变载荷的预留凭据。若提交响应丢失，先查明该事务的记录；不能猜测失败再造意图，也不能对尚未提交的预留签发可执行凭据。

## 第 3 层：账户已提交，但命令提交响应丢失

**面试官：** 现在只预留了一次，但 Place 写入命令日志的响应丢了，提交器再发会不会再次撮合？

**面试者：** 待提交状态和预留同事务持久化，提交器重启后仍能找到原意图，使用原业务身份、载荷和预留凭据继续查询或投递。账户的“已发送”状态只是工作进度，不能证明撮合已接纳，更不能作为再次预留的理由。命令只有持久化多数派提交后才算可靠受理，受理仍不等于已成交。

重投允许占用新的 `commandSeq`。市场按连续逻辑序列执行，先查持久业务幂等状态：首次有效 Place 才接纳与撮合；后续同身份同载荷引用原裁决，形成不改变订单和资产的空效果结果批次，并推进自身序号。空效果不是省略记录，它仍有原结果引用和处理结论。幂等状态、完整结果及新 AppliedSeq 必须原子提交。否则可能记住“做过”却丢失成交，或成交留下却忘记去重。重投也不能刷新原订单的 FIFO 优先级。

## 第 4 层：重复撤单返回原结果还是重新撤

**面试官：** 你说重复 Place 返回原裁决。重复 Cancel 时订单状态可能已变化，应该返回旧结果还是重新撤一次？

**面试者：** 相同撤单请求身份和载荷必须返回那次撤单的原裁决，而不是拿当前订单状态改写历史响应。查询当前订单是另一项读取，可以附带更新版本，但不能混成“原请求后来又成功了一次”。重复进入命令序列的 Cancel 同样生成空效果批次，不再增加取消量、不再释放预留。

如果用户换了撤单请求标识，那是新的操作，仍须鉴权并进入同一市场序列，根据当时实际剩余量裁决。前一次已撤完，新的撤单只能返回已终态或无可撤余量；若订单先全成，不能把它改成“全量撤销”。撮合域保持 `原始量 = 累计成交 + 剩余量 + 取消量`，账户只执行已提交结果中的有效释放动作。不能靠账户端“退款接口幂等”弥补撮合端把两次取消量都加进去的错误。

## 第 5 层：查不到原下单，怎样结束无限重试

**面试官：** 原裁决一直查不到，用户已经不想买了；总不能永远重试 Place，也不能一直占着钱吧？

**面试者：** 可以停止主动重发 Place，持久记录关闭处理中，但这不代表网络中的 Place 消失了。真正结束执行资格，要由有权限的流程提交绑定原意图与预留的 AbortIntent，与 Place、Cancel 共用权威序列；查询未找到和超时都不能直接退款。

AbortIntent 先执行，就在已提交结果里持久化关闭标记，迟到 Place 即使携带原来合法的预留凭据，也不得接纳。Place 先执行，AbortIntent 就撤实际剩余量，不能撤销已成立成交；如果已全成，只返回终态与既有义务。关闭标记、订单变化、幂等结论和 AppliedSeq 一起提交。预留凭据不独立按 TTL 过期，超时任务触发的是这套关闭协议。把凭据在账户端悄悄设为过期，却允许市场按旧凭据执行，会重新打开无钱成交窗口。

## 第 6 层：关闭结果先到，能否先退款再补成交

**面试官：** AbortIntent 已提交关闭结果，但它前面的成交结果还没到账户，能不能先退剩余预留，后面再补账？

**面试者：** 不能越过结果缺口退款。关闭只禁止未来执行，不消除先前成交义务。账户按市场连续结果位置处理，先结转前序完整批次，再应用关闭批次释放实际取消部分；相应进度与资产同事务提交。若退款先于旧成交，已成交资金可能先变成可花余额，稍后再扣就不再有覆盖保证。

用独立变体说明：初始卖盘只有 S1，B1 仍买 0.25@60,100，预留 15,025；先成交 0.10@60,000，再关闭余下 0.15。账户应先支付 6,000，退该成交价差 10，留下 9,015；再按关闭结果退 9,015，合计退款 9,025。不能因为关闭后 leavesQty 为零就退全部 15,025。相同关闭批次重投时，去重记录证明已经处理，不得再退第二遍。

## 第 7 层：重启与记录清理后还能否识别旧请求

**面试官：** 这些幂等和关闭记录都要保存；如果 Redis 重启，或者终态记录清理了，旧请求又来了怎么办？

**面试者：** Redis 只能做加速和抑制重复流量，不能是权威去重库。缓存丢失应回查持久请求绑定与已提交结果，市场恢复还要带回业务幂等索引和关闭标记；查询投影落后也不能把未知翻译为“可以重新下单”。

重试查询还应携带已知意图和结果位置，副本进度不足时返回待确认或转到权威读取，不能让一次落后的“未找到”覆盖已返回的受理事实。即使原结果暂时只能从归档读取，也应保持身份占用，不能为了立即返回而改走新建路径。

记录清理必须有明确的业务重放边界。可以归档完整结果、保留请求键与载荷摘要及原结果定位，或建立持久拒绝旧命名空间的协议，但不能删除一切后重新接受相同身份。本模型不允许请求键悄悄回收再用。如果产品以后约定有限重试窗口，也必须能拒绝窗口外旧请求，并处理仍在途的意图和消息，不能只给去重表加 TTL。关闭标记同样不能因订单不在簿里就删除；否则退款后的迟到 Place 会获得第二次执行机会。

## 第 8 层：用故障反例区分请求幂等与账务幂等

**面试官：** 保留记录能挡住旧请求，那怎么说明请求幂等、命令重投和账户去重确实各自覆盖了缺口？

**面试者：** 我会沿同一身份链手工推演，而不是用“支持 exactly-once”概括。并发首次提交应只有一份预留；账户提交响应丢失后仍找回原意图；命令受理响应丢失后重投，即使获得新序号也只引用原裁决；重复 Cancel 不再增加取消量；结果发布或消费确认丢失时，账户批次去重保证资产只变化一次。三个位置都需要持久身份，但保护的是不同状态。

结果提交不确定时，还必须按 `symbol + commandSeq` 查询已提交记录，未查明前不处理下一命令，不把重算结果当作第二份事实。对 B1 正常案例，同键重试最终仍只能支付 15,015、返还 10，甲得到 0.25 BTC、可用 USDT 为 4,985；同键改数量应冲突，不能生成新成交。若只靠请求缓存而没有结果原子边界，崩溃仍可能留下半次撮合。以上是故障切点的预期性质，不代表已经运行测试。

## 本题收束

- **讲透的机制：** 请求身份和规范载荷持久绑定，预留与待提交状态原子建立；重复命令可占新序号，但只产生引用原结果的空效果批次；关闭与接纳按同一序列裁决。
- **易错边界：** 请求去重不等于账务去重；撤单重试不等于重查当前状态；超时、查不到、缓存过期和订单终态都不是直接退款的依据。
- **反例验证：** 先让 AbortIntent 关闭并完成按序退款，再让原 Place 迟到，随后清空 Redis 并重启市场。恢复后的关闭标记仍须拒绝该 Place，既不重新占资也不成交；若能成交，说明幂等或关闭的持久边界不成立。
