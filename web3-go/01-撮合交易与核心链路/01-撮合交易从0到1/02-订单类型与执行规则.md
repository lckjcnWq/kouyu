# 大问题 2：限价 GTC 怎样执行，改成市价、IOC、FOK 要改变哪些前提？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 价格规则回答“多少钱能成交”，有效期规则回答“没成交的部分怎么办”。本文以零费链下现货限价 GTC 为基线；IOC、FOK 和带保护价及预算的市价单都是另外明确条件的扩展，不是基线已支持的能力。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| LIMIT / 限价 | 买入不能超过的单价，或卖出不能低于的单价。 | 买价 60,100 是上限，遇到 60,000 的卖单仍按更便宜的价格买。 |
| orderType / timeInForce / TIF | 前者描述价格输入方式，后者描述执行和存续要求。 | LIMIT 与 IOC 可以组合，不能把市价、GTC 当成同一维度的互斥标签。 |
| GTC | 未成交部分继续有效，直到成交或取消。 | B2 买价 60,000 时，剩余 0.15 BTC 会挂单并继续占钱。 |
| IOC | 轮到自己时尽量成交，剩余立即取消。 | 允许只成交 0.10，不是要求全成，也不是接口必须几毫秒返回。 |
| FOK | 在自己执行位置全数成交，否则零成交。 | 限价内数量不足就不动对手单，不能先买一部分再补回去。 |
| maker 价 / FIFO | 按原挂单价格成交；同价先接纳的先成交。 | B1 第一笔用 S1 的 60,000，不用双方报价平均数。 |
| 预留 / 价差返还 | 先占支付上限，再把实际未花的部分退回可用。 | B1 占 15,025、花 15,015、返 10；返还不是投资收益。 |
| originalQty / cumFilledQty / leavesQty / canceledQty | 原始、已成交、还可成交和已取消数量。 | 对已接纳订单，原始量等于后三者之和，取消不抹掉成交。 |
| requestedQty / REJECTED | 记录想买多少以及未获接纳的拒绝结果。 | 本文不足量 FOK 约定为拒绝意图，不伪造一个数量不守恒的活跃订单。 |
| tick / lot / quoteUnits | 用整数表示价格刻度、数量刻度和 USDT 最小记账单位。 | 本文三者分别为 0.01、0.0001 和 0.000001 对应单位；先检查溢出再相乘。 |
| 临时成交计划 / 单写者 | 基于自己轮到时的订单簿先算完整方案，期间不让其他命令插入。 | FOK 足量检查与执行看同一份权威状态，不采信外部旧盘口。 |
| ResultBatch / AppliedSeq | 整条命令的结果包和已提交执行进度。 | FOK 的两笔成交一起提交，进程崩溃不能只留下半次全成。 |
| protectionPriceTicks / 保护价 | 市价扩展中明确写入的最差可接受单价。 | 本文市价买入不允许越过 60,100 去无限扫单。 |
| quoteBudgetUnits / 预算 | 市价买入最多允许花掉的 USDT 总额。 | 预算 10,000 就先占 10,000，还要按整数 lot 判断剩钱能买多少。 |
| payload / ruleVersion | 不可变请求内容与适用规则版本。 | 数量、保护价、预算、TIF 都要固定；改保护价不是原请求重试。 |
| AbortIntent / 幂等 | 关闭下单资格；相同业务请求只产生一次效果。 | 超时按原身份恢复，要退款先封住迟到下单，不能只等一个定时器。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，面前只有两档卖单：0.10 BTC 卖 60,000，0.20 BTC 卖 60,100。甲先选限价 GTC，买 0.25、最高价 60,100。系统占 15,025，按挂单价先花 6,000 再花 9,015，买足后返还 10；账户完成结转时甲为 4,985 USDT 和 0.25 BTC。限价是底线，不是强制多花钱的指令。

为了弄懂订单规则，甲把初始账户和卖盘重置，每次只换一个条件。若限价降到 60,000，GTC 只能买到 0.10，剩余 0.15 挂着，仍占 9,000。改为 IOC，同样先买 0.10，但余量在这次裁决里取消，账户结转后甲为 14,000 USDT、0.10 BTC。再改为 FOK，则因为这个价格内不够 0.25，一点也不买；不是先买 0.10 再撤销成交。FOK 必须在自己的执行位置检查足量，并把整个结果一次提交，外部盘口和单线程本身都不能替代这个承诺。

最后甲又从初始状态试一个单独的市价扩展：目标 0.25 BTC，但最多花 10,000，最高保护价 60,100，余量按 IOC 取消。买第一档花 6,000 后剩 4,000，只够按本文数量刻度买第二档 0.0665，花 3,996.65。最终共买 0.1665，花 9,996.65，退未用预算 3.35。所谓市价并不允许透支预算或越过保护价；市价卖出也不能照搬这个 USDT 买入预算。

不管甲选哪种规则，系统都要固定原请求身份和完整参数，可靠提交整包结果，再按序记账。超时不能直接当失败，也不能改价却沿用旧请求号。要放弃就提交有序关闭，已有成交先结转，可退部分后释放；重复送来不再成交或退款。订单规则改变的是怎样执行，不是取消资金与可靠性的底线。

[返回专题总览](README.md)

**流程位置与核心机制：** 位于“预留完成、命令已可靠受理”之后，决定成交价格、数量与剩余量的去向；向账户交付确定的支付及释放依据。本题沿同一笔订单追问执行规则，不替代预留、可靠交付与恢复的独立专题。

**必要前提：** 沿用总览：BTC/USDT 链下托管现货 CLOB，价格优先、同价按接纳顺序，成交取 maker 价；零手续费、不同账户、单交易对单写者。基线仅限价 GTC，IOC、FOK、市价均为明确改变条件的扩展。乙的 S1 为卖出 0.10 BTC@60,000，丙的 S2 为卖出 0.20 BTC@60,100，卖资产均已预留；甲有 20,000 USDT、0 BTC。下文独立变体均重置到这个初始状态。

```text
绑定意图的预留 → CommandLog 多数派提交 → 按序计算成交及剩余量
    → 完整 ResultBatch + AppliedSeq 原子提交 → 发布
    → 账户按序以完整批次结转，并处理确定可退的预留
```

## 第 1 层：限价是成交边界，为什么还要按挂单价支付

**面试官：** 甲提交 B1，限价 60,100、买入 0.25 BTC，限价 GTC 怎样执行？改成市价、IOC、FOK，首先要区分什么？

**面试者：** 限价约束成交价格，GTC 约束未成交部分的存续。买单只能成交不高于限价的卖单，卖单反过来；GTC 允许剩余量持续挂单。市价改变价格输入与保护方式，IOC、FOK 改变立即执行和剩余处理规则，不是四个完全同维度的标签。

B1 先预留 `60,100 × 0.25 = 15,025 USDT`。引擎从最优卖价开始，同价取 FIFO 队首；每次取双方剩余量的较小值，以已有挂单的价格成交。因此先与 S1 成交 0.10 BTC，支付 6,000；再与 S2 成交 0.15 BTC，支付 9,015。B1 全成，S2 剩余 0.05 BTC。

实际支付 15,015，预留价差返还 10。账务完成后甲为 4,985 USDT、0.25 BTC，乙收到 6,000，丙收到 9,015。这里买方限价只是最高支付单价，不是强制成交价；价差返还也不是收益。订单全成先于账户到账是允许的，不能因此提前释放支付义务对应的预留。

## 第 2 层：价差必须精确，怎样让预留与成交用同一套整数

**面试官：** 你算出了返还 10。若价格、数量都带小数，预留、逐笔支付与退款怎样避免各算各的？

**面试者：** 我让三者使用同一套整数单位：价格 tick 为 `0.01 USDT/BTC`，数量 lot 为 `0.0001 BTC`，报价资产单位为 `0.000001 USDT`。于是 `quoteUnits = priceTicks × qtyLots`，没有隐含除法或四舍五入。B1 对应 `6,010,000 × 2,500 = 15,025,000,000 quoteUnits`。

API 十进制字符串直接解析为整数，不先经过 `float64`；非整 tick、非整 lot、非正价格或数量都拒绝。Go 用 `int64` 时，对正整数乘法先检查 `priceTicks <= MaxInt64 / qtyLots`，对累计金额、退款和余额更新还要检查加减边界。不能先乘出溢出值再比较；逐项合法也不代表聚合不溢出。

订单保存 `side、priceTicks、originalQty、cumFilledQty、leavesQty、canceledQty`，数量字段统一存 lots。成交保存双方订单身份、`tradePriceTicks、tradeQtyLots`。B1 两笔支付分别为 6,000,000,000 和 9,015,000,000 quoteUnits，退款为 10,000,000。账户必须使用同一批次的成交明细与预留处置依据，不能根据页面展示金额反算。

## 第 3 层：整数算对以后，没成交的数量和钱应该留在哪里

**面试官：** 全成时退款容易。只把买价改为 60,000，仍买 0.25 BTC，剩余量和预留怎样处理？

**面试者：** 这是独立变体 B2，仍为限价 GTC。先预留 15,000，只能与 S1 成交 0.10，支付 6,000；S2 的 60,100 超出限价，必须停止。剩余 0.15 进入买簿，结转后甲可用为 5,000、预留为 9,000，得到 0.10 BTC。若之后撤单先于新成交执行，释放 9,000，可用变为 14,000。

数量始终满足 `originalQty = cumFilledQty + leavesQty + canceledQty`。B2 挂单时为 `0.25 = 0.10 + 0.15 + 0`；撤完为 `0.25 = 0.10 + 0 + 0.15`。状态可以从 `PARTIALLY_FILLED` 变成 `CANCELED`，但已成交量不能清零。首次合法接纳产生 `prioritySeq`，剩余量据此在同价队列排队。

“剩余预留等于限价乘剩余量”只在账户已结转到相同结果位置时成立。账务落后时，预留还覆盖待支付成交，不能用最新 `leavesQty` 直接覆盖。接下来若不希望剩余量继续占资，需要改变的是 `timeInForce`，不是任意加一个退款定时器。

## 第 4 层：不愿保留剩余量，IOC 怎样在同次裁决里结束订单

**面试官：** 就按你说的改 timeInForce。如果 B2 改为 IOC，能否保留已成交部分，同时立即退掉剩余预留？

**面试者：** 可以，但明确改变基线为 `orderType=LIMIT、timeInForce=IOC`；买价、数量、预留上限及 maker 定价不变。IOC 是在轮到该命令时尽可能立即成交，未成交量取消，不是接口调用必须在某个毫秒数内返回。

从初始状态重来，预留 15,000，成交 0.10、支付 6,000；剩余 0.15 不入簿，直接累计到 `canceledQty`，`leavesQty=0`，结果为部分成交后取消。没有成交时也可约定为全部取消，不能把 IOC 解释成“必须有成交才接纳”。

成交、对手单变化、剩余取消和释放依据必须在同一 ResultBatch 中确定，不能先发布部分成交，再投一个普通撤单命令等它排队，否则余量可能继续成交。账户处理该批次时结转 6,000、释放 9,000，甲最终可用 14,000、BTC 为 0.10。所谓“立即退”是裁决时立即确定可退量，不承诺账户和客户端同时完成；若账户失败，保留预留并重试完整批次。

## 第 5 层：连部分成交也不要，FOK 的足量检查究竟在哪里做

**面试官：** IOC 仍可能买到 0.10。如果要求 0.25 全买到，否则一笔也不买，能否先查询盘口再提交？

**面试者：** 不能把外部盘口查询当保证。现在明确改成限价 FOK：在自己的命令序列位置，以同一权威簿检查可执行量，足够则立即全成，不够则零成交。查询之后可能已经有别的命令吃掉流动性；单写者也不让外部旧快照自动变成有效承诺。

在该位置，先沿价格时间顺序扫描限价内的有效剩余量，形成临时成交计划，累计到目标量即可停止；同时检查金额上限。检查与执行之间不插入后续 Place 或 Cancel，也不让其他 goroutine 修改订单簿。通过检查不是另一次独立占量，执行必须采用同一状态下的计划。

从初始状态重来，限价 60,000 的 FOK 只有 0.10 可买，0.25 不足，S1 也不得被吃掉；限价 60,100 则有 0.30，可按 B1 的两笔成交全买 0.25。

本模型约定不足量为未被接纳意图的处理结果 `REJECTED`：只保留 `requestedQty` 及拒绝原因，不创建活跃订单数量账本，拒绝结果持久关闭原意图并给出预留释放依据。不能创建 `originalQty=0.25`、右侧三个分量全零的订单，再声称数量守恒；也不能把“先成交 0.10，失败后补回去”称作 FOK。

## 第 6 层：检查与执行不插队，为什么仍可能只留下半个 FOK

**面试官：** 你已经保证检查后不插队。如果生成第一笔成交后进程崩溃，FOK 的全成或零成交怎样跨重启成立？

**面试者：** 不插队只覆盖并发，不覆盖持久化。两笔成交、全部订单变化、预留处置、接纳或拒绝结论，必须放进完整 ResultBatch；与 `AppliedSeq` 在同一原子记录中可靠提交后，才成为权威结果并发布。FOK 的全成范围是整条命令，不是每笔 trade 各自原子，也不是要求账户在同一瞬间到账。

例如正在处理逻辑命令 n，输入 CommandLog 必须先多数派提交；计算使用临时变更集。提交结果时检查有效 `epoch` 与前序 `AppliedSeq=n-1`，将完整批次和进度 n 共同提交。结果提交状态未查明，不处理 n+1，更不能逐笔发布。

提交前崩溃，丢弃临时计算，从前一已提交边界恢复，按固化的 `ruleVersion` 继续；提交后确认丢失，按 `symbol+commandSeq` 查原批次，不能重造另一组成交。`tradeId=symbol+commandSeq+matchIndex` 保持稳定。FOK 不足量也有无成交的结果批次，推动进度并确定释放依据。

账户随后在同一数据库的一个事务内处理整批双边结转、退款、分录、去重及 `lastAppliedSeq`。事务失败全部回滚，成功但确认丢失则按原批次去重。不能把撮合的原子提交误说成跨域全局事务。

## 第 7 层：全成仍依赖价格边界，去掉限价后用什么限制市价单

**面试官：** 你的 FOK 计划仍靠限价算可执行量和资金上限。如果用户只说“按市价买 0.25”，难道一直扫到买足为止？

**面试者：** 不能无限扫。本题另立市价买入契约，明确改变基线：`orderType=MARKET、timeInForce=IOC`，同时指定目标数量、最高保护价 `protectionPriceTicks` 和总支付预算 `quoteBudgetUnits`。市价不等于天然 IOC，只是本扩展选择这种组合；市价 FOK 要另行定义足量及预算检查，不由这里自动支持。

独立例子：目标 0.25 BTC，保护价 60,100，预算 10,000 USDT，账户先预留这 10,000，而不是无上限承诺支付。每步先检查最优卖价不越保护价，再取目标剩余、maker 剩余及 `remainingBudgetUnits / tradePriceTicks` 向下取整所得 lots 的最小值。支付后扣减预算，任何一步都不得超预算；空簿、触及保护边界或买不起一 lot 时停止，余量取消，不挂单。

这个例子先买 S1 的 0.10，剩预算 4,000；在 60,100 只能再买 0.0665，支付 3,996.65。最终买到 0.1665，支付 9,996.65，未用预算返还 3.35。预算不够不是透支的理由，盘口不足也不是越过 60,100 的理由。

保护价与预算必须进入不可变载荷，并随命令固化，回放不能取“当前最新价”重算保护范围。若扩展市价卖出，则预留 BTC 数量并指定最低卖价，不能照搬 USDT 买入预算语义。

## 第 8 层：预算已预留但回报超时，怎样避免重下和错误释放

**面试官：** 你要求市价预算绑定载荷。若预留后超时，用户改保护价重试，或者退款后原 Place 才迟到，前面的执行规则还能成立吗？

**面试者：** 先锁定身份与关闭顺序。请求键为 `accountId+commandType+clientRequestId`；同键同规范化载荷复用原意图，同键不同载荷报冲突，改价不是重试。预留事务绑定 `intentId+reservationId+不可变载荷`，载荷包括订单类型、TIF、数量、价格或保护价、预算。凭据仅在事务提交后签发，不能因 TTL 自行失效，否则仍可执行的订单会失去资金覆盖。

Place、Cancel、AbortIntent 都进入同一交易对序列。每条入日志的逻辑命令分配连续 `commandSeq`，不是底层混合日志记录的物理下标。原请求重投可以获得新 seq，但业务去重必须持久化：新位置产生带原结果引用的空效果批次并推进进度，不再次预留、撮合或退款；同键载荷冲突也不能产生新业务效果。

要放弃不确定意图，提交有权限且绑定原预留的 AbortIntent。Abort 先到则持久关闭，迟到 Place 必须拒绝，不能再释放一次；Place 先到则保留既有成交，只撤实际剩余量。普通 Cancel 同样只能取消裁决时仍可撤的部分，不能作为未接纳意图的关闭屏障。

资金释放依据是已提交的拒绝或关闭结果，不是超时、查询未找到或终态标签。账户必须先应用前序成交批次，再应用关闭批次；出现缺口先补齐，不能越序退款。已提交结果即使重复交付，也由批次去重与进度同事务挡住。这样 GTC、IOC、FOK、市价只改变执行契约，不绕开相同的资金和可靠性边界。

**本题收束**

- **讲透的机制：** 限价限制成交范围，maker 价决定支付；TIF 决定剩余量。FOK 在同一序列位置检查并以单批次全成或零成交，市价依靠明确保护与预算形成可预留的执行边界。
- **易错边界：** IOC 不等于必须全成；外部盘口不保证 FOK；市价不等于不限价、不限额；终态不等于账务已完成；未接纳的拒绝请求不能伪造成破坏数量公式的订单。
- **反例验证：** 手工推演先提交 Abort、再投迟到 Place，必须零成交且只退款一次；在 FOK 第一笔临时计算后中断，恢复后只能得到一个完整全成批次或尚未提交的零效果状态；重投结果不能重复结转。再用 B2 的 IOC 与 FOK 对照：前者成交 0.10、取消 0.15，后者零成交、不动 S1。以上是设计核对，不表示运行过工程或测试。
