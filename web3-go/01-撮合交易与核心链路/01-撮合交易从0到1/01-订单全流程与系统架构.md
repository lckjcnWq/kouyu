# 大问题 1：从用户下单开始，一笔订单的完整流程与系统架构是什么？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 先分清谁决定“买到了”，谁决定“钱和币已入账”，谁只是把结果显示出来。本文用零手续费、链下托管的 BTC/USDT 现货订单说明全链路，双边账户在同一事务数据库，不讨论链上确认。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| BTC/USDT / 现货 | 用 USDT 买卖实际 BTC，价格以每枚 BTC 多少 USDT 表示。 | 内部账户增加 BTC，不等于每次交易都向链上钱包转币。 |
| 限价 GTC | 限价规定可接受单价，GTC 让没成交的部分继续挂着。 | 买入限价 60,100 不强迫系统按 60,100 买更便宜的卖单。 |
| 接入校验 / 预留 | 前者检查身份和参数，后者先占住所需资产。 | B1 先占 15,025 USDT，防止甲又把这份钱花到别处。 |
| 账户域 / 撮合域 | 账户域负责钱的归属；撮合域负责订单怎样执行。 | 是否全成看已提交撮合结果，余额是否变化看已提交账务。 |
| CommandLog / commandSeq | 可靠保存的命令序列及市场内排号。 | 下单和撤单按同一序列先后执行，不由哪个网关更早看见决定。 |
| ACCEPTED / PENDING | ACCEPTED 是可靠受理；PENDING 表示某个明确阶段还没确定或完成。 | 预留后命令受理未知，与已成交但结转待处理，是两种不同的等待。 |
| 多数派提交 | 按复制协议让足够副本可靠确认，故障后仍能保住已承诺记录。 | 命令仅在入口内存里排队，不能响应可靠受理。 |
| prioritySeq / FIFO / maker | prioritySeq 是首次合法接纳顺序；FIFO 是先入先出；maker 是原挂单。 | 先选最优价格，同价按 prioritySeq；本文成交取 maker 价。 |
| cumFilledQty / leavesQty | 已经成交多少，以及还可能成交多少。 | 撤单只撤剩余量，不能抹掉累计成交。 |
| ResultBatch / AppliedSeq | 一条命令的完整结果包，以及已提交撮合结果的位置。 | B1 两笔成交与订单变化一起提交，不能只发一笔就当作完成。 |
| tradeId / 稳定身份 | 每笔成交固定的身份证。 | 由交易对、命令序号和匹配序号确定，重投不会换成另一笔成交。 |
| 本地账务事务 / 去重 | 双边资金变化一起提交，并记录该批次已处理。 | 事务失败全回滚；成功后确认丢失，重投不再扣款。 |
| FILLED / settlementStatus | FILLED 表示订单全成；settlementStatus 单独说明账务结转到哪步。 | 可以 FILLED 且 PENDING，不能因此说成交失败或先退款。 |
| lastAppliedSeq / 版本 | 连续处理到的位置与数据的新旧编号。 | 顺着意图、命令、结果、账务、投影逐段找出哪里落后。 |
| 私有回报 / 公共行情 / 投影 | 私有回报通知本人订单，行情展示市场；投影是供读取的复制视图。 | 页面显示不是另一个成交裁判，也不能用旧缓存释放资产。 |
| 跨分片 / 链上最终性 | 跨数据库和上链确认是额外的可靠性问题。 | 本文同库事务完成不代表已解决跨分片结转，更不代表链上最终确认。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，提交 B1：最多以 60,100 USDT/BTC 买 0.25 BTC。入口核对身份、价格和数量，账户先占 15,025 USDT，甲还能使用 4,975。此时只是给这次购买留好了钱；等命令进入可恢复日志，系统才承诺“可靠受理”，依然不是承诺已经买到。

撮合负责人按排号处理 B1。乙原先卖 0.10 BTC，单价 60,000；丙原先卖 0.20，单价 60,100。系统先买便宜的乙，再买丙的 0.15，实际支出 6,000 加 9,015，共 15,015。两笔成交和三个订单的变化一起提交后，甲的订单才权威地成为全成，丙还剩 0.05 BTC 挂着。若另一路撤单与新成交竞争，也由同一顺序决定到底还能撤多少，入口不能直接删订单。

成交结果会被交给账户、私有回报和公共行情。回报可以先告诉甲“全成、资金待结转”，账户则在一次本地事务里给甲加 0.25 BTC、给乙丙加对应 USDT，并退甲多占的 10。完成后甲为 4,985 USDT 和 0.25 BTC；账务中途失败就整批回滚，确认丢了则按原批次查重，不能只给甲加币却不给卖方钱。

如果甲问“为什么已成交却还没到账”，排查人员沿同一个订单编号找：命令进日志了吗，结果提交了吗，账户处理到哪个排号，页面又追到了哪个版本。账户没追上是结转积压，账户已完成但页面没更新是投影延迟，两者都不能靠重撮合或再次退款解决。这就是本文全流程的重点：每一段只承诺自己真正完成的事。

**流程位置与核心机制：** 覆盖从请求进入到账务和展示的全链路，重点回答模块职责、状态权威、顺序与各阶段承诺。具体幂等、恢复和主备算法留给各自母题，不在这里展开成另一套专题。

**必要前提：** 案例、金额和整数单位沿用总览的 B1；产品是链下托管现货，账户双边结转在同一事务数据库内完成，不包含链上最终性或跨数据库双边事务。

## 第 1 层：先把一笔订单讲到真正结束

**面试官：** 如果让你从零设计现货撮合系统，从用户点击下单开始，一笔订单会经过哪些模块？

**面试者：** 我会先锁定产品：链下托管现货、价格时间优先，只支持限价 GTC。在这个模型中，完整链路是接入校验、账户预留、命令可靠受理与排序、撮合裁决、结果可靠交付、账户结转，最后是私有回报和行情投影。

以甲的 B1 为例，先校验 60,100 的价格和 0.25 BTC 的数量，账户事务预留 15,025 USDT。随后把绑定预留身份的命令写入该交易对日志。引擎按序与 S1、S2 产生两笔成交，提交完整结果。账户按结果支出 15,015 USDT，给甲增加 0.25 BTC，再返还 10 USDT 价差，卖方分别得到对应 USDT。

我不会把撮合函数返回当成业务结束。订单可以已经全成，但账务还在处理；接口、回报和查询必须分别说明自己确认到了哪一个阶段。

## 第 2 层：订单服务、撮合和账户谁说了算

**面试官：** 你刚才提了三个模块。如果订单服务显示全成，账户还没扣款，撮合内存里又有另一个状态，哪个才是权威？

**面试者：** 不能脱离状态种类只选一个“总权威”。订单是否成交、成交价格和数量，由撮合域已提交的结果决定；账户可用与预留金额，由账户数据库中已提交的账务决定。订单服务的查询表通常是投影，不另行裁决成交。

这里内存订单簿也不是比日志更高的事实源。引擎可以暂算结果，但只有 ResultBatch 提交后，相关订单变化才成立。提交之后内存必须能从这个位置恢复，投影也必须从这里更新。

所以 B1 全成、甲仍有 15,025 USDT 预留，可以是“成交确定、账务待结转”的暂态，不一定是错账。但甲的可用资金不能因此恢复到下单前；如果查询把未结转预留当作可花余额，那才破坏了资金约束。

## 第 3 层：既然状态分域，下单成功到底是什么意思

**面试官：** 既然成交和账务不是同时完成，你的下单接口返回成功时承诺到哪一步？客户端怎样避免误解？

**面试者：** 我会把受理响应和执行结果分开。只有命令已经进入持久化多数派提交的日志，接口才返回 `ACCEPTED`，并带上 `intentId`、`orderId` 和 `commandSeq`。这承诺可恢复地处理该命令，不承诺它已挂单或已成交。

如果快速路径已经拿到已提交结果，可以附带执行结果，但不能把仅存在内存中的推测当作结果。后续私有回报用订单版本表达 `FILLED` 等执行状态，用独立结转状态表达 `PENDING / APPLIED`。执行状态和账务状态不是一个字段。

如果预留成功但受理尚不确定，我返回可查询的原意图标识和 `PENDING`，而不是伪装成明确失败让客户端换 ID 重下。客户端重试相同业务意图必须使用原请求身份，并可查询原状态。

## 第 4 层：怎样确定价格和时间上的先后

**面试官：** 你说返回了 commandSeq。两个请求来自不同网关，客户端时间也不一样，谁先成交由什么决定？

**面试者：** 在本模型中，先后由该交易对已提交命令日志的顺序确定，不由客户端时间、网关本机时间或 goroutine 抢锁次序确定。订单首次合法接纳时得到 `prioritySeq`，同价订单按这个顺序进入 FIFO。

价格优先于同价时间优先。B1 先吃 60,000 的 S1，再吃 60,100 的 S2；即使 S2 提交得更早，也不能越过更优卖价。同一价位下，先接纳的订单先被成交。成交价取已有挂单价，因此第一笔是 60,000，而不是买方限价 60,100。

“时间优先”的具体时间必须对外定义。这里定义的是市场内部权威接纳顺序，并不是承诺比较所有客户端发送的物理时间，也不承诺跨交易对有一个全局先后。

## 第 5 层：串行撮合如何容纳撤单竞争

**面试官：** 既然每个交易对串行，用户撤单时另一笔单正在吃它，你怎么回答到底撤掉多少？

**面试者：** 撤单必须进入同一裁决序列，不能让 HTTP 处理线程直接从订单簿删除节点。引擎按顺序处理，新成交先到，就先更新累计成交和剩余量；撤单先到，就撤掉当时的剩余量，后续订单不能再成交这部分。

用独立变体 B2 说明：B2 已成交 0.10 BTC，还剩 0.15 BTC。如果在撤单之前又成交 0.04 BTC，撤单只能取消 0.11 BTC。结果应保留累计成交 0.14 BTC、取消 0.11 BTC、剩余零，而不是笼统返回“全部撤销”。

账户按这个权威结果结转和释放，而不是按用户请求撤掉的原数量释放。单写者解决了撮合内部竞争，但并不会自动让下游账务同一时刻完成，这仍需要可靠结果和消费协议。

## 第 6 层：怎样把两笔成交可靠交给账户

**面试官：** 你最后提到下游。B1 有两笔成交，如果只发出第一笔，引擎就宕机，怎样不丢第二笔？

**面试者：** 我不会把“内存里改完订单，再依次发两条消息”作为可靠边界。引擎先形成一个完整 ResultBatch，包含两笔成交、B1/S1/S2 的变化及预留处置依据，并把批次和新的 `AppliedSeq` 放在同一个原子日志记录里提交。

批次没有提交，对外就不存在这次权威结果，恢复后可从旧边界重新计算；批次已经提交，两笔成交就都能从日志找回。分发器即使只发出第一条通知就崩溃，也可以从已提交批次重投。账户按完整批次处理，不凭一条“B1 全成”通知推断全部资金变化。

每笔成交身份由交易对、命令序号和匹配序号确定。重投同一批次不会生成新的成交身份。这样把“结果是否成立”和“消息是否已经送达”分开，运输故障不再意味着成交事实丢失。

## 第 7 层：账户已处理一半，能不能仍然叫可靠

**面试官：** 完整批次到了账户，但给甲加了 BTC 之后，给乙、丙加 USDT 时失败，怎么办？

**面试者：** 在本模型里，这些账户位于同一个事务数据库，整个命令批次的双边资产变更、分录、去重记录和消费进度必须在一个本地事务里提交。不能先提交甲的入账，再另开事务给卖方入账。

事务中途失败就整体回滚，预留和消费进度不变；事务提交成功但确认丢失，重投时读到已处理的批次身份，返回原结果，不重复改资产。消费程序还要校验结果顺序，不能让后来的撤单释放越过前面的成交义务。

代价是一个大命令触及很多对手方时，账务事务会变大，共享数据库会成为容量约束。后续如果拆成跨分片账务，就必须重新设计清算义务和分片结转协议，不能继续宣称原来的本地事务已经覆盖双方。

## 第 8 层：如何告诉用户“成交了，但资产暂时没到账”

**面试官：** 既然账户可能延迟，那用户看到已成交却没有 BTC，会不会认为系统错了？你怎样定义最终完成并定位问题？

**面试者：** 我会在产品和接口上明确区分执行状态与结转状态。私有回报基于已提交结果，可以先告诉用户 B1 已全成、两笔成交分别是什么，但此时结转为 `PENDING`；账户事务完成后再更新为 `APPLIED`。公共行情表达市场已经形成的成交，不必等查询库和所有客户端同时刷新。

定位时沿同一身份链检查：下单意图与预留是否存在，命令提交到了哪里，结果的 `commandSeq` 是多少，账户 `lastAppliedSeq` 是否追上，最后查询投影是否追上。如果权威账务已完成而页面未更新，是投影延迟；如果账务进度停住，是结转问题；不能把这两种情况都叫“撮合失败”。

对于本例，资金处理完成意味着甲得到 0.25 BTC、USDT 可用为 4,985，乙和丙收到对应价款，丙仍为 S2 预留 0.05 BTC。查询页面何时可见是另一层承诺，需要版本、补查和延迟监控来支撑，不能反过来改变成交事实。

**本题收束**

- **讲透的机制：** 资产先预留，命令先可靠受理，撮合结果先提交，再可靠交付、原子记账，查询作为投影跟进。
- **最容易答错：** 用“下单成功”混淆可靠受理、撮合成交和账务完成；把单线程误当成全系统事务。
- **检验反例：** 在两笔成交的分发之间宕机，恢复后必须仍能找到同一完整批次，且最终资产只变化一次。只是给出恢复设计，不表示已经做过故障注入。
