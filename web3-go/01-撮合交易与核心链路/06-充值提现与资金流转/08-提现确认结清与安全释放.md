# 大问题 8：哪些证据允许结清，哪些失败才允许释放？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文范围：判断 Ethereum 主网 USDC 提现 W1 的 30 预占何时可以结清、何时可以退回。甲当前 70 可用、30 预占，B 应实收 30，平台另付 ETH gas；链上已付与数据库已结账是两个完成点。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 业务结清 | 付款义务确已履行，内部账也已应用结果。 | 拿到 hash、RPC 接收或页面提示都不是结清本身。 |
| 授权载荷 / 唯一付款身份 | 固定这笔钱允许由谁、在哪条链、怎样付。 | W1 的发送者、nonce、资产、B 和金额都须与证据一致。 |
| to / calldata | 交易调用的合约与携带的调用参数。 | to 是 USDC 代理，B 在 transfer 参数里，value=0。 |
| receipt / 真实 Transfer | 执行结果与实际代币支出证据。 | 成功回执仍要核对 `Transfer(H,B,30_000_000)` 及异常额外支出。 |
| finalized 检查点 | 固定可信最终历史的高度与 hash。 | 付款块及回执日志须属于其祖先链，不能只看普通确认数。 |
| attempt / 同 nonce 候选 | 原始、加速、取消等多个执行尝试。 | 旧 hash 不丢，最终竞争的是同一链、同一发送者的一个序号。 |
| nonce 双向约束 | 一序号只属一意图，一意图只获一付款序号。 | W1 不得因广播未知再获 n+1 或另一钱包的付款资格。 |
| SETTLE / RELEASE | 支付后消费预占，或确定不会付款后退回。 | 两个动作各有唯一键仍不够，必须争同一终态。 |
| 全额预占守恒 | 一笔受理金额始终有可解释的去向。 | 30 等于未消费预占、已结清与已释放之和，不支持部分提现。 |
| 资格关闭 / SIGNING | 允许签名前可原子关闭，进入签名阶段后不可直接退款。 | 取消与执行器竞争状态版本，不按“没查到 hash”裁决。 |
| 最终不付款证据 | 原序号已被取消或回滚交易最终消耗。 | 还要确认无其他付款授权，不能只证明某一次尝试失败。 |
| epoch / 旧签名 | 当前授权代次与已经生成的有效交易。 | 撤销新授权不会使旧签名消失，取消也可能输给原付款。 |
| 待应用付款 / outbox | 链上已付但账内尚未完成的结果及待发消息。 | 恢复原 SETTLE，不重付、不退款，账务与 outbox 同事务。 |
| REVIEW / 证据冲突 | 无法安全给出确定资金结论的隔离状态。 | 相反 finalized 结果先停机核验，不用最大版本覆盖。 |

## 把整篇文章压缩成一个故事

甲充值的 100 USDC 已入账，申请 W1 向外部 B 提现 30 后，可用变成 70、预占为 30。平台归集 100 到 H，只改变自己的持币位置。广播器返回交易 hash，页面仍应区分“已提交”和“已完成”，因为 hash 只指向一份交易字节，不证明 B 已拿到正确资产，也不证明平台已结账。

观察器核对 W1 的主网、H、唯一 nonce 和授权载荷，确认 to 是 USDC 代理、value 为零、调用参数指定 B 和 30,000,000。成功回执还要配合真实转移日志，目标块也须属于可信 finalized 祖先链。只被包含后又重组，就回到追踪，甲仍为 70／30；若日志金额不符或最终证据矛盾，则隔离核验，不仓促结清或退款。

假设最终证据确认 B 实收 30，账本在一个本地事务中消费预占、写分录、提交 SETTLED 和 outbox。数据库连接这时断了，恢复者先查原 W1：已提交便返回旧结果，未提交则重做同一结算。链上转出不受数据库回滚控制，因此不能因结账未知再付一笔，也不能把 30 退回可用。正常收敛后甲为 70／0，H 为 70。

若换成取消分支，必须在签名资格产生前原子关闭，或者等同 nonce 取消或回滚最终消耗序号，并确认没有其他付款授权，才能释放。节点查不到、租约到期或取消刚广播都不够，旧付款仍可能竞争获胜。SETTLE 与 RELEASE 必须在同一预占终态互斥；确定不付款时才恢复 100／0，已付时只结清。释放审计要列出全部签名请求、候选和最终序号消耗，缺少任何关键环节都继续保留预占并转核验。ETH gas 即使回滚也可能消耗，另记平台费用，不混入 USDC 等式。

**流程位置与核心机制：** 本题位于提现预占之后、业务终态之前，深挖链上付款证据如何变成结清，以及何时能证明未付款并安全释放。核心是 finalized 规范证据、实际 USDC 转移、付款资格闭合和 SETTLE/RELEASE 互斥裁决。

**共同前提：** Ethereum 主网原生 USDC，精度 6 位，平台托管且承担 ETH gas。甲已充值 100 USDC 并入账，W1 向外部 B 提现 30 后为可用 70、预占 30；S1 独立将 D_A 的 100 归集到 H，用户负债不变。H 对 B 的付款最终成立后，甲为 70／0，H 为 70。所有金额用最小单位整数；只按 finalized 规范证据入账或结账，不提前授信；充提意图、账本、分录和 outbox 共用 PostgreSQL 本地事务。

## 第 1 层：提现的“完成”究竟指什么

**面试官：** W1 的 RPC 返回了交易哈希，页面能不能显示提现成功？请先定义业务结清需要证明的事实。

**面试者：** 交易哈希只是一个查找线索，RPC 接收也只是某个节点接触到字节，都不能说明 B 已经收到钱。对 W1 而言，结清至少要证明：指定链的规范最终历史包含了这笔执行；执行结果成功；认可的 USDC 合约按预期从平台热钱包 H 向外部地址 B 转出恰好 30 USDC；这组链上事实能绑定到 W1 唯一的付款意图和授权；然后本地账务以同一 W1 只消费一次 30 的预占。

结清不是单一链上状态，也不是页面状态，而是“外部义务已确定履行”与“内部负债已按证据结账”两个事实都成立。链上已付但数据库尚未应用，可以是短暂、可恢复的中间态；不能提前把它包装成已结清，也不能因内部提交失败再次付款。此时甲仍显示可用 70、预占 30，直到结算分录与状态在本地事务中提交。

## 第 2 层：成功回执为什么不等于付出了 30 USDC

**面试官：** 你要求执行成功和实际转移。具体应核对交易的哪些字段？如果 `receipt.status=1`，但没有预期日志呢？

**面试者：** 先把交易绑到 chainId=1、专用发送地址 H、W1 分配的唯一 nonce 及已授权载荷。直接 ERC-20 转账的交易 `to` 是 USDC 代理合约，`value=0`，调用数据必须解码为 `transfer(B, 30_000_000)`；B 不是交易的 `to`。代理地址、资产策略版本、发送者、nonce、目标和金额都要与 W1 持久授权一致，不能只凭一个交易哈希认领结果。

随后验证 receipt 成功，并从认可的 USDC 合约发出的日志中核对真实 `Transfer(H,B,30_000_000)`。成功回执只表示 EVM 调用没有回滚，不自动证明业务收款人、资产和数量正确；缺日志、发出方不对、收款地址不对、金额不符，或存在无法解释的额外业务支出，都不能按预期 30 结清，应进入核验。费用以 ETH 支付，即使 Token 调用回滚也可能已经消耗，不能把 gas 混进 USDC 的金额等式。

## 第 3 层：哪一种最终性证据足以结清

**面试官：** 上述字段都匹配，而且交易已被打包。如何排除它随后被重组？只看确认数或一个节点的 `finalized` 标签够吗？

**面试者：** 系统须有明确、版本化的 Ethereum 主网最终性证据策略，并把 receipt、交易、日志与其所在区块 hash 绑定。处理结果时，固定一个可信 finalized 检查点 `(height,hash)`，验证付款区块属于该检查点的祖先历史，同时检查已接受检查点之间的连续性。仅有 head、若干确认数、交易进入 mempool 或单个响应里出现 `status=1`，都不足以替代这个证明。

实现上保存来源、区块号与 hash、receipt blockHash、目标日志、最终性检查点及策略版本，使恢复任务能重复验证同一证据。FINALIZED 检查点若与此前已接受的历史矛盾，不能悄悄选择“更新的那个”，也不能让自动结账和相关新出款继续跑；应停止自动资金动作，保留原始响应与区块证据，切换独立节点或人工核验。正常未最终确认或观察分支变化只表示继续等待，W1 的预占仍在，不产生结清或退款。

## 第 4 层：一个 W1 有多个交易哈希时，怎么证明只付一次

**面试官：** 广播重试、加速和取消都可能产生不同 txHash。怎样防止同一 W1 最后出现两笔规范付款？

**面试者：** 交易尝试与业务付款意图要分层保存。W1 是稳定业务身份；每次签名、广播、加速或取消是关联到 W1 的执行尝试，保留各自的 hash、rawTx、内容和观察结果。发送地址 H 的 `(chainId,sender,nonce)` 必须全局唯一绑定到一个意图；反向也必须约束 W1 只获一个付款 nonce，不能用 n 付款超时后再给 W1 授权 n+1。只实现同 nonce 唯一，仍可能让一笔 W1 付两次。

替换交易只允许同 sender、同 nonce 且保持相同付款业务载荷的受控加速或明确不付款的取消。标准专用普通 EOA 在规范链上同一 nonce 只能被一个交易消耗，因此同 nonce 候选可竞争一个执行位置；这依赖无账户委托、无备用私钥旁路、所有出款都经同一 nonce 管理与签名授权路径。数据库的“已处理”标记无法撤销已经生成的旧签名，所以任何候选在被链上最终排除前都必须持续追踪。

## 第 5 层：SETTLE 与 RELEASE 如何互斥

**面试官：** 如果结清和释放各自有唯一账务键，为什么还要额外做状态竞争？

**面试者：** 两个不同键只能分别阻止同一类动作重放，不能阻止对同一 W1 各做一次不同动作。例如付款结果消费者写入 `(W1,SETTLE)`，另一个超时处理器写入 `(W1,RELEASE)`，两条键各自唯一仍可能都成功；结果是同一 30 既从预占中消费，又回到可用，或者余额和负债同时被错改。互斥必须落在共享的 W1／预占终态上。

本地应用事务会锁定 W1 或用期望状态与版本做条件更新，只允许一个从未决状态到 `SETTLED` 或 `FAILED_RELEASED` 的迁移。分录键、意图状态和预占消费在同一 PostgreSQL 事务内提交；第二个相反结果到达时读取已提交终态、保存冲突证据并拒绝资金变化。重放相同终态可以返回原结果，但不能把相反终态当普通幂等重试。全额提款模型还满足 `30 = 未消费预占 + 已结清金额 + 已释放金额`，且结清与释放只能一项生效。

## 第 6 层：什么条件才算“不会再付款”

**面试官：** 仅在签名前关闭资格就能释放。若已进入 SIGNING，哪些证据才足以释放？

**面试者：** 合法释放分两类。第一类是签名前的原子关闭：W1 仍处于尚未取得执行资格的状态，取消或拒绝与迁入 SIGNING 竞争同一版本；关闭动作先提交，旧队列消息和 worker 后续都无法获得签名授权，再在同一业务事务里释放预占。这里的关键不是“还没查到签名”，而是系统从未发出有效执行资格，并且所有签名入口都验证该资格。

第二类是资格已进入执行阶段后的确定不付款：原付款 nonce 已被 finalized 的 reverted 交易消耗，或受控的同 nonce 不付款取消交易已 finalized；同时必须证明 W1 没有第二个付款 nonce、旧签名不会在另一 nonce 执行、候选尝试均已由该 nonce 的规范消耗排除。收到取消交易、RPC 查不到、签名接口超时、租约到期、mempool 消失都不满足条件。只有证据与授权闭合，才可把预占转回可用；原 nonce 的失败 gas 仍单独记平台 ETH 费用。

## 第 7 层：链上已付但数据库失败，如何恢复

**面试官：** W1 已有最终付款证据，结清事务执行期间数据库连接断开。调用方不知道提交成功没有，预占和用户余额应该怎么处理？

**面试者：** 先不能从连接断开推断数据库提交失败，因为事务可能已提交但响应丢失。恢复进程用稳定 W1 与账务动作键查询权威状态：若唯一 SETTLE 分录和 `SETTLED` 已提交，返回原结果；若未提交，则在证据仍有效时重试同一个结清动作。不得创建新 W1、换 nonce、重新支付或退回 30 来“补偿”。

一次最终结果应用事务必须同时校验证据绑定、消费 30 预占、追加借贷分录、改变意图终态、记录已应用结果位置并写入 outbox。任何一步失败则全部回滚，预占仍为 30，链上已付的差异进入可重试的“待应用付款”队列。签名、RPC 与链上交易不塞进数据库事务，也不假设能做跨系统回滚。这样允许资产已经离开 H 而内部负债暂未消灭，但差异必须明确归属于 W1，后续同一证据重放最终让甲从 70／30 收敛至 70／0。

## 第 8 层：退款、拒绝和迟到取消如何避免竞态

**面试官：** 风控拒绝消息晚到，但 W1 可能已经签名；或者取消先释放，旧 worker 随后广播。如何判定谁赢？

**面试者：** 业务裁决要发生在签名授权边界之前。审批拒绝或用户取消在 RESERVED／APPROVED 阶段成功条件更新 W1、关闭签名资格并释放时，worker 必须在签名入口再次检查当前意图版本和授权，而不是只信队列里旧载荷。如果执行器先把 W1 原子迁入 SIGNING 并建立付款 nonce 绑定，取消就不能按普通反向分录释放；它只能成为对现有意图的受控链上处置。

迟到消息按它描述的事实分类：取消请求、RPC 接收取消交易、观察到未最终取消、最终确定不付款是四种不同阶段。前几种不能覆盖已结算状态或解锁预占。业务版本有助于拒绝过期命令，但不能让已签名交易失效。若释放提交后旧 worker仍能得到有效新签名，说明签名入口的资格闭合不成立，应视为安全缺陷而非靠人工对账修复。若链证据显示原付款已 finalized，则结清胜出；只有 finalized 不付款证据及完整授权闭合才能释放。

## 第 9 层：finalized 证据互相矛盾时如何隔离

**面试官：** 一个节点说原付款成功 finalized，另一个给出相冲突的区块视图；或同一 nonce 看似出现付款与取消两笔 finalized 结果。系统应该自动挑一个结论吗？

**面试者：** 不应该。finalized 证据冲突已经超出常规重试和乱序处理范围，表示信任根、节点视图或链状态至少有一项需要复核。应暂停该链相关的自动结账、自动释放、新签名和新的出款授权，保留所有节点响应、检查点、区块 hash、receipt、日志、交易字节和观察时间，标记 W1 为 REVIEW，而不是把它改成普通失败。

核验要从独立来源重建规范祖先关系，检查 chainId、客户端与网络配置、finalized 标签含义、区块 parent 链和交易执行结果，再确认是否是索引器缓存或错误关联。若是数据源故障，修复证据视图后用原 W1 重放；若确认是链层异常或资产损失，则按授权追加冲正或损失处理，不能删除已提交分录。两套互斥终态的证据同时成立，在标准 Ethereum EOA nonce 模型下不应作为普通业务并存；它本身就是必须升级隔离的反例。

## 第 10 层：怎样证明释放规则没有留下隐藏付款

**面试官：** 你给出了几类安全释放证据。如何用一个可证伪的检查判断实现是否仍可能“退了款，旧付款后来又成功”？

**面试者：** 为每个 W1 做一次闭环审计：从预占和授权版本出发，枚举全部签名请求、签名器查询结果、rawTx、nonce 绑定、广播 hash、替换候选及链上观察；再证明要么从未取得签名资格且资格在释放事务之前被原子关闭，要么唯一付款 nonce 已在 finalized 历史中被确定消耗为不付款，且没有其它 nonce 的付款授权。缺任何一环就保留预占并隔离，不用“查不到”填补证据空洞。

结算方向则验证唯一候选在 finalized 规范历史中执行成功，`Transfer(H,B,30_000_000)` 与 W1 全字段绑定，再确认本地只有一条互斥终态分录。可用故障注入在“签名器已签但响应丢失”“广播已发但 RPC 超时”“释放与 SIGNING 并发”“付款已最终但 DB 提交响应丢失”四处中断，重启后检查预占不会同时结清又释放，且不会产生第二个 nonce。若任一场景能让 30 回到甲可用并让旧签名后来付款，规则即被证伪；这是验证方案，不声称已经执行测试。

## 本题收束

### 机制

- 结清要求 finalized 规范证据、成功执行、真实 USDC 转移和 W1 授权载荷一致。
- 释放要求签名前原子关闭资格，或原 nonce finalized 不付款且付款授权完整闭合。
- SETTLE／RELEASE 以同一意图终态和本地事务裁决；链已付、账待应用时重试原结算。

### 易错边界

1. `txHash`、RPC 接收、`status=1`、finalized、账务提交和页面完成不是同一件事。
2. `to` 是 USDC 代理，`value=0`，B 来自 calldata 与真实 Transfer；ETH gas 单独核算。
3. 两个动作各自幂等不等于动作互斥；SETTLE 与 RELEASE 必须竞争同一 W1 状态。
4. 超时、查不到、租约到期和取消已广播都不是不会再付款的证据。
5. epoch 能挡新授权，不能撤销已签出的旧字节；一个 W1 不得得到第二个付款 nonce。

### 证伪反例

```text
W1 已签名 → 广播 RPC 超时 → 节点暂时查不到
→ 系统释放 30 → 旧 rawTx 后来进入 finalized 规范历史
→ 甲可用恢复为 100，但 H 已向 B 付出 30
```

只要实现允许此路径，安全释放条件就不成立。检查该路径中释放事务是否能证明资格已关闭或 nonce 已最终消耗；证明不了就必须维持预占与人工核验。
