# 大问题 10：消息丢失、重复和服务崩溃后怎样恢复原义务？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文范围：讲 Ethereum 主网 USDC 充提在数据库、消息、签名和广播之间崩溃后如何恢复原义务。W1 是向 B 付 30，不因重启生成第二笔付款；甲预占保持 30，直到确定结清或安全释放，ETH gas 另记。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 原义务 / 稳定业务身份 | 系统重启也必须承认的同一收付责任。 | W1 与其付款内容、预占不能被复制成新的提现。 |
| transactional outbox | 跟业务一起写进数据库的待发事件表。 | W1、余额、分录和事件同事务提交，避免占了钱却忘记派任务。 |
| 至少一次 / 投递确认 | 消息可能重复送，发送或接收方确认一个交付阶段。 | 确认不代表签名、链上付款或结账已经完成。 |
| 消费事务 / 去重键 | 收方把业务效果与“已处理”一起保存。 | 提交后再确认消息，不能先确认后落账。 |
| eventId / 业务动作键 | 一次事件的编号与同一业务动作的身份。 | 不同消息也可描述同一 SETTLE，不能只靠 eventId 防重。 |
| 状态版本 / 合法迁移 | 在预期阶段上才允许改变状态。 | 晚到旧审批不能把 SETTLED 改回待付款。 |
| 相反终态 / 证据冲突 | 结清与释放不能并存，矛盾最终证据需隔离。 | 取消已提交不是最终取消，更大版本号也不能覆盖真实付款。 |
| 签名 requestId / SIGNATURE_UNKNOWN | 查回原签名请求的编号与未知签名状态。 | 没收到 rawTx 不能证明没签，接管者仍查原请求。 |
| rawTx / 原字节重播 | 已签交易字节及不改内容的再次发送。 | 先可靠保存再广播，重播不创建新 nonce 付款。 |
| nonce 双向唯一 | 链与发送者下序号归一意图，意图只获一付款序号。 | MQ 去重无法阻止 W1 换 n+1 再付，所以签名端也要约束。 |
| 恢复工作台 / 最低未决 nonce | 从持久状态找待办，先处理钱包队头风险。 | 不能只重放队列或把所有超期任务批量改失败。 |
| 归档 / 灾备回退 | 保留长期业务历史，并承认外部系统不会随备份倒退。 | 旧数据库看不到签名，不等于链和 Signer 也未执行。 |
| 租约 / epoch | 调度占用期限与授权代次。 | 可阻止旧工作者新操作，不能撤回已有有效交易。 |
| finalized / 分区水位 | 可信最终历史与各范围实际完成进度。 | 最大扫描高度或单个 MQ offset 不能证明全系统无缺口。 |
| 恢复准入 | 证据、付款身份、应用差异和预算都可解释后再开放。 | 已最终付款但账未结只补原结算，未知继续保留预占。 |

## 把整篇文章压缩成一个故事

甲的 100 USDC 已合法入账，申请 W1 提现 30。系统在同一数据库事务里把可用改为 70、预占改为 30，并写下分录和 outbox。进程提交后、发布消息前崩溃，后台仍能从 outbox 找回待办。若发布完成却没来得及标记，事件会再发；消费者必须把业务效果、去重和本地状态一起提交，再确认消息，不能让重复投递变成重复预占。

归集 S1 把 100 搬到 H 后，执行器持久固定 W1 的发送者、nonce、载荷和签名 requestId，再向 Signer 请求。Signer 已签却丢了响应，接手者看到库里没有 rawTx，也不能说没签。它查询原请求，取回并核对原字节，可靠保存后再广播。广播再次超时，恢复者重播同一字节、追踪全部候选，仍保持甲的 70／30，不换序号另付。

某个候选最终向 B 付出 30，随后账务提交响应又丢失。程序先查原 SETTLE 是否已提交，未提交才补原结算；链上付款与数据库不在同一事务，不能以重付或退款“补偿”。迟到的审批或取消申请也不能覆盖已结清。若同 nonce 出现相反 finalized 证据，就暂停核验，而不是按消息到达时间或最大版本选一个结果。

灾备若恢复到较早备份，链和签名器却不会倒退。系统先关闭新派单，用签名请求历史、rawTx 归档、nonce 消耗和最终检查点补回外部事实；无法证明的窗口继续冻结。旧工作者的租约和 epoch 可以失效，旧签名仍须追踪。只有扫描缺口、分区应用进度和未决付款都可解释，才逐步开放；正常结局是甲 70／0、H 为 70，而不是“队列清空就算安全”。

**流程位置与核心机制：** 本题跨越数据库提交、outbox 投递、消费端应用、签名、广播和链结果入账，回答服务崩溃后怎样交付并恢复同一笔原义务。重点是至少一次消息下的消费事务、重复与乱序处理、签名和广播的未知窗口、旧 worker 隔离、账务历史保留和恢复准入；MQ 的 exactly-once 不解决链上支出唯一性。

**共同前提：** Ethereum 主网原生 USDC，6 位精度整数，平台托管并承担 ETH gas。甲充值 E→D_A 100，达到 finalized 规范证据后可用 100；W1 向外部 B 提现 30，预占后甲为 70／30。独立归集 S1 将 D_A 的 100 转到 H，用户负债不变；H 最终向 B 付 30 并结账后甲为 70／0、H=70。充提意图、账本、分录与 outbox 在同一 PostgreSQL 本地事务，不使用分布式账本协议；签名器按稳定 requestId 可查询结果。

## 第 1 层：可靠交付的对象是什么

**面试官：** 消息队列显示事件已经发送，是否表示提现任务可靠完成？请先说明本题要交付和恢复的是什么。

**面试者：** 要交付的是一个具有稳定业务身份的义务，而不是一条消息本身。提现 W1 代表平台受理了向 B 支付 30 USDC 的承诺，伴随 30 的用户预占；后续审批、签名、广播、链上观察和结清消息，都只是推动或证明这项义务的阶段性事实。消息可以丢、重、乱序，服务可以在任一阶段崩溃，但恢复后不能把 W1 忘掉、复制成新提现，或把不确定付款当作已失败。

所以至少持久保存 W1 与规范载荷、账本分录、状态版本、每种动作的稳定身份、钱包意图和 nonce、签名请求与 rawTx、广播尝试、链观察及结果应用记录。消息是唤醒处理者的交付机制，数据库中的意图与执行证据才支撑恢复。每个阶段必须能回答“现在知道什么、尚不能断言什么、下一步只能重试哪个原动作”。

## 第 2 层：本地事务与 outbox 如何避免业务写入后无消息

**面试官：** 如果创建 W1 和发送队列消息是两步，进程在中间崩溃会怎样？

**面试者：** 先提交提现与账本，再发 MQ，存在数据库已成功但进程在发布前崩溃的窗口，W1 会预占 30 却没人处理；先发 MQ 再提交数据库，则消费者可能先看到一个不存在或未占资的意图。基线用 transactional outbox 关闭这两个本地写入之间的断裂：在同一个 PostgreSQL 事务里，按请求键创建 W1，条件扣减甲可用 30、增加预占 30、追加分录，并插入含 eventId、聚合版本和载荷摘要的 outbox 记录。

事务提交后 API 才能返回“已受理”。后台投递器扫描待发送 outbox 并发布，发布成功后再更新投递状态；如果发布已成功而标记前崩溃，重启会再次发布，这是预期的至少一次行为。若数据库提交回滚，就连 outbox 也不存在，消费者不会凭空执行。outbox 保证本地业务事实与待交付事件共同持久化，不保证 MQ 永不丢失或消费者恰好运行一次。

## 第 3 层：重复消息和消费者提交边界

**面试官：** outbox 发布后崩溃会重复投递。消费者如何做到消息重复但业务效果不重复？

**面试者：** 消费者要将去重记录、意图状态条件更新、分录或投影更新放进自己的本地事务，并在事务提交后才向 broker 确认消息。若业务处理提交前崩溃，事务回滚，消息重投后完整重做；若数据库已提交但确认前崩溃，重投时根据稳定业务动作键读取原结果并返回，不再重复扣预占或生成新付款授权。

去重键应表达业务动作，例如 `(withdrawalId, SIGNING_REQUEST)`、`(withdrawalId, SETTLE)`，不能只依赖某次投递的 eventId；同一 W1 的业务结果可能由 outbox、链扫描补偿或恢复任务以不同消息 ID 重新交付。相反，去重记录也要核对载荷摘要与版本，发现同键金额或收款人变化应报冲突，而不是静默丢弃。消息确认代表本地消费效果持久化，不代表签名器已执行、链上已经付款或用户提现结清。

## 第 4 层：乱序消息和状态版本如何裁决

**面试官：** 假设结清消息先到，旧的“等待审批”消息后到。消费者是否按时间或最大版本覆盖当前状态？

**面试者：** 不能以到达顺序当业务顺序，也不能用消息里的更大数字盲目覆盖。每个事件绑定聚合身份、产生时观察到的状态版本和允许迁移；消费者在数据库中以期望版本或合法状态集合做条件更新。晚到的旧消息若其前置状态已经不成立，只能作为已处理的过期交付记录或触发重新读取权威状态，不能把 SETTLED 回退成 APPROVED。

终态结果还要按证据类型判断。迟到的“取消已提交”若实际只是取消请求或 RPC 接收通知，不能覆盖最终付款；若它声称同一 nonce 的相反结果也已 finalized，则不是普通乱序，而是链证据矛盾，必须隔离核验。状态版本能帮助拒绝旧命令，却不能证明链上的交易不存在。消费者应区分投递顺序、业务迁移顺序和外部事实确定顺序，并在不确定时读取完整 W1 聚合状态及证据，而非只比较时间戳。

## 第 5 层：签名请求超时为何是未知而非失败

**面试官：** worker 调用签名器后超时，数据库里还没有 rawTx。能否认为没签成功，换一个请求再签？

**面试者：** 不能。超时可能发生在请求到达签名器之前，也可能发生在签名完成而响应返回之前；数据库没有 rawTx 不等于签名器没有生成有效字节。每次签名必须先在本地持久化一个稳定 requestId，并把它绑定到 W1、意图版本、chainId、sender、唯一 nonce、`to/value/data`、费用范围和授权摘要。调用超时后，恢复者使用同一个 requestId 查询签名器，按其持久记录恢复原结果，不创建另一份付款授权。

如果签名器支持幂等查询或结果检索，就持久化并校验返回的签名字节与绑定载荷；如果查询也暂时失败，状态保留为 SIGNING／SIGNATURE_UNKNOWN，30 仍预占，暂停该发送地址上会造成 nonce 混乱的新操作。不能因为新 worker 的租约拿到了，就生成新 nonce 或假定旧请求失效。稳定 requestId 解决的是签名服务交互的恢复身份，不会让旧签名失效，也不替代对 nonce、授权和链上结果的核验。

## 第 6 层：广播未知、rawTx 与链上支出的唯一约束

**面试官：** rawTx 已签好，广播 RPC 超时。如何恢复？为什么 MQ 幂等仍不能保证只付一次？

**面试者：** 先将完整 rawTx、其 hash、付款意图、sender、nonce 和广播尝试持久化，再把它交给广播器。广播返回超时后，节点可能已接收并传播交易，也可能没有；恢复应查询原 hash 和链上 nonce 消耗，并可向多个可信节点重播完全相同字节。相同 rawTx 在链上的重复提交不会制造一个新的 nonce 付款，但要保留所有节点响应和尝试记录。不能生成另一笔独立交易来“确保消息处理成功”。

支出唯一性来自签名授权与链账户约束：一个 `(chainId,sender,nonce)` 只绑定一项意图，W1 也不被授权第二个付款 nonce；替换仅限同 nonce 的同业务付款加速，或经单独授权的不付款取消。发送钱包是专用普通 EOA，无委托、无人工旁路，各类出款共享 nonce 管理。MQ 的 exactly-once 即使存在，也只涉及消息语义；它既不能撤销旧 rawTx，也不能阻止服务用新 nonce 再签一笔，因此不能解决链上支出重复。

## 第 7 层：工作日志、定时恢复和重放顺序

**面试官：** 服务重启后只重放未确认 MQ 消息够吗？还要扫描哪些持久状态？

**面试者：** 不够，因为队列可能已经确认，但消费者在下一外部调用前崩溃；也可能外部调用成功而消费状态尚未落库。恢复应把数据库工作台当作待办清单，周期性扫描过期租约和非终态记录：RESERVED 待审批、SIGNING 与签名未知、已签待广播、发送未知、已包含未 finalized、最终结果待账务应用，以及 outbox 未交付状态。再与签名器 requestId 查询结果、持久 rawTx、链上交易和 nonce 观察交叉核对。

恢复顺序要先确认证据完整性和该钱包最低未解决 nonce，再追踪旧签名、广播及链上结果，接着应用已确定但未应用的充值／付款／归集结果，最后才派发可安全的新工作。不能只扫任务队列深度、靠内存工作日志，或把超期记录统一改 FAILED。日志用于诊断，业务事实必须可从数据库和外部证据重建；任何无法证明是否产生有效签名或付款的记录都继续保留预占并进入人工核验，而不是靠重发完成率掩盖未知窗口。

## 第 8 层：消费者去重历史与灾备恢复

**面试官：** 为节省空间能不能定期删除已处理的 eventId？数据库灾备恢复到较早备份时怎样避免重复付款？

**面试者：** 去重历史要覆盖事件可能重放的最长业务周期；提现、充值和结算的业务动作键应长期保留或以不可丢失的归档形式保留，不能只保留最近几天的 eventId。否则老消息或备份恢复后的回放会被当成新命令，重复创建预占、分录甚至签名任务。若要清理投递记录，也必须保留足以重建业务动作已发生、载荷一致和终态互斥的账务及意图身份。

灾备更危险的是数据库回退到签名前的备份，但外部签名器或链已向前执行。恢复后不能按旧库“没有 rawTx”就重新签款；应以备份时间点之后的外部签名器 requestId 记录、已持久化 rawTx 归档、发送地址 nonce 链上消耗及 finalized 检查点补回事实。对已签字节必须有受控持久备份，备份与恢复流程不能丢失或改写原始 rawTx；无法证明的窗口保持冻结。恢复数据库后也需先关闭新派发，重建外部事实和消费历史，再逐步开放，避免灾备把账本回退变成第二次支出的许可。

## 第 9 层：旧 worker、租约和授权 epoch 的边界

**面试官：** 任务租约过期后新 worker 接管，旧 worker 又恢复；epoch 增长能否保证旧 worker不会付款？

**面试者：** 租约和 epoch 可以阻止旧 worker获得新的数据库授权或发起新的签名请求，前提是签名入口会校验当前授权版本和意图状态。但它们无法撤销已经签出的 rawTx：交易字节可被旧 worker、代理层或网络中的接收方再次广播。更不能仅靠改数据库状态宣称该交易已失效。

接管流程先读回同一 W1 与 nonce 绑定，查询稳定签名 requestId，恢复既有 rawTx；广播只重播原字节，链上结果则持续观察所有候选 hash。若必须处置，使用同 nonce 受控加速或取消并等待 finalized 结果。旧 worker 恢复后，它拿旧 epoch 发起的新操作应被授权入口拒绝；若它提交的是原来已签 rawTx，系统仍必须按潜在外部交易处理。只有专用普通 EOA 的 nonce 最终在规范历史中被消耗，并且没有第二付款 nonce 授权，才能基于链上事实排除这批旧签名的未来执行能力。

## 第 10 层：恢复准入与没有全局 offset 的水位

**面试官：** 所有服务都重启成功，最大扫描高度也追上 head，是否可以认为事件全应用并恢复提现？

**面试者：** 不能。一个最大区块高度不能代表所有日志分区、所有地址、所有消息分区和账务结果都没有缺口；一个 MQ offset 也不代表签名或链执行完成。每种水位必须明确作用域，例如按链和扫描分区记录连续覆盖的 finalized 区间及检查点 hash，按消费者分区记录已提交位置，按业务聚合记录已应用结果版本。它们没有天然的单一全局最大值，不能伪造一个数来宣称全量应用。

恢复准入前，要检查 finalized 历史无矛盾、扫描区间无缺口，所有未决签名和广播都能关联到原 W1 与唯一 nonce，rawTx／签名请求可查，最终付款或不付款结果已应用或明确隔离，SETTLE／RELEASE 状态互斥，消费者至少一次重放不会改写已提交结果，资产与账本差异按币种和共同截止点可解释。之后按钱包分片逐步开放新预占与签名，并继续观测差异。即使消息处理达到 exactly-once，若恢复允许对 W1 换 nonce 付款或丢失旧 rawTx，链上仍可能重复支出，因此 MQ 不构成恢复准入的充分条件。

## 本题收束

### 机制

- 本地事务同时提交业务事实与 outbox，投递和消费按至少一次设计；消费效果、去重状态与本地更新同事务提交。
- 签名用稳定 requestId 查询和恢复；广播先持久化 rawTx，再重播原字节，并持续追踪原 nonce 与全部候选。
- 恢复任务扫描持久业务状态并核对签名器、rawTx、链上 nonce、finalized 结果和账务应用记录。
- 去重与账务历史覆盖完整业务生命周期；灾备不得丢失已签字节及其授权身份。

### 易错边界

1. MQ 确认只说明消息交付阶段完成，不等于业务、签名、链执行或结清完成。
2. 签名调用和广播调用超时都属于未知，不得断言“没有签”或“没有发”。
3. 租约过期、epoch 改变和数据库状态更新不能撤销已签 rawTx。
4. MQ exactly-once 不会替代一 sender/nonce 一意图以及一 W1 不授权第二付款 nonce。
5. 各分区与各类业务有独立进度；没有全局单一 offset 时，不得用最大水位代替完整性证明。

### 证伪反例

```text
签名器已生成 rawTx → 响应丢失 → worker 租约过期
→ 新 worker 因数据库无 rawTx 而用新 nonce 再签
→ 两笔交易先后进入 finalized 规范历史
```

注入该窗口并重启，检查系统是否通过稳定 requestId 找回原请求、保持 W1 唯一付款 nonce，并拒绝第二签名。若消息队列宣称 exactly-once 后仍可能出现第二笔付款，该方案已被证伪；MQ 的交付承诺没有覆盖链上支出。
