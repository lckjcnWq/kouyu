# 大问题 6：签名器怎样只为合法意图付款？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文范围：防御性说明 Ethereum 主网 USDC 提现的可信签名策略与权限隔离。W1 固定向 B 付 30，甲已预占 30；专用普通 EOA 不启用账户委托，无人工密钥旁路，签名成功不等于链上付款或账务结清。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| Signer / 业务审批 | 生成链上有效签名的执行者，与决定是否允许付款的规则。 | Signer 不能自行凭余额发钱，也不能自己消费用户预占。 |
| 可信授权网关 | 真正核验批准内容与当前权限的签名前入口。 | 不接受工作者自报“已审批”就签任意字节。 |
| 完整载荷 / 摘要 | 付款各字段及其内容指纹。 | 网络、发送者、nonce、合约、金额、地址和费用约束都要绑定。 |
| to / value / calldata | 交易调用对象、附带 ETH 数量及合约调用数据。 | to 是 USDC 代理，value=0，data 才指定 B 和 30,000,000。 |
| selector / 白名单 | 指定调用哪种函数，以及允许哪些目标和规则。 | 未知函数、额外调用或不受支持资产必须拒绝。 |
| nonce 双向唯一 | 一序号只属一意图，一意图只获一付款序号。 | 既防两笔任务抢 n，也防 W1 在 n 与 n+1 重复付款。 |
| chainId＋sender | 钱包序号管理的作用域。 | S1 从 D_A 发，W1 从 H 发；同一 H 的业务不能各管各的 nonce。 |
| 签名 requestId | 固定一份不可变签名载荷的恢复编号。 | 相同编号不同内容拒绝；受控加速改变费用需新载荷身份。 |
| rawTx / 持久化顺序 | 完整签名字节，及先保存后交付的纪律。 | 不允许广播器发送尚未可靠登记的内存交易。 |
| 签名未知 | 请求可能已完成，只是结果没有返回。 | 按原 requestId 查询，不能因库中没字节就释放或换 nonce。 |
| epoch / 旧主隔离 | 授权代次阻止失效工作者取得新签名。 | 必须由可信入口核验，不会撤销已产生的有效签名。 |
| HSM / 密钥隔离 | 降低密钥暴露的设备或运行边界。 | 保护密钥不自动证明 B、W1 版本或额度正确。 |
| 停签 / 策略恢复 | 关闭新授权并审查何时重开。 | 已签候选仍追踪，未知预占不因停签而自动退回。 |
| 重播 / 替换 / 新付款 | 相同字节重发、同 nonce 候选变化、产生独立付款能力。 | 换钱包或换 nonce 不是普通 retry；取消与原付款存在竞争。 |
| 费用预算 / 意图额度 | 约束链上花费和业务支出。 | 平台付 ETH 不等于无限加价，也不混扣 B 的 30 USDC。 |

## 把整篇文章压缩成一个故事

甲的 100 USDC 充值已入账，申请向外部 B 提现 30，账内留下 70 可用、30 预占。归集 S1 把 D_A 的 100 搬到 H，不增加甲的权益。审批服务批准 W1 后，执行器不能直接把“金额 30”交给密钥设备让它自由补参数，而要固定主网、H、nonce、USDC 代理、调用数据和费用上限，再由可信授权入口逐项核对。

签名器看到的交易 to 是 USDC 合约，value 是零，B 与 30,000,000 写在 transfer 调用里。若收款地址、合约或序号不符授权，就应拒签。数据库同时约束一个钱包序号只分给一项意图、W1 只拥有一个付款序号；所有共享 H 的归集、调拨和提现走同一登记路径。硬件保护密钥有帮助，却不能替代这些业务规则。

签名请求发出后超时，新工作者接管。它先按稳定 requestId 查询原结果，不因 rawTx 尚未落库就认定未签，更不换钱包重新付。取回签名后，先保存完整字节再交广播器。管理员提升 epoch 可以阻止旧工作者申请新签名，但若旧工作者早已拿到有效字节，这份交易依然可能执行，仍须纳入 W1 的候选追踪，预占不能释放。

若策略出问题，系统停新授权并继续观察旧候选；加速须受同 nonce 与费用上限约束，取消也要单独授权并等待竞争结果。最终证据确认 B 收到 30 后，账本才结清；数据库失败只恢复原结算，不再付款。甲最终为 70 可用、零预占，平台另记 ETH gas。恢复审批也要检查旧未知请求及权限清单，不能只看签名设备重新在线。这里说明的是防御边界和验证设计，不提供真实密钥操作，也不声称生产测试已经完成。

**流程位置与核心机制：** 本题聚焦提现或归集业务意图进入钱包执行域之后、签名之前和签名恢复期间的权限边界。签名器拥有生成有效链上授权的能力，但不拥有余额、审批或业务结清权。安全性来自完整付款载荷绑定、当前授权与意图版本校验、持久 nonce 双向唯一约束、受控入口和可恢复的签名请求，而不是把某个硬件设备称作万能边界。

**必要前提：** 沿用 Ethereum 主网 `chainId=1`、原生 USDC 代理、6 位整数金额、托管地址 `D_A` 与 `H`。E 向 D_A 充值 100 USDC finalized 后甲为 100／0；W1 预占 30 后为 70／30；独立 S1 把 100 从 D_A 归集到 H，甲负债不变；W1 最终向外部 B 支付 30 并结账后甲为 70／0、H 为 70，平台承担 ETH gas。W1 交易层 `to` 是 USDC 代理、`value=0`、调用数据为 `transfer(B,30_000_000)`，B 是 Token 收款方。所有签名和发送受控且无人工旁路；使用普通专用 EOA，不启用账户委托。只有 finalized 规范证据结清，finalized 矛盾即停止。意图、账本分录与 outbox 同一 PostgreSQL 本地事务提交，Signer 和链不在事务内。

## 第 1 层：签名权限与业务权限怎样分开

**面试官：** 平台需要给提现和归集交易签名。签名器应负责什么、不应负责什么？如何避免它根据一个“付款请求”就替业务系统作决定？

**面试者：** 签名器的能力本质上是把指定交易载荷转成可以由链接受的授权，因此它是高权限执行边界，不是提现审批器或账本。充提域负责验证用户请求、风险策略、余额并形成 W1；账本负责可用与预占的变化；授权入口把获准的 W1 版本转换为有限的签名请求；Signer 只校验该请求有可信授权并签固定载荷。它不能自行查到甲有余额就发钱，也不能因签名成功把预占结清。S1 是平台内部归集意图，和 W1 一样要有自己的业务身份和授权，不因“平台自有调拨”就绕过同一受控发送路径。回执、最终性和 Token 转移由链观察与结算流程核验。这样密钥控制与业务判断分离，同时没有把责任寄托在微服务名称上：任何能直接调用密钥的备用脚本、运维入口或进程都可能形成旁路，必须纳入权限盘点并关闭。签名权限不能替代数据库原子性，账本事务也无法撤销链上签名。

## 第 2 层：授权必须绑定完整交易，而非只绑定金额

**面试官：** 如果 W1 只给 Signer 一个金额 30 和用户审批通过标记，Signer 自己再补齐收款地址、网络和 Token 合约，为什么这仍然不够安全？

**面试者：** 因为可签载荷的任一字段被替换，都可能让同一个“金额 30”变成不同资产、不同收款人或另一条链上的付款。授权必须覆盖 chainId=1、发送者 H、nonce、USDC 代理合约地址、交易 `to`、`value=0`、完整 calldata、B、`30_000_000` 数量、费用上限、W1 身份和业务版本。Signer 或其前置授权网关要解码并重建字段，与持久化意图逐项比较，拒绝未知字段、额外调用、错误 selector、额外 Token 转移或链身份不符的载荷。这里 B 是 calldata 中 `transfer` 的 Token 收款方，不是以太坊交易层 `to`；交易层 `to` 是 USDC 代理。对 EIP-155 链身份及签名格式的校验不能替代业务白名单，资产代理地址也要跟随版本化策略。审批不能只签摘要后又允许调用方改变实际字节；应从已审批的规范字段生成确定载荷并计算其摘要，保存摘要和完整字段供恢复审计。否则合法审批会被“参数补齐”步骤变成另一笔付款。

## 第 3 层：nonce 双向唯一约束如何防两类冲突

**面试官：** 你绑定了完整内容。现在两台执行器同时处理 W1，或者一个钱包同时处理 W1 与归集 S1，仅有 nonce 锁能保证正确吗？

**面试者：** 不够，必须有两个方向的持久约束。钱包侧 `(chainId,sender,nonce)` 只能绑定一个业务意图，防止两个提现或归集任务争用同一个链上执行位置；业务侧一个 W1 只能绑定一个付款 nonce，防止 W1 在 n 超时后又被另一台执行器分配 n+1 再独立支付一次。两种约束应由数据库唯一键和条件状态共同保护，而不是只靠进程互斥锁、Redis 租约或各实例查询 `pending nonce`。所有用同一发送钱包的提现、归集、调拨都共享同一个 nonce 登记簿；本例 S1 的发送者 D_A，W1 的发送者 H，两者各自在自己的发送者空间排队。若不同任务共用 H，则必须由同一分配规则串行决定 nonce 与业务绑定。绑定先持久化才允许签名；发生事务冲突时由唯一约束选出一个赢家，其余读取已存在映射并验证载荷完全一致。nonce 不是提现幂等键，也不是全平台全局序号；它只在 chainId 与 sender 范围内定义链上执行顺序。

## 第 4 层：签名请求如何稳定重试并处理未知结果

**面试官：** Signer 已接收请求，但调用方超时；既没有返回 rawTx，也不知道它是否签完。怎样设计 requestId、重试和持久化顺序？

**面试者：** 每个不可变的签名载荷使用稳定 requestId，requestId 绑定 W1 版本、授权 epoch、chainId、sender、nonce 和完整载荷摘要。调用前先持久化这组绑定，Signer 对相同 requestId 的相同载荷提供查询或幂等恢复；同 requestId 若载荷不同必须拒绝。同 nonce 加速若调整费用字段，或单独授权同 nonce 取消交易，都属于新的不可变签名载荷，使用新的 requestId，但仍关联同一 W1 与 nonce，不能因此新建付款 nonce。超时后恢复 worker 查询原 requestId，或以相同身份重取结果，不能换 requestId 重新签同一载荷，也不能因为数据库还没有 rawTx 就认为签名不存在。Signer 返回后先将 rawTx、hash、签名请求结果和费用字段持久化；只有提交成功后，广播器才可取得待发送记录。若持久化响应也丢失，按 requestId 重查数据库及 Signer，再决定继续，不允许直接重签或发送内存中尚未持久化的字节。重放 rawTx 本身可以重复广播而保持同一交易 hash 与 nonce。Signer 的幂等恢复能力若不可用，状态就保持未知并人工核验，不能由调用方猜测为失败。该顺序解决数据库与外部签名服务无共同事务的问题，但不宣称两者原子提交。

## 第 5 层：授权 epoch 与旧主隔离的有效范围

**面试官：** 多实例部署时，W1 的旧主 worker 因租约过期被接管；管理员提升授权 epoch。怎样阻止旧主继续工作？这是否足以撤销它之前拿到的签名？

**面试者：** 授权入口每次签名调用都要校验当前 epoch、W1 当前版本、状态仍允许执行、nonce 绑定和完整载荷摘要；旧主携带过期 epoch 的新请求会被拒绝。epoch 要由权威数据库单调更新并包含在可审计授权记录中，Signer 不能仅信任 worker 自报一个较新值。租约和 leader 选举只决定谁可尝试调度，不是链上安全锁。但更新 epoch 只会挡住之后的新签名请求，无法撤回旧主先前已经拿到的有效 rawTx；那份字节仍可广播，必须并入 W1 的候选追踪，直到同 nonce 被最终消耗或有其他确定结果。接管者应查询稳定 requestId、原签名记录和 nonce，不另起新 nonce。若旧 worker 仅保留部分内存状态，重新上岗也不能绕开服务端授权入口。这个边界要求私钥调用端不能被业务 worker 直接访问，否则 epoch 只是一条数据库约定，过期进程仍能自行签出链上有效交易。

## 第 6 层：策略变更与紧急停签能关闭什么风险

**面试官：** 如果 USDC 策略、提现限额或授权规则发现问题，系统需要紧急停签。哪些操作应立即停止，哪些已有状态仍要继续观察？

**面试者：** 紧急停签应先让授权入口拒绝新签名资格，递增 epoch 或关闭对应策略范围，并停止产生新的 nonce 绑定和新的签名请求。若问题只影响某资产或某钱包，停用范围可以收窄，但范围选择必须有审计记录。已经签出的 rawTx 不会因策略更新而失效，所以广播器和观察器仍要跟踪已知 hash、同 nonce 替换候选与链上结果；停止广播新交易不等于可以释放 W1 的预占。若 finalized 视图矛盾，自动授信、结清和释放都应按证据策略暂停，不用更换 RPC 后马上继续。策略恢复要校验新版本、未解决 nonce、Signer 未知请求和权限清单，再允许新授权。硬件密钥、HSM 或隔离进程能降低私钥暴露风险，但它们不会自动验证 B、W1 版本、nonce 唯一性或费用预算，也不能替代紧急撤销流程。暂停功能本身要防止普通操作员绕过，恢复权限与触发停签权限可以分离，但不需要改变本题既定架构。

## 第 7 层：重试与费用策略怎样不绕过安全限额

**面试官：** 为避免未知交易卡住，团队想让重试任务自动换钱包、换 nonce 或提高 gas。如何确保重试不会绕开单笔金额、频率和费用限额？

**面试者：** 先区分重播、替换和新付款。重播相同 rawTx 不创建新授权；同 nonce 加速是同一 W1 的替换尝试，仅费用字段可按策略变化；换钱包或换 nonce 会产生新的付款能力，不能被标成普通 retry。每个授权在签名入口重新检查 W1 内容、每用户与资产的限额、日累计和费用预算，预算按业务意图及可能并行消耗的候选保守计入，不能在超时后因旧 attempt 暂时查不到就把额度归零。费用上限不允许自动突破；如果达到上限仍无法确认，钱包队列应保持阻塞并升级处置，而不是把限制当软建议。平台承担 ETH gas，但不能因此无限加价，也不能把 ETH 与 USDC 数量相加；USDC 付款金额仍固定为 30。可以把多个任务共享的钱包风险预算作为限流讨论，但它只是额度策略，不能替代“W1 一个付款 nonce”和“nonce 一个意图”的约束。审批后若策略版本收紧，是否停止新签名或要求重审要显式定义；旧签名依然按链上可执行风险追踪。

## 第 8 层：多实例恢复与签名安全的证伪方法

**面试官：** 最后，请总结多实例、旧主、签名未知与紧急停签的恢复规则，并给一个能检验“Signer 只替合法意图付款”的反例或方法。

**面试者：** 恢复先读取权威 W1 状态、业务版本、授权 epoch、唯一 nonce 映射、稳定 requestId 和所有 rawTx/hash；再向 Signer 查询未知请求，恢复同一载荷，不按空 rawTx 或租约过期另签。发送前确认已持久化 rawTx；广播只能使用登记过的原交易或同 nonce 受控替换。安全验证至少构造一个变体：保持 W1=向 B 付 30，却把 calldata 收款地址改为 B2、把代理改为其他合约、把 chainId 改掉，或使用同 W1 的第二个 nonce。只要授权入口对其中任一变体返回签名，边界就被证伪。另模拟旧主在 epoch 变更后提交新签名请求，应被拒；但若它此前已拿到签名，系统仍须追踪且不得释放预占。按固定案例，S1 归集后甲仍 70／30，W1 只有 finalized 付 B 30 才结账至 70／0。上述是可重复的验证设计，不表示已做真实资金或生产环境测试。

## 本题收束

### 已讲透的机制

- 业务审批、账本状态、签名授权、链上执行分属不同权威边界。
- 签名请求绑定完整付款载荷、意图版本、epoch、稳定 requestId 和持久 nonce。
- `(chainId,sender,nonce)→一个意图` 与 `W1→一个付款 nonce` 双向约束。
- epoch 可拒绝旧主的新请求，不能撤销已签出的有效交易；策略停签后仍须跟踪旧尝试。

### 最容易答错的边界

1. Signer 收到“金额 30”不等于获得了正确收款地址、合约、网络和 nonce 的授权。
2. HSM 保护密钥，不天然保证业务字段合法、预算未超或同一 W1 不重复付款。
3. 签名超时和数据库无 rawTx 都是未知，不是未签证明。
4. 重试不能换 nonce 或钱包伪装成同一笔授权；费用上限也不能被自动重试绕过。
5. 普通专用 EOA 与统一受控发送路径是本题前提，不引入账户委托或人工旁路。

### 一个可证伪验证

用同一 W1 的授权分别提交正确载荷和篡改后的收款地址、chainId、Token 合约、金额及第二个 nonce。任一未授权载荷仍能得到签名，或旧 epoch 能发起新签名，即证明权限隔离不足；而旧 epoch 变更前已签出的交易仍必须被追踪，不能把“停签”误当作“撤销”。
