## 先看懂：关键词大白话解释

> 本文范围：用链下托管账户和 Ethereum 主网白名单原生 USDC，串起充值 100、提现 30、归集及故障恢复。用户 USDC 提现费为零，平台另付 ETH gas；最终性规则不推广到所有链，MVP 只是手工教学模型。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 链下托管 / 用户负债 | 币由平台控制，用户持有平台内部记载的权益。 | 甲的可用余额不是某个链上地址的实时余额。 |
| chainId / 合约白名单 | 先确认在哪条链、哪个合约发行的资产。 | 仅认 chainId=1 上指定的原生 USDC，不按代币名字认钱。 |
| 最小单位 / 精度 | 把金额换成整数刻度，避免小数误差。 | USDC 为 6 位，30 USDC 保存为 30,000,000。 |
| 地址登记簿 / D_A | 记录地址归谁、用于什么。 | D_A 固定属于甲，H 是平台热钱包，不能见到入账日志就给用户加钱。 |
| receipt / Transfer | 回执说明交易执行结果，转账事件说明代币转移细节。 | 成功回执还须配合可信 USDC 合约、收款地址和金额核验。 |
| 观察身份 / logIndex | 给某个分支中的某条日志定位。 | 使用链、块 hash、交易 hash 和日志索引；txHash 单独不够。 |
| canonical / finalized | 前者是当前规范链，后者是可信视图中的最终确认历史。 | 本例只对处于 finalized 祖先链上的合格转移授信。 |
| 重组 / 冲正 | 链分支改了要撤销旧观察；已记错账用新分录纠正。 | 未授信分支只撤观察，最终证据矛盾则停机核验，不自动二次入账。 |
| depositId / CREDIT | 一笔合格充值的业务编号及其入账动作。 | 重扫同一充值仍复用身份，只产生一次余额效果。 |
| withdrawalId / requestId | 前者标识付款义务，后者识别入口重试。 | W1 不随交易 hash 更换；同请求键改收款内容必须拒绝。 |
| 可用 / 提现预占 | 可用还能花，预占是已为某笔提现锁住的权益。 | 100 先变成可用 70、预占 30，此时不是已经付给 B。 |
| 本地事务 / 追加式分录 | 数据库内一起提交，并保留每次变化的依据。 | 意图、余额、分录和 outbox 同事务；链上转出不在此事务里。 |
| outbox / 至少一次交付 | 把待发消息跟业务一起保存，允许反复送达。 | 收方还要按业务身份去重，消息送达不是链上付款证明。 |
| 审批 / SIGNING 边界 | 审批确认允许付什么；SIGNING 表示开始取得签名资格。 | 取消必须竞争执行资格，进入签名阶段后不能按“没 hash”退款。 |
| 签名授权 / epoch | 可信策略核对付款内容与授权代次。 | 签名器拒绝旧授权和越权载荷，不能仅凭工作者自报“已审批”。 |
| EOA / nonce | 本例普通钱包按发送者交易序号执行。 | nonce 按链与发送地址统一管理，归集和提现不能各分配一套。 |
| Attempt / rawTx | 同一意图的执行尝试，以及已签名的完整交易字节。 | W1 可重播或受控加速，但不能另换 nonce 再付一笔。 |
| SEND_UNKNOWN | 不知道广播是否已被接收或执行。 | 超时不是失败，保留预占，查询并恢复原付款。 |
| 替换 / 取消竞争 | 同 nonce 的加速或取消，与原交易争夺执行机会。 | 发出取消不保证取消获胜，必须追踪全部候选到最终结果。 |
| SETTLE / RELEASE | 结清已付义务，或把确定不会付款的预占退回。 | 同一 W1 两者互斥，不能各做一次后都算幂等。 |
| 归集 / 钱包流动性 | 平台把自己的币搬到适合出款的位置。 | D_A 到 H 的 100 不再给甲充值；H 空也不代表甲没余额。 |
| 共同水位 / 差异修复 | 在同一链截止点和账务进度下比较证据。 | 已最终付款但未结账属于待应用差异，重试结账而非重付。 |

## 把整篇文章压缩成一个故事

甲打开平台充值页，拿到以太坊主网、指定 USDC 合约和固定地址 D_A，再从外部钱包转来 100 USDC。观察器看到日志，只告诉甲“检测到”，不立即增加可用。它核对成功回执、真实转账、地址归属及规范块身份，等目标块属于可信 finalized 历史，才创建充值业务身份。随后数据库一次提交分录、余额和待发通知，甲得到 100 可用；重复扫描不能再加一次钱。

甲申请把 30 USDC 提到外部地址 B。系统先在本地事务中建立 W1，把可用改为 70、预占改为 30，回复“已受理”。审批绑定的是这笔提现和完整付款内容，不是随便一张通过标记。此时热钱包 H 还是空的，执行器等待平台归集：D_A 的 100 移到 H，只改变托管位置，不增加甲的权益。甲不付 USDC 提现费，平台另外准备 ETH 支付链上费用。

执行器取得签名资格，为 W1 固定链、发送者、nonce 和付款内容，再由受控签名器核验授权。签名字节保存后才广播；若节点超时，系统仍保留预占，追踪原交易，而不是换个编号重新付。需要加速时也受同 nonce 约束；若改走授权取消，原付款仍可能抢先执行。旧工作者即使恢复，也不能取得新授权，但已经传播的签名不能靠数据库改状态收回。

当可信最终证据证明 B 实收 30，平台才在账内消费预占并结清 W1。若付款已完成而数据库故障，继续保存证据和预占，恢复后重试原结算，不再转币。最终 H 有 70，甲有 70 可用、零预占；这组相等只适用于本例共同截止点和零 USDC 费用条件。未最终分支变化先撤观察，最终证据冲突则暂停核验；确认损失后追加授权冲正，不能删账假装从未发生。

### 1.1 讨论基线与准备条件

| 项目 | 本专题约定 |
|---|---|
| 产品 | 平台控制充值地址和出款钱包，用户拥有内部账本债权；不是钱包直连 AMM Swap，也不是用户自行调用 Vault 提款 |
| 链与资产 | Ethereum 主网，`chainId=1`；仅支持白名单中的原生 USDC，精度 6 位；网络与合约共同确定资产，不根据名称或符号认币 |
| 合约 | USDC 主网代理地址 `0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48`；解析与风险策略有版本，不假设代理实现永远不变 |
| 入金识别 | 只接收向平台分配地址的受支持 ERC-20 转账，校验成功回执和目标合约的真实 `Transfer`；不覆盖原生 ETH、内部转账 trace、桥接到账或任意代币 |
| 地址归属 | 充值地址 `D_A` 固定绑定用户甲，不复用给其他用户；热钱包 `H` 与充值地址都在平台地址登记簿中 |
| 入账门槛 | 仅在验证目标转移属于当前可信节点视图中的 `finalized` 历史后，增加可用余额；未最终确认只有观察记录，没有提前授信 |
| 提现规则 | 提现 30 USDC，收款人应实收 30 USDC；本例 B 是外部地址，不是平台控制地址；平台承担 ETH gas，用户 USDC 提现费为零，不混扣 gas 和 Token 数量 |
| 资金分层 | 用户负债分为可用与提现预占；平台链上托管资产单独按地址核算；链上持币位置不等于用户余额 |
| 实现基线 | 充提意图、账本余额、追加式分录和 outbox 在同一 PostgreSQL 本地事务内提交；链观察、签名与 RPC 不进入该事务 |
| 执行方式 | 钱包使用专用普通 EOA，不启用账户委托；所有发送与签名走同一受控路径，无人工旁路；每个发送地址持久化管理 nonce，替换只允许同 nonce、同付款内容的加速或单独授权的取消 |
| 相邻能力 | 不展开撮合、杠杆、保证金、跨链、合约钱包和批量提款；账本与链同步细节引用相邻专题，但不能省略充提依赖的契约 |

**准备条件：** 读者只需理解整数金额、数据库事务和以太坊交易的基本含义。下文用符号地址与交易身份手工推演，不需要私钥、真实资金、运行环境或可运行 Go 工程。

### 1.2 贯穿案例：充值 100，再提现 30

初始假设：甲的可用余额、提现预占均为 0；`D_A` 与 `H` 的 USDC 余额也均为 0。平台另外持有足够的 ETH，能给充值地址提供归集 gas，并承担热钱包出款 gas；ETH 的费用账不并入本例 USDC 等式。

```text
金额统一使用 USDC 最小单位：1 USDC = 1,000,000

外部地址 E → D_A：100 USDC = 100,000,000
    达到入账门槛后，甲：可用 100，预占 0

甲申请 W1：从平台提现 30 USDC 到外部地址 B
    原子预占后，甲：可用 70，预占 30

独立归集 S1：D_A → H，100 USDC
    最终确认后，D_A=0，H=100；甲的负债不变

外部付款 W1：H → B，30 USDC
    最终确认并完成结账后，H=70；甲：可用 70，预占 0
```

本例刻意让热钱包初始为零，以说明：**用户有可提现余额，不代表出款钱包已有流动性。** 归集是平台资产搬运，不是再给用户充值一次，也不应成为解除用户负债的理由。

### 1.3 充值主链路

```text
甲查询充值入口
    ↓
充值服务返回〔网络、白名单合约、固定收款地址 D_A、到账规则〕
    ↓
甲在外部钱包发起 E → D_A 的 100 USDC 转账
    外部钱包负责签名与发送；平台不掌握外部付款的执行权
    ↓
链观察器连续扫描区块与日志，保存证据及扫描水位
    输入：区块、receipt、Transfer 日志、地址登记簿
    输出：充值候选；只是“检测到”，不改用户可用余额
    ↓
充值识别与链视图校验
    验证网络、合约、收款归属、金额、回执成功、区块归属
    排除平台自己的归集／调拨；不支持或归属不明 → 隔离待处理
    ↓
最终性策略确认
    目标块位于可信 finalized 历史，且同高度规范块 hash 一致
    ├─ 未达到 → 待确认；出现链分支变化则撤销旧观察
    └─ 达到 → 固化证据、策略版本和 depositId
                    ↓
充提／账本域的一个本地事务
    唯一业务键去重＋追加充值分录＋可用 0→100
    同时提交充值已入账状态和 outbox
                    ↓
结果投影与通知
    页面显示“已入账／可用 100”，投影延迟可通过权威查询核实
                    ↓
按共同截止区块和账务应用水位核对链上合格入金与充值分录
```

**充值的完成含义：** 平台有符合策略的链上收款证据，而且对应分录、余额、业务状态已经提交。拿到交易哈希、看见一条日志、收到一条消息，都不是同一个完成点。

### 1.4 提现与归集主链路

```text
甲提交提现请求〔requestId、chainId、asset、B、30 USDC〕
    ↓
接入与风险校验
    鉴权、敏感操作验证、地址／网络、限额、资产状态、金额与精度
    参数错误或余额不足 → 拒绝，不留下成功预占
    ↓
充提／账本域的一个本地事务
    绑定请求键与规范化载荷，创建 W1
    可用 100→70，提现预占 0→30；写分录、状态 RESERVED、outbox
    事务提交后返回“已受理”，不是“已付款”
    ↓
审批服务给出绑定 W1 版本与完整付款内容的授权
    拒绝 → 在仍无签名资格时，按条件更新状态并原子释放
    ↓
钱包执行器检查 H 的 USDC 与 ETH 流动性
    本例 H=0 → W1 等待，不把用户余额缺口与钱包流动性混为一谈
    ↓
独立归集 S1：D_A → H，100 USDC
    使用自己的意图、nonce、签名、广播与确认记录
    最终确认后仅调整托管资产位置：D_A 100→0，H 0→100
    不增加甲的余额，不再次计为用户充值
    ↓
W1 条件迁移 APPROVED→SIGNING，进入禁止直接释放的执行阶段
    持久化 nonce 绑定、签名授权与付款内容；受控签名
    已签名字节与 hash 持久化后，才允许交给广播器
    ↓
广播与链上追踪
    ├─ RPC 超时 → 保留原付款身份，记录发送结果未知
    └─ 已接收   → 仍等待链上执行，不代表已到账
    重播相同字节；需要加速时，只创建受约束的同 nonce 替换
    ↓
观察包含区块、执行状态与目标 Token 转移
    区块尚未最终确认 → 仍保留预占；重组后回到追踪
    ↓
确认属于 finalized 历史且 H → B 的实际付款为 30 USDC
    ↓
充提／账本域的一个本地事务
    以 W1 的结算业务键去重，消费预占 30→0
    减少用户负债和对应托管 USDC 资产 30
    同时提交 SETTLED、分录、已应用结果版本和 outbox
    ↓
查询／通知显示“已完成”，对账关闭此付款义务
```

出款的 ETH gas 无论成功还是执行回滚都可能消耗，必须另记费用；“USDC 付款失败”不意味着平台所有资产都没有变化。

### 1.5 主要异常分支

```text
充值日志重复 / 扫描窗口重叠
    → 相同观察键与相同 depositId 重放 → 返回原入账结果，不新增余额

充值尚未最终确认就移出规范链
    → 撤销该分支的观察投影 → 无已入账余额可冲正 → 扫描新规范分支

已宣称 finalized 的证据出现矛盾
    → 暂停相关链的自动授信与出款，保留证据并独立核验
    → 不自动把另一分支当成第二笔充值
    → 真正确认资产损失后，按授权追加冲正／差额分录，不删除历史
```

```text
提现审批拒绝 / 用户取消
    → 若取消先于执行资格产生且原子抢占成功：关闭意图＋释放预占
    → 若已进入 SIGNING 或以后：不能按“还没查到 hash”释放

签名调用超时 / 广播超时 / 节点暂时查不到
    → 原 nonce 与原 W1 继续恢复 → 不新建独立付款、不解冻

交易被包含后重组
    → 保留所有历史观察，回到未最终确认的追踪 → 不提前消费或释放预占

原 nonce 的回滚交易，或受控取消交易，已最终确认
    → 核实没有其他 nonce 的付款授权，旧工作者不能获得新授权
    → 以不会再付款的证据关闭 W1，再原子释放

链上已最终付款，数据库结账失败
    → 保留预占与付款证据，重试同一个结算业务键
    → 绝不通过“再付一次”来修复账务故障
```

### 1.6 案例中的状态、资金与完成点

| 阶段 | 甲可用／预占 USDC | 本例最终确认口径的链上 USDC | 业务承诺 |
|---|---:|---|---|
| 初始 | 0／0 | D_A=0，H=0 | 尚无资金权益 |
| 观察到充值，未最终确认 | 0／0 | 尚未进入最终确认资产口径 | 仅检测到 |
| 充值入账事务提交 | 100／0 | D_A=100，H=0 | 已有可用余额 |
| W1 预占提交 | 70／30 | D_A=100，H=0 | 已受理，未付款 |
| S1 最终确认并应用 | 70／30 | D_A=0，H=100 | 只是资产位置改变 |
| W1 已包含但未最终确认 | 70／30 | 仍按共同 finalized 截止点取数 | 未承诺完成 |
| W1 已最终付款，结账尚待重试 | 70／30 | D_A=0，H=70 | 有确定出款，存在待应用账务差异 |
| W1 结账提交 | 70／0 | D_A=0，H=70 | 付款与负债结清 |

允许“链上已完成、账务待应用”的可追踪暂态；禁止“已经付款又释放 30 到可用”以及“同一付款重复减少负债”。

## 第二部分：核心板块

| 核心板块 | 决定什么、拥有什么状态 | 上下游契约与核心原因 |
|---|---|---|
| 资产与地址登记 | 网络、合约、精度、解析策略版本、地址控制权和用户归属 | 充值入口与观察器共用；认错链、假 Token 或归属错误，后面的事务再正确也在记错钱 |
| 链观察与最终性 | 原始区块／日志证据、规范链视图、扫描水位、缺口与最终性判断 | 交付可重复的证据和撤销，不直接写用户余额；决定何时可以认定外部事实 |
| 充提意图与策略 | depositId、withdrawalId、请求载荷、审批、业务版本和合法迁移 | 连接链证据、预占和钱包动作，决定是否有资格授信、签名、结算或释放 |

| 恢复、对账与回报 | 恢复任务、差异、修复授权、投影水位与通知结果 | 用稳定身份修复交付和应用，不用新付款代替恢复，不直接改余额抹平差异 |

## 第三部分：核心 20%

“20%”指优先掌握决定正确性的机制，不是把完整链路压缩成少量术语。

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 真实转移与归属校验 | 充值识别、提现结果核验 | 证明钱确实进入或离开正确控制域 | 假币入账、错用户、成功回执但未付款 | chain＋contract、receipt、Transfer、地址登记与资产版本 |
| 最终性与链分支 | 入账前、结清前 | 把观察与可承担的业务承诺分开 | 分支转账被当成最终资产 | finalized 证据、块 hash、未最终观察撤销、异常熔断 |
| 意图与尝试分离 | 提现申请至终态 | 一笔付款可多次发送，但不能多次独立支付 | 换 hash 就重复扣款或重复出金 | withdrawalId、attempt、同 nonce 约束、结果聚合 |
| 原子预占与释放裁决 | 提现受理、取消、失败 | 余额竞争和执行资格必须闭合 | 并发提现超额、解冻后迟到付款 | 条件扣减、状态版本、SIGNING 边界、关闭资格证据 |
| 签名授权与 nonce 约束 | 归集、出款 | 账本幂等无法阻止链上第二笔交易 | 两个 nonce 付同一笔、旧工作者复活 | 持久绑定、完整载荷、授权 epoch、rawTx 保存 |
| 确定结果的幂等应用 | 充值入账、提现结账 | 外部确认与数据库无共同事务 | 已付款但账未结、重复分录 | 本地提交边界、业务唯一键、outbox、消费事务 |
| 共同水位的对账与恢复 | 全链路 | 区分正常在途和真实缺失 | 假差异、错误退款或人工重付 | finalized 截止块、账务应用位置、差异分类、追加修复 |

## 第四部分：设计与规则

### 4.1 金额、分录与不变量

所有 USDC 数量用最小单位整数保存。Go 实现可用 `big.Int` 或检查过上界的整数，数据库用范围足够且 `scale=0` 的数值类型；不能用 `float64` 参与入账或比较。拒绝负数、零提现、超精度和溢出，不静默截断。

本例按资产与负债分录理解五类变化：

```text
充值入账：借 托管USDC资产:D_A 100；贷 用户USDC负债:甲:可用 100
提现预占：借 用户USDC负债:甲:可用 30；贷 用户USDC负债:甲:预占:W1 30
内部归集：借 托管USDC资产:H 100；贷 托管USDC资产:D_A 100
提现结清：借 用户USDC负债:甲:预占:W1 30；贷 托管USDC资产:H 30
安全释放：借 用户USDC负债:甲:预占:W1 30；贷 用户USDC负债:甲:可用 30
```

这是一套简化教学账，不是完整会计科目设计。ETH gas 单独记平台资产与费用；不把 USDC 和 ETH 的裸数量相加做守恒。

必须成立的约束：

1. 用户可用和单笔有效预占不为负；所有余额变化都有不可删除的分录依据。
2. 同一合格充值的 `CREDIT` 只应用一次，同一 `W1` 的 `SETTLE` 或 `RELEASE` 只能生效一个；业务唯一键与状态条件同时约束，不能只让两个键分别去重。
3. 对一笔金额为 `A` 的已受理提现：`A = 未消费预占 + 已结清金额 + 已释放金额`；本模型不支持部分提现，结清与释放互斥。
4. 外部有效付款需要有对应 W1、预占与授权；W1 的所有正常付款尝试受同一发送地址及 nonce 约束，不能并行授权第二个 nonce 再付一次。
5. 取消不是一条随时可执行的反向分录。先证明旧付款不会再发生，或在付款授权产生前原子关闭意图，才能释放。
6. 仅就本例的零初值、零 USDC 费用、无损失条件，在全部证据应用完成的共同截止点：`平台托管 USDC 资产 = 甲可用 + 甲预占`。链上已付款但账未结时必须列出待应用出款差异，不能强求不同进度的快照相等。

更一般的资产负债表还包括平台自有资金、费用、应收、损失和其他用户。上述等式不是完整偿付能力证明；USDC 的冻结、暂停、升级与发行方风险也不会因为等式成立而消失。

### 4.2 架构与权威边界

```text
外部用户钱包 ──链上转账──→ Ethereum
                              ↑          │
                         广播器          │区块 / receipt / logs
                              ↑          ↓
                     钱包执行域      链观察与证据域
                     nonce / 尝试    规范链 / 水位 / 最终性
                              ↑          │
                         签名授权        │合格充值 / 确定付款 / 撤销观察
                              │          ↓
用户 ──API──→ 充提与账本域〔同一 PostgreSQL 本地事务〕
               请求去重 / 意图 / 状态版本 / 预占 / 分录 / outbox
                              │
                      审批策略与钱包任务
                              │
                      查询投影 / 通知 / 对账
```

- **链**决定规范历史里的执行与 Token 转移，RPC 是获取证据的接口，不是“付款审批器”。
- **充提域**决定业务资格与状态迁移；**账本**决定用户余额与负债变化。基线将两者放在同一本地事务中，不另引分布式扣款协议。
- **签名器**只接受受控授权并签指定载荷，不凭缓存余额自行决定转账。链观察器不拥有用户余额写权。
- 本地事务只覆盖数据库事实。签名、链执行、消息投递与页面展示都不在同一个原子提交范围里，必须允许可识别、可恢复的中间态。

### 4.3 核心对象与稳定身份

| 对象 | 必要字段与约束 |
|---|---|
| `AssetPolicy` | chainId、contract、decimals、支持状态、解析／最终性策略版本；发布变更可审计 |
| `AddressBinding` | chainId、address、控制域、用户或钱包用途、有效范围；D_A 在本例不重新分配 |
| `ChainObservation` | chainId、blockNumber、blockHash、parentHash、txHash、logIndex、原始日志／receipt、规范性、最终性与证据来源 |
| `Deposit` | depositId、合格观察引用、用户、资产、整数金额、policyVersion、入账状态；同一合格观察只有一个 Deposit |
| `Withdrawal` | withdrawalId、userId、requestId、规范化载荷摘要、amount、reservationId、审批版本、状态版本、执行授权、结算／释放结果 |
| `WalletIntent`／`Attempt` | 归集或付款意图、withdrawalId（如适用）、chainId、sender、nonce、to/value/data、费用上限、授权 epoch、attemptId、rawTx、txHash、所有链观察 |
| `LedgerEntry`／`Outbox` | entryId、业务动作键、资产、借贷分户、金额、原分录引用（冲正时）；eventId、聚合版本、载荷、待交付状态 |

对于本例的直接 Token 付款，交易 `to` 是 USDC 代理合约、`value=0`，调用数据编码 `transfer(B, 30_000_000)`；B 不是交易层的 `to`。同一成功回执中还要核对认可合约发出的 `Transfer(H,B,30_000_000)`，且没有相反或额外的业务支出。固定 finalized 检查点 `(height, hash)`，验证充值／付款所在块属于其祖先链，并把 receipt、log 绑定到该块 hash；处理新区间前检查旧检查点是否一致。对未知 USDC 实现升级或证据冲突暂停自动处理，不只校验代理自身 code hash。

**不要混用三种身份：**

- **观察身份**可用 `(chainId, blockHash, txHash, logIndex)`，能区分分支和单笔交易内多条日志。这里的 `logIndex` 是区块内索引，跨重组可能变化，不是永远稳定的逻辑充值编号。
- **业务身份**是持久化的 `depositId`、`withdrawalId` 和归集 `S1`。本基线仅对最终合格观察创建入账身份，同一观察重放复用它；未最终分支换了，只换观察。若已最终证据矛盾则停机核验，不自动建立第二笔入账。改变为提前授信时，必须另外设计跨分支匹配、冲正与重新确认协议。
- **账务身份**是 `(depositId, CREDIT)`、`(withdrawalId, SETTLE/RELEASE)` 等业务动作键。消息 ID 或某个 txHash 不能替代业务身份；结清和释放还受互斥状态裁决。

### 4.4 状态机与不可跨越的边界

```text
充值观察：SEEN → PENDING → FINALIZED_VALID
                    └─ 移出规范链 → ORPHANED〔保留历史〕
充值业务：FINALIZED_VALID 证据 → CREDITED〔本地事务〕
证据冲突：REVIEW / 暂停自动处理，不把矛盾压成普通 FAILED
```

```text
提现业务：RESERVED → APPROVED → SIGNING → PAYING → SETTLED
           │           │          │          │
           └─取消/拒绝─┘          └──不确定──┘ → 保留预占并恢复
             ↓
       CANCELLED / REJECTED〔关闭资格＋释放，同事务〕

SIGNING / PAYING 之后：
    只有最终不付款证据＋授权闭合 → FAILED_RELEASED
    证据矛盾或内容不匹配        → REVIEW，不能自动释放
```

尝试另存 `SIGNED`、`SEND_UNKNOWN`、`SUBMITTED`、`INCLUDED`、`FINALIZED_PAID`、`FINALIZED_REVERTED`、`FINALIZED_CANCELLED` 等执行证据，不能拿“某次 RPC 失败”直接覆盖提现业务状态。

**四个关键提交边界：**

1. 请求键、意图、预占、分录与 outbox 同事务提交，才算可靠受理。
2. 工作流条件更新进入 `SIGNING`，再生成绑定意图版本的签名资格；取消必须竞争同一个状态，而不是看任务队列有没有消息。
3. nonce 与付款内容先持久绑定，签名请求保存稳定 requestId，签名服务支持按此 ID 查询或幂等恢复；已签名字节持久化后才交付广播。签名调用超时属于未知，不因为库里没 rawTx 就断言没有签名。
4. 最终付款证据应用时，预占消费、分录、`SETTLED` 与结果 outbox 同事务提交；进程崩溃后重放仍使用原业务键。

签名器或授权网关要验证当前授权 epoch、意图版本和持久 nonce 绑定。仅靠 worker 的租约、Redis 锁或数据库状态，不能撤回已经泄露到网络的有效签名；它们最终失效要靠该 nonce 被规范链最终消耗等链上事实。

### 4.5 并发、恢复与对账的实现选择

- PostgreSQL 事务内用请求唯一约束、余额行锁或条件更新、意图版本比较与分录唯一约束。余额不足使整个预占事务回滚；不能先返回成功再异步扣余额。
- Go worker 使用有界队列、超时和上下文取消控制资源；`context` 超时只停止本次等待，不撤销已发生的签名、广播或数据库提交。每个失败都按所处业务阶段解释。
- 钱包 `(chainId, sender, nonce)` 的持久唯一绑定跨归集、调拨和提现共享，不允许多个进程各查一次 `pending nonce` 后独立分配。nonce 卡住时暂停该钱包后续派发或受控加速，不盲目跳号“解决”积压。
- outbox 可重复投递。消费者在自己的本地事务中写入去重／版本、更新投影或任务状态后确认消息；最终性证据变化不能单靠“最大版本覆盖”吞掉冲突。
- 恢复先扫 `SIGNING`、已签名、发送未知、已最终但账未结的记录，核查签名器与链证据，再派新任务。不可用数据库中的空 hash 推断付款未发生。
- 对账固定区块 `(height, hash)` 与账务应用水位：核对充值集合、付款集合、归集集合、用户负债和托管资产。已经最终但未应用、未最终在途、遗漏扫描、重复分录、未授权支出分别归类；修复必须重用原身份或追加授权冲正，不直接改余额。

## 第七部分：工程实践——一个简洁 MVP

### 7.1 目标与范围

用一个**单线程、无崩溃的内存模型**验证：充值去重、提现预占、未知态保留、结清与释放互斥。链证据作为预先核验的输入夹具，不实现真实扫链、最终性验证、签名、广播、归集或持久化恢复；不创建可运行工程、不执行工程测试。

### 7.2 核心伪代码

所有数量均为最小单位整数；命令的字段、资产、正数范围和上界先校验，下面聚焦状态规则。每条命令串行执行；断言失败时不做任何写入，所有检查先于修改，内存提交期间不注入失败。

```text
available = 0; held = 0; deposits = {}; withdrawals = {}

apply(c):
  校验命令结构、整数范围和已核验夹具的身份与内容绑定
  if c.type == CREDIT:
    require c.proof.kind == FINALIZED_IN && c.proof.amount == c.amount
    if deposits.has(c.depositId):
      require deposits[c.depositId] == c.payload; return 原结果
    available += c.amount
    deposits[c.depositId] = c.payload
  else if c.type == RESERVE:
    if withdrawals.has(c.requestId):
      require withdrawals[c.requestId].payload == c.payload; return 原结果
    require available >= c.amount
    available -= c.amount; held += c.amount
    withdrawals[c.requestId] = {payload:c.payload, amount:c.amount, state:HELD}
  else:
    w = withdrawals[c.requestId]; require w 存在
    if c.type == UNKNOWN: return w.state              # 不释放，也不再次扣款
    require c.proof 绑定 w 的身份、金额和全部付款尝试
    target = c.type == PAID ? SETTLED : RELEASED
    require c.type 属于 {PAID, NO_PAYMENT}
    require c.type == PAID ? c.proof.kind == FINALIZED_PAID
                          : c.proof.kind == CLOSED_NO_FUTURE_PAYMENT
    if w.state == target: return 原结果
    require w.state == HELD                          # 相反终态必须拒绝
    held -= w.amount
    if target == RELEASED: available += w.amount
    w.state = target
  return {available, held, withdrawals}
```

这里没有用“安全释放()”隐藏未知交易问题。`CLOSED_NO_FUTURE_PAYMENT` 是**模型外提供的证据假设**，在生产中必须由前述资格关闭或最终 nonce 消耗及授权核验产生，绝不是 `RPC_TIMEOUT` 的别名。MVP 不声称自己验证了链上安全性。

### 7.3 输入与手工预期结果

| 输入序列 | 预期结果 |
|---|---|
| `CREDIT(D1,100)`，再重放相同 D1 | 可用 100，预占 0；只有一个充值效果 |
| D1 已存在，却以同身份改金额为 200 | 载荷冲突，拒绝；仍为 100／0 |
| 接上：`RESERVE(R1,30,B)`，再重放相同 R1 | 可用 70，预占 30；只有一个提现意图 |
| 接上：`UNKNOWN(R1)`，随后 `RESERVE(R2,80,C)` | UNKNOWN 不释放；R2 余额不足，状态仍为 70／30 |
| 接上：`PAID(R1,最终付款证据)`，再重放 | 可用 70，预占 0；W1 只结清一次 |
| 接上：对 R1 输入 `NO_PAYMENT` | 相反终态冲突，拒绝，不能把 30 退回可用 |
| 独立变体：从充值 100、预占 30 开始，输入合法 `NO_PAYMENT`，再重放 | 可用 100，预占 0；只释放一次 |
| 独立变体：只有“节点查不到”却要求 `NO_PAYMENT` | 缺少关闭付款资格证据，拒绝；仍为 70／30 |

金额显示为 USDC，实际输入分别为 `100,000,000`、`30,000,000` 等。上述为手工推演目标，不是工程测试通过声明。
