# 大问题 1：一笔充值和提现怎样走完，系统职责如何划分？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文范围：讲 Ethereum 主网原生 USDC 托管充提的端到端职责和完成点。甲充值 100、提现 30，用户 USDC 提现费为零，平台另付 ETH gas；不把数据库提交、链上最终付款和页面成功混成一件事。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 链上资产 / 账本权益 | 地址持币事实与平台欠用户多少是两套相关记录。 | D_A 归集成零后，甲的内部权益并不会清零。 |
| 充提意图 | 把一次收付的对象、金额和处理阶段固定下来。 | W1 是向 B 付 30 的义务，不是某次 RPC 请求。 |
| 资产与地址登记 | 确定收的是什么币、地址属于谁。 | 核对主网白名单 USDC、6 位精度和 D_A 的甲用户归属。 |
| receipt / Transfer | 分别提供执行结果和具体代币转移证据。 | status=1 仍须核验正确合约向正确地址转移正确金额。 |
| finalized 检查点 | 带高度和块 hash 的可信最终历史锚点。 | 充值或付款块必须在它的规范祖先链上。 |
| 观察键 / depositId | 前者定位分支日志，后者固定合格充值业务。 | txHash 不能区分多日志；块变化也不能自动新加一次钱。 |
| 本地事务 / outbox | 把账内变化及待发事件一起可靠保存。 | 充值状态、分录和余额一起提交，不包含外部链执行。 |
| 可用 / 预占 | 一份可花权益与为提现占住的权益。 | 100 变为 70＋30 只是分类变化，不是已扣掉总债权 30。 |
| 审批载荷 / 状态版本 | 批准的完整内容与本次合法状态代次。 | 换 B 或改金额不能复用旧审批，取消和执行竞争同一版本。 |
| SIGNING / 执行资格 | 允许开始生成付款签名的阶段。 | 先进入这一阶段后，就不能因队列空或 hash 空直接退款。 |
| nonce 双向约束 | 既不让两笔业务抢同一序号，也不让一笔业务占两个付款序号。 | 按链和发送者管理，W1 不得在 n 与 n+1 各付一次。 |
| rawTx / 签名未知 | 已签名字节，以及签名服务是否成功尚不清楚。 | 超时查询原签名请求；没保存 hash 不证明签名从未产生。 |
| 同 nonce 替换 / 取消 | 多个候选争同一个链上执行位置。 | 加速保留付款内容；取消另授权，原付款仍可能先胜出。 |
| SETTLED / RELEASED | 已付款结清或已关闭付款资格后退回预占。 | 两种结果必须互斥，广播超时不属于可释放证据。 |
| 归集 / 流动性预算 | 搬动平台持币位置，并为待付任务留足资金。 | H 初始为零要等归集，多任务不能都承诺同一份钱包余额。 |
| 共同水位 / 恢复准入 | 按相同链与账进度核对，确认旧任务安全后再放新任务。 | 已付未结先补结账，证据矛盾暂停，不用重付来抹平差异。 |

## 把整篇文章压缩成一个故事

甲从外部钱包向平台分配的 D_A 转入 100 USDC。观察器先核对以太坊主网和白名单合约，再验证成功回执、真实转账和甲的地址归属。看见交易并不等于甲能花这笔钱；只有转移属于可信 finalized 历史，充提与账本才在同一数据库事务中记录充值、分录和余额。扫描重复送来证据，仍只认原充值业务，甲可用保持 100。

甲接着向外部地址 B 提现 30。系统建立 W1，把可用改为 70、预占改为 30，告诉甲“已受理”。审批只批准这份付款内容。热钱包 H 此时没有 USDC，平台先把 D_A 的 100 归集过去；这不是甲又充了一次，也不减少甲的总权益。平台另付 ETH gas，不从 B 应收的 30 中偷偷扣费。

流动性就绪后，执行器与取消请求竞争执行资格。执行器先进入 SIGNING，就必须保存原意图、发送者和 nonce，通过可信授权路径签名。即使工作者崩溃、签名调用或广播超时，接手者也恢复原请求、追踪所有候选，不能新分配一个付款序号。取消交易也只是在竞争原 nonce，尚未最终获胜前，不能把预占退给甲。

最终链证据证明 B 收到 30，账本才消费预占。若这时数据库故障，链上 H 已剩 70，账内仍可暂挂 30 预占；恢复程序补做原 W1 的结算，不能再转一次币。结账后甲为 70 可用、零预占，H 为 70。对账还要核对每笔收付而非只看总数；普通未最终重组撤观察，最终证据矛盾则停机核验，授权冲正保留历史。每个停留阶段都要能查到原意图和待办原因，不能只留一句失败。这是教学设计，不是已运行的故障测试。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖充值识别、最终确认、账本入账、提现预占、审批签名、广播追踪、付款结清和链账核对的端到端契约。重点不是罗列服务，而是解释“谁有权改变什么状态、越过哪条边界不能随意撤销”。扫链算法、签名系统、nonce 调度与对账细节由后续独立母题继续深入。

**共同前提：** 沿用总览的 Ethereum 主网 USDC 托管模型；甲从外部充值 100 USDC，再向外部地址 B 提现 30，平台承担 ETH gas。D_A 与 H 初始 USDC 均为零，平台先归集 D_A→H 的 100，再从 H 付款 30；最终甲可用 70、预占 0、H 持有 70。金额使用 6 位精度整数，不提前授信，不混用 AMM、跨链或合约自助提款模型。

## 第 1 层：从用户拿到地址，到提现真正完成

**面试官：** 用户充值 100 USDC，然后提现 30 USDC。请从头讲完整流程，说明系统架构以及每个阶段到底完成了什么，不要只列模块名称。

**面试者：** 在这个模型中，我会先把外部资产流和内部负债流分开，再通过稳定的充提意图把它们连起来。充值并不是“收到交易哈希就加余额”，提现也不是“发送交易后就扣款结束”。

充值时，平台返回明确的网络、USDC 合约、甲的固定充值地址 D_A 和到账规则。甲在外部钱包转入 100。链观察器扫描区块和日志，验证目标合约、地址归属、成功回执与实际转移，先记录“检测到”，不增加可用余额。等目标转移进入可信的 finalized 历史，再由充提与账本域在一个数据库事务里写入充值身份、分录、余额和 outbox。这个事务提交后，甲才有 100 可用。

提现时，API 接收绑定请求身份的“向 B 付 30 USDC”，通过鉴权、地址、限额等校验后，在同一本地事务里创建 W1，把甲可用从 100 减到 70、预占从 0 加到 30，并可靠记录待审批任务。此时只承诺已受理，甲的总债权仍是 100，没有付款，也没有消灭 30 的负债。

审批通过后还要看钱包流动性。本例 H 没有 USDC，所以先以独立归集意图 S1，把 D_A 的 100 转到 H。S1 最终确认只改变托管资产位置，不再给甲加 100，也不减少甲的债权。随后 W1 获取执行资格，分配受控 nonce、签名、保存已签名字节并广播。广播超时仍追踪原意图，不另付一笔。

只有在规范最终历史里验证 H→B 确实付出 30，才在本地事务里消费 W1 的预占、减少用户负债和平台对应资产、提交完成状态与回报事件。账务提交后甲是 70／0，H 是 70。最后按同一链截止点和账务应用进度核对，不能把页面变成“成功”当成链与账已经对齐。

```text
外部充值100
    → 链证据检测 → 最终性验证 → 幂等入账 → 甲可用100
    → 提现W1预占30 → 甲可用70、预占30
    → 独立归集100到H → 用户权益不变
    → W1审批、签名、广播 → 追踪原付款
    → 最终确认付出30 → 幂等消费预占 → 甲可用70、预占0
```

## 第 2 层：链上资产和用户余额究竟由谁说了算

**面试官：** 你刚才说，归集后链上位置变了但用户余额不变，提现预占后用户总债权也不变。那系统里到底有几个权威状态？为什么不直接查钱包余额作为用户余额？

**面试者：** 至少要区分链上资产事实、充提业务事实和账本权益事实。它们相关，但不能互相替代。

以太坊规范链决定哪个地址实际持有多少 USDC、哪笔交易执行过；平台账本决定甲有多少可用和预占；充提意图决定这次外部收付对应哪个用户、处在哪个阶段、什么证据允许结账。钱包执行域掌握 nonce、签名与发送尝试，但没有权力自行把用户余额改为零。

不能直接用 D_A 的余额作为甲余额，因为归集后 D_A 变成零，甲仍有 100 债权；不能用 H 的余额分配给某个用户，因为 H 通常汇集多名用户和平台资金。本例提现预占 30 时，100 的资产还在平台控制域内，只是负债内部从“可用 100”重分类为“可用 70＋预占 30”。

如果由我设计这套教学系统，充提意图与账本放在同一 PostgreSQL 本地事务里，而不是先拆成两个必须分布式协调的服务。充值状态与分录共同提交；提现请求、余额条件扣减、预占、分录和 outbox 共同提交。这减少“状态写成功但没占到钱”的故障窗口。模块边界可以先是代码职责边界，不必先变成网络边界。

但这个事务包不住链上执行和签名器，所以我不会宣称全链路有一个大事务。链观察器只交付证据，签名器只执行授权，账本只按合法业务动作记账。允许它们短暂不同步，前提是每个中间态都能定位到原意图，并且没有把不确定的付款当成可以退款的失败。

如果以后把账本拆成独立服务，就必须增加可查询、持久、幂等的预占凭据和关闭执行资格协议；这是明确改变架构，而不是在本题里靠一句“调用账本服务”跳过原子边界。

## 第 3 层：什么证据允许把充值变成可用余额

**面试官：** 按你划分的边界，链观察器只是交付证据。假设用户给了一个 txHash，节点查到 receipt.status=1，还有一条 Transfer，为什么还不能直接让账本加 100？

**面试者：** 因为这些信息还没有完整证明“正确资产在可接受的规范历史里，进入了属于甲的平台控制地址”。我会依次验证身份、实际转移和最终性。

第一，资产身份必须是 chainId=1 加白名单 USDC 合约，不能看 symbol。日志必须由认可的 USDC 代理地址发出，收款地址确实是当时绑定甲的 D_A，金额是 `100_000_000` 最小单位。receipt 要成功，日志与 receipt 要绑定同一交易和区块证据。用户提供的 txHash 只是查询线索，不能作为平台完整入金集合的来源，也不能证明这笔钱属于发起查询的人。

第二，要验证真实业务语义。一个交易可以包含多条 Transfer，不能只看总交易成功或截取任意一条；还要区分外部入金与平台内部资金搬运。例如 S1 转入 H 也有 Transfer，但这是平台地址之间调拨，不应该为甲再生成充值。地址登记簿和内部意图登记要参与分类，冲突则隔离处理。

第三，`status=1` 不提供最终性。我会固定一个可信节点认可的 finalized 检查点 `(height, hash)`，确认充值所在块属于它的规范祖先链，并核对该高度区块 hash、receipt.blockHash 和日志所在块一致。观察到的 head、交易被打包、满足本系统入账门槛是三个阶段；不能随手把“等几个块”当作所有 EVM 链统一的安全规则。

数据完整性还要靠连续扫链：保存处理水位与区块 hash，重复覆盖扫描窗口，发现断档就补齐。WebSocket 可以加速检测，但重连后不能直接从当前高度继续。如果 finalized 停滞或节点证据冲突，保持待确认，用户看到“等待确认”，而不是通过降低门槛补偿体验。

这里依赖的是认可 USDC 实现下的 Token 语义和可信链视图。不能把“用了 RPC”说成系统独立证明了共识；数据源独立性、节点健康与合约升级都需要单独监控。

## 第 4 层：同一笔充值重扫、重组后重现，会不会再加一次钱

**面试官：** 你要重复覆盖扫描窗口，也要保存区块 hash。那同一日志重复返回，以及交易重组后换一个块重新出现，怎样去重？直接对 txHash 建唯一索引行不行？

**面试者：** 不行。我要分开“一次上链观察”“充值业务身份”和“入账动作”，不能指望一个 txHash 同时解决三个问题。

观察记录可用 `(chainId, blockHash, txHash, logIndex)` 去重。同一交易里可能有多条转账，所以只用 txHash 会漏掉其他合法转移；同一高度也可能有不同分支，所以只存高度不够。重复扫描返回完全相同的观察时，取回原记录，不新建 depositId。

业务入账前还要通过唯一映射，把最终认可的观察固定到一个持久 depositId；账本以 `(depositId,CREDIT)` 作为业务动作键。创建映射、充值状态、分录和余额在一个事务中提交。崩溃在提交前，重试重新处理；崩溃在提交后但回执丢失，重试查到原映射和入账结果，不再加钱。唯一约束冲突必须校验金额、用户、资产等载荷一致，不能把不同内容静默当成成功。

重组需要单独解释：blockHash 会变，`logIndex` 是区块内全局日志位置，也可能变。去掉 blockHash 并不自动得到跨分支稳定身份。本基线不提前授信，未最终观察从旧分支移除时只标记 ORPHANED，不涉及用户分录；新分支重新发现转移后，重新核验，直到最终合格才建立入账身份。

若旧分支已经被系统接受为 finalized，就不能把新分支当成普通重扫继续建立第二个充值。处理新范围前必须核对已接受的 finalized 检查点；发现矛盾就熔断自动入账与相关出款、保留两套证据并核验。这里的保证来自“只对最终认可证据入账＋已接受检查点矛盾时停止”，不是发明了一个永远稳定的事件键。

如果产品改为提前授信，就要另设计跨分支观察与业务充值的匹配、反向分录和重新确认协议，不能只沿用这里的观察唯一键然后声称已经支持。

## 第 5 层：已入账的资产失效，能不能直接回滚余额

**面试官：** 你说已接受的 finalized 证据矛盾就停止自动处理。如果核验后发现确实少了 100，或者 USDC 合约规则发生变化，原充值已经入账了，直接撤销数据库事务不就行了吗？

**面试者：** 不能。原事务早已提交，用户也可能基于那笔权益做了其他操作；删除充值或直接把余额减 100，会抹掉历史，还可能违反可用余额非负的约束。故障恢复不是把已经发生的业务重新假装成没发生。

我会先区分原因：普通未最终重组在本基线里没有入账；所谓 finalized 矛盾可能是 RPC 错误、节点配置或链异常，要先核验，而不是自动冲正。合约暂停或地址冻结通常影响可转出性，不等于原收款从未发生；真正的余额销毁或资产损失才可能改变平台资产。不能用一个 `FAILED` 混淆这些事实。

如果独立核验确认原记账确实需要修正，就生成带原分录引用、原因和授权的追加分录，幂等处理同一个修复动作。若用户还有相应可限制权益，可以依规则限制并调整；若已经支用，缺口要进入应收、差额或平台损失等明示科目，不能把负债和风险一起删除。具体由谁承担、是否允许追偿，是产品、财务与风险规则，不由恢复脚本自行决定。

USDC 还要监控代理实现升级及生效区块，不能只看代理地址或它自身 code hash 不变就继续认定语义不变。未知实现先暂停解析、授信或出款，经核验发布新版本。即使 B 正常收到了 30，后来 B 被冻结，也不能倒推平台那笔提现从未付出；“收到 Token”和“未来永远可转出或赎回”不是同一承诺。

为保持主案例不变，后续仍按原充值合法且未损失的条件讨论。上面的资产损失只是一个独立异常变体，不把它叠加到甲继续提现 30 的正常数值里。

## 第 6 层：提现重复提交、并发申请与取消如何裁决

**面试官：** 回到合法充值后的 100 可用。甲申请提现 30，但 API 超时重试，同时又发起另一笔提现，之后还点了取消。怎样保证既不重复占资，也不在退款后仍然付款？

**面试者：** 我会把“请求去重”“共享余额竞争”和“取消与执行竞争”分别落在数据库约束上，不能只用一个 Redis 锁包住 API。

同一用户作用域的 requestId 只能对应一个提现意图；规范化载荷包含网络、资产、B、金额和费用规则版本。第一次请求在事务里创建 W1，条件扣减可用 30，增加 W1 预占 30，写分录和 outbox。若提交结果因超时未知，重试原键：已有相同载荷就返回原 W1，载荷不同就报冲突，不能新建第二笔。上下文取消只意味着客户端停止等待，不等于数据库事务一定未提交。

另一笔不同 requestId 竞争的是同一用户资产余额，用行锁或 `available>=amount` 的条件更新裁决。独立变体中，两笔分别要提 30 和 80，最多一笔能占到钱；若 30 先提交，80 看到只剩 70就失败。不能让两个事务都先读到 100，再各自异步扣款。这里没有要求主案例实际发起第二笔。

取消则要与付款执行资格争同一个 W1 状态版本。审批通过只代表内容获得授权，还不能任意签名；本例先等待 H 流动性到位，再用条件更新把 APPROVED 改成 SIGNING。取消若先在 RESERVED／APPROVED 原子关闭意图，就在同一事务释放预占，后续执行器即使拿到旧消息也过不了状态条件。执行器若先赢得 SIGNING，取消就不能直接解冻。

审批也必须绑定金额、B、资产和意图版本，改收款地址不能继续沿用旧批准。进入 SIGNING 前，状态提交与授权路径必须保证只有合法的当前意图能分配付款 nonce、请求签名；不能把“队列暂时没任务”当成尚无执行资格的证明。过期或超时只触发核查，不越过这条状态边界自动退款。

## 第 7 层：SIGNING 后崩溃，数据库租约能阻止第二次付款吗

**面试官：** 你把 SIGNING 当成取消不能直接释放的边界。如果 worker 获得资格后签名超时，租约到期由另一个 worker 接管；旧 worker 又恢复了，如何避免两次付款？

**面试者：** 首先，租约只能帮助调度，不能使已产生的以太坊签名失效。要从签名入口约束“同一业务最多有一个付款 nonce”，并承认旧签名可能已经存在。

在签名前，先持久化 W1、预占身份、付款轮次、sender=H、nonce=n、chainId、USDC 合约、完整 to/value/data、费用上限、授权版本和稳定签名 requestId。钱包范围的 `(chainId,sender,nonce)` 唯一约束防止两个意图占同一 nonce；意图侧的唯一付款绑定则防止 W1 被分配 n 和 n+1 两个独立付款 nonce。两条约束解决不同方向的问题，缺一条都可能出错。

实际交易层的 `to` 是 USDC 代理，`value=0`，data 编码 `transfer(B,30_000_000)`。签名器或可信授权网关必须核验这些字段与当前意图授权一致，不只接受“给我签一段字节”。所有热钱包、归集和人工操作都走同一发送管理路径；本模型没有绕过登记簿的备用私钥出款，也不启用 EOA 账户委托来改变执行语义。

签名服务按 requestId 支持查询或幂等恢复。超时后新 worker 查询原签名请求，恢复同一载荷和 nonce；即使无法确认原签名结果，也保留未知态，不解冻、不改成 n+1 重付。rawTx 与 hash 持久化后才交付广播器；正常恢复可以直接重播同一字节。

旧 worker 的新请求由签名授权入口的 epoch 和意图版本挡住，但它可能已经持有有效签名。数据库锁、状态改为 CANCELLED、切换 RPC 都撤不回这份签名。必须继续把它作为候选追踪，直到 nonce=n 在规范链中被最终消耗，或进入其他有充分证据的受控处置。

至于本例归集，S1 的发送者是 D_A，W1 的发送者是 H，各自管理 nonce；如果某钱包同时做调拨与提现，必须共享该钱包唯一的 nonce 管理器。不能因为业务类型不同，就在同一发送地址上各自从 RPC 读取 pending nonce 独立分配。

## 第 8 层：广播超时、替换和链上回滚，什么时候才允许释放

**面试官：** 假设 W1 已经签好，广播超时，两个节点都查不到。后来你又想加速或取消，这时怎样推进？哪些情况才真正能解除那 30 的预占？

**面试者：** 广播超时、两个节点暂时查不到和 mempool 消失，都不能证明原交易以后不会付款。我会保留 W1 与全部候选尝试，优先重播同一 rawTx，并查询原 hash、发送地址 nonce 的链上消耗与规范区块证据。

若费率太低，可以生成同一 H、同一 nonce、同一业务载荷的加速交易，只在授权费用范围内调整费用。txHash 可以变，但 withdrawalId、预占与付款 nonce 不变。标准 EOA 的同一个 nonce 在一条规范历史里只能被一笔交易消耗，因此这些候选不会在最终规范链中各付一次；这不是“去重表”带来的保证。所有 hash 都要保留，不能只追最新一个，因为旧交易仍可能先打包。

取消是不同授权：它试图用同 nonce 的明确不付款交易消耗执行位置。提交取消请求或节点接受替换都不够；只有取消交易进入最终规范历史，核实它确实没有目标付款，且签名入口强制保证 W1 没有其他 nonce 的付款授权，才可以关闭 W1并原子释放。原付款若抢先成功，取消就输，按付款结清。

另一种可释放证据是 nonce=n 的交易已经 finalized 且执行回滚，目标 Token 没有付出；该 nonce 的旧签名以后也不能再执行。此时关闭意图并释放，平台单独记已消耗的 ETH gas。本基线不自动为同一 W1换新 nonce 重付；若仍要付款，必须在明确终结旧义务后采用另行定义的重试业务流程，不能一边释放一边再签。

若只是 INCLUDED 后又重组，回到追踪，预占不变；若成功回执里找不到符合预期的 USDC 转移，则进入 REVIEW，不按“status=1”结清，更不能未经核验判为可退款。相反终态互斥：一笔 W1 不允许既消费又释放 30。

nonce=n 长期卡住还会阻塞 n+1 及后续交易。达到费用上限、H 的 ETH 不足或节点异常时，应背压该钱包并受控加速／取消或转人工，不把等待太久当成失败证据。多切几个 RPC 能改善观察，不会凭空撤销旧付款。

## 第 9 层：钱已最终付出，但内部结账失败了怎么办

**面试官：** 按你的规则，W1 在最终规范历史里确实付出了 30。可账本服务提交时超时，随后又收到了重复的“付款成功”和一条迟到的“取消完成”。这时怎样保证钱和账不出错？

**面试者：** 先把“最终付款事实”和“这次数据库调用结果”分开。付款事实已经成立，就只能继续结清原 W1，不能重发付款，也不能因为结账超时把预占退回。

应用付款结果时，我会在一个本地事务里锁定或按版本条件更新 W1，校验证据绑定它的发送者、付款 nonce、资产、B、整数金额和最终区块；写唯一的结算动作，消费预占 30，追加相应分录，把状态改成 SETTLED，记录已应用证据／结果版本并写 outbox。若数据库提交前失败，整个事务回滚，预占仍为 30，恢复时重试；若提交成功但响应丢失，重查原业务键和状态，返回同一个结算结果。

重复消息不再消费预占，因为业务动作键与终态条件同时生效。消费端处理结果、去重记录与本地状态也要共同提交，提交后才确认消息。只在内存里记“见过这个 eventId”不够，因为重启后会丢；只靠事件 ID 也不够，因为同一个业务结果可能经扫描补偿生成另一条消息。

迟到的取消消息不能用“时间更晚”或“版本号更大”覆盖 SETTLED。要核对它到底是取消申请、取消候选被 RPC 接收、未最终观察，还是声称同 nonce 的另一笔交易也最终确定。如果只是旧阶段消息，保留审计后拒绝非法迁移；如果证据真声称同 nonce 两个互斥结果都 finalized，这是链视图矛盾，要熔断核验，不做普通乱序覆盖。

在结账未完成期间，实际链上资产可能已经是 70，账面负债仍是可用 70＋预占 30。这个差异允许暂时存在，但必须有可追踪的“已最终付款、待应用”桥接项和处理期限。outbox 通知可以滞后，前端也可以显示“链上已确认、结账中”；只有 SETTLED 事务提交才对外承诺整个提现完成。通知失败不回滚链上付款，不触发第二次出金。

## 第 10 层：怎样证明整条链收敛，故障时又该停在哪里

**面试官：** 你允许链上与账本有暂态差异，还依赖多个恢复任务。那如何判断正常在途还是实际丢钱？如果 RPC、签名器和数据库轮流故障，恢复之后怎样证明可以继续出款？

**面试者：** 我会用共同截止点对账和明确的恢复准入条件，而不是只看任务队列清空或前端都显示成功。

先固定 finalized 区块 `(height,hash)`，验证已接受检查点一致性，再明确账务应用到哪些充值、出款和归集结果。对账既比较集合，也比较按资产的余额：每个合格外部入金是否有唯一充值分录，每个最终付款是否有 W1 和唯一结清，每个账面结清是否有付款证据，每个 S1 是否只改变托管资产位置。只对总余额可能漏掉一笔多记和一笔少记正好抵消的错误。

对主案例，账务都应用完成时，链上 D_A=0、H=70，用户负债为可用 70、预占 0。如果 H=70 但账面预占还挂 30，先找到待应用的 W1；如果找得到最终付款证据，重试原结算，不重付。如果账面已结清却找不到对应最终付款，要查证据与状态迁移，不允许直接重建一笔转账掩盖异常。ETH gas 与 USDC 分开核对，账平也不代表发行方风险、地址冻结和偿付能力都已解决。

故障期间按边界停：数据库不可用就不能可靠预占和发放新签名授权；签名器不可用则停新签名，保留原预占，继续观察已签名付款；RPC 分歧或 finalized 检查点异常时，暂停相关链自动授信与新出款，尽量保留采集和人工核验。恢复先处理签名未知、发送未知、最低未解决 nonce、最终结果待应用和扫描缺口，再开放新任务。

Go 并发上用有界 worker、按发送钱包分片和可取消的 RPC 等待，防止积压变成无限 goroutine。用户余额由数据库裁决，钱包流动性也要扣除已经承诺但尚未最终支出的任务预算，不能让多名用户的提现都看见同一份 H 余额。扩展为多个钱包时，每个钱包仍有独立 nonce 与资金预算，不能把同一 W1 同时派给两个钱包来竞速。

我会用故障窗口验收方案：在预占提交后丢响应、签名返回前崩溃、广播后断网、包含后重组、最终付款后数据库失败、结清后重复消费等位置分别中断。每次都检查身份没有换、预占没有重复、未知态没被退款、有效付款最多一次、分录可以解释余额。这些是待实施的验证方法，不是本文已经跑过的故障测试。

## 本题收束

### 已讲透的机制

- **三种事实分开：** 链上执行与资产、充提意图与资格、账本权益与分录，各有权威边界。
- **两段本地原子性：** 受理时请求＋意图＋预占；确定结果应用时结清或释放＋分录＋状态；均连同 outbox 提交。
- **一条外部执行约束：** 签名入口把 W1 锁到唯一付款 nonce，同 nonce 的受控候选解决发送重试，不另起独立付款。
- **一套恢复纪律：** 未知不等于失败；恢复原义务，对齐链与账的水位，不通过重新付款或删除历史来“补偿”。

### 最容易答错的边界

1. txHash、成功回执、finalized、账务提交、页面完成不是同一个状态。
2. nonce 唯一只能防同一 nonce 分给两笔业务，还要反向约束一笔业务不能授权两个付款 nonce。
3. 数据库锁和授权 epoch 阻止的是新的非法操作，不能撤销已经产生的有效签名。
4. SETTLE 和 RELEASE 分别有幂等键仍不够，必须在同一个意图／预占状态上互斥裁决。
5. 归集不是用户充值；热钱包没有流动性不等于用户没有债权；用户债权与平台资产也不能跨进度直接强求相等。

### 一个检验方案的反例

```text
W1预占30 → 已签名并广播 → RPC超时
    → 系统按“查不到”把30退回可用
    → 旧交易稍后进入最终规范历史，实际付出30

此时：用户仍有可用100，平台只剩USDC70
```

如果方案允许这条路径，消息幂等、余额锁、双分录和对账再齐全，也没有阻止重复权益。成立的方案必须在“超时→释放”这一步挡住，保留原付款意图，直到得到确定付款结果或不会再付款的证据。
