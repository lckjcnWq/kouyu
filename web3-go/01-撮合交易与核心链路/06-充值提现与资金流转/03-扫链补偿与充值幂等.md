# 大问题 3：扫链怎样不漏账，重复扫描又怎样避免多入账？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文范围：讲 Ethereum 主网 USDC 的扫描覆盖、缺口补偿和重复入账防护。外部充值 100 只有在证据最终合格且账务事务提交后才可用；扫得快、扫到高处、收到消息都不能替代这两个条件。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 扫链器 / 观察 | 连续收集链数据，并保留当时看到了什么。 | 只交付证据和覆盖状态，没有给甲写余额的权限。 |
| 连续水位 | 从起点到某位置之间没有未解决缺口。 | 不是最大见过高度；20,000,000 只是原文的高度示例。 |
| blockHash / 父哈希 | 区分同高度的不同块，并检查相邻块连接。 | 只记高度会漏掉分支变化，恢复前先核对检查点。 |
| 区间 / 分片 | 把扫描范围切成边界明确的小任务。 | 后完成的高区间不能把总水位推过未完成的低区间。 |
| 重叠窗口 | 故意重复扫最近或故障相关的范围。 | 用重复换取恢复机会，重复观察不能增加第二份用户余额。 |
| 租约 / 幂等 | 租约减少双跑，幂等保证双跑也不重复生效。 | 工作者接管后允许重放，正确性仍靠持久约束。 |
| eth_getLogs / 过滤器 | 按区间及事件条件向节点要日志。 | 范围、资产策略和过滤条件要明确，HTTP 成功不等于资料完整。 |
| 空响应 / 截断 | 返回没内容，或只返回了实际内容的一部分。 | 可疑区间拆分复核，不能吞掉超时或限流后推进水位。 |
| receipt 绑定 | 确认日志来自对应块里成功执行的交易。 | 回执、交易和块 hash 对不上时保持待补。 |
| 证据持久化 / 完成标记 | 数据保存与“这段已扫全”的记录必须相互对应。 | 简单方案同事务提交，分批方案需全部分片完成后推进。 |
| 观察键 | 一条分支日志的持久定位组合。 | 包含链、块 hash、交易 hash、logIndex，不能只用 txHash。 |
| finalized / depositId | 最终历史资格和合格充值的业务编号。 | 未最终分支只撤观察，最终检查点矛盾暂停而非第二次授信。 |
| CREDIT / 载荷校验 | 唯一充值记账动作，还要核对内容相同。 | 同身份改用户或金额不是正常重试，唯一键冲突不能一概吞掉。 |
| outbox / 账务水位 | 待发结果与账务已应用的进度。 | 账务可落后扫描，但必须能找出哪些证据尚待应用。 |

## 把整篇文章压缩成一个故事

甲向 D_A 转了 100 USDC，平台的两个扫描工作者分别领取低区间和高区间。高区间先完成，但低区间遇到节点限流。调度器不能因为已经看见更高块号，就宣布之前全部扫完；它把失败范围留成缺口，连续水位停在缺口之前。甲的页面可以显示等待检测或确认，不能为了追赶进度跳过这一段。

恢复任务缩小范围重试，并核对过滤条件、块 hash、父块连接和日志回执。某次请求返回空数组，系统先检查它是否确实完成、是否受供应商截断或数据能力限制，而不是把“未知”当成“这里没有充值”。重叠窗口再次返回甲的日志时，按分支观察键取得原记录。一笔交易里的其他日志仍各自保留，不因共用 txHash 被覆盖。

工作者取得完整证据后，把数据与区间完成状态可靠关联，再推进连续水位。若保存过程中崩溃，原范围可以重做；若提交成功但响应丢失，重试核对原记录即可。这一步仍没有给甲加钱：还要验证主网白名单 USDC、D_A 归属及可信 finalized 历史。旧分支未最终就消失，只撤销观察；已接受最终检查点冲突，则停止自动授信核验。

最终合格观察映射到同一个 depositId，数据库一次提交 CREDIT、分录、甲的 100 可用和 outbox。两个消费者竞争，也只能有一次余额效果；相同身份换金额必须报冲突。以后平台把这 100 归集到 H，甲的债权仍不变。扫描水位说明资料覆盖，账务水位说明钱是否已记，两者分别核对才能发现漏应用；本文描述的是恢复规则和验证建议，不是实测结果。

**流程位置与核心机制：** 本题从区块与日志采集开始，覆盖扫描范围、水位、完整性、补偿重扫、证据持久化和最终入账应用。扫链的职责是稳定交付可核验、可重放的观察，而不是直接改用户余额；正确性来自可证明的覆盖范围、可发现的缺口、receipt／日志绑定、持久化边界和 depositId／CREDIT 双层去重。RPC 空响应不自动证明没有日志，扫描水位也不能只用一个“已处理最大高度”代表完整。

**必要前提：** 沿用[专题总览](README.md)基线：Ethereum 主网 `chainId=1`，原生 USDC 代理、6 位精度，`D_A` 固定归甲；外部 `E` 转入 100 USDC，合格证据 finalized 后甲账为可用 100／预占 0。S1 将 D_A 的 100 独立归集到 H，用户负债不变；提现 W1 最终向控制域外的 B 付 30，ETH gas 由平台承担。金额只用最小单位整数，充提意图、账本、分录和 outbox 在同一 PostgreSQL 本地事务提交；本题不改变最终性门槛。

## 第 1 层：扫链器的职责边界是什么

**面试官：** 扫链服务持续从 Ethereum 取区块和 Transfer 日志。它是否应该在看到 D_A 收款时直接给甲加余额？

**面试者：** 不应该。扫链器负责把链数据转成可追溯的观察，并声明自己覆盖了哪些区块、哪些范围仍有缺口；它不负责授予用户权益。一个合格分工是扫描器保存区块头、receipt／日志原始证据或可复核引用、规范性状态、扫描范围与水位，识别服务再按资产、地址和最终性策略判断是否为充值，账本仅消费确定的业务结果。

如果观察器直接更新余额，扫描重启、RPC 重复返回和分支变化就会把链采集的暂态直接变成账务副作用，难以审计和撤回。当前 head 的日志只能是候选，不能因为消费者收到了消息就成为信用。对外部 E→D_A 的 100，采集成功后只是“检测到”；finalized 证据校验完成，且 depositId 的 CREDIT 本地事务提交后才成为甲的可用 100。要实现这个边界，首先需定义水位究竟代表什么，而不是把最高块号当作全部进度。

## 第 2 层：水位怎样表示扫描完整性

**面试官：** 服务保存 `lastScannedBlock=20,000,000`，重启后从下一个区块继续。这样能证明此前都扫全了吗？

**面试者：** 不能。一个最大高度只表示某种处理曾推进到那里，不证明中间每个区块和所有分页日志都完整落库，也不证明区块哈希仍属于当前链视图。水位要表达“连续完整覆盖到哪里”，并与该高度的 blockHash、父哈希关系、扫描配置和持久化状态绑定。对每个范围至少区分已请求、已完整接收、证据已持久化、业务已应用等进度，避免把 RPC 返回或任务完成误写成账务完成。

扫描水位应按网络、资产策略和分片范围分别维护，记录起止区间及结果摘要；区块头连续性用于发现缺失父块或错误分支。处理新区间时先核对已有检查点，若旧 hash 不一致则进入分支恢复，而不是继续从高度最大值盲目向前。链观察水位和账务应用水位也不能混为一谈：前者说明证据覆盖位置，后者说明哪些最终合格事件已在数据库入账。接下来要解决重叠扫描和并行分片的竞态。

## 第 3 层：重叠扫描与分片怎样避免漏区间

**面试官：** 为了抗重启，你建议扫描窗口重叠；为提高吞吐又把区块切片并行处理。怎样避免窗口边界留下空洞或多个 worker 覆盖进度？

**面试者：** 我会把扫描工作定义成明确的闭区间或半开区间，持久记录每个区间的起止和完成状态，再让区间本身可重试。重叠窗口只增加重复观察，不应跳过高度；观察存储用区块哈希、交易哈希和 logIndex 等观察身份去重。同一区间被两个 worker 领取时，可用数据库租约或任务状态减少重复工作，但租约失效后仍允许重放，因此正确性必须由持久唯一约束和幂等提交保证，而不是只靠锁。

分片要覆盖所有目标高度且边界明确，例如前一片结束高度与后一片开始高度没有交叉遗漏；动态扩缩分片时保留旧分片完成记录和配置版本，不能只更新全局最大值。不同 worker 对同一高度返回不同 blockHash 时，不能任选其一，应核查分支和数据源。窗口重叠、日志重复或 worker 双跑都应能得到同一观察和同一业务映射。扫描并行解决吞吐，不改变最终性，也不允许其中一个分片推进总水位越过另一个未完成分片。

## 第 4 层：RPC 空响应和数据截断如何处理

**面试官：** `eth_getLogs` 返回空数组，或 RPC 返回 HTTP 成功，是否就能把该区间标记为没有充值？

**面试者：** 不能把任意空响应当作“证明无日志”。请求可能超范围、超时后被包装成空结果、节点数据裁剪、提供商限流，或响应受到日志数量／字节上限截断；不同 RPC 对大区间的限制也可能不同。扫描器要校验调用是否成功完成、响应结构合法、范围与过滤器一致，并监控错误码、超时和数据源能力。可疑区间应拆小重试或换独立数据源核验，不能吞掉错误后推进水位。

对大区间可按有上限的块段请求，分页或分块时明确排序、去重与覆盖边界；若提供商有响应条数上限而没有可靠的截断标记，单个结果少于上限也不一定能证明完整。要结合区块范围、节点文档和独立核对策略确认完整性。持续限流时应退避并施加背压，避免并发重试放大故障；链观察延迟增加是可见的运行状态，不可用降低过滤条件或跳过区块来换表面进度。下一步需要确保取得的日志确实属于对应成功交易。

## 第 5 层：日志怎样与区块、交易和 receipt 绑定

**面试官：** `eth_getLogs` 返回了看似正确的 Transfer，是否可以只按日志字段直接识别充值，不再查 receipt？

**面试者：** 不能只凭孤立日志入账。解析器须确认日志由白名单 USDC 代理发出，topic 和 ABI 数据结构合法，`to=D_A`、金额为预期整数，并把日志的 blockNumber、blockHash、transactionHash、transactionIndex 与所在区块及交易 receipt 绑定。receipt 要成功，且所有引用属于同一规范候选块。这样可以发现供应商拼接、旧分支数据、索引错误或日志与交易身份不一致。

对目标交易的 receipt 查询失败或字段缺失时，观察保持待补，不把“未知”转成“不存在”或合格。receipt 的日志列表与 getLogs 结果若不一致，要保存双方原始返回、标记差异并按策略复核；不能用其中一个结果静默覆盖另一个。最终性判断仍由后续策略做，扫链阶段将证据和来源完整保存。代理升级或合约策略版本未知时也应暂缓自动解释。证据正确之后，关键问题是怎样先落库再推进扫描水位。

## 第 6 层：证据与水位的持久化边界

**面试官：** 如果先把区块数据写入数据库，再单独推进扫描游标，中间崩溃或提交结果未知，怎么恢复而不漏账？

**面试者：** 区块证据与“此区间已经完整持久化”的标记必须通过可恢复的提交协议关联。最简单的数据库路径是在同一个本地事务中写入区块／日志观察、区间完成记录和对应连续水位；事务失败就不能越过区间。若证据量大不得不分批落库，就先持久化每批及可验证的分片完成状态，最后只有在所有分片完整后，才推进连续水位。读者不能仅看到一个全局游标就推断原始证据一定在库中。

崩溃发生在提交前，恢复任务重做区间；提交成功但响应丢失，重试命中相同观察唯一键并验证内容一致。原始日志、区块引用、receipt 状态和来源应保留到满足审计与重放要求，不能只留解码后的“充值 100”结果。数据库事务只保护本地证据与游标，不能和 RPC 或链最终性原子提交。观察持久化后由业务校验器重复消费，outbox 或任务队列可以重复投递，业务消费必须幂等。接下来才讨论如何从完整观察产生唯一 depositId。

## 第 7 层：从最终合格观察到唯一 depositId

**面试官：** 某个扫描区间完整落库，里面发现 `Transfer(E,D_A,100_000_000)`。此时如何避免重扫、分支变化或重复消费制造第二笔充值？

**面试者：** 完整扫描只是覆盖证据，不等于入账授权。候选观察先按 `(chainId,blockHash,txHash,logIndex)` 区分并去重，随后检查目标合约、成功 receipt、D_A 固定归属、资产策略和最终性。只有目标转移进入受信任 finalized 检查点的规范祖先历史，系统才把合格观察唯一映射到一个 depositId。该映射持久保存用户、资产、整数金额、证据引用和策略版本；重组改变 blockHash 时，旧观察与新观察是不同分支记录，不可去掉分支信息强行合并。

建立业务身份后，账本以 `(depositId,CREDIT)` 去重。观察重扫会取得原 depositId，不新建另一笔用户权益；未最终分支撤销只更新观察状态，没有可冲正的用户 CREDIT。若已经接受的 finalized 检查点 hash 矛盾，暂停自动授信核验，绝不自动把另一个观察映射成第二个 CREDIT。这个约束依赖最终性策略与检查点一致性，不声称观察键本身能跨重组稳定。并发 worker 会在映射与事务处竞争，下一层说明完整闭环。

## 第 8 层：并发重试和账务应用怎样闭环

**面试官：** 两个 worker 同时处理同一最终观察，其中一个数据库提交后超时，另一个也准备入账。如何让最后余额和账务身份都只有一份？

**面试者：** PostgreSQL 事务内通过合格观察到 depositId 的唯一映射、`(depositId,CREDIT)` 分录唯一约束和载荷一致性校验共同裁决。一次本地事务里创建或取得 depositId，确认状态仍可入账，追加充值分录、更新甲的可用余额、标记已应用结果并写 outbox。竞争失败者读取赢家提交的同一结果；如果用户、资产或金额不一致，必须报告身份冲突而非吞掉唯一键错误。消息系统可以至少一次投递，不能把恰好一次消费当成前提。

如果事务提交前崩溃，余额、分录、状态和 outbox 一起回滚，扫描或业务任务按原观察重试；提交后响应丢失，按原 depositId 查询返回既有结果。到此外部 E 的 100 只使甲可用从 0 到 100。之后 W1 预占 30 令可用／预占为 70／30，S1 归集 100 至 H 不改用户负债，W1 最终向 B 付 30 并结账后为 70／0。链数据水位和账务应用水位应分别对账，不能用链扫描完成替代入账事务完成。

## 本题收束

### 机制闭环

- 扫描器交付区间完整、可重放的原始观察，不写用户余额。
- 水位表示连续且持久化的覆盖，不是最高看到的块号；区块 hash、区间状态和数据来源共同说明它的含义。
- 重叠窗口和分片任务允许重复执行，唯一观察身份与业务幂等负责收敛；RPC 限流、数据裁剪、截断及异常空响应不能推进完整水位。
- 日志与成功 receipt、区块 hash、交易身份绑定；finalized 规范证据才创建唯一 depositId。
- CREDIT、分录、余额、业务状态和 outbox 在 PostgreSQL 本地事务内提交；链数据与账务分别维护应用水位。

### 易错边界

1. `lastScannedBlock` 不证明中间区间或日志页完整。
2. 任意空数组不是“无入金”的密码学证明；错误响应、裁剪和截断都可能伪装成空。
3. 消费消息幂等不能补回未持久化的区块证据，扫描完成也不能替代最终性判断。
4. 观察键含 blockHash，属于分支事实；depositId 才是入账业务身份，CREDIT 事务负责唯一应用。

### 可证伪反例与验证方法

```text
让 RPC 对中间一个区块范围返回超时／限流，扫描器错误地将其折叠成
空数组并把连续水位推进过去。之后完整回查发现该范围含有合格入金，
则“水位代表完整覆盖”的设计已被证伪。
```

建议检查：注入区间失败、分页截断模拟、响应后崩溃、事务提交响应丢失及两个 worker 并发。预期缺口会阻断连续水位；补扫可复用原观察；最终同一 depositId 仅有一个 CREDIT。以上是验证方法，不是已经执行测试的声明。
