# 大问题 1：一笔订单怎样走完账户资金链路，账本架构怎样划权？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文范围说明：以同一账务数据库内、零手续费的 BTC/USDT 托管现货为背景，解释一笔订单经过哪些权威与提交边界；跨分片只讨论保证如何改变，不宣称已经实现或测试。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 三个提交事实 | 占款、确定成交、完成入账各有落盘时刻 | 不能统称一次“下单成功” |
| 状态所有权 | 每类问题只有指定系统有权裁决 | 撮合管成交，账户管资金，查询管展示 |
| 稳定身份链 | 把一次请求一路串到最终账务的编号关系 | buy-001、B1、R-B1、成交与 journal 相互可追溯 |
| 预留凭据绑定 | 占款证明只供指定意图使用 | 账户、方向、限价、数量与规则都不能随意换 |
| 逻辑单一写权 | 多实例可以写，但必须共守同一入口协议 | 订单服务和后台不能绕过账户域改钱 |
| 资产桶转移 | 从能花的格子挪到订单专用格子 | 预留不减少甲的同币种资产合计 |
| 成交义务 | 撮合确定以后必须履行的收付关系 | 账户还没入账，也不能当作交易不存在 |
| 线性化点 | 并发操作从何时算正式生效 | 本例以权威资金事务成功提交为准 |
| 提交未知 | 没收到回复，却不知道数据库是否已提交 | 沿用原身份查询或重试，不另起一笔扣款 |
| 关闭墓碑 | 持久记录某个意图今后不能再执行 | AbortIntent 在撮合顺序中创建，阻挡迟到 Place |
| 前序成交缺口 | 释放之前还有未取得或未入账的结果 | 撤单先到也不能越过缺口退款 |
| APPLIED | 账务已提交这批结果的证明 | 不只是消息到了，也不是页面已经刷新 |
| 一致恢复点 | 余额、分录、防重与进度恢复到匹配位置 | 不能拿旧余额搭配新游标重新开业务 |
| 跨分片义务 | 拆库后需要另行协调的应收应付 | 本地事务不再覆盖所有买卖方，不能照搬双边原子性 |

## 把整篇文章压缩成一个故事

甲提交 B1，想从已有的 20,000 USDT 中拿出一部分，限价买入 0.25 BTC。负责接单的系统不能自己改余额，而要向账户域申请占款。账户事务将 15,025 USDT 从甲的可用转入 R-B1，并把同一意图的待发任务保存好；甲剩下 4,975 USDT 可用。这时他问“成功了吗”，系统只能回答钱已占住，不能替尚未裁决的撮合系统承诺成交。

假设网络迟迟没有回报，甲又想放弃。一次查不到 B1 并不能证明它不会执行，因为原命令可能还在途中。系统必须把关闭意图送进撮合的同一权威顺序：若关闭在先，持久墓碑挡住迟到命令；若成交在先，就先保留成交义务。主案例中的两笔成交一旦确定，甲实际需付 15,015 USDT，不能再把整个 15,025 USDT 退回让他另花一次。

接着账户拿到完整结果，在同一数据库事务里给乙、丙记 USDT，给甲记 BTC，返还未支出的 10 USDT，同时保存预留变化、去重结果和消费位置。中途崩溃且未提交就整体回滚，提交后回执丢失则重试返回原结果。最终甲可用为 4,985 USDT 与 0.25 BTC。多个 Go 实例也必须遵守这套数据库锁与事务协议，单个进程的互斥锁保护不了别的实例。

若甲页面仍停在旧数，系统先比账户版本，不再执行资金命令；若账务从备份恢复，则一起找回分录、余额、预留和防重进度，并在相同截止点核对义务。再往后即使单库遇到瓶颈，也不能直接按用户拆库后仍声称双方同事务提交：跨库必须另建可恢复的结算协议。这个故事说明的是权责与恢复边界，不是已经完成故障实验的个人经历。

**贯穿案例：** 甲以 20,000 USDT 为期初可用，限价 60,100 买入 0.25 BTC，预留 15,025 USDT；先以 60,000 成交 0.10 BTC，再以 60,100 成交 0.15 BTC。最终支出 15,015 USDT，返还价差 10 USDT，甲有 4,985 USDT 与 0.25 BTC 可用。乙／丙的卖出 BTC 已预留。

## 第 1 层：先把业务完成讲清，而不是先报组件名

**面试官：** 用户提交这笔买单之后，资金到底怎样从“能花”变成“占住”，再变成买卖双方余额？如果由你设计，完整流程和系统架构是什么？

**面试者：** 我会把整条链拆成三个有不同承诺的事实：**账户已经预留、撮合已经确定结果、账户已经完成入账**。查询和推送再告诉用户看到了哪个阶段。不能把它们都叫“下单成功”。

第一步，接入层验证账户权限、交易对、限价、数量、精度和 `buy-001` 的请求身份。账户域接到预留命令，在本地事务中检查可用资金、建立与 B1 绑定的预留 R-B1，写一组从可用到订单预留的分录，并保存幂等结果和订单提交 outbox。提交后，甲可用从 20,000 变成 4,975 USDT，预留变成 15,025 USDT。此时只是资金占住，尚不能说撮合已经接纳。

第二步，提交器把同一 Place 意图可靠送到撮合域。撮合域拥有订单接纳、成交和撤单的裁决权，在权威命令顺序内处理 B1，确定两笔成交，并提交完整结果批次。这个边界之后，T1、T2 是需要履行的成交义务。即使账务消费者暂时没追上，也不能删除成交或把预留全部退回。

第三步，账户域收到完整批次，在一个账务事务里扣甲的 USDT 预留、给乙和丙入账，扣卖方 BTC 预留、给甲入账，再返还 10 USDT 价差。分录、余额、预留明细、去重结果和消费位置共同提交。甲最终变为 4,985 USDT、0.25 BTC 可用，B1 预留归零；丙仍有 0.05 BTC 支撑未成交卖单。

```text
用户订单 → 接入校验 → 账户预留事务 → 可恢复的订单提交
                                          ↓
                                  撮合裁决与结果提交
                                          ↓
                                  账户批次入账事务
                                          ↓
                              账务 APPLIED → 查询／回报追上
```

架构上的原则是：**订单状态由撮合域决定，资金状态由账户域决定，查询只做投影。** 账户域可以有多个 Go 实例，但余额修改必须经过同一套账务写入协议。拒绝可以发生在参数校验、余额检查或撮合接纳；提交结果未知时保留可查询的中间态，不能将 RPC 超时解释成资金已退或业务未执行。

## 第 2 层：有三个完成阶段，究竟怎样避免出现三个“资产真相”？

**面试官：** 你刚才区分了三个事实。那订单服务说全成、账户还显示预留、页面又显示旧余额时，到底听谁的？你会怎样落实状态所有权和关联字段？

**面试者：** 要按问题找权威，而不是给某个服务封一个包办一切的“最终真相”。问订单是否成交，看撮合域已提交的结果；问某笔资产是否可花，看账户域已提交的余额与预留；问页面为什么落后，看投影版本。三者可以暂时处于不同进度，但不能互相替代。

在本例中，B1 全成而 R-B1 仍有 15,025 USDT，不一定是错误：如果 T1、T2 的账务尚未应用，这些钱仍承担履约义务。此时不能把旧余额理解成“成交不存在”，也不能根据订单全成就把预留加回可用。

我会用一条稳定身份链关联它们：

```text
用户请求 buy-001
    → intent_id / order_id B1
    → reservation_id R-B1
    → 撮合结果 batch_id，内含 trade_id T1、T2
    → journal_id / 入账结果 APPLIED
    → account_version / 查询投影位置
```

订单载荷与预留凭据还要绑定账户、交易对、方向、限价、数量和规则版本。`reservation_id` 只说明哪笔预留，不能成为可任意复制、挪用的资金通行证。撮合域必须保证同一意图最多接纳一次，账户域必须保证这份预留只能被对应业务消耗或释放。

具体写权上，订单、风控和人工后台都不能直接更新余额表。它们提交带来源与理由的资金命令，账户写入层验证身份、权限、预留归属和不变量。数据库权限也限制分录与余额的写入口；否则代码里说“只有账本能改”，后台脚本却能绕开，架构边界仍然是假的。

这里“单一写入权威”是逻辑所有权，不要求单实例。反过来，只部署一个实例也不能自动保证正确：它仍可能先改余额、后写分录，中途崩溃。三个域通过身份和提交位置相互证明进度，而不是共享一张谁都能改的状态表。

## 第 3 层：你说分录和余额都由账户域管，怎样证明钱没有凭空增减？

**面试官：** 顺着你刚才的身份链，具体给出 B1 的余额、预留和分录。只检查“余额非负”够不够？那 10 USDT 又应记在哪里？

**面试者：** 不够。非负只能排除部分透支，不能证明对手方收到的钱有来源，也不能证明释放的是当前订单的钱。我会同时检查**同币种分录平衡、余额非负、预留归属与累计闭合**。

先预留：甲 USDT 可用减少 15,025，甲 USDT 订单预留增加 15,025。这是资产桶之间的转移，甲的 USDT 合计没有变化。预留明细是 `initial=15,025, spent=0, released=0, remaining=15,025`。

T1 成交 0.10 BTC，实际成本为 6,000 USDT。甲按限价为这部分数量预留了 `60,100 × 0.10 = 6,010 USDT`，所以其中 6,000 转给乙，10 转回甲可用。同时，乙预留的 0.10 BTC 转给甲可用。此时 B1 尚未结转的预留为 9,015 USDT，恰好覆盖剩余 0.15 BTC 的限价成本。

T2 则消耗甲 9,015 USDT 预留，给丙入账；丙的 0.15 BTC 预留转给甲。丙原来预留 0.20 BTC，剩余 0.05 BTC 继续支持 S2。

本例两笔成交在同一个结果批次、同一个账务事务中提交；上面的“先 T1 再 T2”是计算展开，不承诺外部能读到两者之间的中间余额。

```text
B1：15,025 = spent 15,015 + released 10 + remaining 0
S1：0.10   = spent 0.10   + released 0  + remaining 0 BTC
S2：0.20   = spent 0.15   + released 0  + remaining 0.05 BTC

USDT：4,985 + 6,000 + 9,015 = 20,000
BTC ：甲 0.25 + 丙剩余预留 0.05 = 0.30
```

分录层每次转移都有同资产的负数行与正数行，按 journal 和币种汇总为零。余额索引必须等于审核期初分录加后续已提交分录的累计结果；同一用户同币种的订单预留余额，还必须等于其 reservation 剩余量之和。只有总量对了而预留挂错订单，仍然可能释放错钱。

10 USDT 要有从甲预留到甲可用的两边分录，归入 R-B1 的 `released`，不能只给可用余额做一次 `+10`。金额实现沿用总览的整数单位和合法步长，中间乘法避免溢出；本例能精确整除。手续费为零，不能突然用“手续费抵消差额”解释不平的账。

## 第 4 层：公式成立，多个 Go 实例同时改钱时还成立吗？

**面试官：** 你已经定义了这些不变量。现在甲同时再发一笔下单申请，另一个实例正在给 B1 入账，还有后台在处理释放。你靠什么让这些约束在并发下仍成立？

**面试者：** 我不会先在 Go 里查余额、判断足够，再发一条不带保护的 UPDATE。判断与修改必须处于同一个数据库串行化边界；所有资金操作也必须遵守同一套锁与校验协议。

在当前单账务数据库模型中，我选择短事务加行锁。预留先按固定账户桶键顺序锁定相关余额，再按固定顺序锁定涉及的预留；批次入账先锁该结果流游标，再遵守同样的余额和预留锁顺序。所有路径不能一会儿“先预留后余额”、一会儿反过来。相关余额行需要预建，或通过唯一约束保护的建行协议创建，不能假装 `SELECT FOR UPDATE` 锁住了一个不存在的行。

以同一账户只有 20,000 USDT、两个意图各要预留 15,025 为独立并发反例：第一个事务锁行、检查并扣成 4,975 后提交，第二个拿到锁时必须读取新的已提交余额，因此因不足而拒绝；不能两边都拿最初的 20,000 通过。成交入账给甲返还 10 后，另一个请求可以在其后看到 4,985，但看不到“已退款、还没扣预留”的半边状态。

一次账务事务共同提交：

1. 幂等身份与载荷绑定。
2. 全部 journal／分录。
3. 权威余额与账户版本。
4. reservation 的消耗、释放和剩余量。
5. 相关结果流游标、处理结果及通知 outbox。

其中任何校验失败都回滚整个事务。资金变化的线性化点是这次成功提交，不是 Go 函数返回、channel 收到命令或某条分录执行成功。

Go 的 `sync.Mutex` 只保护同一进程，不能协调另一个实例；单 goroutine 也不自动提供持久化。我会用 `database/sql` 的同一个 `sql.Tx` 执行全部账务 SQL，任何语句出错都走回滚，不能事务中途误用 `db.ExecContext`。锁内不调用撮合 RPC，避免把远程等待变成长期资金锁。死锁或可重试事务错误做有界退避，重试整个事务且沿用原身份；超出上限交给可恢复任务，不无限占用 goroutine。

## 第 5 层：数据库提交了，Go 却收到超时，如何知道该不该再扣一次？

**面试官：** 你把提交当作线性化点。但 `Commit` 时连接断了，调用方没有看到成功。下一次重试怎样判断？如果同一个请求身份带来不同金额呢？

**面试者：** 调用方不知道不等于数据库没提交。连接中断或超时可能留下“已经提交、回复丢失”的窗口，所以我会返回可查询的未知／处理中状态，保留原业务身份，不能直接告诉上游“失败，请换个 ID 再试”。

资金命令用 `(source, business_id, operation_type)` 做持久唯一键，保存规范化载荷摘要和原结果，例如 journal 引用、预留身份与完成状态。预留的结果记录和预留分录在同一事务内；成交批次的结果记录也和本批全部资产变化共同提交。

重试时先竞争同一唯一键。如果前一次已提交，就核验载荷一致并返回原结果，不能继续执行扣款；如果前一次确已回滚，重试事务才有机会创建该键并首次入账。如果原事务仍未确定，新事务按唯一约束等待其结果，不能只因另一个连接暂时查不到记录就认定可以用新身份重做。

同一个 `buy-001` 原来是 0.25 BTC，重试却改成 0.30 BTC，即使仍有余额也必须报身份／载荷冲突。用户真要新建订单，应使用新意图；但先前未知意图仍需查询或关闭，不能靠换 ID 假装它不存在。摘要需要基于规范化字段，不直接哈希字段顺序不稳定的原始 JSON。

这里有不同的幂等范围：`buy-001` 防的是重复创建原下单意图，`reservation_id` 约束的是资金归属，撮合域的意图去重防重复接纳，`batch_id`／连续结果键防重复应用同一批次。若上游把同一经济事件换成全新的业务身份，单一批次防重识别不了；来源还必须保证稳定成交身份、唯一事件归属，账户域据此校验，不能把“有一个唯一索引”称为端到端恰好一次。

这些记录的有效期还要覆盖真实重试、消息重放和灾难恢复窗口。账务分录与关键业务身份长期可查；不能用一个十分钟 Redis 锁作为全部防重证据，过期后让旧批次再次扣款。

## 第 6 层：预留已成功、撮合却查不到订单，为什么还不能退款？

**面试官：** 你说未知结果要查原身份。现在 R-B1 确实存在，但撮合域查询返回“未找到 B1”，用户又等不及要放弃。一直占钱不合理，直接释放不行吗？

**面试者：** 不能仅凭这次“未找到”释放。查询只能说明当前可见范围里没有订单，不能排除原 Place 仍在网络、提交器 outbox 或撮合待处理队列中。退款后迟到命令若还能执行，就会出现同一份钱已经再次可用、又承担成交义务的双花窗口。

在这个模型中，我会把“放弃原下单意图”做成 `AbortIntent(B1)`，与 Place 进入同一撮合权威命令顺序；它的作用不是只查一次订单，而是**关闭这个意图今后的执行资格**。

```text
情况 A：AbortIntent 先被裁决
    → 撮合域提交 B1 已关闭墓碑
    → 之后迟到的 Place(B1) 必须拒绝
    → 账户处理关闭结果，才能释放未消耗预留

情况 B：Place 先被裁决
    → 已经确定的成交保留，不能由后来的 AbortIntent 撤销
    → AbortIntent 只关闭剩余执行资格
    → 账户先应用此前成交，再按关闭结果释放实际剩余量
```

若 Place 恰好就是主案例，一次已经撮合全成，情况 B 最终仍要履行 15,015 USDT 的支付义务，只返还原来的 10 USDT 价差，不能因为用户发了放弃请求就再退 15,025。

这个协议依赖两个约束：第一，任何会让 B1 执行的入口都必须检查同一关闭事实，不能另有一条不查墓碑的快速下单通道；第二，账户域拿到关闭结果后，必须确认此前相关结果都已应用，不可越过成交缺口先退款。预留凭据的签名或哈希本身不会随时间自动失效，真正阻止迟到执行的是撮合域已提交的关闭裁决。

如果关闭请求也超时，就继续查询／重试原关闭命令，保持预留并告警。可以设置恢复时限、限制新风险、人工介入，但不能用年龄代替关闭证据。墓碑清理也必须有晚到命令的拒绝边界，例如旧请求代次不再被接纳；只因过了缓存 TTL 删除墓碑，会重新打开迟到执行窗口。

## 第 7 层：关闭资格并不等于钱都能退，部分成交时怎样算？

**面试官：** 沿着你刚才的情况 B，假设只成交了第一笔 0.10 BTC，然后撤掉剩余 0.15 BTC。可释放量是多少？如果撤单结果先送达账户域，你怎样防止先退钱再补扣？

**面试者：** 这是独立异常变体：只改变 B1 第二笔成交尚未发生，其他初始余额、限价和预留规则不变，不在主案例已全成的结果上再撤一次。

T1 实际花 6,000 USDT，释放该部分限价价差 10，留下 `60,100 × 0.15 = 9,015 USDT` 预留。撮合域随后确定撤销剩余 0.15 BTC，账户才将这 9,015 从 R-B1 转回甲可用。最终 B1 的预留闭合为：

```text
initial 15,025 = spent 6,000 + released 9,025 + remaining 0
released 9,025 = T1 价差 10 + 撤单剩余 9,015

甲最终：14,000 USDT 可用、0.10 BTC 可用、B1 预留 0
甲在本变体的 USDT 支出：20,000 - 14,000 = 6,000
```

这里不能用“原预留减累计实际花费”在任意时刻退款，因为还未撤销的剩余订单同样需要资金支持；必须先有关闭执行资格的事实，再算释放。

对乱序交付，本模型用撮合结果流的连续逻辑序号。假设游标为 41，T1 在批次 42，撤单在批次 43。即使 43 先抵达，账户消费者也不能先推进到 43：先保留或可重取该批次，向可靠结果源补齐 42。42 入账与游标更新共同提交后，再处理 43，原预留已经反映 T1 的消耗和价差，此时只能释放 9,015。

账户域检查完整批次和预留明细，不根据页面上的“已撤单”状态退款。重复收到 42 或 43 返回原应用结果；发现同序号不同内容则停流告警，不能任选一个入账。为了简单，基线按结果流严格顺序处理，代价是缺口可能阻塞该流后续账户更新；生产若改为更细的订单依赖或账户序列，必须重新证明不会绕过前置成交，不能只说“为了吞吐并行消费”。

同一账户在其他交易对的命令也可能并发，但资金竞争仍由第 4 层的数据库余额约束协调。每条流有序，不等于不同流天然没有共享余额竞争。

## 第 8 层：顺序对了，半边入账或消费者崩溃又怎样收敛？

**面试官：** 你刚才要求先应用成交再释放。回到主案例，消费者拿到了含 T1、T2 的完整批次，给乙写完 USDT 后崩溃；另一次又在提交成功但消息确认前崩溃。分别会留下什么？

**面试者：** 先区分“SQL 已执行”和“事务已提交”。当前基线中，T1、T2 的双币种分录、价差、预留和消费位置处于一个账务事务，不能给乙那一步单独提交。

如果给乙的那条更新执行完、但事务提交前进程崩溃，数据库会按事务恢复语义撤销整个未提交事务；甲扣款、乙入账、甲拿 BTC、R-B1 更新和消费进度都不应单独留下。重放原批次仍是第一次有效入账。这是依赖数据库事务能力的设计预期，不是我已经做过故障注入的结论。

如果数据库已经提交，但消息确认或回复丢了，则分录、余额、预留和游标都已经生效。消息源可以再次投递，消费者通过同一结果键核验并返回原 APPLIED，不能再走一次转账。消息确认晚了只导致重复，不应改变资金结果。

还有两种不允许出现的实现：一是先提交“已处理”记录，再去写余额，崩溃后会永久漏记；二是先改余额，再另开事务推进游标，崩溃后容易重复。即使采用 outbox，若它不与业务状态处于同一提交边界，也没有解决这两个窗口。

端到端恢复链路是：预留事务保留待发订单 outbox；撮合域持久保存权威结果及其身份；结果分发允许重复；账户只在入账事务提交后确认消费；账户通知也通过同事务 outbox 或可重读的已提交账务记录补发。每段都需要可恢复的来源，不能只依赖进程内 channel。

如果完整批次校验失败、预留不足或分录不平，我会整批回滚，保留原结果和未履约义务，隔离告警并定位原因。不会跳过该批次推进连续游标，也不会将订单改回未成交。必要时暂停受影响范围的新交易，但不能把其他用户已经确定的资产转移当作普通 RPC 补偿随意撤回。

用户回报上，订单可以是 `FILLED`、账务为 `PENDING`，等账户原子提交后变为 `APPLIED`。这个暂态需要可观测和恢复时限，不能无限挂着还宣称资金链路已经完成。

## 第 9 层：应用记录都在数据库里，恢复和对账还剩什么难点？

**面试官：** 你已经靠事务和幂等处理了消费者崩溃。现在账务库从备份恢复，查询库又落后，运营看到订单全成但账户预留没动。你怎样判断是正常延迟、漏记，还是恢复丢了已确认资金事实？

**面试者：** 我会先固定比较位置，再下结论。撮合域的最新结果和账户库的旧快照本来就不在同一水位，不能只看“订单全成＋预留未清”就补一笔退款或补扣。

对主案例，我会追踪这几个证据：B1 对应的 R-B1 是否存在；撮合批次身份和内容是否确定；该流账户 `last_applied_seq` 在哪里；对应 APPLIED 与 journal 是否存在；余额和预留是否与这些分录一致；查询投影追到了哪个账户版本。

如果撮合批次为 42、账户游标为 41、R-B1 仍为 15,025，这是尚未应用的义务；应补齐并重试 42。若账户已经提交 42，权威余额为 4,985 USDT／0.25 BTC，只有页面仍显示 4,975／0，则修复投影，不重记账。若游标声称已处理 42，却找不到相应分录和应用结果，则违反了共同提交假设，需要隔离调查，不能当作普通展示延迟。

恢复时必须恢复一致的账务快照：分录、余额、预留、幂等结果、游标、期初数据和 outbox 处于匹配恢复点，再按持久事务日志或保留的业务结果补齐。只恢复余额、保留一个更新的游标，会漏记；恢复旧余额却丢掉防重记录，则可能重记。只从撮合结果重放也不够，因为预留创建、原释放及其他资金命令未必都在撮合日志里。

如果备份恢复点早于某些已经向外确认的提交，是否还能恢复这些提交，取决于数据库 WAL、复制和恢复配置。当前方案要求保留已经确认的提交，但没有凭“主备”两个字证明零数据丢失。拿不到这部分持久事实时，不能直接恢复业务并声称资金正确；要限制写入、收集权威记录并明确差异，实际恢复能力需要演练验证。

对账也要分层：分录与余额、预留汇总与明细、撮合义务与应用结果，分别按同一截止点比对。内部账按币种转移平衡，并不证明平台链上托管资产充足；托管资产核对需要独立的链上确认口径、在途出入金和其他负债资料，本例没有提供这些事实，不能从 20,000 USDT 的内部算式推导出真实链上储备。

我会观测未应用批次数、序号缺口、最老预留年龄、提交未知任务、对账差异和投影延迟。超过可接受的恢复时限时，暂停或限速相关新风险；同一份预留保留多久，是恢复与风控问题，不是定时自动释放问题。修复通过重放原身份、重建投影或经审批的追加分录完成，禁止直接改余额让报表对齐。

## 第 10 层：如果单库成为瓶颈，能不能直接按用户分片？

**面试官：** 你上一答反复依赖“一致恢复点”和“本地事务”。如果单库吞吐不够，甲、乙、丙分到不同数据库，这条链还能保持原来的保证吗？你怎样选择并验证，而不是再加一个组件就算解决？

**面试者：** 不能保持原封不动。用户分片后，甲扣 USDT、乙／丙收款、卖方扣 BTC和甲收 BTC 不再是同一个本地事务。**幂等能防重复，不能让多个数据库共同提交；对账能发现差异，不能阻止收款方先花掉一笔尚未有可靠来源的钱。** 所以我不会把“按用户分库＋消息重试”说成原方案的无损扩容。

我会先量清当前瓶颈：是某个热点账户行锁、顺序游标、索引写放大、提交延迟，还是慢 SQL 与无界队列。优先缩短事务、批量应用、拆查询负载并建立背压；这些不改变同批资金转移的原子范围。不能未经测量就从单库跳到分布式账务。

若确实必须跨库，有两个方向：一是采用具备所需跨分片事务能力的存储，重新验证提交、恢复、锁冲突和延迟；二是明确改变结算模型，使用可恢复的分布式结算状态机。后者至少要固定 settlement 身份、参与方集合、各方准备记录、不可任意释放的预留和全局决策。

例如各分片先把应付资产锁入结算专用预留，目的端只记为不可支用的待结算权益；确认全部所需参与方准备就绪后，由可靠、受围栏保护的协调者持久化提交决定，各方依据同一决定幂等完成本地分录。需要中间清算账户时，每个本地账按币种保持平衡，清算应收／应付与未完成义务单独对账。目的端不能仅因收到第一条消息就把钱标成可花。

这里仍有真实代价：全局提交决定与各分片生效之间可能存在可见性差异；若要求严格同时可见，读取也必须受全局事务或等价协议约束。提交决定后某分片宕机只能继续恢复履约，不能用超时改成全局退款。各分片全部确认应用前，整体只能叫结算处理中，不能叫完成。我这里只说明跨分片会改变哪些保证，不把这段协议草图冒充已经实现的生产方案，详细设计属于后续母题。

验证时，我会保留主案例及一个独立的“只成交 0.10 BTC 后撤单”变体，在提交前后、重复投递、乱序、迟到 Place、协调者失联和参与方恢复处逐一构造反例：有没有一份钱既被释放又用于成交，有没有余额已入账却没有来源，有没有进度前进而分录缺失。Go race 检查只能覆盖进程内数据竞争，不能替代多实例数据库并发历史与故障实验；文档中的预期结果也不能写成实验已经通过。

因此本题的架构选择是：**当前教学规模保持同库账务原子性，把跨域未知态、重投和顺序协议讲清；只有在容量证据和产品完成语义明确之后，才改变事务边界。** 不为一个假想瓶颈提前引入无法解释的分布式保证。

## 本题收束

### 讲透了哪些机制

- 预留完成、撮合结果确定、账务完成与页面可见，是四种不同承诺。
- 撮合域拥有执行裁决，账户域拥有资产写入权，查询域不能决定扣款和释放。
- 资金正确性依赖同币种分录、余额、预留归属和业务身份共同闭合，不只是余额非负。
- 本地事务负责共同提交；唯一身份负责重试；可靠来源负责恢复；连续水位负责不越过成交先释放。四者不能互相替代。
- 超时释放必须先关闭原意图的执行资格；订单终态不等于成交义务已经完成入账。
- 恢复、对账和跨分片扩容都必须说明截止点、事实来源与原有保证是否改变。

### 最容易答错的边界

1. **“订单查不到，所以释放。”** 迟到 Place 仍可能执行，需要关闭资格的持久裁决。
2. **“订单全成，所以预留清零。”** 应先结转成交义务，只释放确定未消耗部分。
3. **“MQ 不重复，所以不会重复扣款。”** 真正防重必须与资产事务共同提交，并覆盖正确业务身份。
4. **“对账把余额改回来就行。”** 这会掩盖分录、预留或业务义务错误，修复必须有来源与审计。
5. **“以后按用户分片，事务照旧。”** 跨库后原本的买卖双方原子提交不再天然存在。

### 一个能检验架构是否成立的反例

```text
R-B1 预留成功，甲可用降到 4,975 USDT
    ↓
Place(B1) 在网络或待发任务中延迟，查询暂时未找到订单
    ↓
错误扫描器按超时把 15,025 全部释放，甲又可用 20,000
    ↓
甲将这笔钱用于另一个合法意图
    ↓
原 Place 迟到，仍能持旧凭据被接纳并成交
```

让应答者回答三个问题：**哪条持久记录阻止最后一步，哪个域能创建它，账户什么时候才允许退款？** 如果只能回答“加锁、重试、最终对账”，却说不出关闭裁决与迟到命令的共同顺序，这套资金架构还没有闭合。

主案例和部分成交撤单变体的算式可以手工核对；真正的数据库并发、提交未知和恢复行为仍需工程实验。本题不另外建立工程项目，唯一 MVP 见[专题总览](README.md#七工程实践一个简洁-mvp)。
