# 大问题 12：账本崩溃恢复、分片和热点扩容后怎样继续守恒？

## 先看懂：关键词大白话解释

本文范围说明：起点是多实例共享同一账务库的零费现货；独占领导权、跨库结算与分片迁移均为明确扩展，不把应用任期当数据库耐久性证明，也不声称已完成恢复或容量测试。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 恢复完成条件 | 不只服务启动，还能证明账务状态可继续使用 | 先查合法写入目标、共同状态和未完成义务 |
| 共同恢复集合 | 恢复时必须彼此匹配的一组持久对象 | 分录、余额、预留、幂等、游标与 outbox 不能各取新旧 |
| WAL | 数据库用于持久恢复事务的日志 | 能否找回已确认提交取决于实际配置与留存 |
| PITR | 利用备份和日志恢复到指定时间位置 | 恢复较早点不代表较新的对外承诺可以忽略 |
| RPO | 产品允许丢失到什么程度的恢复目标 | 要由持久化和复制能力支撑，不靠重试口号 |
| RTO | 产品期望多久恢复服务的目标 | 与资金事实完整性分开验证 |
| writer epoch | 某个独占写权作用域的任期号 | 不禁止基线多个实例按事务协议共同写同库 |
| fencing | 在实际提交入口挡住旧任期写者 | 仅换路由或等 Redis 租约过期并不充分 |
| 数据库旧主隔离 | 阻止旧数据库继续接受有效写入 | 两边各查本地旧 epoch 不能解决双主 |
| 热点锁等待 | 许多请求竞争同一余额行而排队 | 加 worker 未必提速，可能只增加冲突 |
| settlement_id | 跨库结算全过程的稳定身份 | 固定参与方、币种、数量及各腿应用结果 |
| prepared 资金 | 已准备履约、但还不能随意释放或支用的资产 | 协调者失联不能自动认定全局取消 |
| 持久全局决定 | 跨分片协议确定继续提交或合法终止的事实 | 已 commit 后故障只能恢复履约，不能超时翻案 |
| 迁移切点 | 旧权威停写后可核验的一致交接位置 | 复制余额之外，还要带身份、预留和未结任务 |
| routing epoch | 账户权威归属变更的版本 | 新库开写前旧库围栏先有效，旧客户端不能继续写 |
| 证据等级 | 区分设计算式、故障实验和性能测量 | 文档检查不等于恢复演练或容量验收 |

## 把整篇文章压缩成一个故事

账户进程在给甲的 B1 入账时退出，恢复程序首先确认自己连的是合法权威库，而不是拿内存缓存继续扣钱。若原事务未提交，整批资金变化都不应留下；若已提交但回执丢失，就按原身份返回 APPLIED。分录、余额、预留、幂等结果、游标与 outbox 要共同解释状态，数据库能连接只是开始，不能自动等同资金业务已经安全恢复。

若事故需要回到较早备份，恢复程序还得找回备份之后已经向用户确认的提交。只重放撮合成交不够，因为预留创建和修复命令未必在撮合日志中。它利用可用的持久日志与全部权威来源核对缺口，无法证明的部分先限制写入。若又发生主备切换，旧应用任期和旧数据库主节点都必须在真实写入入口被阻挡；单调任期号不能找回已经丢掉的分录，也不能单凭改路由阻止旧库继续接受写入。

业务恢复后，甲成为热点，系统先测锁等待、事务时间、连接池和积压，优先缩短事务与限制新风险。若最终确需把甲与卖方放进不同数据库，就承认原本双方同事务入账不再成立：先准备不可支用的结算权益，持久记录全局决定，再让各分片按同一身份完成。决定已经提交而某分片失联，只能继续恢复履约，不能靠超时退款；全部应用前对外仍是处理中。

后来迁移甲的账户，系统先围栏旧库、排空在途事务，按切点复制分录、余额、预留、身份和未完任务，核验后才开放新库。若新库已有提交，回退也不能直接丢弃新事实。最终验收分清算式一致、故障行为与容量证据：手工推演能解释甲的资产，却证明不了掉电耐久、旧主隔离或真实吞吐，未做的实验不能写成已经通过。

**流程位置与核心机制：** 本题从已经确定的业务账务出发，回答进程或数据库故障后如何恢复同一资产事实、怎样防止旧 writer 复活，以及在单库容量不足时如何改变分片边界而不把未知状态说成已结算。它聚焦恢复和容量条件，不代替[交易批次交付](08-成交交付顺序与原子入账.md)的完整消费协议或[多层对账](11-多层对账水位与差异修复.md)的差异处置。

**必要前提：** 链下托管 BTC/USDT 限价 GTC，同一 PostgreSQL 账务库，多 Go 实例，零手续费。甲以 20,000 USDT 下单并预留 15,025；T1 花 6,000 USDT 换得 0.10 BTC，T2 花 9,015 换得 0.15 BTC，返还价差 10。入账后甲可用 4,985 USDT 和 0.25 BTC；丙仍预留 0.05 BTC。已提交的资产变化不可因服务故障随意删除。跨数据库的原子性不属于本基线。

## 第 1 层：服务重启后，先恢复什么才敢继续接资金命令？

**面试官：** 账本进程突然崩溃又重启。你从哪里恢复？看到数据库连上了，是否可以直接接着消费成交批次？

**面试者：** 不能以“进程起来”作为恢复完成。我先确认权威账务库的数据状态、合法写入目标和已提交事务，再恢复命令处理位置和未完成工作。本基线允许多个 Go 实例同时连接同一 PostgreSQL 主库，依赖行锁与唯一约束协调，不要求所有账户命令都经一个应用 leader；只有采用主备消费者或分片独占领导权的扩展方案时，才需要额外核对该作用域的 writer 任期。账本进程内存不是资产事实来源；已提交分录、余额、预留、幂等结果、消费游标和 outbox 才共同描述可恢复状态。

若只是应用进程崩溃，而数据库仍正常并保留提交结果，启动时从数据库读取账户状态、结果流游标和 outbox 未投递项。数据库事务保证未提交的半笔变动回滚，已提交的变动保留。对账务批次重新投递时，账户端用原 `(stream_id, result_seq)` 与 batch 摘要返回原结果，不重复加减余额。

恢复步骤上，我会先禁止该实例接收新的资金写入，确认数据库角色、路由及服务权限；若该实例承担独占的结果流或分片领导权，再读取并校验该作用域持久化的 epoch／fencing 信息。加载必要索引或缓存后，对余额与分录的版本关系做启动检查，核对预留汇总、批次游标和未完成 outbox，之后才逐步开放写入。缓存可以重建，不能用旧缓存覆盖数据库。

如果启动检查发现游标指向的批次找不到结果、余额索引无法由分录解释、或 reservation 闭合不成立，就保持受影响账户或分区只读／限流并告警。不能为了恢复速度把不一致状态强行标记成健康。

在这条路径中，“数据库可连接”“服务健康检查通过”“账务可以安全接新命令”是不同阶段。恢复完成条件必须由持久状态核对与写入围栏共同定义。

## 第 2 层：崩溃发生在事务中间，哪些状态会留下？

**面试官：** 你刚才把多个状态列为共同恢复事实。以 T1/T2 账务事务为例，分别考虑写完乙的 USDT、写完甲的 BTC、提交前崩溃，以及提交后回复丢失，会留下什么？

**面试者：** 在同一 PostgreSQL 事务中，执行了一半的 SQL 不是已经生效的资金事实。假设 T1/T2 的分录、余额、R-B1/R-S1/R-S2、幂等结果、消费游标与通知 outbox 都在一个事务里，提交前进程或数据库会话崩溃，事务恢复后应整体不可见；重投原批次后可以从起点重算。

如果数据库已经提交，但 Go 进程在收到 `Commit` 回复前断线，调用方无法断言成功或失败。这是提交结果未知，不是可用新业务身份再做一次。重试沿用原键，查询或竞争数据库唯一约束，若原事务已提交则返回原 journal 与 APPLIED；若已回滚则首次应用。连接状态的不确定性由持久结果解决。

需要特别防止代码把“一个数据库事务”的表象打破。例如分录走 `tx.ExecContext`，余额却误走 `db.ExecContext`；或者先提交去重行，随后另开事务写资产。这些路径会制造有防重无资产或有资产无防重的崩溃窗口。所有必须共同成立的变化都经同一 `sql.Tx` 并检查每次错误。

恢复还要覆盖数据库自身的 WAL、检查点和存储耐久性设置。事务抽象提供逻辑原子性；是否能承受主机掉电、磁盘损坏和整区故障，取决于实际持久化、复制、备份和恢复策略。设计文档不能凭 PostgreSQL 事务四个字宣称所有介质故障都零丢失。

应用回执、消息确认与账户通知的投递可以在提交后丢失，只能造成重投或延迟；账务事务已提交但对应持久身份丢失则会导致重复风险。因此身份表和分录的保留策略至少覆盖所有可能的重放与恢复历史。

## 第 3 层：账本从备份恢复到较早时间，怎样避免旧数据覆盖新承诺？

**面试官：** 假设误操作后把数据库恢复到了一个较早的时间点，而恢复前已经对外确认了部分入账。你会直接重新开放写入，再等撮合重放把差额补齐吗？

**面试者：** 不会。先确定恢复点相对于已确认业务承诺的位置。账户库除了撮合成交，还保存预留创建、释放、人工调整以及充提等其他资产命令；单从撮合结果重放不能重建这些事实。恢复点早于已确认提交时，需要证明是否能通过 WAL/PITR 恢复到承诺边界，或从全部权威来源重建，不能假设只重放成交就够。

恢复前我会暂停受影响写入，保留事故现场与备份副本，记录恢复目标和所缺的时间范围；恢复后核对分录、权威余额、预留、命令幂等结果、消费游标和 outbox 的共同水位。若某些对外确认的业务事实确实无法找回，明确差异并限制资金操作，不能把较旧的余额静默当作当前余额。

对甲的 R-B1 而言，可能的恢复快照包括：预留事务尚未提交、预留已提交而 Place 尚未确定、成交批次已提交但账户未应用、或 T1/T2 已完整应用。每一种都有不同的资金义务。把所有快照都用“订单还在不在”归并会漏掉预留或重复成交通道。

只有在权威结果与账务状态重新对齐，且旧身份不会被重用后，才能解除写入限制。无法证明的数据缺口应走有审批、有来源的修复与后续复核；不应伪造原始业务分录使账面看起来连续。

恢复目标点（RPO）和服务恢复时间（RTO）要按产品承诺定义。若要求已向用户确认的账务绝不丢，复制与持久化配置必须能支撑该要求并演练验证；这不是一个应用层重试循环能补出来的性质。

## 第 4 层：旧主网络分区后复活，怎么保证只有一个账本写入者？

**面试官：** 单库恢复没有解决主备切换。旧主网络隔离一会儿后重新连上，仍认为自己是 leader，怎样防止两边同时为甲扣款？

**面试者：** 这里引入主备领导权扩展，所谓“唯一写入者”是同一领导权作用域只有一个合法任期，并非禁止基线中的多个 Go 服务实例并发写同库。关键是 fencing，而不只是选出新主。每次获得独占写权都分配单调增加的 epoch 或 token；受该领导权约束的数据库写入口在每次账务事务中验证当前 epoch，旧任期的 writer 一旦被新任期取代，就不能再提交有效变更。

若两个应用实例连接同一个 PostgreSQL 主库，可以把 writer lease/epoch 存在权威数据库中，并在短事务内校验锁定；新任期接管前完成旧任期隔离。不能只在 Redis 里租约到期就相信旧进程停止了，因为 GC 暂停、网络恢复和进程卡顿都可能让旧实例晚到。

若底层是主备数据库切换，须区分数据库复制的提交位置与应用 writer epoch。新主必须知道哪些提交已被确认，数据库高可用协议还要实际围栏旧主，例如撤销其写权限或存储访问、隔离旧节点，或让提交依赖旧主无法取得的有效仲裁。仅让新旧数据库各自校验本地 epoch，旧库仍可能读到旧任期并放行，因此只更新路由或复制一张 epoch 表不足以阻止双主。如果数据库副本落后于已经对外确认的提交，单调 epoch 本身也无法找回丢失分录；数据耐久边界需要独立满足。

撮合流的业务序号和账本 writer epoch 是两个不同维度。接管时，不能把流序号从 42 重置到 1 造成旧结果被当新批次，也不能因为新 writer epoch 变化就绕过原幂等键。序号描述业务连续性，epoch 描述写者任期。

验证要构造旧主暂停、租约过期、新主接管、旧主恢复并提交、数据库故障切换等时序，检查旧任期事务是否被数据库拒绝、已确认游标是否连续、同一 reservation 是否双重消耗。普通单实例单元测试证明不了双主隔离。

## 第 5 层：单库先出现热点账户锁等待，怎样判断容量瓶颈？

**面试官：** 写入权威已经明确，也排除了旧任期写入，但多个服务实例的账户写事务仍在排队，P99 上升。你会先怎么测量，哪些优化不会破坏资金原子性？

**面试者：** 先区分瓶颈是热点余额行、事务时间、索引写放大、连接池耗尽、结果流缺口，还是磁盘提交能力。只看 QPS 或平均延迟无法定位。用数据库锁等待、事务持续时间、deadlock/retry 数、连接池等待、每账户冲突分布、outbox 堆积和尾延迟共同判断。

保持单库事务范围不变的改进包括：缩短事务内工作，不在锁内调用 RPC；预先规范余额和 reservation 的锁排序；减少无用索引、避免重复读取；对同一批结果在一个事务中批量写分录；将通知由事务外同步调用改为同事务 outbox；查询读走可重建投影。每项优化都要确认不会改变防超支和共同提交约束。

高冲突账户上，乐观版本更新可能导致大量重试放大；简单增加 Go worker 会让同一行等待更激烈。按账户键分组、合并可安全合并的命令能降低冲突，但不能合并不同业务身份来丢失审计，也不能让提现和成交被不同队列不加协调地同时扣余额。

批量结算时要控制批大小与最大事务时间。批太小提高提交开销，批太大扩大锁持有和故障回滚范围。选择依据是实际数据和恢复目标，不在文档里虚构阈值。过载时对新风险命令实施有界队列和背压，优先保留撤销或降低风险的处理能力，但释放命令仍必须基于确定的关闭事实。

只有这些不改变跨账户本地原子性的办法仍达不到容量目标，且测量证明存在结构性瓶颈，才讨论账户分片。改变边界要重新写出新模型的资金义务与完成条件。

## 第 6 层：热点账户能否单独分片，用户之间的成交怎么办？

**面试官：** 假设甲是热点账户，乙、丙也可能分别在不同分片。用户分片后，主案例同时扣甲、收乙、收丙、扣卖方 BTC，还能保持一个本地账务事务吗？

**面试者：** 不能。按 owner 分片会让一笔成交跨多个库；原先一个 PostgreSQL 事务共同提交买卖双方两种资产的保证不再成立。给每个分片各加唯一键和重试，只保证局部不重复，不能保证所有参与方同时履约。

我会先评估替代的分区键。按资产分区能让同币种转移聚集，但 BTC 与 USDT 仍跨分区；按交易对分区能聚集成交，却与用户提款或其他交易对的余额竞争冲突；按账户分区查询自然，但跨账户转账会跨库。不存在不说明访问模式就通吃的分片键。

如果采用分布式结算状态机，先建立不可支用的清算应收／应付或专用预留，明确同一 `settlement_id` 的所有参与账户和币种；每个分片本地原子写入 prepare 事实并冻结可用余额，协调者持久提交决定后，各方依决定幂等完成。准备与完成之间资产处于在途，不能被用户花掉，也不能在协调者超时后自动反向释放。

提交决定后若丙的分片宕机，乙已收到的资产可能已不可撤回。全局义务只能继续恢复对丙的支付，或按事先定义的清算责任处理，不能假装全局 abort。全体应用之前对外返回 pending；如果产品要求强一致可见，就必须让读也遵守同一结算决定或使用具备所需跨分区事务能力的存储。

这个变化会影响资金可用性、系统可用性、完成延迟和故障恢复范围。不能因为“分布式事务不好用”就把处理中状态隐藏起来，继续宣称单库语义没变。

## 第 7 层：跨分片协调者失联或恢复，怎样防止旧决定覆盖新决定？

**面试官：** 你采用 prepare 和持久提交决定后，协调者在一部分分片完成时宕机。新协调者起来如何恢复？若两个协调者同时工作，分片凭什么判断谁的决定有效？

**面试者：** 每个结算参与方必须持久保存 `settlement_id、participants_hash、epoch、prepare状态、decision` 和应用回执。协调者只允许在某个被围栏保护的任期写决策；决策一旦持久提交就是不可逆事实，恢复器重读原记录继续应用，不能根据当前超时或参与方暂时不可达把 commit 改为 abort。

协调者任期需要由强一致存储或明确的租约与 fencing 协议授权。分片校验决策的 epoch 和参与方集合摘要，只接受有效任期写入；旧协调者恢复后提交旧命令应被拒绝。仅在进程里用 `sync.Mutex` 或本地文件保存当前 leader，无法约束其他实例和分片。

如果尚无决策而参与方处于 prepared 状态，系统可能暂时阻塞；需要预先定义恢复时限、人工升级和资源保护，但不能让租约过期自动释放已准备资金，因为协调者可能已经提交决策但应答尚未送达。只有协议证明全局未提交并安全地裁决 abort，才能释放。

去重不止按 settlement_id。相同 ID 携带不同参与者、数量或币种是冲突；每个参与方也要把 `settlement_id + leg_id` 与规范化载荷绑定。决策与分片本地账务事务分别有身份，重试必须返回各自原结果。

为了降低阻塞，可以减少跨分片交易、设置额度和清算缓冲、为热点账户采用预授权额度等，但这些都改变风险承受和用户可用余额定义，需要明确账务责任方。不能把恢复未及时这一运营问题通过超时释放变成双花。

## 第 8 层：过载时怎样保护资金正确性和必要的撤单能力？

**面试官：** 不论单库还是分片，队列已经积压，用户还在提交新单与撤单。你如何做过载保护，保证系统不因限流制造资金悬挂或越权释放？

**面试者：** 过载保护的目标是限制未完成义务继续增长，并让已经确定的资金事实仍能恢复。入口为新下单设置有界队列、并发预算和明确拒绝原因；在尚未预留前拒绝，最容易避免悬挂资金。若已预留，必须有可持久重试的 intent/outbox，不能因内存队列满了丢掉释放或撮合提交任务。

撤单不等于免费绕开顺序。撤单如果只是减少风险，可以提供受保护的处理容量，但它仍必须进入同一权威撮合顺序；账户释放只能等撤单裁决与前序成交批次可核对。高优先级只影响排队服务等级，不改变业务序号和资金约束。

对已经收到的成交批次，账户端保留可重取位置，处理滞后就限制新的账户义务或告警，不推进游标跳过缺口。消费速度低于输入速度时，通过反压或上游节流，不能让无界 Go channel 无限占内存。若 outbox、日志或存储空间接近容量上限，应在耗尽前降级接入，避免提交了资金却没有可恢复的交付记录。

用户接口需要区分“接入层拒绝”“预留已成功、撮合待处理”“订单已成交、账务待处理”和“账务已完成”。超时可返回可查询身份，不可以把未知转换成业务失败再鼓励换新 ID。

恢复后按持久游标继续，以稳定身份去重并测量积压年龄。对账不是过载时的实时安全闸，不能让它替代入口限流、执行资格与账户事务的事前约束。

## 第 9 层：容量扩展后，怎样避免分片迁移时双 writer？

**面试官：** 你确认需要将某账户从旧库迁到新分片。切换期间如何保证一份余额只归一个写者？旧库的迟到命令和备份恢复怎样处理？

**面试者：** 迁移要把一个账户的权威写权作为原子路由事实切换，而不是先让新旧两边都写，再靠最终对账选赢家。每个 `(owner, asset)` 或明确的账户聚合在任一 epoch 只有一个可提交的权威写者。

一种保守方案是短暂停写迁移：在权威路由中将账户标为迁移中，阻断该范围的新命令和结果应用；旧库写入口持久化停写围栏，排空已在途事务，记录最后提交切点。然后复制分录、余额、reservation、幂等身份、待处理 outbox 与账户版本，在同一切点核验，再原子发布更高 routing epoch 并开放新库。旧库的停写围栏必须先于新库开写生效，不能等旧客户端刷新路由。结果流游标可能横跨多个账户，不能复制一个市场游标就声称该账户迁移完成；必须暂停相关流并完成可核验交接，或使用已经证明正确的按账户依赖与跨分片结算协议。

如果短暂双读比较，双读只是影子验证，不是双写真相。切换失败回滚时，要判断新库是否已经接收资金命令；若有，就不能简单把路由退回旧快照丢弃这些提交。应冻结相关写入、迁移新库提交回旧库或继续向前恢复，并保留唯一业务身份。回滚是状态迁移，不是删除新事实。

切换消息迟到或旧客户端缓存路由时，数据库／写入网关必须强制校验当前 epoch，不能只依赖客户端自觉刷新。恢复备份也要带上路由版本和分片归属清单，否则旧备份启动后可能对已迁移账户重新接管写权。

验收不仅比较最终总余额，还比较每条分录、预留用途、待处理义务、幂等键、游标和新旧任期拒绝情况；迁移期间构造重复命令、旧主复活和新库提交后回滚请求。长期双写不是完成态。

## 第 10 层：你会用什么证据决定架构已恢复、容量方案可上线？

**面试官：** 最后请给出可以检验的验收条件。哪些结论能由设计与手工推演支持，哪些必须通过真实环境验证？

**面试者：** 我会分成语义、状态、故障和容量四组验收，并标记证据等级。

语义层要检查主例和部分成交撤单变体的资产守恒、每币种分录平衡、预留闭合、执行资格与释放顺序；同键重试不重复入账，缺批次不越过游标，关闭后的迟到 Place 不被接纳。这些可先用模型和手工案例推演，再把规则做成数据库历史测试。

恢复层要在事务前后、数据库提交回复丢失、主备切换、旧 writer 恢复、备份/PITR、结果重放与投影重建等窗口做故障注入，验证已确认提交可恢复或被显式隔离，未提交事务不会半边出现。演练需记录数据库版本、持久配置、复制延迟、恢复点和实际恢复时间；没有跑过就不能称为恢复验证通过。

容量层用代表性的账户热点和多资产访问模式压测并发事务、锁等待、deadlock、连接池、队列积压、磁盘提交延迟与尾延迟。容量结论必须来自实际环境与数据分布；单账户平均负载掩盖热点就不够。扩容后再验证跨分片结算可用性和阻塞代价。

文档设计、伪代码、静态链接与算式检查只支持“规则表述一致、示例计算正确”这一层，不证明数据库隔离、WAL耐久性、故障注入和性能目标已达成。投产门槛要将这些证据分别记录，不能把测试计划误报为测试结果。

若容量不足但跨分片实验尚未证明资金完成语义，不应该先开放无限流量再补对账。应限制风险增长，保留单一可解释的账务权威，并明确什么时候拒绝、处理中和恢复。

## 本题收束

- **讲透的机制：** 事务恢复、提交未知、PITR 一致性、writer fencing、单库热点测量、跨分片结算状态机、背压与迁移期单写者。
- **最容易答错的边界：** 数据库连接恢复不等于账务恢复；应用 epoch 不补回复制丢失；分片加唯一键不等于全局原子；对账不能预防双花；长事务和无限队列不是容量方案。
- **验证反例：** 旧 writer 暂停后新 writer 完成甲的成交扣款，旧 writer 恢复并用缓存余额提交一笔提现。如果新库／数据库没有拒绝旧 epoch，单写者约束就只是约定而非机制。

本题描述的是设计和验证方法，未执行数据库故障注入或性能测试。专题唯一 MVP 见[总览](README.md#七工程实践一个简洁-mvp)。
