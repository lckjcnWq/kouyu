# 大问题 3：余额与流水是什么关系，怎样建立可审计的复式业务账本？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文范围说明：解释同一 PostgreSQL 账务库中的现货业务资产子账，采用按币种记录的正负转移；正式财务借贷科目与托管储备证明需要额外资料，本文不代为补造。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 余额索引 | 把已提交历史累计成便于快速读取的当前数 | 同事务维护的权威索引，不是可随意覆盖的缓存 |
| journal | 将一次账务动作的全部明细装在一起的凭证 | 关联业务来源、操作类型与规则版本 |
| posting | 凭证里某个账户、币种、桶的具体增减行 | 同一转移有负数转出与正数转入 |
| 用户流水 | 为用户阅读而合并整理的业务说明 | 一行买入可对应多种资产分录，不能反向驱动扣款 |
| opening balance | 重算账本时经过审核的起点 | 来源不明时不能虚构平台权益来凑平 |
| 期初去重 | 避免快照覆盖的历史再次累计 | 用期初快照就只加其后分录，不再重复加 opening |
| 每币种平衡 | 同一凭证中同一资产的增减和为零 | BTC 与 USDT 各算各的，不能相互抵数 |
| 业务正确性 | 转移必须真的符合订单、成交与归属 | 价差给错人仍可平衡，故还要核对收付对象 |
| 余额物化 | 在保存历史时一并保存累计状态 | 分录、预留、余额及应用结果不能分开提交 |
| 只追加历史 | 已过账金额与方向不再原地改写 | 错误由引用原凭证的新冲正或补记说明 |
| 客户负债 | 从平台视角看欠用户的资产请求权 | 与平台控制的托管资产分开，不是同一个余额概念 |
| 财务总账映射 | 把业务变化接入正式借贷科目的规则 | 需科目表、会计政策与估值，不能只看正负数 |
| 同水位重算 | 从可信起点累计到同一已提交位置 | 先排除版本差异，再判断索引坏了还是历史缺失 |
| 索引重建与补记 | 修复派生状态和新增业务事实的不同动作 | 历史正确时重建索引；业务缺失才有据追加凭证 |

## 把整篇文章压缩成一个故事

甲在 B1 完成后看到可用 4,985 USDT，想知道这笔钱是怎么来的。账本不能只给他一个余额数，而要从经过审核的 20,000 USDT 期初开始，找到预留和成交的完整凭证。最初的 15,025 USDT 是从甲可用桶转到订单预留桶，同一币种一负一正，资产合计没变。页面可以把它写成一行“下单占款”，但底层必须保留具体账户、桶和业务身份。

接下来那份完整成交凭证解释，甲预留中有 6,000 USDT 付给乙、9,015 付给丙，卖方预留的 BTC 则分别交付给甲。尚未花掉的 10 USDT 要从甲预留扣除、向甲可用增加，不能只在余额上写一个加数。分录与余额索引、预留和消费结果共同提交，才能从同一截止点重算出当前状态；采用独立期初快照时，也不能再把其覆盖的期初分录加一遍。

现在假设检查发现，那 10 USDT 实际被记到了乙的可用桶。USDT 的正负合计依旧为零，整个平台的数量也未必变化，但甲没有收到自己的价差，业务仍然错误。系统必须拿原成交和预留归属核对收付对象，追加引用原凭证的纠错记录，不能删掉旧行让错误消失。若只是正确历史对应的余额索引损坏，则按共同水位重建索引，而不是虚构新交易来补差。

最后，甲还问内部账平衡能否证明平台钱包里有足额资产。答案不能从这本子账直接得出：用户请求权从平台角度属于负债，托管资产要另按链上确认与在途口径核对，正式总账也需要获批的科目映射。未知的期初来源应暴露为资料缺口，不能编一笔权益或收入来调平。本文提供可审计设计和手工推演，不是正式储备审计或已运行测试。

## 第 1 层：流水与余额分别回答什么问题？

**面试官：** 如果数据库已经有账户余额表，为什么还要存分录流水？用户问“我现在有多少”和审计问“这笔钱怎么来的”，能不能只保留一个答案？

**面试者：** 余额是高效读取当前状态的索引；分录是解释每次已提交业务变化的历史事实。余额回答“截至当前已应用位置可用多少”，分录回答“由哪些有身份、有来源的资产变化逐步形成”。两者不是可互相替代的冗余副本：只有分录，每次查询都要扫描长历史；只有余额，无法证明某次扣款的对手方、原因、预留和幂等身份。

我会将一项业务变化记为 `journal`，其下有一组不可变 `posting`。本业务子账的 posting 标识所有者、币种、桶和有符号数量变化。例如预留 15,025 USDT 是甲的 available `-15025` 与甲的 order_reserved `+15025`；它表示桶间转移，不改变甲的 USDT 合计。每个 journal 同一币种的 posting 合计为零。余额索引则与 journal 和 posting 在同一个数据库事务中更新。

余额必须可由可信期初状态和后续已提交 posting 重算：某 owner、asset、bucket 的余额，等于审核通过的 opening balance 加该桶所有后续 posting 的代数和。这个式子的起点不能捏造。若账簿从 20,000 USDT 开始，就必须有已审核的期初来源或明确的迁移快照与其审计凭证；如果对方科目、托管来源或历史无法证明，正确做法是标记历史缺口并调查，而不是编一个 `opening_equity` 让算式看起来漂亮。

这里还要区分通常页面所说的“流水”和不可变分录。页面上一行“成交买入”可能汇总同一交易的基础币入账、报价币支出和价差释放；一行“订单预留”也可能只是用户友好的说明。它们可以合并、分页或按业务分组，但底层仍应保存各币种、各桶的具体 posting。用户流水不能反过来作为账务写入来源；调整页面文案、改变分页方式或者重建投影，不应产生新的资金变化。审计查一行页面记录时，应能沿业务身份找到完整 journal，而不是依靠备注文字猜转移对象。

重算公式还要避免把期初计算两遍。如果审核期初已作为 opening 分录进入累计历史，就从零累计到目标水位；如果使用独立可信 opening 快照，就从该快照截止点之后累计，不再把被快照覆盖的历史重复相加。两种表达在可信来源和截止点一致时等价，但不能混合使用。这样“可重建”才是明确的输入范围和算法，不是一句对所有存量数据都成立的空泛承诺。

## 第 2 层：把这一组记录具体落到哪些表和身份？

**面试官：** 你区分了 journal、posting 和余额索引。数据库里需要哪些字段？如何保证一条业务事实不能被另一条看似相同的消息覆盖？

**面试者：** 我会让一个 journal 表达一次可原子提交的账务动作，posting 表达该动作里各账户桶的增减，余额表保存可查询的物化结果。journal 至少需要 `journal_id、source、business_id、operation_type、rule_version、created_at`；posting 至少需要 `journal_id、line_no、owner_id、asset_id、bucket、delta`。余额唯一键是 `(owner_id, asset_id, bucket)`，并有非负约束或由事务校验保证非负。posting 的 `(journal_id,line_no)` 唯一；journal 与来源身份应有稳定唯一键，例如 `(source,business_id,operation_type)`。

稳定身份的唯一性不能只靠消息系统的投递承诺。重复业务请求到达时，同一身份同一规范化载荷要返回先前结果；相同身份带来不同所有者、币种、金额或规则版本则冲突，不能覆盖历史。对 journal 的业务身份记录载荷摘要，保存 APPLIED 结果和关联账户版本。余额、分录、预留、幂等结果和消费游标在同一事务里提交，让“journal 存在但余额没变”或“余额变了却无 journal”不能成为已提交状态。

posting 一旦提交就只追加，不原地修改已过账行。显示名称、备注等可以存在外围资料，但不能修改分录的身份、方向、金额或业务来源。若业务错误，需要一笔引用原 journal 的冲正或补记，保留原记录和修正关系。账户域只能经统一账务命令写这些对象，订单服务、运维脚本、查询投影不能直接改余额表。

表结构约束要区分单行和跨行。币种、桶枚举、非零 delta、外键与唯一行号可以由普通约束表达；但一个 journal 的全部 posting 按币种为零，涉及多行，不能在每一行的 CHECK 中简单写个汇总查询就认为数据库已经保证。实现可由受控账务写入过程构造全部行并事务校验，必要时采用在提交边界执行的数据库级校验；关键是不能让其他入口绕过它。草稿凭证若存在，必须与已过账事实分开标识，未通过平衡校验的草稿不能更新权威余额或被 APPLIED 引用。

同样，一个完整成交批次可以在内部关联多个 journal，但批次的所有资金变化和结果必须共同提交；也可以采用一个批次 journal，将每笔 trade 的行组保留引用。这里选择后者来贴合主例，行上可附 trade_id、reservation_id 和分组号，使一条用户流水能定位对应金额。无论如何选择，唯一性作用域必须明确：一个批次不能拆半重试，一笔经济事件也不能换 journal 身份再记一次。完整性来自稳定身份与提交协议，不是 journal 数量越多越安全。

## 第 3 层：主案例的分录怎样同时反映预留、成交和价差？

**面试官：** 字段有了。请把甲的预留、T1、T2 展开成分录，说明为什么不能把 10 USDT 只加到可用余额。每种资产的账要怎样核对？

**面试者：** 我采用带符号的资产桶变化表达业务子账。以下每一行是一个转移对，负值转出、正值转入，不能分两次独立提交：

| 业务动作 | 币种 | posting A | posting B |
|---|---|---|---|
| B1 预留 | USDT | 甲 available `-15025` | 甲 order_reserved `+15025` |
| T1 支付 | USDT | 甲 order_reserved `-6000` | 乙 available `+6000` |
| T1 交付 | BTC | 乙 order_reserved `-0.10` | 甲 available `+0.10` |
| T1 价差释放 | USDT | 甲 order_reserved `-10` | 甲 available `+10` |
| T2 支付 | USDT | 甲 order_reserved `-9015` | 丙 available `+9015` |
| T2 交付 | BTC | 丙 order_reserved `-0.15` | 甲 available `+0.15` |

每一转移对必须属于同一币种并加总为零。USDT 按账户看，甲最后支出 15,015，乙收到 6,000、丙收到 9,015；甲自己把 10 从预留移回可用，没有创造新 USDT。BTC 上，乙预留 0.10 用于 T1，丙预留 0.15 用于 T2，剩余 0.05 仍为丙的 S2 预留，甲得到 0.25 可用。每个币种分别核对，不能把 BTC 数量和 USDT 数量相加成一个“全资产守恒值”。

甲的 R-B1 同时闭合为 `15025=spent 15015+released 10+remaining 0`；丙 S2 为 `0.20=spent 0.15+released 0+remaining 0.05 BTC`。若只给甲可用余额加 10，漏掉预留的 `-10`，该 journal 不平、甲余额索引也会与分录重算不一致；若只减少预留、不增加可用，则钱消失。必须把价差作为同一批次中的一对 posting，并更新 reservation 累计量。

主例成交结果在本模型中作为完整批次原子应用。表格的逐项展开用于解释，不意味着外部可以读到只处理完 T1、尚未处理 T2 的一半账户状态。

## 第 4 层：同币种分录平衡了，为什么仍不等于账做对了？

**面试官：** 你能检查每个 journal 按资产加总为零，也能检查余额非负。攻击者把甲的 10 USDT 释放给乙而不是甲，或把甲的余额多记一笔同时补一笔相反方向，平衡检查能发现吗？

**面试者：** 不能。`sum(delta)=0` 只说明这一组业务子账变动没有在该币种的汇总层面凭空增减，不能证明业务关系正确。要进一步校验 posting 所有者和桶是否来自原始命令、交易身份、reservation 归属和撮合成交事实；数量与价格是否在订单和交易规则范围内；买卖双方方向是否匹配；分录余额索引、预留明细和结果批次水位是否共同闭合。

例如把 T1 价差的接收方从甲 available 改成乙 available，USDT 总和仍是零，却把甲的钱错误送给乙。两个账户各自一笔相反错误也可能让全平台余额总和不变。甚至在同一账户借记不正确的桶、贷记另一个桶，`sum(delta)=0` 仍可能让资金用途和订单预留对不上。因此检查应有多个层次：格式与精度合法、journal 每币种平衡、余额不透支、预留归属和累计闭合、来源身份唯一且内容一致、同一业务批次完整、应用游标连续、余额与分录累计一致。

账本还要说明资产边界。内部用户子账相平，不证明链上托管地址有足够 BTC/USDT，也不证明公司没有其他用户负债。托管资产对账需要链上确认、归集钱包、在途充提、手续费和其他负债等口径；本例没有这些数据，不能把内部的 `20000 USDT` 直接当作链上储备证明。严格地说，业务资产子账回答“平台内部给谁记了多少资产请求权”，完整财务总账回答“平台的资产、负债、权益、收入与费用怎样按会计科目确认”；两者需有经过定义的映射。

## 第 5 层：余额表是副本还是权威？如何避免分录与余额分叉？

**面试官：** 你刚才要求余额索引、分录累计与预留同时一致。既然可从分录重算，那是不是不要余额表最安全？如果保留，怎样保证它不慢于分录，或者在不同事务里被独立更新？

**面试者：** 对高频账户裁决，我会保留同事务维护的权威余额索引；从逻辑上说，它是分录历史的物化状态，不是一条可以脱离分录任意修改的第二真相。权威写入事务同时追加 journal 和所有 posting，按固定顺序锁定涉及的余额行，基于事务内已提交余额检查约束，更新索引、账户版本、预留和幂等结果，然后提交。事务里的任何步骤失败都回滚全部变化。查询可以用只读投影或缓存，但扣款与预留判断不能用异步缓存。

一次账务更新可按如下顺序组织：校验来源身份和载荷；锁定结果流位置与相关余额键；锁预留明细；验证业务前态；构造该 journal 的全部 posting；计算每个账户桶的新余额并校验非负；插入 journal 与 posting；更新余额、reservation、消费游标和持久结果；提交。账户和币种排序必须一致，避免两个多账户事务相反顺序锁定造成死锁。多 Go 实例通过 PostgreSQL 锁与唯一约束协调，不靠本地 mutex。

一致性检查不能只看写事务自身。可以定期按水位重算抽样账户或分区的余额索引，比较 `opening + sum(posting)`；比较用户 order_reserved 与 reservation.remaining 汇总；检查已有 APPLIED 是否有完整 journal，journal 是否有确定来源。检查任务发现差异时冻结相关资金命令、保留证据并追查，不执行 `UPDATE balance=某个总和` 来掩盖错误。若因性能使用异步余额投影，必须明确它只是查询视图并显示版本，不能再称其为资金裁决权威。

## 第 6 层：重复入账、提交未知和重放时怎样只生效一次？

**面试官：** 同一 T1 批次可能被重投。先查 journal 不存在再写，是否足够？事务提交时连接断开，调用者不知道成功或失败，应怎样设计？

**面试者：** “先查再写”在并发下有竞态，两个实例都可能查不到，再分别插入。防重由数据库唯一约束和同一事务中的持久结果负责：它们竞争稳定的 `(source,business_id,operation_type)`，其中还绑定规范化载荷摘要。一个事务提交后，另一事务命中唯一键并读取原结果；若载荷不同，返回冲突。如果原事务回滚，重试才可能成为首次有效执行。不能在余额提交以后另开事务记录幂等键，也不能先标 APPLIED 再写分录。

提交回复丢失是未知结果，不等于失败。调用方沿用原业务身份查询或重试；若原事务已提交，就返回原 `journal_id`、账户版本和结果；若数据库尚未决出结果，新尝试需要按唯一约束等待或在事务确定后读取。不能为了“确保成功”换一个 business_id 重新扣款。消费游标若属于成交流，也必须与该批全部 posting 和 APPLIED 结果处于同一提交边界：只推进游标会漏记，只记分录不推进则会重放，所以两者必须一起提交。

当同一来源事件被错误地赋予两个新的业务身份时，数据库的唯一键看不出它们是同一经济事件。撮合域还需提供稳定 trade_id／batch_id，账户域验证其归属与序号；幂等记录保留期限覆盖重投和恢复窗口。重复投递可以安全，来源身份不稳定仍然不能保证只记一次。

## 第 7 层：题目说复式账本，你怎样区分业务双边转移和财务借贷？

**面试官：** 你刚才用原业务身份和 journal 保证重放不重复。即使这些 journal 都唯一、完整且一负一正，是否就能把它们直接当作完整财务凭证？会计也要借贷平衡，两者是不是同一件事？能否给一个期初借方把这本账补平？

**面试者：** 我会准确命名：上面的行是按用户所有者、资产和业务桶记录的**双边资产子账**。对每一币种、每一 journal 检查净变动为零，是该子账的基本约束；它不是完整的总账科目体系，也不自动代表会计上的借贷方向、确认时点、财务报表分类或功能货币金额。

如果总账采用客户资产请求权作为负债类科目，内部 USDT 交易从买方转到卖方，在总账层可能表现为借记买方客户负债、贷记卖方客户负债，平台托管资产总额不因用户间转移改变。可用和预留是否拆成负债子科目，要依据正式科目表和会计政策确认。这里仅说明可能的账户映射方式，不能在没有组织科目表与政策时声称这就是正式凭证。若收取平台费用，还要按确认规则将客户负债减少与平台费用收入等总账科目对应，不能把资产子账中的平台收款桶直接等同收入确认。

期初余额必须能追溯到经过审核的迁移快照、已批准期初凭证及对应的真实托管资产和负债资料。若只知道账户甲有 20,000 USDT，却不知道资金来源与总账对方科目，不能瞎造“现金”“平台权益”或“期初损益”凑平；应明确本教学数据仅从已审核期初状态开始，并把总账映射作为缺失输入。币种数量也不能跨单位相抵：BTC 子账平衡不代表可拿 USDT 行作为借方把 BTC 凭证补平。若财务总账以功能货币记账，还必须按批准汇率、重估时点和汇兑规则独立形成金额。

因此我会分层描述保证：业务资产子账保证所有者、币种、桶和业务事实对应；完整总账通过经批准的科目映射、借贷规则、估值与关账流程证明会计完整性。只验证前一层不能宣称后一层已经平衡。

分录接口还要区分“业务命令”和“已过账事实”。命令输入可以被校验并拒绝；一旦对应 journal 提交，行内容应视为不可变。数据库层可以只给账户写入角色授予 INSERT 权限，不授予 posting 的 UPDATE/DELETE；若保留管理修复通道，也应要求强审计身份、审批编号和原记录引用。时间戳本身不构成顺序证明：并发事务的 `created_at` 可能相近或回退，可靠顺序要依赖源业务序号、账户版本或数据库提交位置。账户版本可在每次成功资金事务中单调增加，供查询解释读到哪个状态，但它不能代替 journal 身份。

期初迁移尤其容易把余额索引当成事实。正确导入至少要冻结或定义切换水位，取得每个账户和资产的外部权威快照，记录来源文件／系统、生成时间、校验摘要、审批人、币种和单位；通过受审计的 opening journal 或受控迁移批次建立起点，再验证迁移前后账户总量及托管口径。若输入只有余额数字而缺少对方科目与资产来源，子账可以将其标成待核证的 opening state，但完整总账不得虚构借贷科目。更不能一边允许旧系统写入、一边不带共同水位地复制余额，否则迁移期间的业务可能漏入或重复。

重建时要能回答“从哪个可信起点、累计到哪个已提交位置”。可按账户或分区定期核对余额索引，不一定每次都扫描全部历史；检查结果应记录起止水位、posting 数量／摘要、差异清单和生成版本。若分区归档了旧 posting，也要保留可验证的封存摘要和恢复资料，保证归档不是不可审计的删除。缓存与只读查询库可以落后，但响应应携带 account_version 或投影水位；账户资金裁决始终读权威库，不用投影的旧余额覆盖写入。

## 第 8 层：发现历史不一致时怎样对账和修复而不破坏审计？

**面试官：** 账本能重算、也有持久身份。现在发现甲的余额索引是 4,985，但按 posting 算出 4,995，或总账有一笔差异。你会直接把余额改回去，还是补一条分录？怎样确定要修哪边？

**面试者：** 先固定同一个业务截止点和恢复位置，分别核对来源结果、APPLIED、journal、posting、reservation、余额索引和总账映射。4,985 与 4,995 的差异可能来自余额索引更新错误、漏记一条分录、期初快照不一致、重复事件、或查询读到不同版本；在识别根因前直接补 10 会制造第二个来源不明的事实。对成交应核对 T1/T2 身份、金额与账户结果序号；对主例还要验证 R-B1 `15025=15015+10+0`、乙丙收款、BTC 交付和 S2 剩余 0.05。

如果 posting 是完整正确而物化余额损坏，可以从可信期初和已提交 posting 重建索引，并记录修复任务、输入水位、操作者和重建版本；历史凭证不改。如果业务事实有误或少了一笔，则通过受审批的冲正／补记 journal 引用原事件及差异原因，追加正确的双边 posting；不能删除旧行。总账与子账差异还需通过已批准映射逐项定位，不能用一个不明“调整科目”吸收。

恢复也要协调分录、余额索引、预留、幂等结果、游标和 outbox 的一致快照。只恢复余额而恢复较新的游标会漏记；只恢复旧余额却保留较新的幂等结果会阻止必要重放。若数据库恢复点丢失已经对外确认的提交，需按 WAL、复制与留存的业务事实识别损失范围，不能仅凭“数据库已启动”宣布账本正确。账户写入层在差异解决前可隔离受影响账户或资产，阻止风险继续扩大。

### 本题收束

**讲透的机制：** journal/posting 记录不可变业务历史，余额索引在同一事务维护；每笔业务子账按币种平衡并可由可信期初重算；稳定身份、完整批次和结果游标共同防止漏记与重复；修复追加且有依据。

**最容易答错的边界：** 用户资产双边转移不等于完整财务总账借贷；分录和为零不证明所有者与来源正确；内部账本平衡不证明托管资产充足；没有真实期初对方科目时不得杜撰一笔来凑平。

**反例与验证：** 把甲的 10 USDT 价差释放给乙，再给另一行记一笔相反方向，仍可能让全局 USDT posting 汇总为零，却没有证明甲获得退款。验证应从稳定成交身份出发，逐项核验所有者、桶、reservation、余额重算和应用水位；总账层另按正式科目映射核对。文中方案是设计与手工推演，不是已运行的数据库或会计审计结论。
