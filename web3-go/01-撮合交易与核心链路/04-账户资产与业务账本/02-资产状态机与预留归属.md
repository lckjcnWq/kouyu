# 大问题 2：可用、预留、在途和抵押怎样建模，哪些能直接相加？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文范围说明：只为同库、无借贷、零手续费的 BTC/USDT 现货定义可用与订单预留两个已记账资产桶；待确认充值、成交在途和永续抵押仅用于说明不能混算的边界。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 已记账现货资产 | 已经被账户账本正式承认的数量 | 同一用户同一币种等于可用加订单预留 |
| 可支用上限 | 当前最多还能批准多少新支出 | 不含展示中的预计到账或未确认充值 |
| order_reserved | 为订单占住、不能另花的汇总桶 | 必须能逐笔对应 reservation 的剩余量 |
| 预留归属 | 这笔占款属于谁、供哪个意图使用 | R-B1 不得挪给其他账户、币种或订单 |
| initial | 创建预留时的原始数量 | 本例创建后不变，不能改它来调平错误 |
| spent | 已经交给对手方的预留数量 | 买方用 USDT 计，卖方用 BTC 计 |
| released | 从预留返回所有者可用的数量 | 包括成交价差与确定撤单的剩余款 |
| remaining | 还被未完成义务占住的数量 | 不能因订单页面显示终态就直接清零 |
| 限价预留上界 | 按最差允许价格为成交数量占的钱 | T1 对应 6,010 USDT，实际支付只有 6,000 |
| 执行资格与账务结清 | 还能否成交、已成交是否入账是两件事 | 已全成或已撤单都可能还有待履行义务 |
| 待入账成交视图 | 告诉用户买到了但还没结转的数量 | 不是额外一份可以加入可用的 BTC |
| 待确认充值 | 看见链上记录但尚未达到入账条件 | 不进入本例两个现货资产桶 |
| Perps 抵押 | 受仓位风险规则控制的锁定权益 | 不沿用现货订单预留的消费与释放规则 |
| 聚合一致性 | 汇总桶与多笔明细始终对得上 | 单行 CHECK 不足以保证，需权威事务统一维护 |

## 把整篇文章压缩成一个故事

甲在现货账户里有 20,000 USDT，下 B1 后看到可用只剩 4,975，便以为资产少了。账户系统沿着 R-B1 告诉他，另外 15,025 USDT 仍属于自己，只是专供这笔买单，不能再用于另一笔支出。这里比较的是同一币种的可用与预留，不是把 USDT 和 BTC 折成一个模糊总数；预留明细还必须写清甲、USDT 和 B1，不能只有一个不知用途的冻结总额。

随后 B1 在主案例中完成两笔交易。系统在同一账务事务的工作副本里先计算 T1：这部分按限价占了 6,010 USDT，实际给乙 6,000，另外 10 返还甲，因此尚占用 9,015。再计算 T2，将 9,015 支付给丙，最终原始预留被解释为已花 15,015、已释放 10、剩余零。甲收到的 0.25 BTC 记在 BTC 可用桶，不能塞进 USDT 的累计字段；两个计算步骤也不是两次可对外读取的提交。

如果从同一期初另走一个独立分支，只成交 T1 就撤掉剩余订单，系统必须先取得 B1 的关闭裁决，并把此前成交按序入账，才能释放余下 9,015 USDT。连同价差共释放 9,025，甲最后有 14,000 USDT 和 0.10 BTC。不能拿其他订单的撤单证明来释放 R-B1：即便所有数字恰好闭合，B1 仍可能继续成交，钱就被错误地重新开放使用。

甲界面上若另有待确认充值、成交待入账或永续抵押，系统分别解释其来源和条件，不把它们统统加入现货可用。多实例修改时，数据库事务一起维护汇总桶、预留明细、分录与幂等结果，再核对归属和累计式；页面只是说明进度。这里的故事用于读懂状态机，不能当成这些扩展产品或并发实验已经实现的证据。

## 第 1 层：先回答“可用”到底是什么意思

**面试官：** 账户有 20,000 USDT，订单限价乘数量正好是 15,025。你会怎样定义用户余额？这笔订单预留以后，用户总资产是少了 15,025 吗？

**面试者：** 我会把“资产数量”和“当前可再次支用数量”分开。此模型里，一个用户、一个币种的已记账现货资产只有两个桶：`available` 与 `order_reserved`。下单前甲是可用 20,000、预留 0；预留成功后是可用 4,975、预留 15,025。同一币种合计仍是 20,000，所以这一步只是改变可支用状态，不是把资产转给平台，也不是资产损失。

```text
已记账现货资产(user, asset)
    = available(user, asset) + order_reserved(user, asset)
可用 = 可以接受新支出命令的上限
预留 = 已指定给某项未完成业务、不可再被另一项业务使用的数量
```

这里的“总资产”只能指当前账户账本里已确认记账的数量，不包括未确认充值，也不能把 BTC 与 USDT 的数量直接相加。若有按汇率折算的净值，那是另一种估值视图，不是资金校验公式。字段名也要带币种和桶的语义；一个没有用途定义的 `balance` 或 `frozen`，不足以回答钱是否能被订单、提现或抵押支用。可用的定义最终要落到资金命令的授权条件：只有账户域确认该桶有足额已记账数量，才能允许创建对应的新支出义务。

状态还必须带有“截至何时”的含义。撮合已经确定成交，不代表账户余额已经把它结转；查询到预留仍在，也不代表订单还能继续成交。账户余额对应账户域已提交的应用位置，订单生命周期对应撮合域的裁决位置。主案例撮合已全成、账户尚未处理时，甲仍显示可用四千九百七十五、预留一万五千零二十五，属于允许的在途状态；必须保留这些资产完成既定支付义务。等账户事务提交后，才能把余额描述为期末状态。为了让用户理解，可以并列展示订单状态和账务状态，不能通过一个笼统的“成功”字段掩盖进度差异。

我也不会把预留解释为某几枚链上代币被移到专用地址。本模型的托管钱包可能汇集多个用户资产，用户间成交只改变内部请求权和可支用状态。预留是平台账本上的业务约束，不是逐笔链上冻结；已经预留不保证链上钱包当前可转出，链上转账已广播也不代表内部预留应立即解除。先限定这些含义，才能讨论下一步预留归谁，而不是让同一个字段同时承担内部交易、链上确认和钱包库存三个职责。

## 第 2 层：两个桶相加成立，预留余额怎样保证不会丢归属？

**面试官：** 你把可用与预留相加得到已记账数量。甲的 15,025 USDT 预留到底是谁的、服务于哪笔订单？如果只在余额表放一个 `order_reserved=15025`，怎样知道能释放多少？

**面试者：** 汇总桶只用于快速裁决，不能替代预留明细。每一笔预留都要有稳定的 `reservation_id`，并绑定 `intent_id`、逻辑所有者、资产、用途、初始量和规则版本。R-B1 属于甲的 USDT，只支持 `buy-001`／B1 对应的买入意图；它不能移给另一个账户、另一个币种或另一个订单。按用户和资产汇总的 `order_reserved` 必须等于该用户该币种所有有效 reservation 的 `remaining` 之和。

我会在明细上保存 `initial、spent、released、remaining`，并维持：

```text
reservation.initial = spent + released + remaining
remaining >= 0
user.order_reserved(asset) = sum(reservation.remaining for that user and asset)
```

`spent` 是已经通过该预留履行的对手方支付量；`released` 是转回所有者可用桶的量；`remaining` 是仍被业务义务占住的量。主例中，买方 R-B1 的 `initial=15025`，T1/T2 后为 `spent=15015, released=10, remaining=0`。S2 的 BTC 预留则为 `initial=0.20, spent=0.15, released=0, remaining=0.05`。账户桶给出总览，reservation 给出所有权和释放依据，两者不一致就应阻断资金命令并调查，不能挑一个方便的数字继续。

状态身份还应有唯一约束，例如一个预留身份只能创建一次，重复请求载荷必须相同；同一 reservation 的账户、资产、初始值和意图绑定创建后不可被普通更新改写。这样不仅避免汇总值对不上，也避免运维脚本把甲的预留挪给乙后仍通过“全平台总额相等”的检查。

## 第 3 层：既然 reservation 有四个数量，成交时状态怎样迁移？

**面试官：** 你已经把 R-B1 的归属和累计字段说清楚。T1 实际只花 6,000 USDT，但按买入限价预留了 6,010；你会怎样同时更新余额桶和这笔 reservation？

**面试者：** 我会把成交拆成“履约支出”和“确定释放”两部分，而不是把订单状态变化直接翻译成清空预留。T1 对 0.10 BTC 的限价上界是 `60,100×0.10=6,010 USDT`，实际成交成本是 `60,000×0.10=6,000 USDT`。因此同一确定成交里，6,000 从甲的 R-B1 转给乙可用，10 从甲的 R-B1 转回甲可用；BTC 方向则是乙的 S1 预留 0.10 转给甲可用。

主例的 T1、T2 属于同一个完整结果批次，在同一个账务事务提交。下面“ T1 后／T2 后”仅是事务内工作副本的计算展开，不是外部可见的两次提交；外部权威查询只能读到提交前或提交后的完整状态。

状态迁移前后可以这样读：

```text
R-B1：initial 15025, spent 0,     released 0,  remaining 15025
T1 后：initial 15025, spent 6000,  released 10, remaining 9015
T2 后：initial 15025, spent 15015, released 10, remaining 0
```

R-B1 的 `remaining` 减的是本次订单数量对应的**限价预留上界** 6,010，而不是只减实际成交成本 6,000。差额 10 需要在账本中明确转回可用，并进入 `released`。到 T2，剩余数量 0.15 的限价成本正好是 9,015，实际成本相同。完整主例最后 `15025=15015+10+0`。这描述的是主案例全成，不表示所有全成订单都没有余额变动，也不表示所有剩余预留都能在收到一条成交消息时立即释放。

状态迁移函数应基于原状态和确定业务事实计算新状态：校验成交属于该订单和 reservation、成交数量未超过剩余数量、实际成本不超过该部分限价上界，然后在一个账务事务内写双方资产转移并更新四个累计量。若只改 `remaining` 不记 `spent/released`，虽可能暂时让汇总正确，却无法解释历史；若先记释放再记实际支付，则会短暂放大可用余额。任何中间状态都不得单独提交给其他资金命令读取。

还可以用两个相互独立的状态维度理解 reservation：一是执行资格仍开放还是已关闭，二是账务义务尚未处理还是已经结清。这不是再增两个资产桶，而是帮助避免把生命周期状态当金额。订单已全成意味着没有剩余可执行数量，却可能仍有尚未应用的支付义务；订单已撤销意味着剩余执行资格关闭，却不能否认更早已确定的成交。只有这些义务都已按序处理，且剩余量已合法消耗或释放，才能宣告 reservation 闭合。`remaining=0` 本身也不能证明全成，因为没有成交而全部撤销时同样为零。

对买卖方的金额字段还要坚持单位单一。R-B1 的 spent 和 released 都是 USDT，不能把甲买到的 BTC 填进这两个字段；卖方 S1、S2 的 spent 才是 BTC 交付数量。订单的累计成交基础币数量属于另一维度，用于校验成交未越过原始数量，而不是与 USDT reservation 直接求和。底层仍按 BTC 的一亿分之一和 USDT 的一百万分之一保存整数；这里为方便口述写成人类可读单位，不能在数据库里混存两种表示。

## 第 4 层：若这个订单只部分成交并撤销，什么事实允许释放剩余量？

**面试官：** T1 的价差你已作为释放处理。现在单独改变一个条件：T1 成交后，订单撤销剩余 0.15 BTC，T2 没有发生。账户收到撤单结果就能把剩下的钱放回去吗？具体是多少？

**面试者：** 这是独立的“部分成交后撤单”变体，不是在主案例 T1、T2 全部完成后再撤一次。只有撮合域已在权威顺序中关闭这 0.15 BTC 的执行资格，且账户确认该撤单之前的成交结果都已应用，才能释放剩余义务对应的预留。订单页面显示 `CANCELED` 不是账户退款的充分证据；否则一个迟到成交可能与已经重新支用的余额冲突。

T1 以后仍有 9,015 USDT 预留支撑剩余数量。关闭资格的结果被按序应用后，9,015 才从 R-B1 转回甲可用。累计 `released` 是 T1 的 10 价差再加撤单的 9,015，即 9,025：

```text
initial 15025 = spent 6000 + released 9025 + remaining 0
甲：14000 USDT 可用，0.10 BTC 可用，R-B1 预留为 0
```

这时 `20000-14000=6000` 是已履行的 USDT 支出。该独立变体不能覆盖主例的期末甲 4,985 USDT、0.25 BTC；主例里没有撤单，T2 也已发生。状态机的重点是将撮合的“还能否成交”和账户的“可用多少”通过确定业务结果连接起来，而不是从订单终态猜金额。

如果撤销命令与 Place 同时发生，撮合域要在同一权威顺序中裁决：若关闭先于接纳，持久关闭记录阻止迟到 Place；若接纳先发生，则先处理已确定成交，再关闭实际剩余资格。账户消费者还需要按连续结果序号处理；收到撤单批次却缺少前序成交批次时，停在缺口处，不能先释放 9,015。订单已关闭是释放资格的一部分，不等于账户已经完成对应的分录迁移。

预留年龄和终态标签只是恢复线索。扫描到很久未变化的预留，可以查询原始意图、重试可靠提交或触发关闭资格命令；不能以“超过十分钟”直接把 remaining 退回。如果撮合查询暂时找不到订单，也要考虑原 Place 仍在网络或提交器任务中。需要放弃时，关闭命令必须与接纳处于同一裁决顺序，且关闭墓碑在迟到请求仍可被接纳的窗口内有效。否则一个签名正确、却已经被释放的旧预留凭据仍可能换来新成交。

恢复任务的结果也要区分“已经关闭但尚待账户应用”“原请求结果未知”“账户已应用、只是页面落后”。前两种继续持有必要的资金约束并恢复原身份，最后一种只重建投影，不再写资金分录。这些中间态可以存在，但要有未处理数量、最老年龄和人工处理入口，不能无期限挂起而缺少解释。超时与查询结果不能代替业务执行资格的确定裁决。

## 第 5 层：为什么不能把“在途”和两个余额桶直接相加？

**面试官：** 你刚才把尚未结转的成交当作义务。那能否再加一个 `in_flight` 桶，把成交待记账的 0.25 BTC 放进去，然后用 `available+reserved+in_flight` 表示账户余额？未确认充值也放这里行不行？

**面试者：** 不能把所有叫“在途”的数量合成同一个可加桶。主例中 T1/T2 一旦成为撮合域确定结果，账户尚未应用前，甲的 0.25 BTC 是待履约的成交义务；它不是已记账可用 BTC，也不是甲又拥有一份新增资产。若查询想展示“成交待入账 0.25”，那是业务进度投影，不应与账本里的 `available`、`order_reserved` 一起算成可支用余额。

未确认充值的语义又不同：链上观察到交易、尚未达到产品确认条件，通常只是外部观察或待确认权益，不进入本例已记账现货桶，也不能拿来通过买单余额检查。若产品选择预先展示它，必须标明确认门槛、可否撤回、风险承担方和最终入账身份；确认后以唯一充值事实记账，而不是将展示行直接当成可用余额。

因此我会把状态和口径拆开：已入账资产桶用于支用；尚未应用的成交、待确认充值和查询侧“预计余额”分别是义务或投影。跨这些口径的数量不能仅因单位相同就求和。对账时也要在相同业务截止点比较：把一个已确定但未应用的成交看成差异前，先区分它是正常在途义务，还是水位已越过却缺分录。

如产品确实需要“待结算”视图，字段至少要注明事实来源、币种、状态、可撤回条件和是否已进入权威账本。它可以用于解释尚未完成的状态，但在明确完成记账之前不能参与余额可支用裁决。展示层把“可用 + 待结算”拼成一个数字时，也必须避免让用户误认为合计都能下单。

## 第 6 层：Perps 抵押也显示成锁定资产，能不能复用现货预留？

**面试官：** 既然未确认充值和成交在途都要分开，那么永续合约的抵押也只是“不能花的钱”。为什么不把它们都计入 `order_reserved`，统一做 `available+reserved=total`？

**面试者：** “不能支用”只是表面相似，义务生命周期与金额变化规则不同。现货订单预留是为某个确定订单锁定数量，成交时按价格、数量消耗，撤销剩余执行资格后释放。Perps 抵押涉及仓位风险、维持保证金、资金费、未实现盈亏和强平条件；可用保证金可能随市场价格改变，释放时机取决于仓位及风险规则。用现货 reservation 表示它会把不同状态机伪装成同一种余额。

即使一个产品让现货钱包资产作为 Perps 抵押来源，也应通过明确的跨产品转账或抵押记录来表达所有权与风险归属。现货可用余额只能在抵押转移事务成功后减少；Perps 抵押账簿再建立自身的抵押权益。解除抵押必须引用仓位／风险域的确定释放资格，不能由现货服务仅凭时间或页面状态退回。若两个域跨库，还要定义在途期间谁冻结资产、失败怎样恢复，不能假设一次普通 RPC 能同时改完两个账本。

本专题不把 Perps 抵押加进主例的 USDT 或 BTC 余额公式。若要支持它，需要扩展模型和总览的产品基线，明确新桶的账务含义、权威来源和守恒关系；不是随手添加一个 `collateral` 数字就算完成状态建模。类似地，提现锁定资产与订单预留虽然都减少可用余额，也可能有不同的取消与外部确认条件，应该各自绑定用途和执行资格，而不是共享一条可以任意释放的通用记录。

## 第 7 层：明细和汇总在多个实例下怎样保持同步？

**面试官：** 你说增加抵押等用途必须先明确写权和转移协议。先不扩展产品，回到现有两个现货桶：多个实例同时处理新下单和成交，怎样防止两个事务基于旧余额都通过，或者预留汇总与明细只更新了一边？

**面试者：** 余额和 reservation 的所有更改必须走账户域唯一逻辑写入口，并在同一个 PostgreSQL 事务里完成。多个 Go 实例不靠进程内 `sync.Mutex` 协调，而是对同一余额键使用数据库锁／条件更新，并使用唯一约束保护 reservation 身份。对一笔新预留，事务锁定 `(owner_id, asset_id, bucket)` 的相关行，检查可用量，再原子地从可用转入预留、建立明细并保存命令幂等结果。不存在的余额行不能假定已经被 `SELECT FOR UPDATE` 锁住，要预建或使用受唯一键约束的建行协议。

对结算批次，事务按固定顺序锁定所有相关余额，再锁 reservation；验证 R-B1 与卖方 reservation 归属、剩余量和业务结果后，统一构造两边分录、余额变更与 `spent/released/remaining` 新值。任何一个参与方不满足条件，整笔批次回滚，不能先改乙余额再发现甲预留不足。使用相同锁顺序减少死锁；数据库可重试错误应以原业务身份重试整个事务，不重放单条 SQL 的局部副作用。

唯一写入口是逻辑所有权，不是单实例部署。后台、风控和订单服务只提交受验证的命令；数据库权限也应阻止绕过写入层直接改余额。Go 代码用同一个 `sql.Tx` 承载事务内查询和更新，不能锁内调用撮合 RPC。事务提交才是状态迁移生效点；RPC 超时后查询原身份，不用新身份再占一次资产。写入层还应检查 reservation 资产、所有者和用途与业务结果绑定，不能因为收到“释放 9,015”的调用参数就盲目执行。

这里的事务需要对“读—判定—写”整体串行化，而不只是把最后两条 UPDATE 放在事务里。若采用 Read Committed，先读到 available=20,000，再在应用层计算金额，之后没有行锁或带版本条件的更新，两个实例仍可能分别成功预留 15,025。可用 `SELECT ... FOR UPDATE` 锁定预建余额行，也可对 `bucket='available'` 的行使用 `UPDATE ... SET amount=amount-$1 WHERE ... AND amount >= $1` 并检查恰好影响一行；同时 reservation 创建、余额桶转移与幂等结果必须在同一事务，获取行锁仍遵循固定键顺序。若条件更新影响零行，要区分余额不足、版本冲突与本应存在的桶行缺失，不能一律报余额不足，更不能继续插入预留明细。

还要小心“明细的聚合约束”不容易直接由单行 CHECK 保证。`initial=spent+released+remaining` 可以由 reservation 行上的 CHECK 约束表达；但 `order_reserved=sum(remaining)` 涉及多行，普通行级约束不能覆盖插入、更新、删除的并发组合。可选择将余额索引视为事务维护的汇总，并通过唯一写入口锁住对应 owner/asset；对所有影响它的新增、消费和释放统一执行聚合增量，另以周期性重算作独立核对。禁止其他路径直接写 reservation 表，数据库权限、存储过程或受控 repository 边界都可以成为落实方式，实际选型应符合团队治理。

资金状态动作应区分意图创建、预留、成交消耗、价差释放、撤单剩余释放和修复冲正。每种命令定义允许的前置状态、来源凭据、影响资产和后置不变量。比如同一 reservation 对某个 trade 重复消耗，必须凭稳定身份返回原结果；把相同 trade_id 改数量不应被当作新的合法增量。reservation 归零后可以标记已闭合，但不能删除历史以便重复创建同一身份。状态转换校验失败应保留原状态，记录可定位的拒绝原因，不能将业务失败变成“余额看起来合理”的自动修正。

## 第 8 层：状态机怎样验证闭合，哪些“看起来守恒”的做法仍然错？

**面试官：** 这些更新都放进了事务。你怎么证明状态机没有少钱、多钱或错放别人的钱？只检查每个币种的总余额不变可以吗？

**面试者：** 仅看总额不够。内部账面上所有同币种余额之和可能没变，但订单甲的 reservation 被错绑到乙，仍会在之后释放错误。验证要同时看桶级非负、同币种转移、reservation 累计闭合、用户资产桶汇总与明细之和、业务意图与预留归属，以及撮合结果应用水位。

对主例，BTC 要逐账户逐归属检查：乙 S1 的 0.10 BTC 已用于 T1；丙 S2 的 0.15 BTC 已用于 T2，剩余 0.05 BTC 仍属于 S2 预留；甲收到的 0.25 BTC 变成可用。USDT 要验证甲从 15,025 预留中实际支付 15,015 并释放 10；乙、丙各自分别收到 6,000 和 9,015。把 10 直接加到甲可用却不减少 R-B1，虽然用户总金额会多 10，也会让明细与汇总分叉。

实现上，我会把状态迁移建成只有合法前置状态才能执行的资金命令，借助数据库约束、固定锁序和事务校验表达不变量；由分录重算余额、reservation 汇总与账户水位的定期检查发现长期偏差。任何差异先定位原业务事实及同一截止点，不直接改余额抹平。可以用主例、独立的部分成交撤单例、重复批次、余额不足和归属被篡改等输入手工核验预期；没有实际运行测试时，只称为验证方案，不能声称已通过。

### 本题收束

**讲透的机制：** 可支用余额与业务预留分桶；每笔 reservation 有所有者和意图，且 `initial=spent+released+remaining`；汇总预留等于明细剩余之和；成交支出、价差和确定取消分别改变对应状态。

**最容易答错的边界：** 未确认充值不是已记账资产；未应用成交是履约义务，不是又一份可花 BTC；Perps 抵押不能因为“也是锁定资金”就混入现货订单预留；账户总数平衡不能证明预留归属正确。

**反例与验证：** 独立故障场景从只发生 T1、尚未关闭 B1 的快照开始：若账户误拿另一订单的撤单证明，把 R-B1 剩余 9,015 转回甲可用，并把它记成 released，则分录平衡、余额非负、汇总与明细相等，`initial=spent+released+remaining` 也成立，但 B1 的 0.15 BTC 执行资格仍开放。甲再次支用退款后，迟到成交就失去来源。这证明数量闭合还必须加上关闭证明与 reservation 的身份绑定，不能只比较汇总数字。

单独漏记 reservation 消耗并不会自行增加 available，因此不能直接推导为甲能够重复下单；若成交历史已 APPLIED、余额已正确转出而明细仍未消费，首先违反的是预留汇总与明细一致性。后续若盲信该明细进行释放或重放，才可能导致错误退款或重复履约，必须先隔离并追查共同提交边界。

正常迁移还应保证 initial 不变，spent 与 released 非负且单调增加，remaining 非负且单调减少；同一业务动作重放不再增加累计量。本例不支持为原 reservation 追加金额或改绑订单，若产品需要改单增资，必须另定义身份、补资和执行资格更新协议。这样可以避免以“修改 initial”掩盖错误消耗，让一个表面永远能调平的公式失去约束力。

本题沿用同库状态机，不另增工程 MVP；专题唯一 MVP 见[总览](README.md#七工程实践一个简洁-mvp)。
