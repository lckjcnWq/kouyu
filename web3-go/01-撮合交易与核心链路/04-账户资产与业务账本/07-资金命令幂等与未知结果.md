# 大问题 7：请求重试、回执丢失和同键不同参数怎样处理？

## 先看懂：关键词大白话解释

本文范围说明：在多 Go 实例共享单个 PostgreSQL 账务库的现货模型中，说明资金命令如何识别同一次动作及收敛未知结果；幂等不替代撮合资格关闭、可靠交付或跨库结算。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 业务幂等键 | 同一动作重试多少次都沿用的身份 | buy-001 代表原下单资金意图，不随 HTTP 连接变化 |
| 来源与账户作用域 | 说明这个键属于谁、授权来自哪里 | 不同用户的同名键不能串单或互查 |
| operation_type | 区分同一业务中的不同资金动作 | 预留已做过，不等于后续成交已经入账 |
| 规范化经济载荷 | 将等价参数变成相同的确定表达 | 0.2500 与 0.25 对应相同 BTC 整数数量 |
| 载荷摘要 | 便于比较完整业务参数的指纹 | 覆盖账户、方向、价格、数量与版本，不负责鉴权 |
| 同键异载荷冲突 | 同一个身份被拿来表达另一笔交易 | 改成 0.30 BTC 必须报冲突，不能覆盖原动作 |
| 唯一键执行权 | 数据库裁决哪个首次事务可以继续 | 两个实例都查不到结果，也不能各自执行 |
| 冲突后独立读取 | 插入未取得键后再读取已提交原结果 | 不把无 RETURNING 行误判为身份不存在 |
| 同事务原始响应 | 将确定决定与资金事实一起保存 | 返回原 R-B1 和预留结果，不拿当前余额冒充历史响应 |
| 稳定拒绝 | 一旦持久决定不执行，同键重试仍不执行 | 后来余额增加也不让原拒绝悄悄变成下单 |
| 未知知识状态 | 调用者暂时不知道资金动作是否完成 | Commit 出错或查询暂空不等于已回滚 |
| 原键仲裁重试 | 让原事务与新尝试争同一个数据库唯一键 | 旧提交就读旧结果，旧回滚才可能首次执行 |
| 身份留存窗口 | 防重证据必须覆盖可能的迟到与恢复时间 | 不能靠短期 Redis 锁或随意 TTL 清空历史 |
| 查询授权 | 读命令结果仍要验证账户权限 | 猜到别人的 command ID 不代表有权查看资产 |

## 把整篇文章压缩成一个故事

甲用 buy-001 提交 B1，账户系统准备为它预留 15,025 USDT。因为网关重试，相同请求同时到了两个实例；它们即使都查询不到旧结果，也不能各自创建预留，而要争数据库中的同一个作用域唯一键。获准的一方将命令身份、规范参数、R-B1、双边分录、余额与原始响应一起提交，另一方等待后读取这份结果，不能再占一次钱。

回执恰好在提交附近丢失，甲不知道 B1 是否成功。系统让他继续查或重试 buy-001，而不是换键，原因是数据库可能已经提交，只有回复没回来。权威查询暂时为空也不证明原事务不会稍后成功；再次沿原键竞争，才能在旧提交时返回原结果、旧回滚时首次有效执行。在基线 20,000 USDT 下，若贸然换键再占同样的钱，第二笔会因余额不足拒绝，却不能据此认定第一笔也失败。

甲重试时若只把 0.25 写成 0.2500，规范化整数相同，应拿到同一结果；若仍用原键却改买 0.30 BTC，则必须冲突。若原命令已经稳定拒绝，后来账户增加资金也不应自动执行旧意图。原预留查询始终解释当时的决定，随后 T1、T2 的入账要用各自稳定结果身份，不能因为预留已成功，就把成交也说成早已完成。

更久以后，系统归档响应或从备份恢复，仍要留住关键身份和结果引用，并使它们与分录、余额和进度处在一致位置。乙即使猜到 buy-001，也只能查询自己被授权的作用域。整套机制识别的是原身份下的重复动作，不能自动识破上游任意换名的经济事件，也不授予退款资格。本文给出的是恢复契约与手工预期，不把未知结果协议说成已运行的网络实验。

## 第 1 层：给一次业务动作一个不会随重试变化的身份

**面试官：** 用户提交 B1 后客户端超时，自动重试三次。你会拿 HTTP 请求 ID、订单 ID 还是消息 ID 防止重复预留？先解释你所谓的“一次”是什么。

**面试者：** “一次”是用户希望发生的同一个资金动作，不是一次网络调用。客户端要为这次下单意图稳定使用 `buy-001`；每次 HTTP 连接、trace ID、代理重试次数可以不同，但不能改变业务身份。账户域以经过认证的来源作用域、business ID 和 operation type 定位命令，例如 `ReserveOrder(buy-001)`，并持久保存它与 B1、R-B1 的映射。首次预留成功后，三次相同请求都应返回同一个 reservation，不会再从甲的可用余额搬走另一份 15,025 USDT。

总览的唯一键是 `(source, business_id, operation_type)`。我会把 `source` 定义成受信调用方／租户及账户作用域的规范标识，或者将这些维度显式列为数据库唯一键字段，二者语义必须相同。不能让客户端自报一个任意 source 就跨账户访问同一个键，也不能只对用户填入的 `buy-001` 建全局唯一索引，误把别人的同名命令当成甲的结果。业务 ID 的命名空间和生成责任必须写进接口契约，不能靠各服务约定俗成。

这里还要分清不同身份的保护范围。命令键防止预留重做；intent ID 防止撮合把同一意图接纳两次；reservation ID 表示哪份资金承担哪个义务；result stream 与 seq 标识哪批确定结果已经应用。它们可以互相引用，但不能只凭“用了同一个订单号”推导所有阶段都幂等。如果上游把同一经济请求换成两个不同业务键，账户会将它们视为两次独立意图；能否识别这种重复，需要上游稳定身份契约，而非数据库猜测用户意图。

业务身份应在第一次可能被执行之前确定，并让客户端保存到能够跨进程恢复的位置。若必须由服务端生成，需先通过可重试的受理身份建立并返回稳定映射，而不是每次重连都生成新订单号。查询接口同时接收作用域和原键，鉴权后返回原结果与关联意图；找不到时只表示尚无可见的持久决定。这样客户端重启、网关重试与服务端任务扫描才能围绕同一个动作协作，避免一边查旧单、一边偷偷创建新单。

## 第 2 层：同一个身份必须绑定同一份规范化业务载荷

**面试官：** 你刚才要求客户端重试 `buy-001`。如果它第一次请求 0.25 BTC，第二次仍用该键却改成 0.30 BTC，系统该怎样处理？直接比较原始 JSON 能解决吗？

**面试者：** 必须返回明确的同键不同载荷冲突，既不能按新数量再执行，也不能不告知冲突便返回旧成功。一个身份只能代表一个已固定的业务动作，否则调用方可能误以为 0.30 BTC 已提交，系统却只做了 0.25 BTC，或者用“最后一次参数为准”覆盖了已经成交的订单。若用户确实要修改，需要定义新的业务动作或新意图，并另外处理原意图是否仍能执行；不能让重试接口兼任改单接口。

我会先做类型化解析和规则校验，再构造规范化业务载荷：账户、交易对的稳定标识、方向、限价整数、数量整数、GTC、规则版本及影响业务的显式默认值。按基线，0.25 BTC 转为 25,000,000 个 BTC 最小单位，60,100 USDT/BTC 转为 60,100,000,000 个价格单位；`0.2500` 与 `0.25` 应规范为同一个整数。价格和数量的步长、正数与溢出检查同样不能省略，不能为“让摘要一样”把非法精度悄悄四舍五入为合法值。

摘要基于固定字段和固定编码次序，而不是字段顺序、空白、浮点格式可能不同的原始 JSON。请求时间、trace ID 等传输属性一般不进入经济载荷，但账户、方向、数量和限价绝不能漏掉。数据库保存规范化版本、必要字段或其可靠引用以及抗碰撞摘要；为了审计与冲突解释，可同时保留关键规范值，不只存一串无法解释的 hash。摘要降低比较成本，不负责鉴权，也不是证明两次请求来自同一个人的签名。

重试还要固定首次采用的规则版本。若首次采用版本 V1，规则配置后来变为 V2，相同请求不能被服务端悄悄按 V2 重新解释而发生另一种经济效果。可以让请求携带已确认的版本，或由持久身份绑定 V1 后返回它；后续比较按保存的规范化规则进行。真要采用新规则，应创建新的业务意图，同时先查清旧意图。规范化方案自身也需要版本化，否则部署新编码后可能把完全相同的旧请求错误判为冲突。

## 第 3 层：两个实例都查不到结果，怎样只让一个取得执行权？

**面试官：** 现在两份完全相同的 `buy-001` 同时到达不同 Go 实例，载荷也一致。它们都先查到幂等表为空。你怎样阻止它们各建一个 R-B1？

**面试者：** 先查为空不能授予执行权，因为两个事务都可能在另一方提交前看到空结果。最终裁决者必须是数据库唯一约束。ReserveOrder 在本地事务中尝试插入规范作用域下的唯一命令键，带上规范化载荷；插入成功者才继续资金校验和写入，冲突者按 PostgreSQL 的唯一索引冲突规则等待前一事务完成，而不是另取一个 ID 绕过冲突。若前一事务回滚，等待者可以取得该键并首次执行；若前一事务提交，就只能读取并核验已有结果。

可使用 `INSERT ... ON CONFLICT DO NOTHING` 配合影响行数判定。影响一行表示当前事务创建了键；影响零行不等于命令失败，也不等于可以直接返回成功，而是应读取持久记录，核对身份、载荷和结果。`READ COMMITTED` 下每条语句有自己的快照；唯一约束可能因为另一事务的记录而阻止插入，即使该行不在当前插入语句的可见快照中。因此通常需要后续独立的 SELECT 取得已经提交的冲突行，不能把单条语句的“没有 RETURNING 结果”误判为不存在。

若直接执行普通 INSERT 遇到唯一冲突，PostgreSQL 当前事务通常已进入错误状态，不能原地继续 SELECT 假装没事；需要回滚后重新开始查询，或采用事先定义的安全冲突处理方式。任何驱动错误、影响行数读取错误都应检查。进程内 mutex、Redis 短锁和先查后写可减轻部分竞争，但不能替代这个跨实例、可恢复的唯一约束。

这里讨论的是无结果流游标的预留命令；撮合批次应用涉及流游标和余额行时，统一遵守母题 05 的结果身份仲裁与数据库锁顺序。本题只约束身份键的唯一性、载荷核验和结果读取，不另定义一套锁序。发生并发唯一键竞争时，冲突方只读取并核验原身份结果，不能先持有后续账务锁再回头争用身份键。

## 第 4 层：让确定结果与资金事实属于同一次提交

**面试官：** 获得唯一键以后，实例先提交“处理中”，再另开事务预留资金，最后写成功结果。这样能方便查询进度，为什么仍然可能让重试不安全？

**面试者：** 这会增加一个独立提交边界，也就增加“占了键却没有资金变化”“资金已经变化却没有最终结果”的恢复状态。如果先把幂等键永久标记为成功，再执行扣款，崩溃可能留下虚假成功；如果先提交资金再补写成功，崩溃后重复请求可能再次执行。当前基线不需要为了可查进度引入跨事务的资金执行权租约，我会让唯一命令行、业务决定与本地资产变化在同一个短事务中完成。

ReserveOrder 的同事务集合是：原身份和规范化载荷、R-B1、可用到订单预留的成对分录、权威余额和账户版本、待发 Place 的 outbox，以及包含 B1/R-B1/预留金额/结果版本的原始响应。事务提交后，查询者看到的是已确定预留成功；提交前，其他事务看不到这条未提交成功事实，重复执行者由唯一约束阻塞或超时后继续查询。原始响应应保存经济决定和引用，不把后来变化的“当前余额”伪装成原请求结果。

确定余额不足时，可以在锁定余额并完成业务判断后，把同一键记录为稳定的 `REJECTED_INSUFFICIENT_FUNDS`，不创建 reservation 或资金分录，然后提交拒绝结果。此后甲余额即使增加，同键同载荷重试也返回原拒绝，不悄悄变成一次晚到下单；用户希望重新评估就提交新的意图。这是本题明确采用的业务契约。语法和精度等尚未受理的输入错误可直接拒绝，不必为任何非法字节都建资金结果行，但要在接口说明受理边界。

数据库错误则不同：死锁、事务语句失败或本地校验发现分录不平时，回滚本次事务及创建的命令行，不能留下成功结果。在本地事务中暂写的 `IN_PROGRESS` 若不独立提交，并不是外部可恢复任务状态；若未来确实改成持久工作流，需要额外定义执行权、围栏、恢复扫描以及资金事务与工作状态的原子关系，不能只多加一个状态枚举。本题保持短事务模型，避免把工作流草图当成幂等的必要前提。

## 第 5 层：Commit 连接中断后，通过原键收敛未知结果

**面试官：** 同一个事务已经执行完所有 SQL，Go 调用 `tx.Commit()` 时连接断了，函数拿到 error。调用方仍未看到结果，下一步到底能不能再预留？

**面试者：** 不能仅凭 `Commit` 返回 error 就认定事务没提交。数据库可能尚未提交，也可能已经把 15,025 的预留及结果持久化，只是提交确认包丢失。此时服务端与调用方的知识状态是未知，不能把它改写成确定失败，更不能建议换 `buy-002` 再试或立即做一笔反向释放。原命令身份是恢复锚点，必须继续沿用 `buy-001`。

恢复端用有权限的原身份向权威账务库查询：若找到同载荷的 `RESERVED`，返回原 R-B1、金额和账户版本；若找到稳定拒绝，返回原拒绝；若载荷不一致，返回冲突。不能仅查询落后的只读副本，然后因“未找到”宣布回滚。即便查询主库暂时为空，也可能是原事务仍在进行或查询发生在其提交之前，这只是暂时没有已提交结果，不是旧事务永远不能成功的证明。

接下来可在可用的主库上重新提交同一键同一载荷，由唯一约束等待并仲裁：旧事务提交则重试命中原结果；旧事务回滚则新事务第一次有效执行。新尝试仍要重新读取受锁余额，而非使用第一次尝试的旧工作副本。若数据库不可达、唯一键等待超过请求期限，就继续返回结果待确认，并由有界的恢复任务查询；不把数据库可用性问题转成无限占用连接的重试循环。

对外协议应同时返回命令身份和查询方式，区分完成、拒绝与暂时未知。查询响应的“尚无已提交结果”与业务拒绝是不同状态；客户端可以按退避查询或原键重试，但不得自动换键。服务可以在本地持久账务之外记录观测到的未知任务用于运维，这种观测记录不是资金事实，不得覆盖最终账务结果。主从切换后的已确认写是否保留还取决于数据库持久性配置，幂等键本身不能恢复被存储系统丢掉的提交。

## 第 6 层：把业务拒绝、可重试错误和未知结果分开返回

**面试官：** 你刚才说客户端不能把未知当失败。若接口所有异常都返回 HTTP 500，上游会统一重试。怎样区分余额不足、死锁、同键改参和 Commit 未知，避免自动重试放大错误？

**面试者：** 我会让协议表达业务确定性，而不只给 HTTP 状态。确定业务拒绝意味着系统已经作出“本动作不执行”的决定，例如已持久化的余额不足，返回稳定拒绝码和原命令键；这不是后台等到余额足够再执行的待办。相同身份重试返回原拒绝，若用户希望重新发起，则使用新意图。身份载荷冲突则说明调用方在复用原键时改变了语义，必须核对原命令，而不是自动重试到成功。

可重试数据库错误必须有“该次事务已确定回滚”的证据，例如 PostgreSQL 死锁受害者。服务可以沿原身份对整个短事务做有限次数重试，重取行锁并重新校验，而非接着执行失败 SQL。达到上限时表达为本次尝试未完成、可原键重试，不能为了尽快返回就将命令标为业务拒绝。约束冲突若来自命令唯一键，应进入原结果读取流程；若是其他数据约束错误，不能都套用相同重试策略。

提交未知表示尚不能确定资产变化是否发生，优先查询同一身份，直到读到确定结果或通过原键仲裁继续完成。永久系统／数据错误，例如 reservation 归属冲突、分录不平或稳定结果源内容不一致，要暂停相关自动资金执行并告警调查；即使错误可被重试“偶然避开”，也不能跳过它推进消费位置。网络错误发生在什么阶段很重要，不能看到 timeout 字样就统一当已回滚。

响应至少携带稳定错误类别、原命令身份、下一步是查询还是原键重试，以及已知的结果引用。查询仍然鉴权，不因拿到 command ID 就泄露账务信息；返回的重试建议也不允许变更数量、价格或账户。对外“请求重复”不应是模糊报错：同键同载荷且已完成应返回原结果，同键异载荷应冲突，原事务未决应等待或待确认，三个状态的恢复动作完全不同。

## 第 7 层：防重记录必须覆盖授权范围和真实重放寿命

**面试官：** 目前重试能返回原结果。但一年后客户端恢复旧任务，或者消息系统重放历史批次，幂等表已经按七天 TTL 清理了。系统会不会又扣一次？别人猜到 `buy-001` 能否查甲的结果？

**面试者：** 如果防重记录彻底删除而旧身份仍被接纳，就确实可能重新执行。保留期不能由缓存成本随意确定，而要覆盖客户端重试、任务恢复、消息重投、灾备回放和审计窗口。对资金命令，应长期保留唯一身份及结果／journal 引用；完整响应可以归档，至少不能失去“这个身份已经作过确定决定”的证据。`spent/released/remaining` 等资金状态仍由账务事实维护，不应依赖 Redis TTL 保护。

如果产品确实要求限制命令接纳年龄，可以引入受验证的命令代次或关闭窗口，使已淘汰代次永久不可重新受理，再讨论旧记录归档。不能仅凭客户端时间戳、客户端自报“这是新请求”或重置服务时钟重新开放旧键。对撮合关闭墓碑也类似：清理记录前要有拒绝旧 Place 的持久边界，单纯时间过去不证明网络里已没有旧命令。这个资格问题由母题 06 深入，不能拿幂等表清理策略替代它。

查询必须重新检查调用方对账户和命令结果的权限。甲与乙都使用 `buy-001` 时是两个作用域，乙不能通过猜到甲的键来读取 R-B1、journal 或余额。账户身份来自验证后的认证信息或可信代操作授权，不直接采用请求体里任意 owner 字段；内部来源的资金命令也要校验来源权限、业务类型和可操作账户范围。幂等只识别重复，不授予操作权。

灾备恢复还要把账务分录、余额、reservation、结果身份和消费进度恢复到一致位置。若旧分录仍在而结果行丢失，重试可能重复；若结果行更新而余额恢复到更旧版本，重试会误报成功并漏记。应以一致快照、WAL 和可重取业务来源补齐，再恢复受理。长期保存幂等行也不能弥补不一致恢复，更不能在数据库丢失已确认写后凭“原来是幂等接口”声称资金事实仍完整。

## 第 8 层：用完整重试历史说明能力范围，而不是承诺万能恰好一次

**面试官：** 假设你已恢复所有身份记录。沿 B1 的完整历史，能否说明哪些重试返回原结果，哪些必须冲突，以及幂等键还保证不了哪些端到端性质？

**面试者：** 首次 `ReserveOrder(buy-001)` 提交后，甲可用 4,975、预留 15,025，唯一结果指向 B1 和 R-B1；回执丢失后，同作用域同载荷重试只返回该结果，余额不再改变。如果在原作用域把数量改成 0.30 BTC，或更改限价、方向，即使仍有余额也必须冲突；试图让原身份跨账户执行则拒绝越权或作用域不符，不能读取另一账户的同名结果。两个实例同时首次提交则由唯一约束决定谁执行，输的一方核对已提交结果；数据库明确回滚者允许原键重试，提交未知者先查询或原键仲裁。

撮合随后确定 T1、T2，账户批次应用要使用自己的稳定结果身份，而不是拿 reserve 的 `buy-001` 当成“所有后续动作都做过”。同批重投返回原 APPLIED 与 journal，不重复支付 15,015，也不重复返还 10。正常闭合为 R-B1 `15,025 = spent 15,015 + released 10 + remaining 0`，R-S2 `0.20 = spent 0.15 + released 0 + remaining 0.05 BTC`；甲期末 4,985 USDT、0.25 BTC。原 reserve 查询仍返回当时的预留决定，当前资金状态由独立余额／reservation 查询解释，不能覆盖历史结果使重试含义漂移。

如果上游把同一经济成交更名为全新 batch 或 trade，单一结果键未必识别得出重复；来源必须保证稳定 trade 身份和唯一归属，账户据契约校验。幂等也不能证明 Place 的预留资格有效、批次无缺口、Abort 已阻止迟到执行或多库同时提交；这些依赖母题 06 与母题文件 `08-成交交付顺序与原子入账.md`、`12-账本恢复分片与容量边界.md` 的相应机制。它防的是正确身份作用域内重复应用，不是任意错误事件都能被自动识别。

验证时我会检查同键同载荷并发、等价数字格式、同键异载荷、越权查询、稳定拒绝后余额变化、唯一约束等待、提交前崩溃与提交后回执丢失，逐项给出预期的结果身份和余额。文档里的推导不是实验已经通过。真正可复述的结论是：业务键、规范化载荷、数据库唯一仲裁、同事务确定结果、权威查询和足够持久的身份记录共同构成幂等闭环；缺少任一项，都不能把一个短期锁或“MQ 恰好一次”当成资金恰好生效一次的证明。

## 本题收束

### 机制与易错边界

- 一个键对应一个业务动作；作用域必须包含被授权的来源／账户和操作类型，不能把 trace ID 或短订单字符串当全局唯一身份。
- 规范化比较经济含义，原始 JSON hash 不足；相同数值形式应相同，关键参数变化必须冲突。
- 多实例并发由 PostgreSQL 唯一约束仲裁，冲突后核验已提交的原结果；先查为空不是执行权。
- 成功或稳定拒绝与该次本地决定共同提交；提交未知不能伪装成确定失败，也不能自动换新键。
- 查询只读已有结果但仍需鉴权；缓存过期、结果归档和灾备恢复不能重新开放旧身份。
- 幂等不替代预留归属、逐币种守恒、可靠结果源、前置成交顺序和跨库结算协议。

### 两个能暴露漏洞的反例

第一，甲的 `buy-001` 实际已经预留 15,025，回执丢失后客户端换成 `buy-002` 再发。**从基线 20,000 出发，第二笔相同预留会因剩余 4,975 不足而拒绝，但第一张订单仍可能成交；不能把第二次拒绝误认成第一次也失败。**若另起“期初余额提高到足以支撑两份预留”的明确变体，两张独立身份订单则都可能成功，说明资金非负约束不能替上游去重。

第二，服务先独立提交“幂等成功”行，再修改余额，改钱前崩溃。所有重试都会返回成功，但 R-B1 和对应分录不存在。反过来先提交资金再补结果也可能重扣。让应答者指出唯一键、载荷绑定、同事务结果和未知查询分别关闭哪个窗口，比只回答“加一个幂等表”更能验证设计是否完整。
