# 大问题 6：从预留、成交到账务释放，怎样保证端到端资金一致性？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文范围说明：账户内所有案例资产同库，但账户预留、撮合裁决与账户应用是三个独立提交边界；本文解释它们如何可靠交接，不假设撮合与账户共享事务。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 端到端闭合 | 从占款到履约或合法释放都有证据可接续 | 不靠“以后对账”来允许中间双花 |
| 持久订单意图 | 崩溃后仍知道原来要提交哪笔订单 | 与预留一起保存，不因重启重新生成 B1 |
| 可靠受理 | 对方已把命令放入可恢复的权威记录 | 不只是收到字节或放进内存 channel |
| 资格契约 | 撮合能核验资金授权覆盖哪些订单参数 | 限价、数量、所有者与规则不能换用 |
| 唯一代次 | 区分原授权生命周期的身份信息 | 已关闭的旧资格不能重新变成可执行 |
| 同序裁决 | Place 和 Abort 由同一个权威顺序决定先后 | 不比较客户端时钟或不同队列到达时间 |
| 关闭墓碑 | 即使订单未接纳，也持久记录不再允许执行 | 拒绝持原凭据迟到的 Place |
| 前置成交截止点 | 关闭之前哪些确定成交必须先入账的位置 | 释放要证明未跳过这些义务 |
| 确定履约义务 | 撮合结果已提交后不能随超时撤掉的收付 | 账务失败应恢复入账，不把整笔预留退款 |
| trade 唯一归属 | 每笔成交固定属于一个确定结果位置 | 外层换 batch_id 也不能再次记同一成交 |
| 批次应用屏障 | 只有连续前序都应用后才处理后续结果 | 去重、资金变化与游标共同事务提交 |
| 价差与剩余释放 | 已成交少花的钱和关闭后剩余占款的不同来源 | 全成只返价差，部分撤单还可释放对应余量 |
| 业务补偿 | 根据合法新事实做的后续动作 | 不是把未知结果或已确定成交随意反向退款 |
| 围栏与分布式完成 | 阻挡旧权威写入，并明确跨库何时算结束 | 多分片全部应用前不能沿用同库已完成宣称 |

## 把整篇文章压缩成一个故事

甲的 B1 先在账户域预留 15,025 USDT，随后提交器还没把订单送到撮合就崩溃了。系统之所以能继续，不是因为内存还记得，而是预留事务同时保存了原意图和 outbox。重启后发送的仍是绑定 R-B1 的同一个 B1；撮合必须核对所有者、限价、数量和规则，不能把这张占款证明复制成另一份订单资格。预留完成与撮合受理从来不是一次跨域提交。

甲等不到回报，要求放弃。系统将 AbortIntent 与 Place 放进同一撮合权威顺序；关闭先发生就留下墓碑，挡住之后迟到的原命令，Place 在先则保留已经确定的成交，只关闭未执行部分。若查询暂时未找到订单，或者关闭请求自身也超时，账户继续保留必要预留并恢复原身份，不能把未知解释为失败，更不能凭预留年龄到期自动退款。

在主案例里，撮合已确定 T1 和 T2，账户即使暂时落后，也必须履行 15,015 USDT 与 0.25 BTC 的交换。完整批次应用时，双方分录、余额、预留、成交去重和游标同库共同提交，甲只收回 10 USDT 价差。若另从期初推演只成交 T1 后关闭的分支，则先应用 T1，再释放余下 9,015；关闭批次先到也必须补前序。这不是宣称该固定数额先退必然透支，而是遵守当前协议的前置证明。

系统恢复时沿撮合结果、APPLIED、分录和账户版本逐段查证：源结果未应用就重试原批次，已入账但页面落后就修投影。若将甲和卖方拆到不同数据库，原先双方同事务的承诺随之消失，必须另有不可支用的待结算权益、可靠全局决定与参与方恢复规则。这里讲的是端到端设计边界，没有把协议草图或手工推演当成已完成工程。

## 第 1 层：把端到端一致性拆成三个独立提交边界

**面试官：** 甲下单以后，账户服务、撮合服务和消息投递各自有自己的数据库或进程。你说的“一致”具体指什么？哪些事情必须同时提交，哪些事情不能假装在一个事务里？

**面试者：** 我会先把完成语义分成三个提交边界。第一是账户预留事务：可用余额减少、订单 reservation 建立、对应分录和待提交订单意图一并持久化。第二是撮合域的命令裁决：Place 被纳入权威顺序，订单被接受或拒绝，产生的成交／撤单结果以完整批次和稳定序号提交。第三是账户应用事务：按照确定批次更新双方分录、权威余额、reservation 剩余量、应用结果及消费进度。

这三次提交互相不能原子化，因为在本基线中它们属于不同业务边界；预留事务提交成功不等于撮合接受，撮合批次提交成功不等于账户已入账，账户事务提交也不等于页面投影已经追上。RPC 返回、channel 收到命令、消息 broker ACK 都不是数据库提交的替代。

账户侧一次批次应用的结果身份、连续进度、所有账户分录、余额桶、reservation、APPLIED 结果和账户版本必须由同一个 `sql.Tx` 提交。结果身份仲裁、数据库锁顺序和连续 `account_version` 的递增统一遵守母题 05；本题不另造一套锁序。撮合域自己的命令顺序是另一提交边界，不能把它与账户库事务混称为同一事务。

正确性靠持久意图和可恢复交接连接三个边界：预留成功后一定有可重投的 Place 意图；撮合确定的成交批次可以重新读取或重发；账户只在自身入账事务提交后标记该结果已应用。任意阶段出错都保留足以继续履约的事实，不以“最终会对账”解释中间资金可能被双花。具体本地锁与事务语义见母题文件 05，本题只引用其本地提交保证，不重新推演锁实现。

## 第 2 层：预留成功与订单受理之间怎样保住执行资格？

**面试官：** 回到甲的 B1。甲账户域已经扣出 15,025 USDT 并返回预留成功，订单提交器还没来得及请求撮合就崩溃。重启后怎样知道要继续做什么，又怎样保证这笔钱只对应 B1？

**面试者：** ReserveOrder 的本地事务要同时写 reservation R-B1、甲 USDT 的可用到预留分录、幂等结果，以及一条待发订单 outbox。此时甲可用 4,975、预留 15,025；提交器可反复扫描 outbox 并交付同一个 `Place(B1, R-B1)`，不能重启后生成一个新 order ID 或第二条独立预留。outbox 的持久性只承诺意图不会随进程消失，不承诺撮合已经接纳。

预留凭据不是任意金额的通行证。它要与 `intent_id、reservation_id、owner_id、交易对、方向、限价、数量和规则版本` 绑定；账户域只允许本账户的对应意图消费或释放，撮合域验证提交的订单载荷与凭据一致，并防止同一意图被接纳多次。若只传一个可复制的 reservation 字符串，却允许它改账户或数量，资金资格就没有和订单语义绑定。

Place 提交器可以有多实例，只要使用同一个稳定身份并允许重复交付。outbox 的待发送、发送中、已确认状态还需要可恢复；“发出请求后把 outbox 删除”会在服务崩溃窗口丢失意图，“每次失败新建意图”则会把同一用户命令变成多份资金资格。这里暂不讨论同键返回原结果的完整 API 语义，交由母题文件 07 专门处理。

若账户预留已提交而 outbox 长期无法送达，监控可触发重试、告警和限制新风险，但不能把超时直接转换成退款。退款需要先证明该 intent 今后不可能被撮合执行；这个证明不能由 outbox 暂时为空、队列指标落后或一次 RPC 超时提供，后续要由同一撮合顺序中的 AbortIntent 给出。

outbox 的交付确认必须说明确认到了哪一层：对端收到字节只是传输确认，撮合把原意图纳入可恢复命令日志才是可靠受理证据。提交器若在对端持久化之后、回写本地已交付之前崩溃，会再次发送相同 Place，这是协议允许的重复，撮合凭原 intent 返回同一决定。如果提前删除 outbox，而对端只放进内存 channel 就重启，资金会被长期占住却找不到后续任务。回收待发记录应以可查询的受理结果或持久关闭结果为依据，并保留原身份及交接引用。

## 第 3 层：撮合域怎样证明一个预留真的对应这张订单？

**面试官：** 假设 Place 已到撮合服务。它如何验证账户预留没有被挪给别的订单？如果撮合只认订单 ID，或者只信调用方传来的预留 ID，会留下什么漏洞？

**面试者：** 撮合域必须有可验证的资格契约，不能只凭 ID 相似或调用者声称“钱已经锁了”。在这个单库账户、独立撮合裁决的模型中，可以由账户域签发不可篡改或可在线核验的资格凭据；凭据覆盖账户、intent、reservation、交易对、方向、限价、数量、规则版本及唯一代次。撮合收到 Place 时校验凭据与载荷逐项一致，并将已接纳的 `intent_id` 绑定到唯一订单记录。

例如 R-B1 是甲为 0.25 BTC、限价 60,100 建立的 15,025 USDT 预留。如果调用方拿同一个 ID 构造 0.30 BTC 订单、改账户为丁，或复制到另一个交易对，撮合必须拒绝；账户域也要在消费成交批次时再次核验订单、reservation、账户和资产归属。跨域不能因为彼此都在内部网络，就省略可追溯的关联条件。

凭据还必须有一次性／代次语义，避免已经 Abort 的旧授权被重新提交。单纯时间过期只能限制某些调用窗口，不能证明已提交的 Place 不会晚到；强制关闭要有撮合域顺序中的持久墓碑。结果批次落到账户时，账户仍要验证成交数量、价格边界、可用预留、稳定 trade ID 和批次身份；资格证明和账户会计校验是两道不同的防线。

如果采用在线核验而非自包含签名，核验接口也要定义超时语义：撮合核验失败不能当作资格存在，核验服务暂时不可用则等待或拒绝受理，不应猜测预留有效。签名凭据要校验发行方、用途、过期策略与规则版本，不能因格式正确就接受任意账户提供的伪造声明。无论采用哪种实现，账户最后仍是资产写入权威，撮合只裁决订单执行资格。

## 第 4 层：Place 与 AbortIntent 怎样在同一权威顺序中竞争？

**面试官：** 现在用户在预留成功后点击取消，而 Place 可能仍在网络、outbox 或撮合队列里。怎样关闭这张订单未来的执行资格，而不是只做一次“查询不到”的判断？

**面试者：** 我会把 `Place(B1)` 和 `AbortIntent(B1)` 放进同一撮合权威命令顺序。Abort 不是账户数据库直接退款命令，而是要求撮合域为这个 intent 作出不可逆的关闭裁决。若 Abort 先被处理，撮合域写入关闭墓碑；所有之后迟到的 Place 必须查到这个墓碑并拒绝，不能因持有原 R-B1 凭据就绕过关闭。

若 Place 先于 Abort 被裁决，撮合域先依据规则接纳订单，并可能在 Abort 之前已经产生 T1、T2 或其他成交。随后 Abort 只能关闭还未执行的剩余资格，不能撤回已确定的成交事实。墓碑需要记录 intent 及命令顺序／代次，保证撮合重启、主备切换和重复请求时仍能判断哪个命令先后；若清理墓碑，必须另有旧代次永久拒绝机制，不能只靠 TTL。

这条顺序必须覆盖所有能执行 B1 的入口。如果有快速通道、人工撮合入口或重放工具不查同一关闭状态，Abort 墓碑就不是全局资格关闭。Abort 自身超时也属于结果未知：继续查询或重试同一个 Abort 身份，期间保持资金预留；不能因一次 RPC 超时、查询副本暂时未找到订单或等待时间过长就释放。

Place 和 Abort 的顺序必须由撮合权威存储或可证明等价的序列器决定，不可依赖两个 Go 实例本地时间戳比较。时钟先后、HTTP 到达顺序或消息队列不同分区的到达顺序，都不自动等于业务裁决顺序。若有主备切换，旧主的写入还要被围栏，避免两个撮合权威各自产生互相矛盾的“Place 先”与“Abort 先”。

关闭结果应带上被关闭的 intent、reservation 绑定、裁决位置、此前已确定成交的截止位置，以及实际关闭的剩余数量。账户据此证明自己没有遗漏前置义务，而不是接受一句没有水位的“已取消”。对于确定拒绝的 Place，同样要保存该意图不再可执行的终态，重复 Place 返回原拒绝，不能等配置变化后又接纳。重新下单需要新意图、新资格，旧拒绝与旧墓碑不被覆盖。这样正常拒绝、用户放弃和迟到命令才都遵循同一身份生命周期。

## 第 5 层：撮合已经确定成交，账户账本还没更新算不算不一致？

**面试官：** 撮合已经提交 B1 全成以及 T1、T2，但账户服务还没有应用结果，甲的查询仍显示 4,975 USDT 可用、15,025 USDT 预留和 0 BTC。是否应该立刻把预留清空，让账户追上订单状态？

**面试者：** 这是一种明确的跨域处理中状态，不等于业务事实丢失，也绝不代表可以提前清空。撮合提交的 T1、T2 已构成确定履约义务：甲应支付 6,000 和 9,015 USDT，分别从乙、丙取得 0.10 和 0.15 BTC。账户侧原预留继续占住这些资产，直到对应完整批次在账务事务内应用。

如果此时仅因订单全成就把 R-B1 全部释放，甲可能已经把 15,025 USDT 用到另一笔订单；之后账户再履行 T1、T2 就会缺少买方资金。反过来，如果先扣甲的钱再单独给乙或丙入账，进程崩溃会造成半边结算。因此应用批次必须原子提交双方各自资产变化、预留消耗／释放、账务结果和本地消费进度。

完整批次是确定事实的传递单位。账户校验来源、`batch_id`、序号、载荷摘要、各笔 trade 身份和涉及预留，再一次性入账；若校验不通过，整个应用事务失败并保留待履约预留，不能把订单改回未成交，也不能跳过结果流位置。每个 `trade_id` 必须在权威来源范围内唯一归属到一个确定批次，且批次身份与载荷摘要永久绑定；同一 trade 出现在另一个批次、同序号出现不同内容或批次重构时 trade 集合变化，都应作为冲突隔离，不能让两个不同 batch key 各自通过批次去重而重复记账。消息可以重复投递，账户按稳定结果身份返回原应用结果。

应用事务先仲裁本批结果身份，确认是新批次后再按母题 05 的锁序取得结果流游标，并要求 `seq = last_applied_seq + 1`；重复身份核验原载荷并返回原结果，不推进第二次。新批次的序号、trade 唯一归属、完整内容和账户资金变化必须同源校验，入账分录、权威余额、reservation、APPLIED 结果、游标和相关账户版本在同一个 `sql.Tx` 提交。缺号等待补齐，内容冲突停流；不能先推进游标或先持有游标，再反向争用结果身份。身份载荷与提交未知后的恢复遵守母题 07。trade 身份的唯一性必须由权威撮合结果来源保证，并在账户消费边界再次校验：例如在 `source_id`／交易对流作用域下，对 `trade_id` 建唯一归属记录，记录其唯一 `batch_id`、结果序号和规范化载荷摘要。第一次成功应用时，这些归属、批次身份、分录、余额、预留、游标和账户版本一同提交。重复收到同一 trade 与同一 batch 是可识别的重放；同一 `trade_id` 出现在不同 batch、同一 `batch_id` 携带不同 trade 集合、或相同序号带来不同内容，都属于来源冲突，必须整批回滚并隔离，不能因外层 batch key 不同而再次记账。

对主案例，账户应用完成前仍可能显示 4,975 可用与 15,025 预留，这个视图必须明确标出账务待应用或按账户版本说明落后位置。它不是可支用总资产以外的一笔额外资金，也不能与“成交待交割”数量重复相加。查询域可以解释进度，但不能据此批准新的支出或自行释放余额。

## 第 6 层：全成时到底可以释放多少，怎么闭合预留？

**面试官：** 甲的 B1 全成，两笔成交实际支付共 15,015 USDT，小于初始预留 15,025。你怎样同时履行成交、交付 BTC，并把释放金额算对？

**面试者：** 以限价预留而实际成交价低于限价的 T1 为例，甲为 0.10 BTC 占用 6,010 USDT，但实际只需付乙 6,000，因此 10 USDT 价差可以转回甲可用。T2 成交价等于限价，对应的 9,015 USDT 全额支付给丙，不产生价差。本例零费用，不会有手续费科目参与抵消。

T1、T2 的账户应用必须按确定成交事实同时转移 USDT 与 BTC：甲的 USDT reservation 转出 6,000 给乙、9,015 给丙；乙的 0.10 BTC reservation、丙的 0.15 BTC reservation 转给甲可用。T1 的 10 USDT 从甲预留转回甲可用。所有变化与 R-B1、R-S1、R-S2 的明细和批次 APPLIED 结果共同提交，而不是先清空买单预留再从普通可用扣钱。

于是买方 reservation 闭合为 `15,025 = spent 15,015 + released 10 + remaining 0`；乙的卖方预留为 `0.10 = spent 0.10 + released 0 + remaining 0 BTC`；丙为 `0.20 = spent 0.15 + released 0 + remaining 0.05 BTC`。甲得到 0.25 BTC、可用 4,985 USDT。这里 `spent` 只代表转给对手方的金额，不含价差返还；`released` 包含价差或经裁决确定撤单的部分，不能用订单终态粗暴把 initial 全部标为 released。

我会在每个 reservation 维度核对初始、已花、已释放和剩余量，在账户桶维度核对 `order_reserved = sum(remaining)`。同时按币种核对同一 journal 内转出与转入闭合。若只检查甲最终 USDT 总额，仍可能把 10 USDT 归错到另一张订单，或把丙的 0.05 BTC 预留错误清掉；总数吻合不是归属正确的充分条件。

这些数值推导按人类可读单位展示，实现仍使用总览的整数最小单位、合法价格和数量步长及防溢出的中间乘法。T1 用限价乘已成交数量算出应解除的占用，再分成实际支付和价差；不能用成交均价乘整单数量倒推每次释放，也不能先对每笔金额任意取整再用尾差凑平。本例两笔成交同属完整批次，中间的 T1 状态只是事务内工作副本，外部只应看到提交前或提交后的状态。若改为多个批次、费用或非整除步长，就要明确改变条件并重新定义金额分配规则。

## 第 7 层：Abort 已关闭订单，为什么仍要先应用成交再释放？

**面试官：** 假设 Place 先于 Abort，B1 已经成交 T1 的 0.10 BTC，之后 Abort 关闭剩余 0.15 BTC。若撤单结果比 T1 的账务批次先到，账户服务可否先返还 9,015 USDT？

**面试者：** 本协议不允许这样做，但必须讲对理由。在这个明确的数字变体中，15,025 先释放 9,015 后仍有 6,010，恰好覆盖 T1 的限价占用，不能声称这一次释放必然造成资金不足或双花。真正的问题是账户跳过了前序成交应用屏障：T1 未应用时，本地 R-B1 仍表示完整 15,025，账户尚未通过已应用事实证明其中多少已花、多少价差已释放、多少才是可撤余量，不能单凭晚到的撤单金额改变累计状态。

T1 应先消耗 6,010 限价占用，其中 6,000 转给乙、10 价差返回甲可用；之后确定撤单的 0.15 BTC 对应 9,015 USDT 才能释放。最终 `initial 15,025 = spent 6,000 + released 9,025 + remaining 0`，其中 released 由 T1 价差 10 和撤销剩余量 9,015 构成。甲最终有 14,000 USDT 可用、0.10 BTC 可用，B1 预留为零。

为了实现先后关系，撮合结果必须有不可跳过的顺序，账户应用游标与本批账务变化同事务提交。若撤单批次先送达但前序成交批次缺失，账户应等待并补齐前序，而不是看到撤单就退钱。即便账户收到的是一个“订单最终状态=取消”的快照，也要确认其前置成交义务已处理；订单域终态不是可释放金额的计算公式。

这个变体与主案例互斥：主案例 B1 全成，不再发生撤单释放；部分成交撤单则只有 T1，不包含 T2。把两者混在同一状态继续累计，会把 15,025 预留同时按全成和撤单两次结算。面试中需要先说明变体改变了哪些事实，再做数值推导，确保每一份初始预留只被消费或释放一次。

假设流游标为 41，T1 属于批次 42，关闭结果属于 43。43 先到时可以持久缓存或保证能重取，但不能把游标从 41 直接改成 43，也不能提前写释放分录再声称稍后会补齐。待 42 的完整账务提交并推进至 42 后，43 才有资格在已更新的 R-B1 上释放 9,015。这个设计以阻塞换取明确的前置证明；若要允许局部乱序，必须另行引入可证明的逐订单依赖和金额归属协议，而非在当前连续游标模型里加一个例外。

## 第 8 层：部分失败、重投与跨域补偿各自能做什么？

**面试官：** 预留事务已提交，Place 可能未送达；撮合已提交成交，账户入账可能失败；账户可能已经提交却没来得及 ACK。你会设计一个分布式事务把它们锁在一起，还是用补偿事务撤回已经完成的阶段？

**面试者：** 在当前基线中不假设跨账户域和撮合域的分布式原子事务。我会让每个域在本地先持久化自己的权威状态，再通过可靠 outbox／可重读结果交接。账户预留及 Place outbox 同事务提交；撮合命令与 ResultBatch 同撮合域提交；账户应用结果、余额分录、预留变化及 APPLIED 位置同账务事务提交。交接可以至少一次，业务身份让重复传递可识别。

失败窗口按事实来源分类处理。Place 发送前崩溃，扫描 outbox 继续投递；Place RPC 超时，查询或重试原身份；撮合批次已确定而账户数据库暂不可用，保留批次并重试，不释放预留；账户事务提交前崩溃，数据库回滚整批；账户已提交但回执丢失，重投同一批次返回原 APPLIED。对确定成交，不存在“超时了就反向退款”的安全补偿，因为对手方可能已经基于成交继续使用资产。

补偿只适用于业务上确实可逆、且有权威新事实的动作，不能用它遮盖提交未知。AbortIntent 是关闭未来资格的业务命令，并非撤销已经成交的账务；冲正是引用原 journal 的新账务事实，也不等价于抹掉成交。若需人工修复，应保留原批次、差异原因与审批链，按追加事实修正，而非覆盖余额。完整幂等结果与未知结果协议归母题文件 07，避免在此重复定义存储表和错误码。

若结果消费持续失败，系统应通过监控最老未应用批次、队列积压和 reservation 年龄发现问题，并限制可能扩大风险的新订单。限流和熔断不能删除已确定成交事实；恢复时要重新取回同一批次、用同一身份继续履约。恢复任务也必须核对原载荷、前序应用水位和各预留归属，不能因为人工触发就绕过正常账户协议。只有确定的撮合拒绝或关闭结果并满足前置应用水位，账户才可释放对应未消耗部分。

## 第 9 层：怎样恢复“订单已全成，资金预留仍挂着”的状态？

**面试官：** 运营看到 B1 全成很久，甲的 15,025 USDT 还预留着。你怎么判断是账户消费者落后、结果批次丢失、已入账但回报丢失，还是账务真的不一致？

**面试者：** 我先对齐权威位置，而不是根据订单页面直接修改余额。查撮合域已提交的批次身份、内容和序号；查账户结果流最后应用序号、该批 APPLIED 和 journal；查 R-B1 的 `spent/released/remaining`、账户 USDT 余额及这些分录；最后看查询投影追到了哪个账户版本。不同层的当前时间戳不能直接比较，要按相同业务身份和水位核验。

如果撮合已提交 seq 42，而账户游标仍是 41，且 R-B1 保持 15,025，这表示结果尚未应用：补取并重试 42，期间保留资金。如果账户已经 APPLIED 42、甲余额正确为 4,985 USDT 和 0.25 BTC，但页面仍显示旧值，修复查询投影即可，不重做账务。如果账户游标声称已越过 42，却没有 journal、应用结果或对应余额变化，就违反了本地共同提交假设，必须限制风险并调查备份恢复或数据库完整性，不能把这种状态正常化成“异步延迟”。

持续故障时可以暂停相关新订单、限制交易、告警最老未结义务，确保后续可恢复；但这些措施是在控制新风险，不是把既有成交取消。账务恢复需要一致恢复余额、分录、reservation、幂等结果和消费游标，再以撮合持久批次补齐缺口。页面投影、消息通知和对账是恢复证据或展示机制，不是释放资金的业务授权。

同一个截止点的对账应比较撮合已提交的义务集合与账户 APPLIED 集合，并将缺口、账户已应用但撮合源不可取、重复批次和投影延迟区分记录。若撮合结果源本身不可恢复，不能凭订单状态摘要自行重建所有逐笔金额；应先限制相关业务，再从权威日志、备份和审计证据确认事实。直接改余额会破坏分录与 reservation 的可解释性。

扫描最老 reservation 只是在找可能卡住的交接，不能单独授权释放。扫描器应沿 intent 查 Place 可靠受理、关闭裁决、前序结果水位及账户 APPLIED 证据：未可靠受理可继续原 Place 或发 Abort；已成交未应用应恢复应用；已关闭且前序已应用才提交原身份的释放动作。每种处理都留下原因、关联身份与进度，使人工接管也遵守同一规则。扫描间隔和超时阈值用于告警及恢复优先级，不改变成交义务，也不是一份预留自然失效的经济规则。

## 第 10 层：本地事务不再覆盖全链路时，保证具体改变什么？

**面试官：** 现在把甲、乙和丙按用户拆到不同数据库。你还能说一笔 T1 的 USDT 与 BTC 转移在同一个本地事务中完成吗？若不能，系统的“完成”应如何重定义？

**面试者：** 不能。分库后，甲扣 USDT、乙收 USDT、乙扣 BTC、甲收 BTC 至少涉及多个本地事务；原来同一账务库里一次 PostgreSQL Tx 的原子性不再覆盖全链路。增加消息重试或幂等键只能使各方重复应用时可识别，不能把多库提交变成同时成功。对账可以发现差异，也不能阻止某个目的端过早把尚未确认的权益拿去消费。

如果真改变这个前提，就要明确分布式结算状态机：每笔 settlement 有稳定身份、固定参与方和资产数量；来源端先锁定不可重复使用的资金；目的端初始收到的是不可支用的待结算权益；所有必要准备状态满足后，受围栏保护的协调者持久提交唯一决策；参与分片按该决策幂等完成本地分录，并记录可恢复进度。决策提交之后某分片故障，必须继续履约，不能因等待超时改为退款。需要清算账户或在途科目时，各本地账仍须按币种平衡并可对账。

这会带来全局决定已提交、部分分片尚未可见的处理中窗口。如果产品要求读者永远只看见“全部完成”或“全部没发生”，查询层也必须参与屏障或等价协议，成本与延迟都改变。所有参与方都已应用之前，只能说明结算处理中，不能沿用原本地事务模型的完成宣称。本文基线没有分片，因而只说明保证何处改变，不把协议草图当作已实现方案；这类规模、恢复和分片边界留给母题 12。

扩展时必须明说改变的是“交易提交”的含义：同库基线中，账户批次事务提交即可说账户账务应用完成；分布式结算中，全局决定已写入但个别参与方尚未应用，只能说协调决定已提交，不能说各账户都已完成。若产品接受异步完成，就需要显式处理中状态和不可支用资产桶；若不接受，则存储或协议必须提供所要求的跨分片原子可见性，不能靠措辞模糊实际差异。

## 本题收束

### 机制与易错边界

- 三个独立提交边界是账户预留、撮合裁决及完整结果批次、账户批次应用；RPC 与消息 ACK 都不是提交本身。
- 预留凭据绑定业务意图和完整订单载荷；撮合资格与账户账务校验分别负责阻止不匹配执行和错误入账。
- Place 与 AbortIntent 必须在同一撮合权威顺序竞争；Abort 先则写墓碑拒绝迟到 Place，Place 先则保留已确定成交并只关闭剩余资格。
- 已确定成交是履约义务。账户应用之前不能因订单全成、查询暂时未找到或超时而释放整笔 reservation。
- 主案例闭合为 B1 `15,025 = spent 15,015 + released 10 + remaining 0`；部分成交再撤销时，前序成交应用后才释放 9,015 剩余限价占用。
- 对确定事实采用可靠重投与原身份应用；不能把退款或反向账务当作任何网络超时的通用补偿。
- 一旦跨库，单个 PostgreSQL 本地事务就不再覆盖买卖双方；必须重新定义 settlement、待结算权益、全局决定和最终完成条件。

### 反例

```text
R-B1 已提交，甲可用 4,975、预留 15,025
    ↓ Place 延迟；一次查询副本暂时找不到 B1
    ↓ 扫描器错误地释放全部 15,025，甲又可用 20,000
    ↓ 甲将其用于别的订单
    ↓ 原 Place 迟到，旧凭据仍能被接纳并成交
```

若答案只能说“加锁、重试、最终对账”，却不能指出是哪条持久墓碑阻止迟到执行、谁有权创建它、前序成交在哪个水位已被应用、账户何时才能释放，这条端到端资金链还没有闭合。验证应覆盖 Place/Abort 竞争、乱序、消费者故障和重复投递；本文给出设计预期，不声称相关实验已经运行或通过。
