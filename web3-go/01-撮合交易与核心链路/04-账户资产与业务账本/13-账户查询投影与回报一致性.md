# 大问题 13：余额查询、私有推送和报表落后时怎样解释完成状态？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文范围说明：在同库现货账务提交之后，解释查询、缓存、私有推送与报表如何追上权威状态。版本号均有各自作用域，文中接口是设计示例，不代表已有投影系统或延迟实测。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 账务 APPLIED | 账户已经提交该批资金变化的状态 | 不等于查询更新、消息送达或用户看到 |
| 权威余额与投影 | 一个决定能否花钱，一个为阅读整理数据 | 缓存再方便也不能裁决扣款或回写账本 |
| account_version | 某账户每次资产事务的统一版本 | 同事务覆盖全部相关币种，不等于撮合 seq |
| as_of_version | 说明本次回答读到了哪个账户位置 | 页面与报表可各自落后，但不能隐瞒截止点 |
| min_version | 调用者要求至少读到某个版本的令牌 | 未追上就有限等待、转权威读或明确返回滞后 |
| 读己之写 | 刚完成动作后能要求看见相应已提交结果 | 由读取版本保证，不靠再次发资金命令 |
| 快照—增量交接 | 先拿一个完整状态，再接其后的变化 | 必须有明确水位，避免订阅切换时漏事件 |
| delta 事件 | 表达相对上个状态增减多少的消息 | 缺前序不能直接相加，否则会得到错误余额桶 |
| 完整事务账户事件 | 同时携带一次事务内全部资产变化 | USDT 与 BTC 不能各到一半却宣称全账户追上 |
| last_seen | 客户端最后连续确认的事件位置 | 只服务重连补发，不反过来证明账务已提交 |
| 至少一次通知 | 允许重复发送，以恢复可能丢失的回报 | 下游按身份去重，投影与自身进度共同提交 |
| 重新快照 | 历史事件过期或缺口无法补齐时重新建基线 | 不能直接跳到最大 delta 版本继续累加 |
| 缓存版本比较 | 只让更新版本替换旧缓存状态 | 防止晚到旧事件覆盖新余额 |
| 私有流授权 | 每次读快照、补发和订阅都验证账户权限 | 不可猜令牌和客户端自报 account_id 都不是授权 |
| 影子投影重建 | 新副本完整构建并核验后再切换读路由 | 不让用户读半成品，更不调用资金写接口修展示 |

## 把整篇文章压缩成一个故事

甲的 B1 已在权威账务库完整入账，账户有 4,985 USDT 和 0.25 BTC，手机页面却仍停在旧数。系统先查看页面的账户版本，确认这是查询投影没追上，而不是再给甲执行一次成交。订单全成、账务 APPLIED、页面追上和推送被看见是不同进度，接口要把各自位置说清楚；甲若带最低读取版本查询，服务不能超时后偷偷返回旧数却声称满足要求。

随后甲断线重连。系统从他最后确认的连续版本继续补发：在本文独立编号示例里，V47 是期初，V48 是完整预留事务，V49 是完整成交入账。若网络先送 V49，客户端不能直接把其中可用增加 10 的变化加到期初 20,000 上，否则会得到错误的 20,010 和负预留。它必须补齐 V48，或重新获取一致快照；同一版本内部的 USDT、BTC 变化也要一起应用，不能只展示一半。

账户通知通过与账务一起保存的 outbox 交付，发布后崩溃可能再次发送，所以投影要按事件身份去重，并将自身数据与消费进度共同提交。历史事件若已过保留期，就明确要求重新快照，而不是假装能从任何旧位置恢复。缓存接收晚到事件时按版本比较，不能让旧余额覆盖新余额；即使甲看见旧的 20,000，再提交订单仍由权威事务检查当前资金，展示延迟不能穿透扣款边界。

甲换设备时还要重新认证，恢复令牌绑定的账户与权限也重新校验，不能改成乙的账户就拿到别人的余额。报表、页面和设备进度各自说明来源，重建副本核验后再切换，始终不回写账本。这个故事解释的是可恢复且不越权的读模型，文中的版本和算式只是设计示例，不是已经运行的推送实验或延迟报告。

**流程位置与核心机制：** 本题位于账户账务提交之后，处理查询 API、账户变更推送与报表等派生视图的进度差异。核心是给用户可解释的版本与完成语义、在断线后补齐变化，并确保投影滞后不会反向改变资产裁决或泄露他人数据。

**必要前提：** 统一采用专题总览的链下托管 BTC/USDT 现货基线：单一 PostgreSQL 账务权威，多实例 Go 服务；甲下单预留 15,025 USDT，T1／T2 共成交 0.25 BTC，实际支出 15,015、返还价差 10。账务应用后甲可用 4,985 USDT 和 0.25 BTC，B1 预留为零。订单成交、账务 APPLIED、查询投影追上与用户收到推送是不同进度。下文不声称具体产品已经实现了这些接口。

## 第 1 层：账户余额已经入账，为什么页面还会显示旧数？

**面试官：** B1 的成交批次已经在账本提交，甲查询页面却仍显示下单前的 20,000 USDT。你会认为账本错了，还是页面错了？系统应如何定义这几个状态？

**面试者：** 我先查账户域的权威余额版本和对应 journal，再查查询投影的消费位置。若同一账务事务已经提交甲的 4,985 USDT、0.25 BTC 和账户版本 V42，而页面投影只到 V41，那么账本事实已完成、页面视图滞后；不能再次扣款或再执行一次成交来“修页面”。

我会把用户能观察到的阶段分开：订单域可能报告 `FILLED`；账务状态可能为 `PENDING` 或 `APPLIED`；账户权威版本表示哪些资产事务已经提交；查询投影版本表示查询服务已经应用到哪里；推送游标只说明某个连接已交付到哪里。它们的生产者、身份和提交条件不相同。

对订单全成但账务未完成的中间阶段，页面可以显示订单已成交、结算处理中，但不能把旧可用余额当成最新可花资金，也不能预先把未入账 BTC 加进权威可用余额。查询接口可以返回 `as_of_version` 或 `as_of_seq`，明确余额截至哪个提交事实。

若余额来自权威库的强一致查询，可以读取最新已提交版本，但仍要处理读副本延迟与缓存；若来自异步投影，就要让接口明确一致性级别。系统不能一边用异步视图，一边对外暗示它总是强一致。

因此“页面数旧”与“资产事实旧”是不同故障。先定位投影版本，再采取补投、重建或路由权威查询；任何展示补偿都不能写回账务余额。

## 第 2 层：仅返回一个余额版本，怎样保证调用方知道它覆盖了什么？

**面试官：** 你刚才建议返回 `as_of_version`。甲的账户有 USDT 和 BTC，订单回报又来自撮合流，单个整数版本怎么表达多路进度？

**面试者：** 先限定版本的作用域。账户域可以为每个账户维护单调增加的 `account_version`，每次已提交的资产事务使相关账户版本前进；查询结果明确“甲账户截至 V42”。它只说明甲账户派生视图读到哪个账户状态，不自动代表撮合域或其他账户也到相同阶段。

如果业务状态还需要跨流关联，就返回一组有名字的版本，而不是伪造全局序号。例如：

```text
order_status: FILLED
trade_stream: market-BTCUSDT / seq 42
account_status: APPLIED
account_version: account-甲 / 1087
projection_version: account-甲 / 1087
```

若账户有多个独立流并行更新，投影必须跟踪它所需流的水位向量，或者消费账户域已经定义好的统一提交版本。只拿最大序号会掩盖缺口，例如 42 未处理但 43 已处理；只有连续完成位置或依赖集合完全满足，才能说“已追上”。

账户版本应与余额、分录、reservation、幂等结果共同提交。若承诺账户版本连续，就在同一事务锁定全部相关余额桶、reservation 后，再按 owner_id 固定顺序锁定涉及账户的版本行并递增，让每个版本都有完整账户事件；所有写路径都遵守这一顺序，不能拿到账户版本锁后再回头增加余额锁。不能直接使用可能因回滚跳号、又不按提交顺序分配的数据库 sequence 当作连续版本。若版本先提交，余额后提交，调用者拿到版本也找不到对应事实；若余额提交后版本未动，投影无法判断需不需要补读。版本的线性化边界就是账户账务事务提交。

API 请求可以携带最低读取版本 `min_version`。若投影已达到它，返回投影结果；若尚未达到，服务按产品策略等待有限时间、从权威库读取或返回明确的 `projection_lag`／重试令牌。不能无限等待，也不能在超时后悄悄返回旧余额而仍声称满足了最低版本。

调用方要用这个令牌控制重复行为：读到旧余额不能据此再发资金命令；资金命令仍通过幂等身份在权威写路径执行。读版本解决“看到了什么”，不负责“资金是否又扣了一次”。

## 第 3 层：余额快照与流水怎么组合，重连后如何补齐？

**面试官：** 用户看到 V42 的余额，之后断网；回来时账户已经到 V50。你推送完整流水还是只发最新余额？如何避免快照和增量之间有洞或重复？

**面试者：** 我会提供可恢复的同步协议，而非依赖长连接永不掉线。客户端请求账户快照与其对应的版本 V；之后订阅严格晚于 V 的变更。若订阅先建立、快照后读，期间事件会重复或发生交错；若快照先读、订阅后建立，中间事件可能丢失。因此服务端需要一个可证明的快照水位和从该位置继续读的变更日志。

一种设计是客户端提交最后确认的连续账户版本，服务端从持久事件源补发 `version > last_seen` 的变化；事件带 `account_id、account_version、event_id、asset、delta或余额视图、business_ref`。若事件保留期已过或版本缺口无法补齐，服务返回“需要重新取快照”，而不是跳到当前最大版本继续推送。

推送可能重复，所以客户端以账户版本和事件身份去重；遇到同一版本内容冲突应停止应用并重新同步。若一个事务为甲同时写 USDT 与 BTC，投影与事件必须避免展示不一致的半边状态。可以推送一个包含完整事务变化的账户事件，也可以用事务组 ID 暂存各条腿，直到完整组到齐后再原子更新本地视图。

如果对一个连接只承诺“尽力实时通知”，明确推送不是持久账务事实；客户端仍应以账户查询和恢复令牌为准。若承诺可断线补齐，则事件源要在承诺保留期内持久保存，并处理慢消费者、限速和重新快照成本。

快照加增量必须存在一个严格交接点。单纯先 `SELECT balance`，再订阅 Kafka topic，无法证明中间没有遗漏；要使用同事务 outbox／可重放日志、数据库快照水位或等价的协调机制，并说明事件在该边界上如何创建和保留。

## 第 4 层：私有推送晚到或乱序，能否直接按时间戳应用？

**面试官：** 你用版本补发。现在 V49 的账户余额事件先到，V48 后到；或者客户端手机时间比服务器慢。应用侧用时间戳排序可以吗？

**面试者：** 不能用客户端时钟或事件生成时间决定资产状态顺序。时钟偏移、网络重试和多个生产者都会改变到达顺序；客户端应按权威账户版本检测连续性。若当前视图在 V47，收到 V49 就先缓存／请求缺失的 V48，不能将 49 应用后再把 48 的旧余额覆盖上去。

若事件是完整余额快照而非 delta，仍需比较版本。V49 快照可以覆盖旧快照，但前提是它明确包含账户 V49 的全部相关变化；若只是某个资产的局部变化，必须有资产子版本或完整事务组边界，不能把别的资产遗漏后称为全账户版本。

对 delta 事件，版本连续尤为重要。举例时将账户版本编号独立于撮合结果序号：V48 是本例预留事务，V49 是整个 T1/T2 入账事务。漏掉 V48 的“可用 -15,025、预留 +15,025”，直接在期初快照应用 V49 的“可用 USDT +10、预留 USDT -15,025、可用 BTC +0.25”，就会得到错误资产桶和负预留。要么拒绝越过缺口，要么从权威当前快照重新基线。对重放事件要去重；相同 event_id 同内容无操作，同版本或身份不同内容则触发一致性错误。

服务器回报“已推送”不代表客户端收到了，更不代表客户端持久化应用。协议可以使用确认游标，但客户端确认只服务重放位置，不能反馈为账务提交进度。客户端重装、设备多端和令牌过期都要能通过账户查询恢复。

时间戳仍可用于展示和诊断延迟，但不作为先后裁决。业务顺序来自账户权威提交版本，撮合序号只说明撮合流顺序，跨流情况下不能未经映射就当成账户版本。

## 第 5 层：通知 outbox 与投影消费者怎样避免“漏发”假象？

**面试官：** 你要求事件能补齐。账户事务提交了，但通知服务没收到；如果 outbox 也在账务事务里，发送成功后标记发送前又崩溃，还是会重复啊？

**面试者：** 是的，outbox 解决的是“账务提交与通知意图不一致”的丢失窗口，不承诺消息只发送一次。账户事务内写 journal、余额、account_version 和 outbox 记录；事务提交后，后台发送器扫描未投递项，向下游发布。若发布后、标记完成前崩溃，重复发布是允许的，下游按事件身份和账户版本幂等消费。

如果把 outbox 标记已发送与网络发送做成两个独立动作，必有一个顺序产生不确定窗口：先标记可能丢通知，先发可能重复通知。因此接受至少一次交付，再让下游去重。对外公开的事件日志若需要长期重连补发，还必须有持久保留、归档或账户快照重置协议；短期 outbox 发送完删除，不等于用户可从任意历史版本恢复。

投影消费者在本地事务中推进自身消费位置并更新投影。若消费源允许重放，同一事件重复时不得二次累计 delta；不同投影可以独立消费，但它们都不能作为扣款的权威来源。投影崩溃后从自身提交位置重建，发现源保留期不足则从权威快照重新开始。

outbox 堆积需要监控最老年龄、未发送数量、重试错误和死信状态。发送器失败不能回滚已完成账务，也不能把事件静默丢弃；当投影或通知长期不可用时，账务可在容量允许范围内继续提交，达到有界存储阈值后则应背压或降级新业务，而不是无限积压。

因此，账务完成定义在账务事务提交；通知完成定义为某消费者达到某版本；客户端可见是另一个阶段。状态 API 应分别呈现这些进度。

## 第 6 层：读副本和缓存加速，会不会把旧钱当成可用余额？

**面试官：** 为了降低查询压力，你把余额读到 Redis 或 PostgreSQL 只读副本。甲刚入账，立即从副本查到旧 20,000，再提交一笔买单。怎么防止超支？

**面试者：** 绝不以读副本或缓存的余额裁决资金可用性。下单预留命令必须在权威写库中基于当前提交状态原子检查并占用资金，使用行锁或条件更新；旧读最多造成界面暂时滞后，不应让第二笔业务通过资金检查。

读路径可以按场景提供不同一致性：普通账户页返回投影版本；用户刚完成账务后带 `min_version` 读己之写，可等待副本追上、临时读主库或返回明确尚未追上的状态。不能只把余额值缓存而丢掉账户版本，否则无法判断缓存新旧。

缓存更新也要防乱序覆盖：事件带单调版本，原子比较后只接受比当前更高的版本。多资产一笔账务事务需要统一账户版本或事务组，避免 USDT 已到 V42、BTC 还留 V41 却对外称“全账户 V42”。缓存丢失可重建；缓存内容不可以回写权威账本。

只读副本的复制位点要与账户版本建立可查映射。如果数据库副本满足某个 WAL 位点，却不能把该位点可靠映射到所需账户版本，API 仍不能假定已追上。主库降级时，强一致读和写入应明确失败或等待，不要在无权威来源时把旧余额当新事实。

最重要的反例是：页面旧余额让用户误以为有 20,000，但权威预留事务必须读到已经提交的 4,985 并按其合法新余额裁决。若同一条 API 既展示缓存又直接在应用层按缓存值做扣款判断，读写分离就穿透了账务不变量。

## 第 7 层：私有事件如何做账户隔离与重连鉴权？

**面试官：** 你为用户提供账户事件流。客户端提交 `account_id=乙` 订阅，用户甲能不能改参数读乙的余额？如果用不可猜的事件 ID 就安全了吗？

**面试者：** 不能把客户端提供的账户 ID 当作授权凭据，也不能把难猜 ID 当成访问控制。服务端从经过认证的主体和授权关系确定可访问账户集合；每次快照、历史补发、实时订阅和游标恢复都重新执行权限检查。

事件查询要限定主体与账户，避免通过通用事件 ID 查询任意交易对手信息。甲自己的成交回报可以按产品规则显示对手方匿名信息，但不能因此获得乙的账户余额、其他订单或内部地址。服务端推送分区和缓存键也必须含有正确租户／账户范围，防止多租户缓存串读。

游标或恢复令牌应绑定账户范围、主体／授权上下文、版本和有效期，并防篡改；即便如此，权限发生撤销后仍需重新授权，不能把长寿命 token 视作永久权限。日志避免记录完整敏感载荷与密钥，审计谁在何时以何种权限读取何种范围。

WebSocket 重连时重新认证，订阅与历史补发经过同一授权检查。断线前的确认游标只说明进度，不证明用户仍有读取权。权限缩减时，系统应停止后续推送并按保留政策处理客户端缓存；服务端无法让已被用户合法下载的数据从其设备上消失，因此应尽量减少超出业务需要的敏感字段。

错误或越权订阅必须拒绝，不返回“是否存在账户乙”的旁路信息。安全边界覆盖 API、推送、导出和运维查看，不能只在 Web 页面隐藏账户选择器。

## 第 8 层：多个投影相互矛盾时，怎样定义完成并验证恢复？

**面试官：** 用户页显示 V50，日结报表只到 V48，另一设备收到了 V51 推送。你如何告诉用户哪一个是最终数，怎样证明投影可恢复而不会影响账本？

**面试者：** 先分别报告来源和进度，不选一个“看起来最大”的数作为万能真相。账户权威当前版本和余额决定资金；订单域决定订单状态；报表有自身快照截止点；设备推送有该设备的连续确认位置。只有账户账务事务提交后的权威状态能裁决资金，不同投影落后意味着各自刷新或补齐。

对于 V50 页面和 V48 报表，我会检查各自明确的 `as_of_version`，确定差的两个版本是否在报表的数据范围内，再补消费或重建该报表。设备收到 V51 不等于设备以前连续收到 V49、V50；若是完整快照可基于版本覆盖，若是 delta 必须检查连续性并补齐。

投影设计要求事件可重放、转换逻辑有规则版本、消费位置与投影更新本地原子提交。重建时从一致账户快照和其后的连续事件开始；先构建新投影、校验版本和金额，再切换查询路由。不能清空生产投影后边重建边让用户读到半成品，也不能让重建任务调用资金写接口。

验证案例至少包括：批次重复、V49 先于 V48、快照后断线、事件过期、消费者提交后确认前崩溃、缓存旧版本覆盖新版本，以及主体授权被撤销。对每个案例规定应拒绝、重试、补发或重新取快照，并检查权威账户余额保持不变。

可观测性报告投影 lag 的版本差与时间年龄、最老 outbox、事件缺口、重建进度、重连成功率和越权拒绝，不以单一“WebSocket在线”指标代表账户可见。阈值按实际产品承诺配置；本文没有运行投影系统或提供延迟实测。

## 本题收束

- **讲透的机制：** 账务与投影的权威分离、账户版本及多流水位、快照—增量交接、至少一次事件与消费幂等、`min_version` 读己之写、读副本隔离和私有数据授权。
- **最容易答错的边界：** 消息已发送不等于客户端已看见；最大版本不等于连续完成；缓存新鲜不能替代权威资金校验；订单全成不等于账务 APPLIED；不可猜令牌不等于授权。
- **验证反例：** 客户端最后确认 V47（甲期初 20,000 USDT），V48 是完整预留事务，V49 是整个 T1/T2 入账事务，网络却先交付 V49。若客户端将其 delta 直接加在期初快照，会误得 20,010 USDT 可用及负预留，而不是正确的 4,985 USDT 可用。正确协议必须识别缺口、补齐 V48 或重新取一致快照；每个版本内部仍应原子包含全部相关资产变化，不能把同一账务事务的扣款和价差拆成两个独立提交版本。
