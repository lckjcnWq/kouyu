# 大问题 5：多实例同时扣款、预留和释放，怎样防止超支？

## 先看懂：关键词大白话解释

本文范围说明：多个 Go 实例共同访问一个 PostgreSQL 账务库，以 READ COMMITTED 下的受保护读写讨论现货资金竞争；不将本地锁扩展成跨库原子保证，也不提供实测吞吐结论。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 读—判定—写 | 看余额、判断够不够、再修改的一整套动作 | 必须整体受保护，不是最后两条 SQL 套事务就够 |
| READ COMMITTED | 每条语句读取当时可见的已提交数据 | 本身不保证先读余额再扣款没有竞态 |
| FOR UPDATE | 让其他修改者等待目标现存行的数据库锁 | 等待后要用锁定读取返回的新余额 |
| 条件更新 | 将“余额够才扣”放进同一条写语句 | amount 下限条件防止基于旧判断盲扣 |
| RowsAffected | 数据库实际改动了多少行 | 零行不代表扣款成功，缺行也不等于余额不足 |
| sql.Tx | 一次本地事务专用的执行通道 | 所有账务 SQL 都用 tx，不能夹用连接池 db 方法 |
| 缺行建行协议 | 安全创建尚不存在的余额桶 | 靠唯一键仲裁后再锁行，不能锁住空查询结果 |
| 唯一索引仲裁 | 让同一身份或同一桶只有一份有效记录 | 不替代余额、分录、预留共同提交 |
| 全局锁序 | 所有写路径按相同键顺序取锁 | 身份、游标、余额、预留、账户版本依次处理 |
| 账户版本锁 | 为同一账户的资产变化分配连续版本 | 取得后不能回头补拿遗漏的余额或预留锁 |
| 死锁受害者 | 数据库为打破等待环而回滚的一方 | 沿原身份有界重试整个事务，不续跑局部 SQL |
| 提交未知 | Commit 通信出错但提交结果未必失败 | 先查持久结果，不立即做反向退款 |
| 进程内同步 | mutex、channel 只协调本实例的工作 | 管不了另一实例，也留不住崩溃后的资金事实 |
| 热点与背压 | 同一份钱竞争太多时限制积压 | 缩短事务和有界排队，不复制余额来并行超花 |
| 一致快照 | 核对数据来自同一个比较位置 | 多条普通查询可能跨提交前后，不能据此判半边提交 |

## 把整篇文章压缩成一个故事

甲只有 20,000 USDT，却同时向两个服务实例提交两个独立意图，每个都要预留 15,025。若两个实例都先普通查询，再各自判断“够用”，两个判断可能同时通过。安全的账户系统会让它们在数据库里争同一余额行：先得到锁的一方检查并扣成 4,975，后一方等到锁后读取新值，因不足而拒绝。各进程自己的 mutex 再严格，也管不了隔壁实例。

获准的一方不能只扣可用，再把预留明细交给另一个协程。它要在同一个 sql.Tx 中建立预留、写双边分录、转移余额并保存命令结果；条件更新还必须检查实际影响行数。假如账户桶尚不存在，空查询并没有锁住这个键，系统须通过预建行或受唯一约束保护的建行协议取得真实行，不能把查不到当作自己独占，也不能凭空初始化一笔正余额。

随后 B1 的完整成交批次到来，系统预先收齐涉及的余额、预留和账户版本键，按全体路径约定的次序取锁，再共同提交付款、BTC 交付和价差。另一个请求只能依据受保护的完整状态决策。发生死锁时，明确被回滚的事务沿原身份重新开始并有界退避；若只是提交连接断开，则先查询原结果，因为钱可能已动。锁内等待撮合 RPC 或无限重试，只会让更多合法请求堵住。

若甲成为热点，系统先看持锁与排队证据，缩短事务、限制积压，不把同一可用余额复制成多份独立额度。检查人员也不能拿提交前后的多次普通查询拼成报告，就断言出现半边入账；核对应固定水位或一致快照。本例保证来自单库权威事务，拆成多个数据库后必须重建结算边界；以上是可检验的并发设计，并非已通过数据库实验的声明。

## 第 1 层：先找出并发下必须一直成立的不变量

**面试官：** 多个 Go 服务实例都能接收资金请求。你会先选择一个锁，还是先定义哪些状态绝不能被并发破坏？用甲的 20,000 USDT 和 B1 说明。

**面试者：** 我先定义不变量，再选保护它们的数据库操作。甲在预留前有 20,000 USDT 可用、0 USDT 订单预留。B1 预留提交后应是可用 4,975、预留 15,025；甲这笔 USDT 总额仍是 20,000。并发下最关键的性质不是“某个 goroutine 一次只做一件事”，而是绝不能让两笔都基于同一份旧余额通过检查。

如果甲同时提交意图 A 和 B，各自都请求预留 15,025，正确结果只能是其中一笔成功，另一笔收到余额不足，不能都成功后把可用余额写成负数，也不能发生“余额只扣一次、却生成两份 reservation”的分裂状态。成交入账时同样如此：甲的 USDT 预留减少、乙或丙的可用增加、卖方 BTC 预留减少、甲的 BTC 可用增加、reservation 累计值以及应用位置，必须表达同一个业务结果。

因此我的并发安全目标是：每个已提交事务都能从前一个已提交状态转移到另一个满足不变量的状态；没有任何其他事务能看见半个转移。这个目标要求资金检查和写入处在同一个数据库提交边界内，具体是行锁或条件更新，另外再以唯一约束保护业务身份与建行。进程内互斥只是优化或局部保护，不是账户资金的跨实例权威。

我会先把跨资产总额拆开检查，不能把 BTC 和 USDT 数字直接相加。无费用且没有外部出入金时，参与账户的同币种转移净额为零；但每个用户的该币种持有量会因交易发生变化。非负余额、预留闭合、分录按币种平衡分别覆盖不同错误，任何单一检查都不足以替代另外两项。

## 第 2 层：在 READ COMMITTED 下怎样读取被锁行的当前余额？

**面试官：** 如果两个实例都先查到 20,000，再各自开始事务扣款，`READ COMMITTED` 这个隔离级别是否已经够了？你会怎样写出检查和修改之间没有竞态的流程？

**面试者：** 仅仅“在事务里”并不够。若普通 `SELECT` 读出 20,000，应用在事务外或未加锁的情况下判断通过，另一个事务也能读到相同值；隔离级别的名字不会自动让“读、判断、改”成为一个不可分割动作。我会在事务内锁定目标余额行，再依据锁定语句返回的行值判断，或者用带余额下限谓词的单条 `UPDATE`。

用行锁时，事务执行 `SELECT ... FOR UPDATE` 锁定 `(owner_id, asset_id, bucket)` 对应行。若第二个事务等待第一个事务提交，在 PostgreSQL `READ COMMITTED` 下，锁定读取会等待并取得更新后的行版本；程序必须使用锁定读取实际返回的余额，不可沿用锁之前缓存的普通读取。比如 A 成功把可用减到 4,975 后，B 拿到锁时看到的是 4,975，再判断 15,025 不足而拒绝。这里的正确性来自明确的行锁和锁后读取，不是“READ COMMITTED 一定串行执行”。

另一种写法是在总览的独立桶行模型上执行 `UPDATE balances SET amount = amount - $1, version = version + 1 WHERE owner_id = $2 AND asset_id = $3 AND bucket = 'available' AND amount >= $1`。并发更新同一行会互相等待，等待后 PostgreSQL 会针对当前行版本重新判断条件；只有 `RowsAffected()==1` 才表示本次可用扣减成立，之后还要在同一事务增加预留桶。若影响零行，就不能假设扣款成功。无论选哪种写法，reservation、对应分录、余额变更和资金命令结果仍需同事务提交；只用原子扣余额 SQL 却在事务外创建 reservation，还是会留下不完整状态。多桶操作采用条件更新也必须遵守固定键顺序，不因为单条语句原子就可以随意交换行锁顺序。

我会明确事务隔离级别为 `READ COMMITTED`，同时把每个读取为何安全说清楚。锁定读取保护的是已有目标行；若流程需要根据多行集合谓词作出不能被幻影行改变的决策，单行锁未必足够，需要改用唯一约束、专用汇总行或更强的约束方案，并重新分析并发历史。本题账户余额桶按唯一键直接定位，因此可以用明确的行锁或条件更新表达竞争点，不把所有业务都抽象成“提高隔离级别”。

## 第 3 层：用 database/sql 把资金变化圈进同一个 Tx

**面试官：** 你已经说明了锁后读和条件更新。落到 Go 的 `database/sql`，怎样防止开发者不小心把某条 SQL 发到连接池的另一条连接，绕过当前事务？

**面试者：** 我会先用 `db.BeginTx` 创建一个明确选择 `sql.LevelReadCommitted` 的 `*sql.Tx`，检查建事务错误，再设置回滚兜底。从第一条身份仲裁到最后一条结果保存，全部调用这个 `tx` 的 `QueryRowContext`、`QueryContext` 和 `ExecContext`，而不是在事务中混用连接池的 `db` 方法。读取时检查 `Scan` 的错误，遍历结果集后检查 `rows.Err` 并及时关闭结果集；写入时检查语句错误和预期影响行数。所有校验、分录、桶余额、reservation、结果与相关 outbox 都成功后，才调用一次 `tx.Commit`，不能在循环中逐个提交资产转移。

资金写辅助函数只接受 `*sql.Tx`，或只暴露事务内方法的受限接口，不能在内部偷偷使用 `db.ExecContext`，也不能把一部分分录交给异步 goroutine。开始事务后，数据库连接池的普通调用可能使用另一条连接，其更新并不属于当前事务，甚至可能等待当前事务已经持有的锁。接口类型和代码审查应一起防止这个错误。`BeginTx` 明确隔离级别，是为了知道依赖何种语义，不表示换成更强隔离级别就能省掉不变量与锁顺序论证。

事务持有余额行锁的时间要短：只做本地校验、读取和 SQL，不在锁内调用撮合 RPC、消息代理或用户回调。锁定前能完成的纯校验，例如限价必须为正、数量符合 BTC 步长、金额乘法无溢出，应尽可能先做，但任何依赖实时余额或 reservation 状态的校验仍要在事务锁定后重做。避免把网络延迟、日志阻塞或大对象编码放进持锁区，减少其他合法资金请求的排队时间。

返回余额不足属于业务拒绝，不需要留下半笔变化。SQL 失败则回滚整个事务。对于 `Commit` 返回的错误，调用方不能把它简单转成“没发生”；提交未知后的身份查询和重试契约归母题 07 深入。`defer Rollback` 是清理兜底，不能替代对每个错误路径的检查，也不能假定 rollback 一定能撤回已经提交的事务。

## 第 4 层：为什么每条 SQL 都要检查错误和 RowsAffected？

**面试官：** 有了事务以后，你执行扣余额、更新 reservation 和推进消费位置。哪些返回值必须逐一检查？影响行数为零究竟代表成功、余额不足，还是数据不一致？

**面试者：** 事务只保证它提交的那些写操作一起提交，不会替应用推断 SQL 的业务含义。每条 `ExecContext` 都要检查 `err`，并在依赖特定行存在或状态匹配时检查 `RowsAffected`。例如条件扣款影响一行才代表扣款成立；影响零行意味着余额不足、账户桶缺失、行状态已经改变或谓词不匹配，具体原因要结合已知前提作安全诊断，不能盲目继续创建 reservation。

处理成交时，我会使用带原状态条件的更新，例如要求 reservation 仍属于 B1、`remaining >= 本次限价占用`，并把 `remaining`、`spent`、`released` 更新到同一事务。若更新行数不是预期的一行，整批回滚并将其视作业务事实与账本状态不匹配，保留可恢复义务并告警。不能因为卖方 USDT 的 UPDATE 已成功，就跳过买方 BTC 交付失败的错误继续提交。

对多条 SQL，我会把校验失败、数据库错误和返回行数不符分别映射为业务拒绝、可重试事务错误、永久数据冲突或待人工调查；不能把所有错误都包装成“余额不足”，也不能吞掉 `RowsAffected` 错误。事务中途失败时，defer 回滚覆盖余额、journal、reservation、幂等结果和游标。若事务已提交但提交确认丢失，就不应执行补偿性的反向 SQL；先按原命令身份查出确定结果，否则一次成功提交可能被第二次扣款抵消或重复。

使用批量 SQL 时，也要核对影响行数与预期明细数相符。若批次包含两个 reservation 更新而只影响一行，即使总余额看起来可解释，批次仍不是完整业务事实。对 `QueryRowContext` 的 `sql.ErrNoRows` 要区别“按设计可空”与“必须存在的账户行缺失”；后者是初始化或数据一致性问题，不应被当成余额为零而继续入账。每项前置条件都应有明确失败分类，失败时整笔回滚。

条件更新的零行结果不能事后用不受保护的查询随意解释。例如扣款失败后余额又因另一笔已提交成交增加，后续查询显示足够，并不说明刚才那次更新成功。应依据该次语句结果判定本次未取得扣减，必要时在新尝试中重新锁定并判断，而非沿用原流程继续写入。对数据库约束错误也一样：已经进入失败状态的事务必须回滚，不能捕获错误后忽略，最后把 Commit 调用当成一切已完成的证据。

## 第 5 层：SELECT FOR UPDATE 锁不住还不存在的余额行怎么办？

**面试官：** 新账户还没有 USDT 余额行，两个实例同时第一次给它建行并预留。`SELECT ... FOR UPDATE` 查不到任何行，你怎样避免两边都认为自己独占了这个键？

**面试者：** 行锁只能锁定已存在的行，不能把“查询结果为空”变成互斥锁。对账户资产桶，我会优先在账户开通或资产初始化时建立零余额行，并用 `(owner_id, asset_id, bucket)` 唯一约束作为最终防线。如果业务确实允许按需建行，则先用 `INSERT ... ON CONFLICT DO NOTHING` 建立候选行，再在独立语句里按键 `SELECT ... FOR UPDATE`，读取并锁住唯一约束保证的那一行。

两个实例并发插入相同键时，唯一索引仲裁：一方插入成功，另一方等待冲突事务结束；之后的锁定读取拿到数据库里唯一存在的余额桶。创建行时金额只能按定义的初始化规则设为零或由一笔有来源的入账初始化，不能把 `ON CONFLICT` 后“没插入”误当成拥有余额，也不能用 `DO UPDATE` 无条件覆盖现存余额。若初始化资产本身需要写入来源分录，应把初始桶行和初始 journal 纳入受控的初始化事务，不能凭行不存在就凭空填正余额。

reservation 行的做法也要区分新建和已存在：ReserveOrder 在业务幂等身份确定后，按唯一 `reservation_id` 创建并绑定 owner、asset、intent 与 payload；成交消费时必须锁定该已存在行。若消费时缺行，说明依赖未满足，不可临时造一个空 reservation 再把成交记成功。对同一批需要建多个桶或 reservation 的路径，仍按稳定键排序插入，避免不同实例以相反顺序争抢唯一索引。

唯一约束负责同键唯一，业务事务负责余额和明细闭合，两者不能互相替代。不能在应用层执行 `SELECT count(*)` 确认无行后再裸 `INSERT`，因为两个事务都可以读到零；也不能用 advisory lock 作为唯一的账务事实保护而缺少实际唯一约束。数据库结构应清晰表达每种桶和 reservation 的自然键，保证错误代码无法静默创建重复资产行。

## 第 6 层：怎样用固定锁顺序降低死锁风险？

**面试官：** 一笔成交可能涉及甲 USDT、乙 USDT、乙 BTC、甲 BTC，以及多个 reservation。两个事务都要拿这些锁，但遍历顺序不一致时会怎样？你如何统一约定？

**面试者：** 如果事务 A 先拿甲的余额行、再等乙，事务 B 先拿乙、再等甲，就会形成等待环。数据库检测到死锁后会牺牲其中一个事务，但死锁检测只是失败兜底，不是设计锁顺序的替代品。我会定义所有资金写路径共同遵守的全序：消费撮合结果时先完成唯一结果身份仲裁，再锁对应结果流游标；随后将所有余额桶键按 `(owner_id, asset_id, bucket)` 排序并逐个锁定；最后把涉及的 reservation 按稳定 `reservation_id` 排序后锁定，再按 owner 排序锁定相关 `account_version` 行。全部必要资产桶和预留锁取得后才能取版本锁，不得拿版本锁后回头追加余额或预留锁；版本号随本次资金变化同事务递增。结果身份仲裁只允许取得本批执行权或读取原结果，不得已持有余额、预留或游标后反向争用同一个结果键。

非消费路径例如单独 ReserveOrder 没有结果流游标，所以在自身命令身份仲裁后跳过游标，按余额排序后再锁或创建 reservation，最后取得相关账户版本锁，不能采用“先 reservation，后余额”的反向顺序。取消释放、管理修正等其他资金命令也遵循余额在前、reservation 在后；如果某路径确实要使用额外互斥行，必须把它明确纳入全局顺序并评估与结果游标的相对位置。

排序必须是代码级规则，不依赖 map 遍历、请求字段顺序或 SQL 执行计划碰巧相同。通常先收集全部键、去重、排序，再逐个锁；一个 SQL `ORDER BY` 有助于表达顺序，但若要严格控制获取锁时机，应确保实际执行方式符合预期。所有实例部署相同版本的锁序协议；滚动升级期间旧版本若顺序不同，仍可能引入死锁，因此死锁处理仍需有界重试。结果流游标在本题只是为完整批次消费给出顺序锁点；完整批次缺口与跨域义务的语义见母题 06 和母题文件 08。

统一锁序不意味着把所有资金操作都锁成全局串行。不同账户、不同资产且不共享 reservation 的事务可以并行；同一账户同一币种的余额桶则天然存在竞争。锁顺序应保证只锁该操作需要的行，避免为一个 BTC 成交锁住账户所有币种或全库单一总锁。不能为消除死锁而牺牲正确性的局部约束，也不能用粗粒度全局锁掩盖数据模型中的依赖关系。

涉及同一账户不同币种的两个事务，即使资产桶互不冲突，最后也要在该账户版本行上排队，才能为每次已提交账户变化分配连续版本。先拿版本锁再找遗漏资产桶会重新形成等待环，所以批次必须提前收集全部参与账户及资产。发现锁集合不完整时，应回滚并重新构造完整集合，而不是在版本锁后临时追加。权威版本行也须预建或受唯一约束保护地初始化，不能把缺行当作版本零后并发各自递增。

## 第 7 层：死锁和序列化失败可以重试到什么时候？

**面试官：** PostgreSQL 返回死锁受害者错误，或者事务遇到可重试冲突。你会自动重跑 SQL 吗？重试次数和退避怎样设，什么错误不能重试？

**面试者：** 对被数据库明确回滚的死锁事务，可以有限次重试完整业务事务，而不是从失败的那条 SQL 接着执行。重试前重新 BeginTx、重新读取余额和 reservation、重新取得全部锁，并沿用原请求或结果批次身份。这样 A 可能先成功，B 在下一次尝试时读到更新后的可用余额，再给出正确业务结果；不能缓存第一次尝试的余额作为重试依据。

重试只覆盖可识别的瞬时数据库错误，例如 PostgreSQL `40P01` 死锁检测；若选择更强隔离级别时，还需识别 `40001` 序列化失败并重跑整个事务。本基线明确使用 `READ COMMITTED`，仍可有死锁。网络断开、语法错误、约束冲突、金额溢出、reservation 不足等不能一概无限重试；唯一键冲突应由幂等协议判定是同一结果还是身份冲突，而不是随机换键再来一次。

我会设定小而有界的重试次数，并采用带抖动的递增退避，同时尊重请求 deadline；到达上限后把操作交给同一身份的可恢复任务或返回“结果待确认”，绝不让 goroutine 无限占着连接和业务队列。重试会增加数据库负载，所以要限制并发、观察死锁率及队列年龄。若所有实例遇到同一热点并同步重试，固定间隔可能形成重试风暴，抖动、全局限流和背压应一起考虑。

特别是 `Commit` 返回连接错误时，不能直接把它当作已回滚的死锁来重放业务；提交是否完成可能未知，应先走持久结果查询路径。重试器要区分事务确定回滚与结果不确定两种状态，并对同一业务身份做幂等恢复。自动重试也不能改变已拒绝命令的业务语义：余额不足后不应后台等待余额增加再悄悄执行原订单，除非接口明确定义了这种排队产品语义。

## 第 8 层：Go 的 mutex、channel 和 context 能保护到哪里？

**面试官：** 既然使用 Go 服务，能不能在每个进程里给账户加 `sync.Mutex`，再用一个 channel 串行处理所有资金命令？这样是否比数据库行锁简单？

**面试者：** 这只能提供单进程内的同步，无法协调两个 Go 实例，也无法在进程崩溃后保存余额事实。实例 A 的 mutex 不会阻止实例 B 抢甲的 20,000 USDT；channel 中尚未处理的命令也会随进程退出而消失。因此我可以用 mutex 保护本地缓存、复用中的临时对象或限制本实例并发，但余额检查、reservation 和分录的权威互斥仍由 PostgreSQL 承担。

单个 channel worker 能让本进程中命令按序执行，却可能把所有账户都串成一个队列，吞吐和故障隔离差；若按账户分多个 worker，也解决不了跨实例的同账户竞争，且多资产成交会跨越 worker。队列只负责背压或调度，命令仍需持久化，消费仍需事务幂等。不能在向 channel 发送成功时就向用户承诺资金已经预留，更不能在收到命令后先 ACK 再异步写账。

`context.Context` 用于传播取消与 deadline，但取消到达不证明数据库回滚了：客户端可能在提交附近超时，而服务端已完成提交。事务 SQL 应带有可控 deadline，提交未知交给同一业务身份查询；不能因 HTTP 请求取消就启动另一个随机身份的逆向操作。使用 `sync.Mutex` 时也不能在持锁期间做网络 RPC 或无限等待 channel，否则本地锁会放大尾延迟。

如果需要进程内按账户限流，可以使用分片 worker 或信号量作为负载保护，但应考虑同一账户跨实例路由、进程故障迁移和排队上限；数据库仍是最后的并发裁决者。Go 层管并发资源与取消，数据库层定义跨实例的资金提交边界，两层职责清楚才不会互相冒充。即使服务临时只有一个副本，也不应该因“目前没有并发”而删掉数据库条件更新和唯一约束，因为部署规模与故障重启都会变化。

## 第 9 层：甲成为热点账户后，怎样扩展而不绕过余额串行化？

**面试官：** 固定锁序解决不了甲的 USDT 热点。如果很多实例不断为甲下单，行锁排队变长，你会不会按订单拆成多个余额行，让请求并行扣款？

**面试者：** 先确认瓶颈是不是这一行：看锁等待时间、事务持锁时长、数据库连接池排队、慢查询和单账户请求分布，再决定动作。若热点确实来自甲的同一币种可用余额，串行化本来就是保护“这一份 20,000 不能重复花”的必要成本。把同一个可用余额复制成多个可独立扣减的行，会把单点竞争换成跨桶总额超支，除非每个桶先独立分配且用户接受各桶之间暂时不可互用的额度语义。

可以先优化不改语义的部分：让事务只锁必要资产桶、提前验证纯参数、批次化非相关写、减少往返、缩短持锁代码、为查询和账务写入合理配置连接池，并对新请求做有界排队或拒绝，避免无限堆积。不能为追求吞吐在事务内调用撮合，也不能先在缓存扣减、稍后异步补账，却仍声称 PostgreSQL 余额是同步权威。查询缓存可减轻读压力，但不能参与可用资金裁决。

按账户把命令路由到稳定分区或单写者，可能降低同一时刻的锁冲突，但多个 Go 实例的所有权转移、故障接管和围栏令牌必须防止旧写者继续落库；最终还要有数据库约束兜底。按用户分数据库则改变了原子事务覆盖范围，不能继续宣称甲扣款与乙／丙收款、BTC 交付在一个本地 Tx 中同时完成。是否采用异步结算或分片，应作为架构前提变化另行论证，不把“扩容”当作取消账务不变量的理由。

拆余额桶不是纯实现优化，因为它改变可支用资金的定义。若把甲的额度预分配到 N 个桶，必须先证明分配额之和等于原可用资金、没有多发额度；若转移桶间额度，还需要新的互斥及分录规则。只检查每个桶非负，却不检查分配总额和转移守恒，仍不能证明用户总额度没有超支。优化前应先说明正确性模型，再说明吞吐收益来自减少哪一种竞争，且不能虚构基准数据或宣称未测的性能提升。

热点还会表现为公平性问题：一串短请求不断插入，可能让某个大批次长时间拿不到全部锁。可以限制同账户的在途请求数量、对积压命令设置可观测等待上限，并优先恢复已经确定的成交义务，避免新预留挤占恢复资源。但不能为了救一个等待很久的请求而绕过余额检查，也不能把排队超时解释成已执行或已退款；返回值仍按是否已经取得持久结果区分确定拒绝、未决与可重试。

## 第 10 层：怎样把并发正确性讲成可检验的历史？

**面试官：** 你已经给出锁顺序、数据库事务和热点处理。最后怎样向面试官证明并发结果不是靠幸运？要用什么反例，什么证据不能夸大？

**面试者：** 我会列出操作历史并规定允许的串行结果。最直接的反例是甲只有 20,000 USDT、两个独立意图并发各请求 15,025：一次应成功，一次应以余额不足结束，最终是可用 4,975、预留 15,025，而不能出现两笔成功、负可用或预留合计 30,050。另一个历史是 B1 成交批次与甲的新预留竞争；事务只能观察到批次提交前或提交后的完整余额，不能观察到乙已收款而甲 BTC 尚未入账的半状态。

检查点至少包括：每次事务提交后所有余额非负；各币种分录按 journal 汇总为零；reservation 的 `initial = spent + released + remaining`；账户订单预留与 reservation 剩余量一致；同一业务身份只有一个确定结果；结果流游标不会越过未提交的应用。主案例最终数值还要闭合为 B1 `15,025 = 15,015 + 10 + 0`、全部参与账户 `4,985 USDT + 6,000 USDT + 9,015 USDT = 20,000 USDT`，以及 BTC 交付和卖方剩余预留符合给定数量。

验证应覆盖两个数据库连接或多个服务实例的并发历史、锁等待与死锁、唯一键竞争、事务中途回滚以及提交后响应丢失；Go race detector 只检查进程内数据竞争，不能证明 PostgreSQL 多实例的资金串行化。本文只定义预期，不声称已运行并发测试、故障注入或生产压测。最容易答错的边界是把隔离级别名当证明、用 mutex 代替跨实例约束、锁住余额却把分录放在事务外，以及死锁无限重试。

最后要记住，本地 Tx 只保证同一个 PostgreSQL 事务中的本地事实；Place／AbortIntent 的资格关闭和跨域成交义务不能由这把余额锁代替，分片后也不能声称本地事务覆盖全链路。若面试官追问“怎样知道所有对手方都完成”，应回答这是跨域应用进度和完成定义，不是再多加一把数据库行锁即可解决的问题。

观察历史也要选对读取方式。事务原子提交意味着没有一半已提交的资金变化，但 `READ COMMITTED` 下两条查询语句可能分别发生在提交前后，所以多次普通查询拼出的报告不自动是一致快照。静态核对应固定截止版本，或用满足一致快照要求的只读事务取得同一位置的数据；参与扣款的路径则依据锁后状态。不能拿一个跨时点拼接的报告证明半边提交，也不能因报告最终数值看起来正确就断言所有中间业务义务已履行。

## 本题收束

### 机制与验证边界

- 资金判断必须基于受保护的当前行：锁后读取，或带条件谓词并检查 `RowsAffected` 的原子更新。
- `database/sql` 的同一个 `sql.Tx` 包含分录、权威余额、预留、结果身份和相关进度；任一错误均回滚，提交未知不等于回滚。
- `READ COMMITTED` 下要讲清锁等待、锁后行版本和谓词重检的作用；隔离级别名称本身不是正确性论证。
- 现存行用 `FOR UPDATE`；不存在行靠预建或唯一约束和建行协议，不能假称锁住空结果。
- 消费路径统一为结果身份仲裁 → 结果流游标 → 排序余额桶 → 排序 reservation → 按 owner 排序的相关 account_version 行；非消费命令在自身身份仲裁后可省略游标，但不能反向取得这些键。持版本锁后不得回头追加余额或预留锁。
- 死锁受害者可按原身份有界重试整个事务；`Commit` 通信失败必须作为可能未知处理。
- Go mutex、channel 和 context 只定义进程内同步、排队和取消行为，不替代数据库跨实例互斥。

### 易错边界与反例

最典型的错误历史是：A、B 都普通读取甲有 20,000 USDT，都在应用层通过 15,025 的余额检查；两边分别扣款并创建 reservation。单条语句都成功不代表整体正确，最终却可能预留 30,050。另一个错误是只更新余额不记分录，或只在单实例加 mutex；它们分别破坏可审计性与跨实例互斥。要回答清楚：数据库中的哪一行被锁、等待者拿到锁后读到什么、整组哪些行在同一事务里提交、提交未知时通过什么持久身份恢复。具体身份结果见母题文件 07，跨域资格与成交履约见母题文件 06；若改变成跨库分片，必须重新定义交易完成语义和结算边界。
