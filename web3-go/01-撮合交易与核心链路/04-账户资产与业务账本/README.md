# 账户资产与业务账本：专题总览

## 先看懂：关键词大白话解释

本文范围说明：本专题讨论 BTC/USDT 托管现货、限价 GTC、零手续费的内部业务账本，案例账户同处一个 PostgreSQL 账务库。链上充提、完整财务总账与跨库结算不属于本例已实现能力；文末 MVP 是伪代码与手工推演，不是工程测试结论。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 托管现货 | 平台代管资产，用户按真实持有量交易 | 账本记录用户请求权，钱包余额不是个人交易余额 |
| 限价 GTC | 限定最差价格，未成交部分继续等待 | B1 最多按 60,100 USDT/BTC 买入，不引入其他订单类型 |
| 可用余额 | 已入账且现在能再次使用的资产 | 预留后甲可用 USDT 为 4,975，不能再花被占住的部分 |
| 订单预留 | 仍属于用户、但专供某笔订单使用的资产 | 不是已经付款，也不是永续合约保证金 |
| reservation | 一张写明占款用途与余量的明细单 | R-B1 把预留与 B1 的唯一意图及载荷绑定 |
| 分录 | 说明谁的哪个资产桶增减了多少的记录 | 与权威余额同事务保存，提交后不改历史 |
| 复式业务账本 | 每次同币种转出都有对应转入的子账 | 平衡只证明数量配对，不证明收款对象正确 |
| 资产与负债 | 托管实物与平台欠用户的义务是两个口径 | BTC、USDT 分开核对；业务子账不能冒充完整财务总账 |
| 固定精度整数 | 用约定最小单位数钱，不用浮点近似 | BTC 为 10^-8，USDT 为 10^-6，价格为 10^-6 USDT/BTC |
| 账户域写入权威 | 所有资产变动都要走同一个逻辑门口 | 可部署多个 Go 实例，但不能各自绕过数据库裁决 |
| 预留事务 | 把占款及提交意图一起落盘的动作 | 余额、预留、幂等结果与订单提交 outbox 一起提交 |
| outbox | 与业务变化一起保存的待交付任务 | 崩溃后还能继续提交同一 B1，不等于跨域共享事务 |
| 撮合执行资格 | 某笔意图仍可被接纳和成交的权利 | 不能凭可复用的预留字符串反复创建订单 |
| AbortIntent | 在撮合权威顺序内关闭意图资格 | 不是超时退款；先履行前序成交，再释放剩余 |
| ResultBatch | 撮合已提交的一整包确定结果 | 完整批次带顺序交给账户，不能漏掉成交只处理释放 |
| 成交应用身份 | 证明某笔成交是否已入账的稳定编号 | 同一 trade_id 换批次也不能再扣一次 |
| 消费进度 | 账本已经连续处理到哪里 | 去重、分录、余额与游标在同一事务前进 |
| 价差返还 | 预留上限高于实际付款时归还的部分 | 10 USDT 是未花掉的预留，不是盈利或补贴 |
| 冲正与同水位对账 | 留下纠错新记录，并在同一截止点核对 | 不删旧流水，也不拿不同进度的数字直接判错 |
| 账户查询投影 | 为页面和推送整理的可重建副本 | 可以落后，不能裁决资金能否扣除或释放 |

## 把整篇文章压缩成一个故事

甲在这个托管现货案例里有 20,000 USDT，想用 B1 买入 0.25 BTC，最高出价为每 BTC 60,100 USDT。账户系统先在权威数据库事务里把 15,025 USDT 从可用移入订单预留，同时保存绑定意图的明细和提交任务。钱仍属于甲，只是不能再用于另一笔订单；多个服务实例同时来争这笔钱，也必须服从同一个事务约束。此时页面显示占款成功，并不表示撮合已经接单。

提交器随后把同一个意图交给撮合。撮合先后确定甲向乙买入 0.10 BTC、向丙买入 0.15 BTC，实际分别支付 6,000 和 9,015 USDT，并可靠保存完整结果。假如回复途中丢失，账户系统不能因为查单超时就把预留退掉；它要找回原结果，或者让关闭意图进入同一裁决顺序，即使关闭成功，也得先处理已经确定的成交义务。

账户消费者拿到连续的完整批次后，在同库事务里一起检查成交身份、预留归属和对手方，完成两种资产的双边分录，再把未花的 10 USDT 还给甲。同一事务还保存消费进度、账户版本和通知意图，因而崩溃重试不能再次扣款。最终甲有 4,985 USDT 和 0.25 BTC，乙有 6,000 USDT，丙有 9,015 USDT，另有 0.05 BTC 继续预留；每种资产各自守恒，不能把币与钱混加。

如果页面还没更新，甲看到的是旧投影，不是第二次结算的理由。对账系统要在共同截止点核对成交义务、分录和余额，发现转错对象时，即使分录平衡也不能判为正确；纠错必须追加有引用、有审批的新记录。托管资产与用户请求权还需另按资产负债口径核对。本专题只给这套设计及同库入账伪代码，不把它说成已跑通的充提系统或跨库工程。

## 一、文字全流程：一笔订单怎样走完账户链路

### 1.1 先锁定讨论基线

| 维度 | 本专题约定 |
|---|---|
| 产品与交易机制 | BTC/USDT 托管现货、价格时间优先的中央限价订单簿，仅限价 GTC |
| 资产控制 | 用户对平台的已确认资产请求权由内部业务账本记录；链上钱包余额不是用户的逐笔交易余额 |
| 执行与结算 | 链下撮合，链下账务结转；订单成交不需要逐笔发送链上交易 |
| 状态归属 | 撮合域决定订单接纳、成交与撤销；账户域决定可用、预留、分录与是否已经入账 |
| 存储边界 | 所有案例账户位于同一个 PostgreSQL 账务数据库；分录、权威余额、预留、幂等结果与消费进度可以处于同一个本地事务 |
| 并发方式 | 多个 Go 服务实例，通过数据库短事务与统一加锁顺序协调；不是整个服务只有一个 goroutine |
| 费用与借贷 | 手续费为零，无杠杆、借款、透支、资金费率、保证金或强平 |
| 充提与链上范围 | 以已经确认的内部期初余额开始；充提、确认与重组只说明接口边界，不在本例中实现 |
| 查询 | 权威余额索引与分录同事务更新；页面、缓存和推送可以异步，不能参与扣款裁决 |

这一基线与[撮合交易样稿](../01-撮合交易从0到1/README.md)的业务数值一致，但本专题按当前提示词拆为独立母题。这里的设计是教学方案，不是对目标公司的架构断言。

**不混用的概念：** 现货预留不是永续仓位保证金；内部账务完成不是链上最终确认；资产账本也不是涵盖收入、税务和法币估值的完整财务总账。

### 1.2 贯穿案例与期初状态

甲初始有 **20,000 USDT 可用、0 BTC**，提交买单 B1：以不超过 **60,100 USDT/BTC** 买入 **0.25 BTC**，请求身份为 `buy-001`。

已有卖单的 BTC 已完成预留：

| 订单／账户 | 方向 | 限价 | 剩余量 | 对应预留 |
|---|---|---:|---:|---:|
| S1／乙 | 卖 | 60,000 USDT/BTC | 0.10 BTC | 0.10 BTC |
| S2／丙 | 卖 | 60,100 USDT/BTC | 0.20 BTC | 0.20 BTC |

除表内资产外，三个账户在本例中的其他余额为零。期初的资产来历由已经审核的期初分录解释，不为构造案例伪造链上充值记录。

```text
B1 初始预留：60,100 × 0.25 = 15,025 USDT

成交 T1：甲向乙买入 0.10 BTC，实际支付 6,000 USDT
成交 T2：甲向丙买入 0.15 BTC，实际支付 9,015 USDT

甲合计支出：15,015 USDT
限价预留差额：15,025 - 15,015 = 10 USDT

最终：甲可用 4,985 USDT、0.25 BTC，B1 预留为零
      乙可用 6,000 USDT，S1 预留为零
      丙可用 9,015 USDT，S2 仍预留 0.05 BTC
```

10 USDT 是原先预留中没有实际支出的部分，不是交易利润或平台补贴。

### 1.3 主流程：从资金申请到结果可查询

```text
甲提交 B1〔账户、交易对、方向、限价、数量、buy-001〕
    ↓
接入层：鉴权、精度校验，检查请求身份与载荷是否冲突
    ├─ 不合法 → 明确拒绝，不进入资金预留
    └─ 合法 → 向账户域发起 ReserveOrder
                  ↓
账户域：一个数据库事务
    锁定甲的 USDT 可用／订单预留余额
    检查可用足够，创建绑定 B1 的 reservation R-B1
    写预留分录：可用 -15,025，订单预留 +15,025
    同时保存幂等结果与待提交订单的 outbox 记录
                  ↓ 提交
甲可用 4,975 USDT，订单预留 15,025 USDT
“预留成功”只承诺资金已占住，不承诺订单已经接纳
                  ↓
提交器：重试交付同一 Place(B1, R-B1)，不重新生成订单身份
                  ↓
撮合域：将 Place 纳入该交易对的可靠命令顺序
    校验预留凭据与订单载荷绑定，裁决是否接纳
    与 S1、S2 撮合，原子提交完整 ResultBatch 及处理位置
                  ↓
订单 B1 已全成，T1／T2 成为确定的成交义务
此时账户尚未处理批次也合法；原预留不能先释放
                  ↓
账户消费者：取得完整批次，校验来源、批次身份与连续序号
                  ↓
账户域：一个数据库事务
    锁定本批涉及的余额与预留
    校验成交范围、预留归属、数量及金额
    写买卖双方 BTC／USDT 分录，返还 10 USDT
    同时更新权威余额、预留明细、幂等结果、消费位置和账户通知 outbox
                  ↓ 提交
账户域将本批记为 APPLIED；失败则整个事务回滚，保留待处理义务
                  ↓
查询／推送投影追上对应账户版本
用户可以分别看到订单终态、账务状态和账户余额版本
```

账户域的 outbox 让“已预留资金但提交器崩溃”的意图仍可恢复；它不与撮合域共享事务。撮合域必须保留已提交结果，直到可可靠重投，不能把一次消息发送成功当成账户已经入账。

### 1.4 主要拒绝、取消与失败分支

```text
余额不足
    → ReserveOrder 返回已确定的拒绝，不产生预留和订单提交任务

预留成功，但 Place 超时
    → 保留原预留，查询／重试原意图
    → 用户要放弃时，提交 AbortIntent 到同一撮合裁决顺序
    → 取得已关闭资格的结果，并处理此前成交后，才释放可释放部分

Place 已接纳但订单尚未全成，用户撤单
    → 撮合域排序成交与撤单
    → 已成交部分保留履约义务，只撤实际剩余量
    → 账户按连续批次先处理成交，再处理相应释放

撮合结果已确定，账户事务失败
    → 不撤销成交、不释放整个预留
    → 保留批次并重试；持续失败时告警与限制风险扩大

账务提交后、回执返回前进程崩溃
    → 重放同一批次，返回原 APPLIED 结果，不重复扣款

查询／推送超时或落后
    → 按账户版本查询／补发，不重新执行资金命令
```

`AbortIntent` 不是“数据库查不到订单就退款”。若它先于 Place 被裁决，撮合域必须持久记录关闭墓碑；迟到的 Place 即使带着原预留凭据也不能执行。若 Place 在前，则先保留已经确定的成交，再关闭实际剩余资格。

### 1.5 分阶段的资金与完成含义

以下 USDT 数值不包含其他业务变动，BTC 单列。

| 阶段 | 甲可用 USDT | 甲预留 USDT | 甲可用 BTC | 已完成与未完成 |
|---|---:|---:|---:|---|
| 下单前 | 20,000 | 0 | 0 | 只有期初资产 |
| 预留事务提交 | 4,975 | 15,025 | 0 | 资金占住，撮合受理尚不确定 |
| 撮合命令可靠受理 | 4,975 | 15,025 | 0 | 命令可恢复，不等于已成交 |
| 成交批次确定 | 4,975 | 15,025 | 0 | B1 全成，存在尚未入账的成交义务 |
| 账务事务提交 | 4,985 | 0 | 0.25 | T1／T2 与价差均已入账 |
| 页面追上账户版本 | 4,985 | 0 | 0.25 | 展示更新；并非又发生一次转账 |

## 二、核心板块：资金真相由谁掌握

| 核心板块 | 决定什么、为什么核心 | 拥有的权威状态 | 上下游契约 |
|---|---|---|---|
| 资产可用性与预留 | 决定同一份钱能否再次用于下单或转出，防止多花 | 可用／预留余额、预留用途与剩余量 | 收到稳定资金命令，返回绑定意图的预留结果；不替撮合决定订单是否成交 |
| 分录与入账事务 | 决定资产转移是否完整、可追溯和只生效一次 | journal、postings、权威余额、持久命令结果 | 接收确定业务事实，在一个事务中提交全部账务变化 |
| 撮合—账户交接 | 决定成交、撤单与释放是否引用同一条事实链 | 撮合域拥有业务结果；账户域拥有应用位置 | 稳定身份、完整结果批次、连续顺序与缺口补齐 |
| 恢复、对账与审计 | 决定异常是否能定位、停止扩散并有据修复 | 差异记录、修复审批与追加分录 | 以同一截止点比对业务义务和分录，不直接改余额抹平差异 |
| 查询与回报 | 决定用户看到的状态是否可解释 | 可重建投影、投影版本 | 告诉读者“看到哪一步”，不能成为扣款或释放依据 |

核心不在于有多少个服务，而在于**谁能创造事实、谁只能消费事实、哪些状态必须一起提交**。

## 三、核心 20%：优先掌握决定正确性的机制

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 带单位的状态与不变量 | 全程 | 先定义哪些资产可花、哪些承担义务 | 把预留、保证金、未确认充值混为一谈 | 每币种守恒、非负、预留归属与累计闭合 |
| 单一资产写入权威 | 预留、入账、修复 | 阻止各服务绕开约束改余额 | 数据库有事务仍会被旁路写穿透 | 数据库权限、命令接口、业务事实与资金事实分权 |
| 精确金额与版本 | 参数、预留、成交结转 | 计算结果必须可重放 | 浮点误差、舍入凭空造钱 | 最小单位、乘法溢出、交易步长、规则版本 |
| 预留与执行资格绑定 | 下单、取消、超时 | 保证资金不会同时被花掉和释放 | 迟到订单在退款后执行 | intent、reservation、载荷绑定、AbortIntent 与墓碑 |
| 本地多状态原子提交 | 每次入账 | 余额、分录与防重必须是同一事实 | 半边转账、分录与余额不一致 | 短事务、加锁顺序、提交未知与持久结果 |
| 稳定身份与有序交付 | 跨域交接 | 重复不多记，缺口不早释放 | 重复扣款、先撤单后结算 | 业务幂等键、载荷冲突、批次完整性、连续游标 |
| 追加式修复与同水位对账 | 故障处理 | 修复必须解释差异而非掩盖差异 | 改对余额却破坏审计和预留义务 | 冲正引用、权限、截止点、正常在途与真实缺失 |

“20%”是优先级，不是省略其余核心环节的题数限制。

## 四、设计与规则：所有母题共用的前提

### 4.1 资产状态与守恒边界

本例只采用两个用户资产桶：`available` 与 `order_reserved`。

```text
某用户、某币种当前已记账资产 = available + order_reserved
available >= 0，order_reserved >= 0

某 reservation：initial = spent + released + remaining
某用户、某币种：order_reserved = 属于该用户该币种的全部 reservation.remaining 之和
```

`spent` 表示通过该预留已经结转给对手方的资产，不包含返还给自己的价差；`released` 包含价差返还和确定撤销的剩余预留。不存在“订单全成所以 initial 全部 released”的规则。

上述第一式是本现货模型的资产桶定义，不是“用户总资产永远不变”：交易会改变用户各币种数量。无外部出入金、无费用时，**所有参与账户的同币种转移净额为零**；BTC 与 USDT 不能直接相加验证守恒。

从 `available` 转到 `order_reserved` 不改变该用户的该币种合计。成交会在不同用户之间转移资产；没有必要把尚未入账的 BTC 再记进一个“待到账可用”字段。若页面展示待结算数量，它是成交义务视图，不能与当前余额重复计入可支用资产。

新增提现预留、抵押或在途资产时，需要重新定义确认条件、桶间转移与会计对应科目，不能直接向本公式添加一个含义不明的 `frozen`。

### 4.2 金额、精度与舍入

本专题教学元数据固定如下：BTC 最小单位 `10^-8 BTC`；USDT 记账单位 `10^-6 USDT`；价格以 `10^-6 USDT/BTC` 的整数表示。这里是本例内部精度，不断言所有链和产品都采用相同精度。

```text
q = BTC 数量对应的整数最小单位
p = 每 BTC 的价格对应的整数 USDT 最小单位
n = p × q / 100,000,000       // n 的单位是 USDT 最小单位

数量步长：0.0001 BTC，即 q 是 10,000 的倍数
价格步长：0.01 USDT/BTC，即 p 是 10,000 的倍数
```

这组步长使合法价格乘合法数量能整除 `100,000,000`，本例不产生舍入残差。先检查步长与数量范围，再计算；Go 中不能让两个 `int64` 先溢出后再转大整数，可用 `math/big.Int` 做中间乘法并显式检查最终范围，注意其可变对象不能无保护地跨 goroutine 共享。

本例无费用。增加费率时必须明确收取币种、计费基数、舍入方向、费率版本和费用科目；不能只给用户扣一笔手续费而没有对应入账方。

### 4.3 架构与职责

```text
订单接入／编排
    ├─ ReserveOrder → 账户域唯一写入入口 → 同一账务数据库
    │                                       ├─ 分录与权威余额
    │                                       ├─ reservation 与幂等结果
    │                                       └─ 订单提交／账户通知 outbox
    │
    └─ Place／Cancel／AbortIntent → 撮合域权威命令顺序
                                      ↓
                                已提交 ResultBatch
                                      ↓ 允许重复，不允许丢失后跳过
                                账户消费与入账事务
                                      ↓
                                账户查询／私有回报
```

“唯一写入入口”是逻辑所有权，不是只能部署一个实例；只有账户域具备余额和分录写权限。风控可以批准或拒绝意图，不能绕过账户域扣款；人工修复也必须通过受审计的追加命令。

撮合资格凭据绑定 `intent_id、reservation_id、账户、交易对、方向、限价、数量、规则版本`。撮合域通过可信接口或可验证凭据取得这些绑定，并在本域防止同一意图接纳多次；不能仅凭一个可重复使用的 reservation 字符串创建任意订单。

### 4.4 核心数据与提交边界

| 对象 | 必要字段／约束 | 权威与含义 |
|---|---|---|
| 资产余额 | `owner_id, asset_id, bucket, amount, version`；唯一账户桶键 | 账户域；与分录同事务维护的权威余额索引 |
| 业务预留 | `reservation_id, intent_id, owner_id, asset_id, initial, spent, released, remaining, payload_hash, rule_version` | 账户域；解释谁占了多少、用于哪一笔意图 |
| 账务事务 | `journal_id, source, business_id, operation_type, rule_version` | 账户域；关联同一业务动作的全部分录 |
| 资产分录 | `journal_id, line_no, owner_id, asset_id, bucket, delta` | 账户域；同 journal 同币种 `sum(delta)=0`，提交后只追加不原地改历史 |
| 命令结果 | 唯一 `(source, business_id, operation_type)`，载荷摘要、journal 引用、结果；source 含经授权的来源／租户／账户作用域 | 同身份同载荷返回原结果；同身份不同载荷报冲突 |
| 撮合结果批次 | `stream_id, result_seq, batch_id, payload_hash, trades, order_changes, reservation_actions` | 撮合域；完整批次提交后才是确定业务事实 |
| 成交应用身份 | 来源作用域内唯一 `trade_id`，绑定结果位置与规范载荷，与分录同事务保存 | 防止同一 T1 换 batch_id 再次入账；合法更正必须引用原身份 |
| 应用进度 | `stream_id, last_applied_seq`，与本批入账同事务提交 | 账户域；防止存在未处理成交时先应用释放 |
| 账户版本 | `owner_id, account_version`；每次改变该账户资产的事务内递增 | 同一版本覆盖本事务全部币种变化；不同于余额桶局部 version 和撮合 seq |
| 投影与通知 | 账户版本、原业务身份、投影进度 | 可重建；投递成功不等于读者已看见 |

这里用带正负号的同币种资产转移表达分录；它描述的是业务资产子账。若接入完整财务总账，必须明确用户负债、托管资产和费用收入等科目的借贷方向及对接规则，不能把 `sum(delta)=0` 当作所有财务正确性的充分条件。

**三个独立提交边界：** 预留事务提交、撮合结果提交、账务应用事务提交。RPC 回复、channel 收到命令和消息发布都不是它们的替代物。

| 动作 | 资产 | 转出桶及金额 | 转入桶及金额 |
|---|---|---|---|
| B1 预留 | USDT | 甲 available：15,025 | 甲 order_reserved：15,025 |

### 4.6 实现选择与明确边界

- **本地原子性：** PostgreSQL 短事务，在事务中校验并修改余额。先仲裁本次命令／结果身份；消费路径再锁结果流游标；随后按账户桶键排序锁全部余额，再按 reservation 键排序锁预留，最后按 owner 排序锁相关账户版本行。无游标路径跳过游标，不能拿到后序锁再回头申请前序锁。纠错范围等额外控制行必须纳入同一全序，详见母题 05、10。相关行预先建立或使用受唯一约束保护的建行流程，不对不存在的行假设已有行锁。
- **幂等与交付：** 数据库唯一键保存原结果，outbox 或可重读结果日志支撑重投。批次唯一性还要配合来源范围内的 trade_id 唯一归属，不能换批次重复同一成交。余额不足可同事务保存稳定拒绝；同键重试不因后来余额增加而变成新下单。普通消息队列的“恰好一次”说法不覆盖跨系统的账务事务。
- **顺序与版本：** 每个撮合结果流使用连续逻辑序号；主备切换不把同一流的业务序号从零重置。只提交 `last_applied_seq + 1`；重复批次核验后返回原结果，缺口等待补齐。不同流竞争同一账户仍由数据库余额锁协调。账户连续版本则在同事务锁版本行并递增，以完整账户事件交付；两类序号都不能直接拿会因回滚跳号的数据库 sequence 冒充。
- **取消：** 撮合域在同一权威顺序内关闭执行资格，账户域按已处理事实释放。扫描器年龄告警可以触发查询或 AbortIntent，不能直接退款。
- **恢复：** 同一命令重放、投影重建和经审批的冲正属于不同动作。确定成交通常重试履约；不能因数据库暂时不可用就删除成交。
- **扩容：** 基线不跨数据库分片。跨分片后不能沿用“一次事务更新所有账户”的保证；要明确清算账户、在途义务、双方应用身份和最终完成条件，另由母题 12 深入。

## 七、工程实践：一个简洁 MVP

### 7.1 目标与范围

只验证**一个已确定成交批次的双币种入账、价差返还、预留闭合，以及同批重试不重复记账**。输入使用 1.3 节预留完成后的快照：甲已预留 15,025 USDT，乙／丙分别已预留 0.10／0.20 BTC；成交来自给定的合法批次。

不实现撮合、预留创建、撤单、远程可靠交付、主备或跨库分片。下面是借用数据库事务语义的伪代码，不是已运行的 Go 工程，也不证明跨域协议已经实现。

### 7.2 核心伪代码

伪代码内部的数量、价格和金额均采用 4.2 节整数单位；`exact(p*q/10^8)` 要求整除，使用不会溢出的中间乘法。`move` 展开了转移的两边，不隐藏清算或分布式一致性能力。

```text
applyBatch(b):                              # 仅处理含 T1、T2 的本例完整成交批次
  检查 b 的来源、元数据版本、交易身份唯一和精度合法
  h = 对 b 规范化载荷计算摘要
  开始数据库事务:
    尝试创建唯一结果键 (b.stream, b.seq)，绑定 b.batch_id 和 h
    若键已存在:
      相同身份与摘要 → 返回原 APPLIED 结果；不同 → 报冲突
    按 trade_id 排序登记来源内唯一成交归属，绑定本结果位置；冲突则回滚
    锁消费游标；要求 b.seq == last_seq + 1，否则回滚并请求补齐
    按统一顺序锁余额、R-B1/R-S1/R-S2，再按 owner 排序锁账户版本行
    读取事务内工作副本 balances、reservations；初始化 lines
    move(from, to, asset, x):
      要求 x >= 0 且两桶属于同一 asset
      balances[from] -= x; balances[to] += x
      lines 追加 (from, asset, -x) 与 (to, asset, +x)
    要求批次中的 T1/T2 身份、对手方、价格和数量逐项等于本例固定输入
    要求 B1/S1 全成，S2 剩余 0.05 BTC
    对每笔成交 t:
      r = R-B1；s = t 对应的卖方预留
      要求 t 的订单、账户、资产与 r/s 绑定一致
      要求 卖单限价 <= t.price <= B1限价，且 t.qty > 0
      cost = exact(t.price * t.qty / 10^8)
      cap = exact(B1限价 * t.qty / 10^8)
      要求 r.remaining >= cap 且 s.remaining >= t.qty
      move(甲预留, 卖方可用, USDT, cost)
      move(卖方预留, 甲可用, BTC, t.qty)
      move(甲预留, 甲可用, USDT, cap - cost)
      r.spent += cost; r.released += cap - cost; r.remaining -= cap
      s.spent += t.qty; s.remaining -= t.qty
    要求 T1.qty == 0.10 BTC 且 T2.qty == 0.15 BTC
    要求 R-B1/R-S1.remaining == 0 且 R-S2.remaining == 0.05 BTC
    要求每个余额非负，lines 按资产汇总为零
    要求各预留 initial == spent + released + remaining
    要求本例各用户各币种预留余额等于其预留明细 remaining 之和
    追加 journal 与 lines；保存余额和预留；last_seq = b.seq
    每个受影响账户版本加一；同事务写含完整多币种变化的通知 outbox
    将该唯一结果键记为 APPLIED，并保存 journal_id 与各账户版本
  提交；返回保存的结果
```

唯一结果键与成交归属的插入、分录、余额、预留、游标、账户版本和通知意图在同一个事务中；校验失败必须使新建身份一并回滚。并发遇到唯一键时，按数据库唯一约束等待原事务的确定结果，不能把另一事务的未提交记录当作成功。通知投递与查询恢复不在本 MVP 范围内，只保存可恢复的通知意图。

伪代码刻意只接纳本例已给定的完整批次，不能把几条 `要求` 外推为通用生产级结果校验器。事务中的 `move` 先构造净变化，最后统一校验；不会逐个提交转出、转入或价差。

### 7.3 输入与预期结果：手工推演

各异常行都从注明的快照独立开始，不把独立变体连续叠加。

| 输入 | 初始条件 | 预期结果 |
|---|---|---|
| 首次处理本例批次，序号 42 | 预留后快照，游标 41；T1 为 0.10 BTC@60,000，T2 为 0.15 BTC@60,100 | 甲 4,985 USDT／0.25 BTC 可用；乙 6,000 USDT；丙 9,015 USDT／0.05 BTC 预留；游标 42 |
| 完全相同的批次 42 再处理 | 上一行已经提交 | 返回原 journal 与 APPLIED，所有余额和预留不再变化 |
