# 大问题 12：Go 怎样限制并发和背压，并在过载时保护撤单？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文不是“多开线程让下单更快”，而是资源有限时如何不丢业务、不误退款，并保留撤单入口。采用现货限价 GTC、零费用、同库账务及多数派日志基线；讨论 Go 并发设计与观测口径，不报告未测量的吞吐成绩。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| goroutine 与并发额度 | Go 的轻量任务，以及允许同时工作的数量上限。 | 应在无限创建任务前取得额度，不能让无数任务堵在队列口。 |
| 有界 channel 与 worker | 容量有限的内存传递队列和处理者。 | 要限制条数、字节与等待时间；入队不是持久受理。 |
| 背压 | 下游忙不过来，上游减少新增工作。 | 扩大缓冲只能拖延拥堵，不能让长期超载消失。 |
| A 前拒绝与历史重试 | 没有持久副作用的新请求可拒绝，旧业务却不能被抹掉。 | 当前重试被限流，不证明其原意图不存在。 |
| A/B/C/D | 意图预留、命令受理、结果裁决、资金入账四个边界。 | 同样队列满，越过不同边界就承担不同后续责任。 |
| context 取消 | 结束这次网络等待或局部调用。 | 不取消已保存意图，不自动解冻，也不等于权威撤单。 |
| 持久待办与租约 | 可重扫任务与临时工作者归属。 | A 后责任不靠原 goroutine，租约过期重投仍用原身份。 |
| actor 单写 | 一个有效执行者串行修改该市场订单状态。 | 不把所有工作都塞进它，也不多开 worker 同写盘口。 |
| 不持锁跨 RPC | 远程等待不应占住余额行锁或订单状态锁。 | 预留凭据与关闭标记支持资格判断，避免同步账户查询形成等待环。 |
| C 提交未知 | 结果是否正式成立尚无结论。 | 暂停后续变更并查询，不能为吞吐跳过；半成品不发布。 |
| 撤单资源保护 | 给撤单与授权关闭保留入口、工作者和提交预算。 | 不是无限优先队列，不保证零等待或必然成功。 |
| 权威顺序与 commandSeq | 已受理命令承诺的裁决先后。 | 撤单保护只能影响未排序准入，不能越过已提交前序成交。 |
| 持久积压与占资配额 | 后台任务也会耗尽容量，新增意图须控制总预算。 | A 前配额与创建协调，保留旧任务的恢复、查询和关闭资源。 |
| 阶段指标与水位 | 分别看各段等待、最老年龄、未知提交和连续进度。 | 不跨市场或拿私有游标乱相减，也不只看 CPU 和队列长度。 |

## 把整篇文章压缩成一个故事

新单洪峰到来，甲的 B2 在事务 A 中保存并预留了 15,000 USDT，接着 channel 满了，甲取消等待，进程又重启。若系统只靠后台 goroutine，任务就会失踪；正确做法是扫描 A 共同保存的待办，用原意图继续投递。没进入 A 的全新请求可以明确拒绝，但当前重试被限流不能抹掉历史业务，A 后拥堵更不能直接丢单退款。

入口先取得并发额度，再创建有限工作任务，同时限制队列条数、字节和等待时间。短事务领取待办后释放锁，远程投递单独有界；租约换人可能重复发送，仍须持久业务去重。撮合 actor 依据已提交输入和绑定凭据裁决，不持锁跨账户 RPC，也不把查询投影当资格权威；C 不确定先停查，不能继续改盘口掩盖日志问题。

为让甲还能退出，入口给 Cancel 和授权 AbortIntent 留资源，但它们取得 commandSeq 后仍按权威顺序执行。若 B2 已成 0.10 BTC，关闭只能撤剩余 0.15；账户尚未结转时仍需留足预留，先支付 6,000、入账 0.10 BTC，再退 9,000，最终可用 14,000。资源保护不授权撤单越过已经在前的成交，也不能因结果队列满而回滚正式事实。

热点市场持续满载时，加投递 worker 只会加长队列，应在 A 前协调新意图配额，保留原义务恢复和关闭能力。观测分别覆盖 A 前排队、A 到 B 待办、B 到 C 裁决、C 到 D 义务年龄及连续水位；账务慢就限制新增责任，而非调大报警或删结果。同一订单簿横拆需要新顺序协议。本文是有界退化与故障窗口的设计推演，没有压测或切主实测结论。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖接入、预留、持久提交、撮合单写及结果消费之间的容量约束，重点是有界并发、分阶段过载语义与撤单资源保护；不扩写 Go 基础，也不重做订单簿专题。

沿用总览的现货限价 GTC、零手续费和 B2 独立变体。四个提交边界分别为 A 意图与预留事务、B 命令多数派持久提交、C 完整结果与 AppliedSeq 原子提交、D 账务事务。日志使用多数派持久化与 epoch 隔离；增加 goroutine 或 channel 均不能改变这些业务边界。分析采用系统边界与失败窗口推演，不虚构压测成绩。

## 第 1 层：先限制什么，才能真正形成背压

**面试官：** Go 怎样限制并发和背压，并在过载时保护撤单？如果每个请求开一个 goroutine，再写到有缓冲 channel，是否已经足够？

**面试者：** 不够，channel 满时仍有无限 goroutine 等待，内存和连接会先耗尽。我会在创建业务 goroutine 前取得并发额度，分别限制请求体大小、在途请求、工作池和队列条数及字节数，并为排队时间设上限。解析、账户事务、持久投递和结果分发使用各自有界 worker；每交易对 actor 只串行修改执行状态，不替代所有服务。channel 只负责进程内调度，发送成功不表示可靠受理，进程崩溃后内容也不会自动恢复。新单与撤单先做资源隔离，是否还能拒绝则取决于业务越过哪个提交边界。查询和慢连接也要独立限额，不能占满交易执行资源后，再用加大缓冲伪装成吞吐提升。

## 第 2 层：同样队列满，不同提交阶段的处置不同

**面试官：** 你说能否拒绝取决于提交边界。如果账户预留成功后才发现提交队列满，是否可以返回过载并直接扔掉这笔新单？

**面试者：** 不能一概扔掉。A 之前确认没有持久副作用，可以明确拒绝本次请求；但重试请求还须识别是否已有原意图，不能据当前入口拒绝推断历史业务不存在。A 提交后已占资且有待提交义务，队列满只能表示调度延迟，要返回处理中并保留原身份；账户事务返回超时则先判定提交是否不确定。B 已提交后命令属于可恢复执行范围，不能为降负载擅自丢弃。C 已提交后成交或关闭结果已经成立，结果消费拥堵不能回滚执行；D 未完成就保留必要预留和结转 PENDING。客户端 context 取消只停止这次等待，不是释放资金的授权。若希望放弃业务，应走同序关闭协议，而不是拿本地超时充当撤单结果。

## 第 3 层：A 之后的工作，不能寄托在后台 goroutine

**面试官：** 你要求 A 后继续完成，但原请求 goroutine 已退出，进程也可能重启。谁保证积压意图最后真的进入可靠日志？

**面试者：** 在 A 的同一数据库事务里创建持久待提交记录，让后台提交器按状态和下次重试时间扫描，而不是依赖请求结束前成功写入 channel。worker 领取有期限租约，使用短数据库事务领取后释放锁，再通过独立的有界调用向日志提交。失败或超时保留待办，用相同 intentId、命令类型和载荷重试；拿到确定的多数派提交结果后才推进本地进度。租约过期可能重复投递，日志中也可能出现重复身份，所以撮合必须持久去重，不能假设租约实现了恰好一次。请求 context 与持久工作流解耦，服务退出时停止领取，未确认工作留待重扫。channel 可以唤醒提交器，但唤醒丢失不影响可恢复性；任何重试都不能新建身份再占资。

## 第 4 层：持久投递不能把 actor 卡在账户网络调用上

**面试官：** 你把网络投递放在短事务之后。撮合 actor 为校验预留再同步调用账户服务，并持有订单锁等回包，会有什么问题？

**面试者：** 这样会让账户延迟扩散到整个交易对，还可能与账户等待撮合结果形成环路。我不会持数据库行锁或订单状态锁跨网络调用，也不会把同步账户 RPC 藏进 actor 的消息处理等待里。预留凭据在 A 提交后签发，绑定意图、载荷和预留；撮合依据可验证凭据及同序关闭标记判断资格，不逐单查询一个会滞后的账户投影，账户也不能单方让凭据失效。actor 只处理已提交输入并生成临时结果，日志写入由有界 I/O 路径完成；C 未确定前不暴露临时状态，也不推进下一条改变状态的命令。必要的提交等待可以暂停单写流水线，但不能用超时跳过该结果；只读查询则走投影，不冒充账户权威。

## 第 5 层：保护撤单的资源，不篡改已经确定的顺序

**面试官：** 你允许 C 等待暂停整个交易对。此时新单把入口和提交资源占满，撤单怎么保护？能否让撤单直接插到已提交新单前面？

**面试者：** 可以保护资源，不能改写既定顺序。我会给撤单及有权限的内部关闭操作预留入口并发、worker 和日志提交份额，并限制账户及交易对的请求速率，避免新单洪峰占满全部连接或数据库资源。两个尚未排序的请求可以按公开的调度规则分配资源，但最终先后仍以 B 的 commandSeq 为准；已经提交的成交来源命令不能被后来撤单越过。C 正在等待也不能插入撤单改变临时计算依据。撤单须有独立幂等请求身份、鉴权及目标校验，预留通道不是无限优先队列，也不保证零等待或必然撤成功。真正的保证是新单不能耗尽所有撤单入口资源，而不是承诺撤单能够战胜权威排序中更早的成交。

## 第 6 层：热交易对不会因为增加 worker 自动扩容

**面试官：** 你给撤单预留了提交资源，但一个热交易对的 actor 已经持续满载，后台待办又不断增长，多加 worker 是否能解决？

**面试者：** 不能，多个 worker 并行改同一本订单簿会破坏单写与价格时间规则；此时增加投递只会加长队列。不同交易对可以分配独立执行分片，但热点交易对仍受单写计算和持久提交能力约束。优化可先做保持原顺序的批量日志提交、减少对象分配及结果批处理，未完成前序 C 不能擅自并行推进。持久积压也必须有上限：新意图在 A 前取得账户和交易对配额，配额占用与意图创建协调提交，过载就停止新的占资，同时保留原意图查询、恢复和关闭的资源。已有义务不能因为超过阈值被删除。若继续横拆同一交易对，必须重新设计全局排序和跨分片匹配，不能把它说成加机器即可解决的小改动。

## 第 7 层：背压是否有效，要按提交阶段与水位观察

**面试官：** 你提出停止新占资来消化积压。怎样判断堵在入口、撮合还是账务，而不是凭 CPU 或 channel 长度猜测？

**面试者：** 我会沿四边界分别观察：A 前排队、拒绝和账户事务延迟；A 到 B 的待提交数量、字节、最老年龄、重试次数和不确定提交；B 到 C 的命令处理落后与结果提交延迟；C 到 D 的未结转批次、最老义务年龄及每交易对账务连续覆盖水位。命令与结果采用同一 commandSeq 时才能在同交易对计算差值，不跨交易对或拿私有 streamCursor 相减。还要监测撤单等待分布、提交器额度、租约回收、goroutine 增长和查询投影滞后。账务变慢时先限制新义务、保留恢复消费资源，不能丢结果或只把报警阈值调大。容量目标和尾延迟必须靠真实测量确定，这里只说明观测口径，不报告未经测量的吞吐数字。

## 第 8 层：故障与过载叠加，仍要回到原身份和权威顺序

**面试官：** 你说不丢已有义务。设 A 成功后 channel 满、请求取消，接着进程重启；恢复期间又收到撤单，而且账务仍然落后，整条链怎样收敛？

**面试者：** 重启后提交器扫描原待办，使用原身份重投 Place，不因断连创建第二次预留。若客户端要求放弃未确定接纳的意图，内部通过 AbortIntent 与 Place 同序裁决：关闭先提交并生效，就留下持久关闭标记，迟到 Place 不能再执行；Place 先处理，就关闭实际剩余量，不能抹掉既有成交。若已经形成 B2 的零点一 BTC 成交，撤单只能关闭余下零点一五；D 落后时仍保留覆盖未结转义务的资金。账务恢复后按结果顺序消耗六千、入账零点一 BTC，再释放九千，最终可用一万四、预留零。保护撤单资源只是帮助它进入 B，不改变这个裁决。无论重放多少次，意图只占资一次，成交不重复记账，也不能撤后再成交。

## 收束：有界的是资源，不可随意丢弃的是业务义务

- **讲透的机制：** 有界接入控制内存，持久待提交承接 A 后责任，actor 保持单写，B/C 决定顺序和事实，D 消化资金义务；背压逐段传递，不能靠无限排队隐藏。
- **易错边界：** channel 非可靠日志；context 不是业务撤销；不持锁跨网络；actor 不同步查账户来决定退款；撤单资源优先不等于命令顺序优先；热点单交易对存在真实容量边界。

**反例验证及预期：** 以下是故障窗口的手工推演，不是已执行压测或工程测试。

| 构造的反例 | 正确的预期结果 |
|---|---|
| A 提交后进程内队列满，随后请求超时并杀掉进程 | 原待办可重扫；不重复占资、不因 context 解冻，也不把队列满当作业务已拒绝 |
| 提交器发出命令后丢回包，租约过期被另一个 worker 重投 | 允许重复提交，稳定业务身份保证只有一份执行效果 |
| 对手单已在 B 排到撤单之前，但撤单来自预留通道 | 仍先处理对手单，撤单只关闭裁决时剩余量；不能宣传插队成功 |
| B2 已撤销但 D 停顿，结果发送队列也已满 | 不丢已提交批次、不全退预留；限制新占资，恢复后按序完成六千成交与九千返还 |
