# 大问题 2：怎样校验请求并保证重复下单只产生一笔业务？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文解决“网络发了几次，业务到底算几笔”。场景是零费用的 BTC/USDT 限价现货，入口以持久唯一约束和资金事务合并同一意图的重试，而不是按看起来相似的价格数量吞掉合法新单。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 认证上下文 | 系统验证登录或签名后确定的真实身份。 | accountId 从这里取得，不能相信请求体随手填的账户。 |
| 限流与幂等 | 限流管能来多少，幂等管同一业务重复来会怎样。 | 限流成功不证明只占款一次；被限流也不等于原业务失败。 |
| RequestKey | 带作用域的业务请求编号。 | 账户＋命令类型＋请求号；不同账户可使用相同字符串。 |
| 规范化载荷 | 把语义相同的输入变成统一业务表达。 | 60100、60100.0 与 60100.00 可得到相同整数价格；执行字段都要绑定。 |
| tick、lot、quote unit | 价格、数量、记账金额各自的最小单位。 | 本文用 0.01、0.0001、0.000001；不用 float64 中转，也不默默舍入超精度输入。 |
| 载荷哈希与审计原文 | 哈希便于定位，规范载荷便于核实真正的要求。 | 不直接哈希原 JSON，也不只凭摘要相等认定业务内容。 |
| 数据库唯一约束 | 多实例竞争时，由持久数据库只允许一份键绑定。 | 先查询不存在不能裁决赢家，进程锁和短缓存也不能替代。 |
| 同事务预留 | 请求身份、意图、占款和待办一起提交或一起撤回。 | 输掉唯一键竞争的事务不能留下第二份冻结。 |
| 提交未知 | COMMIT 的回复丢了，尚不能判断事务成立还是回滚。 | 保持原键查询或重试；不在库外补一笔退款。 |
| 原身份、原结果、当前进度 | 编号不变，原裁决可查，后续阶段可以前进。 | 幂等不意味着永远只返回第一次 HTTP 文本。 |
| 前置拒绝契约 | 尚未创建意图的拒绝，是否永久记住要单独约定。 | 本文余额不足且未绑定时可后来重试成功，不默认缓存首次拒绝。 |
| 撮合去重与批次去重 | 一个挡重复执行，一个挡重复运输导致重复入账。 | 入口只创建一个意图，不代表后面日志只出现一次。 |
| TTL 与持久身份 | TTL 是按时间自动失效；业务身份却不能轻易忘掉。 | 可归档明细，但旧请求不能因缓存过期变成新单。 |
| 有意新单与越权查询 | 真的再买一次要用新键；知道键也不等于有权限。 | 相同参数可对应两笔合法业务，查询仍须鉴权。 |

## 把整篇文章压缩成一个故事

甲下 B1，买 0.25 BTC、限价 60,100，请求号 buy-001。入口先从认证结果确认账户，把价格解析为 6,010,000 ticks、数量解析为 2,500 lots；相乘是 15,025,000,000 个最小 USDT 单位，即 15,025 USDT。甲把价格文本改写成 60100.00 再发，仍是同一载荷；偷偷改成 0.30 BTC 则是同键异载荷，必须冲突，而非覆盖原单。

两个实例同时收到原请求，谁先查到空记录都不算赢家。数据库唯一约束和同一事务裁决：只有一份请求绑定、意图、预留和待办能共同提交；输家结束失败事务后再读赢家，不能留下额外占款。若提交回复断线，服务沿原键确认；查不清就诚实返回未知，不另起业务，也不在数据库外猜着退款。

换一个独立情形，甲首次余额不足，事务没有建意图或留下绑定，后来补足资金再用原键，本文允许重新尝试。若产品要永久固定首次拒绝，就得另存请求决策，不能假装当前已经支持。反过来，一旦意图成功绑定，或已有正式撮合拒绝，后来的余额变化不能把旧键改解释成新订单；原身份、原裁决和演进进度要分别保存。

提交器重发可能产生多个命令位置，撮合仍须持久去重，账户对原结果也须去重；这不是给网络贴“恰好一次”标签。终态后可归档明细，却不能按一天 TTL 忘掉身份，让旧 buy-001 重新下单。甲确实想再买时应用新键，另一账户同名请求要隔离，拿到甲的键也不能越权查询。归档后的查询也仍须校验当前权限，不能把知道旧请求号当成账户所有权。这四种区分才同时防重复、误去重和泄露。

**流程位置与核心机制：**负责从外部请求到唯一持久意图的边界，深入身份、规范化、唯一约束与保留策略；命令可靠提交见母题 03，撮合状态所有权见母题 04。

**必要前提：**沿用限价 GTC 现货模型。B1 的请求号为 `buy-001`，数量 0.25 BTC、限价 60,100 USDT/BTC，初始预留 15,025 USDT。请求重试不能生成另一笔下单意图。

## 第 1 层：把输入校验与业务幂等放在同一条接入链路

**面试官：**怎样校验请求并保证重复下单只产生一笔业务？

**面试者：**我会先从认证上下文确定 accountId，不能直接相信请求体中的账户字段，再校验交易权限、交易对、方向、订单类型、价格数量精度和业务上限。十进制字符串按整数单位解析，乘法前检查溢出。限流是接入保护，不是幂等机制。

通过基础校验后，以 accountId、commandType 和 clientRequestId 组成请求键，在账户数据库内唯一绑定规范化载荷和下单意图。首次请求与预留、待提交记录同事务提交；同键同载荷的重试返回原 intentId 及当前处理进度，同键异载荷返回冲突。因此 B1 即使因响应丢失连发多次，也只对应一个预留，而不是每个 HTTP 请求都扣一次可用余额。

## 第 2 层：同一载荷怎样定义，避免文本不同误判冲突

**面试官：**你说比较规范化载荷。价格写成 60100、60100.0 和 60100.00 算同一个请求吗？

**面试者：**在本模型中它们解析为同样的 priceTicks，就应具有相同业务语义；不能直接对原始 JSON 字节算哈希。规范化载荷包含账户作用域、交易对、方向、订单类型、有效期规则、整数价格和数量等会影响执行的字段，并使用固定字段顺序与规范版本编码。追踪号、网络时间等非业务元数据不参与“是否同一订单”的比较。

同时必须拒绝超出精度的有效数字，不能悄悄四舍五入后制造另一种意图。B1 应解析为 6,010,000 ticks 和 2,500 lots；其乘积为 15,025,000,000 个 USDT 账务单位。可以用哈希辅助索引，但要保存可核对的规范载荷，不能把哈希相等当作唯一审计证据。

## 第 3 层：多实例同时看到请求不存在时谁是赢家

**面试官：**规范化解决了比较问题。但两个接入实例同时查不到 buy-001，都准备预留 15,025，怎样避免竞争？

**面试者：**最终裁决必须来自数据库唯一约束，而不是先查再写或进程锁。事务中创建唯一请求绑定、意图、预留和待提交记录，只有一个事务能成功拥有该请求键。若另一个事务发生唯一键冲突，应结束其失败事务，再读取已提交赢家记录，比较规范载荷，返回原结果或冲突。

资产更新也在同一事务里，所以输家不能留下第二笔冻结。实现可以先争用请求键，再锁余额，减少无谓竞争；如果执行顺序不同，也必须保证唯一键失败导致整个事务回滚。对尚未结束的并发事务要按数据库隔离和锁等待规则处理，不能把一次暂时查不到当成“可以生成新键重试”。跨进程正确性来自持久约束，Redis 锁至多用于减少压力，不能替代这个边界。

## 第 4 层：唯一键有了，余额和返回结果怎样一起落地

**面试官：**赢家拿到了请求键，但它扣余额后数据库连接断开。客户端不知道事务是否提交，又重试了，怎样返回正确结果？

**面试者：**连接断开表示提交结果未知，不等于回滚。客户端仍携带原请求键，服务查询持久请求绑定。如果事务已提交，就能找到原意图及预留，返回原身份，不再次扣款；如果事务确实未提交，唯一约束与余额事务允许同一业务重试重新争取创建。查询和重试即使竞争，也必须落到相同唯一约束，而不是凭本地判断绕过它。

返回结果不应仅缓存最初一个 HTTP 文本，因为订单可能从“正在提交”走到全成。应区分不可变的业务身份、原命令处理结果和可演进的当前进度。若数据库本身不可用而无法判明，返回暂时未知或可重试错误，不声称“下单失败且未扣款”，更不能在数据库之外补一笔反向资金操作。

## 第 5 层：第一次响应是余额不足，重试是否还能成功

**面试官：**你只保证事务成功时保存意图。如果首次请求余额不足，用户后来充值再用同一个键，会得到什么？

**面试者：**要明确产品契约，不能把所有失败混成同一种幂等。本专题的最低保证是：没有提交意图和预留，就没有可执行订单；首次余额不足的事务不会遗留半笔预留。同一键若尚无持久绑定，后来重试可以重新尝试并成功，但这意味着“前置拒绝并非永久记忆”，接口文档必须说明。

如果产品要求连余额不足等业务拒绝也固定为首次结果，就要单独持久化请求决策记录，并让后续重试返回该拒绝，用户另换业务键才能发起新意图。两种都可以设计，不能宣称基线自动支持后者。本模型一旦成功绑定意图，或已提交确定的撮合拒绝，就必须保留其身份和结果，不能因余额变化把同一键重新解释成另一笔成功订单。

## 第 6 层：入口幂等是否足够保证全链路只执行一次

**面试官：**同一键只产生一个意图了。提交器超时重发，命令日志里出现两条 Place，还会不会有两次成交？

**面试者：**入口幂等只覆盖创建意图和占资，不自动覆盖撮合执行。日志中的 commandSeq 标识一次输入位置，intentId 或 orderId 标识业务；两个位置可能携带同一业务，所以撮合还要持久维护业务去重结果。第一次合法 Place 提交接纳结果后，重复 Place 只能引用原接纳，不重新入簿、不刷新优先级，也不产生第二组账务动作。

若第一次结果提交状态未知，必须先查明该结果边界，再处理下一命令，不能靠内存布尔值认定完成。快照和恢复也要包含这些身份与关闭标记。之后账户消费还有批次去重，防止同一个已提交结果被重复运输而重复记账。这些幂等各自覆盖不同边界，不是给系统贴一个“exactly once”标签就结束。

## 第 7 层：幂等记录能不能保留一天后自动删除

**面试官：**你已经需要账户、撮合和消费多处去重。为了控制存储，订单结束一天后清理请求记录可以吗？

**面试者：**只有能证明清理后旧请求绝不再被当作新业务，才可以。单纯 TTL 到期会让断线客户端或滞留任务带着旧 buy-001 回来，系统再次创建意图；即使旧订单早已全成，也会重复交易。活跃订单、提交未知意图、未完成收尾以及仍可迟到的任务，尤其不能直接清理绑定。

可把完整响应和明细归档，但保留紧凑的请求身份、载荷摘要、终态引用或禁止复用标记。若协议设计显式的请求代际和期限，也要在入口、日志投递和撮合验证中统一拒绝过期代际，并证明旧命令不再有效，不能只删缓存。本专题不假定这个清理协议已经实现，默认身份在所承诺的重试范围内持久保留，不能默许 TTL 后自动变成新订单。

## 第 8 层：重试规则怎样防止误去重和越权查询

**面试官：**如果请求键保留很久，用户第二次确实想买同样的 0.25 BTC，该怎样区分？另一账户拿到 buy-001 能查到结果吗？

**面试者：**业务相同不等于请求相同。用户有意再买一次，必须生成新的 clientOrderId；同一账户、同一命令类型、同一键表示重试原意图，而不是“载荷一样就全局合并”。因此不能仅按价格数量哈希去重，否则两笔有意订单会错误地合成一笔。反过来，换键重试超时订单也会绕过幂等，客户端应先查原键。

键包含认证得到的账户作用域，查询也必须重新校验权限，不能因知道请求号就看到他人订单。验证时我会并发提交同键同载荷、同键异载荷、不同账户同字符串，以及同账户不同键同载荷四组情况：分别预期一笔业务、一个赢家加冲突、账户隔离、两笔独立业务。这样才能同时证明没有重复执行，也没有错误吞掉合法订单。

## 本题收束

- **讲透的机制：**稳定请求键、语义规范化、数据库唯一约束与预留同事务，随后由撮合与账务各自覆盖其重复边界。
- **最容易答错：**把幂等当成 Redis 短期缓存；把同样的参数当成同一业务；把前置校验拒绝和已提交结果承诺成同一种保留语义。
- **检验反例：**B1 预留事务提交、HTTP 响应丢失，两个实例同时收到原键重试。预期只有一个 intentId、一个 reservationId、总预留 15,025 USDT；把数量改为 0.30 的同键请求必须冲突，而不是覆盖旧订单。
