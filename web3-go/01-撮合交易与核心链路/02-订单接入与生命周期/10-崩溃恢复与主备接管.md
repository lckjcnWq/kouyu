# 大问题 10：崩溃和主备切换后怎样恢复原订单及执行结果？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文恢复的是已经确认的业务历史，不只是“服务又能启动、盘口总量差不多”。条件为现货限价 GTC、零费用、同库账务，输入与结果分别有多数派持久提交语义；异步备机不自动具备这些能力。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 输入日志 B | 记录哪些命令已经可靠受理及它们的顺序。 | Place、Cancel、AbortIntent 可已受理但还未裁决。 |
| 结果日志 C | 记录哪些成交、订单变化和关闭已正式成立。 | 完整 ResultBatch 与 AppliedSeq 原子提交，回执丢失也不撤销事实。 |
| 提交端点与逻辑序号 | 权威确认处理到了哪里，并以每市场命令号计数。 | S、R 不是底层物理行号，也不是 MQ offset。 |
| 一致快照 S | 在同一完整结果边界保存的业务底片。 | 订单在 S、去重在 S-1 的拼接图不能恢复。 |
| 数量、版本与 prioritySeq | 分别保留数量去向、更新次序和首次排队资格。 | 只存每档总量或剩余量，会丢失成交对象与优先级。 |
| 去重与关闭标记 | 记住旧请求结果，以及旧意图不得重开的事实。 | 终态离簿也不能删掉，防重复单和退款后迟到成交。 |
| 原结果应用 | 按已提交变化重建状态，不重新裁决。 | S+1 到 R 沿用原批次、成交身份和规则，不再生成新成交。 |
| 无结果尾部 | 输入已提交，权威确认却尚无结果的后缀。 | 仅此部分从 R+1 继续执行；回复没到不证明无结果。 |
| 确定性与规则版本 | 重做未结果尾部仍使用原规则和决策输入。 | 不用当前时钟、随机数或新配置悄悄改历史含义。 |
| epoch / fence | 写入任期 / 存储拒绝旧任期的权限屏障。 | 输入和结果两条新写路径都要挡旧，不能只让进程自觉退出。 |
| 前序 AppliedSeq 校验 | 只有已处理位置仍符合预期，才允许追加下一结果。 | 防重复和跳位提交，未知时先查清不继续。 |
| 已提交历史与旧主新写 | 历史合法事实保留，旧权限的新事实不能成立。 | 围栏前合法提交的旧任期结果仍有效，补发由账户去重。 |
| 可丢尾部与持久待办 | 未提交临时副本可丢，已保存责任不能静默遗失。 | A 已成而 B 未成，仍需重扫原待办或授权关闭。 |
| 账户独立水位 D | 账户记着自己的账处理到哪，与撮合恢复位置不同。 | 补交原批继续结转，不把账户余额倒回旧撮合快照。 |

## 把整篇文章压缩成一个故事

甲的 B2 已成交 0.10 BTC 并撤掉 0.15，撮合提交结果后没收到确认就失联，账户还没处理。新进程不能因为旧主没收到回包，就把这段当未执行。它先取得输入与结果的权威提交端点，再验证快照 S；底片要包括数量、版本、原排队位置、去重、关闭和规则，不能只重建一个总量相同的盘口。

查明原成交与关闭已提交到 R，新进程就应用 S+1 到 R 的原结果，保留原 tradeId 和关闭结论，不把 Place 重送进撮合算法造新成交。只有 R 后输入已受理且确认没有结果的尾部，才按原规则继续执行；提交状态未知先停查，不用最新时钟或随机编号替代历史。半成品快照不参与恢复，前序缺口也不能靠猜测跳过。

接管者取得更大 epoch，还得等权威存储对输入与结果都启用拒旧，旧主即使醒来继续算，也不能提交新事实。若旧主任期在围栏前已经合法提交，结果仍要保留；即使它后来重发旧批次，账户也只核验原源记录并去重。多数派不可用时停止新的可靠承诺，不能凭单机还活着就继续宣称无损接管。

甲的账户按自己的水位补交原结果，只支付 6,000、退 9,000，最终可用 14,000 并获得 0.10 BTC，不因撮合重启回滚余额或再付款。另有仅 A 完成的意图由持久待办继续，不许静默丢失。验收要比较结果前缀、身份、关闭、数量和双边分录，进程能启动不是证明；证据缺失时保持受限并补齐历史，不以猜测恢复对外承诺。本文没有执行真实切主或故障注入。

**流程位置与核心机制：**覆盖撮合进程崩溃、备机接管以及恢复后的结果续交付。重点是输入与结果两条持久日志的边界、快照完整性、确定性尾部执行与 epoch 隔离，不重新展开订单簿算法。

沿用现货限价 GTC、零手续费及相关账户同一事务数据库。A 保存意图、预留和待提交记录，B 多数派持久提交命令，C 在有效任期内原子提交 ResultBatch 与 AppliedSeq，D 原子完成全批双边账务、分录、去重与进度。恢复仍需区分“命令已受理”“执行已确定”和“账务已完成”。

## 第 1 层：恢复的不是一份内存订单簿

**面试官：**崩溃和主备切换后怎样恢复原订单及执行结果？

**面试者：**要恢复的是已确认业务事实，而不只是把挂单重新放回内存。输入日志记录 B 已可靠受理的 Place、Cancel、AbortIntent 及顺序；结果日志记录 C 已确定的成交、订单变化、意图关闭和 AppliedSeq。两者不能混为一条“收到过请求”的清单：命令提交不代表执行完成，结果提交后即使回包丢失也不能推翻。恢复时先确认两条日志的提交端点，再从一致快照恢复状态，应用快照之后已提交的结果，最后执行已有输入但尚无结果的尾部。后文 S、R 与 AppliedSeq 都按每交易对逻辑 commandSeq 表示，不与底层物理日志索引或 MQ offset 混用。账户 D 有自己的持久消费进度，通过原结果继续结转，不能因为撮合重启而把账户余额恢复到旧快照。

## 第 2 层：快照必须覆盖哪些隐藏状态

**面试官：**你说先恢复一致快照，如果快照只有价位和剩余数量，为什么重放日志还可能产生新订单或错误优先级？

**面试者：**快照必须是某个已提交结果位置 S 的逻辑状态，包括订单身份、数量分量、订单版本、价格与 prioritySeq，足以恢复同价队列；还要保存业务去重及原处理结果引用、意图关闭标记、有效规则版本和相关配置、AppliedSeq 及日志关联水位。否则迟到 Place 可能因关闭标记丢失重新接纳，重复请求也可能产生第二笔业务。各部分必须来自同一个 S，不能用订单在 S、去重在 S-1 的拼接快照。可以采用一致性复制或写时复制，但快照内容、校验信息与清单完整持久后才能发布；半成品不可作为恢复基线。终态详情可引用可读归档，但去重和关闭能力不能随活跃订单一起消失。

## 第 3 层：已有结果为什么不重新撮合

**面试官：**快照停在 S，结果日志已提交到 R；直接把 S 之后的命令都重新撮合，得到相同结果不是更简单吗？

**面试者：**对于已有提交结果的区间，应把 S+1 到 R 的原 ResultBatch 当作事实应用，恢复订单数量、队列、版本、去重和关闭状态，而不是再次执行撮合并发布新成交。订单变化必须足以重建状态，成交身份、撮合序号与规则版本也沿用原值。否则即使数量碰巧相同，新生成的 tradeId 也可能让账户再次付款；规则或实现变化更可能让成交对象不同。ResultBatch 和 AppliedSeq 在 C 原子提交，因此恢复时不应出现进度已推进、对应结果却不存在的合法状态。应用期间校验批次连续性和前后版本，重建内存不能再次追加同一业务结果；重新交付账户的也只能是原批次。

## 第 4 层：只有输入、没有结果的尾部怎么办

**面试官：**已有结果不能重算，那 R 之后还有多数派已受理命令，原主也许计算到一半，这部分如何执行？

**面试者：**先查清 C 的提交结论，不能把“没有收到追加确认”直接当作没有结果。确认结果端点为 R 后，才从 R+1 按 B 已提交顺序执行尾部，丢弃旧主未提交的临时变更集。每条命令使用当时记录的规则版本、资格绑定与必要决策输入，不重新读取当前时间、随机数或外部最新状态来改变结果。同价优先级取权威接纳顺序，价格和数量使用相同整数规则；业务去重与关闭标记也参与执行。重做期间仍通过 C 提交完整结果，前一条提交不确定就停止并查询，不能跳过。特别是 AbortIntent 在前、迟到 Place 在后时，恢复后仍须拒绝接纳，不能因进程换了就重新赋予资格。

## 第 5 层：备机必须具备怎样的日志能力

**面试官：**按规则执行尾部的前提是备机拿到正确日志。如果只把内存订单变化异步发给备机，能兑现你前面的恢复承诺吗？

**面试者：**不能。本基线要求日志存储对 B 和 C 都提供多数派持久提交、确定的提交端点和新任期拒旧能力；C 的完整批次与 AppliedSeq 是同一原子记录，且只能引用已提交输入。结果不能只落原主本地盘，否则已确认成交仍可能在接管时消失。这里是具备这些语义的复制日志抽象，不是声称任意异步主从数据库都能做到。备机本地应用可以落后，但接管前必须补齐已提交日志，取得可用快照、尾部结果和相应规则资料，再恢复到共同基线。B 的受理确认与 C 的执行确认分别在各自多数派持久后发出；丢失多数派时应停止新的可靠确认，不能靠一台旧主继续承诺可恢复。

## 第 6 层：备机接管时旧主仍活着

**面试官：**即使日志多数派可用，旧主网络隔离后继续工作，两个进程都自称单写者，怎样让旧主真正失去写权限？

**面试者：**单写者必须由存储 fence 保证，不能靠进程自觉退出。接管取得持久的更大 epoch，输入和结果追加都由权威存储校验该授权任期；新主须等两条写入路径都启用新任期拒旧，再读取确定端点并提供服务。C 还检查前序 AppliedSeq，防止同一任期重复或跳位追加。旧主即使仍算出成交，其旧 epoch 写入也不能提交，未提交结果不得发布成有效事实；若旧主在 fence 生效前已经合法提交，则新主必须保留并恢复它。向 MQ 的重投不能被物理阻止也没关系，账户只处理可核验的已提交原批次并去重。只有在存储端检查任期，隔离才覆盖超时、暂停恢复和网络分区。

## 第 7 层：哪些数据可以丢，哪些绝不能丢

**面试官：**旧主被隔离后可能有一段日志被截断，这算不算丢单？尤其客户端没收到回包，应该按什么标准判断？

**面试者：**必须按提交事实区分。没有跨过多数派提交边界的输入尾部、试算结果和发送队列可以丢弃，不能把它们当已成立成交；但 B 已确认的命令不能消失，必须已存在结果或作为待执行尾部继续处理，C 已提交结果也不能被新主改写。客户端没收到回包不代表未提交，恢复后可能查到原受理或原成交。若 A 已提交而 B 尚未提交，账户仍保留意图、预留和待提交记录，继续投递原身份或通过 AbortIntent 有序关闭，不能静默遗失。若 C 已提交而 D 落后，则重新交付原批次，D 以同事务去重接续；不能把重启当退款理由。允许丢未提交副本，不等于允许丢已确认业务。

## 第 8 层：怎样验收恢复结果而不只看能启动

**面试官：**你已经区分可丢尾部和已确认事实，恢复验收怎样证明没有重复成交、漏账或撤后再成交？

**面试者：**应逐个构造 B、C、D 之间的崩溃历史，核对恢复后的结果前缀、身份、订单数量和资金义务，而不只检查进程启动。以 B2 为例，成交和关闭都在 C 提交、D 尚未处理时崩溃，恢复应仍是累计成交 0.10、撤销 0.15、剩余零，不能生成新 tradeId；账户随后只支付 6,000、退 9,000，最终可用 14,000。另验 AbortIntent 已提交而 Place 迟到，恢复后仍不得入簿；验旧 epoch 追加被拒绝，合法已提交前缀不被截断。还要覆盖只有 B 的尾部、空结果、破损快照回退，以及 D 提交但确认丢失的重投。所有断言同时检查连续水位、双边分录与每币种守恒；这些是验收预期，不声称已实测通过。

## 本题收束

- **讲透的机制：**快照恢复同一逻辑时刻的完整状态，已提交结果重建既有事实，未结果输入尾部按原规则执行，存储侧 epoch fence 限定唯一合法写入者。
- **易错边界：**输入多数派持久不能代替结果多数派持久；AppliedSeq 不是账户消费进度；截断未提交副本不等于可以删除已受理命令；异步备机不自动拥有无损接管能力。
- **反例与预期：**旧主已提交 B2 成交与关闭，却未收到 C 确认就失联。错误恢复把这一段当无结果尾部重撮合；正确恢复先查明结果提交端点，应用原成交与关闭，补交原批次，禁止旧 epoch 新写，账务重投仍只产生一次效果。
