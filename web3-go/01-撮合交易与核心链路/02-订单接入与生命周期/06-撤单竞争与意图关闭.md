# 大问题 6：部分成交、撤单和迟到下单怎样得到唯一结果？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文把“我要撤了”变成一个有权威位置、持久结果和资金收尾的动作。使用独立 B2：甲从 20,000 USDT 开始，限价 60,000 买 0.25 BTC、预留 15,000，先成交 0.10；零费用、同库账务，不把不同竞争路径叠加执行。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| Place / Cancel / AbortIntent | 下单、撤已有余量、关闭可能还在途的意图。 | 三者共享本交易对权威顺序，但关闭对象与契约不同。 |
| 权威顺序 | 系统正式承诺的命令先后。 | 不看客户端按键时间；排在撤单前的成交仍可成立。 |
| CANCEL_PENDING | 正在办理撤单请求。 | 不等于余量已经受到保护，不能停止前序命令执行。 |
| 实际剩余与撤销量 | 撤单生效那一刻还没成交的部分，以及本次被取消的部分。 | 已成量不倒退，原量＝累计成交＋剩余＋撤销。 |
| 边界 B / C | 输入可靠受理 / 完整裁决结果正式提交。 | 有撤单位置不等于已撤；关闭要越过 C 才成立。 |
| 临时变更与 AppliedSeq | 草稿变化和已完整裁决的位置。 | 全部订单、关闭、预留动作与进度一起原子提交。 |
| 未知目标 | 普通 Cancel 在该位置没找到可撤订单。 | 不禁止尚在途的 Place 将来被接纳。 |
| 授权关闭与墓碑 | 只有有权限的流程才能永久记下原意图不得执行。 | 不能猜一个 intentId 就抢先阻断他人的业务。 |
| 先关闭 / 先接纳 | 同一意图两种互斥裁决次序。 | 前者拒迟到单且不伪造入簿历史，后者保留成交只撤余量。 |
| 持久业务去重 | 记住旧命令已经怎样裁决。 | 重试返回原结论，新键再次撤终态单也不能新增取消或退款。 |
| 空效果批次 | 重复业务在新命令位置留下进度，但不再产生资产动作。 | 不能复制原成交或原释放清单，否则可能二次履约。 |
| 执行终态与预留 | 不再新增执行，不等于旧付款已经完成。 | CANCELED 时仍可能预留 15,000，其中只有 9,000 可退。 |
| 连续结转与 lastAppliedSeq | 账户按权威结果无缺口推进，并在事务里记下进度。 | 关闭先到要补前序，不能抢在成交前退款。 |
| 恢复与 TTL 清理 | 重启仍须记住旧身份；时间到不自动撤销关闭事实。 | 资金归零也不证明迟到 Place 不可能出现，不能随意删墓碑。 |

## 把整篇文章压缩成一个故事

甲的 B2 已买到 0.10 BTC，还有 0.15 挂着，正好新卖单 0.04 与撤单竞争。若卖单先在权威顺序执行，累计成交变 0.14，撤单只撤 0.11，甲共付 8,400、可用 11,600；若撤单先执行，则仍只成交 0.10、撤掉 0.15，甲付 6,000、可用 14,000。这是重置初始条件的两种分支，不按用户按键时间决定，也不能把两个结果叠加。

日志为撤单定好位置，只完成可靠受理。撮合还得把真实撤销量、订单版本、关闭事实、资金动作和 AppliedSeq 在完整结果中共同提交，才能说已撤。提交确认丢了先查清，不能先发退款再补墓碑；否则重启忘掉关闭，原钱已退，迟到订单却又能买币。

再看 Place 尚未到达的独立情况：甲先发普通 Cancel，得到未知目标，这只说明当时没单，不能退款。真正放弃须由有权限的 AbortIntent 留下持久关闭；若它先处理，迟到 Place 必须拒绝，未接纳对象不伪造撤销量；若 Place 已先处理，就保留成交、撤真实余量。重复关闭或迟到单在新位置只引用旧裁决，不得重复生成释放动作。

没有新增成交的 B2 即使已 CANCELED，账务落后时仍需保留 15,000，先付 6,000 并入账 0.10 BTC，再退 9,000。运输乱序先补齐，记账、去重和消费水位同事务提交，确认丢失也不能二次退款。恢复快照还要保存关闭与去重，不能因订单离簿、余额归零或 TTL 到期便失忆。系统还要分别展示撤单受理、关闭成立和资金完成，等待太久应告警并恢复原任务，而不是把页面成功当成资金已经可花的凭据。本文推演的是这些边界，不是已执行的故障或退款测试。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖 Place、Cancel、AbortIntent 在同一交易对的顺序裁决、完整结果提交和资金收尾。重点不是罗列状态枚举，而是解释哪些成交仍有效、什么才真正阻止迟到执行，以及关闭事实如何持久生效。

使用总览的 **B2 独立变体**，不接在 B1 后面：甲从 20,000 USDT 开始，买入 0.25 BTC、限价 60,000，预留 15,000；先成交 S1 的 0.10 BTC，剩余 0.15 BTC 挂单。仍为现货限价 GTC、零费用、相关账户同一事务库；A 预留、B 可靠命令、C 完整结果、D 账务四边界不变。

## 第 1 层：撤单撤的是尚未成交的数量

**面试官：** 部分成交、撤单和迟到下单怎样得到唯一结果？

**面试者：** 在这个模型中，三者必须由同一交易对撮合单写者按已提交命令顺序裁决，接入服务不能直接把订单改为已撤销。B2 已成交 0.10、剩余 0.15，撤单若在没有新增成交时生效，只将剩余 0.15 转为撤销量，不能撤回前面的成交。最终原始量 0.25 等于累计成交 0.10 加剩余零加撤销 0.15。客户端看到撤单请求已受理，只代表命令进入可靠处理范围，不代表这 0.15 已被保护。普通 Cancel 处理已有订单，必须校验认证账户拥有目标 orderId，不能仅凭知道订单号撤单；要在 Place 是否已经到达都不确定时放弃整个意图，还需要 AbortIntent。两种命令职责不同，但都不能绕过权威顺序和结果提交。

## 第 2 层：新增成交与撤单谁先到，不看客户端时钟

**面试官：** 你说只撤真实剩余量。若 B2 挂着的 0.15 BTC 又遇到一个卖出 0.04 BTC 的对手单，同时甲发撤单，怎么算？

**面试者：** 这是从 B2 部分成交状态分出的两个互斥时序，不把它们连续执行。若新增卖单按权威顺序排在 Cancel 前，并以 60,000 成交 0.04，B2 累计成交变成 0.14、剩余 0.11，Cancel 只能撤 0.11。结转后甲支出 8,400，持有 0.14 BTC，可用 11,600 USDT。若 Cancel 在前，先关闭 0.15 的执行资格，新增卖单不能再与 B2 匹配，B2 仍只成交 0.10，最终可用 14,000、持有 0.10 BTC。客户端发起时间、网关收到时间和 CANCEL_PENDING 都不能推翻这个顺序；撤单并不追溯性冻结已经排在它前面的输入。

## 第 3 层：排序已确定，为什么还不能马上报告已撤

**面试官：** 既然 B 给出了撤单位置，单写者也算出了撤销量，为什么还要等 C，才能说关闭真正成立？

**面试者：** B 的多数派持久提交确定命令进入可恢复处理范围，也确定它相对其他输入的位置，但不等于执行结果已经提交。单写者先在临时变更集中计算成交、撤销和订单版本，再把完整 ResultBatch 与新 AppliedSeq 在 C 原子持久提交。只有越过 C，订单变化和相应成交义务才是可对外发布的事实；不能先改权威可见内存并回包，再希望稍后补日志。若 C 的提交确认不确定，先查该位置是否已提交，未查清前不处理下一条。这样既保留 B 的排序约束，也避免崩溃后撤单回报存在、权威关闭却丢失。有效任期检查还要阻止旧写入者继续提交。

## 第 4 层：查无订单不等于意图已关闭

**面试官：** 你保证了已有订单的关闭。但 Place 回包丢了，我先发普通 Cancel，结果是“未知目标”，能否据此退款？

**面试者：** 不能。未知目标只说明普通 Cancel 在自己的裁决位置没有找到可撤订单，不证明那个意图以后不能被接纳。Place 可能还停在账户待提交记录里，或仍在网络中，晚于 Cancel 进入顺序日志。若把“查无订单”当作永久关闭并退款，迟到 Place 仍可能用原预留凭据进入撮合，形成无资产支持的成交。这个 Cancel 结果也不能改写成已经撤掉原始数量，因为根本没有入簿历史。我们需要的是针对意图的持久否定事实：不仅这次没找到，还要保证将来同一意图不得执行。普通未知目标响应没有该契约，因此未知与已关闭必须分开表示。

## 第 5 层：AbortIntent 怎样关闭尚未到达的 Place

**面试官：** 那个持久否定事实由谁建立？如果任何人都能先占一个 intentId 写关闭标记，不会被恶意阻断下单吗？

**面试者：** AbortIntent 是经过授权的内部命令，必须验证请求方有权关闭已绑定账户和预留的那个意图，不能让外部随意提交猜测出的标识。它与 Place 共享同一交易对序列：若先于 Place 被处理，在 C 写入持久关闭墓碑，并给出该意图未接纳的关闭结果；没有活跃订单就不伪造订单撤销量。之后 Place 校验资格时也必须检查墓碑，不能仅凭签名放行。若 Place 在前，AbortIntent 就按真实剩余量关闭；若已全成，仅返回已有成交义务，不制造退款空间。关闭命令本身也有请求身份，重试保持原目标和授权绑定。账户只能依据这份已提交事实进入后续释放，而非提交 AbortIntent 时就解冻。

## 第 6 层：墓碑和关闭结果之间不能留崩溃窗口

**面试官：** 你先说写墓碑，又说给账户关闭结果。如果墓碑写成功而结果没写，或者结果先写后墓碑丢了，会怎样？

**面试者：** 不能把这两件事当成独立提交。关闭标记、订单剩余量变化、必要成交信息、预留动作和新的 AppliedSeq，都包含在 C 的同一完整原子结果记录中；恢复时再从已提交记录重建派生状态。提交前崩溃，这次处理没有可发布效果，接管者按原位置重做；提交后崩溃，接管者恢复原关闭结果，不重新解释一次新业务。尤其禁止先把释放事件交给账户，再异步持久化墓碑，否则退款后重启会重新接纳迟到 Place。即便内存中先做临时关闭，也不能让未提交状态暴露给后续撮合或回报。C 要么同时留下禁止执行和可结转依据，要么都尚未成立。

## 第 7 层：重放不能再撤一次、再退一次

**面试官：** C 已经共同提交。但关闭回包丢失、客户端重试，Place 又被提交器重复投递，怎样避免重放产生第二份效果？

**面试者：** 接入用请求键和载荷绑定识别重复命令，Cancel 的键必须绑定不可变的目标 orderId，同键改目标属于冲突。撮合还要持久保存业务身份及处理结论，不能假设日志只会出现一次。相同 Cancel 请求返回原裁决结果；换新请求键再次撤同一终态订单，只能返回终态事实，不再增加撤销量。相同 AbortIntent 或迟到 Place 也必须读取原关闭结论，不能重开意图。重复命令即使占据新的 commandSeq，该位置仍要提交明确结果并推进 AppliedSeq，但它引用原业务结果，不复制原成交和释放动作。原位置恢复重放时，稳定的 batchId 和 tradeId 也不重新生成。这样既保留命令序列连续性，又让业务效果只有一份。

## 第 8 层：已撤销以后，预留为什么还可能是 15,000

**面试官：** 你已经做到唯一终态。回到没有新增卖单的 B2：订单 CANCELED 后，账户为什么还可能占着全部 15,000 USDT？

**面试者：** 因为订单执行和账务结转是两种进度。B2 的初次成交已在 C 确定，撤单关闭剩余量也已提交，但 D 可能尚未消费它们，此时原预留 15,000 仍覆盖全部未结转事项。其中 6,000 是买入 0.10 BTC 的既有付款义务，9,000 才是撤掉 0.15 BTC 后可退的资金。终态保证不会再新增该单成交，不代表旧成交已经付款，更不代表整笔预留可退。正确结转先消耗 6,000 并给甲增加 0.10 BTC，再依据关闭结果返还 9,000，最终可用 14,000、预留零。账户暂时落后允许存在；看到 CANCELED 就全退 15,000，会让甲同时保有成交资产和本应支付的钱。

## 第 9 层：运输乱序时怎样保证先履约、后退款

**面试官：** 你要求先处理成交再处理关闭，但结果运输可能让关闭先到，或者 D 提交后确认丢失，具体怎么守住资金顺序？

**面试者：** 账户消费者只对权威已提交的完整批次执行 D，并按该交易对结果序列连续推进。关闭批次先到而前序缺失时，先缓冲或补拉，不能根据终态投影抢跑；无成交的结果也要有明确进度，不能误判成缺口。在同一账务事务中处理批次内相关账户、预留消耗与返还、分录、批次去重和 lastAppliedSeq。若 D 提交后确认丢失，重收同一 batchId 时读取已处理记录，返回原结论，不再退款。账务回滚则进度也不前移，重试整批。这里讲的是本题关闭所需的消费契约，不另外发明一条“紧急退款通道”；否则普通成交和紧急释放又会失去共同顺序。

## 第 10 层：恢复和清理也不能把关闭事实忘掉

**面试官：** 消费者能安全重试了。时间过去很久，预留也归零，能否把墓碑和去重记录按 TTL 删除，省存储？

**面试者：** 不能仅凭时间或余额为零删除，因为原 Place 仍可能从旧待办、重试日志或历史副本再次出现。恢复快照要覆盖订单、关闭墓碑、业务去重以及它们对应的结果水位，接管者只恢复已提交事实，并通过任期隔离挡住旧主。允许归档的前提是证明旧身份不可能再次获得执行资格，或仍有持久索引能够回答其关闭结论；如果引入凭据代际淘汰，也必须由所有恢复与执行路径一致强制，而非临时加个过期时间。本基线没有这样的压缩协议，所以保留逻辑关闭事实，物理归档不能令它失忆。资金已收尾说明当前义务已清，不等于历史身份可以复用，也不意味着迟到命令可以当作新订单。

## 收束：关闭意味着未来不能执行，而非过去没有成交

- **讲透的机制：** B 提供共同顺序，C 把关闭、数量变化、完整结果与 AppliedSeq 一起提交；授权 AbortIntent 用持久墓碑覆盖未接纳意图；持久去重与有序 D 保证关闭不重复生效。
- **易错边界：** 普通 Cancel 的未知目标不是关闭凭证；撤单不回滚前序成交；B 受理不等于 C 生效；执行终态不等于预留归零；墓碑不能按本地 TTL 失效。
- **反例与预期：** 从 B2 的预留完成、Place 尚未入列状态开始，手工安排普通 Cancel → 未知目标 → 迟到 Place，后者仍可能接纳，所以此处不能退款。独立重置后改为授权 AbortIntent → C 提交关闭 → 迟到 Place，后者必须被拒绝且没有活跃订单；D 消费关闭结果后才退还 15,000，甲恢复 20,000 USDT。两个时序的差异就是未知目标与持久关闭的契约差异，不是实测报告。
