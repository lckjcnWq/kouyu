# 大问题 8：怎样保证订单、成交、预留与账务端到端一致？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文的“一致”不是所有页面同时刷新，而是每一步都保住身份、数量、资格和资金义务，并能恢复到同一结果。基线为零费用现货限价 GTC、每交易对有效单写者、相关账户同库；四个提交点不被假装成一次全局事务。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 不变量 | 无论正常还是故障，都不允许破坏的业务约束。 | 数量可解释、资产不超支、同一成交只入账一次。 |
| 允许暂态与禁止结果 | 有明确恢复路径的进度差可以存在，已成立义务被抹掉不行。 | 全成而账务待处理可以，成交后把付款资金全退不行。 |
| 四个边界 A/B/C/D | 保存并预留、可靠受理、提交裁决、双边记账。 | 每一步分别确认，不把后续失败说成前一步从未发生。 |
| 持久待办 | 与意图和预留共同落库的后续提交任务。 | 跨 A 到 B 的非原子窗口继续负责，不靠请求连接活着。 |
| 稳定业务身份 | 始终认得原意图、订单与预留。 | 超时沿原身份重试，重复日志位置不等于新业务。 |
| 执行资格 | 允许指定载荷参与撮合的资产支持和授权。 | 凭据在 A 后有效，账户不能按本地 TTL 单方退款。 |
| AbortIntent 与持久关闭 | 把原意图不得继续执行的裁决记入共同顺序。 | 先关闭拒迟到单，后关闭保留成交、只撤余量。 |
| 原子 ResultBatch | 一条命令的全部结果与进度共同提交。 | 关闭标记与释放依据不能各写一半。 |
| epoch 与前序校验 | 检查写入任期和预期处理位置仍合法。 | 旧主不能新写，提交未知时不推进下一命令。 |
| 未结转义务与水位 | 已确定但尚未履行的资产交换，以及账户覆盖位置。 | 最新剩余零，不证明历史付款已经完成。 |
| 限价预留与成交支出 | 前者覆盖最坏允许价格，后者按真实成交价格支付。 | 每笔买方预留减少 L×q，其中 p×q 付卖方、(L-p)×q 返还。 |
| 同库整批事务 D | 双方余额、预留、分录、去重与进度共同成立。 | 不能只扣买方就当完成，任一失败整批回滚。 |
| batchId / tradeId | 批次与成交的稳定身份，不是运输消息编号。 | 重发沿用原值；重复业务的新批次不得再次装入旧资金效果。 |
| 分资产守恒与共享余额 | 每种币单独核对，跨流共同修改余额仍须数据库协调。 | 不加总 BTC 与 USDT，不用每市场串行替代账户行锁。 |

## 把整篇文章压缩成一个故事

甲从 20,000 USDT 开始下 B2，限价 60,000 买 0.25 BTC。事务 A 保存原请求、意图、15,000 预留和待办，Place 的 B 回执却丢了。系统报告受理未知，仍用原身份查询或重投；钱已占住、命令未确认，是有恢复责任的暂态，不是可以凭网络超时退款的失败。停掉一个提交器，也不能保证网络里的原 Place 永远不到。

甲要求放弃，授权 AbortIntent 与 Place 进入同一顺序。若关闭先执行，C 共同提交关闭标记和结果，迟到 Place 不得接纳；若 Place 先成交 0.10，关闭只撤余下 0.15。C 还必须检查任期和前序进度，提交未知先查清，不能旧主和新主各造一套结果，也不能只写进度却没留下关闭依据。

B2 已是 CANCELED，D 若仍停在成交前，预留必须还是 15,000，其中 6,000 是已有付款义务，9,000 是可退余量。账户按序在整批事务里处理买卖双方资产、分录、去重和水位，先付 6,000、入账 0.10 BTC，再退 9,000，甲最终可用 14,000。不能照最新剩余零把预留覆盖成零，页面终态也不是资金指令。

D 提交后消息确认丢失，再送原批也只读已有处理记录，不二次移动资产；重复 Place 的新位置只留下无新效果结果。BTC 与 ETH 流同时改甲的 USDT，还须统一行锁或条件更新，按每币种核对义务与守恒。相邻 B1 独立案例则是付 15,015、退 10，而非花光 15,025。对账也要在共同截止点逐笔比对原结果、预留归属与收付对象；总数相等仍可能把甲的价差付错人，故不能只凭各币种平衡就宣布所有义务正确。所有保证以同库整批事务为界，跨分片需新协议，本文只给推演与验收预期。

**流程位置与核心机制：**覆盖意图预留、可靠受理、撮合结果到账务结转的跨域边界。本题解释整条链为什么成立；批次交付细节见母题 09，恢复与任期隔离见母题 10。

沿用总览的现货限价 GTC、零手续费、相关账户同一事务数据库基线。B1 全成与 B2 部分成交后撤单是独立案例，不连续执行。采用系统思维划分权威，逆向检查各提交动作之间的失败窗口。

## 第 1 层：先定义“始终对得上”

**面试官：**怎样保证订单、成交、预留与账务端到端一致？

**面试者：**首先要把一致性定义为不变量，而不是要求所有页面同时刷新。已接纳订单始终满足原始量等于累计成交量、剩余量与撤销量之和；同一意图只产生一次接纳效果，同一成交只结转一次。每个币种分别守恒，可用与预留非负，任何有效执行资格都有资产支持。账务落后时，预留还必须覆盖未结转的成交义务，不能只覆盖最新挂单量。允许订单已全成但账户尚未更新，不允许成交已经成立却把对应资金全部退回。最终应由持久工作流追上确定结果，而不是靠回滚已成交订单来消除暂态。

## 第 2 层：这些不变量落在哪几个提交边界

**面试官：**你允许跨域暂态，那又不能用一个数据库事务包住撮合，怎样保证暂态不会变成永久错账？

**面试者：**我会明确四个边界。A 是账户本地事务，原子写入请求绑定、意图、资产预留和待提交记录；B 是该交易对命令的多数派持久提交，只承诺进入可恢复处理范围；C 是完整 ResultBatch 与 AppliedSeq 的原子提交，此时成交与订单变化成立；D 是账户事务，把整批双边资产变化、分录、去重记录和消费进度一起提交。A 到 B 靠持久待办与原身份重投衔接，C 到 D 靠可重读结果和事务消费衔接。每个域只修改自己的权威状态，后续失败保留前一阶段的义务，不假装四处写入是一次全局原子提交。

## 第 3 层：A 成功而 B 的返回丢失

**面试官：**既然 A 与 B 不原子，账户已经预留，但提交 Place 超时，能否取消意图并把钱退回？

**面试者：**不能按调用超时退款，因为 B 可能已经提交，只是确认没有到达。A 必须连待提交记录一起落库，提交器使用原 intentId、orderId、reservationId 和绑定载荷反复查询或投递，不能重建新意图。预留凭据也只能在 A 提交后有效，账户域不能按本地 TTL 单方让它失效。重复命令即使占据不同日志位置，撮合业务去重仍只能产生一次效果。此时可以报告“意图已保存、受理未知”，不能报告“下单失败且资金已退”。长期悬挂由恢复任务继续推进或申请有序关闭，而不是依赖进程内定时器猜测最终结果。

## 第 4 层：查不到也不能排除迟到 Place

**面试官：**如果提交器查询也没查到 Place，为什么还不能退款？已经停掉重试的原请求可能发生什么？

**面试者：**查不到只说明当前没有可见记录，网络中的 Place 仍可能迟到，因此停止本地重试并没有关闭执行资格。应提交同一意图的 AbortIntent，让它与 Place 进入同一交易对命令顺序。AbortIntent 先执行，就在 C 持久化关闭标记，后来的 Place 即使携带原有效凭据也不能接纳；Place 先执行，关闭命令只能撤销当时实际剩余量，既有成交义务不变。已全成时关闭只是确认已有结果，不能创造可退款量。关闭标记必须参加恢复和去重保留，账户只依据已提交关闭结果并按顺序处理此前成交，不能依据“查询为空”释放。

## 第 5 层：关闭标记遇到崩溃与旧主

**面试官：**你把关闭安全性寄托在 C；如果刚改了内存就崩溃，或者旧主恢复后继续写，关闭还能阻止迟到单吗？

**面试者：**内存修改不算关闭成立。撮合先计算临时变更集，只有完整结果、意图关闭事实及新 AppliedSeq 在 C 原子提交后，才能发布关闭结果或允许后续释放。持久存储同时检查有效 epoch 与前序 AppliedSeq，旧任期写入被拒绝；一次 C 提交结果未知时，必须查询该位置，不能继续处理下一条输入。如果 C 未提交，恢复后重做该命令；如果已经提交，则应用原结果恢复关闭标记，而不是重新解释。这样不会出现进度已越过 AbortIntent、关闭记录却没保存的状态，也不会允许旧主用一份过期内存制造第二条合法执行分支。

## 第 6 层：关闭已成立，预留为什么还不能归零

**面试官：**现在 C 已确定 B2 撤单成功、leavesQty 为零，账户仍落后，直接按照最新剩余量清零预留有什么问题？

**面试者：**最新剩余量只描述未来还能成交多少，不描述过去已经成交但尚未结转多少。B2 初始预留 15,000 USDT，先成交 0.10 BTC、支出 6,000，再撤剩余 0.15 BTC。若两批结果都没记账，订单虽然已关闭，账本预留仍是 15,000，其中 6,000 必须支付成交，只有 9,000 可以退回。此时全退会让同一笔钱既能被再次下单，又承担已成立成交。账户应从自己的连续水位依次处理成交批次和关闭批次。只有撮合与账务处于相同结果水位时，才能用限价乘剩余量核对活跃买单预留；不能跨水位直接覆盖余额。这也适用于价差尚未返还的全成订单。

## 第 7 层：按序之外，还要整批原子记账

**面试官：**即使先处理成交再退款，如果买方扣款成功而卖方入账失败，按序消费也救不了，具体怎么提交？

**面试者：**D 必须覆盖本批全部成交的买卖双方，而不是每条腿单独提交。成交数量为 q、价格为 p、买单限价为 L 时，买方预留减少 L×q，卖方获得 p×q 报价币，买方可用返还价差 (L-p)×q；卖方预留减少 q 基础币，买方获得 q 基础币。关闭批次再释放明确取消数量对应的预留。全部余额、预留明细、双边分录、本批去重记录与该交易对消费进度在同一数据库事务提交，并逐项校验预留归属和足额条件，任何一步失败都整体回滚。B1 因而支出 15,015、返还 10，而不是把初始预留 15,025 全当成交款；不能仅检查买方总扣款就宣布双边正确。

## 第 8 层：D 已提交但确认丢了

**面试官：**整批事务提交了，消费者却在确认消息前崩溃；重试会不会再支付一次？依赖 MQ 的去重够吗？

**面试者：**不能依赖 MQ 的投递身份，因为重新发布可能换消息标识。账务使用稳定 batchId，即 symbol 加 commandSeq，并核对批次内容；成交身份是 symbol、首次产生该成交的 commandSeq 与 matchIndex。D 中的批次去重记录与余额同事务，提交后重投只能命中既有记录，不再移动资产；提交前崩溃则整笔事务没有效果，可以原批重做。账户侧 lastAppliedSeq[symbol] 也在同一事务推进，重复与连续性不能分开保存。重复业务命令的新日志位置只产生引用旧结论的无新效果结果，不能重新装入旧成交。所谓一次业务效果，来自持久身份和事务边界，不是运输层宣称只送一次。

## 第 9 层：多个交易对竞争同一份资产

**面试官：**你的去重和进度都按 symbol，BTC/USDT 与 ETH/USDT 同时改同一账户 USDT，甚至以后拆账务分片，保证还成立吗？

**面试者：**按 symbol 只解决各结果流的顺序，不替代共享余额并发控制。当前所有相关账户在同一事务数据库，A 与 D 都必须锁定或条件更新同一账户资产行，预留明细也参与校验；两个交易对不能分别读旧余额再覆盖写回。D 对多账户采用稳定锁顺序，死锁回滚后仍用原批次重试，保证不同流各自推进且金额变化不丢失。如果把成交双方拆到不能共同提交的账务分片，D 的原子前提就消失了，需要另行设计跨分片提交、待清算状态和故障收敛协议。这是未支持的条件变化，不能只加一个消息队列便声称原保证不变。

## 第 10 层：怎样检查协议真的闭环

**面试官：**既然同库事务也是明确前提，怎样验证当前基线，而不是只拿最终余额碰巧正确来证明一致性？

**面试者：**我会围绕 A、B、C、D 的交界手工推演故障历史，同时核对身份、数量、资金与连续水位。比如 A 成功后反复丢失 B 的确认，应只有一个意图和一份预留；先提交关闭再放行迟到 Place，应没有新成交。B2 的成交与关闭都已在 C 提交而 D 暂停时，必须保留 15,000 预留；恢复后先支付 6,000，再释放 9,000，最终甲可用 14,000 并得到 0.10 BTC。随后重复投递两批，余额、分录数量和水位应不变。还要检查每币种守恒与未结转义务，防止单账户看似正确、对手方少入账；缺口未恢复时应保持处理中，不能伪造完成。以上是验证预期，不是实测报告。

## 本题收束

- **讲透的机制：**用四个局部提交边界连接一条可恢复义务链；执行资格先有预留支持，释放必须晚于权威关闭，并保留未结转成交所需资金。
- **易错边界：**可靠受理不等于接纳，执行终态不等于资金终态；查询为空不能证明未执行，同库整批事务不能无条件推广到跨分片。
- **反例与预期：**让 B2 的撤单回报先于成交记账到达。错误方案看到剩余零便全退 15,000；正确方案不以回报驱动退款，仍按结果连续处理，最终只退 9,000，重复回报和重投也不增加退款。
