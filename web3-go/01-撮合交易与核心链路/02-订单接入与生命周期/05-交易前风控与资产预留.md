# 大问题 5：风控与预留怎样防止跨交易对超买及重复占资？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文关心“一份余额不能同时支持两份花费，以及占住的钱何时真能退”。条件是链下限价 GTC 现货、零费用、相关账户同一事务数据库；交易对各自串行，并不能自动解决跨交易对共享余额竞争。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 资产准入 | 正式确认这笔业务有足够资产支持。 | 基础参数通过后，还须在账户数据库裁决真实资金资格。 |
| 可用、预留与总资产 | 可用能另花，预留给原业务占着，两者不是凭空增减总资产。 | 买单按限价乘数量预留，卖单按卖出数量预留。 |
| 共享余额 | 同一账户的 USDT 可被不同交易对同时申请。 | BTC 单写者挡不住 ETH 服务也来花这笔钱。 |
| 行锁与条件更新 | 让检查余额和修改余额在数据库里不可被竞争穿透。 | 可用足够才扣减并增预留，必须检查实际更新结果。 |
| 事务 A | 请求绑定、意图、扣可用、预留和待办一起提交。 | 任一失败整体回滚，不能有占款无意图或有资格无占款。 |
| 请求唯一性 | 同一业务只允许一个持久请求绑定。 | 余额不为负仍可能重复冻结，因此要与 A 共同保证。 |
| 规范化载荷 | 原请求所表达的价格、数量和执行规则的统一表达。 | 同键改条件是冲突，不是编辑原订单。 |
| 预留凭据 | 账户确认 A 已提交后给撮合的可信资格证据。 | 绑定账户、意图、订单、预留、市场和规则，不是一个通用布尔值。 |
| 签名与业务去重 | 签名证明来源和内容，去重防同一资格多次执行。 | 凭据有效也要查关闭标记，不能重复接纳。 |
| 提交未知与 context | 事务或日志回复丢失；context 是本次等待的取消信号。 | 等待结束不等于回滚，不删除持久待办或退款。 |
| AbortIntent | 把关闭资格送进与 Place 相同的权威顺序。 | 关闭先到阻止接纳，后到只撤实际余量。 |
| 相同结果水位 | 撮合和账务都覆盖到了同一条正式结果。 | 只有此时才可按限价乘剩余量核对活跃单预留。 |
| 未结转义务 | 成交已成立，但钱和币尚未在账户完成交割。 | 订单剩余零时，原预留仍可能覆盖全部已确定付款。 |
| 事务 D 与固定锁序 | 整批双方记账，并用统一次序锁多条余额行。 | 防重复和死锁重试要沿原业务；对账不能代替事前防超支。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，同时发出需要 15,025 的 BTC 买单 B1 和需要 6,000 的 ETH 买单。两边都先读到余额充足，也不能都放行，因为需求合计 21,025。真正的裁决发生在账户数据库：若 B1 先在事务 A 中成功，可用只剩 4,975，ETH 失败；若 ETH 先成功，余下 14,000 不够 B1。两个市场各有一个撮合 goroutine，并不能替代这次共享余额竞争。

甲重复提交 B1，还要由请求唯一约束与资金变动共同提交，避免余额较多时重复占款。A 保存意图、预留和待办后才签发绑定原账户与载荷的资格凭据；输掉唯一键竞争的事务必须整体撤回。签名只是证明这份资格真实，撮合仍要持久去重和检查关闭，不能拿同一凭据支持两张订单。

投递回复丢失时，系统沿原意图查询或重投，不能因 context 结束直接退款。甲要放弃，得授权 AbortIntent 同序裁决，等关闭结果正式成立，再由账户顺序履约。单次查不到或普通 Cancel 未知目标，都不能挡住仍在网络里的 Place；凭据也不能一边有效，一边被账户按本地 TTL 偷偷解冻。

B1 全成时，撮合剩余量已经为零，账户却可能还占 15,025，其中覆盖既有成交。D 处理两笔成交后才是支出 15,015、返还 10、得到 0.25 BTC，可用 4,985，不能按最新余量直接全退。热点优化应缩短持锁时间、固定多行锁序、在预留前背压；先放行后对账不能把已经成立的无钱成交变正确。核对时还要把余额、预留明细和已应用位置放在一致切面，不能拼接不同时刻的读数，误判预留少了或凭空补款。以上是可核算的预期，不是跨市场并发实测。

**流程位置与核心机制：** 本题覆盖接入校验之后、可靠受理之前的资产准入，以及关闭之后的预留释放。重点是共享余额竞争、唯一请求与扣资的共同事务、执行资格凭据和不确定状态；完整撤单裁决见母题 06，端到端一致性见母题 08。

沿用总览的现货限价 GTC、零费用和相关账户同一事务库。A 是意图与预留事务，B 是命令可靠提交，C 是完整结果提交，D 是账务事务。本题不增加缓存余额权威、跨库扣资或超时自动解冻机制。

## 第 1 层：先把“有钱下单”变成可证明的约束

**面试官：** 风控与预留怎样防止跨交易对超买及重复占资？

**面试者：** 在这个模型中，接入校验负责鉴权、精度和业务上限，账户域负责决定是否真的有资产支持执行。买单预留限价乘数量，卖单预留卖出数量；预留成功后，资产从可用转入该意图专属预留，不是扣掉账户总资产。B1 买入 0.25 BTC、限价 60,100，需要 15,025 USDT，甲的可用从 20,000 变成 4,975。同一账户在其他交易对买币也要竞争这笔 USDT，不能各自读取一份余额再决定放行。A 必须原子绑定请求、创建意图、移动余额并保存待提交记录；只有这套事实提交，才能提供执行资格。这样既限制总占资，也给后续重试找到原业务的依据。

## 第 2 层：两个交易对同时读到余额充足怎么办

**面试官：** 你说共享账户余额。BTC 和 ETH 两个服务同时读到 20,000，都认为余额足够，具体由谁挡住第二笔？

**面试者：** 挡住它们的是账户数据库，不是交易对 actor。可以对账户与资产对应的余额行加锁，再检查和更新；也可以执行带条件的更新：只有可用不少于所需金额时，才同时减少可用、增加预留，并检查受影响行数。条件判断和修改是一个数据库写操作，竞争事务按数据库的并发语义等待或重试，不把先前读取值当作授权。余额行、意图、预留明细和待提交记录都属于 A，任一环节失败就整体回滚，不能留下扣资却无凭据的半成品。B1 与另一笔需要 6,000 USDT 的 ETH 买单同时竞争时，在没有其他资产变化的条件下最多一笔成功，因为需求合计超过 20,000。Go 进程内的互斥锁无法覆盖另一个服务实例。

## 第 3 层：余额原子更新为什么仍挡不住重复占资

**面试官：** 条件更新只防止余额变负。同一个 B1 请求并发重试两次，如果账户钱更多，两次都能扣成功，怎么办？

**面试者：** 所以余额原子性还要与请求唯一性组成同一个事务。请求键是账户、命令类型和 clientOrderId，并绑定规范化载荷。A 先通过唯一约束争夺这把键，赢家才继续条件扣资、创建一对一绑定的意图、订单、预留和待办，最后一起提交。竞争者等待唯一键事务结束；若赢家提交，竞争者回滚本次尝试，再用新事务读取原记录：同载荷返回原身份和进度，异载荷明确冲突。若赢家回滚，竞争者才能重新尝试创建。不能在唯一键插入失败后继续保留已经发生的扣资，也不能在已被数据库判为失败的事务里强行读取。预查询只可优化路径，真正挡住并发的是唯一约束与余额变动的共同提交。

## 第 4 层：预留凭据不能只是“余额检查通过”

**面试官：** 你已经创建了预留。撮合不直接读账户库，怎样确认这份资格没被换订单使用，或者被重复使用？

**面试者：** 账户域在确认 A 已提交后签发资格凭据，绑定 accountId、intentId、orderId、reservationId、交易对、方向、规范化价格数量、资产金额和规则依据。撮合验证可信签发来源以及全部绑定关系，不能只验证一个“预留有效”的布尔值。预留与意图、订单一对一关联，凭据不能拿去支持另一张订单；相同凭据重复投递则仍由撮合的持久业务去重挡住第二次接纳。签名证明的是已提交授权及其不可篡改性，不替代订单去重或关闭检查。尤其不能一边承诺资格有效，一边允许账户按 TTL 自行解冻：迟到 Place 仍可能携带合法凭据执行。资格的失效要经共同顺序里的关闭协议，而不是本地时钟。

## 第 5 层：提交失败不一定代表事务没成功

**面试官：** 凭据只能在 A 提交后签发。如果数据库提交时断线，或者向 B 投递时超时，账户服务能回滚预留吗？

**面试者：** 必须区分明确失败与结果不确定。若数据库明确回滚 A，当然没有有效预留；但 COMMIT 发出后连接断开，可能已经成功，只是确认丢失。此时用原请求键查询权威事务结果，必要时按同一唯一键协议重试，不另建身份；在确认 A 成功前也不签发凭据。若 A 已成功而 B 的确认丢失，命令可能已多数派持久提交，甚至已到 C，网络超时不能撤销这些事实。持久待提交记录负责恢复，查询或重投原 Place，重复入列由业务身份去重。请求 context 结束只结束本次等待，不删除待办、不退款。短暂“处理中”是允许状态；拿不确定结果当明确失败，再释放资产或用新键补单，才是协议错误。

## 第 6 层：长期悬挂怎样结束，又不提前退款

**面试官：** 一直查询和重试会占着资金。用户决定放弃，但原 Place 可能仍在路上，怎样安全结束？

**面试者：** 放弃要提交有权限的 AbortIntent，让它与 Place 进入同一交易对命令序列，而不是账户直接清空预留。如果关闭先被处理，撮合在 C 持久记录意图关闭标记，迟到 Place 即使凭据正确也不能接纳；如果 Place 已先接纳，就只关闭裁决时真实剩余量，已经确定的成交义务保留。普通 Cancel 对未知订单的“查无目标”不提供这个保证，因此不能替代关闭协议。AbortIntent 在 B 已受理也还不够，必须等关闭结果越过 C，且 D 按序覆盖此前成交和本次关闭，才释放可退部分。关闭结果的提交确认若丢失，继续查原结果；不能因等得久就猜测已关闭。这里接受暂时占资，拒绝资金已退但执行资格仍活着。

## 第 7 层：为什么不能按最新剩余量直接重算预留

**面试官：** 关闭后还要等 D。既然撮合知道剩余量，账户直接把预留改成“限价乘剩余量”，不是更快吗？

**面试者：** 这个公式只在撮合事实与账务处于相同结果水位时成立，不能跨水位套用。B1 在 C 已经全成，剩余量为零，但 D 尚未执行时预留仍应为 15,025，其中覆盖已确定的成交支出。若立即重算成零并全退，甲就能花掉欠卖方的钱。D 按交易对结果顺序消费完整批次，在同一事务里处理相关买卖账户、预留消耗、分录、批次去重和消费进度。本例实际支出 15,015，价差返还 10，最终可用 4,985、获得 0.25 BTC、B1 预留归零。挂单的未成交部分仍需覆盖未来执行；已成交未结转部分则覆盖现有义务。释放必须解释覆盖的是哪一种义务，不能只看一个订单状态或最新数量。

## 第 8 层：热点账户是否值得绕过数据库

**面试官：** 你把共享余额竞争和释放都压到账户事务，热点账户会串行。为了吞吐能否先在各交易对放行，之后再对账？

**面试者：** 不能把不可超支的约束降成事后检查。共享有限余额的竞争本来就需要一个裁决点，先放行再发现超支时，C 里的成交已不能任意撤回。在当前基线下应缩短 A 的持锁时间，把鉴权和解析放到事务外，但事务内仍核对规范化载荷与资金条件；多余额行按统一顺序锁定，死锁或序列化失败用原键重试。接入背压可以拒绝尚未进入 A 的新请求，不能抛弃已提交的持久待办。若未来要按交易对预分配资产额度，必须先建立额度之和不超过账户资产的新协议，那是改变资金模型后的取舍，不是本题已有能力。当前优化目标是在保留 A 原子性和 C 到 D 义务覆盖的前提下减少等待，对账只负责发现异常，不能代替事前约束。

## 收束：资金占用与执行资格必须一起推演

- **讲透的机制：** 账户数据库裁决跨交易对余额竞争；唯一请求、扣资、预留和待办在 A 共同提交；凭据把资产支持绑定到唯一意图；关闭与有序 D 决定何时可释放。
- **易错边界：** 条件扣资不自动等于请求幂等；签名不等于业务去重；TTL、客户端取消、B 超时和查询缺失都不是退款授权；终态前后的在途成交不能凭最新剩余量抹掉。
- **反例与预期：** 手工安排 B1 与一笔需要 6,000 USDT 的 ETH 买单同时通过余额预查询，再同时进入 A。若 B1 赢得余额竞争，应只有一份 15,025 预留，ETH 失败，甲可用 4,975；若 ETH 先赢，B1 应因剩余 14,000 不足而失败。交换事务顺序可改变赢家，但绝不允许同时生成两份有效资格。这是检查事务边界的预期，不是已执行的工程测试。
