# 大问题 1：一笔订单从接入到终态的完整流程与架构是什么？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文先画清“一笔业务由谁接、谁判、谁付钱”。沿用链下 BTC/USDT 限价 GTC 现货、零手续费、相关账户同库事务；全成案例与部分成交撤单案例各自从原始余额开始，不连续累计。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 接入与接纳 | 接入是收请求，接纳是撮合正式认可订单有执行资格。 | HTTP 收到了，不等于订单已经进入可成交状态。 |
| 下单意图 | 保存“这个账户要按这些条件下这一单”的业务记录。 | 与订单、预留绑定，原请求重试仍找回这一份。 |
| 资产预留 | 从可用中划出专款，支持指定订单。 | B1 先占 15,025 USDT，不等于已经全部支付。 |
| 持久待提交记录 | 重启后仍找得到的投递任务。 | 和意图、预留同事务创建，不能只放进内存队列。 |
| 可靠受理 | 命令越过多数派持久提交，故障后仍能恢复处理。 | commandSeq 表示受理位置，不保证全成或到账。 |
| 状态所有权 | 明确哪个业务域能决定哪种事实。 | 撮合管执行，账户管钱，接入管提交，查询只是展示副本。 |
| ResultBatch 与 AppliedSeq | 一整包裁决结果，以及已正式处理到的位置。 | 双方变化和进度原子提交后，执行结果才可发布。 |
| phase 与有界等待 | phase 说明走到哪一步；等待有最长时限。 | 超时结束连接等待，不撤销已提交业务。 |
| AbortIntent | 经授权关闭原意图，阻止它将来迟到执行。 | 先关闭就拒迟到 Place；后关闭就保留成交、只撤余量。 |
| Cancel 的未知目标 | 这次撤单裁决时没找到已有订单。 | 不等于意图永久关闭，不能单独作为退款证明。 |
| 终态与数量守恒 | 终态只结束未来执行，历史数量仍要交代。 | 0.25＝成交 0.10＋取消 0.15＋剩余 0，不是整单从未发生。 |
| 结转 PENDING / APPLIED | 某批结果尚待入账 / 已完成入账。 | 订单已撤时账务仍可能 PENDING，不能全额解冻。 |
| 订单版本与回报游标 | 一个防止旧状态覆盖新状态，一个定位私有流的接续位置。 | 还要单独报告账户水位，不能拿已推送推断已付款。 |
| 同库双边事务 | 买卖双方资产与分录在一个数据库事务中共同成立。 | 改成跨分片就需要新协议，不能沿用当前原子性承诺。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，提交 B1 买入 0.25 BTC、限价 60,100。账户事务一起保存意图、预留 15,025 和待提交任务，可用变为 4,975。就算进程在发命令前崩溃，恢复者也能从持久待办接着送；不是后台 goroutine 消失，订单就没人负责。甲的 HTTP 等待结束，也只结束等待，原请求身份和任务仍在。

命令多数派持久提交，只能告诉甲“已可靠受理”。撮合这个唯一执行裁决者算出 0.10 按 60,000、0.15 按 60,100 的两笔成交，完整结果和进度提交后才有 FILLED。账户再按序在同库事务里完成双边结转，支付 15,015、返还 10，甲得到 0.25 BTC、可用 4,985。查询服务哪怕仍显示处理中，也只能补投影，不能自己生成另一笔成交。

另从初始条件开始，B2 限价 60,000，只成交 0.10，随后撤掉 0.15。执行状态虽然已是 CANCELED，若账务落后，15,000 仍留在预留里：6,000 要付给卖方，9,000 才可退。有序完成后才是可用 14,000 与 0.10 BTC。若 Place 还可能在路上，普通撤单的查无目标不保证安全；授权关闭意图必须在共同顺序中挡住迟到执行，再谈释放。

用户先收到新版撤单回报、又查到旧版部分成交时，客户端按订单版本防回退，断线按独立游标补齐，资金是否完成另查账户水位。验收也不数 HTTP 200，而是逐个提交边界推演中断和重复，检查身份、数量、义务与各币种守恒。每段停留都须查到负责恢复的持久记录和下一步动作，不能让入口说找撮合、撮合说找账户，最后无人接手原义务。本文给的是架构与检查方法，没有运行真实故障测试；双边原子性仍以相关账户同库为前提。

[返回专题总览](README.md)

**流程位置与核心机制：**串起请求接入、资产准入、可靠受理、撮合裁决、资金收尾和用户可见性。本题回答各模块怎样共同完成一笔业务；幂等实现、撤单竞争和结果消费分别在后续母题深入。

**必要前提：**沿用总览的链下现货、限价 GTC、零手续费模型；买卖方位于同一事务数据库，命令与结果有明确的复制提交边界。主案例是 B1，撤单只使用从相同初始状态重新开始的 B2。

## 第 1 层：从用户点击下单开始讲完一笔订单

**面试官：**一笔订单从接入到终态的完整流程与架构是什么？请不要只列服务名称。

**面试者：**在这个模型中，接入先鉴权、检查精度和请求身份，然后账户域在一个事务里保存下单意图、预留和待提交记录。提交器把原意图送入交易对的可靠命令日志，日志提交只代表可恢复受理。撮合单写者按已提交顺序校验资格、接纳或拒绝，计算成交和订单变化，再原子提交完整结果批次与处理进度。结果提交后才能报告权威执行结果。账户消费者随后按序结转双边资产、返还价差或确定可退的剩余预留，并把去重和消费进度一起提交。

对 B1，预留是 15,025 USDT，两笔成交实际支出 15,015，最后返还 10，甲得到 0.25 BTC。订单查询、私有回报和公共行情从结果构建投影，可能晚于执行事实；订单全成、账务完成和页面可见不是同一个时刻。

## 第 2 层：完整链路里究竟谁拥有订单状态

**面试官：**你说结果会进入订单查询和账户系统。如果它们都存有订单状态，究竟谁有权把 B1 改成全成？

**面试者：**只有撮合域有权决定执行状态。接入服务可以保存“请求正在提交”，账户系统可以保存“该批结果已结转”，查询数据库可以保存 FILLED 的投影，但这三者都不能独立生成一次成交或撤单终态。权威是已提交结果中的订单数量和版本，而不是某张名字叫 orders 的表。

具体实现中，每个交易对只有一个有效写入者，内存订单簿是已提交执行状态的工作副本。一次成交的临时计算要形成包含双方变化的结果批次，连同 AppliedSeq 一起提交；提交前不能先推送 FILLED，也不能让账户据临时结果扣款。这样即使查询库还显示 PARTIALLY_FILLED，也只是可见性落后，不是系统里存在两个同等有效的订单结论。

## 第 3 层：客户端收到成功到底成功到哪一步

**面试官：**既然权威结果要等撮合提交，API 应该一直等到记账结束才返回成功吗？

**面试者：**不必，但必须把返回语义拆开。账户事务提交后，可以返回“意图已保存”，带 intentId 和查询入口；如果接口承诺“可靠受理”，就必须等命令多数派持久提交，给出 commandSeq。两者都不能写成“订单已成交”。等待到结果提交，可以返回已接纳、拒绝或具体成交状态，但结转仍可能是 PENDING。

如果业务需要同步等待，可以设等待上限；超时只结束这次网络等待，不改变已提交业务。HTTP 状态码也不能代替业务阶段，客户端需要读明确的 phase、身份和可查询位置。B1 已有 FILLED 结果而账户落后时，返回“FILLED，账务处理中”是诚实的；为了做成一个绿色成功按钮而把阶段揉在一起，会让用户误判是否该补单或能否使用资产。

## 第 4 层：意图保存后到命令受理前如何避免丢单

**面试官：**你允许先返回意图已保存。账户事务已提交，进程却在发送命令前崩溃，这笔订单谁继续处理？

**面试者：**待提交记录必须与意图和预留同事务写入，不能等扣完钱后再放一个内存任务。进程恢复或其他提交工作者会扫描持久待办，按原 intentId、orderId、reservationId 重投。多个工作者可能重复发送，所以账户幂等还不够，撮合也必须按业务身份去重。

账户数据库和命令日志之间没有一个被我们假定存在的大事务，因此允许“资产已预留、命令尚未受理”的在途状态。只要持久工作流仍负责继续提交或发起有序关闭，这个状态就有收敛路径。若提交调用超时，不能直接把待办删掉或退款，因为命令也可能已经提交但回执丢失；必须查原身份或继续幂等重投，而不是另建一笔订单碰碰运气。

## 第 5 层：用户不想等待时怎样结束这个在途状态

**面试官：**用户看到提交超时后要求放弃。你刚说不能直接退款，那怎样关闭一笔可能还没到撮合的订单？

**面试者：**要撤销的是执行资格，不是停止某个 goroutine。这里由有权限的内部流程提交 AbortIntent，绑定原账户、交易对、意图和预留，与 Place 在同一命令序列裁决。如果关闭先发生，就持久记录关闭标记，迟到 Place 只能被拒绝；如果 Place 已经发生，就撤掉裁决时的实际剩余量；如果已全成，只能确认终态，不能撤回已有成交。

关闭结果与处理进度共同提交后，账户消费者按序处理相关成交和关闭动作，再释放确定可退部分。普通 Cancel 查到“目标尚不存在”不具备这个关闭证明，因为迟到 Place 仍可能到达。这个区别把网络未知转换成可裁决的业务动作，否则客户端虽然收到退款，原来的有效命令却可能继续成交。

## 第 6 层：部分成交后撤单怎样界定业务完成

**面试官：**按你的关闭流程，B2 先成交 0.10 BTC，再撤剩余 0.15 BTC。收到 CANCELED 就算整个业务结束了吗？

**面试者：**只能说明执行生命周期结束，未来不能继续匹配。B2 的终态数量应是原始 0.25 等于累计成交 0.10 加撤销 0.15，剩余零。历史成交不能因为状态标签变成 CANCELED 就消失。

资金还要看账户进度。如果成交和撤单结果都尚未结转，甲的 15,000 USDT 仍在预留中：6,000 用于成交，9,000 可退。先按成交结果消费 6,000 并入账 0.10 BTC，再按关闭结果返还 9,000，才能达到可用 14,000、预留零。若只读终态把全部 15,000 解冻，就会让已经买到的 BTC 没有对应支出。真正的资金收尾条件是账户水位覆盖终态及此前的相关结果，而不只是 leavesQty 为零。

## 第 7 层：执行完成但查询和回报不一致怎么办

**面试官：**B2 已经撤销且记账完成，用户却先收到撤单回报，再查到部分成交。你怎样让用户知道哪个状态可信？

**面试者：**查询和回报必须带来源位置与订单版本，而不能只有状态字符串。客户端看到同一订单较旧的 orderVersion 时，不应覆盖已知新版本；私有流还要有独立游标，用于发现断线缺口。账户进度与执行结果位置分别报告，不能拿“回报已推送”推断余额已到账。

若查询副本尚未追到客户端已知版本，服务应明确返回滞后或在有界时间内等待到要求的最小水位，而不是伪装成最新。重连可以补发保留区间内的事件，或在明确快照游标处重建，再接后续增量。订单不存在也要区分“尚未投影”和“权威拒绝”，特别是预留已创建而 Place 仍在途时，不能用查询空结果充当退款指令。

## 第 8 层：如何验证这套跨模块架构确实闭合

**面试官：**你已经列了多个阶段、版本和后台任务。怎样证明它们不是把错误藏得更深？

**面试者：**我会围绕不变量和提交边界验证，而不是统计服务有没有返回 200。对每个已接纳订单，检查原量等于成交量、剩余量和撤销量之和；同一业务身份不能重复接纳；终态不能重新进入撮合；按相同水位核对预留和未履行义务，各资产分别守恒。

再在账户提交前后、命令提交前后、结果提交前后和账务提交前后分别制造中断、回执丢失和重复投递，确认恢复后仍得到相同结果。比如 B1 结果已提交而消费者崩溃，恢复后仍应只记两笔成交、支出 15,015、返还 10，不补第三笔订单。这个方法也揭示架构边界：本模型的账务原子性依赖同一事务数据库，若改成跨分片，必须重新设计履约协议，不能继续沿用原来的保证。

## 本题收束

- **讲透的机制：**意图保存、可靠受理、执行结果、账务完成与展示可见各有边界，跨边界用稳定身份和持久工作流收敛。
- **最容易答错：**把订单 API 返回、订单终态或查询结果中的任何一个，当作整笔业务所有阶段都已完成。
- **检验反例：**B2 已部分成交，撤单结果已提交，账户仍停在成交前。此时预期订单 CANCELED、账务 PENDING、预留仍覆盖 15,000；完整有序结转后才是预留零、甲可用 14,000 USDT 与 0.10 BTC。若立刻全额退款，架构就没有闭合。
