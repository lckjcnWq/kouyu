# 大问题 9：怎样可靠交付结果，避免重复记账和提前退款？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文解释“结果能反复运输，钱却只能正确动一次”。条件仍是零费用现货限价 GTC、同库双边事务；以已提交完整结果为事实源，消息队列、客户端终态和分发器发送标记都不能代替它。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 结果事实源 | 可以重新读取、核验正式裁决的持久记录。 | C 的 ResultBatch 与 AppliedSeq 共同提交后，才允许交付资金处理。 |
| 分发器与运输层 | 把已有结果送给消费者，不重新决定业务。 | 提交后发送前崩溃可补发，内存试算不得提前发送成事实。 |
| batchId | 一个正式结果包的固定编号。 | symbol＋commandSeq，重发不换号。 |
| tradeId / matchIndex | 成交编号 / 原命令内部的成交序号。 | 原成交身份固定，分录再绑定账户、资产和分录类型。 |
| actionIndex | 非成交资金动作在批次内的位置标识。 | 关闭退款没有 tradeId，也必须有稳定效果身份。 |
| 同身份异内容 | 编号一样，内容却不一样。 | 这是冲突需隔离核对，不是可以随手忽略的正常重复。 |
| 重复业务的空效果结果 | 新命令位置引用原裁决，却不重列旧资金动作。 | 仅按新 batchId 去重，挡不住被错误复制的旧成交。 |
| 拆包与完整性 | 大批次可以分片运输，但不能分成独立账务事实。 | 片数、索引和摘要核验齐全才进入 D，缺片向源补读。 |
| 无成交与无效果 | 没成交仍可能有挂单、拒绝或关闭；无效果也要证明处理到此。 | 不能把没有收到消息猜成合法空结果。 |
| 连续 lastAppliedSeq | 账户已无缺口处理到的本市场逻辑位置。 | 后继先到就补前序，关闭不能越过历史成交。 |
| 事务 D | 整批双方资产、预留、分录、去重和进度一起提交。 | 回滚则效果与进度都不留下，提交后重投都不再动钱。 |
| 预留归属与固定锁序 | 校验具体是哪份占款，并用统一顺序锁多账户资产。 | 每流串行不自动解决跨交易对共享余额竞争。 |
| MQ offset 与业务水位 | 运输确认位置和正式记账覆盖位置是两件事。 | 补读以账户连续水位为准，不凭“已发送”宣布已入账。 |
| 可靠归档与保留 | 清理在线结果前，证明所需历史仍可读、可恢复。 | 不能消息确认过就删事实源，也不能提前让去重失效。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，B2 预留 15,000 买 0.25 BTC，先成交 0.10，后撤 0.15。撮合把成交和关闭分别作为完整正式结果提交，分发器却在发成交前退出。恢复者从持久结果接着送，而不是从内存猜；每批沿用原 batchId，每笔成交沿用原 tradeId，退款也有批内动作身份，运输消息换编号不影响这些事实。

关闭批次先到了，账户不能看见 CANCELED 就退 15,000，也不能先退 9,000 后随便跳过成交。它守住连续水位，向源补回缺失前序；若一条大结果只到了部分分片，还须核验齐全，不能把最后一片当作全部完成。没有成交的前序位置也要有正式空结果，不能默认为消息丢了就算无事。

补齐后，D 把整批双方余额、预留、分录、去重和消费进度在同库事务中共同提交。先支付 6,000、给甲入账 0.10 BTC，再依关闭释放 9,000，最终可用 14,000、预留零。若 D 成功但 MQ 确认丢失，重投只命中原处理记录；若事务回滚，水位也不前进，原批完整重做。同身份内容不符则停查，不能当重复吞掉。

随后一个重复 Place 占了新位置，只能产生引用原裁决的无新效果批次，否则新 batchId 会掩盖旧成交被付两次。其他市场同时修改甲的 USDT 仍要遵守数据库锁序和预留归属，不能靠各流分别有序就宣称安全。源记录清理还须考虑落后消费者与可验证归档，发送确认不是恢复完成证明。积压扩大应限制新负担、保留恢复容量，不能丢掉已成立的成交来追平水位。本文描述检查预期，没有运行真实运输故障或账务测试。

**流程位置与核心机制：**聚焦撮合结果提交到资金结转之间的链路：已提交事实、稳定批次身份、完整性、连续水位和整批事务去重。母题 08 解释总体不变量，本题把 C 到 D 的交付契约落到失败窗口。

沿用现货限价 GTC、零手续费及相关账户同一事务数据库。A 原子保存意图、预留和待提交记录，B 多数派持久提交每交易对命令，C 在有效任期内原子提交 ResultBatch 与 AppliedSeq，D 负责整批双边账务。本题用独立变体 B2 的成交后撤单贯穿追问。

## 第 1 层：交付的源到底是什么

**面试官：**怎样可靠交付结果，避免重复记账和提前退款？

**面试者：**先把交付源固定为 C 已提交的 ResultBatch，而不是撮合内存、发送成功标记或客户端回报。撮合先形成临时变更集，完整结果和 AppliedSeq 原子提交后，成交义务才成立；存储必须拒绝旧 epoch 和错误前序位置的写入。分发器按持久结果位置读取，失败后从已知位置继续发布。账户只消费能够对应已提交源记录的完整批次，不接受一个游离的“订单已撤销”通知直接退款。这样即使进程在提交后、发送前崩溃，源记录仍可重新交付；提交前计算出的成交则不能提前记账。可靠性由可恢复事实和重试建立，不由一次网络调用建立。

## 第 2 层：重读结果为何不会创造第二次成交

**面试官：**你说可以反复重读和发布，如果消息每次都有新编号，账户怎样认出同一结果？

**面试者：**业务身份必须在源提交时固定：batchId 为 symbol 加 commandSeq，tradeId 为 symbol、产生该成交的 commandSeq 与 matchIndex，订单变化带 orderId 和 version。重新发送不能按时间或新的随机数重建这些身份。账户去重看 batchId，分录再绑定 tradeId、账户、资产及分录类型；同一身份却出现不同内容应隔离告警，不能当正常重复吞掉。关闭退款等非成交分录则绑定 batchId、actionIndex、账户和资产，不能因为没有 tradeId 就缺少去重身份。注意重复 Place 可能占用新的命令位置，此时新批次只说明重复命令的处理结论，不再次携带有资金效果的旧成交。否则仅按新 batchId 去重仍会重复支付。运输消息编号可以变化，但已经成立的业务事实与资金效果身份必须不变。

## 第 3 层：稳定身份不等于批次完整

**面试官：**身份固定了，但一个命令撮合多笔，大结果被拆包，只收到部分成交或只有终态，该怎么处理？

**面试者：**一个 ResultBatch 应包含本命令全部成交、相关买卖订单变化、预留动作与意图关闭事实，并能核对事件数量、分片编号和内容摘要。拆包只是运输实现，消费者必须收齐并核验后才交给 D；缺一片就补读源，不能先结转已到的半批，也不能先执行关闭退款。组装缓存可以丢失，重启从源重建，不把收到最后一片误认为此前片段已经齐全。没有成交的命令同样必须有明确结果，例如接纳挂单、拒绝、关闭或重复无效果；真正没有业务变化也要有可验证的空批次。这样账户知道某个 commandSeq 已经完成，而不是把消息缺失猜成空结果。本基线限定一个命令一个完整结果批次，若批次大到无法承受，应限制业务规模或另行改变协议，不能暗中拆成独立提交。

## 第 4 层：完整批次仍可能乱序

**面试官：**即使两个批次都完整，B2 的关闭批次先到，成交批次后到，先退钱再补记成交为什么不行？

**面试者：**关闭结果描述的是裁决时剩余资格消失，不代表此前成交已经入账。B2 先成交 0.10 BTC，再撤 0.15 BTC；账户尚未处理成交时预留仍为 15,000 USDT，其中 6,000 对应成交义务，9,000 才能返还。账户侧为每个 symbol 维护连续 lastAppliedSeq，收到后继批次应缓存或补拉缺口，不能越过前一结果先退款。前一个结果即使不含资金效果，也必须有空批次证明才能推进。私有订单终态可以更早展示，但必须与结转进度区分，不能让展示流替代账户结果流。按序是为了保留义务的先后关系，不是为了让页面看起来整齐。

## 第 5 层：连续进度怎样与记账共同成立

**面试官：**你要求连续消费，如果资金写完却没更新水位，或者水位先更新后崩溃，重启不还是会重复或漏账？

**面试者：**D 应在一个事务中锁定该 symbol 的账户消费进度，确认本批正好是下一逻辑 commandSeq 且尚未处理，再更新整批双边余额、预留和分录，插入批次去重记录，最后推进同一事务内的 lastAppliedSeq[symbol]。成交时买方扣除限价对应预留、收到基础币并返还价差，卖方扣除基础币预留并收到成交款，不能只写一侧账户。本批任何一笔失败全部回滚，空批次也要原子记录处理与进度。已提交重复批次校验身份后直接返回既有结论，不再次改余额。账户服务报告的是按 symbol 连续的结果覆盖水位，不能拿某个账户最近一笔成交号冒充全流进度；某账户在中间没有变化也不代表结果缺口可以忽略。这样恢复位置与资金事实始终同生共死，不会靠内存 offset 猜测从哪里继续。

## 第 6 层：两条连续流同时修改共享账户

**面试官：**同一 symbol 的事务串行了，但 BTC/USDT 和 ETH/USDT 的消费者同时改甲的 USDT，分别连续就足够吗？

**面试者：**不够，流内顺序与跨流余额并发是两个约束。两个消费者可以分别锁自己的 symbol 进度，但修改共享账户资产时，都必须遵守数据库相同行锁或原子条件更新规则；A 的新预留事务也要遵守，不能一个走锁、另一个读旧值覆盖。D 还要校验具体 reservationId 的归属与余额，不能只看账户总预留。多账户、多资产按照稳定顺序加锁，发生死锁或并发冲突后整批回滚，以原 batchId 重试。不同 symbol 不必伪造全局撮合顺序，但共享余额更新必须被数据库串行协调，所有改动才能相加而非相互覆盖。这一保证依赖相关账户能够进入同一数据库事务，跨账务分片不属于当前能力。

## 第 7 层：数据库正确了，运输层还能怎样失败

**面试官：**共享账户事务已经解决，如果 D 提交后 MQ 确认丢失，或者 MQ 本身丢了消息，整个链路怎样恢复？

**面试者：**D 提交而消息未确认时，重投会命中同事务保存的去重记录，不再扣款或退款；如果 D 根本没提交，数据库回滚后可以完整重做。MQ 只负责运输，不是成交事实源，MQ offset 也不是账户业务进度。消息缺失时用账户的连续水位向已提交结果存储补读，缺口未补齐不处理后继结果；分发器自己的发送游标不能替代这个核对。即使旧分发器再次发送，账户也只能接受具有源提交依据的原批次，不能接受未提交试算结果。通知、查询投影与账户可以各有进度，但资金只认结果和事务。不能通过“确认过就删源”把可恢复协议退化成依赖消息永不丢失的假设。

## 第 8 层：怎样验收重试和补读没有漏洞

**面试官：**源日志不能随便删，那怎样同时验收恢复正确性和保留策略，避免无限保留掩盖设计问题？

**面试者：**先用 B2 构造可手工检查的交付历史：隐藏成交批次、先送关闭批次，应保持水位不越过缺口，预留仍为 15,000；补回成交后先支付 6,000，再按关闭结果退 9,000，甲最终可用 14,000 并获得 0.10 BTC。再模拟 D 已提交但确认丢失，重复发布两批，余额与分录不能增加。额外将一批拆成不完整片段、同身份改内容，都不得推进账务。源结果只有在所需消费者进度与可靠归档或可验证恢复基线覆盖后，才可按明确策略压缩；账务去重与历史身份也不能随意提前过期。这些是方案验收预期，不是已执行的测试结论。

## 本题收束

- **讲透的机制：**可重读的已提交结果提供事实源，稳定身份区分重投与新业务，完整批次和连续水位约束 D，事务同时保存资金效果、分录、去重与进度。
- **易错边界：**有 tradeId 不代表可以只按消息编号去重；完整批次仍须按 symbol 连续消费；每流串行不替代共享账户数据库并发约束；运输确认不是账务提交证明。
- **反例与预期：**只送 B2 关闭批次并中断网络。错误实现看到 CANCELED 就全退；正确实现保留缺口和预留，不宣告资金收尾。补读完成后仅退 9,000，反复重投也只有一套成交与退款分录。
