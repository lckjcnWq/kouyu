## 先看懂：关键词大白话解释

本专题把“点击买入”拆成能分别查证的业务阶段：先保存意图和占款，再可靠受理、裁决成交，最后记账并让页面追上。公共条件是链下 BTC/USDT 现货、限价 GTC、按已有挂单价成交、零手续费，相关账户共用事务数据库；其他订单类型、跨库和链上结算不是已有能力。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 现货中央限价订单簿 | 用自己的币和钱，与按价格排队的真实买卖单交换。 | 不涉及杠杆仓位；买价是最高接受价，不是每笔固定成交价。 |
| GTC | 未成交的剩余部分一直有效，直到成交或权威撤销。 | 网关等待超时不会让挂单自动过期。 |
| 请求键与规范化载荷 | 请求键标识“哪一次业务”，规范化载荷说明“到底要买什么”。 | 账户、命令类型、请求号共同定键；成功绑定后，同键改价改量是冲突。 |
| 意图与三个身份 | 意图是已保存的买卖要求，订单和预留各有自己的编号。 | intentId、orderId、reservationId 一对一绑定，不因重试另建一套。 |
| 可用与预留 | 可用还能花，预留已给指定业务占住，但还没全部付出去。 | 预留覆盖未来执行与已经成交但尚未入账的义务。 |
| 事务 A 与持久待办 | 把请求绑定、意图、占款和后续提交任务一起存牢。 | 崩溃后有人能接着投递，不会只扣钱却丢掉任务。 |
| 预留凭据 | 账户域确认占款提交后签发的执行资格证明。 | 绑定原账户和载荷；签名不能代替去重，也不允许本地到期便退款。 |
| 边界 B 与可靠受理 | 命令已经达到复制日志的多数派持久提交。 | 获得 commandSeq 只证明可恢复受理，不等于接纳、成交或到账。 |
| 单写者与权威顺序 | 每个交易对只有一个有效裁决者，按共同顺序执行。 | Place、Cancel、AbortIntent 不能由多个模块各判一套终态。 |
| ResultBatch 与边界 C | 一条命令的完整裁决结果和撮合进度一起正式提交。 | 多笔成交、订单变化、关闭与预留动作不可只留下半包。 |
| commandSeq 与 AppliedSeq | 前者是逻辑命令位置，后者是完整裁决到的位置。 | 不是底层日志行号，也不是消息队列的确认偏移。 |
| tradeId 与订单版本 | 分别标识哪笔成交、某张订单变化到第几版。 | 重发不生成新成交；旧展示不能覆盖新版本。 |
| 三组状态 | 意图提交、订单执行、资金结转各自描述不同进度。 | RESOLVED 不必然全成；FILLED 也可能仍在等待结转。 |
| 数量守恒 | 订单原量必须能解释成已成交、还可成交和已取消三部分。 | 已接纳订单满足原量＝累计成交＋剩余＋撤销；拒绝不伪造入簿历史。 |
| Cancel 与 AbortIntent | 前者撤已有订单余量，后者关闭可能仍在途的原意图。 | 普通撤单查无目标，不能证明迟到 Place 永远不得执行。 |
| 关闭标记 | 持久记住某个意图不得再次获得执行资格。 | 先关闭后到达的 Place 必须拒绝；不能按本地 TTL 忘掉。 |
| 事务 D 与账务水位 | 整批双边资产、分录、去重和进度一起入账。 | 先处理前序成交，再处理退款；终态不授权越过历史义务。 |
| 投影、私有游标与快照 | 页面是正式结果的副本，游标定位回报流，快照提供重建起点。 | 回报游标、订单版本和账户水位不能互相冒充。 |
| 恢复与任期围栏 | 按已提交事实重建，并在存储侧阻止旧主继续新写。 | 已有结果只应用；确认无结果的已受理尾部才继续裁决。 |
| 背压与内存 MVP | 背压限制新工作；MVP 是帮助手算的最小模拟。 | channel 不提供持久受理；末尾伪代码不证明崩溃原子性或生产性能。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，想买 0.25 BTC，限价 60,100。接入先确认账户和整数精度，再在事务 A 中把请求 buy-001、意图、15,025 的预留和待提交任务共同保存，可用只剩 4,975。甲没等到响应，仍用原键重试；系统返回同一业务，不再占款。这里记忆的是成功绑定的意图，尚未建意图的余额不足拒绝并不默认永久固定，不能把不同前提的拒绝规则照搬过来。

提交器把原 Place 送入交易对日志，越过 B 才能说可靠受理。撮合按顺序接纳后，先买 0.10 BTC、价 60,000，再买 0.15 BTC、价 60,100。全部变化与进度在 C 共同提交，此时全成与 15,015 的付款义务成立，但账户可以还没动。D 随后在同库事务中结转买卖双方、返还价差 10，甲才得到 0.25 BTC、可用 4,985；页面还须按自己的版本追上，不能把前面任何一次成功当成所有阶段完成。

独立重置初始条件，甲改以 60,000 买 0.25，预留 15,000，先成交 0.10 后撤余下 0.15。撤单与新增成交必须同序竞争；CANCELED 也仍保留已成交的 0.10。若账务还没消费，15,000 仍覆盖付款和退款，必须先付 6,000，再退 9,000，最终可用 14,000。若连 Place 是否到达都不确定，普通 Cancel 的查无目标不够，须由授权 AbortIntent 建立持久关闭，再依据顺序释放可退资金。

遇到崩溃，接管者恢复订单数量、排队位置、去重与关闭标记，原成交只应用不重撮合；有效任期由存储挡住旧主新写。用户重连则补回报或接带水位的快照，不凭页面空白补单。流量过大时，入口限制新单并保留关闭和恢复资源，已受理工作不能直接丢弃退款。最后的内存小模拟只帮助手算这些关系，不代表已经验证数据库、主备或链上系统。

## 第一部分：文字全流程

### 1.1 讨论基线与准备条件

| 项目 | 统一约定 |
|---|---|
| 产品与执行 | BTC/USDT 现货中央限价订单簿；链下托管、链下撮合、链下账务 |
| 已支持订单 | 仅限价 GTC；价格优先，同价按权威接纳顺序；成交价取已有挂单价 |
| 手续费与账户 | 零手续费；买卖方不同账户；相关账户位于同一事务数据库 |
| 接入与资产 | 鉴权确定账户；账户事务原子创建意图、预留和待提交记录 |
| 命令与结果 | 每交易对顺序日志，持久化多数派提交、任期隔离；单个有效撮合写入者 |
| 状态权威 | 账户域拥有预留与账本；撮合域拥有订单执行状态与成交；查询只是投影 |
| 成功含义 | 意图已保存、命令已受理、订单已接纳、成交已确定、账务已完成分别报告 |
| 明确排除 | 默认不支持市价、IOC、FOK、原地改单、跨账务分片、链上结算与重组 |

后文如比较其他订单类型、改单或签名订单，必须明确改变了哪项条件，不能据此声称基线已经实现。无需安装 Go、数据库或消息队列；末尾只有可手工推演的伪代码。

### 1.2 贯穿案例：B1 全成，B2 部分成交后撤单

与相邻专题沿用同一组数值。交易前卖单 S1 为乙的 `0.10 BTC @ 60,000 USDT/BTC`，S2 为丙的 `0.20 BTC @ 60,100 USDT/BTC`，卖出 BTC 均已预留。甲初始可用 `20,000 USDT`、`0 BTC`。

**主案例 B1：**甲提交 `clientOrderId=buy-001`，买入 `0.25 BTC`，限价 `60,100`。

- 预留 `15,025 USDT`，可用降为 `4,975 USDT`。
- 成交 `0.10 @ 60,000` 和 `0.15 @ 60,100`，合计支出 `15,015 USDT`。
- B1 全成：累计成交 `0.25 BTC`，剩余量、撤销量均为零。
- 结转后返还价差 `10 USDT`，甲可用 `4,985 USDT`、`0.25 BTC`，B1 预留为零；S2 剩余 `0.05 BTC`。

**独立变体 B2：**从同一初始状态重新开始，只把甲的限价改为 `60,000`，请求身份改为 `buy-002`。预留 `15,000 USDT`，只成交 S1 的 `0.10 BTC`，剩余 `0.15 BTC` 挂单。随后撤掉剩余量：最终累计成交 `0.10`、撤销 `0.15`、剩余零；甲支出 `6,000 USDT`，可用 `14,000 USDT`、`0.10 BTC`。这个变体不接在 B1 之后执行。

### 1.3 主链路：接入不等于接纳，终态不等于结转

```text
客户端提交 Place〔账户凭据、交易对、方向、价格、数量、clientOrderId〕
    ↓
接入层鉴权与基础保护
    账户身份、权限、限流、十进制解析、精度和业务上限检查
    ├─ 校验失败 → 明确拒绝；尚未产生预留或撮合资格
    └─ 校验通过
         ↓
账户事务〔共享余额的权威边界〕
    唯一请求键 + 规范化载荷绑定
    原子创建 intentId、orderId、reservationId、待提交记录并扣可用/增预留
    ├─ 同键同载荷 → 返回原意图，不重复占资
    ├─ 同键不同载荷 → 冲突，不覆盖旧意图
    └─ 余额不足 → 事务不创建可执行预留
         ↓
持久提交器反复投递原 Place
    命令多数派持久提交 → 获得 commandSeq → 可报告“可靠受理”
    不能把写进进程队列或发送超时当成此阶段的结论
         ↓
每交易对撮合单写者按已提交顺序处理
    校验凭据绑定、业务去重、关闭标记和版本化规则
    生成订单接纳/拒绝、成交与数量变化的临时变更集
         ↓
完整 ResultBatch + 新 AppliedSeq 原子提交
    此后订单执行结果和成交义务成立；不可因客户端断线撤销
    ├─ 私有订单/成交回报投影 → 报告执行状态、订单版本、结果位置
    ├─ 查询投影 → 最终追上权威版本，不参与撮合或退款裁决
    └─ 账户消费者按该交易对结果顺序处理完整批次
                                 ↓
                           一个账务事务
                           双边扣预留/入账、价差返还、确定的剩余释放
                           分录 + 批次去重 + 消费进度共同提交
                                 ↓
                           结转状态 APPLIED
                           账户回报/查询达到相应水位
```

订单挂单期间还可能有新的对手单成交。它与撤单一样，最终通过该交易对的同一权威顺序改变订单；不是由接入服务直接修改状态。

### 1.4 异常分支与收敛

```text
预留提交成功，但 Place 回包超时
    → 返回处理中/未知，保留原请求身份，提交器继续查询或重投
    → 若业务要求放弃：提交 AbortIntent，与 Place 在同一序列裁决
    → 只有已提交关闭结果、相关成交已按序处理，才能释放可退部分

B2 已部分成交，Cancel 与后续对手单竞争
    → 在同一命令序列排先后
    → 先成交：Cancel 只能撤裁决时剩余量
    → 先撤单：关闭剩余执行资格，后续对手单不能再匹配 B2

订单已全成/已撤销，账户消费者失败
    → 执行终态不回滚；预留仍覆盖未结转义务
    → 重放完整结果批次，按账务事务去重，恢复后继续结转

私有回报丢失或查询滞后
    → 按回报游标补发或用带版本/水位的快照重建
    → 不重新生成订单，不以“页面没有”退款
```

### 1.5 沿案例解释数量、资金与完成条件

| 阶段 | B1 的订单事实 | 甲 USDT 可用 / 预留 | 该阶段究竟承诺什么 |
|---|---|---|---|
| 意图与预留提交 | 尚未接纳为活跃订单 | 4,975 / 15,025 | 同一意图被保存，有有效资产支持 |
| 命令可靠受理 | 等待权威处理 | 4,975 / 15,025 | 命令进入可恢复处理范围，不承诺成交 |
| 结果批次提交 | FILLED，累计成交 0.25 BTC | 4,975 / 15,025 | 成交与订单变化已确定，账务可暂时落后 |
| 账务事务提交 | FILLED，结转 APPLIED | 4,985 / 0 | 甲获 0.25 BTC；成交支出与返还均已入账 |
| 查询与回报追上 | 读取相同或更新的版本 | 不产生额外资产变化 | 展示覆盖到相应结果/账户水位 |

B2 若在成交尚未结转时已经撤单，实际预留仍可能是 `15,000 USDT`，而不是零。其中 `6,000` 对应既有成交义务，`9,000` 对应可退剩余量。账户必须先处理成交，再处理有序关闭结果；不能看到 `CANCELED` 就把 `15,000` 全退。

## 第二部分：核心板块

| 板块 | 决定什么、拥有什么状态 | 上下游契约与核心原因 |
|---|---|---|
| 请求与意图接入 | 请求唯一键、载荷绑定、持久意图 | 把不可靠网络重试归并为同一业务；否则每次重试都可能成为新订单 |
| 资产准入 | 可用、预留、预留凭据和待提交记录 | 与共享余额竞争原子协调；向撮合提供不可被单方提前解冻的资格 |
| 可靠受理与顺序 | 已提交命令位置、任期、受理确认 | 为 Place、Cancel、AbortIntent 提供共同裁决顺序，不把到达时间当优先级 |
| 权威生命周期 | 订单数量、执行状态、业务去重、关闭标记 | 在结果提交边界确立唯一成交/撤单结果，不允许多个模块独立写订单终态 |
| 结果与账务收尾 | 已提交结果、账务分录、消费进度 | 防止终态先到导致错退、重复消息导致重复记账，收敛跨域暂态 |
| 查询、回报与恢复 | 投影版本、回报游标、快照水位 | 让用户能识别未知与滞后，并在故障后回到相同业务事实 |

## 第三部分：核心 20%

这里的 20% 指重要性集中，不是减少为两三道题。只保留会决定订单身份、执行资格、唯一终态与资金收尾的机制。

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 持久幂等与载荷绑定 | 请求进入账户事务 | 重试不能创建第二笔业务 | 重复下单、重复占资、旧键被新订单复用 | 唯一约束、规范化、并发赢家、保留策略 |
| 分阶段确认 | 意图、命令、结果、账务提交 | 区分“系统收到”与“业务完成” | 超时误判失败，已成交后补单 | 四个提交点、结果查询与未知状态 |
| 单一状态所有权 | 撮合顺序与结果提交 | 成交和撤单必须由同一裁决者决定 | 状态回退、撤后再成交 | 单写者、订单版本、终态与数量守恒 |
| 预留与资格关闭 | 预留到关闭结果 | 资金释放必须晚于执行资格关闭 | 迟到订单无资金成交 | 原子预留、AbortIntent、关闭标记 |
| 完整结果批次 | 撮合到记账 | 交易事实不能拆成独立猜测 | 丢成交、终态先退款 | 稳定身份、完整性、按序消费、事务去重 |
| 确定性恢复 | 崩溃与接管 | 重启不能重新解释已提交业务 | 已确认订单丢失、恢复后优先级变化 | 结果/输入边界、快照内容、epoch 隔离 |
| 带版本的可见性 | 查询与私有回报 | 投影滞后不能改变权威事实 | 页面闪回、补单、误对账 | 游标、版本、快照水位、账户独立进度 |
| 有界并发与过载契约 | Go 接入到提交 | 局部超时不能破坏业务协议 | 撤单饿死、后台任务泄漏、预留悬挂 | 有界队列、持久待办、阶段化拒绝 |

## 第四部分：设计与规则

### 4.1 身份、字段与权威归属

```text
请求键 RequestKey = accountId + commandType + clientRequestId
    Place 中 clientRequestId = clientOrderId
    Cancel 有独立 clientRequestId，绑定目标 orderId
下单身份 = intentId；一对一绑定 orderId、reservationId 和规范化载荷
命令位置 = symbol + commandSeq
结果批次 batchId = symbol + commandSeq
成交身份 tradeId = symbol + commandSeq + matchIndex
订单变更身份 = orderId + orderVersion
```

请求一旦成功绑定持久意图，同键同载荷返回原处理结果或当前进度，同键异载荷返回冲突；超时不换键。未创建意图前的鉴权、参数或余额不足拒绝，不默认永久缓存首次结果；其重试契约见母题 02。命令日志允许同一业务身份重复入列，撮合还要持久去重；后一个命令位置不能获得第二份业务效果。

| 对象 | 必要字段 | 权威与提交范围 |
|---|---|---|
| 意图 | intentId、orderId、accountId、symbol、requestKey、payloadHash、reservationId、submissionState | 账户事务与预留、待提交记录共同创建；submissionState 不决定订单执行状态 |
| 预留 | reservationId、intentId、asset、amount、载荷绑定 | 账户域；不凭 TTL 单独失效；凭据在事务提交后签发 |
| 命令 | commandSeq、type、业务身份、目标、ruleVersion、验证后的资格依据 | 已提交输入日志；Place / Cancel / AbortIntent 共享每交易对顺序 |
| 订单 | originalQty、cumFilledQty、leavesQty、canceledQty、executionStatus、prioritySeq、version | 撮合域；数量与订单变更在完整结果中生效 |
| 结果 | batchId、trades、orderChanges、reservationActions、intentClosure、ruleVersion | 与 AppliedSeq 同一原子记录提交；无成交命令也有明确结果 |
| 账务 | 分录、批次处理记录、每交易对 lastAppliedSeq、预留余额 | 同一数据库事务处理本批所有相关账户；不以 MQ offset 代替事务进度 |
| 回报 | streamCursor、orderVersion、sourceResultSeq、相关 settlement 水位 | 私有投影；账户可见性与执行可见性分别报告 |

### 4.2 三组状态不能揉成一个枚举

1. **意图/提交状态**：`PREPARED / SUBMISSION_PENDING / COMMAND_COMMITTED / RESOLVED` 等，用于表示持久工作流进度。它们不是订单执行状态；`RESOLVED` 也不必然代表全成。
2. **执行状态**：有效接纳后为 `NEW / PARTIALLY_FILLED / FILLED / CANCELED`；未接纳结果可为 `REJECTED`。本专题对未接纳拒绝保留意图记录，不把它强塞为一个活跃订单。
3. **结转与展示进度**：用结果水位说明账户处理到哪里。单次结果的结转可为 `PENDING / APPLIED`；活跃订单可能后来又成交，不可把一次 APPLIED 当作其永久资金终态。只有订单终态且账户已覆盖终态及此前相关结果，才能说该单资金收尾完成。

已接纳订单满足：

```text
originalQty = cumFilledQty + leavesQty + canceledQty
三个右侧分量非负；cumFilledQty 与 canceledQty 只增不减
NEW：cumFilledQty = 0，leavesQty > 0
PARTIALLY_FILLED：cumFilledQty > 0，leavesQty > 0
FILLED：cumFilledQty = originalQty，leavesQty = 0，canceledQty = 0
CANCELED：leavesQty = 0，canceledQty > 0；允许保留历史成交量
```

未接纳的拒绝/关闭可以没有活跃订单对象，不对其伪造“已入簿后又撤销”的历史。客户端的 `CANCEL_PENDING` 是请求进度，不阻止随后在权威排序中更早的成交。

### 4.3 精度、资金与释放规则

- 价格单位 `0.01 USDT/BTC`，数量单位 `0.0001 BTC`，USDT 账务单位 `0.000001 USDT`。因此 `quoteUnits = priceTicks × qtyLots`，乘法前检查 `int64` 溢出和业务上限；不经 `float64` 中转。
- 买单初始预留为限价乘数量；卖单为数量。不同交易对共享同一账户的可用余额，竞争必须由账户数据库的行锁或条件更新裁决。
- 撮合和账务在相同结果水位时，活跃买单预留应为 `limitPrice × leavesQty`，卖单为 `leavesQty`。在途成交尚未结转时，不能据最新剩余量直接覆盖账本预留。
- 凭据绑定账户、意图、订单载荷、预留与规则依据；只在原预留事务提交后有效。账户域不得按网关超时或本地 TTL 单方撤销它。
- `AbortIntent` 是有权限的内部关闭命令。若先于 Place，持久记录关闭标记并禁止迟到接纳；若后于 Place，撤实际剩余量；若已全成，只返回既有义务。释放以已提交关闭结果及有序账务处理为依据。
- 零手续费、无充提条件下，各币种分别守恒；不能把 BTC 和 USDT 相加验证。跨账务分片需要额外协议，不在这里用“分布式事务”四字假装完成。

### 4.4 架构、顺序与原子边界

```text
接入层〔鉴权、解析、请求身份〕
    ↓
账户数据库
    事务 A：唯一请求绑定 + 意图 + 余额预留 + 持久待提交记录
    ↓ 事务提交后由持久工作流投递
每交易对复制日志
    边界 B：CommandLog 多数派持久提交，分配 commandSeq
    ↓
每交易对撮合单写者〔有效 epoch〕
    处理已提交输入；临时计算，不先发布
    边界 C：ResultBatch + AppliedSeq 原子持久提交
    ├─ 结果运输 → 账户事务 D：双边资产 + 分录 + 去重 + 消费进度
    └─ 结果运输 → 私有回报 / 查询投影
```

日志层拒绝旧 epoch，结果追加检查前序 AppliedSeq；前一结果提交是否成功未查明前，不继续处理下一条输入。`commandSeq` 是每交易对从 1 开始的连续逻辑命令序号，`AppliedSeq` 与账务消费进度按这个坐标表示；底层物理日志可能同时包含结果、任期等记录，物理索引和 MQ offset 不能直接充当该序号。账户事务 A 与边界 B 不是分布式原子提交，靠持久待提交记录、原身份重试和有序关闭收敛。边界 C 与 D 之间允许账务落后，但成交事实不能撤回。

Go 层采用有界接入并发、每交易对 actor 单写、独立结果分发与持久提交器。channel 不是可靠日志；进程内锁不覆盖共享余额；客户端 context 取消不等于已受理业务撤销。

## 第七部分：工程实践——一个简洁 MVP

### 7.1 目标与范围

只手工验证 B2 的一个小闭环：**同一意图不重复预留，关闭阻止迟到 Place，成交和撤单按输入顺序生效，账务落后时不提前释放。**

以下为单进程、无崩溃的内存模拟；输入成交来自已给定对手方，校验限价和剩余量，但不实现订单簿或双边完整账本。它不验证持久化、主备、凭据签发、并发锁或消息传输，也不把顺序执行假称为生产级可靠提交。

### 7.2 一段核心伪代码

金额和数量使用第四部分的整数单位。每个 `id` 代表一个买入意图，`key` 已包含账户、命令类型和请求号；为缩短代码，所有失败均在修改前返回错误。

```text
available = 20_000_000_000; intents = {}; keys = {}; batches = []; applied = 0

Prepare(key, payload):
    若 key 在 keys：同载荷返回原 id；不同载荷返回 CONFLICT
    price, qty = payload.price, payload.qty
    校验 price > 0、qty > 0、整数精度与 price * qty 不溢出
    need = price * qty
    若 available < need：返回 INSUFFICIENT
    id = 新身份；available -= need
    intents[id] = {payload, reserve: need, receivedBTC: 0,
                   accepted: false, closed: false, filled: 0, leaves: 0, canceled: 0}
    keys[key] = id；返回 id

Apply(command):                         # 输入列表的顺序就是本模拟的裁决顺序
    id = command.id；校验 id 存在；i = intents[id]
    若 command.type == PLACE：
        若 i.closed：返回 CLOSED       # 关闭标记一直保留
        若 i.accepted：返回原接纳结果
        i.accepted = true；i.leaves = i.payload.qty
    若 command.type == FILL：
        q, tradePrice = command.qty, command.tradePrice
        校验 i.accepted 且非 i.closed，0 < q <= i.leaves，0 < tradePrice <= i.payload.price
        i.filled += q；i.leaves -= q
        batches.append({id, consume: tradePrice*q,
                        refund: (i.payload.price-tradePrice)*q, btc: q})
        若 i.leaves == 0：i.closed = true
    若 command.type == CLOSE：           # 简化代表 AbortIntent，也能关闭已接纳剩余
        若 i.closed：返回当前终态与数量，不新增退款批次
        remaining = i.leaves 若 i.accepted 否则 i.payload.qty
        若 i.accepted：i.canceled += remaining；i.leaves = 0
        i.closed = true
        batches.append({id, consume: 0, refund: i.payload.price*remaining, btc: 0})
    返回当前数量与 closed                  # 不在此处修改账户预留

SettleNext():                           # 唯一消费者，只允许连续推进
    若 applied == len(batches)：返回 NO_WORK
    b = batches[applied]；i = intents[b.id]
    校验 i.reserve >= b.consume + b.refund
    i.reserve -= b.consume + b.refund
    available += b.refund；i.receivedBTC += b.btc
    applied += 1                        # 单线程模型中与本次变化一起完成
```

`CLOSE` 在未接纳时保留意图关闭事实，但不伪造订单撤销量。模拟没有外部任意批次写入口，因此重试 `SettleNext` 只会继续未处理位置；这不等于展示了数据库崩溃原子性。生产消费者去重与事务机制见母题 09。

### 7.3 输入与预期结果

每行从独立初始状态开始；为便于复述，以下将整数结果换回 BTC/USDT。

| 输入 | 手工推演的预期结果 |
|---|---|
| B2 同键同载荷调用两次 Prepare | 返回同一 id；可用 5,000，预留 15,000，不会变成重复预留 30,000 |
| B2 Prepare → Place → Fill(0.10, 60,000) → Close，尚未 Settle | 累计成交 0.10、撤销 0.15、剩余零；预留仍为 15,000，不因 closed 自动退款 |
| 接上一行，连续 SettleNext 两次 | 第一批消耗 6,000、得到 0.10 BTC；第二批返还 9,000；最终可用 14,000、预留零 |
| B2 Prepare → Close → Place → SettleNext | Place 返回 CLOSED；没有活跃订单，预留 15,000 全部返还，甲恢复 20,000 |
| B2 Prepare → Place → Close → Fill(0.10, 60,000) | Fill 被拒绝，无成交批次；不能撤后再成交 |
| 同键但数量从 0.25 改为 0.30 | 返回 CONFLICT；不改变原意图和预留 |

这些是预期结果，不是工程测试报告；本专题不创建可运行项目、不执行工程测试。

## 学习收束与复利沉淀

本次采用“系统思维看跨域边界、二八法则找关键机制、逆向思维推演失败窗口”的组织方式。可重复使用的检查链是：

```text
请求身份是否稳定
    → 执行资格是否有资产支持
    → 受理与业务结果分别在哪里提交
    → 成交与撤销是否同序裁决
    → 终态之前的义务是否完整交付
    → 账务与展示是否各自追到明确水位
```

最值得固化的规则：**“查不到”不是“未执行”，“已撤销”不是“全部退款”，“goroutine 返回”不是“业务完成”。** 下一步学习时可遮住回答，逐层解释 B2 在任意两个提交动作之间崩溃会留下什么；解释不清的地方就是需要补强的协议边界。
