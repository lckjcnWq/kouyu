# 大问题 3：什么才算可靠受理，响应超时后怎样查询和重试？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文给“受理成功”划一条可查证的线：命令在约定故障范围内已持久可恢复，而不是某个线程收到消息。前提是每交易对顺序复制日志、多数派持久提交和任期隔离；放进任意消息组件不自动获得这些保证。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 可靠受理 | 系统已正式保存输入，承诺后续恢复并给出裁决。 | 不承诺接纳、成交，也不承诺钱已经结转。 |
| 多数派持久提交 | 足够多复制节点按协议把记录存牢并形成提交事实。 | 主节点自己收到了或单机写成功，不等于这一保证。 |
| commandSeq | 一条命令在本交易对里的逻辑位置。 | 有编号说明受理，不足以把执行状态写成 NEW。 |
| 预留在前 | 先为原意图占住资金，再投递可执行 Place。 | 防止命令先成交、后面才发现没钱；颠倒顺序需要新协议。 |
| 持久待办 | 与预留一起保存的投递工作清单。 | A 到 B 不是大事务，靠它跨过中间窗口。 |
| 任务租约 | 暂时把一项待办交给某个工作者处理。 | 到期只换处理者，不是交易预留到期退款。 |
| 提交未知与原身份重投 | 回复超时后，沿同一业务查询或再送。 | 可能已成功而回执丢失，不能换键补单。 |
| 输入位置与业务身份 | 一个表示“排在哪”，一个表示“是哪笔买卖”。 | 同一 Place 可占两个位置，但不能创建两张订单。 |
| 空效果结果 | 重复命令明确引用原裁决，不新增业务变化。 | 新位置仍推进进度，不复制成交、退款或首次排队资格。 |
| ResultBatch 与执行待定 | 完整结果包尚未提交，就还没有正式执行结论。 | 已受理未裁决必须报告处理中，不能伪装已接纳。 |
| 权威未找到 | 在某次权威查询时没有这条输入或结果。 | 仍可能有在途提交器，不证明未来绝不执行。 |
| AbortIntent 与关闭 | 将“不要再执行这个意图”送进共同顺序并持久生效。 | 关闭先到挡迟到 Place，后到保留成交、只撤余量。 |
| epoch 与 fsync | epoch 是写入任期；fsync 是单机持久化动作。 | 接管要隔离旧主；单机磁盘持久不等同多数派故障承诺。 |
| 正确性与活性 | 前者不能做错，后者不能永远无人推进。 | 未知必须有稳定身份、恢复责任、积压告警和收尾路径。 |

## 把整篇文章压缩成一个故事

甲的 B1 已在账户事务中保存意图、占住 15,025 USDT，并写好待提交记录，进程却在发送 Place 前退出。另一工作者接手同一待办，继续使用原意图和订单编号；若只有内存 channel，这项责任就会消失。任务租约只是允许换人投递，不能因为租约到期就把支持原订单的钱退掉，远程调用也不应一直占着余额行锁。

Place 已达到日志多数派持久提交，但回执丢了。甲看到超时，提交器也不知道 commandSeq，双方都不能据此断言失败。重投可以占到第二个输入位置，撮合则按持久业务身份识别原单：第一个合法结果确定一次，第二个结果只引用原裁决并推进位置，不再次入簿、不刷新优先级、不复制成交。网络会重复，业务不能重复。

查询若只确认命令已提交、还没有完整结果，就返回“受理完成、执行待定”，而不是 NEW。普通投影未找到不算证据；即便权威当前未找到，也可能还有工作者在路上。甲坚持放弃时，由授权 AbortIntent 与 Place 同序裁决，先建立永久关闭，或撤掉已接纳的实际余量；账户按序履行此前成交后才释放确定可退部分。

主节点宕机后，新写入者必须恢复已提交前缀，旧写入者由任期围栏挡住；失去多数派就停发新的可靠确认，不能拿单机落盘冒充原承诺。运维还要追踪待办年龄、重试和阻塞原因，让未知有负责人、有恢复动作，而不是无限期叫用户等待。这是一套故障语义和验收设计，不是已经完成的切主实验。

**流程位置与核心机制：**深入意图保存到命令受理、再到执行结果之间的提交语义，解释持久待提交记录和响应不确定窗口。身份唯一性见母题 02，主动关闭迟到请求见母题 06。

**必要前提：**命令日志提供每交易对顺序、多数派持久提交和任期隔离；撮合只处理已提交输入。本题不把 Kafka 配置、内存 channel 或单机写成功自动等同于这些保证。

## 第 1 层：先定义“受理”承诺

**面试官：**什么才算可靠受理，响应超时后怎样查询和重试？

**面试者：**可靠受理是命令已经跨过明确的持久提交边界，系统承诺在故障假设内恢复它并给出业务处理结果，而不是工作线程收到一个对象。在本模型中，Place 进入对应交易对日志并达到多数派持久提交，获得 commandSeq，才可报告可靠受理。它不代表订单必然接纳，更不代表成交和账务完成。

如果调用超时，客户端保持原请求键，查询原意图进度；提交器也沿用原业务身份查询或重投。因为超时无法区分“没送到”和“已经提交但回包丢失”，不能据此返回确定失败、换新键补单或释放预留。服务应同时给出阶段和查询身份，让用户明确是意图已保存、命令已提交，还是执行结果已确定。

## 第 2 层：为什么把预留和命令提交拆成两个边界

**面试官：**既然最终要进日志，为什么不先把订单可靠受理，再异步检查账户和扣预留？

**面试者：**那会改变“谁有资格进入撮合”的协议。如果命令先被当作可执行订单，后续预留失败，撮合可能已经产生没有资产支持的成交；如果先受理但明确不能执行，仍要额外定义等待资金、失败关闭和超时处理。本基线选择先在账户事务中建立有效预留，再提交具备该资格的 Place，避免把无资金命令混进可执行路径。

这不等于声称账户事务和日志是原子的。两者之间允许预留已存在、命令仍未提交的状态，持久工作流负责继续。账户也不能因预留等待太久自行失效，因为它可能已支持一条回执未知的命令。设计重点是准确命名两个边界，并为中间状态提供可恢复的动作，不是用一个“已受理”字段掩盖差异。

## 第 3 层：预留成功后怎样确保提交动作不会丢

**面试官：**两个边界之间靠工作流继续，那进程恰好在预留提交后、生成后台任务前崩溃怎么办？

**面试者：**不能在事务外才生成唯一的任务。账户事务必须共同写入意图、预留和待提交记录，提交器从数据库中的持久待办获取工作。这样扣款提交却没有提交任务的状态就不能出现；进程崩溃最多让任务暂时无人领取，而不是永久丢失。

任务可以用租约分配给工作者，租约过期只允许其他工作者继续投递，不释放交易预留。任务状态更新失败也不能破坏正确性，因为恢复者仍用原身份查询或发送，重复由业务去重处理。不宜拿着余额行锁执行远程日志调用，那既不使两个系统变成一个事务，还会延长锁持有时间，让单个交易对网络故障阻塞同账户的其他业务。

## 第 4 层：日志提交后回执丢失，怎样避免第二次受理变成第二笔订单

**面试官：**待办投递成功，但提交器没收到 commandSeq。它重投后，日志可以出现两条相同 Place 吗？

**面试者：**可以允许日志有两个输入位置，但业务效果只能有一次。日志服务可提供按业务身份查询提交位置的能力以减少重复；即使它没有端到端唯一入列，撮合也必须按 intentId 或 orderId 检查已接纳、已拒绝或已关闭的持久处理记录。第二个位置不能再入簿，也不能为同一笔订单刷新 prioritySeq。

所以要区分“输入位置唯一”和“业务效果唯一”。重复命令仍应产生一个可推进进度的明确处理结果，但只引用原业务结果，不重复产生成交或释放动作。若第一次 Place 已成交，而重复命令后来遇到不同盘口，不能重新按新盘口执行。入口的同键返回和撮合的重复裁决共同覆盖这个提交不确定窗口。

## 第 5 层：命令已提交但业务结果尚未提交时如何查询

**面试官：**日志告诉我原 Place 已提交，但撮合还没给结果。查询接口能直接返回订单 NEW 吗？

**面试者：**不能。NEW 是合法接纳后的执行状态，commandSeq 只证明输入受理，不能证明资格校验和结果提交已经完成。查询应返回原意图存在、命令已提交、执行结果待定；如果展示层只给一个字符串，可以显示处理中，但内部必须保留它和 NEW 的区别。

一旦 ResultBatch 与 AppliedSeq 原子提交，才有接纳、拒绝、部分成交或全成的权威结论。查询从结果投影读到的状态可以落后，要带来源水位，不能把尚未投影解释成权威不存在。对于需要更强查询的内部恢复流程，应查受理日志或已提交结果的权威身份索引；普通查询缓存没有资格证明原命令永远不会执行。

## 第 6 层：查询暂时未找到命令是否足以判定失败

**面试官：**你要求查权威索引。现在权威日志查不到 Place，是不是就可以撤掉预留并通知用户下单失败？

**面试者：**仍然不一定，因为查不到描述的是查询时刻，不是未来不能提交。原提交器可能在网络重试，另一工作者可能还持有原任务，Place 也可能稍后进入日志。单次不存在证明不能关闭执行资格。

若业务决定不再继续下单，要建立有序的关闭事实：发起授权 AbortIntent，在同一交易对序列中决定它与 Place 谁先。关闭先发生时持久保存拒绝迟到接纳的标记，关闭后发生时撤实际剩余量。只有关闭结果提交，并由账户按序处理既有成交与退款动作，才可退确定部分。暂停提交器能减少在途工作，却不是永久关闭证明；换一台机器恢复的旧任务仍必须受到同一个关闭标记约束。

## 第 7 层：什么故障下还能坚持“不丢已受理订单”

**面试官：**如果主节点在确认受理后宕机，你怎样保证备节点有这条命令？单机落盘够吗？

**面试者：**本模型的受理承诺建立在多数派持久提交上，而不是主节点本地追加完成。备节点接管必须基于已提交日志前缀，旧主还要被任期隔离，不能继续产生有效结果。只要在该复制系统承诺的故障范围内，已确认输入就应留在接管节点可恢复的提交前缀里。

单机 fsync 可以支持较弱的单机恢复假设，但如果磁盘随机器丢失，就不能承诺同样的主备安全性。系统失去足够多数派时应停止新的可靠确认，而不是为维持接口可用继续返回成功。这里必须明确依赖日志服务的实际能力及存储持久性；不能因为引入一个消息组件就省略提交策略、复制范围和旧主隔离。

## 第 8 层：用什么现象验收可靠受理协议

**面试官：**你既允许超时未知，又可能暂时停止确认。怎样从用户体验和正确性两方面验收，而不是所有异常都说“再等等”？

**面试者：**正确性和活性要分别验收。正确性上，对任一已返回 COMMAND_COMMITTED 的身份，恢复后必须找得到对应输入或已提交结果；重复查询和重投不能重复占资或改变优先级。活性上，持久待办应有提交延迟、重试次数和最长悬挂年龄告警，失去日志服务时明确报告处理受阻，恢复后继续推进或按授权关闭协议收尾。

用户侧返回稳定身份和当前阶段，提供有界等待与查询，不要求他们持续保持原连接。测试设计应覆盖“预留提交但未发送”“日志提交但回执丢失”“结果已提交但响应丢失”三种不同位置，它们的显示阶段不同，但最终都归并到同一意图。超时未知不是无限免责，而是必须有可追踪身份、恢复负责人和后续闭环的真实状态。

## 本题收束

- **讲透的机制：**可靠受理对应可恢复的已提交输入；持久待提交记录跨过账户和日志之间的非原子窗口；执行结果有独立提交边界。
- **最容易答错：**把写入 channel、网络发送成功或单机落盘直接称为多数派可靠受理；把“权威暂时查不到”当作永久不执行。
- **检验反例：**Place 的日志提交成功，提交器在保存 commandSeq 前崩溃。恢复后允许重投产生第二个位置，但必须仍只有一个 B1、一笔预留、原首次接纳优先级及两笔原成交；不允许生成新业务身份补单。
