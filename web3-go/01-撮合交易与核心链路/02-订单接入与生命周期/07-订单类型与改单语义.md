# 大问题 7：订单类型与改单怎样改变生命周期和优先级？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文比较“订单多承诺一项能力，就要多补哪些协议”。公共基线只有零费用现货限价 GTC；IOC、FOK、市价和原地改单都是显式扩展比较，不是已经实现的功能。各个金额例子从原始盘口独立开始。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 限价 | 买方能接受的最高价，或卖方能接受的最低价。 | 不保证立即成交，也不要求每笔都按限价成交。 |
| maker 价 | 按已经在簿上的对手挂单价格成交。 | B1 限价 60,100，首笔仍可按 60,000 买入。 |
| GTC | 剩余数量继续有效，直到成交或撤销。 | 是基线有效期规则，与价格约束是两个维度。 |
| IOC | 当次能立即成交的部分成交，剩余立即失效。 | 允许部分成交，但不把余量留在队列。 |
| FOK | 当次能全部完成才执行，否则一笔也不成交。 | 不足时不能先吃掉一档，再把余量取消。 |
| 可执行计划 | 在受保护的同一订单簿状态中算出全部合法成交。 | 行情快照深度不能保证检查到执行之间不变化。 |
| 单写与故障原子性 | 单写防命令交错，原子提交防崩溃留下半笔。 | FOK 全部成交及双方变化仍须在 C 完整提交。 |
| 市价与保护参数 | 不指定普通限价，但仍要约定价格或资金边界。 | 市价本身不说明能否部分成交，也不等于无限预算。 |
| 最大花费预算 | 这次买入最多能支出的计价资产金额。 | 撮合不得穿透预留，未用部分依正式结果返还。 |
| 撤旧建新 | 先关闭旧单，再用新身份提出新单。 | 中间有真实窗口，不承诺无缝原子替换。 |
| 总目标量与追加量 | 想累计买到多少，与这次新加买多少不是一回事。 | 目标仍为 0.25、旧单已成 0.10，新单应为 0.15。 |
| 载荷绑定与 Amend | 旧请求不能随手改内容；独立改单命令要有新契约。 | Amend 若未来支持，需绑定目标、预期版本和修改内容。 |
| 优先级保留与重排 | 哪些修改还能保留旧队列位置，必须明确制定规则。 | 同价减量可作为比较规则；增量改价不得默认插队。 |
| 新资产覆盖与释放水位 | 改价增量要足资，减量退款也不能跳过未结转成交。 | C 已关闭不等于 D 已退，不能提前花预计退款。 |

## 把整篇文章压缩成一个故事

甲以 60,100 限价买 0.25 BTC，基线 GTC 先匹配 0.10、价 60,000，再匹配 0.15、价 60,100，共支出 15,015；限价不是每笔一律付 60,100。若盘口不够，GTC 余量继续挂着。要比较其他类型，必须重新开始，不能让前一个实验吃掉的盘口影响后一个结论，也不能把名字加进参数就声称基线支持。

独立把限价改成 60,000，当前只能立即买到 0.10。若扩展为 IOC，可成交 0.10、让 0.15 失效，15,000 预留中支出 6,000、返还 9,000；若扩展为 FOK，买不满 0.25 就零成交，原卖单不变，再依结果退回全部预留。FOK 须在同一受保护状态下先形成完整计划，结果在 C 原子成立；单线程不能替代故障原子性。

甲再提出市价买入，也不能用最新行情估算金额就放行，必须先定义保护价或最大预算，以及不足时是否允许部分成交。随后甲想把已挂 B2 改价，基线只能比较显式撤旧建新：旧单可能在撤单前继续成交，新单也可能预留失败，不能承诺原子替换。若总目标仍是 0.25、旧单最终已成 0.10，新单只应买 0.15；D 未释放前不能使用预计退款。

旧 buy-002 绑定的是原业务，不是可编辑名字，同键换价换量必须冲突。未来真要原地 Amend，要另定请求身份、订单版本、数量边界、优先级与资金协议；同价减量是否保留位置也须公开约定，不能允许小单先占队、再无条件增量插队。新增规则还须绑定可追溯版本，旧单恢复继续用原约定，不能因程序升级就突然改变旧单的排队位置或资金上界。本文给的是扩展所需承诺和反例，没有实现这些扩展或运行工程测试。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题讨论执行规则怎样影响剩余量、成交原子性、优先级和预留。重点不是增加产品功能清单，而是识别每项能力必须补上的协议。撤单本身的竞争见母题 06，请求规范化与幂等见母题 02。

**能力边界：** 公共基线只实现现货限价 GTC，零费用，相关账户在同一事务库。下文的 IOC、FOK、市价与改单全部是**明确改变前提后的设计比较，基线未实现**。比较仍保留 A 资产预留、B 可靠命令、C 完整结果、D 账务四边界，不另建执行架构或第二个 MVP；每个数值变体从总览初始状态独立开始。

## 第 1 层：先分清价格约束和有效期约束

**面试官：** 订单类型与改单怎样改变生命周期和优先级？

**面试者：** 先明确基线只支持限价 GTC：限价限制可接受成交价，GTC 表示未成交剩余量继续有效，直到成交或明确撤销，两者不是同一维度。B1 限价 60,100、买入 0.25 BTC，可以吃掉 S1 的 0.10 和 S2 的 0.15，按已有挂单价共付 15,015 USDT；限价不是强制每笔按 60,100 成交，也不是保证立即全成。若流动性不足，合法剩余量继续入簿，同价按权威接纳顺序排队。IOC、FOK 改变剩余量和执行完整性，市价改变价格约束，改单还会触及原身份、优先级与预留。不能把这些名称当作几个接口参数，就认为基线的状态机和资金协议自然覆盖了它们。

## 第 2 层：IOC 和 FOK 的不同不只是剩余量归零

**面试官：** 你说 IOC 和 FOK 改变剩余量。若把限价改成 60,000、数量仍为 0.25，两者具体会产生什么不同？

**面试者：** 这是两个独立的限价订单扩展比较，其他规则不变，基线都未实现。当前可成交的只有 S1 的 0.10 BTC。限价 IOC 可以立即成交这 0.10，余下 0.15 立即失效，不进入挂单队列；限价 FOK 则要求本次裁决能够完整执行 0.25，否则整笔不成交。两者都不能留下活跃剩余量，但 IOC 可以有成交义务，FOK 失败没有成交义务。A 都可按限价预留 15,000；IOC 的 D 消耗 6,000、返还 9,000，FOK 失败的 D 返还全部预留。扩展规则要定义剩余失效的原因、数量与回报，不能把系统执行条件失效伪称为用户主动撤单，也不能因为“没有挂单”就跳过 C 的完整结果。

## 第 3 层：FOK 的“足够成交”必须在受保护范围内判断

**面试官：** FOK 先查深度够不够，够就循环撮合，不够就拒绝，这样不是已经保证全成或全拒了吗？

**面试者：** 若深度来自独立快照，检查后到执行前对手单可能被成交或撤掉，因此这不构成 FOK。比较方案应在该交易对有效单写者处理一个命令期间，基于同一受保护状态完成资格检查、可执行数量累计和完整成交计划，再一次性提交，其他命令不能插入计划内部。累计的必须是真正符合价格、剩余量和规则条件的可执行量，不是行情显示量。计划不满足 0.25，就不修改任何对手订单、不生成部分成交；满足才生成覆盖全量的临时变更集，并在 C 原子提交。这里的原子范围是该 FOK 的执行结果，不是把 A、B、C、D 合并成一个跨域事务；账务仍可在确定成交后滞后。

## 第 4 层：FOK 算完后崩溃也不能留下半笔成交

**面试官：** 你把 FOK 的计划放进单写者了。如果已经算出多笔成交，结果提交中途失败，会不会一半对手订单被改掉？

**面试者：** 单写者只消除了命令间交错，还需要 C 的原子提交保证故障一致性。计划里的全部成交、双方订单变化、预留动作和 AppliedSeq 必须作为一个完整结果共同提交；计算时使用临时变更集，提交前不发布成交，也不把部分改动暴露成权威状态。明确未提交就按原顺序重算，已经提交则恢复原结果；确认丢失时先查清，不能一边猜失败一边执行下一命令。B1 的原始盘口在 60,100 上有 0.30 BTC，比较中的限价 FOK 买入 0.25 可以一次确定两笔成交；若 C 失败，不能留下只成交 S1 的结果，更不能降级成 IOC。是否全量成交属于业务语义，不是故障时可牺牲的优化项。

## 第 5 层：市价并不意味着可以不确定最大资金风险

**面试官：** FOK 的预检需要价格范围。若客户要求市价买入 0.25 BTC，不再给限价，账户 A 又该预留多少？

**面试者：** 这是另一个改变价格前提的比较，不承接上一笔 FOK，也不能说基线支持。不能用行情最新价乘数量冒充资金上界，因为轮到它执行时盘口可能已变。扩展必须明确价格保护或最大花费预算，以及流动性不足时允许部分成交还是要求全量，市价本身不自动回答这些问题。若选择数量加最高保护价，可按保护价乘数量预留；若选择最大花费预算，撮合就必须按预算限制可执行量，绝不穿透预留。卖出侧仍可预留固定 BTC，但需要最低价格或滑点保护规则。预算和保护参数都进入载荷绑定，未用部分依据 C 的确定结果由 D 返还。无价格上界、无预算又保证任意价格全量成交，在有限余额下无法成立，当前接口应明确拒绝这种未定义能力。

## 第 6 层：改单不能把两条命令包装成一次原子操作

**面试官：** 你要求价格和预算绑定意图。用户下单后想提高价格，能否直接更新原订单字段，或者先撤旧再下新就叫改单？

**面试者：** 基线没有原地改单，只能比较显式撤旧建新：对旧订单提交 Cancel，等 C 确认关闭并取得最终累计成交量后，再用新意图提交新 Place。两条命令之间存在真实窗口，旧单可能在撤单前继续成交，撤单成功后新单也可能因为资金不足或规则校验失败而未建立，不能对外承诺无缝原子替换。若用户要求总买入仍为 0.25，旧 B2 最终已成交 0.10，新单数量应据此为 0.15，而不是默认再买 0.25；若用户确实要追加，那是另一种显式语义。即使 C 已关闭旧单，D 未释放前新单也不能凭预计退款占资，可以等待旧 D 完成或用足够的独立可用余额预留。原子改单要另有协议，当前不能声称具备。

## 第 7 层：原请求键不是修改原订单的入口

**面试官：** 撤旧建新多了一个身份。客户端为了重试方便，保留旧 clientOrderId，只把价格或数量改掉，服务端覆盖原意图可以吗？

**面试者：** 不可以，旧请求键对应的是已经绑定载荷的业务，不是指向一张可随意编辑记录的名字。Place 的同键同载荷返回原意图与当前进度；改价格、数量、有效期或保护预算都属于异载荷，必须返回冲突，不能偷偷改原预留和撮合资格。显式撤旧建新使用独立 Cancel 请求键和新的 Place 键，并可保存关联关系方便查询；这种关联不提供原子性。若未来增加独立 Amend 命令，也应有自己的请求身份，绑定目标订单、预期版本和规范化修改内容，由权威顺序判断是否还能修改。超时后继续重试同一修改意图，而不是生成多次修改；旧订单终态也不能成为复用旧 Place 键的理由，否则迟到重试会被解释成新的业务。

## 第 8 层：优先级优惠必须与数量、资产规则一起定义

**面试官：** 新身份保证了请求语义，但用户认为“只减数量”不该丢掉排队位置。未来支持原地改单，怎样制定规则才不被利用？

**面试者：** 必须把它声明为新增能力，基线仍不支持原地修改。比较中可以规定同价减量保留原优先级，提价、改价或增量重新获得权威优先级，但这是明确的产品规则，不是行业自动成立的事实。减量也不能把目标总量设成低于裁决时累计成交量，必须结合当前版本计算实际可减剩余量；增量或提高买价需要新增资产覆盖。不能先改执行资格再异步补预留，也不能刚减量就在账户侧直接释放，因为先前成交可能未结转。若无法在现有资格绑定、版本和四边界内定义安全调整协议，就继续采用撤旧建新，让新单在 A 足额预留、在权威接纳时重新排队。所谓保持位置的便利，不能允许先用小单占位、随后无条件增量插队，更不能以优惠优先级绕开资金约束。

## 收束：每种订单能力都是一组可执行承诺

- **讲透的机制：** GTC 定义剩余量存续；IOC 允许部分执行后失效；FOK 在受保护状态中计划，并由 C 保证全量或零成交；市价需要明确预算与保护；改单必须同时定义身份、数量、优先级和预留。
- **易错边界：** IOC、FOK 不等于市价；公开深度快照不提供 FOK 原子性；单线程不替代 C 的故障原子性；撤旧建新不默认原子；同键异载荷不是更新；执行关闭不等于退款已可复用。以上扩展均非基线已实现能力。
- **反例与预期：** 在总览初始盘口手工比较限价 60,000、数量 0.25 的 FOK：只能执行 0.10，故 C 应记录零成交的失败结果，S1 的 0.10 完整保留，D 再释放 15,000。若实现先吃掉 S1 再发现不足，并试图撤掉剩余量，它实际执行的是允许部分成交的语义，不能称为 FOK。这是规则验证的预期，不是新建或已运行的工程测试。
