# 大问题 4：订单状态机由谁维护，怎样避免非法状态和状态回退？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文不靠背几个状态单词判断订单是否正确，而是同时核对谁有权裁决、数量去了哪里、变化在哪个提交点成立。场景仍是每交易对有效单写者处理已提交命令，限价 GTC 不因客户端等待超时而过期。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 状态所有权 | 一个事实只能由指定业务域正式裁决。 | 撮合决定执行，接入记录提交，账户记录结转，不抢写同一终态。 |
| NEW / PARTIALLY_FILLED | 已接纳且尚未成交 / 已接纳且只成交一部分。 | 都还有可执行剩余量，不是收到请求就能写 NEW。 |
| FILLED / CANCELED | 全部成交 / 剩余执行资格已取消。 | CANCELED 可以保留历史成交，不能重新回到订单簿。 |
| 四个数量 | 原始量、累计成交、剩余、撤销量。 | 原始量＝后三者之和；已成交和已撤销量不能倒减。 |
| REJECTED 与命令拒绝 | 未接纳意图的结果，与某条操作失败是不同对象。 | 全成后撤单失败，订单仍是 FILLED，不改为 REJECTED。 |
| 临时变更集 | 先把候选变化算在未发布的草稿中。 | 提交成功前，不能让后续命令或账户使用半成品。 |
| ResultBatch / AppliedSeq | 完整结果包 / 已正式裁决到的输入位置。 | 两者一起原子提交，单 goroutine 不能代替持久原子性。 |
| epoch 与 fencing | 写入任期，以及存储端拒绝旧任期写入的围栏。 | 两台各自单线程，仍可能双写，必须在权威存储挡住。 |
| prioritySeq | 首次合法接纳时确定的排队资格。 | 重复 Place 不刷新；部分成交的余量通常保留原优先级。 |
| orderVersion | 同一订单每次权威变化的递增版本。 | 不是命令号，也不直接决定同价队列顺序。 |
| after-image 与增量 | 一个给变化后的完整状态，一个只给本次变化。 | 完整新快照可防旧覆盖；增量缺失不能跳过累加。 |
| 展示去旧与账务连续 | 页面可拒绝旧快照，资金却仍须履行每笔历史义务。 | 不能为了保留最新终态而丢掉先前成交支出。 |
| GTC 与提交超时 | GTC 挂单持续有效，提交超时只是本次等待没结论。 | 定时器不能直接把 NEW 改成 CANCELED 或解冻。 |
| 恢复一致性 | 重建的不只状态标签，还包括数量、版本、优先级和处理记忆。 | 已提交结果原样应用，确认无结果的尾部才继续执行。 |

## 把整篇文章压缩成一个故事

甲提交 B2，买 0.25 BTC、限价 60,000，先成交 0.10，再撤剩余 0.15。撮合给出的最终数量是原量 0.25＝成交 0.10＋剩余 0＋撤销 0.15，状态 CANCELED。这个词不是“什么都没发生”，更不能把之前买到的 0.10 BTC 抹掉。若另一条独立订单已全部成交，后到撤单只能报告无余量，不可把 FILLED 改成 REJECTED。

每次变化由本交易对有效单写者按已提交输入计算，先形成临时变更集，再把全部订单变化和 AppliedSeq 共同提交。一个 goroutine 只防本进程交错，挡不住崩溃和旧主；存储必须检验任期，提交未知时先查明，不向后执行。命令位置表示处理顺序，订单版本表示该单更新次数，首次接纳优先级则决定同价排队，重试不能把它们混成一个编号。

甲先收到新版 CANCELED，后收到旧版 PARTIALLY_FILLED。若两条都是完整状态快照，页面可按版本拒绝旧覆盖，同版本内容冲突还应告警；若是增量，就得补齐缺口，不能直接丢弃。账户更不能套用页面“只保最新”的办法：早先 0.10 的成交仍需支付 6,000 USDT，否则用户保有 BTC 却没付钱。

订单挂久了，定时器也无权凭本地时间把 GTC 变成已撤；提交不确定应通过授权关闭意图收敛。恢复时同样要保留原成交身份、数量、队列、去重和关闭标记，不能重撮合已有结果。资金侧还要查原预留与成交归属，不能用另一张订单恰好相同的金额补齐总数，就认定该单已经完成履约。验收需要比较完整已提交状态与不变量，而非重启后看见同一个状态词就算正确；本文没有执行真实故障实验。

**流程位置与核心机制：**聚焦订单执行状态的权威来源、数量守恒、版本和合法迁移。撤单时序见母题 06，预留与账务跨域一致性见母题 08，投影版本传播见母题 11。

**必要前提：**每交易对单写者处理已提交命令，只有完整结果与 AppliedSeq 提交后执行状态才生效。接入流程状态和账户结转进度不挤进同一个订单枚举。

## 第 1 层：状态机先从权威和数量讲起

**面试官：**订单状态机由谁维护，怎样避免非法状态和状态回退？

**面试者：**执行状态由撮合域维护，接入只记录请求进度，账户只记录资金处理进度。在本模型中，已接纳订单有 NEW、PARTIALLY_FILLED、FILLED 和 CANCELED 等执行状态，但我不会只凭枚举转移保证正确性，还要维护 originalQty、cumFilledQty、leavesQty 和 canceledQty，满足原量等于后三者之和。

成交只增加累计成交、减少剩余量；撤单把实际剩余量转成撤销量，不回退历史成交。FILLED 和 CANCELED 都不能重新进入订单簿。每次变化有递增订单版本，随完整结果批次提交。这样状态标签、数量和执行位置彼此可核对，不能出现数据库写着 CANCELED，订单簿却仍保留可匹配数量的两个事实。

## 第 2 层：部分成交后撤单为什么不是“完全取消”

**面试官：**你说取消不回退历史成交。B2 买 0.25 BTC，成交 0.10 后撤单，四个数量与状态分别是什么？

**面试者：**原量是 0.25，累计成交 0.10，撤销量 0.15，剩余零，执行状态为 CANCELED。这里 CANCELED 表示剩余执行资格结束，不表示从未成交，也不表示把 0.10 BTC 卖回去。数量守恒仍然是 0.25 等于 0.10 加零加 0.15。

如果系统只保存 status 和 leavesQty，就很容易在终态里丢掉“到底全成还是部分成交后取消”的区别。账务和用户回报还需要成交明细、累计成交金额及来源位置。相反，若 0.25 全部成交，状态应是 FILLED，撤销量为零；此后撤单请求可以得到“已全成、没有剩余”的命令结果，却不能把订单改成 CANCELED 来迎合用户最后一次操作。

## 第 3 层：拒绝订单和拒绝撤单是不是一类状态

**面试官：**如果全成后撤单被拒绝，你会把订单状态写成 REJECTED 吗？首次 Place 没通过资格校验又怎样？

**面试者：**不会。REJECTED 作为未接纳订单的业务结果，和一条 Cancel 命令被拒绝是不同对象。全成后的撤单失败，只更新该撤单请求的处理结果，目标订单仍是 FILLED；不能拿命令结果覆盖订单执行状态。

首次 Place 被明确拒绝时，本专题保留请求意图、原因和结果位置，但不创建一个声称曾经入簿的活跃订单。这样不需要对未接纳对象强行套用“成交量加剩余量加撤销量”的已接纳数量公式。若 API 需要统一返回 orderId，可以提前分配身份并返回 REJECTED 结果，但它仍不是订单簿中的订单。这也让接入参数拒绝、撮合业务拒绝和撤单命令拒绝各自有明确归属。

## 第 4 层：单写者如何把合法迁移落实到实现

**面试官：**你把状态都交给撮合域，但 Go 里开一个 goroutine 就足够保证状态机正确了吗？

**面试者：**不够。单写 goroutine 只限制进程内并发，还必须限制它读取哪些输入、提交哪些输出，以及崩溃后如何接续。它只处理已经提交的命令，按 commandSeq 取当前订单、验证前置条件，在临时变更集中计算数量变化、订单版本、订单簿节点变化和相关结果。

变更不能一算出来就向外生效。完整 ResultBatch 和新 AppliedSeq 原子提交成功后，才推进权威状态副本并发布；若为了性能先改内存，也要有可丢弃或可回滚的暂存隔离，提交未知时不能继续执行下一条。主备还需要有效 epoch 和存储侧 fencing，防止两个进程各自“单写”却同时提交。合法迁移来自业务规则与可靠提交边界的组合，不来自 goroutine 这个名称。

## 第 5 层：版本与序号不同，谁决定同价优先级

**面试官：**你已经有 commandSeq、AppliedSeq 和订单 version，还需要 prioritySeq 吗？重复 Place 会不会让订单排到队尾？

**面试者：**这些字段解决的问题不同。commandSeq 是交易对输入位置，AppliedSeq 是已提交处理到的位置，orderVersion 是某个订单每次权威变更的版本，prioritySeq 记录首次合法接纳的优先级。一个命令可同时改变多个订单，而一笔订单也会因后续对手单多次变更，所以不能拿它们互相替代。

重复 Place 不创建新订单，不增加新的接纳优先级，也不因为网络重试重新排队。它可以在后来输入位置产生“原业务已处理”的结果，但不把该位置写为原订单 prioritySeq。订单发生部分成交时通常保留剩余量的原优先级；若未来支持改单，何时保留或丧失优先级必须作为新规则明确制定，不能仅凭 version 变大就自动重排。

## 第 6 层：旧事件晚到怎样避免状态回退

**面试官：**撮合内部顺序明确了，但投影先收到 B2 的 CANCELED，再收到旧的 PARTIALLY_FILLED。版本号怎样发挥作用？

**面试者：**先明确事件携带的是完整状态快照还是增量。若是某订单完整 after-image，投影可以用 orderVersion 条件更新，只接受比当前新的版本，旧版本不覆盖终态；同版本不同内容应告警而非任选一份。若是数量增量，则不能跳过缺口直接累加，必须按序补齐或用可信快照重建，否则中间成交可能被吞掉。

这只是展示侧规则，不改变撮合权威。账户消费者也不能套用“只取最新版本”跳过历史成交，因为每笔资金动作都必须被处理。订单版本帮助防回退，但回报流还有自己的游标用于发现跨事件缺口；账户另有消费水位。一个乐观更新条件不能同时代替这三类连续性保证。

## 第 7 层：本地超时能不能触发状态机终态

**面试官：**既然客户端不能直接改状态，如果订单挂单很久，定时任务能否把数据库里的 NEW 改为 CANCELED？

**面试者：**不能由查询库或账户定时任务直接改执行状态。本基线是 GTC，不存在默认挂单到期；任务擅自取消已经改变了产品规则。即使未来增加有效期，过期也必须成为有明确规则依据的权威裁决，与成交竞争按同一顺序处理，不能只在页面打一个过期标签就解冻。

提交过程超时则是另一回事，它表示原 Place 结果未知，并不等于订单挂单过期。要放弃原意图，必须经过 AbortIntent 的有序关闭，阻断迟到接纳并保留可能已经产生的成交义务。定时器可以触发一个有权限的关闭请求或告警，不能成为第二个状态所有者。否则某个节点时钟先走一步，就会让同一订单在不同模块出现不同终态。

## 第 8 层：怎样验收状态机与恢复后的状态相同

**面试官：**终态规则、版本和超时都明确了。你怎样检查新增功能或崩溃恢复没有破坏这套状态机？

**面试者：**我会把命令序列和数量不变量一起检查。生成 Place、对手单成交、Cancel、重复 Place、重复 Cancel 和 AbortIntent 的不同合法顺序，逐步验证非负、数量守恒、终态不可恢复执行、首次接纳优先级不被重复请求刷新。命令拒绝不能改坏目标订单，未接纳关闭不能伪造已入簿历史。

再把相同的已提交前缀恢复到新进程，比较订单数量、订单簿资格、版本、优先级、业务去重和关闭标记，而不只比较 status。B2 在成交后取消，恢复后即使显示 CANCELED，也必须保留 0.10 的累计成交和原成交身份。若结果已经提交，不能重新跑一遍当时撮合来生成新成交；有已提交输入但没有结果的尾部，才按固定规则继续执行。

## 本题收束

- **讲透的机制：**执行状态、请求结果和结转进度属于不同对象；订单状态由数量、合法迁移和权威提交共同决定。
- **最容易答错：**全成后撤单失败就把订单改为 REJECTED；把 CANCEL_PENDING 当成已阻止成交；靠最后到达的消息覆盖状态。
- **检验反例：**B2 的终态版本先到，旧部分成交版本后到。展示不能回退，但账务仍必须处理这笔历史成交；若系统为了“保留最新”而丢掉 6,000 USDT 的支出，就误把展示更新规则当成资金消费规则。
