# 大问题 11：查询和私有回报怎样处理滞后、重复、乱序与重连？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文解释“页面怎样诚实而可恢复地展示交易”，不把回报连接变成第二个裁决者。沿用零费用现货限价 GTC；执行已确定、账务已完成与查询已追上分别报告，查不到不能直接补单或退款。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 查询投影 | 从正式业务事实整理出的读取副本。 | 可暂时落后，无权决定成交、撤单或释放预留。 |
| 意图、执行、结转进度 | 分别回答要求是否保存、怎样裁决、资产是否完成变化。 | 有意图而没活跃订单，或订单终态而账务待处理，均可能正常。 |
| orderVersion | 某个订单每次权威变化的递增版本。 | 新完整状态不能被旧版本覆盖，同版本异内容需核对。 |
| 后镜像与增量 | 变化后的完整状态，与只说明本次变化的消息。 | 后镜像可去旧；增量跳版本须补齐，不能直接累加。 |
| tradeId 与成交明细 | 原成交的稳定身份及历史记录。 | 状态旧不等于成交无效，明细仍按成交身份去重保留。 |
| streamCursor | 本账户私有持久流中的接续位置。 | 带流代际，连续确认后才可推进，不能拿最大收到号当完成。 |
| sourceResultSeq | 某市场正式结果的来源位置。 | 过滤他人事件会自然跳号，不等于私有回报丢失。 |
| 来源覆盖与账务水位 | 分别证明投影消费到哪、账户履约到哪。 | 私有游标更新不代表钱已到账，不同市场位置不能直接比大小。 |
| 投影本地事务 | 投影更新、事件去重、私有事件和来源进度一起提交。 | 防只前进水位却没留下回报，不是全链路大事务。 |
| 快照覆盖游标 C | 精确说明这份页面底稿已经包含到哪个私有位置。 | 替换本地视图后只接大于 C 的后缀，不能读完实时列表就跳到最新。 |
| 保留保护与分页令牌 | 在有限时间保住交接后缀，让各页属于同一切面。 | 过期要明确重取，不静默漏掉快照与订阅之间的变化。 |
| 账户隔离与重新鉴权 | 续传、分页、历史查询都得重新确认当前权限。 | 游标签名防篡改，不代替授权；服务端先过滤再入连接。 |
| 慢消费者与有界缓冲 | 客户端不读时，连接只能占有限资源。 | 超限断开并要求续传或重建，不阻塞撮合与账务。 |
| 状态快照与完整历史 | 快照恢复当前可见状态，不等于重放所有旧通知。 | 需要全部成交历史时，另走授权历史查询。 |

## 把整篇文章压缩成一个故事

甲的 B2 从 20,000 USDT 开始，预留 15,000，成交 0.10 BTC 后撤余下 0.15。页面先收到版本 5 的 CANCELED，后来收到版本 4 的部分成交。新版完整状态不应被覆盖，但旧回报里的成交明细仍按 tradeId 保留一次；若消息只给数量增量，则不能跳过缺失版本硬加。展示的“最新状态”与“完整历史”不是同一道题。

回报来源从市场结果 100 跳到 105，可能只是中间都属于别人；本账户连续私有游标从 20 跳到 22，却要等 21 补齐后才能确认到 22。服务端把投影、事件追加、去重和来源覆盖共同提交，客户端只保存连续已应用位置。订单版本管一张单，私有游标管这个流，账务水位管钱，不能用一个大号同时证明三件事。

甲断线太久，系统用同一投影库切面给出订单、账户独立水位与覆盖游标 C，再接严格晚于 C 的增量；分页都绑同一令牌，保留窗口过期就明确重建，不悄悄从最新开始。重连还须鉴权，游标不能变成访问别人的通行证。连接太慢可以限量后断开，不能让无限缓冲拖住正式结果消费，也不能把写进 socket 当用户已应用。

这份快照即使显示已撤，D 若尚未覆盖，甲仍可见可用 5,000、预留 15,000 和结转 PENDING。系统应解释落后，先结成交的 6,000 与 0.10 BTC，再退 9,000，最终可用 14,000；不能让页面自己重算退款。查不到订单也不证明意图不存在。资金操作仍回到权威账户事务校验，不能用陈旧页面上的可用数再次批准占款。本文给的是可见性协议和手工预期，没有运行断线或权限工程测试。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖权威结果到用户可见性的最后一段，重点是查询投影、订单版本、私有流游标、缺口恢复与快照交接；不重新展开撮合裁决和账务事务。

沿用总览的现货限价 GTC、零手续费与 B2 独立变体。四个提交边界仍是 A 意图及预留事务、B 命令多数派持久提交、C 完整结果与 AppliedSeq 原子提交、D 账务事务。日志具有多数派持久化和 epoch 隔离；私有回报只能转述已提交事实，不能因连接成功而提高业务承诺。

## 第 1 层：查得到与查不到，分别能说明什么

**面试官：** 查询和私有回报怎样处理滞后、重复、乱序与重连？先说订单查询是否权威，用户下单后查不到应该怎么办？

**面试者：** 在这个模型中，查询是投影，不是决定成交、撤单和退款的地方。账户域拥有意图与预留，撮合域拥有执行事实，查询服务只把这些事实组织成可读视图。因此接口要分别返回意图提交进度、执行状态和结转进度，不能用一个“成功”掩盖差异。A 已提交而 B 尚未确定时，可以查到意图处理中，却没有活跃订单；C 已提交而查询尚未追上时，也可能暂时查不到执行记录。此时客户端用原请求身份查询意图或重试，服务端返回尚不可确认及投影水位，而不是确认下单失败。尤其不能据此重新生成订单或退款：释放资产必须依据权威关闭结果和有序账务处理，不依据页面存在与否。查询可见性晚于业务提交，是允许的暂态，但必须明确暴露这种暂态。

## 第 2 层：用订单版本阻止旧消息覆盖新状态

**面试官：** 你说查询会落后，那私有回报先收到撤单终态，随后又收到旧的部分成交，怎样避免页面状态倒退？

**面试者：** 我会让每次权威订单变化带上单调增加的 orderVersion，并在结果提交时固定下来，不由网关按到达时间生成。事件同时携带订单身份、稳定事件身份和变更后的完整数量状态。投影及客户端对同一订单只接受更高版本，相同版本相同内容视为重复；相同版本内容冲突则告警并核对来源。较低版本不能把已撤销改回部分成交，但其中成交明细仍须按 tradeId 独立去重保存，不能因为订单状态旧就丢掉交易历史。若传输的是数量增量而非完整后镜像，版本跳跃时不能直接相加，必须补齐或拉取快照。因此我优先让状态回报携带后镜像，成交事实单独记录；版本解决单订单覆盖顺序，不承诺整个账户没有漏消息。

## 第 3 层：订单版本、回报游标和资金水位不能互换

**面试官：** 你说 orderVersion 不能证明账户没有漏消息，那加一个全局序号是否就能同时解决重连和资金完成判断？

**面试者：** 不能把不同坐标揉成一个数。orderVersion 只比较同一订单；streamCursor 是账户私有持久流内的投递位置，可由流代际与序号组成，用于断线续传。同一结果产生多条事件，还需要事件索引区分身份。来源位置则是 symbol 与 sourceResultSeq 的组合，不同交易对之间不能比较大小；账户私有流过滤了其他账户事件，来源序号自然可能跳跃。账户域还要独立报告每交易对的账务已应用水位，账户查询副本另有自身覆盖进度，不能拿回报游标代替。只有账务已覆盖目标订单终态及此前结果，且返回的账户视图也覆盖相关账务变化，才可声称资金收尾可见。订单执行回报领先账户结转完全合法，游标很新并不意味着钱已到账。

## 第 4 层：至少一次交付中的重复、乱序与真缺口

**面试官：** 你区分了私有流位置和来源位置。若回报来源序号从 100 跳到 105，私有游标又从 20 跳到 22，各自怎样处理？

**面试者：** 来源跳号未必丢失，因为中间结果可能与该账户无关；是否完整应看投影消费端对该交易对的连续覆盖水位。私有流则约定已提交追加位置连续，收到 22 而尚无 21，就先缓存有限后缀，从最后连续确认的 20 补发，不能直接把确认点推进到 22。投影消费完整结果批次，在一个本地事务内提交事件去重、订单投影变化、私有事件追加与来源覆盖水位；崩溃后至少一次重放，不会只推进水位却漏掉通知。重复投递不能生成新业务效果，发送乱序也不能改变持久流顺序。若缺口无法补回，必须明确要求重建视图；不能静默跳过，再把后续心跳或最新订单版本当作缺口已经修复。

## 第 5 层：快照与增量必须在同一覆盖游标交接

**面试官：** 你要求缺口补不回就重建。先查全部订单，再订阅增量，这两步之间刚好发生撤单，怎样保证既不漏也不重复覆盖？

**面试者：** 快照必须返回覆盖游标 C，不能只返回一组订单。我会在同一可见性数据库的一致性读事务里取得订单集合、账户投影及其独立水位和私有流尾部 C；所有相关投影修改与私有事件追加也必须同事务提交。这样快照精确覆盖到 C，客户端完整替换本地视图，再按顺序应用严格晚于 C 的增量，旧版本仍按规则去重。这只是投影库的原子切面，不代表撮合和账务在现实中同时完成。服务端要先为该切面建立有期限的保留保护，或保证有效回放窗口，再读快照并交接续传；若期间游标已过期，就明确失败重取，不能从当前最新位置悄悄开始。分页快照还必须绑定同一快照令牌，逐页读取变化中的实时列表不具有这个保证。

## 第 6 层：能续传，不代表有权读取这个账户

**面试官：** 你让客户端携带快照令牌和覆盖游标续传。如果它拿别人的游标重连，或者原登录凭据已经撤销，怎样处理？

**面试者：** 重连是新的受保护请求，必须重新校验身份、账户权限和凭据有效性，不能把旧连接曾经鉴权当作永久授权。账户从服务端认证上下文确定，不信任请求里的 accountId；游标和快照令牌绑定账户、流代际、有效期，签名只能防篡改，不能代替当前授权。补发、历史查询、快照分页和实时分发都使用同一账户隔离规则，在进入连接缓冲之前完成过滤，不能先广播再让客户端筛选。凭据撤销或权限变化后要停止后续发送，缓存也按账户和权限范围隔离。其他账户游标应被拒绝，流重建导致代际变化时要求重新同步；错误响应不能泄露目标账户是否存在或其交易内容。这样权限边界不会因“只是重连补消息”而被绕开。

## 第 7 层：慢消费者与保留过期不能变成静默丢失

**面试官：** 你还要求保留回放窗口。若某个已授权客户端一直不读，是否必须无限保存它的队列，避免破坏续传承诺？

**面试者：** 不需要，也不能让一个连接拖垮整个账户流。每连接缓冲按条数、字节和最长滞后时间设上限，发送线程与权威结果消费解耦；超过上限就中止该连接并提示需要续传或重建，不无限增加 goroutine，也不阻塞撮合与账务。客户端只保存已经连续应用的游标，心跳、写入套接字成功或收到最大序号，都不等于它已完成应用。私有增量流有明确保留期，快照保留保护同样有期限；旧游标超期就返回明确的游标过期，由新快照接管。若用户还需要完整历史成交，应走独立的授权历史查询，不能假称状态快照恢复了全部历史通知。丢弃连接内副本可以接受，静默丢事件后仍宣称连续则不可以。

## 第 8 层：恢复后执行终态与资金 PENDING 怎样一起展示

**面试官：** 你说新快照能恢复状态，却不承诺资金已完成。B2 快照显示已撤销，账户还显示原预留，客户端应怎样解释和验证？

**面试者：** B2 初始可用两万，预留一万五，只成交零点一 BTC 后撤剩余零点一五。若 C 已提交关闭结果而 D 尚未覆盖，订单可显示累计成交零点一、撤销零点一五、剩余零，同时结转为 PENDING；账户仍可能可用五千、预留一万五，这不是马上纠正余额的理由。账务先按序消耗六千并入账零点一 BTC，再依据关闭结果退九千，最终可用一万四、预留零。展示应带关闭结果的来源位置、账务覆盖水位与账户视图覆盖进度，落后就继续等待或受限查询，而不是根据订单终态本地计算可用余额。反过来，未接纳意图可能从始至终没有活跃订单记录，仍须查明关闭资格及账务处理；“查不到订单”始终不能变成自动退款条件。

## 收束：把可见性做成可恢复协议

- **讲透的机制：** 订单版本防单订单回退，私有游标保证账户流续传，来源水位定位投影覆盖，账务水位解释资金完成；快照用覆盖游标完成原子交接。
- **易错边界：** 查询不裁决业务；至少一次不等于只发一次；来源跳号不等于私有流缺口；执行终态不等于资金终态；快照不是全历史成交补发。

**反例验证及预期：** 以下仅为手工推演，不声称已执行工程测试。

| 构造的反例 | 正确的预期结果 |
|---|---|
| 先收到订单版本 5 的撤单后镜像，再收到版本 4 的部分成交及重复成交明细 | 状态不回退；明细按成交身份只保留一次，不因旧状态丢成交 |
| 快照切面 C 之后发生撤单，但订阅稍后才建立 | 撤单必在大于 C 的续传后缀；若后缀过期则明确重建，不能静默漏单 |
| B2 已撤销，账务停在成交之前 | 显示执行终态、结转 PENDING；保留未结转义务，不能全退一万五 |
| A 已提交，但订单查询一直没有记录 | 仍按原意图恢复或有序关闭；不得因未接纳或投影缺失自行释放预留 |
