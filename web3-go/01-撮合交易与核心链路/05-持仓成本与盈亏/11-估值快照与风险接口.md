# 大问题 11：查询与风控怎样获得可解释且足够新鲜的持仓估值？

## 先看懂：关键词大白话解释

本文适用范围：ETH-USDC-PERP 线性 USDC 永续，ETH 数量、USDC/ETH 价格、乘数 1，单向逐仓、加权平均、费用独立，仓位与账本同库提交。估值是带证据的派生读数，不是现金到账或完整强平算法。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 一致经济快照 | 数量、成本、现金都来自同一可解释提交边界 | 仓位和账本计数器可不同，但不能乱拼版本 |
| 价格身份 | 说明用了哪条、哪种、哪个来源的报价 | Mark 不能由 last trade 偷换名称顶替 |
| 源时间与接收时间 | 报价生成时刻和系统收到时刻 | 旧价刚到不等于新价，重发不刷新源时间 |
| computed_at | 这次估值实际运行的时刻 | 不证明输入经济事实或报价同样新鲜 |
| source_epoch | 报价来源重启后的代际标识 | 防止序号从头开始被误读为旧数据或更新数据 |
| stale | 输入已超出允许新鲜度窗口 | 可保留最后读数但不能继续称实时权益 |
| 备用价格策略 | 经批准的异常时价格选择规则 | 记录原源、选中源、原因和版本，不临时换价 |
| 风险许可 | 对某用途和额度有条件的允许证据 | 绑定经济与价格条件，不是可永久复用的布尔值 |
| 检查—执行窗口 | 允许之后、真正扣款前状态还能变化 | 提交处重验版本或消费有效持久预留 |
| 已观察成交前沿 | 风险已知道业务发生到哪里 | 已结转表是权威的，也可能尚未覆盖所有成交义务 |
| 完整快照与增量 | 整份状态替换和逐笔变更的不同载荷 | 完整快照可按版本替换，增量缺口必须补齐 |
| 版本化估值缓存键 | 用经济版本、价格身份和规则共同标识缓存 | 只用账户 ID 或短 TTL 不能证明组合正确 |
| 读己之写令牌 | 查询至少追到刚完成的经济序号 | 带风险单元身份，等待有界且不能伪造版本 |
| 决策视角与重算视角 | 当时真实用的依据和事后修正后的分析 | 新报价重算不覆盖旧证据，更不改历史已实现数 |

## 把整篇文章压缩成一个故事

小林刚完成 ETH 永续减仓，权威单元已是数量一点八、成本三千七百八十、毛盈利四百八十、累计费用九点三、现金一千四百七十点七。页面投影还停在前一笔，他刷新后仍看到三 ETH。接口不能把旧数量贴上新版本，也不能取新数量配旧成本六千三；它应返回经济位置，收到“至少序号三”的查询时有界等待、受控回源或明确显示追赶中。

投影赶上后，系统组合来源明确的两千四 Mark，得到未实现盈利五百四十、权益二千零十点七。可报价刚刚接收不代表源头刚生成，重复转发旧数据也不能刷新源时间。若 Mark 已陈旧，页面可以保留带 stale 标记的最后估值，风险却须按策略限制行为，不能偷偷改用最新成交价。当备用策略选择两千三时，浮盈三百六十、权益一千八百三十点七，必须说明换了哪份价格证据。

小林接着申请划出一百 USDC。即使先前估值有效、风险一度允许，也不能承诺立刻到账：允许之后可能发生亏损成交或价格失效，最终提交须重验经济版本、价格条件、订单预留与在途义务，或消费仍有效的额度预留。已经确定但尚未送达持仓的成交也要有人继续约束敞口，不能因为数据库里暂时查不到就当它没发生，更不能为了完成划款丢掉亏损成交。

查询无需每次都锁交易写路径，可缓存不可变经济快照和合格报价；但增量消息有缺口要补，不能像完整快照那样任意跳版本。数天后若价格源修正历史，小林投诉时要同时看到当时真实决策证据和事后重算结果，而不是被覆盖后的单一数字。这样经济进度、价格年龄、展示与执行许可各自清楚，五百四十浮盈始终只是估值，不会被误说成已入账或可提现现金。

[返回专题总览](README.md)

**流程位置与核心机制：** 位于经济结转之后，连接仓位、账本、Mark Price、查询与风险执行。独立重点是怎样构造一个有证据的估值快照，并防止“读到一个好看的权益”被误用为资金或订单的执行资格；不在本题推导完整强平算法。

**必要前提：** 沿用[共同基线](README.md#11-讨论基线)：线性 USDC 永续、单向净仓、逐仓、加权平均成本，手续费单列。持仓与账本在同一数据库事务提交。F3 后 `q=1.8 ETH、C=3,780 USDC、B=1,470.7 USDC、累计毛R=480、费用=9.3`；M1 的 Mark 为 2,400，得到 `U=540、E=2,010.7`。这些数字的结算余数为 0。

本题 8 层沿“经济快照→价格证据→陈旧处置→风险执行→在途敞口→缓存容量→历史解释”推进，不把查询实时性与资金安全混为一谈。

## 第 1 层：你返回的盈亏究竟对应哪一组状态？

**面试官：** 用户查询持仓时，你会返回哪些字段？只把当前数量、余额和最新 Mark 拿来相乘，能不能得到一份可信的未实现盈亏和权益？

**面试者：** 不能只说“拿最新值”，因为几个来源的“最新”不一定属于同一个经济时点。我会先取得同一提交边界下的仓位与账本快照，再与一个明确身份、有效质量的 Mark 组合，返回带版本的估值，而不是一个没有依据的实时数字。

本例经济快照至少包含 `risk_unit_id、account_seq、position_version、ledger_version、qty、entry_cost、cash、settlement_remainder`。其中仓位版本与账本版本可以是不同计数器，不能因为都叫 version 就假设数值相等；它们必须关联同一次可解释的经济快照或公共提交标识。

价格证据至少包括市场、价格类型、价格值、来源、源版本、源时间、接收时间与质量状态。估值结果再记录使用的经济版本、价格身份和计算时间。`computed_at` 表示什么时候执行了计算，不证明经济数据和价格都在该时刻生成。

以 F3 后的经济快照和 M1 计算，`U=1.8×2,400−3,780=540`，`E=1,470.7+540=2,010.7`。如果数量取 F3 的 1.8、成本却取 F2 的 6,300，算出的亏损不是“稍旧”，而是一份不对应任何合法仓位的拼接结果。

如果直接读权威数据库，可以在一个一致读事务中取得相关状态；如果读投影，则要求投影按经济事件原子更新相互依赖的字段，并返回已应用位置。这里只保证经济状态内部一致，价格流仍然独立；应明确表达“经济版本 v、价格 M1 下的估值”，不假装两个流有一个天然的全局时钟。

## 第 2 层：既然价格流独立，你怎样证明这个 Mark 真能用于估值？

**面试官：** 你说价格也要带身份。假如系统刚刚收到一条价格，它的接收时间很新，但其实来源已停更；或者它是最新成交价而不是 Mark，你怎样避免算出貌似实时的风险结果？

**面试者：** 我会把价格类型、来源身份和新鲜度分别校验。接收得晚不等于生成得新，最新成交价也不等于 Mark Price。估值接口必须按市场规则请求规定的价格类型，不能发现 Mark 不可用就悄悄用最后成交价顶上。

价格对象可以记录 `market、price_type、source_id、source_epoch、source_seq、source_time、received_at、value、scale、quality`。来源重启后序号可能从头开始，需要 epoch 或其他不重复身份，不能只比较裸序号大小。跨来源的序号不具备可比性，也不能把市场成交 `source_seq` 与报价序号做大小比较。

有效性至少覆盖市场和单位匹配、价格为该产品允许的值、来源可信、来源没有未处理缺口、价格年龄符合策略。时间检查要处理已知时钟误差和明显未来时间；重复接收一条旧价格不能刷新它的源时间。价格的新鲜度阈值由市场和风险规则配置并留版本，不在材料里编造一个通用“3 秒安全值”。

假设 M1 的源时间已经超出允许窗口，即使派发服务现在才把它送来，结果也要标记 stale。反过来，一个新价格若来源版本倒退、类型为 last trade，也不能因为时间新就当成合格 Mark。

验证失败不改写 q、C 或已实现盈亏。它改变的是“能否形成有效估值”和“风险允许哪些行为”，不能把无效价格输入持仓内核，让历史成本随着行情异常变化。

## 第 3 层：价格不合格后，页面与风险要一起停掉吗？

**面试官：** 你拒绝用陈旧 Mark 产生正常估值，那页面还能显示什么？如果为了可用性启用备用价格源，怎么避免历史报表和实时风控使用了不知情的不同口径？

**面试者：** 页面可读性和风险可执行性应分开。页面可以保留最后一次估值，但必须显示价格源时间、估值版本和 stale 状态，不继续标为“实时权益”；风险则按明确的降级规则决定是否暂停新开仓、限制保证金划出，或者使用已批准的备用价格机制。

我不会一概承诺“价格停更仍允许任何减仓”。取消未成交订单通常不需要一个新价格来实现撤销，但新的减仓成交仍需遵守执行保护、Reduce-Only 资格和市场可交易状态。尤其是标记错误的“减仓”可能过零增加敞口，不能只依据客户端的按钮名称放行。

若产品允许备用源，应把它作为有版本的风险策略，而不是代码中的临时异常分支。输出记录 `fallback_policy_version、original_source、selected_source、reason`，并说明备用源生成的是哪一种价格。不能仅把 last trade 字段改名为 Mark，就认为语义没有变化。

主例的有效 M1 是 2,400；若备用结果是 2,300，对同一 F3 快照可得 `U=360、E=1,830.7`。两个结果都必须标注其来源和用途；不允许用一个口径放行保证金划出，却用另一个口径在用户页面解释同一次风险动作，而不保留证据。

恢复正常源后应生成新的估值版本，旧估值保留在风险审计链中。价格修正可以改变历史分析报表的“重算视角”，但不能静默覆盖当时实际决策所用的证据，更不能据此重写已实现交易盈亏。

## 第 4 层：即使估值有效，风险许可在真正执行时还有效吗？

**面试官：** 假设风险模块用合格 M1 和 F3 快照判断可以划出 100 USDC，返回后又发生一笔亏损成交。资金服务拿到刚才的“允许”就扣款，会有什么问题？你如何闭合这个检查与执行之间的窗口？

**面试者：** 这是典型的检查时与执行时状态变化问题。风险结果不能只是一个没有上下文的布尔值；它必须绑定风险单元、用途、金额、经济版本、价格证据、规则版本以及有效条件，执行者在受控提交边界消费它，而不是把旧许可无限期复用。

在本例同数据库提交域里，可以先在风险单元的命令序列中裁决划出资格，锁定对应控制行，读取权威经济状态和订单／在途约束，再根据认可的价格证据计算允许额度。若后续资金动作不能立即完成，则将这次划出占用建立为持久预留，防止同一额度同时被新开仓和另一笔划出消耗。

若风险计算在锁外进行，提交时至少比较它引用的经济版本、相关预留版本和当前状态。版本改变就重新计算或拒绝旧许可，不能“先扣再对账”。价格也会独立变化，所以还要定义执行处检查的价格有效条件、价格策略版本或风险安全边界；只校验仓位版本并不能发现 Mark 已大幅变化。

这不是说必须把整个价格服务锁在数据库事务里，而是将“以哪份价格证据、在什么有效条件下允许哪种动作”写成协议，并在资金提交或风险额度预留时校验。许可若一次性消费，应有稳定许可身份和消费记录；同一划出请求重试不能重复消费额度。

已经确定的亏损成交则是必须结转的义务，不能因为它让刚才的资金计划不成立就丢掉成交。正确做法是在风险资格上约束未来可执行动作，同时如实结转已发生事实；把义务和许可混为一谈会导致有利成交入账、亏损成交卡住的错误。

## 第 5 层：版本检查只看到已结转状态，未到达的成交怎么办？

**面试官：** 你检查了当前经济版本。但撮合已经产生 F3，清算还没把它送到持仓服务；数据库里仍是 F2。此时你读到的确实是权威数据库，为什么仍可能不够安全？

**面试者：** 因为“权威的已结转状态”不等于“所有已发生义务都已经结转”。一笔确定成交在传输或结转途中，也会改变未来风险；如果系统只读仓位表而忽略订单预留和在途义务，读得再强一致也可能基于不完整的敞口做决定。

订单准入时应已对潜在成交建立必要的风险约束。成交确定后，在这份义务被持仓和账本接续之前，不能因为订单状态变为已成交就先释放所有预留。结转事务需要关联订单侧的待结转量／结转效果，明确哪些约束已经由新仓位状态承接，哪些仍对应未成交或未结转部分。

F3 本例恰好减仓盈利，但不能以此假定在途成交总会改善风险。同样的交付延迟发生在亏损平仓或扩大仓位的 F2 时，提前放掉约束就可能导致超额划出。对于部分成交订单，剩余挂单约束也不能跟着一笔结转全部清空。

如果订单域与结转域不共享事务，要以稳定义务身份和确认协议连接：订单侧在拿到可证明的结转结果前保留相应保护，结转侧返回关联的已应用事件和数量；双方可以暂时重复保守占用，但不能出现两边都认为另一边承担风险的空档。不能只靠一个短 TTL 到期释放。

查询投影可以展示“结转到哪个位置”，风险接口还需要知道已观察的成交前沿和未闭合义务。若无法证明输入已经追上某个必要前沿，应限制扩大风险敞口的行为，而不是将“目前查不到下一笔成交”当成“它不存在”。

## 第 6 层：为了覆盖这些状态，查询接口会不会变得很重？

**面试官：** 你要求一致经济快照、价格证据、版本和在途义务。若每次页面刷新都锁权威行、同步请求风险服务，岂不是拖慢交易？查询缓存怎样用，才能既便宜又不冒充权威？

**面试者：** 不需要让每个页面读取都执行风险事务。首先把只读展示和资金／订单执行拆开：展示走版本化读模型，执行走权威资格接口。页面缓存可以滞后，但必须让滞后可见；交易安全不能靠页面恰好很快来保证。

我会缓存不可变的经济快照，再用指定价格版本计算估值，缓存键至少含风险单元、经济版本、价格身份和估值规则版本。不能只用账户 ID 作键，把旧仓位算出的 U 填到新仓位旁边；也不能只设置一个 1 秒 TTL 就声称有一致性。

价格 tick 很密集时，不需要每个 tick 都更新仓位数据库。可以缓存最新合格价格快照、合并只影响展示的中间估值请求，在用户读取或周期刷新时组合；但成交和现金事件不能因为“中间状态没人看”就跳过。估值计算使用只读数据，不能和 owner 的 `big.Int` 可变对象共享别名。

投影更新要区分事件载荷：若是完整经济快照，可以校验版本后使用更新版本替代旧版；若是增量，则不能跳过中间事件，发现缺口要补齐或重新取完整快照。两种消费方式不能共用一个“只要版本更大就覆盖”的模糊实现。

容量指标也要分开观察：结转输入延迟、经济投影延迟、价格年龄、估值耗时、stale 比例和权威回源压力。刷新快并不证明价格新，估值缓存命中率高也不证明风险许可正确。这里给的是测量维度，不给未经验证的吞吐或毫秒承诺。

## 第 7 层：缓存可能落后，怎样满足用户“我刚成交就要看到”的要求？

**面试官：** 你承认页面可以滞后，但用户收到 F3 处理成功后刷新，仍看到 F2，通常会认为系统错误。怎样提供读己之写，同时不让每个查询都变成无界等待？

**面试者：** 成功响应应携带明确的完成阶段和位置令牌。如果返回的是撮合成交成功，令牌表达成交已确定及其来源位置；如果返回账户结转成功，令牌可以表达该风险单元的 `account_seq=3`。前一种令牌不能伪装成后一种确认。

查询接口接受 `min_economic_seq=3`。投影已经到 3 或更后就返回一致快照；尚未追上则在有界时间内等待或返回“经济结果追赶中”，必要时受控地读权威数据库。不能为了消除用户等待而用 F2 的旧状态标成版本 3，更不能无限阻塞把整个查询线程池耗尽。

令牌必须带风险单元身份，不能只传一个裸整数；其他市场的 3 不代表本市场已追上。若期间发生保证金划转，经济流位置推进而仓位版本未变也很正常，所以读取完成条件应使用共同经济检查点，不仅看 `position_version`。

即使经济状态已追上，价格仍可能 stale。响应可以同时表示“经济结果已到 3”和“最新有效估值暂不可用”，这比把所有状态压成一个 success 更诚实。反过来，新价格配旧经济快照也应清楚显示，而不是用价格时间掩盖结转滞后。

客户端超时以后，用户可以凭原请求／事件身份查询结转结果；不能因页面还没看见就重新提交一个不同身份的平仓命令。读己之写改善可解释性，但它不代替执行侧的请求幂等和资金资格校验。

## 第 8 层：用户投诉强平或权益显示，怎样还原当时依据？

**面试官：** 你已经有位置令牌和价格证据。几天后价格源回补历史数据，用户质疑当时的权益和风险动作，你会用今天重算的结果证明当时正确吗？怎样验证整条接口契约成立？

**面试者：** 不会。今天重算能回答“按修正后的历史输入会怎样”，不能自动回答“当时实际用什么作出决定”。应同时保留当时的经济快照引用、价格证据、估值／风险规则、执行资格记录及最终动作关联，区分实际决策视角和事后重算视角。

对 F3 与 M1 的展示记录，至少能复原数量 1.8、成本 3,780、现金 1,470.7，以及价格 2,400 的来源和质量，重新得到 U=540、E=2,010.7。如果后来用修正价格 2,300 重算，得到 U=360、E=1,830.7，应生成新的分析结果并保留修正原因，不能覆盖旧价格身份后宣称原界面一直显示的是新值。

对真正的风险动作，还要保留它消费了哪一份资格或预留、提交时校验了哪些经济和价格条件。只有一张界面截图或一个最终权益，不能证明没有检查与执行之间的竞态。

验证可以逐个构造可判定的反例：把数量与成本放在不同经济版本，接口应拒绝拼接；重复转发旧价格，源时间不能刷新；Mark 停更，核心仓位哈希应不变；风险许可返回后插入亏损成交，旧许可不能无条件生效；投影停在 2 而查询要求 3，应明确等待或回源，不得伪造新版本。

本题描述的是设计与验证方法，不声称已经进行价格故障演练或风险工程测试。若改为链上合约权威产品，还需要保存相应区块／日志及最终性证据、处理重组观察；那是改变基线后的扩展，不等于在本链下方案里加一个区块高度字段就完成了。

## 本题收束

- **讲透的机制：** 一致经济快照与独立价格证据组合；价格质量、展示新鲜度和执行资格分离；风险在受控提交边界校验版本／消费预留；在途义务不因投影滞后消失。
- **最易答错的边界：** 把最新接收时间当源新鲜度；把 last trade 冒充 Mark；用页面缓存作资金裁决；只校验仓位版本而忽略价格与在途敞口；用事后修正数据覆盖原决策证据。
- **检验反例：** F3 已结转但页面停在 F2，M1 又被重复转发。一个成立的方案应分别报告经济进度与价格年龄，查询要求版本 3 时不伪造响应，资金动作仍受权威经济状态和有效价格策略约束。
