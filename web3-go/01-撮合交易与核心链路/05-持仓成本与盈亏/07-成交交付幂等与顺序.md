# 大问题 7：成交重复、乱序、缺口和确认超时怎样处理？

## 先看懂：关键词大白话解释

本文适用范围：乘数 1 的 ETH-USDC-PERP 线性永续，ETH 数量、USDC/ETH 价格，单向逐仓、加权平均、费用独立；一个账户侧仓位与账本同库提交。讨论可靠输入，不把消息到达或 ACK 当作新的成交。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 分层幂等身份 | 不同层用不同标识防止重复执行 | fill、账户 leg、经济输入、账本效果各护自己的范围 |
| 身份命名空间 | 防止新旧来源碰巧重用同一编号 | 包含来源分区代际等信息，不只信一个裸数字 |
| 规范载荷 | 大家按同一方式表达的经济字段集合 | 价格、费用、账户、规则等含义固定后才算摘要 |
| 本地重算摘要 | 用实际收到的字段重新计算指纹 | 不能只比较发送方声称的 digest 字符串 |
| 身份冲突 | 同一事件标识却带来不同经济内容 | 换价格不能覆盖旧事实，也不能冒充重复成功 |
| source_seq | 撮合来源流里的因果位置 | 过滤其他账户后有空档未必是本账户丢消息 |
| account_seq | 本风险单元连续应用的经济位置 | 必须按前序加一推进，不能由消费者抢到消息决定 |
| 来源完整性证据 | 能证明前面消息已补齐或确实无关的材料 | 未证明缺口无关前，后到事实不能先占权威业务位置 |
| 事务性排号 | 身份映射、事件和连续序号一起持久写入 | 回滚不留承诺空号，重复来源沿用原序号 |
| 待补缺状态 | 输入已可靠保留但尚未应用 | 不是坏成交，也不能被误读为已经完成 |
| 提交后确认 | 经济写入完成以后才告诉上游已处理 | 提交未知沿原身份查询，不造新 ID 重做 |
| 消费者本地 Inbox | 下游把去重证据与自己的副作用一起存 | Outbox 可重发，不代表下游能重复改余额 |
| tombstone 与水位 | 明细归档后仍保存的长期防重证据 | 不能让超过短 TTL 的旧成交重新活过来 |
| 隔离重算 | 在影子状态核验旧历史而不触碰真钱 | 要调真实账务需新更正身份，不删除旧去重记录 |

## 把整篇文章压缩成一个故事

小林在 ETH 永续逐仓里先以两千买二 ETH，再以两千三买一 ETH，随后以两千五卖一点二 ETH。三笔费用分别四、二点三、三。网络却把第三笔先送到持仓服务：此时只完成第一笔，仓位二、成本四千。若直接应用早到的卖出，会先实现六百盈利；以后补买一 ETH，最终虽仍是一点八 ETH，成本却变三千九百，而正确顺序应是成本三千七百八十、毛盈利四百八十。

入口因此不能以到达先后排业务序号。它先核对来源完整性，补到相关前序后，把账户侧身份映射、连续序号和规范事件一起持久保存；与小林无关的市场序号空档则不必硬等。处理器先查身份和实际字段重算的摘要，再查连续序号。重复第一笔只返回旧结果，第三笔留在待补缺状态，第二笔应用后才轮到第三笔，不能跳检查点来消除报警。

正确结转后，小林现金从九百九十三点七增加四百七十七，成为一千四百七十点七。仓位、毛盈亏、费用、结算余数、Inbox、检查点和结果 Outbox 同事务生效。确认丢失后仍沿原身份取回结果，不能重新发号再扣费；同 ID 若把价格改成两千六，就是冲突，不是更正通知。交易另一方有独立 leg，也不能因全局 fill 已出现而被吞掉。

结果派发器与下游都可能重试，所以网络不必只传一次，但每个持久副作用只能生效一次。几个月后归档旧成交，也要以可信水位、摘要或墓碑继续防重，不能删掉近期缓存就让历史复活。若发现旧账需复算，先在影子状态核对，真实调整另建审计事件。整个过程中，小林的订单预留与在途成交责任都不能因接口超时释放，页面追赶也不能反过来改已经确定的事实。

## 第 1 层：为什么全局 `fill_id` 不是完整的账户侧幂等键？

**面试官：** F3 在撮合成交后只有一个 `fill_id`。买卖双方都要记账。若全平台只按它去重一次，会发生什么？

**面试者：** 一个全局 fill 可以影响两个账户，两个账户的持仓方向、费用和账本效果不同。全平台只处理一次就可能让第二个账户侧 leg 被误当成重复；若为双方各生成随机请求 ID，又不能在网络重试时识别同一个业务影响。

我会把身份按层定义：

```text
fill_id            撮合产生的全局成交事实
leg_id             该成交中一个账户角色对应的账户侧影响
economic_event_id  某风险单元需要折叠的一条规范经济输入
effect_id          该输入产生的某一种持仓／账本效果
```

`economic_event_id` 可以由受信任的清算入口稳定生成，或从不可变的成交身份和账户 leg 确定映射；关键是重投不变、不同账户侧结果不冲突。毛盈亏与手续费可有不同 `effect_id`，但关联同一经济输入。

例如 F3 买方 leg 和卖方 leg 各自有自己的经济事件身份。对一个账户重复收到同一 leg，只能影响该账户一次；另一个账户的 leg 不能因 `fill_id` 已在全局出现就被跳过。

身份能指出“是哪一条”，但同一身份的后续消息如果改了价格或费用，系统怎样判断它是重复还是篡改／数据冲突？

## 第 2 层：相同身份但载荷不同，为什么不能覆盖旧记录？

**面试官：** 假设第二次收到的 F3 仍是同一事件 ID，但价格从 2,500 改成 2,600。你会按 last-write-wins 更新，还是只看 ID 返回成功？

**面试者：** 两种都不可以。相同身份、相同规范载荷才是重复投递；相同身份、不同载荷是冲突，意味着上游事实被改写、编码不一致或身份映射错误，必须隔离并追查。

清算入口应在身份生成后构造规范字段集合，例如账户、风险单元、市场、leg、带符号数量、价格、费用、币种、来源序号和规则版本。明确小数 scale、字段顺序、缺省值、字符串规范化和版本，再计算载荷摘要并保存摘要所依据的字段。

不能把任意序列化输出默认当成规范编码。Go map 的遍历顺序不稳定；虽然标准库 `encoding/json` 对支持的 map 键会排序，这仍不等于已定义跨语言的小数、缺省值与编码版本契约。应使用明确的确定编码；哈希不是授权来源，也不代替上游签名或访问控制。

接收方必须从本地实际收到的规范字段重新计算摘要，核验它与发送方声称的摘要一致，再与已有记录比较。否则发送方复用旧 digest 却改变价格，本地只比较 digest 字符串仍会误判成重复。核验失败不改变权威状态，保留证据并隔离。

身份需要带足来源命名空间，例如撮合实例／分区代际、市场、fill 和账户侧角色；系统重建或迁移后不能让旧的数字 ID 在新流里复用。规范摘要覆盖业务字段，不把每次变化的投递次数、网络时间戳混入经济载荷。

处理分支是：ID 未见过才进入新输入流程；ID 已有且摘要相同则返回已存结果；ID 已有但摘要不同则不覆盖、不确认成重复成功，进入隔离与告警。还要避免对非法内容先写成“已处理”，否则修复数据后也无法沿正确流程补入。

重复判定已明确；但不同成交的先后关系不能由哈希决定。撮合的来源序号与某账户实际应用的序号有什么区别？

## 第 3 层：来源序号和风险单元序号为什么不能混为一个数？

**面试官：** 撮合给 F1、F2、F3 全市场序号 100、101、102。该市场有很多账户，某账户只收到 F1 与 F3；F3 的 `account_seq` 应是 102 吗？

**面试者：** 未必。全市场来源序号表达撮合侧的因果顺序，账户侧 `account_seq` 表达某风险单元实际要应用的连续经济输入位置。过滤掉其他账户的成交后，本账户的市场序号自然可能不连续；不能把来源序号空档误判为自己丢消息。

字段应分别保留 `source_seq` 与 `account_seq`。入口要保持对同一仓位相关输入的撮合因果关系，并在风险单元可靠输入流里形成连续账户序号。F1、F2、F3 若都影响本账户，则可以对应 account_seq 1、2、3，即使 source_seq 不是连续数值。

只有在明确完整接收某来源分区的全部事件、按该分区契约处理且分区键与经济顺序一致时，才可直接用其 offset 作为应用检查点。不能把消费者并发领取消息的先后当成交顺序，也不能用 Kafka offset 的数值大小替代账户经济因果关系。

如果同一账户同时受多个来源影响，单个连续 `account_seq` 还需要入口定义一个确定的合并次序；该次序必须符合业务因果约束。对于互不相关的风险单元，可各自有序，不必制造全平台全序。

那么这个连续序号具体由谁分配？若消息先排号、后持久化失败或重复排号，会不会让检查点永久断裂？

## 第 4 层：怎样可靠分配账户序号并保留来源顺序？

**面试官：** 清算入口把消息放入队列时，能否直接用 `atomic.Add(1)` 分配序号？如果进程在排号后崩溃、或重复消费又申请一个新号，会怎样？

**面试者：** 纯内存原子计数只在当前进程内递增，不保证持久，也不提供跨实例唯一顺序。入口要将规范事件身份、输入记录和序号分配写成可靠的持久操作，重复来源事件必须映射回原分配，而不是拿新号再次入队。

一种适合本数据库基线的做法是对风险单元序列头做事务性条件更新：先按来源契约取到下一个可处理输入，检查该 source 事件是否已经映射；若是，返回已有 account_seq；否则持久写入下一连续序号与规范事件，再提交。消费端以序号连续校验执行。

若来源有缺口，例如已见 source_seq=103，但同一有序来源确认一个可能影响本风险单元的 102 尚未到达，不能因为 103 先到就让它先获得可生效的账户序号。可暂存 103 并请求补发 102，或由权威来源证明 102 不影响本账户且允许跳过；这个结论需要持久可审计的跳过标记，不能由超时自行推断。反之，若入口明确知道 102 属于其他账户且不影响本风险单元，就不应要求本账户等待一个无关事件。

本方案明确选择先补齐来源完整性证据，再分配权威 `account_seq`：早到的 103 只保存在来源暂存区，不能先占据本应排在 102 后面的业务位置。否则即使暂不应用，后来 102 也没有正确的前置序号可插入。补齐后分配身份映射、序列头与事件同事务提交；事务回滚不留下已承诺的空号，不使用会在回滚后永久消耗的数据库自增值充当连续业务序号。

序号可靠之后，处理器遇到重复、越序事件或重启补投时，应用层状态机应如何表现？

## 第 5 层：重复、乱序和缺口是三种不同处理结果吗？

**面试官：** F1 已应用、F3 到达、F2 迟到；另一消费者又重送 F1。你会如何区分并发执行、重复和缺口，避免只是把所有消息都塞回队列？

**面试者：** 会先依据身份和摘要处理重复，再依据连续序号处理顺序。F1 同身份同摘要是已完成输入的重投，返回原结果；F3 若 `seq=3` 而 `last_applied_seq=1`，是缺少 2 的待处理输入，不是重复，也不是可立即失败丢弃的坏成交。

缺口输入必须可靠保留，并触发从事件日志或上游补发缺失项。F2 到来后，处理器按 2、3 的顺序应用。若检查点是 3 却无法找到 2，就说明序号分配、事件归档或检查点协议已损坏，需要停止该风险单元写入并调查，而不是把 `last_seq` 直接设到当前最大值。

以案例说明错序危害：F1 后仓位是 2@2,000。若先应用 F3，它先平 1.2，毛盈亏为 600，剩余 0.8 的成本为 1,600；再应用 F2 买 1@2,300，最后 q=1.8、C=3,900、已实现毛盈亏 600。正确顺序得到同样数量，却是 C=3,780 和已实现 480。

事件处理也要避免同一风险单元并行折叠两条有序输入。并行只可用于不同风险单元，或在能证明不冲突且最终状态合并等价时采用；仓位交易通常依赖前态，不能为了吞吐量并发应用再随意覆盖。

即使应用器序号严格递增，Inbox 去重记录若比仓位先提交，或仓位比检查点先提交，仍会出错。它们要怎样绑定？

## 第 6 层：Inbox 与仓位、账本、余数和检查点怎样原子绑定？

**面试官：** 你如何证明一个事件不是“已经被 Inbox 标记完成，却没有改仓”，也不是“已经改仓，但没有幂等记录”？请按 F3 描述同库提交。

**面试者：** 消费确认记录与它代表的经济效果必须在同一事务里提交。Inbox 不是先写一个“看过了”标记再开始做账；它要么是事务内新建并和全部结果一起完成，要么事务整体不留下已处理痕迹。

F3 事务锁定风险单元控制行并验证 owner epoch，查 Inbox；确认摘要与规则版本；要求 `account_seq=last_applied_seq+1`；读取 q、C、账本、余数与相关订单义务；计算新状态；写 position、成本释放、毛盈亏与费用的平衡分录、结算余数、Inbox 处理结果、检查点和 Outbox；一次提交。

若 Inbox 已存在相同摘要且处理完成，返回记录的结果版本；摘要不同则隔离；如果相同事件还处于显式待补缺状态，它不能被误当成已应用。并发唯一冲突后也应读回记录并比较摘要，不能把所有 duplicate-key 错误都吞成成功。

仓位、账本和余数均属于该提交域。对原始毛盈亏按规则转换到现金 scale 时，已入账金额和余数同步更新；否则崩溃重放可能多舍一次或遗漏尾数。

若事务已经提交但清算入口没收到确认，这条链路如何知道是“提交未知”，又如何安全恢复订单或资金状态？

## 第 7 层：确认超时后，哪些状态是未知，哪些绝不能按失败处理？

**面试官：** 清算请求超时了，持仓服务可能已经提交。上游是否应该立刻取消成交、释放订单预留并用新 ID 重试？

**面试者：** 不能。超时只说明调用方没在期限内收到结果，不代表服务端事务回滚，也不代表撮合成交无效。经济事件状态应能表达“提交结果待查”，而不是把传输层超时直接翻译成业务失败。

上游沿原 `economic_event_id` 和原摘要查询 Inbox 或重试。若已提交，返回原 q、C、账本版本和效果结果；若事务确实未提交，重新执行同一个身份；若尚缺前序事件，报告等待补缺；若同身份载荷冲突则进入隔离。调用方不另造 ID 试运气。

订单侧状态与成交处理状态分别跟踪。部分成交后撤销剩余量，只能在撤单／订单权威状态确认后释放对应未成交预留；已成交但结转暂时未确认的数量保留为在途义务。划转与新开仓资格需考虑这项约束，不能根据“接口超时”释放额度。

若已提交结果能查询，但结果通知还没有发给风险和读模型，谁负责可靠交付？

## 第 8 层：Outbox 可以重复投递，为什么不等于 exactly-once？

**面试官：** 你说可在同一事务写 Outbox。派发器发送成功后宕机，无法确认 broker 是否收到了。再发一次时，下游如何处理？

**面试者：** Outbox 保证的是已提交业务结果有一条持久的待交付记录，不保证网络只能送一次。发送成功但 ACK 丢失时，派发器必须重发；因此消费者也要用稳定消息／效果身份进行幂等应用，并验证事件版本单调推进。

一个事件可带 `economic_event_id`、`effect_id`、`account_seq`、仓位／账本版本及规范载荷摘要。风险或查询消费者若看到相同效果身份与摘要，返回之前结果；若身份相同但内容不同，隔离；若版本旧于已应用版本，则拒绝倒退；若有版本缺口，根据自己的状态重放或请求补齐。

消费者先更新自己的数据库再 ACK，也有“更新成功、ACK 丢失”窗口，所以其本地 Inbox 或效果唯一约束必须与本地副作用同事务提交。若消费者执行的是外部不可幂等动作，还需要下游提供幂等键、持久请求查询或业务级对账，MQ 不能替第三方保证一次副作用。

Go channel 只在进程内传递值；MQ 的重试和幂等生产／消费配置也有各自范围。它们不自动保证跨数据库事务、用户现金只变一次或双方清算同时完成。

如果 Inbox 只保留近期记录，几个月后灾备重放一个旧成交，会不会又被当作新输入？

## 第 9 层：归档和去重记录淘汰后，怎样防止历史成交复活？

**面试官：** 为控制 Inbox 存储量，你只留 30 天记录。一次旧消息在备份恢复、上游重放或消费者迁移时超过 30 天重现，如何保证它不会再次结转？

**面试者：** 去重记录的保留期限必须大于系统允许的最大重试和恢复窗口；若来源可能永久重放，就不能单靠短 TTL 明细记录保证永久幂等。淘汰前必须有另一种持久防重依据。

可选做法是保留紧凑 tombstone／身份摘要；对严格连续有序日志，保留可信的最后应用序号和日志分区水位，并拒绝水位之前任何未被证明已处理的消息。但序号水位只有在来源定义了不可回退的事件范围、归档完整可验证且没有身份复用时才安全；否则它会把真正迟到但未应用的事件一并拒绝。

归档应保留可恢复的原始规范事件、规则版本和摘要校验。恢复时从某个经验证检查点开始读取之后的完整区间，核对连续性；不能只恢复仓位快照而丢掉检查点与身份历史，再让旧成交拥有新的处理机会。

水位推进必须等归档对象本身可读、校验通过且检查点已持久化。若先删除明细再写水位，崩溃窗口可能同时丢去重证据与恢复依据；若水位先越过仍未完成的序号，又会把待处理义务错误排除在重放范围之外。保留策略因此也是提交协议的一部分。

如果业务要求人工重算旧事件，应在隔离影子状态中重算并比较；若需要调整真实余额，要创建新的更正身份并关联原事件，而不是删除原 Inbox 记录再重放。清仓也不删除账户级已处理身份、水位或余数。

哪些端到端时序能一起覆盖重复、乱序、提交未知、归档和双边输入这些风险？

## 第 10 层：怎样把交付协议变成可反驳的故障验证？

**面试官：** 请设计一组按身份、顺序、持久化和对手方分别观察的反例。哪些状态允许暂时落后，出现什么结果就足以否定方案？

**面试者：** 我会以稳定预期向量和持久证据验证协议，不只看消费者的 ACK 计数。F1→F2→F3 的预期是 q=1.8、C=3,780、毛盈亏 480、费用 9.3、现金 1,470.7；这个基线用于逐事件比较。

第一组故障覆盖身份：重复 F3 同 ID、同摘要应返回原结果；同 ID 换价格或费用应冲突隔离；买卖双方两个 leg 都应各自处理一次。身份碰撞、串户或一个 leg 被全局 fill 去重吞掉，都是否定结果。

第二组故障覆盖顺序：F1 后先送 F3、再送 F2；系统应保存缺口、补齐序号后按 1、2、3 应用。正确最终数量仍为 1.8，但成本必须是 3,780、已实现毛盈亏必须是 480，而不是错序产生的 3,900 与 600。

第三组故障覆盖提交与通知：分别在事务中途退出、COMMIT 后丢 ACK、Outbox 发送后丢确认。允许查询和风险投影暂时落后，但同一账户侧效果不能重复，检查点不能越过未提交的序号，投影不能倒退。上游必须用原身份查询或重试。

第四组故障覆盖长期恢复：将旧事件从归档重放，校验 Inbox／水位仍阻止二次效果；恢复检查点后逐事件核对输入摘要、account_seq、规则版本、仓位成本、现金和余数。对手方其中一侧暂停时，另一侧的结转可存在，但总清算状态必须揭示仍有待闭合 leg。

观测字段至少包括 source 与 account 序号、事件和效果身份、载荷摘要、处理状态、仓位／账本版本、Inbox 命中、缺口长度、Outbox 投递次数、归档水位与双方 leg 闭合状态。端到端流程可以做故障注入测试；本文件本身提供面试设计，不声称已执行这类工程测试。

### 本题收束

#### 已经讲透的机制

- `fill_id`、账户侧 `leg_id`、经济事件身份和账本效果身份覆盖不同作用域。
- 规范载荷摘要让“重复”与“同身份冲突”可区分，身份不能由任意 JSON 字节序列决定。
- 来源因果顺序与风险单元连续 `account_seq` 各有用途；序号分配必须持久且不能跨缺口生效。
- Inbox、仓位、账本、余数、检查点和 Outbox 在本基线的同一事务中共同提交。
- 超时表示结果未知；可靠投递允许重复；Go channel 和 MQ 不会自动提供端到端 exactly-once 经济效果。
- 长期归档需要摘要、水位或 tombstone 等持久防重依据，不能依赖短 TTL。

#### 最容易答错的边界

1. 以消费者收到消息的先后替代撮合／清算的权威顺序。
2. 把市场全局序号当作每个账户连续序号，或把不同账户 leg 用一个全局去重位吞并。
3. 同 ID 换价格仍返回成功，或用非规范序列化产生不稳定摘要。
4. 先 ACK 或先推进检查点，再异步更新仓位与账本。
5. 订单／清算超时就释放预留、取消已确定成交，或用新身份重试。
6. 认为 MQ exactly-once、Go channel 或短期 Inbox 可以跨数据库、跨重启永久防重。

#### 一个能检验方案的反例

F1 已处理后先收到 F3，再收到同身份同载荷的 F1 重投；F2 随后补到。正确系统忽略 F1 重投、暂存 F3、应用 F2 后再应用 F3，得到 `q=1.8、C=3,780、R毛=480、B=1,470.7`。若最终数量虽为 1.8、但 C=3,900 或 R=600，顺序保证已被反例推翻；若重投再扣一次费用，幂等边界也已被推翻。

本题以可靠输入与交付收束；涉及账户事务分录、预留交接与拆库权衡见 06，不在这里另建可运行 MVP。
