# 大问题 5：定点计算、舍入和余数怎样避免长期资金漂移？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

本文适用范围：乘数 1 的 ETH-USDC-PERP 线性永续，单向逐仓、加权平均、费用独立。数量与价格六位，成本及原始毛盈亏为 USDC 十二位，现金和费用为 USDC 六位；本篇微额向量只检验金额转换，不另造完整成交。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| scale | 整数背后小数点应放在哪里 | 数量一百万代表一 ETH，不代表一百万 ETH |
| 量纲相消 | 数量单位乘价格单位后得到钱的单位 | 六位数量乘六位价格，结果是十二位 USDC |
| 十进制精确解析 | 从字符串直接得到规定整数 | 不先经过 float64 再猜回最小单位 |
| 展示舍入 | 为了页面好读而缩短小数位 | 不许把格式化均价回传重建经济成本 |
| 部分成本 floor | 非负成本比例除法向下取整 | 未释放成本留给剩余仓位，不记作现金余数 |
| 全平直接取 C | 最后关闭时一次拿走全部旧成本 | 既落实空仓语义，也避免多余中间乘法 |
| pending | 本笔毛盈亏加此前结算余数 | 先合起来，再判断有多少能落到六位现金 |
| 向零截断 | 正数去尾、负数也向零靠近 | 不把负零点六微 USDC 按 floor 扣成一微 |
| 有符号结算余数 | 还没入账的小数可以为正也可以为负 | 可随后续盈亏抵销，跨空仓仍保留 |
| 原始／入账桥接 | 十二位结果等于六位结果换算后加余数 | 不能因页面显示零就丢失经济状态 |
| 双权益口径 | 是否计入尚未结算余数的两种视图 | 高精度经济权益和已入账口径都不等于可提现 |
| 中间位宽 | 先乘后除时暂时要容纳多大的整数 | 最后商小不代表中间 int64 乘法安全 |
| big.Int 别名 | 两个引用可能其实能改到同一大整数 | 快照要 Set 深拷贝或明确转移所有权 |
| 舍入规则版本 | 保存这一笔究竟如何取整的证据 | 新代码不能用新默认值重放旧输入 |

## 把整篇文章压缩成一个故事

小林的 ETH 永续账单里，一笔二 ETH、两千价的开仓有四千 USDC 成本，手续费四 USDC。系统把数量记为二百万、价格记为二十亿，两者相乘得到四千乘十的十二次方个成本单位；费用却只记四百万个微 USDC。它们虽然都用整数，却差六个小数位，不能直接混加。成本是合约的入场基准，也不是从一千保证金现金中扣走四千货款。

后来小林的三 ETH 仓位、六千三成本减掉一点二 ETH，释放二千五百二十，剩余三千七百八十，这次恰好整除。处理其他小数量时，比例成本可能除不尽，规则便向下取整，把未分出的成本留给剩余仓位；最后全平直接释放全部旧成本。不能为了让显示均价漂亮而回写成本，也不能把这份成本尾数搬到现金结算余数里。

核对人员再为小林的金额转换单独推演一个微额向量，不把它冒充完整成交：从零余数起，两次各产生正零点零零零零零零六 USDC 毛盈亏。第一次现金入账零，余数保留；第二次入账零点零零零零零一，仍余零点零零零零零零二。负向也镜像处理，两笔相同小额亏损合计入账负一微、余负零点二微。若每笔截零后丢掉尾数，或对负数直接向负无穷取整，长期结果都会偏离。

小林即使已经平仓，余数也不能消失，更不能承诺不足一微的金额可立刻划出。系统须将原始毛盈亏、已入账金额、余数和现金共同保存，恢复时沿历史版本继续。实现还要先推导乘法上界，避免合法整数相乘溢出；若用大整数，不能浅拷贝共享可变对象。只有单位、符号、尾数、位宽和规则都能逐步解释，页面上那个“零”才不会掩盖真正的账务差异。

**流程位置与核心机制：** 本题独立展开母题地图中的精度、舍入与结算余数：不仅要把十进制转成整数，还要区分每个整数代表的单位，确定每一步的舍入方向，并保证未达到最小入账单位的金额仍属于账户经济状态。必要前提是[总览的共同基线与贯穿案例](README.md#11-讨论基线)：线性 USDC 永续、单向净仓、逐仓、乘数 1、加权平均成本、手续费独立、持仓与账本同数据库提交。

**本题固定口径：** 数量和价格各六位；成本及原始毛盈亏为 USDC 十二位；账本现金为 USDC 六位。部分减仓成本释放向下取整，全平释放全部成本；毛盈亏换成现金最小单位时向零截断，余数有符号并跨空仓保留。基线案例为 B0=1,000，F1 买 2@2,000、费用 4；F2 买 1@2,300、费用 2.3；F3 卖 1.2@2,500、费用 3，结果 q=1.8、C=3,780、A=2,100、毛 R=480、H=9.3、B=1,470.7；Mark=2,400 时 U=540、已入账口径 E=2,010.7。

本题共 8 层，沿一条精度主线继续追问：

```text
需要表示哪些量

    → 正负盈亏怎样转换成现金最小单位
    → 余数怎样进入权益口径并跨空仓保存
    → 中间乘积和 Go 整数怎样保证安全
    → 规则版本怎样使重放仍然确定
```

## 第 1 层：把小数改成整数，究竟保存了哪些不同单位？

**面试官：** 你说不用 `float64`、改用整数。若数据库里 `qty=2000000`、`price=2000000000`，别人怎样知道它们分别代表什么？请给出能贯穿开仓、平仓和记账的单位定义。

**面试者：** 整数只消除了二进制浮点的近似表示，并不会自动携带单位。我会把数量、价格、成本、现金和余数分别定义为定点整数，并在字段名、类型边界、规则版本和接口契约中固定 scale。

```text
S = 10^6
数量 q_u = q × S                         单位：微 ETH
价格 p_u = p × S                         单位：微 USDC/ETH
成本 C_u = C × 10^12                    单位：10^-12 USDC
毛盈亏 g_u = g × 10^12                  单位：10^-12 USDC
现金 B_u = B × S                         单位：微 USDC
结算余数 r_u = r × 10^12                单位：10^-12 USDC
```

数量与价格都乘了 `10^6`，所以 `q_u × p_u` 直接是成本或毛盈亏的十二位整数。它不是微 USDC，不能不经换算就加到现金上。

F1 买入 2 ETH@2,000，对应 `q_u=2,000,000`、`p_u=2,000,000,000`，乘积是 `4,000,000,000,000,000` 个 `10^-12 USDC`，即 4,000 USDC。手续费 4 USDC 则是 `4,000,000` 个微 USDC。

内部字段和接口必须让单位可辨认，例如用 `_qty_u`、`_price_u`、`_cost_u`、`_cash_u`，而不是所有值都叫 `amount`。若使用领域类型，也要避免随手把不同 scale 的 `int64` 混在同一个通用参数里。

外部十进制输入也要在进入内核前确定解析契约。可以接受十进制字符串并精确转换到规定 scale；超出 scale 的输入要么按明确规则拒绝，要么按版本化规则转换，不能先解码成 `float64` 再乘 `10^6` 猜回整数。日志和 API 返回值也应标出单位，避免同一个数值在跨服务传递后被当成另一个 scale。

展示舍入和经济舍入不能共享一个隐含的格式化函数。UI 显示均价保留几位可以变化，仓位成本整数与现金过账规则不能随之变化；展示层舍入结果不得被回传作为持仓更新输入。

接下来还要回答为什么乘积单位正好吻合，以及除法发生时为何不能直接使用语言默认的整除规则。

## 第 2 层：为何 `q_u × p_u` 是十二位成本，不是六位金额？

**面试官：** 你给出了字段单位，但公式里开仓成本、平仓毛盈亏和 Mark 未实现盈亏都含乘法。逐项推导量纲，并说明在哪一步才允许舍入到现金 scale。

**面试者：** 对任一成交量，数量单位是 `10^-6 ETH`，价格单位是 `10^-6 USDC/ETH`，相乘后 ETH 抵消，得到 `10^-12 USDC`。因此开仓成本、平仓成交名义额、原始毛盈亏和未实现盈亏可以共享十二位金额表示。

```text
开仓增加成本：abs(d_u) × p_u                   → 10^-12 USDC
部分关闭成本：floor(C_u × c_u / abs(q_u))     → 10^-12 USDC
关闭毛盈亏：sign(q) × (c_u × p_u − K_u)       → 10^-12 USDC
Mark 未实现：sign(q) × (abs(q_u) × m_u − C_u) → 10^-12 USDC
```

开仓 F1 的成本整数是 `2,000,000 × 2,000,000,000`。手续费若已经是六位现金，则换成十二位金额参与同一高精度加减时应乘 `10^6`；只有账本现金更新时，才把经规则处理的毛盈亏折回六位现金。

重要边界是“中间精度不等于输出精度”。不能每乘一次就除回六位，也不能把显示的 2,100.000000 均价乘回数量重建 C。权威量是原始数量和成本；均价是派生显示量。

现在乘除的单位已经明确，但部分减仓时 `C_u × c_u / |q_u|` 未必整除。除出来的尾数应由哪一部分仓位承担？

## 第 3 层：部分释放成本时，余下的一点成本尾数归谁？

**面试官：** 你说成本保留十二位。假设比例除不尽，直接把 K 四舍五入会发生什么？全平时还要用同一条 `floor` 公式吗？

**面试者：** 本题明确选择：成本都是非负绝对值，部分关闭的释放成本 `K_u=floor(C_u×c_u/|q_u|)`，除法的正余数留在仍持有的成本中；关闭量等于旧仓全部数量时，直接令 `K_u=C_u`。

这样做的理由是状态守恒简单：部分平仓后 `C'_u=C_u-K_u`，释放量和剩余量相加严格等于旧成本；向下取整不会多释放一份成本。若换成其他分配规则，必须明确差额归属、保证重放一致，并改变规则版本，不能在不同服务中各自 round。

整除的主例可以直观展示口径：F2 后 `q=3`、`C=6,300`，F3 关闭 1.2，得到 `K=2,520`，剩余 `C=3,780`。这次恰好整除，不代表任意精度输入也会整除。

若某个微单位比例产生 `C_u×c_u = n×|q_u|+a`，其中 `0<a<|q_u|`，规则把 n 个十二位单位释放、把对应成本留在剩余仓位。比如整数向量 `C_u=10、|q_u|=3、c_u=1`，释放 3 个成本单位，余下 7 个单位仍由两份数量承担；它不是“丢掉了这部分成本”，也不应另记成现金余数。

这个分配规则会让某一小份平仓看起来略少释放成本，但其累计效果可由剩余成本精确承接。成本必须作为原始整数持续保存。若改用四舍五入，只要每步都依据当前权威 C、q 计算并从 C 中扣除 K，仍有 `0≤K≤C`，不会因此累计释放超过原成本；但它会改变成本尾数和各笔损益的分配，违反本专题既定的向下取整规则。均价展示的微小变化不能作为修正 C 的依据。

全部平仓直接释放剩余 `C_u`。在精确整数乘除且 `c_u=|q_u|` 时，比例公式本来也恰好得到全部 C；直接取 C 是显式落实清仓语义，并避开不必要的中间乘法。真正会留下幽灵成本的是先舍入均价或先舍入比例再回算释放成本。清空成本也不意味着可以清空损益结算余数，因为那是另一种状态。

仓位成本的尾数已归属剩余仓位；实现毛盈亏转成账本现金时，正负数尾数又应如何处理？

## 第 4 层：正盈亏和负盈亏，怎样换成六位现金且不偏向一侧？

**面试官：** `int64` 有符号除法向零截断。你为什么不统一用 `floor`？当两次小额正收益和两次小额亏损到来时，余数怎样变化？

**面试者：** 成本释放的被除数、除数都非负，所以这里使用 `floor` 没有正负歧义。毛盈亏却可正可负，转换到现金最小单位必须按总览约定向零截断，不能把数学负无穷方向的 `floor` 误当成“截断”。

设原始毛盈亏和历史余数都以 `10^-12 USDC` 表示。每次把 `pending=r_u+g_u`，计算 `posted_u=trunc_toward_zero(pending/10^6)`，再保存 `r'_u=pending-posted_u×10^6`。因此 `posted_u` 是微 USDC，余数仍是 `10^-12 USDC`。

```text
正例：g1=+0.0000006 USDC → 入账 0，r=+0.0000006
      g2=+0.0000006 USDC → 入账 +0.000001，r=+0.0000002

负例：g1=-0.0000006 USDC → 入账 0，r=-0.0000006
      g2=-0.0000006 USDC → 入账 -0.000001，r=-0.0000002
```

如果对负数用 `floor`，单笔 `-0.6` 微 USDC 会立即入账 `-1` 微，正数 `+0.6` 却按另一边界处理，方向性偏差会累积。向零加有符号余数使同方向的小额值累积到一个最小现金单位；后续反方向值也会抵销余数。

这条等式每次都应成立：`累计原始毛盈亏_u = 累计已入账毛盈亏_u × 10^6 + r_u`。结算并非把余数消灭，而是把达到最小单位的部分移到现金。

但若余数尚未入账，它是否属于用户经济权益？空仓时能不能删掉它？

## 第 5 层：清仓后的余数、未实现盈亏和两种权益口径怎样并存？

**面试官：** F3 后你可以从现金算 `E=B+U`。如果原始毛盈亏里还藏着 0.0000002 USDC，账本现金没有这部分。你会把它当零、放在仓位成本，还是单独管理？

**面试者：** 它是已经发生但尚未达到现金最小单位的毛盈亏，应单独保存在风险单元的结算余数中；不是仓位成本，不是可入账现金，也不是可以随 `q=0` 一起清除的临时变量。

为避免偷换口径，我会区分：

```text
已入账现金口径：E_posted = B + U_raw
含结算余数口径：E_economic = B + U_raw + r
```

其中 `U_raw` 先以十二位精度计算。若账本已入账毛盈亏为 `R_posted`，原始累计为 `R_raw`，则 `R_raw=R_posted+r`（换成一致的十二位单位后）。手续费仍以已入账的六位现金独立扣除；不能把余数拿去抵扣手续费，除非产品规则明确将两者合并结算。

主例没有小数尾差：F3 的 480.000000000000 USDC 可精确换算到六位，因此余数为零，B=1,470.7、U=540、E=2,010.7，两种口径相同。

风险策略必须声明用哪种权益口径。若它使用已入账现金，应承认小于一微单位的余数不支持现金划出；若用于内部风险估值而纳入余数，也不能将其伪装成可提现余额。展示可以同时给出已入账和高精度经济视图，但不可用一个模糊的“权益”字段混称。

全平将数量与成本归零，余数仍留在同一账户风险单元，随之后经济事件继续结算。若风险单元真正关闭，需另订有审计依据的最终余数处置流程，不能因仓位为空自动抹掉。

口径正确还不够；上面的乘法、累积和转换会不会在 Go 的中间类型里先溢出？

## 第 6 层：为什么 `int64` 输入合法，乘积仍可能溢出？

**面试官：** 所有 API 字段都能安全解析成 `int64`，是否就能直接算 `C_u×c_u`？若改用 `math/big.Int`，有没有并发或别名问题？

**面试者：** 不能。两个合法 `int64` 的乘积可超过 `int64` 上限，甚至在后续除法之前就溢出。先做足够位宽的运算，再除，才有意义；不能期待“最后的商很小”挽救已经溢出的乘法。

工程实现前应以最大允许数量、价格、成本、费用、单次关闭比例和累计事件数推导各中间表达式上界。对固定区间，可以选经过证明且带溢出检查的宽整数；范围无法有界时可用 `math/big.Int`，但输入、输出仍要校验业务限值，任意精度不等于任意输入都合法。

`big.Int` 是可变对象。其算术方法允许接收者与操作数别名；这方便复用，却意味着复用时可能改写原状态。不要复制 `big.Int` 结构体指针或浅拷贝后认为两份状态独立；在不可变快照、缓存或并行核对中应做 `Set` 深拷贝，或采用明确的所有权转移。

我会把算术边界封装在少量纯函数中，接收已校验值，返回新值和错误；不把 `*big.Int` 暴露给查询或其他 goroutine。即使单写者顺序处理，也不能让一个查询方拿到可修改的内部整数对象。

另一个选择是定点十进制库，但库的默认 scale、舍入模式、零值与溢出行为必须显式固定。使用 decimal 类型不代表可以不写单位和规则版本；不同库或不同默认精度依然可能产出不同经济结果。

输入校验应在转换前完成：数量不得是零，价格需为正，费用非负，十进制位数不能超过该规则版本允许值；超范围或超 scale 应返回明确错误，不能截短后仍把原始载荷摘要当成已验证值。若协议要求截断输入，截断前后的规范值都应有明确定义，避免撮合与结转各自解释出不同数量。

最后，运算安全还要求历史重放选择同一套规则。舍入规则变更时，系统怎样防止新版本悄悄改写旧成交？

## 第 7 层：舍入规则升级后，如何恢复同一笔历史结果？

**面试官：** 现在产品想把成本释放从向下取整改成四舍五入，或把现金截断改成银行家舍入。你只部署新代码再重放事件可以吗？哪些信息必须持久化？

**面试者：** 不可以无标记地重放。舍入是经济规则的一部分，改变它可能改变剩余成本、已实现损益、现金和余数；新代码按新规则重算历史，会得到一段从未提交过的账本历史。

每笔账户侧经济输入应绑定可识别的 `rule_version`，该版本至少覆盖数量／价格 scale、成本释放规则、正负截断规则、余数单位和相关校验范围。计算内核按输入版本选择确定规则；未知版本要隔离并保留待处理义务，不能套用当前默认值。

已经提交的结果需要保留输入、前态版本、原始毛盈亏、现金入账金额、更新后的余数和规则证据。仅存最终均价或展示盈亏无法证明采用了哪条舍入路径。

规则迁移应先在影子状态用新版本重算并比较，明确差异和业务处置，再决定未来事件从哪个边界使用新规则。已经发生的现金效果不能在后台静默改写；若确认历史有错，应创建可审计的更正事件，而不是改旧成交行。

精度处理也应在持仓和账本同一提交里推进：新 C、原始毛盈亏、入账金额、余数和现金不能分别按不同版本计算后拼在一起。这个专题基线下它们属于同一个数据库提交域。

## 第 8 层：怎样设计能抓出精度漂移的反例和检查？

**面试官：** 主案例所有值都整除，可能掩盖舍入错误。请提出针对正负余数、全平、极值和拆单的验证，不要声称你已经跑过生产测试。

**面试者：** 我先把业务不变量与算术边界分开验证，并以独立的高精度参考计算推导预期值。这里提供的是面试验证方案和手算向量，不是本任务运行过的工程测试结果。

第一类检查每次状态迁移：成本非负；空仓成本为零；部分关闭后释放成本与剩余成本之和等于旧成本；全平释放全部旧成本；Mark 更新不改变仓位、账本现金、毛交易历史和结算余数。

第二类检查结算余数恒等式：`R_raw_u = R_posted_u×10^6 + remainder_u`。用连续正小额、连续负小额、正负互相抵消、刚好一微单位、超过一微单位一单位以及跨仓位清仓等向量验证。任何一步丢掉符号或在清仓时归零余数，都应立即被捕获。

第三类检查极值与非法输入：最大数量乘最大价格、成本乘关闭量、最小正数量、零价格、超 scale 输入和中间结果接近位宽上界。预期要么是正确结果，要么是明确拒绝；不能接受静默回绕、负成本或 NaN 式结果。

拆单与合单不应武断断言逐位相等。加仓的数量与成本累加通常可精确一致，但不同关闭比例和成本余数的归属会影响有限精度路径；应按声明的顺序和舍入契约比较，并把差异定位到第一步，而非用最终权益近似一致放过它。

### 本题收束

#### 已经讲透的机制

- 每个整数都带有明确单位，乘法结果保留十二位金额，现金转换才落到六位。
- 成本分摊余数留在仓位；毛盈亏结算余数留在账本风险单元，二者不可混为一类。
- 正负金额统一向零截断，恒等式把原始毛盈亏、已入账金额和有符号余数连接起来。
- 精度规则、位宽、`big.Int` 所有权及历史版本共同决定确定性。

#### 最容易答错的边界

1. 把整数称为“最小单位”，但说不出该字段具体是微 ETH、微价格还是十二位 USDC。
2. 用 `floor` 处理负毛盈亏，或每笔独立截断后丢掉不足一微单位的金额。
3. 全平时用已舍入均价或比例回算成本而留下幽灵成本，或清仓时连结算余数一起删除。
4. 认为所有合法 `int64` 乘积也合法，或将 `big.Int` 浅拷贝后并发共享。
5. 升级舍入规则后直接用新规则重放旧成交。

#### 一个能检验方案的反例

连续两次各产生 `+0.0000006 USDC` 原始毛盈亏。合格实现第一次入账 0、保留 `+0.0000006`，第二次累计入账 `+0.000001`、剩余 `+0.0000002`；将两次分别截成零的实现虽然少量样本现金差异很小，却违反精确桥接式。
