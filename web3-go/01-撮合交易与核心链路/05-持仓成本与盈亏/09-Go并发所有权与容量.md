# 大问题 9：Go 持仓服务怎样选择并发模型并处理热点？

## 先看懂：关键词大白话解释

本文适用范围：乘数 1 的 ETH-USDC-PERP 线性永续，ETH 数量、USDC/ETH 价格；单向逐仓、加权平均、费用独立，仓位账本同库事务。讨论 Go 调度与容量的设计约束，不代表已做并发测试或压测。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 经济并发键 | 决定哪些写入必须排同一队的业务身份 | 同一子账户、市场和逐仓现金桶组成串行单元 |
| 固定 owner 分区 | 用有限处理循环管理许多风险单元 | 不给所有历史账户永久各养一条 goroutine |
| 三种顺序 | 事实先后、持久序号、线程接收先后 | channel 接收顺序不能顶替前两者 |
| 提交态与推测态 | 已持久结果和仅算好但未提交的副本 | 只有提交态能发布为权威快照 |
| 不可变完整快照 | 一整份发布后不再修改的状态对象 | 不把新数量、旧成本与任意现金拼接 |
| 原子指针发布 | 一次换出整个对象的读取入口 | 不代表对象内部可被继续并发修改 |
| big.Int 深复制 | 给大整数建立独立可变存储 | Set 复制或明确转移所有权，防快照被后续 Mul 改掉 |
| 存储侧 fencing | 数据库验证 owner 代次拒绝旧主 | 租约过期、leader 标志和副本数都不能替代 |
| durable source | 崩溃后还能重新取到输入的持久来源 | 内存 channel 只承载可补取任务或通知 |
| 有界背压 | 队列满时停止领取或限制新增负载 | 不丢已确定成交，也不无限扩内存缓冲 |
| 分区内公平调度 | 热点与普通单元轮流得到处理机会 | 子队列有界，单元内部依然保持连续顺序 |
| 单 key 串行上限 | 一个状态链必须逐笔完成的吞吐边界 | 拆买卖流再求和无法恢复正确成本归属 |
| 热点迁移边界 | 换 owner 时确定从哪里交接输入与状态 | 配合 epoch 和排空接管，不能同时建两个有效写者 |
| 容量证据 | 工作负载与延迟、积压等观测共同说明能力 | 1/t 只是串行估算，不是生产吞吐实测 |

## 把整篇文章压缩成一个故事

小林的 ETH 永续单元产生三笔确定成交：买二 ETH 价两千，买一 ETH 价两千三，再卖一点二 ETH 价两千五。高峰时卖出通知先进入 Go channel，如果 owner 按接收顺序直接处理，最后数量虽还是一点八，成本却会错为三千九百、毛盈利六百。正确经济顺序要求成本三千七百八十、毛盈利四百八十，因此单 goroutine 只能避免本进程交错，不能决定业务先后。

owner 读取持久连续序号，先保留第三笔等待第二笔，随后按顺序提交。每次仍要在数据库里校验风险单元锁、前态版本、当前代次及唯一身份，把仓位、现金分录、费用、余数、检查点和消息一起写入。三笔累计费用九点三，初始一千现金最终一千四百七十点七。提交前算好的副本不能发布；查询只能拿完整已提交快照，不能看到一点八数量却配六千三旧成本。

这时旧实例短暂失联，新实例准备接管。持久 epoch 提升要与同一控制行锁协调，切换点前合法提交的事务由新主接着读，切换后旧主再写则被拒绝。只关 channel 或等租约超时，都不能证明旧主没能力连数据库。快照中的大整数也须独立复制，不能原子发布一个指针后继续修改底层对象，让小林刚看到的历史结果悄悄变化。

流量继续上涨，队列满了，系统应暂停领取、从可靠来源稍后补取，并限制新意图，而不是丢弃已成交义务。热点单元可以迁到独立队列，其他单元轮转服务，但不能把小林的买卖拆开并行后只合净数量。通知与估值可独立处理，经济临界路径尽量缩短；容量是否足够仍需观察最老事件年龄、提交延迟与单 key 突发，不能凭 CPU 不高或一句每秒多少笔就宣布已验证。

**流程位置与独立机制：** 本题位于账户侧经济事件进入结转后的执行层，讨论 Go 服务如何把同一风险单元的状态变化串行化、把不同单元并行化，并在热点、过载和故障切换下保留业务正确性。重点是进程内状态所有权、持久事件顺序、数据库原子提交及容量控制各自解决什么问题。

**必要前提：** 沿用线性 USDC 永续、单向净仓、逐仓、加权平均成本、乘数 1、费用单列；持仓和账本在同一数据库事务内提交。主例 F1/F2/F3 仍按权威顺序：`q=1.8、C=3,780、A=2,100、毛已实现=480、费用=9.3、B=1,470.7`；Mark 2,400 时 `U=540、E=2,010.7`。

内部数量与价格六位、成本与原始毛盈亏十二位，部分成本释放向下取整，全平释放全部成本；现金六位，毛盈亏向零截断并保留有符号余数。Go 的整数中间乘积要检查溢出；`big.Int` 可用于宽算术，但其可变对象不可未经复制就跨 goroutine 共享。

本题只讨论实现组织与容量，不另建可运行工程，不假设 benchmark、压测或测试已运行。

本题共 8 层，追问顺序如下：

```text
并发边界按什么业务键划分
    → owner/channel 能保证哪些顺序
    → 状态快照和 big.Int 如何安全发布
    → 为什么单 owner 不能替代数据库事务
    → 主备切换怎样阻止双主写入
    → 有界队列和公平背压怎样保住义务
    → 热点风险单元为什么不能任意拆分
    → 如何用容量与正确性证据判断方案
```

## 第 1 层：你会按什么粒度并行，为什么不能给所有字段各开一把锁？

**面试官：** Go 服务里有仓位、账本、估值和查询。你会按市场起 goroutine、按表加锁，还是让每个字段各自并行？先说明什么状态必须一起看待。

**面试者：** 我先按业务原子单元划边界，而不是按 Go 类型或数据库表划锁。基线中的一个串行风险单元是同一子账户、同一市场及其逐仓 USDC 现金桶；仓位数量、成本、结算序号和账本现金需要在一致的经济事件版本上共同结转。

同一风险单元的 F1、F2、F3 依赖旧数量和旧成本，且顺序会改变损益归属，所以它们必须按权威顺序逐个应用。不同风险单元之间，在不共享现金、不触碰共同限额且写入域允许并行时，可以并行计算与提交。

将“数量锁”“成本锁”“现金锁”拆开会容许不对应同一事务的字段组合；按市场全局锁则会让无关账户互相阻塞，扩大热点范围。按风险单元串行化让锁保护对象和业务一致性边界一致。

物理架构不要求每个风险单元永远有一条 goroutine。风险单元可以稳定映射到固定数量的处理分区，每个分区有一个 owner loop；映射和持久身份要能在重启或重新分区时恢复，不依赖 Go map 当前迭代顺序。

owner loop 是进程内调度优化和可变状态的所有者，不是持久权威本身。权威序号、仓位与账本事务以及幂等效果仍由数据库提交边界约束。

每个风险单元只保证它自身的经济顺序。本例不因所有账户共享一个 Go 进程，就把市场所有事件变成一条不必要的全局顺序。

如果改成全仓共享保证金，现金桶与风险约束可能跨多个市场，原来的市场级并行边界便不成立；要改成账户级协调，或设计明确的共享资金原子协议。不能只把风险单元 key 中的市场字段删掉，就宣称正确处理了全仓竞争。

## 第 2 层：channel 里按先后收到消息，就等于成交的权威顺序吗？

**面试官：** 你让单 owner 依次消费 channel。多个生产 goroutine 同时发送，channel 是 FIFO；这样 F1、F2、F3 的业务顺序是否已经被保证？

**面试者：** 没有。FIFO 只能表达元素进入同一个 channel 后的接收顺序；多个发送方之间的竞争顺序不能替代撮合或清算定义的因果顺序。channel 也不会自动让序号持久化。

系统至少有三种需要区分的顺序：来源事实的权威顺序、风险单元持久的连续应用序号、进程内消息被 owner 接收的调度顺序。后者只有在前两者提供足够信息后，才能安全执行业务。

清算入口应从权威来源按因果关系规范化事件，在持久输入记录中绑定 `account_seq`、事件 ID、载荷摘要和规则版本。重复消息复用同一经济身份，不因每次发送都分配一份新业务事件序号。

owner 收到事件后，先校验风险单元、摘要、当前 owner epoch 和预期序号。若已处理序号相同且身份与载荷匹配，返回原结果；若序号大于 `last_applied_seq+1`，保持待处理并补缺；若小于检查点却找不到对应已处理身份，隔离调查，不按“迟到旧消息”随便吞掉。

序号 3 不能因为先到 channel 就越过 2。F1 后，若 F3 在 F2 前应用，最后数量仍可能是 1.8，但会得到错误成本 3,900 和毛已实现 600，而非正确的成本 3,780 和毛已实现 480。

数据库提交后才推进 owner 的持久检查点和已提交内存版本。若 owner 先把本地 `last_seq` 加一再提交，提交失败后下一笔就会基于并未持久的状态处理，形成内存与数据库双重历史。

通道可以承载事件通知或待取任务，但不能作为已确定成交的唯一存储。进程退出会丢失 channel 缓冲；可靠输入表、持久队列或其他明确的 durable log 才能让事件在恢复后重取。

反过来，如果持久队列的分区键能严格对应风险单元、消费者组具有可靠顺序语义，也仍要校验事件身份、序号和数据库结果。队列顺序减少乱序机会，不消除消费者重平衡、重复投递或提交不确定性。

## 第 3 层：owner 有内存仓位缓存，查询怎样拿到不撕裂且不被修改的状态？

**面试官：** owner 的状态结构里有数量、成本、余数和版本。查询 goroutine 想直接读取，估值 goroutine想保存快照稍后计算。怎样避免 data race、字段撕裂和旧快照被后续修改？

**面试者：** 共享可变 struct 不能因为每个字段是整数就安全。owner 更新多个字段时，直接读取者可能看到新数量配旧成本，也可能触发 Go 数据竞争。要么通过 owner 受控请求读取，要么在提交后复制完整、不可变的快照再发布。

一个可解释的快照应携带风险单元、仓位版本、账本版本、最后应用序号、数量、成本、毛交易盈亏状态、已入账金额、费用和结算余数。估值还要另附 Mark 身份、时间与质量；不能将不同经济版本的字段拼起来称作实时状态。

快照发布可以使用带锁的复制或原子指针发布完整对象。原子指针只能原子地发布一个完整对象引用；如果对象内部仍由 owner 改写，读者仍然不安全。发布前构造全新对象，发布后所有消费者都不得修改它。

查询若缓存版本 2，owner 已提交版本 3，应明确返回版本 2 和陈旧状态，或提供“至少版本 3”的等待／权威读取协议。不能静默把旧快照和新 Mark 拼在一起，除非把该组合标成指定价格下、指定经济版本的估值。

若使用 `math/big.Int` 保存超出 64 位的乘积或累计值，需特别处理别名：`big.Int` 的算术方法会修改 receiver，浅拷贝 struct 不等于深拷贝底层字。owner 继续对共享 `Int` 调用 `Mul`，会改掉已发布快照。

解决方式是把大整数视为不可变快照的一部分：构建新对象时 `Set` 到独立的 `big.Int`，后续计算使用新的 receiver；或在复制和访问时使用明确的锁。绝不把同一个可变 `big.Int` 指针同时交给 owner、查询和审计协程。

输入事件自身也尽量不可变。若事件包含 byte slice、map 或大整数，发送方在发送后继续改写会破坏摘要和重试语义；应在持久化边界做规范编码或深复制，并对相同身份保存稳定载荷摘要。

并发安全不等于经济快照一致。即使所有字段访问都受同一把 RWMutex 保护，也要证明锁定的字段属于同一提交版本，并说明数据库事务成功前快照是否允许发布。

## 第 4 层：只有一个 owner 后，仓位与账本的数据库事务还需要做什么？

**面试官：** 既然同一风险单元由一个 goroutine 处理，是否可以先更新内存，再后台批量写数据库？数据库唯一约束、锁与版本检查还必要吗？

**面试者：** 单 owner 只排除这个进程里该分区的并发修改，不排除另一个实例、旧主、管理脚本或恢复程序同时写，也不提供仓位与账本的原子提交。内存更新不能充当经济事实已持久化。

每个输入的提交仍需在同一数据库事务中完成：锁定或条件更新风险单元控制行，校验当前 epoch、预期序号与前态版本；读取仓位和账本；计算并写新仓、成本释放、现金分录、费用效果、Inbox、检查点和 Outbox；最后一次提交。

空仓首次开仓也需要稳定控制行。不能以“仓位行尚不存在，因此没竞争”为前提让两个实例同时插入；用账户风险单元控制记录、唯一键或等效的可串行化机制处理不存在行的并发。

数据库唯一约束保护账户侧事件身份与效果身份；条件版本更新保护旧前态不能覆盖新结果；epoch 条件保护失效 owner。应用锁可以提高效率，却不应成为唯一正确性防线。

事务失败或结果未知时，owner 不把未提交的 next state 发布为已提交快照，不推进本地持久序号。可以重试同一事件身份；若第一次其实已提交，Inbox 返回原结果，不再扣手续费或增加毛盈亏。

如果暂存了推测态，必须与已提交态分离：下游风险和可划出判断只消费权威提交版本，用户界面也要区分处理中和已结转。更简单的实现是提交成功后才交换 owner 的内存状态。

订单预留与在途义务不能因本地计算得到仓位结果就全部清理。结转事务应按订单协议确认本笔已履行部分，同时保留剩余订单及其他未结转成交对应的约束。

如果为了吞吐而批量提交多个不同风险单元，批量边界是数据库写入优化，不代表它们在经济上成为一个全有或全无事务。批中某一个单元失败时，分别处理各自事务结果和确认，绝不能对上游返回模糊的“这一批部分成功”而无逐项身份。

## 第 5 层：分区 owner 崩溃后，新 owner 接管时如何处理旧主仍在运行？

**面试官：** 负载均衡器已经把请求发给新实例，但网络分区中的旧主恢复了连接，两个实例都认为自己负责同一分区。仅靠租约或 Kubernetes 副本数能阻止双主吗？

**面试者：** 不能。租约超时说明协调方判断某个持有者可能失效，不证明旧进程已经停止，也不保证它无法继续连接数据库。必须让持久存储拒绝失去资格的写入者。

接管过程为分区或风险单元控制记录提升单调递增的 `owner_epoch`。新 owner 读取一致持久状态、取得接管资格后才处理输入。每笔经济写事务都锁定同一控制记录并核验自己持有的 epoch。

旧主如果已经在控制行锁内开始事务，epoch 提升会等待它完成或回滚；于是旧事务在明确切换点前合法提交，或失败。epoch 提升提交后，旧主拿锁再校验就会被拒绝。两个主的竞争结果由数据库持久顺序决定，不依赖时钟比较。

内存锁、进程内 leader flag、Redis TTL 或 channel 关闭都是辅助协调，不是 fencing。它们可以帮助少做无效工作，但必须由所有经济写路径共同检查的持久 epoch 封住旧写者。

接管者先读取同一数据库已提交状态与 `last_applied_seq`，然后重放未完成输入。若本地旧 owner 有未提交缓存，它不能作为接管来源；若数据库提交结果未知，接管者用原身份查询 Inbox 和效果记录来判定。

旧 owner 失效后，已排队在本地内存中的通知不能被当作下一笔唯一事实。可靠输入仍由 durable source 领取；通知重复或丢失由检查点和补取处理。

持久性还取决于数据库高可用语义。如果已确认事务只在主库本地磁盘落地，而故障转移允许落后的副本晋升并丢失它，应用 fencing 不能恢复被数据库丢弃的提交。部署需选择满足经济确认承诺的复制／故障转移策略；不满足时就暂停写入或降低明确的承诺。

这里的“数据库事务已提交”不是链上最终性。若换成合约权威、链上执行的产品，区块包含、确认、重组和最终性需另立规则，不能把数据库 epoch 直接类比成链上终态。

## 第 6 层：队列有界后满了怎么办，怎样既不丢义务又避免一类流量饿死？

**面试官：** 你提到有界 channel。若 F1 到 F3 已确定，但持仓 owner 队列满了，你会丢弃新消息、扩成无界队列，还是阻塞撮合？大量慢账户任务会不会让其他账户饥饿？

**面试者：** 内存队列满是过载信号，不是丢弃经济义务的许可。已确定成交必须先落在可靠持久交付路径，owner 本地队列只承载可重新拉取的工作提示；容量耗尽时对上游施加背压、停止领取更多或持久暂存。

如果撮合提交成交前就需要风险系统的确定准入，准入服务可以拒绝或限流新的交易意图；但成交一旦持久确定，就不能靠拒绝消费者消息来撤回它。清算应保留待处理状态并维持相应在途风险约束。

内存容量按固定上限设计，明确队列满的行为、最大事件大小、重试节奏和租约归还方式。不要通过无限增长 slice/channel 躲过告警；那只是把过载转成 GC 压力、长尾延迟甚至进程 OOM。

事件处理要尽量短小且可恢复。数据库连接池、锁等待和下游 RPC 都是容量瓶颈；owner 若在串行路径内调用慢外部服务，会把一个风险单元的后续全部阻塞。估值、通知和查询不应占用经济写锁的等待时间。

公平性不能只看全局 FIFO。若一个持续爆量的风险单元占满分区队列，会阻塞被映射到同一 owner 的其他单元。可以在分区内按风险单元建立有界子队列并轮转调度，但每个单元内部仍按持久序号串行；配额和优先级不能让某个单元长期不被服务。

对持续热点可动态拆分到不同执行队列，但迁移必须有持久 owner epoch、输入边界和排空／接管协议。不能在两个分区里同时创建同一风险单元的 owner，指望下游数据库锁替代日常调度设计。

过载时可区分可丢弃的展示刷新与不可丢弃的经济事件。Mark 推送在产品允许时可按市场取最新值或压缩中间更新；成交、费用和转账义务必须逐项可追溯，不能用“只保留最新消息”优化。

限流应尽可能作用在新请求和非权威旁路工作上，并为已确定输入预留持久接收能力。监控至少能区分持久未领取数、owner 内存队列长度、最老事件年龄、数据库提交延迟、补缺数量和重试量；只看 goroutine 数量或 CPU 会漏掉真正积压。

## 第 7 层：某个账户形成热点，为什么不能再把它的仓位和账本拆成多条并行流水？

**面试官：** 假设一个高频账户持续交易同一市场，单风险单元 owner 已到吞吐上限。你能把买单和卖单放到不同 goroutine，最后把数量求和、成本和盈亏合并吗？

**面试者：** 不能无条件这样做。该模型按平均成本结转，每一笔反向成交依赖当前 `q、C`；买卖流分开计算会缺少共同的前态，顺序会改变已实现盈亏和剩余成本。

例如 F1 后 F3 和 F2 的错序，最后数量仍为 1.8，但成本和现金桥接不同。分别计算“所有买入总量”与“所有卖出总量”再合并，不能还原哪些数量关闭了哪一时期的成本。

真正的并行空间包括不同风险单元的事件、单笔纯校验中互不依赖的输入解析、独立的查询投影和带版本的估值计算。完成后仍须按同一风险单元顺序折叠并在其事务域提交。

减少热点可以从不改变状态语义的层面做：缩短事务与 owner 临界区、减少重复序列化、批量加载配置、避免同步通知和外部 RPC、分离只读估值、改善数据库键与连接池、压缩冗余快照。需用目标环境测量验证收益，不能声称这些改动必然达到某个吞吐值。

若产品允许改变语义，可以评估更细粒度 lot 模型、按子仓隔离风险或把现金范围拆分，但这会改变平均成本、清算与展示契约，甚至影响风险核算。必须明确迁移算法和用户经济结果，不能作为透明的性能优化。

对每个热点风险单元，单写顺序是必要瓶颈；可提升分区并行度，但不能把同一个 key 的写入并行。系统总吞吐可随独立风险单元数扩展，单 key 的吞吐上限仍受序列化和数据库提交延迟约束。

如果业务要让一个市场账户的极高频变化并行，首先应问能否在上游形成一个语义明确的净额／批次经济事件。只有业务和审计规则承认聚合批次，且证明其与原子逐笔顺序结果等价时，才能采用；不能擅自将成交合并以换吞吐。

吞吐优化后仍要验证费用效果、成本尾数和毛盈亏结算余数的确定性。高精度乘法改用 `big.Int` 或批处理，不得改变向零截断与全平释放全部成本的规则。

## 第 8 层：你会用什么证据判断并发方案既够快又没有破坏经济不变量？

**面试官：** 你没有给出单一吞吐数字。怎样向团队说明容量是否足够，并验证重分区、排队和提交并发没有改变主例的结果？

**面试者：** 先定义需要满足的服务目标和工作负载，而不是给一个脱离机器、数据库和事件分布的数字。包括每秒已确定事件量、每个风险单元的突发强度、热点比例、提交延迟分位数、可接受积压年龄、故障恢复时间和可用数据库连接数。

容量模型要区分单 key 串行上限与多 key 总吞吐。若单事件平均占用 owner 与事务时间为 `t`，单风险单元的理论处理速率受 `1/t` 约束；多个独立 key 可以由多个 owner 并行，但数据库锁、连接池、I/O 和 WAL 可能先达到整体上限。这个关系是估算，不是假装实测。

观测指标要有业务身份和版本：持久接收到提交的延迟、每分区与每 key 的队列深度、最老未处理序号、重复与摘要冲突、序号缺口、事务回滚、epoch 拒绝、快照陈旧时间、恢复重放量及结算余数核对差异。

正确性验证要在实现阶段覆盖确定性向量和并发故障：F1/F2/F3 按正确顺序的结果、F3 重复、F3 先到、同 ID 不同载荷、提交前失败、提交后确认丢失、两 owner 竞争、旧 epoch 写入、队列满后补取以及 `big.Int` 快照隔离。

对并发运行结果，不只比较最后权益，还逐事件比较数量、成本、原始毛盈亏、入账金额、费用、余数、现金和检查点。主例 Mark 2,400 下，权威结果是 `C=3,780、R毛=480、B=1,470.7、U=540、E=2,010.7`；只有权益相同不能证明归属正确。

压力试验应明确数据生成分布与失败条件，避免全是均匀随机账户掩盖热点。没有在目标环境运行压测时，只能描述容量假设与待验证指标，不能宣称系统已达到生产吞吐或高可用指标。

调度公平性的验证还要检查一个慢 key 是否阻塞同分区其他 key、优先级是否使普通账户长期饥饿、超时任务是否不断重排到队尾造成活锁。指标与试验要能观察最大等待时间而非仅平均延迟。

本题的工程结论是分层负责：有界 owner 分区减少进程内共享状态并发，持久事件序号确定业务顺序，数据库事务与唯一约束保护经济效果，存储 fencing 防旧主写入，公平背压处理容量不足。任何一层不能替代其他层。

## 本题收束

### 已经讲透的机制

- **并发键来自经济原子域：** 同一风险单元串行，不同独立单元并行；改为共享全仓现金就要重新定义边界。
- **channel 顺序不是权威顺序：** 来源因果顺序、持久应用序号和进程接收顺序是不同概念，缺口必须等待补齐。
- **快照不可变且完整：** 版本化发布避免撕裂；`big.Int` 和事件载荷需防止可变底层数据别名。
- **进程优化不取代提交：** 单 owner 不能替代同库事务、幂等唯一键、版本校验和存储侧 epoch fencing。
- **容量不足要背压而非丢义务：** 有界队列、持久输入、分区内公平和单 key 热点串行约束需要同时设计。

### 最容易答错的边界

1. 认为 channel FIFO 能替代成交来源顺序或持久日志。
2. 认为只有一个 goroutine 就不用数据库锁、唯一约束或主备 fencing。
3. 将快照指针原子发布后继续修改对象，或浅复制共享 `big.Int`。
4. 队列满就丢已确定成交，或用无界缓冲掩盖持续过载。
5. 为了吞吐把买卖流分开并行，最后仅按净数量合并平均成本与已实现盈亏。
6. 只报平均延迟、CPU 或最终权益，不检查最老事件、热点公平和逐事件经济状态。

### 一个能检验方案的反例

在 F1 后让 F3 先于 F2 进入 channel，并让两个 owner 因切换短暂同时处理该风险单元。如果方案只依赖 FIFO 与内存 leader flag，可能得到错误损益或双写。成立的实现必须按持久序号等待 F2，以事务及当前 epoch 拒绝旧写者，提交后发布不可变版本 3 快照；过载时仍保留并最终处理 F3。
