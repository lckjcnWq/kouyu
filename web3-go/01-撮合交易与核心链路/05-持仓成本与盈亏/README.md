# 持仓成本与盈亏：专题总览

## 先看懂：关键词大白话解释

本文适用范围：链下托管、链下撮合记账的 ETH-USDC-PERP 线性 USDC 永续合约教学方案；数量为 ETH、价格为 USDC/ETH、乘数为 1，采用单向净持仓、逐仓风险单元和加权平均成本，不是现货交割流程。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 线性 USDC 永续 | 用价格差乘数量算损益、用 USDC 记钱的合约 | 开仓不买入实物 ETH，也不支付整笔名义本金 |
| 单向净持仓 | 同一单元只记一个带正负号的仓位 | 正数为多、负数为空，不同时保留两边独立仓 |
| 逐仓风险单元 | 单独算保证金和风险的小账套 | 本例隔离同一子账户、市场及其 USDC 现金桶 |
| 初始保证金现金 B₀ | 开始放进风险单元的钱 | 1,000 USDC 是现金起点，不是持仓成本 |
| 有符号成交量 d | 把买卖方向写进数量正负号 | 买为正、卖为负，由确定成交而非订单意图产生 |
| 入场成本基础 C | 剩余仓位对应的入场名义金额 | 它是算损益的依据，不是付给对手的现金 |
| 加权平均入场价 A | 按剩余成本和数量算出的平均价格 | 非空仓时为 C 除以数量绝对值，不以显示值重建成本 |
| 关闭量与新开量 | 一笔反向成交中平旧仓、开新仓的两部分 | 过零必须先耗尽旧仓成本，再按成交价建反向仓 |
| 毛交易盈亏 R | 只算已关闭仓位的交易价差 | 主例为 480 USDC，不预先混入手续费或资金费 |
| 手续费 H | 每笔成交单独扣的钱 | 主例累计 9.3 USDC，不再计入均价重复扣除 |
| 未实现盈亏 U | 剩余仓位按当前标记价估出的涨跌 | 主例为 540 USDC，不是已经到账的现金 |
| Mark Price | 给剩余仓位估值的标记价格 | 只改估值与风险输入，不改历史成交和成本 |
| 权益 E | 账本现金加剩余仓位估值 | 主例为 2,010.7 USDC，不等于可划出金额 |
| 账户侧经济事件 | 某笔业务事实落实到某一账户的输入 | 交易双方要分别识别，不能全平台仅按 fill_id 去重 |
| 连续经济序号 | 风险单元必须依次处理的事件编号 | 有缺口先补齐，不能按网络到达顺序算均价 |
| 共同提交 | 仓位、钱和处理证据一起生效 | 本例在同一数据库事务写入，不允许只成功一半 |
| Inbox 与 Outbox | 输入防重档案与待交付结果档案 | 配合提交保存，通知重试不产生第二次经济效果 |
| 成本尾数与结算余数 | 成本分摊、货币入账时暂未分完的小数 | 十二位内部金额与六位现金有明确桥接，清仓不删结算余数 |
| 规则版本 | 这次计算采用哪版算法的身份证 | 重放历史必须带旧规则，不能拿今天的配置重算昨天 |
| 权益桥接与逐事件核对 | 把仓位、损益、费用和现金逐笔对起来 | 不只比较最终数量，还要找出第一处状态分叉 |

## 把整篇文章压缩成一个故事

小林向一个 ETH 永续逐仓单元放入一千 USDC，准备做多。系统先核对订单风险并保留必要约束，撮合确认以两千买入两 ETH，持仓才从零变成二，成本基础四千。这里没有交割两 ETH，更没有从现金扣四千；只扣四 USDC 手续费，所以现金是九百九十六。随后再以两千三买入一 ETH，成本累计六千三，数量三，均价两千一，累计费用六点三。这些都来自已提交成交，不是页面上一个“下单成功”提示。

小林接着以两千五卖出一点二 ETH。因为原来是多仓，这次先关闭旧仓，释放成本二千五百二十，毛交易盈利四百八十，剩余一点八 ETH、成本三千七百八十。再扣本笔三 USDC 费用，现金变成一千四百七十点七。成交卖出的名义金额三千并不是现货卖出款，不能整笔加进现金；累计净已结转损益只是四百八十减九点三，即四百七十点七。

这笔减仓结转时，协调层把仓位、盈亏分录、费用、处理记录和结果消息一起提交。若提交后确认丢失，小林看到的重试也只能取回原结果，不能再赚四百八十或再扣三。若第三笔先送到，就要等第二笔补齐；若服务重启，则依检查点和历史规则继续，不拿新算法改写旧成本。小数未到最小货币单位时留存余数，仓位归零也不能凭空抹掉。

最后标记价来到两千四，剩余名义价值四千三百二十，减成本三千七百八十得到未实现盈利五百四十，权益为二千零十点七。它只是指定仓位版本和价格证据下的估值，不是小林立刻能提现的钱。若标记价停更，系统保留成交事实并标注陈旧；若以后卖得超过剩余仓位，必须先平旧多再开新空，不能沿用旧均价制造利润。

## 一、文字全流程：成交怎样变成持仓、损益与账户结果

### 1.1 讨论基线

本专题采用**链下托管、链下撮合与记账的线性 USDC 永续合约，单向净持仓、逐仓风险单元、加权平均入场成本**。这是用于连续推演的教学方案，不代表某家交易平台的协议实现。

- 市场为 `ETH-USDC-PERP`，数量以 ETH 计，价格以 USDC/ETH 计，合约乘数为 1。正数量表示多仓，负数量表示空仓；同一子账户、同一市场至多有一个净仓。
- 用户预先向这个逐仓风险单元划入 1,000 USDC。它是本例的初始保证金现金余额 `B₀`，不是买入 ETH 的货款，也不是“成本总额”。后续没有追加或提走保证金。
- 开仓初始保证金率取教学值 10%；本例开仓与加仓均已通过订单风险检查和必要预留。保证金梯度、强平算法不在这里另建一套专题，但持仓与风险的输入输出必须闭合。
- 成交数量、价格、手续费及规则版本由已提交的成交／清算输入确定。不是根据用户订单意图或前端成交提示修改持仓。订单部分成交按每笔确定的成交更新，撤单只消除剩余订单资格。
- **手续费单独扣 USDC，不并入入场成本；已实现盈亏默认指毛交易盈亏。** 交易净损益另外表达为毛交易盈亏加已入账资金费净额、减手续费，不能把同一手续费再扣一次。
- 主案例资金费为 0，没有交割结算、自动减仓、清算成交和链上结算。资金费是独立经济事件，不通过修改均价伪造；这些能力的接口见后文。
- Mark Price 只参与未实现盈亏与风险估值。价格更新不改变仓位数量、入场成本和历史已实现交易盈亏。

**与现货的关键区别：** 开 2 ETH 多仓、价格 2,000，并不交割 2 ETH，也不从保证金现金扣除 4,000 USDC 名义本金。仓位名义价值、成本基础、保证金现金与权益是不同量。

### 1.2 贯穿案例

下面是本专题新设的教学序列，不声称是用户项目事实。所有成交均已满足成交资格；主案例的金额恰好能精确落到 USDC 六位小数。

| 步骤 | 输入 | 本步手续费 | 本步应发生的事 |
|---|---|---|---|
| 初始 | 空仓，逐仓保证金现金 1,000 USDC | 0 | 数量、成本、累计毛交易盈亏均为 0 |
| 成交 F1 | 买入 2 ETH，成交价 2,000 USDC/ETH | 4 USDC | 开多仓，不扣名义本金，只扣手续费 |
| 成交 F2 | 买入 1 ETH，成交价 2,300 USDC/ETH | 2.3 USDC | 同向加仓，重新加权入场成本 |
| 成交 F3 | 卖出 1.2 ETH，成交价 2,500 USDC/ETH | 3 USDC | 部分减仓，对关闭部分确认交易盈亏 |
| 估值 M1 | Mark Price 为 2,400 USDC/ETH | 0 | 仅重算未实现盈亏和权益视图 |

逐步结果如下。`C` 是剩余仓位的入场名义成本基础，不是资产余额；`R` 是累计已实现毛交易盈亏；`H` 是累计手续费支出。

| 阶段 | 有符号数量 q（ETH） | 剩余成本 C（USDC） | 入场均价 A（USDC/ETH） | R（USDC） | H（USDC） | 保证金现金 B（USDC） |
|---|---:|---:|---:|---:|---:|---:|
| 初始 | 0 | 0 | 不适用 | 0 | 0 | 1,000 |
| F1 后 | 2 | 4,000 | 2,000 | 0 | 4 | 996 |
| F2 后 | 3 | 6,300 | 2,100 | 0 | 6.3 | 993.7 |
| F3 后 | 1.8 | 3,780 | 2,100 | 480 | 9.3 | 1,470.7 |

F3 的成本释放为 `6,300 × 1.2 / 3 = 2,520 USDC`，毛交易盈亏为 `1.2 × 2,500 − 2,520 = 480 USDC`。卖出不是向用户支付 3,000 USDC 现货卖出款，而是结转平仓损益并扣手续费。

M1 时：

```text
剩余仓位名义价值 = 1.8 × 2,400 = 4,320 USDC
未实现盈亏 U     = 4,320 − 3,780 = 540 USDC
累计净已结转损益 = 480 − 9.3 = 470.7 USDC
逐仓权益 E       = B + U = 1,470.7 + 540 = 2,010.7 USDC
权益增量         = 480 − 9.3 + 540 = 1,010.7 USDC
```

这里的 `B` 是该风险单元的账本现金，不是可提现余额。可划出多少，还要受保证金要求、未成交订单预留、待处理义务与风险策略限制。

### 1.3 主流程：从交易意图到可核对结果

```text
用户提交开仓、加仓或减仓意图
    ↓
订单接入与风险准入
    ├─ 检查账户模式、精度、订单资格
    └─ 依据权威风险状态及在途敞口建立必要预留
    ↓
撮合裁决并持久提交成交事实
    ├─ 未成交部分继续挂单或按订单规则结束
    └─ 已成交部分形成稳定 fill_id、成交价、数量与来源顺序
    ↓
清算入口规范化账户侧成交
    ├─ 绑定账户、市场、方向、手续费及规则版本
    └─ 在保持来源因果顺序的前提下形成可恢复的风险单元事件流
    ↓
持仓结转事务〔本例持仓与账本在同一数据库提交域〕
    ├─ 检查输入身份、载荷、连续序号及旧状态版本
    ├─ 持仓内核计算新数量、成本释放和毛交易盈亏
    ├─ 账本登记毛交易盈亏、手续费及对应平衡分录
    ├─ 按订单结转协议处理相应预留义务，保留未成交部分所需预留
    └─ 一次提交仓位、账本、输入处理记录、检查点与结果 Outbox
    ↓
结转完成〔确定的成交不能因通知失败而撤销〕
    ├─ 向交付方确认已处理，重复输入返回原结果
    ├─ 风险模块获得带仓位／账本版本的状态，管理后续风险与划转资格
    └─ 查询投影按版本更新
              ↓
       估值模块组合仓位快照与有效 Mark Price
              ↓
       展示数量、均价、已实现／未实现盈亏、费用及数据版本
```

上述模块可以是同一 Go 服务中的不同职责，不要求每个方框都是独立微服务。订单准入与持续风险不能依赖任意滞后的页面投影；未结转成交带来的敞口必须在风险预留／在途义务中有归属。

### 1.4 主要分支与失败路径

```text
订单被拒绝／尚未成交就撤销
    → 不产生持仓变化，不产生交易已实现盈亏

订单部分成交后撤销剩余量
    → 已成交部分照常结转；撤销剩余部分不撤回已成交持仓

撮合已提交，账户侧成交暂未送达
    → 成交义务仍在；可靠补发，保留相应风险约束，不按调用超时退款

账户侧事件重复／序号缺口／载荷冲突
    → 重复且载荷相同：返回原处理结果
    → 序号缺口：暂存并补缺，禁止先套用后到成交
    → 同身份不同载荷：隔离告警，不能覆盖旧事实

仓位计算完成，但数据库事务未提交
    → 仓位与账本均不生效；按原身份重试

数据库已提交，但处理确认或页面更新失败
    → 不撤销结转；原结果可查询，通知继续投递，投影继续追赶

Mark Price 停更或越界
    → 保留仓位事实；估值标记无效／陈旧，风险按自身策略限制行为
```

没有可靠提交的计算结果不能宣称“账户已结转”。已经结转的成交也不能因为客户端超时而被作为新成交再执行一次。

### 1.5 完成含义不能混用

| 阶段 | 已经承诺什么 | 还没有承诺什么 |
|---|---|---|
| 订单受理 | 订单意图进入确定的处理流程 | 不保证成交，更不保证有仓位 |
| 成交提交 | 成交事实及其结转义务已经确定 | 持仓、账本、查询不一定已追上 |
| 账户结转提交 | 该成交引起的仓位、损益、费用与处理记录共同生效 | 页面不一定可见，价格也不一定新鲜 |
| 查询更新 | 投影到达指定经济事件版本 | 不能代替风控的实时执行资格 |
| 有效估值 | 指定仓位版本与指定价格证据下的估值可解释 | 未实现盈亏不等于已入账或可提现资金 |

## 二、核心板块：谁决定结果，谁拥有状态

| 核心板块 | 决定什么／为什么核心 | 拥有的状态或产物 | 上下游契约 |
|---|---|---|---|
| 成交与清算输入 | 哪些业务事实有权改变仓位；错误输入会污染全部后续结果 | 成交身份、来源顺序；规范化经济事件 | 上接撮合可靠结果，下交稳定账户侧事件；不能拿订单累计量推算新成交 |
| 持仓计算内核 | 开、加、减、平、反向的数量、成本和毛交易盈亏 | `q、C、R、position_version` 及成本释放明细 | 只消费确定输入与旧状态，不内部读取实时报价或配置 |
| 经济结转协调与账本 | 仓位变化和钱是否共同生效 | 现金、损益与费用分录、幂等记录、检查点 | 持仓提出计算结果，账本产生平衡分录；协调层统一提交 |
| 估值与风险接口 | 账面损益怎样成为可解释估值，以及风险决策是否引用正确状态 | 带证据的估值；风险约束与裁决 | 不让价格流重写仓位；不让查询缓存替代权威风险状态 |
| 交付、恢复与核对 | 重复、乱序、崩溃后经济结果能否保持 | Inbox、Outbox、序号、规则版本、重放证据 | 能定位第一处差异，不能以“最终一致”掩盖丢失义务 |

## 三、核心 20%：优先讲透哪些机制

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 合约口径与成本法 | 计算前 | 决定公式和损益归属 | 混用现货、线性与反向合约公式 | 单位、乘数、单向净仓、加权平均、费用独立 |
| 关旧仓／开新仓分解 | 成交折叠 | 所有状态迁移的共同骨架 | 过零沿用旧成本，减仓重新加权 | 关闭量、新开量、成本释放、清仓归零 |
| 仓位事实与估值分离 | 持仓到估值 | 阻断行情污染经济历史 | Mark 更新导致历史已实现盈亏变化 | 仓位版本、价格版本、派生字段 |
| 仓位—账本共同提交 | 经济结转 | 防止有仓无钱或有钱无仓 | 重复入账、手续费漏扣、损益丢失 | 原子域、双向分录、预留义务、稳定效果身份 |
| 身份、载荷与权威顺序 | 输入及恢复 | 成交折叠不是任意可交换求和 | 重复减仓、成本法错序、无法恢复 | 输入去重、冲突隔离、连续检查点 |
| 精度与结算余数 | 计算到入账 | 数学公式正确不等于金额闭合 | 长期微量漂移、正负数舍入不一致 | scale、位宽、成本尾数、结算余数 |
| 单写权限与崩溃恢复 | 执行与高可用 | 进程内串行不等于持久唯一执行 | 双主写、确认后数据丢失 | Go owner、数据库版本、fencing、提交后发布 |
| 权益桥接与逐事件审计 | 展示和核对 | 判断所有环节是否共同成立 | 只看最终数量，漏掉成本和钱的分叉 | 毛／净口径、费用、价格证据、首个分叉位置 |

“20%”表示决定正确性的核心机制，不是只讲少量术语。资金费率算法、强平价格推导、充值提现流程不在这里完整展开，但它们改变现金、仓位或风险资格时，必须经过明确的经济事件接口。

## 四、共同设计与规则

### 4.1 状态、公式与不变量

以人类可读单位表示：`q` 为有符号 ETH 数量，`C ≥ 0` 为剩余绝对入场成本，`A = C / |q|` 为非空仓均价，`p` 为成交价，`m` 为 Mark Price。

```text
空仓：q = 0 ⇒ C = 0；均价不适用，不把除零结果伪装成有效价格。

空仓开仓或同向加仓：
    q' = q + d
    C' = C + |d| × p
    本笔毛交易盈亏 g = 0

反向成交：
    关闭量 c = min(|q|, |d|)
    释放成本 K = C × c / |q|          〔全部关闭时直接取全部 C〕
    本笔毛交易盈亏 g = sign(q) × (c × p − K)
    新开量 o = |d| − c
    若未平完旧仓：C' = C − K
    若恰好全平：  C' = 0
    若过零反向：  C' = o × p
    始终有 q' = q + d，c + o = |d|

未实现盈亏：U = sign(q) × (|q| × m − C)，空仓时 U = 0。
现金桥接：  B = B₀ + 已入账毛交易盈亏 + 已入账资金费净额 − 手续费净支出 + 保证金净划入。
逐仓权益：  E = B + U。
```

这里的 `d` 是有符号账户侧成交量，买为正、卖为负。纯同向成交的关闭量为 0、新开量为 `|d|`。主例资金费和净划入均为 0；只有在明确这些限制后，才能简写为 `B = 1,000 + R − H`。

必须成立的约束：

1. 每个账户侧成交只影响一次经济状态；数量按权威顺序守恒。交易双方是不同的账户侧事件，不能全平台只用一个 `fill_id` 去重。
2. 成本非负，清仓时成本全部释放；历史损益、费用与审计记录不随空仓清零。
3. 减仓不把成交价重新混入剩余仓位均价；有限精度下展示均价可能出现极小尾差，权威量是数量与成本。
4. 费用单独入账；不在成本里加一次、在账本里再扣一次。
5. Mark Price 变动不修改仓位与账本；未实现盈亏不是现金。
6. 同一前态、输入、顺序和规则版本产生相同后态与效果；纠错必须产生可审计的新记录，不能覆盖历史。
7. 已确定成交是待履行义务。结转时出现负现金或欠款，不能把亏损截成 0、回滚撮合成交或丢弃该笔事件；应记录真实结果并转交风险与债务处理流程。

### 4.2 精度与余数口径

本教学方案固定数量、成交价为六位小数，费用与账本现金为 USDC 六位小数。内部名义成本与毛交易盈亏保留 USDC 十二位小数，不使用 `float64`。

- `q_u = q × 10^6`，`p_u = p × 10^6`，两者乘积就是 USDC 十二位小数的成本整数 `C_u`。
- 部分减仓时，`K_u = floor(C_u × c_u / |q_u|)`，成本尾数留在剩余仓位；全部平仓直接释放全部 `C_u`，不留下幽灵成本。这是本方案显式选择的规则，不是所有协议的通用规定。
- 毛交易盈亏先按十二位小数计算。每个风险单元维护有符号结算余数 `r_u`：将本次毛盈亏加入余数，除以 `10^6` 向零截断得到可入账的 USDC 最小单位，余下部分继续保留。
- 余额使用入账金额，内部毛交易盈亏累计使用原始金额。因此以十二位整数表示时，精确关系是 `累计原始毛盈亏 = 累计已入账毛盈亏 × 10^6 + r_u`，不能在存在余数时直接混用这两个 R。
- 前文的 `E = B + U` 是账本已入账口径的权益；若展示包含未结算尾数的更高精度经济权益，还需加上 `r_u / 10^12 USDC`，并与账本口径区分。风险使用哪一口径也必须固定，不能让不足最小货币单位的尾数被静默当成可划出现金。主例余数为 0，两种口径相同。
- 清仓只清数量和入场成本，不删除尚未达到最小货币单位的结算余数；关闭风险单元需另有明确的余数处置规则。
- 乘法与除法的中间值可能超出 `int64`。Go 实现必须推导范围，使用经检查的宽整数或 `math/big` 等实现；不要因输入能放进 `int64` 就认为乘积安全。

主例所有结转金额都能整除到 USDC 六位小数，`r_u = 0`；所以前面的简化金额表没有隐藏余数。

### 4.3 架构与唯一写权限

```text
撮合：成交事实的生产者
    ↓ 可靠成交结果
清算入口：账户侧输入、费用与规则绑定、顺序持久化
    ↓
逐仓风险单元 owner／结转协调层
    ├─ 持仓内核：只计算 q、C、毛交易盈亏和成本释放
    ├─ 账本模块：现金、毛盈亏、手续费、保证金划转与平衡分录
    ├─ 事务控制：Inbox + 连续检查点 + 仓位 + 分录 + Outbox
    └─ 同一提交域：本例共同数据库事务
              ↓
       版本化经济结果
              ├─ 风险模块：持续风险、后续准入与划转约束
              ├─ 查询投影：读模型，不得旁路改仓或余额
              └─ 估值模块 ← 版本化 Mark Price
```

本例串行化与提交的单元为一个专用逐仓风险单元，即同一子账户、同一市场及其 USDC 现金桶。它与其他逐仓单元不能自动互相抵扣。若改成多个市场共享全仓现金，必须重新设计账户级顺序和原子边界，不能只把数据库键里的市场删掉。

账本为每项用户现金变化登记对应的合约损益清算或手续费等平衡分录。成本 `C` 是持仓计算状态，不是把名义本金转给某个对手方的现金分录。

### 4.4 核心对象与交互

| 对象 | 必要字段 | 权威与用途 |
|---|---|---|
| 账户侧经济输入 | `economic_event_id、fill_id、leg_id、risk_unit_id、market、account_seq、source_seq、signed_qty、price、fee、rule_version、payload_digest` | 确认哪一方的哪次经济变化；哈希采用规范编码，不能随 map 序列化顺序漂移 |
| 仓位 | `position_key、qty_u、entry_cost_u、realized_gross_raw_u、position_version、rule_version` | 持仓模块维护；均价可派生，不反向用显示均价重建成本 |
| 账本及结算状态 | `cash_u、realized_posted_u、fee_total_u、settlement_remainder_u、ledger_version` | 账本模块维护；本例与仓位共同提交 |
| 经济效果 | `effect_id、economic_event_id、type、amount_u、journal_ref` | 按事件和效果类型稳定生成；一项毛盈亏、手续费分别有唯一效果身份 |
| 处理记录与交付 | `Inbox身份与摘要、last_applied_seq、owner_epoch、Outbox记录` | 结转协调层维护，负责重复、恢复与提交后交付 |
| 估值快照 | `position_version、ledger_version、price_id、mark_price、price_time、quality、computed_at` | 估值模块维护；说明这组盈亏来自哪些经济事实和价格证据 |

`account_seq` 在本专题指风险单元内的连续经济事件序号，不是全市场 `source_seq`。过滤其他账户后，市场序号不连续是正常现象，不能误判为本账户丢消息。清算入口必须保持同一市场相关成交的来源顺序，再将规范化输入可靠写入风险单元序列；不能以不同消费者抢到消息的先后随意重排。

### 4.5 相邻模块必须履行的契约

- **订单与风控：** 预留反映未成交订单与在途成交义务；成交结转后按订单级协议转移／释放相应约束，不能按“仓位现在变小”就清掉整个订单预留。Reduce-Only 的成交资格由订单执行侧裁决，结转侧不能事后丢弃已确定成交。
- **资金费：** 显式输入带结算期间、唯一身份、方向、金额与规则版本；现金变化不改入场成本。资金费是否计入某种“净已实现盈亏”必须声明展示口径。
- **强平与其他调整：** 清算成交仍作为带来源的成交输入；额外费用、保险／债务结转分别留痕。持仓服务不自作主张修改风险参数。
- **链上产品对比：** 本基线没有链上终态。若以合约状态为权威，提交、执行、确认与最终性属于不同阶段；观察事件被重组撤回的规则要重新定义，不能把这里的数据库提交直接叫作链上最终结算。

## 七、工程实践：唯一的简洁 MVP

### 7.1 目标与范围

在单风险单元内存状态中，验证**开／加／减／平／反向、费用独立、重复事件无额外效果以及数量—成本—现金闭合**。

不实现数据库、可靠队列、订单风控、强平、资金费、主备或链上最终性；下面的整体状态替换仅表达单进程示例的应用边界，不声称具备生产持久事务能力。

### 7.2 核心伪代码

数量、价格使用六位整数，成本与内部毛盈亏使用十二位整数；`S = 10^6`。整数乘积必须使用足够位宽。状态含 `qty、cost、gross_raw、gross_posted、remainder、fee_total、cash、last_seq、seen`，初始现金为 `1,000 × S`，其余为 0。本示例的 `seen` 不淘汰，仅适用于少量输入。

```text
apply(state, event):
    校验 event 属于本风险单元，按规范载荷重新计算并核验 event.digest
    若 seen[event.id] 已存在：
        若已存摘要 != event.digest：返回“身份冲突”，不修改状态
        否则返回原结果，不再扣费或记损益
    校验数量非零、价格为正、精度、费用非负、规则版本已知
    不合格则停止并报告，不确认已处理
    若 event.seq != last_seq + 1：返回“等待补缺”，不修改状态
    next = state 的独立副本
    q = state.qty; C = state.cost; d = event.signed_qty; g = 0
    若 q == 0 或 sign(q) == sign(d)：
        next.cost = C + abs(d) * event.price
    否则：
        c = min(abs(q), abs(d))
        K = C 若 c == abs(q)，否则 floor(C * c / abs(q))
        g = sign(q) * (c * event.price - K)
        o = abs(d) - c
        next.cost = o * event.price 若 o > 0，否则 C - K
    next.qty = q + d
    next.gross_raw += g
    pending = state.remainder + g
    posted = trunc_toward_zero(pending / S)
    next.remainder = pending - posted * S
    next.gross_posted += posted
    next.fee_total += event.fee
    next.cash += posted - event.fee
    next.last_seq = event.seq
    断言 next.cost >= 0 且 (next.qty != 0 或 next.cost == 0)
    断言 next.gross_raw == next.gross_posted * S + next.remainder
    断言 next.cash == 1000 * S + next.gross_posted - next.fee_total
    result = {事件身份, 新数量, 新成本, 本笔毛盈亏g, 入账posted, 新现金}
    next.seen[event.id] = {event.digest, result}
    整体替换 state = next；返回 result

value(state, mark):
    校验 mark 的市场、正值、六位精度与质量
    U = 0 若 qty == 0，否则 sign(qty) * (abs(qty) * mark.price - cost)
    返回 {U_raw: U, equity_posted_raw: cash * S + U,
          equity_economic_raw: cash * S + U + remainder,
          经济版本: last_seq, 价格身份: mark.id}
```

`value` 不修改 `state`；两个 `equity` 字段分别表示已入账口径与含结算余数的高精度经济口径，都不是可划出金额。伪代码中的费用已经是六位 USDC 整数，不与十二位成本直接相减。未知规则或缺口的输入仍是待解决义务，不能静默丢弃。

独立的最小舍入示例：从零结算余数开始，两次各产生 `0.0000006 USDC` 原始毛盈亏，第一次入账 0、余数 `0.0000006`，第二次入账 `0.000001`、余数 `0.0000002`。这只检查金额转换规则，不替代完整持仓情景，也不允许清仓时删除余数。
