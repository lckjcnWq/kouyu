# 大问题 10：崩溃、主备切换与规则升级后怎样恢复同一经济结果？

## 先看懂：关键词大白话解释

本文适用范围：ETH-USDC-PERP 线性 USDC 永续，ETH 数量、USDC/ETH 价格、乘数 1，单向逐仓、加权平均、费用独立；仓位账本同库提交。内部成本毛盈亏十二位、现金六位，恢复沿历史规则保留余数，不涉及链上最终性。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 内存恢复 | 从权威已提交数据库重新装载缓存 | 不需要再给历史成交记一次钱 |
| 权威库重建 | 用可信快照和完整后续事件构造新库 | 先隔离核验与批准，才可提升为真实写入域 |
| 影子重放 | 为比较或排错另算一份隔离结果 | 不付款、不发生产通知，也不代表已切换线上状态 |
| 快照包含边界 h | 明确快照已经算完到第几笔 | 从 h+1 重放，不按模糊时间戳猜范围 |
| 快照登记清单 | 证明文件完整、版本和摘要可用的登记 | 上传开始或文件可读不等于可用于恢复 |
| 输入—结果证据链 | 序号连到事件、摘要、效果和规则 | 只有哈希没原始数据仍无法重算 |
| 首处分叉定位 | 找重放第一次偏离旧结果的位置 | 不因最终权益相同就放过中途成本与现金错误 |
| 不可变规则目录 | 旧版本参数和算法可定位且不被原地改写 | 事件不能因路由到新机器就换舍入算法 |
| 副作用默认拒绝 | 影子任务启动时阻断真实账本与支付出口 | 只换表名不足以证明不会触及生产 |
| 存储持久承诺 | 数据库确认后故障转移究竟能保留什么 | fencing 挡旧主，却救不回复制策略已丢的提交 |
| 分配屏障 h | 迁移时最后已经发出的业务序号 | 不自动等于最后已应用检查点 k |
| 排空或原位移交 | 移交前完成待办，或连原序号把待办一起交出 | k 小于 h 时不能让新主跳过 k+1 到 h |
| 规则纪元 | 新旧语义正式切换的持久边界 | 未知规则先暂停，不回退到最新默认公式 |
| 恢复可写资格 | 状态核验、义务识别和当前写权都满足 | API 能响应、影子比较完成都不单独构成资格 |

## 把整篇文章压缩成一个故事

小林的 ETH 永续单元完成三笔：二 ETH 买在两千，一 ETH 买在两千三，一点二 ETH 卖在两千五。第三笔释放二千五百二十成本，毛盈利四百八十，三笔费用共九点三。数据库把数量一点八、成本三千七百八十、现金一千四百七十点七以及第三笔处理结果、检查点三一并提交，进程却在发送确认前崩溃。启动成功还不等于可以直接接着改仓。

接管者先从一致数据库快照恢复缓存，核对 Inbox、分录、余数零和序号三，再取得当前持久写权限。上游重送第三笔只能返回旧结果，不能重复加四百八十或扣三。若只是重启内存，不必重算已提交账务；若数据库本身须重建，就要取得精确快照边界、后续完整事件和历史规则，在新库逐事件核对，不能靠最新页面均价倒推成本。

恰逢规则升级与分区迁移，处理方在序列分配处建立屏障。屏障表示最后已分配，不必等于最后已应用：若能排空至屏障再移交，就从下一号开始；若无法排空，快照只含实际检查点，尚未应用事件必须连原身份、摘要、规则与序号完整交出。旧主由存储代次拒绝，新主沿旧事件绑定的旧算法继续，不能重新编号或把结算余数置零以图方便。

为排查升级差异，处理方可以固定清单做影子重放，但须禁用真实账本、支付和通知出口，比较完成不是执行授权。若历史算法确实错了，要保留原账、重述影响并审批当前更正，已经划出的现金不会因重放自动追回。恢复经济状态后才组合两千四的 Mark，得到浮盈五百四十、权益二千零十点七；当前行情不能改旧盈利。事件、规则或快照证据缺失时，小林单元保持受限，而不是用“服务已启动”冒充无损恢复。

**流程位置与独立机制：** 本题跨越持久提交、进程恢复、数据库重建、影子重放、主备接管和规则升级。独立重点是区分内存缓存恢复与权威状态重建，定义检查点和快照对应的精确输入边界，保留历史规则及舍入余数，并阻止旧写者或影子结果污染真实账本。

**必要前提：** 沿用链下线性 USDC 永续、单向净仓、逐仓、加权平均、乘数 1、费用单列，以及持仓与账本同数据库事务。主例 F1/F2/F3 顺序应用后为 `q=1.8、C=3,780、A=2,100、毛已实现=480、费用=9.3、B=1,470.7`；Mark 2,400 下 `U=540、E=2,010.7`。

数量、成交价六位；成本与原始毛盈亏十二位；部分成本释放向下取整，全平释放全部成本；现金六位，毛盈亏向零截断并保存有符号余数。清仓不删除余数。资金费、净划入和链上结算不在主例中，若出现必须作为单独事件类型处理。

恢复后仍要遵循：输入身份与载荷摘要一致、同一风险单元权威顺序连续、仓位与账本共同提交、检查点与 Inbox/Outbox 一致。数据库事务提交不是链上最终性。

## 第 1 层：进程重启后，你说“恢复”具体是恢复哪一种状态？

**面试官：** 结转服务崩溃重启，持仓 owner 内存里原来有仓位和 `last_seq`。你会恢复这个 Go 状态、数据库状态还是重新计算？这三件事有什么不同？

**面试者：** 我会先把“恢复”拆成三类，避免一个词掩盖不同数据来源与承诺。

第一类是**进程内存恢复**：服务重启后从权威数据库读取已经提交的仓位、账本、检查点与必要规则上下文，重建 owner cache。通常不必重新计算已提交历史。

第二类是**权威数据库状态重建**：目标数据库丢失、迁移或需要从快照和持久事件构建新库。这需要完整的已提交快照、其后事件和历史规则，结果会与账本和效果记录核对。

第三类是**影子重放**：为了排查错误或评估新规则，在隔离的命名空间／数据库里按历史输入计算另一份状态，与线上结果比较。它不是线上恢复，也不能生成真实资金效果。

主例运行中，F3 的事务已提交但进程在确认前崩溃，首选读取数据库中的 `q=1.8、C=3,780、B=1,470.7、last_seq=3` 与 F3 的 Inbox 结果。再沿原事件身份确认或派发 Outbox，而不是重新对 F3 扣一次 3 手续费。

若事务实际未提交，仓位、账本、Inbox 与检查点都不存在该笔变化；重启后从已提交的序号继续应用 F3。若提交调用超时而状态未知，先查询 Inbox／事务结果，不凭网络错误假设必定回滚。

数据库状态重建时，需要证明重建边界和输入范围；影子重放则需要说明比较对象、规则版本和无副作用隔离。三者可以共用纯计算内核，但不能共用“直接写真实账本”的执行路径。

恢复也不等于重新估值。Mark Price 会变化，当前估值可以在恢复经济状态后重新计算；仓位数量、成本、历史已实现盈亏与现金不应因当前 Mark 改变。

## 第 2 层：如果数据库中的仓位记录也损坏，怎样从持久事实重建？

**面试官：** 假设你不仅重启进程，而是仓位表某段状态丢失，需要从历史重建。只保存所有成交 ID 和最新均价是否足够？账本能从仓位反推出吗？

**面试者：** 不够。重建要依赖可验证的期初状态和之后的完整规范事件，而不是最新展示字段。至少要保留已提交成交及其他经济事件的身份、规范载荷、账户侧序号、规则版本和可追踪来源。

可恢复快照不能只存 `q` 和 `A`。需要 `q、C、累计原始毛交易盈亏、累计已入账毛盈亏、费用、现金、资金费与净划入分类、结算余数、last_applied_seq、规则版本、仓位／账本版本、owner_epoch`，以及快照摘要和构建时间边界。

平均成本下 `C` 是权威值，`A` 是除法派生视图。展示均价可能因格式取整，不能 `A×|q|` 重建成本；清仓期间的 `C=0` 也不能让历史 `R、费用、现金、余数` 自动归零。

账本不能只由仓位反推。仓位可说明毛交易盈亏计算状态，却不包含费用、资金费、保证金转账、人工更正、平衡分录、付款义务或实际现金结转历史。账本重建要有自己的分录流与效果身份，并通过经济桥接核对仓位输出。

事件源应覆盖所有会影响目标风险单元状态的已确认事件类型：账户侧成交、费用效果、资金费、保证金划转、获批更正等。事件只有成交而遗漏独立现金事件，最终仓位可能正确，现金仍然错误。

重建程序先在新表或隔离库构造结果，逐序号核验输入连续性、摘要与唯一效果，再与账本分录、外部转账确认和控制总额比对。只有经过完整校验与切换审批，才能把新库提升为权威写域。

若缺少事件、规则或余数证据，重建就不是完全可证明的。应标记缺口、冻结受影响操作并通过审计决策补充证据或形成更正，不得用“最新均价大致相同”填平未知历史。

快照与后续事件还要有明确的包含关系，例如快照标明已包含到风险单元序号 h，重放必须从 h+1 开始。不能仅按时间戳切片，因为并发事务的提交时间和消息业务顺序不必一一对应。

## 第 3 层：检查点和快照怎样证明没有漏一笔或重复一笔？

**面试官：** 你说快照包含到 h。若快照文件写完而事务检查点先推进，或反过来，崩溃后怎么知道从哪里开始？如何把仓位、账本和输出通知对齐？

**面试者：** 在主基线里，权威检查点 `last_applied_seq` 与仓位、账本、Inbox 处理结果及 Outbox 都在同一数据库事务提交。它们不会合法地独立前进，所以进程恢复读取到的是同一个经济提交边界。

每笔事件的事务顺序是：锁定风险单元控制行并校验 epoch；验证 Inbox 身份、载荷摘要、连续序号和规则版本；读取旧仓及账本；计算 next state；写仓位、分录、效果、Inbox 结果、检查点与 Outbox；一次提交。

事务提交失败时，上述持久字段都不推进。提交成功但确认丢失时，它们都已经推进，重试原身份返回保存结果。Outbox 派发在事务后可重复，消费端仍按稳定输出身份处理。

如果快照作为数据库以外的文件生成，它不天然与数据库事务原子。可以在一致数据库快照上读取固定的版本／序号边界，生成内容后写清包含边界、摘要和状态版本，再将快照登记为可用；启动时校验快照清单与对应数据库日志／事件偏移的关系。

快照尚未登记完成就崩溃，则把它视为未完成文件，不用猜测其序号。登记完成的快照如果缺少后续事件，需要从权威输入源补齐；补齐不到则不能声称完整恢复。

若采用数据库原生日志备份或一致性快照，遵循其写前日志与事务一致性机制，但仍要核验事件检查点、账本版本和规则目录。备份文件可读不意味着其外部队列偏移也和数据库状态原子对齐。

对每个事件保留输入身份和结果摘要，可以在恢复后核验 `seq→event_id→payload_digest→effect_id` 的链条。摘要有助于检测不一致，不替代原始输入和规则本身；只有哈希而无数据，无法重新计算。

快照的更新采用版本化文件／对象与明确登记，避免覆盖上一个可用快照。切换读取最新的完整且经验证版本；不可把上传开始时间当成快照完成时间。

## 第 4 层：怎样证明重放结果与线上逐事件一致，而不是只比最终余额？

**面试官：** 重放到序号 100 万后，最终现金和权益都相同，是否就可以宣布恢复正确？如果中间一笔的已实现和未实现刚好互相抵消呢？

**面试者：** 不可以。最终汇总相同可能掩盖成本、损益归属、费用和序号错误。应对每个输入边界比较完整的经济状态与效果，并定位首个分叉事件。

校验至少包含：`q、C、原始毛盈亏、已入账毛盈亏、结算余数、累计费用、资金费、划转分类、现金、last_applied_seq、仓位版本、账本版本`。账本侧还比较每个事件的分录行、稳定效果身份、借贷平衡和关联引用。

主例错序反例足以说明汇总权益不够。正确序列 F1→F2→F3 在 Mark 2,400 下为 `q=1.8、C=3,780、R毛=480、B=1,470.7、U=540、E=2,010.7`。

若 F1→F3→F2，仍有 `q=1.8`，却变成 `C=3,900、R毛=600、B=1,590.7、U=420`，最终权益也刚好是 `2,010.7`。只检查最终权益会漏掉 120 的实现归属差异与风险输入变化。

逐事件差异报告应指明期望输入、实际输入、规则版本、旧状态、计算明细、新状态、对应账本效果和余数。这样才能区分顺序差异、输入污染、规则差异、账本漏记和恢复缺数据。

对大规模历史可以按经验证的快照边界分段比较，并保留每段状态摘要与事件清单；摘要只是快速定位工具，一旦不匹配仍要展开到差异事件。摘要一致也不能替代抽样或规则正确性的证明。

交叉校验要有独立账本桥接：主例限制下 `B=1,000+已入账毛盈亏−手续费`，扩展场景则显式加资金费净额、净划入和获批调整。原始毛盈亏与已入账金额还需满足六位转换关系 `raw=posted×10^6+remainder`。

Mark 快照要分开比。历史仓位与账本重放不能依赖当前 Mark；若要重现历史风险裁决或对客历史估值，则需要当时的价格身份、时间、质量和风险规则证据。

## 第 5 层：影子重放为什么不能直接再跑一遍生产账本？

**面试官：** 那最简单的排查方式是复制生产数据库后重新消费历史事件。若消费代码会记账、发 Outbox、触发提现或通知，有哪些副作用必须隔离？

**面试者：** 影子重放必须与生产经济效果隔离。它的输出是比较证据，不是第二份真实账本，也不应被任何下游当作已结转事实消费。

我会把重放输入固定为一个不可变清单：风险单元、快照边界、截至序号、事件 ID 与载荷摘要、规则版本集合、代码构建版本和目标数据库标识。运行期间追加到线上新事件的处理范围要由固定截点 h 界定；h 之后的输入不属于这次比较。

影子存储使用独立数据库、schema 或强隔离命名空间，并使用不同的凭据与效果 ID 前缀。生产账本写入、支付渠道、Outbox 消费、用户通知、订单风险命令和保证金转账都必须关闭或被访问控制拒绝。

只把生产数据库克隆后换个表前缀并不必然安全：环境变量、队列地址或全局 ID 生成器仍可能指向生产。重放程序要以默认拒绝方式禁用外部副作用，并在启动时验证目标隔离身份。

重复历史输入在影子库可以产生影子效果，但这些效果只能供比较、不能对外履行。若在生产库用同一效果身份测试，唯一键冲突可能看似幂等；若用不同 ID，则可能重复记钱，两种都不是安全的影子重放。

要评估新规则 v2，可以在同一固定事件清单上跑“历史规则重现”和“候选规则影子结果”两个隔离分支。前者检查能否复现原结果，后者量化规则变化影响，不应悄悄把候选结果写进线上当前仓位。

若业务决定采用候选重建结果，应进入正式迁移和审批过程：冻结或屏障住输入边界，比较差异，生成获批状态迁移和经济更正，再执行一次受控切换。影子报告本身不是执行授权。

历史 Mark 允许和当前 Mark 不同。影子引擎应只对持仓与账本重算使用确定事件；若输出历史估值，读取同一历史清单里的价格证据，否则明确不比较估值字段。

## 第 6 层：规则升级后，旧成交重放要用新代码还是旧规则？余数如何处理？

**面试官：** 现在成本释放或舍入规则升级。新版本跑历史事件可能得到不同的成本和现金；为了代码简单，能不能让所有事件统一套当前规则？

**面试者：** 不能。每个经济输入必须绑定当时适用且不可歧义的规则版本。新代码重放旧数据时，要么调用可用的历史规则实现，要么以可审计方式证明新实现与旧规则在该输入域等价；不能默认当前配置回溯生效。

规则版本至少需要可定位的代码／算法标识和业务参数：数量、价格、金额精度；成本释放舍入；毛盈亏正负截断；费用口径；资金费期间算法；允许的输入范围。版本号相同却参数可被原地改写，仍无法可靠重放。

主例 F3 部分减仓按 `K=floor(C×c/|q|)` 释放成本。若新版本改为四舍五入，历史 C、毛盈亏及后续成本状态可能不同。历史重放须用旧规则，除非该事件明确经过规则迁移并留下迁移事实。

数值余数同样是状态，不是计算器内部临时变量。累计原始毛盈亏的十二位单位与六位账本金额满足 `原始值=已入账值×10^6+有符号余数`。快照、事件或恢复代码丢掉余数，会改变未来某笔刚好跨过一微 USDC 的入账时点。

举例从零余数起，两次各产生 `0.0000006 USDC` 毛盈亏：第一次入账 0、余数 `0.0000006`；第二次入账 `0.000001`、余数 `0.0000002`。若恢复后余数被置零，第二次就入账 0，现金少一微单位；短期最终数量完全相同。

清仓时 `q` 与 `C` 归零，但余数属于累计交易损益结算状态，不随仓位消失。风险单元关闭或迁移时要使用明确的余数处理规则，不能把它塞进最后一笔费用或在重放中静默删除。

恢复计算不读取当前行情，不查当前手续费率，不用处理时间决定规则分支。成交输入应包含已确定的价格、数量和费用；规则目录应可按不可变版本取回。计算环境升级也要注意整数溢出、编译目标和序列化兼容。

新规则上线可按生效序号或明确业务时间边界切换。需要选择按事件持有版本，还是在新纪元前先完成状态迁移；任何方式都要证明一个事件恰好由一个规则解释，不在重试时因配置变化改变结果。

## 第 7 层：主备切换时的 fencing 和持久承诺怎样与恢复配合？

**面试官：** 新主读到检查点 500，就开始处理 501。但旧主因网络分区没有停，稍后恢复并提交另一份 501；或者数据库故障转移丢了已确认的 500。你靠什么阻止两种情况？

**面试者：** 两类问题分别是执行资格与存储持久性，需独立处理。fencing 能让旧主失去写资格，但不能让数据库复制策略凭空保留已丢的数据。

每个风险单元或持久分区有单调递增 `owner_epoch`。新主接管时在数据库控制记录上提升 epoch；每个结转事务都在同一控制行的锁定／条件更新范围里核验 epoch，再校验 `last_applied_seq`。旧主即使进程仍活着，也不能提交过期 epoch 的事务。

接管竞争要有确定点：若旧事务先拿到控制行锁，它提交或回滚后新主才能提升 epoch；若新 epoch 已提交，旧主之后必须失败。仅在事务外读取 epoch 后就长时间计算并提交，存在检查与使用之间的竞态。

序号条件阻止两个有效写者都把 500 推进到 501；事件唯一键与 Inbox 载荷摘要进一步区分同一输入重试和身份冲突。旧主提交被拒后需丢弃本地推测态，重新从权威状态加载。

持久性方面，应用只有在数据库给出符合承诺的提交确认后才能向上游确认经济结转。若数据库在故障切换时可能丢失已确认事务，就必须把该复制配置的风险纳入承诺；高风险窗口可暂停接管／写入或选择更强持久性设置。

恢复时不能将外部消息队列 offset 单独当作唯一检查点，除非队列位点与数据库事务有明确原子协议。常见做法是允许至少一次重投，通过数据库 Inbox 与账户序号去重；提交后再确认消息。

如果提交成功、队列确认前崩溃，消息会重送，但 Inbox 返回原结果；如果确认先于数据库提交，随后崩溃就可能永久丢事件。因此确认次序是持久义务的一部分。

数据库事务的 ACID 提交只定义该链下存储域的承诺，不是区块链上的不可逆最终性。若产品依赖智能合约状态，必须另行处理链上 nonce、重组、确认深度与最终性，不把 DB 事务提交命名成链上最终结算。

## 第 8 层：代码升级和分区迁移期间，如何保证同一个事件不会被两套规则执行？

**面试官：** 你解决了旧主 fencing。现在要部署规则 v2，部分实例已升级，部分还在旧版本；分区还可能迁移。怎样避免同一序号一会儿用旧公式，一会儿用新公式？

**面试者：** 规则选择要由持久经济状态决定，不能由负载均衡器把重试请求发到了哪台机器决定。事件一旦绑定规则版本，重试和接管都沿用该版本。

如果 v2 仅是计算实现优化且能证明与 v1 对所有有效输入逐位等价，可以用差分向量和范围证明支持滚动部署；事件仍记录所适用的语义版本和实现构建标识，差异被发现时能还原实际代码路径。

如果 v2 改变舍入、成本释放、费用口径或资金费规则，就不是透明实现升级。可选择让旧风险单元继续用 v1 直到明确边界，再将新事件切换到 v2；或者在切换前执行经审批的状态迁移，并把新纪元及起始序号持久记录。

迁移一个分区时，先在序列分配控制行上持久建立屏障 h：冻结旧 owner 的新序号分配，并把后续到达的来源事件持久暂存为尚无最终 account_seq 的输入；h 是屏障时刻最后已分配的 account_seq，不是自动等于最后已应用序号。然后选择且只选择以下一种移交方式：A）旧 owner 将所有已分配的 h 以内事件排空并提交，确认 `last_applied_seq=h` 后，在同一一致快照中移交 h；新 owner 从 h+1 开始；B）若无法排空，则取实际已提交的检查点 k（`k=last_applied_seq<h`），快照明确只包含到 k，并连同原身份、载荷摘要、规则版本和原 account_seq 一并移交全部未应用的 `k+1..h` 事件；新 owner 从 k+1 按原序应用，不能重新编号或只移交一个“待处理”标记。提升 epoch、持久切换分区归属后，解除序号分配冻结，由新 owner 先处理移交队列，再按来源权威顺序为暂存输入分配后续序号。若事件身份、顺序或规则证据不完整，保持该分区停止写入并修复证据，不跨边界猜测。任何情况下，快照检查点表示已应用经济状态，不能用输入移交屏障替代。

分区映射不能是各进程独立计算却版本不同的临时哈希配置。路由表或映射纪元应持久、可核对，提交控制行也校验当前 owner epoch／分区纪元，避免旧映射的实例继续写。

部署期间未知规则版本的输入应暂停并告警，不可回退到默认最新公式。等待历史规则载入会增加延迟，但比生成无法复现的资金结果更可控。

如事件保存的是已确定的毛盈亏金额而不是只保存原始成交，则需明确哪个服务负责计算以及如何审计该金额；仅保存金额可能失去独立重算能力。比较好的证据通常同时保留原始成交、规则版本、成本释放明细和结果摘要。

升级完成后，核验所有活跃风险单元都处在登记的规则纪元，未处理输入没有跨边界歧义，旧版本代码在仍有旧事件需要恢复前不能删除。保留期由恢复与合规要求决定，不应因在线流量已切到 v2 就立即移除 v1。

## 第 9 层：如果历史规则本身错了，能不能按新规则重放并覆盖当前状态？

**面试官：** 审计发现旧规则把负数毛盈亏向负无穷舍入，正确规则应向零截断。重新计算所有事件会改变现金。是否直接把历史分录和仓位覆盖成新结果？

**面试者：** 不能覆盖。这里已经不是“恢复原系统历史”，而是更正错误经济事实并调整当前状态。要保留两条可解释路径：当时系统依据什么规则产生旧结果；现在经审批决定产生什么更正结果。

第一步冻结影响范围，登记错误规则版本、起止事件边界、适用风险单元、受影响用户和金额口径。用隔离重放计算旧规则实际结果与拟采用规则结果，逐事件列出差额及其对后续成本释放、毛盈亏、现金、余数和风险历史的影响。

不得把新规则全局应用于所有历史事件后只比较最终现金。新的早期成本会影响后续释放，正负舍入还可能改变余数跨越边界的时点；需要从最早分叉重新推演至当前截点。

正式更正方案应由业务、财务／账务、风险与授权角色审阅，明确哪些状态需要迁移、哪些现金差额构成应收应付、哪些外部转账或对客账单已经发生，以及如何处置负余额。修复身份关联原始输入、旧结果、重述规则、审批与新状态。

执行在受控屏障内进行：校验当前序号、epoch 和前态摘要；以一次同库事务写入被批准的新当前仓位状态、调整分录、原始／已入账毛盈亏、费用或余数变化、更正审计记录、迁移检查点和 Outbox。不能跳过同库仓位与账本共同提交。

旧分录保留，不删除或改金额；新分录提供明确的冲正／差额关系。查询可以展示“原记账”和“经更正当前口径”两个视角，避免用户历史账单无从解释。

若影响已发生提现，影子重放不会自动追回资金。要建立应收、债务或独立追收处理，并由产品和合规规则决定；不能把用户已经收到的链外资金当成重建时可以抹掉的字段。

之后新事件从新的规则纪元和当前状态继续。重试更正事件时返回原更正结果；身份载荷冲突要拒绝。更正自身也需要唯一身份、顺序、审批证据和 Outbox，不能因“这是后台修复”豁免幂等与审计。

## 第 10 层：什么条件满足时，你才会说恢复完成？

**面试官：** 你已经描述了很多检查。最后给出一个清晰的恢复完成定义：服务进程起来、API 能响应就算恢复吗？你会验证哪些主例数值，又有哪些结果仍然不能宣称？

**面试者：** API 能响应只说明进程可用，不代表某个风险单元具备安全写入资格。我会定义恢复状态至少有“读取中、待核验、可读、可写、受限”这些阶段，并说明各阶段允许的操作。

一个风险单元变为可写前，应完成一致读取或通过指定快照与完整事件重建；确认快照边界、序号连续性、输入身份和规则版本可解析；核验仓位、账本、效果及余数不变量；取得当前持久 owner epoch；并确保待处理义务和队列积压已被识别。

若仍有不可解释的序号缺口、规则版本未知、快照摘要不符、分录失衡或 owner epoch 冲突，应停止该单元写入并隔离。其他互不相关风险单元可按隔离域继续服务，但不能将受影响单元伪装成正常。

主例恢复检查的权威结果是：F1、F2、F3 各处理一次；`q=1.8、C=3,780、A=2,100、累计毛交易盈亏=480、累计费用=9.3、B=1,470.7、余数=0、last_seq=3`。指定 Mark 2,400 的估值再得 `U=540、E=2,010.7`，并保留 Mark 身份与质量信息。

如果从 F3 后的恢复状态重复收到同身份、同载荷的 F3，返回原结果，所有累计项不变。相同 F3 身份但价格改为 2,600，要报告载荷冲突。收到序号 5 而 4 缺失，保持 5 待处理，不推进检查点。

影子重放要明确标作“比较完成”，不等价于生产状态已切换。数据库重建通过全量账本对账与切换批准后才是新权威库；普通进程内存重建完成后仍须取得 fencing 写权，不能仅凭数值匹配接管。

恢复完成后 Outbox 可能仍有投递积压，查询投影可能尚未追上。只要这些状态明确、可重试、不会影响经济事实或风险安全，服务可以按策略提供受限读写；若风险裁决依赖滞后投影，则新增风险与划出应被限制。

最终汇报应区分已验证范围：例如恢复了内存 owner、核对到序号 h、仍有 N 个待处理事件、影子差异为空、Outbox 尚在追赶。没有真正执行数据库故障切换或历史重放时，只能讲设计检查，不得虚构实测无损恢复或零停机。

## 本题收束

### 已经讲透的机制

- **三类恢复有不同目标：** 重启重建内存、重建权威数据库、隔离影子重放不能混称。
- **恢复边界可验证：** 同库仓位、账本、Inbox、连续检查点和 Outbox 共同提交；快照必须声明精确包含的序号及摘要。
- **历史计算证据完整：** 原始事件、规则版本、成本释放、费用、余数和效果身份共同支持逐事件重算；当前 Mark 不改经济历史。
- **影子与生产隔离：** 固定事件清单、独立存储和默认拒绝外部副作用；比较结果只有经审批的迁移流程才能成为当前状态。
- **高可用和升级各有边界：** 存储侧 epoch fencing 阻止旧主，持久性设置保住已确认提交；规则变更要用明确纪元与屏障切换。
- **历史纠错追加记录：** 重述不覆盖旧分录；需要完整后缀推演、授权差额和同库迁移，并处理已发生的外部现金效果。

### 最容易答错的边界

1. 将最新缓存均价当恢复源，或只凭最终权益、余额判断重放正确。
2. 把队列 offset、数据库检查点和快照边界当作同一个自动原子值。
3. 用新规则重算旧事件却不保存旧规则，或恢复时把余数置零。
4. 在生产库直接重放历史，触发第二遍账本分录、Outbox 或真实转账。
5. 认为租约到期或旧进程被摘流量就能阻止它写数据库。
6. 把数据库事务提交称作链上最终性，或宣称数据库故障切换能恢复已被存储层丢弃的提交。
7. 用现金差额补偿历史错仓，却不重建成本、损益归属、余数和后续状态。

### 一个能检验方案的反例

恢复 F3 已提交但确认丢失的时点：进程重启应从同一事务看到 `last_seq=3、C=3,780、B=1,470.7`，重送 F3 返回原结果。若已恢复 `last_seq=3` 却缺少 F3 的 Inbox 记录，序号 3 不满足下一笔必须为 4 的条件，不能再次结转；此时无法直接返回原处理结果，应隔离并从可靠记录补证，不能把“未查到 Inbox”当成未处理。只有检查点也错误回退、连续序号校验被绕过等防线进一步失效时，才可能重复实现 480 并再次扣 3。若只恢复现金不恢复成本，Mark 2,400 下 U 会错误；若规则版本缺失，重放可能用新舍入改变后续现金。合格恢复必须同时通过身份、顺序、规则、余数、账本与 fencing 核验。

本文提供设计检查与手工推演，没有执行主备切换、历史数据库重建、影子重放或规则迁移测试。
