# 大问题 1：从一笔成交开始，持仓、成本、盈亏和账户怎样形成完整结果，状态归谁？

## 先看懂：关键词大白话解释

本文适用范围：ETH-USDC-PERP 线性 USDC 永续，数量为 ETH、价格为 USDC/ETH、乘数为 1；单向净仓、逐仓、加权平均成本，费用独立，仓位与账本同数据库提交，主例无资金费和追加划转。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 交易意图与成交事实 | 想买卖和真的成交是两回事 | 只有已确定成交才能推动本题的仓位结转 |
| 状态归属 | 每类事实由谁负责决定 | 撮合管成交，持仓管数量成本，账本管钱，风险管资格 |
| 入场名义成本 | 合约损益计算的起点金额 | 开二 ETH 得四千成本，不是支付四千货款 |
| 保证金占用 | 为承受敞口而限制可用额度 | 教学初始保证金率 10%，不是再次扣走同额现金 |
| 派生估值 | 用已有事实和价格算出的读数 | Mark 更新不反写仓位或历史交易盈亏 |
| 关闭旧仓／开新仓 | 把反向成交拆成两个连续用途 | 卖出超过旧多仓时，超额部分才建立新空仓 |
| 账户侧 leg | 一笔成交落实到某一方的那条结果 | 买卖双方分别去重，不能共享一个全平台完成标记 |
| 非交换折叠 | 换处理顺序可能改变成本与已实现盈亏 | F3 抢在 F2 前会把已实现盈利从 480 变成 600 |
| 提交控制行 | 整个风险单元共同争用的持久门闩 | 空仓也要能锁，不能仅锁碰巧存在的仓位行 |
| 平衡分录 | 用户现金变化有对应的账务另一侧 | 盈亏和费用分别记账，不只改余额数字 |
| 完成阶段 | 受理、成交、结转、可见各有不同承诺 | 页面落后不撤销已提交结转 |
| 版本令牌 | 告诉查询至少要追到哪笔经济结果 | 可等待投影追上，不拿老页面批准划出 |
| owner_epoch 与 fencing | 新主接管后阻止旧主继续写的代际门禁 | 必须在存储提交处校验，channel 不能替代 |
| 逐事件差分 | 从第一笔起比对每个后态和效果 | 最终数量与权益相同也不能证明现金和成本正确 |

## 把整篇文章压缩成一个故事

小林在一个 ETH 永续逐仓单元存入一千 USDC，先以两千买二 ETH，再以两千三买一 ETH。撮合提交成交后，清算入口才把价格、数量、费用、身份和顺序交给持仓结转。此时数量三、入场成本六千三、均价两千一，扣去四和二点三的费用，现金九百九十三点七。成本不是现货货款；保证金要求是风险约束，也不是再扣一遍本金。

接着小林以两千五卖一点二 ETH。内核从旧成本释放二千五百二十，确认毛盈利四百八十，剩余一点八 ETH、成本三千七百八十。协调层不只更新仓位，还把盈亏、三 USDC 手续费、平衡分录、输入处理档案、检查点和待发通知同事务提交。现金因此增加四百七十七，成为一千四百七十点七；如果事务未提交，这些变化就都不能对外生效。

偏偏提交后进程宕机，页面还显示三 ETH，上游又重送减仓成交。新主须先取得持久写权限，读取共同提交的仓位与账本，再凭原身份返回旧结果，而不是重复减仓扣费。通知可继续重投，页面可按版本追赶，但小林不能凭旧页面拿到划出许可。恢复内存也不能用显示均价倒推成本，更不能遗漏结算余数或改用今天的舍入规则。

后来用两千四的标记价估值，未实现盈利五百四十、权益二千零十点七，却不意味着现金又增加五百四十。核对时还要警惕一个陷阱：若减仓错排到加仓前，数量和权益仍可能相同，但已实现盈利六百、成本三千九百、现金一千五百九十点七已经错了。小林这笔事只有在顺序、持仓、账本、恢复证据都闭合后才算讲清，不能用最终总额相等掩盖中途分配错误。


## 第 1 层：请从用户交易讲到持仓、损益与账户结果完成

**面试官：** 在一个永续合约交易系统里，用户开仓、加仓后再部分平仓。你如何从头到尾解释这笔业务？不要先列组件，说明业务经过谁、状态在哪里变化，以及什么时候才算完成。

**面试者：** 我会先说明产品和结转口径：在这个模型中，交易的是 USDC 线性永续，不是买卖现货 ETH。用户的保证金现金为 1,000 USDC；仓位成本表示合约的入场名义成本，不是已经支付给卖方的本金。

完整流程从用户意图开始，但只有确定成交才有权改变仓位：

```text
用户下单
    ↓
订单接入校验，风险模块检查资格并保留必要保证金／在途敞口约束
    ↓
撮合按照订单规则裁决，持久提交成交
    ↓
清算入口形成带账户、市场、成交身份、顺序、价格和费用的经济输入
    ↓
结转协调层读取该风险单元的旧仓位和账本状态
    ↓
持仓内核算新数量、剩余成本、成本释放和毛交易盈亏
    ↓
在同一事务中提交仓位、账本分录、输入处理记录、检查点和结果通知记录
    ↓
风险与查询按版本接收结果，估值模块再组合 Mark Price
```

沿用统一案例：F1 买 2 ETH@2,000，费用 4 USDC，得到多仓 2、成本 4,000、均价 2,000，现金从 1,000 变为 996。不是扣掉 4,000 USDC 名义本金。

F2 再买 1 ETH@2,300，费用 2.3，得到多仓 3、成本 6,300、均价 2,100，现金为 993.7。开仓和同向加仓没有实现方向性的交易盈亏，只有本例的费用扣款。

F3 卖出 1.2 ETH@2,500，费用 3，只关闭旧多仓的一部分。释放成本 2,520，确认毛交易盈亏 480，留下多仓 1.8、成本 3,780、均价仍为 2,100。账本现金增加 `480 − 3 = 477`，变为 1,470.7。

最后，Mark Price 为 2,400 时，未实现盈亏为 `1.8 × (2,400 − 2,100) = 540`，逐仓权益为 2,010.7。这里的 540 只是估值，不是又给现金加了一笔钱。

完成条件要分层表达：订单已受理不代表成交；成交已经确定不代表账户已经结转；仓位与账本共同提交后才算本风险单元的经济结转完成；页面可见和价格新鲜又是后续阶段。不能因为页面没刷新就撤销成交，也不能因为撮合函数返回就宣称资金已完成。

对于失败分支，订单未成交就被拒绝或撤销，不产生仓位；部分成交后撤剩余量，保留已成交结果；成交已提交但结转失败，保留义务继续重试；结转已提交但通知失败，不再改一次经济状态，只继续交付同一个结果。

## 第 2 层：你提到了多个模块，究竟谁有权修改哪些状态？

**面试官：** 你说撮合、持仓、账本、风险和查询都要参与。假如它们都能更新一张 `positions` 表，各写自己需要的字段，会有什么问题？你会怎样分配权威状态和写权限？

**面试者：** 我不会按“哪个模块需要读仓位”分配写权限，而会按“谁有权产生这一类事实”分配。读者可以很多，决定事实的写者必须明确。

在这个模型中，职责分为五类：

1. **撮合拥有成交事实。** 它决定 F3 是否发生、价格和数量是什么、与其他成交的先后关系是什么。持仓服务不能依据页面订单状态自行补造 F3，也不能因为余额暂时异常就宣布它没有发生。
2. **持仓模块拥有仓位计算状态。** 包括有符号数量、剩余入场成本、累计原始毛交易盈亏和仓位版本。它只能消费已确认的成交和允许的显式调整输入，不接受任意字段覆盖。
3. **账本拥有资金事实。** 包括现金、已入账毛交易盈亏、手续费、资金费和保证金划转分录，以及结算余数。持仓模块算出“本笔应实现 480”，账本决定如何把这个确定金额按规则登记为平衡分录。
4. **风险模块拥有风险裁决。** 它依据指定仓位、现金、订单预留、在途成交与价格证据，判断能否新开仓、划出保证金或进入风险处置。它不能为了让风险率好看，直接改数量、均价或现金。
5. **估值与查询拥有派生视图。** 它们组合指定版本的经济状态与价格，生成未实现盈亏和页面数据，但不能反向把计算结果写成新的仓位事实。

这里“各模块拥有”不意味着各有一台独立数据库。我的基线把持仓与账本放在同一个数据库提交域，由结转协调层调用两者的受控接口，在一个事务内共同提交。逻辑上各自有写权限，物理上可以同进程、同事务。

如果大家共享写一张表，最危险的不是字段命名不规范，而是责任与原子边界失去定义。例如，持仓线程先写 `qty=1.8`，账本线程尚未记 480，风险线程用旧成本 6,300 和新数量算风险，查询又用新现金和旧未实现盈亏拼页面；每个字段单看合法，组合却不对应任何真实经济时点。

因此，我会让查询字段可以复制、权威字段不能旁路修改；权限、接口和数据库约束都要体现这一点。明确写权限后，还必须解释这些权威状态怎样共同变化，不能以“这是账本的事”跳过仓位和现金的关系。

## 第 3 层：既然成本和现金分属不同事实，为什么开 4,000 名义仓位只扣 4 元？

**面试官：** 你把成本和资金拆开了。那 F1 的 `C=4,000` 到底代表什么？为什么现金只从 1,000 变成 996？如果成本没从余额扣掉，你怎么解释保证金、均价和权益？

**面试者：** 因为永续仓位的入场名义成本不是现货货款。`C=4,000` 表示 2 ETH 合约敞口按入场价累计的绝对名义成本，它是计算后续平仓损益与未实现盈亏的基准，不是一个能被划走的 USDC 钱包。

F1 开多仓 2 ETH、价格 2,000，名义价值是 4,000 USDC。用户用保证金承受这份合约的损益，而不是用 4,000 USDC 购得 2 ETH 现货。在教学初始保证金率 10% 下，这笔开仓对应 400 USDC 初始保证金要求；它表现为风险占用与可用额度约束，不是又从该逐仓现金桶扣掉 400。费用 4 才是本笔确定的现金支出，因此现金为 996。

F2 之后的加权平均入场价为：

```text
旧数量 = 2 ETH，旧成本 = 4,000 USDC
新增数量 = 1 ETH，新增成本 = 2,300 USDC
新数量 = 3 ETH，新成本 = 6,300 USDC
新均价 = 6,300 / 3 = 2,100 USDC/ETH
```

手续费 4 和 2.3 不进入这个均价，因为我们已经声明采用“成交入场均价＋费用单列”的口径。否则若先把费用抬高到成本，再在现金里扣一次，后续平仓损益和净损益汇总很容易双算。

保证金现金和权益还要继续区分。现金是已入账事实；权益是现金加指定价格下的未实现盈亏。在主例 F3 后，现金 1,470.7，加上 Mark 2,400 下的未实现盈亏 540，得到权益 2,010.7。Mark 跌到 2,300，未实现盈亏变为 360、权益变为 1,830.7，但现金依然是 1,470.7。

我不会把“权益增加”直接解释成“可提现增加”。逐仓现金划出还要检查维持该仓位及未成交订单所需的保证金、在途义务和风险限制。未实现盈亏能否支持特定交易行为是产品风险规则；它无论如何不能仅因前端算出来，就自动成为一笔账本现金。

最后，`A=C/|q|` 是从权威数量和成本派生的均价。数据库可以缓存它方便读取，但不能把四舍五入后的展示均价乘回数量，替代原始成本。否则一次显示精度变更都可能改变用户未来的平仓损益。

## 第 4 层：按你的成本基准，减仓、全平和反向究竟释放什么？

**面试官：** 既然均价来自数量和成本，F3 部分减仓时为什么均价不变？如果卖出数量刚好等于旧仓，或大于旧仓，你能在同一套前提下推导，而不是另外写一套公式吗？

**面试者：** 可以。关键是把反向成交统一分成“关闭旧仓”和“剩余量开新仓”，而不是把所有卖出都当作空仓，也不是把减仓价加入剩余成本重新平均。

F3 前是多仓 3、成本 6,300，均价 2,100。卖出 1.2 小于旧仓，所以全部属于平旧仓：

```text
关闭量 c = min(3, 1.2) = 1.2 ETH
成本释放 K = 6,300 × 1.2 / 3 = 2,520 USDC
本笔毛交易盈亏 = 1.2 × 2,500 − 2,520 = 480 USDC
新数量 = 3 − 1.2 = 1.8 ETH
新成本 = 6,300 − 2,520 = 3,780 USDC
新均价 = 3,780 / 1.8 = 2,100 USDC/ETH
```

在不涉及精度尾差的本例中，剩余均价不变，因为按相同比例释放了数量和成本。主例不能改成 `(6,300 − 1.2 × 2,500) / 1.8`；那相当于把已实现的收益又抵进剩余成本，会混淆入场成本与某些产品另行展示的“回本价”。

接着只改变一个条件，分别推演两个独立变体，二者不连续叠加。

**变体 A：在 F3 后再卖出 1.8 ETH@2,400，费用 4.32。** 关闭全部旧仓，释放全部成本 3,780，新增毛交易盈亏 540，数量和成本都归零。累计毛交易盈亏为 1,020，累计费用为 13.62，现金为 `1,000 + 1,020 − 13.62 = 2,006.38`。空仓只意味着没有方向敞口，不意味着累计损益、费用和历史记录清零。

**变体 B：在 F3 后改为卖出 2 ETH@2,400，费用 4.8。** 前 1.8 ETH 关闭旧多仓，同样实现 540；剩余 0.2 ETH 新开空仓。新数量为 −0.2，新成本为 `0.2 × 2,400 = 480`，新均价为 2,400。累计毛交易盈亏仍为 1,020，累计费用为 14.1，现金为 2,005.9。按同一个 Mark 2,400 估值，新空仓未实现盈亏为 0。

统一写法是：反向成交时，`c=min(|q|,|d|)`，`o=|d|−c`；毛交易盈亏为 `sign(q)×(c×p−K)`。对空仓，买入平仓时 `sign(q)=-1`，自然得到“原入场成本减平仓买入名义额”的收益方向。手续费按已确定输入处理，不通过修改均价分摊来代替扣费。

实际定点数里，部分成本释放按规则取整、尾数留在剩余仓位；全部平仓直接释放全部成本，避免零数量还残留成本。结算余数属于另一层金额转换，不能因为仓位清零就删除。

过零意味着可能扩大反方向敞口，必须已经通过订单执行资格检查。若订单是 Reduce-Only，执行侧就应限制可成交量；持仓服务不能先接到一笔权威的 2 ETH 成交，再私自丢掉 0.2 ETH 来修正上游违规。这会造成成交、仓位和对手方结果不一致。

## 第 5 层：你这套计算依赖旧仓位，重复或错序会不会改变结果？

**面试官：** 你刚才每一步都用到了旧数量和旧成本。如果 F3 重复送达，或者它先于 F2 到达，系统最后数量看起来仍然合理。你如何定义输入身份和权威顺序，证明没有算错？

**面试者：** 先明确：持仓折叠不是对所有字段做可交换求和。数量可以累加，按平均成本确认的已实现盈亏和剩余成本通常依赖顺序，所以“最后数量对”不够。

输入身份必须落到**账户侧经济事件**。同一市场成交可能影响买卖双方，所以不能全平台只拿 `fill_id` 去重一次。我会用稳定的 `economic_event_id`，其来源能唯一对应成交的账户侧 leg，并绑定账户、市场、数量、价格、费用、来源顺序和规则版本；载荷采用规范编码保存摘要。相同身份、相同载荷才是重投，相同身份、不同载荷是冲突，必须隔离而不是后到覆盖。

顺序方面，撮合给出同一市场的来源因果顺序，清算入口在保持该顺序的前提下，将相关输入写入本风险单元的持久事件流。这里用连续的 `account_seq` 做应用检查点，它不是过滤后的全市场序号，也不是消费者线程抢到消息的先后。分配序号本身必须可靠：重复投递不重复占新业务身份，未补齐来源缺口时不能给后续相关成交排一个已经生效的新顺序。

假设 F1、F2、F3 的风险单元序号依次为 1、2、3。仅应用 F1 后收到 3，我会等待补缺或从权威来源获取 2，不先按 3 计算。原因可以直接用案例证明：

```text
正确顺序 F1 → F2 → F3：
    最终数量 1.8，成本 3,780，毛已实现盈亏 480。

错误顺序 F1 → F3 → F2：
    F1 后均价 2,000；F3 提前平掉 1.2，先实现 600。
    剩余 0.8 的成本 1,600，再加 F2 的 2,300。
    最终数量仍为 1.8，但成本变成 3,900，毛已实现盈亏变成 600。
```

这不是可接受的“展示差异”。它改变已实现与未实现损益的归属，影响账单和资金结果；后面看同一个最终权益甚至可能发现不了。

对于重复 F3，处理记录中若已经存在同一身份和摘要，就返回原结果，既不再减 1.2，也不再入账 480、扣 3。去重记录必须和经济变化一起持久提交，不能只在 Go 进程的 map 或 Redis 短 TTL 缓存里留痕，否则重启或过期后旧成交又会生效。

我会把“下单请求身份”“撮合成交身份”“账户侧输入身份”“账本效果身份”区分开。它们关联同一业务，但保护的范围不同；例如一笔成交可以产生毛交易盈亏和费用两种效果，各自都需要稳定身份。

## 第 6 层：去重、仓位和账本三个动作之间失败，怎样避免半笔生效？

**面试官：** 你说去重记录必须和经济变化一起提交。请用 F3 明确描述提交范围：读什么、算什么、写什么？如果仓位已写但 480 的分录没写成功，你准备怎么补？

**面试者：** 在既定的同数据库基线里，我不会允许“仓位已单独提交，分录以后再补”成为正常路径。F3 的持仓、损益、费用和输入处理结果属于同一个经济结转单元，由同一数据库事务提交。通知下游才是事务外的可靠交付。

执行顺序可以具体到下面这些动作：

```text
开始事务
    ↓
锁定该逐仓风险单元的提交控制行，校验当前 owner_epoch
    ↓
查询 Inbox 中是否已存在该账户侧事件
    ├─ 相同摘要且已完成 → 返回保存的结果，不重复写经济状态
    └─ 摘要冲突 → 拒绝覆盖并报警
    ↓
校验输入序号是 last_applied_seq + 1、规则版本有效、前态版本匹配
    ↓
读取本单元仓位、账本和相关结转／预留记录
    ↓
纯内核算出：q 3→1.8，C 6,300→3,780，毛盈亏 +480，费用 3
    ↓
写新仓位和成本释放明细
写毛盈亏入账及对应平衡分录、费用分录及对应平衡分录
按订单结转协议处理本笔已履行义务，不误释放其他剩余量
写 Inbox 的摘要与结果、连续检查点、结果 Outbox
    ↓
一次提交
```

F3 的现金变化是 `+480−3=+477`，旧现金 993.7，提交后为 1,470.7。毛盈亏和手续费分别有唯一 `effect_id`，关联同一经济输入；账本不仅更新用户余额，还登记对应的合约损益清算、费用等平衡侧分录。成本 C 不生成一笔“向用户支付名义本金”的现金流水。

这段事务里任何一步失败，事务都不提交，仓位、分录、去重记录和检查点都不能单独生效。计算可以在内存完成，但提交失败后不能把新状态发布给读者或继续拿它处理下一笔。若数据库已经提交但应用不知道结果，就查询原事件，而不是另取一个身份重做。

并发上，锁住的是整个风险单元的提交控制行，而不是只锁仓位表里碰巧存在的行。空仓也要有可锁定的聚合身份，否则两个首次开仓都可能读到“不存在”。数据库再以输入身份和效果身份的唯一约束作最后防线；唯一冲突后要读取并比较摘要，不是吞掉错误就算成功。

精度上，本例 +480 可以完整入账。如果某笔毛盈亏有不足一微 USDC 的尾数，原始毛盈亏累计、入账金额和结算余数也要在这个事务里共同推进，不能让持仓舍一次、账本再按另一个规则舍一次。

如果为了扩展把仓位和账本拆到不同数据库，这个原子保证就不再存在，必须明确待结转效果、稳定身份、账本消费确认和风险约束如何闭合。那是改变基线后的另一种方案，有异步暂态和运维成本，不能在此处用“加个消息队列”冒充同事务已经实现的保证。

## 第 7 层：事务已经提交，确认却丢了，用户和下游各看到什么？

**面试官：** 假设 F3 的事务实际提交成功，但进程在发送处理确认前宕机；查询投影还显示 F2 的仓位。上游重送 F3，用户又申请划出保证金。这时哪些可以重试，哪些必须阻止？

**面试者：** 这时必须把“结转事实已提交”“交付方是否收到确认”“页面是否更新”分开。F3 的经济结果已经存在，不会因为后两者没完成而变成未成交或未结转。

上游重送 F3 可以，且应沿用原事件身份。接管进程在事务中查到 Inbox 已保存的相同摘要和结果，就返回原结果，不再减仓、不再记 480、不再扣 3。若进程停在提交调用期间，调用方不知道提交是否成功，也是同样的原身份查询／重试，不能凭超时推断“肯定回滚”。

Outbox 记录与经济变化已经共同提交，所以独立派发器可以继续发送 F3 结果。投递仍可能重复，下游用稳定结果身份或版本处理；投影可以从版本 2 追到 3，但不能用迟到的版本 2 覆盖版本 3。这里保证的是一次经济效果，不是声称网络只能传一遍。

用户查询暂时看到 F2 的多仓 3，并不意味着真正仓位还是 3。界面应携带经济版本和数据时间；当请求要求“至少看到 F3 的结果”时，可按返回的版本令牌等待投影追上，超时则明确显示结果追赶中，或走受控的权威查询。

提现或逐仓保证金划出不能根据这个页面视图放行。执行资格必须检查权威现金、仓位、相关订单预留和在途义务，并与风险单元的当前版本协调。即使风险模块事先给出允许，也不能把无版本的旧裁决当作永久通行证：最终执行要在对应提交边界重新校验状态，或消费仍然有效且有额度约束的预留。

这个例子里 F3 减仓并盈利，旧数据不一定更危险；但系统不能把安全寄托在“这次恰好是减仓”。同样的延迟若发生在亏损成交或新开仓之后，过期结果可能放出本不该划走的保证金。

一致读也要说明边界。查询不能把版本 3 的数量 1.8、版本 2 的成本 6,300 和任意版本现金拼成一份报告；可以读取同一经济快照，再组合一个明确的 Mark Price 版本。最终得到的是“经济版本 3、价格 M1 下的估值”，而不是把两个独立变化的流伪装成一个没有时间含义的实时真相。

这就是允许的暂态：权威结转已完成，通知和展示稍后追上。禁止的结果则是以通知失败撤回成交、因重试重复记钱，或者让陈旧读模型决定真实资金能否划出。

## 第 8 层：如果用 Go 的单写 goroutine，为什么还要事务和跨进程隔离？

**面试官：** 你一直依赖风险单元顺序和唯一写权限。在 Go 里按风险单元分配 goroutine、通过 channel 顺序处理，是不是可以省掉数据库锁和版本校验？如果旧主没死、新主已接管呢？

**面试者：** 不能省。Go 的 owner loop 解决的是进程内状态交错问题，数据库事务解决的是持久状态共同生效，跨进程 fencing 解决的是旧执行者失去资格后仍继续写的问题。这三个范围不同。

如果由我设计，我会将风险单元稳定映射到有界数量的处理分区，而不是给每个历史账户永久创建一个 goroutine。一个 owner loop 串行处理本分区输入，内部可以缓存已提交状态，但只有提交成功后才推进内存版本，并发布不可变快照。

channel 的发送与接收可以建立对应内存操作的 happens-before 关系，但不保证输入持久化，也不保证两个发送 goroutine 的竞争顺序就是撮合的业务顺序。owner 收到数据后，仍然要检查持久序号；channel 里少了一笔、进程退出后内容丢失，也要靠可靠输入流和检查点恢复。

共享内存读取同样不能旁路：若 owner 正在修改一个包含数量、成本和版本的 struct，查询 goroutine 直接读取其中字段，仍可能形成数据竞争或撕裂快照。可以让查询走消息请求，或发布不可变对象指针；`atomic` 发布一个完整对象不等于分别原子更新多个字段就形成经济事务。

跨进程时，我会让提交控制行保存当前 `owner_epoch`。新主接管要通过受控流程提升 epoch；每个写事务在锁定相同控制行之后校验所持 epoch，旧 epoch 的写入被存储侧拒绝。不能只在内存检查一次租约，或把 Redis 锁到期当成旧主已经停止的证据。

这里要说清一个竞争时序：若旧主的事务已经拿到控制行锁，新主的接管更新必须等待；旧事务可能在切换点之前合法提交，新主随后从该已提交序号继续。若新 epoch 已经持久生效，旧事务再拿到锁时就必须因 epoch 不匹配而失败。切换点由持久状态和锁顺序确定，而不是由哪台机器的时钟先显示“租约过期”决定。

数据库按风险单元串行化，加上唯一输入身份和版本约束，是经济正确性的底线；Go 单写者减少锁竞争、简化缓存和执行路径，不取代底线。队列还要有边界，过载时回压可靠输入，不能无限堆内存或丢掉已确定成交。

最后，提交成功的持久性要与数据库高可用承诺一致。如果部署使用可能丢失已确认事务的异步副本，却在副本落后时强行接管，就不能继续声称已确认经济结果永不丢失。应选择符合业务要求的持久提交与故障转移条件；不满足时暂停接管或明确损失边界，不能让应用内的一个 channel 掩盖存储层事实。

## 第 9 层：接管进程拿什么恢复，怎样避免重放出另一套盈亏？

**面试官：** 即使你能隔离旧主，新主也要恢复状态。它可以从最新页面缓存恢复吗？如果历史规则升级过、曾经有舍入余数，或者重放时 Mark 已经变化，你如何保证恢复后仍是同一笔经济结果？

**面试者：** 页面缓存不能作为权威恢复源，因为它可能滞后、丢字段，并且把多个来源拼接成显示值。恢复必须从可证明的持久提交边界开始，同时保留足够的原始输入和规则证据。

在本数据库基线里，仓位、账本、结算余数、Inbox 和 `last_applied_seq` 已经共同提交。进程重启时，最直接的做法是读取同一个一致数据库快照，确定最后已应用事件，然后从可靠输入流补齐之后的事件。事务要么全部存在，要么全部不存在，不会出现检查点到了 3、分录还停在 2 的合法快照。

如果数据库状态需要重建，而不只是恢复 Go 内存，就要有经校验的期初快照及其后的完整规范化事件。快照至少包括数量、成本、原始／已入账毛盈亏、费用、现金、结算余数、经济序号、规则版本和核验信息，不能只存 `qty` 与展示均价。

重放时使用每笔事件绑定的历史规则，而不是当前配置。价格／数量 scale、部分成本释放、正负金额截断、手续费口径都可能改变；规则只保留一个“当前版本”会让旧成交得到新结果。事件应保存已经确定的成交价和费用，计算内核不临时访问行情 RPC、读取当前手续费率或以处理时钟决定分支。

Mark Price 的当前值变化，不应影响 q、C 和历史已实现毛盈亏的恢复。它只在恢复后的估值阶段重新组合。如果要复原某个历史时刻的风险报告，还需要当时的价格证据、账本版本、仓位版本和风险规则，不能拿当前 Mark 冒充过去的裁决依据。

对于账本重放，也不能盲目再入账一遍。若只是从已提交数据库重建仓位缓存，读取既有分录和效果身份；若在隔离的新库构建影子状态，则在那里生成待比较的结果，不向真实账本发新的付款。正式恢复继续写入时，仍以稳定效果身份和已提交检查点排除重复。

舍入余数尤其容易漏掉。假设累计原始毛盈亏还含 0.0000002 USDC 未到最小入账单位，它不是页面上的零，而是下一笔结算的输入。快照丢掉它，短期数量和现金都可能看不出差别，但继续处理足够多成交后会出现长期漂移。清仓也不能删除这个累积事实。

如果发现历史规则本身有错误，不能简单覆盖一笔旧成交后只重算当前仓位。旧错误可能改变后续成本释放和损益归属。应先隔离重放定位影响范围，按审计流程形成明确的更正与经济调整记录，再决定如何切换未来状态；已对外发生的资金效果不能以“重新跑一遍历史”为理由悄悄重写。

## 第 10 层：最终数量、权益都对，是否就足以证明你的恢复和结转正确？

**面试官：** 你说要核对重放结果。前面 F1→F3→F2 的错误顺序最终数量仍为 1.8；如果最终权益也一样，你怎样证明实现仍然有问题？请给出可执行的验证思路，并说明你这里实际验证到了哪一层。

**面试者：** 最终数量和权益都相同，仍然不够。必须核对逐事件状态、损益归属和账本效果，而不是只对一个最终总数。

就用前面的错序反例，在 Mark 2,400 下：

```text
正确顺序：
    数量 1.8，成本 3,780，毛已实现盈亏 480。
    现金 1,470.7，未实现盈亏 540，权益 2,010.7。

错误顺序：
    数量 1.8，成本 3,900，毛已实现盈亏 600。
    现金 1,590.7，未实现盈亏 420，权益仍为 2,010.7。
```

错误地提前实现了 120，恰好被未实现盈亏少算 120 抵消。权益一致不证明处理正确；现金、成本、已实现损益以及可划转资格都可能发生变化。这也是为什么核对不能只有“数量一致”和“资产总额看起来没少”。

我会把验证拆成三个层面。

**第一层是每个状态迁移都必须满足的规则。** 例如 `q'=q+d`；反向成交的关闭量加新开量等于成交绝对量；成本非负；空仓成本为零；全平释放全部旧成本；手续费不重复计入成本。Mark 单独更新时，q、C、历史毛盈亏和现金必须全部不变。

**第二层是跨状态的经济桥接。** 在主例的限制下，`B=1,000+已入账毛盈亏−累计手续费`，指定 Mark 下账本已入账口径的权益为 `E=B+U`。有结算余数时，还要用总览规定的十二位／六位整数精确核对 `原始毛盈亏=已入账毛盈亏×10^6+余数`；包含未结算尾数的经济权益还需加上换算为 USDC 的余数，不能与已入账口径混称。资金费和净划入不为零时，桥接式显式加上它们，而不是把差额塞进一个叫“其他”的字段。账本每项用户变化也要有对应平衡分录，效果身份不能重复。

**第三层是时序与故障反例。** 设计 F3 重复、身份相同但载荷不同、F3 先到、事务提交前失败、提交后确认丢失、旧 owner 复活、查询落后和价格停更等情景，分别检查：哪些状态允许滞后、哪些必须共同提交、哪些输入不能提前确认、哪个旧写者必须被拒绝。重放时从第一个事件开始比较 q、C、毛盈亏、入账金额、余数和账本效果，在首个分叉位置归因，而不是等最终权益出错才报警。

如果要实现工程验证，我会保留手算向量，再用与生产内核不同的高精度参考模型做差分；随机覆盖多空、部分平仓、过零、最小数量和极值乘法。不能让所谓 oracle 直接调用生产函数，也不能不考虑舍入规则，就武断断言“拆单与合单永远逐位相同”。

这里交付的是面试材料与[总览中的唯一小型 MVP](README.md#七工程实践唯一的简洁-mvp)：预期数值用于手工推演，没有创建可运行 Go 工程，也没有执行事务故障、主备切换或压测。文档结构检查、算式核对与真正的工程验证是不同证据，不能互相冒充。

同样，这些结论只在已声明的线性、单向、逐仓和链下提交模型中成立。全仓共享余额要提高一致性范围，双向持仓要改变聚合策略，反向合约要改变损益公式，合约权威的链上产品要重新定义执行与最终性。遇到这些约束应先说明改变了什么，再讨论方案，而不是被追问时悄悄换一套系统。

## 本题收束

### 已经讲透的机制

- **业务事实有主权：** 撮合确定成交，持仓确定数量与成本变换，账本确定现金分录，风险决定行为资格，估值组合带证据的状态。
- **永续成本不是货款：** 入场名义成本、保证金现金、权益、可划出金额是不同量；手续费独立，毛／净损益分开。
- **计算必须有顺序：** 关闭旧仓与开新仓使用同一套状态迁移；相同数量和权益可能隐藏错误的已实现损益归属。
- **提交必须有边界：** 输入身份、仓位、账本、余数、检查点和 Outbox 在本例同事务提交；通知与查询允许滞后，经济效果不能半笔生效。
- **可靠性跨越进程：** Go owner loop 不代替持久事务、来源顺序、存储侧 fencing 和历史规则重放。

### 最容易答错的边界

1. 用现货买卖款解释永续现金变化；开 4,000 名义仓位就从保证金里扣 4,000。
2. 把 Mark 波动记成现金或已实现交易盈亏；把权益等同可提现金额。
3. 减仓重新加权均价，或过零后继续沿用旧仓成本。
4. 空仓就清掉历史盈亏、费用或结算余数。
5. 用全平台 `fill_id` 去重账户侧结果，或按消息抵达顺序替代业务顺序。
6. 只说“事务＋幂等＋重试”，却没有指出哪些状态在同一事务、哪个确认点之前不能宣称完成。
7. 认为 channel 天然保证跨进程唯一执行，或者缓存更新成功就是持久提交。

### 一个能检验方案的反例

把 F2 延迟，让 F3 在 F1 后先到。若系统立刻应用它，最后数量和权益可能都与正确序列相同，但成本、已实现盈亏和现金已经不同。

一个成立的方案应当：**先保留待处理输入并补齐权威顺序；按 F1→F2→F3 得到正确分配；重送 F3 没有额外经济效果；Mark 更新只改变估值；重启后仍能从同一提交点得到同一结果。**
