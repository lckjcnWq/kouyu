# 大问题 12：如果改成链上履约，结算完成条件怎样变化？

## 先看懂：关键词大白话解释

> 本文明确切到 C1：在同一条 EVM 兼容链上，由结算合约控制两种标准资产表示，替换内部交付而非额外再付一次。BTC 指该链上的资产表示，零交易手续费，gas 另预算；不承诺原生 BTC 跨链原子交换。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| C1 / 同链资产表示 | 在一条链上使用可由同一执行边界控制的代币。 | 不是原生 BTC 与另一条链 USDT 的直接原子交换。 |
| 资产映射 / 执行域 | 固定链、结算合约、代币地址和单位对应。 | chainId 等参与绑定，不能把同一授权跨域复用。 |
| 余额 / allowance / 锁定 | 有钱、授权可花与实际受规则控制是不同状态。 | 查一次授权不保证未来能付款，撮合前须明确锁定保障。 |
| 清算义务 / 链上可履约性 | 应该交付什么，与此刻是否能可靠执行不同。 | 广播失败或授权撤销不让已经确定的成交责任消失。 |
| 合约原子批次 | 同次执行验证并完成全部必要资产动作。 | T1、T2 和对应锁定变化整体成败，特殊代币与跨链不在此前提内。 |
| 义务 ID / planHash | 稳定经济事项及固定计划指纹。 | 合约在执行资产动作时共同记录已履行，防止换交易后重复付款。 |
| txHash / 交易尝试 | 一次已签名交易的编号，不是义务本身。 | 加速或重签可有多个哈希，仍只能履行同一份义务。 |
| nonce / 替换交易 | 发送账户的交易排号及同号加速尝试。 | 跨实例持久协调，保留新旧哈希，不把 nonce 当账务水位。 |
| gas / revert | 执行消耗与执行回滚。 | gas 单独承担，revert 花了执行费也不代表成交收付完成。 |
| receipt / 义务证据 | 回执说明交易执行情况，还须核实执行了什么。 | success 可能是无关调用或幂等空操作，要查原履行记录。 |
| 规范链 / 最终性 | 当前认可的链分支，以及按明确规则作终局承诺的条件。 | 观察执行不等于最终完成，固定确认数不适用于所有链。 |
| 重组 / 观察失效 | 原先看到的区块不再属于认可历史。 | 重新核验锁定与履行状态，不删除成交或重算义务。 |
| 最终关闭执行资格 | 证明所有有效旧路径已不能再付款。 | 本地超时或一个 nonce 被取消都不足以证明整份义务关闭。 |
| 履行与取消互斥 | 合约按同一义务排他裁决支付或退回锁定份额。 | 取消也要有规范链与最终性证据，经济责任另须显式处理。 |
| 本地收敛 / APPLIED | 本地据链上证据补记状态，与链上事务不是共同提交。 | 确认凭据去重并随本地记录、Outbox 提交，不再额外生成可兑付余额。 |

## 把整篇文章压缩成一个故事

设计者小郑先把条件说清：现在采用 C1，甲、乙、丙交付的是同一条 EVM 兼容链上的 USDT 与 BTC 资产表示，不是原生 BTC 跨链兑换。价格和成交不变、交易手续费仍为零，gas 另有预算。对应资产先进入结算规则可控制的锁定范围；只查钱包余额或授权不够，因为用户下一刻可能把钱转走。这个路径替换内部资产交付，不能先给一份内部可用余额，再在链上付第二份。

结算合约要核对原批次与计划，整体完成 T1、T2：甲支付 15,015 USDT，收到 0.25 BTC 资产表示，返价差 10 USDT，丙仍锁定 0.05 BTC。小郑把稳定义务编号与 chainId、合约和资产映射绑定，合约在资金动作里共同记录履行状态。广播超时后可以重播或按链规则加速，但新旧 txHash 都只是同一义务的尝试；发送 nonce 要持久协调，不能每重试一次就换经济事项身份。

观察员看到成功 receipt，也要查它是否真对应原义务、资产和数量，是否只是重复调用的空操作，再核对区块哈希仍在规范链上。执行成功与达到最终性分开记录，不能见回执就宣布最终可用，更不能把丙剩余挂单的锁定一起释放。若未最终确认的区块被重组移除，失效的是执行观察，不是原成交；锁定和履行标记都要按新规范链重查，继续追踪全部尝试，而非重算另一份付款。

等待太久时，小郑也不会先退款再用新义务补发。只有链上执行规则排他关闭旧路径，并达到要求的最终性，才有安全退出依据；旧路径取消也不自动抹掉成交责任。链上完成而本地宕机，则按同一义务及最终证据补齐本地确认、相关记录和通知，重复扫描不额外造资产。所有保证依赖同链受控资产与明确最终性条件，不能延伸成两条独立链的原子性，更不代表合约已经实现或审计。

**流程位置与独立重点：** 从链下已确定的成交义务出发，讨论链上可履约性、交易尝试、执行证据、重组和最终性。只讲状态与保证边界，不编写合约，不把原专题的内部账户 APPLIED 说成链上最终确认。

**明确变体 C1：** 总览主线没有链上转账。本题单独将履约改为同一条 EVM 兼容链上、可由一个结算合约原子控制的两种标准资产表示；BTC 侧指该链上的 BTC 资产表示，不是原生 BTC 与另一条链的 USDT 直接原子交换。资产映射、链 ID、合约地址、代币地址及单位转换必须冻结；不讨论转账扣费、弹性余额等特殊代币。交易义务仍为零手续费，T1 价款 6,000 USDT、T2 价款 9,015 USDT；甲占资 15,025，返价差 10，收到 0.25 BTC 资产表示，丙仍锁定 0.05 BTC。链上原生币 gas 另有执行预算，不从这些成交金额里暗扣。C1 替换主线的内部资产交付路径，不先按主线给用户形成一份可支配资产，再把同一义务在链上交付一次；本地保留的是对应锁定份额、义务和履约状态的可核对记录，不凭最终确认额外生成一份可兑付余额。

## 第 1 层：为什么链下成交确定不代表链上可以付款？

**面试官：** 如果把这笔业务改成链上履约，撮合结果和清算计划都确定之后，还缺什么才能说结算完成？

**面试者：** 缺实际可执行的资产控制和链上最终履约证据。撮合域确定的是甲欠乙、丙多少 USDT，以及乙、丙应交付多少 BTC 资产；这份义务不会因为链上余额不足、授权撤销或广播失败而消失。但链下数据库里的预留，只能约束本地账户，不能自然锁住一个用户钱包里的代币。一次余额或 allowance 查询也只说明查询时的状态，不能保证下一时刻这些资产仍然可用。

因此 C1 若要在撮合前提供足额履约保证，需要事先将对应资产放在受结算规则约束的链上锁定或托管范围内，并可靠确认锁定及订单绑定；只有授权、没有实际锁定的模型就必须承认可履约性会变化。原始 `ResultBatch` 和 `SettlementPlan` 仍说明经济义务，本地 APPLIED 也只保留其本地账务含义。链上提交、执行观察、达到最终性要另有状态，不能因为计划 READY 或本地写入一条记录就声称链上已经结算。

## 第 2 层：资产已经锁定，怎样防止一边先交、一边失败？

**面试官：** 那假设已经按 C1 锁定资产。你准备怎样执行 T1、T2，才能保留原来“同命令整批完成”的保证？

**面试者：** 需要一个能够在同一链上原子验证并执行完整批次的结算边界：校验批次身份、计划摘要、资产类型、双方订单绑定和锁定额度，完成两种资产的全部收付及预留变化，并记录这份义务已履行；任何必要条件失败都不留下部分经济效果。T1、T2 仍是一份完整批次，不能各发一个互不约束的普通转账后宣称保留了基线原子性。内部资金桶和链上锁定份额也要明确映射，甲的 10 USDT 价差与丙的 0.05 BTC 不能被当作多余资产任意放出。

这个保证有明确前提：合约确实控制对应资产，代币行为符合约定，执行逻辑在失败时能整体回滚，且权限与重复执行检查正确。链下服务写“原子结算”四个字不能建立这些性质；这里只列出合约执行处必须满足的契约，不声称已实现或审计。若换成两条独立链，上述共同事务不存在，本题也不声称靠一个协调服务就能获得两链原子性；那需要重新讨论跨链协议、时序和额外风险。

## 第 3 层：为什么义务 ID 不能直接用 txHash？

**面试官：** 同一链能原子执行了，但服务可能重试、重复广播。你如何识别“同一份义务”，防止第二个链上交易又支付一次？

**面试者：** 我会给原批次建立稳定的义务身份，与原 `batchId`、`sourceHash`、`planHash` 绑定；链上执行域还要固定 chainId、结算合约和资产映射，避免签名或调用跨域复用。`txHash` 只标识一次具体的已签名交易尝试：加速替换、重签等都可能得到不同哈希，却仍然在履行同一份义务。每次尝试单独记录发送方、nonce、交易内容、哈希及观察状态，关联回同一义务，不能每次广播新造一个成交或计划。

业务一次效果必须在合约执行处成立：在同一次原子执行内，检查该义务是否已经履行以及其摘要是否一致，完成资产动作并持久记录履行结果。相同义务同摘要的重复调用不能再转移资产，同身份异摘要要拒绝，不能静默视为成功。链下唯一约束能管本地任务，管不了已经发出的第二个链上交易；真正防止重复交付的是链上义务幂等与资产锁定。原始来源和 `planHash` 保持不变，链上编码或签名封装有自己的版本与摘要，不能为适配调用参数覆盖原计划。

## 第 4 层：广播超时与 nonce 替换怎样恢复？

**面试官：** 你区分了义务和交易尝试。若广播超时，或者交易长期 pending，需要提高手续费替换，具体怎样避免漏追旧交易？

**面试者：** 先持久化待发送尝试及已签名交易的确定信息，再广播；广播返回超时，只说明当前节点没有给出确定答复，不说明网络没收到。恢复时可查询已知哈希、该发送方 nonce 的执行情况及合约义务状态，也可重播同一份已签名交易。发送账户的 nonce 分配要在跨实例持久状态中协调，不能由多个 worker 各自取一次 pending nonce 就随意发出。nonce 顺序还可能让后续交易排队，它不是交易对账务水位。

加速可以在该链规则允许时，以同一发送方、同一 nonce 提交费用更高、仍履行同一义务的替换交易；所有旧新哈希都保留在尝试历史中。某个节点说旧交易已丢弃，不能证明其他节点不再持有它；同 nonce 的取消交易也只有在相关链上结果达到所需最终性后才有意义。即使换了 nonce 再尝试，仍须沿用同一义务身份并依赖合约幂等，不能把旧哈希标“失败”后换个新义务付款。gas 加价是执行成本调整，不允许借替换交易改变原价量、收款人或 `planHash`。

## 第 5 层：交易 receipt 成功为什么仍不足以释放资产？

**面试官：** 假设新交易已经有成功 receipt。既然链上事务原子执行，为什么还不能立刻解除所有锁定、通知用户钱已经最终可用？

**面试者：** 首先要证明它成功做的是这份义务，而不是只看到 `status=success`。需要核对网络、合约地址、调用或事件对应的义务身份与原计划摘要、实际资产和数量，以及合约中的履行状态。成功交易可能调用了无关方法，也可能是一次幂等空操作；当前这次没有付款，不代表原义务尚未完成，必须找出原履行证据。执行 revert 的交易即使消耗了 gas，也没有因此完成成交收付。

其次，要把“观察到执行”与“达到最终性”分开。执行记录绑定区块号、区块哈希及观察依据，核验它仍在所承认的规范链上，再按该链的共识最终性或明确的确认策略判断何时可以作终局承诺。固定等待几个区块不是对所有链都成立的绝对证明。只有完整义务履行与最终性条件共同满足，才更新对应链上完成状态并处理相关可用性；不能只因 receipt 成功就释放该义务仍需的资产，更不能释放丙仍支撑 S2 的 0.05 BTC 锁定。

## 第 6 层：已观察执行被重组移除，应该回退什么？

**面试官：** 你把执行观察和最终性分开了。如果还没达到最终性就发生重组，之前看到的成功交易不在规范链上了，系统怎样继续？

**面试者：** 失效的是那条执行观察，不是链下成交义务。应追加记录原区块哈希失去规范性，将当前链上状态重新核验为待确定、待执行或已由另一尝试执行，并继续追踪全部尝试。原 `ResultBatch`、`sourceHash`、计划与 `planHash` 不变，不能因重组删成交、生成新成交或把应付款重算一遍。旧交易可能在新分支再次被打包，也可能由替换交易完成，恢复仍使用同一义务身份。

如果链上幂等标记随原区块一起被重组移除，那条分支上的资产转移也必须一并按链状态重新判断，不能只相信本地的“曾经执行”标记。新规范链上的有效锁定和实际履行状态才决定是否还能重试；若预先锁定本身也被重组影响，应阻断并重新确认可履约性。对外若尚未开放不可逆使用，只需维持待完成承诺；若早已允许提走资产，就已经引入垫资风险。即便遇到超出预期的深重组或最终性破坏，也应停止相关放款并核查，而不是自动用一笔新付款掩盖缺口。

## 第 7 层：什么时候才能退款或终止旧尝试？

**面试官：** 如果一直等不到结果，业务要求超时退款，然后换个新义务重新提交。怎样证明旧交易不会在退款后又执行？

**面试者：** 单靠等得足够久、某个 RPC 查不到、进程标记失败，或者换一个 txHash，都证明不了旧交易永不执行。只要原尝试还可能被打包、重组后恢复，或者同一授权还允许新的有效提交，就不能退款后再生成另一份义务付第二次。把取消自转交易的广播成功当作结算取消，也不成立；需要根据同一链上的最终结果判断原 nonce 发生了什么，同时确认不存在其他 nonce 的有效尝试。即使某个旧 nonce 已被最终消耗，也不自动证明整份义务的所有执行路径都已关闭。

安全退出要由链上状态和执行规则提供排他性，例如合约按同一义务身份，使“履行”与“取消并退回锁定份额”互斥，并保留不可复用的取消标记；或者所有有效执行入口都严格检查不可绕过的失效条件。取消、到期和执行竞争必须在链上裁决，再确认其规范性及最终性；本地时间超过截止点不是充分证据。若原义务已履行，就不能再退款；若执行资格已被最终关闭，也只是旧链上路径不能再付款，不代表链下已确定的成交义务自动消失，后续违约处理或替代履约仍要显式关联原义务，避免换身份重复付款。

## 第 8 层：单链最终完成之后，本地状态怎样收敛？

**面试官：** 假设最终已证明同一义务完成，或者已经最终取消。链上状态和本地数据库不可能共同提交，你最终能承诺什么，不能承诺什么？

**面试者：** 能承诺的是基于链上执行约束的单次资产效果，以及本地按可核验链上证据恢复收敛，不能声称关系库事务与链上交易天然原子。链上已经完成但本地确认前崩溃时，恢复器按义务身份、全部尝试及规范链上的履行记录补齐本地完成状态，并通过同一数据库事务写确认凭据、相关本地记账和 Outbox；本地确认记录有稳定唯一键和摘要检查，重复扫描不重复增加可用资产。链上真实锁定份额如何变化由合约结果决定，本地表不能凭一条确认消息反向释放合约资产。

最终取消的路径要记录取消证据与原成交尚待解决的经济责任，而不是伪装成成功结算。对账同时保留义务视角、交易尝试视角和链上最终执行视角，才能解释“两个哈希、一份履行”或“交易成功但没有新增支付”。本题所有保证都限于 C1 的同链资产控制与明确最终性假设；换成两条独立链，就不能复用“共同事务全成全败”的承诺。原始 BTC 的发行、跨链资产表示的托管或桥接风险也不因这个结算合约而消失，只是在这里不展开相邻协议。

**本题收束**

- **讲透的机制：** 链下义务固定经济责任，链上锁定决定可履约性；义务 ID 稳定、txHash 属于尝试；nonce 替换、执行核验、规范链观察和最终性各有独立含义。本地状态靠可重复核验恢复，不冒充跨域原子提交。
- **最易答错的边界：** 钱包余额与授权不是锁定；receipt 成功不是义务最终完成；超时不是退款资格；同链幂等与受控资产不是两条独立链原子性的证明。
- **反例检验：** 旧交易广播超时后先退款，再用新义务 ID 支付，旧交易随后仍可执行，就可能出现退款加重复履约。若方案没有合约执行处的稳定义务幂等、资产约束及最终关闭旧路径的证据，增加本地状态或重试次数都补不上这个缺口。
