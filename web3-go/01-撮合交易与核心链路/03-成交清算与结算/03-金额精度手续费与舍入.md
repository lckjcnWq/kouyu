# 大问题 3：金额精度、手续费和舍入怎样确定？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文先讲零费用成交的整数金额，再明确切换到 F1：双方 10 bps，买方收 BTC 时扣费、卖方收 USDT 时扣费，逐成交逐收费侧向下取整。费用规则和净到账不能挪回零费用主线。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| priceTicks / qtyLots | 用整数记录价格格子和下单数量格子。 | 一格分别是 0.01 USDT/BTC 与 0.0001 BTC。 |
| quoteUnit / baseUnit | USDT 与 BTC 各自的最小记账刻度。 | 分别为 0.000001 USDT、0.00000001 BTC，不是同一种单位。 |
| 十进制精确解析 | 直接从受限数字字符串读出整数。 | 不先转 float64，避免误差在入口就进入账本。 |
| 步长校验 | 只允许落在合法刻度上的订单。 | 数量 0.10001 BTC 不符合 0.0001 的订单步长，应拒绝而非偷改。 |
| int64 溢出 / 回绕 | 数超过整数容器范围后变成错误值。 | 乘法前查边界，余额和聚合总额也须检查。 |
| math/big.Int | 可容纳更大整数的工具。 | 仍须限制输入长度与中间规模，不等于可以无限计算。 |
| bps / F1 | bps 是费率刻度，F1 是明确另设的费用条件。 | 10 bps 等于 0.1%，不是 10%。 |
| 毛收入 / 净收入 | 扣费前应收与扣费后实际归用户的数量。 | 甲从收到的 BTC 扣，卖方从收到的 USDT 扣，不加收付款预留。 |
| 平台费用桶 | 保存已实际收取费用的对应资产账户。 | BTC 费用留在 BTC 桶，USDT 费用留在 USDT 桶。 |
| floor / 向下取整 | 舍去不足一个最小单位的部分。 | 理论费用 1.5 单位只收 1，不凭空造出半单位余额。 |
| 计费粒度 | 先分开收费还是合起来收费的规则。 | F1 逐笔逐收费侧算，汇总优化不能重新计费。 |
| 费率版本 / 接纳时冻结 | 订单接受时确定适用的经济规则。 | 后来调费率不覆盖旧订单规则；更换政策须显式改前提。 |
| READY / 历史重放 | 已固定清单与按历史事实重新恢复。 | 应用原计划或加载原版本，不读取当前 VIP 和当前费率改旧账。 |
| 逐币种守恒 / 账户绑定 | 每种资产各自平衡，同时核对给了谁。 | 付错收款人仍可能总量平衡，不能只验合计数。 |

## 把整篇文章压缩成一个故事

开发者小周替甲的买币成交算账，先把单位写在纸上：价格按 tick，订单数量按 lot，USDT 和 BTC 各有自己的细账刻度。T1 的 60,000 USDT/BTC 乘 0.10 BTC，得到 6,000 USDT。他没有先把接口字符串变成浮点数再取整，而是直接精确解析，并拒绝不符合订单步长的数量。乘法前还要查整数边界，因为不用浮点也可能溢出，任意精度工具也不能接受无限长输入。

接着他明确重置费用条件，进入 F1，而非继续零费用主线：价格、数量、成交身份和付款预留不变，双方费率都是 10 bps。甲从收到的 BTC 扣费，卖方从收到的 USDT 扣费。T1 中甲净收 0.0999 BTC，平台收 0.0001 BTC；乙净收 5,994 USDT，平台收 6 USDT。费用有明确归属，不是算完就消失，也不能临时挑哪个余额充足就从哪个币种扣。

小周另拿原文的边界输入检查舍入：两笔毛收入各 1,500 个最小单位，逐笔按 0.1% 向下取整各收 1，合计 2；若先合成 3,000 再算却会收 3。这不是同一次买币的新增金额，而是说明计费粒度的独立例子。他因此先固定逐笔费用，再汇总执行；服务改批次大小、增加 worker 或重放历史，都不能重新选择取整方式。订单接纳时冻结的费率、币种、粒度与版本也一起保留。

按 F1 结清两笔后，甲仍支付 15,015 USDT、返价差 10，但 BTC 净收变为 0.24975；平台收 0.00025 BTC。乙收 5,994 USDT，丙收 9,005.985 USDT，平台收 15.015 USDT，丙的 0.05 BTC 继续预留。小周分别核对两种资产总量，再查每笔收款人和规则，避免“总数对、人却错”。这些算式说明设计应如何验证，舍入边界还须单独核查，不宣称已经执行工程测试。

**流程位置与核心机制：** 覆盖清算金额计算、费用分配与规则重现。本题先沿用零费用主线；第 4 层起明确切换到总览定义的费用变体 F1，不把变体净到账混入其他母题。

## 第 1 层：不用浮点数，具体用什么单位

**面试官：** Go 中怎样表示成交价、数量和最终付款金额，避免精度问题？

**面试者：** 我会先定义业务单位，再选择整数类型，而不是直接说“用 decimal”。本模型价格 tick 是 0.01 USDT/BTC，订单数量 lot 是 0.0001 BTC，USDT 账务单位是 0.000001 USDT，因此 `quoteUnits = priceTicks × qtyLots`，这个乘法没有额外除法或舍入。

T1 的价格是 6,000,000 ticks、数量是 1,000 lots，相乘得到 6,000,000,000 个 USDT 账务单位，即 6,000 USDT。BTC 账务另用 0.00000001 BTC 的 baseUnit，所以 T1 对应 10,000,000 baseUnits。订单数量步长和账务最小单位不同，这样才能表达比下单步长更细的费用。

## 第 2 层：整数方案也可能在入口失真

**面试官：** 那接口传来字符串“0.1”和价格“60000.00”，是不是先转 float64 再乘倍率取整就够了？

**面试者：** 不够。先转二进制浮点可能已经改变数值，后面乘倍率无法保证恢复原十进制输入。应该按受限格式直接解析十进制字符串，检查符号、小数位、最大长度和步长，精确变为整数；是否允许科学计数法、前导零等也要有统一规范。

例如数量“0.10001”不是本订单步长 0.0001 的整数倍，应明确拒绝，不能接入层四舍五入、撮合层截断、清算层再解析一次。规范化后的整数和规则版本进入权威命令，所有后续模块复用，展示保留几位小数不反过来修改账本金额。

## 第 3 层：整数乘法也会溢出

**面试官：** 输入解析精确了，但价格乘数量超过 int64 怎么办？

**面试者：** 先检查业务上限与乘法边界，再执行乘法。对于正整数，确认数量不为零后检查 `priceTicks <= MaxInt64 / qtyLots`；预留用限价乘数量，也要做相同检查。所有相关资产余额和聚合和数也要校验范围，不能只检查单笔价款。

Go 在受控范围内使用 int64 足够简洁；费率计算的中间乘积可能更大，可以采用有明确上限的 `math/big.Int` 或经过验证的整数乘除方案，最后检查结果能否回落到存储范围。任意精度不意味着可以接受无限长输入。发生越界应拒绝输入或隔离不合法源数据，不允许整数回绕后再靠负余额检查碰运气。

## 第 4 层：明确改变条件后，手续费从哪里收

**面试官：** 现在增加双方 0.1% 的手续费，你会直接在甲的付款里多扣 0.1% 吗？

**面试者：** 不会默默这么改，因为甲原来只预留限价价款，付款侧再收费用可能让预留不足。本题从这里切到 F1：双方费率都是 10 bps，maker/taker 暂取相同费率；买方从收到的 BTC 扣，卖方从收到的 USDT 扣。价格、数量、成交身份不变，原付款预留也不变。

T1 中甲毛收 0.10 BTC，扣 0.0001 BTC，净收 0.0999 BTC；乙毛收 6,000 USDT，扣 6 USDT，净收 5,994。两种手续费分别进入平台 BTC、USDT 费用桶。付款侧、收款侧、独立平台币抵扣是不同产品规则，必须先选清楚，不能在实现里临时决定哪个余额比较够。

## 第 5 层：最小单位以下的费用怎样处理

**面试官：** F1 是从收入扣费，如果某笔算出来的费用不足一个最小账务单位，怎么舍入，差额算谁的？

**面试者：** F1 约定按每笔成交、每个收费侧独立计算，`feeUnits = floor(grossUnits × 10 / 10,000)`，净收入等于毛收入减实际整数费用。BTC 用 1 sat 作为最小单位，USDT 用 0.000001。若精确费用为 1.5 个最小单位，收 1 个，净收入为毛收入减 1；未收的 0.5 是本规则放弃的理论费用，不另造半个账务单位。

因此实际资金明细仍是整数且平衡：毛收入等于用户净收入加平台实际费用。若产品要求把舍入差额累计为可结转欠费，就需要新增明确的尾差累积状态、归属和结转规则，不能一边说向下取整、一边又悄悄把尾差记到其他用户账上。

本例 T1、T2 的费用都恰好可整除：T2 的买方费用是 0.00015 BTC，卖方费用是 9.015 USDT。主案例本身不触发尾差，需要额外最小单位边界输入才能检查舍入。

## 第 6 层：逐笔取整为什么不同于合并后取整

**面试官：** 你说每笔独立算费，把同一用户两笔成交合起来计算再取整，不是更省事吗？

**面试者：** 可能更省计算，但会改变费用规则。假设某种资产两个毛收入各为 1,500 个最小单位，费率 0.1%；逐笔向下取整各收 1，共 2；先合并 3,000 再计算会收 3。两者都可定义为产品规则，但不能在“SQL 聚合优化”时偷偷切换。

F1 固定逐笔计费，所以计划先保留每笔收费结果，再汇总平台费用和用户净收入。聚合视图只相加已确定的整数结果，不重新算费。分批、重投、改变 worker 数量都不应改变手续费；反之，如果费用取决于消费者今天凑了多大的批次，重放就无法保持同样义务。

## 第 7 层：费率变更与历史重放怎样共存

**面试官：** 既然计算粒度会影响钱，费率从 10 bps 调到 20 bps 后，积压成交和旧订单的新成交怎样处理？

**面试者：** 先明确生效政策。本教学变体采用订单接纳时冻结费用规则，订单后续成交继续引用原版；旧订单如果需要换规则，应走明确的重新授权或订单替换流程，不能只改配置。另一种按成交序列生效的政策也可行，但必须把生效序列、双方适用版本和预留影响记入权威事实，那已经改变当前前提。

对已经发生的成交，计划记录费率、计费资产、舍入、粒度和版本，READY 后应用原计划。对尚未生成计划的旧批次，加载原版规则重算。不能用“当前 VIP 等级”和“当前费率表”覆盖旧义务，否则同批次第一次算 10、第二次算 20，幂等只能识别冲突，不能替你决定哪笔才正确。

## 第 8 层：怎样从整套金额证明没有漏费或造钱

**面试官：** 按 F1 把整个案例算完，你会核对哪些结果，怎么识别一个总额平衡但仍然错误的方案？

**面试者：** 甲付款仍是 15,015 USDT，价差仍返 10，因此可用 USDT 仍为 4,985；净收 BTC 是 0.24975，平台收 0.00025。乙净收 5,994，丙净收 9,005.985，平台收 15.015 USDT，丙仍有 0.05 BTC 预留。于是 USDT 合计 `4,985 + 5,994 + 9,005.985 + 15.015 = 20,000`，BTC 合计 `0.24975 + 0.00025 + 0.05 = 0.30`。

但合计平衡只是必要条件。若把乙的净收入付给丙，总量依旧平衡，所以还需核对每个成交的收款账户、费用桶、订单绑定与规则版本。边界验证应包含零费用、恰好整除、不足一个单位、最大合法值、越界值，以及“逐笔取整与汇总取整不同”的反例；这些是验证设计，不声称已执行工程测试。

## 本题收束

- **讲透的机制：** 单位先于类型，整数精确解析，受控乘除和舍入，费用币种、粒度与生效版本共同决定义务。
- **最容易答错的边界：** 不用 float64 仍可能溢出；手续费不能凭空消失；逐笔和聚合取整不是等价优化；付款侧收费会改变预留需求。
- **检验反例：** 两笔毛收入各 1,500 最小单位、费率 10 bps；若系统因为批次大小改变而在 2 与 3 个费用单位之间变化，就没有冻结计费规则。
