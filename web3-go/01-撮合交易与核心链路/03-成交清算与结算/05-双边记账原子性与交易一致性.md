# 大问题 5：怎样保证买卖双方资产和成交始终对得上？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文讨论零手续费、同一账务数据库内的完整批次一致性。允许撮合领先账务，但不允许义务丢失、资金提前可用或只完成买卖中的一边；跨库后必须另立协议。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 不变量 | 任何正常或故障路径都不能破坏的底线。 | 数量有去处、预留不挪用、余额非负、同一结果不重复生效。 |
| 受控暂态 | 尚未做完，但事实和资金来源仍能恢复。 | 订单全成而计划待应用可以存在，提前退掉付款预留不可以。 |
| 局部提交边界 | 每个模块自己能够可靠承诺的一段。 | 预留意图、撮合结果与执行进度、账务履约分别定义共同提交范围。 |
| 清算计划 / 履约 | 前者决定应收应付，后者落实资金变化。 | 算出义务并不等于用户已经能花这些资产。 |
| 完整批次原子性 | 一包全部资金变化一起成立或一起回滚。 | T1、T2 以及应用去重和连续进度不能各自提交。 |
| 资金桶变化 / 复式分录 | 桶变化说明钱的流向，复式分录还要遵守科目借贷规则。 | 余额增加并非永远记借，不能把两种表达直接画等号。 |
| 逐币种平衡 | 每种资产单独核对所有增减。 | BTC 不与 USDT 折价混加；平衡仍须再查收款人与订单。 |
| 共享账户竞争 | 不同业务同时修改同一账户资产。 | 交易对单写者挡不住另一交易对或提现路径。 |
| 行锁 / 条件更新 | 由数据库协调并发并核对更新前提。 | 检查版本、非负和影响行数，不是先查够钱再盲写。 |
| 全局锁顺序 | 所有资金路径按兼容的资源次序拿锁。 | 减少互相等待，仍需处理死锁与整批重试。 |
| APPLIED / 唯一约束 | 完成凭据及防止同批次重复提交的约束。 | 完成标记须随资金提交，唯一键冲突不自动证明已到账。 |
| Outbox | 随账务保存的待发完成通知。 | 不要求通知已送达，但提交时须留下可靠待发事实。 |
| Saga / 追加反向事项 | 用新的业务动作处理后果，而非抹掉历史。 | 数据库故障不是撤销既成成交的授权，外部转账也不能凭分录追回。 |
| 分片 / 全局提交决定 | 跨独立库时另需协调的履约范围。 | 幂等和对账不能代替双边共同完成，pending 开放可用也要有依据。 |

## 把整篇文章压缩成一个故事

评审员小何先不问用了什么消息队列，而是请大家写出不可破坏的规则：订单数量要对得上，双方交付的 BTC 要相同，USDT 付款和收款要相符，预留不能给别单借用，同一批结果只能产生一次资产效果。他允许甲的页面先显示全成、账务稍后完成，因为撮合与账户不在一个全局事务里；但这段等待必须有持久成交、固定义务和仍受保护的付款预留，不能拿“最终一致”掩盖失控缺口。

甲这次买到 0.25 BTC，账务需要同时处理他的预留减少 15,025 USDT、可用增加 10 USDT，以及乙收 6,000、丙收 9,015 USDT。乙、丙交出的 BTC 也要同时入甲账户。小何要求完整批次的余额、预留、分录、订单投影、应用去重、水位和通知记录同库提交。只把双方余额放一起还不够：去重晚写会重付，进度早写会漏批，通知事实丢了则用户可能一直看不到完成。

有人说每个交易对只有一个 worker，不必再锁账户。小何指出，甲在另一市场下单或提现也会碰同一份 USDT，进程内互斥锁管不到这些路径。所有资金写入要由数据库锁、条件更新和兼容锁顺序协调，检查版本与影响行数，死锁后整批用原身份重试。他还分别验算 USDT 和 BTC 的增减，不允许拿汇率混加；即使分录平衡，也须查是不是把乙的钱错误付给丙，复式平衡不等于业务正确。

数据库暂时不可用时，小何保留成交、计划与预留，限制新增负担，恢复后完成原义务，不擅自撤销成交。若团队要把双方拆到不同库，他要求另讲准备状态、持久全局决定、恢复与旧协调者隔离，因为各边幂等并不能阻止半笔履约。最后还要检查历史上是否曾过早放钱，而不只看最终余额是否对齐。这些是评审和验证要求，不是已经完成并发实验或灾备演练的声明。

**流程位置与核心机制：** 本题独立承担从预留、成交到双边账务的端到端一致性，重点是不变量、局部提交边界、跨域暂态和共享余额并发；交付细节及崩溃窗口分别由第 06—08 题深入。沿用总览单库整批事务、零手续费基线。

## 第 1 层：先定义“一致”而不是先报组件名

**面试官：** 怎样保证订单、成交、买卖双方资产和预留始终对得上？请不要只回答“事务加幂等加对账”。

**面试者：** 我先定义要保护的规则：订单原始数量等于累计成交、剩余和已撤数量之和；每笔成交双方交付相同 BTC，零费用下付款与收款 USDT 相等；各资金桶和订单预留非负，任何一份预留只能支撑对应意图；相同结果只能产生一次资产效果。账务已应用到某个结果位置时，必须能把这些成交、分录、余额和预留逐项关联起来。

“始终”不意味着各模块同一纳秒展示相同状态。撮合可以领先账务，已 FILLED 的订单可以仍是 READY，但既成义务必须有可靠记录及有效资金覆盖，不能把未付款资产变成用户可用，不能先退后扣。允许暂时未完成，禁止不可恢复遗漏、单边履约和重复花费。

## 第 2 层：没有全局事务怎样定义可靠边界

**面试官：** 你允许撮合领先账务，它们又不在一个事务里，怎样避免边界之间恰好丢一半？

**面试者：** 本模型不是跨域强行假设一个大事务，而是给每个边界定义可恢复承诺。下单时账户事务共同提交预留和意图；撮合只接纳有有效绑定的命令，完整结果与执行进度共同提交到可靠日志。越过这个结果边界，交易义务不能因为下游超时随意撤销。

结果交付允许重复，清算入口持久接管并固化计划，账务域在自己的事务里完成资金和应用记录。交付器未确认接管就重投，接管后由持久任务继续推进，未应用的预留仍保留。若要关闭执行资格，通过撮合有序结果裁决，而不是账户自行超时退款。

这组协议保证边界之间可以停留、可以恢复，却不会失去来源或给同一份钱两个用途。它依赖持久存储、可靠保留及恢复能力，不是用“最终一致”四个字跳过故障假设。

## 第 3 层：双边资金到底哪些字段共同提交

**面试官：** 那进入账务域后，一次事务具体包括什么？只把买卖双方余额放进去够吗？

**面试者：** 不够。事务至少包括完整批次所有成交的资金变化、订单级预留消耗和释放、不可变分录、账户侧订单结果投影、APPLIED 和 planHash、交易对消费水位及 Outbox。它们分别证明“发生了什么”“资金现状是什么”“这个批次是否已生效”“后续从哪继续”。

主案例中，甲预留减少 15,025、可用 USDT 加 10、BTC 加 0.25；乙预留 BTC 减 0.10、USDT 加 6,000；丙预留 BTC 减 0.15、USDT 加 9,015。全部校验成功并共同提交才构成 APPLIED。若只把余额放一个事务、去重记录另写，崩溃后仍可能重复付款；水位另写还可能跳过未处理批次。

Outbox 不要求通知在资金提交前已送达，但要求提交时已经留下可恢复的通知事实。页面失败不能反过来撤销账务。

## 第 4 层：逐币种平衡怎样落到分录

**面试官：** 你说逐币种平衡。BTC 和 USDT 价值相等不就够了吗，为什么还要逐币核对？

**面试者：** 不够，不能用一个币种的增发抵消另一个币种的损失。主案例 USDT 资金桶增减为：甲预留 -15,025，甲可用 +10，乙可用 +6,000，丙可用 +9,015，总和是零；BTC 为乙预留 -0.10、丙预留 -0.15、甲可用 +0.25，总和也是零。

这些是内部资金桶的有符号变化，清楚表达资产从哪来、到哪去；正式复式总账还需按科目性质确定借贷方向，不应把“余额增加就是借”当成通用规律。存储上既保留可追溯资金变动凭据，也保证余额物化更新和它们共同提交。

平衡仍是必要非充分条件，错误收款人也能平衡。因此还要核对每条腿的成交来源、账户、资产、订单及预留绑定，不能让一个数值平衡但把乙的钱付给丙的计划过关。

## 第 5 层：单交易对有序为何还会有并发问题

**面试官：** 如果每个交易对只有一个应用 worker，是否可以不用账户行锁和条件更新？

**面试者：** 不能。甲可能同时在 BTC/USDT 和 ETH/USDT 下单，提现、内部转账和其他资金路径也可能碰同一份 USDT。交易对内单写者只控制本序列，不控制整个账户的所有资产操作，也不自动隔离第二个进程或切换后的旧 worker。

账户域应在数据库中协调竞争。预留时对可用余额做原子条件扣减并建立唯一意图；结转时锁定相关资源，或使用包含版本及非负条件的更新并检查影响行数。两条并发语句都先查“够钱”再无条件写回，会出现丢更新或超额占资，即使各自进程内有 mutex 也无效。

所以业务排序、数据库隔离和持久约束各有范围。不能拿一条交易对日志的顺序证明共享账户天然串行。

## 第 6 层：数据库锁会不会把系统锁死

**面试官：** 多交易对批次会锁多个用户，两个批次各拿一部分锁再互等怎么办？

**面试者：** 需要全局兼容的资源锁顺序，而不只是同一交易对内排序。每个事务先锁自己的交易对水位，再对参与资金资源按统一键排序，例如资源类型、账户、资产、预留身份；所有会同时访问这些资源的资金路径遵守兼容协议。先计算计划、再短事务内校验应用，避免拿锁期间调用远程服务。

仍要准备处理数据库检测出的死锁、锁超时和序列化失败：这些都是整笔事务未成功的可重试结果，回滚后以原身份重试，带退避和限额，不从中间一条 SQL 接着跑。固定顺序能显著缩小死锁面，不意味着再也不用检查数据库错误。

批次涉及账户太多时锁持有时间会上升，容量控制应在接入与撮合命令预算中限制批次规模，不能遇到热点就把同一个完整批次拆成可见半笔履约。

## 第 7 层：APPLIED 标记能否先写来挡重复

**面试官：** 为防止两个 worker 同时记账，先插一条 APPLIED 再慢慢改资金，不是更简单吗？

**面试者：** 如果 APPLIED 单独提交就不对：标记写完后崩溃，资金没动，恢复却会把批次当完成。可以在事务内先争抢唯一 batchId，或者锁水位形成互斥，但这个记录只有随资金一起提交才具有完成语义。

第二个 worker 命中唯一约束时，要等冲突事务决议或回滚并查询原结果。若原事务成功，核对 sourceHash、planHash 后复用；若原事务回滚，原身份重新应用。不能把任意唯一约束异常都当成“钱一定结好了”，也不能在事务已进入错误状态后继续执行其余 SQL。

这种应用边界才提供业务一次效果：运输、计算或执行尝试可多次，真正提交的资金变化只有一次。

## 第 8 层：临时无法记账能否撤销成交补偿

**面试官：** 如果数据库长时间不可用，你会不会用 Saga 撤销原成交，把钱退回去让系统先恢复？

**面试者：** 不会把基础设施故障当成取消既成交易的授权。数据库不可用时，保留可靠成交、计划和预留，进入受控积压，必要时收紧新下单；恢复后按原义务履约。买卖双方可能已经基于成交做了后续决策，不能只因为某次消费者失败就假装成交没发生。

业务确需取消交易必须另有明确规则和授权，而且要检查后续资产是否已被花费。即便追加反向分录，也只是在账务上形成新的事项，不能让过去交易不存在。对不可逆外部转账更不能靠本地负数分录“补偿”成真的资产追回。

所以本题的一致性收敛主路径是完成原义务，而不是失败就回滚成交。对账负责发现异常和提供修复证据，不代替预留覆盖与原子执行。

## 第 9 层：跨独立账务分片后什么保证失效

**面试官：** 如果必须让甲和卖方在不同库，保留幂等与对账，就能维持同样的一致性吗？

**面试者：** 不能，幂等只阻止同一动作重复，不保证不同库的动作共同完成。甲扣款成功、乙到账失败时，两边各自幂等仍然是半笔履约；事后对账发现差异，也不能撤回用户已经花出的可用资金。

改变基线后必须明确新的权威结算决定、各参与者准备与提交状态、恢复规则及旧协调者隔离。可以让分片先锁定或产生不可花费的 pending 结果，等全局提交决定持久确立再开放资金；也可以采用满足故障假设的分布式事务。但准备状态阻塞、协调恢复和可用性代价要一并承认，不能把“发三个消息”叫作原子提交。

本稿不把这个变体当作已完成能力。若面试继续深入分布式事务，应沿新协议单独推演，而不是沿用单库 SQL 事务的结论。

## 第 10 层：怎样验证不变量而不只看最终总额

**面试官：** 你会怎样验证整体一致性，尤其是最终总额正确但中间曾经可重复花费的情况？

**面试者：** 除最终逐币平衡，还要检查历史上的资金可用性、执行资格及每次提交边界。比如故意让后序撤单先到、成交记账落后，确认资金没有提前释放；让同批次并发重投，确认只有一份分录和同一 APPLIED；在资金 SQL 与应用标记之间模拟失败，确认两者不是分开提交。

再核对共享账户：两个交易对并发预留，任意时刻可用不负、每个预留有唯一来源；提交后通知失败，资金依然维持已完成；同一 batchId 换载荷被阻断，而不是被幂等静默忽略。对账在共同水位对源结果、计划、分录和余额建立一对一证据。

最终案例算式只能证明该输入的金额自洽，故障注入、数据库并发实验与灾备演练是不同证据。本专题只交付设计、问答和手工推演，不能把这些检查建议说成已经运行通过。

## 本题收束

- **讲透的机制：** 不变量先定义正确性，跨域协议允许受控暂态，单库事务提供完整资产效果，稳定身份和连续水位维持恢复后的同一语义。
- **最容易答错的边界：** 逐币平衡不证明收款人正确；单交易对有序不证明共享余额安全；幂等不提供双边原子性；补偿不等于撤回已经花出的资产。
- **检验反例：** 所有表最终总额都对，但成交与撤单乱序导致资金短暂解冻并被再次花掉。若只检查最终快照，方案仍可能漏掉最危险的一致性破口。
