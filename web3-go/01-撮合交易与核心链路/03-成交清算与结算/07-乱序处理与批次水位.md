# 大问题 7：乱序、缺批和多交易对并发怎样推进？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文在零手续费、同库整批应用的条件下，解释为什么“先收到”不等于“先能记账”。连续水位是完整履约前缀，不是看见过的最大编号，缺口必须从权威来源补齐。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| lastAppliedSeq / 连续水位 | 前面的每个位置都已完整应用到哪儿。 | 水位 101 不能因为收到 103 就跳成 103。 |
| 接管位置 / 应用资格 | 已经可靠收到，与现在允许动资金不同。 | 103 可在 Inbox 等待，须先完成 102 才能应用。 |
| 完整 ResultBatch | 一条命令的全部成交和状态动作。 | 只有 T1、不含 T2 时，不能先制造部分可用到账。 |
| 分片组装 / 权威清单 | 将传输碎片收齐，并核对源头应有内容。 | 消息自带摘要不能证明没有漏掉另一笔成交。 |
| 空批次 | 没有成交但仍有正式结果的位置。 | 可能含撤单退款；只有核实完整内容后才能判断无资金动作。 |
| 缺口扫描 / 定向补取 | 持续找下一缺失位置，按原编号取回事实。 | 缺 104 就找权威 104，不拿超时当作造空结果的许可。 |
| before / after 数量 | 同一结果应用前后的订单数量证据。 | 撤单只取消真实剩余，不拿最新终态覆盖滞后预留。 |
| NEEDS_REVIEW | 无法证明内容安全时停住核查。 | 阻断原位置并保留后序任务，不跳过继续退款。 |
| 有界唤醒 / 持久积压 | 内存只留有限调度提示，可靠任务在存储中。 | 不能用无界 map 顶住远期结果，也不能删掉已签收任务。 |
| 背压 / 配额 | 忙不过来时限制接收与新业务速度。 | 未落盘不 ACK，停止拉取还须有上游保留和补送保障。 |
| 每交易对序列 | 不同市场各有独立连续排号。 | BTC-USDT 缺口不天然要求 ETH-USDT 同时停下。 |
| 共享余额 / 全局锁顺序 | 不同市场仍会碰同一账户资产。 | 流内有序不能替代数据库并发控制，也不能借别单预留。 |
| 租约 / 旧 worker | 调度授权可能过期，旧执行者却未必停止。 | 新旧执行者都要锁同一数据库水位，并在锁内重读。 |
| 共同提交 / 历史摘要 | 完成证据、资金和进度一起落地，旧内容仍可核对。 | APPLIED、去重、水位与整包资金同事务；旧序号不直接盲返成功。 |

## 把整篇文章压缩成一个故事

账务员小罗的账本连续处理到 101，收件箱却先来了 103。这个变体只在主成交之后增加丙的撤单：102 已确定丙向甲交付 0.15 BTC，103 取消剩下 0.05 BTC。小罗先存好 103，不动资金。因为账户此刻仍显示丙预留 0.20 BTC，若只看最新“已撤”就全部退回，便把尚未履约的成交币也退掉了；丙一旦另花，甲的成交就失去覆盖。

小罗去补 102，第一次只拿到 T1，仍不能开始记账。整包还应有 T2、订单变化和预留动作，必须对照权威清单收齐，而非给残片算个摘要就放行。完整 102 准备好后，他在同库事务里应用全部资金、分录、去重和水位，丙的预留才从 0.20 降到 0.05 BTC。随后应用 103，才把那 0.05 BTC 退为丙可用。水位要么还在 101，要么完整来到 102，不承诺半包完成。

接下来 105 已到，104 却没到。有人说 104 可能没成交，跳过算了，小罗仍向可靠日志定向补取：没有成交也可能有拒绝或撤单释放，必须有权威空批次证明处理内容。若档案缺失或冲突，就停在原位置核查，不能超时后编造空结果。等待期间只保留有界内存提示，任务持久保存，限制远期计划和新增负担；已经接管的义务不会因为缓存满或过期被删除。

另一交易对可以按自己的水位推进，但若同样使用甲的 USDT，仍须由数据库锁和条件更新协调，不能复制出两份钱。小罗重启或任务租约切换时，也不信本地缓存排号：新旧 worker 都要锁水位、重读状态、核对来源与计划摘要，再决定复用旧结果还是应用下一包。这样顺序资格是在资金执行处成立的，而不是调度器说了算；整段只是协议推演，不是已运行的并发测试。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于 Inbox 接管之后、账务事务应用之前，解释收到的结果怎样形成连续、可证明的应用前缀。重点是完整批次、空批次、缺口补取、每交易对水位和共享资金并发，不把运输顺序当作资金释放资格。

沿用总览的零手续费和单关系库整批事务。主案例 `BTC-USDT/102` 包含 T1、T2，起始账务水位为 `101`。为推演乱序，仅在后续明确增加 `103` 对丙的 S2 剩余挂单发起撤单这一命令，不改变批次 102 的成交事实。

## 第 1 层：收到更大序号不代表前面的义务已经履行

**面试官：** 账务只应用到 101，却先收到 103，怎样继续推进，为什么不能直接处理收到的最大序号？

**面试者：** 先把通过来源和完整性校验的 103 持久化到 Inbox，但不应用它。`LedgerCursor.lastAppliedSeq=101` 的含义是“该交易对截至 101 的完整结果都已经结转”，不是“目前见过的最大数字”。只有 102 已经完整接管、生成合法的 `READY` 计划，并在整批账务事务里成功提交，水位才能变成 102；随后 103 才取得应用资格。

所以需要区分接管位置和应用水位。103 可以已接管、甚至已经计算好计划，但仍是等待前序的任务，资金没有因此可用。应用器在数据库事务中锁定该交易对水位，要求 `commandSeq=lastAppliedSeq+1`，而不是在进程内比较一次后就执行。这个限制牺牲了同一交易对跳过慢批次的能力，换来预留、订单结果投影和资金义务始终有共同的顺序解释。

## 第 2 层：后序撤单为什么必须等前序成交结转

**面试官：** 你说顺序关系到预留。假设 103 是 S2 撤单，而 102 还没记账，先处理撤单究竟会出什么问题？

**面试者：** 在 101 的账户状态里，S2 还预留 0.20 BTC；已提交的 102 已经确定其中 0.15 BTC 卖给甲，只剩 0.05 BTC 继续挂单。103 的权威撤单结果只能取消这 0.05 BTC。如果账户应用器先看撮合最新终态“订单已撤、剩余量为零”，就把当前 0.20 BTC 预留全退给丙，会连尚未履行的 0.15 BTC 成交义务一起释放。丙若将这部分可用资产再次使用，后到的 102 就失去原来的资产覆盖。

正确顺序是：先应用完整 102，消耗 S2 的 0.15 BTC 预留并向甲结转，S2 留下 0.05 BTC；再应用 103，校验账户侧订单结果投影的 before/after 数量，释放恰好 0.05 BTC。即使某个孤立的撤单动作看起来可交换，也不能绕过基线的顺序验证；否则需要另建可证明的依赖模型。本题选择连续前缀，而不是靠账户应用器猜哪些后序动作“应该无害”。

## 第 3 层：补到了 102 的一部分，也不能先推进半步

**面试官：** 那就补取 102。但现在只拿到 T1，还没拿到 T2，能不能先记 T1，等齐后再把水位推进到 102？

**面试者：** 在本基线中不能，因为应用原子单位是完整 `ResultBatch`，不是单条成交。102 还包含 T2、相关订单变化、预留动作和完整性信息；只拿到 T1 时无法验证本次 B1 是否全成、S2 应保留多少预留，也不能验证计划是否完整。若传输层不得不分片，应把分片暂存为待组装输入，校验分片身份和内容，组装并核对完整来源后再进入可计划状态，不让任意一个分片冒充完整批次。

完整性要结合权威日志的批次记录、成交清单、计数和规范化 `sourceHash` 核验，单独计算收到内容的摘要并不能证明 T2 没有被漏掉。102 的 T1、T2 都固定后，生成同一份 `READY` 计划，在一个数据库事务中共同应用，水位只有 101 或 102，不存在对外承诺的“101.5”。即使 T1 已执行完若干 SQL，只要整批未提交，就不能把它作为可用资金，也不能发布资金完成回报。

## 第 4 层：没有成交的命令也占有一个必须解释的位置

**面试官：** 你要求每个序号都完整出现。如果 104 本来没有成交，105 已经到了，等待 104 不是永远等不到吗？

**面试者：** 总览约定每条已处理命令都有结果，包括没有成交的空批次，所以“没有成交”不等于“没有结果位置”。应用器仍要取得权威的 104，核对其身份、规则和完整性，解释其中的订单变化与预留动作。撤单或拒绝可能没有成交却需要释放资金，不能只看 `trades` 为空就当作无事发生；只有确认该完整结果确实没有资产动作，资金变化才可以为空。

对于确实无资金变化的 104，仍记录这次批次应用的身份和摘要，在同一个数据库事务中更新必要的订单结果投影、完成状态和水位。这样才能证明 104 已处理，而不是没收到。之后 105 才能继续。若系统只为有成交的命令发送结果，却让消费者按连续 `commandSeq` 等待，就破坏了上下游契约；修复方式是补齐可靠的空结果交付，而不是消费者自行猜出哪些序号可以忽略。

## 第 5 层：缺口长期不出现时，补取要找事实而不是造事实

**面试官：** 如果 104 的空结果在运输中丢了，普通重试一直拿不到，而 105、106 都已就绪，怎样避免永久卡住？

**面试者：** 用“水位下一位置”和已接管更大位置识别缺口，记录等待起点、缺失序号和补取状态，按 `BTC-USDT/104` 向持久化结果日志定向补取。补取必须读取已提交的完整结果：若权威提交位置已超过 104，说明该位置本应可获得，应继续查保留日志、归档或明确的数据异常；若权威来源尚未提交到那里，则不能把未提交或错误来源的更大序号当作依据。消息订阅之外要有可恢复的缺口扫描，避免只靠一次网络唤醒。

超时只能触发退避、告警和升级，不能授权生成一个假的空批次，也不能把水位改成 106。内容冲突、档案缺失或无法证明完整性时，应 `NEEDS_REVIEW` 阻断该位置，保留后序已接管任务和相关预留。这个选择会影响可用性，但它准确表达了“履约前提还未证明”；跳过缺口会把未知的成交、释放或订单变化永久排除在连续前缀之外，后续对账也不能自动补回被提前使用的资金。

## 第 6 层：等待缺口时如何防止后序输入耗尽资源

**面试官：** 不允许跳过 104，但其后的结果不断到来，全部排队会不会把内存和数据库撑满？

**面试者：** 所以等待队列不能是一个无界的 Go map。内存只保留有界的唤醒和候选索引，完整已接管输入在持久存储；同一交易对重复到来的唤醒可以合并，优先调度最老缺口及水位紧邻的就绪批次。计划计算允许有限并行，但每个交易对只按连续位置应用；不能为了“先做点工作”让大量远期计划占满全部 worker 和数据库连接。

持久化积压也需要配额、磁盘容量告警和入口背压。尚未成功持久化的输入不能先 ACK 再丢弃；如果暂时停止拉取，就必须依赖上游仍可保留、补送这些已提交事实的契约，必要时限制新增业务受理，而不是无限生产无法履约的结果。已经 ACK 接管的任务则不能因超过内存或保留时间被删除。容量保护改变的是接收与计算节奏，不改变连续水位和原有义务；确实耗尽安全容量时，应显式暂停，不能承诺“用无界缓存顶过去”。

## 第 7 层：交易对并行不等于共享余额也能无锁并行

**面试官：** 你用每交易对队列隔离积压。那 BTC-USDT 卡在 104，ETH-USDT 能继续吗？如果两个交易对使用同一用户的 USDT 呢？

**面试者：** 两个交易对没有统一的 `commandSeq`，因此 BTC-USDT 的缺口不天然要求 ETH-USDT 也停止；ETH-USDT 可以按自己的连续前缀推进。但它们共享同一个账户数据库，用户的 USDT 可用余额可能是同一行，不能因为 symbol 不同就复制出两份可花资金。每个批次先锁定本交易对水位，再按全局固定资源键顺序锁定受影响的预留和余额；其他资金写入路径也必须使用兼容的锁顺序，并检查绑定关系、影响行数、版本和非负约束。

这样，两个交易对的应用顺序在各自流内确定，交叉的账户资源再由数据库锁裁决实际提交次序。订单级预留必须归属于原订单，不能拿另一个交易对订单的预留填补缺口；BTC-USDT 尚未应用的到账，也不能作为 ETH-USDT 已经可用的余额。热点账户会使部分事务串行，死锁或序列化失败可能要求整批重试，这是单库正确性约束的成本。按交易对分 worker 是调度手段，不是资产分片，也不是可以取消数据库并发控制的理由。

## 第 8 层：接管、重启和旧 worker 都必须重新接受数据库裁决

**面试官：** 共享资源由数据库锁决定，那某交易对 worker 重启或租约过期后，新旧两个 worker 同时推进水位，内存里的顺序判断还可靠吗？

**面试者：** 内存判断只能作调度提示，最终资格必须在应用事务中重验。新旧 worker 都锁定同一个 `LedgerCursor`，读取最新已提交值，再核查批次身份、`sourceHash`、`planHash` 和计划状态。对恰好 `lastAppliedSeq+1` 的合法计划，才能执行整批资产变化，并共同提交 `APPLIED`、账户侧订单结果投影、Outbox 和新水位；对更大的序号持久化等待，对已经应用的序号则核对原有摘要后返回原结果。租约过期不允许旧 worker 绕过这道数据库入口。

如果旧 worker 已持锁，新 worker 等它提交或回滚；拿到锁后必须重读，不能继续使用等待前缓存的水位。进程崩溃但数据库完好时，恢复者从数据库水位和未完成 Inbox、计划重新调度，不从消息 offset 或本地变量接着猜。遇到“水位说已做过，但应用证据查不到”之类不一致，要核查归档或进入阻断，不能把 cursor 当作万能去重记录。整个协议允许接管领先、计划领先和重复执行尝试，禁止资金效果领先于它所属的连续应用前缀。

## 收束：水位是已履约前缀的证明，不是调度进度条

- **讲透的机制：** 一个交易对按完整命令结果形成连续前缀；空批次证明该位置确实处理过；缺口由可信日志补取；水位与分录、余额、预留、订单结果投影及应用记录共同提交；跨交易对调度独立但共享资金仍由数据库约束。
- **最易答错的边界：** 收到最大序号不等于已应用；只有 T1 不算收齐 102；没有成交不代表没有释放动作；超时不能生成空结果；同交易对顺序不能替代跨交易对的账户锁；`NEEDS_REVIEW` 是阻断而不是允许跨过的位置标记。
- **可手工验证的反例：** 从水位 101、S2 预留 0.20 BTC 开始，先送来 103 撤单，再送仅含 T1 的不完整 102：水位必须仍为 101，不能向丙释放 BTC。补齐可信的完整 102 后，整批结转使 S2 剩余预留为 0.05 BTC、水位为 102；再应用 103，才将这 0.05 BTC 退回丙并推进到 103。随后若缺 104 而 105 已到，仍停在 103，直到取得并处理权威 104。若任何一步允许丙先取回 0.20 BTC，或允许水位直接变成 105，就已找到违反资金覆盖或连续前缀的反例。这是手工推演，不是工程测试。
