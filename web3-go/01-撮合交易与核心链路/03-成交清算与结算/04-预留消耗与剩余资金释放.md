# 大问题 4：怎样消耗预留并安全释放剩余资金？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文在零手续费、同库内部结转的前提下，追踪订单预留怎样付款、退价差和退撤单剩余。核心是退款必须有权威依据，且不能越过尚未履行的成交。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 订单级预留 | 为指定下单意图单独占住的资产。 | 不能等成交后再赌可用余额够，也不能借另一张单的预留。 |
| reservationId / 绑定 | 预留编号及它属于谁、哪张单、哪种币的证明。 | 账户总预留够，不代表本次成交有合法资金来源。 |
| 成交切片占资 | 按订单限价分配给本次成交数量的资金。 | T1 对应占资 6,010 USDT，不能只扣实际价款后漏掉差额。 |
| 价差返还 | 切片占资减去实际成交付款。 | T1 返 10 USDT，与卖方到账同事务发生，不先全额解冻。 |
| leavesQty / 剩余预留 | 还可能成交的数量及其资金支撑。 | 丙剩 0.05 BTC 挂单，不能因甲全成就清掉预留。 |
| 同水位解释 | 拿相同处理位置的订单与资金状态一起判断。 | 撮合已到 102、账务仍在 101，不能按最新零剩余量退款。 |
| 账户侧订单投影 | 随账务结果有序推进的订单数量记录。 | 用于核对前后数量及预留，不用异步页面作资金裁决。 |
| 有序撤单结果 | 权威序列中确定取消了多少的记录。 | 103 先到也要等 102，先交付成交，再退真正剩余。 |
| TTL / 超时 | 等待期限或没收到答复，不是业务裁决。 | 可触发查询和告警，不能授权自动释放未知订单的资金。 |
| Place / AbortIntent | 下单与关闭原意图的有序命令。 | 同序列裁决先后，关闭先赢就挡住迟到下单。 |
| APPLIED / 释放幂等 | 已完成记录让同一退款只生效一次。 | 整批资金、分录、去重和水位共同提交，同编号异金额须隔离。 |
| 非负 / 预期版本 | 更新时检查资金下界和记录是否被别人改过。 | 与唯一约束共同防错，不能只靠 Redis 标记已退。 |
| 收入侧与付款侧收费 | 从收到的资产扣，或额外从付款资产扣。 | F1 收入侧不加付款预留；改付款侧必须另定费用覆盖上界。 |
| 竞态 / 过早可用 | 两件事先后交错导致资金被提前拿走。 | 总额最终平衡也不能掩盖中途同一笔钱被重复花费。 |

## 把整篇文章压缩成一个故事

甲有 20,000 USDT，要限价买 0.25 BTC。资金管理员小许先给 B1 单独预留 15,025 USDT，留下 4,975 可用。这个动作不是付款，而是保证成交以后有指定资金履约。撮合先让甲买乙的 0.10 BTC，再买丙的 0.15 BTC。页面已经显示甲全成，甲想立刻解冻，小许却不能照办：执行资格虽然用完，成交款还可能没有结转，先退掉会让甲在别处花掉同一笔钱。

小许按成交数量切片处理。T1 原占资 6,010 USDT，实际付乙 6,000，差额 10 退甲；T2 原占资和付款都是 9,015。整批同库提交后，甲预留减少 15,025，实际付款 15,015，可用变为 4,985 USDT，并收到 0.25 BTC。丙原预留 0.20 BTC，只交付了 0.15，所以 0.05 仍支撑挂单。判断这些剩余必须看账户已处理到的位置，不能把最新页面数量套到滞后的资金状态上。

现在只新增原文的撤单变体：丙在成交后撤掉余下 0.05 BTC，主成交在 102，撤单在 103。即便撤单消息先到，小许也先存着，补齐并应用 102 后，再按 103 退回 0.05，而不是把原来 0.20 全退。退款编号、预留绑定、余额、分录、应用去重和连续水位同事务保存，重复送来的撤单只复用结果；同编号却换了退款量，就必须暂停核查。

另一种故障是预留完成后下单超时，暂时查不到订单。小许不会靠定时器擅自退钱，而是让关闭意图与原下单进入同一权威序列：关闭先到就封住迟到下单，下单先到就保留已有成交、只取消剩余。若本单预留异常不足，也不能拿别单资金遮盖缺口。最后若产品改成付款侧另收费用，还得重新证明预留上界；这已改变零费用条件，不能后台换配置后强扣旧订单。

**流程位置与核心机制：** 覆盖预留从下单占资到成交付款、价差返还和剩余撤单退款的全过程，重点是同水位解释资金、关闭执行资格与释放依据；不重新讲撮合算法。使用总览零费用主线。

## 第 1 层：为什么成交时不直接扣可用余额

**面试官：** 撮合完成后，为什么不能直接查一下买方可用余额，够就扣，不够就取消这笔成交？

**面试者：** 因为撮合结果一旦提交，买卖双方已经形成确定交易义务，不能等到账务时再决定履不履行。若成交前没占资，甲的资金可能同时被另一交易对、提现或第二笔订单使用，后来查余额即使发现不足，也不能让已经卖出的乙承担这次竞争结果。

本模型在下单接纳前先建立订单级预留：甲 20,000 USDT 中占用 15,025，剩 4,975 可用。预留绑定稳定下单意图、订单载荷和资产，只能被这笔意图的权威结果消耗或释放。这样账务处理既成成交时有明确资金来源，不依赖当时可用余额碰巧足够。

## 第 2 层：一笔预留怎样同时支付两次成交

**面试官：** 甲预留了 15,025，但实际只需付 15,015。两笔成交应该各扣多少预留，10 USDT 何时退？

**面试者：** 按买单限价给每个成交数量切片分配占资。T1 成交 0.10 BTC，这部分原占资 `60,100 × 0.10 = 6,010`，实际付款 `60,000 × 0.10 = 6,000`；同一次结转中从预留移出 6,010，其中 6,000 给乙，10 回甲可用。T2 的 0.15 BTC 原占资和付款都是 9,015，没有价差。

整个批次移出甲 15,025 预留，形成卖方收款 15,015 和甲价差返还 10。甲剩余可用从 4,975 变为 4,985。这里没有“先全部解冻再扣可用”的中间步骤，预留消耗和差额返还与双边到账共同提交。

## 第 3 层：卖方剩余预留为什么不能一起清零

**面试官：** 甲已经全成，批次也结算了，能否顺便把丙的预留全部释放？

**面试者：** 不能。预留归属订单，不归属某个批次的整体完成标签。丙的 S2 原卖 0.20 BTC，本批次仅交付 0.15，仍有 0.05 挂单。因此只从 S2 预留移出 0.15 给甲，剩余 0.05 继续受限；S1 全部交付 0.10，预留才归零。

在账务追到同一结果位置后，卖单预留目标应等于有效剩余数量，买单则是限价乘有效剩余数量。但这个“同一位置”很重要：它不是拿任意时刻查到的撮合剩余量，直接覆盖账户预留。若撮合比账务快，剩余量已经下降的那部分可能还没有付款。

## 第 4 层：为什么不能按最新订单状态重算预留

**面试官：** 你强调同一位置。假设撮合页面已经显示 B1 剩余量为零，账务水位却还在 101，按零预留更新究竟错在哪里？

**面试者：** 页面显示的是结果 102 之后的执行状态，而账户还停在 101。把执行状态的零剩余量用于账务 101，会把尚需支付 T1、T2 的 15,025 预留全部退走。两份数据各自可能正确，拼在一起却是跨水位错误。

账户域应维护跟随结转推进的订单结果投影，在处理 102 时验证 before/after 数量、消耗与释放，最后共同推进到 102。账务落后时，预留包含未履约成交义务、未结转的价差以及仍可能成交的剩余占资；不能只用最新 leavesQty 表达这几类资金。

这也是为什么对账要选共同水位，不能拿“现在订单终态”去判定“历史账务多冻结了多少钱”。

## 第 5 层：部分成交后撤单怎样确定能退多少

**面试官：** 现在换一个独立异常变体：S2 在本批次成交 0.15 BTC 后，丙撤掉剩余 0.05。若撤单消息先到资金系统，怎么办？

**面试者：** 只改变 S2 后续增加撤单这个条件，主批次仍是 102。假定撤单结果在同交易对后续位置 103，明确取消的有效剩余量是 0.05 BTC。资金系统先收到 103，也必须暂存等待 102，不能把“订单已撤”解释为原 0.20 BTC 全退。

先应用 102，将 0.15 交付给甲，S2 预留剩 0.05；再应用 103，把 0.05 从预留退回丙可用。103 的释放动作应引用 S2 的预留和结果身份，与数量变化一致。如果 103 也有其他成交，就按完整权威结果处理，不能只抽取撤单字段先解冻。

因此决定释放的是撮合排序后的实际撤销量及前序义务已处理的事实，不是用户点击撤单的时间，也不是消息到达顺序。

## 第 6 层：请求超时而没有订单，能否定时释放

**面试官：** 如果预留成功后下单调用超时，查询暂时又找不到订单，资金一直冻着也不行。能否给预留加 TTL 自动退？

**面试者：** 不能把 TTL 当成资金释放授权，因为原 Place 命令可能仍在网络、日志或处理队列中。若先退款，迟到命令仍被撮合接纳，就会生成没有资金覆盖的成交；一次“查不到”不能证明未来绝不会执行。

需要有序关闭原意图。相邻撮合基线的 Place 与 AbortIntent 进入同一权威命令序列：关闭先赢，就留下拒绝后续 Place 的持久关闭标记；Place 先赢，则关闭操作撤销当时剩余量，并保留此前成交义务。账户域消费最终关闭结果，在前序处理完成后释放真正可退的部分。

超时任务可以触发查询、告警或关闭请求，但没有独立解冻权。这是让冻结可终止的业务协议，不是要求用户无限等待，也不是把超时强行当成未成交证据。

## 第 7 层：重复释放怎样在执行处阻止

**面试官：** 有序关闭解决了资格问题，但同一个退款结果投递两次，会不会把资金退两次？

**面试者：** 释放动作必须跟随稳定结果身份，进入同一个批次应用事务。事务核对 batchId 和 planHash，锁定订单级预留，检查待释放数量及预期版本，然后共同更新预留、可用余额、分录、APPLIED 和水位。第一次已提交后，第二次只能读到相同批次的既有完成记录，不再产生资产变化。

不能仅在 Redis 里先标“已退”再改数据库：先标后崩溃会漏退，先退后标会重退。数据库唯一约束提供持久防重边界，非负及绑定校验提供金额约束，两者不能互相替代。若同一个 ID 携带不同释放金额，不应直接返回成功，而要隔离冲突。

## 第 8 层：共享余额足够为什么仍不能借另一个订单的预留

**面试官：** 若某订单预留记录不足，但甲在另一订单中还冻着很多钱，先挪过来结清，之后对账补回不行吗？

**面试者：** 不行。另一笔预留支撑另一项仍可能执行的交易义务，挪用只是把本笔缺口转移到下一笔。账户总预留大于本次付款，不代表本订单拥有这份资金；必须检查 reservationId、账户、资产、订单意图和金额绑定。

若正常源结果按预期应用却发现本订单预留不足，说明更早的占资、释放、数据恢复或规则边界出了问题，应停止这个位置，保护相关账户并查明差异。不能通过“借冻结”使当前事务表面成功；否则余额总量也许没有变化，却已有两笔义务共享同一份钱，风险被隐藏而不是解决。

数据库中既要维护账户资金桶，也要维护订单预留明细及汇总对应关系。跨交易对共用账户的并发，通过统一数据库锁或条件更新协调，不靠本交易对单写者替其他交易对作保证。

## 第 9 层：费用变化会不会破坏预留公式

**面试官：** 你一直按限价乘数量预留。如果产品要求从买方付款侧收手续费，这个公式还成立吗？

**面试者：** 不成立，除非另有已授权、可靠覆盖的费用资金来源。总览 F1 特意选择从收入侧扣费，所以原付款预留仍够；如果改为买方从 USDT 额外支付费用，就要在下单时按明确规则预留价款加费用上界，并冻结费率及舍入政策。

在订单可拆成多次成交时，逐笔向上取整可能使总费用高于“总价款乘费率再取整”，所以上界还要考虑计费粒度、最小成交粒度或产品采用的累计计费规则。不能只说“多冻一点”而没有证明覆盖范围。

这属于明确改变收费条件后的方案。既有订单若没有覆盖新增费用，不应通过后台更新费率强行扣出负数，必须维持原规则或走重新授权流程。

## 第 10 层：怎样验证释放协议真的封住了竞态

**面试官：** 如果只选几个最能暴露问题的时序，你会怎样检查这套资金释放设计？

**面试者：** 第一组检查成交与释放：让撮合已到 102、账务仍在 101，页面显示全成，确认没有任何查询或定时器能绕过结果应用直接解冻。第二组检查撤单乱序：先到 103 撤单、后到 102 成交，最终应先交付 0.15 BTC 再退 0.05，绝不能退 0.20 后又尝试扣款。

第三组检查迟到 Place：预留后调用超时，AbortIntent 与 Place 在两种顺序下分别裁决。关闭先赢，迟到 Place 永不接纳；Place 先赢，关闭只退未履约剩余量。第四组把退款结果重投、提交响应丢失、进程重启组合起来，资金效果仍只出现一次。

这些检查各自有执行处证据：权威有序关闭标记、连续账务水位、订单级预留绑定、同事务 APPLIED 和唯一约束。不是最后看总余额差不多就算通过；金额守恒也检测不出所有错误时序，尤其检测不出短时间可被重复花费的过早释放。

## 本题收束

- **讲透的机制：** 预留覆盖的是执行资格和未履约义务；付款、价差返还与剩余释放都要按权威结果位置推进。
- **最容易答错的边界：** 最新终态不等于已付款，查询不到不等于未来不执行，总预留充足不等于本订单可用，TTL 不等于解冻授权。
- **检验反例：** 先把预留退给甲，让甲在另一交易对花掉，再收到原成交；如果方案把这个缺口留给“记账失败后对账”，就没有在事前阻止无覆盖成交。
