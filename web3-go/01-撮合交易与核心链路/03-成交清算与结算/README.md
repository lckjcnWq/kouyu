# 成交清算与结算

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本专题讲链下托管 BTC/USDT 现货成交后，怎样确定收付义务并在内部账上履约。主线零手续费、相关账户同库；费用与链上履约另设变体，不能把“已成交”“算好账”和“钱已可用”混为一谈。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 清算 | 算清谁应该付什么、收什么。 | 生成收付义务，不等于余额已更新，也不是强制平仓。 |
| 结算 / 内部结转 | 把应收应付真正落实到账上。 | 主线是内部账户变动，不代表银行付款或链上最终确认。 |
| 限价 GTC / 挂单价成交 | 限价是可接受的价格边界，未成交部分继续等。 | 甲最多付 60,100 USDT/BTC，遇到乙则按乙的 60,000 成交。 |
| 可用余额 / 订单预留 | 可用的钱还能花；预留的钱专门支撑指定订单。 | B1 占住 15,025 USDT，不得挪给另一张订单。 |
| ResultBatch | 一条命令产生的完整结果包。 | 两笔成交、订单变化和预留动作不能拆成残缺事实。 |
| commandSeq / batchId / tradeId | 命令排号、整包编号、包内成交编号。 | 身份由权威结果固定，补送和重试不能换号。 |
| sourceHash / 完整性 | 摘要用于发现内容改变；完整性还要查是否漏项。 | 摘要一致不证明来源可信，也不证明成交没有漏掉。 |
| SettlementPlan / planHash | 固定的履约清单及其内容指纹。 | 列明资产、金额、费用和预留动作，重试沿用原计划。 |
| ruleVersion | 当时采用的规则版本。 | 历史费用和舍入不能被今天的新配置改写。 |
| tick / lot / 最小账务单位 | 把价格、数量、金额分别变成整数刻度。 | 订单数量步长与 BTC 细账单位不同，不能混用。 |
| 价差返还 | 原先多占、最终没花出去的钱。 | 15,025 减 15,015，返 10 USDT，不是交易利润。 |
| Inbox / 运输确认 | Inbox 是可靠收件箱，确认只说明输入已接管。 | 消息签收不代表资金到账，之后还要计算并应用计划。 |
| READY / APPLIED | 前者是计划固定，后者是账务已提交。 | 订单全成仍可能待结转；迟到失败不能推翻 APPLIED。 |
| 同库事务 / 双边原子性 | 在一个数据库里，一组修改全成或全不成。 | 整批分录、余额、预留、应用去重和水位一起提交，不跨独立分片。 |
| 幂等 / 至少一次交付 | 可以收到多次，但同一业务只生效一次。 | 同编号同内容复用；同编号异内容必须隔离。 |
| 连续水位 / 空批次 | 水位标出连续完成的位置；无成交结果也占位置。 | 缺前序就补齐，不能用收到的最大编号冒充完成进度。 |
| 逐币种平衡 / 不变量 | 每种资产各自进出相抵，并守住数量边界。 | BTC 与 USDT 不能混加；平衡也不能证明收款人正确。 |
| Outbox / 查询投影 | 提交后待发通知箱，以及便于读取的副本。 | 通知可迟到，页面副本无权反向裁决余额。 |
| 对账 / 追加修复 | 按相同进度核对证据，出错后留下新凭据纠正。 | 不覆盖原成交、不静默改余额，也不跳过问题批次。 |
| 费用 F1 / 链上最终性 / MVP | 分别是费用变体、链上完成规则和最小教学模型。 | 三者各有额外前提，内存推演不证明数据库恢复或链上能力已实现。 |

## 把整篇文章压缩成一个故事

甲拿着 20,000 USDT 来买币，限价 60,100，想买 0.25 BTC。平台先为他的 B1 留出 15,025 USDT，留下 4,975 可用。乙已经挂卖 0.10 BTC，价格 60,000；丙挂卖 0.20 BTC，价格 60,100，两人的币也已预留。撮合把甲与乙、丙依次配上，产生价款 6,000 和 9,015 的两笔成交。此时确定的是交易事实，不是甲已经拿到可再次花费的币。

负责清算的小林收到完整结果包，先核验来源、编号和有没有漏掉订单变化，再把两笔成交变成不可随意改写的履约清单。主线没有手续费，清单写明甲应付 15,015 USDT、应收 0.25 BTC，并退回多占的 10 USDT。计算采用明确的整数刻度和历史规则版本，不能拿实时行情重估，也不能把另设费用变体的净到账偷偷搬进来。收件箱落盘、清单准备好和真正记账，是不同的完成阶段。

账务员等前序水位完成，才在同一个数据库事务里整包处理。甲付款、卖方收款、双方币的转移、预留变化、分录、应用去重和连续进度一起提交。甲最终有 4,985 USDT 和 0.25 BTC；乙收到 6,000 USDT，丙收到 9,015 USDT，丙未卖的 0.05 BTC 继续预留。检查时 USDT 与 BTC 各算各的，不能折成一个总数；收支平衡之外，还须验证钱确实去了正确的人和订单。

如果结果重复送来，小林比对原身份和内容，不再记账；如果后序先来，就存好等缺口补齐，撤单退款不能抢在成交付款前面。事务中途失败则整包回滚，提交回音丢失则查持久记录，不能凭超时猜没成功。对账发现真错，要留证据并追加修复。末尾内存演示只帮助手算这些约束；逐笔与净额的范围、失败恢复，以及改成链上履约后的最终性，都必须另外说明，不能当成演示已经证明的能力。

## 第一部分：文字全流程

### 1.1 讨论基线

本专题沿用[撮合交易从 0 到 1](../01-撮合交易从0到1/README.md)的主要假设，并把重点从“怎样决定成交”移到“怎样履行已确定的成交义务”。

- **产品与执行：** 链下托管 BTC/USDT 现货，限价 GTC，价格时间优先，以已有挂单价格成交；没有杠杆、借贷、强平或 AMM。
- **状态归属：** 撮合域决定订单执行状态和成交；清算模块按固定规则计算收付义务；账户账务域决定余额、预留、分录和账务完成状态。
- **可靠输入：** 撮合结果以完整 `ResultBatch` 提交到持久化有序结果日志。一个交易对内的 `commandSeq` 连续；每条已处理命令都有结果，包括没有成交的空批次。成交批次及撮合执行进度共同原子提交后，才属于确定事实。
- **结转边界：** 本模型所有参与账户、预留、账务分录及消费水位位于同一个支持事务的关系数据库；一个完整结果批次在一个数据库事务中结转。不假定单库事务能跨越独立分片。
- **手续费：** 贯穿主案例为零。第 03 题单独改变费用条件，给出非零费率、收取币种与舍入规则；不能把该变体的净到账套回零费用主线。
- **资金范围：** 内部账户结转，不发生链上转账。第 12 题只在明确改变履约方式后讨论链上提交、确认与最终性，不将它们视为本基线已实现的能力。

这里的“清算”指确定成交后的收付义务，不是合约交易中的强制平仓；“结算”在主线中指内部账务履约，不意味着银行付款或链上最终确认。

### 1.2 贯穿案例与初始状态

所有金额以 USDT 表示，价格单位为 USDT/BTC。为隔离无关因素，三名用户没有其他订单、充提或账户变化。

| 账户或订单 | 下单前资产与意图 | 下单预留 |
|---|---|---|
| 甲，买单 B1 | 20,000 USDT，买 0.25 BTC，限价 60,100 | 15,025 USDT；可用剩 4,975 USDT |
| 乙，卖单 S1 | 0.10 BTC，挂卖价 60,000 | 0.10 BTC |
| 丙，卖单 S2 | 0.20 BTC，挂卖价 60,100 | 0.20 BTC |

S1、S2 已挂入订单簿，预留均有效。B1 入场，撮合产出同一个批次中的两笔成交：

| 成交 | 买方 / 卖方 | 价格 | 数量 | 价款 |
|---|---|---:|---:|---:|
| T1 | 甲 / 乙 | 60,000 | 0.10 BTC | 6,000 USDT |
| T2 | 甲 / 丙 | 60,100 | 0.15 BTC | 9,015 USDT |
| 合计 | — | — | 0.25 BTC | 15,015 USDT |

为便于追问，将该次 B1 命令的结果位置记为 `BTC-USDT/102`，账务此前已应用到 `101`。`102` 只表示本例的位置，不是必须从此编号开始；此前已提交的预留、挂单结果和水位共同构成起点。

### 1.3 从用户发起到资金完成的主链路

```text
甲提交买单 B1〔限价 60,100，数量 0.25 BTC，稳定请求身份〕
    ↓
账户域原子建立预留〔15,025 USDT，绑定 B1 的意图和订单载荷〕
    ↓
撮合域可靠受理、排序并执行〔这时不代表账务已经完成〕
    ↓
提交完整 ResultBatch〔BTC-USDT/102〕
    ├─ T1：甲向乙买 0.10 BTC，价款 6,000 USDT
    ├─ T2：甲向丙买 0.15 BTC，价款 9,015 USDT
    ├─ B1、S1 全成；S2 剩余 0.05 BTC
    └─ 订单变化、预留动作与批次完整性信息一同固定
    ↓
交付器从已提交结果日志投递〔允许重复，不允许重新生成成交身份〕
    ↓
清算入口校验来源、批次身份和完整性 → 持久化 Inbox
    ↓
清算模块按已冻结规则生成不可变 SettlementPlan
    ├─ 收付资产与数量、费用、预留消耗与释放
    └─ sourceHash、ruleVersion、planHash
    ↓
账务应用器等待前序水位 101，开始数据库事务
    ├─ 锁定交易对账务水位及相关预留、余额
    ├─ 验证计划、数量边界、预留来源和逐币种平衡
    ├─ 消耗甲预留，支付 15,015 USDT，退价差 10 USDT
    ├─ 甲增加 0.25 BTC；乙增加 6,000 USDT；丙增加 9,015 USDT
    ├─ S1 预留归零；S2 保留 0.05 BTC 预留
    └─ 分录、余额、预留、APPLIED、水位 102、通知 Outbox 共同提交
    ↓
已提交账务结果成为内部履约事实
    ├─ 可用资产可供后续交易使用
    └─ 通知 / 查询投影异步更新〔迟到不撤销已经成立的结转〕
```

Inbox 落盘可以作为运输层确认条件，以免依赖长时间持有消息；账务应用器另行重试。**运输确认、清算计划落盘、账务提交是三个边界。** 日志保留与归档必须覆盖尚未安全接管和应用的结果，不能因消息已确认就删掉唯一事实。

### 1.4 主要异常分支

```text
下单校验拒绝 → 不产生成交义务；若已预留，凭有序拒绝 / 关闭结果释放

下单调用超时 → 受理与执行可能已发生
    → 查询或有序关闭原意图，不能直接按超时解冻

成交已提交，结果暂未送达 → 保留预留与成交义务 → 从结果日志补送

结果重复 → 同身份同载荷复用原记录；同身份不同载荷隔离并阻断

收到 104，但账务只到 102 → 持久化等待 → 补取完整 103 → 按序应用

账务事务中途失败 → 整批回滚 → 原计划重试，不删成交、不补发新成交

提交响应丢失 → 按稳定批次身份查询 APPLIED；不凭超时推定未提交

订单部分成交后撤单 → 先履行前序成交义务 → 再按有序撤单结果退实际剩余预留

计划金额错误或规则版本缺失 → NEEDS_REVIEW，停止该交易对推进
    → 定位证据、审批修复，不能跳过后继续释放后序资金
```

暂时的数据库故障进入可重试状态；内容冲突、无法解释的预留不足等进入人工核查状态。两者不能混成“失败了就无限重试”。

## 第二部分：核心板块

| 核心板块 | 决定什么、拥有什么状态 | 为什么核心 | 上下游契约 |
|---|---|---|---|
| 成交事实接管 | 稳定批次、成交身份、来源与载荷摘要 | 输入换身份、缺半批会直接改变经济结果 | 上游完整提交；下游可靠接管、可核对 |
| 清算义务计算 | 收付明细、费用规则版本、计划摘要 | 决定谁应收付哪种资产及多少 | 只消费确定事实，不重撮合、不按现价重估 |
| 预留结转 | 订单级预留、已处理结果位置、释放动作 | 防止先解冻再扣款和跨订单挪用 | 按同一结果位置解释剩余量与资金 |
| 原子账务应用 | 分录、余额、幂等记录、结转状态、水位 | 防止单边到账和重复扣款 | 整批同事务，提交后才成为可用资产 |
| 可靠推进与恢复 | Inbox、缺口、重试、阻断原因、恢复位置 | 消息成功不等于履约成功 | 可补投、可重放、不能越过缺口 |
| 对账与修复 | 同水位证据、差异、追加调整与审批 | 为错误提供可审计收敛路径 | 不覆盖原始成交，不静默改余额 |

撮合算法、完整总账科目设计、持仓成本法、充提风控与智能合约实现属于相邻专题；这里仍须说明资金与状态契约，不能以边界为由跳过双边结转。

## 第四部分：设计与规则

### 4.1 不变量与金额单位

#### 整数表示

- `priceTicks`：每 tick 为 `0.01 USDT/BTC`。
- `qtyLots`：每 lot 为 `0.0001 BTC`，用于订单与成交数量。
- `quoteUnits`：每单位为 `0.000001 USDT`，所以 `quoteUnits = priceTicks × qtyLots`。
- `baseUnits`：BTC 账务最小单位为 `0.00000001 BTC`，所以 `baseUnits = qtyLots × 10,000`。订单步长与账务单位不同；细账务单位用于精确计费，并未放宽订单数量步长。

主案例中 `6,010,000 ticks × 2,500 lots = 15,025,000,000 quoteUnits`。十进制字符串精确解析；先校验正数、步长、业务上限和乘法溢出。Go 的 `int64` 在受控上限内使用；更大中间值可用 `math/big.Int`，但仍需限制输入大小，不能让任意精度变成无界资源消耗。

#### 数量、义务与资产守恒

```text
originalQty = cumFilledQty + leavesQty + canceledQty

每笔成交：买入 baseUnits = 卖出 baseUnits
零费用主线：买方支付 quoteUnits = 卖方收到 quoteUnits

每种资产：本批次所有受影响资金桶的有符号变化之和 = 0
余额、预留均非负；某订单的预留不能被另一订单借用
APPLIED 对应完整计划，不能只对应一条已执行 SQL
```

这里的“资金桶变化”用于说明内部资产转移，不把有符号增减直接等同于完整财务总账的借贷科目。正式复式账要依据科目性质定义借贷方向；不能拿 BTC 与 USDT 按汇率相加抵平。

#### 预留与结果位置

在账务已经应用到同一结果位置后，买单剩余预留目标为 `limitTicks × leavesLots`，卖单目标为 `leavesLots × 10,000 baseUnits`。对一个买方成交数量切片：

```text
该切片占资 = limitTicks × fillLots
实际价款   = tradeTicks × fillLots
价差返还   = 该切片占资 - 实际价款
```

同一事务内把切片占资从买单预留移出，其中实际价款给卖方，差额回买方可用余额。T1 占资 6,010，付款 6,000，返 10；T2 占资 9,015，付款 9,015，返 0。该批次合计移出 15,025 预留。

这是已应用顺序下的计算，**不是用撮合最新剩余量直接覆盖当前预留**。账务滞后时，预留还要覆盖已成交但未结转的义务。只有有序的权威拒绝、撤单或意图关闭结果，才允许退相应未履约剩余资金。

### 4.2 权威状态与架构

```text
撮合域：已提交 ResultBatch〔成交与订单执行事实〕
    ↓ 可重投的交付器
清算入口：Inbox〔来源、完整载荷、摘要、接管状态〕
    ↓ 固定规则计算，无资产副作用
清算模块：SettlementPlan〔收付、预留动作、版本、摘要〕
    ↓ 每交易对按序应用，跨交易对可并行
账户数据库〔统一事务边界〕
    ├─ Settlement：READY → APPLIED
    ├─ Journal：不可变资金变动凭据
    ├─ Balance / Reservation：权威余额与订单级预留
    ├─ LedgerCursor：每交易对连续水位
    └─ Outbox：已提交结转回报
         ↓
查询、通知与对账投影〔不拥有反向改账权〕
```

同一数据库可以承载逻辑分离的清算和账务模块，不为展示微服务数量拆开原子性。Redis 缓存、消息队列 offset 和进程内互斥锁均不能替代数据库中的资金约束。

### 4.3 对象、身份与状态

| 对象 | 身份与必要字段 | 约束 |
|---|---|---|
| ResultBatch | `batchId=(symbol,commandSeq)`，`ruleVersion`，trades、orderChanges、reservationActions、计数、`sourceHash` | 摘要针对规范化业务载荷，不包含可变投递时间；完整性须结合权威来源核验 |
| Trade | `tradeId=(symbol,commandSeq,matchIndex)`，双方账户 / 订单 / 预留、整数价量 | 重投不换身份；非消费端随机生成 |
| SettlementPlan | `planId=batchId`，`sourceHash`、清算及费用版本、legs、释放明细、`planHash` | 同源同版本确定性计算；READY 后不原地重算为新金额 |
| Inbox | 唯一 batchId、sourceHash、原载荷、接管时间与状态 | 同键同载荷复用；同键异载荷冲突阻断 |
| Reservation | reservationId、accountId、orderId / intentId、asset、remainingUnits、version | 绑定原下单意图，不能用“余额足够”代替该预留来源 |
| Journal / AppliedBatch | batchId、planHash、稳定 legId、有符号金额、资产、资金桶 | 批次应用唯一；历史分录不覆盖 |
| LedgerCursor | symbol、lastAppliedSeq | 与本批次所有资产效果共同提交 |
| Outbox | 稳定 eventId、batchId、账务版本、结转结果 | 与账务共同提交，发布仍允许重复 |

`sourceHash` 能发现内容变化，却不能单独证明“没有漏掉本应存在的成交”。还要核对完整批次记录、清单和权威日志；攻击者自己造一个摘要不构成可信事实。

状态语义：`RECEIVED` 表示 Inbox 已接管；`READY` 表示计划已固定；`APPLIED` 表示本地账务事务成功。暂时失败保留重试信息；`NEEDS_REVIEW` 表示遇到冲突、版本缺失或不变量破坏，阻断该位置。`APPLIED` 是单向完成状态，迟到失败消息不能将其降级。订单的 `FILLED/CANCELED` 不替代这些状态。

### 4.4 共同提交边界与 Go 实现选择

账务应用事务按以下逻辑执行：

1. 锁定该交易对 `LedgerCursor`，核实前序位置；已应用批次必须再核对摘要，不能只返回“成功”。
2. 按全局固定的资源键顺序锁定本批次涉及的预留与余额；其他资金写入路径也遵守兼容顺序。条件更新仍检查非负、绑定关系和预期版本。
3. 从连续的账户侧订单结果投影验证 before/after 数量，验证收付与预留动作、逐币种平衡；不查询异步页面缓存作决策。
4. 在同一事务里写分录、改余额与预留、更新订单结果投影、记录 APPLIED 和 planHash、推进水位并写 Outbox。
5. 提交成功才返回资金完成；`Commit` 响应不确定时按 batchId 查询持久结果。运输 offset 不单独决定业务是否应用。

Go 的 worker 数量有界，每个交易对只有一个有效的应用序列；跨实例仍靠数据库约束，不靠 goroutine 自觉。计划计算可以并行，资金应用仍受顺序和锁约束。所有 SQL 错误、影响行数、事务提交错误都须检查；错误分类与重试上限见对应母题。

### 4.5 费用变体 F1：只在第 03 题改变条件

F1 不改变价格、成交量和成交身份，只将双方费率都设为 10 bps，即 0.1%；为简化示例，maker/taker 同费率。买方从收到的 BTC 扣费，卖方从收到的 USDT 扣费，按每笔成交、每个收费侧、最小账务单位向下取整：

```text
feeUnits = floor(grossReceivedUnits × 10 / 10,000)
netReceivedUnits = grossReceivedUnits - feeUnits
```

手续费进入平台对应资产费用桶，不凭空消失；不另收下单前额外费用，因此本变体无需增加原有付款预留。费率、收费币种、粒度、舍入及生效版本在接纳时冻结，结果与计划引用同一版本。

F1 合计：甲收到 `0.24975 BTC`；平台收到 `0.00025 BTC`；乙收到 `5,994 USDT`；丙收到 `9,005.985 USDT`；平台收到 `15.015 USDT`。甲仍付款 15,015 并返价差 10；丙仍预留 0.05 BTC。这里不支持返佣、负费率或独立平台币抵扣，它们需要另行定义规则。

## 第七部分：工程实践——唯一的简洁 MVP

### 7.1 目标与范围

验证零手续费下一个完整成交批次的整数计算、订单级预留消耗、双边资产守恒、同批次重复不再生效和顺序缺口阻断。使用单进程、串行、内存状态的复制后替换模拟整批原子提交，**不验证数据库持久性、跨实例并发、可靠运输、主备、对账修复或链上履约**。

MVP 的输入仅包含可信的教学结果及其规范化身份；来源真实性验证是生产边界，不用一个空壳函数冒充已经实现。

### 7.2 核心伪代码

```text
Apply(batch, state):
    // 金额为受上限约束的整数；batch 不含投递时间等可变字段
    if batch.id in state.applied:
        require state.applied[batch.id] == batch.canonicalPayload
        return "原批次已应用"
    require batch.seq == state.cursor[batch.symbol] + 1
    next = deepCopy(state)  // 失败只丢弃 next，不修改 state
    delta = emptySignedMap()  // key = (account, asset, available/reserved)
    for trade in batch.trades:
        require trade.id 唯一且属于 batch，价格数量均合法，乘法不溢出
        require trade.priceTicks <= trade.buyLimitTicks
        require trade.priceTicks >= trade.sellLimitTicks
        require 买卖账户、订单与预留绑定匹配输入的已有记录
        quote = trade.priceTicks * trade.qtyLots
        held = trade.buyLimitTicks * trade.qtyLots
        base = trade.qtyLots * 10000
        next.reservation[trade.buyOrder] -= held
        next.reservation[trade.sellOrder] -= base
        delta[buyer, USDT, reserved] -= held
        delta[buyer, USDT, available] += held - quote
        delta[seller, USDT, available] += quote
        delta[seller, BTC, reserved] -= base
        delta[buyer, BTC, available] += base
        next.filled[trade.buyOrder] += trade.qtyLots
        next.filled[trade.sellOrder] += trade.qtyLots
    require batch.orderChanges 恰好覆盖本批次受影响的订单，无缺失或重复
    for change in batch.orderChanges:
        order = change.orderId
        require change.beforeFilled == state.filled[order]
        require next.filled[order] == change.afterFilled <= state.originalQty[order]
        next.leaves[order] = state.originalQty[order] - next.filled[order]
        require next.leaves[order] == change.afterLeaves
        expected = 买单限价 * next.leaves[order] 或卖单 next.leaves[order] * 10000
        require next.reservation[order] == expected >= 0
    require 对每一种资产，sum(delta[*, asset, *]) == 0
    for key, amount in delta:
        next.buckets[key] += amount
        require next.buckets[key] >= 0
        append next.journal with (batch.id, key, amount)
    next.applied[batch.id] = batch.canonicalPayload
    next.cursor[batch.symbol] = batch.seq
    state = next  // 教学内存模型的唯一提交点
    return "APPLIED"
```

为控制范围，这段伪代码只接受成交批次和相应订单变化，不实现撤单批次；撤单释放规则由第 04 题论证，不声称已被 MVP 覆盖。生产系统也不能把 `state = next` 当成数据库事务或灾备协议。

### 7.3 输入与预期结果

| 输入 | 手工推演的预期结果 |
|---|---|
| 初始预留如主案例，水位 101，输入批次 102 的 T1、T2 | 甲可用 4,985 USDT 和 0.25 BTC；乙 6,000 USDT；丙 9,015 USDT 且仍预留 0.05 BTC；水位 102 |
| 再输入相同身份、相同规范化内容的 102 | 返回原批次已应用，不新增分录、不再次扣预留 |
| 相同身份 102，但把 T1 价款或数量改掉 | 身份内容冲突，原状态不变，不当作一次新结算 |
