# 大问题 6：成交怎样可靠交付而不重复记账？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文沿用零费用、同库整批结转，讲如何容忍重复发送而只产生一次资金效果。运输确认、计划固定和资金提交各有边界，消息系统的成功不能代替账户数据库的成功。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 至少一次运输 / 一次业务效果 | 同一包可反复送，资金只正式变一次。 | 不追求网络只发送一次，而在账务执行处防重。 |
| 结果日志 / 完整 ResultBatch | 可补送的确定事实来源。 | 成交、订单变化与撮合执行进度先共同提交，不补造新成交。 |
| Inbox / RECEIVED | 持久收件箱及已可靠接管状态。 | 提交成功后才能确认收到，崩溃后仍有任务可查。 |
| ACK | 运输层的签收回执。 | 不承诺清算完成，更不代表资金已经可用。 |
| 持久扫描器 / 唤醒队列 | 前者找未完成工作，后者只提示尽快去做。 | 进程内队列丢失不能让已接管义务永远消失。 |
| 稳定身份 / 规范化载荷 | 辨认同一业务，并比较不可变内容。 | 相同价量不同序号不是重复；同编号不同内容是冲突。 |
| sourceHash / planHash | 原始事实与固定履约计划各自的摘要。 | 用来核对绑定，不单独证明来源完整或计算正确。 |
| 数据库唯一约束 | 由存储裁决同一编号只能占一个位置。 | 两实例先查都不存在时，仍须靠约束和锁防并发重复。 |
| 事务错误 / 约束归因 | 分清是哪条约束或 SQL 真正失败。 | 不能把任意异常都当成别人已成功，失败事务须正确回滚。 |
| APPLIED / 水位同事务 | 完成凭据与连续进度随整包资金共同落地。 | 先改钱后写去重会重付，先标完成后改钱会漏付。 |
| Commit 未知 / 锁内重读 | 提交没回音时，通过原入口串行核查。 | 一次查询未命中不证明回滚，副本滞后和原事务未决都可能存在。 |
| exactly-once 的范围 | “恰好一次”只在具体系统边界内有意义。 | 队列内部事务不自动包住关系数据库的余额与分录。 |
| Outbox / eventId | 随资金提交的通知事实与稳定通知编号。 | 发布可以重试，下游去重，但通知不是另一条记账入口。 |
| 证据保留 / 可靠归档 | 把历史身份与内容凭据留到可核查的位置。 | 旧水位不能替代摘要，热表清理也不能清掉防重资格。 |
| 退避预算 / NEEDS_REVIEW | 临时故障限量重试，内容错误暂停核查。 | 不无限冲击数据库，不为推进跳过无法证明安全的位置。 |

## 把整篇文章压缩成一个故事

运输员把甲买币的完整批次 BTC-USDT/102 送给账务入口，网络却吞掉了签收回音。他不能重新撮合或换个编号，只能重送原包。入口的小唐核对权威来源与完整内容，先把它存入 Inbox，确认提交后才回 ACK。这表示“我可靠接管了”，不是“甲的币已可用”。即使随后进程崩溃，恢复扫描器也能从持久未完成记录找到任务，而不是等用户刷新或指望内存队列还在。

两台实例同时抢到任务时，小唐不相信“刚才查过还没有”，而让数据库唯一键、水位锁和计划状态裁决。重复内容复用旧记录，同编号换金额则留证阻断。清算先固定原零费用规则下的计划，再由账务整批应用：甲预留减少 15,025 USDT，卖方合计收 15,015，甲返 10 并收 0.25 BTC；分录、余额、预留、应用去重、连续水位和通知记录一起提交。不能先改钱后补标记，也不能先提交完成标记再慢慢付款。

如果提交回音丢了，小唐把状态记为未知，按原编号去权威库查。一次没查到仍不能补发，因为原事务可能还在提交，读副本也可能落后。他让重试回到同一加锁入口，等原事务决议后再核对：已完成就复用，确认回滚且前提满足才执行原计划。迟到的失败回调不能推翻 APPLIED。通知则从 Outbox 异步发送，重发通知不会变成第二次记账，队列自己的事务也不能代替这套数据库约束。

服务升级后，旧批次继续引用原计划与历史版本，不因默认费率变化给甲补扣费用。任务退出热表前，摘要、应用凭据和审计关系仍须可靠归档，不能让迟到输入变成新成交。数据库死锁可以退避重试，载荷冲突或预留异常却要停在原位核查。调度还要限制 worker 和重试量，分别观察接管积压与真正完成，避免把 ACK 很多误当成履约顺畅。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题从撮合结果已提交开始，追到输入可靠接管、重复识别和资金完成。重点是至少一次运输如何收敛为一次业务效果，不重复展开第 05 题的全部资产一致性证明，也不以消息队列的承诺替代账户数据库的提交边界。

沿用总览的零手续费、单关系库、完整 `ResultBatch` 整批事务基线。主案例批次为 `BTC-USDT/102`，账务起点水位为 `101`；T1、T2 的价款合计 15,015 USDT，甲退回价差 10 USDT，丙保留 0.05 BTC 预留。以下均为教学设计，不代表实测或个人生产经历。

## 第 1 层：把可靠送达与资金完成拆成不同承诺

**面试官：** 撮合已经提交 T1、T2，结果怎样可靠交付给账户系统，并保证不重复扣款？

**面试者：** 在这个模型中，我不追求网络上“只发送一次”，而是让已提交的成交结果可以反复发送，让账户数据库对同一经济事项只产生一次效果。撮合的完整结果批次与执行进度先共同提交到持久化结果日志，交付器只读取这些确定事实；清算入口可靠接管，固定清算计划，再由账务应用器在一个事务中完成整个批次。网络超时、确认丢失都允许重投，但不能重新撮合或生成一组新成交身份。

这里至少有三个完成边界：Inbox 持久化代表输入已接管，计划 `READY` 代表义务已经固定，账务 `APPLIED` 才代表资金完成。批次 102 只有在分录、余额、预留、批次应用记录和水位共同提交后，才能说甲取得 0.25 BTC、乙丙取得对应 USDT。消息发送成功或者消费者函数返回，并不具备这个含义。

## 第 2 层：Inbox 落盘后就 ACK，未记账的工作由谁接着做

**面试官：** 你允许 Inbox 接管后就确认消息。如果确认之后、资金应用之前进程崩溃，队列不再重投，成交会不会永久漏记？

**面试者：** 不会把后续推进寄托在原消息处理函数上。入口校验可信来源和完整批次后，把稳定批次身份、规范化载荷、`sourceHash` 与 `RECEIVED` 状态持久化，确认数据库提交成功才发送运输 ACK；提交结果不确定时，先核实接管记录，不能直接确认。独立的恢复扫描器或持久任务调度从这些未完成记录继续生成计划、等待水位和应用资金，进程内队列仅是唤醒手段，不是唯一任务来源。

因此，ACK 后崩溃可能留下 `RECEIVED` 或 `READY`，但这些都不是“工作已经结束”。接管存储必须有与承诺相匹配的持久性、备份和恢复安排；结果日志也不能因为队列收到 ACK 就立刻删除唯一事实。另一种选择是等 `APPLIED` 才 ACK，但它会长时间占用运输中的消息，而且仍无法消除提交成功、ACK 丢失造成的重复，所以我选择把运输接管和资金完成分开管理。

## 第 3 层：重复识别必须同时核对身份与内容

**面试官：** 既然 ACK 丢失会重复送到 Inbox，怎样判断是同一个批次，而不是另一笔碰巧相似的成交？

**面试者：** 批次身份由上游事实位置决定：`batchId=(symbol,commandSeq)`，本例就是 `BTC-USDT/102`；成交身份是 `(symbol,commandSeq,matchIndex)`。重投不生成新 UUID。入口以批次身份建立数据库唯一约束，命中同键时还要比较规范化业务载荷及其 `sourceHash`，摘要不包含本次投递时间、重试次数等可变字段。同键同内容复用原记录；不能因为价量恰巧相同，就把不同序号的两笔真实成交合并。

同键异内容不是正常重试，而是来源、编码、恢复或数据完整性出了问题。应保留冲突证据，隔离输入并阻断该位置，不能用后来一条覆盖先来一条。若原批次已经 `APPLIED`，原资金完成状态保持不变，另建冲突核查记录并阻止风险继续扩散，而不是把它降级后再应用一遍。此外，摘要只证明所比较的内容一致，完整性仍要对照可信结果日志和批次清单，不能相信消息自带一个 hash 就认为成交没有遗漏。

## 第 4 层：两个实例同时看见未完成记录时谁获胜

**面试官：** 同键比较可以挡住先后重复。但两个实例同时查到批次不存在，都开始记账，先查再写还安全吗？

**面试者：** 不安全，查询结果和后面的写入之间有竞争窗口。Inbox 的唯一键必须由数据库裁决，两个实例并发接管时，只有一个能创建该身份；另一个在竞争结束后读取已提交记录，核对内容再复用。遇到唯一约束错误还要区分它来自哪条约束，不能把任意 SQL 错误都解释成“别人已经成功”。在 PostgreSQL 这类错误会使当前事务失败的实现中，需要回滚后再查询，或者使用明确的冲突处理语句并检查结果。

资金应用也有独立的数据库防线：按交易对锁定 `LedgerCursor`，锁定对应计划状态，检查是否已应用、是否为下一个序号；批次应用记录对 `batchId` 唯一，分录使用稳定 `legId` 并有对应唯一约束。进程内 mutex、任务租约可以减少重复工作，但租约过期后旧 worker 仍可能执行，因此它们不能替代这些约束。即使两个实例同时认为自己有执行权，也只能有一个事务取得该批次的资金生效资格。

## 第 5 层：为什么只给分录加唯一键仍然不够

**面试官：** 既然分录和应用记录都有唯一键，是不是先改余额，再补一条“已处理”，就已经能防重？

**面试者：** 不能。先提交余额再记“已处理”，在两者之间崩溃，重试会把余额改第二次；先提交“已处理”再改余额，崩溃后重试又会误以为已完成。真正要防重的是资产效果，而不只是某张表里能否插入同名记录。因此应用资格校验、所有资金变化和完成凭据必须处在同一个数据库事务里，不能让一个唯一键遮住两个独立提交之间的空窗。

本例事务先锁定水位并确认前序是 101，再按固定资源键顺序锁定相关预留和余额，验证计划摘要、预留绑定、数量与逐币种平衡。随后共同写入 T1、T2 的分录，消耗甲 15,025 USDT 预留、付款 15,015 并返还 10，转移双方 BTC，更新账户侧订单结果投影，记录 `APPLIED` 与 `planHash`，将水位推进到 102，并写通知 Outbox。任一步失败都不能留下部分资金效果；唯一约束冲突也不能被捕获后忽略，再把前面的余额修改提交。

## 第 6 层：Commit 超时后不能凭一次查询未命中就补做

**面试官：** 你把这些状态放进一个事务了，但 `Commit` 返回超时。数据库可能已提交，也可能没提交，重试怎样知道该做哪一种？

**面试者：** 首先把它归类为“结果未知”，而不是“确定失败”。使用原 `batchId` 去权威数据库查询应用记录与 `planHash`：如果已经存在且摘要一致，返回原 `APPLIED`，不再扣预留；如果摘要冲突，进入核查；读不到记录时，也不能仅凭一次查询认定未提交，因为读副本可能落后，原事务也可能仍在服务端完成提交。

安全重试要重新走同一套数据库串行化入口。新事务锁定该交易对水位和计划状态，在锁内重读应用记录、摘要和前序位置；原事务若仍占有这些锁，新事务必须等待它结束，不能绕开锁另走补款路径。原事务提交则复用结果，确定回滚且条件仍满足才应用原计划。锁等待本身再次超时，就继续保留未知或待重试状态。所有尝试都使用同一身份，迟到的错误回调也无权把已经提交的 `APPLIED` 改回失败。

## 第 7 层：消息系统的事务不能包住账户数据库

**面试官：** 这样看来，消息确认与数据库提交总有间隙。直接使用消息系统的 exactly-once 事务，能不能取消 Inbox 和业务幂等？

**面试者：** 不能直接取消。消息系统内部把消费位置与另一条消息原子提交，不等于它与这个关系数据库的余额、预留、分录共用一个事务。即使先成功记账，再提交消费位置，两者之间崩溃也会重投；反过来先确认再记账，则可能漏记。当前设计不引入跨系统分布式事务，而是用已提交结果日志承担可补投事实，用 Inbox 承担可靠接管，用账户数据库事务承担唯一资金效果，各自覆盖自己的边界。

出站通知使用同样的思想：`APPLIED` 事务内先写稳定 `eventId` 的 Outbox，发布器提交后再异步发送。发送成功但发布标记未保存时可以重发，下游按事件身份去重；发布失败不回滚已经成立的内部结转。Outbox 解决的是“已记账但通知暂时未发”，不应成为第二个记账入口。这样会保留重复运输和投影延迟，却不会把这两种暂态变成重复付款。

## 第 8 层：同一批次换了程序版本也不能换一份金额

**面试官：** 消息可以重复、任务可以恢复，但重试时清算程序已经升级。身份不变、重新算出的计划却变了，数据库唯一键还能保证业务正确吗？

**面试者：** 唯一键只能限制同一身份的生效次数，不能证明第一次生效的内容正确，所以还必须固定计划依据。计划保留 `sourceHash`、清算规则版本、费用规则版本、各收付及释放明细和 `planHash`，在校验后成为 `READY`。应用器读取这份不可变计划，并核对它与原结果的绑定；重试不是取“当前最新规则”再生成另一份金额。主线仍为零手续费，不能因为新版本默认收费，就给本例历史成交补扣费用。

计划尚未固定时，计算可以失败重来，但仍须使用该批次冻结的规则；同源同版本计算不一致、规则版本不可取得或者新程序无法解释旧计划，都应 `NEEDS_REVIEW` 阻断，而不是更新原 `READY` 内容来让 hash 对上。已应用批次还要保留原 `planHash` 作为结果证据。程序升级的代价是兼容旧版本或明确暂停核查，不能用“幂等”这个词掩盖重放时经济义务已经变化。

## 第 9 层：长期重放要求幂等证据活得比一次消息更久

**面试官：** 既然要保留原计划和摘要，那处理成功几天后能否清掉 Inbox 和去重记录，只依靠水位判断旧消息已做过？

**面试者：** 不能按一个任意的缓存过期时间清掉所有证据。水位 102 可以说明连续前缀已经应用，但不能独自回答迟到的批次 101 是否携带了不同内容；也不能解释某个批次采用哪份计划、产生了哪些分录。至少要能通过在线记录或可靠归档查到该身份对应的 `sourceHash`、`planHash`、应用凭据及审计关联。旧输入的序号不大于水位时，要核对既有证据后复用结果，而不是直接回“成功”，更不能把查不到热记录解释成一笔新成交。

Inbox 原载荷可以按明确策略归档，已完成任务也可以离开热表，但前提是档案可核对、恢复时不会遗失幂等资格，而且系统明确允许多长的重投与补取范围。上游日志删除条件要综合安全接管、应用进度、归档和灾备恢复需求，不能只看运输 ACK。若旧摘要暂时无法取回，应进入等待核查，不重新应用。这里讨论的是正常运行中的保留策略；数据库恢复到历史备份后怎样判断资产效果是否仍在，要按第 08 题的灾备边界处理。

## 第 10 层：业务一次效果还需要可推进、可阻断的重试策略

**面试官：** 你把旧输入和计划都留住了，是不是所有未完成批次无限重试，最终总能完成？

**面试者：** 不能。死锁、短暂连接故障、可确认已回滚的事务失败，可以按同一身份退避重试；提交结果未知要先核查并通过锁串行化，不能当成普通失败补做。缺规则、同键异载荷、逐币不平衡或无法解释的预留不足，重复执行不会自动变正确，应记录证据进入 `NEEDS_REVIEW`，阻断该交易对的后序应用。自动重试达到预算后可以暂停并告警，但暂停不是删除原义务，也不能把后续批次当作已处理来推进水位。

Go 调度层使用有界 worker、按交易对合并唤醒和有界退避，避免大量重复投递把数据库连接与锁等待耗尽；跨实例的最终资格仍由数据库决定，跨交易对共享的账户余额也仍需数据库锁和非负等约束。可观测状态应区分接管积压、计划就绪、提交未知、人工阻断和真正 `APPLIED`，不能把 ACK 数当结算完成数。最终保证可以概括为：原义务始终有证据和继续处理的入口，重复尝试不增加资金效果，无法证明安全时停在原位置，而不是为了推进制造第二笔钱。

## 收束：一次效果来自共同提交，不来自一次发送

- **讲透的机制：** 结果日志固定事实；Inbox 在运输 ACK 前可靠接管；稳定身份、内容摘要和唯一约束确定“同一件事”；不可变计划固定金额；资金效果、`APPLIED` 和连续水位同事务；Outbox 将通知重试与资金生效分离。
- **最易答错的边界：** Inbox 已接管不等于已付款；唯一键不等于余额和凭据已经原子提交；一次读不到记录不等于原事务已回滚；已 `APPLIED` 不能因迟到失败降级；历史水位不能代替所有内容核查证据。
- **可手工验证的反例：** 在纸上画出“甲预留扣减已提交—幂等记录尚未写入—崩溃—重投”，就能推导出分离提交会重复扣款。再改为整批同事务，令批次 102 提交后仅丢失响应：两个 worker 用同一身份重试，必须都收敛到原记录，甲仍为 4,985 USDT 和 0.25 BTC、丙仍预留 0.05 BTC，水位仍为 102。若将同身份 T1 的数量改掉，则应冲突阻断而不是再结算。以上是人工时序推演，不是工程测试结果。
