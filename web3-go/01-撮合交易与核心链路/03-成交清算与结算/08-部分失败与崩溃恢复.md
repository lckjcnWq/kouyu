# 大问题 8：部分失败和崩溃后怎样恢复原义务？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文先讨论数据库已提交记录完好的进程故障，再明确增加数据库丢失或回退的灾备条件。恢复的对象是原批次义务和原资产效果，不是重新给用户发一笔钱。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 故障窗口 / 提交边界 | 出错发生在什么承诺成立之前或之后。 | 同样是断线，未提交回滚与提交结果未知要用不同恢复路径。 |
| SQL 成功 / 整批提交 | 语句执行完不等于事务已正式生效。 | T1 写完而 T2 失败，未提交效果整批回滚，不只补 T2。 |
| Inbox / ACK 接管责任 | 持久收件成功后，下游接手后续任务。 | 接管前靠源日志补送，接管后靠持久扫描继续。 |
| 无副作用重算 | 尚未动资产的中间计算可以重新执行。 | 未固定计划可按原版本重算，不能换当前费率。 |
| READY 原子发布 | 完整计划验证后一次变为可应用状态。 | 不能先标就绪再慢慢补明细，固定后不原地改金额。 |
| 服务端未决事务 | 应用进程退出后，数据库可能尚未结束原事务。 | 接管者仍走原锁入口，不能马上另开补款路径。 |
| Commit 未知 | 无法仅凭调用错误确认提交或回滚。 | 按原 batchId 查证，并在锁内重读，查不到一次也不盲补。 |
| APPLIED 单向性 | 已提交完成不被迟到错误降级。 | 整包资金、应用去重和水位同事务确定后，超时回调无权推翻。 |
| 传播恢复 / Outbox | 补通知或页面副本，不再改资金。 | 沿原 eventId 重发，通知没到不代表钱没到。 |
| NEEDS_REVIEW / 重试预算 | 证据异常停查，临时故障有限重试。 | 预留不足不能靠借别单资金或少算付款来“恢复”。 |
| 进程恢复 / 数据库灾备 | 前者持久账还在，后者账可能已丢失。 | 不能把普通重启保证套到旧备份恢复。 |
| 一致恢复点 / RPO | 前者是相互对应的一份历史状态，后者描述容许丢失范围。 | 本稿没承诺零数据丢失，不能拼最新余额与旧去重表。 |
| 停写隔离 / 旧主隔离 | 暂停资金入口，防止新旧系统同时写账。 | 灾备先建立唯一权威恢复环境，再核对共享账户依赖。 |
| 受控重建 / 活账再发 | 重建丢失记录与给仍存在的账户再加钱不同。 | 已由事务日志还原的效果不能再按业务重放一遍。 |
| 追加差额修复 / 后续依赖 | 留住旧历史，用新凭据改差额，并核对之后发生的事。 | 原到账若已被使用，要恢复整条依赖，不能只补一笔就开放交易。 |

## 把整篇文章压缩成一个故事

值班员小孟面对甲买币批次 102 的报错，先问事务到底提交没有。T1 的 SQL 虽然执行完，若 T2 报错导致整批回滚，就不存在乙单独收到可花费资金的正常中间态；他应重试原完整批次，而不是只补 T2。撮合成交已经成立，账务回滚并不撤销它，甲的预留仍要保护原义务，也不能为了尽快恢复可用就退掉付款资金。

若进程在接收时退出，小孟先查 Inbox：尚未可靠接管的由源日志补送，已签收的由持久扫描继续。计划没固定，可以按原事实和冻结版本重算；已 READY 就读原计划，不能服务升级后改成有手续费。若应用进程消失，数据库也未必马上确认原事务回滚，所以接管者仍通过同一水位锁进入。整包余额、预留、分录、应用去重和进度必须共同提交，事务外先“加回预留”反而可能造出多余资金。

若断线恰好落在提交时，小孟把它当结果未知，按原编号查权威库并在锁内复核，不能因为一次没查到就新建补发批次。确认 APPLIED 后，甲应仍是 4,985 USDT 和 0.25 BTC，10 USDT 价差不能再返一次。通知没发则沿原 Outbox 事件补传播，不回滚资金。数据库临时故障可以退避，预留绑定不符或计划冲突则停查，保留证据和原义务，不无限重试撞运气。

现在明确改成灾备场景：数据库只恢复出 101，而灾前可能已经完成 102。小孟先停写、隔离旧主，恢复相互对应的账务、预留、计划、去重和水位，再核对事务日志、源事实与后续资金活动。备份里没有完成记录，不证明灾前没付过；事务日志已还原的效果也不能再发一次。若另接外部付款通道，还须单独核对真实付款凭据。证据闭合后才开放业务，确有经济错误则审批后追加差额修复，而不是覆盖旧账。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题沿已确定成交的履约链逐个切开故障窗口：输入接管、计划固定、事务应用、结果确认、通知发送，最后区分进程恢复与数据库灾备。重点不是重新生成一笔交易，而是依据持久证据恢复原义务，识别哪些效果尚未发生、哪些已成立而不能撤销。

沿用总览的零手续费、单关系库、完整批次同事务基线。批次 `BTC-USDT/102` 包含 T1、T2，起始水位为 `101`，甲预留 15,025 USDT。`READY` 不是资金完成，`APPLIED` 才是本地账务完成；主线没有链上支付。灾备部分明确增加数据库丢失或恢复到旧时点这一条件，不把普通进程重启的保证直接套过去。

## 第 1 层：恢复的是整批义务，不是失败的那条 SQL

**面试官：** 批次 102 有 T1、T2。如果 T1 处理成功，T2 处理失败，该怎么恢复，是否只补做 T2？

**面试者：** 先问“成功”越过了哪个边界。在本模型中，T1、T2 属于同一个完整结果批次，所有资金动作都在一个账户数据库事务里。T1 的 SQL 执行成功、甚至查询在本事务中看到了新余额，都不等于 T1 已经独立提交。只要 T2 失败导致整批事务回滚，T1 的分录、余额和预留修改也必须一起撤销，恢复时重新应用原批次 102，而不是沿着上次程序执行到第几行继续。

撮合已经提交的 T1、T2 则是另一回事：账户事务回滚不撤销成交事实，甲的预留仍需覆盖这些未履行义务。不能删除 T2、重撮合一个替代成交，或者把买方资产解冻来“恢复可用性”。如果确实查到 T1 已单独提交、T2 没提交，就说明实际实现已经破坏了整批事务基线，需要阻断和对账修复，不能声称这只是本方案允许的正常部分成功。

## 第 2 层：先按接管提交边界判断谁负责找回工作

**面试官：** 你说恢复原批次，可进程可能在拿到消息后立刻崩溃。怎么保证原批次还找得到？

**面试者：** 以 Inbox 的持久提交边界划分责任。结果尚未可靠接管时，交付器仍要能从撮合持久化有序结果日志补送；入口不能仅把消息放进 goroutine channel 就确认。Inbox 校验可信来源、稳定 `batchId`、完整载荷及 `sourceHash` 后，在数据库提交 `RECEIVED`，提交确认之前不发运输 ACK。若接管事务已提交但 ACK 没送出，重投只会命中同键同内容，不会制造第二个任务身份。

一旦 Inbox 已提交并发送 ACK，后续工作就由持久化任务扫描继续负责，不能再以“队列不重发了”为漏账理由。重启后查出未完成的接管记录，再生成或读取计划、等待水位、应用资金。接管提交结果未知时先核实，不能把网络错误直接当成未接管。上游日志和归档还须覆盖安全接管、未应用工作及恢复需要，ACK 只能释放运输中的占用，不能授权删除唯一成交证据。

## 第 3 层：计划生成中断与 READY 后中断是两种恢复

**面试官：** Inbox 还在，但清算计划算到一半就崩溃。重启后是接着算，还是重新算？如果已经 READY 呢？

**面试者：** 尚未固定的中间计算没有资产副作用，可以丢弃并从 Inbox 原始事实重算，但必须使用该批次冻结的清算及费用规则版本。计划只有完整收付明细、预留动作、`sourceHash` 和 `planHash` 都写好且校验通过，才能原子发布为 `READY`；可以在事务外计算、事务内完整写入，但不能先把状态改为 READY，再逐条补齐明细。多个生成者竞争同一 `planId=batchId` 时，也应通过唯一约束和内容核对收敛到一份计划。

如果已经 `READY`，恢复时就读取这份不可变计划，不按新部署的默认规则重新解释金额。旧版本规则缺失、载荷摘要不一致，或相同来源和版本产生不同计划，都应 `NEEDS_REVIEW` 阻断。主案例始终零手续费，不能因当前程序新加了收费选项，就让历史 102 重算后少给甲 BTC。恢复可以重新做无副作用的计算，却不能悄悄改写已经固定的义务。

## 第 4 层：数据库语句做了一半，进程退出后不能盲目另开补偿

**面试官：** 计划固定了，应用时已扣甲的预留，但还没给乙加 USDT，进程这时退出，会留下半笔资金吗？

**面试者：** 在正确的同库事务里，这些写入尚未独立提交。数据库确认会话结束后会结束未提交事务并回滚其全部效果；但进程退出到数据库识别连接失效之间可能存在时间差，不能把“应用进程没了”立即等同于“服务端事务已确定回滚”。接管者仍通过相同的水位和资源锁入口进入，让数据库裁决原事务是否结束，而不是绕开它直接补款。

具体而言，原事务锁定水位 101，并锁住相关预留和余额；甲预留扣减、乙丙到账、甲 BTC 到账、S2 剩余预留、分录、订单结果投影、`APPLIED`、水位 102 和 Outbox 都必须同提交。若原事务未提交就结束，重试看到的是旧状态，按原计划整批执行；如果失败点其实已进入提交阶段，就要转为结果未知处理。应用层不需要先给甲加回 15,025 再重来，这种事务外“补偿”反而可能和数据库最终回滚叠加，凭空增加资金。

## 第 5 层：提交结果未知时，只能向持久状态求证

**面试官：** 现在故障点正好是 `Commit`：请求发出后连接断了。怎么区分已回滚和已经全部记账但响应丢失？

**面试者：** 仅靠该错误无法区分，所以保留原身份并标记结果待核实。通过权威数据库按 `batchId` 查询应用记录和 `planHash`：同摘要的 `APPLIED` 表示整批已完成；内容冲突则阻断核查。一次未查到不构成确定回滚，因为读副本可能滞后，原提交也可能还在数据库处理。不能因为调用超时就把计划改为失败、解冻预留或者生成一个新的补发批次。

需要再次尝试时，新事务锁定该交易对 `LedgerCursor` 和计划状态，在锁内重读。若原事务仍在执行，就等待其释放锁；待锁取得后，若已应用则返回原结果，若确实未应用、前序仍为 101 且原计划有效，才重新应用 102。所有 SQL 错误、更新行数和提交错误都检查，新的锁等待超时也不推翻原提交。数据库 `APPLIED` 是单向状态，某个迟到的超时处理协程没有权力把它降为可重试失败。

## 第 6 层：记账后通知失败，不能倒退已经成立的资金完成

**面试官：** 查到 102 已经 APPLIED，但通知没发出去、页面也没更新。用户说没收到，是否应该回滚后重新结算？

**面试者：** 不应该。102 已提交后，甲的 0.25 BTC 以及乙丙的 USDT 已是权威账户资产；通知迟到不否认这些资产。回滚再重算会改写历史，还可能与账户后续操作冲突。在账务事务内写好的 Outbox 才是恢复通知的入口，发布器扫描未完成发送任务，仍使用原 `eventId` 和原批次结果；不能以“重新通知”为名再调用资金应用或发放一个新批次。

若消息已发出但发送标记未提交，恢复时允许重发，由接收方按稳定事件身份处理重复。查询投影则从已提交账务事件或权威记录补建，并展示自己追到的版本，资金完成查询以账户数据库为准。这里恢复的是传播效果，不是资金效果：Outbox 未发送、页面未追上可以作为独立待办，原 `APPLIED` 保持不变，也不能让消息投递结果反过来决定是否已付款。

## 第 7 层：能重试的故障与必须核查的错误分开收敛

**面试官：** 通知能单独补发，应用没完成的就重试。但如果某次重试发现预留不足，是不是多等几次就好了？

**面试者：** 不能把所有失败当成暂态。死锁、可重试的序列化冲突、短暂数据库不可用，属于可能通过同身份重试收敛的问题；原事务已回滚后，采用有上限的自动重试和退避，耗尽预算则保留任务并告警。预留不足、订单绑定不符、逐币不平衡、计划摘要冲突或规则版本缺失，说明当前证据不足以安全履约，应记录预期值、实际值、来源位置和失败阶段，进入 `NEEDS_REVIEW`，停止该交易对越过这个位置。

例如，101 起点甲本应有绑定 B1 的 15,025 USDT 预留，却只查到 15,020，不能从甲别的订单借 5 USDT，也不能把计划付款少算 5 来凑平。要核对此前预留建立和消费记录，确认是遗漏前序、投影错误、数据损坏还是已存在的实现缺陷。READY 内容保持不可变，修复必须保留原证据、审批和独立身份；本题不提供“先改余额再把状态拨回 READY”的捷径。人工介入解决的是证据与合法修复路径，不是授权直接跳过坏批次。

## 第 8 层：普通进程重启从数据库恢复，而不是从内存进度恢复

**面试官：** 故障原因已经排除，进程重新起来。具体从哪里接着做，怎样避免把阻断任务和已完成任务混在一起？

**面试者：** 先明确这个场景的数据库及其已提交记录仍然完好。启动后从数据库读取每交易对连续水位，扫描已接管但未完成的 Inbox、现存计划和待发布 Outbox：只有 `RECEIVED` 的继续生成固定版本计划，`READY` 的等待并争取水位下一位置，`NEEDS_REVIEW` 的保持阻断并呈现核查原因，`APPLIED` 的不再执行资金动作，仅按需要恢复通知和核对证据。消息 offset、进程内任务索引和上次日志打印到哪一行，都不能代替这些持久状态。

接管者还要处理旧任务租约，但租约只是调度优化。旧 worker 如果因网络抖动恢复执行，仍要重新通过水位锁、计划状态、唯一应用记录和资源约束，不可能因持有旧内存状态得到第二次生效资格。恢复后核对水位与应用凭据的一致性，并按统一位置核对分录、余额和预留；遇到无法解释的不一致就停下，而不是把最大的应用序号写回 cursor。这里的原子性保证只针对数据库仍保有已提交事务的情形，不能顺势承诺数据库丢失后也能这样简单重启。

## 第 9 层：数据库灾备要恢复一个一致的历史，而不只是找个旧水位

**面试官：** 那如果丢的就是数据库，备份里只有水位 101，灾前可能已经把 102 回报为资金完成，恢复方法有什么根本变化？

**面试者：** 这已经是数据库灾备，不是应用进程崩溃。首先暂停资金写入和对外完成承诺，隔离旧主及旧 worker，防止新旧数据库同时接受写入。恢复必须覆盖一个一致时点的分录、余额、预留、账户侧订单结果投影、计划、应用记录、水位、Inbox 和 Outbox，不能从不同备份拼一份“最新余额加旧幂等表”。两个交易对共享账户时还要按整个账户数据库的一致状态恢复，不能各选一个最大水位就认为相互独立。

接着确定可以作为权威起点的一致恢复位置，以及它之后到底丢了什么：可用的事务日志、复制记录和归档能否还原已确认提交，已接管输入与冻结规则是否完整，原始预留建立等资金状态是否有恢复依据。撮合结果日志能证明成交义务，但单靠它不自动证明账户数据库已恢复到哪一步，也不能凭空补全预留起点。总览并未承诺零数据丢失灾备；若业务需要 RPO 为零，就必须另行明确提交确认所依赖的复制与持久性条件。已 ACK 的 Inbox 若随数据库丢失、上游唯一副本又删掉，也无法靠业务幂等找回，证据不够时必须继续阻断并核查，不能假称恢复成功。

如果实际系统还连接了充提等外部资金通道，这就是超出内部结转主线的扩展条件：数据库回退不会撤销已经发生的链上转出或银行付款。恢复时必须另外取得稳定履约身份、外部交易或付款凭据、通道状态和相应账户账务的映射，核清哪些资金效果已经发生、哪些内部记录需要重建。某条 APPLIED 在恢复库里缺失，只能说明当前恢复状态没有这条记录，不能证明外部从未履约；在这些证据闭合之前继续停写，不能仅从旧水位启动补发。

## 第 10 层：历史已回报后，重建数据库不等于向活账再付一次

**面试官：** 假设证据表明灾前 102 确实已记账，但恢复库只有 101。是不是重放一次 102 就行？若后来还发现原计划算错，又怎么处理？

**面试者：** 要区分“受控重建丢失的数据库状态”和“在仍存在的活账上再次发放”。前者可以在停写隔离的恢复环境中，依据可核验的完整历史重建 102；已由事务日志恢复出来的效果不能再按业务重放一次，确实尚未恢复的效果也必须使用原 `batchId`、原计划和原分录身份。若灾前到账已用于后续交易，就明确增加了后续资金活动这一条件，必须连同它们依赖的预留、扣减、成交和水位一起恢复到可解释的一致位置，不能只把 102 的入账补出来就开放提款或交易。恢复阶段也不能立即把 Outbox 当作新资金完成事件全量外发；应核对原事件身份和发送情况，再按下游幂等契约补传播。

如果账户数据库实际上保留着 102，再建一个新批次给甲 0.25 BTC，当然是重复发放，不是恢复。若证据确认原计划存在经济错误，已提交历史也不能删除或覆盖为“从未发生”：保留原成交、计划、分录与应用状态，经审批用稳定修复身份追加差额调整，逐币说明资金来源和对手方，同样保证调整分录、余额和修复幂等凭据原子提交。资产可能已被后续使用，无法安全收回时需要阻断和明确损失处理，不能让余额变负或静默抹掉历史。未应用的坏计划则保持阻断，走保留原版本、明确审批和应用资格的修复流程，不原地篡改 READY。恢复的完成条件是原义务、原资产效果及后续依赖全部有一致证据，而不是单独把某个状态字段改成成功。

## 收束：先定位提交边界，再决定重试、补传播或受控修复

- **讲透的机制：** 接管前依赖来源补投，接管后依赖持久任务；计划发布以完整 READY 为界；资金以整批数据库提交为界；提交未知通过原身份和数据库锁求证；已提交后的通知独立恢复；数据库灾备必须重建一致历史和依赖关系。
- **最易答错的边界：** 一条 SQL 成功不是一笔成交独立成功；进程退出不立即证明服务端事务已经回滚；READY 不能按新规则重算覆盖；NEEDS_REVIEW 不能作为跳过水位的理由；进程恢复的“已提交不丢”前提不能套到旧备份；已记账错误应追加修复，不能回滚历史或新建身份重复发放。
- **可手工验证的反例：** 对同一批次 102 画三条时间线。第一条在给乙入账前结束且事务确定回滚，预期整批仍是水位 101 和原预留；第二条整批提交后丢响应，预期查询或锁内重试只返回原 APPLIED，甲仍为 4,985 USDT 与 0.25 BTC，不能再次返还 10 USDT；第三条灾前 102 已完成却只恢复出 101，预期先停写、还原证据与一致历史，不能仅因恢复库查不到 APPLIED 就在活账补发。再分别检查通知是否可重发、已知坏计划是否阻断，即可发现混淆资金恢复与传播恢复的方案。以上均为手工故障窗口推演，不是已执行的工程实验。
