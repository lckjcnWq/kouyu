# 大问题 2：怎样把成交变为可追溯、可重现的收付义务？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

> 本文只把已提交的零手续费现货成交转成固定履约计划，不直接改余额。要分清“认出同一笔事”“收齐全部事实”“每次算得一样”和“确实算对了”这几道不同检查。

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 收付义务 / 清算计划 | 把谁该给谁什么写成可执行清单。 | T1 包含价款、BTC 交付和价差动作，计划完成不等于到账。 |
| batchId / planId | 整包事实与对应清单的稳定编号。 | 以交易对和命令序号识别，同一批次重投不另建经济事项。 |
| tradeId / matchIndex | 一笔成交的身份与包内序号。 | 区分 T1、T2，也识别重复塞入的同一笔成交。 |
| legId | 每条收付或预留动作的固定编号。 | 从原成交、资产、角色和动作派生，便于追查到源头。 |
| UUID / traceId | 可用来标识一次运行尝试的编号。 | 消费时随机编号不能代替稳定的成交和计划身份。 |
| 规范化载荷 / sourceHash | 固定业务内容及其摘要。 | 包含价量、双方和版本，排除重试时间等可变运输信息。 |
| 权威清单 / 来源完整性 | 从可信源确认这一包应该有哪些内容。 | 只给 T1 算出正确摘要，仍可能漏掉 T2。 |
| 显式更正 | 另留经授权的纠错业务记录。 | 引用原成交并说明原因，不用同编号覆盖旧金额。 |
| 规则冻结 / READY | 保存原规则，清单固定后不随配置改变。 | 找不到历史版本就暂停，不能用最新版凑一个金额。 |
| 纯计算 / 确定性 | 输入和版本相同，就生成同样明细。 | 不读实时行情、时间或随机数来决定义务。 |
| planHash / 稳定排序 | 给有固定顺序的清单计算指纹。 | 不让 Go map 的遍历顺序造成同内容不同摘要。 |
| 资金桶 / 聚合执行视图 | 区分可用与预留，再汇总实际更新量。 | 不能只留甲净少多少 USDT，抹掉预留消耗与返还。 |
| 确定性与正确性 | 算得重复一致，不代表业务一定正确。 | 还要核对数量、资产、账户、预留绑定与完整清单。 |
| NEEDS_REVIEW | 证据不足或内容冲突时暂停核查。 | 阻断该位置及后续推进，不静默换规则或吞掉冲突。 |

## 把整篇文章压缩成一个故事

清算员小陈收到甲买币的结果：T1 是甲向乙买 0.10 BTC，价款 6,000 USDT；T2 是向丙买 0.15 BTC，价款 9,015 USDT。主线零手续费，甲为 T1 数量切片原占了 6,010 USDT，所以还应返 10 USDT。小陈的工作不是立即打钱，而是把这些成交、资金来源和预留动作整理成能逐条追查的履约清单，交给后续账务执行。

他给整包沿用 BTC-USDT/102 的身份，每笔成交和每条收付腿也继承稳定编号。第二次运输送来同一包，他先比较规范化内容，而不是再生成随机计划号。若编号相同、数量却变了，便隔离冲突，不能当普通重试吞掉，也不能直接覆盖。另一次只送来 T1，还附着自洽摘要，他仍要回到权威批次清单核对：摘要能说明这份内容有没有变，却不能证明 T2 本来就不存在。

清单计算只使用固定成交价量和当时冻结的规则，不因甲当前余额不足就少算付款，也不随服务升级套用今天的费率。小陈把明细稳定排序，再生成计划摘要；若原版规则找不到，就停下来核查。为了少执行数据库更新，他可以汇总同账户、同资产、同资金桶的变化，但原始明细必须留下。否则只看甲净减少的 USDT，就解释不清预留为什么减少、价差从哪里退回。

交付前，小陈分别检查“能否重复算出同一份”和“这份是否正确”。漏掉 T2、重复 T1、把返还 10 写成 11，都应由完整性、数量或平衡检查挡住；即使金额相抵，也还要检查收款人和订单预留绑定，避免钱付错人。计划一旦固定，后续应用沿用它，不重新撮合或偷偷改历史。这里讲的是可验证的设计方法，不把故事里的核查写成已经跑过的故障实验。

**流程位置与核心机制：** 从已提交成交到不可变清算计划，重点是身份、来源、完整性与确定性计算；不重复展开消息重试协议和账务事务。沿用总览零费用案例。

## 第 1 层：清算究竟产出什么

**面试官：** 你拿到两笔撮合成交后，清算模块究竟要生成什么，而不是直接改余额？

**面试者：** 清算产出一份可核对的履约计划，明确每个账户、每种资产、每个资金桶应该发生什么变化，以及依据哪笔成交和哪版规则。T1 的基础义务是甲向乙支付 6,000 USDT，乙向甲交付 0.10 BTC；再结合甲该数量切片原占资 6,010，得到返还甲 10 USDT 的预留动作。T2 对应付款 9,015 和交付 0.15 BTC，没有额外价差。

计划必须覆盖完整批次的两笔成交和订单变化，不只是生成“甲净变化多少”的汇总数字。汇总可以便于应用，但要保留可追溯明细，知道哪一笔费用或释放来自哪条源记录。此时只固定义务，不制造可用资产；实际资金副作用由账务域原子执行。

## 第 2 层：义务为什么不能每次生成新 ID

**面试官：** 你说计划要追溯到成交。成交、批次和计划分别用什么身份，为什么不用消费时新建 UUID？

**面试者：** 本模型批次身份为 `(symbol, commandSeq)`，例如 `BTC-USDT/102`；批次内成交为 `(symbol, commandSeq, matchIndex)`，例如 T1、T2 各占一个稳定序号。清算计划以 batchId 作为 planId，具体收付腿的 legId 由成交身份、资产、收付角色和动作类型稳定派生，订单级释放动作则绑定对应结果动作身份。

消费时生成 UUID 只能区分两次执行，无法认出它们其实是同一笔经济事项。重投一次就获得新 planId，数据库即使对 planId 建唯一约束，也会把重复当新义务。稳定身份必须从权威事实贯穿到最终执行处，UUID 可以作为一次尝试的 traceId，但不能代替经济事项身份。

## 第 3 层：同一个身份来了不同金额怎么办

**面试官：** 即使身份稳定，第二次送来的 T1 数量变了，你怎样判断它是更正还是重复？

**面试者：** 不能只看 ID 相同就吞掉。Inbox 记录规范化业务载荷及 sourceHash；规范化包含交易双方、订单、整数价量、规则版本、批次明细等不可变字段，排除投递时间、重试次数等运输元数据。同身份同内容可以复用，若内容不同就记录冲突，停止该批次及后续推进。

“更正”必须是显式、有授权的新业务记录，引用原成交并说明更正原因，不能拿同一个身份覆盖金额。摘要只是快速比对工具，关键载荷仍要留存；严重冲突时回到权威日志核对，不能把生产者随手提供的 hash 当成内容正确的证明。

## 第 4 层：有摘要为什么仍可能漏半批

**面试官：** 那生产者把 T2 漏掉，只给 T1 算了一个正确摘要，你不还是会接受吗？

**面试者：** 会，所以摘要解决的是“这份内容是否变化”，不自动解决“这份内容是否完整”。接管边界应对应权威日志中原子提交的完整 ResultBatch，核对 batchId、提交位置、成交计数、明细身份、订单变化和预留动作清单。若运输分片，需要先按权威清单收齐、验证后才能形成完整 Inbox 批次，不能见一条成交就推进整个命令水位。

本例 B1 全成对应 T1 加 T2 共 0.25 BTC。如果只收到 T1，却声称订单从 0.25 变为 0，数量核对就会失败；即使订单变化也被错误裁剪，仍应通过权威批次记录发现缺失。内容内部自洽与来源完整可信是两项检查，互不替代。

## 第 5 层：重放时规则升级会不会改变义务

**面试官：** 你已拿到完整批次，但清算服务升级了费率或算法，旧批次重放时怎样仍算出同样金额？

**面试者：** 规则版本要成为事实链的一部分，而不是调用“当前配置”。订单接纳时冻结会影响经济结果的费用与精度规则，结果引用这些依据；清算计划记录源摘要、规则版本以及计划摘要。READY 后就是一份不可变计划，重试应用原计划，不因为今天费率调整重算成新金额。

若计划还未生成，计算器必须能加载原规则。找不到原版实现或规则不兼容时进入 NEEDS_REVIEW，不能静默降级到最新版。若算法有缺陷，需要保留原输入、旧计算结果与审核决定，通过显式修复流程处理，不让“升级重放”成为隐蔽改账工具。

## 第 6 层：具体怎样计算，才能不依赖易变状态

**面试官：** 冻结版本后，计划生成具体还依赖什么？你会在生成时读账户当前余额来决定付款金额吗？

**面试者：** 不会。付款金额由固定的成交价量和规则决定，不因为当前余额不足就少算一点。计划计算所需的订单限价、预留绑定、成交前后数量及有序释放动作，应来自源批次和此前连续应用的权威订单结果；不可变订单元数据可通过引用核对。当前余额只在资金应用阶段用于验证约束，不能反向决定经济义务。

在实现上，可以把计划生成做成纯计算：规范化整数输入，逐成交生成收付腿与预留动作，再按稳定顺序排序并计算 planHash。相同输入和版本应得到相同计划。不要依赖 Go map 遍历顺序、当前时间、外部报价或随机数，否则业务相同也可能得到不同摘要，故障后无法解释哪份才是原计划。

## 第 7 层：聚合优化会不会丢失经济明细

**面试官：** 你生成的腿很多，能否把同一账户同一资产的变化合并后，只保存一个净数？

**面试者：** 可以合并应用增量，但不能只保存一个失去来源的净数。主案例甲的 USDT 既有预留减少 15,025，也有可用增加 10；如果只写“USDT 减少 15,015”，就丢掉资金桶来源，无法证明占资已经正确关闭。BTC 收入还要追到两个卖方和两笔成交。

所以计划保留逐成交与逐动作明细，另生成按账户、资产、桶聚合的执行视图，并核对两者总和。分录 legId 保持稳定，聚合版本和算法也有记录。聚合减少 SQL 更新次数，并不把本模型变成延迟净额结算，更不能借机取消批次内任一用户的履约明细。

## 第 8 层：怎样验证生成计划既确定又没有漏义务

**面试官：** 确定性计算即便每次都算错，也会得到相同结果。你怎样验证计划本身？

**面试者：** 我会把确定性和正确性分开检查。确定性检查是同一规范化输入、同一版本重算，明细和 planHash 一致；正确性检查则逐成交核对双方基础资产数量与价款，逐订单核对累计成交和预留切片，逐币种核对所有资金桶变化之和为零，并核对完整源清单没有遗漏或重复。

例如故意删除 T2，完整性或 B1 数量检查应失败；把甲的 10 USDT 价差误发 11，逐币平衡与预留目标检查应失败；把同一个 T1 放两次，稳定成交身份及数量检查应失败。还需核对账户身份与预留绑定，防止一个金额平衡但把钱付错人的计划通过。这里只描述验证方法，不声称这些故障实验已经运行。

## 本题收束

- **讲透的机制：** 成交事实经稳定身份、完整性验证和冻结规则，变为不可变、可追溯的收付计划；计划不等于资产已经变化。
- **最容易答错的边界：** UUID 不等于业务幂等，摘要不等于来源完整，确定性不等于计算正确，金额平衡不等于收款人正确。
- **检验反例：** 同 batchId 一次送 T1、T2，另一次只送 T1 并附自洽摘要；若系统不能回到权威完整批次发现差异，就仍可能漏结算。
