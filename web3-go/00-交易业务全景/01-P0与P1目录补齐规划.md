# P0 与 P1 目录补齐规划

## 一、规划范围与优先级

本规划依据[招聘要求](../../深入/面试要求.txt)，在现有业务分类上补齐工程能力和业务闭环，不推倒重建。

- **P0**：优先准备的岗位硬要求，以及防止资金、状态、风险失真的关键能力。
- **P1**：完整产品生命周期和链上交互边界，按实际产品与架构深化。
- 优先级不等于 JD 分类。例如灾备在 JD 中属于加分项，但资金相关的恢复正确性仍应优先准备。

**已建立 [05-Go与交易系统工程](../05-Go与交易系统工程/README.md) 及六个子目录；其中 [06-测试可观测性与故障复盘](../05-Go与交易系统工程/06-测试可观测性与故障复盘/README.md) 已编写专题总览、13 个独立母题（108 层问答）及唯一简洁 MVP，其他专题的正文状态见各自总览。正文交付不代表已完成程序测试、压测、故障演练或链上验证。** 现有 P0／P1 业务目录继续沿用原名称，范围扩展按本文推进，尚不代表已补齐对应正文。专家提示词和撮合正文不因目录建设而改动，避免覆盖已有内容或破坏链接。

### 4.1 资金账本与对账验收

不能只说“使用双分录”或“定时跑对账”。至少回答：

1. 一笔成交对应哪些资产、费用、持仓和业务身份，在哪个事务范围内提交？
2. 每个币种的入账与出账如何平衡，费用和舍入差额记到哪里？跨币种不能直接相加验证守恒。
3. 同一成交重放、账务写入成功但回执丢失、跨分片部分成功时怎样处理？
4. 对账采用什么截止点或事件水位，如何区分正常在途与真实缺失，避免拿不同进度的快照制造假差异？
5. 发现差异后，谁能暂停、补记或冲正，如何留痕？不能直接改余额消除差异。

### 4.2 持续风控验收

风险不是只在下单前和强平时执行。至少覆盖：

- 价格、持仓、资金费率、抵押品、可用保证金和风险参数变化分别触发什么重算。
- 风险服务看到的状态版本与执行模块是否一致；强平前状态已经改善时如何阻止过期指令。
- 撤单、减仓、充值、提现与强平并发时，谁拥有最终裁决权。
- 价格不可用时哪些行为被限制，是否允许降低风险的操作，依据是什么。
- 全仓、逐仓和多抵押品的风险范围不同，未采用的模式明确排除，不混用公式。

## 七、完成标准与推进顺序

### 7.1 逐篇验收

- **适用范围**：产品、成交机制、资产控制和执行结算方式写清；不把教学基线当成目标公司的事实。
- **业务闭环**：正常流程、主要拒绝／取消／失败分支、输入输出、状态和资金变化完整。
- **正确性**：涉及计算时说明单位、精度、舍入和公式适用条件，给出数值推演与不变量。
- **模块边界**：权威状态、排序与事务范围、确认与最终性、上下游责任明确。
- **异常恢复**：重复、乱序、超时、崩溃、部分成功和适用的重组场景有具体时序与结果。
- **工程能力**：用 Go、数据库和网络的具体机制解释方案，交代可观测指标与验证方法，不堆组件。
- **证据边界**：区分设计、伪代码、手工推演、实际执行结果；不编造性能和个人经历。
- **导航状态**：区分规划、已有正文、已审阅和已验证；建立目录不能标成专题完成。

### 7.2 推荐顺序

1. 全景与架构基线 → Go／存储工程导航。
2. 订单接入与撮合 → 成交清算 → 账本、对账与持仓。
3. 保证金 → 持续风控 → 风险价格 → 资金费率 → 强平与坏账。
4. 行情与交易回报 → 链上提交、结算、确认、重组与充提。
5. 按实际产品补 AMM／LP、预测市场、聚合路由；RFQ 和高级做市作为专项深化。

可靠交付、恢复和性能应随每个主题一起讨论，不能等所有正常流程写完后才补异常。

**可复用规则：先验证最小业务闭环，再挑核心机制深入；未展开的关键环节必须标出依赖与归属，不能用“核心 20%”掩盖缺口。**
