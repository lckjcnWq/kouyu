# 大问题 7：Solana RPC 订阅究竟承诺什么，怎样避免把通知流当成完整账本？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| RPC、HTTP、WebSocket | 节点接口、请求响应通道和长连接消息通道 | 接口在线只说明能通信，不代表状态、历史和排序能力都齐全 |
| PubSub、accountSubscribe | 发布订阅机制和单账户变化订阅 | 只把通知当刷新理由，不当完整持久账本 |
| programSubscribe | 按账户所属程序接收匹配通知 | 参数是 Token Program 地址，不是币种 M，也不保证全量初始化 |
| A、B、TA、TB、M、σ1 | 用户、代币账户、币种和交易签名代号 | TA、TB 的变化不能仅凭同 slot 配对成 σ1 |
| SPL Token、mint、authority、owner | 标准代币体系、币种、业务权限和所属程序字段 | RPC 的 owner 是程序，数据内 mint 是 M，权限方才是 A 或 B |
| decimals、原子单位 | 小数位数和最小整数计量 | 六位精度的 100 M 是 100,000,000；不能经浮点转换猜余额 |
| context.slot、Bank | 求值上下文的 slot 和节点状态视图 | 不是账户最后修改位置，也不证明多个请求来自同一状态 |
| slot、signature、持久游标 | 出块机会编号、交易签名标识和可续传日志位置 | slot 可能无块；标准账户通知不保证携带签名或持久续传位置 |
| getMultipleAccounts | 一次读取多个账户的方法 | TA、TB、M 用共同响应校验后整组发布，空账户不当零 |
| commitment、processed、confirmed、finalized | 稳定性要求及三个确认层级 | 通知和读取分别显式指定；本模型只以 finalized 快照更新稳定余额 |
| err、meta、F | 执行错误、交易附带资料和实际费用代号 | σ1 是否成功独立核验，F 从交易资料取，不从代币差额猜 |
| minContextSlot | 请求可接受的最低求值上下文 | 只能设下限，不能精确定位某次通知之后的历史状态 |
| dirty generation | 本地累计刷新理由的计数 | 读期间新增提示必须留给下一轮，计数不等于链上写次数 |
| 投影、revision、stale | 本地余额副本、发布版本和陈旧标记 | 原子发布整组；断线和队列溢出后保留旧值但标陈旧 |
| Geyser、write_version | 增强采集机制和提供方的写版本字段 | 须核实节点、重启边界和可比范围，不是通用跨源链上序号 |
| epoch、delta、重放契约 | 来源世代、增量数据和历史续取规则 | 须说明快照锚点、覆盖起点、缺口与分叉撤回，不能仅凭字段名承诺 |
| genesis hash、历史覆盖 | 集群起源标识和来源实际保留的历史范围 | 换源先验集群；能查当前态不代表能查 σ1 历史 |
| Unknown、重签 | 结果未明和签出另一份消息 | 切源查不到交易不能判失败，也不能换哈希补出第二次转账 |

## 把整篇文章压缩成一个故事

A 从 TA 给 TB 转 100 M，服务想让页面及时显示余额，于是订阅账户变化。收到 TA、TB 在同 slot 的消息，并不能证明它们来自 σ1；通知既没有本例所需的完整写序，也不保证交易签名、初始全量和断线重放。即使换成程序订阅，也要订传统 Token Program 再按 mint 过滤，而不是把 M 当成账户所属程序。

服务因此把每条消息只记为“这组数据需要刷新”，用一次 finalized 的 getMultipleAccounts 读取 TA、TB、M，核验程序、币种、权限、布局和整数后整组提交。假设 confirmed 提示先到，而首次 finalized 读取尚未包含转账，之后又没有通知；周期读取仍须继续，不能清掉本轮提示就永久停工。断线或队列溢出时标陈旧并主动重读；若主源故障，备用源上下文更旧或查不到 σ1，就分别保留旧投影和交易未知，不降低门槛或重新签名。

没有其他收支时，最终组快照可显示 TA=900,000,000、TB=100,000,000 原子单位；σ1 最终成功与费用仍由其交易证据独立说明。恢复到当前余额不等于补齐中间交易，商业增强流带 write_version 也不能直接升级成跨节点完整有序日志。选择来源要看所需能力和覆盖契约，不看连接数或接口同名；本文交付的是有上下文的当前态收敛，不是假造每次写都不丢。

**流程位置与核心机制：** 本题覆盖“账户变化感知 → 数据源选择 → 权威状态读取 → 投影发布”，回答标准 PubSub、HTTP RPC 与增强数据流各自能证明什么。交易确认和账户投影是两条证据链，不用订阅消息代替签名结果，也不用当前状态代替历史完整性。

**固定案例：** 单一 Solana 集群，非托管，传统 SPL Token 普通 mint M，decimals=6。A 控制 TA，初始 1,000 M；B 控制 TB，初始 0。I1 的 T1/σ1 使用 H1，保存对应 lastValidBlockHeight，转 100 M=100,000,000 原子单位。隔离成功结果为 TA=900,000,000、TB=100,000,000；A 的额外系统账户承担实际 `meta.fee=F` lamports，无协议费。TA、TB 已存在，不创建 ATA、不改变租金，不涉及 Token-2022、WSOL、跨链、durable nonce 或自定义幂等程序。服务编排的意图和已签名 attempt 先持久再发送，但不能约束钱包自行广播。

## 第 1 层：订阅到 TA 的变化，就能更新余额和交易结果吗？

**面试官：** 我们给 TA、TB 建立 `accountSubscribe`，收到余额变化就更新数据库。这个方案为什么还需要别的 RPC？

**面试者：** 因为标准账户订阅提供变化通知，不提供一条完整、持久、带全局写序的账户事件日志。在本模型中，通知只说明“账户可能变了”，用于把 TA、TB、M 这一组投影标为 dirty；不直接用通知负载覆盖权威余额。

权威投影由一次显式 `commitment=finalized` 的 `getMultipleAccounts([TA, TB, M])` 产生。响应带共同 context；校验三个账户的身份和数据后，在本地数据库中原子切换整组投影和 revision，避免页面看见 TA 已扣款、TB 尚未到账的拼接状态。

这仍然不证明 I1 的结果。σ1 是否最终成功，要由 signature 状态和必要的交易 meta 判断；`processed`、`confirmed` 只是可撤销预览，finalized 后还要检查 `err`。即使通知中的余额正好为 900,000,000 和 100,000,000，也不能把它当成 σ1 成功的凭据。

## 第 2 层：accountSubscribe 的 slot 能否补出交易身份和全局顺序？

**面试官：** 你说通知没有完整交易语义，但它不是有 `context.slot` 吗？用 slot 排序，再把 TA 和 TB 的同 slot 消息配对，不就能推出是 σ1 吗？

**面试者：** 不能。账户通知中的 `context.slot` 是该通知的上下文，不是全局唯一事件编号。一个 slot 内可以有多笔交易，同一账户也可能多次被写；仅靠 slot 无法区分是哪一次写，更不能给来自不同订阅的消息建立完整先后关系。

标准 `accountSubscribe` 不承诺为账户更新附带 signature，不提供持久恢复游标，也不承诺逐次写事件全部可重放。TA 和 TB 恰好同 slot 变化，只能说明观察上下文相同，不能证明两个消息来自同一笔 transfer。WebSocket 到达先后还会受网络、不同订阅分发和处理调度影响。

因此我不会通过“slot 相等且金额相反”制造交易身份，也不会从 SDK 没有提供的字段中编造 `write_version`。需要知道 σ1 的指令和结果，就查询对应交易证据；需要当前余额，就读最终共同快照。两条链可以关联，但不能相互冒充。

## 第 3 层：改用 programSubscribe，是否就拿到了 mint 的全量状态？

**面试官：** 你担心多个账户订阅难以配对，那改成 `programSubscribe` 订阅 M 的所有账户，再加 mint 过滤，能不能顺便得到全量初始化和所有变化？

**面试者：** 不能先把 mint 和程序所有者混为一谈。传统 SPL Token 账户的 RPC `owner` 是 Token Program，token 数据里的 mint 字段才是 M；token 数据里的 owner 则是 A 或 B 这样的授权主体。`programSubscribe` 的程序参数应是传统 Token Program 的地址，不是 M。

过滤条件可以缩小通知范围，但这不把订阅升级成“某个 mint 的完整快照与生命周期日志”。标准契约不承诺订阅建立时返回所有初始账户，也没有可持久续传的全局游标；还不能把过滤后未收到通知解释为“账户一定没变化”，尤其不能自行假设离开过滤集合时必有足够的删除或退出事件。

本题只维护已知的 TA、TB、M，不需要通过程序流发现全网 token 账户。因此即使选用程序订阅，也只把匹配通知映射为这组账户需要刷新；启动时仍主动读取固定集合，不能以“订阅成功且暂时无消息”宣布初始化完成。

## 第 4 层：显式 commitment 和 minContextSlot 能增加哪些保证？

**面试官：** 你仍然要读快照。如果订阅用 confirmed、读取用 finalized，再给 `minContextSlot` 传通知 slot，是否就能精确读到那次变化之后的状态？

**面试者：** 不能精确定位那次变化。commitment 必须在订阅和读取上分别显式指定，并明确两者用途。confirmed 通知可更早触发刷新，但它指向的分支可能被撤销；finalized 读取只发布本模型接受的最终状态。

`minContextSlot` 是最低上下文要求，不是“请读取指定历史 slot”。节点尚未达到下限时可能无法服务该请求；即使返回了满足下限的 finalized 响应，也可能是更晚的状态，且不能凭 slot 数字证明某条 confirmed 分支最终被采用。把 confirmed 通知 slot 机械地当作必须保留的历史点，会误解这个参数。

此外，一次 `getMultipleAccounts` 的共同 context 能约束这一响应中的固定集合；先读 TA、再读 TB 的两个请求，即使 slot 看似接近，也没有同一个 Bank 的保证。响应 `context.slot` 是读取上下文，不是每个账户最后一次修改的 slot，更不是那笔转账的交易位置。

## 第 5 层：共同快照到底要校验什么，才能作为权威投影？

**面试官：** 你依赖一次共同上下文读取。假设 RPC 成功返回三个位置，但其中一个是 null，或者 SDK 把金额转成了浮点数，这组数据还可以发布吗？

**面试者：** 不能只凭 HTTP 成功或 JSON 解析成功发布。先验证响应确实对应请求顺序中的 TA、TB、M，长度正确，context 和 commitment 符合本次读取要求。账户值为 null 是需要解释的账户不存在状态，不是金额为零；在“两 token 账户已存在”的基线下，应阻止正常余额发布并记录异常。

再验证 RPC 层程序 owner 是传统 SPL Token Program，按相应账户布局解码：TA、TB 的 mint 都应为 M，token owner 字段分别与 A、B 的控制关系匹配，状态应符合当前业务前提；M 应为合法、已初始化的 mint，decimals=6。原子金额使用整数，显示时才按 10 的 6 次方换算，不经过浮点往返。

校验通过后，将三个账户状态、读取 context 和新 revision 放在同一个本地事务中发布。隔离转账成功时应得到 900,000,000 和 100,000,000，但出现其他合法外部交易时不能硬按预期值覆盖实际值。A 的系统账户手续费不在这三个 token 对象里，由交易 meta 单独取得 F，不能从 token 差额推算。

## 第 6 层：断线重连后没有消息，是不是可以视为已追平？

**面试官：** 你有完整快照校验了。连接断开十秒后重连成功，订阅 ID 也重新拿到了，但一直没消息。是否可以直接恢复“实时同步”标志？

**面试者：** 不可以。订阅 ID 是连接上的订阅标识，不是账本偏移量；重连成功只说明新的通知通道建立，不证明断线期间没有变化，也不证明旧连接最后一条消息之后的数据已补齐。

断连、通知处理队列溢出和无法判定的订阅故障都应立即把投影标为 stale，并安排固定集合的 finalized 全量重读。对每次提示增加本地 dirty generation；刷新开始记住当时 generation，响应校验并原子发布后，仅在 generation 未变化时清除该轮 dirty。读取期间到达的新提示必须留下后续刷新义务。

同时还要周期性全量刷新。比如 confirmed 提示到达时，finalized 快照还没包含该变化，此后又没有新的通知；单靠这一轮 dirty 清除会错过后续最终状态。周期刷新提供再次读取机会，但它保证的是在数据源可用、刷新持续进行等条件下当前态收敛，不是每一次中间写都不丢。

## 第 7 层：换成 Geyser 或商业流，能否直接获得强顺序？

**面试官：** 你把标准 PubSub 的边界说得很窄。供应商说其 Geyser 流有 `write_version`、重放和账户与交易关联，我们是不是直接用这些字段替代 dirty 重读？

**面试者：** 可以评估增强能力，但不能只凭字段名升级一致性承诺。必须核实 `write_version` 来自哪个节点或插件、在什么范围内可比较、进程重启或提供方所称的 epoch 切换时是否重置、切换数据源后是否仍有连续性，以及分叉撤销、重复和缺口怎样表达。它不是 Solana 链上通用序号，不能天然跨节点比较。

重放也要问清保留范围、起点语义、快照锚点、从哪一个位置开始包含 delta，以及服务端如何证明没有静默缺口。如果账户更新与 signature 的关联只覆盖某些交易类型或采集路径，不能把未关联的数据强行归因。

只有在这些契约被文档和可核验行为支持、并另行设计快照衔接和失败恢复后，才能采用对应的增量方案。本题的既定基线不更换为商业日志：仍以 PubSub 失效提示、串行 finalized 重读和周期刷新维护当前投影。增强流是改变前提后的选项，不是当前方案已经具备的能力。

## 第 8 层：故障切换时，怎样判断数据源够不够用？

**面试官：** 你要求验证数据源契约。现在主 RPC 故障，备用节点的 finalized context 更旧，而且查不到 σ1；产品要求立即切换且不得显示回退，你会怎样裁决？

**面试者：** 先确认备用节点属于同一个集群，并核对已记录的集群身份，例如 genesis hash；不能只看两个 URL 都包含相同网络名称。账户读取沿用显式 finalized，并以上次已发布上下文设置合理的 `minContextSlot` 下限，拒绝用更旧响应覆盖较新投影。备用节点不满足下限时保留旧值并标 stale，不能为了去掉告警降低读取要求。

σ1 查询空值则单独归入状态证据不足。备用节点当前状态服务正常，不代表其签名历史或最终区块归档覆盖足够；历史链应保留缺口，不把空值变成失败。若 I1 结果未知，也不能因为切了节点就更新 blockhash 重签，普通 SPL transfer 没有链上 I1 消费屏障。

最终可向业务交付的是带时间和上下文的最近已验证投影，以及独立的交易最终状态。不能交付“切换成功，所以所有历史完整、所有写不丢”的虚假承诺。数据源选择的标准是所需能力是否覆盖，而不是接口是否同名或连接是否在线。

## 收束：机制、易错边界与反例验证

- **讲透的机制：** 标准订阅负责使缓存失效，一次 finalized 共同快照负责当前态，signature 和交易 meta 负责交易结果，独立的最终区块覆盖负责业务历史。
- **最易错的边界：** 订阅不承诺持久游标、全局写序、signature 或全量初始快照；程序 owner 不等于 mint 或 token authority；`minContextSlot` 不是历史点查询；商业 `write_version` 不是可跨源通用的链上时钟。
- **反例验证：** 手工安排“confirmed 通知先到 → finalized 重读尚无转账 → 不再有通知 → 稍后转账最终确定”。若没有周期重读，投影可能长期停在旧值；若直接使用通知余额，则可能发布被撤销分支。合格基线既不冒进发布，也保留后续收敛路径，不宣称逐次写完整。
