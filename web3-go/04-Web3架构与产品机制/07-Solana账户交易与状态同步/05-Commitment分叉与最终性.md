# 大问题 5：怎样处理 Solana 的 commitment、分叉与业务最终性？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| I1、T1、σ1 | 业务意图、签名尝试和交易签名标识 | 跟踪 A 从 TA 给 TB 转 100 M 的具体交易，不拿余额替代身份 |
| commitment | 对观察稳定程度的要求 | 是证据的确认强度，不是已等待的秒数 |
| processed | 节点在当前处理视图中看到了结果 | 可能属于后来放弃的分支，只能作可撤销预览 |
| confirmed | 对应区块获得足够活跃质押直接投票确认 | 比 processed 更强，本模型仍不当成最终转账结果 |
| finalized | 达到更强扎根和锁定边界的状态 | 本文最终裁决门槛，仍须另外核验执行有无错误 |
| err、confirmationStatus | 执行错误和该结果的确认级别 | finalized 失败也是可能结果，不能拼接旧成功与新最终性 |
| 分叉、预览撤回 | 临时分支及不再依赖其低确认观察 | 撤回本地推断，不是数据库有权撤销链上转账 |
| slot、block height | 出块机会编号和实际区块高度 | slot 可能无块；520、522 是示意位置，不与有效高度混用 |
| blockhash、parentSlot | 区块身份哈希和父位置字段 | 能取得时保留以辅助分支核验；同 slot 不独立证明同分支 |
| null、Unknown、Pending | 查询未给结果、结果未知和等待处理 | 查无记录不等于最终失败，不能自动重签补转 |
| RPC、PubSub、fork graph | 节点接口、订阅通知和分支关系图 | 普通账户通知不提供完整分叉图，不足以构造完整低确认历史 |
| context、Bank | 求值上下文及节点在某分支上的状态视图 | 两次读取都 finalized，也不代表来自同一时点同一状态 |
| getMultipleAccounts、minContextSlot | 一次多账户读取与最低上下文门槛 | 整组读取 TA、TB、M；门槛不能选择某个精确历史状态 |
| revision、source epoch | 本地裁决版本和来源会话代号 | 用来阻止旧结果回写，不是链上顺序或真实性证明 |
| genesis、来源独立性 | 集群起源标识和数据来源是否实际独立 | 多个接口若同一后端，不能当成独立投票证据 |
| 最终性事故、隔离 | 已采信的最终事实冲突，暂停采用相关数据 | 不能按普通暂态撤回或最后到达值覆盖，需要留证核验 |
| policyVersion、evidenceRef、decisionRevision | 策略版本、证据引用和裁决发布版本 | 历史承诺按当时策略可追溯，配置变化不能静默改写过去 |

## 把整篇文章压缩成一个故事

A 发起给 TB 的 100 M 转账，服务保存 I1、T1 和 σ1。节点先报告 processed 成功，页面可以说“暂时观察到执行成功”，却不能据此承诺最终到账或触发不受控的外部给付；confirmed 也只是更强的暂态。本模型要核实同一集群、同一交易的完整证据达到 finalized 且 err 为空，才确认最终成功，不能把“稳定”误读成“一定执行无错”。

随后原预览查不到了，服务保留旧观察，撤回暂态推断并继续核查，不立刻判失败或重签。若后来拿到可靠的 finalized 失败，就接受失败结果并单列实际费用，而非用旧记录的成功配上新记录的最终性。教学主例中交易在 slot 520 最终成功，余额若读自 519 就继续同步；甲源读到 522、乙源只到 518，则先检查进度差。若声称同一 finalized 上下文却给出矛盾内容，才隔离为信任、配置或最终性问题，不能用最后写入者取胜。

无其他转账时，最终余额是 TA=900 M、TB=100 M；若快照更晚且还有别的收支，展示实际读到的值，不强改回教材数字。账户快照最终性、该笔执行结果和展示新鲜度分别有证据，最低上下文门槛也不等于历史定位器。日后产品降低小额完成门槛，是新的风险策略，不把 confirmed 变成协议上的 finalized，也不能无审批改写旧承诺。

**流程位置与核心机制：** 从“节点看到交易”推进到“产品认可的最终结果”，解释暂态撤回、跨源证据、账户快照与最终性事故。不把普通分叉处理泛化成任意已最终确认事实都能随意覆盖。

沿用总览的 I1／T1／σ1：TA→TB 转 100 M，传统 Token，processed／confirmed 只作预览，finalized 且 err=null 才算本模型最终成功。slot 520、522 仅是教学位置，与 block height 分开。

## 第 1 层：三个 commitment 怎样映射业务

**面试官：** processed、confirmed、finalized 有什么区别？这笔 100 M 转账到底在哪一步可以说成功？

**面试者：** processed 表示某节点已在其处理视图中看到该交易或状态，仍可能属于后来放弃的分支；confirmed 表示对应区块得到足够活跃质押的直接投票确认；finalized 是更强的扎根和锁定边界，适合本模型作为最终业务结果的依据。它们描述的是观察事实的确认强度，不是客户端等了几秒。

但“finalized”本身不等于转账成功。我们还要检查 σ1 的执行结果 err=null，确定它确实是用户授权的那笔交易。若 err 非空，可能是最终确认的失败交易，不能因为确认强度高就记成 TA 已减少 100 M。

本模型把 processed／confirmed 成功显示为可撤销预览，finalized 成功才把 I1 标为最终转账成功。余额投影是否更新另行跟踪，不拿页面看见一个新数字反推最终性。

## 第 2 层：confirmed 预览为什么不能直接当钱花

**面试官：** 既然 confirmed 已有足够投票，为什么还要保留撤回？用户体验不是越早标成功越好吗？

**面试者：** 这取决于产品承诺。本稿选择更保守的最终门槛，是为了在同一前提下讲清状态归属；我不会把低延迟收益伪装成没有风险。confirmed 可以改善交互速度，但服务若据此触发不可逆的外部付款或信用释放，就承担了在它撤回时无法自动恢复的风险。

因此预览和最终结果分开存储与展示，预览不能覆盖已确认的稳定历史。对暂态，系统要能撤销提示、重新查询并解释仍待确认；对已经触发的外部副作用，单纯改回数据库 status 并不能把钱追回来。

如果某产品确实愿意在 confirmed 提前提供额度，必须明确额度、金额、风险预算、损失承担和停止条件。这是改变产品风险策略，不是把 confirmed 改名为 finalized，也不是主例已经支持的能力。

## 第 3 层：分叉身份该怎样保存

**面试官：** 你说可以撤销预览。如果只存了 σ1、slot 520 和“成功”，撤回时怎么知道原观察属于哪条分支？

**面试者：** 这些字段不足以完整表达分叉来源。我会保留数据来源、观察上下文、commitment 和原始响应；能取得交易所在区块的 blockhash、parentSlot／父区块身份时，也保存下来。slot 是位置标签，不是可以独立证明分支相同的哈希。

还要尊重来源能力：标准账户 PubSub 通知没有给出完整 fork graph 和逐笔因果，不能从一条账户通知虚构其所属的完整分叉链。本模型不使用通知负载建立权威低确认余额，而是把它当提示，从 finalized 组读取更新稳定当前态。

交易预览则以 σ1 的可撤回观察表示。若需要维护完整 processed 多版本账户视图，必须另行获取足够的分支、状态与撤销证据，并验证来源契约；不能把主例轻量方案包装成已经具备完整 fork-aware 索引器。

## 第 4 层：具体怎样处理预览消失

**面试官：** 某节点先返回 σ1 processed 且 err=null，之后查询返回 null。你会把它从成功直接改为失败吗？

**面试者：** 不会。预览消失可能来自分支变化、节点切换、缓存范围、节点落后或查询能力不足，单次 null 不足以确定失败。我会保留原观察，将当前可见性和确认进度改成待核查，停止把原预览当作可依赖的成功事实。

跟踪器继续查原 σ1 和相关有效窗口；若换源，先验证集群和来源能力，不能拿一个历史裁剪节点的空响应覆盖已有强证据。尚未超过有效窗口时，原交易还可能重新被处理；即使窗口结束，也需要排除此前已有最终成功，不能立刻重签补转。

状态机允许从“暂时观察到成功”回到“当前未知”，但不把未知转换成明确失败。撤回的是我们的低确认推断，不是由数据库命令撤销链上交易。

## 第 5 层：确认强度与执行结果怎样共同提交

**面试官：** 那么一个来源说 processed 成功，另一个说 finalized 失败，是否只要取 confirmationStatus 更大的那条？

**面试者：** 不能把不同字段、来源和分支随意拼成一个“最强记录”。应核验它们是否指向同一 σ1、相同集群，以及最终规范链上的交易身份，再接受完整证据中的执行结果和确认状态。我们需要的是“这份结果已 finalized”，不是从旧结果取成功、从新响应取 finalized。

在数据库里可以保留多条不可变观察，另外维护当前裁决及其证据引用。若可信最终证据表明 σ1 执行失败，I1 就是最终失败，费用按实际证据单列；旧成功预览被撤销，不能继续生成成功通知。

这种更新可以有本地 revision，但 revision 只排序我们的裁决发布。它不能证明两个上游观察本来在链上有同一位置或兼容性；证据验证必须在发布之前完成。

## 第 6 层：账户快照的 finalized 与交易的 finalized 是一回事吗

**面试官：** σ1 已最终成功，而账户快照也带 finalized，但为什么还不能保证你读到的 TA 就是 900 M？

**面试者：** finalized 指定读取的确认强度，不保证恰好停在 σ1 后一刻。快照可能早于 σ1，也可能晚于它并包含其他转账；而 TA 在真实钱包中还可能有别的支出或收入。主例没有其他交易时才得到 900 M。

我们需要核对共同上下文、集群和账户身份。若读取上下文还没覆盖 σ1 的最终位置，可以要求最低 context 后重读；但 minContextSlot 只设下限，不选定某个历史状态。若读取更晚，应该展示那时的实际余额，并通过交易证据解释 σ1 的 100 M，不把当前余额硬改成教材结果。

本模型用一次 getMultipleAccounts 读取 TA、TB、M，而不是分别读不同时间的账户后声称它们是一张相同 Bank 的快照。确认强度一致是必要条件之一，不是任意多请求数据都可原子拼接的充分条件。

## 第 7 层：多个节点给出不同 finalized 高度怎样处理

**面试官：** 如果节点甲 finalized 读到 slot 522，节点乙 finalized 只有 518，是否说明两者意见冲突，要投票决定哪个余额正确？

**面试者：** 不一定。不同进度可以是正常滞后，slot 522 的余额和 518 的余额本来就可能不同。应先确认集群、上下文和来源健康，不能直接对两个不同水位的余额做多数表决。

我们可以拒绝低于已有最低上下文的读取，或等待落后节点追上再核验；这维护的是读取下限，不证明更快节点一定诚实。若要核对同一历史位置，而普通账户 RPC 又不能固定历史 Bank，就需要具备相应证据的数据源，不能用 minContextSlot 冒充历史定位。

对于已有稳定投影，普通切源不应让旧轮次或低水位结果回写。source epoch 和本地读轮次能围栏旧结果，但这些是控制层约束，真实信任仍依赖来源和规范状态证据。

## 第 8 层：两个可信来源给出矛盾 finalized 事实怎么办

**面试官：** 如果不是进度差，而是同集群同一声称 finalized 上下文，账户内容或区块身份真的矛盾，还按“较新覆盖较旧”处理吗？

**面试者：** 不能。这已经超出正常低确认分叉的处理范围，可能是来源错误、解码或配置错误、缓存污染，或者最终性／信任假设被破坏。应该隔离冲突、保留原始证据并停止依赖该差异的高风险业务，不自动把最后到达的值升级为新真相。

先复核集群 genesis、请求配置、字段规范化、账户生命周期、解码版本和来源独立性，再核验相关区块和规范链证据。若确认是自己的投影错误，可基于已验证证据重建；若是更深的最终性事故，则按人工批准的修复与审计流程处置。

旧的最终成功通知及其外部效果不能通过覆盖一行余额假装没发生。需要明确哪些事实曾被承诺、影响了什么、是否需业务冲正，保留可审计修复，而不是沿用普通预览撤回逻辑。

## 第 9 层：规则升级会不会改写过去的最终性

**面试官：** 如果产品后来决定小额 confirmed 就可以“完成”，你会不会把所有旧 Pending 记录直接批量改成完成？

**面试者：** 不能只按当前配置重算历史标签。业务结果应引用当时采用的最终性策略版本和具体证据，避免同一条记录在不知情的情况下改变承诺。新的策略可以影响新意图，旧意图是否迁移要有明确范围和审批。

即便小额策略允许提前“业务受理完成”，也应保留链上确认级别和风险状态，不把 confirmed 响应伪造为 finalized。对外用词需要区分风险承诺和协议事实，后续若撤回，仍有对应恢复路径。

工程上将 policyVersion、evidenceRef、decisionRevision 分开，让重放在指定策略与输入下得到确定结果。升级解码器、切数据源或修改显示文案，都不能顺手把既有证据边界抹掉。

## 第 10 层：怎样检验最终性方案成立

**面试官：** 最后给一组能证伪方案的场景，不要只说“增加监控”。

**面试者：** 第一，把 processed 成功预览后接一个查无结果，检查系统只撤销暂态推断、进入核查，不制造最终失败或新签名。第二，输入 finalized 且 err 非空，检查不会因为确认等级高而生成成功转账。第三，交易在 slot 520 最终成功，余额读取来自 519，检查页面明确同步中而不重转。

第四，甲源 slot 522、乙源 518，验证先按进度差处理；第五，在同一声称 finalized 上下文输入矛盾内容，验证进入隔离而非最后写入获胜。最后用策略版本变化重放同一证据，检查历史承诺能追溯，不被当前配置静默改写。

这些场景把常规分叉、未知、落后、执行失败和信任事故分开。只有分别定义裁决和恢复条件，最终性才不是界面上的一个绿色勾；本稿给出推演，不声称已经完成验证者级故障注入。

## 本题收束

- **讲透的机制：** 执行结果与确认强度正交、完整证据裁决、低确认撤回、读取上下文及最终性事故隔离。
- **最易答错：** finalized 一定成功；null 一定失败；按最大 slot 多数投票；把 minContextSlot 当历史快照；所有分叉都靠覆盖旧数据处理。
- **检验反例：** 取旧观察的 err=null，再拼接新观察的 finalized，系统能否生成一条没有任何完整原始证据支持的最终成功？若能，证据模型错误。
