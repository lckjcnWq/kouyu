# 大问题 8：同一个 Solana slot 内账户多次更新，怎样排序并维护可信的本地投影版本？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| slot、S、lastSlot | 出块机会编号、示例位置和本地保存的位置 | slot 可能无块，同一 slot 也可能有多次账户变化，不能当逐写版本 |
| TA、TB、M、I1、σ1 | 账户、币种、业务意图和交易签名代号 | 主例转 100 M；另转 10 M 是明确增加的外部操作变体 |
| accountSubscribe、PubSub | 账户订阅和发布订阅机制 | 没有逐次写全量保证，负载只触发刷新，不直接改余额 |
| 大于与大于等于过滤 | 仅接受更大 slot，或也接受相同 slot | 前者可能漏同 slot 后续变化，后者可能让旧值覆盖新值 |
| dirty generation、g、g0、g1 | 刷新理由计数及不同时间点的计数值 | g1 大于 g0 只说明读期间新增提示，不代表多了几笔链上交易 |
| 到达时间、本地序号 | 接收消息的时间和编号 | 只能排序本地观察，不能补出链上执行顺序 |
| projection revision、R | 账户组的本地发布版本及其符号 | 表示第几版已验证视图，不是第几笔交易或第几次账户写 |
| finalized、commitment | 最终性级别和读取稳定性要求 | 本模型在该门槛下读取当前态，不采信低确认通知余额 |
| getMultipleAccounts、context | 一次组读取及共同求值上下文 | TA、TB、M 同次获取；页面读取也须遵守同组版本 |
| minContextSlot、Bank | 最低求值门槛和节点状态视图 | 门槛不锁定历史状态；分别读账户不能拼成共同快照 |
| Token Program、mint、authority、decimals | 代币程序、币种、权限和小数位 | 读完仍要核实身份、布局及六位精度，不能只看请求成功 |
| 本地事务、条件更新 | 整体数据库提交和匹配基准才准写入 | 让整组与 revision 一起切换，旧基准不能绕过裁决发布 |
| 任务身份、epoch | 刷新任务标识和会话或来源代号 | 撤销超时旧任务的发布资格，不等于链上的全局版本 |
| stale、周期刷新 | 陈旧标记和不依赖通知的定时重读 | 没新提示不证明链不再推进，断线后不能只清计数 |
| err、confirmationStatus、F | 执行错误、确认状态和实际手续费代号 | 签名结果独立判断，投影更新不能触发未知交易重签 |
| write_version、可比范围 | 增强来源的写版本及哪些记录可以比较 | 需核实节点、重启和切源边界，不能跨源直接比数字 |
| getBlock、meta、逐写镜像 | 区块查询、执行资料和每次账户写的独立快照 | 可解析限定转账历史，不通用保存任意程序的每次内部写 |
| delta 契约 | 增量来源对覆盖、排序与撤回的明确保证 | 真要逐写审计必须另行验收，不能给 slot 或本地 revision 改名冒充 |

## 把整篇文章压缩成一个故事

A 的 TA 初始有 1,000 M，在一个明确变体中先通过 I1 转出 100 M，随后又独立转出 10 M，于是余额依次是 900 M、890 M。两笔可能在同一 slot；如果通知先送到 890 M，再迟到一条 900 M，用 slot 大于等于过滤会倒退，用严格大于过滤又可能丢掉真正的后续变化。纳秒时间或接收编号只能证明看见的先后，不能证明链上写序。

同步器不应用这些余额负载，只增加本地刷新计数。开始共同 finalized 读取时记住 g0，期间新提示使计数变成 g1，就算本轮快照合法发布，也保留下一轮刷新义务，不能直接清零。TA、TB、M 与本地 revision 在一个事务中切换，页面也按同组版本读取；旧请求超时后须撤销发布资格，迟到响应先验任务身份和基准。节点返回更旧上下文则拒绝回写，重启从数据库已提交版本恢复并重新标待刷新。

如果快照已包含额外 10 M 转出，TA 就应展示 890 M，而不是硬套独立主例的 900 M；本地版本只说明发布了哪版视图，不说明链上写过几次。当前提示处理完也仍要周期刷新，低确认变化可能稍后才最终确定。增强来源的写版本和最终区块交易顺序各有可比与解析范围，都不能未经契约证明就变成任意账户逐写日志；本文宁可承认中间顺序未知，也不编造它。

**流程位置与核心机制：** 本题位于“订阅提示 → 刷新调度 → finalized 快照读取 → 本地投影切换”。核心不是从缺失信息中猜链上写序，而是区分 slot、dirty generation 和 projection revision，通过串行读取与原子发布维护整组当前状态。

**固定案例：** 单一 Solana 集群、非托管、传统 SPL Token 普通 mint M，decimals=6。A 的 TA 初始为 1,000,000,000 原子单位，B 的 TB 为 0；I1 的 T1/σ1 使用 H1，保存对应 lastValidBlockHeight，将 100,000,000 原子单位即 100 M 从 TA 转到 TB。隔离成功后 TA=900,000,000、TB=100,000,000，A 另以系统账户支付实际链上 `meta.fee=F` lamports，无协议费。账户已存在，不创建 ATA、不涉及租金变化，不引入 Token-2022、WSOL、跨链、自定义幂等程序或 durable nonce。意图和已签名 attempt 在服务发送前持久化，但钱包可能自行发送，服务不承诺约束全部外部行为。

## 第 1 层：为什么只保存 slot 不能防止旧余额覆盖新余额？

**面试官：** TA 在同一个 slot S 内先后出现两个余额，客户端只接受 `slot >= lastSlot` 的通知。这样能防止旧状态覆盖吗？

**面试者：** 不能。slot 不是每次账户写入的唯一序号，同 slot 的两次变化比较结果相等，`>=` 会让迟到的旧消息覆盖新消息；改成 `>` 又可能把同 slot 的后续变化丢掉。更根本的问题是，标准 `accountSubscribe` 没有承诺提供每一次原始账户写的完整日志，所以不能先假设两条通知就代表所有中间状态。

例如在一个明确的外部操作变体中，I1 将 TA 从 1,000 M 减到 900 M，随后 A 又独立转出 10 M，TA 变成 890 M。两笔可以位于同一 slot。订阅如果先交付 890 M，再交付较早的 900 M，单靠 slot 判等无法裁决。

因此本模型不直接应用订阅负载。消息只增加本地 dirty generation；权威余额来自一次 finalized 的 TA、TB、M 共同快照。这样不需要伪造不存在的同 slot 写序，也不承诺恢复这个过程中每一笔写。

## 第 2 层：改用消息到达时间或本地递增序号，为什么还是不行？

**面试官：** 你说 slot 不够，那我们为收到的每条消息分配本地序号，或者精确记录纳秒到达时间，按这个顺序应用，不就解决同 slot 冲突了？

**面试者：** 这只给接收过程排了序，没有给链上执行排出序。不同订阅、节点内部缓冲、连接重建和本地 goroutine 调度都可能改变到达顺序；再精确的时钟也只能说明“我们什么时候看见”，不能说明“链上什么时候写入”。

本地递增序号可以用于调度：收到任意相关提示就把 dirty generation 从 g 加到 g+1。它表达“自上次读取以来又有刷新理由”，不表达“第 g 次链上写”。因此允许多个提示合并为一次刷新，也允许没有链上变化的重复提示增加 generation。

相反，如果把这个本地序号作为账户事件版本，迟到消息会因为后分配了大序号而被错误视为最新。设计上要把两个语义彻底分开：链上未知顺序不猜测，本地刷新义务可以精确计数。

## 第 3 层：不使用通知版本，页面应当依赖哪个版本？

**面试官：** 你把 dirty generation 限制为调度计数，那数据库和页面总要有版本。这个版本如何定义，怎样保证 TA 和 TB 不出现半笔转账？

**面试者：** 我会定义 projection revision，表示本地一组已验证快照的发布版本。它在数据库事务中递增，与 TA、TB、M 的新投影、读取 context 一起提交。revision=R 不意味着第 R 笔链上交易，也不意味着账户第 R 次写入。

刷新采用一次显式 `commitment=finalized` 的 `getMultipleAccounts([TA, TB, M])`。先校验三个位置、非空条件、传统 Token Program 所有权、token 账户 mint 与 authority、mint 的 decimals=6，以及整数金额解码，再原子切换整组结果。

读页面时也必须遵守整组 revision：从同一个数据库一致性读取中取出 TA、TB、M，或者先取得不可变快照版本再读对应记录。不能虽然写入是原子的，却在两个独立查询之间跨过一次提交，把 TA 的新版本和 TB 的旧版本拼在一起。隔离成功案例在同一发布版里看到的应是 900,000,000 和 100,000,000。

## 第 4 层：读取期间又来提示，怎样不丢掉刷新义务？

**面试官：** 你原子发布了一组快照，但 HTTP 读取期间来了新通知。发布完成后直接把 dirty=false，会不会把新变化一起清掉？

**面试者：** 会，所以清除 dirty 必须绑定本轮读取开始时的 generation，而不是无条件清零。假设开始读取时 generation=g0，记录该值后发出一次 finalized 共同读取。期间又收到提示，使 generation 变成 g1，且 g1>g0。

响应校验通过后可以发布这组有效快照，但收尾时必须比较当前 generation。若仍等于 g0，才可以说这轮已处理当时已知的刷新理由；若已经增大，就保留 dirty 并串行启动下一轮。新提示可能对应读取已包含的状态，也可能对应读取尚未包含的状态，标准接口不能精确判断，因此宁可多读一次。

generation 的递增、读取完成后的比较和 dirty 清理，要在同一协调锁或等价的数据库条件更新边界内完成。不能先比较相等、释放锁，再独立清除，否则通知可能正好插入这两个动作之间。本地版本解决的是调度竞态，不是补出链上写序。

## 第 5 层：串行重读时，context.slot 应该怎样参与版本判断？

**面试官：** 你已经串行了，但两次 RPC 可能落到不同后端。后一轮返回更旧的 context.slot，或者两轮 slot 相同，你怎样处理？

**面试者：** 对同一集群的最终状态投影，不允许用较旧读取上下文覆盖已发布的较新上下文。读取时可以将上次已发布的 finalized context 作为 `minContextSlot` 下限；若节点达不到，等待或保留旧投影并标 stale，不降低标准来制造新鲜感。返回结果仍要再检查下限，不能只相信请求参数已经消除了所有异常。

两次 context.slot 相同，不代表收到重复链上写事件，也不能据此推算账户修改次数。可以校验内容后把它作为同一上下文的一次刷新确认；是否为这次发布递增 revision 是本地策略，但语义必须一致。本模型若发布新的读取与新鲜度元信息，就同时递增本地 revision，不能将其包装成链上新事件。

`context.slot` 是读取上下文，不是 TA 或 TB 最后修改的 slot；`minContextSlot` 是下限，不会把请求固定在某个历史 Bank。也不能通过分别读取 TA、TB 并挑选相近 slot 重新制造共同快照，固定集合仍必须在一次响应内读取。

## 第 6 层：并发刷新和重启会不会让 revision 倒退？

**面试官：** 你依赖串行读取。如果一次旧请求卡住，超时后又开了新请求，旧响应最后才到；或者进程提交投影后立刻崩溃，下一次启动如何防止旧结果覆盖？

**面试者：** 串行不是“正常时大致只有一个请求”，而是发布资格必须可裁决。每轮读取有本地刷新任务身份；超时后若无法确认旧请求已经结束，就撤销它的发布资格，再启动新轮。旧响应迟到时即使数据合法，也必须先核对当前任务身份，不能直接进入发布路径。

数据库提交时再检查读入的基准 revision 是否仍是当前版，必要时使用事务锁或条件更新。只有赢得提交资格的完整快照才能发布新 revision，冲突结果不能绕过校验逐账户补写。这些只是已有本地数据库的原子性要求，不需要添加新的消息系统。

进程重启后，从数据库已提交的 revision、context 和快照恢复；未提交的候选结果不算已发布。启动时主动标记待刷新或 stale 并重读，不能因为内存 dirty generation 丢失就认为链上没有新变化。若投影已提交、dirty 收尾未完成，最多多读一次；不能因此回退余额或重复执行转账。

## 第 7 层：finalized 重读没有变化，是否能清除所有不确定性？

**面试官：** 你能防止旧响应覆盖了。现在一次 confirmed 通知使 generation 增加，随后 finalized 快照仍是旧余额；generation 又没变，是否可以永远停止刷新，并认定 T1 没发生？

**面试者：** 不能。generation 相等只证明本次读取期间没有新增本地提示，不证明链上不再向前推进。confirmed 通知对应的交易可能稍后才最终确定，也可能被撤销；这次 finalized 快照可以是正确的旧最终状态，却不是未来不会变化的证明。

因此“本轮已处理 dirty”与“没有后续刷新需求”分开。系统保留周期性 finalized 全量刷新，必要时由 σ1 状态进入最终阶段再触发一次刷新。在通知持续可用、RPC 最终能够服务足够新上下文、任务持续执行的条件下，当前态会继续收敛。若断线或队列溢出，则标 stale 并重扫，不能仅清计数。

同样，当前余额没有变化不能证明 σ1 失败，当前余额变化也不能证明 σ1 成功。σ1 的 `confirmationStatus` 与 `err` 独立判断；最终失败仍可能收取 F。账户投影版本不能拿来触发未知交易的自动重签，否则从缓存一致性问题跳成了重复转账问题。

## 第 8 层：如果确实需要逐写顺序，应该承认哪些额外前提？

**面试官：** 你保住了当前态，却没恢复同 slot 中的每次写。供应商给出 `write_version`，或者我们从 getBlock 取得交易顺序，是否就能补成通用账户写日志？

**面试者：** 两者都不能未经限定就补成通用写日志。增强数据流的 `write_version` 必须验证来源节点、生成器的 epoch 或重启边界、可比较范围、切源连续性和分叉处理；它不是链上所有节点共享的通用序号。没有这些契约，两个不同来源的版本号甚至不能直接比较。

最终区块的交易与 meta 可以支持本题限定的传统 SPL 转账业务历史解析，但不能通用恢复任意程序每一次账户原始写。交易指令的先后和账户写快照也不是一个层级：一次交易内可能多次修改同一账户，而标准最终账户状态不会为每次内部修改保存独立镜像。

所以本基线明确交付当前态的一致发布，不承诺每次写不丢。如果产品真的需要逐写审计，就必须另立具有明确快照锚点、完整 delta 覆盖、排序和回滚语义的数据契约，不能把现有 slot、到达时间或 projection revision 改名后冒充。对 I1，本地可确定的是某版最终快照和 σ1 的独立最终结果，不是从通知流猜出的每次余额路径。

## 收束：机制、易错边界与反例验证

- **讲透的机制：** slot 表示链上上下文，dirty generation 表示本地刷新理由，projection revision 表示本地原子发布版；三者不可互相替代。一次共同读取、整组原子写入和整组一致读取共同防止混合版本。
- **最易错的边界：** 同 slot 无法用大小排序多次写；到达时间不是执行时间；读期间新提示不能被清理；相同 context 不代表账户修改序号；切换数据源不自动获得连续版本。
- **反例验证：** 手工推演“读开始于 g0 → 新提示使 g1>g0 → 新读先发布 → 已撤销资格的旧响应迟到”。正确方案保留后续刷新义务，并拒绝旧任务覆盖当前 revision；如果只比较 slot 或最后写入者获胜，就可能退回旧余额。此为机制推演，不声称运行过工程测试。
