# 大问题 1：一笔 Solana 转账怎样从用户发起走到本地最终可见？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 非托管、状态权威 | 平台不代用户掌握资产；真实余额由链上状态决定 | 本地受理请求不能让 TA 真正少掉代币 |
| A、B、TA、TB、M | 转出方、接收方、源账户、目标账户和币种代号 | A 授权从 TA 给 TB 转 M，钱包与代币账户不是同一个概念 |
| SPL Token、mint | 标准代币程序体系和币种定义账户 | 本文固定传统 Token Program，TA、TB 必须属于同一 M |
| decimals、原子单位 | 显示小数位和最小整数计量 | 六位精度下 100 M 等于 100,000,000 原子单位 |
| TransferChecked | 带币种精度检查的转账指令 | 由链上程序验证权限和条件后，同时修改 TA、TB |
| I1、T1、σ1 | 用户意图、具体尝试和交易签名标识 | 记录想做什么、实际签了哪份、链上该查哪笔 |
| H1、hmax | 近期区块哈希及最后有效区块高度 | 保存有效窗口，不能以客户端超时替代协议有效性判断 |
| SOL、F、lamports | 原生币、实际手续费符号和费用最小单位 | A 的系统账户另付 F，不从 100 M 中扣除 |
| RPC、sendTransaction | 节点接口及发送已签交易的方法 | 返回只说明发送层观察，不证明最终转账成功 |
| intentStage、txObservation、accountGroup | 意图阶段、交易观察和账户组 | 分开保存业务进度、链上证据与余额，不塞进一个成功标记 |
| slot、context | 出块机会编号和读取求值上下文 | slot 可能无块；读取上下文不能冒充交易刚执行后的精确状态 |
| commitment、confirmationStatus、err | 稳定性要求、返回的确认级别和执行错误 | 本模型须 finalized 且 err 为空才算最终成功 |
| processed、confirmed、finalized | 已处理、较强投票确认和最终性级别 | 前两者只作暂态；最终性与执行有无错误分开判断 |
| PubSub、失效提示 | 发布订阅通知，以及提醒旧视图可能过期的信号 | 不保证 σ1 对应通知必达，也不负责补全逐笔历史 |
| getMultipleAccounts、minContextSlot | 账户组读取和最低求值上下文门槛 | 一次读 TA、TB、M；门槛不是指定历史时点 |
| 投影、revision、stale | 本地查询副本、发布版本和陈旧标记 | 整组同版本发布，失败保留旧组但声明陈旧 |
| 本地事务、Outbox | 数据库的整体提交和随提交保存的待通知记录 | 余额组与通知一起落库，不等于链与数据库原子提交 |
| 当前态与历史覆盖 | 此刻读到什么，以及过去哪些业务已完整取得 | 余额恢复不等于断线期间每笔交易都找回 |

## 把整篇文章压缩成一个故事

A 要从 TA 给 B 的 TB 转 100 M。传统代币 M 有六位小数，TA 原来有 1,000 M，TB 为零。服务把这件事记为 I1，把金额固定成 100,000,000 原子单位，检查币种、账户和权限后构造 TransferChecked，取得 H1 与 hmax；A 审核签名，形成 T1 和 σ1。平台只是保存意图和证据，不在受理时另扣一份“平台余额”。

服务先保存完整已签字节再发送，结果却超时或进程崩溃。恢复后先查 σ1，在允许窗口内也只能按策略重发原字节，不能换哈希重签来赌旧交易没执行。链上最终成功而本地更新 TB 失败时，也不补转；同步器重新读取 TA、TB、M 的 finalized 共同快照，用一个本地事务提交整组和通知记录。订阅没收到消息则主动重读，不能无限等一条并不保证送达的通知。

没有其他业务时，链上 TA 变成 900 M、TB 变成 100 M，A 另付 F lamports；σ1 最终成功与页面已刷新分别报告。如果读到旧余额就检查上下文是否覆盖交易位置；若更晚余额又回到原值，还要考虑反向转账，不能否认 σ1 或再扣一次。当前余额、该笔结果、逐笔历史完整性是三条证据线，刷新页面只能修投影，不能制造第二次资产转移。

**流程位置与核心机制：** 串起意图、签名、发送、链上执行、确认、账户同步与展示，重点回答谁拥有状态、每一步完成了什么。后续母题分别深入权限、原子性、确认、顺序和恢复，不在本题悄悄改成托管账本。

共同前提采用总览：A 从 TA 向 TB 转 100 M，M 为传统 SPL Token、6 位精度，两账户已存在。初始 TA=1,000 M、TB=0，意图 I1、尝试 T1、签名 σ1，A 用额外 SOL 支付手续费 F。

## 第 1 层：完整业务究竟怎样走完

**面试官：** 从 A 点击转账开始，你会怎样解释完整流程和系统架构，而不是只说“调用一个 RPC”？

**面试者：** 我先把业务意图和链上交易分开。接入层把 I1 固定为向 TB 转 100,000,000 个 M 原子单位，验证集群、账户身份、mint 和金额；构造器读取必要状态、获取 recent blockhash H1 及其 lastValidBlockHeight，再构造 TransferChecked。A 审核并签名，服务保存完整原字节、σ1 和有效窗口后，才按自己的编排路径发送。

RPC 接收只是转发。验证者在有效执行环境中校验签名、账户权限和程序条件，成功时由 Token Program 同时减少 TA、增加 TB。跟踪器继续查询 σ1 的执行结果和确认状态；只有满足本模型的 finalized 且 err=null，才将 I1 判为最终成功。

此外还有账户同步器：它把订阅看成失效提示，读取 TA、TB、M 的同上下文 finalized 快照，原子更新本地投影，再通过带版本的查询和通知展示。最终转账成功和页面余额更新不是同一个完成点；需要分别报告进度，不能把 HTTP 返回当作业务结束。

## 第 2 层：为什么需要区分这么多状态

**面试官：** 你说链上最终成功和页面更新不同。到底谁有权改余额，为什么不在受理 I1 时就扣掉 100 M？

**面试者：** 因为这是非托管模型，平台数据库不拥有 TA 的余额写权限。链上 Token Program 在运行时约束内修改账户数据；平台只能记录用户想转什么、已经拿到什么签名、观察到了什么结果，以及当前读取的链上余额。

本地可以展示“待转 100 M”作为意图标签，但不能把它当成又一份权威扣款。受理时 TA 链上仍可能是 1,000 M；T1 可能永远不执行，也可能因余额、权限或有效窗口变化而失败。若先把本地余额改成 900 M，随后又用链快照覆盖或应用转账差额，就容易重复扣款或展示错误的可用资产。

我会把 `intentStage`、`txObservation` 和 `accountGroup` 分开存储。真正的余额来自有明确集群、commitment 和读取上下文的账户组；待处理意图只是旁边的一项业务事实。

## 第 3 层：落到具体对象和交互

**面试官：** 既然分开存储，一条 I1 记录不足以管理整个流程吗？为什么还要 T1 和 σ1？

**面试者：** I1 标识用户授权的业务目标，T1 标识一份具体构造和签名的尝试，σ1 标识可在链上查询的交易。三者不能合并，因为同一意图可能经历未签名构造失败、原字节重复发送，或者在充分排除原交易成功后创建新尝试。

I1 保存集群、A、TA、TB、M、金额和载荷摘要；T1 保存 I1、签名字节、H1、hmax 和 σ1。发送记录可以有多条，但相同字节的重发仍属于 T1，不增加一笔转账。签名观察另存 slot、err、confirmationStatus、来源和时间，保留未知与暂态。

账户组则保存共同 context、原始字节和校验后的整数，以及本地 revision。这个结构让我们在“已签但发送结果未知”时找回原尝试，也让页面明确展示“转账已最终成功、余额仍同步中”，而不是用一列 status 同时表达四种不同事实。

## 第 4 层：发送中间失败谁负责继续

**面试官：** 你说发送前保存 T1。如果数据库写完服务就崩溃，或者发送成功但没保存回执，会留下什么？

**面试者：** 数据库先保存的是完整已签尝试和待发送状态，因此崩溃后不需要重新构造转账。恢复进程读取 T1，先核验原 σ1；在允许的有效窗口内，可以按策略重发相同原字节。即使 RPC 上一次已经接收，也没有生成第二份不同签名的支出机会。

发送成功但本地回执丢失同样按未知处理。实际交易身份在发送前就能从已签交易确定，不能依赖“收到 RPC 返回值”才认识 σ1。`sendTransaction` 返回或超时只能更新发送观察，不决定最终成功或失败。

这不构成链与数据库的原子事务，解决的是本服务的恢复入口和重试身份。用户自己在钱包中已广播、服务尚未取得签名的路径还需独立接入和核验；不能据本地没有记录就断言链上没有发生。

## 第 5 层：同一笔交易失败和部分同步失败

**面试官：** 你能恢复发送，但假设链上成功了，本地先更新 TA=900 M，更新 TB 时失败，怎么补偿？再转 100 M 吗？

**面试者：** 不能再转。链上这笔普通 Token 转账已经原子完成，本地一半更新是投影事务设计错误，不是链上少转了一条腿。补一笔交易会制造第二次资产转移。

本模型用一次 getMultipleAccounts 读取固定账户组，并在同一本地事务内提交 TA、TB、M、共同 context、revision 和需要交付的 Outbox。事务失败时整组旧值保留，并标明 stale；重新读取和发布，不向链上发修页面的业务命令。

还要注意新快照可能包括其他交易：如果之后 B 又转出一部分，TB 不一定仍是 100 M。我们应展示快照时点的当前状态，用 σ1 的交易证据解释该笔转账，而不是强行把当前余额改成主例预期值。

## 第 6 层：两条证据链怎样汇合

**面试官：** 那么签名已经 finalized 成功，但你读回 TA=1,000 M、TB=0，页面到底该显示什么？

**面试者：** 先不下“链错了”或“需要重转”的结论。我检查快照是否是同一集群、同一组账户、可信 finalized 上下文，读取 slot 是否覆盖 σ1 的最终位置，以及解码和账户身份是否正确。若快照早于交易，显示最终转账成功和余额同步中，安排带最低上下文要求的重读。

如果快照确实更晚，也不能只靠两个余额判定 σ1 没执行，因为其间可能有反向转账。此时要查交易证据和后续支持范围内的历史，解释当前余额。`minContextSlot` 能防止接受明显落后的读取，但不是“读取恰好 σ1 执行后的状态”的历史定位器。

用户接口应该把 transferResult、balanceAsOf 和 freshness 分开。我们可以对它们提供清晰组合展示，却不能把不同水位的数据拼成一个声称同时成立的原子链上瞬间。

## 第 7 层：订阅断线后业务还算完成吗

**面试官：** 你要求余额追上，但订阅在 slot 520 附近断了，没有 σ1 对应的账户通知，难道一直等下去？

**面试者：** 不等某一条必达通知，因为标准账户 PubSub 没有这样的交付保证。订阅只是触发当前态刷新的一条路径；断线标 stale，重连后主动重读，周期刷新也独立存在。对固定 TA、TB、M，组读取能够把当前余额恢复到一个新的 finalized 上下文。

这可以让“当前展示”继续收敛，但不补出断线期间每一笔交易。若产品还提供逐笔历史，就需要另一条有归档覆盖和处理水位的交易扫描链路；它的缺口不能被“现在余额相等”掩盖。

所以 I1 的最终结果可由原 σ1 充分证明，不必等待通知；余额视图能否恢复由当前态读取决定；完整历史是否补齐由历史覆盖决定。这三个条件各有证据和恢复责任，不互相冒充。

## 第 8 层：怎样验证不是只会画架构图

**面试官：** 如果让你验证这套方案，最先用什么反例？为什么不是只检查最后余额等于 900 和 100？

**面试者：** 我先用“发送已经成功但回执丢失”验证恢复后只查或重发 σ1，不重新签出第二笔；再用“链上成功、本地事务提交前崩溃”验证投影可重建、不会二次扣款；最后用“断线期间两笔相反方向转账”验证系统不会用最终余额相等冒称历史完整。

主例的 900 M／100 M 只能验证没有其他业务时的金额预期。还必须检查每条对外状态都能追到原始证据、账户组同版本可见、未知不被降成失败，以及重启不丢掉已持久化的尝试。性能再好也不能替代这些约束。

在这里这些是手工推演和拟定验收场景，不是我已经运行过的链上或工程测试。若进一步落地，才把状态迁移、故障窗口和对账条件变成可执行验证。

## 本题收束

- **讲透的机制：** 意图／尝试／交易身份分层；链上执行与本地投影双证据链；原子组发布和独立恢复责任。
- **最易答错：** 非托管模型先扣平台余额、把 RPC 返回当成功、用补转修复页面、用当前余额证明逐笔历史。
- **检验反例：** σ1 已执行但服务重启后不知道发送回执，方案是否会产生第二个不同签名的普通转账？若会，恢复闭环尚未成立。
