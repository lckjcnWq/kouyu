# 大问题 10：怎样从 Solana 交易、执行 meta 和账户快照中证明一笔转账，而不误判因果？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| I1、T1、σ1、σx | 业务目标、已签尝试、原交易与相似外部交易的签名代号 | 同方向同金额的 σx 不能自动替换 I1 绑定的 σ1 |
| TA、TB、M、A、B | 源与目标代币账户、币种和双方用户 | 交易归因必须对上真实程序、账户和授权关系 |
| signed bytes、H1 | 已签完整字节和被签的近期区块哈希 | 核对完整授权内容，不能只找到一条金额相符的指令 |
| finalized、confirmationStatus、err | 最终性等级、确认状态和执行错误 | 最终业务成功要有同一份可靠结果的 finalized 且无错误 |
| SPL Token、Transfer、TransferChecked | 标准代币体系、普通转账与带精度检查的转账 | Transfer 本身不带 mint、精度，不能混用两种指令字段 |
| mint、decimals、原子整数 | 币种定义、小数位和最小单位数量 | 六位精度的 100 M 是 100,000,000，不用显示浮点数核算 |
| legacy、v0、maxSupportedTransactionVersion | 两种消息格式和查询可接受版本参数 | 未支持版本要隔离，不能返回空账户或空指令冒充无业务 |
| ALT、静态键、loaded addresses | 地址查找表、直接列出的地址和实际加载地址 | 按消息格式还原有效键序列，不能拿当前表随意替代历史证据 |
| programIdIndex、accountIndex、parsed | 程序索引、账户位置和已解析响应编码 | 先正确映射；已展开的键不能再追加加载地址造成错位 |
| meta、inner instructions、CPI | 执行资料、内部指令和程序间调用 | 识别真实调用及整体结果，内部执行轨迹不等于最终提交 |
| 指令路径、日志字符串 | 调用的稳定位置和程序打印的文本 | 路径区分同交易多次转账，文本不能替代真实程序语义 |
| preTokenBalances、postTokenBalances | 交易前后代币余额记录 | 按 accountIndex 和币种配对，不按数组同位置直接相减 |
| uiAmount、缺失字段 | 显示用浮点金额和未提供的记录 | 浮点不用于记账，记录缺失不是金额零 |
| 净额、逐次写入 | 整笔交易前后差与每一步内部修改 | 前后余额只给净效果，不能恢复所有中间写入镜像 |
| fee payer、SOL、meta.fee、F、lamports | 付费人、原生币、实际费用字段、费用符号和最小单位 | F 属于交易费用，不从 M 扣；缺资料是未知，不是零 |
| getMultipleAccounts、context、revision | 共同账户读取、求值上下文和本地发布版 | 证明所读当前态，不替代 σ1 当时的执行前后证据 |
| PubSub、dirty、stale | 订阅通知、待刷新和陈旧状态 | 通知只促使重读，不靠同 slot 和相反金额拼交易因果 |
| lastValidBlockHeight、Unknown、unique(I1) | 最后有效区块高度、结果未知和本地唯一约束 | 过期与空查询不排除过去成功，本地唯一也不阻止新签名再转 |

## 把整篇文章压缩成一个故事

A 想从 TA 给 TB 转 100 M，服务保存 I1 对应 T1 的签名字节、σ1、H1 和完整授权参数。后来余额恰好从 1,000 M／0 变成 900 M／100 M，也不能直接认定是 σ1：A 可能另发了一笔同金额交易。解析器必须查到原 σ1 的可靠最终结果，核对传统 Token Program、两端账户、权限、100,000,000 原子单位和附加指令，而不是用余额对上就认领。

解析 v0 交易时先还原静态键与实际加载地址，正确映射程序、指令和余额索引；看到内部转账日志时还要核验真实指令与整笔执行错误。若后一条指令失败，日志中的转账不产生已提交业务效果，费用仍可能存在。交易前后代币余额按账户索引配对，主例差额为 TA 减 100,000,000、TB 加 100,000,000，合计零；手续费 F 单取 meta.fee，不能混入 M，也不能把缺失字段当零。

一个独立后续变体中，B 再返还 50 M，当前组快照就会是 TA=950 M、TB=50 M，并不推翻 σ1 原本转了 100 M。该笔结果由交易证据说明，当前态由共同快照说明，中间路径由覆盖充分的历史说明；即使 slot 相同也不能跳过这些区分。若只找到相似的 σx 而原 σ1 仍未知，就保留关联未明，不能自动取消原交易、认领替代签名或重签补转。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖“已签名交易识别 → 最终执行结果 → 指令与账户索引解析 → 数量和手续费核验 → 业务归因 → 当前投影对照”。核心是区分请求内容、执行事实和当前状态：有转账指令不等于执行成功，净额匹配不等于归属于某个 intent，账户更新通知也不是交易因果事件。

**固定案例：** 单一 Solana 集群，非托管，传统 SPL Token 程序的普通 mint M，decimals=6。A 控制 TA，初始 1,000 M，即 1,000,000,000 原子单位；B 控制 TB，初始 0。意图 I1 对应 attempt T1/σ1，recent blockhash 为 H1，保存对应 lastValidBlockHeight；计划转账 100 M=100,000,000 原子单位。隔离成功后 TA=900,000,000、TB=100,000,000。A 另由系统账户承担实际链上 `meta.fee=F` lamports，无协议费。两 token 账户已存在，不创建 ATA、不改变租金，不涉及 Token-2022、WSOL、跨链、durable nonce 或自定义幂等程序。意图与已签名 attempt 先持久再由服务发送，但用户钱包可能自行广播，服务不能承诺约束所有外部交易。

## 第 1 层：余额刚好变化 100 M，能证明 I1 成功吗？

**面试官：** TA 从 1,000 M 变成 900 M，TB 从 0 变成 100 M，金额完全匹配。为什么不能直接完成 I1？你需要哪几份证据？

**面试者：** 因为余额变化只提供状态关系，不提供唯一交易身份。A 可能在钱包里独立发起另一笔相同金额转账，或者多笔交易合成相同净额；没有 σ1 的证据，不能把变化归到 I1。

我会先从持久化记录确认 I1 对应的 T1、σ1、signed bytes、H1、源和目标账户、数量，再取得 σ1 的最终状态及交易 meta。只有可信 finalized 结果且 `err=null`，交易内容又与已授权的目标操作匹配，才可以完成 I1。processed 或 confirmed 只能作为可撤销预览，不能作为最终业务成功。

账户状态走另一条链：PubSub 只标 dirty，TA、TB、M 通过一次 finalized `getMultipleAccounts` 获取共同快照，校验后原子发布 revision。它可验证当前余额是否合理，却不负责证明 σ1 的身份。交易已成功而当前余额又被后续交易改变，是允许的，不应因此把 I1 改回失败。

## 第 2 层：怎样确认解析到的交易就是当初授权的 T1？

**面试官：** 你要查询 σ1，但 RPC 返回的交易里确实存在一条转 100 M 的指令。只比对金额是否就够了？

**面试者：** 不够。要核对集群身份、交易签名与持久化 attempt 的关联，并核对被签名消息的完整语义：program ID、源账户 TA、目标账户 TB、授权主体、原子数量、recent blockhash H1，以及任何附加指令。不能找到一条金额匹配的指令就忽略交易里其他改变资金或权限的动作。

标准 SPL Token 的 `Transfer` 指令本身不携带 mint 和 decimals，M 来自 token 账户关系和相关元数据，不能仅凭这条指令的数据解码出 M。若明确使用的是同一传统 Token Program 的 `TransferChecked`，它会额外携带 mint 和 decimals 校验，但也不能跳过源目标身份、签名权限与程序校验。不能把两种指令的字段格式混着解。

本模型预期的是既定普通转账，不把看到的任意自定义程序调用当作等价业务。消息不匹配应暂停自动归因，保留实际链上结果与业务预期冲突的证据，而不是因为数量相同就改写原 intent。服务恢复不到原签名关联时，也不能自动认领钱包的相似交易。

## 第 3 层：版本化交易中的账户索引怎样正确映射？

**面试官：** 你强调 program 和账户身份，但现在返回的是 v0 交易，指令里的源、目标只有账户索引，TA 通过地址查找表加载。你怎样防止把别的账户当成 TA？

**面试者：** 首先显式声明解析器支持的交易版本，例如支持 legacy 与 v0 时设置相应的 `maxSupportedTransactionVersion`，遇到超出范围的版本明确记为不支持，不能用空指令或空账户集合代替。

使用原始 JSON 结构时，v0 指令使用的有效账户键序列需要结合静态 account keys、加载的 writable 地址和加载的 readonly 地址，按协议规定顺序构造。随后 programIdIndex、指令账户索引、token balance 的 accountIndex 和 lamport balance 数组都要映射到相应的有效账户位置，并校验越界或缺失信息。

如果使用已展开账户键的 parsed 编码，要按其返回契约处理，不能再次追加 loaded addresses 导致索引整体错位。还应分清响应里实际可获得哪些字段；缺少重建所需地址时保持不可解析，而不是拿当前地址查找表随便替代交易执行时使用的地址。只有键映射可靠，后续判断“这是 TA、那是 TB”才有依据。

## 第 4 层：顶层指令没有 transfer，日志里却说转账成功，如何判断？

**面试官：** 你把账户索引还原了。假设顶层只有某程序调用，日志打印了 Transfer，内部调用里也有 Token Program 指令。能否据此完成 I1？

**面试者：** 不能只信日志字符串。任意程序可以打印看似熟悉的业务文本，日志中的“成功”也不等于整笔交易最终成功。需要识别真实 program ID，解析实际顶层或 inner instruction，并结合最终 `meta.err` 判断整笔原子交易是否成功提交。

如果讨论 CPI，应明确这是改变调用路径后的对比，不是把本题的普通直接转账悄悄替换成任意程序协议。解析受支持的内部转账时，要保留顶层指令索引、内部指令路径及可用的调用层级信息，以区分一笔交易里的多次转账；但这些信息仍不是每一次账户原始写的快照。

如果一笔交易先执行了转账指令，后面的指令失败，整体最终 `err` 非空，业务状态变更回滚，不能因为日志中出现过 Transfer 就记成成功的 100 M。交易失败仍可能收手续费。因果判断需要“真实指令语义＋整体最终结果”，而不是“出现过某个字符串”。

## 第 5 层：pre/postTokenBalances 怎样核验金额，又有哪些信息缺口？

**面试官：** 你说要结合最终 meta。现在有 `preTokenBalances`、`postTokenBalances`，是否直接把两数组同一位置相减，就可以验证所有转账？

**面试者：** 不能按数组位置直接配对。先通过每条记录的 `accountIndex` 映射到有效账户键，再核对 mint、可用的程序与 owner 信息，将 TA、TB 的交易前后状态对应起来。原子金额使用字符串表示的整数值，不用 `uiAmount` 浮点数做账；decimals 必须与 M 的 6 一致。

在本题仅有这一笔普通转账的成功交易中，TA 应为 1,000,000,000→900,000,000，TB 为 0→100,000,000，差额分别为 -100,000,000 与 +100,000,000，二者合计为零。这个等式核验 token 数量守恒，不把 F lamports 混进来。

但某些历史响应可能缺失 token balance 记录，字段缺失不代表余额零；两个账户本来就存在，也不能看到记录缺失便推断创建或关闭。一笔复杂交易可以对同一账户多次操作，pre/post 只给交易级净效果，不能恢复每个内部步骤。缺少必要信息时标记证据不完整，保留待补，不能用现在读取到的余额冒充这笔交易当时的 pre/post。

## 第 6 层：怎样把 token 数量和手续费准确放进同一笔结果？

**面试官：** 你验证了 token 守恒，但 A 的资产确实还少了手续费。F 怎样确定？失败时手续费和转账金额又怎样分别处理？

**面试者：** F 来自这笔交易实际链上 `meta.fee`，单位是 lamports。消息中的 fee payer 应与 A 的系统账户对应，通常就是有效账户键序列的首个静态签名账户；解析时应基于消息格式核验，而不是把 token owner 或源 token 账户误当作 fee payer。

在本题没有 ATA 创建、没有租金变化、没有额外系统转账或其他 lamport 变动的限制下，fee payer 的交易前后 lamports 差额可用来与 F 交叉核验。但权威费用仍是 meta.fee，不从固定费率估算后当作实际值，也不从 M 的数量差中扣除。成功时 TA、TB 按原子数量转移，A 系统账户另外付 F，无协议费。

若交易 finalized 且 `err!=null`，不能把预期 100 M 记成已转移；失败业务指令的状态修改回滚，但已纳入链的失败交易仍可能支付 F。`confirmationStatus` 决定最终程度，`err` 决定执行成败，meta.fee 记录实际成本，三个维度要分别保存。meta 缺失时费用是未知，不等于零。

## 第 7 层：交易成功与当前投影不匹配时，应该相信谁？

**面试官：** 你已经找到 σ1 的 finalized 成功记录，pre/post 也完全匹配。但稍后共同快照显示 TA=950 M、TB=50 M。是不是交易解析错了，需要回滚 I1？

**面试者：** 不应立刻回滚。先比较证据所描述的时间与对象：交易 pre/post 是 σ1 执行前后的局部事实，当前共同快照是某个更晚最终上下文的状态。slot 即使相同，也可能有其他交易，不能凭 slot 相等就断言两者应相等。

在一个独立变体中，I1 成功后 B 又从 TB 向 TA 返还 50 M，就会得到 TA=950 M、TB=50 M。它不否定 I1 的成功，更不允许把余额“修正”回 900 M 和 100 M。相反，如果当前读的上下文早于所需最终范围，就应保留滞后或 stale 标记并重读，不把旧快照当作矛盾证明。

若业务需要解释中间变化，必须读取有明确覆盖的最终区块交易与 meta；历史覆盖不足就承认原因未明。标准账户通知没有 signature，也没有完整写序，不能拿两条变化消息强行拼成解释。交易证据裁决 I1，快照链发布当前态，历史链解释中间支持范围内的业务，它们各有职责。

## 第 8 层：怎样避免把相似外部交易误认成 I1，又避免重复补单？

**面试官：** 你允许后续交易改变余额。现在 σ1 查不到，但链上有另一笔 σx，转账方向和金额都与 I1 一样，最终余额也符合预期。能否把 σx 绑定给 I1，然后把重复的 σ1 取消？

**面试者：** 不能自动这样处理。相同金额和方向不提供业务身份，σx 可能是用户独立发起的另一笔交易。应先核对 σx 的签名消息是否就是已持久化的 T1，以及钱包侧是否有可验证的授权和 attempt 关联；若只是相似，最多记录一笔已识别的外部转账，不能替换 I1 的 σ1。

也不存在通用的“取消 σ1”接口。应用取消等待不撤销签名；更新 H1 重签会产生另一笔可执行转账，DB unique(I1) 不能让传统 Token Program 拒绝第二笔。即使最终 block height 已超过保存的 lastValidBlockHeight，也只关闭未来窗口，不能证明 σ1 过去没成功；历史查询 null 仍取决于覆盖能力。

因此 I1 保持 Unknown，直到取得足够最终证据排除或确认原成功。σx 是否另行关联需要明确业务核实，不能依靠金额模糊匹配自行完成。当前余额可以准确、外部交易可以确定、I1 仍然未知，这不是数据模型失败，而是诚实保留不同证据链之间尚未证明的关系。

## 收束：机制、易错边界与反例验证

- **讲透的机制：** 从持久化 attempt 锁定交易身份，正确解析版本与账户索引，再结合真实指令、最终执行 meta、token 整数差额和实际 fee 建立限定范围内的业务因果；当前投影独立维护。
- **最易错的边界：** `Transfer` 不自带 mint 与 decimals；v0 加载地址不能漏拼或重复拼；日志和指令存在不等于最终成功；token balance 记录缺失不是零；交易级 pre/post 不等于逐次内部写；F 是 lamports，不是 M。
- **反例验证：** 手工推演两例：其一“转账日志已出现，但后续指令使整笔 finalized 失败”，不能记成功转账，却应保留实际费用；其二“σ1 未知，σx 同方向同金额且余额吻合”，不能自动认领 σx，也不能重签补单。若方案仅靠净额或者日志完成 I1，就没有建立可验证的因果链。不声称已经通过工程或生产测试。
