# 大问题 13：多 RPC 怎样核验同一事实，并在故障切换时保持一致性？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| RPC-P／Q／R、HTTP 200 | 不同节点接口代号和请求层成功响应 | 返回快或通信成功不证明业务结果可信，也不证明后端独立 |
| genesis hash、集群身份 | 网络起源标识与目标链网络 | 防止把不同集群的相同格式地址和签名混为同一业务 |
| I1、T1、σ1、signed bytes | 意图、尝试、签名和已签完整字节 | 换发送源不换交易身份，原字节重发仍是 σ1 |
| TA、TB、M、F | 账户、币种和实际费用代号 | 100 M 业务金额与 A 额外付的 SOL 费用分开 |
| commitment、processed、confirmed、finalized | 稳定性要求及三个确认层级 | 预览与最终结果分别处理，不能把多源投票当链上共识 |
| err、confirmationStatus、meta | 执行错误、确认状态和执行资料 | 核验同一结果的成败、最终性与费用，不能拼各源字段 |
| null、历史搜索、Unknown | 查询没给状态、扩展查询范围和结果未明 | 空值受缓存及历史保留限制，不自动反对已有最终证据 |
| H1、lastValidBlockHeight、block height | 近期哈希、最后有效区块高度和实际区块进度 | 超过有效高度只关未来，不排除过去成功；不能用 slot 比 |
| getMultipleAccounts、context、Bank | 一次组读取、求值上下文和节点状态视图 | 整组切源读取 TA、TB、M，不拼 P 的 TA 与 Q 的 TB |
| minContextSlot、slot | 最低求值上下文门槛和出块机会编号 | slot 可能无块；门槛不是指定历史状态，更大数字也不是真实性证明 |
| owner、mint、authority、decimals | 所属程序、币种、业务权限和小数位 | 组快照仍须核验传统 Token Program、M、控制关系和六位精度 |
| source epoch、round、revision | 来源世代、读取轮次和本地发布版 | 旧来源或旧轮次无权写新版本，即使其 slot 更大 |
| owner fence、复制耐久 | 持久写者围栏和接管所需的数据复制边界 | 旧进程不得提交本地结果，但围栏不能召回已广播签名 |
| PubSub、dirty、stale、projection pending | 订阅提示、待刷新、陈旧和投影待更新 | 切换自身就使组失效并触发重读，不靠旧连接最后一条消息 |
| Geyser、write_version、root、delta | 增强采集、来源写版本、扎根标记和增量数据 | 排序、快照衔接、分支撤回与跨源可比性都须另验契约 |
| raw、checkpoint、W、容量预算 | 原始证据、持久检查点、连续历史水位和资源上限 | 历史能力不足就留洞，不能丢未应用证据后推进水位 |
| 退避、抖动、重试预算 | 重试逐渐放慢、随机错峰和总资源限制 | 避免故障源被重试压垮，保留可信旧值并明确陈旧 |
| 最终性冲突、Outbox | 最终事实矛盾与本地待交付记录 | 隔离留证，不自动覆盖终态、删除通知或补转来恢复表面可用 |

## 把整篇文章压缩成一个故事

A 的 100 M 转账由服务保存为 I1、T1、σ1，再发给 RPC-P。P 超时，备用 Q 查不到结果，服务先核验 Q 的集群与所需能力，不把空值当失败；有效窗口内若改由 Q 发送，也只发原始已签字节。即使可信最终区块高度已超过 H1 的有效高度，仍须查明 σ1 过去是否成功，不能为了“切换可用”自动重签第二笔。

账户同步也整组切到 Q：一次 finalized 读取 TA、TB、M，核验身份与上下文下限，不拼 P 返回的 TA 和 Q 返回的 TB。Q 较晚快照若已包含额外 20 M 转账，就可能是 880 M／120 M，而 P 较早是 900 M／100 M；这首先是不同位置的数据，不是投票选余额。切换使旧来源世代失效，P 后来即使返回更高 slot 也无权覆盖。Q 落后或历史源缺失时，用有界重试和陈旧标记降级，不降低最终性门槛制造新鲜感。

最终 σ1 只按完整可信证据记录一次 100 M 结果和自身费用 F，当前余额则按整组实际快照发布，历史能力与当前态能力分别验收。多个网址未必独立，增强流的写版本也未必跨源可比；同一已核验最终事实若真的互相矛盾，就暂停相关发布、水位和不可逆交付并留证核验，而不是择快、择新或多数表决。安全切换保留不确定性，不替未知交易生成新的执行机会。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖“服务发送、签名核验、账户组重读与历史补查”各阶段的数据源选择。重点是数据源可信度、确认等级、共同读取上下文、source epoch 和切换围栏，而不是通过更多 RPC 投票创造最终性。

**讨论基线：** 单一 Solana 集群、非托管、传统 SPL Token 程序普通 mint M，decimals=6。A 控制 TA，初始 1,000 M=1,000,000,000 原子单位；B 控制 TB，初始 0。两账户已存在，不创建 ATA，不涉及租金变化。业务 I1 的 attempt T1/σ1 使用 H1，持久保存 lastValidBlockHeight，转移 100 M=100,000,000 原子单位。无后续交易时，成功后 TA=900,000,000、TB=100,000,000；A 的额外系统账户支付实际 `meta.fee=F` lamports，无协议费。排除 Token-2022、WSOL、跨链、自定义幂等程序、durable nonce。服务约束自身编排，但用户可自行广播签名交易。

## 第 1 层：接入两个 RPC 就能自动获得高可用和可信结果吗？

**面试官：** 为这笔转账接入 RPC-P 和 RPC-Q，谁先返回就用谁，失败就切到另一个，是否已经同时解决可用性和结果可信问题？

**面试者：** 没有。可用性、时效性、历史覆盖和可信性是不同维度。响应更快只说明这个调用更快结束，不能说明它属于正确集群、使用正确 commitment、具备所需历史，也不能说明两个供应商背后没有共享同一基础设施。

我会先验证配置的集群身份，例如核对预期 genesis hash，禁止把另一个集群的同名 mint 或同格式签名混进来。每份重要证据同时保存来源、方法参数、请求轮次、观察时间、context 或交易 slot、确认等级、原始响应指纹；对历史接口还记录供应商承诺的保留范围。运行时探测区分网络连通、finalized 进度、限流、历史可用性和错误类型，不能一个 HTTP 200 就算健康。

两条业务证据链仍独立：σ1 的状态和交易元数据决定它是否最终成功，TA/TB/M 的共同 finalized 快照决定当前账户投影。RPC 切换不能把这两种证据揉成一项，也不能直接把任意通知的余额写进本地权威组。

多源交叉检查有助于发现滞后、错误配置和数据异常，但少量普通 RPC 的多数意见不是 Solana 共识。我们是在明确的集群最终性与数据源信任假设下读证据，不是用“三个节点有两个这么说”建立一个新的链上裁决层。

## 第 2 层：三个不同状态，是冲突还是观察进度不同？

**面试官：** 你保留来源和确认等级。现在 P 返回 σ1 为 confirmed 且 err=null，Q 返回 null，R 返回 finalized 且 err 非空。能不能按两个“不成功”对一个“成功”来判失败？

**面试者：** 不能这样计票，这三项根本不是同一种事实。P 给出的是可撤销的执行成功预览；Q 没给出状态对象，不能推出失败；R 如果来自经过核验的可信源，给出的是已经最终化的执行失败。`err` 与 `confirmationStatus` 必须独立读取，finalized 并不自动意味着成功。

我会保留 P 的预览历史，不让较早或较低确认等级的返回覆盖最终记录；对 R 再取相应 finalized 交易及 meta，核对 σ1、消息内容和错误语义，并通过其他具备历史能力的可信源复核重要终态。如果证据支持 finalized 失败，则 I1/T1 最终失败，原定 100 M 不转移，但仍记录 A 支付的实际 F lamports。不能因为看到失败就声称费用为零。

Q 的 null 要按查询能力解释：`getSignatureStatuses` 默认只搜索近期状态缓存，历史搜索需要明确启用，启用后也受节点数据保留影响。它不构成反对 R 的最终性证据。`getTransaction` 在指定确认等级下查不到，也不能直接转换成失败。

如果出现两个来源对同一 σ1 给出相互矛盾的 finalized 执行结果，就不是这个普通预览差异场景。我会停止自动终态推进和相关交付，转入信任事故核验，而不是随便挑一个响应或回滚已发布结果来维持表面可用。

## 第 3 层：发送故障切换会不会把一笔转账变成两笔？

**面试官：** 你不按 null 判失败。但 P 的发送请求超时，Q 说 H1 已过期，P 又暂时连不上。切到 Q 时，是继续发原字节，还是换 blockhash 重签以保证可达？

**面试者：** 切换传输通道不应该自动改变交易身份。I1、T1、σ1、H1、lastValidBlockHeight 和 signed bytes 在服务首次发送前就要持久化。向 P 超时后，向 Q 发送完全相同的 signed bytes，仍然是原 σ1；不能让 RPC SDK 的某个重试封装悄悄重新构造和重签消息。

如果已取得足够新且可信的 finalized block height，确认超过 lastValidBlockHeight，那么原交易未来的有效接纳窗口已关闭，继续广播通常不再有价值。但这个结论与 σ1 过去是否成功是两件事，不能用 Q 的过期错误覆盖历史结果；尤其不能把 Q 的 slot 与有效区块高度比较。节点滞后和预检错误也不等同于 finalized 交易执行失败。

我会继续查 σ1 的历史状态、finalized 交易或所需最终区块范围；尚未查清时保留 Unknown，不自动重签。换 blockhash 就会产生新签名，普通 SPL Token 程序无法识别业务 I1，两份不同签名可能各转一次 100 M。本地 I1 唯一键只能避免本服务某些并发编排，不能约束链上，也不能约束用户在钱包外部发送。

发送响应若返回签名，还应与本地 signed bytes 对应的 σ1 核对。发送成功或预检通过不是 finalized 成功，ctx 超时或取消也不会撤回已提交到网络的交易。服务的可用性目标必须服从“不凭不确定结果重复转账”的安全边界。

## 第 4 层：切换账户读取源，怎样防止拼出不存在的余额组？

**面试官：** 你保住了 σ1。账户查询方面，P 能返回 TA，Q 能返回 TB；各自都说 finalized，而且 slot 很接近。为了尽快恢复页面，能不能拼起来发布？

**面试者：** 不能。slot 很接近不等于同一 Bank，跨源同一个 slot 数字本身也不足以证明源可信和数据相同。本题固定 TA、TB、M 很小，我会把整个组重读切到 Q，要求由一次 finalized `getMultipleAccounts` 返回共同 context 的完整组，任何一项缺失或校验失败都不发布半组。

读取下限至少参考已接受组快照的 context；若要发布 σ1 成功关联视图，还要不早于它的 finalized 执行 slot。可以设置 `minContextSlot` 并显式验证响应下限，但这不是“读取恰好那个 slot”的请求，Q 可以返回更高上下文。如果 Q 尚未达到下限，应等待、换合格来源或暴露 stale，不能为了得到结果就把下限悄悄降低。

每组都核对外层传统 Token 程序 owner、TA/TB 的 mint 与授权关系、M 的 mint 布局和 decimals=6，按整数保存余额。context.slot 表示读取上下文，不是 TA 或 TB 的最后修改时间，更不能作为转账事件序号。

多源复核时要比较相同口径的关键字段和账户字节语义，避免因 encoding、JSON 展示格式或非业务字段差异误报。P 在较早上下文返回 900 M/100 M，Q 在较晚上下文返回 880 M/120 M，可能只意味着期间又转了 20 M，不是自动认定 finalized 冲突；也不能把这个较晚快照的 120 M 全归因 σ1。若确需比较同一 Bank 的内容，必须取得相应链身份依据和来源契约，不能用 `minContextSlot` 假装已经固定了 Bank。

## 第 5 层：切换以后旧源的迟到结果怎样处理？

**面试官：** 你把整组切到 Q。问题是 P 的旧请求后来成功返回，slot 甚至比 Q 刚提交的更高；同时旧 WebSocket 还在回调。能不能见 slot 更高就接受？

**面试者：** 不能只看 slot。源已被隔离或读取轮次已失效时，更高数字也不能重新获得写权。我会为每次来源会话分配 source epoch，为每个组刷新分配 round，并由单 owner 串行决定当前有效读取、组 revision 和数据源切换。

切换动作先使旧 epoch 失效，取消旧请求和订阅作为资源回收手段，但不依赖取消必然及时生效。RPC 结果和通知封装中携带 epoch；迟到结果只有在仍属于有效 epoch、有效 round、预期 revision 且校验通过时才可能提交。旧 P 的值即使 slot 更高也不能覆盖 Q 的当前结果。HTTP 超时后若开始新逻辑轮次，旧请求返回同样要被围栏拦住。

通知仍只是 dirty 提示，不直接落余额。旧连接的迟到提示可以丢弃，但切换本身必须无条件把整个组标记 stale/dirty 并触发 finalized 重读，保证丢弃旧源消息不会消灭刷新义务。对于当前有效源，读期间新提示增加 dirty 代数，返回时不能把新的代数清掉，必要时继续下一轮串行读取。

source epoch 是数据来源会话的围栏，进程接管的 owner fence 是另一个层次；二者都要落到提交检查，而不只是内存布尔值。多副本时，新 owner 未达到所承诺的复制耐久位置不能盲目接管；旧 owner 即使还运行，也应失去本地写入和发布资格。它已经发往链上的 σ1 则仍然可能生效，不能被围栏“撤销”。

## 第 6 层：换成 Geyser 数据源，能不能获得统一的写序？

**面试官：** 你担心旧通知乱序。供应商说 Geyser 带 slot 和 write_version，所以切换时直接按这两个字段排序，是否就能替代 finalized 组重读与 source epoch？

**面试者：** 不能把某个供应商提供的字段，当成跨服务、跨重启、跨节点都可比较的协议标准。先要验证这条流的服务契约：write_version 在什么进程或节点作用域内分配、是否重启重置、启动快照与实时消息如何衔接、fork 与 root 如何表达、是否关联交易、是否支持重放、序列缺口如何暴露，以及切换节点后作用域是否改变。

slot 也不是 slot 内每次写的全局顺序。同一个 slot 可能有多次账户写入；没有额外且已验证的序列契约，不能仅按 slot 去重，也不能把 slot 相同的 TA、TB 更新拼成原子组。即使在某个已验证源 epoch 内 write_version 可用于排序，也不能拿源 P 的 900 和源 Q 的 850 比较谁更新，更不能把应用自己的 source epoch 与供应商的序号混为一谈。

本题的标准 RPC 基线仍是账户通知失效提示、串行 finalized 共同读取和周期刷新。要将某条 Geyser 流升级为权威增量通道，需要明确改变并验证数据源契约，补齐快照加 delta 的无缝边界、重放持久性、分支最终化和跨账户组原子发布，而不是仅凭“有 write_version”替换所有机制。

历史业务也不能顺带假设完整。如果供应商只提供实时账户变化，不保证离线重放和交易语义，它仍不能补全离线期间 σ1 的历史记录。此时继续用独立归档和最终区块范围覆盖水位恢复支持的 transfer 历史，不把账户写流冒充任意业务档案。

## 第 7 层：所有来源都不理想，怎样降级而不制造假实时？

**面试官：** 你保留了严格下限和完整组读取。但现在 Q 落后、P 限流、历史源暂时不可用，队列持续增长。是不是只能无限重试，或者放松 finalized 来保证可用？

**面试者：** 既不能无限积压，也不能悄悄降低承诺。我会按故障类型和业务路径做有界降级：账户通知合并为组级 dirty，限制待处理字节、队列长度、并发请求和重试预算；超时采用有上限的退避与抖动，避免多副本同时向故障源重试。历史抓取达到容量上限时停止扩展新范围，不丢未应用 raw 后继续推进 checkpoint。

当前投影保留最后一次可信 finalized revision，同时明确 stale、最后成功读取的 context 和观察时间。观察时间只是服务知道这份快照的时间，不是账户最后修改时间。processed/confirmed 若作为可撤销预览展示，必须与最终投影分栏，不能伪装成降级后的同等终态。若签名已最终成功而投影未追上，查询返回 projection pending，而不是拼接旧余额宣布全部完成。

签名 Unknown 查询、当前组刷新、历史补查可以有不同的预算和优先级，但不共享一个含糊的“RPC 健康”布尔值。当前态可刷新不意味着历史源合格，历史源有旧数据也不意味着它能提供足够新的共同快照。raw 存储同样有容量与复制耐久要求，不是无限缓冲器。

我会测量每个来源各方法的延迟分布、错误类型、可用 finalized 上下文、限流率，以及应用的最老 dirty 年龄、历史缺口年龄、raw 积压字节和本地提交延迟。根据实际数据调并发和批量，不虚构多接一个 RPC 就能提升多少吞吐，也不把更快返回的错误统计成延迟优化成果。

## 第 8 层：真正的 finalized 冲突，能否靠自动切源修复？

**面试官：** 你允许 stale，也不轻易放松终态。现在两个已经核验集群的来源，对同一 σ1 返回相反的 finalized 结果。业务已向下游发布成功；如果选择“最新来源”覆盖，是否能让系统继续前进？

**面试者：** 不能把这个场景当成普通故障切换。我要先冻结相关终态改写、历史 W 推进和不可逆交付，保存两侧原始响应、请求参数、签名消息、交易与块身份、来源会话及时间，核验是否存在请求错配、缓存污染、集群配置错误、代理篡改或供应商错误。必要时引入独立可信来源或自有验证基础设施进行事故核验，但不把简单多数当成最终性证明。

如果确认只是较低确认等级预览与 finalized 的差异，按预览撤销规则处理；如果确实是相互矛盾的 finalized 证据，就升级为信任或最终性事故。已发布历史不能自动常规回滚，不能自动补转 100 M，也不能把原 Outbox 删除后当作从没发生。恢复发布必须建立在明确的可信链与证据裁决上，并有业务影响核查和审计记录。

验收切换机制时，我会先构造不应报事故的情况：P 较早快照是 900 M/100 M，Q 较晚快照含后续 20 M 为 880 M/120 M；应接受上下文差异，而非回滚。再构造必须阻断的情况：同一最终交易证据的 err 相反、同一已核验 Bank 的关键账户内容相反、旧 epoch 的迟到结果试图写新 revision；前两者保全证据并隔离，后者直接拒绝提交。

这样切换的安全性来自“哪些事实可以比较、哪些返回有写权、哪些异常必须停”，而不是永远能找到一个 RPC 给出想要的答案。业务可用性的底线是诚实表达不确定和陈旧，不是用来源切换抹掉不确定。

### 机制收束

多 RPC 用于受控的可用性替代与证据复核。集群身份、确认等级、历史能力、完整组上下文、source epoch 和 owner 围栏共同定义接受条件；相同 signed bytes 保持交易身份，账户组切换必须整组重读。

### 易错边界

多个供应商不等于独立信任；null 不等于失败；err 与 confirmationStatus 不互相替代；minContextSlot 不是指定 Bank；slot 不是账户写序；Geyser/write_version 的跨源可比性必须验证；切换不能自动重签，也不能自动回滚 finalized 历史。

### 反例验证

让 P 发送超时、Q 返回 null、旧 P 的更高 slot 结果迟到，同时 Q 的新快照已包含后续 20 M。正确系统仍围绕 σ1 查证，拒绝旧 epoch 覆盖，不拼账户、不重复转账；真正矛盾的 finalized 结果则触发事故隔离，而不是“择快择新”。
