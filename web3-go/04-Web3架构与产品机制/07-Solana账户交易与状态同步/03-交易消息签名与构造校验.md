# 大问题 3：怎样构造一笔用户真正同意的 Solana 交易？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| I1、TA、TB、M、A | 意图、源账户、目标账户、币种及授权人代号 | 固定为 A 从 TA 向已存在的 TB 转 100 M |
| SPL Token、mint、decimals | 标准代币体系、币种定义和小数位数 | 用传统 Token Program，六位精度下金额为 100,000,000 原子单位 |
| TransferChecked | 带精度核验的转账指令 | 不能在签名之后悄悄改接收账户或追加创建账户动作 |
| 消息、序列化、σ1、T1 | 待授权内容、其字节表示、签名标识和尝试记录 | 签名对应确切消息；发送器只发送保存的已签字节 |
| fee payer、required signer | 付手续费的人和消息要求的签名者 | A 在主例兼任付款方与转账授权方；签名数量正确不等于身份正确 |
| recent blockhash、H1、hmax | 近期区块哈希、其代号和最后有效区块高度 | H1 是被签内容；更换它须重签，并产生新的交易机会 |
| signer、writable、readonly | 签名权限、可写和只读权限 | TA、TB 按需可写，M 只用于校验；权限不是地址可信就能扩大 |
| CPI | 程序间调用 | 下游不能随意把只读账户改成可写，也不能凭空获得签名权限 |
| RPC、preflight | 节点接口和发送前预检查 | 不得替用户改消息；关闭预检查也绕不过实际执行规则 |
| 模拟、replace blockhash | 某状态下试执行，以及模拟时替换哈希的选项 | 模拟不锁资；替换哈希的试跑不证明原签名交易仍有效 |
| compute unit、limit、price | 计算资源单位、请求上限和单价 | 预算过小会失败，调大上限或优先费也不保证被包含 |
| SOL、lamports、micro-lamports、F | 原生币、费用单位、其百万分之一和实际费用符号 | 单价单位不能混用，实际手续费以 meta.fee 记录 |
| legacy、v0 | 传统消息和版本 0 消息格式 | 简单主例用 legacy；不能把未知版本勉强按旧格式读 |
| ALT | 地址查找表 | 缩减消息直接携带地址的负担，不取消计算、大小与权限限制 |
| 静态键、lookup 地址、账户索引 | 消息直接列出的地址、表加载地址和指令引用位置 | 签名者在静态键中；完整键表须按规定顺序还原，不能排序后解码 |
| meta、resolved addresses | 执行附带资料和已解析的加载地址 | 历史解析优先保留当时实际加载证据，不能用今天的表冒充当时 |
| SDK、schema、解码隔离 | 开发工具包、指令结构约定和暂不采用未知数据的处理 | 不支持的版本留原始数据待升级，不能产出猜测的成功记录 |
| 历史水位、血缘 | 已完整处理的进度和结果所依赖的原始资料 | 未解析范围不能跳过；升级后应能追溯和重放 |

## 把整篇文章压缩成一个故事

A 要授权从 TA 给 TB 转 100 M，而不是授权服务“想办法转成”。构造器先把 I1 固定为集群、币种 M、双方账户、A 的权限和 100,000,000 原子单位，生成传统 Token Program 的 TransferChecked，再加入付费人、账户访问声明和近期哈希 H1，保存最后有效区块高度。A 看到实际消息中的金额、收款账户、程序和费用设置后签名，服务保存 T1 的原始字节与 σ1。

模拟虽然成功，之后 TA 仍可能被其他交易花空，H1 也可能在等待期间失效；模拟不替 A 锁钱或占执行位置。发送超时后只能跟踪或按策略重发原字节，不能擅自替换 TB、加指令或换哈希重签。计算预算和优先费同样须在签名前确定，调高也不保证成功。若另一个复杂场景改用 v0 与地址查找表，就必须完整还原加载地址和账户索引，缺少地址或遇到未知版本便隔离，不能靠猜收款方继续执行。

结果要以真实执行为准：100 M 的业务金额与 A 另付的 SOL 费用分开，实际落链失败仍可能收费。签名保证的是消息没有被偷换，不保证余额永久可用、及时收录或交易必成；换哈希重签则是新的授权和执行机会。主例不需要地址查找表，也没有因使用新消息格式就获得跨多笔交易的原子性，未解析的历史更不能算已经完整处理。

**流程位置与核心机制：** 从业务意图进入消息、签名和发送，解释账户列表、有效窗口、模拟、资源预算与版本化消息。确认和未知重试在母题 06 深入，本题先固定“究竟签了什么”。

沿用总览：传统 SPL Token，A 从已存在的 TA 向 TB 转 100 M，6 位精度，A 自付 SOL 费用；主例可用 legacy 消息，不为三个账户的转账强行引入 ALT。

## 第 1 层：从意图变成可签消息

**面试官：** 给你 I1 的转账参数，你怎样构造交易，确保用户签的就是这笔 100 M 转账？

**面试者：** 我会先把 I1 固定成集群、源 TA、mint M、目标 TB、权限 A、原子金额 100,000,000 和 decimals=6，完成账户身份与布局校验，再构造传统 Token Program 的 TransferChecked。两端账户已存在，不在签名前后偷偷加入账户创建或其他业务指令。

交易消息还需要 fee payer、recent blockhash、账户访问描述和编译后的指令；A 作为权限持有者及费用支付方签署该消息。取得 H1 时同时保存 lastValidBlockHeight，用于后续跟踪有效窗口，而不是把本地秒数当成协议到期。

我向用户呈现的是解析后的实际消息，包括程序、接收账户、mint、金额和费用相关设置。签名后保存完整原字节与 σ1，发送器只发这份字节；若后来改变账户、金额、指令或 blockhash，就必须重新获得相应签名，不是“修补参数后继续发原交易”。

## 第 2 层：签名具体覆盖哪些内容

**面试官：** 你说改 blockhash 也要重签。签名究竟覆盖什么，RPC 能不能替你把一个过期 hash 换掉？

**面试者：** 签名覆盖序列化后的消息，所以 recent blockhash、账户键和指令等内容都是授权的一部分。换一个 hash 会改变消息，旧签名不能继续证明用户授权了新消息；RPC 不能不经签名者同意就把消息改掉。

同一份已签交易在不同 RPC 重发，仍是同一 σ1；换 hash 重签会产生新的交易身份和新的链上执行机会。普通 Token 转账没有 I1 字段，链不会因为两个签名来自同一个本地意图就自动合并它们。这也是为什么发送超时不能直接交给“自动换 hash 重签”的黑盒处理。

fee payer 和所有 required signer 必须与消息头及账户顺序一致，不能只检查附带签名的数量。服务需验证签名实际对应这份消息和预期签名者，避免用户审核的是一份摘要，最终发送的却是另一份消息。

## 第 3 层：signer 和 writable 如何约束执行

**面试官：** 消息里有签名还不够吗？为什么必须正确声明哪些账户 writable，哪些账户 signer？

**面试者：** 签名提供授权，writable 描述允许修改的账户，两者解决不同问题。TA 和 TB 的 Token 数量会变化，因此必须按指令需求可写；M 在这笔转账中用于校验 mint 与 decimals，不因为参与指令就自动需要可写。A 的系统账户作为 fee payer 有对应访问需求，A 还必须满足转账权限签名条件。

声明只读的账户不能在执行中随意升级为可写；没有获得 signer 权限的账户也不能在 CPI 中被普通调用凭空升级成签名者。程序能访问哪些账户及权限上限，由交易和运行时共同约束，不是 Go 服务说“这个地址可信”就能绕过。

过多 writable 会扩大冲突集合，降低并发机会；少声明则可能执行失败。因此构造器应使用明确指令 schema，按最小权限生成账户描述，再让模拟检查明显问题，但不把模拟当作权限校验的替代品。

## 第 4 层：模拟成功为何仍可能失败

**面试官：** 既然你模拟了完整消息，为什么执行时余额不足还会失败？模拟到底能保证什么？

**面试者：** 模拟是针对某个读取环境和时点的试执行，不会预留 TA 的资金，也不占住未来执行位置。模拟之后，A 可能通过别的交易花掉代币，账户可能被冻结，或者交易还没被处理 blockhash 就失效。因此模拟成功说明“在该环境与输入下未发现这类执行错误”，不是保证稍后一定成功。

模拟能帮助发现账户顺序、权限、指令数据、余额和计算预算等问题，并给出日志及资源线索。配置上要区分签名前的构造评估和签名后的原字节验证；若模拟使用替换 blockhash 或未校验签名，它不等于验证原签名交易仍处于有效窗口。

发送阶段保持获取 blockhash、模拟和 preflight 的上下文策略一致，降低节点进度差异造成的误拒绝；但最终仍按真实执行结果跟踪。关闭 preflight 只是改变提前检查方式，不会让执行规则失效，也不提供成功保证。

## 第 5 层：资源预算与费用怎样呈现

**面试官：** 你说模拟能给计算资源线索。是否只要把 compute unit limit 和优先费都调大，就能保证尽快成功？

**面试者：** 不能。计算预算要覆盖合理执行需求，并按目标集群和运行时规则设置；不足可能执行失败，过度请求可能增加费用或调度成本，却不保证被包含。优先费是发送与调度策略的一部分，不是确定执行位置的拍卖凭证，更不消除账户争用和业务条件失败。

若加入 Compute Budget 指令，它们本来就是用户待签消息的一部分，必须在签名前确定，并控制允许的费用上界。计算单价常使用 micro-lamports 表达，不能误当 lamports；本稿不把某个静态费率或计算上限写成永久协议常数。

主例只用最终 meta.fee=F lamports 表示实际费用。代币转账金额仍是 100 M，F 由 A 额外 SOL 账户承担。模拟成本、预计费用和实际收费需要区分；真实落链失败也可能收费，不能因业务没转成就把系统账户费用设为零。

## 第 6 层：何时需要 v0 和 ALT

**面试官：** 如果这次不是简单转账，而是账户很多的路由消息，v0 和 ALT 怎样改变你刚才的构造与签名校验？

**面试者：** 这是明确扩大账户集合后的比较。v0 消息可以通过 Address Lookup Table 引用更多账户地址，减少消息中直接列出的地址负担，但不改变这些账户的程序身份、访问权限或实际执行成本。它也不自动让路由跨多笔交易原子完成。

ALT 加载的地址不能充当消息要求的签名者，签名者需要在静态账户列表中。解析消息时要把静态键和正确顺序的 lookup writable／readonly 地址组合起来，才能理解指令的账户索引；不能只看静态列表，或把所有地址按字典序排序后继续解码。

用户审核和服务验证都应解析实际 lookup 结果并核对指令含义，还要检查表的可用性及所需地址是否能在目标执行环境中加载。若消息尺寸、账户或计算约束仍不满足，就重新设计方案；不能承诺“用了 ALT 就没有交易大小与资源限制”。

## 第 7 层：SDK 不支持新版本怎么办

**面试官：** 你要求解析实际 lookup 结果，但 Go SDK 碰到未知交易版本，或者返回数据没有 resolved addresses，能否先按 legacy 解出能读的部分？

**面试者：** 不能把不完整解析当成有效授权或业务证据。构造路径应使用明确支持并经过验证的版本，解析路径则记录原始数据、版本和失败原因，将未知交易隔离。账户索引缺少对应地址时，连“转给谁”都无法可靠判断，不能继续生成成功转账记录。

查询交易时按服务支持的版本显式配置可接受范围，并验证返回内容。对于 v0 历史解析，可以优先使用交易 meta 提供的实际加载地址；不能拿一张今天读到的 ALT，未经历史可用性分析就冒充当时所有状态的完备证据。

后续升级解码器时对隔离记录重放，并保留版本和血缘。升级前的未解析范围不能被历史水位跳过，否则系统会显示“历史完整”，实际只是丢掉了 SDK 不认识的部分。

## 第 8 层：怎样验证用户授权没有被偷换

**面试官：** 把前面的选择合起来，构造器和发送器之间最重要的验收反例是什么？

**面试者：** 我会先固定 A 审核并签名的一份消息，随后尝试替换 TB、改变金额、追加指令或换 H1，验证旧签名不会被接受，服务也不会把新字节作为原 T1 发出。再让发送器超时，验证它只能重发原字节或进入核查，不会擅自重新签名。

另外用模拟成功但执行前余额改变的时序，验证系统接受真实失败并保留费用证据；用 v0 加载地址与静态账户索引交错的样本，验证接收账户、权限和数量解析正确。未知版本则必须隔离而非降级成“能解多少算多少”。

这些反例覆盖了不可变授权、有效窗口、模拟边界和版本解析四条主线。这里给出的是验证方法，不声称已经在目标集群运行或测得某个成功率。

## 本题收束

- **讲透的机制：** 不可变消息、签名者与可写权限、模拟时点、费用预算和版本化账户寻址。
- **最易答错：** RPC 可以自动改 hash 不重签；模拟成功等于预留资金；ALT 里可以放签名者；未知版本先当 legacy。
- **检验反例：** 发送超时后 SDK 自动换 hash 重新签名，而旧 σ1 仍可能执行，构造和发送分层是否能阻止它？
