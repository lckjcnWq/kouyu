# 大问题 9：Solana 账户快照怎样衔接订阅，断线后怎样恢复并说明数据完整性？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| TA、TB、M、I1、T1、σ1 | 账户、币种、意图、尝试和签名代号 | 主例从 TA 给 TB 转 100 M，结果须查原签名 |
| decimals、原子单位、F | 显示精度、最小整数计量和实际费用符号 | 六位精度对应 100,000,000 原子单位；SOL 手续费另计 |
| 当前投影、订阅健康、历史覆盖 | 本地当前态、连接是否可靠和过去哪些范围已完整 | 三种状态分别记录，重连成功不能一并宣布完成 |
| PubSub、HTTP、WebSocket | 订阅机制、查询通道和通知通道 | 两种通道没有共同持久日志位置，先订阅再缓冲也不创造无缝边界 |
| 快照、delta、S | 一次状态读取、增量数据和快照上下文符号 | 标准通知不能按 slot 大小直接接在快照后应用 |
| getMultipleAccounts、Bank | 一次多账户读取和节点状态视图 | TA、TB、M 必须共同响应，分别成功不等于同一状态 |
| finalized、context.slot、revision | 最终性要求、读取上下文和本地发布版 | 整组校验后原子发布；读取位置不是各账户最后写位置 |
| minContextSlot | 最低求值上下文要求 | 不指定历史 slot，也不证明订阅缺口已补 |
| dirty generation、g0、g1 | 刷新理由计数及读取前后计数 | 读期间有新提示就保留下一轮，计数不是链序 |
| stale、失效 epoch、订阅 ID | 陈旧标记、本地连接世代和连接内订阅标识 | 断线、溢出独立标失效；订阅 ID 不是可续传账本游标 |
| 有界合并、节流 | 合并刷新理由和限制请求频率 | 不为每条提示建无限队列，也不能永久吞掉最后一次刷新 |
| W0、W、U | 历史覆盖起点、连续完成水位和本轮最终上界 | 只承诺约定范围从 W0 到 W 的完整处理，不自动从创世覆盖 |
| getBlocks、getBlock、meta | 枚举有块的 slot、取区块和执行附带资料 | 逐块取得完整交易证据，不把超时或缺失响应当空块 |
| skipped slot、覆盖证据 | 未产出最终区块的机会及证明枚举完整的依据 | slot 有跳跃不必丢块，但须有可信完整枚举才能跳过 |
| hmax、block height | 哈希最后有效区块高度及实际区块进度 | 不是历史水位的 slot；过期仍不排除此前成功 |
| signature、指令路径、事件身份 | 交易签名、调用位置和稳定去重键 | 区分同交易多笔转账，重启重解析不重复发布业务记录 |
| 本地事务、发布屏障 | 数据库整体提交和完整后才对外发布的门槛 | 历史、区块完成标记、水位一起提交，洞后大 slot 不越洞 |
| 归档、Unknown、链上消费屏障 | 历史保留能力、结果未知和链上拒绝重复业务的规则 | 无归档就留缺口；普通 transfer 不认识 I1，不能用补历史名义重签 |

## 把整篇文章压缩成一个故事

A 从 TA 给 TB 转 100 M，订阅却在关键时段断开，σ1 在缺口内最终成功。恢复服务先建立新通知通道，再一次读取 TA、TB、M 的 finalized 共同快照，核验后整组发布；没有其他交易时读到 900,000,000 和 100,000,000 原子单位。这只恢复当前余额，既不靠余额确认 σ1，也不声称断线期间每笔业务已找回；先订阅、缓存消息再按 slot 接到快照后面同样没有无缝日志保证。

读期间又来提示，就增加本地计数并安排下一轮；断线或队列溢出则独立标失效，旧任务不能清掉新故障。历史恢复走另一条路：固定覆盖起点和最终上界，完整枚举已产出区块，逐个获取交易与执行资料。假设一个区块解析到第六十笔就遇到未知版本，或者发布事务提交前进程崩溃，连续水位都不能越过该洞；重启按已提交进度恢复，靠交易签名与指令路径去重，不把候选下载当完整发布。

找到 σ1 的最终成功证据后才完成 I1，并记录另付的实际费用；缺归档时则允许“当前余额已恢复、历史未补齐、单笔结果未知”同时存在。期间一进一出净额为零也可能有两笔业务，不能倒推为零交易；slot 没有块需要完整枚举证据，null 或超时不是空块。历史和水位必须共同持久提交，超过哈希有效高度也不能证明缺失历史里没成功，更不能自动重签再转一次。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖“启动初始化 → 订阅与快照竞争 → 断线或溢出 → 当前态重扫 → 最终交易历史回补”。核心是分别定义当前投影可用、观察通道健康和业务历史覆盖，不能用一次成功重连或全量重扫同时宣告三者完成。

**固定案例：** 单 Solana 集群、非托管、传统 SPL Token 普通 mint M，decimals=6。A 控制 TA，初始 1,000 M；B 控制 TB，初始 0。账户已存在，不创建 ATA，不涉及租金变化。I1 的 T1/σ1 使用 recent blockhash H1，保存对应 `lastValidBlockHeight=hmax`，转账 100 M=100,000,000 原子单位。隔离成功后 TA=900,000,000、TB=100,000,000；A 另以系统账户支付实际 `meta.fee=F` lamports，无协议费。不使用 Token-2022、WSOL、跨链、自定义幂等程序或 durable nonce。意图和已签名 attempt 先持久再由服务发送；用户钱包仍可能独立广播。

## 第 1 层：断线后全量重扫，究竟恢复了什么？

**面试官：** TA、TB 的订阅断开一分钟，重连后读到了正确余额。你能宣称断线期间的数据已经完整恢复吗？

**面试者：** 只能说恢复了某个最终读取上下文中的当前账户状态，不能说恢复了每笔业务历史。断线期间可能有多次转入、转出，最终净额恰好为零；当前余额不会保留这些过程。即使现在 TA=900,000,000、TB=100,000,000，也不能单凭余额认定 I1 的 σ1 成功。

我会维护三种不同的信息：账户投影记录共同读取的 context 与本地 revision；订阅健康记录连接和失效状态；业务历史记录从明确起点开始已经完整处理到哪里。σ1 的最终成功或失败则由独立交易证据裁决。

恢复当前态的基线是对 TA、TB、M 做一次 finalized 共同读取，校验后原子发布。恢复支持的转账业务历史则要取得最终区块及交易 meta，并保持覆盖水位。前者无需伪装成无损日志，后者也不能因为前者已恢复就跳过缺口。

## 第 2 层：先订阅、再取快照、缓冲通知，能不能形成无缝边界？

**面试官：** 你区分当前态和历史了。那启动时先订阅并缓存消息，再取快照 S，最后重放 slot>S 的缓存，不就能把当前态升级成无缝连续状态吗？

**面试者：** 标准 RPC 下不能这样承诺。先订阅可以降低漏感知的概率，但订阅成功并不提供“从某个持久位置起，所有账户写都已覆盖”的契约。快照的读取 context 与订阅流之间也没有共同的连续日志位置。

按 slot>S 重放会丢掉快照边界附近无法细分的同 slot 变化；按 slot>=S 重放又无法判断哪些通知已经被快照覆盖。标准通知没有足以解决这一问题的全局写序，缓冲里缺失的消息更不可能靠排序补出来。HTTP 响应与 WebSocket 消息的到达先后也不能当作 Bank 的执行边界。

所以本模型先建立通知通道，再安排 finalized 全量读取，但缓冲的只是“需要再读”的提示，不是待应用的权威 delta。任何通知都使快照失效并触发重读；同时保留周期刷新。这个方案承诺在明确条件下收敛当前态，不承诺从快照起每次写都不丢。

## 第 3 层：既然不重放 delta，首个快照怎样才算可发布？

**面试官：** 你选择重读而不是重放。启动时分别请求 TA、TB、M，然后把三份成功响应拼起来，是否就算完成初始化？

**面试者：** 不算。这三个对象是固定小集合，可以放进同一次 `getMultipleAccounts`，显式请求 finalized。单次响应提供共同 context，避免先读到转账前的 TA、再读到转账后的 TB。多个 HTTP 请求没有同一 Bank 的保证，不能靠时间接近或者 slot 接近补出这个保证。

收到响应后，检查返回数量、请求位置映射、账户非空、传统 SPL Token Program 所有权和数据布局；确认 TA、TB 的 mint 都为 M，授权关系符合 A、B 控制前提，M 已初始化且 decimals=6。金额按整数保存，不把 null 当作零，也不以浮点数解析后再取整。

校验成功后，把整组账户投影、读取 `context.slot` 和本地 revision 在数据库中原子发布。context.slot 只表示读取上下文，不表示三个账户都在该 slot 修改过；`minContextSlot` 只是可接受的读取下限，不是历史 slot 的指定读取能力。初始化完成也只表示有了一版可解释的最终快照，并不表示业务历史已经补齐。

## 第 4 层：初始快照读取期间出现通知，怎样避免清错 dirty？

**面试官：** 你已经定义好快照发布。但在读请求发出后，TB 又有变化提示；发布成功时直接标为 clean，会不会把这条提示丢掉？

**面试者：** 会，所以每次提示都增加本地 dirty generation。读取开始记下 g0，读完后在协调边界内检查当前 generation。若等于 g0，才可以结束这一轮已知的刷新义务；若已经变成 g1>g0，就保留 dirty，串行安排下一轮共同读取。

递增、比较和清理要有原子裁决，不能比较后再异步清零。读期间到达的提示可能对应快照已经包含的变化，也可能对应快照之后的变化；因为无法可靠区分，只能保守地再读一次。generation 是本地调度状态，不代表链上事件序号，也不代表这一轮恢复了 g1-g0 次账户写。

即使 generation 未变化，也不能永远停止刷新。例如 confirmed 通知先到，finalized 读取尚未包含 T1，之后没有第二条通知；需要周期 finalized 全量刷新，或者由独立签名最终状态额外触发读取。清除 dirty 只完成本轮任务，不是颁发永久新鲜证明。

## 第 5 层：读期间断线或队列溢出，怎样处理旧响应？

**面试官：** 你靠 generation 判断读取期间的新提示，但队列已经溢出，或者连接断开导致提示根本没进来，generation 没增加怎么办？

**面试者：** 这些故障必须走独立的失效路径。通知处理队列有界，发现溢出就把这组投影标 stale，并增加本地失效标记；断连或无法确认订阅仍有效时也一样，不能等下一条账户消息来提醒。

每轮读取同时记录当前订阅连接世代或本地失效 epoch。它是本地协调标识，不是 Solana epoch 或链上版本。若读期间失效标记发生变化，旧响应即使能作为一版经过校验的最终快照，也不能据此宣称已完成重连恢复或清除 stale。保守做法是撤销旧任务的发布资格，在新通道建立后重新安排一轮全量读取。

新连接健康、故障后共同读取成功且没有更新的失效条件，才可以清除这次已知连接缺口对应的当前态 stale。此后仍保留周期刷新。原连接订阅 ID 不作为恢复游标，也不恢复任何历史完整性声明。

## 第 6 层：变化一直到来，是否要无限积压或一直保持不可用？

**面试官：** 你每次提示都留下一轮刷新义务。高频变化时 generation 不断增加，队列会不会无限长，页面是不是永远不能用？

**面试者：** 不需要为每条提示排一个完整刷新任务。提示可以合并为一个 dirty 标记与 generation，固定集合由一个协调者串行读取；读取期间再来许多提示，也只要求本轮完成后继续读，不保存无限的 delta 队列。

每次校验通过且没有丧失发布资格的 finalized 快照都可以原子发布，附带 context、revision 和读取时间。即使还有待刷新理由，用户也能看到“截至该最终上下文的已验证状态”，但不能把它显示成绝对实时。若断连未恢复或者已知故障后的重读未完成，则明确标 stale，而不是用持续变化掩盖观测缺口。

刷新可以做有界合并和节流以控制负载，但必须保留周期任务和失败重试，不能在冷却期间永久吞掉最后一次 dirty。取舍是允许一定展示滞后，不是丢弃链上业务；本题没有逐写完整性的承诺，因此没有必要为了每个提示都单独读一次而无限排队。

## 第 7 层：业务历史水位应怎样定义，才能真正说明回补完整？

**面试官：** 你解决了当前态的有界收敛。财务现在要求列出断线期间每一笔受支持的 M 转账，你准备怎么建立不能乱跳的历史水位？

**面试者：** 先明确覆盖起点 W0、目标账户或 mint 范围，以及受支持的传统 SPL 转账解析范围。水位 W 表示从约定起点到最终 slot W 之间，所有应检查的最终区块都已完整取得、校验并处理，不表示只拿到了编号最大的那一个区块，也不表示从创世起覆盖所有历史。

先取得一个最终 slot 上界 U，再在明确范围内枚举最终已产出的区块 slot，例如使用符合覆盖契约的 `getBlocks`，并对列出的区块逐个取 `getBlock` 的交易与 meta。这里 W、U 都是 slot；T1 的 hmax 是 block height，二者不能混用。slot 有跳跃不自动代表丢块，某些 slot 本来没有产出最终区块。

但任何 `null`、超时、裁剪或服务错误都不能当作空块。跳过未产出 slot，需要来自覆盖完整、可信最终链枚举的证据；提供方若只覆盖部分范围，就不能把未列出的部分都解释为 skipped。尚未处理完整的范围只进入待恢复集合，不能推进连续覆盖水位。

## 第 8 层：区块取到了但只解析一半，怎样防止水位虚假推进？

**面试官：** 你定义 W 为完整覆盖。某个区块有一百笔交易，解析到第六十笔时遇到不支持的版本或缺失 meta，随后重启。前六十笔是否要重复记账，W 又怎样处理？

**面试者：** 先区分“已经下载”“已完整解析”和“已发布到业务历史”。下载成功不等于完整处理。请求应显式协商支持的交易版本；若遇到无法解码的消息、缺失关键 meta，或者无法排除与目标范围相关的未知指令，就保留该区块为未完成，不能跳过余下交易推进 W。

业务事件使用稳定身份去重，例如集群身份、交易 signature 和指令路径的组合；顶层与内部指令路径要能够区分同一交易中的多笔受支持转账。局部解析结果可以暂存为候选，但对外的“已覆盖历史”只发布经过完整性检查的区块结果。

在本地数据库事务中完成去重后的历史发布、区块完成标记和可推进的连续水位更新。若大块需要分批暂存，仍保留最终发布屏障；重启后靠事件身份复用候选结果，不能把前六十笔的重复处理变成重复业务记录。后续区块可以先取回，但只要这一块有洞，连续 W 就停在洞前。

## 第 9 层：没有归档覆盖时，还能恢复到什么程度？

**面试官：** 你需要完整区块，但提供方已裁剪那段历史，且没有第二个覆盖源。能否根据现在 TA、TB 的余额倒推缺失交易，或者把日志记为零条继续推进？

**面试者：** 都不能。当前状态到历史不是一一映射。比如断线期间发生一次转入 100 M、一次转出 100 M，与完全没有交易，最终余额可能相同。单靠当前余额不能恢复 signature、指令路径、实际手续费或交易次数。

可以恢复的是当前投影：取得新的 finalized 共同快照并发布，同时把历史覆盖缺口保持为“未完整”，让 W 停在有证据的位置。提供方的最低可服务 slot 或保留说明可帮助定位能力边界，但不能自动证明该区间内每个最终区块、每个关键 meta 都已经齐全。

I1 若也缺乏 σ1 的最终结果，就保持 Unknown。即使最终 block height 超过 hmax，也只是证明 T1 不再具有未来执行窗口，不证明缺失历史中没有成功；没有链上 intent 消费屏障时，不得用“补历史”的名义更新 blockhash 重签。当前态恢复、历史待补、单笔结果未知可以同时存在，它们并不矛盾。

## 第 10 层：怎样在一次崩溃时序中验证三种完整性？

**面试官：** 你允许三种状态并存。请推演：订阅断线，T1 在缺口内最终成功；恢复后快照已发布，但业务历史事务提交前进程又崩溃。重启后怎样保证没有虚假完整、重复记录或重复转账？

**面试者：** 第一次断线立即使投影 stale。恢复时建立新通知通道，读取 TA、TB、M 的共同 finalized 快照，校验并原子发布新 revision；隔离案例显示 TA=900,000,000、TB=100,000,000。这只恢复了当前态，不自动确认 I1，也不推进历史 W。

若历史发布事务尚未提交就崩溃，重启后数据库的 W 仍在旧位置。服务从已提交 W 后继续取得所需区块，校验完整交易和 meta，按稳定事件身份去重后提交历史与新水位。若其实事务已经提交、只是应用没收到结果，重读已提交水位并依靠去重继续，不重复新增那笔业务。

找到 σ1 的 finalized 成功证据后再完成 I1，并记录 `meta.fee=F`；若暂时找不到，I1 保持 Unknown，不创建新签名 attempt。重启时当前投影也重新进入待刷新流程，防止把停机前的新鲜度沿用到现在。三个检查分别是：投影是否整组一致、历史是否无洞推进、交易是否有最终依据；不能用其中一个成功替代另外两个。

## 收束：机制、易错边界与反例验证

- **讲透的机制：** 标准 RPC 下采用通知失效、串行 finalized 重读和周期刷新收敛当前态；受支持业务历史则采用独立最终区块覆盖水位，并将事件去重、完整性标记和水位发布置于可恢复的本地提交边界。
- **最易错的边界：** 订阅先行加缓冲不创造无缝 delta 契约；读取 context 不是最后写 slot；dirty generation 不是链序；断连和溢出必须标 stale；`null` 不等于空块，slot 跳跃不自动等于缺失；getBlock 的交易/meta 也不是任意程序逐写原始镜像。
- **反例验证：** 手工安排“缺口内先转入再转出、净额为零”和“历史洞之后有更大 slot 已成功解析”。合格方案不能从净额零推出零交易，也不能把水位直接推进到更大 slot。当前态可恢复而历史仍不完整，必须在对外交付中保持可区分。此处不声称已经完成生产效果验证。
