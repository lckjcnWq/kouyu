# 大问题 8：拿到 DEX 交易回执以后，怎样证明兑换结果，并处理执行失败、最终性和链重组？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| DEX / Swap / A / R / P | 去中心化交易系统、换币动作、用户、路由合约、池。 | 核验的是 A 用 2000 U 换 W 的确切调用，不是任何成功交易。 |
| receipt / status / EVM | 执行回执、回执中的执行状态、合约执行环境。 | status=1 表示外层没回滚，status=0 表示已包含的调用失败，都还要说明所属分支。 |
| I1 / attempt / txHash / nonce | 应用意图、具体尝试、交易哈希、账户交易序号。 | 回执须对应已知尝试，同 nonce 的取消成功也不能冒充 I1 兑换。 |
| chainId / blockHash / parentHash | 链身份、区块哈希、父区块哈希。 | 用来核对网络、具体包含块和连续分支，同高度不等于同块。 |
| ABI / topic / Transfer / Swap 日志 | 编码约定、事件识别字段、转账和交换事件。 | 发出地址、实际参数及代码都要匹配，同名事件不证明真实换币。 |
| minOut / recipient / value / deadline | 最低输出、收款人、附带原生币数量、执行期限。 | 必须与用户签署的授权一致；本例到达期限就拒绝。 |
| x / y / a / floor / 原子单位 | 两种池储备、输入、向下取整、最小整数金额。 | U 为 6 位、W 为 18 位小数；输出整数算，完整 2000 U 进池，费用不额外重复扣。 |
| approve / allowance / revert / Gas | 设置代币权限、使用额度、回滚、链上执行资源。 | 失败 Swap 内部不留半笔转账，但先前独立授权保留，已包含失败仍耗 ETH 和 nonce。 |
| included / canonical / finalized | 被某块包含、属于当前规范链、按共识前提最终确定。 | 三者分开；包含块须等于最终检查点或位于其祖先链，不只比高度。 |
| 重组 / 共同祖先 / H1′ | 规范分支切换、新旧分支共享的最后区块、替代 H1 的另一块。 | 确认旧块退出后撤回旧观察，不因一次空回执就宣判失败。 |
| RPC / receiptsRoot / stateRoot | 节点接口、收据承诺摘要、状态承诺摘要。 | 普通接口响应不是包含证明；证明还须绑定共识认可的头，存在性也不等于检索完整。 |
| observation / active / revision | 分支观察、当前有效性、本地修订号。 | 同一观察可有效、撤回、再次有效，唯一键不能永久禁止再应用。 |
| finalized 冲突 / 异常隔离 | 与已接受最终链段矛盾的证据，以及暂停自动承诺并调查的流程。 | 不能按普通重组静默改掉最终结论，现实中的不可逆动作也不会随数据库回滚。 |
| indexed / 水位 / 投影 | 已索引进度、完整处理位置、派生查询视图。 | 链上已最终成功而页面未同步，应该补证据，不再发一笔兑换。 |

## 把整篇文章压缩成一个故事

小林终于查到一张 status=1 的回执，想马上认定 2000 U 已最终换成 W。工程师先核对它是否真属于小林签的交易、是否调用正确 R/P、U/W 是否为指定资产、收款是否归小林。主例条件不变时，应是小林剩 3000 U 并获得 0.995015938219190933 W；同名日志或陌生地址的成功不能替代这些证据。

假设这次成功所在 H1 还没最终确定，后来规范链改走别的分支。系统应撤回 H1 对页面的贡献并继续追踪，不能把它改说成一次 status=0，也不能自动再买。若之后又回到同一个 H1，就恢复一次有效结果，不能因为早就见过而永久跳过。每次执行结果都跟着自己的区块身份，而不是脱离分支永远有效。

最终完成还要核验包含块与已验证 finalized 检查点的祖先关系，固定等若干块不等同于这项证据。若最终前缀本身冲突，先暂停调查；若只是页面落后，就补索引。本文教的是让每一层结论有对应证据，而不是找到一张成功回执就把所有不确定性删掉。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖“收到回执 → 核验规范包含关系与执行结果 → 验证真实兑换 → 判断最终性 → 处理重组及异常”。重点是建立链上事实的证据链，不把 RPC 返回成功、EVM 执行成功、业务兑换成立、最终确定和页面已索引混成一个状态。广播未知态的身份恢复见[大问题 7](07-业务身份重试与广播未知态.md)，回执事实向本地投影的可恢复传播见[大问题 9](09-索引投影与跨模块状态同步.md)。

**必要前提：** 金额、期限、R/P 规则与资产假设见[总览](README.md)第 1 节，证据和状态定义见第 4 节。本题核验 A 的 nonce42 在特定区块中的执行，不将前置 approve 一并回滚；最终性采用经验证 finalized 检查点的祖先关系。各异常独立从公共主例改变条件。

```text
原始签名与 attempt 身份
    ↓
交易、区块头与回执相互核对
    ↓
确认当前规范包含关系
    ├─ status 0 → 该次 swap 执行回滚，单独判断失败的最终性
    └─ status 1 → 核验 R/P、资产、输入、收款人与兑换证据
                         ↓
                 得到当前分支上的业务结果
                         ↓
经验证节点的 finalized 区块与包含区块建立祖先关系
    ├─ 尚未达到 → 可撤回的结果，持续跟踪重组
    └─ 已经达到 → 按明确的节点信任条件报告最终结果
                         ↓
本地索引按自身水位发布，不反过来决定链上是否已执行
```

## 第 1 层：一张 status 1 回执究竟证明了什么？

**面试官：** A 的 swap 返回了 receipt，status 为 1。你会立即告诉用户“2000 U 已最终换成 W”吗？为什么？

**面试者：** 不会直接作出这个完整承诺。status 1 只是在这份回执所描述的区块执行上下文里，交易顶层执行没有回滚。首先要确认回执对应 I1 的某个已知 attempt，回执的 txHash、blockHash、blockNumber 与实际区块一致，并确认该区块仍在节点认可的当前规范链上。接着还要检查交易确实执行了已授权的 R 调用，而不是钱包发出的其他成功操作。只有业务证据匹配之后，才能说当前分支上发生了这次兑换；它还可能尚未最终确定，也可能尚未被本地索引发布。

我会把结果拆成“在哪个区块被 included”“目前是否 current canonical”“执行 status 为 0 还是 1”“业务核验是否通过”“是否满足 finality”“本地 indexed 到什么位置”。included 是带区块身份的历史观察，current canonical 会因分支切换而改变，status 也不能脱离其所属区块理解。广播接口返回 hash 甚至比回执更弱，只说明服务拿到传播线索。用这些独立维度回答，才能在后续重组或索引落后时撤回正确的结论，而不是把一个 completed 字段改来改去却无法解释资产发生了什么。

## 第 2 层：执行成功怎样进一步核验为本次兑换成功？

**面试官：** 你说 status 1 还要经过业务核验。假设回执里有一个名字也叫 Swap 的日志，你怎样排除它不是无关交易或伪造事件？

**面试者：** 我会先以签名交易为入口核对 chainId 1、发送者 A、nonce 42、目标 R，以及 data 内的 U/W、P 或确定路由、精确输入 2000000000、minOut、deadline 和 recipient=A；同时检查 value 没有附带未经授权的 ETH。R/P 地址和已确认的不可升级代码属于本题的信任配置，不能因为某日志带有相同 topic 就临时把它的发出者认作 P。只有确切地址、已知 ABI 和已授权调用上下文都匹配，才有资格解释日志的业务含义。

随后结合成功回执中的 P 兑换或储备事件、U/W 的真实合约 Transfer 证据，以及可取得的执行状态或历史追踪结果核对数量和收款。标准 ERC20 与 R 不吞失败的前提，才让这些证据可以连成原子兑换解释。若只拿到了名字相同的日志、解码失败或数量对不上，就保留“EVM 成功、业务证据待核验”，而不是向 A 记一笔 W。区块末状态可能包含本交易之后的其他交易，因此状态查询必须说明锚点，不能把任意 latest 余额直接归因给 I1。

## 第 3 层：用固定数值怎样核对输入、输出和手续费？

**面试官：** 你要求数量和状态对得上。在没有其他交易干扰的主例里，请把这笔兑换的输出、A 的余额和池储备讲成可以手算核对的结果。

**面试者：** 我会统一使用整数原子单位。初始 U 储备 `x=1000000000000`，W 储备 `y=500000000000000000000`，输入 `a=2000000000`；0.3% 手续费意味着定价按 `997/1000` 的有效输入计算，但全部 2000 U 都进入 P。输出为 `floor(a*997*y/(x*1000+a*997))=995015938219190933` W 原子，即 `0.995015938219190933 W`。把该输出乘 `995/1000` 并向下取整，得到本题 0.5% 容忍下的 `minOut=990040858528094978`，主例显然满足输出保护。

成功以后，A 的资产变成 `3000 U、0.995015938219190933 W`，P 的 U 增至 `1002000 U`，W 减至 `499004984061780809067` 原子。手续费对应 6 U 留在池内，不是只给池加 1994 U，也不是另建平台手续费账户；整数向下取整的尾差同样留在池中。A 的 ETH 另因 gas 减少，不应从 2000 U 中扣 gas。上述余额核对依赖“从 H0 到这笔执行没有其他相关资产变化”的主例条件，不能把别人的后续 swap 引起的区块末储备误判为 I1 算错。核对时应逐币种比较输入与输出的去向，不能把不同精度、不同资产的数值直接相加来证明守恒。

## 第 4 层：失败为什么不是“扣了 U，但还没结算 W”？

**面试官：** 你刚才利用 R 的原子性核对余额。如果只把执行时间改成恰好 deadline，或者某一步转账失败，回执 status 0 时分别有哪些状态回滚、哪些仍然保留？

**面试者：** 先看只改变执行时间的变体：当 `block.timestamp=1800000120`，R 的严格条件 `block.timestamp < deadline` 不成立，整笔 swap 应拒绝，而不是把相等当成最后一秒仍有效。另一个独立变体只改变某一步 token 转账的执行结果；因为 R 不捕获失败继续，失败会沿调用栈回滚。无论在检查阶段还是后续调用阶段回滚，本次 swap 内部的 token 转移、P 储备写入以及日志都不会留下部分成功状态，不存在等待 Go 给 A 补发 W 的正常结算阶段。

但 status 0 是已包含的执行失败，不是从未发送。A 的 nonce 42 已消耗，ETH 仍支付实际 gas；此前 nonce 41 的独立成功 approve 继续存在。没有其他资产活动时，A 的 U/W 仍为 5000 U、0 W，P 仍为初始储备，失败 swap 内对 allowance 的扣减也随执行回滚。receipt 通常不会直接给出完整 revert 原因，诊断需要基于准确历史上下文的追踪或重放，不能用 latest 的一次 eth_call 冒充当时执行证据。当前规范失败与最终失败仍需分开判断，不能因 status 0 就跳过重组边界。

## 第 5 层：成功回执所在区块被替换后，哪些事实需要撤回？

**面试官：** 既然失败也可能受重组影响，那主例原本在 H1 中 status 1，后来同高度出现 H1'，原回执消失了。你要把交易改成失败，还是把资产改回去？

**面试者：** 我会先确定 H1 已经不在当前规范分支，而不是仅凭一次 receipt 空响应就断言重组。通过新旧区块头的 parentHash 找到共同祖先 H0，确认新的规范分支后，原 H1 的“当前有效成功”观察应撤回，但保留“曾在 H1 执行成功”的历史证据。它既不是 status 0，也不是证明原交易永远不会执行；同一个签名交易可能回到交易池、进入新分支，或者被 A 同 nonce 的其他候选取代。服务继续跟踪 nonce 42 的竞争组，不能自动构造 nonce 43 补单。

资产由链的规范状态决定，Go 不能通过更新内部余额把链上 U/W 改回去。需要撤回的是依赖旧分支的本地成交、储备和通知投影，并将它们重新对齐到共同祖先及新分支事实。如果新分支重新包含该交易，要用新 blockHash 生成新的观察身份，即使 txHash 相同也重新核验。主例仅在 H1 尚未 finalized 时按普通重组处理；若 H1 已被接受为 finalized，后续冲突要进入最终性异常流程，不能把安全假设失效伪装成一次普通页面刷新。

## 第 6 层：为什么若干次确认不等于 Ethereum 最终性？

**面试官：** 你区分了普通重组和最终性异常。那我规定“等 12 个块就完成”，是否已经足以把 H1 称为最终确定？

**面试者：** 12 个后继区块可以是产品采用的风险等待策略，但它不是 Ethereum PoS 的最终性定义，不能把配置名改成 final 就偷换承诺。我会从经验证的节点取得 finalized 区块 F，核实网络、节点同步情况和共识验证前提，再沿可信区块头关系确认 H1 等于 F 或者是 F 的祖先。只有“包含 I1 的确切区块哈希落在该 finalized 链段上”，才能据此把本次执行标为 finalized。只比较高度不够，因为同一高度的 H1 和 H1' 是不同区块。

这里的经验证不是说一个远程接口声称 finalized 就自动正确。可以由自己运行并验证的执行层与共识层节点提供，也可以明确接受某个提供商的信任与运行保障；后一种情形就应写进服务承诺。finalized 可能推进缓慢或暂时停止，节点也可能落后，此时保留等待状态、显示当前水位，而不是超时后把普通确认数替代最终性。如果产品允许提前展示，应称为“当前规范、未最终确定”，并承担可撤回展示的边界，不把展示速度包装成共识安全性。

## 第 7 层：RPC 和日志的信任边界怎样说清楚？

**面试官：** 你依赖经验证节点的区块关系。若只是从两个公共 RPC 都拿到相同 logs 和 finalized 标签，能否说这套后端已经不信任任何第三方？

**面试者：** 不能。两个 RPC 一致能提高故障发现能力，却不自动消除它们共同依赖同一基础设施、配置错误或恶意返回的可能。eth_getLogs 的普通响应没有天然附带可独立验证的收据包含证明；收到 txHash、logIndex、blockHash 这些字段，也不等于已经证明日志确实属于一个共识认可区块。若使用可信节点的执行与共识验证结果，这是一条合理的信任路径，但要明确是在信任节点的正确验证和所连接的网络，而不是把“链上数据”四个字等同于无信任。

若要缩小 RPC 信任，需要进一步验证共识认可的区块头，并以 receiptsRoot 等承诺核验完整收据和日志包含关系；状态证明也要以相应 stateRoot 为锚。即便有证明，检索是否遗漏所有目标日志仍涉及完整性问题，不能只证明某条存在就宣称整个区间已扫全。本题不把这些证明系统偷偷当作已实现能力。对返回冲突、历史数据缺失或节点落后的情形，服务应标注证据不足并暂停相关确定性推进，不能以供应商多数票代替已经声明的规范链与最终性验证规则。

## 第 8 层：一个旧事件实例重新成为规范事实时怎样处理？

**面试官：** 你要求保留历史证据。假如 H1 先被撤下，后来分支选择又回到同一个 H1，同一条 observation 再次有效，永久唯一键会不会把它挡掉？

**面试者：** 会，所以唯一键只能防止重复保存同一个观察对象，不能代替它的有效性状态机。观察身份是 `(chainId,blockHash,txHash,logIndex)`；同一个 H1 再次规范化时，这个身份可能完全没变。如果第一次应用后只留下“见过”的标记，重组时又把投影减掉，第二次看到它便直接跳过，最终就会出现链上有兑换、本地没有兑换的错误。我会保留 observation 及 active 状态，并把“未激活到激活”的转换和投影应用放在同一个本地事务中；“激活到未激活”则在撤回事务里完成。

相同关联/核验版本的重复激活通知，在已经 active 且相应投影贡献已应用时无操作；撤回以后再次激活必须重新应用，并分配新的投影 revision。若 active 不变但 I1 关联或业务核验后来才齐全，仍需按各投影已应用记录事务化补记，详见大问题 9，不能把 active 当作所有投影均已完成。revision 描述本地认知顺序，不修改链上事件的原始身份。若交易进入不同 blockHash，则属于另一条观察，也不能同时作为当前有效兑换叠加。这里处理的是未 finalized 链段内的分支选择变化，不能用该机制悄悄接受 finalized 区块冲突。完整的撤回、新分支应用和游标提交应由索引本地事务或带不可见构建区的恢复协议覆盖，不能只修一行 active 标记就宣布一致性已经闭合。

## 第 9 层：最终性异常为什么不能靠自动冲正掩盖？

**面试官：** 你已经能撤回、再应用。如果节点突然给出与已接受 finalized 区块冲突的分支，直接按普通重组反做旧事件，不是最省事吗？

**面试者：** 这不是普通深一点的重组，而是我们已对外使用的安全前提出现异常。先停止提升最终状态和触发依赖最终性的不可逆链下动作，保存此前的 finalized 锚点、冲突头、RPC 来源及验证记录，排查是否连错网络、节点损坏或共识安全假设确实受损。系统可以继续隔离采集候选证据，但不能把新响应直接写成正常 finalized 游标，更不能自动覆盖原最终结论，让调用方以为没有发生过异常。

尤其是已经发送的外部货物、不可撤销付款或其他承诺，并不会因为本地投影执行反向更新就被追回。本题基线没有这些业务动作；若单独增加这种产品变体，必须事先说明依赖的最终性信任、风险与异常处置权限，不能声称数据库冲正实现了现实世界回滚。恢复需要明确选定可信锚点、受影响范围和对外解释，再按可审计流程重建投影或处理业务责任。暂停并不是否认有新链数据，而是承认“原安全假设未核清时继续自动兑现”会把一个可调查的问题扩大成不可逆损失。

## 第 10 层：怎样把链上结果、最终性与页面进度一起交给用户？

**面试官：** 假设没有最终性异常，主例已核验成功且 H1 是 finalized F 的祖先，但页面的交易列表仍没更新。怎样回答用户才不会诱导他再换一次？

**面试者：** 我会明确报告：I1 的某个确切 hash 在 H1 中规范执行成功，调用内容和资产证据已核验，包含区块满足 finalized 祖先条件；这与页面索引尚未推进到 H1 是两个事实。交易详情可依据已持久化的回执证据显示结果，同时给出索引水位和投影 revision，说明列表延迟，而不是把空列表解释成“链上没有发生”。若页面要组合池状态和兑换历史，就必须等它们达到一致的查询水位，不能把来自不同版本的数据拼成余额矛盾的界面。

主例在没有其他交易影响时，用户应能复述 A 从 5000 U、0 W 变成 3000 U、995015938219190933 W 原子，P 从 1000000 U、500 W 变成 1002000 U、499004984061780809067 W 原子，ETH 另扣 gas。服务不因列表延迟创建 nonce 43，也不建立托管余额先行“补发”。如果证据尚未齐全，则如实显示业务核验待完成；如果只是索引未就绪，就重放和修复投影。把链执行、最终性与展示分别交付，才能使失败恢复留在正确的责任边界，而不是通过重复兑换修复一个页面问题。

## 本题收束

- **讲透的机制：** 回执必须与已授权交易、确切区块和当前规范链相互核验；status 1 后继续核对 R/P、资产、输入和收款证据。执行成功、业务成立、finalized 与 indexed 是不同维度。最终性依据经验证节点 finalized 区块的祖先关系，普通确认数不能替代。
- **最易答错的边界：** status 0 会回滚 swap 内 token、储备和日志，但已包含失败仍消耗 nonce 与 gas，独立 approve 保留。日志普通响应不是包含证明，多个 RPC 一致不是无信任。旧 observation 可从 active 撤回后再激活；最终性冲突则必须进入异常隔离，不能自动回滚不可逆链下动作。
- **具体反例验证：** 以 H0 为共同祖先，手工推演“未最终确定的 H1 成功 → 切到不含本交易的分支 → 又回到原 H1”。正确投影是有效一次、撤回、重新有效一次，最后仍只有一笔 2000 U 兑换，不能永久去重后丢失，也不能累计两次。另独立把主例执行时间改为恰好 `1800000120`，检查整笔 swap 失败、U/W 与储备不变、nonce 和 gas 消耗、nonce 41 approve 保留；再独立让 finalized 证据冲突，正确行为是暂停最终承诺而非普通自动冲正。
