# 大问题 6：一笔 Swap 链上已经原子执行，为什么端到端仍会不一致，怎样让交易、索引和展示最终对得上？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| Swap / A / R / P / U/W | 换币动作、用户、路由合约、池、两种教学代币。 | A 用 2000 U 换 W，Go 没有用户私钥或内部资产账本。 |
| EVM / 顶层交易 / 原子性 | 合约执行环境、一笔包含全部内部调用的交易、相关变化一起提交或回滚。 | 只覆盖本次 Swap 内部的资产与池状态，不覆盖 Go 数据库或消息系统。 |
| revert / approve / allowance | 执行回滚、设置代币权限、代币使用额度。 | 失败 Swap 内部的额度消耗可回滚，但前一笔已经成功的 approve 不撤销。 |
| Gas / EOA nonce | 链上执行资源、私钥控制账户的交易序号。 | 已包含失败仍支付实际 ETH 执行费并消耗序号，不等于业务换币成功。 |
| 原子量 / 997 / 留池费 | 最小整数金额、扣除 0.3% 费用后的定价系数、留在池内的费用。 | P 收到完整 2000 U，不能只记 1994 U，也不额外向用户再扣 6 U。 |
| IntentId I1 / QuoteId Q1 | 应用中这次兑换意图、基于特定状态的报价。 | 它们不是 P 保存的链上消费标记，数据库去重不能约束所有钱包交易。 |
| attempt / txHash / observation | 签名交易尝试、交易哈希、在特定区块中的观察。 | 同 nonce 替换可以有多个 hash；同一 hash 在不同块出现也要分开观察。 |
| minOut / deadline / recipient | 最低输出、执行期限、收款人。 | 不只是页面字段；原报价过期后若再次兑换，必须重新确认实际授权。 |
| receipt.status / 业务核验 | 执行回执中的成功失败标记、核对是否真的完成用户所需操作。 | status=1 的自转账不是 I1 成交，核验还要看正确合约、资产及收款。 |
| canonical / finalized | 当前规范链、按共识前提最终确定的链段。 | 普通重组可撤回未最终确定的观察；最终性前缀冲突须暂停调查。 |
| projection / revision / 游标 | 派生查询视图、本地修订号、已完整扫描到的位置。 | 版本号解决本地新旧判断，不代替区块证据；游标带区块哈希。 |
| Outbox / MQ / 消费事务 | 本地待发消息表、消息系统、接收方提交处理结果的事务。 | 发送可重复，投影不能重复生效；本地事务不等于全系统同时提交。 |
| 快照 / 增量 / 缺口 | 完整状态、逐项变化、尚未收到的中间版本。 | 完整快照可按契约替代旧版，必须逐项执行的增量则不能跳号累加。 |
| 重组 / 重新激活 / 端到端一致性 | 分支改变、旧观察再次有效、跨阶段结果最终可恢复地对齐。 | 撤回的是派生认知，不发反向 Swap；页面缺结果也不重新扣币。 |

## 把整篇文章压缩成一个故事

小林的 2000 U 已经在链上成功换成 W，但 Go 恰好在保存页面结果之前崩溃。小林看到列表空白，以为没成交。本文先划清边界：R/P 的原子性保证这次换币内部共同成功或回滚，却没有把链、数据库和通知绑成同一个提交按钮；空数据库不能把已发生的交换抹掉。

正确恢复是找回原交易身份、核对规范回执与资产证据，再把观察、查询视图、扫描位置和待发通知一起写入本地事务。重复补扫不重复展示一笔成交，通知重发也按版本处理。若尚未最终确定的区块被替换，系统撤回旧分支贡献、发布更正；之后回到原分支还要能恢复一次，不能被“以前见过”永久挡住。

如果原 Swap 已最终成功，恢复就只补证据和展示，不应让小林按新报价、有效期限再签 nonce43。余额和授权足够时，那会成为第二次真实兑换，而不是重试网络请求。全篇的闭环是允许各系统暂时不同步，但每一步都能凭原证据恢复，绝不靠再做一次经济动作修复一个页面问题。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题贯穿“业务意图 → 报价与签名 → 广播尝试 → 链上执行 → 区块观察 → 数据库投影 → 通知与最终性”。核心是划清 EVM 原子边界、链下本地事务边界与共识最终性边界，解释超时、重复、崩溃和重组时怎样恢复同一笔业务，而不是靠再次划款修复展示。

**必要前提：** 资产、金额、R/P 规则与身份沿用[总览](README.md)第 1、4 节。Go 无私钥或内部资产账本；R 不吞必要转账失败；独立 approve、Swap 内部原子性、链下事务和最终性分别划界。异常变体独立重置到公共基线，故障恢复则沿该故障继续追完。

## 第 1 层：Swap 的原子性究竟把哪些状态放在同一个提交边界？

**面试官：** 在这个单池 DEX 中，怎样保证 A 不会被扣了 U 却拿不到 W？一笔成功 Swap 共同改变哪些权威状态？

**面试者：** 我把保证建立在同一笔顶层交易的 EVM 执行上：R 拉取 A 的 2000 U，P 按实际储备校验并转出 W，更新自己的储备缓存，相关调用都成功才提交结果；任何必要环节失败必须向外传播。主例提交后 A 为 `3000 U、0.995015938219190933 W`，P 为 `1002000 U、499004984061780809067` W 原子量，Swap 不增发 LP 份额。手续费通过公式中的 997 折算有效输入，但全部 2000 U 实际进入池，不是再额外扣 6 U。代币合约保存真实余额，P 保存储备与份额，两者的正确关联由合约代码保证；原子性只保证共同提交或回滚，不会自动修正错误公式或错误收款人。

## 第 2 层：输入已经转入后再失败，哪些会回滚，哪些不会？

**面试官：** 你说各调用共同提交。假设输入已转入 P，随后输出转账返回失败或 P 的最终校验失败，之前的 approve、转账事件、gas 和 nonce 分别怎样处理？

**面试者：** R 必须识别失败并让整笔 Swap revert，不能捕获后返回成功；P 后续校验失败也必须产生相同的外层失败。在这笔交易内部，U/W 转移、储备更新、被消耗的 allowance 和日志一起回滚，不能把执行跟踪里暂时出现的 Transfer 当成已提交日志。独立 nonce 41 的 approve 已经先完成，它不属于本次回滚范围，所以授权仍可能存在。若 nonce 42 的失败交易已经被包含，它依旧消耗该 EOA nonce，并按实际执行消耗 ETH gas；交易被拒绝、从未包含则不能据此断言已经扣过 gas。这些链级记账与 Swap 内部业务回滚分属不同边界，因此“失败就完全没有任何状态变化”是不准确的。

## 第 3 层：链上能回滚，为什么不能把链和数据库包进一个事务？

**面试官：** 上一答把业务回滚和链级记账分开了。现在链上执行可能成功，但 Go 广播请求超时、数据库没有保存结果，能否回滚数据库事务就当交易未发生？

**面试者：** 不能，数据库提交不参与 Ethereum 的执行与共识，回滚本地事务不会撤回已传播的签名交易。应保留不同身份：`IntentId=I1` 表示用户这次业务目的，`QuoteId=Q1` 表示 H0 上的一次报价；Attempt 记录 `(chainId,A,txNonce=42,txHash)`，包含后的日志观察记录 `(chainId,blockHash,txHash,logIndex)`，展示另有 `projectionRevision`。这些对象不能压成一个“订单成功”字段。广播超时只产生传播结果未知，应查询和恢复既有 Attempt；报价、数据库占位均未冻结链上资金。Go 的职责是让本地认知收敛到链上事实，而不是要求链随数据库回滚。

## 第 4 层：传播结果未知时，怎样重试而不执行两次业务？

**面试官：** 你保存了 Attempt，但查询节点暂时也找不到 txHash。为了让 I1 尽快完成，重复广播、同 nonce 加价和换新 nonce 重试各有什么差别？

**面试者：** 相同原始交易重复广播的 txHash 不变，仍是同一个候选，不会因此多执行一次。用户重新签署同 nonce 42 的加价替换交易会产生新 hash，应在 I1 下保留竞争关系；同一条最终链前缀中同一 A 的 nonce 42 只能被一笔交易消费，胜出者还可能是失败交易或取消交易，必须核验语义。若另发 nonce 43，则两笔可能按顺序都成交，因为 P 没有消费 I1 的链上幂等屏障。只要余额和 allowance 足够，5000 U 足以支付两次 2000 U；不能拿某次刚好不足的授权当通用去重。节点暂查不到也不证明原交易从未传播，所以未知状态不能自动升级成新 nonce 重试。

## 第 5 层：找到 status=1 的收据以后，为什么还不能直接落业务成功？

**面试官：** 你说同 nonce 胜出者也可能不是目标 Swap。若某个候选有 `status=1`，怎样证明它真的完成了 I1，而不是成功调用了错误入口？

**面试者：** 我先核对链、发送者 A、nonce 42、目标 R 和解码后的 U/W、输入量、收款人、minOut、deadline，再验证目标 P 的交换事件与指定代币合约的转账、储备变化一致。`status=1` 只证明外层未 revert，成功的零值自转账显然不能算 I1 成交。核验数量要用实际执行前状态，并区分单笔执行边界与区块末状态；同区块还有后续 Swap 时，区块末 `balanceOf(P)` 不等于本笔刚结束的余额。得到相符证据后才能标记“当前 canonical 已包含并执行成功”，仍保留 blockHash 和观察身份。此时还没有解决最终性，也没有保证数据库与通知已经同步。

## 第 6 层：链上结果已核实，进程在数据库与通知之间崩溃怎么办？

**面试官：** 上一答已经形成可信的链上观察。假设数据库更新完成后进程崩溃，通知还没有发出，或者恢复时重复读到同一日志，如何避免漏通知和重复改投影？

**面试者：** 我会在一个本地数据库事务中写入完整扫描块的已核验观察、更新业务投影及其 revision、推进扫描游标，并插入待发通知的 outbox；观察以 `(chainId,blockHash,txHash,logIndex)` 做唯一身份，整笔业务效果在相关证据齐全后才应用一次。提交后崩溃，恢复扫描 outbox 继续发送；提交前崩溃，重新读取观察并重做本地事务。发送后未标记成功也会重复，所以消费者按事件身份和 revision 去重，消息确认放在消费事务提交之后。这个协议解决的是本地持久化与至少一次交付，不是链、数据库、MQ 的全局原子事务；MQ 不可用可以延迟通知，但不能因此重新执行 Swap。

## 第 7 层：本地事务已经提交，区块重组怎样撤销旧投影？

**面试官：** 你已经把观察、投影和 outbox 共同提交了。但这笔成功观察所在区块后来离开 canonical 链，数据库事务不能跟着链自动回滚，该怎样处理？

**面试者：** 需要额外的分支校正协议，而不是假装原本地事务从未发生。我保存父哈希和处理检查点，发现新头不接续时核实共同祖先，将被移除分支的观察失活，撤销其投影贡献，并在本地事务中提高 revision、写出更正通知。不能只依赖一次 `removed` 推送，断线可能漏掉它。大范围重建要完成后再原子切换可见版本，不能展示两条历史的混合结果。交易在新块重新包含时，按新 blockHash 和实际结果重新观察；旧观察若再次回到 canonical，也必须支持重新激活，而非被唯一键永久屏蔽。此前的输出量不自动沿用。这里撤销的是数据库认知，不是给链发一笔反向 Swap。原链上执行痕迹离开 canonical 分支，也不能当成 A 已经永久获得了那笔 W。

## 第 8 层：更正通知先到、旧成功通知后到，会不会又把页面改错？

**面试官：** 上一答会产生更正事件。如果 MQ 先交付 revision 8 的更正，再迟到交付 revision 7 的旧成功，或者同一 txHash 在新块重新出现，消费者应该怎样裁决？

**面试者：** 消费者以业务投影标识记录最后应用的 revision，较旧 revision 不能覆盖较新状态，重复 revision 必须核对事件身份和内容一致性。对于允许跳过中间版本的页面通知，我发送带 revision 的完整快照；如果发送的是必须逐项执行的增量，则发现缺口要先补齐，不能直接跳号相加。同一 txHash 重新包含于新块时，观察身份因 blockHash 不同而改变，不能全局按 txHash 丢弃新观察。生产者仍保证某一当前投影只应用一份有效的 canonical 效果。revision 只是本地发布顺序，不是区块高度，也不赋予链上终局性；它解决迟到消息覆盖，最终完成仍需要共识证据。

## 第 9 层：投影和消息都收敛了，什么证据才能把成交标为最终完成？

**面试官：** 你用 revision 解决了链下乱序，但业务方想在等到若干区块后不可逆地确认完成。为什么不能直接配置“12 个确认即 finalized”？

**面试者：** 固定区块数只是经验等待策略，不能等同于 Ethereum PoS 的 finalized 语义。我会从经验证节点取得 finalized 区块，核实包含本笔交易的区块在它的祖先链上，再结合已完成的调用语义和资产核验，将业务标成最终完成。仅比较两个区块的高度不够，相同高度可以属于不同分支；交易仍在某条非 canonical 分支也不算完成。网络暂时不推进最终性时，应保持“已包含、未最终确定”，不能用本地计时补造最终证据。若出现互相冲突的 finalized 事实或既有最终祖先关系被破坏，已超出普通重组恢复范围，应停机并人工处置，不能照常回滚重发来掩盖安全假设失效。

## 第 10 层：链上已最终成功但本地全无结果，怎样恢复而不再扣一次钱？

**面试官：** 既然最终性给出了不可随意撤销的边界，假设 Swap 最终成功后索引进程崩溃，本地仍只有 I1 和原 Attempt，没有成交投影，恢复闭环应该怎么走？

**面试者：** 恢复从原 Attempt 的 hash 和同 nonce 候选关系查询开始，核对 canonical 收据、R/P 调用语义、币转移与 finalized 祖先关系，必要时从持久检查点补扫区块。证据相符就通过同一套观察幂等键和本地事务补建投影、outbox，再让通知按 revision 收敛；不再签名划款，不做管理员退款，也不根据空数据库发新 nonce。验收应能解释 I1 最终对应哪一个实际 Swap、数量依据哪组执行前状态、哪些观察已失效，以及页面为什么展示当前版本。允许暂时缺索引或缺通知，禁止把缺展示当成没成交、把独立 approve 当成可回滚、把同一效果重复计入当前投影。端到端一致性是证据可恢复地收敛，不是所有系统瞬间同时提交。

## 本题收束

**机制：** 单笔 EVM 交易负责 U/W 资产、P 储备及本次内部日志的共同提交；数据库事务负责观察、投影和 outbox 的共同提交；观察身份、业务身份和 revision 负责去重与校正；canonical 分支跟踪和 finalized 祖先关系负责区分当前有效与最终完成。独立 approve 和 ETH gas 不属于 Swap 内部业务回滚范围。

**易错边界：** 链上原子不跨数据库或 MQ，事务成功也不自动等于业务语义正确；`status=1`、canonical 已包含、通知已送达和 finalized 是不同事实。IntentId 不提供池级幂等，deadline 不证明过去未成交，txHash 也不能代替带 blockHash 的观察身份。普通重组更正不能用来处理最终性安全假设被破坏的情况。

**具体反例验证：** 只设置“链上主例 Swap 已成功并达到 finalized，但本地成交事务尚未写入便崩溃”这一故障。若恢复逻辑因数据库查不到成功，错误引导 A 按新报价、新有效期限重新签署 nonce 43，且剩余授权与新执行约束均满足，A 的 3000 U 仍可能再次被扣 2000 U，造成非预期的第二次兑换；Go 不能自行签名。这里不假定旧 Q1 期限一直有效：仅换 nonce 复用已过期载荷会失败，不能用它证明第二次成功。正确恢复只补观察、投影与通知：A 保持 `3000 U、0.995015938219190933 W`，P 保持 `1002000 U、499004984061780809067` W 原子量，另计实际 ETH gas；重复补扫不新增 Swap，也不重复应用资产展示效果。这是手工推演的验收条件，不是声称已执行工程测试。
