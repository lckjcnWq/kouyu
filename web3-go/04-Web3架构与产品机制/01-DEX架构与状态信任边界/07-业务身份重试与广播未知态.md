## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| DEX / Swap / A / P | 去中心化交易系统、换币动作、用户地址、池。 | A 用 2000 U 换 W；P 不保存应用意图的去重标记。 |
| I1 / Q1 / payload | 这次应用意图、对应报价、请求的实际业务内容。 | 同一编号却换了金额或收款人是冲突，不能用最后一次覆盖。 |
| requestKey / 唯一约束 | 请求去重键，以及数据库不允许重复登记同一身份的规则。 | 约束应用受理，不会阻止用户绕过应用另签交易。 |
| attempt / chainId / sender | 一份交易尝试、链身份、发送者。 | 尝试要能追溯到确切链、A、序号、签名内容和报价。 |
| nonce / txHash / 签名字节 | 账户交易序号、交易哈希、可传播的完整签名交易内容。 | 同字节重广播 hash 不变；改费重签可变 hash，同 nonce 仍属竞争候选。 |
| 广播未知态 / RPC / already known | 未获确定传播结果、节点接口、节点已认识该交易的响应。 | 都不能直接证明成交或未成交；先持久化原交易再发送才能恢复。 |
| 加速 / 替换 / 取消 | 重签提高费用、用同 nonce 竞争、让非兑换交易占用同一 nonce。 | 新候选被某节点接受，不等于旧候选已从全网消失。 |
| latest nonce / pending nonce | 当前链状态中的下一序号、节点结合待处理交易给出的序号视图。 | 前进不证明原 Swap 成功，还可能是取消或已包含失败。 |
| minOut / deadline / recipient / calldata | 最低输出、期限、收款人、合约调用数据。 | 纯加速不偷偷改经济载荷；过期不能证明过去没成交。 |
| approve / allowance / revert / Gas | 设置额度、可用授权、执行回滚、执行资源。 | Swap 内部回滚不撤销此前独立授权；已包含失败仍耗序号和 ETH 费用。 |
| CAS / 行版本 / 租约 | 比较预期版本再写入、记录修订号、有时效的处理资格。 | 避免两个恢复进程互相覆盖，但不能撤销已签链上交易。 |
| observation / blockHash / logIndex | 特定分支内的观察、区块哈希、日志序号。 | 同交易在另一区块重入要重核验，不能只按 hash 永久去重。 |
| canonical / finality / indexed / revision | 规范归属、最终性、索引进度、本地修订号。 | 分开报告链事实、承诺强度和页面进度，不压成一个 completed。 |

## 把整篇文章压缩成一个故事

小林连续点了两次兑换，系统都识别为 I1，但会核对两次金额、收款人和报价是否完全一致。钱包签好的 nonce42 交易先保存原字节和本地计算的 hash，再广播；这样即使发送后崩溃，系统至少知道自己到底发了什么，而不是只记住“有人想买币”。

广播接口超时，查询也暂时为空。正确动作是继续追踪或重广播同一份交易；若小林选择加速，则把同 nonce 的新旧 hash 都留下，看规范链最终包含谁。不能因为 nonce 前进就猜原兑换成功，也不能因为新候选已接收就宣称旧候选已经取消；换新 nonce43 则可能让两笔兑换都成功。

后来系统在期限之后才补到历史，发现原交易早在 t0+12 已成功。此时过期并不能推翻过去，页面应该归并原结果、继续核验最终性和同步，而不是宣称没发生。只有原结果按约定证据关闭后，新的报价、确认和签名才是新一轮兑换；它不是网络重发，也不是 Go 可以代用户做的补偿。

**流程位置与核心机制：** 本题覆盖“兑换意图登记 → 报价与钱包签名 → 原始交易登记 → 广播 → 未知态恢复与替换识别”。重点不是介绍 RPC 方法，而是区分业务身份、签名交易身份与链上观察身份，明确每一种重试究竟重复了什么。回执验证和最终性详见[大问题 8](08-执行回执最终性与重组边界.md)，索引投影和跨模块交付详见[大问题 9](09-索引投影与跨模块状态同步.md)。

**必要前提：** 资产、完整数值和执行保护见[总览](README.md)第 1 节，身份与不变量见第 4 节。本题围绕 I1/Q1 和 A 的 nonce42 恢复；P 没有 intentId 屏障，Go 没有私钥。普通 approve 是独立前置交易，不是 permit，也不与 Swap 共同回滚。每个异常变体独立从主例改变条件。

```text
登记 I1 与不可歧义的业务参数，关联 Q1
    ↓
A 的钱包确认并签名；服务核验、保存签名字节与本地计算的 txHash
    ↓
广播原交易
    ├─ 返回哈希或 already known → 已知传播线索，不等于执行成功
    └─ 超时、断连 → 广播未知态，保留原 hash 与 nonce 42
                         ↓
              跟踪原 hash、同 nonce 候选及规范链历史
                         ↓
              区分原交易、同载荷加速、其他交易与仍然未知
                         ↓
              由规范回执、业务核验与最终性继续收敛
```

## 第 1 层：为什么一个 requestId 不能代表整笔链上兑换？

**面试官：** A 点击兑换后又点了一次，你怎样判断这是同一笔业务，为什么不能只按 txHash 或 requestId 去重？

**面试者：** 我会先分清需要保持不变的对象。I1 表示用户这一次兑换意图，Q1 表示服务在某个链状态和有效期下给出的报价；它们都不是已经发生的链上成交。签名交易属于执行尝试，至少记录 `(chainId,A,nonce,txHash)` 及其替换关系；一次被观察到的日志则用 `(chainId,blockHash,txHash,logIndex)` 标识。页面投影还有自己的 revision，它描述本地认知的版本，不是新的链上交易。把这些身份混为一个 requestId，会让换费后的新哈希被误认成新业务，也会让重组后的历史观察覆盖当前结论。

主例中，I1、Q1 关联的是 A 用 2000 U 换 W、收款人为 A 的授权语义，nonce 42 的交易才承担执行。服务可以让同一个 I1 的重复请求返回已有进度，却不能仅凭这个本地记录保证链上只执行一次。P 并不保存 intentId 屏障，A 仍能在钱包外另签不同 nonce 的兑换。因此这里的保证是应用内识别和安全恢复，不是应用数据库替用户钱包创造链上防重放合约。

## 第 2 层：同一意图的并发提交怎样在签名前收敛？

**面试官：** 既然 I1 是应用内身份，如果两个请求同时带 I1 进来，其中一个偷偷把 recipient 或金额改了，怎样处理才不把不同授权混在一起？

**面试者：** 在这个模型中，我会把 I1 绑定到经过归一化的业务内容，并把“登记身份与保存内容”放在同一个本地数据库事务里。金额先转换成整数原子单位，记录 chainId、A、U/W 合约、R/P、精确输入数量、recipient，以及关联 Q1 的 minOut、deadline 和报价状态锚点。相同 I1、相同内容的并发调用命中唯一记录后，返回同一个已登记结果；相同 I1 却改变 recipient 或数量，应返回内容冲突，不能以最后一次写入为准。事务提交以前也不向调用方承诺它已经成为可恢复的业务记录。

这里要区分意图内容与每份签名交易的完整字段：同 nonce 加速可以有不同费用和不同 txHash，却不能悄悄改变兑换载荷。Q1 失效后的新报价也不能无声覆盖已经交给钱包的旧授权，应作为显式的新版本或新意图让用户重新确认。数据库唯一约束只约束本服务认可的记录，无法阻止钱包另行签名；它更不能代替钱包对实际 to、data、value 和网络的最终核验。

## 第 3 层：为什么要先保存签名字节，再调用广播接口？

**面试官：** 你说重复请求应该能恢复同一笔交易。如果服务发出广播后、保存 txHash 前崩溃，重启后怎么知道链上有没有那笔 swap？

**面试者：** 我会把这个失败窗口前移关闭：收到 A 的签名交易后，先本地解码，校验签名恢复出的发送者为 A、chainId 为 1、nonce 为 42、to 为 R，并确认 data 中的资产、2000 U、minOut、deadline、recipient 与已确认的 I1/Q1 一致。普通 ERC20 兑换不应顺带附带未经同意的 ETH 转账。txHash 可以直接由签名后的原始字节计算，不需要等 RPC 返回。把原始字节、哈希、业务关联和待广播状态持久化成功以后，才允许广播工作继续。

这样，保存后未发送就崩溃，恢复时可发送原字节；发送后未写入网络响应就崩溃，恢复时仍知道原 hash 与 nonce，先查原交易，再决定是否重广播。数据库事务不能把公网 RPC 一起包进去，所以不能消灭“网络是否接收未知”，但可以避免“连原来发了什么都不知道”。若钱包绕过服务自行发送而服务从未收到签名，必须回到 A 的规范链交易历史和用户提供的哈希补关联，不能伪称服务的登记顺序约束了钱包的全部行为。

## 第 4 层：广播超时后为什么不能换一个 nonce 重发？

**面试官：** 现在原字节和 hash 已经保存，但广播调用超时，按 hash 查询也暂时为空。为什么不直接用 nonce 43 重试，提高成功率？

**面试者：** 因为广播超时只说明服务没有拿到确定响应，不说明原交易没有到达节点，更不说明它没有被其他节点传播或已经执行。主例应继续跟踪原 hash 和 A 的 nonce 42，查询相关回执、交易以及规范区块；必要时向已说明信任条件的其他节点交叉核对。只要没有获得相反的确定事实，同一份原始签名字节可以再次广播，它仍是同一个哈希、同一个 nonce 的同一笔交易，而不是第二笔独立兑换。节点返回 already known 也只是传播线索，不是成交凭证。

nonce 43 则是新的可执行交易身份。如果 nonce 42 随后先成交，43 仍可能接着执行，A 有足够资产和授权、且两次执行各自满足保护条件时，就会发生两笔兑换。一次空查询、一个节点的 pending 池缺失或 latest nonce 暂时未变化，都不足以排除这个窗口。服务没有私钥，也没有本地资金冻结能阻止该执行；因此未知态的动作是保留原证据、跟踪或重广播，而不是把新的签名请求伪装成对原网络调用的安全重试。

## 第 5 层：同 nonce 加速为什么仍然需要保留两份交易？

**面试官：** 你不允许偷偷换 nonce，那么 A 在钱包里给 nonce 42 加速、生成新 hash 时，怎样既允许加速又不把旧 hash 当成已经取消？

**面试者：** 加速需要 A 再次签名，Go 服务不能替用户修改旧签名。为了维持“原业务的费用替换”这个语义，我会要求 chainId、发送者、nonce、to、data、value 以及原业务执行约束保持不变，只按规则调整交易费用字段。新签名产生新 hash，登记为同一个 nonce 竞争组中的另一个 attempt，并记录“意图替换哪个候选”，但保留旧 hash 的原始内容和全部观察。某个节点接受新交易，并不意味着全网删除旧交易；其他出块者仍可能拿到旧候选。

同一条有效规范链里，A 的 nonce 42 最多由一笔交易消耗，究竟是哪一笔需要看规范区块中的实际交易，而不是看谁最后调用了加速接口。若新旧两笔业务载荷一致，无论哪笔最终进入，兑换含义都一致；如果所谓加速修改了 recipient、minOut 或调用目标，就已经不是这里允许的纯费用加速，必须重新确认授权并另行分类。发生重组时，旧分支和新分支还可能分别包含不同候选，因此替换关系是跟踪线索，不是脱离区块上下文的永久胜负结论。

## 第 6 层：账户 nonce 前进为什么不能证明原兑换成功？

**面试官：** 既然最终要查规范链，现在节点显示 A 的 latest nonce 已经超过 42，而原 hash 没有回执，是否可以直接认定新 hash 已完成原 swap？

**面试者：** 不能。latest nonce 前进，只能在该节点认可的当前链状态下说明某些 nonce 已被消耗，不能说明消耗 nonce 42 的交易一定是发给 R 的那笔兑换。A 可能在钱包里用同 nonce 发出取消转账，也可能签了另一份调用；即使确实调用了 R，也可能 status 为 0。pending nonce 的含义还取决于节点的交易池视图，不能把它当成已经包含的历史证据。我的下一步是定位当前规范历史中 A、nonce 42 对应的确切交易，拿到完整载荷和所属区块，再核对业务含义与回执。

标准 RPC 并不天然提供一个覆盖所有历史的“按发送者和 nonce 查询”索引，可以借助本地索引、扫描有界区块区间或外部检索定位候选，但检索结果仍要回到规范区块核验。如果查到新 hash 的 to、data、value 与原业务一致，才能关联为同语义尝试；若是给自己转零 ETH，就标记为其他用途的 nonce 占用，而不是成功兑换。在历史尚未找到前应保留“nonce 已消耗、用途待核验”，不能用猜测补齐成交记录。

## 第 7 层：取消和过期为什么都不能立即关闭未知态？

**面试官：** 如果确认另一个候选是取消交易，或者已经超过 Q1 的 deadline，是否就能向 A 保证这笔兑换从未发生，再让他重新兑换？

**面试者：** 我会分别判断，不把这两个变体叠在一起。取消变体只把 nonce 42 的竞争候选换成 A 自转零 ETH 等非兑换交易。它与原 swap 争夺同一个 nonce，取消进入当前规范链后，原 swap 不能再进入这条分支；但在取消最终确定之前仍有分支变化的风险，原 swap 也可能先赢。服务应报告当前证据，而不是把“钱包点了取消”说成已经撤销链上执行，更不能退回已经支付的 gas。

过期变体不增加取消交易，只把观察时间推进到 deadline 之后。R 的条件是执行区块时间严格小于 `t0+120`，所以在 `t0+120` 及之后执行原载荷会拒绝；但它完全可能在主例 `t0+12` 已成交，而服务尚未索引到。现在过期只能限制未来满足条件的执行，不能证明过去没有成交。必须补查原 hash、同 nonce 实际历史及其最终性；若原交易尚未包含，它还可能以失败交易消耗 nonce 和 gas。新的兑换是新的用户决策，不能用“报价已过期”替代旧交易结论。

## 第 8 层：已包含失败后，新的兑换与网络重试有什么不同？

**面试官：** 你要求补查历史。如果终于查到 nonce 42 的 swap 为 status 0，是否可以释放本地冻结的 2000 U，并自动用 nonce 43 再执行一次？

**面试者：** 这里本来就没有本地冻结的托管资产可释放。若 nonce 42 在当前规范链中执行失败，R 不捕获失败继续，swap 内部的 U/W 转移、P 储备写入和日志都会回滚，不存在已付 U、部分收到 W 的正常结果。但作为已包含的失败交易，它仍消耗 A 的 nonce 和 gas；此前独立成功的 nonce 41 approve 不会随着它回滚。在没有其他资产活动的这个变体里，A 的 U/W 仍是 5000 U、0 W，授权保留为 swap 执行前的结果，ETH 则因 gas 减少。

我会把“当前规范失败”与“失败已最终确定”分开。若以避免跨分支重复为目标，新一轮提交应先等原结果按既定最终性策略关闭；不能在原失败仍可能被重组掉时自动发新 nonce。之后重新检查池状态、A 的余额与 allowance，重新报价，例如显式建立 I2/Q2，并由 A 再次确认、签名。旧 Q1 可能已经过期，失败原因也可能没有消失。nonce 43 的新交易是新授权和新执行机会，不是重发 nonce 42 原始字节，更不是服务有权替钱包做的补偿。

## 第 9 层：服务自身的并发恢复能保证到哪里？

**面试官：** 假设你坚持新交易必须重新授权，但两个恢复进程同时处理 I1，或者 A 完全绕过应用在钱包里提交，怎样准确描述“不会重复兑换”的保证？

**面试者：** 对服务内部，我会让 I1 的处理采用带版本的条件更新，并让已确认的签名交易登记有唯一约束。恢复进程先读取持久记录，只能推进自己持有的有效版本；租约过期或竞争失败的进程不能把旧判断写成最新结论。两个广播工作者偶尔把同一份原始字节都发送出去，不会因此产生两笔同 nonce 的规范执行，所以不必把网络调用强行伪装成恰好一次。重要的是它们不能各自基于未知态生成不同 nonce 的新业务，也不能以空查询覆盖已经保存的回执证据。

对钱包外操作则必须承认边界：在授权额度足够的条件下，A 可自行签 nonce 42 和 43 的两笔 2000 U 兑换；P 没有 I1 屏障，只要各笔按其实际执行前状态满足 minOut、deadline、余额和授权，就可能都成功。应用 unique 不参与 EVM 裁决。若要协议级意图去重，必须改变合约或账户模型，让执行入口验证不可重复的授权标识，这已经不是冻结教学基线。本题只能保证服务不把传输重试扩大成额外授权，不能保证用户主动发出的另一笔交易永远不会执行。

## 第 10 层：怎样把一连串未知响应恢复成可解释的结果？

**面试官：** 沿用你划定的边界：I1 广播超时，恢复进程重广播原字节，钱包随后同 nonce 加速，旧 hash 又先出现在区块里。你怎样给出一个不会自相矛盾的最终答复？

**面试者：** 我会先确认这一串动作只形成 I1 的多个传播动作和两个同 nonce 候选，而不是多个新意图。保存旧 hash 与加速 hash 的签名载荷，查验旧 hash 所在区块是否仍属当前规范链，再判断回执 status 和业务匹配。如果旧候选在 `t0+12` 规范执行成功，就报告“原候选已包含、兑换业务核验通过”；加速候选只能标记为同 nonce 竞争未胜出，不能因为它是最新提交而把业务判为失败。反之，旧区块脱离规范链时应撤回当前成功投影，保留历史观察并继续跟踪两份候选。

答复还应分别给出 included/current canonical、执行 status、业务核验、finality 和 indexed 的状态，不把任一个单字段命名为包办所有含义的 completed。达到经验证节点的 finalized 祖先条件后，才能按既定承诺报告最终结果；索引尚未追上时，应明确展示水位而不是再发一笔 swap。每次本地判断带 revision 和来源区块，恢复只从持久证据续做。这个闭环允许网络响应重复、缺失和迟到，却禁止在没有新授权的情况下扩大执行次数，也禁止用覆盖旧记录来掩盖分支变化。

## 本题收束

- **讲透的机制：** I1 管业务意图，Q1 管报价上下文，attempt 管具体签名交易及 nonce 竞争，observation 管区块内证据，revision 管可撤回的本地认知。先持久化可恢复的签名内容，再广播；未知态先跟踪原 hash/nonce，可重广播同原始字节，同 nonce 纯费用加速必须保留竞争历史。
- **最易答错的边界：** RPC 超时不是未发送，查无交易不是确定丢失，账户 nonce 前进不是本 swap 成功，deadline 已过不是历史未成交。取消和替换都要看规范历史。应用唯一键不是 P 的链上意图屏障，独立 approve 也不会因 swap 失败回滚。
- **具体反例验证：** 手工推演“原 hash 广播超时，但在 `t0+12` 已成功；服务在 deadline 后才补到历史”。正确系统仍归并到 I1、nonce 42 的原成功执行，继续核验最终性和索引状态；若系统因为超时或过期生成 nonce 43，或把 I1 标成从未成交，就已经违反本题保证。另将原候选单独改成规范 status 0，检查 U/W 回滚、gas 与 nonce 消耗、独立 approve 保留，不能生成部分成交或内部余额退款。
