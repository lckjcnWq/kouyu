## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| DEX / Swap / A / P / U/W | 去中心化交易系统、换币动作、用户、池、两种教学代币。 | 本文只索引真实兑换，不维护一份能代替链上资产的托管余额。 |
| 索引 / projection / 权威事实 | 搜集链数据、派生查询视图、由链执行与共识规则确定的状态。 | 页面不见一笔兑换，可能是索引缺口，不是链上还欠一笔转账。 |
| I1 / Q1 / attempt | 用户意图、报价、签名交易尝试。 | P 不保存 I1，观察还须与用户意图正确关联，不能看日志名就猜归属。 |
| observation / blockHash / logIndex | 某分支的观察实例、区块哈希、日志序号。 | 身份同时包含链、区块、交易及日志位置，不能只凭 txHash 区分全部事实。 |
| canonical / active | 当前接受的规范历史、观察当前的规范有效性。 | active 只是一项资格，不表示所有业务关联、核验和投影都完成。 |
| appliedContribution / CAS | 已经记入某投影的贡献、核对预期版本后再写入。 | 比较目标与已应用效果，只补差异；补关联时也能补记，不伪造重组。 |
| revision / sourceRevision / transitionId | 本地修订号、源流修订号、一次状态转换身份。 | 激活、撤回、再激活是不同变化，不能只按原观察编号永久消费一次。 |
| 游标 / 水位 / parentHash | 扫描位置、完整处理进度、父区块哈希。 | 抓到第一条日志不算整块完成；扫描完整与业务语义完整分别记录。 |
| Outbox / Inbox / 至少一次 | 源端待发记录、下游已处理记录、允许传输重复的交付方式。 | 本地事务防双写丢失，重复消息不能重复改变投影，但不是跨系统全局恰好一次。 |
| 重组 / 共同祖先 / 重新激活 | 规范分支改变、分叉前共同位置、旧观察重新有效。 | 先撤旧贡献再应用新历史；同一旧块回来也须恢复贡献。 |
| generation / 发布指针 | 不可见的重建版本、指向当前对外完整版本的位置。 | 大范围重组先后台建好再切换，不能一边查询一边混用两条历史。 |
| 增量 / 快照 / 缺口 / token | 逐项变化、完整状态、中间版本缺失、共同查询版本标记。 | 增量有缺口要补齐；组合查询须在相同分支和完整水位，不各取 latest。 |
| finalized / 解码器 / 精度 | 按共识前提最终确定、解释事件数据的程序、金额最小单位规则。 | W 为 18 位小数，解码错就重建投影，不改变链资产；最终性冲突另行暂停。 |

## 把整篇文章压缩成一个故事

小林已经用 2000 U 换到 W，但交易列表和池页面不同步。索引服务先把确切区块里的回执和事件保存下来，再在一个本地事务里发布观察、查询视图、扫描位置和待发消息。这样进程中途崩溃，要么还停在完整旧版、可以重做，要么已经提交完整新版，不会出现游标跳过但结果没写的空洞。

接着 H1 的兑换先有效、被重组撤回、后来又重新有效，源端分别发布 revision101、102、103。下游若先拿到 102，应持久等候并补齐缺失的 101，不能乱加减；103 则必须恢复一次效果，不能因“这条观察见过”而丢弃。若仅仅是小林后来补了交易 hash，让原本已有效的池观察终于关联 I1，也要补记业务投影，不需要编造一次重组。

如果只是本地解码精度算错，服务在不可见的新版本重建，再让各页面在共同水位上切换。它重放的是链事实的解释，不是重新签名换币，小林不会因此再花 2000 U。全文的重点是把“收到、有效、核验齐全、已应用、已发布”分开，才能同时防重复、防遗漏、支持撤回和补证。

## 第 1 层：本地“交易成功”和链上“交易成功”谁说了算？

**面试官：** 链上兑换已经成功，为什么还要索引服务？本地交易表、池表和用户余额如果不同步，哪一个有权决定真实资产？

**面试者：** 索引服务解决的是检索、聚合与展示效率，不接管 EVM 的资产裁决权。在这个模型中，U/W 余额和 P 储备由当前规范链状态决定，Go 的交易表只是从经核验的区块、回执、事件和状态中生成的可重建投影。I1 是服务登记的业务意图，Q1 是报价对象，它们的链下身份由服务维护；某个 attempt 是否真实兑换，则必须回到确切链上证据。链上成功但列表未出现，首先是索引延迟或缺口，不是服务还没有完成一笔内部转账。

主例成功后，无其他相关资产活动时，A 是 3000 U、995015938219190933 W 原子，P 是 1002000 U、499004984061780809067 W 原子，gas 从 ETH 另扣。服务不能为了页面好看创建“可用 W”并声称已经给 A 补余额，也不能修改链上金额去匹配旧缓存。我会让查询返回来源区块、当前规范性、最终性和索引水位，让调用方知道投影反映的是哪个版本。若需要展示链上余额缓存，也必须标明它的状态锚点和覆盖范围，不把只跟踪本产品 swap 的记录表冒充 A 的完整钱包账本。

## 第 2 层：哪些身份和水位才能让投影可追溯？

**面试官：** 你要让查询说明版本。只保存 txHash、一个 success 字段和最后扫到的区块号，为什么不够？应该补哪些有实际用途的字段？

**面试者：** txHash 不能区分它曾在哪个分支被观察到，区块号也不能区分同高度的两个区块。我会分开保存 I1/Q1、attempt 的 `(chainId,A,nonce,txHash)` 及替换关系、observation 的 `(chainId,blockHash,txHash,logIndex)`。回执级结果另带所属 blockHash、status 和业务核验结果，日志本身不是全部交易状态。observation 保留 canonical active 状态和每次激活、撤回的历史；各投影另存所依赖的关联、核验版本以及 appliedContribution/已应用版本，不能把 active 当成“所有投影均已记入”。查询投影保留单调递增的 revision；本地版本前进不要求链高度前进，重组回到较低高度时 revision 仍须增加。

游标至少包含 chainId、已完整处理的 blockNumber 与 blockHash，必要时还包括块内位置，并验证 parentHash 连续性。查询发布水位需要说明规范锚点、完成的投影集合及对应 revision；finalized 锚点单独保存，不把“已抓到日志”当成“已最终确定”。如果 observation 与 I1 的关联缺失，应登记待核验事实，不能靠事件名字猜出 intentId，因为 P 并不存 I1。保存这些字段不是为了堆数据，而是为了回答“这条成功来自哪个区块、是否仍有效、当前页面是否已经包含它”，并为撤回、重放和跨模块缺口检测提供确定依据。

## 第 3 层：扫描一块时怎样关闭投影和游标之间的崩溃窗口？

**面试官：** 字段齐了，但进程更新完兑换记录、还没更新游标就崩溃，或者游标先更新、池表还没写完。你怎样避免重复和遗漏？

**面试者：** 在这个教学模型中，我会把某个规范区块的待发布变化放进一个本地数据库事务：核对当前游标和父块；保存原始观察及其核验、关联版本；按规范归属更新 active；根据各投影自己的资格和已应用记录更新兑换、池投影；写入 Outbox；最后推进游标、revision 和发布水位，一并提交。RPC 抓取可以在事务外进行，但提交时必须检查分支锚点和游标版本没有被其他进程替换，不能拿过期扫描结果覆盖新判断。一个块有多条相关日志时，要确认本次范围已完整抓取，不能拿到第一条就把整块标成处理完成。链数据扫描完整与 I1 关联/语义核验完整分别记录，不能把前者冒充后者；待核验对象必须有持久待办，不因扫描游标推进而失去恢复入口。

这样，提交前任意位置崩溃，事务都没有对外发布，恢复从旧游标重读；提交后崩溃，投影、观察状态、待发消息和新游标已经共同存在。对每个投影，我会由 active、所需核验与关联版本算出目标贡献，再与 appliedContribution 比较，仅把差异及新应用版本提交；重复相同输入无操作。若池观察已 active，但钱包后来才补 hash、关联 I1 或核验随后通过，仍由同一补记路径重新计算目标贡献，以 CAS 检查观察/关联/核验与投影版本，在一个本地事务内补兑换记录、提高 revision、写 Outbox 并更新语义完成水位；不伪造 inactive→active，也不倒退扫描游标。这里的本地事务不涵盖链、RPC 和下游数据库，不能承诺跨链原子提交。若单块数据太大，必须另行设计不可见的构建区与发布点，不能仅把事务拆开后仍声称消费者永远看不到半块状态。

## 第 4 层：重组撤回与新分支应用怎样共同发布？

**面试官：** 你用一块一个本地事务解决了正常扫描。若发现 H1、H2 已被 H1'、H2' 替代，反向撤回旧块以后、正向应用新块以前崩溃，查询会不会暴露一半重组？

**面试者：** 小型教学方案可以把一次已确定范围的分支切换作为单个本地事务：校验旧发布锚点，找到共同祖先 H0；按旧分支逆序撤回 active 观察和相应投影；按新分支正序应用新事实；同时写入有序变化、推进新 blockHash 游标、revision 和发布水位，最后提交。事务前查询读到完整旧版本，事务后读到完整新版本。撤回不是简单减一个兑换额就算完成，池储备投影要恢复前镜像或从共同祖先重放；更不能把仍留在另一个有效分支的事实重复减去。

重组范围太大不能放进同一事务时，我会构建新的不可见投影 generation，记录目标锚点、分段进度和恢复任务；旧发布指针保持不动。崩溃后从构建检查点继续，直到新 generation 的观察状态、全部目标投影、待发布变化及新水位完整，再用一个本地事务切换可见指针。generation 的局部写入也不能提前污染旧版本的可见 active 集合。链在构建期间又变化，就重新校验目标是否仍规范，不满足则重建或追到新目标。不能把已公开游标先移到 H2'，却让交易列表还留着 H2 的成功事实。

## 第 5 层：永久去重为什么会丢失重新规范化的事件？

**面试官：** 你保留了 active 集合。如果旧 H1 被撤回后又成为规范区块，同一个 observation 的唯一键已存在，怎样避免既不重复累计、也不被永久去重丢掉？

**面试者：** 我会把“对象已经登记”“对象属于当前规范历史”和“对象已贡献给哪个投影”分开。唯一键保证同一 `(chainId,blockHash,txHash,logIndex)` 只有一份原始观察；active 只是投影资格中的规范性条件，兑换归属还需正确的 I1 关联与业务核验。第一次规范化且资格齐全时应用并记下贡献；重复相同版本输入无操作；分支撤下时 active 变为 false，目标贡献归零并撤回；同一个 H1 回来且资格仍满足，则重新应用。active 不变但关联或核验补齐时也重新比较目标贡献，不能漏记；关联更正还要按旧贡献撤回、按新归属补记。每次转换、应用记录、投影和 revision 都按前面约定的本地事务或 generation 发布协议共同可见。

例如主例在 H1 使 A 的兑换历史多一笔，切到不含它的分支就撤掉这笔，再回到同一个 H1 时只恢复一次，而不是因唯一键存在永久跳过，也不是把两次激活累计成两笔 swap。若相同 txHash 进入不同 blockHash，要建立另一条观察，切换当前有效来源，不能同时贡献两次兑换。跨模块消息则不能只拿 observation 身份做永久消费键，因为激活、撤回、再激活是三个不同状态变化。它们需要各自的 transitionId 或 sourceRevision，才能让下游区分“重复投递同一次变化”和“同一个链上观察发生了新的有效性转换”。

## 第 6 层：Outbox 和 Inbox 怎样防止双写丢失，又为什么不是 exactly-once？

**面试官：** 既然激活和撤回都有新版本，现在把变化交给通知和查询模块。源库提交后发消息失败，或者下游处理成功但确认丢了，分别怎么恢复？

**面试者：** 源端的 observation、投影、revision 与 Outbox 消息在同一数据库事务中提交，消息至少包含 sourceId、连续 sourceRevision、transitionId、目标对象、状态变化类型、来源区块与发布锚点。发送器从已提交 Outbox 重试投递，收到确认以后再记录发送进度。发送后确认丢失会导致重复投递，但不会因为源业务先提交、消息后发送而永久失去通知。sourceRevision 可以对应一个明确的变化批次，批次完整性也是消息契约的一部分，不能只发出其中一条就让消费者认为整个水位已经到达。

下游在自己的本地事务里登记 Inbox 唯一消息身份、检查应有前序版本、更新投影并推进消费水位，再提交和确认。同一 transition 的重投不再产生第二次业务变化，但以后同 observation 的重新激活拥有新 transitionId，仍应生效。通知若涉及事务外发送，还要继续用下游 Outbox 和渠道支持的幂等身份；若渠道没有这种能力，就明确承认可能重复，不能靠 Inbox 掩盖外部调用窗口。整套机制提供的是两个本地事务加至少一次传输，不把 Ethereum 执行、源库、消息系统和接收方组成跨链 exactly-once，更不意味着一封通知发出后能够随着链重组自动撤回。

## 第 7 层：乱序消息与多模块查询怎样做到水位一致？

**面试官：** 你让消费者检查前序版本。假如它先收到 revision 102 的撤回，后收到 101 的激活，而页面又同时查交易模块和池模块，具体怎样避免显示混合结果？

**面试者：** 我会先定义版本序列的作用域。例如本题对一条 chain 的投影变化流使用连续 sourceRevision，102 到来而已提交水位是 100，就先持久缓冲 102、记录缺口并补取 101，不将 102 宣称为已经应用。101 完整应用并提交以后，再处理 102 的撤回；随后迟到或重复的 101 只按 Inbox 记录确认，不得重新激活旧结果。若消费者只订阅流的一部分，需要专属连续序号或明确的跳过与覆盖标记，不能把自己根本不该接收的 revision 永久当成缺口。若使用覆盖式快照而不是有序增量，也要在契约中说明，不能把两种处理混用。

组合查询时，我会要求交易投影和池投影返回同一个可用发布 token，token 包含分支锚点及版本，不仅是相同高度。跨库场景可保留按 token 读取的版本，协调者取两边都能提供的共同完整水位；若系统不保留历史，就等待两边追到相同目标或明确返回暂不可提供一致快照，不能简单取两个最新结果。仅在同库同一发布事务维护的两张表，可以用一致快照读取。缓存和 WebSocket 同样携带 revision，发现缺口便补查；重组后 revision 前进但链高度可能后退，前端不能按区块号较小就把正确撤回丢弃。

## 第 8 层：如何重建投影而不把链上执行再做一遍？

**面试官：** 你能检测缺口和一致水位。如果旧版本解码器算错过 W 的精度，已有多个下游消费了错误投影，怎样修复，又怎样证明修复不产生第二笔兑换？

**面试者：** 我会把这个变体限制为本地解释错误，链上交易、资产合约和规则均不改变。先冻结受影响投影的确定性发布，定位错误解码器版本、区块范围与下游覆盖水位，从可信的规范与 finalized 锚点重新取得或核验原始证据。以正确的 U 6 位、W 18 位整数规则在新的 generation 重建，保留原始 observation、attempt 与 I1 的关联，核对每个区块的连续性、业务证据及 active 集合；不能只改显示小数位后假定所有累计值已经正确。

修复后的版本通过明确的投影重建发布记录切换，可用高于旧版本的 sourceRevision 或受控的新流 epoch 向下游发布替代快照，并约定旧流停止位置，避免新快照又被迟到旧增量污染。查询在共同 token 上再核对主例：2000 U 输入只对应一次兑换，输出是 995015938219190933 W 原子，P 的 W 是 499004984061780809067 原子。重放的是链上事实到本地投影的解释过程，不是重新签名或广播 swap，因此不会增加 nonce 或转移资产。涉及已发外部通知的错误，按可审计更正处理；finalized 祖先关系异常则走暂停与调查，不用投影重建悄悄抹去安全异常。

## 本题收束

- **讲透的机制：** 链上资产是权威，本地查询是可重建投影；observation 身份、canonical active、关联/核验资格与各投影已应用贡献分别保存，按目标贡献和已应用贡献的差异处理补记、撤回与再应用。投影、观察有效性、应用记录、Outbox、带哈希游标与发布水位必须共享清楚的本地提交边界；大范围重组可用不可见 generation 构建后原子切换。
- **最易答错的边界：** 仅有区块号无法识别分支，永久“见过即跳过”会丢掉再规范化事件，只推进游标会跳过未完成的数据。Outbox/Inbox 不提供跨链 exactly-once；同一 observation 的三次状态变化不是同一消息。查询必须在可用的共同分支版本上组合，不能把交易新水位和池旧水位拼在一起。普通 logs 还依赖明确的 RPC 信任和检索完整性前提。
- **具体反例验证：** 手工推演主例 H1 首次激活为 revision 101，撤回为 102，再次规范化为 103。源端在每次发布事务中途崩溃，恢复后只能看见完整旧版或完整新版；消费者先到 102 则等 101，重复 101 不重加，103 不能被 observation 永久去重挡掉。最后同一发布 token 下只存在一笔有效兑换，数量严格回到主例结果，游标哈希指向实际规范分支。另独立推演 Outbox 已发但确认丢失，预期只重复投递，不重复改变投影，也绝不触发新 swap。再独立推演“池观察已 active、I1 未关联 → 钱包后补 hash 并完成核验”：active 保持 true，兑换投影从未应用变为应用一次，产生新 revision/Outbox；重复补关联无操作，随后重组可按已应用贡献撤回。
