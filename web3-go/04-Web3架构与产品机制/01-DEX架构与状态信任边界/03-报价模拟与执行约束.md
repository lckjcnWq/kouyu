# 大问题 3：链下报价和模拟为什么不能保证成交，怎样将用户意图落实为执行约束？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 报价 / 模拟 | 报价算预计能换多少，模拟是在选定状态上试运行一次调用。 | 都没有把未来池价、用户余额或交易顺序锁住。 |
| A / R / P / U/W | 用户、路由合约、池、两种教学代币。 | A 输入 2000 U 换 W，R 检查保护条件，P 按实际储备执行。 |
| B0/H0 / blockHash / rulesVersion | 报价参考区块、区块哈希、规则版本。 | Q1 必须对应一组共同状态，不能把不同块的储备和配置拼接。 |
| allowance / approve | 可供合约使用的代币额度、设置该额度的授权动作。 | 查询到足额授权不是冻结余额，执行时仍可能付不出币。 |
| 原子单位 / float64 / big.Int | 最小整数金额、近似浮点数、Go 的大整数类型。 | U 为 6 位小数、W 为 18 位；金额用精确整数，big.Int 共享时注意可变性。 |
| x / y / a / floor | 两种池储备、输入量、向下取整。 | 输出按 floor(a×997×y/(1000x+997a)) 算，储备最终收到完整 a。 |
| 997/1000 / 池费 | 输入按 99.7% 参与定价，对应本例 0.3% 池费。 | 2000 U 中有 6 U 对应费用，但不会再额外扣 6 U，也不能只给储备加 1994 U。 |
| minOut / 0.5% 容忍 | 最低可收数量，以及相对本次报价允许的输出下降幅度。 | 下限为 990040858528094978 个 W 原子单位，不是所有成本最多 0.5%。 |
| deadline / recipient | 执行期限、收款人。 | 本例执行时间严格小于 1800000120，收款人固定 A；等于期限拒绝。 |
| sender / to / value / calldata | 调用者、目标地址、随调用发送的原生币、编码后的函数参数。 | 模拟必须对应用户将签的实际调用；只模拟池而漏掉路由可能漏检授权。 |
| eth_call / Gas 估算 | 节点上的试调用、估计执行资源需求。 | 不创建链上交易，不保证未来准入、消耗或及时包含。 |
| 价格影响 / 公允参考价 / MEV | 本次交易推动池价的影响、独立比较价格、利用排序等机会提取的价值。 | 报价准确不等于经济上划算；最小输出也不能证明零 MEV。 |
| goroutine / 不可变快照 / 背压 | Go 并发任务、发布后不再修改的数据、有界排队或限流。 | 提升速度不能以混用区块、共享可变整数或返回过期报价为代价。 |
| revert / 原子边界 | 执行回滚，以及一起生效或撤销的变化范围。 | 本教学 Swap 必要环节失败整体回滚，不临时改成允许部分成交。 |

## 把整篇文章压缩成一个故事

小林想拿 2000 U 换 W，Go 读取同一区块的池储备，按 0.3% 池费精确算出预计输出 0.995015938219190933 W，再把最低输出设为 990040858528094978 个 W 原子单位。它相当于给出一张有状态来源、有保护条件的计算单，不是向池子订下这批币。

小林签名前，系统用真实调用者、目标和参数做模拟，钱包还要核对最终将签的内容。如果别人先交易导致实际输出不足下限，或执行时已到期限，合约就应拒绝；等于下限可以，少一个原子单位不行；本教学合约等于期限则不行。模拟之后再改收款人或目标，旧模拟也就不能证明新调用正确。

为了更快返回，工程师可以缓存和并行读链，但每份报价仍要有共同区块和规则版本，过期就重新确认。即使所有计算都对，原始报价本身仍可能很差，Gas 也另有成本。本文用这个故事拆掉“算准了就一定成交、滑点 0.5% 就最多亏 0.5%”两个误解。

**流程位置与核心机制：** 从读取池状态到钱包签名，重点是报价快照、整数计算、模拟边界与合约执行保护。排序公平与 MEV 在母题 05 深入，本题不扩展为路由搜索算法。

**必要前提：** 使用[总览](README.md)固定的 Q1、B0/H0、2000 U 输入和 0.3% 池费模型。minOut 为 `990040858528094978` 个 W 原子单位，deadline 为 `1800000120`，收款人 A，R 要求执行时间严格小于 deadline。

## 第 1 层：报价是条件计算，不是成交承诺

**面试官：** 链下报价和模拟为什么不能保证成交，怎样将用户意图落实为执行约束？

**面试者：** 报价是在指定历史状态下计算“若按这些条件执行，会得到多少”，模拟是在某个状态上尝试一次调用；两者都没有锁住未来区块的池状态，也没有取得交易排序资格。因此它们降低错误概率，但不能替代链上执行。

主例 Q1 来自 B0/H0：输入 2000 U，按手续费和池储备计算输出 `995015938219190933` 个 W 原子单位。A 接受报价时，还要明确允许的最小输出、期限、输入量、币种地址、路径和收款人。这些最终编码进调用，由 R 在实际执行状态下检查，而不是只由前端保存。

成功语义是“按用户签署的保护条件完成交换”，不是“必定按 Q1 的估算值交换”。价格变化后，输出仍可能高于 minOut 而成功，或低于下限而回滚；不能把允许变化本身认作系统不一致，也不能在用户签名后静默放宽下限来追求成交率。

## 第 2 层：让一份报价对应一组真实快照

**面试官：** 你强调 B0/H0，但调用几个 RPC 读储备，再返回 Q1，不就已经是一份快照了吗？

**面试者：** 多次调用不天然共享同一个时点。读取期间新区块可能到达、端点可能切换、同高度还可能发生重组。我要先确定 chainId 与目标 blockHash，随后所有用于本次计算的状态都绑定该位置，保留池地址、资产地址与精度来源。无法固定历史状态时，明确标注限制并拒绝把它称为一致快照。

对 P 来说，报价至少需要同一次状态观察中的储备和费用规则。对用户预检查，余额和 allowance 也要带位置，但它们只能描述该位置的可执行性，不成为资金预留。服务返回 Q1 时保存 blockHash 和 rulesVersion，防止多个工作线程把新储备与旧配置拼起来。

区块号可以帮助定位，但遇到分叉必须以哈希区分。缓存键至少包含链、池、区块身份及相关配置版本，不用单一 `poolId → latestQuote` 隐藏来源。钱包收到过旧 Q1 时，应重新取价并让用户确认变化，而不是把最新数据直接覆盖在同一个已确认摘要下。

## 第 3 层：精度与费用怎样保持一致

**面试官：** 快照固定后，为什么不用 float64 算出大约 0.995 W 就够了？这个主题不是架构吗？

**面试者：** 架构承诺最终要落实到合约接受的整数，精度是交接契约的一部分。U 有 6 位小数，W 有 18 位小数，`2000`、`2000000000` 与 `2000e18` 不是同一个输入。float64 近似再取整可能把 minOut 或输入变成用户没有确认的数量。

本例用原子单位大整数计算：`floor(a×997×y/(1000x+997a))`，得到 `995015938219190933`。再按 0.5% 容忍向下取整得到 `990040858528094978`。两次舍入都需明确；界面小数用于展示，签名摘要和合约参数始终用整数及精确资产身份。

0.3% 手续费在这个公式中体现为有效输入系数，实际 P 收到的仍是完整 2000 U。不能先算 1994 U 有效输入，再把池新储备写为旧储备加1994 U；那会把留池费用丢掉。本例没有额外平台费和 Gas 代币折算，若新增就应明确改变了费用口径及用户保护条件。

## 第 4 层：模拟必须是用户将要签的调用

**面试官：** 你已经精确算出了输出，再跑一次模拟是否就足以把所有构造错误挡住？

**面试者：** 模拟必须尽量使用实际 sender、to、value、calldata 和对应状态，否则可能只证明某个近似调用成功。比如用服务地址代替 A，可能得到不同的余额和授权结果；只模拟 P 而不模拟 R，就可能漏掉 allowance spender、路径和用户期限检查。模拟还应绑定所用区块并记录结果来源。

普通 `eth_call` 不创建链上交易，也不等于验证钱包最终签署的交易。签名有效性、实际 nonce 准入、费用、区块 Gas 空间以及后续状态变化，并不因一次成功模拟就被保证。即使估算 Gas 成功，也不能承诺未来执行消耗与包含条件完全一致。

所以钱包签名前还需独立核对最终交易摘要，并将它与用户确认内容关联。若模拟后构造器又改了目标、接收人或 minOut，原模拟证据失去对应关系。任何重新报价或改约束，都应形成清楚的新版本，并由 A 重新确认，而不是沿用“刚才已模拟成功”的标签。

## 第 5 层：执行时到底保护哪些条件

**面试官：** 那具体哪些检查必须放在链上？只检查 minOut 是否就足够了？

**面试者：** minOut 只解决输出数量下限，不能替代链、资产身份、输入上限、接收人和时间约束。本例调用固定 R/P 和 U→W 路径，精确输入2000 U、接收人 A、deadline 为 `1800000120`。R 在执行状态下检查期限和输出下限，执行必要转账并传播失败，P 再检查真实输入与池不变量。

只检查“至少得到0.99个某种代币”而不绑定地址，攻击者可以把 W 换成同名假币；不绑定收款人，成功输出可能流向他人；不绑定目标代码，所谓 minOut 字段可能根本不被执行。用户交易签名覆盖的实际调用内容才是权限载体，界面的文本说明不能自行约束合约。

本 R 是严格小于 deadline 的教学规则，因此执行到 deadline 时拒绝；不能因为前端在截止前签了名就获得例外。若用户允许重报价，新条件必须再次确认。复杂 Router 若支持部分成功，还需逐分支定义保护，本例没有这些能力，不能临时引入来解释失败。

## 第 6 层：滑点下限不是公允价值证明

**面试官：** 你给了0.5%的滑点保护，所以用户最多损失0.5%吗？如果 Q1 本身就很差呢？

**面试者：** 不能这么说。0.5% 是相对 Q1 估算输出的容忍，它既不包含 Q1 相对外部市场的偏差，也不是全部经济成本上限。池费、交易自身的价格影响、Gas 和其他市场变化需要分别解释。坏报价乘99.5%仍然是坏报价，合约不能凭一个正确执行的 minOut 证明价格公平。

主例池初始边际价为2000 U/W，输入2000 U的输出少于1 W，既有费用也有曲线上的价格影响。若攻击者在报价前就操纵了池，绑定 H0 只证明“确实按该被操纵状态计算”，不证明经济合理。因此链下可以加入独立参考价、偏离限额、报价新鲜度与大额提示，但这些只是交易选择和风控依据。

若要增加链上参考价约束，则新增了预言机依赖、更新滞后与失败策略，必须明确代价，不能把它当本例原有能力。即便有参考价，MEV、排序公平和可包含性也要另行说明；最小输出保护不承诺交易一定能被包含。

## 第 7 层：缓存与并发优化不能偷偷改变承诺

**面试官：** 独立读链、模拟、参考检查都很慢。Go 服务为了吞吐缓存 Q1，会不会只是工程问题，不影响信任边界？

**面试者：** 会影响，因为缓存失效策略决定了用户看到的条件是否仍具有清楚来源。我会缓存不可变的“状态快照加规则版本”，再按请求输入计算，而不是把一个没有区块身份的输出复用于所有用户。发送响应前检查新鲜度；无法满足时返回过期或降级说明，不伪装成刚刚读取的状态。

Go 中用 `big.Int` 要特别注意其方法会修改接收者，多个 goroutine 共享指针边读边改会让报价失去自洽。应深拷贝或封装只读快照，单一构建者发布完整版本，读者拿到一组不可变值。并行 RPC 应有界、可取消并校验共同 blockHash，不能超时后取任意几个成功结果拼装。

这些优化只降低链下延迟，不取得链上锁或排序权。即使每毫秒更新，也不能将 Q1 升格为未来可执行承诺。性能报告还应区分缓存命中延迟、链读取延迟、模拟时间和链上等待，不用一个平均响应时间掩盖新鲜度或错误率。

## 第 8 层：用边界输入证明保护真的生效

**面试官：** 你说了很多约束，怎样用少量案例验证不是只把字段写进数据库而已？

**面试者：** 我会从同一 Q1 逐项改变条件，检查实际调用的拒绝位置，而不是只验 API 返回值。正常输入应按主例获得 `995015938219190933` 个 W 原子单位；保持其他条件不变，令实际输出恰好等于 minOut，应被允许，少1个原子单位则回滚。时间取 deadline−1 和 deadline，按本 R 的严格规则分别允许与拒绝。

再把 recipient 改成另一个地址，检查钱包最终确认是否识别出与 I1 的不一致；把 W 改成同名异地址代币，检查是否在构造前被拒绝；模拟后修改 calldata，检查原模拟摘要是否不再可复用。这些分别验证用户确认、资产身份和证据绑定，不是重复测同一个校验。

本次只交付这些手工推演标准和总览中的唯一 MVP，不声称已经执行链上测试。完整工程中还需核验真实部署代码与模拟端点能力，尤其不能把本教学 R 的期限语义和整数边界不加核对地套到任意 Router。

## 本题收束

- **讲透的机制**：报价绑定历史快照，模拟绑定具体调用，用户签名绑定权限与条件，R/P在执行时强制用户保护和池规则。
- **易错边界**：模拟成功不等于未来准入或成交；精确快照不等于价格公平；0.5%容忍不等于总经济损失上限；Gas估算不是包含保证。
- **具体反例与验证**：保持 Q1 不变，只让模拟后的目标合约变化。即使新交易 status=1，也不能用旧模拟和旧报价证明 I1 按约完成。检查 attempt 中的调用摘要是否与钱包确认、模拟记录和最终交易一致。
