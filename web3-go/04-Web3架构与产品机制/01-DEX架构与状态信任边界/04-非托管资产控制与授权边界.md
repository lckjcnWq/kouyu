# 大问题 4：用户自己签名就等于资产安全了吗，非托管 DEX 的资产控制与授权边界怎样成立？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| DEX / 非托管 | 去中心化交易系统，以及平台不直接掌控用户签名与内部提款余额的安排。 | 不表示代码绝不会出错，也不表示获授权合约无法动币。 |
| A / R / P / U/W | 用户地址、路由合约、池、两种教学代币。 | A 自行签名，R 从调用者收输入，P 按规则交换；Go 不持私钥。 |
| balanceOf / 储备 / LP 份额 | 代币合约记的余额、池记的储备缓存、流动性提供者的份额。 | P 持币不等于 Go 托管一笔用户余额，A 换币也不因此获得 LP 份额。 |
| approve / allowance | 设置代币权限、该使用者可用的代币额度。 | 授权 2000 U 后 A 仍有 5000 U，没有付款或冻结；Swap 失败不撤回此前独立授权。 |
| spender / transferFrom | 获授权的合约、按授权划转代币的调用。 | A 授权的是 R，不是随便一个调用 R 的人都能指定扣 A 的钱。 |
| msg.sender / 固定入口 | 合约看到的当前调用者、受限制的调用路径。 | 本例 R 只能从当前调用者拉币，不允许任意付款人和任意外部调用。 |
| recipient / minOut / deadline | 收款人、最低输出、执行期限。 | 都需核实实际签名内容；主例收款人为 A，不能只看钱包上的“确认”按钮。 |
| EOA / nonce / txHash | 私钥控制的外部账户、账户交易序号、交易哈希。 | nonce43 的撤销不能越过尚待处理的 nonce42；同 nonce 替换也须看实际胜出者。 |
| approve(R,0) / 无限授权 | 将 R 的额度降为零、给出远超本次需要的长期额度。 | 撤销只管今后权限，不追回已转走资产；无限授权扩大长期暴露。 |
| revert / 原子性 / Gas | 回滚、单笔相关变化共同提交、链上执行资源。 | Swap 回滚不留半笔换币；已包含失败仍付 ETH 执行费并消耗 nonce。 |
| immutable / rebase / 黑名单 | 实现不可升级、按规则调整余额、限制地址转账。 | 本例 R/P 无管理员且代币无这些特殊行为；讨论它们必须明确改前提。 |
| receipt.status / canonical / finalized | 执行状态、当前规范链、共识最终确定的链段。 | 成功回执还要核验调用和资产语义，当前包含不等于最终完成。 |
| 投影 / 重放 / 同步水位 | 链事实的本地视图、重新读取处理证据、完整处理到的位置。 | 页面错就修页面，不能凭数据库重放获得链上退款或多发一次兑换。 |

## 把整篇文章压缩成一个故事

小林有 5000 U，先授权 R 使用其中 2000 U，再签一笔换币交易。授权更像给特定合约一份有额度的使用权限：钱还在小林地址，R 能做什么还由其代码入口限制。本文要求 R 只从当前调用者收币，不能让其他人随便填“小林付款、自己收款”。

若小林执行前把余额转走、只剩 1000 U，哪怕数据库写着“已预留”，2000 U 的 Swap 仍须失败，不能凭空欠款继续给 W。Swap 内部整体回滚，但早先独立成功的授权可能留下，失败交易若已包含也仍付执行费。正常且条件不变时，小林才会剩 3000 U，并收到主例算出的 W。

发现风险后，小林又想撤销授权。若撤销用了 nonce43，它不能抢在待处理的 nonce42 之前；改成同 nonce 竞争也没有必胜保证，更不能追回已成交的钱。本文最终提醒：自己签名只是控制链的一部分，还要核对合约、权限与真实结果；修复展示和恢复资产，是两种完全不同的操作。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题沿“用户持币与签名 → 独立授权 → Router 调用 → 池内交换 → 结果核验”追问谁能改变资产、授权允许什么以及服务端不能承诺什么。重点是资产控制权与信任条件，不把非托管解释成没有合约风险，也不把数据库预留解释成链上锁资。

**必要前提：** 资产、金额与时间沿用[总览](README.md)第 1.1—1.2 节，权威与身份见第 4 节。本题重点使用两个条件：R 只从当前调用者拉取输入，不能任意指定另一个已授权地址作为付款人；普通 approve 是独立前置交易，不与 Swap 共同回滚。主例调用者、付款人与接收者均为 A，不引入代理签名或托管余额。各异常独立从公共基线改变条件。

## 第 1 层：非托管具体不托管什么，池里的币又属于谁控制？

**面试官：** 在这个模型中，用户自己签名发起 Swap，为什么称为非托管？A、Go 服务、R 和 P 分别能改变哪些资产状态？

**面试者：** 非托管首先表示 Go 服务不持有 A 的私钥，也没有可替 A 划款的内部资产账户。A 的 U、W 余额由各自代币合约记录，只有满足代币合约授权规则的调用才能改变它们。P 地址持有的币同样由 `balanceOf(P)` 记录；P 自己保存储备缓存和 LP 份额，它们不是 Go 数据库里的余额。A 签名调用 R 后，R 只能沿既定入口转移本次输入，P 按恒定乘积及手续费规则交换。LP 持有的是按池规则赎回资产的份额，不是服务端可任意支取的账户余额。因此，非托管排除了平台凭数据库指令直接划款，却没有排除用户对合约规则和签名内容的信任。

## 第 2 层：既然服务端不能划款，approve 为什么又让 R 能动用 A 的币？

**面试官：** 你说只有满足代币规则才能转账。那 A 先 approve R 之后，R 的权限保存在哪里，它是不是已经把 2000 U 锁给这次报价了？

**面试者：** approve 改变的是 U 合约里的 `allowance(A,R)`，不是 R 或数据库中的锁资记录。假设 A 按本次数量授权 `2000000000` 原子量，U 允许以 R 为 spender 的调用通过 `transferFrom` 消耗相应额度，但 A 的余额仍是 5000 U，没有资金转入 P。这个额度不绑定 QuoteId、池状态或 deadline，也不保证执行时余额足够。若批准需要 nonce 41，它应先成功进入当前 canonical 链，nonce 42 的 Swap 才具备此前提；批准本身仍有独立的确认状态。独立 approve 已经成功后，Swap 失败不会撤销它。所以授权是未来划款的能力边界，不是本次交易已经付款或已经成交的证明。

## 第 3 层：有 allowance 之后，怎样防止其他人借 R 花掉 A 的钱？

**面试官：** 你把 allowance 定义成对 R 的能力授权。如果别人调用 R，能否把付款人填成 A、收款人填成自己？按次授权又能保护到哪一层？

**面试者：** allowance 只认 spender 地址，不理解“这是 A 自己的交易意图”，所以必须继续检查 R 的入口语义。本模型中 R 从 `msg.sender` 拉取 U；攻击者以自己地址调用，付款人就是攻击者，不能借用 A 的授权。R 也不能提供可任意拼接目标和调用数据的执行入口，否则额度限制无法替代调用隔离。A 还要在签名前核对链、R 地址、U/W、输入量、`recipient=A`、minOut 和 deadline，签名有效不代表这些内容符合自己的预期。按次授权 2000 U 能缩小可被该 spender 使用的额度，却不能证明 R 无漏洞，也不能防止 A 主动签下错误内容；无限授权则扩大长期暴露，不应作为默认便利项。

## 第 4 层：授权和签名都正确，为什么报价之后仍可能没有足够的币？

**面试官：** 上一答已经限制了付款人和额度。现在只改变一个条件：执行前 A 的 U 余额变成 1000 U，而报价仍按 2000 U 输入，数据库已经标记“预留成功”，会发生什么？

**面试者：** Swap 仍应失败，因为真正裁决能否付款的是执行时 U 合约的余额与 allowance，数据库标记不能冻结链上的币。这里 2000 U 的授权还在，但 A 只有 1000 U，`transferFrom` 无法完成；R 必须让失败传播成整个 Swap 的 revert，不能记一笔欠款继续给 A 输出 W。该 Swap 内部已经发生的资产、储备和日志变化一起回滚，独立成功的 approve 不回滚。若失败交易已被包含，A 仍支付实际消耗的 ETH gas，nonce 42 也被消耗。报价与模拟只能描述指定状态下可能发生什么，既不锁余额，也不赋予 Go 服务强制执行权；界面应说明条件未满足，而不是宣称本地预留丢失了链上资产。

## 第 5 层：发现风险后撤销授权，能不能保证待处理 Swap 一定被取消？

**面试官：** 你说 Swap 失败后授权还可能存在。回到主例，假设 approve 已成功、nonce 42 的 Swap 尚在等待，A 现在发送 `approve(R,0)`，能否立即阻止原交易？

**面试者：** 不能把“发出撤销”说成“已经取消”。如果撤销用 nonce 43，同一 EOA 的 nonce 顺序要求它排在 nonce 42 之后，它不能先执行来保护仍待处理的 42。A 可以另外签署 nonce 42 的零授权交易去竞争替换，但这是新的 txHash，是否被接纳和先包含不由服务端保证。同一条最终链前缀里，同一 A 的 nonce 42 只能有一笔交易：若撤销胜出，原 Swap 不再能以该 nonce 执行；若原 Swap 先胜出，撤销交易不能追溯撤销成交。当前 canonical 观察还要区分是否 finalized。撤销只限制之后可用的剩余额度，不能追回已经合法转走的币，也不能靠页面“取消中”改变链上顺序。

## 第 6 层：撤销只能面向未来，那无管理员是不是就完全不需要信任？

**面试官：** 你已经承认不能事后追回。若 R、P 都不可升级、没有管理员，是不是只要撤掉多余授权，就可以说这套非托管系统没有信任风险？

**面试者：** 仍不能这样说。不可升级消除了管理员以后更换实现的权限，但不会自动证明当前代码正确；用户仍依赖入口隔离、转账失败传播、储备更新和价格约束没有缺陷，也依赖自己连接的是正确地址与网络。本模型还明确假定 U、W 无黑名单、升级、转账税或 rebase，所以可以按标准余额变化推导。只有明确改变这些条件，才讨论代币管理员冻结地址、升级逻辑或转账少到账等额外风险，不能把这些权限伪装成主例已经存在。反过来，主例没有后台暂停或强制退款入口，平台客服也不能用“风控”名义从 P 或 A 处冻结、回拨资产。非托管缩小的是可支配权限，不是消除全部依赖。

## 第 7 层：既然不能相信后台承诺，怎样核实资产真的按约定变化？

**面试官：** 上一答要求信任地址和执行规则，而不是客服承诺。如果 Go 服务显示成功、收据也有 `status=1`，A 怎样确认这确实是约定的 2000 U 换 W？

**面试者：** 我会核验 `chainId=1` 上由 A 发出、nonce 42 的实际交易是否调用目标 R，解码后确认输入币、数量、收款人和保护参数，再检查目标 P 的交换事件、指定 U/W 合约的转账以及相应状态变化。`status=1` 只说明外层执行没有 revert，不等于任何成功交易都是这次 Swap。主例在该交易执行边界应得到 A 为 `3000 U、0.995015938219190933 W`，P 为 `1002000 U、499004984061780809067` W 原子量；LP 份额不因 Swap 增发。若同区块还有后续交易，不能拿区块末余额直接冒充这笔的交易后状态。Go 只是保存和展示这些证据，还应区分 canonical 已包含与 finalized，不能成为资金权威。

## 第 8 层：证据与页面不一致时，恢复资产和恢复展示的边界在哪里？

**面试官：** 你已经把执行证据和展示分开。假设交易证据符合主例，但页面仍显示 A 有 5000 U，或者先前观察所在区块退出 canonical 链，系统分别应该做什么？

**面试者：** 第一种是投影错误，应按已经核实的链上结果重建页面和记录，不能再向 A 补发一笔相同 Swap，也不能把数据库余额当成可兑付承诺。第二种是尚未最终确定的链上观察变化，要撤销旧观察对展示的贡献、追踪交易是否在新链重新包含，再重新核验，而不是调用不存在的管理员退款接口。业务最终完成依据经验证节点的 finalized 区块及祖先关系；若最终性本身遭到破坏，应停下自动结论和后续不可逆处置，转人工核验。A 的 ETH gas 与 W 始终分开，本例不通过 unwrap 补足 gas。恢复系统认知可以重放证据，恢复资产则必须遵守当下链上权限，二者不能混为一谈。

## 本题收束

**机制：** U/W 合约拥有余额与授权状态，P 拥有储备缓存及 LP 份额，A 的签名和 R 的固定入口共同限定可执行行为。approve 是独立的能力授权，Swap 才在执行时实际转移输入和输出；Go 不持有资金权威。

**易错边界：** 非托管不等于无信任，授权不等于锁资，按次授权不等于代码正确；独立 approve 不随 Swap 回滚，已包含的 revert 仍消耗 gas 和 nonce。撤销交易、客服状态或数据库锁都不能追溯改写链上顺序。主例没有管理员权限，讨论可升级或恶意代币必须明确改变条件。

**具体反例验证：** 从“nonce 41 已成功授权 2000 U、nonce 42 待处理”出发，让 A 用 nonce 43 撤销授权。仅根据 EOA nonce 规则就能发现：43 不能抢在 42 前执行，因此“提交撤销后原 Swap 必定不会成交”这一承诺不成立。若改成同 nonce 42 的竞争交易，也只能以最终链实际包含哪一笔作为裁决，不能以服务端先收到哪个请求作为裁决。
