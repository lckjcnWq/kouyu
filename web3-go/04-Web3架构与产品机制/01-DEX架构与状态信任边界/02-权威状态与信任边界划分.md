# 大问题 2：链上合约、链下服务和 RPC 各自拥有什么权威，怎样划分 DEX 的信任边界？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| DEX / EVM | DEX 是去中心化交易系统；EVM 是执行以太坊合约的环境。 | 本文只讨论单池现货模型，不把平台内部账本当作链上余额。 |
| 状态权威 / 执行能力 / 观察 | 谁按规则裁决状态、谁有权限发起操作、谁报告所见结果。 | 查到余额不等于有权划款，具备划款权限也不等于拥有用户私钥。 |
| A / R / P / U/W / LP | 用户地址、路由合约、流动性池、两种教学代币；LP 是提供池内流动性并持有份额的角色。 | A 签名，R 执行保护，P 维护储备和 LP 份额，U/W 合约记录余额。 |
| allowance / spender / 非托管 | 代币使用额度、被授权合约、平台不直接掌控用户资产的安排。 | R 获授权后能按代码路径调用代币；非托管不能推导 R 完全影响不了资产。 |
| RPC / chainId / blockHash | 节点接口、链身份、具体区块哈希。 | 给返回值标来源便于核对，但加了哈希的假数据仍是假数据。 |
| Q1 / H0 / rulesVersion | 报价、所用区块身份、规则版本。 | 计算必须使用一组可以共同成立的状态，不能拼新旧储备。 |
| minOut / deadline | 最低输出、可执行时间边界。 | 它们管未来执行是否接受；固定历史快照管的是计算依据，两种保证不同。 |
| 执行客户端 / 共识客户端 | 分别核验状态执行规则和共识历史的节点软件。 | 自行验证可缩小第三方依赖，但仍有软件、运行和共识前提。 |
| Merkle 路径 / 包含证明 / 区块头 | 用树状承诺证明某项数据在某块中存在；区块头承载相应摘要。 | 路径还须绑定已验证的规范区块头，不能仅凭一个证明声称链身份正确。 |
| receipt.status / ABI / topic | 回执执行状态、合约数据编码约定、事件识别字段。 | status=1 不表示必然换到 W；同名事件还须核验地址、参数及调用语义。 |
| canonical / safe / finalized | 规范链及不同强度的共识进度标签。 | 当前包含不等于最终确定；safe 不冒充 finalized，高度大小不替代祖先关系。 |
| immutable / 代理 / 治理 | 不可改变的实现前提、可转发给其他实现的合约、改规则的管理机制。 | R/P 不可升级不代表代币等依赖也不可变，更不是代码安全证明。 |
| 多签 / 延时 / 黑名单 | 多方共同批准、变更等待期、限制某些地址转账的机制。 | 提高门槛不消除管理权；主例无黑名单，加入它必须明确改变条件。 |
| projection / 信任边界 | 派生查询视图，以及某依赖失效会破坏哪些承诺的范围。 | 数据库能修展示，不能补造资产；资产控制、排序公平和自主退出分别论证。 |

## 把整篇文章压缩成一个故事

小林准备通过一个 DEX 用 U 换 W，看到页面显示余额充足、交易模拟成功，就问：“是不是后台说成功，钱就到账？”工程师先把职责拆开：小林签名，代币合约记余额与授权，路由和池按代码执行，Go 只保存请求与展示，RPC 则像提供链上消息的窗口。窗口能报错，却没有因此获得合法划款权。

为了不被消息误导，系统要问每个数字来自哪条链、哪个区块；两个真实但不同时点的读数也不能随便拼成报价。即使回执属于真实区块、外层执行成功，仍须确认调用了正确合约、收款人确实是小林、资产确实是 W，随后再核验规范归属与最终性。多家节点说法一样只能辅助核对，不能自动变成无信任证明。

小林又听说“合约不可升级”，本文继续追问代币和其他依赖是否能改规则。主例明确没有这些管理权限；若另换成可冻结地址的代币，就必须收回“任何人都不能阻断转账”的旧承诺。故事的落点不是笼统说一切都有风险，而是逐项讲明谁能做什么、凭什么验证、依赖失效究竟伤到哪一层。

[返回专题总览](README.md)

**流程位置与核心机制：** 跨越全流程，建立“状态由谁裁决、操作需要什么能力、结果依据什么证据”的对应关系。与完整流程题不同，本题重点推演依赖说谎、观测分歧及所谓去信任化的证明边界。

**必要前提：** 采用[总览](README.md)的单池 EVM 现货模型；A 控制签名，U/W 记录资产余额与授权，P 记录储备与 LP 份额，R/P 无升级管理权，Go 无托管余额。案例金额、身份与最终性策略不变。

## 第 1 层：按状态划分而不是按服务贴标签

**面试官：** 链上合约、链下服务和 RPC 各自拥有什么权威，怎样划分 DEX 的信任边界？

**面试者：** 我不会简单说“链上可信、链下不可信”，而是对每一类状态回答三个问题：谁有权改变它，什么规则约束改变，其他人怎样验证。

本模型中，A 控制交易签名；U/W 合约记录地址余额和 allowance；P 维护储备缓存和 LP 份额，R 负责执行用户保护并调用代币与池。链上交易经验证执行并进入被接受的共识历史后，才形成该历史下的资产结果。Go 有权修改自己的 I1 请求记录、Q1 报价和查询投影，没有修改 U/W 余额的权力。RPC 是观察与传播入口，不因返回了一个余额就成为余额所有者或最终裁决者。

所以信任边界不是“用了哪个组件”，而是“某个依赖出错，哪些承诺会失效”。Go 错价可影响交易选择，恶意构造可诱导错误签名，错误 RPC 可伪造展示，但它们与拿到私钥或合约升级权造成的后果并不相同，需要分别控制。

## 第 2 层：权威、权限和观察为什么不能合并

**面试官：** 你说 RPC 没有资产权威，但用户完全依赖它查余额；R 有 allowance，又不是用户的私钥持有人。这两种权力怎样区分？

**面试者：** 我会分别叫它们裁决规则、执行能力和观测来源。U 按代码决定哪次余额变化合法，这是状态规则；A 的签名与 `allowance(A,R)` 给出受约束的执行能力；RPC 报告某个区块的状态，这是观测。一个组件可以同时拥有多种角色，但不能把角色互相替代。

R 不持 A 私钥，并不意味着它无法影响 A 的资产。A 批准 R 后，R 的代码能在 allowance 与余额允许范围内调用 U，因此必须检查 spender 的代码路径。反过来，RPC 即使显示 A 有 5000 U，也没有替 A 授权的能力；它可能只是误报或恶意误导。

设计上，钱包签名前应展示实际目标和权限，查询输出应附链与区块位置，服务状态中区分用户授权、交易尝试和链观察。如果把这三种概念压成“已验证账户”，后续就很容易将“查到授权”解释成“资金已冻结”，或把“节点返回成功”当作最终化证明。

## 第 3 层：多个真实读数可能拼出不存在的状态

**面试官：** 那只要让 RPC 返回真实数据就够了吗？比如储备、余额和 allowance 都是真值，为什么还需要区块位置？

**面试者：** 因为这些值可能来自不同时间或不同分支，逐项真实不代表组合真实。报价用 H0 的 U 储备、H1 的 W 储备，再用 H2 的授权，可能拼出从未共同存在的一组状态。即使所有接口都诚实，这个组合也不能作为同一时点的报价或履约依据。

我会让 Q1 绑定 chainId、blockHash、R/P 地址、资产身份和规则版本，读取支持固定区块语义的接口；若只能按高度读，还要核对哈希与父链，检测读取过程中发生的重组。读取失败或端点不支持所需历史时，明确降级或拒绝，而不是默默回落到 latest。

固定快照只能说明“这个计算对应一组可说明的历史状态”，不能保证未来 nonce42 按相同状态执行。A 的余额、授权和池价格仍可能变化。所以快照一致性解决的是观测自洽，minOut、deadline 与真实转账检查解决的是执行时约束，两者缺一不可，也不是相同保证。

## 第 4 层：第三方 RPC 说谎时证据到哪一层

**面试官：** 快照带了 H0，但如果 RPC 连 H0 和回执都一起伪造呢？仅仅保存区块哈希是否已经去信任化？

**面试者：** 没有。给假数据加一个哈希字段仍然是假数据。区块位置使事实可追溯，但要判断它是否属于接受的链历史，还需要可信的验证路径。最直接的方案是运行正确配置、正常同步的执行与共识客户端，自己验证状态转换和共识历史；仍应说明客户端实现、硬件运行与共识假设。

多家 RPC 交叉检查能发现分歧、降低某类单点故障，却不自动构成密码学证明，尤其多端点可能共享基础设施。依赖第三方时，产品就应承认自己信任这些服务对规范头、回执和最终性标签的报告，而不是宣传完全无信任。

若采用轻客户端或证明方案，必须把状态或回执证明绑定到已验证区块头及其共识归属。仅有交易签名不能证明它被包含；仅有 Merkle 路径也不能证明路径对应的是正确规范头；普通 `eth_getLogs` 响应本身没有替用户完成这些验证。

## 第 5 层：包含证明也不证明所有业务语义

**面试官：** 假设你已经验证了回执包含，且 status=1。还需要信任什么，为什么不能直接确认 I1 买到 W？

**面试者：** 包含证明可以支持“这个回执属于这个已验证区块”，`status=1` 支持交易外层执行成功，但 I1 的业务结论还依赖调用语义。需要核对交易确实调用预期 R、输入路径和金额、收款人 A，以及本次对应的 P 与代币事实。发给其他地址的成功交易不能因为复用了一个应用标签就变成 I1 的交换。

对于本模型，R 没有捕获必要失败后继续成功的分支，U/W 也是预先限定的标准代币，因此合法调用成功与预期池交换之间有较强关系；这来自已经声明的代码假设，不来自 status 字段本身。接入一个会批处理并忽略子调用错误的 Router，就必须重新核验对应子调用结果。

此外，即使某次成功日志包含了写着 Swap 的事件，任意合约也可能发出同名事件。必须校验发出地址、ABI、参数和代码身份，结合必要资产/池状态事实。证据强度应与声称的结论匹配，不能用形式正确的日志替代语义正确的资产交换。

## 第 6 层：有语义证据仍然要区分规范链与最终性

**面试官：** 你已经核对了真实 R/P 和资产事实。为什么“已包含”仍不足以作为不可撤销结果？

**面试者：** 因为执行结果属于某个区块及其分支。当前规范链接受 H1，不保证下一次观察时 H1 仍然在规范历史里；普通重组可能移除它。因此我保存包含块哈希和当前归属，允许尚未最终化的观察失活，并把“成功执行”与“最终性等级”放在两个维度。

本模型以经验证节点提供的 finalized 检查点 F 为依据，确认 H1 是 F 的祖先。单看 H1 的高度小于 F 的高度不够，因为可能是同高度另一条分支；必须建立在同一条经验证连续历史上。safe 也是有含义的共识进度标记，但不能冒充 finalized。

若最终性信息不可用，就停留在已有证据支持的阶段。若先前已接受的最终前缀与新观察矛盾，这超出正常重组处理范围，应停止依赖该事实开展不可逆动作并调查。所谓最终性是明确共识假设下的强承诺，不是一个绕过所有依赖的绝对真理。

## 第 7 层：合约不可升级也不意味着完整行为永远固定

**面试官：** 那我把 R/P 都写成 immutable，就能说资金路径已经没有管理信任了吗？

**面试者：** 只能说本例去掉了 R/P 的升级和管理员入口，不能据此忽略调用依赖。真实系统还应核对代币是否可升级、暂停、黑名单、增发或改变转账行为，外部预言机和路由注册表是否可改，以及所谓 immutable 地址是否指向一个可升级代理。

本例明确假设 U/W 没有这些权限，因此正常推导可以使用标准转账和逐币种守恒。若将 U 改为可黑名单资产，就是改变了前提：即使 P 不可升级，U 管理者仍可能限制 P 或 A 的转账；资金路径就出现新的控制点。不能一边使用无黑名单的守恒模型，一边在故障回答里凭空让管理员“解冻”。

我会画依赖权限图，沿每条调用边问“谁能更改目标或行为”。多签和延时提高管理操作门槛、提供反应窗口，但没有消除治理能力；不可升级也不能修复原有漏洞。应分别描述故障预防、变更治理和用户选择权，而不是把 immutable 当安全审计结论。

## 第 8 层：把去中心化承诺改成可检验的假设

**面试官：** 你列了这么多依赖，面试时怎样给出一个有判断的结论，而不是只说什么都有风险？

**面试者：** 我会给出可证伪的承诺：本模型里，平台 Go 进程无法独立移动 A 的资产；用户可以不依赖该平台界面自行调用已核实的 R；交易结果由 U/W、R/P 的执行规则和链共识历史决定；平台展示依赖节点与索引，允许晚到但不得创造资产。这些是具体边界，不是泛泛而谈。

然后对每个依赖做一次最小反例：关掉 Go，检查用户是否仍能构造并发送；让 RPC 返回不同哈希，检查是否停止升级确认；替换成同名恶意代币，检查资产身份是否按地址拒绝；将已包含块移出规范链，检查投影是否撤回。若某个承诺在反例下不成立，应缩小承诺或补上机制，不能改口换架构。

“去中心化程度”因此不是一个总分，而是一组按权力、可验证性与退出能力描述的属性。资产非托管、排序不偏袒、数据可得、管理员无权改规则和入口抗审查是不同命题；证明其中一项不等于证明其余全部。

## 本题收束

- **讲透的机制**：以状态和能力划分权威，用区块位置与验证路径支撑观察，把执行语义、规范归属和最终性分层。
- **易错边界**：多 RPC 不等于共识证明；带哈希不等于数据真实；包含证明不等于业务语义正确；代码不可升级不等于依赖不可变。
- **具体反例与验证**：主例只把 U 换成一个有黑名单管理者的同精度代币。检查旧的“R/P无管理员所以任何人都不能阻断退出”是否被撤回，并重新列出 U 的控制能力。这个对照能检验是否真的按依赖权限推理，而不是背诵非托管标签。
