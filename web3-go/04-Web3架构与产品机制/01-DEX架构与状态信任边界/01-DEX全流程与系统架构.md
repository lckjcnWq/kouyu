# 大问题 1：从用户发起到资产交换完成，一笔 DEX Swap 的完整流程与系统架构是什么？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| DEX / Swap / AMM | 去中心化交易系统、换币动作、按池内资产公式交易的自动做市机制。 | 本文是单链非托管现货换币，没有 Go 撮合成交的阶段。 |
| A / U / W | A 是用户地址，U/W 是两种教学代币。 | A 初始有 5000 U，用 2000 U 换 W；U 为 6 位小数、W 为 18 位。 |
| R / P / LP 份额 | R 是执行路径与保护条件的路由合约，P 是池，LP 份额代表流动性提供者的权利。 | 交易者 A 换币不会因此自动获得池的赎回份额。 |
| 钱包 / EOA / 非托管 | EOA 是私钥控制的外部账户；钱包帮助用户核对并签名；非托管描述平台不直接支配资产。 | Go 没有 A 私钥或可提款内部余额，不等于用户无需信任合约代码。 |
| B0/H0 / Q1 | B0/H0 标记报价所用的具体区块，Q1 是这次报价。 | 报价只对该历史状态有计算依据，不锁住未来池价。 |
| approve / allowance / spender | 设置代币使用权限、可用授权额度、获授权使用者。 | R 作为 spender 拉取 U；前置授权是独立交易，不是 Swap 已付款。 |
| minOut / deadline / recipient | 最少收到多少、最迟允许执行的时间边界、给谁收币。 | 必须写入实际调用并由合约落实，本例时间恰等于 deadline 就拒绝。 |
| EVM / 原子性 / revert | EVM 是合约执行环境；原子性是单笔相关变化共同提交；revert 是回滚。 | Swap 不能正常留下只扣 U 不付 W 的半笔结果，但前置 approve 不随它回滚。 |
| Gas / nonce / txHash | 链上执行资源、账户交易序号、签名交易哈希。 | 已包含失败仍耗 Gas 和 nonce；nonce42 与新发 nonce43 可能构成两次兑换。 |
| I1 / attempt / RPC 超时 | I1 是应用意图，attempt 是具体交易尝试；RPC 超时是节点接口未及时答复。 | 应保留原 hash/nonce 查询或重广播，不能把超时当作未执行。 |
| canonical / finalized | 当前接受的规范链、在共识假设下最终确定的链段。 | 已包含与最终确定分开，最终性核对确切区块的祖先关系。 |
| 索引 / projection / Outbox | 扫描链事实、生成查询视图、在本地事务里登记待发通知。 | 写页面数据不会再次交换资产；扫描、投影、游标和通知记录需可靠衔接。 |
| active / revision / 重组 | 当前有效性、本地修订号、规范链切换分支。 | 旧成功观察可能撤回再激活，本地版本提高不等于链永不回退。 |

## 把整篇文章压缩成一个故事

小林拿 2000 U 去换 W。Go 先给计算结果，钱包核实后由小林授权并签名；真正决定能否换成的是链上 R/P。主例没有其他交易改变条件时，小林从 5000 U 变成 3000 U，获得 0.995015938219190933 W，ETH 执行费另算。报价、授权、广播都只是途中的站点，不是最终成交。

假设广播时网络断了，小林看不见结果。系统要保留原签名交易继续查，不能因为页面空白就让小林再签一个新序号，否则两笔可能都成功。若查到执行回滚，则解释清楚：没有半笔换币，但已包含失败仍付执行费，先前那笔独立授权也可能留下。

成功以后，系统还要核验是哪笔调用、属于哪条规范分支、是否满足最终性，再把页面和通知补齐。若未最终确定的块被替换，就撤回旧展示并继续追踪，不是发一笔反向兑换。本文把这一趟流程讲完，是为了不让“接口成功”掩盖资金、共识和展示三个不同完成点。

**流程位置与核心机制：** 建立端到端主线，解释报价、授权、签名、排序、执行、确认与展示如何衔接。后续母题分别深入权限、原子性和故障恢复，本题先把每个交接的责任讲完整。

**必要前提：** 沿用[总览](README.md)第 1.1—1.2 节的单链非托管 AMM 教学模型。A 用 2000 U 换 W，R/P 不可升级且无管理员，Go 没有私钥或内部资产账本；不在回答中临时改成链下订单簿。

## 第 1 层：先讲完一笔业务

**面试官：** 从用户发起到资产交换完成，一笔 DEX Swap 的完整流程与系统架构是什么？

**面试者：** 我会先说明，本模型的价格估算在链下，真正的资产交换和池状态裁决在同一笔链上交易内完成，不存在“Go 撮合完成就算成交”的阶段。

```text
A 请求报价 → Go 读取 B0/H0 池状态 → 返回 Q1 和执行保护
    ↓
钱包核对链、合约、币种、金额、收款人和授权
    ↓
必要时独立 approve R → A 签名 nonce42 的 Swap
    ↓
广播并关联 I1/attempt → 跟踪包含状态
    ↓
规范区块按实际顺序执行 R/P → 成功交换或整体回滚
    ↓
核验交易语义和所在区块 → 等待模型要求的最终性
    ↓
索引提交查询投影和通知 → 展示结果与同步位置
```

主例无状态变化时输出 `0.995015938219190933 W`，A 变为 3000 U 和该数量 W；P 收入完整 2000 U 并支付相同数量 W。A 另付 ETH Gas。交换在区块执行中成立，达到最终性提高结果承诺，页面同步则是另一个完成点。三者可以时间不同，不能只以接口返回 hash 结束整笔业务。

## 第 2 层：把流程中的状态权威落实

**面试官：** 你区分了几个完成点，但钱包、Go、代币合约和池都保存数据。究竟谁有权修改什么？

**面试者：** A 的钱包掌握交易签名能力；Go 管理用户请求、报价和广播尝试，却没有移动 U/W 的独立权力。U/W 合约维护各地址余额和 allowance，R 是 A 授权的 spender；P 的资产余额记在代币合约中，P 自己还维护储备缓存和 LP 份额。这些状态由链上执行规则更新。

R 把用户的 `minOut、deadline、recipient` 落实为执行约束；P 检查收到的真实输入及费用调整后的池不变量。验证节点执行交易并接受某条共识历史，决定哪些合约变化进入当前规范链。索引器只把这些事实映射成方便查询的数据。

所以“Go 中 I1 已完成”最多是一个有证据支持的派生结论，不能让 A 获得链上并不存在的 W。反过来，数据库暂时未更新也不影响已经在规范链发生的资产交换。设计接口时，应返回事实来源与阶段，而不让一个无来源的 `success=true` 同时代表所有层。

## 第 3 层：非托管流程为什么仍需要授权

**面试官：** 既然 Go 不碰资金，R 为什么能把 A 的 2000 U 转入 P？A 已签名还不够吗？

**面试者：** A 签名 Swap 交易，允许以 A 为发送者调用 R；但 R 再调用 U 时，U 看到的调用方是 R，不是 A。因此普通 ERC20 路径还需要 `allowance(A,R)` 足够，R 才能调用 `transferFrom(A,P,2000e6)`。签署交易和配置代币使用权限是两种不同授权。

需要补额度时，A 先发一笔普通 approve。主例可以把前置批准记为 nonce41，Swap 记为 nonce42，不能把两个独立交易画成一个共同原子提交。approve 成功并没有兑换 W，也没有把 2000 U 冻结起来；A 仍可能转走 U，其他受授权操作也可能消耗余额。

如果额度足够，不必每次新增 approve。若给超过本次需要的额度，未来风险范围随之扩大，钱包应明确展示 spender 和额度，而不是用“为了交易请点确认”掩盖权限。即使 R 在本模型中不可升级，也应核实地址与实际代码身份，不能只凭名称或网页标签判断。

## 第 4 层：授权和报价之后仍可能失败

**面试官：** 你已经检查余额、授权并给了报价。为什么执行时还会失败，系统该怎样解释？

**面试者：** 检查只针对观察到的状态，未来执行前可能有其他交易改变池储备、A 的余额或授权。主例 Q1 来自 B0/H0，真正 nonce42 的交易在后续区块执行，必须重新受当时的链上状态约束。Go 提前算过并不构成锁价。

例如单独改变池价格，使实际输出低于 `990040858528094978` 个 W 原子单位，R 应拒绝并让整笔 Swap 回滚。又例如 A 转走 U，R 的转账失败，同样不能只记录“缺少部分输入”后继续产生成交。执行时间达到 deadline 时，按照本 R 的严格小于规则拒绝，即使用户在截止前已经点击确认。

页面应区分“报价已返回”“交易执行回滚”和“尚未知道结果”。已经包含的失败交易可能消耗 Gas 与 EOA nonce，但没有半笔 U/W 交换；前置 approve 可能保留。不能用“交易失败所以什么都没发生”解释所有状态，也不能为改善成功率自动放宽 minOut 或更换收款地址。

## 第 5 层：RPC 超时后的恢复仍属于同一笔业务

**面试官：** 假如不是明确回滚，而是发送 nonce42 时 RPC 超时，页面怎样恢复，才能不让 A 再买一份？

**面试者：** 把它当传播未知，保留 I1 与原交易 hash、sender、nonce、调用摘要的关联。签名字节不变时，可以重新广播同一原始交易；它仍是同一 hash，不会因网络重发变成另一个链上交易。

同时查询原 hash、相关替换关系以及规范历史中的 nonce42，确认实际包含的是什么。若 A 选择加速，应由钱包重新确认同 nonce、同一经济调用的费用替换，不能由 Go 私自签名。若取消，同 nonce 的取消交易也只是在竞争，并不保证能抢在 Swap 前生效。

最危险的“重试”是直接使用 nonce43 再发相同 Swap。P 不保存 I1，nonce42 和 nonce43 都可能合法成功，应用数据库的唯一 requestKey 无法阻止用户钱包外的第二次交易。此时查询暂未找到回执不是不存在的证明；系统要显示待核验并继续原意图，而不是靠再次执行掩盖未知结果。

## 第 6 层：链上成功与链下提交之间的窗口

**面试官：** 假设原交易确实成功了，但 Go 在写数据库前崩溃。是不是仍可能丢成交，需要把链和数据库放进一个事务？

**面试者：** 链和数据库不共享原子事务，也不需要让 Go 变成第二个资产裁决者。恢复依据是链上可追溯事实：从已提交扫描游标继续，核对规范区块、回执与相关池事件，把遗漏的观察重新交付给投影服务。

链下可以把一个完整扫描块的观察写入、派生状态更新、游标前进与 Outbox 通知放进同一本地事务。提交前崩溃就重新处理；提交后重复到达，依据事件实例身份与激活状态避免再次应用。通知允许至少一次，下游按意图和 revision 识别重复或旧版本。

这能让展示最终跟上交易，但不是“数据库重做一次扣款”。本模型没有平台可用余额要结转，重复事件不能被解释成又收到一份 W。若只是把 `receipt.status=1` 直接映射成完成，也仍不够；需核对本次调用的目标、用户保护与真实交换语义，随后再处理其最终性。

## 第 7 层：重组会打破普通单调状态机

**面试官：** 你说投影避免重复应用，但已显示成功的区块后来被重组了，难道状态还能从成功退回去？

**面试者：** 可以撤回尚未最终化的包含事实，而且必须显式表达原因。执行结果是相对于某条链历史的事实：旧 H1 上成功不等于新规范历史上也发生了同一交换。投影需要保存 sourceBlockHash、是否 active 与 revision，而不是只保存一个永远递增的状态枚举。

发现父链不连续或旧块失去规范归属时，从共同祖先撤回旧分支派生结果、补扫新分支。这个过程中保持可恢复的本地提交边界；查询要标重组处理中或切换至一个完整版本，不能把旧余额和新日志混在一起展示。相同事件实例日后再次回到规范历史，还应允许重新激活，不能永久被去重表屏蔽。

正常最终性判断，则要求包含块属于已验证 finalized 检查点的祖先前缀。不能仅以“等了两分钟”宣布完成。如果最终化前缀本身出现矛盾，应暂停依赖它的不可逆后续动作并升级处理，不能当作普通索引延迟静默修正。

## 第 8 层：依赖故障与业务闭环的最后边界

**面试官：** 你把结果依赖于节点和索引，那平台全面停服时，用户是不是仍然被这个架构托管住了？

**面试者：** 要分开资产控制和服务可达性。Go 停服不会自动取得 A 的私钥或改变 U/W 余额；A 可以通过其他合适的 RPC 和界面调用已核实的 R，前提是能够取得正确调用数据、授权足够、链正常且愿意付 Gas。这是可替代入口，不是任何故障下都有即时交易保证。

如果故障发生在 U/W 的规则、链共识、可用流动性或用户签名设备，换一个前端并不能解决。交易者 A 没有 LP 份额，也不能要求池按旧报价退回一次已经完成的 Swap。拥有 LP 份额的角色有另一套按份额取回池资产的路径，不能冒充交易者的无条件赎回权。

我会用四个时刻验收全流程：报价后、签名传播未知、已包含未最终化、最终化但索引未同步。逐个问当前资产在哪里、谁能继续、凭什么减少不确定性。只有这些窗口都能给出明确责任与证据，才算讲完了架构，而不只是列出了几个服务名。

## 本题收束

- **讲透的机制**：链下帮助构造与观察，钱包控制签名，R/P 在链上执行交换，节点共识提供历史与最终性，数据库只提交派生结果。
- **易错边界**：报价不是锁价；approve 不是交换；广播不是包含；已包含不是最终化；Go 写库不是链上记账；停服与资金托管也不是同一件事。
- **具体反例与验证**：从主例分别推演“approve成功但Swap回滚”“nonce42广播未知后又发43”“旧成功块被移除”“最终成功但数据库仍旧”。检查是否出现残留授权、两次交换、错误成功或重复派生效果。以上是手工验证方法，不代表已运行工程测试。
