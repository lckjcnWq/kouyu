## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| DEX / 产品 / 成交机制 | 去中心化交易系统、用户交易何种权利、交易条件如何形成。 | 现货、永续、预测市场是产品；AMM、订单簿、RFQ 是另一维度。 |
| AMM / 恒定乘积 | 自动做市机制、其中一种池定价与校验规则。 | 主例是单池现货，链上按执行时储备交换，不自动保存未成交限价单。 |
| 订单簿 / 撮合 / 部分成交 | 管理买卖单、让条件相容的订单配对、只成交其中一部分。 | 需要订单剩余量、排序和撤单竞争规则，不是给报价加一个限价字段。 |
| 托管 / 钱包授权 / 锁资 | 平台控制内部资产账户、用户授予合约权限、以机制限制资产再被另用。 | 三种资金安排不同，签名和 allowance 不等于资产已锁住。 |
| R / P / I1 / Q1 | 路由合约、池、应用意图、报价。 | 基线 P 不识别 I1；改订单机制后才另外定义订单消费屏障。 |
| orderHash / 订单 nonce / EOA nonce | 订单内容身份、授权消费编号、私钥账户交易序号。 | 用途和防重范围不同，订单级去重也不必然防同一需求换另一订单再买。 |
| maker / LP / RFQ | 提供交易条件者、流动性提供者、向报价方询价的机制。 | RFQ 报价可由对手签署，不再照抄 AMM 池曲线。 |
| firm / 定向报价 / 预占预算 | 有明确承诺条件的报价、限制交易对象、报价方内部先占额度。 | 不自动保证钱包资金链上锁定或一定及时履约。 |
| L1 / Rollup / sequencer | 基础链、一类依赖基础链结算的扩容系统、排序器。 | Rollup 可跑 AMM 或订单簿，不是与它们互斥的成交机制。 |
| 数据可得 / 状态证明 / 争议期 | 能否获得重建状态的数据、核验状态的证据、允许提出挑战的阶段。 | 排序器接收不代表 L1 最终完成，不同 Rollup 的等待与退出规则须分别核实。 |
| 桥 / 跨链消息 / 在途权利 | 衔接链间资产或信息的机制、链间通知、流程未完成时可主张的权利。 | 源链换币已成功而目标步骤失败，不代表所有链都回到起点。 |
| EVM 原子性 / 端到端一致性 | 单笔合约调用共同提交、跨阶段结果可恢复地对齐。 | 单链一笔回滚不会自动撤销别链已执行步骤或链下已成立义务。 |
| canonical / finalized / 投影 | 规范链、按共识前提最终确定、派生查询视图。 | 不能把受理、执行、结算和页面速度放在同一个延迟指标里比较。 |
| 信任假设 / 退出凭证 / 反例 | 承诺依赖的条件、支撑取回权利的证据、用来推翻过强承诺的场景。 | 比较谁能动钱、谁排序、谁验证、故障下如何退出，而非给去中心化打一个总分。 |

## 把整篇文章压缩成一个故事

小林原本只要拿 U 立即换 W，单池 AMM 加自行签名就够了。产品经理想加限价挂单，于是系统不能只改一个价格字段，还得回答订单剩多少、撤单和成交谁先成立、资金是否真被限制再用。若链下已承诺成交，链上结算失败也不一定能靠删记录取消义务。

另一个独立方案找报价方给 RFQ 确定条件。签名报价使条款有凭据，却不代表对方钱包已锁资；若改用 Rollup，排序器的快速接收又是执行环境变化，不会把 AMM 自动变订单簿，更不能冒充 L1 最终结算。每改一个条件，系统都要重新说明资产、权限、完成证据和失败责任。

如果再跨链，源链已换币而桥的后续步骤失败，不能用“原子性”声称一切回到小林最初的资产。应定位资产与权利停在哪里，只恢复未完成步骤。本文最后选择的是满足真实需求的最小组合，并按相同阶段比较费用、速度和退出能力，而不是把不同维度的名词排成一张先进程度榜。

**流程位置与核心机制：** 在已经讲清主例后比较替代方案，回答什么条件变化会迫使架构变化、收益与代价分别是什么。本题不是给项目贴“更去中心化”的总标签。

**必要前提：** [总览](README.md)的单池 L1 AMM 是唯一贯穿数值基线。每个对比明确改变的条件，相互独立，不把签名订单、托管余额和 Rollup 快速回执悄悄拼成本例已有能力。

## 第 1 层：先分开比较维度

**面试官：** 怎样比较 AMM、订单簿、RFQ 和 Rollup 架构，而不混淆资产权威与信任假设？

**面试者：** 先分维度。AMM、订单簿和 RFQ 主要描述流动性组织与成交条件形成机制；现货、永续和预测市场描述交易的产品；托管账户、钱包授权和合约锁资描述资产控制；L1、Rollup、应用链描述执行与共识环境。它们不是四个互斥选项。

本例的组合是“现货＋单池AMM＋非托管钱包授权＋Ethereum L1原子执行”，所以链下没有撮合成交承诺，链上一次执行就形成价格实现和资产交割。一个订单簿也可以完全在链上运行，或链下撮合、链上验证结算；一个 Rollup 同样可以运行 AMM 或订单簿。

比较时我会为每个候选填清资金放在哪里、谁能移动、谁排顺序、谁验证执行、什么状态是权威、用户怎样退出。只有把这些填完，性能与成本的比较才有同口径；不能拿“链下报价很快”与“链上最终结算很慢”当作两种架构的同阶段延迟。

## 第 2 层：从 AMM 改成订单簿改变了什么

**面试官：** 如果业务要求限价挂单和撤单，而不是立刻向池交换，把本例改成订单簿要增加什么？

**面试者：** 这是改变成交机制，不只是给 Q1 增加一个价格字段。订单簿需要持久订单身份、剩余数量、排序规则、部分成交与撤单竞争的裁决，以及可恢复的订单簿状态。AMM 本例中未成交的用户意图不会自动留在链上等待未来价格，也没有服务接纳后必须执行的限价单权利。

若选择链下撮合，还要声明链下结果究竟是候选匹配还是不可撤销义务，并解释资产可履约性。若资产已在托管账户预留，预留与撮合资格要协调；若只有钱包签名，余额和授权会变化，不能靠签名把可用余额冻结住。两种路径的资产权威和失败责任不同。

所以我不会沿用本例“单笔Swap回滚就没有其他义务”的结论。如果链下已承诺不可撤销成交，链上结算失败可能留下待履约义务，不能直接删掉。相应系统必须有独立的交易一致性与履约恢复设计，不能用池的原子性来替代。

## 第 3 层：签名订单又不等于链下托管账户

**面试官：** 那我采用钱包签名限价单，链下订单簿只负责发现，是否就不需要资金和重复控制了？

**面试者：** 仍然需要，只是控制点改变了。签名证明授权条件，不保证余额和 allowance 将来仍然足够，也不自动记录已成交数量。结算合约需要验证域、订单身份、金额、接收人、期限和部分成交累计量或 nonce 消费状态；取消与成交也要由同一权威规则竞争。

链下可以检查余额、限制曝光或做自己的风险预算，但如果没有链上锁资或等价约束，就不能承诺绝对可履约。一个 maker 用同一份钱包余额签出多个订单，不会因为每次签名前余额充足，就让所有订单都能同时结算。订单发现服务的数据库锁也无法阻止钱包外转账。

与本例相比，增加的是跨交易生命周期的订单资格和消费状态。本例 P 不保存 I1，订单合约可能保存 orderHash 的累计成交；但这种订单级防重仍不必然防同一经济需求切换到另一个订单后重复购买。比较架构时应明确防重作用域，而不是笼统写“签名订单天然幂等”。

## 第 4 层：改用 RFQ 得到的承诺有多强

**面试官：** 如果改为找 LP 报一个 firm RFQ，是否就能避免 AMM 报价失效的问题？

**面试者：** RFQ 改变了报价来源与承诺形式。LP 可以签署定向、限时、确定数量的报价，链上合约按签名条件交换，不再按本例池曲线即时求价；用户看到的是有签名依据的执行条件。但是 firm 不自动表示 LP 资产已链上锁定，也不保证用户能及时包含交易。

若 LP 仍自行控制钱包，可能转走资产或撤销授权。LP 自己的风险系统可在签名前预占预算，避免内部过度承诺，但它只约束经过该系统的行为。真正履约仍要靠执行时资产、授权以及报价消费规则，或另行引入明确的锁资机制。

因此收益是可定向协商条件、可能更少价格不确定性，代价是依赖 LP 可用性、资本承诺管理、签名资格和取消规则。AMM 主要依赖池内流动性与曲线，RFQ 依赖报价者及其资金安排；不能简单说一种“无滑点所以没有信任”，更不能将 RFQ 的报价nonce当成EOA交易nonce。

## 第 5 层：改变执行环境后确认语义不能原样搬走

**面试官：** 这些成交机制都可以放到 Rollup。为了更低费用，把本例搬到 Rollup，是不是只换 chainId？

**面试者：** 不是。调用代码可能相近，但排序、数据可得、状态证明、L1结算与退出路径的依赖会变化。排序器快速回执可改善体验，却不等于L1最终化资产结果；用户还需知道数据是否已发布、相应证明或争议机制处于什么阶段，以及系统如何处理排序器故障。

不同Rollup的机制不能一概而论。乐观与有效性证明方案的最终性链路、升级权限和退出条件不同，是否存在强制包含、逃生或可独立重建状态也必须针对具体协议核验。不能从“有证明”推导任何时候都可以马上提现，更不能随便套一个统一等待天数。

与本例L1相比，新增收益可能是执行成本与吞吐改善，代价是更复杂的排序、数据与结算依赖。产品应分别展示排序器接收、L2包含和所采用的结算完成点。如果为了速度提前授信，则又新增平台风险承担，必须单独说明，不能用同一个success覆盖全部阶段。

## 第 6 层：跨链组合不能借用单笔原子性

**面试官：** 如果为了更好价格，先在 Rollup 换 W，再跨链到 L1，你还会沿用“失败全部回滚”吗？

**面试者：** 不会。这改变了执行范围，通常存在多个交易、桥消息和不同链的最终性。本例同一笔EVM调用的原子回滚，只能覆盖本链本次调用内部的状态，不能撤销已经在另一条链完成的转账或交换。

需要拆清每一步的权威结果、资产在途位置、消息身份、可重放性与超时后的权利。源链交换成功而桥或目标链步骤失败时，用户可能持有源链资产、桥内权利或可领取退款，而不是自动回到最初5000 U。重试应对准未完成步骤，不能把整个流程从头再执行一遍。

若采用支持特定跨链原子交换的协议，也要说明额外的锁定、证明、时限和失败条件，不能以“用了跨链协议”省略机制。架构收益是更广的流动性或资产可达性，代价是更长完成链路、更多信任与资本占用。报价比较必须把这些阶段与费用纳入口径。

## 第 7 层：怎样在收益和新增信任之间做选择

**面试官：** 你把每种方案的复杂性都讲出来了，实际设计时怎样选，而不是永远保留所有可能？

**面试者：** 从明确产品需求选择最小足够组合。如果目标只是单池现货、用户自行保管资产，并接受链上等待，本例AMM已能满足，不应为了架构显得复杂再引入链下账户、撮合、桥和排序器。若需求是限价挂单、专业做市或低成本高频更新，再评估相应机制带来的新增状态和责任。

我会把候选方案按同一笔业务的约束对齐：净输出、费用、最大允许损失、最晚执行时间、资金占用、可撤销性、最终结果承诺、故障下用户还可做什么。性能也分别测报价、受理、执行、最终性和查询，不比较不同阶段的数字。

关键问题是新增信任是否有对应收益，能否被限制和验证。例如允许管理员升级可以修复漏洞，但会增加改规则能力；延时能提供反应窗口却不消除能力。如果无法证明用户有实际退出路径，就应如实限制承诺，而不是用“去中心化”作为无需解释失败责任的理由。

## 第 8 层：用一套反例检查不同架构的承诺

**面试官：** 最后怎样验证你的比较没有只是换标签？给一套跨架构也能使用的检查方法。

**面试者：** 先让每个候选写出权力—状态—证据—退出四项，再用同样的问题施压，但按各自规则判断。服务停机时，用户可否绕过入口；排序方拒收时，是否真有其他包含路径；资产管理者改变规则时，谁的转账或退出会受影响；交易结果未知时，什么身份防止重试新增一份权利。

接着移除尚未最终化的包含事实，检查查询是否能撤回、在途义务是否仍正确；让同一事件重复并重新进入规范链，检查不会重复派生或永久丢失；把两步之间的进程杀掉，检查恢复是否依赖一个从未持久化的承诺。这些是故障时序问题，不能靠更换“AMM”“订单簿”“Rollup”的名字解决。

验证输出应是“在这些前提下，这项承诺成立；改变这一权限后，该保证失效”，不是不加限定的架构排名。本次提供手工反例和文档检查，不声称已执行多链故障演练、链上实验或协议安全审计。

## 本题收束

- **讲透的机制**：产品、成交、资产控制和执行环境分维比较；每次改变前提，都重新推导权威状态、完成语义与失败责任。
- **易错边界**：非托管不是成交机制；Rollup不是订单簿的替代名；签名不是锁资；firm不是必然履约；跨链不能继承单笔EVM原子性。
- **具体反例与验证**：只将主例的L1执行改为“排序器先返回接收回执”。若材料仍用同一个完成点宣布L1最终资产到账，说明比较遗漏了结算依赖。要求补出数据、状态验证、结算与退出证据后，再讨论速度收益。
