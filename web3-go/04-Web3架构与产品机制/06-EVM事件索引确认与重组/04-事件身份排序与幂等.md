# 大问题 4：重复、乱序与重入块怎样识别？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| C / T / D | 核验后的 USDC 合约、链上交易、平台充值业务身份。 | T 的观察可变，D 对应的资金义务不能因此履行两次。 |
| chainId / genesisHash | 链编号与创世身份。 | 观察键放在已绑定创世块的链配置下，不混入另一条历史。 |
| observationKey | 分支内一次日志观察的完整定位键。 | 本文为 (chainId,blockHash,txHash,logIndex)，不是只用交易哈希。 |
| H101a / H102b / blockHash | 旧、新分支具体区块的教学符号，以及区块哈希。 | 同一 T 从 101a 重入 102b 后，必须保留两份不同观察。 |
| logIndex / transactionIndex | 日志在整个块内的位置，以及交易在块内的位置。 | 主例交易位置 2、日志位置 7；重入后日志位置可变成 4。 |
| 交易内事件序号 | 从某笔交易完整回执的日志序列另行派生的位置。 | 不是 RPC 的 logIndex，重入执行变化后也不能无条件当稳定业务身份。 |
| depositId / orderId / 业务键 | 协议定义的充值或订单标识，以及识别业务义务的键。 | 普通 Transfer 没有这些原生字段，要明确作用域和多日志匹配规则。 |
| canonical / 候选 / 已应用 | 当前采用分支、尚未采用的材料、已改动投影的状态。 | 原始日志已落盘只证明存过，不能据此跳过未完成应用。 |
| 载荷摘要 / 同键冲突 | 核对内容一致性的摘要，以及身份相同却内容不同。 | 同键金额从 25000000 变为 26000000 应隔离，不是最后写入覆盖。 |
| decoderVersion | 解码程序版本。 | 新版解释可不同，但要分别保存，不能把它伪装成原始日志改变。 |
| Observed / Reverted / 再激活 | 采用某观察、撤销它、在有效证据重新成立时恢复其作用。 | 不能用“处理过 D”永久封死后续有效观察；撤销必须指明具体来源。 |
| messageId / revision | 一条持久通知的身份，以及它在修订流中的位置。 | 41 是旧观察、42 是撤销、43 是新观察；重发仍用原消息身份。 |
| SQL sequence / 持久计数器 | 可因事务回滚留洞的序列，以及事务内共同提交的计数。 | 本文连续流用后者，不把留洞误判成消息丢失。 |
| chainEpoch / writerTerm | 分支代次与写入者任期。 | 一个隔开分支任务，一个围栏旧主，都不能代替 revision。 |
| Inbox / 连续已应用位置 | 消费事务的去重记录，以及已按顺序落实到的位置。 | 先收到 43 不代表可跳过 42；余额增量要先撤再加。 |
| 完整订阅流 / 过滤进度 | 消费者负责的连续流，以及只订阅部分消息时的进度契约。 | 只收子集不能拿全流整数的每个缺口都当丢失。 |
| finalized / 快照截止 revision | 链最终性边界，以及快照已覆盖到哪条发布修订。 | 最终确认后账本按 D 入账一次；重建不能清空去重后重新发钱。 |

## 把整篇文章压缩成一个故事

**起因：** 同一条 T 的日志从订阅和补扫各来一次，都是 H101a／T／7。索引器核对相同载荷，只应用一次 25 USDC，视图为 A=75、B=25。这里去掉的是同一次观察的重复投递，不是宣布所有与 T 有关的未来消息都无效。

**处理与异常：** 未最终的 a 分支被撤销后，T 在 H102b 的第 4 号日志重新出现。系统保留旧、新观察，用 revision 41 的旧观察、42 的撤销、43 的新观察表达变化；即使网络先送来 43，消费者也不能先加成 B=50，再丢弃迟到的 42。若原来同一观察以后重新有效，也应根据已撤销状态重新激活，而不是被“原始键见过”永久屏蔽；同键却换了金额则要停下核验。

**结局与不能混淆的边界：** 连续应用这些修订后，转账视图仍为 75／25，新观察满足 finalized 等条件后，账本按核验后的 D 入账一次 25。若 T 本来含两条合法 Transfer，只按 T 去重会漏业务；改用跨块 logIndex 又会误造新义务。观察键管证据、业务键管义务、messageId 管重投、revision 管顺序，不能让一个字段包办四件事。

**流程位置与核心机制：** 覆盖原始日志落盘、规范分支应用及有序发布之间的身份与顺序契约。核心是区分“在哪条分支观察到哪条日志”“这代表哪项业务义务”“这次状态修订排在什么位置”，不能拿一个 txHash 同时承担三个角色。单块原子提交见 05，撤销恢复见 08，可靠交付见 09。

**必要前提：** 沿用总览的 Ethereum 主网、可信 USDC 地址 C 与整数金额。T 在 `(101,H101a)` 的 transactionIndex=2、区块级 logIndex=7 产生一条 A→B、25000000 最小单位的相关 Transfer，即 25 USDC。初始转账视图为 A=100、B=0。下文未最终重组变体中，T 改为在 102b 重入、logIndex=4；它不与“101a 已被接受为 finalized”同时成立。平台仍只在 finalized 完整前缀及账本提交后入账。

## 第 1 层：先识别观察，再讨论去重

**面试官：** 同一条链上日志可能重复到达、顺序颠倒，交易也可能被重组后重新打包，怎样识别它们？

**面试者：** 先区分日志的分支观察身份与业务身份。在固定链配置下，采用总览的 `observationKey=(chainId,blockHash,txHash,logIndex)` 标识一次观察；链配置还绑定 genesisHash，不能把不同创世身份的数据混在同一命名空间中。重复收到 H101a 中 T 的第 7 号日志，观察键相同；T 重入 H102b 后，观察键不同，必须作为新分支证据保存。

这只能解决“是不是同一次观察”，不能直接决定余额是否增加。原始记录存在，不代表它已经应用，更不代表仍然 canonical。规范 writer 还要检查块的父链接、当前规范映射和应用状态，在单块事务内决定是否改变投影。同一个已完整应用块重复输入不再扣加，但只落盘过候选块时，不能因为存在观察记录就跳过正式应用。

## 第 2 层：日志位置为什么不能跨重组使用

**面试官：** 既然观察键里有 logIndex，能否去掉 blockHash，直接用 `(T,logIndex=7)` 表示这笔充值，既排序又防止重入后重复？

**面试者：** 不能。RPC 的 logIndex 是日志在整个区块内的位置，不是交易内部第几条日志。T 之前其他交易产生的日志数变化，即使 T 自身执行产生的日志序列相同，它的区块级 logIndex 也可能从 7 变成 4。把 `(T,7)` 当业务键，会把新观察误认成另一笔业务；按旧位置寻找，也可能漏掉它。

规范分支内的执行顺序用块高、transactionIndex 和 logIndex 表达，但块高必须对应已确定的 canonical hash；同高度不同 hash 的日志不能混排成一条历史。对于同一完整块，logIndex 本身已有区块内顺序语义，transactionIndex 可用于组织和交叉检查，不能与它矛盾。

若确需交易内序号，要从该笔交易完整且已核验的 receipt 日志序列另行派生，并明确它是“所有日志中的序号”还是某类事件序号。不能把 RPC 字段改个名字就当成交易内稳定身份。

## 第 3 层：一笔交易有多条 Transfer 时怎样匹配业务

**面试官：** 那不用 logIndex，只把 T 当业务键行不行？如果 T 一次给两个充值地址各转 25 USDC 呢？

**面试者：** 仅用 T 会把两条合法业务压成一条，导致漏记。主例的充值意图 D 能通过链、C、T、经核验的收款和金额关联，是因为已明确只有一条相关 Transfer；这是受控前提，不是通用去重公式。

协议有 depositId、orderId 时，优先按协议定义的链、合约或账户作用域组合稳定业务键，并校验该标识确实对应当前证据。普通 Transfer 没有这样的字段，就需要明确多日志归属规则：每条合格转账形成独立义务，还是若干日志按一个充值意图聚合；不能遇到相同金额就随意挑一条。

从完整回执派生的交易内事件序号可以帮助区分同笔交易的多条日志，但重入后的执行会受链状态影响，日志序列和金额不保证不变。即使使用 `(链,C,T,交易内序号)`，也只是经业务规则核验的候选关联。若两条同收款、同金额日志仍无法唯一匹配 D，就应保留歧义并阻止自动确认，不能用“先到先得”制造身份。

## 第 4 层：相同键却不同内容，不是正常重复

**面试官：** 业务匹配规则确定后，重复投递是否只需唯一约束，冲突就忽略？如果相同观察键或 D 对应的金额不一样呢？

**面试者：** 不能无条件忽略。对同一个 observationKey，address、topics、data、transactionIndex 等链上内容应一致；RPC 来源、观察时间这类采集元数据则可以不同。应保存规范化原始载荷及摘要，相同键再次到达时核对内容。若旧内容是 25000000，新内容是 26000000，这不是可接受的重复，要隔离该块、记录冲突并核验来源，不能覆盖原值或采用最后到达者。

decoder 升级导致解释变化，不应伪装成原始载荷变化；解码结果按 observationKey 加 decoderVersion 等版本分别保存。对业务键 D，也要区分允许变化的来源观察、确认状态，与受规则约束的资产、账户、金额等内容。

同一 D 在不同未最终分支中出现不一致候选时，应保留各自证据并重新裁决，不能因 D 相同就视为相同效果，更不能各入账一次。已提交的账本业务键再次收到不同金额，应返回业务冲突而非静默成功；必要纠正走授权流程，不通过修改幂等键绕过约束。

## 第 5 层：原始观察去重之后，撤销与重入怎样表达

**面试官：** 你保留了各分支证据。如果 101a 的 25 已展示，重组撤销后 T 又进入 102b，D 没变，会不会被业务去重挡住，导致页面永远显示撤销？

**面试者：** 这说明业务效果去重不能与观察状态修订共用一个“处理过 D”标记。原始层保留 H101a 和 H102b 两个观察；投影层按规范分支维护当前有效状态。先撤销旧观察对暂态视图的影响，再应用新观察，D 的证据关联可以从旧分支撤销状态转到新分支 included 状态，不能把新观察当成旧消息重发。

下游应接收不同的状态变化：`Observed(旧观察)`、`Reverted(旧观察)`、`Observed(新观察)`。每次变化有独立持久 messageId 和发布顺序；旧观察的撤销不能只发“D 已撤销”而不指明撤销的是哪份证据，否则迟到消息可能撤掉新观察。

账本则拥有另一条边界：两次 included 都不增加可提现充值，旧观察在未最终重组中消失也不需要冲正未发生的入账。等新观察所在块进入 finalized 完整前缀后，账本才按已核验业务义务 D 入账一次 25 USDC。观察状态能够多次变化，资金义务不能因此多次履行。

## 第 6 层：链高度回退，发布序号为什么不能回退

**面试官：** 你用发布顺序防止迟到撤销污染新观察。但重组要把 applied 从 103a 回到 100，revision 是否也恢复成检查点时的值？

**面试者：** 不能。块高描述链上位置，revision 描述平台已发布的状态修订历史；撤销本身也是新事实，不是把已经发布的历史抹掉。假设旧 Observed 的已提交 revision=41，撤销应为 42，新分支 Observed 为 43；即使 applied 高度退到 100，revision 也不能回到 40 后重新使用 41。

在本模型中，由串行 writer 在数据库事务内更新持久计数器，并将对应 Outbox 一起提交。事务没有提交，计数与消息都不生效；事务已提交而发送 ACK 丢失，重发的是原 messageId、revision 和载荷，不能临时生成一个新修订。

若下游以连续 revision 检测缺口，就不能直接把可能留洞的 SQL sequence 当成这条连续流的位置。确认、撤销、恢复边界都要遵守同一已声明流契约。chainEpoch 表示分支切换，writerTerm 用于隔离旧 writer；二者都不代替全流持久递增的 revision。

## 第 7 层：连续发布也可能乱序到达，谁来阻止旧状态复活

**面试官：** 即使 revision 不回退，网络仍可能先送到 43，再送到 42、41。下游只保存见过的最大 revision，是否就安全？

**面试者：** 对增量投影不安全。43 可能依赖 42 先撤销旧余额变化；直接跳到 43，可能使 B 累加成 50，再把迟到的 42 丢弃。最大已见值不等于连续已应用值。

消费者应按其完整订阅流记录已连续应用位置：持久接收乱序消息，41、42、43 按约定顺序应用；缺口通过重投或受控快照恢复解决。Inbox 去重记录、投影改变和消费进度应在自己的数据库事务内共同提交。同一 messageId 再次到达还要核对载荷；同 messageId 或同一流位置出现不同内容属于协议冲突，不能只因为“见过”就忽略。

如果下游仅订阅全流的一个子集，就不能直接用全流整数缺口判断自己漏消息，必须提供可验证的过滤进度或定义独立连续流。只有消息明确是可独立替换的完整状态、具备对象版本与删除语义时，才可能采用另一种乱序覆盖策略；不能把这种前提悄悄套到余额增量上。

## 第 8 层：重启或重建后怎样守住同一条身份契约

**面试官：** 如果进程重启、影子投影重建，或者切换 writer，上述键与序号怎样保证不会重新从头使用？

**面试者：** 身份注册、载荷摘要、已提交 revision、Outbox、账本业务去重记录都属于持久事实，不能随内存缓存或新投影清空。新 writer 必须读取当前持久状态，并在事务内用 writerTerm 围栏阻止旧 writer 提交。新投影可以重放历史事件，但不能把重放等同于新发生的业务，再发一次 D 的资金指令。

如果消费者确实无法保留旧增量历史，需要通过明确的流身份、快照截止 revision 和切换协议恢复，不能用同一流名称把 revision 重置为 1。快照与后续消息还要说明分支 hash、投影版本及完整水位，确保不会把旧分支的消息接到新状态后面。

可以手工推演一个验收序列：重复旧观察、撤销旧观察、应用新观察、迟到重发旧消息、确认新观察、重复 Finalized。期望暂态转账视图最终仍为 A=75、B=25，账本只增加一次 25 USDC。若途中同键载荷冲突，应显式阻断而不是强求“最终成功”；这是设计推演，不是已经运行的测试结论。

## 收束：机制、易错边界与反例

- **机制：** 观察键识别分支证据，业务键识别资金义务，messageId 识别一次投递事实，持久 revision 组织状态修订；各自有明确的内容一致性与提交边界。
- **易错边界：** logIndex 是区块级序号；txHash 不足以区分多条 Transfer；数据库存在原始观察不等于投影已应用；链回退不能使发布 revision 回退；同键异载荷不是正常重试。
- **反例检验：** 单独改变主例，让 T 含两条向不同平台地址各转 25 USDC 的 Transfer。若系统仅按 T 去重，第二笔会漏记；若改为按区块 logIndex 做跨重组业务键，又会在 T 重入新块时重复制造义务。正确方案必须先定义可核验的多日志业务匹配，再分别处理分支修订与 finalized 后的资金去重。
