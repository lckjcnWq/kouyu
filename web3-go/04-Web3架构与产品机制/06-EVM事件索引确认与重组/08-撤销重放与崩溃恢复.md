# 大问题 8：重组和进程崩溃叠加怎样恢复？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| a / b / H100 | 旧分支、新分支、共同祖先的区块哈希。 | 旧链到 103a，新链从 100 后分叉，已接受 finalized 仍是 H100。 |
| T / D / A / B | 交易、平台充值业务、付款地址、平台收款地址。 | T 的 25 USDC 从 101a 被移除后在 102b 重入，D 仍需防重复入账。 |
| undo / replay | 撤销已应用的派生变化，以及按新历史重放。 | 先 103a→102a→101a 撤，再 101b→102b→103b 放，不是链上退款。 |
| 恢复状态机 / 阶段 | 持久记录恢复过程，以及当前正在撤销、重放还是验收。 | 重启读数据库继续，不猜崩溃前循环跑到哪。 |
| tip / 预期 hash | 当前已应用末端，以及本次操作指定的具体块。 | 撤销入口要求二者一致，不能接受“再撤一次高度 101”的裸指令。 |
| recovering / healthy | 正在修复与通过本地恢复检查的模式。 | 恢复中可披露内部水位，但不能把半恢复结果用于健康资金决策。 |
| 前值 / schemaVersion | 修改之前的数据，以及撤销记录所用结构版本。 | 块内多次修改要逆序恢复，还要知道旧行原先是否存在。 |
| COMMIT / ACK 丢失 | 数据库提交，以及提交或交付确认没有返回。 | 没收到回执不证明撤销没成功，先读持久 tip 与任务状态。 |
| Outbox / Reverted | 事务内待发记录，以及撤销具体观察的通知。 | 撤销、任务前进、tip 和通知共同提交，防止重复减 25。 |
| observationKey / logIndex | 分支日志身份，以及区块级日志位置。 | 旧 H101a／T／7 与新 H102b／T／4 分开保存，不能仅用 txHash 屏蔽重入。 |
| revision / chainEpoch | 发布修订号与分支代次。 | 修订号撤销后仍递增，旧代次消息也可能是必须补消费的前序事实。 |
| generation / 影子版本 | 完整投影的版本，以及不直接暴露的重建版本。 | 可保留旧健康快照并标陈旧，完整新版本验证后再切换。 |
| 撤销窗口 / 快照重建 | 保留可直接 undo 的范围，以及从可靠基线重新计算。 | undo 缺失不等于任意日志取负就能恢复，复杂投影可能有顺序依赖。 |
| 最终性冲突 | 新候选否定了已接受 finalized 的前缀。 | 不属于普通撤放权限，不能擅自换快照接着跑。 |
| 恢复边界消息 / 消费水位 | 告诉下游完整切换位置的通知，以及下游已经应用到哪里。 | 本地重放结束不等于消费者已赶上，资金门禁要核对依赖版本。 |
| 账务冲正 / 外部资产 | 账本授权追加纠正分录，以及已发生的实际支付。 | 修复派生视图无权删账，也不会收回已经转走的钱。 |

## 把整篇文章压缩成一个故事

**起因：** A→B 的 25 USDC 在 101a 形成 75／25 的视图，但 a 分支尚未最终就被 b 替换。共同祖先已核验为 100，T 将在 102b 重入。服务进入 recovering，记住固定旧 tip、目标 tip、祖先与下一步，先撤旧链再放新链。

**处理与异常：** 撤完空块 103a、102a 后，进程恰在撤 101a 时崩溃。若事务未提交，数据库仍是 tip=101a、余额 75／25，重启继续撤；若已提交但回执丢失，则 tip=100、余额 100／0，Reverted 和任务进度也已落盘，不能再减一次 25。随后正序应用 b，新 H102b／T／4 应重新起效，不被旧 txHash 去重表挡住；途中查询标明恢复中，不展示拼接余额。

**结局与不能混淆的边界：** 新前缀完整后，视图又是 A=75、B=25，但证据来源必须是 102b；只看金额相等不能验收。核对父链、undo、Outbox、任务进度并生成恢复边界后，本地才可健康，下游和资金路径还看各自水位。旧分支没有最终入账，本轮无须账本冲正；若缺撤销材料或冲突触及已接受最终边界，就转隔离重建或事故流程，不拿“金额取负”冒充通用恢复。

**流程位置与核心机制：** 在已找到共同祖先之后，按事务边界撤销旧后缀、重放新后缀，并支持中途重启。这里的回退是派生视图恢复，不是撤回链交易或删除账本分录。

**必要前提：** 旧链 100→101a→102a→103a，新链在 100 后分叉；T 从 101a 被移除，随后在 102b 重入。接受的 finalized 仍为 H100，undo 材料足够。超窗口和最终性矛盾见 13。

## 第 1 层：先明确撤销与重放顺序

**面试官：** 重组和进程崩溃叠加怎样恢复？

**面试者：** 我把恢复当持久状态机，而不是启动时临时执行的一段循环。先记录旧 tip、目标新 tip、共同祖先、chainEpoch、阶段和下一块，进入 recovering，停止普通采用及不安全确认发布。按 103a、102a、101a 的逆序撤销到 100，再按 101b、102b、103b 的正序应用。每个块的 undo 或 apply 都在数据库事务内连同游标、任务进度和修订 Outbox 提交。重启读取最后已提交阶段继续，因此不会靠猜内存执行到了哪里来恢复。

## 第 2 层：为什么不能先应用新链再减旧链

**面试官：** 两条链的转账最后都抵消，先把新链应用完，再撤旧链不也一样吗？

**面试者：** 一般不一样。投影可能包含顺序依赖、业务状态机和检查条件，不是可交换的数值总和。即使本例都是 25，也可能短暂让 B 变成 50，被查询或下游当成两笔有效充值。用前值恢复时若先放新链，撤旧链又可能覆盖新值。正确做法是先逆序解除旧后缀的依赖，再从共同祖先状态正序重放；恢复期间不把中间状态伪装为健康完整视图。若采用独立影子版本重建，也要在完整验证后原子切换，不是在同一张活动表里随意交换顺序。

## 第 3 层：undo 应该保存什么

**面试官：** 你说要逆序撤销，保存一条“B 减 25”够吗？

**面试者：** 只对严格可逆、无额外副作用的增量可能够；通用投影还要恢复 A、明细状态、计数、索引与派生字段。基线保存块内每次变化的前值及应用顺序，并带 schemaVersion、源观察与变更身份。撤销按块逆序，块内也按相反顺序恢复，尤其同一个地址在一块内被多次修改时不能只读最终余额猜之前状态。新增行与更新行的撤销不同，需要知道旧行是否存在。undo 必须在原应用事务中持久化，不能应用完才异步补写，否则崩溃恰好发生时会缺材料。

## 第 4 层：撤到一半崩溃怎样不重复撤

**面试官：** 已撤完 103a、102a，撤 101a 时进程崩了，重启怎样裁决？

**面试者：** 读数据库当前 tip 和恢复任务位置，而不是重新从旧 103a 盲目跑。若 101a 的撤销事务没提交，tip 仍是 101a，投影仍为 A=75、B=25；下一次撤销同一块。若已提交但回执未到，tip 应为 100，观察已标为非规范或撤销，Reverted Outbox 与任务位置也已提交，不能再减 25。撤销入口要求当前 tip 恰好是待撤 hash，并核验任务阶段；已完成请求返回既有结果。事务原子性让恢复只有两个合法落点，没有半撤一块的第三态。

## 第 5 层：重启后如何重放同一交易

**面试官：** 撤到 100 后，T 在 102b 又出现，你的去重表不是会把它挡掉吗？

**面试者：** 如果去重表只有 txHash，就会错误挡掉。101a 的观察键包含 H101a 和区块级 logIndex=7；102b 的观察是 H102b、T、logIndex=4，两者必须分别保留。旧观察留作审计但不再规范，新观察按新块正常应用。业务意图 D 关联当前合格证据，不把新观察当第二份充值义务。因为旧分支尚未 finalized，账本还未入账，重放后待新分支最终性满足才入账一次。交易相同不代表观察未曾撤销，观察不同也不代表业务金额应加两次。

## 第 6 层：旧消息会不会复活撤销结果

**面试官：** 旧 Observed 已经发出但网络里延迟了，Reverted 先到，下游怎样不复活旧状态？

**面试者：** 修订消息必须带持久递增 revision、chainEpoch、源观察和水位。Reverted 不是删除旧消息，而是更高版本的状态变化；生产全链流按提交 revision 交付，消费者按连续进度或明确的对象版本规则处理，发现缺口先等待补齐。旧消息重复到达只触发去重或被当前版本拒绝，不覆盖新状态。chainEpoch 用于识别旧抓取和分支上下文，不能简单丢弃所有旧 epoch 的消息，因为其中也可能有必须补消费的前序变化。完整交付协议见 09，恢复器负责在每个撤销事务生成应有修订证据。

## 第 7 层：多事务恢复时 API 看什么

**面试官：** 你一次只撤一块，查询在 102a 撤完、101a 尚未撤时会看到什么？

**面试者：** 必须先给读取契约。最简单的基线是 chain_state 标 recovering，受影响 API 返回恢复中、当前内部水位和最后健康水位，不声称结果是可用于资金决策的规范终态。若要求持续展示，可以保留最后完整健康 generation，让只读请求绑定旧快照，并显式标记陈旧；新版本准备好再切换。不能读当前半恢复的余额再配上目标 103b 的水位。恢复的多块事务只是内部可续作边界，并不自动构成对用户一次性原子换链。

## 第 8 层：恢复期间又发生一次重组

**面试官：** 刚把 101b 应用完，目标分支又被 c 替换，是否继续沿 b 到 103 再说？

**面试者：** 不应无条件继续，也不能中断在半块。先完成或回滚当前块事务，持久记录现有 tip 和任务状态，再核验新候选分支。若 c 延续当前已应用前缀，可以调整后续目标；若它否定已应用的 101b，则基于当前持久 tip 重新定位祖先并生成新恢复计划，增加 chainEpoch，淘汰旧候选。已发生的发布 revision 不回退，也不能删掉修订历史。模式保持 recovering，直到明确目标的完整前缀和下游恢复契约满足；不要靠“最终总会重试成功”回避任务版本竞争。

## 第 9 层：undo 不足时能否从日志反推

**面试官：** 磁盘清理删了 undo，但原始 Transfer 还在，能直接把金额取负恢复吗？

**面试者：** 只有已证明投影纯粹由可逆增量组成、基线和全部依赖完整时才可能，而且需要明确另一个经过验证的恢复算法。一般不能把通用投影当数学求和：解析版本变了、账户归属历史丢了或业务状态有不可逆分支，都可能使取负失效。安全选择是冻结受影响投影，从分叉前可靠快照按固定版本重建到新目标，再核验切换。若分叉触及已接受 finalized，则不是“换个快照继续”能自行解决的，必须进入最终性事故流程。

## 第 10 层：怎样判断恢复完成

**面试官：** 所有新块都应用完了，mode 可以立刻改 healthy 吗？

**面试者：** 先检查新父链从共同祖先连续、没有跨已接受最终边界，所有块扫描与解析完整，投影值及源版本一致，undo 足以支撑约定后续恢复，任务位置与 tip 相符，修订 Outbox 无缺口。主例应回到 A=75、B=25，但来源是 102b，不是 101a；仅看金额相同无法验收。然后在事务内标记恢复完成并生成恢复边界消息或新快照，查询恢复健康。下游可能仍落后，要披露消费水位；资金路径若依赖下游赶上，应等其确认所需版本，不能以本地健康代替整条链路恢复。

## 本题收束

- **讲透的机制：** 恢复也有权威状态、原子提交与幂等入口；顺序是逆序撤销、正序重放，发布历史不回滚。
- **最易答错：** 重组就是把金额取负；同 txHash 重入无需再处理；本地重放结束等于全系统恢复。
- **检验反例：** 撤销 101a 的 COMMIT 已成功但 ACK 丢失，重启若再次给 B 减 25，说明撤销没有与任务位置和 tip 共同提交。
