# 大问题 7：怎样发现重组并找到共同祖先？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 100→101a→102a→103a | 当前采用的教学区块链路。 | a、b 区分分支，不是两个可混排的高度列表。 |
| height / hash / parentHash | 区块位置、区块身份、父块身份。 | 相同高度可能换块，父链接才能把确定区块串成历史。 |
| tip / head | 本地已应用末端，以及节点当前采用链头。 | 两者都要带 hash；head 没升高也可能已换分支。 |
| canonical | 本服务按可信链证据采用的规范分支。 | 当前查询所依据的历史，不是“数据库里凡存过的块”。 |
| 同高换头 / 低头 | 高度不变但 hash 不同，以及远端头低于本地。 | 都需要核验，不能只在 head 更高时运行检测。 |
| RPC / 同步状态 / 独立来源 | 节点观察接口、节点追赶程度、不同信任来源。 | 备用节点只到 102a 可能单纯落后，不能立即撤销 103a。 |
| 共同祖先 | 两条固定父链最后共有的具体块。 | 本例 b 从 101 分叉，祖先为 (100,H100)，不是随便选一个较小高度。 |
| 固定候选目标 | 先锁定要核验的具体目标 hash。 | 从 104b 按父 hash 回溯，不在遍历中改查“某高度最新块”。 |
| 对齐高度 / 双向回溯 | 先让高的一侧退到相同高度，再沿双方父链退。 | 104b 先到 103b，再与 103a 一起回退，直到 hash 相同。 |
| 遍历预算 / 失败隔离 | 限制回溯资源，以及证据不足时停止采用。 | 防异常来源无限消耗，取不到父块不代表祖先已经找到了。 |
| 本地旧头 / undo | 已采用旧链的父链接证据，以及后续撤销材料。 | 不依赖 RPC 永久保存孤块；本地丢材料要走快照恢复。 |
| accepted finalized / H100 | 已认可的最终检查点及其具体身份。 | 正常只能撤它之后的后缀，算出更早祖先不授予回滚最终历史的权限。 |
| removed=true | 日志订阅给出的移除提示。 | 可触发核验，但不覆盖空块，也不保证断线期间撤销通知齐全。 |
| chainEpoch / recovery_job | 分支代次，以及持久恢复计划。 | 计划固定旧 tip、目标、祖先、阶段与下一位置，避免边撤边换目标。 |
| 二分祖先搜索 | 利用共同前缀结构加速定位分叉点。 | 前提仍是两条固定且父链完整的分支，不能对实时变化的高度回复做二分。 |
| recovering / 熔断 | 可恢复的分支切换模式，以及最终证据冲突时的事故隔离。 | 前者可计划撤放，后者不能沿普通重组流程自动越过最终边界。 |

## 把整篇文章压缩成一个故事

**起因：** 本地已经采用 100→101a→102a→103a，远端仍报高度 103，却变成 H103b。A 那笔 25 USDC 的旧观察可能已失去规范归属。只比较高度的扫描器会什么都不做，继续把旧分支余额当当前结果。

**处理与异常：** 服务先核验远端是不是错链或落后节点；仅返回相同 102a 的备用节点不足以推翻 103a。确定候选为 104b 后，沿固定父 hash 先退到 103b，再与本地 103a 同步回溯，发现 103、102、101 都不同，直到共同 H100。它把旧 tip、新目标、祖先和分支代次持久化后交给恢复器，而不是按零散 removed 消息直接减余额。

**结局与不能混淆的边界：** 如果 H100 仍是共同祖先且已接受 finalized 边界，恢复器获准撤销其后的 a 后缀并重放 b；这一步只确定撤到哪里，不代表余额和下游都已修复。若候选连 H100 都不延续，哪怕算法找到 99 的祖先，也必须熔断核验，不能自动撤掉已接受最终前缀。找得到祖先、拿得到材料、获准采用新历史，是三件不同的事。

[返回专题总览](README.md)

**流程位置与核心机制：** 根据区块身份与父链接发现分支变化，并界定允许撤销的范围。这里只确定“撤到哪里、准备采用什么”，具体 undo 与崩溃续作见 08。

**必要前提：** 当前采用链为 100→101a→102a→103a，接受的 finalized 为 `(100,H100)`。以下分支 b 的数字是独立重组变体，不与旧分支已经 finalized 同时成立。

## 第 1 层：从父链接发现变化

**面试官：** 怎样发现重组并找到共同祖先？

**面试者：** 索引器持久保存每块的 height、hash、parentHash，而不是仅保存高度。新块正常接入必须是 tip 的下一高度，且 parentHash 等于 tip.hash；不满足就先核验分支，不盲目应用。还要周期性比较本地 tip 与节点当前规范链在相应高度的 hash，覆盖没有收到新块的情况。发现不同后，固定一个候选目标头，沿新旧分支父链接向后找到同一个 hash，得到共同祖先。基线若分支 b 从 101 开始替换，祖先是 H100；后续只能撤销 101a 至 103a，再正序采用 b。

## 第 2 层：同高度没有新块怎么办

**面试官：** 你先检查下一块的 parentHash，但 head 仍是 103，只换成 103b，怎样触发？

**面试者：** 所以检测不能仅运行在“head 高度大于 applied”分支。订阅可能在同一高度发出不同 newHeads，轮询也应比较 hash；收到 `(103,H103b)` 与本地 `(103,H103a)` 不同就进入核验。若节点当前 head 反而低于本地 tip，也不能一直等待它长高，要区分节点滞后和本地分支被弃用。暂时数据不足可以标记来源不健康并暂停确认，不能因为数字没增加就认定没有重组。

## 第 3 层：节点落后还是链真换了

**面试官：** 某个备用 RPC 只有 102，这不也会触发你回滚 103 吗？

**面试者：** 不能把单次较低 head 当撤销指令。我先检查节点身份、同步状态、已知检查点及多个独立来源，区分滞后和分支矛盾。备用节点若返回的 102 hash 等于本地 102a，它只是缺少新头，不足以否定 103a；我不会因此回退。若返回 102b 且不等于本地 102a，就出现真实的观察冲突，但仍需按可信来源策略核验。多源比较是故障发现手段，不是自己投票创造 Ethereum 共识；无法确定时先停止不安全升级，保持证据。

## 第 4 层：怎样实际找祖先

**面试官：** 假设可信候选头已确定为 104b，具体怎样从两条链找共同祖先？

**面试者：** 我把旧 tip 103a 和候选 104b 作为两条不可混淆的哈希链。先沿 104b.parentHash 回退一层到 103b，使高度相同；再比较同高度 hash，不同就同时沿各自 parentHash 向后，直到 hash 相等。若 103、102、101 都不同，到 100 同为 H100，祖先就是 100。候选父块按 hash 获取并验证返回 hash、height 及 parentHash，不能在遍历中改用“该高度最新块”，否则可能拼出一条从未存在的混合链。为防异常来源消耗无限资源，要设置遍历预算与失败隔离。

## 第 5 层：旧分支已查不到

**面试官：** RPC 已不返回旧分支 103a，双向回退还怎么做？

**面试者：** 本地既然已经采用过 103a，就应持久保存它的头、父链接及所需 undo；旧链回退主要读本地，不依赖提供商永久保存孤块。候选链按固定 hash 获取父块，若新分支父块也取不到，就不能完整证明祖先与重放输入，要换可靠历史来源或进入恢复模式。数据取不到不等于祖先就是当前最早能查到的块。若本地旧父链或恢复材料已被清理，需改用经过验证的快照重建，不允许猜一个高度直接扣回余额。

## 第 6 层：祖先踩到最终检查点

**面试官：** 一直回退发现分支在 99 就不同，你是否把 100 也一起撤销？

**面试者：** 不会。我们已经接受 `(100,H100)` 为 finalized，正常重组恢复只能撤销它之后的可逆后缀。若候选证明无法延续 H100，属于最终检查点矛盾，可能是错链、节点故障、配置错误或严重共识事件，必须熔断并核验，不能把“共同祖先找到了”误当“有权回滚到这里”。算法能算出祖先不代表业务授权允许采用它。对外应保留已接受证据及风险状态，资金权限由事故流程控制。

## 第 7 层：核验时链还在继续变化

**面试官：** 找到祖先 100 的过程中，新链又出了 105c，之前算的结果会不会失效？

**面试者：** 找祖先过程绑定目标 hash，所以它对那条候选链仍是确定的，但目标不一定还值得采用。我会在恢复任务启动前重新核验候选目标是否仍被可信节点采用，固定旧 tip、目标 tip、共同祖先和新的 chainEpoch。恢复中若目标继续延长且沿同一父链，可以先完成已固定前缀再追赶；若再次换分支，先让当前任务在明确事务边界停下，再从当前持久状态重新规划。不能每拉一块都替换目标，边撤边拼一条不断变化的链。

## 第 8 层：订阅 removed 能否省掉祖先搜索

**面试官：** logs 订阅会发 removed=true，直接对那些日志反向处理不就够了？

**面试者：** 不够。removed 是有价值的撤销提示，但可能在断线期间丢失，而且只覆盖订阅匹配日志，不覆盖所有空块和状态依赖。它也不提供一个完整、无歧义的新规范前缀。直接按到达顺序减余额可能让旧撤销晚于新包含，或者只撤销半个块。我会用 removed 触发分支核验，依据头链找到祖先，以完整块为单位回退；重复 removed 不再产生第二份撤销。这样没有收到 removed 也可以通过 hash 校验发现重组。

## 第 9 层：为什么不用按高度二分

**面试官：** 线性向后会慢，二分查第一个不同高度是否更合适？

**面试者：** 可以在足够深且数据完整时优化，但先要固定两条候选分支，并能按各自分支得到指定高度的祖先。只有父链接接续的两条链，才有“共同前缀之后一直不同”的结构；若每次按数字向当前 RPC 查询，链在变化，二分判断可能来自多个分支，结论不可靠。对常见短重组，线性回退简单可审计；深到超过预算或 undo 窗口时本来就应转隔离重建，不为了追求算法复杂度跳过证据校验。优化不改变 finalized 下界与材料完整要求。

## 第 10 层：怎样把结果交给恢复器

**面试官：** 祖先找完了，恢复器凭什么知道它撤的是正确旧链、放的是正确新链？

**面试者：** 我会持久化任务：旧 tip 的 hash、目标 hash、祖先 hash、待撤旧块列表或可验证父链、待放新块链、chainEpoch、阶段和下一位置。任务启动事务锁定 chain_state，核验当前 tip 仍等于规划旧 tip，并停止正常 writer 和不安全确认。如果状态已经改变，原计划作废重算。恢复器每次处理也校验当前 tip 与预期块一致，不接受裸高度指令。验证用例可让两个分支高度完全相同但日志不同，预期仍找到 H100，而不是以“已经到 103”直接宣布同步完成。

## 本题收束

- **讲透的机制：** 重组检测比较区块身份，祖先搜索遍历固定分支，采用权限受已接受最终检查点约束。
- **最易答错：** head 不变就不检查；备用节点落后就回滚；removed 就是完整撤销日志。
- **检验反例：** 本地 103a，远端 103b，二者都高于 100。仅比较高度的扫描器不会做任何事，却持续提供已弃用分支的余额。
