# 大问题 9：撤销和确认怎样可靠传给下游？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| Outbox / Inbox | 源事务中的待发记录，以及消费事务中的收件去重记录。 | 前者防提交后丢通知，后者与业务变化同提交，防重试重复效果。 |
| 至少一次 / MQ | 允许重发的传输承诺，以及消息中间件。 | 网络可重复交付，MQ 开关不能单独保证资金正确。 |
| messageId / 稳定载荷 | 一条通知的持久身份，以及重发时不改变的内容。 | ACK 丢失后发原消息，不新造身份伪装第二次状态变化。 |
| ACK / 已发送 / 已消费 | 交付确认、发布端发送状态、消费端事务落实状态。 | 三者不是一回事；没收到 ACK 时消费者可能早已入账。 |
| revision / appliedRevision | 修订流中的序号，以及消费端连续应用的位置。 | 最大收到序号不是已连续落实的位置，不能越过前序余额增量。 |
| pending / applied | 已持久收到但尚未生效，以及已按协议完成应用。 | 乱序消息先待处理，不先记成“已处理”导致以后无法补消费。 |
| SQL sequence / 事务计数器 | 可能留洞的数据库序列，以及随事务共同回滚的持久计数。 | 本文连续流用后者；要允许洞就另定后继协议。 |
| 全链流 / no-op / 过滤进度 | 完整修订序列、不改本业务数据但仍消费的位置、子集流的进度依据。 | 消费无关消息也推进位置，过滤后不能把每个全流数字洞当丢失。 |
| Observed / Reverted / Finalized | 观察到、撤销具体观察、合格最终确认。 | included 展示可撤销，只有符合政策的最终确认才可申请入账。 |
| chainEpoch / recovering | 分支代次与恢复模式。 | 旧代次前序消息仍可能要消费，不能一律删除积压记录。 |
| C / T / B / D | 资产合约、交易、平台收款地址、平台充值业务身份。 | 本例单条合格 Transfer 对应 D 的 25 USDC 义务，不推广为只按 T 去重。 |
| 领域幂等键 / 同键冲突 | 防同一业务义务多次履行的身份，以及同一身份出现不符载荷。 | 新 messageId 不代表新充值，同 D 金额不同要隔离而非覆盖。 |
| delta / 完整状态覆盖 | 依赖前序的增量，以及可以独立替换的自足状态。 | 余额 delta 不能随便丢中间修订；对象覆盖需要另外证明前提。 |
| decoder 回填 / 影子投影 | 更换解码版本重算历史，以及不产生新业务效果的结果集。 | 默认只重算查询，不因重放 Finalized 再造资金义务。 |
| 冲正 / 原分录 | 经授权追加的纠正账务，以及它关联的历史记账。 | 未最终撤销无须冲正未发生的入账，已错账也不能由索引器删除。 |
| 外部幂等键 / 结果查询 | 外部支付独立防重身份，以及查实际支付结果。 | 消费数据库事务包不住外部支付，Inbox 不能替代这层协议。 |
| 快照 / 截止 revision / generation | 固定完整视图、已覆盖的消息位置、投影版本。 | 查询可由快照续接；账本不能把快照余额重新全部入账。 |

## 把整篇文章压缩成一个故事

**起因：** 索引器已经把 A→B 的转账观察与 Outbox 同事务写好，发布器送出后却在记“已发送”前崩溃。恢复时它必须重发原 messageId；若消费者先前已经提交，就通过同事务保存的 Inbox 返回既有结果，而不是再给用户加 25。

**处理与异常：** 在未最终重组变体中，旧 Observed、Reverted、新 Observed 都进入公开修订流。即使撤销先到，消费者也按连续 revision 补齐，不能只靠“每条都处理一次”就宣布顺序正确；恢复期间也不删除已经公开的旧消息来抹掉缺口。新分支最终合格后，账本还按 D 防领域重复，避免新版解码器换个 messageId 又表达同一笔充值时再次加钱。

**结局与不能混淆的边界：** 查询最终反映正确分支，账本只对合格 D 入账一次 25 USDC。普通未最终撤销只修暂态视图，不产生不存在账务的冲正；若已经错记账，则由账本授权追加关联分录。若钱早已对外付走，纠正分录和 Reverted 都不会自动收回资产；消息可靠、顺序正确、业务防重和外部支付恢复仍是不同层的工作。

**流程位置与核心机制：** 连接索引事务和下游业务事务，解释 Outbox／Inbox、顺序缺口、重放、业务冲正及不可逆效果。本题不把消息系统的承诺当成资金正确性的充分条件。

**必要前提：** 索引发布流有事务内分配、严格递增且连续的 revision；Observed 可撤销，Finalized 才能形成本文充值入账资格。普通回放不得重复制造业务义务。

## 第 1 层：先定义可靠的具体含义

**面试官：** 撤销和确认怎样可靠传给下游？

**面试者：** 我把“可靠”拆成三层：源状态提交后必有可恢复待交付记录，传输失败允许至少一次重发，消费时状态变化和去重记录同事务。索引器在块应用、撤销或确认推进事务里写 Outbox；发布器只读已提交记录，使用稳定 messageId、revision、chainEpoch、消息类型及源块证据发送。消费者以 Inbox 和自身投影或账务操作共同提交。这样可以在消息重复的情况下做到同一领域效果不重复；但前提是领域业务键及消息语义正确，不能仅靠 MQ 去重开关。

## 第 2 层：ACK 丢失时谁重试

**面试官：** 发布器发送成功，更新 Outbox 已发送状态前崩溃，会发生什么？

**面试者：** 重启后它会重发同一 messageId，这是允许的。若消费者前一次没提交，新尝试正常执行；若已提交但 ACK 丢失，Inbox 命中已应用记录，返回既有结果，不再加 25。关键是不能先记录“见过消息”再异步入账，否则崩溃后消息被判重复但账没记；也不能先入账再单独写去重，否则会重复入账。若消费包含调用外部支付，数据库事务无法包含外部效果，必须使用独立支付意图、外部幂等键和结果查询，不能把 Inbox 当跨系统原子事务。

## 第 3 层：乱序为什么不只是去重问题

**面试官：** Reverted 比旧 Observed 先到达，两条 messageId 都不重复，Inbox 还能保护吗？

**面试者：** 不能，去重只识别相同消息，不能裁决不同修订的顺序。基线采用单链完整修订流，消费者保存连续 appliedRevision；收到下一 revision 才应用，较大序号先持久化为 pending 并请求补齐，较小或相同序号按 Inbox 结果处理。pending 不等于 applied，补齐前不先盖最终去重章。发送器也按提交序发送，但消费者仍防网络和故障导致的重复乱序。若采用对象级最新版本覆盖，必须证明该消息是自足状态且不依赖被跳过的增量；不能对余额 delta 随便丢中间消息。

## 第 4 层：序号有洞怎么办

**面试官：** 数据库自增 sequence 因事务回滚跳过了一个数字，你的消费者不是会永久等缺口吗？

**面试者：** 所以不能直接把可能留洞的 SQL sequence 当“每个数字都对应消息”的连续协议。基线由单链 writer 锁定事务内 revision 计数器，分配多少条 Outbox 就推进多少，事务回滚计数器也回滚。也可以换成允许空洞的提交日志位置与明确后继映射，但必须改变消费者协议。这里消费者接收完整全链修订流，即使某消息与自己业务无关也显式消费为 no-op，推进位置；若服务端过滤流，必须另外提供该流独立序号或跳过证明，不能把过滤造成的洞当传输丢失。

## 第 5 层：重组时积压的旧消息怎样处理

**面试官：** 发现重组时 Outbox 里还堆着旧分支 Observed，你会把它们删掉吗？

**面试者：** 基线不删除已进入公开修订流的记录，因为可能已有某个消费者拿到，删除会造成不同消费者历史不一致及序号缺口。恢复阶段暂停不安全确认、生成逆序撤销及新分支消息，发布器可以在恢复边界后按完整顺序交付旧观察和其撤销，最后发恢复完成边界；也可以设计带明确快照替代范围的重置协议，但不是简单丢消息。查询和消费者需识别 recovering，不能把中间 Observed 当不可逆资金指令。旧 epoch 不一律丢弃：它可能是必须消费才能理解后续撤销的前序事实。

## 第 6 层：最终确认与领域入账是否同一幂等键

**面试官：** 解析器升级重新发布了一条 Finalized，messageId 不同，账本怎样不重复入账？

**面试者：** 还需要领域幂等键。messageId 防一次交付重试，业务键防同一充值义务经不同消息路径被再次表达。主例 D 对应已核验的单条 C／T／B／25 USDC 充值，账本核验当前最终证据与业务载荷一致，对同一 D 只形成一次入账；相同 D 但金额变化必须冲突隔离，不能 upsert 覆盖。通用多 Transfer 交易不能只有 txHash，必须按领域匹配和协议标识区分。回填或 decoder 重建默认只重算影子查询，不另发资金指令；需纠错时走授权修订，不借新 messageId 绕开旧义务。

## 第 7 层：什么才叫业务冲正

**面试官：** 你区分 Reverted 和账务冲正，那什么时候才需要冲正？

**面试者：** 本文普通未最终重组没有可用充值入账，因此 Reverted 只撤暂态查询，不需要账本冲正。只有已发生的账务结果经核验需要修正，例如资产归属解释错误或已接受最终检查点事故，账本才按授权生成关联原分录的反向或更正分录，保留审计和总账约束。索引器提供证据及受影响清单，不直接删分录、改余额或再次付款。若可用资金已转走，追加分录也不代表资产自动收回，还需要冻结、追偿及损失处理。不能用一个通用 compensate 函数掩盖这些权限和经济后果。

## 第 8 层：积压太多还能保证闭环吗

**面试官：** 消费者离线到 Outbox 历史都快过期，你怎么恢复而不漏一笔充值？

**面试者：** 清理要受消费者可恢复策略约束，不是按本地发送成功就立即删。需要保留足够修订日志、可验证快照及其截止 revision；查询消费者可安装某 generation 快照后从后继继续，快照必须绑定 hash、schema、策略和完整水位。账本不能把查询快照当“所有余额重新入账”，应按稳定业务键核对已完成义务、待交付确认和消费位置，补缺而不重做。若历史已经不可恢复，应阻断资金路径、对账并明确人工恢复范围，不能跳过 revision 后直接标健康。恢复验收必须分别看源 Outbox、消费者 appliedRevision 和账务结果。

## 本题收束

- **讲透的机制：** 源提交、传输、消费、领域效果四层保证；消息身份、修订顺序、业务身份各有不同作用域。
- **最易答错：** Inbox 自动解决乱序；新 messageId 就是新充值；撤销通知能撤回已经付款的资产。
- **检验反例：** 消费者先保存“收到 Reverted”，随后迟到 Observed 又把余额加回来。两条消息都只处理一次，结果仍错，证明去重不等于顺序正确。
