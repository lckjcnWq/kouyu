# 大问题 1：一笔转账怎样走完索引与业务确认？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| Ethereum / RPC | 链执行与共识系统，以及向节点观察它的接口。 | 链决定链上事实，RPC 是观察渠道，页面和数据库不能另造资产。 |
| C / A / B | C 是核验后的 USDC 合约，A 是付款地址，B 是平台收款地址。 | A 转入 B 的是 25 USDC，6 位精度对应 25000000 个最小单位。 |
| T / D | T 是链上交易，D 是平台分配的充值业务身份。 | 本例 T 只有一条相关 Transfer；D 还需关联收款、金额与归属证据。 |
| Transfer / receipt | 合约转账事件，以及交易执行回执。 | 回执成功要与目标事件和业务语义一起核验，不直接等于平台充值完成。 |
| chainId / blockHash / txHash / logIndex | 链编号、区块哈希、交易哈希、区块内日志序号。 | 四者定位分支内观察；T 移入新块后不能照搬旧观察的确认。 |
| canonical / included | 当前采用的规范链，以及交易已被其某块包含。 | included 可以展示，但尚未承诺平台可提现。 |
| applied / 水位 | 已经连续、完整提交到的位置。 | 要带高度与 hash；不是收到的最高头，也不是页面最新刷新时间。 |
| projection / 账本 | 由链事实生成的查询视图，以及拥有平台账户记账权的系统。 | 转账视图 B=25 不代表账本已给用户增加 25 可用额。 |
| undo / 共同祖先 | 撤销派生变化的依据，以及新旧分支最后共有的块。 | 撤回未最终的 101a 要回到共同祖先，不是直接发反向转账。 |
| Outbox / Inbox | 索引事务中的待发记录，以及消费者事务中的去重记录。 | 两边各自提交，靠可靠重试衔接，不存在天然跨系统共同事务。 |
| Observed / Reverted / Finalized | 观察、撤销、最终确认三类消息。 | 前两类调整暂态视图，只有合格的 Finalized 才可进入基线入账流程。 |
| revision | 持久递增的消息修订号。 | 撤销比旧观察更新，不能让迟到的旧观察再次复活已撤回结果。 |
| finalized / 完整前缀 | 有证据支持的最终检查点，以及从基线连续应用的链段。 | 两者还要满足 hash 祖先关系，光说“高度足够”不行。 |
| 3 确认 / ACK | 按本文口径的包含深度，以及通知或调用确认。 | 103−101+1=3 不等于 finalized；ACK 丢失也不等于账本没提交。 |
| 未知态 / 业务键重试 | 暂无充分结果证据，以及沿同一业务身份查询或重试。 | 账本超时不新建第二份充值，RPC 查不到也不证明 T 从未执行。 |
| 冲正 / 外部付款 | 由有权限模块追加的账务纠正，以及已离开内部系统的支付。 | 索引器可提供风险证据，无权删账，也不能靠 Reverted 收回外部付款。 |

## 把整篇文章压缩成一个故事

**起因：** A 把 25 USDC 转到平台地址 B，T 在 101a 执行成功。用户问“到账了吗”，实际上是在问四件不同的事：链有没有转成、索引有没有完整应用、确认消息有没有送到、账本有没有提交。不能用页面上的一个成功图标同时回答它们。

**处理与异常：** 索引器核验 C 和事件，把 101a 的转账视图从 100／0 改为 75／25，同时提交 undo、Outbox 和游标；空块扫到 103a 后，虽有 3 次确认，可用充值仍是 0。若此时 a 分支被移除，就发布更高 revision 的撤销并修复暂态视图；T 后来进入 102b 时继续核验新观察，不把 D 永久判失败。账本调用超时则查同一业务键，不能另记一笔。

**结局与不能混淆的边界：** 无重组的主路径里，101a 属于已接受 finalized 的完整前缀后才发布合格确认，账本以去重和入账同事务增加一次 25 USDC。若重组发生在此之前，本来没有平台入账，就谈不上冲正一笔不存在的账。Observed、MQ 发送成功和页面可见都不授予提现权；已经对外支付的钱也不会因索引撤销自动退回来。

**流程位置与核心机制：** 从链上执行到平台充值完成，讲清各模块权威、完整性提交点与完成含义。采集、原子性、重组和交付的内部算法分别在后续母题深入，本题负责把责任接起来。

**必要前提：** 沿用总览 Ethereum 主网 C 合约 USDC、A 向 B 转 25 USDC、finalized 后平台才入账的基线。索引器不持有私钥、不决定链上执行，也不直接拥有平台账本。

## 第 1 层：从用户转账到业务完成

**面试官：** 一笔转账怎样走完索引与业务确认？

**面试者：** 用户提交 T，Ethereum 将它包含并执行成功，C 在 101a 发出 A 向 B 转入 25000000 个最小单位的 Transfer。索引器通过订阅或轮询发现链变化，从持久游标后连续取块，按确定哈希扫描、解析和验证日志，将完整块的投影、undo、Outbox 与游标同事务提交。此时可展示 included，但还不能给平台可提现充值。等该块进入已接受 finalized 前缀且前缀完整，索引器可靠交付 Finalized；账本再核验业务身份、去重并在自身事务入账 25 USDC，账户查询才能说充值业务完成。链上成功、索引完成、通知发出和账务完成是四个不同边界。

## 第 2 层：既然已经执行，谁说了算

**面试官：** 你说有四个边界，如果节点、数据库和页面给出不同状态，以谁为准？

**面试者：** 要先问是哪种状态。Ethereum 执行和共识决定链上的余额及规范历史；节点 RPC 是我观察它的渠道，不是可任意覆盖历史的业务管理员。索引数据库决定本服务已经验证并应用到哪个 hash，不能把查询缓存当完整链真相。账本决定平台账户是否已入账，页面只是它们的派生展示。因此页面应分别表达“链上已包含、索引水位、最终性、平台处理中”，而不是一个 success 混用。若页面缓存已显示 25，账本尚无分录，不能据页面继续提现。

## 第 3 层：怎样让这些边界可查询

**面试官：** 既然不能只用 success，你会给这笔充值保存哪些状态？

**面试者：** 我会分开保存链观察和业务状态。链观察带 chainId、blockHash、txHash、logIndex、canonical 与最终性证据；索引进度带 applied 高度及 hash、过滤和解析版本、恢复模式；充值意图 D 保存收款归属、金额、关联观察、验证结果和账本业务键。账本保存自己的分录身份及提交结果。included、reverted、finalized 表达观察生命周期，待核验、待入账、已入账表达领域流程。原观察被撤销不意味着 D 永远失败，T 可能重入新块；业务已入账也不能仅因查询 RPC 超时就改回未入账。

## 第 4 层：通知先到而投影没完成怎么办

**面试官：** 你保存了多个状态，如果一收到日志就通知账本，随后数据库写入失败呢？

**面试者：** 这会形成没有可恢复来源的业务通知，所以不能在提交前直接发。我把观察、投影变化、undo、发布记录和 applied 游标放入同一块事务；提交后发布器才读取 Outbox 交付。Finalized 的推进也必须先确认该前缀完整应用，再以事务写确认记录和发布游标。失败前账本不应看到可消费的承诺；失败后靠持久 Outbox 恢复。数据库和账本不共享事务，因此账本仍需 Inbox 与入账同事务，不能认为索引端原子了，下游自然恰好一次。

## 第 5 层：已通知的结果后来被撤销

**面试官：** 事务和通知都成功了，但 101a 被重组移除，之前的通知怎么处理？

**面试者：** 先看通知承诺。Observed 只承诺在某个链视图和水位观察到 T，可以由后续更高 revision 的 Reverted 撤销。索引器定位共同祖先，逆序回退旧分支，再应用新分支；不能用删除数据库记录代替通知下游。基线中未 finalized 的 Observed 不产生平台可用充值，所以撤销仅影响暂态视图，不需要冲正尚未发生的入账。若 T 后来进入 102b，是新的分支观察；对 D 的最终充值判断仍需新的有效最终证据，不能把旧确认标签搬过去。

## 第 6 层：无法撤销的外部动作

**面试官：** 如果下游没遵守你的承诺，看到 Observed 就付款了，发 Reverted 能把钱收回来吗？

**面试者：** 不能。消息撤销不是链上反向交易，也不是外部支付的退款权。必须在接口契约中划定什么状态允许什么动作：查询可显示 included，资金可用只接受合格 Finalized。若产品明确选择提前可用，那是改变风险政策，必须配置限额、准备金、冻结和损失承担，不能伪称无重组风险。已经付出去的款只能由有权限的业务模块追偿或作补偿分录；索引器提供证据和风险信号，无权删账或直接再次转账。

## 第 7 层：不确定时怎样不误判

**面试官：** 那么账本调用超时、节点又查不到 T，充值页面应该失败还是重试入账？

**面试者：** 应保留未知状态并查询原业务键，不能二选一猜结果。账本超时可能发生在事务提交后，使用同一入账身份重试或查分录才能避免重复；RPC 查不到可能是节点滞后、重组、历史缺失或服务故障，不证明交易从未执行。索引侧继续从可靠游标同步、核验规范分支和最终前缀，页面显示链观察及账本各自水位。只有获得明确的业务拒绝证据才标拒绝；“暂未获得充分证据”和“业务失败”不是一个状态。

## 第 8 层：怎样证明闭环而不是画架构图

**面试官：** 你一直强调水位和证据，怎样检验这套端到端叙述真的闭合？

**面试者：** 我会沿主例逐点核对：100 的基线是 A=100、B=0；应用 101a 后转账视图 75／25，平台入账仍为 0；空块到 103a 后虽然有 3 确认，入账仍为 0；Finalized 与完整性满足后只产生一份逻辑充值义务，账本提交后可用额才是 25。再分别插入采集断线、块事务崩溃、确认通知重发、未最终重组和账本 ACK 丢失，确认每个窗口都有持久续作依据且不重复记账。最终检查原始日志、采用分支、发布记录与账本分录能在同一证据链上对应；这些是验证方法，不是本文已经执行的工程测试。

## 本题收束

- **讲透的机制：** 链执行、索引应用、可靠交付、账务入账各自有权威与提交点，靠显式契约连接。
- **最易答错：** 把 receipt 成功、页面可见、3 确认或 MQ 已发送直接等同可提现充值。
- **检验反例：** 101a 已 Observed、账本未入账时发生重组，若系统必须“删一笔账”才能恢复，说明前面的资金政策或状态划分已经错了。
