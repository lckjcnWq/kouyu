# 大问题 6：几次确认才算业务最终完成？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| T / 101a / C | 主例交易、包含它的教学分支块、核验后的 USDC 合约。 | T 转 25 USDC，是否可入账要核对这份具体分支证据。 |
| included / head | 已包含在某块，以及节点当前链头。 | 已包含不是最终；head 增长也不保证最终性推进。 |
| confirmations / k | 确认深度，以及业务自定的展示或风险门槛。 | 本文含包含块计数，103−101+1=3；k=3 不是 Ethereum 协议常量。 |
| latest / safe / finalized | 当前头、安全级别标签、最终检查点标签。 | 三种承诺不同，不能用固定高度差自行替换。 |
| PoS / 超多数投票 | 权益证明共识，以及最终检查点需要的共识支持。 | 推翻最终历史涉及严重故障与罚没条件，不是普通短重组。 |
| accepted finalized | 服务核验后接受的最终检查点。 | 保存高度和 hash，还要延续已接受的 (100,H100)。 |
| hash / parentHash / 祖先 | 区块身份、父块引用、沿父链接可回溯到的旧块。 | finalized 高度 102 不能给另一分支的 101a 盖章。 |
| applied / 完整前缀 | 已逐块完整应用的位置，以及从基线连续成立的链段。 | 节点已最终但本地尚未取全时，不能先发本地完整充值确认。 |
| 发布游标 / Outbox | 已确认发布到哪里，以及事务内保存的待发通知。 | 二者同提交，重启后补齐，不只在初次看到事件时检查最终性。 |
| pending / eligible / rejected | 资格待核验、合格、明确不合格。 | pending 不能当 rejected 跳过；核验完成后即使无新块也要唤醒扫描。 |
| 业务范围 / 前缀屏障 | 某一资产或业务口径，以及不能跨过的首个待核验位置。 | D 在 101a 待定，充值发布可停 100，独立转账视图和链检查点仍可更高。 |
| Finalized / 账本消费 | 合格最终确认通知，以及平台自己的入账事务。 | 发出通知后可用额仍可为 0，消费提交才变为 25。 |
| 政策版本 / 提前可用 | 明确记录的风险规则，以及未按原最终性门槛就放行资金。 | 从 finalized 改成 safe 是改变承诺，不能称为同样安全，也不能再造旧充值。 |
| RPC 标签支持 / 最终性停滞 | 节点是否能提供相应证据，以及共识最终检查点迟迟不前进。 | 超时或不支持时先诊断，不能因用户等久了自动宣布最终。 |
| L2 / L1 / rollup | 二层网络、其依赖的一层网络、相应扩容机制。 | 排序器包含、数据上 L1、证明或争议及提款条件不能混为一个最终阶段。 |
| 熔断 / 授权冲正 | 持久停止危险发布，以及由账本批准追加纠正分录。 | finalized 冲突不能走普通 undo，索引器也收不回已对外付出的资产。 |

## 把整篇文章压缩成一个故事

**起因：** A 的 25 USDC 在 101a 被包含，链头走到 103a，用户看见“3 确认”便问能否提现。本例算式确实是 103−101+1=3，但若 finalized 仍停在 100，平台可用充值依然是 0，不能把演示数字当共识保证。

**处理与异常：** 当最终检查点真正覆盖 101a，索引器还要核验具体 hash 的祖先关系和本地完整应用前缀。假如转账已解码，但 D 的收款归属为 pending，充值发布游标仍停在 100；不能把“还没查清”当“不合格”跳过。资格核验持久化为 eligible 后，即使没有新块，也触发扫描，把 Finalized 和发布游标同事务补齐。

**结局与不能混淆的边界：** 合格通知被账本消费提交后，用户才有这笔一次性的 25 USDC 可用额。最终性停滞就等待和告警，不临时偷换成 safe 或三次确认；其他 EVM 链、L2 也要独立解释承诺。若新证据矛盾到已接受的 finalized，则隔离核验和授权处理账务，不把它当普通重组自动回滚，更不再次入账一份充值。

**流程位置与核心机制：** 把链观察升级为领域认可结果，区分包含、确认数、safe、finalized、索引完整与账务完成；不把业务风险政策伪装成共识事实。

**必要前提：** Ethereum 主网正常 PoS 共识与可信同步节点。本文演示确认数口径为包含块算第 1 次，平台可提现充值只接受合格 finalized 证据。

## 第 1 层：有没有通用确认次数

**面试官：** 几次确认才算业务最终完成？

**面试者：** 没有跨链、跨业务通用的次数。确认数通常表示包含后又增加了多少链深，但不同产品的计数口径也要明确。本文规定 `head-included+1`，所以 T 在 101a、head 到 103a 时是 3 确认；这只是演示风险展示，不是 Ethereum 的最终性规则。我们采用更明确的业务政策：T 所在块属于已接受 finalized 检查点祖先，索引完整应用到相应前缀，业务验证成功，账本消费事务提交后，充值才完成。单靠等待三块不能替代这些条件。

## 第 2 层：safe 和 finalized 到底多了什么

**面试官：** 既然不看三次确认，safe 和 finalized 与 latest 有什么区别？

**面试者：** latest 是节点当前采用的链头，可能因正常 fork choice 改变。safe 和 finalized 是节点暴露的不同安全级别区块标签，语义来自 Ethereum 的执行／共识协作，不能只按它离 head 多远判断。finalized 依赖 PoS 检查点的超多数投票条件；推翻它涉及严重共识故障及重大罚没条件，而不是普通短重组。safe 不等于业务最终性，也不必然等于某个固定高度差。索引器不自己推算投票就擅自给标签，而是验证所用节点身份、同步状态、返回检查点与本地链视图的关系。

## 第 3 层：最终高度覆盖就足够吗

**面试官：** RPC 给出 finalized 高度 102，T 在 101，为什么还需要检查 hash？

**面试者：** 因为“102 大于 101”只比较数字，无法证明它们在同一条分支。我要保存 finalized 的高度与 hash，并沿 parentHash 证明 101a 是它的祖先，同时证明新检查点延续先前接受的 `(100,H100)`。如果 102 属于分支 b，不能给 101a 盖 finalized。已知 canonical 数据出现矛盾时先停止升级并核验，而不是选择更高或更新的回复。高度水位方便计算，但区块身份和祖先关系才是这项确认成立的证据。

## 第 4 层：节点已最终，本地还没扫完

**面试官：** 祖先也验证了，但本地只应用到 100，能先通知 101 的充值已最终吗？

**面试者：** 不能把链最终性当本地业务完整性。可以记录来自节点、已核验的候选检查点，优先补扫到它；可发布前缀必须同时受 applied 和 accepted finalized 限制，并满足祖先关系与业务解析完整性。否则 101 有两条充值事件而我只见到一条，就可能对不完整数据作终态承诺。最终性扫描应有自己的持久游标：在事务内为新覆盖完整块生成 Finalized Outbox 并推进发布位置，重启后继续，不能只在初次看到事件时判断一次。

还要区分“已明确不符合充值规则”和“资格待核验”。本模型采用业务发布前缀屏障：若 101a 的 Transfer 已解码，但 D 的收款归属仍为 pending，充值发布游标最多到 100；链的 accepted finalized 和独立转账视图可以更高，却不能把 pending 当 rejected 跳过去。核验结果持久化后唤醒确认扫描，即使没有新块或新 finalized 通知，也从原发布游标继续，资格 eligible 才产生 Finalized，明确 rejected 则留依据后越过。发布游标与 Outbox 同事务，重复扫描不重复产生义务。若按资产或业务隔离，必须为各作用域维护独立游标，不能用其他范围的进度证明这笔充值已处理。

## 第 5 层：最终性迟迟不推进

**面试官：** 假设 head 一直增长，finalized 十几分钟不动，用户等不及怎么办？

**面试者：** 基线政策下继续等待、告警并展示“链上已包含但最终性未满足”，不能因时间到了自动改成 finalized。先区分节点滞后、RPC 不支持标签、共识最终性停滞和自身补扫落后，再处理对应故障。若业务决定使用 k 确认提前可用，是显式修改风险政策，需要额度、资产种类、准备金、损失处理和版本记录；不能在故障期间悄悄降级。网络继续出块与最终性恢复不是一回事，服务可保留查询而暂停增加可提现额。

## 第 6 层：政策变化能否重放历史

**面试官：** 如果后来把政策从 finalized 改成 safe，旧事件要重新发一次充值确认吗？

**面试者：** 不能把改变政策等同新充值。政策版本应记录在哪条证据下允许何种动作；已经形成的领域义务仍用稳定业务身份去重，索引重算也不能再造一份账务效果。对尚未入账事件，可以按新政策评估资格并生成带版本的状态升级，但要明确提前可用不再具备原来的最终性保证。账本必须知道它接受的是何种承诺。若反向提高门槛，也不能静默抹掉已入账历史，应由领域规则处理冻结和风险，而不是覆写分录。

## 第 7 层：其他 EVM 和 L2 能否照搬

**面试官：** 同样有 eth_getLogs 的 L2，也支持 safe／finalized，是不是不用改系统？

**面试者：** 采集接口可能复用，但业务最终性适配不能省略。L2 的排序器包含、数据上 L1、L1 最终性，以及适用的证明／争议或提款条件不是同一阶段；不同 rollup 和服务商对标签的映射也需核验。若产品关心 L2 内转账展示，门槛可能不同于跨链提款可用，不能一句“L2 finalized”涵盖全部。其他 EVM 链的共识、深重组与标签支持也不同。应抽象可解释的链特定确认策略，输出证据和风险含义，而不是统一写死等待 12 块。

## 第 8 层：如果 finalized 证据真的矛盾

**面试官：** 你把 finalized 当关键边界，如果已经按它入账，后面出现矛盾块还怎么办？

**面试者：** finalized 不是无条件数学不可逆，我仍要设计异常边界。一旦候选与已接受检查点矛盾，先熔断相关确认发布、固定证据、核验节点配置及独立来源，必要时限制受影响充值和提现。不能正常执行 undo 把它当未最终短重组，也不能自动接受新链再发第二份充值。若核实需要修正，由事故决策明确采用历史、影响清单和账本授权冲正；外部付款无法被索引回滚撤回。恢复验收要同时核对规范链、完整投影、确认消息与账本分录，而不是节点恢复连通就解冻。

## 本题收束

- **讲透的机制：** 业务终态由链特定最终性、祖先证明、完整应用与领域提交共同构成。
- **最易答错：** head 增长必然意味着最终性推进；safe 等于 finalized；高度覆盖自动证明同分支。
- **检验反例：** 101a 的 T 有 3 确认，但 finalized 仍为 100；若平台已经增加可提现充值，便违反本文明确的资金政策。
