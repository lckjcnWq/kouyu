## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| C / A / B / T / D | 资产合约、付款地址、平台收款地址、交易、平台充值业务身份。 | 核验 C 的一条 T 日志，把 A→B 的 25 USDC 与 D 关联；不是任何同名代币都可入账。 |
| chainId / genesisHash / blockHash | 链编号、创世身份、具体来源块。 | chainId=1 还要认准链历史，日志必须对应确定的 101a。 |
| receipt.status=1 | 交易顶层执行未失败的回执标记。 | 内部调用可能被捕获失败，不能直接推导任意业务目标已完成。 |
| ABI / decoder / assetPolicyVersion | 编码约定、解码程序、资产业务策略版本。 | 格式能读懂与语义被允许是两道检查，历史解释要记录各自版本。 |
| topic0 / Keccak-256 | 非匿名事件签名所在的首个主题，以及其完整哈希算法。 | Transfer 签名用完整 Keccak 哈希，不是函数四字节选择器，也不是 NIST SHA3。 |
| topics / indexed / data | 日志主题、放入主题的参数、其余数据区。 | 本例 from、to 在主题中，amount 在 data；主题数量和编码也要合法。 |
| anonymous / 动态 indexed 字段 | 不保存签名 topic 的事件，以及主题里只存哈希的复杂字段。 | anonymous 最多 4 个 indexed，非匿名最多 3 个；复杂字段不能靠 topic 还原原文。 |
| uint256 / 6 位精度 | 链上无符号整数金额，以及展示时小数点的位置。 | 原始 25000000 显示为 25 USDC，不用浮点数猜金额。 |
| proxy / delegatecall / call | 代理、借用实现代码在自身上下文执行、普通跨合约调用。 | delegatecall 下日志通常由代理 C 发出；普通 call 要认实际发出者。 |
| 历史实现 / 生效边界 | 某条历史执行位置实际使用的代码及规则。 | 块末状态未必说明块内升级前的版本，必要时细到交易内执行位置。 |
| observationKey / tx.from | 原始分支观察的定位键，以及交易的发起地址。 | 保留源块与日志身份；经路由调用时，tx.from 不直接等于资产原持有人。 |
| 原始证据 / 转账投影 | 保留未改的日志等材料，以及按规则生成的查询视图。 | 解析未知可以留原始数据，但不能把相关事件视为不存在后继续完整应用。 |
| applied / 业务范围水位 | 某个明确过滤及解析范围的连续完整进度。 | C 的 101 无法解释时，该视图停在 100，不能借别的投影的 103 越过缺口。 |
| accepted finalized / 祖先关系 | 已接受的最终检查点，以及来源块是否属于该历史前缀。 | 链最终性可独立前进，但受阻业务不能仅凭高度更高就确认。 |
| Finalized / Outbox / revision | 最终确认消息、事务内待发记录、持久修订号。 | 补齐资格后从旧发布游标补发，重发不创造第二份充值义务。 |
| Inbox / 账本事务 / 冲正 | 消费去重、平台记账提交、授权追加的纠正分录。 | 平台可用额由账本形成，解码器修复无权覆盖已产生的账务历史。 |
| 影子投影 / 正式补发 | 不产生外部业务效果的重建，以及补齐真实未发布义务。 | 升级回填不能顺手再次通知发钱，任务模式和权限必须分开。 |

## 把整篇文章压缩成一个故事

**起因：** T 的回执显示成功，一条日志又恰好能读成 A 向 B 转 25000000。平台仍要追问：发日志的是核验后的 C 吗，所在链和块对吗，当时的 ABI 与实现语义对吗，B 属于哪位用户？否则另一个合约发出同名 Transfer，也可能被误当成 25 USDC 充值。

**处理与异常：** 索引器检查完整 topic 签名、字段布局、整数金额及来源块，再匹配 D。若 C 是代理，要按真实执行上下文认日志地址；若 101 块内发生升级，不能拿块末实现和最新 ABI 生套之前的日志。假如该条相关事件的版本待定，即使 102、103 为空且链已最终化，C 的完整转账视图仍停在 100，保存证据等待核验，而不是把未知事件当零。

**结局与不能混淆的边界：** 历史版本和充值归属补齐后，再核对 101a 仍在已接受 finalized 的完整前缀，事务生成 D 的正式确认；账本消费后只增加一次 25 USDC。正常转账视图为 A=75、B=25，Gas 另付 ETH。若旧解释已造成错误入账，新 decoder 只能提供新版本和差异证据，由账本授权纠正，不能覆盖旧证据、删账，或借回填重复发钱。

**流程位置与核心机制：** 位于按确定 blockHash 完整获取日志之后、投影应用和业务确认之前。核心是把“可信来源的原始日志”“按历史规则解释出的事件”“符合充值规则的证据”分开；采集完整性见 02，最终性门槛见 06，本题不以解析成功代替它们。

**必要前提：** 沿用总览的 Ethereum 主网、可信节点及经核验的 USDC 地址 C，精度为 6。T 在 `(101,H101a)` 内由 A 向 B 转入 `25000000` 个最小单位，即 25 USDC；本例只有一条相关 Transfer。检查点 100 的转账视图为 A=100、B=0 USDC。以下是教学设计；平台可用充值只在 finalized 完整前缀、业务核验及账本消费提交后增加。

## 第 1 层：执行成功与业务成功之间还缺什么

**面试官：** 什么日志可以作为业务成功证据？T 的 receipt 显示成功，能直接给 B 入账 25 USDC 吗？

**面试者：** 不能。receipt 的 `status=1` 只说明这笔交易在对应区块的执行没有以顶层失败结束，不说明任意业务目标都达成。路由合约可能捕获内部失败；某个调用也可能返回失败值但不触发整笔交易回滚。因此，不能从“交易成功”直接推出“指定资产已充值到账”。

在这个模型中，证据至少要串起四件事：确实观察了目标链上某个确定块内的日志；日志由允许的 C 发出并能按当时规则解释；内容符合 B 的充值归属、金额及业务匹配规则；该来源块最终属于已接受 finalized 的完整应用前缀。前三件事支持形成待确认充值，最后还需要账本消费事务才能形成平台可用额。即使已经看到 25 USDC 的 included 记录，平台可用充值仍可为 0。

## 第 2 层：相同事件签名为什么不是资产身份证明

**面试官：** 既然要看日志，找到 `Transfer(address,address,uint256)` 的 topic，解析出 A、B 和 25000000，不就补齐证据了吗？

**面试者：** 还没有。任何合约都可以发出同名、同参数类型的事件。必须先把节点所指向的 `(chainId=1,genesisHash)` 与配置绑定，再检查日志的 `address` 等于经核验的 C；代币名称、symbol、事件签名都不能替代这个身份。

接着按该事件定义检查 topics 数量、indexed 字段位置、地址编码及 data 中 uint256 的合法编码，使用整数保存 25000000，按 C 的 6 位精度展示为 25。不能把缺字段或不合法填充“尽量解析”为正常事件。

对本例非匿名 Transfer，topic0 是 `Transfer(address,address,uint256)` 规范签名的完整 Keccak-256 哈希，不是函数选择器的前四字节，也不是 NIST SHA3-256；from、to 在 indexed topics 中，amount 在 data 中。参数名和 indexed 标记不参与签名哈希，所以同 topic0 仍要核对布局。更一般的 indexed string、动态 bytes、数组或结构体 topic 存的是特殊编码的哈希，不能直接还原原值；非匿名事件至多 3 个 indexed 参数，anonymous 不存签名 topic、至多 4 个。不能让通用 decoder 把所有 topic 都当可逆字段，也不能不认合约和布局就把同签名事件视为 USDC。

日志还应与已获取的块、交易、回执对应：`blockHash`、`transactionHash` 及位置不能相互矛盾；若获取回执核验，也必须检查其来源块，而不是只按 T 查到一次成功就接受。RPC 日志是基于可信节点的观察，不因我们计算了摘要就自动变成独立共识证明。通过这些检查，得到的是“来自 C 的结构有效事件”，仍不是所有业务都已成功。

## 第 3 层：代理调用时究竟认哪个地址

**面试官：** 你要求日志来自 C，但如果 C 是代理、真正逻辑在实现合约里，按 C 过滤会不会漏掉？能否只用最新实现的 ABI？

**面试者：** 常见代理通过 `delegatecall` 执行实现代码时，执行上下文仍属于代理：实现代码里的日志指令所产生的日志，其发出地址是代理 C，而不是实现地址。因此，允许资产身份仍绑定 C；直接调用实现合约发出的相似日志，不能因此当成 C 的充值。若合约使用普通 `call` 让另一合约发日志，则发出地址随实际执行上下文改变，必须按真实机制另定规则，不能统称为代理日志。

同理，T 的 `to` 可能是路由器，并不要求等于 C；真正要核验的是日志发出者及相关业务证据。代理升级可以不改变 C，却改变事件格式或业务语义，所以不能只保留最新实现和最新 ABI。应按历史执行位置选择已审核的 ABI、decoder 和资产策略，解码结果记录版本及原始 observationKey，使同一历史证据能够被重现解释。

## 第 4 层：同块升级怎样定位历史版本

**面试官：** 你说按历史执行位置选 ABI。如果升级与转账发生在同一块，查该高度的实现地址是否已经足够？

**面试者：** 不一定。普通按块查询状态通常得到块执行完成后的状态，不能自动说明块内前一笔交易使用的实现；同一笔交易里也可能发生升级与后续调用。仅用“从第 101 块开始使用新版”可能把升级前的日志用新版解释。

因此，版本登记需要保存 C、实现身份或代码依据、ABI／decoder／资产策略版本、审核来源，以及带分支身份的生效边界；必要时细化到交易顺序和交易内执行位置。升级事件、历史存储、代码及部署资料可共同提供依据，但必须遵循实际代理机制，不能假定所有代理都使用相同槽位，也不能把一条升级事件当成完整证明。普通历史 RPC 不足以判定时，需要更细的执行证据，无法取得就标记版本待定。

还要区分格式与语义：事件签名不包含参数名称及 indexed 标记，相同签名不保证布局相同；即使布局完全没变，实现也可能改变业务含义。因此 ABI 能解码只是结构条件，资产策略仍需明确允许该历史实现的什么语义，未知版本不能自动沿用旧版。

## 第 5 层：未知解析能不能先跳过再补

**面试官：** 如果 101 的历史版本暂时判不清，但 102、103 都抓完了，能否先隔离那条日志，把完整业务水位推进到 103？

**面试者：** 不能在同一业务范围内这样做。可以保存 101 的原始日志、回执、版本疑点及来源，也可以继续预抓后续块；但“原始数据已抓完”与“业务投影已完整应用”是不同承诺。对本例 C 的转账视图而言，101 的相关日志无法解释，完整 applied 水位应停在 `(100,H100)`，不能把未知日志当成不存在。

如果系统另有不受该日志影响的投影，可以在明确独立的合约集合、filterVersion、decoderVersion 和水位口径下继续，但必须对外声明范围与缺口，不能借该投影的 103 水位证明 USDC 充值也完整。真正与当前业务无关的日志可以按有版本的范围规则排除；相关而未知的日志则不是“无关”。

链的 accepted finalized 检查点可以因独立链证据而前进，但受阻业务的最终确认发布不能跨过 101。修复后，应在受控重放中补齐投影、undo、发布记录和连续游标，而不是只改一个“解析成功”标记就宣布已恢复。

## 第 6 层：已解析的 Transfer 怎样成为充值证据

**面试官：** 现在版本问题解决了，确认是可信 C 的正常 Transfer，为什么你还不直接认定平台充值成功？

**面试者：** 因为“发生转账”与“归属于哪一项平台业务”仍有距离。这里需要根据经核验且可追溯的地址归属，将 B 对应到平台账户；再按规则检查资产 C、收款 B、原始金额及充值意图 D。总览中的 D 通过链、C、T 及收款／金额关联成立，依赖本例只有一条相关 Transfer，不能推广为所有交易只用 txHash 匹配。也不能用 `tx.from` 直接推断资金原持有人，因为调用可能经过路由。

在已声明的正常转账模型中，这条 25000000 的事件支持转账视图 A=75、B=25 USDC，Gas 以 ETH 另付，不能从这 25 中暗扣。若换成手续费代币、重基准资产或其他协议，就必须重新定义实际到账、事件与状态之间的关系，不能把本例规则套过去。

更一般地，受信任合约事件可以是某项业务的证据，但没有一种通用日志能证明所有业务结果。Transfer 本身不证明订单已履约、跨链已到账或任意协议已结算；这些结论需要相应协议的权威事件、状态和匹配规则。

## 第 7 层：证据后来才齐全，什么时候允许入账

**面试官：** 你把 D 的业务证据补齐时，链已经 finalized 到 103，怎样既补上这 25 USDC，又不重复确认？

**面试者：** 先核实补齐后的 101 来源块仍是当前采用分支的一部分，而且是已接受 finalized 检查点的祖先；再确认从检查点 100 起到发布目标的相关前缀已完整应用。高度达到 103 不足以替代哈希与祖先核验。若 T 已移入另一分支，应验证新观察，而不是把旧 H101a 的解释结果搬过去。

满足这些条件后，由可恢复的确认扫描从已提交发布游标继续，在同一数据库事务内写入 Finalized Outbox、持久 revision 及确认发布进度。消息引用 D、源块、原始观察和解码／策略版本，供账本核验。Outbox 重发不创造新的业务义务；账本以自己的消费事务完成去重与记账，D 最多增加一次 25 USDC。

这不等于历史重建可以随意重新发送钱。纯 decoder 升级回填应走影子投影；若补齐的是尚未发布的真实充值义务，才按正式确认流程补发。两者必须通过任务模式与权限隔开，不能靠操作者记住“不要重复”。

## 第 8 层：后来发现解释错了，能否改回历史

**面试官：** 如果此前的 ABI 或业务策略有缺陷，已经把错误解释的 D 交给账本了，修好 decoder 后覆盖原记录可以闭环吗？

**面试者：** 不能。原始日志、当时解释版本、已发布内容和账本已消费事实都需要保留。新解释应以新版本保存，与旧解释形成可核对的差异，而不是把旧证据悄悄改成“从来正确”。

若还未形成最终业务效果，可以暂停受影响发布，重建或修订派生投影，并以新的有序修订说明变化。若账本已经记账，应隔离受影响业务，核验错误范围，由账本依据授权追加纠正分录；索引器没有删除账本历史或撤回外部支付的权限。decoder 修复也不能把一个与已接受 finalized 检查点冲突的分支自动认作新历史。

在这个模型中，闭环的判断标准不是“新版能解析”，而是相同原始证据、精确分支与版本能够解释为什么产生或拒绝这 25 USDC；任何已产生的平台资金效果都有可追溯处理。无法解释的缺口要显式保留，不能藏在更高的完整水位里。

## 收束：机制、易错边界与反例

- **机制：** 固定链与可信 C → 历史执行版本解释 → 领域证据匹配 → finalized 祖先及完整前缀 → 账本消费事务。每一步证明不同事项，不能彼此替代。
- **易错边界：** receipt 成功不等于任意业务成功；delegatecall 的日志地址通常是代理；最新 ABI 不代表历史 ABI；隔离未知解析不允许受影响业务完整水位跨过缺口。
- **反例检验：** 101 出现一条无法判定升级语义的 C 日志，102、103 都为空且已 finalized。若系统声称 USDC 完整应用到 103，并允许该前缀触发充值，方案就已经失效。正确结果是保留证据、阻断受影响前缀，核验并补齐后再决定是否形成 D 的一次 25 USDC 入账。
