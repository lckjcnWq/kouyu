# 大问题 2：怎样连续采集且不因订阅断线漏事件？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| RPC / C / T | 节点查询接口、允许的 USDC 合约、主例交易。 | 从可信来源取 C 的日志，以 T 的观察说明怎样不漏块。 |
| newHeads / logs 订阅 | 新区块头或日志到来时的提醒。 | 不是完整历史账单；节点追赶时可能只提示最后一个头。 |
| applied / 持久游标 | 数据库中最后连续完整应用的位置。 | 从 (100,H100) 后恢复，不能把最后收到的 103 直接写进去。 |
| 完整前缀 / 最大完成高度 | 前者每个中间块都完成，后者只说某个高处任务完成。 | 101、103 成功而 102 失败时，连续水位只能到 101。 |
| height / hash / parentHash | 区块位置、具体区块身份、它所引用的父块身份。 | 高度相同也可能换块，恢复时先核验旧 tip。 |
| 空块 / complete | 没有相关日志的块，以及扫描成功且完整的声明。 | 本例 102、103 没有 C 日志也必须登记；超时留下的空数组不能算空块。 |
| filterVersion | 本次“完整”所针对的过滤范围版本。 | 完整扫描 C 不代表扫完全部合约，范围变更要能追溯。 |
| eth_getLogs / blockHash | 查日志的方法，以及指定某个具体块的过滤条件。 | 用 hash 绑定目标；不能再同传 fromBlock、toBlock。 |
| fromBlock / toBlock | 按高度指定查询起止范围。 | 可批量预抓，但固定高度不等于锁住分支对象。 |
| HTTP 200 / 静默截断 | 接口表示请求成功，以及未报错却少返回数据的情况。 | 成功状态码不保证日志全量，要按提供商限制拆窗并核验。 |
| 完整交易／回执集合 | 某个目标块的全部交易及逐笔回执。 | 高度查询降级时要核对集合、位置及每份 blockHash，缺一份也不能宣称完整。 |
| 候选 / canonical writer | 抓到但未采用的数据，以及唯一顺序应用规范状态的写入者。 | 订阅与补扫先汇成候选，不能分别直接改余额。 |
| chainEpoch / tip | 分支代次，以及当前完整应用的末端块。 | 旧分支候选不能接到新 tip 上，提交前还要再次校验。 |
| removed / 载荷冲突 | 订阅的移除提示，以及同一对象收到互相不符的数据。 | 都应触发核验，不能一收到 removed 就与补扫竞争扣余额。 |
| 历史日志 / 历史状态 | 过去的事件资料，以及过去某时点的合约存储。 | 是不同节点能力，不能单凭“归档节点”标签保证能补齐缺口。 |
| 有界退避 / 隔离 | 控制重试节奏，以及把不可解释问题显式停下处理。 | 换源或重试补齐最早缺口，不把游标跳到今天掩盖历史丢失。 |

## 把整篇文章压缩成一个故事

**起因：** 索引器已完整应用到 100，订阅断线后只收到 103 的提示。101a 里恰有 A 向 B 转 25 USDC 的 T，102a、103a 没有相关日志。如果把“收到 103”直接当完成，真正充值会被跳过去。

**处理与异常：** 服务按持久游标补取 101、102、103，核对父链接，优先按各自 blockHash 取全 C 日志。即使 103 先抓完，只要 102 超时，应用进度也停在 101。若只能按高度查询，查询前后头相同也可能经历 a→b→a，中间空结果属于 b；需要目标 hash 的完整交易／回执等来源绑定，材料不够就换源或暂停，不用“读了两遍”假装证明完整。

**结局与不能混淆的边界：** 102 重试后取得可信、完整的空结果，才与 103 一起逐块提交，T 不因断线遗漏，空块也留下完整性记录。这里保证的是不把缺口包装成完整前缀，不是普通 RPC 能证明恶意节点绝无漏报。若历史资料取不回来，游标只能告诉系统缺在哪里，不能替代资料，更不能靠跳水位宣布恢复。

**流程位置与核心机制：** 负责从 RPC 获取可应用的完整块，区分实时提示、原始候选与连续完整前缀；不展开投影事务内部和共同祖先算法。

**必要前提：** Ethereum 主网、固定 C 合约，应用从 `(100,H100)` 开始。RPC 来源正常且可信是扫描完整性的明确假设，不声称普通日志查询本身提供密码学完备性证明。

## 第 1 层：订阅与扫描怎样组合

**面试官：** 怎样连续采集且不因订阅断线漏事件？

**面试者：** 我会把 newHeads 或 logs 订阅当“链可能变化”的低延迟提示，正确性由持久游标驱动的连续扫描保证。循环读取目标头，从 applied 后一块取区块头并核对父链接，再按确定 blockHash 查询 C 的完整日志，交给顺序 writer 应用。重连不沿用内存收到的最后一条日志，而是从数据库已提交位置恢复，同时核验旧 tip 是否仍属于当前链。即使没有通知，定时轮询也会触发扫描；因此丢一次通知只增加延迟，不制造永久缺口。

## 第 2 层：为什么最后收到的高度不能当游标

**面试官：** 既然有 newHeads，收到 103 就把游标设成 103，不是更快吗？

**面试者：** 不行，通知只说明看到了一个头，不说明 101、102 的日志已经完整处理。Geth 在节点同时接收多个块、例如追赶同步时可能只发送最后一个 newHeads；重组还可能在同一高度发送不同头。我的游标表达“从基线到这里每块都完整应用且父链接成立”，不是最大观察高度。收到 103 后应补齐 101、102、103 的候选。若 102 失败，即使 103 已抓完，也只能停在 101，不能用最大已完成任务号冒充连续进度。

## 第 3 层：没有日志的块怎么证明经过

**面试官：** 你说每块都要处理，但 102、103 没有 C 的日志，怎么知道不是漏抓？

**面试者：** 成功得到该确定哈希下的完整空结果，和请求超时后内存中恰好是空数组不是一回事。块记录要保存高度、hash、parentHash、过滤配置版本和扫描完成状态；空块也要通过父链接校验，再事务推进游标。这样“该块确实没有相关事件”和“还没扫描到该块”可以区分。如果 API 出错、达到供应商结果上限、响应被中断或返回约定不明，我不标 complete。完整性仍受节点诚实及 API 契约约束，记录一个布尔值不会凭空证明节点没漏数据。

## 第 4 层：范围限制怎样既快又不漏

**面试官：** 每块查询很慢，改成一次查十万块，再把日志按块分组行不行？

**面试者：** 可以批量拉取候选，但不能忽略提供商的区间、响应字节或日志条数限制。我先固定目标链区间，使用有界窗口，失败或达到上限时递归缩小区间；确定排序和逐块头信息后，才把各块包括空块标为完整。对可能静默截断的接口，单凭 HTTP 200 不能宣布完整，要收缩到单块、获取必要回执或用独立来源核验。若单个热点块也超限制，必须走可取得全量数据的路径或暂停，不能删除过滤条件后假定问题消失，更不能跳过热点块。

## 第 5 层：查询过程中发生重组

**面试官：** 你固定了高度区间，但查头和查日志之间换链了，怎么办？

**面试者：** 高度固定不等于对象固定，所以优先先取得头 H101a，再用 `eth_getLogs` 的 blockHash 过滤获取这一块的日志；blockHash 不与 fromBlock／toBlock 同传。抓到旧分支候选并非错误，错误是把它当新分支应用。writer 还要核对它是否接续当前采用 tip，且来自当前 chainEpoch。

若服务商只支持高度查询，小区间、返回日志 hash 校验和前后重读头只能辅助发现竞争，不能单独证明完整性。即使节点诚实，也可能先读到 101a，查询期间切到没有相关日志的 101b，随后又切回 101a；前后 hash 一样，中间空数组却属于 b。非空结果也可能漏掉另一分支没有返回的事件，不能只验证已返回的条目。

因此降级路径必须另取得绑定目标 H101a 的完整日志来源，例如按 hash 获取该块完整交易列表，逐笔取得完整回执，并核对交易集合、位置及每份回执的 blockHash，再从全体回执日志筛选 C；缺任一回执或发现错配就不标 complete。真正无交易的块可由该确定块的空交易列表核验。若来源无法提供这些材料，就换支持 hash 查询的端点或暂停，不能以多读几次同高度替代绑定证据。这仍依赖可信节点，不是对恶意节点的独立完备性证明。

## 第 6 层：补扫与实时订阅交叉

**面试官：** 同一条 T 既在历史补扫里出现，又从订阅来，怎样不重复？

**面试者：** 两条输入最终都变成带 hash 的候选，由同一 writer 按块采用；订阅日志不会越过 writer 直接改余额。完整性以块扫描为准，分支观察唯一键防止重复存储，块应用状态防止重复加减。若候选载荷不一致则隔离核验，不用 upsert 悄悄覆盖证据。启动时可以先建立订阅再补扫，以减少延迟窗口；由于周期扫描从持久游标推进，订阅建立早晚不成为唯一正确性条件。removed 通知也只触发分支核验，不能和补扫竞争着随意扣回余额。

## 第 7 层：断线和历史缺失怎么办

**面试官：** 进程离线几天，重连的节点又不保留所需历史，你的游标还有什么用？

**面试者：** 游标告诉我缺口从哪里开始，但不能替代历史数据。先核验旧游标 hash 与当前链，再从具备所需区块、日志或回执保留能力的来源补齐；历史日志与历史状态是不同能力，不能只看“归档节点”标签。若没有可用来源，明确停在缺口、标记数据不完整，并禁止把后续充值宣布为已完成完整前缀。可以引入可验证快照和授权的新起点，但这改变了信任与恢复边界，必须记录，不能把游标直接跳到今天来掩盖遗失历史。

## 第 8 层：怎样验收“不会漏”

**面试官：** 停在缺口很保守，怎样证明它既不会漏，也不会永远卡住？

**面试者：** 我会把扫描状态分为候选待获取、已获取待校验、完整待应用和已应用，并记录重试次数、错误类别、最早缺口及停滞时间。暂时故障用有界退避、限流和可替换来源恢复，永久解析或数据问题进入隔离处置，不能无上限空转。验证时让订阅漏掉 101 和 102，只发 103，预期仍补齐到 103；再使 102 请求失败，预期 applied 只能到 101，重试成功后才继续。最后断线并切换同高度分支，检查恢复先验旧 tip 而不是只补更高块。这里的“不漏”是完整前缀不跨缺口的设计承诺，不是保证任何供应商永不出错。

## 本题收束

- **讲透的机制：** 订阅负责及时唤醒，连续扫描和完整块提交负责可恢复进度，二者责任不能反过来。
- **最易答错：** 把最大收到高度、最大完成任务号、HTTP 200 或空数组直接当完整游标。
- **检验反例：** 101 和 103 抓取成功，102 永远超时；若查询仍宣称“完整同步至 103”，完整性机制不成立。
