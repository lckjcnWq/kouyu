# 大问题 12：RPC 分歧或 writer 切主怎样处理？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| RPC 多源 / 共识 | 多个节点观察渠道，以及 Ethereum 自身确定历史的机制。 | 三个服务商可能共用上游，多数回复不能创造共识或证明日志完整。 |
| chainId / genesisHash | 链编号与创世块身份。 | chainId=1 加创世核验是准入基线，仍要检查后续 finalized 祖先关系。 |
| C / T / 25 USDC | 核验后的资产合约、主例交易、待确认充值金额。 | 节点一致报告 103a，也不能在 finalized 仍为 100 时放行这 25。 |
| 端点能力 / blockHash / filterVersion | 节点支持什么查询、目标具体块、过滤范围版本。 | 换源带着原目标和范围，不把同高度另一分支内容拼进来。 |
| safe / finalized / accepted finalized | 安全级别标签、最终标签、服务已核验接受的最终检查点。 | 不支持标签不能用 latest 减固定块数冒充最终性。 |
| 兼容滞后 / 哈希矛盾 | 同一祖先链上进度较慢，以及检查点所属历史冲突。 | 100 是 102 祖先可只是落后；同高异 hash 或否定旧最终前缀要隔离。 |
| 载荷摘要 / 并集 / 交集 | 比较规范化内容的依据，以及合并或只取共同日志。 | 同 H101a 返回转账与空数组时，凑并集或交集都不能自动裁定真相。 |
| 完整交易／回执集合 | 目标块全部交易及对应的执行记录。 | 用来交叉核验完整结果，仍依赖明确可信来源，不凭空变成密码学证明。 |
| canonical writer / 租约 | 规范状态写入者，以及谁暂时应该担任它的选主约定。 | 租约过期不能物理阻止暂停后苏醒的旧进程写数据库。 |
| writerTerm / DB 围栏 | 持久写任期，以及数据库事务中拒绝旧任期提交的机制。 | 接管提高任期，每次应用、撤销、确认都锁状态并复核至提交。 |
| chainEpoch / mode / tip | 分支代次、服务模式、已应用末端。 | 任期对了也要检查这些上下文，避免把完整旧候选接进当前状态。 |
| 唯一有效主库 / 旧库隔离 | 数据库只保留一套有效可写历史，以及封锁旧主写入。 | 两套可写库各自检查 term 都可能通过，单行围栏救不了数据库分裂。 |
| WAL / 同步复制 / 可提升副本 | 预写日志、提交的复制保证、获准接任的数据库副本。 | 要证明副本包含全部已承诺提交，不能只说“用了同步复制”。 |
| 异步复制丢提交 | 新主缺失旧主已经承诺甚至发布的记录。 | 账本可能已加 25，不能清零 revision、Outbox 后当普通重连继续。 |
| Outbox / messageId / revision | 待交付义务、通知身份、持久修订顺序。 | 已提交义务跨任期保留，接管重发原消息，不丢旧任期消息也不重置序号。 |
| ACK / Inbox / 业务幂等 | 交付确认、消费去重记录、防同一充值重复入账。 | ACK 丢失允许重投，下游以自己的事务保证同一义务不再加 25。 |
| 消费水位 / 风险门禁 / 冲正 | 下游落实位置、阻断危险入账的条件、授权账务纠正。 | 进程切主不等于资金恢复；最终性事故另需隔离在途消费与资金权限。 |

## 把整篇文章压缩成一个故事

**起因：** 两个 RPC 对 H101a 给出不同日志结果，一个有 A→B 的 25 USDC，另一个为空。服务先核对链、目标 hash、过滤版本和完整来源，不能把两份回复取并集凑出“可靠充值”，也不能投票宣布最终。

**处理与异常：** 输入核验后，旧 writer 又网络暂停，新 writer 接管。新任期事务锁定 chain_state，提高 writerTerm；旧进程醒来时必须在真实数据库提交处被拒绝。若旧事务先合法提交，新主就接管该事实。数据库也必须只剩一个有效写入口并保全已承诺 WAL；若提升的异步副本丢掉已发布 Finalized，而账本已经加 25，就转事故核验，不能重置消息流假装一切从未发生。

**结局与不能混淆的边界：** 在数据未丢且旧主已隔离的正常接管中，新发布器继续重发原 Outbox；ACK 丢失也仍用原 messageId、revision 和业务关联，账本不重复加 25。验收要分别解释可信输入、唯一写权限、持久交付与消费进度。换 RPC 不是共识，选主租约不是写围栏，本地切主成功也不授予索引器改账、冲正或重新外部付款的权限。

[返回专题总览](README.md)

**流程位置与核心机制：** 跨越节点接入、分支及最终性验证、数据库提交与 Outbox 接管。RPC 多源解决观察可靠性与可用性，writer 围栏解决规范状态写权限，数据库复制解决持久事实是否保留；这三件事不能互相替代。

**必要前提：** 沿用 Ethereum 主网 `(chainId=1,genesisHash)`、经核验的 USDC 合约 C 和 T 转入 25 USDC 的总览案例。单链串行 canonical writer，单块事务包含投影、undo、Outbox、游标与 revision；账本是独立权威，仅消费符合政策的 Finalized 充值。节点被假设为可信且正常验证执行／共识，多节点 RPC 比较不是自行实现 Ethereum 共识，也不授权索引器修改账本。

## 第 1 层：多个 RPC 相同，就能证明链上事实吗？

**面试官：** RPC 分歧或 writer 切主怎样处理？先说多节点：配置三个服务商，两票相同就能接受充值吗？

**面试者：** 不能把 RPC 多数票当共识证明。服务商可能共用上游，可能都在错误配置的分叉上，也可能对日志采用相同的静默截断策略。它们相同只能增加工程置信度，不能自动证明某块已 finalized，更不能证明该块相关日志完整。

我会区分节点准入、观察比较和业务接受三步。先核验端点的链身份与同步能力，再按确定 hash 比较区块头、父链接、日志结果和 finalized 候选；最终接受仍遵守固定节点信任模型、已接受检查点及完整前缀规则。生产若使用自建验证节点、轻客户端或额外证明机制，应另行说明部署与信任条件，不能声称“两个 RPC 一致”已经具备这些能力。

因此，看到三个 head 都到 103a，只能说明它们报告了相同链头。若 accepted finalized 仍是 100，即使 T 已有演示性的 3 确认，25 USDC 仍不能进入平台可提现余额。高可用优先提供可解释的落后或暂停，不以降低最终性门槛维持表面成功率。

## 第 2 层：新端点 chainId 正确，为什么还不能直接切过去？

**面试官：** 你提到节点准入。如果新 RPC 返回 `chainId=1`，不就已经是 Ethereum 主网了吗？还要核验什么？

**面试者：** chainId 是交易域标识，不是不可伪造的网络身份证。至少还要读取创世块 hash，与固定配置比较，并核对本地已经接受的 finalized 检查点。错误端点可能是复用 chainId 的私链，甚至是创世相同但后来分叉的链；所以 chainId 加 genesis 是必要身份基线，却不是后续规范性的充分证明。

端点能力也要实测其响应语义：是否支持按 blockHash 获取日志，是否正确支持 safe／finalized 标签，是否保留恢复所需历史，是否处于同步中，以及限流和截断如何表达。身份或能力未通过的端点不进正式服务池；不支持 finalized 就不能把 latest 减固定块数冒充协议最终性。

请求切源时，携带原目标 `(height,blockHash)` 和过滤版本。取到另一条分支相同高度的内容，必须退回分支核验，不能把它拼成原块的后半部分。订阅断线后由数据库游标补扫，换订阅连接不等于已经补齐遗漏。

## 第 3 层：finalized 变低与 finalized 矛盾有什么不同？

**面试官：** 两个端点都通过准入，一个报告 finalized=100，另一个报告 finalized=102。是分歧就熔断，还是选更高的那个？

**面试者：** 先比较身份和祖先关系，不只比较数值。如果 100 是 102 的祖先，通常是节点进度或可用性差异：保留本地已接受检查点，落后端点不能让它倒退。更高候选也不能直接采用，要核验它延续已接受 finalized，并按策略确认可信来源；索引尚未完整应用到那里时，先保存候选，不能越过缺口发布 Finalized。

真正的矛盾包括同一 finalized 高度出现不同 hash，或更高候选的祖先不包含已接受 finalized。较低候选若连已接受检查点的对应祖先都不匹配，也不是普通滞后。若祖先数据暂不可得，则是“尚不能核验”，暂停推进而不是猜测成立。

任何触及已接受 finalized 的哈希矛盾，先停止相关确认与不安全发布、保留两侧证据并进入事故核验，不能由多数票覆盖旧检查点。后续若证实只是坏端点，可隔离端点并按受控流程恢复；若确有更严重问题，走第 13 题事故流程。未最终区间的不同 head 则可以是正常重组，交给共同祖先与撤销重放机制处理。

## 第 4 层：同一 hash 的日志不一致，能否取并集？

**面试官：** 最终性关系没冲突，但同一个 H101a，一个端点返回 T 的 Transfer，另一个返回空数组。是不是取并集就能避免漏充值？

**面试者：** 不能。并集会把一方伪造或错配的日志也纳入，交集又会静默漏掉真实事件。要先确认请求完全一致：相同 blockHash、合约 C、topics、过滤版本，以及响应是否明确成功、是否存在错误或服务商限制。将日志按确定顺序规范化并比较完整载荷摘要，不能只比数量；同一观察键对应不同金额同样是冲突。

如果没有可信完整结果，就将该块标记为待核验，不推进 applied。可向独立可信节点重查，或获取该块完整交易／回执集合做交叉检查，校验交易、日志位置与 blockHash；这些做法仍依赖具体节点或验证方案，不能一概称为密码学完整性证明。只有确认全量扫描成功，空结果才有“这块没有相关日志”的含义。

RPC 来源、原请求、响应摘要和核验结论要留存。自动故障转移可以换来源，但不得改目标 hash、凑日志或把失败降格为空块。否则 25 USDC 是否出现取决于网络重试顺序，后面的原子事务也救不了错误输入。

## 第 5 层：节点没问题，两个 writer 争主怎样围栏？

**面试官：** 你保证了输入，若旧 writer 网络暂停，新 writer 已接管，旧进程又醒来，怎样防止它继续写？仅靠租约过期可以吗？

**面试者：** 不够。租约或选主只决定谁应该写，数据库围栏必须保证旧任期实际上写不进去。接管者在唯一有效的数据库主库上，通过受控接管事务锁定 chain_state，分配更大的 writerTerm 并记录持有者。只有具备接管资格的控制路径能分配任期，普通旧 writer 不能见到围栏失败后自行提高任期抢回权限。

每次应用、undo、确认发布、恢复进度及规范状态更新，都必须在同一数据库事务里先锁定并核对当前 term、chainEpoch、mode 和预期 tip，再修改对应数据，直至提交才释放锁；也可以由具备等价保证的数据库受限接口统一执行。不能先无锁检查 term，再写业务表，也不能只更新游标时检查，前面却已提交余额。

这让竞争有清楚的线性顺序：旧事务若先取得锁并提交，其结果在任期切换前成立，新主必须接管这段状态；若新任期先提交，旧事务随后读到 term 不符就整体失败。围栏不追溯取消已经合法提交的块，但能禁止任期交接之后的旧主新增提交。

## 第 6 层：数据库本身分裂，writerTerm 还能保护吗？

**面试官：** 旧进程确实读到旧 term，但它连的是失联后仍可写的旧数据库；新主连新数据库。这时两个数据库都能检查通过，怎么办？

**面试者：** 单个数据库里的 term 不能解决两套可写历史。数据库故障转移必须先确保只有一个有效写入口，并用数据库集群仲裁、旧主隔离和存储／网络写入封锁阻止旧库继续接受有效提交。应用租约、DNS 切换或数据库中的一行 term 都不能代替这一前提。无法确认旧库已隔离时，就不能以安全切主完成对外承诺。

还要定义复制耐久边界。块、undo、accepted finalized、revision、Outbox 和恢复任务必须作为一致状态复制。要承诺已确认提交不丢，需要同步复制及允许提升的副本规则，确保被提升副本包含所有已承诺 WAL；不是笼统说“用了同步复制”就足够。

异步副本若丢掉旧主已经提交甚至发出去的 Finalized，可能让账本已加 25、索引却失去消息与幂等事实。此时不能清零 revision 或重建一个空 Outbox 继续服务；应隔离并恢复缺失的提交／发布记录，和下游对账后再决定接管。账本消费不属于索引数据库事务，数据库回退不会自动撤销账本结果。这里的可用性取舍必须公开，不能隐藏成一次普通重连。

## 第 7 层：切主后 Outbox 怎样接管而不丢消息？

**面试官：** 假设数据库没有丢提交，旧发布器发出了 Finalized，但 ACK 丢了，新发布器看到仍未发送。是跳过旧任期消息，还是生成新消息？

**面试者：** 都不对。消息一旦随块或确认事务提交，就是持久交付义务，切主不改变其 messageId、revision、业务关联和源块。新发布器应接管未完成项，按持久流位置重发原消息。账本把 Inbox 去重和充值记账放在自己的同一事务：如果原消息已经入账，再收一次不能再加 25；如果没有，则本次继续完成。

源消息的 writerTerm 可以保留用于审计，发送权由当前发布租约／围栏管理，不能把“消息来自旧任期”解释成“消息无效”。否则切主恰好丢掉旧主已提交而未发送的正确确认。revision 不能从零开始，也不能因为切主留出无法解释的流缺口。

旧发布器可能在围栏变化前拿到消息、变化后才完成网络发送，因此只做发送前检查不能承诺绝无重复。可以使用传输层的生产者围栏进一步限制，但端到端仍按至少一次和消费事务设计。迟到的 Observed 要服从 revision 与 Reverted／恢复边界，不得重新激活被撤销的分支；若已进入 finalized 冲突事故，通知发布与账本消费需要隔离协议，不能靠切主本身阻止已经在途的资金效果。

## 第 8 层：何时能声明切主完成，谁能恢复资金？

**面试官：** 新 writer 已能提交，新发布器也能重发，是否就可以宣布恢复？它能不能顺手把账本和提现状态一并修好？

**面试者：** 切主验收至少要覆盖三条线：输入仍属于固定链身份且延续 accepted finalized；写入已形成唯一有效数据库主库和更高 term，旧主的实际写入被拒；状态与交付从同一个持久位置接续，applied hash、恢复任务、revision、Outbox 和消费者进度都有解释。

故障演练应包含旧 writer 持有未提交事务、进程暂停后苏醒、旧发布器在途消息、ACK 丢失，以及数据库提升副本缺少最新 WAL。前三类要分别验证任期切换顺序、旧主拒写和重复消费无副作用；最后一类若不满足耐久前提，预期应是阻断恢复，而不是强行上线。查询可先以明确水位和降级模式恢复，不等于充值已完成。

索引器只能恢复链视图、规范消息与证据，不能直接修改账本余额、删除分录或重发外部付款。账本服务核验 Finalized、业务键和策略后决定入账；资金冻结、冲正和提现处置要走相应服务的授权流程。高可用恢复的是原有权责与不变量，不是在事故中把所有权限收进一个“恢复脚本”。

## 收束：机制、易错边界与反例

- **讲透的机制：** 多源按固定身份与 hash 核验，最终性按祖先关系判断，写权限在实际数据库事务中围栏，持久提交和 Outbox 义务跨任期延续。
- **最容易答错：** RPC 多数票不是共识；finalized 滞后不等于冲突；租约不是写围栏；writerTerm 不能隔离两套可写数据库；旧任期的已提交消息不能直接丢弃。
- **检验反例：** 旧主提交 Finalized 并使账本入账 25，ACK 丢失后切到落后副本，旧主又恢复连接。合格方案要么证明提交和 Outbox 已耐久复制、旧库已隔离并重投原消息，要么保持事故隔离；绝不能重置 revision、再造一条新充值或要求索引器删除账本分录。
