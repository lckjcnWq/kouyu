# 大问题 13：深重组或最终性冲突后何时能恢复服务？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| C / T / D / B | USDC 合约、主例交易、平台充值业务身份、平台收款地址。 | T 对应 25 USDC，但链上 B 的视图不等于该用户的平台可用额。 |
| accepted finalized / H100 | 已认可的最终检查点及其具体区块身份。 | 事故分类以它为边界，不以重组块数多少决定能否自动回退。 |
| 160a / 160b / 共同祖先 | 旧、新目标分支末端，以及两条历史最后共有的块。 | 教学变体两边可都高 160，祖先却是 100，数字相同不代表恢复正确。 |
| undo 窗口 141—160 | 在线可直接撤销的旧块范围。 | 撤到 140a 仍含旧分支影响，不能就地接上 b。 |
| 超窗口未最终重组 | 没否定已接受最终前缀，但直接撤销材料不足的分支变化。 | 可从祖先或更早可靠快照重建，不等于需要冲掉已最终账务。 |
| finalized 冲突 / halted | 新证据否定已接受最终历史，以及持久事故隔离模式。 | 哪怕只冲突一块也不能自动换链或重建后自行解冻。 |
| recovering / chainEpoch / writerTerm | 恢复模式、分支代次、写入者任期。 | 记录隔离并淘汰旧候选、围栏旧写入，两个编号不混用。 |
| S / 快照清单 | 固定重建起点及其链、范围、版本、摘要。 | 本例可取 S=(100,H100)、A=100/B=0，不能拿未验证的余额备份顶替。 |
| K=(height,hash) / F* | 固定验收截止块，以及验收适用的已接受最终检查点。 | K 可含未最终后缀，只有 F* 祖先前缀内的合格充值能进入最终义务集合。 |
| 影子 generation / recovery_job | 隔离投影代次与持久恢复任务。 | 按固定输入逐块续作，不直接改线上状态或重发正常资金通知。 |
| ABI / schema / 策略版本 | 事件编码约定、投影结构、业务解释规则。 | 重建冻结版本和历史归属依据，不能边回放边用最新规则覆盖过去。 |
| applied / 空块完整性 | 对外连续完整水位，以及无相关事件块也已成功扫描的记录。 | 影子进度不是正式 applied，缺历史不能填空跳过。 |
| revision / Outbox / 恢复边界 R | 持久消息位置、待交付义务、新旧查询状态的明确交接通知。 | R 说明新代次、K 和覆盖范围，不删除旧义务或重置序号。 |
| 查询快照重置 / 消费水位 | 按协议安装完整查询版本，以及下游已落实的位置。 | 下游要确认安装 K/R，broker ACK 不等于已生效；账本不参加余额快照重置。 |
| 风险门禁 / Inbox / Finalized | 账本事务的隔离条件、消费去重记录、最终确认消息。 | 门禁与迟到消费需串行裁决，停发送端挡不住已经在途的确认。 |
| pending / 已成功记账 | 留待核验的消费状态，以及已完成资金效果。 | 被门禁拦住的消息不能先标成功再丢弃，解除条件后仍需可续作。 |
| 冻结 / 冲正 / 外部付款 | 限制资金操作、授权追加纠正账务、实际对外支付。 | 冻结不删历史，冲正也不保证追回已付资产，未知付款仍是未决义务。 |
| 同水位逐项验收 / 分阶段放行 | 在同 K、F*、版本、R 下核对证据，以及按权限逐层恢复。 | 链、投影、消息、消费者、账本都要解释清楚，最后由账本和风控批准资金解限。 |

## 把整篇文章压缩成一个故事

**起因：** 教学变体里，本地到 160a，已接受 finalized 仍是 100/H100，但只保留 141—160 的 undo。新分支从 100 后分叉，T 从 101a 消失后在 102b 重入。撤到 140a 仍带旧历史，不能把它接到 b 上；不过新分支仍延续 H100，这首先是超窗口未最终重组，不是已接受最终历史被推翻。

**处理与异常：** 服务持久隔离受影响范围，从核验过的 S=100/H100 快照按固定版本重建到 K=160/H160b，逐块含空块留完整证据。影子应得 A=75、B=25，再通过持久恢复边界 R 协调查询消费者切版，旧观察不能在快照后复活。单独改变前提：若旧 101a 已最终且账本已入账，后来出现矛盾，则必须转 finalized 事故，账本门禁与在途 Finalized 消费在事务内串行裁决；停掉发布器本身挡不住迟到入账。

**结局与不能混淆的边界：** 普通变体若 F* 仍为 100，哪怕 K 的转账视图 B=25，该充值账本额仍应为 0；新 102b 被最终覆盖且合格消费后才为 25。验收必须同 K、F*、版本和 R，核对逐账户、消息义务、消费者与分录，不能只看总额或高度。最终性事故的纠账、冻结解除和未知外部付款另由权限方处理；先恢复可解释的只读，再逐层放行，不以进程变绿冒充完整资金恢复。

**流程位置与核心机制：** 处理在线 undo 无法覆盖的未最终重组，以及已接受 finalized 遭遇矛盾的事故。重点是隔离、固定检查点重建、消息与账本义务保全，以及同截止 hash 的恢复验收；不是把第 8 题正常撤销重放再讲一遍。

**必要前提：** 仍是 Ethereum 主网、USDC 合约 C、T 转入 B 共 25 USDC。单链串行 writer，单块数据库原子提交，账本仅在合格 Finalized 消费事务完成后入账。订阅只是提示。为讨论超出 undo 的情形，单独扩展一个教学变体：本地 accepted finalized 仍为 `(100,H100)`，旧 tip 为 `(160,H160a)`，在线仅保留 141—160 的 undo，新分支共同祖先为 `(100,H100)`。这不是 Ethereum 固定重组深度或真实事故记录；若真实部署已接受更高 finalized，必须按它重新分类。

## 第 1 层：先判断是深重组，还是最终性事故？

**面试官：** 深重组或最终性冲突后何时能恢复服务？在找共同祖先时发现 undo 不够，是不是从备份恢复就可以？

**面试者：** 先分类，不能以“回退了很多块”代替安全边界。若新分支延续本地已接受 finalized，共同祖先不低于该检查点，只是所需 undo 已被清理，那么属于未最终区域超窗口重组。允许舍弃旧的可撤销投影，从固定且可验证的快照重建。

若候选链与已接受 finalized 的 hash 或祖先关系矛盾，即使只差一块，也必须先熔断核验，不能自动回退该检查点。它可能来自坏 RPC、数据库损坏、配置错误或更严重的链问题；只有调查才能区分，不应一上来宣布协议最终性已经失效。无法取得祖先数据则是证据不足，同样不能猜测安全。

扩展变体的共同祖先为 100，F 也是 100，所以可以进入超窗口重建。反过来，若本地已经接受 F=102a，而候选 102b 不同，就不是“多找两块 undo”能解决的事故。恢复前要先回答是否保住了已作出的最终性承诺。

## 第 2 层：进入隔离，具体停什么、留什么？

**面试官：** 你把事故分开了，但发现问题时仍有 worker、查询、消息和账本在运行。只把索引进程停掉，够不够？

**面试者：** 不够，要持久记录隔离边界和未完成义务。在数据库围栏下将该链置为 recovering 或 halted，记录旧 tip、accepted finalized、最后公开 revision、原因与恢复任务；提高 chainEpoch，让旧分支候选失效，必要时接管 writerTerm，但这两个编号不能互相代替。

暂停受影响的规范写入、确认推进和不安全发布，保留原始头、日志、undo、Outbox 与 RPC 来源证据。采集可以继续以有界方式留证，但不能把新观察直接变成正式状态。查询返回旧水位和恢复模式，或只提供已核验最终前缀，不能把半重建余额称为完整结果。

超窗口未最终重组不意味着所有已最终充值都失效，可先隔离该链的未最终视图和新确认。触及 accepted finalized 的事故则要通知账本／风控暂停受影响的充值自动消费和资金操作，并确认隔离已生效；若影响范围无法可靠界定，应扩大到该链或相关资产，而不是凭猜测只冻结一笔。其他链、其他服务是否继续运行由依赖和风险边界决定，不能无条件全站停机，也不能无条件继续付款。

## 第 3 层：undo 不够，怎样选择重建起点与终点？

**面试官：** 你说保留旧状态并离线重建。旧 tip 是 160a，undo 从 141 才有，那能不能先撤回到 140，再接新分支？

**面试者：** 不能。撤到 140a 仍没有回到共同祖先 100，140a 的投影包含旧分支 101—140 的影响，拿它接 b 分支会形成混合状态。要选高度不高于共同祖先、hash 经核验的固定快照 S，并从 S 的下一块沿新分支正序完整回放。

本例可使用总览的 `(100,H100)` 快照，A=100、B=0 USDC。快照清单还要包含链身份、来源 hash、资产范围、投影 schema、解码／资产策略版本及校验摘要；不能用“昨天的余额备份”代替。更旧快照也可以，但必须补齐历史并重新验证经过原 accepted finalized 的祖先关系，不能因此倒退或遗忘这个最终性承诺。

终点也要先固定为 K，例如 `(160,H160b)`，而不是不断变化的 latest。恢复计划记录 S、共同祖先、K 和选取依据，确认 K 延续 H100。历史数据取不到或快照不可验证，就保持隔离，不能补空余额或自动换到另一条“看起来可用”的链。是否继续采用 Ethereum 主网的权威历史是既定配置；改变信任根或链选择必须另走授权决策，恢复任务无权自行决定。

## 第 4 层：怎样重建而不污染线上状态？

**面试官：** 起点和 K 都固定了，但回放中又崩溃，或者解码器刚升级，怎样保证重建可续作且结果可比较？

**面试者：** 我会建立独立的影子投影代际和持久 recovery_job，绑定快照清单、目标 K、规则版本、当前阶段和下一块。每个块都按确定 hash 获取全量相关证据，按固定顺序解析并原子提交影子区块、投影、undo 与影子应用游标；空块同样记录完整性。重启从最后一个已提交块继续，重复块不能再加一次金额。

重建不能混用“当前时间”“最新地址归属”或运行途中变化的 ABI；需要这些业务输入就固定版本并留可重放依据。未知事件或策略不匹配要停在明确位置，不应为了赶上进度静默跳过。若目的是修复解码器，必须显式指定新版本，并解释与旧结果差异，而不是边重放边改规则。

影子结果不直接发布正常 Observed／Finalized，也不复用或重置线上 revision。否则一次恢复会把历史再通知一遍。旧线上投影和公共 Outbox 保留用于审计，影子游标只是重建进度，不是对外 applied。对本例，101b 不含 T、T 在 102b 重入时，影子结果应按新观察身份得到 A=75、B=25；这仍不等于平台可用充值已增加。

## 第 5 层：投影重建好了，旧消息会不会把它改回去？

**面试官：** 影子结果正确，但旧 Observed 已经发给查询消费者，甚至正在重试。把数据库指针切到影子版本就能恢复所有下游吗？

**面试者：** 不能，投影切换和下游状态重置需要明确的恢复边界协议。先固定旧公开流的截止 revision，并暂停或协调受影响消费者，清点截止前已提交但未完成的 Outbox；不能把它们统统删除，也不能让迟到旧消息在新快照之后继续生效。

对可重建的查询消费者，可以发布一个持久恢复边界 R，携带新代际、精确 K、快照摘要和被替代的观察流范围。消费者在自己的事务中安装同水位快照、记录 R 及恢复代际，再拒绝被覆盖范围的旧观察效果；这必须是约定好的快照重置语义，不是把缺失 revision 当成已消费。仍有交付义务的历史消息继续保留、重投或按该协议记为已被快照覆盖，并留下处理记录。

canonical writer 在围栏下核对恢复任务和基线未变，用一个数据库事务激活新投影代际、canonical 映射入口及 K 的 applied 状态，并生成新的公开恢复边界、推进持久 revision。影子大表提前准备，切换的是一致的代际入口，不逐行向外暴露混合数据。账本不参加这种“用余额快照重置”的协议，它已有的分录和业务去重事实必须独立保留。

## 第 6 层：未最终重组为什么不能冲掉 25 USDC？

**面试官：** 你保留了账本。若 T 从 101a 被移出，查询里从 B=25 变成 B=0，账本不也应该减 25 吗？

**面试者：** 在当前未最终重组变体中，accepted finalized 一直是 100，T 位于其后，所以平台充值本来就不应入账。撤销的是链上观察及可撤销转账投影，平台可提现充值额始终为 0；不存在需要“减回去”的账本分录。把投影余额等同平台账户余额，才会产生这个误操作。

T 后来进入 102b，logIndex 从 7 变成 4，形成新观察；不能因 txHash 相同就复活 101a 的旧观察，也不能把新的区块级 logIndex 当成跨分支业务身份。沿用总览单相关日志的受控规则，充值意图 D 与经核验的链、C、T、收款和金额关联。生产多日志交易还需协议定义的匹配规则。

只有新的 102b 落入已接受 finalized 前缀、该前缀已完整应用并通过业务核验，才产生合格 Finalized；账本使用既有持久业务幂等记录入账一次 25。若在 F=100 时发现账本已经入账，则另有提前确认或消费违规，必须作为额外事故调查，不能把它归因于“正常深重组需要冲正”。

## 第 7 层：已经按 finalized 入账的矛盾怎样处理？

**面试官：** 那单独改变前提：101a 已被接受为 finalized，账本也已增加可用额 25，后来发现与它矛盾的可信证据。现在能不能恢复到 H100，把那条分录删掉？

**面试者：** 不能。此时已越过原先对业务承诺的最终性边界，应先按 finalized 冲突熔断，而不是自动 undo 或选择 RPC 多数链。保全接受检查点的证据、政策版本、Finalized 消息、消费记录和分录，调查是数据源、内部状态、配置还是其他原因造成矛盾；受控恢复必须记录调查结论和授权。

资金隔离由账本／风控执行，索引器只能发出风险事实和受影响业务清单。冻结是限制可用额或支付资格，不是删除历史，也不等于钱必然还在：若这 25 已被提现或转给其他账户，要跟踪实际资金流、未决外部付款及潜在损失，不能把余额强改成 0 就宣布消除了义务。

若核验后需要纠正既有入账，由有权账本服务按授权追加可审计、幂等的冲正或调整分录，关联原分录与事故单；同一授权重试不能重复冲正。若证实只是坏端点，原正确分录也不能因为“事故发生过”而被冲掉。解除冻结与恢复提现同样需要账本和风险流程批准，索引重建成功不自动授予这些权限。

## 第 8 层：隔离之前已在途的 Finalized 怎么办？

**面试官：** 你已经暂停发布和冻结，但事故发生前一条 Finalized 已经在网络里，账本还没处理。等它迟到后，会不会继续把 25 变成可用余额？

**面试者：** 所以隔离不能只停发送端。账本需要持久、可串行裁决的风险门禁：在充值消费事务内核对该链／资产／业务是否被隔离，再与 Inbox、业务幂等和分录一并提交。风险门禁更新与消费使用同一受控锁或等价的原子条件，不能在事务外先查“未冻结”再过很久记账。

消费若先提交，该笔属于隔离前已完成义务，必须被事故清单覆盖，并由冻结及后续授权处置接住；隔离若先提交，迟到消息就不能新增长期可用额。可将它保存为待核验，不把 Inbox 标成“已成功记账”后丢弃，待解除条件满足再续作。索引器要拿到账本门禁生效的确认，超时只能视为隔离结果未知，不能对外宣称资金已安全冻结。

消息本身的 id、源块和原 revision 不应重写。普通切主重投同一已提交 Finalized 与 finalized 冲突隔离是两种场景；前者靠消费幂等继续履约，后者额外受风险门禁约束。已经完成的外部付款不能被这个门禁追溯撤回，只能进入实际资金处置流程。

## 第 9 层：恢复验收为何必须使用同一个截止 hash？

**面试官：** 现在链视图重建好了，风险门禁也确认了。有人说“新旧高度都到 160，余额总数也相同”，可以验收吗？到底要核对哪些结果？

**面试者：** 不可以。同高度可能不同分支，总量一致也可能把 25 记给错人。验收必须冻结共同截止 `K=(height,hash)`、适用的 accepted finalized `F*`、规则版本和公开恢复边界 R，所有对比都声明自己的覆盖范围，不拿某个系统的 latest 与另一个系统的昨天比较。

至少检查五组证据。第一，链身份正确，S 到 K 父链连续、逐块完整，K 与原已接受 finalized 兼容；普通重建不允许覆盖这个承诺。第二，每块证据和投影在 K 对应同一 hash，账户、事件明细、撤销记录和精确整数结果一致，不能只看 A+B=100。第三，恢复边界及 Outbox 在持久 revision 上没有未解释缺口，旧消息不会复活旧分支。第四，各查询消费者确认已经安装 K／R 对应版本，不能以 broker ACK 代替消费生效。第五，账本在自身一致读下逐项核对截至 K、且属于 F* 祖先前缀的合格充值集合，包括业务键、源块、Inbox、分录和待处理状态。

账本账户余额可能还有交易等其他资金流，不能要求它等于链上 B 余额。K 含 T 但 F* 仍是 100 时，投影 B=25、该充值账本额=0 是正确结果；若 F* 已覆盖 102b 且消费完成才应为 25。其他业务通过可界定账务范围核对。finalized 事故还要额外验收冻结、授权调整和外部付款处置，未决项不能被一张“余额相等”截图掩盖。

## 第 10 层：哪些故障通过了，才允许分阶段恢复？

**面试官：** 你把验收口径固定了，但如果恢复流程自身再次崩溃或发生切主，如何证明这些保证还能成立？恢复顺序怎么定？

**面试者：** 我会把失败注入点和预期不变量写成验收矩阵，而不是只跑正常重放。以下都是应验证的情形，不宣称本文已运行工程测试。

| 故障点 | 必须观察到的结果 |
|---|---|
| 未最终重组超过 undo 保留 | 不拼接 140a 与 b 分支；使用经核验 S 重建；accepted finalized 不倒退 |
| 同高度 finalized hash 矛盾 | 熔断、留证据；不自动换链、不自动冲正 |
| 快照摘要错误或历史块缺失 | 重建失败并保持隔离；不补空块、不初始化空账 |
| 回放某块事务中途崩溃 | 该块要么完整生效要么不生效；重启按影子游标续作，金额不重复 |
| 旧 worker 或旧 writer 迟到 | epoch 淘汰旧候选、实际 term 围栏拒绝旧主写入；已提交事实仍被保留 |
| 激活新代际时崩溃、Commit 结果未知 | 查询持久代际、K 和 R 判定；不能重复激活或生成相互矛盾的恢复边界 |
| 恢复边界已发送但 ACK 丢失、旧观察迟到 | 重投同一边界；消费者按事务与代际规则收敛，旧分支不复活 |
| 风险门禁与 Finalized 消费竞争 | 消费先提交则纳入冻结清单，门禁先提交则阻止新可用额；两者都可审计 |
| 切主副本缺少已发布的持久记录 | 阻断恢复并补齐／核验义务；不重置 revision 或 Inbox |
| 账本冲正重试、付款结果未知 | 不重复调整；未知付款留为未决，不声称已撤回或已无损失 |

通过后仍分阶段放行：先开放带准确 K、水位和模式的只读查询，再在围栏下恢复有界采集及规范应用，随后恢复已核验分支的消息与业务确认，最后由账本／风险权限方解除资金限制。若重建后又发生新 head，只能在已验收 K 之后连续追赶；不能把未验收的新分支顺手纳入“已恢复”范围。

每阶段记录批准条件、操作者、证据和停止阈值；发现祖先矛盾、消息缺口或账务差异应重新隔离，而不是回滚数据库备份来抹掉对外义务。恢复完成的标准是各层对同一事实和未决义务达成可追溯的一致解释，不是进程变绿或积压下降。

## 收束：机制、易错边界与反例

- **讲透的机制：** 先按 accepted finalized 分类事故，超窗口未最终重组从固定快照重建；用影子代际与持久恢复边界激活；按同截止 hash、祖先、投影、消息和账本消费验收。
- **最容易答错：** undo 不够不等于允许回退 finalized；冻结不是删除分录；重建不能重置公共 revision、Inbox 或账本；索引服务恢复不代表资金权限已恢复。
- **检验反例：** 新投影在 160b 正确、B=25，但查询消费者还停在 160a，旧 Finalized 正在路上，账本已对原入账发生过外部付款。只比高度和总余额会误报成功；合格方案必须指出消费者代际、门禁竞争结果、原分录及付款义务，任一未核验就不能宣布完整业务恢复。
