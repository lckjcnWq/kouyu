# 大问题 5：怎样保证投影与扫描进度一致？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| PostgreSQL / 原子事务 | 本例数据库，以及一组本地修改共同提交或回滚的边界。 | 保护索引内部恢复义务，不把链和账本包进同一个事务。 |
| canonical writer / chain_state | 唯一修改规范状态的写入者，以及保存链当前状态的行。 | 事务内锁定并复核，不靠事务外“查过没处理”防重。 |
| 101a / H100 / tip | 待应用的具体分支块、前驱哈希、当前已应用末端。 | 从 (100,H100) 接 101a，不能因 102a 先拿到锁就跳块。 |
| height / parentHash | 当前块高度与其引用的父块哈希。 | 同时满足下一高度和父哈希等于 tip，才可接续。 |
| 原始候选 / raw 水位 | 已抓取材料，以及采集阶段自己的进度。 | raw 到 103 不代表业务投影也完整到 103。 |
| projection / applied | 查询视图，以及已连续完整应用的高度和 hash。 | A 减 25、B 加 25，要与对应应用进度共同生效。 |
| undo | 应用时留下的前值或撤销信息。 | 不是出故障后凭当前余额猜“减回去”。 |
| Outbox / revision | 事务内待发记录，以及持久修订顺序。 | 块生效就必须留有可续发通知，不能在提交后临时补写。 |
| Inbox / 消费事务 | 下游去重记录，以及下游自己的业务提交边界。 | 索引事务成功不代表下游已成功，重投要由消费端防重复效果。 |
| 应用标记 / 载荷摘要 | 块是否已经作用于状态，以及其内容一致性的依据。 | 重复块核对后复用结果；相同 hash 内容冲突不能覆盖。 |
| COMMIT 超时 / context 取消 | 提交回执没及时回来，以及调用方不再等待。 | 都不能证明数据库没提交，要读持久状态裁决。 |
| 空块 / 解析失败 | 范围内确无日志，以及有相关日志但看不懂。 | 前者可完整推进，后者必须阻断受影响投影。 |
| filterVersion / decoderVersion | 过滤范围与解码规则的版本。 | 完整性有明确口径，不能把另一范围的水位移来作证。 |
| 准备区 / 激活指针 | 先分批准备完整结果的地方，以及正式切换到哪个完整版本。 | 超大块可分步准备，不能把半块余额标成完整。 |
| READ COMMITTED / 一致快照 | 常见读隔离级别，以及读取同一版本数据的要求。 | READ COMMITTED 的多条语句未必同快照，余额和 tip 不能各取一个新旧版本。 |
| generation / chainEpoch / recovering | 投影代次、分支代次、恢复模式。 | 缓存带版本，恢复中不把中间状态伪装成健康完整查询。 |
| Finalized 发布游标 | 已经产生最终确认通知的连续位置。 | 后续确认推进也要把游标和确认 Outbox 同事务，不能只保护首次应用。 |

## 把整篇文章压缩成一个故事

**起因：** writer 正在应用 101a 的 25 USDC 转账。若先把 B 加到 25、把游标改成 101，再另写撤销记录和通知，任何一次崩溃都可能留下“余额已变、恢复依据却缺失”的半套事实。

**处理与异常：** 因此它在同一事务里锁住链状态，复核前驱 100/H100，写区块完整记录、A/B 变化、undo、revision、Outbox 和 applied。提交前崩溃就整块不生效；COMMIT 回执超时则先查数据库，确认已提交就复用，不再加 25。并行抓完的 102a 即使先拿锁，也要等待 101a，空块也要提交完整进度；有日志却解析失败不能冒充空块通过。

**结局与不能混淆的边界：** 恢复后的状态只能是原来的 100／0 与水位 100，或完整的 75／25 与水位 101a，并留有可交付通知。查询还要把余额和水位按同版本读取，不能拼旧余额加新 tip。这个原子性止于索引数据库；账本何时入账仍由消费事务决定，Outbox 已存在也不等于充值已经可提现。

**流程位置与核心机制：** 从已验证候选块到数据库状态提交，独立讲清原子集合、并发裁决及崩溃窗口。端到端账务边界见 01，撤销恢复的调度见 08。

**必要前提：** PostgreSQL、单链串行 canonical writer、单块完整性边界。原始抓取可先落候选区，但候选存在不代表该块已经生效。

## 第 1 层：原子性的最小闭环

**面试官：** 怎样保证投影与扫描进度一致？

**面试者：** 在这个模型中，一个完整块是最小应用单元。writer 在一个数据库事务内登记采用区块及完整性、插入或核验分支观察、更新投影、保存 undo、分配发布 revision 并写 Outbox，最后推进 applied 高度及 hash。事务提交时这一组状态共同生效，失败则共同回滚。这样 applied 不会越过尚未修改余额的事件，余额也不会已经加了 25 却没有应用记录，导致重启重复加。查询必须读到同一事务版本的投影和水位，而不是分别从不同缓存拼接。

## 第 2 层：为什么不能先保存日志再异步更新余额

**面试官：** 日志已经持久化了，为什么不能先把游标推进，再慢慢算余额？

**面试者：** 可以拆“采集完成”和“业务应用完成”两个游标，但不能把前者命名为完整投影水位。若 raw 游标到 103、projection 只到 100，展示服务必须声明投影仅完整到 100，业务确认也不能据 raw 进度放行。基线选择一个 applied 原子闭环，避免初学者混用。需要异步解析时，原始候选有自己的扫描水位，应用 writer 仍只按连续已验证块推进；未知解析可以留证据，但其受影响业务投影不得跨过去声称完整。

## 第 3 层：事务里怎样防止重复块

**面试官：** 两次处理同一个 101a，都先查到“没应用”，事务还能防重吗？

**面试者：** 不能靠事务外的先查后写。我在事务内锁定该链的 chain_state 行，校验当前 tip 与预期 `(100,H100)`，再检查块的应用标记和载荷摘要。第一个事务提交 101a 后，第二个拿锁看到 101a 已完整应用，核验相同内容后返回既有结果，而不是再次改余额。唯一索引限制分支观察及 canonical 映射；但唯一键只是最后一道约束，不能把重复插入冲突捕获后仍继续加款。若同 hash 候选内容不一致，应停止核验，不以覆盖旧记录来达成所谓幂等。

## 第 4 层：如果两块不同但都已抓完

**面试官：** 101a 和 102a 并行抓完，两个事务争锁，102a 先拿到锁怎么办？

**面试者：** 它必须检查 `height=tip.height+1` 和 `parentHash=tip.hash`，条件不满足就不应用，而是留在有界重排缓冲或候选存储等前驱。数据库锁只保证互斥，不自动保证业务顺序。写入可以串行，但抓取并行；103 先完成不意味着允许从 100 跳到 103。如果发现父哈希属于另一个分支，就交给分支管理，不靠等待队列无限阻塞。对外完整性始终是从检查点接续的前缀，而不是所有成功任务的集合。

## 第 5 层：崩溃点逐个推演

**面试官：** 假设修改 B 余额后崩溃，或者 COMMIT 超时，分别怎样处理？

**面试者：** 若还没提交，事务整体回滚，重启从 100 重新应用；不会残留只加 B 没减 A 的一半结果。若 COMMIT 请求已发送但客户端超时，结果未知，不能马上换新身份重新加 25。我会在恢复连接后读 chain_state、块应用标记及相应 Outbox，核对是否整体提交；若已应用就复用结果，没应用才重试原块。两种情况都以数据库持久状态裁决。context 取消只说明调用方不再等待，不证明服务器侧事务没有提交。

## 第 6 层：Outbox 为什么必须在里面

**面试官：** 余额和游标已经一致了，Outbox 放事务外有什么实质问题？

**面试者：** 放外面会出现两种错误窗口：块已提交但进程在写消息前崩溃，下游永远不知道；消息先写或先发，块事务后来失败，下游看到没有来源的变化。将 Outbox 与块事务同提交，保证“本地生效必有待交付记录”，发布器可以重复发送同一记录。它不保证下游已经生效，也不保证网络只发一次；消费端另用 Inbox 与业务变更同事务。Finalized 在后续独立推进时同理，需要其确认发布游标与确认 Outbox 共事务，否则可能漏确认或重新产生确认。

## 第 7 层：空块与解析失败为什么不同

**面试官：** 102 没有相关日志可以推进，那有日志但解析失败，也能先当没变化推进吗？

**面试者：** 不能。完整空结果意味着配置范围内没有需要应用的事件；解析失败意味着有尚未解释的输入，可能正好影响充值或余额。可以把 raw 完整性记录下来，并推进独立 raw 水位；但受影响投影必须停在前一块，或采用事先明确的按合约／业务分片隔离，让只有不受影响的投影继续。不能把失败事件忽略后还给全局投影盖 complete。过滤版本、decoderVersion 和资产策略版本都应进入检查点，使“完整”有明确作用域。

## 第 8 层：超大块不能一个事务处理怎么办

**面试官：** 如果一个块包含太多日志，事务过大，你会把块拆开提交吗？

**面试者：** 可以分批持久化候选和计算结果，但不能把半块状态以完整水位发布。方案之一是准备区按块落盘所有变化并验证摘要，最后以受控事务激活新投影版本和完整块标记；另一种是明确支持块内应用位置，读者只访问最后一个完整版本，undo 与恢复也要理解块内阶段。基线先不引入这些复杂性，而用块事务换取清晰边界。改变模型时必须说明读隔离、激活指针及崩溃续作，否则“拆事务提速”只是把一半余额暴露出去。

## 第 9 层：缓存与多次查询怎样保持一致

**面试官：** 数据库事务成立，API 分两次读余额和 tip，恰好跨提交怎么办？

**面试者：** 应使用一致快照读取，或把投影值与其版本、水位一同物化返回，并验证读取版本一致。PostgreSQL 的 READ COMMITTED 下多条语句不保证同一个快照，不能因为“用了事务”就误认为两次读取一致；可采用适当隔离级别、单条查询或显式版本绑定。缓存同样按投影 generation、chainEpoch 和水位更新，不能从旧余额缓存加新 tip 得到假完整结果。恢复期间若采用多块 undo，接口返回 recovering 或读保留的完整旧版本，不能伪装当前中间状态是健康新版。

## 第 10 层：怎样检验原子边界真的完整

**面试官：** 你如何检查自己没有漏掉某个必须一起提交的状态？

**面试者：** 我会列出提交后的可恢复事实：采用哪个 hash、完整扫描依据、事件是否已应用、前值怎样撤销、待发布什么、下次从哪里继续。逐个删掉一项做反例：无应用标记会重复加款，无 undo 无法正确回退，无 Outbox 会丢通知，无 hash 游标会认错分支，无策略版本会无法解释重放差异。再在写余额、写 undo、写 Outbox、推进游标、COMMIT 回执的窗口中断，检查恢复结果只能是“整块未生效”或“整块生效且可续作交付”。故障注入是推荐验证，不是本文已经运行的测试。

## 本题收束

- **讲透的机制：** 原子事务覆盖的是完整恢复义务，不只是几张业务表；互斥、顺序、幂等和读版本仍需各自设计。
- **最易答错：** 原始日志持久化等于投影完整；COMMIT 超时等于没提交；用了数据库锁就自动按高度执行。
- **检验反例：** 余额加 25、游标前进，但 Outbox 没写；重启后不再扫描原块，下游永远不入账。这证明事务集合不完整。
