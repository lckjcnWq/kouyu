## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EVM / Ethereum / RPC | EVM 是合约执行环境，Ethereum 是本例的链，RPC 是向节点查询的接口。 | 本文限定 Ethereum 主网，其他 EVM 链和 L2 不自动拥有相同最终性保证。 |
| chainId / genesisHash | 链编号与创世块哈希，一起核对连接的是哪条历史。 | chainId=1 还不够，不能把误连的主网分叉当成目标链。 |
| C / USDC / 最小单位 | C 是核验后的资产合约，USDC 在本例有 6 位小数。 | 25000000 个最小单位是 25 USDC，名称相同的别家合约不能冒充 C。 |
| A / B / T / D | A 是转出地址，B 是平台收款地址，T 是交易，D 是平台充值业务身份。 | D 由核验规则分配，不是 ERC-20 字段；本例 T 只有一条相关 Transfer。 |
| H100 / H101a / H102b | 区块哈希的教学符号，a、b 表示不同分支。 | 101 是位置编号，不是区块身份证；这些不是主网真实历史记录。 |
| Transfer / ABI / decoder | 转账事件、事件编码约定、按约定解读原始字节的程序。 | 能解析出金额还需核对 C、历史版本、收款归属和业务语义。 |
| observationKey / logIndex | 一次分支内日志的身份，以及它在整个块内的日志位置。 | 键为链、blockHash、txHash、logIndex；T 重入新块可能从位置 7 变为 4。 |
| canonical / parentHash / 共同祖先 | 当前采用的链、父块哈希、两条分支最后共有的块。 | 切分支先找到共同祖先，不能把相同高度当作相同区块。 |
| 订阅 / 连续补扫 / 空块 | 通知负责提醒，扫描负责逐块补齐；空块只是没有本次过滤范围的日志。 | 102a、103a 即使没有 C 的事件，也要成功扫描并提交进度。 |
| scanComplete / filterVersion | 声明某个范围已取全的标记，以及当时采用的过滤规则版本。 | complete 依赖可信节点与 API 能力，HTTP 200 或空数组本身不证明完整。 |
| 按 blockHash 取日志 | 先认定具体区块，再查这个区块的日志。 | 高度查询降级必须补充绑定目标 hash 的完整来源，前后重读头不能独自兜底。 |
| projection / applied | 为查询生成的派生视图，以及已连续完整应用到的位置。 | A=75、B=25 的转账视图不是平台账户账本，也不是“最大抓完高度”。 |
| canonical writer / PostgreSQL 事务 | 唯一修改规范状态的写入者，以及本地数据库的共同提交边界。 | 投影、undo、Outbox、游标同提交；它不把 Ethereum 与账本包成全局事务。 |
| undo / replay / recovering | 撤销记录、按顺序重放、正在恢复的查询模式。 | 旧块逆序撤、新块正序放；恢复转账视图不是发起链上退款。 |
| included / confirmations / k=3 | 已包含、按本文口径计算的确认数、教学风险展示阈值。 | head=103、包含块=101 时为 103−101+1=3，仍不能代替 finalized。 |
| safe / finalized / F | 节点给出的安全与最终检查点语义，F 代表已接受的最终检查点。 | 要核验确切 hash 和祖先关系，不能按等待时长或仅按高度认可最终性。 |
| eligible / rejected / pending | 业务资格已合格、明确拒绝、证据尚待补齐。 | pending 会挡住本业务范围的确认发布，链最终性更高也不能跳过。 |
| finalizedPublishedHeight | 已完成最终确认发布的连续高度。 | 不能超过 applied 与 accepted finalized 的较小值，还须满足祖先及业务资格条件。 |
| Outbox / Inbox / ACK | 事务内待发箱、消费者去重收件记录、交付确认。 | ACK 丢失可以重发，消费者需把去重和业务效果放在自己的同一事务。 |
| Observed / Reverted / Finalized | 观察到、撤销观察、符合最终确认条件的三类通知。 | 它们是不同事实，不能把撤销当普通重复，也不能把已发送当已入账。 |
| revision / chainEpoch / writerTerm | 发布修订号、分支代次、写入者任期。 | 修订号在撤销时仍递增；分支代次和旧主围栏各解决不同问题。 |
| big.Int / uint256 / Gas | Go 大整数、链上无符号 256 位整数、执行资源费用。 | 金额不用浮点数；本例 Gas 另付 ETH，不从 25 USDC 暗扣。 |
| halted / finalized 冲突 | 持久停机隔离，以及新证据与已接受最终前缀矛盾的事故。 | 不走普通自动回退；冻结受影响资金与发布，账务纠正由账本授权追加分录。 |

## 把整篇文章压缩成一个故事

**起因：** A 在核验后的检查点 100 有 100 USDC，向平台地址 B 转 25 USDC。交易 T 出现在 101a，产生 C 的一条 Transfer。平台不能因为订阅弹出一条消息就让用户提现，而要先查明是哪条链、哪个区块、哪个资产合约，以及这笔转账对应哪项充值 D。

**处理与异常：** Go 从 100 后逐块扫描，连没有相关日志的 102a、103a 也登记完整结果；在一块事务里写转账视图、撤销依据、Outbox 和游标。此时视图为 A=75、B=25，103−101+1=3 次确认只供展示，平台可用充值仍为 0。若未最终的 a 分支被替换，就退到共同祖先 100，再应用 b；T 在 102b 以新日志位置重入，要认作新观察，不能被旧交易哈希永久挡掉。

**结局与不能混淆的边界：** 正常路径中，101a 进入已接受 finalized 的完整前缀、D 资格合格后，索引器才可靠发出 Finalized；账本消费提交后，可用充值增加一次 25。重组变体则等待 102b 的新证据，不能同时声称旧 101a 已最终。Outbox 重发不是第二笔充值，撤销投影不是链上退款；若矛盾触及已接受 finalized，必须持久隔离和授权核验，不能自动删账或以一份新空账宣布恢复。

**阅读对象：** 准备交易系统与 Web3 后端面试的开发者。正文为教学设计，不代表目标公司的架构或个人生产经历。

## 一、文字全流程

### 1.1 讨论基线与贯穿案例

- **产品与职责：** 托管平台的充值观察及通用链上查询。转账由 Ethereum 执行；Go 索引器只维护派生链视图与确认通知，账本服务拥有平台账户余额和记账权。交易构造、私钥管理、广播与提现不是本题主线。
- **执行环境：** Ethereum 主网，`chainId=1`，固定创世块身份；可信、正常同步的执行／共识节点提供 RPC。C 代表配置中经核验的 USDC 合约地址，精度为 6。C 是符号，不是任意同名代币。其他 EVM 网络、L2 不默认继承这些最终性语义。
- **教学编号：** 100、101、102 等是便于推演的局部连续编号，H100、H101a 和 T 均为符号，不是声称主网真实第 101 块已有 USDC，也不代表 Ethereum 每块都会形成新的最终检查点。所有“F 覆盖某块”均以节点实际最终性证据为前提。
- **存储与并发：** PostgreSQL；单链单个串行 canonical writer，RPC 抓取可有界并行。数据库事务覆盖索引器内部状态，不跨到账本。生产方案保留 undo、Outbox 和持久发布序号，不创建本文的可运行工程。
- **余额口径：** 基线检查点 `(100,H100)` 已核验 A 为 `100000000`、B 为 `0` 个最小单位，即 100 和 0 USDC。投影是该快照加允许合约事件形成的转账视图，不宣称所有 ERC-20 都能仅靠 Transfer 还原余额。
- **本次业务：** 交易 T 在区块 `(101,H101a)` 成功，交易位置为 2，Transfer 的区块级 `logIndex=7`，A 向平台充值地址 B 转入 `25000000` 个最小单位，即 25 USDC。该交易在本例只产生这一条相关 Transfer；交易哈希不等于日志身份。
- **充值业务身份：** 将这笔充值业务记作 D，由平台按核验后的收款、资产、交易和事件匹配规则分配；D 不是 ERC-20 原生字段，也不等于任意一条通知的 messageId。本例限定 T 只有一条相关 Transfer，不代表通用交易均可仅按 txHash 匹配。
- **初始进度：** 索引已完整应用到 `(100,H100)`；接受的 finalized 检查点也是 `(100,H100)`。先观察分支 a 到 103，102a、103a 没有相关日志，但仍需登记并推进扫描游标。
- **确认政策：** 可展示未最终结果；演示性 `k=3` 确认数只用于风险展示，本文定义 `confirmations=headHeight-includedHeight+1`。平台可提现充值只在事件所在块属于已接受 finalized 检查点祖先、该前缀已完整应用、业务核验成功且账本事务完成后增加。3 确认不是 Ethereum 协议常量。

主路径的最终结果：无重组且 101a 后来落入已接受 finalized 前缀时，转账视图为 A=75、B=25 USDC，账本按充值业务规则增加 B 所属平台账户可用额 25 USDC。Gas 以 ETH 支付，不从这 25 USDC 中暗扣；平台手续费在本例为零。

### 1.2 从用户转账到业务完成

```text
用户将转账 T 提交给 Ethereum〔签名与广播由相邻系统负责〕
    ↓
链上执行〔C 的 transfer；区块执行成功并产生 Transfer〕
    ├─ 尚未包含／RPC 暂查不到 → 仍未知，不制造充值
    └─ 执行失败 → 不产生这笔成功转账的持久日志，不入账
    ↓
订阅提示或定时轮询发现链头变化〔不是完整性证明〕
    ↓
读取目标链头与区块头，核对 chainId／创世身份／父哈希
    ↓
从已提交游标的下一块开始连续补扫
    ↓
按确定 blockHash 获取 C 的日志〔空结果也记录完整扫描〕
    ↓
保存原始证据，校验地址／topics／ABI／金额与收款归属
    ├─ RPC 错误或结果不完整 → 不跨过该块
    └─ 解析不明／业务不符 → 留证据；阻断受影响投影或明确隔离
    ↓
canonical writer 再校验预期父块与任期
    ↓
单块数据库事务
    ├─ 分支观察与区块完整性记录
    ├─ 投影变更与 undo
    ├─ 发布 revision 与 Outbox
    └─ 连续 applied 游标〔与上述变化同提交〕
    ↓
查询／下游看到 included 状态与明确的 blockHash、水位
    ↓
持续核对规范分支及 safe／finalized 检查点
    ├─ 未最终重组 → 停止不安全发布 → 撤销旧分支 → 应用新分支
    └─ 已接受 finalized 检查点冲突 → 熔断与人工恢复流程
    ↓
完整应用到已接受 finalized 前缀，事务生成 Finalized 通知
    ↓
Outbox 至少一次交付；账本消费事务核验、去重并记账
    ↓
业务回执／账户查询显示充值完成〔不是仅“索引已完成”〕
```

确认推进可能晚于原块的应用，必须有独立、可恢复的确认扫描；不能只在第一次收到日志时检查一次 finalized。

### 1.3 主要异常分支

```text
订阅断线／重复／同高度新头
    → 从数据库游标恢复，按哈希核对旧 tip，补扫缺口

父哈希不接续／同高度哈希不同／新 head 反而更低
    → 找共同祖先；不能仅比较高度，也不能一直等更高块

分支 a 的 T 被移出，分支 b 暂无 T
    → 撤销观察与暂态投影；未入账金额仍为 0，不产生账务冲正

T 后来进入 102b，logIndex 由 7 变成 4
    → 新分支观察；相同交易不代表原观察从未撤销

Outbox 已发送但 ACK 丢失
    → 重发同一消息；消费去重与业务效果同事务

RPC 返回空日志但未明确成功／服务商静默截断可疑
    → 不当成完整扫描；缩小范围、换源核验或暂停

账本已按 finalized 记账后发现检查点矛盾
    → 冻结受影响资金与发布；核验证据；账本授权追加冲正
    → 索引器不能删除历史分录或直接撤回外部付款
```

### 1.4 沿案例区分各阶段完成

| 阶段 | 链上／投影状态 | 平台可用充值额 | “完成”的准确含义 |
|---|---|---|---|
| 检查点 100 | A=100、B=0 USDC | 0 | 基线已核验，不代表未来交易 |
| 101a 执行成功 | 链上分支 a：A=75、B=25 | 0 | 交易在当前分支成功，尚非业务最终入账 |
| 101a 完整应用 | 投影 A=75、B=25，带 H101a | 0 | 索引内部状态已原子提交 |
| head=103a，F=100 | 按本文口径为 3 确认 | 0 | 展示风险降低，不升级为 finalized |
| 无重组，F 覆盖 101a | 完整应用前缀内，发出 Finalized | 0 或 25 | 是否为 25 取决于账本消费是否提交 |
| 账本消费提交 | 事件证据与账务业务身份对应 | 25 | 平台充值业务完成，可用与链上观察仍是不同账 |

**重组变体单独推演：** 共同祖先为 100，101b 不含 T，回退后转账视图 A=100、B=0；T 在 102b 重入且日志位置为 4 后，视图再次 A=75、B=25。等 `(102,H102b)` 被接受为 finalized 且前缀完整，账本才入账一次 25。该变体不与“101a 已 finalized”同时成立。

## 二、核心板块

| 板块 | 决定什么、为什么核心 | 拥有的状态 | 上下游契约 |
|---|---|---|---|
| 链观察与完整扫描 | 决定是否遗漏块、遗漏日志 | 原始头／日志、扫描完成证据 | RPC 的订阅只是提示；完整性依赖成功扫描与节点信任 |
| 分支与最终性管理 | 决定当前采用哪条链、何时认可最终性 | canonical 映射、tip、接受的检查点、模式 | 不让 RPC 单次回复直接决定业务终态 |
| 原子投影与恢复 | 决定崩溃后是否重复或跳过状态变化 | 投影、undo、applied 游标 | 一个完整块的处理结果同事务生效 |
| 业务证据解释 | 决定某日志能否成为充值或履约证据 | ABI／资产策略版本、归属与验证状态 | 通用日志不能自动替代领域业务成功 |
| 可靠发布与账务边界 | 决定撤销、确认是否被下游正确理解 | revision、Outbox／Inbox、消费进度 | 观察可撤销；账务由账本以独立事务确认 |

## 三、核心 20%

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 高度、哈希与父链接 | 发现／校验分支 | 高度不是区块身份 | 同高度替换被忽略 | 同高换头、低头、祖先证明 |
| 订阅提示＋连续补扫 | 获取数据 | 网络通知不可靠 | 断线永久漏充值 | 空块、范围拆分、已完成而非最大完成游标 |
| 分支观察与业务身份分离 | 解析与去重 | 重组改变日志位置 | 误去重或重复入账 | blockHash／txHash／logIndex／业务键 |
| 单块原子提交 | 应用 | 防止游标越过未生效数据 | 跳块、重复扣加 | 投影、undo、Outbox、游标共同事务 |
| 最终性门槛与前缀完整性 | 业务确认 | 最终性不是等待时长 | 提前形成不可逆付款 | safe、finalized、确认数、策略版本 |
| 逆序 undo／正序 replay | 重组恢复 | 状态不是消息集合 | 错余额、混合分支 | 共同祖先、恢复任务、崩溃续作 |
| 有序修订与消费事务 | 交付 | 数据库提交不等于下游生效 | 迟到消息复活旧结果 | 持久 revision、缺口、幂等边界 |
| 故障隔离与同水位核验 | 恢复验收 | 假恢复比停机危险 | 以新空账掩盖义务 | finalized 冲突、快照、精确截止 hash |

核心 20% 按正确性影响选择，不按篇幅机械截取；下文仍覆盖采集、应用、确认、恢复、交付与运行约束的完整闭环。

## 四、设计与规则

### 4.1 业务规则与不变量

1. **链身份固定：** `(chainId,genesisHash)` 与允许合约配置绑定；只检查 `chainId` 不能排除误连测试分叉。
2. **规范映射唯一：** 对每个已采用高度至多一个 canonical hash。完整模式下 applied 是从基线起父链接接续、逐块成功的前缀，不是已完成任务的最大高度。
3. **观察身份：** `observationKey=(chainId,blockHash,txHash,logIndex)`。`logIndex` 是区块级位置；同一 T 重入新块时观察键变化。原始日志保留，撤销不删除证据。
4. **业务幂等不是通用公式：** 若协议事件含稳定 `depositId/orderId`，需按协议定义作用域并验证。主例仅有一条相关 Transfer，教学充值意图 D 通过链、C、T 与经核验的收款／金额关联；生产多日志交易必须另有匹配规则或交易内事件标识，不能普遍以 T 代表一笔充值。不把区块级 logIndex 当跨重组业务键。
5. **单块原子性：** 日志校验、分支记录、投影变化、undo、Outbox、applied 游标在同一数据库事务中提交；空块提交完整性与游标。已持久的原始候选数据不等于已应用。
6. **前缀水位：** `finalizedPublishedHeight <= min(appliedHeight,acceptedFinalizedHeight)`，且必须核验祖先关系；高度不等式只是必要条件。充值判定分为 eligible、明确 rejected 与 pending：发布游标不能越过本作用域中首个 pending 所在块，即使独立转账视图和链最终性已更高。资格核验持久化后重新触发扫描，从原游标补发；不需要等待新块。finalized 发布游标及 Outbox 同事务；隔离业务有独立水位，不借其他范围进度越过缺口。
7. **重组界限：** 共同祖先不得低于已接受 finalized 检查点；任何与该检查点矛盾的候选都先停机核验，不自动 undo 已认可最终前缀。
8. **两类序号：** `chainEpoch` 标识分支切换，`writerTerm` 隔离旧主；`revision` 是持久、严格递增的发布流序号，回滚也不倒退。事务回滚不消耗已提交 revision；本文串行 writer 用事务内计数器，不直接用可能留洞的 SQL sequence 充当连续流位置。
9. **金额精确：** 原始金额使用 uint256 语义及足够精度的整数存储；Go 用 `big.Int` 或等价边界类型，不用 float64。主例仅有这笔正常转账，因此 A+B 始终为 100 USDC；铸造、销毁、重基准代币另改规则，不能套该守恒式。
10. **暂态与禁止结果：** 允许查询落后、确认未消费、重组期间暂不可用；禁止声明完整却跳块、混用不同 hash 的快照、撤销后旧消息重新生效、finalized 前增加可提现充值。

### 4.2 架构与职责

```text
Ethereum 执行／共识节点〔链执行与共识权威〕
        ↓ RPC：头／日志／回执／safe、finalized
Go 抓取池〔有界并行；只产出带 hash 的候选块〕
        ↓ 连续父链校验、当前 writerTerm 与 chainEpoch
单链 canonical writer〔唯一规范状态修改者〕
        ↓ PostgreSQL 原子事务
原始证据／canonical 区块／转账投影／undo／游标／Outbox
        ├─ 查询：状态＋来源块＋完整水位＋恢复模式
        └─ 发布器：持久 revision 顺序、至少一次传输
                    ↓
领域消费者 Inbox〔自身事务去重与更新〕
        ├─ 查询服务：可撤销的 included 视图
        └─ 账本：仅符合政策的 Finalized 充值入账
```

### 4.3 最小数据与交互契约

| 对象 | 必要字段与含义 |
|---|---|
| chain_state | chainId、genesisHash、writerTerm、chainEpoch、mode、applied 高度及 hash、接受的 finalized 高度及 hash、finalized 发布游标、revision |
| blocks | hash、height、parentHash、canonical、scanComplete、filterVersion、payloadDigest；唯一约束限制每高度 canonical 身份 |
| raw_logs | observationKey、address、topics、data、transactionIndex、logIndex、RPC 来源与观察时间；规范状态从区块映射解释 |
| decoded_events | observationKey、decoderVersion、assetPolicyVersion、from／to／amount、业务验证状态；未知解析不假装成功 |
| projection_changes | blockHash、应用顺序、前值／增量、schemaVersion；组成可逆 undo，回放不得读取当前时间等不确定输入 |
| recovery_job | 旧 tip、目标 tip、共同祖先、阶段、下一处理块、chainEpoch、错误与核验结果 |
| outbox | messageId、chainId、revision、chainEpoch、kind、observationKey／业务关联、源块及完整水位、策略版本；发送状态不等于消费成功 |
| consumer_inbox | 消费者、messageId、已应用 revision／待处理状态；与消费者业务修改同事务 |

消息类型至少区分 `Observed`、`Reverted`、`Finalized` 与恢复边界／快照。消息引用的 blockHash 与原始证据必须可查；“看到”和“撤销”不是同一消息重发。查询跨多块恢复时返回 `recovering`，不伪装为完整旧版或新版。

### 4.4 实现选择与可替代范围

- 以块为最小完整性提交单元，减少日志与游标错位；大块需要候选落盘或分阶段准备，但只有完整块才激活 applied。
- `eth_getLogs` 优先绑定单块 `blockHash`，不能同时带 fromBlock／toBlock；若服务商不支持，前后重读头与小范围查询不能独立证明完整性，必须另以目标 hash 的完整交易／回执集合等绑定来源核验，空结果也不例外；材料不足就换源或暂停。
- 普通可逆转账视图可以 undo；复杂投影允许从固定检查点重建，不能对任意状态机械执行“减回去”。
- 保留有限 undo 窗口及可验证快照。超窗口的未最终重组切换为离线重建；与已接受最终检查点冲突另走事故处置。
- 不依赖 Redis 锁或某个 MQ 的“恰好一次”替代数据库围栏、业务去重与状态版本。

## 七、工程实践：唯一简洁 MVP

### 7.1 目标与范围

手工验证一个小闭环：**以完整块输入，重复不重复应用；父链不符不前进；一块事务更新投影、undo、游标与 Outbox；显式逆序撤销当前未最终 tip 后可正序重放；只有 finalized 完整前缀能生成充值确认，pending 资格不可跳过。** 输入视为已由可信节点按 hash 完整获取并通过 ABI 校验；充值资格明确标记为 eligible、rejected 或 pending，主例为 eligible。简化为单进程串行、单条正常 Transfer。

不实现 RPC、签名、真实数据库、任期切换、自动祖先发现与重组调度、账本或可运行 Go 工程。撤销由手工输入 UndoTip 指定，undo 前值在应用时记录；生产恢复任务见母题 08，不用黑盒函数假装完成。

### 7.2 核心伪代码

```text
输入：Block(height,hash,parentHash,complete,events)、UndoTip(hash)、Finality(height,hash)、Verify、Tick
持久状态：tip=(100,H100)，balances={A:100000000,B:0}，blocks，undo
          finalized=(100,H100)，published=100，revision=0，outbox=[]，pending=[]，mode=healthy
所有入口：若 mode=halted，只留事故证据并返回；解冻必须另走授权恢复，不由普通输入触发

应用块 b：
  若 !b.complete：返回“等待完整块”
  若该 hash 已存且完整载荷摘要不同：事务置 mode=halted 并留证据；返回
  若 blocks[b.hash] 已 canonical 且 complete：返回“已应用”
  若 b.height != tip.height+1 或 b.parentHash != tip.hash：返回“需要分支核验”
  开始事务：
    再检查 mode=healthy、tip 与预期一致；不满足则回滚
    undo[b.hash] = []；保存该块完整事件及原始载荷摘要
    对 b.events 按 (transactionIndex,logIndex) 排序：
      要求 amount >= 0，from != to，余额及 uint256 边界合法
      记录 undo[b.hash] 中 from/to 的前值〔每条按应用顺序保存〕
      balances[from] -= amount；balances[to] += amount
      revision += 1；outbox 加入 Observed(revision,b.hash,event)
    更新 blocks[b.hash] 的高度／父hash／canonical=true／complete=true，保留事件与摘要
    tip = (b.height,b.hash)；提交事务〔空块也提交〕；随后执行 Tick

撤销当前块 UndoTip(expectedHash)：
  若 expectedHash != tip.hash：返回“不是当前tip”，不修改状态
  若 tip.height <= finalized.height：事务置 mode=halted 并留证据；返回
  开始事务：
    再检查 mode、tip/hash 与最终边界；读取该块及 undo
    逆序恢复 undo 中各 from/to 前值
    对该块事件：revision += 1；outbox 加入 Reverted(revision,旧观察)
    标记该块非 canonical；tip = (块高-1,块.parentHash)；提交事务

接收最终性 f：事务保存到 pending〔同高异hash不能互相覆盖〕；随后执行 Tick
资格更新 Verify(源观察,status)：事务记录核验依据与 eligible/rejected 判定；随后执行 Tick
Tick〔每次应用后、周期触发及重启后均执行，超前候选不能被遗忘〕：
  ready = pending 中高度不超过 tip 的所有候选，加上旧 finalized〔无新候选也复查业务屏障〕
  沿已存 canonical parentHash 核对 ready 中每个候选及旧 finalized 的祖先关系
  若任一矛盾：事务置 mode=halted 并保存冲突证据；返回，不改变 accepted finalized
  f = ready 与旧 finalized 中最高的兼容检查点〔兼容但落后不倒退〕
  开始事务：
    再检查 mode=healthy、canonical 链未变；finalized = f
    target = f.height；若 (published,target] 有资格 pending，则 target=首个待核验块高-1
    对 (published,target] 内完整块的每条 eligible 充值事件：
      revision += 1；outbox 加入 Finalized(revision,源块hash,事件业务关联)
    published = target；移除已核验 ready 候选；提交事务
输出：带 mode、tip/hash 的投影与可重投 Outbox；halted 时停止普通发布，资金门禁见 13
```

金额检查只是这个受控例子的前置约束，不是通用索引器拒绝真实链历史的理由。对于 from=to、铸造、销毁或快照缺口，应按配置语义处理；不得据此把完整规范链“修正”为自己猜测的余额。

### 7.3 输入与预期结果

| 输入 | 手工推演的预期结果 |
|---|---|
| 完整 101a，T 转 25000000 | A=75000000、B=25000000，tip=101a，1 条 Observed，尚无 Finalized |
| 重复输入同一完整 101a | 金额与 Outbox 不变，返回已应用 |
| 完整空块 102a、103a | tip=103a；余额不变；F 仍为 100，平台可用充值仍为 0 |
| 单独变体：101a 尚未应用就输入 102a | 父链／高度不接续，不推进 tip，不增加余额 |
| 单独变体：101a 获取不完整 | 不产生投影、undo 或应用游标；不能把空部分结果当完整块 |
| 正常路径 F 推进至已完整应用的 102a | 为 101a 的合格充值产生 1 条 Finalized；再次提交相同 F 不重复产生；账本仍须自行消费 |
| 单独变体：F=100、tip=103a，先收到 101b | 返回分支核验；手工依次 UndoTip(103a／102a／101a)，回到 A=100、B=0；空块不造撤销事件，101a 产生 1 条 Reverted；重复撤 101a 不再扣加 |
| 接上个变体：依次应用空 101b、含 T 的 102b、空 103b，再给 F=102b | 投影再次为 A=75、B=25，源观察改为 H102b／T／4；产生新 Observed 和 1 条合格 Finalized，不复用旧分支确认 |
| 单独变体：已接受 F=102a，又获矛盾 H102b | 持久置 halted；重启及随后正确 F 都不自动解冻，不再应用、撤销或发布普通确认 |
| 单独变体：tip=103a、F=100，先给矛盾 F=(100,H100b)，再给 F=102a | 首次即持久熔断，后一次不得为 T 生成 Finalized；与仅返回“熔断”字符串不同 |
| 单独变体：tip=100，先给 F=102a，再应用完整 101a／102a／103a | 候选持久保存；应用触发 Tick，至 102a 时重新核验并产生 1 条 Finalized；不要求外部重发 F |
| 单独变体：101a 的 D 为 pending、tip=103a，F 推至 102a；稍后 Verify 判 eligible | accepted finalized 可到 102a，published 先停 100；资格更新触发 Tick，才补发 T 的 1 条 Finalized 并推进 published，无需新块 |

以上是伪代码与手工预期，不是工程测试、合约审计或链上实验结果。
