## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| C / T / 25000000 | USDC 合约、主例交易、原始整数金额。 | 6 位精度对应 25 USDC，并发不能把同一金额改写或重复应用。 |
| RPC / worker / goroutine | 节点接口、抓取任务执行者、Go 并发执行单元。 | 可并行取日志和做纯校验，worker 不能直接改规范余额。 |
| canonical writer / applied | 规范状态唯一写入者，以及连续完整应用位置。 | 103 先完成也要等 101、102，不能按最大完成任务号前进。 |
| 候选 / blockHash / parentHash | 准备好的输入、具体块身份、其父块身份。 | 重排既认高度又认 hash，提交还要接续当前 tip。 |
| W / 在途窗口 | applied 之后允许准备但尚未提交的最多块数。 | W 是配置不是固定答案，任务返回后仍占名额，提交或淘汰才释放。 |
| 背压 / 重排缓冲 | 下游慢时限制上游，以及暂存乱序完成结果。 | 最早块卡住时不继续制造无界结果，也不能堵死共享结果通道。 |
| 字节预算 / JSON 放大 | 限制实际内存用量，以及解析后对象比压缩响应更大的开销。 | 块数有界仍可被热点块撑爆，响应、解码和复制都计入预算。 |
| 最早缺口预留 / 候选暂存 | 为阻塞前缀的块留资源，以及受配额管理的磁盘准备区。 | 后续块不能占光额度让 101 永远拿不到资源，暂存不等于已应用。 |
| eth_getLogs / 完整回执集合 | 日志接口，以及块内全部交易回执。 | 不能假定日志查询有通用分页，超限不能截断后当完整。 |
| big.Int / uint256 / float64 | Go 大整数、链上金额边界、浮点数类型。 | 精确存 25 USDC，不缩成 int64 或浮点数，解码后核验范围。 |
| channel / 浅拷贝 / 对象池 | 并发传递通道、共享底层存储的复制、复用对象的机制。 | 发指针不自动转移独占权，发完就归还对象池可能改坏尚未读取的金额。 |
| Set / Sub / Add / undo | 大整数独立赋值、减、加，以及撤销前值。 | 用 Set 独立复制证据和前值，Sub、Add 修改 writer 自己的余额对象。 |
| chainEpoch / writerTerm | 分支代次与写入任期。 | 重组淘汰旧分支任务，任期隔离旧主，两者提交时都要复核。 |
| context / Commit 未知 | 任务取消信号，以及提交回执没确定。 | 取消减少浪费，不能证明数据库没提交；恢复查持久事实。 |
| ABI / transactionIndex / logIndex | 事件编码约定、块内交易位置、块内日志位置。 | 解码可并行，最后仍按确定执行顺序生成投影和 undo。 |
| Outbox / Finalized / 账本积压 | 待交付记录、合格最终确认、下游尚未完成的工作。 | 积压可以降速和停回填，不能把未最终的 25 提前变可提现。 |
| WAL / GC / 阶段测量 | 数据库预写日志、Go 垃圾回收、逐环节定位耗时。 | writer 的 WAL 或锁已是瓶颈时，加 worker 只会增加等待和内存。 |

## 把整篇文章压缩成一个故事

**起因：** 三个 worker 同时准备 101a、102a、103a，含 25 USDC 转账的 101a 最慢，后两个空块先返回。协调者可以先收下后续结果，但 writer 仍从 100/H100 等待 101a；速度不能靠把 applied 偷改成 103 来体现。

**处理与异常：** 未提交窗口和总字节一起限额，并给最早缺口预留额度，防止后续结果占满资源，反过来让 101 无法完成。worker 交出的 big.Int、topics、data 不得再被复用改写，否则日志里原来的 25000000 可能悄悄变成别的金额。此时若换到 b 分支，旧 101a 即使在 context 取消后完整返回，也须被 epoch 淘汰，提交事务再查任期、分支、模式和父 hash。

**结局与不能混淆的边界：** 当前分支取全后仍逐块原子提交，102、103 的空记录也不漏，T 只影响一次视图。验证优化要看最早缺口、堆内存、提交等待和交付滞后，而不只是 RPC 数量；瓶颈在 writer 时继续加并发可能更慢。本文是设计与验证方法，不给虚构吞吐结论，也不因追赶压力放松 finalized 与账本提交的资金门槛。

[返回专题总览](README.md)

**流程位置与核心机制：** 位于 RPC 抓取、候选重排到单块数据库提交之间。重点不是介绍 goroutine，而是让并发只加速数据准备，不破坏连续前缀、分支身份和资源上限；切主围栏的完整机制见第 12 题。

**必要前提：** 沿用总览的 Ethereum 主网、固定 USDC 合约 C、6 位精度，以及 T 向 B 转入 `25000000` 最小单位即 25 USDC 的案例。单链只有一个串行 canonical writer；区块记录、投影、undo、Outbox 和 applied 游标同事务提交。订阅只是唤醒提示，账本只有消费合格 Finalized 通知后才能入账，不能用提高并发或积压过大作为提前入账的理由。以下是设计推演，不是生产实测。

## 第 1 层：哪些工作可以并行，哪些不能？

**面试官：** Go 怎样并行抓取又不乱序写状态？如果 103 先返回、101 还没有返回，谁先写？

**面试者：** 我会把“准备候选数据”和“裁决规范状态”分开。调度器先取得带父链接的目标区块头，给 worker 分配包含链身份、高度、预期 blockHash、chainEpoch 和过滤版本的任务。worker 并行读取日志、校验字段和解码，只返回不可变候选，不直接更新余额、canonical 标志或应用游标。

writer 从数据库的 `(100,H100)` 出发，只接收当前分支预期的 101，再检查 102 的父哈希，最后处理 103。103 先完成就等待，绝不能把最大完成高度 103 当成 applied=103。101a 的 25 USDC 和它的 undo、Observed、游标必须同事务生效；102a、103a 即使没有日志，也要证明扫描成功并提交空块记录。

因此，并行的是网络与纯计算，串行的是链内规范状态迁移。同一高度可能存在多个哈希，重排不能只用高度覆盖结果，还要匹配当前任务指定的哈希与 epoch。

## 第 2 层：等待最慢块时，重排区会不会无限长？

**面试官：** 你让 103 等 101，但若 101 一直超时，后面几万块都抓完了，内存不还是会耗尽？

**面试者：** 所以 worker 数有界还不够，整个未提交窗口都要有界。我会把可调度范围限制在连续 applied 之后最多 W 个块，并限制在途请求数、待重试任务数、已完成重排项数。这里的 W 是容量配置，不是宣称某个固定值适合所有服务。

一个任务从分配开始占窗口名额，直到被提交、淘汰或显式终止才释放；请求返回不代表名额释放，否则调度器仍会源源不断地制造重排结果。缺口 101 未补齐时，窗口不能继续向前滑动。重试使用有限预算、退避和换源策略，仍失败就保留落后状态并告警，而不是跳块。

重排协调者应持续接收并登记乱序结果，不能只阻塞等待 101 的专用通道，导致 101 worker 也因共享结果通道满而无法交付。出错任务也必须有终结结果和资源归还路径；不能每次重试再启动一个无人回收的 goroutine。

## 第 3 层：块数有界，为什么还需要字节背压？

**面试官：** W 已经限制住了块数，为什么还可能内存爆炸？如果最前面的 101 恰好是超大日志块怎么办？

**面试者：** 块大小不均匀，十个热点块可能比一千个空块占用更多内存。还要限制响应体、解压与解码后的对象、重排结果和批量写入缓冲的累计字节。请求阶段预留保守预算，读取过程中限制实际字节，超限必须报“未完整获取”，不能把截断结果当成功。JSON 解码和多份复制会放大占用，预算不能只按 HTTP 压缩字节估算。

同时要避免背压死锁：后续块如果吃完字节额度，最早缺口就可能拿不到获取或解码额度，writer 又无法释放后续结果。我会为最早缺口预留资源，限制后续块占用，必要时淘汰可重抓的远端候选，或将已核验候选转为受配额控制的数据库暂存。

单块大于常规内存预算时，可以流式准备候选，或按可证明完整覆盖的过滤子集、完整回执集合获取；不能假设 getLogs 存在通用分页。暂存清单记录 hash、分片范围、摘要和完整性状态，全部成功后才交给 writer。暂存不等于应用，磁盘、暂存行数与清理也必须有上限。无法完整获取就暂停该块，不拆成几个“已应用半块”。

## 第 4 层：队列传了指针，金额是否仍然可信？

**面试官：** 你说候选不可变，但 Go 的 `big.Int`、切片和复用缓冲都可能共享底层数据。worker 把金额发出去后继续解码，会发生什么？

**面试者：** channel 只交付值或指针，不自动转移可变对象的独占权。`big.Int` 的运算通常修改接收者，结构体浅拷贝也不等于独立复制其内部整数存储。如果 worker 重用金额对象，writer 可能把后续事件的数值当成 T 的 25 USDC；如果 writer 对事件的 Amount 直接做减法，还会破坏证据或重试输入。

我会规定清晰的所有权：候选完成后交付给下游，发送方不得再改它；需要共享或复用时，用 `new(big.Int).Set(src)` 创建独立整数，日志的 topics、data 和其他可变切片也按生命周期复制。对象池只回收已经没有读者的对象，不能在发送成功后马上 Put 回池。

writer 用自己的余额对象做 `Sub`、`Add`，事件 amount 作为只读操作数，undo 的前值也要独立保存。解码后检查非负和 uint256 上界，存储不能截成 int64，更不能转 float64。并发安全不只是“没有 map 同时写”，还包括同一笔金额在交付、重试和撤销时保持同一个值。

## 第 5 层：分支变了，旧 worker 怎样失去资格？

**面试官：** 所有权解决了对象被改的问题，但 101a 抓取期间检测到 101b，旧结果晚到仍然很完整，为什么不能被 writer 接受？

**面试者：** 完整性只证明“这一候选按某规则抓取成功”，不证明它仍属于当前恢复分支。我会让分支切换由串行控制路径持久化：在锁定 chain_state 的事务里记录恢复模式、提高 chainEpoch，并保存恢复任务。所有任务和候选都带创建时的 epoch。协调者先淘汰旧 epoch，writer 在真正提交前仍要再次检查。

最后检查不能只放在 Go 内存里。应用事务锁定同一 chain_state 行，核对当前 writerTerm、chainEpoch、mode、预期 applied hash 和父哈希；任何不匹配都回滚。这样分支切换和应用块有确定顺序：旧块事务若先提交，就属于切换前的持久旧 tip，由恢复任务纳入 undo；切换事务若先提交，旧候选就不能再进入规范投影。

旧任务结果可以按来源保留为分支证据，但不能推进 canonical 游标，也不能产生新的规范状态消息。`chainEpoch` 是分支代际，不是主备任期；即使没有切主，重组也需要淘汰旧分支任务。

## 第 6 层：取消任务能不能撤销数据库结果？

**面试官：** 既然切换时取消旧 context，为什么还要在数据库里检查 epoch？取消之后，那笔正在提交的事务不就自动没了吗？

**面试者：** 不能这样推断。context 取消是停止请求的信号，不是跨网络撤回已经完成写入的协议。数据库驱动可能取消语句或回滚尚未提交的事务，但取消与 Commit、网络断开存在竞争：客户端收到超时，并不能证明服务端没有提交。取消后应显式清理事务，却不能据此删除“刚才可能写入”的余额或消息。

恢复时要在有权威性的数据库连接上查询该块的提交事实，核对 blockHash、完整状态、载荷摘要以及 applied／Outbox 的原子结果。同一完整块已经提交就返回已应用；未提交才按当前 epoch 和任期重试；身份相同而内容矛盾则停下来调查，不能靠重复 INSERT 把差异吞掉。若提交后又发生重组，还要结合 canonical 状态与恢复任务解释，不能只看原始块是否存在。

在 Go 生命周期上，RPC、队列收发和等待都响应取消，worker 退出前释放名额与字节预算；结果通道由明确的拥有者在所有发送者结束后关闭。取消负责减少浪费，数据库围栏与原子事实才负责正确性。

## 第 7 层：串行 writer 遇到热点块，怎样提速？

**面试官：** 现在 101a 是一个日志很多、账户高度集中的热点块，writer 成了瓶颈。能不能开多个 goroutine 同时修改账户，或每处理一批就提交？

**面试者：** 不能为了吞吐偷换原子单元。同一账户在块内可能连续收付，undo 与发布次序也依赖确定顺序。基线仍然以 `(transactionIndex,logIndex)` 整理事件，由单个 writer 决定状态变化。可以并行做不依赖余额的 ABI 解码、静态校验和摘要计算，最后按原顺序合并；不能并行读旧余额后各自覆盖写回。

数据库层可以在一个块事务内批量插入原始日志、undo 和 Outbox，合并同一账户的可验证增量，减少往返，但必须保留审计和恢复所需的事件顺序及前值语义。大块的候选准备可以分阶段落盘，最终激活仍必须原子包含该块全部状态和游标。若做不到，就承认该块带来的延迟，不能把 applied 提前。

控制路径还要能及时进入恢复或熔断，不能排在无界回填队列之后。历史回填使用独立的有界资源预算，不争夺全部连接。Outbox 或账本消费积压时适当降低采集速度、停止非必要回填，展示真实水位；既不丢确认义务，也不把未 finalized 的 25 USDC 变成可提现余额。

## 第 8 层：如何证明优化有效而不是只增加并发？

**面试官：** 你保留了串行提交和背压，怎么知道究竟该调 worker、W、批量大小，还是数据库？怎样验证没有用性能换正确性？

**面试者：** 我会先拆阶段测量：RPC 排队、远端响应、字节与日志数、解码耗时、等待最早缺口的时间、数据库锁等待和提交时间、Outbox 最老未完成消息年龄，再结合 Go 分配量、堆占用、GC 和 goroutine 阻塞位置判断瓶颈。端到端还要看 head 到 applied、accepted finalized 到完整发布、发布到账本消费的滞后，不能只报 RPC 请求数。

容量验证要覆盖空块、热点块、最早块慢而后续块快、限流、重组中旧任务返回、数据库提交超时等负载。分别观察条目数和字节是否受控，确认游标没有跳过缺口、旧 epoch 不生效、重试不重复加 25、热点块不出现半块可见。延迟分位数和资源上限都应来自实际测量与业务目标，本文不编造每秒处理量或“调到多少 worker 最佳”。

若瓶颈是 writer 的 WAL 或锁等待，继续增加 worker 只会增大重排和内存。有效优化是让完成同一正确结果的等待和资源成本降低，而不是让系统更快地产生不完整进度。

## 收束：机制、易错边界与反例

- **讲透的机制：** 有界并行准备、按 hash 重排、窗口与字节双重背压、可变对象所有权，以及提交时的 epoch／任期／父链校验，共同保护连续应用前缀。
- **最容易答错：** channel 有容量不代表全链路有界；context 取消不等于事务撤销；浅拷贝 `big.Int` 不等于独立金额；热点块不能靠提前提交游标解决。
- **检验反例：** 101a 请求最慢，102a、103a 先占满重排区；此时切换到分支 b，旧 101a 又在取消后返回。方案应能为最早缺口释放或预留资源，淘汰旧 epoch，且不能出现 A 被多扣 25、B 被多加 25，或 applied 跳到 103 的结果。
