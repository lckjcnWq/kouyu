# 大问题 4：部分成交和撤单怎样形成唯一且耐久的义务？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 撮合裁决 / 可靠日志 | 按可恢复的顺序决定谁成交、谁取消，并耐久保存。 | 只有达到约定复制确认位置才承诺，不凭协程抢锁或 API 返回先后定结果。 |
| A / B / V / T1 | 买方、卖方、金库和贯穿成交。 | 双方各下 1 WETH 单并已最终建锁；T1 为 0.4 WETH、800 USDC 货款加 0.8 买费。 |
| WETH / USDC / Gas | 封装 ETH 式基础资产、报价资产和链上执行成本。 | 两币分别为 18、6 位小数；Gas 由中继原生币另付，不能混入订单数量。 |
| maker / 轮次预算 | 先到挂单方和本轮最多匹配的基础数量。 | B 按 2,000 限价成交；预算 0.4 后暂停，才有主例的 0.6 余量。 |
| Q / open / pending | 总数量、未成交量和已成交待交割量。 | T1 同提交让双方 open 各减 0.4、pending 各加 0.4，V 锁资还没扣。 |
| settled / cancelled / defaulted | 已交割、未成交取消和违约未交割量。 | Q 等于五类之和，不能把同一数量同时算取消和成交。 |
| COMMITTED / UNKNOWN / attempt | 已提交义务、结果未知及一次链上尝试。 | 尝试超时或失败不删除义务，不把 pending 回填 open。 |
| requestKey / payloadHash / resultRef | 请求键、载荷摘要和原结果引用。 | 超时按原请求查询，同键异载荷拒绝；客户端没收到不等于没提交。 |
| tradeId / H / commitSeq / matchIndex | 成交身份、哈希、提交位置和一次命令内的匹配编号。 | 身份由不复用日志位置等生成，恢复后仍是同一个 T1。 |
| orderHash / fillSeq / nextFillSeq | 订单摘要、本笔每订单序号和合约期待序号。 | T1 双方为 1；下一对手的序号可以不同，不能用交易 nonce 替代。 |
| epoch / 围栏 | 主备任期和阻断旧主继续执行的机制。 | 用于权限与审计，不应把任期加入新成交身份来替换 T1。 |
| Outbox / Inbox / 消费位点 | 待发记录、消费去重记录和已处理消息位置。 | 业务结果与交付事实共同保存，不能先推进位点再异步落义务。 |
| executed / 幂等 / txHash | 链上执行标记、重试不增效果和交易哈希。 | 本地去重不够，换哈希或换批仍须由 V 保护同一成交。 |
| 跨批前驱 / 整批原子 | 另一批中必须先完成的成交，以及本批共同成败。 | 共享订单前驱未最终，后继须同批有序或等待；链下提交后序义务与允许外发不是一回事。 |
| receipt.status / revert / Gas | 回执执行结果、回滚和执行成本。 | status=0 回滚本批金库变化，但中继交易序号和 Gas 可能已消耗。 |
| INCLUDED / blockHash / revision | 暂时入块、分支区块身份和对外修订号。 | 重组撤回观察并发新修订，原成交日志与撤余量决定不撤销。 |
| D / SETTLED_FINAL / DEFAULTED_UNSETTLED / EXPIRED | 截止、最终交割、最终未交割违约与余量过期原因。 | 最终越过 D 且历史完整后核销 pending；未成交 open 过期另归 cancelled。 |
| closeLock / expectedFilledBase / expireUnlock | 正常关锁、预期累计量和到期解锁。 | pending 因违约归零不等于全部交割；正常关闭不能只看 open、pending 为零。 |

## 把整篇文章压缩成一个故事

A、B 各有 1 WETH 数量的订单，资金已在 V 最终锁住。本轮预算 0.4 WETH，B 先到，撮合日志按 2,000 形成 T1，再暂停新增撮合。提交时必须一起保存双方 open=0.6、pending=0.4，货款 800 USDC、买费 0.8 USDC，双方序号 1，以及可恢复的交付事实。若只写成交表没减余量，同一份 0.4 就可能再次卖出；若只减余量没存义务，崩溃后数量就无处可查。

分别从初始状态看撤单竞争：撤单先提交，则该订单 1 全取消，后来的候选不能再形成 T1；T1 先提交，则随后撤单最多撤该方 0.6，不能吞掉 pending，也不会替对方撤单。若 T1 已可靠提交但回报前崩溃，恢复应重放原结果、补发原交付，而非按新行情再撮合。另一个明确恢复撮合的变体中，后续成交要取连续 fillSeq，不能因链上 nextFillSeq 仍是 1 就复用 1；跨批外发还要等待共享前驱最终交割。

撤余量成功后，订单可以是 open=0、pending=0.4、cancelled=0.6，资金却仍锁在 V。超时、回滚或重组都不把那 0.4 改成可再成交；最终证据经原日志只裁决为 settled=0.4 或 defaulted=0.4 其中之一。正常关锁要求全部已提交义务最终交割，不能把违约清空 pending 也算履约；到期则走独立解锁并保留违约记录。这套顺序保障数量和承诺不丢不重，不等于已经进行并发故障实验。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题聚焦最终锁资准入之后的撮合裁决：用同一权威日志决定部分成交与撤单的先后，原子确定数量变化与成交义务，并把这个决定可靠交付给结算。沿用总览 T1：双方订单各 1 WETH，T1 成交 0.4 WETH、价格 2,000、名义金额 800 USDC、买费 0.8 USDC。故障变体分别从指定检查点开始，不把“先撤单”“提交后崩溃”“到期违约”叠在同一次正常交易上。

## 第 1 层：部分成交提交究竟共同确定哪些事实

**面试官：** 部分成交和撤单怎样形成唯一且耐久的义务？先讲 T1 撮合成功时，到底有哪些状态必须一起确定。

**面试者：** 撮合成功不是内存里找到两个价格可匹配的订单，而是一次可靠提交同时确定成交条款和双方数量变化。A、B 的链上专属锁资已最终完成，链下各有 `Q=1、open=1`。主例有教学单轮基础量预算 0.4 WETH，按价格时间顺序匹配该量后暂停该交易对新增撮合，结算和撤余量仍继续，关闭前不恢复。否则双方各 1 WETH 的交叉限价单会继续成交，不能自然只产生 0.4。按这个明确的轮次条件，先到的卖方 B 是 maker，确定 T1 为 0.4 WETH、价格 2,000，800 USDC 名义金额和固定买费规则对应的 0.8 USDC 不能在后续重试时重谈。

同一提交中，双方 `open -= 0.4、pending += 0.4`，保存 T1 的 `tradeId`、双方 `orderHash`、双方本次 `fillSeq=1`、数量、价格、maker 和费用版本，并留下可以恢复的交付事实。T1 已经是经济义务，但金库余额还没变：A 仍锁 2,012.01 USDC，B 仍锁 1 WETH。回报应当是“0.4 已成交、待结算，0.6 尚可成交”，不是“资金已到账”。

数量不变量是每个订单独立满足 `Q = open + pending + settled + cancelled + defaulted`。T1 提交后为 `1=0.6+0.4+0+0+0`。不能只写成交表而忘了减 open，否则同一 0.4 会再次参与撮合；也不能先把 open 减掉却没保存义务，否则崩溃后无法解释这部分数量去了哪里。

## 第 2 层：撤单与 T1 同时到达时，谁决定那 0.4 归谁

**面试官：** 你说一次提交把 0.4 从 open 转进 pending。若用户同时撤单，撮合线程和撤单线程分别读到 open=1，怎样防止一个成交 0.4、另一个又取消 1？

**面试者：** 两个线程不能各自对旧快照做最终决定。对同一订单有影响的 fill 与撤单，必须进入同一权威撮合命令序列，由一个可恢复的顺序裁决。本基线的单交易对订单簿按该序列执行状态机，不把网关收到请求的墙钟时间、两个 API 返回先后或两个协程抢到锁的顺序当成对外可恢复的业务顺序。

独立变体一从初始 open=1 开始：若撤单先被提交，该订单的 1 全部转为 cancelled，后续候选匹配必须重查 open，不能再提交依赖这笔订单的 T1。独立变体二也从初始状态开始：若 T1 先提交，则双方已有 pending=0.4，随后各自撤单最多取消其实际 open=0.6，不能把 T1 也撤回。只撤一方时，也只改变该方 open，不取消对手方的订单余量。

因此撤单指令是“取消裁决时仍然 open 的部分”，不是客户端预先宣称“退还原始数量 1 的资金”。结果要记录实际取消数量、裁决位置和当时累计成交状态。这样不论并发到达怎样，最终只会沿一条顺序更新数量，不会把同一份量同时计入 pending 和 cancelled。

## 第 3 层：所谓同一权威序列，怎样落到持久字段与原子边界

**面试官：** 你把竞争交给“同一权威序列”，但只给每个命令发一个递增号并不能防止半写。T1 和撤单各自需要在哪个耐久边界上确认？

**面试者：** 递增号只是定位，不能代替提交协议。在这个模型中，只有达到约定复制确认的日志位置，才能承诺命令结果已确定；未复制确认的单机写入不作为故障切换后的业务承诺。同一日志位置不能在切主后复用成另一份结果，接管必须覆盖已确认前缀。

T1 的提交单元共同包含命令引用、规则版本、买卖订单变化、确定的成交身份和全部条款，以及恢复交付所需的结果。`tradeId=H(venueId,logPartition,commitSeq,matchIndex)` 将成交定位到不可复用的已提交结果；同一个命令产生多笔匹配时，`matchIndex` 区分它们。请求层另外保存 `owner、requestKey、payloadHash、resultRef`，防止客户端把同一个幂等请求键换成另一种意图。

撤单的提交单元则包含原请求身份、目标订单、裁决时 open、实际取消量、更新后的数量分类和结果引用；它不直接改 V 的 available。若物化表由日志派生，必须能从已提交日志重建，不能把一张尚未更新的查询表当成更高权威。采用数据库事务保存本地结果时，订单数量、成交记录与本地交付记录也要共同提交。复制日志与物化数据库之间若不是同一个事务资源，就靠已提交日志重放衔接，不能声称两者天然原子。

## 第 4 层：提交后崩溃但尚未回报，如何恢复原结果而不是重新撮合

**面试官：** 你说查询表可以重建。现在 T1 已达到复制确认位置，但进程在更新查询表和投递结算前崩溃，用户又没收到回复。重启是重新撮合一次，还是按原结果继续？

**面试者：** 必须按原已提交结果继续，不能重新用当前订单簿撮合原请求。重启先定位快照覆盖的提交位置，再顺序恢复其后的已提交记录；恢复 T1 时使用原来的价格、数量、双方摘要与序号，使订单回到 open=0.6、pending=0.4，并恢复同一个 tradeId 的交付。规则版本也来自原记录，不能用重启后修改过的配置重新解释旧结果。

如果交付使用 Outbox，领域变化与本地 Outbox 共同提交，发布者重启后扫描未完成交付；如果结果日志本身足以确定性生成完整交付，则从该日志恢复未交付的范围。二者都要求“已提交结果必然能恢复出待交付事实”，不要求故障发生前一定已经发出消息。禁止先发一条不可撤回的成交消息，再回头碰运气写入尚未确认的日志。

用户超时后携原 `requestKey` 查询，返回原 `resultRef`，而不是把超时解释成未受理。反过来，如果故障前只有候选匹配或未提交日志，就不能宣称 T1 已存在；恢复后由权威提交状态决定是否继续处理原命令。崩溃窗口的关键是提交前后两类事实，而不是“客户端看没看见”。

## 第 5 层：恢复会重复交付，哪些身份必须保持不变

**面试官：** 你让重启继续投递原 T1，但可能消息已经送到、发布确认丢了。客户端也在重试请求。怎样区分“重放原结果”与“新建另一笔成交”？

**面试者：** 请求重试、结果重投递和链上交易重试是不同层次的重复，分别需要身份与载荷绑定。请求层按 owner 和 requestKey 找原结果，同键不同 payload 拒绝；领域层用原 tradeId 标识 T1，不能把一次重新投递的消息 ID 当成新成交 ID；结算层固定完整载荷的 payloadHash 与计划关联，不能因收到重复消息又分配一份新的经济义务。

结算消费者在一个本地事务中完成 Inbox 去重、义务记录或引用、计划绑定及后续 Outbox。相同 tradeId、相同条款的重复交付返回已有处理结果；相同身份但数量或价格不同是冲突，应停下核查来源，不能最后写入者覆盖。消费位点也不能先推进再异步保存义务，否则重启可能永久跳过一笔 T1。

本地去重还不是链上去重。换交易哈希、换批次甚至换发送尝试，都不能让 T1 重新有效；V 仍以 `executed[tradeId]=payloadHash` 保护执行效果。切主的 epoch 用于围栏和审计，不进入一个“替代 T1”的新经济身份。这样可以重复传递同一决定，同时不重复制造义务或资产变化，不过多笔不同成交之间还需要顺序约束。

## 第 6 层：不同成交都不重复时，为什么仍要每订单 fillSeq

**面试官：** 你解决了 T1 重复。现在独立变体回到 T1 提交后、尚未撤单的检查点，明确恢复该交易对撮合，在容量允许时让同一订单剩余 0.6 产生后续成交。后笔有自己的 tradeId，为什么不能和 T1 随意并行结算？

**面试者：** 因为唯一身份只区分“是不是同一笔”，不表达“哪笔必须先执行”。每个订单单独分配连续 fillSeq，T1 在 A、B 上都是 1；之后一笔涉及 A 的新成交在 A 上是 2，但其新对手订单可能是自己的 1。序号在成交提交时就绑定到相应义务，不能等广播时临时抢号，也不能用交易 nonce 替代，因为 nonce 只串行一个发送者，不串行所有受影响订单。

V 保存各订单 `nextFillSeq`，只有双方提供的本次序号都匹配才能执行新 fill，成功后共同推进。结算编排据此建立共享订单依赖：批内按可执行顺序排列；跨批采用保守策略，前驱已经最终交割后才发送后继。未最终的前驱与后继要么纳入同一批按序执行，要么先等待，不能以前驱刚广播或暂时入块作为跨批放行条件。不共享订单的成交才可能独立安排。默认整批原子，因此错误地把后笔放在前面，可能导致整个批次回滚，而不是自动跳过坏项。

链下还要分清“已分配到哪个成交序号”和“最终交割到哪个序号”。在这个恢复撮合的独立变体中，pending 仍占用原容量，但未被占用的 open 有足够锁资与时间窗口时，链下可以继续提交后序义务，不必把“跨批发送要等最终性”误写成“链下不能再成交”。T1 待结算时，不能因为链上 nextFillSeq 仍是 1，就把 1 再分配给另一笔成交。相同 T1 的链上重放先走执行去重，不再消耗序号；真正的新成交才接受下一序号检查。这个约束保证已提交义务的顺序不被异步交付和多发送者打乱。

## 第 7 层：有了有序义务，撤单为什么仍不能立即退还锁资

**面试官：** 你让已提交成交依序履行。现在另一个独立变体只保留 T1：它已提交但尚未结算，随后双方撤掉实际 open=0.6。既然以后不再产生新 fill，能否马上释放 0.6 对应的资金？

**面试者：** 不能。这个模型刻意把“停止新增匹配”和“释放链上锁资”分开，撤单只关闭撮合资格，不修改已提交成交和 V 的资产状态。此时双方数量为 `open=0、pending=0.4、cancelled=0.6`，V 仍是 A 锁 2,012.01 USDC、B 锁 1 WETH。撤单回报应明确“余量已撤，已有成交待结算，锁资未关闭”，不能只给一个让用户以为钱已退回的“撤单成功”。

也不能由链下按剩余数量自行造一个可用余额。T1 还要花掉 A 的 800.8 USDC 和 B 的 0.4 WETH；若把整单锁资先退给用户再重试 T1，就会破坏锁资支撑。即使理论上能算出部分闲置资金，本基线也不实现提前部分释放，避免在未知交易、累计费用和关闭竞争中额外引入一个释放协议。

正常路径是在 T1 最终交割后保留 A 的 1,211.21 USDC、B 的 0.6 WETH，随后等该订单全部已提交义务最终履行、最终投影对齐，再由授权出口关闭整个剩余锁。若存在上一层的后续成交，也要一并等待，不能只看到 T1 已完成就放行关闭。可见 fillSeq 保护顺序，撤单保护 open，二者都不等于资金释放授权。

## 第 8 层：撤单之后结算失败，为什么也不能回填 open 或复用序号

**面试官：** 按你上一答，撤单后 pending 仍然占资。如果 T1 广播超时，或者整批交易 revert，能否把这 0.4 改成取消或恢复 open，再给用户换一笔成交？

**面试者：** 不可以。COMMITTED 是经济义务的提交边界，不是某一次链上尝试的临时缓存。广播超时或查询无 receipt 记录为 UNKNOWN，因为原交易仍可能迟到执行；回填 open 会使同一 0.4 同时支持旧 T1 和新成交。把它改成 cancelled 也不成立，因为用户撤掉的是当时 open=0.6，不能追溯改变已被日志裁决的 0.4。

若 receipt 的 `status=0`，该批次的金库变更整体回滚，双方余额、累计量和执行标记没有留下一半；中继 nonce 与 Gas 成本则已经发生。要把失败写入 attempt，保持 T1 的数量、价格、身份和 fillSeq 不变，查明失败原因后再安排仍合法的履约尝试。不能因链上下一序号还没推进，就复用 T1 的序号给另一个新 tradeId。

这也解释了后笔为什么不能简单跳过前笔：前笔未执行时，后笔会被订单序号挡住。拆批可以隔离不共享依赖的坏单，但不能改写已经提交的经济条款或跳过有序义务。若现有授权、资金或时间条件已无法履约，需要走证据化退出，而不是靠一条“补偿事务”假装原成交从未发生。

## 第 9 层：何时才能把 pending 归入最终履约或违约

**面试官：** 你既不让失败回填 open，也不让后笔跳过。假如 T1 暂时入块后重组，最终又拖过 D，该怎样结束 pending，才不会把一笔成交同时记成成功和违约？

**面试者：** 要先把未最终观察与最终业务分类分开。T1 暂时入块只记 INCLUDED，保留 blockHash、交易和事件位置；双方在业务最终口径仍为 pending。未最终区块被重组掉，就撤销对应观察投影，回到待观察或待重交。原日志、tradeId 和撤单决定都不撤销，对外用新的 revision 表达观察修订。

主例双方采用同一 D，合约只在 `block.timestamp <= D` 执行 fill，本地时间过去并不证明截止前没有成功。只有最终规范前缀越过相关截止边界，且相关执行历史完整，才能确认截止前已经交割，或确实未交割且未来不能通过原 fill 履行。这里还依赖总览限定的规范后继区块时间戳严格递增与可查询最终性，不能把任意 EVM 链直接当成相同条件。

观察器只提交证据，不直接改订单。最终履约或违约证据以稳定身份命令携 tradeId、载荷依据、规范块及最终水位交回撮合状态所有者，经同一日志验证与去重后，才裁决双方 0.4 从 pending 转为 settled，或转为 defaulted 并标记 `DEFAULTED_UNSETTLED`。证据命令重投递不能重复扣 pending，不能与撤单线程各自读写数量。相同部分只能选择一种最终分类。

在这个撤余量变体中，正常结果是 `1=0+0+0.4+0.6+0`；违约结果则是 `1=0+0+0+0.6+0.4`。两者的经济含义不同，不能都写成“订单已撤销”。如果另一个独立变体没有提前撤余量，到期仍有 open=0.6，则由同一日志的过期裁决将这部分 open 转为 cancelled，记录 `reason=EXPIRED`；原 pending=0.4 仍逐笔核查 settled 或 defaulted，不能混进取消量，也不能把未成交的 0.6 算作违约。

到期 `expireUnlock` 只释放实际未花掉的锁资，不赔付对手方，也不免除原义务；后来另行追偿要追加独立记录，不能重写原违约历史。历史完整性与未来执行互斥共同成立，才能安全结束这一笔 pending 的分类。

## 第 10 层：pending 清空以后，怎样证明关闭条件成立而不越权

**面试官：** 你上一答说正常履约和到期违约都可能让 pending 清空。那关闭服务只查 `open=0、pending=0` 是否就够了？怎样防止它把违约清空和正常结算清空混在一起？

**面试者：** 不够，关闭条件必须核对数量去向、全部已提交义务与最终链证据，而不只是看两个计数为零。正常 `closeLock` 要求该订单没有 open，全部已提交成交义务已经最终交割，日志中已分配的成交与最终执行集合对应，最终链投影水位对齐；pending 因 defaulted 归零不满足“全部交割”。检查应绑定已确认的撤余量结果和对应日志前缀，不能读一张滞后的查询表就签出关闭交易。

正常主例中，T1 最终交割且双方 cancelled=0.6，授权出口才提交 `closeLock(orderHash,expectedFilledBase=0.4 WETH)`。V 核验当前角色、预期累计量和锁状态，关闭后不能再次执行新 fill 或重新建同摘要的锁；最终观察关闭后，A 有 4,199.2 USDC 可用、B 有 1.6 WETH 可用。若关闭广播未知，只记录待观察，不能在本地先释放资产权利。

合约不能从 expectedFilledBase 推出“日志再无未履行成交”。所以授权出口提前关闭仍是本基线的信任风险，不能用链上一个计数掩盖。到期违约路径则使用严格 `block.timestamp>D` 的独立解锁，记录真实返还与违约，不伪装成正常 closeLock 已履约。静态核验可以把 T1 的提交、撤单、交付、执行与最终观察串成一条证据链，同时验数量守恒和逐资产守恒；这说明设计希望满足什么，不等于已经做过并发故障实验或合约审计。

## 本题收束

- **机制：** 同一可恢复日志裁决 fill 与撤单；一次提交共同确定数量变化、成交身份、条款、双方 fillSeq 与交付事实。请求重试查询原结果，结果重投递不新建经济身份，链上尝试失败不删除成交义务。
- **边界：** 撤单只取消实际 open，pending 既不能回填 open，也不能随撤单释放。fillSeq 属于每个订单，不是全局成交序号或交易 nonce；正常 closeLock 要等所有成交最终交割，到期违约退出不能用同一条件伪装成正常履约。
- **验证：** 分别从初始 open=1 推演“撤单先提交”和“T1 先提交”，只应得到全部取消或 `pending=0.4、cancelled=0.6`，不能出现总量 1.4。再从 T1 已提交、余量已撤的检查点独立推演广播未知：旧交易迟到成功不得重复交割；若最终未履行并越过 D，则保留 defaulted=0.4。以上是静态顺序与反例推演，不是工程测试结果。
