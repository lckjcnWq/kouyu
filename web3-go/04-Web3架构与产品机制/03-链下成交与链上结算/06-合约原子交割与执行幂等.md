# 大问题 6：合约怎样保证双边原子交割和执行处幂等？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| V / EVM / 原子交割 | 金库、合约执行环境和相关变化共同成功或回滚。 | T1 的双方锁资、可用权利、费用、累计量和执行标记必须在同一事务内更新。 |
| A / B / WETH / USDC | 买卖双方及基础、报价资产。 | A 付 800.8 USDC 锁资，B 付 0.4 WETH 锁资；不是从双方钱包临时拉款。 |
| available / locked | 可用资产权利与订单专属锁资。 | 结算只在金库内部搬权利，提到外部钱包属于另一接口。 |
| 当前结算角色 | 合约允许发送交割指令的受限身份。 | 连重复调用也先验角色；tradeId 不意味着任何人可创造合法成交。 |
| tradeId / payloadHash / executed | 成交身份、完整载荷摘要和已执行记录。 | 同身份同载荷无变化返回，同身份换载荷拒绝，标记与余额同事务。 |
| DUPLICATE_NO_CHANGE / 幂等 | 重放已成功请求，不再次产生经济变化。 | 在旧序号检查之前识别 T1，不能再扣一次 800.8 USDC。 |
| BUY / SELL / buyHash / sellHash | 买卖方向及双方订单摘要引用。 | 显式核对买锁扣 USDC、卖锁扣 WETH，不能只看方向相反或金额够不够。 |
| q / Q / filledBase / nextFillSeq | 本笔数量、总量、累计成交量及下一序号。 | 新成交必须连续执行且累计不超过整单；换 ID 不换旧 seq 仍失败。 |
| lot / tick / maker / 限价 | 数量步长、价格步长、挂单方和授权价格边界。 | 合约检查声明 maker 属于双方、价格等于其限价，不能证明实际谁先到。 |
| N / feeDelta / 累计费用 | 货款、本笔增收费用及按累计货款取整的收费。 | T1 为 800 与 0.8 USDC，不能信任外部随意报出的费用数。 |
| settleBatch / revert / 整批原子 | 批次交割、执行回滚及批内共同成败。 | 本次第二笔失败会撤销本次新执行的 T1，但不会撤销更早交易已交割的 T1。 |
| receipt.status / Gas / nonce | 回执执行结果、执行资源成本和中继交易序号。 | status=0 仍可能花 Gas、消耗 nonce；status=1 也不等于链最终确定。 |
| 重入 / ERC-1271 / EOA | 外调再进入合约、合约钱包验签规范和私钥账户。 | settle 不外调不代表充值提现都安全；主例用 EOA，合约钱包在建锁时另验签。 |
| ACTIVE / CLOSED / expectedFilledBase | 活跃锁、已关闭锁和关闭时预期累计成交量。 | 关闭后不能再 fill；累计量正确却不能证明链下已无 pending。 |
| D / closeLock / expireUnlock | 截止时间、正常关闭和到期解锁。 | fill 时间可等于 D，expireUnlock 必须大于 D；解锁不撤销过去交割。 |
| 规范分支 / 最终性 / 信任边界 | 当前链归属、共识终局及仍依赖的角色行为。 | 合约防越界与重复，不证明撮合公平或正常关闭时机必然正确。 |

## 把整篇文章压缩成一个故事

A、B 的订单已经在 V 建好专属锁资，撮合日志也已提交 T1：A 买 B 的 0.4 WETH，货款 800 USDC、费用 0.8 USDC。V 收到当前结算角色的指令后，先认明双方买卖方向、同一交易对与扣款资产，再查限价、数量步长、期限、连续序号和锁资。检查成立，才在一个 EVM 事务里同时扣 A 的 800.8 USDC、B 的 0.4 WETH，给 A 0.4 WETH、B 800 USDC、费用账户 0.8 USDC，并写执行标记。

重发同一 T1 时，V 先认出同身份同载荷，返回无变化，而不是拿已递增到 2 的序号误判旧请求。若把买卖摘要互换，就应在角色与资产检查处拒绝；若本次批里 T1 后的一笔到期，整笔调用的新变化连同 T1 标记一起回滚，但中继仍可能付 Gas、消耗 nonce，更早交易完成的 T1 不受影响。正常关闭与交割也由链上锁状态互斥，到期解锁则严格晚于 D，不和允许等于 D 的 fill 共用时间区间。

故事的边界是：金库能保证不留下半边交割、不因合法重放再付一次，却不能靠一个哈希证明撮合日志真实或价格时间公平。恶意授权出口若换成新身份、下一合法序号，并仍符合订单余量与限价，合约可能接受；提前关闭含链下义务的锁也仍是受信编排风险。最后，当前块里执行正确还得等待规范链与最终性证据，不能把函数返回当成最终结算或安全审计结论。

**流程位置与核心机制：** 结算计划到达金库 V 后，实际资产权利如何改变。本题负责合约输入约束、执行去重、检查顺序与事务原子性；链下日志提交由母题 04 负责，链的最终性由母题 10 负责。沿用总览的链上订单专属锁资，不改成钱包 allowance 拉款。

## 第 1 层：为什么链下两笔扣加不能代替链上原子交割？

**面试官：** T1 已经在链下成交，合约具体要原子完成哪些变化，为什么不能先扣买方、再单独给卖方？

**面试者：** 对 T1，V 必须在同一事务中消耗 A 的 800.8 USDC锁资和 B 的 0.4 WETH锁资，增加 A 的 0.4 WETH可用、B 的 800 USDC可用、费用账户的 0.8 USDC权利，同时记录 T1 已执行、双方累计成交量和序号。

如果把买方扣款与卖方收款拆成两笔独立链上交易，前一笔最终成功、后一笔失败，就已经留下单边交割；链下补偿不具备把第一笔链上交易从历史中抹掉的能力。本模型把相关金库内部状态变化放在一个 EVM 调用中，任何检查失败都回滚整笔调用的金库变化。

这保证的是该调用在某一规范分支上的原子结果，不是立即最终结算。交易仍可能重组，receipt 成功也还要经过观察与最终性判断。Gas 由中继另付，不包含在双方 USDC权利守恒里。

## 第 2 层：合约应先核验哪些条件？

**面试官：** 你说把余额更新放进一个调用，但如果中继提交超量、越价或错误资产，原子地做错也没有用，如何阻止？

**面试者：** 合约先验证当前结算角色，再查 tradeId 去重。如果已执行且 payloadHash 一致，返回无变化；已执行但载荷不同则拒绝。对新成交，读取已经建锁时验签并保存的订单，显式要求 `buy.side==BUY`、`sell.side==SELL`，两单属于同一已验证交易对、owner 不同，锁为 ACTIVE，时间不超过双方 D。本例两单的 baseToken 都是 WETH、quoteToken 都是 USDC，买锁扣减资产必须是 USDC、卖锁扣减资产必须是 WETH。仅检查“方向相反”会漏掉 buyHash/sellHash 被互换的输入，可能按错误单位扣锁；不能靠双方金额碰巧不够来阻止它。

随后检查 q 为正且符合数量步长，价格符合 tick 且不高于买限价、不低于卖限价，声明的 maker 是双方之一且执行价等于其限价，双方 fillSeq 都等于各自 nextFillSeq，`filledBase+q<=Q`。V 能验证声明与价格的关系，不能独立证明该 maker 的真实到达优先级。按统一整数规则计算 N 和累计费用差，再验证买锁足够支付 N＋费用、卖锁足够支付 q。

这些检查与状态更新处于同一 EVM 执行上下文，不存在检查完余额后另一个交易插进当前调用中修改锁资的并行窗口。链上交易是顺序执行的；但这不等于链下预检查也能锁住未来链状态。前置模拟只能提前发现问题，最终以合约执行为准。

## 第 3 层：为什么重复检查要放在序号检查之前？

**面试官：** 你把去重放在 fillSeq 前，若第二次提交 T1 时双方 nextFillSeq 已变成 2，直接拒绝不是更简单吗？

**面试者：** 单纯拒绝可以防止再成交，但会把“已经成功的重试”与“真的乱序”混在一起。尤其整批重试时，批内已经交割的旧 fill 应该是无变化成功，不能让它挡住其他本可处理的未执行 fill。

因此执行标记保存 `executed[T1.id]=payloadHash(T1)`。相同身份相同载荷先返回 DUPLICATE_NO_CHANGE，不再检查旧 seq 是否等于当前 seq；相同身份不同载荷必须失败，不能只因这个 ID 存在就声称新载荷成功。新 tradeId 才进入序号与余额检查。

即使去重分支没有再次改变资产，也必须先做角色等必要接入约束，避免把业务结果查询、事件发布或资源消耗暴露成任意执行接口。对已存在的 T1，外部可通过独立只读查询获取执行事实，不能靠重新发送一笔有成本的交易当通用查询。

## 第 4 层：攻击者换一个 tradeId 不就绕过了去重？

**面试官：** 如果去重只记 T1.id，恶意中继把同样的 0.4 WETH改成 T2.id 再发一次，合约怎么知道这是重复经济义务？

**面试者：** 单靠 tradeId 确实不能知道，不能夸大这个键的能力。本模型还用双方 fillSeq 与累计成交上限约束执行；原封不动复制 T1 的 seq=1，改 ID 后因 nextSeq=2 而失败。但是恶意授权出口若同时构造下一个合法 seq、使用尚余数量，在限价和期限内重新匹配，合约可能接受它。

原因是用户签名授权的是订单约束，合约信任撮合方在这些约束内决定匹配，不独立验证每个链下日志位置和价格时间优先。可信服务通过稳定 tradeId、不可变载荷和日志派生规则禁止业务层重建另一份成交；合约提供执行上限，不提供整套链下公平性证明。

如果要求中继完全不受信任，必须改变协议，例如引入用户逐笔成交授权、受验证的日志承诺及证明机制。这些改变有延迟和复杂度成本，不是给 tradeId 再加一层哈希就已经实现。当前方案应限制角色、监控异常匹配并明确这一风险。

## 第 5 层：合约按什么顺序更新，怎样避免重入和半边状态？

**面试官：** 在你承认信任边界之后，正常执行时还有重入或余额更新到一半的问题吗？

**面试者：** settle 的路径只改金库内部账，不调用用户回调或 token transfer。完成全部检查和金额计算后，在同一事务中更新执行标记、双方累计量与 nextSeq、锁资扣减和可用资产增加，最后发出绑定完整 T 的事件。中途发生算术错误或 require 失败，全部更新与事件一并回滚。

避免在结算中外调，是把 token 和钱包的可变行为隔离在充值、建锁验签和提现接口边界。充值必须按实际到账及白名单语义控制记权利，提现必须先扣权利再进行受保护外调，必要时使用重入保护；不能因为结算函数不外调就认为金库所有入口自动安全。

合约钱包若采用 ERC-1271，在建锁时要按规范验签，检查 magic value，并将有效授权约束存成锁对象。它不是结算时再让任意钱包执行任意代码的理由。本专题主例使用 EOA，不把合约钱包撤销后是否影响既有锁资悄悄改成新的授权模型。

## 第 6 层：批内后一笔失败，前一笔与 Gas 怎样处理？

**面试官：** 假设一批先执行了 T1，第二笔因到期失败，T1 已经写入 executed 了，会留下前半批成功吗？

**面试者：** 当前批次是一个外层 EVM 事务，且不捕获单笔失败继续执行，所以第二笔 revert 会撤销这一笔交易内所有 V 变化，包括刚执行的 T1 的资产更新、执行标记和日志。若 T1 原本在更早的交易已经成功，本次对它只是无变化去重，则更早的成功不受本次回滚影响。

执行失败的中继交易仍然可能被纳入规范链并消耗 nonce，同时支付已消耗 Gas；回滚的是调用状态，不是把这笔交易从区块里删除。业务不能把 status=0 当成“什么都没有发生，nonce 可以复用”。

若业务想支持部分批次成功，需要显式改成子调用隔离与逐笔结果模型，并重新定义批次完整性、事件和恢复逻辑。本题不偷偷启用该变体。当前编排器要按 receipt、预期事件和已执行查询还原结果，不能把批内执行到哪一行当作链上部分完成证明。

## 第 7 层：结算与关闭锁资竞争时由谁裁决？

**面试官：** 原子交割解决了批内问题，但如果 closeLock 或到期解锁与 T1 一起排队，是否会出现“已释放又成交”？

**面试者：** 在同一规范链上，V 的锁状态与时间条件提供执行处互斥。正常 closeLock 只能由当前角色调用，检查 ACTIVE 与预期累计成交量；关闭后锁为 CLOSED，后来的 fill 无法扣它。fill 若先执行，累计量改变，基于旧累计量签出的 closeLock 会失败，不能把过期关闭快照强行套上去。

但 closeLock 无法知道未上链的链下 T1，所以提前关闭是否正确仍依赖可信编排协议。只有无 open、全部已提交成交最终交割、观察对齐后才允许签出关闭；角色失陷可违反此条件，合约不能凭 expectedFilledBase 证明没有链下义务。

到期路径不同：fill 仅接受 `timestamp<=D`，expireUnlock 仅接受 `timestamp>D`，不共享合法时间区间。解锁保留已经交割的累计量，只返还剩余锁资，绝不能回滚旧成交。链下对到期后是否违约还要查全最终截止前历史，不能见到一次 unlock 就忽略已执行 fill。

## 第 8 层：如何检查合约保证的边界？

**面试官：** 如何向面试官证明你区分了合约能保证的安全性和链下服务负责的部分？

**面试者：** 我会列三类可反驳命题。第一类是执行安全：新 fill 不得超量、越价、超锁资、超期、乱序；相同 tradeId 重复不产生额外变化，冲突载荷拒绝；所有成功路径逐资产守恒。第二类是批次原子：在第二笔注入失败，第一笔在该事务内的变化也应不存在，但 Gas 和中继 nonce 仍可消耗。

第三类是信任边界：构造一个授权角色在合法限价内使用下一序号的不公平匹配，它可能通过合约，因此不能声称合约已验证价格时间优先；构造未等待 pending 交割就关闭锁资的授权调用，若链上累计量匹配，也可能通过，因此链下关闭协议和权限治理不能省略。

这些是要验证的性质与手工反例，不是已完成的安全审计。最后还应区分“当前分支状态正确”和“最终规范链上已终局”，后者依赖观察与最终性策略，不能在这个合约函数的返回值里得到。

## 本题收束

- **讲透的机制：** 资产、数量、执行标记和序号共同提交；身份与载荷同时去重；整批失败不留本次半边状态。
- **最容易答错的边界：** 合约去重不是链下公平性证明，回滚不退还全部交易成本，正常关闭仍有可信编排前提。
- **反例检验：** 互换 buyHash/sellHash 必须在角色检查时拒绝，即使两个锁的数值碰巧足够也不能按错误资产单位扣款；T1 重放不应再扣 800.8 USDC；换 ID 不换 seq 应失败；换 ID 又换合法 seq 揭示的是受信撮合角色的授权边界，而非哈希本身失效。
