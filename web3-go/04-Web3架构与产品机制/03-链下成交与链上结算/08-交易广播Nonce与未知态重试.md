## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| T1 / 义务 / attempt | 原成交承诺和为履行它进行的一次尝试。 | T1 始终是 0.4 WETH、800 USDC 货款及 0.8 买费，尝试超时不删承诺。 |
| V / EVM / WETH / USDC | 金库、合约执行环境、封装 ETH 式基础资产及报价资产。 | 在单链 V 内用双方专属锁资交割，不因钱包临时授权而获得本例资金资格。 |
| RPC / UNKNOWN / TTL | 节点接口、结果未知和本地过期时长。 | 超时或等太久不是失败证明，不能按 TTL 释放 pending 或锁资。 |
| orderHash / tradeId / payloadHash / planHash | 订单、成交、完整载荷和计划各自的身份。 | 经济身份与条款跨重启、加速不变，不能拿新请求号造一份 T1。 |
| chainId / sender / txNonce | 链、发送账户和该账户的交易顺序位置。 | 持久唯一分配域为链加账户，建锁、结算、关锁若共用账户也共用账本。 |
| latest nonce / pending nonce / 缺口 | 节点已确认或待处理序号信息及低序号空位。 | 只供核对，不直接负责分配；低 nonce 未处理可堵住后面交易。 |
| rawTx / txHash / 交易族 | 原始签名交易、其哈希及同槽位相关候选。 | 先耐久保存 rawTx 才外发，恢复要查全族，不能只盯最后加速哈希。 |
| HSM / 签名任务 | 硬件安全模块及持久的待签动作身份。 | 数据库与 HSM 没有全局事务，签名超时按原任务找结果，不另分配经济动作。 |
| already known / replacement underpriced | 节点已认识交易，或嫌替换报价不够高。 | 都不能证明 T1 已交割或原交易失效。 |
| nonce too low / null receipt | 节点认为序号落后，或当前没返回回执。 | 要查实际消耗者、各候选和规范块，不直接得出成功或失败。 |
| calldata / value / 费用加速 | 调用参数、附带原生币数额及提高交易费用。 | 同 nonce 加速只改允许费用参数，不改目标 V、计划、数量、价格或序号。 |
| receipt.status / Gas | 回执执行结果和执行成本。 | 失败入块仍可消耗 nonce 与 Gas；报价不足没入块不能混称 status=0。 |
| executed / fillSeq / nextFillSeq | 合约成交记录、本笔订单序号和下一序号。 | 同身份同载荷先去重；合约防双扣不代表可任意增加活动发送路径。 |
| blockHash / canonical / 最终水位 | 区块身份、规范归属和已核实的最终处理截止点。 | 槽位已消耗不等于 T1 成功；回执还要核验分支、载荷与执行覆盖。 |
| epoch / 租约 / 围栏 | 任期、数据库写入资格及外发权限屏障。 | 租约到期不撤回已签交易；切主先阻断旧主新签名，再接管旧任务。 |
| D / expireUnlock / closeLock | 执行截止、到期解锁和正常关锁。 | 新 fill 时间不晚于 D；到期解锁严格晚于 D，正常关锁则须全部义务最终交割。 |
| SETTLED_FINAL / DEFAULTED_UNSETTLED | 最终已交割及最终未交割违约。 | 最终前缀越过 D 并查全截止前历史后才能二选一，不由广播错误决定。 |

## 把整篇文章压缩成一个故事

撮合日志已替 A、B 承诺 T1，双方各有 pending=0.4 WETH，但广播结算时节点超时。操作员不能把 A 的 2,012.01 USDC、B 的 1 WETH 锁资退回，或让这 0.4 再参与撮合，因为原交易可能已进网络。发送系统先在持久账本为原计划预留 nonce，由受限签名出口保存 rawTx 后才广播；就算签名调用途中崩溃，也按原任务找回结果，而非再造一个动作。

节点后来报 already known、nonce too low 或查无回执，都只是线索。恢复器展开原 nonce 下的所有签名候选，查规范块、实际槽位消耗者及 V 对 T1 的执行证据；若需加速，只改费用，不改 0.4 WETH、800 货款、0.8 买费或 calldata。若失败回执最终确定且仍有执行窗口，核清旧路径后可为原义务新建合法尝试。切主时还须阻断旧主新签名并接管旧 rawTx，数据库租约不能让已签交易自动失效。

最后，入块成功只先记 INCLUDED，核验完整执行覆盖和最终性后才核销 T1；失败入块则保留 Gas、nonce 与失败历史，不删除义务。若始终未知，须等最终规范前缀时间严格越过 D、截止前历史查全，才能判已履约或违约；解锁另按真实最终结果记录。安全恢复保留了旧交易可能生效的风险，不承诺加价必及时入块，也不以本地超时替用户解除经济责任。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于已提交成交义务、不可变结算计划与链观察器之间，负责解释交易怎样被耐久签出、广播、替换和接管。核心是区分经济身份与交易尝试，持久唯一分配 nonce，保存原始签名交易，围绕同一经济载荷恢复未知交易。沿用总览的单链 EVM 金库 V、T1 数值和主例双方同一截止 D；底层链采用 PoS 风格可查询最终性，规范后继块时间戳严格递增。不把钱包 allowance 当锁资，不用发送成功替代最终交割。

## 第 1 层：广播超时为什么不是成交失败

**面试官：** T1 已在链下成交，调用节点广播结算交易时超时，你怎样判断结果，是否可以释放双方资金？

**面试者：** 不能把调用超时解释成链上失败，更不能释放资金。超时只说明调用方没有拿到确定回复；节点可能尚未接收，也可能已经传播，交易甚至已经入块。T1 的权威事实是撮合日志已经提交：双方 open 各为 0.6 WETH、pending 各为 0.4 WETH，经济条款是交割 0.4 WETH、支付 800 USDC、收取买方 0.8 USDC 费用。这个事实不会因 RPC 返回方式改变。

我会给交易尝试记录广播超时，把义务置于可恢复的 UNKNOWN，而不是创建“失败撤销”事件。此时用于最终业务判断的资金仍是 A 可用 2,987.99 USDC、锁定 2,012.01 USDC，B 可用 1 WETH、锁定 1 WETH；链可能已经变化，只是本地还没有最终证据。后续应恢复原交易、查询执行情况并等待最终链裁决。这里保留风险暴露是必要代价，不能通过把 pending 退回 open，让同一份资金再次形成成交义务。

## 第 2 层：经济身份为什么不能采用 txHash

**面试官：** 你说要恢复原交易，但加速交易会产生新 txHash，怎样保证恢复的是同一笔 T1 而不是另一笔成交？

**面试者：** 我会分层保存身份。订单用绑定签名域的 orderHash；成交用撮合提交位置派生的稳定 tradeId，T1 切主、重发和加速都不改这个身份；完整成交载荷形成 payloadHash；一个有序成交集合及其规则、依赖形成 planHash。链上交易尝试则保存 chainId、sender、txNonce、rawTx、txHash 及替换关系。一个计划可以经历多个尝试，txHash 只定位其中一次签名结果。

例如 T1 的第一次交易和提高费用后的替换交易，txHash 不同，但必须指向相同的成交条款、订单序号和结算计划。V 在执行处保存 executed[tradeId]=payloadHash：同身份同载荷不再改变状态，同身份不同载荷拒绝。重复检查在 fillSeq 检查之前，避免已经执行的 T1 因双方 nextFillSeq 已变为 2，被误当作新序号错误。

这不意味着任意人都能提交自造的 tradeId。V 仍检查当前结算角色、用户订单约束和锁资。链上执行幂等解决重复经济效果，不能代替合法日志身份的产生和签名出口的权限控制。

## 第 3 层：nonce 怎样分配才不被并发和重启复用

**面试官：** 成交身份已经稳定，但两个发送线程同时拿到相同的节点 pending nonce，怎样避免它们把不同计划签成同一个 nonce？

**面试者：** 节点 pending nonce 只能辅助核对，不能承担并发分配。我要以 chainId、sender 为分配域，在持久事务中锁定账户游标，为计划预留 nonce，并以该域加 nonce 建唯一约束。预留记录同时绑定 planHash、目标 V、value、calldata 摘要及签名任务身份，然后推进游标。只有持久提交完成的任务才能进入签名队列。重启后先读这个账本，不从某个节点的一次返回重新开始分配。

如果 lockOrder、结算和 closeLock 共用同一发送账户，它们必须共用这套 nonce 管理；不能各自维护“本模块的下一个 nonce”。账户也不能同时被未受控的钱包或脚本使用。节点的 latest nonce、pending nonce 与本地账本不符时，应暂停新分配、核对已签交易和规范链消耗，不是直接把游标覆盖成较大的值。

唯一预留只防止本系统把一个槽位绑定给两个经济任务，不保证交易一定被打包。某个低 nonce 长期缺失会阻塞后面的交易，因此还要保存预留、待签、已签、已广播等阶段，明确由谁恢复缺口，不能只留下一个不断增长的整数。

## 第 4 层：签名成功但进程崩溃的窗口怎样关闭

**面试官：** nonce 已经持久分配，如果 HSM 已签名、数据库还没记住 txHash 就崩溃，恢复时怎么知道有没有有效交易流出？

**面试者：** 这个窗口必须在签名出口处理，不能假设数据库与 HSM 有全局事务。先持久化签名任务及完整待签载荷，再用原任务身份调用受限出口；出口在可恢复地保存原始签名交易及其与任务的绑定之后，才允许向广播通道交付。txHash 可以从 rawTx 重算，只有 hash 而没有原始交易，不能完成可靠重播。

如果 HSM 已算出签名、出口尚未耐久保存就失败，出口不得先把这份结果发给网络；恢复时继续解析同一个签名任务，而不是新分配 nonce 或换成另一笔经济动作。若采用外部签名服务，就需要它提供可查询的任务结果或受控的重复请求语义；不知道任务结果时保留待恢复状态，不能凭调用超时推断“未签”。即使同一载荷因签名形式产生不同 hash，它也只能属于同一 nonce、同一经济载荷的交易族。

这里的可靠性边界是“原始交易已耐久保存，才可外发”。签名任务表、出口持久结果和广播交付之间仍要恢复衔接，但任何已可能进入网络的交易都应能在账本中找回，不能靠内存中的发送协程证明安全。

## 第 5 层：节点报错能够证明哪些事情

**面试官：** 原始交易已经保存，重播时节点分别返回 already known、replacement underpriced、nonce too low 或 null receipt，这些结果能让你结束 UNKNOWN 吗？

**面试者：** 这些结果都不足以直接把 T1 结案。already known 只说明这个节点认识该交易；replacement underpriced 只说明它拒绝了当前替换报价，原交易仍可能有效；nonce too low 只说明该节点认为这个 nonce 已被消耗或落后，需要查明消耗者；null receipt 只说明这次查询没有返回回执。尤其节点切换、私有传播和短暂分叉都能让这些返回彼此不一致。

我会把返回值追加为尝试证据，记录节点、时间、请求和 hash，但保留 T1 义务与整个交易族。确定接收的广播也只是推进尝试状态，不推进为 SETTLED_FINAL。对于本地可证明没有签出、没有交付的任务，可以恢复发送；对于已经可能外发的任务，发送错误不能撤回它的链上执行能力。

这样做的代价是 UNKNOWN 可能持续存在，不能按一个短 TTL 回收。它必须有专门的观察和恢复责任，而不是变成没人处理的错误日志。要退出未知态，需要规范链证据及最终性，而不是多重试几次后把最后一次 RPC 错误当成事实。

## 第 6 层：怎样查询整个可生效交易族

**面试官：** 既然单个节点错误不够，你具体查哪些证据，怎样避免只盯着最后一次加速的 hash 而漏掉原交易？

**面试者：** 我会从持久任务展开这个 nonce 下的全部原始交易、hash 和替换关系，查询各成员回执及其 blockHash，再核对所在块是否属于当前规范祖先链。同时由完整块观察器索引发送账户和 nonce 的实际消耗，以及 V 的执行结果。标准 JSON-RPC 并不天然提供一个可靠的“按账户 nonce 查交易”接口，这部分应由已验证区块、交易数据和本地索引补足，不能编造一个万能查询。

查到某个成员入块后，仍需核验目标链、发送者、V、计划载荷、receipt 状态，以及对应成交执行结果。对已去重的成交，可能没有新的资产变化事件，还要核对 executed[T1] 与预期 payloadHash 和原执行证据，不能把“没新事件”误报成未交割。

账户 nonce 前进只能证明某个槽位已消耗，不能单独证明 T1 成功；T1 的某个 hash 查不到，也不能证明它永远不会成功。查询结果都要带依据块和最终水位，直到某个交易族成员的结局最终确定，或者期限及完整历史共同排除了未来履约，才有条件进一步分类。

## 第 7 层：同 nonce 加速究竟允许修改什么

**面试官：** 如果查了一轮仍未入块，怎样加速？能否顺便换一个更容易成交的价格，或者使用新 nonce 再发一次？

**面试者：** 在本模型中，加速只调整经过策略允许的费用参数，不改变 chainId、sender、nonce、目标 V、value、calldata 和经济计划。替换结果仍要先保存 rawTx，再广播，并追加到原交易族。节点接受替换所需的费用涨幅与交易类型有关，不能把固定百分比说成全网协议保证，也不能承诺提高费用就必然在 D 之前入块。

不能顺便改价、改数量、改费率或换双方 fillSeq。T1 始终是 0.4 WETH 对应 800 USDC、买方费用 0.8 USDC。即便同 nonce 的两份交易在一条规范链上不能同时执行，改经济载荷也会让“到底哪份合同被签出”取决于打包选择，破坏不可变义务和审计关系。

对仍未知的原任务，默认不另占新 nonce 制造第二条活动发送路径。V 的成交幂等能够阻止同一 T1 重复扣款，但不能消除额外 Gas、依赖阻塞和恢复歧义。新 nonce 只在明确处理旧槽位结局后，为同一未履行义务创建新的合法尝试；若另外签取消交易，它也不等于撤销 T1，更不是本题默认的同载荷加速。

## 第 8 层：nonce 已消耗与义务已履行为什么不同

**面试官：** 你要求先明确旧槽位结局。如果旧交易 receipt status=0，但 nonce 已经前进，下一步是重发还是判违约？

**面试者：** 先把两个事实拆开：status=0 表示这次 EVM 调用失败，V 在该事务中的执行标记、余额、累计量和锁资变化全部回滚；已入块的失败交易仍消耗发送者的 nonce 和原生币 Gas。但这份回执未必最终，短重组可能使其离开规范链，所以先记录失败入块证据，不能立即把旧槽位视为永久不可变。

当失败回执最终确定，再按失败原因与剩余履约窗口处理。如果是 Gas limit 不足或可恢复执行条件问题，且 T1 尚未在其他合法路径交割、依赖满足、链上期限仍允许，可以用新 nonce 提交经济条款不变的后续尝试；原失败记录保留。交易费用报价不足通常使交易不被接收或不被打包，不应混作已经产生 status=0 的执行失败。若规范链显示该 nonce 被不属于账本的交易消耗，则暂停该账户外发、核查签名越权和所有活动任务，不能把 nonce 增长直接映射为 T1 的成功或失败。

即使发现不可修复的执行错误，也不能删除已提交成交。它仍是未交割义务；是否最终违约，还要经过截止和完整历史核验。反过来，status=1 也只进入 INCLUDED，须核对实际成交结果并等待最终性，不能在这一步释放 pending。

## 第 9 层：切主为什么不能只靠数据库租约

**面试官：** 旧交易的记录都在库里，主服务切换时只让新主拿到租约继续发不就够了吗？为什么还要管理签名出口的任期？

**面试者：** 数据库租约只能限制遵守租约的写入者，不能撤回旧主手里已经签出的有效交易。如果旧主失去租约后仍能调用签名器，或者还能广播先前 rawTx，新主重分配槽位和计划就可能产生并行外发。我要在签名出口检查当前任期、任务归属和允许载荷，拒绝过期任期产生新的签名；发送账户的 nonce 账本则保持跨任期唯一，不能因选主重置。

接管顺序应是先阻断旧主新增签名，接管已提交日志、计划、nonce 和出口任务，再枚举所有已签或签名结果未知的任务，恢复观察和缺口，最后恢复新的计划外发。已签 rawTx 即使来自旧任期，也不能因数据库把它标成“废弃”而假装失效。若必须撤销旧链上角色，那是需要链上执行和最终确认的权限变更，在它最终生效前仍要计算原交易的可能效果。

因此任期是外发权限围栏，不是成交幂等键，也不是链上撤销证书。新主继续履行的是原 T1，不因 epoch 改变生成新成交；正常 closeLock 更不能绕过这些尚可生效的旧义务。

## 第 10 层：期限怎样真正关闭未知交易的风险窗口

**面试官：** 如果旧主的 rawTx 永远查不到，难道资金永远不能退出？D 已经过了，能否按本地时间清理 UNKNOWN 并关闭锁资？

**面试者：** 本地时间越过 D 不够。主例双方同一 D，合约只允许块时间不晚于 D 的新 fill。要判 T1 最终未交割，需要最终规范前缀的时间已经严格越过 D，并且从相关建锁和可能执行位置到该最终水位的历史完整，核对所有相关执行和 payloadHash。依据本模型规范后继块时间戳严格递增及可查询最终性的前提，才能既排除截止前已经成功但本地漏看的履约，也排除未来规范链再接入截止前分支的可能性。

历史核验发现已交割，就形成 SETTLED_FINAL 的证据；确认未交割，才形成 DEFAULTED_UNSETTLED 的证据。证据作为稳定身份命令可靠送回撮合状态所有者，经同一日志幂等裁决 pending 转入 settled 或 defaulted，保留原义务和尝试历史，观察线程不直接改订单数量。各订单的 expireUnlock 必须满足 block.timestamp>D，并在解锁结果最终确定后记录实际释放。这个锁终态不是履约或义务免除。

正常 closeLock 走另一条条件更强的路径：没有 open，所有已提交成交最终交割，观察对齐，才可签发；其广播未知也不能提前增加可用余额。本题的取舍是宁可在证据缺口中保留占用，也不把 RPC 失联改写成经济免责。这个模型能够提供安全的分类与退出，不能承诺所有链下成交无条件交割。

## 本题收束

- **机制：** tradeId 与 payloadHash 固定经济效果，planHash 固定结算计划；持久 nonce 账本避免槽位冲突；签名出口先保存 rawTx 再外发；整个交易族接受带规范块和最终水位的观察，合约幂等兜住重复执行。
- **边界：** 广播成功、节点接收、nonce 消耗、入块成功和最终交割是五种不同事实。数据库租约不能撤销已签交易；同 nonce 加速不改经济载荷；失败回滚 V，不回滚 Gas 与 nonce；本地 TTL 不能释放未知风险。
- **反例检验：** 旧交易广播超时后，系统给 T1 换身份、释放 pending 并让 A 继续用同一锁资成交；旧交易随后在截止前成功。即使新请求有请求级去重，也挡不住两份经济义务争夺同一份资金。正确路径必须保留原身份、原始交易和锁资约束，直到最终执行或截止后的完整证据给出终局。
