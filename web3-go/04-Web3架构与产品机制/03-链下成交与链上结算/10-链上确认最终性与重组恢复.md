## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| receipt.status / INCLUDED / SETTLED_FINAL | 回执结果、已入块和最终交割。 | status=1 只是一阶段证据，既不自动证明目标 T1，也不自动允许关锁。 |
| V / T1 / pending | 金库、原成交和待交割数量。 | 暂时观察到 A 得 0.4 WETH、B 得 800 USDC、费用 0.8 时，业务 pending 仍各为 0.4。 |
| WETH / USDC / A / B | 封装 ETH 式基础资产、报价资产，以及本例买卖双方。 | A 用 USDC 买入 WETH，B 收 USDC；观察到的金库权利不等于外部钱包到账。 |
| chainId / blockHash / parentHash / number | 链身份、区块哈希、父区块哈希和高度。 | 高度相同可能是不同分支，规范归属要靠哈希祖先链判断。 |
| txHash / logIndex / 原始观察身份 | 交易哈希、日志位置及这次分支观察的定位。 | 观察身份包含 blockHash，同一交易换分支入块不能混成一条永久成功。 |
| tradeId / payloadHash / 执行覆盖 | 经济身份、完整载荷摘要及核验全部计划结果。 | 新执行项看本次证据，重复项看同一规范前缀的既有执行，不强求重发 Settled 事件。 |
| WebSocket / removed / RPC | 推送通道、撤回提示及节点查询接口。 | 推送只唤醒，漏 removed 仍要验证祖先链；字段齐全也不自动证明节点诚实。 |
| 完整回执集合 / 连续前缀 | 块内无缺失的执行材料及从起点连续处理的历史。 | 不只盯已知哈希或不完整日志分页，缺材料就停在最后完整块。 |
| 整块事务 / 游标 / Outbox | 块级共同提交、处理位置和可靠待发记录。 | 原始日志、投影变化、进度与回报同本地事务，不能写五笔就跨过剩下五笔。 |
| projection / 最终投影 | 可查询的派生状态及已最终的事实视图。 | 未最终观察可撤销，不用它新增最终资金准入能力。 |
| canonical / 共同祖先 / 重组 | 当前规范分支、分叉前共有的最后块及换支过程。 | 先停最终推进，旧块倒序撤回、新块正序接入，不能混用半恢复视图。 |
| UNKNOWN / 再入块 / 再激活 | 待观察状态、新分支重新包含及观察恢复有效。 | 保留 T1 义务，撤回不是取消成交；不能因以前见过就永久丢掉恢复。 |
| revision / 消费去重 | 单调状态修订号及重复消息识别。 | 同 tradeId 的撤回、再入块是新修订，旧消息不能覆盖新状态，号不随回滚倒退。 |
| finalized / PoS / 最终检查点 | 链最终性标签、权益证明共识及其已最终前缀依据。 | 本例按验证后的检查点与祖先关系处理，不泛化成所有网络固定几个确认。 |
| F / O / 最终水位 | 链最终覆盖位置、本地完整观察位置和可核销截止点。 | 同规范祖先链上只推进到两者共同覆盖范围，不能跨过 O 内部的缺口。 |
| 最终证据命令 / 状态所有者 | 带稳定身份的证据交付及唯一订单裁决方。 | 观察器把证据交回撮合日志，后者幂等执行 pending→settled，不让观察线程直接改数量。 |
| D / DEFAULTED_UNSETTLED / EXPIRED_UNLOCKED | 执行截止、最终未交割违约和锁到期释放。 | 最终时间越过 D 加历史完整才判违约；解锁本身不是已履约或未履约证明。 |
| 最终性停滞 / 深重组 / 失败关闭 | 终局不推进、触碰已最终历史及暂停危险动作。 | 不静默改成固定确认数，不按普通短重组自动抹掉已承诺最终的事实。 |

## 把整篇文章压缩成一个故事

观察器看到 T1 的成功回执，当前块里 A 的锁资从 2,012.01 降到 1,211.21 USDC，B 的锁资从 1 降到 0.6 WETH，双方分别得到 0.4 WETH 和 800 USDC，费用账户得到 0.8 USDC。它先核对链、V、载荷和批次全部结果，只记 INCLUDED；业务 pending 仍为 0.4，不拿这些暂时资产再准入。整块日志、可撤销投影、游标与 Outbox 必须一起提交，不能块里十笔只落五笔却已推进进度。

后来同高度出现不含 T1 的新块，即使没有 removed 推送，parentHash 和祖先核验也能暴露换支。观察器找到共同祖先，倒序撤回旧分支，再正序补齐新分支；T1 的日志承诺不删，回到待观察。若原交易重新入块，按新 blockHash 关联同一 T1，再发更高 revision；订阅方不能只因见过 tradeId 就吞掉撤回和恢复。若批内有早已执行的重复项，则引用原规范执行证明，不强求无变化调用再造交割事件。

只有经验证的最终前缀与本地完整观察前缀共同覆盖 T1，观察器才把最终证据可靠交给撮合状态所有者，后者经原日志核销 pending，并由唯一回报投影发出终局修订。若期限 D 已过，也要查全截止前历史再分已交割与违约，不能见解锁就猜结果。最终性停滞或触碰已最终检查点时，停止相关释放和自动终态推进，保存证据进入核查；这不是固定确认数可偷偷替代的承诺。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题从链上执行结束进入链观察、回报与最终核销，负责区分 INCLUDED 与 SETTLED_FINAL，建立按 blockHash 的规范祖先链、完整块事务、可回滚投影、最终水位和领域 revision。公共资产与成交事实沿用总览；主例双方同一截止 D，底层采用 PoS 风格可查询最终性，规范后继块时间戳严格递增。链下成交日志不可撤销，撤销的是未最终的链观察，不是 T1 的经济义务；最终数量转移仍由撮合状态所有者经同一日志裁决。

## 第 1 层：成功回执为什么还不是结算完成

**面试官：** T1 的 receipt status=1，是否已经可以告诉用户结算完成，并释放剩余锁资？

**面试者：** 不可以。status=1 只说明这次交易在某个块内没有以失败状态结束，尚未证明该块属于最终规范链，也不能仅凭状态位证明它执行的就是预期 T1。我会先核对链、发送者、目标 V、成交载荷及实际执行结果，建立 INCLUDED 证据，再等最终性和完整观察前缀满足后核销为 SETTLED_FINAL。

在 T1 暂时入块成功的观察中，A 的 USDC 锁资为 1,211.21，B 的 WETH 锁资为 0.6；A 增加 0.4 WETH，B 增加 800 USDC，费用账户增加 0.8 USDC。但这些尚未最终的变化属于可撤销观察层。链下双方 pending 仍各为 0.4 WETH，不因为回执成功就转为 settled，更不能把暂时出现的可用量拿来作为新的最终准入能力。

最终交割也不直接等于订单锁资可以关闭。主例还有双方各 0.6 WETH 的 open，须由撮合日志接受撤余量，再满足全部已提交成交最终交割和观察对齐等条件，才能签发正常 closeLock。回执、交割终局和订单退出是三个不同边界。

## 第 2 层：观察证据怎样绑定到真正执行结果

**面试官：** 你说要核对实际执行结果，具体保存什么？只记录 txHash、区块高度和 status=1 够不够？

**面试者：** 不够。区块高度在重组前后可以相同，txHash 也可能在另一分支重新入块。我会保存 chainId、blockHash、parentHash、number、块时间，以及 txHash、receipt 状态和每条日志的 logIndex、合约地址、主题与数据。原始观察身份包含 blockHash，领域关联再落到 tradeId、payloadHash 和计划。这样可以回答“哪一条分支在什么位置观察到 T1”，而不是只回答“曾经见过这个 hash”。

对于正常首次执行的批次，要核验预期成交集合与顺序、载荷摘要、数量和费用结果，不能见到一个 T1 事件就把整批所有义务都记成功。对于合约幂等返回的重复项，V 在 seq 检查之前比对相同 tradeId 和 payloadHash，并无变化返回，不一定再发 Settled 事件。因此批次完整性是“新执行项的本次执行证据，加上重复项在同一规范前缀中已核实的执行标记和历史证明”覆盖全部计划，而不是每项在本 receipt 中必须有新事件。不能只看 status=1，也不能把重复调用计作第二次交割；最终核销时，这些既有执行证据同样必须进入完整最终前缀。

记录 receipt 的节点来源和依据块，也便于识别节点返回矛盾。这里的字段是恢复所需证据，并不是证明 RPC 诚实的密码学证明；若要对抗不可信数据源，还需要验证其链与回执证据，不能把字段齐全等同于内容一定真实。

## 第 3 层：完整块观察怎样避免漏一笔就推进水位

**面试官：** 字段齐全仍可能漏事件。如果 WebSocket 少推了 T1，而系统已经看到了后面的区块，你怎么保证“最终之前都观察完了”？

**面试者：** WebSocket 只用来唤醒同步，不承担完整性。观察器从持久游标的下一个块开始，获取选定规范分支的块头和完整相关执行材料，按固定 blockHash 读取并核验，不把多次查询得到的不同分支混成一个块。涉及分页或分段时必须取齐全部结果；空返回只有在该块材料完整、确实没有相关日志时才能作为空块处理。

更稳妥的完整性来源是该块交易清单及对应完整回执集合，确认没有缺交易、缺回执，再筛选 V 的事件并核验预期结算调用。只查询已知 txHash 会漏掉接管前的旧交易，只依赖地址日志流又可能漏掉分页或重连窗口。若当前数据源不支持可信地补齐这些材料，就停在最后一个完整块，不能用新的 head 高度替代观察进度。

我会明确系统对所用节点的信任边界，必要时从独立来源交叉核对，或验证回执与块承诺的一致性。重点不是声称一个 RPC 请求绝不漏，而是只有完整性条件满足后才提交该块；观察存在缺口时，后面的块即使已经被缓存，也不能使业务最终水位跨过去。

## 第 4 层：整块提交怎样覆盖崩溃窗口

**面试官：** 假设一个块有十笔相关成交，前五笔已经写库后进程崩溃。你怎样避免重启时跳过后五笔，或把前五笔记两次？

**面试者：** 下载和解析可以在事务外暂存，但对外可见的提交必须以完整块为边界。一个本地数据库事务中同时写入该块原始日志、规范块记录、可撤销投影变更或撤销材料、完整观察游标以及对应 Outbox。事务提交前崩溃，游标不前进且这一块的领域变化不可见；提交后崩溃，块及其待交付回报同时存在，重启由 Outbox 补发。

原始日志以包含 chainId、blockHash、txHash、logIndex 的身份去重，块提交也要有唯一性和父块前置条件。重放已提交块不再次增加资产或生成同一 revision 的领域效果。只在日志表去重但把余额更新和游标分开提交，仍可能形成“事件已存在、余额尚未改”的半状态，所以去重必须落在同一提交协议中。

未最终投影与最终投影应分层维护。完整块事务可以推进可撤销观察水位，但不能直接把其中每笔成交都标为最终；最终核销另有受祖先关系和最终性限制的推进过程。这样既覆盖崩溃窗口，也为下一步重组留下可逆的依据。

## 第 5 层：不用 removed 通知怎样发现重组

**面试官：** 整块事务保证了不漏提交，但节点可能根本没推 removed。如果原来保存的高度 H 被换成另一块，你怎样发现并定位撤销范围？

**面试者：** 我会持续验证块哈希祖先关系。处理下一个块时，parentHash 必须等于当前规范尖端的 blockHash；重连、切换节点或周期复核时，还要比较已保存尖端及必要检查点是否仍在节点给出的规范链上。因为单靠新增块链接，也可能在一段时间里没有发现旧尖端已经被替换，所以不能只等 removed。

一旦不匹配，先停止该分支的最终推进和依赖它的释放动作，向后沿块头查找共同祖先，验证候选新分支连续性，并列出旧分支需要撤销的块和新分支需要接入的块。高度相同不意味着同一事实，只有 blockHash 和 parentHash 才能界定分支关系。

如果共同祖先位于本地最终水位之前，已经触碰了原最终性假设，应进入异常冻结和证据核查，而不是照普通短重组自动回滚最终资产。正常恢复范围只覆盖未最终分支；这个限制是系统对外终局承诺的边界，不能在深重组时临时假装过去从未宣称最终。

## 第 6 层：撤销观察怎样不撤销成交义务

**面试官：** 找到共同祖先后，原来在旧分支 INCLUDED 的 T1 怎么恢复？是不是把之前的成交删掉，再从新链重新生成一次？

**面试者：** 不能删撮合成交。T1 的 tradeId、条款和双方 open/pending 的来源仍是已提交日志。撤销的只是旧 blockHash 上的执行观察：按旧块从后向前恢复可撤销投影、标记原观察非规范，并使尚未最终的 T1 从 INCLUDED 回到待观察或可恢复的 UNKNOWN。pending 仍各为 0.4 WETH，不返还为 open，也不伪造一笔新的 T1。

随后按新分支的正向顺序接入完整块。如果同一交易在新块重新入块，就用新的 blockHash 建立 INCLUDED 证据；如果换了同一计划的替换交易，也通过稳定 tradeId 关联，而不是新记一份资产。若尚未入块，由外发恢复模块重新核对原交易族、nonce、序号和期限，再决定是否重播。

撤销区块、变更规范游标、恢复投影和生成修订 Outbox 必须有一致的本地提交边界。较大重组可以逐块恢复，但需要恢复中标识及一致读取水位，阻止用户把“旧分支撤到一半、新分支接了一半”的混合投影当成可用最终状态。恢复不是重新裁决链下价格时间优先。

## 第 7 层：回报去重怎样兼容重组修订

**面试官：** 你保留了 T1，但订阅方通常按 tradeId 去重。它先收到了 INCLUDED，再收到重组回退，不就把后者当重复吞掉了吗？

**面试者：** 所以 tradeId 是经济身份，不应独自充当状态消息去重键。对外回报要带 tradeId、单调 revision、状态、依据块和最终水位。第一次 INCLUDED、撤销后的待观察、重新 INCLUDED 都是同一成交的不同修订；消息可以重复投递同一 revision，但不能让消费者因为见过 tradeId 就永远拒绝后续状态。

未最终观察的对外回报投影在提交规范变化的同一事务内分配下一 revision 并写 Outbox；同一个 tradeId 的修订分配需要串行化，最终结果也经这一路径接入，不让不同线程各自生成相同版本。消费者保存每个 tradeId 已应用的 revision：相同 revision 幂等处理，较旧消息不能覆盖较新状态，发现版本缺口时查询当前状态或补齐历史。revision 不因回滚而减小，它记录“本地对事实的认识被修订了”，不是照抄区块高度。

回退回报必须清楚写成未最终观察撤销，而不是“成交取消”。最终结算回报只有 SETTLED_FINAL 才发送相应终局语义。对于会形成其他经济动作的下游，仍要求依据最终状态和权威余额，不能让一条暂时 INCLUDED 通知触发不可撤销的提现或新的无担保成交。

## 第 8 层：最终水位怎样与完整前缀相交

**面试官：** revision 能修正临时认识，但到底什么时候允许发 SETTLED_FINAL？直接用固定确认数，还是读取节点 finalized 就结束？

**面试者：** 首先按具体链定义最终性适配。在以太坊 PoS 基线上，可以使用验证后的 finalized 检查点作为最终性依据，但它不是任意固定确认数的同义词；其他 EVM 网络或 L2 需要另外说明其共识、数据可用性和上层结算条件。不能把一个网络的标签或秒数复制成所有链的资产终局。

本地可核销水位是“已确认最终的规范前缀”与“本地已经完整提交的连续观察前缀”的交集，并要求两者在同一祖先链上。若节点给出最终高度 F，而本地只完整处理到 O，就只能在共同规范分支上推进到两者都覆盖的位置；O 之前有缺块时更不能越过缺口。保存最终水位的高度、blockHash、时间及依据，而不是只保存一个数字。

确认 T1 的真实执行证据属于这个最终前缀、payloadHash 和批次覆盖一致后，观察器在本地事务中固化最终资产投影、推进水位，并写入携带稳定命令身份、tradeId、payloadHash 和最终证据的 Outbox。对重复项，依据的是其既有真实执行，不是把当前无变化调用当成新的交割。命令交回撮合状态所有者，由同一可靠日志裁决 pending 各减少 0.4、settled 各增加 0.4，并提交终态结果及可靠交付记录；观察线程不直接修改订单数量。

若证据已保存但日志命令尚未提交，允许最终链资产与本地 pending 暂时不同，但必须保留两边水位，不能据此放行正常关闭。重试沿用原命令身份，状态所有者核对原成交及终态互斥条件，重复投递只返回原结果。对外回报投影再由同一串行化路径接入这个日志结果、分配下一 revision 并可靠发布，不能让最终回报越过数量裁决。最终检查点先到、观察材料未齐时，T1 仍等待而不是猜测成功。

## 第 9 层：节点分歧和最终性停滞怎样处理

**面试官：** 如果两个 RPC 节点给出的 finalized 哈希不同，或者链一直出块但最终水位不前进，你是否可以临时降成十二个确认继续释放？

**面试者：** 不能静默降级。节点分歧可能来自同步滞后、错误网络、提供商故障或更严重的共识问题，应先核对 chainId、检查点祖先关系和节点健康，把不能解释的分歧隔离。多个节点返回相同结果可以降低单源错误风险，但多数 RPC 不是共识协议的替代，尤其不能只投票比较高度。

最终性停滞时，可继续保存带有未最终标签的完整块观察，但不能把更长的未最终分支自动当成原承诺下的最终资产。应限制依赖最终余额的新准入和正常关闭，保留 pending 与待发布的最终结果；链上仍可能发生 fill 或到期解锁，本地必须继续观察它们，而不是因冻结就忽略链的实际变化。

若未来要改成概率确认策略，那是对终局承诺与风险容忍度的显式变更，需要处理旧义务和已有回报，不能在故障中偷偷切换。对于冲破原最终检查点的重组，也要进入异常核查和受控修复，而非让自动回滚代码把已经对外宣称不可撤销的状态悄悄改掉。

## 第 10 层：同一观察证据怎样服务截止与关闭

**面试官：** 你选择保守等待最终证据，但 T1 的期限已经到了。观察器怎样既不误判违约，又不让一个查不到的交易永远阻止退出？

**面试者：** 观察器需要同时提供过去与未来的证据。过去方面，相关订单从最终建锁、可能执行起点到最终水位的历史必须完整，核对 T1 的 executed 载荷、执行事件和所有已知尝试，不能只看最后一笔 hash；未来方面，最终规范前缀的块时间必须严格越过主例双方共同的 D。依据规范后继块时间戳严格递增和可查询最终性前提，未来规范后继已经不能再执行只允许 block.timestamp<=D 的新 fill。

若 T1 已在截止前交割，即使本地晚收到结果，也应提交最终履约证据命令；若完整证据确认未交割，则提交最终未交割证据命令。两者均由撮合状态所有者经同一日志幂等裁决，分别核销为 SETTLED_FINAL 或 DEFAULTED_UNSETTLED，pending 只能进入其中一种终态。未成交 open 的过期裁决另行进入 cancelled，不混同于 defaulted。到期解锁的锁状态另记 EXPIRED_UNLOCKED，不能把它当作已履约证据。单纯本地时钟越过 D、null receipt 或只看到一笔解锁日志，都不足以替代完整历史。

正常 closeLock 则要求该订单全部已提交成交最终交割、没有 open、日志与最终观察对齐，再由授权出口提交。观察器最终确认关闭后才反映真实释放，关闭广播未知不提前增加可用。它负责给出可验证水位与执行事实，不替撮合日志删除义务，也不凭一个最终高度猜测未观察到的订单已经安全。

## 本题收束

- **机制：** 用 blockHash/parentHash 维护规范祖先链，完整块内原子提交日志、可撤销投影、游标和 Outbox；短重组撤销观察而保留成交；以单调 revision 表达修订；最终水位必须落在最终性与完整观察共同覆盖的规范前缀内；最终证据可靠送回撮合状态所有者，由同一日志裁决 pending 的数量终态。
- **边界：** status=1 不代表预期载荷已最终交割；WebSocket 不是完整性来源；tradeId 去重不能吞掉状态修订；固定确认数不等于所有网络的 finalized；触碰已宣称最终的检查点不能按普通短重组静默处理。
- **反例检验：** 旧块 H 含 T1，系统立即把 pending 清零并给 A 的 0.4 WETH 新增准入；同高度新块 H′ 不含 T1。若系统只按高度保存游标或只按 tradeId 去重，它既无法正确撤销旧观察，也会漏掉重入块修订。正确方案在最终前不释放该能力，并能按旧 blockHash 撤销、按新祖先链重放、以更高 revision 通知认识变化。
