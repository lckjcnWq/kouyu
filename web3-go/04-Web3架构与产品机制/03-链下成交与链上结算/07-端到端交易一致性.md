# 大问题 7：怎样保证链下成交义务与链上资产端到端一致？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 端到端一致性 / 不变量 | 从授权到退出始终不能违反的业务约束。 | 不是所有页面同时刷新，而是义务不变、数量不重用、资产不重复交割。 |
| V / EVM / 四类权威 | 金库、执行环境及签名、资产、撮合、观察各自负责的事实。 | 签名限授权，V 管资产，日志裁决成交撤单，观察器不拥有造币或删义务的权力。 |
| 最终锁资 / 准入快照 | 已最终成立的专属资金占用及其证据。 | 必须核对仍活跃、期限和水位，曾经建锁成功不是永久入场券。 |
| T1 / COMMITTED / pending | 本例成交、可靠提交和已成交待交割量。 | 0.4 WETH 已承诺，金库暂未交割是允许暂态，不能再拿去卖。 |
| WETH / USDC / Gas | 封装 ETH 式基础资产、报价资产和执行成本。 | 本例货款与买费计 USDC，交易量计 WETH，Gas 由中继原生币另付。 |
| Q / open / settled / cancelled / defaulted | 总量、未成交、已交割、取消和违约分类。 | 连同 pending 满足数量守恒；取消与违约有不同经济含义。 |
| tradeId / payloadHash / planHash | 成交身份、完整经济载荷摘要与计划摘要。 | 重启、重投或加速均恢复原 T1，不换名字制造另一份义务。 |
| fillSeq / 前驱 | 每订单连续成交序号及必须先执行的成交。 | 即使不同 tradeId 也不能乱序；恢复撮合的变体不沿用主例暂停条件。 |
| Outbox / 本地事务 / 全局事务 | 待发记录、局部共同提交与跨系统共同提交。 | 计划与交付可本地原子，但数据库与 EVM 不存在隐含全局事务。 |
| executed / 幂等 / 原子交割 | 链上执行记录、重试不增效果和双边共同更新。 | V 已执行而数据库未确认时仍可恢复，不能只靠“已发送”防重复。 |
| nonce / 交易族 / RPC | 发送序号、相关签名候选集合和节点接口。 | 先查旧尝试和执行证据，不能因为接口超时无条件另做经济动作。 |
| Saga / TCC / Cancel | 分阶段补偿或预留模式，以及其中的取消动作。 | 名称不创造逆转链上交割的权限，已成交后没有任意全局 Cancel。 |
| INCLUDED / SETTLED_FINAL | 暂时入块和最终交割。 | 未最终只记观察成功，最终证据回同一撮合日志才核销 pending。 |
| blockHash / revision / 重组 | 分支区块身份、回报修订号及规范历史切换。 | 撤回旧分支投影但不删除 T1；旧分支执行标记不证明新分支已执行。 |
| D / closeLock / expireUnlock | 截止、排空后的正常关锁及到期退出。 | 两种释放都不是无损撤销 T1，关锁须等义务最终交割与观察对齐。 |
| DEFAULTED_UNSETTLED / 最终前缀 | 最终未交割违约和已最终确定的连续历史。 | 最终链时间越过 D 且截止前历史完整，才能排除未来履约并核清过去。 |
| H / S / 同水位对账 | 最终块、已处理撮合前缀以及对齐截止点的比较。 | 暂态差异须能解释，汇总相等仍不能掩盖用户或订单错账。 |

## 把整篇文章压缩成一个故事

A、B 的资金已在金库 V 按订单最终锁好，撮合日志提交 T1：买卖 0.4 WETH、货款 800 USDC、买费 0.8 USDC。双方 open=0.6、pending=0.4，链上还没交割，这不叫系统失去一致性，而是不同权威在描述不同阶段。若此时撤单，最多取消实际 open；另一个明确恢复撮合的变体里，T2 先成交 0.2，撤单就只能撤 0.4，不能每个线程都按旧余量办事。

T1 回报只送到 A 就崩溃，也得从可靠日志恢复同一 T1，补发 B 的回报和结算计划。若 V 已执行而数据库未记成功，恢复先查原交易族及链上标记；同载荷重试不再交割。若入块后重组，则撤回该分支观察、用新 revision 回报，保留原义务等待再观察或重交。所谓 Saga 不能把 A 已取得、甚至已提现的 0.4 WETH 自动拿回来；反向交易若需进行，必须另有同意、新义务与审计关联。

最后，完整规范证据达到最终性，才经撮合日志把 T1 从 pending 归入 settled，排清义务后方可正常关锁。若最终链时间已越过 D，且截止前历史查全仍未履约，则归入违约，余锁到期返还也不算交割；证据不足就仍不能装作确定。全链路闭环靠的是每次承诺有耐久事实、每次资金释放有证据，不是一个“最终一致”口号，更不是跨数据库与 EVM 的全局 exactly-once 或必然履约保证。

**流程位置与核心机制：** 独立串起签名、锁资准入、成交提交、计划交付、合约执行、最终观察与安全退出。本题定义总体保证和跨模块契约；广播细节、重组实现与违约证明分别在母题 08、10、11 深挖。沿用预存金库 V，不混用中心化账本或钱包拉款模型。

## 第 1 层：你说“一致”，究竟保证什么？

**面试官：** 链下已经成交，但链上还有延迟，你怎样定义交易一致性，而不是只说最终一致？

**面试者：** 我会把一致性定义成一组可检查的约束，而不是所有页面同时显示相同状态。首先，同一成交只有一份固定的经济义务；其次，订单数量不能被重复成交、重复取消或凭空消失；再者，链上每笔交割必须符合签名订单并逐资产守恒，同一成交不得重复产生资产效果。

同时允许明确的暂态：T1 已提交、双方 pending=0.4，但金库还没交割；或链上已入块、观察器尚未追上。但这些暂态必须保留原义务、锁资及可恢复进度，不能因超时就把同一数量重新当成 open 或可用资金。

最终结果也不只一种。T1 要么有最终交割证据，要么在未来履约已被协议关闭、过去历史核验完整后记为未履约违约，不能静默删除。当前模型不承诺永不违约，一致性要求如实保存违约与退出，而不是将所有失败包装成未成交。

## 第 2 层：四种不同权威怎样共同支撑这些约束？

**面试官：** 你说要保留义务和锁资，它们分别由谁决定？是否存在一个全局事务锁住全部模块？

**面试者：** 没有数据库和 EVM 的全局事务。用户签名限定授权条款；V 决定真实可用、专属锁资、已执行成交和关闭状态；撮合复制日志决定链下成交与撤单的唯一顺序；观察器负责把规范链事实带水位投影回来，它不是另一个资产裁决者。

跨边界靠分阶段契约：只有最终建锁才允许订单进入撮合；撮合在可靠日志提交时形成义务；计划服务只能忠实转换该义务；V 在资产实际变化处再次核验并幂等执行；链下只有看到完整最终证据才核销 pending。正常关闭必须等已提交义务全部最终交割。

局部原子边界各不相同：撮合内部数量和成交同提交，计划与 Outbox 同本地事务，V 内部交割同 EVM 事务，观察进度与块日志同事务。最终履约或违约证据要以稳定身份命令交回撮合状态所有者，经同一日志裁决 pending→settled/defaulted，观察线程不并发直接修改订单数量。把这些边界及未知态连接起来才能收敛，不是选一个 Saga 或 TCC 名字就跨越了它们。

## 第 3 层：锁资最终成功，撮合准入之前链又变化怎么办？

**面试官：** 你依赖最终锁资作为准入依据，但订单可能接近 D，或者运维关闭锁资。最终成功一次是否足够永久准入？

**面试者：** 不够。最终性证明的是相应历史事实，不表示状态永久不变。准入还要核对该锁未关闭、未进入到期风险窗口，链观察水位没有超过允许的滞后阈值，并在本地为该 orderHash 设置唯一的活动订单实例。

正常协议下，关闭只来自同一成交日志裁决之后的可信编排：先停止 open，再排空 pending，最后签发 closeLock。用户不能在 D 前绕过这一协议任意提走专属锁资；否则链下撮合期间就没有资金保证。若观察过旧、结算角色出现异常或最终性停滞，则暂停新撮合而非继续消费旧准入快照。

临近 D 必须预留保守结算窗口，但窗口是风险策略，不是网络必定及时的数学保证。即使已经停止新撮合，既有义务仍可能因链故障越过 D。系统要继续保存并处置，而不是以“准入时检查过”为由声称无违约可能。

## 第 4 层：准入后，成交与撤单同时发生怎样守恒？

**面试官：** 锁资没有被提走，可是 A 撤掉剩余量的同时又来了成交，怎样防止 pending 和 cancelled 都占同一份量？

**面试者：** 竞争由拥有订单权威状态的同一撮合日志裁决，不让撮合线程和撤单消费者分别修改订单。初始 Q=1，T1 提交后 open=0.6、pending=0.4。若撤单接着被提交，就把 0.6 转为 cancelled；pending 仍为 0.4，不因撤单被释放。

另设一个允许恢复该交易对撮合、预算与容量足够的独立变体，不沿用主例轮末暂停：如果另一个 fill T2 先于撤单提交 0.2，则先形成 open=0.4、pending=0.6，撤单最多取消 0.4。每次变化都满足 `Q=open+pending+settled+cancelled+defaulted`，双方订单变化、成交 T 和交付依据共同提交，不能出现只改一方余量的日志结果。

撤单受理回报只承诺未成交余量已不能被后续撮合消费，不承诺锁资已经可用。若 API 超时，查询原命令位置和结果；不能由网关另起一个释放事务绕过日志。链上释放还有更严格的排空条件。

## 第 5 层：成交已提交，交付一半崩溃能否撤回？

**面试官：** T1 已经向 A 回报已成交，B 的回报和结算消息还没有发出，进程崩溃。直接回滚 T1 让双方重试不是更简单吗？

**面试者：** 不能。可靠提交已经形成双方义务，回报是否送到每个客户端不是成交成立条件；回滚会让已经看到成功的一方持有一个被系统悄悄取消的交易承诺。

复制日志应保存可恢复的完整成交条款与交付位置。重启后从提交前缀继续派生相同 tradeId 和结果；计划服务按 tradeId＋payloadHash 消费，计划与消费完成标记、Outbox 同事务。私有回报也以同一日志事实构建，未收到的一方可以查询或补发。

允许结果延迟或重复送达，不允许形成第二份 T1 或丢掉第一份。若业务选择在复制耐久前就确认成交，主节点丢失后可能无法恢复已承诺结果，那不是消息队列能补救的窗口，必须改变确认条件或承认数据丢失风险。

## 第 6 层：链上执行成功但数据库还没有记成功呢？

**面试官：** 计划可靠了，V 已交割 T1，链下服务在更新数据库前崩溃，重试是不是仍然会重复扣款？

**面试者：** 服务层会重复提交是现实情况，所以真正的去重必须在 V 的资产变化事务里。V 保存 `executed[T1.id]=payloadHash`，同载荷重试无变化；不同载荷冲突。不能把“数据库已发送”作为链上唯一去重依据。

交易尝试与义务分开记录，恢复先查原 nonce/交易族、receipt 和合约执行状态；若重交同一 T1，仍受执行处幂等保护。业务数据库只有获得完整规范链证据并达到最终策略后，才把 pending 转为 settled，而不是在发送函数返回时先释放。

重试若改了 tradeId，就把同一业务动作伪装成另一个动作，合约可能只剩订单 seq 和数量上限作为防线。可信计划与签名出口必须禁止这种重新命名；不能把每次 HTTP 请求都生成新成交身份称为幂等设计。

## 第 7 层：能否用补偿事务撤销链上成功？

**面试官：** 既然不能有全局事务，为什么不使用 Saga：某一步失败就逆向转账，把资产补回去？

**面试者：** Saga 适合组织存在明确补偿语义的业务，但已完成链上交割没有自动可逆性。A 最终获得 0.4 WETH后，可能已经按协议继续使用或提现，系统未必有权把它拿走；即使再做反向交易，价格、费用和外部状态也可能不同。

因此本模型的失败动作通常是重试原义务、暂停新增风险、等待终局证据或记录违约，而不是撤销成功成交。若双方同意反向交易或有额外担保赔付，必须创建新义务、记录授权和与 T1 的关联，不篡改 T1 已发生的事实。

TCC 的 Cancel 同样只能取消仍具备取消资格的预留阶段。撮合已经提交经济义务之后，不存在一个任意时刻可调用的全局 Cancel。链上正常 closeLock 是排空后的余款释放，expireUnlock 是到期后的退出，都不是对 T1 的无损回滚。

## 第 8 层：重组会让链上成功消失，链下应当回退什么？

**面试官：** 如果你不能回滚经济义务，但 T1 所在区块被重组掉，数据库里之前记录的成功怎么办？

**面试者：** 区分经济义务与可撤销观察。未最终的 T1 只应为 INCLUDED，不提前记 SETTLED_FINAL；重组时撤销该 blockHash 对应的资产观察投影和 inclusion 关系，发布带新 revision 的状态修订。原成交日志、T1 的条款与待履约义务保留。

如果原签名交易在新规范链再次执行，相同 tradeId 在这条链上的 V 状态中只产生一次效果；如果新链尚未执行，就继续观察或重交同一义务。不能把旧分支的 executed 标记当作新分支也已执行的证据，更不能为了“重新成交”把 T1 改为 T2。

正常 closeLock 必须等待最终交割与观察对齐，是为了不把这种可撤销成功提前变成释放动作。若底层最终性假设本身被破坏，属于重大事故，需要停止资产释放、保存分支证据并人工治理，不能声称普通 k 个确认策略绝对不会遇到。

## 第 9 层：超过 D 还未交割，怎样结束暂态而不撒谎？

**面试官：** T1 一直 UNKNOWN，D 已经过了。你总不能永远不释放锁资，也不能假装已交割，如何给出唯一终态？

**面试者：** 本地时间越过 D 还不够。先取得包含时间戳严格大于 D 的最终规范链前缀，确认其祖先关系和相关事件完整性，核验 V 的执行标记、订单累计量与 T1 历史。因为未来块时间不能回到 D 前，且 V 不再接受 fill，未来履约已被关闭；完整前缀负责排除截止前已经发生却尚未观察到的履约。

若 T1 已交割，核销为 SETTLED_FINAL；若未交割，pending 转为 defaulted，记录 DEFAULTED_UNSETTLED、原因和证据水位，不改为 cancelled。到期解锁交易若最终成功，单独记录返还剩余锁资。金库资产可退回与原经济义务违约是两个相容事实，不是义务自动免除。

若最终性或历史查询不完整，就保留证据不充分的未知态并阻断受影响资本池新增风险。不能通过批量“过期失败”制造一个假的确定性；当前协议的活性确实依赖链和可验证历史恢复。

## 第 10 层：怎样验证这些局部保证真的闭合？

**面试官：** 最后不要再列组件。如果要反驳你的整套方案，应在哪些两个动作之间注入失败？

**面试者：** 先检查每个承诺后是否有耐久事实：成交确认前后、计划事务提交前后、原始交易持久化与外发之间、V 执行与本地确认之间、完整块保存与最终水位推进之间，都要能从已有事实继续原动作。每个窗口恢复后 tradeId 和条款不变，重复不增加资产效果，未知不减少必要义务。

再用交错时序攻击数量和退出：T1 与撤单争同一份量，T2 越过 T1，closeLock 越过 pending，旧交易在加速后迟到，重组后原交易再入块，到期前成交但到期后才补到日志。每种情况都必须说明谁裁决、保留什么、哪项证据允许改变分类，不能只回答最终对账。

最后在同一最终块 H 和已处理撮合前缀 S 上核对逐订单数量与逐资产金库守恒，差异要能归入明确的 pending、已执行未投影、释放未最终或实际违约，而不能凭汇总余额相等就忽略单用户错误。以上是文档方案的反例验证方法，不冒充实际故障注入或链上实验结果。

## 本题收束

- **讲透的机制：** 不变量定义正确性，分清四类权威，以可靠提交、执行处幂等、可回滚观察和证据化退出连接局部事务。
- **最容易答错的边界：** 最终一致不是允许先超卖；原子交割不是保证必然交割；重组撤销链观察，不删除经济义务；违约不是未成交。
- **反例检验：** 在“V 已执行、数据库未确认”窗口重启，若系统释放锁资或生成新 tradeId，而不是恢复同一 T1 并等待最终证据，端到端保证没有闭合。
