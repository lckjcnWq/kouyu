## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EVM / 单链现货订单簿 | EVM 是执行合约的环境；订单簿按买卖报价组织交易。 | 本例交易 WETH/USDC，不是 AMM 换币、保证金或跨链产品。 |
| V / ERC-20 / available / locked | V 是持币金库；ERC-20 是代币接口；后两者分别是可用权利和订单专属锁资。 | 钱先充值到 V；金库内部可用不等于外部钱包已到账。 |
| A / B / WETH / USDC | A、B 是买卖双方；WETH 是封装 ETH 式资产，USDC 是报价资产。 | 教学配置分别为 18、6 位小数；Gas 用中继原生币另付，不从这笔 USDC 里暗扣。 |
| EIP-712 / orderHash / salt | 结构化订单签名、订单摘要和区分订单的唯一盐值。 | 签名绑定链、V、订单及规则版本；salt 约定不重复不能代替合约记录摘要使用状态。 |
| allowance / lockOrder | allowance 是允许花钱的额度；lockOrder 才是本模型的订单建锁动作。 | 只有最终建锁才能准入，签名、approve 和数据库预留都不等于锁资。 |
| maker / 价格时间优先 | maker 是先在簿上的挂单方；先比价格、再比到达顺序。 | B 先到，T1 按其 2,000 限价成交；合约能验限价，却不能独立证明谁先到。 |
| T1 / tradeId / COMMITTED | T1 是本例成交；tradeId 是稳定义务身份；COMMITTED 表示可靠提交。 | 日志提交了 0.4 WETH 的成交义务，不因广播失败变回“从未成交”。 |
| Q / open / pending / settled / cancelled / defaulted | 订单总量及未成交、已成交待交割、已交割、已取消、违约未交割五类数量。 | Q 等于五类之和；撤单只动 open，不能把 pending 偷换成 cancelled。 |
| fillSeq / nextFillSeq | 每订单成交的连续序号和下一应执行序号。 | 双方 T1 都为 1；共享订单的后笔不能跨过前笔抢先结算。 |
| q / P / N / atoms / lot / tick | 数量、价格、名义金额、最小整数单位及数量价格步长。 | N=q×P/10^18；合法网格恰可整除，不能用浮点近似凑金额。 |
| C / F(C) / ceil / bps | C 是累计名义金额；F 是累计费用；ceil 为向上取整；1 bps 是万分之一。 | 买方收 10 bps，每笔收 F(C+N)-F(C)，避免拆分后重复取整多收费。 |
| payloadHash / planHash / batchId | 完整成交载荷摘要、结算计划摘要和组批身份。 | 换批不改成交条款；同 tradeId 不同载荷必须拒绝。 |
| 原子交割 / executed / revert | 同一事务共同更新、执行记录和失败回滚。 | V 同时改双方锁资、可用、费用和序号；整批失败不保留本批前半段，Gas 不因此退回。 |
| sender / txNonce / rawTx / txHash / attempt | 发送者、交易序号、原始签名交易、交易哈希和一次尝试。 | 加速可换哈希，不能换出另一份义务；nonce 不是订单 salt 或 fillSeq。 |
| RPC / UNKNOWN | 节点接口和结果尚未确定的状态。 | 超时、查无回执不证明失败，不能释放资金或无条件新建经济动作。 |
| INCLUDED / SETTLED_FINAL / finalized | 已入块、业务最终交割和链最终性检查点。 | 入块还要核验 V 的执行覆盖、规范祖先关系及完整历史，才可核销 pending。 |
| blockHash / logIndex / projection / revision / 水位 | 区块哈希、块内日志位置、派生视图、修订号和处理截止点。 | 分支观察可撤回再激活；页面修订不是链上退款，扫描进度也不是完整核验的替代品。 |
| D / closeLock / expireUnlock | 订单截止时间、正常关闭和到期解锁。 | fill 可在时间等于 D 时执行；到期解锁必须严格晚于 D，正常关闭另须排清已提交义务。 |
| DEFAULTED_UNSETTLED | 已成交、但经终局核查确认未交割的违约状态。 | 最终前缀越过截止并查全历史后才能判定；返还余款不等于赔付或免除原义务。 |
| Outbox / Inbox / ACID | 待发记录、消费记录和数据库事务的可靠性属性。 | 各自保护本地提交与重投，不把数据库、消息、签名设备和 EVM 合成一个全局事务。 |
| epoch / 围栏 / MEV | 任期、阻断旧执行者的权限屏障，以及利用纳入排序获利的机会。 | 切主不自动废除旧签名交易；受限出口、容量保护和排序信任仍是独立边界。 |

## 把整篇文章压缩成一个故事

A 想买 1 WETH，B 想卖 1 WETH，先分别把 5,000 USDC 和 2 WETH 充值进金库 V。A 的买限价是 2,010，连同最大 2.01 费用锁住 2,012.01 USDC；B 锁住 1 WETH。等建锁最终确定，撮合服务才接纳订单。本轮只有 0.4 WETH 的教学成交预算，轮末暂停新增撮合；先到的 B 按 2,000 成为 maker，日志可靠提交 T1：买卖 0.4 WETH、货款 800 USDC、买方费用 0.8 USDC，双方各剩 0.6。这里已经有成交承诺，却还没有资产交割。

结算员把这份条款变成不能随重试变价的计划，按双方序号提交 V。执行成功时，V 同时扣 A 的锁资 800.8 USDC、扣 B 的锁资 0.4 WETH，给 A 可用 0.4 WETH、给 B 可用 800 USDC、给费用账户 0.8 USDC。广播超时就追查原尝试，不能再造一笔 T1；同身份同载荷重放不再扣钱。同批后笔失败会回滚本批新变化，入块后若发生重组则撤回观察投影，但可靠日志中的成交义务始终保留。

正常结局是先核验规范链执行和最终性，再经撮合日志核销待交割量，随后撤销双方余下 0.6 并等待锁资最终关闭。A 最终可用 4,199.2 USDC 和 0.4 WETH，B 可用 800 USDC 和 1.6 WETH，费用为 0.8 USDC；提现仍需另办。若链停顿拖过 D，须以最终规范前缀和完整截止前历史判明是否履约：未交割就保留违约事实，到期解锁不算赔付。这套设计防止越权和重复交割，不承诺撮合公平可由合约自证，也不承诺每份链下成交都必然交割。

## 一、文字全流程

### 1.1 固定讨论基线

本专题研究**单链 EVM 现货订单簿：预存金库、链上订单锁资、链下撮合确定成交义务、链上金库内原子交割**。这是用于分析机制的教学设计，不宣称任何公司采用此架构，也不宣称已经完成合约审计、性能测量或生产验证。

- 金库合约 V 持有白名单 ERC-20，维护用户 `available`、每订单 `locked` 和费用账户。用户先充值；只有最终规范链上的余额及锁资结果才成为撮合准入依据。链下数据库不拥有任意增发可提资产的权限。
- 用户签署 EIP-712 限价订单，绑定 owner、资产地址、方向、数量、限价、唯一 salt、截止时间和协议版本；其摘要 `orderHash` 同时绑定签名域中的 chainId、V 地址和域版本。提交 `lockOrder` 时，V 验签并将可用余额移入该订单的专属锁资桶。同一摘要不得重复建锁；salt 不重复只是签发约定，合约仍要记录摘要的使用状态。
- 链下撮合服务等待建锁最终确定，按价格时间优先撮合。一次可靠日志提交原子确定买卖剩余量、待结算量、成交身份及经济条款，产生**不允许因链上失败而删除的成交义务**。链上资产尚未交割，页面只能回报“已成交、待结算”。
- V 只接受当前授权结算出口的成交指令，仍逐项检查双方订单、限价、数量、截止时间、订单内 fillSeq、重复成交身份和锁资。**信任撮合方决定匹配与排序，不等于信任它可以绕过用户签名转走任意资产。** 链上不能独立证明链下价格时间优先，也不能凭 tradeId 自动判断哪个日志是合法日志。
- 每笔 fill 在同一 EVM 事务内，消耗买方锁定报价资产与卖方锁定基础资产，同时增加双方可用资产和费用账户；不在撮合或结算时调用任意 token 转账。真正提到外部钱包属于后续提现流程，需要再次完成链上交易与最终性确认。
- 支持部分成交；每个订单上的 fillSeq 从 1 连续增长。一个批次默认**整批原子**，不支持捕获单笔失败后继续。批内先后顺序也是执行语义；基线保守要求跨批前驱已经最终交割，未最终前驱与后继须同批有序执行或先等待。提高流水线吞吐属于改变条件后的取舍，不是增加 goroutine 就能越过共享订单的依赖。
- 撤单先由同一撮合日志裁决，只停止尚未成交的余量。正常提前关闭链上锁资，须等该订单全部已提交成交义务最终交割，且最终观察已对齐，再由授权出口提交 `closeLock`；关闭为终态，合约检查预期累计成交量和当前锁状态。为简化并发，不提前按部分撤单量释放锁资。
- 订单还有签名截止时间 D：合约只在 `block.timestamp <= D` 时执行 fill；任何人可在 `block.timestamp > D` 后触发到期解锁。假设底层链的规范后继区块时间戳严格递增，采用 Ethereum PoS 风格的可查询最终性；其他 EVM 链必须重新验证这两个前提。到期不抹去已确定的成交义务：未交割义务进入违约处置，不能改称“未成交”。本模型无保险赔付、自动做市商代偿或跨链结算，不承诺所有链下成交必然交割。
- Go 服务使用持久日志/数据库、Outbox、专用 nonce 管理器、受限签名出口及可回放的链观察器。它们是不同可靠性边界，不构成数据库与 EVM 的全局 ACID。

**替代方案的条件变化：** 若改用用户钱包直接授权拉款，余额和 allowance 可随时改变，链下预留不再是链上锁资；若改成全链撮合，则成交裁决者变化；若要无条件保障交割，必须改变到期退出、链上成交承诺登记、抵押或信用兜底等设计，不能只给当前系统加一句“最终一致”。

### 1.2 贯穿案例：T1 的经济条款不随交易重试改变

交易对为 WETH/USDC，WETH 18 位、USDC 6 位。数量步长 `0.0001 WETH`，价格步长 `0.01 USDC/WETH`，两者相乘恰为 `1 micro-USDC`，所以合法网格上的名义金额可精确计算。链上和 Go 均使用整数，不使用 float64。资产映射按 chainId＋合约地址，不按 symbol。

初始只考虑本案例资金：

| 项目 | 买方 A | 卖方 B | 费用账户 |
|---|---|---|---|
| 最终确认的充值 | 5,000 USDC，0 WETH | 2 WETH，0 USDC | 0 |
| 签名订单 | 买 1 WETH，限价 2,010 | 卖 1 WETH，限价 2,000 | 固定收取买方 10 bps |
| 建锁最终完成 | 锁 2,012.01 USDC，可用 2,987.99 USDC | 锁 1 WETH，可用 1 WETH | 0 |

买方锁资 = 限价最大名义金额 2,010 USDC＋最大费用 2.01 USDC。卖方仅锁基础资产。订单绑定固定费率与费用规则版本；不能在重试时更改收费。金库内资产权利也不能和外部钱包余额混成一个口径。

为让部分成交可手工追踪，教学撮合按可暂停轮次执行：本轮基础资产成交预算为 0.4 WETH，仍按价格时间优先分配；轮末在同一日志中暂停该交易对新增撮合，结算与撤余量继续，主例关闭前不恢复。不是两张 1 WETH 的交叉订单在无预算、无暂停的持续撮合中会自然只成交 0.4。

本轮卖方为先到 maker，形成 T1：`0.4 WETH × 2,000 USDC/WETH = 800 USDC`。买方费用 `0.8 USDC`，卖方实收 `800 USDC`，买方实收 `0.4 WETH`。双方 `fillSeq=1`，各剩余 `0.6 WETH`。

主例双方采用同一截止时间 D，先使 T1 最终结算，再撤销各自剩余 0.6 WETH、关闭锁资；异常场景每次独立重置到指定检查点，不把各篇故障叠加。若比较不同截止时间的变体，fill 必须不晚于双方 D 的较小值，而两份锁资分别按自己的 D 到期解锁，不能因一方过期就自动提前释放另一方的锁。

### 1.3 一笔业务主流程

```text
A、B 充值到金库 V
    ↓ 链观察器核对规范区块与最终性，投影最终可用余额
A、B 签署限价订单 → 接入服务校验签名、网格、费率和期限
    ↓
授权中继提交 lockOrder → V 验签、检查可用余额、创建专属锁资
    ↓ 建锁最终确定后，链下持久接纳与价格时间排序
撮合日志裁决 T1
    ├─ A/B open 各减少 0.4，pending 各增加 0.4
    └─ 同一提交保存 tradeId、完整条款、双方 fillSeq 与交付记录
    ↓
结算编排读取已提交义务 → 生成不可变 planHash → 按订单依赖组批
    ↓
nonce 管理器持久分配 nonce → 签名出口保存原始签名交易 → 广播
    ↓
V 在同一事务内核验并交割 T1
    ├─ A 锁资 -800.8 USDC，A 可用 +0.4 WETH
    ├─ B 锁资 -0.4 WETH，B 可用 +800 USDC
    └─ 费用账户 +0.8 USDC，写入 T1 执行标记及双方累计量
    ↓
链观察器记录 included 证据〔blockHash、txHash、logIndex〕
    ↓ 规范链与最终性满足策略，完整区块观察提交
T1 标记 SETTLED_FINAL → pending 转 settled，发布最终结算回报
    ↓
同一撮合日志接受撤余量 → open 转 cancelled，保留链上锁资
    ↓ 所有已提交成交最终交割，投影水位对齐，授权出口提交 closeLock
V 关闭锁资 → 观察最终关闭结果 → 释放剩余资产成为可用
    ↓
业务订单关闭、T1 最终结算；提现到外部钱包需走独立提现流程
```

订单余量被撤销与链上锁资关闭不是同一个时刻。持久受理也不是成交，成交不是交割，receipt 成功不是最终确定，网页显示不是权威状态。

### 1.4 主要分支

```text
签名、价格或精度不合法 → 拒绝，不创建成交义务
建锁广播结果未知 → 保留建锁意图，查询/恢复原交易，不接纳未最终建锁订单
建锁最终失败 → 不进入撮合；到期余量不得继续撮合

撮合提交后调用方超时 → 用原请求身份查询，不创建另一份订单/成交
撤单与 fill 同时进入 → 同一日志裁决 → 只取消实际 open，pending 不释放
结算交易广播超时/查无 receipt → UNKNOWN → 保留义务和锁资，不当成失败
receipt status=0 → 本次调用的金库变更回滚，Gas 已消耗 → 原义务仍在
receipt status=1 → 先 INCLUDED，核验新执行事件及重复项既有执行证据的完整覆盖 → 等最终性
未最终区块重组 → 撤销观察投影，T1 回到待观察/待重交，不删除成交日志

临近 D、积压或链故障 → 停止接纳风险，优先处理既有义务
最终规范链已越过 D → 禁止未来 fill，完整核验截止前执行历史
    ├─ 已交割 → 核销为 SETTLED_FINAL，不能同时计为违约
    └─ 未交割 → DEFAULTED_UNSETTLED，保留追偿/争议事实，不自动赔付
到期 unlock 最终完成 → 记录实际释放，不等同于义务被履行或免除
```

### 1.5 同一案例的状态与资金检查点

| 检查点 | A 的 USDC〔可用／锁资〕 | B 的 WETH〔可用／锁资〕 | 其他资产与义务 |
|---|---|---|---|
| 建锁最终完成 | 2,987.99／2,012.01 | 1／1 | 无成交；双方 open=1 |
| T1 链下提交 | 不变 | 不变 | 双方 open=0.6、pending=0.4；确定 800 USDC＋0.8 费用条款 |
| T1 暂时入块成功 | 观察到 2,987.99／1,211.21 | 观察到 1／0.6 | 可撤销观察层看到 A +0.4 WETH、B +800 USDC、费用 +0.8；业务仍 pending |
| T1 最终交割且最终证据回撮合日志提交 | 最终 2,987.99／1,211.21 | 最终 1／0.6 | 双方 settled=0.4、pending=0；金库最终可用余额已变化 |
| 撤余量并最终关闭锁资 | 4,199.2／0 | 1.6／0 | 双方 cancelled=0.6；A 有 0.4 WETH，B 有 800 USDC，费用账户有 0.8 USDC |

T1 后不立即释放价格改善与费用余量。买方剩余锁资 1,211.21 USDC 不等于剩余 0.6 WETH 的最低资金需求，关闭时才全额返还。USDC 守恒：`4,199.2 + 800 + 0.8 = 5,000`；WETH 守恒：`0.4 + 1.6 = 2`。主例没有代币转账税、rebasing、额外 maker 费、Gas 从 USDC 扣除等隐藏变化；Gas 由中继的原生币单独核算。

## 二、核心板块：谁有权决定什么

| 板块 | 决定什么、为什么核心 | 权威状态与上下游契约 |
|---|---|---|
| 用户授权与金库建锁 | 限定允许交易的资产、数量、限价与期限；防止签名被解释成任意划款权 | V 拥有余额、锁资与摘要使用状态；链下只接纳最终建锁且未关闭的订单 |
| 链下撮合与可靠日志 | 决定成交身份、匹配顺序、余量和不可删除的义务 | 复制提交的命令/结果日志拥有成交与撤单裁决；不把 RPC 成功当作可靠提交 |
| 清算计划与批次编排 | 将成交转换成精确交割量，并防止相同订单跨批乱序 | plan 绑定 tradeId、条款、双方 fillSeq、费率版本和依赖；重试不重新定价 |
| 合约交割 | 使重复、超量、越价、过期与半边扣款不能在执行处成立 | V 原子更新执行标记、订单累计量、锁资与双方可用；不依赖消费者去重保护链上资产 |
| 广播、观察与最终性 | 区分调用尝试、入块事实、规范链和业务终局 | 交易发送者管理 nonce；观察器维护可回滚块日志与最终水位；不以单次查询“没找到”释放风险 |
| 违约、退出与核对 | 结算不成时阻断新增风险，并解释资产与义务为何不同步 | 只有最终链证据及协议互斥条件允许减少风险；修复追加记录、受权限与审计约束 |

## 三、核心 20%：优先深挖的机制

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 义务与资产事实分离 | 撮合提交至交割 | 明确“成交了但未交割”的真实风险 | 把失败当撤单，删除有效成交 | 提交边界、pending、DEFAULTED_UNSETTLED |
| 链上专属锁资与准入 | 建锁、撮合 | 保证资金不能因钱包支出而消失 | 把 allowance 当冻结、并发超卖 | 最终锁资、保留量、期限、跨订单隔离 |
| 身份分层与载荷绑定 | 全链路 | 重试只能重试同一经济效果 | 换 txHash 后重复交割 | orderHash、tradeId、planHash、txNonce、观察身份 |
| 执行处原子性 | V 结算 | 必须在资产真正变化处阻止错误 | 半边交割或重复扣款 | 双方 fillSeq、累计数量/费用、执行标记与余额同事务 |
| 有序义务与批次依赖 | 撮合、组批 | 每订单顺序跨越多个系统 | 后笔抢先、整批阻塞且盲目重发 | 复制日志位置、依赖图、不可变计划 |
| 未知态不能释放 | 广播与超时 | RPC 无法代替链上终局裁决 | 旧交易迟到后超卖/双交割 | 同 nonce 替换、可生效交易族、合约幂等 |
| 最终性与可回滚投影 | 观察与回报 | 块内成功仍可能离开规范链 | 错误记终态、重组二次记账 | blockHash、完整块事务、finalized 水位、修订序号 |
| 失败关闭与证据化退出 | 截止与关闭 | 过去已发生和未来不能发生均需处理 | 到期就称未成交、双重释放 | 最终前缀越过 D、历史完整性、终态互斥 |
| 受限签名与恢复围栏 | 故障与切主 | DB 锁不能撤销已经签出的有效交易 | 双主外发、日志缺口重新成交 | 持久原始交易、epoch、权限撤销与旧义务接管 |

## 四、所有问答共用的设计与规则

### 4.1 数量、费用与状态不变量

1. 每个链下订单以基础资产量计：`Q = open + pending + settled + cancelled + defaulted`，五项非负。defaulted 指已成交但最终未交割的数量，不是取消量；若以后另行追偿，追加独立恢复记录，不重写原历史。
2. 撮合提交同一事务内执行：双方 `open -= q`、`pending += q`，追加同一个 T 的完整条款和交付事实。撤单只将 open 转为 cancelled；到期后的未成交 open 也由同一日志的过期裁决转入 cancelled，原因标注 EXPIRED，不混入 defaulted。pending 仍必须逐笔核查交割或违约；同一价格时间序列裁决 fill/撤单竞争。
3. 单笔义务状态：`COMMITTED → SUBMITTING/UNKNOWN → INCLUDED → SETTLED_FINAL`；未最终观察可回退。最终排除履约后可以 `DEFAULTED_UNSETTLED`，不能从广播错误直接跳转。attempt 单独记录失败、替换、入块等，不覆盖义务身份。
4. V 的每个锁资对象维护 `orderHash/owner/side/assets/Q/limit/D/feeVersion/filledBase/cumQuote/feeCharged/nextFillSeq/remainingLocked/status`。`filledBase <= Q`，锁资、可用、费用账户均非负。`CLOSED/EXPIRED_UNLOCKED` 为锁终态；同一订单摘要不能重新建锁。
5. 名义金额 `N=qBaseAtoms × priceQuoteAtomsPerWETH / 10^18`，要求合法网格且结果整除。乘法检查 256 位边界或使用有明确定义的宽乘除，不在 Go 中先截断成 int64。价格必须同时不高于买限价、不低于卖限价；基线取 maker 限价，V 校验声明的 maker 是双方之一、执行价等于其限价，但无法独立证明其真实到达优先级。
6. 买方累计费用 `F(C)=ceil(C × 10 / 10,000)`，每次收 `F(C+N)-F(C)`，其中 C 为该买订单已经交割的累计名义金额。先累计再作差，避免拆单累计向上取整多收；费率和版本在签名中固定。
7. 单笔执行先显式绑定 `buy.side==BUY`、`sell.side==SELL` 及同一交易对的 base/quote 地址，买锁资产须为 quote、卖锁资产须为 base，不能只检查方向相反。随后买锁 `-N-feeDelta`，卖锁 `-q`，买可用基础资产 `+q`，卖可用报价资产 `+N`，费用可用报价资产 `+feeDelta`；执行标记、双方 nextFillSeq 与累计量同时提交。
8. 对每个白名单 token：`实际金库持币 = Σ用户可用 + Σ订单锁资 + 费用账户权利`，假定没有未分类直接捐赠；若有人直接转币，差额单独记录为未归属，不凭差额给用户加钱。充值提现按真实转入转出改变总权利，内部成交不改变总量。
9. 合约幂等：保存 `executed[tradeId]=payloadHash`；相同身份相同载荷不再改变任何状态，同身份不同载荷拒绝。重复检查须先于 fillSeq 检查，否则重放成功请求会被误报为新序号错误。不得据此把授权出口替换成任何人可伪造 tradeId。
10. 截止 D 关闭未来履约，最终规范前缀越过 D 且相关历史完整才能判定过去有没有履约。最终成功不能再违约；到期解锁不等于赔付，也不追溯撤销已经完成的交割。

链上累计量是当前规范状态，链下 pending 是本地义务分类，两者在观察延迟或重组时可以暂时不同；差异必须带水位。只允许解释得清、可恢复的暂态，不允许以最终对账为由先对外释放可生效风险。

### 4.2 权威与局部事务图

```text
用户签名
   │ 约束授权条款
   ▼
金库 V〔可用、锁资、执行去重、累计量、关闭互斥〕
   ▲                                      │
   │ 受限签名出口/专用中继                 │ 规范块与日志
   │                                      ▼
nonce/原始交易库 ← 结算计划/Outbox ← 撮合复制日志
                                         ▲       │
                         最终锁资准入 ────┘       │ 私有回报/查询投影
链观察器〔块日志、撤销、最终水位、Outbox〕 ────────┘
```

- 撮合可靠边界：约定复制确认的日志位置。相同日志位置不复用，切主接管到已提交位置；同一提交内可派生恢复完整的成交交付，不依赖易失 goroutine。
- 计划边界：消费去重、义务与计划绑定、Outbox 同一个本地数据库事务；计划不改变已经提交的成交条款。
- 外发边界：分配 nonce、确定 calldata/费用上限、记录待签任务；签名出口保存可恢复的原始签名交易后才外发。数据库与 HSM 不存在隐含的全局事务，未知签名任务只能按原任务恢复，不能分配另一笔经济动作掩盖。
- 链上边界：单笔 fill 及其整批调用在 EVM 内原子；receipt 的 status=0 不撤销中继 nonce 的消耗和 Gas 成本。
- 观察边界：整块日志、可撤销变更、观察进度和对应 Outbox 同事务；最终推进需核验祖先关系与完整前缀。最终履约或违约证据作为带稳定身份的命令交回撮合状态所有者，仍经同一日志裁决 pending→settled/defaulted，不让观察线程并发直接改订单数量。重复投递不重复生成领域效果，重组通知不能只依赖 WebSocket 的 removed。

### 4.3 身份与核心交互

| 对象 | 必要字段 | 身份不能替代什么 |
|---|---|---|
| 接入请求 | owner、requestKey、payloadHash、resultRef | 请求幂等不保证链上交割幂等 |
| 订单及锁资 | EIP-712 orderHash、签名、lock 状态、D、规则版本 | salt/签名不是资金；建锁 receipt 也不是最终锁资 |
| 成交义务 T | `tradeId=H(venueId,logPartition,commitSeq,matchIndex)`、双方摘要/序号、q、price、maker、费用版本 | epoch 不是新成交身份，切主重试不改 tradeId |
| 结算计划 | tradeId 集、payloadHash、planHash、依赖、版本 | 新 batchId 不能让旧 fill 重新有效 |
| 交易尝试 | chainId、sender、txNonce、rawTx、txHash、替换关系、签名出口任期 | txHash 随加速改变，不能作唯一经济幂等键 |
| 链观察 | chainId、blockHash、parentHash、number、txHash、logIndex、canonical、finality | 日志位置是观察身份，不是永久成交身份 |
| 对外领域回报 | tradeId、状态、revision、依据块、最终水位 | 同 tradeId 重组后需要新 revision，不能被普通去重吞掉 |

对外结算观察状态的 revision 由观察/回报投影的单一状态所有者在本地事务中分配；最终命令回到撮合日志后，将核销结果交给同一投影合并发布。撮合日志不能另起一个同名 revision 计数器竞争写入。订单回报若另有序列，明确使用独立命名与作用域，不冒充同一成交修订序号。

合约接口为教学抽象：`lockOrder(signedOrder)`、`settleBatch(fills)`、`closeLock(orderHash,expectedFilledBase)`、`expireUnlock(orderHash)`。closeLock 需当前结算角色，且链下先达成关闭条件；合约无法凭 expectedFilledBase 知道是否还有未上链的链下成交，所以信任边界不能省略。expireUnlock 无此角色要求，但必须严格晚于 D；与 fill 的 `<= D` 不重叠。

### 4.4 正常关闭与故障处置的区别

正常撤余量后，只有该订单无 open、无未决义务且最终链投影对齐，才签发 closeLock。若广播关闭超时，锁资仍不得在链下提前按释放增加能力；观察最终关闭后记录真实可用量。

异常到期路径按最终链实际先后处理：截止前已交割则 SETTLED_FINAL；截止后未交割则违约；解锁只返还未花掉的锁资。到期后新建补偿单必须另取同意、另建身份，原义务仍有审计联系。对尚存可执行权利的未知交易，不以手工改表、TTL 或“运维确认”当作链上失效证明。

## 七、唯一工程实践：手工验证一笔 fill 的原子交割

### 7.1 目标与范围

只验证 T1 的检查、双边余额变化、累计费用、执行去重和失败不留半边状态。输入使用已经最终建锁的整数状态；不实现验签算法、复制日志、广播、最终性、批次、撤单、退出或完整 Go 工程。伪代码中的工作副本与一次替换表示单个 EVM 事务的原子语义，不表示 Go 内存复制能够跨库或跨链原子提交。

### 7.2 核心伪代码

```text
settleOne(V, T, caller, chainTime):
    require caller == V.currentSettlementRole
    h = canonicalHash(T)
    if T.id in V.executed:
        require V.executed[T.id] == h
        return DUPLICATE_NO_CHANGE
    W = deepCopy(V)                         # 仅用于手工演算事务回滚
    buy, sell = W.locks[T.buyHash], W.locks[T.sellHash]
    require buy/sell 存在且 ACTIVE，owner 不同
    require buy.side == BUY and sell.side == SELL
    require buy/sell 的 baseToken 均为 WETH、quoteToken 均为 USDC
    require buy 锁桶资产为 USDC and sell 锁桶资产为 WETH
    require chainTime <= min(buy.D, sell.D)
    require T.buySeq == buy.nextSeq and T.sellSeq == sell.nextSeq
    require T.q > 0 且满足 lot，T.price 满足 tick 及双方限价
    require T.maker 是双方之一 and T.price == T.maker.limit
    require T.q <= buy.Q-buy.filled and T.q <= sell.Q-sell.filled
    product = checkedWideMultiply(T.q, T.price)
    require product % 10^18 == 0
    N = product / 10^18
    fee = ceilDiv(checkedWideMultiply(checkedAdd(buy.cumQuote,N),10),10000) - buy.feeCharged
    require fee >= 0 and buy.locked >= N+fee and sell.locked >= T.q
    buy.locked -= N+fee; sell.locked -= T.q
    W.available[buy.owner, WETH] += T.q
    W.available[sell.owner, USDC] += N
    W.fees[USDC] += fee
    buy.filled += T.q; sell.filled += T.q
    buy.cumQuote += N; sell.cumQuote += N
    buy.feeCharged += fee
    buy.nextSeq += 1; sell.nextSeq += 1
    W.executed[T.id] = h
    W.events.append(Settled(T.id, h, T.q, N, fee))
    V = W                                  # 所有 require 成功才提交一次
    return APPLIED
```

canonicalHash 必须覆盖完整结算载荷，不是实际验签或授权的替代；checkedWideMultiply、checkedAdd、ceilDiv 是明确的整数算术原语，须检查边界，ceilDiv 可用商余数法避免 `a+b-1` 的额外溢出。生产合约不能照抄“复制整个金库”算法，也不能让可替换映射引用穿透演算副本。

- [招聘要求](../../../深入/面试要求.txt)、[2026-08-18 面试记录](../../../深入/04-面试记录/面试记录_interview_20260818.txt)、[2026-08-27 面试记录](../../../深入/04-面试记录/面试记录_interview_20260827.txt)：用于选取完整流程、分布式事务与异常交互的追问；记录中的 AI 建议不作为个人事实。
- [EIP-712](https://eips.ethereum.org/EIPS/eip-712)：结构化签名与域隔离本身不提供业务执行去重。
- [ERC-1271](https://eips.ethereum.org/EIPS/eip-1271)：合约钱包验签成功值为 `0x1626ba7e`，有效性可依赖当前状态；若扩展钱包类型，建锁时必须重新验签，不能永久缓存一次成功。
- [ERC-20](https://eips.ethereum.org/EIPS/eip-20)：调用方必须处理 false 返回；decimals、symbol 等元数据不能取代经验证的白名单资产配置，更不能据 symbol 唯一识别资产。
- [Ethereum JSON-RPC](https://ethereum.org/en/developers/docs/apis/json-rpc/)：receipt、status、块标签和日志字段；null 不等于失败，成功不等于 finalized。
- [Ethereum PoS](https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/)：最终性与单纯确认数不同；其他 EVM 网络和 L2 须另定最终性适配，不能复制固定秒数。
