## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| MEV / AMM / 三明治 | 利用纳入排序等机会获利、自动做市池及前后夹击交易。 | 本例不是 AMM 即时定价，外部先买后卖不会自动改 T1 固定价格，但仍有延迟审查与信息套利。 |
| V / 预存锁资 / allowance | 金库、已隔离订单资金及钱包使用额度。 | 在 V 内原子交割，不是结算时依赖公开钱包可变余额拉款。 |
| T1 / WETH / USDC / maker | 原成交、封装 ETH 式基础资产、报价资产和先到挂单方。 | 价格时间优先下 B 为 maker，T1 固定 0.4 WETH×2,000=800 USDC；限价合规不等于真实排序公平。 |
| EIP-712 / orderHash / salt / chainId | 结构化授权、订单摘要、订单区分值和链身份。 | 绑定用户、资产、数量、限价、期限、费用与域，不能当成可任意提现的授权。 |
| bps / feeVersion / 0.8 USDC | 费率单位、收费规则版本和 T1 的买方费用。 | 固定 10 bps，Gas 涨价不允许临时向 T1 用户加收。 |
| 受限签名出口 / signTaskId | 只给允许任务签名的边界和稳定签名任务身份。 | 核对当前任期、来源、目标、方法、载荷和额度，超时沿原任务恢复。 |
| sender / calldata / value / payloadHash | 发送者、调用参数、附带原生币数额和完整载荷摘要。 | 结算签名限制专用账户、目标 V 与零转账 value，不提供通用签名能力。 |
| 角色失陷 / 独立限额 | 授权控制者被攻破与仍由另一可信边界强制的上限。 | 出口自身失陷可绕过离链限额，不能假称基线合约已有额外额度约束。 |
| closeLock / expectedFilledBase | 正常关锁与预期累计交割量。 | 函数白名单不够，还要查链下义务排空；计数无法发现未上链 pending。 |
| epoch / rawTx / 撤权 | 任期、已签原文和链上角色移除。 | 换数据库任期不撤签，撤权需链上生效，仍须核查此前是否已交割或提前关闭。 |
| D / block.timestamp / expireUnlock | 截止、执行块时间和到期解锁。 | fill 可在 D 执行，解锁必须大于 D；暂停不停止链上时间或自动堵住到期出口。 |
| 背压 / 有界队列 / 准入预算 | 限制新增压力、有容量边界的排队及新增风险额度。 | 先停止接纳新义务，不能先确认成交再以积压为由反悔。 |
| fillSeq / 依赖关键路径 / 最终前驱 | 每订单序号、必须串行完成的步骤和已最终交割的先行成交。 | 先挑依赖就绪集合再比期限；跨批前驱最终等待也吃履约窗口。 |
| nonce / UNKNOWN / 交易族 | 专用账户发送序号、未知结果及关联候选。 | 先恢复队头未知槽位，增加协程或盲目换账户不解除订单依赖。 |
| settleBatch / 整批原子 / 模拟 | 批量交割、共同成败与快照预演。 | 大批省固定成本却增等待与失败半径；模拟成功不锁定未来执行状态。 |
| EIP-1559 / base fee / 优先费 / Gas | 交易费用规则、基础费、排序激励和执行资源。 | 费用加速受上限、节奏与累计成本约束，提高报价不保证及时纳入。 |
| 私有发送 / 构建者 / 公开回退 | 非公开交易通道、组织区块者及改走公开网络。 | 引入保密与可用性信任，回退重新暴露信息但仍沿原交易族，不创造新经济动作。 |
| SETTLED_FINAL / DEFAULTED_UNSETTLED / 最终前缀 | 最终交割、最终未交割违约及终局历史。 | D 前执行可 D 后最终确认；最终越过 D 且历史完整才判违约，锁资返还不算赔付。 |

## 把整篇文章压缩成一个故事

T1 已由撮合日志固定：A 买 B 的 0.4 WETH，B 先到，价格 2,000，货款 800 USDC、买费 0.8 USDC。有人看见待上链 calldata 并在外部市场先买后卖，不会像改 AMM 池储备那样自动改变这份货款；但构建者可以延迟纳入，撮合方可以偏袒到达顺序，公开订单也可能被用于信息套利。V 能检查授权、限价、数量和资金，不能独立证明谁真正先到或保证 T1 及时入块。

面对密钥风险，签名出口只接受有原日志依据、依赖满足、金额费用在限额内的当前任期任务；关锁还必须核验没有未履行义务，而非只认函数名。若出口自身失陷，离链限额未必还有效，须按既有权限撤权并接管旧 rawTx，不能换 epoch 就当风险没了。面对拥堵，先背压新准入与新撮合，保留观察、撤余量和旧义务交付资源，再按依赖就绪、期限和年龄调度；队头 nonce 未知或前驱尚未最终，多开 goroutine 并不能清除阻塞。

最后，小批先发可能比等满大批更适合临近 D 的旧义务，Gas 加速也受累计成本约束，不能把中继成本转嫁为更高的 T1 手续费。私有发送能减少部分暴露，却不保证保密、公平、及时包含或零 MEV。若 T1 在 D 前执行、D 后最终确认，仍应算履约；若最终前缀已过 D 且完整历史无执行，就保留违约并记录到期返锁。安全暂停和容量优化只能限制损害，不能把当前有界退出设计变成无条件交割担保。

**流程位置与核心机制：** 本题跨越撮合准入、结算出口、链上执行和到期退出，先辨明攻击者能改变什么，再讨论限权、暂停和容量保护。基线是单链 EVM 预存金库内的现货订单匹配，不是路由到 AMM 的 swap，也不是结算时从用户公开钱包按 allowance 拉款。T1 沿用总览的 0.4 WETH、成交价 2,000、名义金额 800 USDC、买方费用 0.8 USDC；双方同 D，教学单轮预算为 0.4 WETH，轮末暂停新增撮合，继续结算和撤余量，关闭前不恢复新增撮合。下文的背压策略是一般保护机制，不把主例预算冒称为性能上限或实测吞吐。

## 第 1 层：先说明在这个模型里 MEV 发生在哪里

**面试官：** 链下撮合、链上结算是不是天然没有 MEV？如果攻击者看到了 T1 的待上链交易，会不会像 AMM 一样先买再卖夹走用户的钱？

**面试者：** 不能说没有 MEV，但不能套用 AMM 价格曲线的三明治解释。T1 的买卖订单、数量、成交价和费用已经由可靠撮合日志确定，V 执行的是双方专属锁资之间的内部原子交割；执行时既不向 AMM 查即时价格，也不从公开钱包临时拉款。区块前面有人在外部市场买卖，不会自动把 T1 从 2,000 改成另一个价格。攻击者复制 calldata，也不能因此取得当前结算角色或改变收款归属。

仍然存在三类有价值的操纵面。撮合方在链下掌握接纳、匹配和时间顺序，可能延迟或偏袒订单；区块构建者或网络参与者可以延迟、审查、改变包含顺序，影响能否在 D 前执行；公开的订单和交割信息还可能被用于外部市场抢先交易或信息套利。这些影响不必表现为 V 内同一次调用被夹击。

T1 已提交后，延迟到过期可能让原本可履约的成交变成未交割义务，这是这个有截止窗口模型的真实风险。链上限价和锁资能限制执行的经济范围，不能保证交易一定被纳入，更不能证明链下排序公平。因此需要分别讨论资产授权安全、撮合公平与履约活性，而不是用“链下撮合，所以无 MEV”概括三者。

## 第 2 层：签名限制了价格，为什么仍要信任撮合排序

**面试官：** 既然链上检查限价，用户也签了订单，撮合方即使想偏袒别人，最多不就是按用户同意的价格成交？为什么还说有信任风险？

**面试者：** 用户签名给出了允许交易的边界，不代表用户同意平台随意破坏已经公布的价格时间优先规则。EIP-712 订单绑定 owner、资产、方向、数量、限价、salt、D、费率及规则版本，签名域还绑定 chainId、V 和域版本。V 以订单摘要创建专属锁资，并检查数量、价格、序号、锁状态和重复执行，所以结算角色不能把“买 WETH”解释为“任意转 USDC 到任意地址”。

但合约没有看到可信的全量接入队列，无法凭一个 fill 证明哪个订单真实先到、撮合是否跳过更优价格、哪个用户被故意拖延。基线让 V 检查声明的 maker 属于双方，执行价等于该 maker 限价且满足双方限价；它仍然不能独立证明被声明为 maker 的那一方确实具有时间优先级。tradeId 即使看起来按日志位置生成，也不能让 V 自动判断这就是唯一合法日志。

在正常 T1 中，卖方 B 先到，maker 限价 2,000，所以条款固定为 800 USDC 加 0.8 USDC 费用，重试绝不能改成 2,010。另一个独立攻击变体中，失陷角色可能为尚未被链上执行占用的序号构造限价范围内但违反真实顺序的匹配，错误声明 maker，或者偏向攻击者有合法签名的对手订单；这可能在合约约束内造成用户经济损失。不能因为“没有超过买方 2,010 的限价”就称作规则正确。

当前模型靠可信撮合日志、受限签名出口、权限与审计减少这类风险，不提供链上公平性证明。若要改为可验证排序、链上承诺或其他公平机制，需要改变协议和证据输入，并评估信息暴露及延迟代价，不能把它们当成现有 EIP-712 自带的能力。

## 第 3 层：受限签名出口怎样限制角色失陷的损害

**面试官：** 链上证明不了公平，那么受限签名出口具体限制什么？如果结算角色失陷，哪些损害仍然可能发生？

**面试者：** 受限签名出口的价值是把可签动作收窄，并让每次动作都有可恢复的依据，而不是给它一个“验过签所以可信”的名称。服务实例不直接持有可任意操作的私钥；出口只接受当前任期的任务，核对 chainId、专用 sender、目标 V、允许的方法、零外部转账 value、计划来源、payloadHash、订单依赖和规则版本，并限制单笔或滚动窗口内的数量、名义金额、Gas 与费用。未知签名任务要按原 signTaskId 恢复，不能绕开限额另开任务。

这些限制应避免把 exit 变成通用签名 API，也不能只在 API 层做一次、让其他路径直接调用私钥。额度若跨实例共享，预留和核销本身需要耐久且并发安全；多实例各自限额可能把总上限放大。closeLock 不能只检查函数名在白名单，还要验证无 open、无未决义务、最终投影对齐的关闭证据，因为 V 无法凭 expectedFilledBase 看见链下尚未交割的义务。

即使如此，仍须分清失陷范围。普通结算进程失陷但受限出口完好，来源与规则检查可以拦住大量非法任务；如果密钥或签名出口本身被控制，离链限额也可能被绕过。最后只能依赖 V 真正执行的用户授权、角色、锁资、数量、限价、费率、序号和幂等约束。若希望某项限额即使出口失陷仍有效，它必须由独立可信边界或合约强制；给现有基线额外增加链上额度就是显式的条件变化，不能默认已经具备。

当前结算角色没有任意提现权限，也不能通过 fill 任意改写 owner 或多花锁资，但可能违规匹配、选择有利于攻击者的合法对手订单、拒绝服务或提前 closeLock。尤其提前关闭时，如果链上累计量与它传入的 expectedFilledBase 一致，合约并不知道还有链下 pending，锁终态就可能阻断既有义务。结算角色之外的治理或升级权限若另外失陷，风险还可能更大，不能用结算接口的限权替整套管理员权限背书。

## 第 4 层：检测到失陷以后怎样暂停，暂停会牺牲什么

**面试官：** 角色可能提前关闭锁资，那发现异常后直接暂停所有功能、把数据库 epoch 换掉，不就能保住资金吗？

**面试者：** 不够，而且“暂停所有功能”可能把履约与退出一并伤害。应先分清离链能立即停止的动作和必须通过链上权限才能改变的动作。离链可以停止受影响范围的新增撮合与新签名，隔离异常任务、保全日志，既有义务不能删除。数据库 epoch 只围住本地写入；已经签出的 rawTx 不会因 epoch 改变自动失效，旧主仍可能广播。

要阻断失陷地址未来对 V 的调用，需要通过既有授权机制切换或撤销当前结算角色，并跟踪这笔权限交易的规范性与最终性。在此之前，历史已签交易可能抢先执行；撤权以后也要核对此前是否已发生 fill 或 closeLock。不能因为收到一次撤权 receipt 就清空旧交易族，更不能把撤权称为撤销过去的资产交割。

当前公共接口并没有默认赋予一个可暂停所有路径的万能开关。若设计暂停机制，需要明确它究竟限制建锁、settleBatch、closeLock 还是提现，以及谁能启动、解除。尤其基线允许任何人在 `block.timestamp > D` 触发 expireUnlock，不能悄悄把它改成只有平台批准才可退出。只暂停离链服务或撤销结算角色，也不会停住链上时间和这个到期退出条件。

暂停确实有代价：新成交停止、原 pending 等待，正常结算也可能错过 D；若把 closeLock 一并阻断，正常撤余量释放会延迟。故障恢复后不能补签一个过去时间戳绕过期限。安全响应应优先缩小受影响权限和风险范围，但若无法证明结算出口仍安全，就宁可明确承担停止服务与违约处置成本，也不能继续扩大暴露。权限限额的作用是限制这段响应窗口的损害，不是许诺任何暂停都无损。

## 第 5 层：链上拥堵时为什么先保护窗口而不是堆工作线程

**面试官：** 即使没有攻击，Gas 上涨和积压也会让 T1 错过 D。你刚才说暂停有代价，怎样在真正过期前发现风险，难道多开几个结算 goroutine 不行吗？

**面试者：** goroutine 只能增加本地并发，不能制造区块空间、消除专用账户的 nonce 阻塞，或者越过共享订单的依赖。容量保护要围绕订单有效交割窗口，而不是只追求每秒能生成多少计划。

对一笔候选成交，先看双方 D 的较小值；主例双方同 D。再评估从可靠提交到取得执行机会的关键路径：计划与组批等待、受限签名队列、专用账户前置 nonce、可能的费用替换、链上包含延迟、依赖前驱和安全余量。基线保守要求共享订单的跨批前驱已经最终交割，所以若后继要等前驱最终性，这段等待也必须计入；未最终的前驱与后继只能同批按序执行或先等待，不能为了清队列偷偷跨批流水化。

可以把准入原则表述为“到 D 的保守剩余窗口，大于这条关键路径的保守预算及余量”。这不是精确承诺，也不是凭空设一个固定秒数：链上包含和最终性有不确定性，需要结合该网络观测、费用政策与故障状态估计，无法可信估计就收紧或停止新增风险。执行是否合规以块时间戳为准，不能只用服务器墙钟倒计时；最终规范前缀时间戳严格越过 D 且历史完整，才足以排除未来及漏看的过去履约。

还要分清两个时限。fill 必须在 `block.timestamp <= D` 的块中执行，证明它最终成功可以发生在 D 之后；不能把“D 前尚未最终确认”直接当成违约。但准入为了避免临界失败，可以预留更保守的观察和处理余量，跨批前驱的最终等待也确实可能挡住后继。

当旧义务的窗口被积压侵蚀时，先停止接纳新的风险、继续交付已提交义务，再优化局部执行。把已经确定的 T1 删掉以降低 pending，或者在 D 已经不够用时继续高吞吐成交，都是把技术积压转成没有披露的违约风险。

## 第 6 层：怎样把窗口判断落到背压与调度顺序

**面试官：** 窗口已经不足，具体对谁背压、优先处理谁？按 D 从近到远发交易，是否就能解决到期问题？

**面试者：** 先控制义务进入速度，再调度既有义务，且调度必须服从订单依赖和 nonce。单纯按 D 排序，可能把 fillSeq=2 放到 fillSeq=1 前面，结果整批失败，反而浪费最后的窗口。

入口应有有界队列和按风险范围设置的准入预算，不能让内存队列无限增长。订单进入撮合前，既要确认最终锁资，也要确认当前容量能接受新增承诺；已提交前的命令如何拒绝或停止，由权威接纳和日志顺序裁决，不能先确认成交再用背压反悔。容量变化导致停撮合，也应有明确的顺序边界，使并发的 fill 与撤单都能说明是否在暂停前被裁决。主例的单轮暂停是教学边界，不是把已提交成交撤销。

对已提交义务，先建立按订单的依赖图，选择满足前驱条件的可执行集合，再在其中按剩余期限和等待年龄分配资源。专用账户还要优先处理阻塞队头的未知 nonce，否则后续交易即使 Gas 更高也未必能越过它。同批可以容纳有依赖的连续 fills，但要保持拓扑顺序和整批原子语义；跨批必须遵守前驱最终条件。多个独立订单可以合理并行，不能把同一订单拆给多个工作者就当作独立。

控制面和观察面也要保留资源：撤余量命令继续经撮合日志裁决，防止更多 open 变成义务；链观察、最终证据回传、nonce 查询不能被新请求淹没。撤余量只是减少未来风险，不会释放 pending 对应锁资；正常 closeLock 仍等已有成交最终履约，不能把“保护撤单”做成提前放走资金。

如果故障或链停摆使所有窗口都不可控，背压只能阻止新增暴露，不能保证旧 T1 一定履行。待最终前缀严格越过 D、完整核查没有执行，证据经同一撮合日志把 pending 转 defaulted；若已执行则转 settled，两者互斥。承认这条边界比宣称队列最终总能清空更重要。

## 第 7 层：吞吐与成本优化怎样不破坏既定保护

**面试官：** 先背压能控制风险，但旧义务仍要尽量在 D 前交付。批次越大越省 Gas、费用加得越高越快，是不是应该优先把批次与 Gas 都拉满？

**面试者：** 不是。批次、费用和发送并行度都要受失败半径、截止窗口与可承受成本约束。先保证计划经济条款不变，再优化承载这些条款的尝试；不能为了省钱重新定价、改变费用版本或把 T1 换成另一笔成交。

大批能摊薄调用开销，但需要等更多 fills，增加排队延迟，也更容易因为一笔过期、锁状态变化、依赖不满足或 Gas 不足使整批回滚。基线不支持“捕获单笔失败后继续”，所以组批要限制估算 Gas、执行复杂度、批大小和最晚等待时间，并在发送前检查期限与依赖。模拟只能减少明显错误，模拟时的状态不锁定未来区块，不能把模拟成功当作履约证明。临近 D 的可执行旧义务可能值得用小批先发，未必等待凑满。

失败后根据确定原因隔离问题计划，按原 tradeId 和载荷拆批重试，同时保持订单顺序；未知结果先查原交易族，不能直接把同一义务塞进多个不受控发送账户。专用 nonce 的原始签名交易先持久化再外发，替换版本也要完整归档。增加发送账户会增加权限、nonce 和重组恢复复杂度，且不解除共享订单依赖；只有明确分配独立工作并评估代价时，才是可讨论的条件变化。

费用上限要同时限制单次最高成本、连续替换节奏和累计开支，配合中继原生币储备。EIP-1559 费用策略受 base fee、优先费和网络规则影响，不能承诺出任意高价就必定纳入。receipt 失败仍可能消耗 nonce 与 Gas，不能无限自动重试。T1 的 0.8 USDC 是签名固定的交易费用，不会因为中继付了更高 Gas 就向用户临时增收。

这些优化应按端到端交割窗口评价，而不是只看广播速度。当前材料没有性能测量，不能给出“批次扩大几倍、吞吐必定增长几倍”之类结论，更不能用此类推测覆盖截止失败风险。

## 第 8 层：私有发送和暂停恢复能否形成无损安全承诺

**面试官：** 如果再加私有交易通道，降低公开暴露，故障时暂停，恢复时按你说的背压和组批推进，是否就能保证没有 MEV，而且每笔已成交都必然结算？

**面试者：** 仍不能。私有发送是减少某些订单流公开暴露的选择，不改变 V 的授权边界，也不证明链下撮合公平。它引入对中继或构建者的可用性、保密和包含行为的信任；对方可以拒收、延迟或泄露，不能保证在 D 前纳入。若保留公开通道回退，必须说明回退会重新暴露信息，并继续使用已归档的交易族和 nonce 规则，不能在两个通道各造一份经济动作。

恢复时也应分层验证：当前签名和合约角色可信，旧 rawTx 与未知 nonce 已纳入接管，观察前缀完整，已提交义务及依赖可恢复，剩余期限允许受控交付。先恢复必要观察与既有义务，再逐步恢复新增准入。单纯取消报警或重启签名器，不代表旧攻击窗口已经关闭；历史已经签出的有效交易还要跟踪，最终证据继续经稳定身份命令交回撮合所有者，不能由恢复线程直接改数量。

当前基线能强制的是：在合约约束成立时，不越过用户资产、数量、限价、期限和费率边界；同一成交不重复交割，双边资产在同一事务内变化。它依然信任撮合排序和受限角色不提前关闭，且存在审查、拥堵、权限响应延迟和到期退出带来的履约失败。已成交的 T1 即使最后未交割，也保留原条款和违约事实；到期解锁只是返还未花掉的锁资，不是自动赔付，更不是原成交从未发生。

若业务要求所有链下成交无条件交割，必须改变当前条件，例如重新设计到期退出与链上成交承诺之间的关系，或引入明确抵押、信用与补偿责任，并另外分析资金占用、退出权和治理风险。不能靠私有发送、更多 goroutine 或“最终一致”四个字把当前模型升级成无风险保证。

## 本题收束

- **讲透的机制：** 分开分析签名资产边界、链下排序信任和链上包含活性；受限签名出口缩小动作与额度，当前角色在执行处围栏；失陷响应保留历史义务并承担暂停代价；以 D、订单依赖、专用 nonce 和最终性等待构建窗口，先背压再优化批次与成本。
- **最容易答错的边界：** 本模型不走 AMM，也不依赖用户公开钱包 allowance；签名和限价不证明价格时间优先；角色不能任意提现仍可能违规匹配、提前关闭或拖延；数据库换 epoch 不撤销旧签名；暂停不停止链上时间；D 前执行可以 D 后才最终确认，不能提前误判违约。
- **反例：** 系统看到积压后继续高速确认成交，假定稍后提高 Gas 总能清完；同时把共享订单的后继 fills 跨批并行。前驱尚未最终、队头 nonce 又未知，后继批次失败或无法纳入，D 后锁资可以到期解锁。增加吞吐没有履行旧义务，反而制造更多违约。正确方向是先限制新增承诺，按依赖处理原交易族、保留执行证据；最终无法履约时如实记录违约。该反例用于检验机制，不是性能实验结论。
