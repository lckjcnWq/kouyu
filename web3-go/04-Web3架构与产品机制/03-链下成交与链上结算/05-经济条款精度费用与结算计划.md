# 大问题 5：怎样把链下成交转换为不变价、不多收的链上结算计划？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 清算 / 结算计划 | 把成交承诺换算成可核验的整数资产增减。 | 只落实 T1 的原条款，不重新决定价格、费率或交易对手。 |
| V / T1 / maker | 金库、本例成交和先到挂单方。 | T1 买卖 0.4 WETH，按 B 的 2,000 限价成交，金库内部记权利而非两次独立转账。 |
| WETH / USDC / atoms / micro-USDC | 两种资产、最小整数单位和百万分之一 USDC。 | WETH 为 18 位，USDC 为 6 位；0.4 WETH 表示为 400000000000000000。 |
| q / P / N | 基础数量、每 WETH 的报价资产价格、货款名义金额。 | N=q×P/10^18；P=2000000000 micro-USDC/WETH，得到 N=800000000 micro-USDC。 |
| lot / tick / 整除 | 数量步长、价格步长和没有舍弃余数的除法。 | 两步长分别为 10^14 WETH atoms、10^4 micro-USDC/WETH，最小合法货款为 1 micro-USDC。 |
| float64 / big.Int / 宽乘除 | 近似浮点、可变大整数和避免中间溢出的计算。 | 金额不经 float64；Go 大数不能共享指针边哈希边修改，合约也须检查边界。 |
| bps / C / F(C) / ceil | 万分之一费率单位、累计货款、累计应收费和向上取整。 | F(C)=ceil(C×10/10000)，本例费率 10 bps，不是 10%。 |
| feeDelta / expectedCumQuoteBefore | 本次增收费用和预期执行前累计货款。 | 每笔收 F(C+N)-F(C)；合约依据自己的累计状态重算，不盲信计划。 |
| 最大锁资 | 按整单最高允许成本留够资金。 | A 限价买 1 WETH，锁 2,010 货款加 2.01 最大累计费用。 |
| fillSeq / 订单前驱 | 同一订单成交的序号和必须先履行的成交。 | 前笔未交割，后笔不能拿旧 C 改算费用或跳号执行。 |
| tradeId / payloadHash | 经济义务身份和完整规范载荷摘要。 | 同 T1 换机器仍是原载荷，改成 0.5 WETH 或换资产就构成冲突。 |
| planHash / batchId / txHash | 计划摘要、批次标识和签名交易哈希。 | 拆批、Gas 加速可以改变这些外层身份，但不能改变各笔成交及其 fillSeq。 |
| chainId / 编码版本 / decimals / symbol | 链身份、字节组织规则、精度和展示名称。 | 哈希要固定类型顺序与域；不能直接依赖 JSON 格式，也不能凭同名 symbol 换资产。 |
| Inbox / Outbox / ack | 消费记录、待发记录和消息确认。 | 消费完成、原计划和待发任务同本地事务保存；先标已见再崩溃会漏执行。 |
| D / 版本升级 / 终局核查 | 截止时间、规则更换及最终履约检查。 | 升级不改旧授权；旧版被暂停可能损失履约机会，不能把违约包装成安全重试。 |

## 把整篇文章压缩成一个故事

撮合日志已经为 A、B 提交 T1：本轮预算只成交 0.4 WETH 后暂停，B 是 maker，价格 2,000 USDC/WETH。清算员不是再询价，而是把已承诺的交易算成执行清单：用 WETH 的 18 位整数数量乘每 WETH 的 micro-USDC 价格，得到 800 USDC 货款；买方费率 10 bps，对应 0.8 USDC。清单要求 A 锁资减 800.8、B 锁资减 0.4 WETH，同时给双方和费用账户相应金库权利。

为了避免把同一订单切碎后多收费，清算员按累计货款算总费用，只收本次与上次的差。单独的微额取整演示中，第一笔 1 micro-USDC 收 1 micro-USDC 费用，再增加 1 micro-USDC 时新增费用为 0，而不是再收 1；这不是把 T1 改成微额订单。同订单后笔必须等前笔累计状态成立，不能为抢先成功重算价格或序号。写计划与发消息之间若崩溃，就从同一事务保存的原计划和 Outbox 恢复，重复输入还须核对完整载荷。

最终，无论 T1 换批次、加速交易还是重启生成计划，800 货款、0.8 费用、双方身份和序号都应保持不变；变成 0.5 WETH 就要隔离为冲突。费率升级也不能覆盖旧签名版本，前驱违约更不能靠跳号补洞。计划正确只代表经济条款可执行地表达出来，不代表已广播、已最终交割，更不代表已经做过真实跨语言测试。

**流程位置与核心机制：** 承接撮合日志已经提交的成交义务，生成可重试的整数交割计划。本题负责经济条款、数量精度、费用累计与计划身份，不替代合约执行检查或广播终局判断。固定采用总览的金库内结算模型和 T1 案例。

## 第 1 层：成交结果不能直接当转账参数吗？

**面试官：** 撮合已经给出了 T1，为什么还要经过清算和结算计划？计划具体计算什么？

**面试者：** 撮合确定“谁与谁、按什么价格、成交多少、采用什么规则”，清算把这个经济事实转换成执行处能够精确核验的资产增减。二者责任不同，但不能各自再决定一次价格或费率。

在这个模型中，本轮预算 0.4 WETH、轮末暂停新增撮合，所以 T1 是 A 买入、B 卖出 0.4 WETH，maker 价格为 2,000 USDC/WETH。计划计算名义金额 800 USDC、买方费用 0.8 USDC，指定买方锁资扣除 800.8 USDC、卖方锁资扣除 0.4 WETH，增加 A 可用 0.4 WETH、B 可用 800 USDC和费用账户 0.8 USDC。不是直接调用两个互不相关的 transfer。

计划必须携带 tradeId、双方 orderHash、双方 fillSeq、数量、价格、maker 归属、费率及规则版本，绑定撮合提交位置。链上不接受“当前市场价是多少就按多少结算”；撮合后的行情变化不能改变 T1。

## 第 2 层：这些小数如何转换成确定的整数？

**面试官：** 你说 0.4、2,000 和 0.8 都必须精确表达，Go 和合约怎样计算出完全相同的值？

**面试者：** 先统一量纲。数量 q 用 WETH 最小单位，T1 为 `400000000000000000`；价格 P 用“每 1 WETH 需要多少 micro-USDC”，为 `2000000000`。名义金额是 `q×P/10^18=800000000` micro-USDC，费用是 800000 micro-USDC。

本专题的数量步长为 `10^14` WETH atoms，价格步长为 `10^4` micro-USDC/WETH，最小合法乘积除以 `10^18` 恰为 1 micro-USDC，因此网格内金额精确整除。校验步骤是先检查正数、上限和网格，再做宽乘除并核对余数，不能对任意输入先截断后声称精确。

Go 使用有所有权约束的 big.Int 或经过验证的定宽整数实现；合约使用防溢出的运算。Go 中 big.Int 是可变对象，不能把共享指针一边交给哈希线程一边继续乘除。解析十进制输入直接按位转换整数，不经过 float64。

## 第 3 层：若每次费用都向上取整，拆单会不会多收费？

**面试官：** 金额能精确计算了，但 10 bps 费用未必整除。如果把一笔订单拆成很多 fill，每笔都 ceil 会怎样？

**面试者：** 独立逐笔 ceil 可能让拆单多收，所以采用签名绑定的累计规则：设买订单已交割累计名义金额为 C，累计应收 `F(C)=ceil(C×10/10000)`，本次只收 `F(C+N)-F(C)`。

例如累计从 0 到 1 micro-USDC，F 从 0 变为 1；再增加 1 micro-USDC，F 仍为 1，第二笔费用是 0。若两笔各自向上取整就会收 2。这个极小数值用于演示费用规则，不表示 T1 的网格、价格或成交规模发生改变。

买方建锁按整个订单的限价最大名义金额计算最大累计费用。A 买 1 WETH，限价 2,010，对应 2,010 USDC与 2.01 USDC费用，所以锁 2,012.01。因为每笔买入价格不超过限价，且累计基础量不超过 1，累计扣款不会超过这个上界；前提是合约始终执行相同费用版本和累计公式。

## 第 4 层：累计公式让后笔依赖前笔，计划还能独立重试吗？

**面试官：** 你在计划里算出了 feeDelta，但链上前一笔还没执行，当前 C 不一样，怎样避免一上链就金额不一致？

**面试者：** 对同一个买订单，撮合日志为每笔成交记录确定的 fillSeq，并保存按已提交前缀计算的累计报价金额。计划中可以包含 expectedCumQuoteBefore 作为诊断和一致性约束；执行合约仍以自己的累计状态重算本笔费用，不盲信外部 feeDelta。

如果前序成交还没交割，后序 seq 必须等待，不能拿当前链上 C 重新计算一个“能执行”的新计划绕过它。前笔成功后，链上累计量应与计划期待的前缀一致，本笔得到相同 feeDelta。如果不一致，说明缺笔、重复载荷、版本或观察水位有问题，要停止该订单链而不是改金额。

单笔可独立于其他不共享订单的成交重试，但不能脱离自己的订单前驱。如果前序最终违约而后续还未交割，当前基线没有跳号接口；后续也不能悄悄被重编号，须进入终局核查及未履约处置。这是有序模型的明确代价。

## 第 5 层：tradeId、planHash、batchId 与 txHash 怎样区分？

**面试官：** 既然计划会进批次，也可能多次发交易，用哪个 ID 防止同一笔经济义务变成多笔？

**面试者：** tradeId 标识经济义务，由不复用的撮合日志分区、提交位置和匹配序号等稳定字段生成；切主后重放仍得到同一个 tradeId。payloadHash 绑定 T1 的完整规范载荷，不能只哈希数量而遗漏收款人、资产地址或规则版本。

单笔计划或多笔有序集合可以得到 planHash，批次另有 batchId。拆批可以改变批次与集合哈希，但不改变各笔 T 的身份、载荷和 fillSeq。txHash 标识一次签名交易，Gas 加速或换中继可能改变它，所以不是经济幂等键。

Go 和合约必须明确同一套编码：字段类型、顺序、固定宽度、数组顺序、chainId 和合约域。拼接可变长度字符串容易出现歧义；JSON 的字段顺序与格式化也不适合直接作为跨语言共识哈希。记录 hash 算法和编码版本，持久化规范载荷，而不是只留下一个无法解释的摘要。

## 第 6 层：计划生成与交付之间崩溃，怎样不丢或重复生成？

**面试官：** 有了稳定身份，清算服务消费 T1 后，写完计划还没发消息就崩溃，恢复如何知道该做什么？

**面试者：** 在清算服务的一个本地数据库事务中完成消费身份登记、校验成交载荷、插入或读取原计划、绑定 tradeId 和写入 Outbox。事务未提交就重做；已提交则 Outbox 负责继续投递。对同一 tradeId 的再次输入必须比较 payloadHash，完全一致才返回原计划，冲突则隔离报警。

这里的 Inbox 不能只是先插一个“已见过”就 ack。如果采用 pending/applied 两阶段，恢复器必须扫描 pending 并完成原事务；否则进程在“标记见过”之后崩溃会永久跳过计划。最简单的边界是把消费完成标记和业务结果放在同一事务。

Outbox 重投可能产生重复消息，发送者和合约仍分别按计划身份与 tradeId 去重。这套机制覆盖的是数据库内部提交和可靠交付，不证明 HSM 签名与链上调用已经成功。广播与最终性有独立状态，不能在发出 Outbox 后立刻将 T1 改为已交割。

## 第 7 层：费率升级时，待结算计划是否应该使用新版本？

**面试官：** 你保留旧计划，但平台升级了费率或 token 精度配置。让它继续执行旧版本，会不会不符合当前系统规则？

**面试者：** 已经由用户授权并由撮合提交的条款不能被“当前配置”覆盖。订单签名绑定费率和规则版本，成交日志保留使用的版本，计划重试使用同一版本；合约必须仍能验证相应旧版本，或者协议明确禁止该类订单继续成交并按既定退出规则处置。

版本升级应先停止受影响订单的新增撮合，排空或处理旧义务，再切换签名域和执行配置。不能先停掉旧验证器、让所有旧成交无法结算，再称其为正常重试。代币 decimals 在本模型中属于白名单资产配置，不按 symbol 自动跟随同名资产更新；新地址就是新资产。

如果旧版本存在严重安全漏洞，暂停可能是必要选择，但要承认它牺牲结算活性，甚至导致 D 后违约。修复后的新交易若更改用户授权条件，必须重新取得同意；原 T1 的历史、失败原因与新补偿记录都要保留。

## 第 8 层：怎样验证计划正确，而不只验证几个正常数字？

**面试官：** 这些规则听起来完整，怎样用反例说明你的清算方案真的没有靠重试偷换经济条件？

**面试者：** 我会从不变量和跨语言边界反推检查。先核对 T1：800＋0.8 从 A 锁资扣除，800 到 B、0.8 到费用账户，0.4 WETH从 B 锁资到 A，逐资产守恒；再核对累计费用的拆分和合并结果一致，最终总费用只依赖累计报价金额。

然后固定 T1 的 tradeId，多次重建计划，改变机器、重启、批次或发送 nonce，要求载荷完全相同；若将数量从 0.4 改为 0.5、换资产地址或改费率，必须得到冲突而不是新计划。反向输入超大整数、非整除网格、负数文本与溢出乘积，应在生成可执行计划前拒绝。

最后推演 T2 抢在同订单 T1 前执行，应该因 seq 被阻断，不能为了成功而按旧 C 重定费用。这里给的是验证方法和手工预期，不声称已经运行跨语言测试或完成真实合约证明。

## 本题收束

- **讲透的机制：** 清算固化成交条款，整数表达量纲，累计费用作差，稳定身份与不可变计划跨重试保持一致。
- **最容易答错的边界：** txHash 不是成交身份，重新计算不是重新定价，累计费用意味着订单依赖；Outbox 成功不代表资产终局。
- **反例检验：** 将 T1 放入另一个批次并加速交易，若计划价格、数量、费用版本或经济身份改变，这不是同一义务的安全重试。
