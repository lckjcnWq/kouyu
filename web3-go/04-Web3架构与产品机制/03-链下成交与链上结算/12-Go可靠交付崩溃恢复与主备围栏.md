## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| T1 / 可靠复制提交 / WAL | 原成交、满足故障承诺的复制确认及预写日志。 | 单机 WAL 或异步备份不自动保证单机丢失后不丢已确认成交。 |
| V / A / B / WETH / USDC | 金库、买卖双方、封装 ETH 式基础资产与报价资产。 | T1 消耗 A 的 USDC 锁资与 B 的 WETH 锁资；Go 重启不能自己增加金库可提权利。 |
| tradeId / payloadHash / fillSeq | 成交身份、完整载荷摘要和每订单序号。 | 恢复同一笔 0.4 WETH、800 USDC 加 0.8 买费，切主任期不生成新身份。 |
| open / pending / settled / defaulted | 未成交、待交割、已交割和违约分类。 | T1 提交后 open=0.6、pending=0.4；重启或尝试失败不回到 open=1。 |
| Outbox / Inbox / ack | 待发档案、消费去重档案和确认。 | 发送可至少一次，消费结果与完成标记同本地事务，提交后才确认。 |
| ACID / EVM / 局部边界 | 数据库事务属性、链执行环境及各自共同提交范围。 | 计划、签名、链执行、观察分开恢复，没有全局一次提交。 |
| big.Int / 接收者 / 深拷贝 | Go 可变大整数、被运算写入的对象及独立存储副本。 | 用 new(big.Int).Set(source) 等复制，不能原地改订单数量来算货款。 |
| goroutine / channel / slice / map | 协程、通道、切片和映射。 | 传引用不转成不可变值；嵌套金额也得复制，后台快照不能读写同一可变结构。 |
| S / L / (S,L] / 快照 | 快照提交位置、已提交上界、待回放区间及一致状态副本。 | 先验证完整快照，再按旧规则回放，不应用未提交尾部或跳过已提交缺口。 |
| 不可变发布 / 确定性回放 | 发布后不再修改及按原输入规则恢复结果。 | 回放不重新按当前时间过期、按新费率计算，也不直接调用签名器外发。 |
| chainId / sender / nonce / planHash | 链、专用发送者、发送槽位和计划摘要。 | 槽位唯一且跨任期保留，账户不能另供未受协调的脚本人工转账。 |
| signTaskId / HSM / rawTx / txHash | 签名任务身份、硬件签名模块、签名原文和交易哈希。 | 先存可恢复签名原文才准外发，签名超时按原任务查询。 |
| NONCE_RESERVED / SIGNED_DURABLE / UNKNOWN | 已预留槽位、签名已耐久和结果未知阶段。 | 这些状态决定恢复动作，查无回执不能回收槽位或释放锁资。 |
| epoch / 存储围栏 / 签名围栏 | 任期及分别限制写入、签出新交易的检查。 | 旧任期不能新写新签，但已经拿到的 rawTx 不会因此消失。 |
| 当前链上角色 / 撤权 | V 执行时认可的出口及权限变更。 | 最终撤权能挡未来失权调用，却不抹掉此前交割；旧交易仍可能入块花 Gas。 |
| revision / 观察水位 / 最终证据命令 | 状态修订号、链处理位置和稳定身份的终局证据。 | 不能按 tradeId 吞掉修订；证据回同一撮合日志核销数量，不由恢复线程直接改量。 |
| closeLock / D / DEFAULTED_UNSETTLED | 正常关闭、截止和最终未交割违约。 | 恢复运行不等于排清义务；关闭等最终交割，最终过 D 且历史完整才判违约。 |
| 分级就绪 / 失败关闭 | 查询、续交旧义务、新增接单各自放行，以及证据不全时停危险操作。 | 健康检查活着不是资金安全，日志或签名缺口不能靠盲目恢复掩盖。 |

## 把整篇文章压缩成一个故事

Go 撮合服务对 A 回报 T1 已成交后突然崩溃。能让接班人继续承认这笔成交的，不是 A 的截图或内存队列，而是可靠复制日志：双方 open=0.6、pending=0.4，原身份、双方序号、800 USDC 货款、0.8 买费及交付事实一起保存。恢复器选择完整快照 S，重放到已提交上界 L，补发原 Outbox；结算消费者以 Inbox、原计划和后续 Outbox 的本地事务识别重复，不重新撮合一笔 T1。

内存恢复也不能偷懒：快照里的 big.Int、map、slice 若与正在运行的订单共享可变存储，后台写出的“快照 S”就可能混入后来的金额。应在单写所有权边界取得独立副本，回放只重建事实，不顺手广播。另一独立切主场景中，旧主已取得 rawTx 后失去租约，新主须接管旧 nonce 槽位、签名任务与交易族；数据库 epoch 只挡写库，不撤销链上签名，还要在签名出口阻断旧任期新签名，并在必要时按既有权限流程撤销旧链上角色。

新主可以先恢复带水位查询，再受控推进旧义务，最后才按最终锁资、权限和履约窗口恢复新增接单。旧角色即便失权，也要查清撤权前 T1 是否已执行；若旧主曾提前关锁，不能删义务或改表重新锁回。最终证据仍交同一撮合日志核销数量，正常关锁等全部已提交义务最终交割；若最终过 D 且历史完整证实未履约，就记录违约。高可用是接管真实义务并约束旧执行者，不是换主即清空风险或保证所有旧单最终成功。

**流程位置与核心机制：** 本题覆盖撮合提交之后的可靠交付、Go 状态所有权、崩溃回放和主备接管。重点不是重讲广播或最终性算法，而是解释服务消失之后，哪一份耐久事实允许下一任继续履行同一笔义务，以及怎样限制旧主继续制造外部效果。公共基线、状态定义与数值均沿用总览：T1 为 0.4 WETH、成交价 2,000 USDC/WETH、名义金额 800 USDC、买方费用 0.8 USDC，双方 fillSeq=1，主例双方采用同一截止时间 D；教学单轮预算为 0.4 WETH，轮末暂停该交易对新增撮合，继续结算和撤余量，关闭前不恢复新增撮合，不能把 T1 当作无约束持续撮合下自然产生的全部成交。跨批后继保守等待共享订单的前驱最终交割；未最终前驱和后继只能同批有序执行或先等待。各故障变体独立推演，不叠加为一次事故。

## 第 1 层：先找出崩溃以后仍须承认的成交

**面试官：** Go 撮合服务刚告诉用户 T1 已成交就崩溃，重启以后怎样保证这笔成交不丢，也不会再成交一次？

**面试者：** 先把“已成交”的答复绑定到明确的耐久提交条件，而不是绑定到撮合函数返回、写入内存队列或者一次 RPC 返回。在这个模型中，只有撮合权威日志按约定完成可靠复制提交，才允许发布“已成交、待结算”。如果高可用承诺包含单机丢失后不丢已确认成交，那么只在本机写 WAL 或异步复制到备机并不够；必须等满足该故障模型的复制提交条件，不能用低延迟成功回报掩盖耐久性不足。

T1 的同一次权威提交要确定双方 `open: 1 → 0.6`、`pending: 0 → 0.4`，并保存 tradeId、买卖订单摘要、双方 fillSeq、数量、价格、maker 和费用规则。还必须保存可恢复的交付事实：可以直接是同边界提交的 Outbox，也可以是从已提交日志能够唯一派生的交付记录，不能只剩一次 goroutine 调用。这里的原子范围是撮合可靠日志所定义的提交范围，不包括另外的计划数据库、消息系统或 EVM。

提交前崩溃，不能凭客户端曾看见一个临时响应认定成交；提交后即使响应丢失，T1 也已经成为义务。调用方以原请求身份查询，恢复方以原日志位置恢复同一个 T1，不能因为切换了 epoch 再生成新 tradeId。已受理的命令也不等于已经成交：恢复时应读取它的权威处理结果，或按原顺序完成处理，而不是把“请求存在”直接解释为成交。

所以第一道保证是先可靠提交、后确认成交。后面的消息重发和交易重试都只负责把这份已经存在的义务继续向前交付，不负责重新裁决经济条款。

## 第 2 层：提交成功但消息丢失，靠什么交到下一站

**面试官：** 你把 T1 放进可靠日志了，但进程在通知结算服务前就退出；如果重发又碰上结算服务已经处理过，只是确认丢了，怎样同时处理这两个窗口？

**面试者：** 我会把“是否需要交付”保存在耐久事实中，再用至少一次投递与接收端本地去重闭合这两个窗口，而不是让发送成功与成交提交组成一个实际上不存在的分布式原子操作。

撮合侧提交后，交付器扫描未确认的 Outbox，发送稳定的事件身份、tradeId、原载荷及 payloadHash。它在发送前崩溃，记录仍未交付；发送后确认丢失，仍会重发。即使消息系统已经确认接收，也要按约定持久保存发送进度，并保留源日志的重放、缺口补齐能力，不能靠易失游标决定哪些成交永远不再发送。

结算服务收到消息后，在自己的一个数据库事务中完成三件事：插入带唯一约束的 Inbox 身份并核对载荷，绑定 T1 与不可变结算计划，写入后续计划 Outbox。事务提交后才确认消费。事务失败则三者都不成立；事务成功但消费确认丢失，重投命中 Inbox，相同载荷返回已有结果，不重复生成经济动作。同身份不同载荷不是正常重复，要隔离并告警。如果一个计划需要多个成交共同组批，也要保留每笔义务到计划的明确绑定，不能用“某个 batch 已存在”代替逐笔检查。

Inbox 去重只覆盖这个消费者的本地副作用。它既不能证明链上没有执行，也不能取代合约的 `executed[tradeId]=payloadHash`。同样，查询投影接到 T1 的新 revision 时必须允许更新状态，不能只按 tradeId 去重，把后来 INCLUDED 撤销或最终结算回报都吞掉。

这里实际是“撮合提交 → 计划本地事务 → 外发耐久记录 → EVM 事务 → 观察本地事务”几个独立边界。Outbox、Inbox 和 revision 负责恢复边界间的传递，不把这些边界拼成全局 ACID，也不承诺消息物理上只出现一次。

## 第 3 层：消息耐久了，Go 内存里的金额为什么仍可能错

**面试官：** 既然每一站都能重放，Go 服务为了提高效率，直接把订单结构浅拷贝后发给结算 goroutine 和快照 goroutine，可以吗？

**面试者：** 不可以把浅拷贝当成金额隔离。`big.Int` 是可变对象，运算通常把结果写入接收者；复制 `*big.Int` 只是复制指针，直接复制含有大数内部存储的值也不应当作深拷贝使用。结构体中 slice、map、指针还有各自的别名问题。即使使用 channel 发布了引用，也只解决交付的同步关系，不意味着生产者以后修改同一对象就安全。

我会给状态设明确所有权：撮合分区的单写执行者拥有可变订单状态，清算和回报收到的是已提交结果的不可变快照。跨所有权边界的大数用 `new(big.Int).Set(source)` 一类深拷贝方式构造；嵌套 map、slice 以及其中的金额也逐层复制。发布以后不再修改接收者能触及的对象。若使用不可变编码后的整数字节或字符串作消息载荷，解析出的可变大数也由各消费者独立持有，不能又放回共享缓存供多个写者复用。

例如计算 T1 的 800 USDC 名义金额时，不能拿订单限价或原始数量作为乘法接收者做原地计算。应当在私有临时对象上完成乘法、整除、范围和网格检查，再构造新的结果。Go 的任意精度整数也不意味着合约能接收任意大数，计划持久化前仍须检查链上整数边界，不能先转成 int64 或 float64 再补救。

快照也要遵守同一规则。可以在单写者边界取得某个已提交位置 S 的一致性视图，再交给后台序列化；不能让后台遍历仍在变化的 map，或者虽然复制了 map 却继续共享其中的 `*big.Int`。否则得到的“快照 S”可能混入 S 之后的金额，回放时再执行一次就会重复变化。

因此可恢复不只意味着有日志，还意味着快照和日志编码保存的是当时确定的值，而不是以后会被别的 goroutine 改写的引用。

## 第 4 层：快照与日志怎样恢复到同一已提交位置

**面试官：** 你让快照对应提交位置 S，但进程可能在快照写到一半或日志刚追加后崩溃。重启时怎样知道该从哪里继续，避免多回放或少回放 T1？

**面试者：** 我会先关闭对外写入口和外发入口，识别可验证的完整快照与可靠日志前缀，再恢复状态，不能让服务一启动就一边接新订单一边猜旧状态。

快照需要包含分区、提交位置 S、规则与编码版本、内容校验和。快照主体完整持久化、元数据可验证后，才发布为可恢复版本；写了一半的文件不能因为文件名存在就选中。日志截断或归档也必须以快照真正可用及下游仍能恢复为前提，不能快照任务刚开始就删除源日志。

重启时选择完整快照 S，确认复制日志的已提交上界 L，再按序恢复 `(S,L]`。未提交尾部不能当作已确认成交；缺失已提交前缀则停止接管，不能跳过缺口继续。回放使用持久化的规则版本、命令次序和已确定的业务输入，不能重新读取当前时间给历史订单判到期，也不能用新费率重算旧成交。若日志保存了确定的成交结果，恢复时应用结果，不重新用当前订单簿撮合一次来“找回”T1。

回放只恢复领域事实和待交付任务，不在应用每条日志时直接调用签名器或广播 RPC。否则重建内存会产生不可控的外部副作用。领域恢复完成后，再由各自的耐久任务表恢复 Outbox、计划和交易尝试，并以原身份继续。

T1 若在 L 以内，即使客户端没收到确认，也必须恢复为同一份 pending 义务；T1 的发送尝试失败，不会让 `open` 回到 1。快照只证明某个位置的状态，不能替代提交证明；消息确认只证明某段交付，不能允许丢弃尚未履约的义务证据。

## 第 5 层：签名与广播之间的崩溃怎样不丢交易

**面试官：** 内存和任务都恢复了，但旧进程可能已经调用签名器，只是还没记下结果。新进程怎样知道该用哪个 nonce，能不能重新生成一笔交易直接发？

**面试者：** 要把签名任务和交易尝试也做成可恢复状态机，不能把签名当成无副作用的普通函数调用。先为专用发送账户在耐久 nonce 记录中保留唯一槽位，绑定 chainId、sender、nonce、planHash、目标 V、calldata、value 和允许的费用边界，再以稳定 signTaskId 请求受限签名出口。这个账户不能同时供人工转账或另一个未受协调的服务使用，否则数据库中的 nonce 分配并不是账户的唯一外发来源。

可以把尝试阶段理解为：`NONCE_RESERVED → SIGN_REQUESTED → SIGNED_DURABLE → BROADCAST/UNKNOWN → INCLUDED`。签名出口必须先保存可恢复的原始签名交易、对应 txHash 和任务绑定，再允许任何网络出口广播。业务数据库与 HSM 之间没有隐含事务，所以签名出口自身也需要可查询的任务档案：请求超时后按原任务恢复结果，而不是另分配 nonce 并假装前一次不存在。

如果签名已经产生但调用方没拿到结果，只有确认原任务及其外发边界后才能继续。不能假定再次签名必然得到完全相同字节，也不能让临时返回的 rawTx 先经过一个会自动广播的 SDK，再异步补写数据库。对外发送的每个可执行字节版本都必须有耐久档案。加速交易同样先持久化新的签名原文，并保留同 nonce 替换关系；它们仍服务于原经济义务，而不是新成交。

恢复时扫描 nonce 槽位、签名任务、rawTx 与链上观察，补齐缺口。广播超时保留 UNKNOWN，查询不到 receipt 不代表可以回收 nonce 或释放锁资。签名与 nonce 不确定的槽位先隔离，不能靠“取节点 pending nonce 后从头开始”跳过未记录的已签交易。专用 nonce 管理保护的是外发顺序；履约是否已经发生仍由规范链上的执行结果裁决。

## 第 6 层：数据库 epoch 为什么挡不住旧主的链上动作

**面试官：** 你已经有持久任务了。切主时把数据库 epoch 加一，旧主所有更新都带旧 epoch，不就彻底解决双主了吗？

**面试者：** 这只能阻止经过同一数据库条件检查的旧写入，不能撤销旧主已经拿到的私钥能力或原始签名交易。旧交易离开数据库以后，EVM 不会自动查询本地 epoch。旧主即使不能再更新任务表，也可能把旧 rawTx 广播出去；如果发送者仍拥有合约当前结算角色，交易依然可能执行。

所以至少要分三层围栏。第一层是存储围栏：计划领取、nonce 分配、任务推进等写入都检查当前任期，不能只在进程启动时读一次 epoch。第二层是签名出口围栏：服务实例不能直接持有可任意外发的私钥；受限出口在接纳和实际签发任务时检查当前授权任期、允许的 sender、目标、方法、载荷与限额，旧任期不能继续取得新签名。对签名器已经接纳的在途任务，也要有明确停发、完成归档或隔离的顺序，不能假定一次租约失效会使 HSM 正在处理的任务消失。

第三层是执行处权限围栏：V 在执行 settleBatch、closeLock 时检查当前角色。若旧密钥可能失陷，需要通过既有治理或紧急权限切换当前角色，并等待权限变化成为可靠的链上事实。这不是给现有模型临时加一个“epoch 字段”就完成；当前基线靠执行时角色检查阻断失权调用，权限切换自身也有入块、重组和最终性窗口。

正常主备切换可以保留同一专用发送账户，但这意味着历史已签交易仍须接管，不能声称换了数据库主就让它们失效。需要隔离旧密钥时，可按既有权限机制换成新角色地址，新地址使用自己的 nonce 空间；这仍不免除对旧地址历史交易的核查。三层围栏分别限制数据库写、未来签名和链上执行，不能互相冒充。

## 第 7 层：旧签名仍可能有效，新主怎样接管而不丢义务

**面试官：** 既然权限切换也有窗口，旧主手里的 T1 交易可能先于撤权上链。新主该等它失效再接管，还是直接重发 T1？

**面试者：** 先接管事实和义务，再按证据决定外发；不是等旧主“应该死了”就清空旧任务。接管清单应包括已提交义务、每份不可变计划、专用账户全部 nonce 槽位、每个可生效 rawTx 及替换关系、签名器未决任务、完整链观察和当前权限状态。

如果旧角色权限未变、原交易仍符合期限和锁状态，那么它仍可能履约。新主应继续跟踪原交易族，必要时按原 nonce 和受控替换策略推进，不因为换主就重新给 T1 分配另一份成交身份。只有确实需要另一次执行尝试时，也必须保持 T1 的 tradeId 和载荷不变，并结合合约执行幂等、订单依赖及 nonce 状态处理，不能盲目并发外发。

如果最终链上已经撤销旧地址角色，旧地址未来调用不再有结算权限；但这只能约束撤权之后的执行，不能抹掉此前可能已经发生的 T1。旧 EOA 签名交易本身也没有因此从世界上消失，它仍可能被纳入并消耗 nonce、支付 Gas，只是对 V 的失权调用会失败。新主必须核对撤权前的完整规范历史，区分 T1 已交割、只是非最终入块、尚未执行三种情形。

旧主若在撤权前违规 closeLock，锁终态可能阻止 T1 今后履约。这是基线信任边界真实暴露的损害，不能靠新主把锁状态改回去或删掉 T1 来消解。应停止相关新增风险、保存证据，并沿既定的截止与违约路径处理。历史已经存在的义务归新主接管，无论旧发送权限是否还存在。

归根结底，围栏负责限制未来行为；历史核查负责解释过去；义务日志负责保证不能因恢复困难而漏账。三者合起来才构成接管，不是一个锁过期就能完成的动作。

## 第 8 层：恢复服务何时可以重新接单和关闭锁资

**面试官：** 新主已经识别全部旧交易了。怎样定义恢复完成，既不无限停服，也不为了尽快恢复而提前关闭 T1 的锁资？

**面试者：** 我会把“查询可用”“可以继续交付旧义务”“可以接纳新增成交”分成不同的就绪条件，而不是一次健康检查通过就全放开。

首先恢复并校验撮合已提交前缀、规则版本和数量守恒，确认 T1 的身份与 0.4 WETH pending 没丢；其次恢复计划、Inbox/Outbox 和签名任务，确认没有无法解释的 nonce 或可执行签名缺口；再检查当前角色、签名出口围栏及链观察完整性，允许受控推进已有义务。查询可以较早恢复，但必须带当前水位和“待结算”含义，不能用旧缓存宣布最终完成。新增准入还要等待锁资最终投影与有效交割窗口满足要求，不能拿服务存活代替业务安全。

对 T1 来说，新主恢复期间，链下提交本身不会使 A 的 2,012.01 USDC 锁资减少，也不会让 B 的 1 WETH 锁资减少。只有 T1 最终交割证据完整后，观察器才把带稳定身份的最终证据命令交回撮合状态所有者，由同一日志裁决 pending 0.4 转为 settled 0.4，并对重复命令去重；观察线程不能直接并发改订单数量。证据已经落库但该命令尚未提交时，链下数量仍可暂时 pending，必须标明这段交付水位。对应链上最终结果是 A 剩余锁资 1,211.21 USDC、B 剩余锁资 0.6 WETH。若余量撤单也已提交，只是阻止新的 open 成交；仍须等该订单全部既有义务最终交割、最终投影对齐后，才能签发 closeLock。未知发送、服务重启或者旧主失权都不构成提前释放条件。

恢复也有不能自动完成的边界：已提交日志缺口、签名档案缺口、链观察无法确认规范前缀时，应失败关闭相关业务并保留义务；若最终规范前缀越过 D，完整历史又证明 T1 未履约，就把最终违约证据按稳定身份交回同一撮合日志裁决，进入 DEFAULTED_UNSETTLED、pending 转 defaulted，而不是由恢复线程直接改数量，或把任务永久标成“稍后必定成功”。可用性恢复要受事实和期限约束，不能以最终一致为由承诺所有成交都能交割。

## 本题收束

- **讲透的机制：** 可靠日志先于成交确认；Outbox/Inbox 在各自本地事务中保存交付进度；Go 可变大数以深拷贝和不可变发布隔离所有权；快照按已提交位置回放；专用 nonce 与原始签名交易档案先于外发；存储任期、受限签名出口和当前链上角色共同限制双主。
- **最容易答错的边界：** 本地事务不是全局 ACID；channel 不会把 `big.Int` 变成不可变值；数据库 epoch 不会撤销旧签名；撤权不抹去撤权前的履约事实；恢复成功不等于所有旧义务已经完成。
- **反例：** T1 可靠提交后，旧主保存并取得 rawTx，随后失去数据库租约；新主把旧任务删除、恢复 open，又给用户释放锁资能力。只要旧角色仍有效，旧 rawTx 就可能迟到执行，系统已重新承诺同一份资源。正确方案必须保留 T1 和旧交易族，在执行权限、规范历史和终态条件明确前不释放可生效风险。这个反例是机制推演，不是生产事故或工程测试报告。
