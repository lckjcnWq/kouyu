# 大问题 9：批量结算怎样处理订单依赖与局部坏单？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| V / settleBatch / EVM | 金库、批量交割接口和合约执行环境。 | 同一次外层事务按给定顺序执行，不是每个数组项各自独立成功。 |
| 整批原子 / revert / catch | 共同成败、回滚和捕获失败继续。 | 基线不 catch；后一笔失败，本批新写的前笔余额、标记与序号都回滚。 |
| T1 / T2 / T3 | 本例成交及扩展变体中的其他义务。 | T1 保持 0.4 WETH、800 USDC 加 0.8 买费，新增编号不更改主例。 |
| WETH / USDC / A / B | 封装 ETH 式基础资产、报价资产，以及本例买卖双方。 | A 用 USDC 锁资支付，B 用 WETH 锁资交货；两种资产按各自整数精度处理。 |
| fillSeq / nextFillSeq / 双边前驱 | 每订单本笔序号、期待序号和买卖两侧先行义务。 | 一笔 fill 同时属于两条顺序链，只满足买方或卖方一边都不够。 |
| 依赖图 / 拓扑序 / 零入度 | 把必须先后画成关系，按前驱就绪顺序取节点。 | 同订单相邻成交建边，在当前无前驱候选中按稳定日志顺序选取。 |
| 环 / 同序号冲突 / 依赖分量 | 无法合法排序的闭环、序号重复及相连义务集合。 | 属于来源或投影异常，应隔离核查，不能删边改号凑顺序。 |
| nonce / 外部前驱 / finalized | 账户发送序号、批外先行成交和链最终性。 | nonce 有序不保证前批成功；基线要求批外前驱已最终交割。 |
| tradeId / payloadHash / planHash / batchId | 成交、完整载荷、计划和批次身份。 | 换批可换集合摘要，不改变各笔经济身份、条款及序号。 |
| 计划认领 / Outbox | 获得持久发送归属和本地待发记录。 | 候选可并行，认领与计划同事务；尚有可生效旧路径时不另覆盖认领。 |
| C / feeDelta / 累计费用 | 买单累计货款和本笔增收费用。 | 批内顺序承接累计上下文，不能逐笔独立向上取整多收。 |
| eth_call / Gas / calldata | 快照预执行、执行资源和调用数据。 | 模拟与估算只在指定快照成立，不能保证实际区块状态或期限不变。 |
| ACTIVE / blockHash / D | 活跃锁、依据区块和订单截止。 | 发送前查锁、序号、载荷和期限，仍须在实际执行时重新满足条件。 |
| receipt / executed / 执行覆盖 | 回执、合约执行记录和对批内每笔结果的核验。 | 新项核验本次事件，重复项可引用同规范历史的原执行证明，不必再发新事件。 |
| UNKNOWN / 交易族 / 退役发送路径 | 结果未知、相关签名候选和确认旧路径不再生效。 | 超时不直接拆批；最终失败且无其他活动旧路径后，才追加替代计划。 |
| defaulted / 坏单隔离 | 违约未交割分类及暂停受影响依赖的发送。 | 不删除义务、不推进链上序号，前驱违约不使后继自动跳过。 |
| 背压 / 最早截止 / 失败半径 | 限制新增风险、最紧期限及一项错误牵连范围。 | 小批与大批有等待、成本取舍，增加协程不能消除依赖或低 nonce 阻塞。 |

## 把整篇文章压缩成一个故事

编排员想把 T1 与扩展变体的 T2、T3 合成一笔交易省固定 Gas。T1 原条款仍是 A 买 B 的 0.4 WETH、货款 800 USDC、买费 0.8 USDC；若 T2 继续使用 A 的买单，就得用 A 的第 2 序号，还得检查它卖方自己的前驱。编排员从可靠日志读取这些关系，排出稳定拓扑序，而不是按消息到达先后塞数组；批外前驱未最终，就把相关前后笔同批有序执行或等待。

计划认领、不可变集合与 Outbox 一起持久保存，预执行也绑定区块，但模拟通过仍不代表实际一定成功。如果 [T1、T2、T3] 广播超时，不能猜 T2 坏了就立刻拆开重发，旧批可能正在成功。若最终确认整批失败且所有旧发送路径均已排除，再追加拆批计划，保留各笔身份和原载荷；本批新执行的 T1 也随失败回滚，Gas 与账户 nonce 却可能已消耗。

假如 T2 是 T3 的序号前驱，隔离 T2 时必须连带阻断 T3；T1 若自身合法且前驱就绪，可以先履行。不能把 T3 的 seq=3 改成 2，也不能指望把 T2 记成违约就让合约序号自动前进。最终每笔核销须有完整执行证据与最终性；调小批次、控制等待和暂停新增风险只能降低失败半径与违约概率，不能保证链停顿时仍会交割。

**流程位置与核心机制：** 本题连接不可变成交义务与结算广播，重点是每订单 fillSeq 依赖、批内拓扑顺序、跨批就绪条件、整批原子失败及证据化拆批。沿用 V 预存锁资和总览 T1；文中引入 T2、T3 时仅表示独立扩展变体中的后续义务，不改变 T1 的 0.4 WETH、800 USDC 和 0.8 USDC 费用。

## 第 1 层：批量为什么首先要确定失败语义

**面试官：** 为了节省 Gas，把多笔成交放进一次 settleBatch，怎样处理订单依赖和其中一笔坏单？

**面试者：** 我会先明确默认接口是整批原子，而不是“尽量多做几笔”。V 在同一个 EVM 事务中按给定顺序执行 fill，任意一笔检查失败都会使本批在 V 中的全部变化回滚。不能在这个前提下说逐笔 catch 后继续，更不能只根据程序循环走到第几笔就核销前面的成交。

例如把 T1 放在批首，它的预期效果是 A 锁资减少 800.8 USDC、B 锁资减少 0.4 WETH，A 增加 0.4 WETH、B 增加 800 USDC、费用账户增加 0.8 USDC。若后面的新成交失败，以上变化、执行标记和订单序号都不会保留下来；发送者的 Gas 和 nonce 消耗则保留。

编排层要做三件事：按双方订单依赖形成合法顺序；让批次大小、Gas 与履约窗口可控；失败后先确认原尝试结局，再把与坏单无依赖的义务分离处理。批量降低的是平均固定成本，不是把一笔成交的失败自动转成可忽略错误。

## 第 2 层：一笔成交为什么同时属于两条顺序链

**面试官：** 你说按双方订单依赖排序，只按成交时间排序不够吗？如果两批各含同一买单的一笔成交，会发生什么？

**面试者：** 每笔 fill 同时消耗一个买订单和一个卖订单的序号，因此就绪条件是双方前驱都满足。T1 的双方 fillSeq 都为 1。独立扩展变体中，若 T2 再使用 A 的买订单，它的买方序号必须为 2；即使 T2 的卖方没有前驱，也不能越过 T1。只按不同服务看到的到达时间排序，可能使 T2 先进入另一批并在链上因序号错误回滚。

我会以成交义务为节点，对同一订单相邻 fillSeq 建立前驱边；一笔成交的买卖两侧都要建边。撮合提交位置提供确定来源，拓扑排序在当前零入度集合内再用稳定日志顺序等规则择优，得到可重放的批内顺序。读取的是权威提交结果，不按 MQ 到达顺序重新裁决成交。

如果图出现环，或某订单有两个不同成交声称相同序号，这是日志、投影或身份冲突，不是正常拥塞。应隔离相关依赖分量、核对来源，不能随意删一条边或改 fillSeq 来凑出拓扑序。正常方案必须保证每笔义务都能追溯到唯一提交和双方合法前驱。

## 第 3 层：批内有序为什么不等于跨批可并行

**面试官：** 拓扑序在一批内能成立，那是否把 T1 放批一、T2 放批二，同时广播就行？同一发送账户的 nonce 本来就是有序的。

**面试者：** nonce 只规定该发送账户的交易顺序，不能单独充当依赖成功证明。批一可能 status=0，随后批二仍会执行；切换发送路径、补发和重组也会改变我们对前驱的观察。在本题的保守编排策略中，一个批次的外部前驱必须已在最终规范链交割；尚未最终的前驱，要么与后继进入同一个原子批次并排在前面，要么后继暂不成为可发送任务。

这会牺牲共享热门订单的流水线吞吐，却让跨批恢复更简单。若改为允许前驱仅入块就流水发送，必须接受后继回滚、分叉撤销和整条依赖链恢复的成本，不能声称有 nonce 就等价于最终成功。本模型没有借机新增逐笔容错语义。

就绪检查还要读链上双方 nextFillSeq、锁状态和累计量，并带观察水位。T1 已经执行而被重放时，V 先比对 executed[T1] 的载荷并无变化返回，再处理真正的新 fill；不能先用旧序号失败。这个执行处幂等保障重播安全，但不允许编排器无视未完成的前驱。

## 第 4 层：计划认领怎样避免两个编排器各组一批

**面试官：** 你把外部前驱要求收紧到最终成功，但两个编排器可能同时看见 T1 就绪，各组出不同批次，怎样避免计划和重试互相覆盖？

**面试者：** 我会把“选出候选”与“获得发送权”分开。候选可以并行计算，正式认领则在持久事务中检查义务当前绑定、依赖前沿和观察版本，写入不可变计划及逐成交归属，再同事务生成 Outbox。对一个仍有可生效交易的计划，不能把其成交悄悄再认领到另一份活动计划。冲突者重新读取，不以最后写入覆盖旧 planHash。

planHash 绑定有序成交集合、各自完整 payloadHash、双方序号、规则版本和依赖。T1 的身份、数量、价格、费率和 maker 条款不会因换 batchId 改变。费用按买订单累计名义金额计算差额，批内顺序与已最终前缀共同决定累计上下文，不能在组批时把每笔费用独立向上取整。

事务提交后崩溃，由 Outbox 恢复同一计划；事务未提交则没有外发资格。批次重编排需要保留旧计划并追加替代关系，而不是修改已经签出交易所对应的计划正文。链上幂等仍是最后的资产保护，计划认领解决的是可管理的活动发送路径和可解释的恢复，不是替代合约去重。

## 第 5 层：预执行为什么只能减少失败而不能证明成功

**面试官：** 活动计划唯一后，能否先 eth_call 和估 Gas，全部通过就认定批次一定成功？还需要哪些发送前检查？

**面试者：** 不能。预执行只在选定状态快照上成立。我会固定依据 blockHash，核对双方锁 ACTIVE、nextFillSeq、已执行身份及载荷、累计数量和费用、截止时间、当前结算角色，再按同一顺序模拟并评估 Gas 与交易大小。对接近期限或前驱观察落后的计划，即使模拟通过，也可能已经没有合理的入块窗口。

模拟到实际执行之间，其他交易可能先改变序号或关闭锁资，链可能重组，块时间也可能越过双方较早的截止。估 Gas 也不是永久上界。因此检查通过只允许进入受控签名与广播，不允许把 pending 转 settled。真正的新资产效果仍由 V 在执行时重新核验，并由最终观察核销。

这个阶段的收益是提前发现明显错误，减少整批浪费；代价是多一次查询且仍有状态竞争。如果预执行失败，应区分观察落后、缺前驱、重复成交和载荷冲突：前两类先修复观察或等待；同身份同载荷的重复项在 V 中本应先于序号检查无变化返回，不应被预检误拒；载荷冲突则隔离追查。不能为了让调用通过，把已提交 T1 的经济条款改成当前链状态恰好接受的另一笔交易。

广播后的批次核验也要逐项覆盖：新执行项核验本次回执及执行结果，重复项允许由同一规范前缀中已核实的 executed[tradeId]=payloadHash 和历史执行证明覆盖。重复项不一定再发 Settled 事件，不能要求每项都在本 receipt 中出现新事件，也不能仅见 status=1 就把整批核销；最终核销还要求这些证据进入完整最终前缀。

## 第 6 层：整批失败后为什么不能立即拆开重发

**面试官：** 预执行也挡不住竞争。假设 [T1、T2、T3] 广播后超时，怀疑 T2 有问题，直接把 T1、T3 拆出来重发，是否就能隔离坏单？

**面试者：** 超时不是原批次失败，不能直接拆。原批次仍可能整体成功；如果另签拆分批次，就同时存在多组可执行路径，带来费用浪费、依赖混乱和更难解释的回执。默认先保留计划与认领，恢复原始交易、查询全部替换成员和规范链结果；需要加速时沿原 nonce、原经济载荷提高费用。

只有原批次的失败结局在选定最终性下确定、且不存在其他仍可生效的原计划发送路径，才能退役原发送路径并追加拆批计划。status=0 的最终回执证明原批在 V 中没有留下前半批效果，但仍应核对各成交是否已由其他已知合法尝试执行。新批的就绪条件据最终状态重算，成交身份和载荷不改，旧计划与失败原因保留。

这不是为了追求形式上的“永不重复发”，而是把重复限制在可枚举和可恢复的边界内。如果产品选择更激进的并行救援，就必须明确增加 Gas 与状态冲突成本，并仍依靠 V 幂等保护；本题默认不把这项复杂度藏在“自动拆批”四个字里。

## 第 7 层：隔离坏单为什么不能跳过依赖前驱

**面试官：** 原批最终失败后可以拆了。如果 T2 就是坏单，而 T3 的某个订单序号在 T2 后面，是否仍可以只跳过 T2 让 T3 先执行？

**面试者：** 不能。失败隔离的单位不是任意数组元素，而是依赖图中的可执行部分。若 T2 是 T3 在任一订单上的前驱，T3 必须等待；没有依赖 T2 的义务才可以进入其他就绪批次。若 T1 是 T2 的前驱而自身合法，可以先让 T1 单独或与其他独立义务交割，缩小阻塞范围，但不能假装它与 T2 的依赖从未存在。

我会记录坏单根因、受阻后继集合、已用 Gas 和距离截止的余量。临时权限或观察问题可以在条件恢复后继续原义务；若提交记录本身违反签名限价、锁资或序号，不允许改价、缩量、重编号来让它成功，应隔离相关来源并保留未交割义务，最终按期限证据进入违约处置。这个模型没有绕过坏序号的“管理补洞”接口。

尤其前驱已经最终未交割时，链上的 nextFillSeq 不会因链下记了 defaulted 就自行增长，其后继不能自动越过。整批失败会回滚本批执行标记和序号；链下坏单隔离只控制发送，不消灭任何已经提交的经济责任。

## 第 8 层：容量优化怎样不制造新的履约承诺

**面试官：** 依赖前驱不能跳、未知批次不能随便拆，热点订单又会阻塞很多成交。怎样控制批量大小和积压，而不是一直加大批次？

**面试者：** 我会同时约束单批 Gas、calldata 大小、成交数量、组批等待时间和最早履约截止，而不是追求每批尽可能满。共享订单依赖越长，越要避免一个风险项绑住大量独立义务；对零入度且互不依赖的成交，可按截止压力与等待时间选择，保持可解释的公平规则，不重新改变撮合已经确定的价格时间结果。

积压超过可服务窗口时，应限制新增订单接纳和新增撮合风险，把已有义务与必要的撤余量、观察恢复放在优先位置。单一发送账户还有低 nonce 阻塞，增加编排 goroutine 无法消除它；并行计算只能提高候选准备效率，不能越过链上依赖。若未来引入多个结算账户或另一种批次容错接口，需要重新定义授权和跨路径控制，不假装它们是当前基线已有能力。

取舍是小批降低失败爆炸半径和等待，大批摊薄固定费用；保守跨批最终依赖降低吞吐但简化恢复。无论怎样调度，都不能保证链停机或截止迫近时必然交割。容量保护要减少违约概率，而不是把“已承诺但交割不成”改称“坏单已丢弃”。

## 本题收束

- **机制：** 用双方每订单 fillSeq 建依赖图，以稳定拓扑序确定批内执行；外部前驱按最终状态就绪；计划认领与 Outbox 同事务；V 默认整批原子，失败后先证据化退役原发送路径，再隔离无依赖的合法部分。
- **边界：** 账户 nonce 有序不等于前驱成功；预执行成功不等于实际成功；编排隔离不是删除义务；新 batchId 不改变 tradeId；失败回滚 V 的所有批内变化，不退还已消耗的 Gas 和 nonce。
- **反例检验：** T2 使用同一买订单的 seq=2，T3 使用 seq=3。T2 导致整批失败后，若把 T3 改成 seq=2“跳过坏单”，就重写了原提交；若保留 seq=3 强行发送，V 应拒绝。正确隔离必须让依赖后继受阻，同时允许与 T2 无关的就绪成交继续，并保留 T2、T3 的原义务。
