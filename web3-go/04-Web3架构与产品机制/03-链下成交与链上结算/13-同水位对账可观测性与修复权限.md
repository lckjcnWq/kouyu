# 大问题 13：怎样按同一截止点核对义务、锁资和余额？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 同水位 / 截止点相容 | 各视图固定到可重建且能互相解释的处理范围。 | 不是都写同一时间戳，而是说明日志、链块、证据与回报各覆盖到哪里。 |
| L / 提交向量 / H / blockHash | 各分区日志位置、位置集合、选定规范块和块身份。 | H 内执行须有 L 内源义务；不能混入 H 之后的结果，也不能用同高度异哈希替代。 |
| chainId / V / token 地址 | 链、金库与具体资产身份。 | 逐链逐币比较，不把 WETH 和 USDC 折成市值后只核总数。 |
| available / locked / 费用账户 / Σ | 用户可用、订单锁资、协议费用权利，以及求和符号。 | 逐币把三类权利求和对比实际持币；pending 不是第四种可相加的币余额。 |
| 实际持币 / 未归属金额 | V 真正收到的币与没有合法用户归属证明的转入。 | 直接捐赠可单列解释差额，不能据此给某个用户凭空充值。 |
| WETH / USDC / 原子单位 / Gas | 基础币、报价币、最小整数单位和中继执行成本。 | 两币分别 18、6 位；Gas 用原生币另计，不从用户锁资暗扣。 |
| Q / open / pending / settled / cancelled / defaulted | 整单量与五种数量分类。 | 日志独立满足总量守恒，链上已执行但未核销的 pending 不再算第二份需付资产。 |
| tradeId / payloadHash / planHash | 成交、完整载荷与计划身份。 | 从 T1 源日志串到计划、尝试和实际执行，不能按 txHash 数量累计成交。 |
| fillSeq / filledBase / nextFillSeq / cumQuote | 本笔序号、累计基础量、下一序号与累计货款。 | T1 后为 filledBase=0.4、nextFillSeq=2、货款累计 800，仍要核对 owner 与币种。 |
| signTaskId / nonce / rawTx / 交易族 | 签名任务、发送槽位、签名原文和相关候选。 | 定位外发缺口，rawTx 虽非私钥仍可被广播，不能随意公开。 |
| 最终水位 / 完整观察前缀 / latest | 可最终核销位置、已完整处理历史和当前最新状态。 | 历史 H 读不到不能退回 latest 冒充；最终检查点与本地完整度都要记录。 |
| Outbox / Inbox / 证据命令 | 待发、消费记录及送回订单所有者的稳定证据。 | 链已最终而命令未消费可解释 pending，应补传而非再交割或加钱。 |
| revision / 投影 / ACID | 状态修订号、派生查询视图和本地事务属性。 | 修投影不改权威资产，也不产生跨数据库与链的全局快照。 |
| 证据缺口 / 传递缺口 / 实质冲突 | 查不全、消息任务没到，以及同范围内真实不一致。 | 分别补材料、恢复原交付或隔离权限，不能一律自动调平。 |
| 高基数标签 / 受控明细 | 取值很多的指标维度与按权限查询的细节。 | tradeId 留在明细追踪，监控按有限维度看年龄、水位差和窗口压力。 |
| 追加修复 / 状态所有者 / 分权 | 留痕更正、唯一领域裁决者和权限分离。 | 补核销经同一撮合日志；只读对账者不签交易，投影修复者不增可提余额。 |
| D / DEFAULTED_UNSETTLED / closeLock | 截止、最终未交割违约与正常关锁。 | 违约已解释不等于结算成功，报警关闭也不授予提前释放锁资权限。 |

## 把整篇文章压缩成一个故事

值班员发现 T1 仍显示 pending=0.4 WETH，节点最新查询却说 A 已收到 0.4 WETH。值班员先不改账，而是固定各撮合分区提交位置 L、最终规范块 H 的哈希和观察、证据、回报水位。在 H 已交割但尚未关锁的主例里，USDC 权利应为 A 可用 2,987.99 加锁资 1,211.21、B 可用 800、费用 0.8，合计 5,000；WETH 为 A 的 0.4 加 B 可用 1、锁资 0.6，合计 2。即使总数对了，也得核对 800 是否真的属于 B。

沿 T1 的原日志、完整载荷、计划、交易族和执行证据追查，若只是最终证据还躺在 Outbox，pending 就是待回传核销，不是另一份要补给 A 的币。值班员追加修复任务，用原稳定证据身份送回撮合状态所有者，经同一日志把 pending 转为 settled；若只是页面落后，就重建投影。若发现同身份异载荷、无来源执行或提前关锁，则隔离风险而非自动重试。不同权限只做各自的事，修投影不能签链上交易或凭空加余额。

修复后还要先在原截止点复算，再检查新的相容水位和根因是否受控。T1 最终核销并不自动关锁，双方 0.6 余量仍要经日志撤销，再满足正常关闭条件，最终才出现 A 可用 4,199.2 USDC、B 可用 1.6 WETH。若证据最终说明违约，差异可以解释并关闭工单，业务却仍是未交割；对账不是把界面刷绿，更不是第二次发币或把数据库更正说成链上退款。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于成交提交、链上观察和业务终态回报之间，解释怎样取得可比较的证据、逐资产与逐订单定位差异，以及谁有权追加修复。与最终性母题的区别是：这里假设已经能识别规范链和最终前缀，继续追问不同系统的视图怎样对齐、差异怎样解释，而不是把一次最新余额查询当成对账。公共基线与 T1 数值沿用总览；主例双方同一截止时间 D，教学单轮只撮合 0.4 WETH，轮末暂停新增撮合，继续 T1 结算及撤余量，关闭前不恢复新增撮合。异常检查点分别独立推演。

## 第 1 层：先确定对账比较的是哪两种事实

**面试官：** 链下显示 T1 还有 0.4 WETH 待结算，链上查询却显示已经成交 0.4 WETH。这是不是账不平，应该把哪边改掉？

**面试者：** 不能先改任何一边。链下 pending 是已经确定但尚未由本地权威日志核销的义务数量，链上 filled 是某个规范状态里的累计执行量；两者不是天然处于同一时刻，也不是相同口径。观察延迟、未最终入块、最终证据尚未交回撮合日志，都可能造成这种表面差异。

我会分三类事实来核对。第一类是成交义务：T1 是否在撮合提交前缀内，条款是否仍为 0.4 WETH、800 USDC 和 0.8 USDC 买方费用，双方 fillSeq 是否为 1。第二类是资产执行：选定的规范链截止块上，V 是否记录同一 tradeId 与 payloadHash、订单累计量是否增加、锁资和可用资产怎样变化。第三类是证据交付：观察器读到了哪里，最终证据命令是否已经提交给撮合所有者，查询投影又消费到哪个 revision。

例如 T1 只是暂时入块，链下继续 pending 是正确的；如果已经最终交割，但最终证据命令还在 Outbox，订单数量暂时 pending 也有明确的交付原因。应补齐交付和投影，不能再造一笔 T1，也不能直接给用户加一次钱。反过来，若相同截止点、完整证据下仍有无来源扣款或载荷冲突，那才是不能用延迟解释的异常。

因此对账不是选一个看起来更新的系统覆盖另一个系统，而是让每个权威事实在自己的范围内成立，再解释它们之间还缺哪一步传递。运行中出现暂态并不自动说明错误，暂态长期没有可恢复证据也不能一律称为最终一致。

## 第 2 层：用水位组合建立可重复的比较截止点

**面试官：** 你说要选相同截止点，但数据库日志、链上区块和回报 revision 没有共同的时钟。具体怎样固定这一次对账，避免边查边变化？

**面试者：** 我会固定一组可重建的水位，而不是只写“截至今天零点”。这组水位至少包括 chainId、V 地址、资产与规则版本、各撮合分区的已提交位置 L、规范截止块 H 的高度和 blockHash、H 的最终性依据、观察器完整提交到 H 的进度，以及最终证据命令和查询投影各自的消费位置或 revision。高度相同但 blockHash 不同不能当成同一个截止点；一个全局时间戳也不能代替多分区提交向量。

链上读取要固定到 H。节点支持按块哈希读取时明确使用该哈希；不支持时，要通过具有历史能力的节点按高度读取并核对该高度的规范哈希，确认数据确实属于 H，不能失败后退回 latest。数据库则使用一致性快照，或从日志和历史投影重建 L 对应的视图，记录计划、发送和观察各自覆盖了哪些源事件。若历史读取能力不足，本轮应标成证据不全，不能把当前余额冒称为历史余额。

还要检查这组水位是否相容。例如 H 内某笔执行的原始成交日志必须已包含在所取的 L 中；若本地终态快照已经包含 H 之后的执行结果，就要选取能覆盖它们的链截止点，或取得不包含这些后续结果的历史视图。确实跨出了截止点的记录要单列桥接项，不能混进差额。无法取得相容快照时，先补齐源数据或缩小可核对范围，不宣布资产有损失。

这不要求暂停全站创造一个跨库、跨链原子快照。它要求保存每个局部视图的来源和范围，做到相同水位能够重算相同结果。Outbox/Inbox 让传递可恢复，revision 让投影可追踪，都不会把这些独立事务变成全局 ACID。

## 第 3 层：同一块上怎样逐资产验证金库守恒

**面试官：** 水位固定了。你说资产应守恒，能用 T1 的具体数值说明核对什么吗？只把用户总余额加起来够不够？

**面试者：** 不够。必须按 `chainId＋token 地址` 分别核对 V 的实际持币与内部权利，不能把 WETH 和 USDC 折成某个价格后只比较总市值，也不能漏掉锁资和费用账户。基线没有未分类直接转币时，每个 token 都应满足：`V 实际持币(H) = Σ用户 available(H) + Σ订单 locked(H) + 费用账户权利(H)`。有直接转币时，在右侧另外列出未归属金额；它不是可以凭空分给某个用户的充值证明。

T1 在最终建锁以后、执行以前，USDC 内部权利是 A 可用 2,987.99 加 A 订单锁资 2,012.01，合计 5,000；WETH 是 B 可用 1 加 B 订单锁资 1，合计 2。T1 链下提交只改变义务分类，并不改变这组链上资产。

T1 在选定最终块 H 内已经交割、尚未关闭锁资时，USDC 应是 `2,987.99 + 1,211.21 + 800 + 0.8 = 5,000`，依次对应 A 可用、A 锁资、B 可用、费用账户。WETH 应是 `0.4 + 1 + 0.6 = 2`，依次对应 A 可用、B 可用、B 锁资。待余量撤销并最终关闭后，USDC 为 `4,199.2 + 800 + 0.8 = 5,000`，WETH 为 `0.4 + 1.6 = 2`。内部交割和关闭都没有改变 V 持币总数。

所有计算用原子单位整数。USDC 6 位、WETH 18 位不能混算，Gas 是中继原生币开支，不能从这 0.8 USDC 费用或用户锁资里凭空减掉。充值提现需另用真实转入转出解释总权利变化；外部钱包余额不并入 V 内权利。

这一步只能证明总量层面是否一致。即使总量等式成立，也可能把 B 的 800 USDC 记到错误用户，或者错误释放了某个订单的锁资，所以接下来还必须做归属和执行明细核对。

## 第 4 层：总量相等以后怎样查出订单级错配

**面试官：** 假设 USDC 和 WETH 总量都对，但 A 的锁资已经减少，链下 T1 仍是 pending。怎样逐笔核对，避免把同一笔 0.4 同时算成已交割和未履约风险？

**面试者：** 我会建立以 tradeId 为中心的连接，而不是只比较两个汇总字段。先从 L 内的提交记录取得 T1 的双订单摘要、双方序号、数量、价格、费用版本和 payloadHash，核对计划载荷是否相同，再找到可能承载它的交易族，最后连接 H 内的实际执行证据。txHash 是一次尝试的身份，不是成交身份；同 nonce 加速产生多个哈希，也只能核销同一个 T1。

如果 H 已有相同载荷的执行标记，就核验该执行对应的资产变化与累计量：A 锁资减少 800.8 USDC、B 锁资减少 0.4 WETH，买方累计名义金额增加 800 USDC，累计费用增加 0.8，双方 filledBase 增加 0.4、nextFillSeq 变为 2。还要核对 owner、token、锁状态和其他成交明细，不能只看 filled 总数凑巧一致。重复尝试若在合约内无状态变化返回，不能要求本次必有一套新的资产变化事件；应追溯首次执行的规范证据或固定 H 的执行状态，不能重复记账。

随后分别列出“链下源数量分类”和“截至 H 已有执行覆盖”。如果源日志仍显示 pending 0.4，而 H 已最终覆盖 0.4，这 0.4 应标注为待回传核销，不能再作为截至 H 尚需交割的另一份 0.4 添加到余额上。反过来，H 以后才执行的成交不能拿来解释 H 的锁资。pending 是义务维度，不是与金库资产并列可加总的第三种 token 余额。

同一订单还要满足 `Q = open + pending + settled + cancelled + defaulted`。T1 在双方都只发生这一笔成交时，状态可能是 `1 = 0.6 + 0.4 + 0 + 0 + 0`，或核销后的 `1 = 0.6 + 0 + 0.4 + 0 + 0`，但不能两边都计 0.4。后续 fill 依赖也按各订单序号核查：基线跨批前驱必须最终交割；未最终前驱与后继只能同批有序或先等待，不能靠对账事后补足乱序。

## 第 5 层：发现差异以后先补证据还是先停业务

**面试官：** 你已经能把待核销和真实资产异常分开。如果一轮对账发现几处差异，怎样决定先补数据、重试，还是立即停止结算？

**面试者：** 我会先给每个差异保存复现所需的水位与证据，再按它破坏了什么保证决定动作，不能先跑一个“自动调平”脚本。关键是区分证据缺口、已证实的交付缺口，以及在完整同水位下仍成立的经济或权限异常。

第一种是证据不完整：观察器缺块、历史节点读不到 H、查询投影落后、最终证据命令没消费。此时补拉、回放或重建相应投影，保持原义务和锁资，不因某次查询为空宣布未执行。若缺口使新增锁资准入无法确认，就暂停受影响范围的新撮合；不能把“只是延迟”当作继续扩大风险的理由。

第二种是任务传递不完整：T1 有可靠提交但没有计划，或计划有原签名交易而广播结果未知。前者用原事件身份补交付，后者恢复原交易族与规范观察；两者都不重算价格、不新建 T1、不直接释放锁资。只是某个发送 attempt 已明确失败，也只处理这次尝试，不取消成交义务。

第三种是同水位实质冲突：同 tradeId 不同载荷、执行没有对应的权威日志、订单归属错误、余额等式不成立，或者有不应出现的提前关闭。这类差异不能通过盲目重试解决。应按受影响账户、交易对或发送权限隔离新增风险，必要时停止签名出口、启动既有紧急权限流程，并保全完整证据。重试一个载荷冲突可能只会扩大攻击面。

到期也单独判断。主例双方同 D，最终规范前缀时间戳严格大于 D、截止前历史完整且没有 T1 执行覆盖，才能提交违约证据；若已经交割就核销成功，不能同时计为违约。expireUnlock 只解释锁资真实释放，不能替代成交履约证据。处置范围要尽可能与风险边界一致，但不能用缩小报警范围来隐瞒无法解释的资产异常。

## 第 6 层：让可观测性暴露卡在哪一段而不是只报总数

**面试官：** 补证据、补交付、隔离权限是三种不同动作。监控怎样让值班人员看出该做哪一种，而不只是看到“pending 很多”？

**面试者：** 我会按义务和证据传递的阶段记录数量、年龄与水位差，再用稳定身份串联明细。pending 总数只是入口，它不能区分新形成的正常义务与临近 D 仍没有可执行交易的义务。

需要能观察到：撮合已提交位置与交付位置之差、计划 Inbox 和 Outbox 的积压及最老年龄、待签和已签未广播任务、各专用账户最早未决 nonce、UNKNOWN 交易族、included 到最终的等待、链观察完整前缀与节点最终前缀之差，以及最终证据命令已发但未被撮合日志裁决的数量。订单的 `pending→settled/defaulted` 只能由撮合所有者接收稳定身份命令后经同一日志完成；因此“观察器已经最终确认”与“订单已经核销”应有两个可见进度。

另按订单 D 与依赖关键路径观察剩余交割窗口，区分即将到期的旧义务和宽裕期限的新义务。守恒差额必须标明 token 地址、块哈希和数据完整性；不能把 latest 读数抖动画成真实资产亏空。没有实测依据就不编造固定秒数或阈值，阈值要结合该链最终性、发送延迟分布、签名和组批能力以及风险策略设置。

明细查询可以从 tradeId 追到源提交位置、planHash、signTaskId、nonce、txHash 族、blockHash/logIndex、最终证据命令身份和对外 revision。金额明细、签名载荷和 rawTx 按权限保管，不为了排障把它们全部打进公开日志；rawTx 虽不是私钥，仍可能被持有者广播。监控指标的标签用有限维度，tradeId 等高基数字段留给受控明细与链路查询。

最后要让报警附带建议动作和禁止动作：观察缺口建议补块但禁止提前结算；载荷冲突建议隔离但禁止自动换 tradeId；窗口不足建议停止新增风险但保留旧义务交付。可观测性帮助执行正确协议，不能授予值班人员越过协议的权力。

## 第 7 层：修复如何追加、如何分权、怎样恢复数量

**面试官：** 如果监控明确指出最终证据已经存在，只是 T1 的核销漏了，运维直接把 pending 改成 settled 最快。为什么还要走命令和审计，具体怎样修？

**面试者：** 因为直接改表会绕开状态所有权、幂等和历史因果关系。下一次日志回放可能覆盖手工修改，重复回报可能再次计量，关闭锁资流程也不知道这次修改依据什么。修复需要对准出错的边界，不是把所有系统都改成一个“看着正确”的终态。

如果漏的是查询投影，重建投影或补交原领域事件，复用已有事件及其 revision，不触碰权威数量；只有确实新增状态修订时，才由总览规定的同一观察/回报投影所有者持久分配新 revision，不能由修复脚本另起计数器。如果漏的是最终证据交付，追加一条修复任务，引用 T1、payloadHash、H 的最终执行证据、原任务身份与修复原因；使用稳定证据命令身份交给撮合状态所有者。撮合所有者核验证据和现有终态，在同一日志内去重并裁决 `pending 0.4 → settled 0.4`，同时生成回报。命令重复不能再加一次 settled；若原来已经违约或证据冲突，则隔离调查，不直接覆盖成另一种终态。

修复记录应包含受影响范围、前后状态或预期结果、依据水位、操作者、审批者、关联事件和执行结果。普通观察与对账账户只读；投影修复权限不能签发链上交易；证据补交权限不能任意增发可提余额；签名、暂停、恢复和合约权限变更由对应受限角色执行。高风险动作按制度独立复核，避免同一操作者既制造差异、又审批并抹除痕迹。

追加修复不等于所有旧数据永远不能纠错。损坏的派生视图可以重建，错误的业务标注可以追加更正，但原始日志、原链证据与更正之间的联系必须留下。已经最终发生的资产转移不能因链下改账被称为链上回滚；如果确实需要额外资产处理，应走有授权的新业务或链上操作、独立身份和审计，不伪造一笔原来没有发生过的履约。

## 第 8 层：什么证据允许关闭差异和解除保护

**面试官：** 修复命令已经成功提交，也有审批记录了，能立刻把报警关闭、恢复新撮合，并让 T1 的余量解锁吗？

**面试者：** 不能把“修复任务执行成功”当成全部业务条件都满足。首先应在相同截止点复算原差异，证明修复命中了缺失边界；随后推进到新的相容水位，检查修复期间是否又出现后续差异。若只是投影重建成功，而签名出口仍有未知旧任务，或者最终证据命令仍未被撮合日志消费，就不能宣布整个链路已闭合。

T1 的闭合证据应串起来：原撮合提交存在且载荷不变；H 内执行身份和金额完整覆盖；最终证据命令由撮合日志唯一核销；查询与私有回报能给出相应 revision、依据块和最终水位。修复后的订单满足数量守恒，逐资产与逐锁资明细仍相符。恢复新增准入还需要风险根因被控制、当前锁资投影可信、有效交割窗口足够，而不只是 pending 数量下降。

主例里 T1 最终核销后，双方各有 settled 0.4、open 0.6。余量撤销仍需同一日志裁决为 cancelled 0.6；只有该订单无 open、无未决成交义务，最终观察对齐，才允许授权出口发送 closeLock。最终关闭后的 A USDC 可用 4,199.2、B WETH 可用 1.6，是合约真实关闭结果，不是对账脚本主动配出来的目标数。

若独立故障变体中 T1 最终未履约，则按完整截止证据交回撮合日志，pending 转 defaulted 0.4；到期未成交 open 可按过期原因转 cancelled。日后真实释放多少锁资按链上事实记录，不能用默认违约数量推算用户已经收到赔付。此时“差异已解释并处置”可以闭合核对任务，但业务仍有违约义务与追偿事实，不能把它包装成“结算成功”。

所以对账闭环是证据、权威状态、投影和权限处置都可解释且可重算，不是所有界面都变绿。它是发现和修复错误的第二道防线，不能替代执行前的锁资、原子交割、可靠日志与签名围栏。

## 本题收束

- **讲透的机制：** 固定日志提交向量、规范块哈希、最终前缀和消费 revision；先检查截止点相容性，再逐 token 守恒、逐订单归属、逐 tradeId 执行覆盖；按证据缺口、传递缺口和实质异常选择动作；最终证据经同一撮合日志核销，修复追加且分权审计。
- **最容易答错的边界：** 链下 pending 与链上 current 不是同一时刻；义务数量不能与 token 余额直接相加；总量守恒不证明归属正确；补投影不等于改变权威资产；链下更正不等于链上回滚；对账通过也不授予提前关闭锁资的权力。
- **反例：** 观察器落后时，运维看到 T1 pending 0.4，同时读到 latest 上 A 已有 0.4 WETH，就再给 A 手工加 0.4 WETH 作为“补账”。随后最终证据正常到达，同一笔执行被算了两次。正确做法是固定 H，追到原执行和证据交付缺口，补交核销命令或重建投影；没有新的链上资产事实就不能新增可提权利。此处是可复述的反例推演，不宣称已经完成工程验证。
