# 大问题 2：用户签名到底授权什么，怎样防重放与越权？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EIP-712 / orderHash | 结构化签名规范与完整订单摘要。 | 证明用户同意指定条款，不自动证明有钱、已锁资或只用过一次。 |
| structHash / domainSeparator | 订单内容摘要和执行场所的域摘要。 | 内容与 chainId、V、域版本一起绑定，换链、换金库或改费率不能复用原授权。 |
| owner / msg.sender / recipient | 订单资产主体、当前调用者和收款对象。 | 中继可提交但不是用户；成交所得固定记给订单 owner，不能任意改收款人。 |
| baseToken / quoteToken / side / Q / limitPrice | 基础币、报价币、方向、整单数量和限价。 | A 买 1 WETH 最高 2,010，B 卖 1 WETH 最低 2,000，按地址而非 symbol 识别币。 |
| bps / feeVersion / ceil / C / N | 费率单位、费用版本、向上取整、累计及本笔货款。 | 固定 10 bps；累计应收费 F(C)=ceil(C×10/10000)，每笔收增量，不随后台配置改价。 |
| salt / requestKey / resultRef | 订单区分值、接口请求身份和原结果引用。 | 换请求号不能重复建锁；复制签名会一起复制 salt，必须查摘要使用状态。 |
| V / allowance / lockOrder | 金库、代币使用额度和订单建锁。 | allowance 不是冻结；V 验签后同事务消耗摘要使用机会并把可用转成专属锁资。 |
| EOA / ERC-20 / 整数精度 | 私钥账户、代币接口及明确单位的金额表示。 | WETH 18 位、USDC 6 位，验签恢复 owner；不能把 1 个最小单位误当 1 枚币。 |
| tradeId / COMMITTED / fillSeq | 成交身份、可靠提交和每订单连续成交序号。 | T1 是不可因失败删除的 0.4 WETH 义务，双方序号均为 1。 |
| payloadHash / planHash / executed | 完整成交载荷摘要、计划摘要和执行标记。 | 同身份同载荷无变化，冲突拒绝；合约去重先于旧序号检查，但仍先验角色。 |
| txNonce / rawTx / txHash | 发送序号、原始签名交易和交易哈希。 | 加速换哈希不产生新义务；这些身份不替代订单或成交的去重。 |
| open / pending / settled / cancelled / defaulted | 未成交、待交割、已交割、取消、违约数量。 | 撤单只停 open，不是即时链上撤销，也不能释放 pending 的资金。 |
| D / closeLock / expectedFilledBase / expireUnlock | 截止、正常关锁、预期累计成交量及到期解锁。 | 新 fill 时间不晚于 D，解锁严格晚于 D；累计量一致并不证明链下没有未决成交。 |
| ACTIVE / 终态 / 最终规范链 | 活跃锁、不可复活的关闭状态及最终被接受的链历史。 | 同摘要关锁后仍不能重建；入块建锁不够，最终确认后才撮合。 |
| ERC-1271 / isValidSignature / 0x1626ba7e | 合约钱包的状态验签接口及规定成功值。 | 建锁执行时重新验，不能永久缓存接入成功；建锁后换钱包控制者不自动废除旧锁。 |
| 域升级 / 代理 / 信任边界 | 更换授权解释版本、可替换代码的地址机制及仍依赖的权限。 | 旧锁沿原条款执行，不能重置去重；签名规范约束不了拥有任意改码权的管理员。 |
| Outbox / RPC / Gas / 最终水位 | 待发记录、节点接口、执行成本和最终处理截止点。 | 本地交付不等于链上履约；超时未知、失败成本和最终核销分别处理。 |

## 把整篇文章压缩成一个故事

A 想在 V 买最多 1 WETH、单价不高于 2,010 USDC，于是签下包含资产地址、方向、期限 D、salt、10 bps 费用规则的订单。签名还绑定链和 V，不能拿去另一金库当同意书。B 签下卖 1 WETH、最低 2,000 的订单。两人的钱先存进 V，V 在建锁事务里验签、记录摘要已使用并分别锁 2,012.01 USDC 与 1 WETH；随后仍要等建锁最终确定，才能撮合，而不是接入验签成功就算钱已备好。

本轮预算 0.4 WETH 后暂停，先到的 B 以 2,000 形成 T1，货款 800、买费 0.8 USDC。换请求号不能再建同一锁，换交易哈希不能再造 T1，同成交身份改成 0.5 WETH 则必须拒绝。V 按已锁条款、当前角色、完整载荷和双方序号交割。若用户钱包是 ERC-1271 合约，接入时成功但建锁前更换控制者，就按实际执行时重验；若已经最终建锁后才更换，旧锁和已提交 T1 并不自动失效。

正常结果是 T1 最终交割后，撤掉双方 0.6 余量，再由排清义务的授权出口关锁；A 最终可用 4,199.2 USDC、0.4 WETH，B 可用 800 USDC、1.6 WETH。若 T1 尚未上链，错误出口拿 expectedFilledBase=0 提前关锁，计数也可能对得上，因此合约没有证明“链下无 pending”。升级不得重写旧费用或重置去重，到期解锁也不删除违约义务：有限签名能限制越权，却不是撮合诚实、管理员无害或一定履约的证明。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于“用户签署限价订单 → 金库 V 验签并建立订单专属锁资 → 最终锁资后进入链下撮合 → 受限出口提交链上交割”的授权主线，继续追到撤单、关闭、到期、升级和合约钱包的效力边界。重点是把用户同意的条款、各层身份、链上使用状态与执行权限分开，说明签名怎样成为有限授权，而不是任意划款权。公共流程、规则与唯一 MVP 沿用总览，本题不另建工程实践。

讨论固定为单链 EVM、白名单 ERC-20 预存金库 V、链下订单簿撮合、金库内原子交割；只有链上专属锁资最终确定后才能撮合。贯穿案例是 A 买 1 WETH、限价 2,010 USDC/WETH，B 卖 1 WETH、限价 2,000；买方固定支付 10 bps，费率和 `feeVersion` 都进入签名。A 初锁 2,012.01 USDC，B 初锁 1 WETH。B 为先到 maker，沿用总览的单轮 0.4 WETH 成交预算，轮末暂停该交易对新增撮合，结算与撤余量继续，主例关闭前不恢复；不是两张交叉订单在持续撮合中自然只成交 0.4。T1 成交 `0.4 WETH × 2,000 = 800 USDC`，买费为 0.8 USDC。主例双方采用同一截止时间 D，先最终结算 T1，再撤余量并关闭锁资；各故障反例独立从所述检查点展开，不连续叠加。

## 第 1 层：把签名限定为具体订单条款，而不是任意扣款权

**面试官：** 在这套预存金库、链下撮合的模型里，用户签了一张订单，到底同意了什么？撮合方拿到签名后，可以代用户决定哪些事情，又不能决定哪些事情？

**面试者：** 用户同意的是一组有边界的交易条件：在指定链和指定金库内，为这一订单建立专属锁资，再按约定规则分次成交和交割；不是把钱包或金库账户的任意支配权交给撮合方。签名能证明用户同意这些条款，但资金是否存在、是否已锁、剩余多少、是否已关闭，必须由 V 的链上状态回答。

订单的签名内容至少要明确以下几组字段，不能只签一句“买 1 WETH”：

- **主体与资产：** `owner`、`baseToken`、`quoteToken`、`side`。资产按链与合约地址识别，不按 WETH、USDC 这样的 symbol 识别；`owner` 是金库记账主体，不是提交交易的中继地址。
- **数量与价格：** 基础资产总量 `Q`、限价 `limitPrice`。数量和价格使用确定精度的整数，编码、方向和比较规则必须一致。本例价格在 2,000 至 2,010 之间才同时符合双方限价。
- **期限与身份：** 截止时间 `D`、`salt`。D 是最晚允许执行 fill 的链上时间条件，不是“接入服务在 D 前收到了就能永久结算”。
- **收费与解释规则：** 固定买费 `feeBps=10`、`feeVersion`、协议规则版本。费用版本所指向的收费和取整语义必须稳定，不能只签一个版本号，再由后台随意改掉它的含义。
- **签名域：** `chainId`、金库 V 地址、域版本等 EIP-712 域信息。它们也参与最终摘要，防止相同订单被解释成其他执行场所的授权。

在这些约束内，撮合方决定与谁匹配、形成哪笔成交、怎样按价格时间优先排序。本例 A 不必预先逐笔签 T1 的 `tradeId`，但 T1 的数量、价格、收费和收款归属必须落在 A、B 各自授权范围内。A 签的是最多买 1 WETH、价格不超过 2,010，而不是签名一出现就已经成交 1 WETH。

收款对象也不能由结算调用者任意指定：买入资产记给买单的 owner，卖出所得记给卖单的 owner，费用按 V 的既定费用规则记入费用账户。不提供一个任意 `recipient` 就能把卖方所得导向攻击者的出口，也不允许拿订单签名调用提现。

这里有一个必须主动说明的信任边界：V 能检查双方限价、数量、期限和资金，但不能独立重演链下完整订单簿来证明价格时间优先。**限制撮合方不能越过签名条款转走任意资产，不等于链上已经证明撮合方的全部排序和成交日志都诚实。**

## 第 2 层：让 orderHash 同时绑定订单内容与执行域

**面试官：** 你刚才把授权限定在某条链、某个金库和一套收费规则里。如果同一份订单被复制到另一个金库，或者有人只改了费用版本，V 怎样识别它已经不是用户签的那份授权？

**面试者：** 我会用完整的 EIP-712 类型化摘要作为 `orderHash`，而不是只对数量、价格或签名字节做哈希。其逻辑是：先按固定类型编码订单字段得到 `structHash`，再将它与包含 `chainId`、`verifyingContract=V`、域版本等信息的 `domainSeparator` 组合，得到最终签名摘要。V 使用自己的执行上下文和允许的类型、版本重算摘要，不能相信调用者自报一个“已经验证过的 orderHash”。

这形成两道绑定。

第一道绑定经济条款。`owner`、资产地址、方向、Q、限价、D、salt、固定费率和费用版本中任何一项变化，都应改变 `structHash`。例如 A 同意的是 10 bps，攻击者把载荷改成 20 bps，或把 `feeVersion` 换成另一套规则，不能继续拿原签名通过验签。V 还要拒绝不支持的规则与精度，不是“能哈希、能恢复地址”就全部接纳。

第二道绑定执行域。相同订单在另一条具有不同 chainId 的链、另一个 V 地址或另一个域版本下，应得到不同摘要。把 V1 收集的签名直接交给 V2，V2 必须按自身域重算并拒绝，而不是允许调用者传入 V1 的域供它验签。域信息是执行时约束，不是前端展示文字。

编码也属于授权语义的一部分。WETH 使用 18 位、USDC 使用 6 位，链下与链上必须对同一整数、字段类型、字段顺序和类型定义得到相同结果。不能一端把“1”理解为 1 WETH，另一端理解为 1 wei；也不能用有歧义的字符串拼接或不恰当的紧凑拼接代替类型化编码。Go 侧不能先用浮点数生成一套近似金额，再期待合约替它解释。

对 EOA，V 应使用规范验签方式确认恢复出的签名主体就是 `owner`，并拒绝不合法的签名形式；不能把 `msg.sender` 当作用户，因为实际调用者可能是中继。对合约钱包则不能套用“恢复出钱包地址”的做法，后面还要继续区分它的状态验签。

不过，EIP-712 解决的是“这份同意属于什么内容、什么域”，不自动解决“同一份同意已经使用过几次”。同一个域里，原样提交同一摘要，密码学验签仍可能成功。因此，**orderHash 是授权对象的身份，是否还能产生新的锁资或成交效果，必须再查持久业务状态。**

## 第 3 层：分开处理签发、请求、订单、成交与链交易的重复

**面试官：** 你说同一域里的原签名仍然可能验签成功，那让用户每次生成一个随机 salt 不就够了吗？如果客户端换请求号重发，结算服务又换了 txHash，哪些算同一件事？

**面试者：** salt 不能替代任何一层执行状态。它是签发订单时区分意图的字段，不是自动递增、自动消耗的全局安全开关。复制原订单会连同 salt 一起复制；V 如果不记录摘要已经使用，随机性再好也挡不住原样重放。

我会把身份分成以下几层，分别回答“在哪个边界防止重复效果”：

| 层次 | 身份与持久状态 | 能阻止什么，不能替代什么 |
|---|---|---|
| 签发 | owner 与订单中的 salt | 约定新意图使用新 salt；不替代已用摘要状态，也不凭随机性证明只执行一次 |
| 接入请求 | `(owner, requestKey)`、请求 `payloadHash`、`resultRef` | 同一请求同一载荷返回原结果，同键异载荷拒绝；换 requestKey 不能绕过 V 的订单状态 |
| 订单与锁资 | `orderHash`、摘要使用状态、锁资状态 | 同一摘要不能重复建锁；关闭或到期后也不能复活为一张新锁 |
| 成交义务 | `tradeId`、完整成交条款、双方 `fillSeq` | 重试交付同一份已提交义务；不能因切主、换批或广播失败另造一份成交 |
| 链交易尝试 | `chainId`、sender、txNonce、rawTx、txHash、替换关系 | 管理一次发送和同 nonce 替换；不代替成交层与合约执行层的经济去重 |

接入的请求记录应在同一个本地可靠提交边界内保存请求身份、载荷关联与可恢复结果；如果该步需要可靠外发，交付记录也必须可恢复。接口超时后查询原请求，不是另生成 requestKey 就假装原请求不存在。但这只覆盖接入边界，不能让本地数据库和 V 形成全局事务。

成交身份则来自可靠撮合日志，例如 `tradeId=H(venueId,logPartition,commitSeq,matchIndex)`。撮合提交时，双方 `open -= q`、`pending += q`，成交身份、条款、双方订单序号及可恢复交付事实要在同一可靠日志提交中确定。T1 到这一步就是 `COMMITTED`：它是一份不能因为链上失败而删除的义务，但还不是已交割资产，也不是交割保证。

结算时可以因加速产生新 txHash，也可以在确定需要重试后使用新的交易尝试；都必须保留原 tradeId 和经济载荷。txNonce 只约束某个发送者的交易顺序，换发送者或新 nonce 后仍可能再次调用 V，所以不能拿它当成交唯一键。`planHash` 绑定不可变计划，也不能用换计划、换 batchId 的方式把 T1 变成另一笔成交。

还有一个反向边界：用户确实签了两份不同 salt 的订单，它们通常就是两个不同的授权对象；系统不能只因为价格、数量相同就合并。它们能否同时成立，要由各自建锁及共同可用余额约束。这里没有“salt 一样自动撤掉全部旧单”或“换 salt 自动使旧签名失效”的协议。

## 第 4 层：在 V 的同一事务里消耗摘要并建立专属锁资

**面试官：** 你已经把接入去重和订单去重分开了。但假设同一个签名被两个不同 requestKey 同时提交，两边都查到用户有钱；或者建锁广播超时后又重试，怎样保证不会重复占资，也不会拿未锁住的钱撮合？

**面试者：** 最终裁决必须放在 V，不能放在两次链下“查余额成功”上。签名不是资金，钱包余额和 allowance 也不是本模型里的锁资。用户先把资产预存到 V，V 才能把它账内的 `available` 移到这一订单的专属 `locked`，使这笔资产不能再提现或被其他订单重复占用。

`lockOrder` 由基线中的授权中继提交，但 V 仍独立完成校验。执行时重算订单摘要，验证用户签名，检查支持的规则、资产、网格、期限及摘要尚未使用，再检查可用余额足够。随后在同一 EVM 事务内共同完成：

1. 记录该摘要已建立锁资，不能再次建锁。
2. 从对应 owner 的可用余额扣除锁定数量，增加该 orderHash 的专属锁资。
3. 保存 `owner/side/assets/Q/limit/D/feeVersion` 等已接受条款，并初始化 `filledBase/cumQuote/feeCharged/nextFillSeq/status`；`nextFillSeq` 从 1 开始。
4. 产生与本次状态变化一致的建锁事件，供观察器建立可回滚投影。

本例 A 的最大名义金额是 2,010 USDC，最大买费为 2.01 USDC，因此锁 2,012.01 USDC；B 锁 1 WETH。签名、余额和使用状态有任何一个检查失败，整次建锁回滚，不能留下“摘要已消耗但资产没锁上”或“扣了 available 却没有锁资对象”的半边状态。

两笔建锁交易最终按链上顺序执行。若它们使用同一 orderHash，第一笔成功后，第二笔即使换 requestKey、sender 或 nonce，也不能再次建锁；服务可查询并返回原锁资事实，不能把拒绝重复建锁误报成订单资金丢失。若它们是不同摘要，则分别检查执行当时的可用余额，可用余额不足的那一笔失败，不能都凭旧查询结果成功。

广播超时是结果未知，不是证明建锁失败。服务保留原建锁意图及交易尝试，查询或恢复原交易，也可以按同一订单身份查 V，但不能再分配一份新的经济意图来掩盖未知结果。锁最终关闭后，摘要的使用事实也要保留，不能删除锁记录后允许原签名重新建锁。

撮合准入还比“建锁交易成功返回”更严格：观察器必须确认目标锁资出现在最终规范链，且 owner、条款、锁状态和期限符合要求，才持久接纳到订单簿。建锁暂时入块后发生重组，不得已经在链下凭这份暂态资金产生成交。**授权正确、资金锁住、锁资最终确定，是三个连续条件，不能合并成一次接入验签。**

## 第 5 层：让受限结算出口同时受载荷、序号和资产约束

**面试官：** 现在你有了最终专属锁资，T1 也在日志里提交了。但执行交易的是撮合系统控制的结算出口，它能不能改数量、改费用，或者换个 txHash 再扣一次？相同请求重放时，为什么不能先检查 fillSeq？

**面试者：** 最终锁资不意味着结算出口可以任意使用锁里的钱。V 要同时检查调用权限、成交身份与载荷、订单约束以及当前资产状态；这些检查共同限定新效果。它不能只相信“这是内部服务发来的”。

首先检查调用者是 V **当前授权结算角色**。然后按固定、无歧义的规则重算完整成交载荷的 `payloadHash`。载荷绑定 tradeId、买卖双方 orderHash、双方各自的 fillSeq、基础资产数量、价格、maker 及相关费用和规则版本。资产、owner 和期限从对应锁资条款确定；如果载荷也携带这些字段，必须一致，不能形成第二套可覆盖锁资的条款。名义金额和本次费用由既定整数规则复算，不能相信调用者传来的金额。

接着检查 `executed[tradeId]`，且要先于新 fill 的序号检查：

- 已存在且等于这次 payloadHash：这是原效果的重试，不再改变锁资、余额、累计量或序号。
- 已存在但载荷不同：身份冲突，拒绝。原 T1 的执行结果不能被覆盖。
- 不存在：才作为新 fill 继续校验。

这是因为 T1 成功后双方下一序号已变为 2。若先要求 T1 的序号 1 等于当前 nextFillSeq，再做去重，就会把正常重试误判为新成交乱序。相同 T1 在锁关闭或 D 过去之后重放，也只是查证已完成的同一效果，不是重新执行一笔过期 fill。但**重复分支不绕过当前权限检查**；未授权者不能因为知道 tradeId 就获得结算调用权限。

对新 fill，V 检查双方锁存在且 ACTIVE、owner 不同，显式要求 `buy.side==BUY`、`sell.side==SELL`，两单绑定同一交易对的 base/quote 地址，买锁资产为 quote、卖锁资产为 base，不能仅检查方向相反；还要求 `block.timestamp <= min(buy.D,sell.D)`、双方序号分别等于各自 nextFillSeq、数量为正且不超各自剩余量、价格满足网格和双方限价、锁资足够。V 还检查载荷声明的 maker 是双方之一、成交价等于该 maker 的限价；它能检查这种字段一致性，却不能证明真实到达优先级。fillSeq 是每订单的连续序号，不是全市场序号；同一订单的后续成交不能越过先前依赖。跨批保守要求前驱已经最终交割，未最终前驱与后继须同批有序执行或先等待，不能只凭暂时入块就放行后继批次。

费用使用签名固定的 10 bps，累计名义金额为 C 时，`F(C)=ceil(C×10/10,000)`，本次只收 `F(C+N)-F(C)`，所有数值按报价资产最小单位计算。不能把一笔拆成多笔后逐笔向上取整多收，也不能在重试时套用新的费率版本。

T1 的 N 为 800 USDC、费用为 0.8 USDC。V 在同一事务内将 A 锁资减少 800.8、B 锁资减少 0.4 WETH，给 A 可用余额增加 0.4 WETH、给 B 增加 800 USDC、给费用账户增加 0.8 USDC，同时写入执行标记、累计量和双方 nextFillSeq=2。A 剩余锁资为 1,211.21 USDC，B 为 0.6 WETH；价格改善与费用余量此时不提前释放。基线整批原子，任一新 fill 失败则整批回滚；不留下半边扣款，也不在这里调用任意外部 token 转账。

链下可靠日志、结算计划与 Outbox 的本地事务、V 的 EVM 事务是不同边界。receipt 失败不会删除已提交 T1；Gas 与发送者 nonce 的消耗也不会随金库状态一起回滚。入块成功还要经过观察和最终性确认；观察器把最终履约证据作为带稳定身份的命令交回撮合状态所有者，由同一日志裁决 pending 转为 settled，不能让观察线程并发直接修改订单数量。重复执行返回本身也不是新的交割证明，需要核对原执行的规范链证据。

最后，tradeId 和 payloadHash 不是合法日志的密码学证明。被授权出口若伪造一个新 tradeId，仍可能在剩余授权范围内构造一笔链上可接受的成交；V 能限制越价、超量、任意收款和重复效果，却不能仅凭这个身份证明它确实来自合法撮合日志。这个信任不能被“我们有幂等”掩盖。

## 第 6 层：撤单只停 open，正常关闭和到期退出分别裁决

**面试官：** 你说 V 不知道完整链下日志，而且 COMMITTED 失败后不能删。那 T1 已提交、尚未最终交割时，用户撤单是不是应该立即让签名失效并退回锁资？若给 closeLock 加角色检查和 expectedFilledBase，能否由链上保证不会漏掉 T1？

**面试者：** 不能立即退回全部锁资，也不能把撤单理解为抹掉此前授权产生的成交义务。本基线没有另外增加一个链上撤销 nonce 或摘要黑名单协议，不能答到这里时悄悄引入它。

撤单与新成交进入同一权威撮合日志，由日志顺序裁决。若 T1 先提交，双方已经是 `open=0.6、pending=0.4`；撤单只能把 0.6 从 open 转为 cancelled，pending 仍为 0.4，链上锁资不释放。若撤单先提交，后面的撮合不能再用已取消的 open 形成新义务。接入服务删除订单缓存、停止展示，或者用户口头说“撤回签名”，都不能代替这个裁决。

这也揭示了撤单的能力边界：链下日志能禁止诚实撮合系统再生成新义务，但 V 并没有同步保存这次链下撤单裁决，不能独立阻止授权出口在锁尚 ACTIVE 时滥用原授权范围。要消除这类信任必须显式改变协议，不能声称现有撤单接口已经提供即时链上撤销。

正常提前关闭走 `closeLock(orderHash,expectedFilledBase)`。服务先保证订单没有 open，所有已提交义务均已最终交割，相关最终链观察与本地投影对齐，再允许当前授权出口提交关闭。V 检查当前角色、锁状态和实际 filledBase 是否等于 expectedFilledBase，在同一事务内关闭锁并释放剩余锁资；关闭是终态，不能重新建锁或继续执行新 fill。

但角色和计数检查**不能在链上证明没有链下义务**。反例是 T1 已 COMMITTED 却未上链，V 的 filledBase 仍为 0。错误出口提交 `expectedFilledBase=0`，计数完全对得上，却可能提前释放本该支撑 T1 的资金。因此，排空已提交义务、禁止新增 open、最终投影对齐，是授权出口必须承担的链下关闭前置条件；expectedFilledBase 只是防止与链上累计量不一致，不是“无 pending 证明”。广播未知或观察缺口存在时，也不能通过把 pending 手工清零来满足条件。

主例中 T1 最终交割后，双方 settled=0.4、pending=0，再撤 0.6 并最终关闭。A 释放 1,211.21 USDC 后可用 USDC 为 4,199.2，B 释放 0.6 WETH 后可用 WETH 为 1.6；A 仍有已买入的 0.4 WETH，B 有已卖出的 800 USDC。这是关闭后的资产事实，不是撤单请求返回时就能预记的余额。

到期是另一条独立路径。对同一订单，fill 只允许 `block.timestamp <= D`；`expireUnlock` 只允许 `block.timestamp > D`，任何人都可以触发，两个时间区间不重叠。它不要求“所有 pending 都已经交割”，因此确实可能释放支撑未交割义务的剩余资金；这正是基线不保证履约的原因，而不是逻辑上可以抹去 T1 的理由。若比较不同 D 的订单，fill 受双方较早的 D 限制，而各锁分别按自己的 D 到期，不能因一方先到期就提前释放另一方。

链下到期后的未成交 open 也要由同一撮合日志的过期裁决转为 cancelled，原因标记为 `EXPIRED`；pending 不能跟着取消，只能逐笔核查并转为 settled 或 defaulted。判定 T1 是否最终违约，还必须等最终规范链前缀越过相关执行截止点，并完整核验截止前历史；这一判断沿用总览关于规范后继块时间戳严格递增和可查询最终性的假设，不直接推广到任意 EVM 链。已交割的记为 SETTLED_FINAL，最终未交割的才进入 DEFAULTED_UNSETTLED，二者互斥。观察器将最终履约或违约证据以稳定身份命令交回撮合状态所有者，仍经同一日志裁决 pending 的去向，不由观察线程直接改量。到期解锁只记录实际资产释放，违约记录保留原 COMMITTED 事实；不自动赔付，也不把它改名为未成交。到期退出、正常 closeLock 与成交义务的终局核销不能合成一个“超时就撤单”的操作。

## 第 7 层：域升级不能追溯改写已经建锁的授权

**面试官：** 既然撤单不能随意抹掉已有义务，那升级呢？如果 V 仍是同一个代理地址，但域版本和费率规则换了，旧签名、旧锁以及 T1 应该怎样处理？能否直接按新域重算摘要，或者把旧锁全部认作失效？

**面试者：** 必须分开看“尚未建锁的旧签名”和“已经被 V 接受的旧锁”。域版本用于隔离授权语义，不是一个可以追溯删除义务的总开关。

对于尚未建锁的订单，新域入口只能按明确允许的域和规则验签，不能因为代理地址没变，就把旧签名自动当成新域签名。若新建锁只接受新域，旧签名不能在那里建新锁；若要继续接受旧域，则必须明确支持哪些旧类型和规则。这是需要说明的兼容决策，本题不默认增加双域接纳能力，也不把停止接纳旧签名描述成已经解除了既有锁资。

对于已经建锁的订单，V 保存的是当时接受的 orderHash 及其条款。结算通过这个原始身份查锁，不能使用当前域版本重算一个新 orderHash，再声称旧锁查不到或需要重新授权。旧锁中的 D、Q、限价、10 bps、feeVersion 及其累计取整含义都必须继续成立；T1 的 800 USDC 与 0.8 USDC 费用不能因升级变价。

这要求版本兼容不只停留在字段名。即使 `feeVersion` 数字没变，若把它原先指向的 10 bps 规则改成 20 bps，也是在改写旧授权。已锁条款必须保存足够的固定参数，或关联不可变语义的规则版本；执行新 fill 时选用该锁的规则，而不是读取一个能覆盖所有旧锁的“当前费率”。

同样必须保留摘要使用状态、锁的终态、累计成交量、累计费用、nextFillSeq 和 `executed[tradeId]=payloadHash`。升级若重置执行映射，旧 T1 可能重新产生效果；若重置摘要使用事实，已关闭订单可能再次建锁。这不是部署细节，而是授权与去重不变量的延续。旧域锁即便今后不再新建，也仍须有符合原规则的结算、正常关闭和到期处理路径，不能只把入口关掉就称为安全升级。

若换成另一个 V 地址，则执行域也变化。旧签名不能自然授权新 V，新 V 也不能把“复制数据库记录”解释成用户已经同意了资产和锁资迁移；需要另行明确同意与迁移设计，超出当前基线。本题不添加迁移失效协议来绕开问题。

最后，这些是升级必须遵守的安全条件，不是 EIP-712 对升级管理员的强制约束。如果某个管理权限可以任意替换 V 的代码，它也可能改掉验签、费用或资金规则；签名摘要不能在密码学上约束一个拥有任意改码权的管理员。应如实暴露升级权限这一信任边界，不能宣称“域版本正确，所以管理权限也无法侵害旧锁”。

## 第 8 层：ERC-1271 在建锁时验当前状态，建锁后不自动随 owner 变化失效

**面试官：** 你刚才强调已锁条款不能被升级悄悄改写。但若 owner 是 ERC-1271 合约钱包，钱包自己也能更换 owner：接入验签成功后、建锁执行前换了一次，或者建锁后又换一次，该以哪个时刻为准？每次 fill 都重新验签是否更安全？

**面试者：** 要把“签名此刻是否被钱包认可”和“V 已经接受并建立了什么授权”分开。对本题讨论的已部署 ERC-1271 合约钱包，V 调用钱包的 `isValidSignature(orderHash,signature)`，只有返回规定的成功值 `0x1626ba7e` 才按成功处理。调用回滚、返回格式不符或返回其他值都不能当作有效；不能因为服务不认识这个钱包，就退回到错误的 EOA 恢复地址逻辑。

ERC-1271 验签可以依赖钱包当前 owner、阈值、模块等状态，所以一次成功不是永久事实。链下接入可以先验，记录核验所依据的链、区块和摘要作为接入证据，但不能缓存成“这个钱包和签名永远有效”。**真正建立锁资时，V 必须在执行上下文中重新验签。**

可以按三个时间点推演：

1. **接入时成功，执行前变更。** 在区块 H，钱包认可旧 owner 的签名；随后先发生 owner 变更，再执行 lockOrder。如果新状态已不认可原签名，建锁必须失败。链下不能引用 H 上的成功缓存强行放行，也不能凭接入成功先撮合。V 的本次建锁状态与资金变化回滚，中继 Gas 则可能已消耗。
2. **建锁执行时有效。** 若 V 在实际执行时得到成功值，便在同一事务里接受这份条款并建立专属锁资；链下仍须等该锁在最终规范链上确定。接入记录、链上验签和最终撮合准入各有边界，不因为都叫“验签成功”就合并。
3. **最终建锁后钱包再次变更。** owner 变化可能使旧签名在新的 ERC-1271 查询中返回无效，但本基线不把这件事自动解释成已建锁授权失效。钱包地址仍是订单 owner，V 已接受的锁资条款、已提交 T1 以及正常关闭、D 和到期退出规则继续成立。

因此，在本模型里，fill 按 V 已存储的锁资授权执行，不在每笔 fill 前重新依赖钱包当前的签名认可结果。后来的控制者可以按既有鉴权规则发起撤单，停止尚未成交的 open，但仍不能因此释放 pending。若改为每笔 fill 都重新执行 ERC-1271，那么钱包后来变更 owner、撤销模块或修改验签逻辑，就可能使已经 COMMITTED 的成交无法交割；这引入新的即时失效渠道和履约故障窗，不是给现有模型加一句“再验一次更安全”。若要采用，必须重新定义义务和退出协议，本题不悄悄加入。

单次 EVM 事务内部也没有“钱包状态被另一笔交易从中间插入修改”的并发：链上交易按顺序执行，关键是验签依据执行当时的状态，而不是前端发送时或某次 RPC 查询时的状态。若未最终建锁发生重组，应回到新的规范链重新核对事实，不能继续用已经离开规范链的成功当作最终授权证据。

最终边界很明确：ERC-1271 解决合约钱包如何表达当前签名认可；V 的锁资状态决定已经接受的授权怎样执行；撮合日志决定哪些成交义务已提交；D 与退出规则决定还能否交割以及怎样记录违约。任何一层都不能靠永久缓存或后来更换 owner，越权改写另一层的权威事实。

## 本题收束

**机制：** 用户以 EIP-712 签署具体订单条款，orderHash 绑定条款、chainId、V 与域版本；V 在建锁事务内验签、记录摘要使用事实并移动可用资产。最终锁资后，撮合日志原子确定成交义务和每订单 fillSeq；结算出口受当前权限、完整 payloadHash、执行去重、序号与已锁条款共同限制。撤单只停止 open，正常关闭等待已提交义务最终交割并对齐投影，到期则走独立退出与违约核查。

**边界：** salt 不替代摘要使用状态，请求去重不替代链上去重，txHash 不代表成交身份；签名不等于锁资，入块不等于最终确定。COMMITTED 不可因链上失败删除，但不保证履约。授权角色与 expectedFilledBase 不能证明没有链下义务，tradeId 也不能证明来自合法撮合日志。域升级不得改写旧锁条款，ERC-1271 接入成功不可永久缓存，而后来更换钱包 owner 也不自动撤销已建锁授权。本模型没有额外失效协议、质押、保险或代偿保障。

**验证：** 以下是对授权边界的反例推演与预期判据，不是工程实测结果；唯一 MVP 仍在总览。

| 反例或检查点 | 必须得到的解释 |
|---|---|
| 原签名换 chainId、V、域版本或费用条款 | 不能被解释为同一授权；必须按执行域和完整条款重算摘要并校验 |
| 同一 orderHash 换 requestKey、sender 或 txNonce 再建锁 | 不得重复占资；即便原锁已关闭或到期，也不能重新建锁 |
| 当前授权出口重放完全相同 T1 | 执行标记在序号前识别原效果，不再次改变余额、费用或累计量；未授权调用仍先被权限拒绝 |
| 沿用 T1 身份但把数量改成 0.5 WETH | payloadHash 冲突，拒绝，不覆盖原 T1 |
| T1 已 COMMITTED、链上 filledBase 仍为 0 时提交 closeLock，expectedFilledBase=0 | 不能声称计数检查已证明没有义务；这是链下关闭前置条件必须阻止的错误 |
| 在 D 时执行新 fill，或尝试到期解锁 | fill 仍须满足全部条件；expireUnlock 必须严格晚于该锁的 D，不能与 fill 的合法时段重叠 |
| 最终链越过截止点，T1 未交割但锁资已到期释放 | 保留原成交与违约事实，不说未成交、不自动赔付，也不与已最终成功的结算同时核销 |
| ERC-1271 接入成功后、建锁前变更状态；或最终建锁后才更换 owner | 前者依执行时重新验签决定能否建锁；后者不自动废除已锁条款，更不删除已有成交义务 |

沿主例还可复核最终关闭后的资产守恒：USDC 为 `4,199.2 + 800 + 0.8 = 5,000`，WETH 为 `0.4 + 1.6 = 2`。这组数值只能在 T1 最终交割、余量撤销且关闭最终完成后使用，不能提前写进撤单回报作为已释放资金。
