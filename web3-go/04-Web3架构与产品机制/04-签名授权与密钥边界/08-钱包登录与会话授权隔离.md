# 大问题 8：钱包签名登录怎样防重放，又怎样避免登录会话被误当成资产操作授权？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| SIWE / EIP-4361 | 用以太坊钱包证明登录身份的消息规范。 | A 对特定站点和挑战作身份声明，不等于批准 1000 USDC 兑换。 |
| ERC-191 / EIP-712 | 登录消息所用签名封装、兑换所用结构化签名规范。 | 两类摘要按各自规则计算，不能把同一签名换解释跨用途使用。 |
| challenge / 登录 nonce | 服务端为这次登录发的一次性随机挑战。 | 不复用意图 42、Permit nonce 或交易 nonce；客户端不能自选一个就登录。 |
| 128 位 / 32 位十六进制 | 随机强度、同一随机值的一种字符编码。 | 本文示例用安全随机源产生挑战，不是 32 个随机二进制位。 |
| scheme / domain / URI | 访问协议、站点域名、目标资源标识。 | 按可信配置核对，不盲信请求中的 Host、Origin 或转发头。 |
| issued-at / not-before / 到期 | 签发时刻、最早使用时刻、最迟有效时刻。 | 校验消息时间窗；事务外验签后，提交前还要复核当前有效期。 |
| 浏览器绑定 / 消息哈希 | 挑战与预登录浏览器凭据的联系、精确消息指纹。 | 防把别处取得的挑战和签名拼成另一浏览器的会话。 |
| 条件更新 / 影响行数 | 只有条件仍满足才修改、实际修改了几条记录。 | 未用且未过期的挑战只能被一个并发请求成功消费。 |
| 数据库事务 / 会话创建 | 本地状态共同提交、建立已认证访问身份。 | 挑战消费和会话插入同成同败，不是先查再删的松散两步。 |
| 会话令牌 / Cookie | 访问服务的秘密凭证、浏览器传递凭证的载体。 | 服务端保存令牌摘要，提交后发送；响应丢失不代表会话没有创建。 |
| Secure / HttpOnly / SameSite | Cookie 的安全传输、脚本访问、跨站发送限制。 | 与 CSRF 防护和权限校验共同保护会话，不是任一选项包办全部风险。 |
| CSRF | 借浏览器已有凭证诱使其跨站发起操作的风险。 | 有副作用的 API 要检查来源和授权，不能只凭带 Cookie 就放行。 |
| chainId / address / 权限范围 | 认证链、认证地址、会话允许访问的服务能力。 | 主体来自已验会话，请求体的地址或前端切钱包不能自动改主体。 |
| ERC-1271 / 状态变化 | 合约钱包的验签接口、成员或模块等授权条件改变。 | 登录时有效不等于永久有效，更不替 X 的执行时验签。 |
| SwapIntent / allowance / R | 兑换授权、Token 扣款额度、代付 Gas 的转发者。 | 会话不能补出 A 的意图签名，R 的私钥也不能代签 A。 |
| 登出 / 停止转发 / 链上取消 | 撤销会话、停止自家任务、取消 X 的一次性权限。 | 三种裁决面独立，完成前两种不代表旧意图已不能执行。 |

## 把整篇文章压缩成一个故事

**起因：** 小林用地址 A 登录产品，只想查看自己的兑换记录。服务端生成安全随机挑战，绑定当前预登录浏览器与精确 SIWE 消息，要求钱包签的是指定站点、链、地址和有效时间，而不是把 A 已有的 1000 USDC allowance 或第 42 号兑换意图拿来当登录凭据。

**处理及异常：** Go 按 ERC-191 的 SIWE 消息验签，再在短数据库事务里核对未消费、未过期、浏览器绑定和消息哈希，以一次条件更新消费挑战并插入会话。两个并发请求只能一个成功，不能先查未用再各自建会话；若事务已提交但 Cookie 响应丢失，也不能把挑战释放后重建会话。最简处理是重新申请独立挑战；找回原令牌则需要额外的受保护浏览器证明，公开 challengeID 不是取令牌凭证。

**结果及边界：** 登录成功只让已认证 A 在会话范围内访问 API，请求体不能把主体换成 B。即便 A 早已 approve X，Cookie 加一段未签 JSON 仍不能授权 1000 USDC 兑换，必须另有完整 SwapIntent 并由 X 执行时裁决。小林登出并停掉自家 R 后，别人仍可能转发未过期、未取消且资金条件满足的旧意图；真正撤销还需链上取消或提高 epoch 并接受执行竞争。这里不把会话安全设计冒称为已完成并发或钱包实测。

**流程位置与核心机制：** 本题讨论进入产品时的身份认证、challenge 消费和会话创建，并解释它们为什么不属于兑换意图或 Token 授权。核心闭环是“服务端生成登录挑战—验证精确上下文—原子消费并创建会话—按会话权限访问服务”，不是“登录后服务器就能代用户签交易”。

**沿用基线与扩展边界：** 普通 EOA A 自持私钥；Relayer R 是另一个 EOA，服务端只管理 R 的 Gas 私钥。兑换仍在教学 `chainId=1`、域 `OneTrade / 1 / X` 下执行，X 不可升级，`SwapIntent` 字段固定为 `owner、tokenIn、tokenOut、amountIn、minAmountOut、recipient、nonce、epoch、deadline、routeHash`。A 有 1500 USDC，已单独授权 X 1000 USDC；意图 `nonce=42、epoch=7、deadline=T0+120秒`，花 1000 USDC、至少得 0.49 WETH，示例得 0.50 WETH，收款人为 A。SIWE 登录使用独立挑战，不复用意图 nonce、permit nonce 或交易 nonce。已部署 ERC-1271 钱包登录是显式扩展，不默认支持未部署钱包或 EIP-7702 账户能力。

## 第 1 层：钱包登录究竟证明了什么

**面试官：** A 用钱包完成了 SIWE 签名登录，后端能否据此替 A 执行这笔 1000 USDC 的兑换？

**面试者：** 不能。SIWE 证明的是用户对指定站点、指定登录挑战的身份声明，服务端据此建立登录会话，例如允许 A 查询自己的意图记录；它不等于 Token approve、permit，也不是 X 所要求的 SwapIntent。SIWE 按 EIP-4361 的消息格式及 ERC-191 签名封装验证，兑换则有自己固定的 EIP-712 域、结构字段和链上消费规则，不能把同一签名换一个解释就当成交易授权。即使 A 已独立 approve X 1000 USDC，后端仍要拿到正确的兑换意图签名，X 也必须完整验签和执行。R 的私钥只负责外层交易和 Gas，不因用户登录而获得 A 的签名能力。

## 第 2 层：怎样让登录证明只对当前站点和请求有效

**面试官：** 你说登录只证明指定站点的身份。攻击者若从别的网站拿到 A 的签名，或者重放 A 昨天的登录消息，服务端靠什么拒绝？

**面试者：** challenge 必须由服务端生成并保存，不能接受客户端自选一个 nonce 再直接验签。可以使用密码学安全随机源生成 128 位随机值，编码成符合 SIWE 字符要求的 32 位十六进制 nonce，并绑定预登录浏览器凭据及预期消息。服务端逐项核对受信配置中的 scheme、domain、URI、chainId、address、version、issued-at、到期时间和可选 not-before；若配置了 request-id 等约束也一并匹配。域源判断不能信任客户端随意提交的 Origin、Host 或转发头，应由可信代理与配置确定。签名覆盖的必须是发出的精确消息，不能静默补字段或换前缀。时间窗口检查和 nonce 一次性消费共同防重放，只有过期时间而没有消费状态并不够。

## 第 3 层：并发登录为什么必须原子消费挑战

**面试官：** 上一答已经保存了 nonce。两个请求同时提交同一份有效登录消息，如果代码先查询“未使用”，验签成功后再删除 nonce，会发生什么？

**面试者：** 两个请求可能都在删除前读到未使用，分别创建会话，因此“查完再删”没有一次性保证。我会在同一个数据库事务里，按 challengeID 条件更新挑战：要求未消费、未过期、预登录凭据绑定正确，且保存的消息哈希与本次一致；检查影响行数恰好为一，再插入会话并提交。会话保存核验后的 chainId、address、认证方式、认证时间和权限范围，不能取客户端另传的地址。条件更新失败的并发请求不能再创建第二份会话；会话插入失败则整笔事务回滚，挑战也不能留下“消费了却没有会话”的中间状态。Redis 删除与数据库插入若没有共同原子边界，不能被描述成等价实现。

## 第 4 层：验签慢或响应丢失时怎样维持原子语义

**面试官：** 你把挑战消费和会话创建放进一个事务，但验签可能慢，提交后浏览器也可能没收到响应。是不是要一直锁着挑战直到 Cookie 确认送达？

**面试者：** 不需要，也做不到把数据库提交和浏览器收 Cookie 变成同一个事务。可以先读取不可变挑战并在事务外验证签名，再在短事务里重新检查消息哈希、浏览器绑定、当前到期时间和消费条件，避免验签期间过期却被放行；验签通过本身不消费挑战。会话令牌应来自安全随机源，服务端保存其摘要，Cookie 只在提交后发送。若提交已成功但响应丢失，挑战仍已消费，不能因为超时就释放或再创建新会话。最简安全策略是让用户重新申请独立挑战登录；若要恢复原结果，必须额外设计基于原浏览器证明的受保护交付机制，不能只凭公开 challengeID 就返回有效令牌。

## 第 5 层：EOA 和合约钱包登录怎样分别核验

**面试官：** 你在事务外验证签名。普通 EOA 可以恢复地址，但若用户登录的是合约钱包，缓存一次验签通过以后，会话能一直有效吗？

**面试者：** 普通 EOA 路径按 SIWE 精确消息的 ERC-191 digest 验证 secp256k1 签名并匹配 A，不能拿兑换的 EIP-712 digest 来替代。已部署合约钱包扩展则在消息声明的链上，向该钱包做 ERC-1271 验证，要求正确 magic；预检应记录明确区块引用，不能把任意链上的同地址视为同一钱包状态。1271 结果可能随成员、阈值或模块变化，登录会话策略应考虑这些变化，通过重新认证、相关状态变化后的失效处理和敏感操作重验控制风险，不能承诺永久有效。数据库原子事务只解决 challenge 与会话状态，不会锁住钱包链上状态；后续链上兑换仍由 X 在实际执行时重新验签。

## 第 6 层：会话有效为什么还不能替代交易授权

**面试官：** 上一答说敏感操作要重新核验。那么登录会话存在时，前端提交一段“花 1000 USDC”的 JSON，后端替它补齐并转给 R，是否就足够了？

**面试者：** 不足够。会话只能授权调用某个 API，不能把未签名 JSON 升格成 A 的资产意图。后端应从独立的 SwapIntent 签名验证 owner、recipient、amountIn、minAmountOut、nonce、epoch、deadline 和 routeHash，域严格为链 1 的 X，并让 X 在执行时重复裁决。登录 nonce、意图 42、Token permit nonce 和 R 的交易 nonce 分别属于不同状态机，不能为了“统一幂等”混用。SIWE 的 resources 或文字声明也不自动构成 X 能执行的权限。如果产品真要让会话密钥代签，必须显式引入钱包委托或新的授权协议，限制动作和额度；那是改变前提的扩展，不是给现有登录 Cookie 增加一个字段就完成了。

## 第 7 层：浏览器会话本身怎样避免串号与越权

**面试官：** 你要求 API 和交易权限分离，但如果 Cookie 被滥用，或者钱包从 A 切换成 B，登录会话是不是仍可能让服务端按错账户处理请求？

**面试者：** 服务端授权主体必须来自已认证会话中的 chainId 与 address，不能由请求体的 address 覆盖。前端切钱包、切链并不自动改变服务器身份，应明确结束或切换旧会话，再按新身份重新认证；公开地址的查询能力与“自己的记录”访问权限要分开。Cookie 应采用 Secure、HttpOnly 和适当 SameSite，并对有副作用的接口实施 CSRF 防护、可信来源检查和权限校验，SameSite 不能替代全部防护。登出和吊销只撤销会话访问，不能撤销别人已持有的有效 SwapIntent；同理，会话失陷可能泄露数据、滥用提交时机或消耗服务资源，但在没有额外资产委托的基线里，不能凭 Cookie 伪造 A 的新签名。

## 第 8 层：怎样证明三个撤销面没有被混在一起

**面试官：** 你说登出不能撤销交易签名。用户点击“退出并停止交易”，页面显示成功，稍后别人转发旧意图成交，这究竟是漏洞还是产品承诺错误？

**面试者：** 要看承诺覆盖什么。退出会话、停止自己的 Relayer 和链上取消意图是三种不同动作：第一种由会话存储裁决，第二种只约束自身服务，第三种必须由 owner 在 X 上取消 nonce 或提高 epoch，且与执行按链上顺序竞争，最终确认前还存在重组风险。产品若只完成前两种却声称已撤销所有交易权限，就是错误承诺。可以手工推演：同一挑战并发提交只产生一个会话；过期或跨域消息不能登录；有效 Cookie 加未签名兑换不能扣款；登出后旧意图在未取消、未过期且资金条件满足时仍可被任何 Relayer 转发。这些反例分别检验认证、会话和资产授权边界，而不是把所有失败都归因于“nonce 没做好”。

## 本题收束

- **讲透的机制：** SIWE 校验站点、链、地址、时间与独立挑战；挑战一次性消费和会话创建必须共同提交，签名验证与会话令牌交付有各自的故障边界。
- **最易答错的边界：** 登录不是交易授权；验签成功不等于挑战已经消费；响应超时不等于数据库未提交；1271 的登录结果不代表未来交易时的权限状态。
- **检验反例：** 两个请求先后读到同一未使用 nonce，然后各自建会话，最后才删除 nonce。即使签名、域和到期检查都正确，也违反了挑战一次性语义。另一个反例是登出后旧意图仍成交，它检验的是产品有没有把会话撤销冒充链上撤销。
