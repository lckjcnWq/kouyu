# 大问题 3：Go 服务怎样正确验一份 EIP-712 签名，避免整数、前缀、v 和钱包类型边界出错？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| schema / domain | 固定数据结构、可信的签名适用环境。 | Go 按已知 OneTrade / 1 / 链 1 / X 解析，不能任由前端指定一种能通过的规则。 |
| uint256 / 2²⁵⁶−1 | 有上限的 256 位非负整数。 | 拒绝负数、科学计数、非法前导零和越界，不截断高位凑结果。 |
| 最小单位 / float64 | 精确整数记账、可能舍入的大范围浮点表示。 | 1000 USDC 是 1000000000，0.49 WETH 是 490000000000000000，金额不经浮点中转。 |
| big.Int / 接收者 | Go 的大整数对象、运算结果会写入的对象。 | Add、Mul、Set 会改值；浅复制含指针的意图不代表隔离了金额。 |
| goroutine / 不可变快照 | Go 并发任务、之后不再改动的一份输入副本。 | 在安全所有权或锁边界深复制；复制期间也不能有人同时写原对象。 |
| ABI / address / bytes32 | 有类型编码、20 字节地址、32 字节数据。 | 地址严格解码后补齐到 32 字节，routeHash 必须恰好解出 32 字节。 |
| Keccak / SHA3-256 | 两种不能互换的哈希算法。 | 本文用 Ethereum Keccak-256；算法名字相近不代表摘要相同。 |
| digest / personal_sign | 待验的摘要、另一类带消息前缀的签名方式。 | 本文只按 EIP-712 重建摘要，不轮流改前缀试到恢复成功。 |
| secp256k1 / ECDSA | 本例普通账户使用的曲线和数字签名机制。 | 证明具体摘要与签署地址的关系，不证明余额和意图状态。 |
| r / s / v / `\|\|` | 签名的两个整数、恢复标识、字节拼接。 | EOA 入口明确只收 65 字节 r、s、v；v 只适配 0/1 或 27/28。 |
| low-s / high-s | 把 s 限制在曲线阶一半以内、超出该范围的形式。 | 显式拒绝 high-s，不能以交易已有规则为由省掉消息验签检查。 |
| SigToPub / recover / owner | 恢复公钥的函数、恢复动作、声明的授权人。 | 校验格式和值后恢复地址，再与严格解析且非零的 owner 比较。 |
| EIP-155 / EIP-2098 | 交易签名链绑定规则、64 字节紧凑消息签名格式。 | 不能用交易 v 算式盲减，也不把未声明支持的 64 字节当作 65 字节处理。 |
| digest / 消费键 | 完整内容指纹、业务一次性权限的身份。 | 比内容用 digest；消费看链、X、owner、epoch、nonce，不以签名字节去重。 |
| RPC / context / 区块观察 | 读链接口、调用取消或超时控制、所读链状态的位置。 | 超时只说明没拿到观察结论；预检有效也不保证执行时仍有效。 |
| ERC-1271 / 0x1626ba7e | 合约钱包验签标准、其规定的有效返回魔数。 | 属于另设能力的分支，不能用普通 EOA 恢复地址代替，也不天然覆盖所有新账户类型。 |

## 把整篇文章压缩成一个故事

**起因：** 小林已在钱包签下 A 的 1000 USDC 换至少 0.49 WETH 意图，前端却说 Go 验不过。后端先固定可信域和数据结构，把金额按精度解析为 1000000000 与 490000000000000000，严格检查地址、路线指纹和 uint256 范围，而不是在 EIP-712、裸哈希、personal_sign 之间碰运气。

**处理及异常：** 工程师逐步比较 typeHash 对应的类型、domainSeparator、structHash 和 digest，确认使用 Ethereum Keccak 与有类型 ABI，再检查 65 字节 r/s/v、合法 v、low-s 和恢复出的 owner。若两个 goroutine 共用 amountIn 的 big.Int，一个算完摘要、另一个又修改金额，真实 calldata 就可能偏离验过的内容；必须在没有并发写入的边界深复制为不可变快照。完整签名也不放进公开日志排错，更不能为使验签通过而放宽输入规则。

**结果及边界：** 验过只能说明 A 签过这份准确字节内容，Go 还要在明确区块检查 nonce、epoch、期限、余额和 allowance，X 到执行时再裁决。不同合法签名字节不代表两笔独立兑换，同域 A/7/42 仍只能成功消费一次；若扩展合约钱包，须按 ERC-1271 的状态相关验证另行处理。本篇给的是验证设计与代码片段，不把排错流程说成已跑过跨端向量、Go 测试或链上执行。

**流程位置与核心机制：** 本题深入 Go 接收意图之后、Relayer 构造外层交易之前的确定性验签，重点是受限整数转换、ABI 编码、secp256k1 签名格式和并发安全。Go 预检不取代 X 执行时的验签与状态检查。

**讨论前提：** 沿用 `OneTrade / 1 / chainId=1 / X`，普通 EOA A、nonce=42、epoch=7、120 秒期限。X 和资产地址仍是教学占位，本文不提供可广播载荷。代码按 Go 1.21+ 与 go-ethereum 的常用接口说明，是纯验证片段，没有创建工程、指定依赖补丁版或实际运行测试。

## 第 1 层：先固定验签输入，而不是“试到能 recover 为止”

**面试官：** Go 收到前端提交的 SwapIntent 和签名，你怎样组织验签流程？

**面试者：** 我先把请求当作不可信输入，按固定 schema 解析字段，拒绝缺失、额外语义和越界值，再用服务已知的域配置计算 EIP-712 digest，最后按声明支持的签名格式恢复并比较 owner。域不能由前端任意选择，X、token 地址必须严格解码，不能用会静默填充或截断的转换掩盖错误。amountIn、minAmountOut 等 uint256 用十进制字符串传输并受限解析，不经过 float64。验签日志记录 schema 版本、domainSeparator、structHash 和 digest，以便定位差异；不允许 personal_sign、EIP-712、裸哈希之间黑箱重试，碰巧恢复出一个地址不能证明用户签过当前业务。

## 第 2 层：uint256 在 Go 中怎样不丢精度也不共享可变对象

**面试官：** 你说用十进制字符串和 big.Int，具体怎样拒绝溢出？多个 goroutine 共用意图对象又有什么问题？

**面试者：** 字符串应先限定为规范非负十进制，拒绝负号、科学计数、空值和超过 uint256 范围的输入，再转换成独立 big.Int。1000 USDC 必须是 `1000000000`，最小 0.49 WETH 是 `490000000000000000`；若先过 float64，即使后来转回整数也可能已丢位。big.Int 的 Add、Mul、Set 都会修改接收者，把同一指针放到多个任务里，会使预检、哈希和实际 calldata 看到不同数值。我会在受控的所有权或锁边界深复制字段，之后把请求快照视为不可变。复制本身也不能与另一 goroutine 的写入并发，否则仍然存在数据竞争。

以下是受限转换片段；ABI 编码时继续使用返回的整数，不再转回显示小数。

```go
package intentcheck

import (
    "fmt"
    "math/big"
)

func parseUint256Decimal(s string) (*big.Int, error) {
    if len(s) == 0 || len(s) > 78 || (len(s) > 1 && s[0] == '0') {
        return nil, fmt.Errorf("uint256 不是规范十进制字符串")
    }
    for _, c := range s {
        if c < '0' || c > '9' {
            return nil, fmt.Errorf("uint256 包含非法字符")
        }
    }
    n, ok := new(big.Int).SetString(s, 10)
    if !ok || n.Sign() < 0 || n.BitLen() > 256 {
        return nil, fmt.Errorf("uint256 转换失败或超出范围")
    }
    return n, nil
}
```

## 第 3 层：整数正确后，字节编码和签名格式还要怎样约束

**面试官：** 整数已经安全了，接下来怎样保证传给恢复函数的 digest 和签名字节也没有被偷偷变形？

**面试者：** 我用有类型 ABI 编码生成 structHash，再算 `Keccak256(0x19,0x01,domainSeparator,structHash)`；这里用 Ethereum Keccak，不是 SHA3-256，也不额外增加 personal_sign 前缀。address 用严格解析后的 20 字节值，ABI 编成左补零的 32 字节槽，routeHash 必须严格解出 32 字节。签名入口则明确只收 65 字节 `r || s || v`，十六进制解码错误或长度错误立即返回。若将来支持 EIP-2098 的 64 字节紧凑签名，应新增明确适配，不能把任意 64 字节都当作相同格式。v 只兼容 0/1 或 27/28，绝不套用外层交易 EIP-155 的 v 算式去盲减。

## 第 4 层：v、r、s 检查与地址恢复怎样落成代码

**面试官：** 你限定了 65 字节，那具体怎样检查低 s 和恢复地址，避免只调用一次 SigToPub 就认为验签完成？

**面试者：** 我先复制签名字节，避免为了适配 v 修改调用方共享的切片；然后归一化 v，严格检查 r、s 非零且小于曲线阶，并要求 low-s。low-s 只接受 s 不大于曲线阶的一半，减少同一授权的可塑编码。EIP-2 对交易签名的 low-s 要求不能替代这里的检查，因为 ecrecover 预编译仍接受 high-s 消息签名。通过这些检查后恢复公钥，转成 Ethereum 地址，与已经严格解析的 owner 比较，不匹配就拒绝。下面函数只验证“这个 digest 的签署地址是否为 owner”，不会判断 chainId、deadline 或 used；这些条件必须由上游构造可信 digest，并在 X 中再次执行。输入切片在复制期间也须保持不被其他 goroutine 写入。

```go
package intentcheck

import (
    "fmt"
    "math/big"

    "github.com/ethereum/go-ethereum/common"
    "github.com/ethereum/go-ethereum/crypto"
)

func verifyEOA65(digest common.Hash, raw []byte, owner common.Address) error {
    if owner == (common.Address{}) {
        return fmt.Errorf("owner 不能为零地址")
    }
    if len(raw) != 65 {
        return fmt.Errorf("只接受 65 字节的 r||s||v 签名")
    }
    sig := append([]byte(nil), raw...)
    switch sig[64] {
    case 0, 1:
    case 27, 28:
        sig[64] -= 27
    default:
        return fmt.Errorf("不支持的恢复标识 v=%d", sig[64])
    }
    r := new(big.Int).SetBytes(sig[:32])
    s := new(big.Int).SetBytes(sig[32:64])
    if !crypto.ValidateSignatureValues(sig[64], r, s, true) {
        return fmt.Errorf("r/s 越界或不满足 low-s")
    }
    pub, err := crypto.SigToPub(digest[:], sig)
    if err != nil {
        return fmt.Errorf("恢复公钥失败: %w", err)
    }
    if got := crypto.PubkeyToAddress(*pub); got != owner {
        return fmt.Errorf("签署地址与 owner 不匹配")
    }
    return nil
}
```

## 第 5 层：low-s 之后为什么仍不能拿签名字节做业务去重

**面试官：** 你已经拒绝 high-s，并把 v 规范化了，可以把签名字节的哈希当成业务幂等键吗？

**面试者：** 仍然不可以。low-s 只约束一种编码可塑性，同一人仍可能对同一 digest 产生不同的合法签名；以后扩展合约钱包时，更不能假设签名字节恒定。用于比对完整已签内容的是 digest，用于一次性业务消费的是 `(chainId,X,owner,epoch,nonce)`。同键不同 digest 是权限冲突，不能因为签名 bytes 不同就当成两个独立兑换。Go 数据库可以以该键建立唯一约束并保存原 digest，收到同键同内容则返回原任务，同键不同内容返回明确冲突；但这只是自身服务的受理规则，X 的 used 才能阻止其他 Relayer 重复消费。

## 第 6 层：recover 成功后，预检为什么仍要查链上状态

**面试官：** 你已经确定 owner 签过这份内容，也做了本地去重，为什么还要在指定区块做预检？

**面试者：** EOA 恢复结果只证明当前字节的签署关系，不证明 nonce 未用、epoch 仍为 7、deadline 未到、余额和 allowance 足够。Go 应把读取绑定到同一明确区块的编号或哈希，读取 X 与 Token 状态，必要时模拟完整入口，并记录这个观察位置。向 RPC 发送的调用可以有 context 超时，但 RPC 超时只能得出“观察未知”，不能反推交易失败或取消成功。执行时状态仍可能变化，所以 X 必须重新检查；一笔输出不足的 revert 会让本次 used 和资金变化回滚，但 R 的 Gas 可能已支出。不能把预检区块的有效性缓存成直到 deadline 都必然能成交的承诺。

## 第 7 层：一个 recover helper 能不能覆盖所有现实钱包

**面试官：** 如果某个用户填的是合约钱包地址，你刚才的 recover 与 owner 比较还成立吗？

**面试者：** 那就明确改变了普通 EOA 前提，不能把合约钱包地址当作某个公钥恢复地址。若产品新增已部署 ERC-1271 钱包支持，Go 应按该能力调用 owner 的 isValidSignature，检查魔数 `0x1626ba7e`，处理 revert、错误返回和 RPC 失败，并记录指定链及区块；X 执行时仍须再验，因为钱包授权状态可变化。刚才的 65 字节限制只是 EOA 分支，1271 的签名 bytes 应按钱包协议处理并设置资源边界。也不能仅凭 hasCode 把所有现实账户天然二分为 EOA 与 1271；未部署钱包、ERC-6492 或 EIP-7702 都需要单独能力设计，不在本基线中偷偷接入。

## 第 8 层：怎样给出可信的排错与验证结论

**面试官：** 你已经划清了钱包类型，前端仍然说“钱包显示签名成功，Go 却验不过”，你怎样排查而不放宽规则？

**面试者：** 我会先在 EOA 基线内定位：逐项对比类型字符串、域值、地址原始字节、最小单位整数、routeHash、domainSeparator、structHash 和最终 digest，再检查签名十六进制、长度、v 与 low-s；这样能说明差异发生在哪一步，而不是换前缀试到成功。排错不记录私钥，也不把完整可执行签名暴露到公开日志。设计上应准备跨端一致性向量，以及错误链 ID、错误 X、改 recipient、溢出整数、非法 v、high-s 和同键不同内容的反例；本题仅说明这些预期，不声称已运行。即使 Go 与钱包完全一致，最后仍由 X 的执行校验、原子消费和实际资产结果决定业务是否成立。

## 本题收束

- **讲透的机制：** 输入受限解析、精确整数、有类型 ABI、Keccak、明确签名格式和地址比较组成一条确定性验证链；不可变快照避免编码期间的 Go 数据竞争。
- **最易答错的边界：** 不能用 float64 过渡金额，不能把 SHA3-256 当作 Keccak，不能从 EIP-155 交易 v 盲推消息签名 v，不能用签名 bytes 去重业务，不能用 EOA recover 代替 1271。
- **检验反例：** 两个 goroutine 共用同一 amountIn 指针，一个计算摘要后另一个将它乘以精度，再拿修改后的值编码 calldata，签名检查与真实载荷就不再对应。只给 map 加锁或只复制顶层结构体都不能修复 big.Int 的共享可变状态。
