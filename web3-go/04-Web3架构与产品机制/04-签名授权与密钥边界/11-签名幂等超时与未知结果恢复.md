# 大问题 11：签名服务调用超时后，怎样防止重复授权并恢复未知结果？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| K_R / HSM / KMS | R 的私钥、受保护签名设备或密钥服务。 | 签的是 R 的 Gas 外层交易，不是替 A 重签用户兑换授权。 |
| jobID / payloadHash | 受控签名作业号、不可变载荷指纹。 | 同号同内容找原进度，同号改 Gas、nonce 或 calldata 必须拒绝覆盖。 |
| 意图键 / EIP-712 digest | 一次性业务权限身份、该权限具体内容的摘要。 | 链、X、A、epoch、nonce 与完整内容分别记录，不被新 jobID 绕开。 |
| txNonce / 签名预像 | R 的账户交易序号、签名前的准确交易内容。 | 同一外层槽位与同一内容的身份不同于 A 的业务 42。 |
| 尝试 / 签名实例 / txHash | 一次调用、一次产出的签名、签名交易的哈希。 | 同载荷不同 ECDSA 字节可能产生不同 hash，但不代表新兑换权限。 |
| 唯一约束 / 待投递记录 | 数据库防重复规则、可靠登记之后要发的任务。 | 能让本地受理不重复、不丢任务，不能证明设备至多签过一次。 |
| 本地事务 / 外部副作用 | 数据库共同提交边界、设备已产生的真实结果。 | SQL 回滚不能撤回 HSM 已生成的有效签名。 |
| exactly-once | 从头到尾恰好发生一次的强保证。 | 无明确设备接口契约就不能宣称数据库与 HSM 实现这种保证。 |
| 幂等查询 / 结果保留 | 同请求可重复查询原进度、签名结果能保存多久。 | 必须由真实接口支持；审计中“签过”不等于还能取回签名。 |
| 同载荷重签 | 在原作业内再次请求同一准确内容的签名。 | 需受控审批且保留尝试，不冒称找回了原始签名。 |
| context / 租约 / fencing token | 本地等待控制、暂时的推进权、隔离旧代工作者的令牌。 | 可限制谁继续派发和写状态，不能撤回旧工作者先前拿到的已签交易。 |
| 签名未知 / 广播未知 / 执行未知 | 不知道是否已签、不知道是否传播、不知道最终执行结论。 | 各自保存不同身份和证据，不能用一个含糊失败状态盖掉风险。 |
| used / 规范链证据 | 意图不可用状态、当前链分支上的回执事件。 | used 也可能来自取消，不能单凭 true 认定资产已兑换。 |
| Gas 预留 / nonce 占用 | 对可能费用的风险保留、外层槽位的管理状态。 | HTTP 超时或意图失效不代表已签 R 交易不能再花 Gas。 |
| cancelNonce / epoch / deadline | 单笔撤销、代次失效、链上执行期限。 | 分别裁决意图资格，等于期限仍可执行，均不撤回旧 allowance。 |
| 受限结果存储 / 重组 | 专门保存签名与原始交易的受控位置、链分支变化。 | 恢复材料不进普通日志；旧观察被移除后要按新链重查。 |

## 把整篇文章压缩成一个故事

**起因：** 小林的 A 已签好花 1000 USDC、至少收 0.49 WETH 的意图，Go 为 R 的外层交易建立固定 jobID 和 payloadHash。HSM 实际签完，响应却丢失，Go 随后重启。此时没有收到签名只代表结果未知，不能判定没签，更不能把页面更新为已有 500 USDC 和 0.50 WETH。

**处理及异常：** 恢复器先读原作业、审批和完整载荷，按确实存在的接口契约查签名结果；设备只留“已签”审计而不能返回结果时，就承认未知并保留风险。必要的同载荷重签也登记在原作业内，不能换 jobID、换 R 的交易 nonce 绕开控制。新工作者用代次与条件更新获得推进权，旧响应只能补充原尝试证据；围栏能限制旧任务继续推进，不能让它此前拿到的有效签名物理失效。

**结果及边界：** 若旧交易后来被别人广播，系统按 R、txNonce、完整载荷及交易身份关联原尝试，分开判断签名、传播和执行证据。X 成功且达到确认要求时，样例 A 为 1500−1000=500 USDC、0.50 WETH，allowance 为 0；若兑换回滚，则本次资金和 used 回滚，独立 approve 仍在，R 可能已付 Gas。意图取消或到期也不阻止旧外层交易被提交后花费 Gas，未知预算不能因本地超时直接释放；发生重组则撤回旧观察，不把未知硬改成终态。

**流程位置与核心机制：** 本题位于用户意图校验之后、Relayer 外层交易签名及其结果恢复阶段，重点是请求身份、不可变载荷、数据库与签名设备之间的非原子边界，以及签名、广播、执行三个阶段的独立不确定性；不展开交易广播系统的完整设计。

沿用教学基线：`chainId=1`，EIP-712 域为 `OneTrade/1/X`，X 是不可升级的执行合约，地址为教学占位值。A 自持用户私钥；R 的 Gas 私钥 `K_R` 由 HSM/KMS 管理，两把私钥绝不混用。A 的意图使用应用 nonce=42、epoch=7、`deadline=T0+120秒`，与外层交易的 R 账户 nonce 分开管理。下文的作业账本和查询接口是教学设计，不假定所有厂商设备天然提供。

## 第 1 层：请求超时究竟能说明什么

**面试官：** Go 服务调用 HSM 为这笔兑换的 Relayer 交易签名，等待超时了。你会把作业记为失败并重新发起吗？

**面试者：** 不会直接这样做。超时只说明调用方没在期限内拿到结果，不证明 HSM 没有收到请求，更不证明没有产生有效签名。签名可能已经完成，只是响应丢失；后台也可能仍在处理。我会把这次签名尝试标成结果未知，保留原 jobID、不可变载荷和调用记录，再查询或恢复原结果。这里签的是 R 为调用 X 支付 Gas 的外层交易，不是重新替 A 签兑换意图。即使恢复出签名，也只说明交易具备了提交条件，不能直接把页面更新为 A 已从 1500 USDC 变成 500 USDC 和 0.50 WETH。

## 第 2 层：原作业身份怎样绑定原权限

**面试官：** 你说要沿原 jobID 恢复。业务方复用这个 jobID，却把收款人、Gas 上限或交易 nonce 改了，怎么办？

**面试者：** jobID 不能只关联一条可随时覆盖的 JSON。我会在受理时固定语义明确的编码与 payloadHash，绑定 chainId、R、目标 X、value=0、selector、完整 calldata hash、Gas 与费用上限、外层 txNonce，以及 policyVersion、keyVersion 和审批记录。同 jobID 同载荷返回原进度，任何差异都拒绝覆盖。用户意图另有 EIP-712 digest，其一次性身份是 `(chainId,X,A,epoch,nonce)`；同键不同内容应作为冲突处理，不能借换 jobID 绕过。业务身份用于约束兑换资格，签名载荷身份用于约束这一次外层交易，二者不能混成一个 nonce。

## 第 3 层：并发受理是否会产生两个作业

**面试官：** 同一意图同时命中两个 Go 实例，它们都还查不到 jobID，你的“冲突处理”靠什么真正生效？

**面试者：** 不能靠先查后写。我会在共享数据库里用业务唯一键与载荷约束竞争受理，在同一个本地事务中写入作业、不可变审批引用和待投递记录；失败的一方读取胜出的原作业，比较载荷后返回。同一意图如需外层交易替换，应登记为原作业下的新尝试，不能重建一个不受约束的授权入口。签名任务投递可以重复，接收端仍要识别同一身份。这个唯一约束只消除了数据库内的重复受理；它没有让数据库事务覆盖 HSM，也没有证明设备至多执行过一次签名操作。

## 第 4 层：本地事务能否包住 HSM 调用

**面试官：** 既然数据库唯一约束管不到 HSM，我把事务一直开着，等签名完成再提交，不就一起成功或失败了吗？

**面试者：** 不成立。HSM 的密码操作不是数据库的事务参与者；即使回滚 SQL，也撤不回设备已经生成的有效签名。设备成功后进程崩溃、数据库提交失败，仍会留下“可能已签、账本未记”的窗口。我会先可靠记录待签权限，再由工作者调用独立签名服务，返回后补写结果；可靠投递解决任务不丢，不能消除外部副作用的不确定性。签名服务内部若也是“写本地库再调设备”，同样有这个窗口。除非实际接口明确提供可证明的幂等与结果保留契约，否则不能宣称端到端 exactly-once。

## 第 5 层：怎样恢复一份可能存在的签名

**面试官：** 那设备已经签了、签名服务还没保存响应就崩溃，你具体去哪儿找原结果？

**面试者：** 先查签名服务的持久作业，再依已约定的设备请求标识查询可恢复结果，并核对 payloadHash、公钥身份和审批版本。只有接口确实支持请求幂等、查询和足够的结果保留，才能依赖它们；普通审计记录“执行过签名”并不等于可以取回签名。若底层没有这些能力，就必须承认结果仍未知，暂停自动推进或进入受控处置，不能编造查询接口。若设计允许对完全相同载荷再次签名，也须沿原作业显式登记尝试、重新满足策略，而非新开授权；非确定性 ECDSA 可能产生不同签名字节，不能把它冒称为恢复了原签名。

## 第 6 层：重试为什么不能只看签名字节

**面试官：** 同一载荷再签可能得到不同字节，那系统怎样判断这是同一权限，还是已经多签出一笔可花钱的交易？

**面试者：** 要分开记语义意图、外层载荷和签名实例。不同 ECDSA 结果可对应同一交易签名预像，甚至形成不同交易 hash，但不能因此当成两笔独立兑换。原作业保存每个尝试的关联身份；可执行签名或原始交易只进入受限结果存储，不进入普通日志。在同一规范链历史里，R 的同一外层 txNonce 不能执行两笔账户交易；X 又按用户的 epoch、nonce 阻止同一意图重复成功。但这不允许任意重签：改变费用、calldata 或 txNonce 就是新载荷，必须显式审批，并承认原签名仍可能有效。

## 第 7 层：Go 超时与工作者切换如何处理

**面试官：** 旧工作者的 context 已经取消，新工作者接管时，旧请求还可能回来。怎样避免它们各自继续推进？

**面试者：** context 取消只终止本地等待，不是 HSM 的撤销证明。我会用带版本的条件更新决定谁有权写入和推进作业，并在实际控制签名入口的服务验证租约代次或 fencing token；只在 Go 内存里加锁不足以隔离另一个进程。旧响应迟到时，只能核对原 jobID、原载荷后补充关联证据，不能覆盖新策略或新尝试。即使旧工作者已失去推进资格，它先前拿到的有效签名也不会消失，所以业务去重、签名资格隔离与已签载荷的后续观察必须同时存在，不能把抢锁成功当作撤销成功。

## 第 8 层：签名、广播、执行有哪三个未知边界

**面试官：** 旧响应和交易都可能迟到，你会用一个 UNKNOWN 状态概括所有情况吗？

**面试者：** 不会只保留一个无法解释的状态。第一类是签名未知：请求可能到达设备，但尚无可核对结果；第二类是广播未知：已有有效原始交易，发送后无确认，节点报错或暂查不到不代表从未传播；第三类是执行未知：交易可能待处理、已被替换，或已有回执但尚未达到业务确认条件。每类都记录对应身份和观察依据。R 的外层交易失败不等于 A 的意图作废，别的 Relayer 仍可能提交它；反过来，X 显示 nonce 已不可用，也可能来自取消而非成交。要结合具体交易和规范链证据辨别，不能只凭一个 used 位结算。

## 第 9 层：未知时能否取消并释放所有额度

**面试官：** 三个阶段都要观察，业务方嫌等待太久，点取消后能否立刻释放额度并保证以后不会执行？

**面试者：** 离线取消只能停止尚受本系统控制的后续动作，不能收回别人手中的签名。A 可以自己向 X 发 `cancelNonce(7,42)`，或提升 epoch，按规范链顺序与执行竞争；在最终确认前仍有重组风险。到期限制的是 X 执行资格，且 `block.timestamp==deadline` 仍允许执行，不是撤销此前的 allowance。即使意图最终失效，已经签出的 R 交易仍可能被提交并消耗 Gas。因此未知签名涉及的 Gas 预算与外层 nonce 占用不能按 HTTP 超时直接释放；业务资格失效和外层支出风险要分别收敛。

## 第 10 层：用一个故障时序检验恢复闭环

**面试官：** 就用这笔 1000 USDC 兑换推演：设备已签、响应丢失、Go 重启，随后旧交易被别人广播。你的系统最终怎么处理？

**面试者：** 重启后先读取原作业和不可变载荷，不新开相同意图的权限；能恢复签名则核对后继续观察，不能恢复就保留未知及其风险占用。旧交易出现时按 R、txNonce、交易身份和完整载荷关联原尝试，不能仅靠 jobID 猜链上归属。若 X 成功执行且达到确认条件，A 应为 500 USDC 和 0.50 WETH，普通消耗模型下 allowance 为 0，意图不可再用。若交易 revert，本次资金与 used 变化回滚，独立 approve 仍在，R 却可能已付 Gas；若发生重组，则撤回未成立的观察结论继续核对。闭环是恢复同一权限的事实，不是把未知强改成成功或失败。

## 本题收束

- **讲透的机制：** 用业务键约束意图，用 jobID 和不可变 payloadHash 约束签名作业，用尝试、签名结果与交易身份追踪外部副作用；数据库只保证自己的原子提交，跨 HSM 的结果靠明确接口契约与恢复流程收敛。
- **最容易答错的边界：** 超时不等于未签发；context 取消不等于远端撤销；签名成功不等于广播成功，广播被接收不等于链上兑换成功；重签相同载荷也不必得到相同签名字节。
- **反例推演：** HSM 已产生有效签名，数据库却回滚。若系统据此分配另一个 R 交易 nonce、重新签名并释放原 Gas 风险占用，旧交易仍可能迟到。X 的一次性消费可阻止双重兑换，却不能退还多次尝试的 Gas，更不能证明外部签名副作用没有发生。

**依据与适用范围：** EIP-712 定义结构化摘要，不替业务实现 nonce 消费或设备调用幂等。本文没有假定特定 HSM/KMS 厂商支持结果查询，也没有执行故障注入或生产测试。
