# 大问题 1：一笔非托管签名兑换怎样走完全流程，哪些权限与状态不能混为一谈？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| A / EOA / 非托管 | A 是自己掌握私钥的普通外部账户；平台不代管用户密钥。 | 1500 USDC 属于 A，平台签名系统没有替 A 任意花钱的权限。 |
| X / R / Relayer | X 是执行兑换的合约，R 是替用户提交交易并付执行费的转发者。 | R 的密钥付 Gas，X 才按合约规则检查并使用用户授权。 |
| approve / allowance | 前者设置代币使用额度，后者是 Token 保存的剩余额度。 | A 已独立授权 X 使用 1000 USDC；它不是兑换条款，也不是锁资。 |
| SwapIntent / EIP-712 | 一份具体兑换委托，以及把它按固定类型签名的方法。 | A 签的是完整业务条件，不是“允许平台做任何事”。 |
| chainId / domain | 链编号和签名适用的协议环境。 | 本例固定在链 1、OneTrade 版本 1 与 X，不能移到别的执行域。 |
| amountIn / minAmountOut | 精确花多少、实际至少收到多少。 | 输入 1000 USDC，最低输出 0.49 WETH；0.50 只是成功样例。 |
| 最小单位 / uint256 | 代币用整数记账；uint256 是有范围上限的非负整数。 | 两个金额分别编码为 1000000000 和 490000000000000000，不能用浮点数凑。 |
| owner / recipient | 授权人和输出资产的收款人。 | 两者都是 A，转发者不能拿同一签名换成自己收款。 |
| nonce / epoch / used | 一次性编号、权限代次、该编号是否已不可用。 | X 管理 A 的第 7 代第 42 号意图；不同于 R 的交易序号。 |
| deadline / T0 | 最迟允许执行的链上时间、起始时间。 | 本例期限为 T0+120 秒，执行时间等于期限仍允许，超过才拒绝。 |
| routeHash / selector | 路线内容的指纹、合约函数入口标识。 | 路线须与签名一致且通过 X 的白名单，不能因此任意调用合约。 |
| 预检 / 模拟 | 按某个已知链状态提前检查可能的执行结果。 | 不冻结余额；A 后续转走资产或撤回额度，链上仍会失败。 |
| EVM 原子性 / revert | 同一笔执行要么整体提交，要么整体撤回。 | 本次拉币、兑换、输出和 used 一起回滚，独立 approve 不在其中。 |
| Gas / 外层交易 | R 提交给链的调用及其执行成本。 | 兑换回滚仍可能花 R 的 Gas、消耗 R 的交易 nonce。 |
| jobID / payloadHash / HSM | 签名任务编号、固定载荷指纹、受控保管密钥的硬件。 | 独立策略核对 R 的完整交易；签名调用超时不证明硬件没有签出结果。 |
| 确认 / 重组 / cancelNonce | 结果证据逐步稳定、链分支更换、链上取消某个意图。 | 观察可随重组撤回；取消与执行竞争，删本地任务不等于撤权。 |

## 把整篇文章压缩成一个故事

**起因：** 小林的地址 A 有 1500 USDC、0 WETH，之前已用一笔独立且确认的 approve 给 X 恰好 1000 USDC 额度。这次小林只同意花 1000 USDC、至少收到 0.49 WETH，输出仍给 A，签下链 1、X、epoch=7、nonce=42、期限 T0+120 秒及固定路线的结构化意图。签完只是交出有边界的委托，钱还没有冻结，也没有成交。

**处理及异常：** Go 预检并保存固定意图，R 的独立签名服务再核对发往 X 的外层交易，R 付 Gas 提交。X 执行时重新验签、检查期限和当前权限，先标记 nonce 再拉币兑换。若只得到 0.48 WETH，整笔兑换连同 used 一起回滚，先前的 1000 USDC allowance 仍在，R 却可能已经付费。若签名服务超时，则先恢复原任务结果，不能认定没签过；用户此时要求取消，也必须让 A 的链上取消或 epoch 更新与兑换按实际执行顺序竞争。

**结果及边界：** 成功分支实际输出 0.50 WETH，小林变成 1500−1000=500 USDC、0.50 WETH，本教学代币的 allowance 消耗为 0，A/7/42 不可再成功使用。系统核对回执、事件、区块身份和确认等级，遇到重组修正展示。任何人都可转发这份合法意图，但不能改收款人；停止自身 R 不能撤回外泄签名，后到的取消也不能逆转已完成兑换。这里讲的是教材中的权限闭环，不是实际链上测试结果。

**流程位置与核心机制：** 本题贯穿用户签名、Relayer 提交、X 原子执行和结果确认，重点是授权边界、状态归属与失败后果。EIP-712 编码、Go 验签、nonce 和撤销的细节分别由后续母题深入。

**讨论前提：** 严格沿用总览的教学自定义协议，不代表真实部署。链为 `chainId=1`，域为 `OneTrade / 1 / X`；X 是不可升级的执行合约和占位地址。A 是普通 EOA，已通过独立且确认的交易授权 X 恰好 1000 USDC；本次 exact-input 意图不部分成交，业务费为 0，不改变为 Permit、托管账户或合约钱包模型。

## 第 1 层：先讲完一笔兑换，而不是停在签名成功

**面试官：** 用户签名花 1000 USDC，至少换到 0.49 WETH，你会怎样解释这笔业务从开始到结束的完整流程？

**面试者：** A 初始有 1500 USDC、0 WETH，并已给 X 1000 USDC 的 allowance。前端生成固定字段的 SwapIntent，A 用自己的钱包签名，Relayer R 拿到意图和签名后预检，再用 R 的 Gas 私钥签外层交易并提交给 X。X 在执行时重新检查意图、签名和链上状态，拉取 1000 USDC，执行受控路线，校验实际输出不低于 0.49 WETH，再把本笔输出交给 A。若实际得到 0.50 WETH，成功后 A 为 500 USDC、0.50 WETH，普通消耗模型下 allowance 为 0。交易回执成功还要经过约定确认，不能把钱包签名成功或 RPC 接收交易当成兑换完成。

```text
独立 approve 已确认〔Token 中 allowance(A,X)=1000 USDC〕
    ↓
A 审阅并签署 SwapIntent〔签名不移动资产、不冻结余额〕
    ↓
R 预检 → 独立签名服务批准 R 到 X 的交易 → 广播
    ↓
X 在同一 EVM 事务中验权 → 标记 used → 拉币 → 受控兑换 → 校验输出 → 给 A
    ├─ 任一步失败：本次资金与 used 变化整体回滚，R 仍可能支付 Gas
    └─ 执行成功：输出归 A，记录回执与区块证据 → 达到确认要求后对外完成
```

## 第 2 层：有了 allowance，为什么还需要兑换签名

**面试官：** 你说 A 已经 approve 了 X，为什么还要签 SwapIntent？两种授权不是重复的吗？

**面试者：** 不重复。Token 的 allowance 只回答“X 最多还能从 A 转走多少 tokenIn”，不会替 A决定兑换什么资产、最少收多少或谁收款。SwapIntent 才表达这笔兑换的业务权限；X 必须先验明 A 同意了这些约束，才能使用 allowance。R 的交易签名又是第三种权限，它授权消耗 R 的 ETH 和交易 nonce 来调用 X，不代表 R 拥有 A 的资产。用户私钥始终由 A 持有，签名服务控制的是 R 的 Gas 私钥。即使签名正确，没有余额或 allowance 仍不能成交；即使 allowance 足够，没有有效业务意图也不能擅自兑换。

## 第 3 层：兑换权限怎样落到不可替换的具体参数

**面试官：** 既然真正的兑换权限在 SwapIntent 里，R 收到签名后还能改哪些参数？

**面试者：** 签名字段固定为 owner、tokenIn、tokenOut、amountIn、minAmountOut、recipient、nonce、epoch、deadline、routeHash。案例中 owner 和 recipient 都是 A，amountIn 是 `1000000000` 个 USDC 最小单位，minAmountOut 是 `490000000000000000` 个 WETH 最小单位，nonce 为 42、epoch 为 7、deadline 为 T0 加 120 秒。域还绑定 chainId 和 X。R 不能改这些字段而继续使用同一签名；实际路线也必须与 routeHash 对应，并通过 X 内置的目标、selector、资产和池白名单。签名路线不等于允许任意 call，更不等于允许 delegatecall；哈希匹配与可执行能力限制缺一不可。

## 第 4 层：签名与预检为什么都不等于资产锁定

**面试官：** 参数已经绑定，R 也预检过了，为什么到链上还可能因为余额或授权不足失败？

**面试者：** 因为签名只是可验证的授权数据，没有替 A 冻结 1000 USDC。预检之后，A 可能转走资产，也可能发交易把 allowance 改为 0；其他有效意图也可能先使用同一笔余额。余额和 allowance 的权威在 Token，currentEpoch 与 used 的权威在 X，Go 服务的数据库只是观察和编排。R 可以在指定区块模拟以减少无效 Gas，但不能把模拟结果升级为执行承诺。X 必须读取执行时的状态，并以实际 transferFrom 和输出校验的结果决定成功。基线没有链下“预留资金”，因此也不能在失败后编造一笔释放冻结余额的账务操作。

## 第 5 层：先标记 used 会不会造成扣款失败却永久失效

**面试官：** 你说 X 要重新检查并执行，但为了防重放又要先写 used。如果兑换后来失败，这个 nonce 不就白白消耗了吗？

**面试者：** 不会，前提是这些动作确实在同一 EVM 事务内。X 的 nonReentrant 入口完成字段、期限、当前 epoch、used 和签名检查后，在外部调用之前写 used，再做 transferFrom、受控兑换和最小输出校验。任一后续错误都必须向外传播并整体 revert，不能 catch 后返回“业务失败”却保留 used。例如最终只得到 0.48 WETH，minOut 校验失败，本次输入转移、兑换、输出转移、used 和本次日志全部回滚；此前独立 approve 不回滚，案例 allowance 仍为 1000 USDC。失败外层交易仍可能消耗 R 的 Gas 和交易 nonce，这与意图 nonce 未消费不矛盾。

## 第 6 层：任何人转发同一签名会不会直接盗款

**面试官：** 既然失败不会消耗意图 nonce，别人拿到签名抢先提交，或者两个 R 同时提交，会发生什么？

**面试者：** 基线没有 executor 字段，任何 Relayer 都可以转发，因此不能把“不是我们的 R 提交”当作无效条件。两笔交易在链上顺序执行，首笔成功后，`(chainId,X,owner,epoch,nonce)` 对应的不可用位被提交，后笔被拒绝；首笔若整体回滚，后笔仍可能成功。签名已经固定 recipient=A，转发者不能改成自己收款，所以抢先转发本身不盗走这笔输出，但可能提前执行、影响用户时机或令原 R 白付 Gas。若产品要求限定执行者或支付代付费用，就必须明确增加 executor 或费用字段并改变签名 schema，不能从当前签名推导出未签过的权限。

## 第 7 层：Go 服务与签名服务的边界在哪里

**面试官：** 你已经允许多个转发者，自己的 Go 服务还要控制什么，才能不把代付变成任意签名服务？

**面试者：** Go 服务应验证和规范化输入，记录不可变意图及 digest，在指定区块预检后构造 R 到 X 的外层交易。独立签名服务不能只接收业务传来的任意 hash，它要绑定 chainId、R、to=X、value=0、入口 selector、完整 calldata hash、Gas 与费用上限、交易 nonce、策略版本、密钥版本和审批。HSM/KMS 控制的是 K_R，不接触 A 的私钥。签名请求要有 jobID 与不可变 payloadHash；批准请求到达 HSM 后，即使 Go context 超时，也可能已经产生有效签名，应先恢复原请求结果，不能因超时另开一份等价业务权限。服务预检只减少错误，不替代 X 的最终验权。

## 第 8 层：执行成功以后，还缺什么才算闭环

**面试官：** 你已经控制住签名服务了，如果页面看到成功回执，或者用户此时说要取消，这笔业务怎样最终收束？

**面试者：** 页面应区分已受理、已广播、链上成功、达到确认要求，而不是只保留一个布尔值。成功证据要绑定交易哈希、区块哈希、意图键和输出事件，并能在重组后撤回观察结论。用户取消必须由 A 发链上 cancelNonce，或提高自己的 epoch；停止自身 R、删数据库和取消 Go context 都不能撤销别人手里的签名。取消与执行按链上顺序竞争，执行已成功后不能靠后到的取消撤回资产交换。到期也只是禁止后续执行，不会撤销 allowance。最终闭环是资产按同一次执行结果变化、意图最多成功消费一次、观察状态能随确认或重组收敛，而不是声称签名系统能逆转已经完成的交易。

## 本题收束

- **讲透的机制：** Token allowance、业务意图和 R 的 Gas 签名是三种权限；Token 与 X 分别持有权威状态；本次资金变化与意图消费共享 EVM 原子提交边界。
- **最易答错的边界：** 签名不锁定余额，模拟不承诺成交，失败不回滚此前 approve，Gas 与外层交易 nonce 不随业务 revert 恢复；无 executor 的签名允许任何人转发。
- **检验反例：** 假设 X 拉币后输出仅 0.48 WETH，却吞掉错误并保留 used。这既破坏全成全撤，也让用户失去原意图的执行机会，不能用链下补偿冒充基线的正确实现。此处是手工推演，不是实测结果。
