# 大问题 13：用户已经签名授权兑换，为什么 Relayer 的交易签名和 Gas 权限仍需独立隔离？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| A 的意图 / R 的外层交易 | 用户允许的兑换条款、转发者实际提交给链的交易。 | A 的签名放进调用数据，K_R 另签外层交易来承担 Gas，二者不可互换。 |
| approve / allowance / X | 设置代币额度、剩余可扣额度、获授权的执行合约。 | Token 还须允许 X 扣 A 的币，两个签名齐全不代表额度必然足够。 |
| 签名预像 / digest | 准确待签内容、它的哈希摘要。 | 外层交易按交易类型编码，不是直接复用 A 的 EIP-712 摘要。 |
| chainId / to / value | 链编号、调用目标、附带的原生币金额。 | 链 1、to=X、value=0 不等于没有支出，Gas 另付。 |
| selector / calldataHash | 入口函数标识、完整调用数据指纹。 | 策略核对真实交易动作和字节，不能只检查目标地址。 |
| routeHash / abi.encode | 规范路线指纹、有类型编码方式。 | X 仍只执行白名单内的目标、函数、资产和池，不开任意调用能力。 |
| amountIn / minAmountOut | 精确输入、最低实际输出。 | 分别是 1000×10⁶ USDC、0.49×10¹⁸ WETH 最小单位，收款人固定 A。 |
| gasLimit / Gas | 交易最大执行资源量、实际执行资源及费用。 | 合法意图反复失败也可能持续消耗 R 的资金。 |
| EIP-1559 / maxFeePerGas | 一种交易费用机制、每单位 Gas 的费用上限。 | 签名策略明确约束其费用字段，不能把上限当最终实际账单。 |
| maxPriorityFeePerGas / 最坏风险 | 优先费上限、预算需要覆盖的潜在支出。 | 约束费用字段关系，以 gasLimit×maxFeePerGas 管理最坏占用。 |
| big.Int / uint256 | 无损大整数、协议非负整数范围。 | 费用与金额受限计算并复制，不能浮点舍入或共享对象漂移。 |
| jobID / payloadHash / 审批 | 唯一作业号、固定载荷指纹、准许签发的记录。 | 作业与预算预留共同登记，冲突内容不得重复使用旧审批。 |
| txNonce / intentNonce | R 账户交易序号、X 的一次性业务编号。 | 用户意图只可成功一次，不保证不同外层尝试只付一次 Gas。 |
| 替换候选 / keyVersion / policyVersion | 同账户槽位的新交易、密钥版本、策略版本。 | 提价已改变载荷，要新审批并关联旧候选，不销毁旧签名。 |
| HSM 超时 / 风险预留 | 签名结果不明、保留潜在费用责任。 | SQL 回滚和 context 取消不证明没签过，须沿原任务恢复。 |
| 抢先转发 / 原始已签交易 | 别人先提交意图、已具备广播能力的完整交易。 | 只持 A 意图需自己付 Gas；持 R 的原始交易可广播并让 R 付其固定费用。 |
| executor / 代付费 | 指定执行者、从用户资产收取的代付报酬。 | 基线无 executor、业务费为 0，不能只改后端就增加收费权。 |

## 把整篇文章压缩成一个故事

**起因：** 小林的 A 有 1500 USDC，已给 X 恰好 1000 USDC allowance，签下花 1000、至少收 0.49 WETH 的意图。Go 把意图和用户签名装进发往 X 的 calldata，再请 R 用 K_R 签外层交易。签名服务独立核对链、R、X、value=0、入口、完整数据、交易 nonce 与费用，不能认为用户已签就可无限代付。

**处理及异常：** 服务用唯一作业固定载荷并预留最坏 Gas 风险；若选 EIP-1559，以 gasLimit×maxFeePerGas 管理上限，而非宣称实际一定花这么多。假设 HSM 签名超时，预算不能因 SQL 回滚就释放，因为原始交易可能已经存在。此时另一 Relayer 若只拿到 A 的意图，可自己付 Gas 抢先执行，仍必须把输出给 A；若别人拿到的是 R 已签原始交易，则可广播固定交易并让 R 承担费用，但不能修改其中收款人。

**结果及边界：** 别的 Relayer 先成功拿到样例 0.50 WETH 后，A 变成 500 USDC、0.50 WETH，教学 allowance 为 0；R 的旧交易随后仍可能上链，因意图已不可用而失败付 Gas，不能把用户成功直接等同于 R 风险已解除。一般成功下限只是 0.49，不是固定报价；业务费为 0，也没有限定 executor。若要从输出扣代付费或指定 R，须明确新签名字段和执行规则，X 不可升级，不能靠后端政策暗增用户未授权的资产权限。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于用户离线签署兑换意图之后，覆盖 Go 服务构造外层交易、签名服务独立批准和 R 账户支付 Gas 的过程。核心是两套权限、两种 nonce、两种签名摘要与平台支出边界，不扩展为交易广播和替换算法专题。

沿用教学模型：用户普通 EOA A 持有 1500 USDC、0 WETH，独立 approve 已确认且仅授权 X 1000 USDC。意图固定为花 1000 USDC、至少获得 0.49 WETH、recipient=A，示例成功获得 0.50 WETH；业务费为 0。EIP-712 域为 `OneTrade/1/chainId=1/X`，X 不可升级，地址仅作教学占位。用户私钥不交给平台，Relayer R 的 Gas 私钥 `K_R` 才由 HSM/KMS 托管。

## 第 1 层：一笔兑换究竟有哪两份授权

**面试官：** A 已经签了兑换意图，为什么 Go 服务还要申请一次 Relayer 签名，不能把用户签名直接发给节点吗？

**面试者：** A 的签名授权 X 按约定兑换，不是一笔可以直接送入交易池的 R 账户交易。Go 服务把意图和用户签名放入调用 X 的 calldata，再构造由 R 发出的外层交易；`K_R` 对相应交易签名预像签名，才由 R 账户承担 Gas。A 的资产可被 X 转入还依赖此前 Token 上的 allowance，三个条件各有权威状态。A 的签名约束资产动作，R 的签名约束平台账户支出，approve 则给 X Token 层权限，谁也不能互相替代。最终回执成功还必须符合 X 的执行条件，而不是两份签名齐全就算兑换完成。

## 第 2 层：只限制交易发往 X 是否足够

**面试官：** 既然平台签名只负责付 Gas，把签名服务设置为“只签 to=X”是不是就足够安全？

**面试者：** 不够。同一目标可能有多个函数，合法函数也可能携带恶意参数、过高费用或错误交易 nonce。独立签名服务必须核对 chainId=1、预期发送账户 R、目标 X、value=0、允许的 selector 和完整 calldata hash，并把 Gas、费用上限、txNonce、policyVersion、keyVersion 与审批绑定。业务服务不能提交任意 hash 让 HSM 盲签；应由可信策略层解析规范交易、校验其上下文，再生成正确交易类型的签名预像。R 的外层交易签名不是 A 的 EIP-712 意图签名，不能拿同一种摘要或编码互相替代，也不能信任业务服务自报“已校验”。

## 第 3 层：合法 selector 中还能藏什么风险

**面试官：** 你要求签名服务检查完整 calldata，可其中本来就含有用户签名，平台还应检查哪些内容，而不是重复做一遍合约？

**面试者：** 平台应核对作业批准的精确意图和调用编码：owner、tokenIn、tokenOut、amountIn、minAmountOut、recipient、nonce、epoch、deadline、routeHash 都不能在组包后漂移。这里 amountIn 为 `1000×10^6`，最小输出为 `0.49×10^18`，recipient 必须仍是 A。路线计划经固定类型的 `abi.encode` 后取 Keccak 得到 routeHash，且只允许 X 内置白名单的目标、selector、资产和池，不开放任意 call 或 delegatecall。编码时还须拒绝越界整数和不受支持的嵌套参数，避免检查对象与真正签出的字节不一致。平台检查是保护 R 的预算和策略，X 仍须独立验签并执行全部约束；不能因平台预检通过就让合约跳过验证。

## 第 4 层：用户签名有效为什么仍会耗尽平台 Gas

**面试官：** 参数都没有被篡改，但合法意图连续执行失败，平台是不是仍可能被拖垮？

**面试者：** 是的。签名没有冻结 A 的余额或 allowance，预检后状态仍会变化，交易 revert 也可能消耗 R 的 Gas。我会为用户、作业和 R 设置独立限额，用精确整数检查 gasLimit、每单位费用和最大支出；若采用 EIP-1559 交易，还要约束 maxFeePerGas、maxPriorityFeePerGas 及其关系，以 `gasLimit×maxFeePerGas` 管理最坏 Gas 风险占用，而非当作实际收费。Go 用受限的 big.Int 转换和复制，不能用 float64 算金额。value=0 只排除随调用发送原生币，不排除 Gas 费用；模拟成功或 A 有有效签名都不意味着平台应该无限代付。

## 第 5 层：支出审批如何防止重复使用

**面试官：** 限额审批通过后，两个工作者拿同一审批各签一笔交易，单笔都不超上限，你的预算还能守住吗？

**面试者：** 还要把审批变成有唯一身份的支出资格，而非可以重复使用的“允许”布尔值。数据库事务内创建作业、占用预算并固定载荷，签名服务核对同一 jobID 和 payloadHash；冲突载荷不得沿用旧审批。R 的 txNonce 作用域是 `(chainId,R)`，与 A 在 X 上的 `(chainId,X,A,epoch,nonce)` 完全不同。若允许同 nonce 费用替换，应登记为原作业的新载荷、新尝试并显式审批，不能假定原签名消失；若换另一个 txNonce 再提交，则可能多付一次 Gas。业务的一次性执行只保护兑换结果，不自动保护平台支出次数。

## 第 6 层：预算占用能否与设备签名原子提交

**面试官：** 你把作业和预算放在数据库事务里，那 HSM 超时后回滚事务、释放预算，重试时再占用可以吗？

**面试者：** 不可以把数据库回滚当作设备未签发。HSM 不参与这个 SQL 事务，超时前可能已生成有效签名；若释放预算并批准其他交易，原签名迟到就可能让实际风险超过上限。应该先持久化权限和风险占用，再尝试签名，未知时沿原 jobID 恢复结果并保留占用。签名未知、已签后广播未知、上链执行待确认要分别记录，依各自证据收敛。只有能证明未进入签发边界的拒绝，或按明确处置规则解决了存量风险，才能释放对应占用；不能依赖 context.Cancel、设备禁用或暂时查不到交易来证明原签名不存在。

## 第 7 层：别人抢先转发是否窃取了 Gas 权限

**面试官：** 未知期间，别人拿到 A 的意图先提交成功了。这个人是不是盗用了 R 的 Gas 权限，还能把 WETH 转给自己？

**面试者：** 单独持有 A 的意图，只能自行付 Gas 转发，不能凭它让 R 账户支付费用；基线没有 executor 字段，允许任何 Relayer 提交，所以抢先转发本身不盗款，recipient 仍绑定 A，但可能改变提交时机。如果泄露的是 R 已签的原始交易，别人可广播这笔固定交易，使 R 按其载荷付 Gas，却不能改成自己的收款地址；因此它也是敏感可执行材料。若另一个 Relayer 已让意图成功，R 的旧交易后续执行会因 nonce 不可用而失败并可能耗 Gas，平台仍须管理这个存量风险，不能把用户成交直接当作 R 所有预算已安全释放。

## 第 8 层：要收代付费或绑定执行者时改变了什么

**面试官：** 既然任何人都能转发，如果产品要锁定 R 并从用户收到的 WETH 扣代付费，能否只在后端加个收费策略？

**面试者：** 不能，这是改变签名权限和基线。当前业务费为 0，schema 没有 executor 或费用字段，平台不能在 calldata 外悄悄扣费或改 recipient。新产品需定义包含 executor、费用资产、金额或上限、收款方及净输出语义的新签名结构，并由执行合约验证；当前 X 不可升级，不能只改后端便声称原合约支持，必要时要部署新合约并重新取得用户签名及所需 Token 授权。贯穿成功样例中 A 是 500 USDC 和 0.50 WETH、allowance 为 0；一般成功只承诺至少 0.49 WETH，不能把样例输出变成固定报价。失败则本次资金与 used 变化回滚，先前 approve 仍在，R 的 Gas 却可能已经支付。这些账不能靠“用户同意兑换”合并成平台的收费权。

## 本题收束

- **讲透的机制：** 用户意图、Token allowance 和 Relayer 外层交易是三条独立授权链。签名服务从规范完整交易验证策略后再调用设备，支出审批必须绑定唯一作业、载荷、账户 nonce、费用与密钥版本。
- **最容易答错的边界：** A 的兑换权限不等于 R 的 Gas 权限；value=0 不等于零支出；X 的一次性 nonce 不保证 Relayer 只花一次 Gas；后端限流和模拟不能替代合约约束，数据库预算事务也不能原子覆盖 HSM。
- **反例推演：** A 的合法意图被另一个 Relayer 先执行，平台因为“用户已经成功”释放 R 的全部占用，但 R 的已签交易随后被广播并失败收取 Gas。这说明用户资产结果与平台待承担的外层交易费用必须分别核对，不能共享一个“完成”状态。

**依据与适用范围：** EIP-712 负责绑定用户结构化意图，不把该意图自动转换为任意账户的交易签名或 Gas 代付授权。本文采用教学支出策略，没有执行签名调用、广播或费用测试。
