# 大问题 14：怎样审计签名授权链路，既能证明权限边界，又不让日志成为新的签名泄露源？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 授权链 / 最小充分证据 | 谁准许了什么的全过程、能回答问题又不过度收集的材料。 | 先定义要证明的权限和结果，不先把每个完整报文存下来。 |
| domain / digest / 意图键 | 适用环境、已签内容摘要、一次性业务身份。 | 以链 1、X、A、7、42 关联权限，用 digest 核对具体条款。 |
| jobID / payloadHash | R 的签名作业号、不可变完整载荷指纹。 | 串起一次外层签名授权，不拿它替代用户意图身份。 |
| policyVersion / keyVersion / 审批 | 策略版本、密钥版本、准许签发的决定。 | 说明谁依据什么规则批准哪份内容，实际签发仍需相符。 |
| calldataHash / routeHash | 调用数据指纹、规范路线指纹。 | 连同编码版本和受限原载荷，支持重新计算并检查参数没有漂移。 |
| 承诺值 / 结果句柄 | 对内容的哈希指纹、受保护结果的引用。 | 日志可关联、恢复路径可按权限取材料，不把可执行原文四处复制。 |
| 能力凭据 / 原始交易 | 持有就可能触发动作的材料、已签且可广播的完整交易。 | 用户签名可被转发，R 原始交易可被广播，虽不能改 recipient 也有风险。 |
| 恢复数据面 / 审计证据面 | 保存可恢复结果的专门位置、记录发生了什么的留痕渠道。 | 分权、加密并有限留存，写审计不自动获得读取签名的权利。 |
| 秘密 / 异常路径 / 追踪 | 私钥等机密、错误输出渠道、跨服务观测数据。 | 助记词、份额、凭据及签名原文不能通过堆栈、报表或链路日志旁路泄露。 |
| 待投递事件 / 追加式存储 | 本地可靠登记的审计任务、只追加纠正而非覆盖的存储。 | 减少丢失与改写，但不让数据库事务覆盖 HSM 密码操作。 |
| 哈希链 / 外部检查点 | 前后串联的完整性指纹、独立保管的锚点。 | 可帮助发现改写；整链与锚点同被控制就不能据此证明可信或完整。 |
| 签名未知 / 传播未知 / 待确认 | 设备结果不明、网络传播不明、链上证据未稳定。 | 各自写明来源和身份，超时不是设备未签或交易未传播的证明。 |
| 时间戳 / 因果关联 | 日志记录时间、能证明先后依赖的关系。 | 跨系统时钟不天然一致，靠版本和任务关系解释，不按日志时间武断排序。 |
| used / 执行事件 / 取消事件 | 权限不可用状态、成交依据、撤销依据。 | 单看 used=true 不能区分成功兑换与成功取消。 |
| 规范链 / 区块哈希 / 重组 | 当前有效历史、分支内位置、历史分支更换。 | 观察绑定确切区块，分支变动追加纠正，不能静默维持旧终态。 |
| 不变量 / 反例 / 验证范围 | 必须一直成立的规则、可推翻错误承诺的情形、实际做过的检查。 | 教材列出静态审查与手工推演，不因此宣称故障注入或安全测试已通过。 |

## 把整篇文章压缩成一个故事

**起因：** 小林签了第 7 代第 42 号 1000 USDC 兑换意图，R 的 HSM 调用却超时。审查者需要知道 A 授权了什么、哪个策略批准哪份外层载荷、设备是否可能签发、链上最终怎样执行，而不是开启全量日志，把未过期用户签名和 R 原始交易都复制到更多人能读的地方。

**处理及异常：** 系统以域、digest、意图键关联用户权限，以 jobID、payloadHash、审批和版本关联 R 的作业，日志记录最小语义、承诺和受限结果句柄；完整恢复材料另存于加密限权的数据面。设备超时、传播未知和回执待确认分别留证。追加式审计、哈希链及独立检查点帮助识别改写，但设备已签而记录未落盘的窗口仍要披露，不能从“日志没找到”推断没发生，也不能按不同机器的时间戳武断排定链上竞争顺序。

**结果及边界：** 旧交易若迟到并获确认，审查者须用实际规范链回执、事件和 Token 状态核对；在无其他资金变化的成功样例中，A 从 1500 USDC 变成 500 USDC、0.50 WETH，教学 allowance 为 0。若 A 已先取消，used 同样可能为 true，却不是兑换成功，R 的旧交易还可能失败付 Gas；发生重组要追加纠正，证据缺口未解就保留受控未知。审计闭环是清楚交代剩余权限、事实与责任，不是日志齐全便能宣称零风险、恰好一次或安全测试通过。

**流程位置与核心机制：** 本题横跨用户意图、平台审批、HSM 签名和链上执行，重点是最小充分证据、跨阶段关联、秘密与可执行材料隔离，以及能证伪安全承诺的静态验证方法。不建立测试工程，也不把教学推演写成已完成的安全测试。

沿用统一模型：域为 `OneTrade/1/chainId=1/X`，X 不可升级；A 自持用户私钥，R 的 `K_R` 由 HSM/KMS 管理。应用 nonce=42、epoch=7、deadline=`T0+120秒`，本次兑换花 1000 USDC、至少得 0.49 WETH，示例得 0.50 WETH，recipient=A；approve 已独立确认。审计必须区分签名事实、链上业务事实和 R 的 Gas 支出事实。

## 第 1 层：先定义要证明什么

**面试官：** 让你给这套签名授权系统做审计设计，你会不会先把每个接口的请求和响应全部记录下来？

**面试者：** 不会先全量记录，而是先定义证据要回答的问题：谁提出哪一项权限、哪条策略批准、实际尝试签了什么、结果是否确定，以及最后链上执行了什么。用户意图用域、digest 和 `(chainId,X,A,7,42)` 关联，R 的签名作业用 jobID、不可变 payloadHash、审批、policyVersion、keyVersion 和尝试身份关联。A 的意图证明受限兑换权限，设备记录证明签名操作事实，规范链和 Token 状态才决定资产结果。三个来源不能互相冒充；“调用成功”不是成交证据，“设备签过”也不是已经找到完整签名或已经付出 Gas 的证明。

## 第 2 层：不存完整报文怎样查清签了什么

**面试官：** 你只存 digest 和 payloadHash，事后怎么证明没有把 recipient 换掉，又怎样在日志中避免泄露签名？

**面试者：** 审计事件保存规范编码版本、必要的非秘密语义摘要和承诺值，例如域、recipient、金额、routeHash、完整 calldata hash、目标 X、value=0、费用上限及审批引用；需要复核的规范载荷保存在独立受限的业务证据存储，并能按相同编码重新计算承诺。用户签名、R 签名原文和可广播原始交易不进审计日志，私钥、助记词、密钥份额、设备凭据及可恢复密钥材料也绝不记录。请求体、异常堆栈、链路追踪和导出报表同样要排除这些字段，不能只脱敏主日志；哈希可供关联，不代表原始材料可以无限复制。

## 第 3 层：恢复需要签名，为什么审计却不能保存

**面试官：** 上一题强调超时后恢复原签名，这里又不让日志保存签名，是不是为了保密反而损害了恢复能力？

**面试者：** 要分开恢复数据面与审计证据面。签名若需要持久保存，应放在加密、细粒度授权、有限留存的结果存储，由专门恢复路径读取；审计只记录结果句柄、承诺、访问主体和结果，不复制内容。审计写权限不应自动获得读取可执行材料的权限，取回结果也要核对原 jobID 和载荷。即便签名未必属于传统“密码”，未过期且未消费的用户签名可被转发，R 的原始交易可被他人广播，都应按能力凭据保护。把它们打印出来用于调试，会扩大可提前触发执行或消耗 Gas 的人群，受限存储也不意味着底层设备天然支持结果恢复。

## 第 4 层：怎样防止审计记录被补写或删除

**面试官：** 材料隔离好了，但管理员仍能删日志或把“拒绝”改成“批准”，怎么让审计值得信任？

**面试者：** 我会使关键状态迁移在本地事务中关联待投递审计事件，再送到独立权限域的追加式存储；事件携带唯一标识、作业版本、来源和关联顺序，避免重复投递被算作多次审批。可用分段哈希链和独立保管的检查点发现事后篡改，但若攻击者能重写整条链且控制锚点，单靠哈希链并不可信。审计也不是 HSM 的事务参与者，设备操作与事件落盘之间仍有故障窗口，必须记录缺口并与独立来源核对。日志防改只能保护既有证据，不能证明没有未记录的操作，更不能替代签名入口本身的限权。

## 第 5 层：证据缺口应该怎样表达

**面试官：** 你承认可能存在未落盘的设备操作。出现设备超时、广播超时或回执尚未确认时，审计状态怎么写才不误导？

**面试者：** 分别写签名结果未知、传播结果未知、执行结论待确认，并保留观察时间、来源、原请求身份和可恢复的结果引用。超时事件只证明等待结束；设备操作记录未必包含可取回的签名，RPC 暂查不到也不证明未传播。链上观察还需 transaction hash、区块号、区块 hash 和确认策略，发生重组时追加纠正事件，不静默覆盖旧观察。没有统一跨系统时钟，就不能凭日志时间先后断言绝对因果；用审批版本、尝试关联和状态迁移序列说明依赖。用户页可以展示处理中，但内部不能据此抹掉已可能签发的风险。

## 第 6 层：怎样证明资金与权限结果符合模型

**面试官：** 最终查到 X 的这个 nonce 已经不可用了，你就能在审计报告里写“兑换成功”吗？

**面试者：** 不能，nonce 不可用也可能由取消造成，需要关联执行或取消的具体规范链交易、回执和合约语义。这个模型成功时应转入 X 获批的 1000 USDC、得到示例 0.50 WETH 并给 A，A 在案例无其他资金变动时为 500 USDC 和 0.50 WETH，allowance 按固定普通消耗模型为 0。失败则本次资金和 used 变化全部回滚，原先独立 approve 仍在，R 可能已经付 Gas。还要区分交易 revert 和链外预检拒绝，后者不产生该笔链上 Gas；审计不能把预期数值当成任意时点余额证明，必须注明区块和并行交易影响。

## 第 7 层：安全验证怎样从口号变成可证伪规则

**面试官：** 已经能解释结果了，如何检查“没越权”和“故障可恢复”，又不只是多加几条日志？

**面试者：** 我会先静态列出不变量与反例：同 jobID 改 recipient、txNonce 或费用必须被拒绝；错误域和同键不同意图不能增加资格；设备已签而数据库未提交时不得按未签释放权限。执行侧检查 used 在外部调用前标记、任一失败连同资金回滚，期限相等允许而超过禁止，取消与执行依链上顺序裁决。运维侧检查旧钥禁用不被写成旧签名失效，灾备未隔离旧主不得接管；证据侧检查日志和异常路径没有秘密、签名原文或原始交易。这是设计审查与手工时序推演的准则，若未实际运行故障注入，就不能写“全部测试通过”。

## 第 8 层：怎样判断审计闭环而不是证据堆积

**面试官：** 把这些反例都写下来以后，遇到真实事件，什么条件才算可以关闭，而不是堆一包日志就结束？

**面试者：** 应逐项交代权限是否仍可能行使、哪些事实已经确认、哪些风险仍未知，以及谁负责后续。比如 R 的 HSM 超时后旧交易迟到，若能核对原载荷并确认 X 执行成功，记录用户资产结果与 R 费用；若 A 已先取消则说明旧交易可能失败付 Gas，不能把取消当作零成本。若无法恢复签名或证明传播情况，就保留受控未知而不是伪造关闭。报告给出范围、证据来源、缺口和处置决定，任何额外取证仍遵守最小披露。审计的目标是让权限与结果可核验，不是保证零事故，也不是因日志齐全就宣称数据库和 HSM 已经原子提交。

## 本题收束

- **讲透的机制：** 用不可变身份、规范编码承诺和独立证据关联授权、审批、签名与链上事实；恢复材料与审计事件分面保存，追加式留痕与外部锚点用于发现篡改，证据缺口则必须显式披露。
- **最容易答错的边界：** 审计不能记录秘密、用户可复用签名原文、R 签名或可广播原始交易；设备成功不是链上成功，used 不可用不是必然成交，哈希链不是完备性证明，日志时间也不天然构成跨系统总序。
- **反例推演：** 为排查超时而开启全量请求日志，审计平台由此拿到未过期的用户签名和 R 原始交易。即便不能改 recipient，读日志的人也能提前转发或广播，改变执行时机并触发 Gas 支出。这样的日志提高了可见性，却直接破坏权限隔离，不能算安全审计方案。

**依据与验证声明：** 以下规范用于界定签名和重放边界，不能替代项目的链上实现、设备契约与审计权限设计。本文仅提出静态审查条件和预期反例，没有执行安全测试、故障注入或生产验证。
