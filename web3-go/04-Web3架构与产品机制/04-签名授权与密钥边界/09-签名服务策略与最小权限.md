# 大问题 9：Relayer 签名服务怎样约束业务请求，并防止策略批准与实际签名之间被替换或越权？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| R / K_R / Gas | 转发账户、它的私钥、执行费。 | 签名服务管的是 R 的外层交易，不是 A 的 1500 USDC 私钥。 |
| 最小权限 / 独立验策 | 只允许必要动作、签名方自己核对规则。 | 业务说“已检查”不够，不能把接口做成提交任意 hash 就签。 |
| chainId / to / value | 链编号、目标合约、转出的原生币金额。 | 本例链 1、to=X、value=0 只是必要条件，不足以约束所有交易内容。 |
| selector / calldata / ABI | 函数入口标识、完整调用数据、它的编码规范。 | 解码受支持动作并检查真实字节，不能批准文字描述却签另一份数据。 |
| digest / routeHash | 用户授权摘要、受控路线指纹。 | 签名服务独立重算并核对，X 在实际执行时仍须最终验权。 |
| uint256 / big.Int | 有范围的协议整数、Go 精确大整数。 | 金额不经浮点，批准后也不能被共享指针修改。 |
| jobID / payloadHash | 一次受控任务号、完整固定载荷指纹。 | 同任务换内容应冲突，不覆盖旧载荷以规避审批。 |
| policyVersion / keyVersion | 策略版本、所用密钥版本。 | 审批须绑定它们，但历史版本存在不等于现在仍被允许。 |
| TOCTOU | 检查时有效、真正使用时条件已变的竞态。 | 队列等待期间可能停用策略或密钥，实际授权派发前要重新裁决。 |
| 预算预留 / 授权事务 | 先占住可能发生的费用风险、共同提交状态。 | 并发请求不能各看一次旧余额后共同超额，未知结果也不能立即释放预留。 |
| 派发器 / 栅栏 | 向设备发批准请求的受信关口、拒绝过时代次的控制。 | 停用与派发需明确串行化切点，数据库查完再随意发仍有窗口。 |
| HSM / KMS | 保管密钥并提供密码运算的硬件或管理服务。 | 不自动理解用户利益、calldata 语义或应用策略代次。 |
| 在途 / context 超时 | 已发出可能被设备接受、调用方停止等待。 | 可能已经产生签名，取消本地等待不能让该签名消失。 |
| 同载荷重试 / ECDSA | 对同一批准内容再尝试、消息签名机制。 | 仍归原任务且承认可能多份签名，不能承诺设备恰好签一次。 |
| txNonce / 替换候选 | R 的账户交易序号、同槽位新签的竞争交易。 | 提价改变交易摘要，须关联新载荷、新审批，旧候选仍存在。 |
| 审批有效期 / 链上期限 | 本地允许签发的窗口、X 判断意图可执行的窗口。 | 本地到期不会令已签普通 EOA 交易自动过期，模拟也不锁住未来链状态。 |

## 把整篇文章压缩成一个故事

**起因：** 小林的 A 已签好 1000 USDC 换至少 0.49 WETH 的意图，Go 要请 R 代付 Gas。独立签名服务只掌握 K_R，收到的不应是一串“请签这个哈希”，而应是完整外层交易：链 1、R、to=X、value=0、指定入口、完整 calldata、交易 nonce 和费用边界，并独立核对其中 A 的授权及受控路线。

**处理及异常：** 服务把规范载荷固定为 jobID 与 payloadHash，审批绑定策略版本、密钥版本和预算。假设旧策略批准后任务排队，管理员随后停用该策略，派发前就必须按当前状态重查，并通过受信关口阻止过期任务；不能只因旧版本号记录齐全就放行。若 HSM 已接受请求才停用，或 Go 等待超时，则有效签名仍可能晚到，只能按原任务恢复并保留风险预留，不能换个 jobID 绕过控制再签。

**结果及边界：** 返回签名还须核对预期密钥和摘要；以后若提高费用，即使沿用 R 的 txNonce，也已改变载荷，须新审批并关联旧候选。A 的意图 nonce 让同键最多一次成功，不能替 R 阻止重复失败造成 Gas 损失；本地审批到期和围栏更不能撤回已经签出的交易。HSM 不导出私钥仍可能签出规则范围内的恶意请求，所以调用方、速率、预算、审批治理和执行时 X 的检查缺一不可，预检成功也不是成交保证。

**流程位置与核心机制：** 本题从 Go 编排服务向独立签名服务提出外层交易签名请求开始，讨论请求语义、审批绑定、策略版本、TOCTOU 与密钥权限。它不负责替用户生成兑换授权，也不扩写交易广播和确认系统。

**沿用基线：** A 是自持私钥的普通 EOA，初始 1500 USDC、0 WETH，已独立 approve 不可升级的 X 恰好 1000 USDC。用户意图域为 `chainId=1、name=OneTrade、version=1、verifyingContract=X`，字段固定为 `owner、tokenIn、tokenOut、amountIn、minAmountOut、recipient、nonce、epoch、deadline、routeHash`，其中 `recipient=A、nonce=42、epoch=7、deadline=T0+120秒`，相等时仍可执行。兑换花 1000 USDC、至少收 0.49 WETH，示例收 0.50 WETH，不部分成交、业务费为 0。R 是另一个 EOA，其 Gas 私钥 K_R 由 HSM/KMS 托管；所有签名服务策略均约束 R 的外层交易，绝不是托管 A 的私钥。合约钱包、permit 或 MPC 都只能作为明确改变条件的扩展。

## 第 1 层：独立签名服务应该掌握什么权限

**面试官：** Go 业务服务已经验证了用户意图，为什么不能直接把 K_R 放在进程里签交易，而要独立签名服务？

**面试者：** 独立服务把“业务可以请求什么”与“谁能使用私钥”分开，使业务进程失陷不必然等于私钥被导出或可以签任意交易。业务服务提交结构化的外层交易请求，签名服务独立判断它是否符合 R 的最小权限，例如只允许链 1、发往 X、value 为 0 的指定兑换入口，并限制 Gas 与费用。A 的 SwapIntent 仍由 A 签，R 只签支付 Gas 的外层交易，不能把两种签名合并成一种授权。私钥隔离降低暴露面，但不自动提供业务正确性：若接口允许业务传任意 hash 就签，攻击者仍可合法调用签名接口生成危险交易，独立部署本身没有补上策略边界。

## 第 2 层：为什么不能只检查目标地址和 value

**面试官：** 你把请求限制为“链 1、to=X、value=0”。既然 X 不可升级且只执行受控兑换，这三项检查是否已经足够？

**面试者：** 还不够。签名服务要从待签交易的完整字段重新构造签名载荷，验证选用的交易类型、chainId、预期发送者 R、to、value、函数 selector、完整 calldata、Gas、费用上限和交易 nonce，而不是相信请求里另附的文字说明。calldata 应解码成允许的 ABI 结构，检查意图、用户签名和路线参数，拒绝不支持的 selector、模糊或不规范编码，不能批准一个描述却签另一段字节。完整 calldata hash 必须进入审批绑定。若支持带访问列表等交易类型，还需显式纳入其字段；未知类型直接拒绝。to 固定只能限制目标，无法自动限制同一目标中的动作、资源消耗和请求身份。

## 第 3 层：签名服务如何理解 calldata 而不取代 X

**面试官：** 上一答要求解析 calldata。它已经包含用户签名和 routeHash，签名服务是不是只要检查字段齐全，不必再理解兑换语义？

**面试者：** 字段齐全只证明格式完整。签名服务应独立重算链 1、X 域下的 digest，核对 owner、recipient、输入输出资产、金额、期限、epoch 和一次性 nonce 的请求语义；普通 EOA 路径验证 A 的签名，并按固定类型重算 routeHash，检查路线目标、selector、资产、池是否符合服务策略。金额用受限的 uint256 整数转换，不能经 float64，Go 中也不能共享可变 `big.Int` 指针导致批准后值被改写。这些检查减少代付滥用和错误请求，但不是替代 X 的链上裁决：余额、allowance、used、epoch 和实际输出仍由 Token 与 X 的执行状态决定。已部署 1271 钱包的预检是另行支持的扩展，不能伪装成普通 recover。

## 第 4 层：怎样保证审批与签名是同一份载荷

**面试官：** 你说独立检查语义，但业务若在批准以后换掉 recipient、Gas 或 calldata，签名线程怎样发现不是刚才审核的请求？

**面试者：** 我会把请求规范化为不可变载荷，保存 jobID 和 payloadHash；hash 应覆盖完整待签外层交易字段、用户意图与签名数据，以及明确的编码版本。审批记录绑定 jobID、payloadHash、chainId、R、txNonce、费用预算、policyVersion、keyVersion 和审批者身份，不能只写“允许签 job123”。签名线程从签名服务控制的持久记录读取规范字节，重算绑定值后直接构造待签 digest，不再使用业务进程可变对象或未绑定的回调参数。对同一 jobID 提交不同 payloadHash 应报告冲突，不能覆盖旧记录。签名返回后还要校验签名确实对应预期公钥和这份 digest，避免错误 keyVersion 或编码偏差被带到后续流程。

## 第 5 层：版本绑定为什么还没有解决 TOCTOU

**面试官：** 上一答已经绑定 policyVersion 和 keyVersion。若请求在旧策略下获批，但排队期间发生禁用、限额收紧或密钥停用，仍按原审批签名是不是也“没有被篡改”？

**面试者：** 字节没被篡改不代表权限仍然有效，这正是签名策略的 TOCTOU。签名服务在实际授权派发前必须重查当前策略、密钥启用状态和审批有效期，要求审批绑定的版本仍被允许，或重新走当前策略审批；不能仅因为旧版本记录存在就继续签。并发共享的 Gas 预算等可变限额应在同一授权事务中校验并预留，避免两个请求各自检查通过后超限。可以用条件状态转换，把待签记录、有效策略版本和预算预留一起提交为“允许派发”，由受信派发器只领取这种记录。额度与版本都要有权威状态和明确切点，单纯在日志中记录版本号不构成防竞态机制。

## 第 6 层：策略撤销的承诺必须停在哪个边界

**面试官：** 你说先提交“允许派发”，但派发器向 HSM 发请求之前仍有一个时间窗口。管理员这时停用策略，是否保证任何旧请求都不会产生签名？

**面试者：** 不能不加条件地承诺。若希望停用能拦住尚未派发的请求，停用与实际派发必须经过同一受信串行化关口，由派发器检查策略代际并阻止被栅栏隔离的旧任务；仅在数据库检查后随意发 HSM 请求仍有窗口。停用响应应明确表示已停止新派发，以及哪些请求已在途。请求一旦被 HSM 接受，就可能产生有效签名，通用 HSM 不会自动识别我们的数据库策略版本；本地取消、RPC 超时或晚到的停用不能抹掉它。若无法确认在途状态，应按“可能已签”处理。要有更强的即时撤权，需要签名设备侧也支持相应策略或同步栅栏，不能用应用层状态假装已实现。

## 第 7 层：未知签名结果为什么不能换任务再签

**面试官：** 上一答承认 HSM 已接受的请求可能晚到。那签名调用超时以后，换一个 jobID 再签相同业务，最后只使用先返回的结果，可以吗？

**面试者：** 不应这样做，因为超时不是未签，换 jobID 会绕开原审批、预算和幂等控制，形成重复授权。应保留原 jobID、不可变 payloadHash，以及每次尝试、签名结果和后续广播的独立身份，优先按设备能力查询或恢复原结果。设备没有幂等查询也不能宣称实现了“签名恰好一次”；必要的同载荷重试必须处于同一个受控任务下，并保留可能存在多个签名的事实。用于未知费用暴露的预留也不能因 RPC 超时立即释放。ECDSA 同一 digest 可能产生不同签名字节，因此恢复以业务身份、交易载荷和交易 nonce 为依据，不能把签名字节不同理解为独立业务，也不能误判原签名已经消失。

## 第 8 层：同一业务要提高费用时怎样重新授权

**面试官：** 你要求未知结果先恢复原任务。但 R 的交易很慢，业务想保留相同 txNonce、提高费用重新签名，这还是原来的不可变载荷吗？

**面试者：** 不是。费用字段变化会改变外层交易 digest，必须生成明确关联原尝试的新载荷和新审批，不能篡改原 payloadHash，也不能只凭“业务内容一样”跳过签名策略。R 的 txNonce 属于 `(chainId,R)` 范围，与 X 的意图 42 完全不同；同 nonce 候选之间存在竞争，并不意味着旧签名被销毁。新签名仍需满足当前策略、keyVersion、费用与总 Gas 暴露预算，重复候选的预留也要按统一风险口径处理，不能借替换不断放大费用。X 对同一意图只允许一次成功消费，能保护用户意图不被重复结算，但不能自动阻止 R 为失败或重复提交支付 Gas。本题仅限定签名授权边界，不展开替换传播机制。

## 第 9 层：模拟成功能否消除执行时的状态变化

**面试官：** 上一答强调用户意图一次性和 R 的费用风险不同。如果签名前先模拟成功，再限定很短的签名有效期，能否保证策略批准的交易一定按原状态执行？

**面试者：** 不能。模拟是指定区块状态的观察，批准到执行之间 A 仍可转走余额、修改 allowance、取消意图或提高 epoch，池价也会变化；合约钱包扩展还存在 1271 权限状态变化。外层普通 EOA 交易也不会因为签名服务的本地审批到期而自动失去密码学有效性，不能把审批有效期当成链上交易期限。X 只按实际执行时的意图 deadline、epoch、used、签名和最小输出裁决；该 deadline 到来不撤销 Token allowance。签名服务应保存预检区块引用、限定预检新鲜度并控制重验与费用，但明确保留执行失败的可能。失败时用户资金与 used 回滚，R 仍可能付 Gas，模拟成功不是资金冻结或成交承诺。

## 第 10 层：HSM 为什么挡不住获授权的恶意请求

**面试官：** 你已经绑定载荷、重查策略并记录预检。如果攻击者控制了获授权业务账号，构造了规则范围内却恶意消耗 Gas 的请求，HSM 还能替我们挡住吗？

**面试者：** HSM 通常只能证明私钥按允许的接口完成了签名，不知道这笔请求是否符合用户利益。合法凭据提交的恶意请求若通过当前策略，就可能获得真实有效的签名，设备不导出私钥也挡不住。因此还需要调用方隔离、按用户与任务的费用预算、速率限制、可疑请求复核，以及策略管理和审批职责分离；这些约束要在签名授权关口执行，而不是只在被攻陷的业务服务里执行。审计证据应串起原意图 digest、规范载荷、策略与密钥版本、审批、派发、尝试及返回结果。手工反例是 recipient 不变、用户旧意图仍有效但时机恶劣的重复请求：X 的约束可能保护用户最低输出，却不能替 R 的业务风控判断是否值得付费。

## 本题收束

- **讲透的机制：** 签名服务对 R 的完整外层交易独立验策；jobID、不可变 payloadHash、审批、版本和预算构成同一授权事实，不允许任意 hash 即签。
- **最易答错的边界：** 版本绑定不能代替当前策略校验；校验与派发需要明确 TOCTOU 切点；HSM 接受后的未知结果不能按“未签”释放；本地到期不撤销已生成的外层交易签名。
- **检验反例：** 请求以旧策略获批，等待期间策略被停用。若线程仍凭旧审批直接调用 HSM，版本记录再完整也没有阻止越权；若 HSM 已接受请求，再宣称停用让签名“物理消失”，则跨越了系统实际能控制的边界。
- **剩余风险：** 被允许的恶意请求、策略配置错误、审批者失陷、预检与执行状态变化仍需独立治理，不能把 HSM、模拟或用户意图 nonce 当作业务风控的替代品。
