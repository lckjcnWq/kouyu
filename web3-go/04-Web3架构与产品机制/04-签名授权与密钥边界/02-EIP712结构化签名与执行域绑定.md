# 大问题 2：怎样用 EIP-712 把兑换权限绑定到具体参数、具体链和具体执行合约？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EIP-712 / SwapIntent | 结构化签名规范、本协议定义的兑换意图类型。 | 统一钱包、Go 与 X 对授权内容的理解，不自动保证展示诚实或只能执行一次。 |
| schema / encodeType | 数据的固定结构、把类型声明写成规范字符串的方法。 | 字段名称、类型、大小写和声明顺序都参与授权，不能随意更换。 |
| typeHash / structHash | 类型声明的指纹、某份具体数据的指纹。 | 先固定“表格长什么样”，再把这次 A 的全部兑换字段纳入计算。 |
| domainSeparator | 签名适用环境的指纹。 | 来自 OneTrade、版本 1、chainId=1 和 X，X 应自行构建而非相信调用者。 |
| chainId / verifyingContract | 链编号、负责验证并执行授权的合约地址。 | 换链或换 X 通常改变摘要；相同链编号和地址的分叉不一定可区分。 |
| digest / keccak256 | 最终待签名摘要、以太坊使用的哈希算法。 | Ethereum Keccak-256 不是标准 SHA3-256，也不是直接哈希 JSON。 |
| 0x1901 / `\|\|` | 两个固定原始字节、按顺序拼接字节。 | 最终哈希输入为前缀、域指纹和结构指纹，不是把可见字符串拼起来。 |
| ABI / abi.encode | 合约数据的有类型编码规则、标准编码方法。 | 地址补齐到 32 字节、整数按 32 字节编码，不能任意改成紧凑拼接。 |
| uint256 / 2²⁵⁶−1 | 256 位非负整数类型及最大值。 | 大整数可用十进制字符串传输，但声明类型仍是 uint256，不能经 float64。 |
| amountIn / minAmountOut | 输入数量、最低输出数量。 | 1000 USDC 和 0.49 WETH 分别按 6 位、18 位精度换成整数签名。 |
| owner / recipient | 谁授权、谁收款。 | 本例均为 A，但仍是两个独立字段，不能因显示相同而省掉一个。 |
| routeHash / plan | 规范路线计划的哈希、实际路线内容。 | X 重算计划哈希，并从同一计划派生真实调用，不能另用未绑定的 calldata。 |
| target / selector / delegatecall | 调用目标、函数标识、借用其他代码执行的调用方式。 | 哈希匹配不等于目标安全；X 仍限目标、函数、代币和池，不开放任意执行。 |
| nonce / epoch / used | 意图编号、权限代次、已不可用状态。 | 同域同键最多成功一次由 X 的状态消费保证，不是 EIP-712 自动提供。 |
| deadline / revert | 执行期限、整笔回滚。 | 到期由合约比较链上时间；兑换失败时 used 回滚，合法意图未必永久失效。 |
| executor / 版本迁移 | 指定执行者、新规则的发布方式。 | 基线没有 executor、业务费为 0；新增限制或扣费须重新定义并实际执行授权规则。 |

## 把整篇文章压缩成一个故事

**起因：** 小林的 A 要签一份花 1000 USDC、至少收 0.49 WETH 的兑换委托。钱包、Go 和合约 X 不能各自理解“差不多的文字”，于是共同使用固定 SwapIntent 类型，把收款人 A、nonce=42、epoch=7、T0+120 秒期限和路线都写进去，域固定为 OneTrade / 1 / 链 1 / X。金额进入签名前分别变成 1000000000 和 490000000000000000 个最小单位。

**处理及异常：** 三端按同一类型和 ABI 编码计算 typeHash、structHash、domainSeparator，再哈希原始 0x19、0x01 字节与后两个指纹得到 digest。R 若改 recipient 或换一份路线，X 重算出的摘要就不再匹配；即使路线哈希匹配，X 也只执行白名单内能力，不能检查一份计划却调用另一份 target/calldata。Go 若误用 SHA3-256、显示小数或 JSON 哈希，也会与 X 不一致，应拒绝而非猜一种能通过的编码。

**结果及边界：** 签名把允许执行的内容钉住，X 还须在实际执行时检查期限、epoch 和同域消费键，才能限制 A/7/42 最多成功一次；失败整体回滚后，在有效条件下仍可能重试。换执行合约或正确区分的链域不能沿用原签名，但相同链 ID 与地址的分叉不能只靠这个域区分。旧签名也不能凭空增加指定 R 或收费权限；本例 X 不可升级，新业务须明确迁移规则，而不是只改展示文案。

**流程位置与核心机制：** 本题负责把用户看到的兑换约束变成钱包、Go 和 X 共同理解的唯一 digest，深入 domain、typeHash、structHash、ABI 编码和路线承诺。签名恢复实现见母题 03，防重放的状态消费见母题 04。

**讨论前提：** 教学协议的域固定为 `name=OneTrade`、`version=1`、`chainId=1`、`verifyingContract=X`。X 不可升级；X 是不可运行的教学占位地址，不生成真实签名向量。以下整数均为 uint256，普通 EOA A 签署 exact-input、全成全撤意图，业务费为 0。

## 第 1 层：不是签一句“同意兑换”，而是签完整意图

**面试官：** 为什么这笔 1000 USDC 换 WETH 的授权要用 EIP-712？你具体让用户签什么？

**面试者：** 我让 A 签结构化的 SwapIntent，而不是一段不可解释的任意字节。它包含 owner、输入输出 token、1000 USDC 的整数金额、0.49 WETH 的最小输出、recipient=A，以及 nonce=42、epoch=7、deadline=T0+120 秒和 routeHash。domain 另行绑定 OneTrade、版本 1、链 1 和执行合约 X。这样钱包有机会展示有类型的业务数据，X 也能按同一规则验证授权。EIP-712 只统一签名数据与域的哈希方式，不证明前端诚实、不保证钱包展示完整，也不会自动提供 nonce 消费。安全成立还依赖 A 审阅正确数据以及 X 实际执行所有已签约束。

## 第 2 层：类型和字段顺序怎样进入签名

**面试官：** 你强调“同一规则”，如果前端调换字段顺序，或者把 amountIn 改成字符串类型，会不会仍然得到同一个签名消息？

**面试者：** 不会把这些变化视为同一种 schema。SwapIntent 的 encodeType 固定为下面这段大小写和顺序都确定的类型字符串，typeHash 是它的 Keccak-256。structHash 再对 typeHash 和按此顺序编码的字段做哈希。字段声明的顺序决定编码，不依赖 JSON 对象键的遍历顺序；JSON 用十进制字符串传递大整数，也不代表 EIP-712 类型变成 string。把声明从 uint256 改成 string 会改变 typeHash 和字段编码，验证方必须拒绝，而不是自动猜测。owner 和 recipient 即使在本例都等于 A，也保留为两个独立字段，避免另一意图借相同显示文本偷换收款权限。

```text
SwapIntent(address owner,address tokenIn,address tokenOut,uint256 amountIn,uint256 minAmountOut,address recipient,uint256 nonce,uint256 epoch,uint256 deadline,bytes32 routeHash)
```

## 第 3 层：从结构哈希推到最终 digest

**面试官：** 类型已经固定了，domain 到底怎样参与哈希？X 怎样防止调用者传一个假的 domain 给它验？

**面试者：** domainSeparator 根据固定的域类型和域值生成，最终 digest 是 Keccak-256 对 `0x1901 || domainSeparator || structHash` 的哈希，其中 0x19、0x01 是两个原始字节。X 必须根据自己的固定名称、版本、执行时 chainId 和自身地址构建或安全缓存域，不能信任调用者提供的 chainId 或 domainSeparator。这里域类型的 name、version 是动态字符串，先各自哈希后作为 bytes32 编入 abi.encode；chainId 为 uint256，verifyingContract 为 address。Go 与钱包使用相同域值。本教学预期链为 1；链上下文变化时不能继续拿旧缓存无条件验签，X 的域构造应感知实际链上下文。

```text
domainTypeHash = keccak256(
  "EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)"
)
domainSeparator = keccak256(abi.encode(
  domainTypeHash, keccak256(bytes("OneTrade")), keccak256(bytes("1")), chainId, X
))
structHash = keccak256(abi.encode(
  swapIntentTypeHash, owner, tokenIn, tokenOut, amountIn, minAmountOut,
  recipient, nonce, epoch, deadline, routeHash
))
digest = keccak256(0x1901 || domainSeparator || structHash)
```

## 第 4 层：相同公式为什么仍会在 Go 与合约间不一致

**面试官：** 大家都用了这个公式，Go 算出的 digest 还是可能不一致吗？你会先检查哪里？

**面试者：** 会，我先检查是否真的使用 Ethereum Keccak-256，而不是标准 SHA3-256；再逐字节比较类型字符串、domainSeparator 和 structHash。uint256 必须在 0 到 2²⁵⁶−1 范围内按 32 字节大端编码，address 是原始 20 字节左补零到 32 字节，bytes32 原样占一个槽。1000 USDC 是 `1000000000`，0.49 WETH 是 `490000000000000000`，不能把显示小数或 float64 近似值放进去。也不能用 JSON 序列化结果的哈希代替 structHash，或随意把 abi.encode 换成 encodePacked。Go 应使用受限的 big.Int 和有类型 ABI 编码器，拒绝非法输入，而不是截断高位或自动补救后验签。

## 第 5 层：只绑定 routeHash 是否足够限制执行能力

**面试官：** 你已经把普通字段编码对齐了，但路线只有一个 routeHash。R 能不能提交另一段恰好“看起来一样”的路线，甚至让 X 调任意地址？

**面试者：** routeHash 必须来自规范固定类型路线计划的 `keccak256(abi.encode(plan))`。规范要固定字段类型、顺序、嵌套结构和序列的顺序含义，不能让前后端分别按 JSON 文本或自选拼接方式计算。X 收到计划后重新计算 hash，并从该计划派生实际调用，不接受另一份未绑定的目标或 calldata 去执行。即使哈希匹配，也仍要检查 X 内置白名单中的目标、selector、资产和池；签名只能选择协议允许的能力，不能打开任意 call 或 delegatecall。最小输出和 recipient 仍由主结构绑定并由 X 校验，不能只相信路线下游返回的自报数字。

## 第 6 层：域隔离和业务执行检查各自挡住什么

**面试官：** 如果路线和 digest 都正确，把同一签名拿到另一条链或另一个合约上，是否就绝对无法再用？

**面试者：** 在正确实现且域不同的执行环境里，换 chainId 或 verifyingContract 会改变 digest，因此无法继续作为 A 对新域的授权。但这是有前提的隔离，不是对所有分叉的绝对保证：若两个环境同时保留相同链 ID、合约地址和相关状态，仅靠该 domain 无法区分它们。X 内部即使增加多个入口，也必须让所有能执行 SwapIntent 的路径共享同一套消费与能力约束；domain 不会自动隔离同一个合约的任意业务入口。最终还要检查当前 epoch、used、期限、金额、资产和路线。签名绑定“什么可以执行”，状态机决定“此刻是否仍允许执行”。

## 第 7 层：同一合法 digest 为什么还能被重复提交

**面试官：** 既然还有状态机，同一签名在同一个 X 里重复提交时，EIP-712 自己能替你拦住第二次吗？

**面试者：** 不能，EIP-712 明确不自带重放保护。本模型用 `(chainId,X,owner,epoch,nonce)` 作为唯一消费键，同键即使签了不同金额也只能成功一次。X 要求 epoch 等于 currentEpoch[A]=7、执行时间不晚于 deadline、键仍可用，再验签；在 nonReentrant 入口中于外部调用之前标记 used，与拉币和兑换处于同一事务。若输出不足而整体 revert，used 也回滚，原签名在其他条件仍满足时可重试。业务若改成永久消费失败请求，或支持部分成交，就已经改变本模型，不能只换一种数据库去重方式而声称规则不变。

## 第 8 层：未来加费用、执行者或新版本怎样保持边界

**面试官：** 现有 schema 没有 executor 和费用字段，未来产品要指定 R 并收费，可以复用老签名或只改前端展示吗？

**面试者：** 不可以。老签名授权的是任何 Relayer 转发、业务费为 0 的这组固定字段，不能从外层交易发送者或前端文字推导出指定执行者和扣费权限。新能力要定义明确的新类型及费用、执行者约束，并在验证和执行路径实际落实；必要时使用新域版本或新执行合约。本模型中的 X 不可升级，所以不能讲成原地升级 X 后自动兼容。迁移到新 X 也意味着新的 verifyingContract，旧签名不会自动成为新 X 的授权。验证设计时应分别改变 recipient、minAmountOut、routeHash、链 ID、X 和类型版本，预期都不能沿用原授权；再单独推演同域同键重复提交必须由 used 拒绝，而不是由签名算法拒绝。

## 本题收束

- **讲透的机制：** 类型声明、字段编码、执行域三者共同生成 digest；X 自行构造可信 domain，路线哈希和白名单共同限制调用能力。
- **最易答错的边界：** EIP-712 不是 JSON 哈希，不自带 nonce、过期或业务限权；同链 ID 的分叉不能仅靠域区分；不可升级 X 不能被默认为代理合约。
- **检验反例：** 如果 X 校验了 routeHash，却执行调用者另传的 target 与 calldata，签名承诺就没有连到真实执行路径。哈希算法再正确也无法补救这条断开的权限链。本题未运行编码向量或工程测试。
