# 大问题 4：怎样用 nonce、epoch 和域隔离保证一份兑换授权最多成功一次，并在失败与重组后保持正确？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 重放 / 最多一次成功 | 重复拿授权执行、禁止同一权限重复兑现。 | 限制的是成功消费，不是只允许接收一次请求或尝试一次。 |
| intentNonce / 无序 nonce | 协议的一次性业务编号、不要求逐号执行。 | A 的 42 不必等 41，也不等于 A 或 R 的交易序号。 |
| 消费键 / 五元组 | 唯一圈定一份一次性权限的身份。 | 键为 chainId、X、owner、epoch、nonce，跨部署索引不能省掉链与合约。 |
| epoch / currentEpoch | 授权代次、用户当前有效代次。 | A 当前为 7，提高到 8 会拒绝第 7 代意图，不会改 Token 的授权。 |
| used / unavailable | 已执行或取消而不可再用的状态。 | 同一位可能对应不同原因，单看 true 不能断言兑换成功。 |
| digest / 签名 bytes | 已签内容指纹、某种具体签名编码。 | 二者都不能取代消费键；同键不同内容仍互斥，不是各执行一次。 |
| EIP-712 / 域隔离 | 绑定结构化内容及适用环境的签名规则。 | 区分链和 X，但相同链 ID、地址及状态的分叉不一定可区分。 |
| mapping / bitmap | 按键保存状态、用一个字的多位压缩状态。 | 只是存储选择，不改变无序一次性消费规则。 |
| word / `>>8` / bit / `&255` | 找存储字、右移八位、找字内位置、取低八位。 | nonce=42 得 word=0、bit=42；一个 uint256 字能放 256 个不可用位。 |
| nonReentrant / 外部调用 | 防止同笔执行回调重入的入口保护、调用其他合约。 | X 在拉币或兑换之前标记 used，不能只靠交易顺序忽略回调。 |
| 原子消费 / revert | 状态与资金一起提交、失败整体回滚。 | 输出只有 0.48 WETH 时，used、资金及本次 allowance 消耗一起撤回。 |
| Gas / txNonce | 外层交易的执行费与账户顺序号。 | R 的失败交易可能耗费二者，不说明 A 的业务 42 已用掉。 |
| raiseEpoch / 回绕 | 提高授权代次、整数越过上限后绕回小值。 | epoch 只能严格增大，不能降级或清位让未过期旧签名复活。 |
| Permit nonce / SIWE challenge | Token 授权签名序号、登录的一次性挑战。 | 与 X 的兑换 nonce 相互独立，数字碰巧相同也没有联动。 |
| 唯一约束 / jobID / payloadHash | 数据库防重复规则、签名任务号、固定载荷指纹。 | 让自身服务关联原请求，无法代替 X 阻止其他转发者。 |
| 规范链 / 重组 / 区块证据 | 当前接受的链历史、分支切换、结果所在位置。 | 被移除的成交不能继续锁住新链状态，恢复时须重查并解释不可用原因。 |

## 把整篇文章压缩成一个故事

**起因：** 小林的 A 在链 1 的 X 上签了 epoch=7、nonce=42 的意图：花 1000 USDC，至少收 0.49 WETH，期限 T0+120 秒。两个 Relayer 都读到它尚未使用；小林若又用同一个 42 签出另一个最小输出，也只是同一消费键下两份互斥条款，不是新增一次花钱机会。

**处理及异常：** X 按链上顺序执行，在外部调用前于受重入保护的入口写入 used。若首笔实际输出 0.50 WETH 并整体成功，后笔就不能再次消费 A/7/42；若首笔仅输出 0.48 而整体 revert，used 和本次资金、额度消耗都回滚，A 仍有 1500 USDC、0 WETH、1000 USDC allowance，后笔在有效条件下仍可成功。用 bitmap 保存时，42 落在 word=0 的第 42 位；压缩存储不改变上述语义，也不能靠清零来重置旧权限。

**结果及边界：** Go 用完整键与不可变 digest 受理重复请求，同内容找回原任务，异内容报冲突；超时不能自动换新 nonce，否则会新增可执行权限。小林可链上提高 epoch 到 8 作废旧代，但不会重置 R 的交易 nonce、Permit nonce 或登录挑战。最后须用具体区块和执行/取消事件解释 used 的原因；若成功块被重组移除，就按新规范链重查，不能让数据库里的“曾经完成”冒充永不变化的链上锁。

**流程位置与核心机制：** 本题负责兑换资格的一次性消费，从唯一键、同键冲突推进到并发执行、事务回滚、存储结构和恢复。取消竞争的产品语义由母题 05 深入，外层交易 nonce 的广播调度不在这里展开。

**讨论前提：** 教学协议为链 1 上的不可升级 X，A 签 nonce=42、epoch=7、deadline=T0+120 秒的 exact-input 意图。当前 `currentEpoch[A]=7`，1000 USDC 至少换 0.49 WETH，全成全撤、不部分成交，允许任何 Relayer 转发。

## 第 1 层：nonce=42 到底承诺什么

**面试官：** 用户签了 nonce=42 的兑换意图，你怎样定义“不能重放”，而不只是说数据库做幂等？

**面试者：** 我定义为同一个 `(chainId,X,owner,epoch,nonce)` 最多成功消费一次，而不是“同一串签名字节最多收到一次”。这里 42 是 X 协议自定义的一次性业务 nonce，不要求等于 A 的交易 nonce，也不是全链唯一数字。用户在不同 owner、不同 epoch 或不同执行域中使用 42，各自可以是不同权限；在同一键下，则不论签名怎样编码、谁来提交，都只能有一次成功执行或有效取消。这个不变量必须由 X 的权威状态裁决，数据库只能减少本服务重复受理，无法阻止别人直接调用 X。

## 第 2 层：唯一键怎样映射到真实链上状态

**面试官：** 你把 chainId 和 X 都写进唯一键，合约里是否真的要建立一个包含这五个字段的巨大 mapping？

**面试者：** 不一定。在当前链的 X 状态空间内，链和部署地址通常已由执行环境隔离，合约可用 `used[owner][epoch][nonce]`，同时用正确的 EIP-712 域绑定实际链 ID 和 X。跨链服务、索引库和缓存仍必须保存完整五元组，否则两个部署的 42 会被混为一谈。X 的所有可执行入口都必须共享这套消费状态，不能某个入口查 used、另一个只验签。链 ID 不同的部署可由域隔离，但保留相同链 ID、地址与状态的分叉不一定可区分；不能声称这五个文本字段天然解决所有分叉重放。

## 第 3 层：同键签了两份不同内容，按哪一份执行

**面试官：** 如果 A 在 epoch=7、nonce=42 下签了两个不同 minAmountOut，能把 digest 也放进键里，让两份都执行吗？

**面试者：** 不能，这会把“一次性 nonce”改成“每个内容各执行一次”。两份签名的 digest 不同，但消费键相同，应被看作互斥的业务权限；哪份先在链上成功，哪份消费这个键，另一份随后被拒绝。若 A 想替换旧意图，仅仅签一份相同 nonce 的新版本，无法令别人手里的旧版本失效。Go 服务可记录该键第一次受理的 digest，同内容返回原任务，不同内容明确报冲突，但它不能替链上宣布“新版本覆盖旧版本”。真正撤销旧权限应先通过 cancelNonce 或 raiseEpoch 取得链上结果，再使用新的可用键。

## 第 4 层：两个 Relayer 同时通过预检怎么办

**面试官：** 你说链上先成功者获胜，可两个 Relayer 都预检到 used=false，是否还要靠分布式锁避免双花？

**面试者：** 分布式锁最多减少自身重复提交，不是正确性根基。EVM 对交易给出确定执行顺序，第一笔进入 X 后检查 used，标记该键不可用，再做外部调用；第二笔在第一笔提交之后看到 used=true 就拒绝。标记要在 Token、受控路线等外部调用之前，且入口有 nonReentrant，防止外部调用重入时在标记窗口绕过消费。不能只说“交易串行”就忽略单笔交易里的回调。若第一笔整体失败，它的 used 写入不提交，第二笔仍有机会执行；这不是双花，因为此前没有成功兑换。

## 第 5 层：失败为什么不应永久消费这个 nonce

**面试官：** 先写 used 再兑换，如果路线输出不足，是否应该为了防重复请求把 used 留着，不让第二笔再进来？

**面试者：** 不能偷偷改变全成全撤语义。本基线把 used 写入、transferFrom、兑换、输出校验与交付放在同一 EVM 事务，输出只有 0.48 WETH 时必须整体 revert，连同 used、余额变化、allowance 消耗和本次日志一起回滚。此前独立确认的 approve 仍然存在，A 仍有原来的 1500 USDC、0 WETH、1000 USDC allowance。R 可能支付 Gas，其外层交易 nonce 也可能已被消耗；这不表示 A 的意图 nonce=42 已消费。只要 epoch、期限、资金和路线条件仍满足，42 可以重试。若产品希望每次尝试都烧掉 nonce，就要重新设计规则，不能 catch 错误后假装仍是原子兑换。

## 第 6 层：无序一次性 nonce 用 mapping 还是 bitmap

**面试官：** 既然失败后可重试，且多个不同 nonce 可以并行，你会用递增计数器还是 bitmap 存消费状态？

**面试者：** 这个模型的 nonce 是无序的一次性标识，没有“必须先执行 41 才能执行 42”的规则，直接用严格递增计数器会改变可并行性。我可以选 mapping，也可以把每个 owner、epoch 下的 nonce 拆为 `word=nonce>>8` 和 `bit=nonce&255`，用一个 uint256 字承载 256 个不可用位。执行或取消都检查并设置同一位，不做会清除其他位的覆盖赋值。bitmap 只改变存储成本，不改变签名字段、消费键、事务回滚和无序执行语义；稀疏随机 nonce 可能无法获得连续分配的存储收益，不能把压缩效果当作协议保证。

## 第 7 层：epoch 怎样批量失效而不让旧签名复活

**面试官：** 如果 bitmap 很大，要批量取消 A 的旧意图，能否清掉所有位，或者把 nonce 从 0 重新开始？

**面试者：** 不能清空当前 epoch 的消费位来“重置”，那可能让仍未过期的旧签名重新可用。批量作废依靠 A 自己调用 raiseEpoch，使 currentEpoch 严格增加，例如从 7 到 8；执行入口要求意图 epoch 恰好等于当前值，因此所有 epoch=7 的签名立即失去执行资格，不必遍历旧位。新 epoch 可以重新用数字 42，因为键已不同，旧 epoch 则不能再被激活。uint256 增长要拒绝回绕，不能允许任意降级。旧位的清理只有在证明旧 epoch 永不重用、所有入口一致检查之后才可讨论；也不应提前签署未来 epoch 的权限，再误以为提高 epoch 会把这些未来签名一并取消。

## 第 8 层：意图 nonce 与其他 nonce 怎样明确隔离

**面试官：** 你说新 epoch 可以再用 42，那 A 发 raiseEpoch、R 发兑换交易以及 Permit 是否也都跟着重置 nonce？

**面试者：** 都不会。A 发 raiseEpoch 或 cancelNonce 是一笔普通链上交易，它使用 A 在该链的 EOA 交易 nonce；R 提交兑换使用 `(chainId,R)` 范围的交易 nonce，执行 revert 也可能消耗它。X 的意图键属于 `(chainId,X,A,epoch,nonce)`，只有 X 的协议状态决定其可用性。若显式扩展 EIP-2612，Permit nonce 属于对应 Token 的授权协议，Permit 是改 allowance，不是消费兑换意图。SIWE challenge 又是独立登录命名空间，不提供兑换权限。数字相同没有关联，修改 epoch 更不会重置其他 nonce；数据库字段和 API 应使用 intentNonce、txNonce 等明确名称，避免都叫 nonce 后被误接。

## 第 9 层：Go 服务怎样受理重复请求而不制造新权限

**面试官：** 命名已经分清了，Go 服务并发收到同键请求，或者处理超时，该怎样落库和恢复？

**面试者：** 我会对完整意图键建持久化唯一约束，原子插入规范化 digest 与不可变载荷快照。地址按原始字节归一化，chainId、epoch、nonce 用无损整数表示，不能先转 float64 或有符号窄整数；big.Int 和签名切片在安全所有权边界复制。唯一约束冲突后读取原记录，同 digest 关联原任务，异 digest 报冲突，进程内 mutex 不能替代跨实例约束。超时属于结果未知，先按原键和原任务恢复，不自动换新意图 nonce；否则两份不同键都可能有效。外层 R 的签名任务另有 jobID 与 payloadHash，即使其 context 已取消，也不能认定未产生签名。

## 第 10 层：数据库恢复到“已消费”是否就是最终事实

**面试官：** 你已经持久化了任务并查到 used=true，如果随后链重组，或者 used 来自取消而不是成交，恢复器怎样避免误报？

**面试者：** used 只说明该键在所查状态不可用，若执行和取消共用一个位，它本身不说明原因。我会在明确区块查询状态，并关联成功回执、业务事件、交易哈希和区块哈希，区分执行成功、取消成功及尚未确认；失败事务里的事件不构成证据。重组移除原区块后，要撤回相应投影并在新规范链重查 used、currentEpoch、期限和交易结果，不能把数据库曾经的终态当成链上锁。协议保证是对当前规范链状态的原子消费，产品终态还依赖确认策略。预期反例是原成交被重组移除后，键重新可用，而系统仍写“永不可能再执行”；这种确定性承诺超出了链上事实。

## 本题收束

- **讲透的机制：** 完整消费键限定一次性权限；域隔离部署，used 裁决同域重复；无序 nonce、bitmap 和单调 epoch 各有明确职责。
- **最易答错的边界：** 不把 digest 加入消费键来放宽同 nonce 互斥；不永久消费整体回滚的失败兑换；不把 EOA、Permit、SIWE 或签名任务的 nonce 混在一起；不把链下唯一约束当作链上仲裁。
- **检验反例：** A 同键签了两份金额不同的意图，服务按签名 bytes 建唯一索引，X 也按 digest 存 used。两份都可能执行，说明实现保证的是“同一内容不重复”，而不是约定的“同一业务 nonce 最多一次”。此为逻辑推演，未执行工程测试。
