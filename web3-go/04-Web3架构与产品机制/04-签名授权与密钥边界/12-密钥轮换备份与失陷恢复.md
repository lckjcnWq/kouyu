# 大问题 12：怎样轮换、备份和恢复签名密钥，而不遗留旧权限或制造灾备双主？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| A / R / K_R | 用户账户、代付账户、代付账户私钥。 | 平台轮换的是 R 的签名能力，不包含 A 的资产私钥。 |
| 访问凭据 / 包装密钥 / 签名密钥 | 调用设备的凭证、加密保护备份的钥匙、链上签交易的秘密。 | 前两类变更可保留 R，真正换签名密钥通常得到新地址。 |
| EOA / 公钥 / 地址 | 普通账户、私钥对应的公开验证材料、链上身份。 | 本模型不能像改密码一样为旧 R 任意指定新私钥。 |
| R2 / 独立 txNonce | 新 Relayer 身份、它自己账户的交易序号。 | 新地址独立管理 Gas 与 nonce，不能照搬旧 R 的数字。 |
| keyVersion / KMS alias | 密钥版本、可变的密钥别名。 | 审批绑定不可变版本和公钥身份，不能让别名切换偷偷更换签名人。 |
| policyVersion / payloadHash | 策略版本、完整固定载荷指纹。 | 迁移与重签仍须明确审批，不能让旧批准随新环境任意漂移。 |
| 旧签名 / 密钥停用 | 已产生的有效载荷、禁止今后走某托管路径签名。 | 链上不查询后台停用状态，已签交易仍可能被提交。 |
| 业务键 / epoch | X 中一次性意图身份、用户授权代次。 | 链 1、X、A、7、42 不因 R 换到 R2 而新增一次执行资格。 |
| 未知作业 / 风险占用 | 可能已签未回的任务、为潜在支出保留的预算和槽位。 | 交接不能清空重建，否则旧交易迟到时风险被遗忘。 |
| 设备备份包 / 恢复水位 | 产品支持的受保护恢复材料、已恢复记录到哪个位置。 | 不只备份密钥，还要核对任务、审批、nonce、预算和增量证据。 |
| 灾备双主 | 旧区和恢复区同时以为自己有权继续签名。 | 数据库选主不足以隔离仍能离线访问设备的旧主。 |
| fencing / 租约代次 | 实际入口拒绝旧权限、当前工作资格版本。 | 用于停止新签发，不是 X 的用户 epoch，也不能撤回旧主已签交易。 |
| pending nonce / RPC | 某节点看到的待处理序号、读链接口。 | 局部观察看不到全部已签未传播载荷，不能据此认定槽位空闲。 |
| 角色 / allowance / 资产迁移 | 外部系统权力、Token 额度、转移到安全地址。 | R 失陷时要清点真实残余权限，不只把服务切到 R2。 |
| 私钥失陷 / 签名外泄 | 秘密被掌握、一份已签授权被他人取得。 | 前者能继续造新权限，后者在密钥安全时可用具体意图撤销机制收敛。 |
| raiseEpoch / 撤销竞争 | 批量作废旧代意图、撤权与既有执行按链顺序竞争。 | 无法阻止持有 A 私钥者签新意图，迁移资产也不保证在竞争下成功。 |

## 把整篇文章压缩成一个故事

**起因：** 平台准备轮换为小林代付 Gas 的 R。小林的 A 仍自持密钥，旧意图是链 1、X、epoch=7、nonce=42 的 1000 USDC 兑换；平台换钥不改变这份权限。团队先辨别是换设备凭据、换备份包装，还是换真实签名私钥；若真换私钥，就启用新地址 R2，而不是改一个 keyVersion 就说旧 R 原地换好了。

**处理及异常：** 交接先冻结旧版本新受理，盘点未签、可能已签、已广播和执行未知作业，固定载荷与审批，R2 单独管理余额和 txNonce。假设旧机房只是断网、灾备恢复了同一个 R 的密钥和较旧数据库，恢复区不能直接依据一个 RPC 的 pending nonce 开签；必须在真实签名入口隔离旧主，并核对增量作业、受限签名结果与规范链。若隔离不明或记录缺口不能证明安全，就暂停并保留风险，而不是把缺失记录当作从未签过。

**结果及边界：** 受控恢复需要新签发资格、旧作业归属和残余资产权限一起收敛。围栏、设备停用与本地轮换都不能撤回已签交易；若旧 R 私钥已泄露，攻击者能在平台外签名，还须停止旧地址补资、迁移可安全迁走的资产并处理外部角色。独立异常若是 A 私钥泄露，仅提高 epoch 不够，攻击者还能造新意图，用户需安全新地址迁移且不能保证抢救成功；若只是旧意图泄露而私钥安全，才按 nonce 或 epoch 链上撤销并等待确认处理。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖 Relayer 签名密钥的完整生命周期，重点是密钥版本与链上账户身份、旧签名存续、备份与任务状态的一致性、灾备隔离和失陷后的资产迁移。它不把 HSM 的日常访问策略重新展开，也不把用户私钥纳入平台托管。

沿用教学基线：A 是自持私钥的普通 EOA，R 是代付 Gas 的另一个 EOA，只有 R 的 `K_R` 由 HSM/KMS 托管。X 不可升级，域为 `chainId=1/name=OneTrade/version=1/verifyingContract=X`；用户意图的 epoch=7、nonce=42 与平台密钥版本没有对应关系。涉及更换 Relayer 地址或假设 A 私钥失陷的段落，均明确作为对应的运维变更或独立异常变体。

## 第 1 层：先说清轮换的是哪一层密钥

**面试官：** 签名服务准备做定期密钥轮换。你怎样保证轮换后这笔 1000 USDC 兑换还安全？

**面试者：** 我先区分三件事：更换访问 HSM 的凭据、更换加密备份的包装密钥，以及更换真正签交易的 secp256k1 私钥。前两项可以保持公钥与 R 地址不变；第三项一般会得到新 EOA 地址，不能只改一个版本号就说原地址完成了换私钥。A 的私钥与授权不在这个轮换范围。轮换计划要列出旧签名作业、可能已签未回的请求、已签交易和旧 R 的余额；否则新服务上线后，旧版本留下的有效载荷仍可能执行。安全目标不是“新密钥能签”，而是新旧权限和资产都能受控收敛。

## 第 2 层：普通 EOA 能否原地更换私钥

**面试官：** 你说更换签名私钥会换地址，那能让新私钥继续控制原 R，省掉资产和 nonce 迁移吗？

**面试者：** 在这个普通 EOA 模型里不能。地址由公钥导出，不能像修改登录密码一样把原账户绑定到任意新私钥；也不能靠 KMS alias 改变链上的验签关系。若只是重新包装同一私钥，或者在支持的设备间安全恢复同一密钥，仍然控制同一个 R，不属于链上身份轮换。若换成真正的新密钥，就应引入新 Relayer 地址 R2，管理它独立的交易 nonce 和 Gas 余额。合约钱包可以按合约规则更换 owner，但那改变了账户模型；本题不能把这项能力偷加给普通 EOA，也不能指望不可升级的 X 替 R 改私钥。

## 第 3 层：停用旧版本为何不等于撤销旧签名

**面试官：** 那我把旧 keyVersion 禁用，所有新请求改发 R2，旧 R 签过的交易应该也失效了吧？

**面试者：** 不会。停用密钥版本约束的是以后能否经这条托管路径签名，链上验签并不查询 KMS 的启停状态。已经签出的旧 R 交易仍可能被广播，A 已签的兑换意图也不依赖平台 keyVersion，仍受 X 的期限、epoch 和一次性 nonce 约束。基线允许任何 Relayer 提交，因此停用旧 R 不等于取消用户意图。若 A 要取消，必须自己发链上取消或提高 epoch，并与执行按链上顺序竞争。平台轮换不能冒充 A 行使该权利，轮换日志里的“旧钥关闭”也不能作为链上撤销证明。

## 第 4 层：新旧 Relayer 如何受控交接

**面试官：** 既然旧交易仍有效，R 和 R2 交接时，你怎么处理旧作业，又不让新服务把业务再执行一次？

**面试者：** 我会先冻结旧版本的新作业受理，盘点旧作业及签名、广播、执行三个阶段的未知状态，再给每个作业明确归属。未签作业可以在重新审批后迁到 R2；可能已签的作业不能简单清空重建，必须保留旧载荷及风险占用。R2 的 txNonce 从自己的账户状态管理，不能照搬 R 的数字。业务去重仍使用 `(chainId,X,A,7,42)`，不是按 Relayer 地址另开资格。即便策略允许 R2 转发相同意图，X 也只允许一次成功，但两个账户的尝试可能分别花 Gas，因此链上防双花不能替代交接时的预算和任务控制。

## 第 5 层：别名切换怎样避免旧审批签出新载荷

**面试官：** 你说迁移要重新审批，如果工作者只拿到 KMS alias，轮换时 alias 恰好切向新版本，旧审批会不会落到错误密钥？

**面试者：** 会有这个风险，所以审批不能只绑定可变别名。我会固定密钥标识、不可变版本、公钥或地址身份，以及完整待签载荷和 policyVersion；签名服务在真正调用设备前核对实际版本，恢复签名后再验证对应地址。外层载荷还包括 chainId、到 X、value=0、selector、calldata hash、txNonce、Gas 与费用上限。旧审批不能被解释为“当前 alias 指向谁都能签”。如果更换的是同钥包装材料，也应保留版本映射和恢复记录；如果地址改变，则是新签名身份，审批、nonce 和资产交接都要按新身份办理。

## 第 6 层：备份哪些东西才有恢复意义

**面试官：** 固定了版本后，把 HSM 的备份包放到异地，是不是就具备灾备能力了？

**面试者：** 还不够。先确认具体产品是否允许密钥备份、跨设备恢复以及恢复后公钥是否保持不变，不能给“不可导出”自动附加通用备份能力。备份材料应采用设备支持的加密包装、分权审批与独立保管，恢复权限本身也要限权。同时还要保护 jobID、不可变载荷、审批版本、未知尝试、外层 nonce 分配和预算占用记录。只恢复密钥而丢失作业账本，灾备节点可能重新批准已经签过的权限。设备状态与数据库快照并不原子一致，所以还需可核对的恢复水位和增量记录，不能把“都有备份”说成“能无损接管”。

## 第 7 层：怎样证明旧主不能继续签名

**面试官：** 异地恢复了同一个 R 的密钥，但旧机房只是网络隔离、没有真的宕机。你怎样防止两边同时签名？

**面试者：** 不能只依赖数据库选主或进程自觉。我会先让旧主在实际签名授权路径上被隔离，例如撤销旧入口的有效凭据、限制设备访问，或由可验证租约代次的集中签名网关拒绝旧代次；恢复节点必须获得新的受控签名资格。租约失去权威续期后应停止新签发，若旧区仍能凭离线权限直达设备，就还没有完成 fencing。这里的租约代次只是平台权限，不是 X 中 A 的 epoch=7。无法确认隔离时应暂停签名，不冒险接管；而旧主隔离前已经生成的签名仍要作为存量风险处理，不能靠换主删除。

## 第 8 层：隔离完成后怎样处理陈旧账本

**面试官：** 旧主已被隔离，但灾备数据库比它落后，链上 pending nonce 也看不全，你会怎样恢复发送资格？

**面试者：** 我不会直接从某个 RPC 的 pending nonce 开始连续分配。它只是该节点的局部观察，不能列出所有已签未传播交易。应把可验证的作业增量、签名服务记录、受限结果存储和规范链交易对应起来，明确已确认、仍可能占用和无法证明安全的区间；缺少证据的权限与预算继续隔离。恢复同一密钥才是继续控制旧 R；若只能创建新密钥，就按 R2 迁移处理，而不是伪造旧 R 的后续 nonce。灾备目标需要承认证据缺口：恢复服务可用性不能以遗忘未知签名为代价，也不能凭对账承诺不存在丢失记录。

## 第 9 层：私钥已失陷时隔离还能解决什么

**面试官：** 这些隔离都针对平台路径。若攻击者已经拿到了旧 R 的私钥明文，恢复或禁用 HSM 还有用吗？

**面试者：** 仍可阻止平台继续扩大风险，但无法阻止攻击者在平台外自行签名；签名服务的白名单、审批准入都不能约束攻击者。我会停止旧身份的自动充值和新业务，启用经过审批的新 R2，并清点旧 R 的原生币、代币、allowance 和外部角色；有权限控制的外部系统按其真实机制移除旧角色，能安全转出的资产迁往新地址。攻击者也能竞争交易，不能承诺旧余额一定抢救成功。基线 X 没有 Relayer 专属权限，也不依赖旧 R 托管 A 的资产，因此 R 失陷不等于 A 私钥泄露，但旧 R 的资金和有效旧交易仍有风险。

## 第 10 层：如果失陷的是用户 EOA 呢

**面试官：** 你说 R 失陷不等于 A 失陷。换一个独立异常：若泄露的是 A 的私钥，是否只提高 epoch 就够了？

**面试者：** 不够。提高 epoch 可在确认后排除旧 epoch 的意图，却不能改变普通 EOA 的私钥；攻击者仍可签新意图、直接转资产或重新 approve。应由用户迁移到独立安全的新地址，转移资产并清理旧地址的授权和依赖；不保证在攻击者竞争下必能完成。撤销 X 的 allowance 只是阻止当前 transferFrom 条件，不是永久销毁旧签名，后续重新授权或补入资产还可能重新暴露风险。若只是旧意图外泄而私钥安全，则由 A 取消 nonce 或提高 epoch，等待确认即可，不能把“签名泄露”“密钥失陷”和“平台换钥”三种恢复路径混为一谈。

## 本题收束

- **讲透的机制：** 密钥访问凭据、包装密钥和链上签名密钥属于不同层次；身份变化必须落实到新地址、独立 nonce、审批和资产迁移。备份要同时考虑密钥与未知作业，接管前要在实际签名入口隔离旧主。
- **最容易答错的边界：** 轮换不会自动撤销旧签名，EOA 不能原地改私钥；恢复同钥不代表恢复了全部作业事实，禁用 HSM 也阻挡不了持有泄露私钥的人；灾备 fencing 不等于撤回已签载荷。
- **反例推演：** 灾备从陈旧快照恢复同一个 R，旧主仍可签名，新主又认为 nonce 空闲。即使两边对同一账户 nonce 的交易不能在同一规范链历史里同时执行，它们也可能产生冲突载荷、抢占 Gas 预算或让错误业务胜出。若改用新地址但不迁移旧余额、权限与未知作业，风险仍留在旧地址，不能称为恢复完成。

**依据与适用范围：** 旧用户意图能否执行，仍由 X 的 nonce、epoch、期限和资产条件决定，而非密钥管理后台状态。合约钱包按自身规则更新签名人是改变账户模型后的能力，不能反推普通 EOA 也具备。本文仅做机制分析，没有执行备份恢复或失陷演练。
