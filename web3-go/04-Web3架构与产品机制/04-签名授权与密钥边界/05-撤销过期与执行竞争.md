# 大问题 5：签名已经交给 Relayer，用户怎样撤销，过期、执行和取消并发时以什么结果为准？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 链下取消 / 取消 API | 请自家服务停止后续任务。 | 只能影响自己控制的队列，不能抹掉别人持有的有效签名。 |
| cancelNonce(7,42) | 在执行合约里取消一个具体的一次性权限。 | A 发起，针对自己的当前 epoch=7、nonce=42，与执行共用不可用位。 |
| msg.sender / owner | 本次合约调用者、被管理权限的归属人。 | 取消入口从调用者确定 owner；B 不能直接取消 A 的键。 |
| used / Cancelled | 权限不可用状态、成功取消事件。 | used 也可能来自成交，要结合事件和回执区分原因。 |
| AlreadyUnavailable | 该权限之前已不可用的返回结果。 | 不再产生取消事件，不代表后到的取消阻止了一次已成功兑换。 |
| 执行竞争 / 规范链顺序 | 取消和兑换争用同一权限、当前链上实际执行次序。 | 先成功改变状态者决定结果，不看谁先点按钮或先广播。 |
| nonReentrant / 原子事务 | 阻断回调重入、一次整体提交的执行边界。 | 独立取消交易不能插进兑换中间，兑换后续失败则 used 一起回滚。 |
| deadline / block.timestamp / `<=` | 截止时间、执行区块时间、不晚于。 | 本例等于 T0+120 秒仍可执行，只有超过才过期，不用本地钟裁决。 |
| 过期 / 已撤销 / 已成交 | 期限不再满足、权限被取消、资金已交换。 | 三种事实不能互相替代；后来过期不会抹掉期限内已完成成交。 |
| epoch / raiseEpoch | 权限代次、提高代次以批量失效旧授权。 | 从 7 到 8 拒绝旧代，但可能激活预先签过的第 8 代意图。 |
| allowance / approve(X,0) | Token 的使用额度、把 X 的额度设为零。 | 不等于取消意图；再次授权后，仍有效的旧意图可能恢复执行条件。 |
| A / R 的 txNonce | 用户普通交易、转发者外层交易各自的账户序号。 | 命名空间独立，A 无法用自己的同号交易替换 R 的交易。 |
| Gas / 交易替换 | 执行费、同一发送者同序号的新签名交易参与竞争。 | 提高费用不保证取消先到，也不销毁已经存在的旧签名交易。 |
| Go context / 超时 | 本地等待与调用的控制、未及时收到答复。 | 取消等待不证明远端未签发或网络未提交，须恢复原任务证据。 |
| EOA / 密钥更换 | 私钥控制的普通账户、改用另一把密钥或地址。 | 新钱包地址和 R 换钥都不使旧 A 的意图自动失效。 |
| 区块哈希 / 确认 / 重组 | 结果所在分支身份、证据稳定程度、规范分支切换。 | 取消所在块被移除后，旧签名可能重新具备执行资格，页面要修正。 |

## 把整篇文章压缩成一个故事

**起因：** 小林的 A 有 1500 USDC，已独立授权 X 使用 1000 USDC，又签了第 7 代第 42 号兑换意图，要求最少 0.49 WETH、期限 T0+120 秒。签名交给 R 后小林反悔，先点取消按钮。Go 能停自己的未发任务，却不能保证签名没有流到其他 Relayer，所以小林还需自己发 cancelNonce(7,42)，或链上提高 epoch。

**处理及异常：** 若取消先成功，X 拒绝后来的兑换，小林仍有 1500 USDC、0 WETH，原 allowance 仍为 1000 USDC；若兑换先成功拿到 0.50 WETH，后来取消只会返回 AlreadyUnavailable，不会还原资产。若兑换先执行却只有 0.48 WETH 而回滚，used 也回滚，随后取消仍可成功。顺序由规范链上成功提交决定，提高 Gas、取消 context 或先收到 API 响应都不能保证获胜；执行时间恰等于 deadline 也仍可通过。

**结果及边界：** 在兑换获胜分支，小林最终是 1500−1000=500 USDC、0.50 WETH，页面必须说“取消未阻止本次执行”，不能说未扣款。提高 epoch 只处理意图代次，取消意图不清 allowance，清 allowance 也不销毁旧意图，更换地址不替旧地址撤权。取消回执还须附区块身份和确认等级；若其区块被重组移除，要重查并提示仍可能执行，不能把本地已取消当成永久链上事实。

**流程位置与核心机制：** 本题负责已签权限的失效和用户可见结果，从离线取消的局限推进到链上单笔取消、epoch 批量取消、执行竞争、期限边界及重组恢复。只讨论本教学协议，不引入任意调用或真实攻击脚本。

**讨论前提：** A 是自持私钥的普通 EOA，已经在独立且确认的交易里 approve X 恰好 1000 USDC。意图为 epoch=7、nonce=42、deadline=T0+120 秒，1000 USDC 至少得到 0.49 WETH，recipient=A；任何 Relayer 都可转发，不部分成交，X 不可升级。

## 第 1 层：停掉自己的 Relayer 为什么不是撤销签名

**面试官：** A 签名以后后悔了，调用取消 API，再让你的 Go 服务停止提交，能保证不成交吗？

**面试者：** 不能。取消 API 只能控制我们自己的任务队列，签名可能已经被广播、进入其他人的队列或交给另一个 Relayer；密码学签名不会因为删数据库失效。基线允许任何人转发同一意图，因此真正撤销必须让 X 的权威状态不再接受它。A 可以自己发 cancelNonce(7,42) 取消这个键，或提高 currentEpoch 批量作废旧 epoch；期限到了也会阻止以后执行，但三者都不能逆转已经成功的兑换。产品应把“已提出取消”和“链上取消已确认”区分开，不能在 API 返回时就承诺一定不会成交。

## 第 2 层：单笔取消怎样防止别人替用户作废权限

**面试官：** 你说调用 cancelNonce，既然任何人都能转发兑换，是否任何人也能替 A 把 42 取消？

**面试者：** 不可以，转发权不等于撤销权。基线取消入口是 A 自己发送的 `cancelNonce(epoch,nonce)`，owner 从 msg.sender 确定，要求传入 epoch 等于该 owner 的 currentEpoch，并把同一个 used/cancelled 不可用位设为终态。B 调用 cancelNonce(7,42) 只能影响 B 的键，不能影响 A。执行和取消必须访问同一消费位，不能各用一份独立布尔值而遗漏互查。我会在已经不可用时不再写状态或产生 Cancelled，返回 AlreadyUnavailable 而不 revert，与总览 MVP 一致；这不是声称重新取消了一次成交；若需让第三方代取消，就必须另定义受限取消签名和防重放规则，那不是当前基线的能力。

## 第 3 层：执行和取消同时在链上排队怎样裁决

**面试官：** 入口权限清楚了，但 A 的取消交易和 R 的兑换交易同时待打包，哪个结果合法？

**面试者：** 以规范链上的执行顺序和是否成功提交为准，不以 API 时间或广播先后为准。取消先成功写入不可用位，后来的兑换必须拒绝，A 保持 1500 USDC、0 WETH，allowance 仍是此前的 1000 USDC。若兑换先成功，A 变为 500 USDC、0.50 WETH、allowance=0，后来的取消不能把它恢复，也不能返回“已阻止成交”。如果先执行的那笔交易 revert，则它没有提交这次状态变化，后来的有效操作仍有机会成功。因此不能只说“先打包者胜”，而要说“先成功改变该权限状态者决定结果”，两笔失败交易仍可能各自产生 Gas 成本。

## 第 4 层：兑换中途标记 used 后，取消有没有插入窗口

**面试官：** 你强调先成功提交，假如兑换已经设置 used，却在输出校验前失败，取消会不会看到一个半完成状态？

**面试者：** 独立交易不会插入另一笔 EVM 事务的中间，链上取消只能看到兑换提交后的状态。X 在 nonReentrant 入口里先完成检查与验签，再于外部调用前标记 used；这是为了阻断本笔外部调用里的重入，而不是提前宣布业务成功。若最终实际输出只有 0.48 WETH，整笔兑换必须 revert，used、transferFrom、allowance 消耗、路线状态和本次事件一并回滚。随后执行的取消仍可成功。原先独立 approve 不是这次事务的一部分，不会被恢复成 0。不能把 used 拆成一笔提前上链的“占位交易”，否则失败兑换会留下权限被消耗却没有成交的结果，已经违背基线。

## 第 5 层：deadline 相等、过期与已成交分别怎样判断

**面试官：** 若取消还没确认，deadline 先到了，是不是系统就可以直接把这份意图标记为“已撤销”？

**面试者：** 不能把过期和取消混成同一种事实。X 按执行区块的 block.timestamp 检查 `timestamp <= deadline`，相等仍允许执行，只有大于 deadline 才过期；本地时钟、RPC 到达时间和进入内存池的时间都不裁决。deadline 以前已成功的兑换，不会因为当前时间后来超过期限而变成未成交或撤销。过期本身也不写 used，不撤销已存在的 allowance。索引器应先查已有的执行、取消和 epoch 证据，再对仍无成功结果的意图标记“当前已过期”；尚未最终确认时还要保留重组可能，不能按墙上时钟覆盖链上已发生的成功。

## 第 6 层：批量撤销为何使用单调 epoch

**面试官：** 如果 A 有上百份未过期签名，逐个取消太贵，你怎样批量失效，又不让旧签名以后复活？

**面试者：** A 自己发送 raiseEpoch(newEpoch)，X 要求 newEpoch 严格大于当前值，例如把 7 提高到 8。执行入口要求意图 epoch 与当前 epoch 完全相等，所以全部 epoch=7 的旧签名都不再能执行，不需要遍历 nonce。不能允许降回 7，也不能清空旧 used 位后重新使用旧 epoch，否则未过期签名可能复活。新 epoch 可重新用数字 42，因为唯一键已改变；但若 A 事先签过 epoch=8 的未来意图，提高到 8 可能令它生效，不能把提高 epoch 说成“销毁所有已签数据”。单笔 cancelNonce 只接受当前 epoch，旧 epoch 的权限已整体失效，无需补做逐个取消。

## 第 7 层：提高 Gas 或取消 Go context 能否赢得竞争

**面试官：** 既然 raiseEpoch 也要上链，A 想更快撤销，提高费用、替换交易或取消 Go context，能保证胜过 R 吗？

**面试者：** 都不能保证。A 的取消或 raiseEpoch 使用 `(chainId,A)` 范围的 EOA 交易 nonce，R 的兑换使用 `(chainId,R)` 的交易 nonce，两组独立，A 无法用相同 nonce 的交易替换 R。A 自己更早的待处理交易还可能阻挡取消，高费用也不等于确定先执行。同一发送者、同一交易 nonce 的替换需要显式签署新载荷，旧签名不会消失，不能把费用策略当作撤销协议。Go context 只影响本地等待和调用，已交给签名服务或网络的请求可能继续产生结果；收到超时应按原任务恢复观察，而不是返回“已停止，所以链上不可能执行”。

## 第 8 层：撤销 intent、撤销 allowance 和更换密钥有什么区别

**面试官：** 如果不能保证取消先到，A 直接把 allowance 改为 0，或者换一个新钱包地址，是不是更彻底？

**面试者：** approve(X,0) 先成功后，可以让需要拉取 USDC 的后续执行因授权不足而失败，但它不是消灭旧意图：日后 A 再给 X 足够 allowance，旧签名若未过期、未消费且 epoch 仍有效，仍可能执行。它也会影响 A 在 X 上其他需要该授权的业务。反过来，cancelNonce 或 raiseEpoch 不修改 Token 的 allowance，旧授权仍留在 Token。普通 EOA 没有在原地址内任意换公钥的操作，改用新地址不会让旧 A 的签名失效；更换 R 的 Gas 密钥也无关。紧急处置必须分别处理业务意图资格和资产授权，并承认每笔链上操作都与既有执行竞争。

## 第 9 层：取消状态怎样向用户表达而不作假承诺

**面试官：** 这些操作都可能输掉竞争，你会怎样设计接口和数据库，避免前端同时显示“已取消”和“已成交”？

**面试者：** 我把用户请求、取消交易和意图观察分开记录：取消请求已受理只是本地事实；签名或广播未知、待确认、取消成功、执行成功、epoch 失效、过期则对应不同证据。同一意图键保存规范化 digest，取消任务绑定不可变参数和交易身份。收到超时不重新生成另一份意图，重复请求关联原取消任务；如果已经查到成功执行，就回答“取消未阻止本次执行”，不把最后到达的 API 响应覆盖事实。若 used 共用一个位，还要关联成功回执和事件区分消费原因；仅查 used=true 不足以推断取消成功。业务页面可以表达正在竞争，但不能人为挑一个更悦耳的终态。

## 第 10 层：取消回执成功后遇到重组怎样恢复

**面试官：** 如果前端已经看到取消交易成功，随后它所在区块被重组移除，怎样恢复，才不会把旧签名重新暴露的风险藏起来？

**面试者：** 取消成功先记为带区块哈希的观察结果，达到约定确认要求后再给较强的完成承诺。发现原区块不在规范链上，要撤回该区块贡献的投影，重查 X 的 currentEpoch、used、期限和相关交易回执；原取消可能重新打包，也可能被另一笔执行抢先。如果新链上权限仍有效，就明确恢复为“取消未确认，仍可能执行”，而不是坚持数据库里的已取消。相同道理适用于先前观察到的成交：重组移除其状态后，不能仅凭旧事件继续认定 nonce 已永久消费。审计记录保留分叉观察与修正原因，当前业务裁决始终依据规范链证据，而非最后收到的消息时间。

## 本题收束

- **讲透的机制：** 取消是 A 对 X 权威状态的操作，与执行共享同一权限终态；deadline 是执行时谓词，epoch 是单调批量失效屏障，三者不替代 Token allowance 管理。
- **最易答错的边界：** API 取消、停 Relayer、删数据库、取消 context、提高 Gas、更换钱包或 R 密钥，都不直接撤销已经外流的签名。到期相等仍可执行，已经成功的兑换不能被后来的取消逆转。
- **检验反例：** A 先在 API 点取消，R 的兑换先上链成功，A 的 cancelNonce 后上链返回 AlreadyUnavailable、没有产生 Cancelled。正确结果是成交成功、取消未阻止执行、A 有 500 USDC 与 0.50 WETH；若系统仍显示“已取消且未扣款”，就是把本地意愿误当作链上事实。本题仅手工推演，没有执行工程测试。
