# 大问题 7：签名者是合约钱包或受委托密钥时，怎样判断它真的有权执行这笔兑换？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EOA / recover | 私钥控制的普通账户、从摘要签名恢复签署地址。 | 适用于基线 A，不能用恢复出的管理员地址冒充合约钱包 W。 |
| W / owner / recipient | 合约钱包、资产与意图的所有者、输出收款人。 | 扩展把 owner 和 recipient 换为 W，须独立建立 W 的资产、授权和 epoch。 |
| ERC-1271 / isValidSignature | 合约钱包验签规范、向钱包查询是否认可摘要的接口。 | 由已部署 W 按自身当前策略裁决，不是查一把所谓 W 私钥。 |
| 0x1626ba7e / magic | 标准规定的有效返回值。 | 严格解码并检查；空返回、错误值、revert 或资源耗尽不能当通过。 |
| digest / 签名载荷 | 业务摘要、钱包所需的证明材料。 | X 向意图声明的 W 验证，不能让请求方随意另选一个验证器。 |
| staticcall / 只读 | 不允许通过该调用修改链上状态的执行方式。 | 1271 验签不在这里扣累计额度，也不能借验证函数写状态。 |
| hasCode / 账户能力 | 地址是否有代码、明确支持哪类验证方式。 | 只在限定集合内分流，不把所有现实账户永久二分。 |
| ERC-6492 / EIP-7702 | 反事实签名验证相关标准、EOA 委托代码相关机制。 | 都会改变能力假设，本篇不因支持 1271 就自动支持它们。 |
| 多签阈值 / 模块 | 达标需多少批准者、钱包可启停的功能。 | 历史验证通过可能因阈值或模块状态变化而失效，不能永久缓存。 |
| D / 委托范围 | 临时签名密钥、它被允许做的有限动作。 | 成员白名单不够，还要限制链、目标、资产、金额、收款人、路线和期限。 |
| 结构化证明 / 重算摘要 | 可核对的业务字段及证据、由它们重建 digest。 | 模块不能相信一份没有与签名绑定的“已解析金额”。 |
| 单笔上限 / 累计预算 | 每次最多花多少、多次合计最多花多少。 | 只读验签可检查单笔限制，不能独自完成多笔预算的原子消费。 |
| nonce / epoch / used | 一次性编号、权限代次、不可用状态。 | 归属是 X 中 W 的键，不是 D 或某个多签成员的键。 |
| allowance / msg.sender | Token 的使用额度、X 实际看到的调用者。 | 应有 W 给 X 的授权；取消也须由 W 的流程调用，让 X 看到 W。 |
| 执行时验签 / 区块快照 | 真正兑换时再裁决、预检所对应的历史状态。 | Go 的旧块有效结论不能覆盖先执行的模块撤销。 |
| 原子执行 / minAmountOut | 兑换相关变化共同提交、最低实际输出。 | 所有条件仍须满足，0.49 WETH 是下限，0.50 不是验签带来的保证。 |

## 把整篇文章压缩成一个故事

**起因：** 小林原本用普通 A 签 1000 USDC 换至少 0.49 WETH，现在明确改用已部署的合约钱包 W，owner 和 recipient 都变成 W。W 必须另有自己的余额、给 X 的 allowance 和有效 epoch，不能继承小林个人 A 的权限；X 也须从部署时就具备这项验证能力。后端恢复出小林某个成员密钥，并不能说明已经满足 W 的多签或委托规则。

**处理及异常：** Go 在明确区块向 W 查询 digest 的 ERC-1271 有效性，X 执行时再以只读方式查询并检查 0x1626ba7e。假设昨天 D 模块有效、今天关闭模块的交易先成功，今天兑换就应拒绝，不能靠昨天的缓存放行；若兑换先成功，后来的关闭也不能追溯撤销。若 D 被允许单笔最多 1000 USDC，两份不同 nonce 的意图可能都通过只读验签，不能据此声称两笔合计仍最多 1000，累计预算需要另设能与执行原子扣减的路径。

**结果及边界：** 返回正确 magic 只说明 W 此刻认可摘要，X 仍检查期限、epoch、nonce、路线和 Token 资金条件，实际输出至少 0.49 WETH 才可提交，0.50 只是样例。若 W 没有 allowance，整笔失败且 used 回滚；取消 W 的权限也须由 W 的授权流程发起，成员个人直接调用不能替代。登录成功、支持 1271、支持细粒度委托与支持所有现实账户类型，是不同能力，本篇没有把它们混成一张万能授权证书。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于 X 接收意图后的身份与权限验证环节，区分 EOA 密钥恢复、ERC-1271 钱包决策以及委托范围。重点是“哪个地址是资产所有者、谁有权代表它、哪一时刻的权限状态有效”，不把钱包登录或 Token 授权混成验签结果。

**沿用基线与扩展边界：** 基线是 `chainId=1` 上的普通 EOA A，资产为 1500 USDC、0 WETH，已独立授权不可升级的 X 恰好 1000 USDC。意图字段固定为 `owner、tokenIn、tokenOut、amountIn、minAmountOut、recipient、nonce、epoch、deadline、routeHash`，域为 `OneTrade / 1 / X`，`nonce=42、epoch=7、deadline=T0+120秒`，截止时刻相等允许。基线花 1000 USDC，至少收 0.49 WETH，示例收 0.50 WETH，收款人为 A。合约钱包扩展另以 W 为资产 owner 与 recipient，并独立建立 W 的余额、授权和 epoch 状态，不继承 A 的状态；仅讨论已经部署的 ERC-1271 钱包。X 的该能力必须在部署时就被实现，不可升级不等于可以事后加入口。

## 第 1 层：为什么 recover 到一个地址仍不够

**面试官：** 如果把普通 EOA A 换成合约钱包 W，我们继续 recover 签名，然后要求恢复地址等于 owner，不就能复用同一套验签了吗？

**面试者：** 不能。普通 EOA 的参考路径是对精确的 EIP-712 digest 做 secp256k1 验证，恢复地址必须等于 A，并处理 low-s、v 适配和非法值。合约钱包 W 没有一个可以按同样方法恢复出的“W 私钥地址”；它可能由多签成员、模块或受限密钥控制。已部署 ERC-1271 钱包扩展应把原始 digest 与钱包所需签名载荷传给 W 的 `isValidSignature(bytes32,bytes)`，由 W 判断当前权限，要求返回 `0x1626ba7e`。recover 到某个管理员，只能证明该密钥签过，不能证明它达到 W 的阈值，更不能代替 W 自己的权限裁决。

## 第 2 层：支持 1271 需要怎样的调用边界

**面试官：** 你把权限裁决交给了 W。那 X 只要发现 owner 地址有代码就调用 1271，没有代码就 recover，这个实现能覆盖所有钱包吗？

**面试者：** 在本题限定的“普通 EOA 或已部署 1271 钱包”集合内可以明确选择相应路径，但不能把代码有无当成所有现实账户的天然身份分类。未部署钱包需要额外的反事实验证能力，例如 ERC-6492；EIP-7702 下带委托代码的 EOA 又改变了原先假设，本题不自动支持。1271 路径应使用只读调用，限制可接受的调用资源并严格解码返回值；空返回、错误 magic、格式不合法、revert 或调用耗尽资源都按失败处理，不能失败后再尝试猜测消息前缀。X 始终向意图声明的 W 查询，不接受请求方另传一个“同意签名”的验证器地址来冒充 owner。

## 第 3 层：为什么一次验证通过不能永久缓存

**面试官：** 上一答已经选中了正确的 W，并检查了 magic。Go 服务把“这份签名有效”缓存一天，后面直接复用，为什么仍不可靠？

**面试者：** ERC-1271 的有效性可以依赖钱包当前状态，例如多签阈值、成员集合、模块启停、会话密钥额度和撤销状态，也可能依赖链上时间或其他合约。今天返回 magic 不代表明天仍返回，所以缓存不能只以 signature bytes 为键并当成永久授权。Go 预检应绑定 chainId、W、digest 和明确的区块号或区块哈希，记录使用的节点和结果；区块标签必须能对应到具体历史状态，不能把模糊的 pending 结果说成确定事实。真正执行时 X 还要再次调用 W。预检帮助筛除明显失败请求，链上执行时的权限裁决才决定这笔兑换能否进行。

## 第 4 层：执行时再验能覆盖哪些竞态

**面试官：** 你说执行时再调用 W。若预检后管理员撤销模块，或者 W 在验证中尝试改状态、重入 X，资金和 nonce 会不会先动起来？

**面试者：** 若撤销交易在链上先执行，X 随后的验证就应该看到新状态并拒绝；若合法兑换先执行，后来的撤销不能追溯抹掉已完成的结果。一次事务内先后顺序由 EVM 执行决定，不是由 Go 的预检时间决定。X 在重入保护下完成域、字段、期限、epoch、used 和钱包验证，1271 使用静态调用，不能靠验证函数写状态；通过后在任何可改变资金的外部调用前标记 used，再做受控兑换。输出不足就连同 used 和资金变化整体回滚。执行时验证不是“把有效性永久冻结”，它只裁决本次检查点；复杂钱包若在后续调用中改变内部状态，必须明确自己的策略语义，不能靠历史预检补救。

## 第 5 层：委托签名需要证明哪些具体权限

**面试官：** 你提到了模块和会话密钥。若 W 允许临时密钥 D 签名，只要 recover 出 D 且 D 在白名单里，就可以代表 W 花这 1000 USDC 吗？

**面试者：** 不能只检查成员关系，还要验证授权范围。扩展的钱包策略应限制 D 的链、执行合约、可签动作、资产、金额、recipient、路线、有效期和撤销版本，必要时还有累计额度。1271 只有 digest 和签名载荷，并不会天然读懂 SwapIntent；若模块要检查语义，载荷必须携带可验证的结构化字段或授权证明，模块重算同一 digest 并核对限制，不能相信调用者另附的一份未绑定“解析结果”。X 的字段 schema 不因此暗中增加 executor 或委托字段；委托证明属于 W 的验证规则。如果原 W 没有这种模块，就不能把“支持 1271”说成已经具备细粒度委托能力。

## 第 6 层：只读验签为什么不能自己消费额度

**面试官：** 上一答要求 D 的累计额度也受限，但 1271 是静态调用。如果 D 连续签两笔各 1000 USDC，钱包如何靠 isValidSignature 阻止总额超过 1000？

**面试者：** 单靠只读验签不能消费累计预算。两个不同意图都可能在同一旧预算下验证通过；X 的一次性 nonce 只阻止同键重放，并不替钱包维护 D 的总额度。要限制累计支出，必须显式增加具有原子预算消费能力的执行路径，例如钱包模块在受控执行入口中扣减预算并调用 X，且失败时预算与兑换一起回滚；这改变了扩展架构，不能声称现有 X 加一次 1271 查询就能做到。若不改执行路径，只能承诺可由静态规则验证的单笔上限、期限等限制，或另设计确实一次性且能被执行层原子消费的授权机制，不能把单笔权限包装成总额保证。

## 第 7 层：资产授权和意图撤销怎样落到钱包 owner

**面试官：** 你把累计额度排除在普通 1271 能力之外。那不改 X 时，W 能否至少复用 A 的 allowance 和 cancelNonce 来撤销 D 签出的意图？

**面试者：** A 的状态不能搬给 W。扩展中 Token 必须记录 `allowance[W][X]`，资产也应由 W 持有；多签成员个人的 approve 不会授权扣 W 的钱。意图唯一键对应 `(chainId,X,W,epoch,nonce)`，不是某个成员或 D 的地址。X 的 cancelNonce 要求调用者是 owner，因此应由 W 通过自身授权的执行流程调用 X，使 X 看到 `msg.sender=W`；成员直接发交易给 X 不满足条件。提高 W 的 epoch 可以按协议规则批量失效旧意图，关闭 D 模块则影响后续 1271 判断，两者仍与取消执行竞争。更换成员密钥也不必然使所有旧签名无效，要看 W 当前实现是否仍接受那些证明。

## 第 8 层：怎样检验没有把钱包能力与业务授权混淆

**面试官：** 上一答区分了钱包撤销和 X 的撤销。若一份签名在最新状态下返回了正确 magic，是否就能向用户保证会收到 0.50 WETH？

**面试者：** 仍然不能。magic 只表示 W 在当前检查条件下认可该 digest，不代表 Token 余额、allowance、X 的 epoch、nonce、deadline 或池内价格都满足。X 还要完整执行全部业务约束，最终至少得到 0.49 WETH；0.50 只是贯穿示例，不能变成保证成交量。可手工推演三组反例：预检通过后模块先撤销，执行时应拒绝；magic 正确但 W 未 approve，扣款应失败且 used 回滚；钱包认可原意图而有人修改 recipient，digest 改变后不得复用原证明。SIWE 登录验证成功也只说明登录身份，不会补齐这些交易权限。这里列的是检查方法，不声称已经对某个真实钱包做过兼容性测试。

## 本题收束

- **讲透的机制：** EOA 验证密钥对 digest 的签名，1271 由已部署钱包依据当前状态裁决；合约钱包 owner、钱包成员与委托密钥不是同一个地址角色。
- **最易答错的边界：** `0x1626ba7e` 不是永久证书，也不是 Token 授权；1271 静态验证不能独自原子消费累计预算；未部署钱包与 EIP-7702 不能被简单的 hasCode 二分覆盖。
- **检验反例：** 缓存显示 D 昨日有效，钱包今日已关闭 D 模块。如果执行仍靠昨日缓存放行，方案把历史身份结论误当成了当前权限事实。若所有检查通过但余额不足，也必须允许兑换整体失败，而不是伪造成功结果。
