# 大问题 4：怎样理解 EIP-1559 费用，并让 Gas 预算覆盖并发、替换与失败？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| W1 / H / T / U | 提现意图、付款钱包、代币和用户。 | 向外部地址 B 付 100 T，网络费由平台 H 的 ETH 承担。 |
| EIP-1559 / type 2 | 区分基础费、小费和最高单价的交易费规则。 | 本题只用以太坊主网普通交易，不包含桥、二层或 Blob 费用。 |
| maxFee / feeCap | 每单位执行工作量允许支付的总单价上限。 | 40 gwei 是上限，不是一定扣 40；低于区块 baseFee 时不能在该块执行。 |
| priority / tipCap / baseFee | 优先费上限和区块基础费。 | baseFee=30 时有效小费为 2；baseFee=39 时受总价上限挤压只剩 1。 |
| gwei / wei / ETH | 原生币的不同计价单位。 | 1 gwei=10^9 wei，1 ETH=10^18 wei；工作量乘单价才是费用。 |
| gasLimit / estimate / gasUsed | 批准工作量上限、模拟估算及实际消耗。 | 65000、52000、50000 各有含义，不能互相代替。 |
| effectiveGasPrice / 预算 | 执行有效单价，以及内部保留的最坏费用容量。 | 主例实付 0.0016 ETH，预算 0.0026 ETH；差额不是用户收入。 |
| revert / out-of-gas | 合约主动回滚及执行工作量耗尽。 | 已执行失败仍耗费用和 nonce，失败支出按自己的回执算。 |
| nonce_slot / 同槽最大需求 | 一个执行序号及其互斥候选的最坏资源需要。 | X1、加速 X2、取消 Xc 只能同槽竞争，费用取各完整乘积的最大值。 |
| 不同槽求和 / maxPending | 可先后执行的交易预算相加，以及限制未终结槽数量。 | 槽 43 与 42 都可能花钱，不能按互斥候选只留一份。 |
| replacement / price bump | 节点接受替换交易的规则与涨价门槛。 | 是客户端和配置策略，不是共识规定提高固定百分比必成功。 |
| draft / signer / raw | 授权草稿、签名出口及已签交易原字节。 | X2 提费先补预算再批签；签名超时仍可能已有执行能力。 |
| 同水位 / finalized | 按相同区块进度核算，以及共识最终链进度。 | 新余额反映支出时同步核销预留，避免提前放开或重复扣同一支出。 |
| receipt / blockHash / 重组 | 执行回执、具体块身份及规范分支变化。 | 跨分支临时费用不能相加为最终账单，最终获胜者才决定本次成本。 |

## 把整篇文章压缩成一个故事

小林提 100 T，平台批准的钱包预算是 65000×40 gwei，即 0.0026 ETH。真实入块基础费为 30、优先费上限为 2，有效单价才是 32；用了 50000 gas 就付 0.0016 ETH，没花掉的 0.001 ETH 只是恢复平台可调度容量。若基础费改成 45，原交易不能进该块，并不是已经执行失败、该收一笔失败费用。

付款迟迟未入块，平台申请同 nonce 的 X2，把费率改成 50/3 gwei，并按目标节点策略检查接纳条件。它先把槽预算升至 0.00325 ETH，补 0.00065 ETH 后再签名，不把 X1、X2 两份预算相加；另一个 nonce 的提现则必须另外留钱。取消候选出现，也不能撤掉仍可能执行的原付款容量。

若 X2 曾在旧分叉入块，最终却由 X1 获胜，账单只按最终规范链胜出者核算。若最终是回滚或取消，就依据其实际回执记费用，并在未付款证据成立后释放用户冻结。故事把费用有效、节点愿收、预算足够和实际支出分开：能覆盖受控最坏需求，不等于能保证低价、固定时间成交或失败免费。

**流程位置与核心机制：** 本题覆盖“费用报价 → Gas 上限与资金准入 → 同槽加速和取消 → 实际费用结账”。重点是区块费用有效性、节点替换策略、钱包预算和真实支出四种不同约束，不把预测价格当作执行承诺。

**必要前提：** 沿用[专题总览](README.md)的 Ethereum PoS L1、type 2、独占无委托普通 EOA H 与标准 ERC20 T 基线，不引入 AA、7702、L2 或桥。沿用 W1 向 B 提现 100 T、PostgreSQL 本地事实源与平台承担 gas 的规则；完整初始余额和费用参数见总览，本文数字均为教学假设而非实测。

## 第 1 层：费用上限、有效单价和实际支出是三个数

**面试官：** type 2 交易设置 maxFee 40 gwei、priority 2 gwei，为什么实际不一定按 40 gwei 收费？

**面试者：** maxFee 是每单位 gas 愿意支付的总价上限，不是承诺一定支付的价格；priority 是每单位 gas 的小费上限，也不是总费用。在费用有效且能够进入的区块里，有效单价是 `min(maxFee,baseFee+priority)`。主例的 baseFee 为 30 gwei，因此有效单价是 32 gwei，其中 30 gwei 对应基础费，2 gwei 对应优先费。

实际总费用还要乘实际 gasUsed，而不是 gasLimit。本例是 `50000 × 32 gwei = 0.0016 ETH`；最坏预算则是 `65000 × 40 gwei = 0.0026 ETH`。预算与实际相差 0.001 ETH，表示这部分预留容量没有消耗，不是链上另外产生一笔给 U 的退款，也不能把 gasLimit 与 gasUsed 的差额当成代币收入。

W1 的 value 为零，只说明这笔交易不向 T 转原生 ETH，不代表交易免费。H 用自己的 ETH 支付 gas，T 的 100 T 从 H 转给 B，U 的冻结在最终付款确认后核销；平台费用账和用户提现账分别处理，不能把 gas 从 100 T 中暗扣。

## 第 2 层：费用有效性先于打包优先级

**面试官：** 你说有效单价取最小值。如果下一块 baseFee 涨到 45 gwei，能不能仍以 40 gwei 执行，只是不给小费？

**面试者：** 不能。`maxFee=40 < baseFee=45` 时，这笔交易不满足该区块的费用有效性条件，不能被合法纳入该区块；不存在“按 40 执行，再让验证者少收一些”的分支。这个状态不是 receipt.status 为 0，因为交易还没有在该块执行，不能给它记一次执行失败费用。节点可能暂存或拒收，具体取决于节点的池策略，但不改变该区块不能包含它的约束。

如果 baseFee 是 39 gwei，则交易仍满足费用条件，有效单价为 40 gwei，实际小费只有 `min(2,40-39)=1 gwei`。因此提高 maxFee 能为基础费上涨留空间，却不必然提高实际小费；在主例 baseFee 为 30 时，只提高 maxFee 而不提高 priority，有效小费仍可能保持 2。还要检查 `maxFee >= priority` 等字段有效性，不能把不合法费用参数交给广播节点碰运气。

这说明“费用有效”“某节点愿意接收”“构建者最终选择打包”是三件事。报价器可以参考历史费用、当前 baseFee 与目标等待时间，但不能承诺下一块一定打包。暂时低于 baseFee 也不意味着 raw 永久失效，未来基础费降低后它仍可能被执行，不能据此回收 nonce 或释放付款冻结。

## 第 3 层：Gas 估算不能替代执行上限和失败计费

**面试官：** 基础费上涨不等于执行失败。那么 estimate 52000、gasLimit 65000 能保证不失败吗，失败后还会扣费吗？

**面试者：** 不能保证。estimate 是节点针对某个输入与状态给出的估算，65000 是我们批准并签入交易的执行上限；估算证据应保存完整调用参数、区块号与哈希、节点来源，不能把默认 latest 的结果描述成固定状态下的证明。选择余量是受控预算策略，不能覆盖错误 calldata、余额变化或所有未来状态差异，签名以后也不能原地增加这笔 raw 的 gasLimit。

交易一旦被纳入并执行，revert 或 out-of-gas 仍会消耗 gas，而且 nonce 被消耗。执行效果的回滚不回滚 gas 支出；执行顶层 out-of-gas 通常耗尽给定 gasLimit，普通 revert 则按回执中实际 gasUsed 计费，不能把所有失败都机械记为 65000。没有被纳入的拒收、费用不满足或 RPC 超时，则不能凭错误消息推算一笔链上手续费。

主例的实际 50000 仅用于成功路径。失败变体必须用它自己的 receipt 和 effectiveGasPrice，不能照抄 0.0016 ETH。用户可以在有最终未付款依据后取回冻结的 100 T，而平台仍承担这次失败的真实 gas；“用户没拿到代币”和“平台没花钱”不是同义词。

## 第 4 层：预算按不同槽求和、同槽最坏需求计算

**面试官：** 失败也可能耗 gas。H 有 1 ETH，多个提现和同 nonce 的替换交易并发时，怎样确保最坏费用始终有覆盖？

**面试者：** 我会把预算绑定 nonce 槽，而不是只绑定当前选中的 hash。对一个槽 s，gas 预算是该槽仍可能执行的已授权候选中 `gasLimit_i × maxFee_i` 的最大值；不同槽的预算相加。这里取每份候选完整费用乘积的最大值，不是把各候选费用简单相加，也不是从不同候选分别取最高 gasLimit 和最高 maxFee 后混成一笔并不存在的交易。T 的预留也保留该槽尚可能发生的最大付款义务，创建取消候选并不释放旧付款的 100 T。

PostgreSQL 事务先锁 H 的钱包行，检查用户意图资格、T 库存、ETH 容量和 maxPending 小窗口，再原子提交槽位、意图绑定、100 T 与 0.0026 ETH 预留以及 nextNonce 推进。如果独立增加 W2 使用槽 43，它有自己的代币需求和 gas 预算，必须与槽 42 相加。`PendingNonceAt` 既不能替代本地发号，也不能证明这些未决承诺的预算已经得到覆盖。

余额与预留必须使用同一核销水位。一种保守实现是以已核验 finalized 区块 F 的余额为基线，对 F 之后所有未终结槽继续计入最坏预留；临时入块不先释放预算，推进 F 时再将已最终交易的实际支出纳入新余额并终结相应预留。不能一边使用已经扣过 X1 实际 gas 的 latest 余额，一边把它当作从未支出的旧余额再扣全部预留；也不能提前撤掉预留而余额水位仍停在旧块。水位、观察身份与核销进度都要持久化。

## 第 5 层：加速必须同时满足节点策略与预算准入

**面试官：** 预算按槽管理了，那把 X1 的 maxFee 从 40 调到 50 gwei、priority 仍为 2，就一定能替换吗？

**面试者：** 不一定，替换门槛是节点交易池策略，不是以太坊共识规定的固定百分比。以已核验的 Geth v1.16.5 普通交易池策略为例，新的 feeCap 和 tipCap 都要严格增加，并分别满足配置的价格 bump 门槛；只提高 feeCap、tipCap 不变可能被判为 replacement underpriced。不同客户端、配置及入口策略可能不同，不能把某个节点的默认 10% 说成全网统一规则，节点接受也不保证全网都已替换。

如果教学变体把 X2 设为 maxFee 50、priority 3 gwei，仍应依据目标节点策略与当前链环境验证，不能仅凭这两个数承诺接收。X2 保持 `chainId=1,sender=H,nonce=42,to=T,value=0,data=transfer(B,100000000)`，gasLimit 仍为 65000，所有非费用字段都不变，新的费用参数须形成独立审批 draft；改变执行上限属于另述变体，不是这里的 X2。X1 的记录和 raw 不删除，因为它仍可能被其他节点保留并最终获胜。

若 X2 仍采用 gasLimit 65000，其最坏预算为 0.00325 ETH，槽 42 的预留从 0.0026 增至 0.00325 ETH，须先补准入差额 0.00065 ETH，再请求签名。不能等签完才发现差额已被槽 43 用掉，也不能把 X1 与 X2 相加为 0.00585 ETH。同槽 Xc 取消也有自己的 gas 上限、费用与独立授权，更新后的槽预算必须覆盖包括原付款在内的全部未失效候选。

## 第 6 层：签名或广播未知时，预算不能随超时释放

**面试官：** 你要求先补预算。补完以后 signer 或广播超时，预算会不会一直占着？为了恢复吞吐能先退回再重发吗？

**面试者：** 不能因为超时就退回。签名调用与数据库事务不是一个原子操作，所以必须先提交授权 draft 和 signer request，再调用支持按 draft 幂等查询、恢复的签名出口；返回后恢复 sender 并核验所有字段，耐久持久 raw/hash 与 attempt，再提交可消费的广播任务。raw 是可执行能力，不写日志。广播重试使用完全相同的 raw，不能生成新 nonce 交易来“恢复”W1。

signer 超时可能已经签出交易，广播超时可能已经传播交易；节点暂时查无记录也不是从未执行的证明。此时原槽、100 T 钱包预留和最高已授权 gas 预算保持，追踪 X1、X2、Xc 全部候选，按原身份查询恢复。不能只把某一 attempt 标成发送失败，就撤掉同槽中仍可能执行的最大预算。

占用过久是活性问题，需要对最早阻塞 nonce 提升查询与补扫优先级，按预算政策申请加速或独立取消，而不是破坏安全边界。设置总费用上限、maxPending、退避和人工升级，可以限制积压；这些措施只约束新的受控行动，不能使已签旧 raw 失效，也不能把预算过期当作链上交易过期。

## 第 7 层：最终回执才决定实际支出与用户处理

**面试官：** 假设追踪到了回执。究竟何时核销预算，X1 成功、执行失败和 Xc 获胜分别怎么记？

**面试者：** 我会保存回执所属的 txHash、blockHash、规范链关系和最终性证据，先作为可撤销的入块观察，再等所在区块进入已核验 finalized 前缀。最终结账事务检查槽位与意图版本，用唯一结算身份原子写入用户账本、平台 gas 成本、预算核销、W1 终态与 outbox；重复处理同一个最终事实不能再扣一次用户冻结或再记一笔费用。

主例若付款 X1 最终获胜、执行成功且付款证据吻合，实际支出 0.0016 ETH，H 剩余 9900 T 和 0.9984 ETH；U 的冻结 100 T 被核销、可用保持 900 T，平台承担 gas。槽原预留 0.0026 ETH 不再占用，其中未耗的 0.001 ETH 只是恢复平台钱包可调度容量。不能先把 0.0026 ETH 当成实际成本，再补记 0.0016 ETH，造成重复支出。

如果付款执行失败，或独立授权的 Xc 最终占据 nonce 42，则用实际胜出交易的回执计算 gas，确认原付款未完成后把 U 恢复为可用 1000 T、冻结 0。Xc 的 `operationKind=CANCEL`，同 nonce 自转 0 ETH 的 status 为 1 只说明取消交易执行成功，绝不等于 W1 给 B 付了 100 T。回执与交易载荷不匹配时隔离核查，不能自动退款或冒认成功。

## 第 8 层：重组与跨槽费用决定恢复边界

**面试官：** 如果 X2 曾经入块但被重组，后来 X1 又入块，费用与预算会不会按两笔相加？费用积压又怎样影响后续槽？

**面试者：** 不能把不同分叉上的临时费用都当作最终支出。普通 H 在同一规范链上 nonce 42 最多被一个交易消耗，但分叉 A 可以见到 X2，分叉 B 可以见到 X1，Xc 也可能在另一分支出现。应按 blockHash 保存各次观察，撤销离开规范链的临时状态，恢复对整个槽的追踪；只有最终规范链上的实际胜出者产生本次最终 gas 成本。未决期间仍按同槽最高可执行预算覆盖，不能因短暂看到较便宜候选就下调预留。

不同 nonce 则没有互斥保护，42 与 43 可以先后执行，两笔都要付 gas。低 nonce 因 feeCap 过低停住时，高 nonce 即使费率更高也不能越过缺口先消耗 H 的序号，因此调度要优先推进低序号，而不是只让新请求不断进入窗口。若已经签出的低序号候选难以恢复或链视图有冲突，冻结 H 的新分配并人工核对，比放宽预算掩盖未知状态更安全。

最终我能承诺的是：所有受控签名候选都有预算覆盖，实际费用有规范链回执依据，失败费用不转嫁给本模型中的 U。不能承诺费用预测准确、节点统一接收或在固定时间入块。数据库恢复时也必须重建余额水位、所有未终结槽的最大预算和 signer 审计，不能只读 H 当前 1 个余额再清空未决义务。

## 本题收束：机制、易错边界与反例验证

- **机制：** 先检验 feeCap 对目标区块是否有效，再区分有效单价与 gasUsed；预算按不同槽求和、同槽候选费用乘积取最大值，并在提费签名前原子补足。
- **易错边界：** feeCap 低于 baseFee 不能进入该块，不是一次链上执行失败；replacement 没有共识固定百分比；失败或取消仍可耗 gas；latest 余额与预留必须按同一水位核销。
- **反例验证：** 手工将 baseFee 改为 45 gwei，X1 应保持未执行而非记录 status=0；只提高 maxFee、tipCap 不变，不应承诺 Geth 接受替换；让 X2 预算增至 0.00325 ETH，槽预留只能增至该值而不是与 X1 相加；模拟一次失败回执，平台仍应记其实际 gas。以上为手工机制推演，不是工程测试。
