# 大问题 7：交易广播超时后，怎样在不重复付款的前提下恢复并查清结果？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| W1 / slot / X1 | 提现义务、钱包序号槽与首次签名候选。 | 向 B 付 100 T；slot 为链 1、H、42，超时不改变三者身份。 |
| PG / reservation / requestKey | PostgreSQL、本地预留及请求去重身份。 | 请求键绑定载荷摘要，受理和冻结共同提交；重启不再冻结一遍。 |
| draft / signingRequestId | 不可变审批草稿及可恢复签名请求号。 | 签名调用之前保存，响应丢失时靠原身份查结果。 |
| SIGNING_UNKNOWN / UNKNOWN | 不确定是否已签出，以及不确定发送结果。 | 两者都不能自动理解成失败或从未产出交易。 |
| signed raw / txHash | 已签交易原字节及其指纹。 | 在本地计算 hash，先持久原字节，再允许节点广播。 |
| broadcast_task / READY | 指向固定交易的持久发送任务及可消费状态。 | 与 attempt 同事务提交，进程崩溃后仍知道该发送什么。 |
| 至少一次 / 同字节重播 | 允许任务重复交付，并反复发送完全相同的交易。 | 重播不是新转账，不能在重试函数里改 nonce 或暗中提费。 |
| RPC / mempool / already known | 节点接口、局部交易池及已见交易回复。 | 某节点声称见过，只是传播证据，不是付款或入块证明。 |
| replacement underpriced | 节点认为新候选不够满足其替换涨价要求。 | 是局部策略判断，不能证明旧交易已成功或新交易永久无效。 |
| 租约 / owner / fencing | 临时任务归属、持有者及版本围栏。 | 挡旧 worker 越权改库，不能撤销它已拿到的有效 raw。 |
| nonce too low | 节点认为该发送者序号已经被越过。 | 还要查是付款、回滚、取消还是未知交易消耗，不能直接记成功。 |
| null receipt / pending nonce | 没有返回回执，以及节点对未决下一序号的估计。 | 查无不是失败，多个节点差异不能靠多数表决创造最终事实。 |
| inclusion / blockHash / 重组 | 入块观察、具体块身份及规范分支切换。 | 曾有回执又查空时要核对旧块与新链，不删除义务另起付款。 |
| Transfer / finalized / Outbox | 代币事件、最终链进度及同事务待发消息。 | 付款语义与最终祖先关系通过后，才一次终结账本并通知。 |

## 把整篇文章压缩成一个故事

平台替小林把 100 T 的 raw1 发给节点，节点可能已接收，响应却丢了。系统回答“执行中、发送结果未知”，保留可用 900、冻结 100 T。它有提前保存的 W1、nonce 42、签名请求和原始字节，所以重启后能找回同一个付款，而不是靠新交易试探到底能不能到账。

新 worker 重发原字节，旧 worker 租约过期后也可能迟到再发；只要是同一 raw，这仍是同一交易的重复传播。already known 不是入块，null 回执不是失败，nonce too low 也只提示要查谁用了 42。若登记的 hash 都解释不了，就补扫规范区块找实际载荷，发现未知 H 交易便隔离，不凭局部节点一句话结账。

最终查到准确付款、可信 T 的转账事件以及最终链祖先证据，平台才核销一次冻结并生成通知。中途若出现重组，就撤回临时观察、重查整个候选集合；等太久可暂停或审批同槽加速，不能换 nonce 43 再付。可靠广播的目标是副作用有身份、未知可恢复，不是把网络不确定性硬改成失败。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题承接交易构造与签名，讨论授权草稿、签名恢复、原始交易持久化、至少一次广播和未知结果追踪。重点不是“怎样更快入块”，而是越过签名与网络边界后，怎样始终围绕同一业务意图和 nonce 槽恢复，不把接口超时误判为交易失败。

网络、代币语义、资金与费用数值、完成策略统一沿用[总览公共基线](README.md)，所有推演均为教学设计。本题只固定恢复对象：W1、slot=(chain1,H,42) 以及首次 attempt X1/txHash1/raw1，超时不改变这些身份及原资金预留。

## 第 1 层：超时究竟留下了什么义务

**面试官：** W1 的 raw1 调用广播接口超时了，用户问提现是否失败，你怎样回答并处理？

**面试者：** 我会回答“广播结果未知，提现仍在处理中”，而不是失败。发送超时只说明调用方没拿到明确响应：请求可能没到节点，也可能节点已接收并向其他节点传播，甚至交易已经入块而响应丢失。HTTP 超时发生在哪一侧，不能改变已经签出的链上执行资格。

我会把 X1 的发送观察记为 UNKNOWN，保留 W1 与 slot=(chain1,H,42) 的绑定，继续冻结 U 的 100 T，可用余额仍是 900 T。后续处理包括查询 txHash1、查询规范链回执，以及在满足广播策略时重播同一个 raw1；不能因超时生成一笔 nonce=43 的同额付款，更不能直接释放冻结。

这里要区分三件事：PG 中可靠受理了 W1、某个节点见过 X1、链上完成了付款。第一件由业务事务证明，第二件只是传播证据，第三件还需要规范链执行证据和最终性。广播未知必须作为可恢复状态保存，不能压成成功或失败两个值。

## 第 2 层：未知状态依靠哪些持久身份恢复

**面试官：** 你说要恢复同一个 W1 和 nonce 槽，如果服务也重启了，怎样证明没有重新受理、重新分配 nonce？

**面试者：** 在这个模型中，PG 保存 intent、reservation、slot、draft、attempt、broadcast_task、inclusion_observation、ledger 和 outbox。用户请求先以作用域内的 requestKey 和 payloadDigest 检查幂等；首次受理在一个 PG 事务中创建业务意图 W1、冻结 100 T、登记 reservation 和受理流水。相同 requestKey、相同摘要重试时找回原 W1，不再冻结；相同键、不同摘要则冲突拒绝。requestKey 是请求幂等身份，W1 是服务创建的业务意图身份及后续结算关联，不能把二者混成客户端重试键。

分配 nonce 时锁定 chainId=1、钱包 H 的分配状态，再创建有唯一约束的 slot=(chain1,H,42)，把它绑定给 W1，并推进本地分配游标。初始 42 来自已核验的 finalized 链上账户状态和“没有历史未决签名”的基线；运行中必须同时考虑本地已经预留的槽，不能每次用某个 RPC 的 pending nonce 覆盖游标。

attempt 是槽内一次具体签名交易的身份，raw1 与 txHash1 固定属于 X1。请求、业务意图、nonce 槽和交易尝试不是同一种幂等键：requestKey 找回原 W1，W1 约束同一义务只终结一次，slot 防同一钱包 nonce 被不同意图争用，raw/hash 让恢复时知道到底重播什么。进程重启只能恢复这些关系，不能把内存丢失当成授权和付款义务消失。

## 第 3 层：签名完成但调用方失联怎么办

**面试官：** 槽已经持久化，但 signer 签好 raw1 后服务崩溃，PG 里还没有 raw1，重启后能当作“还没签名”吗？

**面试者：** 不能。调用 signer 前，我会先持久化经过授权的 draft 和签名请求，记录 W1、slot、完整交易字段、费用限制、审批信息、draft 摘要以及 signingRequestId。只有这个准备事务提交后才能发起签名，这样签名与 PG 之间即使没有分布式事务，也有一个可查询的恢复锚点。

signer 必须按这个 draft 和请求身份提供幂等、可审计的恢复能力：相同请求不能悄悄变更载荷，结果应能取回原签名交易及审计记录。调用方失联后先查原请求；signer 明确证明未执行才可重试原请求，证明已执行则取回原结果，仍无法证明就保持 SIGNING_UNKNOWN，冻结该槽相关处置，不擅自创建新的付款意图或释放 reservation。

正常 signer 不向网络广播，也不向未经授权的渠道导出 raw。若审计发现签名交易已经异常导出，必须按可能已传播的交易处理并进入风险冻结与补录核查；“业务 PG 尚无 attempt”不构成它无法上链的证明。签后失联是风险边界，不能用一个签名超时错误码把它抹掉。

## 第 4 层：哪一个提交边界之后才允许广播

**面试官：** signer 恢复出了 raw1，但 PG 还没写成功，能不能先发出去，之后补 attempt 和广播任务？

**面试者：** 正常路径绝对不能先广播。先解码 signed transaction，校验 type2、chainId=1、恢复出的发送方 H、nonce=42、to=T、value=0、transfer 的 B 和 100000000、gasLimit=65000、40/2 gwei 费用，以及其余已授权字段和 draft 完全相符；再从原始签名交易计算 txHash1。签名成功并不免除交易语义和预算复核。

然后在同一个 PG 事务中写入 X1 的 raw1、txHash1、draft 关联和 READY 状态，同时创建指向 X1 的 broadcast_task；事务成功提交后，广播工作者才有资格读取 raw1 并调用节点。如果事务回滚，就通过原 signingRequestId 重新恢复同一签名结果再持久化，而不是让无记录的 raw 在网络中运行。

提交后、发送前崩溃，由未完成任务继续发送；发送后、任务回写前崩溃，允许再次发送同一 raw。这样 PG 不需要和节点原子提交，但可以保证正常路径中每一笔可能被服务广播的交易，都有可恢复的原始字节、哈希、授权来源和后续追踪任务。异常导出路径则必须作为风险事件隔离，不能伪装成正常补写。

## 第 5 层：至少一次广播为什么不会重复转账

**面试官：** 你允许任务重复发送，甚至向多个节点发送，同一笔 100 T 不会付两次吗？

**面试者：** 重复发送相同 raw1，不是在构造新交易。它的签名、nonce 和 txHash1 都不变；在同一条规范链上，普通 EOA 的同一个 nonce 只能被消费一次。所以工作者重试必须从 PG 读取原始 raw1，不能重新分配 nonce，也不能在广播重试里随手改费用再签出一个未登记的交易。

具体顺序是领取 broadcast_task、发送 raw1、持久化节点与时间、响应分类和下次动作，再持续做链上追踪。返回 txHash1 或 already known，只能支持“这个节点声称已经接收或见过”；连接失败、超时仍按不确定性处理。返回哈希与本地计算不符需要隔离核查，不能把任何字符串都当成功。

多节点广播能降低单个节点故障带来的可用性问题，但不会把局部 mempool 变成全网权威。replacement underpriced 也只反映该节点对同槽候选和本地替换规则的判断，不证明原交易已付款或新交易永远无效。可靠广播实现的是可恢复的至少一次交付，不是业务层“成功付款一次”的最终证明。

## 第 6 层：租约过期为什么不能撤销旧广播

**面试官：** 一个工作者发送很慢，任务租约到期后另一个工作者接管；旧工作者稍后继续发送，怎样防止它越权？

**面试者：** PG 中可以给任务租约加 owner、到期时间和版本号。新工作者接管后，旧工作者不能再凭旧版本修改任务调度状态、创建新 draft 或写入权威业务结论；所有这类更新都要校验当前租约版本。节点响应作为观察可以保留来源，但不能绕过版本条件推动状态。

然而租约只能约束我们控制的数据库操作，不能让旧工作者已经拿到的 raw1 失效。即使旧工作者在租约到期后发送 raw1，网络仍可能接收；链上校验的是签名、余额和 nonce，不认识我们的任务租约。因此接管设计要允许同 raw 重播，并依靠槽与哈希身份去重，而不是宣称 fencing token 可以撤销已签交易。

若运营决定暂停发送，可以阻止新的正常调度和新授权，但仍必须追踪已经签出或导出的 raw1。即使把 broadcast_task 标成暂停，也不能释放 U 的冻结，更不能因旧租约过期而给 W1 另开 nonce=43。调度资格和链上执行资格是两个不同边界。

## 第 7 层：nonce too low 为什么不是付款成功

**面试官：** 接管者重播 raw1 时收到 nonce too low，这不是说明 nonce=42 已经用过，可以把 W1 标成成功了吗？

**面试者：** 不能。这条响应首先只是该节点在某个链头视角下的判断；即使核验后确认规范链上的 H 已经消费了 nonce=42，也只说明槽被占用了，没有说明是哪一笔交易获胜，更没有说明它是否向 B 转了 100 T。获胜者可能是 X1、同槽加速 X2、取消 Xc，或者授权体系之外的异常交易。

我会先核验 chainId 与节点同步情况，再查询整个槽已登记 attempt 集合的交易和回执，核对对应 blockHash 是否处于当前规范链。如果这些哈希都解释不了 nonce 消费，就通过可信账户交易索引，或定位消费区间后扫描规范区块的完整交易，寻找 from=H、nonce=42 的真实交易。标准 RPC 没有一个通用的“按发送方和 nonce 直接查交易”接口，不能假装单次查 hash 就覆盖全部情况。

找到获胜交易后仍要验证实际 payload、receipt.status 和业务效果，再等待最终性；若发现未知签名交易，冻结钱包新签名和相关资金处置，进入授权泄露或状态缺失调查。nonce too low 可以推动查证升级，不能直接推动 W1 成功，也不能自动把未明义务换成新的 nonce 付款。

## 第 8 层：所有回执都是 null 时怎样继续

**面试官：** 你按槽查了 X1、X2，两个 receipt 都是 null，而两个节点的 pending nonce 还不一致，现在怎样收敛？

**面试者：** 我会把 null 当“当前提供者没有给出这笔交易的回执”，而不是执行失败。交易可能尚未入块、被局部节点遗忘、处于不同分叉视角，也可能节点落后或历史数据能力不足。pending nonce 只反映节点自己的交易池和链头，二者不同本身不能裁决哪个 attempt 已永久退出竞争。

恢复顺序是检查提供者健康与最新规范链头，保留已有 inclusion_observation，再查询全部同槽哈希和 H 的规范链 nonce 变化。若以前观察过入块，现在回执为空，要用原 blockHash 与当前规范区块核对，判断是重组、查询故障还是数据缺失；若规范 nonce 已跨过 42，则回到查找该槽实际获胜交易，不能继续只等某一个 hash。

只要没有确定的终结证据，W1 就保留冻结，任务按退避和预算执行重播或转人工调查。长时间未知可以触发时效告警、暂停该钱包后续付款，或走经审批的同槽替换流程，但不能以等待时长替代证据。暂停是风险控制，UNKNOWN 不是一个到点就能自动改成 FAILED 的计时器。

## 第 9 层：广播证据怎样交接到资金终结

**面试官：** 你终于拿到了 txHash1 的回执，广播模块此时怎样交接，才不会把“见到回执”又误当成成功？

**面试者：** 广播模块交付的是不可丢失的观察：txHash、blockHash、blockNumber、transactionIndex、status、gasUsed、effectiveGasPrice、来源与观察时间，并关联 X1 和 slot。追踪器还要取回实际交易、核验当前规范链包含关系，回执解析器检查 T 的固定语义、精确 payload 及 Transfer(H,B,100000000)，才能形成“付款执行成功”的暂定结论。

这个结论先是 INCLUDED_PROVISIONAL，之后可标记 SAFE，默认仍要等包含该交易的区块被可靠的 finalized 区块覆盖，且确实是其祖先，才允许资金终结。不能只比较高度，也不能以固定 12 个确认代替 Ethereum PoS finality；提供者不支持 finalized 时必须告警或更换能力合格的数据源，不能静默降级。

终结处理器在 PG 事务中锁定 W1 与 slot，校验已验证的最终获胜证据和处理版本，完成一次终结账务与 outbox。正常 X1 付款后，H 为 9900 T、0.9984 ETH，U 冻结归零、可用仍为 900 T；若获胜者执行失败或是取消，则走不同业务分支。广播任务的完成只代表传播工作可以停，不能替代这一资金提交边界。

## 第 10 层：最坏故障窗口怎样证明不会多付

**面试官：** 假设节点实际接收了 raw1，但服务在写发送结果前崩溃；恢复时查不到回执，客服又催着重付，你怎样把整个故障窗口推演闭合？

**面试者：** 恢复者先从 W1 找到原 reservation、slot、X1、raw1 和未完成的 broadcast_task，确认原付款义务仍冻结。它重新发送 raw1，即使原节点已传播，也只是同一交易再传播；查不到回执时继续保持 UNKNOWN。客服请求只能挂到 W1 的调查和处置流程，不能创建一个语义相同、nonce=43 的付款来“试一下”。

如果之后授权加速，就登记同槽 X2，并同时追踪 txHash1、txHash2；原交易不会被撤回。无论哪个付款 attempt 在规范链获胜，都由槽级裁决和 finalized 证据终结 W1 一次。若先前入块的 X1 被重组出去，则撤销其暂定投影并重查全部 attempts，而不是据此解冻或再付；已经确认 finalized 的异常则进入事故冻结与补偿流程，不能随意回滚终态。

整个论证的关键不在“重试次数足够多”，而在每个副作用都有恢复身份：受理对应 W1，资金对应 reservation，签名对应 draft 与 signingRequestId，链上顺序对应 slot，网络发送对应持久 raw/hash，最终记账对应唯一终结记录。允许重复发送和暂时未知，禁止丢失追踪、未明解冻，以及把同一付款义务搬到第二个 nonce 上执行。

## 本题收束

- **讲透的机制：** PG 原子受理冻结，钱包锁与唯一 slot，先持久授权 draft 和签名请求，signer 幂等审计恢复，校验 signed 字段，再原子提交 raw/hash 与 broadcast_task；之后对同 raw 至少一次广播，对整个 attempt 集合持续追踪，最终由规范链执行事实与 finalized 证据驱动一次账务终结。
- **易错边界：** send 超时是 UNKNOWN；already known 不是入块；nonce too low 不是付款成功；null receipt 不是失败；pending nonce 不是全网事实；租约过期、暂停任务和本地取消标志都不能使已签 raw 失效。签后失联不能假设未签，异常 signer 导出必须风险冻结。
- **可推演反例：** raw1 已传播但发送响应丢失，系统因超时释放 100 T，又为 W1 用 nonce=43 签一笔付款。若 nonce=42、43 先后入块，链上就实际支付 200 T，内部却只记录一次提现。正确方案始终保留原 reservation 与槽，重播 raw1 或审批同槽替换，并等最终获胜证据后终结；不能靠“接口最多调用一次”掩盖这个反例。
