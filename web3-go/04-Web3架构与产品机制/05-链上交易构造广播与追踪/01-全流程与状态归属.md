# 大问题 1：一笔链上付款怎样从用户发起走到最终完成？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| W1 / U / H / B / T | 提现意图、用户、付款热钱包、收款地址及代币合约。 | U 提 100 T 到 B；付款的是平台 H，不是用户自己链上签名。 |
| EOA / ERC-20 / Ethereum L1 | 普通签名账户、代币接口及以太坊主网。 | H 独占且无代码委托，T 为已核验的标准 6 位代币。 |
| 受理 / 冻结 | 接下处理义务，并把用户相应权益暂时移出可用余额。 | 可用 1000 变 900、冻结变 100 T，不表示 B 已到账。 |
| 状态权威 / 观察 | 决定某类事实的规则，与对事实的报告。 | 数据库管受理和结算；链管执行；RPC 节点只提供观察及传播入口。 |
| nonce 槽位 / attempt | H 的一个执行序号，以及竞争这个序号的具体交易。 | W1 绑定 nonce 42，X1 付款、X2 加速、Xc 取消不能当三笔提现。 |
| ABI / transfer / value | 合约编码、转币函数及附带原生币金额。 | 调用 T 的 transfer(B,100000000)，value=0，Gas 另付。 |
| 预执行 / Gas 预算 | 在给定状态下试算，以及内部保留的网络费容量。 | 试算不锁定未来执行；用户冻结与 H 的代币及 ETH 容量分别检查。 |
| draft / raw / txHash | 批准草稿、已签交易字节及它的指纹。 | 签前存可恢复请求，签后核对字段并先耐久落盘再广播。 |
| UNKNOWN / already known | 结果未知，以及某节点已见到相同交易的回复。 | 两者都不能终结提现；查无结果也不能证明交易不存在。 |
| receipt.status / Transfer | 回执执行状态及代币转账事件。 | 外层成功还要匹配可信 T 发出的 H 到 B、100 T 的证据。 |
| INCLUDED / 重组 | 暂时被区块包含，以及规范分支变化。 | 旧入块观察可以撤回，不能借机新分 nonce 重新付款。 |
| safe / finalized / 祖先 | 共识进度标签与区块父链关系。 | 默认最终后结账，要证明回执块在最终前缀内，不能只比高度。 |
| 结算键 / Outbox | 防重复账务身份及同事务保存的待发通知。 | 链上已付、本地提交失败时恢复 W1，不再发一次币。 |
| 同水位 / 有界并发 | 用相同观察进度核算资产与义务，以及限制在途工作数。 | 不在旧库存上先释放预留；更多协程不能缩短链的最终性。 |

## 把整篇文章压缩成一个故事

小林申请把平台里的 100 T 提到 B。后台先可靠建立 W1、冻结 100 T，再给热钱包 H 分配 nonce 42，检查 T 库存与平台付 Gas 的 ETH，构造正确合约调用。签名并不是最后一步：必须确认签回字段无误，将可传播的原字节与发送任务保存，才能交给广播器。

发送超时后，页面显示执行中而不是失败退款。系统找回原签名与 hash，继续查同序号的付款、加速和取消候选。某个回执显示成功，也先核对代币、收款人和金额，再把它记成能被重组撤回的临时观察；取消按钮已点击或某节点报告接收，都不能替代最终链证据。

最终链确实包含正确付款，系统才一次核销冻结，并在本地同时记账、结清钱包预算、保存通知。若这次数据库响应丢了，重试的是结算，不是转账。小林能早早看到受理与入块进度，却只有符合约定最终性后资金才终结；要提前给可支配额度，必须另加信用与重组风险规则，不能靠改状态名字提速。

**流程位置与核心机制：** 本题串起受理、构造、签名、广播、入块、最终性和资金结算，明确谁决定什么。具体 nonce 算法、重播、替换与账务原子性分别在后续母题深入，不能用这些模块的名字代替本题完整回答。

沿用总览：Ethereum PoS L1、普通 EOA H、标准 ERC-20 T，用户 U 的 W1 向 B 提现 100 T，平台支付 Gas。所有数值均为教学假设。

## 第 1 层：先完整讲一遍，而不是从 SDK 开始

**面试官：** 如果让你用 Go 设计链上付款服务，从用户申请到真正完成，一笔业务怎样走？

**面试者：** 在这个模型中，我会先建立付款意图，再让意图驱动交易，最后依据最终链证据结算。U 用请求键提交提现，账户和意图在一个本地事务中校验并冻结 100 T，得到 W1。受理完成只承诺可靠处理，不表示链上已经转账。

钱包调度器为 W1 选择 H，在钱包锁下检查代币与 ETH 容量、分配 nonce 42 并预留预算。构造的是对 T 的 `transfer(B,100000000)` 调用，而不是向 B 发送 100 ETH。预执行与估 Gas 后固定审批载荷，受控签名，核验签回交易，再将 raw、hash 和广播任务耐久落盘。广播 worker 发这个 raw，超时也继续追原交易，不重新分 nonce。

追踪器观察同槽位所有交易候选的回执，核验规范链、执行状态和正确的代币转账证据。入块只是临时结果，重组可能撤销；确认交易属于 finalized 链前缀后，成功就核销冻结，最终未付款才释放冻结。账本、意图终态与通知 Outbox 同事务提交，查询分别展示受理、入块和最终结果。

## 第 2 层：到底谁拥有权威状态

**面试官：** 你说数据库里记录状态，链上也有状态。如果两边不一致，谁说了算？

**面试者：** 不是选一个统一覆盖全部状态。数据库拥有本地业务权威：W1 是否受理、用户是否冻结、哪个授权可签、nonce 分配给谁、最终结算是否已经执行。链拥有执行事实：哪个候选消耗 nonce 42、是否回滚、实际 Gas 和资产变化，以及所在区块是否最终。节点的 mempool 和广播响应只是一种观察，不能凌驾于这两类事实。

例如数据库显示 X1 已发送，节点却查不到，不足以把 W1 改为失败；数据库显示“取消请求已批准”，但最终链执行的是 X1，也必须按付款结果结算。反过来，链上发现一笔 H 发出的未知交易，也不能为了对齐余额就伪造一个用户提现意图，应冻结该钱包并查授权与签名审计。

因此我会将业务状态、attempt 传播状态、链观察和结算状态分开。一次 RPC 错误不能直接穿透全部状态机；能够触发资金终结的必须是经过业务核验的最终结果。

## 第 3 层：从权威划分落实到对象身份

**面试官：** 状态分开以后，怎样知道一条回执属于哪个业务？用交易哈希作为主键不就够了吗？

**面试者：** 哈希只能标识一份具体签名交易，不能独自标识业务。W1 是付款意图，`(chainId=1,H,nonce=42)` 是执行槽位。原交易 X1 和提高费用的 X2 有不同 hash，却服务同一笔付款；取消 Xc 也占同一槽位，但操作类型不是付款。

我会保存 `intent → nonce_slot → attempts` 的绑定，并保存每次 draft 的审批载荷。回执首先关联准确 hash 与区块身份，再结合 attempt 的操作类型、实际交易字段和代币日志判断业务结果。不能因为 Xc 的 receipt 是 status=1，就把 W1 标为付款成功。

这套身份还约束重试：查询 hash 可以重复，广播 raw 可以重复，但未知状态不能为 W1 自动再分一个 nonce 43。普通 ERC-20 不认识 W1，两个 nonce 都成功就会付两次，本地唯一结算键挡不住链上多转的 100 T。

## 第 4 层：身份没有解决签名与广播之间的故障窗口

**面试官：** 你说先保存交易再广播。可是签名服务已经签完，客户端还没保存 raw 就崩了，怎么办？

**面试者：** “先存再发”只覆盖得到 raw 之后，不能假装签名和数据库有共同事务。我会先耐久保存授权 draft 与签名请求身份，签名服务按这个身份保存可查询的结果或明确审计状态。收到签名后恢复 sender、核对全部字段，再保存 raw/hash 与广播任务，只有已提交的广播任务才能外发。

客户端在签名返回前崩溃，恢复时要查询原签名请求，而不是当作从未签名。签名服务若无法确认到底有没有产出可用交易，这个槽位就是有风险的未知执行权利，应保留用户与钱包预留并隔离核查。签名服务的幂等、日志保留和复制耐久性因此是接口契约，不是“调用超时可以再试”五个字。

只要有效 raw 已经泄露或进入在途网络，本地删除记录、租约过期和取消 context 都不能让它失效。恢复方案必须继续追踪它；不能依靠清空本地状态重新开始来消除外部风险。

## 第 5 层：广播未知时怎样向用户表达

**面试官：** 原签名可以恢复了，但广播调用超时。用户一直问是不是失败，你怎样返回，资金怎么办？

**面试者：** 我会返回 W1 的“执行中／广播结果待确认”，并附已知 hash 与查询入口，不承诺未付款。用户可用仍为 900 T，冻结仍为 100 T；钱包的付款与费用预算也不能因为一次超时释放。raw 的 hash 在本地就能计算，追踪不依赖广播端返回 hash。

处理器可以查询多个受控节点、重播同一 raw，并记录各提供方响应。多个节点都查无结果仍只是观察，不是全网不存在证明。若有 nonce too low，要找当前规范链到底用哪个交易消耗了 42，失败交易也会消耗 nonce；不能凭报错推断 X1 已成功。

用户取消也是请求系统尝试关闭业务，而不是立即退款。如果已经签出交易，通常要发送受控同 nonce 取消候选，并等待最终获胜结果。界面必须区分“取消已申请”和“最终取消”，否则产品承诺会先于实际可证明的资金安全边界。

## 第 6 层：查到回执是否已经足够

**面试官：** 你拿到了 X1 的 status=1 回执，为什么还要让用户等？

**面试者：** 首先 status=1 表示顶层 EVM 执行未失败，不等于任意业务目标成立。对于本基线，我要核对交易确实来自 H、目标是 T、金额与收款人正确，以及可信 T 发出的 `Transfer(H,B,100000000)` 日志。回执不直接包含 `transfer` 返回的 bool，非标准代币还需要专门规则。

其次回执属于一个具体区块，不是永久不变的成功证书。我要核对 blockHash 与规范链关系，先存 INCLUDED 临时观察；达到最终性之前仍保留用户冻结。若重组把该块移出规范链，就撤销临时观察，继续追踪 X1、X2、Xc，而不是自动用新 nonce 重发。

最终判定还要证明回执块位于可信 finalized 块的祖先链上。只看高度小于 finalized 高度会把旧分叉回执算进去。若 RPC 不支持所需标签或链视图不一致，应等待或按明确产品策略降级显示，不能静默把十二个确认包装成协议最终性。

## 第 7 层：最终证据与本地记账仍不是共同提交

**面试官：** 假设你已经证明付款 finalized，但更新数据库时失败。用户冻结还在，这不是不一致吗？

**面试者：** 这是允许恢复的暂态：链上付款已完成，本地仍保留未核销义务，表现为保守冻结，而不是凭空多出可用资产。最终观察和待结算任务必须可重读，结算器重试同一个 W1。不能为了解决本地提交失败再发一笔链上付款。

在本地事务中，我会检查 W1 的版本和唯一业务结算键，一次写入提现结果、冻结核销、对应账本分录、钱包预算核销以及通知 Outbox。提交成功但响应丢失时，重试查到原结算，不再次扣款。通知消费者也按事件身份幂等，通知是否送达不影响已确定的账务事实。

同时，钱包余额镜像和预留释放要对齐水位：不能在旧余额 10,000 T 上先释放 100 T 预留，短暂把已经付出的资产再次借给后续提现。先保守少报可以，先放开再靠对账追回不成立。

## 第 8 层：性能要求变化时哪些保证不能改

**面试官：** 这样一层层等很慢。业务要求更高吞吐和更低可见延迟，你会怎么改？

**面试者：** 我会先区分可见延迟、广播吞吐和资金终结延迟。受理事务成功后即可返回 W1，节点看到或入块后即可展示阶段进度，没有必要让 HTTP 连接一直等 finalized。最终性本身不是加更多 goroutine 就能缩短的系统瓶颈。

同钱包按 nonce 有序决策，允许小而有界的未决窗口；签名、RPC 查询和不同钱包可以并发。最老未决 nonce 要优先恢复，否则后续高 nonce 的交易再多也无法跳过它执行。增加钱包分片能够扩容，却改变资金分布、调度和补资成本，必须显式加入预算与权限设计，不是悄悄让同一 W1 同时从两个钱包付款。

如果产品选择在最终性前给可支配额度，那是新增的信用与重组风险策略，需要限额、损失承担和补偿规则，不能沿用本基线“最终后结算”的保证。优化可以减少无谓等待，不能把未知结果改名为失败、把广播成功改名为付款成功来制造低延迟。

## 本题收束

- **讲透的机制**：意图驱动执行，链提供结果证据，本地账本终结义务；每个边界有独立状态、身份、提交条件和恢复责任。
- **最容易答错的边界**：签名不等于已存档，节点接收不等于入块，入块不等于业务成功，业务临时成功不等于最终结算；数据库与链没有共同事务。
- **反例验证**：让 X1 广播超时、Xc 在另一分叉临时入块、最终链却保留 X1，再让第一次账务响应丢失。正确结果应是 W1 最终付款一次、冻结核销一次，不因为取消请求释放，也不因为账务超时再次发币。
