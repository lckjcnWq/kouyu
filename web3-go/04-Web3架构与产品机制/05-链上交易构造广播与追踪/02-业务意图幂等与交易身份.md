# 大问题 2：一笔付款为什么要区分请求、意图、nonce 槽位与多个交易哈希？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| U / B / H / T / W1 | 用户、收款地址、平台钱包、代币及提现意图。 | 本篇是一笔从 H 向 B 支付 100 T 的托管提现。 |
| requestKey / 作用域 | 请求去重键及它在哪位用户、哪类业务下有效。 | 同键同内容找回原 W1，不能用过期缓存清理后再次付款。 |
| payloadDigest / 规范化 | 对业务内容做稳定摘要，先把等价输入统一表示。 | 网络、代币、地址、整数金额及用户都要绑定；同键改金额报冲突。 |
| 幂等 / 唯一约束 | 重复处理不增添业务效果，以及数据库强制不重复的限制。 | 先查后插挡不住并发；请求去重、冻结和任务须在受理事务内协调。 |
| 冻结 / 账户行锁 | 暂时不可用的用户权益，以及并发修改账户时的互斥。 | 不同请求也可能竞争同一余额，只有请求唯一键不够。 |
| intentId / nonce_slot | 业务义务身份与钱包执行序号身份。 | W1 表达付款目标，链 1、H、42 表达一个候选竞争槽。 |
| draft / attempt / txHash | 审批草稿、具体签名候选和交易指纹。 | X1 与加速 X2 的 hash 不同，但并非两笔独立付款义务。 |
| PAY / CANCEL | 付款与取消的操作类型。 | 同序号 Xc 自转成功，不代表 W1 的 100 T 已付到 B。 |
| raw / 待签摘要 | 已签交易原字节，以及签名前需要签的消息摘要。 | 查询回执用最终 txHash，不用 signer.Hash 得到的待签摘要。 |
| 同字节重播 / 同 nonce 互斥 | 再传播同一交易，与一个规范链序号只容一个执行候选。 | 广播任务重试读取原 raw；加价是显式的新候选，不藏在重试函数里。 |
| exactly-once / 至多一次 | 恰好成功一次，与最多发生一次是不同承诺。 | 同 nonce 可能一直不执行、回滚或被取消，不能保证业务必成功。 |
| ERC-20 transfer / 业务去重 | 标准转币函数，与识别 W1 的业务规则。 | 标准 transfer 不认识 W1，改用 nonce 43 仍能合法再付 100 T。 |
| inclusion / blockHash / orphaned | 入块观察、区块指纹及已离开规范链的旧观察。 | 同 hash 可在不同块重新入链；去重不能永久忽略后来的规范观察。 |
| finalized / 结算键 / Outbox | 最终链证据、防重复记账身份及待发通知。 | 多个观察者先验最终祖先关系，再按 W1 一次结账，不先到先赢。 |

## 把整篇文章压缩成一个故事

小林连点两次 100 T 提现，还遇到第一次响应丢失。系统按同一个请求键和规范化摘要找回 W1，所以只有一份冻结；如果他们复用这个键却改成 200 T，接口明确拒绝。W1 下面先分配 H 的 nonce 42，再保存付款 X1；后来加速 X2 和取消 Xc 各有自己的 hash，却仍属于同一个执行槽。

X1 广播超时，任务重投只拿原字节再发，不偷偷给 W1 配 nonce 43。Xc 曾经在旧分叉成功，系统保存的是那个区块里的取消观察，没因此退款；重组后最终链保留 X1，就按正确付款处理。同一 hash 以后重新入块，也要形成新位置观察，不能被第一次去重记录挡住。

最终结果按 W1 的结算键只核销一次冻结，重复回执和通知不再增加分录。但若程序另用 nonce 43 又转了 100 T，链可能让两次都成功，收款人就收到 200 T；数据库里只有一条账并不能追回多付资产。故事的关键是每层身份各守自己的边界，不用一个幂等键替代全部执行控制。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题负责跨阶段身份与幂等契约，回答“什么必须只产生一次、什么允许有多个”。Nonce 发号细节见第 05 题，资金原子结算见第 11 题；本地去重不冒充链上业务幂等。

沿用总览 W1：U 向 B 提现 100 T，H 在 Ethereum L1 通过 nonce 42 调用标准 T。X1 为原付款，X2 为同载荷加速，Xc 为独立批准的同 nonce 取消。

## 第 1 层：先说清楚究竟在防哪种重复

**面试官：** 用户重复点提现、网络自动重试、后台重复广播，你怎样避免重复付款？

**面试者：** 我不会用一个“幂等键”统包所有重复。请求层用用户与业务作用域内的 requestKey 找回同一 W1，防止重复创建提现与冻结；执行层为 W1 绑定持久 nonce 槽位，防止未知结果时又分一份可独立执行的付款；广播层重发完全相同的 signed raw，让重复传播仍是同一笔交易；结算层用 W1 的唯一结果键，防止重复观察引起多次账务处理。

这四层解决不同事情。X1 加速成 X2 后 hash 改变，业务还是 W1；把 txHash 当请求幂等键，会让加速看起来像新提现。反过来，仅有 W1 的账本唯一键，却自动换到新 nonce 再付款，虽然账上可能只扣一次，链上仍可能转出两次。

## 第 2 层：同一个请求键可以复用不同金额吗

**面试官：** 你说重复请求返回 W1。如果用户第一次填 100 T，第二次沿用同一个键却改成 200 T，你怎么办？

**面试者：** requestKey 必须绑定规范化后的 payloadDigest，而不是只做一次插入忽略冲突。摘要至少包含网络、资产合约、收款地址、最小单位整数金额、用户身份及影响付款的业务条件。输入先经过明确的规范化规则，金额不能用有精度损失的浮点字符串算摘要。

相同作用域、相同键、相同摘要返回原 W1 与当前进度；相同键不同摘要明确返回冲突，不覆盖旧金额，也不把旧结果当成新请求成功。数据库唯一约束处理两个请求同时首次到达的竞争，输掉插入的事务读取原记录再比较摘要，而不是依赖应用先查后插。

幂等记录应覆盖可能的客户端重试与业务审计生命周期，不能在普通缓存 TTL 到期后让同一旧键重新发币。若产品允许用户主动提交第二次相同提现，那需要新请求身份并走新的余额与风控准入，不靠猜测相同金额来认定重复。

## 第 3 层：请求去重怎样和冻结共同成立

**面试官：** 唯一请求挡住了两份 W1，但第一笔请求冻结成功、写意图失败，资金不还是会挂住吗？

**面试者：** 在本模型的 PostgreSQL 边界内，意图身份、请求摘要、用户资金冻结与初始执行任务属于同一受理事务。事务检查可用余额足够，将 100 T 从可用转为冻结，并建立对应的预留身份；它们要么共同提交，要么共同回滚。受理响应只在提交后返回。

并发请求还要通过账户行锁或带余额条件的原子更新防止超额冻结。唯一 requestKey 只防同一次请求，不能防两个不同请求同时消耗相同余额。对 W1，提交后 U 可用 900 T、冻结 100 T；进程在响应之前崩溃，客户端重试会读到原意图，而不是再冻结 100 T。

如果账户是独立服务，这个本地事务前提就改变了。需要带预留身份的持久授权和可查询协议，处理冻结成功但受理未知，以及撤销与迟到命令的竞争。不能跨服务直接说“数据库事务”仍然覆盖两边；本专题主路径不悄悄改成那个架构。

## 第 4 层：为什么还要引入 nonce 槽位

**面试官：** 现在有 W1 和冻结了，直接在 W1 下面保存 txHash，不用 nonce_slot 会怎样？

**面试者：** 问题是 hash 还没有生成时就需要分配执行资格，而且同一资格后面可能有多个候选。我会先为 W1 建立唯一槽位 `(chainId,H,42)`，再关联授权 draft 和具体 attempt。唯一约束防止本地将同一钱包序号分给两个无关意图；钱包分配器决定序号，RPC 的 pending nonce 只用于观察与恢复。

X1 和 X2 可以共享槽位但各自保存 raw、hash 和费用。Xc 也共享槽位，却带 CANCEL 操作类型和独立授权，不能复用“付款草稿已批准”来签出任意自转。槽位是候选集合的协调身份，W1 是要完成的业务，attempt 是一次实际签名能力，三者不能合并。

数据库保证的是本服务不错误分配，不是链替我们检查 W1。钱包被其他系统使用，或者未知签名出现在网络中，仍可能与槽位冲突；这时必须隔离对账，而不是无视外部事实继续递增发号。

## 第 5 层：广播调用自身的重试该用哪个身份

**面试官：** 你的 worker 发 X1 超时，任务又投递一次。第二次重新构造一笔同样金额的交易可以吗？

**面试者：** 最安全的广播重试是取出已经耐久保存的 raw1，提交完全相同字节，并用本地计算的 txHash1 查询。这样重复 RPC 调用只是再次传播同一交易，不会悄悄改变 nonce、费用、接收人或签名内容。任务至少一次投递是可以接受的，因为执行的是固定 attempt。

重新构造可能读取到新的 nonce 或费率，也可能重新签名得到不同字节，使一次“发送重试”变成新候选甚至新付款。提高费用必须显式申请 X2，重新检查同槽预算并保存新授权和新 attempt，不能埋在 HTTP 超时重试函数里。

Go 的 `SendTransaction` 返回 error 而不是负责赋予交易身份；hash 应在发出前从签名交易取得。要特别区分最终交易 hash 和签名时的待签摘要，不能用 `signer.Hash(tx)` 的结果去查询最终回执。

## 第 6 层：同 nonce 能否等价于业务恰好一次

**面试官：** 同一个 nonce 在链上最多执行一个候选，那是不是 W1 已经保证 exactly-once 了？

**面试者：** 只能说，在本基线的同一规范链里，普通 EOA 的同一 nonce 最多被一个交易执行，它提供的是执行槽位互斥，不自动提供 W1 的业务恰好一次。交易可能一直不入块，也可能 status=0，或者最终获胜的是取消 Xc，所以“最多一个执行”不等于“付款恰好成功一次”。

更关键的是，W1 如果又绑定 nonce 43 或换另一钱包，就产生新的独立执行机会。标准 `transfer` 没有 W1 这个参数，链不会知道两次调用来自同一提现。42 迟到成功而 43 也成功时，收款人拿到 200 T，数据库去重只能阻止多记账，不能追回资产。

因此主路径在旧执行资格未关闭时不自动重发新槽位。即使旧槽位最终失败，是否重新执行也要明确用户预期、审批和资产状态；不能把无限执行直到成功当成没有边界的默认重试。

## 第 7 层：取消是不是关闭执行资格的证明

**面试官：** 那我为 nonce 42 发一个取消交易，然后立刻把 W1 挪到 43，不就能继续了吗？

**面试者：** 发出 Xc 不是关闭资格的证据。Xc 只是与 X1、X2 竞争的另一份有效签名。某节点接纳它，不能撤销其他节点、构建者或旧 worker 已经持有的付款交易；原交易可能先入块，取消也可能在重组后失去位置。

在默认规则下，必须确认最终规范链用 Xc 或其他可核验的未付款交易消耗了 42，且业务证据确实没有把 T 付出去，才能按最终未付款结束 W1 或进入新的受控业务决策。若最终执行的是 X1，且 status=1、付款证据吻合，则按成功结算，不因本地取消按钮已经点击而退款；若最终 status=0，则按失败结算、释放冻结，实际 Gas 仍计费。

完全没有产出签名的槽位也不是随便删：要先关闭原授权与所有在途签名请求，证明旧持有者不能再签出付款，再决定是否在同槽填补或重新绑定。签名是否存在不确定时，仍应按存在外部执行权利来保守处理。

## 第 8 层：同 hash 为何还不能唯一标识链观察

**面试官：** 执行身份我明白了。回执直接按 hash 幂等落库不就行了，为什么还要 blockHash？

**面试者：** 同一签名交易可以先在一个分叉入块，被重组后又在另一块入块；它的交易 hash 相同，包含它的区块身份却不同，执行上下文和实际费用也可能变化。若第一次 hash 命中后永久忽略后续观察，就可能保留旧回执、错过新规范链结果。

我会把 inclusion 观察按 `chainId、txHash、blockHash` 等位置身份保存，日志进一步包含日志索引；高度只用于排序和定位，不足以区分同高度分叉。观察标记 provisional、orphaned 或 finalized，重组撤销的是旧观察及其临时投影，不是删除 W1 或重新分配付款资格。

最终资金结算的去重键仍是 W1 的业务结果，而不是每个 inclusion 键。观察层允许保留多条历史证据，业务层只允许一个经核验的最终结果，两类唯一性承担的职责正好不同。

## 第 9 层：多个观察者会不会制造多份最终结果

**面试官：** A 节点给 X1 的旧回执，B 节点给 X2 的新回执，两边消费者都认为自己看到了成功，怎么避免各结算一次？

**面试者：** 先禁止观察者凭一份回执直接结算。它们只能提交带区块身份与来源的观察；最终裁决器要证明回执块属于所采用可信 finalized 链前缀。两个同 nonce 候选不可能同时在同一合法规范链执行，出现冲突应视为链视图、数据或系统状态不一致，隔离复核，而不是“先到先成功”。

在本地，即使两个处理器都提交同一个合法结果，也通过锁定 W1、检查状态版本与唯一结算键，让意图终态、账本和 Outbox 一次提交。输掉竞争的处理器读取已有结果，若结果不同则报冲突，不覆盖旧记录。

这项原子性只能保证已接受证据不被重复应用，不能使错误证据变正确。数据库唯一约束与链证据校验必须同时存在；前者解决竞争，后者解决能不能结算。

## 第 10 层：用一个完整故障序列检查身份设计

**面试官：** 你怎样验证这些身份不是设计得很漂亮，真正遇到故障仍然会串单？

**面试者：** 我会按身份层级构造可手工推演的反例：同一个请求键并发提交两次且一次响应丢失，应只有 W1 与一份 100 T 冻结；随后改变金额重试应冲突。签名结果恢复必须回到原 draft，广播重复必须回到 raw1，不能偷偷产生新的槽位。

再让 X1 广播未知、X2 加速、Xc 取消，保留三份 hash。先观察 Xc 的临时成功，再发生重组，最终链包含 X1。正确结果是观察历史有多条，W1 最终只有付款成功一条结算，可用 900、冻结 0；Xc 曾经 status=1 不能让用户提前恢复到可用 1,000。

最后重复投递所有观察与最终通知，并模拟账务提交成功但响应丢失。账本不增加第二组分录，通知消费者不重复处理；如果故意为 W1 新增 nonce 43 并使两笔转账成功，检查器应指出链上双付风险，而不是因为数据库只有一条结算就宣称安全。这能检验各层幂等的真实覆盖范围。

## 本题收束

- **讲透的机制**：请求幂等绑定载荷，意图承载义务，nonce 槽位管理执行互斥，attempt 保留签名候选，区块身份管理观察，业务结算键管理资金应用。
- **最容易答错的边界**：同 raw 重播可以安全重试传播，不代表任意新签交易都安全；同 nonce 至多执行一次，不代表业务恰好成功一次；账本去重不阻止链上双付。
- **反例验证**：把同一 W1 同时绑定 nonce 42、43，在链上连续执行两次相同 `transfer`。若方案只检查 requestKey 或结算键而发现不了这两份可执行付款，就没有覆盖端到端重复付款。
