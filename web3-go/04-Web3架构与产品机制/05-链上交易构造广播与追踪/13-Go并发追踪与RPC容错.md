## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |

| W1 / H / T / slot | 提现意图、平台钱包、代币与执行序号槽。 | 100 T 提现绑定链1、H、42，并发不能给同一义务再开新槽。 |
| wallet actor / 状态所有权 | 每个钱包由一个进程内所有者串行做调度决定。 | 预算与候选变更串行，RPC等待放worker；actor不是跨实例付款锁。 |

| durable task / channel / 租约 | 持久任务、内存通道和临时领取资格。 | channel只是缓冲，崩溃后从库重领；队列满不丢已冻结任务。 |

| big.Int / 深拷贝 / slice | 可变大整数、独立复制及可能共享底层数据的切片。 | X2提费不能原地改X1，ABI字节和access list也须明确只读所有权。 |
| Go 1.21循环捕获 | 闭包误用反复被复用的循环变量。 | X1、X2、Xc查询应各有独立快照，不让三次查询都盯最后一个。 |
| RPC / 429 / 退避抖动 | 节点接口、限流响应及错峰延后重试。 | 分类处理错误，重试多层不能相乘；确定构造错误先停查。 |

| cursor / 连续水位 / blockHash | 持久扫描位置、无缺口覆盖进度及块身份。 | 重连补扫，区块、观察与游标同事务，不直接跳最新头。 |

| 最老年龄 / 指标基数 / 恢复准入 | 义务等了多久、指标标签数量和重新开放的安全条件。 | RPC成功率高也可能漏账；具体hash放受控查询，不铺成无限标签。 |

## 把整篇文章压缩成一个故事

平台用Go同时追踪小林提现的X1、加速X2和取消Xc。钱包actor只负责本进程内有序决策，跨实例仍由数据库钱包锁与唯一槽裁决；查询和广播交给有界worker。队列满了先限新提现，已冻结W1仍留在持久任务里，不能因内存channel装不下就漏掉追踪或退款。

一次Go 1.21循环若错误捕获变量，三个查询可能全去查Xc；同时订阅断线，X1却在漏掉的区间付款。正确设计给每个任务独立身份与不可变快照，用持久游标补连续区块，并枚举全部未决hash。context超时只结束等待，NotFound只说明端点暂时没给结果，不能据此把小林的100 T放回可用。

补查最终找到准确付款并证明其最终链归属后，结算器按同一W1只核销一次。监控关注最低未决nonce、最老未知年龄、扫描缺口和最终待应用义务，不仅是调用成功率。高并发的价值是让原义务有界地持续推进，不是多造付款能力；依赖仍有缺口就暂停新签名，而不是靠更多协程或新nonce把指标刷绿。

## 第 1 层：wallet actor 串行什么，不能保证什么

**面试官：** 你要用 Go 同时服务多个钱包，每个钱包又有很多待追踪交易。怎样划分并发，既不撞 nonce，也不让一个 pending 交易卡住全部工作？

**面试者：** 我按 `(chainId,sender)` 建 wallet actor，让一个进程内该钱包的调度状态由单个所有者推进，串行处理预算申请、槽选择和候选变更；查询、签名与广播则交给有界 worker，返回带 W1、slot、draft 或 attempt 身份及预期版本的结果消息。actor 不在自己的事件循环里等交易 finalized，也不持着锁等待 RPC，否则槽 42 pending 就可能阻塞这个钱包的证据处理、取消审批与恢复。

actor 是减少进程内竞争的结构，不是跨实例锁。U 的受理仍由 PostgreSQL 在唯一 requestKey 与 payloadDigest 约束下原子冻结 100 T；H 的分配仍锁 wallet 行，检查 T 与最坏 gas 预算，创建唯一槽 `(chain1,H,42)` 并将 W1 绑定到原付款槽。actor 的缓存游标只供调度，不能覆盖数据库权威；两个实例各有一个 H actor 时，仍由数据库状态条件、唯一约束与当前 epoch 裁决，不能都凭内存 nextNonce 签名。

worker 也没有自行付款的权力。已授权 draft 先耐久，再由 signer 按 draft 持久幂等签名并支持查询；核验 signed 的链、发送者、nonce、payload、gas 和费用后，raw/hash 与 broadcast_task 先共同耐久再外发。DB epoch 还须延伸到 signer 出口的任期与审批校验，但已签 raw 不受围栏撤销；因此 actor 重建或实例切换都必须接管旧签名，不得换一个 actor 就把 W1 重发到 nonce 43。

## 第 2 层：如何让并发有界而不丢掉已承诺工作

**面试官：** actor 把网络工作交给 worker 后，如果新请求与旧交易查询一起暴涨，为什么不能每个任务起一个 goroutine？队列满了又该怎么办？

**面试者：** 我限制的不只是 goroutine 数，还包括内存队列、数据库连接、每个 RPC 端点的在途调用、每个钱包未决槽，以及签名器并发。广播、receipt 查询、区块补扫和最终结算采用受控 worker 池，按链与端点设配额，避免所有任务共享一个无界 FIFO。任务从 PostgreSQL 分页领取，内存 channel 只是短期调度缓冲；worker 崩溃后可按任务租约与持久阶段重领，不能因为 channel 中任务丢失就让 W1 永久无人追踪。

容量要优先保障已有义务：最低未决槽 42、签名或广播 unknown、扫描缺口、finalized 待结算与 outbox 补投有保留配额，新提现准入与新签名可以限流。队列满时让 durable task 保持可领取状态或记录下一次调度时间，不静默丢弃，不先把任务标成完成再尝试入 channel；也不让每个失败 worker 在后台再起一个 goroutine 重试，绕开并发上限。数据库任务被重复领取仍需版本与业务键防重。

已冻结 W1 不能因追踪队列满而释放 100 T。过载应减少新的承诺，必要时暂停 H 的新分配，继续原义务闭环；已签任务无法及时处理则告警升级。服务退出也先停止新领取，让受控在途调用退出或进入可恢复 unknown，再由新实例从耐久状态接管；不能把“全部 goroutine 已结束”报告成“全部交易已失败”。具体池大小与阈值按下游限额和容量测量校准，不编造固定 QPS。

## 第 3 层：context 结束为什么不能转成业务失败

**面试官：** 为了及时释放 worker，你给每次数据库、签名和广播调用都设 deadline。context 到期后，任务怎样退出，资金状态又怎样处理？

**面试者：** context 管理本次调用的等待、资源与取消传播，不是远端副作用的回滚协议。受理事务提交、signer 签出 X1、节点传播 raw 都可能已经发生，只是返回途中超时。worker 可以停止当前等待并回收资源，但要把未确定的阶段记录为待查询恢复，不得统一写 FAILED 并释放冻结。客户端 HTTP 请求结束，也不能自动取消已经可靠受理的 W1；后台任务由独立受控生命周期继续处理，不在请求结束后留下无人管理的 goroutine。

数据库提交结果未知时按原 requestKey 或业务键查询主库；签名调用未知时按原 draftId 查询 signer；广播未知时查询原 hash，并在策略允许时重播原 raw。go-ethereum 的 `SendTransaction(ctx, tx)` 只返回 error，不会额外返回一个供记账的交易 hash；hash 应由已核验交易的 `tx.Hash()` 在本地计算，并在发送前连同 raw 和任务耐久保存。nil error 只说明本次发送调用没有报告错误，不证明付款、入块或最终性。

每次调用都应使用有界 deadline 并及时调用相应 cancel 释放资源，长寿命 worker 不要把所有 cancel 都 defer 到进程退出。超时恢复写入也不能继续使用已经取消的调用 context；应由受控任务调度以新的有限期限记录或重试。即使连 unknown 标记都没来得及写，原 draft、raw 和未完成任务仍足以在重启时识别风险。无论哪种超时，签后 unknown 都不允许为 W1 重新分配付款 nonce。

## 第 4 层：worker 收到的数据为什么必须是独立快照

**面试官：** context 已分清了，但 worker 接收 actor 的交易参数时复制了 struct，为什么仍可能把 X1 的费用或 W1 的金额改乱？Go 1.21 下还要防什么？

**面试者：** struct 值复制不代表内部指针、slice 和 map 深复制。`big.Int` 是可变对象，`fee2 := fee1` 若复制的是指针，两者仍指向同一数值；加速 worker 原地修改它，可能同时改变待签 X1 的参数。应为需要修改的金额、max fee、priority fee、value 建立独立对象，例如 `new(big.Int).Set(original)`，不要浅复制 `big.Int` 的内部存储；ABI data、raw 字节、access list 内部切片等也按实际结构复制或明确只读所有权。金额 100 T 始终用整数 100000000，不经 float64。

actor 向 worker 交付不可变 draft 快照，worker 只返回计算结果与身份，不共享可写的钱包 map、余额指针和候选集合。X2 提费应生成新 draft 并重新审批，不能原地修改 X1 后还沿用其摘要；签名返回时再次核验 signed 字段，即使内存层出现陈旧或被误改的数据，也不能直接外发。raw 需要防止缓冲区复用，并作为敏感执行能力受控保存，不能为了排查问题把它完整写入普通日志。

Go 1.21 的 `for range` 循环变量在相关写法下会被下一次迭代复用，循环中启动闭包可能让多个 goroutine 都查询最后一个 attempt。应显式在每次迭代重绑定，或把 attempt 快照作为闭包参数传入；如果参数里仍有可变指针，也必须解决所有权，单纯复制变量名不够。较新语言版本改变部分循环语义，也不能替代对共享数据的审查。worker 结果回到 actor 后，还要匹配持久版本与 epoch，不能把查询开始时的旧快照无条件覆盖当前 W1。

## 第 5 层：RPC 错误怎样分类才不会越重试越危险

**面试官：** worker 数据隔离了，但 RPC 经常限流、超时或者返回业务错误。你会统一指数退避并切换节点吗？

**面试者：** 不统一。连接错误、超时、429 和可识别的暂时服务不可用，适合按任务总预算设置单次 deadline、指数退避与抖动，遵守适用的服务端重试提示，并受每端点限流和并发上限控制；避免 SDK 自动重试、worker 重试和 actor 重试三层相乘。退避时间耐久化为下次可执行时间，不占着 worker 睡很久；需要熔断时按端点或依赖隔离，不因一个服务商异常阻塞所有本地账务应用。

invalid sender、错误 chainId、参数编码不符等确定构造错误要停下并核查，不应盲目换节点；insufficient funds 需要重新核对链水位、T／ETH 预算和既有承诺，不是放宽预算。already known 只记录已知传播，nonce too low 要查真实槽位胜者，replacement underpriced 按端点交易池策略及已审批提费流程处理。广播失败不自动证明交易没有在别处传播；模拟时的 revert 也不是一份 finalized 执行失败证据，不能据此释放签后冻结。

`TransactionReceipt` 的 JSON-RPC null 在 ethclient 中表现为 `ethereum.NotFound`，表达该端点当前没有可返回的 receipt，不代表 W1 失败。`TransactionByHash` 的查无结果或 isPending 同样只是端点视图。查询可以切到经过网络和能力校验的独立端点，但仍查原 hash；发送故障也只在已有许可下重播相同 raw。发现不同 finalized hash、历史倒退或无法解释的链视图矛盾，应升级证据异常并冻结相关自动决策，而不是一直重试到某节点返回想要的答案。

## 第 6 层：订阅重连为什么必须回到耐久扫描

**面试官：** 查询重试有了，如果用 WebSocket 订阅新头或交易回执，是不是就可以省掉反复扫描？连接断了重新订阅不就行了吗？

**面试者：** 不可以。订阅只用于唤醒“该查了”，完整性靠持久 cursor 与历史扫描。Go 的新头订阅不承诺逐块可靠送达；断线、消费者太慢、缓冲问题或快速同步都可能使客户端漏掉中间块。订阅处理器应监视错误通道与连接生命周期，快速把提示交给有界调度，不在回调里等待整个结算流程，也不能以“刚收到最新头”将数据库 cursor 直接跳到最新高度。

恢复先读取 `(lastScannedHeight,lastScannedHash)`，核对该块与当前规范链关系，并从可控重叠范围补扫；每块保存 hash 和 parentHash，发现父链不连续就补父块或寻找共同祖先。区块记录、该批 observations 与 cursor 在同一个 PostgreSQL 事务提交，任何一项失败都重扫原批次。cursor 表示连续完成的范围，不是见过的最大高度；还需枚举本地所有未决 hash 查询 receipt，避免只扫 Transfer 而漏掉失败或自转取消。

从 Geth v1.16.5 起，ethclient 确有 `SubscribeTransactionReceipts`，但它依赖服务端支持相应 WS／IPC 扩展，不能假设所有 Ethereum RPC 或历史版本都可用。它是 live-only 提示，不替代历史补扫，也不能依赖一个可靠的 receipt removed 通知约定来恢复重组。应按锁定客户端版本与服务商能力探测选择是否启用；不支持时回退既有扫描与查询，不改变资金终结规则。

收到重组线索后，撤销原分支 included 的 provisional 资格与投影，保留冻结 100、原槽与全部 attempt；X1、X2 或 Xc 换分支入块时，观察按 blockHash、交易位置和必要日志位置分别保存，而不是只按 txHash 去重。这样重复订阅、回扫与迟到消息可以安全重叠，断线期间的付款义务仍有持久路径找回。

## 第 7 层：多个 RPC 的回答怎样进入同一个安全决策

**面试官：** 补扫后，节点 A 说 X1 已入块，节点 B 还查不到，节点 C 给出另一个 finalized 高度。并发 worker 把这些结果送回来时，谁有权改 W1？

**面试者：** worker 只提交带来源、查询时间、blockHash、位置和校验信息的观察，不直接修改 W1 资金终态。A 的包含事实可能有用，B 的 NotFound 不是否定，C 的高度也不能单独授予最终资格。链视图核验器要确认网络身份、区块父链，以及候选区块确属可信 finalized 检查点的祖先；多个服务商的法定人数或多数一致可以辅助发现故障，但不是 Ethereum 共识证明。无法解释的 finalized 冲突应冻结自动终结与新签名，不能按最先返回或最高高度胜出。

本地应用也要重验时效和资格。旧查询在 Xc 成为最终胜者之后返回 X1 pending，最多保存一条端点观察，不能把已终结 W1 改回 pending；旧 epoch 的 worker 也不能覆盖新主状态。观察去重使用区块与位置身份，inbox 防重复交付，W1 状态版本和 ledger 唯一业务结算键防重复终结；成功与释放争用同一结算决议，而不是各自一个互不冲突的唯一键。

在合格 finalized 成功后，本地事务一起核销冻结 100、将 T 镜像减少 100、记平台实际 ETH gas、消解对应预算、迁移 W1 终态并写 outbox。只有 finalized status=0，或已授权 Xc 为 canonical finalized winner 且无 T 转出时，才释放 100；两种独立变体仍按实际 gas 记账。普通 reorg 不动已终结账务；若证据冲突触及已接受 finalized 历史，进入事故冻结和受审计补偿，不由并发查询自动回滚终态。

## 第 8 层：怎样衡量追踪容量与恢复完成，而不是只看 RPC 成功率

**面试官：** 最后上线观察时，所有 RPC 的成功率都很高，但 W1 很久未终结。你看哪些指标，又凭什么认定故障已经恢复？

**面试者：** 我看义务的年龄和水位，而不只看调用计数。钱包维度包括最低未决 nonce、最老未决槽的年龄、签名未知数、已签未外发年龄、广播 unknown 数量与年龄、同槽候选数量、未决 T 与最坏 gas 预算。管道维度包括各类持久任务的积压和最老年龄、worker 饱和度、RPC 限流与错误分类、数据库连接等待、版本冲突、signer 查询恢复延迟；队列长度下降也可能是任务被误删，必须与完成义务数对照。

链侧分别记录订阅最后活跃时间、连续扫描水位及 hash、缺口区间、已核验 finalized 水位、最终结果待应用数量与最老年龄、账务共同对账水位。不同阶段不能只取最大高度当作一个“最终进度”。链快照已反映 W1 但账务未应用时，保留桥接义务；钱包预算按同一水位标记支出是否已反映，避免 9900 再减一次 100，或在旧 10000 快照上提前撤掉承诺。指标标签避免直接铺开所有 txHash、地址与 W1 导致无限基数，具体追踪身份放受控日志和查询系统。

恢复准入要求旧主与 signer 任期核对完成、签名审计和数据库耐久水位没有未解释缺口、全部 unknown 有归属或受影响钱包已冻结、扫描补齐且 finalized 祖先关系可信、最低槽与预算可解释、最终结果待结算能持续收敛。随后先恢复既有任务，再逐步开放新签名；单纯进程健康、队列为零或 RPC 成功都不够。主路径最终应收敛到 H 9900 T／0.9984 ETH、U 900／0，W1 一次核销；若依赖或审计仍不可信，就继续保留冻结，不能靠新 nonce 重付来让指标变绿。

## 本题收束

### 讲透的机制

- wallet actor 组织进程内状态所有权，数据库钱包行锁、唯一槽与版本约束负责跨实例权威；签名出口还需任期与审批校验。
- 有界 worker、依赖配额和持久任务共同限制容量，优先保障最老未决槽、unknown、补扫与最终结算，不靠无界 goroutine 藏积压。
- context 取消的是当前等待，不能证明提交、签名或传播未发生；SendTransaction 仅返回 error，hash 本地计算并先耐久。
- 可变 big.Int、切片和循环变量必须有明确所有权；不可变快照、独立复制、Go 1.21 显式捕获与结果版本校验缺一不可。
- RPC 分类重试、订阅能力探测、耐久 cursor、父链检查与批次事务共同闭环；最终终结仍依赖规范祖先与唯一业务决议。

### 最容易答错的边界

1. actor、mutex 和 channel 都不是跨实例付款锁，任务领取租约也不是 signer 授权。
2. nil error 不是成功付款，ethereum.NotFound 不是失败；取消 context 不会撤销已签 raw。
3. receipt 订阅确实存在不代表所有节点支持，更不代表能补历史或可靠通知所有重组移除。
4. RPC 多数不是共识，最新头不是连续扫描水位；只有 txHash 的观察去重会吞掉分支变化。
5. 并发量、最终高度和接口成功率都不能单独证明恢复完成，最老义务与缺口必须可解释。

### 能检验方案的反例

独立推演：Go 1.21 循环为 X1、X2、Xc 启动 receipt 查询，闭包误捕获同一变量，最终都只查 Xc；其间新头订阅断线又重连，程序将 cursor 直接跳到最新头，而 X1 已在漏掉的区间入块。所有存活 RPC 调用都可能成功，系统却漏掉真实付款；若再把 Xc 的 NotFound 当失败退款，就会既付款又释放。正确设计应由独立 attempt 快照、全部 hash 的耐久查询任务、重连补扫和最终结果资格共同阻断这条路径。这里只做机制推演，不创建可运行工程或声称工程测试通过。
