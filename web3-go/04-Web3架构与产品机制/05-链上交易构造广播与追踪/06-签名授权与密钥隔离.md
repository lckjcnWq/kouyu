# 大问题 6：怎样冻结交易授权、隔离私钥，并处理签名后的不可撤回能力？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |

| W1 / H / T / B | 提现意图、付款钱包、代币合约和收款地址。 | 只批准向 B 付 100 T，不是批准任意使用 H 的签名能力。 |

## 把整篇文章压缩成一个故事

小林的 100 T 提现获批后，后台不能把一句“W1 已通过”交给钱包私钥任意签。审批应固定链 1、H、nonce 42、目标 T、收款 B、整数金额、Gas 上限和费率等完整草稿，签名出口从受控来源独立核验。若 worker 把 B 偷换，即使签名恢复出的发送者仍是 H，也必须拒绝这份业务不匹配的交易。

私钥放进硬件后，平台仍只开放受限交易签名，而非任意摘要签名。签名响应丢失就按原请求找结果；返回后重新核对全部字段，先保存原字节和发送任务再广播。切主时旧任期不能申请新签名，但旧主已经持有的有效 raw 仍可能被传播，数据库换任期和撤 API 凭据都擦不掉它。

平台发现风险后暂停新权限、另批同序号取消候选，并继续跟踪原付款。最终链若保留正确付款，就按成功结算；若取消获胜，就按取消并记其真实 Gas，不写成收款成功。密钥隔离减少能创造新执行能力的人，权限围栏管未来受控动作，证据追踪管已有签名，这三件事缺一不可。

**流程位置与核心机制：** 本题覆盖“业务审批 → 不可变 draft → type 2 链上签名 → signer 权限和幂等 → 切主围栏 → raw 持久与广播隔离 → 链上最终裁决”。重点不是选择某种密钥产品，而是说明谁有权签什么、未知结果如何恢复，以及已经签出的交易为何不能被数据库状态撤销。

**必要前提：** 沿用[专题总览](README.md)的 Ethereum PoS L1、type 2、独占无委托普通 EOA H 与标准 ERC20 T 基线，不引入 AA、7702、L2 或桥。沿用 W1 向 B 提现 100 T、PostgreSQL 本地事实源和平台承担 gas 的规则；初始余额与费用参数见总览，文中数字均为教学假设而非实测。

## 第 1 层：审批必须授权具体执行能力，而不只是提现状态

**面试官：** W1 已经审批通过，是不是把 H 的私钥交给业务服务，让它调用 SDK 签名就可以了？

**面试者：** 不可以。业务审批说明可以为 W1 执行一笔指定付款，不能等同于业务服务可以用 H 签任意交易。用户受理时，requestKey 与规范化 payloadDigest 唯一绑定用户、网络、T、B、整数金额和操作语义，原子把 U 从可用 1000 T 改为可用 900 T、冻结 100 T；这个摘要不包含后来调度决定的 H 和 nonce。调度事务锁定 H，绑定唯一槽 `(1,H,42)` 并预留 100 T 与最坏 gas 预算，才建立具体执行资格。

接着完成最终构造、精确状态锚定的预执行和费用核验，持久保存不可变授权 draft 与 signer request，再允许请求签名。draft 必须覆盖 type 2、chainId 1、H、nonce 42、to T、value 0、`transfer(B,100000000)`、gasLimit 65000、maxFee 40 gwei、priority 2 gwei 与 accessList，并关联 W1、审批版本和模拟证据。完整 draftDigest 绑定这些交易字段，签名请求不能只携带“W1 审批通过”这个布尔值。

用户冻结、钱包预留和签名权限是三道不同约束：冻结防止账内重复花费，预留保证 H 的 T 与 ETH 容量，签名权限防止生成越权执行能力。任何一道缺失都不能靠另外两道补上；尤其是金额正确也不能容忍链、合约地址或收款地址被替换。

## 第 2 层：冻结 payload 要防止审批后被替换

**面试官：** 你已经保存 draft。若 worker 在送到 signer 前把 B 改成另一个地址，或者借“加速”修改金额，怎样识别？

**面试者：** signer 不应直接相信 worker 提交的任意字段，也不能只相信 worker 同时提供的“字段加摘要”。它必须从受控授权源加载不可变 draft，或核验由独立审批权限签发、绑定 draftDigest 的授权凭据，再对实际待签交易重新计算摘要。规范编码要包含类型与长度，避免拼接歧义；Go 中金额等 `big.Int` 对象应复制后冻结，避免审批对象被共享指针修改。W1 的业务摘要与具体 draftDigest 分层保存，不能把变更费用伪装成修改原记录。

对付款请求，signer 检查操作类型为付款，目标是白名单 T，value 为零，选择器是标准 transfer，地址和整数金额精确匹配 B 与 100000000，不能仅凭 calldata 前四字节放行。加速 X2 仍占 nonce 42、保持所有非费用字段不变，包括 gasLimit 65000 与 accessList；新的费用参数要在补足槽预算后形成独立审批 draft。未经授权的收款地址、金额或调用目标变化都应拒绝，而不是“复用原审批”。

取消 Xc 则必须使用独立 `operationKind=CANCEL` 和授权，交易改为同 nonce 的 H 自转 0 ETH，通常不带 data；不能让付款权限自然扩展成取消权限。取消审批可以要求付款流程暂停发起新加速，但这只是本地协调，X1、X2 的已签 raw 仍可竞争。数据库原子版本检查决定本地还能批准什么，不决定链上最后哪份交易获胜。

## 第 3 层：type 2 签名绑定哪些字段，怎样验证返回值

**面试官：** payload 冻结后，type 2 究竟签了什么？只验证 sender 是 H 是否足够？

**面试者：** type 2 的签名消息是 `keccak256(0x02 || rlp([chainId,nonce,maxPriorityFeePerGas,maxFeePerGas,gasLimit,destination,amount,data,accessList]))`。这里 amount 是原生 ETH 的 value，本例为零，不是 100 T 的最小单位金额；代币金额位于 data。签名后的交易封装再包含 yParity、r、s，chainId=1 进入签名域，不能把另一链的签名当作本链交易使用，也不能以为 W1 被标准 ERC20 自动理解或去重。

使用 Go 的 go-ethereum 时，要选择支持 type 2 的 signer，例如在相应版本中使用支持该类型的 `types.LatestSignerForChainID(chainID)`；`types.NewEIP155Signer` 只覆盖 legacy 交易，不能因为名字里有 EIP-155 就拿它处理 type 2。签名结果要按 typed transaction 规则解码，重新恢复 sender 为 H，同时核验 type、chainId、nonce、to、value、data、gasLimit、费用和 accessList 的全部字段，而不是只看某个签名验证函数返回成功。

广播 raw 应使用签名交易的 `MarshalBinary` 得到 `0x02` 类型前缀加交易体的规范字节，不能额外包一层外部 RLP 后拿去广播。用这些规范字节计算并核对 txHash，再与 draft、attempt 绑定。恢复出 H 只能证明 H 的私钥授权了这份消息，不能证明它与 W1 的审批相同；全部字段相等才把密码学事实与业务授权接起来。

## 第 4 层：密钥隔离还必须隔离签名权限

**面试官：** 你把私钥放进 HSM 或独立 signer，业务服务拿不到私钥。如果业务服务被攻破，还能不能把 H 的钱转走？

**面试者：** 如果 signer 允许已认证业务服务提交任意 digest 签名，仍然可以。密钥不可导出只解决私钥材料泄露，不能解决签名接口被滥用。因此 signer 的入口必须是受限的结构化交易授权，而不是任意哈希、任意 personal_sign 或可混淆的消息签名接口；核验调用者身份、指定网络和钱包、审批范围、槽位与预算证据、方法和金额限额。付款和取消的授权策略分开，不能给广播 worker 一张同样的签名通行证。

审批凭据必须来自独立受控权限或 signer 可验证的持久授权记录，不能只检查来自被攻破调用者的一句“数据库已预留”。对高风险变更可以要求独立审批、累计支出限额和钱包暂停策略；限额核销也要有持久并发控制，不能多个并发请求各自看见同一剩余额度。H 的服务独占约束还要覆盖运维脚本和人工工具，禁止旁路直接使用同一密钥发交易。

这仍有清晰的信任边界：如果攻击者同时控制合法审批权限和 signer 策略，系统不能保证资产安全；HSM 不会自动理解 100 T 是否合理。审计应记录调用者、draftDigest、审批版本、槽、结果和时间，保留必要的受控交易证据，但不把私钥、raw 或其他敏感执行材料写进普通日志。

## 第 5 层：签名接口幂等要覆盖响应丢失

**面试官：** 权限检查通过后，signer 完成签名却没把响应传回来。业务侧重试同一个 draft，怎样避免再次生成另一笔交易？

**面试者：** 在首次请求前，PostgreSQL 已持久保存 draft、signer request 身份及其绑定摘要。signer 以不可变 draft 身份处理幂等：同身份同摘要查询或返回原结果，同身份不同摘要拒绝；并发请求在出口内串行裁决。不能只靠“ECDSA 通常确定性”来声称幂等，因为实现可能使用随机签名 nonce，业务字段相同也可能产生不同签名字节与 hash，必须有明确的结果恢复契约。

signer 应把授权验证、签名状态与可恢复结果纳入自己的耐久审计，确保已经对外返回的结果可以按原身份找回；客户端拿到后再核验并提交 attempt X1。签名服务内部若在密钥操作完成与结果记录之间崩溃，应按其密钥后端和导出边界判断能否恢复，不能声称数据库与 HSM 天然有同一个事务。无法证明没有签名外发或无法恢复结果时，保留未知并隔离该请求，不能换一个 draft 或 nonce 绕过去。

因此业务侧超时后保持槽 42、用户冻结和钱包预算，查询原 signer request，而不是给 W1 分配 43。同槽重取相同 raw 只恢复已有执行能力；X2 是有明确提费授权的新 draft，Xc 是独立取消授权，两者不是签名调用超时的默认重试。幂等约束的是受控签名流程，不会让普通 ERC20 对新 nonce 自动业务去重。

## 第 6 层：围栏能挡新签名，挡不住已签 raw

**面试官：** signer 有幂等了，但主备切换后旧主仍可能运行。数据库 epoch 能否保证旧主再也影响不了 nonce 42？

**面试者：** 不能作这种保证。epoch 可以约束数据库中配合协议的写者，签名出口还必须核验当前任期、请求授权版本和钱包健康状态，拒绝过期实例的新请求。任期更新与签名授权接受要在出口有可序列化的裁决点，不能先读一次 epoch、隔很久才签；对于已经进入执行的在途请求，要明确等待、关闭或转入未知恢复，不能切主后假装它们不存在。

围栏生效前已经生成的 raw 不受数据库 epoch 控制。它的有效性取决于链签名、nonce、费用和状态等规则，任何拿到 raw 的旧主或第三方都可能广播；就算撤销 API 凭据、删除广播任务或把本地状态改成取消，也不能远程擦掉它。数据库 epoch 不在这份普通 type 2 交易的共识授权条件里，不能声称新主换任期就使旧交易失效。

安全接管应先停止新分配，恢复数据库槽、signer 审计和所有已签候选，再核对链上历史与最新最终性。发现本地缺记录、未知签名或外部使用 H 的冲突就 freeze 并人工核对，而不是根据 pending nonce 重新发号。围栏防止新的受控越权，恢复追踪已有能力，两种职责必须同时成立。

## 第 7 层：私钥与广播隔离后，raw 仍要当执行能力保护

**面试官：** 既然旧 raw 可能被任何人广播，那私钥与广播职责隔离还有什么价值，实际怎样落地？

**面试者：** 价值是减少可产生新执行能力的主体。signer 持有或调用私钥能力，但不需要钱包广播权限和普通业务数据库全量写权限；构造与审批服务提交受限 draft；广播 worker 只读取已经耐久提交、授权发送的 attempt，不拥有私钥，也无权临时更改 nonce、金额或费用。广播接口只接收 attempt 身份或受控 raw，不提供“签名并随意发送”的万能入口。

业务侧收到签名后先恢复 sender 和核验全部字段，将 raw/hash、attempt 与广播 outbox 在同一数据库事务中耐久提交，广播 worker 才能外发。这里的耐久还要覆盖故障恢复承诺：如果只写旧主磁盘，切到缺记录的异步副本，链上 raw 却已传播，就会丢失本地义务。因此数据库复制、备份恢复和 signer 审计要共同支持找回已经可能外发的交易，恢复失败则隔离，不能重新付款。

raw 使用受限读取和加密存储，不写日志、不放普通追踪标签或无关错误上下文；审计以 draft、attempt、hash 和状态引用为主。广播 worker 被攻破仍可能泄露或提前传播它有权读到的旧 raw，这是不能消除的剩余能力；隔离保证它不能自行创造新的合法签名，不保证它读到的交易可以被远程撤回。签名交易 txHash 可用于查询，但只有 hash 不能恢复完整 raw，所以不能为省存储而丢掉恢复所需材料。

## 第 8 层：撤权、取消和业务完成各自依据不同证据

**面试官：** 现在发现 H 的签名权限有风险，平台撤权并发出取消 Xc。怎样确定 W1 最终结果，密钥轮换能否立刻终止旧付款？

**面试者：** 撤销 signer 凭据、暂停新签名和轮换到新钱包，可以限制后续受控行动，但普通 EOA 的地址由密钥决定，更换密钥不能在同一个 H 上原地替换授权规则；迁移资产也是链上操作，存在自身 nonce、费用和竞争。已经泄露的 H 私钥风险更大，不能承诺通过应用撤权恢复其安全；即使只是泄露 raw，它仍然是可执行的旧付款能力，不能靠本地超时或密钥服务停机撤回。

Xc 是同 nonce 自转 0 ETH 的独立候选，不是让 X1、X2 消失的撤销命令。必须追踪三者在各分叉上的包含关系，核验规范链、载荷和 receipt，并等待胜出者进入已核验 finalized 前缀。在同一规范链 nonce 42 最多被一个候选消耗；若 Xc 最终获胜，才有该槽原付款不能再执行的最终依据，W1 可按取消结账，但 Xc.status=1 绝不能写成向 B 付款成功。

主例若付款最终获胜、执行成功且付款证据吻合，gasUsed 50000、有效单价 32 gwei，平台支出 0.0016 ETH，H 为 9900 T、0.9984 ETH，U 可用 900 T、冻结清零；失败或最终取消按各自实际回执记 gas，并在最终未付款依据成立后释放 U 的 100 T。账本结算使用唯一身份和版本在 PostgreSQL 中原子提交；未知期间不释放、不换新 nonce 或新钱包自动重付，因为标准 ERC20 不认识 W1。

## 本题收束：机制、易错边界与反例验证

- **机制：** 先持久授权 draft 与 signer request，审批冻结完整交易字段，signer 执行独立权限、幂等与任期校验，返回后恢复 sender 并逐字段核验，raw/hash 耐久后才交给隔离的广播 worker。
- **易错边界：** 密钥不可导出不等于接口不能被滥用；type 2 必须使用支持其签名域与序列化的实现；数据库 epoch 不能阻止已签 raw 被广播，撤权或取消请求也不等于原付款已失效。
- **反例验证：** 手工将审批后的 B 改掉，即使恢复出的 sender 仍是 H，也必须拒绝；让 signer 已签但响应丢失，只能恢复原 draft；让旧主在切换 epoch 后广播旧 raw，方案必须仍追踪它而非宣称不可能；让 Xc 最终成功，结果必须是取消而非付款成功。以上为手工机制推演，不是工程测试。
