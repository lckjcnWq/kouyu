# 大问题 9：receipt.status=1 是否就能证明 W1 已经向 B 支付 100 T？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| W1 / H / B / T | 提现意图、平台发送钱包、收款地址及代币合约。 | 目标是 T 向 B 转 100 T，不是任意一笔链上交易成功。 |
| receipt.status / 执行成功 | 回执中的交易顶层是否失败回滚。 | status=1 不自动等于正确收款，status=0 也不等于费用与序号没发生。 |
| RPC / 0x0 / 整数解析 | 节点接口、零的十六进制编码及明确单位的数值解码。 | 字符串非空不代表成功，关键字段缺失不能拿估算补成真实证据。 |
| txHash / blockHash / transactionIndex | 交易指纹、具体块身份及块内交易位置。 | 回执必须对应正确块中正确交易，同高度或同 hash 不替代包含关系。 |
| raw / draft / slot | 签名交易原字节、审批草稿和钱包序号槽。 | 对照链 1、H、42 及全部字段，不能只信数据库里的业务标签。 |
| to / value / calldata | 交易调用目标、附带原生币及合约指令。 | to=T、value=0、transfer(B,100000000)，100 T 为 6 位最小单位整数。 |
| Transfer / log.address / logIndex | 代币转账事件、发出合约地址及日志位置。 | 必须是 T 发出、H 到 B、100000000，同名事件不够。 |
| ERC-20 / 返回 bool | 代币接口及函数的真假返回值。 | 交易回执不含普通函数返回值，status=1 不能证明返回 true。 |
| eth_call / 执行追踪 | 条件试执行，以及调查实际调用过程的证据。 | 交易后再 call 不是读取原交易返回值的通用办法。 |
| BUSINESS_MISMATCH / 隔离 | 固定业务前提与所见证据不相容，暂停自动结论。 | 本例 T 成功却缺预期事件时补查，既不冒认成功也不贸然退款。 |
| revert / gasUsed / effectiveGasPrice | 执行回滚、实际工作量和有效单价。 | 失败转账不付 T，但 nonce 与费用被消耗，按该失败回执单独计费。 |
| operationKind / Xc | 授权动作类型及同序号取消候选。 | Xc 自转成功应归取消，不应要求它产生付款事件或核销提现本金。 |
| INCLUDED_PROVISIONAL / finalized | 暂定入块与共识最终链进度。 | 业务效果通过仍保留冻结，最终祖先关系成立才结账。 |
| observation / ledger / Outbox | 带块身份的观察、账本和同事务待发通知。 | 多次历史观察可并存，W1 终结靠唯一键与原子事务只应用一次。 |

## 把整篇文章压缩成一个故事

平台看到小林的 W1 回执 status=1，不能马上告诉他们 100 T 已到账。解析器先把回执和具体区块、交易位置对应起来，再核验 H 调用了 T 的准确 transfer，最后确认事件确由 T 发出，方向为 H 到 B、金额 100000000。别的合约发同名事件，或 B 总余额刚好多 100，都不能替代这笔提现的证据。

若实际是同序号取消 Xc 的成功回执，就归取消而非付款；若付款 status=0，则转账回滚，但序号和 Gas 仍消耗。教学失败变体用 30000×32 gwei，费用为 0.00096 ETH，H 仍有 10000 T、ETH 剩 0.99904。若本例固定 T 显示成功却缺预期事件，系统隔离补证，不凭猜测的函数返回值自动退款或重付。

无论成功还是失败，观察都先是可撤销的，确认属于可信最终链后才进入一次结算事务。旧分叉上的正确付款日志仍不能终结资金，重复回执也不能再记一笔费用。故事把执行状态、付款语义和最终性拆成三层：每层有证据，每层都不能被前一层的“成功”包办。

**流程位置与核心机制：** 本题位于发现入块之后、最终账务之前，回答怎样把交易级执行结果转换成可信的业务结果。重点是回执身份、规范链核验、准确交易载荷、固定代币语义和付款／取消分类；广播可靠性与最终性追踪分别由相邻母题深入。

公共网络、T 的固定语义、资金和费用口径均见[总览公共基线](README.md)，下文均为教学推演。本题仅区分 W1 同槽的付款 X1／X2 与取消 Xc，并核验它们各自在具体区块中的执行效果。

## 第 1 层：执行成功与业务成功差在哪里

**面试官：** 追踪器拿到 txHash1 的 receipt.status=1，能直接把 W1 标为提现成功并清掉冻结吗？

**面试者：** 不能。status=1 表示这笔交易的顶层执行成功结束，没有以交易级失败回滚，但它没有承诺执行的就是 W1 所授权的那次付款。转错合约、转错收款人、转错数量，甚至 nonce=42 的取消自转，都可能得到 status=1；这些都不能算“向 B 支付 100 T”。

我会先把 receipt 绑定到具体 attempt 和包含区块，核验当前规范链，再核对实际签名交易确实是 chainId=1、from=H、nonce=42、to=T、value=0、data=transfer(B,100000000)，并在 T 的固定已核验语义下检查对应 Transfer(H,B,100000000)。只有这些证据一致，才形成“付款执行成功”的暂定业务判定。

这个判定仍不是资金终态。W1 先处于 INCLUDED_PROVISIONAL，U 保留可用 900 T、冻结 100 T；之后核验包含区块进入 finalized 链前缀，才核销冻结并记最终成功。执行状态、业务语义和最终性是三个不同维度，不能用一个布尔 success 合并。

## 第 2 层：回执怎样与正确区块和交易绑定

**面试官：** 你说先绑定回执和包含区块，如果 RPC 返回的字段看起来完整，具体还需要验证什么？

**面试者：** 我会规范化并保存 transactionHash、blockHash、blockNumber、transactionIndex、gasUsed、effectiveGasPrice、status 和 logs，关联 chainId、attemptId、来源和观察时间。status 的 0/1 要按 RPC 编码解析，不能把字符串 "0x0" 当作非空即真；gas 数值按整数和明确单位处理。缺关键字段或互相矛盾的响应只能补查或隔离，不能用估算值填出“真实回执”。

随后按 blockHash 取区块，检查其 number 和 transactionIndex 对应的交易哈希确为该 attempt，再用可信链视图核验这个区块是否规范。只知道 blockNumber 不够，同一高度可能先后对应不同分叉；同一个 txHash 也可能在重组后被另一个区块重新包含。因此 observation 应按 chainId、txHash、blockHash 等区块身份管理，不能仅凭 txHash 覆盖旧观察或宣称重复输入都完全相同。

若回执来自 RPC A、按高度查到的块来自 RPC B，两次请求之间可能刚好发生重组或节点进度不一致。发现 blockHash 不符时，要固定哈希重取相关区块、回执和链头，复核共同链视图后再判断，不把一组跨时点响应拼成确定事实。信任的执行节点和数据源能力也是前提；多家返回一致并不等于本服务重新验证了共识。

## 第 3 层：业务证明为什么同时需要载荷和日志

**面试官：** 区块核验通过，而且日志里看到了给 B 的 Transfer，为什么还要重新核对实际交易载荷？

**面试者：** 因为日志只能在确定的调用、合约和语义下解释。先从实际签名交易或持久 raw 恢复发送方和完整字段，核对它确实属于 W1 的授权 draft 和 slot，确认 type2、chainId=1、H、nonce=42、to=T、value=0、准确的 transfer 选择器和参数，金额为整数 100000000，而不是 100 或 100000000000000000000。费用和 gasLimit 也要对应已批准的 X1 或 X2，不凭哈希标签代替字段校验。

再限定 receipt.logs 中 log.address 必须是 T，事件签名必须是标准 Transfer(address,address,uint256)，索引参数为 from=H、to=B，非索引金额解码为 100000000，并核对日志所属 transactionHash、blockHash 和交易位置。另一个合约也可以发同名事件，钱包余额变化也可能来自其他交易，所以“有 Transfer 字样”或“B 当前多了 100”都不是这笔 W1 的充分证明。

在本题已核验、固定行为的 T 上，准确调用与匹配事件共同解释了这笔 100 T 的执行效果。日志来自交易执行后的回执，不是广播返回 hash 时就能取得的证据；预执行 eth_call 得到的结果也不能冒充实际入块日志。这里没有扩展到任意路由、任意代币或任意嵌套调用，只证明当前固定付款模型。

## 第 4 层：没有匹配事件时为什么不能随便判失败

**面试官：** 实际载荷没错、status=1，却没有匹配的 T.Transfer；有人说 ERC20 返回了 false，你怎样区分并处置？

**面试者：** 首先，交易级 receipt 不携带 Solidity 函数的普通返回值，不能从 status=1 推导 transfer 返回 true，也不能从缺日志推导它一定返回 false。EIP-20 要求调用方处理 false；部分实现可以返回 false 且顶层不 revert，不能仅凭返回 false 就把它归为非标准。本文白名单 T 固定为余额足够时按标准转账并发出事件的已核验实现，所以 status=1 却缺少预期事件的矛盾仍需隔离，不能据此悄悄改写当前付款判据。

对本题 T 来说，准确载荷、status=1 与缺少预期事件互相矛盾。我会先重新获取完整回执，排除提供者截断、错误区块或重组竞态；仍不一致就标记 BUSINESS_MISMATCH 并隔离 W1，冻结继续保留，同时调查合约身份或行为是否偏离白名单假设。没有确定付款证据时不能冒认成功；没有确定未付款证据时也不能自动解冻重付。

若业务将来需要支持非标准代币，应单独建立合约行为适配和明确证明规则，必要时使用可信执行追踪或交易位置前后的状态差异辅助调查。交易后再做一次 eth_call 不是提取原交易 return 的通用方法，区块前后总余额差也可能混入其他交易。不能用这些方便查询替代已经发生的那次执行事实，更不能把异常代币当成本题 T 的正常路径。

## 第 5 层：status=0 对金额、nonce 和费用分别意味着什么

**面试官：** 缺日志的 status=1 要隔离，那么规范链上确定 status=0 的付款，是否就能认为什么也没发生？

**面试者：** 也不能说“什么都没发生”。status=0 表示该交易执行失败，调用产生的代币状态和日志会回滚；在本题直接调用标准 T 的模型里，不会完成这笔 100 T 转账。但交易已经纳入区块，H 的 nonce 被消费，实际执行 gas 仍需支付。这与未入块、查询为 null、广播超时完全不同。

费用必须使用该失败回执的 gasUsed×effectiveGasPrice，不能照抄成功样本的 50000 或估算 52000，也不能一律扣满 gasLimit=65000。作为独立失败变体，假设实际 gasUsed=30000、单价=32 gwei，费用为 0.00096 ETH；H 的 T 仍是 10000，ETH 变为 0.99904。回滚不会把 gas 退回到“完全没消耗”，也不会恢复 nonce=42。

此时业务先记 EXECUTION_FAILED_PROVISIONAL，保留 U 的冻结，等该失败观察进入 finalized 前缀，才结为 FAILED_FINAL 并释放 100 T，U 可用恢复 1000 T、冻结 0。若这张失败回执随后被重组出去，不能把它当作永久未付款证据；要重新追踪该槽所有 attempts，可能在新链上出现成功付款。

## 第 6 层：同槽取消怎样避免被误当成付款成功

**面试官：** 你强调 status=0 也消费 nonce；现在消费 nonce=42 的却是 status=1 的 Xc，怎样避免通用解析器把它当作 W1 成功？

**面试者：** 解析器必须先从授权 draft 和实际 payload 确定 operationKind，再解释 status。Xc 是经过独立审批的同槽取消：from=H、nonce=42、to=H、value=0、data 为空，且费用与 gasLimit 符合取消授权。它的 status=1 表示这笔自转执行成功，不是 T.transfer 成功，不应要求它产生付款 Transfer，更不能因为它与 W1 关联就核销用户的提现本金。

我会把结果记录为 CANCEL_EXECUTED_PROVISIONAL，保留所有候选的观察。只有 Xc 被核验为最终规范获胜者，才把业务结为 CANCELLED_FINAL，含义为取消而非付款成功；释放原 100 T，U 可用恢复 1000 T。平台按 Xc 的真实回执计 gas，H 的 T 不因自转 0 ETH 减少。

同样，找到一个未登记的自转交易也不能自动归为合法取消：必须解释其签名授权和槽归属，否则进入异常签名调查。Xc 已广播或暂时入块都不会撤销 raw1/raw2；X1 的旧回执、X2 的新回执和 Xc 的取消回执必须由规范链与最终性裁决，不能按“最后收到哪一条消息”覆盖业务结果。

## 第 7 层：判定证据怎样安全交给终结器

**面试官：** 现在解析器能区分付款、失败和取消了，怎样交付判定，才能防止回执重复、重组或进程崩溃导致重复记账？

**面试者：** 我会把原始 receipt、实际交易核验结果、匹配日志的 logIndex、业务判定及规则版本，连同 chainId、txHash、blockHash 和槽身份持久化为 inclusion_observation。它表达“在这个区块中观察到什么”，而不是直接改 W1 终态；同一观察重复交付幂等，同 hash 在不同块的观察则分别保存。槽的当前 winner 是可撤销投影，业务资金终结是另一个独立操作。

终结前重新核验包含区块处于可信 finalized 区块的祖先链中，不只检查高度。核验时遇到跨 RPC 链视图不一致，要固定区块身份补查，证据不完整就等待；safe 或固定 12 确认不能静默替代 finalized，提供者不支持对应标签必须显式告警。普通重组撤销旧观察的有效关联和暂定投影，并重查整个 attempt 集合，而不是保留旧成功标签继续结算。

证据成立后，PG 事务锁定 W1、slot 和 reservation，校验终结版本及唯一结算键，一起写 ledger、冻结核销或释放、实际 gas 与钱包预算终结，以及 outbox。提交前崩溃就全部重试，提交后事件发送失败则补发同一事件。链证据解决“发生了什么”，本地事务解决“只结算一次”，二者不能相互替代。

## 第 8 层：怎样用完整数值检验最终判据

**面试官：** 按你这套证据与事务边界，完整复述 W1 的正常结果，并指出如果只认 status=1 会出现什么具体错误？

**面试者：** 正常路径中，X1 在规范链执行，准确载荷为 nonce=42、to=T、value=0、transfer(B,100000000)，status=1，T 发出匹配的 Transfer。入块 baseFee=30 gwei，maxFee=40、tip=2，所以有效单价是 32 gwei；gasUsed=50000，实际费用 0.0016 ETH。65000×40 gwei=0.0026 ETH 是签名前的上限预算，不是最终扣费，也不从用户的 100 T 里折扣。

先观察 INCLUDED_PROVISIONAL，U 仍可用 900 T、冻结 100 T；可靠 finalized 祖先证据成立后，事务核销冻结一次，最终 H 为 9900 T、0.9984 ETH，B 增加 100 T，U 可用仍为 900 T、冻结 0。若是失败或取消最终获胜，则 T 未付款、释放冻结，gas 按各自回执另算；它们不能套用正常成功的资产结论。

最直接的反例是 Xc 自转 0 ETH 得到 status=1，通用程序据此消耗 U 的冻结并报告“B 已收到 100 T”。链上 B 实际没收款，平台却核销了用户负债。另一个反例是付款在旧分叉 status=1，重组后该观察不再规范；即使日志齐全，也不能继续终结。只有把操作类型、执行效果、区块身份和最终性一起交给幂等事务，才能闭合这些反例。

## 本题收束

- **讲透的机制：** 回执先绑定具体交易和区块，核验规范链，再以准确载荷、可信 T 的 Transfer 和固定代币语义解释业务效果；付款、执行失败与取消分开分类，最终证据成立后才在 PG 中一次性终结资金并生成 outbox。
- **易错边界：** status=1 不等于任意合约目标完成，交易级 receipt 没有 ERC20 函数返回值，广播阶段也拿不到实际回执日志。status=0 不转 T，却耗 gas、占 nonce；取消 status=1 是 CANCELLED 而非付款成功。null 不是失败，同 hash 不等于同区块观察，单看高度不证明 finalized。
- **可推演反例：** 给系统一张来自真实 T、字段都匹配的成功回执，但让其 blockHash 位于被重组掉的分叉；另一张 Xc 回执处于最终规范链。正确系统保留旧观察却不认旧付款，最终取消并释放 100 T，只计 Xc 的规范链 gas。若系统仅按 txHash 去重、只看 status 或只比较高度，就会把旧成功保留下来，导致业务和实际收款不符。
