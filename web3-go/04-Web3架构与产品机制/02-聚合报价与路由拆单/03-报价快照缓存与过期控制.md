# 大问题 3：聚合报价怎样固定链上快照、设计分层缓存，并在过期与重组后阻止旧结果继续执行？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| ExactIn、quote 与非托管 | ExactIn 固定花多少，quote 是估算单；非托管表示资产还在用户钱包。 | 10,000 USDC 报价不锁池价、不冻结资金，“有效 15 秒”不是履约保证。 |
| EVM、ERC20 与 rebase | EVM 是以太坊虚拟机，ERC20 是代币标准，rebase 会自动调整余额。 | 本文限同链普通无税、无 rebase 代币，不能借用其他产品的状态规则。 |
| USDC、WETH、raw、decimals | USDC 是稳定币，WETH 是包装 ETH；raw 是最小单位，decimals 是小数位。 | USDC 6 位、WETH 18 位，金额和元数据必须一起绑定快照。 |
| chainId、blockNumber、blockHash | 分别标识链、区块高度和具体区块指纹。 | 相同高度可能有不同分支，不能只存块号来区分状态。 |
| latest 与 RPC | latest 是节点当前最新状态，RPC 是读节点的接口。 | 同时发两个 latest 请求，也可能读到不同区块或不同分支。 |
| EIP-1898 与 requireCanonical | 按区块哈希查询状态的接口约定，以及查询时要求仍在规范链的选项。 | 先验证节点能力；不支持时显式降级或拒绝，不伪称严格同块。 |
| AMM v2/v3 | AMM 是自动做市商；v2 用储备报价，v3 用集中在区间内的流动性。 | 完整快照不只是两组储备，还包括协议类型、费率、方向和适配器版本。 |
| tick、bitmap 与 liquidity | v3 的价格刻度、已初始化刻度索引及活跃流动性。 | 需要覆盖实际报价跨越的范围，缺一段不能用旧数据或零值补齐。 |
| 拓扑缓存与金额缓存 | 前者记“有哪些路”，后者记“这个状态下，这个数量换多少”。 | 同交易对的 100 USDC 不能复用 10,000 USDC 的输出。 |
| TTL 与执行资格 | TTL 是缓存存活时间；执行资格是当前还能否推荐用户签这份计划。 | 未过期不代表仍可签；池禁用、策略变化或分支失效都可提前淘汰资格。 |
| policyVersion 与计划哈希 | policyVersion 是规则版本，计划哈希是有序执行内容的指纹。 | 不允许只把旧报价块号改新，或换接收者后继续使用原绑定。 |
| caller、recipient、router、spender | 分别是付款调用者、接收者、执行合约和获准拉款地址。 | 完整报价缓存必须区分这些上下文，池报价命中不等于执行上下文命中。 |
| allowance、nonce 与模拟 | allowance 是转账额度，nonce 是交易序号，模拟是指定条件下试执行。 | 命中缓存后仍须适用复核，但复核成功也不预留资源。 |
| minOut、bps、deadline 与 gas | 最低收币量、万分之一比例、执行截止时间和另付的执行费。 | 50 bps 下限为 4911111221125379960 raw WETH，不减 gas，由链上检查。 |
| 重组、parentHash 与投影 | 重组是规范分支变化；parentHash 指向父块；投影是链上证据的本地展示。 | 沿父块发现分叉，撤销旧报价的新执行资格与失效成功展示，已广播交易继续单独追踪。 |
| CEX 与 RFQ | CEX 是中心化交易所，RFQ 是询价交易机制。 | 它们的快照与有效性协议另建，不继承本文同笔原子执行承诺。 |

## 把整篇文章压缩成一个故事

小林想换 10,000 USDC，页面给了一份“15 秒内有效”的报价。系统不是记下两次 latest 读到的数字就算完，而是先选定一个区块哈希，把 A 池 600,000 USDC／300 WETH、B 池 400,000／200，以及 0.3% 费率、代币精度和方向一起收进完整快照。它据此算出 6,000／4,000 拆分的 4935790171985306493 raw WETH；这 15 秒只描述服务如何复用结果，并没有锁住市场。

下一位用户只换 100 USDC，系统可以复用有哪些池的拓扑资料，却不能复用小林的金额结果。即使小林自己的缓存命中，也要核对付款人、接收者、Router、拉款地址和实际指令，重新检查适用的余额、授权与模拟条件，再让合约按 4911111221125379960 raw 的下限和截止时间裁决。费用另付，旧计算能复算也不等于当前还适合签名。

报价才过去三秒，原区块却被重组移出了规范链。系统保留旧快照做审计，但立即停止把旧报价给新签名使用，并从新分支重算；已经传播的交易则不能靠删缓存撤回，必须追原 hash 和 nonce。最后若交易回滚，系统用原快照、执行证据和检查时间区分行情变化、授权竞争还是服务混读，而不是把所有问题都推给“报价过期”。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于读链、候选估算、报价复用与签名前复核之间，重点是状态一致性、缓存身份和失效责任；Go 内存所有权与容量治理另见第 13 题，不在此展开。公共前提和字段约定见 [README](README.md)：同链 EVM 非托管 ExactIn，普通无税、无 rebase ERC20，用户自付 gas，无平台费或返佣。能力覆盖 v2/v3 AMM，贯穿例只有两个 v2 直接池；单 Router 固定顺序全量执行所有腿，无部分填充，全部成功或全回滚。

## 第 1 层：先定义报价快照到底冻结了什么

**面试官：** 报价返回“有效期 15 秒”，能不能理解为这 15 秒内池价和用户资金已经固定？

**面试者：** 不能。快照冻结的是“我们依据哪一份状态计算”，不是链上价格或资产。报价至少记录 `chainId/blockNumber/blockHash`，这样才能说清数字来自哪个分支的哪个区块；15 秒只是服务的新鲜度策略，池状态可能下一秒就改变。余额、池储备、allowance、nonce 和 receipt 的权威仍在链上，Go 只保存观察与计划。quote 不锁价、不占资，allowance 也不是预留。教学例输入 10,000 USDC，即 `10000000000 raw`；A 储备为 600,000 USDC/300 WETH，B 为 400,000/200，均收 0.3% 池费。这些储备必须带快照身份，不能只存一个脱离区块的“当前价格”。服务有效期是复用策略，不是池向用户作出的承诺。

## 第 2 层：并发 latest 读取并不构成一致视图

**面试官：** 既然需要区块身份，把 A、B 的储备并发查询 latest，再记录请求开始时的区块号，够不够？

**面试者：** 不够，两个请求可能落在不同高度、不同节点，重组时还可能读到同高度不同哈希。先选定区块头作为锚点，再让相关读取都指向该 blockHash；对支持的方法使用 EIP-1898，并要求适用的规范链校验，随后核对锚点仍然有效。RPC 批量请求也不天然是事务快照。如果供应商不支持按哈希读取，必须显式降级或拒绝：降级可固定区块号并前后核对哈希，发现变化就丢弃重试，同时标明这不是同等级保证。负载均衡到不同节点时前后检查仍可能遗漏中间分支变化，不能把这种方案伪装成严格快照；要求严格一致时直接拒绝。

## 第 3 层：快照完整性不止是两组储备数

**面试官：** 所有储备都锁在同一个 blockHash，就能放心报价了吗？换成 v3 还要补什么？

**面试者：** 还要绑定池地址、token0/token1、方向映射、fee、代币 decimals、池类型以及适配器能力和版本，否则同一储备可能被错误解释。本例 USDC 为 6 位，WETH 为 18 位，0.3% 费率对应 v2 整数公式中的 997/1000；元数据换错会让“精确整数”算出错误数量。v3 不能只缓存 slot0 与当前 liquidity，必须取得报价可能跨越范围内完整的 tick、bitmap 和流动性净变化，跨到缺失边界就补齐后重算或判为不可报价。快照发布前检查依赖齐备，失败则整个相关候选不可用，不能一半用旧 ticks、一半用新池状态，或把缺数据当作零流动性。

## 第 4 层：拓扑缓存与金额报价缓存必须分层

**面试官：** 快照已经完整了，同一 USDC/WETH 交易对是否只需要一个缓存键，所有金额都复用？

**面试者：** 不行，拓扑缓存回答“有哪些池和可用路径”，金额报价缓存回答“这份状态下投入多少能换多少”。前者按链、资产和发现版本管理，并验证快照中的池可用性；后者至少包含 chainId、代币地址、方向、amountInRaw、blockHash、policyVersion 和模型版本，不能只放交易对。本例 10,000 USDC 的 6,000/4,000 拆分得 `4935790171985306493 raw`，这个结果不能复用到 100 USDC。纯池计算结果可按其完整依赖复用，但若返回完整可执行 quote，还必须区分 caller、recipient、minOut、deadline、router/spender 和有序路线。一个池拓扑命中，不代表金额、费用或执行上下文也命中。

## 第 5 层：区分自然过期、依赖变化与执行淘汰

**面试官：** 缓存键带了 blockHash，那是不是设置 TTL 就够了？新区块到来时，旧缓存应直接删除还是继续返回？

**面试者：** 应区分“历史计算是否可复算”和“是否允许给新请求使用”。相同 blockHash 的纯计算仍有审计价值，但新报价入口要检查年龄、允许落后区块数、规范链归属，以及策略和执行能力是否仍有效。TTL 只控制复用窗口；池被禁用、Router 策略更新或数据依赖不完整，都可能要求立即淘汰执行资格。刷新采用新快照组装完整结果后再发布，不能原地把旧报价的 blockNumber 改成最新。并发刷新失败时，只有产品明确允许并标记陈旧展示才可返回旧结果，不能继续标为可签；按新锚点生成报价与保留旧计算证据是两件事。

## 第 6 层：缓存命中后仍要绑定执行与重新复核

**面试官：** 缓存命中且尚未过期，能不能直接让钱包签名？缓存里的哪些字段必须与 calldata 对齐？

**面试者：** 完整 quote 绑定 `chainId/blockNumber/blockHash、policyVersion、requestHash、orderedPlanHash`，以及 `caller/recipient/amountIn/minOut/deadline、router/spender/calldataHash`，签名前逐项核对；改变任一执行字段就重新构造，不能换接收者还沿用旧绑定。余额、allowance、nonce 和 ETH gas 余额还需做适用的新鲜检查，模拟完整交易，但这些检查也不是预留或未来成功承诺。本例 50 bps 的 `minOut=4911111221125379960 raw`，不扣 gas。Router 校验本次实际总输出和链上 deadline；前端倒计时过期可阻止继续操作，没过期却不代表合约受保护。交易排队超过 deadline 仍可能回滚并耗 gas。报价服务撤销执行资格只能阻止后续签名入口继续推荐，不能撤回已经签好并传播的交易，更不能替用户取消链上授权。

## 第 7 层：重组必须撤销旧分支的执行资格

**面试官：** 一份报价只生成了 3 秒，TTL 尚有余量，但它的 blockHash 被重组移出了规范链，能否继续使用？

**面试者：** 不能，分支失效优先于时间窗口。新头处理器检查 parentHash 连续性，发现分叉后定位共同祖先，将旧分支快照及其报价标成不可用于新执行，再从新分支重建。以 blockNumber 为唯一身份会把同高度两个区块混在一起，因此缓存和依赖都要保留 blockHash。已广播的交易不能靠“删缓存”撤回：继续查原 txHash 和 nonce，receipt 可能消失，交易也可能在新分支重新入块；已展示的成功结果要支持撤销。处于签名前的报价则应重新获取并让用户确认新计划。历史旧分支数据可以保留用于审计，但必须清楚标注非规范链，不能重新包装成新报价。

## 第 8 层：把缓存命中变成可解释的证据链

**面试官：** 用户投诉“页面仍显示有效，最后却回滚”，怎样证明是市场变化、授权竞争还是服务错误，而不是一句“区块链不确定”？

**面试者：** 保存报价锚点、完整依赖、逐腿 raw 输入输出、策略版本、构造绑定、命中或重算原因与检查时间，再关联实际 txHash、nonce、receipt 及执行区块。可先在原快照复算：A 输入 6,000 得 `2.961474103191183896 WETH`，B 输入 4,000 得 `1.974316068794122597`，合计应一致；随后核对执行时授权、储备、deadline 和回滚原因，不能把缺证据直接归咎市场。quote、broadcast、receipt、confirmed、finalized、展示分别记录进度。广播 RPC 超时属于未知，先查原交易，不新发重复兑换。这样能区分可复算但已过时、依赖混读以及执行状态变化三种完全不同的问题。

## 本题收束

- **讲透机制：** 固定分支身份，补齐池模型依赖，再分层缓存；缓存命中仍需执行资格检查，过期与重组都不能靠更新显示时间解决。历史可复算性与新执行可用性是两条独立属性。
- **容易答错的边界：** latest 并发不是一致快照；EIP-1898 不支持时不能隐式降级；v3 当前价格不代表所需 ticks 完整；TTL 和前端时间不是合约保护。单笔原子性不涵盖独立 approve，swap 回滚仍消耗 gas。
- **反例与验证：** 在 A、B 读取之间切换区块；让同高度 blockHash 改变；让 100 与 10,000 USDC 请求同时命中；让 TTL 尚未结束但 Router 策略被禁用。应分别丢弃混合快照、隔离旧分支、区分金额键、撤销执行资格，而不是返回一个貌似精确的旧数字。跨链、CEX、RFQ 有各自快照和有效性协议，不复用本题原子执行承诺。
