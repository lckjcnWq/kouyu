# 大问题 1：同链非托管 DEX 聚合交易从报价到最终展示，谁决定结果，系统怎样闭环？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EVM 与同链 | EVM 是以太坊虚拟机；同链指所有操作在同一条链内完成。 | 本文的整笔回滚不覆盖跨链交易。 |
| DEX 聚合器与非托管 | DEX 是去中心化交易所；聚合器帮用户比较兑换渠道，非托管表示不替用户保管资产。 | Go 服务提出路线，不能在自己的数据库里冻结钱包资金。 |
| ERC20、USDC、WETH | ERC20 是代币接口标准；USDC 是稳定币，WETH 是包装后的 ETH 代币。 | 普通代币无转账税、无自动余额重设；USDC 用 6 位、WETH 用 18 位精度。 |
| ExactIn 与 raw | ExactIn 表示固定花多少输入币；raw 是最小单位整数。 | 10,000 USDC 对应 10,000,000,000 raw，不是固定能收到多少 WETH。 |
| quote | 根据一份已知状态算出的兑换建议。 | 不锁价格、不占余额，也不能记作已成交。 |
| 快照与 blockHash | 快照是计算使用的状态底稿；blockHash 是特定区块的指纹。 | 必须说明来自哪条链、哪个高度、哪个分支，不能混用多个 latest。 |
| AMM v2/v3 | AMM 是自动做市商；v2 常用储备公式，v3 把流动性分布到价格区间。 | 主例只有两个 v2 池；v3 还要补齐实际跨越范围的 tick 等数据。 |
| Router、腿与原子执行 | Router 是执行兑换计划的合约；腿是一份分配；原子执行指同笔交易全成或全退。 | A 6,000、B 4,000 按固定顺序执行，不能保留成功的一腿。 |
| allowance、owner、spender、approve | owner 是代币所有者，spender 是获准拉款地址，allowance 是可转走额度，approve 是授予额度的操作。 | 授权不是预留；独立授权交易不会随着后面的换币失败而撤销。 |
| calldata 与计划哈希 | calldata 是实际交给合约的指令；哈希是用来核对内容的指纹。 | 展示路线、接收者、金额和钱包签名内容必须对应，哈希不替代合约检查。 |
| minOut、bps 与 deadline | minOut 是最低收币量；1 bps 是万分之一；deadline 是链上执行截止时间。 | 50 bps 得到 4.911111221125379960 WETH 下限，由合约执行时检查。 |
| gas | 用户另付的链上执行费。 | 不从 WETH 下限扣除；换币回滚仍可能付费。 |
| nonce、txHash、API 与 RPC | nonce 是发送者交易序号，txHash 是交易指纹，API 是程序接口，RPC 是访问节点的远程调用接口。 | 接口返回报价不是成交；广播超时应围绕原交易及同序号替换继续查询。 |
| EIP-1898 与池数据完整性 | EIP-1898 支持按区块哈希查询状态；完整性要求模型用到的数据都已取得。 | 节点不支持就显式降级或拒绝，v3 缺实际范围的 tick 数据不能装作完整报价。 |
| CEX 与 RFQ | CEX 是中心化交易所，RFQ 是询价交易机制。 | 它们的履约和部分完成规则另建，不能照搬本文单笔链上全成全退。 |
| receipt、confirmed、finalized | receipt 是执行回执；confirmed 是达到产品确认策略；finalized 是按链规则达到最终性。 | 有回执不等于已不可逆，成功回执也可能随区块重组失效。 |
| 重组与投影 | 重组是规范链分支变化；投影是根据链上证据生成的本地展示。 | 旧成功证据失效就撤回展示并重新追踪，不再发一次换币补页面。 |

## 把整篇文章压缩成一个故事

小林想把 10,000 USDC 换成 WETH。Go 服务在同一个区块快照中读取 A 池 600,000 USDC／300 WETH、B 池 400,000／200 的储备，两池手续费都是 0.3%。它建议先向 A 投入 6,000、再向 B 投入 4,000，估得 4.935790171985306493 WETH。这是一张有计算依据的建议单，不是已经兑换，更不是替小林把钱或池子锁住了。

小林核对拉款地址、接收者和最终合约指令，必要时先单独授权，再签名换币。计划把最低收币量设成 4.911111221125379960 WETH，并写入截止时间。真正执行时，由 Router 检查本次收款增量和完整输入；第二腿失败，第一腿也撤销，但已消耗的 gas 和先前独立成功的授权不会一起消失。即使刚查过余额和授权，其他交易先执行仍可能让这笔换币失败。

广播时节点突然超时，系统没有替小林换一个 nonce 再做一次，而是保存原交易身份、追踪原 hash 及同 nonce 候选。查到成功回执后，还要核对规范链归属和确认阶段；若成功块被重组，页面撤回旧结果并继续追踪。故事的终点不是“接口返回成功”，而是计划、真实执行、确认依据和页面展示逐层对得上。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题串起请求、授权、快照、计划、签名广播、链上执行、确认和展示，重点区分“服务给出建议”与“链上改变资产”。公共前提、数值和字段约定见 [README](README.md)。主线为同链 EVM、普通 ERC20、ExactIn；Go 只读估算并生成计划，主能力覆盖 v2/v3 AMM，贯穿例仅用两个 v2 直接池。用户自付 gas，无平台费或返佣；单 Router 按固定顺序全量执行所有腿，无部分填充，全部成功或全部回滚。

## 第 1 层：先确定资产与执行结果的权威边界

**面试官：** 用户输入 10,000 USDC，聚合器返回了一条拆单路线。是 Go 服务决定成交，还是链上决定？架构应该怎么拆？

**面试者：** Go 决定“建议执行什么”，链上决定“实际上发生什么”。接入层规范化链、代币、输入量和接收者；快照层固定池状态，适配器计算候选，路由层按同一费用口径比较，构造层生成 Router 调用，钱包负责授权和签名。Router 在实际执行状态中读取和操作池，校验执行保护并转移资产。观察层再依据 receipt、区块归属和日志建立投影。因此余额、池储备、allowance、nonce、receipt 的权威都在链上，服务库只保存请求、报价、交易追踪和可重建视图。API 返回 quote 不是内部记账成交，更不能据此扣一个“平台钱包余额”。

## 第 2 层：非托管报价为何不能预占用户资金

**面试官：** 既然 Go 只给建议，同一钱包同时拿到两份各花 10,000 USDC 的报价，服务能否先冻结余额，保证两份都能成交？

**面试者：** 不能在非托管基线上声称冻结链上余额。报价读取到余额足够，只说明那个区块上的观察成立；quote 既不锁价，也不占用资金。用户仍能转账、换币，其他应用也可能消耗余额。服务可以对本平台请求限流、提示冲突并关联同一业务意图，却不能把本地“已预留”当作合约可履约凭据。两笔交易最终按链上顺序执行，后一笔可能因余额不足回滚。本例输入应明确为 `10,000,000,000 raw`，不能把两次成功报价解释为已获得两份资金承诺。若产品要求硬预留，需要新的锁仓或托管协议，那已经改变本题公共前提。

## 第 3 层：授权检查不能消除钱包并发竞争

**面试官：** 不能冻结余额，那检查 Router 的 allowance 达到 `10,000,000,000 raw`，是否就能保证这笔换币可执行？

**面试者：** 仍不能。allowance 是 owner 对 spender 的转账上限，不是为某份 quote 保留的额度；余额与授权是两个独立条件。必须核对链、USDC 地址、owner 和实际 spender，不能只看钱包展示的某个“已授权”标志。用户可能撤销授权，另一笔交易也可能先花掉余额或额度，执行时的 `transferFrom` 才给出最终裁决。如果需要独立 approve，先明确它是另一笔交易，确认后重新检查并重做适用模拟；approve 成功而 swap 失败，授权不会随 swap 撤销。nonce 只给同一发送者的交易排序，不会给两份报价分配资产，也不能阻止其他 spender 的竞争。

## 第 4 层：一致快照决定估算可信度，不决定成交价格

**面试官：** 既然执行时还会变化，报价层怎样做到至少“算得有依据”，而不是把不同时间的池状态拼起来？

**面试者：** 先固定 `chainId/blockNumber/blockHash`，再把池结构、fee、decimals 和适配能力与储备一起绑定快照；v3 还必须有模拟所需范围内完整的 tick、bitmap 和流动性状态。并发请求都读 `latest` 不等于同一视图，应使用支持的 EIP-1898 按哈希读取；不支持时显式降级或拒绝，不能偷偷混读。教学池 A 为 600,000 USDC/300 WETH，B 为 400,000/200，费率均为 0.3%。同一快照中，6,000/4,000 拆分估得 `4.935790171985306493 WETH`，只是已评候选中的赢家，不是全路由全局最优。快照让结果可复算，却不会阻止后续交易改变储备。缺少任一必要依赖时，要拒绝受影响的候选并暴露原因，不能返回一个看似完整的最佳报价。

## 第 5 层：把建议计划固化成可审计的执行保护

**面试官：** 快照不能锁价，那怎样防止用户签名时路线被换掉，或者打包时拿到远低于报价的结果？

**面试者：** 报价必须绑定 `policyVersion、requestHash、orderedPlanHash`，并连同快照绑定 `caller/recipient/amountIn/minOut/deadline`、`router/spender/calldataHash`。规范化编码后计算哈希，确保“展示的计划”与“钱包签的 calldata”能逐项核对；哈希本身不替代合约检查。Router 按 A 后 B 执行，输入分别为 6,000、4,000 USDC，合计必须等于总输入，任何腿失败都回滚，不能静默跳腿。本例 50 bps 滑点得到 `minOut=4911111221125379960 raw`，以接收者本次实际新增输出核验总下限，并检查链上 deadline。gas 由用户另外支付，不从这个 WETH 下限中扣除。执行下限约束的是整条路线的真实交割，不能把某腿的估算输出记为已到账，也不能用 Router 的既有代币余额补足本次结果。

## 第 6 层：广播超时属于未知结果，不能重新兑换

**面试官：** 用户签了上述 calldata，广播 RPC 超时。后端能否认为失败，换一个 nonce 再发一次？

**面试者：** 不能，超时只表示没有拿到响应，原交易可能已经进入节点、传播甚至打包。发送前持久关联业务意图、`chainId/caller/nonce`、签名交易的本地 `txHash` 与 calldataHash；恢复时先查原 txHash、receipt、账户 nonce，并识别是否存在同 nonce 替换。必要时重播相同签名原文，而不是新 nonce 再兑换。不同节点暂时查不到也不证明未广播。若钱包选择提费替换，要追踪同 nonce 的交易族，并验证替换是否仍是同一意图；“取消交易”也可能输给原交易。只有链上证据能收敛为成功、回滚或被替换，不能用 HTTP 状态把未知结果变成确定失败。

## 第 7 层：receipt 成功还要经过确认与重组处理

**面试官：** 查到原交易 receipt 且 `status=1`，是否可以马上宣布资产不可逆到账？如果 A 已执行而 B 失败呢？

**面试者：** 单笔交易里 A 成功、B 失败会使整笔 swap 回滚，不存在保留 A 成交的部分填充；但失败交易仍耗 gas，先前独立 approve 也不回滚。`status=1` 则表示在 receipt 指向的区块上执行成功，仍需核对 blockHash 是否处于规范链，再按产品策略进入 confirmed，最终跟随链的 finalized 语义。达到若干确认与达到协议最终性不能混写。重组时保留原观察记录，撤回旧分支的成功投影，重新查交易是否在新分支入块；它可能重新 pending，也可能执行结果改变。即使一个分支上成功过，也不能靠历史 receipt 直接宣布永久完成。

## 第 8 层：用分阶段完成契约闭合展示与对账

**面试官：** 如果 receipt、确认进度和页面刷新不同步，面向用户的“交易完成”最终应该承诺什么？

**面试者：** 我会明确区分 quote、broadcast、receipt、confirmed、finalized、展示六个阶段，receipt 阶段还要分成功与回滚。查询返回当前交易身份、区块证据、确认策略及投影进度，不能只给一个含混的 success。观察服务按区块扫描并以 `chainId/blockHash/txHash/logIndex` 识别日志，支持去重、重扫与撤销旧分支投影。普通 ERC20 下核对 recipient 的本次输出、输入消耗和池事件，gas 则根据 receipt 单列；对账要采用共同链上截止点，不能拿当前钱包余额直接对历史 swap。页面落后就重建投影，不再发 swap，更不修改链下余额伪造到账。这样执行事实、最终性判断和展示交付各有完成证据。

## 本题收束

- **讲透机制：** Go 生成可追溯建议，钱包签署明确计划，Router 原子执行全部腿，链上裁决资产变化，观察服务按确认与最终性策略交付可撤回投影。六个完成阶段不能折叠为一次接口成功。
- **容易答错的边界：** quote 不锁价不占资，allowance 不是预留；单笔原子性不包含独立 approve，也不免除失败 gas。链下哈希用于绑定与核对，链上 minOut 和 deadline 才是执行保护。
- **反例与验证：** 让同一钱包取得两份报价后先消耗授权，再模拟第二笔；让广播响应丢失但交易已入块；让成功 receipt 所属区块被重组。应分别出现链上拒绝、查询原交易收敛、撤回旧投影，而不是补发兑换。跨链、CEX、RFQ 的履约和部分完成语义需要另外建模，不能借用本题原子性。
