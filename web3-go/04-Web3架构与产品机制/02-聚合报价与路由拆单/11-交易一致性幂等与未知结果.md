# 大问题 11：用户重试、广播超时和同 nonce 替换交错时，怎样避免重复成交与错误终态？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EVM、DEX 与非托管 | EVM 是以太坊虚拟机，DEX 是去中心化交易所；非托管表示平台不保管用户资产。 | Go 的数据库只能协调与记录，不能直接裁决链上余额和成交。 |
| ExactIn、ERC20 与 rebase | ExactIn 固定花费输入，ERC20 是代币标准，rebase 会自动调整余额。 | 本题限同链普通无税、无 rebase 代币，单笔所有腿全成或全退。 |
| USDC、WETH、raw 与 bps | USDC 是稳定币，WETH 是包装 ETH，raw 是最小单位，bps 是万分之一。 | 输入 6 位、输出 18 位；10,000 USDC 拆分报价 4935790171985306493 raw，50 bps 得到 4911111221125379960 raw 下限。 |
| EOA、sender 与 caller | EOA 是私钥控制的普通账户，sender 是交易发送者，caller 是计划付款调用者。 | 默认用户 EOA 直接发起；平台能转发签名，不等于拥有用户私钥。 |
| businessRequestID 与 HTTP 幂等键 | 一个标识用户的一次业务意图，一个让网络重试回到原请求。 | HTTP 是接口通信协议；双击或断线重试不应自动变成第二次兑换。 |
| quoteID、quoteHash 与计划绑定 | 报价编号、报价指纹及请求、顺序、接收者等执行字段的对应关系。 | 一次业务可重报多版，但同幂等键不能静默换内容或让旧响应覆盖新计划。 |
| rawTx 与 signedTxHash | 完整已签交易字节及据此计算的交易指纹。 | 完全相同字节重播仍是同一笔；平台代广播时先存身份与计划映射再发送。 |
| chainId、nonce 与候选组 | 链身份、发送者交易序号，以及同一发送者同一序号的替换交易集合。 | 多个 hash 可以争同一个 nonce，不代表已经成交多次，旧候选不能随意删掉。 |
| RPC 与 UNKNOWN | RPC 是访问节点的接口，UNKNOWN 表示现有证据无法确定执行结果。 | 发送超时不等于失败，查询原交易或重播原字节，不新开 nonce。 |
| already known 与 nonce too low | 节点提示“已认识这笔交易”及“序号过低”。 | 前者不是成交证明，后者要求查谁消耗了序号，也不是本计划成功证明。 |
| 提费替换与取消 | 用户签同 nonce 的新候选提高费用，或发取消用途的交易竞争该序号。 | 都不是全网撤销旧签名；原交易仍可能抢先成为规范链胜出者。 |
| allowance、to、value、calldata 与 receipt | 转账额度、目标、原生币金额、合约指令与执行回执。 | nonce 被消耗后仍要核对实际交易与受信结算证据，不能把取消或回滚算成目标成功。 |
| intentNonce 与链上至多一次 | intentNonce 是额外合约里的业务意图序号，消费后阻止重复意图。 | 默认报价哈希与数据库锁不具备这个能力，新 EOA nonce 仍可能再次执行相同报价。 |
| deadline 与 block.timestamp | 执行截止时间及实际区块时间。 | 本地到期只限制未来执行，不证明旧交易未曾在期限内成功。 |
| revision 与规范链证据 | revision 是业务结论修订号，规范链证据是当前有效分支上的执行观察。 | 并发结果不能按最后响应覆盖，重组则通过明确的新修订撤回旧结论。 |
| exactly-once、原子性与 gas | exactly-once 是恰好一次处理承诺；原子性是同笔状态全成全退；gas 是执行费。 | 链上和数据库没有共同提交点；服务幂等不等于跨系统恰好一次，失败 gas 与独立 approve 也不回滚。 |
| v2 与 swap | v2 是按两侧储备报价的自动做市池，swap 是兑换调用。 | 主例两个独立 v2 池的两腿在单笔 swap 中全成全退。 |
| CEX 与跨系统提交 | CEX 是中心化交易所，跨系统提交表示多个系统各自保存结果。 | 本文单 Router 原子性不覆盖 CEX、跨链或本地数据库，恢复依赖身份映射和证据重放。 |

## 把整篇文章压缩成一个故事

小林确认 10,000 USDC 按 A 6,000、B 4,000 兑换，最低收到 4.911111221125379960 WETH。小林双击按钮，系统让两次 HTTP 调用回到同一个业务请求；若第二次偷偷换了接收者，就报冲突而非覆盖。平台代广播时，先从已签字节算出交易 hash，核对链、发送者、nonce 与实际指令并保存计划映射，避免“节点已接收，服务却崩溃忘了发过谁”。

广播 RPC 随后超时，系统把它记为 UNKNOWN，不替小林另开 nonce。需要重播就重播相同 rawTx；后来小林签了同 nonce 的提费候选，系统同时保留新旧 hash，因为旧交易仍可能先入块。即便账户 nonce 已增大，也要查实际消耗者到底是原换币、回滚、取消还是外部替换，不能仅凭一个序号或节点提示宣布成功。

最后旧 hash 在规范链上胜出，系统核对它仍是小林确认的计划、收款与下限，再归并结果；若后续重组，则用新修订纠正旧判断。本地 deadline 已过也不能替代这一核验。整套流程提供的是可恢复、可归并的处理，不是假称数据库与链上原子提交；若小林用新 nonce 再签同份报价，默认仍可能再次成交，只有明确增加链上意图去重才能约束业务至多一次。

**流程位置与核心机制：** 本题贯穿请求、报价、用户签名、广播和结果归并，重点是端到端一致性、幂等及 UNKNOWN，不展开确认交付实现。基线为同链 EVM 非托管 DEX 聚合 ExactIn，普通 ERC20，无税、无 rebase，用户自付 Gas；默认标准 EOA 直发，不假设额外的合约业务去重能力。单 Router 交易按固定顺序执行全部腿，全成或回滚，无部分填充。

例子沿用两个独立 v2 池：A 为 600,000 USDC／300 WETH，B 为 400,000 USDC／200 WETH，均收 0.3% 手续费。用户投入 10,000 USDC，精度 6 位，拆为 A 6,000、B 4,000；WETH 精度 18 位。quotedOut 为 `4935790171985306493 raw = 4.935790171985306493 WETH`，50 bps 滑点下 minOut 为 `4911111221125379960 raw = 4.911111221125379960 WETH`。Go 只估算，quote 不锁价、不预留资金，余额、储备、allowance、nonce 和 receipt 的权威都在链上。

## 第 1 层：为什么不能用一个 quoteID 串起所有幂等？

**面试官：** 用户双击交易按钮，为每份报价生成唯一 quoteID，再用数据库唯一键去重，不就能避免两次成交吗？

**面试者：** 只能避免服务内重复建单，不能约束钱包和链上。我会区分 businessRequestID、quoteHash、signedTxHash 及 `(chainId, sender, nonce)` 候选组：业务请求可能经历重新报价，一个 nonce 也可能对应多个替换交易 hash。报价绑定 `(chainId, blockNumber, blockHash)`、policyVersion、canonicalRequestHash、orderedPlanHash，以及 caller／recipient、amountIn、minOut、deadline、router／spender／value／calldataHash。每个签名候选必须映射到被确认的计划版本，不能把旧报价响应覆盖新请求。这里要区分一次用户意图与一次 HTTP 调用：网络重试不产生新意图，用户明确决定再次兑换才建立新的业务身份。这样既能阻止业务串单，也能解释同一业务为什么出现多个 hash，而不是把 hash 数量直接当成交次数。

## 第 2 层：HTTP 幂等怎样处理同键不同内容？

**面试官：** 上一答区分了业务请求，那同一个 businessRequestID 第二次带来不同 recipient 或 minOut，你会复用旧响应还是覆盖旧记录？

**面试者：** 都不能静默做。服务在用户身份范围内以幂等键建立唯一记录，同时保存规范化请求哈希；第一次创建成功后，同键同内容返回原记录，同键不同内容明确拒绝，不能把一笔已签交易换绑到新 recipient。并发请求由唯一约束或条件更新决出一个创建者，避免两个线程都先查不到再各自广播。请求状态需区分“等待签名”和“已有签名候选”，页面重试只是查询或继续既有流程。修改授权字段应产生明确的新版本并再次确认，但旧签名若已外发，版本升级不会使它失效。数据库幂等只约束本系统操作，无法阻止用户在另一钱包入口签出新 nonce。

## 第 3 层：签名与发送之间怎样留下可恢复证据？

**面试官：** 请求记录已经唯一，平台拿到钱包签好的 rawTx 后，为什么不能先发出去，等 RPC 返回 hash 再保存？

**面试者：** 因为 RPC 接收后、平台保存前可能崩溃，恢复时会丢掉查找线索。若平台代广播，应先从已签字节本地计算 signedTxHash，恢复 sender，校验 chainId、nonce、to、value、data 与用户确认计划一致，再持久化候选及请求映射，之后才调用 sendRawTransaction。完整 rawTx 如需保存，应按签名交易敏感性控制访问；至少保留 hash、nonce、sender、chain 和计划关联。平台只是转发用户签名，不因此拥有私钥或替换签名权。若钱包直接广播，应尽早登记钱包返回的 hash／nonce；若回调丢失，就诚实标记证据缺口，不能假装服务一定持有 rawTx 或能自行重签。

## 第 4 层：send 超时以后重试的对象是什么？

**面试官：** 你已经先保存候选，但 sendRawTransaction 超时，数据库里还没有“发送成功”，重试按钮应该重新构造一笔交易吗？

**面试者：** 不应该。发送超时只说明平台没收到确定响应，节点可能已经接收并转发；我会把广播观测记为 UNKNOWN，首先按已保存 hash 查询交易与 receipt，必要时将完全相同的 rawTx 再广播。同样的签名字节必然产生同一个 hash，不会变成新一次交换。RPC 的 already known 说明节点认识它，不代表已经成交；nonce too low 说明需要查 nonce 的消耗者，也不能直接解释为本候选成功。恢复必须围绕已有 sender／chain／nonce 及候选组进行，不新开 nonce。请求层可以重试，签名身份不能因此改变；没有 rawTx 时只能查询或请钱包协助，不能声称平台可自动补签。

## 第 5 层：同 nonce 提费替换为什么还要查旧 hash？

**面试官：** 相同 rawTx 长时间未入块，用户同意提费并签了新交易，旧 hash 是不是就可以立刻标记为已取消？

**面试者：** 不能。替换只是节点对候选的接纳策略，并非全网撤销旧签名；旧交易仍可能被别的节点或构建者收录。我会把新旧 hash 都归到同一个 `(chainId, sender, nonce)`，核对是否只变更费用，还是同时改变 data、value 等业务字段，后者必须重新确认计划。轮询整个候选组，只有规范链证据才决定谁胜出，并继续服从确认策略。同 nonce 的取消交易同理，它也要竞争入块，不能承诺提交取消即撤销。标准 EOA 在一条规范链上只能有该 nonce 的一个胜出者，但重组可能换掉胜出者；因此不能删旧 hash，更不能用“已替换”掩盖仍未决的组状态。

## 第 6 层：账户 nonce 增长能否证明交易成功？

**面试官：** 新旧 hash 都查不到，但 latest transactionCount 已经大于目标 nonce；既然这个 nonce 用掉了，能不能把业务标成功？

**面试者：** 不能，nonce 只证明该规范链头状态下序号已消耗，不说明消耗者执行了什么。可能是原交易成功、swap 回滚、取消交易，甚至用户在外部钱包签出的另一个替换。应追查规范区块中同 sender、同 nonce 的实际交易，再核对 to／value／calldata、receipt 和受信 Router 的业务证据。pending transactionCount 只是节点的待处理视图，更不能作为最终裁决。若节点缺少历史或索引能力，保持未决并显式记录“nonce 已观察到消耗，归属待核验”。由链头 nonce 推导业务成功，或由某个 RPC 查不到 hash 推导业务失败，都是把不完整观测当成了执行事实。

## 第 7 层：链上业务至多一次需要额外什么？

**面试官：** 同 nonce 组解决了替换问题，但用户在另一个入口用新 nonce 重签同份 quote，你的服务唯一键还能挡住链上第二次成交吗？

**面试者：** 挡不住，quoteHash 不会自动写入链上已消费集合。默认 EOA 直发只能说“本客户端协调一个未决执行组”，不能承诺整个业务链上至多一次。如果产品确实要求更强语义，应明确采用带 intentNonce 的合约变体：按 chain／Router 域、已认证 owner 与 intentNonce 识别意图，把 recipient、金额、minOut、deadline 和计划纳入授权；合约在外部交互前标记消耗，交换失败时消耗标记一起回滚。这样才约束不同 EOA nonce 的重复意图，而且仍以规范链为准，重组可撤销旧消耗。本题不默认新增这种合约，也不把数据库锁或客户端按钮禁用说成同等保护。

## 第 8 层：deadline 过期为何仍不能关闭 UNKNOWN？

**面试官：** 默认模式没有合约意图去重，保持 UNKNOWN 又影响用户继续交易；deadline 已过，为什么不能认为旧交易再无风险？

**面试者：** 因为“未来执行会过期”不等于“过去没有执行”。deadline 是绝对链上时间，旧交易可能已在 block.timestamp 不大于 deadline 的块中成功，只是 RPC 落后或响应丢失。先追踪所有候选是否已有规范 receipt，以及 nonce 是否被别的交易消耗；本地超时只能触发恢复，不裁决业务失败。即使确认尚未执行，过期 rawTx 仍可能入块后 revert 并耗费 Gas，在这个未决窗口也不能静默给同一业务另开 nonce。需要时由钱包发起同 nonce 取消并等待其证据，或提供明确的未决说明；不能把要求用户重签包装成系统已经证明旧单失败。

## 第 9 层：并发观测怎样避免状态相互覆盖？

**面试官：** 恢复任务查到旧 hash 成功，另一个任务稍后收到新 hash 的发送失败；两个更新谁覆盖谁？

**面试者：** 不能按响应到达时间做最后写入胜出。我会按证据层次存候选观测：广播响应、pending 可见、带 blockHash 的 receipt、规范性及确认进度分别记录，再在业务聚合状态上用 revision 条件更新。新 hash 的发送失败不推翻旧 hash 的规范成功，某候选回滚也不自动代表整个替换组失败；先识别同 nonce 的实际胜出者，再验证是否执行目标计划。遇到区块失去规范性，才用明确的重组转移撤销旧判断，保留原观测，不让状态只能前进而无法纠错。HTTP 返回成功、链上执行成功和页面显示成功是三层事实，不能用一个布尔值承担全部语义。

## 第 10 层：端到端一致性最终承诺到哪里？

**面试官：** 现在有请求唯一键、签名前校验、先存后发和候选归并，能不能称系统实现了交易与数据库的 exactly-once 原子提交？

**面试者：** 不能，链上与数据库没有共同提交点。数据库已存而尚未发出的窗口，通过已有签名恢复发送；链上已执行而本地未记结果的窗口，通过 hash／nonce 追踪补记；UNKNOWN 不靠新 nonce 逃避。实际业务成功还需规范 receipt、受信 Router 日志和本次资产结算证据匹配计划，不能只看 status 为 1。系统能承诺的是可恢复、可归并且不冒充确定性的处理流程，业务至多一次则取决于明确采用的链上或客户端边界。失败 swap 仍付 Gas，独立 approve 不回滚；这些成本与副作用也要如实呈现。结果确认和可靠通知另走交付机制，不能倒过来让页面或通知回执裁决链上交易。

## 本题收束

- **机制：** 业务键约束请求身份，计划哈希约束签名语义，交易 hash 约束签名字节，sender／chain／nonce 组约束替换候选；先保存映射再代广播，UNKNOWN 通过链上证据恢复而不是盲目重做。
- **错边界：** 服务幂等不等于链上防重；同 nonce 至多一个胜出者不等于同 quote 至多一次；nonce 消耗不等于 swap 成功；到期不等于从未执行；平台能转发不代表能替用户签名。跨交易、CEX、跨链也不能沿用单 Router 原子承诺。
- **反例验证：** 节点接收交易后超时，客户端重新点按钮，只能回到原候选；提费交易尚未胜出而旧 hash 入块，应归并旧结果；用户新 nonce 再签同 quote，默认链上可能二次成交。若把这三种情况都叫“已幂等”，就没有说明幂等究竟约束哪一层。
