# 大问题 9：聚合报价怎样变成授权边界清晰、两腿全成或全退的执行计划？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EVM、DEX 与非托管 | EVM 是以太坊虚拟机，DEX 是去中心化交易所；非托管表示平台不持有钱包资产。 | Go 只估算，真正拉款、兑换与回滚都由链上合约裁决。 |
| ExactIn、ERC20 与 rebase | ExactIn 固定输入；ERC20 是代币标准；rebase 会自动重设余额。 | 本题只支持普通无税、无 rebase 代币，全部输入必须准确用完。 |
| USDC、WETH 与 raw | USDC 是稳定币，WETH 是包装 ETH；raw 是最小单位整数。 | USDC 6 位、WETH 18 位，本次输入为 10000000000 raw USDC。 |
| AMM v2/v3 | AMM 是自动做市商；v2 用储备模型，v3 用集中流动性区间。 | 数值例是两个独立 v2 池，但安全执行还要覆盖适配器与 v3 认证回调。 |
| caller、recipient 与 EOA | caller 是付款调用者，recipient 是收款人，EOA 是由私钥控制的普通账户。 | 默认 EOA 直接发交易；付款人必须受认证，收款地址不能由后端临时换。 |
| Router 与 adapter | Router 是组织兑换的执行合约，adapter 是对接具体协议的适配器。 | 只能调用受限的可信路径，不开放任意目标加任意指令。 |
| allowance、owner、spender 与 transferFrom | owner 是代币所有者，spender 是获准拉款地址，allowance 是额度，transferFrom 是按额度转账的调用。 | 授权足够不代表可以任意拉款，实际只允许取本次输入。 |
| approve | 给指定地址设置代币转账额度的交易。 | 独立 approve 与换币各有 nonce、回执和 gas，换币回滚不会撤销已成功授权。 |
| calldata、to、value 与签名 | 合约指令、目标地址、附带原生币及用户对最终交易的授权。 | 钱包要核对实际交易与解码字段，不能只签页面上的报价编号。 |
| canonicalRequestHash、orderedPlanHash、calldataHash | 规范请求、有序计划和实际指令的指纹。 | 哈希能核对字节，不自带可信来源、链上校验或业务防重能力。 |
| U0、W0 与 R0 | 分别是拉款前 Router 的 USDC、WETH 和收款人 WETH 余额基线。 | 只花本次输入、只转本次产出，不能把 Router 或收款人旧币算作本次结果。 |
| minOut、quotedOut 与 bps | 最低收币量、估算毛输出及万分之一比例单位。 | 50 bps 从 4935790171985306493 raw 得到 4911111221125379960 raw 下限，检查收款人真实增量。 |
| revert、原子性与 gas | revert 撤销当前交易状态；原子性是同笔全成或全退；gas 是执行费。 | 后腿或最终检查失败，前腿转账一起撤销，但已耗 gas、交易 nonce 和独立授权不回滚。 |
| nonReentrant 与回调认证 | nonReentrant 防止入口被嵌套进入；回调认证只放行本次预期的池回调。 | v3 正当回调不能一概封死，也不能放任任意合约借回调混用结算余额。 |
| deadline 与 block.timestamp | 截止时间及执行区块时间戳。 | 由合约检查绝对期限，页面倒计时不能裁决；本地过期不证明过去没成交。 |
| nonce 与 intentNonce | nonce 是账户交易序号，intentNonce 是额外设计的业务意图序号。 | 默认同 nonce 只允许一个规范链胜出者，不阻止新 nonce 重复做同份报价；业务去重需额外合约能力。 |
| UNKNOWN 与到期检查 | UNKNOWN 表示没有足够证据判定交易结果。 | 期限到了也要查是否此前已入块，不能凭本地时间判失败并用新 nonce 重做。 |
| CEX 与其他交易 | CEX 是中心化交易所；其他交易有各自独立的提交点。 | 中心化交易所、跨链和多笔调用不能自动继承本文单笔 Router 原子边界。 |

## 把整篇文章压缩成一个故事

小林确认花 10,000 USDC，按 A 6,000、B 4,000 的顺序换 WETH。系统不仅给出预计 4.935790171985306493 WETH，还把付款人、收款人、拉款地址、调用顺序、4.911111221125379960 WETH 下限和截止时间绑定到最终交易。小林核对钱包实际待签内容；若先做独立授权，那只是允许受信地址在额度内拉款，不是确认这次换币已经完成。

Router 执行前记下自己的 USDC、WETH 和收款人的 WETH 基线，只拉本次 10000000000 raw USDC，再按固定额度执行两腿。它要求本次输入全部花完，自己的旧余额不受消耗，最终收款人新增 WETH 不低于下限；假如 Router 原有 1 WETH、本次只产出 4.8 WETH，也不能拿旧币补到合格。第二腿失败或最终转账后检查不足，整笔状态一起回滚，但用户仍付已消耗 gas，先前独立授权仍在。

小林还问：有了原子性，是否既防重入又防重复成交？答案仍是否。执行器要限制入口、适配器和经过认证的 v3 回调，避免两个结算上下文互相垫款；默认 EOA 模式下，同一报价用新 nonce 再签仍可能第二次成交。哈希用于核对，交易原子性管单笔全成全退，业务至多一次要另设意图去重，三种责任不能混成一个“安全”标签。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题承接报价与拆单，追问计划如何进入用户签名、代币授权和单笔 Router 交易。基线为同链 EVM、非托管 DEX 聚合 ExactIn，普通 ERC20，无转账税、无 rebase，用户自付 Gas；主线适用 v2/v3 AMM，数值采用两个独立 v2 池。Go 只估算，不预留用户资金、不锁池价；链上余额、储备、allowance 和执行结果才是权威。

用户以 10,000 USDC（6 位精度）换 WETH（18 位精度）。A 池为 600,000 USDC／300 WETH，B 池为 400,000 USDC／200 WETH，手续费均为 0.3%；计划依次向 A 投入 6,000、向 B 投入 4,000 USDC。总 quotedOut 为 `4935790171985306493 raw`，即 `4.935790171985306493 WETH`；50 bps 滑点对应 minOut 为 `4911111221125379960 raw`，即 `4.911111221125379960 WETH`。所有保护都必须落实到同一笔交易的实际执行路径。

## 第 1 层：报价快照为什么还不是可执行承诺？

**面试官：** Go 已经算出 A 六千、B 四千及总输出，为什么不能把这三个数交给 Router 就认为交易受保护？

**面试者：** 因为计算结果没有说明“基于哪个状态、允许谁把什么资产送到哪里”。我会将报价绑定到 `(chainId, blockNumber, blockHash)`，再带上 `policyVersion`、`canonicalRequestHash`、`orderedPlanHash`，以及 caller、recipient、amountIn、minOut、deadline、router、spender、value、calldataHash。块高相同仍可能发生重组，所以不能省略块哈希；腿的顺序改变也必须改变计划哈希。caller 是本基线的实际付款 EOA，recipient 可以不同，但收款地址必须进入用户核对范围，不能由执行服务临时填写。这里快照只是报价证据，并不冻结储备或余额。真正执行时，Router 必须重新依据链上状态完成交换，并强制检查输入、输出和期限，不能把 Go 算过一次当成链上保证。

## 第 2 层：哈希绑定怎样避免只是“材料齐全”？

**面试官：** 上一答列了 orderedPlanHash 和 calldataHash，如果攻击者连计划和哈希一起换掉，这些字段还能保护什么？

**面试者：** 哈希只证明字节对应，不能自己证明来源可信。我会对请求采用固定编码和整数单位，计划按执行顺序编码 token、pool、adapter、amount 和参数，再重新计算哈希；客户端根据被认可的报价来源核对整份计划。签名前还要检查实际交易的 chainId、to、value、data，以及 data 解码后的收款人、金额、minOut 和 deadline。标准 EOA 签名覆盖最终交易，不是只签页面上的报价编号。若 Router 没有校验某个报价元数据的逻辑，不能声称它会自动验证快照或 policyVersion；元数据绑定负责防串单，链上执行断言才负责阻止越权结算。

## 第 3 层：交易签名为何不能替代代币授权核对？

**面试官：** 用户已经核对并签了 Router 的 calldata，为什么你还要单独绑定 spender？

**面试者：** 因为 ERC20 allowance 授予的是某个链上地址从 owner 转走代币的能力，不是对某份报价的认可。交易的 to 是 Router，不代表真正调用 transferFrom 的 spender 必然相同；本题选择由指定 Router 拉款，就必须让 spender 等于这个已验证地址，并检查 USDC 合约及 chainId。授权可设为本次 `10000000000 raw`，但即使已有更大 allowance，执行路径仍只能拉取本次 amountIn。若 approve 是前一笔独立交易，必须等链上授权生效再执行；swap 回滚不会撤销已经成功的 approve。两者的 nonce、receipt 和 Gas 分别追踪，不能包装成一笔原子交易。

## 第 4 层：有限拉款怎样隔离 Router 的历史余额？

**面试官：** spender 已经正确，但 Router 原来就留有 USDC 或 WETH，怎样防止旧余额被拿来凑本次输入输出？

**面试者：** 我会在任何拉款、swap 前记录 Router 的 USDC 基线 U0、WETH 基线 W0，以及 recipient 的 WETH 基线 R0。入口要求 caller 与实际付款人一致，recipient 非零且不属于 Router、本次 adapter 或池等执行地址，避免结算资产回流执行路径。随后只 transferFrom 本次 amountIn，并要求 Router 的 USDC 增量恰好为 `10000000000 raw`。后续每腿使用固定额度，本次 WETH 产出按相对 W0 的增量计算，绝不把 balanceOf 全额转给用户。余额差不是孤立的万能判据：必须与固定路径、全量花费和受限交互一起成立，才能排除挪用历史余额的窗口。

## 第 5 层：两腿顺序怎样形成输入守恒？

**面试官：** 既然拿到了准确的本次输入，A 执行后能不能临时把剩余资金重新分给 B，以免第二腿失败？

**面试者：** 不能静默改变已授权计划。本次按顺序给 A `6000000000 raw`、给 B `4000000000 raw`，两腿额度之和必须等于 amountIn；目标池、adapter 和 token 方向都固定。v2 的估算遵循带手续费的常数乘积公式，并逐腿向下取整，但真正输出由执行时储备决定。两池独立只表示 A 不会直接修改 B 的储备，不表示两腿可以拆成独立交易。执行器还要核对每腿实际消耗与额度一致、全程累计消耗为一万 USDC，最终 USDC 回到 U0；本基线不支持剩余输入，不能仅凭函数返回成功就把未用完的余额留在 Router。

## 第 6 层：为什么最终检查收款人增量？

**面试官：** 上一答已经约束每腿输入，如果 adapter 返回的两腿输出相加超过 minOut，为什么还不能直接宣布成功？

**面试者：** 返回值可以算错，也不必然代表资产已经到收款人。我会将 Router 相对 W0 的本次 WETH 增量转给 recipient，再检查其最终余额减 R0 至少为 `4911111221125379960 raw`。这样 Router 历史 WETH 和 recipient 原有 WETH 都不能替本次报价兜底；同时保持 Router 的历史基线不被消耗。总 minOut 是本次最终到账底线，不要求每腿按六四比例各自达到一个未签署的底线；如果产品另设腿级约束，也要纳入计划。USDC 全量消耗、资产方向及 recipient 增量任一不符都 revert，不能用伪造返回值、错误币种或“稍后补发”替代结算。

## 第 7 层：第二腿失败时原子回滚究竟覆盖什么？

**面试官：** 如果 A 已成功、B 因储备变化失败，或者最终转账后才发现增量不足，A 的交换和收款转账还能撤销吗？

**面试者：** 可以，因为它们都在同一笔外层交易调用树内。Router 不吞掉关键失败，任何腿、转账或最终断言失败都向外 revert，前面的 transferFrom、A 的储备修改、B 的修改及已发生的 WETH 转账一起回滚，相关执行日志也不作为成功日志留下。本题没有部分填充。撤销的是这笔交易的状态效果，不是免费执行：失败交易仍消耗 Gas，并在规范链上消耗该 EOA nonce，独立成功的 approve 也仍然存在。2 gwei 下单路 120,000 Gas 约 0.00024 ETH，双路 180,000 约 0.00036 ETH，都只是估算，不能从 WETH 的 minOut 中扣减。

## 第 8 层：余额断言为什么还需要重入与回调认证？

**面试官：** 最后一定检查余额差，为什么还担心恶意 adapter 在两次快照之间重入？v3 又确实需要回调，怎么兼容？

**面试者：** 如果重入能开启第二次结算、替换 recipient 或共用中间余额，两个执行上下文就可能相互垫付，单个差值不能证明归属。因此入口使用 nonReentrant，router、adapter、pool 均来自白名单，并约束调用方法和参数，不能提供任意 target 加任意 calldata 的执行器。普通 ERC20 基线不依赖收款钩子，但外部 adapter 仍是交互面。v3 回调不能简单与入口共用一个拒绝全部重入的修饰器；应只放行预期池的认证回调，核对 factory／池身份、本次执行上下文、应付 token 与债务上限，其他入口保持锁定。白名单若可升级，还要明确其代码与升级权限信任边界。

## 第 9 层：deadline 到底由谁判定？

**面试官：** 回调和结算都限制住了，用户本地看到报价还剩五秒，能保证交易不会过期吗？

**面试者：** 不能。deadline 必须是写入已签 calldata 的绝对时间戳，例如 Router 入口要求 `block.timestamp <= deadline`；它不是服务端收到请求后再加一段秒数。最终只由包含该交易的规范区块时间裁决，用户手机时钟和 Go 时钟只能用于提前提醒。交易执行期间块时间固定，不会出现 A 在期限内、B 在期限外的墙钟式分裂；但交易可能排队到更晚的区块才整体失败。广播状态未知时，即便本地时间已过 deadline，也要查询它是否早在期限内入块，不能直接标记失败并再发一次。过期限制执行窗口，并不证明过去没有执行。

## 第 10 层：同一份计划还能被再次成功执行吗？

**面试官：** 前面绑定了 calldataHash、金额和期限，同一份 quote 在 deadline 前被用两次，Router 会自动识别吗？

**面试者：** 不会，quoteHash 不是链上自动防重开关。默认标准 EOA 直发时，同一 sender、同一 nonce 在规范链上只能有一个交易胜出，但用户用新 nonce 再签相同 calldata，余额与授权充足就可能再次成交；原子性只保证每笔交易内部全成或全退。客户端可协调同一业务只维护一个未决 nonce 组，UNKNOWN 时不另开 nonce，但不能把这种协调宣称为链上业务至多一次。若产品明确要求后者，应另设验证 caller 的 intentNonce 消耗映射，将消耗与交换放在同一笔交易中，失败共同回滚；那是明确的合约能力变体，不是本基线默认自带，更不能把承诺推广到跨交易、CEX 或跨链。

## 本题收束

- **机制：** 报价证据绑定最终交易；spender 约束拉款权限，固定顺序与额度约束执行路径，历史余额基线和收款人增量约束结算归属，最外层 revert 统一兑现原子性。
- **错边界：** quote 不锁价；哈希不自带来源认证或防重；approve、Gas、其他交易不随 swap 回滚；白名单与余额检查不能替代回调认证。deadline 看链上时间，不看页面倒计时。
- **反例验证：** Router 原有 1 WETH、本次只产出 4.8 WETH，必须失败而不是拿旧币凑 minOut；A 成功而 B 失败，不能保留 A；同 quote 用新 nonce 再执行，默认 EOA 模式不能承诺自动去重。这三个反例分别检验资产隔离、交易原子性和业务防重是否被混为一谈。
