## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 正确性与最优性 | 正确性关心计划是否合法、算得对不对；最优性关心是否在给定范围内选得最好。 | 安全但不是最优的计划仍可执行，毛输出很高却无效的计划不行。 |
| MVP 与验收方法 | MVP 是最小可行验证范围；验收方法是准备怎样检验。 | 本文不再添加第二个工程，差分、故障注入和压测都是待实施方法，不是已运行结果。 |
| raw、USDC 与 WETH | raw 是代币最小单位；USDC 是稳定币，WETH 是包装 ETH。 | 比较原始整数，不只看“约 4.93579”这种展示小数相近。 |
| 不变量 | 一类输入下始终应满足的规则。 | 例如分配守恒、输出小于池储备、重复池读更新状态，但成立前提也要一起写清。 |
| v2、Pair 与 ERC20 | v2 是储备式自动做市模型，Pair 是对应池合约，ERC20 是代币标准。 | 普通代币也可能被直接捐赠；实际余额不等于储备时不能照搬简化更新式。 |
| 凹性与整数差分 | 凹性描述连续模型的边际收益递减；整数差分是输入增加最小单位时输出变化。 | 向下取整会造成台阶，不能要求每个整数增量都严格递减。 |
| v3、tick、sqrtPrice 与 liquidity | v3 按价格区间组织流动性；tick 是价格刻度，sqrtPrice 是平方根价格，liquidity 是活跃流动性。 | 差分不仅比最终输出，还比跨区间后的完整终态与费用。 |
| 差分验证、SDK 与参考版本 | 差分把同一输入交给独立实现比较；SDK 是开发工具包；版本说明比较对象。 | 用受信目标版本和同一快照，不能拿新工具包对旧部署，也不能复制本地结果充当独立预期。 |
| 穷举、离散网格与贪心 | 穷举检查小范围所有合法方案，网格限定输入步长，贪心做局部增益选择。 | 用同候选、同费用和同网格验优化器，离散参考不等于连续全局最优。 |
| gas 与净价值 | gas 是另付的执行费，净价值是毛输出减同币种费用估值。 | 100 USDC 拆分多出的币不够新增 0.00012 WETH 等值 gas，池报价算对仍可能选错计划。 |
| Builder、calldata 与 hash | Builder 构造交易，calldata 是实际合约指令，hash 是内容指纹。 | 独立解码实际指令，核对接收者、金额、顺序、下限和期限，计划身份与交易身份不能混用。 |
| from、value、target 与 delta | 调用者、附带原生币、目标及本次资产变化量。 | 完整预检覆盖真实调用环境和各方资产变化，Router 旧余额不能凑本次输出。 |
| minOut、deadline 与原子回滚 | 最低收币量、执行期限以及同笔状态全退。 | 任一腿或最终断言失败全部撤销；历史余额、独立授权和已耗 gas 各有边界。 |
| txHash、sender、nonce 与 UNKNOWN | 交易指纹、发送者、序号和结果未知状态。 | 在广播响应丢失等窗口追原交易，不用新 nonce 重复换币；最后能对账不为中途重复执行开脱。 |
| revision、outbox 与 eventId | 结果修订号、待发事件表和稳定事件身份。 | 重组发布新修订，结果与事件同事务保存，消费去重且不让旧事件覆盖新判断。 |
| trace、RPC 与高基数标签 | trace 是调用追踪记录，RPC 是节点接口，高基数标签是取值极多的指标维度。 | 钱包和交易 hash 放受控日志，不做无限指标标签；签名交易和接口密钥也不能随意公开。 |
| 影子报价、灰度与能力登记 | 先只计算不执行，再逐步限额开放，同时记录协议真正支持什么。 | 缺 tick、输入不能用完或升级未受监控时限制执行，不能先让用户承担未知风险。 |
| EVM 与新链适用性 | EVM 是以太坊虚拟机，只规定执行环境的一部分。 | 接新链仍需另验费用、资产身份、有效期和最终性，不能用统一接口名替代这些模型。 |

## 把整篇文章压缩成一个故事

小林看到聚合器能返回约 4.93579 WETH，准备判断它是否可信。验证者没有把这个显示值直接抄成测试答案，而是保存输入整数、池储备、费率、快照和顺序，独立核对每腿数学与状态变化，再用目标协议同版本的参考计算或完整调用做差分。v3 还要比跨 tick 的终态，普通 v2 也要检查方向、舍入，以及实际余额是否被捐赠打破了储备相等前提。

接着小林只换 100 USDC：全 A 毛输出 0.049841717967864339 WETH，六四拆分为 0.049845030450464088，但多出的币小于额外 0.00012 WETH 等值 gas，优化器必须选择全 A。验证者又给 Router 预存 1 WETH，让本次只产出 4.0 WETH；若系统拿旧币凑成 5.0 WETH 通过主例下限，就是结算归属错误。单池算对、路线选对、实际指令和资产保护兑现，是三个都要检查的环节。

最后在签后未发、已发丢响应、已落库未通知、已成功后重组等窗口主动制造故障，检查始终追原 hash 和 nonce、UNKNOWN 不被误判失败、修订与通知不会倒退。准备接新协议时先影子报价，再按证据逐级限额开放，安全不变量失败就关适配器。这是一套待实施、能暴露反例的验收路线，不是文稿已经跑完测试，更不是部分用例通过就证明所有未知漏洞不存在。

[返回专题总览](README.md)

**流程位置与核心机制：**覆盖输入、报价、计划、执行与结果恢复的证据。本题建立可反驳的验收方法，不再添加第二个工程 MVP；提到的差分、回放、故障注入与压测均为待实施方法，不是本次已经运行的实验。

## 第 1 层：能返回报价，为什么不代表实现正确？

**面试官：**聚合器已经能为主例返回约 4.93579 WETH，你怎么判断不是刚好算对了一次？

**面试者：**我会把正确性拆开，不能只看一个最终小数。首先核对请求的链、资产、精度和数量；然后核对状态是否同块且完整；再检查每腿输出、共享池状态、整计划成本、输入分配以及用户保护。最后是实际构造和结果追踪是否兑现相同语义。优化目标与安全约束也分开：不是最优的合法计划可以安全执行，毛输出很高但无效的计划不能执行。

主例保存原始整数、池储备、手续费、快照身份、策略、候选和计划顺序。参考结果应独立计算，而不是把实现打印的数字复制成预期。这样才能从某个差异回到具体公式或状态边界，而非只判断界面小数是否相近。

## 第 2 层：把“算对”写成哪些不变量？

**面试官：**你要独立参考结果，但不可能为所有金额手写答案。哪些性质适合自动生成输入检查？

**面试者：**对普通 v2 池，检查输入、储备为正，输出为整数且小于输出储备；在固定池状态和同一费率下，输入增加时输出不应下降，但可能因整数舍入持平。在本稿初始实际余额等于储备的前提下，更新时输入储备增加完整输入，输出储备减少实际输出，且不出现负值；同块余额与储备必须一起核对，直接捐赠可使普通 ERC20 池不满足这一前提。若适配器支持不相等状态，另按 Pair 的实际余额、输入识别和储备写回验证，不能将简式当普遍不变量。凹性、边际递减只在明确的连续模型或容许舍入误差的规则下检查，不能要求每一个整数差分都严格递减。

对计划，检查逐腿初始输入相加等于总输入，中间币沿边正确传递，重复池使用更新后的同一状态，费用币种与单位一致。对构造，检查 recipient、amountIn、minOut、deadline 和顺序与用户确认一致。这些性质能筛掉大类错误，但不能独自证明目标合约的每一步舍入、回调与权限安全。

## 第 3 层：性质通过，为什么还需要差分验证？

**面试官：**你的 v3 适配器也满足输入守恒和输出不为负，却可能跨 tick 多算一点。怎么建立更强的参考？

**面试者：**针对固定协议版本，把相同快照和输入分别交给本地适配器与受信的目标协议参考实现或完整合约模拟，比较原始整数输出、终态 sqrtPrice、tick、活跃流动性以及费用。参考必须固定版本和调用条件；不能用最新 SDK 对着旧部署，看到差异就说链上错了。

v3 特别检查恰好到 tick、向左向右跨界、零流动性间隙、价格限制、极小数量和多段舍入。v2 也要核对方向、费用和整数运算顺序。不同来源的一致结果提高证据强度，但如果本地代码与参考复制同一个错误，仍会漏检；因此保留公式性质、边界手算、目标调用差分三类互补证据，不只换一个库名。

## 第 4 层：池报价都正确，拆单为什么仍可能错？

**面试官：**每个池的输出都与参考一致，但优化器把 100 USDC 拆成两腿，用户净价值反而下降。怎样验收优化算法？

**面试者：**池模拟正确不证明计划选择正确。我会构造足够小的独立路径集合和离散输入网格，用穷举枚举合法分配、调用顺序和整计划费用，作为这个受限问题的参考；启发式输出与同一网格、同一费用口径比较，分别记录差额与覆盖条件，而不是把离散参考称为连续全局最优。

本例 100 USDC 全 A 毛输出 `0.049841717967864339 WETH`，60/40 拆分毛输出 `0.049845030450464088 WETH`，增益小于额外 `0.00012 WETH` 等值 Gas，必须选全 A。还要加入共享池、费率不等和新增腿固定成本，让只按边际毛输出贪心的算法暴露缺陷。近似误差超标可以缩小适用范围，不能靠放宽用户保护掩盖算法问题。

## 第 5 层：怎样证明生成的 calldata 与报价是同一个计划？

**面试官：**优化器选对了，但 Builder 编码时换了收款人，或者适配器只模拟独立腿。怎样把验证延伸到执行端？

**面试者：**我会把有序计划规范编码后形成身份，并独立解码实际 calldata，逐项核对 chainId 对应的目标、router/spender、caller、recipient、token、数量、调用顺序、minOut、deadline 和 value。签名封装会影响交易 hash，计划身份与交易身份需要映射，不能混成一个 hash。

预检使用完整调用环境，包括 from、value、余额、授权和实际 target。若在受控快照执行，应核对钱包、recipient、Router 与每个池的本次资产 delta，不只看返回值；把原 Router 历史余额与其他用户资金预先放入场景，检查它们不能被算进本次输出。任一腿失败与最终输出不足都应撤销全部 Swap 状态；独立授权和 Gas 则分别核对，不虚构全系统回滚。

## 第 6 层：执行正确后，怎样验证超时和重组恢复？

**面试官：**完整调用模拟和余额都对，但上线最难的是断连、重复推送和重组。你会把故障放在哪些窗口？

**面试者：**围绕不可原子跨越的边界放故障：已签名未广播、广播成功但回执丢失、入块观察到但本地事务未提交、结果已写但通知未发、通知已发但消费者确认丢失，以及成功块随后离开规范链。每个窗口都检查是否保留原 txHash、sender/nonce 和计划关联，能否继续查询或重发相同已签名交易，而非新开 nonce 重复兑换。

观察端用替换交易组和规范区块身份恢复；重组产生新 revision，撤回旧成功投影并继续追踪。结果与 outbox 同事务写，消费者用 eventId 和 revision 幂等更新。验收不仅看最终能否显示成功，还检查中间没有把 UNKNOWN 判成失败、没有重复业务成功、旧事件不会覆盖新修订。异常最终收敛不能为中间不安全的资金动作辩护。

## 第 7 层：生产指标怎样区分算错、状态变化和费用变贵？

**面试官：**恢复方案能收敛，但用户说“实际到手比报价低”。你会查哪些证据，避免把正常行情变化当算法 bug？

**面试者：**我会分开记录报价块、预检块、入块身份与时间，保存请求、候选覆盖、算法/适配器版本、计划及费用来源。先核对实际执行是否仍是原计划、实际输入是否一致，再区分报价到执行的状态变化、协议模拟误差、Gas 数量误差、Gas 单价变化、费用换算价格偏差和保护内滑点。不能只用一个“报价准确率”把这些原因混在一起。

指标包括有路由率、搜索截断比例、候选失败类型、净价值改善、预检/入块回滚原因、交易未知时长、确认修订、投影滞后与分阶段延迟。原始请求和 hash 进有权限的日志或 trace，不把每个钱包或 txHash 当指标标签制造高基数；签名交易、RPC 密钥与用户身份也不能直接无差别公开。

## 第 8 层：怎样安全接入新协议而不扩大未知风险？

**面试官：**已有这些证据后，产品要加入新 v3 分叉。能不能先让它返回报价，等出现误差再补修？

**面试者：**只能在不执行的影子报价阶段这样收集证据，不能把“有数字”当可安全执行能力。先登记部署地址、代码与配置版本、资产限制、fee/tick 规则、回调认证、授权方式、完整输入支持、Gas 和错误语义。缺少 tick、无法证明输入全用完、目标可升级而未监控等条件，都应限制能力或不开放执行。

灰度按离线参考差分、完整调用验证、影子报价、受限内部执行与小额限流逐步推进；每阶段设金额、覆盖与错误阈值，安全不变量失败就关闭该适配器，不自动改走未知目标。审计和用例覆盖只能证明已覆盖条件下的行为，不能证明未知漏洞不存在。接入新链还需另建费用、身份、有效期和最终性模型，不把 EVM 约束包装成所谓万能接口。

## 本题收束

- **讲透的机制：**独立参考与不变量互补、协议差分、有限域穷举、构造与执行证据闭环、故障窗口、结果修订、分层归因与能力灰度。
- **最容易答错的边界：**无负数不是报价正确；合约模拟通过不是未来必成；单池报价正确不是拆单最优；最后对上账不是未知期间可以重复执行；通过部分测试不是未知协议安全证明。
- **反例验证：**给 Router 预存 1 WETH，再让本次输出只到 4.0 WETH；若实现把历史余额凑成 5.0 WETH 通过本例 minOut，则执行验证失败。再只复制本地算法生成预期值，应主动承认这不是独立差分证据。
