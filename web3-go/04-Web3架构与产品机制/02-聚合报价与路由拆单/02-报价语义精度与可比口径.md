# 大问题 2：聚合报价里的“能收到多少”怎样定义，才能整数精确、跨候选可比且不误导成交承诺？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| ExactIn | 固定输入数量，输出由实际兑换状态决定。 | 计划花 10,000 USDC，不承诺一定收到报价中的 WETH。 |
| EVM、ERC20 与普通代币 | EVM 是以太坊虚拟机，ERC20 是代币接口标准。 | 本文限同链、无转账税、无 rebase 自动余额重设的代币，不含跨链或中心化交易所成交。 |
| USDC、WETH 与 decimals | USDC 是稳定币，WETH 是包装 ETH；decimals 是小数位数。 | USDC 用 6 位、WETH 用 18 位，不能把两种 raw 数字直接当同单位比较。 |
| raw 与 float64 | raw 是最小单位整数；float64 是不能精确表达所有大整数的浮点类型。 | 10,000 USDC 必须解析为 10000000000 raw，不能先转浮点再乘精度。 |
| amountInRaw、quotedOutRaw、minOutRaw | 分别是计划输入、估算毛输出和执行最低收币量。 | 三者承担不同职责，报价数字不是已到账数字。 |
| AMM v2/v3 | AMM 是自动做市商；v2 用储备曲线，v3 用分价格区间的流动性。 | 主例用 v2 算法，不能把同一公式套给 v3。 |
| a、Rin、Rout 与 floor | a 是输入量，Rin/Rout 是输入币和输出币储备，floor 是向下取整。 | 先算完整乘积，再做整数除法；997/1000 表示计入 0.3% 池费后的输入系数。 |
| 逐腿舍入 | 每份分配按合约自己的整数规则算完，再加总。 | A 的 6,000 和 B 的 4,000 分别取整，不能合并两池储备后只算一次。 |
| 快照与 blockHash | 快照是计算底稿，blockHash 是具体区块的分支指纹。 | 候选必须基于同一状态、同一输入和同一执行规则才可比较。 |
| overlay 与共享池 | overlay 是计划自己的临时状态层；共享池指多条调用用到同一份储备。 | 后腿要读前腿更新后的储备，且输入储备增加完整输入，不只增加扣费后部分。 |
| gas、gwei 与净值 | gas 是执行工作量，gwei 是 ETH 单价单位；净值是毛输出减同币种成本估值。 | 用户另付 ETH；WETH 净值只供排名，不是钱包实际收到的币数。 |
| bps、minOut 与价格影响 | bps 是万分之一；minOut 是执行下限；价格影响是交易本身沿池曲线造成的价格变化。 | 50 bps 容忍的是报价后执行输出的恶化，不重复扣已计入报价的价格影响或池费。 |
| deadline 与 allowance | deadline 是执行截止时间；allowance 是允许指定地址转走代币的额度。 | 期限由合约检查，授权不等于资金已为报价预留。 |
| requestHash、orderedPlanHash、calldataHash | 分别为规范请求、有序计划和实际合约指令的指纹。 | 改接收者、金额或腿顺序就要重建对应绑定，不能只沿用报价编号。 |
| tick 与降级排名 | tick 是 v3 的价格刻度；降级排名是明确缩小可计算范围。 | 缺 tick 不能装作报价完整，缺 gas 不能按零成本参加最佳净值排名。 |
| API 与 EIP-1898 | API 是程序接口，EIP-1898 支持按区块哈希查询状态。 | 报价接口保持统一字段语义；节点不支持所需状态读取能力时要说明降级或拒绝。 |
| CEX 与 RFQ | CEX 是中心化交易所，RFQ 是询价交易。 | 费用、履约和时效语义不同，不能直接塞入本文同链 AMM 估算口径。 |

## 把整篇文章压缩成一个故事

小林看到页面写着“10,000 USDC 可换 4.935790171985306493 WETH”，先问这到底是哪一种数量。系统把输入固定为 10000000000 raw，在共同快照中，对 0.3% 费率的 A、B 两个独立池分别投入 6,000、4,000 USDC，逐腿整数计算后合得 4935790171985306493 raw WETH。这个数是预计毛输出，不是执行保证，也不能拿界面截短的小数重新参与计算。

接着系统比较划不划算。按 2 gwei 的教学假设，全 A 的 120,000 gas 折成 0.00024 WETH，双池的 180,000 gas 折成 0.00036 WETH，拆分净值仍较高；但输入只有 100 USDC 时，拆分多得的 0.000003312482599749 WETH 不够支付额外 0.00012 WETH 成本。小林因此明白，到账估算、经济排名和执行底线必须分别展示，不能用一个“最终接收”字段糊在一起。

小林接受 50 bps 滑点，系统基于毛输出而非净值生成 4911111221125379960 raw 的 minOut，并绑定接收者、顺序、期限和实际签名指令。如果候选复用同一池，就更新临时储备后重算；如果 v3 数据或费用缺失，就排除候选或明确降级，而不是补零宣布最佳。最终承诺是一个能复算、能核对、由合约执行时保护的估算契约，不是提前宣布成交。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于输入规范化、池报价、路由比较与执行参数固化之间，解决同一个“输出数量”在估算、排名、保护和到账中的不同语义。公共前提及公共字段见 [README](README.md)：同链 EVM 非托管 ExactIn，普通无税、无 rebase ERC20，用户自付 gas，无平台费或返佣。主能力为 v2/v3 AMM，贯穿例仅用两个 v2 直接池，单 Router 固定顺序全量执行、无部分填充、全部成功或全回滚。

## 第 1 层：先把 ExactIn 的输入与输出承诺分开

**面试官：** 产品写着“10,000 USDC 可换 4.935790171985306493 WETH”。这句话少了哪些关键语义？

**面试者：** 首先要说明这是指定链、指定代币合约、指定快照和路线下的 ExactIn 估算，不是锁价承诺。输入固定为 10,000 USDC，输出随执行时的池状态变化；余额和 allowance 足够也只是检查结果，不是资金预留。字段至少分成 `amountInRaw、quotedOutRaw、minOutRaw`：前者是计划花费，第二个是快照估得的代币毛输出，第三个才是合约成功必须满足的最低接收量。另列 `estimatedGasCostOutRaw、netOutRaw` 用于经济性比较，不能把它们冒充到账数。实际输出来自链上执行与接收者变化，receipt 成功后还要经过确认与最终性判断。

## 第 2 层：十进制展示必须还原为最小整数单位

**面试官：** 你区分了 `amountInRaw` 和展示值。如果 API 接收字符串“10000”，Go 可以转 float64 再乘 decimals 吗？

**面试者：** 不可以，金额走十进制字符串校验和大整数运算。本例 USDC 为 6 位，`amountInRaw=10000000000`；WETH 为 18 位，两者不能直接用同一数量尺度相除。先从绑定的代币元数据取 decimals，按十进制位拆解，拒绝负数、超范围和超出支持精度的输入，不静默四舍五入。池 A 的 USDC 储备为 `600000000000 raw`，WETH 储备为 `300000000000000000000 raw`。对大整数 API 还要明确结果写入哪个接收变量，防止中间运算改掉后续还要使用的输入。输出在比较完成后再格式化，不把展示截断结果送回计算链路。

## 第 3 层：逐腿整数舍入必须复现合约公式

**面试官：** 已经用整数了，是否把理想汇率乘输入就行？6,000/4,000 拆分的输出究竟怎么得到？

**面试者：** 要按池模型算实际交易规模，不能用边际价替代有限输入报价。A 储备为 600,000 USDC/300 WETH，B 为 400,000/200，均收 0.3% 池费。对每个 v2 池，用 raw 整数执行 `out=floor(997*a*Rout/(1000*Rin+997*a))`，先完整乘法，再除法向下取整，不能先算 `floor(997*a/1000)` 改变结果。A 输入 6,000 USDC 得 `2.961474103191183896 WETH`，B 输入 4,000 得 `1.974316068794122597`，逐腿取整后相加为 `4935790171985306493 raw`。每腿必须先完成自身的整数舍入，不能先把两池储备相加后只除一次。中间乘积使用足够位宽的大整数，校验结果符合合约范围，不截断为六十四位，也不先截成展示小数再求和。v3 必须用跨 tick 的协议整数数学，不能把同一恒定乘积公式强套过去。

## 第 4 层：可比候选必须共享快照、输入和执行语义

**面试官：** 这个拆分输出比单池高，能否直接叫最优报价？如果两条候选复用了同一池呢？

**面试者：** 只能叫已评候选中的赢家。相同快照下，全 A 为 `4.903519845238290407 WETH`，全 B 为 `4.863770519794131277`，6,000/4,000 为 `4.935790171985306493`；这不证明搜索过所有路径与比例。候选必须同 chainId、代币地址、方向、总输入、blockHash 和执行规则，输入腿之和严格等于 `10000000000 raw`。本例两池互不共享，所以可以独立算后相加；复用同一池时必须按固定执行顺序更新虚拟储备，不能让两腿都消费初始状态。快照还要覆盖结构、fee、decimals、能力和所需完整 v3 ticks，否则数字即使精确也不可比较。更新虚拟状态时，输入储备增加实际全额输入，输出储备减少本腿输出；手续费留在池中，不能把扣费后的有效输入误当成储备实际增量。

## 第 5 层：代币毛输出与经济净值是两套指标

**面试官：** 已评候选中拆分毛输出最高，那用户一定应该选拆分吗？能不能把 gas 一并扣在 WETH 输出里？

**面试者：** 应用同一成本口径比较，但不能改写实际到账语义。教学假设有效 gas 单价为 2 gwei，单 A 为 120,000 gas，双池为 180,000 gas，分别花 `0.00024 ETH` 和 `0.00036 ETH`；仅假设 ETH 与 WETH 估值 1:1，经济净值为 `4.903279845238290407` 和 `4.935430171985306493 WETH`。这些 gas 是教学常量，不是实测，具体费用模型见 [第 8 题](08-Gas估算与费用归一化.md)。100 USDC 时，全 A 毛输出 `0.049841717967864339`，60/40 拆分为 `0.049845030450464088`，多出的约 `0.00000331248 WETH` 小于额外 gas `0.00012 WETH`，拆分反而不划算。池费已在公式中计入，不能再减一次 0.3%。接口同时返回毛输出、成本估值、净值与排名策略，前端不得只显示一个未标注的“最终接收”。候选排序必须使用同一时点的费用假设，不能给单池取低价而给拆分取另一时点高价。

## 第 6 层：滑点下限约束代币交割，不约束经济净值

**面试官：** 既然净值更贴近经济性，50 bps 的 minOut 应该基于净值设置吗？价格影响是不是也再扣 50 bps？

**面试者：** minOut 基于本次代币毛输出，不能拿 gas 折算净值代替。对拆分结果计算 `floor(4935790171985306493*9950/10000)`，得到 `4911111221125379960 raw`，即 `4.911111221125379960 WETH`。价格影响已经体现在有限输入的池报价里；50 bps 是在该报价基础上允许的执行输出恶化，不是再次收取池费或重复计算价格影响。Router 验证 recipient 本次新增的总 WETH 不低于下限，并检查 deadline；不能用 Router 原有余额凑数。任何腿失败都回滚，swap 失败仍耗 gas，独立 approve 不在该原子范围内。前端显示倒计时也不能替代链上检查。这个下限不是目标成交价，更不是保证成功率的承诺；愿意接受更多输出恶化，不代表愿意接受任意授权、任意接收者或额外输入。

## 第 7 层：用确定性绑定阻止“同名报价、不同计划”

**面试官：** minOut 已正确，但报价被缓存后换了接收者，或者 A、B 顺序被交换，怎么发现它已不是原报价？

**面试者：** 报价对象绑定 `chainId/blockNumber/blockHash、policyVersion、requestHash、orderedPlanHash`，同时绑定 `caller/recipient/amountIn/minOut/deadline、router/spender/calldataHash`。requestHash 来自规范化请求，金额用 raw、地址用确定性编码，不能把同一语义的不同字符串随意当不同请求；orderedPlanHash 必须保留腿顺序、池与金额，不能为了“稳定”按地址重排。最终 calldataHash 与钱包待签内容核对，任何执行字段改变都重新构造绑定。gas 折算的价格来源、时间和费用策略也应留作排名证据。哈希保证可检测的不一致，不代表合约自动认可链下报价，也不能阻止链上状态随后变化。

## 第 8 层：错误与降级也必须保持统一的报价契约

**面试官：** 如果一个 v3 候选缺 ticks，另一个候选缺 gas 数据，服务还能返回“最佳净输出”吗？怎样避免半真半假的精确数字？

**面试者：** 缺 ticks 的候选不能按完整报价参与比较，返回明确的不可报价原因；缺 gas 则不能把未知成本当零。可以拒绝净值排名，或显式切换为“仅比较可计算毛输出”，同时标明候选覆盖范围、排除原因和策略版本，不能沿用原来的最佳净值标签。复算证据要包含快照、模型、逐腿 raw 输入输出、合计、成本与舍入规则。并发 latest 不是固定视图，EIP-1898 不支持时必须显式降级或拒绝；旧分支快照可审计但不能用于新执行。最终返回的是可解释的估算契约，不把 quote、broadcast、receipt、confirmed、finalized 或展示阶段混成“成交已完成”。

## 本题收束

- **讲透机制：** 固定 ExactIn 语义，十进制输入转 raw 整数，逐腿复现合约舍入，在共同快照和成本口径下比较；毛输出负责交割估算，净值负责经济排名，minOut 负责链上保护。
- **容易答错的边界：** 不能重复扣池费，不能从 minOut 扣用户另付的 gas，不能用浮点数或展示截断参与计算，也不能把已评候选赢家写成全局最优。ETH 折成其他输出币必须另外声明价格来源与陈旧性。
- **反例与验证：** 复算全 A、全 B 与拆分的 raw 输出；将总和先取整与逐腿取整作对照；用 100 USDC 场景证明毛输出排序不等于净值排序；再交换共享池腿顺序，检查虚拟状态更新。跨链、CEX、RFQ 涉及不同费用、履约和时效语义，只能另设比较契约，不能直接塞入本题口径。
