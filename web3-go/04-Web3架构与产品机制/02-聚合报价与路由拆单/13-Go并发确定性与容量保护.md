# 大问题 13：Go 报价服务怎样兼顾稳定结果、低延迟与过载保护？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| H 与不可变快照 | H 代表一份已固定身份的链上状态；不可变表示发布后不再改写。 | 所有候选读同一底稿，不靠加锁把不同区块的数据伪装成同一版本。 |
| 候选计划与 overlay | 候选是一整套待比较执行方案，overlay 是它自己的临时池状态层。 | 完整候选之间可并行；同计划共享池的两腿仍按实际顺序模拟。 |
| big.Int 与接收者 | big.Int 是 Go 大整数，运算接收者就是结果写入的对象。 | reserve.Mul(reserve, amount) 会改储备，外层 map 没改也不代表只读。 |
| 深拷贝与所有权 | 深拷贝真正复制内部数值；所有权说明谁能改、谁负责释放。 | 复制结构体或切片不够，结果发布后不能还被 worker 的临时对象覆盖。 |
| scratch 与 sync.Pool | scratch 是计算缓冲，sync.Pool 是可复用对象的临时池。 | 结果若仍指向缓冲，归还后别的任务清零就会篡改已报金额；对象池不是可靠缓存。 |
| worker、collector 与总序 | worker 计算，collector 汇总，总序为所有候选规定稳定先后规则。 | 只有 collector 决定最终计划，按净值、整计划 gas 和规范标识排序，不按谁先完成。 |
| goroutine、channel 与 errgroup | Go 并发任务、通信通道和协同等待任务的工具。 | 通道发送不延长对象所有权；一个普通候选失败也不应自动取消所有候选。 |
| context 与取消 | context 携带截止时间和取消信号。 | 长计算要检查取消，结果发送也要可退出，避免请求结束后任务仍永久卡住。 |
| RPC 与 worker pool | RPC 是节点调用接口，worker pool 是固定数量的执行任务。 | 工作线程、任务队列与调用寿命都设上限，并由统一协调者关闭结果通道。 |
| 确定性数量预算与墙钟预算 | 前者限制算多少项，后者限制最多花多久。 | 数量预算便于回放，时间上限保护服务；超时前收齐的集合仍可能因调度不同而变化。 |
| best-found/incomplete 与冻结 | 已找到最好但未完整评估；冻结指不再修改已交付结果。 | 晚到候选不能悄悄改路线，重报要给新版本并重新确认。 |
| 全局配额与资源隔离 | 配额限制所有请求总消耗，隔离给不同职责保留容量。 | 请求内有界不等于进程有界，报价洪峰不能挤死已提交交易的未知结果追踪。 |
| minOut、授权与降级 | minOut 是链上最低收币量；授权是代币拉款许可；降级是明确缩小能力。 | 可少搜路径，但不能放宽下限、忽略授权或省掉最终保护来换吞吐。 |
| 共享加载与生命周期 | 多个请求共用一次数据读取，以及底层读取何时开始、取消和结束。 | 第一个等待者取消，不能连带杀死其他请求；共享加载本身也须有超时上限。 |
| H2、tick 与分层缓存 | H2 是另一状态版本，tick 是集中流动性价格刻度；分层缓存区分拓扑、池状态和金额。 | 不能拿 H 冒充 H2，缺 tick 不算完整，100 USDC 稳定币报价也不能复用于 10,000 USDC。 |
| profile、GC 与分位延迟 | profile 是性能剖析，GC 是垃圾回收，分位延迟用来观察较慢请求。 | 先找到分配与尾延迟瓶颈再池化，并区分队列、节点、模拟、汇总和编码耗时。 |
| -race 与串行参考 | -race 辅助发现数据竞争，串行参考是固定条件下不并行的对照实现。 | 逐候选对 raw 最小单位整数、费用、计划和 hash 指纹；没有竞争报告不等于业务正确。 |

## 把整篇文章压缩成一个故事

小林请求一份聚合报价，服务让多个 worker 从同一快照 H 计算独立候选，每个计划独占自己的数值和 overlay。一个 worker 很快算完，却把仍引用 scratch 的输出发送后马上归还对象池；下一任务将缓冲清零，collector 眼前的报价也跟着变了。修复不是给外层 map 加锁，而是让结果真正脱离临时对象所有权，共享底稿永不成为可写接收者。

金额不再串改后，小林仍发现两次超时返回的赢家不同。collector 虽然稳定排序，但两次在时间上限前收齐的候选集合不同，排序不能补回没算完的信息。系统因此同时设置数量预算和时间上限，记录完成、失败与超时的候选，冻结已交付结果，并诚实标注 best-found/incomplete；晚到的更好方案只能形成新报价，不能偷偷替换小林正在确认的计划。

高峰期很多人同时询价，系统再限制全局 RPC、在途请求和总模拟量，并给已提交交易追踪保留独立资源。热点读取可以合并，但一个等待者取消不能拖掉其他人，更不能把 H 的数据充作 H2。扩大并发或启用池化之前，用固定状态和候选集对照串行结果、打乱完成次序、检查取消与底稿未变；这些是待实施验收方法，不是文稿已经给出的压测成绩。并发只负责提速，不负责创造优化确定性或成交保证。

[返回专题总览](README.md)

**流程位置与核心机制：**贯穿快照读取、候选模拟、整计划择优与接口返回。本题深入 Go 内存所有权、并发完成协议和预算；快照的链上身份由第 03 题建立，报价算法由第 04—07 题建立，不通过加锁掩盖不同状态版本。

## 第 1 层：哪些计算可以并行，哪些不能？

**面试官：**聚合器用 Go 并行计算很多路径，你怎样降低延迟，又不让并发改变最终路由？

**面试者：**我先把请求固定到一份完整的不可变快照，再并行模拟相互独立的候选计划。每个候选读取相同 H，但拥有独立的可变数值和池状态 overlay；同一个计划内部若重复使用池，就按真实链上调用顺序执行，不能把共享状态的两腿并行独立报价。

worker 返回规范化结果，只有 collector 可以更新本请求的候选集合并生成最终结果。collector 按净价值、整计划 Gas、规范计划标识等显式总序选择，不按完成先后选择。这样并发用于加速独立计算，不成为隐含业务排序权。即使服务合并部署，这些内存写权限也不应混在一起。

## 第 2 层：只读快照为什么仍可能被 big.Int 写坏？

**面试官：**你说候选只读同一快照，但池储备使用 `*big.Int`。有人写 `reserve.Mul(reserve, amount)`，外层没有更新 map，算只读吗？

**面试者：**不算。`big.Int` 的运算通常会写接收者，外层 map 不变并不代表其指向的数值不变。这个例子直接修改共享储备，其他候选会看到被乘过的状态，甚至只出现业务错误而不一定稳定触发崩溃。

我会让快照的数值对象发布后永不作为可写接收者，把接口写权限限制在适配器内部；每个候选用独立临时值作为接收者，确需复制时用 `new(big.Int).Set(source)`，不通过浅复制结构体宣称独立所有权。返回结果同样不能引用即将复用的 scratch。Go 的引用约束不是深度只读类型，仍需代码约定、审阅和验证共同保证。

## 第 3 层：对象池是否会重新破坏所有权？

**面试官：**每个候选都分配临时大整数，成本很高。你用 `sync.Pool` 复用对象，worker 返回结果后就归还 scratch，可以吗？

**面试者：**只有结果已经脱离 scratch 所有权才可以归还。假设 `result.amountOut` 指向池中的一个 `big.Int`，worker 发送结果后立刻 `Put`，下一个任务把该值清零，collector 读到的报价就改变了；channel 发送完成只保证特定同步关系，不保证发送对象今后不被修改。

我会区分工作缓冲和已发布结果：返回结果深拷贝必要金额，或明确把对象所有权转交 collector 并由它在最后释放，不能两种协议混用。`sync.Pool` 也不是必须保留对象的缓存，随时可能丢掉对象。先用 profile 确认分配是瓶颈，再做池化；优化必须保留固定输入的金额与计划一致性，而不是只看分配次数下降。

## 第 4 层：worker pool 怎样处理取消与单个候选失败？

**面试官：**所有权解决了，但请求超时后 worker 还在算；又有一个池调用出错。你会用一个 `errgroup`，遇错取消所有候选吗？

**面试者：**不直接把所有候选失败都当成请求级错误。不可用的单个池、某条路径不支持的 tick 范围，通常应返回带类型的候选结果；快照身份损坏、请求约束错误等才可能要求整体失败。否则一个低质量候选就能杀掉已经可用的主路径。

并发使用固定 worker 数、有界任务队列和总请求 context，每个 RPC 派生更短的超时。worker 在循环、跨 tick 等长计算边界检查取消；外部库若不支持取消，还要限制并发和调用寿命。发送结果时同时选择 `ctx.Done()`，防止 collector 已退出却永远阻塞发送。任务调度方关闭任务入口，统一协调者在 worker 全退出后关闭结果通道，不能让多个 worker 各自关闭共享通道。

## 第 5 层：超时降级会不会让结果依赖机器调度？

**面试官：**你说 collector 稳定排序，但 100 毫秒只收齐部分候选。两次运行收齐的集合不同，结果仍然可能不同，怎么解释“确定性”？

**面试者：**必须缩小承诺范围：同请求、同快照、同策略、**同一候选及其有效结果集合**，稳定得到相同计划；墙钟预算下收齐的集合不同，不能保证赢家相同。只排序不能把信息缺失消除。

我会同时设置确定性的展开/模拟数量预算与墙钟保护。数量预算便于回放，墙钟上限保护服务。达到上限后 collector 冻结结果集，记录哪些候选完成、超时或失败，返回 `best-found/incomplete`，或在产品要求完整评估时拒绝返回。晚到结果不能悄悄改已确认计划。需要重报就产生新报价版本，并按用户保护规则重新确认。候选覆盖信息是报价质量的一部分，不是内部日志可有可无的细节。

## 第 6 层：稳定结果如何避免被请求洪峰拖垮？

**面试官：**你已有请求内预算，但大量用户同时请求复杂资产对，每个请求都能占满 worker。怎样限制整体负载，不拖死交易追踪？

**面试者：**请求内有界不等于进程整体有界，还要限制在途请求、全局 RPC 并发和总模拟预算。按资产对、金额档位或复杂度设置调度配额，防止一个稀疏图请求耗完所有资源；队列满时明确拒绝或按策略缩小候选，不无限排队后返回已过期报价。

报价计算和已提交交易追踪应采用隔离资源预算，至少避免共享一个可被搜索任务占满的 RPC 信号量。报价慢可以让用户重报，提交未知若长期不恢复会诱发重复执行风险。降级可以减少跳数、路径数，或只评估已知直接池，但必须改变策略版本/覆盖说明；不能擅自放宽 minOut、忽略授权或跳过最终链上保护来换取吞吐。

## 第 7 层：热点缓存与合并加载有什么新竞争？

**面试官：**为了减少热点池的 RPC，你把所有请求合并到同一个加载任务。第一个请求取消时，其他请求的共享加载也被取消，怎样修正？

**面试者：**共享加载的生命周期不能直接绑定第一个等待者。等待者可以分别停止等待，底层加载由独立的短生命周期 context、引用管理或统一刷新任务控制，且有全局并发与时间上限，不能因为“共享”就无限后台运行。

合并键必须包含完整状态身份和数据需求。`H` 上的 A 池储备可以共享，`H2` 上的请求不能拿 H 的结果冒充命中；v3 的已加载 tick 范围也不能被当成完整范围。加载完成后一次发布完整只读对象，失败不发布半成品。拓扑缓存、同块池数据与金额报价分层：如果把 100 USDC 的金额结果错误复用于 10,000 USDC，再完美的取消协议也救不了业务正确性。

## 第 8 层：怎样证明这些优化没有改变业务结果？

**面试官：**你修好了缓存与取消，准备扩大 worker 数并开启池化。上线前具体比较什么，怎么找尾延迟和正确性之间的取舍？

**面试者：**我先固定快照、候选集合、费用和策略，用串行参考实现与并行实现逐项比较每个候选的原始整数输出、费用、最终计划和规范 hash。打乱任务完成顺序、map 插入顺序和取消时机，检查已冻结结果不再变化；重复报价后验证原始快照内容未变。`-race` 能辅助找数据竞争，但不能证明候选集合、金额口径和内存生命周期正确。

容量上分开观察队列等待、RPC、图展开、跨 tick 模拟、collector 和编码的分位延迟，再结合分配、GC、goroutine 数和取消后的存活任务定位瓶颈。按并发和复杂度逐步提高负载，验证拒绝、降级和追踪隔离。这里描述的是验收方案，不是本稿已运行的压测或性能结论；只有业务结果一致，性能提升才值得接受。

## 本题收束

- **讲透的机制：**不可变输入、独占可变数值、明确结果所有权、单 collector 决策、有界任务与取消、有限覆盖下的诚实确定性、报价与提交追踪资源隔离。
- **最容易答错的边界：**map 不变不是数值只读；channel 不延长对象所有权；稳定排序不保证超时前收齐相同候选；请求内限流不等于全局容量保护。
- **反例验证：**让一个 worker 返回仍引用 scratch 的输出后立刻归还对象，另一个任务将其清零；若 collector 的金额随之改变，方案不成立。再让最优候选恰好迟到，系统应标注未完整搜索或拒绝，而不是输出“全局最优”。
