## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EVM、DEX 与非托管 | EVM 是以太坊虚拟机，DEX 是去中心化交易所；非托管表示平台不持有用户资产。 | Go 只能估算，不能先占住池深或用户资金。 |
| ExactIn、ERC20 与 rebase | ExactIn 固定输入，ERC20 是代币标准，rebase 会自动调整余额。 | 本题限普通无税、无 rebase 代币，全输入在同笔交易用完，不做部分填充。 |
| USDC、WETH 与 raw | USDC 是稳定币，WETH 是包装 ETH；raw 是最小单位整数。 | 输入 6 位、输出 18 位，10,000 USDC 为 10,000,000,000 raw。 |
| poolID、fee 与 direction | 池的真实身份、手续费和兑换方向。 | 同链同合约即同一池，反向边、别名或不同适配器标签不能造出第二份深度。 |
| 共享代币与共享池 | 经过同一种币，不等于使用同一份可变储备。 | A、B 都换 USDC/WETH 但池独立；两条路都指向 A 才必须耦合模拟。 |
| chainId、blockNumber、blockHash | 链身份、块高和具体区块指纹。 | 所有候选从同一个完整快照起步，不用新状态修补某条旧报价。 |
| a、Rin、Rout、γ 与 floor | 输入量、两侧储备、扣费系数及向下取整。 | γ=997/1000 只进入报价公式，更新输入储备仍增加完整 a。 |
| 实际余额与储备相等 | 池真正持有的币数等于其记录值。 | 有人直接捐赠可能打破相等，本简化模型发现后拒绝，不能继续照抄储备更新式。 |
| overlay 与写集检查点 | overlay 是候选私有状态；检查点记下分支修改前的旧值。 | 同一计划按顺序共享更新，分支失败要恢复全部修改，不能污染别的候选。 |
| big.Int 与深拷贝 | Go 大整数会写运算接收者，深拷贝才有独立数值。 | 只复制外层对象不够，否则并发候选仍可能互相改储备。 |
| 缓存依赖版本 | 缓存需要说明它基于哪份状态。 | 同一个区块和输入不够，还要区分当前 overlay 已被前腿改到了哪一步。 |
| AMM v2/v3、tick 与 latest | AMM 是自动做市商，v2 用储备曲线，v3 用价格区间，tick 是价格刻度，latest 是节点当前最新状态。 | 所需区间数据不全就关闭候选，不能补另一时刻的状态或套 v2 公式。 |
| 有序计划与原子性 | 有序计划固定调用先后；原子性保证同笔全成或全退。 | 原子性不代表调用可交换；换顺序或合并同池调用都要重新报价。 |
| minOut、bps、actualOut 与 deadline | 最低输出、万分之一、实际输出与执行截止时间。 | 50 bps 下限检查收款人本次新增输出，不能用合约历史余额凑够。 |
| gas 与净值 | 另付的执行费及扣费后的经济估值。 | A+B 的教学 gas 不能直接套给共享池计划；回滚仍耗 gas，不从 minOut 扣。 |
| best-found/incomplete | 已发现最好结果，但搜索覆盖不完整。 | 可以保守拒绝共享池，只能声称在支持空间内选优，不能冒称全图最优。 |
| CEX 与 RFQ | CEX 是中心化交易所，RFQ 是询价交易。 | 这类交易不在本文共享链上池状态的主线，不继承单 Router 全回滚承诺。 |

## 把整篇文章压缩成一个故事

小林的 10,000 USDC 原本分给两个独立池：A 6,000、B 4,000，预计拿到 4.935790171985306493 WETH。后来注册信息出错，两条路线名字不同，实际却都调用 A 池。如果各自从 A 的原储备报价，系统会错误展示 4.942308159496938314 WETH；数字每一位都可以算得精确，整份估算仍然不可能按这个前提执行，因为同一份初始深度被用了两次。

系统修正池身份后，按先 6,000 再 4,000 的顺序在同一个私有 overlay 中重放。第一腿后 A 的 USDC 储备变成 606,000，WETH 变成 297.038525896808816104；第二腿只能输出 1.941988434651949806 WETH，总数为 4.903462537843133702。若先 4,000 再 6,000，总数又变成 4.903462348083510117；若合成一次 10,000 输入，则是另一份需重新报价的计划。交易全成全退不代表这些调用可以随意交换或合并。

小林原本确认的 A+B 下限是 4.911111221125379960 WETH，错误 A+A 计划实际低于它，可信 Router 应让整笔换币回滚，不能保留第一腿，也不能拿旧余额补差。系统可以选择暂不支持共享池，但必须明示候选覆盖范围；要支持就保存每步状态与顺序，并隔离不同候选。这样才是修复模型，而不是靠提高滑点让用户吞掉高估。

**流程位置与核心机制：** 位于候选组合和拆单评价之间，并贯穿最终执行校验。必须先识别路径间共享的池状态，再在同一私有 overlay 内按 Router 的真实调用顺序重放，不能先把各腿独立报价相加再补一个折扣。

统一限定同链 EVM 非托管 DEX 聚合、ExactIn、普通 ERC20，无转账税、无 rebase、无平台费或返佣；USDC 6 位、WETH 18 位，不跨链、不执行 CEX、不以 RFQ 为主线。权威余额及储备在链上，Go 仅持同一 `(chainId, blockNumber, blockHash)` 的不可变快照。多路径在一个 Router 交易中顺序执行且全部回滚；quote 不锁价、不占资，gas 由用户另付。

## 第 1 层：共享的是代币，还是某个具体池的可变状态？

**面试官：** 两条路径都经过 USDC，是不是就不能并行报价或拆单？

**面试者：** 不应按代币重叠判断，要比较实际池集合。节点使用 `(chainId, tokenAddress)`，边保留 poolID、fee、direction；其中池身份应规范到链与合约地址，同一池的反方向、不同标签或不同适配器仍访问同一份状态。两条路径共享 USDC 但使用不同池，并不会相互改变对方储备；反过来，名称不同的两条候选也可能最终调用同一池。本例 A 为 600,000 USDC/300 WETH，B 为 400,000 USDC/200 WETH，手续费率都为 3/1000，扣费后的输入系数 γ 为 997/1000，池合约相互独立。因此 A、B 是可以独立报价的两份流动性，不能把同一个 A 登记两次冒充两个独立来源。

## 第 2 层：独立池为什么可以相加，成立条件具体是什么？

**面试官：** 已经确认 A、B 不同，怎样证明它们的拆分结果能够汇总？

**面试者：** 在同块快照和普通代币前提下，A 的兑换不改变 B 的报价状态，反之亦然；输入也必须分别固定且守恒。本例 amountIn 为 10,000 USDC，即 10,000,000,000 raw，A 输入 6,000 输出 2.961474103191183896 WETH，B 输入 4,000 输出 1.974316068794122597，总计 4.935790171985306493 WETH，即 4,935,790,171,985,306,493 raw。这里相加的是不相交池状态下的输出，不是任意路径的普遍规律；仍需保证真实 calldata 的资产传递与余额足够。拆分只是一个交易中的顺序调用，不是同时发生，也没有因为报价就占住两池资金。两腿可以并发计算各自输出，但执行编码必须保留明确顺序，并将输入不足或方向错误判为计划不可行。

## 第 3 层：把同一个 A 池当成两份来源，具体会高估多少？

**面试官：** 如果注册错误让两条候选都指向 A，但仍分 6,000/4,000，会出现什么数值问题？

**面试者：** 若两条腿分别从旧储备独立计算，6,000 USDC 得到 2.961474103191183896 WETH，4,000 得到 1.980834056305754418 WETH，看似能相加为 4.942308159496938314 WETH。这甚至高于正确的 A+B 拆分，但第二腿假设 A 完全没被第一腿成交改变，实际上买了两次同一份初始深度。这只是复用既有 A 的故障反例，没有新增第三个池。必须按规范化 poolID 检测交集，不能用路径名称或代币对去重；即使独立报价缓存命中、每腿公式都正确，总数仍是不可执行的估计，问题在状态依赖而非算术精度。不能用多扣一些滑点容忍来替代重算；这会把服务端高估转嫁成用户愿意接受的低成交价，而没有修复报价模型。

## 第 4 层：改用同一 overlay 后，第二腿实际应得到多少？

**面试官：** 找到了交集，那按照先 6,000 后 4,000 的顺序，具体怎样修正状态？

**面试者：** 按总览的余额与储备相等前提，采用 `out=floor(997*a*Rout/(1000*Rin+997*a))`；若同块发现未同步捐赠，本简化适配器直接拒绝，不能把储备当作实际余额。第一腿输出不变，之后 overlay 中 A 的 USDC 储备变为 606,000，WETH 变为 297.038525896808816104；输入储备增加完整 6,000，不能只加扣费后的 5,982，因为手续费也留在池内。第二腿读取新储备，4,000 USDC 仅得到 1.941988434651949806 WETH，两腿合计 4.903462537843133702，明显低于旧态相加的 4.942308159496938314。Go 只改该计划自己的 overlay，不改底层快照；池反方向边也要映射到这份已更新状态，不能各存一份互不关联的储备。每次状态写入应关联调用序号和旧值，方便复算差异；仅保存最后总输出，无法定位哪一腿错误读取了旧储备。

## 第 5 层：正确维护状态之后，调换两条腿是否一定等价？

**面试官：** 都在同一个交易内而且输入总额不变，先 4,000 后 6,000 能直接沿用上面的总输出吗？

**面试者：** 不能。这个 A 池反例中，先 4,000 的输出为 1.980834056305754418 WETH，再用更新状态处理 6,000，输出为 2.922628291777755699，合计 4.903462348083510117，与先 6,000 后 4,000 并不相等。手续费留池和逐笔状态变化使顺序进入计算，整数舍入也必须逐笔遵守；不能从“交易原子性”推出“调用可交换”。如果决定把两笔相邻同向 A 调用合并成一次 10,000 输入，则会变成全 A 输出 4.903519845238290407 的另一份计划，必须重新报价、估算 gas 与编码，不能仅在执行阶段静默合并。最终计划应绑定有序调用列表，而不只是绑定池集合；同一组池、同一总输入并不唯一确定报价。

## 第 6 层：多候选并发搜索时，怎样保证一个计划内共享、计划之间隔离？

**面试官：** 顺序已经影响结果，Go 同时评估很多顺序时，overlay 应怎样组织才不串状态？

**面试者：** 每个候选计划从同一个不可变快照派生独立 overlay，按确定的调用序列读取“本计划已写状态，否则底层状态”，写入后再推进下一步；分支探索要复制或回滚本分支的写集，失败分支不能把储备留给下一个候选。`big.Int` 也要深拷贝，不能共享可变接收者。不同完整计划可并发，单个共享状态序列不能拆成互不知情的逐腿任务。可用写集检查点记录分支开始位置，失败时逆序恢复所有池旧值，再探索下个分支；不能只恢复当前报错的池。缓存若只含区块与输入，会错误复用第一腿之前的报价，还应识别依赖池的 overlay 版本；缺少该上下文的缓存应直接绕过。状态不全、v3 实际跨越区间缺 ticks 或不支持的回调语义都要失败关闭，不得读 latest 或套 v2 公式补出一个成功结果。

## 第 7 层：状态模拟仍可能过时，链上怎样让错误计划不部分成交？

**面试官：** overlay 没串数据，但旧态高估的计划若被提交，最终由谁拦住？

**面试者：** Router 必须核验 deadline 与接收方最终 `actualOut >= minOut`，actualOut 应是本交易归属用户的实际新增输出，不能拿合约旧余额充数。正确 A+B 输出在 50 bps 滑点下，minOut 为 `floor(4935790171985306493*9950/10000)`，即 4,911,111,221,125,379,960 raw，不能扣 gas。若错误地执行 A+A，其真实总输出 4.903462537843133702 低于此值，应整体回滚；即便按错误旧态总数生成 50 bps 阈值，也仍会失败。原子性要求不能吞掉某腿失败后保留前腿成交，余额、授权或中间转账失败同样传播回滚；已经消耗的 gas 不会退还。回滚后若要重试，应重新取得一致状态、重新报价并核验当前授权和期限，不能把失败当作暂时网络波动而盲目重发旧计划。

## 第 8 层：如果暂不支持共享池，怎样降级才不变成“假最优”？

**面试官：** 全计划状态搜索和顺序枚举成本很高，能否直接禁止共享池？

**面试者：** 可以，明确把它作为保守基线：在组合阶段拒绝池集合相交的计划，仅比较独立组合，并说明覆盖范围，不声称任意图全局最优。本例独立 A+B 在固定候选集中获胜；教学气价统一为 2 gwei，单 A 120,000 gas、双腿 180,000 gas，成本分别为 0.00024/0.00036 WETH 等值，净值分别为 4.903279845238290407 与 4.935430171985306493。这些不是实测，也不能自动套到共享池计划。若候选枚举未完成，返回 `best-found/incomplete`；若没有支持的可行计划，就返回明确失败，而不是把共享报价伪装成独立报价后继续签名。

## 本题收束

- **机制：** 按真实池身份识别冲突，同一计划内共享私有 overlay、按真实顺序更新；计划之间严格隔离，最终输出与期限由链上兜底。
- **最易答错边界：** 同代币不等于共享池；同池反方向仍共享；v2 储备增加完整输入；原子性不代表顺序无关。重排、合并或替换路径都必须重新报价，不能沿用旧 minOut。
- **反例验证：** 复用 A 的两条独立旧态报价合计 4.942308159496938314，实际顺序执行仅 4.903462537843133702 WETH；它不是给 quote 加几位小数就能修好的误差。提交后若不足 minOut，所有腿回滚且用户仍付已消耗的 gas。
