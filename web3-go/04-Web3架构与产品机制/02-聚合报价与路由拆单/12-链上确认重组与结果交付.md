# 大问题 12：交易已有 receipt 后，怎样确认真实成交、应对重组并可靠交付可撤销的结果？
<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| EVM、DEX、ExactIn 与 ERC20 | EVM 是以太坊虚拟机，DEX 是去中心化交易所，ExactIn 固定输入，ERC20 是代币标准。 | 本题同链非托管、普通无税无自动余额重设代币，不把其他产品的成交语义带进来。 |
| USDC、WETH、raw 与 bps | USDC 是稳定币，WETH 是包装 ETH，raw 是最小单位，bps 是万分之一。 | 输入 6 位、输出 18 位；10,000 USDC 拆分的 50 bps 下限为 4911111221125379960 raw WETH。 |
| receipt 与 status | receipt 是交易执行回执，status 表示顶层调用成功或回滚。 | status=1 不自动证明执行了目标换币，空调用或错误 Router 也可能成功。 |
| sender、nonce、to、value、calldataHash | 发送者、交易序号、目标、原生币金额及合约指令指纹。 | 先用它们匹配实际交易和用户确认计划，再判断目标业务是否成功。 |
| Router、recipient 与 actualOut | 受信执行合约、收款人及本次实际输出。 | 合约应隔离历史余额、用完输入，并强制收款人本次增量达到下限。 |
| Transfer、日志地址与 trace | Transfer 是代币转账事件，日志地址说明谁发出事件，trace 是调用轨迹。 | 结合可信代码、实际指令与本交易证据归因，不能只认同名事件或块末余额差。 |
| chainId、blockHash、txHash、logIndex | 链、具体区块、交易与日志序号的身份字段。 | 原始证据带分支身份，交易重入块时不会混成同一条永远有效的旧观察。 |
| canonical 与确认深度 | canonical 指当前规范链；确认深度描述入块后上面叠了多少块。 | 先验区块哈希仍规范，再按声明口径累计，不能所有链统一等十二块就算最终。 |
| safe、finalized 与 L2 | safe/finalized 是节点提供的安全或最终性阶段标签；L2 是二层网络。 | 必须按目标链解释，二层入块与底层结算也不是同一保证。 |
| 重组、pending 与 UNKNOWN | 重组是规范分支改变，pending 是待入块，UNKNOWN 是结果证据不足。 | 旧成功块失效后重新核验同 nonce 组，不能只把确认数清零却保留成功结论。 |
| revision 与撤销事件 | revision 是递增修订号，撤销事件指出哪条旧结论失效。 | 保存历史，不删旧成功；新撤销版本高于旧成功版本。 |
| outbox 与本地事务 | outbox 是随业务结果一起保存的待发送事件表。 | 结果和待发事件同库原子落地，进程崩溃后仍能补投，不代表数据库能回滚链上执行。 |
| eventID、inbox 与至少一次投递 | eventID 是稳定消息身份，inbox 保存消费去重记录，至少一次意味着可能重复发送。 | 去重记录与投影更新同事务；同消息再到不能再做一次业务。 |
| 增量事件与快照 | 增量描述一步变化，快照描述完整当前状态。 | 增量版本有缺口就补齐，旧版本不能覆盖新版本；不能把两类协议混用。 |
| 投影、webhook 与交付状态 | 投影是结果的页面读模型，webhook 是向外部地址推送，交付状态记录是否送达。 | 页面离线或通知失败不改变链上成交，重试的是通知而不是换币。 |
| gas、approve 与原子边界 | gas 是执行费，approve 是独立授权，原子边界是同笔全成全退的范围。 | 换币回滚不撤销已耗费用和前一笔成功授权，也不包含数据库或外部通知。 |
| AMM v2/v3 | AMM 是自动做市商，v2 用储备曲线，v3 用集中流动性区间。 | 主例为两个独立 v2 池；对其他链上协议也须核对该区块实际执行的受信结算代码。 |
| CEX 与外部执行 | CEX 是中心化交易所；外部执行不在同一笔链上调用树中。 | 中心化交易所、跨链和其他独立交易不能借用本文单 Router 全成全退承诺。 |

## 把整篇文章压缩成一个故事

小林的 10,000 USDC 换币返回了 status=1 的回执，页面没有立刻认定永久成功。观察服务先核对链、发送者、nonce、真实 Router 指令，再核对可信结算事件和本次资产证据，确认执行的是 A 6,000／B 4,000 这份计划，收款增量不低于 4.911111221125379960 WETH。它不会拿小林当前余额减上一块余额凑证明，因为同块可能还有别的转账。

交易在规范链上累积确认后，系统按本链策略形成结果，并把业务修订和待发 outbox 事件放进一个本地事务。即使刚落库就崩溃，也能恢复投递；消息重复时消费者用稳定 eventID 去重。随后原成功块被重组掉，系统保留旧证据，发布更高 revision 的撤销，并重新追踪原交易或同 nonce 胜出者，而不是把确认数归零却继续展示成功。

假设撤销 revision 8 先送到，旧成功 revision 7 后送到，页面仍应保留更新的撤销判断；增量缺版本就补事件或拉权威快照。小林手机离线、webhook 重试都只是交付问题，不意味着链上没成交，更不能自动补发兑换。最终页面追上的是带确认依据、可被合法修订的业务结论，通知成功也不把尚可重组的结果变成不可撤销事实。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题承接广播追踪，聚焦“执行证据—规范链确认—重组纠偏—可靠交付”。基线是同链 EVM、非托管 DEX 聚合 ExactIn，普通 ERC20，无税、无 rebase，用户自付 Gas；主线为 v2/v3 AMM。单笔 Router 交易按固定顺序执行所有腿，全成功或回滚，不支持部分填充。Go 只估算，quote 不预留资金、不锁价，链上余额、储备、allowance、nonce、receipt 才是权威。

例子采用两个独立 v2 池：A 为 600,000 USDC／300 WETH，B 为 400,000 USDC／200 WETH，手续费均为 0.3%。10,000 USDC（6 位精度）拆为 A 6,000、B 4,000，WETH 为 18 位精度；quotedOut 为 `4935790171985306493 raw = 4.935790171985306493 WETH`，50 bps 滑点下 minOut 为 `4911111221125379960 raw = 4.911111221125379960 WETH`。收到 receipt 只是开始核验，既不是页面立即标绿的充分条件，也不是通知永不撤回的承诺。

## 第 1 层：status 为 1 为什么不够证明业务成功？

**面试官：** 节点返回 receipt.status 等于 1，说明整笔交易没有回滚，为什么还不能直接标记这一万 USDC 的兑换成功？

**面试者：** status 为 1 只说明该交易在那个区块中的顶层执行成功，不说明它一定执行了目标业务。应先匹配 chainId、sender、nonce、交易 to／value／calldataHash 和已确认计划，再验证受信 Router 的结算日志及本次资产增量证据。空调用、错误 Router，甚至会吞掉内部失败的另一套合约，都可能返回成功。基线 Router 必须强制检查全量花费一万 USDC、两腿顺序和 recipient 本次 WETH 增量至少为 minOut，否则整体 revert。只有交易身份、受信代码语义和结算证据都对应，才能认定“目标计划已执行”，随后还要处理区块是否规范、确认是否满足策略的问题。

## 第 2 层：怎样核验本次到账，而不误用块末余额？

**面试官：** 上一答要求资产增量证据，能否查询收款人当前 WETH 余额减去上一个区块余额，差值够大就通过？

**面试者：** 不能，两个块间可能有其他转账，同块也可能有用户自己的交易，块末差值不能归因到这一笔。我会依赖已认证 Router 在交易内记录基线、隔离历史余额、最终转账并检查 recipient 增量的执行语义，再核对其结算事件中的 caller、recipient、token、amountIn、actualOut 与计划关联；如事件不含全部字段，则结合实际 calldata 解码。还应核对受信 token 的本交易 Transfer 记录，必要时用可验证的执行 trace 辅助归因。日志要检查发出地址，不能只认事件名称或 topic；两腿的池与顺序也应匹配 orderedPlanHash 所指计划，而不是只认一个相近的输出数。原始证据键可采用 chainId、blockHash、transactionHash、logIndex，保留区块身份，避免重入块后与旧观测混淆。receipt 不自带通用资产差值证明，Router 可升级时还要确认该区块执行的受信版本，不能拿今天的代码解释昨天的日志。

## 第 3 层：业务证据正确以后怎样累计确认？

**面试官：** 交易身份和结算事件都匹配了，是否再等固定十二个块，就能对所有 EVM 链宣布最终成功？

**面试者：** 不能套统一数字。先保存 receipt 的 blockNumber、blockHash、transactionIndex，并核对规范链该高度的区块哈希；只有匹配且链头建立在该块之上，才能累计确认。若采用含入块块的口径，深度是 headNumber 减 blockNumber 加一，口径必须写清。确认策略还要记录 chainId、policyVersion、阈值或 safe／finalized 依据，并区分链的共识与节点标签语义；某些 L2 的入块和底层结算也不是同一层保证。业务可在产品认可的确认级别形成结果，但不能把概率确认说成绝对不可逆。status 为 0 的执行失败同样需要规范性与确认检查，失败交易也可能被重组掉。

## 第 4 层：重组时为什么不是把确认数归零就完了？

**面试官：** 原 receipt 已有几次确认，后来同高度 canonical hash 变了；保留成功状态、把确认数清零，等待它重新长回来行不行？

**面试者：** 不行，旧 receipt 已不再证明当前规范链上的执行。应将其作为被孤立的历史观测保留，撤销据此形成的当前业务结论，并检查同 nonce 候选组在新规范链中的情况。若原交易重新入块或另一有效候选胜出，重新核验业务证据并从新 blockHash 累计确认；若只能看到 pending，则回到待入块；若没有可靠归属证据，则回到 UNKNOWN。不能只按 txHash 缓存永远成功，因为相同交易在不同前序状态下可能重入后回滚。deadline 已过也不能直接判历史失败，要看规范链是否存在到期前的执行；旧块里曾经成功，不代表今天仍有那次资产转移。

## 第 5 层：已宣布成功的结果如何撤销而不篡改历史？

**面试官：** 用户已经收到成功通知，重组后又回到 UNKNOWN；你是删除旧成功记录，还是坚持业务终态不能变化？

**面试者：** 两者都不合适。我会保留每次证据和判定，给业务聚合记录递增 revision；旧成功形成一个历史事件，重组形成新的撤销事件，说明撤销哪条结果、旧 blockHash、当前依据和新的未决状态。若产品在确认阈值达成时称其业务成功，就必须声明该级别的可撤销性；finalized 的保证也要服从具体链的安全假设，异常破坏时进入明确的纠偏流程。业务终态是按当时策略及证据给出的业务判断，页面只是该判断的异步投影，不能拿页面已显示成功阻止修正。也不能删除历史伪装成从未通知过，否则用户无法理解余额回退和后续重新确认。

## 第 6 层：链上已成功但通知任务丢失怎样恢复？

**面试官：** 上一答需要先改本地结果再发撤销事件，如果数据库更新成功后进程崩溃，消息还没发出，页面怎么知道变化？

**面试者：** 在同一个本地数据库事务里更新业务状态与 revision，同时写入 outbox 事件；事务提交后，派发器再投递，失败可重试。事件包含稳定 eventID、businessRequestID、revision、事件类型、证据块哈希和策略版本，重试不能重新生成 eventID。若链上已有结果而本地事务尚未提交就崩溃，由链上追踪任务重新核验并补记；若本地事务已提交但尚未派发，outbox 继续投递。这只保证本地结果与“需要发出的事件”同时落库，不是链上与数据库的分布式原子事务。链上不会等待数据库提交，DB 也不能 rollback 已入块交易，跨边界依靠恢复和重放闭环。

## 第 7 层：outbox 重复和乱序怎样不覆盖新结论？

**面试官：** 派发成功后标记已发送之前又崩溃，重试会重复；如果成功事件还比撤销事件晚到，消费者怎么处理？

**面试者：** outbox 通常是至少一次投递，不能许诺发送绝不重复。消费者以 eventID 做 inbox 去重，并把去重记录和页面投影修改放在同一个本地事务中；否则先去重后崩溃可能永久丢更新。再按 businessRequestID 检查 revision，旧版本不得覆盖新版本。若事件是状态增量，发现版本缺口应暂存并补取缺失事件或权威快照，不能盲目跳号；若协议明确提供完整快照，才按其规则接受更新。重组撤销是更高 revision，不是把 revision 倒退。短信、邮件或外部 webhook 不一定与消费者数据库原子，接收方仍需幂等或补偿，不能把页面去重能力扩大成所有外部副作用的 exactly-once。

## 第 8 层：怎样区分交易结果与交付结果？

**面试官：** 业务状态、outbox 和消费者都有证据了，如果用户页面离线，或 webhook 一直失败，系统应该把交易退回失败吗？

**面试者：** 不应该，交易是否成功由规范执行证据和确认策略决定，交付状态单独记录待发送、重试或已确认接收。页面恢复时带上已应用 revision 拉取当前权威快照并补齐事件，不能把“用户没看到”改写为“链上没成交”。反过来，通知成功也不阻止后续重组撤销，最终页面应展示最新判定、确认级别、相关 hash 及必要的撤销历史，而不是永远保留第一张成功卡片。可靠交付还以服务最终恢复、接收方可用为前提，不能承诺离线端即时收到。失败 swap 仍耗 Gas，独立 approve 仍可能有效，这些与兑换结果分别呈现；不因投递失败自动重发一笔交换，也不自动放宽 minOut 求一个新的成功结果。

## 本题收束

- **机制：** 先验证交易和受信结算语义，再按 canonical blockHash 与链相关策略确认；重组保留旧证据并发布高 revision 撤销。本地结果与 outbox 原子落库，消费者以 eventID 幂等、revision 保序，页面最终追上业务判断。
- **错边界：** receipt.status 为 1 不等于目标业务成功，块末余额差不等于本次到账，确认数不等于普适最终性；页面状态不是链上裁决，通知成功也不是不可撤销承诺。单 Router 原子性不能延伸到 CEX、跨链、其他交易或本地数据库。
- **反例验证：** receipt 来自错误 Router，即使 status 为 1 也不得交付目标成交；原成功块被孤立，应撤销而非删除历史；revision 8 的撤销先到、revision 7 的成功后到，页面不能被旧成功覆盖；消息重复不应再触发交换。这些反例分别检验执行归属、规范性和交付一致性。
