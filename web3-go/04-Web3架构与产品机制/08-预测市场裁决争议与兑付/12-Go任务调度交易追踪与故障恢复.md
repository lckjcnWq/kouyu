# 大问题 12：Go 怎样调度到期任务，在提交后崩溃、广播不明时恢复原交易？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| keeper / 受限热钱包 | 帮忙触发公开入口的执行者／支付执行费的系统签名账户。 | 只做合法到期调用，不替用户签提报、挑战、成交或领取。 |
| S / Proposed / Disputed / Finalized | 权威合约／暂定提报／争议中／业务终局。 | 到期先重读状态，不能按旧任务把已争议市场强制写成 YES。 |
| closeAt / challengeEnd / arbitrationEnd | 交易、挑战、仲裁的不同截止。 | S 自己执行时校验；Go 定时器只唤醒任务，不拥有延期或改判权。 |
| 业务任务键 | 给“推进哪个市场的哪个动作”一个稳定编号。 | 包含 chainId、S、marketId、动作，依赖提报时再绑定 proposalId。 |
| lease / epoch / fencing | 有期限的工作租约／接管代次／拒绝旧代次写入的围栏。 | 限制数据库协作，不是 S 验证的链上权限，更不能撤销已签交易。 |
| sender / nonce / 发送槽位 | 发送地址／其交易序号／被某任务占用的序号记录。 | 同地址串行分配，并对地址与 nonce 建唯一约束，不靠各 worker 独立读 pending 值。 |
| calldata / value / chainId | 调用内容／交易携带原生币数量／链身份。 | 连同目标 S、费用和任务一起保存，防止恢复时换成另一个业务。 |
| 原始签名交易 / txHash | 可重新广播的确定字节／该交易指纹。 | 必须先可靠落库再广播，签名器不能私自先发网络。 |
| RPC / mempool / Unknown | 节点接口／节点看到的待打包池／广播或执行待核实。 | 单节点看不到或超时，不构成“原交易从未发送”的证明。 |
| replacement / 候选集合 | 同 sender、nonce 的加速替换／新旧全部交易尝试。 | 加速不是新业务，通常保持目标和载荷，仅改费用；原候选仍可能先入块。 |
| receipt.status / 规范回执 | 执行状态标记／属于当前有效分支的回执。 | 节点收下不等于执行成功，成功回执还要核验事件、块和业务含义。 |
| 目标达成 / 原交易结案 | 市场已被合法推进／自己的发送尝试有了确切结局。 | 别人先最终化可满足目标，却不能伪造本钱包成功，迟到原交易仍需跟踪。 |
| context.Cancel / goroutine | 停止本地等待的取消信号／Go 轻量并发任务。 | 取消不能收回已签字节；租约接管也不能随意丢弃原 nonce。 |
| 有界 worker / 持久积压 | 限量执行者／保存在数据库的未完成任务。 | 内存只装工作集，队列满则停止预取，不为每个市场无限开并发。 |
| 背压 / 退避 / 抖动 | 放慢接入／稍后重试／错开重试时刻。 | 对限流要持久记录下次执行时间，给未知槽位核查留预算。 |
| 链最终性 / 业务前提失效 | 历史稳定阶段／原动作已不再合法。 | 非最终 nonce 观察可能回退，Disputed 不是无争议任务应盲重试的暂时错误。 |

## 把整篇文章压缩成一个故事

**起因：** Go 看到 M1 的 challengeEnd 为 04:10，保存无争议最终化任务；到期时仍要读取 S 是否 Proposed。worker 领取租约后，经同地址串行通道绑定发送 nonce，把目标、载荷、费用、原始签名交易和哈希可靠保存，才调用广播 RPC，不能只在内存注册一个定时回调。

**处理及异常：** 本文的故障链是“已经广播、响应丢失、worker 崩溃、租约被新实例接管”。新实例继承原槽位与所有候选，单个节点查不到仍标 Unknown；可在核验后重播相同字节，或为同 nonce 受控加速。此时别人已先最终化，任务目标可以据链事实标为已满足，但原候选仍可能迟到，不能伪造它的成功回执或盲换新 nonce 再发。

**结果及边界：** 迟到原交易由 S 的当前状态拒绝，不产生第二个向量，却仍可能耗 Gas；本地 context 取消和 epoch 围栏都不能使已签交易从世界上消失。恢复扫描用持久任务、有界并发、退避和背压保住核查能力，不承诺提高 worker 数就能提高链容量。keeper 只能花自己的 Gas 触发公开到期入口，不能因用户期限已过而补签挑战、代领或延长期限。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖“发现可执行的到期入口 → 持久化任务 → 分配发送 nonce → 保存签名交易 → 广播追踪 → 重核链状态 → 恢复或结束”。重点是 Go 编排怎样在不掌握用户私钥的前提下恢复，而不是重新设计裁决或领取合约；规范链回退与完整投影机制分别见第 11、13 题。

**必要前提：** 沿用总览的单链 EVM、不可升级 S 和一次提报、一次有效挑战、固定 K 的状态机。Go 不保管用户私钥，不替用户签署新的成交、提报、挑战或领取资格。系统 keeper 可以使用受限热钱包，为无人提报、无人挑战或仲裁超时后的**公开到期入口**支付 Gas；这不是代表用户领取。任务租约、数据库提交、RPC 返回、合约终局和链最终性分别成立，不能互相替代。

## 第 1 层：调度器究竟有权推进什么

**面试官：** 如果由你设计，Go 怎样把预测市场的到期事项推进完，又不变成替用户裁决和付款的中心？

**面试者：** 我会把 keeper 定位为公开入口的活性补充，而不是业务权威。以 M1 的 YES 提报为例，Go 记录 `challengeEnd=04:10`，到期后读取 S：只有仍为 Proposed、没有有效挑战且链上时间满足条件，才构造无争议最终化交易。如果已是 Disputed，就改为等待 K 或固定的仲裁截止，不能沿原计划强行写 YES；如果已终局，只核对结果并结束对应任务。closeAt 的交易禁令由 S 每次执行时检查，不依赖这个定时器。keeper 不签用户的挑战或 redeem，也不把到期提醒当成用户授权。它只是用自己的 Gas 触发任何人都可调用的入口，结果仍由当时链状态和合约规则决定，因此停机影响自动推进速度，不会把改判权转移给 Go。

## 第 2 层：把到期意图变成可恢复事实

**面试官：** 你说定时器只负责发现到期；如果进程在 04:10 前重启，或者两台实例同时发现到期，怎样保证任务不丢、不各自发一笔交易？

**面试者：** 我不会只在内存里注册一个定时回调，而是保存业务任务，任务键至少包含 `chainId、S、marketId、动作类型`，依赖提报的任务再绑定 `proposalId`。同一业务键唯一，重复发现只更新原任务的观察信息，不新增业务。记录计划时间、状态、重试时间、租约持有者、epoch 和关联交易尝试；实例用条件更新领取有期限的执行租约。重启后先扫描未终结任务，再从规范链状态补查可能遗漏的到期事项，所以事件交付或定时唤醒不是唯一恢复入口。到期时间只是唤醒提示，每次真正执行仍核对链上时间、提报身份和状态。若挑战使旧任务失效，保留旧任务的失效原因，再为仲裁超时建立相应任务，不能把原无争议动作偷偷改成另一个裁决动作。

## 第 3 层：任务去重之后还要控制发送顺序

**面试官：** 唯一任务键挡住了重复业务，但两个不同市场可以共用一个 keeper 地址。它们同时发送时，nonce 怎么分配，崩溃后又凭什么恢复？

**面试者：** 我会把“领取业务任务”和“占用发送地址的 nonce 槽位”分开。多 worker 可以并行准备不同市场，但同一发送地址只能由受控的串行通道分配 nonce；在数据库事务里保存 `sender、nonce、taskId` 的绑定，并对地址与 nonce 建唯一约束，不能让每个 worker 独立读取 pending nonce 后自行签名。首次接管还要核对该地址的链上 nonce 和已有未决槽位，未知缺口未查清前不能重复分配。每次尝试保存目标合约、calldata、value、费用参数及候选哈希。签名器不得私自广播，签名后的原始交易和哈希必须可靠保存后才能调用广播 RPC。这样数据库里的发送槽位先于网络副作用存在，恢复者能知道自己要寻找哪一个 nonce、哪一个业务动作，而不是重启后凭当前 pending 值从头再来。

## 第 4 层：提交后崩溃与广播结果不明

**面试官：** 你已经保存签名交易，但广播 RPC 超时，随后进程崩溃。新实例查不到回执，怎么判断到底没发出去，还是已经执行了？

**面试者：** 这时必须标成“广播或执行未知”，不能用查不到回执推导未执行。新实例先加载原槽位和全部候选哈希，查询交易、回执及所在块是否仍属规范链，并核对 S 的当前状态；单个 RPC 的 mempool 不可见不具有否定证明。原始签名交易已保存时，可以在核验仍适合传播后重播完全相同的字节，它的哈希和 nonce 不变，不会新增一个业务意图。若崩溃发生在保存签名之前，原槽位仍保留，不能直接释放给另一市场；应恢复签名记录或按同一业务、同一 nonce 受控续作。广播返回成功也只表示节点接收，不表示合约成功。即使回执 `status=1`，仍要结合事件、块哈希和业务状态判断完成阶段；回执回滚或暂不存在，都要保留可继续追踪的事实。

## 第 5 层：链上状态已经被别人推进怎么办

**面试官：** 你说还要核对 S；如果原交易一直查不到，但 S 已经终局，或者发送地址的 nonce 已经前进，能否据此把任务直接判成功？

**面试者：** 要把业务目标是否达成与原交易是否结案分开。S 已终局时，可以记录“公开到期目标已被链上事实满足”，连同当前向量、原因和观察块保存，但不能伪造成本钱包的成功回执；未决交易仍要追踪，迟到执行可能只会回滚并消耗 Gas。如果市场变成 Disputed，原无争议任务就是前提失效，不是应重试到成功。地址 nonce 前进只能说明某些 nonce 在该观察分支被消耗，应定位相应发送者与 nonce 的规范链交易，核实是原候选、替换交易还是非预期交易；历史查不全时继续未知并告警。只有确认旧槽位的结局、当前业务仍需推进，才考虑新的发送 nonce。非最终块上的 nonce 消耗还可能回退，所以同时保留确认级别，不把一次 latest 查询当成永远不会变化的结论。

## 第 6 层：加速不是重新提交一笔业务

**面试官：** 原槽位没有被消耗，市场也仍满足到期条件，但费用太低长期不打包。怎样加速，又不制造第二次最终化或丢掉原交易？

**面试者：** 加速应作为同一槽位的 replacement：保持发送地址和 nonce，绑定同一业务任务，通常保持 chainId、目标 S、calldata 与 value 不变，只按所用交易类型调整费用参数，并受 Gas 预算约束。新候选也要先持久化签名交易、哈希及替换关系，再广播；追踪范围必须包含新旧全部候选，不能认为发送了 replacement 就等于原交易消失。规范链上同一地址同一 nonce 最多执行一个候选，但哪个候选被包含、是否成功及会否重组，仍需观察。若业务前提已改变，应先把任务转为失效或待核查，而不是借“加速”签另一个裁决结果。费用提高也不保证赶上某个块，更不延长合约期限。即使需要新的业务尝试，也必须先解释旧 nonce 的结局，不能把 RPC 超时直接翻译成递增 nonce 再发。

## 第 7 层：租约隔离不了已经签出的交易

**面试官：** replacement 和原交易都已签出时，旧 worker 的 lease 过期，新 worker 接管。epoch 和 `context.Cancel` 能不能保证旧 worker 彻底失去影响？

**面试者：** 不能。epoch 能对数据库写入做 fencing，例如要求“任务仍归本实例且 epoch 相同”才准更新状态、申请下一次签名；取消 context 可以停止本地等待、退出 goroutine 或中断一次 RPC，但都不能撤销已签名交易，更不能撤销已经上链的执行。旧 worker 即使写库被拒绝，手上的有效原始交易仍可能被广播，因此接管者必须继承原 nonce 槽位和候选集合，不能因租约更换就给同一动作换 nonce。签名前尽量再次检查租约、使用集中受控的发送通道，只能缩小竞态窗口，不能把它说成 S 验证了 epoch；本基线合约没有这种协议。最终依靠持久发送身份、候选追踪和 S 自己的状态前置条件收敛。服务退出时停止接纳新签名工作，把未知尝试留给恢复扫描，不以 context 返回错误就把链上动作标为已取消。

## 第 8 层：故障恢复遇上积压和限流

**面试官：** 你要求接管后继续追踪全部未知尝试；如果停机恢复时积压很多市场，RPC 又开始限流，怎样避免恢复逻辑本身把服务拖垮？

**面试者：** 我会让数据库保存积压，内存只装有界工作集，扫描分页并按重试时间领取，不为每个市场无限创建 goroutine。对发送、回执追踪和链状态核对分配明确并发预算，保留未知 nonce 的核查能力，避免新任务把旧交易的追踪全部挤掉；同地址的发送仍串行，不能靠扩大 worker 数突破 nonce 顺序。RPC 限流后退避并加抖动，把下次执行时间写回持久任务，队列满则停止继续预取，接入层对非关键查询实施背压。恢复顺序先校验规范链观察位置，再核对发送槽位和当前市场状态，最后决定续播、替换或终结；错误分类避免把业务前提失效当暂时故障重试。公开到期最终化可晚些触发，但用户挑战有严格的上链期限，不能承诺拥堵时一定受理成功，也不能由 keeper 代签补救。并发和预算应由实际测量确定，不虚构吞吐与恢复时长。

## 本题收束

- **讲透的机制：** 用业务键固定任务身份，用发送地址与 nonce 固定链上尝试槽位，签名交易先可靠保存再广播；恢复时联合原哈希、全部 replacement、规范链回执和 S 当前状态判断。任务完成与交易结案分别记录，未知不能被超时掩盖。
- **最易错边界：** 数据库事务不与 EVM 原子提交；lease／epoch 只能限制本地协作，`context.Cancel` 不撤销已签交易；同 nonce replacement 不是新业务。Go 不持用户私钥，系统 keeper 的公开到期调用也不能转化为替持有人签署领取或挑战。
- **反例检验：** 手工推演“原交易已广播但响应丢失 → worker 崩溃 → lease 接管 → 其他人已最终化 → 原候选迟到”。正确结果是核实已有终局、保留原候选追踪，迟到交易由 S 拒绝而不改向量；不能另签用户领取、按新 nonce 盲发，也不能因本地取消就宣称原交易不存在。这是恢复逻辑检查，不是已运行的工程测试。
