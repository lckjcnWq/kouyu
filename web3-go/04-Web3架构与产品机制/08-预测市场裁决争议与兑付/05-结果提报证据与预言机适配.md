# 大问题 5：结果提报怎样绑定证据，预言机又怎样适配市场？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 提报 / Proposed | 提交一个允许被挑战的暂定结果。 | P 报 YES 不是 S 已经验证现实赛果，更不是允许领取。 |
| YES / NO / INVALID | 满足条件／明确不满足／按规则无法有效判断。 | 无源记录不是 NO，不能把一切“不是 YES”都塞进 NO。 |
| chainId / S / marketId | 哪条链／哪个市场合约／哪个市场。 | 证据和操作必须绑定 M1 的完整身份，不能凭问题文字相同串市场。 |
| rulesHash / evidenceHash | 规则指纹／此次提报所引用证据的字节指纹。 | 前者固定判断标准，后者固定引用内容；都不自动证明赛果真实。 |
| Awaiting / readyAt / proposeBy | 等待提报状态／开始和结束边界。 | 仅在 Awaiting 且 `readyAt <= t < proposeBy` 时接受首次提报。 |
| proposalId / proposedAt | 唯一提报身份／链上记录的提报时刻。 | 由成功提报建立，不能因 Go 超时另起一轮身份。 |
| challengeEnd | 允许挑战的截止。 | 从提报所在块时间起两小时，不能靠更换证据重开或缩短保护。 |
| C / BondVault / escrow | 抵押币／独立保证金合约／尚未分配的保证金额度。 | 10 C 保证金实收与提报同事务，不能拿市场 reserve 补交。 |
| 原子收取 / 回滚 | 收钱和记录共同提交或共同撤销。 | 竞争中第二个提报失败，其保证金收取也回滚，不留下孤儿资金。 |
| 证据归档 / 版本界限 | 保存可取回的原文／采用哪一时刻前的源记录。 | 可晚提交证明，但只能证明 readyAt 前已有的合格记录，不能纳入之后的新修订。 |
| oracle / 布尔断言 | 外部裁决依赖／对某句话回答真或假。 | “YES 断言为假”可能源于取消或描述错误，不天然推出 NO。 |
| UMA OOv3 / assertionId | 一类乐观预言机及其断言身份。 | 是接入时需核对版本语义的参考，不是本稿三枚举状态机的别名。 |
| K / msg.sender | 绑定的仲裁合约／当前调用者地址。 | S 校验只有 K 可从合法争议状态送入裁决，应用层白名单不够。 |
| Disputed / arbitrationEnd | 争议中／仲裁资格截止。 | 回调还要匹配 proposalId、rulesHash，且执行时间严格小于截止。 |
| Finalized / 提款信用 | 唯一兑付结果已写入／保证金归属已记账。 | 写向量与分配信用同事务，信用实际提款、持有人领取是后续不同动作。 |
| 回调重试 / 规范链 | 再送一次结果／当前有效分支。 | 每次重试重新检查状态和期限；外部系统结算成功不保证市场回调已成功。 |

## 把整篇文章压缩成一个故事

**起因：** P 准备向 M1 报 YES，不能只传一个结果字符串。P 要绑定链、S、市场、原 rulesHash 和 evidenceHash，归档可取回证据，并在允许的首次提报窗口向 BondVault 存入 10 C。S 一次事务把实收保证金与唯一 proposalId 共同建立，得到的只是 Proposed。

**处理及异常：** 若另一人先报成功，P 的迟后交易失败，10 C 收取也随之回滚；若源记录缺失，就按固定源顺序判断是否 INVALID，不能先报 NO 再随意改口。本文的适配反例是赛事取消导致“YES 断言为假”：这应按市场规则解释，不能机械变成 NO。即使外部结论合理，错误调用者、串错 proposalId 或迟于仲裁期限的回调也不能写入终局。

**结果及边界：** 合法 K 裁决被 S 接受后，唯一向量和保证金信用分配共同提交；若分配失败则整体回滚，重试仍须满足当时状态和时间。哈希只证明引用了哪些字节，不能证明比赛或来源时间；外部 oracle 已结算、S 已终局、保证金已提款和持有人已兑付必须分别核验，不能用一个“预言机成功”代替全部阶段。

**流程位置与核心机制：** 负责从现实记录到有身份、可挑战的提报。采用自定义的三结果枚举与一次提报规则，不将真实协议的断言布尔返回直接当作市场兑付向量。

## 第 1 层：提报者应该提交什么，而不是只交一个 YES

**面试官：** 官方赛果已经有了，提报接口和链上记录应该包含哪些内容？

**面试者：** 提报至少绑定 chainId、S、marketId、rulesHash、枚举结果 YES／NO／INVALID、证据内容哈希和提报者。S 验证当前是 Awaiting，且 readyAt 小于等于链上时间、时间小于 proposeBy，再原子收取 10 C 保证金并建立唯一 proposalId、proposedAt 和两小时 challengeEnd。证据原文在可获取归档中保存，链上不接收无限长资料。这个调用的结果是 Proposed，不是已经证明提报真实，也不是发出了兑付授权。结果类别、身份与期限必须由 S 检查，不能只依赖 Go 参数校验后把任意值写入。

## 第 2 层：保证金已交但提报失败会不会留下孤儿资金

**面试官：** 你说原子收取保证金，如果另一个人抢先提报，后一个人的 10 C 是否会被锁在 BondVault？

**面试者：** 在本模型中，提报通过 S 调用绑定的 BondVault，在同一 EVM 事务内完成状态检查、保证金实收和提报记录。抢先者已经让 Awaiting 变为 Proposed 后，后续提报应失败；即使资金调用在其他检查前发生，只要最终 require 失败，整笔事务也回滚，不会留下“钱收了但没有提报”的成功状态。BondVault 限制只有 S 能建立相应业务 escrow，并按 proposalId 记录，不能凭用户随意转账自动获得提报资格。Go 超时则查询原交易和 S 状态，不能在不知道首笔是否生效时另造一份独立提报。

## 第 3 层：证据哈希能不能自动证明赛果

**面试官：** 既然提报证据上了哈希，是不是智能合约就已经验证官方赛果是真的？

**面试者：** 不是。哈希只能绑定字节，S 并不会据此理解赛事、认证网页发布者或判断源记录的时间。Go 证据归档保存来源标识、E1 身份、原始内容、采集信息和可获得的版本或签名证据；挑战者及 K 按 rulesHash 对应规则复核。本基线采用截至 readyAt 已发布的最新有效源记录，晚提交的证明可以证明早已存在的记录，但不能把 readyAt 后的新修订变成允许使用的事实。没有来源真实性证明时必须承认仲裁信任，不能把 evidenceHash 或数据库时间包装成“事实已经密码学验证”。

## 第 4 层：主源迟到是否可以先提报 NO 再补证据

**面试官：** 如果直到 readyAt 主源还没结果，你能先报 NO，等它发布再改吗？

**面试者：** 不能。没有结果和结果明确为 NO 是两种事实。应按预定条件尝试合格备用源；截至规则界限仍无法得到有效记录，就提报 INVALID，而不是把缺失当成负面结果。本模型首次提报一旦成功不能修改 outcome 或替换证据承诺，也不支持重新开始挑战窗口。发现提报错误可以在窗口内由有效挑战进入 Disputed，由 K 按原规则判断；不能让提报者用“补证据”改变原话，又保留原本已接近结束的挑战期。如果需要可更正提报，必须单独定义如何重启窗口、处理保证金和防止无限拖延。

## 第 5 层：接入布尔断言预言机时为什么不能直接映射 NO

**面试官：** 若换成一个预言机，它告诉你“YES 断言是 false”，不就直接等于 NO 吗？

**面试者：** 不一定。false 可能表示该断言的描述、来源或时间限定不成立，不天然证明本市场的合法反向结果；M1 还有 INVALID。适配层必须说明断言到底询问什么，何种外部返回足以确定某个枚举结果，以及被否定后是等待进一步裁决、重新提报还是异常结案。当前模型的 K 直接输出受限三枚举，不使用布尔断言替代。若真正接入 UMA OOv3，就要按选定版本核对 assertionId、争议、结算和回调语义，再重新写适配状态机，而不是保留当前所有超时和保证金规则却把函数名改成 UMA。

## 第 6 层：外部回调怎样防止串市场或旧结果注入

**面试官：** 即使枚举映射正确，如果外部回调把另一市场的结果传进来，S 怎么挡住？

**面试者：** S 不能只检查结果字段合法，还要验证 msg.sender 是创建时绑定的 K，回调绑定 M1、原 proposalId 和 rulesHash，当前状态确实是 Disputed，并且链上时间仍小于 arbitrationEnd。第三方不能用相同文字问题或另一轮提报 ID 代替；市场已经 Finalized 或回调已经迟到时，不能覆盖向量。若真实适配器有异步请求 ID，还需要持久映射外部请求身份到具体市场和轮次，校验域并防重复。Go 的去重表只能减少重复处理，合约入口必须独立抵挡错误调用，因为任何人都可以直接构造交易绕过应用层。

## 第 7 层：回调重试或部分失败怎样与最终化收敛

**面试官：** 那回调写了一半、保证金分配失败，重试会不会有第二个结果？

**面试者：** 本模型 S 写结果向量、改变 Finalized 状态和让 BondVault 分配提款信用处在同一 EVM 事务中，任何一步失败都整体回滚；不存在合法的“向量已提交但该事务的保证金分配没提交”状态。重试仍需满足当前状态和期限，不能因为旧尝试曾在链下发送就免检。若第一次已成功，后一次不能重写终局，也不能再分配信用；若第一次被移出规范链，则按新分支事实处理。真实外部预言机若把“记录结果”和“回调市场”拆成不同事务，必须保留可查询和可重试的结果传递，不能假设回调永不失败；这属于适配变体，不是当前原子边界。

## 第 8 层：怎样证明适配没有把三个概念混在一起

**面试官：** 最后你如何验收“外部证据到市场结果”的这条链？

**面试者：** 我会分别验证三件事：现实记录是否满足规则、外部系统究竟裁决了哪个命题、S 在当前状态能接受哪种结果。用主队常规时间未胜、赛事取消和记录缺失三个独立输入，检查是否分别得到 NO、INVALID、INVALID，而不是一律把非 YES 归成 NO。再用错误回调者、错误 proposalId、已经最终化和仲裁迟到等负例，验证输入即使看起来合理也不能越权写链。最后检查引用证据能按哈希取回，外部协议版本和信任假设有明确说明。这样验收的是映射和执行契约，不宣称已经证明现实信息源永不出错。

## 本题收束

- **讲透的机制：** 提报身份、证据承诺、保证金实收、外部结果映射及回调权限必须共同绑定到同一市场规则。
- **最容易答错的边界：** 断言为假不天然等于 NO，哈希存在不等于事实为真，外部 oracle 结算不等于持有人收到兑付款。
- **反例检验：** 因“赛事已取消”否定 YES 断言，却把 100 NO 全额支付，会把本应 `[1,1]/2` 的权利错误替换成 `[0,1]/1`。
