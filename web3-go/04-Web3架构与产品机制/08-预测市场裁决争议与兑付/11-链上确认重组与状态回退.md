# 大问题 11：链上确认和重组之后，裁决与领取状态怎样正确回退？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| Finalized / 业务终局 | 市场在该分支上不再接受普通改判。 | 不能把合约状态名直接翻译成“底层链历史永不撤销”。 |
| receipt.status / 执行成功 | 回执标记该块里调用是否正常提交。 | status=1 只证明某次分支内成功，不替未来规范性与最终性作担保。 |
| outcomeState / claimExecutionState / chainFinalityState | 结果阶段／领取执行阶段／链最终性阶段。 | 页面分别展示，避免把暂时成功领取叫成最终不可逆到账。 |
| canonicalCursor / finalizedCursor | 本地完整应用的规范水位／已核实的最终水位。 | 都保存高度与哈希，承诺不能超过本地验证过的共同前缀。 |
| RPC / 最终性策略 | 节点访问接口／如何核实历史稳定性的规则。 | 单个节点标签或任意几个确认块不是普遍绝对证明，网络未指定不编数字。 |
| hash / parentHash / height | 区块完整指纹／父块指纹／高度。 | 同高度可换块，空日志块也必须保留父链连续性。 |
| txHash / logIndex / 观察键 | 交易哈希／日志序号／识别某次包含观察的组合。 | 再加 chainId 和 blockHash；同一交易换分支后不能沿用旧执行结果。 |
| removed / WebSocket | 日志撤回提示／实时订阅连接。 | 断线可丢提示，重组检测必须能靠完整父链独立完成。 |
| 共同祖先 / orphaned | 新旧分支最后共享块／不再规范的旧观察。 | 只撤销祖先之后的实际影响，终局块没消失就不误删向量。 |
| undo / before-image | 可逆变更资料／修改前的值。 | 与投影共同落库，回退按块及块内操作逆序，避免重启后再次扣同一金额。 |
| reorgId / 回退阶段 | 本次分叉恢复身份／已走到的步骤。 | 保存目标祖先、当前位置，崩溃后从最后成功事务续做。 |
| rebuild / 检查点 / 影子投影 | 重新建查询副本／可信块快照／未切换给用户的新副本。 | undo 不足时从仍属规范链的完整快照重放，验证后再切换读指针。 |
| Inbox / Outbox | 规范应用去重记录／待发送状态通知。 | 旧应用撤销后允许重新激活，新观察不能被永久去重误挡；通知不再次付款。 |
| revision | 对外状态的单调修订号。 | 余额可恢复旧数值，版本却要提高，已发送旧通知只能用新更正覆盖。 |
| S / reserve / BondVault | 市场合约／分市场抵押／独立保证金金库。 | 回退要一并恢复相关状态，不能只删领取行却保留旧扣款或保证金信用。 |
| immutable vector / 深重组 | 分支内不可普通修改的向量／穿过已承诺最终历史的分叉。 | 前者不保证跨分支结果不变，后者须事故隔离，不能宣称数据库重建消除了链外损失。 |

## 把整篇文章压缩成一个故事

**起因：** 旧分支中 M1 最终为 YES，A 销毁 60 YES＋100 NO，领取 60 C，页面发出了成功但未最终的通知。随后新块父哈希接不上本地游标，Go 必须查完整父链找共同祖先，不能因为高度继续增长就沿用旧成功记录。

**处理及异常：** 本文主重组变体把终局块和 A 的领取块都移除了，新分支仍为 Disputed。旧向量、领取及相关保证金观察要随对应历史撤销，A 恢复原份额，reserve 恢复到该新分支应有的 100 C；只删 A 的领取行会留下假账。持久 undo 或可信检查点重建让恢复可续做，随后用更高 revision 发更正；相同 txHash 若重新入块，也要按新块重新判断，不能照抄旧 60 C。

**结果及边界：** 新分支仍争议中就不可领取；若它日后合法终局为 NO，同一领取调用在恢复的余额上可能付 A 100 C，而非旧分支的 60 C。这是分支历史改变，不是管理员改判或重新 mint。旧付款随旧历史失效，不产生链外补款义务；若分叉穿过已承诺最终水位，则进入最终性异常处置，已交付的链外资产不能靠本地 rollback 自动追回。

[返回专题总览](README.md)

**流程位置与核心机制：** Go 观察最终化、领取和保证金事件之后，怎样维护完整规范链、定义两层最终性、持久回退与重放，并把更正传播到查询和通知。S 中的裁决互斥、单次领取原子性仍沿用公共基线，不把重组恢复改造成链下补款系统。

**必要前提：** 单链 EVM 自定义合约 S 以六位小数 C 足额发行 YES／NO。S 在同一规范分支上只写一次终局向量，当前持有人主动销毁全部两类余额领取；截止后禁止外部份额转让和新铸造，终局后也不能重新 mint。业务 Finalized 与底层链最终性严格分离。

**贯穿案例与独立变体：** A 抵押 100 C，卖 40 YES 给 B 收 24 C，A／B 持仓为 60 YES＋100 NO／40 YES。YES 下领 60／40 C，INVALID 下领 80／20 C。以下重组变体单独推演，BondVault 的保证金信用不与买方 B 的份额兑付混用。

**恢复主线：** 发现父链不连续 → 找共同祖先 → 持久撤销旧分支或从检查点重建 → 顺序应用新分支 → 提升 revision 并更正通知 → 核对最终性假设与同块不变量。回退的是本地派生状态，不是凭数据库命令让真实链回滚。

## 第 1 层：Finalized 为什么还不是链最终？

**面试官：** 市场已经 Finalized，用户也看到成功领取回执，为什么还要等待链的确认或最终性？

**面试者：** `S.state=Finalized` 只表示该执行分支上的业务裁决已经结束，普通入口不能再改向量；回执 `status=1` 表示交易在某个块中成功执行。若该块尚未达到所选链的最终性，它仍可能被替换，最终化、销毁和转 C 都可能不再属于规范历史，不能据此承诺不可撤销。

查询应拆出 `outcomeState、claimExecutionState、chainFinalityState`，并附观察块哈希和水位。主例 A 的 60 C 可以显示“链上执行成功、尚未最终”，而不是把业务终态映射成“已最终到账”。S 执行时只能读取当前分支，不能等待未来最终性才完成 redeem。

Go 的最终性门槛用于对外承诺和链外不可逆动作，不是给合约增加第二个提款条件。确认深度只是某种风险策略；有原生最终性信号的链应按其共识语义核实，不能把任意固定几个块说成绝对安全。

## 第 2 层：最终性策略怎样落到可查询字段？

**面试官：** 你要单独展示链最终性，那持久化哪些水位，怎样避免用一个 latest 状态混过去？

**面试者：** 我会持久化 `canonicalCursor=(height,hash)` 表示完整应用到哪个规范块，另存 `finalizedCursor=(height,hash)` 和最终性策略版本，交易观察保留包含块、确认情况与 receipt.status。索引落后时，不能仅因节点 finalized 高度已经上升，就把尚未完整应用的数据也标成最终；本地承诺只能覆盖已验证的共同前缀。

链未指定网络和共识参数，因此不能编造“12 确认必定最终”等数字。若使用风险深度，记录深度与它不是协议最终性的事实；若使用原生 finalized 标记，核实对应块哈希和父链，不能只相信单个 RPC 的字符串标签。

节点不同步、提供商相互矛盾或最终性信号异常时暂停提升承诺水位，保留可解释的“暂未核实”。业务可以继续在合约允许范围执行，但不能因页面需要确定答案而预先给用户链下可提现信用。

## 第 3 层：为什么高度和 txHash 都不足以识别重组？

**面试官：** 既然有规范游标，每次从上次高度加一拉日志不就行了，为什么还需要完整区块哈希父链？

**面试者：** 同一高度可以先后对应不同区块；新块高度加一也不证明它接在已应用分支上。因此索引器保存每块完整 `hash、parentHash、height`，校验新块父哈希等于当前游标哈希。不能只截取哈希前缀，也不能只跟踪出现 S 日志的块，因为重组可能跨过没有业务日志的空块。

每条观察使用 `chainId、blockHash、txHash、logIndex`，另带交易序号用于排序。相同 txHash 可以在另一个分支重新被包含，块位置、日志与执行结果可能变化；只用 txHash 去重会把新分支的有效观察误删。WebSocket 的 removed 通知只是提示，断线可能丢失，必须能靠父链独立发现异常。

拉取日志前后还要核对其所属块，避免 RPC 在调用之间切换分支造成拼接。父链不匹配或块内容不完整时停止推进本地游标，先定位分叉，不能跳过问题高度继续累计“成功领取”。

## 第 4 层：发现分叉后怎样确定撤销范围？

**面试官：** 如果父哈希不匹配，你怎样找出该回退哪些裁决和领取，而不是把整个市场都清空？

**面试者：** 从新候选链头沿父哈希回溯，与本地已保存的规范祖先比较，找到共同祖先 `(height,hash)`。先固定本次候选链头，若节点又换分支就重新核实；分叉判断依据哈希连通关系，而不是“两个 RPC 高度差不多”。旧分支共同祖先之后的完整区块，都属于待撤销范围。

若旧分支的 YES 最终化块被移除，其后的 A 领取、C 转账、BondVault 信用分配以及可能的提款也随对应旧链历史失效。新分支上的 S 可能回到 Proposed 或 Disputed，不能只把 A 改成待领，却保留旧 YES 向量和已扣 reserve。若只移除领取块而保留最终化块，则向量不应回退。

共同祖先若早于本地已承诺最终水位，就不是普通短重组。应进入最终性异常处置而非悄悄下调水位；没有足够历史定位祖先时，从经核实的更早检查点恢复，不能猜一个高度强行接链。

## 第 5 层：undo 怎样持久化，才能在回退时再次崩溃也恢复？

**面试官：** 撤销范围找到了，但如果只靠内存记旧值，回退到一半服务又崩溃怎么办？

**面试者：** 应在正向应用完整区块时，就把市场、持有人、reserve、供应、保证金信用和交易观察的 before-image 或可逆增量持久化，并与本块投影、Inbox 状态、Outbox、规范游标一起提交数据库事务。先改投影再异步写 undo 会留下无法恢复的窗口，不可接受。

回退按旧区块逆序、块内操作逆序处理；每个回退提交边界同时恢复对应业务行、将旧观察标为 orphaned、撤销规范应用标记、更新可撤销的待发消息和游标。持久记录 `reorgId、目标祖先、当前回退位置、阶段`，重启后从最后成功事务继续，不能再次逆减同一份余额。

领域旧值可以恢复，但对外 revision 的高水位不能跟着倒退，否则新更正可能被缓存当旧消息丢掉。已发送的通知也不能靠删除 Outbox 收回，必须保留审计和后续更正；回退锁定规范写入角色，避免两个索引器各接一条分支。

## 第 6 层：没有足够 undo 时怎样 rebuild 而不遗漏新分支事件？

**面试官：** 你要求 undo 可恢复，如果保留窗口不够，或者需要全量重建，该怎样和正常重放衔接？

**面试者：** 从带明确块哈希、规则版本和完整投影快照的可信检查点重建，先确认该检查点仍在选定规范分支上。它必须包含市场与 owner 余额、供应、reserve、裁决、保证金及必要订单状态，不能只存一张“已领用户表”。在影子投影中按完整区块和块内顺序重放，验证水位与不变量后再切换读指针。

若祖先在快照之前，就选择更早检查点或从部署块重建；不能拿不再规范的快照继续算。重建期间旧投影明确标注陈旧或暂不可用，切换时分配更高 revision，避免新旧表混读。历史区块无法完整获得时，应停止承诺恢复完成。

新分支若重新包含同一 txHash，应按新 blockHash 重新执行观察；被撤销的 Inbox 应用不能成为永久屏障。同一观察日后重新成为规范也要允许恢复应用，但当前规范应用重投不能重复增减余额。重放不再次发送历史付款，只生成必要的查询投影与可识别的状态更正。

## 第 7 层：相同领取交易在新分支上还是原来那次结果吗？

**面试官：** 你说同一 txHash 可能重新出现，那原领取意图是否可以直接沿用旧的“成功付款 60 C”？

**面试者：** 不可以，交易身份固定不代表执行上下文固定。旧分支上 A 可能在 YES 终局后成功领取 60 C，新分支若未 Finalized，同一 redeem 会回滚；若新分支按规则终局为 NO，且原份额恢复，同样 calldata 可能成功兑付 100 C。单次 immutable vector 约束在每条规范分支内，不能把旧分支结果强加给新分支。

因此意图保留，旧尝试的包含观察标为 orphaned，继续追踪该哈希和同 nonce 替换交易；不能沿用旧 receipt.status、日志或金额。重新被包含后按新块状态记录执行，并以稳定意图关联，不能因观察键变化就新建一项外部付款义务。

S 只会在该分支消费实际余额并付款，旧分支被撤销不是用户后来收到新份额，更不需要重新 mint。暂时查不到交易仍是未知，须核对规范 nonce 与候选交易，不能直接用新 nonce 反复广播或由 Go 补发 C。

## 第 8 层：查询与通知怎样表示“先成功，后撤销”？

**面试官：** 新分支状态已经恢复，用户却收到了旧的“已领取”通知，怎样让页面和下游可靠更正？

**面试者：** 查询返回一致快照，包含市场和 owner revision、规范块哈希、已索引水位、链最终性状态；不能在重组处理中把旧向量和新余额拼起来。新分支应用或回退更正都发布更高 revision，缓存只接受更新版本；如果某个余额恢复到原数值，也要保留新的规范来源与版本。

Outbox 把“旧观察已撤销／新分支已确认”作为可重投的状态变更，带逻辑通知身份、观察来源和 revision。消费者以 Inbox 在自身事务中识别重复与乱序，缺版本就拉取快照。已发消息无法撤回，应发更正，而非假装旧通知从未存在；外部发送成功但确认丢失也可能导致重复通知。

这些事件只通知事实，不触发另一次 C 支付。不能用变化的 blockHash 或 revision 作为外部付款新身份；如果扩展到外部支付，须等待最终性并由对端以稳定义务键原子防重。未最终时不发可提现链下信用，本模型根本没有第二条付款通道。

## 第 9 层：最终性假设失效的深重组还能靠回滚解决吗？

**面试官：** 即使外部付款等到了选定最终性，若后来发生击穿该假设的深重组，重建数据库就能把系统恢复无损吗？

**面试者：** 不能。链和本地投影可以重新选择规范历史，但银行已付款、商品已交付或其他链已放行的资产，不会因为删除一条 Outbox 或逆转一个账务行就自动回来。常规 undo 只恢复本地派生状态，同链原子性也从未覆盖这些真实外部副作用。

若观察到共同祖先早于已承诺最终块，应暂停提升最终性水位及新的外部不可逆动作，保留两条历史、支付凭证和受影响义务，核实共识与节点分歧后按事故流程决定如何接纳新规范历史。不能静默降低 finalizedCursor 并宣布“已自动修复”，更不能以补款掩盖已经形成的风险敞口。

基线只在 S 内转 C，没有提前授予链下可提现信用，所以不人为扩大暴露；但用户基于最终承诺已发生的外部行为仍可能受损。接入外部系统时必须事先写明风险承担、限额、追回或补偿机制，最终性是有前提的安全承诺，不是数学上的永不反转。

## 第 10 层：恢复完成怎样验证到资金和最终性边界？

**面试官：** 进入普通恢复或事故处置后，凭什么宣布新分支投影可信，而不只是游标追上了链头？

**面试者：** 我会选定已完整应用的规范块哈希，核对其祖先连续性，再在该块查询 S 的状态、向量、owner 余额、供应和 reserve，并核对 BondVault 的 escrow、信用及提款。最终化前两边供应等于 reserve；终局后用精确整数检查 `reserve*D>=totalYES*nY+totalNO*nN`，付款流水只计该规范前缀内的成功执行。

手工安排三类独立分支：仅领取块消失，终局块仍在；终局和后续领取一起消失；相同交易重新包含但结果改变。每类还插入“撤销事务后崩溃”和“消息已送达但确认丢失”，要求重启能继续、金额不重复扣、revision 不倒退。尾差与未领负债分开，不靠修改 reserve 让对账通过。

最后确认旧观察不再被查询为规范成功，Inbox 允许应当发生的新分支重放，Outbox 只更正不付款。若触及已最终历史，必须保留事故状态和外部损失清单，不能以本地重建成功代替风险清偿；这些是校验条件，不是已运行工程测试的结论。

## 本题收束

**讲透的机制：** 业务终局、执行成功、索引可见和链最终性是四个层次。完整区块哈希父链识别规范历史，持久 undo／可信检查点 rebuild 恢复派生状态，单调 revision 与可重投更正让查询、缓存和通知跟上新事实。

**易错边界：** 高度不能识别分支，txHash 不能唯一代表执行结果，removed 通知不能代替父链验证。回退不等于再付款；同链旧转账随旧历史失效，不表示链外副作用自动逆转。S 的 immutable vector 不是跨分支不变，Finalized 也不等于任何共识网络上的绝对最终。

**反例检验：** 旧分支 YES 下 A 领取 60 C，随后终局及领取块都被替换；新分支仍 Disputed。正确状态是 A 的原份额与 reserve 按新链恢复、旧成功观察撤销、页面更正、无外部补款。若分叉还穿过已承诺最终性且外部资产已支付，必须显式报告真实敞口，不能说一次数据库 rollback 已经无损解决。
