# 大问题 8：怎样保证裁决到兑付的端到端一致性？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 端到端一致性 | 各阶段对结果、权利、付款和展示有互相衔接的保证。 | 不是把 S、用户未来领取和 Go 数据库硬说成一个大事务。 |
| S / C / M1 | 权威市场合约／六位小数抵押币／本例市场。 | 份额、reserve 和向量由 S 决定，数据库没有创造付款资格的权力。 |
| 完整集 / 二级交易 | 成对铸造的互补权利／持有人之间换手。 | 100 C 铸两边各 100，B 买 40 YES 付给 A 的 24 C 不增加抵押。 |
| reserve / totalYES / totalNO | 剩余市场抵押／尚未销毁的两类总供应。 | 最终化前相等，之后按剩余向量负债核验，不拿保证金填差。 |
| nY / nN / D | YES、NO 的兑付分子与共同分母。 | `pay=floor((qY*nY+qN*nN)/D)`，qY、qN 是本人的最小单位余额。 |
| Finalized / finalizationId / reason | 唯一业务终局／身份／结案原因。 | 身份为 `(chainId,S,marketId)`，超时和 K 裁决即使同为 INVALID 也须区分原因。 |
| BondVault / escrow / credit | 独立保证金金库／待分配额／可提款信用。 | 最终化原子分配信用，不代表已经提款，更不代表份额持有人已收款。 |
| redeem / burn / 原子性 | 本人领取／消费份额／同事务共同提交。 | 清余额、扣供应与 reserve、转 C 一起生效；付款失败全回滚。 |
| 意图 / clientRequestId / payloadHash | 用户要完成的业务／请求编号／载荷指纹。 | 保持原领取含义，不因网络超时或换交易哈希制造新付款权利。 |
| txNonce / txHash / replacement | 交易序号／签名交易哈希／同序号替换关系。 | 一个意图可有多个候选哈希，Unknown 只是结果待核实，不是明确失败。 |
| 观察键 / blockHash / logIndex | 识别某次分支内日志的位置组合。 | 使用链、块哈希、交易哈希和日志序号，不能仅用 txHash 永久去重。 |
| Inbox / undo / 游标 | 本地应用标记／撤销信息／处理到哪里。 | 与一整块投影同数据库事务提交，崩溃后可确定重做或续做边界。 |
| Outbox / revision | 待发送通知记录／本地状态修订号。 | 通知只交付状态，不再次转 C；旧版本不能覆盖更正后的状态。 |
| 规范链 / 重组 | 当前有效分支／分支切换。 | 要撤销市场、持有人、保证金和通知等旧投影，不只删一行领取记录。 |
| 业务终局 / 链最终性 | 合约不再普通改判／共识层历史稳定性。 | 前者不替代后者，未最终日志不能授权链外可提现信用。 |
| 剩余负债 / 尾差 | 仍未消费的兑付权／已舍弃的不足最小单位部分。 | reserve 同时可能覆盖二者，不能把 B 尚未领的 40 C 当成可用余款。 |

## 把整篇文章压缩成一个故事

**起因：** M1 已有 100 C 抵押，A 持 60 YES＋100 NO，B 持 40 YES。合法最终化写入 YES 向量，并与 BondVault 的信用分配同事务提交，但 Go 恰在写投影前崩溃。链上权威仍是 Finalized，不能为迎合旧数据库撤回裁决，也不需要等数据库恢复才允许用户直接领取。

**处理及异常：** A 随后领取，S 同事务烧 60 YES＋100 NO、付 60 C，响应又丢失，页面还显示待领。恢复程序要追踪原意图的候选交易、读取指定块余额，并把完整区块的投影、Inbox、undo、Outbox 和游标共同提交；重复通知不触发第二次付款。若之后这段非最终分支被替换，则撤销旧观察、恢复新规范状态并发布更高 revision，而不是照旧日志补 60 C。

**结果及边界：** 在未被撤销的 YES 主例里，A 已领 60 C 时 reserve 为 40 C，B 仍有 40 YES、可再领 40 C，不能被“市场已领取”标志封死。这个暂态正确，页面落后也可恢复；错误的是未终局付款、改判后换比例、把未知当失败或链外多付。链上原子性、本地事务、可靠通知和共识最终性各有边界，合起来也不构成全局恰好付款一次的自动保证。

[返回专题总览](README.md)

**流程位置与核心机制：** 串起抵押与所有权、裁决终局、主动领取和 Go 查询投影，说明各阶段共同保证什么、在哪里提交、失败后凭什么恢复。整数算法、领取入口安全与区块回退分别由第 9、10、11 题继续深入。

**必要前提：** 严格沿用总览的单链 EVM 自定义合约 S。C 和两类份额均为六位小数；完整集足额抵押，截止后不得新铸造、外部转让或成交；最终化前可合并完整集，终局后也不能重新 mint。S 的终局向量只写一次，当前持有人一次销毁该市场全部两类余额领取。

**贯穿案例：** A 锁定 100 C，铸造 100 YES＋100 NO；卖给 B 40 YES，收到 B 的 24 C。A 剩 60 YES＋100 NO，B 持有 40 YES，reserve 仍为 100 C。YES 终局时 A／B 分别领取 60／40 C；独立 INVALID 变体为 80／20 C。

**本题判断线：** 足额权利 → 唯一兑付参数 → 原子消费与付款 → 可撤销的规范链投影 → 达到链最终性后的对外承诺。允许索引暂时落后，不允许用链下补款掩盖状态未知。

## 第 1 层：端到端一致性究竟要保证什么？

**面试官：** 从裁决写入到用户拿到 C，怎样定义端到端一致性，而不只是说“用了事务”？

**面试者：** 我会先把结果、权利、付款和展示拆开。S 的 `state、nY、nN、D、finalizationId` 决定按什么赔；`balance[marketId][owner]` 决定谁能领；`reserve` 和份额销毁记录决定是否已经履行。Go 的领取状态只是这些链上事实的投影，不能反过来决定付款。

必须保证未 Finalized 不可领、终局向量不可普通改写、没有余额不能重复领，每次成功领取都同时消费权利并支付对应整数 C。终局并不要求所有用户同时完成领取，允许 A 已领取而 B 尚未领取。

故障边界也要写清：广播成功、回执成功、查询可见、底层链最终是不同承诺。服务重启后可以补索引，但不得因为页面没更新就再付一次钱，也不能把业务 Finalized 宣称为链最终。

## 第 2 层：这些兑付权利最初怎样得到资产覆盖？

**面试官：** 你要求付款对应权利，怎样证明 A、B 的权利没有在交易或争议中变成无抵押负债？

**面试者：** 在这个模型中，S 实收 100 C 才铸造 100 YES＋100 NO；最终化前保持 `totalYES=totalNO=reserve`。完整集合并要同时销毁两边相同数量并返还 C。成交只在一个事务内把 40 YES 从 A 转给 B，并让 B 向 A 付 24 C，既不增发份额，也不把这 24 C 再计入 reserve。

所以裁决为 YES 后看当前余额，A 领 60 C、B 领 40 C；INVALID 时按 `[1,1]/2` 计算，分别为 80 C、20 C。不能因为 B 买入花了 24 C 就向 B 退 24 C，否则剩余用户的兑付就可能没有覆盖。

BondVault 中 P、Q 的提报或挑战保证金是另一套权利，不是买方 B 的持仓。跨合约对账必须分别列出 reserve 与保证金 escrow／credit，不能拿争议奖励填市场缺口，或把同地址物理余额都当可兑抵押。

## 第 3 层：裁决怎样只产生一套不可变兑付参数？

**面试官：** 抵押足额还不够，如果前一批按 YES 领、后一批按 NO 领，怎样阻止？

**面试者：** S 必须先验证裁决路径和当前状态，再在同一链上事务写入终局枚举、白名单向量、`reason` 和 `finalizationId=(chainId,S,marketId)`。只有 YES `[1,0]/1`、NO `[0,1]/1`、INVALID `[1,1]/2` 合法；进入 Finalized 后，任何普通入口都不能再次写向量，也没有管理员改判或升级当前市场的后门。

例如已成功挑战的市场处于 Disputed，无争议最终化入口必须失败；K 只有在固定仲裁截止前且身份、提报和规则绑定正确时才能裁决，超时走预定 INVALID。这些检查在 S 中执行，不能只由 Go 定时任务过滤。

同次最终化还通过 BondVault 按 reason 分配保证金信用。ArbitrationTimeout 优先让 P、Q 各返 10 C，即使 Q 主张的就是 INVALID，也不能仅因结果相等奖励 Q 20 C。信用分配失败则终局字段和事件一起回滚，成功后另行提款。唯一写入约束针对同一规范链分支，重组撤销旧分支不是管理员改判。

## 第 4 层：最终化原子提交是否等于整条链路一个事务？

**面试官：** 你说 S 与 BondVault 同事务，那是不是可以把数据库更新和用户收款也放进一个“大事务”？

**面试者：** 不可以。S 调用同一 EVM 链上的 BondVault，属于同一交易调用栈，任何未被吞掉的失败可使整笔交易回滚；它不包括 Go 数据库，也不包括未来各用户分别发起的 redeem，更不是跨链原子提交。最终化事务只固定兑付参数和保证金分配，不遍历所有持有人付款。

假设最终化成功后 Go 在提交投影前崩溃，链上仍然是 Finalized，用户仍可直接领取。恢复时按规范块重新索引 `finalizationId` 和向量，而不是撤回裁决以迎合旧数据库。反过来，数据库记录“已广播”也不能让未上链的向量生效。

因此要给每个提交边界独立语义：链上交易决定权威状态，数据库事务决定本地投影版本和游标。两个边界间允许暂时不一致，通过重放收敛，绝不能宣称不存在故障窗口。

## 第 5 层：一次领取的原子边界在哪里？

**面试官：** 最终化与领取可以分开，那单次领取怎样避免“钱已转、份额没销毁”或相反的状态？

**面试者：** `redeem(M1)` 先在 S 中检查 Finalized，读取调用者当前全部 `qY、qN`，按 `floor((qY*nY+qN*nN)/D)` 一起计算付款。随后在同一事务清零两类余额、扣减供应及 reserve，再安全转 C 给本人；转账失败必须令前述修改及事件全部回滚。

主例中 A 成功领取会同时销毁 60 YES 和 100 NO，只付 60 C；B 的 40 YES 不受影响。只持输方也可主动销毁并领取零 C，两类余额都为零则拒绝，不设置 `claimed[marketId]` 阻断整个市场。

截止冻结和终局禁止 mint 保证领取后该账户不能再取得新份额，重复调用不会形成新权利。这里的安全依据是权威余额已被消费，不是 Go 的请求标记；合约也不能等待未来链最终性才执行，只能检查执行分支上的状态。

## 第 6 层：超时未知怎样避免演变成第二次付款？

**面试官：** 如果链上领取已经完成，但调用方超时没拿到回执，你怎样继续而不重新履行？

**面试者：** Go 先持久化领取意图，绑定 `clientRequestId、chainId、S、marketId、owner、payloadHash`；交易尝试另存 `sender、txNonce、txHash、replacement关系`。同一意图可以有多个候选哈希，不能因为换哈希就认为产生了新的兑付权。广播超时只进入 Unknown／待核实状态，不记成明确失败。

恢复时追踪候选交易的规范链回执、同 nonce 替换情况，并在指定块读取 S 的余额和领取事件。已成功消费的份额不再支付；交易回滚则原份额仍在。暂查无回执既不能证明未广播，也不能证明资金已经到账。

即便另一个请求误提交了新的链上调用，已清零余额也会让它失败，但服务仍应避免浪费 Gas。更不能绕过 S 另转一笔 C“兜底”，因为那笔转账不会消费原有权利，也不受 redeem 的防重边界保护。

## 第 7 层：链上事实怎样可靠进入数据库？

**面试官：** 你依赖规范链回执和事件判断，那索引进程在写记录到一半时崩溃怎么办？

**面试者：** 索引器以完整区块为应用边界，先验证块哈希、父哈希和日志完整性，再按交易与日志顺序构建变更。观察键使用 `chainId、blockHash、txHash、logIndex`，不能只用 txHash；不同分支上相同交易的包含位置和执行前提可能不同。

一个数据库事务共同提交本块的 Inbox 应用标记、市场和持有人投影、可恢复的 undo 信息、Outbox 及规范游标。提交前崩溃就重做该块，提交后重投则识别本次规范应用已经完成；空日志区块也必须维护父链连续性。数据库事务不包含 EVM 执行。

若链上领取已成功而投影仍显示待领，这是允许的滞后，应暴露查询水位。禁止根据滞后投影再支付。若事件不全或指定块读取与日志不符，停止提升游标并重取，不能跳过缺口假装同步完成。

## 第 8 层：可靠通知会不会把一次领取变成多次外部付款？

**面试官：** 数据库与 Outbox 同时提交后，消息仍可能重投或乱序，怎样保证下游不把它再当一笔付款？

**面试者：** 首先，本模型的 Outbox 只交付状态和通知，实际 C 已由 S 的 redeem 转给本人，不存在通知消费者再打款的步骤。消息带市场／持有人 `revision`、观察块哈希和链最终性状态；消费者保存已见版本，旧版本不覆盖新版本，发现缺口就重新查询权威投影。

Inbox 去重保证同一规范应用不重复修改本地记录，Outbox 重投保证通知有机会到达，两者都不能自动保证外部系统“恰好付款一次”。发送成功但确认丢失时仍可能重发，消费者必须能够识别同一逻辑通知。

如果另行接入银行等不可逆支付，那已经超出基线：必须等待选定链最终性，采用稳定付款义务身份，并由收款系统原子记录幂等键与支付结果；同键异金额应停机核查。不能把区块哈希或 revision 当新付款身份，也不能未最终就给可提现信用。

## 第 9 层：已展示的终局或领取被重组撤销怎么办？

**面试官：** 通知带了版本，但如果通知依据的区块消失，之前说的“唯一终局”和“已领取”怎样处理？

**面试者：** 唯一终局是在同一规范分支内成立；重组可能让最终化和领取交易一起从规范历史消失。S 在新分支上的向量、余额、reserve 以及 BondVault 信用以新链状态为准，Go 不能继续保留旧分支的“已领”来抵消链上已经恢复的权利。

索引器凭完整块哈希父链找到共同祖先，使用持久 undo 逆序撤销旧分支，或从可信检查点 rebuild，再应用新分支。市场、持有人、保证金、交易观察、游标与待发通知必须一并恢复，不能只删除一行领取记录。

对外发布更高 revision 的撤销或更正，已送达消息不能物理收回。撤销本地“已到账”不等于发补偿款；同链旧付款也随旧历史失效。若最终性假设被深重组击穿，已经发生的真实外部损失不是常规回滚能够消除的。

## 第 10 层：怎样验证整条一致性链真正闭合？

**面试官：** 回退后怎样证明已经收敛，而不是只是把页面状态改得看起来合理？

**面试者：** 我会固定同一个规范块哈希，把 S 的向量、供应、分市场 reserve、持有人余额和已成功领取量与投影比较。最终化前检查两边供应等于 reserve；最终化后用精确整数检查 `reserve*D >= totalYES*nY+totalNO*nN`，并核对 reserve 等于实收铸造减合并返还减成功兑付。保证金独立核算，不能串账。

同时核对每次成功领取的余额消费与 C 转账，零兑付允许没有 C 转账但必须有销毁依据；未领负债不能误报为尾差。查询与通知还要指向相同 revision 和规范水位，不能拿不同块的“最新值”拼出假缺口。

手工反例可选“最终化成功后服务崩溃、A 领取回执丢失、消息重复、随后非最终分支被替换”，要求每一步都有可解释状态，而非补款。安全性不代表保证活性：链停机、C 冻结或无人发交易仍可能延迟兑付，不能靠改结果消除这些前提。

## 本题收束

**讲透的机制：** 端到端一致性不是全链路一个大事务，而是足额抵押、唯一终局、单次领取原子性、可重放投影与明确最终性承诺共同组成的契约。权威始终在 S，Go 可以落后、恢复和更正，不能自行生成付款权利。

**易错边界：** 二级成交款不是新抵押；买方 B 不是保证金挑战者；Finalized 不是链最终；S 与 BondVault 同链原子不等于数据库或跨链共同提交；幂等通知不等于幂等外部支付。尾差留在 reserve，不借保证金或其他市场余额粉饰缺口。

**反例检验：** 主例 YES 下 A 已领 60 C、B 尚未领 40 C，服务崩溃后不能因“市场已领取”拒绝 B，也不能因“A 的投影没更新”再付 A。若这一段领取历史被非最终重组撤销，必须按新规范分支恢复余额与版本，而不是在链外多补 60 C。
