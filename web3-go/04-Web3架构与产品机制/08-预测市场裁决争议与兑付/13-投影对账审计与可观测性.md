# 大问题 13：怎样在同一条链上事实中证明抵押、头寸、兑付、保证金和页面对得上？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 投影 / 对账 / 审计凭证 | 可重建查询副本／核对同口径事实／可追查依据。 | 不是比较两页数字凑巧相等，要能解释某规范块结束时的合约状态。 |
| blockHash / 块高 / 规范前缀 | 完整区块身份／位置序号／当前有效历史截至某块。 | 同高度可能不同分支，所有状态和流水须落在同一块哈希边界。 |
| RPC / 历史状态查询 | 节点接口／读取过去某块的合约值。 | 无法取得指定块就报告无法核验，不能偷偷用 latest 假装历史快照。 |
| S / C / reserve | 市场合约／六位小数抵押币／逐市场剩余抵押。 | B 付 A 的 24 C 不算 S 入账，共用地址也不能串市场补洞。 |
| M / G / BY / BN / P | 累计实收铸造／合并返还／领取烧 YES／领取烧 NO／累计兑付。 | 都是同尺度最小单位整数；此处 P 是付款总量符号，不是提报者姓名。 |
| totalYES / totalNO | 尚未销毁的供应。 | 分别等于 `M-G-BY`、`M-G-BN`，零付款 burn 也必须累计。 |
| `reserve=M-G-P` | 剩余抵押等于实收减已返还与已兑付。 | 不含保证金、直接捐赠和二级交易额，失败交易不计成功兑付。 |
| nY / nN / D / 剩余负债 | 两类兑付分子／共同分母／还未消费的理论权利。 | 终局后检查 `reserve*D >= totalYES*nY+totalNO*nN`，不强求供应仍相等。 |
| 尾差 / 未领抵押 | 舍入留下的小额／仍覆盖未消费份额的资产。 | 两边供应全零后才能把剩余 reserve 归为全领取后尾差。 |
| BondVault / escrow / 未提信用 | 独立保证金金库／待分配保证金／已分配待提额度。 | 加上累计已提保证金等于历史实收，转信用不是已经提款。 |
| 物理余额 / 捐赠盈余 | 合约地址实际持币／直接转入但无业务权利的币。 | 与分账汇总外层核对，盈余不会自动增发份额或提高兑付。 |
| 事件身份 / logIndex | 某分支内日志的完整位置／日志序号。 | 含 chainId、blockHash、txHash 和 logIndex，同次 burn 的多种事件不能重复计量。 |
| Outbox / revision | 本地待发通知／状态修订号。 | 与投影及游标同数据库事务，发送可重复，旧版本不能覆盖更正。 |
| finalizationId / 观察身份 | 稳定终局业务身份／具体分支中的包含记录。 | 前者可不变，后者随块变化，不能把新观察当新付款义务。 |
| 重组 / 共同祖先 / 修正通知 | 分支切换／共享历史边界／说明旧观察已失效的新消息。 | 回退后提高 revision，不补款，也不假装已发通知可以物理收回。 |
| 可观测性 / 高基数标签 | 能从信号定位异常／取值极多的监控维度。 | 指标用受控动作和错误类，marketId、txHash 留在日志追踪中下钻，阈值须有实测依据。 |

## 把整篇文章压缩成一个故事

**起因：** M1 锁入 100 C 后，A 卖给 B 40 YES 收 24 C。对账人员固定某个规范 blockHash，既读 S 快照也汇总完整流水，确认抵押仍为 100 C。YES 下 A 已领 60 C 时，累计领取烧毁为 60 YES、100 NO，因而剩余供应为 40 YES、0 NO，reserve 为 40 C，不能因为两边不相等就报抵押不足。

**处理及异常：** 本文重组变体里 B 接着烧 40 YES、领 40 C，成功通知已经发出，对应领取块却被移出规范历史。系统找到共同祖先并撤销旧影响，在保留终局与 A 领取的这个变体下，恢复 B 的 40 YES 及对应 40 C reserve，再用更高 revision 发修正通知。不能把旧分支累计付款与新分支供应混在一起，更不能因 B 出示旧通知就链外再付 40 C。

**结果及边界：** 恢复后逐项核对 `totalYES=M-G-BY`、`totalNO=M-G-BN`、`reserve=M-G-P`，独立重核 BondVault 的 escrow、未提信用及已提款；没有完整历史快照就明示无法核验。B 的未领 40 C 仍是负债覆盖而非尾差，直接捐赠也不是可挪用储备。页面、通知、流水和合约值须带同一规范来源；真实链上覆盖失败应留证上报，不靠手改投影或保证金补洞消警。

**流程位置与核心机制：** 本题覆盖“规范块与合约快照 → 完整事件投影 → 数量及资金对账 → 通知交付 → 重组修正 → 审计定位”。第 12 题关注发送任务是否恢复，本题关注恢复后读到的事实是否属于同一规范链前缀，以及页面、账务解释和链上状态能否相互证明。

**必要前提：** 沿用 S 持有市场抵押和 YES／NO、C 与份额均为六位小数、终局向量不可修改、当前持有人主动 burn 领取的教学模型。BondVault 的保证金 escrow、未提信用和实际提款独立于市场 reserve；二级成交的付款不是抵押入账。Go 数据库是可撤销、可重建的查询投影，不是第二本有权创造兑付资格的资产账。

## 第 1 层：先确定对账到底在证明什么

**面试官：** 预测市场已经有合约事件和页面余额，为什么还要对账？你会怎样定义“对得上”？

**面试者：** 我会要求投影能在指定规范块结束时，复现该块对应的 S 状态和已发生资金变化，而不是比较两个页面数字恰好相等。以 M1 为例，A 锁入 100 C，再把 40 YES 卖给 B 得到 24 C，投影必须同时解释 A、B 的份额变化和市场 reserve 仍为 100 C；把 B 的 24 C 又加进 reserve，即使页面总资产看起来更多也是错误。每份投影要带 `chainId、S、blockHash、块高、revision` 和最终性级别，结果终局、领取执行与链最终不能合成一个“成功”。链上快照是校验对象，事件流水解释它如何形成；两者不一致时先找遗漏、重复、分支或金额口径，不能让 Go 修改用户兑付权来迁就数据库。

## 第 2 层：同高度不是同一份快照

**面试官：** 你要求指定规范块；如果 reserve 从一个 RPC 读取，供应量从另一个 RPC 读取，两边都说是高度 H，这样够不够？

**面试者：** 不够，同一高度在重组时可能对应不同哈希。我会先固定目标 `blockHash`，确认投影游标已经完整应用到这个块，再把 reserve、两类供应、向量及 BondVault 查询都绑定该哈希。有的节点支持按块哈希查询，有的只接受块高，能力必须事先核实；只能按高度查时，需要校验查询前后的规范哈希一致，有歧义就整批废弃重读，不能把它包装成绝对原子的快照。使用不同 RPC 也必须证明指向相同块，历史状态不可用应报告“无法核验”，不能默默退到 latest。索引时验证父子哈希连续，按交易序号和日志序号处理完整块；对账在块结束位置比较，不能拿半个块的投影对整块状态。快照匹配仍不等于链已最终，所以审计记录另外保存最终性水位和观察时间。

## 第 3 层：供应、销毁和累计付款怎样同时核算

**面试官：** 假设同块快照已经解决；终局后两类供应不再相等，又可能有零付款销毁，你具体用哪些等式判断漏记？

**面试者：** 我会用最小单位整数分别累计：铸造实收抵押及每类铸造量记为 M，完整集合并返还量及每类合并销毁量记为 G，领取销毁分别记为 BY、BN，累计兑付款记为 P。在本模型同尺度下，必须满足 `totalYES=M-G-BY`、`totalNO=M-G-BN`、`reserve=M-G-P`，并用事件汇总值核对同块合约值。领取为零也必须累计 burn，不能只处理有付款的记录。终局前领取量为零，供应与 reserve 相等；终局后改查 `reserve*D >= totalYES*nY+totalNO*nN`，不能继续强求两类供应相等。M1 判 YES 后 A 领取，剩余供应是 40 YES 和 0 NO，reserve 为 40 C。INVALID 则按每个 owner 两类余额先相加再取整；只有两类供应均为零仍有 reserve 时，才可把剩余归为已实现尾差，不能把尚未领取的抵押全叫尾差。

## 第 4 层：资金充足不能靠保证金池来证明

**面试官：** 你核算出了 reserve；如果 S 的物理余额与它不等，或者 BondVault 还有 20 C，能否据此认为市场总归有钱、对账可以放行？

**面试者：** 不能，必须分清逐市场账和不同合约的资产边界。多个市场共用 S 时，要先汇总同一种 C 的各市场 reserve，再与 S 在同一块的实际 C 余额核对；直接捐入只形成待解释的物理余额盈余，不增加份额或兑付比例，也不能用另一市场的抵押覆盖 M1 缺口。BondVault 则单独满足“累计实收保证金＝尚在 escrow＋当前未提信用＋累计已提保证金”，其实际余额还要与 escrow 和未提信用核对，直接捐入同样单列。一次受挑战的终局可把 20 C 从 escrow 转成胜方信用，这时并没有向胜方转账，不能既累计信用又累计已提款。S 与 BondVault 在同一最终化交易中的状态变化必须一起观察，不能在日志中间就判缺钱。保证金信用可独立提款，市场领取和保证金提款不能共用已领标记或互相抵销。

## 第 5 层：投影与通知的本地原子边界

**面试官：** 既然一次最终化要同时观察 S 和 BondVault，如果数据库更新后通知发送失败，页面和审计记录怎样避免各说各话？

**面试者：** 我会把规范块应用、事件去重记录、市场及保证金投影、revision、游标和 outbox 消息放进同一个数据库事务，事务失败则整批不推进。事件身份包含 `chainId、blockHash、txHash、logIndex`，不能只用 txHash 去重；同块按交易和日志顺序消费，并按事件语义避免把同一次 burn 的业务事件与份额转移事件重复计量。成功提交后，通知 worker 再从 outbox 发送，消息带对象身份、revision、观察块和确认级别，接收方按消息身份幂等并拒绝陈旧版本覆盖。这样可以防止“投影提交了但通知意图丢失”，却没有实现数据库与 EVM 跨域原子，也没有实现数据库与外部通知服务的一次性共同提交。发送成功后来不及记已发送可能再次投递，必须允许重复；通知只是某次链观察的可追溯表达，不额外创造付款义务。

## 第 6 层：已发出的通知遇到重组

**面试官：** 你说通知表达某次观察；如果“B 已领取 40 C”的通知已经发出，随后对应区块被重组掉，outbox 又不能把消息收回来，怎么办？

**面试者：** 我会先把该通知所依据的块标成孤块，找到共同祖先，撤销旧分支影响，再按新规范分支重放。撤销可以使用反向变更记录，也可以从可信快照重建，但投影 revision 必须产生新的版本，不能把版本号退回去让下游误以为是旧消息重发。修正通知写入新的 outbox 记录，引用旧消息及其观察块，明确旧领取观察已撤销，并给出新水位下的余额和交易确认状态。原 `finalizationId` 可保持业务身份不变，具体观察记录则因 blockHash 不同而区分；用户余额等相关对象也要随分支一起修正。原交易可能重新进入待打包状态，不能把撤销页面记录等同于链上永不执行。最重要的是不链下补给 B 40 C：旧日志被撤销不证明多了一笔真实欠款，补款会在原交易重新入块时造成重复支付。

## 第 7 层：修正之后仍有差异怎样归因

**面试官：** 已经回退重放，B 却坚持收到过成功通知，reserve 对账也仍报警；你怎样留证并区分索引错误、尾差和真正的资金异常？

**面试者：** 我会以一次对账运行身份串起目标块哈希、合约地址、规则和向量、原始日志位置、快照查询结果、计算口径及投影 revision，再把 B 的请求、候选交易、回执和通知版本接入同一条证据链。先核查两边游标、规范分支和精度是否一致，再定位最早发生供应或资金等式偏差的块，检查遗漏日志、重复计量、错误事件解码及合约绑定；不能先手改余额消掉告警。尾差要由真实领取的向下取整解释，尚存头寸对应的 reserve 不是可随意处理的盈余。若在同一规范块上，合约自身的 reserve 与剩余负债已经违反约束，就超出投影修复范围，应保存可复核证据并上报风险，不能拿 BondVault 或链下转账遮盖。原始证据和通知修正保留关联历史，重建读模型不等于删除事故经过。

## 第 8 层：把证据链变成可操作的观测信号

**面试官：** 逐笔查证太慢；你已经能定位最早偏差，平时怎样观测才能先发现问题，又不让海量市场标签压垮监控？

**面试者：** 我会让告警对应可验证的失效条件，而不是随意填成功率。索引延迟同时看规范头与应用游标的块高差、最后成功应用时间，并单独记录最终性水位；链本身不出块与 Go 不推进要区分。资金侧只对同 blockHash 且数据完整的对账产生结论，观测供应及 reserve 等式偏差、负债覆盖失败、保证金 escrow 到信用转换差异；未取得历史快照记为核验不可用，不当作“差异为零”。交付侧看待发 outbox 年龄、重复投递和修正通知积压，交易侧看未知尝试年龄与 RPC 限流。常规指标使用受控的链、动作和错误类别，marketId、txHash 等高基数身份留在日志、追踪与审计记录中，通过关联标识下钻。阈值和容量依据实际数据制定；本文只给信号定义与处置方向，不声称已有监控结果、延迟分位值或故障恢复成绩。

## 本题收束

- **讲透的机制：** 以相同 blockHash 的完整规范链前缀为比较边界，同时核算 reserve、两类剩余供应、分别已 burn 数量与累计 pay；BondVault escrow、未提信用和已提款另成守恒式。事件解释变化，合约快照验证结果，审计凭证连接两者。
- **最易错边界：** 同高度不等于同块；outbox 与投影共同数据库事务不等于与 EVM 共同提交；业务终局身份不等于观察身份，重组修正要提高 revision。通知修正不能变成链下补款，保证金不能替市场抵押兜底，零付款领取也消耗份额。
- **反例检验：** 手工推演“旧分支 B 已 burn 并领取 40 C → 通知已发 → 重组后该领取不存在”。新分支投影应恢复 B 的 40 YES 和对应 reserve，增加修正 revision；BondVault 按新分支独立重核，原交易继续追踪，不新增 40 C 链下支付。若把旧分支 pay 与新分支 supply 混在一起，应识别为快照口径错误，而不是市场突然资不抵债。这里给出的是检查方法，不是测试通过结论。
