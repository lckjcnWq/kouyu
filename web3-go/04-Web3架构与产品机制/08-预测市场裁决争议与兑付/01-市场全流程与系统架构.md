# 大问题 1：一笔预测市场业务怎样从创建走到领取完成？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| M1 / E1 | M1 是教学市场，E1 是它询问的指定赛事。 | 问的是主队是否在常规时间获胜，不是任意口径的“赢球”。 |
| C / S / K | C 是抵押币，S 是市场合约，K 是绑定的仲裁合约。 | C 和份额均为六位小数；S 管资产与状态，K 只在规定路径内裁决。 |
| YES / NO / INVALID | 满足条件、不满足条件、按规则无法有效结案。 | INVALID 用异常兑付向量结案，不是第三种可交易份额。 |
| 完整集 / reserve | 一对互补份额；reserve 是某市场专属抵押分账。 | 锁 100 C 铸 100 YES＋100 NO，不能理解成要赔 200 C。 |
| 二级成交 | 已有持有人把份额卖给另一个人。 | B 的 24 C 支付给 A，40 YES 换主人，抵押仍为 100 C。 |
| closeAt / observeAt / readyAt | 停止交易、观察事件、开始允许提报的不同边界。 | M1 分别为 00:00、01:00、02:00 UTC，停盘不等于已经可裁决。 |
| proposeBy / challengeEnd / arbitrationEnd | 提报、挑战、仲裁各自的截止。 | 期限控制不同入口，不会因为后台任务没跑就自动顺延。 |
| Awaiting / Proposed / Disputed | 等待提报、已有暂定结果、进入争议。 | 这些是结果阶段；Awaiting 不代表交易始终开放。 |
| Finalized / 兑付向量 | 业务裁决完成；向量规定每类份额能领多少。 | 只有合法最终化才能写入唯一向量，官方赛果本身不能直接改 S。 |
| BondVault / 提款信用 | 独立保证金金库；记录某人以后可提取的额度。 | 最终化分配保证金归属，不等于已经给提报者转账，更不等于持有人已领款。 |
| redeem / burn | 领取；销毁已消费的份额权利。 | 每人主动领取，销毁与 C 付款同事务完成；失败则共同回滚。 |
| EVM / 原子事务 | 合约执行环境；一笔交易中的相关变化共同提交或撤销。 | 不能正常留下只销毁份额不付款，但它不把 Go 数据库也包进同一事务。 |
| 净现金流 / reserve | 前者是用户收支，后者是市场尚存抵押。 | A 的 −100＋24＋60＝−16 C 不是市场缺了 16 C。 |
| 规范链 / 链最终性 | 当前接受的链分支；共识层对历史稳定性的保证。 | Finalized 是业务终局，仍可能处于尚未最终确定的区块中。 |
| 投影 / 重组 | 从链事实生成的查询副本；规范分支切换。 | Go 要撤销旧展示并重放，不能用旧领取日志额外补款。 |
| 活性 / 公开推进入口 | 在前提满足时，业务能继续往下走。 | 到期后任何人可发交易推进，不代表到钟点自动执行，也不能消除停链或 C 冻结。 |

## 把整篇文章压缩成一个故事

**起因：** A 参加 M1，先确认 E1 的赛果口径、源顺序和无效条件已经锁定，再存入 100 C，拿到 100 YES＋100 NO。B 在截止前花 24 C 买走 40 YES，于是 A 剩 60 YES＋100 NO，B 有 40 YES；交易款在两人之间流动，S 的抵押还是 100 C。

**处理及异常：** 市场 00:00 停盘，01:00 到观察界限，02:00 才可提报。P 的 YES 先是 Proposed，不是付款命令；及时挑战会转入 Disputed，由 K 在期限内裁决，逾期则按原规则 INVALID。无人挑战的主例到期后有人触发 YES 最终化，随后 A、B 各自领取。领取转账失败会连同份额销毁一起回滚；这些争议或失败分支是独立变体，不能都叠成主例已经发生的事实。

**结果及边界：** YES 主例支付 A 60 C、B 40 C，恰好用完 100 C；A 净收支 −100＋24＋60＝−16 C，B 为 −24＋40＝16 C。市场已终局不等于 B 已点击领取，某块中执行成功也不等于链已最终。Go 只能核验、追踪和修复投影；重组时不能凭旧页面再付一笔，也不能把 0.60 C 成交价说成客观胜率。

**流程位置与核心机制：** 负责端到端架构、权威状态和完成语义。沿用总览 M1 的 100 C 完整集及 40 YES 二级成交案例；细节分别由后续抵押、争议、一致性和恢复母题展开。

## 第 1 层：从用户参与到最后到账，完整流程是什么

**面试官：** 如果由你设计一个预测市场，从市场创建到用户最后收到钱，完整流程和架构是什么？

**面试者：** 在这个模型中，我先把问题、官方源及备用顺序、交易和观察时间、INVALID 规则写入不可修改的市场配置。A 锁定 100 C，S 铸造 100 YES＋100 NO；A 把其中 40 YES 卖给 B，链上同一事务转移份额并收取 24 C。截止后禁止新铸造、外部转让和成交，等到 readyAt 才可提报。提报经历挑战期；有争议走固定仲裁器，无争议或仲裁超时按预定入口形成唯一向量。最后各持有人销毁份额领取 C。Go 负责证据、交易编排与索引，不裁决现实结果，也不在数据库凭空改用户链上余额。

## 第 2 层：哪些资产变化属于市场，哪些只是用户之间交换

**面试官：** 你说 A 已经拿到 B 的 24 C，最终又能领取，这是不是市场重复支付？

**面试者：** 不是。24 C 是 B 向 A 支付的二级交易款，市场抵押仍为 100 C，S 不因此增加抵押或份额供应。YES 胜出时 A 的 60 YES 领 60 C，B 的 40 YES 领 40 C，100 NO 不产生付款，总兑付是 100 C。A 的净现金流是 −100＋24＋60＝−16 C，B 是 −24＋40＝16 C。必须把用户钱包现金流和市场 reserve 分开，否则既会误把二级成交当新增抵押，也可能将两类份额各按 1 C 计算成 200 C 负债。

## 第 3 层：谁有权把暂定结果变成最终兑付权

**面试官：** 既然资金必须按结果支付，Go 收到官方赛果后能直接把市场设为 YES 吗？

**面试者：** 不能。官方赛果是证据，不是修改 S 的权限。Go 可展示证据或帮助构造提报，真正状态变化必须通过 S 的合法入口。P 的 YES 提报先生成 Proposed 和 challengeEnd，尚不能领取。有人及时挑战则进入 Disputed，只有绑定的 K 在仲裁期限前裁决，或到期走预设 INVALID，才能生成 Finalized。无人挑战则到期任何人可触发按提报结果最终化。S 保存规则、状态和向量的权威事实，Go 数据库保存可重建投影；不能因为后台任务认为证据充分，就跳过合约状态机。

## 第 4 层：交易截止、观察和裁决为什么必须分开

**面试官：** 你强调状态机，那 closeAt、observeAt、readyAt 能否合并成一个时间？

**面试者：** 在 M1 中不能：00:00 停止交易，01:00 是事件观察界限，02:00 才结束数据发布缓冲。用户在 00:30 不能成交，但市场也不能因为已经停盘就直接提报或领款。结果状态初始为 Awaiting，交易许可另用 closeAt 判断，不需要靠一个枚举同时承载所有时间含义。分开后能表达“已停盘但仍等待证据”“已有提报但尚可挑战”。如果产品允许赛中交易或滚动观察，那是重新定义交易和证据边界的另一种市场，不能在当前追问中悄悄改变 M1 的期限。

## 第 5 层：没人提报或仲裁器不工作，资金会怎样

**面试官：** 分成多个阶段后，如果提报者或仲裁器一直不工作，用户不就一直被锁住了吗？

**面试者：** 我不会只依赖某个 Go 服务触发推进。Awaiting 持续到 proposeBy 仍无提报时，任何人可最终化 INVALID；有效提报后，无争议到 challengeEnd 可最终化，有争议则到固定 arbitrationEnd 后可走 INVALID。这里保证的是在链正常出块且有效交易能被包含的前提下，存在有限的公开推进路径，不是到钟点自动执行。完整集持有人还可在最终化前按规则合并，但只持单边份额的人不能无条件拿回原成本。链停机、交易长期受审查或 C 无法转出，是这套时间规则不能独自消除的外部风险。

## 第 6 层：裁决、保证金返还和用户领取可以算一次完成吗

**面试官：** 你已经最终化了，是否就能告诉用户“市场结算完成，钱已到账”？

**面试者：** 需要区分三种资产事实。S 最终化时写入向量，并在同一个 EVM 事务内让 BondVault 把保证金分配成提款信用；这说明裁决和保证金归属已确定，不说明信用已提走。持有人还要分别 redeem，只有对应交易成功才发生份额销毁和 C 转账。主例里即便 A 已领 60 C，B 仍可能保留 40 YES 和 40 C 未领权利。系统应显示“结果已终局”“你可领取 40 C”“你的领取交易执行成功”等不同阶段，不能用一个市场级 settled 布尔值代替所有人的支付完成状态。

## 第 7 层：已经执行的领取遇到链重组如何解释

**面试官：** 领取回执已经成功了，你说到账以后，包含它的区块又被重组怎么办？

**面试者：** 首先，“回执成功”是某个区块哈希对应分支上的事实，不是不可撤销的外部承诺。正常重组移除领取事务时，同链的 burn 和 C 转账一起被移除；Go 必须回退到共同祖先、撤销相关投影，再按新分支重新确认结果和权利。页面应能从已执行但未最终修订为待确认或未知。对于其他系统的可提现信用、法币支付等不可逆动作，要等约定最终性再授权，而不是凭旧日志付款。若链已承诺的最终性本身遭到破坏，则属于异常事件，需要隔离和审计，不能声称常规索引重放自动消除了所有外部损失。

## 第 8 层：怎样验证架构真的闭环，而不是模块拼图

**面试官：** 这些阶段都说清了，你会怎样验证这套设计没有漏掉交互缺口？

**面试者：** 我会沿 M1 把每个输入、权威状态和完成边界列出来，并做独立变体推演。先验证 100 C 抵押只支持合计 100 C 的完整集负债，再检查二级成交是否只转移权利；随后用“挑战先上链、无争议最终化后上链”的竞争确认不能绕过 Disputed；最后用领取转账失败、重复请求、区块重组检验 burn、付款与投影边界。每一步都问谁有权重试、重试依据哪条持久事实。这样可以允许用户尚未领取、索引暂时落后等合法暂态，同时明确禁止未终局付款、改判后二次兑付和根据过期日志独立补款。

## 本题收束

- **讲透的机制：** 规则形成权利，完整集提供抵押，争议形成唯一向量，领取消费权利，索引呈现不同完成阶段。
- **最容易答错的边界：** 官方证据不等于写链权限，Finalized 不等于每个用户已收到资金，也不等于底层链最终。
- **反例检验：** B 从未发起 redeem，但市场页面显示“B 已到账 40 C”。即使兑付总额算对，完成语义仍然错误。
