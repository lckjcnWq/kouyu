# 大问题 4：份额怎样成交，交易截止与交割如何竞争？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 头寸 / YES / NO | 持有的份额权利／问题成立与不成立的两类份额。 | B 真正拿到 40 YES 才取得相应兑付权，挂单展示不算持仓。 |
| C / 六位小数 | 付款和抵押使用的币／金额精度。 | 40 YES 与 24 C 分别编码为 40_000_000 和 24_000_000 个最小单位。 |
| S / marketId | 实际执行交换的合约／市场编号。 | 签名必须限定 M1，不能复制到另一个市场履约。 |
| 全量签名卖单 | 卖方签下数量与总收款，履约时一次全部交换。 | 本例卖 40 YES 收 24 C，不引入部分成交或链下先成立的付款义务。 |
| maker / taker | 卖单签署者／履约买方。 | A 的签名授权扣 A 的份额，B 提交交易并向 A 付款。 |
| domain / chainId | 签名适用的验证域／链编号。 | 域绑定链和 S，消息还绑定市场、方向、数量与总额，防止跨域复制。 |
| orderNonce / expiration | 订单防重编号／订单自身期限。 | nonce 消费与成交同事务；订单期限和市场截止都要满足。 |
| allowance / 当前余额 | 付款币使用授权／执行当时实际可扣的资产。 | B 有授权还要有钱，A 签单后也可能已卖掉份额。 |
| escrow / 链下冻结 | 链上真实托管锁资／应用层暂时标记不可用。 | 基线签单不预留份额，Redis 标记不能替代 S 的执行时检查。 |
| fill / 原子交割 | 履约入口／份额与付款共同完成。 | 付款失败时 nonce、份额和成功事件一起回滚，不能只交一条腿。 |
| closeAt / block.timestamp | 市场交易截止／交易执行所在块的时间。 | 必须严格小于 closeAt；恰等于 00:00 就不能成交。 |
| mempool / 执行顺序 | 待打包交易池／规范分支里实际先后。 | 截止前进池不保证及时执行，Go 接单顺序不决定链上胜负。 |
| cancel_requested / 链上撤单 | 申请撤单的本地状态／真正让订单身份失效。 | 撤单先成功才能挡后续 fill，不能追回先前已完成的成交。 |
| 外部转让 / merge / redeem | 给别人转份额／成对合并／终局领取。 | 截止后前者冻结；最终化前仍可合并，领取内部销毁不被转让开关误拦。 |
| reentrancy / revert | 外部调用绕回重复执行／事务回滚。 | C 转账须传播失败并防重入；Go 展示不在该原子边界内。 |
| 价格 / 兑付向量 / 链最终性 | 成交条件／未来付款规则／历史稳定性保证。 | 0.60 C 不是客观概率或本金保底；成交最终也不决定赛果。 |

## 把整篇文章压缩成一个故事

**起因：** A 签下在 M1 全量卖出 40 YES、总收款 24 C 的订单，B 想接单。S 不按网页四舍五入的“0.60”重新算钱，而是核验签名里的整数数量、总额、链与合约域、市场、nonce 和期限；签名本身不锁 A 的份额，也没有给 B 保证成交。

**处理及异常：** 合法的截止前履约会在一个事务内消费订单身份、转 40 YES 给 B、从 B 向 A 付 24 C。本文临界变体中 A 在 23:59 签单，B 的交易却到 00:00 才执行，因已等于 closeAt 必须整笔回滚。撤单与 fill 竞争也看规范链执行先后，不听 Go 收件时间；付款失败或余额不足不能留下半笔交割。

**结果及边界：** 正常成交后 B 获得 40 YES，S 的 reserve 不因两人交换 24 C 而增加。它未来可能兑付 YES 下 40 C、NO 下 0、INVALID 下 20 C，既不保底退 24 C，也不证明“胜率就是 60%”。截止后普通转让也冻结，但成对合并和终局内部销毁按各自规则处理；链最终性确认所有权交换，不替未来结果背书。

[返回专题总览](README.md)

**流程位置与核心机制：** 负责用户怎样通过二级交易取得兑付权。基线是单链、全量签名卖单、链上原子交换，不是链下撮合先产生独立付款义务；份额在 closeAt 后禁止外部转让。

## 第 1 层：预测市场的价格怎样变成用户持仓

**面试官：** A 想把 40 YES 以每份 0.60 C 卖给 B，具体怎样成交和交割？

**面试者：** A 签署限定 M1、YES、40_000_000 份额最小单位、总付款 24_000_000 C 最小单位的全量卖单，订单还包括 maker、nonce、期限和可选买方限制。B 在截止前提交交易，S 验证签名、订单未消费、A 份额足够及 B 的付款授权，在同一事务内消费订单身份、转移 40 YES，并从 B 向 A 转 24 C。任何一段失败全部回滚。成交后 B 的 40 YES 就是其未来兑付权，市场 reserve 不变；签名和 Go 返回“已挂单”本身不转移权利，也不代表资产已锁定。

## 第 2 层：怎样让这份签名只在原来的市场有效

**面试官：** 你说按签名成交，那同样的 40 和 24 能否被复制到另一条链或另一个市场执行？

**面试者：** 不能只签价格和数量。我会使用明确类型的签名编码，域绑定 chainId 和验证合约 S，消息绑定 marketId、YES／NO 枚举、maker、份额数量、总付款、orderNonce、expiration 及 taker 限制。S 重建摘要并验证签名者等于实际扣减份额的 maker；域或载荷有任何变化，摘要都不同。将订单显示为“0.60”只用于阅读，执行按固定整数总额，不让前端浮点换算重写付款量。若支持合约钱包签名，需要显式加入其验证接口和行为约束；本基线先限定常规外部账户签名，不能默认所有钱包验证方式相同。

## 第 3 层：同时挂出多份订单会不会重复出售份额

**面试官：** A 对相同 40 YES 签了两份不同 nonce 的卖单，平台是不是必须在 Redis 先冻结持仓？

**面试者：** Redis 冻结只能改善展示，不能保证非托管份额的交割。本模型签名不预留链上资产，S 在实际履约时检查当前余额并按链上事务顺序执行。两单如果合计不超过 A 的可用份额，都可能成交；超过时后来的事务因余额不足整体回滚，不能形成“先承诺必成交再补资产”的义务。同一个订单 nonce 则由 S 原子消费，禁止重复成交。若产品要保证挂单期间资产必定可用，就要增加链上 escrow 或资产锁定机制，并改变用户退出和资本占用规则，不能用链下缓存假装已经实现该保证。

## 第 4 层：截止前签名、截止后上链是否应成交

**面试官：** 如果 A 在 23:59 签名，B 的交易到 00:00 才被打包，是否算截止前已经下单？

**面试者：** 在 M1 中不算成功成交。S 每次执行新铸造、外部转让和 fill 时都要求 block.timestamp 小于 closeAt，同时检查订单自身 expiration；签名时间和 Go 收到时间不能替代执行资格。00:00 等于截止界限，整笔 fill 必须回滚，订单身份也不能被成功消费。本规则牺牲临界点提交的确定成交体验，换取合约能自证的边界。前端应提前提示拥堵和执行期限，但不能保证提交进 mempool 就已经获得份额。区块时间仍有链规则允许的偏差，业务不能承诺秒级现实时间的绝对精确性。

## 第 5 层：截止与撤单竞争，谁来决定结果

**面试官：** 那 A 同时撤单，B 同时成交，Go 服务怎样决定谁先？

**面试者：** Go 不拥有最终裁决顺序。撤单是由 maker 触发链上 nonce 失效，fill 是检查并消费相同订单身份；同一个规范分支中，先执行的合法操作决定后续能否成立。撤单先提交成功，后续 fill 拒绝；fill 先成功，撤单不能追回已经转移的份额和交易款。两者如果都在 closeAt 之后，fill 因时间资格失败，撤销未成交签名仍可作为防重或清理操作，但不是退款。平台可以用本地状态标识 cancel_requested，不能在链上取消最终确认前向用户承诺原签名绝无执行可能。

## 第 6 层：为什么既有截止还要冻结普通转让

**面试官：** fill 已经停止了，为什么连普通 YES／NO 转账也要限制？这是不是所有预测市场都这样？

**面试者：** 不是通用规则，是本教学模型的明确选择。我们把截止后的持有人集合固定，便于解释争议期间权利和最终领取，不允许用户绕过 fill 入口直接把份额转走。S 因此必须同时约束普通份额转让，而不是只停 API 或订单簿。完整集合并在最终化前仍允许，因为它同时消除两类权利和对应抵押；终局后 redeem 的内部销毁不是普通转让，不受该开关阻止。允许到期后继续交易的协议也可以正确，但就必须继续处理领取前后转移、操作者权限及价格发现风险，不能将两种持有人假设混用。

## 第 7 层：一边交换完成另一边失败怎样恢复

**面试官：** 你说内部先转份额再收付款，如果 C 的 transferFrom 失败，B 会不会已经拿走 40 YES？

**面试者：** 不会，前提是两条腿都在同一个 EVM 事务里，付款失败必须向上传播并回滚整笔调用。订单 nonce 消费、A／B 份额变化以及成功事件也随之撤销，不能捕获错误后继续返回成功。S 还需对外部 token 调用加重入防护，采用先校验、更新内部效果、再外部交互的模式，并限定 C 的行为。这里的原子性不覆盖 Go 数据库，Go 可能已经展示提交中，随后需要根据失败回执修正；它不能为了兑现本地状态而再从运营钱包向某方补一笔款，从而破坏原来的无成交结论。

## 第 8 层：成交价格是不是概率或最终回报保证

**面试官：** 这笔 0.60 的成交已确认，能否告诉 B“市场认为胜率 60%，你保底能拿回 24 C”？

**面试者：** 两个结论都不能保证。0.60 是这笔交易的单位价格，受流动性、偏好、信息、风险和执行约束影响，不是 oracle 证明的客观概率。B 的最终回款按固定向量计算：YES 胜出 40 C，NO 为 0，INVALID 为 20 C，而非以成交成本 24 C 保底。成交被链最终性确认只说明持仓和交易款交换在该假设下成立，不决定未来赛果。验证交易模块应检查精确数量、总额、签名域、nonce、截止和回滚，再把这些事实与裁决、收益展示分开，避免把价格、所有权和未来价值混成一句承诺。

## 本题收束

- **讲透的机制：** 域绑定签名、当前余额校验、链上 nonce 互斥、执行时截止和双腿原子交割。
- **最容易答错的边界：** 挂单签名不预留资产，截止前提交不保证截止前执行；二级交易款不属于市场 reserve。
- **反例检验：** 23:59 接收的交易在 00:00 上链，仍因本地“下单时间有效”放行，会绕过已定义的合约截止规则。
