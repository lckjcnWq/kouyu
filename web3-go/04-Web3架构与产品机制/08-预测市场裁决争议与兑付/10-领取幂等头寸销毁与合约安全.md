# 大问题 10：怎样防止重复领取、头寸销毁后无款与合约攻击？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| redeem / burn | 本人发起领取／销毁已经消费的份额。 | 一次清掉 M1 的本人全部 YES、NO，防重依据是链上权利消失而非页面打勾。 |
| S / Finalized | 权威市场合约／已有唯一兑付向量的状态。 | S 执行时检查终局和真实余额，不信客户端缓存金额。 |
| qY / qN / nY / nN / D | 本人两类余额／两类兑付分子／共同分母。 | `floor((qY*nY+qN*nN)/D)` 给出应付 C 最小单位数。 |
| C / reserve / totalYES / totalNO | 抵押币／本市场剩余抵押／未销毁总供应。 | 成功领取同时扣对应供应与 reserve，失败不得留下任一扣减。 |
| claimed[marketId] | 给整个市场设置“已领取”的标志。 | 不能用它防重，否则 A 先领就会堵死 B 的独立权利。 |
| closeAt / 禁止 mint | 外部转让截止／禁止重新铸造。 | 终局后也不能再取得新份额，不为假想“以后又收份额”另设领取轮次。 |
| owner / msg.sender / recipient | 权利人／当前调用者／收款地址。 | 本模型只允许本人烧本人份额并付给本人，不提供任意代领或重定向。 |
| tx.origin / 签名授权 | 最初发起交易的地址／合法许可依据。 | 不用 tx.origin 认权，Go 记录意图也不等于获准替用户操作。 |
| clientRequestId / payloadHash | 稳定请求编号／请求内容指纹。 | 同编号同载荷找回原意图，同编号改市场等含义要报冲突。 |
| txNonce / txHash / replacement | 发送者交易序号／候选哈希／替换关系。 | 一个领取意图可有多个尝试，换哈希不会产生新兑付权。 |
| Unknown / 重试 | 结果待核实／按证据继续提交。 | RPC 超时或未找到不代表失败；先查全部候选、nonce 和指定块权利。 |
| 检查—效果—交互 / 重入锁 | 先验资格、再改内部状态、最后调用外部／防止绕回重复执行。 | 先清余额再安全转 C，相关入口加防护，不把“先 burn”误解为不能回滚。 |
| ERC-20 / 安全转账封装 | 抵押币接口／统一处理受支持返回行为的调用方式。 | false、revert 等失败要让整笔回滚，无返回值成功按受支持币语义处理。 |
| 零兑付 / 非零份额 | 付款算为零／仍有可消费权利。 | 输方或舍入为零仍可本人销毁，可跳过零额转账，但空余额调用要拒绝。 |
| rebase / 冻结 / 脱锚 | 自动改余额／发行方限制转账／价格偏离面值。 | 前者被基线排除，后两者仍是风险；冻结失败保留权利，不保证活性或购买力。 |
| Inbox / Outbox / revision / 重组 | 应用去重／通知待发／修订号／分支切换。 | 只恢复查询与通知，不再驱动付款；撤销旧观察后仍以新规范链余额为准。 |

## 把整篇文章压缩成一个故事

**起因：** M1 最终为 YES，A 有 60 YES＋100 NO，B 有 40 YES。A 调用 redeem，S 在执行时读取本人余额，算出 60 C，先清余额并扣供应、reserve，再安全转币。不是先让 Go 写“已领取”，也不接受一个能把 B 的款转给别人的 recipient 参数。

**处理及异常：** 本文先在转 C 处制造失败：A 的份额、供应、reserve 和事件必须全部回滚，不能留下“已 burn，等待后台补款”。正常重试成功才消费 A 的两类份额并付 60 C；若成功响应丢失，Go 追踪原意图、nonce 和候选哈希，不能直接另转 60 C。即使用新 nonce 重复调用，第一笔已消费余额后第二笔也应拒绝，服务幂等只是少浪费 Gas 的辅助层。

**结果及边界：** A 成功后再领失败，B 仍可独立领 40 C，抵押按 100－60－40＝0 C 收束，绝不能被市场级 claimed 标志拦住。独立 NO 变体中 B 虽只领零，也可本人销毁 40 YES；不要求出现 C 转账才算消费成功。安全转账和重入防护防双领、丢权，不承诺 C 不冻结或链不停机；数据库落后与非最终重组只按规范事实恢复，不授权链外补款。

[返回专题总览](README.md)

**流程位置与核心机制：** 从用户发起 redeem 到同事务销毁和转 C，围绕权利消费、业务意图与交易尝试、失败回滚、授权及外部调用安全连续追问。金额算法沿用第 9 题，规范链回退由第 11 题深入；本题不增加后台代付、任意收款人或新交易机制。

**必要前提：** S 在单链 EVM 上拥有权威份额、reserve 与唯一终局向量。C 和份额均为六位小数；当前持有人一次销毁全部 YES／NO，向自己地址领取。C 无转账扣费、rebase 或回调，仍使用安全转账封装并考虑冻结、返回失败与回滚。

**权限时间边界：** `block.timestamp >= closeAt` 后禁止新铸造、外部份额转让与成交；完整集合并只允许到最终化之前。终局后也不能重新 mint。账户成功 burn 后不能再获得新份额，不构造“后来又收到份额”的场景来改变幂等设计。

**贯穿案例：** A 锁 100 C 得 100 YES＋100 NO，以 24 C 卖 40 YES 给 B；最终 A 持 60 YES＋100 NO，B 持 40 YES。YES 下 A 领 60 C、B 领 40 C；INVALID 独立变体分别领 80 C、20 C，保证金另在 BondVault。

## 第 1 层：防重复领取应该消费什么权利？

**面试官：** 如果让你设计 redeem，怎样保证同一个人不能领两次，又不会误伤其他持有人？

**面试者：** 防重依据是 S 中该市场、该持有人的份额余额被原子消费，而不是设置市场级领取完成。入口验证 `state==Finalized`，读取调用者 `qY、qN`，要求至少一边非零，计算 `floor((qY*nY+qN*nN)/D)`，然后清零这两类余额并销毁供应。余额全零时再次调用就拒绝。

主例 A 成功领取会消费 60 YES＋100 NO，只付 60 C；B 的 40 YES 仍可单独领取。不能设置 `claimed[marketId]=true`，否则 A 抢先领取会封死 B。按用户设置完成标记也只能是辅助信息，不能替代余额消费与原子付款。

本基线在截止后禁止外部转让，终局后禁止 mint，且最终化后不能再合并。成功销毁后该账户没有取得新份额的路径，因此无需为假想的“以后又收到份额”另开领取轮次。未成功交易则没有消费权利，仍可重试。

## 第 2 层：请求幂等和交易幂等怎样区分？

**面试官：** 既然链上余额能防双领，Go 服务是不是只保存一个 txHash 就够了？

**面试者：** 不够。业务意图表示“owner 领取某链、某 S、某市场的全部余额”，用 `clientRequestId、chainId、S、marketId、owner、payloadHash` 持久化。同一个请求标识再次提交相同载荷，返回原意图；同标识换市场或收款含义要报冲突，不能悄悄改写旧记录。

交易尝试是这项意图的一次链上提交，另存 `sender、txNonce、txHash、replacement关系、receipt.status、blockHash`。加速替换可能让一个意图对应多个哈希，哈希本身不是兑付义务身份；同一意图也可能经历明确失败后重新提交，不能把所有历史尝试覆盖掉。

本模型由 owner 自行签署领取，Go 不因持久化了请求就获得动用头寸的权限，交易签名者与链上调用者要匹配。服务层幂等减少重复操作和 Gas，链上权利消费才是跨请求、跨进程防重复付款的最终边界。

## 第 3 层：未知交易怎样安全重试？

**面试官：** 如果同一意图的第一次交易广播超时，用户又点领取或要求加速，你怎样处理？

**面试者：** 先把原尝试标为结果未知，而不是失败。追踪所有候选哈希和发送者 nonce，在规范链上核实是否被包含、是否成功，以及同 nonce 是否被另一交易消费；单个 RPC 返回“未找到”不足以证明原交易不会迟到。加速交易沿用同 nonce 并记录替换关系，不能只保留最新哈希。

同一规范分支上同发送者、同 nonce 只能有一笔交易生效；若错误地用新 nonce 又发 redeem，两个调用也会按链上顺序执行。第一笔成功消费余额后，后一笔因两边余额全零失败，不产生第二笔兑付，但可能仍耗 Gas。不能把两笔回执中的“失败”误解释为整个意图未完成。

只有核实原尝试已失败或被其他交易替换，且指定块仍有可领余额，才安排后续提交；规范链成功但尚未最终仍标明该阶段。无论等待多久，Go 都不能绕过 redeem 另转一笔 C 作为超时补偿。

## 第 4 层：入口怎样防止缓存余额和并发读取造成错误销毁？

**面试官：** 你要求查询余额后再重试，但从查询到上链还有时间差，合约怎样避免信任过期 qY、qN？

**面试者：** `redeem(marketId)` 不接受客户端金额作为权威输入，而是在执行时读取 S 自己的终局向量、调用者两类余额和 reserve。客户端预估可以携带块哈希供展示，却不能据此清除某个旧快照数量。至少一边非零的判断用两项分别比较，不能先无保护地把两个 uint256 相加再判断。

先前查询如果发生在最终化前，用户仍可能合并完整集，只有执行时状态有效；但 Finalized 后所有外部转让、新铸造、成交和合并都关闭。此时同账户余额变化来自领取本身，两个并发领取最终由链上事务顺序裁决，不由 Go 的分布式锁决定。

链重组是另一条分支上的状态恢复，不是该账户收到新份额。RPC 缓存或投影落后只能影响预估和是否值得发交易，不能让 S 在余额为零时接受旧请求付款，也不能让一次消费越过本人实际持仓。

## 第 5 层：销毁、扣抵押和付款怎样排布？

**面试官：** 链上余额读对了，你会先给用户转 C，再 burn，还是反过来，怎样防止中途失败？

**面试者：** 我会采用检查、内部效果、外部交互的顺序，并给相关入口设置重入保护。检查 Finalized、合法向量、本人非零余额和 `reserve>=pay` 后，先清零本人两类余额，扣 `totalYES、totalNO、reserve`，再安全转 C 给本人，成功后形成领取事件；这些动作都位于同一 EVM 事务。

若安全转账返回失败、revert 或 Gas 不足，必须向上传播失败，使销毁、供应扣减、reserve 扣减和本次日志全部回滚。不能 catch 后只记一个“待补付款”，那会把主动领取改造成额外债务账本，并改变本题承诺。

先更新内部状态还能让意外外部重入看不到原份额，重入锁再封住跨入口路径。它们是纵深保护而非异步一致性协议：转账成功后应用数据库写失败，不会回滚链上交易，只能靠索引恢复，不能再补发一次款。

## 第 6 层：输方与零兑付怎样安全消费？

**面试官：** 你把“成功”与转账绑在一起，但只持输方或舍入为零时，是否应拒绝销毁？

**面试者：** 不应拒绝。入口要求非零份额，不要求 `pay>0`。例如独立 NO 终局变体中 B 有 40 YES、付款为零，他仍能由本人调用，把 YES 和对应供应销毁；INVALID 的最小单位余额也可能因向下取整得到零，不能因此锁死权利消费流程。

当 pay 为零时可以跳过 ERC-20 零金额转账，仍在同事务清零余额、扣供应并记录包含 `qY、qN、pay=0` 的领取事件；reserve 不变。若两边本来就为零，则明确拒绝，不能把每次空调用都登记为新领取。事件提交成功才是零兑付完成依据，不能要求一定出现 C 的 Transfer。

两边都清零是本模型一次领全的规则，即使其中一边是输方也不保留到以后。截止后禁止转让、终局后禁止 mint，所以不会存在稍后又积累新份额补取零头的路径；舍入尾差留在 reserve，不向 BondVault 索取补偿。

## 第 7 层：谁能销毁，谁能收款，怎样防止授权绕过？

**面试官：** 你说零兑付也能 burn，那任意人替 B 调用，或把 B 的款领到自己地址，会不会被视为无害操作？

**面试者：** 本模型只允许当前持有人本人调用，销毁 `balance[marketId][msg.sender]`，C 也只能付给该调用者地址。不提供可任意填 `owner、recipient` 的接口，不用 `tx.origin` 判断身份，也不能把交易事件里出现的某个地址当授权。即使 pay 为零，别人强制 burn 仍越过了权利人的操作权限。

Go 意图中的 owner 要与实际签名发送者、合约地址、chainId 和 marketId 对齐，防止错误网络、同名市场或篡改 calldata；RPC 预估成功不替代签名授权。这里没有代领和元交易，不能临时把服务端签名当用户许可。

若另行支持签名代领，必须改变基线并补齐域隔离、签名 nonce、期限及接收地址绑定，不能只加一个 owner 参数。S 的普通转让开关只限制外部份额流转，不能误拦终局后的内部销毁，否则本人的合法领取也会被封死。

## 第 8 层：安全转账封装能覆盖哪些币风险？

**面试官：** 授权没问题、代码也先 burn 后转账，遇到抵押币冻结或非常规 ERC-20 返回值，还能承诺销毁后一定到账吗？

**面试者：** 安全封装应兼容受支持币的无返回值成功行为，并把显式 false、revert 等失败提升为整笔 revert；不能直接调用 transfer 后忽略返回值。本基线还假设 C 无扣费、无 rebase、无回调，铸造时核实实收数量，因此 reserve 与转出数量有确定单位意义。随意更换为其他币会破坏这些前提。

如果 C 因发行方冻结而拒绝向某地址转账，领取失败并恢复原份额和 reserve，安全性仍成立，但活性受阻。不能为了宣称到账而吞掉错误，也不能增设管理员收走该用户抵押的路径。币脱锚则影响经济价值，不是重入锁能够解决的问题。

无回调假设不等于可以删除所有外部交互防护；仍应限制可调用入口，核对供应扣减、整数范围并设置重入锁。封装只覆盖调用成功语义，不证明发行方永不冻结，更不保证真实购买力。

## 第 9 层：链上已领取怎样成为可靠的查询结果？

**面试官：** 冻结导致失败可以重试，但成功后服务崩溃、日志重投，会不会又把领取任务放回待付队列？

**面试者：** 查询状态应从规范链观察构建，而不是从 HTTP 返回结果推断。领取记录保存 `chainId、blockHash、txHash、logIndex` 及 owner、市场、销毁量和 pay；数据库事务一起应用 Inbox、余额投影、undo、Outbox 和完整区块游标，重启后可从提交边界续做。

同一规范应用重复投递不再扣余额，发送通知也不驱动再次转 C；业务意图只是被这次成功执行满足。查询和通知带 owner／market revision、观察块及链最终性阶段，旧消息不能覆盖新状态。链上成功但数据库落后时，应显示水位或处理中，不凭旧投影发外部补款。

若非最终区块被重组，要撤销旧观察、恢复规范分支的余额与任务状态，再核实交易是否重入新分支；不能永久保留“已领”屏蔽已经恢复的权利。业务 Finalized 与领取被包含都不等于链最终，未最终不能生成可提现的链下信用。

## 第 10 层：怎样用失败窗口检验领取安全闭环？

**面试官：** 重投和回退机制都有了，你会怎样检查没有隐藏的双领、丢权或跨用户误伤？

**面试者：** 我会沿执行边界逐段手工推演，而不是只验证 happy path。主例 YES 下，在余额清零后让转账失败，预期 A 的 60 YES＋100 NO、供应和 reserve 全部恢复；正常重试成功只付 60 C，A 再次领取失败，B 的 40 C 权利保持不变。任何靠市场级 claimed 封锁 B 的设计都不成立。

再检查同意图多个 txHash、同 nonce 替换、不同 nonce 重复提交、成功但响应丢失，以及只持输方的零兑付。对每次规范成功执行核对销毁量与付款；失败交易只能消耗 Gas，不能留下份额扣减、付款事件或本地已付账。恶意 recipient 参数和越权 owner 参数不应存在。

最后加入服务重启和非最终分支回退，确认查询 revision 提升、通知可更正，且没有任何独立外部转账。这里是检查标准，不声称完成合约审计或执行工程测试；深重组击穿链最终性时，真实外部损失仍需单独处置，不能靠再次 burn 消除。

## 本题收束

**讲透的机制：** 服务层持久意图与交易尝试分离，合约层通过当前余额消费完成防重；同事务检查、销毁、扣 reserve 和转 C，任一付款失败整体回滚。本人领取、固定接收者、安全转账与重入防护共同封住执行入口。

**易错边界：** 不维护市场级 claimed，不以 txHash 充当业务意图，不把未知交易判成失败，不把零付款判成无效领取。成功 burn 后不能再获得新份额，这是冻结和禁 mint 的既定结果；不能为虚构后续收份额场景改变模型。保证金不是份额兑付补偿池。

**反例检验：** A 成功领取后响应丢失，B 还未领取。A 的重复请求必须最多重新查询或产生失败链上尝试，不能再付 60 C；B 必须仍能领 40 C。若 A 的转账失败却被清空份额，或 B 被全局领取标志拦住，哪怕服务有幂等表和分布式锁，也没有实现正确领取。
