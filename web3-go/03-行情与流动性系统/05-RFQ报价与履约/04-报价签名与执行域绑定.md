# 大问题 4：怎样让报价签名只在正确的链、合约、用户与交易条件下生效？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
| --- | --- | --- |
| EIP712 / typed payload | 按固定字段和类型对完整交易条件签字。 | 绑定双方、资产、金额、身份、nonce 和截止时间；标准本身不自带业务防重放。 |
| domain / 执行域 | 说明这张签字凭据属于哪套协议、哪条链和哪个合约。 | name、version、chainId、verifyingContract 必须一致；S 用自身可信配置，不能照信外部传入的域。 |
| bytes32 / uint256 | 固定长度标识与无符号整数的协议类型。 | Q1、R1 只是业务符号，实际映射须约定；字段类型和顺序也是摘要规则，不能靠 JSON 遍历猜。 |
| maker / taker / msg.sender | 出资报价人、定向交易人和当前调用人。 | M 签名并出 WETH，A 自己调用且唯一收款；S 要求调用人就是已签 taker，不留未签 recipient 旁路。 |
| EOA / ECDSA / low-s | 普通密钥账户、验签算法和签名规范化要求。 | 本文只支持 M 的 EOA 签名，不回退到委托签名或合约钱包；规范化不等于防重复履约。 |
| 签名字节 / payload 摘要 | 签字证明的具体编码，与被授权内容的身份。 | 同摘要可有不同合法签名；它们仍是一份义务，不能按字节差异允许再成交。 |
| quoteNonce / quoteId | 前者控制链上使用资格，后者标识业务报价。 | S 在固定域按 maker 与 quoteNonce 消费一次；quoteId、rfqId 和 A 的交易 nonce 都不替代它。 |
| Unused / Filled / Cancelled | 尚未消费、已交换、已撤销。 | 成功转账才消费，失败全回滚；到期可仍是 Unused，不必写出一个 Expired 链上终态。 |
| deadline / cancel | 执行时间界线，以及 maker 的链上撤销动作。 | fill 要求区块时间严格小于截止；接受不排定优先级，fill 与 cancel 按链上顺序竞争。 |
| 规范链 / 最终性 | 认定当前采用哪条历史，以及何时接受结果稳定。 | 相同域的分叉不被签名自动识别；释放预占须排除旧成交，不能靠本地 TTL 或一次查无结果。 |

## 把整篇文章压缩成一个故事

M 准备向 A 卖 1 WETH，风险服务先预占额度，再固定支付 3000 USDC 的完整载荷。Go 服务、钱包和 S 必须按同样字段类型、顺序与执行域计算摘要，否则看似同名的报价也不是同一授权。协议还须补齐真实地址与标识编码，文中的业务符号不能直接当部署参数。A 自己提交交易，S 不仅恢复 M 的签名，还核对调用人就是 A、收款人不能被换、资产金额合法且未到截止。验签即使再次通过，S 的 maker 与报价 nonce 状态也只允许一次成功交换；转账失败则连消费状态一起回滚。同一内容重新签出不同字节仍是同一权利，不能多预占或多成交。M 若想撤销，必须上链 cancel，平台写取消或 A 已接受都不能裁决先后。签名也未冻结钱包，授权撤销仍会使执行失败。观察到成交后还要核对规范链和最终性，重组可能让旧分支的 Filled 消失；同域分叉也不是签名标准能自动隔离的。只有核实最终成交，或证明旧资格关闭且此前未成交，才结清预占，不能到期就当承诺从未发生。

**流程位置与核心机制：** 从 LP 批准并固定报价、M 签署 EIP712 消息，到 A 提交交易、S 验签与消费执行资格。重点是签名到底授权了哪些条件、合约怎样强制落实，以及域分离、nonce 和取消分别覆盖什么问题；不提供可运行合约或攻击复现。

## 第 1 层：签名先绑定完整交易条件，再由 S 强制执行

**面试官：** 怎样让报价签名只在正确的链、合约、用户与交易条件下生效？

**面试者：** 必须同时设计结构化签名内容和合约执行约束，不能只说“用了 EIP712，所以安全”。M 签的是一个明确域中的完整报价，S 则根据同一份数据验签，并逐项检查执行条件。

EIP712 domain 明确包含 `name、version、chainId、verifyingContract`。前两项是本协议预先固定的名称和版本常量，后两项必须是 `1` 和 S。报价结构包含 `quoteId、rfqId、maker、taker、makerToken、takerToken、makerAmount、takerAmount、quoteNonce、deadline`，每个影响权利或可核验身份的字段都参与签名。

主例的签名授权是：M 向 A 卖出 `1e18` 个 WETH 原子单位，换取 A 的 `3000e6` 个 USDC 原子单位，执行 nonce 为 73，执行时间必须严格早于 `1800000020`。不能把这份签名理解为“任何人可以拿到 1 WETH”，也不能理解为“平台可以在以后另填成交价格”。

S 不仅验证恢复出的签名地址等于 M，还要求 `msg.sender == quote.taker == A`，两种代币属于对应白名单，金额合法，`block.timestamp < deadline`，`state[M][73] == Unused`。WETH 收款地址从已签的 taker 得出并固定为 A，USDC 固定转给已签的 maker M，不接受一个不在签名内的可替换 recipient。

这套组合中，签名说明谁授权了哪些条件，执行逻辑说明什么情况下能使用授权。EIP712 标准本身不内置重放保护；域分离、执行 nonce 的一次消费、取消和严格截止需要分别落到协议规则与 S 的状态检查里。

## 第 2 层：相同字段名不代表一定计算出相同摘要

**面试官：** 你说所有字段都参与签名，但 Go 服务、钱包和 Solidity 可能各用一套编码。怎样防止“都叫 deadline”却签出不同消息，或者让调用人指定一个错误域？

**面试者：** 把字段类型、顺序、类型名称和域配置当成协议的一部分，而不是各服务的默认值。在本题的编码约定中，`quoteId、rfqId` 使用 bytes32 标识，参与者与 token 使用 address，两个 amount、quoteNonce 和 deadline 使用 uint256；`Q1、R1` 是业务符号，实际如何映射成 bytes32 必须预先约定，不能一端签字符串、一端按任意 hash 解释。

EIP712 的结构摘要由固定的类型描述与按声明顺序编码的字段形成，最终签名摘要组合 `0x1901` 前缀、domain separator 和报价结构摘要。说明这些组成是为了检查各端是否一致，不是让系统手写一套模糊的字符串拼接；实现应采用明确支持标准类型编码的库，不用 `personal_sign` 的个人消息前缀代替 typed data，也不把 JSON 对象的自然遍历顺序当作协议编码顺序。

S 自己构造预期 domain：固定 name/version、当前受支持网络的 chainId=1、`verifyingContract=address(S)`，并校验所处链符合本模型。链下可以把 domain 随报价提供给钱包核对，但 S 不能直接相信调用参数里的 chainId、名称或 verifyingContract，再据此构造任意域摘要。若合约复制到其他地址，新的地址不应继续接受绑定旧 S 的签名；若运行在不同 chainId 的链上，也不能沿用只缓存 chainId=1 却不检查实际链的错误做法。

基线没有给出 name/version 的字面值，也没有给出实际合约与代币地址，因此本文只说明必须固定并一致，不虚构部署参数。正式协议必须补齐这些常量和类型描述，并用跨语言的相同输入、相同中间摘要、相同最终摘要进行一致性核对。只校验“恢复地址看起来像 M”而不核对待签内容，不足以说明业务条件正确。

## 第 3 层：正确签名也能被重复提交，谁负责一次性

**面试官：** 现在各端能算出同一摘要。假如 A 原样提交同一份合法签名两次，domain 和验签都不会变，怎样避免卖出两份 WETH？

**面试者：** 原样提交两次，EIP712 的验签本来都可能通过，所以要由 S 的执行状态限制消费。主例在固定 `chainId=1、S` 内，以 `(maker=M, quoteNonce=73)` 定位状态，第一次成功交换将 `Unused` 改为 `Filled`，之后的相同报价调用必须因为状态不再 Unused 而拒绝。M 的合法 cancel 也可以把 Unused 改成 Cancelled，使后续 fill 失效。

报价资格必须和两条 ERC20 转账同处一笔 EVM 原子调用：先校验并写入消费状态，再执行安全转账；任何转账或后置检查失败都回滚整个调用，包括 nonce 写入。这样不会出现成功交换两次，也不会出现转账失败却永久烧掉执行资格的半成品结果。发生重入时，重入防护和已消费检查阻止同一资格再次进入交换。

`quoteId` 是稳定的业务身份，但不是本模型的唯一执行屏障。即使某份载荷换了一个 quoteId，只要仍使用 `(M,73)`，也不能在第一次消费后再执行；签发端更应禁止同一 `(M,73)` 绑定两份不同 payload，而不是让链上“谁先执行谁赢”掩盖错误签发。反过来，两份不同 nonce 的 firm 报价，即使属于同一个 R1，也可能分别是有效权利。

A 的交易 nonce 也不能替代报价 nonce。相同原始交易的重广播只有同一交易哈希，但 A 仍能用不同交易 nonce 再调用同一报价，所以 S 必须自行检查报价资格。应用对 R1 只选择一个 intent，并不意味着 S 对 R1 建立了跨 maker 或跨报价的全局一次成交约束；本模型没有这个额外状态。

## 第 4 层：为什么不能拿签名字节本身做防重键

**面试官：** 既然摘要固定了，直接保存已经用过的签名 hash，不是比维护 maker nonce 更简单吗？M 偶尔会重新签同一 payload，又应该怎样处理？

**面试者：** 不能把“签名字节是否出现过”当成业务消费权利。ECDSA 可以对同一摘要产生不止一个合法签名表示；签名服务重试也不应依赖必然返回逐字节相同的结果。即使采用规范化签名检查，授权身份仍应由已签 payload 和执行 nonce 决定，而不是由某一份证明的字节身份决定。

S 使用可靠 ECDSA 校验，拒绝非法长度、非法恢复参数、零地址恢复结果，并实施 low-s 等规范要求，恢复出的地址必须等于 payload 中的 maker M。这个规范化减少歧义和错误输入，但不取代 `(M,73)` 的一次消费。这里仅支持 M 的 EOA 签名，不因为验签失败就回退到其他签名模式、EIP1271 或所谓平台代签。

签名服务对同一 `quoteId` 重试时，只能签同一份不可变摘要；得到另一份合法签名也仍然是同一个交易权利。数据库可以保存签名副本和交付次数用于审计，但不能因为有两份不同字节就预占两次或允许成交两次。若同一 quoteId 对应不同摘要，则是数据冲突，应停止外发并调查，而不是继续按“新签名”处理。

LP 为同一 `(M,73)` 误签不同价格时，链上状态最多允许一份成功，不会自动判定哪份才符合最新风控。所有已泄露的合法 payload 都可能在消费前被使用，所以签名任务必须从准备阶段就确保同 nonce 同载荷。安全的 nonce 分配和不可变性是签发职责，不能把成本转嫁给事后链上竞争。

## 第 5 层：验签成功为什么不等于资产已锁定

**面试官：** 你已经保证签发不复用 nonce。那 M 的签名是否证明它确实有 1 WETH 可卖？如果定价和签名服务之间超时，LP 的义务该怎么处理？

**面试者：** 签名证明 M 授权了这组条件，不证明钱包里现在或以后都有资产，也不冻结 allowance。主例 M 初始有 10 WETH 且已对 S 足额授权，但它仍可能在 A 执行前转走资产或撤销授权。一次 eth_call 模拟成功也只是该区块快照上的执行结果，不是锁资操作。

LP 的库存风险服务必须先以数据库事务为 quoteId 预占 1 WETH，再确定并持久化不可变 payload，只有对应风险记录与摘要都就绪才允许签名外发。签名接口读取确定的准备记录，不能让任意前端请求随意指定金额、taker 和 nonce 后直接拿 M 的密钥签字。预占是该 LP 内部的保守风险约束，不是平台对链上资产的控制权。

最危险的窗口是签名可能已产生，但调用方没收到响应。签名服务超时、进程崩溃或外发接口返回未知，都可能发生在有效签名已经进入日志、队列或网络之后。除非能够证明从未产生或泄露可用签名，否则继续保留原义务，只能围绕同 quoteId、同摘要恢复，不得释放后把同一额度签给另一份报价。

已经签出的报价也不能因数据库改成 Cancelled 而失效。LP 想停止义务，要么由 M 发链上 cancel 并核验结果，要么等待执行资格按严格 deadline 关闭，同时核验此前没有成交。风险服务控制“下一份签名能否产生”，S 控制“这份授权能否执行”，两个边界不能互相冒充。

## 第 6 层：签名有效期与链上取消怎样真正生效

**面试官：** 你说只能通过 cancel 或到期关闭旧资格。A 已接受并广播后 M 才取消，谁优先？A 在最后一秒广播，超过 deadline 才执行，又算谁的承诺有效？

**面试者：** 链下接受没有链上排序权。M 必须以自己的 EOA 调用 S.cancel，由 S 以 `msg.sender` 限定只能取消该 maker 的 nonce；这里不接受平台后台标记、第三方取消请求或额外链下取消签名来代替这个操作。

在同一规范链历史中，fill 和 cancel 按真实执行顺序竞争。如果有效 fill 先成功，`(M,73)` 为 Filled，后续 cancel 不能改写资产交换；如果 cancel 先把 Unused 改为 Cancelled，后续 fill 即使签名和金额都正确也必须失败。若 fill 先执行却因余额不足而回滚，nonce 仍是 Unused，接下来的 cancel 仍可成功，不能把“先被包含过一次失败调用”误当作已经消费。

截止同样由 S 执行时判断。主例 `deadline=1800000020`，在 `1800000008` 执行符合时间条件，在 `1800000020` 执行就因等于截止而拒绝。广播时间、钱包确认时间、平台 Selected 时间都不能替代区块时间戳；不能采用 `<= deadline` 放宽一秒边界。

到期时 Unused 可以仍然保持 Unused，Expired 是依时间与规范链观察推导的资格视图，不需要把每份报价自动写成第三种链上终态。状态终态仍是 Filled 或 Cancelled。应用显示“已到期”，不能因此忽略此前有效时间内的成功 fill，下一步还必须做规范链和最终性核验。

## 第 7 层：域绑定与一次消费仍不等于任何情况下都绝不重放

**面试官：** 你有 domain、nonce 和 deadline 了，是否就能对用户保证“无论重组、换节点或分叉，这份报价都绝不再次执行”？到期预占什么时候才能释放？

**面试者：** 保证要限定在采用的链和最终性模型内。chainId 与 verifyingContract 能隔离不同 chainId 的网络和不同结算地址；name/version 固定协议上下文。但如果某个分叉保留相同 chainId、相同合约地址和相同状态条件，EIP712 并不会识别它是“经济上另一条链”。这不是本题可以通过口头承诺跨越的保证，生产服务必须明确规范链与最终性来源。

同样，`t0+8` 的 fill 如果还未最终确认，可能随区块重组从规范链消失。旧分支的 Filled 不能当作新分支的永久状态；新规范链上可能仍为 Unused，且在未到截止的执行时间里仍可能填充。应用需要撤销旧包含观察并重扫，不能以数据库已经写过 Filled 为由拒绝读取新链事实，也不能把重新观察的同一意图误报为第二笔独立成交。

预占释放要证明未来不可执行，并排除过去已成交。最终确认的 Cancelled 可以构成关闭资格的证据；按过期关闭时，需要最终性覆盖时间戳不小于 deadline 的规范区块，核对此前完整历史、S 的状态和相关事件。如果此前已 Filled，则按实际成交消耗义务并对齐资产快照，而不是释放成未花掉的 1 WETH。

因此本地 TTL、缓存里查不到回执、某节点返回 Unused，都不能独立证明安全释放。规范链证据有缺口时保留义务，必要时暂停新签发。最终性被异常打破则进入事故处理边界，不继续宣称普通超时重试规则足以覆盖。EIP712 负责签名语义，nonce 负责本链一次消费，链观察负责认定哪次消费属于最终事实。

## 第 8 层：怎样核对签名覆盖范围而不误判保护能力

**面试官：** 你把保证收敛到了明确的规范链和最终性边界。具体怎样审查这份签名协议，确认没有漏字段，也没有把应用层保证说成链上保证？

**面试者：** 先建立一份有效主报价的核对样本，固定各端使用的域、类型描述、完整 payload、结构摘要和最终摘要，确认 M 的签名与 A 发出的调用使用同一份内容。正式联调还要补齐实际 name/version、bytes32 标识映射与地址配置，这些不是文档里可以靠 Q1、R1、S 符号直接运行出来的值。

然后逐项改变一处条件进行人工审查或后续受控验证：改变 chainId、verifyingContract、name/version，应不再是 S 当前接受的域；改变 taker、任一 token、任一 amount、quoteNonce、deadline、quoteId 或 rfqId，摘要应改变，原签名不再授权修改后的载荷。换调用人则即便原签名仍对原载荷有效，也应在 `msg.sender == A` 检查处被拒绝。固定收款人从 payload 派生，不能留出一个未绑定的旁路参数。

再核对状态与资产边界：第一次在 `t0+8` 成功后状态为 Filled，A/M 余额严格等于公共主例，重复调用被 nonce 拒绝；第二条资产腿失败时，nonce、第一条转账和成功事件全部回滚；deadline 等于时拒绝；cancel/fill 顺序改变时只有对应的规范链结果。链外结果投递以事件身份和消费事务防重，不用签名字节去重代替执行状态。

最后明确没有保证的部分：同 R1 不同 nonce 是独立权利，应用只选一个 intent 不能使其他有效签名自行失效。切换新报价前必须关闭旧权利并排除旧成交，或明确承认约束仅在应用层、无法阻止 A 手工执行其他报价。单次模拟不锁资，签名也不保证 Gas、余额、授权或包含时间始终满足。能说清这些限制，才算真正解释了“只在正确条件下生效”，而不是把所有风险都归给一个签名标准。

## 本题收束

### 讲透的机制

- domain 的 name/version/chainId/verifyingContract 限定签名上下文，完整 typed payload 绑定参与者、资产、金额、身份、nonce 和 deadline；S 用自己可信的域配置验签，不接受调用者指定任意域。
- EIP712 本身不内置防重放。S 的 `(maker, quoteNonce)` 一次消费、maker 链上 cancel、严格 deadline 和原子资产交换共同约束授权的使用。
- LP 签名前的数据库事务预占防内部超额承诺；签名可能泄露就保留义务。规范链和最终性证据才支持成交消耗或未成交释放。

### 易错边界

签名正确不等于资产已冻结，low-s 不等于业务防重放，quoteId 不等于唯一执行屏障，A 的交易 nonce 不等于 maker 的报价 nonce。域绑定不能自动识别保留相同域条件的分叉；应用只选择一个 R1 意图，也没有给 S 增加跨 maker 的全局消费屏障。

### 具体反例与验证

以下为审查与人工推演，不提供攻击步骤，不宣称已执行工程测试：

1. 只改一个签名字段或 domain 字段：核对摘要与恢复结果，原签名不得授权新条件；改调用人则由调用绑定检查拒绝。
2. 原样提交两次有效主报价：第一次可成交，第二次必须被 `(M,73)` 的 Filled 阻止，而不是指望第二次验签失败。
3. 同一 payload 得到两份不同签名字节：仍只对应一份执行资格和一份 1 WETH 预占。
4. `block.timestamp == 1800000020`：拒绝；不是把签名当作提前广播者的过期通行证。
5. cancel 先成功或 fill 先成功：以规范链真实顺序分别得到 Cancelled 或 Filled；失败 fill 不消费 nonce。
6. 截止前成交被观察但未最终确认：本地到期不得释放；重新核验规范链后再决定确认、重建或关闭义务。
7. 同 R1 另有不同 nonce 的报价：承认它是独立权利，不能把应用的单选框解释成 S 的全局防双买机制。
