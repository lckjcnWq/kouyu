# RFQ 报价与履约：核心深挖面试专题

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
| --- | --- | --- |
| RFQ / exact output | 带着需求找人问价，并固定最终想买到的数量。 | 本专题统一为 A 用 USDC 买 1 WETH，同输出比较成本；不是订单簿撮合或池内自动定价。 |
| maker / taker / LP | 报价出资方、选择交易方，以及流动性提供者。 | M 签报价并出 WETH，A 自己发交易且唯一收款；平台不持有双方钱包资产。 |
| firm quote / 展示报价 | 已签具体交易条件，与页面展示这份条件的动作。 | firm 是约定条件下的经济承诺，不是保证可成交；展示、签名、接受和履约各是独立阶段。 |
| 库存预占 / 非托管 | 内部为义务留额度，而真实资产仍在外部钱包。 | 签名前以数据库事务准入，未知签名继续占用；不能冻结 M 转账或阻止撤销授权。 |
| EIP-712 / 执行域 | 用结构化签名绑定条款，并限定链和结算合约。 | 固定双方、资产、原子金额、nonce、deadline 及域；验签不替代执行资格、余额和授权检查。 |
| quoteId / rfqId / quoteNonce | 报价身份、询价身份和链上报价消费序号。 | Q1 关联业务，R1 可有多份报价；S 按 maker 与 quoteNonce 消费，不按 R1 跨报价择一成交。 |
| Accepted / intent / TxAttempt | 选择记录、逻辑执行意图和钱包的具体交易尝试。 | 接受不成交不锁资；多个哈希可属原意图，A 的交易 nonce 不等于 M 的报价 nonce。 |
| 原子整数 / Gas | 精确到代币最小单位的数量，以及付给网络的执行费。 | USDC 6 位、WETH 18 位；Gas 另付原生 ETH，不能混入 USDC/WETH 守恒或事后改价。 |
| fill / cancel / deadline | 执行交换、maker 撤销，以及执行时间界线。 | S 只允许 Unused 成功进入 Filled 或 Cancelled，失败全回滚；时间等于截止也拒绝。 |
| 规范链 / finalized | 当前采用的链历史，以及按政策核验的最终性边界。 | 包含可因重组撤回，最终期限覆盖还须排除过去成交；越过承诺边界走事故处理。 |
| consumed / released / 同水位 | 成交核销、未成交释放，以及余额义务采用相同证据范围。 | 最终成交后余额 9、活动承诺 0、可报 9；不能重复扣库存或先释放旧余额上的承诺。 |
| outbox / inbox / revision | 待发义务、接收去重记录和持久状态版本。 | 至少一次交付加本地事务防重复效果，旧通知不覆盖新结果；不构成链、数据库和消息的全局事务。 |

## 把整篇文章压缩成一个故事

A 有 5000 USDC，想固定买到 1 WETH。平台有界询价，M 结合行情与库存形成价格，先在风险库预占 1 WETH，再固定原子金额、执行域和 nonce，签出 3000 USDC 的定向报价。平台验签、预检和比较成本后展示，A 接受只形成意图，仍须自己用钱包调用 S。S 核对调用人、完整条款、授权余额、严格截止和未消费资格，将两种转账与 Filled 一起提交；失败全回滚，Gas 另付 ETH。主例最终 A 为 2000 USDC、1 WETH，M 为 3000 USDC、9 WETH。广播未知时系统追原交易，不换新权利补单；取消与 fill 看链上成功顺序，签名和内部预占都不锁钱包。观察器连续扫描、处理重组并核验最终性，再让风险侧同水位核销，查询与通知用 outbox、inbox 和版本可靠收敛。到期释放还须排除此前成交，切主和过载也不能忘掉旧签名。本专题只用普通白名单资产、全量履约，不支持部分成交、中继和自动回退。各母题分别深挖这些边界，末尾伪代码只推演固定报价的单链竞争与回滚，不冒充真实签名、链观察、故障实验或全链路工程。

## 第一部分：文字全流程

### 1.1 讨论基线：究竟在交易什么

采用一个明确的教学模型：**单链 EVM、非托管现货、链下定向签名报价、taker 自己发交易、链上全量原子交换。** 不把托管账本的冻结、订单簿撮合或 AMM 的滑点模型混入本案例。

| 维度 | 本文统一假设 |
|---|---|
| 产品 | 用 USDC 买入固定数量的 WETH，按 exact output 比较报价 |
| 网络与合约 | `chainId = 1`；固定、不可升级的结算合约 S；地址使用符号表示，不是部署配置 |
| 交易双方 | maker M 是出资并签名的 EOA；taker A 是自行提交 fill 交易的 EOA，也是唯一 WETH 收款人 |
| 报价 | 链下 EIP-712 定向 firm quote，绑定 A、资产、原子金额、nonce、期限与执行域；firm 指约定条件下的经济承诺，不等于链上已锁资 |
| 执行数量 | 全量一次交换，不支持部分履约，也不支持在原报价上改数量 |
| 资产 | 白名单普通 ERC-20：USDC 6 位、WETH 18 位；排除转账扣税、rebase 和回调型资产 |
| 权限 | 双方已向 S 完成足额 allowance；授权和余额仍可能在执行前变化 |
| 费用 | 无协议费、无单列 LP 费，价差已包含在报价中；A 用额外原生 ETH 支付 Gas，不计入两种代币余额 |
| 资产控制 | 钱在用户和 LP 钱包，不在平台账本；LP 内部库存预占只限制其自身报价策略，不冻结钱包 |
| 取消与到期 | M 通过 S 的 cancel 撤销 nonce；到期以执行区块的 `block.timestamp < deadline` 为准，等于期限即拒绝 |
| 排除能力 | 不支持中继、代付 Gas、委托签名、EIP-1271、跨链、部分成交、自动对冲或自动 AMM 回退 |

这里的“接受”仅表示 A 在应用中选中报价并形成执行意图。**成交裁决在 S 内，最终资产结果在规范链上。** 数据库写成 Accepted 不会保留链上价格或阻止链上 cancel。

### 1.2 贯穿案例与完成结果

`t0 = 1,800,000,000` 是方便推演的教学时间戳，不是实际交易记录。

- A 初始持有 **5,000 USDC、0 WETH**；M 初始持有 **0 USDC、10 WETH**。
- A 请求买入 **1 WETH**，询价身份 `rfqId = R1`。
- M 返回 `quoteId = Q1`，`quoteNonce = 73`，`deadline = t0 + 20`。
- 签名原子金额：`makerAmount = 1,000,000,000,000,000,000` WETH 原子单位，`takerAmount = 3,000,000,000` USDC 原子单位。
- A 在应用中选中 Q1 后，由自己的钱包向 S 提交 fill；假设它在 `t0 + 8` 的区块成功执行，随后该区块进入本文采用的最终性边界。
- 最终 A 为 **2,000 USDC、1 WETH**；M 为 **3,000 USDC、9 WETH**。`(M, 73)` 在 S 内为 Filled。

**三个不同身份：** `Q1` 是业务报价身份，`73` 是 S 内的 maker 报价执行 nonce，A 的钱包交易 nonce 则由 A 的交易序列决定，不能混用。

### 1.3 主流程：从询价到义务闭合

```text
A 发起询价〔R1、A、USDC→WETH、固定买入 1 WETH〕
    ↓
询价服务校验资产、数量、用户和请求身份
    ↓
向有限数量的合格 LP 扇出请求〔统一截止预算〕
    ↓
M 的定价服务读取完整行情与库存风险快照
    ↓
M 的风险服务在数据库事务中预占 Q1 对应的 1 WETH
    ↓
持久化不可变报价载荷与 (M,73) 分配，再由 M 的签名服务签发
    ↓
报价服务收集、验签、过滤期限与条件，比较相同输出的总成本
    ↓
向 A 展示 Q1〔1 WETH 换 3,000 USDC、deadline、S、网络、Gas 估算〕
    ↓
A 选中 Q1〔应用持久化执行意图；这不是链上成交〕
    ↓
A 的钱包核验并广播 fill(Q1, signature)
    ↓
S 在执行区块校验签名、A、金额、期限与 nonce
    ├─ 任一条件不满足 → 交易失败；换币状态全部回滚，Gas 另计
    └─ 条件满足 → nonce 置 Filled，双向 transferFrom，在同一事务内完成
                         ↓
链观察器保存区块哈希、receipt 与 Filled 日志
                         ↓
校验规范链并推进确认状态；达到最终性边界后确认最终成交
                         ↓
M 的风险服务对齐确认余额和预占核销〔10→9 WETH，active 1→0〕
                         ↓
Outbox 交付结果；消费方幂等更新订单查询与私有回报
                         ↓
A 查询到已最终确认；LP 的报价风险义务与本地投影闭合
```

询价服务通常属于报价平台，库存风险与签名服务属于 LP。它们可以是不同参与方的服务，图中的衔接不表示共享数据库。平台不能替 LP 证明钱包资产已被锁定。

### 1.4 主要异常分支

```text
输入非法或无合格 LP → 拒绝或返回无报价；没有资产交换
报价计算完成但风控预占失败 → 不签发 firm quote
预占完成、签名或外发结果未知 → 按签名可能已泄露处理，继续占用风险
询价超时后报价迟到 → 不覆盖已选意图，也不自动执行迟到报价
A 点击接受但没有发交易 → 只是应用意图，不能记成交或扣代币
广播超时或查不到 hash → 保留未知状态，查原交易和 nonce，不创建新权利补单
```

```text
M 的 cancel 与 A 的 fill 竞争
    ↓
同一规范链上的实际执行顺序裁决
    ├─ 有效 fill 先成功 → Filled；后续 cancel 不能改写
    ├─ cancel 先成功 → Cancelled；后续 fill 拒绝
    └─ fill 先执行却 revert → 没有消费 nonce；cancel 仍可能成功

到达 deadline
    ↓
未来有效规范区块拒绝 fill
    ↓
不能据本地时钟直接释放预占
    ↓
核验覆盖 deadline 的最终规范链前缀和此前执行历史
    ├─ 曾 Filled → 记消耗，并对齐余额
    └─ 最终无 fill 且不可再执行 → 释放预占
```

未最终确认的包含可能被重组撤回，应退回对应的未决状态并重新核验；不能把 receipt 消失解释为资金已经安全可释放。各异常独立改变一个条件，不与主案例的成功余额同时叠加。

## 第四部分：设计与规则

### 4.1 不变量与业务规则

1. **执行身份：** 在同一 `chainId + S` 中，`(maker, quoteNonce)` 从 Unused 最多成功进入一个终态。报价业务 `quoteId` 的唯一约束不能替代链上执行约束。
2. **签名完整：** 报价的 `quoteId、rfqId、maker、taker、两种 token、两个原子金额、quoteNonce、deadline` 均进入结构化签名。域显式包含 `name、version、chainId、verifyingContract`，S 不接受外部调用者任意指定执行域。
3. **调用绑定：** `msg.sender == quote.taker == A`，WETH 接收方固定为 A，USDC 接收方固定为 M；没有可被中途替换的额外 recipient。
4. **期限：** `block.timestamp < deadline`；本地倒计时仅做 UX 和提交预算。Expired 是推导视图，不要求 S 自动把 Unused 改成 Expired。
5. **原子交换：** 成功时 A 支付 3,000 USDC 且得到 1 WETH，M 反向变化；任意资产腿或校验失败，两条腿、nonce 变更及成功事件一起回滚。交易失败仍可能消耗 Gas。
6. **同币种守恒：** 主案例 `USDC: 5,000 + 0 = 2,000 + 3,000`，`WETH: 0 + 10 = 1 + 9`。ETH Gas 不混入此式。
7. **签名不是资金冻结：** 内部风险上 `activeCommitment <= usableInventory` 是按明确快照、共享资本口径建立的准入约束，不是任意未来钱包状态的密码学保证。钱包转账或撤权仍可导致 fill 失败。
8. **风险只闭合一次：** 最终成交后 `confirmedInventory: 10→9` 且 `activeCommitment: 1→0`，可新增承诺容量前后均为 9；不能余额扣一次、预占核销再扣一次。
9. **释放证据：** 非成交释放必须证明未来不可执行并排除历史成交。对于过期，要在采用的最终性假设内核验时间覆盖 deadline 的规范链前缀、S 状态和必要执行证据；不以缓存 TTL、HTTP 超时或单次未查到为依据。
10. **选择的保证范围：** 应用可保证同一请求只选择一个 intent，但不同 firm quotes 是不同链上权利，S 没有跨 maker 的全局 R1 消费屏障。平台不能宣称恶意或手工绕过界面的 A 无法成交多个报价。

### 4.2 架构与权威

```text
A / 钱包
    ├─ 询价、选择 → 报价平台〔请求与 intent 数据库〕
    │                  ├─ 有界扇出 → LP M〔定价 → 风险事务 → 签名〕
    │                  └─ 返回不可变 quote + signature + 执行参数
    └─ 自行签署并广播交易 → EVM / S / USDC / WETH
                                  ↓
                         链观察器〔连续扫描、块哈希与最终性〕
                                  ↓
                   原始观察 + 业务投影 + Outbox + checkpoint
                                  ↓
                     私有回报 / 查询投影 / LP 风险核销
```

平台数据库、LP 数据库与 EVM 不构成一个全局事务。每个局部事务的提交边界必须明确；跨域用持久义务、可验证结果和恢复推进收敛。链上状态与链下观测冲突时，先核实规范链与观察水位，不以本地终态压过资产事实。

### 4.3 核心对象与交互

| 对象 | 必要字段 | 作用与边界 |
|---|---|---|
| RFQRequest | `requestKey、payloadHash、rfqId、taker、tokens、exactOutput、deadlineBudget` | 同键同载荷返回原请求；同键异载荷拒绝 |
| SignedQuote | 上述签名字段、`domain、digest、signature、pricingVersion` | 签名权利不可变；定价审计版本可以额外存证，不临时改金额 |
| LPReservation | `quoteId、maker、token、amount、status、riskVersion、evidenceRef` | 记录本 LP 尚需保留的承诺；不是用户资产冻结表 |
| ExecutionIntent | `intentId、requestKey、quoteDigest、taker、selectionVersion` | 应用选择事实；改用新报价需要显式新决策 |
| TxAttempt | `intentId、sender、txNonce、txHash、calldataHash、status` | 钱包返回的信息需核验；同 nonce 提费可有多个 hash |
| ContractState | `(M,73) -> Unused / Filled / Cancelled` | 真正的报价执行屏障；到期可能仍存 Unused |
| ChainObservation | `chainId、blockNumber、blockHash、txHash、logIndex、canonical、finality、revision` | 观察身份保留分叉区别；业务结果身份另行建立 |
| Delivery / Projection | `eventId、payloadHash、businessKey、revision、checkpoint` | 至少一次交付；消费事务防重与防旧版本覆盖 |

**教学编码约定：** `quoteId、rfqId` 使用 `bytes32`，参与者及 token 使用 `address`，金额、nonce、deadline 使用 `uint256`；字段类型、名称和顺序属于协议。Q1/R1 是可读符号，不是直接提交的钱包参数；具体 bytes32 映射、domain 的 name/version 字面值及真实地址需在正式协议联调时固定，本文不虚构部署配置。最终性核验采用主网 `finalized` 边界及规范祖先关系，不指定没有依据的固定确认数或等待时间。

签名身份、链上事件与投影身份不能混为一键：观察身份包含 `blockHash`；最终领域结果可用 `chainId + S + maker + quoteNonce + kind` 识别。对未最终状态的变更还要有明确 revision，不将可撤回观察永久当作不可变成交。

### 4.4 实现选择

- **Go 金额：** 资产原子数量使用校验后的十进制字符串与 `math/big.Int`，拒绝负数、越界及隐式浮点转换；共享快照不传递可变指针别名。
- **报价并发：** 有界 worker/信号量与总截止预算；向有界结果通道收集，响应校验后才进入候选集。取消 context 不意味着远端 LP 从未签发。
- **LP 风险存储：** 数据库唯一键约束 `quoteId` 和 `(maker, quoteNonce)`；排序锁定共享钱包/资产风险行，事务内验证并预占。Redis 只做缓存或限流，不是 firm 签发的唯一权威。
- **签发恢复：** 持久化签名任务与确定载荷后外发；签名和响应超时视为可能泄露，重试同一载荷，不能凭服务重启认为旧签名无效。
- **链上验证：** 可靠 ECDSA 校验、低 s 等规范检查、nonce 终态、重入保护和安全 token 调用；完整审计与可运行合约不在本文 MVP 范围内。
- **观察存储：** 完整块的原始记录、业务变化、Outbox 和 checkpoint 在同库事务内提交；持久化块哈希与连续水位，不能只记录见过的最大块号。
- **故障策略：** 读不到可靠链状态时暂停新签发或降低额度，继续保留不明义务。回报、取消、确认与风险核销有独立容量，不让新增询价耗尽恢复通道。

## 第七部分：工程实践——一个简洁 MVP

### 7.1 目标与范围

只验证**同一规范链内，固定报价的 fill/cancel 竞争、严格期限和双腿回滚**。输入已经过正确 EIP-712 验证，报价已获预占；模型使用原子整数，操作按区块执行顺序串行。

不实现真实签名、Go 工程、RPC 广播、链重组、数据库恢复、风险释放或通知交付；`ATOMIC` 明确表示教学执行器的本地回滚边界，不代表数据库与链共同事务。

### 7.2 核心伪代码

```text
q = verified Q1                  # 固定已验签载荷，deadline = t0 + 20
state[(M,73)] = Unused
balances = { A.USDC: 5000000000, A.WETH: 0,
             M.USDC: 0, M.WETH: 10000000000000000000 }
allowances = { A.USDC_to_S: 5000000000,
               M.WETH_to_S: 10000000000000000000 }

apply(action, caller, blockTime):
  ATOMIC:                         # 失败回滚当前这次调用的全部状态变化
    require q.maker == M and q.quoteNonce == 73
    if action == Cancel:
      require caller == M and state[(M,73)] == Unused
      state[(M,73)] = Cancelled
      return Cancelled
    require action == Fill and caller == q.taker == A
    require q.tokens == (WETH, USDC)
    require q.amounts == (1000000000000000000, 3000000000)
    require blockTime < q.deadline
    require state[(M,73)] == Unused
    state[(M,73)] = Filled         # 先消费资格；后续失败仍整体回滚
    require balances[A.USDC] >= q.takerAmount
    require allowances[A.USDC_to_S] >= q.takerAmount
    balances[A.USDC] -= q.takerAmount
    balances[M.USDC] += q.takerAmount
    allowances[A.USDC_to_S] -= q.takerAmount
    require balances[M.WETH] >= q.makerAmount
    require allowances[M.WETH_to_S] >= q.makerAmount
    balances[M.WETH] -= q.makerAmount
    balances[A.WETH] += q.makerAmount
    allowances[M.WETH_to_S] -= q.makerAmount
    emit Filled(Q1, M, A, 73, q.amounts)
    return Filled
```

生产中的安全 token 调用必须处理失败和返回 false；这里直接展开受信任普通 token 的余额与 allowance 变化，以便看见回滚覆盖的实际字段，不用一个“安全交换()”隐藏关键动作。

### 7.3 输入与预期结果

以下各行从初始状态独立开始；同一行内多个操作才按顺序承接。它们是手工推演，不是工程测试结果。

| 输入 | 预期结果 |
|---|---|
| A 在 `t0+8` fill Q1 | Filled；A=2,000 USDC/1 WETH，M=3,000 USDC/9 WETH，成功事件一条 |
| A fill 成功，再次 fill Q1 | 第二次因 nonce 已 Filled 拒绝；余额不再变化 |
| M 先 cancel，A 后 fill | Cancelled；fill 拒绝，双方代币保持初始值 |
| A 先有效 fill，M 后 cancel | Filled；cancel 拒绝，不能回滚已成功交换 |
| A 在 `t0+20` fill | 到期拒绝；链上仍可为 Unused，余额不变 |
| 独立变体：M 的 WETH allowance 改为 0 后 A fill | 第二条资产腿校验失败；第一腿 USDC、nonce 与成功事件一起回滚；A 仍可能支付 Gas |
| B 用同一签名调用 fill | 因 caller 不是 A 拒绝，不发生交换 |

## 资料依据与证据边界

- [EIP-712：Typed structured data hashing and signing](https://eips.ethereum.org/EIPS/eip-712)：规定结构化编码与域分离，标准本身不提供重放保护；本教学模型主动选用 chainId 和 verifyingContract 等字段。
- [EIP-20：Token Standard](https://eips.ethereum.org/EIPS/eip-20)：授权与 transferFrom 接口；调用方必须处理返回 false，不能把未抛异常等同于成功。
- [Ethereum JSON-RPC](https://ethereum.org/en/developers/docs/apis/json-rpc/)：区块标签、receipt 的执行结果和块哈希；`status=1` 与 `finalized` 是不同证据。
- [交易业务全景](../../00-交易业务全景/README.md)：约束产品机制、执行、资产控制及证据分层，不据招聘材料推断目标公司采用本方案。

本文是可推演的教学设计，不是某个现有 RFQ 协议的逐行说明，也不是用户真实项目经历。静态文档检查、整数算式复核不等同于合约审计、并发故障验证、链上实验或性能测量。
