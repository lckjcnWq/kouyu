# 大问题 9：请求超时、重复点击或广播结果未知时，怎样重试而不重复交易？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
| --- | --- | --- |
| requestKey / 请求幂等 | 给一次 API 操作稳定编号，重试复用原处理结果。 | 按用户和操作限定作用域；同键同语义复用，同键不同语义冲突，缓存过期不能丢活跃映射。 |
| intentId / quote digest | 用户逻辑交换意图的编号，与完整签名内容的摘要。 | 意图串联执行，摘要固定条件；保留 intentId 却换新报价 nonce，仍可能产生两份独立权利。 |
| quoteNonce | S 内控制 maker 报价消费的业务序号。 | 重试保留原报价资格；S 按它至多成功 fill 一次，不按 rfqId 全局防重复购买。 |
| txNonce / txHash | A 账户的交易排序号，与具体签名交易的哈希。 | 一条账户 nonce 替换线可有多个哈希；账户 nonce 前进不证明 RFQ 成交。 |
| rawtx / calldata | 已签交易的完整字节，与调用 S 的业务参数。 | 有授权可重播原 rawtx；只有 calldata 不赋予服务代签权，钱包返回的信息也要核验。 |
| BroadcastUnknown | 不知道交易是否已传播或执行。 | 超时、单个节点查无 hash 都不能当未发送证据；保留原意图与风险义务继续取证。 |
| 手续费替换 / 钱包取消 | 用同账户 nonce 竞争原交易位置。 | 加速须保持原业务内容；自转账取消只竞争该账户序号，不撤销 maker 的报价资格。 |
| IncludedSuccess / finality | 目标交换已被某块执行，以及该结果达到既定最终性边界。 | 包含可因重组撤回，未终局不能据此释放预占或触发不可逆消费。 |
| ExpiredUnfilled | 最终证明执行期限已过且此前未成交。 | 要最终链覆盖 deadline、连续扫描及同块状态历史一致，不能靠本地时钟推断。 |
| active / consumed / released | 义务仍在、已由成交核销、已证明无成交而释放。 | 签名可能泄露和广播未知都保持 active；最终成交要与余额同水位对齐，不能再扣一次。 |

## 把整篇文章压缩成一个故事

A 点击接受 Q1 后没收到接口响应，又点了一次。两个实例通过数据库唯一请求键核对相同语义，返回原 intent 和报价摘要，而不是再签新 nonce。同一请求键若带来不同交易内容则明确冲突，不能覆盖原响应。LP 签名器若也超时，继续保留原 1 WETH 预占并查原任务，因为签名可能已交给 A。钱包为账户 nonce 104 签出 H1，广播未知后又加速成 H2；服务保存两个哈希，核对目标、金额和调用数据不变，必要时仅重播获授权的原始交易。账户 nonce 前进也不能宣布成交，胜者可能是其他业务或一次回滚，须查实际交易、回执和 S 的报价状态。若 H1 最终完成原交换，只核销一次义务，不能因 H2 查不到就另签报价。若暂时包含后重组，则继续追踪原资格。到期也要最终链覆盖 deadline 并核清此前无 fill 才能释放；若原报价未成交且已关闭，新报价仍需 A 重新确认。这样重试复用的是同一权利和可恢复证据，不是让相同 intentId 包装出两份可同时成交的授权，重复尝试的 Gas 成本也不会被抹掉。

**流程位置与核心机制：** 用户请求 → 固定报价与逻辑交换意图 → A 钱包签发交易 → 广播、替换与未知结果查询 → 旧权利闭合。本题重点区分请求、报价、意图、交易尝试和 nonce，说明重试复用什么、什么时候禁止创建新权利；链观察与重组详见第 10 题，可靠通知与恢复详见第 11 题。

**必要前提：** 公共资产、签名、合约规则和余额案例沿用[专题总览](README.md)，本题只强调三项边界：

- 始终重试同一 Q1：`rfqId=R1、quoteNonce=73、deadline=t0+20`，固定 digest 不能因超时换金额、期限或 nonce。同 R1 的不同 quoteNonce 仍是独立权利，S 不按 rfqId 全局防重。
- A 自己的钱包签发交易，服务只提供 calldata、记录钱包实际给出的 attempt；A 的 txNonce 独立于 quoteNonce，不支持服务代签、代发新交易。同一 quote 最多成功 fill 一次，但重复交易可能消耗 gas。
- LP 内部先预占 `1 WETH`、固定 payload 后签发。签名不锁资；签名可能泄露或广播结果未知时继续占风险，只有最终链证据才能闭合原权利。

```text
用户请求键 + 固定 quote digest
    ↓ 本地持久化逻辑 intent，重复键校验相同语义
返回同一份 quote / fill calldata
    ↓ 由 A 钱包决定签名、发送
记录 wallet attempt：rawtx/hash/from/txNonce（以钱包实际提供为准）
    ├─ 广播超时 / hash 查不到 → Unknown，查询或重播原签名交易
    ├─ 加速 → 同 sender、同 txNonce、同业务 calldata 的手续费替换
    └─ 链上观察 → 暂态包含 → 按链政策确认最终结果
          ↓
最终 Filled / 最终 Cancelled / 最终证明未成交且过期
    ↓ 才闭合原权利；新报价必须另有用户同意
```

## 第1层：重试之前，先说明究竟是哪一种身份不能变

**面试官：** 请求超时、重复点击或广播结果未知时，怎样重试而不重复交易？

**面试者：** 我不会把“重试”统一实现为再签一份报价或再发一笔新交易，而是先区分五类身份。用户请求键识别一次 API 操作；`intentId` 表示一次逻辑交换意图，并绑定用户请求键与确定的 quote digest；quote digest 固定 EIP-712 域和签名字段；`(chainId,S,M,quoteNonce)` 标识合约可消费的一次业务权利；钱包交易则由 `from、txNonce、txHash` 描述一次链上尝试。

其中 `quoteNonce=73` 是 M 的报价业务唯一号，不是 A 的钱包交易 nonce。一个 intent 可以有多个交易尝试；A 的一条 `(chainId,A,txNonce)` 替换线上，也可能存在多个 txHash。不能用一个 txHash 当作整个业务身份，更不能拿 `intentId` 充当合约防重机制。

重复 API 请求返回原意图和原报价；未知广播优先查询、必要时重播原签名交易。即使 A 用不同交易 nonce 多次提交同一 quote，S 仍最多成功 fill 一次，因为 `(M,73)` 的检查和置位与代币转移在同一个 EVM 事务内。但失败交易仍可能消耗 gas，所以“最多成交一次”不等于“重试没有成本”。链下 `Selected/Accepted` 只说明选择或受理，不说明已经成交。

## 第2层：同一请求同时进入两个实例，靠什么真正复用原意图

**面试官：** 你说重复请求返回原意图。如果两个实例同时收到同一请求键，或者同键却换了价格，怎样保证不是各自创建一份？

**面试者：** 我会给请求键明确作用域，例如 `(A,操作类型,requestKey)`，并由数据库唯一约束裁决，而不是依赖进程锁或 Redis 的短期缓存。请求行保存标准化语义载荷及其哈希、`intentId`、quote digest、处理阶段和可恢复响应引用。语义至少包含 chainId、S、A、报价身份及 digest；金额使用整数，不能因为 JSON 字段顺序或十进制展示不同误判，也不能只比较一个不可信的客户端 quoteId。

同一事务内创建请求记录和对应 intent，或读到既有记录后比对载荷。相同键、相同语义返回既有状态；相同键、不同语义返回明确冲突，不覆盖原记录。两个实例并发插入时只有一个成功，另一个在唯一键冲突后读取已提交记录。若响应尚未生成，返回“处理中”和原查询标识，而不是另建意图。

对于本题的一次逻辑 swap，还应约束同一 A、同一 quote digest 不被不同请求键伪装成两次独立接受，允许新请求键关联回原 intent。请求缓存可以加速查询，却不能在 TTL 到期后抹掉活跃权利与未知交易的持久映射。用户需要再次交易时必须显式创建新意图，不把“缓存没了”解释成允许再交易。

## 第3层：数据库能防重复请求，却管不到签名已经发出去的窗口

**面试官：** 请求和 intent 都落库了，但签名服务已生成报价，接口返回前崩溃；本地不知道用户是否拿到签名，这时怎样处理？

**面试者：** 签发前先在 LP 风险服务的本地事务内预占 `1 WETH`，确定 quoteNonce 73、deadline 和完整 payload，并持久化签发任务。共享 M 的 WETH 预算在同一受控边界内仲裁，不能两个实例都读取 10 WETH 后各自无约束签发。签发任务只能处理已提交的固定 payload，不得在重试时重新取当前价格、延长 deadline 或分配新 nonce。

签名生成、网络交付和数据库提交无法组成一个原子事务。实际签名结果已持久化时，重试直接返回同一份 quote 和签名；如果签名端已处理但本地结果未知，就查询原签发任务，保持原 payload 和风险占用，不启动一轮“换 nonce 再签”。签名端应能按任务身份找回原结果；找不回时宁可阻塞恢复，也不把未知签发当作从未发生。

只要签名可能已经暴露，原权利就可能绕过本服务直接被 A 提交。数据库写个 `Failed`、删除 intent 或让请求键过期，都不能撤销它。这里保留的是 LP 内部风险预占，不是把 M 的链上 WETH 锁进平台；M 仍可转走资产或改变 allowance，所以预占也不构成履约保证。

## 第4层：报价身份固定以后，钱包与广播之间怎样记录尝试

**面试官：** 你不重新签报价，那 A 钱包发送 fill 时超时怎么办？服务能否自行补发，怎样知道补的是原交易？

**面试者：** 服务只提供固定 S、quote 和签名对应的 fill calldata，并记录 A 钱包实际给出的 attempt；A 的私钥始终在钱包，不在报价服务。钱包能在发送前提供 rawtx 时，可先持久记录 rawtx、计算出的 hash、恢复出的 from、chainId、txNonce、to、value 和业务 calldata，再由钱包广播，或在用户授权范围内由服务重播这份已签名原交易。重播不需要也不赋予服务签名权。

若钱包先广播后回调，服务可能只拿到 hash，甚至在回调前崩溃。此时必须承认记录不完整，以 intent、钱包返回信息和链上补查恢复；不能编出一份 rawtx，也不能宣称数据库必然早于实际广播。对钱包提交的 hash 和 rawtx 要验证匹配，并核对实际 sender 为 A、目标为 S、业务内容对应原 digest，不能相信浏览器传来的标签。

广播 timeout 只把该 attempt 记为 `BroadcastUnknown`。节点未返回成功、某个 RPC 查不到 hash、钱包页面显示发送失败，都不是交易未执行的证据。已有 rawtx 可以按原字节重播；没有 rawtx 时请求钱包继续原尝试或补交信息，同时持续链观察，不自行选择一个新钱包 nonce 再构造交易。

## 第5层：钱包“加速”产生新 hash，怎样不把替换当成第二笔业务

**面试官：** 你记录了原 rawtx，但钱包加速后 hash 变了。怎样判断这是原尝试的手续费替换，还是用户换了一笔交易？

**面试者：** 把 `(chainId,from,txNonce)` 作为替换线身份，并保留线上每一个候选 hash，而不是把旧 hash 覆盖掉。例如 A 的 `txNonce=104` 对应 H1、H2，二者 sender 相同、nonce 相同，均调用 S 对同一 quote 做 fill，只调整满足钱包和节点规则的手续费字段，就可标记为同业务加速候选。`104` 与报价 nonce `73` 没有相等关系。

安全的手续费替换应保留目标、value、业务 calldata 等执行语义，不能借“加速”悄悄换收款方、金额或报价。服务拿到 rawtx 就解析核验；只拿到 hash 时，候选语义先标为待核实，查回完整交易后再归类。网络接受 H2 并不证明 H1 从所有节点消失，两个 hash 都要保留到规范链胜者确定。

钱包若把 calldata 改成其他业务，或者同 nonce 发一笔自转账“取消交易”，要显式记录为不同语义的 attempt，并说明它竞争的只是 A 的这个交易 nonce，不是链上取消 `(M,73)`。即使它获胜，quote 仍可能被 A 用另一个钱包 nonce 提交；客户端取消交易也不能替代 M 调用 S.cancel。

## 第6层：看到 nonce 前进，为什么仍不能宣布 RFQ 已完成

**面试官：** 既然同 nonce 最多一个规范链胜者，查询到 A 的链上 nonce 已超过 104，能否直接把 H1/H2 对应的 RFQ 标成成功？

**面试者：** 不能。A 可以同时发送其他业务，nonce 前进只说明较早 nonce 已被某些规范交易消费，不说明消费它的交易调用了 S，更不说明 fill 成功。pending nonce 还可能只是节点交易池视图。即便某个钱包报告“已替换”，我也要找到实际规范链胜者，而不是把这个标签当成交证明。

补查应围绕候选 hash、A 的目标 nonce 和连续块交易进行，必要时向钱包补充获取替换 hash；若 RPC 不提供按 sender/nonce 的直接查询，就通过受信索引或区块扫描恢复，不能假定标准 RPC 一定有这个接口。对胜者核对 from、nonce、to、input、receipt 的 status 与 blockHash，再核对 S 的 `(M,73)` 状态和对应事件，且证据必须处于同一规范链视图。

若胜者是另一笔业务，原替换线已失去执行机会，但 quote 可能仍是 Unused。若胜者调用 fill 却回滚，只能说该 attempt 失败；S 的状态和两次转账均回滚，quote 可能仍可执行。A 愿意再次提交时，可以在同一 intent 下显式新增钱包 attempt，仍用原 quote；这不是生成新报价，更不是服务未经授权替 A 发交易。

## 第7层：找到了成功回执，哪些动作仍然不能做

**面试官：** 现在确实查到 S 的成功 fill 回执和 Filled 事件。是否可以结束 Unknown、释放占用，并让用户换一个新报价继续重试？

**面试者：** 可以结束“没有任何包含证据”的状态，但不能直接跨到永久终态。记录包含该交易的 blockNumber、blockHash、txHash、logIndex，核验它仍属于规范链，再把 intent 投影为 `IncludedSuccess`，同时保存观察版本。回执成功还必须对应预期 quote；一笔无关的 status=1 交易不是本 RFQ 的成功。

在终局之前，区块可能被重组替换。页面可展示“已包含、等待最终确认”，但不能据此释放风险后再签发新的同目的权利，或触发不可逆的下游消费。保守方案是在最终证明形成前继续占用 1 WETH，暂态余额另存，避免把最新余额和旧 reserve 混算。

如果原包含被撤回，intent 回到仍未最终确定的状态，重查替换线、quote 状态和当前规范链时间；它可能重新进入交易池、在另一块被包含，也可能被 cancel 或到期阻断。终局政策按链配置，例如验证以太坊主网 `finalized` 标记及对应区块祖先关系，不把 N 个确认或本地等了多久说成绝对不可逆；第 10 题专门展开这套观察机制。

## 第8层：报价已经到期，怎样证明原来没有成交

**面试官：** 你要求等最终证明，但 deadline 只有 20 秒。当前时间已经超过 deadline，原 hash 又查不到，为什么不能释放 1 WETH？

**面试者：** 因为 deadline 关闭的是未来执行窗口，不抹掉过去可能成功的 fill。`block.timestamp<deadline` 是合约执行条件；本机时间超过 `t0+20`，甚至最新头的时间已过期，都不能证明 `t0+8` 没有成功成交，也不能证明当前最新分支已经最终确定。

释放至少要拿到一个按链政策认可的 finalized 规范链边界 F，其区块时间满足 `F.timestamp>=deadline`，并使连续扫描覆盖到 F；在 F 的同一块哈希视图核验 quote 状态和完整相关历史。若仍为 Unused 且无成功 fill，可以推导 `ExpiredUnfilled`：过去未执行，未来受 deadline 阻断。若为 Filled，就按已成交收束，不能走过期释放；若最终 Cancelled，也可按取消闭合，不必继续等到期。状态、历史和扫描边界矛盾时暂停，不挑一个方便释放的来源。

不能查到历史状态、扫描有缺块、供应商 finalized 视图不一致时，保留占用并记录待恢复义务。最终未成交才把 reserve 从 active 变为 released。最终成交则在一致的资产投影边界把 M 的 confirmed WETH 从 10 对齐为 9，reserve 从 active 1 变为 consumed；不是先当失败释放，再把同一成交扣一次。

## 第9层：原权利闭合之前，为什么同一个 intentId 挡不住重新报价的双成交

**面试官：** 保留占用会影响体验。能否保持 intentId 不变，改成新 quoteNonce、延长 deadline，给用户“重试一次”？

**面试者：** 不能把它包装成无风险重试。新 quoteNonce 对 S 来说就是一份新的独立权利；除非合约本来实现了跨报价互斥，而本题没有，链下相同 intentId 不会让 S 拒绝旧 quote。即使两份报价都带同一个 `rfqId=R1`，S 也没有按 rfqId 的全局消费屏障；旧 quoteNonce 73 与新 nonce 74 可能分别成功，用户就会做两笔交易。

正确顺序是先证明旧权利最终不可执行，并排除它已经执行：例如最终 Cancelled 且历史无 fill，或覆盖 deadline 的 finalized 前缀证明 ExpiredUnfilled。M 发出 cancel 但尚未最终确定不够，因为 fill 可能在它前面获胜。若旧 quote 最终 Filled，原交换已完成，不能再以“补原单”的名义生成新权利；用户若还要买 1 WETH，那是另一笔明确同意的业务。

即使旧权利最终未成交，新报价的价格、金额、期限或 nonce 也形成了新 digest，必须让 A 重新同意并由钱包签发相应交易。记录新 intent 或明确的新意图版本及前驱闭合证据，保留关联用于解释，但不复用旧幂等键覆盖旧响应。代价是等待和重新确认；收益是不会把用户本来只想完成一次的请求扩成两份可同时执行的授权。

## 第10层：进程重启以后，怎样继续原义务而不是“重新执行一遍”

**面试官：** 旧权利不能随便重建，那服务崩溃重启后，面对请求缓存丢失、钱包 nonce 已变和多个未知 hash，具体从哪里恢复？

**面试者：** 恢复入口是数据库中的未闭合 intent、固定 quote digest、签发任务与风险预占、请求键映射和全部 wallet attempts，而不是缓存或进程内重试队列。先核对 quoteNonce 的分配与使用记录，保证已经分配或可能签出的 73 不会被重新分配；再核对规范链与链观察检查点，补查每条钱包 nonce 替换线的实际胜者及 S 的状态和历史。

恢复动作分开处理：已持久化的报价响应可原样重发；有授权且保留 rawtx 的原交易可重播；签名外发不确定继续保留风险并查询原任务；钱包交易外发不确定继续取证。不同实例可以用数据库版本或租约避免重复调度，但租约失效不能撤销已发出的签名和 rawtx，因此合约业务 nonce、同 nonce 替换线和最终链证据仍是最后边界。没有 A 的再次授权，服务不会“恢复性”创建一个新钱包交易。

恢复是否完成，要看每个意图是否有可解释的未决原因或最终证据，每个 active reserve 是否有对应权利，每个 attempt 是否保留语义与替换关系。依赖仍不可用时允许保持 Unknown 和继续占用，不允许以超时阈值把未知改成失败。这样优先保证不重复成交和不错误释放，而不是用一次自动重签换取表面的成功率。

## 本题收束

- **讲透的机制：** 请求键负责 API 去重，quote digest 固定业务内容，intent 串联一次用户意图，quoteNonce 限制合约权利消费，钱包 txNonce 与 txHash 描述执行尝试。它们不能互换；数据库事务、钱包签发与链执行也不构成一个全局事务。
- **最容易答错的边界：** 广播 timeout 或查不到 hash 不等于没执行；钱包 nonce 前进不等于 RFQ 成功；同一 quote 最多 fill 一次不等于不会重复付 gas；到期不等于过去没有 fill；新 nonce 的报价不是原请求的安全重发。签名可能泄露时必须继续占风险。
- **一个具体检验（手工推演，非已运行测试）：** A 对 nonce 104 签出 H1，广播响应丢失，重复点击复用原 requestKey、intent 和 quoteNonce 73；钱包再以同 nonce、同 calldata、提高 fee 签出 H2。假设规范链在 `t0+8` 包含 H1 且成功，即使当前 RPC 查不到 H2，也应最终只认一次 Filled：A 为 `2000 USDC/1 WETH`，M 为 `3000 USDC/9 WETH`，reserve 只 consumed 一次。过程中不得因 H2 消失、请求超时或 deadline 已过而创建 nonce 74 的报价；若把规范链胜者改成 A 的其他业务，则不得宣布 RFQ 成交，而要继续核验 73 是否可执行。上述时点是案例条件，不是主网确认或终局时长保证。
