# 大问题 11：履约结果怎样可靠交付，服务崩溃后又怎样恢复未完成义务？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
| --- | --- | --- |
| 履约终局 / 交付义务 | 链上交换已有最终结论，与系统还欠谁一份结果。 | 通知失败不把成交变回未成交，更不允许补扣款或重新 fill；必要消费者各自追踪。 |
| 完整块事务 / checkpoint | 将一块的观察、投影、通知待办和扫描位置一起保存。 | 提交前崩溃整块重读，进度不能先走；最终性升级另有本地事务，不与链共同提交。 |
| outbox / 至少一次 | 先持久记下欠发消息，再允许失败重发。 | 同一 eventId、同一不可变内容反复派送；租约只管调度，不能保证消费者只收到一次。 |
| inbox / 消费事务 | 把收到过的消息与本地业务效果一起提交。 | 去重记录、payloadHash、版本判断和投影更新不能拆开；否则先去重后崩溃会漏效果。 |
| eventId / payloadHash | 稳定消息身份与其内容摘要。 | 同 ID 异内容要隔离，不当普通重复；摘要只核一致性，不替代生产者认证。 |
| ACK | 接收方按协议确认到了哪个持久处理阶段。 | 内存入队、持久接收、业务已应用不是同一边界；ACK 丢失可重发，不能先标完成。 |
| revision / watermark | 领域更新版本与依据的链处理范围。 | 不随重组回退版本，带块哈希和世代防乱序；依赖增量的消费者有缺口就补取，不能盲跳。 |
| active → consumed / released | 仍占风险、最终成交核销，或最终未成交释放。 | 风险侧用同一事务对齐余额和预占；消息已发出不代表预算可重新开放。 |
| epoch / 恢复保护 | 任务所属代次，以及证据未齐时暂停新增风险。 | 旧实例不能用过期代次提交，但已暴露签名不失效；恢复继续原义务，不新造钱包交易。 |
| 对账 / 死信 / 去重墓碑 | 补查事实缺口、长期交付失败和归档后的防重复凭据。 | 对账不重做交换，死信不等于完成；未闭合义务不能 TTL 删除，清理须覆盖重放边界。 |

## 把整篇文章压缩成一个故事

A 与 M 已在 S 完成交换，扫描器却在记录结果前崩溃。重启后它先验证检查点哈希，再连续重扫，把原始观察、查询投影、版本、outbox 和新进度作为整块事务提交；最终性核验后另建最终结果交付义务。派送器把事件 E 发给 LP 风险服务，接收方在同一事务保存 inbox、核对摘要和版本，将余额 10 对齐为 9、预占从 active 改为 consumed。ACK 在网络丢了，E 再来只返回既有结果，不再扣库存；同 ID 异内容则隔离。迟到的低版本暂态消息不能覆盖最终状态，增量缺口要补取，其他外部副作用继续用下游 outbox。客户回调长期不可用只留下独立欠交付项，进死信也不算成功，更不能再发 fill 补通知。多实例按代次和唯一约束恢复原报价、交易尝试及未发消息，对账只补事实与投影缺口。查询可如实显示最终成交，但风险未同水位对齐前预算仍冻结；义务未结清不能 TTL 删除，系统宁可明确欠着，也不以重做交换伪造完成。

**流程位置与核心机制：** 规范链事实 → 本地履约投影与交付义务 → outbox 派送 → 消费者 inbox 与状态提交 → 风险及通知义务收束 → 崩溃扫描和对账恢复。本题重点是“事实已发生后，谁还欠谁什么、在哪里持久保存、重复和故障后怎样继续”，不重新展开请求身份设计或共识原理；相关边界分别见第 9、10 题。

**必要前提：** 公共资产、签名、合约规则和余额案例沿用[专题总览](README.md)，本题只强调三项边界：

- 非托管交换已由 `chainId=1` 的固定 S 原子执行；平台只恢复事实与后续义务，不持有 A 私钥、不因通知失败再执行扣款。恢复围绕固定 Q1、quoteNonce 73 和原钱包 attempts，不重签新权利。
- 使用至少一次交付，不承诺端到端 exactly-once。暂态观察可撤回，最终结果按第 10 题的链政策核验；不可逆消费者不得消费未最终事件。
- LP 内部 `active reserve=1 WETH` 在未知结果下保留；最终成交时将 confirmed WETH `10→9` 与 reserve `active→consumed` 在风险侧同一事务对齐，或保持保守冻结待对账，不能重复扣减或提前释放。

```text
链上 fill 已发生（不受本地 DB 或消息发送成败控制）
    ↓ 连续块扫描、校验规范链与完整性
本地同一完整块事务
    ├─ 原始日志与规范性证据
    ├─ quote / intent 暂态投影与 revision
    ├─ 结果 outbox
    └─ checkpoint(blockNumber,hash)
    ↓ finality 核验后，以本地事务发布最终结果与后续义务
outbox 至少一次派送，发送不确定保留原 eventId
    ↓
消费者同一 DB 事务：inbox + payloadHash + projection/state
    ↓ 提交后才 ACK；若再有外部副作用，另建下游 outbox
崩溃恢复：检查点重扫 + 未闭合 intent / nonce / attempt + 未交付义务
```

## 第1层：链上已经成功，服务究竟还需要可靠交付什么

**面试官：** 履约结果怎样可靠交付，服务崩溃后又怎样恢复未完成义务？

**面试者：** 先把三种完成分开：S 已在规范链执行交换、本地已在可信边界记录结果、必要消费者已持久处理结果。交易成功不会因为服务停机而等待消息队列；反过来发送一条“成功”消息，也不会让尚未执行的 fill 发生。我的目标是链上确定结果不漏入本地，本地确定结果不丢交付义务，重复交付不重复改变消费者状态。

本题必要消费者可以是 LP 风险投影、履约查询服务或客户回报接收端。它们处理的是外部钱包资产和履约事实，不是再替 A 扣一次 USDC，或者替 M 再转一次 WETH。对案例中的成功交换，真正资产变化只有 S 的一次双向 transferFrom；通知失败不能触发一笔“补扣款”。

设计上使用可恢复扫描、本地事务 outbox、消费者事务 inbox 与持久版本。这里保证至少一次传递，并在有明确身份和本地事务的范围内让效果幂等，不宣称消息、数据库和链组成 exactly-once。崩溃之后继续的是数据库中尚未闭合的义务，而不是把整笔业务从签发报价开始重跑。

## 第2层：怎样防止“结果已记录，却没有消息需要发送”

**面试官：** 你说结果不丢交付义务。如果已经更新 intent 为成功，写 outbox 前崩溃，会不会永远没人收到？

**面试者：** 不能把这两次写入拆开。扫描器准备好完整区块材料后，在同一数据库事务内写入原始链观察、更新 quote/intent 投影、持久分配 revision、写出结果 outbox，并推进 `checkpoint(blockNumber,hash)`。失败则整个区块不提交，重启从旧检查点重读；成功则即便派送进程从未启动，也能从 outbox 找到义务。检查点不能先于日志和消息推进。

观察身份使用 `(chainId,blockHash,txHash,logIndex)`；领域结果身份使用 `(chainId,S,M,quoteNonce,kind)`。同一领域结果的暂态包含、撤回和 finalized 是不同状态变更，各有持久 eventId 与 revision，不能复用同一 eventId 改写内容。outbox 保存不可变事件体及 payloadHash、领域身份、revision、目标消费者和当前交付状态；重扫相同块不能重新生成另一份同版本义务。

finality 往往晚于最初扫描，因此最终升级也要有自己的本地事务：核验已完整扫描的规范前缀和 finalized 证据后，更新最终投影，写最终事件及风险处理义务，记录采用的边界。事务不能原子包含链上 fill，也不能让写 outbox 代替上链；如果本地事务失败，链上交换仍已发生，只能靠重扫继续恢复。

## 第3层：outbox 已提交，为什么派送成功也不能只发一次

**面试官：** outbox 可以补上提交后未发送的消息，但发送后收到 ACK 前崩溃，怎样判断要不要再发？

**面试者：** 我不尝试仅凭本地标记判断网络另一端是否处理过，而是接受至少一次派送。派送器以短租约或条件更新认领待投递记录，事务提交后再调用消费者；发送前不把它标成已交付。消费者给出符合协议的持久处理 ACK 后，派送器才把该目标标成 acknowledged。网络调用放在数据库事务外，避免长期持锁却依旧无法获得跨网络原子性。

发送前崩溃，租约过期后继续；发送成功但 ACK 丢失，继续发送同一 eventId、同一 payloadHash；ACK 已到但本地标记未提交，也同样可能重发。事件体不能每次增加新的时间戳导致哈希变化，重试次数、传输时间放在独立传输元数据里。多目标交付要分别追踪状态，一个回报服务 ACK 不代表 LP 风险消费者也处理了。

使用有上限的并发、退避和抖动控制重试，租约过期可能造成并发重复发送，所以租约是调度手段，不是消费者防重保证。若消费者协议中的 200 只表示写入其内存队列，就不能把它当成业务已持久处理；需约定持久入站或处理完成的具体 ACK 边界，并在查询和监控里区分传输受理与效果完成。

## 第4层：消费者怎样保证“已去重”与“效果已完成”不可分离

**面试官：** ACK 丢失会重复发送。消费者先记一个“eventId 已收到”，然后再改投影，能否防止重复？

**面试者：** 不能，先去重后崩溃会让重试跳过尚未发生的效果。消费者必须在同一数据库事务内插入 inbox `(producer,eventId,payloadHash)`，核对版本并更新 projection/state，最后提交；只有提交后才 ACK。唯一约束负责并发裁决，不是先查缓存再写。事务回滚时 inbox 和效果都不存在，重试能够完整重做；事务已提交时重复消息读取既有 inbox，确认同哈希后返回原处理结论，不再重复应用。

相同 eventId 却不同 payloadHash 必须隔离、报警并核对生产者，不得覆盖既有内容，也不能把它当普通重复 ACK 掩盖。哈希基于约定的不可变规范化事件体；生产者身份和内容真实性还需要鉴权与签名等协议保障，payloadHash 只解决一致性核对，不替代认证。

如果效果还包括发送邮件、调用另一个 HTTP 服务或写另一个数据库，这些动作不属于 inbox 事务。应在当前事务内再写下游 outbox，由下游按自身幂等协议处理。外部接收端若不支持可查询、可去重的业务键，就必须承认存在重复或不确定窗口，不能因本地 inbox 唯一就宣传端到端效果恰好一次。

## 第5层：每个 eventId 只处理一次，为什么旧消息仍可能破坏状态

**面试官：** inbox 已经能去重，但旧分支的 Included 和重组后的撤回本来就是不同 eventId。它们乱序到达，怎样不把撤回覆盖掉？

**面试者：** eventId 防相同消息重复，不防不同消息乱序。消费者要在同一 inbox 事务里持久保存该 quote 已采用的 revision、当前阶段和链处理 watermark。生产者撤回旧观察时分配更高 revision，不能因回到祖先而回退版本号。例如 Included 为 31，撤回为 32，重含为 33；先处理 32 后收到 31，可以记入 inbox 但不覆盖现态。

watermark 不只有高度，还要包含对应块哈希、重组世代和已核验 finality 边界；高度相同不代表同一分支，撤回事件也可能指向更低高度。对完整状态事件，消费者可依据新版本替换可撤回的 UI 投影，但不能让迟到旧事件触发一次新的资金效果。对依赖每个增量或副作用的消费者，revision 缺口必须持久缓冲并请求补发或重建，不能跳过 32 后直接应用 33 的局部增量。

业务处置状态与“已见过消息”也要分开：缺口消息可在事务里记为 pending，不能记成 applied 后再遗忘。若协议 ACK 表示已应用，pending 不能回该 ACK；若表示已持久接收，则另追踪 applied 进度。删除旧 inbox 前必须有可证明覆盖的去重保留边界和持久版本水位，否则历史重放会复活旧状态。不可逆消费者仍只处理最终事件，revision 不能成为随意消费暂态结果的理由。

## 第6层：状态通知没有重复，LP 风险为什么仍可能双扣或多释放

**面试官：** 假设版本和 inbox 都正确了。最终成交消息把 M 的 WETH 改成 9，又把预占释放，如何保证没有一度按 10 去重新签报价，或者把同一成交再扣一次？

**面试者：** 余额投影与风险预占必须使用同一个来源边界。案例初始本地 confirmed WETH 为 10，active reserve 为 1，保守可分配量为 9；最终 fill 进入可信前缀后，应在 LP 风险服务的同一数据库事务内提交该最终事件的 inbox、把余额投影对齐到 9、将 reserve 从 active 变为 consumed，并记录来源块和应用标记。此时该 reserve 不再 active，可分配量仍为 9，不是 8 或 10。

如果采用逐事件减量，确认这笔 fill 尚未包含在已有余额基线中才减 1；如果采用包含该 fill 的块哈希余额快照 9，则不能再减一次。reserve 的 consumed 是解释原预算已经变成真实支出，不是额外扣款；成交不能走“失败释放”路径。只有最终 Cancelled 或覆盖 deadline 的 finalized 规范前缀证明 ExpiredUnfilled，才能把预占改为 released，且要核验状态、历史与连续扫描完整性。

生产者数据库与 LP 风险数据库没有跨库事务。若风险服务暂时不可用，原 reserve 继续 active，不能因消息已发出或用户页面已成功就释放；风险侧完成本地原子对齐后才让相应新预算可用。若余额镜像由另一路先更新，必须通过快照覆盖关系与 reserve 映射协调，协调不了就保守冻结相关预算。平台不能为“补账”新增一次 M 钱包扣款，也不能把消费者 ACK 当成链上资产发生变化的时刻。

## 第7层：服务在链上执行后立即崩溃，恢复应从哪一份事实开始

**面试官：** 你保证了风险服务自己的事务，但更早的扫描服务可能在 fill 已执行、本地还没记结果时崩溃。重启后具体先查什么？

**面试者：** 先进入恢复保护状态，不能只加载数据库中的 `Pending` 就按未成交重新报价。恢复同时核对四类持久材料：未闭合 intent 与固定 quote、quoteNonce 分配和使用记录及 active reserve、钱包 attempt/替换线及外发不确定记录、扫描 checkpoint 与未交付 outbox。数据库认为未完成，不代表链上未执行。

先验证 checkpoint 的块哈希仍在当前规范链上；如不匹配，按共同祖先恢复暂态且保留单调 revision，若越过已承诺边界则暂停隔离。随后连续扫描补齐检查点之后的完整块。链已 fill、数据库事务未提交时，重扫生成缺失的投影与 outbox；事务已经提交但进程没收到提交结果时，依靠原始观察唯一约束和版本记录识别已处理，不再次减量或另造 eventId。

同时补查钱包尝试的实际规范交易和 S 状态、历史，防止只盯住一个已被替换或漏记的 hash。恢复以后每个意图必须有最终证据，或者持久的未决原因和下一步任务。没有查清的项继续占风险，不能把“服务启动成功”当成恢复完成。恢复顺序服务于可信边界，不要求所有 intent 都等全库扫描完才查询，但不能在其所依赖边界未验证时放开该项新增风险。

## 第8层：两个恢复实例同时工作，会不会恢复出新的交易

**面试官：** 恢复期间可能有两个实例接管，旧实例也可能没死。怎样让它们只继续原义务，而不是各发一笔新交易？

**面试者：** 用数据库唯一键、状态版本和带 epoch 的任务认领控制本地推进：扫描者提交必须符合预期检查点，finality 提升必须符合当前投影版本，outbox 派送按目标认领，nonce 分配必须持久且不可复用。旧实例不能用过期 epoch 提交新状态，但过期租约不能撤销已经交给钱包的 calldata、已经暴露的报价签名或已广播 rawtx。

因此恢复动作还要按语义限制。报价通知重发同一签名和 payload；交易重播只能是钱包实际提供且授权重播的原 rawtx；手续费替换由 A 钱包决定，并核验同 sender、同 txNonce、同业务 calldata。服务不持有 A 私钥，不能因抢占恢复任务就新造一笔钱包交易。钱包只返回 hash 或外发结果不确定时，持久查询义务即可，不把 nonce 查询结果当作代签授权。

A 的交易 nonce 前进可能是其他业务，必须查实际胜者和 S state/event。签发端外部调用不确定也保留原签发任务、payload 和 reserve，不能换 quoteNonce 补签。epoch 能阻止旧工作者写数据库，不是链上 fencing；已暴露的报价只有合约状态、deadline 与最终规范链证据才能闭合。两个实例即使重复投递原消息，也应由 inbox 收敛，而不是靠“只有一个进程大概在跑”维持正确性。

## 第9层：任务队列都恢复了，为什么仍需要独立对账

**面试官：** 你已经能重扫和认领所有任务。如果某条任务从来没有写入队列，或者历史上发生过半套状态，对账怎样补救而不再制造一次履约？

**面试者：** 任务恢复只覆盖已持久化义务，对账还要检查源事实与派生状态之间的缺口。我会分别核验：连续规范块和原始日志是否覆盖目标前缀；每个最终领域结果是否有对应 intent、风险处置和必要 outbox；每个 active reserve 是否对应仍可执行或结果未知的权利；每个已确认交付是否有接收方按协议可核验的处理证据。nonce 分配记录中可能签出却没有完整响应的项，也不能因为缺一行 intent 就忽略。

发现链上已 fill 而本地缺结果，回到同一规范化应用入口，用领域身份和观察身份补建派生状态，仍受事务和唯一约束保护；不能直接执行一条无来源的余额修正 SQL，更不能再发一次 fill。若最终结果存在而 outbox 缺失，按稳定的结果版本补建唯一交付义务，保留修复来源。消费者状态损坏时，从可信快照及覆盖边界重建，或走带新修复版本的明确协议；原 eventId 已在 inbox 时，简单重发不会神奇修复被破坏的投影。

供应商缺块、finalized 停滞、历史状态不可查或同 ID 异 payload 时，保留阻塞原因并隔离，不选择一个看似一致的余额强行调平。对账是持续发现和修复投影缺口的机制，不替代事前的完整块事务、inbox 事务和合约业务防重。修复已公开最终结果还要遵守第 10 题的异常修正边界，不能拿一个更高 revision 把最终事实随意反转。

## 第10层：消费者长期故障时，什么才算完成，什么必须继续欠着

**面试官：** 对账能找到欠缺，但消费者一直不可用，或消息进入死信队列，难道这个 RFQ 永远不能结束？怎样区分完成与长期故障？

**面试者：** 不用一个总 `Done` 掩盖所有维度。我会分别持久记录链上履约终局、LP 预算处置、查询投影进度、每个必要消费者的接收和应用进度，以及可选分析通知的状态。链上已经最终 Filled 就可以如实查询这项事实；但 LP 风险未原子对齐时，其预算不能重新开放。客户回调未 ACK 是尚欠交付，不会让已完成交换变回未成交。

重试次数耗尽只是转入待处置或死信，不是义务已履行。保留原 eventId、payloadHash、revision、目标和最近错误，告警并支持按原身份重放。限制每个目标的并发与积压，避免故障消费者拖垮扫描；链扫描持续推进到持久 outbox，必要时因存储压力显式限流新增业务，不静默丢结果。监控未闭合 intent 年龄、最老 outbox、消费者版本缺口、扫描落后和 active reserve 与终局不符等信号，而不是只看队列长度为零。

归档清理也要有边界：未闭合义务不能 TTL 删除；已交付项的 inbox、版本水位和去重墓碑需要覆盖承诺的重放窗口，quoteNonce 分配记录不能因归档被重新使用。若业务决定终止某个通知渠道，必须有明确的义务转移或获授权的豁免记录，而不是改成成功。整个取舍是允许暂时“已成交但通知待补、预算待核对”，不允许以吞掉未知或自动重做交易换取表面闭环。

## 本题收束

- **讲透的机制：** 连续扫描把链事实恢复进本地；完整块事务使原始日志、投影、outbox 与 checkpoint 不分家；至少一次派送以稳定 eventId 重试；消费者把 inbox、payloadHash 和 projection/state 放在同一事务；持久 revision/watermark 防止迟到旧事件覆盖。跨数据库、链与外部 HTTP 没有被这些局部事务变成全局原子操作。
- **最容易答错的边界：** 先记 inbox 后改状态会丢效果；先标已发送后调用网络会丢消息；ACK 丢失可能导致重复；死信不等于完成；暂态结果不能不可逆消费；LP 的 confirmed balance 与 reserve 必须同口径对齐，不能把外部钱包资产再当平台账本扣一次。对账补缺，不替代事前约束。
- **一个具体检验（手工推演，非已运行测试）：** S 已在 `t0+8` 成功 fill，扫描器在完整块事务提交前崩溃；重启重扫只能生成一份该版本 outbox。最终边界核验后，最终事件 E 到达 LP 风险消费者：在同一事务内提交 inbox(E,hash)、余额 `10→9`、reserve `active 1→consumed`，但 ACK 丢失；生产者重启再发 E。消费者应返回既有结果，不再扣 1、不再改变 reserve。随后即便收到更低 revision 的暂态 Included，也不能覆盖最终状态；若收到 E 的不同 payload，应隔离。最终 A 仍为 `2000 USDC/1 WETH`，M 为 `3000 USDC/9 WETH`，只有一次链上交换，没有“通知失败补扣”。客户回调若仍未成功，就保留独立待交付义务，而不是把 E 删掉或再造一个新报价。
