# 大问题 10：怎样区分交易包含、确认与最终结果，并正确处理链上重组？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
| --- | --- | --- |
| 包含 / 确认 / 最终结果 | 进了具体块、在当前链上继续稳定、达到既定最终性政策。 | 三个阶段不能合成一个成功布尔值；status=1 还须对应 A 调用 S 的目标报价。 |
| 观察身份 / 领域结果身份 | 哪块里的哪条日志，与哪份报价权利发生了什么结果。 | 前者含 blockHash 区分分支，后者按链、S、maker、quoteNonce、结果类型防重复业务计数。 |
| checkpoint / parentHash | 已处理块的位置与哈希，以及下一块指向的父块。 | 启动和续扫都要验连续性，只存高度会把旧分支和新分支拼接。 |
| 完整块事务 | 一块材料齐备后，将观察、投影、通知待办和进度一起提交。 | 失败整块重读，无业务日志也要推进连续性；空响应不自动证明无事件。 |
| 共同祖先 / orphaned | 新旧链共同的最后一个块，以及已失去规范性的旧观察。 | 普通回退只撤销本地暂态应用，再重放新链，不发反向转账补偿。 |
| revision / eventId | 领域状态更新版本，与一条稳定消息的身份。 | 重组可回退内容但版本继续增加；同领域不同阶段不是同一条可变消息。 |
| watermark / 重组世代 | 消息所依据的处理范围及链视图代次。 | 须带哈希和世代，不能仅凭高度或收到顺序判断新旧；版本缺口按消费语义补取。 |
| finalized 边界 F | 按本链政策核验后可据以作最终承诺的区块。 | 核对来源、预期链、祖先关系与扫描覆盖；固定秒数、N 确认或 RPC 多数均不是绝对证明。 |
| ExpiredUnfilled | 期限已最终覆盖且历史未成交的派生结论。 | F 时间达到 deadline、同哈希状态为 Unused 并核清历史才成立；不是 S 自动写入的状态。 |
| consumed / released / fail closed | 成交核销、无成交释放，以及证据冲突时先停。 | 余额和预占同水位；冲突越过已承诺最终边界要隔离并走事故修正，不当普通浅重组。 |

## 把整篇文章压缩成一个故事

扫描器在旧分支看到 A 的 fill 成功，先核对 S、报价事件和状态，发布“已包含”，仍保留预占。它不依赖 WebSocket 恰好送全，而是连续读取区块，把整块观察、暂态投影、outbox 和带哈希检查点一起提交。重启发现同高度哈希变了，就暂停终局发布，找到共同祖先，逆序撤回旧观察、正序重放新分支；回退的是本地事实，不是替 A 发反向转账。新分支再次包含同一报价，只增加观察证据，不多算一笔成交。撤回消息和重新包含消息用更高 revision，迟到旧成功不能把界面改回去。随后核验 finalized 边界 F 的来源、祖先关系和本地扫描覆盖，才发布最终结果。若新链已到截止，仍须排除截止前 fill，不能只看时间生成未成交结论。最终成交在风险侧事务中同水位更新余额并核销预占，通知晚到前保持保守占用。若冲突越过已承诺的最终边界，立即隔离并升级事故处理，不用普通重组回退假装能自动逆转下游已消费的权益。

**流程位置与核心机制：** A 提交 fill → 观察交易与合约执行 → 连续区块投影 → 重组撤回或重新包含 → 按链政策形成履约终局。本题重点是“在什么链视图下知道什么、可以承诺什么”，不把区块包含当作永久业务终态；请求重试身份见第 9 题，结果交付和消费事务见第 11 题。

**必要前提：** 公共资产、签名、合约规则和余额案例沿用[专题总览](README.md)，本题只强调三项边界：

- 观察 `chainId=1`、固定 S 中的 Q1：`(M,quoteNonce=73)`；fill/cancel 由规范链顺序裁决，状态改变与双向 transferFrom 在同一 EVM 事务内共同成功或回滚，链下 Accepted 不算成交。
- `deadline=t0+20`，执行条件为 `block.timestamp<deadline`；Expired 是规范链时间推导，合约仍可为 Unused。到期只关闭未来执行资格，不证明过去未 fill。
- LP 的 `1 WETH` 风险预占在最终证据前保留。主网可按政策使用经核验的 finalized 边界，不把 N 确认或固定秒数当绝对终局；普通重组只撤回暂态，越过已承诺边界要暂停隔离。

```text
钱包广播 / RPC 回执 / WebSocket 提示
    ↓ 只作为定位线索
连续读取规范链区块、交易回执与 S 的日志
    ↓ 校验 parentHash、完整块与执行语义
本地完整块事务：原始观察 + 暂态业务投影 + outbox + checkpoint
    ├─ 头部延伸 → 包含 / 确认进度变化，仍可撤回
    ├─ 重组 → 找共同祖先 → 撤回旧分支 → 重放新分支
    └─ 经校验的 finalized 边界覆盖观察
          ↓
按政策发布最终 Filled / Cancelled / ExpiredUnfilled
    ↓ 对齐风险预占与资产投影，再交付最终结果
```

## 第1层：同一个“成功”，到底可能指哪三个阶段

**面试官：** 怎样区分交易包含、确认与最终结果，并正确处理链上重组？

**面试者：** 我会把执行结果和链稳定程度分开。**包含**是交易出现在某个具体 blockHash 中，有回执和执行结果；**确认**是它仍在当前规范链上，其后已有若干后继块，或满足系统定义的中间政策；**最终结果**则要求承载该结果的区块进入本链配置的 finality 边界，并通过业务与数据完整性核验。这不是一个 `success=true` 能表示的状态。

即使 receipt.status=1，也先确认交易确实由 A 调用 S、执行的是原报价、事件与 `(M,73)` 状态一致。业务成功不是“某笔交易没有回滚”。若 fill 成功，双向代币转移在该链分支内原子发生；若回滚，业务状态和两次转账均不生效，但 A 仍可能支付 gas。

包含和普通确认阶段允许因重组撤回，不能据此触发不可逆资金或权益消费。界面可以展示“已包含、确认中、最终完成”，附证据块与观察版本。以太坊主网可以按政策使用 `finalized` 标记，但必须核验来源与祖先关系；不能说“等 N 个块绝对终局”，也不能承诺某个固定秒数内一定最终完成。

## 第2层：区块可能变，业务身份与观察身份怎样各自稳定

**面试官：** 你把包含绑定到 blockHash。原 fill 在另一块重新包含时，怎样判断这是新观察，还是又成交了一次？

**面试者：** 保存两套身份。链观察身份是 `(chainId,blockHash,txHash,logIndex)`，表示在某块里看到的某一条日志；领域结果身份是 `(chainId,S,M,quoteNonce,kind)`，例如这份 quote 的 Filled 结果。前者区分分叉上的证据，后者防止一次权利因重放或重新包含被计算成多次成交。

同一 txHash 重新包含到不同 blockHash，可能有不同交易位置或 logIndex，所以不能只按 hash 去重后丢掉新证据。每条原始观察保留区块号、父哈希、交易和解码字段、规范性及撤回标记；领域投影保存当前采用的证据、阶段和持久单调递增 revision。原观察可以从 canonical 变为 orphaned，但不能覆盖成“从未见过”。

同一领域 Filled 结果经历暂态包含、撤回、重新包含和 finalized，不是四次成交。对外消息为这些状态变化分配不同 eventId，并携带领域身份和 revision；不能把领域身份直接当成所有阶段共用且内容可变的消息 ID。最终余额只按一次权利消费对齐，不按观察条数累计扣 WETH。

## 第3层：有了这些身份，怎样保证链观察不是漏了半个区块

**面试官：** 身份能去重，但如果 WebSocket 漏掉 Filled 日志，或者一个区块只处理一半就宕机，投影怎么可信？

**面试者：** WebSocket 只用于唤醒扫描，正确性依赖连续区块扫描和可核验的检查点 `checkpoint(blockNumber,hash)`。从检查点下一块开始，读取头、必要交易回执及 S 的相关日志，核对父哈希、交易所属块和日志地址；涉及状态查询时也固定在同一 blockHash，不能日志用旧分支、状态用 latest。

网络读取和解码先在数据库事务外准备完整块材料。准备完成后，在一个本地事务内锁定扫描进度并核对预期父检查点，插入该块原始日志、更新暂态业务投影、分配 revision、写出 outbox、推进 checkpoint。无关日志也不能导致漏掉目标事件；无业务日志的块同样要记录连续性。任何一步失败整块不提交，下次从原检查点重读，不允许半块推进。

所谓完整还依赖数据源能力，不能见到一次空日志响应就宣称绝无事件。对范围限制、分页、截断和回执缺失要显式处理；可按块读取回执与日志交叉核对，遇到不同来源冲突则阻塞。若读取期间发生重组，提交的是带哈希的可撤回观察，后续头部校验会触发修正，而不是把这一小段网络窗口冒充全局原子性。

## 第4层：完整块已提交，重启时为什么还要校验检查点哈希

**面试官：** 每块事务已经原子提交。服务重启后直接从 checkpoint.blockNumber+1 扫描，为什么还不够？

**面试者：** 因为数据库事务只能证明“本地完整处理过这个哈希的块”，不能证明停机期间它始终是规范块。启动时先比较保存的检查点哈希与数据源当前在同高度给出的规范块哈希，并验证它属于所采用链视图。只保存高度会漏掉同高度换块，直接往后扫就把旧分支投影和新分支日志拼在一起。

哈希相同时才沿 parentHash 继续；不同时进入寻找共同祖先的重组流程。扫描器持久保存足够的区块头、原始日志、应用记录及回退材料，不只保存最后一个数字。数据库事务在提交时再次检查 checkpoint 和扫描者版本，避免两个恢复实例从同一个父块派生出互相覆盖的进度。

如果本地 checkpoint 正确但供应商暂时落后，不能立即宣布发生重组并删历史；先区分源落后、源分叉和数据损坏。服务可保持只读进度或保护状态，等待一致证据。检查点之后遗漏的块通过重扫补齐；不能仅查询当前 `(M,73)` 为 Filled 就忽略交易、历史证据和未发送结果，因为状态查询本身不恢复完整履约义务。

## 第5层：找到共同祖先以后，怎样撤回旧分支而不再改一次链上余额

**面试官：** 假设检查点确实在旧分支上，已对外报告过包含成功。找到共同祖先以后，具体回退什么、按什么顺序做？

**面试者：** 先暂停受影响报价的终局发布和风险释放，向后比对保存的头与当前规范链，直到共同祖先 C。仅在 C 没有越过已承诺 finality 边界时走普通回退。对 C 之后的旧块按逆序撤销暂态应用：原始日志标为 orphaned，撤销它们对暂态 quote 投影的贡献，恢复未最终闭合的意图，并为曾外发的观察生成撤回通知。

每个回退块也要原子提交：日志规范性、暂态投影、撤回 outbox、checkpoint 一起变化。若多块回退或重放中途宕机，持久恢复阶段记录目标祖先和已完成位置，报价保持保护状态，重启继续而不是把中间结果拿来释放风险。随后从 C 的后继块正序应用新分支，仍按完整块事务提交。

回退的是本地链观察，不是再发一笔反向 transferFrom。旧分支上的转账效力随链重组撤销，服务没有 A 或 M 的私钥，也不应自行创造补偿交易。已发送的暂态消息无法撤回网络字节，必须用更高 revision 的撤回或替代消息纠正；尚未发送的过时 outbox 可以标记 superseded，但最终投影仍要可查询，不能只指望删除消息就让消费者忘掉旧状态。

## 第6层：回退时版本也回退，会不会被迟到的旧成功覆盖

**面试官：** 你恢复了祖先投影，但旧成功通知可能还在网络中。消费者先收到撤回，再收到旧成功，怎样避免又显示已成交？

**面试者：** 业务内容可以回退，消息版本不能随之回退。例如该 quote 在旧块上生成 `revision=12,Included`，撤回生成 `revision=13,PendingAfterReorg`，新块重含生成 `revision=14,Included`。恢复时即使重建了祖先状态，revision 分配器也必须持久保留已使用的最大值，不能恢复成祖先的 11 再发一个新的 12。

每个消息带领域身份、eventId、revision、阶段、来源 blockHash 和链处理 watermark。消费者持久保存该 quote 已采用的 revision；晚到的 12 只能归档或去重，不覆盖 13/14。watermark 需要带哈希和重组世代，不能只比较区块高度，因为同高度的新分支不是旧数据。更高 revision 也不等于更高区块号，撤回本身就可能指向更低的祖先。

依赖逐事件变更的消费者还需要检测版本缺口并补取或重建，不能简单丢掉中间义务。对本题 UI 状态投影可以使用带完整状态的替代事件；任何不可逆消费只接收经政策认可的最终事件。具体 inbox 与本地事务见第 11 题，这里要保证链侧先生成稳定、可追溯的版本，不能把乱序问题全推给前端。

## 第7层：新分支出现 cancel，或者跨过 deadline，谁决定 quote 的结果

**面试官：** 现在旧 fill 被撤回，新分支同时出现 M 的 cancel 和 A 的 fill，甚至块时间已过 deadline。你的投影怎么裁决？

**面试者：** 按新规范链实际区块和交易顺序重放 S 的执行，不按 API 接收时间、钱包点击时间或哪个 RPC 先通知。若有效 fill 先成功，则 `(M,73)=Filled`，后续 cancel 不能再从 Unused 转移；若 cancel 先成功，则状态为 Cancelled，后续 fill 回滚。即便同块发生，也由交易位置和合约状态检查确定唯一胜者，不存在链下服务再投一次票。

fill 还必须满足所在区块 `block.timestamp<deadline`。等于 deadline 就拒绝；先广播或先进入交易池不能保留过期执行资格。若执行回滚，双向转账、Filled 状态及该次调用的日志均回滚，不能把一份失败回执解码为成交。某次 fill 因 allowance 或余额不足回滚，也不自动取消整份 quote，只说明该次尝试失败。

`Expired` 不一定是合约写入的枚举，也不必有一条 Expired 日志。最新块时间跨过 deadline 时，可以显示当前视图下已过期，但要形成最终未成交结果，还必须排除 deadline 之前已经成功 fill。不能用最后一次失败回执替代对 `(M,73)` 和完整历史的检查，也不能让重组前的 cancel 继续阻挡新分支真实成功的 fill。

## 第8层：怎样从“当前视图下过期”推进到可以承诺的最终结果

**面试官：** 你说过期也要排除历史成交。最终边界怎样选、怎样验证，才能把暂态结果提升为最终结果？

**面试者：** 把 finality 作为显式链政策配置，而不是在代码里写死“12 确认”。本题以主网 finalized 标记为例：取得 F 的高度、哈希与时间，验证数据源确实服务 chainId 1 及预期链、F 的祖先关系与本地规范链一致，且扫描器已经完整处理到 F。供应商报告一个标签不等于我们已处理该标签以下的日志；chainId 相同也不能排除错误分叉或错误源，仍要核对预期链标识与哈希。

Filled 或 Cancelled 的承载块必须是 F 的祖先或 F 本身，业务状态与历史证据一致，才能升级为相应最终结果。若要声明 `ExpiredUnfilled`，还要求 `F.timestamp>=deadline`，在 F 固定块哈希查询为 Unused，并从有可信起点的连续扫描中确认无成功 fill；否则“没见到日志”只是扫描不完整。固定哈希查询可使用数据源支持的块哈希参数；不支持时应增加块前后校验或换具备所需能力的来源，不能悄悄使用 latest。

遇到 finalized 停滞、数据源落后或不同源哈希冲突，就停在等待或隔离状态，不用应用超时强造终局。使用自有验证节点或多源比对能降低错误数据风险，但仍要说清信任假设；不能把简单多数 RPC 当成共识证明。本题的 `t0+8` 是成功包含的案例时间，不是终局到达时长。

## 第9层：最终证据形成后，风险占用与 LP 余额怎样同口径变化

**面试官：** 假设 Filled 已进入 F，M 链上 WETH 是 9。本地原来记 10、active reserve 为 1，怎样避免成交和释放各扣一次？

**面试者：** 本地维护的是 M 外部钱包资产的投影与 LP 风险预算，不是平台托管账本。在本案例没有其他钱包变动时，LP 风险服务应在自己的数据库事务内消费最终证据，把 confirmed WETH 从 10 对齐为 9、把这份 reserve 从 `active 1` 变为 `consumed`、记录该结果已应用及必要后续 outbox；经消息接收时，inbox 也在这个事务中。这些风险侧变化共同提交；不能先把余额设为 9，仍把同一 reserve 当 active 再减成 8，也不能单独释放 reserve 而保留旧余额 10 供继续报价。链观察器的完整块事务和 finality 升级事务不与 LP 数据库组成跨库事务；结果到达风险侧之前保留原占用。

保守口径下，终局前使用上一个可信余额 10 减 active 1，可分配量为 9；终局后使用新边界余额 9、该 reserve 不再 active，可分配量仍为 9。`consumed` 是预占已被实际交割消耗的说明，不是再从钱包转走 1 WETH。若最终未成交且 Cancelled 或 ExpiredUnfilled，reserve 才变 released，余额在无其他变动的案例中仍为 10。

若余额由快照更新，必须记录快照覆盖的块哈希，避免已经反映 fill 的 9 再应用一遍成交减量。若余额靠日志投影，则要覆盖该钱包的其他相关变动并核对快照；M 可自行转账，不能假定只有本报价影响余额。资产投影与 reserve 无法在同一本地事务对齐时，先保持预算不可用，等待幂等对账完成后才开放报价，不能用异步最终会好来解释已超配的窗口。

## 第10层：如果重组越过已承诺的最终边界，还能照常“撤回”吗

**面试官：** 你已经依 F 发布最终结果、consumed 了 reserve。后来数据源给出一条越过 F 的重组，你还能用更高 revision 按普通回退恢复吗？

**面试者：** 不能当作日常浅重组处理。先区分数据源错误、配置错误和真实违背既定 finality 假设的事件；只要与已承诺边界矛盾，就暂停受影响范围的新风险与最终发布，隔离冲突数据，保存双方链头、祖先关系、F 证据和已外发结果。不能自动撤销已经被下游不可逆消费的最终结果，然后说幂等机制会修好。

处理需要重新核验可信节点与链政策，明确影响哪些 quote、余额投影、reserve 和消费者。如果证实此前承诺基于错误证据，使用独立的事故修正流程：更正记录保留原结果 lineage，协调下游恢复或人工处置，并承认无法自动逆转的外部影响。这里是改变已公开事实的异常修正，不是普通 `Included→Pending`，更不能偷偷再让 A 发一笔交易来“补齐”。

设计取舍是正常路径简洁、可撤回观察充分，但最终边界冲突必须 fail closed。保留原始块、观察版本和交付记录有存储成本，却能回答“当时依据什么承诺、哪些义务已被消费”；只保留当前状态虽然省空间，遇到这种事件就既无法证明，也无法有序修复。

## 本题收束

- **讲透的机制：** 执行结果与稳定阶段分离；观察身份绑定分叉证据，领域身份绑定同一合约权利；连续扫描、完整块原子提交和哈希检查点形成可恢复链视图；共同祖先回退只修暂态，finalized 边界才支持最终承诺。
- **最容易答错的边界：** status=1 不自动等于目标 RFQ 成交；高度增加不证明旧块仍在规范链；Expired 不要求链上枚举变化；deadline 只阻断未来执行；N 确认不是绝对终局；普通重组撤回与跨承诺边界的事故修正不能混为一谈。
- **一个具体检验（手工推演，非已运行测试）：** 在旧分支 B 的 `t0+8` 块观察到 fill，产生 revision 21；B 被浅重组移除，产生 revision 22 的撤回，风险保持 active。新规范分支在 `t0+19` 块再次成功包含同一 quote，产生 revision 23，并在后续经核验的 F 下产生最终版本；F 的时间已覆盖 deadline。应保留两份不同 blockHash 的观察，但最终只有一个 Filled，不能因“已过期”发布 ExpiredUnfilled，也不能因两次观察扣两次 1 WETH。即使旧 revision 21 最后到达，消费者也不能覆盖新状态。若让共同祖先落在已承诺 F 之前，则应转为暂停隔离，而不是普通自动回退。案例不承诺这些区块在现实主网的到达间隔。
