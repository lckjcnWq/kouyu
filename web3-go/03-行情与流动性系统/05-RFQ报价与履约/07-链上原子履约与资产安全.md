# 大问题 7：结算合约怎样保证报价只履约一次，并让两种资产原子交换？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
| --- | --- | --- |
| EVM 原子交换 / revert | 同一链上调用内，两条资产腿和状态一起提交或回滚。 | 第二腿失败要撤销第一腿、nonce 写入和日志，不靠另发退款；不回滚已经消耗的 Gas。 |
| EIP-712 / digest | 按固定执行域和完整结构计算的签名摘要。 | M 授权确切资产、金额、双方、nonce 和截止；原子执行正确不代表授权检查可以省略。 |
| msg.sender / 唯一收款人 | 当前真正调用 S 的地址，以及条款规定的资产接收人。 | A 自己调用并收到 WETH，不接受外部另传 receiver；复制调用数据不使第三人获得收款权。 |
| allowance | 代币持有人允许 S 代为扣币的权限额度。 | 与 A 的交易签名、M 的报价签名各管一层；授权不是资产已经转入 S。 |
| nonceState / quoteNonce | S 持久保存的报价执行资格。 | 固定域内按 maker 与报价 nonce 至多成功消费一次；换 txHash 或 A 的账户 nonce 不绕过它。 |
| 检查—状态—交互 | 先验条件，再写消费状态，最后调用代币转账。 | 先置 Filled 防重复进入，但后续失败须向上传播；吞掉失败会破坏双边安全。 |
| SafeERC20 / 安全转账 | 让失败返回、异常返回或底层回滚不能被误当成功。 | 只处理调用结果，不担保任意币的经济行为；本文仅支持普通白名单 WETH、USDC。 |
| nonReentrant / 重入保护 | 防外部调用期间再次闯入关键执行路径。 | 不只防同一 nonce，还需审查共享状态入口；不是支持回调币或任意外部调用的许可。 |
| fill / cancel / deadline | 消费报价、maker 撤销报价和执行时间条件。 | 首先成功转换者生效，失败 fill 不占终态；执行时间等于截止也拒绝。 |
| receipt / consumed | 链上尝试的回执，以及最终成交后的本地义务核销。 | 成功回执先是包含观察，须核对规范链与最终性；核销须同余额水位，不能把已花资产重新释放。 |

## 把整篇文章压缩成一个故事

A 拿着 M 签的报价调用 S，准备付 3000 USDC 换 1 WETH。双方的扣币授权、M 的报价签名和 A 的交易签名各管一层，不能互相替代。S 先核对完整签名域、条款、调用人 A、白名单资产、严格截止和未消费 nonce，再写 Filled，依次转 USDC 和 WETH，并发出成交事件。若最后发现 M 撤销了 WETH 授权，失败必须向上传播，整笔调用回滚，A 的 USDC 和报价资格都恢复，不需另一笔退款；但 A 仍可能付 ETH Gas。安全转账封装不能把 false 当成功，白名单也不能被同名假币替换；重入保护覆盖关键路径，却不意味着支持任意回调资产。若正常成功，A 得到 WETH，同一报价换交易哈希再来仍被 nonce 拦住。M 的 cancel 与 fill 按首先成功的链上状态转换裁决，模拟通过不会锁住后来变化的余额、授权和时间。后台拿到成功回执后先记已包含，核清规范链与最终性才将预占核销，并把余额和义务对齐。这样保证的是一次执行内部双边安全和单资格至多一次，不是拿到 firm 就必成交，也不是数据库已与链共同提交。

**流程位置与核心机制：** A 持有 M 的报价签名 → A 直接调用 S.fill → 验证签名、身份、时间与 nonce → 消耗执行资格 → 两侧资产转移 → 整笔提交或整笔回滚。本题深入 EVM 内部的授权边界、唯一执行屏障、转账与回滚；资本预占见第 5 题，竞争状态序见第 6 题，链下到链上的总一致性见第 8 题。

**必要前提：** 公共模型沿用总览 [1.1 讨论基线](README.md#11-讨论基线究竟在交易什么)、[1.2 贯穿案例](README.md#12-贯穿案例与完成结果)与 [4.1 不变量](README.md#41-不变量与业务规则)，本题只深入固定 S 的 EVM 执行边界。

- Q1/R1 的签名绑定 A、M、两种 token、`1e18` WETH、`3000e6` USDC、nonce 73 及 `deadline=1800000020`；调用人和唯一 WETH 收款人都是 A，不接收另一个任意 receiver。
- S 内唯一执行屏障是固定 `chainId+S+maker` 范围下的 quoteNonce；quoteId/rfqId 不另外提供链上防重放或共享消费。先写 Filled，再做两侧安全转账，失败必须整笔回滚，终态不能覆盖。
- 只对普通白名单 WETH/USDC 论证，使用重入保护；firm 与内部预占不保证余额或授权一直存在。合约原子成功、规范链最终确认及本地库存核销是不同边界。

## 第 1 层：原子交换究竟承诺什么，不承诺什么？

**面试官：** 结算合约怎样保证报价只履约一次，并让两种资产原子交换？具体到本例，怎样避免 A 已付 3000 USDC 却没有收到 1 WETH，或同一份报价被重复成交？

**面试者：** 把两侧 ERC-20 转移与报价执行资格的消耗，放在 S 的同一笔 EVM 交易中。交易成功时，nonce 73 从 Unused 变成 Filled，3000 USDC 从 A 到 M，1 WETH 从 M 到 A；只要任何校验或转账失败，所有这些变化一起回滚，不允许留下一侧付款或已消耗 nonce 的半成品。

这里的原子性是“要么全部交换，要么全部不交换”，不是“拿到 firm 报价就必然交换”。A 余额不够、M 转走 WETH、授权被撤销、报价过期或者 nonce 已取消，都会使整笔交易失败。A 即使未成交，也可能支付已经消耗的 Gas。

只履约一次依靠 S 的持久化执行状态。它不能靠后端记一个 quoteId，也不能靠“同一 txHash 不会再打包”间接推断，因为 A 可以用不同 EOA 交易 nonce 提交相同报价。

因此，要把两个保证分开说：EVM 交易边界保证成功时两侧资产一起改变，报价 nonce 屏障保证同一执行资格在同一规范链历史上最多成功消费一次。

## 第 2 层：合约怎样知道这就是 M 同意给 A 的那笔交换？

**面试官：** 你把两条转账放在一笔交易里，但如果 A 把 makerAmount 改成 10 WETH，或者第三人复制签名改收款人，交易仍然可以原子地偷走资产。授权边界怎么建立？

**面试者：** 原子性不等于授权正确，S 必须先验证完整交易条款。EIP-712 的结构化 payload 应覆盖 `quoteId、rfqId、maker、taker、makerToken、takerToken、makerAmount、takerAmount、quoteNonce、deadline`，字段类型和顺序固定；金额使用 uint256 原始单位，不把“1”或“3000”这样的展示值带进签名。

域分隔符固定包含协议 name/version、`chainId=1` 和 `verifyingContract=S`。S 用自身地址与当前链身份构建或核验域，不能接受调用者提交的任意 domain 当成可信输入。结构哈希和域一起形成 digest，恢复的签名者必须严格等于 payload 中的 M；EOA 签名应按规范库检查签名长度、v、低 s 等合法性，并拒绝零地址恢复结果。

然后要求 `msg.sender==taker==A`。资产转移目标由已签条款决定：USDC 从 A 到 M，WETH 从 M 到 A；fill 不另收一个任意 receiver，也不接受调用者替换 token 或数量。第三人即使复制 calldata，也因调用者不是 A 失败。

A 自己发送的 EOA 交易签名授权本次对 S 的调用，M 的 EIP-712 签名授权报价条款，双方对 S 的 token allowance 又授权具体扣币能力。三者分别回答“谁在调用”“M 同意什么”“S 能从谁的 token 余额扣多少”，不能省掉任意一层。

## 第 3 层：为什么有完整签名还必须有 maker nonce 屏障？

**面试官：** 你已经绑定了 Q1、A、链和合约，为什么还要存 nonce？用 quoteId 或签名字节去重不行吗？

**面试者：** 签名验证只证明 M 同意过这些条款，不会让签名在第一次执行后自动失效。即使 payload 完全不变，A 仍能再次调用；所以 S 内要有 `nonceState[maker][quoteNonce]`，默认 Unused，只允许成功 fill 转为 Filled 或 M 的 cancel 转为 Cancelled。

在 S 内，唯一执行屏障是 `(M,73)`；链下完整定位再加 `chainId` 和 S。quoteId 用于关联业务、签名和事件，即使它也参与签名，仍不是另一套独立的防重放存储。不能把数据库的 quoteId 唯一约束说成 S 已经消费了链上权限。

如果误把不同 quoteId、不同条款都签到 `(M,73)`，它们不是两次独立可成交的承诺，而是在争同一执行资格；只要一份成功，另一份就不能成功。签发系统仍应禁止这种冲突，不能把它当成免预占的常规做法。反过来，同样内容换一个新 quoteNonce，就形成新的链上权限，需要新的风险准入，不能拿来作为网络超时重试。

也不按签名字节去重。签名编码或表示形式不应决定业务权限是否被消耗，规范化校验用于排除异常签名，nonce 状态才是跨交易稳定的执行屏障。

## 第 4 层：fill 与 cancel 争同一个 Unused 时，写入顺序怎么安排？

**面试官：** 你用 `(M,73)` 作为屏障。若 fill 和 M 的 cancel 同时进区块，合约怎样避免两个都成功，或者先转币后才发现已被取消？

**面试者：** 在同一条规范链历史中，EVM 按交易顺序执行，不能把两笔交易当成数据库里同时运行的线程。fill 先做全部前置检查，再把 Unused 写成 Filled，然后调用 token；cancel 按 `msg.sender=M` 定位自己的 nonce，只允许 Unused 写成 Cancelled，不能替别的 maker 撤销。

fill 的语义顺序是：进入重入保护 → 检查调用身份、条款、签名、时间和 nonce → 写 Filled → 从 A 向 M 转 USDC → 从 M 向 A 转 WETH → 发出完整履约事件 → 成功退出。cancel 的终态转换同样必须受身份与 Unused 检查，不能保留管理员任意重置 Filled 的后门。

若 cancel 先成功，fill 看到 Cancelled 就失败；若 fill 先成功，cancel 不能覆盖 Filled。但如果排在前面的 fill 因后续 token 转账失败而回滚，它写的 Filled 也消失，后面的 cancel 仍可成功。这叫“首先成功提交状态转换者获胜”，不是“首先进入函数者获胜”。

时间检查使用严格的 `block.timestamp < deadline`。过期 fill 回滚后，nonce 可以仍为 Unused；M 此后依然可以取消它，合约没有依靠后台自动执行的 Expired 转换。

## 第 5 层：第二条转账失败时，第一条已经支付的 USDC 怎么回来？

**面试官：** 你先写 Filled，再把 3000 USDC 转给 M，最后转 WETH。如果最后一步授权不足，A 的 USDC 已经转走，如何补偿？

**面试者：** 不需要另一笔链上退款补偿，因为第一条转账仍处于同一笔尚未提交的 EVM 交易。只要 WETH 转账失败向上传播为 revert，EVM 会回滚本次交易调用树中的 token 状态变更、S 的 nonce 写入和日志。最终 A 仍有 5000 USDC、0 WETH，M 仍有 0 USDC、10 WETH，nonce 仍 Unused，前提是初始资产没有其他交易改变。

危险实现是捕获转账失败后仅返回 `false`，或者发一条失败事件却继续正常返回。这样 EVM 交易可能 `status=1`，第一腿却已成功、第二腿没发生。正确实现不能吞掉任一必要资产转移的失败，也不能允许“第一腿成功先记账，第二腿异步补齐”。

`Filled` 事件只在两腿完成后发出更容易审计；即使此前误先发了日志，后续 revert 也会移除该次交易的日志，不能作为成功凭据。交易追踪中曾出现过调用或临时写入，不等于规范链状态已提交。

失败仍会消耗 A 的 Gas；这部分是执行费用，不属于回滚的 ERC-20 交换。A 的 EOA 交易 nonce 通常也因已打包执行而被消耗，但报价 nonce 73 随业务回滚恢复，两种 nonce 不可混为一谈。

## 第 6 层：怎样让 token 的异常返回也触发整笔回滚？

**面试官：** 你要求转账失败必须向上传播，但有些 ERC-20 返回 false，有些不返回数据。只调用 transferFrom 就能保证两腿成功吗？

**面试者：** 不能，必须使用经过审视的安全调用封装，例如具有 SafeERC20 语义的 safeTransferFrom：底层 revert 必须向上传播；返回布尔值时必须是 true；兼容已明确支持且没有返回值的实现；非预期返回格式不能默认为成功。token 地址必须是白名单中的真实合约，不能把对 EOA 的空调用当转账成功。

但安全封装只处理调用结果，不验证任意 token 的经济语义。恶意 token 可以返回 true 却不转账，税币可以让接收量小于发送量，rebase 可以使余额差不代表这次转移。因此当前基线明确只支持普通白名单 WETH/USDC，排除这些资产，不声称 safeTransferFrom 可以把任意 ERC-20 变成可信现货资产。

本案例直接按原始数量执行 `3000e6` 和 `1e18`，不在合约里做浮点换算，不另扣费用，也不允许 A 把 makerToken 换成同名假币。对支持资产的行为假设、地址和精度必须在接入时固定并审查。

如将来要支持转账税或回调资产，需要重新定义实际到账量、回调防护和价格条款，这是改变资产模型的替代方案，不能在当前固定数量报价下静默兼容。余额差校验可以作为特定资产模型的附加检查，但也不能替代可信 token 边界。

## 第 7 层：先置 Filled 后转账，为什么还要重入保护？

**面试官：** 你已经先写 Filled，相同 nonce 的重入会失败，而且基线排除了回调币。为什么还强调 nonReentrant 和可信 token 边界？

**面试者：** 先写 Filled 主要防同一执行资格在外部调用期间被再次消费，但它没有自动保护其他 nonce、其他入口或共享状态。只要执行外部合约代码，就应审查整个调用面，不能把一个 nonce 的检查当成所有跨入口不变量的保护。

S 对履约关键路径使用重入保护，并遵循检查—状态变更—外部交互顺序；与履约共享关键状态的入口要采用一致的重入边界或证明不会破坏不变量。重复进入当前 nonce 无法绕过状态检查，尝试从其他路径干扰结算也不应在半完成交换时被放行。

当前只允许可信普通 WETH/USDC，正常路径不依赖 token 回调；重入保护是纵深防护，不是宣称已经支持回调资产。S 也不提供任意 target/calldata 调用，不做 delegatecall 到调用者提供的地址，不用 tx.origin 替代 msg.sender，不在校验前调用外部“授权服务”决定权限。

代价是少量 Gas 和更严格的组合性边界，但本基线没有聚合器代收、闪电回调或委托执行需求，因此不应为未要求的组合能力扩大攻击面。真正的边界是小而可审计的合约入口加受限 token 集，而不是一句“加了锁所以绝对安全”。

## 第 8 层：模拟通过且授权充足，为什么链上仍可能失败？

**面试官：** 你已经限制 token 并防重入。若 A 提交前 eth_call 模拟成功、M 有 10 WETH 且 allowance 足够，为什么还不能保证成交？内存池里别人复制交易又会怎样？

**面试者：** 模拟只读取某个区块或节点视图，不会冻结随后要用的状态。模拟后 M 可以转走 WETH、撤销授权或提交 cancel，A 可以花掉 USDC，打包时也可能已经过 deadline。正确的模拟能提前发现部分错误，但不能给未来状态发交割保证。

复制 calldata 的第三人不能改成自己收款，因为签名绑定 A 且 S 检查 msg.sender。别人原样传播 A 已签好的原始 EOA 交易，只是在帮助广播同一笔由 A 授权的调用，不获得改 receiver、token 或金额的权限。区块构建者可以影响交易顺序，但不能在不破坏签名或合约检查的情况下改变条款。

真正保留的竞争是 M 的 cancel 与 A 的 fill，以及其他交易对余额、授权的改变。它们必须由执行时的状态校验处理，不能用更高 Gas 或更频繁模拟承诺确定胜出。授权给 S 也不是资产已经转入 S，它只是一项扣币权限。

若业务要保证“接受后 M 不能撤销、资金不能挪用”，需要新增链上锁定或抵押规则，改变当前可撤销、非托管的基线。在本模型中，正确的资产安全是失败不发生单边支付，而不是消灭所有失败可能。

## 第 9 层：receipt 成功就能宣布最终成交并释放预占吗？

**面试官：** 你把失败风险留给执行时校验。假设拿到 status=1 的 receipt，两腿都成功了，后台可以立即结算库存并把原预占释放吗？

**面试者：** 可以记录 Included 成功观察，但不能立即把它当最终事实释放资本。receipt 必须对应 A 发给正确 S 的 fill、匹配原 payload 和执行身份，并在正确的规范区块中具有预期事件与 nonce 状态；同一笔交易在非最终分支上的成功可能因重组消失。

链观察记录 `chainId、txHash、blockNumber、blockHash、logIndex、canonicality、finality`，核验 receipt 所在区块仍在规范链上，再按适用最终性推进。若它被重组移走，要撤回 Included 观察并重新查询 nonce；此时原签名可能恢复可执行，不能让本地已经释放的 1 WETH 支持第二份承诺。

最终 Filled 后，内部 reservation 是 consumed，不是把同一资产重新变成空闲 1 WETH。对齐余额水位后，应为 `余额9、活动承诺0、净可报9`，不能在新余额上再扣一次，也不能在旧余额10上先移除承诺。

若 receipt 为 status=0，经过适用最终性后只归档该次失败；nonce 可能仍 Unused，期限内可用原报价身份重试。若要认定到期无成交，则需最终规范链前缀覆盖 deadline，并核验状态、历史和所有旧 attempt。EVM 原子性保证一次执行内部的一致，不替后台解决分支选择、最终性或跨域投影。

## 第 10 层：怎样审查“只成交一次且双边安全”不是口头承诺？

**面试官：** 你已经区分了原子执行和最终确认。若要审查固定合约 S，应把哪些具体性质和反例作为验收条件？

**面试者：** 我会先验证两条合约级性质：在同一规范执行历史中，`(M,73)` 最多发生一次成功的 Unused→Filled；每次成功 Filled 都对应恰好一笔 A→M 的 `3000e6` USDC 和一笔 M→A 的 `1e18` WETH，且收款人不可替换。下面是验证设计，不表示已经运行测试。

1. **正常成交：** `t0+8` 成功后 A 为 2000 USDC、1 WETH，M 为 3000 USDC、9 WETH，nonce Filled；Gas 仅消耗 A 的额外 ETH。
2. **篡改与重放：** 改金额、token、taker、deadline、rfqId 或域均导致签名无效；相同报价换 txHash 再发不能第二次成功；第三人复制 calldata 不能收款。
3. **第二腿失败：** 在发起前撤销 M 的 WETH 授权，必须让第一腿 USDC、nonce 和履约事件一并回滚，而不是产生一条成功 receipt 加失败返回值。
4. **取消竞争：** cancel 先成功则 fill 失败；fill 先成功则 cancel 失败；fill 先执行但 revert 后 cancel 仍可成功。检查失败是否被错误地“烧掉”报价 nonce。
5. **边界与 token：** 时间戳等于 deadline 时拒绝；非白名单、异常返回和失败调用不应进入成功路径；重入入口不得绕开 nonce 或在半交换状态破坏共享不变量。
6. **链观察：** 非最终成功被重组移走后，不得继续向用户宣称最终完成，资本投影也不能沿用旧分支释放结果。

对不可升级 S，错误不能靠“上线后改实现”轻松修复，所以签名格式、token 行为、入口权限和回滚传播都必须在部署前审查。当前方案的安全结论始终带着明确前提：普通白名单资产、单链、EOA 自行执行和适用最终性边界。

## 本题收束

- **机制：** 完整 EIP-712 条款与域绑定、A 唯一调用及收款、M 签名与双方 allowance、maker nonce 唯一屏障、先状态后交互、安全转账、失败向上传播、重入与 token 边界。
- **易错：** 签名不是冻结；quoteId 不是独立防重放；不同 EOA nonce 可以重放同一 payload，必须靠 S 的报价 nonce 拦住；第二腿失败不是另发退款，而是整笔回滚；回滚不退还已消耗 Gas；receipt 成功不等于最终确认。
- **反例与验证：** 若第二腿失败后 USDC 已转出，或 nonce 留在 Filled，说明失败没有穿透完整交易边界；若第三人能改 receiver，说明原子交换虽成立但授权已失效。原子性、权限正确性和最终性必须分别证明，不能用其中一个替代另两个。
