# 大问题 1：一笔做市成交如何经过报价、库存、对冲与业务收尾？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 做市 | 在交易所挂买单和卖单，供别人来交易 | 本文是 A 所现货做市，不是 AMM 或永续杠杆交易 |
| 对冲 | 再做一笔反方向交易，降低多买或多卖的数量风险 | 在 B 所独立成交；B 失败不能撤销 A 已发生的成交 |
| 权威事实与投影 | 场所确认发生的交易，以及本地根据证据整理的账 | A/B 各自掌握执行真相；本地旧余额快照不能抹掉新成交 |
| delta、H、E | 已确认偏离、尚未确定执行的对冲、规划后预计还差多少 | delta=Q−20，E=delta+H，买正卖负；不能用 E 代替确认库存 |
| Ubuy、Usell | 所有订单尚可能带来的买入或卖出余量 | 含待撤和未知订单；数量区间为 [delta−Usell, delta+Ubuy] |
| 本地事务与 Outbox | 把一次成交处理和后续任务一起保存 | 去重、库存、意图、处理位置共同提交；不覆盖 B 的交易 API |
| clientOrderID 与 UNKNOWN | 请求的稳定身份，以及暂时查不清的结果 | 身份字段不必然支持幂等；查询未找到也不必然证明未受理 |
| generation 与 owner epoch | 报价的代次，以及本地写入者的任期 | 新代次不让旧挂单消失，新任期不自动阻断旧外部请求 |
| 本所可用资产 | 真正能在那一家交易所拿来下单的币或钱 | 总 ETH 中性不表示 B 还有足够 ETH 卖出；跨所划转是另一流程 |

## 把整篇文章压缩成一个故事

小林在 A 做 ETH/USDT 现货双边报价，在 B 备好资产准备对冲，两所最初各有 10 ETH 和 100000 USDT。A 挂出的买单以 1999 成交 0.6 ETH，系统先按场所证据去重，再把库存增加、处理位置和 B 卖出意图一起记入本地事务，避免重启后只记库存却漏了后续任务。

B 请求超时，系统没有换 ID 再卖一次，也没有把总 ETH 写回 20，而是保留卖出 0.6 的执行可能。B 后来确认成交 0.4，确认敞口降为 0.2，未决卖量也剩 0.2；补齐最后 0.2 后才真正数量中性。假设本例零手续费且 B 全部成交于 1998，现金反而少了 0.6 USDT。A 的余单仍可能成交，B 的可卖 ETH 也已减少。文章从这件事追问到架构：谁拥有事实、哪些内容能本地原子提交、未知结果如何恢复、备机怎样隔离旧出口。不能把“已经安排对冲”“数据库已提交”或“总量回正”当作所有业务都结束。

**流程位置与核心机制：** 承担端到端起始母题，讲清模块责任、资产变化、完成条件和外部边界；报价计算、预算原子性、成交一致性和未知态协议分别在后续母题深挖。本题沿用总览的 A/B 两所现货案例，不改成永续、AMM 或跨链套利。

## 第 1 层：不要从公式开始，先讲完一笔业务

**面试官：** 如果由你设计做市系统，请从双边报价讲到一笔成交被对冲、资产可以核对为止，说明完整流程与系统架构。

**面试者：** 我会先把做市和对冲分成两个相互反馈、但不原子的交易过程。A 所报价提供流动性；A 的成交改变库存；B 的独立现货交易降低相对目标库存的数量风险。对冲失败不能撤销已经在 A 发生的交易。

在这个模型中，系统读取 A/B 行情、订单和账户事实，先检查输入是否完整有效，再计算公允价、库存偏斜、报价尺寸和资金空间。候选报价通过预算检查后，先持久化报价身份与发送任务，再请求 A 接纳。接纳后仍只是活动订单，可能成交、被撤销或继续等待。

A 买入成交 `0.6 ETH @ 1,999` 后，本地按权威成交更新投影：A 变为 `10.6 ETH / 98,800.6 USDT`，总确认库存比 20 ETH 的目标多 0.6。系统一方面调低报价中心，另一方面持久化 B 卖出 0.6 的对冲意图。B 若最终以 1,998 卖完，B 变为 `9.4 ETH / 101,198.8 USDT`，总 ETH 回到 20，USDT 却减少了 0.6。

```text
有效行情与账户事实 → 候选报价 → 预算/意图持久化 → A 挂单
    → A 成交 → 本地去重和库存更新
        ├─ 重算报价，管理旧单余量
        └─ 持久对冲意图 → B 独立成交 → 更新 B 库存
              → 核对成交、订单、资产与损益，结束对应执行义务
```

所以架构至少需要行情适配、策略决策、订单执行、成交观察、库存预算、对冲协调及对账恢复；这些不是一串同步 RPC，而是由持久事实连接的状态机。主案例对冲完成后，A 的买单余量 0.4 和卖单 1 ETH 还要管理，不能在流程图中凭空消失。

## 第 2 层：反馈环里谁有权说“已经成交”

**面试官：** 你说行情、执行、库存都在反馈。如果 A 的订单 API、本地订单表和库存表短暂不一致，谁有权决定实际成交与资产变化？

**面试者：** A 和 B 分别拥有各自场所的订单、成交与托管账务真相。策略只能提交意图，不能因为自己发出了卖单，就认定 B 的 ETH 已减少。本地订单表和库存表保存带证据的投影，必须说明覆盖到哪个成交或账户水位。

本地需要区分三种权威。第一是**外部执行事实**：哪笔订单被场所接纳、成交多少、余量是否不可再执行。第二是**本地处理事实**：哪条外部成交已被去重应用，当前意图和预算如何形成。第三是**策略决策**：下一代报价和对冲目标是什么。决策不能改写外部事实，外部乱序回报也不能任意覆盖已提交的本地处理位置。

例如我们已观察 A 买入 0.6，之后收到一份更早的余额快照仍显示 10 ETH。不能直接把 A 库存覆写回 10，再声称敞口消失。应该核对快照切点与成交水位；能够证明快照覆盖哪些成交，才按同一切点重建投影。无法证明时标记缺口并保护，不制造一个“看起来同步”的数字。

Go 实现中可让一个逻辑 owner 接收这些归一化事件并决定本地状态转移，I/O worker 只返回证据。owner 是本地串行决策者，不是外部交易所的撮合引擎，也不能强迫两个场所按同一顺序成交。

## 第 3 层：接纳、部分成交与数量风险是三个阶段

**面试官：** 既然 B 的执行事实归 B，那么 B 返回订单接纳后，系统能否认为 0.6 ETH 已对冲，恢复中性报价？如果只成交了 0.4 呢？

**面试者：** 都不能按意图数量一次性减少确认库存。订单接纳只说明获得执行资格，确认风险要按实际成交变化。

B 刚接纳卖 0.6 时，确认 `delta=+0.6 ETH`。未决对冲 `H=−0.6 ETH`，预计残差 `E=delta+H=0`。E 的作用是提醒规划器“已经有一份覆盖意图，不要再卖同样的 0.6”，不是证明市场风险归零。报价仍根据确认 delta 和最坏风险来控制。

B 确认卖出 0.4 后，B 的 ETH 减为 9.6、USDT 增为 100,799.2；确认 delta 变成 +0.2，H 同时只剩 −0.2，E 仍为 0。这是执行可能逐步转成确认持仓变化。不能让 delta 减少 0.4 后，又从预计残差额外扣一次“已完成对冲 0.4”，否则会过度对冲。

A 的买单也类似：原始 1 ETH 中 0.6 已经成为库存，余下 0.4 仍可能买入。更早成交但更晚送达的回报依然要入账；如果订单终态先到、本地还缺累计成交，先补证据再释放。接纳、累计成交闭合、余量终止、账户证据对齐和页面可见，是不同的完成含义。

## 第 4 层：从“更新库存”追到可靠产生对冲义务

**面试官：** 你已经把部分成交口径讲清楚了。但 A 的 0.6 已记库存，进程恰好在创建对冲意图前崩溃，重启后会不会永远漏掉这次对冲？

**面试者：** 如果这两个动作分别裸写，确实存在这个缺口。在教学基线中，我把一次成交消费的去重记录、库存投影、处理位置，以及由此产生的必要计划/意图和 Outbox 放进同一个本地数据库事务。

处理 A 成交时，先以 `(venue, account, tradeID)` 建唯一记录；事务读取本地订单、库存、已有未决对冲与配置，计算新的状态和仍需覆盖的量，再共同提交。提交前崩溃，所有本地变化一起回滚，来源成交会再次被获取或重放；提交后崩溃，去重结果和对冲义务都存在，发送者能从持久记录继续。

如果同一笔成交重复送达，唯一约束使其不会再次增加库存，也不会再次创建同量意图。事务重试时要依据最新已提交状态重新计算，而不是在内存中先修改持仓、失败后再凭猜测回滚。

我只声称这个事务消除了**本地已记成交却漏持久工作流**的窗口，不声称 PostgreSQL 可以把 B 的真实成交包含在同一事务中。Outbox 已发送表示任务交付推进，不是 B 已成交；将持久任务删掉也不能代表业务完成。

## 第 5 层：本地可靠不代表外部副作用一次

**面试官：** 对冲意图已持久化，发送 B 请求后超时；你不知道 B 是否成交。既然 Outbox 会重试，怎样防止再卖 0.6？

**面试者：** 先把外部身份固定下来。持久意图必须在发送前绑定 clientOrderID、账户、方向、数量、限价和载荷摘要，发送尝试复用原身份。是否可直接重投，取决于 B 是否明确保证该身份在所需保留期内幂等；不能把“支持 client ID 字段”直接等同于幂等提交。

超时后进入未知态，保留其全部尚未排除的执行可能与预算。优先按原身份查订单，补查逐笔成交并核对累计数量。若查到部分成交，就只更新这部分并保留余量；若查到可取证终态，补齐全部累计成交后才移除不能再执行的部分。

一次查询返回“未找到”不一定能证明从未受理，可能是读模型延迟、查错账户或时间窗口不覆盖。没有足够证据时宁可保持保护与人工升级，也不能换新 ID 再卖一次。若 B 没有可靠查询或去重契约，必须承认在该 API 条件下无法证明外部逻辑一次，降低自动化权限。

这也是为什么“重试＋对账”不是万能答案：重试需要稳定身份和可判定范围，对账负责收集证据、恢复未知，不是允许我们先制造两笔不受控交易再事后修正。

## 第 6 层：对冲未明时，报价还会继续制造新风险

**面试官：** 你选择保留未知态，但 A 仍在报价。若卖对冲未明时 A 再发生一笔反向成交，或新旧两代报价重叠，单看 E 会不会做错？

**面试者：** 会。E 是净额规划指标，不能覆盖所有成交顺序。系统还要跟踪每一笔活动、待撤、在途和未知订单的未确认剩余，把仍可能买入的数量记为 Ubuy、仍可能卖出的数量记为 Usell，保守可达区间是 `[delta−Usell, delta+Ubuy]`。

本例 A 买入 0.6 后还有买余量 0.4、卖余量 1，B 有未决卖 0.6，确认 delta 为 +0.6。区间为 `[-1.0,+1.0] ETH`。虽然 E 为 0，A 若先卖完、B 后卖完，总库存可能偏空；A 若先买完而卖单都没成，则可能偏多。

如果此时 A 又确认卖出 0.6，delta 会回到 0，但未知 B 卖单仍可能执行，不能因为原始做市流已经净额抵消就删除它。应评估撤销 B 余量及新的风险上界；若要建立反向意图，也必须证明旧执行可能与新意图共同处于预算内，不能机械对 E 下反向单。

报价更新同样如此：新 generation 只是新决策，不会自动撤销旧外部单。先撤后挂能减少重叠却产生空窗；先挂后撤要给重叠留资金和风险预算。系统不承诺任意行情下持续双边，而是优先守住确定的执行约束。

## 第 7 层：风险区间正确，为什么仍可能无法对冲

**面试官：** 假设区间和去重都正确，连续多次都是 A 买入、B 卖出，总 ETH 一直回到 20。为什么这套系统仍可能在某一刻无法继续对冲？

**面试者：** 因为总数量中性不保证资产在正确场所。每次 A 买入、B 卖出都会把 ETH 分布向 A 倾斜，把 USDT 分布向 B 倾斜。总 ETH 仍是 20，但 B 可以用于现货卖出的 ETH 越来越少，A 可用于买入的 USDT 也会减少。

这个模型没有借贷或裸卖空，所以 B 的卖对冲受 B 自己的可用 ETH 和已占用承诺约束。不能把 A 多出来的 ETH 当成 B 立刻可卖的余额，也不能靠“后面会划转”授权当前卖单。资金再平衡是单独的存取、确认与风险流程，可能耗时、受限或失败。

因此架构上需要各所资产预算与组合敞口同时存在。预算检查应绑定到订单意图，并原子占用；如果一个账户的多个 pair 共享 USDT，单 pair owner 不足以防重复用钱，要在账户资产维度协调。场所 free/locked 快照与本地承诺必须去重对齐，不能把已锁资金从 free 中再扣一次，也不能漏扣尚未反映的在途单。

当 B 对冲能力下降时，我会在真正耗尽前缩小 A 买侧、扩大风险侧价差、停止新扩险报价或撤单。能不能继续“只减仓”也要看所有待决订单，而不是把某个方向永久标成安全。稳定提供流动性是受资金和风险约束的目标，不是越过硬约束的理由。

## 第 8 层：恢复与变体不能偷偷改变这套保证

**面试官：** 如果主进程崩溃由备机接管，或者以后把 B 改成 DEX，这套闭环哪些地方能沿用，哪些必须重新证明？最后怎样验收它成立？

**面试者：** 能沿用的是分层思想：原成交不可回滚、确认事实与执行可能分离、先持久意图再产生外部副作用、未知态保守覆盖、以证据完成恢复。但接管和执行场所改变都会引入新的边界，不能只换一个适配器名字。

备机先取得新的本地 owner epoch，拒绝旧 epoch 的状态写入；这不够阻止旧进程已经发出的外部请求。还需让旧出口或凭证不能继续发单，并对接管前后的在途身份逐笔查单、补成交和对账。无法证明隔离与未决范围时不能直接开放新报价。恢复顺序是控制发送权、还原持久状态、补齐证据、验证预算，再逐步放量，不是发现进程存活就恢复双边。

若 B 改成 DEX，还要定义授权、nonce、交易替换、Gas、最小输出和确认层级；广播不等于成交，入块不等于最终确定，重组可能要求撤销观察投影并重新评估补偿交易。不能照搬 CEX 的终态与余额证据，也不能把原案例从现货数量控制暗换为永续空仓或 AMM LP。

验收时我会逐点推演 A 成交前后、本地提交前后、B 发送前后以及接管前后的崩溃、重复与乱序：每笔成交只影响资产一次，任何未决执行可能不因超时或接管消失，同一成交义务不因恢复漏规划，资产分布和累计成交能闭合。收益另按统一标记价、费用和执行成本评估，不用“对冲率 100%”替代正确性或盈利证明。

## 本题收束

- **讲透的机制：** 做市与对冲是两个独立执行域，由成交事实、本地原子工作流和可恢复证据连接；架构边界必须与风险和资金边界一致。
- **最容易答错的边界：** 接纳不是成交，E 为零不是确认风险为零，总 ETH 中性不是 B 有足够资产，对冲全成不是 A 余单自动结束。
- **检验反例：** B 卖 0.6 请求超时，A 随后卖出 0.6，系统又重启。若方案直接删除旧对冲、换 ID 补单、将剩余挂单清零或只靠本地锁恢复，则不能证明闭环成立。
- **可复用推演规则：** 每次说“完成”都补问：哪份证据、哪个执行域、哪些剩余义务；每次说“风险已降”都检查确认资产与未决承诺是否同时解释得通。
