# 大问题 8：对冲请求超时、部分成交和撤单竞争时，怎样避免重复交易与过早释放余量？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| intent、clientOrderID 与载荷摘要 | 已记牢的执行义务、提交身份和固定参数指纹 | 同身份不能换数量或价格；字段存在不代表永久幂等 |
| UNKNOWN | 不能证明外部单还会怎样执行 | 可与“已确认部分成交”同时成立；未知的是余量，不是否认已有成交 |
| 幂等作用域与保留期 | 在哪些账户和多长时间内，重复请求被认为是同一次 | 若只保证活动单 ID 唯一，全成后重发可能创建第二单 |
| 查询覆盖与负面证明 | 查对身份、时间和分页后，能否证明请求绝不会执行 | 多次未找到或 TTL 到期都不能自动证明从未受理 |
| delta、H、E | 确认库存偏离、未决对冲有符号余量、预计残差 | 买正卖负，E=delta+H；部分成交同时推进库存和 H |
| leaves、累计量与逐笔成交 | 外部说剩多少、已成多少，以及每一笔的实际证据 | 小 leaves 不能先缩承诺；累计数字不能冒充有身份的逐笔成交 |
| 撤单受理与取证终止 | 答应处理撤单，与证明实际余量已不能成交 | 还需补齐累计成交；撤单被拒不等于原下单被拒 |
| Outbox 与 ownerEpoch | 持久派送任务与本地决策任期 | 未标已发不代表外部没收到，任期也不自动隔离旧外部出口 |
| 后继意图 | 旧单执行可能查清后，按新条件安排的下一笔 | 不以新 ID 掩盖原单未知态；风险、资金可否决后继交易 |

## 把整篇文章压缩成一个故事

小林已为 B 卖出 0.6 ETH 持久化身份、预算和发送任务，结果请求超时。系统保留 UNKNOWN，不换 ID 补卖；即使查询暂时未找到，也先检查覆盖与延迟。后来查到成交 0.4 ETH@1998，重复推送只应用一次，B 变为 9.6 ETH、100799.2 USDT，delta=+0.2、H=−0.2。

接着终态先到，显示累计已成 0.5、取消 0.1，但本地还缺一笔 0.1。系统此时仍保留原 H=−0.2，而不是立即释放再卖 0.2。补齐缺失成交后，B 为 9.5 ETH、100999 USDT，delta=+0.1、H=−0.1；确认最后 0.1 不可再执行，才清掉对应 H 并评估新卖 0.1。崩溃接管也沿原身份恢复，并隔离旧发送通道。文章的主线是每次缩小执行可能，都要有证据：超时、终态标签、重启或取消请求本身，都不能替代数量闭合。

> 公共基线见总览第四节；以下仅列本题必要前提。

**流程位置与核心机制：** 对冲意图持久化 → B 请求结果不确定 → 查询补成交 → 部分成交与撤余量 → 崩溃接管。重点是“哪些证据允许缩小执行可能性”，不是把网络返回值当作资产事实。

**必要前提：** A 是链下托管 CEX 的 ETH/USDT 现货做市所，B 是独立现货对冲所。两所各预置 10 ETH、100000 USDT；无杠杆、借贷、裸空和跨所原子事务。目标总 ETH 为 20，Q 为确认 ETH 总数，`delta=Q-20`。A 初始 bid1999、ask2001 各 1 ETH；A 买入 0.6@1999 后为 10.6 ETH、98800.6 USDT，delta=+0.6。B 的卖 0.6 意图提交后，`H=-0.6`、`E=delta+H=0`，delta 仍为 +0.6。H 买正卖负，包含 Unknown，均以本地已可靠投影的成交为基准；数值忽略手续费。

```text
事务持久 intent、固定 clientOrderID、预算、outbox
    ↓ 提交后发送 B
明确拒绝且证明无执行资格 → 记录证据后释放
超时/断流/语义不明 → Unknown，保留 H 与预算
    ↓ 按原身份查订单、补成交、核对累计量
部分成交 → 去重、资产、意图剩余在本地共同提交
    ↓ 请求撤余量
终态已取证 + 成交证据闭合 → 释放真正未成交余量
    ↓ 按确认 delta 与剩余 H 重算，风险/资金可否决新意图
```

## 第 1 层：请求超时到底意味着什么？

**面试官：** B 卖 0.6 ETH 的请求超时，你会立刻再发一张卖 0.6 吗？

**面试者：** 不会。超时只说明客户端没有得到确定结果，可能根本没到 B，也可能已经受理、部分成交甚至全成。把它当失败换新订单，会让两张单都成交，造成过度对冲。我会保留原意图为 Unknown，继续占用其剩余 H、风险承诺和当地资金预算，并进入查单补成交流程。

下单前必须已经持久化 intent、clientOrderID、固定参数和 outbox；事务提交前不允许发送。outbox 能修复“本地已提交但尚未发送”的窗口，但它是至少一次派送，不能使外部成交恰好一次。A 的买入已经发生，即使 B 请求失败也不能回滚 A 成交；这里需要的是可恢复的独立交易工作流，不是补偿数据库余额来假装跨所原子成功。

## 第 2 层：固定 clientOrderID 能保证什么？

**面试官：** 你保留原身份，那一直用同一 clientOrderID 重试，就一定不会重复下单了吗？

**面试者：** 要看 B 的协议，不能把字段名当成幂等保证。我需要确认唯一范围、同 ID 同参数的重复提交行为、终态后是否允许复用、历史保留期和查询可见延迟。载荷摘要绑定账户、交易对、方向、数量、保护价格和订单类型；同 ID 换参数应在本地拒绝。

如果 B 只保证活动订单 ID 唯一，原单全成后重复 POST 可能再创建订单，不能盲重发。通常先按原 ID 查单与成交；仅在协议明确支持且保证仍有效时，重放原请求。想改价格要先终止旧执行可能，再创建有新身份的后继意图，不能原地改老意图冒充重试。若外部没有足够的幂等或查询能力，系统必须接受暂停与人工核验，不能声称达成绝对外部恰好一次。

## 第 3 层：Unknown 与已成交能否同时成立？

**面试官：** 如果你已观察到部分成交，但订单查询仍超时，还能标 Unknown 吗？状态机怎么表达？

**面试者：** 可以，因为 Unknown 是对剩余执行状态的知识不足，不是否认已观察成交。我分开记录发送/查询知识、执行证据和本地投影：原始数量、已可靠投影成交量、交易所报告累计量、外部 leaves、终态证据和来源版本不能压成一个状态枚举。

比如先看到 0.4 成交但不知道余下 0.2 是否活跃，可以表达“已确认 0.4、剩余 Unknown”。H 的剩余由本地已投影量和已取证不可执行量推导，不能单拿一个更小的 leaves 去覆盖。订单可能早已全成，只是本地尚未记账；在补齐前，未确认部分仍须被 Ubuy/Usell 覆盖。较新订单状态和较老资产投影混用，会制造没有任何承诺覆盖的风险空档。

## 第 4 层：查不到订单能否证明没下成？

**面试官：** 既然你要查询证据，连续几次返回“订单不存在”，是不是可以结束 Unknown？

**面试者：** 不一定。可能查错账户、ID 类型或历史接口，也可能是最终一致延迟、分页遗漏、查询范围太短；原始请求还可能在网络或发送队列中迟到。单次不存在、重复不存在或本地 TTL 到期，都不能直接证明从未受理。

我会校验查询身份和覆盖范围，结合历史订单、逐笔成交、订单回报及已知发送位置取证，并以退避和限频控制查询。只有协议能证明最终不受理，且原请求已不可能继续送达，才结束执行可能。若做不到，就保持 Unknown、限制新风险并升级处理。缺口会让确认 delta 只是过时投影，不能拿一个旧余额快照“查不到变化”作为负面证明；余额核对也需要可解释的截止边界。

## 第 5 层：补到 0.4 成交怎样安全落账？

**面试官：** 现在查到了 B 卖出 0.4 ETH@1998，而且 WebSocket 又推了一次同一成交，哪些量要一起改变？

**面试者：** 每笔用 `(venue, account, tradeID)` 唯一键，不以 orderID 去重。首次处理时，在同一本地事务中写入成交、更新 B 资产、意图完成量与剩余、计划、处理位置及必要 outbox；重复输入不再改任何投影。交易所拥有成交与账务权威，事务只保证本地变化共同提交，不覆盖 B。

这时 B=9.6 ETH、100799.2 USDT，Q=20.2、delta=+0.2；未决卖量余 0.2，H=-0.2，E=0。卖 0.4 让 delta 减 0.4，同时 H 增 0.4，因此 E 不因这笔执行重复变化。计划已完成量不能再从持仓减一次，订单累计成交 0.4 也不能再造一笔成交；同一 tradeID 的载荷冲突需隔离核验。实盘还要按成交费用资产修正净库存和现金。

## 第 6 层：先到终态、后到成交如何处理？

**面试官：** 本地只投影了 0.4，但订单终态显示累计成交 0.5、剩余 0.1 已取消。你能先把剩余 H 清零吗？

**面试者：** 不能。此刻还有 0.1 已发生但未投影的成交，终态只证明不会再产生新成交，不代表本地已经记完。我把订单标记为“终态已观察、成交待补齐”，原本相对本地投影的 H=-0.2 仍保留，预算也不抢先释放，不直接用累计量补写一个缺少身份的虚构成交。

取回缺失的逐笔成交，假设也是 1998：B 变为 9.5 ETH、100999 USDT，delta=+0.1，同时 H 从 -0.2 变为 -0.1，E 仍为 0。累计量与本地成交集合闭合、证据证明最后 0.1 不可执行后，才释放这 0.1，使 H=0、E=0.1，再检查是否创建后继意图。若终态累计本就是 0.4，补查证明无缺口后释放 0.2；这两个分支不能混算。

## 第 7 层：撤单成功为何仍可能看到迟到成交？

**面试官：** 你要求终态闭合，那撤单接口成功之后，为什么还要等成交？重复撤单又该如何处理？

**面试者：** 先区分“已受理撤单请求”和“已取消实际余量”。撤单与成交由 B 按其规则排序，撤单到达前发生的成交可以晚于撤单响应送达；本地不能用接收时间拒绝它。撤单超时则是撤单结果未知，不是原单失效；“撤单被拒”也不等于“原下单被拒”。

重复撤单仍指向原订单，恢复时核验累计成交和终态，不生成新对冲身份。只有无更多执行且成交完整，才在事务中消除旧承诺、释放预算并重新规划。后续同一成交重复回放由唯一键挡住；若终态闭合后又出现此前未见且与累计量矛盾的成交，应暂停相关规划、重新取证，而不是因本地已终态而丢弃交易所事实。数据库事务也不能阻止已经在 B 的订单继续成交。

## 第 8 层：等待取证期间遇到反向成交怎么办？

**面试官：** 你选择保留 Unknown，期间 A 又发生反向成交。能不能用新成交净掉旧对冲，再释放预算？

**面试者：** 不能，库存方向变了不等于 B 的执行资格消失。风控看所有未确认买卖的独立组合，`[delta-Usell,delta+Ubuy]`，U 以本地可靠投影量为基准，包含 A 余单、B 未决与待撤；H 已在其中，不能再额外加一次。原例 A 买余 0.4、卖余 1，B 未决卖 0.6、delta=0.6，最坏区间是 [-1,1]，不是 E=0。

反向成交后要重新计算整个区间，不能仅按 E 新发相反单。即使净数量很小，两个方向也可能只成交一个。预算分别检查 B 买入的 USDT 和卖出的 ETH，free 已排除 locked，不能双扣，也不能因旧快照未显示 Unknown 就解除本地占用。跨所资产不能瞬移；风险与当地资金均可否决候选新意图。等待期间可以缩减或撤 A 风险来源，但撤单前仍计入旧承诺。

## 第 9 层：接管如何不把 Unknown 再发一遍？

**面试官：** 等待取证时 owner 宕机，新实例读到未完成 outbox，如何避免把已经在 B 的单再发一次？

**面试者：** 新实例先恢复原 intent/clientOrderID、尝试记录、成交投影、水位、预算与未决状态，再查询原外部订单。outbox 未标完成不证明外部没收到；标成已发也不证明成交，不能把重启当作首次发送。对“可能已越过外部边界”的任务，按 Unknown 恢复，而不是无条件执行 POST。

本地 ownerEpoch 和条件更新只能挡旧实例写数据库，B 不认识这个 epoch。接管还需隔离旧出口、凭证或会话，防止分区中的旧实例继续外发；已越过出口的请求仍要查询。新的查单与发送必须受当前资格约束。无法证明旧执行资格已失效时，保持保护模式；先开放更多发送再做对账，会把一个待确认意图扩大成双写事故。单 goroutine、租约和事务都不能单独解决外部 fencing。

## 第 10 层：怎样验证恢复真的没有过度对冲？

**面试官：** 你恢复了同一身份和出口资格，怎样证明这条链闭合，而不是只看状态都变成完成？

**面试者：** 我按失败窗口手工推演：提交前、提交后发送前、B 受理后回包前、部分成交入账前、终态到达但成交未齐、接管前后。检查同一权威成交只投影一次，H 不因超时或小 leaves 凭空减少，预算不提前释放，任何后继意图都能指出旧执行可能已结束的证据；不以“总状态完成”替代数量守恒。

主路径若 B 最终卖满 0.6@1998，B=9.4 ETH、101198.8 USDT，Q=20，delta=H=E=0，总 USDT=199999.4，毛损益=-0.6。报价此前仍用确认 delta：F=2000、s=1，按 tick0.01 向下取 bid、向上取 ask；delta=0.2 时为 1997/1999，post-only 拒绝后重算。数量对齐仍有 A 余单、场所、费用和价格风险，不等于盈利或零风险；USDT 无须每笔链上转账，DEX/链上变体必须另改前提。

## 机制、易错边界与反例验证

- **讲透的机制：** 固定身份与载荷、发送知识和执行事实分离、Unknown 保留承诺、逐笔成交原子投影、终态与成交闭合后释放、外部隔离后恢复。
- **易错边界：** clientOrderID 不天然支持永久幂等；查不到不等于未受理；较小 leaves 不能先缩 U/H；撤单成功不等于所有成交已投影；TTL 和 owner 切换均非释放证据。
- **反例验证：** 从已投影卖 0.4 的切点，先输入累计 0.5 的取消终态，再丢失那笔 0.1 的成交。若系统立刻清 H 并卖出确认残差 0.2，缺失成交追回后可能过度对冲。正确处理是在缺口阶段保留 H=-0.2，补齐后只释放真实未成 0.1，再评估新卖 0.1。上述为预期状态推演，未创建项目或声称工程测试通过。
