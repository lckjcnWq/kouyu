# 大问题 10：Go 做市进程怎样在并发、崩溃和主备切换后继续正确处理订单？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 单逻辑 owner | 同一风险单元的订单、库存和意图只由一个决策入口改 | 按 accountGroup、pair 划分，不代表独占全账户资产或控制跨所成交顺序 |
| worker、有界队列与不可变快照 | I/O 工人异步办事，任务不无限堆，读者只看不改 | worker 交回证据，不能直接覆盖 owner 状态；成交不能像旧报价一样随意丢弃 |
| 本地事务、去重与 Outbox | 把已处理事实、资产变化和后续任务一起记牢 | 提交后才发布对应状态；Outbox 不把外部 API 变成恰好一次 |
| quoteGeneration、ownerEpoch | 报价目标的代次与本地领导权任期 | 旧目标可禁发，但旧代真实成交仍须核验入账 |
| clientID 与 UNKNOWN | 稳定外部请求身份，以及暂不能判定的结果 | 超时不换身份补单；能否原样重试取决于场所去重契约 |
| 快照水位与外部取证 | 本地恢复到哪条已提交记录，以及停机期间外部发生了什么 | 恢复日志不代表已看到全部外部成交，仍要补拉与对账 |
| RPO、RTO | 允许丢多少已记录状态，以及多久恢复到安全服务 | 异步复制不能声称 RPO=0；RTO 不只量进程启动 |
| fencing 与在途命令 | 限制旧执行者继续办事，并清点已越过出口的请求 | 数据库围栏不让交易所订单消失；外部出口或凭证还要真正隔离 |
| Ubuy、Usell 与恢复准入 | 所有可能买卖的量，以及是否可重新发单的门槛 | 未知继续保守覆盖，不能清空 map 或反向补单来冒充恢复 |

## 把整篇文章压缩成一个故事

小林把行情和回报交给同一逻辑 owner，网络请求由 worker 异步发送。A 买入 0.6 ETH 后，去重、库存、对冲意图和 Outbox 已在同一事务提交；B 卖 0.6 的请求刚发出，旧主就停顿了。新主读到待完成任务，不能照单重发，因为 B 可能已经成交。

新主先隔离旧发送出口，恢复可靠快照与日志，再按原身份查单补成交。如果只确认 B 卖了 0.4，应恢复成 delta=+0.2、H=−0.2，余单仍可能执行，不能再补卖 0.2。后来旧主复活，本地 epoch 能阻止它写库，但只有外部出口或凭证控制才能阻止继续发新命令；已经发出的请求仍需取证。恢复期间也不能无限开 goroutine，必须给成交接入、撤单和查询留下有界容量，证据不齐就保持禁止新增。本文证明的是从进程内串行，到持久提交，再到外部执行和安全接管的完整边界，不是“用了锁和 channel 就不会重复交易”。

**流程位置与核心机制：** 外部行情及私有回报 → owner 串行决策 → 本地事务与 outbox → 异步外部执行 → 回报归并；故障后经过隔离旧出口、恢复本地投影、外部取证与预算核验，再恢复报价。本题重点是状态所有权、跨故障边界和接管证明，不是实现交易所撮合引擎。

**必要前提：** A 做 ETH/USDT 托管现货做市，B 做独立 CEX 现货对冲，各有 10 ETH、100000 USDT，总 ETH 目标 20。无借贷、杠杆、裸卖空、跨所原子事务和逐笔链上转账。`delta=Q-20` 只含两所确认 ETH；F=2000、s=1、tick=0.01、lot=0.001，`r=F-k*delta`，`k=10 (USDT/ETH)/ETH`，买价向下、卖价向上取整；post-only 明确拒绝后刷新状态重算。每所成交和账务是权威，本地只是可恢复投影；外部 API 不在本地数据库事务内。

## 第 1 层：Go 的并发边界应该怎样划

**面试官：** 行情、成交、撤单和对冲都并发到来，你会怎样组织 Go 做市进程，避免库存与订单状态互相覆盖？

**面试者：** 我会按 `(accountGroup,pair)` 设置单逻辑 owner，统一修改确认库存、活动订单、未知意图、风险承诺、报价代次和策略状态。行情接收器、私有回报接收器和 I/O worker 只产出事件，不直接改这些字段。owner 每处理一个事件，先校验身份及外部事实，再推进状态并产生下一步意图，从而让本地决策有明确顺序。

这里的顺序不是交易所实际撮合顺序，也不是跨账户全局顺序。A 和 B 可以独立成交，本地必须根据各所身份及游标归并。多个交易对共用 USDT 时，单 pair owner 也不能独占余额，仍需账户级串行预算或跨 pair 原子预算服务。读路径使用不可变快照，不能让监控 goroutine 拿到 map 后顺手改仓位。这个模型解决本地并发，不声称消除了外部不确定性。

## 第 2 层：owner 不阻塞，旧任务结果怎样处理

**面试官：** 你把修改权收归 owner，但下单调用要等网络。如何不阻塞成交处理，又防止旧报价结果回来覆盖新报价？

**面试者：** owner 只把已经完成准入和预算绑定的执行意图放进有界工作队列，worker 异步调用 API，再把结果作为事件交回。事件携带 intentID、clientID、quoteGeneration、ownerEpoch 和外部订单身份。quoteGeneration 表示报价计划新旧，ownerEpoch 表示领导权世代，二者不能混用。

行情变化后，尚未发出的旧报价可以在出口处复核并废弃；但已经发出的旧代订单，即使结果过时，也必须登记它确实被接受或成交的事实，再安排撤单或重估。不能因为 generation 小就丢弃真实成交。worker 结果不能直接替换整个订单对象，否则一个迟到 ACK 可能把已部分成交的订单写回 New。所有队列有容量和过载策略；普通报价可以被拒绝或合并，成交和未知单取证不能按同样规则随意丢弃。

## 第 3 层：串行内存状态为什么仍不可靠

**面试官：** 旧结果不会覆盖了，但 owner 收到 A 买入 0.6 的成交，刚改内存就崩溃，重启如何不漏持仓或重复对冲？

**面试者：** 我会在同一个本地事务里插入去重成交、更新本地持仓及现金投影、更新相关订单累计量、记录对冲意图及必要预算绑定、写入 outbox。成交唯一键是 `(venue,account,tradeID)`，不是只用 tradeID。事务提交成功后才能发布对应内存状态和派发新增意图；提交结果不明时先查询持久事实，不继续使用猜测的状态。

重复成交若命中唯一键，就不能再次改变余额或再创建一笔对冲。A 买 0.6 后，本地应可靠得到 A 的 10.6 ETH、98800.6 USDT 和 delta=+0.6。若账户预算由独立服务管理，不能把它冒充成本地事务的一部分：使用稳定意图先取得幂等授权，未完成的授权保守保留并可恢复；没拿到授权时，事务可记录待预算意图，但不能发外部订单。原子性必须说清实际覆盖哪些表和哪个数据库。

## 第 4 层：事务提交后，怎样跨过外部下单边界

**面试官：** outbox 已经提交，worker 下单后超时。你把 outbox 再投一次，交易所会不会收到两张对冲单？

**面试者：** 会有这个风险，所以 outbox 只保证意图不丢，不能把跨交易所调用变成 exactly-once。发送前必须持久化稳定 clientID 和确定载荷；对同一意图不生成新 ID 掩盖重试。响应丢失后记录 Unknown，保留资产及风险承诺，按原 clientID 查询订单并补拉成交，不能直接宣告失败后再卖一次。

如果交易所明确支持在规定范围内按 clientID 去重，才可以按其契约重试，并核实保留期、账户作用域及载荷冲突规则；否则优先查单取证，必要时停新增并人工介入。查单暂时不存在，也不必然排除了在途请求。订单 ACK 仅证明接纳，不是成交；B 确认卖出后才减少 Q。outbox 的“已派发”“外部已接纳”“成交已入账”必须分别表示，不能在一个 sent 布尔值里混成一个完成状态。

## 第 5 层：成交先于 ACK，甚至撤单后才到，怎样归并

**面试官：** 你要求按 clientID 取证，但私有成交可能先于下单 ACK，撤单终态也可能先于成交明细。owner 如何保持确定状态？

**面试者：** 我会把外部事实与本地执行进度分开保存。成交无论何时到达，都先按唯一键落账；可利用 clientID 或外部订单号关联原意图，暂时无法关联的事实也不能丢弃。累计成交量按权威回报校验，不把重复累计值当增量再次记仓。迟到 ACK 只补充外部身份，不回退已经确定的成交和终态。

如果撤单终态说累计成交 0.4，但本地只有 0.3 的明细，就存在 0.1 的账务缺口。应阻止新增风险、补齐明细并保守保留必要承诺，不能在持仓少记 0.1 时释放全部剩余预算。也不能先按累计量改仓、后按明细再改一次。终态证明不再有未来剩余执行，但历史成交仍可能迟到；订单终态和账务完整性是两个条件，查单及成交游标对账共同提供证据。

## 第 6 层：有快照和日志，为何重启还要查交易所

**面试官：** 你能可靠归并已收到的事实。那么快照加日志已经恢复，为什么还不能立刻报价？

**面试者：** 因为日志只包含本地已取到的事实，停机期间外部仍可能成交。恢复时先关闭新报价入口，加载带提交位置、规则版本和校验信息的快照，再回放其后已提交记录。outbox 和 Unknown 意图恢复出来后也不能立刻盲重发，要先查活动订单、补私有成交、核对余额和冻结量。

每所分别维护成交游标或快照水位。若交易所提供一致性游标，就从约定边界接续；若 REST 余额与成交接口没有共同水位，就先缓冲增量、重叠拉取并去重，再重复核对，必要时维持停新增直到窗口收敛，不能把两个不同时间的响应拼成原子快照。比如本地只记到 A 买 0.6，而 B 已卖 0.4，补齐后 delta=+0.2、H=-0.2，E=0；报价仍依据确认 delta，未知剩余也继续占预算，不能恢复成“已经卖完”。

## 第 7 层：主机永久丢失时，本地可靠提交还算可靠吗

**面试官：** 你依赖已提交记录恢复，但主机连磁盘一起损坏了。备用进程如何知道哪些成交、预算和外部意图必须保留？

**面试者：** 沿用总览的 PostgreSQL 事务基线，我会选择具备明确复制提交契约的高可用部署，避免主备各维护一套可分叉本地真相。成交投影、预算绑定、外部意图和 outbox 必须进入其可靠提交边界，出口只执行能够证明已提交的意图。备用进程从该边界恢复，不能从落后的只读副本直接宣布接管。

如果只用异步复制，就要明确允许的本地 RPO 和补偿责任，不能宣称零丢失。交易所成交通常可以补拉，但“已经发出、尚未查到”的意图和预算也可能丢，补成交不能覆盖所有窗口。owner 租约和递增 epoch 也要可靠保存，关键提交检查当前 epoch，阻止旧主继续修改本地状态。租约过期只改变谁有权决策，不自动撤销旧主已经发往交易所的命令，这个缺口还需要单独隔离。

## 第 8 层：数据库 fencing 能防止旧主继续下单吗

**面试官：** 旧主已无法提交数据库，但它暂停前拿到一个已提交下单任务，恢复后仍能直接调用交易所。新 epoch 能挡住它吗？

**面试者：** 只在本地检查 epoch 挡不住，交易所通常不知道这个字段。我会把外部发送能力也纳入隔离：例如只允许受控账户出口持有交易凭证，出口按当前 ownerEpoch 及意图身份校验执行资格，旧主不能绕过；或者切换时明确禁用旧凭证、旧出口或相关网络路径，并确认隔离生效。若无法建立这种边界，就不能声称安全自动接管。

出口还要记录在途命令，暂停时关闭旧代准入并清点已发送范围。即便撤销旧凭证，也不能假设此前已到交易所的请求不存在；它们仍需查单和对账。失效 epoch 的回调不能再授权新命令，但携带的真实成交应交给现任 owner 核验、去重和落账，而不是丢掉。fencing 隔离未来执行权，取证收敛过去不确定性，两者缺一不可。

## 第 9 层：隔离旧主之后，备用何时算接管完成

**面试官：** 你已经隔离旧出口，但还有几张在途 Unknown 订单。备用能否凭新的租约马上发一套相反订单，把风险抵消？

**面试者：** 不能。新的租约允许它成为唯一决策者，不代表它已经掌握安全状态。接管应经历暂停准入、确认外部隔离、恢复可靠记录、补成交与活动单、核对余额及预算、验证行情、最后有限放行。Unknown 买卖未确认量分别保留，按总览的 Ubuy、Usell 计算 `delta_min=delta-Usell`、`delta_max=delta+Ubuy`。U 以本地可靠入账的成交为基准，不能只按外部最新 leavesQty 缩减，也不能按买卖净额抵消。

例如确认 delta=+0.2、未决卖 0.2，并不能再卖 0.2 来“保险”，两张都成交会变成 -0.2。未知预算若未查清，只能保守占用；仅在最坏边界、资产和价格保护都允许时讨论受限操作，否则停新增。恢复后的 quoteGeneration 负责新的报价计划，ownerEpoch 负责新的执行资格；旧代已接受订单仍在状态里，不能通过清空 map 或切代号把它们从世界上删除。

## 第 10 层：恢复期间再过载，怎样保持上述保证

**面试官：** 你把接管做成证据门禁，但恢复时又涌入补成交、行情和撤单，怎样不因 Go 队列阻塞而再次失控，并证明方案不是纸面正确？

**面试者：** 我会为回报持久接收、撤单与风险取证保留独立的有界通道和限频预算，在交易所总限频内统一调度。owner 不等待 worker 网络返回；行情可合并为最新有效状态，历史成交则靠可靠接收或补拉游标承接。若持久化或消费落后超出安全范围，就保持禁止新增，而不是无限开 goroutine、扩大 channel 掩盖积压。优雅退出先封新增、可靠记录未决，再让下一 owner 恢复；进程超时退出不表示外部订单已撤完。

验证可以手工推演或另行故障注入：分别卡在事务提交后发送前、交易所接受后响应前、部分成交后撤单前、旧主停顿后复活等窗口，检查成交只落账一次、未知预算未释放、旧主无新增出口能力。RTO 从故障检测一直量到安全放行，不能只量进程启动。性能优化先测队列等待、持久化及网络尾延迟，再决定分片或分配优化，不虚构 GC 优化实测；本文不声称已经运行测试。

## 本题收束

- **讲透的机制：** 单逻辑 owner 解决本地状态竞争；本地事务与 outbox 保护内部事实和意图；稳定 clientID、外部隔离及对账覆盖 API 边界与接管窗口。
- **最容易答错：** 单 owner 等于全账户余额独占、outbox 等于外部只执行一次、旧 generation 成交可丢弃、数据库 fencing 等于旧主不能访问交易所。
- **反例检查：** 旧主发送 B 卖 0.6 后暂停，新主只看到已成交 0.4。若新主直接补卖 0.2，而旧单剩余 0.2 后来成交，就会重复对冲；正确接管必须保留原未知承诺，先取证再决策。
