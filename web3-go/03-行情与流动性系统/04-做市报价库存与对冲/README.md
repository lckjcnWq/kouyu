# 做市报价、库存与对冲：专题总览

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 做市与双边报价 | 同时摆出“我愿意多少钱买、多少钱卖”的订单 | A 所 ETH/USDT 现货挂单；不是承诺两边都会成交或一定赚差价 |
| Post-Only | 只允许挂在簿上等待别人来成交 | 到达 A 时若会立即吃单，可能被拒；不能自动改成吃单 |
| 公允价 F、半价差 s | 心里的参考估值，以及买卖价离中心各留的距离 | 教学值为 2000 和 1 USDT/ETH；F 不是 B 的保证成交价 |
| 确认库存 Q、目标 Qtarget、敞口 delta | 已确认有多少 ETH、希望留多少，以及多了或少了多少 | 两所合计目标 20 ETH；delta=Q−20，不是永续合约仓位 |
| 未决对冲 H、预计残差 E | 已安排但还可能执行的对冲，以及扣除这些安排后还缺多少 | 买正卖负，E=delta+H；E 为零只能防重复规划，不能证明实际风险消失 |
| Ubuy、Usell | 所有仍可能买入或卖出的未确认余量 | 包括待撤、在途和 UNKNOWN；用来算最坏数量区间，不能双边净额抵消 |
| 本所资产预算 | 发单前先占住该交易所实际需要的资产额度 | A 的 ETH 不能直接支付 B 的卖单；free 与已反映的 locked 不重复扣 |
| UNKNOWN | 请求发出后，还没有足够证据判断外部结果 | 保留余量和预算，按原身份查单补成交，不当作失败重发 |
| Outbox 与本地事务 | 把库存变化和后续要办的任务一起记牢 | 只保证本地状态共同提交，不能让 A 成交与 B 对冲变成同一笔原子交易 |
| owner epoch 与外部隔离 | 本地写入权的任期号，以及阻止旧进程继续发单的措施 | 数据库围栏不自动撤销已发订单，还要控制外部出口并查清在途单 |
| MTM（按市价估值）与损益归因 | 按同一个参考价估值，再解释钱到底赚亏在哪里 | 数量回归目标不等于盈利；费用、价格变化和执行成本需另算 |

## 把整篇文章压缩成一个故事

小林做了一套现货做市系统，A、B 两所各放 10 ETH 和 100000 USDT，没有借贷或裸卖空。系统先确认行情完整新鲜，再在 A 挂出买 1999、卖 2001 的订单，各 1 ETH，并先记录身份与预算。A 买侧成交 0.6 ETH 后，系统把去重记录、库存变化、对冲意图和待发送任务一起提交：总 ETH 从 20 变成 20.6。

接着它准备在 B 卖出 0.6 ETH。这份安排让 E 变成零，却不能提前把确认敞口清零；请求超时也只能保留 UNKNOWN。B 先确认卖出 0.4，再确认卖出 0.2，系统逐笔减少库存和对应未决余量，不重复下单。最终两所合计恢复 20 ETH，但按本例零手续费、B 全在 1998 成交，现金只剩 199999.4 USDT，毛亏 0.6。系统还要核对资金与成交、管理 A 剩余买单 0.4 和卖单 1 ETH。整套专题就是证明：行情失效、撤单乱序、进程重启时，这些真实义务也不会因一张本地状态表变绿而消失。

## 一、文字全流程

### 1.1 讨论基线：两所现货做市，不混入永续和 AMM

| 维度 | 本专题约定 |
|---|---|
| 产品与场所 | 在 A 中心化交易所的 ETH/USDT 现货订单簿双边做市，在独立的 B 中心化交易所现货市场对冲 |
| 资产与执行 | 链下托管，两所预先备好 ETH 和 USDT；无杠杆、借贷、裸卖空；卖单必须有本所可用 ETH |
| 报价订单 | A 使用限价、Post-Only 报价；报价包含代次、价格、剩余量与有效输入版本。Post-Only 拒绝后重算，不假定一定能挂上 |
| 对冲订单 | B 使用受价格保护的可成交限价子单；可部分成交，支持的有效期以场所协议为准，不假定无限深度或立即全成 |
| 交易事实 | 各所拥有各自订单、成交与托管账务的权威状态；本地持仓、余额和订单记录是带来源证据的投影 |
| 本地提交 | 以 `(accountGroup, pair)` 为逻辑决策单元；成交去重、库存投影、计划/意图变化、事件处理位置及 Outbox 在本地事务中共同提交 |
| 跨所边界 | 本地事务不能覆盖外部交易所；A 成交与 B 对冲不是一个原子事务，不支持“B 失败就撤销 A 成交” |
| 风险目标 | 管理总 ETH 相对目标库存的数量敞口，同时检查各所资产、全部未决承诺与对冲能力；数量归零不等于盈利或无风险 |
| 费用与划转 | 主案例手续费为 0、无划转；扩展题明确加入费用及其扣费资产。跨所调拨是独立工作流，不作为每笔对冲的前置动作 |
| 范围外 | 不实现 AMM LP、永续保证金与资金费、期权 Greeks、跨链桥和链上交易执行；比较时必须明确改变前提 |

这是一套教学架构，不声称相邻专题已经采用相同的提交方案。无需安装 Go、数据库或消息队列；环境准备是理解订单簿、托管余额、十进制定点单位和下述状态约定。不建立可运行项目、不执行工程测试。

### 1.2 贯穿案例与单位

新设独立案例，不接续其他专题的成交序列：

- A 初始 `10 ETH + 100,000 USDT`；B 初始同样为 `10 ETH + 100,000 USDT`。
- 总 ETH 目标 `Qtarget = 20 ETH`；确认库存 `Q = QA + QB`；数量敞口 `delta = Q − Qtarget`。
- 公允参考价 `F = 2,000 USDT/ETH`，教学半价差 `s = 1 USDT/ETH`。
- 教学偏斜系数 `k = 10 (USDT/ETH)/ETH`，所以 `k × delta` 的结果是价格偏移，不是资金金额。
- 价格最小变动 `tick = 0.01 USDT/ETH`，数量步长 `lot = 0.001 ETH`；最小名义金额另按场所规则检查。
- 候选中心价 `r = F − k × delta`，买价 `floorTick(r − s)`，卖价 `ceilTick(r + s)`。
- 初始 A 买价 `1,999`、卖价 `2,001`，两侧各 `1 ETH`。下述主路径只有买侧成交，不假定卖侧也赚到一次点差。

这是为推演库存控制选择的线性规则，**不是普适最优报价模型**。行情、深度、费用、逆向选择和场所约束仍可能否决候选报价；不把公式输出视为无条件可发送的订单。

| 阶段 | A：ETH / USDT | B：ETH / USDT | 确认 delta | 未决对冲 H | 预计残差 E |
|---|---|---|---:|---:|---:|
| 初始 | 10 / 100,000 | 10 / 100,000 | 0 ETH | 0 ETH | 0 ETH |
| A 买入成交 0.6 @ 1,999 | 10.6 / 98,800.6 | 10 / 100,000 | +0.6 ETH | 0 ETH | +0.6 ETH |
| B 卖出 0.6 的意图持久化、尚未成交 | 同上 | 同上 | +0.6 ETH | −0.6 ETH | 0 ETH |
| B 已卖出 0.4 @ 1,998，余量仍可能成交 | 同上 | 9.6 / 100,799.2 | +0.2 ETH | −0.2 ETH | 0 ETH |
| B 余下 0.2 也以 1,998 成交 | 同上 | 9.4 / 101,198.8 | 0 ETH | 0 ETH | 0 ETH |

`H` 是已持久化、尚未排除执行可能的对冲剩余量的有符号和，买入为正、卖出为负，包含 `UNKNOWN`。`E = delta + H` 仅用于避免重复规划，**不能代替实际库存或最坏风险**。B 尚未成交时，E 虽为 0，ETH 价格风险仍在。

主路径最后：

- 总 ETH 回到 `20`；总 USDT 为 `199,999.4`。
- 毛现金变化 `0.6 × (1,998 − 1,999) = −0.6 USDT`，忽略手续费。
- 数量对冲完成仍亏损，不能把初始买卖价差 `2 USDT/ETH` 当成本次利润。
- A 尚有买单 `0.4 ETH` 与卖单 `1 ETH` 的承诺，需撤换或继续管理；不是“对冲完成就没有任何挂单风险”。

### 1.3 主链路：从报价到可核对的收尾

```text
策略 owner 收到行情、账户/订单事实与风险配置
    ↓
校验输入〔场所序号连续性、接收年龄、价差/深度、成交水位、资金与配置版本〕
    ├─ 关键输入无效 → 阻止新扩险报价，申请撤旧单，继续接收成交与对账
    └─ 有效 → 计算公允 F、确认 delta、全部未决承诺与本所资金空间
                  ↓
生成候选 bid/ask/size〔偏斜、价差、精度、价格保护、Post-Only〕
                  ↓
本地事务：检查并占用预算，持久报价意图、clientOrderID、代次和发送任务
                  ↓ 提交后才发送
A 所接纳/拒绝/结果未知
    ├─ 拒绝且无成交可能 → 记录证据、释放对应承诺，重新评估
    ├─ 超时或断流 → UNKNOWN，保留承诺；按原身份查单补成交
    └─ 接纳 → 报价挂单；撤单、成交、部分成交由 A 的事实裁决
                  ↓
A 买单成交 0.6 ETH @ 1,999
                  ↓
本地成交事务〔唯一成交键、订单已观察量、库存/现金投影、处理位置〕
    A ETH +0.6，A USDT −1,199.4；确认 delta = +0.6
    同一事务重评未决对冲、持久必要计划/意图和 Outbox
                  ↓
报价反馈：按确认 delta 重算候选报价；旧代次未终结仍保留预算
对冲反馈：按 E 及最坏区间、B 的资金/深度生成卖出 0.6 的意图
                  ↓
B 适配器在意图持久化后发送受价格保护的子单
    ├─ 部分成交 → 每笔确认成交更新 B 库存，减少同笔未决剩余
    ├─ 超时 → UNKNOWN；查询订单与成交，不换身份盲目补单
    └─ 全成/可取证终止 → 集齐累计成交证据，消除对应执行可能
                  ↓
本例 B 合计卖出 0.6 @ 1,998，delta 回到 0，H 回到 0
                  ↓
核对 A/B 成交、订单累计量、资产变动、本地投影与来源归因
管理 A 余单：继续报价或撤销，并证明其剩余义务如何结束
                  ↓
报告数量对冲结果、−0.6 USDT 毛损益与仍存在的挂单/场所风险
```

每所自行完成链下成交及账户处理，本地要获取与成交相匹配的账务证据。私有回报、REST 成交查询和余额快照可能不同步；余额投影不能因为一次旧快照而覆盖新成交。本地 `FILLED` 也不等于观察到了全部资金处理或页面已刷新。

### 1.4 主要分支与失败窗口

```text
Post-Only 报价因触价被拒 → 当前行情重算，不原价无限重试
新报价预算通过，但旧报价在撤单中 → 两代同时计入承诺；预算不足则等旧代取证

撤单请求返回成功 → 检查其语义：已受理，还是已确认撤余量？
    已确认撤余量但累计成交尚未补齐 → 补成交再完成投影与释放
    更早发生的成交晚到 → 仍须入账，不以本地撤单时间拒绝

A 成交已发生、本地提交前崩溃 → 重放来源成交；唯一键防重，仍须触发未完成规划
本地成交事务成功、B 请求尚未发送 → 从持久意图/Outbox 继续
B 可能已成交、回包超时 → 保留 UNKNOWN 与预算，先查询原身份
B 仅部分成交后终止 → 保留已成交；取证并释放实际未成余量，再规划残差

B ETH 不足/深度不足/限频 → 不假定能卖空；缩减 A 风险侧、撤单、升级保护
A/B 数据源缺口 → 暂停依赖不完整状态的扩险决策；不能靠重新连接直接恢复
```

### 1.5 哪些“完成”不能混为一谈

| 阶段 | 已经成立 | 尚不能推出 |
|---|---|---|
| 本地意图持久化 | 身份、参数与预算可恢复 | 外部所接纳或成交 |
| 外部所接纳 | 订单获得场所内的执行资格 | 已成交、资金可自由使用 |
| 场所成交确定 | 原交易发生了资产义务 | 本地已投影、对冲已完成 |
| 本地成交事务提交 | 去重、库存和衍生意图一致推进 | 外部所副作用只有一次 |
| 对冲已全成且取证 | 本笔数量风险按成交降低 | 必然盈利、挂单清空、可忽略场所风险 |
| 对账完成 | 指定水位的订单、成交、余额可解释 | 未来不会再有成交或市场变化 |

## 二、核心板块

| 板块 | 决定什么、为什么核心 | 状态及上下游契约 |
|---|---|---|
| 行情与公允价格 | 报价是否在可用事实之上，而不是拿旧价接刀 | 发布带源序号、接收时间和质量的行情快照；不拥有成交真相 |
| 报价控制 | 决定价格、数量、存续与撤换 | 使用风险许可生成代次；每个外部订单独立跟踪，不以最新代次覆盖旧订单 |
| 库存与预算 | 决定真实敞口及还能承诺多少资产 | 成交投影、活动/待撤/未知剩余、场所资产桶；跨交易对共享余额需要共同裁决 |
| 成交一致性 | 决定一笔成交是否只更新一次、能否恢复 | 原始成交事实、唯一键、投影水位、计划与 Outbox 本地原子提交 |
| 对冲工作流 | 决定何时交易、交易多少及如何取证 | 计划、子单、稳定身份、部分成交和未知态；不能反向取消 A 的成交 |
| 保护与恢复 | 决定输入失效、过载、崩溃后是否扩大风险 | 模式版本、owner epoch、外部出口隔离、查单补成交及恢复门槛 |
| 损益与验证 | 决定策略到底在赚什么、哪里失效 | 统一标记价、费用/划转、成交后漂移和执行成本；不把模拟结果当实盘证据 |

## 三、核心 20%

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 有质量与水位的行情 | 报价前、重连后 | 价格正确先依赖输入正确 | 连接在线却持续按旧价挂单 | 缺口、快照衔接、接收年龄、偏离与可执行深度 |
| 价差、偏斜与尺寸联合约束 | 候选报价 | 控制利润来源与风险方向 | 只会套公式，越调越亏或超限 | 单位、舍入、逆向选择、Post-Only、缩量/单边暂停 |
| 确认敞口与未决承诺分离 | 报价、对冲前 | 未成交不是风险已消失 | E 为零就释放库存预算 | delta、H、双侧最坏区间、本所资金 |
| 原子预算与执行可能性 | 发单、撤换 | 并发及旧单仍能成交 | 旧单没撤完又花一次资金 | 新旧代次、未知单、跨 pair 共享资产 |
| 成交事实驱动本地事务 | 每笔 A/B 成交 | 资金与工作流必须同进退 | 库存更新成功但永远漏对冲 | 去重键、投影、意图、处理位置与 Outbox |
| 稳定外部身份与证据恢复 | 请求超时、部分失败 | 外部副作用不在本地事务中 | 换 ID 补单造成过度对冲 | client ID 语义、查询覆盖、累计成交与终态 |
| 有界 owner 与外部隔离 | Go 并发、主备 | 单写与恢复不能停留在进程内 | goroutine 顺序正确却重启双发 | 有界队列、持久水位、epoch、凭证/出口 fencing |
| 可闭合损益与时间外验证 | 评估迭代 | 高频成交不等于正收益 | 赚点差叙事掩盖滑点与尾损 | 统一 MTM、现金流、markout、排队、延迟和费用 |

“20%”表示优先掌握决定结果的机制，不按篇幅机械取五分之一；母题仍须完整覆盖这些机制。

## 四、共同设计与规则

### 4.1 库存、对冲与最坏区间

主案例以 ETH 为基币、USDT 为计价币，固定目标库存 20 ETH：

```text
Q = QA + QB                                  # 确认 ETH 资产，不是永续仓位
delta = Q - 20
H = Σ(未决对冲有符号剩余)                     # 买正卖负，包含待发送和 UNKNOWN
E = delta + H                                # 仅供规划，不作风险释放依据

Ubuy  = 所有仍可能买入的未确认剩余量之和        # A/B；含待撤、在途、UNKNOWN
Usell = 所有仍可能卖出的未确认剩余量之和
可达 delta 区间 = [delta - Usell, delta + Ubuy]
```

这里的剩余量以**本地已可靠纳入投影的成交量**为基准。可能已成交但回报尚未收到的量仍被区间覆盖；不能用新订单快照里的较小 `leavesQty` 先缩小承诺，却不补入对应成交。B 对冲也是 U 的一部分，不能先算入 U 再额外重复加 H。

若 A 的买单余量 0.4、卖单余量 1，B 卖对冲余量 0.6，当前 delta 为 +0.6，则保守区间为 `[-1.0, +1.0] ETH`。不能认为 A 双边单能同时成交而净额抵消，也不能假定 B 必然先成交。每次确认一笔成交时，要同步把该数量从未确认承诺转到确认库存；取证终止后才移除不能再执行的余量。

该区间管理数量风险，不保证价格跳变下的货币损失上限，不替代各所资产限制和流动性压力情景。数据缺口导致无法可靠界定执行可能性时，应升级保护而不是输出伪精确区间。

### 4.2 本所资产与预算规则

- A 买单依 A 的 USDT 承担限价本金与费用缓冲；A 卖单依 A 的 ETH。B 同理。
- A 多了 ETH，不代表 B 立刻多出可卖 ETH；B 库存耗尽需要预置补充或独立再平衡。
- 本地原子检查并占预算，是为了阻止自身并发发单透支；外部所的余额检查是另一道门，不应依靠反复被拒来实现资金管理。
- 选择一套口径：可从可信总资产减去全部已知外部锁定及本地未被外部锁定覆盖的承诺；也可从场所 `free` 再减尚未体现在该快照中的本地承诺。**不能从 free 再减一遍同一笔已反映的 locked。**
- 共享 USDT 的多个 pair 需要账户资产维度的原子预算服务或共同 owner；pair 单写不能自动解决账户共享余额竞争。
- 未知态、撤单中和新旧报价重叠继续占预算；TTL、断连和 owner 切换都不是资金释放证据。

### 4.3 报价规则与版本

报价使用确认 delta。本例 A 买入后 `r=1,994`，原始候选为买 `1,993`、卖 `1,995`；待 B 真正确认卖出后才逐步回归中性。这个较大的教学偏移仅用来展示方向和单位，仍要通过价格偏离、风险与场所规则检查，不表示应在真实市场按此参数发送。

`F` 是参考估值，不是 B 保证可成交的价格。计算对冲成本应看交易方向、足够深度、费用及限价保护。库存偏多时下移中心价通常让买价不积极、卖价更积极，但不保证自然卖出，也可能牺牲价格和收益。

每个候选绑定：`marketVersion`、`inventoryVersion`、`riskConfigVersion`、`quoteGeneration`、`ownerEpoch`。`quoteGeneration` 标识报价更新，不隔离旧进程；`ownerEpoch` 标识本地写权限，不撤销已发外部命令。版本也不能让已在外部挂着的旧报价自动失效。

### 4.4 架构、权威状态与交互

```text
A/B 行情适配器 ── 带质量与水位的快照 ──┐
A/B 订单/成交观察器 ── 原始证据 ──────┤
账户资产/配置输入 ── 版本化状态 ──────┤
                                       ↓
                  单逻辑 owner〔accountGroup, pair〕
                  报价决策 / 库存风险 / 对冲规划
                                       ↓
             本地数据库事务〔本地权威处理记录，不取代场所真相〕
             Inbox/Fill + Inventory + Orders/Intent + Budget
                         + ProcessedPosition + Outbox
                                       ↓
                    有界发送 worker / 速率预算
                        ↙                    ↘
                   A 报价 API             B 对冲 API
                        ↘                    ↙
                  查询、成交回报、订单与账户对账
                                       ↓
                       回到 owner 按证据推进
```

本地实现选择 PostgreSQL 事务、唯一约束与条件版本作为教学基线；不是要求每家交易系统采用同一数据库。计算内核用定点数，内存用于热状态和不可变读快照；可靠性来自持久事实，而非 goroutine/channel。

外部交易所不会接受本地 owner 的内部锁。已经发送的订单可能在本地停机后成交；主备恢复需约束旧出口/凭证，查询在途订单、补齐成交，再开放新风险。只拿数据库锁不能证明外部单写。

### 4.5 核心对象与身份

| 对象 | 必要字段与含义 |
|---|---|
| MarketSnapshot | 场所/交易对、源序号、接收时间、价档/深度、质量、版本；跨所序号分别维护 |
| Fill | `venue/account/tradeID`、orderID、方向、数量、成交价、费用及扣费资产、发生/接收时间 |
| InventoryProjection | 各所资产、确认 delta、输入水位与版本；余额快照替换须有可解释切点 |
| QuoteOrder | generation、clientOrderID、载荷摘要、场所 ID、原始/已观察成交/剩余量、执行证据 |
| HedgeIntent | intentID、来源成交/风险批次、目标方向数量、子单、剩余执行可能、状态与规则版本 |
| Budget | 账户/资产、归属订单/意图、占用来源、外部已覆盖量、版本；释放绑定确切证据 |
| Outbox/ProcessRecord | 事件身份、持久处理位置、待发送任务、尝试记录和 owner epoch |

本专题的 `tradeID` 指适配层按场所命名空间规范化后的成交身份；若原始 ID 只在交易对内唯一，应把 `pair` 纳入规范 ID 或唯一键，不能原样当作账户全局唯一。同一规范身份的载荷冲突进入隔离核验，不覆盖原事实。

对冲批次可覆盖多笔 A 成交，但保留可审计归因；一笔意图可有多个顺序执行的子单，不能用子单新 ID 掩盖原子单未决。client ID 是否支持幂等提交、保留多久、查询何时可见，必须按场所协议确认。

### 4.6 合法状态、提交和恢复不变量

订单应区分提交/查询知识与执行事实：可用 `PERSISTED → SEND_PENDING → LIVE/PARTIAL → FILLED/CANCELED/REJECTED` 描述主路径，`UNKNOWN` 表示对外部执行状态证据不足，不能当作“没有订单”。撤单申请不是终态，拒单也要确认是哪次操作被拒，不能把“撤单被拒”当成“原单从未存在”。

共同不变量：

1. 每个权威成交只应用一次；确认资产等于期初加成交、费用、明确划转与调整。
2. 原成交不可因对冲失败回滚；对冲是另一笔有独立资金约束的交易。
3. 本地成交去重、投影更新、必要计划/意图与可靠交付记录共同提交；失败全部回滚。
4. 未持久化意图不得发送；外部超时不得换身份盲目补单；Outbox 已发不是成交完成。
5. 撤单与终态的证据需和累计成交闭合，才可消除执行可能或释放承诺。
6. 已成交数量计入 delta 后，要减少对应未决剩余；不能同笔既扣持仓又扣一次预计残差。
7. 风控、恢复和人工处置不旁路写库存；所有调整记录原因、身份和证据。
8. 允许外部已成交、本地尚未观察等暂态，但必须有保守覆盖与恢复路径；禁止把暂态当无风险空档继续扩险。

### 4.7 Web3 变体的明确边界

如果把 B 改为 DEX 交易，必须重新定义授权、nonce、交易替换、滑点与最小输出、Gas、链上可见性、确认层级、回滚及重组。交易广播、入块和最终确认不能混为一谈；链上未知态也不能直接转成链下“未成交”。这些是改变执行与结算基线后的独立设计，本专题不在现货 CEX 答案中偷偷加入 AMM 储备或永续保证金公式。

## 七、工程实践：一个简洁 MVP

### 7.1 目标与范围

只手工验证一个闭环：**成交去重 → 确认库存更新 → 未决对冲占位 → 部分成交不重复规划 → 未知时保留执行可能。** 假定单 owner、内存顺序执行、无费用，输入为已确认成交、已取证终止和请求超时；H 用整数 ETH 最小单位表示。不实现真实持久事务、API、资金预算、行情、报价撤换或生产恢复。

下列已确认成交以样例显式输入；伪代码里的意图只是记录，不会真的发单。所有成交量必须为正整数单位且价格合法，B 成交必须关联本例已登记的意图，超时与终止输入也必须指向已知意图；无关或冲突输入先拒绝。乘积的计价精度、除法和溢出由读者按定点规则推演，`qty / 1000` 表示精确单位换算，不是截断整数除法，不用 float64 下单。

### 7.2 核心伪代码

```text
Qtarget = 20000                           # 1 单位 = 0.001 ETH
q = {A:10000, B:10000}; cash = {A:100000, B:100000}  # cash 展示为 USDT
seen = map(); intents = map(); nextID = 0
for event in inputs:                      # 同一事件的变化视为一个不可分割步骤
    if event is Fill:
        key = (event.venue, event.account, event.tradeID)
        if key in seen:
            require seen[key] == event.payload
            emit("DUPLICATE"); continue
        h = intents[event.intentID] if event.intentID else null
        if h != null:
            require event.venue == B and event.side == h.side
            require 0 < event.qty <= h.remaining
        seen[key] = event.payload             # 规范业务字段，不含接收时间
        sign = +1 if event.side == BUY else -1
        q[event.venue] += sign * event.qty
        cash[event.venue] -= sign * (event.qty / 1000) * event.price
        if h != null:
            h.remaining -= event.qty; h.filled += event.qty
            if h.remaining == 0: h.status = FILLED
    else if event is TerminalEvidence:
        h = intents[event.intentID]
        require event.cumFilled == h.filled
        require event.provesNoMoreExecution   # 外部给定证据；本例不实现查单
        h.remaining = 0; h.status = TERMINAL # 重复证据不再释放；已成交仍保留
    else if event is Timeout:
        h = intents[event.intentID]
        if h.remaining > 0: h.status = UNKNOWN   # remaining 不变；不回退已证实终态
    delta = q[A] + q[B] - Qtarget
    H = sum((+1 if h.side == BUY else -1) * h.remaining for h in intents)
    E = delta + H
    if E != 0:                               # 简化为逐笔立即规划，无阈值
        nextID += 1
        intents[nextID] = {side: SELL if E > 0 else BUY,
                           original: abs(E), filled: 0, remaining: abs(E), status: PERSISTED}
    emit(q, cash, delta, intents)             # 没有外部成交就不修改库存
```

这段代码刻意不把 `E=0` 当作风险释放，也不声称已实现“可靠交付”。无资金和最坏区间检查，不能直接接 API；若未知卖单期间又发生反向成交，它可能规划一个反方向意图，生产系统必须先按第 04、07、08 题限制或撤销旧执行可能，不能照搬本简化策略同时双发。
