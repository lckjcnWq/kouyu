# 大问题 5：重复、乱序、缺口与回补怎样不污染规范状态？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| stream／event_id | 先确定哪条源业务流，再确定流内哪一次事件。 | Q1 身份由 source、instrument、channel、native_epoch、native_seq 构成，不用时间或连接号替代。 |
| native_epoch | 上游原生序号所属命名空间的世代。 | 必须有协议证据才能更换；本地重连或看到序号变小均不能自行判定换代。 |
| connection_generation／sync_generation | 一项标记连接生命周期，一项标记本地同步尝试。 | 都不等于原生 epoch；旧同步响应不能覆盖新同步状态。 |
| Raw hash／稳定业务摘要 | 一个核对收到的字节，一个核对事件真正表达的内容。 | 摘要排除接收包装；允许的等值数字文本不算冲突，身份相同而业务不同必须隔离。 |
| last_seen_seq／last_applied_seq | 最高看见哪里，以及连续、合法应用到哪里。 | 看见 103 不代表已越过缺失的 102；接收高水位不能冒充连续进度。 |
| GAPPED／QUARANTINED | 前者表示原生顺序缺了一段，后者表示内容或语义冲突待裁决。 | 都使源不能贡献候选；好看的新价格、重连和心跳不能自动恢复资格。 |
| canonical_emit_seq | 规范报价与失效、恢复控制共用的内部交付顺序号。 | 不等于 native_seq；接收方按期望号去重和补齐，未来号先暂存并保守阻断源。 |
| REST 回补／repair_id | 通过另一个接口找回指定范围事件，并标记这次修复请求。 | 返回必须属于同一原生流并验证覆盖；HTTP 200、最大序号和条数都不证明完整。 |
| 有界待处理区 | 暂存还不能连续应用的事件，限制条数、字节和等待时长。 | 满了就保持不合格并受控转同步，不无界堆积，也不删掉持久 Raw 冒充已修复。 |
| snapshot_seq | 权威快照声明覆盖到的源序号边界。 | 需按协议衔接后续事件；新基准恢复当前状态，不等于补回被跳过的历史。 |
| 源裁决事务／Outbox | 把身份裁决、状态、处理位置与待发事实一起提交。 | 提交前重做、提交后补发；不承诺与外部源及聚合端形成全局事务。 |
| READY／revision | READY 表示同步依据成立；revision 是明确纠错的历史更正版。 | READY 后仍可能陈旧；普通回补不修旧轮，显式更正也不改原 T、cut 或延长期限。 |

## 把整篇文章压缩成一个故事

阿远的源处理器已应用 101，先收到完整 BBO 103。虽然包里买卖两边都有，教学协议仍要求序号连续，所以他记录缺失 102、把源置为 GAPPED，并持久发送失效控制，不让聚合继续借用 101。103、104 留在有界待处理区，REST 补回的 102 也先存 Raw，再交同一负责人核验；合法时依次应用到 104，随后实时重发的同一 102 不再推进，若内容不同则隔离。回补的请求世代、原生 epoch 与本地连接世代各管各的，旧响应不能倒退新同步。若缓存超限或历史不可得，只有带明确衔接边界的权威快照才能建立新基准，不能把失去的历史说成补齐。每次裁决把状态、连续位置、输入进度和 Outbox 一起提交，失效与恢复按同一内部序列交付。恢复 READY 还要另查时间新鲜度，普通迟到只进以后轮次，不能借修订复活旧轮。阿远最后核对真实 API 的身份与顺序能力：全市场跳号未必是本频道缺口，没有稳定身份也不能拿本地编号冒充完整去重。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于 Raw 已持久之后、可信 canonical 进入聚合之前。源分区单 owner 负责逻辑身份、稳定业务摘要、协议顺序、缺口和恢复边界；market 单 owner 只消费这些持久事实，不自行猜测源是否连续。重点是“同一事件是什么”“什么时候缺了一段”“补回的记录凭什么恢复可信状态”，不把本题扩写为增量盘口重建专题。

**必要前提：** 主例为 CEX 现货 `ETH/USDC` 的完整 BBO 绝对值观测，一条观测同时包含 bid、ask 和两侧数量，价格为 `USDC/ETH`、数量为 ETH；买卖价和数量均为正，`bid<=ask`。`price_scale=10^6`、`qty_scale=10^8`，由十进制字符串精确解析，超出 scale 拒绝，乘加使用宽整数并检查溢出，`mid_int=floor((bid_int+ask_int)/2)`。

教学协议明确规定：每个 `stream=source+instrument+channel+native_epoch` 的 `native_seq` 连续；发现断档立即进入 `GAPPED` 并退出候选，经有界补齐或有依据的权威新快照同步后才能恢复。这个假设不能推广到所有交易所 API；若真实协议的序号不是本频道连续序号，必须另定适配契约。连接重连世代不重置源原生 epoch，也不重置去重身份。硬质量状态为 `SYNCING / READY / GAPPED / QUARANTINED`，源新鲜度和轮次离群另判。

共享轮次 T 的 A—E 均已进入冻结可见前缀，配置为五个独立组：A 为 `1997/1999，mid=1998，age=100ms`；B 为 `1999/2001，mid=2000，age=120ms`；C 为 `2001/2003，mid=2002，age=80ms`；D 为 `2399/2401，mid=2400，age=100ms`；E 为 `2000/2002，mid=2001，age=5000ms`。`age=T-source_event_time`，只有 `0<=age<=2000ms` 且时间可信才有时间资格，future、未知时间和时钟质量不明硬排除。E 陈旧，A—D 一次中位数为 2001，超过 1% 偏离剔除 D，A/B/C 满足至少三源、三个独立组，等权结果为 2000。包质量为 `VALID`，失败则 `UNAVAILABLE`、`price=null`；合法包 `valid_until=min(T+1000ms, 每个贡献源的 source_event_time+2000ms)`，仅 `now<valid_until` 可实时消费，旧价只作独立 `last_good` 展示。

```text
采集器 → 持久 Raw〔原始字节、来源、接收信息、hash、位置〕
    ↓
源分区单 owner：身份与业务冲突裁决 → 原生顺序和缺口裁决
    ├─ 连续且合法 → canonical + READY 所需证据
    ├─ 缺口 → GAPPED 控制 + 有界等待或回补
    └─ 身份冲突 / schema 冲突 → 隔离和失效控制
    ↓
REST 结果也回到同一 owner，不绕过它直接写最新行情
    ↓
market owner 冻结持久输入前缀 → 每源至多一个可信候选
```

## 第 1 层：事件身份应该由哪些字段组成？

**面试官：** 多源行情怎样定义事件身份，才能在重复、重连和 REST 回补时认出同一份 BBO？

**面试者：** 我会优先使用源协议定义的稳定身份。主例里一个逻辑事件的身份是 `event_id=(source,instrument,channel,native_epoch,native_seq)`；前四项定义 stream，最后一项定义其中的事件。`instrument` 是经过市场契约确认的源市场身份，不能只用展示字符串 ETH/USDC，因为现货、永续、不同报价资产或不同频道可能使用相近名称。映射到内部 market 时保留市场定义和映射版本，不能把多个源事件压成一个仅有 market 和时间的 ID。

连接编号、WebSocket 订阅编号、采集进程启动时间、Raw 日志位置只描述一次运输和落盘，不是源事件身份。比如同一 stream 的 seq 120，先在连接 `conn-7` 收到，重连后在 `conn-8` 又收到，仍然是同一个逻辑事件。每次接收可以各自留下不可变 Raw，但源 owner 只能让它作为同一逻辑事实推进一次状态。

`native_epoch` 也不能用“本地重连次数”代替。它来自源协议的真实序号命名空间变化证据；如果协议没有提供可确认的 epoch 变化，连接断开不能授权本地把 seq 清零后视为新流。否则同一旧事件重发就会变成“新事件”，真正序号复位也可能与旧数据碰撞。我会把 epoch 依据作为源契约的一部分，无法确认时先同步或隔离，而不是猜测。

## 第 2 层：同一个身份重复出现，怎样区分重发和冲突？

**面试官：** 你固定了逻辑身份，但 REST 和 WebSocket 的外层字段不同。同一个 seq 收到两次时，怎样判断是正常重复还是源内容冲突？

**面试者：** 我会为同一逻辑身份比较稳定业务内容摘要，而不是比较整个传输包，也不是只比较 Raw hash。业务摘要覆盖该源事件所定义的业务事实，例如源市场身份、bid、ask、两侧数量、源事件时间及必要业务标志；字段选择和规范化方式由 `business_hash_schema` 明确。接收时间、连接 ID、请求 ID、压缩方式、HTTP 头和采集位置都不进入摘要，因为这些字段在正常重发时就会变化。

例如 seq 120 的 bid 字符串先是 `1999.000000`，后是 `1999`，若协议允许这两种等值表示，精确解析后得到同一个价格整数，不能仅凭字节不同判冲突。两次 Raw hash 可以不同，业务摘要却相同。原始证据仍全部保留，canonical 用稳定 `event_id` 关联它们。映射版本属于处理依据，不能因为后来升级映射就把源原本相同的一次事件误判为源发出了两份业务内容；真正的历史重算应另记修订依据。

如果同一 event_id 的 ask 从 2001 变成 2011，或者事件时间改变而协议并未定义可变字段，我会记录 `IDENTITY_PAYLOAD_CONFLICT`，保留两份证据，隔离该身份并使受影响源状态不可贡献，通常进入 `QUARANTINED` 等待裁决。不能用最后写入覆盖先前值，也不能说“价格更晚收到就更真”。冲突通知必须能使已有候选失效，而不只是把第二条丢进旁路日志；但已经发布的轮次仍不能原地覆盖，纠错走追加 revision。

## 第 3 层：完整 BBO 也必须因为序号缺口停止贡献吗？

**面试官：** 你能识别重复了。现在源已经应用 seq 101，却先收到完整 BBO 的 seq 103；它不是盘口增量，为什么不直接用 103？

**面试者：** 在本题教学契约下仍然不能直接用。这里明确要求这个 stream 的 native_seq 连续，缺口代表当前同步与数据完整性承诺被破坏，而不只是“无法对盘口做加法”。完整 BBO 说明 103 自己包含完整买卖一档，并不自动证明它具备协议授权的重新同步资格。因此 owner 发现期望值是 102、实际收到 103，就把源从 `READY` 改为 `GAPPED`，记录缺失范围 `[102,102]`，对聚合发出失效控制。

我会区分 `last_seen_seq=103` 和 `last_applied_seq=101`，把 103 放进按序号索引的有界待处理区，不让接收高水位冒充连续应用高水位。若 102 随后到达且身份、内容、schema 都合法，就依次应用 102、103；确认连续后可以恢复 READY，并把 103 的完整 BBO 作为最新状态。主例不额外要求连续成功三次或等待一秒，不能悄悄加恢复门槛。

如果另一个真实 API 规定“每个完整快照都可独立替代旧状态，seq 仅是全市场计数”，那必须显式改变源契约，而不是照搬本题的 `[102,102]` 缺口推断。本题先遵守已经声明的连续序号模型；究竟允许跳过缺口还是必须补齐，是协议和产品保证决定的，不是看包看起来完整就自行决定。

## 第 4 层：缺口状态怎样及时撤掉已经发布给聚合的源候选？

**面试官：** 你已经把源改成 GAPPED，但聚合缓存里可能仍有 seq 101 的好价格。如果只有 canonical 正价事件才往下游发，怎么保证它真的退出？

**面试者：** 缺口本身必须是聚合可消费的持久控制事实。源 owner 在处理 103 时，提交 `source_status=GAPPED`、`last_applied_seq=101`、缺口区间、103 的待处理引用、当前源状态失效记录、输入 cursor 和 outbox；这些放在同一个 DB 事务中。这样事务提交后，既不会只有状态变更而通知永久丢失，也不会已经越过 103 的输入位置却忘记缺口。

控制事件需要包含 `stream`、`source_state_generation`、`reason=SEQ_GAP`、缺口范围和证据位置。源事务为 canonical 与质量/控制事件分配共同连续的 `canonical_emit_seq`，它是下游交付序号，不是源的 native_seq。Outbox 按源分区串行，前条被 market Inbox 持久接纳后才发下条；接收方用 `expected_emit_seq` 去重并检验顺序。若异常收到未来 emit 序号，先 pending 并保守阻断受影响源，补齐后才按序应用，不能让旧 READY 盖掉新 GAPPED。

某轮前缀包含缺口控制，就不能回退到 seq 101 顶替；如果该轮前缀在控制之前，只能按当时可见事实决策，不能事后假装早已知晓缺口。下一轮即使没有新正价，也应因失效控制重新计算，有效源不足时输出 `UNAVAILABLE`、`price=null`。补齐后也由同一 owner 发出更高状态代际的 READY 及其 canonical，按同一交付序列衔接。READY 只说明连续与质量证据恢复，是否陈旧仍按该轮 T 计算；刚补齐的 seq 103 也可能已是几秒前的旧观测。

## 第 5 层：REST 回补接口需要承诺什么，才算补齐了缺口？

**面试官：** 既然恢复需要真实补齐，那调用一次 REST 查到一些记录，就足以宣布缺口解决吗？你会怎样定义回补契约？

**面试者：** 不足以。首先要确认这个 REST 接口确实能返回同一 stream、同一 native_epoch、同一频道语义下的原生事件，而不是只有“当前 ticker”或按时间聚合的 K 线。对 `[102,102]` 的回补，我会记录 `repair_id`、目标 stream、epoch、请求范围、请求时的同步代际 `sync_generation` 和协议版本。接口返回的事件身份和业务摘要必须能按与实时流相同的规则验证，不能给 REST 人造另一套 seq 来填洞。

若 API 支持按序号区间查询，契约要说明端点是否包含、页游标的稳定性、结果是否可能重叠、是否声明区间完整，以及历史保留范围。响应即使 HTTP 200，也可能只有部分记录；最终是否补齐，应由 owner 维护的缺失区间和逐条身份验证决定，而不是“请求成功”决定。比如请求 `[102,110]` 返回 102、103、105，104 仍是缺口，不能用页面条数或最大 seq 110 替代覆盖证明。

如果接口只支持按时间查询，事件时间相同、回退或边界截断都可能漏记录；除非协议另有足够的覆盖证明，不能据此承诺原生序号区间已完整。若源没有可验证的事件回补能力，就明确走权威新快照同步，或者保持 GAPPED，而不是编造 REST 具备的能力。回补命令和响应都保留原始证据，网络工作线程只负责拉取，是否恢复仍由源 owner 裁决。

## 第 6 层：回补和实时流同时返回相同或交错的事件怎么办？

**面试官：** 你要求 REST 也经过源 owner。那么实时 102、REST 102 和实时 104 同时到来，怎样汇合才不会重复推进或错过缺口？

**面试者：** 我会把所有入口统一成持久 Raw 输入，再由同一个源 owner 串行裁决，不让 REST 工作线程直接改 `last_applied_seq` 或写最新价。假设当前已应用 101，待处理区已有 103，owner 先处理实时 104，就把缺失范围保持为 `[102,102]`，缓存 104；随后 REST 102 到达，验证通过后按 102、103、104 连续排空，最后 `last_applied_seq=104`，才有条件恢复 READY。

若实时 102 随后出现，同一 event_id、同一业务摘要就按重复处理，不再推进第二次，也不增加一个“独立观测票数”。若实时 102 与 REST 102 的业务内容不同，则进入身份冲突隔离，不能因为 REST 来自“补数据接口”就天然更权威。回补的传输来源只解释证据怎么来的，不改变同一个源事件必须有稳定业务事实的要求。

REST 分页重试也沿用这套身份规则，页与页重叠没有问题，缺页则仍不能恢复。并发请求的响应要校验 `repair_id`、epoch 和同步代际，过期请求不能把新同步会话的游标倒退。即使补齐最终产生了最新 104，聚合也只在冻结前缀里取该源最新可信 BBO 的一个候选，不会把 102、103、104 都送进中位数当三份来源。

## 第 7 层：缓存放不下，或者历史已经无法补回，怎样安全切快照？

**面试官：** 你把 103、104 都缓存了，但 102 一直补不回来，后续事件不断到达。内存不能无限增长，该怎样退出等待？

**面试者：** 我会给乱序待处理区设置事件数、字节数和等待时长上限，同时限制 REST 回补范围与并发。比如教学上的独立容量示例可以设最大待处理 1000 条、8MiB、等待 2s；这些是明确示意的容量策略，不是声称实测值，也不改变主例 age 阈值。达到任一上限就记录原因、停止无界堆积，并进入新的快照同步尝试；此时依然不能贡献价格。Raw 已经持久，丢弃的是可重建的内存索引或失效同步代际的待处理视图，不是删掉原始证据。

快照必须具备可校验的同步契约。例如权威响应给出同一 stream、同一 epoch 下的完整 BBO 和明确边界 `snapshot_seq=150`，并说明它覆盖至该序号的状态；owner 记录 `snapshot_id`、原始证据、`sync_generation` 和边界，把 150 作为这次同步的新基准，丢弃这个同步视图中不再需要的低序号等待项，然后只衔接满足协议关系的 151、152。这个动作是在协议授权下重建连续状态，不是伪称丢失的 102—149 都已补到。

若所谓快照只有“现在的 bid/ask”，没有序号或其他可建立流边界的标记，就不能和带 seq 的实时流安全拼接。必须依赖源提供的原子订阅快照、边界 token 或其他明确机制；没有机制就保持不可用。这些是完整 BBO 的同步接口边界，不在这里展开逐档订单簿重建。新快照已经具备可信状态时，主例允许直接 READY，不附加未声明的恢复防抖。

## 第 8 层：重连、epoch 变化和旧回补响应怎样隔离？

**面试官：** 你给快照加了同步代际。如果期间连接重建，旧 REST 响应晚到，甚至源真的重置了序号，怎样避免旧结果污染新状态？

**面试者：** 我会把三种代际分开：`connection_generation` 只标识传输连接；`sync_generation` 标识本地正在执行的同步尝试；`native_epoch` 标识源原生事件身份的命名空间。重连只改变第一项，不能凭它修改第三项。比如同一 epoch 下已应用 seq 150，换连接后重发 149，仍是旧事件，不是新价格，也不能刷新 age。

旧同步尝试 `sync_generation=7` 的快照在当前第 8 次同步时到达，不能再据此提交 READY 或回退同步边界。里面若有可验证的同 epoch 原生事件，可以按当前策略作为历史证据或经正常身份路径处理，但“这是旧响应”绝不授权直接覆盖当前状态。若其中出现同 id 异内容，仍需记录冲突，而不是为了忽略旧任务就掩盖证据。

真正 native_epoch 改变必须有源协议证据，例如明确的会话 epoch token 变化；owner 记录旧 stream 关闭和新 stream 同步控制，再为新 stream 建立可信基准。旧 epoch 的迟到事件可以留下历史证据，但不能更新新 epoch 的当前投影。对于没有 epoch token、又可能重置序号的 API，不能凭 seq 变小就猜出了重置；要按其协议重新同步和确认命名空间，无法确认时隔离。心跳和连接成功最多证明通道在工作，不证明缺失历史已补齐或当前 BBO 已可信。

## 第 9 层：owner 在应用回补和恢复 READY 之间崩溃怎么办？

**面试官：** 你已经区分各种代际，但 owner 可能刚写入 canonical 就崩溃，还没写 READY 或推进游标，恢复后会不会出现重复和半恢复？

**面试者：** 我会把源侧一次裁决的关联状态放在同一个 DB 事务：事件身份与业务摘要判定、源状态、连续应用位置和缺失区间、canonical 或失效控制、输入 cursor、待交付 outbox，以及恢复所需的同步元数据。若待处理体量较大，可以只在事务里保存已持久 Raw 的引用和有界索引，但不能让唯一副本只存在于内存。采集 Raw 的持久边界在前面，源事务不会宣称和外部交易所或整条消息系统形成一个大事务。

例如处理补回 102 时，事务把 102—104 的合法推进结果和最终 READY 状态一起提交。提交前崩溃，cursor 未前进，重启后从原 Raw 位置重做；提交后崩溃，身份记录和 cursor 已在，outbox 仍可续发，不会重新创造一份业务事件。如果一段回补需要分批提交，则每批都保留准确的 `last_applied_seq` 与缺口状态，在真正闭合前不提前 READY，最后恢复必须引用已经提交的 canonical。

market owner 还要把聚合状态、round/revision、输入 cursor 和 outbox 放在它自己的 DB 事务里。这是两个 owner 各自的本地原子边界，靠可重试交付和稳定身份衔接，不能说源数据库提交就等于所有聚合轮次已更新。普通迟到或回补只进入后续轮次，不能给旧冻结轮追加候选以恢复有效性。源撤回、映射纠错等显式更正才生成 revision，保持原 T、原观测 cut 和原 manifest，追加 `correction_manifest`、纠错引用及 `supersedes`，可重算受影响候选和值，但不覆盖原记录、不延长当前有效期限。缺口、隔离或过期即使没有新正价，也应形成可交付的失效或不可用结果。

## 第 10 层：真实 API 不满足连续 seq 时，这套设计还有哪些保证？

**面试官：** 你把主例的闭环讲通了。若换成只有时间戳、全市场递增 ID 或更新区间的真实 API，能否继续宣称完整去重、检测所有缺口和任意顺序重放一致？

**面试者：** 不能，必须先把协议能力说清。只有时间戳时，同一毫秒可能有多条不同事件，重发也可能重新带服务器时间，不能用 `source+timestamp` 自动得到可靠逻辑身份。内容 hash 可以用于识别部分相同载荷，但同样的 BBO 可能是两个真实观测，不能据此证明事件唯一或序列完整。如果没有稳定事件身份，我会明确降低保证，或要求额外的协议证据，不把本地递增号伪装成源去重身份。

全市场 seq 在单品种频道里天然会跳号，不能照本题把每个跳号都判 GAPPED；更新区间协议则可能以 `first_seq / last_seq / prev_seq` 判断衔接，而不是逐条加一。独立完整快照协议也可能允许每个新快照重建可信当前状态。每个适配器应记录自己的 `sequence_semantics`、`identity_semantics` 和恢复依据，再向聚合提供统一的可信状态及原因，不让“统一 schema”掩盖保证不同。链上日志、最终性和重组不是本题主例，若接入应作为独立变体另定身份与撤销契约。

我能承诺的是同一持久 Raw/控制历史、规则版本、输入顺序和轮次 T 下重放相同，而不是任意到达顺序具有相同中间历史。手工检查可以从 101 开始输入 103、REST 102、重复实时 102，预期先 GAPPED、再连续到 103、重复不推进；把最后一条 102 改成异内容，预期隔离而非覆盖；让旧 epoch 的快照在新 epoch 同步后返回，预期不得复活旧状态。不同 marker 边界可能留下不同中间轮次，这不应被错误的“最终一致”口号抹掉。

## 收束：机制、易错边界与反例

**机制：** 源原生身份与稳定业务摘要解决“是否同一件事”；协议连续边界与缺口区间解决“是否少了一段”；REST 和快照通过同一源 owner 验证和汇合；同步代际、原生 epoch 和本地事务共同约束恢复的适用范围。canonical 保留来源、市场定义、映射版本及原始 hash 和位置，原始证据不覆盖。

**易错边界：** Raw hash 不等于业务冲突摘要；连接重连不等于源 epoch 重置；完整 BBO 不自动免除本题连续性承诺；HTTP 200 不证明区间补齐；较大 seq 不证明中间无缺口；READY 不保证新鲜；最新源状态失效后不能借用旧好价；时钟未知、schema 冲突和身份冲突不能靠补齐序号洗白。

**反例：** 源已应用 101，先见 103，随后重连把本地 epoch 加一并直接发布 103，最后 REST 返回 ask 不同的 102。这个实现表面上拥有较新价格，却同时逃避了缺口、破坏了去重身份并掩盖内容冲突。正确做法是先 GAPPED，保持原 native_epoch，经同一 owner 验证 102；发生冲突就隔离，不以重连、last-write-wins 或新接收时间恢复可用。
