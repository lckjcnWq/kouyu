# 大问题12：怎样演进规则并证明系统没有静默失真？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 不可变规则包／rule 摘要 | 保存完整计算口径，并用内容摘要定位具体版本。 | 覆盖解析、尺度、筛选、组数、权重、取整和 TTL；只写 v2 或随时读配置中心不够。 |
| ACTIVATE marker | 持久输入中宣布一套规则从此处起生效的控制记录。 | 与 active_rule、cursor 事务绑定；回滚也追加记录，旧轮不变，单市场不等于全市场同时切换。 |
| schema／语义兼容 | schema 是字段结构，语义兼容则要求字段经济含义仍能正确使用。 | 可解码不等于单位、独立性或新鲜度规则兼容；新字段未知不能填零凑合。 |
| 影子比较／shadow 权限 | 同一输入与采样时刻下运行另一规则，但不影响生产。 | 只改变声明变量，隔离状态和写凭证；结果更好看也无权激活或写生产 Outbox。 |
| bp／Q2 阈值 | 基点是百分之一的百分之一；Q2 是独立收紧阈值的教学变体。 | 100bps 为 1%，10bps 为 0.1%；Q2 主例只剩 B/C，不足三源三组而不可用。 |
| source-age／receive-age | 报价事实有多老，以及本地收到这份证据距采样多久。 | 重投可让收包指标活跃，但不能刷新源事件时间；未来或未知时钟不能由接收时间洗白。 |
| 语义 SLO | 不只看进程在线，而看有效使用、完整性、交付和可用性的服务目标。 | 分母包含约定市场和时段或独立采样，不只数成功出包；安全错误不能被高成功率抵消。 |
| valid_until／last_good | 固定使用截止，以及独立展示的历史好结果。 | 实时还需前缀完整、规则满足和时钟可信；旧价展示不计当前可用，等于截止已不可用。 |
| 连续进度／安全阻断 | 处理完整前缀的位置，以及已知必须先收紧的限制。 | 未来失效先持久阻断，补旧有效消息不短暂放行；源交付序号不证明外部全史完整。 |
| 故障矩阵／不变量 | 列出注入点、前态、预期状态与应一直成立的规则。 | 没有 panic 或告警图标不是通过证据；本文是设计推演，不声称做过故障演练。 |
| revision／correction_manifest | 显式历史更正版与纠错依赖清单。 | 保留原 T、cut；有旧截止只收紧，无旧可用截止则至多原 T，历史修订不恢复实时资格。 |
| 保留窗口／最小权限 | 保存证据的有限期限，以及只授予任务必要的读取或写入能力。 | 删除须同步降低恢复承诺；不把密钥、鉴权头和高基数身份散播进 Raw、指标或影子环境。 |

## 把整篇文章压缩成一个故事

规则负责人小许准备把离群门槛从 1% 收紧到 0.1%，没有直接改线上配置。她冻结同一前缀、T 和源状态，在隔离影子中配对比较：中位数仍为 2001，A 差 3 也超新门槛，只剩 B、C，故 Q2 不可用，而 Q1 仍是 2000。这是可解释的可用性变化，不是差异越小越正确；影子也没有生产写权。审批后由合法负责人追加生效记录，后续轮次才冻结完整新组合，回滚仍追加记录，不复活旧价。上线监控分别看源年龄、接收年龄、各段持久进度、失效传播和截止，避免高速重播旧报价把健康刷绿；可用性分母还要覆盖完全没出包的时段。后来发现分组资料错了，即使价格没变，小许仍先关闭受影响资格，固定证据，再隔离复现、修复并以新轮恢复；历史更正保留原切面且不续期。她把原因补进故障矩阵，核对撤回消费证据与恢复边界，同时按最小权限和保留窗口处理原文，绝不把测试设计说成实测通过或为了审计永久散播秘密。

**流程位置与核心机制：** 本题覆盖规范规则与聚合规则的版本化、持久生效 marker、影子比较、语义可观测性、故障验证及证据保留。重点不是让进程一直存活，而是能回答“这一轮为什么取这些源、按哪套规则算、何时失效、改规则后是否改变产品语义”。第10题的交付事务和第11题的确定性恢复是本题所依赖的基础，本题不另建工程或执行测试。

**必要前提：** 产品是 CEX 现货 ETH/USDC BBO 完整绝对值观测的聚合参考，不是 Mark、可成交报价或强平许可。源状态使用 `SYNCING/READY/GAPPED/QUARANTINED`，产品质量使用 `VALID/UNAVAILABLE`；陈旧与本轮离群作为原因，不作为永久源状态。主协议假设同一 `source+instrument+channel+native_epoch` 内 native_seq 连续，其他协议另述其完整性证据，连接世代不等于 native_epoch。

公共 Q1 为：T 的持久可见前缀内 A=1997/1999、mid=1998、age=100ms；B=1999/2001、mid=2000、age=120ms；C=2001/2003、mid=2002、age=80ms；D=2399/2401、mid=2400、age=100ms；E=2000/2002、mid=2001、age=5000ms；五个源分别属于五个独立组。按 `0<=T-event_time<=2000ms` 排 E，只求一次中位数 2001，用 `abs(p-m)*10000>m*100` 排 D，至少三源三组才对 A/B/C 等权平均 floor 得 2000，否则 `UNAVAILABLE, price=null`。价格与数量分别使用 `10^6/10^8` scale，精确字符串解析、超 scale 拒绝、宽整数检查。

## 第1层：规则升级必须保留哪些可解释的事实

**面试官：** 这个系统能输出 2000，进程也没有报错。以后调整异常阈值或源分组时，怎样知道新旧结果变化是规则预期，还是系统在静默算错？

**面试者：** 先让每个结果绑定完整决策证据，再谈监控。只有最终价格和一个 `v2` 字符串，无法区分输入变化、配置漂移和计算错误。每轮应冻结 T、持久输入前缀 vector、实际候选与排除、源分组和时钟质量配置；结果保存 `{product_id,round_id,revision,T,rule,vector,candidates/exclusions,group,quality,price,valid_until,supersedes}`。

`rule` 应能定位不可变规则包和内容摘要，覆盖解析语义、scale、溢出处理、新鲜度、一次中位数约定、离群阈值、最少源/组、权重和取整、TTL，以及依赖的规范规则和执行语义版本。源分组、时钟质量也要有不可变版本，不能只记录“读取了配置中心”。同一编号的规则内容不允许被后台原地覆盖。

Q1 的证据链应显示：E 因源事件时间陈旧被排除；四个 mid 求一次中位数 2001；D 超过 1% 被排除；A/B/C 分属三组；floor 平均为 2000；有效截止为 T+1000ms。若程序虽然输出 2000，却错误地把 E 当作贡献源或把 D 的排除归因于格式错，语义仍然不正确，不能因为价格巧合相同而放过。

先定义这些不变量，才能对新旧版本比较“相同输入下的决策差异”。这是用证据区分预期变化与缺陷，而不是让监控阈值替产品规则作裁决。

## 第2层：跨进程升级，怎样保证同一轮不会读到半套新配置

**面试官：** 你把版本绑到结果了，但源 owner、market owner 的进程不可能同时升级。如果配置中心在 T 前后修改，怎样保证一轮不混用旧阈值、新分组和新时钟规则？

**面试者：** 生效点应是持久有序输入中的 marker，而不是各进程看到的墙上时钟。先发布不可变规则包并校验执行器支持，再由合法 owner 将包含 `change_id`、目标规则摘要、分组/时钟版本、兼容前提和预期前序版本的激活 marker 追加到 market Inbox。

```text
不可变新规则包就绪
  → 前置条件检查与影子验收
  → 合法 owner 追加 ACTIVATE marker
  → market 按持久顺序消费 marker
  → active_rule 与输入 cursor 同事务提交
  → 后续轮次 marker 一次冻结完整新规则组合
```

轮次 marker 的位置决定它使用哪套 active_rule；不允许一轮中途刷新配置。生效 marker 和轮次结果都能在重放中再次定位，提交失败则整体不生效。已有轮次保持原 manifest；回滚也是追加新的激活 marker，恢复未来语义，不删除新规则历史，也不重写旧结果。规则恢复不意味着上一版本的历史价格重新获得有效期，仍需新轮次和原始事件时间约束。

普通旧回补不向历史轮次补观测；新鲜数据改变观测 cut/T 时开新轮。输入撤回、映射纠错等历史修订则保留原 T 和原观测 cut，追加 correction manifest、持久纠错输入引用、新规范解释与 supersedes，可以重算候选、分组和值，但原 manifest 仍不可变。更正后仍不可用则 price=null、无可用截止；更正后历史合格时，被 supersedes 指向的旧版若有可用截止，取旧截止与按原 T、纠正后依赖重算截止的最小值；旧版若不可用、无可用截止，则新截止至多原 T，只修订历史而不恢复实时使用。连续修订沿用该分支收紧期限，历史高 revision 也不回退更新的当前轮次；当前恢复另开新轮。

若变化涉及源规范 schema，源侧也要有自己的流内版本边界，canonical 带上 schema/规范语义版本。先部署可识别新旧 schema 的读端，再在源流有序切换；market 激活前验证所需源的准备证据和输入前缀。缺少兼容证据时维持旧规则或明确 UNAVAILABLE，不能把无法解释的新字段当成零。需要全市场原子切换时还要单独设计跨 market barrier，本模型的单 market marker 不自动提供全局同时性。

结构兼容只说明字段可解码，不说明语义兼容。把“参考价”改成“可成交价”、改单位、改组独立性或允许更陈旧来源，都需要产品契约审查；不能因为 JSON 没改字段就默认为安全。取舍是升级需要前置准备和边界证据，但避免滚动部署期间出现无法复现的混合规则。

## 第3层：影子结果不同，怎么判断该放行还是回滚

**面试官：** 你先做影子验收。假设 Q2 把离群阈值从 1% 改成 0.1%，影子结果与 Q1 不同，是不是差异率越低越好？影子能否顺手把更好的价写回生产？

**面试者：** 都不能。影子要消费相同持久输入、相同 T、相同前缀与源状态证据，只在声明的规则变量上不同；如果影子用更晚到达的数据、当前配置或当前时间，差异没有可比性。差异先按原因分类，而不是把所有差异压成一个百分比。

在这个独立 Q2 变体中，只把阈值参数从 100bps 改成 10bps，公式变为 `abs(p-m)*10000>m*10`。E 仍先被排除，m 仍一次求得 2001。A 差 3，`3*10000>2001*10`，因此也被排除；B/C 各差 1，可保留；D 仍被排除。只剩 B/C 两源两组，不满足三源三组，因此 Q2 应为 UNAVAILABLE，而 Q1 为 VALID、2000。这是阈值收紧带来的预期可用性变化，不是实现一定有 bug，也不能为了让差异率好看而偷偷放松最少组数。

比较记录至少保存配对轮次、输入摘要、规则摘要、候选集合差异、排除原因变化、quality 转换、仅在双方有效时有意义的价格差、有效期变化与计算失败。输入摘要不一致应先判为不可比较，不能纳入规则效果。可用性下降是否可接受，需要产品按独立来源覆盖和风险目标决定，不由影子进程自行发布。

影子使用独立状态空间和权限：可读取获准的历史输入，只能写 shadow 结果，不具有生产 ownership、规则激活、产品 outbox 或生产发布权限。仅写一个 `shadow=true` 标志但复用生产写凭证不够。正式放行由合法 owner 追加已审批的 marker，影子不会因为“结果看起来更好”而获得生产写权；出现差异也不能直接覆盖生产历史。

## 第4层：规则正确，哪些监控仍能漏掉静默失真

**面试官：** 影子隔离了。生产每秒都有消息，队列延迟也低，但交易所一直重复发送五秒前的报价。你要监控什么，才能不把它判为健康？

**面试者：** 必须区分 source-age 和 receive-age，再追踪每一个持久边界。对选中的原始观测，`source_age=T-event_time` 反映业务证据有多老；`receive_age=T-receive_time` 反映本地最后一次收到该证据距采样多久。刚收到五秒前的报价可以 receive-age 很小，却 source-age 很大。若事件时间比接收时间新很多，还要看时钟质量，而不是把负 age 截成零来掩盖未来时间。

采集侧分别记录 socket 心跳、Raw 提交、原始 event_time、native epoch/seq 和连接世代、重复率、同 id 异 hash、缺口与时钟异常。重复包可以刷新连接活跃指标，但不能刷新业务观测时间或源价格新鲜度；稳定业务 hash 不包含重投的接收时间。source-age 不可信时应显示时钟原因，不能靠 receive-age 证明源行情新鲜。

处理侧监控 raw cursor 落后、源状态停留、源事务分配的连续 canonical_emit_seq 与接收侧 expected_emit_seq 差距、源到 market 的 pending/安全阻断、market 连续 cursor 缺口、tick 最老待处理时间、规则 marker 的排队与生效状态、候选数和独立组数、排除原因、UNAVAILABLE 原因、outbox 最老未确认位置、消费者连续游标与安全阻断。canonical_emit_seq 同时覆盖规范与质量/控制事件，不等于 native_seq；每源串行交付必须等前条在 market Inbox 持久接纳，确认丢失重试不能再分配新位置。结果侧检查 `valid_until-now`、已过期却仍被实时使用的情况、last_good 是否被冒充当前价、历史轮次是否回退当前投影。

标签要有界：按 market、源、阶段、规则版本或受控原因聚合，raw id、round id、hash、用户身份放在受控审计记录里，避免把每条事件做成高基数指标。链路关联从 result 的 vector 回到 Inbox/canonical/Raw，而不是要求每一个 Raw 都复制整段敏感 payload 到日志。

这些指标不是越多越好，而是每个关键状态都有“处理落后、业务陈旧、语义错误”三类可区分信号。进程存活和 QPS 只能覆盖第一层，覆盖不了源正在高速重播旧数据。

## 第5层：怎样把健康度写成不会被刷绿的语义 SLO

**面试官：** 指标都能看到，但告警还是需要目标。如果只看 VALID 比例，系统永远复用 last_good 就能刷出高可用；你怎样定义真正有用的 SLO？

**面试者：** 要把安全性、数据完整性、交付时效和可用性分别定义，不能用单个“成功率”互相抵消。安全不变量是不能允许实时使用已知无效或已过期价格；一旦独立检查器发现这类暴露，即使全日 VALID 比例很高也必须处置。

实时可用条件为 `quality=VALID`、所需前缀完整、来源满足规则、时钟质量可接受且可信 `now<valid_until`。恰好 age=2000ms 可以通过历史筛选，但成为贡献源会令截止不晚于 T，不构成实时可用。UNAVAILABLE 的 price 必须为 null；last_good 单独展示原时点与原截止，不计为当前可用价格。

可用性分母用约定 market 范围和服务时段的墙钟覆盖，或独立固定采样网格，不能只统计生产成功发出的轮次；否则完全停止出包也可能没有失败样本。还需分别统计用户可用性和在上游条件满足时的系统履约情况：前者把源不足时的不可用如实计入，后者帮助归因，不能以外部原因从所有报表中删除故障。

交付 SLO 从权威结果提交到消费者持久应用计算，并单列失效传播延迟、缺口恢复时长和有效期剩余量。失效传播慢不应靠提高消费时效预算掩盖，下游本地截止是独立安全底线。完整性 SLO 覆盖可观测 native 序号缺口、Raw 后阶段连续性和配置激活证据，不承诺不可观测的 Raw 前所有网络丢失都已被测量。

独立语义检查器根据获准输入摘要重新验证候选、组数、阈值和截止，不只检查结果消息格式。对账、指标和审计系统自身也要有心跳、滞后与缺样告警，防止“监控没收到数据所以没有报错”。目标值和预算应由产品用途、上游能力、TTL 及故障域协商，本题不虚构已测达标率或生产 SLO 数字。

## 第6层：不用真实故障结果，怎样设计一组可反驳方案的验证

**面试官：** 你定义了语义 SLO，但只在正常 Q1 下重算一遍不足以证明。怎样把上述边界变成故障验证矩阵，并避免写成“重启一下看看有没有报警”？

**面试者：** 每一项先写明注入点、持久前态、应保持的不变量、预期业务状态和独立证据。以下都是设计及手工推演，不代表已执行测试或演练：

| 故障或边界注入 | 必须成立的预期 | 应核对的独立证据 |
|---|---|---|
| Q1 五源正常输入 | E 陈旧、一次 m=2001、D 离群；A/B/C 三组得 2000，截止 T+1000ms | 冻结候选、排除原因、规则及计算摘要 |
| source-age=5000ms，但 receive-age 很小 | 源业务证据陈旧，不能因活跃收包变成贡献源 | 原 event_time、各接收证据、陈旧原因 |
| age 分别为 -1、2000、2001ms | 未来观测拒用；2000 可过历史筛选但贡献时截止<=T；2001 陈旧 | 比较符、时钟配置、实时出口记录 |
| 源或聚合事务提交前崩溃，提交后响应丢失 | 前者不留下半状态；后者查询原身份，不重复生新事件 | cursor、状态、outbox 和数据库提交事实 |
| 相同 logical id 重投，再改一位业务价格 | 同内容去重；异 hash 隔离，不覆盖 Raw 或原结果 | hash、冲突记录、源隔离与后续质量输入 |
| broker 确认丢失、消费提交后 ack 丢失 | 同身份可以重发，本地投影不重复生效 | outbox、consumer_seen、连续 cursor 与投影事务 |
| 源 emit_seq 先到未来 GAPPED，再补旧 READY/BBO | 持久 pending 与该源阻断；expected 不跳，连续补齐后才按最终状态决定资格 | 源 outbox 接纳确认、expected_emit_seq、market 安全控制输入 |
| cursor=100，先到102失效，再到101有效 | 102 先持久收紧，cursor 不跳；补齐时旧有效价不能短暂覆盖失效 | pending、safety_block、每次出口判定 |
| 原轮 UNAVAILABLE、无可用截止，显式纠错后历史合格 | 保留原 T/cut；新截止至多原 T，不恢复实时使用，当前恢复另开新轮 | 原质量、supersedes、correction manifest、无截止分支与当前指针 |
| 断流但无任何新价格，tick 排队 | 本地到期即停用；持久 tick 最终传播失效，不只等新价 | 原截止、tick 位置、处理落后与失效结果 |
| 旧主暂停，新任期生效后旧主恢复 | 旧主任期的新事务失败；旧任期合法 outbox 可由新主原样补发 | ownership 行、事务结果、原 id/hash/截止 |
| 备库缺已确认提交或快照缺块 | 不凭较老快照声称 RPO=0；不接受不完整 manifest | 复制确认水位、manifest、恢复阻断原因 |
| 激活 marker 前后交错输入并中途崩溃 | 旧轮不变；新轮使用完整新组合；恢复不混版 | marker 顺序、active_rule/cursor 事务、轮次摘要 |
| Q2 阈值影子尝试写生产 | 影子写权被拒；Q2 仅剩 B/C，输出 UNAVAILABLE 不影响 Q1 | 权限配置证据、独立 shadow 结果、生产 outbox |
| 重放时换当前配置、墙钟及 map 顺序 | 固定输入/前缀/T/规则时业务结果不变；故意篡改版本应被识别 | 不可变规则摘要、稳定序列化与首个差异位置 |
| outbox 过载、历史日志保留已到期 | 有界背压；不静默删除失效义务；补不回则显式 gap | 容量阈值、最老位置、保留决策与缺口记录 |
| Raw 提交前丢包且上游无历史补发 | 明确能力缺口，不声称全史完整或用本地序号掩盖 | native 连续性证据、协议能力和 gap 声明 |

矩阵的通过依据不能是“没有 panic”，而是注入前后持久状态与对外可用判定满足不变量。告警验证还要人为区分注入被检测、检测器已上报、责任方接收、恢复证据闭合这几个阶段；一个告警图标不等于完成修复。

这些设计只能说明如何寻找反例，不能形式化证明任意实现永不失真。真实验收还需要执行记录和可复核证据；本次按任务约束只给设计，不运行命令或报告测试通过。

## 第7层：证据越留越多，怎样同时满足恢复与隐私边界

**面试官：** 你为每个故障都要留证据。若 Raw、快照和审计永久保留，既有成本又可能存进鉴权头、订阅标识甚至 IP，怎样不因可观测性制造另一个风险？

**面试者：** 先区分业务原始证据与传输秘密。行情业务 payload、native 身份和必要时间证据可进入不可变 Raw，但采集层应使用允许列表，不把 token、私钥、cookie 或完整鉴权头当成“必须原样保留的证据”。传输秘密不参与稳定业务 hash；接收连接信息和可识别元数据单独受控，不能复制到每条指标标签中。

数据按用途分层：恢复所需 Raw/Inbox/控制与规则依赖、未完成交付义务、审计摘要、可选诊断日志，各自有最小权限、加密、访问审计和保留窗口。公共价格不含账户明细并不意味着周边元数据没有隐私风险。生产到影子或故障验证环境只传获准业务内容和必要证据，不克隆生产密钥或无限制数据库凭证。

保留窗口必须和恢复/补发承诺相容。清理前确认至少有可用且依赖闭合的快照、其后连续日志、对应规则包和执行语义；最慢消费者若仍在承诺窗口内，不能删掉唯一补发路径。判重身份与 hash 的保留也要覆盖合法重试/补发期，否则被删除的 seen 可能把旧消息当新消息。窗口外应拒绝过旧回补或通过显式检查点恢复，而不是假装永久去重。

不可变不等于必须永久保存。依法或按策略到期删除时，可按分区销毁完整对象、保留不泄露内容的删除和缺失范围记录；不原地改 Raw 假装从未有过，也不能在法定删除后继续宣称该区间可精确重放。若发现秘密已误入 Raw，需走独立安全处置：撤销秘密、隔离访问、按政策删除受影响副本并记录证据缺失，不能以审计名义继续无限传播。

取舍在于诚实降低某段历史的恢复能力，而不是为了“可追溯”无期限收集敏感数据。只有连保留与删除的后果都公开，恢复承诺才可信。

## 第8层：监控、升级和恢复怎样形成可操作闭环

**面试官：** 证据有期限，影子和故障设计也不等于真实正确。如果上线后发现一批 2000 其实来自错误分组，但价格数字恰巧没变，如何处置而不是改条配置就宣布结束？

**面试者：** 首先按语义错误处理，而不是按“价格差为零”降级。错误分组可能让同一实际来源被算作三个独立组，即使 mid 恰好都是 2000，也不满足产品资格。先冻结扩大变更、阻断影子转正和可疑写路径，把受影响范围、规则/分组摘要、输入 cursor 与起止轮次固定下来。

对仍在实时使用的受影响结果，由合法 owner 追加明确的质量控制输入，经持久有序 Inbox 产生失效结果或按契约追加撤回 revision，保留 supersedes 关系并可靠传播。消费者先收紧、不等待旧有效消息补齐；已过期结果本来就不得使用，但历史错误仍需登记，不能因过期而删除证据。源确实有完整连续性时无需为了配置错误把所有源永久 QUARANTINED，源质量和产品规则问题要分别归因。

随后在隔离空间按原规则复现问题、按修复规则影子比较，识别是分组资料错误、激活边界错误还是实现把配置混版。修复通过新 marker 生效，旧轮次不被原地改写；若需更正历史，保留原 T 和原观测 cut，追加 correction manifest、新规范解释、纠错输入引用和 supersedes，允许重算候选及价格但不延长原截止，不能让旧历史轮次回退当前投影。重新对外有效必须依靠新的合法轮次、新鲜证据和正确分组，不能把 last_good 复制成一条新鲜结果。

最后核对四个闭合条件：受影响结果已定位且撤回传播有消费证据；未来输出来自已确认新规则边界；固定输入下的新旧差异得到解释；保留/补发和不可恢复 gap 的能力声明与实际一致。缺一项就不能仅凭进程健康宣布结束。应把本次首个失真原因转成矩阵中的明确反例和语义检查，不额外声称不存在其他未知缺陷。

整个闭环把规则变更、权威状态、实时安全和审计连在一起。它提供的是可追责、可反驳、可恢复的证据体系，不是“部署监控后绝不会出错”的空泛保证，也不把教学设计包装成个人生产事故经验。

## 收束：机制、易错边界与反例验证

**讲透的机制：** 不可变规则包和输入证据；跨版本持久生效 marker；同前缀同 T 的影子比较及生产权限隔离；source-age 与 receive-age 分离；以实时安全和连续性为中心的语义 SLO；可反驳的故障矩阵；恢复承诺约束下的数据保留与隐私；从发现到失效传播、修复再生效的闭环。

**最容易答错的边界：** 结构兼容不是语义兼容；新版本消息可解析不等于混版可计算；影子价更接近市场不等于有写权；source-age 不会被重投刷新；历史 VALID 不等于实时可用；相同价格不等于相同资格；配置回滚不复活旧有效期；测试设计不是测试通过，监控沉默也不是健康证明。

**反例验证，仅作设计推演，不执行测试：** 同一 Q1 前缀分别喂给生产 100bps 规则和隔离影子 10bps 规则。预期生产为 A/B/C、VALID、2000，影子为 B/C 两源两组、UNAVAILABLE；若影子仍输出 2000，应追查是否错误复用生产候选或绕过最少组数。再把所有收包时间刷新而不改 event_time、把合法原截止置于当前之前，预期 QPS 可以很高，但语义检查仍判实时不可用。若影子能写生产，或任何出口因接收时间新而恢复有效，即使所有进程无报错，也应判定方案不成立。
