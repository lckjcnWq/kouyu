# 大问题 8：链上数据怎样采集并处理最终性与重组？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| EVM 日志变体 | 把链上合约事件接入观察系统的独立教学场景。 | 不混进 CEX Q1 主例；池子状态或 Swap 事件不天然是完整 BBO。 |
| block_hash／tx_hash／log_index | 区块身份、交易身份和区块内日志位置。 | 加链实例组成日志身份；同高度不同哈希是不同分叉事实，日志索引不是源流连续序号。 |
| 规范链视图 | 当前有证据选定的有效区块分支。 | 链上日志是否可用依赖此视图，收到或执行成功不等于永远不能撤回。 |
| 补扫／范围覆盖 | 固定目标分支后，把所需区块和事件查完整。 | 实时订阅用于尽早发现；无日志的块也要记覆盖，超时或截断不能当空结果完成。 |
| Raw／覆盖／最终性检查点 | 分别记录收到哪里、完整处理哪里、哪个链前缀满足最终性政策。 | 三者不能共用一个 latest height；覆盖与最终性位置都要配区块身份和证据。 |
| 共同祖先／重组 | 两条分支最后共有的区块，以及规范分支发生替换。 | 从可信检查点恢复时先补齐公共链尾段再接新分支，不能跳过祖先之前的状态事件。 |
| removed／tombstone | 撤回通知，以及持久保存的目标撤回屏障。 | 先撤回后到原日志也不能复活；重复撤回不重复逆转，但合法再激活须有新视图证据。 |
| 依赖链／当前失效屏障 | 从区块追到候选、产品的引用链，以及先禁止当前使用的持久约束。 | 当前撤回不能等待全部历史修订完；Raw 不删除，历史纠错另追加。 |
| 最终性政策／finalized | 按具体链共识与信任条件认定某链前缀足够稳定的规则或标签。 | 不是通用固定块数，也不等于 READY、新鲜或可成交；冲突须升级隔离。 |
| RPC／故障域 | 读取链数据的节点接口，以及可能一起出错的读取路径。 | 多端点不是天然独立多数；多个 RPC 读同一池也不是多个价格来源。 |
| source_event_time／decimals | 链观察时间依据，以及 token 原始整数的小数精度。 | 区块时间非精确执行时刻；token 精度非产品价格尺度，仍要核对资产、方向与单位。 |
| revision／supersedes | 显式撤回或纠错的历史版本链。 | 保留原 T、cut；有旧截止只能收紧，无可用旧截止则至多原 T，不复活旧轮或倒退当前。 |

## 把整篇文章压缩成一个故事

链上采集工程师阿宁收到一条从未见过原日志的 removed，没有直接丢弃，而是存原文与目标撤回屏障，暂停相关候选并核验分支。服务崩溃后补扫拿到原日志，持久屏障仍在，迟到 add 不能自动生效。她把实时订阅当提示，从带哈希的检查点向固定目标补扫，连无日志区块也记覆盖，只有整段处理完才推进覆盖位置。发现旧 a100 与新 b100 冲突时，她找共同祖先；从更早快照恢复，必须先重放公共链尾段，再接新分支，分批修复全程保留进度与 Outbox。源端撤回沿依赖链先关闭当前使用，再追加历史修订，不等历史全修完，也不删 Raw 或续旧轮期限。若找不到保留范围内的祖先，或冲突触及已接受最终检查点，就继续不可用并升级核验，不能靠多数 RPC 或回扫窗口耗尽恢复资格。即使链事实完整且满足最终性政策，也还要查市场新鲜度、资产与精度方向；这个独立链产品不能冒充 CEX 完整 BBO，更不能直接授权强平。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于“链上事实发现 → 完整补扫与检查点 → 规范链视图 → 标准化候选 → 聚合依赖与修订”。重点是采集完整性、分叉身份、重组撤回、最终性依据和多 RPC 信任，不展开池子路由、深度估算、Mark 或清算规则。

**必要前提：** 总览 Q1 仍是 CEX 现货 ETH/USDC 完整 BBO：轮次 T 中 A—E 的 mid 分别为 1998、2000、2002、2400、2001，age 分别为 100、120、80、100、5000ms；五个独立组，先排除 E，再按中位数 2001 的单轮 1% 规则排除 D，A/B/C 等权得到 2000。本题不会把链上数据悄悄塞进这个主例，而是**明确引入通用 EVM 日志采集教学变体**：链上 adapter 维护一个带区块依赖的独立观察产品或候选类型，采用单独版本化的准入规则。池子储备、Swap 事件或预言机更新都不天然等于 CEX 双边价量为正的完整 BBO。

链实例由已校验的网络标识确定，必要时包含 genesis 等区分信息；日志逻辑身份包含链实例、`block_hash`、`tx_hash`、`log_index`，区块高度只是位置，不是分叉身份。Raw 不可变；源分区单 owner 裁决身份、规范链视图、标准化与源状态；market 单聚合 owner 冻结持久规范事件、控制记录和轮次 marker。输出质量沿用 `VALID/UNAVAILABLE`，源状态沿用 `SYNCING/READY/GAPPED/QUARANTINED`，不把链上最终性标签混入这些枚举。

## 第1层：把链上事件视为带分叉依赖的事实，而不是永久消息

**面试官：** CEX 行情已经能采集了，增加一个 EVM WebSocket 日志订阅就能复用同一套流程吗？

**面试者：** 可以复用 Raw、owner、规范事件与 outbox 的职责划分，不能直接复用“收到消息就永久生效”的事实模型。链上日志依赖它所在的区块，以及该区块在当前规范链视图中的地位。即使交易执行成功且日志已经收到，区块之后仍可能离开规范分支。我要保存的不只是事件值，还包括链实例、区块高度和哈希、父哈希、交易与日志身份、采集位置、规范链视图版本、最终性证据和依赖关系。

教学变体的流程是：先持久保存 RPC 响应与订阅原文，再按经过校验的区块链关系补扫和核对，由链源 owner 形成规范链视图；将有效链事实转成规范事件；下游在准入政策允许时纳入候选；重组时再发布撤回与替代事实。候选必须能反查到支撑它的区块及事件，否则原始日志撤回后，下游不知道需要撤回谁。

链上不能照搬 Q1 对 native stream seq 连续的教学假设。EVM 日志没有覆盖所有相关事实的统一原生连续 seq，`log_index` 也不是每源流上的连续编号。adapter 可以为自己提交的规范事件分配连续内部位置，但它只能证明内部交付顺序，不能证明链上没有漏抓。完整性仍依靠区块范围覆盖、头部链接和补扫证据。

刚启动、只订阅到最新日志时，源应为 `SYNCING`，而不是立即 `READY`。只有起始基线可信、所需范围覆盖完成、规范链依据足够且准入条件成立，才恢复贡献资格。如果订阅断连导致覆盖不确定，应先进入 `GAPPED` 并撤掉当前候选，不能保留旧值直到碰巧收到下一条事件。

## 第2层：实时订阅负责低延迟，重扫负责可恢复覆盖

**面试官：** 你说不能靠订阅证明完整。断线之后具体从哪扫到哪？同一个区块反复扫描，会不会重复应用？

**面试者：** 我会把订阅看成“尽早发现变化”的提示，把按区块哈希和范围进行的补扫看成恢复主路径。先从持久检查点读取最后确认覆盖的区块号及哈希，校验它是否仍在选定规范分支上，再选择本次有证据的扫描目标头。扫描范围要有边界和固定目标身份，不能一边扫一边无限追逐不断增长的 latest。

补扫按受控范围拉取相关合约和 topic 的日志，同时取得必要头部，检查父子关系、日志的 block_hash 和目标分支是否一致。RPC 若支持按 block hash 过滤，可优先绑定具体区块；范围查询在扫描期间发生分叉，则要复核端点和各日志归属，发现变化就舍弃这次规范化决定并重扫，而不是把两条分支拼成一个范围。

检查点之外还需要一个有限重叠窗口，让断线边界、RPC 延迟和浅重组有机会被再次核对。重扫遇到同一个逻辑日志身份与相同业务摘要时幂等复用；同身份内容不同要保留冲突证据并隔离，不采用“最后一次 RPC 响应覆盖前一次”。同高度不同 block_hash 则是不同分叉事实，不属于重复。

范围内没有日志也必须记录覆盖。否则无法区别“这个区块确实没有相关事件”和“根本没有查询过”。节点超时、限流、范围过大或响应可能截断时，不能把空结果或部分结果标为完成；应缩小区间、逐块补齐，必要时核对 receipts。某个 provider 声称响应完整仍是一项信任前提，不能把普通 RPC 返回包装成密码学上的完整性证明。

重扫期间候选是否可用，要按缺口范围和产品依赖判断；无法证明连续覆盖时先失败关闭。等缺口补齐并建立可信快照或连续性证据后，再由 owner 发布恢复事实，不能让网络重连动作直接把状态改回 `READY`。

## 第3层：区分抓到、覆盖完成和最终确认三种检查点

**面试官：** 假设一批日志抓到了，也都写入 Raw，但规范事件还没处理完就崩溃。检查点推进到哪，才能既不漏又不把重复变成二次更新？

**面试者：** 我会区分至少三类持久位置。Raw 接收位置只说明原始响应已保存；扫描覆盖位置说明某个有明确区块身份的范围已完整处理；最终性检查点说明哪个链前缀满足当前链的最终性政策。三者不能用一个“latest height”混为一谈。高度还要配哈希，单独的 100 不能说明是哪条分支的 100。

Raw 先独立追加，允许存在已经持久但尚未规范化的证据。链源 owner 读取待处理批次，在同一数据库事务中提交日志身份与摘要判定、规范链相关状态、规范事件或拒绝记录、批次处理进度、消费 cursor 和 outbox。只有范围内所需内容全部完成，才能在最后一个事务中推进覆盖检查点。大范围可以拆成小批并记录块内进度，但未完成区块不能被标成整块已覆盖。

因此崩溃发生在 Raw 持久后、规范化事务前，恢复后从 Raw 重处理；发生在规范化事务提交后、消息发出前，则靠 outbox 继续交付。订阅和重扫都找到同一日志时，身份表保证只创建同一个生效事实。这里的“只生效一次”来自业务幂等，不来自幻想 RPC 或消息队列永不重复。

market owner 另有自己的事务，将聚合状态、round/manifest、消费 cursor 和 outbox 同步提交。源端事务与 market 事务不是跨服务大事务，中间允许交付延迟，但源端已经持久的撤回或规范事件不能因进程重启消失。两者之间沿用连续 `canonical_emit_seq` 的有序交付契约：报价、撤回和质量控制共享源分区序号，outbox 等前条经 market inbox 持久接纳后再发下条；接收方校验 `expected_emit_seq`，未来位置 pending 并阻断该源，补齐再按序应用。它不能反过来证明链抓取完整，也不能把迟到旧 add 排到新撤回之后重新生效。

如果先推进覆盖到 100，再异步处理 98 的最后一条日志，崩溃后从 101 开始扫，就会永久漏掉事实。反过来先持久处理进度、后推进覆盖，只会带来可幂等重做。我要选择后者，并让每个检查点都能追到对应的区块与覆盖证据。

## 第4层：从检查点发现分叉，按共同祖先撤回派生状态

**面试官：** 现在恢复时发现持久检查点是高度 100、哈希 a100，而选定 RPC 说规范块是 b100。你具体怎么处理，不只是说一句回滚？

**面试者：** 我会先停止让这个链源继续贡献可用候选，持久记录发现冲突的链视图与证据。接着沿经过核验的父哈希向后找共同祖先，例如两条分支在 97 一致，旧分支是 a98、a99、a100，新分支是 b98、b99、b100。没找到共同祖先之前不能凭相同高度直接覆盖状态，也不能只把检查点数字减三就假装完成修复。

Raw 中的旧分支数据不删除。owner 追加重组计划与规范链视图变更，记录共同祖先、离开规范链的块集合和进入规范链的块集合。对于依赖旧块的事件，生成有身份的撤回事实；对于新分支，先补齐头部、日志和覆盖证据，再按区块与日志顺序生成替代事实。

如果维护的是有状态的池子投影，不能只删除最新价格。可以从共同祖先处或更早、且哈希已核验属于公共链的可信状态检查点恢复。检查点若在高度 90、共同祖先为 97，必须先按序重放公共链 91—97 的相关状态事件，重建祖先块处理完成后的状态，再重放新分支 b98—b100；不能从 90 直接跳到 b98，漏掉公共链尾段。只有检查点已经覆盖到 97 时，才可直接接新分支。每段都要验证区块衔接与所需事件的覆盖，缺少证据就保持不可用。如果使用逆操作，则按反向顺序撤销旧分支 a100—a98，保留公共链状态；也必须有足以精确逆转的旧状态，不能假设所有事件都有简单可交换的减法。恢复期间状态保持 `GAPPED` 或 `SYNCING`，不会从旧分支挑一笔看起来还不错的历史价格顶替。

重组可能涉及很多行，不能要求一次无限大的事务。可以用持久 reorg_id 与阶段进度分批处理，但在一个小事务中先关闭源资格并写入待撤回证据，后续每批状态更新、进度与 outbox 同事务。只有全部撤回、替代和覆盖校验完成后，才能发布新视图恢复 `READY`。

崩溃在分批中间时，由持久阶段继续，旧的可用状态不会因重启重新出现。market 侧接到关闭资格的控制记录就要触发当前重算，不等所有历史轮次修订完成才撤掉不可信候选。不同 owner 的传播仍有延迟，需要由消费契约约束，而不是宣称整个系统在一个瞬间原子回滚。

## 第5层：重复 removed 与先撤回后到原事件都要有持久裁决

**面试官：** 上一答能主动发现重组。如果 WebSocket 又发来重复的 `removed=true`，甚至先收到 removed、从没见过原日志，会不会把状态扣两次，或者以后又被补扫复活？

**面试者：** 我会把“日志事实”和“对该事实的撤回动作”分开建模。日志身份包含 block_hash，稳定业务摘要覆盖其业务内容，不把传输字段 removed 当作原日志业务内容变化。撤回动作引用目标日志身份，并带可去重的动作身份、分支视图或重组依据。这样原事件与 removed 不会被误判为同身份不同价格的内容冲突。

重复 removed 只重复证明同一个撤回决定，不重复逆转投影。如果首次撤回已经与状态、cursor 和 outbox 一起提交，重发只得到“已处理”；如果事务未提交，恢复后仍可完整执行一次。不能在内存里放个 seen 集合就认为重启后也成立。

对于没见过原事件的 removed，我会保留原始通知，并持久化指向目标身份的待核验撤回证据或 tombstone，而不是因为“本地没有”直接丢弃。随后补扫才到的原日志，必须先碰到这份屏障：在撤回已被验证且适用的链视图下不能生效；证据尚不充分时保持待定并关闭相关候选资格，不能按它是第一次出现就直接入选。

removed 通知本身也有信任边界。仅某个 RPC 的通知不能自动抹去已经由更强证据确认的链事实，应触发头部与规范分支核验；核验失败或冲突扩大时进入隔离。即使通知最终被拒绝，也应持久保存拒绝理由和所依据的证据，使同一通知重试不会得到随机结论。

还要避免另一种极端：给 block_hash 写一个无期限禁止标记，导致同一块在后续有证据的分支切换中合法重新进入规范链也永远不能使用。撤回作用于特定规范链视图，重新激活必须是有新证据、可审计的显式动作，不能由一条迟到 add 自动取消 tombstone。历史撤回保留不变，新视图决定当前资格。

## 第6层：撤回必须沿依赖到达候选、当前价格和历史轮次

**面试官：** 假设原日志已参与一个聚合轮次。你撤回了源端日志，怎样确保缓存里的聚合价格不会继续有效？

**面试者：** 源端撤回只是第一步，必须有可追踪的依赖链：`block_hash → 日志/源状态版本 → 规范候选 → round/revision → 对外价格包`。候选若是多条日志或一个池子状态检查点推导出来的，要记录完整的依赖范围或可展开的状态版本引用，不能只引用最后一笔交易，然后遗漏它之前所有支撑状态。

在源 owner 的事务里，撤回相关规范事件、清除当前候选资格、更新源状态、推进 cursor 与写出 outbox 同步提交。market owner 消费到这份控制事实后，在自己的有序输入里立即触发当前撤回或新轮次。若剩余源或独立组不达门槛，就输出 `UNAVAILABLE, price=null`；不能让“价格暂时没变化”阻止有效性更新。

历史轮次仅对源撤回、映射纠错等显式更正追加 revision，以独立 correction manifest 引用原 manifest、被更正依赖、持久纠错证据与 supersedes，不覆盖旧记录。原轮次 T 与原观测 cut 不变；普通迟到、回补日志以及新分支新到观测只进入后续轮次，不能补入旧 cut 恢复旧轮有效。更正可以重新解释或撤回原 cut 内候选，再按原规则重算。更正后仍不可用则 price=null，不携带可用截止；更正后历史合格且被 supersedes 指向的旧版有可用截止时，修订截止取旧截止与按原 T、原 cut 内更正后贡献重算截止的最小值。若旧版为 UNAVAILABLE、无可用截止，则修订截止至多为原 T，只修订历史，不授予实时使用；后续修订不能跨过这次不可用决定恢复旧轮实时资格，当前恢复另开新轮。当前已有更晚轮次时，旧轮次 revision 只修订历史，不回退当前指针；如果同一依赖也支撑当前轮次，另发当前失效事实。

若历史依赖很多，当前失效与历史修订不能互相等待。可以先提交一个指向失效区块集合或链视图的持久失效屏障，读取当前结果时校验依赖是否跨过屏障，再异步展开历史 revision。否则修完数百万个历史轮次之前，当前查询还可能读到已知不可信的包。屏障是显式协议，不是只写一条后台任务日志就自然拥有的能力。

本地事务不能让已离线的消费者即时知道重组。价格包需要携带链视图或依赖引用，主动撤回通过 outbox 可靠交付；强约束消费者还需在动作入口校验权威有效性，或只消费满足特定最终性政策的产品。异步展示客户端至多在约定传播窗口与 TTL 内收敛，不能把“最终会修好”说成“重组从未影响过外部观察”。本题产品仍不直接授权强平。

## 第7层：最终性由具体链的协议与信任条件定义

**面试官：** 依赖撤回这么复杂，直接等 12 个区块就当最终，不就不用修订了？`processed`、`confirmed`、`finalized` 可以统一成三个阶段吗？

**面试者：** 不可以。确认区块数可以是风险政策的输入，不是通用的绝对不可逆证明。不同链的共识、最终性检查点、节点标签与故障假设不同，不能把某条链的 `processed`、`confirmed`、`finalized` 直接套到通用 EVM，更不能把名称相同当成承诺相同。

对选定链，我会先定义 provider 所称 latest、safe、finalized 或其他标签的准确语义，再定义产品接受什么证据。例如允许未最终观察的产品，必须明确记录当前头、祖先关系与重组可修订属性；要求某种最终性政策的产品，要确认事件区块是已验证最终检查点的祖先，并记录该检查点的高度、哈希、政策版本和证据来源。具体门槛只有在选定链后才能给出。

`READY` 只说明该源已建立符合其采集契约的可信状态，不自动等于某条候选满足所有产品的最终性要求。同一个事件可以已经完整采集，但对高最终性产品仍不具备候选资格。链标签与最终性证据进入 manifest，输出仍只用 `VALID/UNAVAILABLE` 表达当前产品是否达到自己的规则，不另造一个混乱的大状态枚举。

对于依赖 L2 的产品，还要明确是否依赖排序器、L1 批次包含、证明或挑战阶段；不能看到 L2 节点提供 finalized 字段，就忽略产品实际要求的结算层条件。若采用仅按后继块数的概率政策，也应把残余重组风险与回撤规则讲清楚。

如果已接受的最终性检查点后来发生冲突，这是信任或共识假设被突破，不是普通加几次重试的浅重组。系统应暂停相关资格、保留两边证据、升级隔离并按显式恢复协议处理。所谓最终性减少的是在既定假设下的撤回需求，不是授权删除证据或永远不设计失效路径。

## 第8层：多 RPC 是信任交叉检查，不是接口多数天然正确

**面试官：** 你刚才多次提到验证证据。如果有三个 RPC，两个说 a100，一个说 b100，直接多数投票可以解除隔离吗？

**面试者：** 不应按端点个数直接投票。两个域名可能同属一个 provider、共享上游或同时落后，第三个也可能更接近真实规范头。先要固定链实例、比较的高度或已知检查点、provider 的同步状态以及所声称的最终性标签，排除“一个比较 latest、另一个比较 finalized”的伪冲突。

对同一高度不同哈希，要核对祖先关系和受信任检查点，而不是选最高高度或最先返回的节点。对同一个 block_hash 的日志结果不同，则是日志完整性或节点行为问题，需要逐块补扫、比较 receipts 或使用更强验证路径。头部链接只能说明一组头彼此相接，普通 RPC 的日志列表仍可能缺项；如果没有验证 receipts 与根的完整路径，就不能声称已经独立验证了日志全集。

多 RPC 政策应配置真实故障域与信任权重，保留每个响应和冲突证据。证据不足时让相关源进入 `QUARANTINED` 或 `GAPPED`，当前产品不能继续以旧值冒充合格。恢复需要可审计的依据，例如核验到可信检查点、完成缺口范围复扫并按政策解决冲突，不是“下一轮多数刚好一致”就无痕放行。

RPC 的独立性和价格来源的独立性也要分开。三个独立节点读取同一个池子，是对同一链事实的三个读取路径，不是聚合算法中的三个独立报价源。即使链事实得到更强交叉验证，它仍可能只是一个依赖组。

若改为自建并验证节点，收益是减少 provider 信任，代价是节点运行、链实现与同步验证成本。它也不能消除链协议本身的最终性假设。方案必须明确在哪一层信任谁，不能以“多 RPC 加 quorum”四个字替代证据与故障裁决。

## 第9层：采集完整、链上最终和市场新鲜是三个独立条件

**面试官：** 假设 RPC 也核对过了，区块还满足最终性政策。这个链上价格是不是就能按 Q1 的 2 秒新鲜度直接放进去？

**面试者：** 不能。链上事实是否完整、是否满足最终性政策，以及它对当前市场是否新鲜，是三个独立判断。一个一小时前已经最终确认的更新，仍然可能是陈旧市场信息；一个刚收到的区块也不意味着里面的价格在接收瞬间才产生。

教学变体必须定义 `source_event_time` 的来源与限制。区块时间是出块层的时间，不等于精确的交易执行墙钟时间，合约自己带的时间字段也要核验含义和可信范围。未知时钟、无法解释的未来时间都不能用本机接收时间替代。如果变体明确采用 Q1 的 `0<=T-source_event_time<=2000ms` 和 1000ms 观察窗口，那么很多正常的最终确认事件会因延迟而不可用，这是规则的真实后果，不能在被追问时悄悄放宽。

需要更长观察窗口时，应创建新的产品或规则版本并说明风险，而不是修改 Q1。可用包仍以 `min(T+窗口, 各贡献源事件时间+时效上限)` 限定，revision 不延长旧轮次期限。age 恰好达到上限可以作为历史筛选合格证据，但若截止正好等于 T，就没有实时可使用窗口。

资产与单位也要单独校验。链上 token address、网络、decimals 与资产映射决定它是否真的是目标资产。池子两种储备的比值需要明确方向、十进制校正、宽整数计算、舍入和可代表的经济含义；USDC 的 token 原始精度不等于本产品的 `price_scale=10^6`。不能把 wei 储备比值直接命名为 USDC/ETH，也不能把单一储备比值伪装成双边价格与数量都为正的完整 BBO。

因此链候选应带明确类型与准入政策。需要 BBO 的产品就拒绝不匹配类型；允许链上观察的独立产品则按自己的数学定义生成候选。最终性证据不会自动赋予候选正确单位、可成交性或新鲜度，任何一个条件失效都要更新当前资格，而不是退回一个旧好值。

## 第10层：超出回扫窗口与最终性假设时，选择可解释的失败关闭

**面试官：** 最后把故障连起来：先收到一个未见原事件的 removed，随后崩溃，恢复补扫又拿到原日志；再发现分叉超过保留窗口，甚至冲突到已接受的最终检查点。整条链怎样收敛？

**面试者：** 第一阶段，收到 removed 时先把原文和指向目标日志身份的撤回证据持久化。即使本地没有原日志，也保留待核验屏障并触发分支核查。进程如果在该事务提交后崩溃，恢复必须读到这份证据；如果事务没提交，则从 Raw 重做，不能依赖已丢失的内存标记。

第二阶段，补扫拿到原日志时，先按含 block_hash 的身份去重并检查撤回证据。证据已验证且该块不在当前规范链，原日志只补齐审计事实，不进入有效投影；仍待核验则继续不授予资格。重复 removed 不重复逆转。假设事务已生成撤回 outbox，但还没送达就再次崩溃，恢复后重发同一个撤回动作，由下游按身份幂等消费。

第三阶段，核验分支发现找不到保留窗口内的共同祖先，不能推断“窗口以外都安全”。先保持源资格关闭，从更早的可信检查点、归档数据或重新校验的链状态恢复覆盖。没有足够证据就继续 `UNAVAILABLE`，不能拿本地最早剩下的区块假装共同祖先。

如果分叉还冲突到已经接受的最终检查点，升级为最终性或信任假设破坏，相关数据进入隔离。需要独立核验链实例、provider、共识或最终性证据以及受影响依赖，按显式管理流程建立新的可信基线。只有当允许使用的证据重新完整、冲突被裁决、历史与当前失效事实均持久后，才允许源恢复，而不是自动把检查点向后改写。

在整个过程中，当前价格需要尽早撤回，历史 round 通过 revision 保留原事实与纠错链，旧 revision 不覆盖更晚 round，过期包不续期。Raw 永不因修复被删除。检验方案时，应能回答每次崩溃后从哪一份持久记录继续、哪个依赖当前无资格、哪一个 outbox 还待交付，以及为什么外部不会因迟到 add 重新获得旧数据的使用权限。这些是可推演的正确性条件，不是虚构的演练或实测结论。

## 收束：机制、易错边界与反例

**讲透的机制：** 用带 block_hash 的身份保存分叉事实；以区块覆盖和检查点补扫修复订阅缺口；以共同祖先、持久重组阶段与撤回证据修复派生状态；依赖链连接源候选、当前结果与历史 revision；最终性和多 RPC 校验都明确自己的信任条件。

**最容易答错的边界：** 日志索引不是源流连续 seq；扫描游标不是最终性检查点；同高度不是同一块；removed 不是删除 Raw；未见原事件的撤回也不能丢；多个 RPC 不是多个独立报价源；区块数不是通用绝对最终性；最终确认不等于新鲜，也不等于 CEX BBO。

**检验方案的反例：** removed 先于 add 到达且跨一次崩溃，迟到 add 若能直接生效，说明撤回证据没有持久闭环；最终性冲突时若系统还能仅凭回扫窗口耗尽而恢复 `READY`，说明它把本地保留策略错误当成了链上信任证明。
