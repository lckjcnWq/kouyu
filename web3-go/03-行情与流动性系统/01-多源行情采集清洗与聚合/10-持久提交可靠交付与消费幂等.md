# 大问题10：怎样可靠提交行情并避免重复或失序生效？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| Raw／源事务／聚合事务 | 分别完成接收存证、源规则裁决与轮次产品裁决的提交边界。 | 前一阶段成功不代表后一阶段已完成；各层状态、cursor 与输出义务局部原子提交。 |
| Inbox／Outbox | 已持久接纳的待处理输入，以及业务提交后必须交付的待发事实。 | 两者衔接独立事务；确认不明就重发原身份，不另造轮次或改载荷。 |
| logical id／业务 hash | 标识哪件业务事实，以及它的稳定内容。 | 同 id 同内容幂等，同 id 异内容隔离；接收时间、连接和重试次数不参与业务摘要。 |
| native_seq／canonical_emit_seq | 上游原生流顺序，以及内部规范报价和控制共用的顺序。 | 后者事务内分配、回滚不消耗业务位置；前者的采集完整性不能由后者证明。 |
| expected_emit_seq／pending | 接收端期待的下一号，以及先到未来号的持久暂存。 | 未来号先阻断源，暂存确认不是连续接纳确认；补齐后按序应用，不让旧 READY 盖新故障。 |
| publish_seq／broker offset | 产品自己的连续交付号，以及消息系统内的传输位置。 | 用前者查产品发布缺口，不能拿 offset、轮次号或可能留洞的数据库 sequence 替代。 |
| round_id／revision／supersedes | 观察轮次、同轮更正版本，以及直接被替代的旧版。 | 当前按先轮次后修订比较；旧不可用版无截止时，更正截止至多原 T，后续不跨过去续期。 |
| RECEIVED／APPLIED | 已持久保管消息，与已把消息纳入连续应用前缀。 | seen 不能只有布尔值；暂存过的消息补齐时仍需排空，不能被去重逻辑吞掉。 |
| continuous_cursor／safety_block | 连续应用到哪里，以及已经知道必须暂停使用的限制。 | 收到未来失效先收紧，cursor 不跳；分批补齐也不能短暂放出旧有效价。 |
| broker ack／消费幂等 | 消息系统接纳确认，以及消费者本地重复应用无额外效果。 | ack 不等于所有消费完成；去重、投影和进度同事务，外部 HTTP 副作用另需协议。 |
| valid_until／last_good | 结果不可续期的截止，与单列的历史好价。 | 过期包仍可推进合法消费历史，但不能实时使用；实时要求 VALID 且可信 now 小于截止。 |
| owner_epoch／RPO | 当前写者世代，以及故障可容忍的数据丢失范围。 | 围栏挡旧写但撤不回在途包；本机事务原子不代表异步副本切主时 RPO 为零。 |

## 把整篇文章压缩成一个故事

交付工程师阿澄发现发布确认丢失，选择重发原 Outbox，而不是另造一份价格。源侧先将状态、规范输出、Raw 进度与待发记录一起提交，规范报价和失效控制再按内部连续号进入市场 Inbox；聚合也把轮次、输入进度与结果待发记录同事务保存。真正难点出在消费者：连续 cursor 仍为 100，却先收到 102 宣布失效。阿澄把完整消息持久暂存并立即阻断实时使用，不把 cursor 跳过去；101 的旧有效结果补到时，按序折叠仍保留已知限制，不能短暂露出 2000。她把已接收与已应用分开，避免去重反而吞掉待处理消息，缺失发布项优先按产品交付号补取。历史高修订只改历史，原截止不因首次收到、重发或切主刷新，原不可用轮的纠错也不能授予新实时窗口。积压要有界背压，逐条契约不能随手删 Outbox。最后她明确可靠性的边界：消费事务不保护库外副作用，本地数据库提交不保证异步切主零丢失，Raw 之前没收到又无法回补的事实仍是缺口。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题贯穿“持久 Raw → 源规范事务 → market 聚合事务 → outbox 发布 → 消费事务”，重点是每个提交窗口的完成含义、稳定身份、重试、连续游标、失效优先与复制边界。日志快照和主备接管的完整恢复过程由下一题展开；本题先回答已经形成的交付义务怎样不被超时、重复和乱序破坏。

**必要前提：** 采用 CEX 现货 ETH/USDC 的 BBO 完整绝对值观测，不是盘口增量，也不是 Mark、可成交报价或强平许可。价格、数量由精确字符串转换为 `price_scale=10^6`、`qty_scale=10^8` 的定点数；超 scale 拒绝，中间乘加做宽整数检查。主协议教学假设为同一 `source+instrument+channel+native_epoch` 内 `native_seq` 连续；连接世代不是 `native_epoch`，不能用本地接收编号证明上游无缺口。

贯穿结果沿用公共 Q1：采样 T 的持久输入可见前缀内，A 为 1997/1999、mid=1998、age=100ms；B 为 1999/2001、mid=2000、age=120ms；C 为 2001/2003、mid=2002、age=80ms；D 为 2399/2401、mid=2400、age=100ms；E 为 2000/2002、mid=2001、age=5000ms。A—E 是五个独立组。先按 `0<=T-event_time<=2000ms` 排除 E，再对剩余 mid 只求一次中位数 `m=2001`，用 `abs(p-m)*10000>m*100` 排除超过 1% 的 D；A/B/C 满足至少三源、三组，等权平均向下取整得到 2000。不足时输出 `UNAVAILABLE, price=null`，不能拿 last_good 冒充本轮有效结果。

## 第1层：先分清哪一种成功已经不可随意撤销

**面试官：** 从外部行情接入到消费者可用，这条链路怎样保证可靠交付？接口返回成功、消息发送成功和消费者看到价格，分别代表什么？

**面试者：** 我会把“成功”拆成五个持久边界，而不是承诺外部 API 到消费者天然 exactly-once：

```text
外部观测
  → Raw 独立提交：只承诺原始证据已被接收系统持久保存
  → 源事务提交：源状态 + canonical 事件 + 已消费 raw cursor + 源 outbox
  → 聚合 Inbox 持久接纳：事件身份去重 + market 内权威输入顺序
  → 聚合事务提交：聚合状态 + round/revision + 输入 cursor + 结果 outbox
  → 至少一次发布
  → 消费事务提交：去重记录 + 本地投影 + 连续 cursor
```

源分区和每个 market 分别只有一个合法 owner。教学上使用同一 PostgreSQL 权威存储，阶段之间仍通过独立事务交付，不用一个跨全链路长事务。源事务中的 `raw_cursor` 表示这段 Raw 已被判定和处理，不表示必然产生有效 canonical；无效输入也要留下拒绝或冲突证据。聚合 Inbox 还必须持久记录质量控制、源失效、expire tick 和轮次 marker，不能只收价格事件。

聚合结果至少包含 `{product_id,round_id,revision,T,rule,vector,candidates/exclusions,group,quality,price,valid_until,supersedes}`。`vector` 固定本轮各输入分区的实际前缀，候选及排除原因固定“为什么是 2000”。结果提交产生不可遗忘的交付义务，但 outbox 的 broker 确认只说明 broker 接收，不说明每个消费者都已应用。消费者事务成功也仅覆盖它自己的本地状态；消费者再调用外部 HTTP，仍需另一个可靠协议。

这种拆分允许阶段间短暂落后，却禁止“Raw 已提交所以价格已可用”和“发送函数返回所以消费者已生效”这两种跨边界推断。

## 第2层：Raw 已提交，源事务只做了一半怎么办

**面试官：** 你允许阶段间落后。假设 Raw 已经提交，源 owner 更新了 READY 和最新价格后崩溃，却没有写出 canonical；恢复时怎样知道该重做还是跳过？

**面试者：** 这种“状态先提交、事件后提交”的写法应被禁止。源处理一条或一批 Raw 时，先在事务内锁住该源分区的 owner 记录，验证 `owner_epoch`，再读取期望的 `raw_cursor` 和 native 流进度；源状态、canonical、游标和源 outbox 只能一起提交或一起回滚。

源事务还要为所有发往 market 的规范事件和质量/控制事件分配每源分区连续的 `canonical_emit_seq`。它不是上游 native_seq，也不是 Raw 接收序号；一次 Raw 可产生零个或多个输出。事务锁住源分区计数行，按确定顺序为实际输出分配连续位置，连同状态、cursor 和 outbox 一起提交，回滚则不消耗这些业务位置。本教学每个源分区路由到对应 market；若跨多个 market 扇出，应为每条目标交付流定义连续性，不能让接收方误把发往别处的序号当缺口。

例如持久 `raw_cursor=80`，Raw 81 已存在。事务处理 81 后准备把源置为 READY、更新 `last_native_seq`、插入带 emit_seq 的 canonical 和 outbox，并把 cursor 推到 81。若提交前崩溃，数据库仍是 80，恢复后再读 81；若提交后响应丢失，数据库已是 81，查询原处理身份即可，不生成另一个“新事件”。不能以 Go 内存里的 cursor 或函数返回位置判断提交事实。

序号跳变则在同样的事务边界里记录 `GAPPED`、缺口范围和必要的下游质量控制义务，不把完整绝对值观测等同于“协议缺口已经修好”。源状态只用 `SYNCING/READY/GAPPED/QUARANTINED`；陈旧和本轮离群是质量原因，不另造永久状态。`READY` 也不意味着任何采样 T 都能使用该源。

Raw 的 `raw_append_id` 标识不可变接收证据，业务判重依赖 stable logical id 和稳定业务内容 hash。连接变化、接收时间、重试次数不进入业务 hash；同 id、同业务内容不重复推进源状态，同 id、不同业务内容写冲突证据并隔离，不覆盖原 Raw。协议没有 native 序号时，必须另述可证明的缺口边界，不能套用这里的连续性结论。

代价是源分区内需要串行事务和持久判重索引，但换来可定位的崩溃恢复点，而不是靠重新连线猜状态。

## 第3层：事务成功后，发布确认丢失怎么办

**面试官：** 源事务现在不会写一半。但 outbox 已提交，发布器向下游发出了消息，确认包丢了；重发会重复，不重发可能丢，怎么选？

**面试者：** 选择重发，但重发同一个不可变交付事实。outbox 至少保存 `outbox_id`、目标分区、业务事件 id、payload、`payload_hash`、创建时的 owner 任期、发送状态和重试信息；发送 attempt 可以变化，业务身份和载荷不能变化。

源到 market 也要有业务顺序，本题选择“每源分区串行交付 + 接收端连续性保护”。发布器只在 emit_seq=n 已被 market Inbox 持久接纳并确认后才发送 n+1，不把网络 send 成功当接纳。接收事务锁住该源的 `expected_emit_seq`：等于期望值才按顺序接纳、更新期望并追加 market Inbox；小于期望值时按 id/hash 核对原接纳事实，返回原确认，不分配新 Inbox 位置；同 id 不同 hash 则隔离。原接纳确认丢失时，源重试 n 并获得原确认，然后才能继续 n+1。

若故障切换或异常通道先送来未来 emit_seq，接收方必须持久保存 payload/hash 到 pending，记录源交付 gap，并持久追加该源的安全阻断输入，不把未来原事件冒充已连续接纳。后续旧 READY/BBO 补到时，阻断仍优先；待缺口补齐，按 emit_seq 连续排空 pending 后，才依最终源状态决定是否解除。未来 GAPPED/QUARANTINED 尤其不能被迟到旧 READY 覆盖。pending 暂存确认也不能被发布器当成“已连续进入权威 Inbox”的接纳确认。

聚合结果 outbox 到 broker 也是相同思路：broker 确认前保持可重试；确认丢失可以再次发送。`PENDING/SENT` 是发送进度，不是价格质量。`SENT` 不等于所有订阅方应用；需要消费者回执的产品应另存各消费组进度，不能复用一个发送状态承诺全体完成。

发布器认领、更新发送状态等权威写也要在事务中验证当前 `owner_epoch`。不过数据库围栏不能撤回已经在网络中的旧发送，所以网络层仍可能出现重复、迟到和乱序，必须由接收身份和消费规则兜底。旧任期已合法提交的 outbox 可以由新任期合法发布器补发；补发不能重写 T、事件时间或有效期。

这里的取舍是接受重复传输，避免“确认不确定”导致静默丢失。去重解决的是重复副作用，不是阻止第二个网络包出现。

## 第4层：消费者怎样把去重、投影和游标真正绑在一起

**面试官：** 既然重发是正常路径，消费者收到同一个 2000 结果两次时，怎样证明投影只应用一次？把消息 id 存 Redis 够吗？

**面试者：** 不够。先写 Redis 再写投影会留下“已去重但未应用”，反过来则可能应用两次。教学模型把 `consumer_seen`、本地投影和连续业务游标放在消费者同一个数据库事务里。

先明确三个编号：`publish_seq` 是每个 product 在聚合结果事务中分配的连续交付序号；`(round_id,revision)` 是业务决策身份；broker offset 只是传输位置。`publish_seq` 通过锁住 product 计数行、与结果一起提交来分配，不直接用可能因回滚留下空洞的数据库 sequence 冒充连续业务序号。事件 id 可以是 `(product_id,publish_seq)`，同一 id 永远绑定同一个业务 hash。

假设本地连续 cursor 为 100，收到 101。消费者在事务内锁住该 product 投影，查重并校验 hash，记录接收事实，按轮次和 revision 规则应用结果，再把 cursor 从 100 推到 101，一起提交。提交前崩溃则全部不成立；提交成功但 broker ack 丢失，重投只命中原记录，不再次应用。broker ack 必须晚于本地持久提交，broker offset 提交本身不代替本地事务。

`seen` 还要区分“已持久接收”和“已按序应用”；乱序消息不能仅插入一个去重 id 就丢掉 payload。投影记录当前决策身份、quality、price、valid_until，以及独立的 last_good 和安全阻断状态。外部付款、通知等不在这个数据库里的副作用，不受该事务自动保护，必须再用本地 outbox 或对端幂等协议。

由此可以说本地投影具有幂等应用效果，不能把它扩大成整条外部链路 exactly-once。

## 第5层：缺口后先收到无效，不能只傻等前一条

**面试官：** 你说按序应用。现在 cursor=100，101 丢在路上，102 已明确宣布当前轮次 UNAVAILABLE；如果等待 101，消费者不是继续拿旧有效价吗？

**面试者：** 所以连续游标和安全投影必须分开。连续 cursor 仍停在 100，但已验证来自合法产品流的 102 不能被忽略。消费者把 102 的完整 payload、hash、序号存进持久 pending Inbox，并在同一个事务里登记 `gap_from=101`、阻断原因和已知失效约束，让实时服务先变成不可用；这一步不假装 101 已处理。

假设 102 是 round 51 的失效 revision，投影此前显示 round 50 的 2000。收到 102 后，服务不再返回该旧价为有效值，可以另列 last_good，但标明陈旧且不续期。随后 101 到达，即便它是 round 51 的较早有效 revision，也不能在补齐过程中短暂解除已经持久记录的失效约束。

实现上保留 `continuous_cursor`、`pending`、`current_decision`、`safety_block` 和适用的失效决策前沿。补齐时在一个事务里按 101、102 连续折叠，或者分批折叠但始终保留安全约束，直到可以给出完整前缀下的最终状态。若先收到的是未来有效消息而不是无效消息，保守方案同样因 gap 暂停有效服务，避免缺失位置中藏着尚未处理的撤回。

旧历史轮次的失效修订只修订它所指向的历史，不能无条件覆盖更新的当前轮次；但是出现交付缺口本身仍足以保守阻断，直到顺序证据完整。

取舍是部分乱序会牺牲短暂可用性，但不会为了等待顺序完整而继续暴露已知不安全的旧结果。所谓“先收紧后补齐”不是偷偷把 cursor 跳到 102，而是先持久执行安全限制。

## 第6层：补齐时怎样避免去重记录反而吞掉待应用消息

**面试官：** 102 已经写过 seen，101 后来补到了。普通消费逻辑发现 102 重复就返回，会不会永远无法推进？如果 101 根本补不回来怎么办？

**面试者：** 会，所以 `seen` 不能是一个无状态布尔标记。可以使用 `RECEIVED/APPLIED` 两阶段语义：RECEIVED 表示 payload 已持久保管，APPLIED 表示已纳入连续前缀；转移和 cursor 更新仍在本地事务里完成。重复消息即便不再插入，也要触发从 `cursor+1` 开始的 pending 排空，不能直接跳过后续收敛。

在例子中，101 接收事务先验证内容，再依序读取 pending 101、102，推进 cursor 至 102，同时提交最终投影和适用失效前沿。若因批量上限只处理 101，安全阻断必须保留，不能让 101 的有效价在两个事务之间漏出来。只有缺口已消除、应处理的失效已应用，并且存在未过期且不早于相关安全约束的合法后续结果时，才允许恢复有效服务。

缺失项优先从保留的产品发布日志按 `publish_seq` 补取，不用 broker offset 猜。若发布日志已删除，可以采用有证明的投影检查点：包含 product、覆盖至 H 的连续发布前缀、当前轮次及 revision、质量、原始有效期、规则摘要和完整性校验。安装时还要合并本地已知 H 之后的 pending 与失效约束，不能被一个更旧检查点洗掉。

这种检查点恢复只适用于“维护当前行情投影”这种可重建消费契约。若消费者需要逐条执行历史结算义务，跳到 H 不等于履行历史副作用，必须找回事件或显式进入不可恢复 gap。补不到时保持不可用并暴露缺口，不伪造连续 cursor，不把死信当作成功处理。

## 第7层：消息已经可靠送到，也可能在使用前过期

**面试官：** 即便缺口补齐，排队两秒才送达的 2000 也不能再用。有效期由生产端还是消费端负责？没有新价格时谁让它失效？

**面试者：** 生产端决定不可变的业务有效截止，消费端在每次使用时再次约束，二者不能互相替代。每轮固定 T 和输入前缀，`valid_until=min(T+1000ms,各贡献源 event_time+2000ms)`。Q1 中 A/B/C 的源截止分别为 T+1900、T+1880、T+1920ms，因此结果截止是 T+1000ms；`now==valid_until` 已不可用，使用条件是严格的 `now<valid_until`。

质量标签只使用 `VALID/UNAVAILABLE`，源的 READY 是另一条状态轴。恰好 `age=2000ms` 的观测可以通过历史筛选，但若它成为贡献源，`valid_until<=T`，结果即便在历史计算上标为 VALID，也已不能在 T 或之后实时使用；消费端的实时可用条件始终是 `quality=VALID` 且可信 `now<valid_until`，不是只认标签。

结果排队两秒后首次到达，消费者仍应持久接收、去重、推进合法连续 cursor，但实时服务从未将它当作新鲜有效价。`received_at`、重发时间和主备切换时间只能用于运维，不能替换 `event_time` 或 T。last_good 也保留原事件时间和原截止，显示用途不能续期。

上游需要把 expire tick、源失效控制持久排进 market Inbox，触发新的不可用结果或修订；即使市场不再来价格，也必须产生可重放的失效事实。下游不能只依赖这一条失效消息及时到达：查询、缓存出口和实际使用价格的路径都检查截止，调度器可以提前撤掉缓存，但“定时器一定准时”不是安全前提。

本地使用时读取可信时钟是实时防护，不等于重放历史时调用 `time.Now()`。若消费端时钟质量失去保证，无法证明尚未过期，应保守停止有效服务并标注时钟原因。代价是可能早停，但不会因时钟回拨或消息重投把过期参考价重新激活。

## 第8层：修订号更大，也不能把当前轮次退回历史

**面试官：** 你要求保留截止。假设当前已经是 round 52，迟到补发的是 round 51 的 revision 9，比当前 revision 0 大；要不要覆盖？同一轮补出更多源后又能否恢复可用？

**面试者：** 不能只比较 revision。需要持久、单调的轮次次序，例如 `round_id` 内含 product 范围的轮次序号；当前投影按“先轮次、再同轮 revision”比较。`publish_seq` 负责交付完整性，`round/revision` 负责业务新旧，二者不能混用。round 51 revision 9 可以更新历史记录、检查 supersedes 和审计 hash，但不能把 round 52 的当前投影回退。

同一轮可以追加更高 revision，但必须写明修订契约：原 T、原观测前缀 vector、原候选和规则 manifest 不能被原地改写。输入撤回、映射纠错等历史修订，保留原 T 和原观测 cut，追加 `correction_manifest`，记录持久纠错/撤回输入的身份与位置、新规范解释、适用规则和受影响证据，再以 `supersedes` 指向原 revision。可以据此重算候选、分组和价格，但旧 manifest 与结果仍在；新版本增加了显式纠错依赖，并非声称“完全相同输入及规则自行算出不同值”。普通新鲜数据改变观测 cut/T，或常规规则升级影响未来计算，才开新轮，不能借历史修订偷偷换时间窗口。

因此普通旧回补不能给原轮偷偷补观测、再凭高 revision 恢复有效；新鲜输入应驱动新轮。若独立链变体后来撤回某条链上证据，可以在原 cut 上追加历史 revision 并重算，但不能删除 Raw，也不能让历史修订回退较新的当前轮次。映射纠错即使令候选恢复三组，也必须保留原 event_time。更正后仍不可用则 price=null、无可用截止；更正后历史合格时，被 supersedes 指向的旧版若有可用截止，取旧截止与按原 T、纠正后依赖重算截止的最小值；旧版若为 UNAVAILABLE、没有可用截止，则新截止至多原 T，只修订历史，不能恢复实时使用。连续修订同样逐版收紧，不能跳过中间不可用状态找回早期截止；已经过去的有效期不会重新开始。更晚轮次的新鲜有效结果只有在相关缺口已补齐、适用失效已处理后才能解除阻断，数值更大的 revision 本身不够。

这里宁可把历史修订和实时恢复分开处理，也不采用“最后到达者获胜”，因为网络到达顺序不是业务时间顺序。

## 第9层：一直重试会不会拖垮系统

**面试官：** 这些规则都保守了。现在 broker 长时间不可用，outbox 越积越多，里面大部分有效价已经过期；是否可以直接删除旧消息，只发最新有效价？

**面试者：** 在本题的逐条连续发布契约下，不能静默删除，因为被删位置里可能有失效、规则 marker 或消费者尚未见过的历史修订，删除还会制造永久序号缺口。先把发送重试与业务截止解耦：退避、抖动、重试预算限制资源，业务消息仍按原身份保留；过期消息送到时只能作为历史事实应用，不能变成新鲜价格。

outbox 要记录积压数量、最老未交付位置、失败原因、下一重试时间和保留截止。达到容量保护阈值时对新接入或新轮生成实施明确背压，保留已接受交付义务及必要失效控制的处理容量；不能继续无界接收，最后依靠进程 OOM 代替策略。不能完成持久提交的 Raw 不确认成功，无法保存的上游区间应通过回补或显式 gap 说明。

若产品只需要最新投影，可以另行设计带检查点的压缩订阅协议，让检查点证明覆盖到哪个发布前缀、保留当前失效状态和原截止，消费者显式安装并审计这次游标跨越。它改变了消费契约，不是发布器随手丢掉若干 outbox。需要历史事件的订阅方仍须保留可补发日志。

毒消息或同 id 异 hash 进入隔离和告警，不自动标记 APPLIED 来消除积压；可用独立持久隔离证据允许输入处理继续，但当前产品的安全阻断及未履行义务必须仍可见。工程取舍是把容量上限写进服务承诺，而不是用“最终重试总能成功”掩盖磁盘和保留期的有限性。

## 第10层：数据库说提交成功，换主后却没有这条记录怎么办

**面试官：** 你把可靠性建立在数据库提交上。如果主库提交了 outbox 并返回成功，但异步副本还没复制就被提升，消费者甚至已经看到过该结果，你还能承诺不丢吗？

**面试者：** 不能仅凭本地主库事务成功承诺跨故障 RPO=0。事务原子性回答“同一个权威数据库里几项状态是否一起提交”，复制承诺回答“哪些已确认提交在失去主库后仍可恢复”，这是两个问题。

若承诺 RPO=0，数据库的确认条件必须覆盖声明的故障域，例如合适的同步持久确认和合法主库仲裁，并且新主必须证明包含承诺过的提交前缀。具体是否等待备库 flush 或 apply 要按数据库配置说明；不是配置一个同步名字就覆盖所有地域或全机房丢失。无法证明安全接管时应停止写入和有效服务，而不是拿较老快照立刻恢复 READY。

若采用异步复制，就应声明可能丢失的已确认窗口。切换发现缺口时进入恢复或不可用状态，使用剩余 Raw、发布日志和消费者回执做证据对账；消费者见过某个 hash 是下游见证，不等于已经找回对应 Raw、规则和源状态。不得复用旧事件 id 发布不同内容，不能把无法恢复的提交伪装成从未存在。

此外，Raw 之前的网络丢失不在数据库事务保护范围；有历史补发协议才能回补，没有就只能显式记录 gap，不能保证全史完整。消费者之外的副作用也不在本地投影事务范围。

所以完整承诺是：在明确的输入持久边界、复制故障模型、日志保留范围内，以事务建立局部事实、以 outbox 建立可重试义务、以身份和有序游标实现消费收敛、以期限和失效优先保证不误用。任何超出这些边界的 exactly-once 说法都需要额外协议，不能由“用了消息队列”推出。

## 收束：机制、易错边界与反例验证

**讲透的机制：** 阶段提交的完成语义；源与聚合各自的状态／游标／outbox 原子事务；稳定业务身份和 hash；至少一次发送；消费接收与应用分离；连续游标与安全阻断分离；轮次优先、同轮修订；不可续期的截止；复制 RPO 与本地事务分开承诺。

**最容易答错的边界：** Raw 成功不是产品成功；源 READY 不是本轮新鲜；broker ack 不是消费生效；seen 不是 APPLIED；revision 大不一定更新；网络重发不是新行情；旧任期合法 outbox 不等于旧任期仍可提交新事务；本地事务成功不等于异步副本不丢数据。

**反例验证，仅作设计推演，不执行测试：** cursor=100 时先收到 102 的 round 51 失效，再收到 101 的 round 51 有效，最后收到 103 的 round 50 高 revision。预期在收到 102 后立即阻断；补齐 101、102 后连续 cursor 推进但仍失效；103 可以完善历史却不能恢复旧价格。再把同一个 102 重发、把 101 延迟到截止之后，结果仍不能变成有效。若任何步骤出现“短暂恢复 2000”“截止被接收时间重置”或“跳过缺口却声称连续处理”，方案即不成立。
