# 大问题 1：一轮多源行情怎样从外部输入变成可消费产品？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| BBO | 一个交易场所当前最好的买价和卖价，以及对应挂单量。 | Q1 接收现货 ETH/USDC 的完整双边观测，不是成交记录或盘口增量。 |
| mid／参考价 | 买卖报价的中间值，以及按规则汇总出的观察数。 | 各源先算 mid，再筛选聚合；2,000 是参考价，不保证能成交，也不能直接记账。 |
| Raw | 把实际收到的内容和接收经过留下来的原始凭证。 | 证明本系统收到过什么，不证明外部源诚实、全史完整或后续处理已完成。 |
| Canonical | 按明确规则翻译成统一语义的数据。 | 保留资产、单位、时间与解释版本；纠错追加记录，不涂改 Raw。 |
| owner | 对一块状态负责、按顺序裁决的处理者。 | 源 owner 管源流，市场 owner 管轮次；进程内串行不等于跨进程只有一个写者。 |
| Tick(T)／冻结前缀 | 把采样时刻作为输入，并划定本轮已经看见的事件范围。 | 冻结的是持久输入，不是 T 时全球市场事实；普通晚到事件进入后续轮次。 |
| manifest | 本轮计算的材料清单与依据。 | 保存输入截止位置、各源应用位置、候选引用和版本，支持按同一切面复算。 |
| Outbox | 和业务状态一同落库的待发送记录。 | 提交后崩溃可补发原产品；投递可能重复，不能把重试包装成新采样。 |
| round_id／revision | 第几轮观察，以及该轮第几版更正。 | 历史更正保留原 T、原 cut 和原清单；消费者不能按最后收到的包覆盖当前结果。 |
| VALID／UNAVAILABLE | 本轮规则合格，或证据不足而不可用。 | 质量与价格共同提交；新不可用轮次不能被后到的旧有效轮次冲掉。 |
| valid_until | 这份结果最晚能用到什么时候。 | 使用时要求 now 小于该期限；主例截止 T+1,000ms，缓存、重发和页面刷新均不续期。 |
| 围栏／owner_epoch | 写入时核验当前负责人世代的门禁。 | 必须在权威事务中排除旧写者；只靠租约或 goroutine 唯一性不够。 |

## 把整篇文章压缩成一个故事

后端工程师小林要给页面提供 ETH/USDC 参考价。他先把五个场所的完整买卖报价存成原始证据，再由各源负责人核对身份、顺序、单位和时间，连同处理位置与待发记录一起提交。市场负责人遇到持久采样事件，封住本轮已见输入：先排掉陈旧的 E，再用一次中位数筛掉离群的 D，剩下 A、B、C 算出 2,000。小林交付的不是一个裸数字，而是带来源清单、质量和原定截止时间的结果包。发布后进程崩溃，新负责人凭快照与日志恢复，校验写权，再补发原包，不能重新采样给旧价续命。页面先收到新轮不可用、后收到旧轮有效时，必须保住已知限制；没有任何新消息，也要自行检查到期。普通晚到只影响以后，明确纠错才追加历史修订。最后小林用停更、重复、倒序和崩溃反例逐层核对承诺：原始写成功不等于产品可用，局部事务不等于端到端正确，冻结输入也不是掌握全球同时刻事实。这条链交付可追溯的观察，不负责下单、成交或资金结算。

**流程位置与核心机制：** 串起采集、规范、源资格、聚合、交付和消费的完整闭环，明确各阶段的权威状态与完成含义。具体协议接入、去重、聚合算法和恢复分别由后续母题深入，本题负责解释它们为什么必须组成同一条链。

**必要前提：** 沿用总览 Q1：CEX 现货 ETH/USDC 完整 BBO，五源 mid 分别为 1,998／2,000／2,002／2,400／2,001，年龄为 100／120／80／100／5,000ms；本轮冻结前缀已包含这些观测。它们是独立组的教学配置，聚合产品不是 Mark，也没有资产结算动作。

## 第 1 层：先把一轮业务讲完

**面试官：** 假设让你设计多源行情采集、清洗与聚合系统，你怎样从外部输入一直讲到用户能正确使用结果，而不是只列几个组件？

**面试者：** 我先定义交付的是“按指定来源和规则计算的最新有效观察”，而不是承诺全市场真实价格。采集器接收外部 BBO，先持久记录原始载荷与接收证据；源分区 owner 解释原生身份、顺序、资产、单位和时间，提交规范事件与源状态；市场聚合 owner 在持久 Tick(T) 处冻结可见前缀，计算候选、质量和期限，提交完整产品包；发布器至少一次交付，消费者去重、更新本地投影，并在实际使用时复核版本、质量和到期条件。

主例先因陈旧排除 E，对 A—D 的 mid 取中位数 2,001，再排除超过 1% 的 D；A/B/C 满足三源三组，参考价为 2,000。结果不只返回这个数，还返回本轮身份、采样时刻、输入证据、贡献源、排除原因和期限。没有达标候选时也要输出不可用，不能因为没有新价就一直显示旧结果为健康。

这条链没有用户资金移动。外部交易所才拥有其订单和成交事实，我们只拥有接收、解释和计算事实。用户看到 2,000 不等于能在三个场所同时以这个价买到 ETH，公共报价也不能直接驱动账本记账。

## 第 2 层：究竟是谁拥有真相？

**面试官：** 你刚才说源 owner 和聚合 owner 都提交状态。如果同一报价同时出现在原始库、规范库和页面里，哪个才是真相，谁能修改它？

**面试者：** 必须按事实类型回答，不能选一个数据库就说它拥有所有真相。外部源拥有原生报价事实；Raw 记录我们在某时某连接收到哪些字节，它不能证明源诚实，却能证明后续解释依据了什么；规范层拥有某规则版本下的解释；聚合层拥有某冻结切面下的产品裁决；页面只是投影，不应反向修改上游状态。

例如适配器后来发现某字段原来是 quote 数量，Raw 不能被改成 base 数量来掩盖错误；应追加规范纠错，引用原始记录和旧新映射版本，随后产生必要的产品修订。页面刷新迟了，应恢复投影，而不是重新造一轮采样使旧价看起来更年轻。

执行上，每个源流的身份、连续位置和同步状态由同一 owner 串行裁决，每个市场的轮次和 revision 由市场 owner 裁决。不同 owner 通过有身份的持久事件沟通，不共同写一个含义模糊的“最新行情行”。跨进程唯一写入还要靠事务内围栏，而不是只靠进程内串行。

## 第 3 层：原始写成功，到底能承诺什么？

**面试官：** 既然 Raw 是接收证据，采集器写成功后就向监控报告“行情处理成功”可以吗？后面的处理都会重试。

**面试者：** 不可以把完成阶段合并。Raw 成功只表示这次接收证据跨过了本层声明的持久边界，后面仍可能因资产未知、序号缺口或时间失真而拒绝规范化。即使规范成功，也可能未进入当前 Tick 前缀；即使产品已提交，也可能尚未送达消费者。监控应分别记录接收持久位置、规范进度、聚合进度和消费进度。

本模型的源事务把源状态、规范输出、Raw cursor 和 Outbox 一起提交。这样不会出现 cursor 已前进却没有相应规范事件的正常提交结果。聚合事务同样绑定聚合状态、本轮产品、Inbox cursor 和 Outbox。事务之间靠稳定事件身份与至少一次传递接续，不假设它们是一个横跨所有阶段的大事务。

还要说明“持久”依赖数据库复制承诺。如果只写单机磁盘，本机提交不能证明机房故障后不丢；如果宣称零已确认数据丢失，就必须匹配相应复制和切换策略。重试也不能恢复 Raw 之前从未收到、上游又不支持回补的数据。

## 第 4 层：逐层正确，为什么整条链还会错？

**面试官：** 你把每层都放进局部事务了。是不是可以说端到端一致性自然成立？请给一个各层都没崩溃却仍错误的场景。

**面试者：** 不能。局部事务只解决本层状态和输出共同提交，不能自动约束消费者如何解释产品。比如生产端已输出第 21 轮 UNAVAILABLE，网络先把它送到消费者，随后第 20 轮 VALID 的补发包到达；如果消费者按“最后收到的覆盖”，就会恢复旧健康状态。两个包可能都合法提交，但组合使用错了。

因此产品必须携带 `product_id、round_id、revision、quality、valid_until、rule_version`，消费者按轮次和修订语义更新，而不是按接收时间。已经知道的新限制要持久保存；中间缺口没补齐前，可以先收紧当前可用性，但不能让更旧的有效包把它抹掉。连续 cursor 与当前限制并非同一个字段。

端到端一致性由这些契约共同构成：源身份不能被连接重建改变；规范输出可回指证据；轮次冻结规则确定；数值和质量共同提交；消费应用幂等且不逆序放宽；使用时检查期限。对账是发现异常与修复证据，不是事先允许任意混用状态的理由。

## 第 5 层：没有任何新消息，结果怎样失效？

**面试官：** 上一答靠第 21 轮无效包保护消费者。如果所有采集连接半开，既没有新报价，也没有断线事件，聚合器如何知道该发第 21 轮？

**面试者：** 时间本身必须进入处理模型，不能把“收到正价格”当唯一触发。Q1 使用持久 Tick(T) 作为轮次输入，定期重新检查各源当前状态和事件年龄；独立的报价停滞检测还可以产生源质量控制。即使 TCP 心跳仍通，只要源事件过了 2,000ms 资格窗口，也不能进入新一轮候选。

消费者也不能只等生产端发不可用包。每个 VALID 包都包含固定 `valid_until`，使用时检查 `now < valid_until`。主例有效期限为 T+1,000ms，发布重试、页面轮询和缓存命中不能把它改成“本次接收时间+1秒”。生产端或网络完全停住，旧包仍应在消费者到期。

这种期限提供的是有界陈旧，不是瞬时全局失效。若源在包发出后立刻出问题，限制通知可能延迟；在包的合法期限内，消费者可能尚未知晓变化。需要更强执行保护时，应在对应业务系统设计屏障与权威复核，不能把本观察产品的 TTL 宣称为完整风险授权协议。

## 第 6 层：冻结本轮，是否就等于同一时刻？

**面试官：** 你用 Tick 冻结输入，能不能把 2,000 描述为“时刻 T 全市场的价格”？如果某条更早发生的 C 报价晚到呢？

**面试者：** 只能说它是 Q1 在采样 T、按已观察输入前缀形成的参考，不能说掌握了 T 时全市场事实。各源时钟和网络路径不同，外部更早发生的事件可能还在路上；Tick 截断的是本系统的持久输入，不是外部世界。

本轮 manifest 保存 Inbox 截止位置、各源实际应用位置、候选引用和规则版本。普通晚到的 C 事件进入更后的输入前缀，只影响后续轮次，不回填旧轮候选。若是明确的源撤回或映射纠错，才追加对应旧轮次 revision：保留原 T、原观测 cut 和原 manifest，另存纠错依据及 correction manifest，再重算受影响结果。不能原地换掉旧轮候选又声称历史从未变化。

确定性也要带条件：同一有序前缀、同一 T、同一配置和版本应复算相同结果；把 C 放到 Tick 前与 Tick 后是不同输入，允许产生不同中间轮次。为了复算而按 source_id 排序只能稳定同一候选集合的计算，不能弥补两个运行实际观察切面不同。

## 第 7 层：服务重启后怎样续上这条链？

**面试官：** 现在聚合器在产品提交后、发布前崩溃。新实例只恢复最后价格 2,000，再从最新消息开始消费，够不够？

**面试者：** 不够。它还需要已提交的输入 cursor、各源最新规范状态与资格、轮次/revision、规则与配置生效位置、已知限制及待发 Outbox。只恢复 2,000 既不知道它来自哪些源，也不知道有效期限，更无法判断重放事件是重复还是新增。直接从 latest 开始会漏掉崩溃间的失效或修订。

新实例先取得新的 owner 世代，在数据库事务里验证写权，再从一致 checkpoint 与其后持久输入恢复。已提交未发布的产品通过 Outbox 补发原身份；重复送达由消费者去重。旧实例即使租约超时后继续运行，也不能通过权威写入检查生成新结果。

合法历史不因切主而消失。旧任期已经提交的 Outbox 可以由当前发布者继续投递，期限仍是原值。它不能因为“旧任期”被全丢，也不能被重新包装成新 T 的有效结果。若恢复证据缺失，必须暴露不可恢复缺口或重新同步，不能用一个看起来合理的当前价格补造历史。

## 第 8 层：怎样证明架构闭环，而不是组件齐全？

**面试官：** 你已经讲了状态、事务、期限和恢复。如果面试官要求不用再加组件，只用几个反例判断这个方案是否成立，你会怎么检查？

**面试者：** 我会按承诺穿过故障窗口检查。第一，保存 Raw 后立刻停止规范处理，系统只能报告接收成功，不能报告产品可用。第二，同一业务事件在两个连接重复到达，规范状态只能生效一次，接收证据可以有两份。第三，出现源缺口或静默停更，聚合与消费必须撤销对应资格，不能靠旧价续命。

第四，在产品事务提交后、消息确认前停止发布，恢复应补发同一轮同一修订；消费者的最终投影不能因重复改变。第五，先到无效新轮、后到有效旧轮，不能放宽已知限制。第六，用固定 manifest 重放，结果数值、质量、排除原因和期限一致，而不是只检查价格差不多。

这些是验证设计，不意味着已经执行工程实验。真实工程还要测各段时延、队列容量、数据库故障和恢复时间，并记录条件。对本面试模型，最重要的是每项保证都能指出负责状态、提交边界和失败后的续接方式，而不是回答“加 Kafka、Redis、重试和对账就行”。

## 本题收束

**讲透的机制：** 从原始证据到规范资格、冻结轮次、完整产品包和消费复核，各层完成点不同；局部原子性通过身份、版本、顺序、失效与恢复契约连接成端到端保证。

**最容易答错的边界：** Raw 可靠记录不代表全史完整，聚合提交不代表消费者已经应用，收到旧报价不代表新鲜，单 owner 不代表分布式无双主，观察参考不代表可以成交或记账。

**反例与验证方法：** 让第 21 轮 UNAVAILABLE 先于第 20 轮 VALID 补发到达，再重启消费者。若旧价重新获得有效资格，或重启忘记已知限制，说明系统只做了消息去重，没有完成状态与可用性的闭环。
