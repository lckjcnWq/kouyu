# 大问题11：崩溃和切主后怎样恢复同一套行情状态？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 权威提交前缀 | 经存储与复制承诺确认、接管方必须包含的历史范围。 | 先证明恢复到了哪里，不能靠快照文件时间或重新拉到最新 BBO 猜历史。 |
| cursor／vector | 某阶段处理位置，以及多个输入分区各自处理到哪里。 | 源与市场进度可不同，但已引用事件和未完交付都必须找得到。 |
| Checkpoint／快照 | 保存恢复所需状态与相应处理边界的检查点。 | 不只存 mid，还须恢复缺口、判重、限制、版本、期限和 Outbox 义务。 |
| MVCC 一致视图／因果闭合 | 在同一数据库可见切点读取，并保证依赖事件不缺失。 | 源比聚合领先可以合法，任意混搭新旧字段不行；多库不能直接借用单库结论。 |
| COMPLETE manifest | 声明快照已完整可用的清单，列出对象、摘要和依赖。 | 缺块、校验失败或规则包不可取回就不能接管；hash 也不单独证明来源可信。 |
| 确定性重放／执行语义 | 用同一有序历史与当时规则重算，以及解析、取整、溢出等具体含义。 | 固定 Raw、T、控制、前缀与版本，不读取当前时间或配置；只比价格相同不够。 |
| 逻辑重放／权威恢复 | 前者隔离验证旧历史，后者恢复正式库中的原事实与身份。 | 只有 Raw 未必能找回原轮次、到达顺序和发布身份，不能默认向生产重新发布。 |
| owner_epoch／数据库围栏 | 新负责人世代，以及每次写事务核验其写权的机制。 | 校验锁持有到提交，接管竞争同一权威行；Redis 租约或进程锁不能替代。 |
| RPO／复制水位 | 容许丢失数据的范围，以及日志收到、落盘、应用到哪里。 | 本机提交不等于接管零丢失；缺承诺前缀就不能宣布 RPO=0 接管成功。 |
| 合法旧 Outbox／在途消息 | 旧任期已提交的交付义务，以及尚在网络中的包。 | 新主可原样补发旧义务，旧主不能新提交；在途包仍需消费去重与顺序保护。 |
| 历史 VALID／实时有效 | 当时规则计算合格，与现在仍满足期限和完整性要求。 | 历史重放保留原 T；接管实时阶段另记当前 Tick，未过期且有新合法决策才恢复使用。 |
| gap／保留依赖 | 无法证明完整的历史范围，以及恢复承诺依赖的日志与规则。 | 新同步可恢复未来，不能抹掉不可恢复历史；修订也不延长旧截止或倒退当前轮。 |

## 把整篇文章压缩成一个故事

值班工程师小孟接管行情服务时，快照只覆盖市场输入 700，旧主却可能已经提交 701 的失效结果。她没有立刻加载快照里的 2000 对外服务，而是先确认唯一权威数据库及复制水位是否包含承诺过的 701；若声称零丢失却拿不出这段提交，就不满足接管条件。她校验完整快照清单、对象摘要、规则包与因果依赖，再恢复源顺序、缺口、市场输入进度、已知限制和待发义务，按原 T 与原版本重放后续日志。相同输入应得到相同候选、质量和期限，不只价格碰巧一致。新任期通过事务行锁围栏取得写权，旧主恢复后提交 702 必须失败；旧任期合法的 701 却要由新发布者原样补发，不能一刀切丢弃。历史恢复正确不代表现在有效：她另记接管时 Tick，让实时出口继续检查原截止，不给旧包续期。缺坏快照可退到可用检查点，日志真缺失则登记不可恢复区间；当前外部报价最多建立未来基线。隔离逻辑重放也不能仅凭 Raw 就向生产补造丢失的发布身份。

**流程位置与核心机制：** 本题覆盖源规范与 market 聚合两级状态的恢复，以及数据库复制、快照、确定性重放、owner 围栏和主备接管。重点不是“备机重新拉一遍价格”，而是恢复到有证据的一致输入前缀，继续履行已提交交付义务，同时不把历史状态重新包装成新鲜行情。

**必要前提：** 教学主线是 CEX 现货 ETH/USDC 的 BBO 完整绝对值观测，主协议假设同一 `source+instrument+channel+native_epoch` 内 native_seq 连续。本地连接世代不等于源 native_epoch。持久 Raw 独立提交；源分区单 owner 的源状态、canonical、raw cursor、outbox 同事务；每 market 单 owner 处理包含规范事件、质量控制、失效 tick 和轮次 marker 的持久有序 Inbox，聚合状态、round/revision、输入 cursor、outbox 同事务。使用 PostgreSQL 的条件锁、唯一约束、CAS 和数据库事务围栏作为教学模型，不拿 Redis 租约代替数据库提交权。

公共 Q1 的 T 时刻可见前缀包含五个独立组：A=1997/1999、mid=1998、age=100ms；B=1999/2001、mid=2000、age=120ms；C=2001/2003、mid=2002、age=80ms；D=2399/2401、mid=2400、age=100ms；E=2000/2002、mid=2001、age=5000ms。按 2000ms 新鲜度先排 E，只求一次中位数 2001，再用 `abs(p-m)*10000>m*100` 排 D，A/B/C 等权向下取整得 2000。价格 scale 为 `10^6`，数量 scale 为 `10^8`，精确字符串解析、超 scale 拒绝、宽整数检查都属于必须随重放保留的规则。

## 第1层：恢复的到底是哪一种状态

**面试官：** 行情进程崩溃之后，重新连接交易所拿一份最新 BBO，不就恢复了吗？你说的“恢复同一套状态”具体指什么？

**面试者：** 最新 BBO 只能帮助恢复未来可观测性，不能证明崩溃前哪一轮已经提交、哪条失效尚未发布，以及消费者见过什么。恢复对象至少有三部分：输入处理进度、业务裁决状态、未完成交付义务。

源侧要恢复各 native 流的 epoch、连续 seq、缺口与隔离原因、最新合格观测、raw cursor 和 canonical/outbox 身份。聚合侧要恢复 market Inbox 的连续处理位置、每源最新状态和观测、轮次序号与 revision、冻结的 T/vector、候选和排除原因、规则与源分组版本、当前结果、last_good、期限及未完成 outbox。源状态 `SYNCING/READY/GAPPED/QUARANTINED` 与结果质量 `VALID/UNAVAILABLE` 是不同状态轴，不能从“重连成功”推导源 READY，更不能推导产品 VALID。

```text
确定权威提交前缀
  → 读取校验通过的快照或数据库状态
  → 按对应游标重放剩余持久输入
  → 核对状态与结果摘要、交付身份
  → 获得新 owner 任期并恢复尚未完成的义务
  → 处理接管时持久 tick / 新输入，重新决定实时可用性
```

例如崩溃前 Q1 结果 2000 已提交但未发送，恢复后应补发原结果，而非生成一个新 T 的 2000。若已过 `valid_until`，它只能是历史交付事实，实时服务仍不可用。Raw 已存在但尚未形成 canonical 则从源 cursor 继续，不把 Raw 持久化误认成产品完成。

## 第2层：快照要保存哪些内容，才能不丢掉半个决策

**面试官：** 你说要恢复输入进度和交付义务。那快照只存最新五个 mid 和一个输入 offset，缺少什么？请说到具体字段。

**面试者：** 缺少使这五个 mid 有业务含义的上下文。快照不能只有可展示的价格，还要包含状态机恢复所需的最小充分状态和外部证据引用。

源快照要有分区身份、状态与原因、各 native 流的 epoch/连续 seq、连接世代的独立记录、已消费 raw cursor、未决缺口、同步基线，以及 stable logical id/hash 判重索引的可恢复引用。还要保存事务分配的连续 `canonical_emit_seq` 及源 outbox 接纳进度，它覆盖规范与质量/控制输出，不等于上游 native_seq。最新观测保存 bid/ask/数量、原 event_time、接收证据、canonical id；缺少 event_time 就无法重算新鲜度。

market 快照要有 Inbox cursor、各上游输入前缀 vector、每源 `expected_emit_seq`、乱序 pending 及安全阻断、每源可用性与质量证据、当前/待闭合轮次、冻结 T、实际候选及排除、原 manifest 和追加的 correction manifest、完整规则和源分组/时钟配置引用、当前 `round_id/revision`、quality/price/valid_until/supersedes、last_good 原时点，以及计时任务的持久语义状态。若设计中只在轮次事务边界拍摄，就不必序列化进程临时栈，但必须能重新推导下一次应入队的 tick；已经入队的 tick 不能丢掉。

交付方面保存 outbox 的恢复范围、业务 id/hash、连续发布序号和发送进度的可信来源。若 outbox 独立备份，要在 manifest 中指向同一个一致切点的 outbox 数据集，不能恢复状态却忘了交付义务。网络“已发”可能没有可靠确认，恢复后仍允许按原 id 重发。

快照可以引用不可变规则包和历史日志，而不把所有 Raw 内嵌一遍；但引用对象必须可取回且校验通过。只存版本名却让规则内容随时间改变，不是可恢复快照。

## 第3层：分开拍摄源和聚合快照，怎样证明没有穿越前缀

**面试官：** 这些字段很多，直接遍历内存拍下来可能拍几秒。若源 cursor 是新值，聚合候选还是旧值，快照各自看着都合法，组合起来怎么发现？

**面试者：** 快照必须说明它覆盖的是哪个一致切点，而不是“文件完成时刻”。教学单数据库模型优先用一个可导出的 MVCC 一致视图，在同一可见提交切点读取源状态、聚合状态、cursor 和 outbox。源比聚合处理得更靠前不是错误；错误是读取了不可能在同一切点共同成立的字段。

还要检查因果闭合：聚合已消费的 Inbox 前缀里引用的每条 canonical 都可在快照或其引用日志中找到；源状态已经推进却聚合尚未处理的 canonical，必须仍存在于 outbox、Inbox 或明确的可重建日志中。不能因“源 cursor 已经过了”就删除聚合尚未接纳的中间交付事实。

源到 market 沿用每源分区串行交付：emit_seq=n 持久接纳并确认后才交付 n+1，接收侧锁住 expected_emit_seq，以 id/hash 核对重试，不给重复分配新 Inbox 位置。快照若有未来 emit 的 pending，必须同时保留源安全阻断；补齐时先按 emit_seq 连续应用，迟到旧 READY/BBO 不得覆盖已知新 GAPPED/QUARANTINED。恢复不能只保留 pending payload，却丢掉其已知失效约束。

若改成多个独立数据库，就不能借用单库 MVCC 结论。需先确定各阶段高水位，持久化 barrier，再选取因果闭合的前缀 vector，并保留各阶段之间仍在途的事件；没有分布式一致切片协议，就宁可分别恢复并重交付，不把任意几个快照拼成全局最新。

文件发布还需要 manifest：包括 snapshot_id、schema_version、范围、数据库切点/日志位置、源 raw cursor vector、market Inbox cursor、outbox 覆盖边界、对象清单和每块 hash、规则包与执行语义摘要、依赖快照、生成状态及原 owner 任期的审计证据。原任期只是历史来源，恢复不能把它直接重新安装成当前写权限。先写临时对象、校验完整，再原子发布 `COMPLETE` manifest；缺块、hash 不符或依赖不全的快照不可接管。

manifest 的 hash 证明内容没有意外变化，不单独证明其来源可信；可信存储与发布权限也要限制。这样付出快照协调成本，换来“恢复点可解释”，而不是依据修改时间选一个看起来最新的文件。

## 第4层：同一份 Raw 为什么还可能重放出不同的结果

**面试官：** 你已经固定快照切点了。快照后按 Raw 重算就一定得到原来的 2000 吗？如果重放时当前配置、系统时间和 map 遍历顺序都变了呢？

**面试者：** 只固定 Raw 不够。确定性承诺应写成：相同原始证据、相同有序输入前缀、相同 T、相同完整规则及依赖，得到相同业务输出。它不承诺“相同集合、任意到达历史”都有相同中间轮次。

重放输入必须包括源规范事件、缺口/隔离/恢复控制、expire tick、轮次与规则生效 marker、原时钟质量证据；若产品使用换汇，还要固定历史汇率事件和依赖前缀。CEX ETH/USDC 基线不需要凭空加汇率依赖，但不能在独立跨币种变体中去网络查询当前汇率。

每轮重用记录的 T，不调用 `time.Now()` 给历史观测计算新的 age；规则、源分组和时钟配置按不可变摘要读取，不联网取“最新版本”。普通旧回补不重开历史观测 cut；输入撤回或映射纠错则保留原 T/cut，重放追加的 correction manifest、新规范解释与 supersedes，可以重算候选和值，但不覆盖原 manifest。更正后仍不可用则 price=null、无可用截止；更正后历史合格时，若被 supersedes 指向的旧版有可用截止，取旧截止与按原 T、纠正后依赖重算截止的最小值；若旧版不可用、无可用截止，则新截止至多原 T，只修订历史而不恢复实时使用，连续修订同样收紧。重放必须保留这个分支，不能从更早版本借期限。新鲜数据改变 cut/T 则属于新轮。执行语义包括精确字符串解析、scale、超精度拒绝、宽整数溢出处理、一次中位数的偶数样本约定、阈值严格大于和 floor。候选排序、同时间冲突裁决和结果序列化都必须稳定，不能依赖 Go map 的遍历顺序或浮点求和顺序。

Q1 应重放出 E 陈旧、m=2001、D 离群、A/B/C 三源三组、price=2000，以及同样的候选清单和排除原因。只比较 price 不够，两套错误候选也可能巧合算出 2000。执行器或 schema 升级要能加载旧语义，不能用新解析器默默“修正”旧输入。

到达顺序不同可能使某源在早一轮尚不可见，所以中间 UNAVAILABLE 与 VALID 的历史不同是合理现象；把到达顺序和前缀也固定以后，仍不一致才是确定性故障。

## 第5层：恢复后计算一致，怎样不重复生成已提交结果

**面试官：** 重放能算一致，但崩溃前可能已经提交了 round 51，只是进程没收到提交响应。重放会不会再生成一份 round 51，甚至给它分配新发布序号？

**面试者：** 恢复应先读取数据库事实，不能从进程记忆判断“提交到哪”。快照后的输入处理仍按原事务边界恢复：`输入 cursor + 聚合状态 + 轮次结果 + outbox + 发布序号` 原子提交。如果数据库显示 round 51 已存在且 cursor 已过其 marker，就不重新生成一个结果；未提交的事务则从旧 cursor 重做。

结果使用稳定身份，例如 `(product_id,round_id,revision)`；交付使用 `(product_id,publish_seq)`，两者都有唯一约束和稳定业务 hash。遇到同身份同 hash，说明是相同事实的重试；同身份不同 hash 必须停在差异位置调查，不能用 upsert 把原结果覆盖。`owner_epoch` 和发送 attempt 属于提交/运维证据，不因为恢复换任期就改变业务载荷身份。

还要区分两条恢复路线。数据库本身的备份加事务日志恢复，应恢复原 outbox 和业务序号，这是权威状态恢复；从 Raw、控制日志和旧规则做逻辑重放，默认写隔离空间，用来验证状态与结果，不直接向生产发布。若要用逻辑重放补足丢失的权威数据，必须有完整有序 Inbox、原轮次分配和发布身份的映射证据，先与外部已见结果对账，再在围栏保护下接管，不能声称只要 Raw 还在就能重建所有历史交付身份。

代价是需要保留比“原始价格”更多的控制和决策日志，但它避免灾后重复发出一个身份不明的新历史，也避免已有消费者被迫接受同 id 异内容。

## 第6层：重放正确不代表旧主已经失去写权

**面试官：** 假设备机已经重放到正确状态，但旧主只是网络分区，没有死。双方都认为自己是 owner，怎样防止两边继续写？只用 Redis 租约为什么不够？

**面试者：** 租约过期只能告诉协调层“可以尝试换主”，不能撤销旧进程已经持有的内存状态和数据库连接。教学模型在权威数据库里为每个源分区、market 分区和发布职责保存 `owner_id/owner_epoch`，新 owner 通过条件更新获得递增任期。

每次权威事务先以条件行锁验证当前任期，例如锁住对应 ownership 行，确认 epoch 与调用者相等，然后在该锁保持到提交的事务里更新状态、cursor、outbox 或发布进度。接管递增 epoch 也必须竞争同一行锁。这样旧事务若先合法提交，就排在接管之前；新任期已提交后，旧主再开启事务会因 epoch 不符失败。不能先在 Redis 检查租约、再无条件写数据库，也不能仅在每分钟心跳时检查一次。

源 canonical 接纳、market Inbox 的权威顺序分配、轮次提交和 outbox 状态写都要覆盖，不能只围住价格表。Go 的互斥锁只约束一个进程，单 owner 协程也不能替代跨进程任期检查。

这仍依赖“唯一的权威数据库写域”。若数据库本身裂成两个都可写且互不仲裁的主库，两边各自递增 owner_epoch 也会形成两套合法记录，应用层围栏无法救场；数据库高可用必须先保证主库唯一或故障时拒写。取舍是故障分区时宁可暂停，也不允许两个 market owner 独立裁决。

## 第7层：新主从哪一个位置接管，快照最新就够了吗

**面试官：** 你挡住了应用双主。但备库最新快照和主库最后一次提交可能相差几秒，新主到底以谁为准？数据库事务成功能否直接推出接管不丢？

**面试者：** 不能。快照只是恢复起点，最新性必须由数据库复制和事务日志前缀证明。接管先按数据库的仲裁与恢复规则确定唯一权威库，确认它包含服务曾承诺持久化的提交范围，再从快照加后续日志恢复到该范围；没有日志位置、复制水位和确认语义，仅靠文件时间不能证明最新。

若承诺 RPO=0，确认条件应覆盖声明的故障模型，确保新主不会丢掉已确认源 cursor、轮次或 outbox。主库本地提交、备库收到日志、备库持久 flush 和完成 apply 是不同水位，要说明配置到底等待哪一步；全站故障不在单机同步副本模型内，就不能声称全站也零丢失。

若承诺有限 RPO，异步复制缺口必须在接管状态中显式呈现。新主不能因为有一个旧的 VALID 2000 快照就继续实时服务；需要识别丢失区间、尝试恢复剩余 Raw/Inbox/结果日志并对账。外部消费者已经见过而权威库丢失的结果不能通过复用 id 写另一份内容来“修复”。

确认权威前缀后，新 owner 取得新 epoch，加载与该前缀一致的源/market 状态，验证 pending 交付，再恢复处理。源分别按证据处于 SYNCING、GAPPED、QUARANTINED 或 READY；产品是否可用重新由有序输入和期限判断，不把统一切主开关当成 READY 的充分条件。

这使“接管完成”成为可核对的状态，而不是进程启动成功的同义词。

## 第8层：旧任期已经提交的 outbox 要不要全部扔掉

**面试官：** 新 epoch 已生效，你说旧主不能再写。那 outbox 里 owner_epoch 还是旧值的记录，究竟是非法数据还是必须补发的义务？旧主已经在途的消息怎么处理？

**面试者：** 必须区分“事实形成时的任期”和“当前谁有权继续工作”。旧任期在被替换前已经合法提交的 outbox 是权威历史的一部分，不能一刀切丢弃；新合法发布器以自己的当前任期认领并补发，保留旧记录的业务 id、payload hash、T、round/revision 和原有效期，只新增认领与发送 attempt 的运维证据。

新任期之后旧主发起的新提交必须拒绝。但旧主在围栏切换前已读取或已发出的网络包无法由数据库撤回，仍可能到达 broker。因此消费者按业务身份去重，按连续 publish_seq 检测缺口，按 round/revision 管理当前投影；不能简单规定“消息创建 epoch 小于当前就全部丢弃”，否则会丢掉合法历史义务。

新主也不能假设 outbox 标成 SENDING 就已交付；未有可信接纳确认的记录允许重复发送。发送确认丢失，最多增加相同事实的重复包，不重新生成一个更晚 T 的事实。旧主若尝试更新发送状态，也因当前 epoch 检查失败。

如果 broker 另外提供生产者 fencing，可以减少旧连接继续写入，但不替代业务去重、历史有效期和数据库围栏。这个取舍接受少量在途重复，避免为了“切换干净”而丢掉已经承诺的交付。

## 第9层：历史恢复正确，为什么仍不能立即发布有效价

**面试官：** 新主已经补齐日志和 outbox。现在历史上 Q1 的 2000 完全一致，为什么还不能立即恢复对外有效服务？重放期间到底该不该推进时间？

**面试者：** 历史重放不能用当前时间改变旧轮次，但恢复实时服务必须面对现在。这两个阶段应明确分开。

历史阶段严格使用原 T、tick、规则和输入顺序，得出原 `VALID/UNAVAILABLE` 与原 `valid_until`，以验证恢复一致性。Q1 贡献源 A/B/C 的截止分别为 T+1900、T+1880、T+1920ms，叠加产品上限后 `valid_until=T+1000ms`。几秒后重放出 VALID 的历史结果，并不代表现在仍可使用。恰好 age=2000ms 的贡献源可以通过历史筛选，却使截止不晚于 T，实时条件从 T 开始就不满足。

接管实时阶段由新 owner 将接管时的时间/时钟质量证据和应有失效 tick 持久写入有序 Inbox，再由正常事务生成当前轮次的决策。如果调度器因崩溃漏发了本应产生的 tick，不能假造其在历史上准时到达；应保留中断区间，在当前真实持久位置补记控制输入。即便该输入尚未处理，对外出口也必须以可信 `now<valid_until` 防止旧价继续有效。

新观测要重新满足源连续性和同步约束。重连后本地连接世代变化不构成源 native_epoch 变化；相同 native 流仍应接续 seq，存在缺口就按 GAPPED 恢复。旧回补 event_time 不刷新，新 T 也不会把五秒前观测变新。

因此接管后可以先提供明确 UNAVAILABLE，并将 last_good 独立展示；只有新的有证据决策满足规则、没有未解决缺口且尚未到期，才恢复实时有效服务。这不是重放不成功，而是历史正确性和当前可用性本来就是两个判断。

## 第10层：日志删掉或上游不支持补发，还能恢复多完整

**面试官：** 你依赖 Raw、控制日志和后续日志。若快照坏了，老日志已被清理，上游又只提供当前 BBO，这时怎样选择保留策略，又怎样诚实处理不可恢复区间？

**面试者：** 保留策略先由承诺倒推，而不是磁盘满了再删。至少计算恢复所需最新可用快照及其依赖、其后 Raw/canonical/Inbox 控制日志、规则与执行语义包、判重历史和待交付 outbox；还要覆盖最慢承诺消费组的补发窗口、审计需求和备份恢复窗口。清理前验证 manifest 闭合、备份可读取、恢复起点存在，不能因为生成了新快照文件就立刻删除其依赖。

故障时按完整性分级：有有效快照和连续后续日志，可以恢复声明前缀；缺一条控制或轮次 marker，就不能声称完全重现中间轮次；只有 Raw 时，可能重新规范和计算部分证据，却未必重建原到达顺序与发布身份；只有当前外部 BBO，则最多建立未来同步基线，无法补出丢失历史。

原始证据保持不可变，缺失区间记录为 gap，包括已知起止、涉及的流、最后可信位置、不可恢复原因和受影响产品。若协议支持重同步，可以经过 SYNCING 和新的已证明连续基线恢复未来 READY，但历史 gap 永久保留在完整性声明中；若不能证明未来边界，就继续 GAPPED 或不可用。不能通过更换连接世代、手工清空 cursor 或将旧数据接收时间改成现在，把历史缺口洗成完整。

Web3 重组是独立链变体，不改变本题 CEX 前提。若存在链上证据撤回，应以持久控制和追加 revision 修订受影响结果，不删除 Raw 来让重放“看不到曾经发生过什么”。

验证应设计为从损坏快照回退到上一个可用 manifest、重放至固定切点、比较状态/结果/交付摘要；再设计缺失日志时能否明确停在缺口而不是输出伪正确价格。本题只规定验证输入和预期，不执行测试，也不声称已测得 RTO/RPO。

## 收束：机制、易错边界与反例验证

**讲透的机制：** 恢复输入进度、业务裁决与交付义务；因果闭合的快照切点；完整 manifest；固定 T、顺序、控制和规则的确定性重放；逻辑验证与权威恢复分离；数据库事务围栏；按复制承诺接管；合法旧 outbox 补发；保留依赖和不可恢复 gap。

**最容易答错的边界：** 最新 BBO 不是恢复历史；快照文件新不等于提交前缀新；同一 Raw 集合不等于同一到达历史；Redis 租约不等于写围栏；两套独立可写主库不能靠应用 epoch 自救；旧任期已提交事实仍有效，但旧主不能新提交；历史 VALID 不等于现在未过期；上游无补发能力时不能保证全史完整。

**反例验证，仅作设计推演，不执行测试：** 快照覆盖 market Inbox 700，原主已提交 701 的失效结果及 outbox、未拿到发送确认后失联。先证明新主数据库是否包含承诺过的 701，再取得新 epoch。若包含，应补发同身份同 hash 的 701，重复不改变消费者结果；旧主尝试提交 702 必须被围栏拒绝。若不包含且服务声明 RPO=0，则接管条件不成立，不能仅加载快照中的 2000 并宣布恢复。另将历史回放时钟拨到现在，预期历史结果摘要仍相同，但实时出口因原 valid_until 已过而保持不可用。
