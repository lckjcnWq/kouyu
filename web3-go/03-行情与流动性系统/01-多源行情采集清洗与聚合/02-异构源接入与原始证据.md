# 大问题 2：多源接入怎样保留原始证据并处理协议差异？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 协议能力契约 | 先说清一个源能提供什么、保证到哪，再决定怎么接。 | 区分完整观测、序号增量、原生快照和历史回放；未知能力不能默认最强。 |
| 完整 BBO／增量 | 完整 BBO 给出双边当前值，增量只告诉你局部变了什么。 | Q1 只接完整 BBO；增量源须先依原协议重建合法视图，不能跳过缺口直接使用。 |
| Raw | 保存收到的原始内容与接收证据。 | 统一 JSON 已经经过解释，不能替代原文；敏感连接信息须按明确策略处理。 |
| 原始字节摘要／业务摘要 | 前者核对保存的字节，后者核对同一事件的业务内容。 | 接收时间和连接包装不同可导致字节不同，却不一定构成业务冲突；脱敏摘要须说明对象。 |
| 原生业务身份 | 上游协议对一次业务事件的标识。 | 有稳定身份才有相应的强去重依据；自己生成 UUID 不能补出上游身份。 |
| 连接世代 | 本地这一轮连接生命周期的编号。 | 标记接收路径，不加入原生事件身份；两个连接也不是两个独立经济来源。 |
| pong | 对方对连接心跳的回应。 | 只证明链路某环节响应，不证明订阅正确、报价更新或规范状态跟上。 |
| SYNCING／READY | 正在建立同步依据，以及已建立协议要求的同步资格。 | 重连成功不能直接变 READY；READY 仍须另查报价年龄。 |
| 回补／当前快照 | 回补找回过去事件，快照提供某个位置的完整状态。 | 新快照可以恢复当前状态，但不能证明断线期间没有遗漏变化。 |
| 限频预算／退避抖动 | 共享请求配额，并把失败重试分散开。 | 按源实际限频作用域调度实时与恢复任务，避免同时重连打满上游。 |
| 持久边界 | 系统承诺故障后仍能找回记录的确认位置。 | Q1 先保存 Raw 再产生权威产品；先发后存的快路径不能冒充同等可恢复产品。 |
| 历史连续范围 | 有证据证明哪些过去区间没有缺失。 | 与当前状态是否同步分别记录；恢复到相同价格不等于中间历史完整。 |

## 把整篇文章压缩成一个故事

接入工程师阿岚给同一场所开了两个 WebSocket，希望断线时少丢行情。她没有把两个连接算作两个来源，而是先登记协议能力，再保存各自收到的原始载荷、接收时间与连接世代。同一原生报价到达两次，留下两份接收证据，规范状态只生效一次；若稳定业务内容不同，就保留证据并隔离。后来连接一直回复 pong，目标市场却不再更新，她把连接活跃、同步状态和报价新鲜度分开，旧报价照样失去资格。恢复时，各市场共享源级配额，退避并限制快照、回补和缓存容量；不能因队列塞满就把残片当连续历史。新快照的价格恰好没变，也只能证明当前状态恢复，不能抹掉断线期间的缺口。为守住可恢复承诺，她先跨过 Raw 持久边界才供权威处理，保存前明确脱敏范围，绝不归档密钥。真正的低延迟优化要先测各段耗时；另外开可丢快路径，也必须与可靠产品分开，不能让下游误以为同样有证据保障。

**流程位置与核心机制：** 负责外部协议到持久 Raw 的入口，回答接到什么、能证明什么、在哪些地方可能丢失，以及协议差异怎样显式进入能力契约。第 05 题再深入原生身份、缺口与回补算法，本题不展开完整盘口重建。

**必要前提：** 主例仍是 Q1 的五源现货 ETH/USDC 完整 BBO。原生流内连续序号、完整双边绝对值观测是教学协议前提，不是所有交易所 WebSocket 的统一保证。源事件时间与接收时间分别保存。

## 第 1 层：接入器的责任不只是连 WebSocket

**面试官：** 让你接入多家 CEX 和链上行情，第一版接入层怎么设计？如果大家都能输出 price 和 timestamp，为什么还要做协议适配？

**面试者：** 我会先为每个源建立能力和语义契约，再实现连接。至少说明事件种类、资产对、价格与数量单位、时间含义、身份和序号作用域、快照与增量关系、重连恢复方式、限频与历史补发能力。字段同名不表示业务相同：某条 price 是最近成交，另一条是最优卖价，不能作为同一种候选直接平均。

采集层负责连接生命周期、订阅、读取、限频和 Raw 封装；适配规则负责解释源协议，并输出可审计的规范事件或拒绝理由。Raw 中保留原始载荷、来源、连接世代、接收时刻、内容摘要与原生身份线索。即使解析失败，也应能保留足够证据重现失败，而不是仅打一条“解析出错”日志。

Q1 首版只接完整 BBO，不假装已经支持所有增量盘口、成交聚合和 DEX 池状态。加入链上源时，其区块身份、重组和最终性是明确的新契约，不能把 block number 填进 seq 就认为完成适配。

## 第 2 层：怎样让“能力契约”真的限制程序？

**面试官：** 你列了很多文档字段。如果一个源没有连续序号，工程师还是把它送进统一 seq 检查器，靠约定能避免吗？

**面试者：** 不能只靠说明文字。我会把协议能力做成版本化配置与强类型适配接口，例如声明 `FullObservation`、`SequencedDelta`、`NativeSnapshot`、`HistoricalReplay`，同时声明 identity_scope、sequence_scope 和数量语义。规范层只在能力满足时调用对应状态机，未知能力不能默认当最强能力。

没有连续序号的完整 BBO 流，可以按该源承诺替换当前观测并记录收到的位置，但不能声明检测到了所有中间漏包。增量盘口必须先按其原生协议重建合法源视图，再产生 BBO；不能跳过缺口，把收到的两条变化直接当全新完整报价。接口输出应携带输入种类和资格证据，让下游知道这个数如何成立。

这也是版本边界。某源新增 checksum 或修改订阅聚合方式时，应有新能力版本与生效点；历史输入仍按旧能力解释。把所有输出压成 `{price, timestamp}` 会隐藏不确定性，反而使统一服务更难正确使用。

## 第 3 层：保存哪些原始数据才足够？

**面试官：** 有了能力配置，Raw 直接保存解码后的统一 JSON 不就够了吗？保存完整原始字节是不是浪费，而且还可能含敏感信息？

**面试者：** 统一 JSON 已经是一次解释结果，不能代替原始证据。解码可能丢掉未知字段、数字文本、枚举差异和消息边界；如果先把数字转成 float64，后面保存再多字段也无法恢复原来的十进制。Raw 应保留协议载荷或经过明确安全处理的原始内容，并关联采集器版本、源定义、接收身份与摘要。

但原始不等于无边界地收集秘密。公共行情不需要把 API 密钥、认证签名、完整 Cookie 或用户私有回报写进归档。应在封装规则里区分行情载荷与敏感连接元数据；必须脱敏的字段说明脱敏策略和可验证范围。若保存的是脱敏内容，摘要也要明确对应保存内容还是传输原文，不能拿不同字节的 hash 混称同一证据。

大载荷可先写不可变对象，再由 Raw 记录引用对象地址、长度和内容摘要；只有对象已达声明持久边界，引用才可提交为可用。对象缺失时不能推进解释进度。成本可以通过保留期、分层存储和压缩管理，但删除前要检查回放、审计与去重承诺依赖，不能为了省容量静默缩短已经承诺的恢复范围。

## 第 4 层：两个连接收到同一报价，算什么？

**面试官：** 假设为降低断线风险，同一源开两个 WebSocket 连接，同一 native_seq 在两个连接各收到一次。两份 Raw 的字节或接收时间还可能不同，怎样记录才不会把它当两个源或冲突？

**面试者：** 两次接收有两个 Raw 身份，因为路径和接收时刻确实不同；但可能对应同一个原生业务事件。业务身份使用源原生流与 seq，连接世代只表示本地连接生命周期，不加入原生业务身份。源独立组也仍是同一组，两个连接不是两个经济来源。

冲突检查比较稳定业务内容摘要，而不是整个接收信封的 hash。接收时间、连接世代和传输包装不同不应制造业务冲突；协议中具有业务意义的 bid、ask、数量和源事件时间等必须纳入。原始字节摘要仍保留，用于核查两个包装究竟哪里不同。如果稳定业务内容相同，规范状态只生效一次；不同则保留两份证据并隔离，不能挑更晚到的一份覆盖。

若源协议没有稳定业务身份，我们就不能靠自行生成 UUID 声称原生事件去重完备；UUID 只能消除自己重发同一记录。可以建立受限的内容指纹启发式，但要说明相同数值可能是两次真实观测，启发式不能悄悄吞掉合法更新。

## 第 5 层：连接没断，为什么还要判源失效？

**面试官：** 你把两个连接视为同一源。那只要有一个连接持续收到 pong，是不是这个源就可以保持 READY？为什么还需要报价停滞检测？

**面试者：** pong 证明连接某个环节在响应，不证明目标市场订阅生效、业务数据持续产生或我们已应用到最新位置。还可能出现订阅确认丢失、服务端只发心跳、解析器持续失败、写入阻塞或某个 symbol 被停止推送。所以要把连接活跃、协议同步资格与报价新鲜度拆开。

READY 在 Q1 表示已建立原生流的可信同步状态，不是永久新鲜证书。报价是否进入本轮，还要按 T 与源事件时间检查。监控分别看最后网络字节、最后合法业务事件、最后持久 Raw、最后规范应用和源时间年龄，才知道停在哪里。某个市场长期无更新是否异常，也应结合该协议的事件产生规则，不能对所有市场用相同“每秒必须一条”假设。

重连后也不能立刻把 SYNCING 改成 READY。要确认订阅、原生 epoch 与恢复位置；需要快照的源取得可衔接快照，需要回补的源补齐或明确历史缺失。源状态与控制事件持久提交，不能只在采集进程内设布尔值。

## 第 6 层：重连怎样避免把上游压垮或永远恢复不了？

**面试官：** 你说失效后要回补和重连。如果五十个市场同时断线，所有连接都立刻重订阅、拉快照，怎么避免恢复流量把上游限频和本地存储一起打满？

**面试者：** 恢复也是受控工作负载，需要源级共享限频预算、指数退避与抖动、并发上限，以及实时与回补任务的优先级。不能每个市场各自认为有完整 API 配额；供应商按 IP、账号或连接限频时，应在相应作用域统一分配。明确的限频响应要更新下次可尝试时间，而不是忙循环重试。

队列和缓存必须有界。恢复期间若增量到达快于快照建立速度，可以丢弃这次未完成同步并重建新的同步点，但必须保持源不合格并记录原因；不能把缓存溢出后的残片宣布为连续历史。若源不能暂停，我们只能承认有未接收数据，按能力回补或显式标缺口。

退避不能取代可观测的终止条件。达到恢复预算、无法取得历史或长期不支持目标市场时，要告警和隔离，输出证据不足，而不是无限重试同时对外显示健康旧价。具体快照衔接由第 05 题解释，本层确保恢复请求的调度不会破坏其前提。

## 第 7 层：为了低延迟，能否先发布再补 Raw？

**面试官：** 上一答为了恢复和取证保存了很多状态。若行情时延要求很低，先从内存规范化并发布，Raw 异步归档，能不能同时声称低延迟和完整可恢复？

**面试者：** 可以设计两类服务，但不能给一条没有越过持久边界的路径附加完整恢复承诺。Q1 选择先保存 Raw，再提交规范输出，所以权威产品可以回指已持久证据。先发后存的变体在进程崩溃时可能留下已经被使用、却没有完整证据的结果，不能说它和 Q1 的可靠产品等价。

如果业务明确需要更快观察，可以单独提供标为非权威、可丢失的快路径，使用不同产品身份和能力契约，不能让消费者在相同 topic 上无法区分。若快路径影响真实交易决策，调用方要承担并设计其证据与风险约束，不是加一个 `provisional` 字段就自动没有影响。

真正优化 Q1 应先测延迟分解：接收、排队、Raw 提交、规范处理和发布各占多少，再考虑批写、分区、减少分配或复制策略。改变持久确认点属于保证变更，不只是性能开关。没有测量不能虚构“异步后降低多少毫秒”，也不能用更快掩盖恢复范围缩小。

## 第 8 层：接口返回成功，仍有哪些数据根本恢复不了？

**面试官：** 你保住了已持久的输入。如果采集器重启后从 REST 拉到当前 BBO，而且数值和断线前一样，能否把断线期间标为完整无缺口？

**面试者：** 不能。当前完整快照能帮助恢复当前状态，不证明中间没有变化。价格先涨后跌再回到原值，两个端点相同，但中间市场历史不同。若源提供权威、覆盖该范围的历史序列，才能按其完整性契约补齐；只拉当前 BBO 不能还原中间所有观测、成交或路径。

因此应分别记录“当前状态已同步”和“历史连续范围”。新快照可能使当前源恢复 READY，同时历史缺失区间仍永久保留。消费者做最新观察可接受新同步状态，做策略回测或完整事件研究则必须看到缺口。不同用途不能共用一个没有范围说明的 healthy 标志。

我会用一个独立反例检验采集承诺：断线期间发生两次方向相反的变化，恢复端点不变。如果系统自动把缺失区间抹掉，说明它把状态恢复当成事件恢复。已持久输入的确定性重放是可实现承诺，未接收且不可回补的事实不是靠重试或数据库事务能够补出来的。

## 本题收束

**讲透的机制：** 协议能力先于统一接口，Raw 接收证据与原生业务事实分层；连接、订阅、同步和新鲜度分别管理，恢复请求受配额与容量约束。

**最容易答错的边界：** 两个连接不是两个独立源，传输信封不同不等于业务冲突，pong 不等于报价有效，当前快照不证明历史完整，异步归档不能冒充已跨越可靠边界。

**反例与验证方法：** 构造同一业务事件跨两连接重复、只有 pong 没有报价、断线端点相同但中间变化的三组输入；检查 Raw 能保留接收差异，规范状态不重复生效，当前资格到期，历史缺口不被新快照抹除。这是验证设计，不声称已进行工程实验。
