# 盘口重建、行情计算与实时推送

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| ResultBatch | 撮合确认后交给下游的一整包事实 | 包含成交和价位最终量；可靠提交后不能因行情故障撤销成交。 |
| L2 盘口 | 按买卖方向、价格汇总的剩余挂单量 | 不含账户、订单身份及同价排队位置；行情服务不因此获得撮合权。 |
| 绝对量更新 | 把该价位剩余量直接设成指定值 | 不是再加减一次；零量删除，但仍需顺序和缺口校验。 |
| sourceLogID / sourceSeq | 源日志身份证和该交易对的事实位置 | 无成交批次也推进；不是过滤后的成交编号或消息队列偏移。 |
| depthSeq / tradeSeq | 对外深度帧和逐笔成交各自的排号 | 深度可合并多批，逐笔按笔编号；不能与源序号互换。 |
| streamID / epoch / leaderTerm | 频道身份、发布历史世代和领导权令牌 | epoch 隔开不可混接的历史，leaderTerm 在受保护资源处隔离旧主。 |
| 快照锚点与订阅屏障 | 一张定格图，以及拍图期间先接住更新的安排 | 快照内容须匹配已提交发布序号；客户端再从该位置连续应用。 |
| BBO / Top-N | 最优买卖报价，以及只展示前若干档 | 从完整簿派生；报价不等于最新成交价，限深不能丢失补档依据。 |
| V / Q / VWAP | 成交量、成交额、按成交量加权的均价 | V=Σq，Q=Σ(p×q)，VWAP=Q/V；本批贡献不冒充全天累计。 |
| 事件时间 / K线修订 | 成交发生的时间，以及对旧时间桶的更正 | 不是网络收到的时间；滚动窗口与K线桶有不同边界和版本。 |
| tick / lot / 定点数 | 价格和数量各自的最小步长及整数表示 | 乘积有金额单位，须防溢出；显示舍入不反写精确盘口。 |
| GAP / STALE / 重同步 | 缺事实、数据过旧，以及重新建立可信起点 | 心跳正常不证明行情完整；断线可续传不等于任何时候都能免快照恢复。 |

## 把整篇文章压缩成一个故事

B1 想买入 0.25 BTC，撮合按原有卖盘形成两笔成交，可靠提交批次 101。行情值班员小林没有去改余额，而是让单写者先核对源身份和连续位置，再把卖 60000 删除、卖 60100 设为剩余 0.05，同时记录成交贡献。读者只能看到整批完成的版本，不能看到扫单一半的盘口。本批成交额为 15015 USDT、均价为 60060，既不是卖一报价，也不是全天统计；账户链路另行结转并释放零费案例中的预留价差。发布器从完整簿派生限深视图，用自己的深度序号记录合并范围，逐笔则逐笔保留。网关先接住更新再取同切点快照，客户端校验身份、连续应用后才算跟上。若慢连接积压，就明确失效并重同步，不让它拖住撮合；若源缺批，旧簿只能带异常状态展示。进程崩溃靠检查点和可靠日志恢复，切主还要在发布资源处挡住旧主。小林最后对照重放结果和端到端新鲜度验收，记住快照只恢复它承诺的状态，连接在线、序号看似连续和余额可用都不是同一件事。

---

本专题面向 Go / Web3 交易后端面试，按“完整业务 → 核心板块 → 核心机制 → 统一设计 → 母题连续问答 → 一个简洁 MVP”组织。一个母题一个文件；以下方案是教学设计，不代表个人生产经历或实测结果。

## 一、文字全流程

### 1.1 讨论基线

- **产品与交易机制**：BTC/USDT 托管现货订单簿，价格时间优先、Maker 价成交；案例手续费设为零。不是 AMM，也不是链上结算订单簿。
- **权威状态**：撮合负责订单与成交事实；行情服务消费已可靠提交的 `ResultBatch`，维护可重建的公共投影，无权撮合、撤单或修改资产。
- **发布边界**：批次已提交后可以发布公共行情，不要求等账户结转为 `APPLIED`；但行情可见不代表余额已可用。账务失败保留成交义务，由账户链路恢复，不能撤回真实成交来修行情。
- **公共数据**：完整 L2 按买卖方向和价格聚合剩余量，不公开账户、订单身份和同价队列。对外可提供全量价位视图或明确限深的 Top-N 视图。
- **顺序**：一个交易对的投影由单个逻辑写者处理。`sourceSeq` 是该交易对已提交结果流的连续位置，不是过滤后的逐笔成交编号，也不是 Kafka offset 或时间戳。
- **恢复范围**：当前 L2 快照只保证盘口起点，不自带历史成交、24 小时统计或 K 线。指标初始化另取可信历史或完整指标检查点；缺少时明确标记 WARMING/UNAVAILABLE。案例中的 0.25 BTC 与 15015 USDT 是批次贡献，不冒充全历史累计值。
- **实现范围**：用 Go 1.21+ 的单写者、不可变帧、有界队列与可靠源日志解释机制，不搭建实际工程。跨市场聚合与链上重组仅作为改变前提后的比较。

### 1.2 贯穿案例与单位

价格单位为 USDT/BTC，数量单位为 BTC，金额单位为 USDT。`tick=0.01 USDT/BTC`，`lot=0.01 BTC`。内部使用整数 `priceTicks` 和 `qtyLots`；如 60000 对应 6000000 ticks，0.10 对应 10 lots。时间示例均为 UTC。

初始源快照水位 `sourceSeq=100`：

| 方向 | 价格 | 剩余量 | 说明 |
|---|---:|---:|---|
| 买 | 59900 | 0.40 | 最高买价 |
| 卖 | 60000 | 0.10 | 卖单 S1 |
| 卖 | 60100 | 0.20 | 卖单 S2 |

用户 B1 买入 `0.25 BTC @ 60100`。已提交批次 `sourceSeq=101` 包含：

1. `tradeID=T101-1`：`0.10 BTC @ 60000`，成交时间 `12:00:10.100`。
2. `tradeID=T101-2`：`0.15 BTC @ 60100`，成交时间 `12:00:10.101`。
3. 批次结束后的价位绝对量：卖 60000 为 0，卖 60100 为 0.05；B1 全成，没有新增买档。

正常后续批次 `102`：卖 60200 新增 0.30 BTC，无成交。异常题里的“先收到 103”“跨代重建”等均是独立变体，不累计改变这条正常路径。

### 1.3 主链路

```text
B1 提交买单 0.25 BTC @ 60100
    ↓
交易接入与预留〔交易链路负责准入、预留和订单身份〕
    ↓
撮合裁决〔生成两笔成交、订单变化及价位最终绝对量〕
    ↓
可靠提交 ResultBatch 101〔事实不可因行情失败而取消〕
    ├─ 账户链路 → 消费成交并结转预留资产 → 形成可查询账务结果
    └─ 行情接入 → 校验交易对、源世代、sourceSeq、批次完整性
                       ↓
                 单写者原子应用整批
                 〔L2 + 本批成交指标 + sourceSeq 一起前进〕
                       ↓
                 生成同水位不可变视图
                    ├─ 深度/BBO → 发布器生成连续 depthSeq 与源覆盖区间
                    ├─ 逐笔成交 → 每笔独立 tradeSeq、稳定 tradeID
                    └─ ticker/K线 → 按约定窗口、事件时间和版本计算
                       ↓
                 可续传日志/环形缓冲与快照版本协调
                       ↓
                 网关订阅屏障 → 快照 → 连续增量 → 实时扇出
                       ↓
                 客户端校验身份与序号，整帧更新本地簿
                       ↓
                 页面标明版本与新鲜度，展示本次成交和新盘口
```

主要完成条件不相同：撮合提交意味着成交已确定；投影到 101 意味着行情已处理该事实；网关写出意味着字节交给连接，不代表用户已展示；客户端应用到某序号才意味着其本地视图达到该版本。公共页面的任何完成状态都不能替代账户结转。

### 1.4 主要异常分支

```text
重复 101 → 身份/内容相符则忽略，不重复累计成交；相同位置内容冲突则隔离
期望 101 却先见 103 → 停止推进 LIVE 水位 → 有界等待/补取 101、102
    ├─ 能补齐 → 连续应用，再恢复 LIVE
    └─ 日志已过期或缓冲溢出 → 重取一致快照 → 建立新订阅屏障
快照生成期间继续产增量 → 先挂缓冲，按快照序号裁剪，再连续交付
慢客户端队列超限 → 明确 RESYNC_REQUIRED 或断连，不静默丢深度帧
行情进程崩溃 → 从检查点和可靠源日志重放，不能要求撮合重做成交
源链路异常而连接仍存活 → 显示 STALE/GAP，不用 Ping/Pong 伪装数据新鲜
```

### 1.5 沿案例核对状态与资金

批次 101 应用后，最高买价仍为 59900，最高卖价变为 60100、卖一量 0.05；卖 60000 被删除。两笔成交的总量为 `0.25 BTC`，总额为 `6000 + 9015 = 15015 USDT`，本批 VWAP 为 `60060 USDT/BTC`。本批结束 BBO 的价差为 `200 USDT/BTC`，中间价为 `60000 USDT/BTC`，最新成交价为 `60100 USDT/BTC`，三者不能混称“当前价格”。

交易链路为 B1 预留的限价资金是 `60100 × 0.25 = 15025 USDT`；实际支出 15015，零费条件下应释放价差 10。卖方合计交付 0.25 BTC。行情只引用这些已确定事实，不写余额、不负责释放预留。账务最终应依两笔成交身份幂等结转；行情重复收到 101 不能多生成一笔成交或再次增加成交量。

## 二、核心板块

| 板块 | 决定什么、为什么核心 | 拥有的状态与交互契约 |
|---|---|---|
| 权威事实接入 | 判断“到底漏没漏、能不能继续” | 源身份、连续水位、批次完整性；向源日志补取，不能靠时间排序猜补 |
| L2 重建 | 决定当前可展示盘口是否正确 | 完整买卖价位、精度元数据；整批应用、单写者推进 |
| 行情计算 | 决定成交量、价格、窗口统计是否可信 | 成交身份、滚动窗口、K线版本；成交驱动，不用盘口变化猜交易 |
| 发布与快照衔接 | 决定客户端能否构造同一版本状态 | 每视图连续序号、源覆盖范围、可续传记录、快照锚点 |
| 实时分发与客户端恢复 | 决定弱网、扇出与背压是否伤害正确性 | 订阅身份、有界队列、应用游标、重同步状态机 |
| 恢复与验证 | 决定故障后能否继续给出可信行情 | 一致检查点、领导权隔离、重放校验和、端到端新鲜度 |

## 四、统一设计与规则

### 4.1 不变量、公式与边界

1. 完整 L2 的键是 `(side, priceTicks)`，量为非负 `qtyLots`，零量删除。事件使用**价位最终绝对剩余量**，不是正负增量；同一批次同一键只出现一次最终值。
2. `sourceSeq` 从最后已应用位置逐批连续推进；无成交、无盘口变化的合法结果也推进源水位。不能在已过滤成交流上要求每个 `sourceSeq` 都出现。
3. 整批提交可见；正常连续撮合的批次结束时若双边非空，`bestBid < bestAsk`。一侧为空时 BBO 相应字段为 `null`，中间价和价差不伪造为 0。
4. 成交量 `V=Σq`，成交额 `Q=Σ(p×q)`，VWAP 为 `Q/V`，无成交量则为 `null`。最新价按权威成交顺序确定；不能用最大到达时间选择。
5. 窗口定义为 `(T-W, T]`，其中 `T` 是服务端声明的行情计算时点；一分钟 K 线定义为 `[minuteStart, minuteStart+60s)`。滚动统计和 K 线桶边界不同。
6. 价格与数量乘积先使用经过范围检查的宽整数/定点十进制，再按 scale 转换；Go 的 `int64`、乘法溢出和浮点误差都不能忽略。输出十进制字符串；不得让 JavaScript 的 `Number` 承接任意 64 位整数。
7. 普通深度流允许合并中间变化，但承诺覆盖范围内每个变更键的最终绝对值及删除。逐笔成交流不能以“最新价覆盖”冒充无损交付。
8. 公共行情允许延迟，不允许把缺口后的簿标成 LIVE；允许 STALE 的旧快照，但必须带水位与状态。行情不承诺所有客户端同时可见。

### 4.2 三类序号与世代

| 字段 | 作用域 | 含义与使用限制 |
|---|---|---|
| `sourceLogID + sourceSeq` | 单交易对权威结果流 | 源日志身份与连续位置；正常撮合主备切换若保留同一日志不改身份 |
| `streamID + epoch + depthSeq` | 单交易对、深度规则及视图 | 发布深度的连续位置，和 sourceSeq 不一一对应；快照锚定该序号 |
| `streamID + epoch + tradeSeq` | 单交易对逐笔成交流 | 每笔成交递增，成交保留稳定 tradeID；批次 101 可以产生两条 |
| `candleKey + revision` | 单交易对、周期、开始时间 | 同一根 K 线的修订顺序，不当作盘口游标 |
| `leaderTerm` | 受保护发布资源 | 切主 fencing 令牌，不等同于客户端 epoch |

发布 `epoch` 标识不可混接的序列历史，**每个发布 epoch 固定绑定唯一 sourceLogID**。正常接管只有在源日志身份不变、恢复发布水位、保留帧内容并隔离旧主后才可延续旧 epoch；本专题默认恢复或接管无法证明这些条件时新建 epoch，通知重同步。源日志身份更换则必须通过授权换源屏障新建发布 epoch，不允许把旧源 501 到新源 1 写成同一个连续覆盖区间。不能改 epoch 来掩盖源数据缺失：新 epoch 的快照仍须来自连续、可信水位。

### 4.3 核心对象与交互

```text
ResultBatch:
  market, sourceLogID, sourceSeq, schemaVersion, instrumentVersion
  levelSets[] = {side, priceTicks, qtyLots}       // 本批最终绝对量
  trades[] = {tradeID, eventTime, priceTicks, qtyLots, ordinal}
  batchHash                                    // 可验证完整内容

Projection:
  sourceLogID, lastSourceSeq, fullL2, health
  成交窗口/K线计算状态及规则版本                // 仅恢复需要时持久化

DepthFrame:
  streamID, epoch, depthSeq, prevDepthSeq
  sourceLogID, sourceFrom, sourceTo, levelSets[], viewVersion // 同源连续覆盖

DepthSnapshot:
  streamID, epoch, depthSeq=S, sourceLogID, sourceTo=W
  viewVersion, bids[], asks[], checksum, health
```

`sourceFrom/sourceTo` 是发布器上次覆盖位置之后、本次覆盖到的连续源范围；即使其中没有深度变化，也不能谎称存在逐批深度帧。可通过明确的进度帧推进覆盖水位和 depthSeq；单纯传输心跳不具有此含义。不同 channel 的覆盖进度分开维护，不能拿 ticker 水位代替深度已交付水位。

相同源位置而不同 `batchHash` 是源事实冲突，不按普通重复忽略。快照必须以不可变视图/一致检查点生成，源水位与价位内容匹配。运行中生成发布快照，只能锚定已经完成该视图发布提交的 depthSeq；不能把投影最新 W 硬贴到旧发布 S。

### 4.4 架构与提交边界

```text
已提交源日志〔可回放，按交易对路由〕
    ↓
单交易对投影写者〔完整批次校验 → 更新私有状态 → 推进源游标〕
    ↓ 同水位不可变视图/有界发布交接
发布器〔按视图差分/聚合 → 分配发布序号〕
    ↓
发布记录 + 对应快照锚点〔协调提交；承诺可续传范围〕
    ↓
网关分片〔先登记订阅缓冲 → 取已提交快照 → 衔接缓存帧〕
    ↓
每连接唯一写协程〔限字节数和年龄的队列〕
    ↓
客户端〔身份校验 → 序号连续 → 原子更新 → 渲染〕
```

- 源提交与行情消费不在一个分布式事务里。行情落后可重放，不能倒逼撮合撤销提交事实。
- 投影内多个价位、指标和游标属于同一批次原子可见范围。持久检查点必须包含它声称覆盖的全部恢复状态；不持久化某指标就明确从日志重建它。
- 发布序号分配、帧内容、可续传记录与快照锚点需要一致协调。可以使用单写者发布日志；若只用易失环形缓冲，进程重启后换 epoch 并重同步，不承诺原 epoch 跨重启可续传。
- 客户端应用和服务器写 socket 不在共同事务里；采用游标、重复抑制、断线恢复，而不是端到端 exactly-once 口号。

### 4.5 实现选择与替代条件

教学实现采用“哈希表存价位量 + 有序价格索引”的完整 L2；单交易对单逻辑写者，读侧引用不可变版本。价格稠密、范围受限时可比较数组/位图；不能把不同数据结构的复杂度混写。Top-N 从完整 L2 派生，不能直接把视图外价位丢掉后还声称能正确补档。

如果源来自外部交易所，应以其文档的更新 ID、区间与快照契约为准，本专题的 `sourceSeq` 逐条规则不能直接套用。如果改成链上订单簿，需加入区块 hash/高度、日志位置、确认级别及重组回滚；如果改成 AMM，深度是由储备与报价曲线推导的估算，不是原生挂单 L2。

## 七、工程实践——一个简洁 MVP

### 7.1 目标与范围

只验证“可信全量快照 + 连续绝对量批次 → 原子更新 L2 → 正确 BBO 与本批成交统计”的小闭环。MVP 采用单写者、同步输入和批次内唯一成交身份；不实现持久化、WebSocket、发布聚合、补日志、完整滚动窗口或主备，也不声称通过工程测试。

### 7.2 核心伪代码

以下 `sumWide` 表示带范围检查的宽整数求和；`qtyLots` 的 lot 为 0.01 BTC，价格一个 tick 为 0.01 USDT/BTC，因此乘积一个单位为 0.0001 USDT。校验失败不修改旧价位和已应用水位，但健康状态会按原因转为 INVALID 或 RESYNC_REQUIRED。

```text
state = {logID, lastSeq, bids, asks, health: LIVE}   // 从可信快照 100 载入
highestSeen = state.lastSeq                         // 接入元数据，不是已应用水位
onBatch(b):
    if state.health in {INVALID, RESYNC_REQUIRED}: return REBUILD_REQUIRED
    if b.logID != state.logID: state.health = RESYNC_REQUIRED; return RESET_REQUIRED
    if b.seq <= state.lastSeq: return DUPLICATE     // MVP 假设重复内容相同
    if schema/精度不符 or 重复价位键 or 非法价格/数量/成交身份:
        state.health = INVALID; return INVALID_BATCH
    highestSeen = max(highestSeen, b.seq)
    if b.seq != state.lastSeq + 1:
        state.health = GAP
        return NEED_SEQUENCE(state.lastSeq + 1)    // 不提前应用后来的批次
    next = copy(state)                             // 小数据示例，正式方案可不用全复制
    volumeLots = 0; quoteUnits = 0
    for t in b.trades:
        volumeLots = checkedAdd(volumeLots, t.qtyLots)
        quoteUnits = sumWide(quoteUnits, t.priceTicks * t.qtyLots)
        if overflow: state.health = INVALID; return OUT_OF_RANGE
    for x in b.levelSets:
        side = next.bids if x.side == BID else next.asks
        if x.qtyLots == 0: delete side[x.priceTicks]
        else: side[x.priceTicks] = x.qtyLots
    bid = maxKeyOrNull(next.bids); ask = minKeyOrNull(next.asks)
    if bid != null and ask != null and bid >= ask:
        state.health = INVALID; return INVALID_BOOK
    next.lastSeq = b.seq
    next.health = LIVE if next.lastSeq == highestSeen else GAP
    state = next                                   // 整批一次可见
    return {sourceSeq: b.seq, health: state.health, bid, ask, volumeLots, quoteUnits,
            vwapTicks: null if volumeLots == 0 else quoteUnits / volumeLots}
```

伪代码的乘法必须在宽整数类型中执行，不能先以 int64 溢出再转换；VWAP 的除法保留有理数/定点结果，不默认做整数截断，显示舍入另按约定执行。这里只输出本批统计；重复内容冲突校验、可信快照构造和连续源的可靠交付是输入前提，不伪装成已经实现的能力。`highestSeen` 只防止补齐一部分后过早恢复 LIVE，不代表全局最新源水位；本例不保留乱序批次，调用方补齐后须重新送入之前被拒绝的批次。若合法 next 批次因语义或范围错误被拒绝，旧簿保留但健康状态应置为 INVALID 并停止对外承诺 LIVE，等待修复输入或重建。

### 7.3 输入与预期结果

| 独立场景 | 输入 | 手工预期 |
|---|---|---|
| 正常扫单 | 快照 100 后应用 101 | 删除卖 60000，卖 60100=5 lots；bid=5990000 ticks（59900）、ask=6010000 ticks（60100）；成交量25 lots；成交额150150000 quoteUnits，即15015 USDT；VWAP=6006000 ticks，即60060 USDT/BTC |
| 正常无成交 | 已到101后应用102：卖60200=30 lots | 源水位102；原卖一不变；本批成交量0、VWAP=null，不清零历史累计量 |
| 同内容重复 | 已到101再送101 | 返回DUPLICATE；水位、价位、本批之外统计均不增加 |
| 缺口 | 从100直接送102 | 返回NEED_SEQUENCE(101)，health=GAP，仍保留快照100，不能先加入卖60200 |
| 补齐 | 上一场景再送101，然后重送102 | 应用101后仍为GAP；重送102后到102并恢复LIVE，各批事实只应用一次 |
| 非法批次 | 从100送101但包含负量或溢出金额 | 返回INVALID_BATCH或OUT_OF_RANGE；全部旧价位及水位保持100 |
| 空边界 | 独立变体：完整批次删去全部卖档 | ask=null，价差/中间价=null，不能输出价格0 |

## 八、可复用的方法沉淀

本专题采用“系统边界 → 不变量 → 故障窗口 → 恢复动作”的分析顺序。后续设计缓存、CDC、实时榜单等投影系统，也可以先问四件事：权威事实在哪里、版本标识是什么、跨哪个窗口会丢状态、客户端怎样发现失效。**绝对量能降低重放风险，但不能替代连续性证明；连接存活能证明通道可用，但不能证明数据新鲜。**
