# 大问题 7：深度怎样限频聚合又不破坏连续性？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 限频聚合 | 先处理全部事实，再按节奏合成较少的深度帧 | 不跳过源批次，也不承诺展示窗口内每次挂撤单路径。 |
| sourceSeq / depthSeq | 源事实位置，以及指定深度视图的发布位置 | 101、102 可合成下一帧 S+1；两笔成交不必对应两个深度号。 |
| 变更键并集 / 末值 | 窗内所有动过的方向价位，以及各自最后绝对量 | 完整深度不能只保留末批，也不能把多个绝对量相加。 |
| 零量标记 / levelSets | 需要删除的记录，以及帧内价位设置集合 | 簿内已删的键仍须在待发布集合保留删除，避免客户端残留旧档。 |
| sourceFrom / sourceTo | 本帧承接的连续源范围起止位置 | 来自逐批完整校验，不是取所见最小最大号拼区间。 |
| 进度帧 / 心跳 | 无价位变化但提交覆盖进度的帧，以及连接探活 | 前者推深度号和覆盖水位，后者不能证明源已处理。 |
| Top-N / 视图退出 | 从完整簿派生的限深展示，以及离开展示集合 | 退出可编码为删除，但不表示完整簿该价位真实归零。 |
| 已提交视图 / 快照锚点 | 已形成发布承诺的版本，以及快照对应的发布位置 | 最新投影簿不能硬贴旧发布号；订阅屏障修不好错误锚点。 |
| 候选序号 / 发布提交 | 内部分配的位置，以及记录成为对外历史的边界 | 提交不明先查日志；已提交重试必须同号同内容，不重新生成。 |
| 易失环形缓冲 / epoch | 会随重启消失的留存区，以及不可混接的历史身份 | 无法恢复旧帧与锚点则换代重同步，但换代不填源缺口。 |
| fencing / leaderTerm | 资源拒收旧主写入的围栏，以及领导权令牌 | 必须在受保护资源执行，不能只靠客户端 epoch 隔离双主。 |
| tradeSeq / 无损逐笔 | 每笔成交的位置，以及保留所有成交事实的承诺 | 两笔可一起运输，却不能只保留最后价；与聚合深度终态语义不同。 |

## 把整篇文章压缩成一个故事

发布工程师小柏要降低 BTC/USDT 深度推送频率，但没有让投影偷跳批次。写者先完整应用 101 和 102，发布器把它们覆盖为下一深度帧 S+1，记录源范围 101 到 102。合并时收集所有变更键，卖 60000 的零量删除、卖 60100 的最终 0.05、卖 60200 的 0.30 都保留，而不是只发最后新增档或把绝对量相加。若订阅每侧一档，就从完整簿比较旧、新展示集合，删除旧卖一并补入新卖一；退出视图不代表真实挂单清空。即便源批没有深度变化，覆盖进度也须经明确提交，心跳不能代替。小柏把帧原内容、序号、续传记录和可恢复锚点统一提交后，才暴露新快照；提交不明先查，发送失败则同号重发。窗口和队列超预算只能有界等待或显式失效，不能静默漏键。重启若丢了易失历史，就以可信状态换 epoch 重同步，并另用围栏挡旧主。最后他明确产品只承诺连续深度终态，两笔成交仍须各自保留，不能把末值合并宣传成逐事件无损历史。

**流程位置与核心机制：** 已提交结果批次 → 完整 L2 投影 → 限频聚合与视图差分 → 发布提交 → 可续传深度帧及同版本快照。本题关注变更键并集、连续源覆盖、Top-N 补档与发布历史的一致性，不展开连接扇出实现。

前提沿用总览：BTC/USDT 托管现货，价格时间优先、Maker 价成交、零手续费；`tick=0.01 USDT/BTC`，`lot=0.01 BTC`，内部使用整数 `priceTicks/qtyLots`。快照 `sourceSeq=100` 为买 59900/0.40、卖 60000/0.10 和 60100/0.20。正常批次 101 包含两笔成交，结束时卖 60000 删除、卖 60100 剩 0.05；102 新增卖 60200/0.30，无成交。以下异常都是独立变体，不累计改写这条正常路径；全部内容为教学设计，不代表个人经历或实测。

## 第 1 层：多个源批次怎样成为一个深度帧

**面试官：** 批次 101 已经改变盘口，102 又紧接着到达。如果对外深度需要限频，怎样合成一帧，又不把源事件和发布序号混为一谈？

**面试者：** 在这个模型中，限频发生在投影之后，不是让投影跳过批次。单写者先完整应用 101，再完整应用 102，不能截取扫单中间态；发布器在窗口关闭时冻结对应水位的不可变结果。假设初始已提交深度锚点为 `epoch=E、depthSeq=S、sourceTo=100`，这两个批次可以合成下一帧，记为 `depthSeq=S+1、prevDepthSeq=S、sourceFrom=101、sourceTo=102`。这里 `sourceSeq` 属于单交易对权威结果流，`depthSeq` 属于指定 `streamID+epoch` 的发布历史，二者不一一对应。101 的两笔成交不要求生成两个深度序号，102 没有成交也仍须处理。发布器合并的是这些完整批次造成的价位更新，最终帧经过发布提交后才对外可见；窗口只改变发布频率，不改变源事实与处理顺序。

## 第 2 层：末值合并为什么必须保留变更键并集

**面试官：** 你说窗口内合并价位更新。如果实现只保留最后一个批次的更新，或者把同一价位的变化直接相加，会在哪一步出错？

**面试者：** 完整深度的合并必须取窗口内所有变更键的并集，再按源顺序为每个键保留最后一次绝对量，键是 `(side, priceTicks)`。正常案例合并 101、102 后，卖侧应包含 `6000000 ticks→0 lots`、`6010000 ticks→5 lots`、`6020000 ticks→30 lots`，不是只留下 102 的新增档。完整 L2 遇零量会删除实际价位，但聚合器的待发布映射必须保留这个零量删除标记，否则客户端会继续显示卖 60000。即使某键在窗口内先删后加，或者末值恢复到窗口前的数量，这份并集契约也保留其末值。卖 60100 的 5 lots 是“设置为 5”，不是“再扣 5”；不能把成交扣减量与最终剩余量混用，也不能把多个绝对量相加。绝对量有利于重复应用同一内容，却不能替代对漏键、序号和源缺口的检查。

## 第 3 层：没有价位变化也必须证明源覆盖连续

**面试官：** 变更键并集只能描述改了什么。如果某个批次不改盘口，或者从 100 之后先收到 103，你如何证明这一帧没有漏掉源事实？

**面试者：** 连续性来自逐批校验和应用，不能拿窗口内最小、最大编号拼一个覆盖区间。发布器保存上次已提交覆盖水位 W，下一帧的 `sourceFrom` 必须为 W+1，`sourceTo` 只能到已经连续处理的位置；同一 `sourceLogID` 下，每个中间批次都必须完整通过校验。独立缺口变体中，从 100 先见 103，就停在可信水位 100、标记 GAP 并补取，不能宣称已经覆盖 101—103。同内容重复不再累计，同位置内容冲突则隔离。另一个独立变体中，合法批次没有深度变化，投影源游标仍然前进，但对外深度覆盖不能自动冒进：可以把它纳入下一帧的连续区间，也可以在等待上限内提交 `levelSets` 为空的显式进度帧，同时推进 `depthSeq` 与覆盖水位。这表示确实处理了源批次；连接心跳只证明通道存活，不具有这种提交和覆盖语义。

## 第 4 层：Top-N 必须从完整簿派生并显式移除退出档

**面试官：** 既然连续区间已经保证所有批次都被处理，为节省带宽，能不能直接把合并后的价位列表截成 Top-1？删掉卖一之后，客户端又从哪里补档？

**面试者：** 不能截断变更列表，也不能只维护 Top-1 后丢弃更深价位。完整 L2 仍按前面的规则处理全部更新，Top-N 是有独立 `streamID` 和 `viewVersion` 的限深视图。发布器比较上次已提交视图与本次完整簿派生视图，发送所有退出键的视图删除、新进入键的绝对量，以及留存键的末值变化。正常案例按每侧 Top-1 发布时，旧卖档是 60000/0.10，新卖档是 60100/0.05，因此必须删除 60000 并补入 60100；60200/0.30 虽不对这个视图发送，仍保留在完整簿中。独立挤档变体中，新增更优卖档会让仍有余额的旧档退出 Top-1，此时零量删除若作为协议编码，只表示从客户端限深视图移除，不表示完整簿实际归零。必须区分视图退出与真实清空，否则以后补档就会丢掉仍然存在的流动性。

## 第 5 层：快照必须锚定已经提交的发布版本

**面试官：** 你比较的是“上次已提交视图”。如果投影已经到 102，但聚合帧还没提交，新订阅能否直接读取最新盘口，再挂上旧的 `depthSeq=S`？

**面试者：** 不能。快照的价位内容、`sourceTo` 和发布锚点必须属于同一个已提交版本，投影进度不等于发布进度。若可见锚点仍是 `S、sourceTo=100`，就只能返回该锚点的不可变快照，不能把 102 的盘口和水位硬贴在 S 上。另一种合法选择是先将覆盖 101—102 的帧提交为 S+1，再提供对应 102 状态、锚定 S+1 的快照；限深视图无变化但需要更新覆盖时，也要经过相应进度帧提交。运行中的最新可变簿不能被临时拼成旧版本快照，快照应从保存的不可变视图或可恢复的同版本记录生成，并携带匹配的身份和视图规则。订阅端先登记增量缓冲、再取快照、从锚点下一序号衔接，只能解决并发交接竞态，修不好错误锚点。即使绝对量重放偶然得到相同数量，也不能把这种偶然当作版本契约成立。

## 第 6 层：发布提交怎样跨过崩溃与重试窗口

**面试官：** 你要求先提交 S+1 再暴露新快照。如果序号已经分配却写日志失败，或者记录成功但发送失败，怎样避免空洞和同序号不同内容？

**面试者：** 在可跨重启续传的方案中，我会让单写者发布日志统一裁决提交：候选序号、不可变帧、源覆盖区间、可续传记录，以及可从持久基线和记录还原的快照锚点，一起形成提交版本，提交完成才推进对外尾游标并允许发送。候选 S+1 只是内部预分配；提交前失败不外发、不占可见序号，恢复时只认完整提交记录。如果提交结果不确定，先查询日志确认，不能直接另取一个序号。提交已经成功、发送之前崩溃，恢复后仍重发原 `epoch+depthSeq` 的原帧；已经写出但没有收到应用确认，也按同样身份重试，由客户端校验游标和重复。后来的投影不能重新生成 S+1，否则相同序号会对应不同内容。快照指针也只能指向相应提交版本，不能单独提前更新。因此日志追加、可续传查询和快照对外读取必须共享这个提交边界，而不是分别写完就各自宣告成功；写入 socket 更不是客户端已经应用的证明。

## 第 7 层：资源上限、易失恢复与世代隔离怎样同时成立

**面试官：** 上一层依赖可恢复的发布记录。如果热点持续涌入，而部署只有易失环形缓冲，聚合窗口和队列怎样有界？进程重启后还能沿用旧 epoch 吗？

**面试者：** 有界首先意味着不能无限等窗口关闭：要限制等待时长、变更键数、帧字节数与待发队列，并在完整批次边界封帧。若触及容量上限但发送频率预算尚未释放，就有界排队、暂停接入并依靠可靠源日志追赶；无法继续承诺时显式失效或要求重同步，不能静默丢帧后仍标 LIVE。单批已超帧上限时，也不能擅自拆成客户端会逐帧可见的普通更新。只有易失环形缓冲，就只承诺记录尚存期间的续传；重启后若无法恢复旧发布尾部、原帧内容和锚点，必须建立新 epoch，让客户端重新取可信快照。能恢复同一历史且隔离旧主，才有条件延续旧 epoch。换代本身不能填源缺口，仍须补齐源或取得可信一致快照；也不能用换代代替隔离旧发布者。fencing 是受保护发布资源拒绝旧 `leaderTerm` 的执行约束，epoch 则是客户端区分不可混接历史的身份，两者不能互相替代。

## 第 8 层：连续终态不等于逐事件无损

**面试官：** 你要求新 epoch 也只能从可信状态恢复。那么即使每次恢复后的深度完全正确，窗口内被末值覆盖的变化算不算丢数据？逐笔成交能否照样合并？

**面试者：** 是否算丢数据，要先看该流承诺什么。普通聚合深度承诺从上一个锚点应用连续帧后，得到各帧 `sourceTo` 对应的完整深度或声明的 Top-N 终态，不承诺重现窗口内每次数量变化、最优价跃迁和挂撤单路径。因此中间变化可以被末值覆盖，但不能漏掉契约内应交付的键、删除和补档，也不能省略连续源覆盖。逐笔成交流的语义不同：正常 101 的 `T101-1` 是 0.10 BTC@60000，`T101-2` 是 0.15 BTC@60100，都必须保留稳定成交身份，并各自占一个 `tradeSeq`，不能只留最后成交价。正常 102 新增卖档但没有成交，既不能补造逐笔，也不能清零历史累计量。若产品要求还原每次报价变化或逐订单队列，就应提供另一条明确无损的事件流并承担其吞吐成本，不能把聚合深度宣传成逐事件历史。序号连续证明的是这条已声明发布历史没有断帧，不自动证明其他通道无损或已经追上源头。

---

**机制：** 完整批次连续应用，完整深度按变更键并集保留绝对末值，限深视图显式删除和补档，发布记录与快照锚点共同提交。

**易错边界：** 视图移除不等于完整簿归零；无变化源推进不等于已经交付；进度帧不等于心跳；epoch 不等于 fencing，也不修复源缺口。

**反例：** 合并 101、102 却只发布卖 60200/0.30，客户端会残留卖 60000/0.10；即使 `depthSeq` 连续，盘口仍然错误，说明序号连续不能替代内容完整。
