# 大问题 8：WebSocket 怎样完成订阅和大规模扇出？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| connectionID / subscriptionID | 一条连接和其中一份订阅的身份 | 重连是新连接，取消重订是新订阅，不能仅凭同 topic 接旧回调。 |
| requestID / payload 幂等 | 控制命令的身份，以及同请求只受理一次 | 同连接同 ID 同内容复用结果，异内容报冲突；容量不足应拒绝新命令。 |
| topic / channel | 规范化后的订阅主题，以及深度等数据通道 | 市场、限深参数和版本都参与身份，别名不能绕过去重与配额。 |
| ACK / READY_SENT / applied | 控制已受理、准备标记已写出、客户端已应用 | 是不同阶段；ACK 不证明缓冲屏障成立，READY 写出也不证明本地簿已更新。 |
| S / B / 订阅 FIFO | 快照切点、固定的追赶尾部，以及先进先出队列 | S、B 都是同发布历史的深度序号，快照和 S+1 到 B 之后才排 READY。 |
| 共享快照 / 独立游标 | 多人复用同版只读内容，各自维护交付进度 | 每人仍需自己的缓冲与补取范围，不能共享别人的 READY 状态。 |
| generation / 取消屏障 | 订阅操作代次，以及停止旧身份投递的有序边界 | 不等于发布 epoch；已写字节无法撤回，客户端应用前也要核对身份。 |
| 唯一写协程 / deadline | 统一写连接的执行者，以及写入截止时间 | 数据、控制与 Ping/Pong 都协调出口；写阻塞超时要关底层连接并回收资源。 |
| 引用计数 / 扇出 | 本机需求数量，以及一份上游帧分发多人 | 按需订上游不按连接重复订；公平轮转不能打乱同流帧顺序。 |
| 有界队列 / RESYNC_REQUIRED | 限制积压的缓冲，以及本订阅必须重建的通知 | 超限不静默跳深度帧；通知写不出也不能无限等，必要时断连。 |
| depthSeq / sourceSeq / Pong | 发布进度、源事实进度，以及通道往返响应 | 各自不同；大整数精确解析，Pong 不推进行情游标或证明数据新鲜。 |

## 把整篇文章压缩成一个故事

用户小吴反复点击订阅 BTC/USDT，网关按连接和 requestID 复用同内容命令的结果，没有重复加引用；ACK 只是受理，不等于盘口已就绪。待规范 topic 的上游真正接通，网关先挂本订阅缓冲，再取已提交切点 S 的快照，补齐到尾部 B，按顺序排快照、连续帧和 READY。很多用户可以共用只读快照和编码结果，却各有屏障、游标及补取需求，后来者不能借前人的准备状态过关。小吴取消又重订时，旧任务虽返回合法快照，也因订阅身份失效而丢弃，取消屏障还清理尚未写出的旧帧。每连接只有一个写出口协调业务消息和控制帧，写超时便关闭底层连接并幂等回收引用。热点帧按需接一次，再按字节预算公平扇出，同流顺序不能倒置；某慢客队列超限就局部失效，通知发不出则断连，不拖累其他人。最终网关写过 READY 仍不算客户端应用，Pong 正常也不算行情新鲜；必须结合精确游标、源覆盖和健康状态，才知道页面实际跟到了哪里。

**流程位置与核心机制：** 已提交发布记录与同版本快照 → 网关订阅屏障 → 每连接串行写出 → 客户端应用。重点解释会话身份、控制请求幂等、快照衔接与复用、按需订上游和有界扇出；网关不重新分配发布序号，也不决定撮合与账务结果。

前提：沿用总览的 BTC/USDT 托管现货、零手续费案例，`tick=0.01 USDT/BTC`、`lot=0.01 BTC`。源快照 `sourceSeq=100` 后，B1 买入 `0.25 BTC @ 60100`；已提交批次 `101` 删除卖 60000，将卖 60100 设为 0.05 BTC；正常 `102` 仅新增卖 60200 的 0.30 BTC。`sourceSeq` 是权威源位置，`depthSeq` 是单视图发布序号，`epoch` 标识不可混接的发布历史；下文 S、B 均为同一 `streamID + epoch` 内的深度序号。异常均为独立变体，不累计改变正常路径；本文为教学设计，不代表个人经历或实测结果。

## 第 1 层：怎样识别会话、订阅与重复控制请求？

**面试官：** 用户建立 WebSocket 后订阅 BTC/USDT 深度，网关需要记录哪些身份，怎样避免一次请求重试变成两份订阅？

**面试者：** 在这个模型中，连接建立不等于订阅完成。网关为连接分配 `connectionID`，绑定已确认的主体或匿名会话及配额，每份订阅另有 `subscriptionID`。先校验市场、channel、全量或 Top-N 参数及规则版本，再规范成唯一 topic；不能让市场别名绕过去重与限额。控制请求以 `(connectionID, requestID)` 为键，保存规范操作、完整 payload 与受理结果；同 ID 同 payload 复用原订阅身份，不重新登记或增加引用，同 ID 异 payload 明确返回冲突，不能暗改订阅。去重记录有容量上限，耗尽则拒绝新命令，而不是淘汰仍允许重试的记录后再次执行。订阅 ACK 仅表示控制受理，不代表快照写出或客户端应用；重连生成新连接身份，不能默认继承旧连接的去重语义。

## 第 2 层：ACK 之后怎样建立不漏帧的订阅屏障？

**面试官：** 你说订阅 ACK 只是受理；如果取快照时行情还在发布，快照与实时帧怎样衔接，网关什么时候才算准备好？

**面试者：** 在上游已就绪的 topic 顺序域，先为该订阅登记有界增量缓冲，再取已完成发布提交的不可变快照，快照携带 `streamID、epoch、depthSeq=S、sourceTo`，不能把投影最新内容贴到旧 S。丢弃缓存中不大于 S 的帧，从 S+1 校验连续序号与前驱，缺帧则从同一发布日志补齐。随后由串行状态机固定缓冲尾 B，把快照、S+1 至 B 的连续帧和 READY 标记依次排入该订阅 FIFO，后到帧只能接在后面，不能先清空缓存再另挂实时回调。唯一写协程成功写过 READY 后才记 `READY_SENT`，它仍不是客户端应用状态。缓冲溢出或 epoch 不符就终止此次同步，不能带洞转 LIVE。若快照覆盖源 100，包含源 101 的后继深度帧应体现两处卖档变化，但发布 S+1 绝不等于源 101。

## 第 3 层：万人同时订阅时能共享什么快照工作？

**面试官：** 每个订阅都先挂缓冲再取快照，如果一万人同时进来，能否只生成一份快照，并让大家共用这条同步进度？

**面试者：** 可以复用快照计算与只读内容，不能共用订阅屏障和游标。快照服务先固定已提交版本，按 `streamID、epoch、S、viewVersion、instrumentVersion` 合并在途请求；共享对象的价位、`sourceTo` 与校验和必须同属该版本，不能把 topic 的“最新快照”指针不断更新后仍声称内容相同。公共 payload 可共享不可变引用，订阅身份则由各自信封补充。每个等待者仍先登记自己的缓冲，再独立裁剪、补齐和推进发送游标；后到者即使复用旧 S，也可能没有缓存到 S+1，必须单独补日志，保留范围不足就改取新快照，不能照搬别人的 READY 状态。一个等待者取消只解除自己的引用；共享任务在没有等待者时才可取消，并受截止时间限制。快照复用节省生成与编码成本，不消除最终向每条连接发送字节的成本。

## 第 4 层：取消再订阅怎样隔离迟到快照和旧帧？

**面试官：** 共享快照还没返回，用户就取消并重新订阅相同 topic；旧任务稍后成功，而且序号看起来连续，怎样避免它覆盖新订阅？

**面试者：** 不能只按 topic 或序号识别订阅。本模型每次重订都生成不复用的 `subscriptionID`；若复用订阅槽位，也可递增 generation，但它与发布 epoch 完全不同。异步快照回调、缓冲项和待写信封都携带订阅身份，入队前与出队时都核对当前有效记录。取消先令旧身份失效、停止投递并解除它的上游需求引用；连接写出口再处理取消屏障，丢弃尚未写出的旧帧，把取消 ACK 排在屏障之后。已经写出的字节无法撤回，客户端异步应用前也必须检查身份，不能让旧快照回滚新簿。取消与重订分别用新 `requestID`，旧订阅请求的重试仍指向旧记录，不自动复活。共享快照若还有其他等待者就继续运行，但旧订阅的回调必须失效；这里换的是订阅身份，不因取消而擅自更换发布 epoch。

## 第 5 层：一个连接怎样统一写数据与协议控制帧？

**面试官：** 你把取消 ACK 放在写出口屏障之后，但数据、订阅响应以及 Ping/Pong 都可能由不同协程触发，怎样真正保证顺序，又避免慢写卡死？

**面试者：** 每条连接只有一个写协程，数据、订阅 ACK、READY、取消屏障以及 WebSocket 的 Ping、Pong、Close 都通过它统一序列化。读协程负责收包、更新收到 Pong 的时刻并投递事件，不直接写 socket；使用库时也要避免默认控制处理器绕过这个出口。写者检查订阅身份，并保持同一 stream 的 FIFO；Ping/Pong 可以在消息边界优先处理，但业务控制消息不能跨越自身依赖屏障，Close 生效后不再写行情。优先级不能打断已经阻塞的写，因此每次写都有有限 deadline，队列等待也有年龄上限。写失败或超时便强制关闭底层连接、取消连接 context，让读写循环退出，再幂等释放队列、快照等待者、订阅引用和定时器。不能指望再写一条 Close 帧去解除已经无法完成的写，更不能为每个发送临时启动协程堆积等待。

## 第 6 层：大量连接怎样按需订上游并公平扇出？

**面试官：** 单连接唯一写者解决了并发写，但几万连接都订同一个热点，难道每条连接都订一次上游？热点 topic 又会不会饿死其他 topic？

**面试者：** 上游订阅按网关本机有需求的规范 topic 建立，不按连接复制，更不为每条连接订全市场。引用计数包括正在同步和持续接收的有效订阅；首个引用触发 `IDLE→SUBSCRIBING→ACTIVE`，上游可接帧后才启动各订阅的快照屏障，最后一个引用退出才发起退订。计数与状态转换由同一 topic 状态机串行维护，异步响应带操作代次；退订中重新出现需求，要记住新需求，完成旧操作后重订，不能被迟到退订响应清掉新引用。上游帧只接收一次，再向本机订阅者共享不可变内容。热点订阅者列表分批推进，跨 topic 按字节预算轮转，避免一次遍历吞掉全部调度时间；但每个订阅的同一 stream 必须保持序号和快照屏障顺序。公平调度只改变不同 stream 的交错方式，不承诺跨 topic 全局有序，也不能让 S+2 越过 S+1。

## 第 7 层：慢客户端怎样局部失效而不拖住整个网关？

**面试官：** 你说跨 topic 轮转且共享不可变帧，如果某条连接长期写不动，扇出能否等待它，或者丢几帧后继续把最新盘口推过去？

**面试者：** 扇出只能做非阻塞、有界投递，不能等待某个连接释放空间。每订阅和每连接都限制消息数、待发字节与最老消息年龄，共享帧的引用保留也要计入资源约束，不能因为 payload 只编码一次就无限挂引用。深度队列越界后，该订阅立即失效，停止追加并清除未发送旧帧，不能丢掉中间帧却继续标成 LIVE；恢复必须重新建立快照屏障。网关可用预留控制配额尽力发送带订阅身份和已写游标的 `RESYNC_REQUIRED`，这里的游标仍不是客户端 applied 游标。控制队列同样有界，通知无法入队、写不出或超时就直接断开，不能为了告知失败而无限等待。单订阅失效可只停该 topic；若连接级预算或写 deadline 失败，则关闭整条连接并回收其引用。其他连接继续接收，不把一个慢用户的背压传给公共发布流。

## 第 8 层：怎样区分交付完成、客户端应用与行情新鲜？

**面试官：** 即使已经隔离慢客户端，服务器写成功且持续收到 Pong，能否宣称用户拿到了最新盘口？客户端应用后、确认前断线又该怎样解释？

**面试者：** 不能。订阅 ACK 是控制受理，写 socket 成功只说明本地传输写完成，`READY_SENT` 也只是网关写过订阅屏障；客户端按订阅身份、`streamID、epoch` 校验，整帧原子更新后才推进 applied 游标，页面渲染还在其后。应用确认只能报告客户端声称到达的位置；应用后确认前断线，服务端无法据此判定是否已应用，只能在恢复时按身份与序号重放去重，缺口则重同步，没有端到端 exactly once。`sourceSeq、depthSeq` 等大整数经 JSON 传十进制字符串，浏览器用 BigInt 等精确整数处理，不能用 JavaScript Number，也不能按字符串字典序比较；epoch 变化则旧历史不能继续拼接。Pong 仅证明通道往返，数据新鲜度还要看源、投影与发布覆盖水位、各环节观测时间及显式健康状态。市场无成交不等于过期，正常 102 仍推进源覆盖；源停滞时即使心跳正常也应标 STALE/GAP，传输 Ping 不推进行情游标。

**机制收束：** 身份与请求幂等确定“哪份订阅”，先缓冲后取已提交快照确定“从哪里开始”，单写出口、按需上游和有界队列确定“怎样持续交付且局部失效”。

**易错边界：** 共享快照不共享订阅游标，订阅身份不等于发布 epoch；控制受理、socket 写出、客户端应用与页面展示不是同一完成条件，Pong 也不是行情新鲜证明。

**反例：** 独立变体中，旧订阅 A 的快照在取消并建立 B 后才返回，即使 topic 与 epoch 相同也必须丢弃。若仍应用到 B，控制请求幂等、TCP 有序和心跳正常都无法防止旧快照回滚新盘口。
