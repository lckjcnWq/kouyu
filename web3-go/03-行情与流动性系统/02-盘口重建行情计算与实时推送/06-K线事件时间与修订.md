# 大问题 6：K 线遇到迟到成交与修订怎样处理？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| K线 / OHLCV | 一段时间的成交摘要，以及开、高、低、收和成交量 | 只汇总真实成交，盘口新增或撤单不改变成交高低价。 |
| eventTime / [start,end) | 成交发生时间，以及含起点不含终点的时间桶 | 12:01:00 属于下一分钟；网络收到的分钟不决定归桶。 |
| (eventTime, sourceSeq, ordinal) | 先按发生时间，再按源批次及批内顺序排列 | 用于本桶开收盘；ticker 全历史最新价只按权威成交顺序，口径不同。 |
| tradeID / 同批可见 | 成交身份，以及涉及多个桶的更新一起生效 | 重放不多算，跨桶批次不能只提交一部分后就推进源水位。 |
| 接入延迟 / 事件时间迟到 | 首次接收减发生时间，以及落在已公布时间进度之前 | 两者不同，也都不直接等于 sourceSeq 缺口。 |
| watermark / L | 事件时间处理进度，以及示例允许迟到量 | 最大有效事件时间减 L 只是候选估计，不能证明未来绝无更早成交。 |
| 业务封口 / 在线修订期限 | 常规聚合结束，以及历史桶留在热处理范围的期限 | 都不是删除真实成交的许可；期限外还要登记并执行历史更正。 |
| candleKey / revision | 定位一根柱的键，以及该柱的持久修订号 | 同键只接更高版本；不能用深度序号替代，也不随发布换代归零。 |
| 完整替换载荷 / 修订提交 | 一整版柱数据，以及内容、版本、待发布记录共同落定 | 重试发同版原内容，避免旧 HTTP 响应覆盖新推送或重复增加成交量。 |
| empty / STALE | 已知无成交的空桶，以及数据落后无法确认的桶 | 空桶量额笔数为零、OHLC 为 null；参考价不冒充本分钟成交。 |
| 子桶贡献 / 父柱 | 分钟柱的完整版本，以及由其派生的小时柱 | 新 revision 替换旧贡献并重算必要极值，不把修订再加一遍。 |

## 把整篇文章压缩成一个故事

图表开发小岑在 12:01 才收到 B1 的两笔成交，起初想画进新一分钟。后端让他按 eventTime 放回 12:00 桶，仅这两笔时开盘 60000、收盘 60100，成交量 0.25 BTC、成交额 15015 USDT；新增卖档的 102 不产生新成交。桶内开收盘按事件时间和权威顺序共同排序，晚收到不等于收盘更晚，重放也不多算。系统用公布的迟到策略推进候选 watermark，但源连续和墙钟经过都不能证明时间事实已全部到齐。后续连续批次若带来 12:00:05 的成交，就比较首尾键、修订整根柱，把内容、revision 和发布记录一起提交，旧查询不能盖掉新版本。超过在线修订期限也不丢事实，而是加载历史桶完成官方更正。没有成交的分钟保留空桶，量额笔数为零、价格为空；断流时却只能标落后，不能谎称没有交易。重启要恢复排序键、去重和持久版本；小时柱接到分钟修订时替换旧贡献并重算极值。小岑最终看到的是可追溯修订的图表，不是用换 epoch 掩盖错误、或拿上一根收盘伪造的新成交。

[返回专题总览](README.md)

**流程位置与核心机制：** 位于权威成交投影到时间桶行情之间。本题通过归桶、OHLC 排序、成交去重、事件时间进度与修订提交，解释一根 K 线怎样持续更新、封口和恢复；不是按接收分钟重新组织成交，也不复用深度序号充当 K 线版本。

**讨论前提：** 沿用总览中的 BTC/USDT、零手续费，`tick=0.01 USDT/BTC`、`lot=0.01 BTC`。批次 101 的两笔成交发生于 UTC 12:00:10.100、12:00:10.101；正常批次 102 只有新增卖档、没有成交。分钟桶是 `[start,end)`，滚动窗口才是 `(T-W,T]`。全部异常均为独立变体，以下是教学设计而非个人经历或实测结论。

## 第 1 层：用权威成交构造第一根分钟 K 线

**面试官：** 批次 101 产生两笔成交，你会怎样计算 12:00 的分钟 K 线？如果 WebSocket 到 12:01 才收到，两笔应落到哪个桶？

**面试者：** 我按成交 eventTime 归入 UTC 的 `[12:00:00,12:01:00)`，不按行情服务或浏览器的接收时间归桶。该分钟仅考虑这两笔时，开盘价为 60000，最高价 60100，最低价 60000，收盘价 60100；成交量 0.25 BTC，成交额 15015 USDT，成交笔数为 2。恰在 12:01:00 的成交属于下一个桶，和滚动窗口左边界的判断相反。批次 102 没有成交，只推进连续源水位，不能因卖 60200 新增而抬高 K 线最高价或增加笔数。撮合已经提交的成交才能进入统计，撤单与挂单都不构成交易价格。K 线是可重建的公共投影，不负责修改成交或资产，页面看到该柱也不代表账户已经结转。

## 第 2 层：明确开收盘的全序，而不是最后到达者获胜

**面试官：** 你说开盘取第一笔、收盘取最后一笔。如果两笔 eventTime 完全相同，或后续权威成交的时间戳更早，究竟怎样定义第一和最后？

**面试者：** 我为桶内成交定义排序键 `(eventTime,权威成交顺序)`。权威成交顺序在同一 sourceLogID 内由 `(sourceSeq, ordinal)` 确定，因此相同时间戳仍可唯一比较；tradeID 用于身份识别，不能假定字符串字典序就是撮合顺序。开盘取最小排序键的价格，收盘取最大排序键的价格，高低价则取全部真实成交价格的极值。实现上保留首尾排序键及对应价格，新成交到来后分别比较，而不是每收到一笔就覆盖 close。独立变体中，后续连续源批次带来 eventTime 更早的成交，可能改变 open，却不一定改变 close。ticker 的全历史最新成交按权威成交顺序选取，因此它可以与这根桶的 close 不同；这不是数据冲突，而是两个字段有不同的排序契约。

## 第 3 层：让去重、桶统计和源水位同批生效

**面试官：** 首尾排序已经确定，但同一 101 重放一次，或一批成交跨两个分钟桶时，怎样避免笔数翻倍、一个桶已更新而另一个桶还没更新？

**面试者：** 单交易对逻辑写者先校验完整批次、连续 sourceSeq 和内容摘要，再在私有状态里更新涉及的所有桶，最后把桶状态和源水位一次变成可见。101 的两笔 tradeID 不因重放改变；已应用的同内容 101 不再累计，同位置内容冲突则隔离。新源位置重用已有 tradeID 时也核对成交归属和内容，不能重复计数或静默吞掉冲突。如果一批跨桶，每个桶各自计算，但同一源水位的投影提交不能只覆盖其中一个。数量以 lots 求和，成交额在经过范围检查的宽整数中先乘后加；一个乘积单位为 0.0001 USDT。先用 int64 乘到溢出再转宽类型仍然错误。对外 OHLC、量、额及大整数位置使用十进制字符串，不能让 JavaScript Number 隐式舍入。桶更新版本还不等于深度已发布版本，两条发布链路不能互相代替完成确认。

## 第 4 层：区分迟到量、事件时间进度和“可以封口”

**面试官：** 你能原子更新多个桶，但 12:00 的桶什么时候算结束？一笔 12:00:59.900 的成交到 12:01:02 才接入，是否应因超时丢掉？

**面试者：** 我把接入延迟定义为首次接收时间减 eventTime，本例是 2.100 秒，内部排队耗时另计；它不代表 sourceSeq 有缺口，也不决定成交真假。事件时间迟到则指接入时 eventTime 已落在此前公布的 watermark 之前，两种时间量不能混用。若声明允许迟到 L=2 秒，这只是本题的示例策略。常见候选 watermark 是已见最大有效 eventTime 减 L，它表示计算进度估计，不天然证明未来绝不会出现更早成交；异常未来时间也必须先校验，不能推高 watermark。watermark 到达桶 end 可以触发业务封口，但真实的晚到成交仍要走修订。若要求不可逆终局，必须另有权威事件时间下界等保证，仅靠源连续或墙钟经过两秒不够。正常 102 无成交，也不能从 sourceSeq=102 推导分钟已结束；连续性回答的是有没有漏批，watermark 回答的是时间进度假设。

## 第 5 层：迟到后怎样发布不会倒退的修订版本

**面试官：** 你保留迟到成交并修订，但旧分钟柱已通过 WebSocket 发出。如果实时修订、HTTP 查询与重试交错，客户端怎样知道哪个版本才是新的？

**面试者：** 我以 `candleKey=(交易对,周期,开始时间)` 定位同一根柱，用持久的 revision 表示它的修订顺序。独立变体中，某个后续连续批次含一笔 12:00:05 的成交，它可改变 open、量、额或极值；我重新比较首尾键并生成更高 revision，而不是往客户端仅发送“成交量加多少”。发布载荷包含完整 OHLCV、成交额、笔数、源水位、规则版本、封口状态及 revision，客户端仅接纳同键更高版本，同版本不同内容应视为冲突。桶的新状态、revision 和待发布记录一起提交，提交后重试仍重发相同版本内容。HTTP 读到的是已提交版本；旧 HTTP 响应晚于新推送到达时不会覆盖它。revision 不是 depthSeq 或 tradeSeq，也不因网关重连、发布 epoch 更换而自动归零。

## 第 6 层：封口限制的是常规处理，不是抹掉成交事实

**面试官：** 你用 revision 修复已经发出的柱，但若允许无限迟到，热内存和修订都会无限延长。怎样设置修订期限，又不把期限外的真实成交吞掉？

**面试者：** 我把业务封口和常规在线修订期限分开：前者说明本轮常规聚合已结束，后者限制多少历史桶留在热状态。期限是产品规则，随规则版本公布，不宣称它能证明之后没有旧成交。超过期限的真实成交仍进入权威逐笔及持久历史，系统登记更正任务，加载或重建受影响旧桶，再以同一 candleKey 的更高 revision 发布官方更正；不能为了节省热状态而跳过成交。更正完成前查询应能表明待修订，不能把旧柱永远标成无条件终局。如果产品坚持“封口后永不变化”，就必须另设可查询的更正数据，并明确旧柱不再代表全部已知事实，这改变了对外契约。本题采用可更正历史柱，不撤回真实成交，也不靠新 epoch 把旧错误藏起来；热内存有限并不要求历史事实被删除。

## 第 7 层：没有成交时怎样推进时间和表示空桶

**面试官：** 你已把历史状态移出热内存，但市场一直没成交，候选 watermark 不动。前一根柱怎样封口，接下来的空分钟是缺失数据还是零价格柱？

**面试者：** 没有权威事件时间进度信号时，我可以按服务端时钟和公开迟到策略进行业务封口，但明确它是可修订的判断，不冒充源提供了硬 watermark；若源契约提供可信时间下界，才按该下界推进。空桶语义也要固定：本题保留空分钟记录，量、额和笔数为 0，OHLC 为 null，标记 empty，并附源覆盖状态。为图表连线可以另提供上一根非空柱 close 作为参考价，但不能填进 OHLC 冒充本分钟真实成交，更不能标出一笔虚构交易。第一根之前没有可用参考价时仍为 null，跨空桶涨跌也必须声明比较的是上一非空收盘，而不是零。若只是行情断流，就不能确认“空桶无成交”，应标成 STALE 或待补齐；传输 Ping/Pong 正常也不能改变这个判断。

## 第 8 层：恢复和多周期计算都必须保住修订语义

**面试官：** 你让空桶保留显式状态、旧桶继续可更正。如果服务重启，或者小时柱由分钟柱汇总，怎样避免 revision 回退和迟到成交被再次累加？

**面试者：** 恢复必须使用同水位检查点及可靠源重放，包含桶累计值、首尾排序键、去重依据、时间进度策略、规则版本和历史修订记录；不能只恢复 OHLC 后再把 101 全加一遍。公开 revision 由持久桶记录约束，不从进程内零值重新分配。小时柱若从分钟柱派生，要按子桶身份保存已采用 revision 和完整贡献，更高分钟 revision 到来时替换旧贡献，而不是再次相加；旧高低极值被修订掉时需要重新计算，空桶参考价也不能参加真实成交极值。其开收盘延续事件时间及权威顺序规则，父柱与修订通知同样协调提交。如果只持有易失发布缓冲，重启应新建发布 epoch 并重同步，但历史 candleKey 的版本仍可查询。客户端按键和版本幂等应用，服务器写出不等于用户应用，不承诺端到端 exactly once。

## 机制收束与易错边界

**机制：** eventTime 决定归桶，`(eventTime,权威成交顺序)` 决定开收盘，稳定身份防止重复累计，`candleKey + revision` 让晚到更正成为显式、可查询的版本变化。

**易错边界：** 分钟桶是 `[start,end)`；源连续不等于时间完整，业务封口不等于不可逆终局。空桶零成交不能伪造成零价格，发布 epoch 不能替代持久修订历史。

**反例：** 一笔 eventTime=12:01:00 的成交若进入 12:00 桶，归桶有误；一笔后接入但 eventTime=12:00:05 的成交若无条件覆盖 close，排序有误；HTTP 旧 revision 能覆盖推送新 revision，则客户端修订契约不成立。这些是手工推演，不是实测结果。
