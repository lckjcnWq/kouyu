# 大问题 3：源事件重复、乱序或缺失时，怎样保证盘口仍然可信？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| sourceLogID + market + sourceSeq | 哪段源历史、哪个交易对、哪一批事实 | 同号跨日志不是同一事实，不能跨身份比较序号大小。 |
| 最后连续水位 / 最大已见序号 | 已完整处理到哪里，以及最远看见哪里 | 看见 103 不代表已应用 102，健康水位不能越过缺口。 |
| 绝对量 | 某价位在批末应剩的总量 | 设置可重复不等于全簿可跳批；漏掉删除会留下幽灵档位。 |
| GAP / CATCHING_UP / RESYNC | 缺批、正在追赶，以及放弃本轮追赶重新同步 | 有界补取成功才回 LIVE，旧快照只能带落后或失效标记提供。 |
| 轻量封套 / depthSeq / tradeSeq | 保留源进度的外壳，以及两个对外流的排号 | 无公开变化也验证源位置；深度帧和成交笔数不能拿来替代源连续性。 |
| batchHash / 规范化 | 批次内容指纹，以及固定字段和排序的编码方法 | 同位置异内容要隔离，不因旧序号就一律当正常重复。 |
| 传输分片 / 业务批次 | 一包数据的若干运输片，以及不可拆开的应用单位 | 源提交标记不证明本地已收齐载荷，收全校验后才应用。 |
| 输入仲裁 / 单写者 | 将实时和补取送到同一入口决定应用顺序 | 两条路径不能各自推进游标或累计同一成交。 |
| L2 快照 / 历史恢复闭包 | 当前挂单定格图，以及恢复某指标所需的全部状态 | 簿可恢复不代表漏掉的逐笔、滚动量和K线已经恢复。 |
| 发布 epoch / 授权换源屏障 | 不可混接的发布历史，以及受控切换源身份的交接点 | 本模型换 sourceLogID 必换发布 epoch；换身份不能抹去缺失事实或成交义务。 |

## 把整篇文章压缩成一个故事

值班员小许从快照 100 接行情，收到 101 后完成扫单更新，再来的同内容 101 被挡在入口；接着却跳到 103。他没有把绝对量直接写进去，因为独立故障变体里，缺失的 102 可能正好删除卖 60100，跳过便会留下幽灵卖档。系统把最后连续水位留在 101，进入 GAP，有限缓冲后续批次并向可靠日志补取。实时和补取即使同时送来 102，也只能经过同一写者应用一次，价位、成交统计和游标共同推进。若批次被拆片，先收全校验；同号内容不符则隔离，不能当重复吞掉。无公开变化的合法批次仍要核验源进度，对外深度和逐笔各用自己的序号。等待超预算或日志已过期，小许放弃本轮追赶，重取可信盘口并建立衔接；但当前快照补不回历史成交，窗口和K线须另找归档，否则明确不可用。若源重建换了日志身份，更不能把新号与旧号接起来，必须授权换源并新建发布世代。验收要证明每个 LIVE 水位都有完整前缀，而不是只看最终卖一碰巧正确。

[返回专题总览](README.md)

**流程位置与核心机制：** 负责权威结果流到行情投影的连续性，不处理客户端续传。重点是命名空间、批次完整性、缺口状态机和恢复边界。

**必要前提：** `sourceLogID + market + sourceSeq` 标识单交易对的已提交结果；从可信快照 100 开始。本题异常均为独立变体，正常案例仍是 101 扫单、102 新增卖档。

## 第 1 层：重复、乱序、缺口分别怎样处理

**面试官：** 行情服务从快照 100 开始，依次收到 101、101、103。怎样处理，能直接应用 103 吗？

**面试者：** 第一条 101 校验后整批应用，状态和游标推进到 101；同内容重复 101 不再应用；随后期望 102 却收到 103，必须进入 GAP，不能直接更新。后续事件可以在大小和时间都有上限的缓冲区等待，服务向可靠日志补取 102，再依序应用。

这是“最后连续水位”，不是“见过的最大序号”。GAP 时最多提供标记为落后或失效的旧版本，不发布一个声称覆盖到 103 的 LIVE 簿。若补取失败、日志过期或缓冲超限，就转重建流程；不能因为 103 的价位都是绝对量就推断整簿已修复。

## 第 2 层：序号从哪里来，为什么不能用时间戳

**面试官：** 你依赖连续序号。能不能用撮合时间、Kafka offset 或订单编号来判断中间缺了什么？

**面试者：** 不直接替换。撮合时间可能重复、回拨或精度不足；订单编号不是所有结果的连续顺序；分区 offset 可能夹有其他交易对或控制记录。这里明确由该交易对权威结果日志提供连续 sourceSeq，源日志身份避免重建历史后把同号当同一事实。

若底层分区包含多个交易对，接入层要给每交易对提供明确的逻辑序列或可信覆盖证明，不能过滤后仍要求物理 offset 连续。若消费外部交易所提供 `[firstUpdateID,lastUpdateID]` 区间，则按其官方衔接规则验证覆盖，不照搬本题“一批恰好加一”。没有顺序契约时，行情消费者不能自己发明一个序号来证明源事实没丢。

## 第 3 层：没有成交或盘口变化，源序号要不要推进

**面试官：** 你说它是结果日志，但有些批次只拒绝订单、没有公开变化。行情过滤掉之后，不就仍会出现跳号？

**面试者：** 所以基线的接入连续性校验发生在过滤之前。行情消费完整结果流，或消费明确保留连续位置的轻量封套；即使批次没有 levelSets 和 trades，也先验证它是 next，然后推进源水位。

对外深度流另设 depthSeq，不要求每个 sourceSeq 都生成普通帧。发布器可聚合一段连续源范围并声明覆盖到哪里，无变化时按协议发进度帧。逐笔只有成交时才有 tradeSeq。这样既能证明源已处理到 102，也不会错误要求客户端收到一个根本不存在的“第 102 笔成交”。过滤是业务选择，连续性必须在合适的层证明。

## 第 4 层：相同序号不同内容是否也当作重复

**面试官：** 你忽略重复 101。如果第二个 101 里的卖 60100 不是 0.05，而是 0.08，也忽略吗？

**面试者：** 这不是正常重复，而是源事实冲突或解码错误。应比较可信的批次身份与规范化 hash，发现同一个 sourceLogID、交易对和位置对应不同内容时隔离流并告警，不能按“先到为准”悄悄吞掉。

完整内容包括价位最终值、成交身份、顺序与规则版本。hash 的输入序列化和字段覆盖必须固定，不能让 map 随机迭代顺序造成假冲突。运行中可保留有限近期指纹，较早重复需要依靠不可变源日志及可查询记录验证；不能声称用无限内存保存所有历史。若源契约保证历史不可变，可以信任该保证，但发现矛盾仍要升级故障，而不是把所有旧号都定义为正确。

## 第 5 层：一批事件被拆成多条消息怎么办

**面试官：** 你对整批算 hash。批次 101 很大，传输层拆成多条，先收到一个价位更新就能应用吗？

**面试者：** 不可以把传输分片当业务提交。封套应携带 batchID、sourceSeq、分片数或完成标记及完整性校验；接入层在有界空间内收齐并验证整批，再交给投影。缺一片时 sourceSeq 仍停在 100，不能先对外删卖 60000。

更简单的选择是源发布完整批次消息并约束最大尺寸，避免消费者自行拼装复杂事务。若业务批次必须分片，要定义超时补取、重复片冲突、尺寸上限和崩溃后重新收齐。提交标记只证明源提交，不自动证明本消费者已经拿到全部载荷；两者都成立后，才能推进本地连续水位。

## 第 6 层：补取和实时流同时送来 102，怎样避免竞争

**面试官：** 你补取缺失批次时，实时流也可能补到同一个 102。两条路径会不会各算一次成交？

**面试者：** 两条路径不能各自直接改状态，都汇入同一交易对写者的输入仲裁。写者以最后连续水位为准：第一份正确 102 应用后，另一份同身份同内容按重复处理；103 只有在 102 完成后才应用。

缓冲也按源位置索引，并验证重复内容，不让补取线程另维护一份会独立前进的游标。批次内先校验成交身份，再同时更新 L2、成交统计和 sourceSeq。这样去重不是只挡住一次 map 设置，还挡住成交量再次相加。如果需要持久恢复，游标与统计状态必须来自同一恢复边界，否则重启仍可能把已加过的成交重新累计。

## 第 7 层：等待缺口是否会无限占内存

**面试官：** 你把后来的 103 以后都缓冲。假设缺的 102 一直取不到，实时流持续进来怎么办？

**面试者：** 不能无限缓存。我会同时限制条数、字节数、等待年龄以及并发补取次数。超过预算就停止这一轮追赶并进入 RESYNC，不靠增加 goroutine 或内存“扛到恢复”。若源支持暂停读取且不会影响其他交易对，可暂停该分片；否则隔离热点交易对并舍弃可重取的本地缓冲。

状态机可以是 LIVE → GAP → CATCHING_UP → LIVE，预算或日志可用性失效则到 RESYNC。每次转移记录缺口起点和最后可信水位。旧快照可继续作为 STALE 查询结果，但对实时消费者必须明确失效，不能一边等缺口一边不断更新部分价位，因为那样已经不再是任何可信水位的完整簿。

## 第 8 层：源日志过期后，换快照是否万事大吉

**面试官：** 你决定重取快照。如果 102 已被清理，新快照是 500，直接切到 500 就能恢复所有行情吗？

**面试者：** 可信完整 L2 快照 500 可以恢复盘口状态，但不能自动恢复 102 到 500 之间全部逐笔、滚动成交量和 K线历史。新快照必须说明包含什么，不能用当前卖档反推历史成交。

盘口可在一致快照和后续增量屏障建立后切换；统计若需要过去 24 小时交易，则还要从可靠成交归档或包含窗口状态的检查点恢复。缺少这些输入时，对相关字段标记不可用或历史缺失，不伪造完整。换发布 epoch 可以告诉客户端旧历史不能混接，却不能证明源缺口已补齐；只有新快照自身可信，并且明确放弃了哪些历史承诺，才算诚实恢复。

## 第 9 层：源重建后序号归零，怎样避免误接

**面试官：** 你强调可信快照。如果源故障后新日志从 1 开始，而旧连接又迟到发送 501，谁的序号更大？

**面试者：** 不能跨日志身份比大小。`sourceLogID` 与 sourceSeq 一起标识历史，新日志不是旧日志的数字回退。收到新身份要先校验授权和切换协议，取得对应快照及连续起点；旧身份消息从此被隔离。

正常撮合主备接管若沿用同一已提交日志，可以保持 sourceLogID 和连续位置，但领导权 term 仍用于防止旧主继续写入。若旧历史确实被替换，必须解释替换依据、保留和可能丢失范围，不能仅仅换个 ID 就把未解决的成交义务抹掉。对外发布 epoch 与源日志身份不是同一个字段，但本模型规定每个发布 epoch 固定绑定一个 sourceLogID：授权更换源日志时必须新建发布 epoch、建立可信快照及订阅屏障，不能跨源拼接连续覆盖区间。

## 第 10 层：怎样用最小反例证明状态机没有偷跳

**面试官：** 你有了日志身份、缺口恢复和重建。怎样验证没有某条隐藏路径会跳过 102？

**面试者：** 我会用可手工枚举的事件排列对照参考执行。先取快照 100，再把同内容 101、102、103 做重复与乱序排列，只允许写者在 next 到达后推进；最终内容应与严格顺序应用一致，过程中发布的每个 LIVE 水位都必须有完整前缀。

再注入同序号异内容、缺一片、补取与实时重复、日志过期和身份切换，检查是否隔离而非静默修复。关键断言是“连续水位从未越过未验证的位置”，而不只是最终 hash 碰巧相同。性能优化可以改变缓冲和重试方式，不能降低这条断言。此处是验证方法设计，不是声称已经运行了这些故障测试。

## 本题收束

- **讲透的机制：** 源身份、连续前缀、整批输入、统一仲裁、有限补取与显式重建。
- **易错边界：** 绝对量不是缺口容错，过滤流跳号不是源必然漏数据，当前快照不包含完整成交历史。
- **检验反例：** 独立变体中，将正常 102 的新增改为撤掉批次 101 后仍存在的卖 60100/0.05，103 只更新别的价位且不再触及 60100。跳过这份 102 后，即使后续所有价位使用绝对量，幽灵卖档 60100/0.05 也可能永久存在。
