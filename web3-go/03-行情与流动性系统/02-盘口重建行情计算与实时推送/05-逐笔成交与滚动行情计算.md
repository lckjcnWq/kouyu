# 大问题 5：怎样正确计算逐笔、最新价和滚动统计？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 逐笔 / ticker | 每笔真实成交的记录，以及汇总行情字段 | 只由已提交成交生成；撤单、新增挂单和盘口减量都不能直接当成交。 |
| tradeID / ordinal | 成交的稳定身份，以及批内的权威次序 | 身份决定是否重复，(sourceSeq, ordinal) 决定全历史哪笔最新。 |
| sourceSeq / tradeSeq / epoch | 源批次位置、逐笔发布位置和发布历史世代 | 无成交批次只推进源位置；重试不能为同一发布记录另编新号。 |
| tick / lot / 金额单位 | 价格步长、数量步长及两者相乘的量纲 | 本例整数乘积单位为 0.0001 USDT，乘法和累计须先保证范围。 |
| V / Q / VWAP | 成交量、成交额和量加权均价 | 分别求和 q、p×q，再用 Q/V；不是把两笔价格直接平均。 |
| eventTime / 权威成交顺序 | 成交发生时间，以及源规定的事实顺序 | 前者决定窗口成员，后者决定最新价；不能用接收时间替代任一者。 |
| T / W / (T-W,T] | 计算时点、窗口宽度，以及左开右闭的成员范围 | 左边界成交要淘汰；该滚动窗不是左闭右开的分钟K线桶。 |
| P_ref / P_end / change | 边界参考价、窗口终值及相对变化 | 本题参考价取边界前驱，终值按窗口内权威次序取末笔；缺基准或空窗则 null。 |
| 空窗 / 全历史最新价 | 窗内无成交，以及不局限于窗口的最后成交价 | 窗量额为零、极值和均价为空；旧最新价可保留，但不能假装刚成交。 |
| 迟到 / ticker 版本 | 统计发布后才接入的有效窗口成交，以及整组字段的修订身份 | 迟到不是源缺批；修订字段共同发布，不重排源流或偷改 eventTime。 |
| 检查点 / 可续传记录 | 可恢复计算状态，以及已提交的逐笔发布历史 | 只存累计值或最新价不够；易失历史丢失后不能声称原世代可无缝续传。 |

## 把整篇文章压缩成一个故事

小唐给 B1 的成交页写统计，发现卖盘减少便想加成交量，同事提醒撤单也会减量。于是他只读取已提交批次里的 T101-1、T101-2，按稳定身份去重，用批内顺序确定最新价 60100。价格 ticks 与数量 lots 在宽整数中相乘，本批得到 0.25 BTC、15015 USDT，量加权均价 60060，不是两笔价格的简单平均。页面改看最近一分钟后，他声明计算时点 T 和窗口宽 W；在 T=12:01:10.100、W=60 秒时，第一笔恰在左边界被排除，只剩 0.15 BTC、9015 USDT。定时淘汰还要同步维护极值，空窗时量额为零、均价为空，但全历史最新价可以保留并显示原时间。第一笔虽已离窗，仍可充当边界参考价，不能拿卖一代替涨跌基准。迟到成交按事件时间修订窗口，却不重排权威源顺序，所有字段随版本一起更新。无成交批次只推进源水位，不能伪造逐笔进度。进程恢复时，小唐要重建成员、去重和参考前驱，还原逐笔发布记录；只恢复累计量或第二笔价格，既不能证明没多算，也不能冒充两笔都已无损交付。

**流程位置与核心机制：** 位于已提交 `ResultBatch` 到逐笔成交流、ticker 的计算与发布之间。本题关注成交身份、权威顺序、定点金额、事件时间窗口及空窗语义；K 线桶和修订详见下一题，不能拿盘口变化代替成交事实。

**讨论前提：** 沿用总览中的 BTC/USDT 托管现货订单簿，零手续费，`tick=0.01 USDT/BTC`、`lot=0.01 BTC`。快照水位为 100，批次 101 有两笔成交，正常批次 102 只有卖 60200 新增 0.30 BTC。窗口数值推演假定相关窗口除案例两笔外没有其他成交；窗口外参考价是否已知另行说明，不能从 L2 快照推导成交历史。以下为教学设计；迟到、重复和恢复均是独立变体，不累计改变正常路径。

## 第 1 层：先确定哪些事实能进入成交统计

**面试官：** B1 买入 0.25 BTC 后，卖 60000 消失、卖 60100 减少。你怎样生成逐笔、最新价和成交量，能直接从这两档变化计算吗？

**面试者：** 不能，撤单也会让挂单量减少，新增挂单还可能抵消同批成交带来的减少。我只消费已可靠提交的批次成交列表：T101-1 是 0.10 BTC、价格 60000，T101-2 是 0.15 BTC、价格 60100，分别保留身份并生成逐笔记录。两笔合计成交量 0.25 BTC、成交额 15015 USDT；按权威成交顺序，最新价为 60100。深度则独立应用批次最终绝对量，两条投影在整批应用后一起对读者可见。批次 102 没有成交，不能因新增卖档而生成逐笔或清零历史成交量。行情依据撮合提交即可推进，不必等待账户 APPLIED，但这些统计不能证明余额已经可用，也不负责释放 B1 的价差预留。

## 第 2 层：把成交身份、权威顺序和发布顺序分开

**面试官：** 你说每笔保留身份并按权威顺序更新最新价。如果 101 重复送达，两笔时间戳又相同，或者 102 没成交，具体依靠哪些字段？

**面试者：** 我先按 `sourceLogID + sourceSeq` 校验批次连续性和内容，再用批内唯一、稳定的 `ordinal` 确定成交顺序；同一源日志内，权威成交顺序就是 `(sourceSeq, ordinal)`，不是 eventTime，更不是网关收到的时间。`tradeID` 表示同一成交事实，恢复和重发都不能换身份。同位置同内容的 101 不再计量，同位置内容冲突必须隔离；新源位置若重复使用同一 tradeID，也要核对已记录的成交归属和内容，不能再算一笔，更不能把身份冲突静默吞掉。逐笔发布使用自己的 `streamID + epoch + tradeSeq`，101 可以产生连续的两条，102 只推进源处理水位，不凭空占一条成交。不能拿过滤后看不到 102 判断漏成交，也不能每次重试都分配新 tradeSeq；若延续原 epoch，必须恢复原发布记录与序号映射，而不只是记住最新价格。

## 第 3 层：让同一成交在金额和前端表示上保持精确

**面试官：** 你已能保证两笔只累计一次，但“0.25 和 15015”怎样从整数算出来？如果金额乘积超出 int64，或者浏览器用 Number 接收序号呢？

**面试者：** 价格先转为 ticks，两笔分别是 6000000 和 6010000；数量是 10 和 15 lots。量之和为 25 lots，即 0.25 BTC。一个价格数量乘积单位等于 0.0001 USDT，所以成交额整数为 150150000，换算得到 15015 USDT。计算必须先进入经过范围检查的宽整数或定点十进制，再做乘法和累加，不能让 int64 先溢出再转大整数。VWAP 用成交额除以成交量，得到 60060 USDT/BTC；换回 ticks 时为 6006000，不能把两笔价格直接平均。VWAP 不一定恰好落在 tick 上，因此对外显示精度和舍入规则另行声明，不改写成交事实。金额、数量以及可能超过 JavaScript 安全整数范围的 sourceSeq、tradeSeq 都以十进制字符串输出，客户端比较游标用 BigInt 或等价精确类型。

## 第 4 层：从本批统计扩展到真正的滚动窗口

**面试官：** 整数累计已经正确，如果页面要显示最近一分钟的成交量，你会怎样从本批合计扩展，特别是窗口左边界和跨分钟时刻？

**面试者：** 我先固定计算契约：服务端声明计算时点 T，窗口是 `(T-W, T]`，按成交 eventTime 判断成员，并附带已连续处理的源水位和规则版本。假设 W 为 60 秒，T 为 12:01:10.100，T101-1 恰落左边界，应被排除，T101-2 仍在窗口内，此时量为 0.15 BTC、额为 9015 USDT、VWAP 为 60100。这不是 12:01 那根分钟 K 线；分钟桶采用 `[start,end)`，两笔原本都属于 12:00 桶。实现上按事件时间维护有序索引和可删除累计状态；除新成交驱动外，定时计算也要淘汰 `eventTime <= T-W` 的成员。不能只在有成交时更新，否则停盘后窗口量会一直不归零；只按到达顺序排队，在允许迟到时也无法可靠淘汰。

## 第 5 层：窗口淘汰后仍要正确处理极值与空窗

**面试官：** 你用事件时间索引淘汰旧成员，但窗口最高价被淘汰，或者两笔最终都离开窗口怎么办？上一笔最新成交价是否也应该变成零？

**面试者：** 量和额可以减去被淘汰成交的精确贡献，最高、最低价则不能只保留一个变量。我会为窗口成员维护带计数的价格有序索引，删除某价格的最后一笔后再读取剩余极值；事件时间索引负责成员资格，两者和累计值在同一次视图更新内变化。这样 60000 离窗后，若只剩第二笔，高低价都为 60100。两笔均离窗时，窗口量和额是 0，窗口高低价、窗口内首末价和 VWAP 都为 null；不能执行除零，也不能拿上一分钟高低价补上。全历史最新成交价是另一个字段，仍可为 60100，并带原成交时间。它可以很旧，不能被写成“刚发生的成交”；同时应区分无交易的正常空窗与源链路落后造成的数据不完整，后者必须标注 STALE 或 GAP。

## 第 6 层：给涨跌字段一个不可含混的价格基准

**面试官：** 你把全历史最新价与窗口字段分开了，但产品还要“最近一分钟涨跌”。到底和窗口首笔比，还是和窗口开始前的价格比，空窗又显示什么？

**面试者：** 我会先把字段口径写进协议。本题的窗口涨跌采用边界参考价：在已知成交中，选 eventTime 不晚于 `T-W`、按 `(eventTime,权威成交顺序)` 排序的最后一笔作为 P_ref；终值 P_end 是窗口成员里权威顺序最后一笔的价格。涨跌额为 P_end 减 P_ref，涨跌比例为该差额除以 P_ref，不用买一、中间价或 VWAP 替代。即使参考成交在窗口外，也须保留可查询的边界前驱信息，并返回参考时间与规则版本。沿上一例，左边界的 T101-1 可作参考，窗口内只余 T101-2，涨跌为 100 USDT/BTC，比例约 0.166667%。若窗口空，或缺少可信参考价，相应涨跌字段为 null，而非默认零。这个口径不同于“窗口首笔到末笔”，也不同于昨日收盘涨跌，不能共用一个无说明的 change 字段。

## 第 7 层：迟到成交不改变源顺序，但可能修正窗口和基准

**面试官：** 你的 P_ref 依赖事件时间前驱。如果某个连续到达的后续批次带来更早 eventTime 的成交，是否要重排源流，又如何避免旧统计和新基准混在一起？

**面试者：** 不重排源流。我把接入延迟定义为服务端首次接收时间减 eventTime，处理排队时间另记；晚于某个 T 的统计发布才被接入、却按 eventTime 属于其窗口的成交，是对该已发布统计的迟到输入。这不等于 sourceSeq 缺口。独立变体中，后续连续批次可能带一笔事件时间更早的真实成交，仍按源顺序幂等应用，再按 eventTime 插入窗口索引或边界前驱索引。它可能修正当前 T 的量、极值或 P_ref，但全历史最新价仍按权威成交顺序决定，不能简单选最大时间戳。我把修正后的所有字段、计算时点、源水位和 ticker 版本一起发布；同一 T 有修订时版本必须前进，历史已发布的时点则走明确的历史修订契约，不假装旧帧已经被追溯修改。若 eventTime 晚于 T，先不纳入该时点窗口；异常未来时间按源时钟规则隔离，不能擅自改成接收时间。源序号真缺失时仍停止连续水位，不以“允许迟到”为理由跳过。

## 第 8 层：恢复要覆盖窗口状态和逐笔发布承诺

**面试官：** 你承诺修正字段一起可见。如果进程在累计后、发布前崩溃，重启后怎样既不多算两笔，也不把逐笔成交流恢复成只有最新价？

**面试者：** 检查点必须覆盖同一源水位下的成交去重依据、窗口成员与累计值、极值索引可恢复信息、价格基准前驱以及计算规则；不保存的部分就从足够早的可靠日志重建，不能只存 0.25 和 15015。读取已提交源水位后只应用后续完整批次，定时淘汰也按声明的 T 重算。逐笔发布另有提交边界：tradeSeq、每笔内容和可续传记录一致提交，重发同一记录仍是同一身份。若只保留易失发布缓冲，重启不能证明旧历史可延续，就换 epoch 并明确重同步；历史成交仍须能按稳定 tradeID 查询或补取。T101-1 和 T101-2 可以放进同一传输包，却不能用第二笔覆盖第一笔冒充无损逐笔。服务器写出与客户端应用没有共同事务，因此采用游标和重复抑制，不承诺端到端 exactly once。

## 机制收束与易错边界

**机制：** 可靠成交身份决定“算几次”，权威顺序决定“哪笔最新”，事件时间决定“属于哪个窗口”；定点金额、窗口成员、计算时点与版本共同定义可解释的 ticker。

**易错边界：** `(T-W,T]` 不等于分钟桶；空窗不等于价格为零；涨跌必须声明参考价，源断流不等于市场无成交。深度、成交价、VWAP 和账户余额分别有自己的语义。

**反例：** 在 T=12:01:10.100、W=60 秒时，如果仍报量 0.25 BTC，说明左边界淘汰错误；若无成交的 102 增加了 tradeSeq 或成交量，说明把源进度当成交。两者都能直接推翻统计契约，不需要虚构运行结果。
