# 大问题 4：快照生成期间行情仍在变化，怎样与实时增量无缝衔接？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 快照 / 增量帧 | 某版完整视图，以及之后的变更记录 | 本文衔接深度发布流；帧内量仍按协议设置绝对值，不是重复加减。 |
| depthSeq=S / sourceTo=W | 发布切点，以及该版覆盖到的源事实位置 | 示例 S=50、W=100，不是同一计数，不能互换或直接相减。 |
| streamID / epoch / viewVersion | 频道、发布历史和视图规则的身份 | 同名交易对不够；限深、精度或世代不匹配不能拼接。 |
| 订阅屏障 / ACK | 更新已被接住的交接点，以及确认消息 | 确认应在登记缓冲或取得可重放起点后，收到请求本身不算屏障。 |
| 不可变版本 / 发布锚点 | 不再变的内容，以及与其一致提交的发布位置 | 不能把投影最新簿贴到旧发布序号上，也不能遍历正在修改的 map。 |
| prevDepthSeq / 连续衔接 | 帧声明的前驱位置，以及逐帧接续检查 | 安装快照 50 后要接 51；源覆盖区间不能替代本协议的帧连续性。 |
| 有界缓冲 / 分片快照 | 有预算的更新暂存，以及拆开运输的同一张快照 | 缓冲溢出须补齐或重来；快照分片收全校验前不能当完整簿。 |
| 线性化点 / 单一状态机 | 可明确判定切换完成的瞬间，以及串行处理入口 | 追赶转实时也要协调，新帧不能掉在两条独立发送路径之间。 |
| 保留范围 / 跨节点交接 | 还能重放的帧区间，以及不同节点间的快照衔接 | 快照之后的必需帧必须可取，节点当前更快不代表历史足够。 |
| Top-N 差分 | 旧展示集合到新展示集合的变更 | 要补入进入档、删除退出档；不同视图即使源水位相同也各有发布切点。 |
| subscriptionID / generation | 一次订阅及本地同步尝试的身份 | 与服务端 epoch 不同；旧快照晚到也不能覆盖新订阅。 |

## 把整篇文章压缩成一个故事

用户小陈打开盘口，先拉到源水位 100 的快照，再订实时流，却发现卖 60000 一直没消失：批次 101 的帧恰好从两次请求的缝里漏了。工程师改成先登记有界缓冲，等订阅屏障真正生效，再取得深度切点 50、源覆盖 100 的一致快照。安装后丢弃缓冲里已被覆盖的帧，只从 51 连续应用，不能把源号 101 当发布号。快照服务也不能拿已更新到 102 的簿冒充切点 50，内容与锚点须协调提交。追到缓冲尾部时仍走同一串行入口，让新帧无论何时到达都有去处。若缓冲溢出或必需帧已过保留期，就补日志或重启同步，不能删老帧后宣称成功；跨节点也检查同一历史和可补范围。小陈切成十档视图时重新建立基线，进入、退出档都从完整簿派生。先前请求晚到，则按本次 generation 拒绝，不靠取消请求碰运气。最终只有快照完整、身份一致、帧连续并且交接完成，页面才转 LIVE，网络请求全部成功不是验收依据。

**流程位置与核心机制：** 解决某个深度视图的快照锚点与订阅屏障，既适用于网关向客户端交付，也可用于内部消费者。源缺口识别见上一题；客户端长期恢复状态机见第 10 题。

**必要前提：** 快照标注 `streamID、epoch、viewVersion、depthSeq=S、sourceTo=W`。S 属于发布序列，W 属于源序列，二者不能直接相减或互换。以下以已发布快照 S=50、W=100，以及覆盖批次 101 的深度帧 51 为例。

## 第 1 层：为什么先请求快照再订阅会漏数据

**面试官：** 客户端先 HTTP 拉盘口，再打开 WebSocket 订增量，为什么不够？你会怎样设计？

**面试者：** 两个动作之间存在窗口。假设 HTTP 返回快照源水位 100，订阅建立前批次 101 已发布，实时流只从 102 起送，客户端会永远保留卖 60000。请求都成功也不能证明没有丢事实。

我会先在服务端或客户端建立实时缓冲屏障，再取得带发布锚点的快照 S=50，丢弃缓冲中序号不大于 50 的帧，从 51 连续应用。也可以提供一个把起点和快照绑定的订阅接口，内部完成同样的协调。重点不是一定用 HTTP 或 WS，而是快照到增量之间有可验证的连续交接，而非依赖两次请求时间很近。

## 第 2 层：先订阅只是先发了请求，屏障怎样才算成立

**面试官：** 你说先订阅。客户端发出订阅请求后立刻拉快照，服务端可能还没真正挂上订阅，这不还是有窗口？

**面试者：** 对，所以必须有明确的屏障确认。网关应先把订阅登记进该 stream 的扇出路径或取得可重放起点，建立有界缓冲，然后才确认订阅已受理。确认要带 subscriptionID、stream 身份以及可验证的起点语义，不是“收到 JSON 就 ACK”。

如果实时扇出在另一个进程，网关需要等上游订阅真正生效，或者依靠上游保留日志从指定游标补齐。没有这一步，客户端先发请求也不能消除竞态。确认只表示恢复通道已经覆盖该窗口，不表示快照已到达，更不表示客户端已经拥有一份可展示的盘口。

## 第 3 层：快照内容怎样对应它声称的序号

**面试官：** 订阅屏障成立了。快照服务遍历 map 需要时间，开头是 100、结尾已经是 101，怎样避免混合快照？

**面试者：** 快照必须来自不可变版本或一致读取边界，而不是遍历一个同时修改的簿再贴上“当前序号”。投影先整批生成版本 W，发布器把该视图对应的帧和发布锚点 S 协调提交，再允许快照服务引用这一对内容与身份。

若投影已到 102、发布器仅完成到覆盖 100 的 S=50，不能把最新簿 102 标成 S=50。要么返回对应 100 的已发布视图，要么等待发布提交到新锚点。数据内容、水位、视图参数、精度版本和校验和都要来自同一版本。只给快照加一个时间戳无法证明这些内容属于同一时刻。

## 第 4 层：缓冲里哪些帧可以丢，哪些必须接上

**面试官：** 你拿到 S=50 的快照，缓冲里有 49、50、51、52。具体怎么裁剪？

**面试者：** 先验证 streamID、epoch 和 viewVersion 都匹配，再安装快照 50；49 和 50 已被快照覆盖，可以丢弃，随后要求 51 的 prevDepthSeq=50，再依序处理 52。每帧是一个发布单位，sourceFrom/sourceTo 用来说明源覆盖，不用 sourceTo=101 去误要求“上一帧必须是100”。

如果只有 52 没有 51，就先补取 51，不能因为 52 修改的是不同价位而直接应用。若协议改为覆盖区间型帧，是否允许某帧覆盖客户端期待位置，必须由那个协议明确保证完整变更集合；本题基线用逐帧连续 depthSeq，不能临时借外部交易所的更新区间规则跳过帧。

## 第 5 层：快照太慢导致缓冲溢出，能否继续拼接

**面试官：** 你先缓冲再等快照。行情很快、快照很慢，缓冲溢出了，丢最老几帧后继续行不行？

**面试者：** 不行，丢掉的帧如果在快照之后，就是不可证明的缺口。缓冲需要字节数、条数和年龄预算，超限后这一轮同步失败，显式重启同步或从保留日志补齐，不能继续声称无缝。

可以减少快照大小、使用分片快照传输、缓存不可变快照和增加恢复吞吐，但它们都不改变完整性条件。分片快照还要带统一 snapshotID、总片数和校验，客户端收齐前不能把部分价位当完整簿展示。频繁重启同步时应退避或限流，避免快照风暴；不能只扩容缓存，把根本追不上的订阅永久挂起。

## 第 6 层：从缓冲切成实时时是否又有第二个窗口

**面试官：** 你已应用到缓冲尾部 52，准备切换实时。新来的 53 恰好在切换瞬间到达，怎么保证不会漏或乱序？

**面试者：** 同一个订阅不能有两条互不协调的发送路径。我会让网关的订阅状态机或客户端单消费者统一处理快照、缓冲和实时帧：缓冲清理与“进入 LIVE”的转移在同一串行边界完成，53 无论在哪一刻到达都进入这一个有序入口。

也可以一直走同一队列，不真正更换通道，只把状态从 SYNCING 改成 LIVE。不能先宣告缓冲为空，释放锁，再把新帧改送另一协程，因为这会产生漏帧、越序或重复。重复可用序号识别，越序也不能让新状态提前可见。切换动作本身必须像业务处理一样有明确的线性化点。

## 第 7 层：跨节点取快照与增量怎么办

**面试官：** 你把切换串行化了。但快照来自节点 A，订阅来自节点 B，两边缓存进度不一样，还成立吗？

**面试者：** 成立的条件是它们引用同一已提交发布历史，并能满足该快照之后的保留范围。A 返回 S=50，B 若最早可补到51就能交接，即使B当前已到60；若B仅保留55以后，则必须拒绝这份快照的衔接，换更新快照或去共享日志补51—54。

同名交易对不够，还要相同 streamID、epoch、viewVersion 和精度版本。A 的旧 epoch 快照不能与 B 的新 epoch 增量拼接；B 也不能本地随意重编号。为了简化，可把快照和续传路由到同一逻辑发布分片，网关仍可多实例；但亲和路由是实现选择，不是掩盖协议缺失的理由。

## 第 8 层：Top-N 和聚合会不会破坏快照衔接

**面试官：** 你要求 viewVersion 相同。如果客户端只订十档，服务端每 100 毫秒聚合，快照还能只带最后的源水位吗？

**面试者：** 不够。十档与完整簿是不同视图，100毫秒发布节奏也改变帧序列；快照要锚定这一个视图的已提交 depthSeq，并携带足够的规则身份。其后增量必须是相对于该视图上次已发布状态的差分，包括档位退出删除和进入补档。

例如十档边界变化而进入档没有新的源事件，发布器仍要从完整簿算出新成员。一个源 W 可对应多个视图各自不同的 S，不能只说“都到101”就认为可接。改视图参数通常重新订阅并取新快照；若协议支持原地切换，也必须提供显式屏障和基线替换，而不是客户端改变显示行数后沿用旧游标。

## 第 9 层：同步期间用户取消再重订，旧快照怎么办

**面试官：** 你要求重新订阅。用户第一次快照还没返回就切换视图，新订阅已成功，旧快照晚到会不会把新状态覆盖？

**面试者：** 所以还要区分本地订阅 generation。每次重新同步、切换交易对或视图，都分配新的 subscriptionID/generation；HTTP快照响应、缓冲帧、异步校验结果都与它绑定，旧 generation 即使内容合法也丢弃。

取消旧请求只是资源优化，不能作为正确性保证，因为响应可能已在路上。stream epoch 描述服务端发布历史，generation 描述这次客户端同步尝试，它们解决不同问题。新订阅先完成屏障、快照和连续追赶后才原子替换当前展示；期间旧视图若保留，只能作为明确标记的旧数据，不能让两代更新交叉写同一簿。

## 第 10 层：怎样覆盖快照竞态的全部关键窗口

**面试官：** 有了 generation，怎样验证初次订阅到 LIVE 的整条路径没有遗漏一个切换窗口？

**面试者：** 我会围绕几个线性化点枚举：订阅屏障前后、快照版本取得前后、快照安装前后、缓冲尾部追平前后、generation更新前后。让101、102分别落在这些位置，检查最终客户端状态与同水位参考簿一致。

再分别加入丢51、重复51、快照分片缺失、跨epoch、缓存过期和旧响应晚到，正确结果必须是补齐或拒绝同步，不能是带缺口进入LIVE。记录客户端最后应用S与源覆盖W，而不只检查屏幕价格；因为漏掉一个暂时不影响卖一的深层删除，也已经是错簿。这是一组手工和后续实现验证的设计，不冒称已执行工程测试。

## 本题收束

- **讲透的机制：** 先建立可证明的增量覆盖，再取得同版本快照，以发布游标衔接，并在单一状态机内切换实时。
- **易错边界：** “先发订阅”不等于屏障建立，源水位不等于发布序号，取消请求不能保证旧响应不再到达。
- **检验反例：** 快照 50 取到后，帧51在订阅生效前消失，客户端从52开始。即使所有网络请求成功，也必须拒绝这次同步，而不是显示为LIVE。
