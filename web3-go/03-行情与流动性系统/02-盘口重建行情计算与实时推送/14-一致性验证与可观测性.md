# 大问题 14：怎样证明行情正确，并在出现错簿时及时发现？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 不变量 / 连续前缀 | 每个合法版本必须成立的规则，以及从可信起点未断的事实链 | 校验状态、顺序、计算和交付，不拿页面在跳或无人投诉当证据。 |
| 参考实现 / 逐水位对照 | 简单可信的计算基准，以及每个可见边界分别比较 | 最终相同不能抹去中间错误 LIVE，内部簿正确也不证明对外删除已交付。 |
| checksum / 规范化编码 | 内容指纹，以及固定排序、字段、比例和分隔的编码 | 同身份同版本才能比较，依赖编码及碰撞假设，不是自动补回缺失量的纠错码。 |
| streamID / epoch / viewVersion / depthSeq | 哪个频道、哪段历史、哪种视图、哪一帧 | 连同源覆盖对齐后才能核对；Top-N 摘要只能验证那部分价位。 |
| 故障窗口 / 共同提交边界 | 可能只完成一半的执行间隙，以及状态一起落定的位置 | 逐个枚举检查点、游标、发布锚点和客户端应用，不靠随机重启替代分析。 |
| sourceSeq / depthSeq / tradeSeq | 源批次、深度帧和逐笔各自的计数单位 | 只能在相同命名空间比较落后量，不能跨单位直接相减。 |
| 数据年龄 / 时钟误差 | 数据已等待多久，以及跨机器时间差的不确定性 | 按接入、应用、发布、写出、客户端阶段拆分，结合队列年龄和水位判断。 |
| 事件时间 / 源进度 / Ping-Pong | 交易发生时间、源处理边界和传输探活 | 冷清可长时间无成交；普通探活不证明源已完整处理，缺口不能因此变健康。 |
| 高基数 / 抽样追踪 | 指标标签组合过多，以及保留有限诊断细节 | 连接和成交身份不无限铺成时间序列，日志还须限期和脱敏。 |
| 影子状态 / 隔离 / fencing | 旁路重建待校验状态、停止错版扩散和资源侧拒旧主 | 对账用于发现与修复，不能替代事前围栏、防缺口及整批可见规则。 |

## 把整篇文章压缩成一个故事

巡检员小梅看到 WebSocket 心跳正常、页面价格不停跳，却发现客户端还残留卖 60000。她先把受影响视图标为失效，保留输入、版本和游标，不急着重启抹现场。排查从同 stream、epoch、视图和深度切点开始，统一整数编码与排序后比较 checksum；十档摘要即使相同，也不能替深层档位背书。小梅沿客户端、网关、发布器到投影逐段对照，发现内部已处理删除，但对外帧漏了键。后来绝对量恰好修好终态，也不能证明此前公开的 LIVE 正确，因此验证设计要逐边界与参考重放比较，并枚举缺片、冲突、崩溃和切主窗口。监控则拆开源到接入、排队、发布、写出及应用年龄，只在同类序号内看落后，结合时钟误差与队列预算判断。没有新成交可能只是市场冷清，不能伪造成交证明活跃，也不能让 Pong 掩盖源停滞。连接细节放有限抽样追踪，不把身份全铺成高基数指标。修复按影响范围隔离并校验切换，还要追查统计和K线；对账能收敛问题，却不替代事前执行约束，设计过的测试也不冒称已经运行。

**流程位置与核心机制：** 跨接入、计算、发布与客户端，建立可验证的不变量和观测方法。本题是质量验证设计，不是额外工程项目，不声称实际运行测试或测得服务指标。

**必要前提：** 使用总览的源连续前缀、整批投影、发布视图、客户端游标与健康状态。对照必须在相同身份、规则和水位上进行。

## 第 1 层：上线后没人投诉，能说明盘口正确吗

**面试官：** 盘口一直在跳、WebSocket 连接稳定，怎样证明它不是一份持续更新的错簿？

**面试者：** 不能用“在动”和“在线”证明正确。我会把正确性拆成状态、顺序、计算和交付四类断言：价位量合法、批次结束不交叉；连续水位没有偷跳；成交量和金额来自稳定成交身份；客户端只在同 stream/epoch 下连续应用。

然后用简单可信的参考实现顺序回放同一输入，与优化实现逐水位比较。总览的101可手工核对：卖60000消失、卖60100剩0.05，总量0.25、金额15015、VWAP60060。手工案例证明我们理解了规则，但它不覆盖所有故障，也不能据此宣称性能或生产稳定性已验证。

## 第 2 层：双方都算 checksum，怎样保证比较有意义

**面试官：** 你用参考状态对照。实际线上服务和客户端都输出 checksum，直接比较能定位错簿吗？

**面试者：** 必须先对齐身份和版本。比较同一 streamID、epoch、viewVersion、depthSeq 以及对应源水位，约定买价降序、卖价升序、字段和分隔符、整数 scale、零量剔除及编码。否则只是不同水位或不同序列化顺序导致假警报。

Top-N 校验和只能证明那N档，不覆盖深层幽灵档；哈希相等也依赖碰撞概率和规范化协议，不是数学上绝对证明。checksum不一致应触发隔离、诊断与重同步，不能把它当成能够自动找回缺失量的纠错码。若客户端在错误视图上算对了自己的hash，也不能代替服务端提供可信比较基准。

## 第 3 层：最终状态一致，为什么还要逐边界比较

**面试官：** 你比较同水位的状态。如果最后103一致，为什么还要比较101和102，最终收敛不就够了吗？

**面试者：** 因为系统可能在中途发布错误的LIVE状态，而后来某个绝对量更新恰好修复。用户或策略已经按错误盘口决策，最终一致无法撤回这个影响。要验证每个公开可见版本都来自合法连续前缀，而不只是结束时hash相同。

故障输入可以对101重复、把102和103交换、丢一个传输分片、让相同序号带不同内容。合法行为是等待、补齐或重建，不能跳过去后“等将来修好”。参考比较还应检查发布帧的删除键、源覆盖和快照锚点；内部簿正确但对外漏掉某个删除，仍然是端到端错误。

## 第 4 层：故障输入怎样覆盖持久化窗口

**面试官：** 顺序边界能比较。恢复时常见的问题是“算完了但还没存”，你怎样选崩溃位置？

**面试者：** 按状态共同提交边界列窗口，而不是随机重启后看页面。重点位置包括批次校验后、状态更新后游标提交前、检查点文件写完但清单未切换、发布帧记录后快照锚点提交前、网关写出后客户端应用前。

每个位置分别说明恢复依据：投影靠一致检查点和可靠源重放，发布靠已提交记录或换epoch重同步，客户端靠最后应用游标而非最后收到游标。验证结果要检查成交统计没有重复累计、同一个发布身份没有不同内容、旧主不能继续有效发布。故障注入属于后续可实施方法，本专题未运行这些测试，不能写成“全部通过”。

## 第 5 层：恢复正确了，线上应该观测哪些延迟

**面试官：** 你能验证恢复。实时系统更容易出现“没错但落后”，监控一个消息延迟值够不够？

**面试者：** 不够。我会分开观察源提交到接入、接入排队、批次应用、发布排队、网关写出和客户端应用年龄。时间差受跨机器时钟误差影响，要同时观察同一命名空间的水位落后量、最旧队列年龄、补取状态和缓冲使用量。

不同序号不能直接相减，sourceSeq和depthSeq不是同一单位；逐笔条数落后也不等于源批次数落后。指标应标明含义和健康状态。特别要区分“市场没有新成交”与“接入断了”：源侧可验证进度或心跳说明已处理到何处，而普通Ping/Pong只说明连接有响应，不能证明源行情仍在更新。

## 第 6 层：没有成交时怎样避免新鲜度误报

**面试官：** 你说不能用最新成交时间衡量所有健康状态。某市场半小时没有成交，怎样判断是正常冷清还是行情停了？

**面试者：** 分别维护业务事件时间、源处理进度和通道活性。逐笔最新成交时间长时间不变可以合法，源进度却应按其协议持续有可验证更新；如果交易对确实没有任何结果，源可提供带身份和位置的健康证明，说明日志已检查到该边界，而不是伪造一笔成交。

观测中标明空闲和停滞的区别，告警阈值由市场特征及契约决定。GAP状态即使连接心跳正常也不能转LIVE；新鲜度恢复需要连续数据或可信快照。反过来，一次时钟偏差也不应触发“漏单”结论，要结合序号、队列和源健康判断。此处不编造一个适用于所有交易对的毫秒SLO。

## 第 7 层：高基数指标会不会先拖垮观测系统

**面试官：** 你想看每个客户端的应用年龄和游标。如果把连接ID、tradeID都做指标标签，会发生什么？

**面试者：** 时间序列基数会失控，观测本身可能占用大量资源。我会把稳定且受控的维度用于指标，例如服务分片、频道类型、健康状态和经过容量评估的交易对；连接、订阅、成交身份放在抽样日志或可查询追踪里，设置保留期和脱敏规则。

聚合指标关注分位延迟、缺口次数、重同步率、慢客断开原因和队列预算；诊断日志保留stream身份、源覆盖、发布游标与本地generation，便于串起链路。公共行情里不能顺便写入私有账户明文。观测能帮助复现故障，但不能靠事后日志代替事前的原子边界与可靠交付约束。

## 第 8 层：发现不一致后，修复顺序是什么

**面试官：** 你有可查日志和指标。线上发现某分片checksum不一致，是先重启、重算，还是继续发送等待对账？

**面试者：** 先控制错误传播，标记该视图失效，停止以LIVE身份推进并通知必要消费者重同步；保留诊断水位、版本和输入证据，避免盲目重启抹去现场。再判断是单客户端、网关缓存、发布器、投影还是源事实问题，按同身份同水位向上逐段对照。

若投影坏了，就以可信快照和连续日志构建影子状态，校验后显式切换；若仅某客户端坏了，隔离该订阅即可。修复后不仅核对当前盘口，还要检查成交统计、K线修订与发布历史是否受影响。对账只能发现并收敛已发生问题，不能证明此前没有错误，也不能代替fencing、防缺口和整批可见性。

## 本题收束

- **讲透的机制：** 同身份同水位对照、逐公开边界验证、故障窗口枚举、数据新鲜度与连接活性分离。
- **易错边界：** 最终hash相同不证明中间版本正确；Top-N校验不覆盖全簿；对账不是预防错序的执行协议。
- **检验反例：** 服务心跳一直正常，深度消费却卡在100，成交源已到101。如果监控只看连接存活或最新价是否非零，就会把陈旧盘口误判为健康。
