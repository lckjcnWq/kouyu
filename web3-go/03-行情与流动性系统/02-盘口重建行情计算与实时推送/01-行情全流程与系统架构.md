# 大问题 1：一笔成交怎样变成客户端可见的盘口、逐笔与行情指标？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 权威撮合结果 / 公共投影 | 已确定的交易事实，以及面向公众的派生读模型 | 撮合裁决成交，行情只能重建视图，不能修余额或自行撤销成交。 |
| 价位绝对量 / L2 | 某方向某价格上现在还剩多少挂单 | 批次 101 把卖 60100 设置为 0.05，不是再减 0.05。 |
| 可靠提交 / 账户结转 | 成交义务确定，以及资产账本实际完成入账 | 行情可先显示已提交成交；不代表预留已经释放或余额已经可用。 |
| sourceSeq | 单交易对权威结果流的连续位置 | 源到投影逐批检查；从 100 先见 103 应进入缺口状态。 |
| streamID + epoch + depthSeq | 深度频道身份、历史世代和发布位置 | 深度可合并或跳过无变化源批次，不能要求它与 sourceSeq 一一对应。 |
| tradeSeq / tradeID | 逐笔流位置，以及成交本身的稳定身份 | 一批可含多笔；重发不能让同一成交再次增加成交量。 |
| 不可变视图 / BBO | 完成后不再改的版本，以及该版最优买卖报价 | 多价位、源水位和报价同批可见；不同指标仍须声明各自水位。 |
| 订阅屏障 / 扇出 | 先缓冲再接快照的交接，以及一帧分给多个连接 | 共享帧不等于共享客户进度；写出 socket 不等于客户端已应用。 |
| 有界队列 / 重同步 | 限制积压的缓冲，以及重新建立可信本地状态 | 慢客应隔离或显式失效，不能静默漏掉必需深度帧。 |
| finalized / 链上重组 / AMM | 链上终局、分叉回退，以及按池子曲线兑换的机制 | 只是改前提后的比较；不能把托管订单簿的提交和 L2 模型直接搬过去。 |

## 把整篇文章压缩成一个故事

B1 的买单成交后，客服小周发现页面已经出现两笔成交，余额却还没变，担心行情把交易做了两遍。后端解释，撮合已可靠提交批次 101，成交义务确定，但账户消费者仍在结转；零费案例实际支出 15015 USDT、预留 15025，应由账务释放差额 10，行情没有这项权限。行情单写者核验连续源批次后，整批删除卖 60000、设置卖 60100 剩余 0.05，再交出不可变版本，避免读到一半的新盘口。深度按自己的发布序号交付，两笔成交各有逐笔位置，指标标明各自水位，不把异步结果硬拼成同一瞬间。网关只接本机需要的频道，复用帧但隔离慢连接；新订阅先缓冲更新，再接一致快照。小周即使看到服务器写出成功，也要等客户端应用才能说本地已更新。缺批时停止健康推进，不能靠心跳或时间戳证明完整。若以后换成链上来源，还得处理确认、重组和回滚；换成 AMM，连挂单深度模型也要重定，不能只换一个接入口。

[返回专题总览](README.md)

**流程位置与核心机制：** 串起权威撮合结果、行情投影、发布、分发和客户端应用，解释每段的完成条件。具体排序、快照和恢复分别在后续母题深入。

**必要前提：** 沿用总览的 BTC/USDT 托管现货案例。B1 买 0.25 BTC，批次 101 产生两笔成交；公共行情是已提交结果的派生视图，不是资产系统。

## 第 1 层：从成交确定讲到页面可见

**面试官：** B1 这笔订单成交后，盘口、最新价和客户端页面是怎样更新的？

**面试者：** 在这个模型中，撮合先可靠提交批次 101，里面同时给出两笔成交和批次结束后的价位绝对量。行情服务校验源身份、顺序和完整性，再由交易对单写者整批更新 L2 与成交统计；卖 60000 删除，卖 60100 剩 0.05。发布器根据同水位视图生成深度帧、逐笔帧和指标更新，网关按订阅分发。客户端从一致快照起步，检查增量身份和序号，整帧应用后再渲染。

我会把“撮合已提交”“投影已应用”“网关已写出”“客户端已应用”分别说明。它们是不同阶段，不能把服务器写 socket 成功当作用户已经看到，更不能当作账户已经结转。

## 第 2 层：既然是派生视图，谁有权修正成交

**面试官：** 你说行情由撮合结果派生。行情服务发现数量不对，可以自行修改成交或撤掉这笔交易吗？

**面试者：** 不可以。撮合拥有订单和成交裁决权，行情只拥有公共投影。比如收到批次 101 后计算出负的卖档量，应该先判断是精度、事件语义、缺失前序还是源批次错误，标记异常并停止推进，不能在行情内把数量钳成零，更不能修改账户。

恢复应从可信快照和连续源日志重新构建；如果确定权威源本身有业务错误，则走显式、更正可追溯的业务协议，不靠行情服务偷偷改历史。L2、ticker、K线即使分开计算，也必须标注各自覆盖的源水位，不能因为它们都来自同一批次就默认任何时刻完全同步。

## 第 3 层：行情已见成交而余额没变，是否矛盾

**面试官：** 你不让行情决定账户，但客户端先看到 T101-1、T101-2，余额仍旧，这算不算交易不一致？

**面试者：** 这是需要解释的跨投影暂态，不一定是错误。批次已可靠提交意味着成交义务已经确定；账户消费者还在按成交身份结转时，公共行情可以先发布。B1 零费实际支出 15015 USDT，相对 15025 的预留应释放 10，资产处理由账务链路幂等完成。

禁止的是行情提前消费未提交候选成交、余额提前释放后迟到成交又执行，或账户失败就让行情删除真实成交。接口应分别暴露订单成交状态和账务可用状态，必要时说明账户更新中。不能为了页面“一起动”而让公共行情阻塞在每个账户回调上，也不能把这种异步当作允许账务无限期不收敛。

## 第 4 层：异步链路怎么证明没有漏事件

**面试官：** 既然各段异步，怎样证明行情不是漏了一个批次后仍然往下发布？

**面试者：** 源到投影使用该交易对连续的 `sourceSeq`，在 100 后只能应用 101，再到 102。投影水位和本批状态一起前进；先见 103 要进入 GAP，而不是用时间戳排序后继续。

投影到客户端则使用独立的 `streamID + epoch + depthSeq`。因为没有盘口变化的源批次可能不生成普通深度帧，客户端不能要求 sourceSeq 每次只加一。深度帧应声明覆盖范围，发布器负责证明该范围源事实连续。逐笔另有 tradeSeq，一批两笔成交占两条位置。每段都有自己的连续性契约，不能用“消息队列保序”代替跨段证明。

## 第 5 层：多种行情怎样避免拼出不存在的瞬间

**面试官：** 源顺序有了，但深度和 BBO 被不同协程读取，会不会出现卖一价格已更新、卖一量却还是旧的？

**面试者：** 会，所以我不让多个协程边写边读同一个可变簿。单写者先完成整个批次，再发布不可变版本，BBO 从该版本派生。批次 101 的两处卖盘更新和 sourceSeq=101 是同一个可见边界，不能逐价位向读者暴露。

ticker 和 K线如果由独立消费者计算，允许稍后完成，但返回各自水位和版本。客户端若要同屏严格对齐，就选定共同水位或服务端组合后的完整版本，而不是把“最新深度”和“最新成交统计”拼起来后声称来自同一时刻。一般展示可以允许受控差异，协议必须把这种差异讲清楚。

## 第 6 层：分发速度跟不上时能否反压撮合

**面试官：** 你要求发布同水位视图，如果几万个客户端变慢，行情会不会反过来阻塞撮合？

**面试者：** 不应让外部连接成为撮合提交的同步依赖。撮合把已提交事实保留在可靠源日志，行情通过游标消费；网关又以每连接有界队列隔离慢客。慢客户端需要断开或显式重同步，不能让全部订阅等它，也不能静默跳过一条必需深度帧。

发布侧可以按约定聚合深度绝对量，但必须保留覆盖区间内每个变更键的最终值，逐笔成交不能拿最新一笔覆盖所有成交。如果行情自身整体落后，要保护源日志保留期、降低可选视图成本和限制新订阅；即使撮合继续，也应把对外行情标为延迟或不可用，而不是伪装实时。

## 第 7 层：网关是否要保存所有交易对

**面试官：** 慢客隔离了，但每台网关都接全市场数据，会不会浪费带宽和内存？

**面试者：** 不需要默认接全量。网关可按本机活跃订阅维护引用计数，仅订阅有需求的交易对与视图；热门频道可以复用同一份不可变序列化帧，再扇出到连接队列。最后一个订阅离开后，可延迟退订防止频繁抖动，但缓存和延迟都要有上限。

这不会改变快照和增量契约：首次订阅仍须建立缓冲屏障，不能先返回某个缓存快照再临时开流。网关一般不重新计算权威 L2，更不拥有撮合权。网关缓存只在身份、水位和新鲜度都可验证时才可复用；不能因引用计数非零就断言上游数据健康。

## 第 8 层：换成链上系统后哪些前提失效

**面试官：** 你让网关复用已提交结果。如果订单簿的成交来自链上，“已提交”还具有相同含义吗？

**面试者：** 这是明确改变源事实终局性，不是加一个 RPC 就能沿用。基线里可靠提交后的成交不会因行情重建撤销；链上订单簿还需要区块 hash、高度、交易和日志位置，并区分 pending、确认及 finalized。未终局区块可能重组，消费者必须能回滚到共同祖先，撤销相关簿和统计，再应用新链。

网关与客户端也要得到重置或修订标记，不能把旧链的 101 和新链的 102 当成连续事实。若产品是 AMM，则所谓深度来自储备和报价曲线，连 L2 的状态模型都变了。我会先声明产品和终局性，再设计序号与恢复，而不在前面坚持 CEX、被追问时悄悄切到另一套架构。

## 本题收束

- **讲透的机制：** 权威事实与派生状态分离，每段独立定义版本、完成条件和恢复责任。
- **易错边界：** 撮合提交不等于账务完成，socket 写出不等于客户端应用，连接在线不等于行情新鲜。
- **检验反例：** 假设账户暂未结转且某客户端掉线，批次 101 仍应只确定一次；其他客户端可看到正确行情，掉线者恢复后不得让成交量多加 0.25 BTC。
