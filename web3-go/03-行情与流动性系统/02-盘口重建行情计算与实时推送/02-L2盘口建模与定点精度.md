# 大问题 2：怎样建模并高效维护一份正确的 L2 盘口？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| L2 / L3 | 按价位汇总的盘口，以及细到订单的公开数据 | 本文只建 L2，不保存撮合同价队列，也不能据此推断个人排队位置。 |
| side / priceTicks / qtyLots | 买卖方向、整数价格和整数剩余量 | 键为方向加价格，值为数量；同价买卖不共用一个键。 |
| 绝对量 / 零量删除 | 直接设置现存总量，设为零就移除档位 | 设置重复不再扣量，但旧设置会覆盖新值，不能免除连续性校验。 |
| 哈希表 / 有序索引 / P | 快速找量的字典、按价格排序的目录和价位数 | 两份结构同步维护；更新通常涉及 O(log P)，不能泛称全部操作常数时间。 |
| 单写者 / 不可变视图 | 一个逻辑执行者改簿，读者只看完成的版本 | 单写者不自动防止半批读取，源水位、价位和报价要同版发布。 |
| BBO / 交叉簿 | 最优买卖报价，以及买价达到或超过卖价的状态 | 本文连续撮合基线要求批后 bestBid<bestAsk；空侧用 null，不用零价代替。 |
| Top-N / 补档 | 只展示前若干档，以及靠后价位进入展示范围 | 从完整簿派生差分；内部丢掉深层价位后不能凭输出协议找回。 |
| tick / lot / scale | 价格步长、数量步长，以及整数换回业务量的比例 | 本例各为 0.01，价格乘数量的一个整数单位是 0.0001 USDT。 |
| checked arithmetic / 宽整数 | 检查溢出的计算，以及容纳更大中间结果的整数 | 必须在乘法前选择足够范围，溢出后再转大整数无效。 |
| instrumentVersion | 交易对精度规则的版本号 | 同一整数可在新旧 lot 下代表不同数量；变更需生效水位和迁移屏障。 |

## 把整篇文章压缩成一个故事

工程师小何要给 BTC/USDT 页面提供盘口，先拒绝复制撮合的账户和订单队列：公众只需要按方向、价格汇总的 L2。批次 101 到来后，他把卖 60000 删除，把卖 60100 的量设为 0.05，而不是再扣一次；入口仍拦住重复和乱序，避免旧值把新簿覆盖。价位量放在哈希表，有序索引负责找最优价格，二者由同一写者维护，但读者只拿整批完成的不可变版本。产品只显示十档，他仍保留完整簿，让第十档删除时，原第十一档即使没有新事件也能补上，并对旧、新展示集合生成删除和新增。计算金额时，小何核对 tick 与 lot 的单位，在足够宽的整数里相乘，输出字符串，不让显示舍入污染内部数量。后来数量步长调整，他按版本和生效屏障迁移，旧客户端不能继续按旧比例解释。最终验收不仅看价位是否有序，也看批后买卖是否交叉；合法空侧返回 null。绝对量、单写者和整数各解决一类问题，任何一个都不能单独保证整份簿正确。

**流程位置与核心机制：** 负责投影内部的价位状态、索引、批次可见性、Top-N 和数值精度。它不重新实现撮合的价格时间队列，也不替代下一题的源连续性校验。

**必要前提：** 使用总览的 BTC/USDT 完整 L2。tick=0.01，lot=0.01，输入价位为批次结束后的绝对剩余量。

## 第 1 层：L2 与撮合订单簿有什么区别

**面试官：** 你要重建盘口，会保存每笔订单的 ID、账户和时间优先队列吗？

**面试者：** 公共 L2 不必保存这些。它按买卖方向和价格聚合同价位剩余量，键是 `(side, priceTicks)`，值是 `qtyLots`；撮合内部的订单身份、同价时间队列和撤单索引属于另一层权威状态。

例如卖 60100 初始有 0.20 BTC，可能由一单或多单组成，L2 只关心总剩余量。应用 101 后该档为 0.05，卖 60000 消失。只有 L3 产品才需要公开订单粒度的增删改协议，而且仍不能泄露账户。先确定数据层级，是为了避免把撮合引擎全量复制到每个行情服务，也避免用 L2 推断根本没有发布的排队位置。

## 第 2 层：绝对量为何优于减量，能否任意跳过事件

**面试官：** 你把 60100 直接设置成 0.05，而不是减去 0.15。这样重复事件就安全了，是否可以忽略顺序？

**面试者：** 不能。绝对量让同一次设置重做不会再次扣量，但迟到旧设置仍会覆盖新状态。若 101 把 60100 设为 0.05，102 的独立变体又把它设为 0.08，再到的旧 101 就不能回写 0.05。

而且跳过一批可能漏掉另一个价位的删除；后面某一档有新绝对量，并不能修复全簿。因此仍需源身份和连续 sourceSeq，重复批次在状态机入口拦截。量为零是删除价位，不是保留一个零量卖一；负量、未知 side、非法 tick/lot 和同批重复键在修改前拒绝，不能边应用边等校验失败后再想办法回滚。

## 第 3 层：既要查价位，又要找最优价，用什么结构

**面试官：** 你需要按价格设置和删除，还要快速找卖一、买一。只有 Go map 够吗？

**面试者：** 小型教学数据用 map 后排序可以解释正确性，但对持续更新的生产设计，我会用哈希表保存价位量，配合有序价格索引。哈希查询通常是均摊 O(1)，有序索引插入删除 O(log P)，P 是价位数；若维护最小/最大端缓存，取 BBO 可以 O(1)，否则按索引实现是 O(log P)，不能泛称所有结构都常数时间。

map 与索引必须由同一个写者同步更新，删除最后一个最优价位时更新端点。若价格范围很小且稠密，可以用数组和位图换取更低常数，但成本与价格范围相关；若范围宽且稀疏，不能申请一个覆盖所有可能价格的巨大数组。选择应由价位分布和更新模式决定。

## 第 4 层：有序索引正确，为什么仍会暴露错簿

**面试官：** 你让 map 和索引由同一写者更新。批次 101 要删一个价位再改另一个，读协程夹在中间怎么办？

**面试者：** 单写者只解决写竞争，不自动解决读到中间态。我会让写者在私有可变状态完成全部校验和更新后，生成同水位不可变读视图；快照、BBO 和发布器都引用完整版本。需要的话使用持久化树或复制变更节点，不要求每次复制整个簿。

批次 101 不能让读者先看见卖 60000 已删，却仍把卖 60100 的量当成 0.20。状态指针、sourceSeq 和派生 BBO 必须一致发布。如果采用锁，也必须把整批变更和读快照放在正确的互斥边界内，不能逐个 map 操作加锁后宣称批次原子。选无锁读不是目标，同版本读才是目标。

## 第 5 层：只推十档，为什么内部还要完整簿

**面试官：** 既然读者拿不可变视图，而产品只显示十档，能不能内部也只保留十档，节省内存？

**面试者：** 如果源只提供局部深度，可以设计明确的局部协议，但不能假装它是完整簿。本基线保留完整 L2，再派生 Top-10；因为第十档删除时，原第十一档可能没有任何新事件，却必须进入新视图。

发布 Top-N 增量应比较“上一次已发布的 Top-N”和“本次完整簿的 Top-N”，生成离开集合的删除和进入集合的绝对量。只转发源的前十档变化会漏补档。若内存必须裁剪，就需要权威上游提供足够覆盖的快照和可信补档保证，或由权威上游持续提供完整 Top-N 替换，接入层以每次完整成员替换局部状态；单纯把下游输出改成“完整 Top-N 替换”，无法找回内部已经丢弃的第十一档。这是输入协议与能力改变，不是 map 里随手删掉深层价位的优化。

## 第 6 层：价位都正确，计算为何还可能差一分钱

**面试官：** 你提到价格索引和数量都用整数。直接用 int64 乘价格和数量，再除 scale 就够了吗？

**面试者：** 还不够，必须检查乘法与累计溢出，并声明量纲。案例价格一个 tick 是 0.01 USDT/BTC，数量一个 lot 是 0.01 BTC，所以乘积一个单位为 0.0001 USDT。T101-1 是 6000000×10=60000000 个金额单位，即 6000 USDT。

Go 可以在范围证明充足时使用 int64 并做 checked arithmetic，超过范围则采用宽整数或定点十进制。不能先 int64 相乘溢出后再转 big.Int。聚合量同样要检查上限；输出用十进制字符串，避免 JavaScript Number 丢失大整数低位。金额舍入发生在哪一步、朝哪个方向，都应由产品规则规定；盘口剩余量不能凭显示精度反向覆盖内部精确值。

## 第 7 层：交易对调整精度时怎么办

**面试官：** 你把 scale 写进规则了。交易对从 0.01 改成 0.001 的数量步长，旧快照还能接新增量吗？

**面试者：** 不能在缺少版本协议时直接接。相同整数 10 在旧 lot 下是 0.10 BTC，在新 lot 下是 0.010 BTC；把它们混起来，即使序号连续也会把量缩小十倍。需要 instrumentVersion 明确元数据及其生效水位，由源保证跨变更的解释规则。

如果能精确迁移，服务在屏障位置转换完整状态，校验总量后发布新视图版本；若无法保持原协议，就建立新 stream 视图/epoch 和快照，要求客户端重建。旧客户端不支持新版本时明确拒绝或退订，不能继续按旧 scale 解析。版本变更不能靠字段名仍叫 qtyLots 就假设含义没有变化。

## 第 8 层：怎样判断簿是坏了，而不是市场特殊状态

**面试官：** 版本和数量都检查了，如果发现买一高于卖一，是否一定是程序错误？空一边又该怎样处理？

**面试者：** 在当前连续撮合的现货基线中，完整已提交批次结束后双边非空应满足 bestBid<bestAsk；出现交叉先隔离并核对源与投影，不自行删除挂单“修复”。但如果明确切到集合竞价、停牌阶段或跨场所合成簿，这个不变量可能不同，应先改变模型和阶段标记，而不是套用旧断言。

一侧为空本身合法，卖一或买一返回 null，相应价差和中间价也为 null。空簿不能返回 0 作为有效报价，否则可能触发错误的行情告警甚至下游风控。验证要在批次边界和同一水位进行；读到不同版本的两侧产生的交叉，不是市场真的允许套利，而是读一致性有问题。

## 本题收束

- **讲透的机制：** 方向价位建模、绝对量语义、完整簿与限深视图分离、整批可见及定点精度。
- **易错边界：** 设置幂等不等于顺序无关，单写者不等于读者看不到中间态，Top-N 不等于完整 L2。
- **检验反例：** 设第十档删除、第十一档没有事件。如果客户端最终只剩九档，说明实现只转发了源变化，没有从完整簿派生新的视图差分。
