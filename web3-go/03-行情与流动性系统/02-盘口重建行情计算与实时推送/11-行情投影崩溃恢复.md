# 大问题 11：行情投影崩溃后，怎样恢复同一事实水位、正确统计并继续可信发布？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 源提交 / 投影提交 / 发布提交 | 事实确定、完整计入本地、确定对外帧内容的三道边界 | 可各自落后；行情崩溃不能要求撮合重做或撤销成交。 |
| 恢复状态闭包 / 检查点 | 恢复全部承诺输出的足够状态，以及它的一致保存版本 | 不只是 L2 和累计值，还须覆盖去重、窗口、规则及修订所需依据。 |
| C100 / C101 / L2 源快照 | 同水位完整检查点的示例名，以及只提供盘口的定格图 | 完整 C100 可重放指标，只有盘口 100 不能默认更早统计为零。 |
| lastSourceSeq / 消费确认 | 本地完整应用位置，以及给传输系统的收讫进度 | 恢复以一致检查点为准；确认走得更远不能成为跳过重放的理由。 |
| tradeID / batchHash / 去重 | 成交身份、批次指纹，以及避免重复计量的依据 | 去重标记、统计和游标要共同提交；同号异内容或身份冲突须隔离。 |
| T / (T-W,T] / 淘汰状态 | 计算时点、滚动窗和已经移除哪些成员的记录 | 恢复成员及时间推进规则，避免再次扣除或漏扣到期成交。 |
| OHLC / revision / 水位线 | 桶内价格摘要、持久修订号和事件时间进度 | 首尾排序键、封口及待修订状态也要恢复；不能只存四个价格。 |
| 持久交接 ID / 快照锚点 | 可查证同次发布交接的身份，以及已提交发布版的位置 | 重试找回原帧原号，不能用新投影内容重做旧号或贴旧锚点。 |
| epoch / leaderTerm / 易失缓冲 | 发布历史世代、围栏令牌和重启会消失的留存 | 丢原发布依据须换代且隔离旧主；换代不补源缺口，tradeID 不随之改变。 |
| WARMING / UNAVAILABLE / 统计覆盖 | 指标尚在补齐、无法提供，以及哪些历史已有证据 | 授权快照可单独救簿，不能由此声称逐笔、窗口及历史K线全部恢复。 |
| 确定性重放 / 规则版本 | 固定条件重算同一状态，以及决定计算语义的规则身份 | 固定源前缀、T、水位线和舍入规则；升级须迁移，不能以重启时 now() 偷换目标。 |

## 把整篇文章压缩成一个故事

行情进程处理批次 101 时，只删除卖 60000、累计第一笔金额就崩溃了。值班员小顾没有请撮合重做，而是丢弃半批，回到包含盘口、统计、去重和游标的完整 C100，再重放整个 101，得到一次 0.25 BTC、15015 USDT 的贡献。只恢复盘口会掩盖双算，单独先存去重又会漏算，所以检查点必须把这些状态放在同一边界。窗口还要知道成员和已经执行的淘汰，K线还要恢复首尾排序键、修订和时间策略，不能只留累计值。投影恢复到 101 后，发布若仍停在覆盖 100 的 S，就查持久交接记录重用原号原帧，不能把新簿贴到旧 S。只有易失发布缓冲时改建 epoch 并隔离旧主，但这并不修复源缺批。若日志已过期，授权 L2 快照只能先救当前簿，逐笔和指标还须归档或可信指标检查点；证据不全就标 WARMING 或不可用，等满一个窗口也不自动补回旧K线。小顾最终固定源水位、计算时点和规则版本对照重放，分别验收各通道后才恢复 LIVE，不让“盘口看着正常”替缺失统计背书。

[返回专题总览](README.md)

**流程位置**：可靠提交 `ResultBatch` → 行情单写者应用 → 一致检查点与源日志重放 → 不可变视图 → 发布记录及快照锚点 → 网关与客户端。本题讨论行情投影与发布恢复，不让撮合重新裁决成交。

**核心机制**：检查点必须构成“恢复状态闭包”；盘口、指标、去重状态与源游标共同恢复，再独立解决发布序号和快照锚点的一致性。不能证明历史连续或统计完整时，明确失效，不靠换世代伪装恢复。

**简短前提**：

- 沿用 BTC/USDT CEX 现货 L2，`tick=0.01 USDT/BTC`、`lot=0.01 BTC`，内部以整数价格档和数量手数计算。源快照 `sourceSeq=100`：买 59900=0.40，卖 60000=0.10、60100=0.20。
- 已提交批次 101：`T101-1` 为 `0.10 BTC @ 60000`，事件时间 `12:00:10.100 UTC`；`T101-2` 为 `0.15 BTC @ 60100`，事件时间 `12:00:10.101 UTC`。批后卖 60000 删除、60100=0.05，本批成交量 0.25 BTC、成交额 `6000+9015=15015 USDT`。正常 102 仅新增卖 60200=0.30，无成交。
- 源身份为 `sourceLogID + sourceSeq`；每个发布视图使用 `streamID + epoch + depthSeq/tradeSeq`，深度与逐笔各自编号。`leaderTerm` 是隔离旧发布者的令牌，不是客户端 `epoch`。
- 15015 仅指批次 101 的贡献。源快照 100 未提供历史统计，不能据此把历史累计额或完整 24 小时成交额设为零。以下故障、窗口过期和规则升级均为独立变体，不累计改变正常基线；内容为教学设计，不代表生产经历或实测指标。

## 第 1 层：崩溃恢复究竟恢复什么，依据哪个提交边界？

**面试官：** 行情进程在批次 101 之后崩溃，重启后把盘口重新加载出来，是否就算恢复成功？

**面试者：** 不算。要恢复的是同一事实前缀对应的完整投影，以及与它协调的对外发布历史，不能只恢复一张看起来合理的簿。先区分三个边界：源提交确定成交事实；投影提交表示盘口、指标与源游标一致前进；发布提交确定某个视图序号对应哪些不可变内容。三者可以落后，不能混称“处理完成”。源已可靠提交 101，即使行情仍停在 100，也只能重放 101，不能要求撮合重做成交，更不能回滚真实成交来迁就行情。恢复期间保留可信旧版本并标明 `RECOVERING/STALE`；源缺口则标 `GAP`。只有状态、水位和发布衔接分别验证通过，相关通道才能恢复 `LIVE`。

## 第 2 层：怎样让检查点真正覆盖上一层所说的完整投影？

**面试官：** 你要求盘口、指标和源游标一致。检查点只存完整 L2、累计成交额与 `lastSourceSeq=100`，够不够？

**面试者：** 不够。闭包的意思是：从检查点加后续可靠输入，能恢复所有承诺的输出，不能还依赖崩溃前的某个内存集合。至少保存交易对、完整 L2、`sourceLogID + lastSourceSeq`、精度与交易标的元数据版本、输入模式和计算规则版本、所需内容校验依据，以及成交去重状态。价格索引可从完整 L2 重建，但必须明确重建规则。窗口、未完 K 线和修订所需状态也属于闭包，不能只留下累计值。去重集合可以由可证明等价的游标替代，但须证明源批不可变、成交身份不会在后续新批重复，且游标之前全部成交已与指标共同提交；单个最大成交时间不满足证明。哪些状态选择不持久化，就必须声明其重建输入与覆盖范围，不能默认重启后自然补齐。

## 第 3 层：累计值之外，窗口和 K 线还藏着哪些恢复状态？

**面试官：** 上一答把窗口和 K 线列入闭包。若累计额已保存，为什么还需要成交成员、时间和修订信息？

**面试者：** 累计额不能回答“接下来该减谁”。滚动窗口 `(T-W,T]` 要恢复成员的成交身份、事件时间、量额及等价淘汰结构，还要保存计算时点 `T`、待入窗成员、已执行的淘汰位置与后续时间推进规则。先前已累计的金额不一定属于当前窗口；已消费但事件时间晚于 `T` 的成员，也不能因尚未入窗就丢弃。另须恢复水位线、迟到接纳与封口策略、相关版本和待处理状态。

未完 K 线不仅有 OHLC、量额，还要有决定开收盘的首末事件位置及权威并列顺序、封口状态、当前 `revision`、已发布修订状态和待修订窗口。此处按约定事件时间排序，同时间用权威源位置及批内 `ordinal` 决胜；最新成交价仍按权威成交顺序确定。101 的两笔若都在同一分钟且此前无成交，才得到 O=60000、H=60100、L=60000、C=60100；此前已有成员时不能覆盖它们。

**独立窗口过期变体**：令 `W=24h`，`T` 推进到次日 `12:00:10.100`，左开边界恰好淘汰 T101-1，本例在窗贡献变为 9015 USDT、0.15 BTC；历史累计贡献仍是 15015。恢复不能把这一淘汰动作再减一次，也不能忘减。

## 第 4 层：整批应用中只改了一半就崩溃，怎样退回一致状态？

**面试官：** 既然窗口成员和去重状态都要保存，假设源 101 已提交，本地只删了卖 60000，并累计第一笔 6000 就崩溃，怎么办？

**面试者：** 丢弃这段未完成投影，整体退到最近完整检查点 C100，再从可靠源重放整个 101。这里 C100 必须是覆盖所承诺指标的恢复闭包，不是仅有 L2 的源快照 100。恢复时一起还原盘口、指标、成员、去重集合和 `lastSourceSeq=100`，不能保留第一笔的去重标记，再重算其余状态。重放完成后才形成 C101：卖 60000 删除、卖 60100=0.05，101 的贡献恰为 15015、0.25，游标推进到 101。

实现上，单写者可在私有暂存状态应用整批，再一次切换读侧不可变引用；持久化则用事务，或完整数据先可靠落盘、校验后按持久化协议切换检查点清单。这里的“原子”指可见状态和检查点的一致边界，不意味着内存多字段修改天然持久原子。没有完整提交标记的半批不能被当成 C101，不能靠观察某个价位已删除猜测批次完成。

## 第 5 层：源提交、消费确认与成交幂等如何配合重放？

**面试官：** 上一答从 C100 重放 101。如果崩溃前已经确认消费 101，或者 C101 已落盘但确认没发出去，重启该听哪个游标？

**面试者：** 恢复以检查点中的 `sourceLogID + lastSourceSeq` 为准，消费确认不能替代它。这里选择先持久化完整投影提交，再确认消费：若 C101 已完成但确认丢失，收到重复 101 时核验身份及内容一致后跳过；若只有 C100，则主动补取 101，而不是因外部消费位置已到 101 就从 102 开始。若系统允许提前确认，必须另有覆盖恢复区间的可靠日志与保留保证，否则该方案不成立。

成交去重与指标、源游标必须在同一检查点或事务中提交。源批重复抑制只解决“同一批再次送达”，不能证明分开持久化的去重和成交额没有漏算、双算。同一源位置的 `batchHash` 冲突，或同一成交身份对应不同内容，必须隔离并查证；缺少校验依据时不能仅凭序号较小就忽略。正常 102 虽无成交仍推进源水位，但不增加成交量额；到期淘汰则由声明的 `T` 单独决定。

## 第 6 层：投影恢复了，发布提交前后崩溃又怎样处理？

**面试官：** C101 已恢复且不会重复累计，但发布器最后提交的是源水位 100、深度序号 S。此时崩溃，能把新盘口标成旧 S 发出去吗？

**面试者：** 不能。旧锚点必须保留为不可变的 `(streamID, epoch, S, sourceTo=100, 内容)`；不能把投影最新水位 101 硬贴到旧发布 S。投影到发布器的交接需有持久交接 ID，以及不可变视图或可确定再生它的全部依据。发布器将该 ID、分配的序号、帧内容、源覆盖范围、规则版本和对应快照锚点协调提交，再向网关开放。深度与逐笔分别记账，不能拿深度 S 推测 `tradeSeq`。

若在发布提交前崩溃，恢复后仍从旧锚点生成待发布内容；未提交的序号不得曾作为有效帧对外可见。若发布记录已经提交、但投影尚未记下交接完成，则按同一交接 ID 查询或幂等取得原发布批次，复用原序号与字节，不能再分配一个序号把同一交接当成新发布。已发布 K 线修订与待交接修订也遵循此约束。查不到记录且无法证明未提交时，不能在旧 epoch 内猜测续接；这是发布协议不确定，不是再加一次成交额的理由。

## 第 7 层：如果上一层的续传记录只在内存环形缓冲里呢？

**面试官：** 上一答依赖可查证的原发布批次。独立变体：没有持久发布日志，只有易失环形缓冲，但投影检查点完整，重启能延续旧 epoch 吗？

**面试者：** 不能。本变体中进程重启丢失了原帧与续传依据，必须建立新 `epoch`，按各视图协议重新编号、建立快照锚点并通知客户端重同步。恢复后的 `streamID + epoch + depthSeq/tradeSeq` 不能与旧世代的数字拼接。稳定 `tradeID` 仍属于同一成交事实，不随发布世代改变；重新交付历史逐笔可能产生传输重复，但不允许再次累计投影指标。需要补完整逐笔历史时仍须可靠成交日志，不能假装环形缓冲还在。

同时先隔离旧发布者；`leaderTerm` 用于 fencing，不承担客户端世代职责。新 epoch 只能解决发布历史无法延续，不能解决源缺口：若本地到 100、期望 101 却只有 103，仍须停在 `GAP`，不能给 103 换个新世代就声称源连续。盘口和统计的恢复证明也不会因换 epoch 自动成立。

## 第 8 层：源日志过期后，授权源快照能恢复到什么程度？

**面试官：** 上一答说新 epoch 不能掩盖源缺口。独立变体：C100 后的 101 已超出在线日志保留期，现在能取到授权源的 L2 快照 102，是否可以全部恢复？

**面试者：** 只能按快照契约救盘口，不能默认救统计。先验证它确实来自权威或被授权的可靠源，核对交易对、`sourceLogID`、水位 102、精度元数据、快照完整性与内容校验，再以该快照接续同源 103 及之后的完整批次。它为盘口建立了新的可信起点，不代表本地曾消费缺失的 101。

即使快照包含卖 60100=0.05、卖 60200=0.30，也推不出这期间必然发生 T101-1、T101-2，更推不出完整窗口成员、15015、K 线开收盘及已发布修订历史。不能把 C100 的统计贴上 `lastSourceSeq=102` 就跳过缺失成交。应分别维护盘口可信水位和统计覆盖状态：盘口证明通过后可以独立恢复服务；缺失统计标 `WARMING/UNAVAILABLE`，逐笔历史明确缺段。只有另有可信统计恢复材料，才能宣称对应统计已追平。

## 第 9 层：怎样补齐上一层缺失的滚动历史和 K 线？

**面试官：** 上一答只救回盘口。若还要恢复完整 24 小时统计和受影响 K 线，需要哪些额外证据，等 24 小时是否足够？

**面试者：** 可用归档成交日志，或可信指标检查点加后续日志，但必须证明覆盖。证明应关联源身份、连续区间、检查点水位、计算时点 `T`、水位线及规则版本；只按日期找出一批成交，无法证明迟到事件和中间批次没有遗漏。仅从某检查点之后重放也不够：检查点以前发生、仍处于目标窗口内的成员必须由前置状态或更早归档提供。未完 K 线同样需要已有 OHLC、首末事件位置、量额、revision、已发布修订及待修订状态，不能把恢复后第一笔误当整根 K 线的开盘。

恢复后按权威成交时间与约定并列顺序重建，核对窗口成员、淘汰和迟到处理结果，再接回在线源。输入不全就维持 `WARMING/UNAVAILABLE`，局部量额不能冒充完整值。等待一个窗口长度，仅在可信起点以后持续完整接收、事件时间覆盖和迟到边界均可证明时，才可能使当前滚动窗口重新完整；不能机械地“重启满 24 小时就转正常”。已丢失的历史 K 线、任意历史查询或全历史累计值，不会靠墙上时间流逝自行恢复。

## 第 10 层：如何确定性重放，并在规则变化后验收恢复？

**面试官：** 上一答即使找齐历史，重放时窗口又在过期，规则也可能升级。怎样证明恢复结果可信，而不是算出另一份同名行情？

**面试者：** 先固定检查点、输入前缀与目标 `(源水位, T, 水位线, 规则版本)`。事件驱动部分按源批次及权威批内顺序应用；时间驱动部分按记录的计算时点或可重建的定时规则推进，保存淘汰进度，不能用重启时的 `now()` 冒充崩溃前的 `T`。相同输入、整数精度、舍入和迟到规则应产生相同逻辑状态。恢复旧状态后追到新的当前时点，是另一次明确的时间推进，不要求新旧窗口金额强行相等。

**独立规则升级变体**：若迟到接纳范围由 v1 改为 v2，应先按 v1 重放，或经明确迁移、重建生成 v2 状态；不能拿 v2 读取 v1 检查点却省略语义迁移。旧 `candleKey + revision` 的已发布内容不可静默覆盖；采用可识别规则版本的后续修订，或显式新规则命名空间，并保留对外解释与重同步边界。

最后按相同目标时点验收：源连续且身份一致、L2 内容与水位匹配、去重及量额一致、窗口完整且无重复淘汰、OHLC 与修订正确、发布序号及不可变锚点可衔接、旧发布者已隔离。各通道验收并追到可信新鲜位置后才标 `LIVE`，不能因盘口正确就替缺失统计背书。

### 机制收束

恢复链条是“选取完整检查点 → 状态与游标一起还原 → 连续重放已提交事实 → 按声明时点恢复窗口与修订 → 查证发布交接或新建世代 → 分通道验收”。源提交回答事实是否成立，投影提交回答事实是否完整计入，发布提交回答外部身份对应什么内容；消费确认和 socket 写出均不能替代这些边界。

### 易错边界

- **L2 源快照不等于指标检查点**：只有盘口水位，无法证明窗口、去重、历史 K 线和修订闭包完整。
- **源批幂等不等于指标恢复正确**：绝对量重复设置可以不伤盘口，但分开持久化的成交额与去重标记仍可能双算或漏算。
- **源水位不等于发布序号**：`sourceLogID + sourceSeq` 与每视图 `streamID + epoch + depthSeq/tradeSeq` 分属不同命名空间；`leaderTerm` 不能混作 epoch。
- **新水位不能贴旧锚点**：恢复到 101 的簿，不能标记成原来只覆盖 100 的旧 S；修改快照标签不是发布提交。
- **无成交不等于所有统计不变**：正常 102 不新增量额；若 `T` 另行推进，滚动窗口仍可淘汰成员。累计贡献、窗口值与本批值必须分开解释。
- **正确性有适用边界**：这里争取的是可信输入与明确恢复协议下的投影一致性，不承诺端到端 exactly-once 或零丢失。覆盖证据缺失时必须暴露缺段、陈旧或不可用状态。

### 手工反例收束

以下是两个互不叠加的独立反例，仅跟踪 101 对成交额的增量 `ΔQ`，起点 `ΔQ=0`，不假设更早历史统计为零。

1. **去重先落、累计未落**：本地先持久化 T101-1、T101-2 的“已处理”标记，尚未持久化 15015 就崩溃，源游标仍为 100。重放 101 时两笔因标记被跳过，最终 `ΔQ=0`，漏掉 15015。源批能重复投递，并不能修好这组不一致状态。
2. **累计先落、去重丢失**：本地先持久化 `ΔQ=15015`，去重标记和源游标尚未持久化就崩溃。重放 101 又增加 15015，最终 `ΔQ=30030`。盘口绝对量即使完全正确，也掩盖不了成交额双算。

正确边界只有一致的两端：退到完整 C100，同时恢复其去重、窗口、累计和游标，再整批重放 101，得到一次 `15015 USDT、0.25 BTC` 的贡献；或者恢复完整 C101，对已核验同内容的重复 101 不再增加贡献。正常 102 只新增卖 60200=0.30，不再贡献成交额。无论选哪一端，源中已经提交的两笔成交都不重做，也不因行情崩溃而撤销。
