# 大问题 10：客户端断线后怎样续传，并恢复一份可信的本地盘口？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| sourceSeq / depthSeq / tradeSeq | 源批次、深度发布帧和逐笔成交各自的位置 | 本文快照深度号 500 覆盖源 100，两类计数不相等，逐笔恢复也独立。 |
| streamID / epoch / generation | 发布频道、不可混接的历史和本地订阅尝试代次 | 旧异步结果须按 generation 拒绝；服务端 leaderTerm 不能替代这些身份。 |
| CATCHING_UP / GAP / STALE | 追赶中、帧缺口和数据过旧 | 连接建好不等于 LIVE，旧簿可灰显但不能继续冒充实时。 |
| 快照锚点 S / 订阅屏障 | 完整视图的发布切点，以及先接住后继更新的交接 | 先缓冲再取一致快照，从 S+1 接续；投影最新内容不能贴旧 S。 |
| BigInt / 定点数 / 数值排序 | 精确大整数、整数比例表示和按实际数值比较 | 十进制字符串不能先过 Number，也不能按字典序排价位或比较序号。 |
| 绝对量 / 整帧提交 | 设置价位最终量，以及全部变化一起成为可读版本 | 零量删除、非零覆盖，验证完成才同时推进游标；异步任务不能暴露半帧。 |
| received / applied / 持久版本 | 已收到、已完整应用，以及簿和身份游标一起保存 | 续传只依据对应本地簿的应用位置；只留游标、丢簿时必须取快照。 |
| prevDepthSeq / 同号摘要 | 帧的前驱位置，以及识别同内容重复的依据 | 重复可忽略，跳帧须停下补齐；绝对量不能消除漏删除的后果。 |
| 续传尾 H / 保留范围 | 恢复时捕获的已提交尾部，以及仍可重放的历史 | 先协调缓冲，再重放到 H 并接实时；过期改走快照，不直接跳最新帧。 |
| checksum / 同版本比较 | 内容摘要，以及在同身份同序号同视图下核对 | 摘要相等只证明双方内容相同，不证明源事实没有遗漏。 |
| 新鲜度 / 源覆盖健康 | 数据距可用时点的距离，以及服务端对事实完整性的声明 | 重复帧或 Pong 不刷新业务进度，深度健康也不证明逐笔及账户完成。 |

## 把整篇文章压缩成一个故事

小林的浏览器从深度快照 500 起步，它覆盖的是源水位 100。客户端先建立订阅缓冲，再安装同版快照，精确解析整数字符串，完整应用帧 501：删除卖 60000、设置卖 60100 为 5 lots，最后才推进 applied 游标。服务器虽已写出 502，浏览器尚未提交就断线，因此重连报告的是 501，而不是最后收到的编号。服务端先协调实时缓冲和已提交尾部，再重放 502 及后续，客户端依旧逐帧检查前驱、去重、整帧提交。若只保存过 501 游标却丢了对应本地簿，就不能从 502 凭空补出完整盘口；若历史已经过期，也必须重新取快照。当前簿恢复成功不代表漏掉的逐笔历史也补齐。小林再次同步时，旧 Worker 或旧快照响应按 generation 被挡在最终提交入口，不能回滚新簿。摘要只和同身份同切点服务端版本比较，还要另看源健康和新鲜度。最终帧连续、摘要相同也不能替服务端源缺口背书，换 epoch 或 Pong 正常都不是“拥有可信实时盘口”的充分条件。

**流程位置：** 已提交行情发布记录 → 网关订阅屏障 → 客户端安装快照、应用增量 → 本地盘口与页面展示。

**核心机制：** 用订阅状态机约束可见性，以快照锚点衔接连续增量；只确认整帧应用后的游标，通过订阅代次、校验和与新鲜度区分“收到数据”和“拥有可信行情”。

**简短前提：** 沿用 BTC/USDT 托管现货 CEX 完整 L2，价格与数量分别使用 `priceTicks`、`qtyLots`，`tick=0.01 USDT/BTC`、`lot=0.01 BTC`。源快照在 `sourceSeq=100`，批次 101 扫掉卖 60000，并使卖 60100 剩余 0.05；批次 102 仅新增卖 60200 的 0.30。为说明客户端发布游标，本文假设该深度视图在源水位 100 的已提交快照锚点为 `depthSeq=500`，随后帧 501 覆盖源批次 101，帧 502 覆盖源批次 102；这不是两类序号相等的约定。各异常是独立变体，不累计改变正常案例。

## 第 1 层：连接建立以后，为什么还不能直接展示 LIVE？

**面试官：** WebSocket 已经连上，而且开始收到 BTC/USDT 消息了，客户端为什么还要有恢复状态机？

**面试者：** 连接只证明传输通道存在，不能证明本地簿完整。我会先从 DISCONNECTED 进入订阅与缓冲阶段，安装一致快照后进入 CATCHING_UP，只有增量连续且数据健康才转 LIVE。发现缺口进入 GAP，数据失去新鲜度则标 STALE；无法补齐时进入 RESYNC_REQUIRED。旧簿可以灰显，但不能继续冒充实时版本。状态同时绑定市场、视图规则和 `streamID/epoch`，深度游标是 `depthSeq`，逐笔游标另用 `tradeSeq`；`sourceLogID/sourceSeq` 只描述权威源覆盖，不能拿来替代客户端游标。`leaderTerm` 属于服务端隔离资源，不是客户端订阅世代。后续恢复只相信已完整应用的游标，而不是最后收到的消息编号。

## 第 2 层：进入缓冲阶段时，快照请求与订阅谁先发生？

**面试官：** 你说安装快照前先缓冲。如果先请求源水位 100 的快照，再订阅增量，具体会漏在哪里？

**面试者：** 快照读取到 100 后、订阅生效前，批次 101 可能已经发布；安装快照以后就永远少一次扫单。因此应先建立网关订阅屏障，让该订阅后续帧进入有界缓冲，再读取同一 `streamID/epoch` 的已提交快照。快照声明 `depthSeq=S=500`、`sourceTo=100`，安装后丢弃缓冲中不晚于 S 的帧，要求后继帧从 501 连续衔接；501 应明确以前序 500 为基础。快照必须来自发布已提交版本，不能将投影已到 101 的内容硬贴在锚点 500 上。若读取快照期间缓冲溢出，或者首个保留帧已无法衔接 S，当前尝试失效，重新建立屏障；不能直接跳到缓冲尾部。

## 第 3 层：屏障对齐了，为什么解析快照仍可能制造错簿？

**面试官：** 现在快照和帧 501 能衔接，但浏览器把所有 JSON 数字都转为 Number，本地重建还有什么风险？

**面试者：** 屏障只能保证版本关系，不能挽救数值被解析时改写。协议应将任意 64 位序号、价格整数与数量整数输出为十进制字符串，客户端校验格式、范围和精度版本后，用 BigInt 或明确的定点库处理，不先转 Number 再补救。60000 是 6000000 ticks，0.10 是 10 lots；两者乘积一个单位为 0.0001 USDT，不能把整数乘积直接显示成 USDT。价位索引按数值比较，不按字符串字典序排序，序号也不能在超过 `2^53-1` 后仍用 Number 递增。展示小数与内部计算分离，BigInt 输出 JSON 时重新编码为字符串。快照和增量的 `viewVersion`、精度元数据不兼容，就不安装这一版本。

## 第 4 层：数值正确后，怎样避免一帧只应用一半？

**面试官：** 整数表示已经一致。帧 501 同时删除卖 60000、把卖 60100 改成 5 lots，能否每改一个价位就刷新页面并保存游标？

**面试者：** 不行，否则页面或异步读者会看到同一帧的中间态。我先检查身份、前序、全部价位键与取值，再在私有候选版本中应用所有最终绝对量：零量删除，非零覆盖，随后检查最终簿不变量、计算 BBO，一次替换可读版本，同时将已应用游标推进到 501。快照安装也遵循整版本替换，不能边清旧簿边让页面读取。JS 单线程不自动保证跨异步任务的原子提交，渲染、Worker 回包和持久化都需围绕版本边界组织。若保存离线簿，价位、身份、精度和游标必须原子保存为一份版本；若无法做到，重启后作废缓存重新同步，不能凭单独保存的 501 跳过尚未落盘的变化。

## 第 5 层：整帧提交之后，重复帧和缺口分别怎么处理？

**面试官：** 本地已经原子应用到 501。如果再次收到 501，或者下一条直接是 503，为什么不能都当作“绝对量覆盖”继续处理？

**面试者：** 同身份的 501 若与已接受内容一致，只忽略，不重新提交版本或触发业务回调；逐笔流的重复另按自身游标处理，不能从深度帧累计成交。在保留摘要的范围内发现相同序号内容冲突，要隔离并重同步，不能当普通重试。503 则是另一种独立异常：预期 502，却收到 `prevDepthSeq=502` 的后继帧，必须停在 501，标 GAP，并有界缓冲或从已应用游标补取，不能提前覆盖。绝对量重复写入通常不会多扣盘口，但遗漏的删除仍可能留下幽灵价位。合并深度帧可以覆盖多个连续源批次，客户端不能要求 `sourceSeq` 每次只加一；应核对发布序列及其声明的覆盖关系。逐笔成交独立检查 `tradeSeq`，稳定 `tradeID` 不替代交付连续性。

## 第 6 层：断线续传应报告收到的序号，还是应用的序号？

**面试官：** 沿用刚才“从已应用游标补取”的规则，换成独立的断线场景：服务器已写出 502，客户端只提交到 501，重连时该从哪里开始？

**面试者：** 从本地确实拥有的 `streamID/epoch/depthSeq=501` 开始，不能用 socket 收到 502、服务器写成功或尚未提交的解析任务作为完成凭据。服务器校验续传范围后，先为新连接登记实时缓冲，在与缓冲边界协调的位置捕获已提交日志尾 H，重放 502 至 H，再裁剪重复并连续交付 H 之后的实时帧。客户端仍按整帧提交推进游标，重放与实时交接处的重复按同一规则抑制。逐笔流提交自己的应用游标，不能因为深度到 502 就声称两笔成交已展示。若客户端只持久化游标而丢失对应本地簿，501 已不具备恢复意义，应取快照，不能要求服务器从 502 开始替它补出整个盘口。

## 第 7 层：服务器日志已经过期，续传失败怎样降级？

**面试官：** 你要求服务器从 502 重放。作为独立变体，如果这个位置已经超出保留范围，能否直接发送最新帧让客户端继续？

**面试者：** 不能，最新帧只包含变更键，不负责删除所有已错过的旧档位。服务器应明确返回续传过期或 RESYNC_REQUIRED，客户端终止旧恢复尝试，重新执行先缓冲、取已提交快照、从 S 后连续追赶的流程；清楚标明旧视图暂不可实时使用。同一 epoch 下仅因保留窗口缩短，也可以重新取快照，不必把每次过期都解释成发布历史换代。盘口快照能恢复当前 L2，却不能补回错过的逐笔成交；产品若承诺完整逐笔历史，就要从可靠历史接口补齐并按稳定身份衔接，否则明确历史不完整，不能用最新价伪装无损交付。滚动指标同样取可信指标状态，不能从一份当前盘口推导过去成交额。

## 第 8 层：重新取快照时，怎样拒绝上一次订阅的迟到回包？

**面试官：** 过期后你重新订阅并取快照，但旧请求的快照更晚返回。两次请求恰好还是同一 streamID 和 epoch，怎么避免旧快照覆盖新簿？

**面试者：** 客户端每次订阅或重同步都递增本地 `generation`，把请求、连接回调、缓冲队列和异步解析任务绑定到这个代次。回包进入处理和最终提交前都核对当前代次，并结合服务端订阅标识、`streamID/epoch` 与视图规则；不是当前代次的结果直接丢弃，不能仅比较市场名或 epoch。旧 HTTP 请求即使取消失败，或旧 Worker 已经开始计算，也没有权提交到新代次。新一代安装快照后，只消费属于自身屏障的缓冲；旧一代迟到的控制消息也不能把新状态改回 GAP。`generation` 隔离本地订阅尝试，`epoch` 隔离发布历史，二者都不能拿 `leaderTerm` 替代。

## 第 9 层：拒绝旧回包后，如何证明本地簿正确且仍然新鲜？

**面试官：** generation 已防止串回包，序号也连续。这足以标 LIVE 吗，还是还要校验和与新鲜度判断？

**面试者：** 序号连续证明没有跳过已编号的帧，不证明解析和更新没有出错。我按协议约定的方向、数值排序、整数编码及校验范围生成摘要，只和相同 `streamID/epoch/depthSeq`、相同视图规则的服务端摘要比较；不能拿 501 的本地簿对比 502 的最新摘要。摘要不符就冻结实时标记并重同步。新鲜度另看服务端声明的源覆盖与健康状态、发布进展、接收后的单调时钟耗时和产品约定预算，不能用 Ping/Pong 代替。市场安静时没有新成交不等于源停摆，应结合可信源进度与健康信号判断；收到重复帧也不能不断刷新“数据刚更新”。深度、逐笔、ticker 各自报告水位与新鲜度，不能相互冒领完成。

## 第 10 层：校验通过的新 epoch，能否掩盖服务端源缺口？

**面试官：** 你已经把校验与新鲜度分开。独立地假设上游从源 100 直接跳到 103，却换 epoch 发来一份摘要正确的“最新快照”，客户端能据此恢复 LIVE 吗？

**面试者：** 不能。摘要只能证明双方拥有同一份内容，无法证明这份内容完整吸收了权威事实；换 epoch 只切换发布命名空间，不修补缺失的 101、102。服务端必须从可信源快照与连续日志证明投影覆盖，未完成时暴露 GAP、STALE 或不可用；客户端核对这一契约，但不假装自己能仅凭公开 L2 独立验证全部撮合事实。回到正常案例，快照 500 安装后，501 应删除卖 60000、保留卖 60100 的 5 lots，502 再加入卖 60200 的 30 lots；源健康、身份一致、衔接连续、摘要吻合且未失去新鲜度，才允许这一订阅转 LIVE。两笔成交是否已展示按逐笔通道判断，行情可见更不代表账户结转已经完成。

### 机制收束

先把一次订阅绑定到独立 generation，再用发布身份与快照锚点建立起点；每帧完成校验、整帧更新和游标提交后，才获得新的恢复位置。断线只重放尚未应用的发布记录，续传过期则显式切回快照恢复，而不是猜测丢失内容。校验和约束同版本内容，新鲜度约束当前可用性，两者都不能替代源连续性的服务端保证。

### 易错边界

`sourceLogID/sourceSeq`、`streamID/epoch/depthSeq`、`streamID/epoch/tradeSeq`、客户端 generation 与服务端 `leaderTerm` 各有作用域。服务器写出不等于客户端应用，客户端应用不等于已持久化；是否支持跨浏览器重启续传，要看本地版本是否一致保存。完整 L2 与 Top-N 的快照、差分及摘要范围不能混用，也不能由深度恢复成功推断逐笔历史已完整。

### 手工反例收束

客户端停在快照 500，卖 60000 还有 10 lots。它漏掉 501，只把 502 的“卖 60200=30 lots”覆盖进去；所有数量都非负，最新连接也正常，但旧卖档仍在，卖一错误地停在 60000。这个反例说明绝对量不等于无缺口。同样，即使新订阅已经正确应用到 502，只要允许旧 generation 的快照 500 迟到后重新安装，盘口仍会回退；必须在最终提交入口拒绝旧代次，而不只在发请求时取消旧连接。
