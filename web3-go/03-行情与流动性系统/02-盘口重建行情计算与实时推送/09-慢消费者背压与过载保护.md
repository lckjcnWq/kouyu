# 大问题 9：慢客户端和流量峰值怎样保护系统？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 背压 / 非阻塞投递 | 下游来不及处理的压力，以及不原地等它的入队方式 | 慢连接局部失败，公共投影不能持锁等 socket；入队失败必须处理。 |
| 有界队列 / 在途帧 | 有资源上限的积压区，以及已出队但尚未写完的数据 | 条数、字节、年龄、单帧大小一起管，出队不等于占用已释放。 |
| 逻辑字节 / 物理内存 | 每连接应承担的帧大小，以及进程真正留住的对象容量 | 共享编码省复制，但慢客引用仍能钉住旧帧和缓冲。 |
| 高水位 / hard limit / deadline | 提前退出阈值、不可突破上限和写入截止时间 | 失效后停止追加；控制通知写不出时要断连，不无限等告警送达。 |
| RESYNC_REQUIRED / epoch | 当前订阅必须恢复的状态，以及公共发布历史身份 | 单连接失效不改变公共 epoch，队列清空也不能让失效订阅自动复活。 |
| 发布前聚合 / 已提交帧 | 尚可按规则合并的变化，以及内容身份已固定的记录 | 网关不能删中间深度帧后沿用原序号；合并须保留变更键并集和删除。 |
| latest-state ticker / 无损逐笔 | 只承诺最新完整状态的指标流，以及每笔都保留的成交流 | 前者满足契约才可覆盖未写旧值，后者不能只留最后成交。 |
| 扇出游标 / 公平轮转 | 一帧分发到哪里，以及跨热点分配工作预算 | 可分批调度订阅者，但同订阅的前后帧不能越序。 |
| backlog / 源日志保留 | 已投影未发布的积压，以及可靠事实还能取多久 | 暂停消费须留足恢复区间；新投影检查点不能代替未交付的历史成交。 |
| 恢复准入 / 退避抖动 | 限量接收重建任务，以及错开重试时刻 | 防止断连后形成快照风暴；无额度明确拒绝，不建立无界等待。 |
| applied 游标 / 通道覆盖进度 | 客户端已完整应用的位置，以及各流已处理的事实范围 | 深度、逐笔、ticker 分开看；Pong 和服务器写成功都不证明应用新鲜。 |

## 把整篇文章压缩成一个故事

行情高峰里，小孟的手机长期写不动，网关没有让公共投影等他，而是非阻塞投递到独立队列。预算不仅数消息，还算字节、最老年龄、单帧和正在写的帧；虽然大家共享编码，小孟挂住的旧对象仍占物理内存。达到高水位，订阅明确失效并停止追加；通知写不出或 deadline 到期就关闭底层连接，回收引用，不能再开协程抢写。运维想只保留最后消息，工程师指出已提交深度不能这样改：漏掉 101 的删除，即使后来收到 102 仍会残留卖 60000；两笔逐笔也不能只剩后一笔。合法合并只能在发布前按并集保末值，完整替换型 ticker 才有另外的覆盖规则。热点扇出分批轮转，公共交接也满时在完整批次边界暂停消费，依靠可靠源日志追赶，不把内存无限撑大。大量用户回来还须恢复准入、共享快照和退避，历史过期则明示不能续传。最后队列归零、Pong 正常都不足以恢复 LIVE；必须逐订阅完成连续恢复，核对应用进度与新鲜度，不能借换 epoch 或深度恢复掩盖缺失成交。

**流程位置与核心机制：** 覆盖公共投影、发布交接、网关扇出、连接写出到客户端恢复，重点解释背压如何在有界资源内转化为明确失效，而不阻塞公共行情或悄悄改变通道语义。

前提：沿用总览的 BTC/USDT 托管现货订单簿、价格时间优先、Maker 价成交与零手续费，`tick=0.01 USDT/BTC`、`lot=0.01 BTC`。行情只消费已提交的 `ResultBatch`，不改变撮合和资产事实；以下均为教学设计，不代表生产经历或实测容量。

贯穿案例：从源快照 `sourceSeq=100` 出发，B1 买入 `0.25 BTC @ 60100`；批次 `101` 产生 `T101-1：0.10 BTC @ 60000`、`T101-2：0.15 BTC @ 60100`，删除卖 60000，卖 60100 剩余 0.05。正常批次 `102` 仅新增卖 `60200=0.30 BTC`，没有成交。后文异常均为独立变体，不累计改写正常路径；`sourceSeq`、`depthSeq` 与 `epoch` 沿用总览各自的身份和连续性契约。

## 第 1 层：慢连接为什么不能反向堵住公共投影

**面试官：** 同一份 BTC/USDT 行情要推给许多客户端，其中一个连接长期写不动，怎样避免它拖住公共投影和其他订阅者？

**面试者：** 我会把公共状态推进与连接交付拆成不同的完成边界。单交易对写者校验并整批应用已提交结果，生成同水位不可变视图，只向有界发布交接区移交，不在投影循环里等待 socket，也不持公共状态锁遍历连接。网关再把已提交帧引用投递到独立连接队列，入队采用带结果的非阻塞操作；不能入队就进入该订阅的失效流程，而不是等待慢客户端腾位置，更不是忽略失败。这样，批次 101 的删除价位和两笔成交能继续成为公共行情，不会因某个用户的网络状况撤回。连接自己的积压由连接处理，公共交接自身过载则按独立预算暂停行情消费，不能把它变成等待某个连接恢复。这里保护的是公共投影与分发隔离，不承诺所有客户端同时看见同一版本。

## 第 2 层：队列有界为什么不能只限制消息条数

**面试官：** 你说连接独立使用有界队列，但深度帧大小不一，而且很多连接共享不可变帧；只限制队列条数，真的能限制内存和延迟吗？

**面试者：** 不能。我会同时约束待交付条数、字节数、最老待交付项年龄和单帧大小，并把正在写出的帧纳入占用，避免出队后预算就凭空消失。条数控制管理开销，字节数控制积压体积，年龄限制数据落后时间，单帧上限防止一次大帧击穿预算；年龄还需要独立定时检查，不能只在新帧入队时判断。连接按引用帧完整编码大小记逻辑字节，进程另按唯一帧对象及底层缓冲实际保留容量记物理内存，序列化、压缩缓冲也要有界。共享帧只是减少复制，慢连接仍可能钉住大量旧对象，所以还要限制共享帧总保留量和保留时间。超过单帧上限时拒绝不兼容的订阅或使用事先约定的分片协议，不能临时拆改已提交深度帧。

## 第 3 层：高水位之后怎样显式失效并结束卡住的写入

**面试官：** 你把最老年龄和共享保留量也算进预算了；如果唯一写协程已经卡住，队列达到高水位，但控制消息同样发不出去，怎样真正收回资源？

**面试者：** 对要求连续交付的订阅，我会在高水位触发时原子切换为 `RESYNC_REQUIRED`，停止接收新行情，不让停止入队后的旧队尾继续冒充 LIVE；高水位是提前退出的保护阈值，硬上限 `hard limit` 则是绝不能突破的资源边界。可以预留受限的控制帧空间，但通知并非必达：触及硬上限、年龄超限或无法及时通知，就关闭连接。每个连接只有一个写协程，数据和控制写入由它串行完成，每次写设置不可无限续期的 deadline；管理方只发取消信号、必要时关闭底层连接来打断阻塞，不另起协程抢写。退出时幂等注销订阅、释放队列和在途帧引用、回收字节预算并停止相关定时任务。没有收到错误帧的客户端，也必须把断线视为需要按游标核对，而不能默认期间没有漏帧；连接失效本身不改变公共发布 `epoch`。

## 第 4 层：哪些通道可以覆盖，哪些帧绝不能事后合并

**面试官：** 你选择提前失效，但峰值可能很短；能不能先把队列里的旧消息覆盖掉，让深度、ticker 和逐笔成交都只保留最新一条？

**面试者：** 不能用一种覆盖策略处理所有通道。深度一旦提交了固定的 `streamID + epoch + depthSeq` 及帧内容，网关就不能删除中间帧或现场合并后仍沿用原序号；绝对量也不能抵消漏掉变更键的错误。允许的合并应发生在发布提交之前：若把正常批次 101、102 聚合为一帧，必须取两个批次变更价位的并集，保留卖 60000 的零量删除、卖 60100 的 0.05 和卖 60200 的 0.30，声明连续源覆盖 `sourceFrom=101、sourceTo=102`，再分配发布序号，不能只取最后一批。网关若提供独立派生深度流，必须另设 `streamID`，定义自身序号、覆盖范围和快照契约，不能悄悄改原流。ticker 只有明确采用 latest-state 协议、承诺用户不需要每个中间点，且新载荷完整替代旧状态时，才可覆盖尚未写出的旧值；部分写出的帧不能改。逐笔则必须保留两笔独立事件，`T101-1`、`T101-2` 各有稳定 `tradeID` 和独立递增 `tradeSeq`，不能静默丢前者只留后者；无损交付赶不上时应明确失败并按历史恢复。

## 第 5 层：不改帧的前提下怎样隔离热点扇出

**面试官：** 你把深度合并限制在发布前，网关不能靠改帧消化压力；如果热门交易对的订阅扫描和入队已经占满 CPU，即使连接都不算慢，怎样保护其他行情？

**面试者：** 我会让发布器只向有界网关分片交接一次不可变帧，扇出由分片自己的调度循环完成，不让发布器同步等全部订阅者。每轮只处理受限的订阅批次并保存扇出游标，热点队列与其他交易对按配额轮转，同一订阅必须先处理前帧再处理后帧，不能因并行任务完成顺序不同而乱序。编码结果按协议版本共享，连接仍分别记账；准入同时限制单连接、租户和交易对的订阅规模与出站字节，不能让创建更多连接绕过总额。分片积压也受条数、字节、年龄和共享内存预算约束，耗尽时明确失效受影响的落后订阅，不让最慢分片反向阻塞其他分片。限额依据实际扇出工作量和资源余量调整，不编造承载人数；即使拒绝新订阅，也不能偷偷删除已有深度流里的已提交帧。

## 第 6 层：投影到发布的热点积压怎样有界且可恢复

**面试官：** 你能隔离热点扇出，但若上游持续产生结果，连投影到发布的交接区也满了，继续堆内存或暂停消费各有什么边界？

**面试者：** 我会在完整批次边界停止领取后续结果，把未消费事实留在可靠源日志，而不是无限增加内存队列。投影应用水位与发布提交水位分别记录，已投影但未发布的 backlog 同样限制字节、条数和年龄；恢复时根据已提交发布锚点与可靠源日志重建待发布内容，源日志保留必须覆盖最早未发布事实，不能仅凭较新的投影检查点就跳过中间逐笔。已提交发布记录复用原身份和内容，快照也只能锚定已提交 `depthSeq`，不能给旧发布序号贴上最新投影内容。发布前可按上一层规则聚合深度，但不能删成交或越过源缺口：期望 101 却先见 103 的独立变体，必须停在可信水位并标 GAP。若保留窗口耗尽，深度从可信一致快照恢复，逐笔则另补可靠历史或明确声明不可续传；不能假装 backlog 已清空。无法证明发布历史连续时换 `epoch` 并重同步，也不能用换代掩盖源缺失。行情落后不影响已经提交的撮合事实，更不能撤销成交或要求账户释放其应承担的义务。

## 第 7 层：重连和重同步为什么还要有恢复准入

**面试官：** 你把超限订阅转为重同步，公共积压过期也会触发恢复；如果大量客户端同时回来取快照、补逐笔，怎样避免保护动作本身压垮系统？

**面试者：** 恢复要经过独立准入，不能让每次重连都直接启动快照构建。我会限制并发恢复任务、快照生成与编码内存、快照出站字节及历史重放速率，为已在线的实时流保留资源；同一视图版本和已提交锚点可复用不可变快照，不按连接重复扫描盘口。没有额度就明确拒绝或给出重试提示，不建立无界等待队列；客户端使用有上限的指数退避加随机抖动，服务端仍独立执行配额，不能依赖客户端自觉。深度优先核对 `streamID + epoch + depthSeq` 是否仍可续传，否则先建立有界订阅缓冲，再取一致快照并衔接后续序列；缓冲再次超限就中止本次恢复，而非继续扩容。逐笔按稳定身份从可靠历史补取，不能拿深度快照代替成交记录。恢复任务取消或连接退出后立即归还预算，避免断线重试留下重复任务。

## 第 8 层：队列回落和心跳正常为什么仍不能宣布健康

**面试官：** 你通过恢复准入把队列压下来了，客户端也重新拿到快照并正常回 Pong；如果它的应用线程仍落后，怎样判断真的恢复健康，又能承诺什么交付语义？

**面试者：** 我会分别观察源提交、投影应用、各通道发布、网关写出和客户端自报应用的位置，以及生成到应用确认的延迟，不用心跳替代业务进度。深度比较同一 `streamID + epoch` 内的已发布与已应用 `depthSeq` 及其源覆盖；逐笔比较自身 `tradeSeq` 和稳定成交身份；latest-state ticker 比较最新状态版本与计算时点，不能拿它的水位证明深度已交付。正常 102 没有成交，逐笔最新仍是 `T101-2` 并不异常；需要证明源已推进时，应使用约定的通道覆盖进度，不能伪造新成交或递增假的 `tradeSeq`。只有各订阅按自身契约完成恢复、无未解决缺口，队列降至低水位且应用延迟在声明阈值内持续稳定，才转 LIVE；已失效订阅不能仅因队列清空就直接复活。客户端确认也只是自报已应用，不证明页面渲染或账务完成。写 socket 与客户端应用不在共同事务里，断线可能导致重放重复，所以只承诺游标校验、重复抑制与按保留范围恢复，不宣称端到端 exactly once。

**机制：** 按资源预算隔离积压，按通道契约处理超限，以显式失效、可靠重放和受限恢复闭合链路。

**易错边界：** 共享不等于不占内存；绝对量不等于任意丢帧；连接重建不等于发布换代；socket 写出、应用确认和数据新鲜是不同状态。

**反例：** 队列只留下正常 102 的卖 60200 更新，客户端仍可能保留本应删除的卖 60000；逐笔只留 `T101-2`，成交量就只剩 0.15 而非 0.25。即使队列归零、心跳正常，也不能把这种状态标为健康。
