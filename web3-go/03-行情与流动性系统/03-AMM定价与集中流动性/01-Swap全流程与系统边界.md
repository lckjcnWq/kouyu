# 大问题 1：一笔集中流动性 Swap 怎样走完整条链路，谁对价格、付款和最终结果负责？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| Swap / exact-input | 按规则拿一种币换另一种币；先给输入预算 | 本例最多用1500 T1买T0，触及价格限制可以少花，不代表一定花完 |
| P / s | 每个T0值多少T1，以及这个价格的平方根 | P=T1/T0，s=√P；T1输入使价格上升，两币均18位精度 |
| tick / 活跃L | 价格网格位置，以及当前这段价格能用的深度 | tick240处A退出、B进入，L从100000变50000，不是池资产余额 |
| 毛输入 / 净输入 | 用户付的钱，以及扣费后真正推动价格的钱 | 0.3%输入费、协议不分成；实数主例1500=1495.5净额+4.5费用，链上逐步整数舍入 |
| 报价快照 / blockHash | 给一次估算贴上所用链上版本的标签 | Go读取确定区块的状态进行模拟，不锁价、不预留池流动性 |
| minOut / 价格限制 / deadline | 最少收多少、价格最多走到哪、最晚何时执行 | 本例1470 T0、tick420和有效期限各管一件事，不能互相替代 |
| allowance / approve | 允许某合约花币，以及设置这份许可的操作 | 不是冻结资金；独立授权已成功，不会因后来的Swap失败而撤销 |
| callback / 正delta | 池回头要求调用方补齐本次应付的输入币 | 路由验证合法池后支付T1，池核对余额增量，不能只信授权或转账返回值 |
| revert / 交易原子性 | 同一笔交易中的相关动作一起撤销 | 回调或minOut失败会撤销本次交换和转账，但不抹去gas支出或先前独立授权 |
| 回执 / 确认 / 重组 | 当前入块结果、可信进度，以及链分支更换 | status=1不等于最终不可逆；索引需撤销孤块上的交易及LP投影 |
| burn / collect | 减少头寸深度，以及真正把已记账资产领走 | LP本金构成、费用权益、待领取额分别记录，减仓不等于钱包到账 |

## 把整篇文章压缩成一个故事

小林想用最多1500 T1买T0，后端按同一blockHash读取池状态。两币均18位精度、输入费0.3%、协议不分成；报价只是估算，小林设置最少收1470 T0、价格不越tick420及执行期限。链上轮到他时重新计算：先用A的L100000，到tick240后切为B的L50000，连续模型预计输出约1472.669192 T0，链上还须逐步整数舍入。池先转出T0，再由合法回调收实际T1，付款或最小输出检查失败就同笔回滚，不能留下第一段成交。若把价格限制改到240，仍要求1470就失败；改为1190才可能少用预算成功，未花的钱是否需退款取决于付款路径。交易入块后索引突然崩溃，工程师按原交易和nonce核实、重扫，不让小林换新nonce盲目再买。后续若重组，交易页面、池状态、A/B本金与费用投影一起撤销重建；独立授权和已付gas不因Swap回滚消失，LP减仓也仍须领取才算到账。页面应把输入预算、实际消耗、输出和确认进度分开列明；报价服务只负责解释版本，路由落实保护，池与代币合约各自裁决执行和余额，不能互相越权。

[返回专题总览](README.md)

**流程位置与核心机制：**从用户兑换意图到链上执行、付款、确认与展示，建立端到端责任边界。本题解释各阶段怎样接起来；定价算法、回调安全、Go 快照与重组恢复分别在后续母题深入。

**必要前提：**沿用总览的单池 v3 风格基线：T1 买 T0、最多输入 1500 T1、minOut 为 1470 T0、价格限制 tick420；A/B 在 tick240 交接活跃流动性。这里没有链下托管账户或订单簿撮合。

## 第 1 层：从用户点兑换开始，完整流程是什么？

**面试官：**用户想拿 1500 T1 换 T0，请你从点击兑换讲到业务真正完成，不要只介绍池里的定价函数。

**面试者：**我会分为报价、用户授权与提交、链上执行结算、确认与投影四段。

先由 Go 服务读取一个确定区块版本的池状态，按 T1 输入方向逐段模拟，返回预计输出和对应的 blockHash。用户接受的不是“锁定成交价”，而是带 minOut、价格限制、deadline 等条件的兑换意图。余额与 allowance 不足时先补授权，然后钱包签名广播。

链上按交易实际执行前的状态计算输出，途中经过 tick240 就切换活跃 L；池转出 T0，通过回调收取应付 T1，核对余额，路由检查最小输出。任一关键检查失败，整笔交易中的兑换状态和代币转移回滚。

成功回执只说明本次交易在当前链上执行成功。Go 索引器还要按规范链同步事件与状态，页面展示实际消耗、输出和确认阶段；达到所在链的确认策略后才能给出相应完成承诺，重组则必须撤销原投影。

## 第 2 层：报价既然不是锁价，究竟由谁拥有真实状态？

**面试官：**你说报价只是模拟。报价服务、路由和池都在算价格，谁才有最终裁决权？

**面试者：**链上池在规范链的执行位置拥有权威价格、tick、活跃 L、费用和头寸状态。ERC-20 合约拥有余额和 allowance。Go 服务只是读取这些状态的带版本副本，不能因为给过报价就要求池保留流动性。

路由负责把用户条件落实为执行约束，例如 deadline 是否有效、输出是否达标、回调是否来自合法池。它可以让整笔兑换回滚，但不能在池外宣布另一份价格覆盖池的执行结果。

本例报价依据 tick0、L100000 的快照；如果另一笔交易先消耗流动性，轮到本交易时就必须用更新后的状态执行。没有“旧报价优先”的权利。索引数据库即便还停在旧区块，也只能说明展示滞后，不能改变成交事实。

## 第 3 层：权威池怎样把这 1500 T1 变成两段成交？

**面试官：**既然池裁决，请沿你的例子说明关键状态和金额怎样变化，不能只说调用 Swap。

**面试者：**起点 s 为 1，A 活跃，L 为 100000。先计算到 tick240 的 sqrt 价格 `s_b≈1.012071681663366439` 需要多少净输入：`100000(s_b-1)≈1207.168166 T1`。含 0.3% 费用需要约 1210.800568 T1，输出约 1192.769433 T0。

该步费用约 3.632402 T1 归跨界前的 A。随后在 tick240 加上净流动性变化 `-100000+50000=-50000`，活跃 L 变成 50000，再用余下约 289.199432 T1 毛输入在 B 段继续算。

最终总输出约 1472.669192 T0，s 约 1.017838318337，tick 为 353，活跃 L 为 50000；B 获得约 0.867598 T1 的费用。它低于 tick420 限制且输出大于 minOut，所以在连续数学模型中可以成功。链上需要按每步整数舍入重算，不能直接把展示小数当作精确转账额。

## 第 4 层：计算结果出来了，但用户不付款怎么办？

**面试官：**你刚才已经把池状态推进到了 tick353。如果回调扣不到用户的 T1，会不会留下已成交但未结算的缺口？

**面试者：**不会留下已提交的兑换缺口，前提是采用这里的同一笔 EVM 交易边界。池可以先更新内部状态、转出 T0，再回调调用方收 T1；这些仍是交易执行中的暂态，不是已独立提交的成交。

回调中路由应验证来源确实是该链、该工厂下预期的池，再按正 delta 支付应付金额。池比较输入代币的回调前后余额，要求至少增加应付数量；不足、transferFrom 失败或回调异常都会 revert，撤销本交易此前相关写入、转账和日志。

这里不需要引入交易所式预留账户来补洞。allowance 只是授权，余额可能在执行前被其他交易花掉；失败时回滚 Swap，独立完成过的 approve 不会跟着撤销，失败 gas 也不会返还为零。

## 第 5 层：付款成功，但最小输出检查失败呢？

**面试官：**假设池回调付款已经成功了，路由随后发现实际只收到 1460 T0。是不是只能接受坏价格再补偿？

**面试者：**不是。只要 minOut 在同笔交易内检查并且错误没有被吞掉，路由 revert 会把整个调用树中本次 Swap 的池状态、T1 支付、T0 输出及相关日志一起撤销。不能把池函数返回当作已经越过最终提交边界。

需要区别两种“部分”：多区间 Swap 的中间步骤不是独立可提交的部分成交；价格限制提前终止则可能得到一份使用部分输入的最终执行结果。但后者仍必须满足 minOut，失败就整笔撤销。

如果某产品把交换、事后检查分成两笔链上交易，那么原子性前提已改变，不能再声称后一次检查能回滚前一笔成交。本专题不采用这种设计。

## 第 6 层：限制提前停止时，没用掉的钱在哪里？

**面试官：**既然可以只使用部分输入，把价格限制改到 tick240，会怎样完成付款和展示？

**面试者：**从原始快照重新执行，池到 tick240 时停止，连续模型输出约 1192.769433 T0，只消耗约 1210.800568 T1，剩余约 289.199432 T1。如果仍用原 minOut1470，就必须整笔失败；如果明确把 minOut 改为1190，这个部分使用输入的变体可以成功。

钱包作为付款人的常见单跳路径只需要按实际正 delta 付款，未消耗预算原本就留在钱包，不存在池欠用户退款。如果先把整笔预算充值到路由，剩余金额留在路由，则需要明确退款或余额领取路径，不能以“池会退”为借口遗漏。

对外要同时展示预算、实际消耗、实际输出和未消耗额，不能显示“1500 全部兑换”。若产品要求全额花完，应增加同笔交易的实际输入约束，并说明那是更强的路由规则。

## 第 7 层：链上成功、索引失败，业务算什么状态？

**面试官：**这个部分使用的变体成功入块了，但 Go 服务在写数据库前崩溃。能让用户再点一次吗？

**面试者：**不能据此认定链上失败并让用户盲目重做。执行事实在规范链中，数据库失败只是投影没有跟上；新 nonce 的交易可能再次进行一次合法 Swap，不会被链下同一个报价 ID 自动拦住。

服务需要保留意图与交易关联，恢复后按原 txHash、发送者 nonce、回执和规范链区块核实。索引通过重扫区块恢复，事件去重和投影/游标同事务避免半写。广播超时或暂时查不到回执应显示“结果待确认”，而不是直接显示失败并释放某个不存在的链上预留。

如果交易处于未最终确认区块，要保留 provisional 状态与 blockHash。后续发现 parentHash 分叉时撤销孤块投影，重新判断原交易是否待打包、被替换、重新执行或最终失败，不能永久保留旧成功页面。

## 第 8 层：撤销成交投影时，LP 的本金与费用展示怎样一起恢复？

**面试官：**你说重组后撤销旧成功页面。这笔 Swap 已让 A 显示成单边 T1 并赚到费用，撤销时只改交易者页面够不够？

**面试者：**不够，交易者输出、池价格、活跃 L、LP 本金构成与费用权益都源自同一分支事实。若主例所在旧区块退出规范链，相关投影都要回到共同祖先，再按新分支重建；不能撤销用户成交，却继续用孤块的 tick353 和 A 的约3.632402 T1费用做收益展示。

若新分支到该处仍是原始条件，A 应恢复区间内双币本金、活跃L恢复100000；若新分支有其他操作，则必须按新状态计算，不能只对旧余额加减一个固定补偿数。LP 的减仓、领取也分别绑定各自交易和区块；burn 减少 L、collect 才转账的区别不能在恢复中丢掉，具体生命周期见07。

链下观察和投影可以撤销，已经基于候选成交发出的外部不可逆付款却不会被数据库回滚自动收回，因此本模型不在未达到相应确认策略时承诺此类副作用。完整闭环要求所有相关读模型指向同一规范分支，并分别说明执行、领取和确认进度，而不只是把一个成交布尔值改成失败。

## 本题收束

- **讲透的机制：**链上池裁决兑换，路由落实用户保护，同交易回调完成资金收付，链下只投影和追踪；LP 的减仓与领取另有完成条件。
- **最容易答错：**把报价当锁价，把 allowance 当冻结，把池返回当最终提交，把收到成功回执当最终性，把 burn 当已经到账。
- **反例检验：**从原始快照将 minOut 改为1473，池计算后甚至完成回调，路由仍应使整笔兑换回滚；独立 approve 仍有效、gas仍消耗。若答案说“保留第一段成交再补差价”，原子边界就讲错了。
