# 大问题 7：LP 从增仓、减仓到领取资产，头寸与资金究竟怎样变化？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| core position / owner+lower+upper | 池内按拥有者和上下界保存的一份头寸账 | 还受池地址隔离；不是直接以NFT tokenId记账，owner可能是管理器合约 |
| NFT / tokenId / 管理器 | 外围把头寸权益包装成的凭证及其编号 | 同池同区间多个NFT可对应一个聚合core头寸，不能把聚合资产全算给每张NFT |
| L / activeL | 自己头寸的深度，以及当前价格全部活跃深度 | A出区间仍有L100000，但不贡献当时activeL；L不是两币数量或市值 |
| s、a、b / x、y | 当前及上下界sqrt价格，以及T0/T1本金数量 | 区间内x=L(1/s-1/b)、y=L(s-a)；低于区间全T0，高于区间全T1，不含费用 |
| amountDesired / 最低数量保护 | 最多愿投入多少币，以及能接受的投入下限 | 外围按执行价算可支持的L，双币中短板约束L，报价配比不是执行承诺 |
| mint / mint callback | 增加L，以及池要求付清新增本金 | 更新状态后回调验来源和付款，池验余额增量；不足同交易撤销，授权不等于建仓 |
| feeGrowth / 检查点 | 公共费用增长及本头寸已结算的位置 | 增减L前先结旧L的费用，费用不会自动成为新增L |
| burn / decreaseLiquidity | 减少流动性并把返还本金记入待领账 | 返回amount0/1不代表已转账；区间外A全退不减少B当前activeL |
| tokensOwed / collect | 已记待领数量，以及实际扣账转币 | owed可同时含本金和费用；core collect不刷新增长，不能一概套到外围管理器 |
| burn(0) / NFT burn | 不减L的费用刷新，以及销毁NFT凭证 | 前者需core头寸有L；后者通常要L和欠款清空，与减仓不是同一动作 |
| blockHash / 未知结果重试 | 资产展示的状态版本，以及先核实再重发 | RPC超时不等于减仓失败；分两笔交易的领取失败不撤销先前减仓，重组可撤回投影 |

## 把整篇文章压缩成一个故事

LP阿敏给A区间[-240,240)增L100000，初始需约1192.769433 T0和同量T1。两币18位、T1/T0计价，输入交易费0.3%、协议不分成；这些是实数本金，链上仍按整数规则付款。管理器算L后，池更新边界和头寸，再回调收币，少付就同笔撤销。随后1500 T1买T0的交换把价格推过240，A本金全变成约2399.937600 T1，另赚约3.632402 T1费用；A不再活跃，却没有消失。阿敏全量减仓，旧L费用先结算，本金记入tokensOwed，钱包仍可能一分未增；collect才扣欠款转币，若只领一半，L为0也仍有剩余资产。后端在同一blockHash下分别显示未退本金、应计费用与待领额，不把管理器聚合余额重复算给每张NFT。减仓和领取若分两笔，后者失败不撤销前者；RPC超时先查原交易，不能盲目再减。core刷新、外围collect和销毁NFT各有条件，不能用一句“burn完已提现”抹平。若把减仓领取合并为同一交易，必要转账失败就一起撤销；若区块后来重组，还须按新分支重建权益。页面据真实转账确认到账，不把授权、头寸凭证或函数返回当作资产已经进入钱包。

[返回专题总览](README.md)

**流程位置与核心机制：** 覆盖 core 头寸、NFT 包装、mint 付款、burn 记账和 collect 转账，不把它们合称为“提现”。公共基线与单位见总览；本题沿用 A 的 [-240,240)、L=100000 和 B 的 [240,480)、L=50000，特别区分头寸 L 与池活跃 L。

```text
LP 选择区间与资产上限 → 计算可增加 L → mint 更新头寸及 tick
    → 回调付款并检查池余额 → 原子成功后确认头寸
交易累计费用 → 头寸更新结算费用 → burn 减少 L、本金记入欠款
    → collect 扣减欠款并转币 → 按链确认资产到账
付款、数量保护或授权失败 → 当前交易整体回滚
```

贯穿交换：用户最多付 1500 T1 买 T0，最低收 1470 T0，价格上限 tick420，deadline 由路由检查。交换越过 tick240，最终 tick353、s≈1.017838318336633561、P≈1.035994842274346199、activeL=50000。数值为连续实数手算，链上整数按步舍入，未作上链验证。

## 第 1 层：一个 LP 头寸究竟由什么标识？

**面试官：** LP 新建头寸后拿到 NFT，是不是池里也按 tokenId 保存资产？

**面试者：** 不是。core 在每个池自己的 positions 映射里，以 `keccak256(abi.encodePacked(owner, lower, upper))` 定位头寸，保存 liquidity、两种币的费用增长检查点和 tokensOwed。池地址提供映射隔离；只拿这个哈希跨池查询并不唯一。

使用 NonfungiblePositionManager 时，core owner 通常是管理器合约，不是 NFT 持有人；tokenId 是外围层的身份。相同池、相同上下界的多个 NFT，会聚合到管理器名下同一个 core 头寸，外围再按 NFT 记录各自 L、检查点和欠款。因此直接读 core 聚合余额，不能当成某个 NFT 的全部资产；NFT 转移改变控制权，也不是把池内流动性移动到另一个价格区间。

## 第 2 层：确定区间后，究竟需要交哪两种币？

**面试官：** 既然头寸按区间组织，为什么有人只交 T0，有人却要两种币？

**面试者：** 资产构成由当前价格相对区间的位置决定，不是任意选择。记 a=√P_lower、b=√P_upper，人类可读本金为：

- s≤a：x=L(1/a-1/b)，y=0，全为 T0。
- a<s<b：x=L(1/s-1/b)，y=L(s-a)。
- s≥b：x=0，y=L(b-a)，全为 T1。

x、y 分别是 T0、T1 数量，不包含待领费用。A 初始 a=1/1.0001^120、b=1.0001^120、s=1，因此 x=y≈1192.769433438381804424；B 的当前价格低于下界，只需 T0。L 不是两种币之和，更不是美元市值。上下界必须按 tickSpacing=60 对齐；恰在下界时 T1 本金为零，不代表头寸一定不活跃，活跃性还要按池保存的 tick 判断。

## 第 3 层：用户交的是资产上限，谁决定最终 L 和付款？

**面试官：** 两种币不能任意配比，用户填入 amountDesired 后，mint 怎么保证没有少付或多记流动性？

**面试者：** 外围根据执行时价格和资产上限计算 L；区间内分别由 T0、T1 算出可支持的 L，再取较小者，另一种币可能有未使用余额。不能把页面报价时的配比当作执行时保证，最低投入数量和 deadline 应在外围校验。

core mint 先更新头寸、边界及必要的活跃 L，算出应付数量，再调用调用者的 mint callback。回调需要验证来者是可信工厂对应的规范池，付款方再通过授权转入应付资产。池比较回调前后余额，要求增量至少等于应付值；不足即整笔回滚，先写的 L 不会无偿保留。增加 L 的应付量倾向向上取整、移除的返还量向下取整，不能用浮点配比替代链上整数运算。授权成功只代表允许转币，不代表头寸已经创建。

## 第 4 层：交换把 A 推出区间，它的头寸消失了吗？

**面试官：** 主例最后 activeL=50000，A 的 100000 是不是已经被烧掉，必须重新存币？

**面试者：** 没有。activeL 是当前价格上参与成交的总流动性，不等于所有头寸 liquidity 的总和。tick240 右跨时，A 的 -100000 与 B 的 +50000 共同令活跃 L 从 100000 变为 50000；A 的 positions.liquidity 仍为 100000。

A 只是全部本金变成 T1：`100000×(b-a)≈2399.937599775025698687 T1`，T0 本金为零；此前承接第一段交换赚得约 3.632401704122298579 T1 费用。它在区间外不再赚后续交换费，但保留减仓和领取权利。价格回到区间时，原头寸会重新活跃，无需再次 mint。自动重入区间与主动调整上下界不是同一件事，后者通常需要退出旧区间再建立新头寸。

## 第 5 层：A 执行 burn 后，钱为什么还没到钱包？

**面试官：** 既然 A 仍有本金，我对它 burn 全部 100000 L，为什么余额可能完全没增加？

**面试者：** core burn 是减流动性与记账，不是立即转币。它先用旧 L 结算该头寸新增费用，再减少头寸 liquidity、更新上下界 tick；若当前处于区间内，还会减少池的活跃 L。退出本金被加入 tokensOwed，返回的 amount0/1 是本金数量，不代表已经到账，也不代表包含所有历史费用。

对已在区间外的 A 全部 burn，活跃 L 仍为 B 的 50000；A 的 L 变零，理论待领 T1 约为 2399.9376+3.6324，具体取决于既有检查点与整数舍入。tokensOwed 同时容纳退出本金和已结算费用，不能看到这个字段就全部当作手续费。通过 NFT 管理器调用 decreaseLiquidity 也主要是减仓和累计欠款，还受授权、最低数量与 deadline 约束，并不等价于把钱转到 NFT 持有人。

## 第 6 层：collect 能不能顺便算出全部新费用？

**面试官：** burn 会结算费用，那我不减仓只 collect，能否拿走截至当前的全部收益？

**面试者：** 必须区分 core 和包装层。core collect 只从已经记录的 tokensOwed 中按请求上限取较小值、扣账并转币，不刷新增长检查点。对仍有流动性的 core 头寸，常先调用 burn(lower,upper,0) 做 poke，再 collect。burn0 不减 L，也没有退出本金；若头寸 L 已为零，这种 poke 会因不存在可更新流动性而失败，但已有欠款仍可以领取。

NonfungiblePositionManager.collect 不只是原样转发：该 NFT 的 L>0 时会先 pool.burn(...,0)，读取聚合头寸的 inside 增长，再结算该 NFT 的分账后领取；L=0 时跳过刷新。因此“collect 永远不更新费用”和“collect 永远自动结算”都不准确，必须明确调用的合约层。管理器的 NFT burn 又是销毁凭证，通常要求 L 与欠款都清空，不能和 core burn 混为一谈。

## 第 7 层：减仓成功但领取失败，会不会丢钱？

**面试官：** 既然 decrease 和 collect 是两步，第二步 revert 后，第一步留下的状态怎样处理？

**面试者：** 看交易边界。通过同一原子交易把减仓和领取组合起来，若后面的转币或数量检查 revert，前面的减仓、费用结算也回滚；不会出现同一失败交易内 L 已减少但欠款没记的半成品。若分两笔交易，第一笔已经成功，则第二笔失败不撤销第一笔，欠款仍在，重新检查授权、收款地址和请求数量后可再次领取。

RPC 超时不是执行失败。后端需先按交易哈希、回执和规范链核实，再决定补发，而不是重新无条件发送相同 decreaseLiquidity；重复减仓会真的再减一次，或因余额不足失败。collect 成功后会扣欠款，不能重复领取同一余额，但“领取剩余欠款”也不等于用户意图层天然幂等。确认数和重组处理还决定何时可以把到账展示为业务终态。

## 第 8 层：怎样把头寸展示与资产核对做正确？

**面试官：** 有聚合头寸、未结算费用和分步交易，钱包页面应怎样避免把资产重复计算？

**面试者：** 应在同一 blockHash 下读取价格、tick、NFT L、费用检查点和欠款，不能仅凭相同高度混入不同分支。未退出的本金由当前 s 和该 NFT 的 L 计算；应计费用由 inside 差和旧检查点推导；已退出但未领取的本金已在欠款中，不能再按原 L 计算一次。core 与 NFT 的余额只能在各自层次核对，不能把聚合欠款加到每张 NFT。

本例先给 A burn 全量、再 collect 一半：头寸 L=0，但剩余欠款仍是资产；此时界面显示“头寸价值零，资产已全部领取”就是错误。展示还需保留块哈希及待确认状态，重组时撤回旧投影。以转账结果和欠款变化核对实际到账，允许明确的整数尘埃，不虚构所有 NFT 分账永远与聚合余额逐 wei 相等。

## 收束：讲透机制、易错边界、反例验证

- **讲透机制：** mint 先定 L 再回调验款；burn 减 L 并记欠款；collect 才实际转钱；NFT 管理器另有身份与分账层。
- **易错边界：** 出区间不等于头寸消失；core collect 不刷新费用；NFT decrease、collect、销毁凭证是三种不同动作。
- **反例验证：** A 出区间后全量 burn，池 activeL 应仍为 50000，A 的 L 为零但仍有 T1 欠款。若实现要求再次存币才能领取，或 burn 后直接把欠款清空，就破坏了资产权利。
