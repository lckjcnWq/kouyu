# 大问题 3：怎样正确处理平方根价格、代币精度和舍入，避免 Go 报价与合约结果不一致？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| 原子单位 / decimals | 合约记账的最小整数单位，以及小数位数 | 18位币的1个完整币为10^18原子单位；显示18位不等于float64有18位精度 |
| P_raw / P | 原子单位比例，以及人类读的币价 | P_raw=raw1/raw0，人类P=P_raw×10^(decimals0-decimals1)，币种顺序不能由界面随意调换 |
| S、Q / Q64.96 | 把平方根价格放大为整数保存 | S=sqrtPriceX96，Q=2^96，s_raw=S/Q；还原价格不能先整除再平方 |
| L / uint128 | 单段活跃流动性及其合约范围 | 等18位主例的人类L100000需放大10^18；不是池余额，也不能只放大金额不放大L |
| A、B / amount0、amount1 | 两个有序的编码sqrt价格，以及该段两币数量 | A<B时amount1=L(B-A)/Q，amount0=LQ(B-A)/(AB)；此处A/B不是LP姓名 |
| FullMath / 宽乘除 | 中间乘积很大时仍能正确乘完再除 | 最终结果放得下不代表中间不溢出；Go还须复刻目标算法顺序和拒绝条件 |
| 向上取整 / 向下取整 | 不够整单位时多收一格或少付一格 | 输入delta通常上取整、输出下取整；下一价格取整还要结合方向和exact-input/output |
| feePips / remaining | 百万分之几的费率，以及还可用的毛输入 | 本例feePips=3000；到目标与预算耗尽两类步骤按SwapMath分别计算费用 |
| 负tick / floor | 负价格网格编号，以及朝负无穷取整 | -1按spacing60压缩为-1，不是向零截断得到0；TWAP负平均tick也有类似边界 |
| feeGrowth / 模2^256 | 每单位L累计费用，以及固定宽度回绕规则 | 目标版本费用差值可能须模运算；big.Int负数不会自动变成uint256回绕结果 |
| 逐步差分 | 在相同输入状态上逐项对照目标算法 | 比较每步金额、S、tick、L和费用；实数手算及最终小数接近不等于整数兼容 |

## 把整篇文章压缩成一个故事

阿岚把T1买T0的报价搬到Go，主例两币均18位、输入费0.3%，先用float64显示18位，结果在tick240前差一个原子单位，却错误切进B区间。她改用整数：金额与人类L一起放大10^18，S按Q=2^96编码sqrt价格，输入和输出依合约逐步取整。随后接入token0为18位、token1为6位的变体，人类价格2000对应原子比例2×10^-9，若仍写2000就错了12个数量级。她继续核对宽乘除、uint160/uint128范围和费用分支：只剩1原子单位时，净额可能为0、全额成为费用，不能靠统一下取整制造输出；负tick压缩必须floor，费用增长回绕则按目标版本做模运算。最后列出同区块逐步差分计划，记录首个整数分叉而不是用小数容差掩盖。这样才具备可验证路径，文中的手算并不代表已经跑过合约测试或证明所有边界正确。她为每类数注明单位、位宽、符号、舍入和回绕规则，签名前也不再用显示小数倒推参数；遇到目标合约不接受的范围，后端同样拒绝，而不是因为大整数算得出就放行。

[返回专题总览](README.md)

**流程位置与核心机制：**负责从状态解码到每步金额计算的数值正确性。本题处理单位、Q64.96、整数宽度与舍入；同版本状态读取及 goroutine 所有权见11。

**必要前提：**沿用总览的价格方向、费率和区间。主例小数用于实数推演，不是链上精确结果；实际金额、L和中间数值必须采用目标合约所规定的整数尺度。

## 第 1 层：你会用什么数据表示价格和金额？

**面试官：**把前面的 AMM 公式移到 Go，直接用float64再保留18位小数可以吗？

**面试者：**不能作为精确报价或链上参数的依据。float64不能精确表示大部分十进制小数，整数超过其有效精度也会丢失末尾位；把显示格式设成18位并不能补回信息。一个原子单位的差异都可能改变是否跨tick、是否达到minOut。

我会将代币金额保存为原子单位整数，使用math/big.Int等整数工具计算；sqrt价格使用与合约一致的Q64.96编码，L按uint128语义检查范围。对外展示时才按decimals格式化，不再拿经过格式化的数倒推精确金额。

主例的人类可读L100000，链上应按本例等decimals尺度换成 `100000×10^18`。把金额乘10^18却漏缩放L，公式形式相同，结果仍会完全错误。

## 第 2 层：Q64.96保存的究竟是哪一种价格？

**面试官：**你说与合约一致，sqrtPriceX96到底怎样还原价格？两个币decimals不同又怎么办？

**面试者：**它保存原子单位比例的sqrt价格。令编码整数为S、Q为2^96，`s_raw=S/Q`，`P_raw=(S/Q)^2=raw1/raw0`。若要得到每1个token0值多少个人类单位token1，需乘 `10^(decimals0-decimals1)`。

主例两币都是18位，初始S为Q，对应人类价格1。如果明确改变条件，token0为18位的资产、token1为6位的稳定币，人类价格为2000，那么原子价格是 `2000×10^(6-18)=2×10^-9`，不是2000。只有完成单位转换才能得到正确S。

反过来把S平方还原时，Go可用宽整数乘法并保留为有理数或指定精度的商；不要先截成整数的S/Q再平方，否则低于1的sqrt价格会直接变成0。token0/token1顺序由池身份确定，不由UI买卖方向决定。

## 第 3 层：既然要平方，为什么不直接存价格？

**面试官：**编码这么绕，存P的定点数不更简单吗？sqrt价格解决了什么具体计算问题？

**面试者：**sqrt价格让固定L区间的数量变化更直接。上行净输入T1是 `L(s'-s)`，T0输出是 `L(1/s-1/s')`，知道净输入后可线性得到新的s。若直接存P，每步就要处理平方根或等价的更复杂表达式，并同步控制精度。

Q64.96同时给整数和小数部分固定尺度，但并不是所有价格都能精确表示。实际S与tick网格由TickMath的整数算法确定，不应使用浮点 `pow(1.0001,tick/2)` 来生成签名参数。

编码选择还约束范围。v3以uint160保存sqrt价格，L以uint128保存；中间乘积可能远超这些宽度。用big.Int不意味着可以省略合约输入范围检查，超范围的Go计算也许有答案，链上却会拒绝。

## 第 4 层：具体金额公式如何避免中间溢出？

**面试官：**那就用S和L演算。两个编码sqrt价格A小于B时，金额公式是什么，中间数放得下吗？

**面试者：**理想公式是 `amount1=L(B-A)/Q`，`amount0=LQ(B-A)/(AB)`，方向决定哪一个作为输入、哪一个作为输出。直接先乘所有uint256再除，会在最终结果可容纳时仍中间溢出，所以不能只检查返回值。

Solidity版本使用FullMath等宽乘除辅助，并通过分步计算、受控的备用表达式处理部分路径。Go的big.Int可以精确容纳中间乘积，但仍要复刻合约的运算顺序、上取整位置、分母正数与范围拒绝，不能仅凭“最终有理数相同”认定逐位等价。

特别是token0下一价格的源码包含依赖旧版算术回绕的溢出探测。若把它机械粘进Solidity0.8受检查算术，可能在进入备用分支前就revert。移植应固定原算法和编译语义，再决定用显式宽计算还是有证明的unchecked范围。

## 第 5 层：舍入只是末尾一位，为什么要分方向？

**面试官：**假设中间数不溢出，把所有除法统一向下取整不就最简单吗？

**面试者：**不行，输入和输出承担不同约束。到达某个目标价格需要收足输入，因此输入delta一般向上取整；允许给出的输出delta向下取整，不能因取整多付代币。exact-output还要保证价格推进足够获得目标输出，具体下一价格函数的取整方向要结合token方向分析。

例如token0下一sqrt价格函数采用向上取整，token1相关函数最终价格向下取整。这不是“所有价格保守上调”，而是配合方向，使exact-input不多给输出、exact-output不低估必要移动。

在合约中每一步都可能取整，分两段取整后的和不必等于整笔最后只取整一次。若本例A段恰好差一个原子单位才能到边界，舍入会影响是否cross和下一段费用归属。只对最后总输出round一下，无法修复错误的中间执行轨迹。

## 第 6 层：手续费也能直接乘0.003再截断吗？

**面试官：**你已经分清输入输出舍入。费用呢，1500乘0.003等于4.5，何必每步那么麻烦？

**面试者：**4.5是本例连续模型的总费，不是通用整数实现。exact-input先用 `floor(remaining×(10^6-feePips)/10^6)` 得到可用净输入预算。若足够到目标价，目标净输入按规则向上取整，手续费通常为 `ceil(netIn×feePips/(10^6-feePips))`。

如果在该段内就耗尽输入预算，SwapMath按 `remaining-netIn` 确定本步费用，确保总消耗恰好不超剩余预算，其中可能包括整数舍入余量。不能对每步都用 `floor(gross×0.003)` 替代。

一个极小的边界例子是只剩1个原子单位输入，0.3%费率下可用净额向下取整为0，可能没有价格移动和输出，剩余额被计为费用。正minOut会让整笔交易失败。小额实现若将fee向下取0再让净额为1，就已经偏离目标合约语义。

## 第 7 层：负tick和费用累积的算术也照常除就行吗？

**面试官：**逐步舍入已经有规则，tick映射和feeGrowth计算还会踩什么不同的整数坑？

**面试者：**至少有两种不同语义。第一，负tick压缩需要数学向下取整。tick=-1、spacing=60，对应压缩tick应为-1，而不是向零截断的0；否则向左扫描会跳错bitmap word。TWAP平均tick遇到负数除不尽时也要按相应规则修正，不能默认Go或Solidity整数商就是floor。

第二，feeGrowth的uint256累计与差值在目标版本中可能使用模2^256语义。Go的big.Int相减会产生任意精度有符号结果，不会自动回绕；若忽略目标合约的模运算，溢出前后手续费检查点可能算成负数。它与金额超范围应拒绝的场景不能混为一谈。

因此移植需要为每类数写清单位、宽度、符号、舍入和是否允许模回绕。不是所有数都套一个统一的“安全除法”或“负数报错”就正确。

## 第 8 层：怎样验证数值兼容，不把手算当测试通过？

**面试官：**规则这么多，交付Go报价器时怎么证明没改坏？你现在这份文档已经证明了吗？

**面试者：**文档只给出了讨论规则和实数手推，未证明实现兼容，也没有执行工程测试。真正实现时，应固定合约提交、编译版本、链和池配置，先构造可复现的同区块状态，再对照目标实现的逐步输入、输出、费用、新S、tick和L，而非只对最终小数。

边界集至少包括S=Q、两币decimals不等、负tick、最小原子输入、刚好到tick、差一个原子单位不到tick、极端价格和L、手续费回绕边界，以及达到价格限制后剩余输入。发生差异时记录首个分叉步骤和原始整数，避免用容差把错误跨界掩盖掉。

实数参考可检查量级、方向和守恒，但只有与固定整数算法逐位对比并覆盖拒绝条件，才能支持相应兼容结论。即便差分样例通过，也不等于所有并发、恶意代币或链上安全场景都已验证。

## 本题收束

- **讲透的机制：**金额原子单位、sqrt价格编码、宽乘除、分方向舍入以及不同种类整数的语义必须一致。
- **最容易答错：**保留18位等于18位精度；S/Q先整除再平方；L不缩放；所有除法下取整；big.Int自动等价于uint256。
- **反例检验：**把原条件改成token0为18位、token1为6位、人类价格2000。如果实现把P_raw仍设成2000，就会出现12个数量级的单位错误，再精巧的tick算法也救不了。
