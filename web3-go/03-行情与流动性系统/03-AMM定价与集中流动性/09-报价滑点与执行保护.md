# 大问题 9：怎样把报价变成可执行的滑点保护，而不混淆费用、价格冲击与剩余输入？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| exact-input / amountInMax | 先指定最多愿意花多少输入币 | 本例1500 T1买T0是预算，触及合法价格限制可少花，不保证用完整笔 |
| expectedOut / quoteBlockHash | 模拟预计收获，以及所用状态版本 | 预计约1472.669192 T0不等于锁价；真正执行取决于轮到交易时的链上状态 |
| fee / 毛净输入 | 协议收费，以及扣费前后的输入数量 | 本例0.3%输入费、协议不分成；1500扣费后1495.5进入曲线，不再另收一遍 |
| price impact / 执行滑点 | 自己沿曲线推价的影响，以及实得相对报价的偏离 | 两者和费用分开；同状态按同规则成交，不因输出低于1500就发生执行滑点 |
| s / activeL | P=T1/T0的平方根，以及当前段深度 | T1输入令s上升，跨240后L由100000变50000；不是用总池资产估深度 |
| 终价 / 平均支付价 | 成交后局部价格，以及实际输入除以实际输出 | 终价约1.03599，不等于整笔含费平均价约1.01856，也不是用户数量下限 |
| minOut / amountOutMinimum | 这次交易最少必须拿到的输出量 | 本例1470 T0需编码成18位原子单位整数；实际不足就同笔回滚，不自动降低 |
| sqrtPriceLimit / deadline | 池价最远可走到哪，以及路由最晚允许何时执行 | tick420限制终点价格，deadline限制期限，各自不替代minOut，也不保证及时入块 |
| consumedIn / unspentIn / delta | 真正消耗、没有花掉的预算和池实际收付量 | unspentIn=1500-consumedIn；回调只付实际正delta，预算余量不是池欠款 |
| allowance / 预充值退款 | 花币许可，以及钱已先进路由时的余款处理 | 钱包直付的未花部分仍在钱包；预充值须按本请求账退，不得扫路由总余额 |
| exact-output / maxIn / MEV | 指定输出、最多付款，以及交易排序带来的风险 | 足额检查须核对具体路由；minOut及私有提交都不构成绝对防夹保证 |

## 把整篇文章压缩成一个故事

小林看到1500 T1只能换约1472.669192 T0，问少掉的是否全是滑点。后端小乔解释：两币18位、输入费0.3%、协议不分成，1495.5净额还要沿A/B曲线成交；费用、自己造成的价格冲击和报价后状态变化造成的执行偏离不是一回事。她给报价附blockHash，把1470 T0最小输出、tick420价格限制和路由期限编码为用户约束，连续小数不直接当链上参数。链上若只得到1469，哪怕池已收付款，也由同笔路由检查撤销全部交换。若合法触限而少用输入且输出达标，则按实际delta结算；钱包直付的余款没离开钱包，预充值路径则必须准确退款，不能用路由总余额代替请求余额。系统同时展示平均支付价、终价和实得，不悄悄放宽保护来提高成功率。后来产品改为必须买到1470 T0，她重新核对足额输出与maxIn，而非信接口名字；较紧minOut会增加回滚概率，也不能消除公开排序和夹子风险。签名前还要把链、池、方向、收款人和原子单位逐项对齐；绿色报价页面不能替代规范链回执与实际收付。

**流程位置与核心机制：** 从报价生成交易约束，到池内逐步成交，再由路由在同一交易内检查实际输出；重点是约束含义与资金闭环，不展开回调实现。

**必要前提：** 公共基线、价格方向与金额单位见总览；本题沿用输入侧 0.3% 费用和 A/B 在 tick240 交接流动性的条件，重点区分报价估算与用户签名接受的执行条件。

贯穿请求是 exact-input：最多 1500 T1 买 T0，方向 oneForZero；minOut=1470 T0，价格限制为 tick420 对应的 sqrtPrice。deadline 由教学路由检查，不属于 core 池参数。文中小数是连续数学推演，整数逐步舍入会略有差异，不代表工程验证。

```text
锁定报价区块与请求 → 计算预期输出、实际消耗及终态
    → 用户确认 minOut、sqrtPriceLimit、deadline
    → 教学路由检查期限 → 池逐步交换
        ├─ 输入耗尽或到达价格限制 → 返回实际输入、输出
        └─ 回调付款失败 → revert
    → 同一交易检查实际输出 ≥ minOut
        ├─ 满足 → 仅结算已消耗输入，处理路由剩余资金
        └─ 不满足 → 整笔交换回滚
```

## 第 1 层：报价比 1500 少，是否就是滑点？

**面试官：** 用户花最多 1500 T1，报价只有约 1472.669 T0。少掉的都是滑点吗？

**面试者：** 不是。初始 P=1 只表示极小交易的现货交换关系，不能直接用 1500 T1 对应 1500 T0 当可成交承诺。费用是协议明确的收费规则；price impact 是本次交易沿池曲线改变价格造成的影响；执行滑点则是实际成交相对约定报价的偏离，例如报价后其他交易改变了状态。

我会返回 `quoteBlockHash、amountInMax、expectedOut、feeAmount、sqrtPriceAfter、amountInConsumed`，把价格影响的比较口径单独标注。本例从固定初态计算出 1472.669192125127908224 T0，如果执行恰好沿同一状态和整数规则完成，不能因为它小于 1500 就说发生了执行滑点。把三个概念混成一个百分比，会导致用户误以为手续费可以靠提高滑点容忍度消除。

## 第 2 层：既然不是滑点，这个输出怎样逐段算出来？

**面试官：** 你说沿曲线成交，那跨 tick240 时，费用和 price impact 怎样分别落到数量上？

**面试者：** oneForZero 令 s 上升，每一段固定 L 时，净 T1 输入为 `L(s₂-s₁)`，T0 输出为 `L(1/s₁-1/s₂)`。费用从毛输入中扣除，不能先让全部毛输入推动价格再追加一次收费。

到 tick240，`s_b=1.012071681663366439`。A 段毛入 1210.800568040766192842、净入 1207.168166336643894263、出 1192.769433438381804424，费 3.632401704122298579。向右跨过该 tick，A 退出、B 进入，activeL 从 100000 变为 50000。B 段净入 288.331833663356105737、出 279.899758686746103800、费 0.867598295877701421。

两段共费 4.5 T1，总出 1472.669192125127908224 T0；终态 P=1.035994842274346199、tick353、activeL=50000。fee 先决定进入曲线的净额，曲线和分段流动性再决定输出。要单独报告“纯 price impact”，必须说明是否用零费曲线作对照，不能把输出差额机械拆成两个同单位的减数。

## 第 3 层：终价、平均价和 minOut 为什么不是同一个保护？

**面试官：** 你已经算出终价，直接限制终价不超过 tick420，为什么还要 minOut？

**面试者：** 终价是交易结束时的边际价格，平均成交价是实际 T1 支出除以实际 T0 收入，二者不相等。价格限制约束池价格前进的边界；minOut 约束本次交易最终拿到的数量，属于不同维度。

本例终态 tick353，说明这次计算未触及 tick420；minOut1470 相对报价留出的数量空间约为 2.669192 T0，约占报价的 0.1812%，不是“0.3% 手续费再加 0.1812% 就能无条件成功”。路由要把 1470 编码为 T0 最小单位整数，并检查实际返回输出。报价生成的时点、费用和舍入口径都应可追溯；不能在提交前悄悄降低 minOut，让陈旧报价看起来仍然有效。

minOut 也不是“防夹保证”。公开待打包交易暴露方向与容忍边界，其他交易可能抢先改变状态，再在本交易后交易，使用户在仍满足 minOut 的价格成交。较紧的保护会缩小可接受损失，也增加回滚概率；受信任的私有提交通道可以减少公开暴露，但有信任、可用性和排序条件，不能保证不受 MEV 影响。deadline 只限制期限，不能解决这类排序风险。

## 第 4 层：价格限制先触发，exact-input 会强制花完吗？

**面试官：** 既然两个保护独立，若执行时先到 tick420，却还剩 T1，core 会为了 exact-input 把 1500 全花掉吗？

**面试者：** 不会。core 循环同时受剩余指定数量和 sqrtPriceLimit 限制，触及价格限制可以提前停止。exact-input 在这里不能被解释为“任何情况下必须全量成交”。本例初态下输入先耗尽；现在讨论的是报价后池状态改变这一明确变体。

路由应读取实际 delta，记录 `consumedIn、actualOut、unspentIn`，其中 `unspentIn=1500-consumedIn`。只要到达的价格和输入条件合法，部分消耗本身不是欠款，也不是 core 失败。随后是否接受，取决于教学路由的明确产品规则及 minOut：实际输出不足 1470 就回滚，达到则可接受部分消耗。不能把剩余指定量加入回调应付额，也不能宣称所有路由都有额外的全量输入检查。

这里还要检查执行起点。若执行前价格已经达到或越过上行限制，core 会因价格限制不合法而拒绝，不是把它当零成交成功。只有从合法起点向上走到限制，才是正常提前停止。tick420 应用对应的整数 sqrtPriceX96 表达，不能用浮点近似后随意取整；方向、上下界和初始价格关系都须校验。服务也不能为提高成功率，在用户签名后自动把限制移得更远。

## 第 5 层：部分消耗后，剩余输入究竟在哪里？

**面试官：** 你允许部分消耗，那么用户签了 1500 的额度，未消耗部分是不是必须从池里退款？

**面试者：** 要先区分资金路径。教学路由若在回调中直接从钱包 `transferFrom` 到池，只转正 delta 对应的实际消耗。allowance 是可支取上限，不等于已扣款；未花的 T1 原本就在钱包里，池没有退款义务。

若改变为预充值路由，先把 1500 转到路由，再由路由支付实际 delta，就必须在这笔调用内显式退还本请求剩余款，并明确接收者。不能以路由总余额当作该用户退款额，否则会扫走其他资金。可按本次入账、实际支付和已退金额核对，结束时要求请求余款归零；标准 ERC20 假设下，退款失败应使调用回滚。预充值方案增加资金驻留和退款失败路径，不能把它与钱包直付描述成同一种结算。

## 第 6 层：拿不到 minOut 时，先收下部分结果再补偿行不行？

**面试官：** 既然退款有额外路径，若输出只有 1469，先结算再链下补差能减少失败吗？

**面试者：** 这改变了产品承诺。当前模型要求教学路由在同一 EVM 交易里、池调用返回后检查 `actualOut>=1470`；不足直接 revert。池价格、流动性与手续费状态、代币转账和本交易日志一起回滚，不留下一个等待链下补差的半成品。退款失败也不能吞错后宣告成功。

链下补偿会引入信用风险、身份核对和另一次付款，不再等价于原子 minOut 保护。失败交易仍可能消耗 gas 与发送者 nonce，先前独立成功的 approve 也仍有效。deadline 只让教学路由拒绝过期调用，不保证到期前被打包，更不替代输出检查。链下服务超时不能越过这些链上判断宣布成功或退款完成。

## 第 7 层：改成 exact-output，是不是就没有这些边界了？

**面试官：** 你强调数量下限，那直接要求买到 1470 T0，并限制最多付 1500 T1，是否更简单？

**面试者：** 这是从 exact-input 改成 exact-output：固定目标输出，以 `maxIn` 限制成本，已改变母题前提。它适合必须拿到某个数量的业务，但仍须说明遇到价格限制时是否要求足额输出，以及剩余资金怎样处理。

不能只看到接口名便推断足额保证。参考 v3-periphery 的单跳实现，exact-output 内部在未传自定义价格限制时有足额输出检查，传入非零限制时不能沿用这一无条件结论。若教学路由承诺“必须买到 1470”，应明确检查实际输出等于目标，并检查实际输入不超过 1500；任何一项失败都回滚。收益是数量目标清楚，代价是输入不确定且合约约束必须审计，不能靠名称替代代码。

## 第 8 层：怎样判断这些保护真的对应用户意图？

**面试官：** 既然接口名称不足以保证语义，你会如何检查报价、交易参数和余额结果没有脱节？

**面试者：** 我会把用户意图绑定为 `chainId、pool、tokenIn/out、recipient、amountInMax、minOut、sqrtPriceLimitX96、deadline`，展示报价区块哈希与估算消耗，签名前检查编码方向和单位。tick420 是价格限制，不要求等于某个 LP 边界；tickSpacing60 约束 LP 边界，不表示交易终态只能落在 60 的倍数。

验证分三条手工路径：原始初态应得到约 1472.669192 输出并通过 minOut；改变执行前态使实际输出为 1469，应整笔回滚；再构造先触限的变体，核对只付 consumedIn，钱包直付无额外退款，预充值则退回精确余款。以上是验证方式而非已运行测试。链下“成功”最终应依据规范链回执及实际结果，不能只依据报价页面显示绿色。

## 收束：讲透、易错与反例

- **讲透：** 费用决定净输入，价格冲击来自曲线，执行滑点描述报价与执行差异；minOut、价格限制和期限分别约束不同风险。
- **易错：** exact-input 不代表 core 必须花光；未消耗输入不属于池欠款，allowance 也不是预付款。
- **反例：** 路由预收 1500，只付 1400 却不退 100，即使 actualOut 满足 minOut，资金闭环仍然失败。
