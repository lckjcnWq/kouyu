# 大问题 5：一笔 Swap 跨过多个 tick 时怎样逐步成交，如何处理反向、价格限制和零流动性？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| swap step / target | 一次只算当前深度能走的一段，以及本步终点 | target取下一候选tick价格与用户limit中更近者，不把未来L提前合并 |
| s / activeL | 当前平方根价格，以及当前参与成交的深度 | P=s²=T1/T0；净入T1=L(s'-s)，只在L不变段有效，L不是池资产 |
| remaining / calculated | 还没处理的指定数量，以及累计的另一侧币量 | 主例remaining是含费T1预算；exact-output时含义、符号和更新方式须按算法另定 |
| 毛输入 / 净输入 / fee | 实际消耗、推动价格的量和输入侧费用 | 本例0.3%费，净入不重复扣费；连续小数仅供手算，整数步骤另核对 |
| initialized / cross | 真有LP边界状态，以及越界时切换状态 | 到达候选tick且已初始化才翻转outside、改变L；空word边缘不凭空增减L |
| liquidityNet | 向右越界时活跃L应改变多少 | tick240为-50000；上行加它，下行取反，费用先归旧L再切换 |
| oneForZero / zeroForOne | T1换T0向上走，以及T0换T1向下走 | 在240反向可先零距离cross，存储tick设239，不能因价格未动而漏切L |
| minOut / sqrtPriceLimit | 整笔最少收多少，以及价格最多走到哪 | limit允许少用输入；输出不足minOut则同交易全回滚，不保留第一段 |
| 零L / gap | 当前价段没有头寸承接的空档 | v3 Core可零额推进搜索，不能除以L；教学MVP明确不实现该能力 |
| QuoteBudgetExceeded | 报价服务资源预算不足的明确失败 | 限step、word、RPC和时间，不把计算截断伪装成协议允许的部分成交 |
| exact-output / amountInMaximum | 指定要收多少输出，以及最多能付多少输入 | 不等于把exact-input字段改名；足额输出检查还须核对具体路由与limit分支 |

## 把整篇文章压缩成一个故事

阿禾检查一笔1500 T1买T0的交换，两币18位、输入费0.3%、协议不分成。循环先比较tick240与价格限制tick420，用A的L100000走到较近边界：连续模型消耗约1210.800568 T1、输出1192.769433 T0，先把约3.632402 T1费用记给旧L，再cross切到B的50000。余量继续兑换，总输出约1472.669192，满足minOut1470，实际链上须按步整数舍入。她另从原快照把limit改到240，输出便不足1470，不能保存第一段；明确改minOut1190才可少花预算成功。随后反向时，240上的零距离cross必须先恢复A；删掉B形成空档时，v3能搜索并零额推进，不能除以0，也不能称为空档成交。Go模拟设步数、word和RPC预算，超限就报错而非交付半截报价，取消计算也不取消已广播交易。若换成指定输出模式，还得重定剩余量、舍入与最大输入保护，不能沿用这份预算逻辑冒称足额交付。阿禾把剩余输入、累计输出、费用、终点价格和活跃深度一起核对；即使总输出碰巧接近，也不能放过费用归错人或反向边界错位，否则下一笔交易才会暴露损坏的状态。

[返回专题总览](README.md)

**流程位置与核心机制：**把02的单段数学与04的边界索引组合成一笔完整Swap执行，负责剩余量、跨界顺序、零流动性和停止条件。金额整数细节引用03，手续费权益引用06，不重复扩写完整账本。

**必要前提：**主例从tick0开始，T1买T0，最多1500 T1，minOut1470 T0，limit为tick420；A[-240,240) L100000，B[240,480) L50000。所有小数是连续模型推演，实际整数实现以目标合约为准。

## 第 1 层：跨多个区间的执行循环怎样组织？

**面试官：**如果用户一笔输入要经过几个不同L的区间，你怎样组织Swap算法，而不是循环调用一个固定价格函数？

**面试者：**每轮都围绕“当前状态能走到哪里”执行。先按方向查下一候选tick，取它的sqrt价格与用户limit中更近的目标；根据当前L、剩余预算与费率，计算能否到达目标，得到本步新价格、净输入、输出和费用。

然后更新剩余指定数量、累计另一侧数量和本段费用；如果恰好到达候选tick且它已初始化，才cross并按方向改变活跃L。未到边界就按实际新价格更新tick。直到预算耗尽或达到价格限制，返回整笔实际delta。

循环中的状态至少包括sqrtPrice、tick、activeL、amountSpecifiedRemaining、amountCalculated和输入币种feeGrowth。查找边界、推进价格、记费、cross各有顺序，不能在一开始先把未来所有LP的L合并。

## 第 2 层：怎样判定本步到边界还是耗尽预算？

**面试官：**你说判断能否到目标，用主例第一步具体算给我看。

**面试者：**当前s=1，下一初始化边界是tick240，目标 `s_b≈1.012071681663366439`，比limit tick420更近。A段净输入门槛是 `100000(s_b-1)≈1207.168166 T1`，含费用约1210.800568 T1。

总毛预算1500足够到边界，所以第一步输出约1192.769433 T0，剩余毛预算约289.199432 T1。本步手续费约3.632402 T1，不能把它从剩余净额再扣一遍。

整数实现不是用小数比较：先算可用扣费净额，再与上取整的目标净输入比较，按SwapMath规则确定本步费用与剩余。若剩余不足，终点就在本段内部；不能先到边界再以“负余量”退回来，因为cross会影响L和费用状态。

## 第 3 层：第一段记费、cross、第二段执行为什么要这个顺序？

**面试官：**到240了，先把L改为50000，再用该L分配第一步费用，结果看起来也能累计，总体有什么错？

**面试者：**错在费用必须归为这一步提供深度的旧活跃LP。第一步由A的L100000完成，先将该步费用计入输入币种的global增长，再执行tick outside翻转；最后上行加tick240的net=-50000，切换成B的L50000。

若先换L再记费，增长分母错误，而且cross时记录的outside不包含应属于旧区间的费用，inside权益会发生错配。即使总转账费用仍是4.5，LP之间的分配也已不正确。

随后B段使用余下约288.331834 T1净输入，最终s约1.017838318337，输出约279.899759 T0，费用约0.867598 T1归B。总输出约1472.669192，末tick353、活跃L50000。必须同时核对输出与权益，不能只检查用户总额看起来合理。

## 第 4 层：刚跨到边界又反向，如何避免重复或漏跨？

**面试官：**现在改变一个条件：第一笔恰好停在tick240，下一笔立刻T0买T1。怎样恢复A的活跃L？

**面试者：**上行到240后，池存储tick为240，活跃L已经是B的50000。下一笔zeroForOne向左查找时会包含当前边界240；如果sqrt价格仍等于该边界，先以零距离处理它的cross，net取反，因此从50000加50000回到100000。

向左越过后存储tick设为239，防止同方向再跨一次240。接下来才能在A段按T0输入公式推进。不能因为价格没变化就跳过这次边界处理；它决定此后交易是谁提供流动性。

如果是从主例最终tick353反向，要先在B内部走到240，给B记该段费用，再做上述cross。这里“恰好停在240”是独立变体，不能与已经走到353的状态混用金额。

## 第 5 层：价格限制把循环截断时，整笔数量怎样解释？

**面试官：**再从原始状态开始，只把limit改到tick240，预算还是1500。预算没花完，循环是不是应该继续？

**面试者：**不应该，价格限制是明确停止条件。到240后已经达到limit，得到实际消耗约1210.800568 T1、输出约1192.769433 T0、未消耗约289.199432 T1。core按实际完成量返回delta，不保证exact-input一定花完整笔预算。

但主例minOut1470仍然有效，这一变体输出不足，教学路由必须整体回滚。只有明确把minOut也改为1190等可满足值，才能保留这个部分使用输入的结果；此时它是一份完整成功的交易，不是中途失去原子性的半笔成交。

到达初始化边界时仍需按目标实现更新tick与L，包括恰好碰到limit的情况。不能为省步骤让价格在240、存储状态却仍声称A活跃，导致下一笔方向切换出错。

## 第 6 层：跨界后没有活跃流动性，是否一定立即失败？

**面试官：**保持主例起点，但删除B，让A上界到更远的头寸之间形成空档。你会在L=0时直接除法吗？

**面试者：**不能除以0，也不能直接套 `s'=s+net/L`。需要按具体协议处理，不能把所有AMM都讲成“零L立即revert”。在v3 Core中，循环可继续查找下一tick或word边界；L=0时到目标的输入输出delta为0，可把价格零额推进到下一搜索目标，再在初始化tick恢复L。

这种推进本身不给用户输出，也不消耗可用于正常兑换的净输入；如果先前没有费用，零L也不能计算 `fee/L`。后续是否还能成交取决于limit前有没有恢复有效L，而不是空档价格显示移动了就算有深度。

如果整个前方都没有可用L，就可能推进到价格限制，输出不足而被minOut拒绝。为控制教学范围，总览MVP遇gap直接返回UnsupportedGap；那是MVP明确未实现的能力，不是声称v3本身一定报同样错误。

## 第 7 层：循环怎样保证会停止，又不把预算不足当成功报价？

**面试官：**空word很多、极小输入又可能不移动价格。你的Go模拟怎么防止卡死和资源耗尽？

**面试者：**先区分算法终止与服务预算。算法每轮应通过消耗剩余量、推进价格、推进搜索tick或到达limit取得进展；零距离边界cross可以依赖存储tick方向更新避免重复，极小exact-input则可通过费用消耗掉剩余额。实际实现要显式检查没有任何进展的非法状态。

服务还应限制总step、扫描word数、RPC补页数和总时间；预算不足返回QuoteBudgetExceeded或状态不完整错误，不能把目前累计输出包装成“1500输入的完整报价”。只有协议允许并明确报告的价格限制停止，才属于有效的部分使用输入。

共享快照必须不变，本次模拟的剩余量和跨界状态独立。如果context取消，释放本地计算与RPC资源，但不能宣称取消了已经广播的链上交易。超时改变服务是否继续计算，不改变链上Swap的权威执行结果。

## 第 8 层：换成exact-output，哪些结论不能原样照搬？

**面试官：**最后改变数量语义：用户指定必须得到固定T0。能只把remaining字段换个名字沿用吗？

**面试者：**不能。exact-output以剩余输出为主约束，逐步计算为了达到该输出需要推进到什么价格、收取多少输入和费用，并对价格函数和delta采用相应舍入规则。需要用amountInMaximum保护输入，而不是沿用exact-input的输入预算更新方式。

价格限制仍可能在输出目标完成前触发，所以“必须足量”要由明确的路由规则检查并整体回滚，不能只看到接口名就断言所有路径都保证。具体v3 periphery版本对自定义limit可能存在不同检查分支，生产接入需核对实际代码；本专题的主例没有悄悄切到这一模式。

验证时应在同一初始状态下，比较到边界、未到边界、反向、gap和limit的轨迹，并同时检查实际输入、输出、fee、最终tick和L。仅比较最终输出不够，因为错误的费用归属或边界状态可能留待下一笔才暴露。

## 本题收束

- **讲透的机制：**单步定价决定当前段，费用在旧L下计提，cross改变下一段；方向、剩余量和价格限制共同决定停止状态。
- **最容易答错：**提前换L分配旧费用；exact-input必全额使用；边界零距离不必cross；零L一定立即revert；服务步数截断等于协议正常停止。
- **反例检验：**第一笔从原始快照恰好上行停在240，第二笔立刻反向。正确轨迹先把L从B的50000恢复到A的100000，再向左定价；若第二笔仍按50000算，说明边界方向性被漏掉。
