# 大问题 12：怎样用链上事件维护可报价投影，并在确认变化与重组后恢复到正确分支？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| receipt status / canonical / finality | 本次执行成败、是否在规范链及最终可信程度 | status=1只说明某区块执行成功；确认策略按链配置，固定12块不是通用最终性 |
| chainId、blockHash、txHash、logIndex | 链、分支区块、交易和日志位置的身份组合 | 用于事件去重；同tx可有多日志，也可在新分支重新包含，不能只按txHash拦截 |
| transactionIndex / 应用顺序 | 区块内交易位置及日志先后 | 按块、交易、日志位置应用，不按网络到达顺序，先Mint后Swap会改变结果 |
| 报价投影 / post-block | 给查询与模拟用的派生状态，以及整块处理后的版本 | 不拥有池裁决权，不冒充交易前态；只承诺声明字段范围 |
| Mint / Burn / gross / net | 增减L事件，以及边界绝对量和向右净变化 | 两端gross同增减、net一正一负，gross决定初始化；net=0也可能保留bitmap位 |
| storage补读 / 同版本 | 从合约状态补事件未覆盖字段 | 必须同blockHash，缺历史不能拿latest补；事件不自动重建完整费用和预言机 |
| 持久游标 / 连续补扫 | 已完整处理到的块号和hash，以及按块补齐 | 订阅在线不证明完整，空日志块也推进；removed通知只是提示，不能唯一依赖 |
| undo / 数据库事务 | 变更前值，以及投影和进度一起提交的局部边界 | 投影、撤销记录、去重与游标同提交，缓存发布在其后；不是链上与数据库的同一事务 |
| 共同祖先 / orphaned | 两条链共同起点，以及已退出规范链的旧包含 | 从后向前撤旧分支、再正序重扫新分支，不能只回退一块或只修Swap末价 |
| generation / 检查点 | 隔离构建的一代投影，以及可信恢复起点 | 恢复完原子切换，缺undo或深重组时停止发布并重建，不把半恢复状态当当前报价 |
| 撤销事件 / 外部副作用 | 通知下游原观察失效，以及链外已经执行的动作 | 可撤数据库投影，不能自动收回银行付款；同交易重入新链须按新前态重算 |

## 把整篇文章压缩成一个故事

索引员小唐看到小林的1500 T1买T0成功入块，先记“已包含”而非最终成交。主例两币18位、输入费0.3%、协议不分成，连续参考输出约1472.669192 T0，链上以整数结果为准。小唐按块内交易和日志顺序处理Mint、Burn、Swap，用含blockHash的事件身份去重；不只看最终L，还维护gross、net和bitmap，必要字段同hash补读。每块把投影、undo、去重记录和游标同事务提交，空日志块也补扫，数据库提交后才发布完整块末快照。新head忽然接不上父hash，他找到共同祖先，逆序撤旧分支、正序扫新分支，在隔离代中完成再切换。原txHash又出现也按新身份和新前态处理，不能因旧去重键漏算，也不能保留旧成交再加一次。恢复后核对连续范围和同hash状态，缺undo或历史就停报重建。确认策略按具体链配置，数据库撤回不了已发的链下款；这套投影只覆盖报价需要，不宣称完整还原所有费用和预言机存储。订阅只作同步提示，不能以连接正常证明事件齐全；恢复验收还需核对边界数据，不只比较当前价格相近。

**流程位置与核心机制：** 从区块、回执和日志构建链下读模型，处理事件顺序、数据完整性、原子游标与分叉恢复；投影服务报价，不拥有链上裁决权。

**必要前提：** 公共池规则与金额单位见总览；这里只重建声明范围内的报价投影，不把数据库事务当作链上提交，也不宣称仅靠事件恢复全部费用和预言机存储。

贯穿 swap 为 exact-input 最多 1500 T1 买 T0，oneForZero，minOut1470 T0、价格限制 tick420；deadline 由教学路由检查，非 core 职责。连续数学输出 1472.669192125127908224 T0，终态 P=1.035994842274346199、tick353、activeL50000；整数逐步舍入略异，本文不声称工程验证。

```text
获取 header 与成功日志 → 校验 blockHash、parentHash、顺序及范围完整性
    → 同块应用 Mint/Burn/Swap → 必要时读取同 blockHash storage
    → 一个数据库事务提交投影、撤销记录、已处理事件与游标
    → 发布带 blockHash 的 post-block 快照 → 按链策略提升确认状态
新 head 的 parentHash 不衔接
    → 查共同祖先 → 撤销旧分支 → 重扫新分支 → 原子发布新版本
```

## 第 1 层：receipt status=1，为什么还不能算最终成交？

**面试官：** swap 回执已经 status=1，为什么行情服务仍要记录确认状态，而不是直接写“最终成交”？

**面试者：** status=1 只说明该交易在回执所指区块执行成功，不保证这个块永远处于规范链。记录至少包括 `chainId、txHash、blockNumber、blockHash、status、canonical、confirmationState`；先标记 included，再按该链策略推进 safe 或 finalized，而不是把成功执行和最终性合成一个布尔值。

投影是链上事实的派生读模型，不能反过来证明交易已最终确认。当前规范链回执发生变化，就要更新观察结果。失败交易 status=0 的 trace 可能展示执行过程，却没有可保留的成功业务日志；不能把 trace 中回滚前的 Swap 当成交。gas 和 nonce 的消耗也不能被误识别为兑换完成。

## 第 2 层：日志重复和乱序时，什么身份才能去重？

**面试官：** 既然包含关系会变化，同一 txHash 的日志在重连时又收到一遍，你用 txHash 去重够吗？

**面试者：** 不够。一个交易可有多个日志，同一交易还可能在不同分支重新包含。事件键采用 `chainId/blockHash/txHash/logIndex`，保留所属分支；应用顺序按 `blockNumber、transactionIndex、logIndex`，不能按网络到达时间或 txHash 排序。

同键重复只应用一次，但去重记录和投影更新必须同事务，否则会出现“记了已处理却没更新状态”。新分支中的同 txHash 不是旧事件简单重复，应先撤旧分支再按新身份处理。收到相同高度不同 hash 时也不是随便覆盖一行，而是分叉信号；原始日志可保留审计，是否计入当前报价由 canonical 视图决定。

## 第 3 层：只跟 Swap 事件，能否还原集中流动性？

**面试官：** 身份和顺序明确了。Swap 事件有最终 liquidity，你只更新它，下一次跨 tick 是否就能报价？

**面试者：** 不能，跨界还需要各 initialized tick 的 liquidityNet。Mint 数量 d 时，lower 的 net 加 d、upper 的 net 减 d，两端 gross 都加 d；Burn 按移除数量做反向更新。gross 从零变非零或从非零变零时更新 bitmap；零数量 Burn 不能凭空翻转位。

当前 tick 落在 `[lower,upper)` 时，增减仓还会改变 activeL；先前 Swap 改过 tick 后，必须用事件顺序中的当前 tick 判断。以共享边界240为例，A 与 B 都存在时 gross=150000、net=-50000，右向跨越令 activeL 从100000变50000。仅保存 net 会漏掉“净变化为零但 gross 非零”的初始化边界，净值为零也不能直接清 bitmap。

## 第 4 层：把 Mint、Burn、Swap 都接上，是否就能重建全部池状态？

**面试官：** 你已经维护区间与末态，是否可以承诺仅靠事件完全重建 Uniswap v3 池存储？

**面试者：** 不能。Swap 事件可提供执行末态的 sqrtPrice、tick、liquidity 和数量，但手续费增长、tick 的 outside 累计量、oracle observations 等不应笼统宣称能由这些事件完整还原。报价投影必须列出范围：支持单池价格路径所需的价格、activeL、bitmap、liquidityNet 等，不承诺完整 LP 费用或预言机核算。

超出事件可覆盖字段时，读取相同 blockHash 的 storage，必要时使用 trace 或回放；节点无法提供历史状态就失败或从可用检查点重建，不能拿 latest 补洞。Swap 日志是该次 swap 末态；只有整块事件处理完、补读完成，才可发布 post-block 快照，不能把它称作该交易执行前状态。

## 第 5 层：日志订阅没断，为什么仍要按区块补扫？

**面试官：** 范围已经限定，如果 WebSocket 持续在线，收到事件就发布，不是更低延迟吗？

**面试者：** 在线不证明日志完整，订阅可能丢消息或重复投递。订阅只触发同步，持久游标保存 `number、hash`，按连续区块范围补扫并核对每个 header 的 parentHash。空日志块也要推进游标，否则无法区分“没有事件”和“还没处理”。

查询固定边界，校验日志的 blockHash 属于所取 header，并在发布前复核分支；分页与范围查询期间发现重组就废弃该批或按新分支重取，不能接着拼。低延迟候选视图可单独标记，不覆盖已完整发布的版本。`removed=true` 可以触发撤销检查，但不能依赖服务永远收到每条 removed 通知。

## 第 6 层：更新投影后崩溃，游标没推进会怎样？

**面试官：** 你依靠持久游标补扫，若进程恰好在写完 activeL、尚未推进游标时崩溃，重启会不会重复加减？

**面试者：** 每块用一个数据库事务提交：验证期望父游标、写投影变更、写 undo、写已处理事件、推进游标。提交前崩溃则全部不可见，提交后崩溃则从新游标继续；并发同步者用行锁或比较游标版本，防止同时推进不同分支。

undo 记录每个被改键的旧值及原记录是否存在，覆盖 slot0 投影、activeL、tick net/gross、bitmap 和关联标记。不可只保存最新 Swap，因为恢复还要撤销 Mint/Burn。缓存也不能在数据库提交前发布新快照；提交后缓存发布失败可由游标重建，不让内存领先持久事实。这里的原子性属于链下数据库，不会修改或锁定链状态。

## 第 7 层：parentHash 对不上，怎样准确撤销而不越撤越乱？

**面试官：** 崩溃窗口闭合了。现在新 head 的 parentHash 不是当前游标 hash，直接退一个块再重放够不够？

**面试者：** 不够，分叉可能深于一块。沿旧分支和新分支 header 找到共同祖先 C，按高度从后向前应用旧分支 undo；若 undo 按事件记录，同块还要逆事件顺序。旧事件及包含关系标为 orphaned，再按正序扫描新分支到目标 head。

每一步撤销或重放都让投影和游标同事务变化。为了不让报价读到只恢复一半的状态，可暂停发布，或在隔离 generation 中构建并在完成后原子切换 published 指针。恢复期间宁可返回同步中，也不声称旧版本是当前链。共同祖先与旧数据缺失时转检查点重建，不凭当前价格猜测如何“抵消”旧交易。

## 第 8 层：重组后原交易又出现，业务如何避免双计？

**面试官：** 新分支重扫时，同一笔 swap 又被包含，且 logIndex 变了。你既保留旧日志又应用新日志，会不会显示两次成交？

**面试者：** 原始事件按分支身份可以各保留一份，但当前业务视图只统计 canonical 包含关系。旧事件的投影影响已经被撤销，新事件再按新位置应用；不能简单在旧记录上把 blockHash 改掉，因为同交易可能在新前态执行出不同结果，甚至失败。

若下游已消费候选成交，应发送带原事件身份的撤销或版本切换，再交付新确认结果；不能只补一条新成交。涉及不可逆链下付款时，采用更强确认策略并保留对账，不承诺数据库回滚能撤销外部银行付款。本题只保证报价投影随规范链恢复，不能把跨系统副作用伪装成 EVM 原子性的一部分。

## 第 9 层：多等几个块，是不是就可以删除所有恢复记录？

**面试官：** 你担心外部副作用，那统一等 12 个块，再删 undo，是否就算最终安全？

**面试者：** 不能把固定块数当跨链通用最终性。确认数、safe/finalized 标签、共识机制与 L2 的结算语义都按目标链配置；“12”只能是某个产品的风险策略，不是数学终局。可以给报价使用较新候选块，同时给结算使用更强确认状态，但必须分别暴露。

undo 和 header 的保留窗口要覆盖承诺的重组深度，并设置 finalized 检查点。超过窗口、检查点 hash 不符或出现策略外深重组时，停止发布，从可信祖先重新扫描，并告警而非静默跳过。最终性信息也应记录来源和高度；数据库里写一个 finalized 标签不能创造链上的最终性。

## 第 10 层：怎样证明恢复后的投影不是“看起来差不多”？

**面试官：** 你选择检查点重建，恢复完成后怎样给出明确验收条件，而非只比较当前价格？

**面试者：** 验收至少检查游标 hash、连续 parentHash、无缺口的扫描范围、canonical 事件唯一性，以及同 blockHash 的 slot0、L、相关 bitmap/tick 对账。比较字段必须覆盖声明的报价范围，不能只看价格相同就说投影完全一致。之后才切换发布版本。

可手工设计分叉：旧分支在240附近先 Mint 再 Swap，新分支保留 Swap 却取消 Mint。若恢复只改 Swap 末态、不撤边界 gross/net，后续跨 tick 报价就会暴露错误。再分别推演事务提交前后崩溃、重复日志与失败交易：最终发布状态应与直接扫描新分支一致。这是验证方法，不是已运行测试或完整池存储重建证明。

## 收束：讲透、易错与反例

- **讲透：** 事件身份属于分支，投影与游标共同提交，重组按共同祖先撤销再重扫，发布版本必须对应完整块末状态。
- **易错：** status1 不是最终性，净流动性为零不等于 tick 未初始化；恢复链下投影不能直接改链状态。
- **反例：** 只按 txHash 去重，旧分支事件已撤销后却拒绝新分支同交易日志，会永久漏掉真实成交。
