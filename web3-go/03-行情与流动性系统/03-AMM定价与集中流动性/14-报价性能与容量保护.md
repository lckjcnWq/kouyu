# 大问题 14：Go 单池报价怎样提升吞吐并保护容量，同时不牺牲报价正确性与执行约束？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| steps / ticksCrossed / wordsScanned | 计算步数、跨真实边界数和扫描位图组数 | 一组含256个压缩tick；单word位操作快不等于整笔O(1)，稀疏区间也可能昂贵 |
| activeL / 分段模拟 | 当前段有效深度，以及遇边界换L继续算 | 本例跨240由100000变50000，不可用池余额或固定初始L替代全程 |
| floor / tickSpacing | 向负无穷取整，以及LP边界网格间隔 | tick=-1、spacing60压缩为-1；方向或负数索引算错不能靠缓存修复 |
| 不可变快照 / 版本缓存 | 只读状态集合，以及按确定版本复用数据 | 键含链、池、blockHash、fee和模型，需声明覆盖范围；TTL不是规范链证明 |
| singleflight / 缓存击穿 | 同键只加载一次，以及失效后大量请求同时重读 | 失败不发布半成品，共享任务有界，不能让等待者超时触发无限重复加载 |
| RPC批量 / EIP-1898 | 合并网络请求，以及按hash读状态的约定 | 批量本身不保证同块；同H分批补读，provider不支持则明确弱化或拒绝保证 |
| maxSteps、maxWords、maxRPC / deadline | 一次报价能耗用多少计算、读取和总时间 | 服务预算用完要报错，包含排队时间；不是链上路由期限，更不取消已广播交易 |
| QUOTE_BUDGET_EXCEEDED / priceLimit | 没算完的服务错误，以及协议允许的价格终点 | 前者不交付成功报价；后者可合法少用输入，但仍须明确实际消耗和输出 |
| scratch / big.Int所有权 | 临时运算空间，以及谁有权修改大整数 | 每请求独占，不能浅拷贝共享后原地修改，更不能把模拟终态写回给下一用户 |
| pending / confirmed | 待打包预测，以及按所选确认策略认可的状态 | mempool可能替换或改序，预测须单独标记，不能当作已执行池状态 |
| 准入 / 背压 / 指标基数 | 限制工作进入、让负载有界，以及监控标签数量 | 队列、租户和热点按成本限额；观察排队/加载/计算，hash放日志，不编造QPS或P99 |

## 把整篇文章压缩成一个故事

报价洪峰到来，工程师小孟发现有些请求扫很多空word，慢的并非“单池只有一个公式”。仍以1500 T1买T0为例，两币18位、输入费0.3%、协议不分成，连续模型跨240后换B深度，完整输出约1472.669192 T0，整数实现另按版本核对。她先拆排队、快照加载和模拟耗时，再按同blockHash共享不可变数据、singleflight合并加载，RPC分批并行也固定H且限制规模。每个报价独占大整数和工作态，不能把上一请求的tick353当下一人的起点。某任务到240就碰服务步数上限，必须报预算不足，不能把1192.769433包装成1500输入完整报价；只有用户价格limit触发才是协议允许的停止。入口用有界队列、热点和成本配额，取消及时释放本地资源，确认查询保留恢复通道。过载时可以拒绝或明确给旧参考价，却不放宽minOut、limit和签名期限。她以同版本重复结果和真实指标判断优化，不把pending预测当成交，也不在没压测时承诺吞吐和P99。缓存覆盖范围、负价格网格和失败退避一起纳入检查，扩容也不能突破远端节点的并发上限。

**流程位置与核心机制：** 从请求准入、状态加载到逐 tick 模拟和结果返回，找出真实复杂度，控制缓存击穿、计算预算及过载；不把性能优化扩展成独立工程。

**必要前提：** 公共池规则与金额单位见总览；本题优化的是同版本快照上的独立只读报价，不能将模拟终态写成下一用户的链上起点，也不包含多池最优路由。

贯穿请求为 exact-input 最多 1500 T1 买 T0，oneForZero，minOut1470 T0，价格限制 tick420；deadline 由教学路由而非 core 检查。连续数学输出 1472.669192125127908224 T0、P_final=1.035994842274346199、tick353、activeL50000；整数按步舍入略异，不声称工程验证。

```text
校验输入 → 有界队列与租户/热点预算
    → 命中指定链版本的不可变快照
        └─ 缺失 → 同键单飞加载，RPC 并发与批大小受限
    → 请求独占工作态，按 bitmap 和 initialized ticks 模拟
        ├─ 输入完成或价格触限 → 返回报价、消耗量、版本
        └─ 数据缺失、限步、超时或取消 → 明确错误
    → 观测排队、加载、计算成本与拒绝原因，反馈容量策略
```

## 第 1 层：报价是不是套一个公式就能做到 O(1)？

**面试官：** 单池只有两个币，直接用公式算出输出，为什么还需要讨论容量保护？

**面试者：** 集中流动性是分段定价，不能把初始 L 套到整个区间。计算要找下一个 initialized tick 或 word 边界，运行 swap step，必要时跨 tick 更新 L，再继续。成本取决于经过的 initialized ticks、扫描的 bitmap words 和大整数运算，不只取决于金额或“单池”二字。

本例先在 A 段成交，到 tick240 换成 B 段，最终停于 tick353；完整数学输出约1472.669192。这个案例边界少，不代表所有请求都便宜。服务可记录 `steps、ticksCrossed、wordsScanned、rpcCalls、allocatedBytes`，但没测量前不能宣称某个 QPS 或 P99。优化首先定位 CPU、分配还是历史 RPC 才是瓶颈。

## 第 2 层：bitmap 能否保证始终只扫描一个 word？

**面试官：** 你说扫描 words，那 nextInitializedTickWithinOneWord 名字里有 one word，为什么还会成为长尾？

**面试者：** 每次调用只在一个 word 的指定方向范围内查找，未命中返回该范围对应的 word 边界及 initialized=false，不代表全局没有流动性。外层循环可能继续跨 word；跨过多少范围才决定总成本，不能把单次位操作 O(1) 当整笔报价 O(1)。

压缩 tick 必须按 floor 除以 tickSpacing。比如 tick=-1、spacing60，压缩索引应为 -1，不是 Go 有符号除法向零截断得到的0。左向 lte 保留当前位置及更低位，找最高置位；右向从下一压缩位开始，找最低置位。方向或负 tick 修正错了，会漏边界或选错目标；这种错误不能靠加缓存、加机器解决。

## 第 3 层：减少扫描时，缓存可以只按池地址吗？

**面试官：** 你已经能定位需要哪些 words，把它们缓存起来，是不是只用 pool 地址做 key 就够了？

**面试者：** 不够。快照 key 至少包含 `chainId+pool+blockHash+fee+模型版本`；覆盖的 words/ticks 也要有完整性元数据。相同地址可能在不同链，重组前后同高度可能不同 hash，不同模型也可能有不同舍入行为。按池缓存“最新字段”再任意拼接会生成不存在的状态。

可以共享不可变快照，并用 singleflight 合并同键的加载；失败时不发布半份对象，重试受退避预算约束。快照过期不应一边原地改 bitmap、一边让报价读取。结果缓存还要绑定 amount、方向、priceLimit 等参数。缓存提高复用率，代价是内存、版本回收与失效复杂度；TTL 只是回收策略，不是规范链一致性证明。

## 第 4 层：批量 RPC 和并行读取能自动保证同一状态吗？

**面试官：** 同键加载仍可能要读多个 word。把 RPC 一次批量发出、并行补 ticks，是否既快又原子？

**面试者：** 批量只减少往返，不能自动固定 latest 的区块。所有适用状态调用要显式指定同一 blockHash；provider 支持时用 EIP-1898，并根据用途要求 canonical。不支持则明确采用固定高度加前后 hash 核验的较弱回退，或拒绝强一致报价，不能隐式混块。

RPC 并行数、单批大小和补读范围都有上限，超限分批仍保持同一 H。部分读取失败就不发布完整快照，不能拿另一个区块的缓存填空。还要避免单飞等待者超时造成大量重复加载，加载任务采用服务级有界生命周期。收益是摊薄网络延迟，代价是 provider 限额、响应体与内存压力，需要分别观测而非无限开 goroutine。

## 第 5 层：请求跨太多 tick，能否停下来返回“近似最优报价”？

**面试官：** 你给 RPC 设置预算，CPU 也可能被一个复杂请求占满。最多算 100 步就返回当前结果行不行？

**面试者：** 可以限步，但不能把未完成计算标成成功报价，更不能叫最优。请求应携带或受服务限制的 `maxSteps、maxWords、maxRPC、deadline`；达到计算预算就返回明确的 `QUOTE_BUDGET_EXCEEDED`，说明目标链版本和消耗预算，可返回诊断字段但不提供可执行成功承诺。

要区分预算耗尽与合法价格触限：core 允许 exact-input 到 limit 提前结束，后者可返回实际 consumedIn、out 和剩余量；前者只是服务没算完，不能伪装成同一种部分成交。保守降级可以拒绝复杂请求或要求缩小输入后重新报价，但那是新请求，须经用户确认，不能内部截掉金额仍显示原始1500的报价。

## 第 6 层：同池大量报价，为什么不顺序写入一个模拟状态？

**面试官：** 你限制了单次成本。热点池仍有很多请求，用一个 goroutine 顺序处理并复用终态，岂不省去复制？

**面试者：** 排队处理可以复用不可变输入和独占 scratch，但不能把上个请求的模拟终态变成下个请求的起点。两个用户针对同一 H 的独立报价都应从 H 出发；把第一个模拟的 tick353、L50000 写回共享状态，会把并不存在的成交当作链事实。

每个模拟独占 remaining、sqrtPrice、activeL 和 big.Int receiver；共享 map 与数值只读，浅拷贝不能隔离 big.Int 底层数据。若另做 pending 预测，要显式标记预测顺序、候选交易和来源，不能混入 confirmed 快照。mempool 交易可能被替换、失败或排序变化，预测不等于确定成交；只有链上真实执行才裁决顺序和资产变化。

## 第 7 层：队列满了，怎样降级而不破坏用户保护？

**面试官：** 并发各算各的仍会把机器打满。你具体拒绝谁，能不能放宽 minOut 来减少失败重试？

**面试者：** minOut 不能作为容量旋钮。接入层用全局与租户限流、热点池配额、有界队列和工作池，队列等待超过预算就拒绝；把等待时间计入请求总 deadline，取消后及时停止本地工作。已广播交易的确认查询可用独立小资源池，避免报价洪峰把恢复通道一起堵死。

可优先复用正确链版本的快照，或提供明确标旧、不可直接执行的参考价；执行报价超出新鲜度策略就重新读取或拒绝。不能用另一个区块数据冒充原版本，也不能静默降低 minOut、放宽 priceLimit 或延长用户 deadline。降级应减少可用功能与负载，不降低资产保护。错误响应要说明过载、数据不可用还是预算不足，便于调用方采用退避而非立即重试风暴。

队列不能只限请求条数，还要限制预估成本：已知需要大量缺失 words 的请求可占更高权重，防止少数昂贵任务挤占全部工作者。估算错误时仍靠运行时步数与时间预算兜底。扩容只能增加独立只读计算与加载能力，不能取消每个 provider 的并发上限；否则本地实例越多，远端限流和重试风暴反而越严重。

## 第 8 层：怎样证明优化有效，而不是把错误藏进低延迟？

**面试官：** 你给出了很多限制，最后怎样判断该扩容、优化还是继续拒绝，而不编一个漂亮性能数字？

**面试者：** 分开记录 queue_wait、snapshot_load、simulate 的延迟分布，结合命中率、singleflight 合并数、inflight、拒绝原因、steps/words、RPC错误、GC和分配成本。标签控制基数，blockHash 与 txHash 放结构化日志或采样 trace，不直接做无限维 metrics label。以实测分布定位瓶颈，未测量不声称吞吐或 P99 提升。

正确性检查用同一 hash、相同参数重复计算，确认结果不受并发数和缓存命中影响；本例应与连续结果接近，但整数对照须按同版本舍入，不以小数完全相等作为链上证明。再用稀疏 words、负 tick、极多边界、加载失败和预算触发推演拒绝路径。容量上限以服务完成正确工作为目标，不把更快地返回错误成功当性能提升。

## 收束：讲透、易错与反例

- **讲透：** 真正成本由逐步模拟、tick/word 遍历与状态加载组成；不可变共享、请求独占、有界资源是优化底座。
- **易错：** 批量 RPC 不自动同块，限步不等于价格触限；pending 不是确定成交，性能降级不能放松 minOut 或链版本。
- **反例：** 只算到 tick240 就因限步返回1192.769433为“1500输入的完整报价”，既漏掉 B 段，又混淆未计算输入与实际未消耗输入。正确结果是预算错误，而不是假报价。
