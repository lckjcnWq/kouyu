# 大问题 11：Go 报价服务怎样读取同一链上状态，并让并发模拟不污染共享快照？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| blockHash / parentHash | 某个确定区块及其父块的身份 | 相同高度可有不同分支，快照绑定hash而非每个字段各读latest |
| EIP-1898 / requireCanonical | 用区块哈希读状态及要求该块仍属规范链的接口约定 | 实际provider须支持；固定高度前后验hash只是较弱检测，不能声称等价强保证 |
| slot0 / liquidity / bitmap / ticks | 价格位置、活跃深度及未来边界数据 | 都须同版本；余额不是L，只读当前L也算不出跨240后的深度 |
| post-block / pre-tx | 整块处理完的状态，以及某笔交易执行前的状态 | 本服务只承诺块末快照；Swap事件末态既非交易前态，也未必是整块末态 |
| 覆盖范围 / 懒加载 | 已读了哪些word和tick，以及按需补读 | 缺页不代表没有边界，补读仍须固定H，失败不可用latest填空 |
| 不可变快照 / 原子发布 | 建好后不再改的输入对象，以及一次切换整个引用 | 短锁或atomic.Pointer可切版本，不能边填map边让请求读取 |
| big.Int receiver / 深拷贝 | 大整数运算写入的目标对象，以及独立复制数据 | 结构体或指针浅拷贝不隔离底层字数组；Set创建独立工作值，禁止写共享net |
| scratch / sync.Pool | 临时运算对象，以及复用这些对象的池 | 每个请求独占，结果复制完且无引用后才归还，不能把已归还指针交给调用方 |
| singleflight / 缓存键 | 同键加载只做一次，以及区分结果身份的字段 | 键含链、池、hash、费率和模型；报价还含方向、金额和limit，TTL不证明规范链有效 |
| context / 资源预算 | 请求可取消的生命周期，以及计算和加载上限 | 等待者与共享任务分开有界管理，取消本地工作不等于撤销已广播Swap |
| 原子单位 / 模型版本 | 合约整数币量，以及具体算法语义的版本 | 两币18位主例须匹配整数舍入；同hash但不同算法也不能混成同一报价 |

## 把整篇文章压缩成一个故事

小许接到两个并发请求，都是1500 T1买T0，两币18位、输入费0.3%、协议不分成。他最初把latest读来的价格、L和tick拼装，可能把H、H+1、H+2混成从未存在的池。于是先选H，固定hash读取价格、活跃L、bitmap和必要边界，缺页也只向H补；provider不支持时明确拒绝强保证或标注较弱回退。整块事件和补读完成才发布不可变post-block快照，不能拿Swap末态冒充交易前态。两个goroutine各自深拷贝可变big.Int和工作态，不能原地取反共享net，也不能把第一个模拟的tick353写给第二个当起点。正确的整数算法应给两者同一确定报价，文中连续参考约1472.669192 T0并非精确测试结论。缓存与singleflight按hash、模型及参数隔离，结果复制后才归还scratch。取消一个等待者不应拖垮其他人，服务任务也不能无限后台运行；重组后停用H作当前报价，本地取消和缓存命中都不能改变链上实际执行。返回值先复制再归还复用对象，加载失败不发布半份快照；字段一致、内存隔离与版本新鲜度缺一不可，批量读取也不能代替这些保证。

[返回专题总览](README.md)

**流程位置与核心机制：** 从链上状态采集到本地报价返回，建立区块一致性、快照发布和可变大整数的所有权边界；不展开交易发送工程。

**必要前提：** 公共基线与单位见总览；Go 服务只做带 blockHash 的 post-block 快照和独立报价，不构造链下权威池，也不承诺恢复每笔历史交易的 pre-tx 状态。

同一请求为 exact-input 最多 1500 T1 买 T0，oneForZero，minOut1470 T0，价格限制 tick420；deadline 由教学路由检查，core 不检查。连续数学结果为总出 1472.669192125127908224 T0、P_final=1.035994842274346199、tick353、activeL50000。整数按步舍入略异，本文不声称工程验证。

```text
选定 header〔chainId、number、hash、parentHash〕
    → 固定该 hash 读取 slot0、L、bitmap、initialized ticks
    → 校验来源、覆盖范围和完整性 → 构建不可变快照
    → 原子发布快照引用
    → 每个请求独占工作状态与 big.Int scratch
    → 本地逐步模拟 → 返回报价 + blockHash + 模型版本
        └─ 缺数据、区块失效或预算耗尽 → 明确失败，不混入 latest
```

## 第 1 层：为什么每个字段都从 latest 读取仍然可能报错价？

**面试官：** Go 服务依次读取 slot0、liquidity 和 ticks，都用 latest，不就拿到了最新状态吗？

**面试者：** 每次 latest 都可能落在不同区块。slot0 可能来自 H，active liquidity 来自 H+1，边界 tick 的 liquidityNet 来自 H+2；拼出的状态从未在链上存在。RPC 批量调用只合并传输，不自动把多个 latest 固定到一个状态。

我先选定 header，再让所有读取绑定同一 blockHash。快照至少包含 `chainId、pool、blockNumber、blockHash、parentHash、sqrtPriceX96、tick、liquidity、fee、tickSpacing、bitmap、ticks`，并说明 tick 数据覆盖范围。报价所有中间状态都从这个版本出发，结果也携带版本。所谓“最新”是选块策略，不是允许字段各自追最新；一致但稍旧可解释，混合新旧则没有确定语义。

## 第 2 层：provider 不支持按 blockHash 调用怎么办？

**面试官：** 你依赖哈希锁定，但 provider 不支持 EIP-1898，直接改用区块号是不是一样？

**面试者：** 不完全一样。支持时，对适用的状态查询传 `{"blockHash":H,"requireCanonical":true}`；未知块或已非规范链应处理为错误。所有分批读取都保持 H；如果其中一批失败，不得只对该批回退 latest。

不支持时必须显式选择弱化策略：固定 number=N，读前记录 N 对应哈希 H，所有查询均指定 N，读后再核对哈希。重组发生过又恢复原视图等情形下，前后检查仍不能严格证明中间每次读都来自 H。因此它只是检测性回退，可选更稳定的 safe/finalized 块并标注保证较弱；要求强一致时应拒绝该 provider 或使用能固定分支的节点。重试要重建整份快照，不把不同尝试的字段拼接。

## 第 3 层：固定了一个块，具体还要读什么才算完整？

**面试官：** 哈希一致解决了跨块，但只读 slot0 和池里两个 token 的余额，能否推导后续跨 tick 的价格？

**面试者：** 不能。token 实际余额包含手续费、捐赠等，不等于 active L，更不能直接当恒定乘积模型的虚拟储备。报价要从 slot0 的 sqrtPrice、tick 和独立的 liquidity 出发，再按 bitmap 找 initialized tick，读取对应 liquidityNet；liquidityGross 和 initialized 标记可用于结构校验。

本例到 tick240 时 s=1.012071681663366439，向右跨越后按 liquidityNet 更新 L：A 的 100000 退出、B 的 50000 进入，净变化 -50000。只缓存初始 L 会错算后半段。可以按请求方向懒加载 bitmap words 与 ticks，但每次补读仍锁定同一 H，并记录覆盖范围；目标范围缺失时应报告数据不完整，不能假定 tick 未初始化。fee、tickSpacing 和池身份也必须验证，不能只按地址猜模型。

## 第 4 层：事件带着最终价格，能不能省掉快照读取？

**面试官：** 你还要读不少 storage。如果已有 Swap 事件的末态，直接拿它作为这笔交易的报价起点行不行？

**面试者：** 不行，那是事件所在 swap 的执行末态，不是它的 pre-tx 状态。同一区块后面可能还有 Swap、Mint、Burn；单个事件也未必代表整个区块的最终池状态。完整处理该块事件后得到的状态才可能用于 post-block 投影，并且必须与该 blockHash 的 storage 对齐。

如果要复算某笔交易执行前的报价，仅有块末 eth_call 不够，需要交易级回放或 trace 等额外能力，不能把末态倒置成起点。当前服务选择 post-block 报价快照，不承诺交易前历史重演；事件用于提示失效、维护可覆盖字段与触发补读。重组使 H 失效时，停止把它当作当前可执行状态，但可保留哈希标记的历史结果供排查。

## 第 5 层：不可变快照用了 big.Int，结构体复制够不够？

**面试官：** 你说快照发布后只读，那把含 `*big.Int` 的结构体复制给请求，再修改副本，可以省内存吗？

**面试者：** 结构体复制只复制指针；即使按值复制 big.Int，也可能共享底层字数组，不能把浅拷贝当所有权隔离。map、slice 和其中嵌套的 tick 数值也有相同问题。`Add、Sub、Mul、Quo` 都会写 receiver，接收者绝不能指向共享快照。

工作态需要独立构造，例如 `new(big.Int).Set(snapshot.SqrtPriceX96)`；tick 输入可只读引用，但所有计算输出写入本请求的 receiver，不能对共享值做原地取负。快照构建期间也不得边填 map 边发布。可用内部封装避免暴露可变指针，访问器返回深拷贝或只提供受控读取。额外分配有成本，但靠注释说“只读”不能阻止别名写坏报价。

接口层还要隔离序列化结果与内部对象：返回的金额可以转成最小单位十进制字符串，不能把 scratch 指针直接塞进结果后立即归还复用池。接入时拒绝负输入、越界数值和无效方向，内部始终按整数执行既定舍入；人类单位只用于展示，不能先转浮点数再转回链上整数。这样复制边界、精度边界和对象生命周期才是一套完整约定。

## 第 6 层：多个 goroutine 同时模拟，锁到底放在哪里？

**面试官：** 深拷贝保证了起点隔离，但每个报价会跨多个 tick。如果给整个池加互斥锁，是不是最稳妥？

**面试者：** 给快照发布加短锁或用 `atomic.Pointer` 切换完整对象即可，没必要把所有只读模拟串行化。请求持有某一快照引用后，即使新的快照发布，它仍应沿旧版本算完并返回旧 hash，不在中途换底座。

每个 goroutine 独占 `remaining、calculated、sqrtPrice、tick、activeL` 和全部 scratch big.Int。若用 sync.Pool 复用 scratch，只能在调用结束、返回值已复制且没有其他引用后归还，不能跨 goroutine 复用仍在计算的对象。两个请求从同一初态独立报价，不是把第一个的终态写回共享池让第二个继续；后者是在模拟链上排序，已经换了问题。全局锁虽然容易避免竞争，却牺牲并发且掩盖所有权设计缺陷。

## 第 7 层：缓存命中和 singleflight 会不会重新引入串态？

**面试官：** 你把共享限制为快照，但缓存和 singleflight 都会返回同一个对象，如何防止旧链状态或模型版本被误用？

**面试者：** 快照键至少是 `chainId+pool+blockHash+fee+模型版本`；不同 tick 覆盖范围要有清晰元数据或独立键，不能用一份不完整数据冒充完整快照。报价结果缓存还要加入方向、amount、priceLimit 等影响计算的参数，不能只按池地址缓存一个输出。

singleflight 只合并同键的加载，结果在发布前校验并冻结，调用者仍不能取得写权限。加载失败不发布半成品，也不无限缓存错误；失败重试受退避和并发预算约束。重组后可保留旧 H 的历史缓存，但“当前报价”入口须重新验证选块资格，不因为 TTL 未到就继续使用。版本化键解决身份隔离，不自动解决规范链新鲜度，这两条检查都要有。

## 第 8 层：context 取消后，怎样收尾而不误导用户？

**面试官：** 同键加载正在共享，某个请求超时取消。你会取消加载、回滚结果，还是继续后台计算？

**面试者：** 先区分请求等待者与共享任务。等待者 context 取消就停止等待；共享加载可以由服务级有界 context 控制，避免第一个调用者超时把其他等待者都打断，也不能无限后台占资源。逐步模拟检查取消与步数预算，返回取消或预算错误，不返回半程输出冒充成功。

取消本地报价不改变链状态，更不能撤销已经广播的 swap；若上层已发送交易，仍应按原 txHash 查询。验证时可让两个请求共享 H，各自模拟同一 1500 输入，预期得到同一确定结果且快照保持 tick0、L100000；取消其中一个，不影响另一个。再发布 H+1，旧请求只返回 H 或明确失败，不能出现旧价格配新 liquidity。这是可执行的检查思路，未运行工程测试。

## 收束：讲透、易错与反例

- **讲透：** 区块哈希约束数据来源，不可变对象约束共享方式，独占 scratch 约束计算写入；三者共同保证报价可复现。
- **易错：** 批量 RPC 不自动同块，事件末态不是 pre-tx，实际余额不是 L；浅拷贝 big.Int 也不是深拷贝。
- **反例：** 计算左向跨 tick 时对共享 liquidityNet 原地取反，另一个 goroutine 即使读取同一 blockHash，也会算出被内存污染的错误结果。
