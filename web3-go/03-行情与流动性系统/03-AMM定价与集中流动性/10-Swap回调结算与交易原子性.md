# 大问题 10：池先付出代币再回调收款，怎样保证 Swap 结算与整笔交易的原子性？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文中的含义与边界 |
|---|---|---|
| EVM调用树 / 原子性 | 一笔顶层交易中的嵌套调用，以及失败一起撤销的范围 | 池计算、收付和路由检查在同笔中完成；不含先前独立approve或链下副作用 |
| recipient / payer | 接收输出币的人，以及支付输入币的人 | 本例接收T0、付款T1；回调参数必须符合路由已接受的本次调用，不能开放代付 |
| amount0Delta / amount1Delta | 以池视角表达的两币应收应付变化 | 正数是调用方应付池、负数是池已付出；T1买T0时正常为T0负、T1正，金额含输入费 |
| callback / canonical pool | 池要求付款的回调，以及可信工厂下确定的合法池 | 先验msg.sender、币序、fee和调用上下文再转币，不能信calldata自报地址 |
| allowance / transferFrom | 用户授予花币权限，以及实际扣款 | 授权不冻结余额；付款时仍可能余额或权限不足，直付只扣实际正delta |
| balanceBefore / balanceAfter / owed | 回调前后输入币余额，以及本次必须收足的量 | 要求after≥before+owed；预先捐币不自然抵扣本次欠款，少一原子单位也失败 |
| slot0.unlocked / guard | 同池关键入口的重入开关 | 结算期间限制受保护写入，不是全局锁，也不使临时可读状态变成已确认事实 |
| minOut / 退款检查 | 路由要求的最少输出，以及预充值剩余钱的处理 | minOut1470 T0在池返回后仍可同笔检查失败回滚；必要退款失败也不能吞错 |
| revert / status=0 / gas | 撤销执行效果、失败回执及执行成本 | 失败业务状态和日志不保留，但已入块失败交易仍消耗gas并推进发送者nonce |
| txHash / nonce / 未知态 | 交易身份、发送序号，以及尚不能确定结果的状态 | 超时先找原交易及同nonce替换；链下幂等键挡不住新nonce的第二次Swap |
| canonical / confirmationState | 是否属于当前规范链，以及确认可信进度 | 原子成功不等于最终性，重组要撤销旧包含关系并核实新分支结果 |

## 把整篇文章压缩成一个故事

小林以最多1500 T1买T0，两币18位、输入费0.3%、协议不分成，连续模型预计收约1472.669192 T0，链上按整数执行。路由先查期限，池上锁、计算并转出T0，再回调收T1。这不是赊账：路由先验可信工厂对应的池和付款上下文，再付含费正delta；池验输入余额增量，少一原子单位也撤销这次状态和转账。预先approve只是许可，余额不足仍会失败，同池锁也不等于所有池都锁住。即便池收足款并返回，外层若发现输出仅1469、低于minOut1470，仍须向外revert，不能吞错报成功；预充值退款也在闭环内。失败已入块交易的gas和nonce不会归零，独立授权仍在。后来广播响应超时，后端保留原hash、sender和nonce查链，不换新nonce再买一次。即使查到成功回执，也记录blockHash和确认状态；区块被替换后撤旧观察、查新包含，原子性只保证某次执行整体成败，不保证那次包含永远有效。用户预算不是池应收账，触限时只付实际消耗；事先捐入池的币也不自动抵这笔回调款。池返回、路由成功与链上终局应分别标识。

[返回专题总览](README.md)

**流程位置与核心机制：** 聚焦一笔 swap 交易内部的状态、输出、回调收款和路由检查；广播及未知回执只讨论必要边界，不扩成交易发送专题。

**必要前提：** 公共基线与单位见总览；本题限定标准 ERC-20、可信教学路由和同一笔 EVM 交易调用树。单池 guard 不代表全局锁，独立授权交易也不包含在 Swap 的回滚范围内。

用户 exact-input 最多付 1500 T1 买 T0，即 oneForZero；minOut1470 T0、价格限制 tick420，deadline 由教学路由而非 core 检查。连续数学输出为 1472.669192125127908224 T0，终态 P=1.035994842274346199、tick353、activeL50000。整数按步舍入略异，未声称工程验证。

```text
教学路由检查 deadline → pool.swap 检查并上锁
    → 计算并写入池价格、tick、流动性、费用等状态
    → 向 recipient 付 T0 → 读取池 T1 balanceBefore
    → 回调路由 → 路由验证池身份 → 支付正 delta 的 T1
    → 池检查 balanceAfter ≥ balanceBefore + owed
    → 发出 Swap 日志并解锁 → 路由检查 minOut、处理余款
    ├─ 全部通过 → 本交易效果保留，之后等待链确认
    └─ 任一必要检查失败并向外 revert → 本交易链上效果回滚
```

## 第 1 层：先出币，为什么不等于无担保放款？

**面试官：** 池先把 T0 转给用户，才要求路由付款。如果付款失败，池不是已经损失了吗？

**面试者：** 这个“先后”发生在同一 EVM 调用树内，不是两个独立提交。池锁定后计算交换，写入必要状态，再输出 T0，调用发起者的 swap callback 收款，最后检查输入币余额。检查失败会 revert，先前的状态写入和 T0 转账也被撤销。

因此安全性来自结算检查加 EVM 回滚边界，不是相信路由承诺稍后付款。池成功返回也不是业务最终完成：外层教学路由还要检查 minOut。只有整个顶层交易成功，相关效果才保留；随后是否仍在规范链上属于确认问题，不能用局部函数返回代替。

## 第 2 层：回调中的正负 delta 到底表示什么？

**面试官：** 你说余额检查收款，具体应收多少？是用户声明的 1500，还是池算出的某个 delta？

**面试者：** 看 pool 返回并传给回调的有符号 `amount0Delta、amount1Delta`：正数是调用者应付池的币，负数是池已付出的币。本例 oneForZero，正常有输出时 amount0 为负、amount1 为正；完整消耗时应付约 1500 T1，已付约 1472.669192 T0，链上均为最小单位整数。

若价格限制提前触发，应付只等于实际消耗的正 delta，不是 amountSpecified 的全部上限。正 delta 已包含对应输入手续费，不能回调时再加收一次。池检查的是当前 T1 余额至少比 balanceBefore 增加 owed；允许多付不代表应主动多扣，更不能把未消耗输入记为用户欠池的账。

## 第 3 层：用户已经 approve，为什么付款仍会失败？

**面试官：** 实际欠款明确了，用户事先给路由 1500 allowance，回调是不是就一定能支付？

**面试者：** 不一定。allowance 是支取权限，不是资金预留。用户可能在 swap 执行前花掉余额或改掉授权；实际执行时 `transferFrom(payer,pool,owed)` 才判断权限和余额，教学路由要使用检查返回值的安全转账方式。

钱包直付只扣 owed，未消耗部分留在钱包。若采用预充值路由，则由路由支付并按本次资金记录退余款，不能混用两种账户路径。池在输出后、回调前记录输入币 balanceBefore，所以调用 swap 以前直接向池捐入 T1，不会自然抵掉本次 owed。标准 ERC20 前提简化了到账判断，但不能省略池自己的余额增量验证。

## 第 4 层：付款依赖回调，怎样防止伪造回调盗用授权？

**面试官：** 你让回调执行 transferFrom，攻击者直接调用路由 callback，传入 payer 和正 delta，不就能盗币？

**面试者：** 所以回调先鉴别发送者，后付款。教学路由按可信 factory、排序后的 token0/token1 和 fee 定位 canonical pool，要求 `msg.sender` 等于该池；不能接受 calldata 自报的任意 pool。回调路径、输入币和 payer 还须对应路由已接受的本次调用语义。

仅检查“delta 为正”或用户 allowance 足够都不构成身份校验；反过来，验证 canonical pool 也不代表任意 payer 参数天然可信。外层入口要限定谁能指定付款人，回调不能成为开放的代付接口。验证失败立即 revert，不尝试换地址重试。这里沿用可信部署的教学路由，不把恶意代币兼容性悄悄加进模型。

## 第 5 层：状态先更新，回调期间能否再次交换同一个池？

**面试官：** 身份校验挡住了假池，但真实池回调时，路由或 recipient 还能重入，把尚未收齐款的状态继续交易吗？

**面试者：** swap 入口检查 `slot0.unlocked`，通过后置为 false，结束结算并发出 Swap 事件后才恢复为 true。同池受该 guard 保护的状态修改入口不能在中途重新进入，否则 revert。不能因为 swap 的源码不是直接写一个 lock 修饰器，就说它没有锁。

锁并不禁止读取临时 slot0，也不等于锁住所有池、所有路由。回调中读到的状态尚未越过交易成功边界，不能当成已确认快照。跨池组合调用也不由这个池锁自动保证业务安全；教学路由仍需保护自身资金与调用上下文。收益是允许回调结算，代价是必须同时理解局部锁和顶层回滚，不能只答“有锁所以安全”。

## 第 6 层：输出成功，但回调少付一个最小单位，会留下什么？

**面试官：** 既然锁住了同池写入，假设 T0 已经发出，回调也返回了，只少付 1 wei，池怎样收敛？

**面试者：** 池不以 callback “正常返回”当作收款证明。它读取 T1 balanceAfter，要求 `balanceAfter>=balanceBefore+owed`；少 1 wei 就失败。正常传播的 revert 会撤销这次 swap 的价格、tick、liquidity、feeGrowth、输出和已付输入，并恢复锁状态，不需要异步任务补收这一 wei。

如果路由用低级调用捕获错误，失败的 pool 子调用效果仍回滚，但路由自己先前的预充值、记账等操作未必自动回滚。因此本教学路由不能吞掉结算错误后报告成功，应继续向外 revert，或者明确完成自己所有补偿路径。当前方案选择前者，避免把池级回滚误说成任何外围代码都自动无副作用。

## 第 7 层：池已经收足款，路由 minOut 失败还能撤销吗？

**面试官：** 你把池子调用失败讲清了。若池已解锁返回，路由发现只收到 1469 T0，这时还能回滚池吗？

**面试者：** 能，只要仍在同一顶层交易，教学路由检查 `actualOut>=1470` 失败并向外 revert，已经成功返回的 pool 子调用效果也撤销，相关 token 转账和本交易事件日志一并消失。这里不需要再向池发送一笔“反向交易”。预充值路由若必需的退款失败，也应采用同样的顶层失败语义。

但成功后发生的链下报警不能倒回已提交交易；那是另一条边界。还要区分独立 approve：它若此前在另一笔交易成功，swap 失败不会撤销授权。原子性包住的是当前交易调用树，不是用户最近点击过的所有操作，更不包括链下日志系统已经记录的观察。

## 第 8 层：全部回滚，用户是否就完全没有损失？

**面试官：** 你说代币和日志回滚，那失败交易是否连 gas、nonce 和外部展示都恢复？

**面试者：** 不是。已经被包含、执行失败的普通 EVM 交易仍消耗 gas，发送者 nonce 也前进；回滚的是执行效果，不是把交易从区块里删除。失败回执 status=0，不应从执行 trace 中看到曾经 emit 就生成正式成交记录，回执中也没有可保留的成功业务日志。

链下展示可以保留 `submitted、included_failed` 等观察状态，但必须标出交易哈希、区块哈希和失败原因，不能显示“已成交待补币”。尚未被打包的超时交易则不能直接归为执行失败；如果 RPC 返回不确定，不能据此推断 nonce 已消耗或余额已回滚。恢复要先查权威链事实。

## 第 9 层：广播超时后，为什么不能直接换 nonce 重发？

**面试官：** 那么服务不知道交易是否进入区块，用户又催结果。加一个链下幂等键，再用新 nonce 发同样 swap 可以吗？

**面试者：** 不可以把幂等键说成链上防重复保证。普通 pool 不认识这个键；不同 nonce 的两笔有效交易可能先后执行，形成两次 swap。当前交易可能已广播，只是响应或回执查询丢失。

应保存原始签名交易、hash、sender、nonce，查询原 tx 与 receipt，并核对 receipt 的 blockHash 是否属于当前规范链。必要时跟踪同 nonce 的替换交易；同一账户同 nonce 在同一规范链不能各自成功包含两次，但这不等于每个 hash 都有最终回执。仅凭 mempool 查不到不能断言永远不会执行。这里不扩展发送队列设计，核心是未知结果先恢复原交易身份，而非创建第二个经济动作。

## 第 10 层：怎样闭合“原子成功”和“链上最终可信”的差距？

**面试官：** 你已经查到原交易 status=1，但后来区块被替换。之前的原子性承诺是不是失效了？

**面试者：** 没失效，是承诺范围不同：原子性说明它在某次执行中要么整体成功，要么整体失败；规范链与最终性决定这次执行是否仍被承认。记录应包含 `txHash、blockHash、status、canonical、confirmationState`，重组后把旧包含关系标成 orphaned，再查原交易是否在新链重新包含。

不能因旧回执成功就重复支付链下奖励，也不能因旧回执消失就盲目创建新 nonce swap。手工验证可分别推演回调少付、minOut 失败、成功块被替换三条时序：前两者检查本交易链上效果回滚但 gas/nonce 仍消耗，第三条检查业务观察撤销并按新链恢复。三者不能都用“失败重试”四个字覆盖。

## 收束：讲透、易错与验证方式

- **讲透：** 临时写状态、先输出、认证回调、按正 delta 收款、余额校验与顶层路由检查，共同构成结算闭环。
- **易错：** 锁不是全局锁，allowance 不是预留，pool 返回不是路由终态；独立 approve 不随 swap 回滚。
- **验证方式：** 将付款故意少算一个最小单位，预期没有持久 swap/token/log 效果；再用新 nonce 重发同样意图，预期它仍可能再次成交，证明链下幂等键不能替代链上约束。此为推演，未执行测试。
