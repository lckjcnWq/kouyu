# 大问题 3：08:00 到底按哪份仓位扣费？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 资金费／手续费／借款利息 | 资金费是多空持仓间按规则收付的钱，用于影响持仓激励；不是撮合服务费或借钱利息。 | 本题决定谁承担周期资金费，不按用户成交次数收费。 |
| q、f、M／收付约定 | q 是带方向数量，f 是周期比例，M 是结算参考价。 | 本文多正空负，D=q×M×f、ΔB=-D，正费率多付空收，负费率反向。 |
| F0800／UTC | F0800 是截至 UTC 08:00 的这轮资金费编号。 | 八小时用于定义周期，并不表示每人按持有分钟数交钱。 |
| 结算时点快照 | 只看规定截止位置的仓位来确定本轮资格。 | 屏障前已经平仓可不参与，屏障后平仓仍承担原快照义务。 |
| 逻辑屏障 S5000 | 权威经济事件序列中的一道截止线。 | 它不是成交，不凭“时钟刚好 08:00”读取缓存。 |
| 墙钟时间／提交顺序 | 墙钟是日历时间；提交顺序是经济事实先后成立的位置。 | 点击早、消息先到都不能替代执行域认定的先后。 |
| 前序事件／后序事件 | 截止线之前和之后的经济动作。 | 前序成交先结转；后序成交和划出等待资金费账务提交。 |
| 成交结转 | 将已经确定的成交落实到仓位、现金和费用账。 | 交易已成交但账户尚未处理时，不能先拍不完整快照。 |
| 账户消费水位 | 账户已连续处理到哪个经济事件位置的证明。 | 必须覆盖全部前序义务，不是只看到一条最新消息就算追上。 |
| 单向净仓／逐仓风险单元 | 单向净仓把同一市场多空相抵后的数量记一份，逐仓单元单独核算风险。 | 快照按稳定单元身份列出，不能从挂单自行猜持仓。 |
| 完整清单／平台自营仓 | 完整清单包括该市场全部参与者，也包括平台或做市商自己的仓。 | 三条记录恰好相抵，不代表没有漏掉另一组成对账户。 |
| Σq=0 | Σ 表示求和，全部多空数量应相抵。 | 不为零先查漏项、重项或前序缺口，不能继续生成计划。 |
| 尾差账户 | 承接最小货币单位舍入造成的小额差异的专用账户。 | 不能吞掉 0.5 ETH 之类的数量敞口，更不能凭空造钱。 |
| 仓位版本／账本版本 | 给仓位和资金变化标明已处理到哪一版。 | 快照数量、屏障位置和账本进度要能互相证明。 |
| snapshot_hash／schema | hash 是内容校验指纹，schema 是记录字段的结构约定。 | 清单数量、排序、版本与摘要一起固定，恢复时不换解释方式。 |
| 暂存分片／原子发布 | 大快照可先分块存放，但最后一次性宣布完整内容可用。 | 写了一半的快照不能因进程重启就变成权威输入。 |
| SEALED／READY／APPLIED | 依次表示封存证据、计划验好、资金共同提交。 | 冻结费率、确定仓位归属和真正扣款是不同工作，不能混称“结算成功”。 |
| owner epoch／存储围栏 | 接管任期号配合数据库写入校验，拒绝旧负责人继续改结果。 | 已 SEALED 就复用原快照，旧 worker 复活也不能重拍。 |
| risk_pending／划出门禁 | 风险待确认标记和禁止资金外流的持久限制。 | APPLIED 后风险未确认前，不能提前开放划出和增险。 |

## 把整篇文章压缩成一个故事

1. 甲问：“我在八小时里持有过仓位，08:00 一定要付钱吗？”本文答案不是看持有多久，而是看 S5000 截止线。资金费是多空间的周期转移，不是手续费或借款利息；按本文多正空负的应付约定，正费率多付空收。

2. 执行域先停在屏障，账户把前序成交全部结转，才列出完整仓位。主例甲 +5 ETH、参考价 2,000、周期费率 0.0001，应付 1 USDC。若甲全平已在屏障前提交并结转，本轮快照为零；若平仓排在屏障后，仍按 +5 归属费用，不能拿后来零仓推翻旧账。

3. 快照要连同清单数量、版本和摘要一起发布，漏页或数量不相抵就暂停，尾差账户不能救场。费率证据封存不是扣款，快照只确定资格，完整计划在同库事务 APPLIED 后才改现金。之后恢复只能复用原证据，旧 owner 被数据库拒写；结转不改入场价，也不抹掉平仓前已产生的义务。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于周期输入冻结与金额计划之间，回答谁承担 F0800 费用。沿用总览的 UTC 窗口、链下撮合和内部账本、单向净仓、逐仓风险单元、结算时点快照规则；屏障 S5000 是逻辑事件序号，不是成交。不同于第 2 题决定费率，本题决定资格；绝不改成按窗口内持有时长累计。本文共十层，逐步从屏障顺序追到快照持久化、owner 接管和恢复验证。

## 第 1 层：屏障快照的仓位规则是什么

**面试官：** 甲在 00:00 持仓，07:59 平仓，是否仍付 F0800？请直接说明 08:00 的资格规则。

**面试者：** 本专题选择结算时点快照，不按窗口内持有时长累计。市场执行域在 08:00 建立逻辑屏障 S5000，账户状态完成屏障前全部经济事件后，快照其中各风险单元仓位。窗口中曾经持仓但 S5000 前平掉，快照数量为零，不承担该周期；S5000 后才平仓的仓位仍承担本周期费用。S5000 不是一笔成交，也不是按墙钟取一个“差不多 08:00”的缓存读数；它是可恢复经济顺序上的截止位置。

## 第 2 层：为什么必须先完成屏障之前的所有事件

**面试官：** 你用 S5000 定义截止位置。如果某笔成交的时间戳是 07:59:59，但结转消息还没消费，是否可以先按当前仓位快照？

**面试者：** 不可以只凭时间戳判断。关键是成交在权威执行序列中位于 S5000 前，且对应持仓与账本结转已完成；账户消费水位必须覆盖所有前序事件。否则当前仓位缺少已确定成交，资格清单和 `Σq` 都不可信，周期保持等待并补齐缺口。墙钟时间只帮助定位窗口，不替代已提交顺序。快照的仓位版本、账本版本和屏障位置需彼此可核对；前序结转失败时不能把成交当作不存在，也不能让费用任务另行猜测仓位。

## 第 3 层：S5000 前后到达的成交如何划界

**面试官：** 若一笔成交在网络上迟到，或撮合与费用 worker 并发推进，谁裁定它属于屏障哪侧？

**面试者：** 执行域给经济事件分配可恢复的权威顺序，按提交位置而非消费者到达时间裁定。S5000 前的成交必须在快照前完成账户结转；S5000 后的成交尚不能执行其账户变化，需排在资金费账务提交之后。若单个撮合动作与屏障竞争，执行域必须给出唯一顺序：要么该成交先提交并纳入前序水位，要么屏障先成立而成交留在后序，不能同时进入快照又在账后重放。worker 乱序只能影响处理进度，不能改变已定序列。

## 第 4 层：完整持仓清单需要覆盖哪些对象

**面试官：** 账户仓位服务返回了甲、乙、丙三条记录，数量正好和为零。光看这个结果能证明清单完整吗？

**面试者：** 不能仅凭数量和为零证明完整。清单要按市场和 S5000 水位枚举所有参与资金费的风险单元，包括普通用户、平台或做市商自营仓；每条记录带稳定风险单元身份、仓位数量、仓位版本及账本版本。冻结时保存清单条数、排序规则、摘要和屏障位置，并能证明枚举水位没有缺页或漏分片。零仓可按约定省略或显式记零，但规则必须固定，避免清单数量随序列化方式变化。账户 owner 提供权威仓位，费率 worker 无权从订单或当前缓存自行拼出持仓。

## 第 5 层：总净仓为零的校验发现不平衡怎么办

**面试官：** 清单完整性元数据齐全，但数量合计是 `Σq=+0.5 ETH`。能不能继续扣付，最后把差额塞给尾差账户？

**面试者：** 不应继续。在线性双边净仓基线中，同市场全部仓位应满足 `Σq=0`；不平衡首先意味着漏清单、重复成员、市场/单位错配或未结转成交。尾差账户只平衡金额舍入误差，不能吞掉数量敞口或替平台仓位兜底。周期应停在冻结或计划校验前，定位第一个差异并补齐权威快照，再用同一屏障位置重算完整摘要。只有数量守恒、成员完整、仓位版本连续后，才将快照证据封存并交给计划计算器。

## 第 6 层：快照必须怎样持久化才可恢复

**面试官：** 你检查了完整成员和 `Σq=0`。快照落库时如果数据写完但水位没写，或反过来，怎样避免恢复出一份“看似完整”的状态？

**面试者：** 持久快照要绑定同一个逻辑提交点，至少记录周期与市场、`barrier_seq=S5000`、完整风险单元清单、每项仓位/账本版本、清单数量、数量和、排序规则、内容摘要、规则版本及快照 schema 版本。数据内容与“快照已 SEALED”的阶段标记必须在一个原子提交中成立；若存储设计不能同事务写完，就先写不可见的暂存分片，验证所有分片和摘要，再原子发布清单指针与水位。崩溃留下未发布数据只能清理或续建，不能被恢复程序当作权威快照。

## 第 7 层：快照后平仓仍付费，哪些操作必须等屏障

**面试官：** S5000 快照记录甲为 `+5 ETH`，账务事务尚未提交时用户全平或申请划出，甲最终要不要付本周期费用？

**面试者：** 甲仍按冻结的 `+5 ETH` 承担本周期费用。快照后的平仓是后序经济事件，要等资金费账务提交后才改变账户状态；划出资金也不能抢在已确定的结算义务之前。其他会影响资格或承接能力的操作必须遵守同一屏障协议，不能只停撮合却让提现服务并行清空现金。账务提交之后，风险重算可以异步，但 `risk_pending` 门禁仍阻止增加风险和划出，直到 owner 按新账务版本确认。这里不是按用户持有的分钟数折算费用。

## 第 8 层：worker 乱序或旧 owner 复活时谁能提交快照

**面试官：** 快照 worker 取得 S5000 后暂停，新 owner 接管；随后旧 worker 恢复，并用旧水位提交另一份清单。怎样避免双份快照？

**面试者：** 周期唯一身份、阶段版本、冻结摘要和单调增加的 owner epoch 必须由持久存储在写入时校验。新 owner 接管后，旧 epoch 即使进程仍存活也不得提交状态、清单指针或后续计划；仅在 RPC 层检查租约不够。新 owner 应先读取周期权威状态和执行域水位，若 SEALED 已提交就复用原 `snapshot_hash`，不能按实时仓位重拍；若提交结果未知，先查询原周期记录再决定续做。执行域保持屏障，直到后续结转完成，不能因旧 worker 超时而自动放开市场。

## 第 9 层：故障发生在 SEALED 提交边界两侧怎样恢复

**面试官：** worker 分别在快照写入中途崩溃、SEALED 提交成功但回执丢失、以及账务提交前崩溃，三个情况能否都“重新跑一次快照”？

**面试者：** 不能用一个重跑动作覆盖三个边界。SEALED 之前崩溃时，未发布的暂存快照不是权威结果；接管者在屏障仍有效且前序水位完整的前提下可按同一 S5000 重建。SEALED 已提交但回执丢失时，按周期身份查询并复用原快照摘要，绝不能读取新仓位覆盖它。账务提交前崩溃时则保持冻结快照与计划，按原证据继续；账务已提交但确认未知时先查询 APPLIED。证据不全或摘要冲突就暂停隔离，而不是以重新快照掩盖缺口。

## 第 10 层：用什么边界验证证明快照协议成立

**面试官：** 请给一个能推翻设计的并发与恢复验证序列，特别检查 S5000 附近的成交、平仓和 owner 切换。

**面试者：** 固定一笔成交与屏障竞争，让测试分别建立“成交先于 S5000”和“屏障先于成交”两种权威顺序；第一种必须结转后进入快照，第二种必须延后到资金费之后。再令甲在 SEALED 后平仓，恢复后仍应按原 `+5 ETH` 结算；删除一个账户分片或让 `Σq` 不为零时必须拒绝冻结。随后在快照数据写入、SEALED 提交前后、回执返回前注入崩溃，并让旧 epoch 在新 owner 接管后尝试发布不同摘要；预期是至多一个快照成为权威，且旧写被拒。以上是验证判据，不是已执行测试。

## 本题收束

讲透的是 S5000 前序完成、后序延后、完整账户清单、`Σq=0` 校验、快照与水位原子持久化，以及旧 owner 被存储端围栏。最易错的是用墙钟或消费者到达顺序裁定、用尾差账户掩盖数量不平衡，或改成窗口内持有时长计费。验证反例是快照后平仓且旧 worker 复活：费用仍基于唯一冻结摘要，旧任期不能换一份快照；本文未声称并发测试已运行。
