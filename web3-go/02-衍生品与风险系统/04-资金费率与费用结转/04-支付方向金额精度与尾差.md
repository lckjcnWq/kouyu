# 大问题 4：收付方向、金额精度和尾差怎样确定？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 资金费／手续费／借款利息 | 资金费是持仓多空按规则定期收付的钱，用于调节持仓激励；不是成交服务费或借款计息。 | 本题算这轮资金费的方向和精确金额，不给成交另外定价。 |
| 线性合约／合约乘数 | 线性表示金额随数量和参考价直接相乘；乘数是每份合约对应的单位倍数。 | 本文乘数为 1，q 用 ETH、M 用 USDC/ETH，结果用 USDC。 |
| 带符号仓位 q | 用正负区分多仓和空仓的数量。 | 本文多仓为正、空仓为负，不先把所有数量取绝对值。 |
| 周期费率 f | 本轮名义价值需要收付的比例。 | 0.0001 是本 8 小时周期的万分之一，不是年化，不再乘 8/24。 |
| M／Mark Price | 结算时固定的标记参考价。 | 主例为 2,000，不是用资金费重新改写后的成交价。 |
| D／ΔB | D 是有符号应付，ΔB 是账户现金变化，两者符号相反。 | D=q×M×f，ΔB=-D；按此约定正费率多付空收，负费率反向。 |
| 结算名义价值 | 把仓位换算成计费规模，不是用户实际交出的本金。 | 主例 5 ETH 对应 10,000 USDC 的计费规模，应付仅 1 USDC。 |
| 固定点／q_u、M_u、f_u | 把小数按固定倍数放大后存成整数，后缀 u 表示整数单位。 | 数量和价格各乘 10⁶，费率乘 10¹²，防止浮点末位漂移。 |
| 微 USDC／现金最小单位 | 一个微 USDC 是百万分之一 USDC。 | 现金按 10⁻⁶ USDC 入账，不能直接记比它更小的余额。 |
| raw_num／10¹⁸ | raw_num 是尚未缩放的有符号乘积，分母用于还原为微 USDC。 | raw_num=-q_u×M_u×f_u，再除以 10¹⁸，而不是除后直接当 USDC。 |
| 宽整数／big.Int／溢出 | 中间乘积需要足够大的整数空间，big.Int 可表示任意精度整数。 | 结果能放进 int64 不代表连乘也行；溢出应拒绝整份计划。 |
| trunc_toward_zero／向零截断 | 舍弃不能入账的小数部分，正负都朝零靠。 | 不等于负数向下取整，不能让付款方天然多扣一个微单位。 |
| 风险单元／每周期一次舍入 | 风险单元是一份独立仓位账；舍入按它和周期确定粒度。 | 不按线程、分页或 SQL 批次再舍一次，也不先合并不同用户。 |
| 余数／尾差账户 round_u | 余数是单行未能入账的高精度部分，尾差是全周期的金额平衡项。 | round_u=-Σ用户ΔB_u；不把余数跨周期累积，也不把尾差当隐藏收费。 |
| Σq=0／金额守恒 | Σ 是求和；先确认全量多空数量相抵，再确认用户加尾差金额相抵。 | 金额配平不能证明仓位清单完整，漏仓不能用尾差遮住。 |
| 独立微额例 | 专门观察最小单位舍入的另一个例子。 | +0.000008/-0.000004/-0.000004 ETH 得 -1/0/0 微 USDC，尾差 +1，合计零。 |
| SEALED／READY／APPLIED | 分别固定输入、验好计划、提交资金效果。 | 本题只生成金额计划；冻结费率和仓位归属不等于已经入账。 |
| plan_hash／稳定排序 | 对按固定顺序编码的计划生成校验指纹。 | 换 worker、页大小或重试日期，逐行金额和指纹都应不变。 |
| 不变量／账务归因 | 不变量是每次都必须成立的规则，归因说明这笔钱为何变化。 | 资金费改现金和费用记录，不改数量、入场成本、毛交易盈亏或累计指数。 |

## 把整篇文章压缩成一个故事

1. 甲多仓 +5 ETH，乙、丙是空仓。资金费是持仓双方的周期转移，不是手续费或借款利息。按本文应付 D=q×M×f、现金变化 ΔB=-D 的约定，参考价 2,000、周期费率 0.0001 时，甲付 1 USDC，乙、丙各收 0.6 和 0.4；负费率则方向反转。

2. 计算器拿到的是已冻结费率和屏障仓位，不再查询现在持仓。它用宽整数算每个风险单元，统一向零截断到微 USDC。独立微额例原始收付相抵，截断后用户合计少 1 微 USDC，尾差账户就加 1 微 USDC，双方合计仍为零；这只是精度平衡，绝不是多造一笔钱。

3. 全量仓位不相抵或漏页就停止，不能靠尾差掩盖。计划验好仍未扣款，要等账本共同提交才生效。分页、重试不能改变舍入，快照后的平仓也不能取消既有归属；费用只影响现金与费用记录，不改成交价、仓位数量或历史盈亏。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于快照与费率冻结之后、账务应用之前，决定每个风险单元应付或应收多少，以及舍入后怎样保持金额守恒。与第 03 题的“谁进入快照”不同，本题不重新裁定仓位；与第 05 题的“怎样共同提交”不同，本题只产出可复算的金额计划，不更新余额。

## 第 1 层：先定义符号，资金费方向怎样判断？

**面试官：** 基线里正负仓位和正负费率分别代表什么？怎样直接判断付款方向？

**面试者：** 我先固定现金变化的符号，避免把“应付”误当成正数。`q` 为带符号仓位，多仓为正、空仓为负；`M` 是正的结算参考价；`f` 是本周期带符号费率。定义有符号应付 `D=q×M×f`，现金变化为 `ΔB=-D`。因此 `f>0` 时多仓 `q>0` 的 `D>0`，要付钱；空仓收钱。若 `f<0`，乘积符号翻转，支付方向随之反转。费率是本 8 小时周期的最终值，不再乘 `8/24`。后续讨论都沿用这个符号约定，账本展示的是现金变化而非应付额；若把两者都称为“资金费金额”，就容易把扣款写成加款。主例中多仓应付为正、现金变化为负，必须能从同一公式直接复算出来。

## 第 2 层：README 的整数单位如何落到现金最小单位？

**面试官：** 有了有符号关系，计算怎样转换到 USDC 的最小单位，避免小数误差？

**面试者：** 全程使用 README 约定：`q_u=q×10^6`，`M_u=M×10^6`，`f_u=f×10^12`，现金单位是 `10^-6 USDC`。先算有符号宽整数 `raw_num=-q_u×M_u×f_u`，再得到 `ΔB_u=trunc_toward_zero(raw_num/10^18)`。分母来自三个输入缩放与现金缩放之差。主例 `q=+5、M=2000、f=0.0001` 得 `ΔB=-1 USDC`。不能再按费率年化，也不能在结果上重复乘周期长度。这里 `ΔB_u` 是微 USDC 整数，最终显示 USDC 时才除以 `10^6`；若先把每个输入转成浮点小数再相乘，不同语言或执行顺序可能产生不同末位。

## 第 3 层：为什么必须使用宽整数，怎样证明不会溢出？

**面试官：** 整数乘法仍可能溢出；Go 服务应该怎样选类型和检查边界？

**面试者：** `q_u×M_u×f_u` 的中间结果可能远大于最终微 USDC 金额，不能因为结果能放进 `int64` 就用 `int64` 连乘。先依据允许的最大仓位、价格和费率计算乘积上界，再选能覆盖上界的有符号宽类型；上界不便固定时用 `math/big.Int`，或逐步做溢出检查。转换到数据库整数列前还要检查结果范围。溢出时整份计划失败并保留冻结输入，绝不饱和、回绕或改用 `float64` 得到看似合理的金额。若用定长类型，检查必须发生在每次乘法之前，不能等乘完再判断，因为溢出后的值已经失真；还要测试最大正负边界及最小值取绝对值的特殊情况。

## 第 4 层：向零截断和按风险单元舍入为何重要？

**面试官：** 中间商定后，除法余数怎样处理？为什么不能统一向下取整或按批次先汇总再舍？

**面试者：** 每个风险单元、每个周期仅对其有符号原始值除一次，并向零截断。这样正负值使用对称规则，微额不会因负数向下取整而天然偏向某一方。不能按分页、线程或 SQL 批次先分组舍入，否则切换批大小就会改变结果；也不能先把不同用户的仓位净额合并，抹掉各自收付。原始分子、截断后的入账额和余数都写入计划证据；同一冻结输入在不同 worker 上必须算出同一结果。这不是“每个批次各自找平”，而是逐风险单元先确定金额、全周期汇总尾差；执行顺序改变也不能改变任何一行的舍入结果。

## 第 5 层：出现微额时，尾差账户怎样补平？

**面试官：** 逐风险单元截断后用户金额不再严格零和，怎样让账务仍守恒？

**面试者：** 对所有已校验风险单元算出 `ΔB_u` 后，尾差账户变化定义为 `round_u=-Σ用户ΔB_u`，于是用户与尾差账户的合计变化严格为零。README 的独立例中，仓位为 `+0.000008/-0.000004/-0.000004 ETH`，原始现金变化为 `-0.0000016/+0.0000008/+0.0000008 USDC`；逐单元向零截断后是 `-1/0/0` 个微 USDC，尾差账户记 `+1` 个微 USDC。尾差是精度平衡项，不是可归属给用户的隐藏费用。计算尾差必须使用同一周期完整计划里全部用户的已舍入金额，只生成一个确定的平衡项并纳入该周期 hash；不能在各分页里分别创建尾差行，否则多个局部平衡会相互重复。

## 第 6 层：怎样排除仓位缺失被尾差掩盖？

**面试官：** 若尾差账户总能把金额配平，快照漏了一个账户会不会也被“平衡”掉？

**面试者：** 不会把金额守恒误当作仓位完整性证明。先按同一市场、同一结算屏障核验完整风险单元清单，并要求含平台或做市商自营仓在内的 `Σq=0`；清单数量、摘要或净仓不符就拒绝生成 READY 计划。随后才验证 `Σ用户ΔB_u+round_u=0`。尾差账户只吸收合法仓位按最小货币单位截断后的残差，不能吞下仓位缺口或大额敞口。资金费只改现金及费用归因，不改数量、入场成本、毛交易盈亏，也不改变累计指数。

## 第 7 层：批次拆分、重试和跨周期怎样保持同一金额？

**面试官：** 计划很大需要并行计算，或者同一周期隔天重试，如何避免舍入和结果漂移？

**面试者：** 先从冻结快照生成按风险单元稳定排序的完整计划，所有分片只负责计算分配给自己的行，最终汇总后统一产生尾差账户行；分片边界不参与舍入规则。READY 后保存原始证据、每行金额和 `plan_hash`，worker 重试只能重算同一个 hash，不能读取最新仓位或新费率。每个周期单独截断，余数不跨周期累计，也不挪到下一期抵消；否则交易分拆方式会改变经济结果，并违反本专题逐周期规则。无论物理批次如何并行，单个风险单元的输入、舍入算法版本和输出必须绑定在一起，按固定顺序序列化后计算计划摘要，不受分批影响。

## 第 8 层：计划提交前应验证哪些不变量？

**面试官：** 你会在入账前设置哪些硬校验，发现一个金额不符时怎样处置？

**面试者：** 我会校验单位与版本、所有乘法的溢出检查、快照清单摘要、`Σq=0`、逐单元向零截断，以及 `Σ用户ΔB_u+round_u=0`，再复算 `plan_hash`。可用反例是把 `f` 从正改成负却沿用原付款方向，或把负数截断改为 floor；前者应使全部收付反转，后者会造成方向性尾差。任何校验失败都留在 READY 之前并隔离该周期，不能调费率或篡改累计指数来“配平”。验算还应从同一快照独立重建计划，逐行比较输入摘要、原始分子、入账微单位与尾差；只检查总和为零不足以发现两行互相抵消的错误。

**收束：** 方向由 `q×f` 决定，现金变化取其负数；精度由固定整数单位、宽乘法、向零截断和逐风险单元周期舍入决定。最容易犯的错是让尾差掩盖不完整快照，或改动费率和累计指数来凑平；用符号反转例与微额例即可检验规则是否闭合。
