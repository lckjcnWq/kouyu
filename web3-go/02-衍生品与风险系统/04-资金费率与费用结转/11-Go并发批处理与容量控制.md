# 大问题 11：Go 中怎样处理全量周期结转的容量与延迟？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 资金费／手续费／借款利息 | 资金费是持仓多空间的周期转移，用于影响持仓激励，不是成交服务费或借钱利息。 | 提高吞吐不能改变费用由哪轮仓位承担，也不能让重复任务再扣钱。 |
| q、M、f／周期算一次 | 数量、参考价和周期费率相乘得到有符号应付，现金变化取其负数。 | 本文多正空负、正费率多付空收；+5×2,000×0.0001 付 1 USDC，不再乘周期比例。 |
| S5000／前序水位 | S5000 是资格截止屏障，水位证明前序经济事件已连续处理完。 | 多开 goroutine 不能补出缺失成交；后序经济动作仍等待资金费账务提交。 |
| SEALED／READY／APPLIED | 分别是证据封存、全计划验好、资金共同提交。 | 费率冻结与仓位归属属于输入，纯计算完成也不等于已经改余额。 |
| goroutine／worker pool | goroutine 是 Go 的轻量并发任务，worker pool 用固定数量工作者处理任务队列。 | 只并行计算计划行，不按账户数无限启动任务，也不让各 worker 各自扣款。 |
| 纯函数／不可变输入 | 同样输入必得同样输出，不读取实时状态或修改外部余额。 | 每个风险单元从冻结行算出计划行，规则和单位固定。 |
| 确定性／plan_hash | 确定性要求调度方式改变仍有相同结果；hash 是内容校验指纹。 | 单 worker、多 worker 和不同分页大小都应得到同一规范计划摘要。 |
| 宽整数／向零截断 | 宽整数防中间乘积溢出，向零截断按固定规则去掉最小单位以下部分。 | worker 不能改用浮点数，也不能共享修改同一个大整数对象。 |
| jobs／results channel | Go 中传入任务、传回结果的通信队列。 | 固定队列容量，生产、计算、汇总持续并行，避免只投任务不收结果互相卡住。 |
| 背压／在途窗口 | 下游忙不过来时限制上游继续生产；在途窗口限制未完成工作量。 | 给并发数、页数、单页字节和重排缓存都设上限，而不只限制线程。 |
| context／ctx.Done／select | context 传播取消信号，Done 表示已取消，select 让收发同时响应取消。 | 取消后停止计算并等待收尾，不留下永远等不到消息的 goroutine。 |
| 共享可变累加器／数据竞争 | 多任务同时改同一个总数，若缺乏协调会互相覆盖或产生不稳定结果。 | worker 返回独立结果，汇总端按固定顺序归并数量、金额和摘要。 |
| keyset 分页／OFFSET | keyset 按稳定唯一键续读，OFFSET 按“跳过多少行”分页。 | 只对不可变快照按稳定键读取，不在变化的仓位表上翻页猜完整性。 |
| staging／清单覆盖 | staging 是没有资金效果的计划暂存，覆盖检查确认每个输入都恰好有结果。 | 页可分别保存，缺页、重复页、零金额行都要核对，全部验好才 READY。 |
| 尾差／全周期汇总 | 尾差只平衡合法舍入残差，不是收入来源。 | 逐风险单元算金额，最终统一补尾差，不让每个分页自行造平衡项。 |
| SQL 批处理／事务 COMMIT | SQL 可分批执行，但 COMMIT 才使事务效果对外成立。 | 全周期只共同提交一次，全部分录、余额、去重、门禁与 Outbox 同交。 |
| 取消／提交未知 | 请求停止不证明数据库尚未提交，超时结果可能未知。 | 用独立恢复上下文到主库取周期锁查原结果，未决时不重扣、不放门禁。 |
| p50／p95／p99／长尾 | 分位数描述一组耗时中不同位置，长尾是少数特别慢的任务。 | 分别测快照、计算、锁等待和提交，不能把计划 CPU 快了当作整体更快。 |
| WAL／连接池／热点锁 | WAL 是数据库预写日志；连接池提供有限连接；热点锁是少数记录的高竞争。 | 提交慢可能受日志刷盘或共享账户阻塞约束，不一定靠加 worker 解决。 |
| MQ／跨片原子性 | MQ 是消息队列；跨片原子性要求不同分片的经济效果共同成败。 | 消息都确认不等于一个事务，当前基线不支持多个分片分别入账。 |
| 同一一致性快照／容量边界 | 在同一历史截面核查全部效果，同时承认单库能承受的规模有限。 | 只允许整周期全无或全有；超过实测容量需另设计，本文没有给出实测吞吐。 |

## 把整篇文章压缩成一个故事

1. 系统要给全市场结转资金费，慢了不能先给每个账户开一个并发任务扣钱。这是持仓间的周期转移，不是手续费或借款利息。按本文多正空负的约定，正费率多付空收，甲 +5 ETH、参考价 2,000、周期费率 0.0001 付 1 USDC；快照后平仓也不改旧归属。

2. 先等屏障前事件齐备，封存费率、价格和仓位，再让有限 worker 各算独立计划行。队列和在途页都有上限，结果按稳定键汇总，检查完整清单与全周期尾差，全部验好才 READY。分页是存计划，不是分批生效；换并发度不能换金额或摘要。

3. 只有应用器在同库事务内共同提交全部分录、余额、去重和风险待办，才是 APPLIED。取消或回执丢失先查原结果，不能重扣。若慢在锁或日志刷盘，多加 worker 未必有用；跨片消息确认也不等于原子提交。结转不改成交价、不抹历史，超出单库容量必须承认边界并重设计。

**必要前提与边界：** 基线仍是单个支持事务的关系数据库、全周期资金效果在一个账务事务内提交，市场执行域落实逻辑屏障并等待前序账户事件结转。Go 并发只用于不可变输入上的确定性计划计算；禁止多个 worker 分别入账，以免一个周期半数账户已扣、半数尚未处理。跨库、跨片和链上原子结算不属于当前能力。

**流程位置与核心机制：** 对应 READY 计划生成与 APPLIED 事务的实现容量。先用有界并发提高纯计算效率，再保护完整计划、原子提交、屏障延迟和可恢复性；吞吐优化不能改变周期资金效果的原子边界。

## 第 1 层：先定位周期耗时而不是先加 goroutine

**面试官：** 一个周期有数百万风险单元，结转延迟很高，你会先怎样拆解问题？

**面试者：** 先把端到端延迟拆成等待屏障和前序水位、快照读取、确定性金额计算、数据库锁等待与提交、风险与 Outbox 后续处理，并记录每阶段的持续时间、行数和字节数。并发只可能缩短独立的计划计算，不能缩短缺失的上游成交，也不能让数据库事务自动变快。基线中单库、全周期事务和市场屏障是正确性前提；先找到主耗时和长尾账户，再优化对应阶段，避免线程增加后把 CPU、内存或数据库锁争用放大。

## 第 2 层：哪些工作可以并行而不改变结果

**面试官：** 确认金额计算占主要 CPU 后，怎样把它放到 Go worker pool 里？

**面试者：** 先冻结输入快照和规则版本，把每个风险单元映射为纯函数 `输入行 → 计划行`：宽整数乘法、向零截断、资产单位和单元舍入规则均固定，不读写余额、不取实时仓位、不访问可变配置。worker 只返回带原始序号或稳定风险单元 ID 的结果；汇总端按规范键排序，再统一计算金额守恒、尾差、行数和 `plan_hash`。worker 调度顺序可以变化，结果字节和摘要不能变化；共享可变累加器会引入数据竞争和非确定性，应避免。

## 第 3 层：如何给并发、内存和背压设上限

**面试官：** 如果快照读取速度远高于计算速度，怎样避免 goroutine 和内存无限增长？

**面试者：** 固定 worker 数和 jobs/results channel 容量，另设在途页数及单页字节上限；并发度按 CPU 与内存预算测量，不按账户数启动 goroutine。生产者、worker、汇总者持续流水工作，发送和接收都用 `select` 响应 `ctx.Done()`，避免主线程只投递不收结果造成互相阻塞。生产者关闭 jobs，协调者等待全部 worker 退出后关闭 results，错误统一取消并等待收尾。慢页不能让重排缓存无限增长，应由在途窗口背压或落到持久暂存；宽整数对象也不能在 worker 间共享修改。

## 第 4 层：计划分页时怎样证明整批完整

**面试官：** 全量快照和计划放不进内存，只能分页处理，何时才允许标 READY？

**面试者：** 对不可变快照按稳定唯一键做 keyset 分页，不在变化的仓位表上用 OFFSET 翻页。冻结清单记总行数、键范围、页身份及有序摘要；汇总者用有界缓冲写计划 staging，页重试同身份须同内容，零金额行也纳入覆盖检查。按规范顺序流式汇总摘要、数量和及宽整数金额和，与冻结清单逐键匹配，再补尾差；全部完成才由有效任期协调者标 READY。暂存页可以分次提交但没有资金效果，接管须围栏旧写者并校验缺页，不能第一页算完就扣款。

## 第 5 层：取消与提交结果未知怎样处理

**面试官：** Go 请求超时触发取消，但数据库可能刚好提交成功，怎样避免再次扣款或提前放开市场？

**面试者：** 计算取消只留下可校验的暂存页，不代表已入账。READY 后由唯一应用器开启事务，锁周期行并校验任期、摘要、屏障和预期版本，按稳定键顺序锁资金行；可分批执行 SQL，但全周期只 COMMIT 一次，分录、余额、幂等、APPLIED、risk_pending、缓冲与 Outbox 同交。提交超时只能记结果未知：用独立恢复上下文到主库获取周期锁，等待旧事务定局；APPLIED 且同摘要就返回原结果，确认回滚且仍 READY 才重试。未决时保留门禁，不能因一次非锁查询未见 APPLIED 就重扣或放行。

## 第 6 层：单库全周期事务的热点怎样量化

**面试官：** 线程扩展后 CPU 利用率提高了，但提交延迟反而变长，下一步怎样定位？

**面试者：** 分开观测快照读取、计算、计划持久化和 APPLIED 事务的 p50/p95/p99、行数、事务持续时间、锁等待、死锁、WAL 生成与刷盘、连接池等待、复制延迟和热点账户分布；这些是要采集的指标，不预设数值结论。数据库阶段可检查执行计划与索引、减少重复读取、按稳定键批量处理并统一加锁顺序，但不能为了缩短事务把全周期效果拆成多个独立提交。若风险单元集中到少数账户，锁热点是真实约束，应先做针对性测量和容量上限，而不是盲目加 worker。

## 第 7 层：数据库承载不了时能否用消息队列分片

**面试官：** 单库事务已经达到容量边界，能不能让每个分片消费者处理一批账户，消息都成功就认为周期原子完成？

**面试者：** 不能。队列确认只能说明各消费者处理了消息，不能把不同分片的余额、账本、幂等与风险门禁变成同一个原子提交；中途一个分片成功、另一个失败会暴露周期半成品。当前方案明确不支持跨片资金费提交，超过经过测量的单库规模就停止扩容承诺并重新设计状态归属。若未来改变前提，必须另行定义跨片清算在途、全局周期状态、用户可用性门禁和足额资金／损失保障，以及补偿或终局裁决；消息队列本身不能替代这些机制。

## 第 8 层：怎样验证容量控制没有牺牲正确性

**面试官：** 这套并发批处理何时算可交付，最关键的反例验证是什么？

**面试者：** 验证时分别测量计划计算与数据库提交的资源曲线、锁等待和屏障暂停时间，并检查单 worker、多 worker、不同分页大小的规范计划内容及摘要一致。故障注入覆盖缺页、重复页、worker 中断、取消、提交前崩溃、提交后回执丢失及 Outbox 延迟；同一权威一致性快照内只能看到全周期无资金效果，或全部效果与门禁共同 APPLIED。机制收束是有界并行只优化计划，单库事务才决定资金成立；易错边界是用 MQ 确认代替原子。反例是在同一快照中出现半周期入账，这即失败；跨越提交点的两次独立读取不算该反例。
