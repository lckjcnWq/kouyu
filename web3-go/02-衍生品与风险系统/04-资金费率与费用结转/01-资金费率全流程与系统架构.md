# 大问题 1：一次资金费从触发到关闭怎样走完整链路？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 永续合约／ETH-USDC 线性永续 | 没有固定到期日的衍生品；这里按 ETH 数量计算、用 USDC 记钱。 | 合约乘数为 1，不是买入多少名义价值就支付多少本金。 |
| 资金费／手续费／借款利息 | 资金费用周期收付影响持仓激励，帮助永续价格贴近参考市场；它不是成交服务费，也不是借钱的利息。 | 本文是持仓多空之间的转移，不能当作平台每次成交的收入。 |
| 多仓、空仓与 q | 多仓偏向受益于上涨，空仓偏向受益于下跌；q 用正负号区分方向。 | 本文多仓为正、空仓为负，主例甲为 +5 ETH。 |
| f、M、D、ΔB | 分别是周期费率、结算参考价、有符号应付和现金变化。 | D=q×M×f，ΔB=-D；按本文约定，正费率多付空收，负费率反向。 |
| 周期／UTC／cycle_id | 周期是一轮费用；UTC 是统一时区；cycle_id 是这轮业务的固定编号。 | 每 8 小时一轮，F0800 指截至 08:00 的原周期，重试不能另起编号。 |
| 逐仓风险单元 | 单独核算一份仓位抵押和风险的小账本。 | 金额按风险单元计算，不把不同用户先合并成一个净额。 |
| 观察窗口／溢价样本 | 在规定时间内收集永续报价与指数价的偏离程度。 | 样本决定费率，不直接决定谁有资格付费。 |
| 调度器 | 到点发起任务的系统组件。 | 它登记周期和屏障意图，没有决定仓位或直接扣钱的权力。 |
| 权威状态／owner | 最终说了算的持久记录，以及负责推进这份记录的组件。 | 行情管费率证据，执行域管顺序，账户 owner 管仓位，账本管资金生效。 |
| 逻辑屏障 S5000 | 在经济事件队列上划一道可恢复的截止线。 | 不是一笔成交；前序必须结转完，后序经济动作等资金费提交。 |
| 消费水位／完整性水位 | 证明数据已处理到哪个位置，而不只是“等了多久”。 | 成交或样本还有缺口时不能先用缓存封存结果。 |
| 持仓快照 | 保存截止线处每个参与单元的仓位及版本。 | 决定本周期费用归属，不按窗口内持有分钟数累计。 |
| WAIT_INPUT／SEALED | 前者等齐证据，后者封存规则、费率、价格和仓位证据。 | SEALED 表示输入固定，不表示现金已经扣除。 |
| FundingPlan／READY | FundingPlan 是逐项收付清单；READY 表示完整计划已验好。 | 先算齐再入账，计划生成器不能边算边改余额。 |
| plan_hash／摘要 | 给规范内容算一个校验指纹，用来发现载荷变化。 | 同周期不同指纹应隔离，不能借重试改费率或换仓位。 |
| Σq=0／尾差 | Σ 是求和；全市场多空数量应相抵，尾差只处理最小货币单位的舍入残差。 | 数量漏项不能塞给尾差账户；用户与尾差账户的金额变化合计须为零。 |
| 分录／同库事务／APPLIED | 分录记资金来路去处；事务让一组修改全成或全不成；APPLIED 是已生效标记。 | 全部收付、余额、去重与待办共同提交，才承诺真正入账。 |
| 幂等／效果键 | 同一业务重复执行，不能产生第二次经济效果。 | 每个风险单元的周期费用有固定身份，回执丢失也不能再扣一次。 |
| Outbox／risk_pending | Outbox 是同事务保存的待发通知；risk_pending 是风险尚待确认的持久标记。 | 入账后可补发通知，但增险和划出门禁不能因通知延迟提前解除。 |
| CLOSED／同水位核对 | CLOSED 表示规定的核对与风险确认完成；同水位指比较同一处理截止位置。 | 不承诺所有页面同时刷新，也不表示历史以后绝不会需要追加调整。 |
| owner epoch／围栏 | epoch 是接管任期号；围栏要求存储端拒绝旧任期写入。 | 换 worker 只能续做原周期，不能产生另一份有效结果。 |

## 把整篇文章压缩成一个故事

1. 甲做多 5 ETH，乙、丙分别做空 3 和 2 ETH。永续没有到期日，系统用资金费影响多空持仓激励，而不是收成交手续费或借款利息。按本文符号，正费率由多方付给空方；参考价 2,000、周期费率 0.0001 时，甲应付 1 USDC，乙、丙各收 0.6 和 0.4。

2. 到了 08:00，调度器不能直接扣钱。执行域先停在 S5000，账户补齐前序成交，费率域补齐窗口证据，随后一起封存费率、参考价与仓位。封存是确定依据，完整计划验好是准备完成，两者都不是已入账。

3. 账本用一个数据库事务共同登记全部收付、余额、去重和风险待办，提交为 APPLIED 后现金才变化。通知丢失就补发，不能再扣；风险确认和同水位核对完成才关闭。快照后平仓不免掉已归属费用，当前零仓也不能推翻旧快照；结转只改现金和费用记录，不改成交价或抹掉历史。

**流程位置与核心机制：** 本题覆盖费率观察、周期冻结、资格快照、计划生成、资金入账到核对关闭的端到端链路，重点是每个事实由谁拥有、何时成为权威，以及“完成”分几层。沿用总览的链下托管、ETH-USDC 线性永续、单向净仓、逐仓风险单元与同库事务基线；具体费率公式见第 2 题，S5000 的仓位边界见第 3 题，账务原子细节和恢复协议分别留给第 5、6 题。

## 第 1 层：先把一周期业务从头到尾讲完

**面试官：** 一次资金费不是用户下单触发的普通扣款。请从周期开始讲到可以关闭，说明这条业务链实际经过什么。

**面试者：** 在这个教学模型中，ETH-USDC 线性永续每 8 小时结算一次。价格管道按 UTC 窗口积累报价与指数样本，费率计算器按固定规则得到带证据的最终费率；到期调度器为稳定周期身份创建结算任务并请求市场执行域停在逻辑屏障。账户域消费完屏障前经济事件后，冻结费率、参考 Mark 和全量持仓快照。计算器据此生成并校验不可变计划，账务应用器在同库事务内提交全部分录、余额、去重、APPLIED、风险待办和 Outbox；随后解除屏障，风险及查询投影追上并核对，满足条件才 CLOSED。

## 第 2 层：周期任务已创建，哪些状态分别由谁负责

**面试官：** 你说调度器创建结算任务。若它只能发起流程，周期、费率、仓位和现金的权威状态分别归谁？

**面试者：** 调度器只持久化稳定 `cycle_id`、窗口结束时刻和屏障意图，不决定费率或用户资格。行情/费率域负责样本来源、规则版本及最终费率证据；执行域负责权威经济事件顺序和屏障位置；账户 owner 负责按该位置形成仓位、现金及版本；账本应用器是唯一能把计划变成资金效果的写入方。风险结果、查询页和消息投影只是派生状态。这样同一周期的费率不是从仓位缓存推导，仓位也不是由调度 worker 根据当前时间猜测。

## 第 3 层：不同阶段的“完成”分别承诺了什么

**面试官：** 既然状态由多个域拥有，`WAIT_INPUT`、`SEALED`、`READY`、`APPLIED`、`CLOSED` 能否都对外说“结算成功”？

**面试者：** 不能。`WAIT_INPUT` 仅说明周期身份和屏障意图已接管，前序输入可能未齐；`SEALED` 才冻结费率、参考价、规则及仓位证据，但尚未扣款；`READY` 表示整份计划校验通过，现金仍未改变。只有 `APPLIED` 的共同事务提交才成立资金效果；它同时留下幂等身份、`risk_pending` 和结果 Outbox。`CLOSED` 则表示账务同水位核对通过、必要风险确认完成，不代表查询页面永不延迟。暂停保留原阶段并附原因，不能抹记录另开周期。

## 第 4 层：SEALED 的输入不全，为什么不能先算一部分

**面试官：** 如果费率窗口只缺一个槽，或账户前序成交消费到 S4999 但还有一笔待处理，能否先用现有数据生成快照，再补剩余部分？

**面试者：** 不能把不完整输入包装成最终结果。费率窗口缺槽、报价陈旧或完整性水位未达标时留在 `WAIT_INPUT`，不能缩小分母或默认为零；前序成交未结转则账户状态尚未达到屏障，不能快照缓存。只有数据管道证明窗口完整、执行域停在 S5000 且账户消费水位覆盖全部前序事件，才冻结同一组规则、费率、Mark 和仓位版本。否则补入迟到成交会改变谁有资格，补入费率样本又会改变所有收付金额。

## 第 5 层：冻结输入后，怎样从资格得到完整计划

**面试官：** `SEALED` 已经固定输入，但还没有入账。如何确保它能转成一份完整、可检查而不是边算边扣的计划？

**面试者：** 计算器读取冻结快照和最终周期费率，为每个风险单元生成有符号应付、按总览精度规则得到的入账额，并形成尾差平衡项。计划包含周期身份、证据摘要、快照摘要、逐项金额与 `plan_hash`；按稳定风险单元顺序计算，检查全量清单数量、`Σq=0` 和用户加尾差账户的金额守恒。分页只可用于物化计划，不能第一页算好就扣款。计划校验失败时仍未产生经济效果，可用原冻结输入重建；同周期不同摘要则是冲突，不是正常重试。

## 第 6 层：计划正确，何时才真的改变账户资金

**面试官：** 既然计划可复算，账务服务逐条写分录、失败后继续下一条是否也能达到相同余额？

**面试者：** 不行，用户不能看到先扣款而收款方尚未入账的半批状态。总览基线把全部参与单元、尾差账户、余额、资金费累计、效果去重、周期 `APPLIED`、风险待办和结果 Outbox 放进同一关系数据库事务。事务检查周期与计划摘要、屏障凭据、状态版本和稳定效果键；任何一项失败便整体回滚。只有共同提交才对外承诺资金已结转。这里的原子性限于这个单库教学规模，不能把跨库 RPC 或消息队列说成同一数据库事务。

## 第 7 层：APPLIED 已提交，风险服务或回执却没有跟上

**面试官：** 事务已经提交，但风险消费者离线，调用方也没收到成功回执。周期要不要回滚，或者换 worker 再扣一遍？

**面试者：** 都不应做。`APPLIED` 是不可因通知失败撤销的经济事实；调用方按原周期身份和计划摘要查询原结果，Outbox 按原事件身份补发。风险待办持续保留，增加风险和划出资金的持久门禁不能提前解除；风险 owner 按账务版本重算并确认后才解禁。事务提交前崩溃则无部分分录，按冻结计划重试；提交后响应丢失则查回原提交。查询投影可以暂时落后，但不能据此再造一笔资金效果。

## 第 8 层：worker 乱序接管或周期关闭时怎样证明链路收敛

**面试官：** 两个 worker 因租约切换同时推进，一个拿着旧输入，一个看到风险事件尚未到达。怎样避免它们把周期推进成两个结果？

**面试者：** 周期唯一键、状态版本、冻结摘要和存储端 owner epoch 共同约束推进；worker 只能提交与当前阶段匹配的同一周期载荷，旧任期写入应被拒绝。市场屏障及风险门禁是持久业务状态，不是某个 worker 的内存锁。新 worker 先查询 `WAIT_INPUT` 到 `APPLIED` 的权威阶段，再按原证据续做；若账务已提交则只补事件、核对后关闭。差异不能覆盖原计划，应隔离并走追加调整流程。更细的抢锁、Outbox 重投和并发测试属于第 5、6 题，本题只定义端到端承诺。

## 本题收束

讲透的是权威状态分域、冻结输入后计划、`APPLIED` 才改变资金、`CLOSED` 还需核对的分层承诺。最易错的是把任务触发、`SEALED`、RPC 成功或页面刷新说成结算完成。可用“前序成交缺口”及“提交成功但回执丢失”做反例检查：前者不得快照，后者不得重复扣款；本文描述设计验证条件，不声称已运行测试。
