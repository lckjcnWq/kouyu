# 大问题 7：平仓、强平和资金费同时发生时谁先执行？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 资金费／手续费／借款利息 | 资金费通过多空持仓间的周期转移调节持仓激励，不是成交服务费或借款利息。 | 平仓成交可能另有手续费，但不能把它与本轮资金费混成一项。 |
| q、M、f／支付方向 | q 是带方向数量，M 是参考价，f 是周期费率。 | 本文多正空负，D=q×M×f、现金变化为 -D，正费率多付空收，负费率反向。 |
| 平仓／减仓 | 平仓把现有数量降到零，减仓只减少一部分风险敞口。 | 已归属的周期费用不会因随后数量减少或归零自动消失。 |
| 强平 | 风险系统在不再满足规则时，受控执行减仓等处置。 | 不是一句“强平优先”就可以越过经济顺序或免除资金费。 |
| 反向成交／过零 | 反向成交可能先减掉原仓，再建立相反方向的新仓。 | 从 +5 卖 7 是先平 5 再开空 2，后两份不能冒充纯减仓。 |
| S5000／逻辑屏障 | 权威经济事件顺序里的截止位置，不是一次成交。 | 前序成交结转后才快照，后序经济动作等资金费提交。 |
| 结算快照／时点资格 | 保存截止位置仓位，决定该周期由谁收付。 | 不按八小时内持有多久折算，点击时间和网络到达时间也不裁定资格。 |
| 订单受理／实际成交 fill | 受理仅表示收到命令，fill 才是已经确定的成交事实。 | 挂单未成交不能当作已经平仓；已成交但消息迟到则必须补齐结转。 |
| order_id／fill_id／source_seq | 分别标识订单、单笔成交和成交在源序列的位置。 | 用这些证据关联真实执行和账户进度，不凭客户端界面猜仓位。 |
| 账户应用水位／UNKNOWN | 水位证明账户已处理到哪里，UNKNOWN 表示结果尚未查明。 | 有缺口或未知就查询原事实，不能按“应该没成功”重发经济动作。 |
| SEALED／APPLIED | SEALED 封存费率和仓位证据，APPLIED 表示资金事务共同提交。 | 屏障不是扣款点，封存归属与实际扣款也不是同一阶段。 |
| 持久接收／允许执行 | 命令可以先排队保存，不等于允许立即成交或释放现金。 | 屏障后平仓可等待，但不能先执行并让用户提空资金再补旧费。 |
| risk_pending／增险门禁 | 风险待确认期间保留的权限限制。 | APPLIED 后可按序处理合格减仓、撤单，但增险与划出仍等待风险确认。 |
| 预留／撤单终态 | 预留是为在途订单占住资金，终态是权威确定撤单已完成。 | 发出撤单请求不等于能释放全部预留，须防在途成交未结转。 |
| position_version／cash_version | 仓位与现金的状态版本。 | 资金费只改现金，也能让原强平决策的依据过期。 |
| price_id／rule_version | 标明风险判断引用哪份价格和规则。 | 执行端不能只在 RPC 入口看一次，最终裁决前还要核对当前版本。 |
| case_id／action_id／RECHECK | 前两者标识处置案例和具体动作，RECHECK 表示旧许可须重新检查。 | 重决策前先查原动作已成交量与未知余量，不能再按旧目标卖一次。 |
| 可减量 | 当前真实仓位允许减少的最大数量。 | 用户已减 3、原多仓剩 2，旧卖 5 的强平不得把账户卖成空仓。 |
| 两类 owner_epoch／围栏 | 资金费负责人任期与风险单元处置负责人任期各有归属。 | 接管周期不等于获得强平权，存储和执行端分别校验所属任期。 |
| Outbox／效果去重 | Outbox 持久保存待发通知，去重确保同身份只产生一次效果。 | 回执或通知丢失时恢复原记录，不撤销已提交费用或重复平仓。 |

## 把整篇文章压缩成一个故事

1. 甲持有 +5 ETH，临近 08:00 请求平仓，同时风险系统也准备强平。资金费是持仓间周期收付，不是手续费或借款利息；按本文多正空负的约定，正费率多付空收。参考价 2,000、周期费率 0.0001 时，屏障仓位若仍是 +5，甲就应付 1 USDC。

2. 谁先不是看谁先点击，而是看成交在 S5000 哪侧。屏障前全平且结转完，快照才为零；仅收到“已受理”不算平仓。费率和仓位证据封存后先做完整资金费事务，APPLIED 才改现金，后序成交随后执行；甲再平仓也不能免掉这 1 USDC，费用不改原成交价。

3. 账务提交后风险仍待确认，不能先放开划出或反向开仓。若用户先减 3 ETH，旧强平仍想卖 5，就必须按新现金、仓位版本复核，最多处理有效可减的 2，不能卖成空仓。接管和超时恢复都查原身份，旧任期不得写入，未知成交也不能靠再造动作掩盖。

**必要前提：** 沿用总览的链下托管、ETH-USDC 线性永续、单向净仓和逐仓风险单元。F0800 的屏障为 S5000，不是成交；屏障前成交必须先完成账户结转，屏障后经济动作等待资金费账务提交。主例甲为 +5 ETH，应付 1 USDC。以下平仓、部分成交和反向成交均为明确比较顺序的独立变体，交易对手的成交与仓位也同步结转，不把它们叠加回原三账户快照。

**流程位置与相邻题边界：** 03 题负责屏障与完整快照的建立，05—06 题负责账务原子提交及恢复；本题接着讨论命令资格、接管围栏与旧强平许可。08 题再解释资金费提交后的风险重算。本题不改成持有时长累计，也不增加“强平优先所以免资金费”的例外。

## 第 1 层：以经济屏障而非墙钟裁决先后

**面试官：** 平仓、强平和资金费同时发生时谁先执行？用户说自己在 07:59:59 点了平仓，你会据此免掉 F0800 吗？

**面试者：** 不会。先后由可恢复的权威经济顺序与 S5000 决定，不由点击时间、网络到达时间或 worker 启动时间决定。成交若排在屏障前，账户必须先完成相应仓位、现金和手续费结转，资金费才按结转后的仓位封存快照；屏障后的成交则先等资金费 APPLIED。主例甲在屏障快照仍为 +5 ETH，就承担 1 USDC，之后平仓不改这项义务。屏障本身不是扣款提交点，执行域必须真正停在边界，不能只有资金费程序停止读数，而撮合仍继续产生屏障后的成交。

## 第 2 层：用成交提交与账户水位区分受理和平仓

**面试官：** 你要求屏障前的平仓先结转，但用户收到“订单已受理”，账户服务仍没看到结果。该把仓位置零，还是继续等待？

**面试者：** 受理只说明命令进入处理，不证明已成交。要关联 `order_id`、`fill_id`、成交 `source_seq` 与账户已应用水位：成交若已经权威提交在 S5000 前，就必须补齐其双边结转，不能因消息迟到而漏进快照；若只是挂单未成交，就仍按真实持仓计费。独立变体中，甲的 5 ETH 全平在屏障前提交并结转，快照数量才是零。若成交结果 UNKNOWN 或前序水位有缺口，保留屏障并查询权威记录，不能凭“看起来已平”或当前缓存零仓封存。版本与完整清单对齐，才有排除该仓位的证据。

## 第 3 层：反向成交按实际数量归属且不绕过增险门禁

**面试官：** 若查到的不是全平，而是甲从 +5 ETH 发出卖出 7 ETH 的反向单，你怎样把它接到刚才的屏障规则上？

**面试者：** 比较三个独立时序：7 ETH 全在屏障前成交并结转，甲快照是 -2 ETH，应收 0.4；仅 3 ETH 在屏障前结转，快照是 +2 ETH，应付 0.4；全部排在屏障后，F0800 仍按原 +5 ETH 收 1。每种情形都要纳入交易对手，维持全量净数量为零，不能固定乙、丙不动。屏障后的反向单也不能因为前 5 ETH 是减仓，就自动放行过零后的 2 ETH 开空；APPLIED 后 `risk_pending` 未解除时，增险部分仍被阻止，严格减仓部分按权威剩余量执行。

## 第 4 层：持久接收平仓不等于允许经济效果越过屏障

**面试官：** 你说严格减仓可以按序处理。S5000 已封存，甲急于全平，能否先成交并释放现金，稍后再按旧快照补扣那 1 USDC？

**面试者：** 不能，这会偷换总览的执行顺序。资金费 APPLIED 前，市场执行仍停在 S5000；可以按接入协议持久接收后续命令，但不能提前执行屏障后的成交或划出。否则用户可能平仓后移走全部抵押，再留下无法承接的旧周期费用。资金费事务提交后，市场屏障才允许有序推进；风险待重算的门禁继续阻止划出和扩险，不妨碍按账户 owner 顺序处理合格撤单、减仓。撤单也必须等权威终态才释放剩余预留，不能以等待太久为由假定撤单成功或在途成交不存在。

## 第 5 层：旧强平许可须在最终执行边界重新复核

**面试官：** 资金费提交后才轮到强平，但强平命令引用的是提交前现金。若用户先有一笔减仓，执行端还能按旧目标继续卖吗？

**面试者：** 不能。命令需带 `case_id、action_id`、风险单元 `owner_epoch`，以及决策引用的 `position_version、cash_version、price_id、rule_version`。资金费只改现金也会使原许可过期；先有减仓则仓位版本也过期。执行前在权威裁决边界复核当前输入；旧版本返回 `RECHECK`，不能只在 RPC 入口读一次后无条件下单。若仍需强平，先确认原 action 没有已执行或 UNKNOWN 的余量，再以新决策接续动作，原载荷不可偷改。最终撮合还要校验当前可减量，避免用户减仓和旧强平共同把多仓卖成空仓。

## 第 6 层：分别围栏资金费 owner 与风险单元接管权

**面试官：** 旧命令需要检查 owner。若屏障期间资金费 worker 切主，同时风险单元被强平协调者接管，这两个 epoch 是同一个东西吗？

**面试者：** 不是。`FundingCycle.owner_epoch` 约束谁能推进 F0800；风险单元或强平案例自己的 `owner_epoch` 约束谁能发有效处置命令，二者不能串用。资金费新 owner 接续原 `cycle_id、barrier_seq、plan_hash`；已 SEALED 的快照原样读取，未封存则仍要证明同一屏障前沿完整。风险接管则按该单元权威顺序提交处置权、权限状态与新任期，并检查当前经济版本；接管本身不改变仓位、不免除资金费。各自存储提交面都验证所属 epoch，旧主即使复活也不能写；接管后未执行旧命令重新复核，已提交成交则继续可靠结转。

## 第 7 层：提交结果未知时先恢复原事实再推进命令

**面试官：** 新 owner 查到资金费事务曾经超时，无法判断是否 APPLIED；旧强平 action 的响应也丢了。怎样恢复而不再次扣费或再次平仓？

**面试者：** 分别按原身份查权威提交证据。F0800 若已 APPLIED 且 `plan_hash` 一致，返回原账务结果，以其版本有序推进屏障后命令；确定未提交才用冻结计划重试。证据暂不可得，就保持屏障及限制，不把超时当作未提交。强平 action 同样先查累计 fill、剩余执行资格和账户应用水位；已有成交必须结转，未知余量不能另造 action 覆盖。资金费账务、去重、`risk_pending` 和 Outbox 同事务，因此事件通知丢失只需补发，不撤销已提交费用。恢复的对象是原周期、原动作和实际成交，不是重新快照或按旧目标再卖一次。

## 第 8 层：用交错序列检验顺序、围栏与减仓上限

**面试官：** 你分别恢复了周期和 action，怎样验证它们组合后仍正确？请给出足以推翻设计的交错，而非只检查最终 CLOSED。

**面试者：** 可推演：甲 +5 ETH 已入 S5000 快照，资金费 APPLIED 回执丢失；等待中的用户减仓先减少 3 ETH，旧强平命令仍要求卖 5 ETH；随后旧 owner 复活重发。正确结果是资金费仍只扣 1，旧账务任期拒写，强平先查询原动作并按新版本复核，最多处理当前仍有效的可减 2 ETH，不得开出空仓。另对比屏障前全平应为零仓快照，屏障后全平仍付 1。核对冻结摘要、连续成交水位、每个 fill 只结转一次及风险门禁未被提前解除；任一不符便能定位到顺序、幂等或执行资格缺口。

## 本题收束

- **机制：** S5000 固定费用资格；APPLIED 决定资金效果；后续命令以当前版本和所属任期取得执行权。
- **易错边界：** 用受理时间代替成交顺序，凭减仓意图放行反向开仓，混用两类 epoch，或接管后改写原快照。
- **反例检验：** 已封存 +5 ETH，若屏障后全平能先释放现金，或旧 5 ETH 强平能在用户已减 3 ETH 后继续全卖，屏障和最终执行门禁均不成立。以上为教学推演，不是生产经历或故障测试结果。
