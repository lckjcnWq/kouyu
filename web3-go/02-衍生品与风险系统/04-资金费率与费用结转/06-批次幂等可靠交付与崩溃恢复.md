# 大问题 6：重复调度、回执丢失和崩溃怎样恢复？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 资金费／手续费／借款利息 | 资金费通过持仓双方周期收付影响持仓激励，不是成交服务费或借款计息。 | 任务重复触发不代表又产生了一轮新费用。 |
| q、M、f／收付符号 | q 是带方向数量，M 是参考价，f 是周期费率。 | 本文多正空负，D=q×M×f、ΔB=-D，正费率多付空收，负费率反向。 |
| F0800／cycle_id | 对市场和周期结束时刻确定的固定业务编号。 | 回执丢失仍查原 F0800，不能用新 UUID、启动时间或重试次数当新周期。 |
| effect_key／风险单元 | effect_key 标识一项经济效果，风险单元是一份独立仓位风险账。 | 一个周期有多条“单元／USDC／资金费”效果，不能只用周期编号代替每行身份。 |
| event_id | 一条待交付通知的固定编号。 | 通知身份不等于费用身份，重复收到通知不能再次收付资金。 |
| payload_hash／plan_hash | 前者校验某载荷，后者校验完整计划内容。 | 摘要用来发现同身份内容变化，不代替固定业务键另造经济效果。 |
| 幂等／去重 | 同一件事调用多次仍只有一次业务效果。 | 相同键相同内容返回原结果，相同键不同内容必须隔离。 |
| SEALED／READY／APPLIED | 分别表示证据封存、计划验好、资金提交。 | 原费率和仓位归属已固定也可能还未入账，恢复不能把阶段混为成功或失败。 |
| 不可变快照／规范编码 | 保存原截止仓位，并按固定字段、单位和顺序描述输入。 | 重试不用当前仓位或新配置，排序差异也不能凭空制造不同摘要。 |
| 同库事务／COMMIT | 把全部资金分录、余额和控制记录作为一个提交整体。 | 去重、APPLIED、风险待办和 Outbox 也在同一提交边界内。 |
| Outbox／Relay | Outbox 是账务同事务保存的待发箱，Relay 是把通知送出去的转发者。 | 先持久保存再可靠补发，转发者崩溃不会要求撤销原资金效果。 |
| 至少一次／exactly-once | 至少一次允许重复交付；exactly-once 是“恰好一次”的更强承诺。 | 消息发送成功不等于端到端只处理一次，需要各处理域自己防重。 |
| inbox／本地副作用 | inbox 是消费者的已收事件表，副作用是更新本地风险或投影等结果。 | 事件去重与本地修改共同提交；外部副作用还需要外部幂等身份。 |
| 提交未知／回执丢失 | 客户端没得到答案，但数据库可能已经成功。 | 超时不是未提交证明，不能立即重扣或放开资金门禁。 |
| 周期行锁／独立恢复上下文 | 行锁让恢复者等原事务定局，独立上下文避免原请求取消把恢复也取消。 | 取得锁后再读权威状态；普通读到旧 READY 不能证明旧事务回滚。 |
| owner／租约 | owner 是本轮负责人，租约是暂时授权工作的时限。 | 租约到期可触发接管，但它本身挡不住旧进程恢复后继续写。 |
| owner_epoch／fencing | epoch 是持久任期号，fencing 是在存储端拒绝旧任期写入。 | 每次资金写都校验任期、阶段和摘要，且依赖同一个可串行裁决的权威库。 |
| 双主／权威存储 | 双主指两方都认为自己有权写；权威存储负责最终裁决。 | 两个独立数据库各自发任期号，不等于已经具备安全围栏。 |
| 账务版本／跨周期乱序 | 版本记录经济事实进度，通知可能晚于后一期到达。 | 迟到 F0800 通知不能覆盖 F1600 后的新风险状态，也不是再次扣旧费。 |
| risk_pending／风险门禁 | 保存待重算目标并限制增险、划出。 | 通知未到就持续保留，只有满足目标版本的确认才可解除。 |
| adjustment_id／目标减累计 | 纠错用新调整身份，只追加目标总效果与已有总效果之差。 | 本题差额为 target−(original_applied+prior_adjustments)，保留原周期和原账。 |

## 把整篇文章压缩成一个故事

1. 按本文符号，正费率多付空收；甲多仓 5 ETH、参考价 2,000、周期费率 0.0001，应付 1 USDC。这是持仓间资金费，不是手续费或借款利息。系统先封存费率和屏障仓位，再验好完整计划，最后共同提交分录、余额、去重和风险待办。

2. 恰好数据库提交后连接断了，调用方没收到答案。新 worker 不能把“没回执”当“没扣款”，而要带原周期编号到权威库取得行锁，等旧事务定局；查到同摘要 APPLIED 就返回原结果，确认回滚才按原计划重试。即使甲后来平仓，也不能换当前零仓重算旧义务。

3. 通知可重复送达，消费者把事件去重与本地修改一起提交；旧 owner 复活由存储任期围栏拒写，迟到旧通知也不能覆盖新版本。账务已生效不因通知失败撤销，风险门禁等确认再解。真有错就追加差额并引用原账，而不是改成交价、删历史或再造一次原费用。

**流程位置与核心机制：** 本题位于周期接管、计划冻结、账务提交与异步交付的恢复边界，核心是区分“哪个结算周期”和“周期内哪项经济效果”，并让任意重试收敛到同一结果。与第 05 题详解账务原子事务不同，这里只引用其提交契约，重点讨论 Outbox 至少一次投递、提交未知、跨周期迟到事件和 owner 围栏。

## 第 1 层：周期身份和经济效果身份有什么区别？

**面试官：** 定时器重复触发同一个周期，怎样证明它不是一笔新资金费？

**面试者：** 周期身份回答“这是哪个结算窗口”，由市场与周期结束时刻形成稳定 `cycle_id`，例如 `ETH-USDC-PERP/20261018T080000Z`；效果身份回答“这个周期里哪一个风险单元、资产和费用类型的金额已经产生”，例如 `cycle_id/risk_unit/USDC/FUNDING`。一个周期包含多个效果键，所以不能混为一谈。调度重试必须查回原周期状态；不能用 worker 启动时间、重试次数或重新生成的 UUID 当新周期身份，否则同一义务会被重复收付。身份还应把币种与经济类型编码清楚，不能只用账户 ID；计划 hash 用于检测载荷相同与否，不应替代唯一效果键，否则同一效果改载荷时反而会生成第二条资金记录。

## 第 2 层：Outbox 至少一次投递怎样做到业务上不重复？

**面试官：** Relay 发布成功后若在标记已发送前崩溃，同一事件会再次发出，消费者怎么办？

**面试者：** Outbox 在账务提交时已与 APPLIED 一起持久化，Relay 采用至少一次投递，因此消费者不能假设只收到一次。事件带稳定 `event_id`、周期、`plan_hash` 和账务版本；消费者在自己的处理域以 `event_id` 建唯一 inbox 记录，并把 inbox 与本地副作用共同提交。重复事件命中同一身份时返回已处理结果，不再重复更新。若副作用在外部系统，仍需外部幂等键或可查询结果；消息系统的发送确认不能证明端到端 exactly-once。投递成功后才标记 Outbox 完成会自然留下重复窗口，所以协议必须按“至少一次”设计；先标完成再发布则会留下永久丢失窗口，不能靠调整顺序消除两难。

## 第 3 层：为什么快照与计划必须冻结为不可变证据？

**面试官：** READY 周期恢复时，能否重新读取当前仓位和最新费率，再算一次相同周期？

**面试者：** 不能。SEALED 后的快照、费率证据、参考价、规则和算法版本必须有稳定摘要；FundingPlan 完整物化并通过总量校验后生成不可变 `plan_hash`。恢复 worker 只从这些证据重算或验证同一 hash，不读当前仓位补旧周期，也不因配置已更新而改变已承诺金额。若同一 `cycle_id` 出现不同快照或 hash，这是冲突而不是新计划；应隔离并保留证据，不能以最新值覆盖原计划。摘要需用字段有序、单位明确的规范编码并包含行数，避免同一内容因序列化顺序不同而出现假冲突，或因漏掉一行而仍被误判为相同。

## 第 4 层：事务提交前后崩溃分别怎样处理？

**面试官：** 应用器在任意指令后崩溃，哪些情况可直接重试，哪些要先查询？

**面试者：** 事务提交前崩溃，关系数据库回滚分录、余额、APPLIED、效果身份及 Outbox，持久周期仍为 READY，恢复者可以按原 hash 重试。提交之后崩溃，即使调用方没拿到回执，数据库中的 APPLIED、效果记录和 Outbox 已共同存在，不能再执行第二次经济变化。若崩溃点靠近 COMMIT 而客户端无法判断结果，就进入“提交未知”处理，不按进程日志推断；权威判断必须回到数据库中的周期与计划身份。另有准备阶段的 SEALED 或 READY 持久事实，但它们只证明证据和计划存在，不证明现金事务已提交；恢复逻辑不能把所有非终态都压成“失败”或把 APPLIED 当成可重做状态。

## 第 5 层：提交结果未知时，如何恢复调用方和批次？

**面试官：** 调用方超时后立即重跑批次会怎样？正确查询和重试顺序是什么？

**面试者：** 独立恢复上下文先连到权威数据库，按 `cycle_id` 开启事务并锁定周期行；若原应用事务仍持有该行锁，恢复者等待它提交或回滚，不能让等待超时被误读成业务失败。取得锁后再读状态与 `plan_hash`：若为 APPLIED 且 hash 相同，返回原结果；若原事务已回滚、周期仍 READY 且没有效果，再用同一冻结计划重试。普通未加锁读到 READY、效果表为空只代表看不到未提交写入，不能证明资金事务没提交。若状态或 hash 冲突就隔离；数据库不可用则保持未知和门禁，不查延迟投影来判定。

## 第 6 层：owner 租约过期后，怎样防止旧 worker 继续提交？

**面试官：** 分布式锁过期并由新 owner 接管，暂停很久的旧 owner 恢复后如何被隔离？

**面试者：** 仅靠租约或 Redis 锁不够，周期记录要维护单调递增 `owner_epoch`。新 owner 接管时持久递增 epoch；应用事务锁定周期行，并校验提交者携带的 epoch 仍等于数据库当前值，同时校验预期状态与 `plan_hash`。旧事务若先持有行锁，接管必须等它提交或回滚后再递增；旧 owner 一旦越过已提交的新 epoch，就无法通过数据库围栏。租约负责触发接管，数据库 epoch 才是拒绝旧写入的最终条件。每次接管还需记录 owner 身份、epoch 和接管原因，避免运维层把同一个 epoch 重用；写接口不得接受缺省 epoch，否则旧客户端会绕过围栏检查。

## 第 7 层：事件跨周期迟到或乱序到达怎么办？

**面试官：** F0800 的风险事件在 F1600 之后才送达，消费者能否按到达顺序直接覆盖当前状态？

**面试者：** 不能。事件携带原 `cycle_id`、屏障序号和账务版本，风险 owner 按账户当前版本处理，不允许旧版本覆盖新版本；收到较旧事件时查询缺失版本或重放事实，再基于最新仓位与余额重算，并只确认 `risk_pending` 中已满足的目标版本。周期执行侧也不能让后续屏障越过尚未完成的前序经济义务；若旧周期尚未 APPLIED，应暂停推进，而不是让迟到旧费用套用新快照。已经 APPLIED 但通知迟到，则是下游补齐，不是再次入账。若旧周期已关闭后才发现漏记，不能把迟到事件直接附加到新周期计划；应冻结影响范围、判定它是原账恢复还是经审批的调整，并保留原周期到修正事件的引用链。

## 第 8 层：已结算后发现错误，怎样修正而不伪装成新周期？

**面试官：** 事后发现费率证据或某行金额有误，直接重开周期重算是否最简单？

**面试者：** 已 APPLIED 的原周期和分录不可改写，也不能把修正伪装成下一期 `cycle_id` 或同周期的新计划。应创建独立 `adjustment_id`，引用原周期与原效果、审批依据、目标累计金额和已调整净额，只计算差额 `target−(original_applied+prior_adjustments)`，再按自己的幂等身份追加账务事件。重复执行同一个 adjustment 返回既有结果；同一身份却出现不同目标值则拒绝。原始费用、修正原因和净结果因此都能沿审计链重建；修正只影响账务与风险状态，不回写原周期快照、费率证据或累计指数。

## 第 9 层：两个 owner 同时认为自己是主节点时怎样 fencing？

**面试官：** 网络分区或租约延迟导致双主，epoch 机制在什么条件下才能真正挡住旧主？

**面试者：** 两个 owner 必须向同一个权威关系数据库提交，接管通过对周期行的串行更新取得更大的持久 epoch；每次资金写都在事务内比较 epoch、状态版本和计划 hash。若新主已提交更大 epoch，旧主即使恢复网络也只能失败，不能仅凭本地租约仍有效而写入。若两边各有独立数据库，或数据库本身发生双主且不能串行裁决，单调数值并不足以 fencing；必须先有具备共识/单一写主能力的权威存储，否则系统应停止资金写入，不能宣称双主安全。有效 fencing 的证明点是存储端对每次写都执行比较并拒绝旧 epoch，而不是两个进程各自声称任期更大；恢复演练应让旧主延迟后恢复并真实尝试写入，验证数据库拒绝它。

## 第 10 层：怎样验证完整恢复链真的没有漏账或重账？

**面试官：** 你会怎样设计故障注入与恢复核对，覆盖提交未知、乱序和旧主？

**面试者：** 对每个持久边界分别模拟崩溃：事务提交前重启应无任何资金效果；提交后丢回执再重启应返回原 APPLIED；Outbox 发布后丢确认应允许重复投递但 inbox 只产生一次副作用；旧 owner 在 epoch 递增后提交必须被拒；F0800 事件晚于 F1600 到达不能回退风险版本。再模拟旧事务持有周期锁时恢复者到达，恢复者必须等待旧事务提交或回滚后才能读取终态，不能从普通读的 READY 前态误判。最后按同一屏障水位核对周期、计划 hash、效果清单、尾差、Outbox/inbox 和风险确认版本。这里只描述验证设计与预期，不声称已实际运行测试。

**收束：** 周期身份固定结算窗口，效果身份固定窗口内经济行，事件身份固定投递事实；三者不可互相替代。恢复依靠冻结证据、权威状态查询、至少一次投递下的消费幂等、跨周期版本检查和单调 owner 围栏。最危险的反例是让迟到旧事件覆盖新版本，或在不同数据库各自选主后仍宣称 fencing 有效；修正必须作为引用原账的追加调整。
