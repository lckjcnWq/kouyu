# 大问题 5：怎样保证资金费收付与账本共同成立？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 资金费／手续费／借款利息 | 资金费是多空持仓间的周期转移，用于影响持仓激励；不是成交服务费或借钱利息。 | 本题讨论怎样把一轮收付完整记账，不改变已定计费规则。 |
| q、M、f／D 与 ΔB | 数量、参考价、周期费率相乘得到应付，现金变化取其负数。 | 本文多正空负，正费率多付空收；+5×2,000×0.0001 应付 1 USDC。 |
| 结转／账务一致性 | 结转是把应付应收落实到账；一致性要求相关记录描述同一件已生效事实。 | 不能付款方已扣、收款方尚未入账，就宣称本周期成功。 |
| SEALED／READY／APPLIED | 分别是输入证据封存、完整计划验好、资金共同提交。 | 冻结费率与仓位归属是依据，APPLIED 才真正改变现金。 |
| cycle_id／plan_hash | 前者是周期固定编号，后者是完整计划的内容指纹。 | 同一周期只能生效一个冻结计划，换 worker 不换编号或金额。 |
| 不可变分录／余额 | 分录保留每笔变动的原因和金额，余额表示当前还剩多少。 | 余额不能替代历史流水，差异不能用覆盖原账掩盖。 |
| 正式总账／借贷平衡 | 按资产、负债等科目性质记录资金双方；借贷是会计记账方向。 | 不等于用户界面的加号和减号，付款方客户负债减少、收款方增加。 |
| 尾差账户／Σ | 尾差承接合法舍入残差，Σ 表示合计。 | 全周期用户变化加尾差必须为零，但不能借此吞掉漏仓或制造资金。 |
| 同库事务／COMMIT／回滚 | 一个数据库内的成组修改，要么共同提交，要么整体不生效。 | 全部收付、余额、去重、APPLIED、风险待办和 Outbox 共同成立。 |
| 效果键／幂等 | 效果键给一项经济变化固定身份，幂等保证重试不再产生一次变化。 | 周期、风险单元、币种和费用类型确定身份，不把重试次数塞进去。 |
| 唯一约束／载荷冲突 | 数据库拒绝重复身份；同身份不同内容不是普通重复。 | 命中唯一键后要比对摘要，不能忽略冲突却再加减余额。 |
| 行锁／稳定锁序 | 行锁让竞争写者排队，稳定锁序让大家按同一顺序取得锁。 | 先锁周期，再按约定键锁余额与门禁，其他资金写路径也必须遵守。 |
| 余额版本／死锁 | 版本防止旧值覆盖新值；死锁是写者相互等待。 | 版本不符或死锁时整体回滚，再按原身份有界重试，不承认半批成功。 |
| Outbox／查询投影 | Outbox 存待发事件，投影是给页面和查询使用的派生视图。 | 通知或页面可以暂时落后，不能据此认定权威账本未提交。 |
| risk_pending／划出门禁 | 风险待确认标记及限制资金外流的持久状态。 | 与资金同提交，风险 owner 按新版本确认后才解除对应限制。 |
| 共享现金池／账户级版本 | 多份风险单元共用同一个现金余额的变体。 | 计费仍逐单元，承接能力却要按全账户检查，不能各自重复使用同一余额。 |
| 跨库／RPC／原子边界 | 跨库是不同数据库，RPC 是跨服务远程调用；原子边界决定哪些修改能一起成败。 | 两次 COMMIT、Redis 锁或消息重试都不自动等于全局原子事务。 |
| 提交未知／权威查询 | 超时可能发生在提交前也可能发生在提交后。 | 恢复者取得周期行锁，等原事务定局，再查原状态和摘要，不凭延迟页面重扣。 |
| 负现金／用户欠款 | 账面负数可表示用户尚未付清的义务，不是实际收到的钱。 | 不能把应付截成现有余额，也不能把欠款当真实托管资产。 |
| 信用／损失缓冲 | 平台已授权、可控制的真实承接资金或能力。 | 完整收款需有真实来源；欠款、缓冲占用和门禁须一起入账，无能力就暂停整批。 |

## 把整篇文章压缩成一个故事

1. 一轮资金费已经算好：按本文多正空负、正费率多付空收的约定，甲 +5 ETH、参考价 2,000、周期费率 0.0001，付 1 USDC，乙、丙合收 1。这是持仓间转移，不是手续费或借款利息。费率封存、仓位归属和计划验好，都还不是扣款。

2. 账本不能先扣甲、明天再补乙丙。它锁住周期和相关余额，在一个数据库事务内写全分录、余额、效果身份、APPLIED、风险待办与通知。共同提交才生效，失败就整体回滚。回执丢失时查原周期，不换身份再付一次；风险未确认前，划出门禁继续保留。

3. 若甲钱不够，不能随意减掉应付，也不能只给收款方造余额。必须有真实授权缓冲承接欠款并一起记账，否则整批暂停。共享现金要整体检查，跨库则另需协议，不能冒充同一事务。平仓不取消已归属费用，结转不改成交价；历史有错也只能留痕追加调整。

**流程位置与核心机制：** 本题承接第 04 题产出的不可变金额计划，在同一关系数据库提交域内，让所有分录、余额、处理身份、APPLIED、风险待办和结果 Outbox 一起成立。不同于第 06 题的投递与崩溃推进，本题关注资金效果的原子边界、并发锁序、共享现金约束和负余额承接；不把跨库、消息系统或页面投影说成同一事务。

## 第 1 层：账务一致性具体要保证什么？

**面试官：** 资金费批次可能涉及很多账户，怎样定义“结转一致”，而不是只说最后对账？

**面试者：** 在本基线中，正确结果是冻结计划里的每个风险单元和尾差账户各产生一笔确定效果，余额按计划变化，且 `ΣΔB_u+round_u=0`。一个周期只能有一个生效计划，同一效果身份不能重复入账；允许账务已完成而风险重算、查询投影暂时落后的明确暂态，但 `risk_pending` 必须保持，禁止未确认风险前划出资金。对账负责发现遗漏，不会让已经半提交的资金自动变成原子结果。边界是同一个 APPLIED 只能对应唯一冻结计划，不能因个别行暂时失败就承认其他行已独立完成；若本地事务无法覆盖全计划，必须先保持整周期屏障和门禁，再采用可审计的分布式协议推进。

## 第 2 层：分录、余额与周期记录怎样共同表示这笔费用？

**面试官：** 这些效果落到哪些持久对象，余额是否可以代替账本？

**面试者：** 以 `cycle_id` 和冻结的 `plan_hash` 锁定计划，为每个风险单元写带稳定效果键的不可变分录，同时按同一金额更新余额及余额版本，并保存前后版本供审计。正式总账按 USDC 资产和账户性质登记借贷；用户间转移可表现为付款方客户负债减少、收款方客户负债增加，尾差账户单独承接舍入平衡。余额是查询和风控的当前视图，不能替代分录；如果它与分录不一致，应阻断并修复，而不是覆盖历史账。每个分录行保留原始业务键与币种，批次控制记录保存行数和摘要，提交前检查借贷平衡、效果集合完整及余额版本连续，避免账本平衡却漏了一个收款账户。

## 第 3 层：哪些状态必须在一个事务里落地？

**面试官：** 逐行分录和余额都写完后，APPLIED、幂等记录和风险事件何时产生？

**面试者：** 本基线的参与账户、仓位、账本、幂等记录和门禁位于同一支持事务的关系数据库。开启事务并校验 READY 周期及计划摘要后，写完全部分录和余额版本，再登记效果身份；同一事务内把周期置为 `APPLIED`、写处理结果身份、标记受影响风险单元 `risk_pending` 并写结果 Outbox。只有共同提交后周期才算资金生效。若 APPLIED 和 Outbox 拆提交，恢复时会遇到“已扣但无待办”或“待办已发但钱未记”的歧义。批次可以先在事务外准备完整 READY 计划，但任何一行现金变化都不得先于全体分录和控制记录提交；事务过大时要明确暂停与迁移策略，不能悄悄改成逐页已生效。

## 第 4 层：多 worker 同时处理周期时如何锁定？

**面试官：** 两个 worker 或普通成交同时更新同一余额，怎样避免死锁和覆盖？

**面试者：** 所有资金写路径约定同一锁序：先按主键锁周期及状态版本，再按 `(资产, 风险单元/账户 ID)` 稳定升序锁余额与门禁，最后插入效果、分录和 Outbox。周期行让同周期应用串行，余额行则与成交等其他资金写路径协调；更新时带预期余额版本，版本不符就回滚重算，不能用旧快照覆盖新值。统一锁序必须由所有相关写者遵守；只在资金费 worker 内排序，无法消除它与反向锁余额的成交事务之间的死锁。锁等待超时或死锁受害者要整体回滚，再用同周期、同 hash 有界重试；不能把部分锁到的行当成部分成功，也要监控长事务和热点账户对前序成交的阻塞。

## 第 5 层：唯一约束在并发正确性里负责什么？

**面试官：** 应设置哪些唯一键？唯一冲突时能否简单忽略并继续提交？

**面试者：** 数据库至少约束 `(market, cycle_end)` 对应唯一周期，并约束 `(cycle_id, risk_unit_id, asset, effect_type)` 唯一效果；Outbox 结果事件也有稳定唯一键。锁和状态机负责业务顺序，唯一约束是并发竞态下的持久防线。发生冲突不能无条件 `ON CONFLICT DO NOTHING` 后照样更新余额：应读取已有记录并比对 `payload_hash/plan_hash`，相同则收敛到原结果；同键不同载荷必须回滚并隔离，不能把载荷冲突当作成功重放。唯一键的列要覆盖实际经济粒度，尾差账户也要有每周期唯一效果；若把费率或 worker ID 加进身份来躲冲突，重试就会被误认成新效果，失去防重意义。

## 第 6 层：多风险单元共享一个现金账户时怎么避免超支？

**面试官：** 基线是逐仓，但如果账户层多个风险单元共用同一 USDC 现金池，逐仓余额检查为什么不够？

**面试者：** 这改变了资金可用性约束，但不改变每个风险单元的计费和舍入。计划仍逐单元计算，再将本周期净现金变化汇总到共享现金账户；提交前按全体前序义务计算账户可承接额，检查总扣款不会超过现金加已授权信用缓冲，且收款额不会因此成为无担保可用资产。事务同时锁共享池余额、所有相关风险单元及门禁，并验证一个账户级版本。不能让两个 worker 各自看到足额余额后分别扣成功；基线没有信用能力时，超限就暂停整批。共享池变体必须把完整周期效果仍放在共同原子提交里，不能先按账户分页扣一部分，再用后页失败作为可接受状态；否则收款方看到的是部分结算义务。

## 第 7 层：共享现金的锁序与门禁怎样推进？

**面试官：** 多个周期、提现和成交都竞争共享池，如何确定顺序并防止部分风险单元先放开？

**面试者：** 由账户 owner 为共享现金池定义单调账务版本，资金费周期、成交和划出都在同一权威顺序中校验预期版本。批次事务锁周期后，按账户 ID 再按风险单元 ID 排序锁共享池和相关行；若门禁跨度过大导致无法原子覆盖，就不能假称已经全账户结算，而应先冻结划出并通过有序账户级批次完成。APPLIED 时将风险待办绑定目标账务版本；风险 owner 只有在确认该版本及其之前所有义务已处理后才能清门禁，不能逐页完成就提前开放部分共享现金。可把“已计算”“已提交”“风险已确认”作为不同水位持久记录，崩溃后从最后一个权威水位继续；门禁只按账户级完整水位推进，过期 worker 的确认也必须校验 epoch 与目标版本。

## 第 8 层：跨库或分库后，哪些承诺必须收窄？

**面试官：** 为了扩容把账本、风险门禁或账户余额拆到不同数据库，原来的“一个事务全部提交”还成立吗？

**面试者：** 不成立，关系数据库事务不能跨独立数据库自动提供原子提交。要保留同一承诺，就须把周期及其资金状态放在同一个事务分区，或采用有明确准备、提交、补偿与可查询状态的跨库协议；Outbox 加重试本身只保证可恢复交付，不让多个库原子生效。分区后还要定义单账户/风险单元路由、跨分区结算和门禁承接，承认中间状态及暂停条件。不能把两个本地 COMMIT 或 Redis 锁描述成全局原子事务。若选择协议化拆分，只有全部参与方都进入 PREPARED 且协调器持久记录决议后才能推进提交；超时必须查询协调状态或继续阻塞，不能让某库自行超时回滚、另一个库仍永久保留扣款。

## 第 9 层：提交成功但客户端没有收到响应怎么办？

**面试官：** 数据库可能已经提交，网络却在响应前断开。重试如何避免再次收付？

**面试者：** 调用方用稳定 `cycle_id` 查询权威数据库，不因超时就换一个周期或效果键。若查到 `APPLIED`，先核对请求 `plan_hash` 与已存 hash 相同，再返回原提交结果；不同则是载荷冲突。若仍是 READY 且没有效果，才按原冻结计划重试。提交状态未知期间不能靠内存缓存判定失败，也不能先释放屏障或放开划出；查询投影可能落后，必须查权威提交域或满足读后写一致性的接口。若原事务还可能未结束，恢复者还要在权威库取得周期行锁并等待其提交或回滚后再判状态；未加锁读到旧的 READY、效果表为空，不能证明事务没提交，因为旧事务的未提交写入对普通读不可见。

## 第 10 层：付款现金不足时，如何守住真实资产边界？

**面试官：** 应付金额大于用户现金，能否把付款截到余额，或者先给收款人全额入账？

**面试者：** 截断付款会破坏既定费率义务与收付守恒，不能这样做。README 的完整方案允许逐仓账面现金转负，但负数必须在正式账务中成为用户应收或明确欠款，并在同一提交域登记信用／损失缓冲占用、限制划出并置 `risk_pending`；后续追偿是新事件，不再重复扣同一笔费用。只有平台已授权承接该欠款且有真实缓冲时，才能让收款方收到完整金额。若无承接能力，就在入账前暂停整批，不能制造无担保可用资金。这里的“现金不足”不是数据库允许写负数就自动解决，欠款科目、缓冲额度、收款方可用性和提现门禁必须共同有权威记录，并由后续风险重算决定解除条件。

**收束：** 原子边界是 README 指定的单个关系数据库事务；账务可以先于风险与查询完成，但门禁和 Outbox 必须与账务同提交。共享池要有账户级版本与整体门禁，跨库则明确失去单库原子性。用并发重复应用、共享余额双扣及余额不足的反例检查效果唯一和资金承接是否真实。
