# 大问题 6：保证金划转与逐仓／全仓模式切换如何安全完成？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 保证金 / 抵押归属 | 承担合约风险的钱，以及哪部分资金正式属于哪个风险范围。 | 追加是移动资金归属，不是改变价格或凭空增加资产。 |
| 逐仓 / Cross 全仓 / 风险池 | 逐仓给仓位专用资金；全仓共享指定池内资金；池定义共同担责范围。 | 从逐仓切全仓，必须说清桶外的钱是否实际纳入。 |
| 线性永续 / 多仓 / 未实现盈亏 U | 无固定到期日、按数量乘价差算盈亏；多仓跌价亏；U 是账面浮盈浮亏。 | 1 ETH@100、Mark84，U=−16，追加保证金不改变这笔浮亏。 |
| Mark / Equity E | 用于风险估值的价格；本例 E 是池余额加 U。 | 桶20时E4，真实追加20后桶40时E24，Mark本身不产生现金流水。 |
| IM / MM / IMR / MMR | 初始与维持要求金额，以及各自比例。 | 本例20%与5%是教学值；能否划出不能只看是否高于MM。 |
| Available / 可转金额 | 可新增风险额度与实际允许划出的金额，是两个口径。 | 划出还须查现金、预留、未结算义务与操作后状态。 |
| TransferCollateral / ChangeMarginMode | 前者移指定金额；后者改变仓位、资金与裁决规则的归属。 | 可以同流程协调，但不能用改一个 mode 字段代替转账。 |
| transfer_id / migration_id / payload_hash | 划转身份、迁移身份、内容摘要。 | 同一请求重试继续原流程，同编号换金额要拒绝。 |
| source_hold / 源占用 | 转账前先锁住来源资金，防止同时下单、提款或转给另一桶。 | 外侧仅20，两笔各转20只能一笔成功占住，hold不是另一份资产。 |
| 账本分录 / journal_id / 事务 | 正式记录源减少、目标增加的流水及其身份；事务把关联修改一起提交。 | 不用两条无关联的改余额接口转钱。 |
| LEDGER_COMMITTED / APPLIED / DONE | 账务已提交、风险池已应用、两端效果和结果已对齐。 | 钱在账本进入目标后，目标风险服务仍须追到对应版本才可用它准入。 |
| 源 hold 交接 / 在途状态 | 旧余额尚未更新时保留锁定；在途表示效果尚未全部到齐。 | 源不能先解除锁定、再等余额减少，否则旧钱又能花一次。 |
| 冻结 FREEZING / 排空 DRAINING | 阻止新扩险与冲突操作，并处理完旧订单、成交和相关义务。 | 冻结不是暂停行情，也不是不再监控强平条件。 |
| 屏障 h / 连续检查点 k | h 是已安排的界线；k 是之前事件已完整处理到哪。 | h=121、k=118时，不能因界线已写下就说119和120都办完。 |
| 权威终态 / 执行水位 | 撮合证明订单最终结果，以及此前哪些成交已完整处理。 | 查询没有活动单，不足以排除消息还在路上的成交。 |
| PREPARED / COMMITTED / cutover | 迁移已准备好、唯一切换记录已提交，以及新旧归属交接点。 | 准备阶段不开放新池；切点后以新归属为准向前补齐。 |
| 成员版本 / mode version / owner epoch | 哪些仓位属于哪个池、当前模式、当前负责人代次。 | 共同防止旧池和新池同时对同一笔钱放行订单。 |
| 试算 / 输入摘要 / 版本校验 | 用明确价格和规则预检查目标状态，并在提交前检查依据是否仍有效。 | 准备后价格变了就重算，不能拿旧“通过”结果硬切换。 |
| 风险处置 / 救援追加 | 前者处理触线仓位；后者按授权向风险桶补充资金。 | 追加可能改善权益，但不能自动取消已经启动的流程或已成交强平。 |
| 超时未知 / 幂等 / fencing | 没答复不等于没办成；同业务只生效一次；拒绝旧负责人写入。 | 故障后查权威记录，不重复划钱，也不让旧主重新开放源池。 |
| 回滚 / 中止 / 审计补偿 | 未提交时按证据放弃；提交后若要撤回，记一笔新的合法反向操作。 | 不能删除原流水或直接覆盖余额来假装转账没发生。 |
| 资金守恒 / 唯一归属 | 内部转钱不生钱，每份可用资产与仓位只有一个活动归属。 | 最终总额40还不够，中途也不能两池都凭40开仓。 |

## 把整篇文章压缩成一个故事

小林的逐仓桶有20 USDC，外侧还有20；1 ETH多仓从100跌到Mark84，浮亏16，桶权益只剩4，低于本文维持要求4.2。小林想把外侧20追加进去。系统必须先占住来源，确认它没被别的订单或提款用掉，再正式记录外侧减20、桶内加20；风险池应用这笔账务版本后，才能按桶40算权益24。全账户还是原来的40，并没有赚20。

若小林改口说“直接切成全仓”，系统要多办一件大事：把哪些资金、仓位和责任交给哪个池说清。只把桶内20带过去，权益仍是4，模式名称不会自动带来外面的20。本文还要求先停新扩险，处理齐旧订单和成交，再按目标状态试算，在唯一切点交接归属与裁决权；风险处置活跃时不能用普通模式切换绕过去。

如果中途断网，系统查原划转或迁移编号：正式提交前，可在证据齐全后中止；提交后则继续补齐，不靠覆盖余额“回滚”。源池未追齐时继续锁住转出额，目标未追齐时也不抢先使用。全文就是在防止搬钱、搬仓时两头都认领，或者两头都不负责；行情和风险监测在搬家期间仍不能停。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于资金归属变更与风险池成员迁移阶段。划转需要证明同一笔 USDC 从哪里来、何时不再支持源池、何时可以支持目标池；模式切换还需要把仓位、订单义务、抵押范围和风险裁决权移动到唯一的新版本。重点是源资金准入与占用、账务提交、冻结排空、唯一切换提交点以及失败后的可恢复路径，不是把一个 `margin_mode` 字段改掉。

**共同前提：** 沿用[总览的讨论基线](README.md#一文字全流程保证金风险如何从下单走到可解释的账户结果)：链下托管、线性 USDC 永续、单向净持仓、单一 USDC 抵押品、合约乘数为 1，`IMR=20%`、`MMR=5%`。账户初始 40 USDC；逐仓单仓桶有 20，另 20 在桶外；Cross 池有 40。主例多仓 1 ETH，入场价 100，无费用、资金费、档位、其他仓位和未结算义务。已结算损益包含在余额内，Mark 估值不直接产生现金。`E <= MM` 表示需要风险处置，不表示已经执行强平。

| Mark | U | 名义价值 N | IM | MM | 原逐仓 E | 原 Cross E |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 0 | 100 | 20 | 5 | 20 | 40 |
| 90 | -10 | 90 | 18 | 4.5 | 10 | 30 |
| 84 | -16 | 84 | 16.8 | 4.2 | 4，触发 | 24，不触发 |

参数仅是教学模型，不是行业通用值。两列是独立模式的原始比较，不意味着点击“切换”就自动多出 20。后文追加、划出和迁移均显式给出资金来源、划转金额与新归属；不引入真实平台的操作政策。

本题共 8 层，追问顺序如下：

```text
划转改变什么 → 转出准入与资金占用 → 账务提交与目标可见
    → 为什么模式切换更复杂 → 屏障、冻结和排空
    → 唯一归属切换与前后风险校验 → 超时崩溃与恢复 → 反例验证
```

## 第 1 层：追加保证金是改变杠杆，还是移动真实资金归属？

**面试官：** 主例逐仓在 Mark=84 时权益只有 4。用户想把桶外 20 USDC 加进来，或者直接切成 Cross，能不能把风险计算里的余额从 20 改成 40？

**面试者：** 不能只改计算输入。原逐仓的账本归属只有 20，未实现亏损为 16，所以 E=4、MM=4.2，需要风险处置；桶外另 20 不属于该风险池。增加逐仓保证金是显式划转，改变抵押资金归属，不改变仓位数量、入场价和线性合约盈亏公式。

追加 20 真正提交后，桶外余额从 20 变成 0，隔离桶余额从 20 变成 40；Mark 仍为 84 时，`E=40−16=24`，IM 16.8，MM 4.2。全账户的账本资金合计仍为 40，未实现亏损仍为 16，不是凭空赚了 20。

“切成 Cross”则还改变损失共担边界。若只把原桶内 20 带进一个新的 Cross 池，另外 20 仍在池外，权益仍只有 4；要得到总览的 Cross E=24，必须明确把全部 40 纳入该池，且额外 20 的归属变更已经提交。

因此我会区分两种命令：`TransferCollateral` 移动指定金额，`ChangeMarginMode` 迁移风险池成员与裁决规则。二者可以由同一迁移工作流协调，但不能用改字段替代账本转移，也不能把模式名称本身当作资金来源。

## 第 2 层：转出方如何保证这 20 没被订单、提款或另一笔划转占用？

**面试官：** 明确了资金来源后，两个请求可能同时把桶外的 20 转走；也可能用户想从已有仓位的池中抽出保证金。准入和并发边界具体是什么？

**面试者：** 先定义划转身份和源锁定，再按源风险范围检查操作后的状态。记录至少包括：

| 对象 | 关键字段 |
|---|---|
| 划转命令 | `transfer_id、command_id、payload_hash、asset、amount、from_scope、to_scope` |
| 源资金占用 | `source_hold_id、hold_amount、source_version、risk_decision_id、state` |
| 账务与结果 | `journal_id、ledger_commit_version、target_applied_version、result_id` |
| 归属约束 | `from_mode_version、to_mode_version、migration_id、owner_epoch` |

同一 `transfer_id` 不变金额、不变方向；同身份不同载荷拒绝。本题桶外余额没有其他风险义务时，两个各转 20 的请求必须竞争同一个源资金版本：第一笔原子锁定后可用为 0，第二笔拒绝，不能各自拿旧余额通过。提款和其他划出也必须读取同一个锁定事实。

若源是风险池，本题选择一条明确但不声称通用的教学规则：普通划出后须满足 `E_after >= 当前仓位 IM + 未成交增量预留 + 其他锁定额`，并且不得处于风险处置或模式迁移冲突状态。IM、未决成交和挂单必须来自一致输入；待释放的撤单余量不能提前当作自由资金。

主例 Mark=90 时，逐仓 E=10 虽然高于 MM=4.5，却低于 IM=18，本题不允许抽走保证金。Cross 在 Mark=100、无挂单和其他锁定时，40−20=20 是这一规则下的风险上限；实际可转金额还要受账本现金、未结算义务和目标约束限制，不能宣称 Available 永远等于可提现额。

源校验与 `source_hold` 建立必须在一次池级裁决中提交。锁定不减少总账现金或 Equity，但会让这份资金不能再支持新的订单、提款或第二笔划转。价格或参数变化会使提交时条件失效，因此锁定不是永久风险通行证；最终划出前仍要在排序边界重验，失败则不提交划出。

## 第 3 层：钱从源到目标，哪个时刻才允许目标用于风险？

**面试官：** 源已经锁住，但目标属于另一个风险池。先减源还是先加目标？如果账本和风险服务不在同一个数据库，怎样避免两边同时可用或者中间丢钱？

**面试者：** 不采用两条独立的“余额减 20”和“余额加 20”接口。资金转移由一个有身份的账务事实表达，在同一账本事务中提交源归属减少、目标归属增加、hold 消费、唯一流水与待交付事件。USDC 内部划转的金额和为零，不生成交易损益，也不改入场价。

可以用以下持久状态表达工作流：

```text
REQUESTED → SOURCE_HELD → LEDGER_COMMITTED → APPLIED → DONE
                    └─ 确认未提交账务 → ABORTED
```

`LEDGER_COMMITTED` 表示账本余额归属变化已经提交，是现金事实的权威提交点；此时源账本余额已减少、目标账本余额已增加。它不自动表示两个风险池都已能按新余额准入。`APPLIED` 表示相应风险池已应用并记录这笔账务版本；只有源池应用扣减后，源池的新裁决才按新余额可见，只有目标池应用增加后，目标抵押才可进入该池的风险计算与准入。`DONE` 表示两侧效果和结果记录已对齐。网络回包、账本提交和风险池准入可见是不同阶段。

若账本和风险投影异步协作，源 hold 必须先对所有源额度使用者生效，再允许账本提交。账本提交后、源风险池尚未应用该版本时，账本已是减少后的权威余额，但风险池可能仍保有旧版本；这段期间必须继续保留对应划出锁定或直接停扩险，不能让旧池按旧余额再花一次。源池在**同一风险状态迁移**中应用余额减少版本并移除 hold 后，新余额才成为该池准入可见状态。目标账本虽然已增加，目标池在核验账务提交身份并应用目标版本前也不得使用这笔抵押；目标晚到不意味着允许源继续花。

如果源、目标的锁要同时取得，按固定 scope 顺序获取，或者由一个协调记录排序，避免双向划转死锁。不能在等待网络时一直持有数据库事务锁；应以持久准备状态衔接，推进时再短事务校验版本。

在跨域效果未齐的窗口，账本资金仍有明确归属或在途状态，风险侧可保守锁住，但不能把“源 hold 20”当成又一笔 20 资产。恢复按原 `transfer_id` 补发和追齐。只有有证据证明账务尚未提交、也不可能稍后提交，才允许释放源 hold；RPC 超时不是该证据。

## 第 4 层：为什么模式切换不能复用一笔划转就结束？

**面试官：** 划转已经有事务了，模式切换是不是再写个 `mode=CROSS` 就行？仓位还在、订单也在，为什么非要有迁移状态机？

**面试者：** 因为模式决定同一仓位由谁计算风险、哪些抵押共同承担亏损、挂单授权属于哪个池，以及强平工作流操作哪组成员。只转钱不迁仓，会留下无资金担保的旧仓；只改 mode 不移资金，会让两个池同时认领或都不认领。

迁移记录至少需要：

- `migration_id、payload_hash、state、source_pool_ids、target_pool_id`；
- `old_mode_version、new_mode_version、old_member_version、new_member_version、authority_epoch`；
- 精确的仓位成员清单、抵押划转清单、订单／预留／成交义务清单及其摘要；
- 每个相关池的冻结屏障 `h`、已应用检查点 `k`，每张订单的最终执行水位；
- 账务准备／提交身份、迁移前后风险输入摘要、`cutover_commit_id` 和失败原因。

本题选择易证明的协议：**可带已结转仓位迁移，但先冻结扩险，撤掉活动订单，排空预留与未结转成交；有活跃强平／风险处置流程时不允许普通模式切换。** 这不意味着行业都禁止带订单切换；若要支持，必须显式迁移每笔授权与义务，不能留给后台最终一致去猜。

状态主线为：

```text
REQUESTED → FREEZING → DRAINING → PREPARED → COMMITTED → COMPLETED
                  提交前确认可撤销 ─────────→ ABORTED
```

Mark=84 的逐仓 E=4 已触发风险条件，不能用改模式来绕开既有风险处置。本题允许在权限和强平工作流校验下做“只入不出”的救援追加；追加到桶后重算，协调方确认原风险工作流是否仍适用。若平仓已经成交，追加不能撤销成交；原工作流没有解除或结清前，普通模式迁移仍不放行。

## 第 5 层：冻结屏障已分配，是否就说明迁移前的旧操作都处理完了？

**面试官：** 你在池序列里写了一个冻结屏障 h，发现系统返回“已接受”，就开始搬仓，可以吗？刚受理的订单、迟到成交、行情变化该怎样处理？

**面试者：** 不可以。必须区分**已分配／已持久化的屏障 h**和**已完整应用的连续检查点 k**。h 证明屏障在顺序中有位置，不证明此前事实及其跨域效果已经应用。

例如 h=121、k=118，119 的成交还没结转、120 的预留还未应用，不能因为屏障已持久化就宣称仓位和余额已经排空。冻结命令在权威顺序中确立界线：h 之后的扩险和冲突划出不得再授权；h 之前已合法受理的命令仍必须按旧模式完成或取消，不能直接抛弃。

本题的排空条件同时要求：

1. 相关各池 `k >= h`，且 k 表示连续完整应用，不是“见过的最大序号”。
2. 旧模式不再签发新扩险授权；所有已签发授权有受理／拒绝或撤销证据。
3. 活动订单拿到权威终态，并追齐终态之前的成交执行序列。
4. 每笔确定成交的仓位、账本、预留交接已齐；没有一边释放旧预留、一边漏掉新敞口的空窗。
5. 其他抵押划转、提款与成员变更已结清或纳入冻结范围；没有活跃强平工作流。

仅有 `k >= h` 也不够：屏障之前受理的订单可能在之后才得到成交／撤单终态，新的结转事件会推进 k 到更后面，所以要再核验订单与跨域效果水位，记录最终排空切点。

冻结的是新的扩险与冲突的归属变更，不是暂停 Mark 或风险监测。行情继续推进、现有仓位继续可能恶化。若出现需要风险处置的条件，由同一控制边界先裁决，迁移停下或提交前中止，不能用“正在切换”屏蔽风险触发。救援追加若改变了输入，也必须重新准备和校验，不能沿用旧快照。

## 第 6 层：真正切换时，怎样保证旧池和新池只有一个有裁决权？

**面试官：** 订单已经排空，接下来具体改哪些东西？逐仓转全仓、全仓转逐仓如何验证金额和风险？若系统跨数据库部署，哪一个记录能决定最终归属？

**面试者：** 先生成不可变迁移清单，列出仓位、抵押分录、成员关系、新旧模式版本、准备输入和最终风险校验。然后在唯一切换提交点，把资金归属、成员映射与风险裁决权从旧版本换到新版本，不能让新池抢先开放、旧池稍后再停。

如果采用同一事务存储，可在短事务内验证仍处于 `PREPARED`、owner epoch 有效、输入版本未变化、无风险工作流抢先生效，然后共同提交账务分录、成员版本、活动归属指针、迁移终态与待交付事件。模式迁移的多项变更具备这个事务条件是本设计的明确要求，不是数据库天然跨服务原子的假设。

若部署上不能同事务，须先在冻结范围内完成耐久准备，并由**唯一权威切换记录**引用完整准备证据：未提交的目标成员和抵押不能对外可用；提交后按新活动归属读取，未追齐的域继续拒绝扩险，恢复只向前补齐。准备方不能自行超时解锁，与协调方的提交判定竞争。若做不到这种提交协议，就只提供受限离线切换，不能靠两边各改一个 mode 字段宣称安全。

数值校验必须体现资金清单：

- **逐仓转 Cross，Mark=100：** 原桶内 20 加桶外显式纳入的 20，新 Cross 余额为 40，E=40、IM=20。只携带桶内 20，则 E=20，不是 40。
- **Cross 转逐仓，Mark=100：** 将 20 明确分配给该仓，另 20 留在桶外，目标 E=20、IM=20，符合本题采用的迁移后 `E >= IM` 且 `E > MM` 规则。
- **Cross 转逐仓，Mark=84：** 若仍只分配 20，目标 E=4、MM=4.2，直接触发，不能批准；若显式分配全部 40，E=24、IM=16.8、MM=4.2，才通过本题这组数值检查。账户总资金没有增加。

参数和价格不能因 PREPARED 就被永远钉住；切换提交要核对仍有效的输入与规则，变化则重算并重新准备。新旧风险触发也必须在提交边界比较模式版本、成员版本和控制代际：已提交切换后，旧触发不能绕过围栏操作新池；已提交的成交和债务则不会因版本失效而消失，必须履约和结转。

## 第 7 层：超时、重复或崩溃后，什么时候能回滚，什么时候只能继续？

**面试官：** 假设迁移提交前断电、账务已经提交但结果丢失，或者切换提交后新池通知没送到。用户不断重试，又有旧主恢复，怎样收敛到一个结果？

**面试者：** 超时只说明结果未知。重试沿用原 `transfer_id` 或 `migration_id`，同身份同载荷查询原状态，同身份不同载荷拒绝；每笔账务、成员切换和目标应用都有唯一效果身份，不能以重试次数生成新的划转。

恢复先查询权威提交记录，再按边界行动：

| 持久事实 | 恢复动作 | 禁止做法 |
|---|---|---|
| 仅有请求或源 hold，确认不存在账务提交且不会迟后提交 | 按协议继续或提交 ABORT；验证后释放 hold／冻结 | 只因 RPC 超时直接解锁 |
| 冻结已生效但排空未完成 | 按原屏障和订单身份追齐，或者提交前有序中止 | 把冻结标志清零后假装订单都未受理 |
| 账务已提交、风险侧尚未追齐 | 重放同一账务效果；源维持覆盖，目标待版本核验后开放 | 再转一次；或原地把余额改回旧值 |
| 切换已 COMMITTED，但部分域或通知未追齐 | 新归属为准，继续冻结未齐部分，幂等向前完成 | 把旧模式重新设为活动，与新模式双写 |

提交前中止还要确认没有已完成的经济归属变化、旧订单义务已经有明确去向，并在旧模式当前输入上重算后才能恢复准入。已经提交的转账若需要撤回，应生成新的反向划转并重新检查源池可转金额；这叫补偿，不是删除原流水。已经提交的模式切换要切回，也是一笔新迁移。

新 owner 接管时获得更高 epoch，并在存储侧 fence 旧主。冻结记录、迁移阶段、h/k、准备清单、账务身份和待交付事件都要可恢复。旧主携带旧模式版本或旧迁移阶段的继续执行会被版本／epoch 校验拒绝；但切主之前已合法提交的转账和成交仍须保留，不能一刀切丢弃。

长期卡住的迁移需要明确所有者、告警、查询权威订单／账务的恢复入口及人工复核依据。人工处理也必须按同一提交记录继续或产生审计补偿，不能直接在数据库改两个余额、清一个冻结位来“修好”。

## 第 8 层：怎样证明没有重复计资，也没有借模式切换逃避风险？

**面试官：** 最后给出能推翻方案的检验。只对比迁移前后总余额是 40，能否说明切换安全？

**面试者：** 不能。两边同时短暂计入同一份资金，最后归一到 40，也可能已经对外多授了一次订单额度。应逐提交点验证资产归属、可用额度、唯一裁决权以及未决义务，而不只看最终总额。

| 反例／故障注入 | 必须检查的结果 |
|---|---|
| 桶外仅 20，同时发出两笔各追加 20 的请求 | 仅一笔建立有效源占用；同身份重试不重复扣加 |
| Mark=84，追加转账账务尚未提交 | 逐仓仍为 E=4，不得提前显示为可用 E=24 |
| 账务已提交，目标先追齐、源投影仍旧 | 源必须被 hold／冻结覆盖，不能继续把转出的 20 用于新单 |
| h=121、k=118，或订单终态已到但之前成交效果缺失 | 不能进入 PREPARED，更不能开放新池 |
| Cross 在 Mark=84 请求仅分配 20 切成逐仓 | 目标 E=4、MM=4.2，拒绝，不能用迁移前 Cross E=24 掩盖 |
| 切换提交与风险处置抢占同一控制版本 | 只有一个控制决策先有效，后者按新版本重验；不允许双重裁决 |
| 切换提交后崩溃，再重复所有事件并复活旧主 | 只有一个活动归属，继续补齐，不回退模式、不重复转账 |

还要在任意阶段追问：原有 USDC 的总账金额是否守恒？hold 是否只是约束而未被再算成资产？每个仓位和抵押是否只有一个活动风险池？每个确定成交的义务是否全程有人覆盖？新旧结果能否用提交身份和版本复现？

这些是设计级检验和手工数值案例。本文没有运行数据库分布式事务、真实交易所迁移、故障演练或生产性能测试，不把协议说明冒充实践报告。

## 本题收束

### 已经讲透的机制

- 划转是有唯一身份和双边账务效果的抵押归属变化；目标可用必须晚于权威提交。
- 源校验与资金占用共同排序，旧余额与源 hold 的交接必须原子，不留再次可用的窗口。
- 模式切换还迁移仓位成员、订单义务与裁决权，需要冻结、排空、准备和唯一提交点。
- h 是已分配屏障，k 是已完整应用检查点；跨域订单和成交效果还需各自的终态水位。
- 提交前可以按证据中止；提交后先向前完成，必要时以新划转／新迁移补偿，不能篡改历史。

### 最容易答错的边界

1. 把改 `margin_mode`、追加保证金和调整杠杆当成一件事。
2. 因逐仓 MM 尚未触发就允许抽资，忽略操作后的 IM、预留和未结算义务。
3. 目标先加可用、源稍后再扣；或源余额未追齐却提前解除 hold。
4. 把屏障分配成功当成旧状态已应用，或把所有冻结理解为暂停行情与风险处置。
5. 切换后仍让旧模式订单、旧触发和旧主有权创建新效果。
6. 提交结果未知时直接解冻；账务提交后通过覆盖余额“回滚”。

### 一个能检验方案的反例

Mark=84，Cross 持有 1 ETH@100、池内 40，E=24，尚未触发。用户切逐仓，只愿意给该仓分配 20，剩下 20 要放在桶外。若系统先拿 Cross 的 E=24 校验通过，再更新 mode，却不重算目标逐仓的 E=4、MM=4.2，就把本应拒绝的迁移包装成“安全切换”。

正确方案需要在唯一切换提交点之前检验目标真实资金归属：本题规则下拒绝仅分配 20 的方案；若明确分配全部 40 并完成对应账务，目标 E=24 才成立。即使准备期间价格变化、回包丢失或进程崩溃，也不能让旧池继续认领已转出的资金，不能让新池提前使用未提交资金，更不能让同一仓位同时受两套模式裁决。
