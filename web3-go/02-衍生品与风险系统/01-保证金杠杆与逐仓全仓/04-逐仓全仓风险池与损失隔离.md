# 大问题 4：逐仓和全仓如何划定损失范围与一致性边界？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 保证金 / 抵押归属 | 支撑交易风险的钱，以及哪笔钱正式分配给哪个风险范围。 | 同一个用户的钱，也不能在几个池里同时当作可用资产。 |
| 逐仓 / Isolated / 隔离桶 | 给某个仓位或风险单元圈出专用资金。 | 本例桶 20，外侧 20 不自动拿来放行订单或填补亏损。 |
| 全仓 / Cross / 共享池 | 约定池内的资金与所有成员仓位一起承担损失。 | 池有 40，不是每个市场各拥有一份 40，也不包括所有其他账户。 |
| 风险池成员 / collateral_scope | 成员表示哪些仓位和义务属于池；抵押范围表示哪些资产可用。 | 归属要有正式记录，不能仅凭页面显示“全仓”。 |
| 线性永续 / 多仓 / PnL | 无固定到期日、按数量和价差算盈亏的合约；多仓跌价亏；PnL 就是盈亏。 | 1 ETH 从 100 跌到 84，两种模式都亏 16，不再乘杠杆。 |
| Mark / U / Equity | 风险估值价格、未实现浮盈浮亏，以及余额加浮盈浮亏后的权益。 | Mark=84 时逐仓权益 4，全仓权益 24。 |
| IM / IMR / MM / MMR | 初始要求金额及其比例、维持要求金额及其比例。 | 本例分别按名义规模的 20% 和 5% 算；权益不大于 MM 才触发本文处置。 |
| Available / 名义杠杆 / 权益杠杆 | 可用于新风险的额度；仓位相对初始要求或当前权益的比例。 | 同样名义 100、IM20，全仓以权益40衡量实际比例为2.5，而非又多亏少亏一次。 |
| 资本效率 / 损失传播 | 同一池资金可支撑多个成员，但其中一个成员亏损会挤掉其他成员的缓冲。 | BTC 仓位亏损可能让原本看似安全的 ETH 也失去共享支持。 |
| 共同失败域 / 经济与技术隔离 | 一起受损的范围；资金隔离与算力、数据库等资源隔离是两件事。 | 逐仓不自动互相承担账务损失，但仍可能一起受错误行情或服务拥堵影响。 |
| owner / 权威事实 / 投影 | 状态负责人、正式记录、供查询的整理结果。 | 风险系统负责裁决，不得因想让权益变正而伪造账本余额。 |
| 池级串行化 / CAS / TOCTOU | 同池操作有共同先后；CAS 是版本未变才提交；TOCTOU 是检查与使用之间状态变了。 | 分市场各加锁，仍可能同时花掉共享的最后 20。 |
| 子额度 / 租额 / 授权水位 | 将总额度不可重复地分给执行单元，并限定使用版本。 | 总共 20 可各分 10，不能各分 20；旧授权失效须在受理边界真正拦住。 |
| reservation / consumed_im | 为未成交订单先占额度；consumed_im 记录某批批准预算已交给成交的份额。 | 历史预算去向不等于随价格重算的当前仓位 IM。 |
| transfer_id / 划转 / 在途状态 | 带唯一编号的资金归属转移；在途表示流程尚未全部完成。 | 源减少、目标增加必须可对账，中间不能两边同时花。 |
| 自动追加保证金 | 经授权，在规则触发时从其他范围正式转钱进逐仓桶。 | 这是额外策略，不等于逐仓默认就能读取桶外全部余额。 |
| 模式迁移 / migration_epoch / 切点 | 把资金、仓位与裁决权迁到新模式；代次和切点限定何时换负责人。 | 不是只把 mode 改为 CROSS，也不是复制一份资金给新池。 |
| 冻结 / 排空 / 屏障 | 停止新冲突操作，并确认旧订单、成交和结算已经按要求处理齐。 | 冻结扩险不等于停止行情和持续风险监测。 |
| 试算摘要 / 输入版本 | 记录迁移预检查究竟用了哪份价格、规则和成员状态。 | 提交前价格或资金变了就要重算，不能拿过期“通过”结果切换。 |
| 迟到成交 / 旧授权 / fencing | 已经成交但消息晚到；过期负责人发出的新指令；存储或执行端阻止旧权能生效。 | 旧授权可失效，已经确定的成交义务却不能一并丢弃。 |
| 强平 / 跳空 / 穿仓 / 追索 | 强制处理仓位；价格跨越阈值；损失超出担保资金；缺口最终向谁要求偿付。 | 逐仓约定日常风险边界，不单凭模式名保证永不穿仓或绝对免除欠款。 |
| 幂等 / 日志重放 / 不变量 | 同一业务只生效一次、按历史事件恢复，以及始终不能破坏的规则。 | 任意恢复阶段都要守住资金守恒、唯一归属、成交不消失。 |

## 把整篇文章压缩成一个故事

小林有 40 USDC，开 1 ETH 多仓，入场价 100。选逐仓时只给该仓 20，另外 20 留外面；选全仓时则让同池 40 一起支撑。Mark 跌到 84，仓位都浮亏 16，逐仓权益剩 4，全仓剩 24。维持要求同为 4.2，逐仓触线而全仓没触线，原因是可承担损失的钱不同，不是盈亏公式不同。

但全仓的 24 不是 ETH 独享的钱。文章另设双仓例子：若同池还开了 BTC 多仓，BTC 的亏损也会消耗这份权益，甚至把全池拉成负数。与此同时，ETH 和 BTC 的新订单也不能分别拿同一份剩余额度通过检查。共享资金就要共同裁决，不能各市场先放行、事后再把风险相加。

若小林想救逐仓，必须把外面的 20 正式划入，源余额变 0、桶余额变 40，权益才变 24；想切全仓，还得明确搬哪些钱、仓位和未决义务，并保证只有一个池负责。极端行情若来不及平仓，逐仓仍可能出现缺口，不能偷偷挪桶外资金抹平。全文强调的不是模式名称，而是每一时刻“谁的钱在承担哪份风险、谁有权作决定”。

**流程位置与核心机制：** 本题贯穿抵押归属、下单预留、风险聚合、资金划转、模式迁移与故障恢复。逐仓和全仓首先定义“哪些资产和仓位共同承担损失”，随后才决定公式的求和范围、准入的串行化键、处置对象和迁移协议；不是给同一余额查询换一个模式参数。

**共同前提：** 沿用专题总览与[母题01](01-保证金风险全流程与状态归属.md)：链下托管、线性 USDC 永续、单向净持仓、单一 USDC 抵押品。主例合约 `ETH-USDC-PERP`，乘数1，1 ETH在100 USDC开多，Mark有效且新鲜。账户初始40 USDC；逐仓是一仓一池，桶内20，另20留在外侧且不参与；独立比较的Cross是一子账户内单一USDC共享池，池内40。`IMR=20%`、`MMR=5%`，无档位、费用、资金费、其他仓位、挂单、锁定或外部资金变化。余额已包含已结算损益，不重复加一次。

**公式边界：** 全文公式、池边界和 `E<=MM` 触发条件都是上述简化教学模型，不是行业通用保证金、追索或强平规则。多仓位、划转、模式切换和系统异常均为显式扩展，不能把它们混回主例。真实产品还需定义法律追索、负债、支持资金、档位、抵押折扣与执行损失承担规则。

## 第1层：逐仓和全仓究竟是一种余额算法，还是一种损失承诺？

**面试官：** 一个用户总共有40 USDC。逐仓只用20、全仓用40，这只是风险引擎取余额的不同方式吗？隔离的对象到底是什么？

**面试者：** 首先是经济共担范围，其次才是余额取数。逐仓把指定抵押与一个隔离风险单元绑定；本例一仓一池，ETH仓只依赖桶内20，不能因同属一个用户就顺手读取外侧20。全仓把池内合格抵押与所有成员仓位共同估值，本例Cross的40都承担成员风险。

一个最小的池定义需要 `risk_pool_id、mode、collateral_scope、member_version、mode_version、policy_epoch`。仓位和订单预留要能指向其归属池，抵押要由账本分配记录证明归属，处置触发也必须带相同池身份和成员版本。模式不是前端枚举，而是一组贯穿准入、估值、划转与执行的契约。

逐仓的“不参与”是默认不能自动扣划、不能用于放行该桶新订单、不能拿来抬高该桶权益；若开启自动追加保证金，那是另外授权的显式划转策略，不再是本主例的资金边界。全仓的“共享”也只是这个Cross池，不是该用户所有子账户、所有币种或全平台资金天然互保。

隔离承诺还要与欠款追索和平台支持政策区分。本题先约束正常风险记账与裁决：损失由所属桶或共享池承受，不越界挪钱。若执行后出现桶外缺口，谁最终承担必须由产品与法律规则另行规定，不能只凭`ISOLATED`字段推导绝对的赔付或免责结论。

## 第2层：同样亏16，为什么逐仓触发而Cross不触发？

**面试官：** 你说池边界先于公式。现在两种模式都买1 ETH@100，Mark跌到84。请给出同一数值链，并说明全仓是否改变了杠杆或盈亏乘数。

**面试者：** 不改变这笔仓位的损益。本例线性合约 `U=q×(Mark−Entry)`、`N=|q|×Mark`，需求为 `IM=N×20%`、`MM=N×5%`；仅在本文简化模型成立。两种模式的区别是权益中的权威抵押B：逐仓20，Cross40。

| Mark | U | N | IM | MM | 逐仓E / Available | Cross E / Available |
|---|---:|---:|---:|---:|---:|---:|
| 100 | 0 | 100 | 20 | 5 | 20 / 0 | 40 / 20 |
| 90 | -10 | 90 | 18 | 4.5 | 10 / -8 | 30 / 12 |
| 84 | -16 | 84 | 16.8 | 4.2 | 4 / -12.8 | 24 / 7.2 |

此表Available按无订单、无锁定的 `E−IM` 计算。Mark84时逐仓 `4<=4.2`，满足本例处置条件；Cross `24>4.2`，未满足。若风险引擎错误地把外侧20算入逐仓，就会得到24并漏触发，这不是估值误差，而是越过了资金归属边界。

开仓IM都是20，对应名义敞口相对所需IM为5倍；Cross实际敞口相对全池权益是 `100/40=2.5` 倍。主例从100跌到84，两边都亏16，不是逐仓亏80或Cross亏8。Cross的缓冲更大只是它让更多已归属资金承担同一亏损。

Available和处置也不能混淆。逐仓90时Available−8，不允许按普通准入再扩大风险，但E10仍高于MM4.5。逐仓84触发只说明需要风险处置，不表示能按84成交；Cross未触发也不表示外侧资金或其他子账户可以任意提走。

## 第3层：Cross提高资本效率，为什么也会扩大共同失败域？

**面试官：** 你把Cross多出来的20称作缓冲。若这20又支持了另一市场的仓位，ETH是否还能认为自己独享这份缓冲？请给出损失传播的具体反例。

**面试者：** 不能。共享权益不是为每个仓位复制一份保证金。做一个独立扩展：在主例开仓时的Cross池中再买入 `0.01 BTC@10000`，BTC合约也为乘数1的线性USDC永续、使用相同IMR/MMR，不引入费用和资金费。此时ETH名义100、BTC名义100，总IM40恰好由池内40支持，新增风险额度为0。

随后ETH Mark84、BTC Mark仍为10000：ETH U−16、BTC U0，池权益24，总名义184、总MM9.2，尚未触发。若BTC Mark再跌至7500，BTC U为 `0.01×(7500−10000)=−25`，当前名义75；池权益变成 `40−16−25=−1`，总名义159、总MM7.95，已经满足风险处置条件。这里仅做跳价后估值推演，不保证系统能在此之前完成处置，也不声称这是某种发生频率。

原来只看ETH的单仓主例时，Cross E24显得充足；新增BTC亏损却能吃掉ETH依赖的同一份权益。不能继续给ETH显示“还有独立24”并各自下单。若其他仓位盈利，U也可在本例Cross中抬高池权益，但本例MM仍按各仓当前名义需求相加，没有组合保证金的对冲减免。

逐仓的资本效率代价恰好相反：只要没有显式划转，别的桶或外侧资金再充足，也不能自动挽救ETH桶。产品可以允许用户重新分配资金，但这是一笔改变归属的操作，不是计算器自动“找一个有钱的仓”补进去。隔离降低跨仓污染，共享提高复用并扩大共同失败域，这才是模式取舍。

## 第4层：经济共担范围怎样映射到账本、仓位和风险状态？

**面试官：** 上一层同一份权益支持了多个市场。系统有账本、持仓、订单和风险四个服务，怎样保证大家讲的是同一个池，而不是四套各自正确的归属？

**面试者：** 先定义权威事实和不可重叠的归属，再允许各服务做投影。不能在每个服务各加一列`mode`就宣称完成隔离。

| 状态 | 权威所有者 | 必须携带的池边界证据 |
|---|---|---|
| 抵押分配、结算和划转 | 账本／抵押品域 | 资金来源、目标池、分配金额、划转身份和账本版本 |
| 净持仓及成本 | 持仓／清算域 | 仓位身份、市场、数量、归属池及生效版本 |
| 未决订单与预留 | 订单域及风险授权记录 | 订单身份、池身份、成员版本、未决量和占用 |
| 有效Mark与风险规则 | 行情域与参数域 | 价格身份／质量、配置版本、计算规则 |
| 池级权益和风险裁决 | 风险池owner | 已应用序号、完整输入摘要、状态和原因 |

账本一个逻辑分配可以落在多笔明细里，但同一份USDC不能同时作为外侧可花余额、逐仓可用抵押和Cross可用抵押。仓位在一个生效模式版本上只有一个风险归属；迁移中的中间态可以显式存在，但不能两个池同时取得对它的准入与处置权。

风险引擎能重算派生状态，不能为使权益对上自行修改账本。查询服务可以汇总多个桶显示用户总资产，但该汇总不是任何单桶的准入余额。价格和配置可以共享来源，资金占用与成员关系仍必须按池隔离。

因此，逐仓的正常风险计算可以按桶并行；Cross的一个逻辑切点必须覆盖全部共担成员。物理上是否同进程、同库或同分片是实现选择，逻辑上必须能证明余额、仓位和义务属于同一成员版本，而不是拼接各服务的最新值。

## 第5层：Cross为什么不能按市场各锁一把锁？

**面试官：** 你允许不同逐仓桶并行，又说Cross覆盖全部成员。若Cross的每个市场各自使用Go channel串行处理订单，再异步上报池级汇总，为什么仍然不安全？

**面试者：** 因为市场锁保护的是市场内顺序，不保护共享抵押的唯一使用权。回到只有ETH主仓、Mark100的Cross主例：E40、现仓IM20、Available20。两个市场各自读取这20，分别批准需15的新订单，就会承诺30新增需求，总需求50超过40。

正确做法是在共享 `risk_pool_id` 的同一逻辑顺序上检查并建立预留。第一笔占15后Available变5，第二笔不能再依据旧版本批准15。划出是从池中移走共享抵押，同样须与该池新订单准入共用池级顺序：若先批准占15，随后划出必须基于剩余5及操作后风险状态重判；若先提交划出，后到订单只能读取扣除划出后的版本。任何会减少共享权益或新增优先义务的操作也必须纳入同一顺序或等价的版本CAS，例如提款、手续费扣收和周期结算；本主例费用与资金费为0，这些是扩展操作，不能因不在简化算例中就绕开Cross额度裁决。把划出或提款放在独立钱包锁上、却让订单仍使用旧池状态，依然会超额承诺。池owner可负责排序，但耐久提交还需把预留、资金移出或义务入账、池版本、命令结果和交付意图一起推进；数据库条件更新或另一套可证明等价的协议也可以。

部分成交时，风险需求从订单预留转为仓位IM，跨市场仍共用这一池级顺序。历史 `consumed_im` 只记录某次批准额度怎样流转，不等于今后随Mark和配置变化的当前仓位IM。重估、补额和撤单释放需要新的明确版本或追加身份，不能悄悄改写历史批准。

如果单一热门Cross池吞吐成为瓶颈，可以分配保守子额度：例如把当前20可用额不可重复地租给两个执行单元各10，市场只能在租额内批准；租额授权绑定池级风险水位、参数和成员版本。订单受理与有效版本比较须在同一授权提交边界原子裁决，不能先查旧水位、随后无条件受理。Mark、配置或池成员变化使池级可用额度下降时，中心owner推进风险水位，并在该提交边界围栏旧授权上的新增受理；受理端不能只靠稍后送达的异步失效通知。围栏前已确定的受理必须计入未决义务，围栏后的旧版本受理拒绝；随后按新状态重算／重分配未用额度。已经被订单预留占住的额度不是空闲租额，须重新估值并作为在途义务处理；若重估出现缺口，停止扩险并按策略撤销未受理余量或处置已承诺订单，不能静默把额度借给其他市场。回收和再分配也须有版本、围栏及未决义务证明；若不能实现这条共同提交边界，就仍用池级协调，不把异步子额度方案当作安全优化。代价是额度碎片、协调与回收复杂度，不能把每个市场都发20称为分片优化。

逐仓桶虽可分别准入，仍共享同一用户外侧资金来源。若两个桶同时请求追加保证金，源账户扣款必须在源资金域协调，不能因目标桶隔离就让同一20被两个目标各领一次。经济隔离不是所有跨域协调都可以删掉。

## 第6层：从外侧划20进逐仓桶，什么时候才能改变风险结论？

**面试官：** 你说目标桶并行不等于资金来源独立。现在逐仓Mark84、E4，用户想把外侧20全部追加，系统哪些阶段可以把E展示或裁决为24？

**面试者：** 回到原逐仓主例，没有其他仓位。用户请求本身不能使目标权益增加；源资金预占也只表明这20暂时不能再被别处使用，不表示目标已获得可用抵押。源校验、预占和划转提交须与每个受影响风险池的owner及模式迁移门禁共用可比较的 `pool_epoch/migration_epoch` 或等价耐久排序；若来源是风险池，须包含源池，若目标是风险池，须包含目标池。迁移fencing必须在权威提交边界生效：账本事务须条件校验 `source_version、source_pool_epoch、target_pool_epoch、migration_state`，或由同一耐久协调日志串行决定门禁与转账提交；只在风险服务先查状态、依赖异步通知再提交账务不够。权威账本划转事务提交时，账本中的来源余额减少20、目标桶余额增加20；风险池只在应用了该账本版本后，才以桶余额40和新版本重算并用于准入裁决，E由4更新为24。期间查询与风险准入要分别标明账本事实版本和风险应用水位，不得提前使用尚未应用的目标余额。

```text
创建transfer_id并记录来源、目标、金额及预期版本
    → 校验并预占源外侧20，检查目标处置／迁移状态
    → 权威提交借记外侧20、贷记目标桶20的账务效果
    → 目标应用该账本与归属版本，重算E、IM、MM
    → 交付完成结果；查询投影随后更新
```

若源与目标同属一个可事务化账本，两边分录和状态可在同一事务提交。若跨存储域，本题选择显式在途账户／不可支用的转账状态衔接：源确认扣划后目标按同一 `transfer_id` 入账，在途期间两端不能同时支用；通过恢复续跑消除在途项，而不是宣称跨服务RPC天然原子。金额对账必须能解释源减少、在途与目标增加的总和守恒。

主例提交前总归属为外侧20、桶20；提交后外侧0、桶40，总计仍40。Mark84的未实现亏损始终−16，所以用户总体风险估值在两边都是24；变化的是ETH桶可依赖的范围，不是凭空赚了20。目标IM16.8、MM4.2，划入后的Available为7.2。

若划转响应超时，沿原身份查结果，不能重复加20或直接回退源余额。若风险处置已经启动，追加资金是否被允许、是否能终止处置须按执行状态机校验；即使新E超过MM，也不能撤销已经确定的平仓成交。划出也必须检查操作后目标池约束，不能绕过挂单预留只看现金足不足。

## 第7层：直接把逐仓模式改成Cross，为什么比划转更复杂？

**面试官：** 追加20需要这么多归属证据，那用户说“我不划转了，直接把现仓从逐仓改成全仓”，能不能把mode改一下就让外侧20生效？

**面试者：** 不能。模式切换同时改变抵押、仓位、订单和处置的责任范围；资金划转只改变一笔抵押归属。为了讲清可实现边界，本题采用保守策略：只在无未决订单和预留、无在途成交／结算／划转、无活动风险处置时，允许保留仓位进行模式迁移。否则明确拒绝或先进入受控排空，不能假称无缝支持所有状态。

迁移发起时，`MIGRATING` 门禁与源池转账提交须争用同一控制版本／耐久排序；先胜出的动作决定后续路径。若旧epoch下的划转提交先胜出，迁移必须读取更新后的账本与池版本再启动；若门禁先胜出，则推进 `migration_epoch` 并阻止扩险和新跨边界划转，记录 `migration_id、from_pool、to_pool、start_seq、old_mode_version、new_mode_version`，该旧epoch划转的账本提交CAS失败，hold 保留至同一 `transfer_id` 得到权威中止终态。所有旧epoch转账都终结后，才可建立迁移清单和切点；不能让迟到的账务效果落入已迁走的源桶。直至归属切点提交，源池仍是仓位和抵押的唯一风险owner，按源池有效Mark和参数继续做持续风险检查；若触发风险处置，冻结迁移，在源池按现行版本处置或等待规则允许后再重启迁移，不能因已进入迁移态而暂停风险责任。主例资金费与费用仍为0；若扩展为存在周期结算或其他按时间／序号生效的账务事件，也必须明确切点归属：切点前归源池并在清单中结转，切点后归目标池，不得两边重复应用或两边都漏掉。随后请求订单与撮合的停止受理／排空屏障，取得终结水位，并使所有成交与结转追到该水位。只看到订单查询“数量0”还不够，在途成交可能尚未投影。

屏障完成后才建立清单：哪些仓位、抵押、结转义务与成员关系将迁移。目标池按有效Mark和一整版参数试算，并记录 `trial_input_digest、price_id、config_version、source_seq、target_seq`。若尚有未决义务、处置状态不允许或不满足目标初始要求，就不提交归属切换。真正提交时必须在同一迁移协调边界校验试算绑定的Mark、参数、源／目标池水位和成员版本仍有效；任一变化就冻结提交、重建清单并重试试算，不能用过期试算切换。风险触发与归属切点须争用同一控制版本：若 `E<=MM` 的处置先提交，迁移保持冻结且由源池继续负责；若切点先提交，后续风险事件只由新归属池处理，旧池不得按旧版本再执行一次。不能出现两池都处置或切点窗口无人负责。源与目标若都能接收并发命令，需要统一迁移协调顺序或按确定键序锁定，不能两个池互相等待还继续放行。

独立举例：在主例Mark100且无其他义务时，把逐仓仓位连同桶20与外侧20迁入一个新的空Cross池。账务来源明确是“借记旧桶20、借记外侧20、贷记新Cross池40”，即 `20+20=40` 的迁移而非复制；完成后空目标池余额40、仓位1、E40、IM20，旧桶和旧外侧可支用金额均归零。这里的40是切点后的目标余额，不是迁移前已有余额；若目标池迁移前另有独立抵押40，且两笔来源资金均实际转入，则切点后目标余额应为80，再按全部成员重新聚合风险。必须区分目标池迁移前余额与迁入后的目标总额，不能把某个阶段的40和已包含其中的旧桶20重复相加。同样，目标已有其他成员时，须基于目标真实余额和成员状态重新聚合，不能覆盖它的余额。

最后在一个明确的归属提交点使新成员版本生效并撤销旧池权能，再解除目标门禁。若不能单库事务完成，就以耐久迁移状态机保证中间态不可支用、可恢复，直到终态才向用户承诺完成。失败只可在切点前安全放弃，或在切点后续跑／记审计补偿；不能直接覆盖余额和pool_id来“回滚”。

## 第8层：排空后还有迟到成交，或者旧owner复活，怎么证明没有被切换吞掉？

**面试官：** 你依赖屏障和模式版本。假如旧模式的成交消息在新池生效后才到，旧owner也拿着旧内存继续写，系统应该丢弃这些消息吗？

**面试者：** 先区分“消息迟到”和“业务事实在切点后才产生”。一个成交已经确定就不能因旧 `mode_version` 而丢掉；但旧owner在失去权能后发起的新授权，必须被拒绝。源事实与准入权是两种不同的东西。

在第7层保守迁移协议下，所有屏障前已确定成交应该在归属切点前结转。若新池生效后收到它的重复通知，通过 `fill_id`、已应用序号和迁移清单证明已处理，返回原效果，不再改仓位。若通知晚到且从未被结转，说明屏障证据、事实水位或迁移门禁被违反，不能当普通旧消息静默跳过。

这类异常要冻结相关池的扩险，查找撮合权威事实及其原始责任归属，按原成交身份补齐义务，再根据耐久迁移映射结转到当前归属；产生可审计修复记录，不能随意把成交塞进两个池，也不能因为源池已经关闭而把它变没。正常模式切换只支持上一层已声明的干净切点，异常修复不等于对外承诺支持任意在途迁移。

旧owner的写入通过更高 `owner_epoch` 在存储侧围栏；旧模式的授权还要由撮合接入校验模式／策略版本及门禁，不能只在风险服务内存里拒绝。旧授权在门禁之前已被撮合接受的，必须纳入排空；门禁之后不允许继续生成新可执行义务。

恢复依赖 `migration_id、transfer_id、fill_id、member_version、mode_version、owner_epoch` 和连续日志，不能仅恢复一个`mode=CROSS`字段。相同迁移重试续跑原状态；同一身份不同载荷要隔离。资金总量、成员唯一归属与未决义务都对齐后，才能重新开放准入。

## 第9层：逐仓真的只会损失桶内20吗？

**面试官：** 你把跨池挪用和旧权能都堵住了。若价格跳空穿过风险阈值，逐仓还会不会欠钱？Cross是否只是“更安全的逐仓”？

**面试者：** 逐仓隔离正常担保范围，不保证执行损失天然以20封顶。本例连续估算逐仓满足 `20+(P−100)=0.05P` 的交点约84.210526；这只是无费用、无滑点、无离散舍入的触发边界，不是成交保证。若跳到70才产生执行机会，先按Mark估值会得到 `E=20−30=−10`、MM3.5，说明桶已出现风险缺口；此时未实现亏损不等于已经完成的现金结算。

如果进一步独立假设确实在70全部平仓、费用仍为0，仓位损失确定为30，原桶20不足10。缺口由保险、平台资本、对手方规则或其他明确约定如何承担，属于风险瀑布与追索政策。本例不预设这些支持，也不允许为了把桶余额“补成非负”而偷偷扣外侧20。

Cross在只保留ETH主仓且Mark70时E为 `40−30=10`，高于MM3.5；代价是池内40都暴露在这笔风险下。如果更多成员同时亏损，Cross也会穿仓；在第3层双仓扩展里已经得到负权益。资本更多不等于风险上限更小，最终还取决于总敞口与损失相关性。

隔离还分为经济失败域和技术失败域。一个桶的坏账不应通过错误记账污染外侧或其他桶；但它们可能共享行情、数据库和计算资源。Mark异常会影响多桶，热门Cross重算也可能压满公共线程池。需用池身份做权限与账务隔离，用资源配额、背压和明确保护策略控制技术传播；不能因为按桶分了map就声称所有失败域已经隔离。

## 第10层：怎样检验资金边界、迁移切点与损失传播确实成立？

**面试官：** 你既没有承诺逐仓绝不穿仓，也没有把Cross当成无限互保。现在给出能检验边界而不只是演示公式的用例，以及每种错误会暴露什么。

**面试者：** 我会按“公式、归属、并发、迁移、失败域”分别设断言，并保留中间提交证据。

先固定主例的100、90、84金标准。特别是Mark84逐仓E4触发、Cross E24不触发；将未划转的外侧20直接加入逐仓时，测试必须失败。查询层即使显示用户总体估值24，也不能以该汇总替代逐仓E4的准入和处置。

再检验共享传播。第3层双仓扩展在ETH84、BTC7500时应有U合计−41、E−1、N159、MM7.95；若ETH仍被当作独享E24而继续扩险，说明按市场拆分了真实共担范围。并发两笔各占15、Cross可用20时最多一笔完整通过；订单占用15与提款／划出15并发时，也只能按同一池序中的先后结果裁决，不能都读旧Available20后通过。手续费或周期结算若扩展启用，也须进入影响池权益的同一顺序。两个隔离桶同时从外侧20各请求追加20时，源资金最多完成一笔，而不是目标各自算得够就双付。

划转测试逐阶段注入超时、重复与崩溃。主例追加20的终态必须是外侧0、桶40，Mark84下桶E24；在途阶段金额能被账本分配与在途账户解释，不能外侧仍可花20、桶又可用40。重试同一transfer_id不得再增加20。

迁移测试覆盖订单排空前拒绝切换、旧epoch转账在门禁前受理但未终结时不得生成切点、门禁与旧epoch转账提交竞争时仅一个CAS胜出，胜负结果分别更新迁移输入或拒绝转账且保留hold、屏障前成交先结转、风险触发与切点竞争时只有一个控制版本胜出、切点后重复消息不重复生效、新旧成员版本不重叠、旧owner写入被围栏。若注入违反屏障的未结转旧成交，应进入冻结与修复路径，而不是直接丢弃。成员迁移不能改变用户总抵押，也不能漏掉债务或未决预留；目标试算后修改Mark或IM/MM配置，过期摘要必须导致提交CAS失败并重算。

最后做两个不同层次的隔离检查：模拟一桶价格跳到70并验证没有自动越界扣外侧资金；模拟一个池积压，检验其他池的资源与门禁策略，而不是声称经济隔离自然保证服务不受影响。本文给出的是设计推演、数值和测试断言，没有运行生产强平、数据库故障演练或性能验证，不能把它们写成已有实践证据。

## 本题收束

### 已经讲透的机制

- 风险池先定义损失共担与抵押归属，再定义Equity求和、准入序列和处置对象。
- 逐仓20与Cross40改变缓冲和可参与资产，不改变1 ETH本身的线性盈亏。
- Cross复用权益，也让成员亏损传播到全池；逐仓提高隔离性，但会留下闲置资金与单桶缺口。
- 分片必须尊重经济共担：Cross按池协调额度，逐仓跨桶划转仍需协调来源资金。
- 划转有账务身份与在途状态，模式迁移还需排空屏障、成员切点、门禁和恢复映射。
- 迟到确定成交不可丢，过期授权与旧owner不可继续创造义务；两者必须分别处理。

### 最容易答错的边界

1. 同一用户的资产就能随时参与任一逐仓桶，或Cross天然覆盖所有子账户。
2. 各市场独立批准共享池额度，再异步汇总就能保证不超用。
3. 历史预留消费额永远等于当前仓位IM，或重估可以改写历史批准。
4. 划转请求已发出就把资金计入目标，源端却仍可花费同一金额。
5. 只改mode或pool_id就完成模式切换，查询无订单就等于没有在途成交。
6. 旧版本成交一律丢弃，或旧owner靠进程内锁就能停止写入。
7. 逐仓绝不穿仓、Cross没有风险，或经济隔离等于基础设施完全隔离。

### 一个能检验方案的反例

原主例逐仓桶20、外侧20，Mark84时E4已触发；若系统未经已提交划转就按40计算E24，它直接违反隔离承诺。若用户随后确实追加20，正确终态才是外侧0、桶40、E24，重试不得再加一次。

再把相同总额迁移为Cross：切点前后总抵押仍40，仓位只有一个风险归属，旧授权不可在新模式下偷偷生效。若两个池都能各自凭40放行订单，或某笔旧成交因模式版本过期被丢掉，说明迁移没有守住一致性边界。总体状态所有权与承诺阶段见[母题01](01-保证金风险全流程与状态归属.md)。
