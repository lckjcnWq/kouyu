## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 保证金 / 逐仓 / Cross | 承担交易风险的钱；逐仓只用指定桶，全仓共享约定池。 | 资金属于哪个池，也是风险快照必须证明的事实。 |
| 线性永续 / 仓位 / 敞口 | 无固定到期日、按数量乘价差算盈亏的合约；仓位是未结束交易；敞口是价格风险规模。 | 漏掉刚成交的0.5 ETH，就漏掉一半真实风险。 |
| Mark / Entry / U / N | 标记估值价、入场价、未实现盈亏、当前名义规模。 | 1 ETH@100、Mark84时，U=−16、N=84，不能漏成交后仍按0.5计算。 |
| Equity / IM / MM / Available | 当前风险权益、初始要求、维持要求、扣除占用后可新增风险额度。 | 本例逐仓E4低于MM4.2；公式对了但输入拼错，一样可能误判安全。 |
| 源事实 / 派生结果 / 投影 | 正式业务记录、据此计算的结论、供查询的副本。 | 风险系统不能为了补快照，自己创造一笔余额或成交。 |
| 一致切点 / 风险快照 | 一组数据在明确业务进度上的可解释组合，不只是同一秒读到。 | 必须说明哪些成交、划转、订单和规则已经包含。 |
| 版本向量 | 不同来源各记自己的版本，再一起说明本次用了哪几版。 | ledger57、position44不是可以随意比较大小的同一种序号。 |
| account_seq / source_seq | 池内业务顺序号与来源自己的顺序号。 | 它们提供各自顺序，不自动让跨服务的账务和持仓一起完成。 |
| 屏障 h / 检查点 k / seen_max | 安排好的处理界线、连续完整处理位置、曾见到的最大号码。 | 看到了121但缺119，只能说见过121，不能说已处理到121。 |
| domain_effect_watermarks / 未决义务 | 各部门已处理齐的进度，以及已经发生但没记齐的业务影响。 | 成交通知已到、余额或仓位未到，仍须保留该成交风险。 |
| 因果前置 / 屏障快照 | 一项变化依赖另一些变化先被覆盖；屏障快照证明一个区间的相关效果都在其中。 | 预留消失时，成交风险必须由真实仓位或明确在途记录接住。 |
| event_time / receive_time / wall-clock | 事件产生时间、收到时间、机器普通时钟时间。 | 网络和时钟偏差会打乱到达顺序，不能靠时间接近证明一致。 |
| price_id / 新鲜度 / quality | 价格身份、数据是否足够新、来源质量是否合格。 | 版本没倒退，不代表价格没有过期；两项都要查。 |
| config_version / effective_seq | 一整套参数的身份及其生效位置。 | 不能IM用新参数、MM用旧参数，回滚也应发布新版本。 |
| formula_version / rounding_version | 用哪个公式和哪套小数取整规则计算。 | 同一原始数据换了舍入规则，可能产生不同风险结果。 |
| RiskResult / decision_id / input_digest | 风险结果、裁决编号、规范化输入摘要。 | 记录“本次为何通过或触线”，供复算、去重和下游校验。 |
| canonical / 规范化编码 | 固定单位、字段顺序和表达方式，让相同输入有相同表示。 | 摘要不是随意把几个展示字符串拼起来。 |
| CAS / 预期版本 / 原子占额 | 仅在读到的状态仍有效时提交，并同时占住所需额度。 | 算完后若钱被转走，旧的“可下单”不能继续生效。 |
| 影子敞口 / 在途覆盖 | 正式持仓未追齐时，临时且有身份地覆盖确定成交风险。 | 最终仓位到了要正确替换，不能漏算，也不能永久加成两份。 |
| 迟到 / 重复 / 乱序 / 幂等 | 消息晚到、重复来、顺序被打乱；幂等保证同业务只生效一次。 | 旧价格不覆盖新估值，但迟到的真实成交不能扔掉。 |
| 快照 / 连续日志 / 重放 | 保存恢复锚点，再按之后的完整记录恢复状态。 | 重放历史结果用原规则，不能临时读取现在的价格替换。 |
| owner_epoch / fencing / Outbox | 负责人代次、拦旧负责人写入、持久保存待交付结果。 | 换主不改业务事实，通知丢失也只补发原结果。 |
| 缺口 / UNKNOWN / reason_code | 中间记录缺失、当前不可可靠判断、明确的错误原因。 | 不完整就限制扩险，不能把算不出来默认成安全。 |

## 把整篇文章压缩成一个故事

小林的逐仓桶有20 USDC，已经在100买成1 ETH，但风险服务暂时只看到旧仓位0.5。行情先送来Mark84，订单预留又已经被移除。若程序拿“每个服务最新的一条”直接拼接，就只算出一半浮亏、漏掉一半仓位，看似还能交易，实际上完整仓位应浮亏16，权益4，低于本文MM4.2。

正确做法是给各来源标进度：这份余额包含哪些流水，这份仓位包含哪些成交，预留处理到哪里，价格与规则是哪一版。看到编号121却缺119，不代表已完成121；要等缺口补齐，或由可校验快照证明完整效果。等待时可以按已证明的在途义务覆盖风险，不能无依据地释放，也不能等正式仓位到来后重复叠加。

即使输入齐了，算完到批准之间资金仍可能被转走，所以提交前还要比较相关版本，并把批准和占额度一起落下。价格过期、规则半更新、日志缺失，都应明确限制扩险，不拿旧“安全”兜底。崩溃后按同一输入和原规则重放。全文要证明的不是每个字段都最新，而是这些字段放在一起，确实讲得出同一段业务历史。

**流程位置与核心机制：** 本题位于跨域输入到风险准入、持续风险判定及处置交付的交界。核心是定义“同一时点”在异步账本、持仓、订单、行情与参数域里的可验证含义：风险结果必须绑定可重放的版本向量、连续应用检查点和一致的生效规则，拒绝把各服务恰巧最新的字段拼成从未存在过的账户状态。

**共同前提：** 沿用[总览的讨论基线](README.md#一文字全流程保证金风险如何从下单走到可解释的账户结果)：链下托管、线性 USDC 永续、单向净持仓、单一 USDC 抵押品，合约乘数为 1，`IMR=20%`、`MMR=5%`。账户初始 40 USDC；逐仓单仓桶 20，另 20 在桶外；Cross 池 40。主例为多 1 ETH@100，资金费、费用、档位及其他义务为零，已结算损益已计入余额。风险条件是 `E <= MM`，不代表执行完成。

| Mark | U | N | IM | MM | 逐仓 E | Cross E |
|---:|---:|---:|---:|---:|---:|---:|
| 100 | 0 | 100 | 20 | 5 | 20 | 40 |
| 90 | -10 | 90 | 18 | 4.5 | 10 | 30 |
| 84 | -16 | 84 | 16.8 | 4.2 | 4，触发 | 24，不触发 |

数值及费率仅为教学模型，不是行业通用值。主例没有挂单和其他在途义务；涉及它们时，会单独说明如何计入快照，不将未说明的仓位偷偷合并。

## 第 1 层：每个服务都给最新值，为什么不一定是同一时点？

**面试官：** 风险服务读到最新余额 40、最新仓位 1 ETH、最新 Mark 84、最新 MMR 5%。它计算 E=24、MM=4.2。既然都是各自最新，能说结果一定正确吗？

**面试者：** 不能。四个“最新”可能对应不同的业务序列位置，组合状态从未同时存在。例如 40 是划转前余额，1 ETH 是成交后仓位，Mark=84 已经有效，而新成交的账务／持仓结转还没到齐。算式正确，输入组合仍可能不成立。

对于给定的权威快照，公式是：

```text
U = q × (Mark − Entry) × multiplier
N = |q| × Mark × multiplier
IM = N × IMR
MM = N × MMR
Equity_iso = 已归属该仓桶的账本余额 + U
Equity_cross = 池内账本余额 + 池内仓位 U 之和
```

所以 Mark=84 的逐仓主例应是 `20−16=4`，Cross 是 `40−16=24`；计算必须明确对应哪个余额和仓位版本。账户外的另 20 不能因被读到就加入逐仓余额。

时间戳相近也不能证明同一切点。一个事件的产生时间、源提交时间、网络抵达时间、消费者应用时间不同；时钟偏差和重试会改变抵达顺序。风险裁决需要业务因果版本或屏障证据，而不是按 wall-clock 把字段排序。

## 第 2 层：一个可审计的 RiskResult 应绑定哪些版本和身份？

**面试官：** 既然“各自最新”不可靠，RiskResult 需要保存什么才能重算？仅记录一个 `snapshot_time` 或最大 offset 可以吗？

**面试者：** 不够。结果必须描述风险池身份、确切输入水位与规则版本，以及可复现的输入摘要。至少包括：

| 分组 | 必须明确的身份或版本 |
|---|---|
| 风险边界 | `risk_pool_id、mode_version、member_version、collateral_scope` |
| 账本 | `ledger_version、ledger_account_seq、balance_digest、pending_settlement_watermark` |
| 持仓 | `position_version、position_exec_seq、position_digest` |
| 订单／预留 | `order_version、reservation_version、order_exec_watermark、unresolved_obligation_digest` |
| 价格 | `price_id、source_id、market_seq、event_time、receive_time、quality、freshness_policy_version` |
| 参数 | `config_version、tier_version、effective_seq、rounding_version` |
| 裁决 | `decision_id、risk_input_epoch、account_seq、owner_epoch、formula_version` |
| 输出 | `equity、IM、MM、available、status、reason_codes、canonical_input_digest` |

`snapshot_time` 只说明某个时钟读数；最大 offset 只说明见到过多远，不证明中间没有缺口。摘要必须采用规范化编码、固定单位和字段顺序，对相同版本输入得到相同摘要。金额计算精度、舍入规则和公式版本也属于可复现性，而不是实现细节。

RiskResult 是在这些源事实上的派生裁决，不成为账本余额或持仓的权威所有者。强平工作流若消费它，应同时核验其输入版本仍适用；查询投影可滞后，但不能反向覆盖风险裁决版本。

## 第 3 层：有账户序号时，它到底能解决什么？

**面试官：** 如果给同一风险池所有变更分配单调 `account_seq`，是不是只要有这个序号，风险快照就天然一致？

**面试者：** 序号可以提供池内业务排序，但不能自动让不同域的效果在同一数据库事务中完成。它要有明确分配者、持久提交语义、事件身份、缺口处理与消费者应用水位。

对会改变池状态的事实，例如账本划转、成交结转、预留建立／消费／释放和模式变更，应存在可比较的顺序。事件序号 119 已分配但未应用，120 已到达，消费者的 `max_seen=120` 不等于连续应用到 120。需要 `applied_contiguous_seq=118` 这类检查点；缺 119 就不能把池宣布为版本 120。

价格更新可能来自独立行情序列，参数更新也可能是控制面发布。它们未必合理地占用每个账户的同一全局流水。账户序列不能替代价格和配置的来源身份、生效边界及新鲜度判断。

因此我会分开记录：事实序号、已经完整应用的连续检查点、跨域待结转义务、价格行情水位、配置有效版本。它们通过风险池裁决规则形成输入版本向量，不是把不同域的整数硬拼成一个“全局版本”。

## 第 4 层：分布式源域没有共同事务，怎样构造可解释切点？

**面试官：** 账本、持仓、订单和行情各自独立写入，没有一个涵盖它们的数据库事务。你如何证明所选版本向量对应一个可接受的逻辑状态？

**面试者：** 先明确哪些事实之间有因果依赖，再建立可核验的一致性屏障。确定成交发生后，仓位及相关账务必须能追溯到该成交身份；预留不能在成交结转前消失；划转目标不能早于权威账务提交可用。价格与参数则按已定义的行情水位和有效版本选择，并检查新鲜度。

可行的协议形态包括：账本／持仓事件通过稳定 `trade_id` 和版本屏障协调；风险池 owner 仅在依赖版本连续时应用事件；或者风险快照服务从不可变源版本构造 barrier snapshot。选择哪种取决于系统边界，但必须能回答“这个切点包含了哪些事件、缺了什么、哪些在途义务仍在”。

一份候选向量例如：

```text
ledger=57, position=44, order=83, risk_pool_seq=121,
price_id=ETH-8841, config_version=12, mode_version=3
```

只有当 121 所需的账本、持仓和订单前置效果都已连续应用、对应成员模式仍为 3、价格 id 符合选定水位与新鲜度策略、配置 12 在该裁决点有效，才可计算。这个向量是说明，不暗示所有系统都使用这些编号。

如果服务无法提供稳定版本、快照屏障或关联事件身份，风险侧就不能证明彼此一致。可以拒绝扩大风险，等待补齐；若使用保守影子敞口，也要说明如何避免仍在仓位中的同一成交被双计，不能把“保守”变成不可解释的重复扣减。

## 第 5 层：水位 h 已经分配，为什么还要等 k 追上？

**面试官：** 风险输入协调器分配屏障 `h=121`，行情与余额读取也都返回了。可应用检查点只有 `k=118`。是否可以用屏障后到的某个快照跳到 121？

**面试者：** 不能只凭屏障已分配就跳过。`h` 表示已有一个持久排序位置；`k` 表示已连续、完整应用到的位置。若 119 是成交导致的仓位变化、120 是对应账务或预留交接的一部分，直接读取新的余额、旧仓位再宣称到 121，仍会形成不存在的组合。

系统可以通过校验过的源快照安全恢复水位，但快照必须明确包含至哪个序号、覆盖哪些域和待处理义务，并以原子检查点替代被压缩的事件区间。此时不是“跳过缺口”，而是证明快照已经包含该段完整效果。

本题将进度字段拆开：

- `allocated_high_watermark=h`：已分配／持久化的屏障位置。
- `applied_checkpoint=k`：连续完整应用的位置，不得越过缺口。
- `seen_max_seq`：收到的最大事件号，仅供诊断，不能作完成证明。
- `domain_effect_watermarks`：账本、仓位和订单各自已完成的效果位置。
- `unresolved_obligation_ids`：已确定但跨域效果尚未齐全的业务义务。

成交消息 119 已应用，但对应账务还没到，则账户序号可能推进，域效果水位仍显示未结转义务。风险计算须用明确的在途义务覆盖或暂停扩险，不能声称 `k=121` 代表所有域已齐。

长时间缺口要告警、限流或停扩险，并由拥有该水位的恢复流程查询原事件、重放或用可校验快照修复。把最大 offset 写进数据库并不能修好序列断裂。

## 第 6 层：价格和参数也会变化，版本向量如何避免“半新半旧”？

**面试官：** 账户事件已追齐，但 Mark=84 比旧价格更新，MMR 参数也在切换。能否仓位用新 Mark、IM 用新参数、MM 仍用旧参数先算一个结果？

**面试者：** 不能把一次规则发布拆成未声明的混合。价格与参数都有独立身份及生效契约，应在风险裁决边界选择明确版本，并将其连同仓位与余额版本记录。若参数包内 IMR、MMR、档位、舍入规则共同发布，必须作为一个原子 `config_version` 生效，不能各读各的 latest。

本例参数固定 `IMR=20%`、`MMR=5%`。同一仓位在 Mark 100、90、84 分别得到 `(U,N,IM,MM)=(0,100,20,5)、(-10,90,18,4.5)、(-16,84,16.8,4.2)`。若新价格身份为 84，逐仓 E=4、Cross E=24；不能拿旧 Mark 90 的 MM=4.5 配新 Mark 的权益冒充某个价格切点。

行情源应区分事件时间、接收时间、行情序号、质量与有效期；旧消息重送不能覆盖已经应用的新版本。若价格迟到但序号更新，按行情域规则判断是否可用；墙钟时间较新的旧版本不一定更权威。价格失真或超过新鲜度门槛时不扩险，并使用预先定义的保护策略，不能把陈旧价标记成“同一时点”。

参数配置需要有不可变内容、发布身份、生效序号／时间规则和回滚身份。配置回滚也是一个新版本，不删除历史。某个风险结果重放时，必须用其原参数版本重算，不能默默拿当前参数替换。

## 第 7 层：算完风险后，怎样避免提交前输入又变了？

**面试官：** 读取屏障、计算都完成了，但结果返回前又发生一笔成交或划转。如何保证基于旧快照的“可以下单”不会在新状态下继续生效？

**面试者：** 风险计算可以在不可变快照上执行，但扩大风险的批准必须在提交边界做版本比较与占额。用 `risk_pool_id、account_seq、ledger_version、position_version、order/reservation_version、price_id、config_version、mode_version、owner_epoch` 作为预期向量；任何会使裁决失效的版本变化，事务都不得创建新预留，必须重取一致快照并重算。

例如计算时池余额 40、IM 20、可用 20；期间一笔提款／划出和一笔别的订单竞争同一池序列。若裁决提交时仅检查 position version，却未检查余额、reservation 和归属版本，旧结果仍可能批准超额。CAS 应覆盖全部影响准入的版本，或把这些事实统一纳入池序列。

Mark 更新的处理需要明确定义提交生效点。系统可规定准入根据提交前最近一个已接受且未过期的 Mark 水位，但要在提交时校验该水位仍在允许的新鲜度范围；不能要求计算期间全市场价格完全不动。参数版本则按有效序号，在同一个裁决点选择生效配置。

通过的 RiskResult 和 reservation 应共享 `decision_id、decision_version、input_digest`。批准被成功提交后，稍后的 Mark 下跌会触发下一次风险重算，不会追溯抹掉已确定成交；若订单仍未成交，可按订单协议重估、追加预算或撤单，但未确认撤销前保留风险义务。

失败路径要可见：版本冲突返回可重试原因；序号缺口、未知模式、陈旧价或缺失参数返回不可扩险的明确原因码。不能用旧结果兜底成功，也不能把重试变成新 reservation 身份。

## 第 8 层：迟到、重复、乱序输入分别怎样处理？

**面试官：** 持仓事件重复，Mark 倒退，配置变更晚到，而账本事件有缺号。哪些直接去重，哪些重排，哪些应阻断裁决？

**面试者：** 每种输入按其权威域身份和顺序处理，不能用一条通用“按时间排序”规则：

| 输入情况 | 裁决方式 |
|---|---|
| 同一 `trade_id` 或账本 `event_id` 重复且载荷相同 | 返回已应用效果，不重复改仓／余额；身份相同载荷不同则隔离 |
| 账本／持仓／订单序列缺口 | 暂停跨过缺口的连续检查点；查询并重放缺失事件，或接受可校验覆盖该区间的源快照 |
| 旧序号事件迟到 | 若已由更高连续检查点覆盖则幂等忽略；否则按序补齐，不能按到达时间另排新位置 |
| 新序号事件迟到 | 等待其前置缺口，未连续应用前不能作为完整池状态 |
| Mark 重复 | 相同 `price_id` 产生幂等更新，不重复触发副作用 |
| Mark 版本倒退或质量无效 | 不覆盖已应用水位；标记输入异常并执行预定的停扩险／保护策略 |
| 新参数已发布但未到生效点 | 仍按旧有效版本；到达生效边界后切到完整新配置包 |
| 生效配置有缺失字段或版本冲突 | 拒绝用拼接配置计算，阻止扩险并报告配置缺口 |

迟到并不总等同无效。成交事实即使很晚到，仍需按交易权威顺序补结并保留义务；旧行情如果已被新行情覆盖，不能改写当前估值，但可用于审计历史。风险引擎需区分“不能覆盖当前派生状态”与“可以丢弃业务事实”。

所有拒绝扩险和处置输出带 `reason_code、input_digest、watermark`。若结果已被消费方采用后才发现上游事实有错，应追加纠正事件与新版本，不原地篡改旧 `RiskResult`，并通知依赖该版本的订单／处置流程重验。

## 第 9 层：进程崩溃、快照损坏或参数重放后怎样恢复确定性？

**面试官：** 风险 owner 在应用事件 121 后崩溃，提交回包丢失；备机有一份检查点 118 的快照和之后的重复日志。怎样安全恢复，避免丢输入或双算？

**面试者：** 检查点和其覆盖范围、输入摘要、规则版本以及下一段事件位置要一致提交。备机从最后一个校验有效的连续检查点恢复，重放之后的事件并以稳定身份去重；若只证明到 118，就不能声称已应用 121。

风险应用事务至少要共同记录：输入事件身份及载荷摘要、派生池状态／版本、连续应用检查点、结果身份和待交付输出。事务提交但回包丢失时，按同一决策／事件身份查询已提交结果；事务未提交时重放才会产生一次效果。

恢复发现两份不同状态都宣称同一 `(risk_pool_id, account_seq, owner_epoch)`，需依据耐久提交记录和 fencing 选出唯一链，隔离分叉而非按时间挑“较新”的内存副本。新 owner 取得更高 epoch，存储端拒绝旧 owner 写入；检查点恢复不能覆盖已提交的新 owner 进度。

快照缺事件时，可从前一个有效快照重放完整日志；日志也有缺失则需要从权威账本、持仓、订单、行情与配置域重新构造并核对输入摘要。重建期间停扩险，不能仅靠把 offset 快进到队尾恢复服务。

若参数版本已下线，仍要能够读取不可变配置内容或等价校验摘要，按原规则复现历史结果。配置回滚生成新版本；相同输入向量与同一版本公式应有相同输出。结果推送丢失由持久待发记录补交，消费方按 `decision_id` 幂等，不需要重算成另一个决策。

## 第 10 层：怎样设计反例证明风险结果没有使用虚假快照？

**面试官：** 给一组明确的测试，能暴露单字段最新、最大 offset 和消息抵达顺序这些错误。哪些结果必须固定？

**面试者：** 我会在模型测试中重排同一组业务事件，改变重复次数、网络到达顺序和崩溃位置，同时断言每个提交点都满足风险输入证据与池边界。关键反例是：

| 场景 | 必须得到的行为 |
|---|---|
| 主例 Mark=84，余额 20、仓位 1 ETH、IMR/MMR=20%/5% | 逐仓 E=4、IM=16.8、MM=4.2，触发；Cross 余额 40 时 E=24，不触发 |
| 逐仓读到池外 20 的最新钱包余额，却没有已提交划转版本 | 快照仍按 20 计算，不能误报 E=24 |
| 成交序号已见到 121，但 119 缺失，120 是关联账务效果 | `seen_max=121` 不提升连续 k；补缺前禁止以该状态批准扩险 |
| 价格更新到 84，持仓仍是成交前 0.5 ETH，但成交义务存在 | 风险结果必须等待结转或按明确影子敞口覆盖，不得报告仅 0.5 ETH 的安全状态 |
| Mark=84 被重复、随后旧 Mark=90 迟到 | 重复幂等；旧水位不覆盖新估值，不产生倒退风险结果 |
| IMR 已生效、MMR 新版本尚缺 | 不拼接新旧参数，阻止扩险并记录配置缺口 |
| 风险结果刚算完，reservation／划转版本先变化 | 提交比较失败，重取快照，不得按旧 Available 成功 |
| 每个事件应用后立即崩溃，重复重放，旧主复活 | 检查点只推进一次，幂等结果一致，旧 owner 写入被拒 |

还应校验规范化摘要、定点精度、舍入版本和公式版本；阈值 `E=MM` 按本题 `<=` 触发。对状态机做属性测试：同一事件集合在合法因果约束下重放得到同一结果；改变真实版本、池归属或参数版本必须能改变摘要；任何缺口不得伪装成完成水位。

以上是验证设计与手工算例，不代表这些测试已经运行。本文没有运行 Go 风险引擎、数据库故障注入或行情系统实验。

## 本题收束

### 已经讲透的机制

- 同一时点不是 wall-clock 相近，而是源版本、因果前置、连续应用水位与生效规则共同定义的逻辑切点。
- 风险结果绑定风险池成员、余额、仓位、订单／预留、价格、参数、规则及规范化摘要。
- `h` 表示已分配屏障，`k` 表示已连续完整应用；见到最大序号不代表缺口已补齐。
- 价格、参数和账户事实使用各自权威水位，再由风险裁决契约建立可解释版本向量。
- 扩险提交要对输入版本做 CAS／排序校验；不一致、陈旧或未知时停扩险，而非拿旧快照兜底。
- 迟到的成交仍是业务事实；旧消息不得覆盖当前状态，修正以新版本追加，故障恢复按身份确定性重放。

### 最容易答错的边界

1. 把“每个服务最新”或相近时间戳当作快照一致性证据。
2. 把消息最大 offset、屏障分配 h 当成连续检查点 k。
3. 把风险快照摘要当成新的余额或仓位权威。
4. 参数分字段 latest、价格与仓位任意拼接，忽略配置有效点和输入质量。
5. 把迟到成交当无效消息丢弃，或在成交、账务和仓位交接中释放旧约束后漏掉新敞口。
6. 计算通过后不再检查版本，提交时仍用已经失效的 Available。
7. 崩溃恢复时快进 offset、替换历史参数，或让旧主覆盖新检查点。

### 一个能检验方案的反例

逐仓风险桶余额是 20，仓位投影仍为 0.5 ETH；成交域已经确定另一笔 0.5 ETH 成交，Mark 更新到 84。余额、旧仓位、价格各自都可能是其来源当时的“最新值”，但它们拼成的 0.5 ETH 风险状态漏掉了确定成交。

若风险侧先移除该成交的订单预留，却还没应用新仓位或等价影子义务，Available 会被虚增；若它又把影子与最终仓位永久相加，则会双计。正确机制是用成交身份保持覆盖，记录各域效果水位；在同一版本交接中让影子义务转为权威仓位，或在无法证明连续覆盖时拒绝扩险。对同一逻辑切点，最终应算出主例逐仓 E=4、MM=4.2，而不是凭一组字段的更新时间宣称安全。
