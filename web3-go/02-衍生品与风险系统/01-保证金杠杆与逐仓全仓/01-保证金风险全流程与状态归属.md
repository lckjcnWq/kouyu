## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| ETH / USDC / 抵押品 | ETH 是交易标的；USDC 是目标锚定美元的稳定币；抵押品是承担交易风险的资产。 | 用 USDC 支撑 ETH 合约，教学价格 100 不代表实际行情。 |
| 链下托管 / 线性永续 | 平台内部托管记账；交易没有固定到期日，固定仓位的盈亏随价格变化按固定比例计算。 | 开 1 ETH 仓位，不等于买到 1 ETH 现货；也不是每步都写区块链。 |
| 开仓 / 平仓 / 单向仓位 | 建立交易叫开仓，减少或结束交易叫平仓；同市场按一个净方向算。 | 主例持有 1 ETH 多仓，上涨赚、下跌亏。 |
| 保证金 / 杠杆 | 保证金是支撑风险的钱；杠杆表示仓位规模相对相应资金有多大。 | 100 的名义规模需要 20，比例是 5 倍；20 不是手续费。 |
| Entry / Mark Price | Entry 是入场价格，Mark 是系统做风险估值的标记价格。 | 入场 100、Mark 为 84，不能据此承诺按 84 成交平仓。 |
| q / multiplier / 名义价值 N | q 是带多空方向的数量；乘数换算合约规模；N 是当前仓位的绝对规模。 | 本例 q=1、乘数=1，Mark=84 时 N=84 USDC。 |
| PnL / U / 未实现盈亏 | PnL 是盈亏；U 是尚未通过平仓等结算的浮盈浮亏。 | U=1×(84−100)=−16，不再乘一次 5。 |
| Equity / E / 权益 | 本例把风险范围内的余额与浮盈浮亏合起来估值。 | 逐仓 20−16=4；全仓 40−16=24。不是另一份现金账户。 |
| IM / IMR | IM 是初始保证金要求金额；IMR 是计算这个要求的比例，主要管扩大风险。 | 本例 IMR=20%，Mark=84 时现仓 IM=16.8。 |
| MM / MMR | MM 是维持现有仓位的保证金要求金额；MMR 是对应比例。 | 本例 MM=84×5%=4.2；权益不大于 MM 时触发处置。 |
| Available / 可提现额 | 前者表示按规则还能承担多少新增风险；后者是允许实际转走多少资金。 | Available 为负不等于欠这么多钱，也不单独决定是否强平。 |
| 逐仓 Isolated / 隔离桶 | 给该仓位单独分配一笔风险资金，桶外的钱不自动参与。 | 桶里只有 20，即使同用户外面还有 20，也不能直接算入。 |
| 全仓 Cross / 风险池 | 同一约定范围内的钱和仓位共同承担风险。 | 这里共享 40，不代表平台所有资产都互相担保。 |
| 敞口 / 扩险 | 敞口是暴露于价格变化的风险规模；扩险是把这份风险扩大。 | 多买同方向合约通常会扩大敞口，需重新准入。 |
| 限价 / 撮合 / 部分成交 | 限价规定可接受价格边界；撮合让买卖配对；部分成交表示只执行一部分。 | 下单不等于成交，已成交部分不能靠撤单撤回。 |
| 保证金预留 / reservation_id | 未成交前先占额度；编号用来识别同一笔占用。 | 预留成功只表示额度占住，不是已有仓位或已损失资金。 |
| 账本 / 持仓 / owner | 账本记正式资金事实；持仓记成交后的交易状态；owner 是各类状态的系统负责人。 | 风险系统负责判断，不能把浮亏又擅自记成一笔账本扣款。 |
| 原子性 / TOCTOU | 检查与占额作为整体完成；TOCTOU 是查完到真用之间，额度被别人占了。 | 可用 20，两单各要 15，最多完整批准一单。 |
| 风险快照 / account_seq / 水位 | 给相关数据标处理进度，确认它们可以组合成同一份有依据的状态。 | 不能把新价格、旧仓位、已释放预留随便拼起来。 |
| 参数版本 / 风险档位 / 抵押折扣 | 标明本次用哪组规则；规模分档可用不同要求；抵押资产可能不按全部市值认可。 | 主例无档位与折扣，不代表真实平台也没有。 |
| 划转 / 模式切换 | 划转改变钱的归属范围；切换逐仓全仓改变共同扛损失的成员。 | 都必须有正式记录和生效点，不能只改页面字段。 |
| 强平 / 穿仓 | 强平是强制减少或关闭仓位；穿仓是损失超过可承担资金，出现缺口。 | 触发时可能还有正权益，且不保证能及时、按预估价成交。 |
| RPC 超时 / 幂等 | 超时是没收到答复；幂等是同一业务重试只生效一次。 | 预留响应丢失不能视为没预留，应按原编号查结果。 |
| Inbox / Outbox / offset | 可靠衔接消息处理与业务记录的机制；offset 只是消费位置。 | 收到消息或推进 offset，不自动证明账本和风险更新已提交。 |
| owner_epoch / fencing / 重放 | 负责人代次、阻止过期负责人写入的围栏，以及按历史事件恢复状态。 | 新主接管后，旧主复活也不能继续占用额度。 |
| 定点数 / Decimal / Golden Case / 不变量 | 明确精度的金额计算；有标准答案的用例；始终不能破坏的规则。 | 检查小数边界、固定数值和资金不重复使用，不能只看最后余额。 |

## 把整篇文章压缩成一个故事

小林账户里有 40 USDC，想在价格 100 时开 1 ETH 多仓。本文规定初始保证金率 20%，所以这笔仓位需要 20，相当于 5 倍的开仓名义杠杆。系统先检查资格、占住额度，再把订单送去撮合；只有确定成交后，才形成对应仓位和结转义务。页面稍晚显示，不会让已经确定的交易消失。

若选逐仓，小林只分配 20 给这笔仓位，外面的 20 不自动救场；若选全仓，同池 40 一起扛。标记价跌到 84，两种模式都浮亏 16，不是再乘 5。逐仓权益剩 4，全仓剩 24；维持保证金同为 4.2，于是逐仓触发本文的处置条件，全仓未触发。强平是否执行、按什么价成交，还需要后续流程确认。

整个系统最怕的是各部门“各算各的”：两张订单同时花同一额度、风险服务漏掉刚成交的数量、把逐仓外的钱偷算进来，或者响应丢失后再扣一次。本文后面的版本、预留、正式流水和故障恢复，都是为了让每一步都有编号、有顺序、可核对：钱归账本记录，仓位归成交事实确定，风险服务据此算能否继续交易，不能凭计算结果凭空改钱。

## 第 1 层：从开仓意图讲到风险结果更新

**面试官：** 一个用户以 5 倍杠杆开 1 ETH 永续，你如何从提交订单讲到系统形成可解释的保证金状态？先沿一条具体流程说明哪些步骤是确定的、什么时候才算完成。

**面试者：** 我会先把产品与模型说清楚：这里是链下托管的线性 USDC 永续，Mark Price 为风险输入，撮合成交后才形成仓位。杠杆用于限制敞口相对保证金的比例，不是把盈亏再乘一次。

本例账户有 40 USDC，用户买入 1 ETH，限价允许在 100 成交。最大杠杆为 5 倍，对应初始保证金率 20%；维持保证金率 5%。若使用逐仓，就先把 20 USDC 划入该仓风险桶，另外 20 不自动参与这笔仓位风险。若使用全仓，40 USDC 都在一个共享风险池中。然后流程是：

```text
用户提交订单意图〔账户、市场、方向、价格、数量、请求身份〕
    ↓
接入校验〔权限、合约、精度、账户模式与订单约束〕
    ↓
风险池 owner 读取带版本的余额、仓位、挂单、价格与规则
    ↓
校验新增敞口后的 IM、杠杆上限和仓位限额
    ├─ 不满足或输入不可信 → 拒绝扩险，不进入撮合
    └─ 满足 → 原子建立有身份、有上限的保证金预留
                    ↓
撮合产生零笔、一笔或多笔确定成交
                    ↓
成交事件按稳定身份更新持仓与账本，预留转成已成交仓位约束
                    ↓
风险池应用新版本并重算 Equity、IM、MM、Available 和状态
                    ↓
版本化结果被下游接收；查询视图随后更新
```

重要的完成阶段有四个：订单受理只表示意图进入确定流程；风险预留成功表示额度被占住，不表示成交；成交确定表示有待结转的业务义务；仓位、账本、预留和风险输入达到约定版本后，风险视图才可说处理到该成交。页面可见是之后的投影阶段。

举例说，成交后 Mark=84。逐仓桶的权益是 `20 + 1×(84−100)=4`，维持保证金是 `84×5%=4.2`，因此满足本例定义的风险处置条件。全仓权益为 `40−16=24`，维持保证金仍为 4.2。这个差异来自风险资金范围，而不是另一套 PnL 公式。

如果撮合还没成交，拒单或撤单不改持仓；部分成交只结转成交量；确定成交后即使风险服务暂时不可用，也不能把成交抹掉。系统需要保留待处理义务和已有预留，按同一成交身份恢复，而不是在错误窗口释放保证金。

## 第 2 层：你说的权益、IM、MM 和可用余额分别是什么意思？

**面试官：** 流程里计算了 Equity、IM、MM 和 Available。很多系统把这些都叫“保证金余额”。请沿用 1 ETH 的案例，给出彼此不同的定义和使用场景。

**面试者：** 我会把它们作为不同量输出，并注明风险池、单位、价格和版本。主例只有 USDC 抵押，所以公式比较简单；真实系统若有抵押折扣、费用、档位或负债，需要把对应规则显式加入。

对线性合约，未实现盈亏 `U=q×(Mark−Entry)×乘数`，当前名义价值 `N=|q|×Mark×乘数`。在逐仓里，`Equity_iso=该仓保证金余额+该仓未实现盈亏`；在全仓里，`Equity_cross=共享抵押价值+共享仓位的未实现盈亏之和`。本例余额已反映结算完的费用、资金费和已实现损益，不在权益公式里重复加这些项目。

初始保证金是扩大敞口时的资本门槛：`IM=N×IMR`。本例 IMR 是 20%。维持保证金是已有仓位继续存续的最低风险要求：`MM=N×MMR`，本例 MMR 是 5%。风险处置条件使用权益对照 MM，而不是判断 Available 是否大于零。

`Available` 是按产品契约可以用于新增风险的额度视图。这里定义为 `权益−当前仓位 IM−尚未体现在仓位 IM 中的挂单预留−其他锁定额`。主例 Mark=84 时，逐仓权益 4、IM 16.8，因此 Available 为 −12.8；全仓权益 24、IM 16.8，Available 为 7.2。逐仓已触发 MM 风险条件，全仓尚未触发，但全仓也不代表能再用同一份额度重复开仓。

这些数回答不同问题：Equity 表示当前按估值组合出的风险价值；IM 表示开仓和维持新增敞口所需的资本额度；MM 用于判断现有风险是否需要处置；Available 用于准入和可用额度。可提现额还可能受未结算义务、提款限制或产品策略约束，不能把 Available 直接等同提现余额。

## 第 3 层：设置 5 倍杠杆后，为什么盈亏不是价格变化乘 5？

**面试官：** 你将 5 倍解释成 IMR 的倒数。若价格从 100 跌到 84，账户亏 16 还是 80？用户调高杠杆后，现有仓位的风险到底改变在哪里？

**面试者：** 对 1 ETH 的线性仓位，毛未实现盈亏是 `1×(84−100)=−16 USDC`。杠杆不改变合约乘数，也不改变这条 PnL 公式。把它算成 −80，是把保证金收益率和合约损益金额混为一谈。

开仓时的名义价值是 100 USDC，初始保证金需求是 20，所以名义敞口除以初始保证金为 5 倍。亏损 16 相对初始保证金 20 是 −80%；这可以说是初始保证金回报率下降 80%，但不是账户又亏了 80 USDC。逐仓桶权益因此从 20 变成 4，而不是变成 −60。

用户调整杠杆档位，可能改变 IMR、最大可开名义敞口、下单预留和系统采用的风险档位；它不应直接改仓位数量、入场价或历史盈亏。若产品允许存量仓位调杠杆，还要说明新 IM 要求在何时生效、降低杠杆是否必须追加保证金、并发订单如何处理。系统不能只改 UI 上的 leverage 字段，却继续用旧参数放行订单。

还要区分用户配置的杠杆与当前权益杠杆。开仓配置是 `100/20=5`；Mark=84 时逐仓的当前权益杠杆是 `84/4=21`。后者反映亏损后权益变薄，不是配置突然从 5 倍自动改成 21 倍。正因为权益变化会让有效风险迅速恶化，系统需要持续重算而不能只在下单时检查一次。

## 第 4 层：为什么逐仓和全仓是风险边界变化，不只是两个公式？

**面试官：** 现在同样的 1 ETH 都跌到 Mark=84。逐仓进入风险处置，全仓没有。假如账户还有别的仓位、用户能划转余额，谁能承担亏损？一致性单元要怎么变？

**面试者：** 逐仓与全仓首先定义了哪些资金和仓位共同承担损失，其次才是聚合公式。逐仓以隔离桶为边界；本例分配的 20 USDC 加该仓 PnL 得出权益 4，账户外的 20 不因同属一个用户就自动可用。全仓则将风险池内合格的余额与仓位共同估值，所以同一跌幅下共享 40 USDC 后还有权益 24。

逐仓的收益是损失范围更明确、跨仓污染较少；代价是资金使用效率低，单仓更容易进入风险区，可能穿仓。全仓提高了资金复用率，但一个仓位的亏损会消耗其他仓位可依赖的共享权益，多个市场同时波动也会扩大共同失败域。全仓是同一池成员共享，不意味着所有账户全平台互保。

状态分区应与经济共担范围匹配。逐仓可以按隔离仓位或产品定义的风险单元串行化；全仓必须覆盖共享抵押余额、该池全部仓位和挂单预留。若仍按每个市场独立计算再异步相加，两个并发下单可能各自看到未被另一市场消耗的额度，合计超过账户权益。

同样，跨市场共享需要定义统一价格切点或可解释的版本水位。风险引擎拥有池级派生状态和裁决权，不拥有账本现金或持仓事实。查询层能展示组合结果，但不能靠它成为跨市场的原子裁决者。

## 第 5 层：两笔并发订单都看到有额度，如何避免重复占用？

**面试官：** 全仓池当前权益 40，初始保证金需求 20。如果两个市场同时各自校验一笔新增订单，都读到 Available 20，它们都可能通过。你如何在下单到成交之间保证额度只用一次？

**面试者：** 风险检查必须产生可消费的额度预留，而不是只返回 `true`。针对共享 Cross 风险池，两个命令要在同一个风险序列或等价的原子提交边界上裁决。

假设两笔订单各需 15 USDC 初始保证金。第一笔在池状态版本 8 上通过并原子预留 15，池剩余额度变为 5；第二笔排在后面时必须基于版本 9 的新额度判断，因此被拒绝或缩量。若两个检查分别在无锁旧快照上通过，之后才插入预留，就产生 TOCTOU 超额风险。

预留对象至少需要稳定的 `reservation_id`、风险池、决策版本、批准额度、已消耗量、已释放量和状态。成交量消耗相应预留；部分成交后余量继续受约束；撤单只有在成交与撤单竞争已经按权威顺序裁决后，才能释放确认未成交的部分。对同一批准版本／额度分段，金额守恒是 `approved_im = consumed_im + released_im + remaining_im`，不能消耗与释放同一份额度两次。它记录历史额度分配，不表示 `consumed_im` 永远等于当前仓位 IM；后者随 Mark、仓位和参数变化重算，订单剩余风险需求的重估和补额也要记录新版本。

重试沿用原命令身份。风险服务提交预留但响应丢失时，客户端不能生成新身份再占一次额度；系统查询原 reservation 并返回原结果。若成交已发生但预留消费消息迟到，风险池要把未结转成交作为在途义务保守计入，不能一边保留完整开仓能力、一边假设订单已结束。

Go channel 可以让一个进程内的 owner loop 排队，但持久化预留、数据库提交和多实例切换还要有唯一约束、版本检查或 fencing。channel 的顺序本身不是账户额度的耐久事实。

## 第 6 层：订单服务、账本、持仓和价格都各自“最新”，为什么仍可能算错？

**面试官：** 你说多服务状态需要一个序列。假如风险引擎读到了最新 Mark=84、旧仓位 0.5 ETH、新余额 40 和新订单预留，单看每个来源都没错，怎么判断这个组合能不能用于裁决？

**面试者：** 单字段最新不等于组合状态曾经同时成立。风险结果必须携带输入版本、水位或事件序列，并满足跨域因果约束。否则可能把刚成交后的价格和成交前仓位组合，漏掉一半敞口。

我会把输入分成源事实和派生状态：账本版本负责余额与划转，持仓版本负责成交后数量，订单版本负责剩余预留，价格版本包括 Mark 身份、时间和质量，参数版本负责 IM/MM、档位和费率。一个 `RiskResult` 记录这些版本及规范化输入摘要，能够被离线重新计算。

若同一风险池有权威 `account_seq`，它可用于串行应用池内会改变风险的事件；价格还要定义可用水位或发布快照屏障。没有共同序列的分布式设计，可使用版本屏障或事件时间水位并明确允许的暂态，但不能单纯比较各服务 wall-clock 时间。读到序号缺口时，不应宣布已处理到更后版本。

Mark=84 的风险结果要和对应仓位、余额及参数版本一起存证。如果价格更新先到而成交状态未追上，系统可以按当前协议延迟裁决、使用保守在途敞口，或禁止扩险；不能静默拿旧仓位得到“安全”结论。风险引擎不需要把所有原域合并成一个微服务，但需要一个能解释其输入集合的逻辑切点。

## 第 7 层：把 20 USDC 从账户转进逐仓桶，或者把仓位切换成全仓，要做什么？

**面试官：** 用户在 Mark=84 时发现逐仓权益只有 4，想从账户外侧再划 20；另一个用户要求把有仓位的逐仓账户直接切成全仓。能不能只改一条 margin 字段或把钱包余额读进来？

**面试者：** 不可以。划转改变抵押品归属，是需要有身份、账务记录和风险版本的经济操作；模式切换改变风险共担范围，更不是展示字段更新。

逐仓追加 20 时，系统先校验资金来源的可用余额及其是否已被其他用途预留，再在明确的提交边界生成唯一 `transfer_id` 和账本分录，目标隔离桶余额增加 20，源余额同步减少。风险状态只有在这笔转账权威提交后才把权益从 4 更新到 24。发送超时就按原身份查询，不能再次扣源账户或重复加仓桶。

模式切换需要先定义迁移前后哪些仓位、订单、余额及待结算义务属于该风险池。教学上我会要求没有未结算订单、未完成预留、在途成交和强平工作流时才允许直接迁移；否则先冻结会扩大风险的操作，按确定序列结清或显式迁移每项义务。切换时写入新 `risk_pool_id` / mode version，并保证旧、新模式不能同时对同一资金和仓位取得裁决权。

若需要在持仓期间切换，迁移状态机要记录开始版本、转入转出金额、风险参数、最终归属和完成标记；任一步超时可查询并续跑，不能让两个池都把同一 20 USDC 计为可用。迁移失败只能依据已经提交的账本和成员关系继续或产生审计补偿，不直接覆盖历史余额。

## 第 8 层：Mark 到 84 时触发处置，是否意味着系统立刻能按 84 平仓？

**面试官：** 逐仓在 84 时权益低于 MM。Mark 消息可能重复、延迟，订单刚好部分减仓，参数也可能在这个时刻升级。你怎样避免使用过期风险结果盲目强平？

**面试者：** `Equity <= MM` 是某一版输入下的触发条件，不是执行价格保证，也不是可直接写进仓位的强平事实。风险引擎要为触发绑定仓位、账本、预留、Mark 质量和风险参数版本，然后由强平状态机在执行边界校验该触发仍适用。

若 Mark 84 重复到达，同一价格身份不应产生重复的风险状态副作用；若价格版本倒退，旧结果不能覆盖新版本。若价格陈旧或多源异常，产品要事先规定停止扩险、限制某些操作或进入保护模式，不能用不可信价格当作精确触发证据。若价格跳空穿过阈值，风险引擎可以确认账户需要处置，但市场成交可能更差或无法成交。

同一时刻若部分平仓已经确定，风险状态必须按其业务序列重新计算；旧的强平触发不能忽略新仓位版本。参数升级也要有生效序号，不能让一笔裁决一半用旧 MMR、一半用新 IMR。若新参数提高要求，如何处理存量账户和宽限期是参数治理策略，不是计算函数自行决定。

Mark=84 的连续算式给出交点约 84.210526，但真实系统还会受到跳价、舍入、费用和执行过程影响。强平成交价由实际执行决定，风险预估价不是真相源。本题只说明触发输入与重新校验，如何撤单、部分强平和承担穿仓由强平专题展开。

## 第 9 层：风险预留提交后响应丢失，或者主节点崩溃，如何恢复？

**面试官：** 风险主节点已提交 15 USDC 预留但 RPC 响应丢失；随后进程崩溃，旧主恢复时还可能继续写。你怎么保证订单不重复占额、也不因为故障漏掉已提交成交？

**面试者：** 先区分提交结果未知和确定未提交。调用超时只能说明调用方未收到结果，不能证明预留或成交不存在。恢复依赖持久化身份和连续提交点，不依赖进程内 map 或消息 offset 单独推断业务事实。

同一预留命令重试时使用相同 `reservation_id` / 请求身份。风险池存储侧对该身份设唯一约束并保留载荷摘要；重复同载荷返回已提交结果，身份相同但载荷不同则隔离。余额/风险额度状态、reservation、应用序号及待交付结果要在一个清楚的事务或等价协议下共同推进。

新 owner 接管时先获得更高 `owner_epoch`，写入同一风险池的事务需校验 epoch。旧主即使进程复活，也不能在新 epoch 生效后继续写入。新主从有效快照及之后连续事件恢复；快照损坏就回退到可校验的更早锚点并重放，不越过日志缺口。

风险预留与成交消息跨服务时，采用 Inbox/Outbox、可靠日志或等价机制保证业务效果可重放。消息可能重复，消费者用稳定业务身份去重；消费者组 offset 只表示消费位置，不自动和账本/风险数据库副作用原子。成交已提交而风险投影未更新时，把在途义务保留并继续补齐，不因可用性压力直接释放额度。

## 第 10 层：怎样证明系统没有重复放行、错用逐仓余额或漏掉阈值？

**面试官：** 你已经有公式、版本和恢复路径。测试只看最终账户权益是否正确够不够？请给出能推翻方案的反例，以及上线前实际需要什么证据。

**面试者：** 只看最终权益不够。不同错误可能相互抵消，或者最终金额一致但中途已经两次放行了同一保证金。正确性需要同时验证每次迁移、风险池边界、命令顺序和故障恢复。

第一类是公式 Golden Case：主例在 100、90、84 的结果必须分别得到 `U=0、−10、−16`；在 84 时逐仓权益 4、MM 4.2，应触发；全仓权益 24，应不触发。阈值等值 `E=MM` 使用本题约定的 `<=`，边界两侧一个最小货币单位的值也要测试。

第二类是池归属反例：把逐仓桶外的 20 USDC 直接加进 Equity，系统就会把 84 时风险结论从触发改成安全；正确实现必须要求显式、已提交的划转事件。对全仓，则同时安排两个市场并发各占 15，而可用额度只有 20；最多一笔完整通过，不能两笔都依据旧快照通过。

第三类是时序和故障：预留提交后响应丢失、部分成交与撤单竞争、重复成交、风险输入序号缺口、参数切换中断、旧主复活、Mark 倒退或陈旧。逐事件核对权益、IM、MM、Available、reservation 守恒和结果身份；确认业务暂态有时限和所有者，未完成的额度不被静默释放。

金额计算使用定点数或受控 Decimal，建立舍入方向、位宽上界、负值和档位切换测试。可用属性测试检查：增加有效抵押不应降低 Equity；在其他输入不变时扩大同方向敞口不应减少其名义风险；从逐仓外侧划转前后，全账户总账守恒；同一输入序列和参数版本重放得到相同风险结果摘要。跨语言或合约执行时，用独立参考模型做差分。

本文交付的是讨论基线、完整母题问答和手工数值案例，没有运行 Go 工程、数据库故障演练、链上实验或性能测试。结构检查、算式手推、模型测试和生产观测是不同证据，不能互相替代。

## 本题收束

### 已经讲透的机制

- 保证金术语各自有定义：Equity 是风险估值，IM 管新增敞口，MM 管存量处置，Available 是准入额度视图。
- 杠杆限制名义敞口相对保证金，不改变线性合约 PnL 公式。
- 逐仓与全仓首先改变共同承担损失的池边界，进而改变并发裁决和一致性范围。
- 预留是有身份和生命周期的额度约束；成交、撤单和重试不能重复消耗或释放。
- 风险结果要绑定余额、仓位、订单、价格和参数版本；风险触发不等于强平成交。
- 超时未知、崩溃恢复和主备切换都依赖持久事实、去重身份与存储侧 fencing。

### 最容易答错的边界

1. 把杠杆说成盈亏乘数，或将初始保证金当成已经损失的手续费。
2. 把账户总余额自动计入逐仓权益，忽略显式划转和风险池成员关系。
3. 认为 Cross 只需把每个市场各自风险结果相加，忽略共享抵押下的并发超用。
4. 把 Equity、Available、可提现额当作同一个余额字段。
5. 把 IM 需求、订单预留重复扣除，或成交后同时保留完整订单预留和仓位保证金。
6. 用各服务“最新值”拼接风险快照，或者把消息抵达时间当业务顺序。
7. 认为风险触发就是按计算价格强平成功；认为 RPC 超时就能直接释放预留。

### 一个能检验方案的反例

同一笔 1 ETH 多仓，逐仓桶有 20 USDC，账户外还有 20 USDC；Mark 从 100 跌至 84。若没有已提交的划转，逐仓权益只能是 4，不能偷用外侧 20 得到 24。全仓可以按其规则使用池内 40，权益为 24。再令全仓两个并发订单都尝试占用 15 USDC，而可用只有 20：若二者都被放行，风险池原子预留或排序约束没有成立。

一个成立的设计应能按同一风险池版本重算出上述结果，重复请求只返回原预留，模式迁移和划转有账本身份，迟到价格／成交不会覆盖新版本，接管后的旧主写入会被拒绝。
