# 大问题 8：定点精度、舍入与风险档位边界如何保持保守且可复现？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 保证金 / 风险裁决 | 用来承担交易风险的钱，以及系统按规则判断能否开仓或是否需处置。 | 小数误差可能真的多放行一笔，不只是页面不好看。 |
| Mark / Entry / q / multiplier | 标记估值价、入场价、带方向数量、合约规模换算系数。 | 四者单位和精度不同，不能因为底层都是整数就互换。 |
| PnL / U / N | 盈亏、尚未结算的浮盈浮亏、当前名义规模。 | 线性合约先算价差与有方向数量，名义价值则取数量绝对值。 |
| Equity / IM / MM / Available | 风险权益、初始要求、维持要求、可新增风险额度。 | 权益不应算高，需求不应算低，否则账户被错误判得更安全。 |
| IMR / MMR / E<=MM | 初始比例、维持比例，以及本文“等于也触发”的处置规则。 | 20%和5%是教学参数，不是所有平台标准。 |
| 定点数 / amount atoms | 用整数记录固定的小数步长；atom是一个最小金额单位。 | 本文编码示例一个金额原子为0.000001 USDC，20记为20,000,000。 |
| scale / 量纲 | scale在本文指编码乘数；量纲表示字段是ETH、USDC还是价格等。 | 数量scale=10^8，金额scale=10^6，不能直接把两个编码整数相加。 |
| quantity / price / rate scale | 数量、价格、费率各自的编码倍率。 | 20%在费率scale=10^8时记为20,000,000，不是20或0.2直接混算。 |
| 规范化 / 量化 | 把输入变成统一单位与精度；超出精度时按明确规则处理。 | 小数位过多应拒绝或明确取整，不能每个服务随意舍入。 |
| floor / floorDiv | 数学向负无穷取整，即取不大于原数的整数。 | −0.1个原子变−1，保守估值不把小额亏损抹掉。 |
| ceil / ceilDiv | 向正无穷取整，取不小于原数的整数。 | 非负保证金要求10.2个原子取11，不可取10后错误放行。 |
| 向零截断 / round | 向零截断去掉小数部分；round的具体含义由语言库决定。 | −0.1截断成0会低估亏损，不等于floor，也不能默认等于保守规则。 |
| 风险估值 / 现金记账 | 风险估值按保守规则判断承受能力；现金记账记录真实经济流水。 | 将微小浮亏向下量化，不等于凭空给现金账本再扣一笔钱。 |
| 舍入点 / 计算图 / 双重舍入 | 规定在哪一步取整；多步随意取整会让最终结果与另一种顺序不同。 | 先算名义再算保证金，还是直接合并计算，必须统一定版。 |
| 中间位宽 / int64 / 溢出 | 整数可表示范围有限，乘法中途就可能超出，即使最终答案很小。 | 乘完才换大类型已来不及，溢出不能当正常需求继续算。 |
| MinInt64 / abs / checked arithmetic | 最小有符号整数、绝对值运算、带越界检查的计算。 | 最小整数直接取负也可能越界，除法向上取整的加一也需检查。 |
| 任意精度整数 / mulDiv | 可扩展整数位数的计算方式；安全处理乘后除的工具或算法。 | 要明确其越界与舍入语义，不能靠名称保证金融计算正确。 |
| 风险档位 / 边界B / 半开区间 | 不同仓位规模用不同要求；半开区间一端包含、一端不包含。 | 本文扩展采用[lower, upper)，刚好等于B归下一档，仅为示例契约。 |
| 候选敞口 / 选档口径 | 按这笔订单执行后可能形成的规模选规则，并说明用未舍入值还是量化值。 | 不能只按旧仓位低档验算，漏掉跨档后的更高总要求。 |
| config_version / 生效序号 | 一整套精度、档位和比例的身份及启用位置。 | 不能一笔裁决混用新IMR和旧MMR，重放要找回原规则。 |
| Golden Case / 差分测试 / 属性测试 | 标准答案用例、与独立模型逐项比较、检查大量输入是否遵守规律。 | 比整数中间值与状态，不只比较页面都显示4.20。 |
| 失败关闭 / 不可可靠计算 | 算错或缺规则时，不放行新的风险，并明确报告异常。 | 不用0、饱和值或浮点近似来伪装安全。 |

## 把整篇文章压缩成一个故事

小林要开一笔刚好卡在资金门槛上的仓位。程序精确算出需要10.2个最小金额单位，而小林只有10。如果开发者随手截断成10，订单就可能获批；按本文“保证金要求向上取整”的规则，应取11，于是不能准入。一点小数误差，在交易系统里就是多承诺了一份风险。

为了杜绝这种分歧，团队约定用整数记录金额，但不能只说“都用整数”：ETH数量、价格、USDC金额和费率各有单位与编码倍率，乘除后在哪一步取整也要写清。浮亏−0.1个金额原子，向零截断会变0，而本文风险估值用floor得到−1；这不是新增现金扣款，只是不把风险权益算高。乘法中途越界也必须报错，不能绕成一个小数继续放行。

后来产品加入规模档位，刚好碰到分界B时归哪一档、按成交前还是成交后规模判断，也必须唯一。Go服务和离线复算要使用同一版规则，比较完整整数而非页面小数。全文讲的不是盲目提高精度，而是把单位、取整、范围、选档和生效点都变成可检查的契约，异常时宁可停扩险，也不猜一个安全答案。

**流程位置与核心机制：** 本题位于风险计算的数值内核，从输入规范化、名义价值与盈亏计算，一直延伸到 IM/MM 档位选取和阈值裁决。核心不是选一个“精度足够高”的浮点类型，而是让每个字段的单位与 scale 固定、每次舍入方向可说明、边界规则与生效版本可追溯，并在任何溢出或未知规则时拒绝扩大风险。

**共同前提：** 沿用[专题总览的讨论基线与贯穿案例](README.md#一文字全流程保证金风险如何从下单走到可解释的账户结果)：链下托管、线性 USDC 永续、单向净持仓、单一 USDC 抵押品，`IMR=20%`、`MMR=5%`，账户 40 USDC。1 ETH 在 100 USDC 开多；逐仓只把 20 USDC 分到该单仓桶，另 20 留在池外；Cross 池为 40 USDC。Mark 为 100、90、84 时，`U=0、-10、-16`，`N=100、90、84`，`IM=20、18、16.8`，`MM=5、4.5、4.2`。Mark=84 时逐仓 `E=4`，按 `E <= MM` 触发风险处置；Cross `E=24`，不触发。以上全部是教学模型，不是生产协议规则或实测结果。

本文为说明实现契约，另举一组可替换的编码例子：数量以 `10^8` 为 scale（ETH），价格以 `10^6` 为 scale（USDC/ETH），金额以 `10^6` 为 scale（USDC），费率以 `10^8` 表示比例（20% 编码为 `20,000,000`）。这些 scale 不是由基线推导出的行业标准；实际合约需根据输入精度、乘数和数值范围定版。

## 第 1 层：金额、价格和数量都用整数，怎么避免单位混乱？

**面试官：** 你说不用浮点数。给出一个可检查的表示方式，并说明 1 ETH、84 USDC/ETH 和 USDC 余额 20 分别是什么整数。只说“乘个精度”还不够。

**面试者：** 我会给每个字段声明业务单位、scale、允许范围和规范化规则。本文将 scale 定义为编码乘数而非小数位数：数量 `q` 的 `quantity_scale=10^8`，一个数量原子是 `10^-8 ETH`；价格 `price_scale=10^6`，一个价格原子是 `10^-6 USDC/ETH`；金额 `amount_scale=10^6`，一个金额原子是 `10^-6 USDC`；费率 `rate_scale=10^8`，一个费率原子是比例值 `10^-8`。因此：

```text
q = 1 ETH       -> 100,000,000 quantity atoms
P = 84 USDC/ETH -> 84,000,000 price atoms
B = 20 USDC     -> 20,000,000 balance atoms
IMR = 20%       -> 20,000,000 rate atoms
```

数量原子和价格原子相乘后除以数量 scale，结果正好是金额原子：`q_atoms × P_atoms / 10^8 = amount_atoms`。若乘数也以 `10^m` 编码，通用金额计算为 `q_atoms × P_atoms × multiplier_atoms / (10^8 × 10^m)`；乘数为 1 且 `m=0` 时退化为上式。价格与数量字段不能只因底层都是 `int64` 就互换；类型、字段名、序列化 schema 和 API 单位说明都要保留维度。收到多于约定小数位的输入时，先按产品契约拒绝或在边界显式量化，不能让每个服务自行舍入。

## 第 2 层：PnL、名义价值和 IM/MM 怎样在固定 scale 下计算？

**面试官：** 单位明确后，1 ETH、Entry=100、Mark=84、乘数为 1 时，你怎样算 `U`、`N`、IM 和 MM？如果公式中有除法，谁决定结果精度？

**面试者：** 所有结果都落在金额 scale，计算次序写进版本化规则。未实现盈亏先算价格差，再乘有符号数量和乘数；名义价值先取数量绝对值；IM/MM 再乘已选费率：

```text
U_atoms = floorDiv(q_atoms × (mark_atoms - entry_atoms) × multiplier_atoms,
                    quantity_scale × multiplier_scale)
N_atoms = ceilDiv(abs(q_atoms) × mark_atoms × multiplier_atoms,
                  quantity_scale × multiplier_scale)
IM_atoms = ceilDiv(N_atoms × IMR_atoms, rate_scale)
MM_atoms = ceilDiv(N_atoms × MMR_atoms, rate_scale)
```

其中 `multiplier_atoms` 与 `multiplier_scale` 表示合约乘数及其 scale；主例乘数为 1、`multiplier_scale=1`。示意中的 `floorDiv` 是数学向负无穷取整，`ceilDiv` 面向非负整数。`U=-16,000,000` 金额原子，`N=84,000,000`；向上取整后 `IM=16,800,000`、`MM=4,200,000`，分别显示为 -16、84、16.8 和 4.2 USDC。主例恰好能被 scale 整除，故舍入不改变这些结果。

“向上取整”针对非负风险需求；对有符号 PnL 则要按数值方向定义，不能把语言中的 `round` 当成统一策略。公式、除数、scale 与舍入模式应作为数值契约的一部分。

## 第 3 层：权益和风险阈值要向哪边舍入？

**面试官：** 若 PnL 不能整除一个金额原子，直接截断负数会得到更接近零的亏损。权益、IM/MM 和 `E <= MM` 分别怎么处理，才能不把账户算得比实际更安全？

**面试者：** 先声明“保守”的含义：风险可用权益不虚高，风险需求不虚低。对有符号未实现 PnL，金额量化使用向负无穷取整；这样正收益不会被抬高，负亏损也不会被截成较小的损失。单一 USDC 抵押的本例中，`Equity = confirmed_balance + U`，中间结果使用同一金额 scale；若将来加入折扣、汇率或费用，每个转换也要按对权益保守的方向处理。

IM、MM、手续费预留等非负需求向正无穷取整。`Available` 用保守权益减去向上取整后的需求与预留，不对最终差额再做有利于准入的舍入。风险阈值在同一金额 scale 上比较：本例是 `E <= MM`，等值也触发；不能把两边分别转成二进制浮点数再比较，也不能在 UI 显示到两位小数后用展示值裁决。

例如仅用于检验舍入的边界用例：`q=0.1 ETH`、价格差为 `-0.000001 USDC/ETH`，精确 PnL 为 `-0.0000001 USDC`，即 `-0.1` 个金额原子。floor 得到 `-1` 个原子，Go 的有符号整数除法向零截断却会得到 `0`，把风险权益抬高一个原子。对正分母 `d`，可先做经检查的整数除法得到 `q=n/d`、`r=n%d`；当 `n<0` 且 `r!=0` 时再将商减一，才是 floor。应检查该减一操作的范围。这是风险估值的保守量化，不是凭空给现金账本新增亏损分录。

因此，在非整金额原子的边界，允许的保守误差方向是权益不增加、保证金需求不减少。若误差能使本应拒绝的扩仓通过，舍入规则就违反了准入不变量。

连续方程的交点也不能直接充当离散系统的裁决边界。逐仓主例的连续交点为 `1600/19 ≈ 84.210526315789`；按本文六位价格、金额 scale 和定向舍入，Mark=`84.210527` 时 `E_atoms=4,210,527`、`MM_atoms=ceil(84,210,527×5/100)=4,210,527`，等值仍触发；Mark=`84.210528` 时 `E_atoms=4,210,528`、`MM_atoms=4,210,527`，才不触发。主例的 100、90、84 不受此细节影响；连续交点也始终不是保证能成交的强平价格。

## 第 4 层：连续乘除怎样避免重复舍入和顺序不一致？

**面试官：** `q × P × multiplier × rate` 可能有多个比例。如果每乘一次都回到金额 scale，结果会不会和一次性计算不同？你怎样固定舍入点？

**面试者：** 会不同，所以要规定计算图，而不是只规定“结果保留六位”。优先在足够宽的整数中间域一次完成分子乘积、合并除数，再在明确的业务边界舍入一次。例如先得到精确有理数的名义价值，再向上取整到金额原子，之后以该 `N_atoms` 计算 IM/MM 并各自向上取整。若业务选择直接从未量化的名义价值算 IM，则也可以，但这两种口径必须择一并版本化，不能让不同服务各自实现。

实现还要固定负数除法语义。许多语言整数除法朝零截断，和数学上的 `floor` 不同；可使用明确的 `floorDiv` / `ceilDiv` 辅助函数，或把有符号量拆成符号与绝对值后按方向计算。不得通过先转 `float64` 再转回整数来“简化”舍入。

对教学例子，主值均能整除，适合作为 Golden Case；非整除用例则专门验证计算图和方向。只要任一阶段的舍入可能影响准入或风险状态，该阶段就必须有单元测试和版本说明。

## 第 5 层：乘法中间值溢出或绝对值越界怎么办？

**面试官：** 即使输入都在 `int64` 内，两个定点整数相乘仍可能越界。`abs(MinInt64)` 也无法表示。你会饱和截断、取模，还是换成浮点数继续算？

**面试者：** 都不能静默继续。乘法、加法、减法、取绝对值和舍入增量都要有范围检查；有符号最小值不能直接取负。可用经证明的更宽中间位宽和 checked arithmetic，或者使用任意精度整数作为参考实现；若产品要求固定宽度，就必须在入口限制量、价格、乘数、费率和档位上界，并证明所有合法组合的中间值仍可表示。

按主例编码，`100,000,000 × 100,000,000 = 10^16` 尚在 `int64` 内，但若在同一分子继续乘 IMR 原子 `20,000,000`，中间值为 `2×10^23`，即使最终 IM 只有 20 USDC 也早已越界。因此必须在乘之前提升到足够位宽／任意精度，或采用已证明安全的约分与 mulDiv；乘完再扩大类型没有用。非负 `ceilDiv(n,d)` 也不宜不加检查地用 `(n+d-1)/d`，应由 `n/d`、`n%d` 计算并检查商的加一范围。

任一步溢出、除数为零、输入超出 scale 或结果超业务上限，都产生明确的数值错误码和输入版本证据。对新开、加仓或其他扩大风险操作，拒绝裁决并保持不产生额度预留；不能把超大需求饱和成 `MaxInt64` 后继续做差，也不能将溢出回绕成小正数。存量风险计算遇到异常时，状态应标成不可可靠计算并进入保护流程，而不是报告 `HEALTHY`。

## 第 6 层：仓位碰到风险档位边界，究竟选哪档？

**面试官：** 现在增加风险档位，名义价值恰好等于边界 `B`。不同实现一个选低档、一个选高档，IM/MM 就可能不同。怎样定义可唯一重现的选择？

**面试者：** 档位配置必须定义无重叠、无空洞的区间、量纲、边界包含关系、档位内费率或限额，以及适用的仓位范围。一个明确的示例约定是按候选操作后的未舍入名义价值选择半开区间 `[lower, upper)`；于是恰好 `N=B` 进入以 `B` 为下界的下一档。若真实产品采用不同口径，例如按最大仓位数量选档、按累进维持保证金求和或用不同边界约定，应以其正式规则为准，不能把这个例子说成通用做法。

档位选择前使用的名义价值精度也要确定：可以用精确的宽位有理数比较边界，再把需求向上量化；或者明确规定按金额原子量化后的值选档。两者都能实现，但边界附近可能不同，不能混用。新订单应按候选操作后的风险敞口选档，不能只拿成交前档位验算导致订单跨档后低估需求。

测试至少覆盖 `B` 前一个可表示原子、恰好 `B`、`B` 后一个原子，并确认边界归属唯一。总览教学主例没有风险档位，仍固定使用 `IMR=20%`、`MMR=5%`；这里的 `B` 只说明如何扩展模型，不改变 100/90/84 的既定结果。

## 第 7 层：档位调整何时生效，怎样防止一次裁决混用两套参数？

**面试官：** 配置中心发布新档位时，有些分片已收到，有些还在用旧配置。一个风险结果如何证明使用的是同一套规则？存量仓位和正在处理的订单又怎么办？

**面试者：** 参数不是无版本的“当前配置”。每套规则要有不可变的 `config_version` 或内容哈希，并声明风险池／合约适用范围及生效点，例如风险池有序的 `effective_account_seq`。一条裁决绑定唯一配置版本；计算期间不能分别读到新 IMR 和旧 MMR，也不能按服务本地发布时间猜测是否生效。

生效协议要定义存量仓位如何重算、未成交预留是否重估、已批准订单是否沿用决策版本、配置传播尚未完成时是否暂停扩险。可以选择在序号边界原子切换并按新规则重算，也可以安排明确的迁移期；但不能在版本不一致时放行扩大风险。风险结果应保存规则版本、档位 ID、选档输入和规范化摘要，使同一输入重放能得到同一结果。

## 第 8 层：怎样证明不同语言和重放结果一致，而不只比较展示小数？

**面试官：** Go 服务、离线审计脚本和另一个语言的风控服务都按规则实现。它们都显示 `4.20` 不代表内部裁决一致。你如何验证跨语言确定性和边界安全？

**面试者：** 比较规范化输入、整数中间结果、舍入后的金额原子、档位 ID、配置版本、状态码和结果摘要，而不只比较格式化字符串。建立独立的高精度参考模型，对合法输入做差分测试；生产实现与参考实现若在整数结果上不一致，就定位到 scale、舍入、档位或溢出契约，不能用容差掩盖。

固定案例必须覆盖 Mark=100/90/84 的 `U/N/IM/MM` 和逐仓／Cross 权益，确认 84 时逐仓触发而 Cross 不触发。反例还应包括负 PnL 的非整除、`E=MM` 与其上下一个金额原子、档位边界两侧、最大合法数值、乘法溢出、`MinInt64` 绝对值、缺少配置版本、重放同一输入及输入精度超限。属性测试可检查需求舍入不低于精确需求、权益舍入不高于精确权益、同一版本输入重复计算结果完全相同。

这些是建议的验证设计，不表示已经运行过测试或在生产中观察到相关结果。要声称验证完成，仍须实际执行并报告测试范围和结果。

## 本题收束

### 已经讲透的机制

- 每个定点字段都有单位、scale、范围和入口量化规则；底层同为整数不代表量纲相同。
- PnL 与风险需求使用不同方向的舍入契约，且阈值比较使用未格式化的同 scale 整数。
- 计算图、舍入点、负数除法和溢出处理都属于版本化风险规则。
- 档位的区间归属、候选敞口口径和参数生效序号必须唯一、可审计。
- 相同输入版本与规则版本必须得到相同整数结果；异常数值不能降格为安全结果。

### 最容易答错的边界

1. 认为“用整数”就自然精确，却没有写单位、scale、溢出范围和舍入方向。
2. 对负数用朝零截断，低估亏损；或把 `round` 当成所有语言共同的舍入语义。
3. 每步随意回到金额 scale，造成双重舍入和跨语言结果分歧。
4. 用展示精度做 `E <= MM` 判断，或把等值边界当成不触发。
5. 档位恰好等于边界时没有包含关系，或用成交前档位判断跨档后的仓位。
6. 溢出后饱和、回绕或转浮点继续计算；配置尚未生效一致时仍扩大风险。

### 验证反例

构造一个独立的准入边界用例：`N_atoms=51`、`IMR=20%`，精确需求为 `10.2` 个金额原子，可用权益为 `10` 个原子且无其他占用。正确的 IM 向上取整为 11，Available 为 -1，不能准入；若向零截断 IM 为 10，Available 变成 0，就可能按 `Available>=0` 错误放行。构造名义价值恰好 `B`，让两种实现选出不同档位；若结果没有唯一归属，参数契约不完整。最后将接近上限的数量与价格相乘；若溢出被当成小数继续准入，失败关闭没有成立。

上述反例与主例应共同进入可重复的数值测试；所有档位和额外精度规则仍属明确的实现契约示例，不改变专题的教学基线。
