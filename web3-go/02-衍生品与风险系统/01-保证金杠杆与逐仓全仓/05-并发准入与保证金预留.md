# 大问题 5：并发下单、成交和撤单如何避免重复使用保证金？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 保证金 / 线性 USDC 永续 | 保证金是支撑交易的钱；本例合约以 USDC 计盈亏，按数量乘价差计算。 | 不是手续费，也不等于借钱买现货。 |
| Cross 全仓 / 逐仓 / 风险池 | 全仓共享池内资金，逐仓只用指定桶，风险池是一起算风险的范围。 | 并发额度应按共享资金的池来协调，不是按单张订单各锁各的。 |
| Equity / IM / MM / Available | 当前风险权益、扩大风险的初始要求、现仓维持要求、扣除占用后的新增风险额度。 | 主例 Mark=100 时全仓 E40、IM20、可用20；预留本身不减权益。 |
| Mark / 名义价值 / 杠杆 | 风险估值价、仓位绝对规模、规模与相应资金的比例。 | 固定 Mark100 和 20% 要求时，买 0.75 ETH 的增量要求才简化为 15。 |
| 并发 / TOCTOU | 多笔操作交错进行；TOCTOU 是查完余额到实际占用之间被其他操作插队。 | 两单各需 15，不能都读到同一份可用20并通过。 |
| 原子裁决 / CAS / owner | 检查和占额共同提交；CAS 只允许版本没变的提交；owner 是系统负责人。 | 第一单占15后，第二单必须看到只剩5，本文选择整笔拒绝。 |
| reservation / approved_im | 带身份的订单额度预留，以及当时批准的预算。 | 这份历史预算记录去向，不是已经支付或损失的资金。 |
| remaining / consumed / released | 同一批准批次里，仍占用、已交给成交、已确认退回的预算份额。 | 三部分合起来等于原批准额；当前仓位 IM 则另按新价格算。 |
| approved_qty / cum_fill_qty / unresolved_qty | 批准数量、累计成交量、尚未确定结果的量。 | 数量守恒与 USDC 预算守恒是两本不同单位的账。 |
| command_id / order_revision / payload_hash | 请求身份、订单版本、请求内容摘要。 | 重试认原请求；同编号换了数量或方向不能覆盖原授权。 |
| 送撮合授权 / submission_state | 批准订单可执行的凭据，以及是否已经被撮合受理的状态。 | 必须先有耐久预留再送单，受理未知时不能释放。 |
| 部分成交 / trade_id / 额度转换 | 只执行一部分；成交身份确保只处理一次；对应额度从订单约束转成成交风险。 | 成交0.25后，原预留15中的5转入仓位要求，余单仍占10。 |
| 在途义务 / 影子仓位 | 成交确定但账本或持仓尚未追齐时，用明确记录保留其风险。 | 不能出现预留已释放、真实仓位又没更新的漏算窗口。 |
| 撤单意图 / 权威终态 | 点击撤单只是请求；撮合的最终状态才证明哪些量不会再成交。 | 发了撤单不代表整笔余量都可退，撤单前可能又成交一笔。 |
| terminal_exec_seq / effects_watermark / DRAINING | 最终执行序号、已完整应用效果的水位、等待补齐的阶段。 | 收到终态也要确认此前成交齐全，不能只看“撤单成功”四个字。 |
| Reduce-Only / 反手 | 只减已有仓位的执行限制；越过零后开出相反仓位叫反手。 | 两笔只减仓单共享可减量，不能分别都占完整原仓。 |
| 不利成交 / 需求重估 | 成交价比估值不利会立即浮亏；价格或规则变化后要重新算所需额度。 | 原预留15不是永久够用的保证，更不能用旧预算抹掉新缺口。 |
| 改单 / amend / 撤旧建新 | 修改已存在订单；若无原子修改协议，就先终结旧单再建新单。 | 旧单仍可成交时，不能先把它的预算借给新单。 |
| 幂等 / 去重 / TTL | 同业务只生效一次、识别重复记录；TTL 是记录保留期限。 | 去重证据不能太早删除，否则旧订单重投可能重新变新单。 |
| Inbox / Outbox / offset | 可靠记录已收业务和待交付消息；offset 仅表示消息读到哪。 | 读取成功不等于业务副作用已提交，重发须可安全重复。 |
| owner_epoch / fencing / 快照重放 | 新负责人代次、拒绝过期权能、从保存状态和后续事件恢复。 | 进程重启不代表预留归零；旧主复活也不能继续创造新授权。 |
| 不变量 / 故障注入 | 始终必须成立的规则，以及在关键步骤故意模拟失败来检查。 | 最终现金对上仍不够，必须检查中途从未重复花额度。 |

## 把整篇文章压缩成一个故事

小林的全仓池有 40 USDC，已持有 1 ETH 多仓。固定 Mark=100、初始保证金率20%时，现仓要求20，可用额度20。现在两笔加仓单同时各要15，系统让第一笔检查和预留一起提交，第二笔看到只剩5后拒绝。这里占住15不是花掉15，而是不让其他请求再拿它作担保。

获批的0.75 ETH买单先成交0.25，对应5转换成仓位风险，剩余0.5继续预留10。小林发出撤单，但撤成前又成交0.1，只是消息晚到。最终真正成交0.35、撤销0.4，所以预算15应分成已消费7、已释放8；全部结转后总仓位1.35，IM27，可用13。若撤单消息先到就退10，其中2便会被重复使用。

因此系统不能凭“点了撤单”“调用超时”或“消息读完了”退钱，而要拿到权威终态，补齐此前成交及账务效果。途中崩溃，就按原订单、成交和预留身份恢复，旧负责人也得被围栏拦住。全文在证明同一件事：风险从挂单转为成交、再转为真实仓位时，不能漏一瞬，也不能重复算两份；历史预算与实时保证金要求还必须分开。

**流程位置与核心机制：** 本题覆盖风险准入、订单送撮合、部分成交、撤单和成交结转。核心不是在余额上加一把锁，而是把共享风险池的“检查与占额”做成同一次可恢复裁决，再用订单执行顺序把额度从未成交预留转成成交义务，最终只释放被权威终态证明不再可能成交的余量。

## 第 1 层：两笔订单都看到有余额，为什么不能都放行？

**面试官：** Cross 账户已经有主例的 1 ETH 多仓，Mark=100，两笔加仓订单同时到达。每笔再买 0.75 ETH，成交价格也假设为 100。怎样避免两笔订单重复使用保证金？

**面试者：** 当前 Cross 权益为 40，仓位 IM 为 20，没有其他预留，所以新增风险可用额度是 20。每笔加仓需要增量 IM `0.75×100×20%=15`。两笔如果各自读到 20，都先返回通过，再异步扣额度，合计会批准 30，超过已有 20；这是检查与使用分离的 TOCTOU 问题。

我会以共享 Cross 风险池为裁决单元，让两个请求竞争同一个可提交版本。第一笔在池版本 8 上原子完成校验和预留 15，提交版本 9，可用额变成 5。第二笔只能在版本 9 上裁决；本题采用不足则整笔拒绝，因此第二笔拒绝，不默默把数量改小。

```text
Available = E − 当前仓位 IM − 未成交增量 IM 预留 − 其他锁定额
          = 40 − 20 − 15 − 0 = 5
```

这个 15 是风险额度占用，不是从 40 USDC 中支付了 15；账本现金和权益不因预留本身减少。逐仓的相同主例在 Mark=100 时桶内权益 20、IM 20，可用为 0，不能把桶外另 20 自动拿来支持新订单。

池级串行裁决、数据库行锁或版本 CAS 都可以表达同一约束，但必须覆盖检查及预留提交。只在某个 Go 进程里锁住读取，或按订单号分别加锁，都不能防住共享资金的两个请求。

## 第 2 层：预留究竟存什么，事务必须一起提交哪些状态？

**面试官：** 你把第一笔订单占住了 15。如果只存一个 `reserved=15`，之后怎样知道谁有权消费或释放？请把状态和事务边界说具体。

**面试者：** 我会区分池状态、预留身份和订单执行进度，至少保留以下字段：

| 对象 | 关键字段 | 用途 |
|---|---|---|
| 风险池 | `risk_pool_id、mode_version、member_version、account_seq、owner_epoch、input_version` | 限定共享范围、当前裁决版本和写入者 |
| 命令 | `command_id、payload_hash、result_id` | 同一请求重试返回原结果，同身份不同载荷拒绝 |
| 预留 | `reservation_id、order_id、order_revision、risk_pool_id、approved_im、remaining_im、consumed_im、released_im、decision_version` | 标识批准预算及其去向 |
| 数量进度 | `approved_qty、cum_fill_qty、terminal_unfilled_qty、unresolved_qty、applied_exec_seq` | 跟踪成交、终止余量和未决数量 |
| 交付与屏障 | `submission_state、terminal_exec_seq、effects_watermark、outbox_id` | 证明撮合是否受理、终态之前的成交是否已完整结转 |

下单事务在存储侧校验 owner epoch、模式版本和输入版本，读取足以完成裁决的池状态，再共同提交：命令去重结果、reservation、池级占额及新序号、待送撮合的持久命令。任一失败就整体不生效；撮合请求只能在这个提交之后发出。

这里的 `consumed_im` 是批准预算中已转交成交处理的历史份额，不是当前仓位 IM，更不是已经亏掉的现金。对于固定版本的一笔批准预算，要求：

```text
approved_im = remaining_im + consumed_im + released_im
approved_qty = cum_fill_qty + terminal_unfilled_qty + unresolved_qty
```

数量等式中的已成交量包括已确定但尚待完成跨域结转的成交。金额等式只记录这一批准版本／分段额度的历史预算去向，不是当前保证金占用公式；实时仓位 IM 依据当前 Mark 和当前参数另算，价格或规则变化后不必等于 `consumed_im`，两者不能混为一张余额表。

本题预留阶段可取 `HELD、SUBMIT_UNKNOWN、LIVE、CANCEL_PENDING、DRAINING、CLOSED`。状态迁移必须由持久事实驱动：例如 `DRAINING` 表示已知订单终态、但之前成交或账务效果尚未全部追齐，仍不能把未决额度当可用。

## 第 3 层：预留提交以后，怎样避免未占额订单先进入撮合？

**面试官：** 状态已经落库，但向撮合发请求又是一个网络操作。如果先发后写、写完没发、发了没收到回包，各有什么处理？

**面试者：** 不能先发后写，否则撮合可能已成交，而预留事务后来失败，形成没有预算支持的确定义务。正确顺序是先持久提交预算和待交付命令，再由交付方发送同一订单版本。

送撮合的授权至少绑定 `order_id、order_revision、reservation_id、risk_pool_id、mode_version、approved_qty、允许的价格边界、授权代际`。撮合或其接入边界必须校验授权，重复送达同一订单版本不得变成两张独立订单。订单修改也不能复用一个已失效版本的批准额度。

三个故障窗口分别处理：

1. **提交前崩溃：** 没有有效预留，也不应存在合法送撮合命令；同身份重试重新查询裁决。
2. **提交后、发送前崩溃：** 持久待交付记录仍在，恢复后继续发送；期间额度保持占用。
3. **发送后响应丢失：** 标为受理结果未知，按原订单身份查询或重投；不能按“客户端没看到成功”释放。

只有撮合权威证明该版本没有受理且以后也不会受理，或者返回可核验的终态及执行屏障，才能进入释放流程。明确拒绝必须排除同身份的并发受理，不能把某一次失败回包等同于原订单不存在。

即使授权附带有效期，也必须规定撮合如何拒绝过期授权、如何处理过期前已受理订单，以及怎样确认不存在在途成交。风险服务本地定时器到期，不足以证明额度能被安全再用。

## 第 4 层：部分成交时，预留怎样变成仓位需求而不重复扣除？

**面试官：** 第一笔 0.75 ETH 加仓单已经进入撮合，其中 0.25 ETH 在 100 成交，余下 0.5 还挂着。现在应占多少保证金？如果持仓和账本通知先后到达呢？

**面试者：** 在这个独立推演里 Mark 始终为 100、无费用，原仓位 1 ETH，Cross 余额 40。成交后仓位变成 1.25 ETH，IM 从 20 增到 25；订单剩余 0.5 ETH 的增量预留为 10。因此：

```text
批准预算 15 = 已转交成交处理 5 + 未成交仍预留 10 + 已释放 0
新 Available = 40 − 25 − 10 = 5
```

不能继续扣完整 15 再扣仓位 IM 25，这会把同一成交份额扣两遍；也不能先把 5 释放为可用，过一会儿才增加仓位 IM，这会短暂造出 5 的额外开仓能力。

在单事务风险投影中，同一个 `trade_id` 对应的仓位版本、预留消费、成交义务状态、去重记录和池序号一起推进。若仓位与账本由不同权威域异步交付，风险侧先把这笔成交登记为 `pending_trade_obligation`，记录数量、成交价、预算份额、应到的仓位／账本版本及完成位图。

转交预算时，风险覆盖必须连续：未成交预留减少的同时，风险影子仓位或待结转义务接住相应敞口；待权威效果齐全，再用真实仓位替换影子，不能同时叠加两份。若无法证明这个过渡估值保守，就暂停该池扩险，保留未决占用，等待版本屏障，而不是猜一个 Available。

本例同价加仓没有已实现盈亏，账本金额不变，但仍需有“本成交无需金额变动／对应结转已完成”的明确证据。真实减仓会涉及已实现损益，不能因为余额数没变化过就跳过结转依赖。

## 第 5 层：撤单请求到了，为什么不能马上释放余下 10？

**面试官：** 现在用户撤掉剩余 0.5 ETH。撤单确认先到风险服务，最后一笔成交消息却晚到了。怎样保证同一份 10 不会既成交又被释放？

**面试者：** 撤单请求只表达意图，不是订单已经不能成交的证据。我会让成交与撤单由撮合权威按同一订单执行序列裁决，终态携带最终累计成交量、未成交终止量和 `terminal_exec_seq`，风险侧核对自己已应用的连续执行水位。

假设撤单前又成交 0.1 ETH：最终累计成交应为 0.35，真正撤销的是 0.4。Mark=100 的推演中：

```text
0.75 = 已成交 0.35 + 已撤销 0.40 + 未决 0
15   = 已消费预算 7 + 已释放 8 + 仍预留 0
仓位 = 1.35 ETH，IM = 27，Available = 40 − 27 = 13
```

如果风险侧只看见早先 0.25 的成交，收到终态也不能直接释放 10。它应进入 `DRAINING`，补齐终态之前缺失的 0.1 成交及其结转效果，或者用包含这些效果的权威快照完成等价核验；完整之前不能把该份额释放出来。

```text
收到撤单请求 → CANCEL_PENDING，预留不变
收到权威终态 → 固定最终成交量及终止余量
核对执行序列连续、成交效果齐全 → 消费成交份额，释放终止余量
```

网络迟到的成交只要在权威终态之前，就必须履约；它不因“客户端先看到撤单成功”而无效。重复的终态或成交按身份返回原效果。若出现权威序列上在最终终态之后的新成交，或终态累计量与成交集合冲突，应隔离并对账，不能默默多释放或丢掉成交事实。

## 第 6 层：能否把所有订单都按“数量乘 20%”预留？

**面试官：** 你刚才能按数量线性分摊，是不是卖单可以直接预留零，买卖相反就互相抵消？Mark 变化以后，15 的预算还永远够吗？

**面试者：** 不能。前面的线性分摊依赖同方向加仓、固定 Mark=100、成交价=100、没有档位和费用。这是便于解释预算转换的特例，不是通用订单风险公式。

单向净持仓中，普通卖单可能先平多、再过零开空；多个相反挂单也可能以不同顺序成交。必须计算产品允许的成交路径及其增量风险，不能无条件把相反委托净掉。最简单的保守做法是不授予未经证明的互相抵消优惠。

Reduce-Only 还要有可执行的数量约束。已有 1 ETH 多仓，两张各卖 0.8 的 Reduce-Only 如果各自看到可减 1，并在执行时不再约束，合计成交 1.6 就会反向开空。撮合应按确定顺序限制可减量，保证成交总量不会越过实时净持仓；并发平仓、普通单和强平占用的减仓资格也要协调。不能只因为接口字段叫 Reduce-Only，就假定它天然无风险。

价格和参数变化时，实时订单风险也需要重估。原 `approved_im=15` 是历史预算证据，不必始终等于当前风险需求。若允许追加预算，应建立有独立身份的补充批准批次，每批分别守恒；若预算不足，则按契约限制新增成交、缩量或撤掉未成交余量。尚未确认撤销的订单仍算未决义务，不能把“已发撤单”当成减险成功。

对于可能产生不利成交价或滑点的订单，准入就应覆盖允许价格边界内的成交后损益和 IM，必要时在成交提交前重新授权；成交一旦确定，不能因后续重估不通过就撤销它。Mark 波动也可能让存量 Available 变负，这要求阻止继续扩险或进入处置，不意味着可以删除既有成交。

## 第 7 层：预留原子了，划转、行情和模式变更还能怎样破坏它？

**面试官：** 假设订单预留自身有事务，但同时有人转走 Cross 余额，行情更新了 Mark，另一个请求还在切换账户模式。只锁 reservation 表是否足够？

**面试者：** 不够。需要共同排序的是影响同一池可用额度和归属的命令，不只是 reservation 的写操作。划出资金、创建新预留、确认成交、释放余量、模式冻结，都必须对同一池状态版本裁决。

例如先允许转出 20，又让下单基于转出前的 40 预留 15，即便两个业务各自事务正确，组合仍然超用。它们必须共享池级版本检查或同一个有序 owner：先转出后下单，第二步看到余额和锁定的新版本；先预留下单后转出，划出校验必须看到那 15。

计算若较重，可以在不可变输入版本上算，再在短事务内比较 `account_seq、mode_version、member_version、price_id、config_version、owner_epoch` 以及相关锁定版本；有任一变化就重新裁决，不能只 CAS 一个不随资金划转更新的计数器。

行情和配置以明确生效点纳入风险输入。这里的版本正确不代表价格足够新鲜，提交时仍需校验新鲜度、质量与未结转义务。跨源有缺口，就停扩险或采用已证明保守的覆盖方式。

模式迁移开始后，旧模式不能继续签发新授权；已经受理的旧订单须被结清或显式迁移。本题采用先冻结扩险并排空旧订单的路径。风险池顺序与撮合订单执行顺序不是同一个序号，二者靠订单身份和终态屏障衔接，不能把某个 Kafka offset 直接当作所有域都已结清的证据。

## 第 8 层：超时、重复请求和改单如何不重复占额或释放？

**面试官：** 第一笔预留成功后客户端超时，于是重试；后来撤单回包也丢了，用户又点了改单。多个接口之间怎样保证身份不乱？

**面试者：** 下单、撤单、改单各自有稳定命令身份，但都指向明确的订单版本。下单重试沿用原 `command_id`；相同身份和载荷返回原批准或拒绝结果，身份相同但载荷不同返回冲突，不能覆盖原订单。客户端换新身份代表另一笔意图，系统不能靠“看起来很像”猜它是重试。

预留已提交、响应未知时，查询持久结果。撤单请求重复只重复确认原撤单意图，真正释放仍由订单最终执行状态驱动，且释放记录必须有唯一业务键，例如 `(reservation_id, terminal_revision)`。同一笔 `trade_id` 重复到达，不能重复消费预算、加仓或结算。

改单要区分产品有没有原子 amend 协议。没有时采用撤旧再建新：旧单未拿到终态屏障之前不能提前释放，新单若要同时上线必须有独立足够的预算。不能把旧单的 10 暂时给新单用，却让旧单继续可能成交。有原子改单时，也要由撮合确认旧版本停止成交和新版本开始的同一个切点，风险预算才能在同一裁决中移交。

去重结果不能随意按短 TTL 删除。至少要覆盖订单寿命、重投及恢复窗口；归档后保留可查询的终态身份或拒绝过期身份的代际边界。否则一笔几天前已撤销的订单重投后，可能被重新当成新单。

所有“超时后重试”都只是重新查证或推进同一工作流，不产生一次新的消费或释放资格；不确定状态由恢复任务继续追踪，不能靠超时自动归零。

## 第 9 层：主节点崩溃后，如何恢复到同一份额度账？

**面试官：** 如果在预留提交、成交消费、撤单释放的任意一步崩溃，另一个实例接管；旧主还可能复活。哪些数据决定恢复结果？

**面试者：** 恢复依据是耐久业务提交点，而不是内存 map、Go channel 或单独的消息消费位置。池状态、预留变更、成交去重、应用水位和待交付结果应在同一事务或等价可证明协议中推进；事务前崩溃则无效果，事务后崩溃则恢复原效果并继续交付。

跨服务交付用持久待发记录和消费去重衔接：生产方提交业务事实与待发记录，消费方提交业务效果与 Inbox 身份。发送可能重复，但同一成交或释放效果只提交一次。如果业务写入与消费 offset 分离，offset 提前推进可能漏账，offset 落后则必须允许幂等重放。

新 owner 取得更高 `owner_epoch` 后，从可校验的快照与其后的连续事件恢复，检查预留预算守恒、未决订单、未齐成交效果和终态屏障。所有池写入在存储侧校验 epoch；旧主拿着旧锁或旧连接复活也不能写。

外部效果也需要围栏：撮合接入校验订单授权代际和模式版本，避免旧主在新模式下签发新订单。不过，**已经合法提交且仍有效的旧授权**不能只因切主就假定不存在；它可能已在撮合中，恢复后仍须保留相应预留，查到终态或完成明确撤销协议。

恢复扫描遇到长期 `SUBMIT_UNKNOWN` 或 `DRAINING`，按原订单和成交身份查询、补发、补齐水位；不明确时保持限制扩险并告警。进程重启不能把 reservation 设为零，消息队列追平也不能替代订单、仓位与账本效果的完整性核对。

## 第 10 层：怎样验证中途从未把同一额度花两次？

**面试官：** 你有状态、版本和恢复机制了。最终余额对上是否就够？请给出可以直接推翻方案的事件序列。

**面试者：** 不够。预留不改现金，最终现金正确完全可能掩盖中途两笔超额授权。应逐个已提交状态检查数量、预算去向、可用额度和身份，而不只比较最后的 40 USDC。

| 检验序列 | 必须成立的结果 |
|---|---|
| 主例 Cross 在 Mark=100，同时申请两笔各占 15 的加仓 | 最多一笔完整通过；另一笔看到只剩 5 后拒绝 |
| 原下单提交成功但回包丢失，重复发送十次 | 只有一个预留和一个有效订单版本，额度只占 15 |
| 成交 0.25 后又成交 0.1，撤单终态先于后一笔成交消息到达 | 不提前释放 10；补齐后消费预算 7、释放 8，仓位为 1.35 |
| 已消费成交预算但仓位或损益结转缺一部分 | 保留对应义务或停扩险，不出现“既无预留又无仓位”的空窗 |
| 撤单确认与成交、释放消息各自重复，并在每个提交边界崩溃 | 重放后终态和预算去向相同，不重复结转或释放 |
| 旧主恢复后试图写新预留，或旧模式发出新授权 | 在写入／授权边界被代际围栏拒绝 |
| 逐仓主例 Mark=84，未发生追加划转 | 仍是 E=4、MM=4.2，不能借桶外 20 得到“安全”结论 |

还要检查 `approved_qty` 的去向守恒、每笔预算批准批次守恒、同一成交义务在预留／影子／真实仓位之间没有漏算或重复计入，以及终态之前的执行序列没有缺口。对价格变化后的实时 IM 单独验证，不要求它永远等于历史 `consumed_im`。

这些是应执行的模型与故障测试清单；本文提供手工数值推演和协议设计，没有运行 Go 撮合、数据库并发、故障注入或性能测试，也不声称来自某个真实平台实践。

## 本题收束

### 已经讲透的机制

- 并发安全的提交单元是共享风险池的检查与占额，不是单张订单或一次余额读取。
- reservation 是有身份、数量、预算去向和版本的约束；权益不因预留本身减少。
- 成交份额先转成交义务，再与权威仓位、账本效果对齐，风险覆盖全程连续。
- 撤单释放依赖权威终态和连续效果水位；网络先后与本地超时都不能替代它。
- 幂等解决重复，序列解决先后，事务解决局部提交，epoch 围栏解决旧主；它们各解决一个明确漏洞，不能互相代替。

### 最容易答错的边界

1. 把已消费预算当成当前 IM，价格一变就无法解释守恒。
2. 先释放成交预算、后更新仓位，或仓位 IM 与完整订单预留重复扣除。
3. 收到撤单请求就释放；看到终态但未补齐此前成交也直接释放。
4. 把普通反向单当成天然减仓，把 Reduce-Only 当成无需执行约束的标签。
5. 锁住预留表却不约束资金划出、模式变更和其他共享额度使用者。
6. 认为授权到期、客户端超时、消费者 offset 追平或主进程重启就代表义务消失。

### 一个能检验方案的反例

Cross 原仓 1 ETH、Mark=100、余额 40，先批准加仓 0.75 ETH 的 15 预留，成交 0.25 后再成交 0.1。风险侧先看见撤单终态，后看见第二笔成交。如果它先按旧累计成交量释放 10，并允许新单用掉这 10，那么其中 2 USDC 已经属于迟到成交的预算，却又得到了一次授权。

正确方案必须把最终累计成交 0.35 和终止余量 0.4 对齐：消费预算 7、释放 8，全部结转后仓位 1.35、IM 27、Available 13。这个结论在消息重排、重复和任意提交点崩溃后都应相同；否则“有锁、有队列、有重试”还没有证明保证金不被重复使用。
