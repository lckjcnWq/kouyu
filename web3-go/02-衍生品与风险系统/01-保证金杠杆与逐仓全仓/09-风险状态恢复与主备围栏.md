## 先看懂：关键词大白话解释

| Inbox / Outbox | 已处理消息身份簿与待发送消息箱，跟业务提交可靠衔接。 | 前者防重算，后者让结果提交后即使断电也能补交付。 |
| offset / broker | 消息消费位置与消息中间件。 | offset前进不自动证明风险已记账，更不代表强平已执行。 |

| 日志缺口 / 乱序 / 重放 | 中间事件缺失、到达先后颠倒、按历史顺序重新应用。 | 501之后缺502，不能直接跳到503放行新风险。 |
| 原始规则 / calculator_version | 历史事件使用的参数与计算器版本。 | 重放不能临时拿当前Mark或新费率代替过去输入。 |
| 运行字段 / 业务摘要 | 重试次数、机器时间等执行信息，与真正决定业务结果的输入分开。 | 新主epoch更高，不意味着同一历史风险应被当成一次新触发。 |

| RPC超时 / 提交未知 | 没收到答复，无法仅凭调用方判断操作是否已成功。 | 查原事件和提交记录，不能重新占额或自动清掉旧预留。 |

## 把整篇文章压缩成一个故事

风险主节点刚把小林一笔订单的预留和处理结果提交，就断网，调用方没有收到成功。随后节点崩溃，客户端又重试。如果新节点把超时当失败，就可能再占一次；如果一重启就把预留清零，又可能让已经送进撮合的订单失去风险覆盖。正确恢复先查原编号，已提交就沿原结果继续，未知则保留义务。

新节点拿出序号500的有效快照，接着读到501、重复501、503。重复501按身份只处理一次，但502缺了，就不能自称已经恢复到503，也不能借“队列空了”开放新单。恢复还要使用原参数和计算规则，找回订单预留、未齐成交、去重证据和待发送结果；坏快照回退到更早有效锚点，缺口补不上则继续限制扩险。

最后旧节点又活了。新节点已取得代次8，存储必须拒绝旧代次7的写入，不能只期待旧节点自觉停机。风险结果可以补发，下游也按同一裁决身份去重；重放到逐仓E4、MM4.2只恢复风险触发，不代表再执行一次强平。整篇要恢复的是唯一、完整、可追溯的业务状态，而不只是让进程重新亮绿灯。

## 第 1 层：风险分片崩溃后，什么才算一笔状态更新已提交？

**面试官：** 风险分片读到一笔成交，更新仓位风险并准备返回成功。它在不同指令之间都可能崩溃。请定义业务提交点，而不是只说“写数据库”。

**面试者：** 先区分外部源事实和风险派生状态。成交事实由撮合／成交域权威提交，风险服务不能因自身失败撤销成交。风险分片的提交点则应是一个可持久恢复的原子边界：风险状态已经按该事件及规则版本更新，事件身份和已应用序号已记录，待交付的 RiskResult／通知已进入同一事务的 Outbox，且新 owner epoch 校验通过。只有这一耐久事务提交后，风险服务才能确认“已处理到该序号”。

一个具体的关系库存储方案，是在同一事务中追加 `RiskJournal(pool_id, account_seq, event_id, payload_digest, normalized_input, config_version, calculator_version)`，写入池状态、Inbox、命令结果和 Outbox，并条件更新 owner epoch 与期望状态版本。Journal 不只记录外部成交，也记录预留命令、撤单释放、参数激活等风险自身的状态迁移；否则仅靠成交日志无法还原未成交订单已占住的额度。事务提交依赖所选存储的耐久保证，不能把仅写入进程缓存叫提交成功。

如果存储不支持单事务，就必须设计等价的日志协议，并证明崩溃后可判定哪些阶段已生效。内存字段更新、RPC 返回、消息已拉取或消费者 offset 前进都不是充分提交证据。对 Mark=84 的例子，结果应同时记录对应余额、仓位、订单、价格和规则版本；只保存 `liquidatable=true` 无法解释或重算。风险日志中保存的仓位与余额是带源版本的风险侧副本，不因此取得账本或持仓域的权威所有权。

## 第 2 层：重复成交或风险事件如何保证只生效一次？

**面试官：** 风险分片已经应用成交并提交，但确认响应丢失；生产者重发同一事件，另一条路径还可能送来重复 Mark。如何避免仓位、预留或风险状态被加两次？

**面试者：** “恰好一次传输”不是前提，目标应是至少一次传递下的幂等业务效果。每个事件用稳定 `event_id` 或 `(source, source_seq)` 标识；风险分片在应用状态的事务中记录 Inbox 去重身份。重复身份且载荷摘要一致时返回原处理结果或 no-op；身份相同但载荷不一致时隔离并告警，不覆盖已有事实。

成交消费要按成交 ID 更新持仓和预留；同一成交重放不再增加数量。Mark 更新需要价格来源与版本，旧版本不得回写覆盖新状态。若处置结果自身产生通知或任务，也用稳定 `decision_id`，由下游去重。去重记录保留时间必须覆盖最大重放、故障恢复和补数窗口；如果身份序号可长期重放，就需要长期可验证的检查点或压缩规则，而非任意过期。

## 第 3 层：恢复快照需要包含什么，怎样证明快照内部一致？

**面试官：** 为了少重放日志，你定期做快照。若快照只有权益、IM、MM 和当前仓位，能否安全恢复预留、重复事件和待发结果？

**面试者：** 不够。快照必须代表同一风险池提交点的完整可恢复状态，至少包括：池身份与模式版本、账本和仓位已应用版本、订单及预留的批准／消耗／释放状态、最新可用价格身份及质量、参数版本和档位规则、风险结果及其输入摘要、连续 `account_seq` 水位、Inbox 去重检查点、未完成 Outbox、在途义务，以及快照 schema 版本和校验摘要。

快照内容与水位必须原子对应：不能先写“已到序号 500”，实际只存到 498 的状态。可通过同一事务、写时屏障或先记录完整日志再发布快照清单来实现，并在清单中保存快照 ID、序号、数据校验和及配置版本。启动时校验摘要和 schema 兼容；快照缺字段、校验失败或混入不匹配的风险池版本，就不能拿它宣布可服务。

还要区别最后分配序号 `h` 与连续已应用检查点 `k`：例如日志已分配到 `h=503`，但风险状态只连续应用到 `k=500`，快照就只能标记 `k=500`。分配过序号并不证明该条日志已提交；恢复时应从权威日志确认其提交／中止状态及可追赶的耐久屏障，不能直接把 `h` 当已处理水位。若接管要求追到屏障 `h`，必须证明 `(k,h]` 的必需记录已耐久并连续应用；未提交的已分配槽位须由原协议明确终止或补齐，不能静默跳过。快照存在只证明恢复锚点可用，不证明已经追平屏障。

## 第 4 层：日志重放遇到重复、乱序和序号缺口怎么办？

**面试官：** 快照水位是 500，日志随后读到 501、501、503；中间 502 暂时没到。风险引擎能否先应用 503，再继续提供准入？

**面试者：** 首先要明确定义风险池内有序事件序列，或定义具有相同保证力的分区水位协议。若采用连续 `account_seq`，恢复只从快照水位之后按序应用；同序号同身份重复可去重，冲突身份要隔离，501 之后缺少 502 时不能声称状态已经达到 503。对会影响敞口的缺口，应将该池置为恢复中／降级，阻止扩大风险，直到缺口补齐或通过权威源对账并生成明确修复事件。

每次重放都使用原事件载荷及绑定的参数、数值内核版本，保存历史配置与计算器，不能从远端临时读取“现在最新”价格或规则。相同业务状态摘要排除接管 epoch、重试次数和恢复机器时间等运行字段，以免新主接管本身改变裁决身份。事件不能仅按到达时间排序；Mark 的时间戳也不能替代价格版本或风险池应用序号。已提交日志用于恢复时不能事后把行情改成最新值或省掉已经产生的触发；行情合并只能发生在明确允许的提交前边界，且不得破坏必需的阈值证据、业务序号和输入水位。

## 第 5 层：消息 offset、风险状态事务和响应确认应该怎样排序？

**面试官：** 消费者应用风险状态后、提交消息 offset 前崩溃会重复消费；先提交 offset、再写风险状态又可能永久漏算。怎样安排？

**面试者：** 如果风险状态库和消息 broker 不共享事务，常见稳妥次序是先在风险状态事务中原子写入新状态、Inbox 身份和 Outbox，再提交状态库；事务成功后才确认消息 offset。若在这两步之间崩溃，消息可能重投，但 Inbox 会去重；不能反过来先确认 offset 再写状态。

下游结果通过 Outbox 异步发送，发送可重复；接收端再以 `decision_id` 幂等处理。若发送成功但 Outbox 标记未提交，重发是预期情况。消息 offset 表示传输消费进度，不等于风险状态的提交证据，也不等于订单、账本或强平状态机已完成。不同存储边界要分别说明其耐久提交点与重试身份。

## 第 6 层：主备切换时如何 fencing，避免旧主复活继续写？

**面试官：** 旧主只是暂时网络隔离，并没有退出；选主后新主开始处理事件，随后旧主恢复。依靠租约过期或进程自觉退出够不够？

**面试者：** 不够。每次接管要得到单调增加的 `owner_epoch`，并且所有能改变风险权威状态的写入都必须由存储层验证 epoch。新主取得 epoch `e+1` 后，旧主的 epoch `e` 写入即使来自仍存活的进程也必须被拒绝。fencing 需覆盖状态、已应用序号、Inbox 和 Outbox 等权威提交面，不能只在 RPC 层检查一次。

租约或选主服务用于决定候选 owner；真正阻止旧主写入的是被写入存储强制执行的 token／epoch 比较。接管必须先在权威存储中原子提交新 epoch，再允许新主服务；每笔旧、新主事务都对同一池的 epoch／状态版本条件更新或加锁，使检查与写入不可分割，不能先读 epoch 再无条件写入。这样旧主已开始但未提交的事务，要么排在新 epoch 激活之前完成，要么因条件失效而失败，不得在新 epoch 生效后漏过检查。旧主返回 stale-owner 错误后必须停止消费并重新同步，不能自动换成新 epoch 后沿用旧内存状态。

## 第 7 层：提交结果未知、坏快照或日志不完整时怎样接管？

**面试官：** 主节点客户端在事务超时后不知道提交成功与否；同时最新快照校验失败，而日志归档短暂不可读。新主能不能用当前查询投影补齐后先放行？

**面试者：** 不能把未知当未提交，也不能把投影当权威日志。先使用原事件身份查询提交记录；若事务已提交，恢复到该提交点并由 Outbox 补发；若确定未提交，按同一身份重放。证据暂不可得时，把相关命令标为结果未知并保留其风险占用或在途义务，不生成第二笔额度，也不释放已有预留。

坏快照应回退到最近一个校验通过且 schema 兼容的快照，从其后的连续耐久日志重放。若没有可覆盖缺口的权威日志，就保持该风险池不可用于扩险，等待恢复、源域对账或受控的显式修复事件。查询投影可以帮助发现差异，却不能单凭“看起来最新”创建权威成交、余额或参数版本。恢复期间记录所用锚点、缺口范围、修复依据和审批身份。

## 第 8 层：状态恢复后，怎样避免风险通知或强平任务重复产生副作用？

**面试官：** 重放到 Mark=84 后再次得到逐仓 `E=4, MM=4.2`，风险通知可能重复发，处置消费者也可能重复接单。风险计算是确定的，副作用如何处理？

**面试者：** 把风险计算结果和副作用命令分开。风险结果由 `risk_pool_id + input_digest + config_version` 等稳定要素形成确定身份；同一风险状态重算应得到同一结果身份。写入 Outbox 时在事务中只产生该身份一次；投递失败后可重发，接收端按 `decision_id` 去重并检查其所引用的仓位、价格和规则版本。

风险处置消费者还需自己的持久状态机和幂等键。本专题的 `E <= MM` 只说明该版本风险条件成立，不表示强平已成交；恢复重放不能越过处置域，直接重复下单、重复扣款或伪造完成状态。若新的减仓或价格版本已经改变判断，处置域按其契约校验触发是否仍有效。

## 第 9 层：接管时怎样对账未完成预留、成交与撤单？

**面试官：** 风险分片切换时，一笔订单部分成交，成交事件已在撮合域确定，但风险分片只消耗了一部分预留；撤单结果也在路上。新主能否把剩余预留释放以提高可用额度？

**面试者：** 不能只凭超时、订单查询缓存或“订单看起来已撤”释放。恢复时按稳定 `order_id`、`reservation_id`、成交 ID 和源域版本分别对账。已确定成交必须结转成持仓和已消耗额度；撤单只有在权威顺序确认剩余量未成交且撤单生效后，才可释放对应余量。成交与撤单竞态按订单域的权威序列裁决，不能由风险分片的接收先后决定。

风险分片在对账完成前保留未决额度或按明确策略保守计算在途风险。检查预留守恒：批准额度只可能分解为已消耗、已释放和仍未决部分，不能重复记入。逐仓的账户外 20 USDC 仍不能因恢复时重建余额而混入隔离桶；Cross 则重建其池内 40 USDC 与仓位的归属版本。源账本、仓位和订单成员关系必须对齐后才生成可扩险风险结果。

## 第 10 层：怎样用故障注入证明恢复闭环成立？

**面试官：** 你已经有快照、重放和 epoch。请给出可推翻设计的故障序列与判定条件；只看到服务健康、队列清空够不够？

**面试者：** 不够。验证应在每个耐久边界前后注入崩溃、超时、重复和网络分区，并检查业务不变量。至少包括：状态事务提交前后杀进程；提交成功但响应丢失；Inbox 已写但 offset 未提交；Outbox 已发送但标记未写；快照写入中断或校验失败；日志缺号、重复和乱序；旧主隔离后新主取得更高 epoch，再恢复旧主尝试写入；部分成交与撤单竞态；参数版本切换期间故障。

每次恢复核对风险状态是否等价于从有效锚点完整重放的结果，风险池序号是否连续，成交和余额只应用一次，预留守恒，Outbox 与下游副作用按身份去重，旧 epoch 写入必被存储拒绝。主例重放应保留 Mark=84 时逐仓 `E=4、MM=4.2` 触发、Cross `E=24` 不触发的差异；不能因恢复将逐仓池外 20 算入桶内。

还需验证相同日志与参数版本反复恢复产生同一状态摘要；故障期间未知结果不会释放风险额度；日志不可恢复时风险池会保持限制而非报告安全。以上是验证方案，不是声称已经执行过故障演练。

## 本题收束

### 已经讲透的机制

- 风险分片的提交点要把状态、应用序号、去重身份和待交付结果置于可恢复的耐久边界。
- 快照必须与水位一致，并包含预留、去重检查点、规则版本、在途义务和未完成 Outbox。
- 重放以稳定事件身份、连续序号和原始规则版本为依据；offset 不等于业务提交。
- 新 owner 使用单调增加的 epoch，存储层对每次权威写入执行 fencing。
- 未知提交、日志缺口和坏快照都不能靠投影猜测；无法证明完整时暂停扩险并保留风险占用。
- 风险结果及下游副作用各自幂等，恢复不等于重复执行成交或强平。

### 最容易答错的边界

1. 把 RPC 超时当作确定未提交，创建新身份重复预留。
2. 只保存余额和仓位快照，遗漏应用序号、去重记录、配置版本、预留和 Outbox。
3. 先提交 offset 再提交业务状态，或把 offset 当成风险结果已耐久的证明。
4. 依赖租约和旧主自觉停机，却不在存储写入处验证 owner epoch。
5. 越过序号缺口、用查询投影补权威事实，或在未确认撤单／成交前释放预留。
6. 重放风险状态时直接重新下处置订单，未区分风险触发与执行状态机。

### 验证反例

令旧主 epoch=7 与新主 epoch=8 同时存活；若旧主还能在状态存储提交一次风险预留，fencing 只停留在选主层。令状态事务已提交但 offset 未提交后崩溃；若重放成交使数量翻倍，Inbox 与业务状态没有原子关联。令快照声明序号 500 却缺少 499 对应的预留状态；若系统仍在 500 之后继续放行，快照水位和内容不一致。

恢复正确性的证明对象不是“服务又启动了”，而是完整可追溯的风险状态、连续提交点、无重复业务效果、无遗漏在途义务，以及旧主无法再写。故障注入实际结果应单独记录，本文不声称已做实测。
