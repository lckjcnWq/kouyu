# 大问题 10：风险输入异常或服务积压时如何降级而不放大风险？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 保证金 / 逐仓 / Cross | 支撑交易的钱；指定桶独立承担，或指定池共同承担。 | 故障时也不能为了“救账户”擅自动用逐仓外资金。 |
| 仓位 / 敞口 / 扩险 | 已有未结束交易、承担的价格风险规模、增加这份风险。 | 加仓、扩大挂单、减少担保资金等都可能恶化风险。 |
| Mark / 新鲜度 / 来源质量 | 用于估值的标记价、数据够不够新、来源是否可信。 | 最后一次有效价84，过期后不能继续冒充当前有效价。 |
| Equity / IM / MM / Available | 当前权益、初始保证金要求、维持要求、可新增风险额度。 | E<=MM是本文触线条件；“算不出来”不是E>MM，也不是已平仓。 |
| DEGRADED / UNKNOWN / RECOVERING | 降级、不可可靠判断、恢复中。 | 状态须显式输出，不能拿旧HEALTHY掩盖输入失效。 |
| 降级 / 失败关闭 | 异常时收窄权限，无法证明安全就不新增风险。 | 不是停掉所有动作，也不是为了可用性跳过风控。 |
| 降级矩阵 / 能力状态 | 逐项列明哪些操作允许、拒绝或需条件校验。 | 开仓、撤单、减仓、追加、提款、模式切换不能一刀切。 |
| 不变量 | 无论正常或故障都不许破坏的底线。 | 已成交不抹掉、未知预留不乱放、池外资金不越界。 |
| 保护估值 / 应急参数 | 事先规定、带版本和适用范围的异常处理规则。 | 不能临时挑一个有利价格或较严比例，就声称一定保守。 |
| 版本缺口 / scale / 溢出 | 相关业务未处理齐、数值编码精度、运算越界。 | 任一关键输入不可信都应明示异常，不返回零需求或安全默认值。 |
| 撤单 / 权威确认 / 预留 | 请求取消未成交订单；撮合确认才证明余量不再成交；预留先占额度。 | 撤单请求发出或超时，都不足以释放余量。 |
| Reduce-Only / 反向开仓 | 只能减少现仓的执行限制；卖过原多仓数量就可能开新空仓。 | 多1时两单各卖0.7，若无共同约束会反手空0.4。 |
| 可减额度 / 执行边界 | 当前还允许减掉多少，以及真正提交成交的地方。 | 接口打了只减仓标签仍不够，成交时须原子限制过零部分。 |
| 只减数量 / 经济减险 | 仓位数量减少与风险缓冲改善，不是同义词。 | 极差价格平仓可能使实际亏损增大，即使名义规模变小。 |
| 限价 / 滑点保护 / 流动性 | 允许成交价格边界、约束偏离程度、市场是否有足够对手方。 | 有条件允许减仓不保证能成交；无可信边界不能宣称普通市价单必然减险。 |
| 救援追加 / 自由余额 | 按规则从真实未占用资金补抵押。 | 只入不出也须查来源；不能牺牲另一个风险池来假装救援。 |
| 模式迁移 / 提款 / 移出抵押 | 改共同担责范围、转出现金、抽掉风险支撑。 | 依赖完整输入，本文异常矩阵中拒绝或等待恢复。 |
| 在途义务 / 幂等结转 | 已成交但相关记账未齐的责任，以及只应用一次的补齐处理。 | 降级仍需继续处理确定成交，不能丢消息或回滚交易。 |
| 背压 / 限流 / 有界并发 | 处理不过来就控制入口和同时进行的工作量。 | 队列落后时少接新风险，不以丢成交换取看起来追平。 |
| 行情合并 / 阈值证据 | 按明确契约合并某些价格更新，但必须保留承诺处理的风险事件。 | 90→84→90若只留最后90，可能漏掉逐仓在84的触发。 |
| 退避 / 重试风暴 | 故障重试放慢节奏；无限同时重试会反而压垮服务。 | 恢复任务也要受控，不能越重试越追不上。 |
| reason_code / 水位差 / 最老事件年龄 | 异常原因、处理进度落后多少、最久未处理的事件等了多久。 | 不只看服务能否响应，还要知道风险判断落后在哪。 |
| owner_epoch / fencing / Outbox | 负责人代次、阻止旧节点写入、持久保存待交付结果。 | 恢复前确认权能唯一，触发通知可补发但不虚构平仓完成。 |
| 恢复门禁 / 稳定窗口 / 渐进放量 | 重新开放前的业务条件、持续观察期、先小范围放开。 | 队列为零不是充分条件，还要对账、补缺、校验规则与价格。 |

## 把整篇文章压缩成一个故事

小林有1 ETH多仓，风险系统最后收到Mark84，按本文逐仓桶20的模型，权益4低于维持要求4.2。接着行情断流，风险队列也积压。产品想继续接单，但系统不能把过去的价格和过去的HEALTHY结果当当前判断；输入不可信时先拒绝新的扩险，并把降级原因、版本和未完成义务说清。

系统不必什么都停：撤单可以继续请求，但确认前不释放预留；追加可以在资金来源可靠时受控进行；只减仓则必须知道真实可减数量，并在执行处防止反手。原来多1，两张卖0.7的单不能各自放行到最终空0.4。即使只减数量，极差成交价也可能恶化权益缓冲，因此还需要可验证的价格保护，不保证市价平仓一定经济上减险。

积压时控制新入口，成交和资金流水不能丢；90→84→90也不能无条件只留最后90而抹掉触线证据。服务恢复后，除了进程健康，还得确认日志无缺口、订单与预留对上、价格新鲜、规则一致、旧主不可写，再逐步开放。全文讲的是系统看不清时少作新承诺，同时继续兑现已经作出的承诺，而不是关掉风控赌它没事。

**流程位置与核心机制：** 本题位于持续风险裁决的异常处置阶段，处理行情陈旧或冲突、输入版本不一致、计算失败和服务积压。核心是在无法证明风险状态可靠时，区分扩大风险与降低风险的操作；通过明确的降级矩阵、未决额度约束和可检查的恢复门禁，既不把异常数据伪装成安全，也不让降级逻辑本身制造更多敞口。

**共同前提：** 沿用[专题总览的讨论基线与贯穿案例](README.md#一文字全流程保证金风险如何从下单走到可解释的账户结果)：链下托管、线性 USDC 永续、单向净持仓、单一 USDC 抵押品，`IMR=20%`、`MMR=5%`，账户 40 USDC。1 ETH 在 100 USDC 开多；逐仓桶为 20 USDC，另 20 在池外；Cross 池为 40 USDC。Mark=100/90/84 时 `U=0/-10/-16`、`N=100/90/84`、`IM=20/18/16.8`、`MM=5/4.5/4.2`。Mark=84 时逐仓 `E=4`，因 `E <= MM` 触发本例处置条件；Cross `E=24`，不触发。以上是教学模型，不是所有真实交易系统的通用策略。这里的“只允许减险”需要被订单、持仓和执行语义共同保证，不意味着服务故障时一定能成功平仓。

本题共 8 层，沿着异常判定到恢复逐步增加约束：

```text
降级首先要保护什么不变量
    → Mark 陈旧或冲突时怎样裁决
    → 输入缺失、版本不齐或计算异常时怎样失败关闭
    → 建立逐项操作降级矩阵
    → Reduce-Only 怎样避免反向开仓和重复释放额度
    → 服务积压时怎样背压并保留在途义务
    → 降级状态如何传播且不误报安全
    → 恢复要经过哪些门禁才重新开放扩险
```

## 第 1 层：风险服务异常时，降级要守住哪些不变量？

**面试官：** 风险输入或计算服务不可用时，产品希望尽量不断服。你会先定义什么，避免“可用性优先”被解释成仍然正常开仓？

**面试者：** 我会先定义不可破坏的不变量：没有可信、版本一致的风险输入，就不批准扩大敞口；已确定成交不能被降级回滚；未知结果对应的预留不能提前释放；逐仓不能偷用池外抵押；无法计算不能被标为健康；减仓动作也不能反向增加敞口。状态至少区分正常、降级、恢复中和不可判定，并为每种状态确定允许的命令集合和责任 owner。

降级是风险权限收窄，不是把风控检查跳过。它可以牺牲新开仓可用性，但应尽量保留经过严格边界验证的撤单、减仓和追加有效抵押等操作。减险是否可执行还依赖订单、撮合、账本等必要域可用；风险引擎单方面说“允许”不能保证成交或结算。

## 第 2 层：Mark 陈旧、跳变或来源冲突时如何处理？

**面试官：** 价格源停止更新，最后一个有效 Mark 是 84；另一个来源刚报 90，但时间和质量标记不可靠。你能否任选一个价格继续算出 `HEALTHY` 或触发强平？

**面试者：** 不能静默挑值。风险输入要带价格身份、来源、采样／发布时间、质量和新鲜度策略版本。超过配置的最大年龄或来源冲突不满足既定聚合规则时，当前风险状态应标记为价格降级／不可判定；禁止新的风险扩张。最后一个已验证价格可以用于解释最近一次已知结果，但不能冒充当前 Mark，也不能据此清除已存在的限制状态。

若产品事先定义了保守压力估值或应急价格规则，可以按该规则版本产生单独标记的保护性裁决；不得把临时选出的旧价、均价或人工改值称为有效 Mark。若最近一次有效版本已经满足 `E <= MM`，降级不能把该触发状态自动清回健康。若尚未触发，也不能仅因旧价格没有越线就放行新增仓位。是否启动具体处置由相应处置状态机决定，本题不把风险判定等同强平执行。

## 第 3 层：版本缺口、未知档位和数值错误时怎么失败关闭？

**面试官：** 行情是新鲜的，但持仓版本比成交日志落后；或者 IM/MM 配置版本未知、数值运算溢出。是不是只要有一个结果字段还能算出来，就可以部分放行？

**面试者：** 风险裁决必须对同一风险池的一致输入集合负责。持仓与成交序号有缺口时，不能用旧仓位配新价格声称风险安全；参数缺失或档位不确定时，不能猜默认费率；溢出、scale 超限或校验失败不能转成零值。结果应带具体原因码、缺失版本或错误类型，并将该池置为不可扩险。

如存在明确、可证明更保守的备用参数或数据源，可由版本化保护策略选择；该策略要说明适用范围、风险方向和退出条件。不能只凭“取较严者”一句话处理，因为不同 IM/MM、抵押和仓位版本未必可直接比较。恢复到可信状态前，保持限制并持续追赶或对账。

## 第 4 层：出现异常时，每类操作允许、限制还是拒绝？

**面试官：** 请给出具体操作矩阵。至少区分开仓、撤单、减仓、追加保证金、提现和模式切换；不能把所有请求都一概拒绝，也不能笼统说只减仓。

**面试者：** 以下是本专题可采用的教学降级矩阵，实际产品必须按交易与账本语义定版。`未知/不一致风险输入`表示不能用现有数据作正常风险准入；底层执行域本身故障时，矩阵中的“允许”也需进一步收紧。

| 操作 | 降级策略 | 必要边界 |
|---|---|---|
| 新开仓、加仓、提高杠杆、扩大挂单敞口 | 拒绝或排队待恢复，不创建新的风险预留 | 不用陈旧风险结果或推测参数放行 |
| 撤销未成交订单 | 允许发起；未获订单域权威确认前不释放剩余预留 | 与成交竞态按订单域序列裁决，超时查询原订单身份 |
| Reduce-Only 减仓 | 有条件允许；若仓位版本、数量或执行约束不可信则拒绝／排队 | 原子保证只减不增、不反向，并满足可验证的价格／滑点保护；成交后按确认数量结转 |
| 向仓位追加抵押 | 有条件允许 | 资金来自账本确认的池外自由余额，唯一划转 ID；若来自另一风险池，须先证明转出不损害源池安全 |
| 提现、移出抵押、减少隔离桶资金 | 拒绝 | 可能削弱风险缓冲，需完整健康状态重新裁决 |
| 逐仓／Cross 模式切换或风险池迁移 | 拒绝或冻结至恢复完成 | 需全量成员、订单和待处理义务一致后走迁移状态机 |
| 已提交成交的账本／仓位结转 | 必须继续幂等处理，不得因降级丢弃或回滚 | 以成交身份和权威序号恢复，未结转义务继续占用风险 |
| 风险处置结果交付 | 保留并重试，不虚构执行完成 | 风险触发与下游执行状态分离、下游按身份去重 |

撤单是减险意图，不等于撤单已经生效；追加抵押通常改善缓冲，但仍需验证其归属和是否已被其他用途占用。矩阵要明确允许、拒绝、排队和结果未知各自的响应语义与查询方式。

## 第 5 层：Reduce-Only 怎样保证故障时不会反向开仓？

**面试官：** 一个多仓当前是 1 ETH，用户提交卖出 1.2 ETH 的 Reduce-Only 单。持仓服务有延迟，两个减仓请求还并发到达。怎样保证它们不会共同反向开出空仓？

**面试者：** `reduce_only` 不能只是客户端标签。订单接入、风险池和撮合／执行边界必须共同验证它相对权威仓位只缩小绝对敞口。单向仓位中，卖出多仓的有效成交总量不得超过当前可减的 1 ETH；两个并发请求必须在同一仓位版本或原子减仓额度上排序，后到者只能使用前一笔未占用的剩余额度。若仓位版本不可得，不能基于陈旧的 1 ETH 假定额度仍在。

执行时要重新检查方向、目标数量和剩余仓位，并在撮合执行边界原子裁剪／取消过零部分。部分成交只扣减对应减仓额度；撤单确认后才释放未成交余量。以 1.2 ETH 申报可以被拒绝或按明确产品规则裁剪到最多 1 ETH，但不得出现成交 1 ETH 后剩余 0.2 ETH 自动开空。若系统不能在撮合边界保证 Reduce-Only 语义，就应在该故障状态拒绝此类订单，而不是把希望寄托在下游事后补偿。

只减数量也不代表执行经济上一定更安全。忽略费用，若在可信 Mark `M` 下平掉多仓 `x` ETH，成交价为 `F`，权益相对按 Mark 估值会变化 `x×(F−M)`，MM 则减少 `x×M×5%`；极差成交价可能让 `E−MM` 缓冲反而下降。因此应有可验证的限价／滑点保护或事先版本化的应急执行策略；无可信价格界限时，不能宣称普通市价 Reduce-Only 必然减险，可以拒绝／排队或交给受控处置流程。本例费用为零，不在推导中悄悄加入真实费率。

## 第 6 层：服务积压时怎样背压而不是丢事件或重复扩大风险？

**面试官：** 风险分片处理速度落后输入 30 秒，队列还在增长。丢掉旧 Mark、只读最新状态或继续消费订单准入请求，哪种方式安全？

**面试者：** 先区分可合并的行情快照与不可丢的业务事实。若 Mark 流协议明确允许提交前合并中间行情，要保留时间、质量和覆盖水位，并证明不会漏掉必须处理的阈值触发；例如 90→84→90，直接只保留最后的 90 会丢掉逐仓在 84 的处置证据。若每版有效 Mark 都承诺风险检查，就不能这样合并；已提交的行情／风险触发日志也不能事后重写。成交、账本、划转、订单预留及参数生效事件不能因为队列大就丢弃。只读“最新”也不能跳过必须应用的成交序号。

当延迟或积压超过预设门槛，立即停止新开／加仓准入，进行背压、限流或拒绝，并暴露分片水位、最老事件年龄、缺口和未决预留。消费者重试采用退避与有界并发，避免故障时重试风暴进一步拖慢状态推进。已提交成交及结果 Outbox 持续可靠处理；未知提交不释放额度。恢复速度提升后仍按序追赶，不能以跳过日志换取队列变短。

## 第 7 层：怎样暴露降级状态，避免下游继续把旧结果当成“安全”？

**面试官：** 风险服务返回上一次成功的 `HEALTHY` 结果，但其输入比当前成交和价格落后。下游只看布尔状态，仍可能放行新单。接口应怎样表达降级？

**面试者：** 风险结果除了 `status`，应携带 `decision_id`、输入摘要、账本／仓位／订单／价格／参数版本、结果生成时间、风险池应用水位、价格新鲜度和可执行能力状态。对过期或不完整结果，返回显式 `DEGRADED`、`UNKNOWN` 或拒绝原因，不把旧 `HEALTHY` 伪装成当前裁决。准入端要求结果满足策略规定的最低版本和新鲜度，否则按限制状态处理。

监控应关注水位差、最老未处理事件、缺号、价格年龄、错误与溢出次数、epoch 拒写、未知命令和未决预留；告警应能区分风险输入降级、计算不可用、下游执行不可用和恢复中。对 Mark=84 的逐仓触发，通知延迟不能改写风险事实；通知发出也不能标记平仓完成。状态变更、拒绝原因和人工介入都要可审计。

## 第 8 层：服务恢复后，满足哪些门禁才能重新开放风险扩张？

**面试官：** 队列已清空，服务健康检查也通过。你会立刻恢复开仓吗？请给出从恢复中到正常的门禁，并说明如何避免开关反复抖动。

**面试者：** 不会只凭进程健康或队列为零重新开放。恢复门禁至少包括：

1. **所有权与存储：** 当前 owner epoch 有效，旧主写入已被 fencing，状态存储和日志可持久提交。
2. **连续性：** 从有效快照到当前应用水位无未解释序号缺口，账本、仓位、订单和成交输入已追平所需版本。
3. **业务对账：** 每笔 reservation 的已批准量可分解为已消耗、已释放和未决量；成交／撤单竞态、未完成划转及 Outbox 均有权威归属，池外资金未误计入逐仓。
4. **参数与价格：** 生效中的规则版本完整一致；价格源达到配置的新鲜度和质量要求；scale、溢出和计算校验无未决错误。
5. **结果验证：** 用恢复后的同一输入重算风险结果，摘要与权威重放／独立核对一致；逐仓与 Cross 的教学案例仍分别得到 84 时 `E=4` 与 `E=24`。
6. **渐进放量：** 先进入受限观察或小范围准入，监控错误率、版本延迟和风险结果差异；所有条件持续满足配置的稳定窗口后，才按策略解除限制。门槛和稳定时间应版本化，不临时凭感觉填写。

任何门禁失败就留在恢复中／降级状态，告警并给出具体原因；不自动放宽。逐步开放可以降低恢复后异常扩散的范围，但它不能替代逐项对账和风险计算正确性证明。门禁全部通过仅表示准入条件恢复，不表示已有风险已经自动处置或订单执行已经成功。

## 本题收束

### 已经讲透的机制

- 输入不可信时先冻结风险扩张；健康状态不能由陈旧结果或空字段推断。
- 降级矩阵区分开仓、撤单、Reduce-Only、追加抵押、提现、模式迁移和已提交事实结转。
- 减仓只有在权威仓位、并发额度和撮合边界共同保证不反向时才安全；撤单确认前不能释放预留。
- 积压时对不同事件按语义背压；成交、账本和划转不能因队列压力被静默丢弃。
- 恢复必须通过所有权、连续性、对账、参数、价格、计算和渐进放量等明确门禁。
- 降级中的风险处置是裁决与执行两种状态，不能把触发等同成交。

### 最容易答错的边界

1. 把“最后一个有效 Mark”说成当前有效 Mark，或选择对自己有利的冲突来源。
2. 将所有操作一概关闭而忽略安全撤单／严格减仓，或反过来笼统声称只减仓都放行。
3. 把 Reduce-Only 当作请求字段，不在并发和成交边界防止仓位翻向。
4. 撤单请求超时就释放预留；对积压中的成交和账本事实直接丢弃。
5. 服务健康检查通过或队列归零后立即放开扩仓，不对账输入版本和未决义务。
6. 用降级标记掩盖过期的 `HEALTHY`，或将 `E <= MM` 说成平仓已成功。

### 验证反例

令 1 ETH 多仓的仓位版本停在旧值，两个并发 Reduce-Only 卖单各成交 0.7 ETH；若没有共享减仓额度约束，最终会反向开出 0.4 ETH 空仓。令 84 的 Mark 已陈旧而风险服务继续返回旧 `HEALTHY` 并允许加仓；这证明状态新鲜度门禁失效。令撤单响应丢失时提前释放 reservation，随后发现撤单前已有成交；该账户可能同时把成交风险和已释放额度计算成双重可用。

最后令服务积压已清零，但参数版本仍不一致或成交序号有缺口；若系统重新允许开仓，恢复门禁只检查了可用性，没有证明风险状态完整。正确的降级应限制新风险、保留已承诺义务并让每个恢复条件都可审计。本篇矩阵与门禁为教学设计要求，不表示任何真实系统已经采用或通过测试。
