# 大问题 4：接管后怎样撤单，并承接撤单前后的在途成交？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、权益、MM | 保证金是承担亏损的资金；权益包含浮动盈亏；MM 是继续持仓的最低要求。 | 本例 Mark 84 时权益 4、MM 为 4.2，严格不足才触发强平复核。 |
| 逐仓、强平 | 逐仓限定风险核算范围；强平是风险不足时系统组织的被动减仓处置。 | 触发不是已经成交，也不意味着一定全平或亏光，更不是逐仓绝对损失封顶。 |
| Mark、实际成交价 | 前者用于估值，后者是市场真正执行的价格。 | 不能按 Mark 84 假定所有旧订单及强平单都在 84 成交。 |
| 接管、风险模式 | 接管确定系统裁决者，风险模式约束接下来允许哪些操作。 | 不能让已有订单自动消失；也不是把真实资产所有权交给执行器。 |
| 增险订单、减仓订单 | 前者可能扩大风险，后者用于减少现有仓位。 | 多头增险买单会加仓；卖单超平则通常来自并发减仓或重复执行。 |
| 撤单封口 | 关闭订单剩余成交资格，并确定此前到底成交了多少。 | 不只是发出撤单请求，还要接住封口前的全部经济影响。 |
| order_id、cancel_id | 订单和撤单动作各自的稳定身份。 | 超时后按原身份查询，不另造身份掩盖原动作状态。 |
| cancel_requested、ACK | 前者是已经请求撤单；ACK 是确认回报，具体含义由接口契约定义。 | “请求已收”不能当作“余量已全部取消”。 |
| 订单终态、remaining_qty | 终态表示订单不再继续变化；remaining_qty 是剩余未成交数量。 | 终态要同时解释累计成交和真正取消的余量。 |
| cancel_seq、成交前沿 | 撤单生效的执行序号，以及它所界定的完整成交边界。 | 证明哪些成交已经确定、此订单此后不会再新增有效成交。 |
| cum_filled_qty、last_fill_seq | 累计成交数量，以及最后一笔成交的执行序号。 | 不能只看 canceled 标签，还要追齐这些数量与序号。 |
| fill、fill_id | 真实成交及其稳定识别号。 | 封口前合法 fill 即使晚到，也要按身份只结转一次。 |
| applied_fill_seq、消费水位 | 本地已经处理到的成交位置。 | 与执行前沿比较，可以发现还缺哪些成交，而非见去重成功就认为完整。 |
| 在途义务、待结转 | 已确定或仍可能发生的责任，以及尚未正式应用的成交。 | 已成交 0.4、只入账 0.3，就还有 0.1 ETH 必须追齐。 |
| 仓位投影、有效暴露 | 投影是已处理事件形成的仓位视图；有效暴露还要考虑未应用义务。 | 页面 q=1 不一定仍能卖出 1，不能忽略撮合端已发生的减仓。 |
| UNKNOWN、NOT_FOUND | UNKNOWN 是结果未知；NOT_FOUND 是此次查询没有找到。 | 查询落后时两者都不能证明未执行，更不能成为盲发新单的理由。 |
| 预留、释放 | 预留为订单占住额度；释放让不再需要的额度重新可用。 | 只能按确认取消的余量及权威结转契约释放，不能直接清零。 |
| Reduce-Only、过平 | Reduce-Only 只减现仓；过平是减超过零、反而开出相反方向仓位。 | 用户和强平卖单必须在最终执行点共享同一可减数量约束。 |
| owner epoch、权威序 | epoch 是负责人权限代次；权威序是执行端裁决先后的记录。 | 旧代次不能发新命令，但不能据此拒绝其先前合法成交。 |
| 恢复门槛、未决义务闭合 | 恢复要同时满足风险数值要求和经济责任查清。 | 本文教学条件为 E>=MM 且执行余量、未决义务关闭；生产缓冲需另行明示。 |
| 退避重试、隔离核验 | 退避是逐渐放慢查询；隔离是暂停使用冲突事实并核对来源。 | 重试耗尽不是订单终态，序号冲突也不能靠静默丢消息解决。 |

## 把整篇文章压缩成一个故事

小林用保证金持有多头，价格下跌使权益，也就是现金加浮动盈亏，低于维持要求。系统接管强平后发现，他还有旧挂单。接管只是改变系统权限，不会替市场撤单，所以协调者必须先关闭不允许的订单余量，查清撤单前已经发生的成交。

一张旧减仓单的撤单回报先到了，显示累计成交 0.4 ETH，但本地账本只处理了 0.3。余下 0.1 是待结转义务，不会因为界面显示“已撤单”而消失。系统按执行序号追齐成交，只释放确定取消部分的预留，再用更新后的仓位与资金评估风险，不能仍照旧仓位发满量卖单。

如果撤单或查询超时，UNKNOWN 只表示结果未知，必须按原身份继续查并保留约束。用户同时减仓时，最终执行点还要限制所有卖单累计不超过现有可减仓位，避免减成空头。Mark 不是成交价，发送撤单不是封口完成，强平触发也不是清仓完成；只有余单、在途成交和账务责任可解释，后续执行才有可靠起点。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖强平接管后关闭增险订单、确认撤单权威边界、追平撤单前已产生或仍可能产生的成交，并把未决义务带入强平执行。重点不是“发了撤单”而是确定订单执行序列截至哪里、尚有哪些成交可能改变经济状态，以及在风险收敛前如何维持约束。case/owner epoch 的竞争规则见大问题 3；强平 action 的后续策略见大问题 5、6。

**必要前提：** 沿用[总览共同基线](README.md#11-讨论基线)：链下托管线性 USDC 永续，单一逐仓多头 `q=1 ETH、P₀=100、C=20、r=5%`，忽略费用与资金费，严格 `E<MM` 触发。Mark 84 下 `E=4、MM=4.2`。Mark 是风险估值，不是成交价格。用户减仓、强平成交和撤单竞态中的合法确定成交都要按权威事实结转；撤单只影响订单未成交剩余量。

本题共 10 层，沿“为何封口→撤单事实→成交前沿→在途结转→未知订单→保护接续→Reduce-Only→并发超平→完成条件→故障验证”推进。

## 第 1 层：接管后为什么不能直接发强平卖单？

**面试官：** 风险单元已进入强平模式，为什么还要先处理已有订单？直接发一笔 Reduce-Only 卖单是否不够？

**面试者：** 因为已有订单和在途成交可能继续改变仓位、可减数量和资金状态。接管只限制新的业务权限，不会让已受理订单从撮合中消失。如果系统不知道哪些增险意图仍能成交、撤单前有多少 fill 已确定，就可能基于旧风险快照判断暴露和预留。

封口的目标是关闭不再允许的订单资格并收齐其成交前沿，而不是假定一旦发送撤单就立即没有风险。协调者按稳定订单身份撤销仍有效的剩余量，保留执行端已受理状态和未知结果；达到可解释的撤单与成交水位后，强平执行再基于更新后的经济状态继续。

## 第 2 层：撤单请求、撤单成功和订单终态有何区别？

**面试官：** 撤单 API 返回成功，是否说明订单已彻底取消、之后不可能再有成交？

**面试者：** 不一定。“请求已接收”只代表撤单命令进入处理；“撤单权威确认”要说明订单执行序列在哪个位置接受了撤销；订单终态还需给出该位置前的累计成交及实际取消剩余量。系统需要区分 `cancel_requested、cancel_accepted/canceled、filled_qty、remaining_qty`，而不是用一个布尔值 `canceled=true` 覆盖时序。

若撤单前订单已全部成交，撤单可能返回已完成或不可撤；若部分成交，撤单只封住余量，已成交部分仍是有效事实。调用超时既不证明撤单未受理，也不证明订单仍活动，必须用原 `cancel_id/order_id` 查询权威状态。接口响应词语必须与执行端真实语义一致。

## 第 3 层：什么是撤单的权威成交前沿？

**面试官：** 如何描述撤单确认时“之前的成交都已确定，之后不再新增”的边界？

**面试者：** 执行端需要提供可比较的订单事件序号或等价的终止游标。撤单终态可表达 `cancel_seq`、该序号前的 `cum_filled_qty`、`last_fill_seq` 和被取消的剩余量；其契约是所有不晚于封口位置的撮合结果都已确定，且该订单之后不会再产生新的有效 fill。字段名可以不同，关键是边界可验证且不会因消费延迟而倒退。

风险协调者再比较这个执行前沿与自己已处理的 fill 水位。如果撤单终态已给出累计量 0.4 ETH，但本地只消费到 0.3 ETH，就存在 0.1 ETH 待结转义务；不能因为订单已显示 canceled 就把剩余经济影响当零。若执行端只返回状态不提供前沿或可查询的成交账本，系统就无法证明撤单封口完成，只能维持受限状态并继续对账或升级处理。

## 第 4 层：撤单前成交已确定但尚未入账，仓位按哪一个数算？

**面试官：** 撤单确认显示已有 0.4 ETH 成交，但持仓服务仍显示 `q=1`。这笔成交没有结转前，强平可以继续按 1 ETH 发卖单吗？

**面试者：** 不能简单把仓位投影中的 `q=1` 当作没有变化。已确定的 0.4 ETH fill 是不可撤销的经济义务，应按其稳定 `fill_id` 结转；在结转完成前，风险计算必须把它表示为待应用变化，避免再次卖出已在撮合端成交的数量。可用“已结转仓位＋执行端确定但未结转的 fill”推导保守的有效暴露，但必须明确不同价格和成交方向，不能只做净数量猜测。

成交发生后，持仓和账本要由各自权威结转边界更新；强平协调者不直接把仓位扣掉 0.4。若结转失败，记录保持待处理并继续风险约束，恢复时重放同一 fill 身份。当前 case 或当前 owner epoch 已变化，都不是拒绝该合法成交的依据；有效性取决于执行来源、成交序号和稳定身份。

## 第 5 层：订单查询超时或返回 UNKNOWN，怎样继续封口？

**面试官：** 撤单调用超时，订单查询也暂时返回 UNKNOWN。为了赶紧减险，能否把订单按未执行处理并另发平仓单？

**面试者：** 不能把超时或一次 `NOT_FOUND` 当作未执行证明。查询可能落后于撮合受理水位，撤单可能已生效但回报未到，也可能已经部分成交。UNKNOWN 期间保留最大合理的未决暴露与必要的抵押／订单约束，使用原 `order_id/cancel_id` 查询，不另造一个逻辑撤单或放松保护。

恢复要判断查询水位覆盖到了什么：执行端若确认订单从未受理且查询达到相应受理水位，可以按策略结束原意图；若部分成交或已撤销，则按累计成交前沿结转并更新剩余量；若仍未知，就保持受限并重试查询或转人工处理。有限退避可以保护依赖系统，但重试次数耗尽不是经济终态，不能据此释放预留或宣称撤单完成。

## 第 6 层：撤单与迟到 fill 并发，什么事实优先？

**面试官：** 本地先收到 cancel ACK，随后才收到一笔时间戳更早的 fill。应该以消息到达顺序还是事件时间处理？

**面试者：** 以执行端权威序号和撤单契约定义的成交前沿处理，不以网络到达顺序或客户端时间戳处理。若 fill 在封口序号之前且来源权威，它必须结转；cancel ACK 只是可能先到达的终态通知，不能抹掉其前沿内的成交。若某 fill 声称晚于已封口序号仍属于同一订单，则要检查执行端契约、序号冲突或重复身份，并隔离核验，而不是擅自按当前 case 状态丢弃。

一致性消费可以短暂保留 `cancel_terminal_seq` 和 `applied_fill_seq` 两个水位；只有成交来源确认该订单前沿完整，且前沿内的 fill 均已入结转或明确待结转，才算完成封口。消息队列可以重投，消费端按 fill 身份去重并校验序号连续性；但去重不能替代检查缺失区间，尤其不能把“暂时没收到”解释成“没有成交”。

## 第 7 层：在途义务没闭合前，强平风险保护怎样接续？

**面试官：** 撤单已确认，但有成交尚在账务结转中。系统是否可以解除用户交易限制，或把订单预留全部释放？

**面试者：** 不可以只根据撤单状态解除保护。强平接管期间，风险模式要持续阻止不允许的新增长风险；已成交但未结转的义务要纳入暴露估计，已撤剩余量对应的预留只能按订单／账本权威结转契约释放。撤单成功、资金释放、成交结转和风险恢复是不同边界，不能由强平协调者把它们压成一个 `cancel_done`。

若系统能按权威成交前沿证明所有成交已结转，剩余量为零且没有其他未决执行义务，再以新仓位和账本版本复核恢复。教学门槛是 `E>=MM` 且关闭执行余量与未决义务；生产额外缓冲必须显式配置。否则保护继续，即使页面已经显示“撤单成功”或“强平订单已发”。

## 第 8 层：Reduce-Only 怎样在最终执行点防止过平？

**面试官：** 强平和用户减仓可能同时影响仓位。只在发单前检查卖出数量不超过当前多仓，能保证不会卖成空头吗？

**面试者：** 不够，仓位可能在检查和成交之间被用户平掉或被另一笔强平成交改变。Reduce-Only 必须在最终撮合／执行裁决点按当前可减仓位限制实际可成交数量，累计填单不能超过当时仍可减少的方向性暴露；剩余量应拒绝或取消，不能越过零仓位反向开仓。并发的其他 Reduce-Only 订单也必须共享这个最终约束，而不能各自基于同一旧仓位通过全量检查。

增险买单对已有多仓通常会增加 `q`，它本身不是独立的“卖单超平”原因；它会改变风险暴露和撤单前后的有效状态，但超平主要来自用户减仓与重复／并发平仓执行没有在最终边界串行裁决。若产品允许接管后用户继续减仓，应让两类减仓竞争同一个剩余可减数量；强平服务本地的目标仓位快照不能代替撮合端约束。

## 第 9 层：哪些条件同时满足，才算撤单封口和义务交接完成？

**面试官：** 你需要给强平执行器一个明确的“可以继续”的信号。这个信号应建立在哪些事实之上？

**面试者：** 信号应引用风险单元和 case、受影响的订单集合、每个订单的权威撤单终态及成交前沿、截至前沿的累计 fill 数量、fill 已结转与待结转清单、剩余订单量，以及当前仓位／账本版本和公共经济序。它表达的是“哪些命令入口已封住、哪些经济义务仍在途、基于何种有效暴露可以继续”，不是简单的布尔 `all_canceled`。

若仍有确定 fill 未结转，执行器可以在产品定义的保守约束下并行推进部分流程，但不能把未结转量忽略；如果无法证明剩余风险边界，就保持暂停或采用明确受限的 Reduce-Only 规则。只有当前沿闭合、未决义务已结转或纳入持续保护、仓位与账本可解释，才允许下一阶段使用新的复核许可。该门槛不要求停止系统所有活动，而是要求风险计算不再遗漏任何已受理经济事实。

## 第 10 层：怎样验证封口机制经得住故障与乱序？

**面试官：** 你会设计哪些反例来检查撤单和在途义务的闭环？如何识别实现只是依赖回报顺序碰巧正确？

**面试者：** 至少检查撤单请求超时但已部分成交、cancel ACK 先于前沿内 fill 到达、成交结转失败后协调者重启、旧 epoch 订单在新 owner 接管后产生已确认 fill、用户与强平同时减仓、同一 fill 重投、成交序号缺口，以及执行端查询水位落后。每个用例都检查仓位数量守恒、现金只结转一次、订单剩余量不被误释放、旧 owner 无法提交新命令、合法历史 fill 不被拒绝。

特别要看最终 Reduce-Only 边界：让两笔各自看似合法的卖单并发争用同一份多仓，再让用户先完成减仓，观察累计成交是否仍可能越过零。若只能靠 API 到达顺序、消息时间戳或“通常 ACK 先来”解释正确性，方案没有定义权威前沿。以上是设计验证清单，不声称执行过工程测试或故障注入。

## 本题收束

- **讲透的机制：** 撤单要有权威终态和成交前沿；前沿内的确定成交必须结转；UNKNOWN 保持受限；在途义务闭合前继续风险保护；Reduce-Only 在最终撮合点限制实际数量。
- **最容易答错的边界：** 超时不等于未执行；撤单 ACK 不等于没有迟到 fill；epoch 过期或 case 关闭不能否定权威成交；增险买单本身不是卖单超平的原因。
- **检验反例：** 旧 epoch 订单已被受理，撤单 ACK 先到，之后收到封口序号之前的 0.2 ETH 确定 fill。系统必须结转这 0.2 ETH 并更新有效仓位，不能以“已撤单”或“旧 owner”拒绝，也不能再按旧仓位重复卖出。
