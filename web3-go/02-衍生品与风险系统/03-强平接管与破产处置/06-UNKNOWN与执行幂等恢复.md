# 大问题 6：强平超时、部分成交或执行器崩溃后怎样恢复？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、权益 E、MM | 保证金承担亏损；权益还包含浮动盈亏；MM 是继续持仓的最低要求。 | 本例现金 20，Mark 84 时权益 4、MM 为 4.2，严格 E<MM 才触发复核。 |
| 强平、部分成交 | 强平是系统组织被动减仓；部分成交是计划只执行了一部分。 | 不必然全平或亏光，系统不能按计划提前减少权威仓位。 |
| Mark、真实成交 | Mark 是风险估值，真实成交才是市场已经发生的结果。 | 本例 0.5 ETH@84 必须是权威成交，不能从 Mark 84 推定出来。 |
| RPC、ACK、HTTP 成功 | RPC 是远程调用；ACK 是回报；HTTP 成功是某个接口层的成功响应。 | 都要看具体契约，不能自动等同于市场已成交或资金已入账。 |
| UNKNOWN | 调用方尚不知道执行端最终做了什么。 | 可能未受理、部分成交或全成；不是确定失败，不能盲发新单。 |
| NOT_FOUND | 当前查询未找到该身份的记录。 | 可能有复制、索引或队列延迟，不是从未执行的证明。 |
| case_id | 一整次风险处置的案件身份。 | 一个案件可有多个动作，不用它替代逐笔执行或成交身份。 |
| action_id、step_id | action_id 标识逻辑执行意图，step_id 标识可审计的步骤或版本。 | 重试保持原身份；新步骤必须有业务依据，不能只是超时后换号。 |
| fill_id、经济效果 | fill_id 标识逐笔真实成交；经济效果是它引起的仓位与资金变化。 | 同一成交在其对应账务腿上只应用一次。 |
| 幂等、重复投递 | 幂等是同一业务请求重复到达仍只产生原效果；重复投递是消息再次到达。 | 只说“会重试”不够，执行端和结转端都要认稳定身份。 |
| 规范化载荷、摘要 | 将请求按固定格式整理，再生成识别其内容的摘要。 | 数量、方向、价格保护、期限等都要绑定；同 ID 不同内容必须拒绝或隔离。 |
| 查重先于资格检查 | 先判断是在查询旧结果，还是创建新业务。 | 案件已关闭也要能返回已有动作结果，不能因此漏掉已成交义务。 |
| 查询水位、排空证明 | 查询水位说明查询覆盖到哪里；排空证明说明相关在途请求已核清。 | 只有可信契约和覆盖范围足够，才能判断是否确实未受理。 |
| 原身份重发、替代动作 | 前者重试同一个意图；后者创建新的经济意图。 | 原身份重发需执行端支持幂等且载荷相同；替代前先关旧资格并对账。 |
| cum_filled、增量 fill | cum_filled 是累计成交总量，增量 fill 是一笔新增成交。 | 累计 0.3 变 0.5 不是又成交 0.5，逐笔结转仍须取得真实 fill。 |
| 单调序号、源水位 | 随执行进度推进的顺序标识，以及成交源已覆盖的位置。 | 用来发现累计量倒退、序号缺口或成交明细不一致。 |
| owner_epoch、fencing | 当前负责人权限代次，以及拒绝旧负责人新命令的围栏。 | 不能用新代次否定旧动作已产生的合法成交。 |
| 检查点、重放 | 检查点保存处理位置；重放从持久记录恢复处理。 | 本地检查点不是执行事实源，落后可补，异常领先要暂停核验。 |
| Outbox、Inbox | Outbox 保存待发意图；Inbox 保存收到的回报身份与处理记录。 | 能帮助可靠交付和恢复，但 Outbox 已发送不证明外部已成交。 |
| exactly-once、单飞 | exactly-once 指只产生一次业务效果；单飞限制同一范围同时只有一个在途意图。 | 外部不支持稳定身份时不能空口保证只执行一次，只能采取更保守约束。 |
| 恢复门槛、在途义务 | 恢复门槛决定能否解保护；在途义务是尚未核清或结转的责任。 | 教学要求 E>=MM 且余单和相关义务核清，服务重启成功不等于业务恢复完成。 |

## 把整篇文章压缩成一个故事

小林的保证金用来承担多头亏损，价格下跌后，权益连同浮动盈亏已低于维持要求。系统复核后发出动作 A，准备减仓 0.5 ETH。远程调用超时，执行器没有收到回报，但这只说明结果未知：市场可能没接单，也可能已经成交。Mark 只是估值价，不能代替成交证据。

恢复进程先读取动作 A 的持久身份和原载荷，再按这个身份查执行端。一次 NOT_FOUND 可能只是查询落后，不能改名动作 B 再卖一笔。若执行端支持稳定身份幂等，可以按相同身份和内容恢复原动作；不支持时就必须保持更保守的限制。假如查到 A 已成交 0.3，就先取得逐笔成交并结转，而不是再按旧仓位补卖完整 0.5。

后来累计回报变为 0.5，它表示总量达到 0.5，不是又新增 0.5。新负责人也不能以旧权限代次为由丢弃这些合法成交。只有旧余单关闭、成交水位追齐、账本更新后，才能重算是否还要继续减仓。恢复的目标是接续原事实，不是靠多发订单赌成功；强平也不必然清空仓位或耗尽保证金。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题承接强平动作已生成并可能发往执行端之后的结果不确定窗口，讨论如何区分重复投递与新意图、查询原事实、恢复累计成交并安全替代旧动作。它不重讲部分强平策略或账务原子结转；核心是 UNKNOWN 期间不制造第二份经济意图，且已确定成交不能因旧 epoch 失效而丢弃。

**必要前提：** 使用专题基线：`q=1 ETH、P₀=100、C=20、MMR=5%` 的线性逐仓多头，忽略费用和资金费；`E=C+q(M−P₀)、MM=qM×5%`，严格 `E<MM` 才触发，等值不触发。教学恢复为 `E>=MM` 且余单和在途义务核清。Mark 84 时 `E=4、MM=4.2`；若实际 `0.5 ETH@84`，现金 12、余仓 0.5。执行超时不改变这些权威业务事实。

## 第 1 层：什么情况下执行结果应进入 UNKNOWN？

**面试官：** 强平 action 已发到执行端，但 RPC 超时，没有收到 ACK。你会把 action 标成失败并再创建一笔吗？

**面试者：** 不会。超时只说明调用方没有在期限内拿到结果，不能说明执行端没收到命令。执行端可能已受理、已部分成交、已完全成交，也可能根本没接收；在事实查清前应进入 `UNKNOWN`，保留原 action 身份和风险保护，避免创建第二个经济意图。

状态上至少要分清“已持久创建”“发送中”“结果未知”“执行端已终态”“成交已结转”。HTTP 返回成功通常只证明某个传输边界收到请求，不自动等于成交；网络错误也不能当未执行证明。协调器的重试策略应从同一稳定身份查询和恢复，而不是用超时次数推导业务结论。

## 第 2 层：case、action、step 和 fill 身份分别解决什么问题？

**面试官：** 你说要保留原 action 身份。为什么还需要 case、step 和 fill 多层身份？

**面试者：** `case_id` 表示一个风险处置生命周期，`action_id` 表示该 case 中一个逻辑执行意图，`step_id` 表示这个意图的一个可审计执行步骤或版本，`fill_id` 标识执行端确定的一笔成交事实。它们不能互相替代：一个 case 可含多个动作，一个动作可分多笔 fill，而一个 fill 只应在其对应的业务账务腿上产生一次经济效果。

身份应由持久化的业务意图稳定生成，并且跨重试、进程重启和网络切换保持不变。新 step 不是超时后的“换个 ID 再试”，而应在旧动作已关闭执行资格、累计结果已恢复之后，依据新风险状态创建。这样审计时可以从案例追到每次动作、每笔 fill 与对应的经济结转。

## 第 3 层：同一身份带着不同请求载荷重试怎么办？

**面试官：** 客户端用同一 `action_id` 重试，但第二次把数量从 0.5 改成 0.8，或修改了价格保护。服务端应当以哪次请求为准？

**面试者：** 同一身份必须绑定规范化载荷，至少覆盖风险单元、方向、数量上限、Reduce-Only、价格保护、有效期、规则版本及必要的执行参数。服务端对规范化载荷计算摘要并持久保存；同一身份和同一摘要是重复请求，可以返回原受理结果，同一身份但摘要不同则是身份冲突，必须拒绝或隔离，不能覆盖原动作。

规范化要消除无意义差异，例如字段默认值、精度格式和枚举编码；但不能把会改变经济含义的字段省略。若确实需要调整数量或价格边界，应先关闭旧动作的后续执行资格、核对其累计 fills 和在途状态，再创建新的 step/action 身份并引用前序动作。原地改写载荷会让恢复者无法判断执行端究竟收到哪个版本。

## 第 4 层：恢复时为什么重复查询必须先于当前状态检查？

**面试官：** worker 重启后先看到 case 已进入 `RECOVERING` 或稍后被标成 `CLOSED`。对原来的 action 重试请求，应该先拒绝当前终态，还是查询已有结果？

**面试者：** 必须先按稳定身份查已有 action 记录和结果，再决定这次调用是返回原结果、继续恢复还是拒绝新意图。若先检查“当前 case 不允许发单”就直接拒绝，客户端可能收不到已经确定成交的原始结果，恢复任务也可能漏掉结转义务；若无视终态重新发单，则会制造重复减仓。

一个可靠顺序是：规范化请求并验证身份载荷；查找该身份的持久记录；命中且载荷一致时返回或推进原 action 的恢复；命中但载荷冲突时隔离；只有身份不存在时，才检查当前 case/epoch 是否允许创建新动作，并在同一持久边界登记。这个顺序让“幂等重放”和“新业务资格”成为两条清楚的路径。

## 第 5 层：执行端查询返回 NOT_FOUND，能否证明命令没执行？

**面试官：** 按原 `action_id` 查询得到 `NOT_FOUND`。这是否意味着可以释放所有保护并重新发一笔新订单？

**面试者：** 不能仅凭一次 `NOT_FOUND` 得出未执行。查询存储可能有复制延迟、索引滞后或有限保留期；请求也可能仍在网络、队列或执行端内部排队。要知道该查询覆盖到哪个接收水位、是否包含在途请求，以及执行端是否保证身份唯一查询。缺少这些契约时，空查询结果不是“从未执行”的证据。

安全恢复要么继续查询并等待可证明的权威水位，要么用同一稳定 action 身份在执行端执行幂等再提交，使执行端返回原状态或首次受理结果。若执行端不支持稳定身份、也不能给出排空或拒绝证明，就只能采用更保守的单飞、仓位上限、持续保护或人工仲裁；不能宣称此类接口提供 exactly-once。

## 第 6 层：什么时候可以安全重发原动作，什么时候不能创建新意图？

**面试官：** 旧 action 超时，查询又暂时无结果。重发原身份和新建 action 有什么根本区别？

**面试者：** 原身份重发是在重试同一逻辑意图，前提是执行端能按身份去重并返回既有状态；相同身份不得改变载荷。新建 action 则是新的经济意图，可能与旧动作同时执行，只有原动作已确定终态、剩余量已经对账且当前风险快照仍授权时才允许创建。

例如 `action-A` 目标卖 0.5 ETH，超时后以同一 `action-A` 查询或幂等重发，是在恢复同一个动作；把它改成 `action-B` 卖 0.5 ETH，则不能作为“重试”。如果 `action-A` 实际已成交 0.3 ETH，新的 0.5 ETH 意图可能导致总减仓 0.8 ETH，甚至超过当前仓位。替代动作前必须关闭旧资格并从权威累计成交得到剩余敞口。

## 第 7 层：累计回报和增量 fill 怎样区分？

**面试官：** 执行端先回报累计成交 0.3 ETH，之后恢复查询又返回累计 0.5 ETH。若都按新增成交处理，会发生什么？

**面试者：** 把累计值误认为增量会重复结转。`cum_filled=0.3` 和后来的 `cum_filled=0.5` 表示累计进度从 0.3 增到 0.5，差额最多是 0.2，而不是再入账 0.5；实际结转仍应由每个稳定 `fill_id` 的逐笔事实驱动，不能只靠累计数字合成成交身份。

回报协议要明确消息是快照还是增量，并包含单调序号或源水位。增量 fill 按 `fill_id` 去重；累计快照按 action 序号和已应用累计量校验，只推进观察到的进度，不重复创建 ledger entry。若累计量倒退、超出目标上限、与 fill 列表不符或序号缺口未补齐，应暂停该动作并拉取权威成交明细，而不是猜测差额。

## 第 8 层：owner epoch 过期后，旧执行者的结果如何处理？

**面试官：** 新 owner 已接管并把 `owner_epoch` 推进，旧 worker 随后收到一个成交回报。因为 epoch 旧，这笔 fill 是否应该丢弃？

**面试者：** 不能丢弃已由执行端确定的成交事实。epoch 用于阻止旧执行者提交新的有效命令或覆盖当前案例状态，不用于否定在其失效前已经发生的市场成交。恢复者要验证该 fill 属于原 action、身份和载荷一致、成交源权威，然后按原 fill 身份进入结转；它可能改变当前仓位和风险结论。

新 owner 应先关闭旧 epoch 的未来执行资格，并查询所有旧动作和在途订单。已确定成交照常结转，未决动作继续 UNKNOWN，已确认取消的剩余量才算关闭。随后基于结转后的经济版本重新评估；不能因新 owner 的计划覆盖掉旧 epoch 的真实 fill，也不能让旧 worker 借迟到回报的名义发出新的订单。

## 第 9 层：崩溃恢复如何覆盖检查点与执行端之间的窗口？

**面试官：** 协调器写入 action 后崩溃，或者执行端已成交但本地检查点尚未推进。恢复流程依赖哪些持久事实？

**面试者：** 检查点只能帮助定位进度，不能作为执行事实的唯一来源。恢复者需要读取持久 case、action/step 状态、owner epoch、已知 fill 水位，以及执行端按稳定身份查询得到的权威状态；之后逐项补齐缺失回报，并通过成交结转的幂等边界应用经济变化。检查点落后可以重放，领先但与权威源不符则需暂停并审计。

在同一数据库内可把 action 状态更新、接收回报的 Inbox 记录和推进恢复检查点放在一个事务中；跨外部执行端的发送通常不能与本地事务原子提交，可用持久 Outbox 重发同一身份。Outbox 解决“本地意图可继续发送”，不证明外部执行成功；外部状态仍须查询、对账。每一步都应能从稳定身份和水位重新计算，不依赖某个进程内存。

## 第 10 层：恢复流程何时可以创建替代动作并解除保护？

**面试官：** 原动作查到部分成交，余单被取消。此时是否可以立即发替代动作或恢复普通交易？

**面试者：** 先把确定成交按 fill 身份完成结转，取得新的仓位与账本版本；核实原订单余量已权威关闭、未收到的成交回报已追到执行端水位，并确认没有其他有效 action。然后重算风险，只有新快照仍需处置时才基于新授权创建替代动作。若余单或成交水位仍不确定，维持保护并继续恢复。

解除保护还要满足产品的恢复门槛和经济义务闭合。教学规则是 `E>=MM` 且余单、在途及已确定未结转义务核清；具体产品若有安全缓冲，要明确标成生产策略变体。case 的展示状态、worker 健康或一次空查询都不能代替这些条件。相反，若原 action 的 fill 已确定但 ledger 尚未追上，case 可以保持执行保护，却必须继续履行该成交结转。

## 本题收束

- **机制：** 稳定 `case/action/step/fill` 身份、规范载荷与冲突隔离；恢复先查原身份，UNKNOWN 不等于失败；累计快照和增量 fill 分别处理；替代动作须关闭旧资格，旧 epoch 的确定成交仍要结转。
- **易错边界：** `NOT_FOUND` 不是未执行证明；同一身份不能换载荷；重发原身份和新建意图不是一回事；累计成交回报不能当作新的增量 fill；epoch fencing 不可抹除已成交事实。
- **反例：** `action-A` 卖 0.5 ETH 已成交 0.3，但 ACK 丢失。恢复者因查询暂时 `NOT_FOUND` 新建 `action-B` 再卖 0.5，之后 `action-A` 的 0.3 成交回报到达，最终总卖出 0.8。正确路径是先查询并收敛 `action-A`，逐笔结转其 fill，再据新仓位决定是否创建替代动作。
