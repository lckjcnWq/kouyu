# 大问题 2：强平触发如何复核，如何应对过期或失真的风险输入？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、逐仓 | 保证金是承担仓位亏损的资金；逐仓按指定仓位及其资金范围核算风险。 | 本例起初放入 20 USDC，不把逐仓解释为任何情况下都不会产生额外缺口。 |
| 线性 USDC 永续 | 没有固定到期日、盈亏按价格差线性计算并以 USDC 结算的合约。 | 这是本文公式的产品范围，不覆盖所有合约类型。 |
| q、P₀、C | 分别是仓位数量、入场价、逐仓现金。 | 初值为 1 ETH、100 USDC/ETH、20 USDC；入账后 C 才能改变。 |
| Mark、M | 用于风险估值的标记价。 | 可用于判断要不要强平，但不是执行端承诺的成交价。 |
| U、E | U 是未平仓的浮动盈亏；E 是现金加浮盈亏后的权益。 | 本例 U=q×(M−P₀)，E=C+U，不能把现金余额单独当权益。 |
| MM、r | MM 是最低维持要求；r 是计算它所用的维持保证金率。 | 本例 r=5%，MM=q×M×r。 |
| E<MM、E>=MM | 前者是本文触发复核的严格条件；后者是教学恢复门槛的数值部分。 | 等值不触发；恢复还要求执行余量、未决义务关闭，不偷偷加生产缓冲。 |
| 候选、decision | 候选是待确认的风险案件；decision 是此次评估结论。 | 不能凭候选直接长期授权减仓。 |
| 风险快照 | 把某次风险计算使用的数据和证据一起保存。 | 不只是一个“需要强平”的布尔值，要能重建判断过程。 |
| position_version、ledger_version | 仓位记录和资金账本各自的修订号。 | 分别最新并不代表它们已经包含同一批经济变化。 |
| public_economic_seq | 同一风险单元中，已提交经济事件的公共顺序位置。 | 用来对齐成交、补抵押、费用等变化，不是行情序号。 |
| 公共水位、投影 | 水位表示处理到哪条事件；投影是由事件生成的状态视图。 | 仓位到 105、账本到 103 时不能硬拼快照，应等待或标为不完整。 |
| price_id、price_source_seq | 一条价格证据的身份和其来源的顺序号。 | 避免用不同来源或倒退的价格冒充同一份有效证据。 |
| price_time、price_quality | 价格的时间信息和质量状态。 | 刚收到不代表足够新、更不代表可信，要按规则检查陈旧、偏离和源异常。 |
| 补抵押、请求受理 | 补抵押是向风险单元增加资金；受理只是系统接受了请求。 | 2 USDC 真正入账后才能按本例计入权益，不能提前算上未决入金。 |
| review_id、执行许可 | 复核通过后形成的有限执行凭据。 | 绑定案例、经济版本、价格、规则、时效和最大动作范围。 |
| 最终命令受理点 | 真正决定命令能不能进入执行的边界。 | 必须阻断已失效许可，不能只信前面服务的缓存。 |
| rule_version、buffer | rule_version 标识一版规则；buffer 是产品额外要求的安全余量。 | 本文不把生产缓冲混入教学门槛，改变门槛就要明示新规则。 |
| 定点数、舍入 | 按约定的小数单位计算，并规定如何处理多余小数。 | 保证严格比较的含义稳定，不自行编造币种精度或舍入位数。 |
| tick、背压、channel | tick 是行情刷新；背压是处理端来不及时让上游感知；channel 是 Go 进程内传递任务的通道。 | 可合并价格重算唤醒，但不能静默丢掉成交和入账事实。 |
| 持久日志、重放 | 将事件可靠保存，恢复时按记录重新处理。 | 重算任务可以重复，经济事实必须保留身份和消费水位。 |

## 把整篇文章压缩成一个故事

小林用 20 USDC 保证金持有入场价 100 的 1 ETH 多头。价格下跌会消耗权益，也就是现金加浮动盈亏后还能承担风险的金额。Mark 到 84 时，本例权益为 4，维持要求为 4.2，系统生成强平候选；候选只是需要复核的风险信号，尚未卖出任何仓位。

候选刚生成，小林又补入 2 USDC。如果账本已正式入账，其他条件不变时权益变为 6，旧候选就不能继续放行。风险服务必须对齐仓位、账本的经济水位，同时确认价格没有陈旧或失真，再按新版本复核。只收到补款申请，不能提前把钱算进来；只拿两个服务各自的最新值，也可能拼出从未真实存在的状态。

复核通过后，系统签发有版本、期限和数量范围的许可，执行端再检查一次，过期就重评。Mark 不保证成交价，触发也不等于清仓。行情拥堵时可以少做重复估值，却不能丢掉成交、补款等经济事件；恢复保护还要查清余单和未决义务，而非只看权益回到门槛上方。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖风险服务从读取经济状态、构造触发候选到执行前复核并签发有限许可的过程。重点是快照必须能说明它依据哪份仓位与账本、哪个公共经济序、哪条价格证据和哪版规则；候选不能直接变成长期有效的执行权。唯一活动案例与执行者仲裁属于大问题 3，撤单及在途订单闭合属于大问题 4。

**必要前提：** 沿用[总览共同基线](README.md#11-讨论基线)：链下托管、线性 USDC 永续、单一逐仓多头，`q=1 ETH、P₀=100 USDC/ETH、C=20 USDC、r=5%`，忽略手续费、资金费和额外现金变化。`U=q×(M−P₀)`，`E=C+U`，`MM=q×M×5%`，严格 `E<MM` 才进入复核。Mark 90 时 `E=10、MM=4.5` 不触发；Mark 84 时 `E=4、MM=4.2` 触发复核。恢复条件按教学门槛显式要求 `E>=MM`，并且执行余量与未决义务均已关闭；生产缓冲属于另一个需明示参数的规则版本。

本题共 8 层，沿“计算口径→快照绑定→一致读取→补抵押竞争→价格质量→执行许可→精度与边界→事件调度与事实保全”推进。

## 第 1 层：风险评估到底要比较什么？

**面试官：** 给定一个逐仓多头和 Mark Price，风险引擎如何判断强平触发？哪些数字只是风险信号，哪些是实际经济结果？

**面试者：** 在本基线里，我先取同一风险单元的仓位数量 `q`、入场成本 `P₀`、逐仓现金 `C` 和合格 Mark `M`，算 `U=q×(M−P₀)`、`E=C+U`、`MM=q×M×r`，然后严格按 `E<MM` 产生复核候选。等值不触发，不能把实现时的 `<=` 当成无关紧要的代码细节。

Mark 是估值输入，不是强平成交报价。Mark 84 下的 `E=4、MM=4.2` 只证明按指定口径该风险单元越过维持线；它既不改 `q` 或 `C`，也不承诺以 84 成交。实际仓位和现金只能由权威成交及其结转改变。

## 第 2 层：有了比较结果，怎样让快照可解释？

**面试官：** 你说候选不能直接执行。候选至少绑定哪些字段，才能在稍后被审计并判断是否仍有效？

**面试者：** 我会保存 `risk_unit_id、position_version、ledger_version、public_economic_seq、price_id、price_source_seq、price_time、price_quality、rule_version`，以及当次计算出的 `q、P₀、C、M、U、E、MM、decision`。每个版本或序号都要有明确的生产者和比较语义；否则一串数字只是日志文本，无法证明快照中各字段来自同一可解释时点。

其中 `public_economic_seq` 是该风险单元所有影响经济判断的已提交变化的公共顺序水位，例如仓位成交结转、抵押入账、费用或资金费入账。它不是行情序号，也不替代仓位和账本版本；它帮助发现“两个本地版本看起来没变，但中间有经济事件遗漏”的情况。价格侧则单独保留来源序号、时间和质量状态，不能把更新时间新误认为价格正确。

## 第 3 层：仓位与账本来自不同服务，怎样避免拼出不存在的状态？

**面试官：** 仓位服务刚发布版本 17，账本服务返回版本 42。它们各自都最新，怎样证明合并出来的风险快照没有漏掉一笔成交或资金变化？

**面试者：** 需要可比较的经济边界，而不是分别取两个“最新值”。一种做法是两类状态都携带同一风险单元的已应用经济序，风险服务只组合覆盖到同一公共水位的仓位和账本；若仓位已应用到序号 105、账本只到 103，就等待账本追平或把评估标为不完整，不能用 105 的仓位搭配 103 的现金得出执行许可。

也可以由统一的风险快照构建器消费有序经济事件，并记录每个来源的版本与已应用位置。无论部署形态如何，快照必须区分“事件已产生”“仓位投影已应用”“账本投影已应用”；读副本延迟、跨服务消息滞后或重建期间的缺口都应让复核重试或暂停，而不是暗中回退到较旧缓存。

## 第 4 层：快照生成后用户补抵押，旧候选怎么办？

**面试官：** Mark 84 时形成候选后，用户补入 2 USDC。请求已经返回成功，但风险引擎尚未消费到账本事件，旧候选还能不能执行？

**面试者：** 先问补抵押的权威状态。如果账本已提交，新现金为 22、其他条件不变时 `E=6、MM=4.2`，旧候选必须失效并按新账本版本重算；如果只是请求受理、入账仍未确定，不能把请求成功当作现金已生效。待决的入金义务要保留其身份与状态，但是否可计入可用权益由产品明确规则决定，本教学基线不预先把未入账请求算作抵押。

执行资格需要绑定候选时的账本版本和公共经济序。补抵押事件若先于执行许可提交，旧许可的版本条件就不匹配；若两者竞争，则必须由同一权威序列或等价的提交比较决定先后。风险服务看到旧消息、收到重复事件或消费落后时，可以重算和去重，但不能让一条迟到的旧候选覆盖较新的经济状态。

## 第 5 层：Mark 更新快，不代表价格证据一定有效

**面试官：** 快照版本匹配，但价格源有分歧、时间戳倒退或短时断流。你如何判断是触发、等待，还是降级？

**面试者：** 价格证据需要显式携带来源、序号、事件时间、接收时间、质量状态和适用的价格规则版本。评估器依据规则版本定义的有效性检查决定使用、拒绝或暂停；单纯“最近收到”不能覆盖来源序号倒退、超出有效期、异常偏离或聚合质量不满足门槛等情况。

如果教学规则没有定义价格降级路径，我会选择暂停签发新执行许可并保留候选，而不臆造一个备用价格或偷偷放宽阈值。产品若要使用备用指数、保护带或延迟策略，应把来源选择和切换条件版本化，使同一 `price_id` 的含义稳定；旧证据恢复有效也要重新走复核，不能直接续用已过期许可。

## 第 6 层：复核通过后，许可怎样绑定最终执行边界？

**面试官：** 复核刚返回“仍触发”，接着仓位又发生变化。风险服务如何避免把已经过时的判断交给执行端？

**面试者：** 复核结果应产生一个有范围、有版本、有时效的 `review_id` 或许可对象，至少绑定 `case_id、position_version、ledger_version、public_economic_seq、price_id、rule_version`，并说明它授权的是哪种受限动作与最大数量。它不是“这个账户可以任意卖出”的永久标志，也不能由调用方把其中版本替换成更新值。

最终命令受理点必须校验许可仍处于有效状态，并确认许可绑定的风险状态没有被后续经济变化取代。若订单系统与风险状态无法原子提交，就用明确的执行前检查／风险资格状态转移形成可裁决边界；竞态失败时重评，不以风险服务缓存或进程内锁做最终裁决。谁拥有接管权及多执行者如何 fencing 留给下一母题深入。

## 第 7 层：精度与恢复门槛怎样避免边界漂移？

**面试官：** 金额和数量有小数精度，计算后可能恰好落在 `E=MM` 附近；部分成交后风险变好，是否就能立刻解除强平？

**面试者：** 关键金额应用定点数或有明确定义的十进制精度，统一币种最小单位、合约数量步长、价格精度和舍入方向，并把这些规则纳入 `rule_version`。不能依赖二进制浮点的近似比较，也不能在权益、保证金两侧采取不同舍入方式后仍宣称实现了严格 `E<MM`。本题忽略舍入尾数；生产精度必须由合约规格确定，不能在此补造具体位数。

恢复判断在教学基线中显式采用 `E>=MM`，且执行余量和未决义务全部关闭。只剩 `0.5 ETH` 不等于风险已解除：按 `0.5 ETH@84` 实际结转后现金 12、剩余成本 50，Mark 84 下 `E=4、MM=2.1`；仍需检查执行端是否有余单或未确定订单义务。生产系统可以设 `E>=MM+buffer` 或其他安全余量，但那是明确改变的规则参数，必须进入规则版本和解释记录，不能把缓冲偷偷混进“等于即可恢复”。

## 第 8 层：行情事件很多，怎样合并计算又不丢经济事实？

**面试官：** 同一风险单元每秒有大量 Mark 更新，事件调度开始背压。可以把排队中的事件只保留最后一条吗？崩溃重启后怎样确认没漏掉补抵押或成交？

**面试者：** 对可重算的价格刷新，可以按风险单元合并待评估任务，只保留当前有效的最新价格证据，避免每个中间 tick 都重复做完整计算；但价格源序号倒退、质量变化和规则切换仍需可见。合并的是计算唤醒，不是把经济变化从账本中删除。

仓位、账本、成交结转等经济事实要由持久事件日志或可恢复的权威状态保留，并有各消费者已应用的水位。Go 的有界 channel 可以让生产者感知背压，worker 按 `risk_unit_id` 串行合并重新评估任务；channel 满时不能静默丢弃经济事件，应让持久层留存并在恢复时按水位补读。评估任务可重复计算，经济事实必须可重放和核对；手工检查的价值是验证最新状态与事件水位一致，而不是声称队列永不积压。

## 本题收束

- **讲透的机制：** 风险快照绑定仓位、账本、公共经济序、价格证据与规则版本；复核与最终执行许可分层；调度可以合并重算，但经济事实不能丢。
- **最容易答错的边界：** “最新”不代表跨服务一致；Mark 不等于成交价；补抵押请求受理不等于账本入账；教学恢复条件不包含未声明的生产缓冲。
- **检验反例：** Mark 84 生成候选后，2 USDC 已先于命令受理入账。若执行端仍凭旧账本版本许可卖出，方案就没有真正把风险判断绑定到执行边界。
