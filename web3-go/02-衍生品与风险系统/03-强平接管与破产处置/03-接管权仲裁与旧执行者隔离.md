# 大问题 3：多个执行者竞争时，谁拥有有效接管权？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、权益 E | 保证金是承担亏损的资金；权益还要加上仓位的浮动盈亏。 | 本例现金 20、浮亏 16 时权益为 4，不是账面现金仍有 20 就安全。 |
| 逐仓风险单元 | 按指定仓位和资金范围独立核算的风险对象。 | 使用 risk_unit_id 识别；不因此承诺逐仓在任何情况下都没有额外缺口。 |
| MM、强平复核 | MM 是继续持仓的最低要求；不足时需要复核是否启动被动减仓。 | 本例 MM=4.2、E=4，严格 E<MM 触发，尚不代表已经成交。 |
| Mark | 判断风险时采用的标记价。 | 本例为 84，不是撮合端承诺的实际成交价。 |
| 扫描器、Orchestrator | 扫描器发现风险任务；Orchestrator 是协调后续处置的服务。 | 可以有多个实例发现同一风险，但不能各自建立独立卖出流程。 |
| active case、case_id | active case 是仍在处理的案件，case_id 是案件的稳定身份。 | 同一风险单元同时最多有一个活动案例。 |
| owner、owner_id | 当前有权继续裁决该案处置动作的执行者及其身份。 | 这是系统权限归属，不是用户资金或仓位的真实所有权。 |
| owner_epoch | 每次授予或转移执行权时递增的代次。 | epoch 8 生效后，epoch 7 不能再凭旧资格提交新动作。 |
| case_version、条件更新 | 案件修订号，以及只有预期版本匹配才允许提交的写法。 | 两个执行者都想接管时，由持久提交结果裁决谁成功。 |
| CAS、compare-and-swap | 先比较记录是否仍为预期值，匹配才替换。 | 可实现接管竞争，但只保护数据库还不够，下游受理也要校验。 |
| lease、租约 | 一段时间内暂时持有权限的约定。 | 到期可启动接管，却不能证明旧进程已停止运行。 |
| fencing token、围栏 | 下游用来拒绝过期执行者新命令的凭据。 | owner_epoch 要检查到真正能产生经济动作的受理点。 |
| action_id、持久意图 | 给一次具体动作稳定编号，并先可靠记录准备做什么。 | 重启后查原动作，不因换 owner 就换号再发一单。 |
| 已受理订单 | 执行端已接下、可能仍能成交的业务承诺。 | 换 epoch 不会自动撤掉它，新 owner 必须查询和接续。 |
| fill_id、accepted_epoch | 成交身份，以及产生该成交的订单当初被受理时的代次。 | 用来核验来源；不能只因 accepted_epoch 旧就拒绝合法成交。 |
| execution_seq、受理水位 | 执行事件的权威顺序号，以及已确认覆盖到的位置。 | 判断命令是在围栏前还是后受理，不看网络消息谁先到。 |
| 经济结转、投影 | 结转是正式应用成交的仓位和资金变化；投影是处理后的状态视图。 | 迟到 fill 仍需只结转一次，视图没更新不代表成交没发生。 |
| 未决义务、UNKNOWN | 未决义务是尚未完全核清的责任；UNKNOWN 是结果未知。 | 缺回报时保留约束并查询，不能盲发新单，也不能假定旧单消失。 |
| 复核许可、经济版本 | 有限处置资格，以及它所依据的仓位、账本和公共经济序。 | 接管提交前若补抵押或减仓已生效，应让旧许可失效并重评。 |
| Reduce-Only、权威排序 | Reduce-Only 只允许减现仓；权威排序裁决用户操作和接管谁先提交。 | 是否允许用户继续减仓由产品规定，最终执行不能越零开反向仓。 |
| context、进程内锁 | context 可通知 Go 任务停止；进程内锁协调同一进程的并发。 | 都不能替代跨实例的持久仲裁和下游围栏。 |

## 把整篇文章压缩成一个故事

小林拿保证金持有逐仓多头，价格下跌后，现金加浮动盈亏得到的权益低于维持要求，系统需要复核并可能强平。两台扫描器同时发现风险，执行者甲、乙都想处理。此时既没有真实成交，也不能让两人各卖一遍；系统先按同一风险单元建立唯一活动案件，再由持久条件更新选出当前负责人。

甲拿到第 7 代权限后发出订单，随后失联。乙接管并推进到第 8 代，执行端从此拒绝甲新发的旧代次命令。但甲先前已被受理的订单不会凭空消失。乙要查询原动作，继续追踪余单和成交；若结果未知，就保留保护，而不是换个动作号重发。

稍后，第 7 代订单的一笔合法成交才到达。乙必须核验并按成交身份只结转一次，不能以甲已过期为由拒绝。小林同时补款或减仓，也要按权威提交顺序重评风险。这里交接的是系统裁决权，不是资产所有权；Mark 只是估值价，接管成功也不等于强平成交成功。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题位于候选复核到强平接管之间，解决同一风险单元上唯一活动案例、执行者所有权、旧 owner 隔离，以及用户操作和强平提交的排序。核心区分是 epoch fencing 阻止旧执行者发出新的有效命令，但不能抹掉已被执行端权威确定的历史成交。撤单的具体序号与在途义务由大问题 4 深入。

**必要前提：** 沿用[总览共同基线](README.md#11-讨论基线)：链下托管、线性 USDC 永续、单一逐仓多头，`q=1 ETH、P₀=100 USDC/ETH、C=20 USDC、r=5%`，忽略费用与资金费，严格 `E<MM` 触发。Mark 84 时 `E=4、MM=4.2`。风险复核已产生绑定仓位、账本、公共经济序、价格和规则版本的有限许可；执行成交仍由执行端确定，仓位与现金仍由经济结转权威域更新。

本题共 10 层，沿“唯一活动 case→owner epoch→持久竞争→执行端 fencing→已受理命令→旧 epoch 成交事实→复核提交窗口→用户排序→恢复接管→安全收束”推进。

## 第 1 层：多个扫描器同时发现风险，谁可以创建处置案例？

**面试官：** 两个扫描器同时发现同一个逐仓仓位满足强平条件。怎样避免创建两个活动案例并分别卖出？

**面试者：** 我会以稳定的 `risk_unit_id` 标识风险单元，并在持久状态中保证同一时刻至多一个活动处置案例。扫描器可以重复发现和投递候选，但只有通过权威状态迁移赢得案例创建或复用已有活动案例的一方，才能继续申请接管；候选本身不持有下单权。

案例至少记录 `case_id、risk_unit_id、status、trigger_snapshot_id、owner_id、owner_epoch、case_version`。活动唯一性要由持久存储可执行的条件约束实现，例如风险单元主记录上的条件更新或唯一活动键，而不是靠两个 Go 实例碰巧共享一把内存锁。输掉竞争的一方读取并跟随既有 case，不另建一条并行强平链。

## 第 2 层：唯一案例仍可能有两个 owner，怎样选出当前持有者？

**面试官：** case 唯一了，但两个 Orchestrator 都读到 `status=REVIEWED`，先后尝试接管。owner 的交接需要什么持久事实？

**面试者：** 每次所有权授予或转移都推进单调递增的 `owner_epoch`，并在持久提交时比较预期 `case_version/owner_epoch`。只有成功提交新 epoch 的实例才成为当前 owner；败方不能仅凭本地缓存、锁竞争曾经胜出或租约尚未超时继续发有效命令。

epoch 是 fencing token，不是单纯的进程编号。每条新执行命令都带 `case_id、owner_epoch、action_id`，权威命令受理点比较它是否仍是当前 epoch，并记录已受理的命令身份。租约可帮助判断何时启动接管，但租约过期本身不能证明旧进程已停止，也不能替代受理点的 epoch 校验。

## 第 3 层：只在数据库校验 epoch 够不够？

**面试官：** 案例更新使用 compare-and-swap 拒绝旧 epoch 写入，是否已经彻底隔离旧执行者？

**面试者：** 只有当每一个能产生新经济动作的最终边界都执行 fencing 才够。若旧 owner 绕过案例数据库，直接把订单提交给撮合，或者某个下游只验证账户、不验证 epoch，旧执行者仍能造成真实市场效果。因而 fencing 必须延伸到新命令的最终受理方，必要时也延伸到账户风险模式变更、订单准入和后续动作授权。

不同存储不一定能共享一个大事务，但要明确哪些边界由同一顺序裁决，哪些用可验证的版本条件连接。旧 owner 即使拿着有效期较长的复核快照，也只能在当前 case epoch 仍被权威承认、风险许可仍匹配时创建新动作。服务发现、Go context 取消和租约都只能加速旧实例停止，不能作为正确性的最终保证。

## 第 4 层：epoch 变化时，之前已受理的订单会怎样？

**面试官：** owner epoch 从 7 推进到 8。epoch 7 已提交且被执行端受理的订单，是否会自动失效或取消？

**面试者：** 不会。epoch fencing 控制的是新命令能否被接受，不会反向删除已经受理的业务义务。旧 epoch 的订单可能仍挂在市场、正在撮合、等待取消，或已经产生待结转成交；新 owner 必须先查询和接续这些既存事实，再决定是否创建下一步动作。

执行端要区分“旧 owner 新提交的命令”与“旧 owner 在 fencing 生效前已受理的订单”。前者应拒绝；后者按照订单自身的状态机和权威执行序继续处理，直到成交、取消或其他明确终态。若系统支持按 epoch 撤销旧授权，也必须明确它影响的是尚未受理的命令还是已受理订单，不能把一个 token 失效表述成市场订单瞬间消失。

## 第 5 层：旧 epoch 的成交晚到，新 owner 能不能拒绝？

**面试官：** epoch 8 已接管，随后收到一笔由 epoch 7 订单产生、且执行端已权威确定的成交。当前 case 和仓位都变了，是否可以因为 epoch 过期而拒绝这笔 fill？

**面试者：** 不能拒绝合法确定的历史事实。成交记录应携带稳定 `fill_id、order_id、action_id、accepted_epoch、execution_seq、qty、price` 等身份和来源证据。账务和仓位结转依据执行端权威成交顺序验证该 fill，再以稳定身份只应用一次；当前 owner epoch 用来限制新动作，不用来否定已经发生的经济义务。

若旧 fill 尚未进入仓位／账本投影，新 owner 必须把它列为待结转义务，并在风险评估中保留相应的不确定暴露或保护约束。遇到同一 fill 身份载荷冲突，要隔离并查权威来源；不能为了“当前状态不允许”而静默丢弃，也不能因重投再记一次。经济结转拒绝的应是无效来源或冲突事实，而不是它来自旧 epoch。

## 第 6 层：复核通过到接管提交之间，状态又变了怎么办？

**面试官：** 风险服务读到 `E=4、MM=4.2` 并批准接管，但在 case 提交前用户已经成功减仓或补抵押。如何关闭这个时间窗口？

**面试者：** 复核许可应绑定具体 `position_version、ledger_version、public_economic_seq、price_id、rule_version`。接管提交时比较这些版本与当前风险单元的权威经济位置；若已经推进，就不能拿旧许可直接进入可执行状态，而要回到风险复核。这样把“复核通过”和“获得可下单权”作为两个状态，不把两者之间的空隙交给缓存一致性碰运气。

如果用户命令和接管命令由不同服务提交，就需要一个明确的风险单元权威顺序或等价的条件竞争机制。先提交的命令改变后续裁决条件，后提交的一方按新版本继续或失败重试。不要用跨多个服务的长事务锁住行情、用户接口和撮合；也不要因分布式事务难做就省略提交时的版本校验。

## 第 7 层：用户减仓与接管同时提交，怎样保证结果唯一？

**面试官：** 用户发起 Reduce-Only 平仓的同时，强平协调者也准备提交接管。谁先谁后由什么决定？

**面试者：** 必须把二者放进可解释的权威顺序。可以由风险单元协调者为相关命令分配提交序号，也可以由共享持久记录上的条件状态迁移裁决；不要求所有 API 请求都经过一个全局线程，但必须保证同一风险单元的“用户命令资格”和“处置模式切换”不会各自成功而互不知晓。

若用户命令先被权威受理并成交，强平复核需读取新仓位和未结成交义务；若接管先提交，普通新增风险命令被拒，用户 Reduce-Only 能否继续则由产品规则与最终执行约束决定。对两边返回超时的请求，查询原身份的权威结果，不以客户端响应到达顺序推断业务顺序。用户权限策略和精确撮合裁决不在本题扩写，但不能留成“并发时看谁快”。

## 第 8 层：新 owner 接管时，如何接续旧 owner 留下的中间状态？

**面试官：** owner 7 在写入 action 意图后崩溃，执行端可能已受理，但 case 中还没有订单回报。owner 8 如何恢复而不重复下单？

**面试者：** 新 owner 先从持久 case 与命令意图读出 `action_id、owner_epoch、受理状态`，再查询执行端对该稳定身份的受理、订单和成交状态。若旧命令已受理，就接续其状态；若权威确认未受理，才在当前许可仍有效时决定重提或生成后续动作；若结果未知，保留约束并继续查询，不能把缺少回报等同于未发生。

创建 action 意图与对外发送之间要有可恢复的关联，保证重启后知道“准备发送的是哪个动作”，但不要把队列里的发送记录当成成交事实。稳定 action 身份解决同一业务意图的重试关联，epoch 解决谁可以创建新意图；它们是不同维度，不能用每次接管换新 action_id 来掩盖旧动作的未知状态。

## 第 9 层：epoch fencing 与历史结转发生竞态，边界在哪里？

**面试官：** 一个旧 owner 的命令恰好与 epoch 8 的接管并发；另一笔 epoch 7 fill 又在接管后才被消费。最终系统怎样区分应拒绝的操作和必须接受的事实？

**面试者：** 对“新命令”，以执行端权威受理顺序为准：若它在 epoch 8 生效后才到达且没有当前授权，拒绝；若受理发生在 epoch 8 前，则它已经成为需接续的订单义务。接管事务必须能确定它读取或封住了哪个受理水位，或者让新 owner 在持有执行权前查询并纳入该水位之后的所有旧动作。

对“确定成交事实”，以执行端权威 execution sequence/fill 身份为准，不能再用当前 epoch 判定发生与否。若成交序号晚于接管时读到的水位，它仍要进入经济结转，并触发对当前仓位和风险状态的重评。fencing 是阻断旧命令写入，不是历史过滤器；把两者混为一谈会产生账实不符。

## 第 10 层：如何证明系统没有双主，也没有因接管漏掉旧义务？

**面试官：** 新 owner 已成功推进 epoch。你用哪些可核验事实判断旧执行者已被隔离、旧受理订单与成交也都被接续？

**面试者：** 第一，持久 case 中只有一个当前 `owner_epoch` 和一个活动 case；第二，执行端拒绝低 epoch 的新命令，并能列出已受理但未终结的旧 epoch 订单；第三，成交源的已消费水位与仓位／账本已应用水位可以比较，所有已确定 fill 均结转或处于明确待结转状态。只有这三类事实同时可见，才能说“旧 owner 不再产生新业务写入，历史义务仍在收敛”。

可设计故障注入检查旧实例在 lease 过期后继续发命令、接管提交和用户减仓同时发生、旧 epoch fill 在新 epoch 后到达等反例。期望是旧新命令只有一个受理顺序、合法 fill 不丢、风险约束不因接管而释放。这里给出的是验证设计，不表示已运行并通过并发或工程测试。

## 本题收束

- **讲透的机制：** 一个风险单元只有一个活动 case；持久单调 epoch fencing 新命令；已受理订单与确定成交作为旧义务由新 owner 接续。
- **最容易答错的边界：** 租约过期不等于旧主停止；epoch 变更不取消已受理订单；旧 epoch 是命令权限信息，不是拒绝合法成交事实的理由。
- **检验反例：** epoch 8 生效后，执行端确认一笔 epoch 7 的成交已在先前受理订单中发生。正确系统要结转该 fill、重评仓位，同时拒绝 epoch 7 此后才提交的新命令。
