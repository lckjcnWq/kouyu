# 大问题 7：强平成交、仓位、费用和账务何时共同完成？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、逐仓现金 C | 为指定仓位承担亏损的资金。 | 初始为 20 USDC；逐仓限定风险范围，不代表任何情形都不会欠账。 |
| U、权益 E、MM | U 是浮动盈亏；E 是现金加 U；MM 是继续持仓的最低要求。 | 主例 Mark 84 时 E=4、MM=4.2，严格 E<MM 才启动复核。 |
| Mark、强平成交 | Mark 是风险估值；成交是市场真正执行的数量和价格。 | 触发不等于成交，不能直接以 Mark 替代执行价格。 |
| q、P₀、成本 | q 是仓位数量，P₀ 是入场价；这里成本是剩余仓位对应的入场金额。 | 平半仓后 q=0.5、成本 50，不表示每 ETH 入场价降成 50。 |
| 已实现损益、未实现盈亏 | 前者来自已平仓部分，后者来自仍持有部分的估值。 | 0.5 ETH@84 实现亏损 8，剩余仓位在 Mark 84 下仍浮亏 8。 |
| fill、结转 | fill 是确定成交；结转是正式应用对应仓位、损益、费用和资金变化。 | 收到回报或页面更新，不等于所有经济变化共同完成。 |
| FILL_CONFIRMED、SETTLEMENT_PENDING | 分别是成交已确定、结转尚在进行。 | 账务故障不能取消已发生的成交，要持续保护并恢复结转。 |
| SETTLED、RISK_REVIEWED | 分别表示该笔已完成结转、已用新经济状态复核风险。 | 一笔结转成功后，整个强平案件仍可能需要继续处置。 |
| venue、market、fill_id | 分别标识执行场所、市场和来源成交。 | 裸 fill_id 不一定在全平台、所有账户间唯一。 |
| account_leg_id、账户经济腿 | 对某个账户应承担的一份成交经济效果设置稳定身份。 | 按账户腿防重，避免重复入账，也避免误删其他账户的合法效果。 |
| 载荷冲突、隔离 | 同一身份却出现不同内容时，暂停应用并核查来源。 | 同账户腿数量或金额不同，不可覆盖原记录或当成普通重复。 |
| 复式账本、分录 | 按对应借贷关系记录资金责任的账本，以及其中的正式记录。 | 仓位变化、现金变化和损益费用要能对上，而不是只修改一个余额字段。 |
| 同 DB 事务、回滚 | 在同一数据库内共同提交或共同撤销的一组操作。 | Inbox、仓位、分录、现金和结转状态可在声明的事务范围内保持一致。 |
| 跨库、暂态 | 数据属于不同数据库时，短期可能只完成部分交付。 | 两个本地事务不是一个原子事务，必须显式保留待结转状态并可恢复。 |
| Inbox、唯一约束 | Inbox 记录收到的业务身份；唯一约束阻止同一身份重复生效。 | 防重记录要与经济变更一起提交，不能先记“已处理”却漏改账。 |
| Outbox、检查点 | Outbox 保存已提交的待发送结果；检查点保存处理到的位置。 | 提交后崩溃仍可补发，但检查点不能越过缺失事件。 |
| at-least-once、exactly-once | 前者允许消息至少送达一次、可能重复；后者在此强调经济效果只应用一次。 | 不声称网络只会发送一次，靠稳定身份和提交协议防止重复记账。 |
| 手续费、资金费、负余额 | 都会影响最终资金；负余额表示仍有未承担的责任。 | 必须核齐全部确定义务，不能只看当前余额，更不能把负数截零隐藏。 |
| 冲正、补记 | 用新的关联分录撤正旧错误或补齐遗漏。 | 费用迟到或修正要保留调整身份及历史凭证，不覆盖原账。 |
| case、owner_epoch | case 是处置案件；epoch 是执行负责人权限代次。 | 控制新动作资格，不能阻挡旧案件或旧代次合法成交继续入账。 |
| 恢复门槛、经济水位 | 恢复条件决定何时解保护；水位说明仓位、账本已处理到哪里。 | 本文教学要求 E>=MM 且余单与在途义务核清，不能只凭页面状态恢复。 |

## 把整篇文章压缩成一个故事

小林用 20 USDC 保证金持有入场价 100 的 1 ETH 多头。权益要把现金和浮动盈亏一起算，Mark 跌到 84 时只剩 4，低于本例维持要求 4.2，系统启动强平复核。随后市场真实成交 0.5 ETH@84；这不是因为 Mark 为 84 就推定成交，也不说明必须全平。

这半仓实现亏损 8，现金应从 20 变为 12，仓位从 1 变为 0.5，剩余入场成本为 50。结转服务为小林这一份经济效果设置稳定账户腿身份。若持仓和账本同库，就在同一事务内共同提交，失败一起回滚；若跨库，就保留明确的待结转状态并可靠补交。成交消息重来时返回原结果，不能再减一次仓、再扣一次钱。

即使案件已关闭或负责人已更换，迟到的合法成交仍要入账；手续费、资金费也不能遗漏或用余额截零掩盖。结转后，系统读取新版本检查风险和余单，Mark 仍为 84 时权益为 4、维持要求为 2.1。只有在途义务也核清，才可能解除保护，不能拿“收到回报”代替经济完成。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题深入执行端已经确定成交之后，如何把 fill 可靠地变成仓位、现金、费用和账户账本变化，并在崩溃、重复交付和强平状态迁移中保持经济一致。它不讨论如何选执行价格或估算最终坏账；重点是 fill 不能丢、不能重复，且结转完成之后必须重新判断风险恢复门槛。

**必要前提：** 沿用专题基线：链下托管线性 USDC 永续，单一逐仓多头 `q=1 ETH、P₀=100、C=20、MMR=5%`，主例忽略手续费、资金费。`U=q×(M−P₀)、E=C+U、MM=q×M×5%`，严格 `E<MM` 触发、等值不触发；教学恢复 `E>=MM` 且余单与在途义务核清。Mark 84 下 `E=4、MM=4.2`；成交 `0.5 ETH@84` 后现金 12、余仓 0.5、成本 50，Mark 84 下 `E=4、MM=2.1`。

## 第 1 层：执行端的成交回报为什么还不等于账户结转完成？

**面试官：** 撮合端回报强平订单已成交 0.5 ETH，用户查询页也显示仓位减少。能否把 case 直接标为结案？

**面试者：** 不能只凭回报已发送或页面投影。成交事实、持仓变化、现金损益、手续费分录和账户可查询状态，可能处在不同处理阶段。订单执行端确认某个 fill，只表示成交义务已确定；账户经济状态要等权威结转边界提交，并能证明仓位和对应账本变更一致。

我会区分 `FILL_CONFIRMED`、`SETTLEMENT_PENDING`、`SETTLED` 和 `RISK_REVIEWED` 等阶段。确定 fill 后不可因账务服务失败而撤销成交；应保留待结转义务和必要风险限制，以同一成交身份重试。结转完成也不自动代表强平 case 已解除，还要基于新经济版本核实余单、在途动作和恢复条件。

## 第 2 层：成交身份如何避免重复入账，又为什么不能只用平台裸 fill_id？

**面试官：** 成交消息可能被重复投递。用 `fill_id` 做全平台唯一键就足够了吗？

**面试者：** 应按账户经济腿去重，而不应假定某个执行场所的裸 `fill_id` 在全平台、所有账户和所有业务映射中永不重用。可用 `account_leg_id` 作为本账户待结转经济效果的稳定身份，并记录来源 `venue、market、fill_id、account_id、position_id、case_id、action_id` 等关联证据；同一 `account_leg_id` 重复投递返回原结转结果。

如果同一来源 fill 映射到不同账户或不同经济腿，必须由明确的分配记录表达，不能让全局 `fill_id` 去重误伤另一合法账户腿。反过来，同一账户腿若以不同载荷再次出现，也不是普通重复，而是身份冲突或数据损坏，应隔离处理。身份的唯一范围、保留期限和恢复查询能力都属于结转契约。

## 第 3 层：强平成交对持仓和账本的最小经济变化是什么？

**面试官：** 对 `0.5 ETH@84` 的多仓强平 fill，账户应发生哪些权威变化？

**面试者：** 在忽略费用的主例中，这笔 fill 实现损益 `0.5×(84−100)=-8 USDC`。结转后持仓由 `1 ETH、成本100` 变成 `0.5 ETH、成本50`，逐仓现金由 20 变成 12；这两组变化描述同一经济事实的持仓与资金视图，不能一边已提交而另一边永久缺失。

Fill 的数量、方向、价格、手续费和来源序号都要被校验，数量不得超过当前可平仓位及允许的在途约束。风险评估随后读取同一版本的持仓和现金，在 Mark 84 下得到剩余未实现亏损 -8、权益 4、维持保证金 2.1。实现盈亏与未实现盈亏的划分随仓位变化，但账户总经济结果应能与真实成交和抵押变动解释一致。

## 第 4 层：仓位和账本如何保证共同原子提交？

**面试官：** 更新仓位成功，但账本分录失败，或者反过来，系统怎样防止二者分叉？

**面试者：** 若仓位表、现金余额和复式账本在同一个数据库所有权边界内，可以在单个数据库事务中校验 `account_leg_id` Inbox、锁定或比较仓位版本、写入仓位新版本、写入平仓损益与费用分录、更新现金账户并标记结转完成。任一步失败都回滚，重试时由 Inbox 唯一键返回已提交结果，不重复改变经济状态。

如果仓位服务和账本服务分属不同数据库，就不能把两个本地事务说成一个原子事务。可以先在权威服务提交可恢复的结转事件和 Outbox，再由下游 Inbox 幂等消费，并通过检查点或对账收敛；中间期间要显式保留 `SETTLEMENT_PENDING`，查询投影不得冒充最终账务事实。方案改变了原子范围，必须说明暂态、补偿边界和何时允许解除风险限制。

## 第 5 层：Inbox、检查点和 Outbox 各自覆盖什么故障窗口？

**面试官：** 为什么需要 Inbox 和 Outbox？它们是否就能保证成交消息 exactly-once？

**面试者：** 在同一数据库事务内，Inbox 唯一记录与账户经济更新一起提交，可以使重复交付不重复产生账务效果；检查点记录已处理到的源序号，帮助重启后从缺口处继续；Outbox 则把本地已经提交的待发送结果与业务变更共同持久化，防止数据库提交后通知丢失。三者解决不同的恢复窗口，不把消息传输变成真正的 exactly-once。

可沿用相邻持仓／结算专题的同 DB 方案：对一个账户经济腿，Inbox 插入、仓位更新、账本分录、现金变更和结转状态在一个事务完成。若 Outbox 发往外部服务，重复发送仍会发生，下游必须用自己的稳定身份幂等；检查点也不得越过未补齐的序号缺口。保证的是 at-least-once 传输下经济效果只应用一次，不是网络只传一次。

## 第 6 层：费用、负余额和修正事件如何如实记账？

**面试官：** 强平费导致风险单元现金变负，或者手续费稍后才从执行端确定，能否先把余额截成零，待对账再补？

**面试者：** 不应截零。负余额是必须显式记录的账户经济结果和潜在缺口，不能通过余额下限隐藏责任。手续费、资金费或其他费用要按明确币种、金额、符号、来源及规则版本记入对应分录；如果费用尚未确定，就保留未结费用义务并避免过早宣布结转和风险处置全部完成。

费用晚到或费率修正应使用独立且稳定的调整身份，新增冲正／补记分录并引用原 fill 与原费用记录，不覆盖历史分录。交易本金、已实现损益和手续费分别归因，便于逐币对账。若产品允许负现金由保险或其他机制承担，那是后续独立经济事件；不能让成交结转服务悄悄把负数归零。

## 第 7 层：case 已关闭或 epoch 已变化，迟到的确定成交还能入账吗？

**面试官：** 强平 case 状态已变成 `CLOSED`，旧 owner epoch 的回报此时到达，报告一笔之前已确定的成交。结转入口应因终态或 epoch 旧而拒绝吗？

**面试者：** 不能让 case 状态机阻断已确定成交的经济结转。Case/epoch 门禁控制是否还可创建新处置动作；成交身份与权威来源证明经济事实。结转入口应先按账户腿身份查重并验证该 fill 真实属于原执行动作，随后完成其应有的仓位和账本变化，即使这会使 case 需要重新打开风险评估或进入结案修正。

旧 epoch 不能提交新订单，但它在有效期内已确定的 fill 仍需履行。迟到 fill 入账后要推进仓位／账本版本，撤销基于旧版本做出的恢复结论，并重新检查是否存在过平、费用欠项或额外缺口。若声称 case 永不回退，系统仍须有补充结案调整或重新评估的显式状态，不能丢弃经济事实来保住状态机的单调外观。

## 第 8 层：结转后怎样重算风险并判断完成？

**面试官：** 事务已提交，仓位与账本余额看起来一致。什么时候能解除强平保护？

**面试者：** 事务提交只完成这笔 fill 的本地经济变化。风险协调者要读取同一经济版本的仓位、现金、费用状态、有效 Mark 和规则，计算新的 `E` 与 `MM`，并核清所有强平余单、在途执行和确定未结转的成交。主例 `0.5 ETH@84` 结转后，Mark 84 下 `E=4、MM=2.1`，按教学门槛满足 `E>=MM`；只有余单及在途义务也核清，才可认定风险恢复。

生产系统可能要求超出维持保证金的恢复缓冲或持续多个风险周期，但这是改变了恢复条件的明确产品变体，应说明计算口径与版本。风险已恢复、仓位和账本已结转、case 已关闭、负余额／费用已处置是不同完成事实。查询页延迟可稍后追上，不应反过来成为权威结转提交的替代证据。

## 第 9 层：如何从崩溃和重复回报中验证结转协议成立？

**面试官：** 进程可能在事务提交后、回报发送前崩溃，也可能事务回滚但消息已经被消费者看到。怎样验证不会漏记或重记？

**面试者：** 对每个窗口都要明确数据库中可观察的事实和恢复动作。提交后发送前崩溃时，Inbox/结转状态已存在，Outbox 重发同一结转结果；提交回滚时，Inbox 和经济变更应一起不存在，重放原来源事件才能首次应用。若消息先于本地提交对外可见，就说明发布边界设计错误，不能靠下游重复去重弥补缺少的经济事实。

验证应覆盖同一 fill 重复交付、不同账户腿共享来源 fill、账本写失败、提交后宕机、Outbox 重发、序号乱序、费用迟到和旧 epoch 回报等反例。对账用于发现本地状态、执行源和账本之间的缺口，随后追加可审计修复；它不能代替事务内唯一约束、执行端数量限制和可靠恢复边界。这里描述的是应验证的性质，不声称已执行工程测试。

## 第 10 层：怎样定义“强平成交与账户结转完成”？

**面试官：** 如果 fill 已结转，但风险又因费用导致 `E<MM`，系统应将此次强平标成功还是失败？

**面试者：** 应把“动作结果”和“整个案例状态”分开。该 fill 的结转可以是成功且不可撤销的；强平 case 仍可能处于处置中，因为新的净经济状态仍未满足恢复门槛。不能为了让 case 成功而回滚一笔真实成交，也不能因为 case 尚未关闭就拒绝已确定 fill 的重复查询。

完整结转完成至少意味着：每笔确定成交在账户经济腿上只应用一次；持仓、损益、费用和现金账本在声明的原子边界内一致；未完成跨库交付有持久 Inbox/Outbox 和水位可恢复；新风险结论引用结转后的版本；余单和在途义务已闭合后才解除保护。若仍有负余额或未定费用，必须留在明确的待处理状态，而非用一个“强平成功”字段盖住它们。

## 本题收束

- **机制：** 以 `account_leg_id` 做账户经济腿去重，使用同 DB 事务原子提交 Inbox、仓位、分录、现金与检查点；跨库用持久 Outbox/Inbox 恢复；费用和负余额如实记账；结转后按新版本重评。
- **易错边界：** 全平台裸 `fill_id` 不是账户腿身份；消息 exactly-once 不等于经济 exactly-once；case 终态与旧 epoch 不能阻挡确定成交结转；费用迟到时不能把余额截零。
- **反例：** 仓位表先把 `q` 改成 0.5，随后账本写失败，进程又在重试时再次更新仓位。若无同事务 Inbox 和唯一经济腿，仓位可能变 0 或现金重复扣损；正确协议要么两者共同回滚，要么共同提交并让重复回报返回原结果。
