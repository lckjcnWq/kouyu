# 大问题 10：保险基金怎样按损失瀑布覆盖缺口且不超扣？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、权益、MM | 保证金承担亏损；权益含浮动盈亏；MM 是维持仓位所需最低金额。 | 本例 Mark 84 时权益 4、MM 为 4.2，严格不足才触发强平复核。 |
| Mark、成交价、强平 | Mark 用来估值，成交价来自实际执行，强平是系统组织的被动减仓。 | 触发不是全平、不是亏光，更不能把 Mark 84 当作最终成交价。 |
| 逐仓风险范围 | 规定哪些仓位和资金参与本次风险及亏损核算。 | 不擅自动用其他账户补洞，也不把逐仓说成绝对不会产生缺口。 |
| 最终缺口、loss_id | 最终缺口是核齐确定义务后的资金不足；loss_id 是这笔损失身份。 | 独立全平 1 ETH@78、无费用时缺口为 2，不叠加半仓路径。 |
| 最终定损、未结义务 | 定损要核齐成交、费用、资金费等；未结义务是仍待确认或履行的责任。 | 不能仅凭暂态负现金或当前余额就扣基金；真实移交固定源损失也须有明确边界。 |
| 保险基金、损失瀑布 | 基金按协议用有限资金承担损失；瀑布规定适用层级和顺序。 | 本例最多覆盖 1.5，不是无限兜底，也没有所有平台通用的赔付顺序。 |
| 总余额、可用余额、已预留 | 总余额是账面资源，可用余额扣除已承诺及规则限制，预留是尚未实际支出的占用。 | 多个 worker 不能各自拿同一笔缓存总余额重复花。 |
| policy_holdback、规则版本 | policy_holdback 是政策要求暂不动用的储备；版本标识具体分配规则。 | 会影响可分配额，不能暗中改变原始核定损失金额。 |
| allocation_id、分批分配 | 每次承担动作单独编号，同一损失可以合法分多次覆盖。 | L1 的 A1=1.0 与 A2=0.5 不同；A1 重试不得再次扣款。 |
| 幂等、身份冲突 | 同 ID 同内容重复只返回原结果；同 ID 不同内容必须查错。 | 防重复不能替代多个不同申请争用基金时的余额保护。 |
| 核定总额、remaining | 核定总额保留原损失及追加调整；remaining 是仍未承担部分。 | 新申请不能超过核定总额减生效覆盖再减其他有效预留，不能把剩余当原总额。 |
| 原子预留、资金池版本 | 在同一权威边界占住额度，并记录资金池状态修订号。 | 预留 1 后，1.5 的池子只剩 0.5 可分；不允许两边各承诺 1。 |
| 预留转生效、双重计数 | 资金真正提交后，要把原预留转成已承担金额。 | 同一笔不能既当有效预留又当生效覆盖，再扣一次可用额。 |
| 复式分录、journal | 用对应账务记录表达双方变化；journal 是不可变的权威流水。 | 基金减少和损失账户获得覆盖应属于同一经济提交，不能只改两个缓存字段。 |
| 贷记覆盖、原始损失 | 贷记覆盖是向源风险单元记入承担款；原始损失仍保留历史。 | 源从 -2 到 -0.5，基金从 1.5 到 0，原核定 2 不改写为 0.5。 |
| UNKNOWN、提交水位 | UNKNOWN 表示结果未知；提交水位说明权威记录查到了哪里。 | 超时查原 allocation，不能因余额视图没更新就新建分配再扣。 |
| loss_adjustment_id、冲正 | 前者标识追加定损调整，冲正以新反向分录更正旧记录。 | 费用迟到或错扣均保留原凭证，不删除历史或覆盖金额。 |
| 资产、精度、尾差 | 资产说明是哪种币；精度和尾差规定小数如何正式入账。 | 双边用同一金额规则，不能两边独立舍入造成钱对不上。 |
| covered、assigned、remaining | 分别是已覆盖、按其他明确规则已承接和仍待处理的金额。 | 各类承担不得重复，三者合计要能解释当前核定损失。 |
| 基金完成、损失结案 | 基金动作完成只说明这一层做完；结案还要证明剩余责任已处理。 | 覆盖 1.5 后的 0.5 仍须保留去向，不能默认 ADL 或余额截零自动清偿。 |

## 把整篇文章压缩成一个故事

小林用 20 USDC 保证金持有入场价 100 的 1 ETH 多头。价格下跌后，权益连同浮亏低于维持要求，系统启动强平复核；Mark 是估值价，不保证真实成交。独立全平路径若最终在 78 成交、忽略费用，亏损 22，留下缺口 2。系统仍要核齐成交、费用及其他确定义务，才能把这笔损失交给基金环节。

协议规定基金对这笔损失最多能用 1.5。系统给损失一个稳定身份，再为每次分配单独编号，可以先覆盖 1、再覆盖 0.5；重试第一笔不会再扣一次。若别的损失同时申请同一池子，要在权威账本原子预留，不能两个执行器都看到余额 1.5 就各花 1。预留提交后转为生效承担，不能两边重复计数。

覆盖 1.5 后，源负余额从 -2 变成 -0.5，原始损失仍保留为 2。回报超时就查原分配，费用更正则追加调整，不能换号重扣或删除历史。保险不是无限兜底，基金这一层完成不等于整个案件结清；剩余 0.5 仍要按明确规则处理，也不能默认交给 ADL 凭空消失。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题接在坏账核定之后，讨论有限保险基金如何承担确定的缺口，以及多次分配、并发申请和迟到更正如何留痕。它不讨论 Backstop 接管仓位，也不把 ADL 视作基金扣款；基金分配只处理已有明确责任、币种、金额和协议规则的损失记录。

**共同前提：** 沿用[总览基线](README.md#11-讨论基线)：链下托管线性 USDC 逐仓多头，`q=1、P₀=100、C=20`，固定 `MMR=5%`，忽略费用、资金费，严格 `E < MM` 触发。Mark 90 为 `E=10、MM=4.5`，不触发；Mark 84 为 `E=4、MM=4.2`，触发。保险核算使用独立坏账变体：整仓在 78 全平，现金 `20 + 1×(78−100) = -2 USDC`，确认缺口 `2 USDC`；基金最多有 `1.5 USDC` 可用于该笔损失，不与部分成交例叠加。

本题共 8 层，沿“确认缺口→有限余额规则→分批身份→并发预留→复式分录→UNKNOWN→迟到更正→结案核验”推进。

## 第 1 层：基金应该覆盖什么，不应该覆盖什么？

**面试官：** 仓位平掉后现金为负，是否可以直接从保险基金余额减掉差额？基金分配前要先确认什么？

**面试者：** 先把成交和费用按权威身份结转，确认源仓位全关且撤单、在途成交和相关结算义务核清，再对具体USDC风险单元最终定损。另一条允许路径是残仓已经按09题的成对经济提交真实移交给Backstop，并依据事先约定的价格/责任边界，把源账户已固定的损失与目标仍承担的市场风险分开核定；仅给残仓加标记或变更执行owner并没有转移经济风险。只有这样确认的缺口才能进入基金规则；风险估值不足、未平仓时的暂态负现金、未确认费用和预估滑点不能直接记成最终赔付损失。

独立例中，真实全平价 78 产生已实现毛损失 22，现金从 20 到 -2，所以在忽略其他现金项的约定下损失缺口为 2。Mark 84 的触发状态、简化破产价 80 和实际 78 的成交结果各自承担不同作用。若采用跨保证金或纳入费用，就要重建完整币种账，不可把“账户负数”当不需解释的基金扣款依据。

## 第 2 层：基金有限时，分配顺序怎样定义？

**面试官：** 已核定 `loss_id=L1` 的缺口为 2，但基金可用资金只有 1.5。系统怎样表达覆盖上限和剩余 0.5？

**面试者：** 分配规则要有明确的协议版本、资产、可用于该层级的限额、优先级和舍入规则。本例在规则版本 R 下最多分 1.5，生成 1.5 的已核定覆盖，并将 `L1` 的 0.5 明确保留为未覆盖责任。基金资金不足不是四舍五入或账户截断条件，不能把缺口 2 的 loss 状态直接标成已结清。

要区分基金账面总余额、当前可分配余额和已预留余额。教学例中若总余额是 1.5、没有其他预留，则最多可分 1.5；生产系统可能还需留最低储备或对不同产品层级限额，这些改变可用额，却不改变 `loss_id` 原始核定金额。协议若规定基金先于其他机制或只覆盖某类费用，必须在规则版本中显式表达。

## 第 3 层：同一个 loss_id 分多次执行，怎样避免重复或覆盖？

**面试官：** 第一次只覆盖 1.0，恢复后再覆盖 0.5。如果以 `loss_id` 做唯一幂等键，第二次会被误判成重复。应该怎么建模？

**面试者：** `loss_id` 标识被分配的那笔核定损失，分配动作则各有唯一 `allocation_id`。`L1/A1=1.0` 与 `L1/A2=0.5` 是两个不同的分配分录，都引用同一个 loss；重试 A1 只返回 A1 原结果，不能以 L1 覆盖 A1 或把 A2 拦成重复。每条分配还绑定账户、资产、正金额、规则版本、来源分录及请求载荷摘要。

对 L1 要检查所有承担方已生效分配的净额与未提交但有效的预留之和，不超过原核定缺口加追加调整得到的当前核定总额；已提交分配由预留转成生效额，不能两边重复计数。等价地，新申请额不能超过“当前核定总额−已生效覆盖−其他有效预留”。上限是核定总额，不是已经减过覆盖款的 remaining 再与历史分配求和比较。基金侧则另行检查当前已预留/待支出不超过未支出的基金资源。若同一 allocation ID 的金额或资产与首个提交不同，作为身份冲突隔离，而不是改写历史。这样可分批完成、重复可判定，也能在恢复时区分“同一分配重试”和“该损失的下一次合法分配”。

## 第 4 层：多个 loss 并发申请同一有限基金，如何防止超额承诺？

**面试官：** 两笔各 1 USDC 的缺口同时看到基金可用余额为 1.5，都准备覆盖 1。仅靠 allocation_id 幂等为什么不够？

**面试者：** 幂等只能阻止同一身份重复记账，不能阻止两个不同身份超额使用共享资源。分配服务必须在权威资金池序列内对可用余额做原子预留或扣减：`available = settled_balance − outstanding_reservations − policy_holdback`。例如一笔先成功预留 1 后，可用余额降至 0.5，第二笔至多预留 0.5；若协议不允许部分覆盖，就拒绝并保留该损失待处理。

预留、allocation 状态和资金池版本要在一个持久边界提交，不能先读 Redis 缓存余额再异步写账。若预留过期，先按 reservation/allocation 身份确认没有资金提交；若已提交而响应丢失，继续原分配的查询与恢复。并发事务可以锁基金账户、做带版本条件更新，或使用等价的单写者分片；选型要保证跨实例时的上限约束仍成立。

## 第 5 层：一笔覆盖应留下哪些可核对分录？

**面试官：** 现在为 L1 提交 1.5 的覆盖。只把 `fund.balance -= 1.5` 和 `loss.remaining -= 1.5` 写进两个表，出现部分提交时怎么查？

**面试者：** 我会以一条不可变分配业务分录记录 `allocation_id、loss_id、asset、amount、fund_account、loss/clearing_account、rule_version、source_refs、状态`，并在复式账本中同时产生基金减少 1.5 与损失承担/清算账户增加 1.5 的相反方向分录。两边必须属于一个账务提交，或由不可变 journal 驱动可恢复投影；其后再从已提交 allocation 汇总 `L1` 的剩余额。

本例按基金向源风险单元贷记覆盖款处理：覆盖前源账户 USDC 余额为 `-2`，提交 1.5 的双边分录后变为 `-0.5`；基金可用余额从 1.5 降至 0，原始核定缺口仍记 2，基金覆盖 1.5，剩余待处置 0.5。若具体产品把未覆盖部分记为独立应收负债而非负现金，账面科目可以不同，但净缺口守恒关系不变。不能把原始 loss 直接改写成 0.5 而丢失来源。外部可见状态如“已赔付”应由该确定分录投影而来，不能先更新页面状态、之后再尝试扣基金。币种精度和尾差也必须进入正式金额规则，不能在两边独立舍入。

## 第 6 层：扣款结果 UNKNOWN 时，怎样恢复？

**面试官：** allocation 已发送给账本，调用方超时。重启后基金余额看起来还是 1.5，能否以新 allocation ID 再扣一次？

**面试者：** 不能用余额快照判断原提交失败。对原 `allocation_id` 查询权威 journal 和提交水位；若分录已提交但读模型还滞后，返回原 allocation 结果并等待投影；若权威端确认原身份被拒且不存在提交，才按协议决定是否重试同一身份。查询尚未越过该请求的可见水位时，UNKNOWN 仍是 UNKNOWN，保留预留和缺口状态。

若同一 allocation 被第二次投递，账本应以身份唯一约束命中原 journal；原 ID 换金额则冲突，不得新扣。基金余额的单一快照也不足以证明“没有这笔记录”，因为期间可能有其他 loss 分配或迟到回滚。恢复以分录集合、资金池版本和 allocation 状态共同裁决。

## 第 7 层：事后发现原始缺口或基金分录有迟到更正，能否覆盖旧值？

**面试官：** 交易所迟到补报费用，发现原缺口应是 2.1；或者审计证实基金扣款有误。是否直接把 L1 金额改成 2.1，或删除原 allocation？

**面试者：** 不覆盖已确认的核定和分配历史。先验证迟到事件的身份、来源序列、币种、影响范围与原成交的关联，生成追加的 `loss_adjustment_id`，表达原核定 2 到新核定 2.1 的 +0.1 差异，再按规则为差额创建新的 allocation。若错扣，应追加反向冲正/退款分录并引用被冲正的 allocation，然后按更正后的可用余额重算；原分录仍保留审计可见性。

更正可能影响以前已经派给后备机制的余额，所以必须定义责任升级和冻结范围，不得通过把 `remaining` 字段重写为零或改小来隐藏负债。旧 rule version 下已完成的合法分配通常仍是历史事实；是否重算其责任由显式迁移/更正规则决定，不能让重放器以新规则重解释旧分录。

## 第 8 层：什么条件下可以将基金环节和 loss 结案？

**面试官：** 基金扣款完成、基金服务返回成功，是否足以将 L1 标成已解决并解冻关联风险？请给出一个超额并发的验证反例。

**面试者：** 基金环节只有在 loss 核定、分配分录、资金池余额与 allocation 汇总一致，所有预留及 UNKNOWN 都有确定结论，且 `covered + explicitly_assigned_by_other_rules + remaining = assessed_amount` 时，才可标为已完成或明确的部分完成。这里基金只覆盖了 1.5，剩余 0.5 仍由协议指定的下一层负责或维持待处置；基金返回成功不等于整个 loss 关闭，更不自动解除其他仓位的风险保护。

反例是两个 worker 各基于余额 1.5 提交 1.0，页面最后显示“已覆盖 2”。正确账本只能允许一个预留 1.0、另一个最多 0.5（若协议允许部分）；总分配不得超过 1.5，L1 覆盖不得超过 2，且每一笔都有独立 allocation ID。可据此手工检查资金不变量；这不是并发测试或生产资金验证。

## 本题收束

- **讲透的机制：** 缺口以权威 fill 和账务结果核定；有限基金按可用余额原子预留；`loss_id` 与多条 `allocation_id` 分工；双边分录、UNKNOWN 查询和迟到更正都保留不可变历史。
- **最容易答错的边界：** 幂等不等于并发余额保护；基金部分覆盖不能把原缺口改成已结清；余额缓存不证明分配不存在；纠错要追加调整而非擦除历史。
- **检验反例：** L1 的 1.0 allocation 已提交但 ACK 丢失，worker 重试 A1，同时另一个 worker 为 L2 提交 1.0。方案必须既避免 A1 重扣，也在同一资金池原子边界内把有效分配限制在 1.5 之内。
