## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 链下托管、线性 USDC 永续 | 托管方在链下管理账本；合约无固定到期日，盈亏线性计算并以 USDC 结算。 | 全专题只用此教学范围，不直接套到反向合约、多抵押或链上执行。 |
| 保证金、逐仓现金 C | 放入指定风险单元、用来承担仓位亏损的资金。 | 本例 C=20；逐仓限定风险范围，不作任何情况下的绝对损失封顶承诺。 |
| 多头、q、P₀ | 多头涨价赚、跌价亏；q 是数量，P₀ 是每单位入场价。 | 主例为 1 ETH 多头、入场价 100 USDC/ETH。 |
| Mark、M、P_exec | M 是风险估值标记价，P_exec 是实际执行价格。 | Mark 84 不能保证卖出价也是 84，估值不能冒充真实成交。 |
| U、未实现盈亏 | 尚未平仓部分按当前风险价格计算的浮动赚赔。 | 本例 U=q×(M−P₀)，Mark 84 时 U=-16。 |
| E、权益 | 保证金现金加上浮动盈亏后的风险承受能力。 | 基线忽略费用和资金费，E=C+U，此时为 4，不等于现金余额 20。 |
| MM、r | MM 是继续持仓的最低保证金要求，r 是维持保证金率。 | 本例 r=5%，MM=q×M×r；Mark 84 时为 4.2。 |
| E<MM、强平复核 | 权益严格低于维持要求时，产生需要复核的处置候选。 | 本专题数学等值不触发；不混用相邻专题的 <= 规则，触发不等于成交或亏光。 |
| 风险单元、快照版本 | 风险单元是共同核算对象；快照版本记录所用仓位、账本、价格和规则。 | 用户补款、减仓或价格证据变化后，要让旧许可失效并重评。 |
| case_id、owner_epoch、fencing | case_id 是案件身份；epoch 是负责人代次；fencing 拒绝旧负责人的新命令。 | owner 是系统裁决权，不是真实资产所有权；旧合法成交仍需接续。 |
| 撤单、预留、成交前沿 | 撤单关闭剩余资格，预留占住额度，前沿说明封口前已确定哪些成交。 | 发送撤单或收到受理回报，不等于余单终结和全部资金释放。 |
| action_id、step、累计量 | 动作身份、执行步骤和截至当前的总进度。 | 同身份重试不生成新意图；累计成交从 0.3 到 0.5 不代表又新增 0.5。 |
| UNKNOWN、NOT_FOUND | UNKNOWN 是结果未知，NOT_FOUND 是此次查询未找到。 | 超时或一次查空都不能证明未执行，先查原身份，不能盲发新单。 |
| Reduce-Only、过零 | Reduce-Only 只减现有仓位；过零指平超后开出反向仓位。 | 用户和强平并发时，最终执行点必须共同限制可减数量。 |
| fill_id、account_leg_id、结转 | 成交身份、账户经济效果身份，以及正式应用仓位和资金变化的过程。 | 确定 fill 不可因入账失败而丢弃，同一账户腿也不能重复扣钱或减仓。 |
| 在途义务、经济水位 | 前者是尚未核齐或结转的责任，后者表示已处理到哪个可比较位置。 | 仓位、账本及成交源要追到可解释边界，不能仅看各自最新页面。 |
| P_bank、破产价、D | P_bank 是特定假设下权益归零的理论价格；D 是最终资金缺口。 | 初始简化破产价为 80；D 要在相关确定成交、费用及资金费等义务核齐后逐币计算。 |
| loss_id、负余额 | loss_id 标识核定损失；负余额如实表示尚未承担的资金责任。 | 独立全平@78 且无费用时缺口为 2，显示截零不等于清偿。 |
| Backstop、transfer、basis | Backstop 是后备接收方，transfer 是仓位经济移交，basis 是成本基础。 | 必须有容量、真实资本、双方经济腿和责任起点，换 owner 不等于接仓，接仓也不抹亏损。 |
| 保险基金、allocation_id | 基金以有限资源按规则吸收缺口，allocation_id 标识一次具体承担。 | 独立例覆盖 1.5 后仍欠 0.5；多次分配须各有身份且共享余额不能超扣。 |
| ADL、配对减仓 | 自动减仓按协议选择合格反向对手仓位，关闭仍存续的敞口。 | 不是任意扣盈利用户现金；已全平且配对闭合后，现金欠账须另按明确机制处理。 |
| E>=MM、恢复门槛 | 数值恢复条件加上相关执行、撤单与账务义务核清。 | 生产缓冲必须另行声明；风险解除、普通交易重开和损失结案分别判断。 |
| owner loop、channel、持久提交 | 前两者协调 Go 进程内任务，持久提交保存跨重启可裁决事实。 | 有界队列能背压，但不提供持久性或跨实例围栏；重放不应再次下单、扣基金。 |
| MVP、手工推演 | MVP 是只覆盖核心机制的最小示例；手推是按输入演算预期变化。 | 总览伪代码不是生产原子事务，也没有实现或验证真实撮合、基金、Backstop 和 ADL 系统。 |

## 把整篇文章压缩成一个故事

小林拿 20 USDC 保证金持有入场价 100 的 1 ETH 多头。保证金承担亏损，权益还要计入浮动盈亏。Mark 跌到 84，权益为 4、维持要求为 4.2，于是生成强平候选。系统先核对仓位、账本、价格和规则是否仍有效，再选出唯一处置者；接管的是系统裁决权，不是资产所有权，也没有让仓位立刻成交。

协调者关闭增险订单，追齐撤单前的成交，再以稳定身份发出只减仓动作。回执超时就查原动作，不盲发新单。若实际成交半仓@84，只把这半仓结转为现金 12、余仓 0.5，再按新状态判断是否可停止；Mark 不保证成交价，强平也不必然全平或亏光。

另走独立全平@78 的路径，无费用时缺口为 2。核齐全部确定义务后，若基金按例覆盖 1.5，剩余 0.5 仍须处理，不能与半仓路径混算。Backstop 真接仓不等于亏损消失；ADL 仅在仍有合格配对敞口和明确规则时适用，不能替闭合后的现金欠账凭空找人。最后逐项核对动作、成交、账本和责任去向，分别决定风险解除、交易重开与损失结案，不能只看页面显示成功。

## 一、文字全流程：从风险触发到风险解除或坏账处置

### 1.1 讨论基线

本专题使用**链下托管、线性 USDC 结算永续、单一逐仓多头**作为教学基线，不代表任何具体平台实现。

- 风险单元为一个账户在 `ETH-USDC-PERP` 上的一个逐仓仓位。主案例 `q=1 ETH`、入场价 `P₀=100 USDC/ETH`、逐仓抵押现金 `C=20 USDC`。
- 固定维持保证金率 `r=5%`，忽略手续费、资金费、额外抵押变化、其他仓位和挂单占用。全仓、多抵押、反向合约和保证金阶梯不套用本例公式。
- 本例未实现盈亏 `U=q×(M−P₀)`，逐仓权益 `E=C+U`，维持保证金 `MM=q×M×r`。严格采用 `E < MM` 触发复核；`E=MM` 不触发。边界、费用项与具体清算规则由产品定义。
- 本专题教学恢复门槛为 `E >= MM`，并要求撤单、在途成交和相关账务义务已核清；生产安全缓冲必须另行明示。相邻保证金专题采用 `E <= MM` 作为处置评估条件，与本题严格 `<` 的等值边界不同，阅读时不能混为同一产品规则。
- Mark Price `M` 是风险估值输入，不是强平成交承诺。强平阈值、破产边界和实际执行价分别表示风险进入条件、权益耗尽条件和真实成交结果。
- 风险评估产生候选，不直接修改仓位或账本。强平协调层拥有持久处置案例和执行资格；订单／撮合拥有命令裁决和成交事实；持仓／账务按稳定成交身份结转经济结果。
- 主案例假设普通订单簿执行。保险基金、Backstop 与 ADL 是不同机制，是否采用及先后顺序由产品协议定义；不暗示所有永续产品均具备这些机制。

### 1.2 贯穿案例与数值

| Mark Price | 未实现盈亏 U | 逐仓权益 E | 维持保证金 MM | 结果 |
|---:|---:|---:|---:|---|
| 90 USDC/ETH | -10 USDC | 10 USDC | 4.5 USDC | `E > MM`，不触发 |
| 84 USDC/ETH | -16 USDC | 4 USDC | 4.2 USDC | `E < MM`，进入复核 |

Mark 为 84 时，候选条件成立，但系统还未成交。若强平实际成交 `0.5 ETH@84` 且忽略费用，毛损失为 `0.5×(84−100)=-8 USDC`，剩余多仓 `0.5 ETH`、入场成本 `50 USDC`、抵押现金 `12 USDC`。按同一个 Mark 84 估值，剩余未实现盈亏 `-8`、权益 `4`、维持保证金 `0.5×84×5%=2.1 USDC`。系统必须根据实际 fill 和新风险快照决定继续处置还是满足恢复条件，不能在发单时假定风险已下降。

**独立坏账变体，不与上面的部分成交叠加：** 初始 `q=1、P₀=100、C=20`，忽略费用时简化破产价格 `P_bank=80`。如果全平成交价是 78，毛损失 22，风险单元现金为 `-2 USDC`，缺口为 2。假设教学协议允许 1.5 USDC 保险基金覆盖，覆盖后还剩 0.5 USDC 待协议定义的补资、追偿或其他损失分配。ADL 只有在仍有可配对的未平仓位、合格反向仓位及明确执行和分配规则时才适用；全平结算闭合后的现金缺口不能直接称为 ADL 平仓。该例不代表通用处置顺序。

### 1.3 主流程

```text
价格、仓位、抵押、费用／资金费或参数发生变化
    ↓
风险服务读取同一风险单元的版本化经济状态与有效价格证据
    ↓
计算权益、维持保证金和未结义务
    ├─ 未越过规则边界 → 记录评估，不产生强平执行权
    └─ 越过规则边界 → 创建候选〔case_id、position_version、price_id、rule_version〕
                         ↓
                   执行前复核
                    ├─ 状态已改善／证据过期 → 撤销旧候选并重算
                    ├─ 价格不可用 → 按产品策略暂停或降级
                    └─ 条件仍成立 → 持久取得风险单元处置权及 owner_epoch
                                      ↓
                               禁止新增风险，有序关闭增险订单意图
                                      ↓
                               以稳定 action_id 发出 Reduce-Only 执行命令
                                  ├─ 无成交／部分成交 → 保留实际进度，重新评估剩余风险
                                  ├─ 超时／失败 → 查询原 action_id，不另造重复平仓意图
                                  └─ 实际成交 → 以稳定 fill_id 送入持仓与账务结转
                                               ↓
                                      依据实际成交价、数量和费用结转经济状态
                                               ↓
                                      读取新版本风险快照
                                         ├─ 达到恢复条件 → 记录依据后解除处置模式
                                         ├─ 仍超限且可执行 → 继续减仓或进入协议指定后备机制
                                         └─ 仓位关闭仍有负余额 → 核清在途成交及结算义务，固化缺口
                                                                     ↓
                                                        按协议用有限基金覆盖，剩余待补资／追偿／独立分配
                                                                     ↓
                                                        核对成交、账本、资金池和处置记录后结案
```

### 1.4 关键异常分支

```text
候选基于旧快照生成，执行前用户已补抵押或减仓
    → 读取权威新版本并重算；不执行旧许可

强平接管与用户撤单／减仓竞争
    → 在风险单元权威顺序中裁决；只处理仍有效的订单和仓位

接管已提交，撤单调用超时
    → 查询原撤单身份与在途成交；超时不等于撤单终态

强平执行超时或部分成交
    → 用原 action_id 查询累计 fill 和剩余量；不按原目标盲目重发

成交确定但持仓／账务结转失败
    → 保留成交义务与风险约束，以原 fill_id 恢复结转，不撤销成交

仓位已关闭但现金为负
    → 核清执行与结算义务后定损，按协议处理基金／补资／独立损失分配；不得截断负余额或谎报结案

保险基金不足或 ADL 对手方不可执行
    → 进入显式待处置状态并限制相关风险，不能把未覆盖部分算作已吸收
```

### 1.5 状态与完成点

| 阶段 | 权威事实 | 尚未承诺 |
|---|---|---|
| 风险候选 `TRIGGER_CANDIDATE` | 某份状态与价格证据越过规则边界 | 未接管，也未成交 |
| 已复核／接管 `LIQUIDATING` | 条件仍成立，风险单元处置权已生效 | 仓位不一定下降，风险未必解除 |
| 指令已受理 | 执行端接收稳定身份的强平意图 | 不保证有流动性、成交或结转完成 |
| 成交已提交 | 实际成交身份、价格、数量已确定 | 持仓和账务可能仍在途 |
| 成交已结转 | 仓位、损益、费用及抵押经济效果按结转契约生效 | 强平案例不一定解除，坏账不一定清偿 |
| 风险解除 | 新版本达到产品恢复门槛，执行义务已闭合 | 不自动恢复全部交易或提现权限 |
| 坏账结案 | 缺口按协议覆盖或后备分配，证据可对账 | 不能用页面状态或人工改余额替代 |

## 二、核心板块

| 核心板块 | 决定什么／为何核心 | 权威状态 | 上下游契约 |
|---|---|---|---|
| 风险触发与复核 | 风险状态是否达到强平条件；旧状态会造成错平 | 版本化经济状态、价格证据、参数版本、复核结果 | 消费仓位与风险价格，不直接写仓位或生成成交 |
| 接管权与命令裁决 | 用户操作和强平如何获得唯一有效顺序 | 案例状态、owner epoch、处置资格 | 对接订单与资金操作，阻断双重执行和过期授权 |
| 强平执行与反馈 | 如何在真实流动性下减险 | action、累计成交与剩余量 | 复用执行模块；部分成交后须反馈并重评 |
| 成交结转与恢复 | 强平成交如何只影响一次经济状态 | fill 身份、仓位／账本版本、结转进度 | 复用持仓和成交结算边界，失败不撤销成交事实 |
| Backstop 与剩余风险分配 | 仓位移交和亏损由谁承担、如何结束 | 接管仓位、缺口、基金分配、ADL 状态 | 仓位移交、现金吸收和 ADL 是分开的经济事实 |

## 三、核心 20%

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 版本化触发与执行前复核 | 候选到接管 | 风险随仓位、抵押和价格变化 | 基于过期信号错误强平 | 经济版本、价格身份、规则边界、重评时点 |
| 风险单元接管与唯一裁决 | 用户操作与强平并发 | 必须确定谁能发后续有效命令 | 双重减仓、反向开仓、旧主继续写 | 状态机、epoch、业务顺序、fencing |
| 增险意图关闭与在途义务 | 接管到执行 | 撤单与成交可以竞争 | 预留过早释放或遗漏迟到成交 | 撤单权威终态、成交前沿、Reduce-Only |
| 部分执行与 UNKNOWN 恢复 | 强平执行 | 发单不代表流动性足够或已成交 | 重复卖出或把未成交当作已减险 | 稳定 action、累计 fill、剩余量、先查后重试 |
| 强平成交与经济结转 | 成交到账本 | 已确定 fill 必须进入仓位与资金 | 仓位与现金分叉、重复损失 | fill 身份、提交边界、在途风险约束 |
| 破产缺口与损失瀑布 | 平仓后 | 执行价可能穿过破产边界 | 隐藏负余额、基金超扣、坏账重复分配 | 逐币金额、loss 身份、基金上限与剩余缺口 |
| Backstop 仓位移交 | 执行降级 | 仓位转移不等于损失消失 | 仓位和责任双计或无人承担 | source/target 仓位、成交/估值、转移完成条件 |
| ADL 与安全结案 | 后备分配与恢复 | 后备机制会影响其他账户 | 选择不确定、审计缺失、未结风险重开 | 规则版本、确定排序、对手方执行和重开门槛 |

“20%”表示聚焦决定强平结果的机制，不机械限定章节比例。保证金模型、标记价格生成、资金费率算法、撮合和通用账务分别引用相邻专题；本专题讲清它们对强平的输入输出，不重写完整教材。

## 四、共同设计与规则

### 4.1 状态、公式与不变量

令 `q>0` 为本例多仓数量，`P₀` 为入场价，`C` 为风险单元 USDC 抵押现金，`M` 为有效 Mark，`r=0.05`。本教学基线忽略费用、资金费、舍入尾数和其他余额：

```text
未实现盈亏 U = q × (M − P₀)
逐仓权益 E = C + U
维持保证金 MM = q × M × r
候选条件 = E < MM
简化破产价格 P_bank = P₀ − C / q     〔仅适用于本例线性逐仓多仓〕
实际缺口 D = max(0, −结转后的风险单元现金)
```

- 主例 `M=84` 时 `E=4 < MM=4.2`；`M=90` 时 `E=10 > MM=4.5`。84 是风险估值，不是成交承诺。
- 实际执行价 `P_exec` 决定真实已实现损益。全平后的现金（忽略费用）为 `C+q×(P_exec−P₀)`；`P_exec=78` 得现金 -2、缺口 2。费率、资金费、档位、多资产和舍入改变公式时必须显式声明。
- 部分减仓以权威成交数量为准，不得过零扩大风险。实际 fill 和结转结果进入风险重评。
- 相同 case、action、fill 或 allocation 身份的重试不得重复接管、成交、记账或分配资金；相同身份不同载荷必须隔离。`loss_id` 标识损失，允许其下多条独立 `allocation_id` 分批覆盖，但合计不得超过调整后的核定总额。
- 允许候选、接管、执行、待结转、UNKNOWN 和待处置等可恢复暂态；禁止旧风险许可直接执行、把目标量当成交量、负余额截零或未覆盖坏账标记结案。
- 保险基金余额不得超扣；每次分配有币种、金额、来源事件、规则版本与前后余额。ADL 资格和排序须由产品规则定义，不能由服务临时猜测。

### 4.2 架构与权威顺序

```text
仓位／账本版本 + 合格风险价格
    ↓
Risk Engine 评估／复核〔产生候选，不改仓〕
    ↓
风险单元协调者〔持久 case 状态、epoch 与命令资格〕
    ├─ 冻结增险并关闭增险意图
    ├─ 创建稳定 action_id 与 Reduce-Only 命令
    └─ 接收执行结果并控制累计数量
            ↓                          ↓
    订单／撮合执行              Backstop／损失分配流程
            ↓                          ↑
    fill_id → 持仓与通用账务结转 → 新风险版本 ─┘
```

本例中风险评估、执行和账务可以独立部署，但不因此改变责任边界。仓位和价格证据沿用[持仓成本与盈亏专题](../../01-撮合交易与核心链路/05-持仓成本与盈亏/README.md)与[估值快照与风险接口](../../01-撮合交易与核心链路/05-持仓成本与盈亏/11-估值快照与风险接口.md)；成交记账沿用[成交清算与结算专题](../../01-撮合交易与核心链路/03-成交清算与结算/README.md)。强平协调者维护案例和执行资格，不越权修改仓位、账本或订单簿。

### 4.3 必要对象与实现约束

| 对象 | 必要字段 | 权威用途 |
|---|---|---|
| 风险评估 | `risk_unit_id、position_version、ledger_version、price_id、rule_version、equity、maintenance、decision` | 解释候选所依据的状态、价格和参数 |
| 强平案例 | `case_id、status、trigger_snapshot_id、review_version、owner_epoch、reason` | 串联接管、执行、结转、解除与坏账处置 |
| 执行动作 | `action_id、case_id、attempt、reduce_only、target_qty、filled_qty、remaining_qty` | 查询重试与累计进度，避免重复逻辑动作 |
| 成交输入 | `fill_id、action_id、account_leg_id、qty、price、fee、source_seq、rule_version` | 真实执行事实，以稳定身份进入结转 |
| 缺口与分配 | `loss_id、allocation_id、asset、assessed_amount、allocated_amount、fund_before/after、allocation_rule_version、status` | 损失与分配分别标识，表达待覆盖、已覆盖与后备责任，逐币审计 |

Go 进程内可以按风险单元分区用 owner loop 串行处理，并用有界队列背压；channel 不提供持久性或跨进程隔离。数据库在持久提交时比较案例版本和 `owner_epoch`，新 owner 接管后旧主以旧 epoch 发起的新命令必须被裁决端拒绝。已由执行端合法确认的旧 epoch fill 仍需验真、确定归属并结转，不能以隔离旧主为由抹除；租约过期本身不能证明旧主已停止。

执行端必须在最终裁决点限制累计成交量不超过当前可减仓量；若撮合不支持 Reduce-Only，就需要等价的撮合端约束。UNKNOWN 先查询执行事实和成交记录，再决定继续；重复运输允许，重复经济效果不允许。暂时故障可对原身份限次退避，载荷冲突、坏价格和超量指令必须隔离或暂停，不可一概无限重试。

## 七、工程实践：唯一的简洁 MVP

### 7.1 目标与范围

在单一逐仓风险单元里手工推演**候选复核、接管、部分强平、成交后重算，以及负余额由有限保险基金覆盖后的剩余缺口**。不实现真实价格源、撮合、持久事务、主备 fencing、资金费、多抵押、完整 Backstop 或 ADL；伪代码中的整体状态替换只表达逻辑步骤，不代表生产原子提交。

### 7.2 核心伪代码

金额单位 USDC，数量单位 ETH。主例忽略费用、资金费和舍入；保留 `fee` 字段只是表示真实结转须扣除确定费用。`s.actions` 是已受理动作集合，`s.seen/s.pending/s.allocations` 初始为空。输入 fill 已由权威源验真并归一化身份，结转适配层提供它对应的前后公共经济序；原始执行序号不能冒充公共经济序。复核时的仓位、账本与价格/规则已在本例单写者内对齐，实际权益由这些状态计算，不信任调用方自报金额。

这是串行内存手推，不实现持久事务、跨实例竞争或身份生成；`copy` 后整体替换只表达基金和损失一起变化，不提供生产原子性。迟到、乱序或仓位不相容的真实 fill 保留在 `pending` 并阻止结案，交由正文恢复流程核查，不在这个小例子里实现改账或既有 allocation 冲正。

```text
review(s, r):
    if r.risk_unit_id != s.id: return REJECT
    if r.position_version != s.position_version: return RECHECK
    if r.ledger_version != s.ledger_version: return RECHECK
    if r.public_economic_seq != s.public_economic_seq: return RECHECK
    if not r.price_valid: return PAUSE
    if r.equity >= r.maintenance: return NO_LIQUIDATION
    if s.status not in {ACTIVE, TRIGGER_CANDIDATE}: return EXISTING_CASE
    s.status = LIQUIDATING
    s.owner_epoch += 1
    s.case_id = stable_case_id(s.id, r.public_economic_seq, r.price_id, r.rule_version)
    s.new_risk_allowed = false
    return s.case_id

apply_fill(s, f):
    if f.fill_id in s.seen:
        old = s.seen[f.fill_id]
        if old.digest != f.digest: return IDENTITY_CONFLICT
        return old.result
    if f.qty <= 0: return REJECT
    if (f.action_id not in s.actions or s.status != LIQUIDATING
        or f.previous_economic_seq != s.public_economic_seq or f.qty > s.qty):
        if f.fill_id in s.pending and s.pending[f.fill_id].digest != f.digest:
            return IDENTITY_CONFLICT
        s.pending[f.fill_id] = f
        s.new_risk_allowed = false
        s.status = RECONCILIATION_REQUIRED
        return RETAINED_FOR_RECONCILIATION
    pnl = f.qty * (f.price - s.entry_price)
    s.qty -= f.qty
    s.cash += pnl - f.fee
    s.position_version += 1
    s.ledger_version += 1
    s.public_economic_seq = f.economic_seq
    result = {qty: s.qty, cash: s.cash, realized: pnl}
    s.seen[f.fill_id] = {digest: f.digest, result: result}
    if s.qty == 0:
        s.status = EXECUTION_DRAINING
    return result

finalize_loss(s, required_fill_watermark, applied_fill_watermark, outstanding_actions):
    if s.status != EXECUTION_DRAINING or s.qty != 0: return REJECT
    if s.pending or outstanding_actions != 0: return WAIT
    if applied_fill_watermark < required_fill_watermark: return WAIT
    s.deficit = max(0, -s.cash)
    if s.deficit > 0:
        s.loss_id = stable_loss_id(s.case_id, required_fill_watermark)
        s.status = NEEDS_COVERAGE
    else:
        s.status = REVIEW_RECOVERY
    return {loss_id: s.loss_id, deficit: s.deficit, status: s.status}

cover(s, allocation, fund):
    if allocation.id in s.allocations:
        old = s.allocations[allocation.id]
        if old.request != allocation: return IDENTITY_CONFLICT
        return old.result
    if s.status not in {NEEDS_COVERAGE, PENDING_PROTOCOL_COVERAGE}: return REJECT
    if allocation.amount <= 0 or allocation.asset != s.asset or fund.asset != s.asset: return REJECT
    if allocation.loss_id != s.loss_id or fund.balance < 0: return REJECT
    if fund.balance == 0: return WAIT_FOR_FUND
    next_s = copy(s); next_fund = copy(fund)
    applied = min(next_s.deficit, allocation.amount, next_fund.balance)
    next_fund.balance -= applied
    next_s.cash += applied
    next_s.deficit -= applied
    next_s.status = REVIEW_RECOVERY if next_s.deficit == 0 else PENDING_PROTOCOL_COVERAGE
    result = {covered: applied, remaining: next_s.deficit, status: next_s.status}
    next_s.allocations[allocation.id] = {request: allocation, result: result}
    atomically_replace_demo_state(next_s, next_fund)
    return result
```

### 7.3 输入与预期结果

`required_fill_watermark` 是从本案例全部动作的权威终态映射出的成交前沿，`applied_fill_watermark` 是账务已完整应用的同一成交序号空间的连续前沿；不能直接比较独立的 execution seq 与 fill seq。表中的“水位核清”还要求无 UNKNOWN、无 `pending`，且相关费用及其他结算义务已确定；这里的终态、水位和权威证明作为输入，不伪装成已经实现的外部查询。

| 输入 | 前置状态 | 手工预期结果 |
|---|---|---|
| `q=1、P₀=100、C=20、Mark=84、r=5%` 的有效评估 | `ACTIVE`，版本匹配 | `E=4、MM=4.2`，接管进入 `LIQUIDATING`；尚未成交 |
| 风险版本过期或价格无效，包括只补抵押而仓位不变 | `ACTIVE` | 仓位／账本／公共经济版本任一不匹配即重新复核；价格无效暂停，不创建强平动作 |
| `0.5 ETH@84`，费用 0 | `LIQUIDATING`，`q=1、cash=20` | `q=0.5、cash=12、已实现=-8`；Mark 84 下 `E=4、MM=2.1`，须按恢复门槛复核 |
| 同一 `fill_id`、相同规范摘要重复输入 | 上一笔已处理，包括最后一笔使仓位归零 | 返回原结果，仓位与现金不再变化；同身份不同摘要返回冲突 |
| 权威 fill 首次晚到，case 已进入恢复／分配状态或经济序不连续 | 尚未结转该 fill | 保留到 `pending`，进入 `RECONCILIATION_REQUIRED` 并限制新增风险；不当作未成交，也不盲目套用当前仓位 |
| allocation 金额非正、币种不匹配 | 有待覆盖缺口 | 拒绝；基金与源余额、缺口不变；基金可用为零则等待，不记录零额赔付 |
| 仓位归零但仍有未决 action 或 fill 水位未追平 | `EXECUTION_DRAINING` | 不核定最终缺口、不开放新执行通道；待执行义务排空后再结算 |
| 独立变体：`1 ETH@78` 全平，费用 0 | 初始仓位，不叠加部分减仓 | action/fill 水位核清后 `cash=-2、deficit=2`；基金余额 1.5 时分配 1.5，剩余 0.5 待协议后备处置 |

这些结果是手工演算，不是执行测试或保险／ADL 生产策略验证。
