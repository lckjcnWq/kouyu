## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、U、E、强平 | 现金加未实现盈亏 U 得到权益 E，权益不够维持要求可能强制减仓。 | 主例 U 为 12、E 为 512 USDC，现金仍 500，不能把估值当实际收付。 |
| Index／Mark、I／M | 外部市场参考价／合约风险估值，I、M 是相应符号。 | 主例 I 为 2,000、M 为 2,006，算式正确只覆盖正确性的一部分。 |
| 四类正确性 | 规则是否正确、输入是否合格、状态交付是否完整、最终用价是否有效。 | 连接活着、页面更新或价格接近市场，都不能单独证明全链正确。 |
| 不变量、反例、可证伪 | 必须始终成立的约束，以及能让错误设计失败的输入。 | 过期仍能增仓就是约束被击穿，不以平均误差小来抵消。 |
| 黄金向量、独立参考实现 | 已人工确定预期的输入组，以及不复用生产计算内核的校验程序。 | 防止同一算术错误在主备和离线程序中一起“通过”。 |
| bps、阈值、最小价格单位 | 比例基点、合格比较边界、价格能表达的最小刻度。 | 1% 恰好保留，超一个 0.000001 USDC/ETH 就可能排除，须固定中位数测试。 |
| 源年龄、盘口年龄 | 在固定采样 T 时，外部报价和本地簿状态已存在多久。 | 分别覆盖 2,000／2,001 ms 与 500／501 ms，未来时间也应拒绝。 |
| 宽整数、有理数、舍入 | 足够大整数、精确分数、规定何处截断。 | 独立重算需对齐每个取整点，不能只看结果为正或大致接近。 |
| 基差、均值、限幅 | 本地合约相对指数偏离，先求窗口均值，再限制均值影响。 | 要验证先平均后限幅、负值截断、缺点和跨版本，不只重复主例。 |
| 重放一致、哈希一致 | 按同内核重建相同状态，或得到相同摘要。 | 说明没有分叉，不证明内核规则本身正确，更不证明输入真实。 |
| 独立市场参考、共同上游 | 旁路报价可辅助比较，但也可能共享生产数据依赖。 | 一致可能共同错，不一致也可能只是时间、单位或规则不同。 |
| 副作用隔离、最小权限 | 离线验证不能触发现实资金或交易动作。 | 回放历史 ACTIVE 不连接生产强平出口，也不刷新线上授权期限。 |
| price_id、decision、执行身份 | 分别定位价格、风险判断和实际业务效果。 | 用稳定身份串证据，不把不同机器墙钟简单排序当因果事实。 |
| Outbox／Inbox、ACK | 生产待发记录／消费应用记录，以及相应边界确认。 | 故障要打在提交、发送、确认之间，验证补发、幂等和检查点。 |
| 消费水位、已知限制 | 已连续应用的位置，以及已经收到的更高限制要求。 | 新 HALTED 已知时先收紧，迟到旧 ACTIVE 不能复活权限。 |
| 经济版本、在途敞口、最终复核 | 仓位现金的状态身份、未完成义务，以及产生效果前再检查。 | 强平意图后已到账补款，应使旧判断失效重算。 |
| SLO、p99、尾延迟 | 服务目标、99% 样本所处的分位边界，以及慢尾部耗时。 | 需在声明负载与故障条件下实测，本文不虚构目标值或性能结果。 |
| T、usable_until、延迟预算 | 采样起点、原包截止、全链共享的时间额度。 | T 后 1,500 ms 包含排队到执行，最老合格源到末端可能已有 3,500 ms。 |
| GC、重连洪峰、容量 | 垃圾回收、集中重连冲击，以及有限资源能承担的负载。 | 压测同时看正确拒绝、有效授权比例和资源，不能只报吞吐。 |
| 高基数标签、结构化日志 | 标签取值过多会拖累指标；详细证据放可检索记录。 | 指标用市场、源、原因等受控集合，账户与 price_id 留在受权限保护的证据中。 |
| 活性探测、告警抑制 | 外部确认系统仍在产出；减少重复告警但保留真正事故。 | 业务和监控一同停摆时，零超时计数不算成功。 |
| 影子评估、回归、反事实 | 新规则旁路试算、保留旧事故用例、在假设下推演另一种结果。 | 静态重放收益不是现实确定收益，调参资料与最终验收资料要隔离。 |
| 补偿／冲正、证据缺口 | 用授权新记录修复损失，以及无法证明的历史部分。 | 不直接改余额或补采今天数据冒充当时输入，不把验证计划说成已通过测试。 |

## 把整篇文章压缩成一个故事

小林投诉被错误强平。价格会改变持仓浮盈浮亏和保证金权益，权益不足才可能引出处置；所以调查不能只找一张当时的价格截图，更不能先把余额改回去，就宣布事故已经解决。

工程师先按执行身份追查真实成交，再查风险决定、完整价格包、仓位现金版本和在途义务。他把验证分成规则、输入、状态交付、最终用价四层：Mark 算对但过期仍被接受，照样是业务错误；心跳正常而源时间不前进，也不代表报价新鲜。

数值层用人工黄金向量和独立精确计算，覆盖年龄、1% 阈值、负基差截断和窗口缺点；协议层则计划在提交后漏发、消费后未确认、漏收限制及补款竞争处注入故障，核验能否补发、去重、拒绝或重算。离线重放必须断开生产动作出口。

线上再看源年龄、消费缺口、剩余期限和执行拒绝，不能只看 CPU 或平均耗时。已发生的经济事实保留，损失按权限补偿或冲正。最后把事故转成可复现用例，再隔离调参与验收资料评估新规则；没有实际运行记录，就只称设计预期，不声称测试通过。

## 第 1 层：价格正确究竟验证什么？

**面试官：** 聚合器上线前，只要用几组输入检查指数和 Mark 的算式，再看线上价格没有明显偏离，是不是就能说风险价格系统正确？

**面试者：** 只能说明少量算例符合预期，还没有证明整条价格链路的正确性。我会把目标拆成规则正确、输入资格正确、状态与交付正确、最终用价正确四类，并分别给出能够失败的检查条件。

规则正确是同样输入、顺序和 R1 得到同样源集合、指数、窗口、Mark 和模式。输入资格正确是源、单位、时间、身份和独立分组满足要求；即使一个陈旧源的数值恰好等于最新市场价，也不能当成合格输入。状态与交付正确是已确认轮次可恢复、无效轮次不漏发、完整价格包不被拆开、重复不推进恢复计数。最终用价正确是风险动作绑定当前经济事实，并且价格质量、模式、期限和必要水位都允许这项动作。

主例可作为一个明确的数值向量：排除 D、E 后指数 2,000，30 点基差均为 0.3%，Mark 2,006；2 ETH 多仓的浮盈为 12，现金仍为 500。但还要有反例：仅两源合格应无指数；盘口过期应降级；消费者断线且旧包过期后应拒绝增险。能在这些反例中正确拒绝，才说明系统没有把“有个看起来合理的数”误当作正确。

## 第 2 层：怎样设计能击穿算法边界的输入？

**面试官：** 你提出了不变量和反例。对于指数筛选、基差和精度，你会选择什么边界，避免只是测试主例的重复版本？

**面试者：** 我会先从 R1 每个比较符和取整点推导边界，而不是随机生成一些差不多的价格。源年龄 2,000 ms 在边界上合格，2,001 ms 不合格，未来时间不合格；盘口年龄 500 ms 合格、501 ms 不合格。离群阈值比较要使用与生产规则一致的宽整数交叉相乘，覆盖恰好 1% 和超出一个最小价格单位的情况。

为了不让待测值本身移动中位数，可以构造初筛报价 `1,980、2,000、2,000、2,020`，中位数固定 2,000，两个边缘值恰好在阈值上，应全部保留。把 2,020 改为 2,020.000001 时，中位数仍是 2,000，只排除这个源；剩余三源的均值按六位向下取整。这是独立算法向量，不改主案例。

基差则覆盖负值、平均除不尽、先限幅与后限幅结果不同、窗口缺一点、跨规则、重复 Tick 和时间跳格。比如 29 点为零、最后一点为 30% 的独立向量，先平均得到 1%，再限幅为 0.5%；若误把每点先限成 0.5% 再平均，只得到约 0.0166666%，会明显违反 R1。位宽检查还要覆盖允许输入上界以及中间乘积溢出，不能只测返回值是否为正。

这些向量的预期结果最好由独立的精确算术推导，并记录所有中间状态。性质检查也要注意适用条件：固定候选集的精确总和应不依赖容器遍历顺序，但不能断言“任意加入一个源，指数一定不变”，因为加入源可能改变中位数和最终集合。

## 第 3 层：独立重算为什么不会复制同一个错误？

**面试官：** 你说用独立程序和精确算术核对。如果离线程序也调用生产聚合函数，结果当然一致。怎样避免一个错误在主备和离线验证里同时通过？

**面试者：** 我会区分重放一致性和算法独立校验。调用同一个计算内核重放，能发现输入、快照或执行顺序分叉，但可能把同一算法错误稳定复制出来；它不等于规则正确。因此需要两种证据，而不是把结果哈希相同当成全部验收。

一类是固定的黄金向量，以文字规则和人工可复核算式确定预期；另一类是独立实现的参考计算，使用明确的大整数或有理数中间结果，在各规则点按规定取整，不直接复用生产函数的舍入与筛选实现。两者都对齐同一输入截止位置、R1 配置和历史样本，比较候选资格、排除集合、中位数、指数、每点基差、均值、限幅、模式，而不是只比较最终 Mark。

另一个独立市场参考只能作为旁证，不是规则正确性的绝对真值。它可能采用不同源、时间和计价币，也可能与生产共享上游。生产结果与它一致，不证明没有共同错误；不一致，也不自动证明生产算法有 bug。必须先核对时间、单位和源依赖，再把差异归类为规则差异、输入差异或实现差异。

离线回放还必须隔离副作用：读取历史输入不能连接生产强平命令出口、刷新线上有效期或重新发放授权。即使是只读代码路径，也应使用独立命名空间和无生产写权限的身份，避免恢复程序把历史 ACTIVE 当成今天仍可执行的状态。

## 第 4 层：数值没分叉，怎样发现交付和执行层仍然错？

**面试官：** 假设独立重算证实每轮 Mark 都对，但偶尔有人按过期价格增仓。你如何验证并定位这种价格没错、业务效果却错的故障？

**面试者：** 我会把稳定身份串成证据链：原始输入位置对应 `price_id`，完整价格包对应消费者处理位置，风险决策绑定价格、仓位、现金、在途敞口和风险参数版本，执行结果再绑定这项决策及最终复核结果。检查的对象不是所有时间都相等，而是每条业务效果能否解释它使用了什么状态、越过哪个提交边界。

故障验证应插在具体窗口：价格事务提交后、Outbox 发送前停止发布者；消费者事务提交后、ACK 前中断；先送第 102 轮再送 101；漏掉 HALTED 后断线到旧授权过期；强平意图形成后再到账一笔保证金；旧主失去任期后尝试提交。预期分别是可补发、重复无新效果、缺口阻断并收紧、过期失效、执行处重新复核、旧主写入失败。

已知无效或过期的价格必须在最终业务动作边界产生拒绝，而不仅仅是监控报警。尤其消费者观察到较新限制包后，迟到旧 ACTIVE 不能使权限倒退放开；恢复需要新的、满足 R1 恢复条件的裁决。若消费者只更新显示价格，真正的资金与撮合执行仍接受旧 token，说明验证位置放错了。

实际实验还要记录故障注入位置、提交结果、重试身份、恢复检查点及最终业务效果，不能只看请求返回一个错误。一个超时可能发生在事务已经成功以后，因此“不再调用”不证明没有副作用；要核对既有执行事实和幂等记录。

## 第 5 层：线上如何监控业务失真，而不是只看机器活着？

**面试官：** 上述故障不是每天都能注入。线上需要哪些指标，才能在系统连接正常但数据失效时发现问题？

**面试者：** 我会沿证据生命周期设置指标，而不是只统计 WebSocket 存活或每秒消息数。源侧看源时间年龄、接收到达延迟、序号推进、冲突数、单位拒绝与有效源／独立组覆盖；聚合侧看排除原因、源集合变化、离散度、指数与本地盘口基差、窗口完整度和各模式持续时间。心跳增长而源时间或价格业务序号长期不动，要与真正的有效报价更新区分。

提交到消费侧看 Tick 到提交、Outbox 未交付年龄、消费者水位差、价格包剩余有效期以及各阶段队列年龄。执行侧看因过期、未知规则、缺口或非 ACTIVE 被拒绝的动作数，以及过期价格被实际接受的次数；后一类应被视为不变量被破坏的严重事件，而不只是普通可用性波动。展示价仍更新不能掩盖风险 owner 已经落后。

指标聚合标签宜限制为市场、源、模式和原因等可控集合，不把每个 `price_id`、账户或请求作为高基数标签。具体证据放在结构化日志和按权限可检索的审计记录里，链路使用稳定身份关联，并保护账户等敏感数据。量化监控覆盖不是采集越多越好，而是异常发生时能定位哪一段违反了契约。

“数字不变”也不等于源坏了，真实市场可能没有变化；“数字变了”更不证明真实。需要结合源序号、时间、场所状态和独立参考判断。监控可以建议暂停或报警，但新增价格规则与自动限制必须通过已定义的授权接口进入市场或执行控制序列，不能让监控脚本随意写 Mark。

## 第 6 层：1,500 ms 的期限怎样变成可测量的延迟预算？

**面试官：** 你监控剩余有效期。如果报价合格但每轮到执行时只剩几毫秒，你会怎样定义 SLO 和容量，而不是再把有效期随意调长？

**面试者：** 本例的授权期从预定采样 T 计到 `T+1,500 ms`，所以队列、计算、持久化、发布、消费和等待执行都会消耗同一预算。要分段量测 Tick 排队时间、聚合计算、事务提交、Outbox 交付、风险重算及执行等待，并看端到端尾延迟，不能只报告聚合函数平均耗时很小。

容量验证应在已声明的市场数、源更新频率、热点分布、消费者数及故障条件下测量，覆盖重连洪峰、慢数据库、慢消费者和 GC 暂停。先确认正确性，再报告吞吐、分位延迟、有效授权比例、队列最大年龄、丢弃或受限行为及资源占用。本题没有实测环境，不给出虚构的 p99 或每秒处理量。

可用性 SLO 的目标值需要按产品风险预算制定，不能直接把教学 1,500 ms 当成行业承诺。缩短服务延迟可以增加有效用价余量，调长期限则增大允许陈旧范围：源在采样时已可达 2 秒，执行晚 1.5 秒就可能接近 3.5 秒。若时钟漂移预算失控，连这个上界都不能可靠主张，应限制动作而不是只把告警阈值调宽。

监控本身还要有独立的活性检查。例如业务与指标出口一同停止时，“没有超时计数”不是成功；需要外部探测最近价格裁决和用价健康，确认告警链路仍能送达。报警的去重与抑制应保留根事件和业务影响，不因五个源同时失效而把市场级 HALTED 告警全部静默掉。

## 第 7 层：投诉错误强平后，怎样形成可信事故结论？

**面试官：** 这些告警都上线了，但用户仍投诉被错误强平。你拿到的日志时钟也有偏差，怎样确定影响范围和修复方式，避免凭一张价格截图判断？

**面试者：** 我先按业务稳定身份、单域序号和提交证据建立因果时间线，墙钟用于辅助展示并注明误差，不能拿不同机器毫秒时间简单排序决定谁先发生。先核对真实强平执行与成交，再查它绑定的风险决策、完整价格包、账户版本和最终复核；页面截图只能作为线索，不能替代这些权威事实。

影响范围也要分层：哪些轮次价格或模式出错，哪些消费者应用了它，哪些账户形成风险决策，哪些决定真正执行或结转。并非所有见过错误价格的账户都有经济损失，也不能只核对已经被用户投诉的账户。若只影响投影可重建，若影响未执行指令应撤销其资格或要求重算，若已经产生确定成交与经济分录，需要有权限的调查和补偿／冲正流程，不直接改余额抹掉原事实。

止损时按 R1 动作矩阵限制新增风险、划出及不具资格的自动强平，保留撤单、实到账保证金及符合执行约束的主动减仓。已经发生的债务和风险不会因为价格被改正而自动消失，要单独处理。恢复应有价格链路、消费水位、执行拒绝条件和账户核对证据；应急覆盖到期也不自动证明可以 ACTIVE。

事故报告应分开写确定事实、仍待验证的推断、止损动作、经济影响与后续改进。发现审计缺口就诚实说明不可证明的部分，不能用补采的今天数据拼成“当时我们肯定看见了”的历史输入，也不能把人工修复后的最终平衡当成原流程从未出错的证据。

## 第 8 层：怎样用事故资料改进规则，而不反复拟合同一组案例？

**面试官：** 你找到了首个错误点，也有历史事故集。团队说把阈值调到这些事故都不再发生就上线，你如何证明这不是只修好了昨天？

**面试者：** 我会先把不允许违反的条件固定，再比较可用性与风险代价。比如证据不足必须无效、超期不能授权、重放不重复产生资产动作，这些不是调参后可以接受的平均误差；而离群阈值导致的误停、平滑导致的反应延迟，则要同时衡量业务代价，不仅统计错价少了多少。

调参用的资料和最终验收资料应隔离，并覆盖不同时间段、不同流动性、真实整体跳价、单源异常、共同上游错误和全源失效。还要保留专门的边界向量与事故回归，避免新规则修复一例却破坏旧不变量。历史资料不能证明未来分布外和新型协同故障绝不会发生，结论应限定到已检验条件。

新规则先影子运行，在相同输入位置和经济状态上比较候选、指数、Mark、模式以及可能引起的准入和强平差异。反事实账户后果需要声明假设：真实订单和流动性不会因为重算自动保持不变，不能把静态重放盈亏当作确定的真实收益。任何不能解释、不能重放或在关键失败条件下更危险的规则，都不应因为平均价格误差更小就直接获得生产权威。

最后把修复落实成可验收事项：新增一个能够触发原问题的输入向量或故障场景，定义旧实现如何失败、新实现如何拒绝或收敛，记录版本与实际验证结果，再通过受控生效事件切换。回退也是改变未来规则的新事件，不删历史。复盘真正的产物是下一次能提前阻断的机制，而不是一句“加强监控”。

## 本题收束

**讲透的机制：** 规则、输入、持久状态、传播、经济版本和最终执行要分别验证，稳定身份与共同截止点将证据连成链；独立重算、故障窗口和业务监控各覆盖不同缺口。

**最容易答错的边界：** 哈希一致只证明一致，不一定证明正确；平均误差小不证明业务风险小；心跳和页面正常不证明源新鲜、风险已追平；历史回放不能再次获得线上副作用权限。

**反例与验证方法：** 构造价格生产持续正常、消费者漏收限制轮次且断线的场景。保持监控心跳和页面推送可用，让原 ACTIVE 包超过自身期限后再提交增仓请求。正确方案应在最终执行边界拒绝，而不是等监控告警后再补救；若请求仍成功，说明价格算法虽正确，用价资格链路仍未成立。这里描述预期验证，不声称已经执行。
