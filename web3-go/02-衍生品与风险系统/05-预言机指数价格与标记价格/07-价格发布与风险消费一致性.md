# 大问题 7：怎样保证价格、质量、权限和风险决策的端到端一致性？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、权益、强平 | 现金和持仓浮盈浮亏形成权益，权益不足可能触发强制减仓。 | 主例浮盈 12、权益 512，不改现金；判断与实际处置是不同事实。 |
| Index／Mark、完整价格包 | 外部参考价／风险估值，以及绑定数值、质量、模式和期限的交付单元。 | 不能从一个缓存拿新 Mark，再配另一个缓存的旧 ACTIVE。 |
| price_id、price_stream_id、round_seq | 稳定价格身份、所属价格流、流内业务轮次。 | 同一轮不因重发、换连接或切主而换身份。 |
| quality、FULL | 质量说明价格证据是否完整，FULL 是完整条件成立。 | FULL 仍可能处于恢复观察，不自动授权增仓或强平。 |
| mode、ACTIVE／HALTED | 模式说明允许哪些动作；ACTIVE 是正常，HALTED 是风险价停用。 | 无效包两价为空，不拿历史末次好价填当前字段。 |
| sample_time、usable_until | 采样时刻，以及这份包最晚授权到何时。 | 固定 T 后 1,500 ms，消息重投和重启都不续期。 |
| 共同事务、checkpoint | 一批状态一起落定，以及相应输入处理位置。 | 源、窗口、价格、模式、恢复计数和进度一起提交，不能半新半旧。 |
| Outbox、至少一次 | 与状态同事务保存待发记录，之后允许重发直到可靠交付。 | 防止提交后崩溃漏发，但不保证消息只出现一次。 |
| Inbox、幂等、摘要 | 消费端登记业务身份、内容及应用结果，重复不多产生效果。 | 必须与本地投影、进度、限制和任务登记共同提交。 |
| ACK、完成点 | ACK 是某个边界的确认，不是整条链路都完成。 | 数据库已提交、消息已接收、风险已应用、动作已执行分别确认。 |
| exactly-once、事务域 | 一次效果的承诺必须限定在哪个共同提交范围内。 | 本地 Inbox 不能天然让撮合、账本等远端服务也只执行一次。 |
| 连续水位、缺口追赶 | 记录已经连续处理到哪一轮，漏轮就补日志或受信任快照。 | 不能只取最大序号便宣称已经完整应用。 |
| 已知限制水位、门控 | 已知更高轮次已收紧权限时，先把限制落实到动作裁决。 | HALTED 先到但有缺口，也应先收紧；迟到旧 ACTIVE 不能复活授权。 |
| 受信任快照、衔接位置 | 可证明覆盖哪些状态的完整存档，以及后续从哪里继续。 | 可替换纯价格投影，不授权跳过历史形成的独立经济义务。 |
| 组合经济状态、因果一致 | 把有关联的仓位、现金和未完成事项按可解释顺序合在一起。 | 各服务各取“最新”可能漏亏损或重放抵押，记版本号还不够。 |
| pending exposure、在途义务 | 已形成但尚未全部结转的成交、预留、划出等风险。 | 从在途迁到正式状态时，按经济事件身份对账，避免漏计和重计。 |
| position／ledger／risk_rule version | 仓位、账本及风险规则版本，连同价格和在途版本绑定决策。 | 任一相关状态改变，旧决定都可能需要作废重算。 |
| decision_seq、动作身份 | 风险判断的顺序号，以及实际动作的稳定业务编号。 | 决策完成不等于动作完成，重试也不能另起身份制造第二次效果。 |
| 原子复核、检查后竞争 | 将资格校验与取得执行资格或效果绑定，避免检查后状态又变。 | 无保护地查完版本再调用远端，不算端到端原子保证。 |
| Reduce-Only | 只减已有仓位，不能越过零开出反向仓位。 | 两笔各卖 2 ETH 要按当前仓位和竞争执行量排序裁剪。 |
| 有界陈旧、权威屏障 | 前者只限制旧授权寿命；后者把限制纳入更强的统一执行边界。 | 未收到停用事件可能暂用未过期旧包，但已知限制必须立即生效。 |
| owner 任期、发布围栏 | 控制谁能提交与发布权威结果的写权机制。 | 未提交候选不得绕过 Outbox；切主不重置业务身份和限制。 |

## 把整篇文章压缩成一个故事

小林持仓的浮盈浮亏会改变保证金支持的权益，进而影响增仓、提现和强平。价格服务算出 Mark 2,006 还不算完成：若风险端拿到新数值却搭配旧权限，或强平时漏看已经到账的补款，正确价格也会导致错误动作。

生产端因此把窗口、价格包、模式、进度和 Outbox 一起提交。发布失败可以补发，消费者用稳定身份与摘要去重，并把 Inbox、应用结果和限制一起落地。发送成功不等于风险已应用，更不等于账户已经被实际处置。

消费者漏轮要追赶，但先收到权威 HALTED 时不能等补齐才停；它先记住更高限制，迟到旧 ACTIVE 即使未过期也不能重新授权。然后把仓位、现金、挂单预留和未结转成交组合成可解释的经济状态，而不是随手拼各服务最新值。

真正执行时，资格校验要与预留或经济效果在权威边界闭合。补款或减仓改变状态，旧决定就须重算。尚未收到停用事件时只能承诺有界陈旧；到原期限必须停止授权，不能拿可靠消息或原子指针宣称全平台瞬时冻结。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题覆盖价格裁决事务、Outbox 发布、风险 Inbox、连续消费水位、经济状态组合、风险决策及最终执行。核心不是承诺全平台同时切价，而是让每个完成点可解释：生产端共同提交什么，消费者怎样去重和追赶，已知限制怎样阻断旧授权，最后一笔业务效果如何与复核原子闭合。

**必要前提：** 严格沿用总览及 01 的链下订单簿、线性 USDC 永续合约和 R1。指数至少有 3 个合格源及 3 个独立分组，源年龄为 0—2,000 ms；盘口年龄为 0—500 ms，买卖两侧各至少 10 ETH；连续 30 个同规则一秒样本形成完整基差窗口，均值按 ±0.5% 限幅。价格包期限固定为 `T+1,500 ms`，不随消费或重发刷新。主案例为 `I=2,000、M=2,006`，2 ETH 多仓、入场均价 2,000、保证金现金 500。故障和并发场景均为独立变体，不叠加改变主案例；不另设超时或容量数字，也不将设计推演声称为工程验证。

## 第 1 层：为什么交付单元必须是完整价格包，而不是一个 Mark 数字？

**面试官：** 价格服务已经算出 2,006，直接把它发给风险服务不就够了吗？为什么还要一起发质量、模式、规则和期限？

**面试者：** 因为 2,006 只说明数值，不说明它有没有执行资格。在这个模型中，风险消费者收到的是完整价格包：`price_id、round_seq、index、mark、quality、mode、rule_version、sample_time、usable_until、input_cutoff、evidence_digest`。价格身份是 `price_id=(market, price_stream_id, round_seq)`，不能只按当前连接或消息投递编号识别一轮。

数值、质量和模式不能分开拼接。`FULL` 描述完整价格证据成立，但处于 `RECOVERING` 时仍不能开放增仓或自动强平；`DEGRADED_BASIS` 可以有候选 `M=I`，却只有受限权限；`INVALID_INDEX` 的本轮指数和 Mark 都为空，不能拿历史末次好价填进去。展示旧好价可以保留原时间与陈旧标签，但它不是当前授权。

因此消费协议的第一条是整包校验并整包应用：不能从行情缓存取新 Mark，再从旧模式缓存取 ACTIVE。本进程可以用不可变对象一次替换指针保证字段可见性，但权威身份和生效资格必须来自已提交价格结果；下一步要回答的就是这个“已提交”包含哪些状态。

## 第 2 层：价格包生效时，为什么窗口和 checkpoint 也必须一起提交？

**面试官：** 你说必须来自已提交结果。那我先把价格包写入数据库，窗口稍后落盘，checkpoint 最后推进，至少价格本身可靠了，为什么不行？

**面试者：** 因为下一轮依赖的不只是最后一个价格。R1 选一个关系数据库作为共同事务域，本轮把源候选与流身份检查状态、基差窗口、价格包、quality、mode、恢复计数、输入 checkpoint 和 Outbox 一起提交；事务还校验 owner 任期与预期前版本。计算阶段的候选不能提前覆盖权威状态或广播出去。

若只存价格，崩溃后可能重复追加同一个样本、漏掉恢复计数，或者从错误输入位置继续计算。共同事务让提交前失败回到上一个已提交状态，提交后失败则恢复本轮完整状态；无效轮次也提交 `INVALID_INDEX/HALTED` 与推进后的 checkpoint，不能因为没有数值就让消费者等不到限制事件。

数据库确认不明时，按稳定 `price_id` 和输入位置查询已有结果，重试仍使用同一身份；不能换号再算一轮。同身份只允许一个已提交载荷，发现异内容必须隔离调查。持久边界也要说清：普通单机提交不自动等于跨机器故障不丢已确认轮次，更不等于风险服务已经应用；数据库与消息系统之间还存在另一段故障窗口。

## 第 3 层：Outbox 怎样解决漏发，为什么仍然是至少一次交付？

**面试官：** 既然数据库和消息系统之间还有窗口，能不能事务提交后立即发消息，发送成功就算完成？Outbox 到底多解决了什么？

**面试者：** 直接“提交后发”会在提交成功、发送前崩溃时漏发；先发再提交则会暴露根本没生效的候选。Outbox 与本轮状态在同一事务里形成待发布事实，发布者只读已提交记录，重启后可以继续投递，所以不需要把数据库和消息系统假装成一个原子提交域。

但发送成功和写回已发送标记之间仍会失败：消息系统已经接收，发布者没记住，就会重发。正确承诺是至少一次交付，不能用 Outbox 宣称消息只出现一次。重发保持原 `price_id`、原载荷、原采样时间与原期限，投递尝试有自己的记录，但它不成为新的价格业务身份。

数据库已提交、消息系统已接收、风险单元已应用和业务动作已执行分别确认。生产端 ACK 只承诺声明的持久提交边界；消息 ACK 也不能证明账户已完成风险重算。若生产者能绕过已提交 Outbox 广播内存候选，这条旁路必须被封住或独立验证，否则消费者无法仅凭收到消息判断其权威性。

## 第 4 层：Inbox 去重怎样与应用原子绑定，而不是先记“收到过”？

**面试官：** 你接受至少一次，那么消费者加张去重表就够了吧？先把消息 ID 写进 Inbox，再更新价格缓存，重复消息直接丢弃，会有什么问题？

**面试者：** 先写“已处理”再应用，中间崩溃会永久漏应用；先应用再记去重，也可能重复触发后续效果。Inbox 应以稳定的价格业务身份去重，校验规范载荷摘要，并与本风险消费域的价格投影、消费进度、限制状态和必要的重算任务共同持久提交。不能用每次重投都会变化的 broker delivery ID，或用 owner 任期变化来把同一轮当成新业务。

同身份同内容重试返回已有应用结果，不重复推进水位或累加恢复次数；同身份异内容不采用“后到覆盖”，而是隔离并收紧依赖该流的授权。如果重算异步执行，事务可以可靠登记待重算任务，但必须同步推进使旧决策失去资格的门槛，不能因为重算还没完成就继续拿旧通过回执增仓。

消息确认应放在本地持久应用边界之后。这里的“效果一次”只覆盖这个事务域内的投影和任务登记，若后续要向撮合或账本发动作，还需稳定动作身份、独立幂等与执行协议；一张 Inbox 表不能跨服务提供天然的 exactly-once。并且去重只解决重复，下一条消息跨过了尚未收到的轮次时，还必须处理缺口。

## 第 5 层：发现缺口时怎样追赶，已知失效包又怎样立即阻断旧包？

**面试官：** 你说要处理缺口。如果较新的 HALTED 价格包先到了，中间少一轮，消费者坚持连续处理，那是不是只能等补齐以后才停？这时迟到的旧 ACTIVE 包还能重新授权吗？

**面试者：** 不能把等待连续应用变成延迟收紧权限的理由。我会区分“已连续应用到哪里”和“已经知道必须遵守的限制”。正常价格投影按固定价格流的连续轮次推进；发现缺口就请求已提交日志补齐，缺口未闭合时不开放依赖新价格的动作。较新的受信任 HALTED 或其他受限包一旦获知，立即在本地权威门控中登记其限制水位，并使较旧的 ACTIVE 决策失去执行资格。

这份已知限制与执行仲裁使用同一顺序或原子版本检查，不只是存在另一个后台缓存里。迟到旧包可以用于补齐历史，但不能降低已知限制水位，也不能覆盖当前模式；即使旧包自己的 `usable_until` 尚未到，也不能绕过已经获知的较新失效。解除限制只能依据后续按序验证、符合 R1 恢复条件的已提交结果，不能凭任意一个更大的 ACTIVE 标签直接解锁。

追赶可以读取原流的缺失轮次，也可以采用受信任的一致快照：快照必须给出市场、价格流、规则、覆盖位置、模式及衔接依据，随后从覆盖位置之后续接。价格流身份不能任意切换以清空水位；本地重启同样不能忘掉已知限制。快照可替换纯价格投影，不代表可以跳过历史轮次已经产生的独立成交、债务或其他经济义务。

所以消费者需要的是可恢复的进度与限制协议，而不只是一个最大序号。价格状态追上以后，风险单元还要证明自己采用的仓位、现金与在途状态能组成同一个可解释的经济状态，否则新价格照样可能生成错误动作。

## 第 6 层：怎样组合仓位、现金和在途义务，而不是各取“最新值”？

**面试官：** 你说价格追上仍可能判断错。假设仓位、账本和成交结转来自不同服务，我把每份数据各自的最新版本放在一起，版本号也都记录下来，为什么还不够？

**面试者：** 因为“各自最新”不保证因果关系一致。一笔成交可能已经形成经济义务，仓位投影先更新，现金结转还没到；若只记录版本号却不解释这段差异，仍可能少算亏损或重复释放抵押。风险单元要有组合经济状态的协议，明确各流已处理位置、成交到仓位及账本的关联身份，以及哪些义务尚在结转途中。

决策至少绑定 `price_id、position_version、ledger_version、pending_exposure_version、risk_rule_version`，并保存组合依据。未结转成交、挂单预留、正在执行的减仓或划出等，按动作性质计入在途敞口与占用；一个义务从 pending 迁移到正式仓位或现金时，要按稳定经济事件身份对账，原子或经明确衔接协议消除重计和漏计，不能只因某个服务说“已完成”就提前释放。

这个一致性单位是风险单元，不是全平台共享一个全球瞬时快照。在本例逐仓模型中仍需处理账户自己的关联经济流；若变成全仓或多抵押，还要重新定义组合范围，不能沿用本题公式。某个依赖缺口无法解释时，应收紧新增风险与划出，不把“最终总会同步”当作当前偿付能力证明。

一旦组合状态成立，风险 owner 才按该组版本生成带 `decision_seq` 的结果。主案例可得未实现盈亏 12、权益 512，并判断本轮不触发强平；这些仍然不是现金变更，也不是永久执行许可，接下来必须把决策与最终效果接起来。

## 第 7 层：最终执行复核怎样与动作原子闭合，避免检查后再变化？

**面试官：** 你已经让决策绑定整组版本。那执行端收到“风控通过”，先检查这些版本没变，再调用撮合或资金服务，是否就足够了？

**面试者：** 还不够，检查通过到动作生效之间可能再次变化。最终执行必须在风险单元权威仲裁序列中，把当前价格身份与期限、质量与模式、已知限制水位、经济版本、风险规则和动作幂等身份一起复核，并让“检查仍有效”和“取得执行资格或发生经济效果”形成不可被并发穿透的原子边界。

同一事务域可以通过锁定权威状态或条件更新，把版本校验与预留、扣减资格或记账共同提交；串行 owner 也必须让检查和状态推进位于同一权威顺序。只做无锁读取后调用远端 API 不构成这个边界。相关状态变化就让旧决策失败或重算，不能修改回执上的版本号来假装已经重新判断。

跨服务时不能凭空宣称一笔本地数据库事务锁住所有模块。应明确哪个服务拥有最终资格、如何发放有范围且可撤销或需再次验证的预留、撮合与资金端怎样幂等消费，以及失败时如何对账。对于仍以价格为前提的最终动作，旧预留不能绕开该执行点对当前模式和期限的检查；无法建立这一协议时，就不能承诺端到端原子复核已经实现。

因此执行回执应记录最终使用的价格和经济版本、限制水位、执行身份与结果。价格包应用、风险判断通过和实际成交或划出依然是不同事实；这一原子边界最需要用账户状态恰好发生变化的场景来检验。

## 第 8 层：补保证金和并发减仓到来时，旧决定怎样失效？

**面试官：** 你说账户状态一变就使旧决定失效。那强平决定发出后用户已经补足保证金，或者两笔 Reduce-Only 同时进入执行，具体由谁挡住旧动作？

**面试者：** 在补保证金的独立变体里，实际到账并被权威经济状态接纳后，现金或组合版本就推进；旧强平决定所绑定的版本不再适用。最终强平执行在同一仲裁边界发现版本不同，必须重新判断，不能凭“发出时确实需要强平”继续减仓。待确认转账不能当成补足，到账先后以权威接纳顺序为准；新获知的受限价格模式同样会使自动强平失去资格。

在并发减仓的另一独立变体里，当前为 2 ETH 多仓，两笔各卖出 2 ETH 的 Reduce-Only 不能各凭同一旧快照全量成交。最终撮合或执行按当前权威仓位与竞争中的执行量排序、裁剪或拒绝：第一笔全平后，第二笔不得反向开仓。入口标记 Reduce-Only、风险预检查和本地去重都不能替代这个最终裁决。

主动减仓还要满足用户执行价格保护、有可用对手方，真实成交原子结转损益与费用；不能顺带划出抵押、发放估值信用，或忽略其他在途义务。非 ACTIVE 时本模型暂停自动强平，但撤单和已确认到账的保证金仍可按事实处理，有条件的主动减仓也不依赖旧 Mark 授权。这不是保证偿付，成交可能暴露负现金与剩余债务。

这些变化进入同一个风险执行约束后，已知旧决策就不能继续生效。但如果生产端已经提交 HALTED，而该执行域根本没收到，单靠本地版本检查还看不到这件事，必须继续讨论期限究竟保证什么。

## 第 9 层：固定期限为什么只能保证有界陈旧，不能保证瞬时冻结？

**面试官：** 你承认执行域可能尚未收到 HALTED。既然每个包都有 `T+1,500 ms` 的期限，能不能对外说价格一失效，平台就已经全部冻结？

**面试者：** 不能。本模型是异步交付：生产端提交限制后，尚未知情的消费者可能在旧 ACTIVE 包到期前仍按旧资格执行，这是明确的传播窗口。期限阻止旧授权无限延长，不会让未收到事件的机器瞬间知道新模式。Outbox、Inbox 和原子快照都不能消除这段信息传播时间。

用价点独立检查 `sample_time ≤ now ≤ usable_until`，重发、查询、心跳和重启都不能刷新期限。运行时钟要有可靠的漂移监测，无法信任期限判断时就收紧动作。R1 的源年龄在采样时最多 2,000 ms，最后用价时最老合格源可能接近 3,500 ms；1,500 ms 是输出授权期，不是保证整个链路里的源数据永远不超过 1,500 ms。

同时要区分两种情况：尚未获知限制时，只能承诺预算内的有界陈旧；已经获知较新的失效包时，即使旧包没到期，也必须受限制水位约束，迟到旧 ACTIVE 不能复活授权。到期之后，依赖该包的增仓、划出和自动强平均不得继续，不能等待重算任务或连接恢复才停。

如果产品要求源失效提交与所有动作之间有更强的统一屏障，就要另行把限制纳入共同准入或最终执行序列，或在动作提交前取得权威围栏确认，并承担网络分区下的延迟与不可用代价。这是强化架构的独立变体，不是现有 R1 的期限已经提供了瞬时冻结。

## 第 10 层：消费者重启和追责时，怎样证明旧授权没有被复活？

**面试官：** 你区分了“尚未知情”和“已经知道”。那消费者重启后只加载最后一个 ACTIVE 缓存，或者动作重试时换了个请求号，怎样防止这些路径重新放行，又怎样查清责任？

**面试者：** 恢复必须加载共同提交的 Inbox、连续应用水位、已知限制、当前完整价格包、风险组合版本与在途义务，再衔接后续日志。历史 ACTIVE 包只是一条历史事实；不能因重启清掉限制水位，不能因重新投递重置期限，也不能把价格流任意换名绕过去。只有通过后续已提交结果和正常恢复条件，才有资格解除已知限制。

动作重试保留原始业务动作身份和载荷约束，先查询已经预留或执行的结果，再决定重试，不能仅靠新的网络请求号触发第二次效果。稳定身份要分别贯穿价格、风险决策和经济执行，但三者不是同一个完成点；价格应用成功不代表动作已执行，动作已执行也不能因重放价格被再次执行。

追责从实际动作身份反查：执行时使用的价格包及期限、执行域已知限制水位、组合经济版本、在途义务、风险规则、决策身份，再向前追 Inbox 应用、Outbox 发布和生产事务。这样才能区分生产裁决错误、传播尚在预算内、已知限制未落实、经济状态漏算，或执行检查后竞争。已经确定的成交和账本事实不能靠重算 Mark 直接删改，修复另走有授权的新经济记录。

本题给出的是协议与手工故障推演，没有执行工程验证。能成立的承诺应逐项限定：共同事务防半提交，Outbox 与 Inbox 支持至少一次下的幂等应用，水位和限制防旧包绕过，经济版本与原子执行防过时决策，期限只约束陈旧上界；不能把它们压缩成“消息可靠所以全局强一致”。

## 本题收束

**讲透的机制：** 一致性沿完成点闭合：价格状态、窗口、模式、checkpoint 和 Outbox 同事务；Inbox 与本地应用及限制共同提交；风险单元组合可解释的经济版本和在途义务；最终执行把复核与执行资格或经济效果原子绑定。跨服务保证必须有明确协议，不能由本地原子操作自动外推。

**最容易答错的边界：**

- Outbox 不是仅投递一次，Inbox 也不是跨所有服务的 exactly-once 保证。
- 稳定业务身份不随重发、切主或网络请求变化，同身份异内容不能覆盖。
- 连续水位负责追赶，已知限制负责立即收紧；等缺口补齐才能停用旧授权是错误设计。
- 记录一组版本号不等于组成一致经济状态，未结转与正在执行的义务不能遗漏。
- 最终复核后再无保护地远程执行，仍有竞争窗口；已经知道的失效不能被尚未过期的旧包绕过。
- 期限提供有界陈旧，不提供生产端提交失效后的全平台瞬时冻结。

**一个能检验方案的反例：** 独立乱序变体中，消费者尚持有有效期内的旧 ACTIVE 包，随后先收到更高轮次的权威 `INVALID_INDEX/HALTED` 包，但中间存在缺口。此时应先持久收紧限制，再追赶缺口；一个迟到或重投的旧 ACTIVE 包即使尚未到期，也不能让旧增仓或强平决定执行。若系统因为“旧包仍有效”“新包还没连续应用”或“重启清过缓存”而放行，说明已知限制没有进入最终原子裁决，而不是消息最终会补齐就能解决的问题。
