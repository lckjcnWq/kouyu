## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、权益、强平 | 持仓按价格估算浮盈浮亏，改变权益，权益不足可能强制减仓。 | 改一个价格阈值可能改变全市场账户风险，不是普通页面配置。 |
| Index／Mark、价格裁决 | 外部参考／合约风险估值，以及本轮按规则作出的结果。 | 源集合变了，指数、Mark、质量和权限都可能跟着变。 |
| R1／R2／R3、rule_version | 原规则、新规则、后续规则的不可变版本身份。 | R2 只影响生效位置之后；R3 可恢复 R1 内容，但不删除 R2 历史。 |
| 配置中心、热更新 | 分发运行参数的工具，以及运行中修改参数。 | 分发成功不等于价格权威已经按序生效，不能轮次中途偷换参数。 |
| 源名单、独立分组 | 允许谁报价，以及它们有哪些共同控制或依赖。 | 属于影响价格语义的配置，多接口不能自动视为独立。 |
| bps、离群阈值、时效 | 基点比例、偏离筛选边界、数据年龄要求。 | R1 为 100 bps 即 1%、源年龄最多 2,000 ms；放宽会改变候选集合。 |
| 规则载荷、规范化摘要 | 规则的精确内容，以及按约定格式计算的内容指纹。 | 版本名或一个可变 URL 不足以证明当时批准了什么。 |
| 审批身份、权限、审计事件 | 谁提出、谁有权批准、做过什么的不可覆盖记录。 | 不虚构审批人数，批准内容必须与实际生效摘要一致。 |
| 预定生效轮次、实际生效位置 | 计划从哪轮切换，以及市场顺序中真正提交在哪里。 | 审批通过与已生效是两回事，两者都要有证据。 |
| owner、Tick、权威顺序 | 市场负责人、定时采样事件，以及系统唯一解释先后的事件序列。 | 配置与报价、Tick 同序，边界前用 R1，边界后用 R2。 |
| 事件身份、幂等、冲突 | 标识一次变更；重复不多执行；相同身份异内容应拒绝。 | 不以重复消息推进第二次生效，不允许后到内容覆盖批准记录。 |
| input_cutoff、price_id | 本轮输入截止位置，以及价格包稳定身份。 | 让实际价格能反查是哪份配置和哪些输入产生的。 |
| 历史重放、实现语义 | 按历史输入与规则重建，包含当时的精度和计算顺序。 | 新代码仍要复现旧规则，不能用当前参数重算并覆盖旧价格。 |
| 连续 30 点、同版本窗口 | 同一规则下每秒一个、连续完整的基差样本。 | R2 生效后重新积累，不直接接入 R1 窗口，即使只改一个阈值。 |
| DEGRADED_BASIS／LIMITED | 基差条件不足，以及对应受限权限。 | 新版本窗口未齐而指数有效时，候选 Mark 取指数，不照常放行业务。 |
| FULL／RECOVERING／ACTIVE | 整包完整／恢复观察／正常授权。 | 窗口齐后仍须连续三个完整轮次，不能把单点合格当成全部恢复。 |
| 影子计算 | 新规则旁路试算，只看差异，不作生产裁决。 | 不自动获得写权，不自动让预计算样本和恢复计数迁入生产。 |
| 回滚、迁移策略 | 回到旧规则内容的新事件，以及获准的状态转换约定。 | 基线仍重建版本窗口；若另许复用样本，须另证兼容性并明确新语义。 |
| 职责分离、最小权限 | 不让同一权限包办所有操作，只给完成任务所需范围。 | 能重启采集器不代表能改源门槛，能审批不代表能任意写强平价。 |
| 应急授权、期限、退出 | 限定临时能力何时可用、何时撤销、怎样回归正常规则。 | 到期只撤权限，不自动把 HALTED 或 LIMITED 变 ACTIVE。 |
| 人工定价、新规则路径 | 人工输入价格若被允许，必须是明确另批的策略。 | 不能伪装普通预言机包，不能凭应急标记跳过范围、期限和执行校验。 |
| 经济事实、冲正、执行复核 | 已成交或已记账的事实，用新记录修错，动作前再核当前资格。 | 换规则不直接改历史现金或成本，事故须追到实际执行证据。 |

## 把整篇文章压缩成一个故事

小林的永续仓位靠保证金支撑，风险价格改变浮盈浮亏和权益，甚至影响强平。运营嫌 1% 离群筛选太严，想把配置中心改成 2%；工程师提醒，这会改变谁能进入指数，不是调一个无关紧要的开关。

团队先把精确规则内容固化为 R2，保存摘要、理由、范围、提出者和批准者，再让配置事件进入报价与 Tick 的同一权威顺序。批准不等于已生效，必须记录真正的轮次边界，价格包也携带对应版本，不能一轮用一半新参数。

R1 历史继续按 R1 重放，R2 不能覆盖旧价或删掉已完成成交。切换后按基线重建 R2 的连续窗口，完整后再过恢复观察；影子试算只提供比较证据，不自动拿到生产权限。上线不佳时，以新事件回滚，也不能抹掉 R2 曾经生效的事实。

值班人员可以获得限定范围和期限的应急权限，却不能任意改 Mark、刷新旧价或手工解禁。权限到期只代表临时能力结束，市场仍按真实数据恢复。若出现错误强平，就从执行结果反查批准摘要、生效位置、窗口和消费资格，修复另留新记录。

**流程位置与核心机制：** 本题位于价格规则、源配置、模式裁决与运行治理的交界处。重点是把每次参数变更作为有内容摘要、审批身份和生效轮次的不可覆盖事件；新规则不能回头改写 R1 历史，也不能靠回滚或紧急权限绕过恢复与审计。

**必要前提：** 本题沿用总览的链下 R1 主案例：五个配置源、至少三个合格独立分组、2,000 ms 源年龄、100 bps 离群阈值、每秒采样、30 点基差窗口和 ±0.5% 限幅。变更规则形成新版本 R2；R1 的历史裁决保持原样。审批人数、角色名和具体权限策略属于组织治理，本题只说明必要的分权边界，不虚构某组织的实际流程。

## 第 1 层：为什么不能在配置中心直接改一个阈值？

**面试官：** 运营发现 1% 离群阈值过滤太严，直接把配置中心改成 2% 不就好了？为什么要引入版本和流程？

**面试者：** 因为这个阈值会改变哪些源进入指数，进而影响价格、质量和业务权限。若计算过程读取可随时变动的“当前配置”，同一个 Tick 可能在不同实例得到不同源集合；重放历史时也会按新阈值重新解释旧报价。阈值不是普通展示开关，而是价格算法输入的一部分。

我会把规则视为不可变版本。R1 的源名单与独立分组、时效、离群条件、最小有效集合、平均和舍入、基差采样／窗口、限幅和有效期等内容组合成明确规则载荷，并有稳定的 `rule_version` 与内容摘要。系统只能在明确生效位置开始使用新版本，不能让一次热更新悄悄改变进行中的轮次。

因此变更的首要问题不是“参数存在哪”，而是“谁批准了什么精确内容、从何时起生效、怎样解释之后的结果”。这也决定审计记录必须引用实际生效的内容摘要，而不能只记录一个可能被复用的版本名称。

## 第 2 层：一次可审计变更至少要记录什么？

**面试官：** 如果参数版本号、操作者和时间都有了，是否足够复盘？源列表和生效时间还可以从当前配置反查吧？

**面试者：** 不够。审计事件要能独立说明被批准的内容和它如何进入市场顺序。至少记录规范化配置内容或其不可歧义摘要、变更前后版本、提出者与审批者的身份、各自权限及审批结果、理由和关联工单／事件、目标市场与范围、创建时间、预定生效轮次，以及最终被市场 owner 接纳并提交的生效位置。

配置载荷应覆盖会影响价格语义的字段：源身份和独立分组映射、市场与计价单位、时间阈值、离群算法与边界、最小源数、权重、精度／舍入、盘口资格、窗口和限幅、质量模式迁移及价格有效期。若只摘要一个外部可变 URL，之后无法证明当时内容；应保留不可变载荷或能校验其摘要的内容存档。

审批记录与生效事件是两种不同事实：审批通过不意味着价格 owner 已按序应用；已提交生效事件则说明了具体轮次采用的新规则。审计应能从批准的摘要追到生效事件，再追到受它影响的价格包和证据，而不能仅以操作者的聊天记录为证。

## 第 3 层：怎样让配置生效轮次进入价格权威顺序？

**面试官：** 审批后由配置服务广播 R2，多个价格实例订阅。怎样避免部分实例先用 R2、部分实例仍用 R1？

**面试者：** 市场 owner 必须把配置变更与报价、Tick 放进同一权威事件顺序。配置事件带有版本、内容摘要、审批证明或审批记录引用和预定生效轮次；owner 验证它有效后，在该轮次边界提交状态变更。轮次之前完整使用 R1，轮次之后使用 R2，不允许一轮中间换参数。

配置事件与轮次裁决应在共同提交边界上有可追溯关系。价格包明确写出 `rule_version` 和输入截止位置；故障恢复回放的是当时已提交的配置事件，而不是启动时重新读取“当前活动配置”。如果配置消息重复，按稳定事件身份幂等；内容相同但身份冲突，或同身份摘要不同，则拒绝覆盖并告警。

其他服务可以缓存配置用于展示或预计算，但不能因此成为价格规则的第二权威。如果 owner 尚未确认 R2 在指定轮次生效，发布者不得把 R2 结果标成已生效价格；配置分发的连接状态也不能替代权威轮次回执。

## 第 4 层：R1 已经产生的历史，怎样避免被 R2 回放覆盖？

**面试官：** 价格服务升级后用新代码重放过去输入，发现历史价格有差别。能不能把数据库旧价格覆盖成 R2 重算结果，让历史与当前规则保持一致？

**面试者：** 不能。历史轮次按当时生效的 R1 和其实现语义解释；R2 只适用于明确的生效位置之后。价格包及其证据应保留规则版本、源集合、输入截止位置和裁决摘要，历史审计记录不可被新参数覆盖。升级计算代码也要能复现旧版本语义，或明确标注无法重现，而不是悄悄套用新逻辑。

回放使用历史配置事件、已接纳输入、Tick 的固定采样时间和输入位置，不以新阈值筛旧源，也不取当前墙钟重算源年龄。若调查发现 R1 当时的结果确有错误，可增加有权限的调查、纠错或补偿事件并关联原价格身份；不能把“后来认为 R2 更合理”当成改写旧事实的理由。

价格历史与经济历史还要分开：更新价格规则不会删除已完成成交、修改入场成本或直接重写账本现金。需要修复已经产生的业务后果时，应通过独立的授权流程记录新经济事件，保留原始执行证据和修复原因。

## 第 5 层：R2 上线时，30 点窗口怎么处理？

**面试官：** R1 窗口已经有 30 个合格基差样本，R2 只改一个离群阈值。为何不能直接把旧窗口接到 R2 后继续计算，避免停在 LIMITED？

**面试者：** R1 的历史样本是按 R1 的源集合与规则资格形成的。即使本次改动看起来只触及离群阈值，它可能改变指数源集合和每个采样点的指数，因此基差也有不同解释。按专题规则，窗口不能混用规则版本；切换到 R2 后要从符合 R2 的有效单点重新积累完整 30 点窗口。

在窗口未完整期间，若当前指数有效，候选 Mark 退化为指数，质量为 `DEGRADED_BASIS`，模式进入或保持 LIMITED；指数无效则按 R1 进入 HALTED。窗口重新完整后，价格包质量可成为 FULL，但模式仍须遵守连续三个完整轮次的 RECOVERING 门槛。单点样本有效不等于整轮 FULL，也不等于自动恢复 ACTIVE。

可以在影子路径提前用 R2 计算候选结果，比较源筛选、指数、基差和模式差异，并为窗口切换评估影响。但影子计算不自动获得权威写权或业务生效资格；只有经批准的生效事件到达指定轮次，R2 才成为生产规则。

## 第 6 层：上线效果不佳时，回滚是不是把配置改回 R1？

**面试官：** R2 上线后出现异常，值班人员把配置中心的值改回 R1 就可以了吧？这样不是最快吗？

**面试者：** 这会让权威历史里的规则顺序消失，也可能让不同实例对生效轮次产生分歧。回滚应当是一个新的、经过授权的规则事件，例如新版本 R3 的内容与 R1 相同，但它有自己的内容摘要、审批、理由和生效轮次。它不会删除 R2 已经生效的轮次。

回到旧规则内容也不代表旧状态可原样复用。R3 按该专题的窗口规则重新建立对应版本的完整样本；未满足窗口和恢复条件前保持受限。若确有经批准的迁移策略允许重用经证明兼容的历史样本，也必须把兼容性条件和证据写入新的规则语义，不能在事故时临时口头认定。

紧急情况下可以有缩短审批路径，但路径仍需限定操作角色、市场范围、字段范围、有效期和理由，产生不可覆盖的紧急变更事件，并在之后完成复核。紧急通道不能拥有直接改写历史价格、任意指定 Mark 或跳过执行端校验的权限。

## 第 7 层：权限应怎样分层，应急权限到期后发生什么？

**面试官：** 事故期间让值班人员有管理员权限，等危险过去后自动收回，不是足够灵活吗？到期时间到了，系统能否直接恢复 ACTIVE？

**面试者：** 不能把运维权限和价格裁决权混在一起。职责应至少区分输入连接与采集运维、规则提出、规则审批、生产生效、审计查询和业务执行授权；能重启采集器不等于能变更独立源集合，能批准规则不等于能写入强平价，能看审计不等于能抹除记录。具体角色名称和审批人数由组织确定，系统需强制记录权限主体及其授权范围。

应急权限应绑定身份、市场、允许操作、起止时间、理由和关联审批，采用最小权限；撤销和到期都生成审计事件。到期的语义只是操作者不再有这项临时权限，不是系统自动把 HALTED／LIMITED 改成 ACTIVE。权限结束后，价格仍按当前规则、窗口质量、数据新鲜度和三轮恢复条件逐步裁决。

R1 不授予人工定价或绕过既定校验的权限。若另行批准人工价格或特殊动作政策，必须明确这是新规则变体，而不是临时管理员权限的自然延伸；独立定义来源、证据、动作范围、生效位置、期限及退出条件，并在生效前完成授权与审计。执行端必须识别这条已批准路径，校验其自身资格、范围、期限和当前经济状态，不能凭应急标记跳过 R1 校验或混用两套价格与权限。人工输入、消费者和实际执行身份应留有显式证据，不伪装成普通 oracle 价格包，也不声称拥有原自动规则的同一保证。

## 第 8 层：怎样从审计证据判断变更是否安全，事故怎样闭环？

**面试官：** 配置事件、审批和版本都有了，仍发生了错误强平。你怎样判断是参数设计问题、审批问题、切换问题还是消费者沿用了旧状态？

**面试者：** 从实际执行身份反查它使用的价格包、`rule_version`、价格期限、风险参数版本、模式和消费者水位，再追到该轮输入截止位置与配置生效事件。核对审批主体是否有权、批准摘要是否与实际载荷一致、实际生效轮次是否匹配，以及窗口是否含跨版本样本、模式是否按 R1 迁移、最终执行是否重新验证了价格资格和账户状态。

若输入和历史规则正确但 R2 逻辑本身不适合预期风险，问题在规则设计；若摘要与审批不一致，问题在审批／发布管道；若 R2 过早或半轮生效，问题在顺序与事务；若价格包已降级但执行使用旧 ACTIVE，问题在传播和消费端。先定位第一处不一致，再暂停相关权限、保全证据、限制依赖该结果的动作，避免直接覆盖配置或价格来消除表面异常。

**本题收束：** 每次变更应包含不可歧义的配置内容摘要、审批与操作身份、范围、理由、生效轮次和实际提交位置；R1 历史永不被 R2 覆盖，规则切换按版本重建窗口，影子计算不自动生效，回滚是新的规则事件。容易答错的是把配置中心热更新当权威、认为版本号能代替配置内容、把旧窗口直接接到新规则，或认为紧急授权到期就可自动 ACTIVE。

**反例：** R2 已在第 500 轮生效，随后操作员把配置字段改回 R1 并删除 R2 记录；服务重启后按当前值回放第 480 轮，得到另一个源集合，并将旧价格包标成新 ACTIVE。若系统仍允许这种结果，说明规则历史不可变、事件审批摘要或回放版本边界至少有一处没有真正约束权威状态。
