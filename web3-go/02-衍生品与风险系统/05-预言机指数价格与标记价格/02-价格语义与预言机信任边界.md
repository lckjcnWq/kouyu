# 大问题 2：最新成交价、指数价格、标记价格与预言机各解决什么问题？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、权益、强平 | 抵押现金加持仓浮动损益形成权益；不足以维持持仓时可能强制减仓。 | 用错价格会影响风险判断，但价格刷新本身不是现金收付。 |
| 线性永续、USDC／ETH | 无固定到期日、按价差计算损益的合约；USDC 是计价币，ETH 是标的。 | 本文价格单位为 USDC/ETH，不能把不同计价币的裸数混用。 |
| Last Price | 本市场最近一笔已经确定的成交价。 | 证明发生过一笔成交，不单独代表整个外部市场的合理价格。 |
| Index Price、I | 按规定来源和算法得到的外部参考价。 | 主例 I 为 2,000；它不是本地永续最后成交的同义词。 |
| Mark Price、M | 产品用来估算持仓风险的标记价。 | 主例 M 为 2,006，用于估值，不保证用户能以此价平仓。 |
| Oracle、预言机 | 将外部事实送入可信执行范围的机制。 | 不预测未来，也不天然等于某一种价格。 |
| 订单簿、条件单、触发 | 订单簿记录买卖意愿；条件单满足约定后才发起后续订单。 | Mark 触及阈值不代表已有对手方，更不代表按触发价成交。 |
| trigger_price_kind、trigger_once_id | 触发依据的价格种类，以及防止同一触发重复发生的身份。 | 只在明确增加条件单能力的变体中使用，不能默认主例已支持全部触发类型。 |
| 未实现／已实现盈亏、现金 | 未平仓估值与实际交易结转的损益不同；现金由账本确认。 | 浮盈 12 不先入现金；独立平仓变体的损益 -20 也不能与它重复结算。 |
| 签名、载荷、信任域 | 签名证明某授权身份签过这份内容；信任域限定它在哪里有效。 | 不证明市场真实；换链、换 feed 或换验证合约不能随意复用报告。 |
| API、多源、独立分组 | API 是数据入口；独立性看它们是否共享上游或故障依赖。 | 五个入口未必五份独立证据，配置分组也不是绝对安全证明。 |
| R1、中位数、离群 | R1 是本文规则版本；中位数居中；离群指偏离参照过大。 | 先按中位数筛一次 1% 离群，再查至少三源三组，最后等权平均。 |
| USD／USDC、单位转换 | 美元与稳定币不是无条件一比一；换算要按单位消去方向计算。 | 独立变体用 ETH/USD 除以 USDC/USD，不能把两个 2,000 视为同一报价。 |
| scale、舍入 | scale 标识整数价格的精度；舍入规定留下哪些小数。 | 单位和精度也属于价格契约，转换结果按原文六位向下取整。 |
| price_kind、price_id、rule_version | 分别回答哪类价、哪一包、按哪套规则生成。 | 风险接口接收完整 Mark 包，不接受任意正数冒充风险价。 |
| sample_time、usable_until | 前者是采样时刻，后者是本包可授权使用到何时。 | 本例期限是采样 T 后 1,500 ms，新收到消息不替旧源刷新年龄。 |
| FULL／DEGRADED_BASIS、quality | FULL 表示整包条件完整；后者表示基差条件不足。 | 两包数值相同也可能有不同资格，不能只比较 price。 |
| ACTIVE／LIMITED／RECOVERING | 正常授权、限制动作、恢复观察的不同模式。 | 质量恢复 FULL 也可能仍在 RECOVERING，不立即放开新增风险。 |
| 模式屏障、有界陈旧 | 屏障在执行序列中约束动作；有界陈旧只限制旧授权最长寿命。 | 消费者断线可能漏收停用状态，期限不等于瞬时全平台冻结。 |
| 影子计算、语义兼容 | 新方案旁路试算；语义兼容是经济含义一致，不只是字段一样。 | 影子结果不裁决生产，供应商或公式变更仍要受控版本和切换计划。 |

## 把整篇文章压缩成一个故事

小林看到持仓页按 2,006 显示浮盈 12 USDC，想立刻提现。客服先解释：保证金和浮盈共同影响权益，权益又关系能否继续持仓及是否强平；但估值上涨不是现金到账，Mark 也不是市场承诺给他的成交价。

工程师因此给三种价格分工：Last 记录本地最后成交，Index 提供外部参考，Mark 按规则估算风险。预言机只是运送外部事实的机制，不会预知价格。若另设条件单，必须写清用哪种价格触发；触发后仍要过风控和撮合，不能凭一个阈值制造交易。

采购说接五家 API、加签就安全了，工程师继续追问上游是否独立、签名覆盖什么内容、报价是否新鲜。外部源若报美元，还要用合格汇率转换，不能把 USDC 默认当美元。

最终消费者收到的不只是 2,006，而是带类型、单位、规则、质量、模式和期限的完整包。基差不足、恢复观察或到期时，数字看着正常也不能照常授权。以后换供应商或公式，必须明确新版本生效位置，不能拿同名字段掩盖经济规则已经改变。

**流程位置与核心机制：** 本题位于定价规则和模块接口的入口，解决“某种价格能够证明什么、支持什么动作、由谁裁决”的问题。聚合公式细节由第 04 题展开，本题着重防止不同价格及信任模型在接口和面试回答中被偷换。

**必要前提：** 沿用总览的链下 ETH-USDC 线性永续合约、逐仓风险单元与 R1 教学规则。主例 `I=2,000、M=2,006`，2 ETH 多仓、均价 2,000、现金 500；报价单位为 USDC/ETH。其他数字均为独立变体，不代表实时价格或目标平台参数。

## 第 1 层：为什么一个市场需要三类价格？

**面试官：** 最新成交价、指数价格、标记价格和预言机是什么关系？如果让你负责定义价格服务接口，你会怎样避免调用方把它们混用？

**面试者：** 我先按事实和用途区分：最新成交价描述本市场最近一笔确定成交；指数描述按指定源集合和规则形成的外部市场参考；Mark 描述按产品规则形成的衍生品风险估值。预言机则是把外部事实带入受信任执行域的机制，它可以传递原始报价或聚合报告，不天然等于其中某一种价格。

在本模型中，最新成交价用于成交行情，指数来自多源现货报价，Mark 在指数上叠加受限的平滑基差，参与未实现盈亏和保证金判断。它们之间有数据依赖，但没有“最后一个更新的数就是全业务通用价格”的规则。一个源的现货成交价可以成为指数的候选输入，也不能因此把整个指数叫作本地永续最新成交价。

接口不会只返回 `{price: 2006}`。至少需要 `market、price_kind、base_asset、quote_asset、scale、price_id、rule_version、sample_time、usable_until、quality、mode`，并能追到证据。还应让风险接口显式接收完整 Mark 价格包，而不是任意数值。这样能够在接入和执行处拒绝“拿 Last 冒充 Mark”，而不是只依赖变量名和开发者记忆。

## 第 2 层：价格类型正确，是否就能决定所有订单触发条件？

**面试官：** 你用类型区分了 Last 和 Mark。那止损、限价成交和强平是不是都应该统一用更稳定的 Mark，避免插针？

**面试者：** 不应该。风险估值、条件单触发和真正成交是三个不同决定。限价单能否成交由权威订单簿、对手订单及执行规则决定，不能因为 Mark 触及限价就凭空产生成交。条件单可以选择 Last、Index 或 Mark 作为触发依据，但这是需要在订单契约里明确的产品能力，本 R1 主模型没有默认实现全部触发类型。

如果增加条件单这个明确变体，订单应记录 `trigger_price_kind、trigger_rule_version、threshold、comparison、trigger_once_id` 等必要事实。比如 Mark 触发只产生一次后续订单意图，后续订单还须通过准入、执行保护和撮合；触发成功既不代表成交，也不保证按触发价成交。价格不可用时如何暂停触发、恢复时是否检查穿越，都要事先定义，不能用缓存旧价猜测。

强平同样不是“Mark 一到阈值就直接扣走仓位”。本例用 Mark 计算权益和维持保证金，满足规则才形成复核意图，最终执行处还要确认价格、模式和经济状态有效。更平滑的价格可能减少局部噪声，也可能延迟真实风险反映，所以不能把统一使用 Mark 当成所有动作都更安全的证明。

## 第 3 层：既然 Mark 不保证成交，未实现盈利能不能直接入账？

**面试官：** 你把触发和成交拆开了，但账户已经按 2,006 显示盈利。用户说自己有 12 USDC 盈利，为什么不能马上把它记成现金或提现？

**面试者：** 因为这里的 12 是持仓在指定 Mark 下的未实现盈亏，不是已经发生了新的结算事件。主例的现金仍是 500，权益是 `500+12=512`；价格事件既没有平仓，也没有产生一项由账本确认的现金收付。持仓数量和入场成本也不会因这个数刷新而变化。

实际减仓时，持仓和清算模块根据确定的成交价、数量、费用计算已实现损益，并与账本按约定共同结转。假设独立变体中全部 2 ETH 在 1,990 平仓且忽略费用，交易损益为 -20，现金变为 480；不能先把浮盈 12 当现金加进去，再只记 -20，留下重复获益。

产品可以允许某些未实现盈利支持后续保证金，或者具有定期盯市结算，但那是不同信用或结算规则，需要明确风险折扣、结算事件、对手方义务和划出约束。本模型没有这种现金结转能力。即便某种盈利可支持保证金，也不自动等于可提现额；订单预留、在途义务和偿付约束仍需进入最终划出判断。

## 第 4 层：只要预言机有签名，就能把这项浮盈当成真实吗？

**面试官：** 你说未实现盈亏依赖 Mark 的证据。如果我们给价格加上预言机签名，是否就解决了“这个价格可信不可信”，从而可以放心按它做风控？

**面试者：** 签名最多证明授权身份签过指定载荷，不能证明载荷对应真实市场，也不能证明多个签名者用了独立上游。还要检查签的是哪种价格、哪个市场、哪个规则、哪个时间，签名门槛与密钥权限如何管理，以及实际消费位置是否验证这些条件。

本 R1 主模型的信任基础是运营方配置的源、经鉴权的采集、确定的价格计算和受控发布，没有凭空增加链上去中心化保证。即使给同一运营方的输出加签，也只是增强传输和来源认证，不会把单方采集和规则治理自动变成多方共识。

如果明确改为链上签名报告模型，还要把 feed、链和验证合约等域绑定到被签内容，限制旧报告和错误域复用，并在业务执行时验证价格资格；这由第 11 题深入。该变体改变的是执行和信任边界，不会把“足够签名”“报告已上链”“市场价格真实”“业务已经结算”变成同一个命题。

## 第 5 层：签名不能保证真，多个源是否就足够？

**面试官：** 那就不用依赖单一签名，我们接五家 API。R1 也要求至少三源三组，是不是已经可以说不存在单点和操纵风险？

**面试者：** 不能。API 数量、组织数量、经济定价场所和上游数据独立性是不同维度。五个域名可能使用同一行情供应商，两个交易场所也可能共享停机依赖，配置中的三组只是我们对独立性的受控声明，不是运行时自动推导的安全证明。

R1 对当轮合格报价以中位数筛一次 1% 离群，再检查至少三源和三个独立分组，最后等权平均。这能排除主例中 2,400 的孤立报价，同时拒绝证据不足的情况，但不能抵抗多数源同向错误、共同计价币失真或采集层统一改写。即使五家都给相同数值，也可能是同一个共同故障传播到五个入口。

所以我会把承诺写成“在配置、源诚实性、时间和计算假设成立时，按 R1 给出可追溯参考”，而不是“指数保证绝对公允”。共同故障监测可以用不同供应路径的旁路参考和质量指标辅助，但旁路检测不自动获得修改权威指数的权限；若它触发业务暂停，应通过明确的受限动作契约，而不是在读取接口里暗中替换价格。

## 第 6 层：外部源报 USD，本地用 USDC，为什么不能直接当作一样？

**面试官：** 你提到共同计价币失真。如果最可靠的几家源只报 ETH/USD，而合约结算币是 USDC，直接把 2,000 USD 看成 2,000 USDC 行不行？

**面试者：** 不行，那是在没有声明的情况下假设 USDC 始终按一美元交易。要把源纳入本指数，必须采用显式单位转换规则；缺少合格汇率就不能把输入伪装成已经标准化的 USDC 报价。

例如独立转换变体中，ETH/USD 为 2,000 USD/ETH，USDC/USD 为 0.98 USD/USDC，则 ETH/USDC 为 `2,000/0.98≈2,040.816326 USDC/ETH`，按本例六位价格向下取整。若拿到的是 USD/USDC 的倒数表示，运算方向也要相应改变，不能只看字段名包含这两种资产就相乘。

转换后证据依赖两条价格流，其时效、身份、采样截止和规则都要满足要求；接入输出保留原始两值、单位、版本及计算关系。很多源共用同一个转换汇率时，还引入共同失效点，不能因为原始 ETH 报价来自不同场所就忽略它。R1 主案例已经标准化完成，以上不把新汇率数值叠加回 2,000／2,006 的主例。

## 第 7 层：单位对了、源也够，为什么仍要把质量和权限一同交付？

**面试官：** 现在我能判断报价种类、单位和来源了。调用方只接收经过这些验证的 Mark 数值，不接收复杂的模式状态，是否可以简化接口？

**面试者：** 会丢失决定能否执行的重要信息。在 R1 中，指数合格但基差窗口不完整时，候选 Mark 也有一个正数，且等于指数，但质量是 `DEGRADED_BASIS`、模式为 LIMITED；完整窗口刚恢复时质量可以 FULL，模式仍是 RECOVERING。仅凭价格为正，调用方区分不了这些情况。

因此数值、质量、模式、规则和期限必须共同发布并共同验证。ACTIVE 也不是永久许可：本例价格包的授权期限固定为采样 T 后 1,500 ms，源的年龄不会因收到新包被清零。过期后即使相同数值仍然看起来合理，也不能据其继续增仓、划出或自动强平。撤单、实到账保证金和受约束的主动减仓则按各自事实与执行规则处理。

传输断线还意味着消费者可能暂时不知道生产端已经 HALTED。期限只提供有界陈旧，不提供瞬时全局冻结；如果业务需要更强语义，要在实际准入或执行序列建立模式屏障，并解释同步失败时谁停止执行。把复杂模式删掉，只是把风险从接口里隐藏了，不是把问题解决了。

## 第 8 层：后续换预言机或换 Mark 公式，怎样保持业务语义稳定？

**面试官：** 你要求调用方严格验证这一包内容。如果以后换一家预言机，或者换成另一种 Mark 公式，是不是只要字段不变，消费者就不用关心了？

**面试者：** 要区分载荷结构兼容与经济语义兼容。字段仍叫 Mark，不代表采样时间、源信任、误差、失效条件和动作权限相同。把 30 点基差换成另一种风险价，会改变账户估值和触发行为；把链下采集换成合约权威报告，还会改变提交、重组与最终性边界。

变更必须产生受控规则版本与明确生效位置，消费者只接受自己已经支持的版本；遇到未知版本不能按旧规则猜着用。源、窗口和计算影响价格时，按 R1 的既定策略切换到新版本后重建窗口并恢复；历史 R1 轮次继续按 R1 解释，不用新公式回写过去的权益与成交。

如果由我设计上线验收，会用同一批历史证据同时跑新旧计算，比较源集合、窗口、最终价格、模式和潜在动作差异，而不是仅比两个价格平均差多少。影子计算不获得生产裁决权，切换仍需审批、执行端支持和回退计划。这样即使供应商换了，消费者知道自己接受的是哪份经济契约，而不是只有一个拼写没变的字段。

## 本题收束

**讲透的机制：** Last、Index、Mark 各有事实和用途，Oracle 描述输入信任机制；价格的类型、单位、来源、质量、模式和版本共同定义可用契约。

**最容易答错的边界：** 签名不证明市场真实，多源不证明经济独立，Mark 不保证成交，未实现盈利不自动结转现金；接口结构兼容也不代表风险规则兼容。

**反例与验证方法：** 给调用方两个同为 2,000 的候选包，一个 FULL／ACTIVE、一个 DEGRADED_BASIS／LIMITED。若系统只因为数值相等就允许后一包支持增仓或自动强平，说明它实现的是裸数接口，没有落实价格语义和用价资格。此为设计反例，不声称已经执行系统实验。
