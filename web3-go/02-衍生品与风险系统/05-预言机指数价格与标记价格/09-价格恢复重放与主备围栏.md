# 大问题 9：崩溃与主备切换后，怎样恢复同一价格历史？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
| --- | --- | --- |
| 保证金、权益、强平 | 价格影响持仓浮盈浮亏与权益，权益不够维持要求时可能强制减仓。 | 恢复错一段价格或权限，可能让账户被错误放行或处置。 |
| Index／Mark、价格历史 | 外部参考价／合约风险估值，以及每轮形成的裁决序列。 | 恢复目标不是找回一个最后 Mark，而是找回能解释下一轮的完整上下文。 |
| owner、状态机 | 市场状态负责人，以及按输入逐步推进的一套确定规则。 | 可变源状态、窗口、模式和计数都需要恢复，经济账本不归价格服务覆盖。 |
| 输入流、源流身份、序号 | 输入流记系统接受了哪些事件；源流和序号记外部源自身先后。 | 两层身份都要保存，源重连与 owner 切主不是同一件事。 |
| Tick、T、input_cutoff | 定时采样事件、固定采样时刻、输入截止位置。 | 历史按记录的 T 和截止前缀重算，不能联网重新采过去。 |
| 快照、一致位置 | 某个已提交位置上的全量状态，而不是各表分别挑最新行。 | 价格、窗口、模式和检查点必须对应同一可证明的状态版本。 |
| checkpoint、round_seq | 输入处理检查点，以及市场业务轮次。 | 检查点关联输入流和已提交价格；轮次不随重启或任期改变归零。 |
| 共同事务、前版本校验 | 一批状态共同落定，并拒绝基于错误旧状态继续提交。 | 源、窗口、价格、模式、计数、进度及 Outbox 同成同败。 |
| Outbox、已提交发布 | 与价格状态一起持久保存待发消息，发布者只发这些结果。 | 提交后崩溃可补发，未提交内存候选不能走旁路广播。 |
| 确定性重放、历史规则 | 相同可靠输入按当时算法重建相同结果。 | 不取当前墙钟或当前配置重解释过去，缺证据不能复制旧点补洞。 |
| ACK、提交边界 | ACK 是确认，必须说清确认到哪个持久层级。 | 本机提交确认不自动保证主机毁坏后也不丢。 |
| 已提交前缀、复制水位 | 连续可证明已生效的一段历史，以及副本持久到哪里。 | 接管依赖连续前缀，不能把多个副本的最新行随意拼起来。 |
| RPO／RTO | 故障后可能丢失的已确认数据边界／恢复服务需要的时间。 | 取决于复制与切换协议，不能由“用了数据库”直接推出零损失。 |
| 心跳、租约、网络分区 | 连通信号、限时权利声明、机器之间暂时无法通信。 | 可辅助选主，不代表旧主真的停止运行或写入。 |
| fencing token、任期围栏 | 把递增写权代次送到存储处，由实际写入边界拒绝旧主。 | 任期 8 生效后，任期 7 不能再提交新价格或 Outbox。 |
| 历史任期、当前发布权 | 一包当年是否合法提交，与现在谁能执行补发，是两层判断。 | 任期 7 合法提交的旧 Outbox 可补发，不因切到 8 就失去历史权威。 |
| price_id、price_stream_id、幂等 | 价格身份、所属业务流、重试不多生一份效果。 | 切主保持身份和原载荷；原包时间与期限也不变。 |
| 连续轮次、未提交候选 | 已提交序列连续，未提交计算不算一个对外生效轮次。 | 本基线不预留带空洞轮次，允许空洞须另有证明和消费协议。 |
| FULL／LIMITED／RECOVERING／ACTIVE | 条件完整／受限／恢复观察／正常授权。 | 实际窗口缺损才按规则重建，重启本身不强制清空仍完整的窗口。 |
| usable_until、当前授权 | 原包有效截止，以及现在执行动作的资格。 | 历史状态恢复不等于旧授权恢复，过期也不改写历史质量。 |
| 对账、故障注入、不变量 | 核对身份与效果、主动制造故障、检查始终应成立的约束。 | 应验证崩溃、双主、复制落后等路径；本文没有灾备实测结论。 |

## 把整篇文章压缩成一个故事

小林的持仓价格会改变浮盈浮亏和权益，严重亏损时可能强平。凌晨价格进程崩溃，值班同事想读出最后 Mark 就重启；负责人拦住他：同一个数背后，窗口、源序号或恢复模式不同，下一轮判断就可能不同。

他们先取一致位置的快照，恢复源候选、流身份、Tick、规则、窗口、模式、计数、价格和 Outbox，再接续可靠日志。历史只能按当时采样时间和输入截止重放，不能用今天行情填昨天缺口。每轮状态与检查点共同提交，确认不明时按稳定身份查询重试。

主机损坏还要核对复制水位：本机 ACK 并不自动承诺跨机器零损失。新主确认连续已提交前缀，再推进持久任期围栏，让旧主实际写失败，同时封住未提交候选的发布旁路。旧任期合法提交的消息仍可按原身份补发。

最后，恢复历史不等于恢复旧授权，原包期限不能刷新；完整窗口也不因重启本身就清空。若证据真有缺口，就保持受限并按规则恢复。核验需比较每轮证据、状态和权限，而不只是最终价格相同；未做演练就不能宣称灾备保证已验证。

**流程位置与核心机制：** 本题聚焦价格 owner 的持久状态、检查点、确定性重放、主备切换和已提交价格的可靠发布。核心不是只恢复最后一个 Mark，而是从一致输入位置恢复所有会影响下一轮裁决的状态，并让数据库写权限和发布权限都受任期围栏约束。

**必要前提：** 沿用总览的链下托管、每市场单写、固定一秒 Tick、R1 指数与标记价格规则、模式迁移及价格／窗口／模式／检查点／Outbox 同事务基线。价格数据库只承诺自身声明的持久提交边界；跨机器 RPO 由复制与故障转移协议决定。这里讨论的是设计机制，不声称已经实现或验证生产级灾备。

## 第 1 层：进程重启时，恢复的到底是哪一份状态？

**面试官：** 服务重启后，如果我只读出最后一个标记价格，再从新报价继续计算，不就能恢复了吗？为什么还要保存这么多状态？

**面试者：** 不够。最后一个 Mark 只是历史裁决的结果，不包含下一轮计算所依赖的上下文。要重建同一条价格历史，恢复材料至少要覆盖：截至某个接入位置的标准化输入及源身份、流 ID 和序号状态；每个确定的 Tick 及其采样时间、输入截止位置；当轮适用的规则版本；指数筛选所需的源候选；基差样本窗口及每点当时的指数、盘口和有效性证据；质量、市场模式和连续恢复计数。

还要保存已提交的价格包、业务 `round_seq`、输入检查点、owner 任期／写围栏状态和待投递 Outbox。检查点必须说明它对应哪个输入流位置和哪个已提交价格版本。否则可能出现“窗口已经推进但价格没有”“价格发布了却没有检查点”或“恢复计数凭空增加”的分叉。

因此我会把持久状态看成一个可解释的状态机快照，而不是一个缓存的价格字段。恢复目标是从快照覆盖的位置继续，重建后续权威结果；快照之前的成交、仓位和账本事实并不归价格服务所有，也不由价格恢复覆盖。

## 第 2 层：这些状态怎样保证来自同一个一致位置？

**面试官：** 源候选、窗口、模式、价格包和 Outbox 各有自己的表。若快照时分别查询它们，怎样避免读到不同轮次的混合状态？

**面试者：** 快照要对应一个一致的已提交位置，例如数据库事务提交序号或与输入日志对应的检查点。实现可以在一致性事务中读取全部状态，也可以用状态版本和输入位置校验后生成快照；关键是不能把不同提交时刻的表拼成一个貌似完整的快照。快照元数据应明确记录市场、价格流身份、最后已提交 `round_seq`、规则版本、输入截止位置和状态版本。

每一轮裁决仍按 R1 约定，在同一事务里写入源状态变更、基差窗口、价格包、质量与模式、恢复计数、检查点及 Outbox。事务校验前一状态版本和 owner 任期；任何一项写入失败就整体回滚。Outbox 只能描述已提交价格包，不能先广播候选再补数据库记录。

若数据库隔离级别无法提供所需的一致快照，就要显式采用版本校验、锁定或日志位置建立边界，不能用“备份任务很快”代替一致性证明。备份完成位置也必须与提交水位一起记录，后续日志从该位置连续衔接。

## 第 3 层：重放时如何得到确定结果，哪些东西绝不能重新采？

**面试官：** 有了快照，服务能不能重连行情源，拉当前报价，然后把它们塞进历史 Tick，尽快补齐窗口？

**面试者：** 不能。历史重放只能使用当时已可靠接纳的输入、已排序的 Tick、配置事件和实现所需的历史版本。重新采集网络行情会得到后来才到达或已经变化的数据；重新读取墙钟也会改变报价年龄和有效期限。两者都会把“恢复同一历史”变成“用今天的信息改写过去”。

Tick 必须带有固定的采样时刻 T、输入截止位置及规则版本；源记录保留当时的 `source_time`、`received_at`、序号和接入位置。回放按这些已记录的值执行 R1 的过滤、聚合、基差和舍入。运行时仍用可靠时钟检查 `usable_until`，但这只决定现在能不能用某个已提交包，不会重新计算历史包当时是否有效。

如果缺少某段输入、Tick 或实现语义，就不能靠复制最新源状态或复制旧基差样本填洞。应把缺口标为恢复不完整，限制用价并按明确流程补齐证据或重新建立窗口。重放可确定的是已接纳历史在既定规则下的结果，不是对外部市场真实状态的全知证明。

## 第 4 层：提交 ACK、已提交前缀与 RPO 分别承诺什么？

**面试官：** 调用方收到本轮成功 ACK 后，主机立刻损坏，备机却没有这条记录。是不是“已经提交”就意味着 RPO 为零？

**面试者：** 不是。ACK 必须说明自己承诺的持久边界。若只在单机数据库本地提交后应答，它至多说明本机事务达到该数据库的提交条件；不能推导整机或机房故障后仍能恢复。要承诺已确认轮次不丢失，复制确认条件、故障切换判定和 ACK 时机必须匹配，例如等待约定副本或多数派持久化后再确认。

备机可恢复的对象是连续的已提交前缀，不是若干表里“看起来最新”的行。需要明确复制水位和输入检查点如何对应，以及哪些提交已确认、哪些仍不确定。若调用方超时而提交结果未知，它按稳定轮次身份查询或重试；同一身份只能返回原载荷，不能在新主上再生成另一份结果。

RPO 描述故障后可能丢失的已确认数据边界，RTO 描述恢复服务所需时间。只有当复制协议、同步级别、故障检测和切主规则共同满足目标，才能对外作相应承诺。消费者收到价格包与生产者 ACK 也不同：ACK 不等于每个风险单元都已应用该轮。

## 第 5 层：新主接管时，怎样让旧主在实际写入处失去权力？

**面试官：** 通过心跳判定旧主失联，再给新主一个租约够不够？网络分区时旧主可能还在运行，它也可能继续提交或发布。

**面试者：** 心跳和租约可以帮助选主，却不能单独构成写防护。必须把递增的 owner 任期或 fencing token 带到实际持久写边界，并让数据库在每次状态事务中比较当前任期。新主取得任期 8 并推进数据库围栏后，携任期 7 的旧主即使仍活着，也不能写源状态、窗口、价格包、检查点或 Outbox。

新主只有在确认取得有效写围栏、恢复到可证明的已提交前缀并核对接续位置后，才产生新的权威 Tick。围栏不是只检查进程内的租约；如果最终存储没有拒绝旧任期写入，旧主仍有能力制造第二条历史。

发布旁路也要封住。发布者只读取已提交 Outbox，核验持久价格身份、原载荷和该记录在提交时的合法写权；当前发布者自身的运行权限与记录的历史任期分开验证。任期 7 已合法提交的记录，不因数据库围栏推进至 8 就失去历史权威性，未投递完成的旧任期 Outbox 仍可按原身份、原载荷和原期限补发。不能让旧主把未提交的内存候选直接广播、写另一条未围栏总线或绕过数据库保护；消费者仍校验身份、顺序、已知限制和期限，合法历史补发也不会自动重新获得当前用价资格。

## 第 6 层：切主后轮次序号、价格身份和恢复计数怎么处理？

**面试官：** 新主换了进程和任期，是否应该把 `round_seq` 从 1 重新开始？如果不重置，未提交轮次留下的序号空洞又怎么办？

**面试者：** `round_seq` 是单市场、固定价格流身份内的业务顺序，不能因为 owner 任期改变而重置。任期是写权世代，业务序号是价格历史位置，两者解决不同问题。新主从最后一个已提交轮次继续；`price_id=(market, price_stream_id, round_seq)` 保持稳定，消息重投仍指向同一价格事实。

本主基线只在共同事务中分配并提交业务轮次，已提交 `round_seq` 连续；未提交候选不消耗一个对外已生效的轮次，重试沿用原 Tick 与预期接续位置。输入位置、Tick 身份和价格身份要有明确关联，配置事件与模式裁决也能在该顺序中定位。若另设预留序号允许空洞的协议变体，就必须增加可验证的空洞／中止证明、追赶与审计规则，不能直接沿用本专题“发现缺口先补齐”的消费者协议。

恢复计数从快照和已提交后缀重建。重复处理同一 Tick 或重复投递同一 Outbox 不能把 `RECOVERING` 的连续合格轮次多加一次；发生不合格轮次则按 R1 清零或切换模式。切主本身既不重置计数，也不凭任期变化创造一次合格轮次。

## 第 7 层：恢复出最后一个好价格后，是否可以立即重新授权业务？

**面试官：** 快照能证明最后一个 Mark 是完整的，数据库也恢复了。服务一启动就把旧包重新发布成 ACTIVE，是不是能缩短停机？

**面试者：** 不能把恢复价格计算状态等同于当前可用授权。旧包的 `sample_time` 和 `usable_until` 不变，重发不能刷新它的期限。启动后要先校验输入检查点连续、当前源身份与流状态正常、指数证据达标、当前盘口与窗口满足 R1，并确认市场模式和消费者水位能支持相应动作。

旧包过期只撤销它现在的用价资格，不改写其历史 quality、生产端 mode 或历史样本资格，也不单独构成清空窗口的理由。新一轮仍按自己的输入和连续窗口裁决：指数有效但基差不完整为 `DEGRADED_BASIS`／`LIMITED`，指数不可用为 `INVALID_INDEX`／`HALTED`。实际缺口、无效点或规则切换使窗口不完整时，才按相应规则积累真实新样本，不复制历史值，也不把旧 Mark 当成新样本。仅从受限状态返回 FULL 时，首轮进入 `RECOVERING`，连续第三轮完整提交后回到 ACTIVE；若已提交状态本来是 ACTIVE，且接续各轮仍持续 FULL，重启或切主本身不强制重新恢复，但旧包到期前后都只能依其原资格使用。

风险执行处还需检查收到的价格是否在当前期限内、消费进度是否满足动作要求、仓位与账本状态版本是否仍匹配。这样恢复过程中页面可以展示历史末次好价，但新增风险、划出和自动强平不会仅凭历史包获得新授权。

## 第 8 层：备份不完整、日志断档或跨区切换时怎样判定能否接管？

**面试官：** 灾备演练发现备份存在，但某源流的日志少了一段，另一个副本却有最新价格行。是不是直接选时间戳最新的那份就行？

**面试者：** 不行。行的墙钟时间最新不代表输入前缀完整，也不代表窗口、模式和 Outbox 与它属于同一事务位置。接管前要核对快照检查点、复制日志连续性、最后已提交价格身份、Outbox 水位和 owner 围栏；无法证明这些状态衔接时，不能拼表挑最新值。

如果缺失的是可能影响某轮源候选、Tick 或配置排序的日志，就无法确定那轮到底采用了什么输入，应将恢复位置停在最后可证明的前缀，并按缺口规则重新补入有来源的事件或从可信状态重新建立窗口。旧消息迟到不能覆盖高水位，重放也不能把不确定数据伪装为已提交历史。

灾备方案需要在数据损失、服务可用性和风险动作许可之间明确取舍。高可用副本若无法证明提交连续性，宁可短暂保持受限，也不能把断档后的猜测标成 FULL；反过来，长期停摆也会积累市场风险，要有告警、人工升级和解除条件，而不是把“安全停机”当作没有成本。

## 第 9 层：怎样验证恢复协议没有制造双主或重放漂移？

**面试官：** 文档写了快照、任期和检查点，怎样证明实现没有遗漏？是否只要比对恢复前后的最终 Mark 一样就够了？

**面试者：** 只比最终 Mark 太弱。不同的源集合、窗口、质量或模式可能碰巧得到同一个数，却给出不同的业务权限。应从同一已提交输入前缀分别做连续运行和快照后重放，比较每个轮次的候选源、排除原因、指数、盘口证据、窗口、Mark、质量、模式、恢复计数、规则、期限、价格身份和 Outbox 载荷。

故障窗口要覆盖事务提交前崩溃、提交后 ACK 丢失、提交后发布前崩溃、主备同时存活、旧主晚提交、旧主绕过 Outbox 发布、复制落后、快照与日志不连续及重复消费。每个场景都要验证唯一权威结果、检查点推进、旧任期拒写、重复投递幂等和最终执行处的时效检查。

这些是验证计划和应满足的不变量，不是本次文档任务已经执行的故障测试。生产承诺应以实际演练记录、数据库和复制配置、故障注入结果及恢复审计为证据；仅凭代码结构或一次正常重启不能证明 RPO、RTO 和分区行为。

## 第 10 层：如何处理“已 ACK 价格丢失”或“旧主价格被消费”的事故？

**面试官：** 事故中，调用方有 ACK，但灾备没有那一轮；另一次又发现旧主断线后发出的包被风险服务消费。你会怎么定位和止损？

**面试者：** 先按价格身份、提交序号、输入检查点、复制水位、owner 任期、Outbox 状态、消费者水位和最终执行记录还原时间线。若 ACK 早于承诺的复制边界，这是 ACK／RPO 契约或复制配置问题；若围栏生效后旧主仍能让未提交候选或非法新计算进入受信任发布路径，则是发布旁路或提交证明验证的问题。旧任期历史上合法提交的 Outbox 在切主后补发并不构成违规，仍须遵守身份去重、顺序、已知限制和原期限；不能仅凭包里的旧任期或发送发生在切主之后就认定事故。两类真正违规都不能只用“主备切换有延迟”概括。

止损时冻结依赖不确定价格历史的增险和资金划出，保全不可覆盖的输入、事务和消息证据。价格服务在可证明的前缀上恢复；缺失轮次不能事后拿当前行情补写成历史。已执行成交和账本分录仍保留原事实，若产生损失，走独立的调查、授权修复或补偿流程。

**本题收束：** 机制上，恢复要重建源身份／状态、Tick、R1 规则、窗口、模式计数、检查点、价格与 Outbox 的一致前缀；主备围栏必须落到实际存储写防护和所有发布路径，业务序号不随任期重置，恢复后还要重新判断当前用价资格。常见误区是只存末次价格、用墙钟或网络重采历史、把本地 ACK 当 RPO=0、用心跳代替写围栏，以及认为数据库围栏自动保护了旁路发布。

**反例：** 旧主任期 7 在分区侧保留 ACTIVE 内存状态，新主任期 8 已把数据库围栏推进到 8 并提交 HALTED。若旧主因数据库拒写而无法写价格表，却能把内存中的新 Mark 直接发布到另一条总线，消费者仍可能把它当新价格使用。只有实际存储拒写、发布只读已提交 Outbox、消费端校验价格身份／期限及执行端复核共同成立，才能阻断这条旧主旁路。
