# 大问题 05：并发下单怎样原子检查并预占？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 单向逐仓永续 | 用一个带方向的合约数量记仓位，并用本风险单元专用现金支持它。 | 交易的是 ETH-USDC 合约，不交割 ETH，外部资金不自动补入。 |
| q、B、E | q 是净持仓，B 是已记账现金，E 是加上浮盈亏后的权益。 | 初始 q=2、B=E=1,000；这里现金和权益相等只是没有浮盈亏。 |
| IM、r、R | IM 是初始保证金要求，r 是比例；R 是持仓和普通挂单的保守总需求。 | r=10% 是教学值，O1 后 R=700，不是一笔七百的手续费或扣款。 |
| Q*、Qmax、Nmax、Mark | Q* 是最坏绝对仓位，Qmax 限数量，Nmax 限名义金额；Mark 是风险估值参考价，不保证执行价。 | 合计 4.5 ETH、9,000 USDC 超过本例 4 和 8,000，不能只查资金。 |
| O1、O2、并发 | 两个独立买单在时间上重叠到达。 | 各自单算能过，不代表把两份资格同时交出去也能过。 |
| check-then-act | 先看状态、过一会再修改，而这段空隙中别人也可能修改。 | 两请求都看到 q=2、看不到对方预占，就是超限来源。 |
| 原子检查并预占 | 检查候选与保存其执行义务形成不可拆开的业务结果。 | 不是先返回通过，再异步补一张预占记录。 |
| 活动订单、风险聚合 | 活动订单保留真实剩余义务；聚合是便于快速计算的汇总。 | 汇总可由明细重算，不能明细丢失后把义务当零。 |
| marketSeq、全序 | 给所有相关命令一个共同先后编号。 | O1 在前时，O2 必须在已经计入 O1 的状态上判断。 |
| RECEIVED、appliedSeq | RECEIVED 只说明请求已保存；appliedSeq 表示业务已经处理到哪里。 | 排到序号不等于保证风险通过，更不等于成交。 |
| owner、ownerEpoch、fencing | owner 是当前处理者，epoch 是任期，fencing 是阻止旧任期继续写。 | 主备切换后，旧进程即使没停，也必须在数据库提交时被挡住。 |
| 控制行、行锁、条件更新 | 用共同数据库记录协调处理权，锁住或核对前置值后才更新。 | 只锁各自新订单不够，两张订单原本没有共享订单行。 |
| PostgreSQL 事务 T | 数据库将相关业务记录作为一组共同保存。 | 订单、预占、结果、处理位置及涉及的成交经济效果要一起成立。 |
| RequestKey、唯一约束 | 一次请求的稳定身份及数据库禁止重复保存该身份的规则。 | 同一个 O1 重试不会再占一份 1.5 ETH 义务。 |
| payloadHash、规范化载荷 | 将价格、数量等业务内容统一表达后生成内容指纹。 | 同键数量从 1.5 改 1 是冲突，不是原请求的安全重试。 |
| COMMIT 未知 | 提交确认丢失，可能成功也可能未成功。 | 先查权威结果，不凭 HTTP 超时认定失败并重跑。 |
| 工作副本、内存订单簿 | 前者用于提交前试算，后者用于快速查已提交订单。 | 二者不是第二个权威提交点；提交未知不能继续用草稿撮合。 |
| Outbox、事件 ID | 同事务保存的待发送通知及通知的稳定身份。 | 重发回报不重做成交；进程崩溃后仍能继续交付。 |
| goroutine、mutex、channel | 分别是 Go 并发执行单元、进程内锁、进程内传递消息的通道。 | 都不能单独证明跨实例互斥、掉电恢复或持久受理。 |
| token、TTL、墓碑 | token 是执行凭据，TTL 是有效时长，墓碑是持久关闭记录。 | 拆服务后凭据到期不证明执行端已停，必须确认关闭并防迟到。 |
| 线性化、串行化业务结果 | 对外能把重叠操作解释为某个明确的一前一后结果。 | 关键不是让每段计算都不并行，而是不交出彼此冲突的执行资格。 |
| 故障注入、恢复重放 | 主动制造断连或崩溃，再依据持久记录恢复，用来检验承诺。 | 文中是验证方案，不是已经跑过的测试成绩。 |

## 把整篇文章压缩成一个故事

甲持有两个 ETH 永续多仓，权益一千，数量上限四个。两个入口几乎同时收到买一点五的 O1 和买一个的 O2。各自看旧状态时，前者最坏三点五、需求七百，后者最坏三、需求六百，都显得安全；一起获准却会到四点五，越过数量与名义限额。

解决办法不是再加一遍余额查询，而是让请求进入共同的持久顺序。O1 在前，就把检查结果、订单余量和预占一起提交；O2 随后必须看到它，算出拟四点五并拒绝。预占只占风险空间，现金并没有减少。进程内一个 goroutine 能排队，但另一台机器和重启后的进程仍要由数据库任期与处理位置约束。

如果 O1 已提交却没收到回包，同键重试只找回原结果；若提交是否成功不明，市场暂停并查证，不能赌一次重做。内存簿和通知也只认已提交事实。这样无论并发还是故障，都只存在一份订单义务；把服务拆开后，凭据到期更不能冒充执行端已经关闭。

[返回专题总览](README.md)

**范围与前提：** 本题覆盖同一账户、ETH-USDC 线性永续、单向逐仓下普通订单的并发准入。沿用 README 的唯一裁决事务 T：订单、风险聚合、双方仓位/账本（若立即成交）、命令结果、处理位置和 Outbox 在同一 PostgreSQL 事务提交；不切换为 Risk/Matching token 双架构。固定初始 `q=2、B=E=1,000、m=2,000、r=10%、Qmax=4、Nmax=8,000`，O1 买 1.5，O2 买 1。

**流程位置与核心机制：** 交易前检查到执行资格建立之间。重点是检查与预占必须是一个串行化业务结果；数据库提交提供持久原子性，Go 单线程或进程内锁不能单独提供跨实例、重启后的保证。

## 第 1 层：两笔各自通过，为何合起来会超限？

**面试官：** O1 和 O2 几乎同时到达，若它们各自读取同一初始仓位并都通过，会发生什么？

**面试者：** 初始仓位是 2 ETH，数量上限是 4。O1 单独申请 1.5 后最坏仓位为 3.5，可以通过；O2 单独申请 1 后是 3，也可以通过。但若两单都接纳，合计买单余量是 2.5，最坏仓位变成 4.5，已超过 Qmax，名义敞口也到 9,000，超过 Nmax。问题不在公式，而在两次检查都没有看到对方创造的义务。逐仓权益是 1,000，两单单独估算 R 分别为 700 和 600，表面都够钱；这说明现金检查不能替代共享数量限额，准入必须将候选订单放进已有活动义务后再裁决。若把两笔并行请求都按“当前仓位不超过4”直接返回通过，服务可能只在后续成交时才发现合并暴露超限，但那时订单已获得执行资格，风险约束已经迟了一步。

## 第 2 层：怎样定义“原子检查并预占”？

**面试官：** 既然两次并发读取会看到旧状态，你说的预占到底是什么状态？

**面试者：** 预占不是扣现金，而是把获准订单的剩余执行义务写进活动订单与风险聚合。O1 接纳后，`b=1.5、Q*=3.5、R=700`，现金仍为 1,000。检查候选 O2 时必须读到 O1 已提交的余量，计算拟态 `b=2.5、Q*=4.5、R=900`，因此因仓位和名义限额拒绝。检查、订单创建和聚合变化不能分成三个独立步骤。若接口只返回 300 USDC 的“可用缓冲”却没有保存订单身份，后续撤单便无法准确释放对应义务；因此预占应能追溯到订单剩余量，聚合只是可重算索引。订单状态从未接纳到活动、部分成交、终态撤销时，分别保留拒绝原因、filled、remaining 和 canceled；由这些权威量重算聚合，可以在崩溃恢复后检出缓存聚合与订单明细不一致。

## 第 3 层：并发请求通过什么权威顺序裁决？

**面试官：** 如果订单创建与风险聚合同事务，两个数据库事务仍可能同时读到 2 ETH，顺序由谁决定？

**面试者：** 单市场命令先持久受理并分配 `marketSeq`，有效 owner 只应用 `appliedSeq+1`。事务 T 锁定市场控制行并检查 `ownerEpoch`，再按顺序处理命令。若 O1 是较早命令，就先提交其预占，随后 O2 从更新后的工作副本计算并拒绝；顺序不能由 HTTP 到达时刻、Go goroutine 谁先抢到锁或数据库查询返回快慢隐式决定。两个请求即使不同入口、由不同实例接收，也按已分配的命令序号进入同一队列；受理序号提交与业务应用位置分开，允许显示 RECEIVED，却不提前承诺风控通过。序号分配必须自身原子，不能两入口都拿到同一位置；应用事务遇到序号缺口则等待前项，不跳过失败命令，否则后续风险快照就没有确定前态。

## 第 4 层：序号、锁和事务各自解决什么？

**面试官：** 既然有 `marketSeq`，为什么还要事务锁和 owner epoch？

**面试者：** 序号给出业务命令的全序；事务锁和条件更新让提交者不能越过 `appliedSeq+1`，owner epoch 则隔离已经失去所有权的旧实例。T 在同一数据库事务内读取控制版本、检查、写订单及预占、保存决定、推进处理位置和写 Outbox。序号本身不互斥，锁本身也不证明持久顺序；三者职责不同，需共同落实到可恢复提交记录。举例说，旧 owner 即使仍认为 O2 该执行，也必须因 epoch 不匹配而更新零行并停止；不能只靠租约心跳告警后继续写入。锁定控制行后还应校验状态版本与参数/价格激活序号，只有事务提交才让新的 `appliedSeq` 可见；不能先在内存推进游标，失败时再期待数据库补齐。

## 第 5 层：请求超时重试如何避免第二次占额？

**面试官：** O1 的事务已提交，但 HTTP 回包丢了，客户端重试会不会再插入一张订单？

**面试者：** 受理时用账户作用域内的 `RequestKey` 唯一约束，并保存规范化载荷摘要、命令身份和原结果。相同键、相同载荷只返回原命令状态，不再次执行；相同键但数量或价格不同则返回冲突。若业务命令序号因重试流程再次出现，它只能引用既有裁决并推进处理，不得重复增加 1.5 ETH 余量或重复生成成交。请求键要在足以覆盖客户端重试、队列积压和恢复窗口内保留，不能用短 TTL 到期就删除；否则旧网络重投可能被误认成全新订单。对相同键载荷冲突也要保存并返回稳定冲突结果，避免客户端更换数量后借同一请求身份绕开限额重试；订单 ID 与客户端键应有明确映射。

## 第 6 层：事务失败或提交结果未知时怎么办？

**面试官：** 如果数据库在提交附近断连，服务不知道 T 到底提交了没有，能否直接重跑计算？

**面试者：** 不能凭连接错误猜测回滚。先按命令身份查询持久结果和 `appliedSeq`：若结果存在，就应用已提交状态并复用响应；若明确未提交，才以同一身份继续；暂时无法判定则暂停该市场后续命令。T 提交前崩溃时订单与预占一起回滚，受理命令仍待处理；提交后崩溃时结果、状态和 Outbox 已共同存在，恢复不能再造一次效果。恢复还要检查订单聚合版本和处理游标吻合，若持久结果查不到但复制尚未追平，应等待权威存储确认，不能以本地缓存猜未提交。只有明确确认未应用时才回放命令；发现序号已推进但结果缺失属于存储/不变量异常，应隔离市场并审计，不能跳过或重造。

## 第 7 层：为何 Outbox 和内存订单簿也必须受提交约束？

**面试官：** 事务提交成功后进程还要更新内存簿并通知客户端，若此处失败，会不会破坏刚才的原子性？

**面试者：** 内存簿是已提交状态的索引，不是第二个权威提交点。提交后按序应用变更；进程若在数据库提交后、内存更新前崩溃，恢复从持久订单和处理位置重建。Outbox 与业务结果同事务写入，异步发布可重试但带稳定事件 ID。回报暂时延迟可以接受，不能为追求即时页面更新而在提交前发布未确定订单或成交。内存应用也要记录最后应用的 marketSeq，遇到重复序号跳过、发现缺口则暂停并重建；这样数据库耐久事实与热路径索引才不会悄悄分叉。Outbox 消费失败只影响通知，不得回滚已提交成交；若簿更新失败则停止撮合读取该簿并重建，不能先让新订单按不完整深度匹配。

## 第 8 层：Go 单线程或单实例锁能否替代数据库裁决？

**面试官：** 你用持久事实恢复内存簿；如果再用一个 Go goroutine 串行访问它，能否省掉数据库锁、序号和 epoch？

**面试者：** 单 goroutine 可简化单进程内存状态的并发访问，却不解决进程重启、第二实例误接管、请求超时重放和持久化原子性。单实例锁只在该进程存活时有效；重启后锁消失，旧主也可能继续向数据库写入。因此至少要有持久命令位置、事务内条件更新和可校验的 owner epoch；Go 的串行执行是优化与局部约束，不是耐久或跨实例共识。比如进程先向客户端返回“已接纳”但订单只在内存 map 中，机器断电后这个承诺无法恢复；正确回执必须区分已持久 RECEIVED 与 T 已提交的准入结果。即便单进程服务只有一个 goroutine，数据库提交也要确认所需的复制耐久级别，不能把函数返回或 channel 已发送视作掉电后可恢复。

## 第 9 层：拆分 Risk 与 Matching 服务会缺少什么保证？

**面试官：** 你要求持久顺序和跨实例原子提交；若为扩容明确改成独立 Risk 与 Matching 服务，各自提交再发消息能保住这些保证吗？

**面试者：** 这是显式架构变体，不再拥有本题事务 T。Risk 单独返回 token 后，仓位、价格或订单可能先变化；Matching 仍可能按旧 token 成交。token 必须绑定账户、市场、数量和状态版本，但 TTL 到期只说明风险服务不再承认它，不能证明执行域已停止消费或已有命令已退出队列。要由执行域按同一市场顺序提交关闭确认，并持久写入 token/意图墓碑；任何迟到的 token 命令先查墓碑并拒绝，在途成交也须先纳入覆盖或明确结清，才能释放额度。否则分域协议丢失“状态与资格一次提交”的保证，不能只加 Kafka、重试或补偿就宣称等价。即使 token 在到期前抵达，撤销与成交若竞争也须由执行域排序，确认关闭后才可退回风险额度。

## 第 10 层：用什么反例验收原子预占和恢复？

**面试官：** 你说拆域不能直接等价于 T；那回到原基线，怎样用提交点两侧的反例验证“状态与资格一起提交”确实成立？

**面试者：** 并发提交 O1 买 1.5 与 O2 买 1，确定 O1 先序列化后，唯一合法结果是 O1 活动、O2 因 `Q*=4.5` 拒绝；不得两单均通过。再在 T 提交前后分别杀进程，检查订单数、预占、结果、Outbox 与 `appliedSeq` 要么全无要么全有；同键重放不得增加义务。收束机制是“唯一顺序＋事务提交＋可重放身份”；易错点是把 cash 当预占；反例就是两次各读旧 q=2。还应在旧 owner 恢复后故意提交一次，确认 epoch 条件使其失败；若它仍能写入第二份订单，说明 fencing 只存在于应用内而非权威提交边界。对额度索引做故障重建时，还要从 O1 的剩余订单明细重算回 Q*=3.5/R=700，而不能把预占表空缺解释为无风险义务。

## 机制、易错与反例收束

- **机制：** 同一 `marketSeq` 顺序内完成检查、订单与预占、结果和处理位置的事务提交；用持久身份应对重试，用 epoch 隔离失权 owner。
- **易错：** Go 单 goroutine、进程锁、风险服务 token 或 TTL 都不等于持久的跨实例原子性；分域时必须执行域按序关闭并写迟到墓碑。
- **反例：** O1 与 O2 都只读到 q=2，分别通过后合计 Q*=4.5、N=9,000；若两张仍活动，原子预占没有成立。
