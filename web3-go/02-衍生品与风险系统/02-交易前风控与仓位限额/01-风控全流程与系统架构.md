# 大问题 1：一笔订单怎样完成风控、执行与风险收尾？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| ETH-USDC 线性永续 | 用 USDC 计价、计算盈亏，交易的是 ETH 价格变化对应的合约，不是购买并提走 ETH。 | 买入 1.5 ETH 合约不等于从现金支付 3,000 USDC 本金。 |
| 多仓、单向净持仓 q | 多仓随价格上涨获利；单向账户用一个带正负号的数量表达持仓，多为正、空为负。 | 甲从多仓 2 ETH 变为多仓 2.5 ETH。 |
| 逐仓风险单元 | 给某个市场的仓位划出专用资金和风险边界。 | 本例只认专用 USDC 现金桶，外面的钱不自动补进来。 |
| 全仓共享预算 | 多个仓位按规则共用一个抵押资金池，不是所有账户的钱都能随意用。 | 本文不实现全仓；拆成多个市场时不能各自重复使用同一共享池。 |
| 账本现金 B、权益 E | 现金是已记账余额；权益还计入当前持仓尚未兑现的盈亏。 | 主例没有浮盈亏，二者恰好都是 1,000，不代表永远相等。 |
| IM、MM | IM 是建立持仓所需的初始保证金要求，MM 是维持持仓的最低保证金要求；都不是手续费。 | 本例原持仓 IM 为 400；不能把开仓检查与后续风险处置混为一谈。 |
| 风险总需求 R、可用空间 | R 是支持现有仓位和未成交义务需要留下的风险预算；本文可用空间是权益减 R。 | O1 挂单后 R=700，可用空间为 300，但现金仍为 1,000。 |
| O1、O2 | 两个不同的下单请求，不是同一张单的两次重试。 | O1 买 1.5 ETH，O2 另买 1 ETH；后者必须计入前者的义务。 |
| 受理、接纳、执行 | 受理是保存请求，接纳是允许订单进入活动状态，执行才是发生实际成交。 | 入口收到了请求或风险通过，都不能直接报告成交。 |
| 风险预占 | 提前把未成交订单可能用掉的额度算进去，防止被另一笔请求重复使用。 | O1 新增 300 风险需求，不是提前扣掉 300 现金或确认损失。 |
| Mark、价格与配置版本 | Mark 是用于风险估值的参考价格；版本说明用了哪份价格和规则。 | Mark 不是承诺成交价；价格或规则更新会使旧批准失效。 |
| 共同权威顺序 | 所有会影响该市场风险的动作按同一条可查顺序处理。 | 撤单和成交谁先成立，由这条顺序决定，不由页面先显示什么决定。 |
| 协调层、逻辑所有权 | 各模块负责各自计算，协调层负责让相关结果一起成立。 | 风控不能擅自扣现金，账本不能自行宣布订单已撤。 |
| 业务事务 T、原子提交 | 将一组业务修改打包保存，要么一起生效，要么一起不生效。 | 订单余量、双方持仓、账本和风险变化不能各成功一半。 |
| 撮合、双边门禁 | 撮合寻找价格可匹配的买卖单；门禁在成交前检查两边是否仍有资格。 | 甲合格不代表对手方也合格，任一方不合格都不能生成该笔成交。 |
| 部分成交、剩余量 | 一张单只成交一部分，没成交的部分继续承担未来执行义务。 | O1 成交 0.5 后还余 1，风险从订单转向持仓，不是消失。 |
| 权威撤销 | 负责执行的系统已经确定订单余量不能再成交。 | 撤单请求发出不算完成，确认撤余 1 后 R 才降到 500。 |
| CloseIntent、关闭墓碑 | 持久保存“不要再执行这个意图”，即使订单还没出现也留下禁止记录。 | 关闭先到时，迟到的下单不能重新创建订单。 |
| COMMIT、结果未知 | COMMIT 是提交数据库事务；确认消息丢了，只能说不知道是否成功。 | 超时不能直接认定失败，更不能立即释放预占。 |
| owner、epoch | owner 是当前有权处理市场的实例，epoch 是它的任期编号。 | 新实例接管后，存储层要挡住旧任期继续写入。 |
| Outbox、查询投影 | Outbox 是同事务保存的待发通知；投影是由已提交事实生成的查询或页面视图。 | 通知可以晚到、重发，不能因此再成交一次或反改权威状态。 |
| RPC、context | RPC 是跨服务调用；context 常用于取消一次调用的等待。 | 调用报错或客户端停止等待，不等于已持久受理的业务自动撤销。 |

## 把整篇文章压缩成一个故事

甲在 ETH-USDC 永续的逐仓账户里有现金一千，已经持多仓两个 ETH。现在他想再买一点五个。系统不能只回答“有钱”，而要先保存请求，再把原仓位和这张单一起检查。按本文教学规则，原仓位需要四百风险预算，加上新订单后需要七百；这不是扣手续费，也不是花三千本金买 ETH。

紧接着，甲又申请买一个。虽然合计需求九百仍有权益支持，但如果两单都成交，仓位会到四点五，超过四个的上限，所以第二单拒绝。第一单随后成交零点五，仓位变成二点五，挂单还剩一个，总需求仍是七百：只是未来义务变成了真实持仓。

甲再撤掉余下一个，只有撤销正式提交后，需求才降到五百，现金始终一千。中间若网络超时，系统先查原请求结果，不能当作失败重做。整个故事的关键不是组件有多少，而是每一步都有唯一顺序和共同提交：批准不保证成交，旧批准也不能绕过新价格下的检查。

沿用总览的线性 USDC 永续、单向逐仓、单市场共同权威顺序与同库业务事务 T。主案例现金 1,000、持多仓 2 ETH、均价/Mark 2,000，O1 买入 1.5 ETH；不采用现货支付 3,000 本金的模型。

## 第 1 层：从提交到收尾，完整链路怎样讲

**面试官：** 用户下单后，交易前风控到底做了什么，怎样讲完这笔业务？

**面试者：** 在这个模型中，入口先鉴权和检查参数，再把带稳定请求身份的命令持久受理。有效协调者按市场顺序读取仓位、现金、活动订单和当前价格配置，判断候选是否满足保证金与限额；通过后把订单和风险预占一起写入。订单可匹配时，还要在实际成交前检查双方最新资格。成交的订单余量、双方仓位、现金分录和风险变化在 T 一起提交；挂单则等待后续同序成交或撤单。O1 最终成交 0.5、撤余下 1，甲仓位变成 2.5，风险需求从 700 降为 500。最后回报和查询追上版本，才是用户可见的收尾，不把入口返回“通过”当作整笔业务结束。

## 第 2 层：谁有权改风险真相

**面试官：** 你用了入口、风控、撮合和账本，哪个模块拥有最终状态？

**面试者：** 它们有不同的逻辑所有权：入口确定账户与请求身份，订单模块裁决接纳和匹配，持仓内核计算数量成本，账本模块维护现金分录，风控内核算准入和执行门禁。协调层让这些变更在一个事务中共同生效。风控不会直接凭估值结果改现金，账本也不能自行宣布订单已撤。当前架构不是让多个服务各写一份“权威账户”，而是通过同一受控写入口和事务建立对应关系。页面缓存、风险看板、扫描器可以观察和提出重评请求，不能旁路修改仓位或预占。这样才能回答某个版本的 R 究竟对应哪组订单，而不是用“最终一致”掩盖多写者。

## 第 3 层：为什么已经有现金还要预占

**面试官：** 既然甲现金有 1,000，为什么不能每次查到有钱就让订单进撮合？

**面试者：** 因为现金不是可重复使用的无限风险预算。初始 2 ETH 仓位 IM 占 400，O1 的 1.5 ETH 尚未成交也有执行义务，保守总需求变成 700；后一个请求必须看到这份义务。预占在这里不是把 300 从钱包转走，而是把活动订单和剩余量纳入风险计算。O2 再买 1 ETH 时，虽然拟总需求 900 仍小于权益 1,000，但最坏数量达到 4.5，超过数量限额 4，也超过名义限额。若只查现金或只看已成交仓位，就会把未成交义务漏掉。预占的作用是约束未来执行，不是生成费用或提前交割 ETH。

## 第 4 层：风险通过与订单可执行是否同一事实

**面试官：** 你说预占约束未来执行。可风控刚算完，撮合前价格就变了，原来的通过还算数吗？

**面试者：** “某版本算过通过”和“当前可以成交”不是同一个事实。本基线把价格激活、风险裁决和匹配放到共同顺序；接纳订单与预占在 T 共同提交，后续成交又用当时有效的价格配置和最新仓位重检。旧通过记录只作审计，不是永久许可证。如果新价格或配置使旧挂单失去支持，先关闭其执行门禁，再按规则确定撤销或重裁；没有重裁的订单不能靠旧布尔值继续成交。若价格输入本身无效，进入 CANCEL_ONLY，不连 RO 都盲目放行。这样价格变化可以让存量风险被动恶化，但不会在系统已知失效后仍按旧许可继续增加风险。

## 第 5 层：挂单转为成交，风险是否真的减少

**面试官：** 成交时订单剩余减少，你是不是就能释放相应的开仓预占？

**面试者：** 只能说约束的归属改变，不能说风险凭空消失。O1 成交 0.5 后，甲的仓位从 2 到 2.5，剩余订单从 1.5 到 1；在同价零费用主例中，持仓 IM 从 400 变为 500，订单部分从 300 变为 200，总需求仍是 700。两部分必须同事务计算与提交。如果先减订单预占、后更新仓位，另一张订单就可能在空窗中获得本不该有的资格。当前 T 同时完成成交和经济结转，没有异步的未结转成交；若未来拆成独立系统，就必须增加在途义务覆盖，而不能照搬这里“看到已提交余量即可算风险”的结论。

## 第 6 层：撤单和响应超时在哪里结束

**面试官：** 那用户撤单或下单超时，什么时候可以把风险空间还给他们？

**面试者：** 撤单请求到达不算关闭；必须在共同顺序中确定实际剩余量，和可能更早的成交一起解释。O1 已成交 0.5 后，权威撤销 1 ETH，订单未来资格归零，T 同时重算 R=500，但现金仍是 1,000，没有所谓退回 200 USDC 的转账。下单超时也不能直接释放，因为原命令可能已经持久受理。用户要放弃时提交 CloseIntent；若关闭先于迟到 Place，保留墓碑阻止它接纳；若 Place 已在前，就保留成交、只关闭余量。业务收尾依赖持久事实，不依赖客户端 context、RPC 错误或缓存是否查到订单。

## 第 7 层：事务失败后由谁继续

**面试官：** 你把多个状态放一个事务，但提交时连接断了，协调者怎么知道该继续还是重做？

**面试者：** 明确回滚时，T 的订单、成交、仓位、分录、结果和应用位置都不生效，原持久命令仍待处理。COMMIT 后连接断开则结果未知，不能假定没提交，也不能继续用内存草稿处理下一条。协调者应暂停该市场的应用，按原命令身份查询权威结果和 appliedSeq；提交成功就恢复已保存变化，未提交才按同一身份重做。外部回报由同事务 Outbox 继续投递，推送失败不会重新执行成交。恢复时还要使用有效 epoch 隔离旧 owner，不能让另一个实例与未知状态的原实例同时写。事务解决局部共同变化，身份和恢复协议解决提交确认丢失。

## 第 8 层：为什么选择合并裁决，拆开会失去什么

**面试官：** 这个合并方案看起来耦合重，实际拆成 Risk、Matching 和 Ledger 不可以吗？

**面试者：** 可以，但那是改变原子边界后的设计，不是把函数改成 RPC 就保持原保证。当前方案适合单市场逐仓教学：风险边界清楚、结果容易恢复，代价是市场串行和同库事务容量。拆开后要说明哪一域拥有执行资格、风险许可绑定什么、迟到命令如何关闭，以及成交已确定而仓位现金未更新时谁覆盖在途风险。全仓还需要跨市场共享预算，不能让每个市场独立消费同一抵押物。优化应先测出当前瓶颈，再选择分区和可证明的预算协议。无论部署多少服务，都不能退化成“先成交、风控失败再撤”，因为撤单不撤销已有成交。

## 收束：先讲业务承诺，再讲组件

- **讲透的机制：** 受理、接纳、执行和可见性分层；逻辑模块分责；共同提交让订单义务与持仓风险无空窗。
- **易错边界：** 本例没有 ETH 交割和名义本金扣款；风险释放不等于现金退款；入口通过不是永久成交许可。
- **验证反例：** 在 O1 部分成交前后各插入 O2，检查 q 与余单是否始终覆盖 3.5、总需求是否始终为 700；若某一中间态 R 掉到 600 后才补回 700，就暴露了跨模块空窗。这个反例是设计检查，不是已执行测试。
