# 大问题 12：超时、重试、关闭与崩溃后怎样恢复？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 线性永续、逐仓风险单元 | 用 USDC 计算合约价格差，本仓使用专用现金而非自动调用所有资金。 | 本例不交割 ETH，不存在按名义本金全额支付的现货模型。 |
| q、B、E、R | q 是净持仓，B 是已记账现金，E 加入浮盈亏，R 是持仓与挂单总风险需求。 | O1 后 R=700 而 B=E=1,000；预占不是扣费或已发生损失。 |
| IM、Qmax、Nmax、Mark | IM 是初始保证金要求；后两者限制数量和名义额；Mark 是估值参考价。 | 教学比例 10%、限额 4/8,000；保证金非手续费，Mark 非承诺成交价。 |
| 幂等、一份业务效果 | 同一操作无论重试多少次，都不多创建订单、成交或资金变化。 | O1 重投三次不能变成三张各 1.5 的买单。 |
| RequestKey、鉴权作用域 | 请求身份包含已经确认的账户、命令类型和客户端请求号。 | 不同账户同名请求号不是同一份业务，也不能互相关闭。 |
| payloadHash、规范化载荷 | 将实际方向、价格、数量等统一表达，再生成内容指纹。 | 同键数量改为 1 就是冲突，不是 O1=1.5 的安全重试。 |
| intentId、业务意图 | 用户这一次想完成的交易意愿的稳定身份。 | Place 与 CloseIntent 可以是不同请求，却指向同一个应关闭的意图。 |
| 受理事务 A、RECEIVED | A 持久保存完整请求及序号；RECEIVED 表示可以恢复处理。 | 未承诺风控通过、挂单或成交，不是“已经买到”。 |
| 业务事务 T、共同提交 | 将订单、风险、双方经济效果、结果、处理位置和通知一起保存。 | 基线没有成交已确定却等另一个数据库补仓位的暂态。 |
| CONFLICT、风险拒绝 | CONFLICT 指同键内容不一致；风险拒绝是已保存的业务结论。 | 同键同载荷返回原拒绝，后来补钱也不自动重算；新申请要新身份。 |
| UNKNOWN、超时 | UNKNOWN 是当前不知道结果；超时只说明本次等待没等到确认。 | 不等于下单失败，更不等于可以退款或换键再下一单。 |
| 主库、延迟副本、权威查询 | 副本可能还没同步最新记录；权威查询必须能判断原提交事实。 | 暂时查不到订单，不证明订单没受理，也不证明原消息不会迟到。 |
| COMMIT、工作副本 | COMMIT 提交事务，工作副本是提交前的试算草稿。 | 确认丢失时暂停查证，不能拿草稿先推送成交。 |
| marketSeq、appliedSeq | 命令的共同序号与已经应用完成的位置。 | 重启从确定的下一条继续；缺口要查清，不能跳序。 |
| Place、CloseIntent | Place 申请下单；CloseIntent 持久请求关闭原业务意图。 | 客户端停止等待不是 CloseIntent，也不自动撤单。 |
| 关闭墓碑、CLOSED | 墓碑持久记住某意图不得执行；CLOSED 表示已关闭。 | Close 先到时即使订单不存在也要留记录，挡住迟到 Place。 |
| NOT_FOUND、关闭确认 | NOT_FOUND 只是此刻没查到；关闭确认还保证该意图不能再产生未来执行。 | 两者不是同义词，不能查无记录就宣布“绝不会成交”。 |
| 部分成交、终态与数量闭合 | 成交只关闭相应部分；终态不再有可执行余量，原单各份数量都有去向。 | 成交 0.5 后只能撤余 1，最终 1.5=0.5+1，不能撤掉已成部分。 |
| TTL、迟到窗口 | TTL 是设定的保留或有效时长；迟到窗口是旧消息仍可能重来的时间范围。 | 到期只能触发核实或关闭，不能自动释放仍可执行订单的预占。 |
| ownerEpoch、fencing | 当前处理者任期与提交处阻止旧任期写入的机制。 | 旧主复活不能与新主各成交一次；隔离写权限不等于恢复丢失数据。 |
| tradeId、legId、journalId | 分别标识成交、该成交某一方效果、账务记录。 | 相同业务重放只复用身份，不能再加一次仓位或分录。 |
| Outbox、消费者幂等 | 先同事务保存待发事件，再由接收方按事件身份防止重复处理。 | 通知允许重发，成交和现金效果不允许重做。 |
| WAL、同步复制、RPO | WAL 是数据库恢复日志；同步复制等待约定副本保存；RPO 衡量灾难后可丢多少已确认数据。 | RPO 为零必须有真实部署支持，epoch 和重试都变不回已丢日志。 |
| 归档、压缩墓碑 | 把历史移到可审计存储，或用较小记录保留不可复用的关闭身份。 | 清理不是把旧意图忘掉后当新单重新接纳。 |

## 把整篇文章压缩成一个故事

甲提交买一点五 ETH 永续的 O1，却迟迟没收到回包。他不能立即换请求号再下一笔，因为原请求可能已经保存，第二个号会成为另一份交易义务。正确做法是带原身份查询或重投：受理了就等原命令，已裁决就返回原结果；同键改数量则明确冲突。

若执行事务提交时断连，处理者也不能猜失败。它暂停后续应用，查原结果与处理位置；已提交只恢复索引和通知，确认未提交才按同一身份重做。甲如果不想等，就提交关闭原意图的请求。关闭先到也要留下墓碑，不能因订单尚不存在就忘掉，否则迟到的 O1 又会被接纳。

若 O1 已成交零点五，关闭只能撤剩余一个，最终仓位二点五、需求五百、现金仍一千，不存在退款。TTL 到期和客户端断线都不是释放依据。新主接管用任期挡旧主写入，但若部署真的丢了已确认数据库日志，任期也救不回来；不丢已确认交易的承诺，必须由实际持久化和复制条件支撑。

[返回专题总览](README.md)

**流程位置与核心机制：** 本题沿请求身份、未知结果、关闭竞争、崩溃与接管展开，重点是“一份身份、一份业务效果”怎样跨越网络与进程故障成立，不把幂等简化成临时缓存。

**范围前提：** ETH-USDC 线性永续、单向逐仓，初始 `q=2、C=4,000、B=1,000、Mark=2,000`，`r=10%、h=5%、Qmax=4、Nmax=8,000`。O1 买 `1.5@2,000`，部分成交 `0.5` 后 `q=2.5、remaining=1、R=700`，撤后 `R=500、B=1,000`。受理事务 A 独立保存 `RequestKey+payloadHash+marketSeq+command`；业务事务 T 按共同权威顺序，将订单、预占、双方仓位/账本、结果、appliedSeq 与 Outbox 同库提交。不存在“成交已提交、等待另一数据库补记本笔仓位”的基线暂态。

## 第 1 层：幂等到底绑定什么事实

**面试官：** 超时、重试、关闭与崩溃后怎样恢复？你会怎样定义一次下单的幂等身份，以及可以承诺的完成阶段？

**面试者：** 我会把鉴权后的账户、命令类型和客户端请求号组成 RequestKey，绑定规范化载荷摘要，并单独保留业务 intentId。事务 A 唯一保存这份绑定、完整命令和市场序号，提交后只能说 RECEIVED，不能说风控通过。有效 owner 再按序执行事务 T，订单、预占、相关双方仓位账本、结果和处理位置共同提交，才有可查询的业务结论。重投同一身份只找回这条命令，不再增加订单。O1 因而只有一份一点五的原始数量和七百总需求，不会因为客户端重试三次变成三笔交易义务。

## 第 2 层：同键异载荷与已受理拒绝怎样返回

**面试官：** 你把身份绑定载荷，如果用户重试时把 O1 数量从 1.5 改为 1，或者原请求已经被风控拒绝，应该重新计算吗？

**面试者：** 同键改数量必须返回 CONFLICT，不能悄悄改单；摘要要覆盖方向、限价、数量、RO 标志和意图身份，十进制先规范化，避免等值表达被误判不同。若已经受理且事务 T 保存了风险拒绝，同键同载荷返回原拒绝，即使后来补了保证金，也不重新获得资格；用户应换新请求身份。受理前的参数非法或过载拒绝没有产生这份业务承诺，要明确区分。原准入结果与订单当前进度也分开查询：O1 后来撤销了，重复 Place 仍返回原命令结果及关联身份，不会因为订单已终态而重新创建。

## 第 3 层：受理回包超时怎样避免“双下单”

**面试官：** 如果事务 A 可能已经提交，但客户端没收到序号就超时，它查询暂时没找到，能不能换请求号再下一次？

**面试者：** 不能把没收到或暂时没查到解释为没受理。超时可能落在 A 提交后、回包前，读副本也可能尚未追上；换号会把原一点五买单变成两份独立意图。我会让客户端用原 RequestKey 查询权威存储或同键重投，由唯一约束返回原序号。查到 RECEIVED 就等待原命令应用，查到结果就返回原结果；尚未查明则保持 UNKNOWN。即使一次权威查询确实未找到，也不能证明网络中的原 Place 永远不会迟到。若用户真的要放弃，需要提交能关闭原意图的 CloseIntent，而不是靠本地超时标记结束。

## 第 4 层：业务提交未知怎样处理内存和对外消息

**面试官：** 现在查到了受理序号，owner 执行事务 T 时连接断开，COMMIT 成败不明，能否重算并先把成交推给用户？

**面试者：** 我会暂停该市场的继续应用和发布，先从数据库核实这条序号的结果及 appliedSeq。若事务已提交，就读取共同提交的订单、风险、双方经济效果和 Outbox，应用内存索引；若确认回滚，则从原状态重做这一条命令。不能只看本地工作副本或一张订单表猜测。比如零点五成交可能已经提交，重试必须复用唯一 tradeId、分腿和分录身份，不能再增仓一次。提交前不对外确定成交，提交后通过 Outbox 交付；网络报错既不是失败证明，也不是可以单边回滚仓位或释放预占的依据。

## 第 5 层：关闭先于迟到下单为什么需要墓碑

**面试官：** 客户端仍不放心，发了 CloseIntent；如果它比仍在网络中的 Place 更早到达，订单不存在时直接返回成功够不够？

**面试者：** 不够，必须把“这个意图已经关闭”作为持久事实。CloseIntent 有自己的请求键，并指向经过鉴权的原意图；若它先进入共同顺序，事务 T 保存关闭墓碑，后到 Place 即使参数和余额合法，也只能得到 CLOSED，不能新建预占。若 Place 已先受理，关闭一般排在它后面，就按实际处理结果关闭余量。墓碑作用域必须和原意图一致，不能让另一个账户关闭同名请求。单纯返回 NOT_FOUND 没有约束未来，迟到 O1 仍可能占出七百需求，这正是“查不到订单”和“已禁止该意图执行”的区别。

## 第 6 层：关闭与部分成交竞争时怎样收尾

**面试官：** 如果不是关闭先到，而是 O1 已挂出、又与零点五成交竞争，关闭最终应该释放多少，怎样防止双退？

**面试者：** 以共同顺序决定：若零点五成交先提交，仓位变二点五、成本五千，O1 余量一，总需求仍七百；关闭随后只撤这一，订单累计成交零点五加撤销一等于原始一点五，需求降到五百。现金始终一千，没有退款分录。若关闭先裁决，就撤原余量一点五，后续匹配找不到合法余量，不应产生成交。重复关闭只返回同一终态或无新增效果的结果，不能再减一次占用。事务 T 同时保存数量、风险和结果，避免先减聚合预占、崩溃后订单仍可成交的中间状态。

## 第 7 层：TTL 和客户端断线为什么都不是释放依据

**面试官：** 你一直保留原身份和墓碑，数据会增长；可不可以过了十分钟 TTL 就清掉记录、释放占用，让用户重新请求？

**面试者：** TTL 只能触发查询或提交关闭意图，不能证明交易义务已经消失。命令可能已受理尚未应用，订单也可能仍在簿上；按超时减掉预占会让它保留成交能力却失去风险覆盖。释放只能依据同序提交的终态和整体重算，客户端断线同理。身份记录清理还要覆盖迟到与重投窗口，必要时保留不可复用的压缩墓碑；若约定身份带有效期，就在受理端永久拒绝过期身份，而不是删除后当成新请求。已经归档的成交和账务也仍有审计义务，不能用缓存过期实现业务“遗忘”。

## 第 8 层：旧 owner 复活怎样在存储层被挡住

**面试官：** TTL 不能代替业务关闭，那主进程失联后由新 owner 接管，旧进程又恢复，会不会双方各提交一次成交？

**面试者：** 接管要在数据库市场控制行上提交递增 ownerEpoch，新 owner 只使用新值。每个业务事务先锁定同一控制行，核对 epoch 与 appliedSeq，所有订单、账本及处理位置修改都受这次核验约束；旧 epoch 必须在存储层失败，不能仅靠进程内租约自觉停机。若旧事务先持锁，它要么先完成再由新主接管，要么回滚，不能与新 epoch 的有效写入交错成立。旧主也不能发布未提交工作副本；交付者只认已提交 Outbox。epoch 约束写权限，唯一业务效果约束重复，两者解决的不是同一个故障窗口。

## 第 9 层：重启怎样从数据库重建而不重做旧效果

**面试官：** 存储层已经挡住旧主，新 owner 从什么位置恢复，怎样保证重建订单簿不会漏掉已受理命令或重复记账？

**面试者：** 它先取得新 epoch，在一致数据库快照中读取 appliedSeq、活动订单、双方相关状态和结果，再重建内存索引，只从下一条命令继续。A 的序号分配与命令保存共同提交，不能用会留下回滚空洞的裸序列号假定日志连续；下一条缺失必须查清，不能跳过。T 已提交的命令不再产生效果，未提交的整条重做。经济输入缺口则保护停处理，不能为了恢复进度忽略应扣费用。Outbox 可重复投递，但消费者以事件身份防重并核对版本；查询投影落后不改变权威状态，也不构成再次扣款或释放的理由。

## 第 10 层：数据库故障后的 RPO 承诺需要什么条件

**面试官：** 你把恢复依据都放在数据库，如果主库损坏、备库少了最后两条已确认事务，靠重试和 epoch 能保证不丢已确认交易吗？

**面试者：** 不能，epoch 防双写，不会把丢失日志变回来。若承诺已确认事务 RPO 为零，部署必须让受理 A 和业务 T 都在要求的同步复制、持久落盘条件满足后再确认，并且只提升含这些已确认记录的副本，同时隔离旧主写入。只把 WAL 留在一台机器或异步复制，就不能作同样承诺。若灾难恢复出现数据缺口，必须停交易、核实可恢复日志和对外确认范围，不能把已确认 O1 当成从未发生再接纳。客户端重投只能复用仍可证明的身份，无法替代丢失的仓位、账本与墓碑事实；保证范围必须和真实复制部署一致。

## 收束：机制、易错边界与反例

- **讲透的机制：** A 负责持久身份和顺序，T 负责唯一业务结论；未知提交先核实，意图关闭靠墓碑，接管靠存储层 fencing，恢复靠共同提交的状态与处理位置。
- **最易答错：** 同键异载荷不能复用；已受理风险拒绝可以返回原拒绝；未找到不等于未来不能迟到；TTL、断线、响应失败都不自动撤单或退款。Outbox 的可重投递不等于交易效果可以重做。
- **反例检验：** 分别在 A 提交后回包前、T 提交后更新内存前切断连接，预期同键重投始终只有一份 O1。再让 CloseIntent 先提交、Place 后到，预期只有墓碑而无活动订单。对已部分成交的 O1 连续关闭两次，预期 `filled=0.5、canceled=1、R=500、B=1,000`。
- **部署边界：** 上述故障点是验证设计，不是已执行的故障注入结果；复制耐久性和 RPO 必须另有真实部署证据。本题不新增工程或第二个 MVP。
