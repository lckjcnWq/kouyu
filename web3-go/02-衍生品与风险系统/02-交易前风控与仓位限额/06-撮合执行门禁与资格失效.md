# 大问题 06：挂单早已通过，成交前为什么还要检查？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 线性永续、单向逐仓 | 以 USDC 结算价格差，一个带方向的净仓使用专用资金承担风险。 | 不交割 ETH，也不能自动调用其他逐仓或钱包的钱。 |
| 限价单、GTC | 限价单给出最差可接受价格；GTC 表示未结束前可持续挂着等待。 | 挂得久不代表批准永久有效，更不代表一定成交。 |
| 中央订单簿、撮合 | 订单簿记录买卖意愿；撮合按价格、顺序等规则寻找可成交双方。 | 本基线候选成交价取已有挂单价，不由 Mark 直接指定。 |
| 准入、执行资格 | 准入是在当时条件下允许订单进入活动状态，资格仍受后续约束。 | “曾经通过”不能替代每笔实际成交前的检查。 |
| q、B、E | 分别是净持仓、已记账现金和计入浮盈亏的权益。 | 价格上涨可让 E 增加，但不代表数量和名义限额一定通过。 |
| Mark / m、priceId | Mark 是风险估值参考价，priceId 标识选用的那份价格。 | 新 Mark 生效必须重算，且它不保证订单的实际执行价。 |
| configId、风险版本 | configId 指明规则内容，风险版本指明账户状态更新位置。 | 输入任一变化，旧计算都可能不再适用。 |
| Q*、Qmax、Nmax | 最坏绝对仓位、数量上限、名义敞口上限。 | O1 余量 1.5 加现仓 2，Q*=3.5；新 Mark 2,400 时名义 8,400 超限。 |
| IM、MM、R | IM 是初始保证金要求，MM 是维持保证金要求，R 是覆盖持仓和挂单的总预算。 | 都不是手续费；资金覆盖 R 不允许绕过名义限额。 |
| 双边门禁、经济后态 | 同时检查买卖双方，并试算成交后两边的仓位、现金与风险。 | 甲通过但乙失败，不允许先生成成交再补救乙。 |
| 订单版本、remaining | 订单版本说明状态更新到哪里，remaining 是还能成交的余量。 | 候选成交不能消耗已撤订单，也不能超过任一方实际余量。 |
| 事务 T、工作副本 | 工作副本先模拟，T 把通过后的相关修改一起提交。 | 被拒候选不消耗甲余量，也不留下乙的一半分录。 |
| marketSeq、价格激活 | marketSeq 是共同顺序；价格激活是新参考价在该顺序中正式生效。 | 新价格先于匹配，就必须按新条件裁决，而非等后台扫描碰巧扫到。 |
| 生效屏障、重裁 | 屏障先关闭未覆盖的旧资格，重裁再按新输入判断。 | 可以分批计算，但未重裁订单不能趁空窗继续成交。 |
| 队列积压、价格质量 | 更新堵在路上或来源不可靠，都可能使看起来最新的参考价不可用。 | 不能只看旧价时间戳未过期，就忽略待激活消息的明显延迟。 |
| CANCEL_ONLY、RO | CANCEL_ONLY 禁止一切新成交；RO 是约束为只减仓的订单。 | 本文价格无效时连 RO 也停，不能把标签当紧急成交豁免。 |
| 权威撤单、终态 | 已按共同顺序提交关闭，明确余量不再能成交。 | 客户端点击撤单或显示处理中，都不是这个承诺。 |
| tradeId、唯一效果 | 每笔确定成交的稳定身份，确保重复处理不重复改变资产和仓位。 | 原成交回放只能复用，不再加一次 filled。 |
| ownerEpoch、fencing | 当前处理者的任期号，以及在存储层阻止旧任期写入的规则。 | 旧内存订单簿还在，也不能获得第二份成交权。 |
| COMMIT 未知、UNKNOWN | 提交确认丢失，当前不知道是否已成功。 | 先查权威记录；副本暂时查不到不能证明成交未发生。 |
| Outbox、投影 | Outbox 保存已提交待交付事件，投影是页面和查询看到的派生视图。 | 回报可以延迟，不能因此回滚成交或重复执行。 |

## 把整篇文章压缩成一个故事

甲持多仓两个 ETH，挂买一点五，初始 Mark 两千时最坏数量三点五、总需求七百，订单获准等待。这只是允许它在条件有效时排队，并非保证某天一定成交。后来参考价涨到两千四百，甲的浮盈让权益增至一千八百，却也让最坏名义敞口达到八千四百，超过本文八千的教学上限。

所以新价格生效后，系统先关掉未重裁订单的执行资格，再重评并撤掉失效普通单，不能边慢扫边继续信任旧批准。即使甲仍通过，真正成交前也要确认对手单没撤、两边余量足够、实际价格符合限价，且双方成交后状态都合法。Mark 只是估值参考，不会保证成交价格。

撤单与匹配若竞争，就按共同序号决定：成交先成立，只撤剩余；撤单先成立，后续匹配不能再用该单。事务提交前都只是候选，提交后才有双边成交事实；回包丢失只触发查证，不允许重造一笔。价格无效时则进入只撤单模式，RO 也不能借旧批准继续成交。

[返回专题总览](README.md)

**范围与前提：** 沿用 README 的 ETH-USDC 线性永续、单向逐仓、限价 GTC 与事务 T。准入只代表在某个价格、仓位、配置和模式版本下建立了有约束的挂单资格，不代表永久可成交。价格无效进入 `CANCEL_ONLY`，不成交；每笔成交前同时校验买卖双方当前状态和执行语义。

**流程位置与核心机制：** 本题从活动挂单进入撮合、成交提交，聚焦资格何时失效、失效与撮合如何定序，以及已确认成交为何不能靠撤单回滚。

## 第 1 层：通过准入的订单为什么不能直接成交？

**面试官：** 一张限价单接纳时已通过风控，撮合找到对手单后为何还要再检查？

**面试者：** 接纳判断使用当时的 `q、B、m、配置、活动订单和保护模式`，但等待期间这些输入可能变了。比如原来 `m=2,000、Qmax=4`，挂单可在当时的 `R=700` 下通过；随后价格版本、仓位或 MM 健康状态改变，旧资格不再代表当前安全。撮合必须把“可排队”与“此刻可执行”区分开。活动订单只是当前规则下有约束的候选义务，不是撮合永远有效的通行证；每次成交既改变仓位又消耗剩余量，因而下一笔要基于刚提交的后态重新判断。若市场连续收到成交、价格激活和配置激活，裁决顺序决定采用哪一组输入；不能让成交线程并行读旧版本，而把更新事件事后补写到风险状态。

## 第 2 层：执行门禁具体读取什么最新状态？

**面试官：** 既然要重新检查，你所说的“最新”是读哪些版本，如何避免拼出不存在的快照？

**面试者：** 在市场命令序列中的当前位置读取双方账户仓位、现金/权益、活动订单及剩余量、有效价格身份 `priceId`、风险参数 `configId` 和模式。它们须属于同一风险单元版本，并在 T 的事务工作副本上计算；不能分别从缓存拿仓位、从数据库拿订单、再用新价格凑成一组从未共同成立的事实。决策证据保存序号和版本。工作副本先检查对手单仍活动、双方限价满足成交价，再求双方经济后态；任一方失败就不写成交，且失败原因要与采用的版本一并保存，供查询和恢复复用。核心字段可包括 buyOrderVersion、sellOrderVersion、riskVersion、priceId、configId 和 decisionSeq；T 条件更新时验证这些版本仍是本命令前态，避免读取后有另一条写入悄悄覆盖。

## 第 3 层：准入后价格上涨，旧单是否仍能成交？

**面试官：** 你把 priceId 纳入执行快照；若 Mark 从 2,000 涨到 2,400，O1 买单还在簿上，怎样重裁它？

**面试者：** 要按生效序号的新 Mark 重算数量、名义、R 和权益，不能沿用 `M1`。例如 Mark 从 2,000 涨到 2,400，q=2 且 O1 买余量 1.5 时，保守上界 Q*=3.5、名义为 8,400，已超过 Nmax=8,000；此时 U=800、E=1,800，R=840 虽有资金覆盖，也不能绕过名义限额。价格激活命令生效后，尚未重裁的单先不可执行，再确定撤销失效普通单；不能让后台慢扫期间继续撮合。这里不要求行情到达瞬间同步扫完整本订单簿，但生效屏障必须先关闭未重裁订单的执行门禁，扫到明确截止位置并追平之后才可重新开放。若价格恢复同时配置也变为 V2，重裁必须使用明确激活顺序，例如先 M2 再 V2，不能用部分订单算 M2/V1、另一些算 M2/V2 后开放全市场。

## 第 4 层：价格失效或队列积压时是否能按旧价撮合？

**面试官：** 若新价格消息在队列里积压，但旧价格的时间戳看起来尚未过期，能否继续用它撮合？

**面试者：** 不能只凭旧快照的年龄放行。价格激活待应用、队列延迟超阈值、源质量异常或价格身份不可确认时，系统停止普通准入和成交，并按基线进入 `CANCEL_ONLY`；此模式禁止任何新成交，只保留撤单和安全管理动作。价格恢复后，先确定新 `priceId` 的生效序号，再重裁存量订单，追平前不开回撮合。裁决证据记录 priceTime、接收/决策时间、质量和 mode，回放使用原证据；不在恢复时拿当前墙钟重算过去是否过期，否则同一命令回放可能得出相反结果。若健康监控尚未确认新源连续有效，单条恢复消息不够重开；应按已定义质量门槛更新保护模式，并将模式切换也写入顺序，避免不同撮合 worker 对同一价格源得出不同放行判断。

## 第 5 层：成交价和双边账户如何共同门禁？

**面试官：** 价格恢复且甲已按新版本重裁通过，是否就可以生成成交，再让乙的结算系统事后处理？

**面试者：** 不可以。执行价须满足双方限价与市场规则，且买卖双方的逐仓风险、订单剩余量、保护模式和经济后态都要在同一 T 中校验。甲通过但乙现金不足、订单已撤或被保护模式阻断时，不得生成一笔只有单边义务的成交。成交数量、双方仓位变化、现金分录、订单剩余和预占一起提交；对手方也有合法开空资格与抵押只是本题案例的明确前提。若双方数量单位或市场乘数不同，先按合约精度规范化到同一成交数量，再计算两边持仓后态；不得先给一方减余量、后发现另一方不支持而留下半笔。例如双方订单各余0.5，撮合候选0.5时先检查两边orderVersion与remaining均足量，再算费用/损益与后态；若乙风险失败，整个候选回滚，甲余量不变。

## 第 6 层：撤单和成交同时到达时谁获胜？

**面试官：** 你要求同时检查双方 remaining；若用户撤单正与这笔成交竞争，前端先显示撤单请求，还能成交吗？

**面试者：** 前端发出不构成裁决。撤单命令和匹配命令进入同一 marketSeq 顺序：若成交先序列化并提交，撤单只能撤其后剩余量；若撤单先提交，订单剩余归零，后续撮合不能再引用它。撤单回执只有在权威终态提交后才能承诺“不会再成交”；等待裁决时预占仍保留，避免先释放额度再让迟到撮合成交。举例 O1 剩余 1 时若 fill 先执行 0.4，则 cancel 只能撤 0.6，最终累计成交 0.9、撤销 0.6；若 cancel 先关闭 1，后到 fill 必须拒绝，这两种结果不能混成“撤单成功但又多成交”。撤单结果还区分请求已受理与终态已提交；网络超时回 `UNKNOWN` 时用户应查原 request key，不能因客户端重试换新键而发出第二张卖单或误报撤销完成。

## 第 7 层：T 提交未知或实例切换后如何防止双成交？

**面试官：** 成交事务提交后连接断了，旧 owner 还继续撮合，而新 owner 已接管，会怎样保证唯一结果？

**面试者：** 成交有稳定 `tradeId`，并在 T 中与双方订单变化、经济效果、`appliedSeq` 和 Outbox 唯一提交。未知提交先查询结果，不再次创造 trade。owner 接管递增 epoch，数据库拒绝旧 epoch 的写入；新 owner 从最后已提交序号恢复。若旧实例仍持有内存订单簿，也必须因 fencing 失败而停止发布，不能依赖“协调服务已通知它”。例如同一个 tradeId 的回放只返回原成交，且双方订单 filled 数不再增加；若数据库提交结果未知但主库不可读，则暂停该市场而不是用可能滞后的副本认定未提交并再撮合一次。epoch 校验要覆盖命令处理与成交写入，不只在启动时检查；旧进程的任何后续事务都必须因条件更新失败而撤出撮合路径。

## 第 8 层：什么时点算成交确定，如何验证门禁闭环？

**面试官：** 你强调只能复用已提交的 tradeId；到底什么时候能对用户承诺成交，怎样验证门禁失败没有留下半笔效果？

**面试者：** T 提交前只是工作副本中的候选撮合，提交后成交、双方仓位/分录、订单余量及风险占用才共同确定；私有回报由同事务 Outbox 后续投影。验证时让价格失效、撤单竞争和旧 epoch 写入分别夹在匹配前后，检查任何未过门禁的成交都无经济效果，已提交成交不会因推送重试重复。核心机制是资格版本化并逐笔复核；易错点是把接纳当永久许可；价格无效仍成交就是直接反例。验收还应确认回报暂时滞后时查询仍返回提交版本，且门禁拒绝不会消耗订单数量或留下单边账本分录。成交确定后即使用户随即撤单，也只能撤剩余部分，不能反向删除已经结算的 trade；例如已成交0.4、原余1，终态只能是filled增加0.4、撤销0.6。

## 机制、易错与反例收束

- **机制：** 每笔撮合按同序的双边状态、有效价格、配置和保护模式重检，成交及其经济后态由事务 T 共同确定。
- **易错：** 把“曾经准入”当永久执行许可，或把发出撤单当撤单已终态；回报投影延迟也不能倒改权威结果。
- **反例：** Mark 从 2,000 到 2,400 后，q=2 且普通买余量 1.5 的 N=8,400 超限；若沿用 M1 许可成交，门禁失效。价格无效时成交同样违反规则。
