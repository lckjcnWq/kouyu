# 大问题 09：怎样保证订单、持仓、账本和风险一致？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 线性永续、单向逐仓 | 用 USDC 计算价格差，以一个带方向的净仓和专用现金承担风险。 | 没有现货 ETH 交割，其他账户的钱也不自动支持当前仓位。 |
| 订单、成交 trade | 订单是尚待履行的交易意愿，成交是已确定的双边交易事实。 | 订单接纳不等于成交，撤掉余单也不能抹去已成交部分。 |
| q、C、B、E | q 是净持仓，C 是剩余入场成本，B 是已记账现金，E 还计入浮盈亏。 | O1 成交后 q=2.5、C=5,000，但同价零费用下 B=E=1,000。 |
| 风险需求 R、预占 | R 覆盖已持仓与活动订单义务；预占使未来义务不能被忽略。 | 成交 0.5 后 R 仍为 700，不是钱包扣款，也不是确认损失。 |
| IM、Q*、名义限额 | IM 是初始保证金要求；Q* 是最坏数量；名义限额限制其按 Mark 折算的金额。 | 资金、数量、名义金额分别检查，不能互相代替；保证金不是费用。 |
| Mark、价格证据 | Mark 是风险参考价，证据说明用了哪个版本、当时是否可信。 | 估值不能保证执行价，重放也不能拿新价格改旧成交。 |
| 不变量 | 不管发生正常操作还是故障，都必须成立的业务关系。 | 一致性要落成可核对的关系，而非仅说各服务最后都会成功。 |
| original / filled / canceled / remaining | 分别是原始量、已成交量、已撤量和剩余量。 | O1 最终 1.5=0.5+1+0，每份数量都必须有去向。 |
| 双边数量、唯一成交身份 | 每笔成交买卖数量对应，并有稳定身份防止重复应用。 | 买方加 0.5 与对手方减 0.5 都要成立，不能只更新主动单。 |
| 账本、同币种平衡分录 | 账本记录资金变化；每种币的来去记录要按规则平衡、可追溯。 | ETH 仓位数量对得上，不证明 USDC 现金账也对得上。 |
| 逻辑所有权、协调层 | 模块负责自身规则，协调层负责将相关结果一起提交。 | 订单管匹配、持仓管数量成本、账本管分录，不能各自独立拍板提交。 |
| 受理事务 A、RECEIVED | A 保存请求身份、内容和顺序；RECEIVED 只承诺可恢复处理。 | 还不能向用户承诺风控通过、挂单或成交。 |
| PostgreSQL 业务事务 T | 将本命令涉及的订单、双边经济效果、风险与结果放在同库一次提交。 | 本基线没有“成交已确定、等待另一个库补仓位”的中间状态。 |
| 工作副本、原子提交 | 提交前先试算；正式保存时要么整组成功，要么整组不生效。 | 账本检查失败，不能留下 filled 已增加或单边仓位变化。 |
| marketSeq、appliedSeq | 前者是命令共同序号，后者是已完成应用的位置。 | 恢复从确定位置继续，不能只凭内存猜最后处理了哪条。 |
| tradeId、分腿、分录身份 | tradeId 标识成交；分腿标识双方各自效果；分录身份标识账务记录。 | 重试同一笔成交不再记第二份仓位或资金效果。 |
| 提交未知、权威查询 | 没收到提交确认不能判断成功与否，要查能确定原事实的存储。 | 延迟副本查不到不能当作没发生，更不能重新撮合。 |
| Outbox、事件幂等 | 同事务保存通知，再按稳定事件身份反复交付但只产生一份消费效果。 | 解决通知丢失和重复，不代替 T 内的账本提交。 |
| 查询投影、回报游标 | 查询投影是页面视图；游标说明它已覆盖到哪个版本。 | 页面落后不改变成交，也不能拿旧状态覆盖新终态。 |
| 对账、补偿命令 | 对账找出记录差异，补偿通过可审计的新动作修正问题。 | 事后发现错误不能替代成交前检查，更不能随手改历史事实。 |
| Risk token、TTL、关闭墓碑 | 分服务许可、许可时长、执行端持久关闭记录。 | 到期不证明旧命令不能执行，拆域后还要证明关闭与迟到阻断。 |
| 在途成交覆盖 | 成交在一域已确定、另一域尚未更新时，仍为它保留风险预算。 | 是拆库变体必须补的协议，不能照搬同库 T 没有该暂态的便利。 |
| goroutine、channel、ownerEpoch | 前两者是 Go 进程内并发机制，后者是权威处理者任期号。 | 单线程只约束本进程；数据库仍要用任期挡住另一实例和旧主。 |

## 把整篇文章压缩成一个故事

甲的买一点五 ETH 永续订单被接纳后，系统记录一份余量和七百总风险需求。后来成交零点五，不是只把订单标成“部分成交”：买卖双方都要有同一笔成交，甲仓位从二变二点五、成本变五千，余单变一，风险仍七百；本文同价零费用下现金仍一千。

这些关系构成同一笔业务的不同账。系统先在工作副本检查数量闭合、双方仓位和资金分录，再用一个数据库事务一起保存。账本校验失败就整组不生效，不能留下半笔成交。最终撤余一，订单满足一点五等于零点五成交加一撤销，需求降到五百，不产生退款。

事务提交后即使通知没发出，成交也已经成立；恢复只重发同一事件，不再撮合一次。页面可以落后，却必须标明版本。若为了扩容拆成多个库，就失去这组共同提交保证，必须补足在途风险覆盖和执行端关闭协议。对账和消息防重各有用处，但都不能把半笔经济效果变成正确成交。

[返回专题总览](README.md)

**范围与前提：** 本题负责端到端一致性，沿用 README 唯一基线：ETH-USDC 线性永续、单向逐仓、单市场合并协调层、同一 PostgreSQL 事务 T。订单决定匹配，持仓计算数量/成本，账本维护现金与平衡分录，风控计算准入与门禁，协调层让相关变化共同提交。拆域方案只作为显式变体说明其缺失保证。

**流程位置与核心机制：** 串起受理、准入、执行、部分成交、撤单、持久结果与回报。重点不是宣称“最终一致”，而是明确不变量、唯一裁决点、T 两侧故障语义及查询投影的边界。

## 第 1 层：这条链路要保证哪些业务状态彼此一致？

**面试官：** 从用户下单到撤单结束，订单、仓位、账本和风险之间的“一致”具体指什么？

**面试者：** 订单的累计成交量必须对应已确定成交；成交双方的持仓变化与现金分录必须匹配；活动订单剩余量必须仍受风险预算约束；终态撤单不能再产生新成交。主案例 O1 买 1.5，最终成交 0.5、撤 1、余量 0，甲仓从 2 到 2.5，R 从 700 经部分成交仍为 700、撤单后为 500，现金仍 1,000。这些不是一个“订单状态”字段能代替的。实际含义是订单存量代表未来执行义务，trade代表已发生经济义务，风险R覆盖前者与后者的合并；任一层少一笔或重复一笔，限额和账户余额就可能各自看似正常却彼此不符。还要区分业务结果和投影结果：回报暂缺不影响已提交成交，成交缺失也不能由页面订单状态推断为未发生。

## 第 2 层：怎样把这些目标写成可检查的不变量？

**面试官：** 既然有多个状态，怎样防止每个模块都说自己正确却总账对不上？

**面试者：** 我至少检查四组不变量：每张已接纳订单 `original=filled+canceled+remaining`；每笔成交买卖双方数量相等、身份唯一；持仓数量与成交方向/数量相符，账本分录按币种平衡；活动订单集合按当前价格、配置和仓位重算后满足适用的 Q*、名义与 R 规则。它们在 T 的工作副本验证，状态和 `appliedSeq` 一起提交；对账可发现错误，但不能替代提交前约束。以O1验订单恒等式是1.5=0.5+1+0；仓位则是2+0.5=2.5，成本按成交价增加1,000，现金在零费用的永续例中仍为1,000。每个校验均有明确维度，不能拿成交数量平衡掩盖现金分录不平。成交买方数量+0.5与对手方数量-0.5相抵，不代表USDC分录可省略；这里只因永续同价、零费用而净现金效果为零，仍须保留可追溯的平衡账务事实。

## 第 3 层：谁拥有状态，谁拥有最终裁决权？

**面试官：** 你提到订单、仓位、账本、风控各有职责，如何避免多个服务互相改写权威事实？

**面试者：** 订单逻辑决定匹配和订单生命周期，持仓逻辑按已确定成交算q与成本，账本逻辑生成双边现金分录，风险逻辑计算准入与逐笔门禁；模块可在协调事务中计算，但不能各自独立提交并都自称有最终裁决权。协调层按marketSeq构造T，检查版本与双边后态后统一写入。持仓服务不得绕过入口改逐仓q。模块只返回计算值；账本校验失败则丢弃整个工作副本并保留原订单余量，避免重试重复副作用。拒绝也记录原因与输入版本，但不增加活动订单、成交或资金分录。

## 第 4 层：T 的原子边界到底包括哪些记录？

**面试官：** 如果成交已经在订单表标记完成，但账本还要异步写入，最小的共同提交范围是什么？

**面试者：** T包括涉及订单的filled/remaining、成交身份、双方仓位与成本、双边现金分录、风险聚合与RO分配/撤销、命令结果、处理位置及Outbox。提交前只在工作副本计算，回滚则这些效果全无，故没有“成交已确定但本笔账务未落地”的状态；Outbox只负责后续回报，不能代替账本。更早的受理事务A可持久记录RECEIVED，但不作准入或成交承诺；T才决定拒绝、挂单或成交。A与T间必须保留同一命令身份、序号和载荷摘要，否则恢复无法判断已受理请求是否已裁决，会丢失或重复应用。

## 第 5 层：已有挂单执行和 O1 案例如何落在同一事务？

**面试官：** 把 O1 接纳和 0.5 成交放到这个一致性模型中，分别哪些事实会改变？

**面试者：** 接纳 T 读取 q=2、m=2,000 与 V1，算 `Q*=3.5、R=700`，共同写入 O1 剩余 1.5、预占聚合、接纳结果和序号。之后成交 T 再检双方、价格和当前版本，写成交 0.5、甲 q=2.5、相对手 q 的反向变化及账本分录，同时把 O1 余量改成 1；风险重算后 R 仍 700。两次事务可分开，但每次内部效果必须闭合。若对手方仓位变化导致拒绝候选成交，O1仍保留余量1.5；若同一笔交易双方都通过，则买方与卖方的数量变化相反，订单两侧filled均增加0.5，不能只推进主动单。T还应记实际成交价和双方费用规则；若未来加入非零费用，权益、现金分录与风险缓冲需按明确币种和舍入同步扩展，不能沿用本例零费用结果。

## 第 6 层：T 提交前后崩溃分别允许什么结果？

**面试官：** 服务在数据库提交前崩溃与提交后、发布回报前崩溃，恢复语义有什么不同？

**面试者：** 提交前崩溃时 T 原子回滚，不能残留半张成交或单边分录；持久受理的命令仍未应用，可从 `appliedSeq+1` 重放。提交后崩溃时订单、成交、双方经济效果、结果、序号和 Outbox 已存在，恢复应重建内存索引并重发同一事件，不能重新撮合造第二个 trade。未知提交先按命令和 trade 身份查询，不能把超时当失败后盲目重做。若主库暂时不可读，正确动作是保持命令未知并暂停该市场，而非从延迟副本查不到trade就重新生成；恢复检查点也必须包含规则版本与价格证据，确保重放重现原裁决。若风控参数在恢复期间已切换到V2，历史命令仍按当时已激活的V1证据重放；追平之后再处理V2激活，不能用当前配置改写已提交结果。

## 第 7 层：Outbox 和查询回报如何保持正确但不越权？

**面试官：** 若 Outbox 被重复投递、查询投影落后，怎样避免把可见性误当作业务状态？

**面试者：** Outbox 事件含稳定业务 ID 和已提交序号，消费者按事件身份幂等，私有订单回报或页面投影可暂时落后，但不能反向修改权威订单、仓位或风险状态。回报应表达覆盖到哪个版本；查询到旧版本就标明进度，而非虚构最新成交。对账可按 tradeId、订单量与分录汇总检测遗漏，修复通过有审计的补偿命令完成，不直接改写历史事实。公共行情与私有回报也是投影，不是T的提交条件；但成交回报只能引用已提交tradeId。若消费者收到序号缺口，应拉取快照或重放缺失事件，不能按到达顺序把较旧订单状态覆盖较新终态。投影修复也不应直接重发一笔新trade，而应从outbox或权威成交记录重建视图，确保消息重复不造成账户二次记账。

## 第 8 层：拆成独立 Risk、Matching、Ledger 后具体丢失什么？

**面试官：** 如果团队决定服务拆分，为什么不能照搬同样的“事务 T”名字并继续宣称保证不变？

**面试者：** 多库或服务各自提交不再有单一 T，不能原子保证资格、成交和双边账务一起可见。Risk token 可能在仓位变化后仍被使用，Matching 可能先确认成交而 Ledger 延迟；除绑定版本、撤销协议、在途成交覆盖和唯一 trade 效果外，还要由执行域按同一顺序持久确认关闭 token，并写关闭墓碑拒绝迟到命令。TTL 到期不是执行域已关闭的证据，过期请求仍可能排队或在途；额度只能在关闭确认且在途效果已覆盖后释放。没有这组协议就失去 T 的原子性，对账只能发现偏差，不能防止超限成交。

## 第 9 层：并发、epoch 和 Go 单线程如何纳入一致性证明？

**面试官：** 单市场由 Go 单 goroutine 处理时，是否已经证明跨重启与主备下的一致性？

**面试者：** 只证明同一进程内按该 goroutine 的顺序访问内存，不证明命令已持久、提交耐久或旧 owner 不再写。必须把 `marketSeq/appliedSeq/ownerEpoch` 与事务条件更新放进持久存储，只有当前 epoch 且处理下一序号的 T 能提交；部署还要兑现数据库复制耐久性承诺。旧主即便内存队列里仍有十条待撮合消息，失去epoch后也须逐条提交失败并停止消费，不能把消息已经出队当作仍有裁决权。进程内 channel 适合串行化工作，不是跨实例 fencing，也不能代替恢复位置和幂等身份。若服务部署两副本，二者各有一个单线程 goroutine 仍能同时处理同一市场；只有持久epoch条件让其中一方写入失败。主备切换后还要从已提交游标恢复，不能以本地内存最后读数当作权威进度。

## 第 10 层：怎样用一组故障反例验收端到端闭环？

**面试官：** 给出最能暴露“局部都成功、全链路却不一致”的验证场景，并总结易错边界。

**面试者：** 先接纳 O1，再让成交 T 在提交前崩溃，确认成交、仓位和账本均无变化；恢复后提交一次，再于 Outbox 发布前崩溃并重复投递，确认只有一个 trade，q=2.5、O1 余 1、R=700；最后撤余 1，得成交 0.5、撤销 1、q=2.5、R=500、现金 1,000。核心机制是明确不变量加单一提交边界；易错是把对账、消息幂等当原子性；单边成交留存就是反例。还要故意让账本写入校验失败，确认整个T无订单filled与仓位变化；之后恢复再提交，应只产生一个trade和一组平衡分录，才能证明失败路径也闭合。反向再测提交已成功但响应丢失，重复命令必须读取同一结果；若多出一个tradeId或filled从0.5变1.0，就说明幂等边界与原子提交没有覆盖到同一业务身份。

## 机制、易错与反例收束

- **机制：** 将订单数量守恒、双边成交身份、持仓/账本变化、风险预算、命令结果和处理位置放进 T；T 后用 Outbox 投影，未知提交按身份查询恢复。
- **易错：** 把服务都“最终成功”当作原子性，或以对账代替事前门禁；拆域时 TTL 到期也不证明执行权已关闭，必须有执行域同序关闭确认与迟到墓碑。
- **反例：** 若成交已扣 O1 余量、甲 q 已变 2.5，但账本无对应双边分录，订单局部正确仍是全链路不一致；事务前失败应全无，事务后失败应可唯一恢复。
