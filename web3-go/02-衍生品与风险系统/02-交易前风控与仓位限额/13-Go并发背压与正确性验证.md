# 大问题 13：Go 怎样在热点和过载下守住风控边界？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 逐仓永续、q/B/E/R | 本仓用专用现金交易价格差；q 是净仓，B 是现金，E 含浮盈亏，R 覆盖持仓和挂单风险。 | 不是买 ETH 现货，外部钱不自动可用，R 也不是已扣现金。 |
| IM、Q*、Mark | IM 是初始保证金要求，Q* 是最坏绝对仓位，Mark 是估值参考价。 | 保证金不是手续费；资金够不代表数量通过，Mark 不保证成交价。 |
| owner、ownerEpoch | owner 是当前有权处理市场的实例，epoch 是它的任期号。 | Go 内存里只有一个处理者仍不够，数据库必须拒绝旧任期写入。 |
| goroutine、状态所有权 | goroutine 是 Go 的并发执行单元；所有权规定谁可以改一份状态。 | 接入可并发，同市场订单簿和风险索引不能由任意任务直接修改。 |
| 不可变快照、工作副本 | 前者供只读任务参考，后者供业务提交前独立试算。 | 不能共享可变内容，也不能把未提交草稿发布成成交。 |
| 工作池、并行预计算 | 用数量受控的执行者提前算建议，计算可以同时进行。 | 建议不产生准入权；O2 先算完不代表可以跳过 O1 提交后的状态。 |
| 版本再检、共同序号 | 提交前核对建议依赖的状态是否还有效，业务仍按已定顺序应用。 | O1 先提交后，基于旧快照算出的 O2 必须重算为拟 4.5 并拒绝。 |
| channel、有界队列 | channel 是进程内通道；有界队列明确限制可积压多少任务。 | 假设容量 100 不是可靠日志，也不是性能实测；丢唤醒不许丢业务命令。 |
| 背压、高水位、退避 | 系统忙到设定程度时限制新增工作，并让调用方稍后再试。 | 受理前可以拒绝过载，已持久受理不能随意丢弃或改称失败。 |
| 事务 A / T、appliedSeq | A 保存受理事实，T 保存业务结果，appliedSeq 标记已完成处理位置。 | 数据库承担已受理义务，channel 只是提示还有工作要做。 |
| 撤单接入优先、越序 | 可以为撤单预留接入容量，但不能让已排后面的撤单跳过前面的成交。 | 到达先后与调度快慢不能改写已分配的业务顺序。 |
| 价格积压、CANCEL_ONLY | 价格更新堵塞可能使输入不可信；CANCEL_ONLY 禁止一切新成交。 | 保护不能等队列慢慢排空，价格无效时 RO 也不能新成交。 |
| context、客户端取消 | context 可结束一次调用的等待或传递取消信号。 | A 已提交后客户端断线不等于撤单，处理仍由可恢复流程负责。 |
| 连接池、COMMIT 未知 | 连接池限制数据库连接；提交确认丢失时结果可能已成功。 | 限制等待并发，但不能把超时解释成零点五成交没发生。 |
| 定点、scale、位宽、溢出 | 固定小数单位变整数；scale 是倍率，位宽决定可容纳范围，越界会失真。 | 数量价格相乘前就要保证容量，事后转宽整数补不回溢出。 |
| ceil / floor、向零截断 | 前两者为向上和向下取整；向零截断在负数上与 floor 不同。 | 需求向上、可认权益向下，不能因负数处理给账户虚增空间。 |
| big.Int、接收者复用 | big.Int 可处理大整数，但方法可能直接修改承载结果的对象。 | 对共享快照复用可变对象，会让所谓纯计算暗中改掉输入。 |
| 对象别名、浅拷贝 | 多个变量指向同一底层数据；浅拷贝只复制外壳。 | map、切片看似复制后，试算仍可能污染原订单和仓位。 |
| 纯计算、IO | 纯计算只根据输入算结果；IO 是读写数据库、网络等外部动作。 | 没有 IO 不自动保证安全，输入对象可变和数值溢出仍会出错。 |
| CPU、GC、尾延迟 | CPU 负责执行，GC 回收内存；尾延迟关注少数特别慢的请求。 | 要包含排队时间，不只量处理函数，也不能先猜加任务就提速。 |
| 高基数指标、可观测证据 | 把大量不同账户直接做指标标签会造成巨大维度；证据包括分段计时和受控明细。 | 用版本与序号关联排队、计算、提交、通知，定位瓶颈而不泄漏无限账户标签。 |
| race 检测、参考模型、故障注入 | 分别检查内存竞争、独立核对业务结果、制造断连崩溃观察恢复。 | race 没报警不证明不超限；本文是验证计划，不是已运行测试。 |
| RO、MM、H 不减、Outbox | RO 是只减仓且不许反手的约束；MM 是持仓维持保证金要求，H 为权益减 MM，成交后不得下降；Outbox 保存已提交待发回报。 | RO 不机械套普通开仓断言，通知重发也不允许重做成交。 |

## 把整篇文章压缩成一个故事

市场突然涌来大量 ETH 永续订单，工程师想“每单开一个 goroutine，算完就写”。但甲原有多仓两个，O1 买一点五、O2 买一个，各自看旧快照都通过，合起来却到四点五。因此并发只能先算建议，最终仍由有效处理者按共同顺序复核并提交：O1 在前，O2 就要看到新状态并拒绝。

队列也不是越大越安全。本文假设 channel 容量一百，满了以后，尚未受理的普通请求可以退避；已经保存到数据库的命令不能丢，哪怕唤醒提示没塞进去，也要从处理位置继续读取。给撤单留接入容量有意义，却不能让后到撤单越过已经排前的成交。

数据库慢或客户端取消时，更不能把超时当业务失败并释放风险。提交未知先查清，试算副本不能泄漏到真实状态。整数运算还要防溢出，共享 map 和大整数也要防被试算改写。最后用独立模型、故障注入和含排队的延迟证据验证，而不是靠 race 没报警或丢请求后的低延迟，宣称系统正确又高效。

**流程位置与核心机制：** 本题把 Go 状态所有权、有界资源、数据库等待、保护门禁与验证证据串起来；每次工程取舍都要回答它是否改变顺序、释放义务或制造第二份效果，而非独立背诵组件知识。

**范围前提：** 固定 ETH-USDC 线性永续、单向逐仓。初始 `q=2、C=4,000、B=1,000、Mark=2,000`，`r=10%、h=5%、Qmax=4、Nmax=8,000`。O1 买 `1.5@2,000`，O2 独立买 `1@2,000`；O1 部分成交 `0.5` 后 `q=2.5、remaining=1、R=700`，撤后 `R=500、B=1,000`。单市场一个有效 owner，受理 A 与同库业务事务 T 不变；不为提高吞吐改成异步跨库结转。以下队列容量仅是说明策略的假设值，不是实测能力；不创建 Go 工程或执行工程测试。

## 第 1 层：goroutine 怎样分工而不分裂权威状态

**面试官：** Go 怎样在热点和过载下守住风控边界，能不能每个订单一个 goroutine，分别检查余额后修改订单簿？

**面试者：** 接入和查询可以并发，但同一市场的业务状态由一个有效 owner 按共同顺序应用。订单簿、活动余量和风险索引不允许任意 goroutine 直接改，事务工作副本也不能在提交前发布；只读任务拿不可变快照。O1 先获得资格后，O2 必须看到 Q*=3.5 的状态，算出候选 4.5 而拒绝，不能两边各读 q=2 后分别通过。Go 内存所有权只减少数据竞争，数据库仍要校验 ownerEpoch 和处理位置。验证时既要检查共享引用是否被修改，也要检查这个业务结果，race 检测没有报警并不证明没有并发超限。

## 第 2 层：并行预计算为什么还需要版本再检

**面试官：** 单 owner 可能成为热点，如果让工作池并行算 O1、O2 的风险，再由 owner 写结果，怎样避免把旧计算当成有效许可？

**面试者：** 工作池只能返回带状态、价格和配置版本的建议，不产生准入权。若两笔都基于初始快照计算，O1 候选 Q* 为三点五，O2 为三，看似各自通过；O1 提交后，O2 的前置版本已失效，必须按当前订单重新计算，得到四点五并拒绝。不能因为计算任务完成顺序不同而改写已分配序号。我会强制安排“O2 先算完、O1 先提交”的调度作为反例，检查失效建议被丢弃。版本核验和写入都放在同一事务控制之下；单独读版本再异步提交，仍然留下检查后状态改变的窗口。

## 第 3 层：有界 channel 满了，已受理义务放在哪里

**面试官：** 版本再检会增加等待，如果 owner 的 channel 容量假设为 100，已经满了，第 101 条该丢弃还是无限加 goroutine？

**面试者：** 两者都不行，要先区分是否已经提交 A。受理前可以明确返回过载并要求退避；已经受理就必须保留数据库中的完整命令，channel 只是唤醒提示，重启或漏通知都能从 appliedSeq 后读取。可以不把第 101 条塞进内存，但不能删除其持久义务或谎称已拒绝。并发数、字节数、受理积压和最老等待时间都要有界管理，达到高水位就停止普通新增受理，而非把压力转成无限数据库日志。我会用容量一的队列推演漏通知与进程退出，预期两条已受理命令仍各处理一次，不因 channel 关闭而释放预占。

## 第 4 层：保护撤单不能偷换成已受理命令越序

**面试官：** 队列已经积压，用户急着撤单，能不能开一个高优先级 goroutine 绕过前面订单直接改 remaining，价格更新又怎样保护？

**面试者：** 不能绕过共同权威顺序。可以在分配序号前给撤单和控制输入预留接入容量、限制普通单来源，减少未来拥塞；一旦序号已经确定，就不能让后到撤单跳过前面的成交。价格接收过旧或激活积压时，要先失效关闭普通准入和执行，价格无效则 CANCEL_ONLY，不能等旧价慢慢过期。若前面卡的是经济输入缺口，先保护并补齐义务，撤单只能等待有序应用。验证可以固定“成交在前、撤单在后”的序号再反转到达时间，预期始终先结转真实成交、只撤余量，而不是谁的 goroutine 调度快谁赢。

## 第 5 层：数据库慢时怎样限制资源而不误判提交

**面试官：** 既不能越序，数据库慢会把所有请求拖住，Go 里怎样设超时和连接池，才不把客户端取消变成业务取消？

**面试者：** 我会限制等待数据库的并发和每批预取规模，业务 owner 只推进当前下一序号，不堆出无限事务。接入请求 context 取消只结束本次等待；A 已提交后，由可恢复处理流程负责命令，不能自动撤单。T 的执行可以有超时，但 COMMIT 遇到断线时结果未知，要暂停后续应用，查询结果和 appliedSeq，确认后才更新内存。工作副本失败就丢弃，不能泄露半成状态。验证时把故障分别放在提交前和提交后，预期前者整笔回滚、后者复用结果；连接池超时本身不能证明零点五成交没发生，更不能据此退占用。

## 第 6 层：数值和对象别名怎样破坏“纯计算”

**面试官：** 超时处理清楚了，即使风险计算没有 IO，Go 代码是不是只要用 int64、不用 float64 就一定安全？

**面试者：** 还不够，数量和价格各六位相乘，中间值就可能先溢出，必须在乘法前选择足够位宽，并校验输入范围。需求向上取整、可认权益向下取整，负数不能把向零截断误当 floor；成本与原始盈亏按十二位保留规则处理。若用 big.Int，还要防止复用可变接收者改掉共享快照，切片和 map 的浅拷贝也不是真独立工作副本。我会用独立参考算式与边界生成检验 R，并检查计算前后输入摘要不变。O1 部分成交后的预期仍是 R=700，撤后才是 500，这比“用了整数类型”更能说明语义正确。

## 第 7 层：怎样区分 CPU 热点、存储慢和输入失效

**面试官：** 这些保护都可能降低吞吐，线上发现尾延迟增加时，你怎样判断该优化计算、数据库还是队列，而不是简单加 goroutine？

**面试者：** 我会把受理等待、已受理积压年龄、纯计算、锁与事务提交、Outbox 交付分别计时，并关联 seq、decisionId、价格和配置版本；账户身份放受控明细，不直接做无限高基数指标。再结合 CPU、分配、阻塞和 GC 证据定位热点，同时观察保护原因、提交未知次数与重评进度。压测设计要包含热点账户、普通单和撤单混合，分别注入慢数据库、价格积压，检查延迟上升时仍否执行保护。延迟分位数应覆盖排队时间，不能只测处理函数。只有实际采样后才讨论批量预取或索引优化，不能先宣称加工作池就提高某个倍数。

## 第 8 层：怎样用可复核证据证明优化没有改错结果

**面试官：** 假设据这些证据做了优化，你会怎样验证它既没越限、没双成交，也没有靠丢请求制造低延迟？

**面试者：** 我会让独立参考模型与实现处理同一条已定序命令流，对照数量闭合、风险公式、双方账本平衡和唯一效果，再随机生成重复、关闭、价格及配置交错。已受理命令必须能找到结果或明确待处理义务，不能只统计成功响应。并发调度检查版本失效，race 检测补充内存安全，故障注入覆盖 A/T 提交两侧、重启和旧 epoch 写入。性能测试再核对积压、拒绝率及撤单尾延迟，避免把丢弃工作当优化。普通准入必须 E≥R；RO 则检验有效价格、方向、可平量和 H 不减，不能把所有路径机械套同一断言。这里是验证计划，不是已跑出的结果。

## 收束：机制、易错边界与反例

- **讲透的机制：** 并发用于接入、只读计算与交付，不分裂市场裁决；版本再检约束并行建议；有界资源和背压控制新增压力，持久命令承担已受理义务。
- **最易答错：** channel 不是可靠日志，context 取消不是撤单，race 检测不等于业务正确。撤单接入优先不意味着已受理越序；盲目扩大工作池可能增加冲突、存储等待和尾延迟。
- **反例检验：** 初始状态并行预算 O1、O2，强制 O2 先算完但 O1 先提交，最终只能保留 O1，O2 拟 `Q*=4.5、N=9,000` 被拒绝。随后 O1 成交 `0.5`、重复关闭并重启，预期 `q=2.5、filled=0.5、canceled=1、R=500、B=1,000`，不能多一笔效果或因丢命令显得更快。
- **证据边界：** 本文将验证方法融入工程追问，仅给出可执行的检查思路和手推预期；没有运行 Go、数据库并发、故障注入或性能测试，不新增单题 MVP。
