## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| ETH-USDC-PERP、线性永续 | PERP 表示永续合约；用 USDC 计算 ETH 价格变化对应的盈亏，不按普通到期日结束。 | 本专题不交割 ETH，也不从现金扣除全部名义本金。 |
| 合约乘数、数量与价格单位 | 乘数规定一单位合约对应多少基础数量；数量和价格单位一起决定金额。 | 教学乘数为 1，数量用 ETH，价格用 USDC/ETH，不能脱离单位套公式。 |
| 单向净持仓 q、多空 | 一个数表示当前方向与数量，多仓为正、空仓为负；多随上涨获利、空随下跌获利。 | q=2 是多两个，q=-1 是空一个，普通反向成交可能穿零。 |
| 逐仓、全仓、抵押物 | 逐仓划出专用资金；全仓按规则共享一个抵押池；抵押物是用于支持风险的资产。 | 本文只实现逐仓，外部资金不自动可用；全仓也只共享规则纳入的池。 |
| B、C、A | B 是已记账现金，C 是剩余持仓入场成本，A 是平均入场价。 | 主例 B=1,000、C=4,000、A=2,000；C 不是从 B 扣掉的本金。 |
| 已实现损益、U、资金费 | 已实现损益已经落账，U 是尚未兑现的持仓盈亏，资金费是永续持仓按规则发生的支付。 | B 已含已入账项目，不能重复加历史盈利；主例手续费和资金费均为零。 |
| Equity / E、IM、MM、Available | E 是现金加浮盈亏；IM 是初始保证金要求；MM 是维持保证金要求；本文 Available 是 E−R 的风险空间。 | 四者不同，保证金不是手续费；初始 E=1,000、IM=400、MM=200、可用 600。 |
| 杠杆 | 用较少保证金承担当量更大的合约风险，改变资金占用和收益率感受。 | 既定数量的盈亏按价格差计算，不能算完再乘一次杠杆。 |
| Mark / m、M1 | Mark 是用于风险估值的参考价，M1 标识其中一份价格快照。 | 主例 m=2,000，不保证实际成交也在 2,000；执行仍要检查双方限价。 |
| 限价、GTC、订单簿 | 限价限定最差可接受价格；GTC 可持续等待；订单簿保存买卖报价与顺序。 | 本例取已有挂单价成交，找得到对手且门禁通过才可能执行。 |
| 普通单、Reduce-Only / RO、OCO | 普通单可开反向仓；RO 强制只减仓不反手；OCO 是需真实保证的一单执行取消另一单。 | 本基线没有 OCO，不能默认买卖互相抵消；RO 也要分配可平量并逐笔重检。 |
| b/s、u/v、Q* | b/s 是普通买卖余量，u/v 是 RO 已分配买卖余量，Q* 是保守区间中的最大绝对仓位。 | 覆盖不同成交顺序，不能只拿当前 q 或净挂单量判断未来风险。 |
| Qmax、Nmax、名义敞口 | Qmax 限 ETH 数量，名义额用 Mark 把风险数量换成 USDC，Nmax 限该金额。 | 教学上限为 4 ETH、8,000 USDC；名义额不是现货应付金额。 |
| G、L、R、风险预占 | G 是持仓加普通订单毛数量，L 是不利成交价差缓冲，R 是总风险需求；预占把未成交义务先算入。 | 占用额度不是扣现金或确认亏损，也不能在 R 外再重复减一份订单需求。 |
| NORMAL / REDUCE_ONLY / CANCEL_ONLY、H | 三种模式依次为普通交易、受约束减仓、禁止新成交；H 是权益减持仓 MM 的健康缓冲。 | RO 要求成交后 H 不下降；价格无效时进入 CANCEL_ONLY，连 RO 也停。 |
| 受理、接纳、成交、终态 | 依次是请求已保存、订单获准、交易实际成立、订单不再有可执行余量。 | 审批不等于成交，低于 MM 只是交给处置方评估，不代表已强平。 |
| 事务 A、事务 T、PostgreSQL | A 保存请求与顺序；T 用 PostgreSQL 数据库将相关业务结果打包共同保存。 | 订单、双边仓位账本、风险、结果和待发通知都在 T 中一起成立。 |
| marketSeq、appliedSeq、输入版本 | 命令顺序、已应用位置，以及所用价格配置和状态的身份。 | 决策要有同一时点的证据，缓存“最新值”拼接不能直接裁决。 |
| ownerEpoch、fencing | 当前市场处理者的任期号，以及在提交处阻止失权旧实例写入的机制。 | 一个 Go 线程不替代持久处理权，主备切换不能同时造两份结果。 |
| RequestKey、payloadHash、幂等 | 原请求身份、内容指纹，以及重复提交不增加业务效果的规则。 | 同键同内容找回原结果，同键改数量冲突；拒绝结果也不能借重试改成新申请。 |
| UNKNOWN、CloseIntent、TTL、墓碑 | UNKNOWN 表示结果未明；CloseIntent 请求关闭原意图；TTL 是时长；墓碑持久阻挡关闭后的迟到命令。 | 超时或到期不证明失败，也不自动释放；关闭必须与执行共同排序。 |
| original / filled / remaining / canceled | 原始量、已成量、剩余量、已撤量。 | 主例最终 1.5=0.5+0+1；成交把订单义务转成持仓义务，撤单只去掉未来余量。 |
| Outbox、查询投影、在途覆盖 | Outbox 是同事务待发事件，投影是页面视图，在途覆盖为跨域尚未结转成交保留风险预算。 | 本文同库无本笔异步结转暂态；拆库必须补协议，不能把通知延迟当成交未成立。 |
| MVP、定点数、伪代码 | MVP 是最小教学模型；定点数用固定小数倍率表示整数；伪代码说明逻辑而非完整运行工程。 | 总览只做手工推演，不证明数据库并发、灾难恢复或性能已经通过。 |

## 把整篇文章压缩成一个故事

甲在 ETH-USDC 永续逐仓单元里有现金一千，持多仓两个、均价两千。Mark 也是两千，因此权益一千。按本专题教学规则，初始保证金四百、维持保证金二百。他提交买一点五的 O1，系统先保存身份，再检查同一版本的资金、仓位、挂单和规则，通过后总风险需求变七百，现金并没被扣走。

另一笔买一个的 O2 随后到来：拟需求九百虽有权益支持，最坏仓位四点五、名义九千却超过四与八千的上限，所以拒绝。O1 后来成交零点五，仓位二点五加余单一，总需求仍七百；正式撤余单后才降到五百，原单量也闭合为零点五成交加一撤销。

十三篇文章就在这条线上逐层排雷：输入不能拼时点，并发不能重复占额，成交前要重检双方，RO 不能反手也不能靠差价越平越险。价格或参数变化先失效再重评；超时先查原事实，关闭要防迟到，回报可晚但成交不能重做。最终证明的不是“审批过一次”，而是执行资格从建立到结束始终受约束；Mark 不保证成交，强平与实测结论也不能凭空宣布。

## 一、文字全流程

### 1.1 产品、执行与状态基线

| 维度 | 本专题约定 |
|---|---|
| 产品 | `ETH-USDC-PERP` 线性永续，合约乘数 1，数量以 ETH、价格以 USDC/ETH 表示 |
| 账户 | 单向净持仓；一个子账户、一个市场及其专用 USDC 现金桶组成逐仓风险单元 |
| 执行 | 链下托管、中央限价订单簿、限价 GTC；成交价格取已有挂单价，禁止自成交 |
| 经济口径 | 加权平均成本；永续不交割 ETH、不扣名义本金；主案例手续费、资金费均为 0 |
| 裁决范围 | 单市场命令、成交、撤单、保证金划转、资金费输入、价格激活、参数激活进入共同权威顺序 |
| 提交方案 | 教学基线采用合并协调层；订单、风险预占、相关双方仓位/账本、命令结果和 Outbox 在同一 PostgreSQL 事务提交 |
| 所有权 | 订单模块决定匹配；持仓模块计算数量/成本；账本模块记现金与分录；风控模块计算准入和执行门禁；协调层原子提交 |
| 持久与主备 | 数据库保存命令序号、处理位置、owner epoch 和结果；承诺的复制耐久性必须由部署保证，不能用本地 channel 代替 |
| 范围外 | 不实现全仓、多抵押物、组合保证金、跨库成交结转、市价/IOC/FOK、链上结算和强平执行算法 |

这是为说明风险正确性选定的教学架构，不要求真实平台合并所有服务，也不声称相邻专题已经采用同样提交方案。产品和损益口径与[持仓成本与盈亏](../../01-撮合交易与核心链路/05-持仓成本与盈亏/README.md)兼容；跨域异步结转作为明确改变条件后的比较。

无需安装 Go、数据库或队列。环境准备仅为理解上述假设与整数单位；末尾提供手工伪代码，不创建运行工程。

### 1.2 贯穿案例：数量限额与资金充足是两道检查

新设独立案例，不接在相邻专题的成交序列后执行：

- 甲的逐仓现金 `B=1,000 USDC`，已持多仓 `q=2 ETH`，均价 `A=2,000`，成本 `C=4,000 USDC`。
- 有效 Mark Price `m=2,000`，价格身份 `M1`；未实现盈亏 `U=0`，权益 `E=1,000`。
- 配置 `V1`：IM 率 `r=10%`，MM 率 `h=5%`；数量限额 `Qmax=4 ETH`；名义敞口上限 `Nmax=8,000 USDC`。这些均为教学值。
- 初始没有活动订单，现有仓位 IM 为 `400`，MM 为 `200`。`B` 已包含历史已入账损益，不能再加一次历史盈利。
- 候选 O1：买入 `1.5 ETH @ 2,000`；另一独立请求 O2：买入 `1 ETH @ 2,000`。
- 主流程按给定后续流动性，让 O1 先挂单、后成交 `0.5 ETH @ 2,000`，再撤余下 `1 ETH`。对手方有合法的空头开仓资格、足够抵押；正文只展示甲的数值，不省略双边事务义务。

| 阶段 | 甲仓位 q | 普通买单剩余 b | 最坏绝对仓位 Q* | 保守总需求 R | 权益 E | E−R |
|---|---:|---:|---:|---:|---:|---:|
| 初始 | 2 | 0 | 2 | 400 | 1,000 | 600 |
| O1 获准且挂单 | 2 | 1.5 | 3.5 | 700 | 1,000 | 300 |
| O2 在 O1 后申请 | 2 | 拟为 2.5 | 拟为 4.5 | 拟为 900 | 1,000 | 拟为 100 |
| O2 拒绝后 | 2 | 1.5 | 3.5 | 700 | 1,000 | 300 |
| O1 成交 0.5 | 2.5 | 1 | 3.5 | 700 | 1,000 | 300 |
| O1 余量撤销提交 | 2.5 | 0 | 2.5 | 500 | 1,000 | 500 |

O2 虽然资金需求只有 900、权益足够，但 `4.5 > 4` 且 `4.5×2,000 > 8,000`，仍被拒绝。风险占用没有从现金扣走：整个主案例 `B=1,000`，变化的是执行义务与可准入空间，不是退款进账。

### 1.3 主流程：从意图到业务收尾

```text
客户端提交 O1〔身份、账户、市场、买卖、限价、数量、Reduce-Only 标志、请求键〕
    ↓
接入层：鉴权、规范化十进制、精度、粗限流及静态产品检查
    ├─ 失败 → 未受理拒绝；不产生风险预占
    └─ 通过 → 持久命令事务：绑定请求与载荷，分配 marketSeq
                      ↓ 提交
                RECEIVED：可恢复，尚未保证风险通过或成交
                      ↓
有效 owner 按已提交顺序处理命令
    读取该顺序点的现金、仓位、活动订单、价格/配置、保护模式
    在事务工作副本中：核验版本与输入有效性 → 算 Q*、R、候选准入
    ├─ 拒绝 → 持久原因和输入版本，推进处理位置，不生成活动订单
    └─ 通过 → 建立订单剩余量及对应预占，获得受约束的执行资格
                      ↓
    如有可匹配对手单：每笔成交前检查双方最新状态和执行语义
        ├─ 门禁不满足 → 不确定成交；阻断/撤销失效普通订单并继续解释结果
        └─ 门禁满足 → 生成成交，减少订单剩余量，更新双方仓位和经济效果
                      ↓
    同一事务提交：订单 + 风险状态 + 双边仓位/分录
                    + 请求结果 + 处理位置 + Outbox
                      ↓
    内存订单簿应用已提交变化；提交未知时暂停并查询，不继续发布
                      ↓
O1 挂单等待后续对手单，或因全成/权威撤销结束
    后续成交与撤单仍按同一顺序和事务规则裁决
                      ↓
最终核对：累计成交 0.5 + 撤销 1.0 = 原始 1.5
          仓位 2.5、均价 2,000、现金 1,000、订单剩余/预占为 0
                      ↓
查询/私有回报追上版本：报告接纳、部分成交、撤销及最终风险占用
```

共同事务不表示每条命令都扫描整个市场。订单簿可用内存索引，持久订单与已提交结果是恢复依据；工作副本的匹配结果在提交前不对外发布。对手方风险状态和成交价格也必须通过门禁，不能只有甲通过就生成双边义务。

### 1.4 主要拒绝、超时与失败路径

```text
参数非法/账户无权限 → 在受理前拒绝
余额足够但仓位超限 → 保存 LIMIT_EXCEEDED；不建订单、不改变原预占
同键同载荷 → 返回原命令/结果；同键异载荷 → CONFLICT

命令入库后回包超时 → UNKNOWN/处理中，按原请求键查询或重投
    用户要放弃 → 提交 CloseIntent，与 Place 在同一顺序裁决
    Close 先到 → 持久关闭墓碑；迟到 Place 不得创建订单
    Place 先到 → 保留已成交，只关闭实际余量

撤单已发送、尚未裁决 → 预占保留；不能依据客户端页面释放
事务提交前失败 → 所有业务变化一起回滚；原命令仍待处理
事务提交后回复/推送失败 → 原结果重用；不重复成交或释放

价格陈旧/配置未知/经济输入缺口 → 普通开仓阻断，必要时进入 CANCEL_ONLY
有效价格下风险恶化 → 重评存量挂单，撤销不再支持的普通订单
    仍低于 MM → 提交带证据的风险处置请求；强平执行方再次复核
```

`CloseIntent` 与相邻订单专题的 `AbortIntent` 同属“持久关闭意图”协议，不是普通“订单不存在”响应。本基线若受理回执已含序号，关闭通常排在 Place 后；墓碑仍覆盖不同网络路径造成关闭先到的情况。

### 1.5 完成阶段与资金含义

| 阶段 | 已承诺 | 没有承诺 |
|---|---|---|
| 命令持久受理 | 原身份可恢复处理 | 风控通过、挂单或成交 |
| 业务结果事务提交 | 准入结果、订单/预占及本命令成交经济效果共同成立 | 页面已经收到 |
| 活跃挂单 | 在当前规则下有受约束的执行资格 | 未来价格变动后仍无条件可执行 |
| 终态提交 | 该单不能再成交，已发生经济效果已共同结转 | 用户能提现全部现金 |
| 投影可见 | 展示覆盖到指定版本 | 又发生一次资产或风险动作 |

合并提交消除了本基线内“成交已提交但该笔仓位账本还未结转”的暂态；不将这个便利推广到拆库模型。异步方案必须保留在途成交的风险覆盖，不能看到订单余量变小便提前释放。

## 二、核心板块

| 板块 | 决定什么、为什么核心 | 权威状态与交互 |
|---|---|---|
| 风险状态与输入 | 决定一次判断究竟使用哪组事实 | 现金/仓位/订单归原模块维护；协调层提供同序快照，价格/配置通过版本化激活 |
| 准入计算内核 | 决定候选请求是否创造额外执行资格 | 无 IO 计算 Q*、名义敞口、IM/损失缓冲、原因码；不直接修改钱 |
| 预占与订单资格 | 决定多个入口能否重复花同一空间 | 活动订单剩余量、预占明细、RO 可平量；与接纳共同提交 |
| 执行门禁与经济结转 | 决定已有订单此刻能否成交及如何转为持仓 | 最新权威状态、实际成交价、双方约束；成交/仓位/账本/预占共同提交 |
| 持续重算与保护 | 决定旧资格何时暂停、撤销或重新授权 | 价格/经济/config 变化触发，处置模式与原因可审计 |
| 持久工作流与恢复 | 决定重试、未知、崩溃后是否仍只有一份效果 | 请求身份、命令序号、处理位置、epoch、结果、Outbox；查询不拥有裁决权 |

## 三、核心 20%

| 核心机制 | 流程位置 | 为什么核心 | 不掌握的后果 | 重点深入细节 |
|---|---|---|---|---|
| 带版本的一致风险快照 | 准入/执行/重算 | 决策依赖多类变化 | 拼出从未成立的风险状态 | 风险单元、序号、价格年龄、配置身份 |
| 可达敞口与保守需求分离 | 准入 | 限额和保证金不是同一指标 | 买卖单抵消、资金够就超限放行 | Q* 区间、R 的上界、成交不利价差 |
| 检查与预占原子化 | 接纳 | 阻止并发穿透 | 两笔各自通过、合计超限 | 事务工作副本、唯一键、版本条件 |
| 剩余订单转持仓 | 部分成交/撤单 | 风险应转移而非凭空消失 | 成交先释放、撤单再重复释放 | 剩余量、成本/现金、整体重算 |
| 执行端再检与 RO | 每笔匹配前 | 入口通过不能覆盖后续变化 | 旧许可成交、平仓穿零 | 双边门禁、可平量分配、价格保护 |
| 动态生效与保护模式 | 价格/配置/经济事件 | 风险随输入改变 | 被动超限仍继续增仓 | 确定生效点、拒绝新风险、撤单/处置 |
| 身份、提交与恢复 | 全程 | 网络重试不等于新业务 | 双占、双成交、TTL 早释放 | 命令/业务身份、墓碑、fencing |
| 数值与证据 | 全程 | 边界一单位即可反转决策 | 溢出、精度错判、无法审计 | 定点、有向舍入、版本证据、反例 |

“20%”表示优先掌握决定正确性的机制，不是以少量题目代替完整覆盖。

## 四、共同设计与规则

### 4.1 现有仓位、权益与限额

以下用人类单位，实际使用定点数：

```text
q：有符号 ETH 仓位；C：非负剩余入场成本
U = sign(q) × (abs(q)×m − C)，空仓 U=0
E = B + U                         # B 已含已入账损益/费用/资金费
IMpos = ceilMoney(r×m×abs(q))
MMpos = ceilMoney(h×m×abs(q))
```

权益不是现金，也不是可提现金额。风险占用是对执行资格的约束，不将它伪造成一次现金扣款或费用分录。保证金划出必须与订单竞争同一风险空间并有账务转移身份；补保证金必须实际入账才改善 E。

普通订单既可能减仓也可能穿零，**方向相反不等于 Reduce-Only**。设普通买单剩余量总和为 `b`，普通卖单为 `s`，RO 买/卖单已分配余量分别为 `u/v`，全部非负：

```text
没有 RO：普通订单可达净仓区间 [q − s, q + b]
包含 RO：采用保守区间 [q − s − v, q + b + u]
Q* = max(abs(q), abs(q − s − v), abs(q + b + u))
准入普通单：Q* <= Qmax 且 m×Q* <= Nmax
```

包含 RO 的区间是上界，不声称每个端点都可达，因为 RO 会随仓位变化被裁撤。它不能被简单忽略：q=2、普通卖单3、RO卖单2，若 RO 先平掉2、普通卖单再开空3，最终可到 −3；只看原来的 [−1,2] 会漏算。接纳 RO 时若扩大保守端点到超限，必须先同事务撤掉导致冲突的普通订单再重评，不能假称“RO 永不影响其他挂单预算”。本例选择先撤同方向普通订单、必要时继续撤最晚普通订单，直到限额支持；若仅现有仓位已被动超限，允许不扩大绝对仓位的 RO，但所有普通增险资格保持关闭。

此处不支持 OCO 互斥承诺；不能假定买卖同时成交并先相抵，也不能用 RO 给普通订单提供保证金抵扣。数量限额、名义限额可以并存，价格上升时后一项可能被动超限；这不是历史成交非法，而是后续增险资格要收紧。

### 4.2 保守保证金预占：明确牺牲哪些资本效率

本教学采用**现有仓位加全部普通订单的毛数量上界**，不声称是最省保证金的算法：

```text
G = abs(q) + b + s
L = Σ普通买单[remaining × max(limit − m, 0)]
  + Σ普通卖单[remaining × max(m − limit, 0)]
R = ceilMoney(r×m×G) + ceilMoney(L)
准入普通单：输入有效、模式 NORMAL、限额通过、E >= R
展示分解：Rpos = ceilMoney(r×m×abs(q))；Rorder = R − Rpos
```

`G >= Q*`；因此资金规则可能拒绝一个按可达净仓精算本能通过的订单，属于显式保守取舍。L 覆盖以当前 Mark 估值时、限价单在最差合法成交价带来的即时损失；买成交价不高于限价，卖成交价不低于限价。普通反向单的平仓损失已经通过 E 的现有 U 与 L 处理，不能再把全部名义成交款扣现金。

在固定 Mark、零费用和线性合约下，一笔买入 `d>0` 的权益变化为 `d×(m−p)`，卖出为 `d×(p−m)`；减仓导致的现金/未实现损益转换不额外创造权益。普通订单成交后 G 不增加，已预留的 L 可以覆盖实际不利价差，构成保守预算的依据。价格和配置变化后必须重新计算，不承诺旧 R 永久有效。

主例 O1：`R=10%×2,000×(2+1.5)=700`。独立变体把其买入限价改为 2,100：`L=150`、`R=850`；不能仍宣称只占 300。加入非零费用时，要固定费币、费率/舍入，并在 R 加最大执行费用缓冲；不能只在成交后才发现现金不足。

### 4.3 Reduce-Only 与保护模式

RO 的可平量与保证金预算分开：

- 对非零 q，RO 方向必须相反；有效 RO 剩余量之和不得超过 `abs(q)`。本例按接纳顺序分配额度，超额新申请直接拒绝，不暗中缩量。
- 普通成交或处置改变 q 时，在同一事务按原优先级保留可支持的 RO，超额尾部订单整体撤销；本方案不实现自动改单。旧 RO 不得在新方向仓位上复活。
- 每笔 RO 成交再检方向、实际量不超过当前仓位及其获分配余量，并检查有效价格和执行保护。以 `H=E−MMpos` 为教学健康缓冲，要求实际成交后 `H' >= H`；这明确排除“只减数量却用极差价格扩大风险”的成交。多笔按实际执行顺序再算，不复用旧 H。
- RO 不走普通单 `E>=R` 的开仓门槛，不提供普通保证金抵扣；因此可能挂着但当前没有可执行价格。用户应看到门禁原因，而非保证一定平仓。
- `NORMAL` 允许普通单；`REDUCE_ONLY` 只允许满足上述门禁的 RO、撤单和经确认的补保证金；`CANCEL_ONLY` 禁止一切新成交，只保留关闭与安全管理动作。本专题选价格无效时进入 `CANCEL_ONLY`，**不把无可信价格下的 RO 一律认定安全**。
- 低于 IM 不自动等于强平；低于 MM 进入风险处置评估。强平执行权限、成交价带与破产处置在相邻专题定义，不用 RO 门禁阻挡协议要求的独立清算路径，也不虚构清算已经完成。

### 4.4 顺序、事务与版本

```text
命令受理事务 A
    RequestKey 唯一键 + 规范化摘要 + marketSeq + 完整命令
    ↓ 持久受理，可返回 RECEIVED
业务应用事务 T〔只处理 appliedSeq+1〕
    检查 ownerEpoch、前置版本、活动 priceId/configId 与模式
    → 在工作副本计算订单/预占/匹配/经济变更
    → 校验双方后态，登记同币种平衡分录与唯一效果
    → 原子保存结果 + 状态 + appliedSeq + Outbox
    ↓ 提交后
内存索引/查询通知更新；提交未知先查确定结果
```

数据库中的市场控制行协调顺序与 fencing；受理序号分配和业务应用均使用明确的行锁/条件更新。只有一个有效 owner 应用该市场命令，数据库仍检查 epoch。所有影响逐仓风险的写入必须走此入口；不允许外部持仓服务绕过它改仓。

价格入口有两个不同用途：内容激活命令决定回放时使用哪个 priceId；健康门禁根据接收年龄、队列延迟和源质量阻断陈旧输入。运行时的“此刻年龄”不能从价格版本号猜测；裁决持久保存 decisionTime、priceTime、quality 和门禁结论，回放使用原证据，不重新读取当前墙钟。价格激活待应用或积压超过阈值时先停普通准入/成交，不能以“队列里旧价还没过期”为由拖延保护。

配置激活、价格更新会使旧决策版本不再适用。存量订单必须用当前状态重裁；失效普通订单确定撤销，未轮到重裁的订单先不可执行。大型市场可采用“先关闭全市场增险门禁→按截止点分批重评→追平后开放”的变体，不能一边慢扫一边信任旧通过标记。

| 对象 | 关键字段与用途 |
|---|---|
| 请求/意图 | `accountId, commandType, clientRequestId, payloadHash, intentId`；鉴权后的身份作用域，重复请求不生成第二笔业务 |

### 4.6 精度与临界值

数量和价格均取六位小数，USDC 账本六位，成本/原始盈亏十二位；费率用带分母的整数。乘积使用足够位宽，不能让 `int64` 先溢出再转 `big.Int`。风险需求向上取整到 USDC 最小单位；可认权益保守向下取整，正负值区别数学 floor 与向零截断。成本释放、现金结转及余数沿用[持仓专题](../../01-撮合交易与核心链路/05-持仓成本与盈亏/README.md)的明确规则，未入账正尾数不作为可花现金，负尾数不能忽略。

主例全部整数可精确计算；扩展到舍入边界时，必须保存原始值、结转值与余数，不能以显示均价反推成本。

## 七、工程实践：唯一的简洁 MVP

### 7.1 目标与范围

只手工验证**同一风险单元的普通同向买单准入、唯一请求、部分成交后风险转移、权威关闭与迟到下单阻断**。固定 `m=p=2,000`、零费用、IM 10%、Qmax 4、Nmax 8,000，输入全部为合法六位整数；数量用 ETH 最小单位、金额用 USDC 最小单位。

这是单线程、无崩溃的内存模拟，不实现订单簿、双边账本、数据库、价格/config 更新、RO、强平或跨域可靠性。外部给定的成交量只用于风险占用推演，不是假装实现了撮合引擎。

### 7.2 一段核心伪代码

`S=10^6`；本例 `m=2,000×S`，所以名义价值为 `m×qty/S`，保证金为其十分之一，主例金额均可整除。中间乘积使用足够位宽；所有失败在状态修改前返回。

```text
q=2*S; cash=1000*S; orders={}; keys={}; closed=set()

risk(q, orders):
    b = sum(o.remaining for o in orders if not o.closed)
    Q = q+b                            # 仅支持本例非负仓位、同向普通买单
    N = m*Q/S
    R = ceilDiv(N, 10)
    return {Q,N,R}

prepare(key, limit, qty):
    h = canonical(limit,qty)           # key 已包含账户和命令类型
    if key in keys:
        return 原结果 if keys[key].hash==h else CONFLICT
    if key in closed: return CLOSED   # 同一意图关闭后不能因迟到而重新接纳
    require limit==m and qty>0 and 精度/范围合法
    next = orders 的独立副本
    next[key]={remaining:qty,filled:0,canceled:0,original:qty,closed:false}
    x=risk(q,next)
    if x.Q>4*S or x.N>8000*S or x.R>cash:
        keys[key]={hash:h,result:RISK_REJECT}; return RISK_REJECT
    orders=next; keys[key]={hash:h,result:ACCEPTED}
    return ACCEPTED                    # 返回准入结果，不冒称已经成交

fill(key,d):
    require key in orders and not orders[key].closed
    o=orders[key]; require 0<d<=o.remaining
    next=orders 的独立副本
    next[key].remaining-=d; next[key].filled+=d
    x=risk(q+d,next)
    require x.Q<=4*S and x.N<=8000*S and x.R<=cash
    orders=next; q+=d                  # 同价成交不改变本例权益/现金
    if orders[key].remaining==0: orders[key].closed=true; closed.add(key)
    return {q,risk(q,orders)}

close(key):
    closed.add(key)                    # 也能关闭从未获准的原意图
    if key in orders and not orders[key].closed:
        o=orders[key]; o.canceled+=o.remaining; o.remaining=0; o.closed=true
    return {q,risk(q,orders)}          # 重复关闭不增加 cash
```

本模拟将已裁决的风险拒绝也绑定到原请求键，与主基线的持久结果语义一致：同键同载荷重试仍返回原拒绝，条件改善后重新申请须换新意图/请求键；同键异载荷始终冲突。`keys` 保存的是原准入结果，重复调用不会重建已经结束的订单；Close 墓碑阻止尚未裁决的迟到请求获准，当前订单进度另从 orders 查询。模拟中的整体替换不证明真实数据库的原子持久性。

### 7.3 输入与预期结果

主路径按顺序执行，独立反例另从初始状态开始，以下换回人类单位：

| 输入 | 手推预期 |
|---|---|
| 初始 | q=2、现金/权益 1,000、R=400 |
| prepare(O1,2,000,1.5) | 接纳；Q*=3.5、R=700、E−R=300 |
| 完全相同 O1 再 prepare | 返回原 ACCEPTED；不增加剩余量或 R |
| 同一 O1 数量改为 1 | CONFLICT，不改原订单 |
| 在 O1 后 prepare(O2,2,000,1) | 拒绝；拟 Q*=4.5、名义 9,000；实际仍 q=2、R=700 |
| fill(O1,0.5) | q=2.5、余单 1、R=700；不将原 300 占用全部释放 |
| close(O1)，再 close(O1) | 首次撤余量 1，累计成交 0.5、撤销 1；两次结果均 R=500、现金 1,000 |
| 已关闭 O1 再 fill | 拒绝，无新的仓位变化 |
| 独立：close(O3) 后迟到 prepare(O3,2,000,1) | CLOSED；q=2、R=400，不重新占用空间 |

这些结果是手工推演。静态检查只能支持文档结构、路径和算式，不代表 Go、数据库并发、故障注入或性能验证通过。
