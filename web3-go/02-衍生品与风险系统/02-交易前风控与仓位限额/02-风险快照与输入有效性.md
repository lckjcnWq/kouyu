# 大问题 2：怎样获得能用于裁决的一致风险快照？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 线性永续、逐仓 | 前者按价格差用 USDC 计算合约盈亏；后者把本仓风险限定在专用资金范围。 | 这里评估的是 ETH 合约仓位，不是现货付款，逐仓外资金不自动可用。 |
| q、C、B | q 是带方向的持仓数量，C 是剩余持仓的入场成本，B 是已记账现金。 | 起点分别是 2 ETH、4,000 USDC、1,000 USDC，C 不等于钱包扣款。 |
| Mark、M1/M2 | Mark 是风险估值参考价格；M1、M2 是不同价格快照的身份。 | 使用 M1=2,000 计算，不表示订单一定按 2,000 成交。 |
| 配置 V1、configId | 一整份保证金、限额、精度等规则及其唯一身份。 | 不能拿 V1 的保证金率搭配另一版限额，拼成不存在的规则集。 |
| 权益 E、IM、R | E 是现金加未实现盈亏；IM 是持仓初始保证金要求；R 还覆盖未成交订单义务。 | 初始 E=1,000、持仓 IM 和 R 均为 400；保证金不是手续费。 |
| 一致风险快照 | 描述同一个逻辑时点的完整证据包，而非几项看起来最新的数。 | 仓位、活动订单、现金、价格、规则和模式都要能对应起来。 |
| 状态版本 | 给一份已确定状态编号，说明它更新到了哪一步。 | 仓位版本变了，依赖旧仓位计算的结果就不能直接写入。 |
| PostgreSQL、MVCC | PostgreSQL 是数据库；MVCC 让事务按规则读取某个一致的数据版本。 | 数据库一致读不自动覆盖外部行情服务和配置中心。 |
| price/config activation | 价格或规则已正式纳入本市场裁决，而不仅是网络消息已收到。 | 激活事件与订单进入共同顺序，决定订单到底使用哪一版。 |
| market sequence、appliedSeq | 前者是市场命令序号，后者是已经完成业务应用的位置。 | 序号负责先后，不能把它当成价格是否新鲜的证明。 |
| sourceTime、receiveTime、decisionTime | 分别是来源标注时间、系统收到时间、实际判断时间。 | 三种时间帮助判断源时钟偏差、网络延迟和裁决时的价格年龄。 |
| 价格质量、最大年龄 | 价格还要可信、足够及时，不只是有一个数。 | 停更十秒只是文中追问情境；能否使用要看已配置门限，不能泛化。 |
| VALID / STALE / INVALID | 分别表示有效、陈旧、无效的输入状态。 | 保存当时为何这样判断，恢复时才不会重新猜测。 |
| 墙钟、受控时钟 | 墙钟是机器显示的当前时间；受控时钟还要考虑偏差和使用规则。 | 不能因另一台机器重放时已过很久，就改判历史订单。 |
| 确定性重放 | 用原命令和原证据恢复时，得到同样的已裁决业务结果。 | 重放历史判断不等于拿历史价格批准今天的新订单。 |
| CANCEL_ONLY、RO | CANCEL_ONLY 是只保留关闭等安全动作、不允许新成交；RO 是只减仓订单。 | 价格无效时连 RO 也不能自动放行，无法估值就不能证明安全。 |
| 不可变配置、schemaVersion、哈希 | 不可变表示发布后不原地修改；schemaVersion 说明字段格式；哈希是内容校验指纹。 | 缺字段、格式不支持或内容不符，都不能擅自套默认值。 |
| owner、fencing | owner 是有权处理市场的实例；fencing 是在提交处挡住失权实例。 | 旧实例即使还活着，也不能按旧配置继续写业务结果。 |
| 事务 T、工作副本、CAS | T 打包保存业务结果；工作副本先试算；CAS 是仅当前置版本仍匹配时才更新。 | 版本检查失败就丢弃试算，不能把旧结果硬写进新状态。 |
| reason code、输入摘要 | 前者说明为何通过或拒绝；后者标识这次使用的输入。 | 审计不仅看“通过”二字，还要还原对应价格、订单和规则。 |
| token、TTL、关闭墓碑 | token 是执行许可凭据，TTL 是有效时长，墓碑是持久的禁止执行记录。 | 拆服务后到期不等于执行端已关闭；必须防止迟到许可继续成交。 |
| 物理日志偏移 | 数据库存储日志中的位置，不是市场业务事件的编号。 | 恢复要记录它与市场序号的对应，不能假定两者相等。 |

## 把整篇文章压缩成一个故事

风控要决定甲能不能再买 ETH 永续，像会计审一份材料：甲持多仓两个、成本四千、现金一千，参考价两千，用规则 V1，初始需求四百。难点不是把这些数字分别查出来，而是证明它们属于同一个已经成立的时点。

假如仓位查询已经更新为二点五，订单查询却还停在另一版本，风控就可能把一次成交遗漏或重复计算。数据库能让本库读取一致，却不能替外部行情决定何时生效。因此价格和配置都要先获得身份，按市场顺序激活，再与仓位、订单及裁决结果一起留下证据。

还有一种陷阱：价格编号最新，但来源早已停更。系统必须检查时间和质量，失效就停止新成交，不能拿 RO 标签绕过。重启后则复用历史裁决保存的证据，而不是拿今天的时钟重判昨天。结论是：数值算得对不够，输入组合也必须真实存在；恢复旧事实更不等于允许新交易沿用旧价格。

## 第 1 层：什么才叫“一致快照”

**面试官：** 风控从账本、持仓、订单、价格和配置读数据，如何保证不是把几个时间点拼在一起？

**面试者：** 风险快照不是若干服务此刻各自返回的“最新值”，而是一个有身份的逻辑状态：风险单元序号、现金/账本版本、持仓版本、活动订单版本、价格 ID、配置 ID 和保护模式。对这组不可变输入计算，结果再带上同一证据摘要。基线把相关变更放入共同市场顺序，并在业务事务应用前序状态后形成快照，所以计算读的是一个确定前态。查询缓存可以落后，但不能参与裁决。以 q=2、M1=2,000、V1 为例，E=1,000，IMpos=400；若另读到 q=2.5、却仍配旧的活动订单或旧配置，数值即使算对也不代表任何真实可用状态。

## 第 2 层：同一事务快照是否自动覆盖价格

**面试官：** PostgreSQL 的一致性读不能把账本、仓位、订单、Mark 一次性读齐吗？

**面试者：** 单库事务能为事务内行提供数据库快照，但不能自动为外部价格服务或配置中心建立共同提交点。必须把已验证的 price activation 和 config activation 作为带身份、带序号的事实纳入本地权威状态；订单裁决事务记录选用的 ID。收到网络消息不代表价格已激活，激活顺序要由市场序列决定。数据库事务隔离级别负责本地并发可见性，业务序号负责市场事实先后，二者不能互相替代。如果价格 M2 和订单 O2 同时到达，序列先后决定 O2 使用 M1 还是 M2，不根据两个服务的墙钟或 goroutine 谁先醒来决定。

## 第 3 层：价格“最新”但已经陈旧怎么办

**面试官：** 如果价格序号最新，但价格源停更了十秒，按序处理是不是仍可放行？

**面试者：** 序号新不代表市场事实新鲜。价格快照应包含 market、priceId、sourceTime、receiveTime、质量等级、来源健康摘要和有效性；裁决时按明确的最大年龄与质量门槛判断。年龄需由受控时钟比较，并把裁决时点和结论记录下来，重放则使用原证据与原裁决结果，不拿重放机器的当前时钟重算。若超过门限，普通开仓和可能扩大风险的成交停在 CANCEL_ONLY；撤单和查询可继续，RO 也不默认安全。阈值属于配置，不在价格算法专题重建。系统若只保存价格值而没有时间和质量，无法区分“平稳市场”与“输入冻结”。

## 第 4 层：行情事件滞后时，陈旧判断怎么确定性重放

**面试官：** sourceTime 受时钟偏差影响，机器重启后会不会对同一价格得出不同的新鲜度结论？

**面试者：** 需要把运行时判断与重放确定性拆开。实时激活时，利用接收端可信时钟、来源时间偏差预算和质量规则计算 `VALID/STALE/INVALID`，将这些证据、门限版本和结论写入已提交命令；应用序列以持久事件身份推进。恢复回放原命令时重用当时已确定的门禁结论，不再把历史价格同当前墙钟相减。若原事件缺少必要证据或规则版本不可读，按未知处理并限制风险扩大，而不是猜一个通过值。这让在线执行可以使用时钟作输入，同时使同一已裁决日志得到相同业务结果。

## 第 5 层：价格和仓位异步到达，顺序选什么

**面试官：** 价格每秒变化很多次，成交也持续发生。你用 market sequence，会不会因为行情队列慢而把成交乱序？

**面试者：** 本模型选择单市场统一序列来定义业务因果；价格数据可以先由价格域聚合，再以激活命令进入市场风险状态。成交、订单、撤单、风险参数与保护模式变化都按该序列应用。若将高频价格全部序列化会成为容量瓶颈，可按明确的价格快照时点批处理或只发布足够影响裁决的版本，但必须保持其语义和重放边界。不能给行情另一个不受约束的时钟，再在订单到来时拼最近缓存。序列缺口时，持仓事件不可跳过；可以把新准入关闭并补齐缺口。市场序号和数据库物理日志偏移不是同一坐标，恢复记录需映射它们而不假设相等。

## 第 6 层：配置半更新和版本不一致如何避免

**面试官：** 配置里 IM、仓位限额和费率分开推送，一台实例更新了 IM，另一台还没更新限额，怎样裁决？

**面试者：** 将完整规则集编译成不可变配置快照，带 schemaVersion、configId、语义摘要和激活序号；不得逐字段热写共享对象。裁决只引用一个已激活的完整版本，缺字段、未知 schema、哈希不符就不服务该版本。对于单市场共同 owner，激活事件在序列边界替换整个配置指针并写入 appliedSeq。若部分实例还没追上，fencing/路由不得把命令分发到旧 owner；若切换无法证明完成，就停止普通增险而不是让实例各自回退默认值。配置内容的正确性校验和运行时原子发布是两件事，需分别检查。

## 第 7 层：输入快照如何原子绑定决策结果

**面试官：** 你有了所有版本号，怎样确保日志里的决策不是引用了版本 X、状态却按版本 Y 修改？

**面试者：** 一条命令在事务中读取 `appliedSeq+1` 对应状态及活动 price/config ID，构建不可变工作副本，算出接纳、拒绝或成交；同一事务保存所用 ID、输入摘要、reason code、状态变化和新 appliedSeq。事务提交后这些事实成套存在，提交前任何一项失败都回滚。不能先更新订单，再异步写风险快照；也不能先推进游标再等仓位服务。若处理位置 CAS 失败，丢弃草稿并在新序号重新裁决。对 O1 的审计记录至少能说明 q=2、剩余订单 0、M1、V1、Qmax=4 下 R=400，以及准入 O1 后相应状态为什么 R=700。

## 第 8 层：拆成多个服务时的代价

**面试官：** 业务要求 Risk、Matching 和 Oracle 分别独立扩容，能否让它们只用版本号互相调用？

**面试者：** 版本号本身不提供原子提交。跨服务需要定义授权凭据绑定的账户/风险状态版本、订单、方向、数量、限价带、规则及唯一消费身份，并解决凭据产生后另一个成交或撤单怎样改变其效力。尤其不能凭 TTL 到期自动退款，因为旧 Place 可能迟到；必须有与执行方共同顺序的关闭墓碑，证明旧命令不再能成交。价格服务也要区分来源版本与市场激活版本。拆分的收益是团队和容量独立，代价是增加在途义务、失效重裁、补偿与故障恢复协议。本专题不把它们伪装成现有实现，只说明这是改变架构边界后必须补齐的证明。

## 收束：快照是可复核的证据包

- **讲透的机制：** 风险结果绑定同一逻辑状态、价格证据、配置版本和裁决序号，并与变更共同提交。
- **易错边界：** MVCC 不覆盖外部服务；最新序号不代表新鲜数据；版本号不能使多个系统原子。
- **反例：** 让 q=2.5 的新持仓配上遗漏成交前订单预占的旧订单版本，再用 Mark M1 和 V1 算出“通过”。即便结果数字可复算，输入组合也不对应任何已提交状态，方案不成立。
