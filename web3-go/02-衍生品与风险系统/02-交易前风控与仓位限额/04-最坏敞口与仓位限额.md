# 大问题 4：多方向挂单怎样进入仓位和名义限额？

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| ETH-USDC 线性永续、逐仓 | 以 USDC 计算 ETH 合约盈亏，专用资金只支持这个风险单元。 | 不买入实物 ETH，逐仓外资金也不自动成为可用保证金。 |
| 净仓 q、多空正负号 | 将持仓方向和数量合在一个数里，多为正、空为负。 | q=2 是多两个，q=-1 是空一个，不是亏了一个 ETH。 |
| 活动订单、剩余量 | 已获准、尚未结束的订单；剩余量是未来还可能成交的部分。 | 限额看未成交义务，不能只看已经形成的仓位。 |
| b、s | 普通买单、普通卖单各自的剩余量合计，都是非负数量。 | 它们不是买卖之差，不能先抵消后再检查。 |
| 可达净仓区间 | 在允许的不同成交顺序下，仓位可能落入的数量范围。 | 无 RO 时用 `[q−s,q+b]` 覆盖任一侧先成交的情况。 |
| abs、max、Q* | abs 去掉正负号，max 取最大；Q* 是最大可能绝对仓位。 | 两端哪边离零更远，就要按哪边的风险数量检查。 |
| Qmax、数量限额 | 用 ETH 数量表达的硬上限，不关心当前价格高低。 | 本文教学上限为 4，拟 4.5 就超限。 |
| Mark / m | 用于风险估值的参考价格，不是保证执行价格。 | 当前 m=2,000，价格更新会改变名义额，但不直接改变 ETH 数量。 |
| N*、Nmax、名义限额 | N* 把最坏数量按 Mark 折成 USDC；Nmax 限制这个金额。 | O1 后为 7,000，拟再加 O2 后为 9,000，高于上限 8,000。 |
| Equity、IM、R | 权益含浮盈亏，IM 是持仓初始保证金要求，R 还覆盖挂单义务。 | 资金能覆盖 R，不代表数量和名义限额也通过；IM 不是手续费。 |
| 预占 | 把订单将来可能消耗的风险空间先纳入限制。 | 不是现金扣款，也不是未成交就确认损失。 |
| 普通反向单、穿零 | 方向与当前仓位相反的普通单，可能先平仓再继续开反向仓。 | 多 2 卖 3 可以变空 1，不能仅因“卖出”就认定减险。 |
| Reduce-Only / RO | 每次成交都只能减少当前仓位，不能反手开仓的订单约束。 | 不是普通反向单的别名，仍要在执行时重检。 |
| u、v、RO 分配余量 | 分别是已经分配给 RO 买单、卖单的可平剩余数量。 | 保守区间加入 u、v，不能因 RO 名称就把它从限额中删掉。 |
| 保守上界 | 宁可多留空间，也不漏掉允许路径的外包范围。 | 含 RO 的两个端点不一定都能达到，但不能只凭理想成交顺序缩小它。 |
| OCO、互斥承诺 | OCO 常指“一单成交后取消另一单”，系统必须真正保证两者不同时形成义务。 | 本基线没有这种原子互斥，不能假设买卖单会自动相消。 |
| 被动超限 | 数量没主动增加，因价格或规则变化越过新门槛。 | 要收紧后续资格，不是删除过去已经合法发生的成交。 |
| 部分成交、数量守恒 | 成交一部分后，原单量仍等于已成、已撤、剩余三项之和。 | O1 成交 0.5，仓位加 0.5、余单减 0.5，最坏端点不凭空减少。 |
| 共同事务、版本 | 相关修改一起提交，并说明对应哪一份状态。 | 不能先删订单义务，再异步补仓位，制造虚假的空余额。 |
| API、mutex、owner/fencing | API 是请求入口；mutex 是进程内互斥锁；owner/fencing 确保只有有效处理者能写。 | 多入口仍须共用权威裁决，单进程锁挡不住另一实例重复占额。 |

## 把整篇文章压缩成一个故事

甲持多仓两个 ETH，市场最多允许四个。他挂买一点五后，当前仓位仍是二，但未来可能到三点五。此时再挂买一个，不能因为“现在还只有二”就通过：两张单若都成交会到四点五，按两千参考价折算还达到九千，数量与名义限额都失败。

如果同时挂买一点五和普通卖三个，也不能先把买卖相抵。卖单可能先成交到空一个，也可能只有买单成交到多三点五，所以要检查整个范围。RO 更容易误解：多二、普通卖三、RO 卖二，若 RO 先平仓，普通卖单之后仍可能开出空三；只看普通单就会漏掉这条路径。

因此本文用保守区间覆盖顺序差异，再分别检查数量、名义额和资金。第一单部分成交零点五后，仓位二点五加余单一，端点仍是三点五；撤余单才下降。价格上涨还可能让数量不变的仓位名义超限，这要求限制后续增险，不是回滚旧成交。所有上限均是本文教学参数，不是交易平台统一规则。

**流程位置与核心机制：** 本题覆盖活动订单如何影响未来仓位边界，以及数量上限和名义敞口上限如何独立裁决。初始保证金算法见母题 03；本文不重复其资金需求公式。

沿用 README 的 ETH-USDC 线性永续、单向逐仓案例：当前净仓 q=2 ETH，Mark m=2,000，Qmax=4 ETH，Nmax=8,000 USDC。活动单按当前剩余量计算；主例没有 RO，含 RO 时另按 README 的保守边界处理。

## 第 1 层：为什么检查对象不是已成交仓位

**面试官：** 账户当前只有 2 ETH，低于 4 ETH 上限，为什么还要看未成交订单？

**面试者：** 挂单虽然未改变 q，却给未来成交留下了执行资格。若当前多仓 2 ETH 已有普通买单 1.5 ETH，所有买单都成交时仓位会到 3.5；这时再只看已成交 q 接受另一张 1 ETH 买单，最终可达 4.5 ETH。风险裁决必须覆盖活动订单可能产生的仓位，而不是只统计成交事实。这里的预占不是把资产先扣走，而是将尚未履行的风险义务纳入准入边界。主例 O1 接纳后 `Q*=3.5`，拟加 O2 后 `Q*=4.5`，所以 O2 必须被仓位限额拒绝，即使保证金权益足够。

## 第 2 层：普通买卖挂单的最坏仓位怎样算

**面试官：** 如果同时有买单和卖单，怎么判断最坏净仓？

**面试者：** 令当前有符号仓位 q，普通买单剩余量总和 b，普通卖单剩余量总和 s。假设任一侧的订单可以先后独立成交，可能的净仓区间是 `[q−s, q+b]`。最大绝对仓位为 `Q*=max(abs(q−s),abs(q+b))`；空单场景也要考虑 `abs(q)`，而它已包含在这个区间，因为 b、s 非负。不能把 b 和 s 先互相抵消：q=2、b=1.5、s=3 时，卖单全成可到 -1，买单全成可到 3.5，所以 Q*=3.5；若只看净挂单量 b−s，就会错误地把未来风险当成更小。

## 第 3 层：为什么反向普通单仍可能扩大绝对风险

**面试官：** q=2 时，卖出 3 ETH 明明先平仓，为什么会按风险订单占用？

**面试者：** 普通卖单允许继续成交并穿过零，故全成后是空 1 ETH。是否属于减仓不能只由订单方向猜，必须由独立的 Reduce-Only 执行约束保证。再叠加一张普通买单 2 ETH，可能先卖出到 -1 再买入到 1，也可能卖单仅部分成交；仓位区间和毛数量预占都不能默认两方向相抵。只有在产品明确实现互斥/OCO、能够原子撤销对手义务时，才可采用更紧的联合可达集合；本基线没有 OCO，因此按保守独立成交建模。这个边界也解释了为何普通反向订单和 RO 必须使用不同的资格语义。

## 第 4 层：RO 加入后可达区间为什么要保守扩展

**面试官：** RO 会在仓位变成零时失效，能否先忽略它对区间的影响？

**面试者：** 不能简单忽略，因为一组普通订单可能先改变仓位，再给 RO 创造可平空间。设 RO 卖余量 v、RO 买余量 u，README 采用保守区间 `[q−s−v,q+b+u]`，并按两端绝对值取 Q*。这不是断言两个端点都一定能到达，而是把订单顺序改变后的风险路径纳入上界。例如 q=2、普通卖 3、RO 卖 2：普通卖先成交 2，仓位归零，RO 余量按规则撤销，普通卖余量再成交 1，结果是空 1；但若 RO 先平 2，普通卖余量之后仍可能穿零至空 3。因此只算 `[q−s,q+b]=[-1,2]` 会漏掉一条合法顺序。接纳 RO 若使上界冲突，须按已声明的优先策略同事务撤销冲突普通单并重算。

## 第 5 层：数量限额和名义限额怎样并列检查

**面试官：** 得到 Q* 后，检查 `Q*<=Qmax` 是否就够了？

**面试者：** 不够。数量上限检查 ETH 数量，名义上限按指定风险价格估算 USDC 敞口，本基线是 `N*=m×Q*`，两条硬约束都要通过。主例 O1 后 Q*=3.5、N*=7,000，均通过；再加入 O2 后 Q*=4.5 超过 4，N*=9,000 也超过 8,000，故拒绝。两个门槛需分别记录结果和原因，不能只回一个“额度不足”。它们的业务目的不同：数量限制仓位规模，名义限制美元价值。某些产品还会采用风险档位或更复杂的价格缓冲，那是规则版本变化，不应把教学公式冒充为交易所统一规范。

## 第 6 层：价格变化怎样影响名义限额与存量订单

**面试官：** q 和订单数量没变，Mark 从 2,000 涨到 2,300，会发生什么？

**面试者：** 数量 Q* 不变，但 N*=m×Q* 上升。以 2.5 ETH 仓位为例，Mark 2,000 时名义 5,000；升至 2,300 时为 5,750。若它仍低于 Nmax=8,000，限额通过；若新 Mark 使现存暴露越过 Nmax，系统应标记被动超限并禁止增加风险，按策略重评/撤销可能扩大风险的普通挂单，但不能改写已经发生的成交。价格版本激活与订单重评需有确定生效点；在重评完成前，旧资格不可继续被当成永久有效许可。数量限额不会随 Mark 变化，名义限额则会，因此两个状态要分开呈现。

## 第 7 层：订单剩余量、成交和撤单怎样保持边界连续

**面试官：** O1 成交 0.5 后，为什么不能认为风险占用减少了 0.5 ETH？

**面试者：** 因为同一方向买单成交时，订单剩余从 1.5 减到 1.0，仓位从 2 增到 2.5；最坏端点仍是 3.5，风险只是从“可能成交”转成“已成交”，并未凭空消失。若先删除订单预占再提交仓位更新，会产生短暂 Q*=3.0 的假窗口。共同事务中一起更新后，边界连续；确定撤销余下 1 ETH 后，买单义务归零，Q* 才由 3.5 回落到 2.5。数量守恒核对 `original=filled+remaining+canceled` 是必要的，但还要检查这些分量与权威订单状态同一版本，避免对旧余量重算。

## 第 8 层：高频更新和多个入口怎样避免限额穿透

**面试官：** 两个 API 实例几乎同时看到 Q*=2，都准备各接纳 1.5 ETH，怎么避免合计超限？

**面试者：** 不能依赖各自内存里的订单索引或先读后写的无锁计算。二者必须进入同一风险单元/市场的串行裁决顺序，或使用具备等价线性化语义的条件更新：第一个事务提交订单与预占后，第二个重读新订单集合，计算 Q*=5.0 并拒绝。若用数据库聚合，锁定范围必须覆盖所有影响同一风险单元的写入；仅锁候选订单行无效，因为两笔新订单原本没有共同记录。若采用分片/多 owner，需要共享预算令牌或唯一 owner/fencing，并证明失败、迁移和迟到写入不会重复消费额度。Go mutex 只约束一个进程，不能替代数据库或跨实例的裁决权。

## 收束：限额计算是未来路径的边界证明

- **讲透的机制：** 用有符号净仓和活动订单剩余量构造保守可达边界；数量、名义和资金预算分别裁决。
- **易错边界：** 普通反向单可能穿零；RO 会受仓位顺序影响；Mark 变化可令名义额被动超限；部分成交是订单义务向仓位的转换。
- **反例：** q=2、普通卖 3、RO 卖 2，只计算普通单区间会得到下界 -1，但允许 RO 先平仓、普通卖再开空的路径可到 -3。若限额判断漏掉 RO 分配余量，便没有覆盖实际允许的执行顺序。
