# 大问题 08：部分成交、撤单怎样转换和释放风险占用？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| ETH-USDC 永续、逐仓 | 用 USDC 计算 ETH 合约盈亏，专用现金只支持当前风险单元。 | 不交割 ETH、不支付名义本金，逐仓外资金不自动可用。 |
| q、C、A | q 是带方向的持仓，C 是剩余入场成本，A 是平均入场价。 | 主例成交后 q=2.5、C=5,000、A=2,000，成本不是现金扣款。 |
| B、U、E | B 是已记账现金，U 是未实现盈亏，E 是二者相加的权益。 | 本文同价零费用时 B=E=1,000、U=0，不是所有成交都这样。 |
| Mark / m、成交价 | Mark 是风险估值参考价；成交价才是实际确定交易义务的价格。 | 主例二者都为 2,000 只是教学设定，不是 Mark 保证执行价。 |
| IM、r | IM 是初始保证金要求，r 是本文用于计算的比例。 | 原持仓需求 400，新增持仓后为 500；都不是手续费。 |
| O1、O2 | 两笔独立请求，O1 买 1.5，O2 另买 1。 | O2 被拒不应改变 O1 的数量或占用。 |
| original、filled | original 是原单总量，filled 是累计已经成交的量。 | O1 原始量 1.5，部分成交后 filled=0.5。 |
| remaining、canceled | remaining 是仍可成交的量，canceled 是已确定撤掉的量。 | 撤余 1 后 remaining=0、canceled=1，不能把已成交 0.5 算成撤销。 |
| 数量守恒 | 每一份原始订单量都必须有去向，不能凭空多出或消失。 | 始终核对原始量等于已成、已撤、剩余三项之和。 |
| b、G | b 是普通买单余量合计；本例 G 是持仓绝对数量加普通订单余量。 | 成交 0.5 后 q 增、b 减，G 仍为 3.5。 |
| R、风险预占 | R 是支持持仓和活动订单的总风险需求，预占是把未来义务提前纳入预算。 | R=700 不表示钱包已扣 700，更不表示已亏 700。 |
| 仓位需求、订单需求 | 将总需求按已形成仓位与未来订单义务拆开理解。 | 部分成交使 400+300 变成 500+200，总量没有下降。 |
| E−R、可用风险空间 | 权益扣除总风险需求后，还能支持多少新增风险。 | 挂单时为 300、撤余后为 500，不能当成可提现余额。 |
| Q*、Qmax、Nmax | 最坏绝对仓位、数量上限、名义金额上限。 | O2 拟产生 4.5 ETH、9,000 USDC，超过教学上限 4、8,000。 |
| L、不利价差缓冲 | 普通限价单可能按比 Mark 不利的价格成交，提前为差额留空间。 | 限价不同于 Mark 时要重算；撤单能去掉余单缓冲，却不能撤销已成交损失。 |
| marketSeq、权威撤单 | 共同序号决定成交和撤单先后；权威撤单是系统已提交关闭事实。 | 发送撤单或页面隐藏订单，不足以提前释放预占。 |
| 事务 T、原子转换 | 将订单余量减少与持仓增加作为同一组业务修改保存。 | 防止先释放订单需求、稍后才补仓位需求的虚假空窗。 |
| RequestKey、载荷摘要 | RequestKey 标识原请求，摘要标识该请求的业务内容。 | 同键重试返回原结果，不能因重投再接纳被拒的 O2。 |
| tradeId、提交未知 | tradeId 标识唯一成交；提交确认丢失时不能确定成功与否。 | 先查询再恢复，不能因未收到回报就把 q 再加 0.5。 |
| 幂等、整体重算 | 幂等是重复请求不多产生效果；重算从当前真实订单和仓位得出 R。 | 重复撤单不是再次执行“可用额度加 200”。 |
| 定点精度、向上舍入 | 用固定小数单位的整数运算，并保守地把需求向上取整。 | 不能每笔先向下舍入，凑出不足一个最小金额单位的预算缺口。 |
| Outbox、查询投影 | 同事务保存的待发通知，以及之后生成的页面视图。 | 页面落后只影响可见性，不授权人工改余额或再次释放。 |

## 把整篇文章压缩成一个故事

甲有一千 USDC 逐仓现金，持多仓两个 ETH，挂买一点五。按本文同价、零费用的教学规则，总风险需求从四百升到七百，可用风险空间三百，钱包没有扣走七百。另一笔买一个虽只让拟需求达到九百，却会把最坏仓位推到四点五，所以因限额被拒，原单不变。

第一单成交零点五后，仓位升到二点五，余单降到一个。原来四百持仓需求加三百订单需求，变成五百加二百，总量仍七百。不能看见余单少了三分之一，就向账户“退”一百，否则新增持仓还没被覆盖，下一笔请求已经用掉假空间。

用户随后撤单，只有共同顺序中正式关闭余下一个，总需求才降为五百。最终一点五等于成交零点五加撤销一，现金仍是一千，没有两百退款流水。若实际价格不同，还须重算权益和价差缓冲，不能推广七百恒定的结论；重复撤单或回包超时也只能找回原事实，不能多释放一次。

[返回专题总览](README.md)

**范围与前提：** 沿用 README 主案例：`q=2、B=E=1,000、m=2,000、r=10%`，O1 为普通买 1.5@2,000，O2 买 1 被拒。随后 O1 成交 0.5，余 1，再权威撤销余量。主案例零费用、价格不变、成交价等于 Mark；现金不是风险预占。

**流程位置与核心机制：** 本题追踪活动订单义务如何在部分成交时转成持仓义务、撤单时只释放未成交量，以及订单数量守恒与风险金额变化如何在同一事务 T 中保持一致。

## 第 1 层：O1 接纳后风险占用是多少？

**面试官：** q=2、O1 买 1.5@2,000，使用 README 的毛需求公式，接纳后发生了什么？

**面试者：** O1 是普通买单，活动余量 `b=1.5`，没有普通卖单，因此 `G=abs(2)+1.5=3.5`。固定 Mark 下 `R=10%×2,000×3.5=700 USDC`，权益 E 仍是 1,000，未用缓冲为 300。它不是从现金扣 700，而是建立受限执行资格；数量上限最坏仓位为 3.5，也低于 4。后续撤销或成交只能按实际余量转换。交易事务还应保存订单原始量1.5、已成交0、已撤0和剩余1.5，供后续两种状态变化分别更新。不能只记一笔700的账户级冻结，因为同时挂着多张单时无法知道哪个成交或撤销释放了哪份义务。R 的逐单分解可展示仓位需求400、订单毛需求300，便于核对，但两项仍是风险计算结果，不是两个现金子账户。

## 第 2 层：O2 为什么因限额拒绝，不是因为钱不够？

**面试官：** O1 活动时再申请 O2 买 1，为什么不能只检查 `E>=R`？

**面试者：** 若接纳，普通买单总余量变 2.5，`G=4.5`，故 `R=900`，现金/权益 1,000 的确足够；但 `Q*=4.5>Qmax=4`，名义敞口 `4.5×2,000=9,000>Nmax=8,000`。所以 O2 必须拒绝，且不改 O1 的订单、剩余量或 R。资金足够只通过资金检查，不能覆盖独立的数量与名义限额。拒绝决定要与 O2 的请求键、载荷摘要和采用的 V1/M1 证据一起持久化；如果客户端因超时重试同一请求，只返回原拒绝结果，不得先将 O1 余量写成2.5再回滚其中一部分。若其后条件改变，需要用户用新意图重新申请。对外原因码应指出 Qmax 与 Nmax 哪项失败，而不能返回“保证金不足”，否则调用方会错误地重复补钱。

## 第 3 层：部分成交 0.5 时，订单和仓位如何转换？

**面试官：** O1 随后成交 0.5@2,000，成交提交后 `q`、余单、风险需求分别是多少？

**面试者：** 同一事务 T 中 O1 累计成交变 0.5、剩余变 1；甲的多仓从 2 变为 2.5。毛量 `G=abs(2.5)+1=3.5`，所以 R 仍为 700。原来订单的 0.5 义务没有消失，而是从“可能成交的挂单”转成“已持仓风险”；余下 1 仍是订单风险。该固定价零费用场景下，B、U、E 均不变，不能按余量减少就释放 100 的保证金。持仓成本同时从4,000变为5,000，均价仍为2,000；这项状态变化和成交记录一起落账，之后按仓位的未实现盈亏公式计算权益。订单累计成交只增加一次，若T提交结果未知则先查tradeId，不能因没有收到回报而再把q加0.5。

## 第 4 层：为什么不能简单按剩余量比例释放占用？

**面试官：** 订单余量从 1.5 降到 1，按剩余数量比例是否应该释放三分之一的预占？

**面试者：** 不能把独立的订单 R 当现金押金按比例退款。成交 0.5 已使仓位从 2 增到 2.5，仓位需求从 400 增到 500；订单余量需求从 300 降到 200，总 R 仍是 700。精确数值变化是“订单义务减少、持仓义务增加”，而非总需求降低。撤单与成交都要按整数精度和规定舍入各自重算，不能先把每笔金额向下舍入再汇总，导致预算少占一个USDC最小单位。若限价与 Mark 不同，还需把已实现/未实现权益变化和 L 的实际转移一起重算，不能只乘剩余比。成交后旧订单预算与新仓位预算是同一风险聚合的两部分，不能先释放旧额再异步登记新额；否则两步之间会错误放行另一笔订单。固定Mark和零费用仅让该例两部分恰好等量转移，不应推广为所有成交金额恒定。

## 第 5 层：撤单请求何时能释放剩余额度？

**面试官：** 客户端发送撤单后立即看到成功，是否可以先把剩余 1 的风险占用释放？

**面试者：** 不可以。撤单命令进入同一市场顺序，在 T 中与成交竞争。若撤单先提交，O1 剩余变 0、撤销量增加 1，执行资格关闭；若匹配先提交了部分成交，撤单只能处理更新后的实际余量。等待权威裁决期间仍保留预占，因为订单可能仍被撮合引用。只有终态撤单提交后才释放那 1 ETH 的未来执行义务。撤单服务应返回“处理中”而非立即宣称已撤；执行端确认订单不再可引用后，T 才写canceled数量与终态结果。客户端页面即使乐观隐藏订单，也不能据此重新把700风险占用减掉。

## 第 6 层：最终撤余量后各项数值如何闭合？

**面试官：** O1 成交 0.5 后成功撤掉余下 1，给出最终数量、R 和现金。

**面试者：** 最终 `q=2.5`，O1 原始 1.5 满足 `1.5=0.5 成交+1.0 撤销+0 余量`。没有活动普通订单时 `G=2.5`，所以 `R=10%×2,000×2.5=500`；现金仍为 1,000，权益仍为 1,000。R 从 700 降到 500，原因是撤销了未成交义务；并非把 200 现金转回账户。仓位 IM 是 500，剩余订单 R 为零。撤单后无普通余量，L也为零；即使原限价为2,100，剩余订单的损失缓冲也随权威撤销消失，但已成交价差造成的现金或未实现损失必须保留，不能一并撤销。成交经济结果是 q=2.5、C=5,000、A=2,000；撤单只关闭剩余1，不增加现金分录。账务流水只反映真实成交与费用，这里费用为零，因此B保持1,000，页面上的风险需求下降不产生一笔“退款”流水。

## 第 7 层：失败窗口和重复撤单怎样维持数量守恒？

**面试官：** T 提交后回包丢失，客户端重复撤单；或者提交前进程崩溃，怎样避免重复释放？

**面试者：** 撤单命令使用稳定身份，结果与订单更新、风险聚合、处理位置及 Outbox 在 T 中提交。提交后重试返回原结果，不再对 R 做第二次减法；提交前失败则订单余量仍为 1，预占也仍在，恢复后重放同一命令。重放前须依据处理游标确认撤单命令确实未提交，避免在主库短暂不可读时将同一关闭意图误判为新动作。派生聚合可以重算，但权威订单需满足 `original=filled+canceled+remaining`，且 `remaining≥0`；不能把“释放额度”实现为非幂等的独立余额加法。风险聚合若是增量维护，恢复时还应从订单明细重新求和并与索引版本比对。若成交事件与撤单事件都在日志中，恢复严格按marketSeq重放，例如先成交0.2再撤0.8，不能因撤单消息先抵达消费者就倒置业务顺序；恢复结果仍须是filled0.7、canceled0.8、remaining0。

## 第 8 层：怎样用反例证明风险转换和资金口径正确？

**面试官：** 最后给出最小的验收链，并指出常见错误。

**面试者：** 依次接纳O1、拒绝O2、成交0.5、撤余1，检查`(q=2,b=1.5,R=700)`、O2无效果、`(q=2.5,b=1,R=700)`、`(q=2.5,b=0,R=500)`，现金始终1,000。若fill后R=600，是只减订单未加持仓；若撤单后现金=1,200，是把风险需求错记成现金退款。边界验证再把撤单与0.4成交按相反marketSeq各跑一次：成交先则只撤0.6，撤单先则后续成交拒绝；两条结果都满足数量恒等式，重复投递也不能多加canceled。并在成交价不等于Mark时重算权益及L，确认固定案例R恒定并非通用假设；手推时同时保留成交记录、订单终态与风险版本，核对它们来自同一次裁决，不因查询投影暂时落后就直接修改余额或释放额度。

## 机制、易错与反例收束

- **机制：** 成交把订单义务转成持仓义务，撤单只消除权威裁决后未成交的余量；每次变更在 T 中重算 R 并满足 `original=filled+canceled+remaining`。
- **易错：** 按成交比例直接释放风险、按撤单请求先释放、把 R 当现金扣款，或重复撤单时再次做减法。
- **反例：** O1 从 `q=2,b=1.5,R=700` 成交 0.5 后必须是 `q=2.5,b=1,R=700`，不是 R=600；撤余后 R=500、现金仍 1,000。
