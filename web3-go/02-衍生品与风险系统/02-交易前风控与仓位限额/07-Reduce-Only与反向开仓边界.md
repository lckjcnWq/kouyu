# 大问题 07：多笔 Reduce-Only 怎样不抢同一份可平量？

<!-- 大白话导读开始 -->

## 先看懂：关键词大白话解释

| 关键词 | 大白话解释 | 在本文里怎么理解 |
|---|---|---|
| 单向逐仓永续 | 一个带方向的净仓，用专用资金支持合约风险，不交割 ETH。 | q=2 是多两个 ETH 的合约仓位，外部资金不会自动加入本仓。 |
| 普通反向单 | 下单方向与当前仓位相反，但没有禁止继续开反向仓的约束。 | 多 2 卖 3，可先平 2 再开空 1，并非必然减险。 |
| Reduce-Only / RO | 强制每笔成交只能减少现有仓位、不许反手的订单语义。 | 不是 API 上勾一个标签就完事，接纳和执行都要检查。 |
| q、abs(q)、仓位符号 | q 包含方向；abs(q) 是不带方向的数量；符号区分多与空。 | q=0 没仓可平，q 从正变负说明已翻成空头。 |
| 穿零、反手 | 平光原方向后继续成交，建立相反方向仓位。 | 普通单可在合法门禁下这样做，RO 不允许。 |
| 可平量、分配余量 | 当前仓位最多能关闭多少，以及其中已经分给某张 RO 的份额。 | 多 2 不能给两张各 1.5 的 RO 同时承诺总共 3 的可平资格。 |
| 接纳顺序、超额拒绝 | 用确定先后分配有限额度，不够就按已声明规则拒绝。 | 本文新 RO 超额整单拒绝，不暗中替用户把数量缩小。 |
| b/s、u/v | b/s 是普通买卖余量，u/v 是已分配的 RO 买卖余量。 | 都是非负数，分别放入保守区间，不能先互相抵消。 |
| Q*、保守区间 | Q* 是区间两端及当前仓位中最大的绝对数量；区间覆盖允许的风险路径。 | 多 2、普通卖 3、RO 卖 2，保守下界是 -3，不是 -1。 |
| Qmax、Nmax | 允许的最大数量及按 Mark 估值的名义敞口上限。 | 教学上限为 4 ETH、8,000 USDC，RO 加入也可能触发冲突重裁。 |
| B、E、C | B 是已记账现金，E 是含浮盈亏的权益，C 是剩余持仓入场成本。 | C=4,000 不是四千现货付款；主例同价时 B=E=1,000。 |
| Mark、成交价、限价 | Mark 用于估值，成交价是实际交换义务的价格，限价限制用户可接受价格。 | 三者不同；可信 Mark 不等于差价很大的成交也安全。 |
| G、R、L | G 是持仓加普通余单的毛数量，R 是保守总需求，L 是普通单不利价差缓冲。 | RO 不为普通订单提前减免 R，尚未成交的减仓不能当作信用。 |
| MMpos、H | MMpos 是当前持仓维持保证金要求；H 是权益减 MMpos 的健康缓冲。 | 主例 E=1,000、MMpos=200，所以 H=800；它不是可用开仓额度。 |
| H'≥H、模拟后态 | 撇号表示候选成交后；要求健康缓冲不下降，先模拟再决定是否提交。 | 卖 1 于 1,600 会使 H 从 800 降到 500，拒绝时不能真写入亏损后余额。 |
| IM、E≥R | IM 是初始保证金要求；E≥R 是普通开仓资金门槛。 | RO 不机械套普通开仓门槛，但仍受价格、方向、可平量与 H 约束。 |
| 尾部整单撤销 | 仓位变少后，优先保留较早 RO，不支持的后续 RO 整单结束。 | 多仓只剩 1.2 时，先到 A=1 保留、后到 B=1 撤销，不自动改为 0.2。 |
| 旧方向资格失效 | 原来依附多仓的卖 RO，不能改用来扩大后来形成的空仓。 | 普通成交从 +2 直接到 -1 时，同事务撤旧 RO，不必等一次 q=0 事件。 |
| 冲突普通单、资本变体 | 为容纳新 RO，按声明策略先撤造成限额冲突的普通单；变体单独更改假设。 | 普通卖 4.1 的例子另设现金 5,000，不能套回主例 1,000 宣称可接纳。 |
| NORMAL / REDUCE_ONLY / CANCEL_ONLY | 正常交易、仅受约束减仓、禁止新成交三种状态。 | 价格无效进入最后一种，RO 也不成交；并非所有保护都允许减仓。 |
| 事务 T、数量守恒、Outbox | T 让相关修改一起成立；数量守恒保留已成已撤余量；Outbox 负责发已提交回报。 | 自动撤尾单和仓位变化同次提交，重试不复活旧资格。 |
| 独立清算路径 | 协议授权的风险处置流程，权限与普通用户 RO 不同。 | 提交处置请求不等于已经强平，RO 门禁也不替代清算规则。 |

## 把整篇文章压缩成一个故事

甲持有两个 ETH 多仓，想卖出离场。普通卖三个可以平掉两个后再开空一个；RO 才承诺不反手。因此两张各一点五的 RO 不能各自看见“有两个可平”就都通过，系统要按接纳顺序分配这两个的额度，超额新申请整单拒绝。

这还不够。若同时挂普通卖三个与 RO 卖两个，RO 先平光后，普通单仍可能开出空三个，所以 RO 不能从仓位限额中简单删掉，也不能给普通订单抵扣保证金。之后仓位变小，超额尾单要同事务撤销；若普通成交直接把多仓翻为空仓，旧卖 RO 立即失效，不能等下一次多仓出现再复活。

最后还看成交价格。按本文教学主例，权益一千、维持保证金二百，健康缓冲八百；若卖一个成交于一千六百，权益降到六百、维持保证金降到一百，缓冲反而只剩五百，应拒绝。只减数量不保证减险，可信价格失效时更要停掉 RO 成交；已获分配额度从来不是保证成交的通行证。

[返回专题总览](README.md)

**范围与前提：** 沿用 README 的单向逐仓永续、事务 T 和 `Q*` 保守区间。RO 可平量预占与普通订单毛需求 `R` 分开；RO 不提供普通单保证金抵扣。RO 执行必须方向相反、不穿零、价格有效且 `H=E-MMpos` 不下降。接纳 RO 若影响普通订单限额，先在同事务撤冲突普通单；仓位变化后超额尾部旧 RO 整单撤销。

**流程位置与核心机制：** 聚焦“减仓意图”如何保持为减仓，避免多单重复占用同一仓位、先后成交导致反向开仓，并明确 RO 与普通相反方向订单不能混作净额抵消。

## 第 1 层：反向普通订单为什么不等于 Reduce-Only？

**面试官：** 账户持多 2 ETH，提交卖出 3 ETH，方向与仓位相反，为什么不能直接称为 RO？

**面试者：** 普通卖3可以先卖掉2 ETH多仓，再卖1开空，结果穿过零；“反向”只说明下单方向，不限制成交后的状态。RO是执行约束，要求仓位非零、方向相反且任何成交量不穿零，不能只看受理时的仓位。q=2时普通卖3成交后会成为q=-1，正是反例。实现上把`reduceOnly`作为订单语义和审计字段持久化，并在每笔撮合重新验证；API标签不构成门禁。q=0时RO卖单没有可平额度，应拒绝，不能退化为普通开空单。普通卖3可分两次成交，先卖2平多、再卖1开空；剩余普通卖量在重检通过时仍可执行。RO卖3则在q=2时直接因超额拒绝，不能冒充同一种执行语义。

## 第 2 层：多张 RO 为什么必须分配可平量？

**面试官：** 你说 RO 每笔都不能穿零；q=2 时两张 RO 卖单各申请 1.5，单独看都未超仓位，为什么还不能都接纳？

**面试者：** 两张各自校验会重复使用同一份 2 ETH 可平量，总余量却是 3。若两张都按普通订单簿可成交，先卖 1.5 后仓位只剩 0.5，另一张仍有 1.5，就有穿零风险。因此接纳时维护确定的 RO 可平量分配；本基线按接纳顺序分配，现有仓位最多支持 RO 余量合计 2。超额新 RO 请求整体拒绝，不悄悄截成较小数量。分配记录要随订单剩余量同步减少，并能说明撤单或成交释放了多少份额；否则重试会再次拿到同一配额。遇到多个入口时也必须进 T 排序，不允许各自维护局部的“可平仓位”。此分配是保守承诺，不代表撮合优先级必须改变；若较后 RO 先成交，仍按其实际成交扣减自身配额并在 T 后对剩余订单按原分配顺序重裁。

## 第 3 层：RO 进入仓位限额时为何不能忽略？

**面试官：** RO 分配合计已不超过 abs(q)，是否就可以在最坏可达仓位 Q* 中忽略 RO，只计算普通订单？

**面试者：** 不行，必须用 README 的保守区间 `[q-s-v, q+b+u]`，普通单与 RO 都纳入但不假装它们会互斥抵消。例子中 q=2、普通卖余量 s=3、RO 卖余量 v=2、买单为零，区间是 `[2-3-2,2]=[-3,2]`，所以 Q*=3；只算普通单会得到下端 -1，漏掉 RO 先平仓后普通单开空的路径。该区间是保守上界，不声称端点必然可达，也不能因执行时会重裁就在准入时忽略 RO。u 是 RO 买余量、b 是普通买余量，均为非负量，计算时取两个端点绝对值与当前仓位绝对值的最大值。它同时用于数量和 Mark 名义限额；不是把订单方向净额相抵后的单一净仓估计。若多头 q=2，普通买 b=0.5、普通卖 s=3，RO 卖 v=2、RO 买 u=0，则两端为 -3 与 2.5，Q*=3；即使 RO 会被重裁，按此基线准入仍使用这个保守上界。

## 第 4 层：接纳新 RO 导致超限，应撤谁？

**面试官：** 沿用这个保守区间，另起变体把现金改为 B=E=5,000，已有普通卖 4.1@2,000；再申请 RO 卖 2 导致候选范围超限，撤谁？

**面试者：** 这是明确的资本变体，其余 Mark=2,000、Qmax=4、Nmax=8,000 不变。普通卖4.1时区间为[-2.1,2]、Q*=2.1、N=4,200，毛需求R=1,220，现金足够。加入RO卖2后区间[-4.1,2]、Q*=4.1、N=8,200，超限；T必须先撤冲突普通单，再重算并接纳RO，否则拒绝。撤单与接纳同事务。本方案先撤与新RO同方向的冲突普通单，必要时按确定顺序撤最晚普通单直到支持限额；新RO可平量若超额仍直接拒绝。若只是既有仓位被动超限，则关闭普通增险资格，允许不扩大绝对仓位的RO按门禁减险。撤单原因与被移除的订单ID须随新RO结果一起持久化。

## 第 5 层：普通单和 RO 的保证金预算怎样分开？

**面试官：** 你会在同一 T 撤冲突普通单并重算 R；能否干脆用 RO 抵扣普通单预算，少撤几张单？

**面试者：** README 的保证金预算对现有仓位和全部普通订单按毛数量计算，`G=abs(q)+b+s`，另计普通订单不利限价损失 L；R 不给 RO 减免信用。RO 可平量分配解决的是“不穿零”，不是保证其一定成交；它可能没有有效价格，也可能因健康缓冲而暂不能执行。若拿 RO 抵扣普通单，普通单可能先成交而 RO 未成交，形成没有抵扣依据的风险敞口。按主例 q=2、O1 普通买1.5，普通毛量G=3.5、R=700；另外接纳 RO 不会把这700下调。若RO卖单被价格门禁挡住，普通单仍承担原需求，只有撤销普通单或其余量变化后才重新计算R。RO 成交后 q 实际减小，下一状态的仓位需求可以随事实降低，但那是已发生减仓的效果，不是未成交 RO 带来的事前信用。

## 第 6 层：普通单成交后如何裁掉超额 RO？

**面试官：** 你说只有实际 q 变化才重算；回到 q=2、RO 卖 A=1/B=1 的独立例子，普通成交改变仓位后，旧分配怎样处理？

**面试者：** 同一 T 中先把仓位改为 2.5，再按原优先级重算可平量。A、B 都是反向卖单，2 ETH RO 余量仍不超过当前多仓 2.5，所以都可保留；但若普通卖单或其他处置使仓位变为 1.2，余量总和 2 就超额。系统保留先接纳的 A=1，把尾部 B=1 整单撤销，不自动把 B 改为 0.2，且撤销结果、预占释放与新仓位同事务提交。部分成交的 RO 本身也先减少其 remaining，再与其他 RO 顺序比较；例如 A 已成交0.4且还余0.6、B余1，总分配1.6，仓位1.2时只整单撤尾部B。原订单量守恒仍保留已成交数，不把自动撤销伪造成改量。自动撤尾单的原因与旧、新分配版本要进结果与 Outbox；若用户稍后重试被撤 B，不得恢复其旧1 ETH资格，必须以当前仓位重新申请。

## 第 7 层：RO 执行时为何还需价格和健康门禁？

**面试官：** 保留的 RO 已有可平额度，仍不穿零；为什么成交前还要检查实际价格和 H=E-MMpos？

**面试者：** 数量下降不代表健康缓冲必然改善。按主例初始 `B=E=1,000、q=2、C=4,000、Mark=2,000`，`MMpos=200、H=800`。若 RO 卖 1 的有效成交价是 1,600，释放成本 2,000 并实现亏损 400 后，`B'=E'=600、q'=1、MMpos'=100、H'=500`，小于原 H，必须拒绝该 RO 成交。每笔还要检查价格有效、方向相反、成交量不超过当前仓位及分配余量；多笔按新 H 逐笔重算，不能复用挂单时的旧检查。这里价格有效指有可信 Mark 和满足订单限价的候选成交价，并不等于 H 门槛自然通过。若以2,000卖1，权益仍1,000、MMpos减至100、H升到900，就可通过健康缓冲这道检查；两种候选价格应给出不同裁决。拒绝时只是工作副本的模拟后态，不能把600余额或q=1实际写入。

## 第 8 层：价格无效时 RO 能否作为紧急平仓通道？

**面试官：** H 门禁依赖可信 Mark；若价格失效进入 CANCEL_ONLY，能否为了紧急减仓而例外放行 RO？

**面试者：** 本专题明确价格无效时进入 `CANCEL_ONLY`，该模式禁止一切新成交，包括 RO；只允许撤单和安全管理动作。没有可信价格就无法检查执行价保护和 H 是否下降，放行可能把无法估值的损失当作安全减仓。若协议清算有独立强制执行权限，那是另一条明确规则和职责，不是把无效价格下的普通 RO 偷偷豁免。举例价格源断连且上一笔 Mark=2,000 已过质量阈值，即便 RO 卖1的限价为1,900，也不能拿限价替代公平估值计算实际健康变化；必须阻断并返回不可执行原因，仓位和成交量保持原值。恢复价格后还需按新价格、模式和仓位重裁这张RO；之前挂着不代表自动立即成交，尤其不能用恢复前的 H 作为继续执行的依据。

## 第 9 层：RO 旧单如何避免在反向仓位复活？

**面试官：** 有效价格恢复后你会重裁旧 RO；若普通卖 3 在一笔成交中让 q 从多 2 直接翻为空头 -1，没有持久 q=0 中间态，何时撤旧 RO？

**面试者：** 不能等一个持久的 q=0 状态，因为这笔普通成交可以直接跨零。T 在任何成交后比较变更前后的仓位符号；若 q 变为零或符号翻转，就在同一事务撤销所有依附旧方向的 RO，并重算分配与风险区间。旧卖 RO 不能在 -1 空仓上复活为开空单；新的平空请求要按新方向、新意图准入。该撤销必须与普通成交共同提交，避免跨零后旧 RO 被后续撮合消费。例如旧RO卖单余1时，普通卖3使+2直接变-1，剩余1应计入 canceled 并写入终态理由“仓位方向失效”；不是把它继续保留等下一次多仓出现后复活。

## 第 10 层：怎样验证 RO 既不穿零也不授信？

**面试官：** 旧方向 RO 在跨零的 T 中关闭了，怎样用同一组边界案例验证它不复活，同时没有为普通单错误授信？

**面试者：** 从 q=2 开始，先接纳 RO 卖 2，再申请 RO 卖 0.1，后者必须拒绝；另放置普通卖 3，保守区间仍须算到 -3，不能因 RO 标签把它缩成 -1。让 RO 以低于有效保护的价格触发，必须阻断成交并保持订单/持仓不变；再改变仓位使旧 RO 余量超额，确认尾部整单撤销。收束机制是额度分配、保守区间、逐笔门禁；易错点是按单独校验或方向推断安全；q=2、普通卖3、RO卖2 是反例。还要将普通卖3改成一笔成交，验证 q 从 +2 直接变为 -1 时在同一 T 撤掉旧 RO，不能等待 q=0 事件；并将 Mark 无效注入执行前，确认系统进 CANCEL_ONLY 且无成交。最后用普通卖4.1、RO卖2的资金变体核对加入RO后 Q*=4.1、N=8,200，并确认同事务先撤冲突普通单才可继续评估RO，测试范围覆盖了仓位、价格和限额三类边界。

## 机制、易错与反例收束

- **机制：** RO 按仓位方向分配可平余量，普通与 RO 同时进入 `[q-s-v,q+b+u]`；成交后重检价格与 `H`，仓位归零或翻号时同事务撤旧方向资格。
- **易错：** 将反向普通单当 RO、遗漏保守区间中的 RO、把 RO 当普通单 R 的信用，或等 q=0 持久出现才撤旧单；直接穿零时不会有这个中间状态。
- **反例：** q=2、普通卖 3、RO 卖 2 的可达上界包含 -3；若忽略 RO 只算 -1。再用 q=2、卖价 1,600 的 RO 测 H：H 从 800 降至 500，必须拒绝。
